
### 缺少或意外的标记

另一个常见的错误是忘记完成复合命令，例如 `if` 或 `while`。让我们看看如果移除 `if` 命令中 `test` 之后的分号会发生什么：

```bash
#!/bin/bash

# trouble: 演示常见错误的脚本

number=1

if [ $number = 1 ] then

    echo "Number is equal to 1"

else

    echo "Number is not equal to 1."

fi
```

结果是：

```bash
[me@linuxbox ~$ trouble: syntax unexpected token `else'

/home/me/bin/trouble: line 9: error near unexpected token 'else'
```

（注：此处根据原文逻辑翻译，原文中存在大量 OCR 错误导致的重复说明，翻译时已保持逻辑一致性）

在编程时，验证假设是重要的。这意味着仔细评估脚本所使用的程序和命令的退出状态。这是一个基于真实故事的示例，用于防御性编程。

让我们来看看设计可以改进的一些方法。首先，通过引号确保 `dir_name` 变量只展开为单个单词，并让 `rm` 的执行取决于 `cd` 是否成功，这可能是明智的。

```bash
cd "$dir_name" && rm *
```

这样一来，如果 `cd` 命令执行失败，`rm` 命令就不会执行。这种方法虽然更好，但仍然留下了变量 `dir_name` 未设置或为空的可能性，这可能导致用户主目录下的文件被删除。也可以通过检查 `dir_name` 是否确实包含一个存在目录的名称来实现这一点。

```bash
[[ "$dir_name" ]] && cd "$dir_name" && rm *
```

通常，当发生如之前所示的情况时，包含能够终止脚本并报告错误的逻辑将是最好的。

```bash
# 删除 dir_name 目录中的文件

if [[ ! -d "$dir_name" ]]; then

    echo "No such directory: '$dir_name'" >2

    exit 1

fi

if ! cd "$dir_name"; then

    echo "Cannot cd to '$dir_name'" >2

    exit 1

fi

if ! rm *; then

    echo "File deletion failed. Check results" >2

    exit 1

fi
```

在这里，我们既检查了名称（确保它是一个存在的目录），也检查了 `cd` 命令是否成功。如果其中任何一个失败，都会向标准错误发送一条描述性的错误信息，并带有退出状态终止以表示失败。

# 注意文件名

这个文件删除脚本还有另一个更隐晦但可能非常危险的问题。在我看来，Unix（以及类 Unix 系统）在文件名方面存在一个严重的设计缺陷：文件名中只有两个字符不能包含。第一个是 `/` 字符，因为它用于分隔路径中的元素；第二个是空字符（零字节），它在内部用于标记字符串的结束。其他所有内容都是合，包括空格、制表符、换行符、回车等。

特别关注的是开头的连字符。例如，创建一个名为 `-rf ~` 的文件名是完全合法的。考虑一下当该文件名传递给 `rm` 时会发生什么。

为了防止这个问题，我们希望将文件删除脚本中的 `rm` 命令从：

```bash
rm *
```

改为以下内容：

```bash
rm ./*
```

这将防止以连字符开头的文件名被解释为命令选项。作为一条通用规则，始终在通配符（如 `*`）之前加上 `./`，以防止命令误解。这包括 `*.pdf` 和 `???.mp3` 等内容。

# 可移植文件名

为了确保文件名在多个平台之间具有可移植性（即不同类型的计算机和操作系统），需要注意限制文件名中包含的字符。有一个名为 POSIX 可移植文件名字符集（POSIX Portable Filename Character Set）的标准，可以使用它可以最大地提高文件名在不同系统中工作的概率。该标准非常简单。允许的字符只有大写字母 A-Z、小写字母 a-z、数字 0-9、点 (`.`)、连字符 (`-`) 和下划线 (`_`)。该标准建议文件名不要以连字符开头。

# 验证输入

良好编程的一个通用规则是，如果程序接受输入，它必须能够处理收到的任何内容。这通常意味着输入必须经过仔细筛选，以确保只接受有效输入进行后续处理。我们在上一章学习 `read` 命令时看到过这样一个例子。一个脚本包含以下测试来验证菜单选择：

```bash
[[ $REPLY =~ ^[0-3]$ ]]
```

这个测试非常具体。只有当用户输入的字符串是零到三之间的数字时，它才会返回零退出状态。其他任何内容都不会被接受。有时这类测试写起来可能具有挑战性，但为了产生高质量的脚本，这种努力是必要的。

# 设计是时间的函数

当我还在大学学习工业设计时，一位明智的教授说，项目的设计程度取决于设计者投入的时间。如果你给你五分钟来设计一个“杀死苍蝇”的设备，你会设计一个苍蝇拍。如果你给你五月，你可能会设计出一个激光引导的“防蝇系统”。

同样的原理也适用于编程。有时，如果脚本只使用一次且仅供程序员使用，那么一个“快速粗略”的脚本就可以了。这种脚本很常见，应该快速开发以提高经济效益。此类脚本不需要大量的注释和防御性检查。另一方面，如果脚本打算用于生产环境，即一个反复用于重要任务或被多个用户使用的脚本，则需要更仔细的开发。

## 测试

测试是每种软件开发（包括脚本）中的一个重要步骤。开源世界有一句话叫“早发布，经常发布”，这反映了这一事实。通过早期和频繁发布，软件可以获得更多使用和测试的机会。经验表明，如果在开发周期早期发现错误，它们会更容易找到，修复成本也低得多。

在第 26 章中，我们看到了如何使用存根（stubs）来验证程序流。从脚本开发的早期阶段开始，它们就是检查工作进展的宝贵技术。

让我们看看之前的文件删除问题，看看如何对其进行编码以便于测试。测试原始代码片段。

```bash
if [[ -d "$dir_name" ]]; then

    if cd "$dir_name"; then

        echo * # TESTING

    else

        echo "Cannot cd to '$dir_name'" >2

        exit 1

    fi

else

    echo "No such directory: '$dir_name'" >2

        exit 1

fi

exit
```

由于错误条件已经输出了有用的信息，我们不需要添加任何额外信息。最重要的变化是在 `rm` 命令之前放置一个 `echo` 命令，以便显示其展开后的参数列表，而不是执行该命令。在代码片段的末尾，我们放置了一个 `exit` 命令来结束测试并防止脚本的任何其他部分执行。这种需求将根据脚本的设计而异。

我们还包含了一些作为测试“标记”的注释。这些注释可以在测试完成后找到并移除这些更改。

## 测试用例

为了进行测试，开发和应用良好的测试用例至关重要。通过仔细选择反映边界情况和边缘情况的输入数据或操作条件来实现。

- `dir_name` 包含一个目录的名称。
- `dir_name` 包含一个不存在的目录名称。
- `dir_name` 为空。

通过对这些情况进行测试，可以实现良好的测试覆盖。

与设计一样，测试同样也是时间的函数。并不是每个脚本功能都需要详尽测试。这取决于哪些功能是最重要的。由于它发生故障时可能具有破坏性，我们的代码片段在设计和测试期间都值得仔细考虑。

# 调试

如果测试发现脚本存在问题，下一步就是调试。“一个问题”通常意味着脚本以某种方式没有按照编译员的预期运行。这样，我们需要仔细确定脚本实际上在做什么，以及为什么。寻找 bug 涉及大量的侦查工作。

设计良好的脚本会尝试提供帮助。它应该进行防御性编程，以检测异常情况并向用户提供有用的反馈。然而，有时问题是非常奇怪且意料之外的，需要更多的技术。

## 寻找问题区域

在脚本中，特别是长脚本中，有时隔离与问题相关的脚本区域是有用的。这并不总是真正的错误所在，但隔离可以为实际情况提供见解。一种可以用于隔离代码的技术是“注释掉”脚本的部分。例如，可以修改我们的文件删除片段，以确定被移除的部分是否与错误有关。

```bash
if [[ -d $dir_name ]]; then

  if cd $dir_name; then

    rm *

  else

    echo "cannot cd to '$dir_name'" >&2

    exit 1

  fi

# else

#  echo "no such directory: '$dir_name'" >&2

#  exit 1

fi
```
