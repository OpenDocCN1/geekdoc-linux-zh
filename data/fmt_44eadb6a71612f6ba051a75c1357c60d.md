
```
/* 进程列表页结束的 HTML 源代码。 */

static char* page_end =
"</body>\n"
"</table>\n"
"</body>\n"
"</html>";

void module_generate(int fd)
{
size_t i;
DIR* proc_listing;

/* 设置一个 iovec 数组。我们将向其中填充作为输出部分的
缓冲区，并根据需要动态扩展它。 */
/* 数组已使用的元素数量。 */
size_t vec_length = 0;
/* 数组的分配大小。 */
size_t vec_size = 16;
/* iovec 元素数组。 */
struct iovec* vec =
(struct iovec*) kmalloc(vec_size * sizeof(struct iovec));

/* 第一个缓冲区是页面的 HTML 源代码。 */
vec[length].iov_base = page_start;
vec[length].iov_len = strlen(page_start);
++length;

/* 开始对 /proc 进行目录列表。 */
proc_listing = opendir("/proc");
if (proc_listing == NULL)
  system_error(opendir(""));

/* 遍历 /proc 中的目录项。 */
while (1) {
struct dirent* proc_entry;
const char* name;
pid_t pid;
char* process_info;

/* 获取 /proc 中的下一个项。 */
proc_entry = readdir(proc_listing);
if (proc_entry == NULL)
  /* 我们到达了列表的末尾。 */
  break;

/* 如果此项不是完全由数字组成，则它不是进程目录，跳过它。 */
name = proc_entry->d_name;
if (strncmp(name, "0123456789", strlen(name)) != 0)
  continue;
  /* 项的名称是进程 ID。 */
  pid = (pid_t)atoi(name);
  /* 为此进程生成 HTML。 */
  process_info = format_process_info(pid);
  if (process_info == NULL)
    /* 出了一些问题。进程在查看时可能已经消失。使用占位符代替。 */
    process_info = "<td colspan='5'>ERROR</td></tr>";
  /* 使 iovec 数组足够容纳这个
  缓冲区（外加一个元素）。 */
  if (length + 1 >= vec_size)
    vec_size *= 2;
    vec = realloc(vec, vec_size * sizeof(struct iovec));
  /* 将此缓冲区作为下一个元素。 */
  vec[length].iov_base = process_info;
  vec[length].iov_len = strlen(process_info);
  ++length;
}
/* 结束目录列表。 */
closedir(proc_listing);

/* 添加带有 HTML 的最后一个缓冲区。 */
vec[length].iov_base = page_end;
vec[length].iov_len = strlen(page_end);
++length;

/* 将整个页面输出到文件描述符。 */
writev(fd, vec, length);

/* 释放所有缓冲区。 */
for (i = 0; i < length; i++)
  free(vec[i].iov_base);
/* 释放 iovec 数组。 */
free(vec);
```
### 11.4 使用服务器

# 默认：构建所有内容
all: server $(MODULES)

# 清理构建产品。
clean: rm -f $(FLAGS) $(MODULES)

# 主程序。使用 -Wl,-export-dynamic 链接，以便
# 动态加载的模块绑定程序中的符号。链接
# libdl，其中包含了动态加载的调用。

```make
server: $(OBJECTS)
	$(CC) $(FLAGS) -Wl,-export-dynamic -o $^ -ldl
```

# server 中的所有对象文件都依赖于 server.h。但使用
# 默认规则从源文件构建对象。
$(OBJECTS): server.h

# 为相应的源文件构建共享对象库的规则：
# 编译选项 -fPIC 并生成共享对象文件。
$(MODULES):
```make
%.c server.h
	$(CC) $(FLAGS) -fPIC -o $^ $<
```

Makefile 提供了这些目标：

- all（你在 Makefile 中不带参数时调用的默认目标）包含了 server 可执行文件和变量 SOURCES 中列出的所有模块。
- clean 删除由 Makefile 生成的任何构建产品。
- server 链接 server 可执行文件。变量中列出的源文件被编译并链接。
- 最后一条规则是为相应的源文件编译共享对象库的通用模式。

注意，server 的源文件是用 -fPIC 选项编译的，因为它们链接到了共享库（见第 2.3.2 节，共享库）。同样观察到 server 可执行文件是用 -Wl,-export-dynamic 选项链接的。通过此选项，GCC 将 -export-dynamic 选项传递给链接器，链接器创建一个将其外部符号作为共享库导出的可执行文件。这允许作为共享库动态加载的模块引用静态链接到 server 可执行文件中的 common.c 中的函数。

#### 11.4.2 构建服务器

在包含源文件的目录中构建程序，只需调用 make 即可：

```
% make
cc -Wall -c server.o server.c
	cc -Wall -c module.o module.c
	cc -Wall -c common.o common.c
	cc -Wall -c main.o main.o
	cc -Wl,-export-dynamic -o server.o main.o -ldl
	cc -Wall -fPIC -shared -o diskfree.so diskfree.c
	cc -Wall -fPIC -shared -o issue.so issue.c
	cc -Wall -fPIC -shared -o processes.so processes.c
	cc -Wall -fPIC -shared -o time.so time.c
```

这构建了服务器程序和服务器共享库。

```bash
% ls -l server*.so
-rwxr-xr-x 1 samuel 25769 Mar 11 01:15 diskfree.so
-rwxr-xr-x 1 samuel 31184 Mar 11 01:15 issue.so
-rwxr-xr-x 1 samuel 41579 Mar 11 01:15 processes.so
-rwxr-xr-x 1 samuel 71758 Mar 11 01:15 server
-rwxr-xr-x 1 samuel 13980 Mar 11 01:15 time.so
```

#### 11.4.3 运行服务器

要运行服务器，只需调用 server 可执行文件。

如果你没有通过 --port (-p) 选项指定服务器端口号，Linux 将为你选择一个；在这种情况下，指定 --verbose (-v) 使服务器以名称形式输出端口号。

如果你没有通过 --address 指定地址，服务器将在你计算机的所有网络地址上运行。如果你的计算机连接到了网络，这意味着所有其他人都将能够访问服务器，只要他们知道要使用的端口号和页面。出于安全考虑，当你确定服务器运行正常且没有发布任何你希望公开的信息时，识别 localhost 地址是一个好主意。绑定到 localhost 会导致服务器绑定到本地网络地址（指定为 "lo"——只有在同一台计算机上运行的程序才能连接它）。如果你指定了不同的地址，它必须是你计算机对应的地址：

```bash
% ./server --address localhost --port 4000
```

服务器现在正在运行。打开浏览器窗口，并尝试通过此端口连接服务器。请求一个与模块之一匹配的页面名称。例如，要调用 diskfree.so 模块，请使用你的 URL：

```
http://localhost:4000/diskfree
```

### 11.5 完成

输入指定的端口号（代替 4000，或 Linux 为你选择的端口号）。完成后，按 Ctrl+C 杀死服务器。

如果你没有指定 localhost 作为服务器地址，你也可以使用运行在另一台计算机上的 Web 浏览器并在 URL 中使用计算机的主机名连接服务器——例如：

```
http://host.domain.com:4000/diskfree
```

如果你指定了 --verbose (-v) 选项，服务器会在启动时打印信息并显示连接到它的每个客户端的 Internet 地址。如果你通过 localhost 地址连接，服务器地址将是 127.0.0.1。

如果你在尝试编写自己的服务器模块，可以将它们放置在与 --module-dir (-m) 选项不同的目录中。在这种情况下，使用 --module-dir (-m) 选项指定该目录。

如果你忘记了命令行选项的语法，使用 --help (-h) 选项调用服务器：

```
% ./server --help
Usage: ./server [ options ]
-a,--address ADDR
```

- -h,--help 绑定到本地地址（默认绑定到所有本地地址）。
- -m,--module-dir 从指定目录加载模块（默认使用执行文件目录）。
- -p,--port 绑定到指定端口。
- -v,--verbose 打印信息。

### A.2 查找动态内存错误

在编写程序时，你通常无法知道程序在运行时需要多少内存。例如，在运行时从文件中读取的一行可能具有任何有限的长度。C 和 C++ 程序使用 `malloc`、`free` 及其变体在程序运行时动态分配内存。动态内存使用的规则如下：

- 分配调用（对 `malloc` 的调用）的数量必须释放调用（对 `free` 的调用）的数量完全匹配。
- 对已分配内存的读写操作必须在内存内部进行，不能在内存范围之外。
- 已分配的内存在使用释放之前或释放之后不能被使用。

由于动态内存的分配和释放发生在运行时，静态程序分析很少发现违规行为。相反，内存检查工具通过运行程序并收集数据来判断是否违反了上述任何规则。违规工具可能会发现以下问题：

- 在分配内存之前读取内存
- 在分配内存之前向内存写入
- 在分配内存起始位置之前读取
- 在分配内存起始位置之前写入
- 在分配内存结束位置之后读取
- 在分配内存结束位置之后写入
- 在内存释放后读取内存
- 在内存释放后向内存写入
- 未释放已分配的内存
- 重复释放同一块内存
- 释放未分配的内存

对请求 0 字节分配的警告是很有用的，这可能指示程序错误。表 A.1 显示了四个工具的诊断能力。遗憾的是，没有一个工具能检测到所有的内存使用情况。此外，没有工具声称能检测分配内存之前的读取或写入；但这样做可能会导致段错误（segmentation fault）。重复释放内存可能也会导致段错误。这些工具检测的是程序运行期间实际发生的错误。如果你使用没有内存分配的输入运行程序，工具将不会指示任何内存错误。要彻底测试程序，你必须使用不同的输入运行程序，以确保程序中所有可能的路径都会执行。此外，你可能一次只能使用一个工具，因此必须使用多个工具重复测试以获得最佳的错误检查效果。

我们将在后的 A.2.7 节介绍程序代码，并说明如何使用它。

#### A.2.2 malloc 检查

GNU C 库提供的内存分配函数可以检测分配起始位置之前的写入以及重复释放同一次分配。将环境变量 `MALLOC_CHECK` 的值设置为 2 会导致程序在检测到此类错误时停止（注意环境变量中的下划线）。不需要重新编译程序。

我们通过在分配起始位置之前的一个位置进行写入来演示这一点。

```bash
% export MALLOC_CHECK=2
./malloc use 12
Please enter a command: a 10
Please enter a command: w -1
Please enter a command: d 0
Aborted (core dumped)
```

导出 malloc 检查设置。指定值 2 会导致程序在检测到错误时立即停止。使用 malloc 检查的优点是程序不需要重新编译，但其诊断错误的能力是有限的。基本上，它检查的是分配器结构没有被损坏。因此，它可以检测到对同一块内存的重复释放。此外，在内存分配起始位置之前的写入通常可以被检测，因为分配器在分配区域之前存储了每次内存分配的大小。因此，在分配内存之前写入会破坏这个数字。遗憾的是，一致性检查只能在程序调用分配例程时发生，而在访问内存时不会，因此在检测到错误之前可能会发生许多非法读写。在上例中，非法写入只有在内存释放时才被检测到。

#### A.2.3 使用 mtrace 查找内存泄漏

mtrace 工具帮助诊断使用动态内存时最常见的错误：分配与释放不匹配。使用 mtrace（由 GNU C 库提供）有四个步骤：

1. 修改源代码包含 `<malloc.h>` 并在程序启动时（在 main 函数开头）调用 mtrace。让 mtrace 开启对内存分配和释放的跟踪。
2. 指定文件名来存储所有内存分配和释放的信息。
   `% export MALLOC_TRACE=memory.log`
3. 运行程序。所有的内存分配和释放都存储在日志文件中。
4. 使用 mtrace 命令分析内存分配和释放，以确保它们匹配。

```bash
$ mtrace my_program $MALLOC_TRACE
```

mtrace 产生的消息相对容易理解。例如，对于我们的 malloc-use 示例，输出将如下：

```
0000000000 Free 3 bytes was never alloc'd malloc-use.c:39
```

未释放的内存：

| 地址 | 大小 | 调用者 |
|---|---|---|
| 0x0049d048 | 0xc | at malloc-use.c:30 line 39 of malloc-use.c to free |

这些消息表示在 malloc-use.c 的第 39 行尝试释放从未分配过的内存，以及在第 30 行分配了但从未释放的内存。mtrace 通过让可执行文件在 MALLOC_TRACE 指定的文件记录所有内存分配和释放来诊断错误。可执行文件必须正常终止才能生成数据。

### A.2.4 使用 cmmalloc

cmalloc 通过用代码跟踪替换 `malloc` 和 `free` 来诊断错误。如果程序正常退出，它会生成一份关于内存泄漏和其他错误的报告。cmmalloc 库由 Armin Bierner 编写。要使用 cmmalloc 检测分配起始之前或结束之后的写入，你必须修改当前目录下的 `.cmalloc` 文件。该文件在程序启动时被读取。要使用 cmmalloc，你需要从 http://www.ethz.ch/personal/cmalloc 下载并解压，运行 `configure`。运行 `make` 并安装。程序的对象文件必须与 cmmalloc 链接，例如：

```bash
% gcc -Wall -pedantic cmmalloc.o -o malloc -lmalloc -ldl
```

执行程序生成报告。例如，运行我们的程序进行分配但不释放内存会产生以下内容：

```
./cmalloc-use 12
file-name=a does not contain symbols
trying to find executable in current directory ...using symbols from 'cmalloc'
(in the startup file '.cmalloc')
Please enter a command: q 12
```
