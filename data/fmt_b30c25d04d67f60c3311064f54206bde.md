因为我们在编译时是该源码的“维护者”，因此我们将将其保留在 `/src` 中。由发行版安装的源码将安装在 `/usr/src`，而我们维护的、供多个用户使用的源码将安装在 `/usr/local/src`。

正如我们看到的，源码通常以压缩文件的形式提供。它有时称为 tar 包（tarball），是组成源码的目录和文件层次结构。到达 FTP 站点后，我们检查 tar 文件列表并选择最新版本进行下载。在 ftp 中使用 `get` 命令，我们将文件从 FTP 服务器复制到本地机器。

一旦下载了 tar 文件，就必须对其进行解压。这是通过 `tar` 程序完成的。

```
[linuxbox]$ tar xzf diction-1.11.tar.gz
```

```
[linuxbox]$ ls
diction-1.11      diction-1.11.tar.gz
```

该程序像所有 GNU 项目的软件一样，遵循源码打包的特定。Linux 生态系统中的大多数其他源码都遵循这一标准。标准的一个元素是：源码文件被解压后会创建一个包含源码树的目录，该目录将命名为 `project-xx`，其中包含项目名称和版本号。这种方案允许安装同一个程序的多个版本。然而，在解压之前检查树的布局通常是一个好主意。有些项目不会创建目录，而是直接将文件交付到当前目录中。这会使我们组织良好的源码目录变得混乱。为了避免这种情况，请使用以下命令检查 tar 文件的内容：

```
tar -tvf tarfile | head
```

## 检查源码树

解压 tar 文件会创建一个名为 `diction-1.11` 的新目录。该目录包含了源码树。让我们查看内部。

```
[me@linuxbox src]$ cd diction-1.11
```

```
[me@linuxbox diction-1.11]$ ls
config.guess diction.c getopt.c nl
config.h diction.pot getopt.h nl.po
config.sub dictionary.spec getopt_int.h README
configure dictionary.spec INSTALL sentence.c
config.in diction.in install-sh sentence.h
COPYING Makefile.in style.in
en en_GB misc.c style.c
de.po en_GB misc.h test
diction.1.11 getopt1.c NEWS
```

在其中，我们看到了许多文件。GNU 项目以及许多其他项目的程序都会提供 `README`、`INSTALL`、`NEWS` 和 `COPYING` 文档文件。这些文件包含了程序的描述、如何构建和安装它以及其许可条款。在尝试编译程序之前，仔细阅读 `README` 和 `INSTALL` 文件始终是一个好主意。

目录中其他有趣的文件是那些 `.c` 和 `.h` 结尾的文件。

```
[me@linuxbox diction-1.11]$ ls *.c
diction.c getopt1.c misc.c sentence.c style.c
```

```
[me@linuxbox diction-1.11]$ ls *.h
getopt.h getopt_int.h misc.h
```

`.c` 文件包含该包提供的 C 程序（`style` 和 `diction`），并被分为多个模块。大型程序拆分成更小、更容易管理的片段是常见做法。源码文件是普通文本，可以使用 `less` 查看：

```
[me@linuxbox diction-1.11]$ less diction.c
```

`.h` 文件被称为头文件。这些同样也是普通文本。头文件包含了包含在源文件或库中的例程描述。为了让编译器编译这些模块，它必须接收到完成整个程序所需模块的描述。在 `diction.c` 的开头附近，你会看到这一行：

```
#include "getopt.h"
```

这指示编译器在读取 `diction.c` 中的源码时读取 `getopt.h`，以便“知道” `getopt.c` 中的内容。`diction.c` 文件提供了 `style` 和 `diction` 程序共享的例程。

在 `getopt.h` 的 `include` 语句之前，我们看到了一些其他 `include` 语句，例如：

```c
#include <regex.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
```

这些也引用头文件，但它们引用的是位于当前源码树之外的头文件。它们由系统提供以支持每个程序的编译。如果我们查看 `/usr/include/`，就可以看到它们。

```
[me@linuxbox-1.11]$ ls /usr/include
```

该目录中的头文件是在安装编译器时安装的。

## 编译程序

大多数程序通过简单的序列进行构建。

```
./configure
make
```

`configure` 程序是随源码树提供的 shell 脚本。它的工作是分析构建环境。大多数源码都被设计为可移植的。也就是说，它被设计在一个类 Unix 系统上构建。但为了实现这一点，源码在构建过程中可能需要微调，以适应系统之间的差异。`configure` 还会检查必要的工具和组件是否已安装。因为 `configure` 不在 shell 预期程序的位置，我们必须通过在命令前加上 `./` 来显式地告诉 shell 它的位置，以指示程序位于当前工作目录。

```
[me@linuxbox-diction-1.11]$ ./configure
```

`configure` 在测试和配置构建时会输出消息日志。当它完成后，它看起来像这样：

```
+- checking libreadline presence... yes
- checking for readline.h... yes
- checking for library gettext... none required
- configure: creating ../config.status
- config-status: creating Makefile
- config-status: creating diction.1
- config-status: creating diction.texi
- config-status: creating diction.spec
- config-status: creating style.1
- config-status: creating test/run
- config-status: creating config.h
```

`config.status` 文件非常重要。这里的重要的是没有错误信息。如果有，说明配置失败了，在纠正错误之前程序将无法构建。

我们在源码目录中看到了几个新文件。最重要的是 `Makefile`。`Makefile` 是一个配置文件，指示 `make` 程序具体如何构建程序。没有它，`make` 将拒绝运行。`Makefile` 是普通文本文件，所以我们可以查看它。

```
[me@linuxbox diction-1.11]$ less Makefile
```

`make` 程序将 `makefile`（通常命名为 `Makefile`）作为输入，它描述了组成程序的组件之间的关系和依赖关系。

`makefile` 的开头部分定义了在 `makefile` 后部分使用的变量。例如我们看到了如下行：

```
CC=gcc
```

这将 C 编译器定义为 `gcc`。在 `makefile` 后面，我们看到了它被使用的一个实例。

```
diction: diction.o sentence.o misc.o getopt.o dictionary.o
$(CC) -c $^ diction.o sentence.o misc.o \
getopt.o dictionary.o $(LIBS)
```

在这里执行了替换，`$(CC)` 在运行时被替换为 `gcc`。

`makefile` 的大部分由定义目标组成——在这种情况下是可执行文件 `diction` 及其依赖的文件。剩余的行描述了从组件创建目标所需的命令。在这个示例中，我们看到可执行文件 `diction`（产物之一）依赖于 `diction.o`、`sentence.o`、`misc.o`、`getopt.o` 和 `dictionary.o` 的存在。随后，在 `makefile` 中，我们看到了这些每个文件目标的定义。

```
diction.o: diction.c config.h getopt.h misc.h sentence.h
```
