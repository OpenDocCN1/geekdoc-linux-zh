
小巧真的非常美。力量并不属于大而强者，而属于小而有能者。你只需要看看如今美国景观上紧凑型汽车的数量，就能意识到数万人得出了相同的结论。大众汽车通过“复古”甲虫再次做到了这一点。“小巧”是一种潮流。而且是永远的潮流。

这种对微小事物的不仅限于汽车。人们发现，小东西通常比它们的大尺寸对应物具有巨大的优势。平装书的销量一直超过硬装版书籍，部分是因为它们更便宜，部分是因为它们更容易随身携带。手表取代口袋表是因为它们尺寸更小、便携性更高。技术的进步使得今天的微型电子元件在某些比大型元件更强大。口袋电视、掌上电脑和手持控制器的销量正在飙升。即使是今天的核武器也比二战期间投向日本的原子弹小得多，但它们拥有远强大的破坏力。

我们这个不断缩小的宇宙很大程度上归功于卓越的技术。需要高度先进的技术才能将一台主机计算机缩小到可以握在手心的微芯片。如果没有高密度微处理器提供的微型化能力，今天的许多产品会因为太笨重而无法使用。

尽管如此，使用这些高科技奇迹仍然需要一定水平的用户素质。似乎设备越小、越先进，用户就必须了解越多才能使用它。

一个例子是家用微波炉的演变。早期版本使用一个启动按钮和一个简单的定时旋钮。然后，随着计算机芯片价格的下降，生产可编程的微波炉变成了一种时尚。这些微波炉智能得多，但它们也需要更智能的用户才能利用其先进功能。

另一种观察角度是，孩子并不是用极细记号笔学习写字。他们从大而粗的蜡笔开始。为什么呢？蜡笔要求孩子用他们所能的任何抓握方式握住它。使用刀头记号笔写字需要更高手部灵活性。孩子在第一次拿起蜡笔后好几年里，才能达到这种技能水平。

从这些例子中，我们可以得出几个结论。首先，小小的事物与人的交互并不良好。虽然技术可能让事物变得更小，但人并没有变得更小。一旦达到某个缩小的程度，人们就会失去直接处理事物的能力，必须求助于增强他们正常感官的工具。例如，钟表匠不会用肉眼仔细检查瑞士手表内部的微小零件。他必须诉诸使用放大镜来看到这些组件。同样，在今天的半导体制造设施中，显微镜被用于发现每平方英寸集成数百万个晶体管的集成电路缺陷。

人类感官的功能仅限于狭窄的范围内。声音可能太轻或太响而听不见。存在频率低于眼睛可感知范围的光波。通过嗅觉，我们可以区分不同的品种或对臭鼬的臭味感到作呕，但我们很难区分两只臭鼬之间的气味。

随着技术导致事物变得越来越小，它们最终会达到我们的感官无法感知的程度。人类若要处理它们，需要一种特殊的界面。随着计算机变得越来越复杂，存在物与感官感知之间的差距在不断扩大。执行任务的软件与其用户界面之间的距离变成了一个不断扩大的空洞。

关于微小事物的第二个结论是，虽然它们不与人交互良好，但它们倾向于彼此之间交互。它们小小的尺寸赋予了它们巨大的灵活性。它们非常适合在许多情况下进行集成。

考虑这个例子：下一次当你看到社区里有一一辆搬家车时，观察工人是如何加载客户物品的。如果他们要把一辆汽车放在货车上，汽车会是先放的。然后他们决定下一个大件放在哪里。他们接着放中等尺寸部件，然后是小部件。这个顺序是显而易见的。但实际上发生的情况是，较小的物体以千上万的方式相互组合以完成任务。虽然在放置小部件方面有一定的灵活性，但较大的部件提供的放置选择较少。

如果你只有小部件会发生什么？你会获得最大的灵活性。然而，这种灵活性是有代价的。小部件越多，人们就越难处理它们。管理它们变成了一个严重的问题。

同样，在计算机软件世界，拥有许多小程序可以让你具有最强的适应能力。遗憾的是，随着模块越来越小，与用户交互的问题也随之而来。模块越多，处理它们的复杂性就越高。

## 第8原则：避免捕获用户界面

这为软件设计师带来了一个困境。他希望他的应用程序具有最大的灵活性，因此由一组小模块构建了它。然而，他也受限于软件必须易用的要求的限制。人们很难处理过多的小模块。

`Unix` 采取了不同的方法来解决这个问题。大多数其他系统试图通过一种被称为“捕获式用户界面”`CUI` 的软件来桥接用户与执行任务的模块之间不断扩大的差距。而 `Unix` 开发者意识到，这个差距正在不断扩大。他们没有通过大量的“意大利面条”代码将用户和底层模块连接起来，而是通过小的区块或层来处理这个差距。

既然我们已经说 `Unix` 和其他操作系统在这一点上存在分歧，你可能怀疑这背后有逻辑。答案来自于 `Unix` 哲学的下一个十条。

在我们开始讨论避免 `CUI` 的原因之前，我们首先需要定义它们。`CUI` 是一种与应用程序交互的样式，它存在于系统上最高命令解释器的范围之外。一旦你从命令解释器调用应用程序，在应用程序退出之前，你就无法与命令解释器进行通信。实际上，你被囚禁在应用程序的用户界面中，直到你采取了导致它释放你的行动。

让我们用一个例子来澄清这一点。假设你有两个程序，一个是列出你的电子邮箱内容的，另一个是在文件中搜索文本字符串。如果邮件和搜索程序使用 `CUI`，你的交互可能看起来像这样：

```
$ mail 从命令行调用邮件程序。
MAIL>dir 显示邮箱内容。
MAIL>exit 退出邮件程序。返回命令解释器级别。
$ search 调用搜索程序。
SEARCH>find jack *.txt 执行搜索。
SEARCH>exit 退出搜索程序。
:
:
$ 我们回到了命令解释器级别。
```

注意这里层级之间的流程。首先，调用 `mail` 命令将你置于自己的输入解释器内部。它强迫你与它的命令解析器交互。解析器的命令集与调用它的命令解释器的命令集不同。其次，要执行搜索命令，你必须先通过退出命令离开邮件程序。然后你从主命令解释器调用了 `search` 命令。你在搜索应用程序内部，你必须与另一个解释器交互。这个解释器的行为与主命令解释器和邮件解释器都不同。唯一的相同点是它要求你退出命令。

你可以看出这种方法明显的缺点。你必须熟悉三个不同的解释器，每个解释器都有自己的交互语言。在小范围内这听起来并不难，但在拥有数百个应用程序的系统中，很快就会变得不可接受。此外，在执行命令时，在退出之前你什么也做不了。例如，在回复邮箱中的某封信时，你需要包含另一个文件中的某些文本但忘记了哪一个。你必须退出邮件命令，或者退出搜索，并返回邮件命令。那时你可能已经忘记了你在邮件应用程序中的上下文。

以上是明显的缺点。`Unix` 拥者的捕获用户界面的缺点并不那么明显。但在探索这些之前，让我们把这种 `CUI` 与 `Unix` 风格的“非捕获”界面进行对比：

```
shs>can
can 命令列出邮件文件夹的内容。
:
:
sh>grep jack *.txt
grep 在所有以 .txt 结尾的文件中搜索字符串 "jack"
```

注意 `Unix` 用户在 shell 提示符或主命令解释器级别调用所有命令。每个命令完成任务后，控制权返回到 shell 提示符。不需要单独退出每个命令。用户只需要学习一种语言——即 shell，`Unix` 命令解释器的语言。

批评者可能会指出，用户仍然必须学习每次命令调用时要提供的参数顺序。这是事实。但在 `CUI` 中，用户必须首先回忆要运行哪个命令，然后从其 `CUI` 中调用哪个子命令。因此，记忆量几乎增加了一倍。

因此，并不意外，采用 `CUI` 的系统通常必须提供高度复杂的帮助系统来引导用户进行选择。另一方面，大多数 `Unix` 用户即使没有复杂的帮助系统也能运行得很好。如果用户输入错误的命令，`Unix` 命令通常会返回简单的消息，列出所需的参数及其用法。

因此，我们定义了 `CUI` 并提到了它们的一些一些显而易见的缺陷。然而，`Unix` 用户避开它们的真正原因要深得多。这与命令之间相互交互的方式有关。在 `Unix` 环境中，没有任何命令是孤立存在的。命令在不同的时间相互相互作用。`CUI` 干扰了多个命令实现这种相互作用的能力。多命令交互是 `Unix` 的核心概念。

### 6.1.1 CUI 假设用户是人类

`CUI` 的生产者基于“人坐在键盘前”这一前提进行设计。他们期望用户对应用程序提供的提示输入响应。然后应用程序再执行计算或完成任务。

然而，问题在于，即使是最快的人也比平均计算机慢。计算机可以以闪电速度进行操作，而且不会疲劳或休息。正如之前提到的，人类的功能仅限于在一个很窄范围内。例如，最快的打字员每分钟打字也多不过 80 字。大多数 `CUI` 最终都会达到一个用户必须对提示做出的的点。即使如此，最快的计算机也并不比最低端的 PC 高多少。几乎所有 PC 都能毫不费力地捕获用户输入的文本。只要系统受限于在人类施加的限制范围内运行，它就无法发挥最大潜力。

当我面对运行在非常快的工作站上的窗口系统时，我发现了这种现象。在 PC 出现之前的，大多数人习惯在终端上扫描文本文件。终端通常允许你通过按下 `<^C>` 组合或“HOLD SCREEN”键来停止和开始显示输出。在 9,600 bps 或更低的现代速度下，大多数人可以轻松地控制滚动速度。然而，今天的窗口系统没有像通信速度那样的人工限制来控制系统显示文本的速度。用户完全取决于 CPU 及其 I/O 能力。可以说，如果让计算机任其发展，它显示文本的速度将比任何人通过输入 `<S>` 来处理的速度快得多。随着大缓存内存和兆赫兹范围内的机器变得普遍，这种情况在未来将恶化。

由于人类对计算机施加了限制，任何必须等待用户输入的系统，其运行速度只能和坐在键盘前的人。换句话说，一点也不快。
