
`-r` 或 `--no-builtin-rules` 标志会导致默认后缀为空。

## 第 10 章：使用隐式规则

变量 `SUFFIXES` 在 `make` 读取任何 Makefile 之前就会被定义为默认后缀列表。你可以通过针对特殊目标 `.SUFFIXES` 的规则来更改后缀列表，但这不会改变该变量。

### 10.8 隐式规则搜索算法

以下是 `make` 用于搜索目标 `t` 的隐式规则时使用的程序。该程序适用于每个带有配方（recipe）的双冒号规则、每个带有配方的普通规则的目标，以及每个不是任何规则目标的前提条件（prerequisite）。在搜索规则链时，对于来自隐式规则的前提条件，也会递归地执行此程序。

该算法中没有提到后缀规则，因为一旦读取了 Makefile，后缀就会被转换为等效的规则。

对于形式为 `'archive(member)'` 的归档成员，将运行一次以下算法，使用整个目标名称 `t`；如果第一次运行没有找到，则使用 `(member)` 作为目标 `t`。

1. 将 `t` 拆分为目录部分 `d` 和其余部分 `n`。例如，如果 `t` 是 `'src/foo.o'`，则 `d` 是 `'src/'`，`n` 是 `'foo.o'`。
2. 列出所有目标匹配 `t` 或 `n` 的规则列表。
3. 如果列表中任何规则不是针对 `n` 的通配匹配规则（match-anything rule），则从列表中移除所有非终端的通配匹配规则。
4. 从列表中移除没有配方的规则。
5. 遍历列表中的每条规则：
    a. 找到 `s`，它是 `t` 或 `n` 中被目标模式中的 `%s` 匹配的非空部分。
    b. 通过将 `s` 替换为 `%s` 来计算前提条件名称；如果目标模式不包含链，则将 `d` 添加到每个前提条件名称的前面。
    c. 测试所有前提条件是否存在或是否“应当存在”（如果一个文件在 Makefile 中作为目标或显式前提条件被提到，我们称它“应当存在”）。

如果所有前提条件都存在或应当存在，或者没有前提条件，则该规则适用。

6. 如果到为止没有找到模式规则，则加大尝试。对于列表中的每个模式：
    a. 如果该规则是终端规则，则忽略它并处理下一条规则。
    b. 按照之前的方法计算前提条件名称。
    c. 测试所有前提条件是否存在或应当存在。
    d. 对于每个不存在的前提条件，递归地执行此算法，查看该前提条件是否可以通过隐式规则生成。
    e. 如果所有前提条件都存在、应当存在或可以通过隐式规则生成，则该规则适用。

7. 如果没有隐式规则适用，则 `.DEFAULT` 规则（如果有的话）适用。在这种情况下，给 `t` 分配与 `.DEFAULT` 相同的配方。否则，`t` 没有配方。

一旦找到适用的规则，对于该规则中除匹配 `t` 或 `n` 的模式外的其他模式，模式中的 `%` 将替换为 `s`，并存储生成的文件，直到执行重做目标文件 `t` 的配方。配方执行后，这些存储的文件名每一个都会存入数据库，并标记为已更新且与文件 `t` 具有相同的更新状态。

当为 `t` 执行模式规则的配方时，自动变量将设置为对应的目标和前提条件。参见第 10.5.3 节 [Automatic变量]，第 120 页。

## 11 使用 make 更新归档文件

归档文件是包含名为“成员”（members）的子文件；它们由程序 `ar` 维护，主要用途是链接的子程序库。

### 11.1 作为目标的归档成员

归档文件中的单个成员可以作为 `make` 中的目标或前提条件。你按照如下方式指定文件 `archive` 中名为 `member` 的成员：

```
archive(member)
```

这种构造仅适用于目标和前提条件，不适用于配方（recipes）！你在配方中使用的绝大多数程序都不支持这种语法，且无法直接对归档成员进行操作。只有 `ar` 和其他专门为操作归档设计的程序才能做到这一点。因此，更新归档目标的有效规则必须使用 `ar`。例如，此规则通过拷贝文件 `'hack.o'` 在归档 `'foolib'` 中创建一个成员 `'hack.o'`：

```
foolib(hack.o)
ar foolib hack.o
```

事实上，几乎所有的归档成员都是通过这种方式更新的，并且有一个隐式规则为你完成这一切。**注意：** 如果归档文件不存在，则需要 `'c'` 标记。

要在同一个归档中指定多个成员，你可以将所有成员名称写在括号之间。例如：

```
foolib(hack.o kludge.o)
```

等同于：

```
foolib(hack.o) foolib(kludge.o)
```

你也可以在归档成员引用中使用 Shell 风格的通配符。参见[文件名中的通配符](page23)。例如，`'foolib(*.o)'` 扩展为 'foolib' 归档中所有以 '.o' 结尾的成员；也许 `'foolib(hack.o) foolib(kludge.o)`。

### 11.2 归档成员目标的隐式规则

记得目标形如 `'a(m)'` 代表归档文件 `a` 中名为 `m` 的成员。

当 `make` 为此类目标查找隐式规则时，特殊特性包括匹配 `(m)` 的隐式规则，以及匹配实际目标 `'a(m)'` 的规则。这条目标为 `'(m)'` 的特殊规则通过将文件 `m` 拷贝到归档中匹配。例如，它将通过将文件 m 拷贝到归档来更新 `'a(m)'`。

一旦找到适用的规则，对于该规则中除匹配 `t` 或 `n` 的模式外的其他模式，模式中的 `%` 将替换为 `s`，并存储生成的文件，直到执行重做目标文件 `t` 的配方。配方执行后，这些存储的文件名每一个都会存入数据库，并标记为已更新且与文件 `t` 具有相同的更新状态。

当为 `t` 执行模式规则的配方时，自动变量将设置为对应的目标和前提条件。参见第 10.5.3 节 [Automatic变量]，第 120 页。

#### 11.2.1 更新符号目录

作为库使用的归档文件通常包含一个名为 `'__SYMDEF'` 的特殊成员，它包含了其他成员定义的外部名称目录。在你更新了任何其他成员后，需要更新 `'__SYMDEF'` 以其能够正确汇总成员。这是通过运行 `ranlib` 程序实现的：

```
ranlib archivefile
```

通常你将此置放在归档文件的规则中，作为所有成员的前提条件。例如：

```
libfoo.a: libfoo.a(x.o) libfoo.a(y.o) ...
	ranlib libfoo.a
```

此效果是更新归档成员 `'x.o'`、`'y.o'` 等，然后更新符号目录 `'__SYMDEF'`。更新成员的规则此处未显示；你可以省略它们并使用前节描述的拷贝文件到归档的隐式规则。在使用原子性更新 `'__SYMDEF'` 的 GNU `ar` 程序时。

### 11.3 使用归档的危险

在使用并行执行（`-j` 选项；第 5.4 节 [并行执行]，第 47 页）和归档时，必须小心。如果多个命令同时在同一个归档文件运行，它们将无法相互感知并损坏文件。

未来的 `make` 版本可能会提供一种机制，通过对所有操作同一个归档文件的配方进行序列化来规避这个问题。目前，你必须通过其他方式编写 Makefile 来避免此问题，或者不使用 `-j`。

## 第 12 章：扩展 GNU make

### 12 扩展 GNU make

`make` 提供了许多高级功能，包括许多实用的函数。然而，它并不包含完整的编程语言，因此具有局限性。有时，这些局限性可以通过使用 shell 函数调用单独程序来克服，但这可能效率低下。

在 make 的内置功能无法满足你的需求的情况下，有两种扩展 make 的方法。在提供该功能的系统中，你可以利用 GNU Guile 作为嵌入脚本语言（参见第 12.1 节 [Guile 集成]，第133页）。在支持动态加载对象的系统中，你可以用任何语言编写自己的扩展（可以编译成此类对象）并加载它以提供扩展功能（参见第 12.2.1 节 [load 指令]，第136页）。

#### 12.1 Guile 集成

`make` 可以在构建时支持 GNU Guile 作为嵌入扩展语言。Guile 实现了 Scheme 语言。对 GNU Guile 以及 Scheme 语言及其特性的回顾超出了本手册的范围：请参见 GNU Gu 和 Scheme 的文档。

你可以通过检查 `.FEATURES` 变量来确定 make 是否包含对 Guile 的支持；如果可用 Guile，该变量将包含 guile 字样。

Guile 集成提供了一个新函数：`guile`。`guile` 函数接收一个参数，该参数首先由 make 以正常方式进行扩展，然后传递给 GNU 评估器。评估器的结果被转换为字符串，并作为 make 中 guile 函数的扩展。

此外，make 还暴露了 Guile 过程以便在 Guile 脚本中使用。

##### 12.1.1 Guile 类型的转换

`make` 中只有一种“数据类型”：字符串。相反，GNU Guile 提供了多种数据类型。make 和 GNU Guile 之间接口的一个重要方面是将 Guile 类型转换为 make 字符串。

这种转换在两个地方相关：首先，当 Makefile 调用 `guile` 函数评估 Guile 表达式时，该评估的结果必须转换为 make 字符串，以便 make 进一步评估。其次，当 Guile 脚本调用提供给 make 的参数时，必须转换为字符串。

Guile 类型到 make 字符串的转换如下：

- `#f`
假（False）被转换为空字符串：在 make 条件判断中，空字符串被视为假。

- `#t`
真（True）被转换为字符串 '#t'：在 make 条件判断中，任何非空字符串都被视为真。

- symbol
符号或数字被转换为该符号或数字的字符串表示。

- 可打印字符被转换为相同的字符。

仅包含可打印字符的字符串被转换为相同的字符。

- 列表将递归地按上述规则进行转换。这意味着任何结构化列表将被扁平化（即 `(a b c d e)` 是 `''` 转换为字符串 `'a b c d e'` 的结果）。

任何其他 Guile 类型都导致导致错误。在未来的 make 版本中，可能会转换其他 Guile 类型。

对 `'#f`（空字符串）和 `'#t`（非空字符串 '#t'）的翻译设计目的是为了允许你将 Guile 布尔值结果作为 make 条件。例如：

```make
$($guile access "myfile" R_OK),$($info myfile exists))
```

由于这些转换规则，你必须考虑你的 Guile 脚本的结果，因为结果会被转换为字符串并由 make 解析。如果脚本没有自然结果（即脚本仅为了副作用而存在），你应该添加 `'#f` 作为表达式，以避免 makefile 中出现语法错误。

##### 12.1.2 从 Guile 到 make 的接口

除了在 Makefile 中使用的 `guile` 函数外，`make` 还暴露了一些过程供 Guile 脚本使用。在启动时，`make` 会创建一个新的 Guile 模块 `gnu_make`，并将这些过程导出为该模块的公共接口：

- `gmk-expand`：此过程接收一个参数，该参数首先由 make 以正常方式进行扩展，然后传递给 GNU 评估器。评估器的结果被转换为字符串，并作为 guile 函数的扩展。

- `gmk-eval`：此过程接收一个参数，该参数首先由 make 以正常方式进行扩展，然后传递给 GNU 评估器。评估器的结果被转换为字符串，并作为 guile 函数的扩展。

- `gmk-close`：此过程接收一个参数，该参数首先由 make 以正常方式进行扩展，然后传递给 GNU 评估器。评估器的结果被转换为字符串，并作为 guile 函数的扩展。

##### 12.1.3 使用 Guile 示例

在 make 中使用 Guile 的简单示例：

```make
$(guile access "myfile" R_OK),$(info myfile exists)
```

#### 12.2 加载对象

> **警告：** `load` 指令和扩展功能在此版本中被视为“技术预览”。我们鼓励你尝试此功能并感谢你的反馈。但我们无法保证向后兼容。

如果你的系统提供此功能，GNU `make` 可以利用它加载动态对象（参见8.14 [shell 函数]，第97页）。

##### 12.2.1 load 指令

通过在 Makefile 中放置 `load` 指令将对象加载到 GNU make中。`load` 的语法如下：

```make
load ...
或：
load(symbol-name) ...
```

GNU make 动态加载文件对象。如果 object-file 不包含目录路径，则在当前目录查找。如果没有找到或包含了目录路径，将搜索系统特定路径。如果加载因原因失败，make 将打印消息并退出。

如果提供了 symbol-name，将将其用作初始化函数的名称。如果没有提供 symbol-name，初始化函数名通过取 object-file 的基名直到第一个非有效符号字符（字母、数字和下划线是有效符号字符）来创建，并附加后缀 _mk_。

可以使用 `load` 指令加载多个对象，并可以在同一域内使用两种形式。

初始化函数将提供调用加载操作的文件名和行号。它应该返回 int 类型的值，失败返回 0，成功返回非 0。如果返回 -1，GNU make 将不会尝试重建对象文件。

例如：

```make
load mk_funcs.so
```

将加载动态对象‘mk_funcs.so’。对象加载后，make 将调用（假设由共享对象定义）函数 `mk_funcs_gmk_setup`。

```make
load ../mk_funcs.so(init_mk_func)
```

这将加载动态对象 '../..mk_funcs.so'。对象加载后，make 将调用函数 `init_mk_func`。

无论对象文件在 `load` 指令中出现多少次，它只会被加载一次（并调用其设置函数）。

对象成功加载后，其文件名将被追加到 `.LOADED` 变量中。

如果你希望在加载动态对象失败时报告为错误，可以使用 `-load` 指令代替 `load`。如果对象加载失败，GNU make 将失败且不会生成任何消息。失败的对象不会添加到 `.LOADED` 变量中，你可以通过查询该变量来确定加载是否成功。

##### 12.2.2 加载的对象会被重新构建

加载的对象将经历与 Makefile 相同的重构过程（参见第 3.5 节 [How Makefiles Are Re]，第 14 页）。如果任何加载的对象被重新创建，make 将从头开始重新读取所有的 Makefile，并重新加载这些文件。加载的对象不需要执行任何特殊处理来支持此操作。

构建加载的对象所需的规则由该 make 对象本身提供。

##### 12.2.3 加载对象接口

> 警告：为了使此功能有用，你的扩展需要调用 GNU make 内部的各种函数。此版本提供的编程接口不被认为是稳定的：在 GNU make 的未来版本中，可能会添加、删除函数或更改函数的签名或实现。

为了有用，加载的对象必须能够与 GNU make 交互。这种交互包括加载对象提供给 Makefile 的接口，以及 make 提供给加载对象以操作 make 操作的接口。

加载对象与 make 之间的接口由 'gnumake.h' C 头文件定义。所有用 C 编写的对象都应该包含此头文件。任何非 C 语言编写的加载对象都需要实现此头文件中定义的接口。

通常，加载对象会在其设置函数内部使用 `gmk_add_function` 例程来注册一个或多个 GNU make 函数。这些函数的实现可以使用 `gmk_expand` 和 `gmk_eval` 例程来执行任务，并可选地返回一个字符串作为函数展开的结果。

### 加载对象的许可

每个动态扩展都应该定义全局符号 `plugin_is_GPL_compatible`，以断言它已根据 GPL 兼容许可获得授权。如果此符号不存在，make 在尝试扩展你的函数时会产生致命错误。

该符号的声明类型应该是 `int`。它不需要在任何注释段中，尽管代码仅仅断言该符号在全局作用域中。类似下面的代码：

```c
int plugin_is_GPL_compatible;
```
