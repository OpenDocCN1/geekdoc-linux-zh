
在日志应用程序中，`Logger`对象可以组织成层级结构。这是通过将日志命名为`'app.net.client'`实现的。这里存在名为`'app'`、`'app.net'`和`'app.net.client'`的不同`Logger`对象。当在任何日志上发布消息并成功通过过滤器时，该消息会传播并由所有父日志处理。例如，在`'app.net.client'`上成功发布的消息也会传播到`'app.net'`、`'app'`以及根日志器（`root logger`）。

以下`Logger`属性控制着这种传播：

`log.propagate`

一个布尔标志，指示消息是否传播到父日志器。默认设置为`True`。

```python
log.setLevel(level)
```

返回日志器的有效级别（effective level）。如果已使用`setLevel()`设置了级别，则返回该级别。如果没有显式设置级别（即该级别为`logging.NOTSET`），则此函数将返回父日志器的有效级别。如果没有任何父日志器设置了级别，则将返回根日志器的有效级别。

分级日志的主要目的是能够过滤来自应用程序不同部分的日志消息。如果你想关闭来自应用程序中`'app.net.client'`部分的日志消息，可能需要添加如下所示的配置代码：

```python
import logging
logging.getLogger('app.net.client').propagate = False
```

或者在这种情况下，我们忽略程序模块中除最严重消息以外的所有消息：

```python
import logging
logging.getLogger('app.net.client').setLevel(logging.CRITICAL)
```

分级日志的一个方面是：处理日志消息的决定完全由发布消息的`Logger`上的级别和过滤器做出，而不是由任何父日志器的过滤器做出。因此，如果消息通过了第一组过滤器，它将被传播并由所有父日志器*处理*，无论它们自身的过滤器和级别设置如何——即使这些设置会拒绝该消息。初看之下，这种行为是不背直觉的，似乎像是一个`bug`。然而，将子日志器的级别设置为比其父级低的值是覆盖父级设置的一种方法，实现了某种级别的提升。以下是一个示例：

```python
import logging

# 顶层日志器 'app'
log = logging.getLogger('app')
log.setLevel(logging.CRITICAL)

# 只接受 CRITICAL 级别的消息。

# 子日志器 'app.net'
net_log = logging.getLogger('app.net')
net_log.setLevel(logging.ERROR)

# 在 'app.net' 上接受 ERROR 消息
# 这些消息现在将由 'app'
# 日志器处理，尽管它的级别是
# CRITICAL。
```

使用分级日志器时，你只需要在你想要更改过滤或传播行为的地方对日志对象进行配置。因为消息自然地传播到根日志器，而根日志器最终负责产生输出以及你使用`basicConfig()`进行的任何配置。

## 消息处理

通常，消息由根日志器处理。任何`Logger`对象都可以为其添加特殊的处理器（`handlers`）来接收和处理日志消息。这是通过`Logger` (`handler`)的这些方法实现的

```python
log.addHandler(handler)
```

向日志器添加一个`Handler`对象。

```python
log.removeHandler(handler)
```

从日志器中移除`Handler`对象`handler`。

`logging`模块提供了多种预构建的处理器，用于将日志消息写入文件、流、系统日志等。这些将在下一节中进行更详细的描述。然而，下面的示例展示了如何使用这些方法挂钩日志器和处理器。

```python
import logging
import sys

# 创建一个名为 'app' 的顶层日志器
app_log = logging.getLogger('app')
app_log.setLevel(logging.INFO)
app_log.propagate = False

# 为 'app' 日志添加一些消息处理器
app_log.addHandler(logging.FileHandler('app.log'))
app_log.addHandler(logging.StreamHandler(sys.stderr))

# 发布一些消息。这些消息将进入 app.log 和 sys.stderr
app_log.critical('Creeping death detected!')
app_log.info('FYI')
```

当你添加处理器来处理消息时，你的意图通常是覆盖根日志器的行为。这就是为什么在前面的示例中禁用了传播（即`'app'`日志器将直接处理所有消息）。

## 处理器对象

`logging`模块提供了一系列预构建的处理器，可以以各种方式处理日志消息。这些处理器通过它们的`addUser`方法添加到`Logger`对象中。此外，每个处理器都可以配置其自己的过滤器和级别。

## 内置处理器

以下处理器是内置的：

```python
handlers.DatagramHandler(host, port)
```

将消息发送到 UDP 服务器。`address`指定目标为`(host, port)`元组。如果省略，则使用目标地`('localhost', 514)`。

```python
handlers.FileHandler(filename, mode)
```

将日志写入文件。`mode`指定要使用的文件模式。默认模式为`'a'`。

```python
handlers.HTTPHandler(host, url)
```

将消息发送到 HTTP 服务器。`host`是简单的字符串或元组`(host, port)`。

```python
handlers.MemoryHandler(capacity, flush)
```

此处理器在内存中收集消息。`capacity`是缓冲区大小，`flush`是函数。

```python
handlers.SMTPHandler(mailhost, fromaddr, toaddrs, subject)
```

将消息发送到远程主机。`mailhost`是 SMTP 服务器的地址，`fromaddr`是目标地址，`subject`是用户。

```python
handlers.SocketHandler(host, port)
```

使用 TCP 连接将消息发送到远程主机。`host`和`port`指定目标。

```python
handlers.StreamHandler([fileobj])
```

将日志写入已打开的文件对象。如果没有提供参数，消息将写入`sys.stderr`。

```python
handlers.SysLogHandler([address, facility])
```

将日志消息发送到 UNIX syslog 守护进程。`address`指定目标为`(host, port)`元组。

```python
handlers.RotatingFileHandler(filename, mode, maxBytes)
```

将日志消息写入文件。`maxBytes`指定文件的大小。

```python
handlers.TimedRotatingFileHandler(filename, when, interval, backupCount)
```

与`TimedRotatingFileHandler`类似，文件的轮转由时间而非大小控制。

```python
handlers.WatchedFileHandler(filename, mode, encoding)
```

与`FileHandler`相同，但会监控日志文件的设备和打开状态。如果自上次发布日志消息以来文件发生了变化，则将关闭并重新打开。

## 处理器配置

每个`Handler` `h`都可以配置它自己的级别和过滤。使用以下方法来实现：

```
h.setsetLevel(level)

设置要处理的消息的阈值。`level`是一个数字代码，例如`ERROR`或`CRITICAL`。

```
h.addFilter(filt)

向处理器添加一个`Filter`对象，`filt`。有关更多信息请参阅`Logger`对象的`addFilter()`方法。

```
h.removeFilter(filt)
```

从处理器中移除一个`Filter`对象，`filt`。
