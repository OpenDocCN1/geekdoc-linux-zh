图标和图像在直接操控用户界面（例如 Microsoft Windows）中是有用的，只要你处理的是非常小的数据集。当你有十几个或更多文件时，你需要图标上的文本说明来帮助你识别文件内容。这些说明最终变得比图标本身更重要。经验丰富的 Windows 用户通常会将他们的“资源管理器”或文件管理器类型的应用程序设置为“在大图标中显示文件名列表”。

Windows 文件夹类型的文件树视图尤其尤为繁琐。这是一种令人遗憾的讽刺，文件树架构在 Unix 和 Windows 世界中运行得相当良好。在 Windows 中，通过点击图标来导航文件树可能非常耗时且深感疲惫。Linux 和 Unix 高级用户发现文本的精确性在这里是一个优势，因为文件树的文本表示可以很容易地输入到 `grep` 等简单搜索中：

```
find . | grep myfile
```

在这种情况下，`find` 命令返回当前文件夹包含的所有文件和文件夹列表。`find` 命令以递归方式运行，因此它将打开目录中的所有文件夹以及在这些文件夹中找到的所有文件夹，无限循环。`grep` 命令选择列表中包含字符串 `"myfile"` 的文件名或多个文件名。

上述命令对于宽广且深的文件路径具有明显优势，例如 `/home/mikeventcalendar/2004/May19/Bahamas/Freeport/Princess/Towers.txt`。通过指定 `"Towers.txt"` 而不是 `"myfile"`，你可以快速定位该文件。当然，Unix 允许你将一个命令的结果作为另一个命令的输入。这里是在 Unix 下定位和编辑 `"Towers.txt"` 文件的快速方法：

```
vi 'find | grep Towers.txt'
```

要在 Windows 上执行等效操作，你必须从“主”文件夹开始，逐层进入每个文件夹，直到找到 `"Towers.txt"` 文件。然后，你必须对一个包含不是几十或几百个文件的文件夹调用文字处理程序。逐一导航每个文件夹直到找到通所需文件的正确文件夹路径，确实是非常枯燥的。

如果这种技术还不够快，考虑一下 Linux 命令。它的工作原理与 `find` 命令几乎完全相同，不同在于它使用一个包含引用指针索引的数据库来几乎瞬间定位文件和文件夹。人们可以在几分之一秒找到隐藏在成千上万文件堆中的文件。

通过使用文本而不是图标和 GUI，你可以轻松处理任意宽度和深度的树结构。这并不是说你不能在 Windows 下操作树结构。它们在 Windows 下只是更加繁琐。随着数据量的增加，点击越来越多的对象变成了一项艰巨的任务。另一方面，使用文本允许你非常精确地指定要访问的内容，即使它嵌套在很多层之下。

## 原则 1：小即是美

在 Windows 3.1 早期，Microsoft Windows 是一个覆盖在更小的 MS-DOS 之上的小型 GUI（图形界面）。然而，随着时间的推移，它变成了一个规模庞大的巨兽。尽管有了本应有助于减少空间占用的共享库，像 Microsoft Office 和 Internet Explorer 这样的应用程序现在因其巨大的体积而获得了“臃肿软件”（bloatware）的流行俗号。如果你认为它们之所以这么大是因为提供了这么多功能，我邀请你回顾关于“人的三个系统”的讨论。这些都是遭受“第二系统综合症”应用程序的绝佳案例。当微软最终意识到这些应用程序需要变小而不是变大时，它就已经踏上了通往第三系统的道路，我们已经确定这是三者中最好的。在此期间，我们不得不硬着数百个功能，这些功能对于增强我们执行这些应用程序初衷的核心任务的能力几乎毫无帮助。
