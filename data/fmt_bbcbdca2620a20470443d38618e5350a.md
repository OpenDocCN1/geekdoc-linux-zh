## 循环

日常生活充满了重复的活动。每天上班、遛狗和切胡萝卜都是涉及重复一系列步骤的任务。让我们考虑切胡萝卜的情况。如果我们用伪代码来表示这种活动，它可能像这样：

## break and continue

## 故障排除

现在我们的脚本变得越来越复杂，是时候看看出现问题时会发生什么了。在本章中，我们将查看脚本中发生的某些常见错误，并检查一些可以追踪和消除问题的有用技术。

## 语法错误

一类常见的错误是语法错误。语法错误涉及对 shell 语法某些元素的输入错误。shell 在遇到此类错误时将停止执行脚本。

在后续讨论中，我们将使用这个脚本来演示常见的错误类型：

```bash
#!/bin/bash
# trouble: script to demonstrate common errors
number=1
if [ $number = 1 ]; then
    echo "Number is equal to 1.
else
    echo "Number is not equal to 1"
fi
```

> 按照写法，此脚本运行成功：

```
[me@linuxbox ~$ trouble]
Number is equal to 1.
```

## 缺少引号

让我们编辑脚本，删除第一个 echo 命令之后参数末尾的引号。

```bash
#!/bin/bash
# trouble: script to demonstrate common errors
number=1
if [ $number = 1 ]; then
    echo "Number is equal to 1.
else
    echo "Number is not equal to 1."
fi
```

发生的情况是：

```
[me@linuxbox ~$ trouble]
/home/me/bin/trouble: line 10: unexpected EOF while looking for matching ''
/home/me/bin/trouble: line 13: syntax error: unexpected end of file
```

它产生了两个错误。有趣的是，错误消息报告的行号并不是删除缺失引号的地方，而是程序中后得多的地方。如果我们在缺失引号后继续追踪程序，就能看到原因。`bash` 会继续寻找闭合引号，直到找到它，而它恰好在第二个 `echo` 命令之后。之后，`bash` 变得非常困惑。后续 `if` 命令的语法被破坏，因为 `fi` 语句位于一个被引号引用（但未关闭）的字符串中。

在长脚本中，这种错误可能很难找到。使用带有语法高亮的编辑器会有帮助，在大多数情况下，它会以与其他类型的 shell 语法不同的方式显示引用字符串。如果安装了完整版本的 `vim`，可以通过输入此命令启用语法显示：

```vim
:syntax on
```

## 缺少或意外的标记

另一个常见错误是忘记完成复合命令，例如 `if` 或 `while`。让我们看看如果删除 `if` 命令中 `test` 之后的分号会发生什么：

```bash
#!/bin/bash
# trouble: script to demonstrate common errors
number=1
if [ $number = 1 ] then
    echo "Number is equal to 1."
else
echo "Number is not equal to 1."
fi
```

# 结果如下：

```
[me@linuxbox-$ trouble]
/home/me/bin/trouble: line 9: syntax error near unexpected token 'else'
/home/me/bin/trouble: line 9: 'else'
```

再次，错误消息指向了一个发生于实际问题之后的错误。

发生的情况非常有趣。正如我们所回忆的，`if` 接受命令列表并评估最后一个命令的代码。在我们的程序中，我们意图让这个列表由单个命令 {（即 `test` 的同义词）组成。`[` 命令紧随其后，作为参数列表出现，在我们的案例中，那是四个参数：`number`, `1` 和 `]`。在删除分号后，`then` 也被添加到列表中，这在语法上是合法的。

下一个 `echo` 命令也是合法的。它被解释为命令列表中的另一个命令，`if` 将评估其退出码。接下来遇到了 `else`，但它的位置是错误的，因为 shell 将其识别为保留字（对 shell 有特殊含义的单词）而不是命令名称，这就是错误消息的原因。

## 意外的扩展

错误可能会在脚本中间歇性发生。某些时候脚本运行良好，另一些时候会因为扩展的结果而失败。如果我们恢复缺失的分号，并将 `number` 的值更改为空变量（如下所示），我们演示了：

```bash
#!/bin/bash
# trouble: script to demonstrate common errors
number=
if [ $number = 1 ]; then
  echo "Number is not equal to 1."
else
  echo "Number is not equal to 1."
fi
```

运行此更改后的脚本会得到以下输出：

```
[me@linuxbox-$ trouble]
/home/me/bin/trouble: line 7: [: = unary operator expected
Number is not equal to 1.
```

我们得到了这个相当晦涩的错误消息，随后是第二个 `echo` 命令的输出。问题在于 `test` 命令中 `number` 变量的扩展。当命令

```
[ $number = 1 ]
```

在 `number` 为空的情况下进行扩展时，结果是

```
[ = 1 ]
```

这是无效的，并产生了错误。`=` 运算符是一个二元运算符（它要求每边都有值），但第一个值缺失了，所以 `test` 命令期望一个一元运算符（例如 `-a`）。此外，由于 `[ $number = 1 ]` 在 `number` 为空的情况下进行了扩展，结果是 `[ = 1 ]`，它是无效的，并产生了错误。`=` 运算符是一个二元运算符（它要求每边都有值），但第一个值缺失了，所以 `test` 命令期望一个一元运算符（例如 `-a`）。

## 逻辑错误

与语法错误不同，逻辑错误阻止阻止运行。脚本会运行，但不会产生预期的结果。常见的有几种类型：

- 错误的条件表达式：很容易出现逻辑错误。
- 差一（Off by one）：在编写计数器时，可能会运行过头或终止过早。
- 意外情况：大多数逻辑错误都是源于程序遇到了未预见的数据。

## 防御性编程

编程时验证假设是非常重要的。这意味着要对所使用的程序和命令的状态进行仔细评估。这是一个基于真实故事的例子。一位不幸的系统管理员写了一个脚本在一个重要服务器上执行维护任务。脚本包含以下两行代码：

```bash
cd $dir_name
rm *
```

只要变量 `$dir_name` 中指定的目录存在，这两行代码在本质上就没问题。但如果它不存在呢？在这种情况下，`cd` 命令失败，脚本将继续执行下一行，并删除工作目录中的文件。这完全不是预期的结果！这位不幸的管理员因为这种设计破坏了服务器的重要部分。
