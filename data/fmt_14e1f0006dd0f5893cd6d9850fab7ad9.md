## 监控系统负载

你是否见过系统随着等待状态和运行时间统计数据的增加而变慢，并最终系统崩溃？我见过，当所有的“头（警告标志）”开始从方块上冒出来时，那场面可并不好看。在本章中，我们将介绍一些监控 Unix 系统负载的技术。当系统在重负载下运行不顺畅时，有很多可能的原因。系统可能有一个失控的进程，每秒钟产生大量的僵尸进程；或者由于系统管理员之间的竞争，看谁的系统可以在重启的情况下运行最久，系统可能已经运行了一多一年。无论如何，我们都希望在系统负载的早期阶段主动捕捉症状。

监控系统负载时，只有三个基本点需要关注。首先是查看 `uptime` 命令产生的负载统计信息。该输出表示 AIX 中过去 5、10 和 15 分钟内运行队列中的平均任务数，而在 HP-UX、Linux 和 Solaris 中则是过去 1 分钟。第二个要查看的测量指标是内核/用户/应用程序的 CPU 使用率、I/O 等待时间和空闲时间的百分比。这四项指标可以通过 `iostat`、`vmstat` 和 `sar` 的输出获得。我们将逐一查看这些内容。监控 CPU 负载的最后一步是找到“CPU 大户”。大多数系统都有类似 `top` 的监控工具，它可以按 CPU 使用率降序排列显示 CPU 进程用户。

我们还可以使用 `ps aux` 命令，它按从高到低显示每个进程的 CPU 使用率。我们将在本章查看这些内容。首先，让我们看看这些使用的命令的语法。

## 语法

与 Unix 一样，监控系统负载的方法不止。我们可以使用以下任何命令来获取系统负载统计信息：`uptime`、`iostat`、`sar` 和 `vmstat`。为了说明每种命令的能力，我们将逐一查看每一个命令。

### uptime 语法

使用 `uptime` 命令是获取系统负载测量值最直接的方法。`uptime` 命令输出的一部分是对过去 5 分钟、10 分钟以及最后一次测量（平均值为 15 分钟）内运行队列平均长度的直接度量。对于 HP-UX、Linux 和 Solaris，`uptime` 命令是对过去 1 分钟、5 分钟以及最后一次测量（平均值为 15 分钟）内运行队列平均长度的直接度量。运行队列的长度是通过在一段时间内等待 CPU 的进程平均数来衡量 CPU 忙碌程度的。

在使用 `uptime` 命令时我们需要加入一些逻辑，因为输出字段取决于自上次系统重启以来的持续时间，而且 Unix 可能会倾向于显示我们正在运行的内容。我们将测试这些这些选项，并提供一个与 Unix 变体和自上次系统重启以来的时间相关的字段提取表。我们稍后会看到。第一个是 1-9 分钟，第二个是 1-23 小时，第三个测量值是系统运行超过 24 小时的情况。在系统运行至少一天后，我们必须重新考虑小时和分钟！信不要相信，负载字段在每天中都会持续浮动。当系统达到重启当日的整小时（精确到分钟）时，会增加一个 `hr` 字段；这也是为了纪念小时的。

### AIX

当 AIX 系统运行 26 分钟时，显示此 `uptime` 输出。我们需要的字段是第 `9` 位置。

# uptime
01:46PM  up 26 mins,  7 users,  load average: 3.11, 1.38, 0.58
```

当 AIX 系统运行 1 小时 22 分钟时，显示此 `uptime` 输出。我们需要的字段在第 `8` 位置。

```

当 AIX 系统运行 2 天 22 分钟 3 分钟时，显示此 `uptime` 输出。我们需要的字段在第 `10` 位置。

```bash

```

当 AIX 系统运行 21 天恰好 17 分钟时，显示此 `uptime` 输出。我们需要的字段在第 `11` 位置。

09:16PM up 21 days, 17 mins, 9 users, load average: 1.31, 1.82, 1.63
