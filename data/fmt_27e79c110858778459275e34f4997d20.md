
要理解为什么 HTTP 容易受到此问题的影响，需要理解为什么会有待处理的连接请求。服务器队列请求的原因有两个：要么是在等待三次握手的完成，要么是在等待服务器进程执行 `accept()` 调用。为了建立 TCP 连接，客户端发送带有 SYN 标志的连接请求。服务器通过发送设置了 SYN 和 ACK 标志的数据包响应，然后等待客户端发送最后的 ACK 来确认响应。连接请求被放入积压中。一旦建立了 TCP 连接，服务器进程将执行 `accept()` 从队列中移除连接。在繁忙的服务器上，该系统调用执行可能会延迟，导致连接在队列中停留一段时间。

通常情况下，服务器进程会及时调用 `accept()`，这不会导致积压队列填充。然而，三次握手所需的完成确实会导致队列填充并丢弃待处理请求。

Microsoft Windows NT 4.0 的最大等待队列（backlog）大小为 6。

对于繁忙的 Web 服务器，系统管理员应该考虑将等待队列大小从默认值增大。未能这样做可能会有效限制其 Web 服务器与互联网的整体可用性。

注意：填充特定进程的等待队列已曾用于互联网上许多多次广为人知的拒绝服务攻击。攻击者会向 Web 服务器发送包含伪造源 IP 地址的 TCP 连接请求，而这些地址是无法触达的。Web 服务器会向这些伪造地址发送其 SYN 和 ACK 数据包——从而将请求放入等待队列中。由于无法到达伪造地址，服务器将永远接收不到响应，最终在 75 秒后导致请求超时。

为了对 Web 服务器实施拒绝服务，攻击者只需要每隔 60 到 70 秒发送足够数量此类的消息（约 10 条）即可。这样，等待队列将一直处于满载状态，导致无法进行访问。

## 连接终止

在繁忙服务器上运行 HTTP 可能会极大地消耗可用系统资源。上一节概述了服务器如何可能填满其等待队列，并在系统资源重新分配之前阻止创建新的 TCP 连接。在本节中，我们将研究 Web 服务器如何由于处理已建立 TCP 连接终止的方式而耗尽可用系统资源。

HTTP 协议的操作会导致已建立的 TCP 连接在数据传输完成后立即终止。TCP 连接的终止由 Web 服务器发起，完成 TCP 协议规范定义的“主动关闭”（active close）。这是通过向客户端发送带有 FIN 标志的 TCP 数据包来实现。接收后，客户端将返回确认包，然后完成规范概述的“被动关闭”（passive close）——涉及向 Web 服务器发送带有 FIN 标志的 TCP 数据包并等待服务器确认。

TCP 协议规范允许客户端或服务器对任何连接执行主动关闭。然而，执行此操作的一端必须将连接置于名为 TIME-WAIT 的状态。这样做是为了确保任何滞留包都能被妥善处理。在 TIME-WAIT 期间，连接信息——存储在名为事务控制块（TCB）的结构中——必须被保存。

注意：TIME-WAIT 值计算为等于最大段寿命的两倍（这就是为什么它通常被称为 2msl 值）。段寿命与网络内 IP 数据报的存活时间（TTL）值有关。等待 TIME-WAIT 持续允许 TCP 确保连接被正确关闭——执行主动关闭的主机需要留存足够的时间，以便另一端可以传输其 FINAL 包——即使某些确认包丢失也是如此。

通常，由已建立 TCP 连接的客户端端执行主动关闭。HTTP 应用的操作反转了这一点——由 Web 服务器发起关闭。其最终效果是，某些服务器资源在 TIME-WAIT 期间无法被重新分配。

UNIX 服务器分配固定数量的 TCB——其值通常可配置到最大 1024。在繁忙的 Web 服务器上，所有可用的 TCB 可能会被临时用尽，导致客户端显示“找到网站，正在等待回复”的消息。可以使用 `netstat` 程序来确定当前处于 TIME-WAIT 状态的待处理 TCB 数量。

## 通信协议操作——TCP 与拥塞管理

对 HTTP 的一些主要批评与其对底层通信协议的使用效率低下有关。TCP 协议被设计为一种窗口化通信协议。此类协议允许接收站通过提供关于其当前能够从发送端接收多少数据的指示来实施某种程度的流量控制。其目标是让接收站向发送端指示其处理发送数据的速度有多快。

重要的是，窗口的使用可能没有考虑连接网络在传输公告窗口大小内数据量的能力。考虑两个网络主机之间的数据交换：接收站将向发送端公告其能够接收的数据量，最高为某个最大值。发送站将传输请求的数据量，接收端将其放入缓冲区中。接收站将从这些缓冲区中读取数据，释放出空间以接收更多发送端的数据。接收端将请求发送端传输一个窗口的数据，以填充其接收缓冲区内的可用空间。

这种操作将运行良好——前提是两个主机之间的网络能够传输请求的数据量。考虑如果两个主机连接到路由的广域链路上的情况。如果路由器或链路变得拥塞，它可能无法处理接收站宣称可以接收的所有数据。网络需要能够指示发送端减慢传输！接收站可能根据其缓冲区为空的事实而公告其能够接收给定数量的数据，但中间的网络却做不到。

慢启动算法（slow start algorithm）提供了这种功能。它是通过一种被称为“拥塞窗口”（congestion window）的操作实现的。该值根据接收站返回的确认包数量进行递增。发送端将传输数据量，该量为拥塞窗口或接收端公告的窗口大小中的较者。通过这种方式，发送端现在可以根据接收站以及网络的能力来限制其传输。这与 HTTP 有关，因为慢启动会在已建立连接上的数据传输中增加往返延迟。这是因为慢启动状态下的拥塞窗口大小被初始化为一个数据包——这意味着发送端只会传输单个数据包，然后等待接收站的确认。在收到每个确认后，拥塞窗口大小将翻倍，直到匹配接收端公告的窗口大小。

## 使用缓存减少下载
