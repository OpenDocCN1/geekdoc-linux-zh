
在大多数 Linux 内核中，`SEMMNS` 通常被设置为 `SEMMNI * SEMSSL`。这没有问题，但它假设每个用户都会登录到每个数据库。如果只有一个数据库，则没有实际需要进行任何计算，但在多个数据库上，这可能会有些浪费。但如果你预计将有一个非常大的数据库和一个非常小的数据库（例如，只有 5 个用户的开发数据库，而生产系统有 400 个用户相比之下），请考虑修改 `SEMMNS`。一个好的经验法则是：取每个数据库，使用 `pronon` 找到每个数据库的最大用户数，并将这些数字相加。每个数据库额外增加 5，并额外增加 10% 以确保安全。

在某些 UNIX 变体中，还有信号量结构体和信号量映射 (`SEMUME/SEMAP`)，但在 Linux 中这些不再被使用。

# 其他杂项参数

除了共享内存和信号量外，还有几个需要考虑的参数：

- `MAXUMEM`—进程的最大内存使用
- `NOFILES`—每个进程的最大打开文件数
- `NFILES`—全系统的最大打开文件数
- `NBUFS`—磁盘缓冲区数量

由于每个用户以及数据库进程必须连接到共享内存段，每个 Linux 进程必须访问的内存量可能比通常大得多。`MAXUMEM` 需要设置为等于 Progress 可执行文件的大小加上系统内最大的共享内存。一个好的规则是使用 `SHMSEG * SHMMAX`（这提供了可能的最大共享内存）并加上 5MB，或者直接设置为系统中的物理 RAM 数量。

正如我们稍后讨论的，某些数据库由一、二或三个操作系统文件组成。然而，使用多卷结构的较大数据库被拆分成许多操作系统文件。当使用此类数据库时，可能需要修改 `NOFILES`、`NFILES` 和 `NINODES` 参数。在 Progress V8.3 版本中，数据库可以使用的文件最大数量是 256。（V9 具有使用数千个文件的能力，因此当 V9 在 Linux 上可用时，请务必进行更好的计算。）每个用户需要三个标准的输入/输出/错误文件，加上任何创建的临时文件和打印文件（多达 12 个文件句柄，不计相关文件）。因此，`NOFILES` 永远不应高于 300。

`NFILES` 是全系统的文件数，其最大值将是用户数乘以数据库数乘以每个数据库中的操作系统文件数。记住，这只是 Progress 的使用量。Linux 本身和其他 Linux 的打开文件必须加到这个数字中。Progress 手册建议 `NFILES` 使用这个最大值，但正如你从这个计算中看到的，那个数字会变得非常大。这种计算可能是安全的，但如果每个用户都登录到每个数据库，在实际上，较小的数字可能更合适。

在只有一个数据库的站点上，这通常不是问题，但在较大的站点上，将每个数据库的用户数乘以该特定数据库的操作系统文件数。每个数据库的这些值随后将相加以创建 Progress 的使用量。计算出一个 `NFILES` 的真实值。也许应该再增加 10% 以防扩展或登录模式的影响。再对操作系统文件使用增加另一个 10%。

最后一个需要检查的参数。Progress 使用自己的缓冲区池来管理记录访问，标准的 Linux 磁盘缓冲区并不完全有用。在 RAM 紧缺的系统中，稍微减少缓冲区并将其分配给共享内存是有益的。`NBRFS` 控制缓冲区数量，但使用此参数时应谨慎。所有的打印文件、程序文件和其他操作系统文件都必须通过 Linux 磁盘缓冲区。将此值调低可能会允许数据库获得更好的性能，但会导致打印和其他磁盘访问变慢。如果有疑问，请从原始设置逐渐减少此参数。仔细观察系统在新的 Progress 程序运行时是否有打印停机和暂停。结合 Progress 工具查看缓冲区池如何影响数据库性能。关于内存平衡的更多细节见后文配置部分。

自定义设置的某些引人理由是，Progress 所需的所有其他环境变量都将根据 `$DLC` 采用默认值。将 Progress 可执行文件放入 `PATH` 中是有益的。请为所有数据库管理员将 `$DLC` 目录和 `$DLC/bin` 都添加到 `PATH` 中，这样数据库实用程序就会位于他们的路径中。

## 终端设置—PROTERMCAP

Progress 使用一个名为 Vermont Views 的类光标库进行屏幕绘制和涂图（通过带有 `vv_` 前头的错误消息进行识别）。`TERM` 值必须非常准确。Progress 有一个名为 `PROTERMCAP` 的类 termcap 配置文件，它定义了标准 termcap 不具备的额外终端属性。这些属性主要围绕 Progress 4GL 允许的广泛功能键和颜色功能。随程序分发的 `PROTERMCAP` 文件已经提供了许多终端的定义。对于 Linux，在 linux 终端类型下提供了一个 Linux 控制台的条目。对于 X 终端使用，假设使用 xterm 类型。旧的占用空间类型（如 Wyse 50、Televideo 925 等）不再支持其占用空间属性模式。请注意某些极其逼真的终端仿真器上的仿真。真实的 vt100 原始布局只有四个功能键，而真实的 vt220 在 `PROTERMCAP` 文件中为“真实”键定义了预定义的用途。虽然某些仿真器提供了额外的键，但 Progress 仅提供了中断键。你可能需要修改 `PROTERMCAP` 或切换到具有完整功能键组的仿真器。Progress 技术手册中详细描述了特定的 `PROTERMCAP` 条目，并涵盖了本书的范围。但总的来说，这里是使用 `PROTERMCAP` 的一些建议。保持原始配置文件不变。不要直接修改原始文件，而是创建它的副本，并将 Linux 环境变量 `PROTERMCAP` 设置为新 `PROTERMCAP` 文件的完整路径（这是一个有理由自定义并覆盖默认设置的情况）。终端配置中出现的另外两个问题是退格键（Backspace）和 Linux 中断。Progress 期望退格字符在 DEC 终端上由 Ctrl-? 定义（即 Delete 键）。Progress 还期望使用 Delete 键作为删除字符功能，这与某些将终端 Delete 键程序为中断的设置冲突。无论哪种情况，使用 `stty` 命令更改这些值。Ctrl-C 是 Progress 提供的通常接受的中断替代方案：

```
stty erase ^h intr ^c
```

## 客户端/服务器模式设置

如果你的访问仅通过 Telnet 仿真且是所谓的自服务客户端，则不需要额外的步骤。客户端/服务器模式不等同于通过 Telnet 访问 Linux 机器。如果你将以客户端/服务器模式访问数据库，必须编辑一个额外文件。Progress 需要机器的 TCP/IP 地址，并为通过网络访问每个数据库一个专用的 TCP/IP 端口。机器的 IP 地址应该已经通过机器的 TCP/IP 设置设置好。要预留 TCP/IP 端口，请编辑 `/etc/services`。每行的格式如下：

`name    port    protocol`

为每个数据库创建一行，将 `name` 替换为每个数据库的唯一标识符。你可以使用数据库的实际名称作为标识符以便于识别。选择当前正在使用的最后一个端口之上的端口，并在每个端口之间至少留出 500。此端口并不是唯一使用的端口，通过 Progress 的最小端口分配方案，如果多个数据库的端口太近，有时会发生冲突。Progress 的 TCP 端口不会使用 UDP。

# 配置

配置 Progress 数据库并不困难。必须做出几个决策，然后就可以准备实际数据库了。首先，我们关注 Progress 使用的目录结构，然后讨论磁盘空间与磁盘速度之间的。

## 目录结构

为 Progress 数据库配置目录结构是准备部署应用程序的重要部分。如果你只是把所有内容都丢进一个大目录而不去担心，那么这种解决方案不仅难看，而且会导致未来管理上的混乱。一个经过良好设计的组织良好的目录结构对于运行良好的站点至关重要。通常情况下，为数据库和应用程序不同用途的部分创建文件系统。这样，你就可以将文件系统映射到不同配置的磁盘上，并根据文件系统的目的进行调优，如 fs 块大小、RAID 类型，以及日志文件系统可用时的许多其他针对文件系统用途的选项。最后，应该考虑表 8.1 中的以下结构：

| 目录名称 | 用途 |
| :--- | :--- |
| `/opt/progress/dlce8b` | 为每个版本的 Progress 建立不同的目录——这使得更新、测试和潜在的回滚变得简单得多。 |
| `/mnt/db` | `.db`、`.st` 和 `.d#` 扩展都存放在这里。这应该是条条化和镜像的磁盘组，其 fs 块大小与 db 块大小完美匹配，并具有最大的可靠性和恢复选项。 |
| `/mnt/bi` `/mnt/ai` | `.bi` 和 `.ai` 文件系统应该位于镜像磁盘上，而不是条带化磁盘，具有最大的可靠性和恢复性文件特性。 |
| `/mnt/logs` | 你应该为 lg 文件和其他监控数据建立一个文件系统。每天晚上将日志扫描到此文件系统中。它不需要镜像或条带化——普通的磁盘即可。创建一个归档策略，将文件放在以 yy.mm.dd 命名的目录中以便拥有可搜索的历史。以相同的方式归档你的 `.ai` 文件。 |

这些文件系统——条带化和镜像是快速且可靠的，但不需要高度的可恢复性或适用性。全日志（Linux 可用的日志化 fs 选项）并非必要，因为你可以从备份恢复，但可靠性很重要，因为如果文件系统不可用，用户会可能会崩溃。
