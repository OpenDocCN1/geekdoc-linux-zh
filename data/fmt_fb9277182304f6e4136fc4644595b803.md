
此命令显示`/home`目录层次结构中所有以"rc"结尾的点文件的权限。如果你的用户的家目录保留在`/home`中，这会向你显示可能存在权限的用户。

# 为用户设置默认文件权限

作为系统管理员，你可以为进入你系统的所有用户文件定义默认权限设置。`umask`命令设置新文件的默认权限。

# 设置可执行文件权限

所有者应该对普通用户运行的程序文件拥有写入权限。例如，`/usr/bin`中的程序文件应该具有只有root才能读取、写入和执行的权限设置；其他所有人的设置应该只包含读取和执行。当所有者之外的人员可以写入程序文件时，可能会出现严重的安全漏洞。例如，如果root以外的人可以写入诸如`/usr/bin/zip`的程序，恶意用户就可以将真实的`zip`程序替换为木马程序，从而损害系统安全，破坏其所到任何地方的文件和目录。因此，请始终检查你系统中程序文件的权限是否正确。频繁运行`COPS`来检测权限相关问题。

### 总结

不恰的文件和目录权限通常是许多用户支持事件的原因，也是许多安全问题的根源。理解文件和目录权限对于Linux系统的系统管理至关重要。通过为文件设置默认权限、处理全局访问的文件以及`set-UID`和`set-GID`文件、利用高级`ext2`文件系统安全特性、使用如`Tripwire`、`AIDE`、`ICU`等文件完整性检查器，你可以增强系统的安全性。

可插件认证模块（PLUGGABLE AUTHENTICATION MODULES，PAM）最初由Sun Microsystems为Solaris操作系统开发。Linux-PAM项目为Linux平台提供了PAM。PAM是一套共享库，用于授予对PAM敏感的应用程序权限。

### 什么是PAM？

你可能会奇怪，为什么像`csh`、`cfhn`、`ftp`、`imap`、`linuxconf`、`login`、`rexec`、`rsh`、`su`、`login`和`passwd`等程序突然就理解了影子密码方案（见第12章），并使用`/etc/shadow`密码文件代替`/etc/passwd`文件进行身份验证。它们之所以这样做是因为Red Hat在分发这些程序时使用了强大的认证方案——PAM。这些PAM敏感的程序可以通过同时使用影子密码方案和几乎任何其他认证方案来增强你的系统安全性。

传统上，认证方案是构建在授予用户权限的程序内部的。像`login`或`passwd`这样的程序包含了身份验证所需的代码。随着时间的推移，这种方法被证明几乎是不可扩展，因为引入新的认证方案需要你更新并重新编译授予权限的程序。为了减轻权限软件开发人员编写安全认证代码的负担，PAM诞生了。图10-1显示了PAM如何工作。`(img/6d17ba5e3d859ca2b0a3b2544265_0.png)`

图10-1：PAM如何与权限程序工作

当像`/bin/login`这样的权限程序变为PAM敏感程序时，它的工作方式如图10-1所示：

1. 用户调用此类应用程序以访问服务。
2. PAM敏感应用程序调用底层PAM库执行认证。
3. PAM库在`/etc/pam.d/`中查找应用程序特定的配置文件。该文件告诉PAM需要什么类型的认证。（如果没有配置文件，则使用`/etc/pam.d/other`中的配置。）
4. PAM库加载所需的模块。
5. 这些模块让PAM与应用程序中的对话函数（conversation functions）进行通信。
6. 对话函数向用户请求信息。例如，它们要求用户密码或视网膜扫描。
7. 用户通过提供请求的信息做出响应。
8. PAM认证模块通过PAM库向应用程序提供状态。
9. 如果认证成功，应用程序执行以下操作之一：

- 授予用户请求的权限
- 通知用户过程失败

将PAM视为一种从应用程序中减轻认证负担并为应用程序堆叠多种方案的机制。例如，`/login`应用程序的PAM配置文件所示列表10-1。

列表10-1：`etc/pam.d/login`

```
###PAM-1.0

auth    required      /lib/security/pam_securetty.so

auth    sufficient    /lib/security/pam_hosts.auth.so

auth    required      /lib/security/pam_stack.so service=system-auth

auth    required      /lib/security/pam_nlogin.so

account required      /lib/security/pam_stack.so service=system-auth

password required      /lib/security/pam_stack.so service=system-auth

session required      /lib/security/pam_stack.so service=system-auth
```

在此文件中，来自`/lib/security`的多个可插件认证模块对用户进行认证。

## 表10-1: PAM模块类型

| 模块类型 | 说明 |
| --- | --- |
| auth | 执行实际的身份验证。通常，auth模块需要用户提供密码或其他身份证明。 |
| account | 处理身份验证请求的所有计数方面。通常，account模块会检查用户的访问是否符合所有访问准则。例如，它可以检查用户是否在安全主机上以及在特定时间内访问服务。 |
| password | 设置密码。 |
| session | 处理会话管理任务，例如刷新会话令牌（token）。 |

控制标志定义了PAM库如何处理模块的响应。目前允许表10-2所示的四种控制标志。

## 表10-2: PAM模块控制标志

| 控制标志 | 说明 |
| --- | --- |
| required | 此控制标志告诉PAM库要求同一行中指定的模块必须成功。当模块返回指示失败的响应时，身份验证肯定失败，但PAM会继续处理其他模块（如果有）。这可以防止用户检测到验证过程中的哪个部分失败了，因为知道这些信息可能会帮助潜在的攻击者。 |
| requisite | 此控制标志告诉PAM库一旦收到失败响应，立即终止身份验证过程。 |
| sufficient | 此控制标志告诉PAM库，如果收到成功响应，则认为身份验证过程完成。继续处理配置文件中的其他模块是没必要的。 |
| optional | 此控制标志很少使用。它消除了对模块成功或失败响应的强调。 |
