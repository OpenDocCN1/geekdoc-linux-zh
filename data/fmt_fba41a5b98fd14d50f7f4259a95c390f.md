
有很多市场原因导致你可能不想发布你的知识产权：你想领先于竞争对手，你并不拥有你知识产权之基础的所有代码等等。如果你有不打算与世界其他部分共享的知识产权，你需要非常小心，不要包含任何其他开源项目的源代码，即使这可能在其他情况下缩短你的上市时间。包含来自其他开源项目的源代码（或基于其他开源项目开发你的软件）通常会导致你的源代码受到该开源项目条款的约束——这对于那些想要维护知识产权的人来说是一件坏事。

对于应用程序代码，`Linux` 下有很多闭源应用（最著名的是 `Netscape`）。在内核空间，有很多仅二进制的内核模块的示例（例如 `DiskOn`，用于本书后后的示例）。但在内核空间中，维护负担通常是一个非常昂贵的代价。由于内核有许多更改模块接口的选项（例如 `SMP` 与 `UP`，大内存版本等），即使是单个内核发布，每个平台可能都需要多次构建。此外，内核接口会发生，导致仅二进制内核模块的所有者拥有损坏的代码需要不断修复。此外，当 bug 出现时，标准的内核开发人员可能会拒绝帮助使用仅二进制内核模块，而是将他们推给模块的所有者。

- 内核发布快速且猛烈。

`Linux` 内核的变化可能出来很快，并且在不同版本之间可能存在显著差异。如果你觉得必须跟上最新版本，这可能要求非常高。

- 内核发布并不总是按预期出现。

如果你想根据最新内核中提供的功能集来计划发布你的产品，但不想发布测试版代码，这可能会很困难。

- 很难知道你的更改是否会被采纳。

如果你对内核进行了更改，你无法确定它们会被合并到主源代码中。有时，一个运行完美的内核更改可能会被内核维护者完全拒绝，认为它在 `Linux` 哲学上是错误的。（你希望它们被采纳，以便其他人在内核接口变化时对这些更改进行维护。）

- `Linux` 不害怕破坏向后兼容性。

与其他操作系统不同，`Linux` 并不充满“陈旧代码”。也就是说，它没有许多特定版本的代码。这使得阅读源代码变得容易得多，因为没有充斥着大量的 `#ifdef` 和兼容性代码。遗憾的是，这意味着某些在 `Linux` 下运行良好的程序可能会在较新的内核上停止运行。这通常是驱动程序维护者的责任，确保驱动程序是最新的，因此你可能需要由于接口消失而花费时间修复 bug。

# GNU 如何影响你

如果你打算在项目中使用 `Linux`，你必须理解的两个重要许可是 `GNU` 通用许可证（`GPL`）和 `GNU` 语言许可通用许可证（`LGPL`）。`Linux` 操作系统的源代码受 `GPL` 保护，而 `GNU` `C` 受 `LGPL` 保护。附录 A 和 B 为这些许可的全文。

## GPL 和 LGPL 的相似之处

由于 `GPL` 和 `LGPL` 都是自由软件基金会的创作，它们非常相似。它们都具有以下重要属性：

- 拷贝左（Copyleft）

Copyleft 术语是由 `GNU` 项目的人发明的，是版权（copyright）一词的双关语。Copyleft 指开源许可中的条款，它阻止个人或公司获取受 `GPL` 许可的源代码副本、进行修改、更改许可，从而“封闭”他们修改过的原始源代码版本。一旦一段代码被放在 `GPL` 或 `LGPL` 下，该代码本身及其所有衍生作品对任何相关方都以源代码形式可用。如果第三方对此代码进行更改并分发，他们必须向其分发软件的任何人提供这些更改和原始源代码。

首先，当新代码版本出现时，你不需要反复重新应用（修复）你的补丁。这可能会变得非常累人，尤其是当代码发布频繁且你想保持与最新状态时。

其次，`GPL` 要求你在发布产品时，要么附带更改的源代码，要么提供有效期至少三年的源代码书面报价。通常接受的观点是，如果你的更改已经在标准分发版中可用，你只需要引导想要这些更改的人指向标准分发版即可。

《`GNU` 通用公共许可协议》(`GPL`) 和《`GNU` 语言许可公共许可协议》(`LGPL`) 的两个版本都包含在本书的附录中。如果你正在考虑将 `Linux` 作为你嵌入式应用的操作系统，你应该花时间阅读并理解这些协议。与许多法律术语不同，从软件开发者的角度来看，这些协议非常易读且易懂。

### GPL 和 LGPL 有何区别

在 `GPL` 或 `LGPL` 下许可源代码会产生相似的结果。对任何代码的任何更改都必须对感兴趣的人开放，以此此类推。唯一真正的区别在于专有代码是否可以与开源代码链接。`LGPL` 允许实体将其专有代码链接到开源代码，并分发生成的二进制文件而不受限制，只要这些二进制文件是动态链接的。二进制文件仍然受所有者要求的任何专有许可保护。

最明显的例子是 `C` 库 `glibc`。由于它是基于 `GPL` 发布的，像 `Oracle` 这样的专有软件公司可以在内部编译并链接其数据库应用程序，将二进制文件放在 `CD` 中并仅发送这些二进制文件。这些二进制文件将在 `Linux` 内核下运行（内核受 `GPL` 保护），使用动态 `glibc` `C` 库（后者受 `LGPL` 保护）。如果 `Oracle` 决定对 `C` 或 `Linux` 操作系统进行更改，他们必须将这些更改提供给任何需要的人，但他们不需要提供数据库本身，因为它是与 `LGPL` 的 `glibc` 动态链接的。

如果你的整个嵌入式应用环境空间非常紧缺，且整个应用位于单个可执行文件中，你可能想对其进行静态链接。如果你这样做并使用了 `GPL` 下的库（例如 `glibc` 库），你将不得不向所有客户提供目标代码或源代码。`GPL` 的第 66 允许你根据需要提供目标代码的书面报价。因此，对于嵌入式设备制造商来说，静态链接代码可能会变成维护、支持和责任的噩梦。我建议动态链接你的代码，以免掉入这个陷阱。

### Linux 何时不适用？

现在我们谈到 `Linux` 何时不适用的话题。显然，没有任何操作系统适用于所有情况。由于 `Linux` 携带的负担很少，它涵盖了比大多数系统更多的情况——但它对所有事情来说都不是完美的。在决定使用 `Linux` 作为你嵌入式应用的操作系统之前，你应该仔细考虑以下几点。

- 你可能无法接受 `GPL`。

嵌入式开发人员最关心的问题可能是 `GPL` 和 `LGPL` 许可协议。这些开源许可是好事；没有它们，我们甚至没有在嵌入式应用中使用 `Linux` 的选择——嵌入式应用的巨大增长将会缓慢得多，并且仅限于专有软件。然而，这些许可使得某些基于 `Linux` 的应用无法上市。

- `Linux` 很大。

对于任何考虑将 `Linux` 作为嵌入式操作系统的人来说，另一个关注领域是它的尺寸。即使你从操作系统中提取出所有内容，它仍然很大。如果你正在构建一个蚂蚁大小的纳米探针，并且只有 100 字节内存来运行 `Linux`，那么 `Linux` 并不适合你。压缩后大约占用 400KB。当启动时进行压缩时，它将占用近一兆字节。（尽管 `Linux` 运行内核加上几个基础用户空间应用大约需要 800KB。）对于一个真正的嵌入式应用，最小的现实内存大小可能是 2MB。

- 适用性。

对于某些嵌入式应用，其他操作系统更合适。例如，如果你正在构建一个手持式 PIM（个人信息管理器），在功能和尺寸上超越 `PalmOS` 将花费大量工作。你不需要精力放在你的应用程序上，而是必须精力放在让手笔工作、小型内存管理等上。

- 安全性。

关于开源操作系统是否比闭源源码操作系统更安全的争论。一方面，无法访问你嵌入式应用源代码的坏人无法盯着那些源代码看几天，试图寻找攻击你设备的方法。这个坏人仅限于尝试随机攻击，直到他找到一个有效的方法，或者在他所选的操作系统中找到通用漏洞。

另一方面，如果坏人可以弄清楚你正在使用哪个版本的 `Linux`，他就可以获取源代码并寻找漏洞。问题是，他能找到吗？许多人认为开源软件更安全，因为有许多眼睛在查看代码并修复安全问题。

每个论点都有其理由。底线是：如果你使用 `Linux` 且你的嵌入式应用在网络上存有价值的数据，你应该确保可以向客户分发安全更新。安全问题会被发现，如果你无法升级嵌入式应用上的软件，你就会遇到问题。

- 市场因素。

当然，许多非技术问题可能要求你选择另一种操作系统。如果你使用 `OS X` 而不是 `Linux`，市场可能会向你的创业公司投入资金。

### 嵌入式 Linux 工作坊

在本书中，我将指定硬件并提供让你运行的软件。现在有许多 `Linux` 开发小组，它们都有很棒的主意。它提供的功能集已足够开始工作：

- 它具有基于 Web 的界面，你可以通过网络进行管理。
