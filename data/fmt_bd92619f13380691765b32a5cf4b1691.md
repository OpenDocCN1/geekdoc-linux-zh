
互斥锁的概念在很大程度上与此前定义的阻塞概念相吻合（第 5.2 节）。被称为互斥锁（Mutexes）的同步原语能够阻止一段代码在多个流中同时执行。实际上，互斥锁是操作系统级阻塞的一种实现。顾名思义，互斥锁消除了互斥性（注：此处原文用词略有歧义，通常指实现互斥访问）。其主要任务是在代码已在某个线程中执行时，阻塞所有试图访问该代码的线程。互斥锁有两种状态：空闲和忙。初始状态为“空闲”，并支持两种可能的原子操作。

- **获取互斥锁**（`mutex_lock`）：如果互斥锁处于空闲状态，则将其置为忙，流继续执行（进入临界区）；如果互斥锁处于忙状态，则流进入待机状态（即“等待互斥锁”或“锁定在互斥锁上”），执行权交由另一个流。获取互斥锁的流被称为该互斥锁的所有者：

```c
mutex_lock ( mutex_t mutex )
{
    if (mutex.state == free)
    {
        mutex.state = locked;
        mutex.owner = this_thread;
    }
    else
        sleep ();
}
```

- **释放互斥锁**（`mutex_unlock`）：互斥锁变为空闲；如果有多个流在等待，则从中选择一个，该流开始执行，占用互斥锁并进入临界区。在大多数实现中，流的选择是随机的。只有所有者才能释放互斥锁。以下是该操作的伪代码：

```c
mutex_unlock (mutex_t mutex)
{
    if (mutex.owner != this_thread)
        return error;
    mutex.state = free;
    if (waiting_threads ())
        wakeup (some_thread);
}
```

某些实现提供了第三种操作：尝试获取互斥锁（`mutex_trylock`）：如果互斥锁空闲，则行为类似于 `mutex_lock`；如果忙，则立即返回错误并继续执行。以下是使用互斥锁实现临界区的最简单实现。

```c
mutex_t mutex;
mutex_lock (mutex);
// 临界区
mutex_unlock (mutex);
```

互斥锁与二元信号量的主要区别在于，互斥锁只能由其所有者释放，而信号量可以由任何有权访问它的流进行修改。

## 进程间通信

到目前为止，我们讨论的是同一进程内流之间的交互。这种交互的主要特征是数据交换在技术实现上的便捷性——一个进程中的流使用同一个地址空间，因此可以像访问自己的数据一样自由访问共享变量数据。由于数据交换在实现上没有技术困难，在此情况下需要解决的主要问题就是流的同步。

另一方面，由于每个线程都在进程的地址空间内执行，因此组织不同进程间流交互的任务往往是一个问题。这本身涉及进程间交互（进程间通信或 IPC）的问题。对于不同进程的流而言，同步问题同样相关，但在大多数情况下，它们并不基于共享数据的概念（因为进程之间默认不存在共享数据）。此外，还需要解决在受保护的地址空间之间安全交换数据这一挑战。解决方案的方法定义了不同类型的进程间交互。

## 进程间交互的类型

进程间交互的实现通过三种基本方法完成：*消息传递*、*内存分配*和*映射内存*。

另一种 IPC 方法是考虑此前讨论过的信号技术。

## 映射内存

在许多操作系统中，映射内存是其他类型的进程间交互和系统决策所基于的基本系统机制。当然，映射内存通常与文件系统接口结合使用，在这种情况下，我们谈论的是*映射到内存的文件*（内存映射文件）。

这项技术确保特殊的系统调用（通常是 `mmap()`）将进程地址空间的一部分唯一地映射到包含该部分的文件。此后，对该内存的写入操作会导致映射文件的内容发生变化，这立即对所有有权访问该文件的应用程序可见。其他应用程序也可以在其地址空间中映射同一个文件，并通过该文件进行通信。

## 结论

- 同一交互进程中的流可以访问托管在该进程地址空间中的共享数据。任何流都可以随时修改这些数据，从而导致竞争状态，其结果取决于流的执行顺序。

- 流同步机制用于确保对共享数据的正确访问；其中最主要的是确保互斥访问，即在特定时间只有一个流可以访问此类数据。使用阻塞来实现互斥。

- 可以使用各种同步原语来解决同步问题。最简单的原语包括信号量、互斥锁、条件变量、读写锁和屏障。

- 更高级的机制是监视器（monitor）概念，它结合了互斥锁和条件变量，并设定了一些规则来协调它们的交互，以保护共享数据。

`monitors` 是实现流同步的最一致的方法。

# 第 6 章：内存管理

不同类型的内存被组织成一个层次结构。在该层次结构的较低层级，内存具有更大的容量，但成本较低且速度较慢；随着层次结构向上移动，内存变得更加昂贵且速度更快（其容量也随之变小）。最便宜且最慢的存储设备是硬盘。它也被称为辅助存储。更快且更昂贵的内存存储在安装在计算机上的内存芯片中——这种内存被称为主内存。更快的存储设施具有不同的缓存处理器，至少这些缓存的容量更为有限。

内存管理是一项相当困难的任务。所需的内存特性往往识别得不够充分，为了不妨碍用户的工作，必须实现不同内存类型的协调机制。因此，当前应用程序可能无法完全放入主内存中，而未使用的代码可以占用存储在硬盘上的时间和 COBOL 代码。在本节中，我们将探讨使用主内存的技术。

### 虚拟内存技术基础

我们首先考虑引入虚拟内存概念的前提条件。在这种情况下，每个进程都加载到其自身的连续物理内存部分中，下一个进程紧随前一个进程之后开始。如果分析这种方法的内存分配特性，可能会产生以下问题。

- 我如何执行需要比计算机上安装的物理内存更多的内存的进程？

- 当进程在错误地址（例如 P2 在 `0x7500` 处）执行写操作时会发生什么？

- 如果一个进程（如 P1）需要更多内存来执行，我该怎么办？

- 进程何时能获知执行它的特定物理内存地址、哪个内存将开始执行它，以及代码中使用的内存地址应如何转换？

- 如果进程不需要分配给它的所有内存，我该怎么办？

将进程直接加载到物理内存中无法回答这些问题。显然，需要一些内存转换工具，以便进程可以使用与物理内存地址不同的地址集。在了解这些地址的特性之前，让我们简要探讨一下应用程序的组成和加载特性。

程序通常作为磁盘上的二进制可执行文件存在，这是编译和布局后获得的。它必须被加载到内存（进程地址空间）中才能执行。现代架构允许进程位于物理内存的任何位置，同一个程序可以容纳加载到不同内存位置的不同进程。事先无法知道程序将被加载到哪个内存区域。

在执行期间，进程访问不同的地址，特别是当调用函数时，它使用其地址（这是代码地址），全局变量访问存储该变量值的内存地址（这是数据地址）。

程序员通常不会直接在程序中使用内存地址，而是使用符号名称（函数、全局变量等）。通过编译和布局，这些名称被链接到重定位地址（这些地址以相对单位指定，例如“模块开头起 100 字节处”）。在运行程序时，重定位地址反过来被绑定到内存中的绝对地址。实际上，每次绑定都是一个地址集到另一个地址集的映射。

- 内存保护。发生在进程代码中的寻址错误应仅影响该进程的执行。当 P2 进程在 `0x7500` 处执行写操作时，必须被错误中断。内存安全策略是为每个进程存储一个有效的地址范围，并检查每次内存访问操作是否属于该范围内的地址。

- 不绑定到物理内存地址。无论进程的内存位置和物理内存大小如何，都可以执行该进程。进程地址空间被分配为一个大的静态地址集，其中每个地址都是可重定位的。处理器和硬件应能够将这些地址转换为主内存的物理地址（同一地址在不同时间或不同进程中可能对应不同的位置，包括其地址）。

### 虚拟内存的概念

虚拟内存——一种在进程使用的内存地址和桌面应用程序使用的物理内存地址之间引入额外一层转换的技术。这种转换应确保内存得到保护，且进程不绑定到物理内存地址。

借助虚拟内存，进程地址空间的物理内存可以是碎片化的，因为进程占用的大部分内存大部分时间都是空闲的。存在所谓的“九零一零规则”或“局部性规则”，该规则指出进程中 90% 的内存访问仅涉及其地址空间的 10%。你可以移动地址，使得仅将当前实际使用的进程地址空间部分映射到主内存。

在这种情况下，地址空间的未使用分区可以映射到较慢的内存，如硬盘空间，而此时其他进程可以使用主内存，而主内存之前正显示这些分区的地址。当需要某个分区时，其数据从磁盘加载到主内存，也许取代了在特定时刻变得不再需要的分区（这些分区现在将被存储在磁盘上）。从磁盘读取数据的速度如此慢，因此关键在于内存寻址时间。

通过这种方式，你可以显著增加进程地址空间的大小，并确保大于主内存的进程得以执行。

### 虚拟内存实施问题：内存碎片化

使用虚拟内存时出现的主要问题是其实施的效率。因为每次访问内存时都需要进行地址转换，如果不谨慎地实施这些转换，可能会对整个系统的性能产生最坏的影响。如果大多数内存访问实际上迫使系统访问磁盘（比主内存慢数万倍），那么运行这样的系统将几乎是不可能的。虚拟内存实施性能提升的问题将被讨论。
