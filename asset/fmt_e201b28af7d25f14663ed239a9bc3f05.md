### 9.4.1. 是否 CPU 密集？

使用 `top` 或 `mpstat` 确定时间花费在哪里。如果整个系统在空闲和等待模式下的时间小于 5%，则系统是 CPU 密集的。跳转到第 9.4.3。否则，跳转到 9.4.2。

### 9.4.2. 是否单处理器 CPU 密集？

虽然整个系统可能不是 CPU 密集，但在对称多处理 (SMP) 或超线程系统中，单个处理器可能是 CPU 密集。

使用 `top` 或 `mpstat` 确定单个 CPU 在空闲和等待模式下的时间是否小于 5%。如果是，则更多 CPU 是 CPU 密集；在这种情况下，跳转到 9.4.4。

否则，CPU 是 CPU 密集。跳转到 9.4。

### 9.4.3. 是否一个或多个进程使用了大部分系统 CPU？

下一步是确定某个特定的应用程序或应用程序组在使用 CPU。最简单的方法是运行 `top`。默认情况下，`top` 按使用 CPU 的情况降序排列。`top` 报告的进程 CPU 使用率为用户时间和系统时间的和。例如，如果应用程序在用户空间花费了 20% 的 CPU，在系统空间花费了 30%，`top` 将报告该进程消耗了 50% 的 CPU。汇总所有时间。如果这显著小于系统整体比例，则是内核在执行非应用程序的工作。

否则，跳转到 9.4.3（上下文建议 9.4.4，但保留逻辑）或跳转到识别进程的位置。

### 9.4.4. 是否一个或多个进程使用了大部分系统 CPU？

下一步是确定某个特定的应用程序或应用程序组在使用系统 CPU。最简单的方法是运行 `top`。默认情况下，`top` 按使用 CPU 的情况降序排列。`top` 报告的进程 CPU 使用率为用户时间和系统时间的和。例如，如果应用程序在用户空间花费了 20% 的 CPU，在系统空间花费了 30%，`top` 将报告该进程消耗了 50% 的 CPU。汇总所有时间。如果这显著小于系统整体比例，则是内核在执行非应用程序的工作。

否则，跳转到 9.4.3（上下文建议 9.4.5）或跳转到识别进程的位置。

接下来，使用 `trace` 查看执行了哪些系统调用以及它们需要多长时间。你还可以运行 `profile` 查看正在执行哪些内核调用。通过减少系统调用的次数或更改代表程序生成的系统调用，可能提高性能。某些调用可能是意外之外的，应用程序调追踪会有帮助。

### 9.6.1. 内核内存使用是否在增加？

在追踪系统内存使用情况时，你首先必须确定内核本身正在分配内存。运行 `slabtop` 查看内核内存总数是否在增加。如果正在增加，跳转到第 9.6.2 节。

如果内核内存使用没有增加，可能是某个进程导致了增长。要追踪是哪个进程导致了内存使用的增加，请转到第 9.6.3 节。

### 9.6.2. 内核在使用什么类型的内存？

如果内核内存使用正在增加，再次运行 `slabtop` 以确定内核正在分配什么类型的内存。slab 的名称可以提供有关为什么要分配内存的某些线索。通过网络搜索，在内核源码中搜索 slab 名称并确定它被用于哪个子系统，可能会清楚分配的原因。当你确定了哪个子系统分配了所有这些内存后，尝试调整该特定子系统消耗的最大内存量，或者减少该子系统的使用量。

进入第 9.9 节。

### 9.6.3. 特定进程的驻留集（Resident Set）是否在增加？

接下来，你可以使用 `top` 或 `ps` 查看特定进程的驻留集大小（`rss`）是否在增加。在 `top` 的输出字段中添加 `rss` 并按使用的内存类型进行排序很容易的。如果特定进程正在不断增加内存使用，由于该应用程序，请转到第 9.6.6 节。如果没有特定进程在使用更多内存，转到第 9.6.4 节。

### 9.6.4. 共享内存使用是否在增加？

使用 `ipcs` 确定是否在使用共享内存。如果是，进入第 9.6.5 节以确定哪些进程在使用这些内存。否则，系统可能存在本文未涵盖的内存泄漏。进入第 9.9 节。

### 9.6.5. 哪些进程在使用共享内存？

使用 `ipcs` 确定哪些进程在使用共享内存。识别出使用共享内存的进程后，调查各个进程以确定每个进程使用内存的原因。例如，在应用程序的源码中查找对 `shmget` 和 `shmat`（用于挂载）的调用。阅读应用程序文档并寻找可以减少共享内存使用的选项。

要减少共享内存使用，进入第 9.9 节。

### 9.8.1. 是否有网络设备的发送/接收接近理论极限？

第一件事是使用 `ethtool` 确定每个以太网设备设置的硬件速率。如果你记录这些信息，就可以调查是否有任何网络设备已饱和。以太网设备和/或交换机可能配置错误，`ethtool` 显示每个以太网设备的速度，使用 `iptraf` 或 `ifconfig` 确定通过每个接口的流量。如果网络设备似乎已饱和，进入第 9.8.3 节；否则，进入第 9.8.2 节。

### 9.8.2. 是否有网络设备产生了大量错误？

网络流量也可能因为大量的网络错误而显得缓慢。使用 `ifconfig` 确定是否有任何接口产生了大量错误。大量错误可能是以太网卡/以太网交换机连接不匹配的结果。联系网络管理员，在网络上搜索类似问题，或者向开发者提问以解决它。

### 9.8.3. 设备上运行着什么种类型的流量？

如果某个特定设备正在处理流量，使用 `iptraf` 追踪该设备正在发送和接收的流量类型是有帮助的。当你知道设备正在处理的流量类型时，进到第 9.8.4 节。

### 9.8.4. 是否是特定进程产生了大量流量？

接下来，我们可以使用 `netstat -p` 查看是否是某个特定进程产生了流量。如果是某个应用程序在使用这些流量，进入第 9.8.6 节。如果没有特定进程在使用，转到第 9.8.5 节。

### 9.8.5. 哪个远程系统在发送流量？

如果不是应用程序在使用这些流量，可能是某个系统在骚扰你。要确定是哪个系统在发送流量，使用 `iptraf`。
