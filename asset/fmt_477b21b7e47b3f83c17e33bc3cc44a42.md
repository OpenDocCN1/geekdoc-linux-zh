`includedir` 用于安装用户程序通过 C 语言 `#include` 预处理器指令包含的头文件的目录。这通常应该是 `/usr/local/include`，但应写为 `$(prefix)/include`。如果你正在使用 Autoconf，请将其写为 `@includedir`。

除了 GCC 以外的大多数编译器不在 `/usr/local/include` 目录中查找头文件。因此，通过这种方式安装头文件仅适用于 GCC。有时这将成为问题，因为某些库确实旨在与 GCC 配合工作。但某些库的意图是与其他编译器配合。它们应该在两个地方安装其头文件，一个由 `includedir` 指定，另一个由 `oldincludedir` 指定。

`oldincludedir` 用于安装供 GCC 以外使用的 `#include` 头文件的目录。这通常应该是 `/usr/include`。如果你正在使用 Autoconf，你可以将其写为 `@oldincludedir`。

Makefile 命令应该检查 `oldincludedir` 的值是否为空。如果是，它们不应尝试使用它；它们应该取消头文件的第二次安装。

包不应替换此目录中的现有头文件，除非该头文件来自同一个包。如果你的 Foo 包提供名为 `foo.h` 的头文件，那么如果满足以下任一条件，它应该在 `oldincludedir` 目录中安装该头文件：(1) 那里没有 `foo.h` 或 (2) 存在的 `foo.h` 来自 Foo 包。

要判断 `foo.h` 是否来自 Foo 包，请在文件中放置一个魔术字符串——注释的一部分——并使用 `grep` 查找该字符串。

Unix 风格的机页（man pages）安装在以下位置之一：

`mandir` 安装此包的机页（如果有）的顶层目录。它通常是 `/usr/local/man`，但你应该将其写为 `$(prefix)/man`。如果你正在使用 Autoconf，请将其写为 `@mandir`。

`man1dir` 用于安装第 1 节机页的目录。将其写为 `$(mandir)/man1`。

`man2dir` 用于安装第 2 节机页的目录。将其写为 `$(mandir)/man2`。

`manext` 已安装机页的文件扩展名。它应该包含一个点，后跟相应的数字；它通常是 `1`。

`man1ext` 已安装的第 1 节机页的文件扩展名。

`man2ext` 已安装的第 2 节机页的文件扩展名。

… 如果该包需要在手册的多个节中安装页面，请使用这些名称代替 `manext`。

最后，你应该设置以下变量：

`srcdir` 正在编译的源码所在目录。该变量的值通常由 configure 脚本插入。如果你正在使用 Autoconf，使用 `srcdir = @srcdir@`。

例如：

```
# 安装目录的通用前缀。
# 注意：此目录在启动编译时必须存在。
prefix = /usr/local
exec_prefix = $(prefix)
# 命令可执行文件的存放位置。
bindir = $(exec_prefix)/bin
# 编译器使用的目录存放位置。
libexecdir = $(exec_prefix)/libexec
# 安装文件的存放位置。
infdir = $(prefix)/info
```

如果你的程序向一个标准目录之一安装了大量文件，那么将它们分组到该程序的特定子目录中可能会很有用。安装目录拥有一套统一变量名称的想法是为了让使用户为不同的包指定相同的值。为了使这有用，所有由变量 `prefix` 和 `exec_prefix` 的值指定的内容以及所需的子目录都必须存在。实现这一点的一种方法是通过下文描述的 `installdirs` 目标。

### 14.5 用户的标准目标

所有 GNU 程序的 Makefile 中都应该包含以下目标：

- `all`

编译整个程序。这应该是默认目标。此目标不需要重建任何文档文件；Info 文件通常包含在发行中；DVI 文件仅在显式请求时制作。

默认情况下，Make 规则应使用 `g` 进行编译和链接，以便执行程序具有调试符号。不介意的用户可以在以后需要时自行剥离。

- `install`

编译程序并将可执行文件、库等拷贝到实际使用时应所在的文件位置。如果有一个简单的测试来验证程序已正确安装，此目标应该运行该测试。

安装时不要剥离可执行文件。粗心的用户可以使用 `install-strip` 目标来这样做。

如果可能，编写 install 目标使其不修改构建程序目录中的任何内容，前提是刚刚执行了 `make all`。这对于在一个用户下构建程序并在另一个用户下安装非常方便。

命令应该创建要安装文件的所有目录（如果它们不存在）。这包括由变量 `prefix` 和 `exec_prefix` 的值指定的目录以及所需的子目录。实现这一点的一种方法是通过下文描述的 `installdirs` 目标。

在安装任何机页的命令前使用 `-`，这样 make 将忽略任何错误。这是因为某些系统没有安装 Unix 机页文档系统。

```
$$(DIR)$(infodir)/foo.info
$(POST_INSTALL)
```

```
# . 中的新 info 文件可能比 srcdir 中的多。
-test f foo.info; then d=;
else=$(sccdir); fi;

```

```
# 仅当 install-info 存在运行时运行它。
# 使用 'if'而不是仅仅在行前加 '-'，这样我们就能注意到 install-info 的真实错误。
```

```
# 我们使用 '$(SHELL) -c' 是因为当存在未知命令时
# shell 不会优雅地失败。
if $(SHELL) -c 'install-info --version' \
>/dev/null 2>&1; then
  install-info --dir-file=$(DESTDIR)$(infodir)/dir \
  $(DESTDIR)$(foo.info); \
else  true; fi
```

在编写 `install` 目标时，必须将所有命令分为三类：普通命令、安装前命令和安装后命令。请参见第 14.6 节 [安装命令分类]，第 143 页。

### `uninstall`

删除所有已安装的文件——即 `install` 目标创建的副本。

此规则不应修改编译所在的目录，只应修改安装文件的目录。

卸载命令与安装命令一样分为三类。请参见第 14.6 节 [安装命令分类]，第 143 页。

### `install-strip`

类似于 `install`，但在安装时会对可执行文件进行剥离（strip）。在简单的情况下，该目标可以简单地使用 `install` 目标：

```
install-strip:
  $(MAKE) INSTALL_PROGRAM='$(INSTALL_PROGRAM) -s \
  install
```

如果软件包不仅安装脚本还安装真正的执行文件，则 `install-strip` 目标不能直接引用 `install` 目标；它必须剥离可执行文件但不剥离脚本。

`install-strip` 不剥离构建目录中正在拷贝用于安装的可执行文件。它只应该剥离已安装的副本。

通常我们不建议剥离可执行文件，除非你确定程序没有 bug。然而，安装一个剥离过的执行文件用于实际运行，同时在其他处保存未剥离的可执行文件以防出现 bug，是合理的。

### `clean`

删除当前目录下所有由构建程序正常产生的文件。不要删除由配置记录的文件。还要保留可以通过构建生成但通常不需要的文件（因为发行包已自带）。

如果 `.dvi` 文件不是发行包的一部分，请在此删除它们。

### `distclean`

删除当前目录下所有由配置或构建程序产生的文件。如果你解压了源码并构建了程序但没有创建任何其他文件，`make distclean` 应该只留下发行包中的文件。

### `mostlyclean`

类似于 `clean`，它可能会跳过删除少数人们通常不想重新编译的文件。例如，GCC 的 `mostlyclean` 目标不会删除 `libgcc.a`，因为重新编译它通常没有必要且耗费大量时间。

### `maintainer-clean`

删除当前目录下几乎所有可以通过此 Makefile 重新生成的文件。这通常包括 `distclean` 删除的所有内容，以及更多：由 Bison 生成的 C 源文件、标签表、info 文件等。
