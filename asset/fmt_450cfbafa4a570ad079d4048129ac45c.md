
在研究 Shell 脚本的理由时，你可能会认为作者是反 C 的；也就是说，程序永远不应该再用可移植语言 C 来编写了。如果是这样，你就错过了重点。有些时候，用 C 而不是 Shell 编写程序是完全合理的。但这些情况发生的频率比你想象的要低。

同样，由于现在对面向对象的语言和工具的过度炒作，很容易掉入跳过 Shell 并用 Java 等流行语言编写所有软件的陷阱。虽然 Java 在很多方面都是极佳的语言，特别是在代码复用方面，但它仍然是一种编译语言（即你必须从源代码编译 Java 程序，Java 运行时引擎才能解释它）。本节将让你意识到 Shell 作为 Java 的替代方案，如果这还没有完全改变你的想法。

### 5.2.1 Shell 脚本为你提供强大的杠杆

Shell 脚本由一个或多个语句组成，原生或解释型程序和其他 Shell 脚本执行这些语句。它们通过将每个命令加载到内存并执行它，间接运行运行程序。根据语句的类型，顶层 Shell 程序可能选择不等待单个命令执行。执行的命令可能是从几百、上千甚至上万行 C 代码编译而来的，其中大部分并不是你编写的。是别人花时间对这些程序进行编码和调试。你的 Shell 脚本仅仅是受益者，它利用那些代码来提供优势。尽管你付出的努力相对较少，但你获得了多达百万行或更多行代码的收益。这就是杠杆。

在塑料家居用品的多级营销中，技巧是让别人为你完成大部分工作。你正试图创造一种局面，某人播种而你收获部分。Shell 脚本提供了这种机会。它们给了你整合他人努力以实现你目标的机会。你不需要编写 Shell 脚本中大部分代码，因为别人已经为你做过了。

让我们来看一个例子。假设你想有一个命令，单行列出系统用户的用户名。为了让它更有趣，让我们用逗号分隔每个用户的名称，并且每个用户只显示一次，无论该用户在系统中打开了多少会话。这就是我们用 `bash` Shell（一种特定的命令解释器）编写的 Shell 脚本样式：

```
echo 'who' | awk '{print $1}' | sort | uniq | sed 's/ /\, /g'
```

尽管这个 Shell 脚本只有单行，但它调用了六个不同的可执行程序：`echo`, `who`, `awk`, `sort`, `uniq`, 和 `sed`。这些命令以某种串行并行的方式同时运行。除了启动序列的 `who` 命令外，每个命令都从序列中的上一个命令接收数据，并将其输出发送到序列中的下一个命令。由 `'|'` 字符表示的多个管道管理着数据传输。序列中的最后一个命令 `sed` 将其输出发送到用户的终端。

每个命令与其他协同工作以产生最终输出。`who` 命令产生系统用户的列式列表。它通过管道机制将其传递给 `awk`。`who` 输出中的第一个命令包含用户名。`awk` 命令保存这一列并丢弃由 `who` 生成的其余数据。然后，用户列表被发送到 `sort`，它按字母顺序进行排列。`uniq` 命令丢弃任何可能登录的重复名称。最后，`sed` 命令将其输出发送到用户的终端。

| 命令 | 代码行数 |
| :--- | :--- |
| echo | 177 |
| who | 755 |
| awk | 3412 |
| sort | 2614 |
| uniq | 302 |
| sed | 2093 |
| **合计** | **7353** |

### 原则 7：使用 Shell 脚本增加杠杆和可移植性

这个 Shell 脚本中的一行执行了相当于 9535 行代码！虽然这个数字并不惊人，但足以证明我们的观点。我们的力量增加了 9355 倍。1。再次，这就是杠杆。

这是一个简单的 Shell 脚本示例。现在的 Shell 脚本可能跨越几十页，包含数百行命令。当你考虑到每个可执行文件背后的代码时，这些数字开始变得惊人。正如我们以后将看到的，这种现象曾让爱因斯坦感到震惊。

### 5.2.2 Shell 脚本也利用了你的时间

Shell 脚本的一个内在优势在于它们是解释的而不是编译的。在标准的 C 语言开发环境中，事件序列如下：

```
THINK-EDIT-COMPILE-TEST
```

Shell 脚本开发者的环境短了一步：

```
THINK-EDIT-TEST
```

Shell 脚本开发者跳过了 编译步骤。对于今天的高度优化的编译器来说，这似乎不是一个巨大的胜利。配合快速的 RISC 处理器，此类编译器可以在眨眼之间将代码转换为二进制文件。但现在的应用程序很少是独立存在的单个文件。它们通常是日益复杂的大型构建环境的一部分。过去在快速机器上编译需要几秒的内容，现在由于集成水平的提高可能需要分钟或更长时间。更大的程序可能需要几分钟或更长时间。整个操作系统及其相关命令构建需要几个小时。

在跳过编译步骤的情况下，脚本编写者可以保持开发工作的专注。他们不需要在等待命令构建时去喝咖啡或读邮件。直接从编辑跳转到测试，他们不会因为等待编译器完成而中断思路。这大大加速了软件开发过程。

一个需要考虑的关键点是执行时间和编译时间。许多较小的应用程序（记住我们在这里讨论的是 Unix/Linux）可以在几秒钟内完成任务。如果编译花费的时间比使用脚本要长得多，那么编写脚本可能是值得的。反之，一个脚本可能需要运行几个小时，而编译后的程序在几分钟内就能执行。通过各种方式，编写脚本可以节省时间。你只需要将它们复制到新机器上即可运行。此结束。没任何麻烦。

遗憾的是，“知足”的能力并不是程序员的典型美德。如果程序员发现空闲时间琢磨一个脚本，你可以打赌他们会 (1) 为其添加一些新功能，(2) 尝试通过改进脚本本身使其运行更快，或 (3) 尝试通过用 C 语言重写其或部分内容来提高性能。你能猜哪一种最有吸引力吗？

用 C 重写脚本的欲望源于一种信念：C 程序比脚本运行得更快。这侵蚀了程序员对一个整洁、有序、一切都经过良好调优且高效世界的渴望。这是一种自尊。他知道自己可以用 C 语言编写，而且从一开始就会运行得很快。由于某种原因，他没有这样做。当你问他为什么选择用脚本来编写程序时，他会感到愧疚，他可能会谦虚地说：“我当时只有那么多时间了。”他会在这个借口后跟着承诺，当他有更多时间时，他将用 C 重写。

是时候克服这种想法了。怀疑他是否还会这样做。像 Microsoft Visual Studio 或 Borland Builder 这样的大 IDE 又怎样？它们提供优越的调试和编辑功能吗？是的，提供。它们非常擅长为开发者隐藏底层复杂性。有时这是好事。但经常的抱怨是，当出现问题时，人们仍然必须进入底层查看 IDE 做了什么。那个让语言变得易用的漂亮壳现在变成了开发者的噩梦，因为他试图弄清后台发生了什么。

相反，脚本让一切变得非常直观。它们所做的一切就在你面前。没有什么被隐藏在精美的 GUI 菜单之后。讽刺的是，脚本比所谓的视觉产品更视觉。

### 5.2.3 脚本比 C 更具可移植性

利用软件的一种明智方法是让它具有可移植性。我们之前了解到将你的软件分享给他人是重要的。任何从一个平台移动到另一个平台的程序都可能被很多人使用。使用你软件的人越多，杠作用越大。

在 Linux 环境中，脚本通常代表了最高水平的可移植性。大多数在一个 Linux 系统上运行的脚本可能在另一个系统上只需少量修改即可运行。由于它们是解释执行的，因此没有为了使用而对它们进行编译或其他转换。可以在设计上让一个脚本变得不可移植，但这种实例很少见，而且通常是不被鼓励的。

脚本也倾向于失去与 C 源代码常见的“所有权”污名。人们很少保护它们。它们对所有人都是显而易见的，没有人认为保护内容是个人或公司的职责。尽管如此，这里仍需要采取谨慎。美国和其他国家的版权法为脚本提供了保护。一个人是否想对脚本申请版权那是律师的问题。

关于可移植性的章节敦促你不要用 C 重写脚本，因为明年的机器会让它们运行得更快。由于脚本通常具有高度的可移植性，将它们移动到明年的机器通常不需要付出努力。你将它们复制到新机器，它们就能运行。就这样。没任何麻烦。

遗憾的是，维持现状的能力并不是程序员的典型美德。如果程序员发现空闲时间来摆弄一个脚本，你可以打赌他们会 (1) 为其添加一些新功能，(2) 尝试通过精炼脚本本身使其运行更快，或 (3) 尝试通过用 C 重写其或部分内容来提高性能。你可以猜哪一个最有诱惑力吗？

是时候克服这种想法了。怀疑他是否还会这样做。对于他那些奇的理论，这两个想法显然对他留下了深刻印象。他明白，少量的东西通过不断倍增可以增长到惊人的程度。需要像他这样敏锐头脑才能察觉到这种简单想法中的力量。
