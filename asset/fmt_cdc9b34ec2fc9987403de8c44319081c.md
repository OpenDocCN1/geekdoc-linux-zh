## 复习

让我们快速回顾一下我们涵盖的一些关键 dbspace（数据库空间）。

- `rootdb`: 在我们安装和初始化数据库时创建。
- `physdb`: 将包含物理日志；必须从 `rootdbs` 移动到它自己的 dbspace 中。
- `logsdbs`: 将包含逻辑日志；必须从 `rootdbs` 移动到它们自己的 dbspace 中。
- `tempdbs`: 默认位于 `rootdbs`，它将指向它自己的 dbspace，用于排序、查询和临时表。
- `dbs_dbs`: 将包含数据库条目，但不包含表条目。
- `databds01`: 将包含表。
- `indexdbds01`: 将包含索引。

## Physdb

出于性能考虑，将物理日志移动到它自己的 dbspace 是一种标准做法。物理日志是数据库活动的缓冲区或缓存，这些活动尚未写入数据库。将其重新定位到它自己的 dbspace 允许你根据需要扩展或缩小其大小，而不会影响 `rootdbs`，并允许提高性能。

正如我们讨论过的，`rootdb` 包含了你在此服务器上为该实例创建的每个数据库的内核。你可以拥有多个 Informix 实例；每个实例都有自己的 `rootdb` 以及与其他实例隔离的 dbspaces。尽力减少对 `rootdb` 的风险是至关重要的。重新定位物理日志是我们采取的首要步骤之一，以确保 `rootdb` 仅保留最少的活动——跟踪数据库中所有内容的位置——以及管理引擎。

### 确保你的 Informix 引擎正在运行

```
$ onstat
```

如果引擎没有运行，它现在将通过 `oninit` 程序启动，不带任何选项，或者至少仅使用 `-v` 选项（详细输出标志）：

```
$ oninit -v
```

在创建 `rootdb` 之后，你**不应该**使用 `-i` 选项来运行 `oninit`。这样做等同于格式化你的硬盘。有一个例外：你可以使用 `oninit -v`，它会在引擎启动时显示详细输出。请小心不要使用 `-i` 选项，否则 `rootdbs` 将被重新格式化。在生产服务器上执行此操作将使你的简历变得“非常亮眼”（反讽）。

一旦引擎运行，你可以先用 UNIX/Linux 命令创建 `physdbs`，然后用 Informix 命令创建它，就像你之前创建 `rootdbs` 一样。

## 创建一个 physdb 文件

UNIX 和 Linux 允许你在执行 `>filename` 命令时创建一个长度为零的文件。

```
$ cd /opt/data
$ >physdb
$ chown informix:informix physdbs
$ chmod 660 physdbs
```

这创建了文件，但里面空空一物。

我们大多数的后续步骤需要在单用户模式（single-user mode，或所谓的静默模式模式）下进行。我们还将利用两个工具——`onpaces` 和 `onparams`——你只有作为 DBA 时才会使用它们。

`onpaces` 可以在多用户模式下，但 `onparams` 必须在引擎处于单用户模式时运行。要进入单用户模式，请运行 `onmode -s`。在此命令后添加一个 `s` 可以跳过以下询问：

```
rebel:root # onmode -s
```
