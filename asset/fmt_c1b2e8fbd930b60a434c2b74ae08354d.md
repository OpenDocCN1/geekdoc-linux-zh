
UNIX 提供了一个令人印象深刻全面的工具包，帮助你完成管理、维护和排除 TCP/IP 网络各个方面的工作。使用相应的命令，你可以完成从配置网络接口到收集性能统计的任何操作。在所有命令中，你在本章中遇到了两个：`ifconfig` 和 `route` 命令。这两个命令在大多数 UNIX 变体中都是通用的，`route` 命令已在本章“路由表维护”章节中进行了详细介绍。现在，我们详细解释 `ifconfig`。每个与 TCP/IP 相关的命令将在稍后的“排除 TCP/IP 故障”章节介绍。

`ifconfig` 命令用于配置或检查网络网卡的配置值。你可以使用 `ifconfig` 为接口分配 IP 地址、网络掩码、广播地址或更改其某些参数。`ifconfig` 始终在启动时由 TCP/IP 启动脚本使用，根据接口配置文件的规定设置这些参数（参见下文关于接口配置的说明）。

### 网络接口配置文件

遗憾的是，并非所有的 UNIX 变体的配置信息（如 IP 地址、网络、广播地址等）都存储在同一个位置。下表提供了本章中讨论的每个平台存储此类信息的参考。接口配置文件由启动脚本获取，并供 `ifconfig` 命令配置支持的接口：

| 平台 | 配置文件 |
| :--- | :--- |
| SVR4 | `/etc/conf.d/` |
| Linux | `/etc/network/scripts/ifcfg-xxx` |

`ifconfig` 的通用语法过于全面，无法通过一个示例进行有意义的解释。因此，将在不同的场景下分段介绍。

### 设置 IP 地址、子网掩码和广播地址

在最形式的形式，`ifconfig` 命令的语法如下：

```
ifconfig interface IP_address netmask mask address
```

用于设置网络接口的基本参数，其中：

| 参数 | 描述 |
| :--- | :--- |
| `interface` | 标识网卡的标签。例如，3C509 被称为 `el30`。 |
| `IP_address` | 分配给网络的 IP 地址。你可以选择性使用主机名，前提是 `/etc/hosts` 文件包含相应的名称进行关联。 |
| `mask` | 可能的子网掩码。如果掩码留为默认值（即网络未划分为子集），你可以忽略此参数。同一物理网络上的所有主机的掩码必须为零。 |
| `broadcast address` | 网络的广播地址。广播地址必须使得同一物理网络上的所有主机的广播地址都设置为相同的值。 |

在接下来的示例中，使用 `ifconfig` 设置 3C509 网网的 IP 地址、子网掩码和广播地址：

```
# ifconfig el30 150.1.0.1 netmask 255.255.0.0 broadcast 150.1.255
```

可选地，你可以使用主机名代替 IP 地址来配置接口，如下所示：

```
# ifconfig el30 netmask 255.255.0.0 broadcast 150.1.255
```

其中主机名在 `/etc/hosts` 文件中映射到有效的 IP 地址。此示例可以进一步简化，使子网掩码和广播地址都设置为其默认值。

### 使用 ifconfig 检查接口

要检查受支持接口的配置参数，输入：

```
# ifconfig interface
```

因此，要检查 3c509 的配置，输入：

```
# ifconfig el30
el30:flags=23<UP,BROADCAST,NOTRAILERS>
  inet 150.1.0.1 netmask fffff000 broadcast 150.1.255
```

上面的响应确认了 3Com 接口已配置为 IP 网络地址 150.1.0.1，掩码为 fffff000（即点点表示法 255.255.0.0 的十六进制等），广播地址为 150.1.255。

响应报告括号内包含的信息：

| 标志 | 描述 |
| :--- | :--- |
| UP | 表示接口已启用并积极参与网络。如果接口被禁用，UP 将被替换为空值。 |
| NOTRAILERS | 表示接口接受广播：一种通过重新排列以太网字段来提高效率的技术，主机 I/O 架构从中受益。由于这种技术随时间变得不再流行，将不再讨论。 |

要检查系统支持的所有接口的配置，请在以下示例中使用 `-a`（代表所有接口）配合 `ifconfig` 命令：

```
# ifconfig -a
lo:flags=49,LOOPBACK,RUNNING
  inet 127.0.0.1 netmask ff000000
ne2ko:flags=23UP,BROADCAST,NOTRAILERS
  inet 100.0.0.1 netmask ff000000 broadcast 100.255.255
el30:flags=23UP,BROADCAST,NOTRAILERS
  inet 150.1.0.1 netmask fffff000 broadcast 150.255
```

上面的响应涉及三个接口。第一个 `lo` 指的是回环接口，并分配了回环地址 127.0.0.1 和默认 A 类网络。第二个（即 `ne2ko`）和第三个（即 `el30`）分别指 NE2000 和 3C509。所有接口都已启用（即 UP）可以使用。

**使用 ifconfig 启用/禁用接口** `ifconfig` 命令支持多个可选参数，其中 `up` 和 `down` 参数可启用或禁用接口。通常在排除网络故障时，在路由器上临时禁用接口，并将可疑分段与其他部分隔离。在某些系统中，除非在使用 `ifconfig` 修改接口配置之前禁用了接口，否则配置更改将生效。

```
# ifconfig interface down
```

例如，要禁用 3C509 网络接口，输入：

```
# ifconfig el30 down
```

注意括号内包含的信息中缺少 UP 关键字意味着接口已关闭。执行此操作，输入：

```
# ifconfig el30 down
el30:flags=22<BROADCAST,NOTRAILERS>
  inet 150.1.0.1 netmask fffff000 broadcast 150.255.255
```

要启动它，你只需输入

```
# ifconfig el30 up
```

## NFS 文件共享

如 FTP 和 TELNET 等网络应用程序提供了在网络共享资源的机制，但它们也存在自身固有的局限性和不便之处。以 FTP 为例，除非文件被传输到本地主机，否则用户无法使用本地程序和 shell 命令处理文件。更糟糕的是，必须挂起或退出 FTP 会话才能处理传输的文件。此外，使用 FTP 对于习惯了常用 UNIX 文件相关命令的用户来说，存在学习支持上的学习曲线。

网络文件系统 `NFS` 避免了其他文件系统访问方法带来的局限性。从用户的角度来看，一个 NFS 可访问的资源处理方式与本地资源完全相同。在设置时，远程文件系统将作为本地文件系统的一部分显示给用户。访问 NFS 文件系统不需要登录或输入密码。对于用户来说，访问挂载的 NFS 文件系统只需在 UNIX 文件系统层级中切换目录即可。

## NFS 概念

网络文件系统 `NFS` 允许用户进程和程序对远程挂载的文件系统进行透明的读写访问。透明性意味着程序可以继续工作并处理位于 NFS 挂载文件上的文件，无需对其代码进行任何修改。这是因为 NFS 设计得巧妙，将远程资源作为本地资源呈现给用户。

NFS 遵循客户端-服务器模型，其中服务器是提供文件系统资源并配置为与其他系统共享的系统。一个 NFS 可共享资源通常被称为导出文件系统 `exported filesystem`。客户端是远程用户。它像使用本地文件系统的一部分一样使用导出的文件系统。为了实现这种透明性，客户端将导出的目录挂载到本地文件系统上。

图 20.30 显示了 `/efs` 是主机 `tenor`（NFS 服务器）上的导出目录。如阴影区域所示，由于导出了 `/exports` 目录，其下方也是。从客户端 `jade` 访问目录的操作是在本地文件系统中创建一个目录（如图中的 `/rsfs`），并使用 `mount` 命令（在后面的命令上）挂载远程文件，如下所示：

```
# mount -F nfs tenor:/efs /rsfs
```

## 远程过程调用

远程过程调用（由 Sun Microsystems 开发）为 NFS 等其他网络服务提供了基础，称为基于 RPC 的服务器。

RPC 定义了一种透明的计算服务，该服务将一个进程分为两个组件：客户端和服务器。客户端组件位于向远程网络共享资源发起 RPC 用的本地主机。服务器组件管理共享资源，并处理和响应从客户端收到的 RPC 调用。

当远程过程在服务器端执行时，本地 RPC 用户进程会等待返回结果，其等待方式就像对本地资源发起调用时所等待的一样。

**传输层支持** 作为一种进程/应用层协议，RPC 依赖传输层协议在 RPC 客户端和服务器之间交换请求和响应。在 TCP/IP 下，RPC 支持通过 UDP 和 TCP 传输。

大多数 RPC 活动由 UDP 传输协议承担。这主要是因为 RPC 程序的生命周期相对较短，使得创建和终止 TCP 连接的产生相关开销高得不合理。因此，消息序列化和可靠性检查被内置在 RPC 服务器中。TCP 连接通常是为了传输数据块而建立的。

与 FTP 和 TELNET 等 TCP/IP 应用不同，RPC 服务器不依赖于已知的传输端口。它们在启动时被动态分配一个可用的端口号。

你的主机上支持的 RPC 服务器完整列表可以查看 `/etc/rpc` 文件的内容。其内容的部分列表如下：

```

```

该文件中的每个条目包括（服务器名称、程序编号以及可选的一个或多个别名）。

**程序编号** **端口映射器** 由于 RPC 服务器在启动时动态分配端口号，因此产生了一种机制，使服务器能够被客户端发现。RPC 通过采用一个中间件——端口映射器 `port mapper` 来实现这一点，它代表 RPC 服务器监听请求。客户端最初不是通过端口号寻址服务器，而是在请求时（在 `/etc/rpc` 文件中）对它们进行寻址。启动时，每个 RPC 服务器都会向端口映射器（实现为 `/rpcbind` 守护进程）注册自己。

在客户端首次请求 RPC 服务之前，它应该联系 `rpcbind`（即 RPC 服务器监听请求的端口号上对应的端口映射器）。在获得良好的响应后，客户端缓存端口号并使用它直接连接到 RPC 服务器。可以理解，为了让客户端到达端口映射器，端口映射器必须是可用的。

**过程编号** 每个 RPC 服务器由一个程序编号标识。客户端使用程序编号请求特定的服务。服务器使用过程编号识别要执行的函数。

**版本编号** 每个 RPC 服务支持多个版本。客户端在请求中指定版本号。服务器检查是否支持该版本。

## NFS 守护进程

与许多 UNIX 系统一样，NFS 通过一组守护进程实现。某些守护进程运行在服务器上，另一些运行在客户端上。一部分守护进程在双方都运行。以下是每个守护进程的功能描述：

- `nfsd` 是 NFS 守护进程，它运行在服务器上，负责处理和响应客户端请求。`nfsd` 通过解析操作性质并调用本地 I/O 来处理请求。`nfsd` 通常在系统启动时被调用。由于性能考虑，会启动多个 `nfsd` 实例。

- `biod` 是块守护进程。它运行在 NFS 客户端上，代表客户端从 NFS 服务器读取和写入数据。同样，性能考虑因素决定了客户端上会启动多个 `biod` 实例。然而，需要注意的是，调用过多的 `biod` 实例可能会导致性能下降。

- `mount` 运行在 NFS 服务器上。它负责处理客户端挂载请求。回图 20.30，当在主机 `jade` 上调用 `mount -F nfs tenor:/efs` 时，客户端向 NFS 服务器发送 NFS 请求。除非主机 `tenor` 运行 `mount`，否则将无法响应该请求导致挂载失败。NFS 服务器只运行一个 `mount`。

- `lockd` 在客户端和服务器均运行，该守护进程处理文件锁。在客户端侧，进程发出请求；服务器端的 `lockd` 响应这些请求并管理锁。

- `Statd` 在客户端和服务器均运行，该守护进程维护正确执行的文件锁的状态。它的用性在服务器崩溃时尤为明显，因为它有助于在服务器恢复后回收文件锁。

# 设置 NFS 服务器

一旦你决定了想要在服务器上与其它主机共享文件系统的哪些部分，就可以开始设置 NFS 了。

## 在 SVR4 上设置 NFS（包括 Solaris 2.x）

在 SVR4 下导出文件系统（即将其变为可共享）涉及使用某些命令。该命令的语法为：

```
share [-F nfs] [-o options] [-d description] pathname
```

其中，

- `-F nfs`: 指定导出的文件系统的类型。UNIX 支持许多不同的远程可访问文件系统。此类文件系统的示例包括 RFS（远程文件系统）和 AFS（安德鲁斯文件系统）。如果 NFS 是你系统中唯一的分布式文件系统，则可以省略此选项。

- `-o options`: 指定适用于导出的文件系统的限制条件。表 20.4 列出了这些选项及其对影响的简要描述。

- `-d description`: 描述性语句。

- `- pathname`: 指定要导出的（或共享的）路径。

# 表 20.4. 挂载 NFS 文件系统时 -o 选项支持的选项。

| 选项 | 描述 |
|---|---|
| `rw=host[:host...]` | 允许 `host` 参数中指定的主机对导出的文件系统具有读写访问权限。 |
| `ro=host[:host...]` | 将 `pathname` 以只读方式导出给列出的主机。如果没有指定主机，则所有除使用 `ro` 之外的客户端都将被允许只读访问权限。 |
| `anon=uid` | 在访问 `pathname` 时，为匿名用户分配不同的 `uid`（即 `uid` 为 0 的用户）。默认情况下，匿名用户被分配用户 `nobody` 的 `uid`。用户通常具有与公共用户相同的权限。 |
| `root=[host[:host...]` | 允许指定的主机具有 `root` 访问权限。用户的 `uid` 为 0。除非进行指定，否则不允许 `root` 具有对 `pathname` 的访问权限。 |
| `secure` | 在授予用户权限访问 NFS 挂载的文件系统之前，强制执行验证要求。 |

在图 20.30 所示的场景中，使用以下 `share` 命令允许主机 `tenor` 导出并共享文件系统的 `/exports` 子集。所导出的文件系统被标记为 `rw`，允许其他主机对其具有读写访问权限：

```
# share -F nfs -o ro=saturn -d "Just an example" /fs
```

此处显示的 `share` 命令对 `/fs` 目录没有 `root` 权限。

```
# share -F nfs -o ro=violin /fs
```

除了 `violin` 之外，尝试挂载 `/efs` 目录的主机将失败并收到“Permission denied”（拒绝访问）的消息。

在接下来的示例中，为来自主机 `jade` 的用户授予 `root` 权限：

```
# share -F nfs rw, ro=jade /efs
```

要查找导出了哪些文件系统，只需输入 `share` 而不带命令参数：

```
# share
/nfs rw ""
/efs rw,ro=viper ""
```

## 在启动时自动共享

在系统启动时导出或共享文件系统（SVR4）是一件简单的事，涉及编辑 `/etc/dfs/dfstab` 文件。在该文件中，你应该包含许多 `share` 命令（必须完全使用上述说明的语法），以处理 NFS 服务器导出的所有目录。例如，这两个 `share` 条目是从主机 `tenor` 的 `/etc/dfs/dfstab` 文件中提取的：

```
# share -F nfs /nfs
share -F nfs rw, ro=saturn /efs
```

当系统以构建时的级别三运行时，将读取 `/etc/dfs/dfstab` 的内容并执行其 `share` 条目。系统管理员无需手动发布这两个 `share` 命令。

该程序从 `/etc/init.nfs` 脚本调用，通过 `shareall` 导出 `dfstab` 文件中的所有文件系统。如果你使用命令行，可以使用 `as` 来强制共享，特别是在你对 `/etc/dfs/dfstab` 进行了更改并希望立即实施这些更改时。

## 在 BSD 和 Linux 上设置 NFS

Unix 系统依赖于 `/etc/exports` 文件来控制哪些目录被导出。`/etc/exports` 文件中的条目必须遵循以下语法：

```
pathname [-option][,option]...
```

其中，`pathname` 指定被导出的目录，`option` 指定持久访问权限。以下是支持的选项的描述：

| 选项 | 描述 |
|---|---|
| `rw=[hostname]:[:hostname]...` | `rw` 授予使用 `hostname` 参数指定的主机读写权限。如果没有指定主机，则向网络上的所有主机授予读写访问权限。如果没有指定任何选项，`rw` 是默认的访问权限。 |
