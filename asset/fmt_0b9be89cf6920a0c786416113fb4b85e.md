
`/var` 占用 100MB，`/var/spool` 占用 500MB。

我们可以按照以下方式使用 `part` 关键字来表示它：

```
part / --size 100
part swap --size 256
part /tmp --size 100
part /usr --size 500
part /usr/local/ --size 500
part /var --size 100
part /var/spool --size 500
```

这对于恰好为 2056 兆硬盘的系统有效，但在现实世界中并不实用。然而，通过使用 `--grow` 和 `--maxsize` 选项，创建一个适用于各种磁盘大小的通用分区方案：

```
part / --size 100
part swap --size 256
part /tmp --size 100 --grow --maxsize 200
part /usr --size 500 --grow --maxsize 1024
part /usr/local --size 500 --grow --maxsize 1024
part /var --size 100 --grow --maxsize 200
part /var/spool --size 500 --grow
```

当此配置应用于具有 4GB 硬盘的系统时，该配置将产生以下分区大小：

```
/ 100MB
swap 256MB
/tmp 200MB
/usr 1024MB
/usr/local 1024MB
/var 200MB
/var/spool 1292MB
```

这种分区方案可能并不完美，但它确实反映了配置。当将相同的分区方案应用于具有 9GB 硬盘的系统时，生成的分区大小为：

```
/ 100MB
swap 256MB
/tmp 200MB
/usr 1024MB
/usr/local 1024MB
/var 200MB
/var/spool 6412MB
```

这些分区反映了为硬磁盘 `spool` 目录留出空间的需求，同时为添加软件和维护日志文件留出了充足的空间。

此外，邮件服务器配置所需的软件也需要安装。在 `@packages` 部分中指定 `@server` 对于邮件服务器来说就足够了。最后，在安装完成后可能需要修改某些文件。这通过在 `kickstart` 文件的 `@post` 部分中添加一些行来实现。

系统管理员管理的每台邮件服务器可能都有不同的硬件配置。这意味着 `kickstart` 配置文件无法在系统之间共享。毕竟，在完成生成一个良好的配置的所有工作后，这将是一种浪费，也是另一个可能的错误来源。

## 延伸阅读

完全重装系统具有显著的优势。这可以使系统处于一个已知的状态，并消除机器可能存在的任何特殊性。系统会随着时间的推移而发生变化，因此定期将工作站群恢复到相同的配置是一件好事。因此，作者建议使用安装机制进行桌面级升级。唯一的例外是当需要升级一个或几个软件包以修复紧急问题时。在这种情况下，最好使用 `U` 或 `RPM` 而不是构建服务器。通常情况下，这种操作可以在客户端运行的同时完成，但内核和内核模块除外。

升级服务器有两种方法。如果有可用硬件，应该从零开始构建、配置并测试一台新服务器。然后，随着时间的推移，将用户迁移到新服务器。一旦旧服务不再被使用，硬件就可以被收回并在未来的升级中重新使用。作者将这种方法称为 `摆臂机升级`（swing machine upgrade）。这是理想的升级路径。遗憾的是，预算限制或服务器提供服务的独特特性可能要求对系统进行 `原地升级`（upgraded in place）。这始终是一项具有风险的尝试，因为服务器比客户端需要更多的定制，而这些定制往往是系统所提供服务的关键。对于原地升级，升级机制是优选，因为它们的风险较小。系统整体保持完好，关键的系统配置文件不会被删除。对于客户端工作站来说，这并不重要，但对于关键服务器来说，能够升级而非重装的能力是一个非常理想的。

## 用户与组管理

用户账户管理是系统管理的核心。它不仅占据了系统管理员的大部分时间，而且是痛苦的主要来源之一。某些用户对他们的账户永不满意，无论是他们的 `shell`、磁盘空间配额、用户名，还是虚拟桌面的配置。

`LINUX` 为用户和组的管理提供了强大的工具，使得在中小型站点中，这些任务的映射比在传统的 `UNIX` 环境中要轻松一些。在本章中，我们将研究这些工具的作用、在实践中的用方法，以及它们如何与其他工具协同工作。我们还考虑了如何制定用户管理策略以满足业务需求。

大型站点的用户和组管理面临一些挑战，例如维护 `uid` 到用户的一致映射，而标准工具无法满足这一点。在章末尾，我们将考虑管理大型用户数据库的工具、策略和程序。

## 用户与 uid

`uid` 标识文件、目录和进程的所有者。每个数字 `uid` 对应一个用户名（或登录名），并可选地对应一个用户名。`uid` 到用户名的映射通常位于孤立机器的 `/etc/passwd` 文件中，位于网络化机器的 `NIS` 或其他分布式数据库中。

通常，用户名可以用于登录一个或多个系统，但少数被称为“伪登录”（pseudo-logins）的用户名无法登录任何系统。用户名通常属于某个人，大多数人在（任何特定组织内）只有一个用户名。`root` 是一个明显的例外，因为在大多数系统上有多个个人使用 `root`，而且每个使用 `root` 的人也应该有一个自己的个人用户名。

正如公民在政府让他们自由做决定时生活得最好一样，当系统管理员让用户选择自己的用户名时，用户工作得最好。一些系统管理员尝试过正式的用户名分配方案，例如名字的前两个字母后跟姓名的前五个字母。每种此类方案都会导致冲突，这些冲突通常通过在组织层用户名后添加数字来解决。即使在没有冲突的情况下，这些方案对于将真实姓名转换为用户名的映射也几乎没有帮助，而且对士气有害。

每个用户都都有一个相应的密码，其哈希值也存储在 `/etc/passwd`、`/etc/shadow` 或 `NIS` 中。每个用户还有其他属性，例如默认 `shell`。

## 伪登录 (Pseudo-Logins)

伪登录的存在是为了让进程以伪登录的 `uid` 运行，而任何用户无法使用相应的用户名登录任何机器。大多数 `LINUX` 系统上发现的一些伪登录包括 `bin`、`daemon`、`adm`、`lp`、`mail`、`news`、`uucp` 和 `nobody`。

如有必要，可以创建额外的伪登录。一些系统管理员会创建一个用户名与要作为 `shell` 执行的命令相匹配的伪登录账户。示例包括 `hostname`、`ifconfig`、`netstat` 和 `who`。在创建任何伪登录时，都应该考虑到安全问题，特别是当尝试使用该用户名登录会导致执行命令时。记录创建每个伪登录的原因是非常重要的。

## 组与 gid

组提供了一种聚合用户的机制，以便可以反复向一组用户授予权限，而无需每次都列出成员。`passwd` 文件或映射表包含一个 `gid` 字段。这是 `Unix` 的遗留，它曾限制用户在任何给定时间只能属于一个组。用户所属的组信息现在源自组文件或映射表。

组文件或映射表包含一个条目列表，每个组一个条目。每个条目包含四个字段：组名、`gid` 和成员列表。

## 添加用户

通常用于添加 `UNIX` 用户的命令是 `useradd`。由于 `useradd` 不创建 `NIS` 条目，运行它的命令的主机应该是 `NFS` 服务器，它将根据系统管理员在 `/etc/skel` 中设置的模板主目录为用户创建主目录。它还会创建 `/etc/passwd`、`/etc/shadow` 以及可能的 `/etc/group` 条目，这些条目可以在 `NIS` 主服务器上添加到 `NIS` 中。

我们建议用户至少复用一年，除非他们达到了数字限制，此时应从底部开始重新分配。因此，我们建议分配比所有其他用户大的下一个 `uid`，直到达到上限。目前该数字被内核限制为 216；然而，`glibc` 允许为 232。除非受到 216 的限制，否则大多数站点永远不需要复用用户。

无论给新用户添加了什么内容，都必须进行记录，并在可能的范围内实现自动化。修改用户账户信息、禁用用户和删除用户也是如此。组织内的所有系统管理员都应该能够从内网站点轻松找到正确的程序。

## 更新用户

更新用户的标准命令是 `usermod`。它接受多种选项。通常，每个选项对应于用户账户的特定属性。例如，命令

`usermod -G techpubs,marcom jjones`

将使用户 `jjones` 成为 `techpubs` 和 `marcom` 组的成员。`jjones` 将不再是他之前可能所属的任何组的成员。这些组必须存在。
