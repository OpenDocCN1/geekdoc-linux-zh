
# 第 4 章

## 4. KVM 切换器
`KVM` 切换器允许你为多个系统连接一个键盘、视频控制台和鼠标。你可以使用 `KVM` 切换器来降低在多个系统上设置控制台的成本，并从单一位置查看你所有的控制台。

## 5. Jumpstart 与 Kickstart
`Jumpstart` 可以在没有任何设备的情况下安装操作系统；而 `Kickstart` 则（至少）需要一张软盘进行操作系统安装。你可以使用 `NFS` 进行网络安装，`Kickstart` 除了 `NFS` 之外，还提供了 `FTP` 和 `HTTP` 等更多网络安装选项。

## 6. 软件包管理系统
软件包管理系统能够列出系统中已安装的所有软件，并可以通过单个命令添加或删除这些软件。你不需要担心跟踪每个应用程序安装时安装的每一个文件。软件包管理系统还可以为你管理软件依赖关系。

# 第 4 章 续

## 1. 质量保证团队
质量保证团队是一个专门测试你的系统功能和可用性的人员小组。他们将测试这一重大任务从你手中移出，让你能够专注于系统管理任务，如监控服务和维护硬件。

## 2. 单元测试
单元测试检查系统的单个功能组件，以验证每个系统组件是否都按照其原始规范工作。在许多情况下，你不需要对系统的每个功能单元进行单元测试（例如，操作系统和软件供应商通常会在发货前对产品进行测试）；然而，单元测试应该涵盖影响系统预期用途的所有组件和功能。你不需要在系统中不会被使用的单元测试或功能（事实上，应该考虑消除或禁用此类元素，以避免来自无意义组件的潜在问题）。

## 3. 负载测试
系统的两种大类负载测试涉及以下内容：

- 测试系统在固定时间内可以执行的操作次数。变负载负载测试在固定时间内引入尽可能多的负载，并根据该时间段内完成的平均请求数来衡量性能。这种测量对于确定系统的崩溃点，或导致系统在规格范围内停止运行的压力水平很有用。
- 测试系统执行固定数量操作所需的时间。恒定负载测试向系统引入恒定的压力水平（通常以服务请求的形式），并根据系统完成每个请求的平均时间报告性能。这些数据对于预测系统在已知条件下的性能有用。

## 4. 等差数列与等比数列
等差数列的成员之间的差异是固定值，而等比数列的成员之间的差异是固定比率。在增加系统压力时，确定性能测量所遵循的数列类型，对于准确的容量规划至关重要。性能与输入呈几何关系的系统，其性能下降的速度会比呈线性关系的产品的更快。

## 5. Alpha 测试与 Beta 测试
`Alpha test` 允许潜在用户测试功能上尚未稳定或完成的产品。用户可以对功能以及他们希望在成品中看到的内容提供价值建议。`Beta test` 允许用户测试功能上完整（或基本完成）的产品。`Beta test` 有助于在产品发布给大众之前发现 Bug 和其他困扰。

# 第 5 章

## 1. 系统管理员时间管理
系统管理员每天应该留出空闲时间，以应对可能发生的紧急情况，这些情况可能会干扰他们的其他日常活动。如果一切正常，可以使用这段时间追赶其他工作、阅读邮件列表并检查最新的操作系统补丁。

## 2. 服务台人员管理
通过提供充分的培训和工具来帮助服务台 `help desk` 人员高效工作，可以降低员工流失率。定期与服务台人员见面以评估当前的支持问题并收集对各种问题的意见，是留住员工的另一个关键。你还通过为服务台提供一条清晰且可实现的职业路径（可能通往成为系统管理员）来鼓励员工留在公司；以前的服务台人员通常是非常敏锐的系统管理员，因为他们对客户需求有真正的理解和知识。

## 3. 收益递减规律
收益递减规律会影响系统管理员，当有太多人试图修复同一个问题时，他们会互相干扰并可能加剧问题，而其他问题和需求却无人问津。

## 4. 值班指南
任何值班指南 `on-call guidelines` 至少应定义以下三点：

a. 它们应该分配对每个报告问题的响应责任。
b. 它们应该规定值班人员服务期间的地点、活动和响应时间。
c. 它们应该清晰地分配并描述系统管理人员、管理层和服务台人员之间的通信手段。

## 5. 升级程序
升级程序 `escalation procedure` 定义了如何以及何时将问题交给不同级别的支持，直到到达能够解决该问题的组。所有支持流程都需要升级程序，以指定中心联系点（如服务台）最终如何将问题路由到及时修复这些问题的组。

## 6. 预定义表单
预定义的表单强制用户输入有助于识别、定义和解决特定问题所需的信息。通过要求用户回答服务台人员在启动解决过程必须询问的问题，表单有助于减少问题解决的延迟。自由格式的邮件则由终端用户自行决定服务台可能问题可能需要哪些信息。

# 第 6 章

## 1. 主动监控与响应式监控
主动监控 `Proactive monitoring` 检查服务的统计数据和趋势，寻找潜在服务停机的预警信号，使系统管理员能够在问题发生之前将其阻止。响应式监控 `Reactive monitoring` 观察实际的停机状况，要求系统管理员在停机发生后做出响应。

## 附录 B • 答案

### 2. 端口监控
端口监控仅验证服务的端口是否接受连接；它并不会实际测试服务的功能。

### 3. syslog 配置
若要发送级别为 `kern` 且信息为 `info` 的系统日志，你需要在 `syslog.conf` 中添加以下内容并重启 syslog：

```
kern.info /var/log/kern
```

### 4. 通信冗余
向系统管理员同时发送寻呼页面和电子邮件，可以确保即使其中一条通信线路不可用（例如传呼机超出范围），他或她仍能收到消息。应急报告技术中的冗余是至关重要的，因为这种冗余在系统组件和功能中是必要的。

### 5. 外部监控
外部监控通过互联网访问你的服务，这可能代表了你的用户连接到你服务的方式。外部监控还可以防止监控器与网络服务之间的内部网络故障导致虚假的停机报告。例如，如果与互联网的连接断开，外部监控将认为你的服务不可用；但内部监控仍会认为你的服务是可用的，因为它使用内部网络访问你的服务。

### 6. 日志轮转
日志轮转 `Log rotation` 可以防止日志文件随时间推移占用所有可用磁盘空间，并允许生成更小、更易分析的日志文件。

# 第 7 章

## 1. 沙箱
沙箱会模拟你的生产环境，这样你在沙箱中运行的任何测试都会产生与你在生产平台上应获得的结果具有可比性。

## 2. 补丁模式
你应该在单用户模式下进行补丁，因为运行的进程较少，可能干扰或受到补丁过程的影响。如果你无法将系统切换到单用户模式，你应该选择在非峰期应用补丁，并在开始前杀死所有非本质进程。

## 3. 共享库
共享库是一个包含在不同程序间共享代码的文件。在升级操作系统时，必须特别注意共享库，即使升级后的共享库只发生微小的变化或不兼容性，也可能影响许多对你系统功能至关重要的程序。

## 4. 磁盘更换
在不支持热插拔的服务器上更换磁盘，你必须关闭服务器、移除旧磁盘、插入新磁盘、启动服务器，并（如果新磁盘与旧磁盘型号不同）重新配置系统以识别新磁盘。在支持热插拔的系统上，你只需移除旧磁盘并插入新磁盘，让硬件和操作系统处理磁盘交换过程的细节即可。（不过，这些只是通用步骤——在更换磁盘之前请务必阅读供应商的文档。）

## 5. 确定终端用户
系统管理员可以使用以下一种或多种方法确定特定服务的终端用户：

- 读取服务的文档，以了解谁会使用此类服务。
- 从账户数据库中提取信息，例如 Unix shell 用户的 `/etc/passwd`。
- 使用日志文件或网络流量分析器分析服务的使用情况。
- 与实际用户、销售人员、客户经理或任何可能知道谁在使用特定服务的人进行交流。

# 第 8 章

## 1. 维护窗口
安排维护窗口的最佳时机是受维护影响的服务使用率最低的时段。

## 2. 活动日志
活动日志提供了以前问题的历史记录以及处理方式。在开始处理停机故障之前审阅这些日志，可以避免你再次犯同样的错误，甚至提供解决问题的实际方案或步骤，从而节省时间。

## 3. SLA
`SLA` 服务水平协议规定了客户从提供者处期望的服务水平，通常体现在保证的运行时间和响应时间上。为了避免违反最大停机时间的 `SLA`，你监控服务的间隔时间应小于该特定服务指定的最大停机时间。这种时间安排可以确保系统管理员在超过服务的最大 `SLA` 之前收到错误或失败通知。

## 4. 回滚时间
你应该在维护窗口中留出回滚更改的时间，以便如果升级或安装未成功，可以在窗口结束前完成回滚程序。

## 5. 权宜之计
权宜之计 `Band-Aid solutions` 仅覆盖问题的症状，或通过增加基础设施来抑制问题。它们并没有解决实际问题，从长期来看会增加系统的复杂性。在需要快速解决问题的情况下，权宜之计是合适的。然而，权宜之计应该是暂时的；计划在任何权宜之计之后采取寻找并修复问题源的措施。

# 第 9 章

## 1. 停电风险
停电通常伴随着电压浪涌和低电压，这可能会损坏电子设备。电压浪涌通常发生在断电后恢复供时，而电压波动的“脏电”会严重损坏设备并威胁你的数据安全。浪涌保护和备份（如 `UPS` 不间断电源）对于保护设备免受此类损坏至关重要。

## 2. UPS 功能
`UPS` 在停电时提供电池备用，并保持恒定的电压水平以保护硬件免受“脏电”影响。

## 3. 发电机与 PDU
连接到建筑 `PDU` 电源分配单元的发电机允许你在停电期间无缝切换市电电源和发电机电源（反之亦然）。

## 4. 热备地与温备地
热备地 `Hot site` 除了活动硬件外，还包含你数据的实时副本，你可以无缝将业务迁移到热备地，而无需移动任何数据。温备地 `Warm site` 仅包含活动硬件，你必须在将业务迁移到温备地之前首先传输数据的最新副本。

## 5. 灾难恢复规划
灾难恢复规划维护你所有资源的数据库，包括员工、硬件、软件和供应商。如果发生任何变化，软件会更新其数据库，更改将自动传播到你所有的程序和文档中。否则，将手动更新。

## 6. 灾难恢复中心
灾难恢复中心不仅包含活动硬件，还包含你数据的实时副本，你可以无缝将业务迁移到该中心，而无需移动任何数据。
