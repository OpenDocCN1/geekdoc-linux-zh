
然而，你可以创建一个组。每个组都被分配一个唯一的数字，称为组 ID（`GID`）。每个组包含一个或多个用户 ID。一个用户 ID 可以是多个组的成员，但组不能包含组；它们只能包含用户。像用户一样，组也有名称。但是，与用户名不同，组名并不重要；系统内部始终使用组 ID。

继续我们的例子，你可以创建一个经理组，并将所有经理的用户 ID 放入该组中。你可以创建一个任何组内成员都可以读取但组外成员无法读取的文件。通常情况下，你只能与资源关联一个组。没有办法指定如果用户在组 7 或组 42 中，就可以访问文件。

如果你好奇查看自己的用户 ID 是多少以及属于哪些组，可以使用 `id` 命令。例如，输出可能如下：

```
uid=501(mitchell) groups=501(mitchell),503(cs1)
```

第一部分显示运行命令的用户的 ID 是 501。命令还显示了相应的用户名，并显示在括号中。命令显示用户 ID 501 实际上在两个组：组 501 (`mitchell`) 和组 503 (`cs1`)。你可能奇怪为什么组 501 出现了两次：一次在 gid 字段中，一次在 groups 字段中。我们稍后会解释这一点。

## 10.1.1 超级用户

有一个账户非常特殊。该用户的用户 ID 为 0，用户名通常为 `root`。它有时也被称为超级用户（superuser）。`root` 用户可以执行任何事情：读取任何文件、删除任何文件、添加新用户、关闭网络访问，等等。以 `root` 权限运行的进程（即以 `root` 身份运行）可以执行许多特殊操作。

这种设计的麻烦之处在于，许多程序需要由 `root` 运行，因为其中许多程序都需要这些特殊操作。如果这些程序任何一个出现异常，就会导致混乱。当程序由 `root` 运行时，没有有效的方法可以限制它；它可以做任何事情。由 `root` 的程序必须编写得非常小心。

### 10.2 进程用户 ID 和进程组 ID

到为止，我们讨论的是由特定用户执行的命令。这并不准确，因为计算机并不知道它在使用哪个用户。如果 Eve 学会了 Alice 的用户名和密码，Eve 就可以以 Alice 的身份登录，计算机允许她做 Alice 能做的一切事情。系统知道正在使用哪个用户，而不是哪个用户在尝试执行命令。如果 Alice 不被信任能保管自己的密码，那么你作为应用程序开发者的做什么都无法阻止 Eve 访问 Alice 的文件。系统安全的责任由应用程序开发者、系统用户和系统管理员共同承担。

每个进程都有一个关联的用户 ID（`UID`）和组 ID（`GID`）。当你调用一个命令时，它运行在一个进程中，该进程的用户 ID 和组 ID 与你的 ID 和组相同。当我们说一个用户执行了某个操作时，我们实际上是指具有相应用户 ID 的进程在执行该操作。当进程发出系统调用时，内核决定是否允许操作继续。它通过检查进程尝试访问的资源相关的权限，并检查与执行操作进程关联的用户 ID 和组 ID 来做出判断。

现在你知道 `id` 命令打印的那个字段是怎么回事了。它显示的是当前进程的 ID。尽管用户 501 多个组，但当前进程只能有一个组 ID。在之前显示的示例中，当前组 ID 是 501。

如果你需要在程序中管理用户 ID 和组 ID（如果你在编写处理安全的程序，你就会需要），你应该使用在 `<sys/types.h>` 中定义的 `uid_t` 和 `gid_t` 类型。尽管用户 ID 和组 ID 本质上是整数，但要避免对这些类型使用了多少位做出任何假设，也不要对其进行算术运算，应将它们视为用户和组身份的透明句柄。

- 1. AT&T 对其 UNIX 操作系统只有一个特殊用户这一事实。相比之下，早早一个拥有多个用户的操作系统被称为 MULTICS。当然，GNU/Linux 与 UNIX 的兼容性最高。

要获取当前进程的用户 ID 和组 ID，你可以使用在 `<unistd.h>` 中声明的 `getuid` 和 `getegid` 函数。这些函数不接受任何参数，并且它们始终有效；你不需要检查错误。列表 10.1 显示了一个简单的程序，它提供了 `id` 命令的部分功能：

#### 列表 10.1 (simple.c) 打印用户和组 ID

```c
#include <sys/types.h>
#include <unistd.h>
#include <stdio.h>

int main() {
    uid_t uid = getuid();
    gid_t gid = getegid();
    printf("uid=%d gid=%d\n", (int) uid, (int) gid);
    return 0;
}
```

当运行此程序时（由运行真实 `id` 程序的同一个用户运行），输出如下：

- * simpleid

`uid=501 gid=501`

### 10.3 文件系统权限

查看用户和组实际运作的一种良好方法是查看文件系统权限。通过检查系统如何将权限与每个文件关联，并查看内核如何检查允许谁访问文件，用户 ID 和组 ID 的概念应该变得更加清晰。

每个文件恰好有一个所有者和一个所有组。当你创建一个新文件时，该文件由创建创建进程的用户和组所有。

对于 Linux 而言，你对文件可以做的基本操作是读取、写入和执行。（注意，创建文件和删除文件不被视为对文件可以进行的操作；它们被视为对包含该文件的目录可以进行的操作。我们稍后会讨论这一点。）如果你无法读取一个文件，Linux 就不会让你查看该文件的内容。如果你无法写入一个文件，你就无法更改其内容。如果你对某个程序没有执行权限，你就无法运行该程序。

- * 实际上，有一些少数例外，涉及粘滞位（sticky bits），将在后第 10.3.2 节“粘滞位”中讨论。

Linux 允许你指定这三种操作——读取、写入和执行——哪些可以由所有者、所有组以及其他人执行。例如，你可以说所有者可以对文件做任何想做的事，所有组中的任何人都可以读取和执行该文件（但不能写入），而其他人无法访问它。

## 10.3 文件系统权限 203

```c
/* 获取文件信息。 */
stat (filename, &buf);
/* 如果权限设置允许文件所有者向其写入内容，
则打印一条消息。 */
if (buf.st_mode & S_IWUSR) {
    printf("Owning user can write %s\n", filename);
    return 0;
}
```

如果你在我们的 `hello` 文件上运行此程序，它会显示：

- ./stat-perm hello

`Owning user can write 'hello'.`

常量 `S_IWUSR` 为文件所有者提供写权限。所有位位都有其他常量。例如，`S_IRGRP` 是文件所有组的读取权限，而 `S_IXGRP` 是对既不是所有者也不是所有组成员的用户的执行权限。如果你在变量中使用权限，变量的类型为 `mode_t`。对于大多数系统调用，`stat` 如果无法获取文件信息，将返回 -1 并设置 `errno`。

你可以使用 `chmod` 函数更改现有文件的权限位。你可以调用 `chmod` 并传入你想要更改的文件名以及你设置的权限位，这些权限位是通过之前权限常量的按位或表示的。例如，此行将使 `hello` 对其所有者可读可执行，但禁用与 `hello` 相关的所有权限：

```c
chmod ("hello", S_IWUSR);
```

相同的权限适用于目录，但它们的含义不同。如果用户被允许读取目录，则该用户能够看到目录中存在的文件列表。如果用户被允许写入目录，则允许该用户从目录中添加或删除文件。注意，如果用户被允许写入目录，即使她没有修改该目录的权限，也可以从目录中删除文件。如果用户被允许执行目录，则允许该用户访问并执行其中的文件。在无法访问目录的情况下，无论文件本身的权限如何，用户都不允许访问该目录中的文件。

总结一下，让我们回顾内核如何决定是否允许进程访问特定文件。它会检查访问的用户是否是所有者、所有组的成员或其他身份。访问用户所属的类别用于决定检查哪些读/写/执行位。内核会检查操作是否是针对适用于该用户的权限位执行的。

- 4. 如果路径中的某个文件组件不可访问，内核也可能拒绝对该文件的访问。例如，如果一个进程无法访问目录 `/tmp/private/`，即使该文件的权限被设置为允许访问，它也无法读取 `/tmp/private/data`。

有一个重要的例外：以 `root` 身份运行的进程（用户 ID 为 0）始终被允许访问任何文件，无论与其相关的权限如何。

#### 10.3.1 安全漏洞：没有执行权限的程序

除了读、写、执行权限外，还有一个被称为“粘滞位”（sticky bit）的魔位。此位仅适用于目录。

设置了粘滞位的目录仅允许在你是文件所有者时才删除该文件。如前所述，通常如果你对包含文件的目录具有写权限，就可以删除该文件，即使你不是文件的所有者。当设置了粘滞位时，你仍然必须拥有目录的权限，但你必须是你所删除的文件的所有者。

典型的 GNU/Linux 系统上的某些目录设置了粘滞位。例如 `/tmp` 目录，任何用户都可以在其中放置临时文件，因此目录位专门设计供所有用户使用，使得目录对所有人都可写。但如果一个用户可以删除另一个用户的文件，那就糟糕了，因此在该目录上设置了粘滞位。只有所有者（当然也包括 `root`）才能删除文件。

当你运行 `ls /tmp` 时，可以通过权限位末尾的 `t` 看到粘滞位已设置：

```bash
% ls -ld /tmp
drwxrwxrwt 12 root       2048 Jan 24 17:51 /tmp
```

与 `stat` 和 `chmod` 对应的常量是 `S_ISVTX`。如果你的程序创建了行为类似于 `/tmp` 的目录（即许多人在那里放东西，但不应该能够删除彼此的文件），那么你应该在目录上设置粘滞位。你可以通过调用以下命令使用 `chmod` 在目录上设置粘滞位：

```bash
% chmod o+t directory
```

- 5. 这个名字是过时的；它追溯到一个时代，当时设置粘滞位会导致程序在执行时保留在主内存中。分配给程序的页面被“卡”在内存中。

要通过程序化方式设置粘滞位，请调用带有 `S_ISVTX` 的 `chmod`。如果你的程序创建了行为类似于 `/tmp` 的目录（即许多人在那里放东西，但不应该能够删除彼此的文件），那么你应该在目录上设置粘滞位。

## 10.4 真实与有效 ID 207

这里有一个谜题：以非 `root` 用户身份运行，你是否可能永远变成 `root`？使用之前的技术，这似乎是不可能的，但这里证明了它可以实现。

```bash
% whoami
mitchell
% su
Password: ...
% whoami
root
```

`whoami` 命令就像 `id` 命令，区别在于它只显示有效用户 ID（effective user ID），而不显示所有其他信息。`su` 允许你在知道 `root` 密码的情况下成为超级用户。

`su` 是如何工作的？因为我们知道 shell 在最初运行时，其真实 ID（real ID）和有效用户 ID 都设置为 `mitchell`，因此 `setuid` 不允许我们更改它的其他 ID。

诀窍在于 `su` 程序是一个 `setuid` 程序。这意味着当它运行时运行时，进程的有效用户 ID 将是文件所有者的 ID，而不是执行 `exec` 调进程的有效用户 ID。（真实用户 ID 仍然是执行时的 ID。）要创建一个 `setuid` 程序，如果你在命令行调用 `chmod +s`，则使用 `S_SUID` 标志；或者通过程序调用 `chmod`。

例如，考虑列表 10.3 中的程序。

### 列表 10.3 (setuid-test.c) Setuid 演示程序

```c
#include <stdio.h>
#include <unistd.h>

int main () {
    printf("uid=%d eid=%d\n", (int) getuid(), (int) geteuid());
    return 0;
}
```

现在假设这个 `setuid` 程序由 `root` 所有。在这种情况下，`ls` 的输出将如下所示：

```
-rwsr-xr-x root root 11931 Jan 24 18:25 setuid-test
```

`s` 位表示该文件不仅是可执行的（正如 `x` 位指示的那样），而且设置了 `setuid` 和 `setgid`。当我们使用这个程序时，得到的输出如下：

```bash
% whoami
mitchell
% ./setuid-test
uid=501 eid=0
```

6. 当然，还有一个类似的 `setgid` 程序概念。运行时，有效组 ID（effective group ID）与文件的所有组 ID 相同。大多数 `setuid` 程序也是 `setgid` 程序。

注意，当程序运行时，有效用户 ID 被设置为 0。你可以使用 `chmod` 命令权限配合 `u+s` 或 `g+s` 参数分别在可执行文件上设置 `setuid` 和 `setgid` 位——例如：

```bash
% ls -l program
-rwxr-xr-x 1 samuel  csl      0 Jan 30 23:38 program
% chmod g+s program
% ls -l program
-rwxr-xr-x 1 samuel  csl      0 Jan 30 23:38 program
% chmod u+s program
-rwxr-sr-x 1 samuel  csl      0 Jan 30 23:38 program
```

你也可以使用带有 `S_ISUID` 或 `S_ISGID` 模式标志的 `chmod` 调用。它最初以有效用户 ID 为 0 运行。然后它会提示你输入密码。如果密码与 `root` 密码匹配，它会将真实用户 ID 也设置为 `root` 并启动一个新的 shell。否则，它会退出，毫无留情地让你作为一个非特权用户。看一眼 `su` 程序的权限：

```bash
% ls -l /bin/su
-rwxr-xr-x 1 root  root      14188 Mar 7 2000 /bin/su
```

注意，它由 `root` 所有，并且设置了 `setuid` 位。注意 `su` 并没有实际上改变运行它的 shell 的用户 ID。相反，它用新的用户 ID 启动了一个新进程。原始 shell 被阻塞，直到新 shell 完成且 `su` 退出。

### 10.5 用户身份验证

通常，如果你有一个 `setuid` 程序，你并不希望它为所有人提供服务。例如，`su` 程序只在你知道 `root` 密码时才允许你成为 `root`。该程序在执行操作之前，会让你证明你有能力成为 `root`。这个过程被称为“身份验证”（authentication）——`su` 程序正在检查你的身份是否真实。

如果你正在管理一个非常安全的系统，你可能不想让人们仅通过输入普通密码就登录。用户倾向于写下密码，而黑客倾向于找到它们。用户倾向于选择涉及他们的生日、宠物名字等的密码。密码并不安全。

- 7. 据发现，系统管理员选择 `god` 这个单词作为密码的频率比任何其他密码都高。（随你怎么想吧。）所以，如果你在某台机器上需要 `root` 权限而系统管理员不在身边，一点“神圣的启示”可能正是你需要的。

例如，许多组织现在要求使用由特殊电子 ID 卡生成的“一次性”密码，用户随身携带。同一个密码不能使用两次，而且如果不输入 PIN，你就无法从 ID 卡中获得有效密码。在安全设施中，攻击者必须同时获得实体卡和 PIN。

如果你正在编写一个需要身份验证的程序，这种被称为可插拔认证模块（Pluggable Authentication Modules, PAM）的机制让这一切变得简单。

### 列表 10.4 示例

```c
#include <security/pam.h>
#include <security/pam_misc.h>
#include <stdio.h>

int main ()
{
    pam_handle_t* pam;
    struct pam_conv pamc;

    /* 设置对话机制。 */
    pamc.conv = misc_conv;
    pamc.appdata_ptr = NULL;

    /* 启动新会话。 */
    if (pam_start("su", getenv("USER"), &pamc, &pam) != PAM_SUCCESS) {
        fprintf(stderr, "验证失败!\n");
        return 1;
    }

    /* 验证用户。 */
    if (pam_authenticate(pam, 0) != PAM_SUCCESS) {
        fprintf(stderr, "验证失败!\n");
    } else {
        fprintf(stderr, "验证通过。\n");
    }

    /* 全部完成。 */
    pam_end(pam, 0);
    return 0;
}
```

要编译这个程序，你必须链接两个库：`libpam` 和一个辅助库 `libpam_misc`：

```bash
% gcc -o pam pam.c -lpam -lpam_misc
```

#### 10.6.1 缓冲区溢出（Buffer Overruns）

几乎每个 Internet 守护进程（daemon），包括 `sendmail` 守护进程、`finger` 守护进程、`talk` 守护进程等，都曾在某一个时刻通过缓冲区溢出被攻击过。
