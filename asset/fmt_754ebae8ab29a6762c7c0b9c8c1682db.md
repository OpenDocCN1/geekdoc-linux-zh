
# 13.1.2 运行 GDB

列表 13-1 的第一行显示了如何从命令行调用 GDB。由于我们正在进行交叉调试，因此我们需要为我们的主机系统和目标系统编译的交叉版本 GDB。我们按照所示调用版本的交叉-gdb，并向 `xscale_be-gdb` 传递二进制文件的名称，随后是核心转储文件的名称——在本例中，简单地称为 core。在 GDB 打印出几行描述其配置和其他信息后，它显示了终止的原因：信号 11，这表示段错误。

GDB 加载二进制文件、其依赖的库以及核心文件时会接着输出几行。GDB 启动时打印的最后一行是故障发生时程序当前的位置。以 `#` 字符串开头的行表示栈帧（栈帧 0 位于虚拟地址 `0x00012ac4` 处的 `ClearBlock()` 函数中）。

> 信号及其关联数字定义在 Linux 内核源码树的 `.../arch/<arch>/include/asm/signal.h` 中。

接下来的带有 43 的行是来自 `led.c` 文件的错误源行行号。从那里，GDB 显示其命令提示符并等待输入。

为了提供一些上下文，我们输入了 gdb `list` 命令，使用了其缩写形式 `1`。在没有歧义的情况下，GDB 会识别缩写。在这里，程序错误并没有直接呈现出来。根据 GDB 对核心转储的分析，这里是出错的行：

```
*ptr = 0;
```

我们对变量 `ptr` 发射了 gdb `print` 命令，缩写为 `p`。正如列表 13-1 所示，指针 `ptr` 的值为 0。因此得出结论，段错误的原因是空指针解引用，这是许多编程语言中的常见错误。从这里开始，我们选择使用 `backtrack` 命令查看导致此错误的调用链，这可能会带我们回到错误的源头。列表 13-2 显示了这些结果。
