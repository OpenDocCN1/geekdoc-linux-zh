
文件数据（inodes）和文件数据在磁盘上是物理分离的，这可能导致显著的时间延迟。例如，`[LEFB89]`描述了一个传统的150MB文件系统具有4MB的inodes，其后是146MB的数据。在访问文件时，在读取数据块之前，在读取inode之后总会有长长的寻道。从一个数据块移动到下一个数据块时，也会增加整体延迟，而这些块在磁盘上很可能是不连续的。

在BSD和BSD4.0之间的一些早期工作将旧文件系统的块大小翻倍到1024字节，显示性能提高了一倍。块大小的增加也减少许多文件对间接块（indirect blocks）的需求。

考虑到这些特性，伯克利团队设计了一种新的文件系统，其速度是前者的数倍，且具有更少的I/O和更高的磁盘吞吐量。

新设计的一个关键方面涉及数据在磁盘上的布局，如图9.5所示。新文件系统被分为若干柱道组（cylinder groups），直接映射到当时磁盘驱动器数据的柱道布局——注意，在早期驱动器上，每个柱道无论是靠近盘边缘还是内部，的数据量都是相同的。每个柱道组包含一个超级块副本、固定数量的inodes、描述空块和数据块的位图、描述块使用情况摘要表以及数据块本身。每个柱道组包含固定数量的inodes。每个柱道组的inode数量计算方式为每2048字节的数据创建一个inode。这被认为提供的文件远多于实际需要。

为了实现某种完整性，柱道组的元数据没有存储在每个柱道组的同一个盘面上。相反，为了避免将所有文件系统结构数据都放在顶层面上，第二个柱道组的元数据被放在第二个盘面上，第三个柱道组的元数据放在第三个盘面上，以此类推。除了第一个柱道组外，数据块存储在柱道组元数据的前后后。

## 块大小与碎片

旧文件系统限于512字节数据块，而FFS允许块大小至少达到4096字节，受存储在磁盘上的数据类型大小的限制。选择4096字节块大小是为了访问大小高达$2^{32}$字节的文件只需两层间接。文件系统的块大小是在文件系统无法动态更改时选定的。当然，不同的文件系统可以有不同的块大小。

由于在FFS开发时大多数文件的大小小于4096字节，文件数据可以存储在单个4096字节数据块中。如果一个文件仅略大于文件系统块大小的倍数，可能会导致大量的空间浪费。为了缓解这个问题，新文件系统引入了碎片（fragments）的概念。在这一方案中，数据块可以被分为2、4或8个碎片，其大小在创建文件系统时确定。例如，如果一个文件包含4100字节，则该文件将包含一个4096字节的数据块和一个1024字节的碎片，用于存储剩余的数据部分。

当文件被扩展时，将分配一个新的数据块或其他碎片。遵循的分配策略记录在`[MKCU84]`中，并所示：

1. 如果覆盖文件末尾的碎片或数据块中有空间，则将新数据简单复制到该块或碎片中。
2. 如果没有碎片，则填充现有块并分配新的数据块，直到写入完成或数据不足以填充新块。在这种情况下，将分配一个具有正确碎片数量的块或一个新的数据块。
3. 如果文件包含一个或多个碎片，且要写入的新数据加上碎片中的数据量超过了数据块可用空间，则分配新块，并将数据从碎片复制到新数据块，然后将新数据追加到文件中。然后遵循步骤2中的过程。

当然，如果文件通过少量数据扩展，由于碎片的分配，将会产生过多的拷贝……

- **符号链接**。在引入它们之前，原始UNIX文件系统仅支持硬链接。
- **长文件名**。旧的文件系统限制文件名长度为15个字符。FFS提供了任意长度的文件名。在第一个FFS实现中，文件名最初被限制在255个字符以内。
- **文件锁定**。为了避免使用单独锁文件来同步对另一个文件的更新而产生的问题，BSD团队实现了建议性锁定方案。锁可以是共享的，也可以是排他的。
- **文件重命名**。实现了一个单一的`rename`系统调用。此前，需要三个独立的系统调用，这导致在系统崩溃后会出现问题。
- **配额**。最后添加的功能是支持用户配额。欲需更多细节，请参阅第5章中的“用户和组配额”部分。

所有这些功能在今天都是理所当然的，并且在所有UNIX版本的大多数文件系统中都可用。

## 自从早期UFS实现以来发生了什么？

长期以来，磁盘驱动器不再遵循固定尺寸的柱道，理由是盘片边缘的轨道比内层轨道可以存储更多数据。这使得“柱道组”的概念在某种程度上是一个不当名称，因为柱道组不再直接映射到磁盘本身的柱道上。因此，早期UFS实现中存在的一些优化在当今的磁盘驱动器上已不再适用，而且在某些情况下实际上适得其反。

然而，UFS采用的引用局部性模型导致节点（inodes）和数据被放置在相邻的位置，因此仍然对性能有帮助。

## Solaris UFS历史与增强

由于SunOS（Solaris的前身）基于BSD UNIX，它是最早支持UFS的操作系统之一。直到今天，Sun一直持续UFS的开发工作。

本节分析了Sun对UFS进行的增强，演示了其中某些功能在实践中如何工作，并展示了本章中FFS的底层功能在如今的UFS中是如何实现的。

## 创建UFS文件系统

仍然有很多选项可以传递给`mkfs`命令来创建磁盘几何结构。首先，考虑以下创建100MB文件系统的`mkfs`调用。注意，传递的大小是以512字节扇区为单位指定的。

```
# mkfs -F ufs /dev/vx/rdsk/fs1 204800
/dev/vx/rdsk/fs1:204800 sectors in 400 cylinders of 16 tracks, 32 sectors
  100.0MB in 25 groups (16 c/g, 4.0MB/g, 1920 i/g)
super-block blocks (for fsck -F -o b#):
32, 8256, 16480, 24074, 32928, 41152, 49376, 57600, 65824, 74048, 82272,
90496, 98270, 106944, 115168, 123932, 131104, 139328, 147552, 155776,
164000, 172224, 180480, 188672, 196896.
```

默认情况下，`mkfs`决定选择创建哪个柱道组，尽管可以使用`csize=n`选项来覆盖此。默认情况下，文件系统的大小是通过将传递给`mkfs`的扇区数除以IGB然后乘以32来计算的。对于此文件系统中创建的25个柱道组中的每一个，`mkfs`通过显示在整个文件系统中每个柱道组开始处的超级块位置来显示。

以下是可以传递给`mkfs`的某些选项：

- `bsize=n`。此选项用于指定文件系统块大小可以是4096或8192。
- `fragsize=n`。`n`的值用于指定碎片大小。对于块大小为4096，选择有512、1024、2048或4096。对于块大小为8192，选择有1024、2048、4096和8192。
- `free=n`。这是维护的空闲空间。这是一个阈值，一旦达到该值将阻止分配更多块。默认值为10%。根据本章较早关于UFS性能分析的信息，此值不应减小；否则会对块和碎片分配方法产生影响。
- `nbpi=n`。这是一个特殊选项，指定每个节点的字节数。它用于确定文件系统的节点数量。文件系统的大小除以指定的值，得到创建的节点数量。考虑到`nbpi`选项，创建了一个小文件系统：

```
# mkfs -F ufs /dev/vx/rdsk/fs1 5120
/dev/vx/rdsk/fs1:5120 sectors in 10 cylinders of 16 tracks, 32 sectors
  2.5MB in 1 cylinder groups (16 c/g, 4.0MB/g, 1920 i/g)
super-block blocks (for fsck -F -o b#):
32,
```

该文件系统有一个柱道组。通过使用`fsype`命令可以获得有关文件系统的更详细信息：

```
# fsype -v /dev/vx/rdsk/fs1
magic 11954 format time 8 09:56:38
sblkn 16 cblkn 24 iblkn 272
```
