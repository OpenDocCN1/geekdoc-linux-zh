
一些人表示担忧，Unix 的软件开发方法虽然非常适用于小系统，但并不适用于更大的系统。他们认为，在没有详尽设计的情况下开始编码阶段是工程上的自杀。他们声称缺乏足够的远见会导致灾难。

然而，我们并不是说一个人应该在没有充分设计的情况下跳入大型系统的编码。为了定义适当的目标，某种推敲是必要的。在继续之前记录每个细节非常有用，因为细节可能会改变。这里的关键在于识别系统如何被拆分成更小的组件。然后每个组件都可以在小得的设计领域内进行架构设计。

还要考虑到，Unix 拥有“极少前置设计”的优势，它演变成了一个能够处理曾经属于大型系统任务的系统。这种规模的系统传统上需要无数次的功能规范和详细设计文档。今天存在大量的 Unix 文档，但大部分描述的是通过几位进取的技术出版者的努力已经存在的设计。原始规范几乎不存在。

与大多数按传统方式规划的系统不同，Unix 是从原型演化而来的。它源于一系列设计迭代，从一个用途有限的实验室系统变成一个用来处理艰巨任务的系统。它是某种设计哲学的活证明，这种哲学对某些人来说是非正统的，但产生了卓越的结果。

# 可移植性优先

于是我，作为 1991 年 USENIX 技术会议的参会者，漫步在纳什维尔 Opryland 酒店的长廊，沉浸在那座乡村音乐堡垒的宏伟奢华氛围中，在人群中穿行，希望偶上名人，并沉浸在已签署出版合同的满足感中。

一切进展得异常顺利。我关于 Unix 哲学的书籍提案被毫不犹豫地接受了。（“有这么多的人需要这本书。”）。合同谈判很顺利。（“我想要 `$n$` 美元的预付款。”）“好的，你得到了。”设定了一个合理的截止日期。（“我们会给你几个月的时间，让你过得轻松些。”）你不能要求比这理想的处境了。

说实话，我快害死了。在克服了为一个我磨练多年的话题写书的最初热情后，我一头撞进了一个我在心理上还没有准备好的现实：现在我必须写出这个东西了。

我过去的写作经验主要是为一家地区娱乐杂志挤稿。我学会了如何将单词串在一起。我知道主题句、动作动词以及被动语态的使用。我可以抓住读者的注意力并保持他们的兴趣。然而，写杂志文章让我变成了一个出色的短跑运动员。现在是时候跑马拉松了。我做的第一件事就是冲向一个朋友寻求建议。他是一位写过本书的作者，以前跑过这场比赛。我问，我能做什么来应对这个看似艰巨的任务？

> “一台笔记本电脑，”他回答道。

看到我脸上石器人般的表情，他解释说写一本书是一个全有全无的命题。要把如此多的想法写在纸上需要密集、集中的精力。作为现代技术的一项惊人成就，典型的笔记本电脑在一个比三环活夹还薄的包装内装了比台式电脑更强大的功能。重量不到五磅，其低外形设计便于携带。它们配有硬盘和内置调制调器器是日常计算任务（如计算电子表格、文字处理和编程）的可靠得力。

不久前，苹果电脑播放了一段电视节目，显示两个高管讨论各种电脑的优点。他们都在谈论技术规格，其中一个似乎有了深刻的启示：最强大的计算机不是 CPU 最快、硬盘最大或最华丽的那台；而是使用最频繁的那台。

如果仅根据这一标准判断，笔记本电脑有一天将成为人类历史上以来最强大的计算机。它没有实验室超级计算机那种令人眩晕的速度。它没有最新的磁盘阵列技术的存储容量。它的图形能力将一直落后于最快的桌面显示器。它几乎不是性能的典范，它只有一个优势：可移植性。

这带我们进入 Unix 哲学的下一个准则。你可能希望对这一条做特别标记。它标志着 Unix 拥有数千年工作量寿命的原因。

## 原则 4：可移植性优于效率

软件开发涉及选择，每个选择都代表妥协。有时开发者必须写一个简短简单的子程序，因为他没有时间包含更复杂的。在其他时候，内存可能是可能是限制。在某些情况下，必须避免使用过多小数据包的网络连接，使用的网络协议倾向于大块传输。程序员在尝试满足往往冲突的目标时，总是在一系列妥协中做出选择。

程序员面临的一个困难问题是可移植性与效率的权衡。这也是一个痛苦的选择，因为偏向效率会导致不可移植的代码，而在性能不佳的软件中选择可移植性。

高效的软件不会浪费 CPU 周期。它充分利用底层硬件，通常完全忽略可移植性问题。它利用了如图形加速器、缓存内存和专用浮点指令等特性。

### 4.1 原则 4：可移植性优于效率

尽管从纯主义的角度来看，高效的软件很有吸引力，但在许多不同的机器架构上运行软件的价值使平衡倾向了另一方。其原因更多是财务考虑而非技术：在当今的计算环境中，仅运行在一种架构上的软件会限制其潜在的市场营销能力。

内置可移植性并不意味着你必须接受效率低下且技术上晦涩的软件。相反，从可移植软件中获得最佳性能需要更高水平的技术造诣。然而，如果没有这种造诣，你还有另一种选择，即可以等到硬件变得面世。

#### 4.1.1 明年的硬件将运行得更快

我们过去会在这个空格处填入“年”：明年的硬件将运行得更快。由于硬件技术飞进的速度之快，我们有时可以说下个季度甚至下个月的硬件可能运行得更快。如今计算机制造商不断缩短的产品开发周期使他们能够以比过去短得多的时间生产新型号。供应商们通过频繁发布更高性能、更低价格的产品相互超越。结果是，你今天使用的任何设备很快都会感觉像你大学实验室里那台笨重的旧巨兽。

这种向更紧凑的设计周期的趋势将继续加速。今天的半导体设计师使用复杂的仿真器来创建其微芯片的后续版本。随着这些仿真器（强大的计算机）不断获得加速，开发者可以更快地创建设计。这些新芯片将成为明天仿真器的引擎。这种现象随着每一代硅处理器的出现而滚雪球。半导体设计世界正处于一个眩目的、向上的性能螺旋中。

随着更快的机器取代慢的机器，关键问题就不再是你的软件是否充分利用了硬件的所有功能，而是你的软件是否能在较新的机器上运行。你可能会花费几天或几周的时间调整应用程序，以便在今天的平台上获得更好的性能，结果发现下一次硬件升级就让你“免费”获得了十倍的速度提升。然而，你的软件可能是可移植的，以便利用下一台超级计算机。

在 Unix 环境中，这通常意味着将软件写成 `shell` 脚本。一个 `shell` 脚本由多个可执行命令放在单个文件中，通过 Unix 命令解释器间接执行。由于典型的 Unix 发行版中存在大量微小的、单一用途的命令，所有的底层任务都可以从 `shell` 脚本轻松构建。

脚本的一个附加好处是，它们比用 `C` 语言编写的程序要可移植得多。这听起来可能很异端，只有在绝对必要时才应该考虑用 `C` 编写程序。在 Unix 环境中，`C` 缺乏 `shell` 脚本的可移植性。程序通常在头文件定义、机器架构大小以及 Unix 实现的许多其他不可移植特性上存在差异。随着 Unix 从 16 位发展到 32 位和 64 位架构，大量的软件变得无法运行，因为 `C` 并不非常可移植。`C` 仅仅是 20 世纪 80 年代的汇语言而已。

如果你想让程序运行在 Unix 之外的其他系统上怎么办？还存在其他的语言选择，每种选择都有其独特的优缺点。如果你的目标仅仅是可移植性，那么 `Perl` 和 `Java` 很好地符合要求，因为它们在 Unix 和 Windows 平台上都有实现。然而，仅仅因为一种语言被移植到 Unix 之外的平台，并不意味着另一个平台遵循 Unix 哲学和 Unix 的办事方式。你会发现，例如 Windows 上的 `Java` 开发者倾向于成为交互式开发环境（IDE）的大力支持者，这些环境隐藏了底层的复杂性；而 `Java` 开发者通常更偏于让他们离开图形用户界面的工具和环境。

#### 4.1.2 不要花太多时间让程序运行得更快

如果它运行得已经足够快，就接受它已经满足你需求的现实。所有用于调整子程序和消除关键瓶颈的时间都应该考虑到未来硬件平台的性能提升。抵制为了软件而编写软件的倾向。记住，明年的机器就在眼前。

许多 Unix 程序员犯的常见错误是用 `C` 语言重写脚本以获得性能上的微小优势。这是浪费时间，不如把时间花在从用户那里获得建设性的反馈上。有时 `shell` 脚本可能确实运行得不够快。但是，如果你绝对需要高性能，并且认为你需要 `C` 才能实现，请仔细考虑一下——考虑一遍。

### 4.1 原则 4：可移植性优于效率

尽管某些特定的应用程序除外，否则用 `C` 语言重写脚本通常是不划算的。

警惕“微优化”，如果——这是一个非常大的“如果”——你必须优化 `C` 程序的性能，Unix 提供了 `prof` 和其他工具来识别使用最频繁的子程序。调整被调用成百上千次的程序可以以最小的努力产生最大的改进。

提高程序性能的另一种方法是检查你处理数据的方式。例如，我曾写过一个简单的脚本，可以在一秒内搜索分散在数千文件中的超过两百万行源代码。秘密在于先创建一个数据索引。索引的每行都包含一个唯一的单词以及包含该单词的所有文件列表。大多数程序使用的符号少于 20,000 个，这意味着索引不会超过 20,000 行。对于 Unix 工具 `grep` 来说，搜索 20,000 行是一个相对简单的任务。一旦 `grep` 找到了唯一的单词条目，它只需打印与该单词关联的文件列表。它非常快，由于数据处理的方式，它是可移植的。

#### 4.1.3 最高效的方法很少是可移植的

当你利用硬件能力时，你的软件就变成了销售硬件的工具，而不是一个独立的软件。这限制了它作为一种软件产品的效能，并导致你以低于其内在价值的价格出售它。

#### 4.1.4 可移植软件还减少了对用户培训的需求

一旦用户花时间学习了一个应用程序包，他就可以在未来的平台上通过运行同一个包来从这项投资中获益。
