
如果这种方法行不通，那么在任何情况下，你的下一步都应该是让用户缓慢离开键盘，同时让手一直放在键盘上（希望），这可以防止由于同时冲突尝试补救局面而引起的任何问题。你最好的选择是使用 `kill -2 (SIGINT)`。`kill -2` 只是在目标 4GL 过程中触发 `STOP` 条件，导致 `-p` 启动过程重新运行。进程不会死亡，但你不会做任何坏事。如果问题类似于“Tm 挂起”，用户可能会直接找回他们的会话，而无需重新通过 UNIX 登录；如果是网络或 PC 挂起问题，你就没辙了。

如果你确实需要 `kill -2`——也许你限制每个用户只能登录一次，由于网络问题导致空闲会话阻塞了访问——那么你仍然应该 `kill -2` 让进程进入稳定状态。当状态稳定后，`.lg` 文件会显示任何事务购买已完成，且它不再积累 CPU 时间和执行 IO 操作，此时如果用户已经关闭了终端，使用 `kill -1 (SIGHUP)` 就可以非常安全地终止它。`kill -15 (SIGTERM)` 具有相同的效果。

使用一系列 `kill` 命令并不是一个好主意，除非你在这些操作之间留出足够的时间，并监控 `.lg` 文件和状态。如果你中断了 Progress 的清理程序，且对中断的中断没有被正确处理，可能会导致数据库崩溃。使用 shell `trap` 命令来捕获信号是一个坏主意。它会破坏这些信号的正常运行，并导致系统不稳定。如果你退出了 _progress 会话_，然后输入命令并重新回来，那么你的系统就处于风险之中。这种情况下最常见的问题是逃逸进程——试图消耗所有 CPU 的进程。如果你已经摆脱了

`kill -8 (SIGFREE)` 的行为取决于 Progress 的版本。在某些版本中，它就像一个没听到的信号——也就是说，它会转储核心并在进程没有尝试清理的情况下死亡，这本质上与 `kill -9` 一样。这是因为你可能持有某个锁（latch），从而导致数据库崩溃。在较新的版本（包括 Linux 8.3 版本）中，它会像发送 `SIGHUP` 一样进行清理，同时创建一个 `procore` 文件。

最近版本中的 `kill -16 (SIGUSR1)` 允许进程在不影响进程（进程继续运行）的情况下创建 `procore` 文件和 `protrace` 文件。这是一个非常奇妙的功能，尽管它没有得到良好的支持（没有在任何地方被记录，TS 对其存在一无所知）。`protrace` 文件非常有用，它记录了进程在接收信号时所在的位置。这包括行号，对于追踪用户在变成“挂起”时到底（真的）在做什么非常有帮助。

`kill -9 (SIGKILL)` 永远不是一个好主意。它也永远没有必要。有一种说法认为 `kill -9` “很好”，因为它“总是有效”。这并不是事实——一个在某些状态下阻塞的进程不会对任何事物做出响应——包括 `kill -9`。当你使用 `kill -9` 时，被杀死的进程无法自我清理（这是 UNIX 的特性——`kill -9` 被定义为不可捕获）。看门狗进程（Watchdog）注意到客户端异常，然后尝试关闭会话并清理客户端。看门狗在很多时候成功清理。有时关键资源正被持有（受锁保护），除非必要的数据在客户端的易性内存中，否则无法清理。在这种情况下，看门狗会关闭数据库（如果你没有运行看门狗进程，断路器将执行此功能）。

对新闻组帖子、法律简报书和知识库条目的数据库提供高级搜索。索引的访问通过单一的 4GL 函数 `CONTAINS` 提供。

## 国际化

国际化涵盖了广泛的话题，从支持亚洲字符集的双字节（Double enabled）Progress 版本，到 Progress 错误消息的语言翻译、区域化的日期和数字格式，以及基于国家字符集的对齐表排序功能。Progress 通过丰富的字符处理功能具备了所有这些特性。

此外， Progress 还提供了一项名为 `Translation Manager`（翻译管理器）的额外可选可选付费产品。它的主要功能是扫描 Progress 4GL 源代码，并确定应用程序中用于各种消息和屏幕标签的字符串。然后可以将此列表交给专业的翻译人员，而无需他们了解任何计算机知识。可以保留多份翻译后的字符串副本，并在 `Translation Manager` 产品中进行轮换。

## 7x24 运行

Progress 从几个版本开始到当前版本，添加了在线备份功能。然而，目前适用于 Linux 的产品中仍缺少几个功能。Linux 8.3 版本不允许在索引重组期间期间保持数据库在线。索引的激活和去激活以及大多数其他数据库架构更改目前可能无法在线进行。

Progress 正在缓慢添加功能以缓解其中一些问题。例如，可以在不重新组织数据表的情况下添加新字段。此外，版本 9 提供了在线表移动和在线索引构建。Linux 平台计划在引入 Progress 9.1 期间进行迁移。

## 不支持 BLOB

二进制大对象（BLOBs）是如电影和音频剪或地理数据等的数据片段。Progress 目前不支持这些内容，并计划在未来提供最少支持。目前支持大小最大 32 k字节的较小对象，它是使用数据库作为存储为文件指针的 BLOB 索引。然而，如果你有大量的重多媒体存储需求，那么 Progress 可能不是一个理想人选。

## 不支持并行查询

少数顶尖数据库系统已经集成了跨多个 CPU 处理单个数据库查询的能力。该技术背后的实现被证明调试极其极其昂贵且耗时。当今的大规模并行 CPU 架构可以产生大量的 CPU 资源。然而，此类机器的成本以及创建该技术的াম使其超普通中型计算机部门的承受范围。此外，也无法保证你可能进行的单个查询是否能从多个 CPU 的处理中获益。在许多情况下，IO 操作成为瓶颈而不是 CPU。在这些情况下，花在并行查询系统上的所有资金都将浪费。

## 不支持分布式锁管理器

为了在多个数据库之间提供完整的事务回滚，在引入 Progress 会话同时连接到多个数据库的能力后不久引入了名为“两阶段提交”（2-Phase Commit）的功能。如果这些数据库位于同一个系统中，没有问题，因为两阶段提交方案涉及主内存中的数据。如果这些数据库位于不同的机器上，该方法将不再有效。要实现此类功能，需要一个分布式锁管理器。该软件的理论和实践非常复杂且构建昂贵。继续运行也更加昂贵。PSC 的立场是，这种锁管理器的费用对于习惯高投资回报率（ROI）数据库的客户群来说太高了。因此，Tedo 和 TopEnd 等系统产品不是 Progress 的候选对象。

## 总结

Progress 数据库多年来证明了自己是一个极其可靠的产品，同时易于使用和管理。安装过程无非是从介质中复制并设置几个变量。尽管它具有诸如前滚恢复（Roll Forward Recovery）和两阶段提交（2-Phase commit）等许多功能，但这些并不是强制性的，管理也十分简单。有许多启动选项可以自定义 Progress 的操作、提高性能并平衡资源利用。尽管 Progress 是成本敏感型和中型企业的极佳选择，但某些大型公司可能需要 Linux 上的 V8.3 版本未提供的 24x7 运行功能。除了这些高端功能外，Progress 以得低的成本提供了知名数据库所具备的所有真正重要的功能。
