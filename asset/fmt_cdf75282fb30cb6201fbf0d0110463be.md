### 2.2 防御性编程

编写在“正常”情况下运行良好的程序是困难的；在失败情况下表现良好的程序更难。本节演示了一些用于发现 Bug 以及检测和从运行中问题的编程技术。

本书后介绍的代码示例故意跳过了错误检查和恢复代码，以免掩盖基本功能。然而，第11 章最后的示例“示例/Linux 应用程序”回到了如何使用这些技术。

#### 2.2.1 使用 assert

编程时应记住的一个良好目标是：Bug 或意外错误应该让程序尽可能早、戏剧地失败。这将有助于你在开发和测试阶段早期发现 Bug。不显现的失败往往会被忽略，直到程序交到用户手中。

检查意外情况的最简单的方法之一是 C `assert` 宏。该宏的参数是一个布尔表达式。如果表达式求值为假，程序将终止，并打印包含源文件、行号和表达式文本的错误信息。`assert` 宏非常有用，用于测试函数参数的有效性、测试函数调用（以及 C++ 中的方法调用）的前后条件，以及测试意外的返回值。

每个 `assert` 的使用不仅是对条件的运行时检查，也是程序操作的文档。如果你的程序包含一个 `assert(condition)`，告诉阅读源码的人在程序这一点 `condition` 应该是真的，如果 `condition` 为假，那么可能是程序存在 Bug。

对于性能敏感的代码，运行时检查（作为 `assert` 使用）可能会产生巨大的性能损失。在这种情况下，你可以在编译代码时开启 `NDEBUG` 标志。设置 `NDEBUG` 后，`assert` 宏的所有出现处将被预处理掉。建议仅在性能需要时这样做，并且仅针对性能敏感的源文件。

由于 `assert` 宏可能会被预处理，请确保你在 `assert` 中使用的任何表达式都不会产生副作用。具体来说，你不应该在 `assert` 表达式内部调用函数、分配变量或使用修改运算符（如 `++`）。

#### 使用 tmpfile

如果你在使用 C 库 I/O 函数并且不需要将临时文件传递给另一个程序，可以使用 `tmpfile` 函数。它可以创建并打开一个临时文件，并返回一个指针。当指针关闭或程序终止时，临时文件会被自动删除。

GNU/Linux 还提供了其他生成临时文件和临时文件名的函数，包括 `mktemp`、`tmpnam` 和 `tempnam`。不要使用这些函数，它们存在前面提到的可靠性和安全性问题。

### 2.2 防御性编码

假设例如，你在循环中反复调用一个函数 `do_something`。`do_something` 函数在成功时返回 0，失败时返回非零值，但你并不预期它在程序中会失败。你可能会想写成：

```
for (i = 0; i < 100; ++i)
assert (do_something () == 0);
```

然而，你可能会发现这种运行时检查会带来过大的性能开销，并决定以后在编译时定义 `NDEBUG`。这将移除 `assert` 调用，因此该表达式会被求值，而 `do_something` 永远不会被调用。你应该编写下面的代码：

```
for (i = 0; i < 100; ++i)
int status = do_something ();
assert (status == 0);
```

另一个需要记住的点是，你不应该使用 `assert` 来测试无效的用户输入。用户不喜欢应用程序因无效输入而带有“晦涩错误信息”的崩溃。你仍然应该检查无效输入，并根据输入产生合理的错误信息。仅将 `assert` 用于内部运行时检查。

使用 `assert` 的一些良好场景是：

- 检查空指针，例如作为无效的函数参数。`assert (pointer != NULL);` 产生的错误信息 `Assertion 'pointer != ((void *)0)' failed.` 比你的程序解引用空指针时产生的错误信息 `Segmentation fault (core dumped)` 更具信息量。

- 检查参数值的限制条件。例如，如果一个函数应该只在参数 `foo` 为正值时才被调用，请在函数体开头使用此代码：

`assert (foo > 0);`

这可以帮助你检测对函数的误用，而且也让阅读函数源码的人非常清楚地知道对参数值存在限制。

不要吝啬；在整个程序中要大量地使用 `assert`。

#### 2.2.2 系统故障

我们大多数人最初接受的教育是编写编写沿着良好定义路径执行完成的程序。我们将程序划分为任务和子任务，每个函数通过调用其他函数来执行相应的子任务以完成一个任务。在输入适当的情况下，我们期望函数能产生正确的输出和副作用。

计算机硬件和软件的现实情况干扰了这一理想化的梦想。计算机资源有限；硬件会故障；许多程序同时执行；用户和程序员会犯错。这些现实情况往往出现在应用和操作系统的边界上。因此，在使用系统调用访问系统资源、执行 I/O 或其他目的时，不仅要理解调用成功时发生了什么，还要理解调用如何以及何时可能失败，这是至关重要的。

系统调用可能以多种方式失败：

- 系统可能耗尽资源（或程序可能超过系统对单个程序强制执行的限制）。例如，程序可能尝试分配过多内存、向磁盘写入过多内容，或同时打开过多文件。

- 当程序尝试执行其无权限执行的操作时，Linux 可能会对系统调用进行拦截。例如，程序可能尝试写入标记为只读的文件、访问另一个进程的内存，或杀死用户的程序。

- 系统调用的参数可能是无效的，可能是因为用户提供的输入，也可能是因为程序 Bug。例如，程序可能会向系统调用传递无效的内存地址或无效的文件描述符。或者，程序可能会尝试将目录作为普通文件打开，或将普通文件的文件名传递给目录。

- 系统调用可能因为程序外部的原因而失败。这在系统调用访问硬件设备时经常发生。设备可能是故障的，或者可能不支持特定操作，又或许驱动器未插入磁盘。

- 系统调用有时会被外部事件中断，例如信号的投递。这可能并不意味着直接失败，但如果需要，重启系统调用是调用程序的责任。

在一个大量使用系统调用的、编写良好的程序中，花费用于检测和处理错误及其他情况的代码往往比用于程序主工作的代码要多。

#### 2.2.3 系统调用的错误代码

大多数系统调用在操作成功时返回 0，在失败时返回非零值（尽管许多调用有不同的返回约定；例如，`malloc` 返回空指针来表示失败）。虽然这些信息可能足够判断程序是否应该照常继续执行，但可能无法提供足够的信息来从错误中进行合理的恢复。

大多数系统调用使用一个特殊变量 `errno` 在失败时存储额外信息。当调用失败时，系统会将 `errno` 设置为一个指示何处出现问题的值。在失败调用后，立即将该值复制到另一个变量中。当你下一次进行系统调用时，`errno` 的值会被覆盖。

错误值是整数；值由预处理器宏给出——例如 `EACCES` 和 `EINVAL`。始终使用这些宏来引用 `errno` 而不是整数值。如果你使用了 `errno`，请包含 `<errno.h>`。

GNU/Linux 提供了一个方便的函数 `strerror`，它返回错误代码的字符字符串，适用于错误消息。如果你使用了 `strerror`，请包含 `<string.h>`。

GNU/Linux 还提供了 `perror`，它直接将错误描述打印到 `stderr`。在错误描述之前向 `perror` 传递一个字符前缀，前缀通常包含失败函数的名称。如果你使用了 `perror`，请包含 `<stdio.h>`。

这段代码片段尝试打开一个文件；如果操作失败，它将打印错误消息并退出。

```
fd = open("input.txt", O_RDONLY);
if (fd == -1) {
    /* open 调用失败。 */
    fprintf(stderr, "error opening file: %s\n", errno);
}
```

取决于你的程序和系统调用的性质，失败时的适当可能是打印错误信息、取消程序、重试调用甚至忽略错误。尽管如此，包含处理所有可能失败模式的逻辑是非常重要的。注意，当我们检测到程序 Bug 时，我们使用 `exit` 或 `assert`，这会产生转储文件。这对于事后调试很有用。对于不可达的错误（如内存耗尽），我们使用 `exit` 并返回非零退出值。

```
retval = chown(path, user_id, -1);
if (retval != 0) {
    /* 保存错误码，因为它会被下一次系统调用覆盖 */
    int error_code = errno;
    /* 操作未成功；出错时返回 -1。 */
    assert(retval == -1);
    /* 检查 errno 的值并采取适当行动。 */
    switch (error_code) {
        case EPERM:    /* 权限拒绝。 */
                      /* 路径在只读文件系统中。 */
        case EROFS:    /* 路径过长。 */
        case ENAMETOOLONG: /* 路径不存在。 */
        case ENOENT:   /* 路径的组件不是目录。 */
        case EACCES:   /* 路径的组件不可访问。 */
            /* 文件出现问题。打印错误消息。 */
            fprintf(stderr, "error changing ownership of %s: %s\n",
                   path, error_code);
            /* 不要结束程序；也许给用户选择另一个文件的机会…… */
            break;
        case EFAULT: /* 路径包含无效的内存地址。这可能是一个 Bug。 */
            abort (0);
        case ENOMEM: /* 耗尽内核内存。 **/
            fprintf(stderr, "%s\n", strerror(error_code));
            exit (1);
        default:
            /* 其他未预料的错误码。我们已经尝试处理了所有可能的错误码；如果漏掉了，那就是一个 Bug！ */
            abort (0);
    }
}
```

### 2.2 防御性编码

你完全可以直接使用这段代码，如果调用成功，它的行为是完全相同的：

```c
rval = chown (path, user_id, -1);
assert (rval == 0);
```

但如果调用失败，这种替代方案并没有报告、处理或从错误中恢复的任何努力。

使用第一种形式、第二种形式还是两者之间的某种形式，取决于你的程序对错误检测和恢复的需求。

#### 2.2.4 错误与资源分配

通常，当系统调用失败时，取消当前操作是合适的，但不必终止程序，因为可能从错误中恢复。实现此点的一种方法是从当前函数返回，并向调用者传递一个表示错误的的返回代码。

如果你决定从函数的中间返回，那么确保在函数之前成功分配的任何资源都先被释放是至关重要的。这些资源可能包括内存、文件描述符、指针、临时文件、同步对象等。否则，如果你的程序继续运行，在发生错误之前分配的资源将会泄漏。

例如，考虑一个从文件读取到缓冲区的函数。该函数可能会遵循以下步骤：

1. 分配缓冲区。

2. 打开文件。

3. 从文件读取到缓冲区。

4. 关闭文件。

5. 返回缓冲区。

如果文件不存在，步骤 2 将失败。适当的行动方案可能是从函数返回 NULL。然而，如果缓冲区已经在步骤 1 中被分配，则存在内存泄漏的风险。你必须记住，在任何你没有返回的控制流中的某处释放缓冲区。如果步骤 3 失败，你不仅必须在返回之前释放缓冲区，还必须关闭文件。

列表 2.6 显示了你可能如何编写此函数的示例。

> 列表 2.6 (`readable.c`) 在异常情况下释放资源

```c
#include <fcntl.h>
#include <stdlib.h>
#include <sys/stat.h>
#include <unistd.h>

char* read_from_file (const char* filename, size_t length)
{
  char* buffer;
  int fd;
  ssize_t bytes_read;

  /* 分配缓冲区。 */
  buffer = (char*) malloc(length);
  if (buffer == NULL)
    return NULL;
  /* 打开文件。 */
  fd = open (filename, O_RDONLY);
  if (fd == -1) {
    /* open失败。在返回前释放缓冲区。 */
    free(buffer);
    return NULL;
  }
  /* 读取数据。 */
  bytes_read = read (fd, buffer, length);
  if (bytes_read != length) {
    /* read失败。在返回前释放缓冲区并关闭 fd。 */
    free(buffer);
    close(fd);
    return NULL;
  }
  /* 一切正常。关闭文件并返回缓冲区。 */
  close(fd);
  return buffer;
}
```

Linux 在程序终止时会清理分配的内存、打开的文件以及大多数其他资源，因此在调用 `exit` 之前没有必要手动释放缓冲区和关闭文件。你可能需要手动释放其他共享资源，例如临时文件和共享内存，这些资源的生命周期可能比程序长。

### 2.3 编写与使用库

几乎所有程序都链接到一个或多个库上。任何使用 C 函数（如 `printf` 或 `malloc`）的程序都会将 C 运行时库链接。如果你的程序有图形用户界面 (GUI)，它将链接到窗口库上。如果你的程序使用数据库，数据库提供程序将给你提供你可以方便地访问数据库的库。

在这些种情况下，你必须决定是静态链接还是动态链接库。如果你选择静态链接，你的程序会更大且更难升级，但可能更容易部署。如果你动态链接，你的程序会更小、更容易升级，但更难部署。本节解释了如何进行静态和动态链接，更详细地检查了权衡，并为决定哪种链接方式对你更优提供了一些“经验法则”。

#### 2.3.1 归档 (Archives)

存档（或静态库）仅仅是存储为单个文件的对象文件集合。（存档大致等同于 Windows 的 `.lib` 文件）。当你向链接器提供一个存档时，链接器会搜索它需要的对象文件，提取它们，并将它们链接到你的程序中，就像你直接提供了这些对象文件一样。

你可以使用 `ar` 命令创建存档。存档文件传统上使用 `.a` 扩展，而不是对象文件使用的 `.o` 扩展。以下是你如何将 `test1.o` 和 `test2.o` 组合成单个 `libtest.a`：

```bash
% ar c test1.o test2.o
```

`cr` 标志告诉 `ar` 创建存档。现在你可以使用 `gcc` 或 `g++` 的 `-l` 选项与此存档链接，正如第 1 章“入门”中 1.2.2 节“链接对象文件”所述。

当链接器在命令行上遇到存档时，它会在存档中搜索从已处理的对象文件中引用的所有符号（函数或变量）的定义。因为链接器在遇到存档时进行搜索，所以通常将存档放在命令行的末尾是有意义的。例如，假设 `test.c` 包含2.7 中的代码。

> 列表 2.7 (`test.c`) 库的内容

```c
int f ()
{
    return 3;
}
```

> 列表 2.8 (`app.c`) 使用库的程序

```c
int main ()
{
    f ();
    return 0;
}
```

现在假设将 `test.o` 与其他对象文件组合以产生 `app`。以下命令行将无效：

```bash
% gcc -o app -L. -libtest
app.o: In function 'main':
app.o:(0x4): undefined reference to 'f'
collect(2): ld returned 1 status
```

错误消息表明，尽管 `libtest.a` 包含 `f` 的定义，链接器也没有找到它。这是因为没有搜索存档。相反，如果你使用这一行，就不会报错：

```bash
% gcc -o app app.o -L. -libtest
```

#### 2.3.2 共享库

共享库（共享对象或动态链接库）与存档相似，都是对象的组合。然而，有许多重要的区别。最根本的区别是，当共享库链接到程序时，最终的可执行文件并不包含共享库中的代码。相反，可执行文件仅包含对共享库的引用。如果系统上的多个程序链接到同一个共享库，它们都会引用该库，但都不会实际包含它。因此，该库被所有链接它的程序“共享”。

第二个区别是，共享库不仅仅是对象文件的集合（链接器从中选择部分来满足未定义引用）。相反，组成共享库的对象文件被组合成单个对象文件，使得链接共享库的程序始终包含库中的所有代码，而不仅仅是需要的部分。

要创建共享库，你必须使用编译选项 `-fPIC` 编译组成库的对象，如下：
