## 11.9. 寻找时间差异

现在我们已经缩小了哪些函数负责创建菜单的范围，我们想要找出哪些部分占据了所有时间，哪些部分相对轻量。一种在不使用任何性能工具的情况下实现这一点的绝方法是直接禁用某些代码段并观察性能的变化。尽管这会导致 `nautilus` 运行异常，但它至少能指示哪些函数消耗了所有时间。

我们首先必须建立一个基准，因为我们正在测试的二进制文件编译时使用的标记与 Red Hat 提供的不同。我们像以前一样对脚本进行计时。在这种情况下，在我们自己编译的版本上，运行 100 次迭代需要 30.5 秒。接下来，我们注释掉 `eel_pop_up_context_menu` 调用。这显示了 `nautilus` 检测到鼠标点击并决定需要创建上下文菜单花费了多少时间。即使我们完全优化了这些函数中的所有命令，我们的运行速度也不会比这快。在这种情况下，运行所有 100 次迭代需要 7.6 秒。接下来，我们注释掉被认为耗时最长的 `bonobo_window_add_popup`。如果我们注释掉 `bonobo_window_add_popup`，完成 100 次迭代需要 21.9 秒。这意味着如果我们优化掉 `bonobo_window_add_popup`，可以从总运行中节省约 8 秒，改进了近 25%。

## 11.10. 尝试可能的解决方案

因此，正如我们所看到的，`bonobo_window_add_popup` 是一个昂贵的函数，每次我们创建弹出菜单时都调用它。如果我们反复使用相同的参数调用它，可能缓存它初始调用返回的值，并使用它代替调用那个昂贵的函数。列表 11.19 显示了实现此目的重写函数示例。

### 列表 11.19。

```c
void
fm_directory_view_pop_up_background_context_menu
(FMDirectoryView *view,
GdkButton *event)
{
 /* Primitive Cache */
  static FMDirectoryView *old_view = NULL;
  static GtkMenu *old_menu = NULL;

  g_assert (FM_IS_DIRECTORY_VIEW (view));

  /* Make the context menu items not flash as they update to
  proper disabled;
   * states. by forcing menus to update now.
   */
  if ((old_view != view) ||
      view->menu_states_untrustworthy)
  {
    update_menu_if_pending(view);
    old_view = view;
    old_menu = create_popup_menu(view,
      FM_DIRECTORY_VIEW_POPUP_PATH_BACKGROUND);
  }

  eel_pop_up_context_menu (old_menu,
    EEL_DEFAULT_POPUP_MENU_DISPLACEMENT,
    EEL_DEFAULT_POPUP_MENU_DISPLACEMENT,
    event);
}
```

在这种情况下，我们记住了上次生成的菜单。如果我们处于同一个视图中，并且认为该视图的菜单没有发生变化，我们就直接使用用过的菜单，而不是创建一个新的。这并不是一种复杂的技巧，如果用户没有在目录 1 中打开弹出菜单，而在目录 2 中打开，它就会失效；如果目录 1 中打开了弹出菜单，`nautilus` 会创建一个。在打开菜单时，第一个检查是查看缓存中是否已经有了菜单。如果缓存的菜单可以查看，则直接使用；否则，可以创建一个。这对于特殊目录特别有用，例如桌面、计算机或主目录，用户可能会多次打开弹出菜单。在应用此建议的解决方案并配合 100ms 的超时时间后，时间已下降到 24.0 秒。这是 20% 的性能提升，接近于完全不创建菜单时能获得的提升（21 秒）。在各种目录中创建弹出菜单的方法是有效的。

## 11.11. 章节总结

在本章中，我们确定了应用程序的特定组件为何会有高延迟（`nautilus` 中的弹出菜单）。我们弄出了如何自动化创建弹出菜单（`xautomer`），并扩展了 `nautilus` 创建弹出菜单花费的时间（100 次迭代）。我们使用 `profile` 来找出 `nautilus` 在哪个函数中耗费了所有时间。然后，我们使用 `trace` 和 `gdb` 来确定哪些共享库调用负责了所有的调用。在我们确定了哪些库调用成本很高之后，我们尝试减少或限制它们被调用的次数。在这种情况下，我们在分配新菜单时存储了它的指针，并在稍后使用它以避免不重新加载。我们创建了一个建议的补丁，然后针对它运行了我们的测试，以查看是否有所提高，且功能似乎没有受到影响。下一步是将该补丁提交给 `nautilus` 开发者。本章关注于单个应用程序，而下一章将介绍一个集中在系统级问题的性能搜猎。这种类型的搜猎可能涉及系统的许多不同领域，包括硬件（磁盘、网络和内存）和软件（应用程序、共享库和内核）。
