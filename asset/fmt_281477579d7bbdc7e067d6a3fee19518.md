# 修改并挂载文件系统

现在你准备好在 `fs` 文件中创建文件系统了。我们将使用 `e2fs` 文件系统，因为它是 Linux 中测试最充分的文件系统：

```
mkfs.ext2 .fs
```

提示：你的根文件系统有多种文件系统供选择。选择通常取决于 `ext2` 或 `minix`。我通常使用 `ext2` 文件系统，尽管 `minix` 文件系统要小得多。

现在挂载文件系统。Linux `mount` 命令非常擅长从文件系统本身判断类型。如果出现问题，你可能需要使用 `-t` 选项告诉它正在处理的文件系统类型。

```
mount -o loop fs /mnt
```

# 创建设备

你准备好为你的嵌入式环境创建所需的特殊文件了。你必须使用 `cp` 命令的 `-a` 选项以便复制目录条目而不是合并文件。

```
mkdir -p /mnt/dev
(cd /dev && cp -a console full kmm loop0 loop1 mem null port ram0 ram1 tty0 tty1 tty2 tty9 tty2 tty3 urandom zero /mnt/dev)
(cd /mnt/dev && ln -s /proc/core core)
(cd /mnt/dev && ln -s ram1 ram)
```

现在，为控制台创建 `terminfo`。该文件包含了控制台转义序列的定义，用于清除屏幕和绘制线条等操作：

```
cp -p /usr/share/terminfo/1/linux /mnt
```

# 拷贝 Minicom 可执行文件

将 Minicom 可执行文件拷贝到 `initrd` 文件系统并命名为 `/linuxrc`：

```
cp minicom-1.83.0/src/minicom /mnt/linuxrc
```

你将其命名为 `/linuxrc` 是因为这是 Linux 内核在完成引导后将运行的脚本（在这种情况下是程序）的名字。你可能会预期命名为 `init`。但由于你正在使用 Linux 内核的 `initrd` 功能将应用程序加载到内存中，你必须将其命名为 `linuxrc`，因为这是 Linux 在启动 `initrd` 时时预期的名称。

# 设置根目录

通过使用 `/mnt` 作为根目录运行 `linuxrc` 程序来测试设置。这样，你就知道 `/linuxrc` 运行的环境与它在设备上运行的环境相同：

```
chroot /mnt /linuxrc
```

`chroot` 运行第三个参数指定的命令，并使用第二个参数指定的目录。该命令无法访问指定根目录以外的计算机上的任何文件。你运行 `/linuxrc` 而不是 `/mnt/linuxrc` 是因为 `chroot` 发生在执行之前，而一旦 `chroot` 发生，`linuxrc` 文件就在新目录结构的根部了。

如果一切顺利，Minicom 程序应该会启动。如果你很有冒险精神，可以连接一个调制调器并让 Minicom 充分测试。退出 Minicom 按 `Ctrl+A` 然后按 `X`。

## 使用 chroot 在你的构建机上进行测试

当你的构建机运行的处理器与目标机器相同时，你可以使用一些额外的调试技巧。其中最方便的之一是 `chroot` 技巧。

在构建过程中，你会创建一个机器启动所需的根文件系统镜像。一旦创建了镜像，可以使用回环设备（loopback device）将其挂载。然后你可以使用 `chroot` 命令将子 shell 的根目录更改为挂载的文件系统。你在子 shell 中输入的任何命令都将限于使用你创建的文件镜像内的文件。这对于检查目标设备非常方便。在将软件提交到目标设备之前，确保你的软件通常运行良好。例如，如果你缺少某个动态库，并且运行了需要该库的命令，该命令将会报错。

然而，某些东西将无法工作。例如，任何依赖于 `/proc` 文件系统的命令都会失败。这是因为 `chroot` 环境无法使用 `/proc` 文件系统。

## 测试与调试

嵌入嵌入式系统的调试是一项令人生畏的任务。与相比之下，在个人计算机上开发软件要容易得多——你的软件下方有一个操作系统，可能不需要捕获意外事件，有一个可以显示调试信息的屏幕，以及可以给软件提供输入的键盘和鼠标。你的嵌入式设备可能不具备这些任何东西；你可能只有一个软件可以使其闪烁的小 LED 灯——或者你可能连这一个都没有！

从一开始起，你就需要在设计嵌入式应用程序时考虑到诊断功能。如果你不这样做，很有可能你最终将面对一个小盒子，而完全不知道发生了什么。你会怀疑它是否会再次发生——而它确实会。这让开发人员陷入噩梦。

本章介绍了一些显而易见（以及一些不那么明显的）技巧和技术，以加速开发并提高你的嵌入式 Linux 设备的“可调试性”。

## 尽可能在你的主机计算机上进行测试

目标计算机是一个有趣的玩具，一旦它开始工作，它似乎就是进行所有测试的自然场所。毕竟，那是软件最终必须运行的地方——为什么不测试它呢？

这种理由是无效的。你应该尽可能在你的主机计算机系统上测试你的大部分软件。如果你的主机运行的是不同的处理器，请修改你的 `Makefile`，以便软件可以为你的主机或目标进行构建。如果你的软件依赖于只有在目标上才能找到硬件，你仍然可以通过 `#define` 掉实际上需要目标硬件的代码部分，在主机上测试大部分代码。
