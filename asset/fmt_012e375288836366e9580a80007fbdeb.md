
`zip` 文件目录结构中的特定位置也可以使用。此外，`zip` 文件可以与常规路径组件混合使用。这是一个示例：
`sys.path.append("/tmp/modules.zip/lib/python")`

此外，你还可以将 `.egg` 文件添加到搜索路径。`.egg` 文件是由 `setuptools` 库创建的。这是安装第三方 Python 库和扩展时经常遇到的一种格式。一个 `.egg` 实际上是一个包含了一些额外元数据（例如版本号、依赖项等）的 `.zip` 文件。因此，你可以使用处理 `.zip` 文件的标准工具从 `.egg` 文件中检查并提取数据。

尽管支持 `zip` 文件导入，但仍有一些需要注意的限制。首先，只能从存档中加载 `.py`、`.pyc`、`.pyc` 和 `.pyo` 文件。用 C 编写的共享库和扩展无法直接从存档中加载，尽管 `setuptools` 等包提供了了一种通方法（通常是通过将 C 提取到临时目录并从那里加载模块）。此外，当从存档中加载 `.py` 文件时（下文描述），Python 不会创建 `.pyc` 和 `.pyo` 文件。因此，提前创建这些文件并将其放入存档中是很重要的，以避免加载模块时性能低下的。

## 模块加载与编译

到为止，本章将模块描述为包含 Python 代码的文件。然而，通过 `import` 加载的模块实际上分为四大类：

- 用 Python 编写的代码（`.py` 文件）
- 已编译为共享库或 DLL 的 C 或 C++ 扩展
- 包含一组模块的包
- 用 C 编写并链接到 Python 解释器的内置模块

在查找模块（例如 `foo`）时，解释器会在 `sys.path` 的目录中搜索以下文件（按搜索顺序列出）：

1. 定义包的目录 `foo`
2. `foo.pyd`、`foo.so`、`fmodule.so` 或 `fmodule.dll`（编译后的扩展）
3. `foo.pyc`（仅当使用了 `-o` 或 `--o` 选项时）
4. `foo.py`
5. `foo.py`（在 Windows 上，Python 也会检查 `.py` 文件）。

稍将简述包：编译扩展将在第26章“扩展和嵌入 Python”中描述。当模块首次被导入时，它会被编译成字节码并写回磁盘作为 `.py` 文件。在随后的导入中，解释器会加载此预编译的字节码，除非 `.py` 文件的修改日期更新（在这种情况下会重新生成 `.py` 文件）。`.py` 文件与解释器的 `-o` 选项配合使用。这些文件包含去除了行号、断言和其他调试信息的字节码。因此，它们体积略小，并允许解释器运行得稍快。如果指定的是 `-O` 而不是 `-o`，你将打包代码且文档字符串也会被移除。这种文档字符串的移除仅在创建 `.py` 文件时（即加载它们时）发生。如果 `sys.path` 中的任何目录中不存在这些文件，解释器将检查名称是否对应于内置模块名。如果没有匹配项，将抛出 `ImportError` 异常。

文件自动编译为 `.pyc` 和 `.py` 文件仅在配合 `import` 语句时发生。程序不会产生此类文件。此外，如果包含 `.py` 文件的目录不允许写入（例如由于权限不足或它是 `zip` 存档的一部分），则会创建这些文件。解释器的 `-b` 选项会禁用这些文件的生成。

只要 `.pyc` 和 `.py` 文件可用，就不一定存在对应的 `.py` 文件。如果，如果你正在打包代码并希望包含源码，可以将一组 `.py` 文件合并在一起。但是，请注意，Python 对检查和反汇编有广泛支持。如果提供了源代码，精通的用户仍然能够导入并发现有关你程序的细节。此外，请注意 `.py` 文件是特定于版本的。因此，为某个版本的 Python 生成的 `.py` 文件可能在另一个版本无法工作。当导入搜索文件时，它以大小敏感的方式进行——除非底层文件系统不区分大小写，例如 Windows 和 OS X（这些系统是不区分大小写的）。因此，作为通用规则，导入只会导入 `foo.py` 而不是 `FO.PY`。

## 模块重载与卸载

Python 并没有为卸载已加载模块提供真正的支持。虽然你可以从 `sys.modules` 中移除模块，但这并不会从内存中卸载模块。因为导入该模块的其他组件可能仍然持有该模块的引用。此外，如果模块中定义了类的实例，这些实例包含指向类对象的引用，而类对象又持有指向它所在模块的引用。

模块引用存在于许多地方，这使得在修改实现后重载模块通常是不可行的。例如，如果你从 `sys.modules` 中移除模块并重新导入它，这不会追溯地更改所有指向该模块的引用。相反，你将拥有最新语句创建的新模块以及来自代码其他部分创建的旧模块引用。这通常不是你想要的，除非你仔细控制任何生产代码的整个执行环境。

旧版本的 Python 提供了一个 `reload()` 函数来重载模块。然而，使用该功能从未真正安全（出于上述所有原因），并且并不被积极建议作为可能的调试辅助工具。Python 3 完全删除了此功能。因此，最好不要依赖它。

最后，应该注意，C/C++ 扩展无法以任何方式安全地卸载或重载。没有提供此类支持，而且底层操作系统可能禁止这样做。因此，你唯一的选择是重启 Python 解释器进程。

## 包

包允许将一组模块分组在一个公共包名下。这种技术有助于解决不同应用程序之间模块的命名冲突。包通过创建一个与包同名的目录并在其中创建 `__init__.py` 文件来定义。然后，你可以根据需要在该目录下添加源文件、编译扩展和子包。例如，一个包的组织结构可能如下：

- Graphics/
  - `__init__.py`
- Primitive/
  - `__init__.py`
  - `lines.py`
  - `fill.py`
  - `text.py`
- Graph2/
  - `__init__.py`
  - `plot2d.py`
- Graph3/
  - `__init__.py`
  - `plot3d.py`
- Formats/
  - `__init__.py`
  - `gif.py`

## 第 8 章 模块、包与发行

`png.py`
`tiff.py`
`jpeg.py`

`import` 语句首先被导入，文件中的代码以以下方式从包加载模块：

- `import Graphics.Primitive.fill`
这会加载子模块 `Graphics.Primitive.fill`。该模块的内容必须显式命名，例如 `Graphics.Primitive.floodfill(img,x,y,color)`。
- `from Graphics.Primitive import fill`
这加载了子模块 `fill` 但允许在没有包前缀的情况下使用；例如 `fill.floodfill(img,x,y,color)`。
- `from Graphics.Primitive import floodfill`
这加载了子模块 `fill` 但可以直接访问泛洪函数；例如 `floodfill(img,x,y,color)`。

每当包的任何部分被导入时，`__init__.py` 中的代码就会被执行。它可以是空的，也可以包含执行包特定初始化的代码。在导入过程中遇到的所有 `__init__.py` 都会被执行。因此，`import Graphics.Primitive.fill` 语句将较早显示，除非你先执行了 Graphics 目录下的 `__init__.py`，然后是该目录下的 `__init__.py` 文件。

包的一个问题是对该语句的处理：
`from Graphics.Primitive *`

使用该语句的程序员通常用它将与包相关的所有模块导入到当前命名空间。然而，由于文件名随系统而异（特别是关于大小写敏感性），Python 无法准确确定哪些模块。结果是，它导入了目录下 `__init__.py` 文件中定义的所有名称。这可以通过定义一个列表 `__all__` 来修改，该列表包含所有与包相关的联模块名称。此列表应该定义在包的 `__init__.py` 文件中，如下：

```python
# Graphics/Primitive/__init__.py

__all__ = ["lines", "text", "fill"]
```

现在，当你使用语句 `from .Graphics.Primitive *` 时，所有列出的模块都会按预期加载。

包的另一个微妙问题涉及同包包内的子模块。例如，为了导入其他子模块，假设 `Graphics.Primitive.fill` 模块想要导入 `Graphics.Primitive.lines` 模块。要实现这一点，你可以直接使用全名（例如 `from Graphics.Primitives import lines`），或者使用如下的包相对导入：

```python
# fill.py

from . import lines
```
