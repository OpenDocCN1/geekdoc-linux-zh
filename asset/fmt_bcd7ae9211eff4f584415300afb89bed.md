
根据具体情况，信号分为同步信号和异步信号。同步信号发生在活动进程流的执行过程中（通常通过错误产生——访问错误的内存区域、错误的浮点运算、执行处理器设计中不存在的指令）。这些信号由操作系统内核生成，并立即发送给导致错误的进程线程。

异步信号可以在进程执行的任何时刻被接收：

- 程序员可以使用系统调用向另一个进程发送异步信号，在 POSIX 系统上，该调用称为 `kill()`，其参数是信号编号和进程标识符

- 信号也可能由某些外部事件（按键、终止等）引起

在处理此类信号期间，系统必须中断当前代码的执行，执行处理器代码，并返回到接收信号时执行的那条指令。

## 信号布局

在接收到信号时，进程可以通过三种方式之一进行响应（响应方式称为信号处置）：

- 调用信号处理程序

- 忽略该信号，此时信号“消失”且不采取任何操作

- 使用默认操作（这是每个信号的默认设置，通常会导致进程终止）

进程可以为每个信号设置单独的处置方式。

## 信号阻塞

进程不仅可以设置信号的处置方式，还可以确定其在那一刻是否愿意接收某种类型的信号。如果进程尚未准备好，它可以阻塞这些信号。如果要把一个被阻塞的信号发送给进程，系统会将其排队，直到进程解除阻塞。进程通过更改 `进程信号掩码`（一个存储关于哪些信号可以立即传递给进程的特殊数据结构，通常存储在其控制块中）来阻塞和解除阻塞信号。后代进程继承祖先的信号掩码。

## 信号示例

考虑 POSIX 定义且 Linux 支持的信号（名称旁边括号内给出信号编号）。例如，同步信号包括在访问受保护的内存区域时由系统生成的 `SIGSEGV` (11) 信号。

异步信号包括：

- `SIGHUP` (1) - 挂断通信线路（例如，用户注销系统）

- `SIGINT` 和 `SIGQUIT` (2, 3) - 来自键盘的程序中断信号（分别由用户按下 Ctrl+C 和 Ctrl+\ 生成）

- `SIGKILL` (9) - 立即终止程序（此信号无法被捕获、阻塞或忽略）

- `SIGUSR1`、`SIGUSR2` (10, 12) - 可由应用程序使用的用户信号

- `SIGTERM` (15) - 请求程序关闭（与 `SIGKILL` 不同，此信号可能被忽略）

除了 `SIGSEGV` 之外，所有这些信号的默认操作都是终止程序（对于 `SIGSEGV` 还会生成额外的内存转储（core dump）——一个存储进程地址空间映像以供后续分析的文件）。

## 设置信号处置

使用 `sigaction()` 系统调用来设置信号处置。

```c
#include <signal.h>

int sigaction(int signum,              // 信号编号
              const struct sigaction *act, // 新处置
              struct sigaction *old_act); // 返回之前的处置
```

使用具有以下字段的 `sigaction` 结构体来描述处置：

- `sa_handler` - 指向信号处理函数的指针

- `sa_mask` - 指定在处理程序内部将阻塞哪些信号的信号掩码

- `sa_flags` - 附加标志

将 `sa_mask` 和 `sa_flags` 零化的限制（不阻塞任何信号）：

```c
struct sigaction action = {0};
```

`sa_handler` 字段应设置为指向先前声明的函数的指针，该函数看起来像这样：

```c
void user_handler(int signum)
{
    // 信号处理
}
```

此功能充当一个信号处理器。`signum` 参数决定了发送给处理程序的信号（同一个处理程序可以通过多次 `sigaction()` 调用注册到多个信号）。注册完成后，每当接收到相应的信号时，该处理程序始终会被调用：

```c
#include <signal.h>
void sigint_handler(int signum)
{
    // SIGINT 处理
}
// ...
struct sigaction action = {0};
action.sa_handler = sigint_handler;
sigaction(SIGINT, &action, 0);
```

如果需要组织信号的等待，最简单的方法是打开系统调用 `pause()`。在这种情况下，进程进入待机模式，当收到任何信号时，它将退出该模式：

```c
// 通过 sigaction() 让处理程序帮忙
pause(); // 等待信号
```

## 信号生成

让我们看看如何向进程发送信号。这使用了 `kill()` 系统调用。

```c
#include <signal.h>
int kill(pid_t pid, // 进程 ID
     int signum); // 信号编号
```

例如，向命令行中指定的进程 `pid` 发送 `SIGHUP` 信号：

```c
kill(atoi(argv[1]), SIGHUP);
```

## 进程异步执行的组织

考虑一下如何利用信号处理来组织进程的异步执行。如您所知，调用 `waitpid()` 会导致子进程同步执行。启动子进程的时间是异步的。因此，对于该子进程，在父进程中不调用 `waitpid()` 似乎很自然。但当事件结束后，它将变成僵尸进程。

为了避免这种情况，您必须利用这样的事实：在子进程结束时，父进程会接收到一个特殊的 `SIGCHLD` 信号。在此信号处理程序中调用 `waitpid()` 将从进程表中移除子进程信息，从而在系统中不留下任何僵尸进程。

```c
void clear_zombie(int signum)
{
    waitpid(-1, NULL, 0);
}
struct sigaction action = {0};
action.sa_handler = clear_zombie;
sigaction(SIGCHLD, &action, 0);
if ((pid = fork()) == -1)
    _exit();
if (pid == 0)
{
    // 子进程异步运行
    exit();
}
else
{
    // 父进程没有 waitpid() 调用
}
```

# Linux 中的线程管理

## 多线程的基本支持

直到最近，Linux 唯一的多线程支持是 `clone()` 系统调用，它允许基于现有进程创建新进程。这个调用类似于 `fork()` 调用，但具有其他一些特性。

- 对于新进程，需要指定一组特殊的标志，这些标志决定了资源如何在父进程和子进程之间分配。可以共享的资源包括地址空间、打开的文件信息和信号处理程序。请注意，在传统的 `clone()` 实现中，对进程标识符 (pid)、父进程 ID 以及一些其他重要属性没有特殊用法。

- 新进程可能可以设置一个新的栈（结果是，调用 `clone()` 后，两个进程可以共享一个公共内存段，这使得栈共享对于通用用途来说是不可接受的）。

对 `clone()` 的支持意味着实现了 1:1 的多线程方案。系统中的主要实体是进程，而不是线程（在 Linux 中，内核管理的实体被称为进程，而不是内核线程）。Linux 上传统的多线程实现确定用户线程映射到内核中的进程。因此，在 Linux 中单独查看线程数据结构是不切实际的——它与进程一样，使用相同的 `task_struct` 结构显示。

## Linux 传统多任务支持的缺点

自 `clone()` 系统调用以来，Linux 内核中的多线程基础未发生根本性变化。在此期间，Linux 已经从实验系统演变为一个行业通用的系统，其中实现了企业级重型应用。

这种系统的使用导致了多线程高可靠性和可扩展性的实现。

显然，`clone()` 系统调用的实现并不满足这些要求。我们在内核系统级别拥有完整的多线程处理设施实现。

线程控制是标准 POSIX 1996 相应 API 的一部分，该 API 被称为 POSIX 线程。

## Linux 内核线程

除了用户进程和线程，Linux 还支持一种特殊类型的调度对象，即已知的内核线程。这些线程像普通进程和线程一样被调度，每个都有自己的 ID (pid)。内核线程与进程和用户线程的区别在于：

- 它们的线程功能在内核代码中定义。

- 它们仅在内核模式下运行。

- 它们拥有不可访问的内存区域：用户模式下分配的内存。

## 线程管理软件的接口

### 创建线程

为了向当前进程添加新线程，POSIX 使用 `pthread_create()` 函数，其语法如下：

```c
#include <pthread.h>
int pthread_create(pthread_t *th, pthread_attr_t *attr,
                   void *(*thread_fun)(void *), void *arg);
```

考虑一下该函数的参数：

- `th` 是指向预定义结构体 `pthread_t` 类型的指针，然后传递给其他函数以处理线程；然后调用 API 来处理该线程（线程句柄）。
