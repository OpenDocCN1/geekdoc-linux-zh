
**访问调试工具**：与目标计算机相比，你很可能在主机计算机上拥有更好的调试工具——并且对它们有更多的控制权。主机计算机可能是一台运行 Linux 的桌面级计算机。在上面，你拥有一系列优秀的软件开发工具——不仅是编译器工具，还有调试器、调试库、内存边界检查库、如 `strace` 等工具等等。这些工具中的许多可能无法放入你的目标机中；它们甚至可能还没有被移植到你使用的处理器上。但并不意味着你不能使用它们。在你的主机机器上编译软件允许你使用这一系列工具来调试代码——一旦你对更改表示满意，就可以为目标重新编译代码。

**更简单的循环**：在主机上的调试循环几乎比在目标机上需要少得多的精力。你开始测试已修改代码的时间越短越好——特别是如果你像我一样，修改一小部分代码然后运行它，再修改更多小部分并运行。你的主机计算机为自己编译代码的速度可能与为目标编译的速度一样快；一旦编译完成，你不需要将其移动到任何地方——你可以在原地运行。将代码移动到目标机可能需要几分钟（或更长时间），仅仅是为了发现你犯了错误，然后重复整个过程。

当然，你确实需要在目标上进行测试，而且目标环境可能与主机环境非常不同，不仅在硬件方面，而且在运行时——C 语言库、其他库、实用程序等。如果你太长时间没有将开发代码移动到目标计算机上，你可能会在对目标环境做出某些错误假设时，浪费大量时间进行回溯。这在项目刚开始时尤为如此，因为你对环境还很陌生——首要任务应该是让硬件运行起来，然后至少每天测试一次你的软件。

有时在你的主机机器上调试软件是有意义的。例如，如果你正在为只存在于目标机上的硬件实现驱动程序，你显然无法在主机机器上完成开发存根代码以外的工作。你可能还想避免在主机机器上测试任何“危险”的软件。例如，任何作为功能的一部分、会在它看到的第一个硬盘的第一个分区上创建新文件系统的软件都不应该在你的主机机器上测试——即使你认为危险的代码路径是无法触及的。你最初那样想时可能是正确的，但当你测试和调试软件时，你可能会意外激活错误的代码路径并毁掉你的机器。

## chroot

有时启动 VMware 太麻烦，或者你可能在库方面遇到了问题，而目标机根本无法启动。如果你的主机和目标机运行相同的硬件，或者你只是在与主机相同的硬件上测试你的软件，你可以解压并将根文件系统挂载为回环文件系统（`mount -o loop`），然后 `chroot` 到它。这样做可以让你获得几乎与在不同硬件上运行时相同的环境。你运行的任何二进制文件都将使用目标的库，文件系统将是相同的，以此此类推。这对于测试许多类型的问题足够了。你甚至可以花点心思将代码复制到文件系统中。

然而，某些东西是不相同的：

- `Kernel`：你在主机上运行的 Linux 版本可能与目标机上的不同。取决于版本之间的差异大，`chroot` 环境在你的主机上可能完全无法工作。
- `Boot code`：通常在目标硬件启动时完成的任何必要设置代码，在启动 `chroot`ed 环境时必须手动运行。
- `/proc`：你不能在 `chroot`ed 环境中挂载 `/proc` 文件系统，因此任何依赖于它的软件都会遇到困难。
- `Network connections`：网络设施不是文件系统的一部分，因此它们在 `chroot`ed 环境中可见的。
- `System V IPC`：由于 System V 进程间通信结构（共享内存、消息队列和信号量）不存在于文件系统中，因此它们对 `chroot`ed 环境可见的。

## 用户模式 Linux (User Mode Linux)

在 `chroot` 和 VMware 之间是 User Mode Linux。User Mode Linux 允许在一个用户模式 Linux 进程的限制内设置一个完整的 Linux 内核和运行时环境。

设置之前描述的 `chroot` 示例要困难一点，但大多数提到的限制都被消除了。更多信息请参阅 `http://user-mode-linux.sourceforge.net/`
