
## times.deny

用户在此时间段内无法登录。注意，如果用户已经登录，这不会将其踢出。格式与 `times.allow` 相同。如果 `times.allow` 和 `times.deny` 重叠，则以 `times.deny` 为优先。

## 文件标志

所有的类 Unix 操作系统都有相同的文件系统权限，为文件的所有者、组和其他所有用户分配读、写和执行权限。FreeBSD 用文件标志扩展了该方案，标志与权限配合工作以增强您的系统安全性。某些标志用于与安全无关的功能，但我们将特别关注安全标志。你可以在 `man flags(1)` 中找到文件标志的完整列表。

这些标志中的许多具有影响安全级别的不同效果，将在下一节中介绍。理解安全级别需要理解文件标志，而文件标志又依赖于安全级别。目前，当你遇到提及安全级别时，只需点头微笑即可；一切在接下来的几页中都会变得明朗。

以下是常见的文件标志：

### appnd

系统级只追加标志只能由 root 设置。带有此标志的文件可以添加内容，但不能删除或以其他方式编辑。这对于日志文件特别有用。在用户的 `.history` 文件上设置 `appnd` 如果账户被攻破时会很有趣。由于入侵者的一种常用策略是移动历史记录或将其软链接到 `/dev/null` 以便管理员看不到发生了什么，`appnd` 确保了脚本小子无法通过这种方式掩盖踪迹。查看某试图删除 `appnd` 文件的记录几乎很搞笑；你几乎能看到攻击者在尝试各种方法时挫败感不断增加。当系统在安全级别下运行时，此标志无法被移除。

### schg

系统级不可变标志只能由 root 设置。带有此标志的文件**不能**添加内容，也不能删除或以其他方式编辑。这对于关键系统文件特别有用。当系统在安全级别下运行时，此标志无法被移除。

## 安全级别

安全级别是内核设置，通过改变基本系统行为来禁止某些操作。随着安全级别的提高，内核的行为会发生细微变化。例如，在低安全级别下，标志位可以合并。一个文件可能被标记为不可变——但你可以移除该标记、编辑文件并重新标记。当你增加安全级别时，该文件标记将无法被移除。系统的其他部分也会发生类似的变化。总的来说，提高安全级别引起的行为变化会让入侵者感到沮败或停止。通过 `rc.conf` 选项 `kernel_securelevel_enabled=YES` 启用安全级别。

安全级别通过对你的行为施加限制增加了系统维护的复杂性。毕竟，许多系统管理任务都是入侵者为了掩盖踪迹而可能做的。例如，在高安全级别下，你不能在系统运行时格式化或挂载新的硬盘。另一方面，安全级别对入侵者的阻碍远大于对你的阻碍。

## 安全级别定义

安全级别共分为 5 级：-1、0、1、2 和 3，其中 -1 最低，3 最高。一旦你通过 `kernel_securelevel_enable` 选项启用了安全级别，就可以启动时通过 `kernel_securelevel` 变量设置安全级别。你可以随时提高安全级别，而不仅仅是在启动时，但如果不重启到单用户模式，你就无法降低它。毕竟，如果你可以随时降低安全级别，你的入侵者也会这样做！

### 安全级别 -1

默认情况下完全没有提供额外的内核安全。如果你正在学习 FreeBSD 并频繁更改配置，请保持在安全级别 -1，并使用内置的文件权限和其他 Unix 安全措施来确保安全。

### 安全级别 0

安全级别 0 仅在启动期间使用一次，且不提供任何特殊功能。当系统进入多用户模式时，安全级别会自动提高到 1（在 `/etc/rc.conf` 中设置等同于设置 `kernel_securelevel=1`）。不过，如果你有执行被更高安全级别所禁止的操作的启动脚本，这可能会有所帮助。

### 安全级别 1

在安全级别 1（基本安全模式）下，事情变得有趣起来：

- 系统级文件标记可能无法关闭。
- 你不能加载或卸载内核模块（见第 5 章）。
- 程序不能通过 `/dev/mem` 或 `/dev/kmem` 直接写入系统内存。
- 没有任何操作访问 `/dev/io`。
- 挂载的磁盘无法直接写入（你可以向磁盘写入文件，但你无法直接访问原始设备）。

对于普通用户来说，安全级别 1 最明显的影响是 BSD 特有的文件标记无法被修改。如果一个文件被标记为系统级不可变，而你想替换它，那很遗憾了。

### 安全级别 2

安全级别 2 具有安全级别 1 的行为，并额外增加了两个：

- 无论是否挂载，磁盘都无法以写模式打开。
- 你对系统时间的修改不能超过一秒。

这两项对于新系统管理员来说似乎无关，但它们提供了重要的安全保护。虽然 Unix 提供了编辑器等工具来编写文件，但也绕过工具甚至绕过实际文件系统来访问硬盘底层的 0 和 1。如果你这样做，就可以无视文件权限更改任何文件。这种情况通常只发生在你安装新硬盘并必须在上面创建文件系统时。通常，root 用户可以以这种方式直接写入磁盘。在安全级别 2 下，root 无法这样做。

同样，另一个老旧的黑客技巧是更改系统时间、编辑文件，然后将时间改回来。这样，当管理员寻找可能引起问题的文件时，被篡改的文件似乎已经几个月或多年没有变动过了，因此看起来不是显而易见的担忧来源。

### 安全级别 3

安全级别 3 是网络安全模式。除了安全级别 1 和 2 的设置外，你无法调整包过滤规则。你主机上的防火墙是不可变的。如果你系统启用了包过滤或带宽管理，且这些规则经过了良好优化且不太可能更改，你可以使用安全级别 3。

## 你需要哪种安全级别？

适合你环境的选择完全取决于你的状况。例如，如果你刚将 FreeBSD 机器投入生产并仍在进行微调，请将安全级别保持在 -1。然而，一旦系统调优完成，你就可以提高安全级别。大多数生产系统在安全级别 2 下运行良好。

如果你使用 FreeBSD 的包过滤或防火墙包之一，安全级别 3 看起来可能很有吸引力。但在启用此功能之前，请务必确定你的防火墙规则是正确的！安全级别 3 会让你在不中断连接的情况下无法更改防火墙。你是否百分之百确定你的没有任何客户会来打电话说：“这里有一张支票，关于我的带宽”？

## 安全级别和文件标记实现了什么？

考虑这样一种情况：有人入侵了你 Apache Web 服务器上的一个 CGI 脚本，利用它引导进入 shell，然后利用该 shell 将他自己提升到 root 权限。

如果你相应地设置了安全级别，也许这个攻击者会感到沮丧，因为他无法将你的内核替换为特殊编译的内核。没问题；他仍然可以将各种系统程序替换为带有木马的版本——这样当你下次登录时，你新版本的 `login(1)` 就会将你的密码发送到匿名的 Web 邮箱或互联网网络。

所以，为了保护你的关键文件，你四处运行 `chflags schg -R /bin/*`、`chflags schg -R /usr/lib` 等。如果你忘记了某个文件——比如，像 `/etc/bsdextended` 之类的东西——入侵者就可以修改该文件。他随后可以在深夜重启系统，而你可能不会注意到。你如何坐下来彻底审计 `/etc/rc.d`？

你认为系统是安全的，每个文件都受到了保护。系统启动过程尝试执行该目录下的任何以 `.sh` 结尾的文件。因此，入侵者可以通过在该处放置脚本来造成巨大损害。毕竟，`/etc/rc.d` 在启动结束时提高安全级别。如果他创建一个杀死 `/etc/rc.d` 以免其提高安全级别的脚本，然后转身运行他的 `/var/hidden/.rootkit` 来完成破坏系统呢？

当然，还有其他方法，仅限于入侵者的创造力。只需记住，安全是一个没有简单解决方案的棘手问题。一旦入侵者拥有命令提示符，那就是你与他们的对决。如果他们足够优秀，你在发现被入侵时已经太晚了。通过遵循良好的计算实践并保持系统更新，你可以保护自己。

## 网络目标

入侵者通常进入监听网络的应用程序，而不是操作系统。减少针对你的服务器的攻击数量的一种方法，是识别所有监听网络的程序并禁用任何不必要的程序。FreeBSD 提供了 `sockstat(1)` 作为识别监听网络程序的简单方法。

我们在第 6 章介绍 `sockstat`；运行 `sockstat -4` 显示所有 IPv4 TCP/IP 端口。你开启的网络端口都是潜在的弱点和潜在的威胁。关闭不必要的网络服务就能最安全。

## 总结

一旦你只开放了必要的网络端口，并且知道哪些程序正在使用这些端口，你就知道哪些程序是你最需要关注其安全性的。如果 FreeBSD 安全团队发布了关于你未运行的服务漏洞的公告，你可以安全地推迟实施修复，直到下一次维护窗口。然而，如果安全团队宣布你正在使用的程序存在漏洞，你就知道必须尽快实施修复。如果他们宣布你使用的某款网络软件存在严重问题，你就知道必须迅速行动。能够对真实风险做出智能且快速的响应，有助于保护你免受大多数入侵者。文件标记和安全级别等工具可以减少成功入侵者能造成的破坏。最后，使用用户组将自己的系统管理员限制在系统的特定部分，可以保护计算机免受意外或故意损坏。

# 第 8 章 磁盘与文件系统

![](img/b00144f770bf509a54e1d770bb05a101_240_0.png)

管理文件系统和磁盘的重要性无论怎么强调都不为过。你的磁盘包含你的数据，可靠性和灵活性对于操作系统来说至关重要。FreeBSD 支持多种文件系统，并有许多处理它们的方法。在本章中，我们将考虑每位系统管理员执行的最常见的磁盘任务。

## 磁盘驱动入门

大多数人将磁盘驱动器视为脆弱的魔法盒。如果你对待驱动器很粗暴，可能会让它发出嘎吱声和摩擦声，如果受到足够的虐待，你甚至可以让“魔法烟雾”逃逸，使其再也无法工作。要真正理解文件系统，你必须稍微了解磁盘内部发生了什么。如果你有一个不再尊重的旧硬盘，尽管拆开外壳并跟随学习。

在硬盘外壳内部，你会发现一叠圆形的铝制或塑料圆盘，通常称为盘片。当驱动器运行时，盘片以每分钟数千转的速度旋转。硬盘上的 RPM 数衡量的是盘片的旋转速度。

薄薄的磁介质覆盖在盘片上。这些磁性材料被排列成数千万个圆环，称为轨道，从盘片的内芯延伸到边缘，就像树的年环一样。这些轨道以 0 和 1 的字符串形式存储数据。每个轨道被划分为扇区。外圈道的每个扇区存储的数据比内圈轨道对应的扇区更多，而且读取相同量的数据，外轨道所需的时间比内轨道短，因为外轨道移动速度更快。

读写头安装在每个盘片上方，当盘片经过时读写数据，就像唱片针一样。这些读写头读写很快，但它们必须等待磁盘移动到它们下方的正确位置。磁盘性能基本上取决于这些盘片经过驱动器头部的速度有多快，这正是 RPM 变得重要。

## ATA, SATA, SCSI 和 SAS

> 我假设你对标准磁盘存储技术的知识已经很熟悉。如果不熟悉，请花点时间在网上查看关于这些主题的优秀教程，即使是维基百科上的短文也可以。我会在那里提供关于如何使用这些技术的建议，但 SCSI ID 和 LUN 则是另一本书的主题。

## 设备节点

我们在第 3 章中简要提到了设备节点，但让我们详细考虑它们。设备节点是代表系统中硬件的特殊文件。它们被用作用户程序与设备驱动程序或物理设备之间的逻辑接口。通过对设备节点使用命令，向设备节点发送信息数据，你是在告诉内核对物理设备执行某操作。这些操作对于不同的设备可能非常不同——向磁盘写入数据与向声卡写入数据大不同。所有设备节点都存在于 `/dev` 中。

在操作磁盘或分区之前，你必须知道它的设备名称。FreeBSD 磁盘设备节点来自于该类型硬件的设备名称。驱动程序名称又来自于设备中使用的芯片组，而不是设备看起来像什么。

表 8-1 显示了最常见的磁盘节点。如果想查看完整细节，请参考帮助页。

### 表 8-1：存储设备与类型

| 设备节点 | 帮助页 | 描述 |
| :--- | :--- | :--- |
| `/dev/fd*` | `fdc(4)` | 软盘 |
| `/dev/acd*` | `acd(4)` | IDE 光驱驱动 |
| `/dev/ad*` | `ad(4)` | ATA 和 SATA 硬盘及分区 |
| `/dev/cd*` | `cd(4)` | SCSI 光驱驱动 |
| `/dev/da*` | `da(4)` | SCSI 和 SAS 硬盘、USB 和闪存存储等 |

连接到硬件 RAID 控制器的磁盘不为每个磁盘使用设备名称。相反，这些 RAID 控制器为每个 RAID 容器呈现一个虚拟磁盘，使用以 RAID 驱动程序命名的设备节点。例如，`amrd(4)` 驱动程序将其虚拟磁盘呈现为 `/dev/amrd*`。一些 RAID 磁盘使用 `cam(4)` 抽象层，因此硬盘显示为 `/dev/da*` 设备。

## 硬盘与分区

虽然我们在第 2 章中讨论过分区，但让我们从磁盘设备的角度来考虑分区。我们第一个控制器上第一个可能的 ATA 磁盘是 `/dev/ad0`。随后的磁盘是 `/dev/ad1`、`/dev/ad2` 等以此类推。

第五个字段告诉 `dump(8)` 该文件系统是否需要备份。如果设置为 0，`dump` 将完全不备份该文件系统。否则，该数字表示触发此文件系统备份所需的最小 dump 级别。详情请参阅第 4 章。

最后一个字段 `Pass#`，告诉系统在启动过程中检查文件系统的完整性。所有具有相同 `Pass#` 的分区都将用 `fsck(8)` 进行检查。只有根分区的 `Pass#` 为 1，并且会被检查。所有其他文件系统都设置为 2，这意味着 FreeBSD 在根文件系统之后挂载它们。不需要检查的交换分区和只读媒体设置为 0。

掌握了这些知识后，让我们来看 `/etc/fstab` 示例：

| Device | Mountpoint | FType | Options | Dump | Pass# |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `/dev/ad4s1b` | `none` | `swap` | `sw` | `0` | `0` |
| `/dev/ad4s2a` | `/` | `ufs` | `rw` | `1` | `1` |
| `/dev/ad4s1a` | `/amd64` | `ufs` | `rw` | `2` | `2` |
| `/dev/ad4s1f` | `/amd64/` | `ufs` | `rw` | `2` | `2` |
| `/dev/ad4s5d` | `/amd64/` | `ufs` | `rw` | `2` | `2` |
| `/dev/ad4s2e` | `/tmp` | `ufs` | `rw` | `2` | `2` |
| `/dev/ad4s2d` | `/var` | `ufs` | `rw` | `2` | `2` |
| `/dev/ad4s3d` | `/home` | `ufs` | `rw` | `2` | `2` |
| `/dev/acd0` | `/cdrom` | `cd9660` | `ro` | `0` | `0` |
| `data:/tmp` | `/mnt` | `nfs` | `rw,noauto` | `0` | `0` |

我们的第一个条目 `/dev/ad4s1b` 是交换空间。它没有挂载在任何地方；FreeBSD 使用交换空间作为二级内存。第二个条目 `/dev/ad4s2a` 是根分区。注意设备名称——虽然交换在 slice 1 上，但根文件系统在 slice 2 上。根目录与交换空间不在同一个 slice 上！

第三个分区是 `/dev/ad4s1a`。我们通常期望根分区在那里，但它被挂载为 `/amd64`。接下来的两个分区也在 slice 1 上，但挂载在 `/amd64` 下。我们的 `/tmp` 文件系统在 slice 2 上。

接下来的条目 `/var` 和 `/home` 是磁盘上看起来正常的分区。我们的 CD 挂载在 `/cdrom` 上，并且在启动时不会挂载。最后一个条目没有以设备节点开头。这是一个网络文件系统 (NFS)，它告诉我们当专门请求时，在本地机器上挂载远程目录。我们将在本章稍后的部分讨论 NFS。

此文件系统表来自一台双启动机器，运行着 FreeBSD/i386 和 FreeBSD/amd64。这就是为什么该表看起来不正常。在运行 i386 的同时，我可以访问 amd64 文件系统并使用 amd64 交换空间。

## 现在挂载了什么？

如果并非所有文件系统都在启动时自动挂载，并且管理员请求了额外的挂载，你如何确定系统现在挂载了什么？运行不带任何选项的 `mount(8)` 来查看所有挂载的文件系统列表：

```
# mount
/dev/ad4s2a on / (ufs, local)
devfs on /dev (devfs, local)
/dev/ad4s1e on /tmp (ufs, local, soft-updates)
/dev/ad4s2e on /usr (ufs, local, soft-updates)
/dev/ad4s2d on /var (ufs, local, soft-updates)
/dev/ad4s3d on /home (ufs, local, soft-updates)
```
