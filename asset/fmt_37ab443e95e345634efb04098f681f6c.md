如你所见，RCS 将每个版本的更改记录为 `foo.c,v` 文件中的 `diff` 命令。因此，你可以通过使用 `co -rX.X` 命令在任何时间成功地检索每个版本，其中 `X.X` 是你想要的版本。此外，由于更改是 `diff` 格式，原始文档的许多更改可以相当高效地存储（尽管某些人可能会认为应该使用压缩）。

有时你必须创建一个文件的“分支”版本，仅仅是为了在版本的中间进行临时的或专门的修复。在这种情况下，你使用 `co` 命令的 `-rX.X` 选项来创建一个分支。

例如，为了对 `foo 1.2` 进行特殊发布，你使用以下命令：

```
# co -l -r1.2 foo.c
RCS/foo.c,v --> foo.c
revision 1.2 (locked)
done
```

在进行更改并把 `foo.c` 回库时，`ci` 命令会将版本提升到 1.2.1.1 并响应如下内容：

```
# ci foo.c
RCS/foo.c,v <-- foo.c
new revision: 1.2.1.1; previous revision: 1.2
enter log message, terminated with single ` or end of file:
>> a temporary fix
>> .
done
```

你也可以合并程序的不同版本。例如，要将从 1.1 的更改引入 1.3，你可以使用 `rcsmerge` 命令，但首先你必须以锁定状态检出 `foo.c`：

```
# co -r1.1 foo.c
RCS/foo.c,v --> foo.c
revision 1.1
done
# rcsmerge -p -r1.1 -r1.3 foo.c >foo.merged.c
RCS file: RCS/foo.c,v
retrieving revision 1.1
retrieving revision 1.3
Merging differences between 1.1 and 1.3 into foo.c; result to stdout
```

注意 `rcsmerge` 的输出必须重定向到文件。要移除特定版本，请使用：

```
# co -l -r1.2 foo.c
RCS/foo.c,v --> foo.c
revision 1.2 (locked)
done
```

要创建一个仓库，首先将环境变量 `$CVSROOT` 指向仓库的绝对路径。

在执行命令之前，请确保该目录存在。然后执行带有 `init` 选项的 `cvs` 命令。

例如，以下命令检查 `CVSROOT` 的设置，验证仓库根目录是否存在，然后创建仓库：

```
$ echo $CVSROOT
/usr/local/cvsroot
$ ls -ld $CVSROOT
drwxrwxrwx 4 trimblef users 1024 May 17 14:55 /usr/local/cvsroot
$ cvs init
$
```

`cvs` 命令会静默工作，在 `/usr/local/cvsroot` 目录下创建一个管理层级结构。你可以使用 `-d` 选项覆盖 `$CVSROOT` 环境变量的设置。例如，以下命令会在 `/usr/cvsroot` 下初始化一个 CVS 仓库，即使 `$CVSROOT` 环境变量指向不同的位置：

```
cvs -d /usr/cvsroot init
```

事实上，你可能会发现许多 `cvs` 命令都允许你以这种方式指定仓库的根目录。

仓库现在已准备好管理你的源代码。请确保你的开发人员通过在他们的环境中设置 `$CVSROOT` 环境变量来指向相应的仓库，或者在 `cvs` 命令行中使用 `-d` 选项。

## 仓库

正如我提到的，仓库除了受控制的源代码外，还包含管理文件。CVS 的运行并不要求层级结构中的管理部分存在。然而，这些文件支持许多有用功能，强烈建议保留它们。图 25.1 显示了调用 `cvs init` 后在 `$CVSROOT/CVSROOT` 目录下创建的文件。

**图 25.1** 仓库初始化后 `CVSROOT` 目录的内容。

请注意，某些文件的扩展名为 `,v`。这是 RCS 控制下文件的默认扩展名。事实上，这些是 RCS 文件，它们说明了 CVS 如何作为 RCS 的前端来使用。除了实际的源文件外，可以使用适当的 `cvs` 命令检出并修改管理文件。以下是仓库中每个文件的用途描述：

- `checkoutlist`：此文件支持 `CVSROOT` 中的其他管理文件。它允许你为各种 `cvs` 命令自定义诊断信息。
- `commitinfo`：此文件指定了执行 `cvs commit` 命令时应执行的程序。通过这种方式，你可以在文件进入仓库之前对其进行合理检查。CVS 分发的 `contrib` 目录包含许多实用的示例脚本。
- `cvswrappers`：此文件定义了在检入或检出时执行的*封装程序*。该文件的一种可能用途是格式化提交的源文件，使其外观和结构与仓库中的其他文件保持一致。
- `editinfo`：此文件允许你在提交开始之前但在日志记录之后执行脚本。如果脚本以非零值退出，提交将终止。
- `history`：此文件跟踪所有影响仓库的命令。
- `loginfo`：`loginfo` 文件与 `commitinfo` 类似。主要区别是 `loginfo` 在文件提交后进行处理。该文件的典型用途包括发送电子邮件以及在提交发生后向文件追加日志消息。
- `modules`：此文件允许你为一组文件定义符号名称。如果不这样做，你必须为引用的每个文件指定一个相对于 `$CVSROOT` 目录的部分路径。
- `notify`：此文件控制由 `cvs watch add` 和 `cvs edit` 命令设置的观察通知。
- `rcsinfo`：此文件允许你为提交日志话指定模板。
- `taginfo`：此文件定义了在任何标签操作后执行的程序。例如，如果标签名称发生变化，你可以配置文件向原始开发人员发送邮件，通知他们文件已更改。

## 将文件导入仓库

现在仓库已经初始化，你可以添加文件和文件目录。你通过使用 `import` 命令来实现。例如，假设你有以下准备好纳入版本控制的源代码文件层级结构：

```
$ find . -print
.
./src
./src/main
./src/main/main.c
./src/main/main.h
./src/print
./src/print/print.c
./src/print/print.h
./src/term
./src/term/term.c
./src/term/term.h
$
```

在包含 `src` 目录的目录下，运行以下命令：

```
$ cvs import -m "initial release" project myvtag myrtag
cvs import: Importing /usr/local/cvsroot/project/src
cvs import: Importing /usr/local/cvsroot/project/main
cvs import: Importing /usr/local/cvsroot/project/print
cvs import: Importing /usr/local/cvsroot/project/term
```

在前面的命令中，`-m` 选项提供了导入的描述。下一个选项 `project` 标识目录。接接的参数分别标识供应商标签（vendor tag）和发布标签（release tag）。
