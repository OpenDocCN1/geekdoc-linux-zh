
在本章中，我们确定了为什么一个应用程序（GIMP 过滤器 `lic`）是 CPU 密集型的。我们确定了应用程序的基准运行时，设定了优化目标，并保存了一张参考镜像以验证我们的优化没有改变应用程序的行为。我们使用了 Linux CPU 性能工具（`oprofile` 和 `ltrace`）来调查应用程序为什么是 CPU 密集型的。然后，我们使用 `gdb` 来理解应用程序的工作原理，并想出不同的优化方法。我们尝试了几种不同的优化，但最终，我们选择了经典的“增加内存使用以减少 CPU 使用”的性能权衡方案。

我们超越了优化目标，并验证了我们的优化没有改变应用程序的输出。

虽然本章侧重于优化单个应用程序的运行时，但下一章将介绍一次性能搜寻，重点在于减少与 X Windows 交互时的延迟。减少延迟可能是困难的，因为单个事件往往会触发一系列不显见的其他事件。困难之处在于确定哪些事件被调用了以及每个事件花费了多长时间。

# 第 11 章 性能搜寻 2：延迟敏感型应用程序 (`nautilus`)

本章包含一个如何使用 Linux 性能工具在延迟敏感型应用程序中发现并修复性能问题的示例。

读完本章后，你应该能够：

- 使用 `ltrace` 和 `profile` 确定延迟敏感型应用程序中产生延迟的位置。
- 使用 `gdb` 为每次对“热点”函数的调用生成堆栈跟踪。
- 使用性能工具确定使用许多不同共享库的应用程序时间耗费在哪里。
- 将本章作为模板，寻找延迟敏感型应用程序中高延迟的产生。

## 11.1. 延迟敏感型应用程序

在本章中，我们调查了一个对慢延迟敏感的应用程序。延迟可以被认为应用程序响应不同外部或内部事件所需的时间。一个应用程序只有少量的 CPU 时间来响应不同的事件。然而，它对特定事件的响应不够快。在修复延迟性能问题时，我们需要减少对各种事件响应的延迟，并找出应用程序的哪些部分降低了响应。正如你所看到的，追踪延迟问题的策略与追踪 CPU 密集型问题的策略略有不同。

这次性能调查与 GIMP 调查的显著区别在于，我们试图减少的时间级是毫秒级的，而不是秒级的。当时间如此短时，要确保你捕获的分析数据确实是你试图测量的事件的结果，而不是仅仅是启动和停止性能分析工具时产生的噪声，是非常困难的。然而，这段短时间范围也使得在有趣的时间段内对应用程序的所有方面进行追踪变得可行。

## 11.3. 寻找基准/设定目标

正如前面提到的，第一步是确定问题的当前状态。为了让我们的工作更轻松一点，并避免上一节提到的某些问题，我们将创建一个小窗口和弹出菜单问题使其看起来更像我们之前测量的长时间运行 CPU 密集型任务。单个弹出菜单出现的时间在毫秒范围内，这使得很难用我们的性能工具进行准确测量。正如之前提到的，在感兴趣的时间内（即打开实际菜单花费的时间）启动和停止这些工具将很困难。在这里，我们看到了我们感兴趣的内容（即我们点击的菜单）。我们不会只打开一次菜单，而是将连续快速打开 100 次菜单。这样，打开菜单花费的总时间将增加 100 倍。这使我们能够使用分析工具来捕获有关菜单如何执行的信息。

因为手动点击 100 次会很乏味，而且人类（除非经过良好训练）无法以可重复的方式可靠地打开 100 次弹出菜单，我们必须对其进行自动化。为了可靠地打开 100 次弹出菜单，我们依赖于自动化包。`xautation` 软件包可以在 http://httpajoo.net/projects/xautation.html 获取。它可以向 X 服务器发送任何窗口事件，模拟鼠标点击。下载 `xautation` 文件、解压并编译它后，我们就可以使用它来自动化鼠标点击。

与 GIMP 不同，我们不能简单地测量 `nautilus` 使用的 CPU 数量，我们需要让弹出菜单问题看起来更像我们之前测量的长时间运行 CPU 密集型任务。单个弹出菜单出现的时间在毫秒范围内，这使得很难用我们的性能工具进行准确测量。正如之前提到的，在感兴趣的时间内（即打开实际菜单花费的时间）启动和停止这些工具将很困难。在这里，我们看到了我们感兴趣的内容（即我们点击的菜单）。我们不会只打开一次菜单，而是将连续快速打开 100 次菜单。这样，打开菜单花费的总时间将增加 100 倍。这使我们能够使用分析工具来捕获有关菜单如何执行的信息。

（注：此处去除了原文中反复出现的重复段落，以保持文档整洁。）

### Listing 11.1.

```bash
#!/bin/bash
for i in seq 100; do
  echo $i
  ./xte 'mousemove 100 100' 'mouseclick 3'
  ./xte 'mousemove 200 100' 'mouseclick 3'
done
```

`Listing 11.1` 中的命令将光标移动到 X 屏幕 `(100,100)` 并点击右键（`3`）。这会弹出菜单。然后我们再次点击右键并关闭此菜单。然后它们移动到位置 `(100,100)` 并重复。

接下来，我们使用时间查看 100 次迭代花费了多少时间。这就是我们的基准时间。通过我们的优化，我们将再次检查改进了什么。Fedora `nautilus` 的基准时间为 26.5 秒。

最后，我们必须为优化选择一个目标。一种方法是找到弹出 100 次菜单所需的时间。另一个例子是快速菜单。虽然菜单不像 `nautilus` 那么复杂，但它们至少是一个上限。

## 11.4. 为性能搜寻配置应用程序

调查的下一步是为性能搜寻设置应用程序。虽然 GIMP 立即重新编译了应用程序，但我们将在 `nautilus` 上处采取不同的方法。它可能很难确定哪些部分需要重新编译，因为它依赖于许多不同的共享库。而不是重新编译，我们将下载并安装每个应用程序和库的调试信息。对于 Fedora 和 Enterprise Linux，Red Hat 提供了一组 `debuginfo rpm`，其中包含了编译器在编译应用程序时生成的符号信息和源代码。每个二进制包或库都有相应的 `debuginfo rpm`。然而，它允许开发者或调查性能问题的人下载并使用相应的 `debuginfo` 包。在这种情况下，Red Hat 版本的 `profile` 也会识别 `debuginfo` 包，并在分析应用程序（如 `nautilus`）和库（如 `gtk`）时获取符号。在这种情况下，我们将下载 `gtk`、`nautilus`、`glib` 和内核的 `debuginfo`。

## 11.5. 安装和配置性能工具

排查的下一步是安装调查问题所需的性能工具。正如我们在对 GIMP 进行性能排查时所的那样，我们将同时安装 `profile` 和 `ltrace`。在这种情况下，我们还将下载并安装 `gdb`（如果尚未安装的话）。`gdb` 允许我们查看运行应用程序的某些动态方面。

## 11.6. 运行应用程序和性能工具

接下来，我们运行应用程序并使用性能工具进行测量。由于我们已经怀疑许多进程和库的复杂相互作用可能是问题的原因，我们将从 `profile` 开始，看看它能显示什么内容。

由于我们只希望在打开弹出菜单时让 `profile` 测量事件，我们将使用如列表 11.3 所示的命令行，在运行打开和关闭 100 个弹出菜单的脚本（`script.sh`）之前和之后立即启动并进行性能分析。

### 列表 11.3.

