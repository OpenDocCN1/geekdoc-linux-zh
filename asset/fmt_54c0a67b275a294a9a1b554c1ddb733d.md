
getopt.o: getopt.c config.h getopt_int.h

dictionary.o: dictionary.c config.h getopt_int.h

misc.o: misc.c config.h

sentence.o: sentence.c config.h misc.h sentence.h

style.o: style.c config.h getopt.h misc.h

```
.C.O:
$(CC) -c $(CFLAGS) $(CFLAGS) $<
```

这一切看起来非常复杂。为什么不简单地列出编译所有部分的步骤然后完事了呢？这个问题的答案很快就会变得明朗。在此期间，让我们运行并构建我们的程序。

```
[me@linuxbox diction-1.11]$ make
```

`make` 程序将运行，并使用 `Makefile` 的内容来指导其操作。运行完成后，我们将发现所有的目标现在都出现在我们的目录中了。

```
[me@linuxbox diction-1.11]$ ls

en install-sh sentence.c

config.guess de.po

config.h dictionary en GB sentence.h

config.hin dictionary.1 en_GB.mo

config.log dictionary.1.in en_GB.po misc.c style

config.status dictionary.c getopti.c style.1

config.sub dictionary.o getopti.o misc.o style.1.in

configure dictionary.pot getopt.c NEWS style.c

config.in dictionary.spec getopt.h nl style.0

COPYING dictionary.spec getopt-int.h nl.mo

de dictionary.text nl1.po

de.mo dictionary.texl INSTALL README
```

在这些文件中，我们看到了 `diction` 以及我们着手构建的程序。应该祝喜一下！我们刚刚从源代码编译了我们的第一个程序！
但出于好奇，让我们再次执行 `make` 吧。

```
[me@linuxbox diction-1.11]$ make

make: Nothing to be done for `all`.
```

它只输出了这条奇怪的信息。是怎么了？为什么我们没有再次构建程序呢？啊，这就是 `make` 的魔法。`make` 并不是重新构建一切，它只构建需要构建的部分。由于所有目标已经存在，`make` 判定无事可做。我们可以通过删除其中一个目标并再次运行来观察它会做什么。让我们删掉其中一个中间目标。

```
[me@linuxbox diction-1.11]$ rm getopt.o

[me@linuxbox diction-1.11]$ make
```

我们看到它重新构建并链接了 `diction` 和 `style` 程序，因为它们依赖于缺失的模块。这种行为指出了 `make` 的另一个重要特性：它保持目标是最新的。`make` 坚持认为目标比依赖项更新。这完全合理，因为程序员经常会更新部分源代码，然后使用 `make` 来构建完成产品的新版本。`make` 确保根据更新后的代码需要构建的所有内容都已完成构建。如果我们使用 `touch` 工具来“更新”源代码文件，我们可以看到这种现象发生：

```
me@linuxbox diction-1.11]$ ls -l dict getopt.c

  -rw-XR-X 1 me             37164 2009-03-05 06:24 dict

  -rw-r---- 1 me             33125 2009-03-03 17:45 getopt.c

[me@linuxbox diction-1.11]$ touch touch.c

[me@linuxbox diction-1.11]$ ls -l dict getopt.c

  -rw-XR-X 1 me             37164 2009-03-05 06:24 dict

  -rw-r---- 1 me             33125 2009-03-05 06:23 getopt.c

[me@linuxbox diction-1.11]$ make
```

在 `make` 运行后，我们看到它将目标恢复到比依赖项更新的状态。

```
[me@linuxbox diction-1.11]$ ls -l dict getopt.c

  -rw-XR-X 1 me             37164 2009-03-05 06:24 dict

  -rw-r---- 1 me             33125 2009-03-05 06:23 getopt.c
```

智能地仅构建需要构建的内容对程序员来说是一个巨大的优势。虽然在我们的小型项目中，节省时间的优势可能并不明显，但在较大的项目中，它是非常的。记住，Linux 内核（一个经历持续修改和改进的程序）包含了数百万行代码。

# 安装程序

封装良好的源代码通常会包含一个名为 `install` 的特殊 `make` 目标。这会将最终产品安装到系统目录中。通常，这个目录是 `/usr/local/bin`，本地构建软件的传统位置。然而，普通用户通常无法写入此目录，因此我们必须使用超级用户（superuser）来执行安装。

```
[me@linuxbox diction-1.11]$ sudo make install
```

执行安装后，我们可以检查程序是否已就绪。

```
[me@linuxbox diction-1.11]$ which diction

/usr/local/bin/diction
```
我们已经完成了！

## 总结

在本章中，我们学习了 `configure`、`make` 和 `install` 这三个命令如何用于构建程序。我们看到了 `make` 如何通过跟踪依赖关系来避免重复工作。`make` 坚持认为目标比依赖项更新。我们还学习了什么是 shell 脚本，它们是包含系列命令的文本文件。我们学习了如何使用 shebang 来指定解释器，以及如何执行脚本。

# 什么是 shell 脚本？

从简单的术来说，shell 脚本是一个包含系列命令的文件。shell 读取该文件并执行这些命令，就像它们直接在命令行中输入的一样。shell 有些独特之处在于它既是一个界面也是一种脚本语言。

# 如何编写脚本

为了成功创建并运行脚本，我们需要做三件事：

- 编写脚本。shell 脚本是普通的文本文件。
- 使脚本具有执行权限。
- 将脚本放在 shell 可以找到的地方。

# 脚本格式

按照传统，我们将创建一个“Hello World”程序来演示：

```
#!/bin/bash
```

```
echo 'Hello World'
```

我们脚本的第一行看起来有点神秘。它似乎是一个以 # 开头的注释，但实际上是一个被称为 shebang 的特殊结构。shebang 用于告诉内核执行后续脚本的解释器名称。

# 执行权限

我们要做的下一步是让我们的脚本可执行。这通过 `chmod` 轻松完成。

```
[me@linuxbox ~]$ ls -l hello_world

  -RW-R--R-- 1 me 63 2018-03-07 10:10 hello_world

[me@linuxbox ~]$ chmod 755 hello_world

[me@linuxbox ~]$ ls -l hello_world

  -RWX-XR-X 1 me 63 2018-03-07 10:10 hello_world
```

脚本有两种常见的权限设置：`755` 适用于所有人都可以执行的脚本，`700` 适用于只有所有者可以执行的脚本。注意脚本必须可读才能执行。

# 脚本位置

设置权限后，我们现在可以运行脚本了。

```
[me@linuxbox ~]$ ./hello_world

Hello World!
```

为了脚本，必须在脚本名称之前加上显式路径。如果我们这样做，就会得到这个：

```
[me@linuxbox ~]$ hello_world

bash: hello_world: command not found
```

`PATH` 变量包含一个由冒号分隔的搜索目录列表。我们来看 `PATH` 的内容。

```
me@linuxbox ~]$ echo $PATH
