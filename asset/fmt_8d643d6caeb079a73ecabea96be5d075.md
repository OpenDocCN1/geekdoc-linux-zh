
Python 3 重新组织了标准库多个部分的命名，特别是与网络和 Internet 数据格式相关的模块。此外，许多旧模块已从库中删除（例如 `gopherlib`、`rfc822` 等）。

现在模块标准使用小写名称。`ConfigParser`、`Queue` 和 `SocketServer` 等模块已重命名为 `configparser`、`queue` 和 `socketserver`。

# 绝对导入

在 Python 3 中，推荐使用绝对导入。绝对导入指定从项目根目录到模块或函数的完整路径。例如：

```python
from package.module import function
```

相对导入也是可能的，并使用点符号法表示当前包或父包。例如：

```python
from .module import function
```

然而，绝对导入通常更具可读性，并且在包结构变化时更不容易出错。

作为输出，`2to3` 会识别出它认为有问题并可能需要更改的所有程序部分。这些部分以上下文差异（context-diffs）的形式显示在输出中。虽然我们是在单个文件上使用 `2to3`，但如果你提供一个目录名称，它会递归地查找目录结构中所有的 Python 文件，并为其中的所有内容生成报告。

默认情况下，`2to3` 不修复任何源代码——它只报告可能需要更改的代码部分。`2to3` 面临的一个挑战是它往往拥有不完整的信息。例如，`spam()` 函数中的 `has_key()` 已被移除，改为使用运算符。`2to3` 报告了这一变化，但在没有更多信息的情况下，尚不清楚 `spam()` 是在操作一个字典，还是 `d` 可能是其他类型的对象（也许是数据库），恰好提供了 `has_key()` 方法，但使用运算符时会失败。`2to3` 的另一个问题是 Python 2 会自动将字节字符串（bytes strings）提升为 Unicode，这导致经常会看到某些不小心将这两种字符串合并在一起的代码。

遗憾的是，`2to3` 无法解决所有这些问题。这就是为什么编写良好的单元测试很重要的原因之一。当然，这一切取决于具体的应用程序。

作为一种选项，可以指示 `2to3` 修复选定的不兼容性。通过输入 `2to3 -1` 可以获取“修复器”（fixers）的列表。例如：

```bash
%2to3 -1
适用于 -f/--fix 选项的可用转换：
apply
bastetring
buffer
...
xrange
readlines
zip
```

使用此列表中的名称，只需输入 `2to3 -f fixname filename` 即可看到修复实际上会更改什么。如果你想应用多个修复，请为每个修复指定单独的 `-f` 选项。确实想将修复应用到源代码文件中，在 `2to3 -f fixname -w filename` 中添加 `-w` 选项。这是一个示例：

```diff

--- example.py (original)
+++ example.py (refactored)

+for i in range(10):
     print i, 2*i
```

`-f` 选项的对应项是 `-x` 选项。如果你使用 `2to3 -x fixname`，它将应用除你用 `-x` 选项列出的之外的所有修复器。虽然可以指示 `2to3` 修复一切并覆盖你的所有文件，但在实践中最好避免这样做。请记住，代码转换是一门精确的科学， `2to3` 并不总是能做“正确的事”。以有方法的方法处理代码迁移总比祈祷保佑要好。

`2to3` 有几个可能实用的额外选项。`-v` 选项启用详细模式，打印可能对调试有用的额外信息。`-p` 选项告诉 `2to3` 你已经在代码中使用了 `print` 语句且它不应该被转换（通过 `__future__.import_print` 启用）。

# 迁移策略

这是一个将 Python 2 代码迁移到 Python 3 的实用策略。再次，采用有方法的方法迁移比一次性完成要好。

- 1. 确保你的代码有足够的单元测试，并在 Python 2 下通过所有测试。

- 2. 将代码迁移到 Python 2.6 并确保所有测试通过。

- 3. 开启 `-z` 选项到 Python 3。处理所有警告并确保程序运行（如果你正确执行，你的代码在 Python 2.5 及更早版本中仍然工作）。你只是清理了程序中积累的杂质（如果不这样做的话）。

- 4. 备份你的代码（不言而喻）。

- 5. 将单元测试迁移到 Python 3 并确保环境正常。单独的单元测试将失败（因为你还没有迁移任何代码）。

- 6. 使用 `2to3` 将程序本身转换为 Python 3。运行单元测试并解决出现的所有问题。有很多不同的方法。如果你足够幸运，可以告诉 `2to3` 修复一切并看看发生了什么。如果你更谨慎，可能会先让 `2to3` 修复明显的内容（print 语句、模块名等），然后以碎片化的方式处理剩余问题。在此过程结束时，你的代码应该通过所有单元测试并以以前的方式运行。

理论上，可以结构化代码使其在 Python 2.6 中运行并在无需干预的情况下自动转换为 3。然而，这需要遵循现代编码规范——至少你需要确保 Python 2.6 中没有警告。

# 同时支持 Python 2 和 3

迁移到 Python 3 的最后一个问题是否存在一个可以在 Python 2 和 3 上无需修改即可运行代码库。虽然在某些情况下这是可能的，但生成的代码可能会变成一团糟。例如，你必须避免所有的 `print` 语句并确保所有语句以避免异常（从 `sys.exc_info()` 中提取）。因此，如果你必须维护在 Python 2 和 3 上运行的代码，最好的办法是让代码尽可能简洁并在 Python 2.6 下运行，确保拥有单元测试套，并尝试实现自动转换。
