### 为什么性能如此重要？

如果你曾坐等电脑完成某项任务（一边敲击桌子，一边咒骂，一边心想“为什么要花这么长时间？”），你就知道拥有一个快速且调优良好的计算机系统是多么重要了。尽管并不是所有的性能问题都能轻松解决，但理解系统变慢的原因意味着：你可以从软件层面修复问题、升级缓慢的硬件，还是干脆把整台电脑扔出窗外。幸运的是，大多数操作系统——特别是 Linux——都提供了工具来查明机器运行缓慢的原因。通过使用一些基础工具，你可以确定系统在何何处变慢了，以及哪些部分运行效率低下。

虽然系统缓慢对终端用户来说特别令人烦恼，但对于开发者来说，性能调优应用程序有一个更重要的理由：高效的应用程序可以在更多系统上运行。如果你编写了运行缓慢且需要高性能电脑的程序，你就排除了那些拥有较慢电脑的客户，从而缩小了潜在用户群。此外，调优良好的应用程序可以被更多客户使用；当潜在客户在两个功能相似的不同应用程序之间做出选择时，他们通常会选择运行更快或效率更高的那一个。最后，一个生命周期较长的应用程序可能会经过几轮优化以应对不同的客户需求，因此知道如何追踪性能问题是关重要的。

如果你是一名系统管理员，你就有责任向系统用户确保其运行在适当的性能水平。如果系统运行缓慢，用户就会抱怨。如果你能快速确定问题并修复它，他们就会停止抱怨。作为额外的回报，如果你调优了应用程序或操作系统（从而避免了他们购买新硬件），你就能让公司的财务算师们感到高兴。了解如何有效地使用性能工具，可能意味着在解决性能问题时，是花费几天时间还是只花几个小时时间。

### Linux：优势与劣势

如果你使用 Linux、维护 Linux 并在其上进行开发，那么你处于一种奇特但良好的境地。你能够以以前所未有的权限访问源代码、开发者和邮件列表，这些邮件列表通常会在设计决策做出后记录其背景。Linux 是一个寻找和修复性能问题的绝佳环境。这与专有环境形成了对比，在专有环境中，很难直接接触软件开发者，可能很难找到关于大多数设计决策的讨论，而且几乎无法访问源代码。除了这种高效的环境外，Linux 还拥有强大的性能工具，让你能够发现并修复性能问题。这些工具可以与其专有系统的对手媲美。

尽管有这些令人印象深刻的优点，Linux 生态系统仍然面临需要克服的挑战。Linux 性能工具散落在各地。不同目标的群体开发这些工具，导致工具并不集中在某处。某些工具包含在标准的 Linux 发行版中，如 Red Hat、SUSE 和 Debian；另一些则散落在互联网各处。如果你试图解决性能问题，你首先必须知道你需要的工具确实存在，然后弄清楚在哪里可以找到它们。由于你还需要学会如何联合使用这些工具来确定哪里出了问题，这可能是一门艺术，但随着经验的增加会变得更容易。尽管大多数通用策略都可以记录下来，但 Linux 并没有任何指南告诉你如何聚合性能工具来实际解决问题。大多数工具或子系统都有关于如何调优特定子系统的信息，但没有关于如何将其与其他工具配合使用的。许多性能问题跨越了系统的多个领域，除非你知道如何集体使用这些工具，否则你无法解决问题。

### 为什么要学习使用性能工具？

为什么有人应该投入精力去调优系统或应用程序？

- 调优良好的系统可以用更少的资源完成更多工作。
- 调优良好的应用程序可以在旧硬件上运行。
- 调优良好的桌面系统可以为用户节省时间。
- 调优良好的服务器为更多用户提供更高的服务质量。

如果你知道如何有效地诊断性能问题，你就可以采取针对性的方法来解决问题，而不是盲目尝试并希望有效。如果你是一名应用程序开发者，这意味着你可以快速确定是哪部分代码导致了问题。如果你是一名系统管理员，这意味着你可以弄清楚系统的哪个部分需要调优或升级，而无需浪费时间去尝试不同的解决方案。如果你是终端用户，你可以找出哪些应用程序在卡顿，并向开发者报告问题（或者在必要时更新你的硬件）。

Linux 正处于一个十字路口。大部分功能已经完成。Linux 及其应用程序的下一个演进步骤是经过调优来竞争并超越其他操作系统的性能。某些性能优化（例如显著提升线程性能的 `NativeIX Thread Library` 库，以及改进应用程序启动时间的 `objectlinking`）刚刚开始集成到 Linux 中。Linux 亟待改进。

### 我可以进行性能调优吗？

性能调优最棒的一点是，你不需要了解整个应用程序或系统的细节就能有效地修复性能问题。性能调优需要与典型的应用程序开发者互补的技能集。

你需要敏锐且执着。寻找和消除性能问题需要的比程序员更像侦探。当你开始时，性能可能非常糟糕。但一旦你追踪到原因并将其根除，如果你足够好，系统随后就会快一倍。*搞定！*

要到达最后，你必须理解强大但有时令人困惑的 Linux 性能工具世界。这需要努力，但最终是值得的。这些工具可以向你展示你从未想过的应用程序和系统的方面。

# 第 1 章 性能查找技巧

在没有远见规划的情况下解决问题是痛苦的。你会浪费时间，并不断感到于问题原因反复从指间溜走。通过遵循正确的程序，你可以将一次沮丧的性能查找转化为一个有趣的侦探故事。每一条信息都让你更接近真魁祸首。人并不总是值得信赖，证据将是你唯一的朋友。当你调查问题时，它会经历不同常的转折，你在查找初期发现的信息可能就是你最终解决问题的关键。最棒的部分是，当你最终抓住“坏人”并解决问题时，你会感到一种肾上腺素飙升的快感和成就感。

如果你从未调查过性能问题，起步可能会无所适从。通过遵循一些显而易见和不易的技巧，你可以节省时间。本章的目标是为你提供帮助查找性能问题的系列技巧和指南。这些都是从浪费时间换来的深刻教训。这些技巧将帮助你快速解决性能问题。

阅读本章后，你应该：

- 避免重复他人的工作
- 避免重复自己的工作
- 避免因收集信息产生误导
- 创建一份关于你调查的有用参考文档

尽管没有任何性能调查是完美的（你几乎总是说“如果我早点想到就好了”），但这些技巧可以帮你避免性能调查中的常见错误。

## 1.1 通用技巧

### 1.1.1. 详尽记录（保存一切）

在调查性能问题时，你可能做的最重要的事情就是记录你看到的一切。一组组织良好的笔记允许你比较配置如何影响性能。虽然可以重新测试，但测试配置通常是非常耗时的。

- 记录硬件/软件——这涉及记录硬件（内存大小、CPU 类型、网络、磁盘）以及软件环境（操作系统和版本）。这些信息早期看起来可能无关，但在追踪问题时，你可能会更改配置。保存 `cat /proc/pci`、`dmesg` 和 `uname -a` 的输出。
- 保存并组织性能结果——这允许你在运行很久之后回顾结果。保持笔记有序并避免重复更为高效。
- 记录命令——当你运行性能工具时，你经常会创建测量你感兴趣区域的复杂命令。如果你想重新运行测试，或在不同的应用程序上运行，重现这些命令可能会非常麻烦且难以完成。最好记录下使用的具体内容。这样你可以在未来的测试中重现准确的命令行，回顾过去的结果时也能看到具体测量了什么。Linux 命令 `script`（在第 8 章“实用工具：性能工具助手”中详细描述）或从终端“剪切和粘贴”都是实现此操作的好方法。

## 1.2. 性能调查概述

本节概述了在开始性能调查时需要的一系列基本步骤。由于最终目标是修复问题，最好的主意是在接触性能工具之前先对问题进行研究。遵循特定的方案是解决问题且不浪费宝贵时间的有效方法。

### 1.2.1. 确定指标、基准和目标

性能调查的第一步是确定当前的性能，并弄清楚需要改进多少。如果你的系统性能低于预期，你可能会认为值得花时间进行调查。如果系统性能接近其峰值，那么可能就不需要调查了。确定性能值允许你设定合理的性能预期，并为你提供一个性能目标，以便你知道何时停止优化。你总是可以对系统进行微调，但如果没有性能目标，你可能会浪费大量时间去挤榨那额外的百分之几性能，尽管你可能并不需要它。

#### 1.2.1.1 建立指标

为了确定你已完成，你必须为系统性能创建一个或使用一个已建立的指标。例如，如果你正在优化 Web 服务器，你会选择“每秒处理的 Web 请求数”。如果你没有一个衡量性能的目标，在调优系统时，几乎无法判断你是否取得了任何进展。

#### 1.2.1.2 建立基准

在你确定正在衡量特定系统或应用程序的性能后，确定当前的性能水平至关重要。在任何调优或优化之前运行应用程序并记录其性能；这被称为基准值，它是调查的起点。

#### 1.2.1.3 建立目标

在为性能选择指标和基准后，选择一个目标也是至关重要的。这个目标将引导你走向性能搜索的终点。你可以无限地微调系统，并且总是可以通过投入更多精力让它变得好一点。如果你选定了目标，就会知道何时结束。选择一个合理的目标，以下是起点：

- **通过相似配置查找结果**——这是一种理想情况。如果你能找到性能更好的相似系统，不仅可以为你的系统选择目标，还可以通过比较配置差异来辅助工作。将另一个系统作为参考在调查问题时非常有用。
- **查找行业基准结果**——许多网站都比较各个系统的基准测试。某些基准只能通过努力实现。然而，许多基准系统都有特定的配置结果，这些配置可以帮助你调优系统。
- **使用不同的操作系统或应用程序**——这可能是在你的系统上运行不同的应用程序。例如，如果你有两个 Web 服务器，其中一个运行较慢，尝试运行另一个看看性能是否更好。如果系统在任何一种情况下性能更好，你就知道原始配置有改进空间。

## 1.3. 章节总结

性能调查应该是一个令人满意且兴奋的过程。如果你有一个良好的方法来研究和分析，性能调查将多次得到回报。首先，确定其他人员是否存在类似的问题；如果是，尝试他们的解决方案。为你的调查创建一个合理的指标和目标；指标让你知道何时完成。自动化性能测试。确保保存测试结果并记录任何与问题相关的信息。最后，定期查看记录以发现可能遗漏的信息。如果你遵循这些指南，你将有一个清晰的目标和清晰的调查程序。

本章为性能调查提供了背景，后续章节涵盖了 Linux 性能工具。学习如何使用这些工具、它们可以提供什么类型的信息，以及如何结合使用它们查找特定系统上的性能问题。

# 第 2 章 性能工具：系统 CPU

本章概述了系统性能工具。这些工具是跟踪性能问题的第一道防线。它们可以向你展示系统的整体性能以及哪些区域出现了异常。本章讨论了这些工具可以测量的统计数据以及如何使用单个工具收集这些数据。阅读本章后，你应该：

- 理解系统性能的基本指标，包括 CPU 使用率
- 理解哪些工具可以检索这些系统性能指标

## 2.1 CPU 性能统计

每个系统性能工具都提供了提取统计数据的不同方法。尽管没有工具显示所有统计数据，但某些工具会显示相同的统计数据。与其每个工具都多次描述统计数据的含义，我们在工具显示之前只进行一次审查。

### 2.1.1. 运行队列统计

在 Linux 中，进程可以是就绪的（runnable）或阻塞等待事件完成的。阻塞进程可能在等待 I/O 设备的数据或系统调的结果。如果一个进程是就绪的，意味着它正在与其他就绪进程竞争 CPU。就绪进程并不一定正在使用 CPU，但当 Linux 调度器决定运行哪个进程时，它会从就绪进程列表中选择。当这些进程处于就绪但等待使用处理器时，它们形成了一个所谓的运行队列（run queue）。队列越长，等待的进程就越多。

性能工具通常显示就绪进程的数量和等待 I/O 的阻塞进程的数量。另一个常见的系统统计数据是平均负载（load average）。系统的负载是就绪和阻塞进程的总数。例如，如果有两个进程正在运行，三个可运行，那么系统的负载就是五。平均负载是给定时间内的负载量。通常，平均负载包括 1 分钟、5 分钟和 15 分钟。这允许你看到负载随时间的变化。

### 2.1.2. 上下文切换



大多数处理器一次只能运行一个进程。某些处理器（如超线程处理器）实际上可以同时运行多个任务，Linux 将它们视为多个单线程处理器。为了创建一个进程同时运行多个任务的幻象，Linux 内核在不同进程之间不断切换。进程之间的切换被称为上下文切换（`context switch`），当切换发生时，CPU 保存旧进程的所有上下文信息并检索新进程的所有上下文信息。上下文包含了 Linux 为每个进程跟踪的大量信息，包括指令指针在哪里、分配了哪些内存以及进程打开了哪些文件。这些切换可能涉及大量信息的移动，上下文切换的开销很大。如果可能，最好减少上下文切换次数。

为了避免上下文切换，了解它们是如何发生的至关重要。首先，上下文切换可能源于内核调度。为了保证每个进程获得公平的处理器时间，内核会定期中断，并在每次周期性中断发生时，如果合适，调度器会启动另一个进程而不是当前进程。你的系统可能会根据架构和内核定时器每秒产生中断。检查中断频率的一种方法是使用 `/proc/interrupts` 来确定一段时间内发生的中断次数。这在列表 2.1 中所示。

#### 3.1.1. 内存子系统与性能

在现代处理器中，从内存子系统中保存和检索信息通常需要由 CPU 执行代码并操纵这些信息。CPU 通常花费大量的空闲时间，等待从内存中检索指令和数据，然后对其进行执行或操作。处理器具有不同级别的缓存，以补偿缓慢的内存性能。如 `profile` 等工具可以显示各种处理器缓存缺失发生的位置。

#### 3.1.2. 内存子系统（虚拟内存）

任何 Linux 系统都具有一定量的 RAM 或物理内存。在对这些物理内存进行地址时，Linux 将其划分为内存块或“页”（`pages`）。在分配或移动时，Linux 操作的是页大小的块，而不是单个字节。在报告某些内存统计数据时，Linux 内核报告每秒的页数，该值取决于其运行的架构。代码列表 3.1 创建了一个小型应用程序，显示当前架构下每页的字节数。

##### 代码列表 3.1：

```c
#include <unistd.h>
int main(int argc, char *argv[])
{
    printf("System page size: %d\n", getpagesize());
}
```

在 IA32 架构上，页大小为 4KB。在某些情况下，页大小的内存块会导致过大的开销，内核使用更大的块来管理内存，被称为 `HugePages`（大页）。这些页比 4KB 大 2048KB，并极大减少了管理大量内存的开销。像 Oracle 这样的应用程序使用这些大页来管理内存。如果 `HugePages` 没有被数据完全填充，可能会浪费大量的内存。一个半满普通页浪费 2KB 内存，而一个半满 `HugePage` 可以浪费 1,024KB 内存。

Linux 内核可以散布这些物理页，并向应用程序呈现一个布局良好的虚拟内存空间。

##### 3.1.2.1 Swap（物理内存不足）

所有系统都具有一定量的 RAM 或物理内存。Linux 内核允许应用程序在所需内存超过可用内存时使用硬盘作为临时内存来运行。这个硬盘被称为交换空间（`swap space`）。虽然交换是处理进程的一种极方法，但它真的非常慢——比物理内存慢 1000 倍。它可以帮助确定你的系统使用了多少交换空间。

- 对应用程序进行性能分析（Profile），以确定哪些源代码行和函数耗时最长。

## 4.1. 进程性能统计

分析应用程序性能的工具多种多样，并且在 Unix 早期就以各种形式存在了。理解应用程序如何与操作系统、CPU 和内存系统进行交互，对于理解其性能至关重要。大多数应用程序并不是自包含的，它们会调用 Linux 内核和不同的库。对 Linux 内核的调用（或系统调用）可能像“我的 PID”一样简单，也像“从磁盘读取 12 块数据”一样复杂。不同的系统会有不同的性能影响。因此，库调用可能像内存分配一样简单，也像图形创建一样复杂。

### 4.1.1. 内核时间与用户时间

应用程序消耗时间最基础的划分是内核时间和用户时间。内核时间是消耗在应用程序代码或库代码中的时间量。Linux 拥有如 `top` 和 `ps` 等工具，可以（适当地地）启用应用程序是将时间花在应用程序代码还是内核代码上。它还拥有如 `profile` 和 `strace` 等命令，允许你跟踪代表进程执行了哪些内核调用，以及这些调用花费了多久才完成。

### 4.1.2. 库时间与应用程序时间

任何即使只有微小复杂性的应用程序都依赖系统库来执行复杂操作。这些库可能会导致性能问题，因此能够看到应用程序在特定库上花费了多少时间是非常重要的。虽然直接修改库的源代码来修复问题并不总是可行，但可能更改应用程序代码调用不同或更少的库函数。`ltrace` 命令和 `profile` 工具集提供了一种在应用程序使用库时分析库性能的方法。Linux 加载器 `ld` 内内置的工具可以帮助你确定使用许多库如何减慢应用程序的启动时间。

### 4.1.3. 细分应用程序时间

当已知应用程序是瓶颈时，Linux 提供了工具允许你对应用程序进行性能分析，以确定时间在应用程序内部消耗在哪里。如 `gprof` 和 `profile` 等工具可以生成应用程序的分析报告，精确指出哪行源代码导致了大量时间的消耗。

## 6.1. 磁盘 I/O 简介



在深入研究性能工具之前，有必要了解 Linux I/O 系统的结构。大多数现代 Linux 系统有一个或多个磁盘驱动器。如果它们是 IDE 驱动器，通常命名为 `hda`、`hdb`、`hdc` 等；而 SCSI 驱动器通常命名为 `sda`、`sdb`、`sdc` 等。磁盘通常被分为多个分区，分区设备是通过在基础设备名称后添加分区编号生成的。例如，系统中的第一个 IDE 硬盘通常标记为 `/dev/hda2`。每个单独的分区通常包含文件系统或交换分区。这些分区挂载到 Linux 根文件系统中，如 `/etc/fstab` 中指定的所示。这些挂载的文件系统包含了应用程序读取和写入的文件。

当应用程序执行读或写操作时，Linux 内核可能在其缓存中存储了文件的副本，或者直接返回请求的信息。如果 Linux 内核在内存中没有该数据的副本，则会访问磁盘。请求被放入 I/O 队列，如果磁盘当前忙碌，请求将等待磁盘可用，然后被处理。

## 6.3. 缺失了什么？

Linux 上的磁盘 I/O 工具提供了有关特定磁盘或分区的利用率信息。遗憾的是，在您确定某个特定磁盘是瓶颈后，没有任何工具可以查查出是哪个进程导致了所有的 I/O 操作。

通常，系统管理员对哪些应用程序在使用磁盘有相当的了解，但并不总是如此。很多时候，例如，我正在使用 Linux 系统时，磁盘开始无缘无故地剧烈作响。我通常可以运行 `top` 并寻找可能导致问题的进程。然而，通过排除我认为没有在进行 I/O 的进程，我通常能找到罪魁祸首。这需要对各种应用程序应该执行的功能有所了解。这种方法也容易出错，因为对哪些进程导致问题的推测可能是错误的。此外，对于拥有许多用户或运行多个应用程序的系统，确定哪个应用程序可能导致问题并不总是可行或容易的。其他 Unix 系统支持 `ps` 命令的 `inblk` 和 `cublk` 参数，这些参数可以显示代表特定进程发出的磁盘 I/O 流量。目前，Linux 内核并不跟踪进程的 I/O，因此 `ps` 工具没有办法获取这些信息。

你可以使用 `lsof` 来确定哪些进程正在访问特定分区上的文件。在列出所有访问文件的 PID 后，你可以使用 `strace` 挂接到每个 PID 上，并查出哪一个正在进行大量的 I/O。虽然这种方法有效，但它真的是一个“治标不治本”的方案，因为访问分区的进程可能很多，挂载并分析每个进程的系统调用非常耗时。这还可能会漏掉短生命周期进程，并在它们被追踪时导致进程运行变得无法接受地缓慢。

这是 Linux 内核可以改进的领域。快速跟踪产生 I/O 的进程的能力将允许更快地诊断与 I/O 性能相关的问题。

### 9.4.1. 是否 CPU 密集？

使用 `top` 或 `mpstat` 确定时间花费在哪里。如果整个系统在空闲和等待模式下的时间小于 5%，则系统是 CPU 密集的。跳转到第 9.4.3。否则，跳转到 9.4.2。

### 9.4.2. 是否单处理器 CPU 密集？

虽然整个系统可能不是 CPU 密集，但在对称多处理 (SMP) 或超线程系统中，单个处理器可能是 CPU 密集。

使用 `top` 或 `mpstat` 确定单个 CPU 在空闲和等待模式下的时间是否小于 5%。如果是，则更多 CPU 是 CPU 密集；在这种情况下，跳转到 9.4.4。

否则，CPU 是 CPU 密集。跳转到 9.4。

### 9.4.3. 是否一个或多个进程使用了大部分系统 CPU？

下一步是确定某个特定的应用程序或应用程序组在使用 CPU。最简单的方法是运行 `top`。默认情况下，`top` 按使用 CPU 的情况降序排列。`top` 报告的进程 CPU 使用率为用户时间和系统时间的和。例如，如果应用程序在用户空间花费了 20% 的 CPU，在系统空间花费了 30%，`top` 将报告该进程消耗了 50% 的 CPU。汇总所有时间。如果这显著小于系统整体比例，则是内核在执行非应用程序的工作。

否则，跳转到 9.4.3（上下文建议 9.4.4，但保留逻辑）或跳转到识别进程的位置。

### 9.4.4. 是否一个或多个进程使用了大部分系统 CPU？

下一步是确定某个特定的应用程序或应用程序组在使用系统 CPU。最简单的方法是运行 `top`。默认情况下，`top` 按使用 CPU 的情况降序排列。`top` 报告的进程 CPU 使用率为用户时间和系统时间的和。例如，如果应用程序在用户空间花费了 20% 的 CPU，在系统空间花费了 30%，`top` 将报告该进程消耗了 50% 的 CPU。汇总所有时间。如果这显著小于系统整体比例，则是内核在执行非应用程序的工作。

否则，跳转到 9.4.3（上下文建议 9.4.5）或跳转到识别进程的位置。

### 9.6.1. 内核内存使用是否在增加？

在追踪系统内存使用情况时，你首先必须确定内核本身正在分配内存。运行 `slabtop` 查看内核内存总数是否在增加。如果正在增加，跳转到第 9.6.2 节。

### 9.6.2. 内核在使用什么类型的内存？

如果内核内存使用正在增加，再次运行 `slabtop` 以确定内核正在分配什么类型的内存。slab 的名称可以提供有关为什么要分配内存的某些线索。通过网络搜索，在内核源码中搜索 slab 名称并确定它被用于哪个子系统，可能会清楚分配的原因。当你确定了哪个子系统分配了所有这些内存后，尝试调整该特定子系统消耗的最大内存量，或者减少该子系统的使用量。

### 9.6.3. 特定进程的驻留集（Resident Set）是否在增加？

接下来，你可以使用 `top` 或 `ps` 查看特定进程的驻留集大小（`rss`）是否在增加。在 `top` 的输出字段中添加 `rss` 并按使用的内存类型进行排序很容易的。如果特定进程正在不断增加内存使用，由于该应用程序，请转到第 9.6.6 节。如果没有特定进程在使用更多内存，转到第 9.6.4 节。

### 9.6.4. 共享内存使用是否在增加？

使用 `ipcs` 确定是否在使用共享内存。如果是，进入第 9.6.5 节以确定哪些进程在使用这些内存。否则，系统可能存在本文未涵盖的内存泄漏。进入第 9.9 节。

### 9.6.5. 哪些进程在使用共享内存？

使用 `ipcs` 确定哪些进程在使用共享内存。识别出使用共享内存的进程后，调查各个进程以确定每个进程使用内存的原因。例如，在应用程序的源码中查找对 `shmget` 和 `shmat`（用于挂载）的调用。阅读应用程序文档并寻找可以减少共享内存使用的选项。

要减少共享内存使用，进入第 9.9 节。

## 10.1. 密集型应用程序

在本章中，我们调查了一个密集型应用程序。优化密集型应用程序是非常重要的，因为它是最常见的问题之一。它通常是经过调优应用程序的最后边界。当磁盘和网络瓶颈被消除后，应用程序就会变得密集。此外，购买更快的磁盘或更多内存通常比升级 CPU 更容易，因此如果一个进程是密集型的，追踪并修复 CPU 性能问题是一项重要的技能，而不是直接买新系统。

## 10.2. 识别问题

性能猎寻的第一步是识别要调查的问题。在本例中，我选择调查在使用 `GIMP`（一个开源图像处理程序）时出现的一个性能问题。`GIMP` 可以切割和处理图像的各个方面，但它还有一套强大的过滤器可以各种方式扭曲和改变图像。这些过滤器根据复杂的算法改变图像。通常，这些过滤器完成需要很长时间，并且非常消耗 CPU。其中一个过滤器是 Van Gogh (`LIC`)，它接收输入图像并对其修改，使其看起来像梵高风格的绘画。这个过滤器完成所需的时间特别长。完成时间取决于图像的大小、机器 CPU 的速度以及传递给过滤器的参数值。

## 10.3. 寻找基准/设定目标

任何性能调优的第一步都是确定问题的当前状态。以 `GIMP` 过滤器为例，我们需要弄清楚运行特定图像需要多少时间。这就是我们的基准时间。一旦有了这个基准，我们就可以尝试进行优化并看看它是否能缩短执行时间。有时，测量某个操作耗时是比较困难的。这不像使用秒表那么简单，因为在我们的进程 CPU 密集型任务运行时，操作系统正在调度其他任务。除了 CPU 密集型任务外还有其他任务在运行，挂钟时间（wall-clock time）可能会大于进程实际使用的 CPU 时间。在这种情况下，我们很幸运；通过在过滤器运行时查看 `top` 命令，我们可以看到 `lic` 进程占用了大部分 CPU 使用率，如列表 10.1 所示。

## 10.4. 为性能调优配置应用程序

我们调查的下一步是通过带符号（symbols）的方式重新编译应用程序，为性能调优做好准备。符号允许性能工具（如 `oprofile`）调查哪些函数和源代码行导致了所花费的 CPU 时间。

对于 `GIMP`，我们从其网站下载 `GIMP` tar 包，然后对其进行重新编译。在 `GIMP` 和许多开源软件的情况下，重新编译的第一步是运行 `configure` 命令，它生成用于构建的 `makefile`。`configure` 命令会将任何 `CFLAGS` 环境变量传递给 `makefile`。在这种情况下，由于我们希望构建带符号的 `GIMP`，我们在 `makefile` 中将 `CFLAGS` 变量设置为 `-g`。此命令在列表 10.3 所示。

### Listing 10.3.

```
[root@localhost gimp-2.0] env CFLAGS=-g ./configure
```

然后我们运行 `make install` 安装带符号的 `GIMP` 版本，当我们运行这个版本时，性能工具将告诉我们时间花费在哪里。

## 10.9. 增加图像缓存

相关网站解释说 GIMP 管理图像的方式略微反直觉。GIMP 并不是将图像存储在一个大数组中，而是将图像分解一系列瓦片（tiles）。这些瓦片的大小为 64x64。当用户想要访问图像的特定像素时，GIMP 会加载相应的瓦片，找到并返回像素值。每次获取像素的调用都可能缓慢。如果对每个像素重复此过程，将极大降低性能，因为 GIMP 每次都会重新加载瓦片，而不是使用缓存值。幸运的是，GIMP 提供了一种方法来缓存旧瓦片并在每次使用缓存值。这应该会提高性能。GIMP 提供的缓存数量可以通过使用 `gimp_tile_cache_ntiles` 调用来控制。该调用目前在 `lic` 内部使用，并将缓存设置为图像宽度的两倍。

尽管这看起来缓存已经足够了，但 GIMP 可能还需要更多。测试此点的简单方法是将缓存增加到一个非常大的值，看看性能是否会提高。因此，在这种情况下，我们将缓存量增加到正常用量的 10 倍。在增加此值并重新运行过滤器后，我们得到了 2 分 40 秒的时间。这虽然增加了 6 秒，但我们还没有达到 2 分 30 秒的目标。这说明我们必须从其他领域寻找提高性能的方法。

## 10.10. 碰到了（瓦片）瓶颈

除了使用瓦片缓存外，网页还提供了一种提高 `get_pixel` 性能的更好方法。通过直接访问像素信息（而不调用 `gimp_pixel_rgn_get_pixel`），可以大幅提高像素访问的性能。

GIMP 可以为过滤器程序员提供直接访问图像瓦片的方法。这样过滤器就可以像访问数据数组一样访问图像数据，而无需调用 GIMP 库。然而，有一个陷阱：当你直接访问像素数据时，它仅针对当前瓦片。GIMP 会遍历图像中的所有瓦片，让你最终能够访问图像中的所有像素，但你无法同时访问所有像素。你只能查看单个瓦片的像素，这与 `lic` 访问数据的方式不兼容。当其过滤器在特定位置生成新像素时，它根据周围像素的值计算新值。因此，在瓦片边缘生成新像素时，`lic` 过滤器需要周围所有像素的像素。不幸的是，这些像素可能在图像的上一个瓦片或下一个瓦片上。由于这些像素信息可用，图像过滤器无法使用这种优化访问方法工作。

## 10.12. 验证正确性？

在优化显著减少过滤器运行时间后，有必要验证生成的图像是否相同。通过加载原始图像并与生成的图像进行对比，使用 GIMP 计算两者的差异。如果原始图像和优化后的图像相同，则所有像素都应为 0（黑色）。然而，视觉上看起来是黑色的，但在仔细检查（使用颜色选择器）后，某些像素是非零的。这意味着原始和优化后的图像是不相同的。这通常令人担心，因为这可能表明优化改变了过滤器的行为。然而，对过滤器源码的仔细检查显示，在运行过滤器之前使用了随机噪声对图像进行了抖动处理。由于两个图像之间的差异非常微小，我们可以假设优化没有引入任何问题。

## 10.13. 下一步工作

我们已经超过了 `lic` 过滤器性能提升 10% 的目标，从这个意义上说，我们已经完成了优化过程。然而，如果我们想继续提高性能，就必须在使用新的优化方案时对过滤器重新进行性能分析（`reprofile`）。在每次应用性能优化后，对应用程序进行重新性能分析是非常重要的，在继续优化应用程序时不要依赖旧的分析数据。应用程序的运行时行为在每次优化后都可能发生巨大变化。如果你在每次优化后都不进行性能分析，就可能会面临追踪一个不再存在的性能问题的风险。

在本章中，我们确定了为什么一个应用程序（GIMP 过滤器 `lic`）是 CPU 密集型的。我们确定了应用程序的基准运行时，设定了优化目标，并保存了一张参考镜像以验证我们的优化没有改变应用程序的行为。我们使用了 Linux CPU 性能工具（`oprofile` 和 `ltrace`）来调查应用程序为什么是 CPU 密集型的。然后，我们使用 `gdb` 来理解应用程序的工作原理，并想出不同的优化方法。我们尝试了几种不同的优化，但最终，我们选择了经典的“增加内存使用以减少 CPU 使用”的性能权衡方案。

我们超越了优化目标，并验证了我们的优化没有改变应用程序的输出。

## 11.9. 寻找时间差异

现在我们已经缩小了哪些函数负责创建菜单的范围，我们想要找出哪些部分占据了所有时间，哪些部分相对轻量。一种在不使用任何性能工具的情况下实现这一点的绝方法是直接禁用某些代码段并观察性能的变化。尽管这会导致 `nautilus` 运行异常，但它至少能指示哪些函数消耗了所有时间。

我们首先必须建立一个基准，因为我们正在测试的二进制文件编译时使用的标记与 Red Hat 提供的不同。我们像以前一样对脚本进行计时。在这种情况下，在我们自己编译的版本上，运行 100 次迭代需要 30.5 秒。接下来，我们注释掉 `eel_pop_up_context_menu` 调用。这显示了 `nautilus` 检测到鼠标点击并决定需要创建上下文菜单花费了多少时间。即使我们完全优化了这些函数中的所有命令，我们的运行速度也不会比这快。在这种情况下，运行所有 100 次迭代需要 7.6 秒。接下来，我们注释掉被认为耗时最长的 `bonobo_window_add_popup`。如果我们注释掉 `bonobo_window_add_popup`，完成 100 次迭代需要 21.9 秒。这意味着如果我们优化掉 `bonobo_window_add_popup`，可以从总运行中节省约 8 秒，改进了近 25%。

## 11.10. 尝试可能的解决方案

因此，正如我们所看到的，`bonobo_window_add_popup` 是一个昂贵的函数，每次我们创建弹出菜单时都调用它。如果我们反复使用相同的参数调用它，可能缓存它初始调用返回的值，并使用它代替调用那个昂贵的函数。列表 11.19 显示了实现此目的重写函数示例。

### 列表 11.19。

```c
void
fm_directory_view_pop_up_background_context_menu
(FMDirectoryView *view,
GdkButton *event)
{
 /* Primitive Cache */
  static FMDirectoryView *old_view = NULL;
  static GtkMenu *old_menu = NULL;

  g_assert (FM_IS_DIRECTORY_VIEW (view));

  /* Make the context menu items not flash as they update to
  proper disabled;
   * states. by forcing menus to update now.
   */
  if ((old_view != view) ||
      view->menu_states_untrustworthy)
  {
    update_menu_if_pending(view);
    old_view = view;
    old_menu = create_popup_menu(view,
      FM_DIRECTORY_VIEW_POPUP_PATH_BACKGROUND);
  }

  eel_pop_up_context_menu (old_menu,
    EEL_DEFAULT_POPUP_MENU_DISPLACEMENT,
    EEL_DEFAULT_POPUP_MENU_DISPLACEMENT,
    event);
}
```

在这种情况下，我们记住了上次生成的菜单。如果我们处于同一个视图中，并且认为该视图的菜单没有发生变化，我们就直接使用用过的菜单，而不是创建一个新的。这并不是一种复杂的技巧，如果用户没有在目录 1 中打开弹出菜单，而在目录 2 中打开，它就会失效；如果目录 1 中打开了弹出菜单，`nautilus` 会创建一个。在打开菜单时，第一个检查是查看缓存中是否已经有了菜单。如果缓存的菜单可以查看，则直接使用；否则，可以创建一个。这对于特殊目录特别有用，例如桌面、计算机或主目录，用户可能会多次打开弹出菜单。在应用此建议的解决方案并配合 100ms 的超时时间后，时间已下降到 24.0 秒。这是 20% 的性能提升，接近于完全不创建菜单时能获得的提升（21 秒）。在各种目录中创建弹出菜单的方法是有效的。

## 12.7. 模拟解决方案

`strace` 揭的信息显示 `prelink` 花了大量时间尝试打开和分析无法预链接的二进制文件。测试链接二进制文件缓存是否能提高 `prelink` 性能的最佳方法是修改 `prelink`，将其所有链接二进制文件添加到初始缓存中。遗憾的是，向这些“未链接”二进制文件添加代码可能是一个复杂的过程，涉及大量关于 `prelink` 内部的知识。一种更简单的方法是用已知的链接二进制文件替换所有链接的二进制文件来模拟缓存。这会导致先先链接的二进制文件在运行时被忽略。这正是如果我们拥有缓存时会发生的情况，因此我们可以用它来估计如果 `prelink` 缓存并忽略链接二进制文件，我们将看到的性能提升。

为了开始实验，我们将 `/usr/bin/` 中的所有文件复制到沙箱目录并在该目录上运行 `prelink`。该目录包含了二进制文件、shell 和无法进行预链接的库。然后我们在沙箱目录上运行 `prelink`，让它创建一个新缓存而不是系统缓存。这如列表 12.5 所示。

列表 12.5。


- 理解 Linux 作为性能调查平台的优势

## 13.1. Linux 工具的现状

本书将介绍当前的 Linux 性能工具、如何单独使用它们，以及如何结合使用它们来解决性能问题。与 Linux 的各个方面一样，这些性能工具也在不断演进，因此在调查问题时，查看性能工具的 `man` 页（手动帮助页）或文档以确定其用法是否发生变化总是一个好主意。性能工具的基本功能很少改变，但通常会添加新特性，因此查看特定工具的最新发布说明和文档是有帮助的。

## 13.2. Linux 还需要哪些工具？

在我们遍历 Linux 工具时，我们发现整体性能调查功能存在一些缺陷。这些缺陷是内核局限性的结果，而另一些则仅仅是因为没有人编写工具来解决这些问题。然而，填补这些缺陷将使得追踪和修复 Linux 问题变得容易得多。

### 13.2.1. 缺陷 1：性能统计数据是分散的

一个显而易见的缺陷是 Linux 没有工具能为特定进程提供相关的性能统计数据。在原始 UNIX 中，`ps` 是为了填补这个缺陷，而在 Linux 上，它相当良好，但没有涵盖其他商业实现所提供的所有统计数据。某些统计数据对于追踪性能问题无价的——例如，`inblk`（入 I/O 块）和 `outbl`（出 I/O 块）指示了磁盘 I/O 的使用量；`vcsw`（自愿上下文切换）和 `incsww`（非自愿上下文切换）通常显示应用程序正在使用的网络 I/O 量。

### 13.2.2. 缺陷 2：缺乏可靠的调用树

下一个问题是 Linux 缺乏一种为进程提供完整调用树的工具。虽然像 `perf` 和 `system` 等工具提供了一些信息，但它们通常难以使用，或者无法提供执行流的全景。

### 13.2.3. 缺陷 3：I/O 归因

最后一个缺陷是缺乏一种能将 I/O 操作准确归属于特定进程或线程的工具。这使得识别 I/O 相关瓶颈的根源变得困难。

## 13.3. Linux 性能调优

尽管存在上述缺陷，Linux 仍然是优化性能的理想场所。它是为开发者编写的，因此它对性能调查人员非常友好。Linux 有几个使其变得伟大的特性：

### 13.3.1. 可用的源码

首先，开发者可以访问整个系统的大部分（如果不是全部）源代码。在追踪似乎出现在你代码之外的问题时，这是无价的。在没有源码的商业 UNIX 或其他操作系统上，你可能需要等待供应商调查问题，而且你无法保证他们会修复。然而，在 Linux 上，你可以自己调查问题并弄明为什么会发生性能问题。如果问题在你的代码之外，你可以修复它并提交补丁，或者直接运行修复后的版本。通过阅读 Linux 代码的源码，如果你意识到问题出在你的代码中，你就可以修复它。无论何种情况，你都可以立即修复，而不会受限于等待他人的。

### 13.3.2. 轻松接触开发者

Linux 的第二个优势是相对容易找到并联系特定应用程序或库的开发者。与大多数专有操作系统相比（在后者很难确定哪位工程师负责某段特定代码），Linux 开放得多。通常，特定软件的开发者的姓名或联系信息随软件包一起提供。接触开发者允许你询问关于特定代码的行为、运行缓慢的代码意图是什么，以及执行给定的优化是否安全。开发者们通常非常乐意为此提供帮助。

## 13.4 章节总结

在本章中，我们研究了 Linux 性能工具集存在不足的几个领域，并提出了一些理想的解决方案。我们还讨论了为什么 Linux 是进行性能调查和优化的良好平台。

改进 Linux 性能取决于你，这位读者。Linux 性能和 Linux 性能工具的改进机会随处不在。如果你发现了一个困扰你的性能问题，请修复它，或者将其报告给开发者并与他们合作修复。无论哪种方式，都不会再受到该问题的影响，整个 Linux 社区都从中受益。

## 附录 B 安装 profile

系统性能分析器 `profile` 是一项强大的性能工具，其安装/使用可能会很复杂。本附录描述了在 Fedora Core 2 `FC2`、`Red Hat Enterprise Linux` `EL3` 和 SUSE 9 `S9` 上安装 `profile` 时遇到的一些问题。

### B.1 Fedora Core 2 `FC`

对于 `FC2`，Red Hat 提供了 `profile` 的软件包，应该使用这些包而不是 `profile` 网站上的。单处理器内核不提供必要的 `profile` 驱动程序。Red Hat 将必要的内核模块与 SMP 版本的内核一起打包。如果你想运行 `profile`，即使你是在单处理器机器上运行，也必须使用 SMP 内核。

### B.2 Enterprise Linux 3 `EL3`

对于 `EL3`，Red Hat 再次提供了 `profile` 的软件包，应该使用这些包而不是 `profile` 网站上的。单处理器内核不提供必要的 `profile` 驱动程序。Red Hat 在 SMP 或大内存版本的内核中包含了必要的内核模块。如果你想运行 `profile`，即使你是在单处理器机器上运行，也必须使用 SMP 或大内存内核。在 `EL3` 中使用 `profile` 的更多信息请参阅 `http://www.redhat.com/docs/manuals/enterprise/RHEL-3-Manual/sysadmin-guide/profile.html`。

### B.3 SUSE 9.1

对于 SUSE 9.1，SUSE 提供了 `profile` 的软件包，应该使用这些包而不是 `profile` 网站上的。所有版本的 SUSE 内核（默认、`SMP` 和 `bigSMP`）都支持 `profile`，因此所提供的任何内核都可以工作。
