# 11.8. Using gdb to Generate Call Traces

The two tools for retrieving information about functions our application was gave us different information about which functions were the hot functions. We theorized that the high-level functions that trace reported calling the low-level function opprofile was reporting. It would be nice to have a tool that could show exactly functions were calling g_type_check_instance_is_a to verify this.

Although no Linux tool shows us exactly which functions are calling a particular function, gprof should be able to provide this callback, but this requires recompiling the application and all the libraries that it relies on the -pg flag to enable. For nautilus, which relies on 72 shared libraries, this can be a daunting and inflexible task, so we have to look for another solution. Newer versions of profile also provide this type of information, but because only samples periodically, we would need to account for any given function.

Fortunately, we can creatively use gdb to extract information. Gdb to trace the application quite slows down the run; we do not really care the trace takes a long time. We are interested in finding the number of times a particular function is called rather than the amount of time it called, so it is acceptable for it to take a long time. Luckily, the pop-up menu is in the millisecond range; even if 1000 times slower with gdb, it only takes about 15 minutes to extract the full trace. We value the information which outweighs our need to retrieve it.

In particular, to find which functions are calling g_type_check_instance_is_a, we are going to use two different features of gdb. First, we use gdb's ability to set a breakpoint at that function. Then we use gdb's ability to generate a traceback with bt at that breakpoint. These features are really all that we need to figure out which functions are calling this but manually recording the information and continuing be bounded. We would need to use bt ; cont each time gdb breaks in the function.

To solve this, use one of gdb's features, gdb can execute a set of commands when it hits a breakpoint. By using the command we can tell gdb to execute bt; cont every time it hits the breakpoint in our function. Now the backtrace displays, and the application continues running every time it g_type_check_instance_is_a.

Now we have to see the actual traces. We can set the breakpoint in g_type_check_instance_is_a at the start of nautilus, and gdb would show tracing information when it is called when we are creating a pop-up menu. We would need to limit tracing to only when we are popping. To do this, we set another breakpoint at the beginning and end of the fm_directory_view_pop_up_background_context_menu function. When we reach the first breakpoint, we start the tracing in g_type_check_instance_is_a; when we reach the second breakpoint, we stop the debugger. This limits the backtrace to that which is generated when we are creating a pop-up menu. Finally, we need to be able to save this backtrace information for post-processing. We can use gdb's log to output it to a file as shown in Listing 11.12.

# Listing 11.12.

```
# Prevent gdb from stopping a screenful of output
set height 0
# Turn on logging to a file (default: gdb.txt)
# Turn off output to the screen
set logging redirect on
# Stop when a popup menu is about to be created
break fm-directory-view.c:5730
```
