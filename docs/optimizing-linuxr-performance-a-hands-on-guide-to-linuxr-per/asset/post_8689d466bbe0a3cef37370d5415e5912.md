
## 6.3. What's Missing?

The disk I/O tools on Linux provide information about the utilization of a particular disk or partition. Unfortunately, after you determine that a particular disk is a bottleneck, there are no tools that enable you to figure out which process is causing all the I/O.

Usually a system administrator has a good idea about what application uses the disk, but not always. Many times, for example, I have been using my Linux system when the disks started grinding for apparently no reason. I can usually run `top` and look for a process that might be causing the problem. However, by eliminating processes that I believe are not doing I/O, I can usually find the culprit. This requires knowledge of what the various applications are supposed to do. It is also error prone, because the guess about which processes are causing the problem might be wrong. In addition, for a system with many users or running applications, it is not always practical or easy to determine which application might be causing the problem. Other Unixes support the `inblk` and `cublk` parameters to `ps`, which show you the amount of disk I/O issued on behalf of a particular process. Currently, the Linux kernel does not track the I/O of a process, so the `ps` tool has no way to get this information.

You can use `lsof` to determine which processes are accessing files on a particular partition. After you list all PIDs accessing the files, you can attach to each of the PIDs with `strace` and figure out which one is doing a significant amount of I/O. Although this method works, it is really a Band-Aid solution, because the number of processes accessing a partition could be large and it is time-consuming to attach and analyze the system calls of each process. This may also miss short-lived processes, and unacceptably slow down processes when they are being traced.

This is an area where the Linux kernel could be improved. The ability to quickly track processes which are generating I/O would allow for much quicker diagnosis of I/O performance-related problems.

## Chapter 7. Performance Tools: Network

This chapter introduces some of the network performance tools available on Linux. We primarily focus on the tools that analyze the network traffic on a single box rather than network-wide management tools. Although network performance usually does not make sense in total isolation (that, nodes do not normally talk to themselves), it is valuable to investigate the behavior of a single system on the network to identify local configuration and application problems. In addition, understanding the characteristics of network traffic on a single system can help to locate other problem systems, or local hardware and applications errors that slow down network performance.

After reading this chapter, you should be able to:

- Determine the types of IP traffic flowing in and out of the system (gkrellm, iptraf, netstat, etherape).
- Determine the amount of each type of IP traffic flowing in to and out of the system (gkrellm, iptraf, etherape).
- Determine which applications are generating IP traffic (netstat).

## 7.1. Introduction to Network I/O

Network traffic in Linux and every other operating system is abstracted as a series of hardware and software layers. The link, or layer contains network hardware such as Ethernet devices. When moving network traffic, this layer does not distinguish types of traffic but just transmits and receives data (frames) as fast as possible.

Stacked above the link is the network layer. This layer uses the Internet Protocol (IP) and Internet Control Message Protocol (ICMP) to address and route packets of data from machine to machine. IP/ICMP make their best-effort attempt to pass the packets between machines, but they make no guarantees about whether a packet arrives at its destination.

Stacked above the network layer is the transport layer, which defines the Transport Control Protocol (TCP) and User Datagram Protocol (UDP). TCP is a reliable protocol that guarantees that a message is delivered over the network or generates an error if the message is not delivered. TCP’s bubbling protocol, UDP, is an unreliable protocol that delivers deliberately (to achieve the highest rates) but no guarantee delivery. UDP and TCP define the concept of "service" to IP and UDP receive messages on numbered "ports". By convention, each type of network service is assigned a different number. For example, Hypertext Transfer Protocol (HTTP) is typically port 80, Secure Shell (SSH) is typically port 22, and File Transfer Protocol (FTP) is typically port 21. In a Linux system, the file `/etc/services` defines the ports and types of services they provide.

The final layer is the application layer. It includes all the applications that use the layers below to transmit packets over the network. These include Web servers, SSH clients, or peer-to-peer (P2P) file-sharing clients like bitorrent.

The lowest three layers (link, network, and transport) are implemented or controlled within the Linux kernel. The kernel provides statistics about how each layer is performing, including information about the bandwidth usage and error count as data flows through each of the layers. The tools covered in this chapter enable you to extract and verify statistics.

### 7.1.1. Network Traffic in the Link Layer

At the lowest levels of the network stack, Linux can detect the rate at which data traffic is flowing through the link layer. The link layer, layers above have pieces of information much larger than the frame size, the link layer breaks everything into frames to send them over the network. This maximum size of data in a frame is known as the maximum unit (MTU). You can use network configuration tools such as ip or ifconfig to set the MTU. For Ethernet, the maximum size is 1,500 bytes, although some hardware supports jumbo frames up to 9,000 bytes. The size of the MTU has a direct impact on the efficiency of the network. The frame in the link layer has a small header, so using a large MTU increases the ratio of data to overhead (header). When using a large MTU, the number of frames decreases.

## 7.2. Network Performance Tools

This section describes the network performance tools available to diagnose performance problems. We start with the tools to determine the lowest level of network.

### 7.2.1. mii-tool (Media-Independent Interface)

mii-tool is an Ethernet-specific hardware tool used to configure an Ethernet device, but it can also provide information about the current configuration.

#### 7.2.1.1. Network I/O Options

mii-tool requires root access to be used. It is invoked with the following command line:

```
mii-tool [-v] [device]
```

mii-tool prints the Ethernet settings for the given device. If no devices are specified, mii-tool displays information about all available devices. If the -v option is used, mii-tool displays verbose statistics about the offered and negotiated capabilities.
