# 13.2. What Tools Does Linux Still Need?

As we toured the Linux tools, we saw some holes in the overall performance-investigation functionality. These holes are the result of kernel limitations, and some just exist because no one has written a tool to solve the problem. However, filling of these holes would make it dramatically easier to track down and fix Linux problems.

# 13.2.1. Hole 1: Performance Statistics Are Scattered

One glaring hole is that Linux has no tool that provides relevant performance statistics for a particular process. ps was to fill this hole in the original UNIX, and on Linux, it is pretty good but it does not cover all statistics that other commercial implementations provide. Some statistics are invaluable in tracking performance problems—for example, inblk (I/O blocks read in) and outbl (I/O blocks out) which indicate the amount of disk I/O is using; vcsw (voluntary context switches) and incsvw (involuntary context switches), which often show the amount of network I/O an application is using; msg (messages sent on pipes and sockets) and msgrecv. An ideal tool would combine all these tools presented so far (including profile, top, ps, strace, ltrace, and the /proc file system) into a single application. A user would profile this single process at once and extract all the important performance statistics. Each statistic would be updated in real time, enabling a user to debug an application as it runs. It would group statistics for a single area of investigation in the same location.

For example, if I were memory usage, it would show exactly how memory was being used in the heap, by stacks, shared memory, and in map. If a particular area was much higher than I expected, I could drill down, and see which functions allocated the memory. If I were investigating CPU usage, I would start with statistics, such as how much time is spent in system time versus user and how many calls a particular process is making, I would be able to drill down into either the system or user time and see which functions are spending all the time and how they are called. A small script that uses the appropriate tools to gather and combine this information would go a long way to achieving some of this functionality, but fundamental changes in the behavior of the tools would be necessary to realize this.

# 13.2.2. Hole 2: No Reliable and Complete Call Tree

The next performance hole is the fact that there is currently no way to provide a complete tree of a program's execution. Linux has several implementations. profile provides call-tree generation, but it is by sampling, which will not catch every call that is made. gprof supports calls but it is not possible to provide the full activation of every library that a process calls with support. This most promising tool, valgrind, is a skin called calltree, described in the section, "5.2.5 kcachegr," in Chapter 5, "Performance Tools: Process-Memory," which has a goal of providing a accurate call tree. However, it is in development and does not work on all binaries.

This-call tool would be useful even if it dramatically slowed down application performance as it runs. A common way of using this would be to profile to figure which functions in an application are "hot," and then run the call tree to figure out why the application called them. The profile tool would provide an accurate view of the application's bottlenecks when it runs at speed, and the call tree, even if it runs slowly, would show why and how the application called them.
