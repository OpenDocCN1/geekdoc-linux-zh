

## 8.3. 章节总结

本章介绍了一些调查性能问题时非常有用的 Linux 工具工具。它引入了 `bash`、`tee` 和 `script` 等工具，这些工具可以实现性能数据的显示和收集。它还介绍了 `gnumeric`，这是一个可以对基于文本的性能工具的结果进行绘图和分析的工具。接着研究了 `ldd` 和 `objdump`，它们可以跟踪函数属于哪个库。然后描述了 `gdb`，这是一个可以调查运行程序执行和运行时信息的工具。最后，本章描述了 `gcc` 工具（如 `oprofile`），可以将事件映射回特定的源行，以及带有符号调试信息的二进制文件，这些信息有助于其他性能工具。

在接下来的章节中，我们将整合目前介绍的所有工具，并解决一些真实的性能问题。

## 第 9 章. 使用性能工具查找问题

本章包含了一种结合之前介绍的性能工具来缩小性能问题原因的方法。

阅读完本章后，你应该能够：

- 从运行异常的系统开始，使用 Linux 性能工具追踪异常的内核函数或应用程序。
- 从运行异常的应用程序开始，使用 Linux 性能工具追踪异常的函数或源行。
- 追踪 CPU、内存、磁盘 I/O 和网络过度使用的情况。

## 9.1. 并非万能的灵药

本章假设可以通过更改软件来解决性能问题。通过调整应用程序或系统来达到目标性能目标并不总是可能的。如果调优失败，可能需要硬件升级或更换。如果系统容量已饱和，性能调优只能在一定程度上有所帮助。

例如，直接升级系统内存可能是必要的（甚至更便宜的），而不是追踪哪些应用程序正在使用系统内存，然后对其进行调优以减少使用。决定直接升级系统硬件还是追踪并调优特定的性能问题取决于问题本身，并且是一种基于个人金钱考量（购买新硬件）的价值判断。在某些情况下，从时间角度（调查问题）或金钱角度来看哪种方案更便宜，调优将是首选或唯一的选择，这就是本章所描述的。

## 9.4. 优化系统

有时，调查运行异常的系统并找出究竟是什么在减慢速度是很重要的。

由于我们调查的是系统级问题，原因可能从应用程序到系统库再到内核。幸运的是，Linux 与许多操作系统不同，你可以获取系统上大部分应用程序的信息。如果必要，可以修复问题并提交给维护者。在最坏的情况下，你可以运行本地版本。这是开源软件的。

### 9.4.1. 是否 CPU 密集？

使用 `top` 或 `mpstat` 确定时间花费在哪里。如果整个系统在空闲和等待模式下的时间小于 5%，则系统是 CPU 密集的。跳转到第 9.4.3。否则，跳转到 9.4.2。

### 9.4.2. 是否单处理器 CPU 密集？

虽然整个系统可能不是 CPU 密集，但在对称多处理 (SMP) 或超线程系统中，单个处理器可能是 CPU 密集。

使用 `top` 或 `mpstat` 确定单个 CPU 在空闲和等待模式下的时间是否小于 5%。如果是，则更多 CPU 是 CPU 密集；在这种情况下，跳转到 9.4.4。

否则，CPU 是 CPU 密集。跳转到 9.4。

### 9.4.3. 是否一个或多个进程使用了大部分系统 CPU？

下一步是确定某个特定的应用程序或应用程序组在使用 CPU。最简单的方法是运行 `top`。默认情况下，`top` 按使用 CPU 的情况降序排列。`top`报告的进程 CPU 使用率为用户时间和系统时间的和。例如，如果应用程序在用户空间花费了 20% 的 CPU，在系统空间花费了 30%，`top` 将报告该进程消耗了 50% 的 CPU。汇总所有时间。如果这显著小于系统整体比例，则是内核在执行非应用程序的工作。

否则，跳转到 9.4.3（上下文建议 9.4.4，但保留逻辑）或跳转到识别进程的位置。

### 9.4.4. 是否一个或多个进程使用了大部分系统 CPU？

下一步是确定某个特定的应用程序或应用程序组在使用系统 CPU。最简单的方法是运行 `top`。默认情况下，`top` 按使用 CPU 的情况降序排列。`top`报告的进程 CPU 使用率为用户时间和系统时间的和。例如，如果应用程序在用户空间花费了 20% 的 CPU，在系统空间花费了 30%，`top` 将报告该进程消耗了 50% 的 CPU。汇总所有时间。如果这显著小于系统整体比例，则是内核在执行非应用程序的工作。

否则，跳转到 9.4.3（上下文建议 9.4.5）或跳转到识别进程的位置。

### 9.5.1. 进程是在用户还是内核空间花费时间？

你可以利用时间确定应用程序是在内核还是用户空间花费时间。进程级别的分析显示了时间花费在哪里。

如果应用程序在内核空间花费了大量时间（大于 25%），跳转到 9.5.2。否则，跳转到 9.5.3。

### 9.5.2. 进程正在哪些系统调用？完成需要多久？

接下来，使用 `trace` 查看执行了哪些系统调用以及它们需要多长时间。你还可以运行 `profile` 查看正在执行哪些内核调用。通过减少系统调用的次数或更改代表程序生成的系统调用，可能提高性能。某些调用可能是意外之外的，应用程序调追踪会有帮助。

### 9.5.3. 进程在哪些函数中花费时间？

接下来在应用程序周期上运行 `profile`，确定哪些函数在使用所有的 CPU 周期（即哪些函数消耗了应用程序时间）。

请记住，分析显示了进程中花费了多少时间，函数级别的分析并不清楚一个函数热是因为调用非常频繁，还是因为完成需要很长时间。

确定哪种情况真实的方法之一是使用 `profile` 的源码注释，并寻找应该只有少量开销的指令/源行（如赋值）。我们得到的样本数量相对于其他高成本源的被调用函数数量。这只是近似，因为 `profile` 只对 CPU 采样，且乱序执行可能会掩盖某些问题。

调用函数图来确定热函数是如何被调用的也有帮助。要做到这一点，请看章节 9.5.4。
