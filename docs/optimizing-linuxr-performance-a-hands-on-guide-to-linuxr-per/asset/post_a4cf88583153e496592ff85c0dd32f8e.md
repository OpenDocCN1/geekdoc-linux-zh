
## 10.3. Find a Baseline/Set a Goal

This first step in any performance hunt is to determine the current state of the problem. In the case of the GIMP filter, we need to figure out how much time it takes to run a particular image. This is our baseline time. Once we have this baseline, we can then try an optimization and see whether it decreases the execution time. Sometimes it can be tricky to time how long something takes. It is not as easy as using a stopwatch because the operating system is scheduling other tasks at the same time that our process CPU-intensive job is running. If there are others running in addition to the CPU-intensive one, the wall-clock time could be greater than the CPU time that the process actually uses. In this case, we are lucky; by looking at top as the filter is running, we can see the lic process is taking up most of the CPU usage, as shown in Listing 10.1.

### Listing 10.1.

```
[ezolt@localhost ktracer]$ top
```

```
top - 08:24:48 up 7 days, 9:08, 6 users, load average: 1.04, 0.64, 0.76

PID USER PR NI VIRT RES SHR S %CPU %MEM TIME+
32744 ezolt 25 0 53696 45m 11m R 89.6 14.6 01:16 lic
2067 root 15 0 06952 21m 17m S 6.0 6.8 01:56:22 X
32738 ezolt 15 0 35292 27m 14m S 2.3 8.7 00:05:08

```

From this, we can deduce that GIMP actually spawned a separate process to run the filter. When the filter is running, we can use ps to track how much CPU time the process is using and when it finishes. When we have the PID of the filter using top, we can refer to Listing 10.2 and ask ps to periodically observe how much CPU time the filter is using.

### Listing 10.2.


### Note

If you need to time an application but do not have a stopwatch, you can use time and cat as a simple stopwatch. Just type time cat when you want to start, and press <Ctrl-D> when you are finished. time shows how much time has passed.

When running the lic on the reference image (which is a fetching picture of gimp) and using the ps method just to time the filter, we can see from Listing 10.2 that it takes 2 minutes and 46 seconds to run out of the box, so we can know the amount of time that the filter takes out of the box, which we can use for the performance hunt. ## 10.4. Configure the Application for the Performance Hunt

The next step in our investigation is to set up the application for the performance hunt by recompiling the application with symbols. Symbols allow the performance tools (such as oprofile) to investigate which functions and source lines are responsible for the CPU time that is being spent.

For the GIMP, we download the GIMP tarball from its Web site, and then recompile it. In the case of GIMP and much open-source software, the first step in recompilation is running the configure command, which generates the makefiles that will be used to build. The configure command passes any flags present in the CFLAGS environmental variable into the Makefile. In this case, because we want the GIMP to be built with symbols, we set the CFLAGS variable to -g3 in the Makefile. This command is shown in Listing 10.3 and overrides the current value of the CFLAGS environmental variable and sets it to -g3.

### Listing 10.3.

```
[root@localhost gimp-2.0.3]## env CFLAGS=-g3 ./configure
```

We then make and install the version of GIMP with all the symbols included, and when we run this version, the performance tools will tell us where time is being spent.

## 10.5. Install and Configure Performance Tools

The next step in the hunt is to install the performance tools if they are not already installed. Although this might seem like an easy thing to do, it often involves chasing down custom-made packages for a distribution or over recompiling the tools from scratch. In this case, we are going to use profile on Fedora Core 2, so we have to track down both the profile kernel module, which in Fedora's case, is only included in the symmetric multiprocessing (SMP) kernels and the profile package to which library functions are called and how often they are being called. Fortunately, ltrace is included in Fedora Core 2, so we do not have to track it down.

## 10.6. Run Application and Performance Tools

Next, we run the application and take measurements using the performance tools. Because the lic filter is called directly from GIMP, we have to use tools to catch and monitor an already running process. In case of profile, we can start profile, run the filter, and then stop profile after the filter has completed. The lic filter takes approximately 90 percent of the CPU when running, the system-wide collects will be mainly relevant for the lic. When lic starts, we start profile in another window; when lic finishes, we stop. The starting and stopping of profile is shown in Listing 10.4.

### Listing 10.4.

```
[root@localhost ezolt]# profile --start
[root@localhost ezolt]# profile --dump
[root@localhost ezolt]# profile --stop
```

ltrace must be run a little differently. After the filter has started, ltrace can be attached to the running process.
