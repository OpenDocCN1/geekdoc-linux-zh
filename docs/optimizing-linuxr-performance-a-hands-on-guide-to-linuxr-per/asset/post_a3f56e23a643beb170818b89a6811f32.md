
## 11.9. Finding the Time Differences

Now that we have narrowed down which functions do the work of creating the menu, we want to figure out which pieces are taking up all the time and which pieces are relatively lightweight. A great way to do that, without using any performance tools at all, is to just disable pieces of code and see how it changes performance. Even though this causes nautilus to function incorrectly, it will at least indicate which of the functions are taking all the time.

We first have to start by taking a baseline, because the binaries we are testing have been compiled with different flags than those provided by Red Hat. We time the scripts as we did before. In this case, a run of 100 iterations takes 30.5 seconds on the version that we compiled ourselves. Next, we comment out the `eel_pop_up_context_menu` call. This shows how much time it took nautilus to detect the mouse click and decide that a context menu needed to be created. Even if we completely optimize all the commands in these functions, we will not be able to run faster than this. In this case, it takes 7.6 seconds to run all 100 iterations. Next, we comment out `bonobo_window_add_popup` it says is taking the most amount of time. If we comment out `bonobo_window_add_popup`, the 100 iterations take 21.9 seconds to complete. This says that if we optimize away the `bonobo_window_add_popup`, it can save ~8 seconds off the total run, which is nearly a 25 percent improvement.

## 11.10. Trying a Possible Solution

So, as we have, `bonobo_window_add_popup` is an expensive function that must be called every time we want to create a pop-up menu. If we are repeatedly calling it with the same parameters, it may be possible to cache the value it returns from the initial call and use that instead of calling that expensive function. Listing 11.19 shows an example of a rewritten function to do just that.

### Listing 11.19.

```c
void
fm_directory_view_pop_up_background_context_menu
(FMDirectoryView *view,
GdkButton *event)
{
 /* Primitive Cache */
  static FMDirectoryView *old_view = NULL;
  static GtkMenu *old_menu = NULL;

  g_assert (FM_IS_DIRECTORY_VIEW (view));

  /* Make the context menu items not flash as they update to
  proper disabled;
   * states. by forcing menus to update now.
   */
  if ((old_view != view) ||
      view->menu_states_untrustworthy)
  {
    update_menu_if_pending(view);
    old_view = view;
    old_menu = create_popup_menu(view,
      FM_DIRECTORY_VIEW_POPUP_PATH_BACKGROUND);
  }

  eel_pop_up_context_menu (old_menu,
    EEL_DEFAULT_POPUP_MENU_DISPLACEMENT,
    EEL_DEFAULT_POPUP_MENU_DISPLACEMENT,
    event);
}
```

In this case, we remember the menu that was generated last. If we are in the same view, and we do not believe that the menu for view has changed, we just use the menu that we used instead of creating a new one. This is not a sophisticated technique, and it will break down if the user does not open a pop-up menu in directory 1, and opens in directory 2, if there opens a pop-up menu in directory 1, nautilus will create a new one. When opening a menu, the first check is to see whether we already have menu in the cache. If the cached menus could be viewed; otherwise, one could be created. This could be especially useful for special directories, such as the desktop, computer, or home where the user will likely open a pop-up menu more than once. After applying this proposed solution and with the 100ms timeout, the time has dropped to 24.0 seconds. This is a 20% performance improvement, and close to the improvement that we would get if we did not create the menu at all (21 seconds). Creating pop-up menus in various directories worked.

In this case, we stored a pointer to a new menu when it was allocated and used it later to avoid unneeded reloads. ## Chapter 12. Performance Hunt: The System-Wide Slowdown

This chapter contains an example of how to use the Linux tools to find and fix a performance problem that affects the entire system rather than a specific application. After reading this chapter, you should be able to:

- Track down which individual process is causing the system to slow down.
- Use `strace` to investigate processes that are not CPU-bound.
- Use `strace` to investigate how applications are interacting with the Linux kernel.
- Submit bug reports that describe the problem so that an author or maintainer has enough information to fix it.
