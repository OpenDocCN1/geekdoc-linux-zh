## Access Options in /etc/exports
You don't have to just give away your files and directories when you export a directory with NFS. The options in part after each entry in /etc/exports, you can add options that allow or limit access by setting read/write permission. These options, which are passed to NFS, are as follows:

- ro—Client can mount this exported file system read-only. The default is to mount the file system read/write.
- rw—Explicitly asks that a shared directory be shared with read/write permissions. (If the client chooses, it can still mount the directory-read-only)

### User Mapping Options in /etc/exports
In addition to define how permissions are handled generally, you can use options to set the permissions that specific users have to NFS file systems.

One method that simplifies this process is to have each user multiple accounts have the same username and UID on each machine. This makes it easier to map users who have the same permissions on a mounted file system that they do on their local hard disks. If that method is not convenient, there are other ways of setting user permissions and the /etc/exports option that you can use for each:

- root_user—The client's root user is generally mapped into the nfsnobody username (UID 65534). This prevents a client computer's root user from being able to change all files and directories in the shared file system. If you want the client's root user to have root permission on the server, use the no_root_squash option.

There may be other administrative users, in addition to root, that you want to squash. Consider squashing UIDs 0–99 as follows: squash_uid=0–99.

- nfsnobody user/group—By using nfsnobody username and group name, you essentially create a user/group with permissions that do not allow access to any files belonging to any real servers, unless those users open permission to everyone. However, files created by the nfsnobody user or group are available to assigned as the nfsnobody user or group. To set all remote users to the nfsnobody user/group, use the all_squash option.

The nfsnobody user is assigned to UIDs and GIDs of 65534 to prevent the ID from running into a valid user or group ID. Using anoid or angid options you can change the nfsnobody user or group, respectively. For example, anoid=175 sets all anonymous users to UID 175, and angid=300 sets the GID to 300. (Only when the number is displayed when you list file permission unless you add entries with names to /etc/password and /etc/group for the new UIDs and GIDs.)

## Exporting the Shared File Systems

After you have edited your /etc/exports file, run the exports command to have exported directories (available to other computers on the network). Reboot your computer or restart the NFS service, and the exports command runs automatically to export your directories. If you want to export them immediately, run exports from the command line (as root).

![](img/a2d958d7eab32ca5b89b2b8af808aa70_753_1.png)

It's good idea to run the exports command after you change the exports file. If any errors are in the file, exports identifies them for you.

Here is an example of the exports command:

```
# /usr/sbin/exports -a -v
exporting maple:/pub
exporting spruce:/pub
exporting maple:/home
exporting spruce:/home
exporting *:mnt/win
```

The -a option indicates that all directories listed in /etc/exports should be exported. The -v option says to verbose output. In this example, the /pub and home directories from the local server are immediately available for mounting by those computers that are named (maple and spruce). The /mnt/win directory is available to all client computers.

Running the exports command temporarily makes your exported NFS directories available. To have your NFS directories available on an ongoing basis (that is, every your system reboots), you need to set your nfs startup scripts to run at boot time. This is described in the next section.

## Starting nfs Daemons

If NFS has been disabled on your system (or is not active by default), you need to start it. Different Linux distributions have different ways of turning on the NFS service, as you saw in the “Getting NFS” section earlier in the chapter. This section explores how the service is turned on in Fedora and other Red Linux systems.

In Fedora, you use the chconfig command to turn on the NFS service so that your files are exported and the nfs daemons are running when your system boots. There are two startup scripts you want to turn on for the service to work properly. The NFS service exports file systems (from /etc/exports) and starts the nfs daemon that listens for service requests. The nlock service starts the lockd daemon, which helps file locking to prevent multiple simultaneous use of critical files over the network.

To run chconfig, type the following as root user:

```
# chconfig nfs on
# chconfig nfslock on
```

The next time you start your computer, the NFS service will start automatically, and your exported directories will be available. If you want to start it immediately, without waiting for a reboot, type the following:

```
# /etc/init.d/nfs start
# /etc/init.d/nfslock start
```

The NFS service should now be running and ready to share directories with other computers on your network.

## Using NFS File Systems

After a server exports a directory over the network using NFS, a client computer connects that directory to its own file system using the mount command. That’s the same command used to mount file systems from local hard drives, CDs, and floppies, but with slightly different options.

mount can automatically mount NFS directories added to the /etc/fstab file, as it does with local disks. NFS directories can also be added to the /etc/fstab file in such a way that they are not automatically mounted (so you can mount them manually when you choose).

### Manually Mounting an NFS File System

If you know that the directory from a computer has been exported (that is, available), you can mount it using the mount command. It is a good way to make sure it is working before you set it up permanently. Here is an example of mounting the /tmp directory from a computer named maple:

```
# mkdir /mnt
mount maple:tmp /mnt
```

The first command (mkdir) creates the mount point directory (/mnt is a common place to put mounted disks). The mount command identifies the remote computer and shared file system by a colon (maple:tmp), and the local mount point (/mnt) follows.

> If the mount fails, make sure the NFS service is running on the server and that the server's firewall does not deny access. From the server use ps ax nfs to see a list of nfs servers. If you don't see them, try to start your NFS daemons as described in the previous section. To view your firewall rules, use iptables -L (see Chapter 17 for a description of firewalls). By default, nfs daemon listens for requests on port 2049. Your firewall must accept udp requests on port 2049 (nfs) and 111 (rpc).

To ensure the mount occurred, type mount. This command lists all mounted disks and NFS file systems. Here is an example of the mount command and its output (with file systems not persistent to this discussion edited out):

```
# mount
/dev/hda3 on / type ext3 (rw)
...
maple:tmp on /mnt/maple type nfs (rw,addr=10.0.0.11)
```

The output from the mount command shows the mounted disk partitions, special file systems. The first output line shows the hard disk (/dev/hda3), mounted on the root file system (/), with read/write permission (rw), with a file type of ext3 (the standard Linux file system). The just-mounted NFS system is the /tmp directory from maple (maple:tmp). It is mounted on /mnt/maple and its mount type is nfs. The file system was mounted read-write (rw), and the IP address of maple is 10.0.0.11 (addr=10.0.0.11).
