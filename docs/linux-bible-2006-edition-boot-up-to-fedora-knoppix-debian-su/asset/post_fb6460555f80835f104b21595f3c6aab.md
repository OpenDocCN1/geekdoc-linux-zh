`ranlib [-v|-V] file`
This generates a symbol map in file. It is equivalent to `ar -file`.

# The ldd Command

While nm lists the symbols defined in an object file, unless you know what library defines functions, it is not terribly helpful. That is ldd's job. It lists the shared libraries that a program requires to run. Its syntax is:

```
ldd [options]
```

ldd prints the names of the shared library files. Two of ldd's most-useful options are -d, which reports any missing functions, and -r, which reports functioning and missing data objects. For example, the following ldd reports that the client maint (which may or not be installed on your system) requires eight shared libraries.

```
$ ldd /usr/bin/mutn
libcurses.so.5 -> /lib/libcurses.so.5 (0x40020000)
ssl.so.0 -> /usr/libssl.so.0 (0x40066000)
crypto.so.0 -> /usr/libcrypto.so.0 (0x40097000)
libc.so.6 -> /lib/libc.so.6 (0x40195000)
libpgm.so.1 -> /lib/libpgm.so.1 (0x402c5000)
ldl.so.2 -> /lib/ldl.so.2 (0x402cb000)
/ld-linux.so.2 -> /lib/ld-linux.so.2 (0x40000000)
libcurses.so.5 -> /lib/libcurses.so.5 (0x402ce000)
```

The output might be different on your system.

# The ldconfig Command

ldconfig determines the runtime links required by shared libraries that are located in /usr/lib and /lib, specified in libs on the command line, and stored in /etc/ld.so.conf. It works in conjunction with ld.so, the dynamic linker/loader, to create and maintain links to the most current versions of shared libraries available on your system. It has the following syntax:

```
ldconfig [options] [libs]
```

A bare ldconfig updates the cache file, /etc/ld.so.cache. -options controls ldconfig behavior. The -v option tells ldconfig to be verbose as it updates the cache. The -p option says to print without updating the current list of shared libraries which is similar to the $PATH environment variable. ld.so knows.

# Environment Variables and Configuration Files

The dynamic linker/loader ld.so uses a number of environment variables to customize and control its behavior. These variables include:

- LD_LIBRARY_PATH—This variable contains a colon-separated list of directories to search for shared libraries at runtime. It is similar to the $PATH environment variable.
- $LD_PRELOAD—This is a whitespace-separated list of additional, user-specified shared libraries to load before all other libraries. It is used selectively to override functions in other shared libraries.

ld.so also uses two configuration files parallel to those environment variables:
- /etc/ld.so.conf—Contains a list of directories that the linker/loader should search for shared libraries in addition to the standard directories, /usr/lib and /lib.
- /etc/ld.so.preload—Contains a disk-based version of the LD_PRELOAD environment variable, including a whitespace-separated list of shared libraries to be loaded before executing a program.

You can use $LD_PRELOAD to override installed versions of a library with a specific version; this is often useful when you are testing a new (or different) library version but don't want to install the replacement library on your system.

# Source Code Control

Version control is an automated process for keeping track of and managing changes made to source code files. Why bother?

- One day you will make one fatal edit to a source file, delete its predecessors, and forget exactly which line or lines of code you "fixed"
- Simultaneously keeping track of the current release, the next release, and eight bug fixes manually become mind-numbing and confusing
- Frantically searching for the backup tape because one of your colleagues overwrite a source file for the fifth time will drive you to the edge

One day, over your morning cappuccino, you will say to yourself, "Version control, it's the Right Thing to Do."

# Source Code Control Using RCS

The Version Control System (RCS) is a common solution to the version control problem. RCS, which is maintained by the GNU project, is available on almost all UNIX systems, not on Linux. Two alternatives to RCS are the Concurrent Version System (CVS), which is also maintained by the GNU project, and Source Code System (SCCS), a proprietary product.

Before you proceed, Table 29-5 lists a terms that will be used throughout the chapter.

| Table 29-5: Version Control Terms | Description |
| :--- | :--- |
| Lock | RCS prevents multiple users from editing a file simultaneously. |
| Revision | Versions begin with 1 and increase numerically with each check-in. |
| Working file | The file you check out for editing. |

In addition to storage, RCS manages versions of files. To get started, use the `co` command to check out thedy.c file from the repository.

# Checking Files In

To see version in control, make a change to the working file. If you haven't already done, check out and lock the howdy.c. Change anything you want, but I recommend adding `\n` to the end of `printf()` because Linux (UNIX), unlike Windows, do not automatically add a newline.

Next, check the file back in RCS will increment the revision number to 1.2, for a description of the the made, incorporate the changes you made into the RCS file, and (increasingly) delete the original. To prevent deletion of your work-files during check-in, use the -l or -u option with `ci`.

# Making Changes to Repository

When using `ci`, both the -l and -u options cause an implied check-out of the file after the check-in. -l locks the file so you can continue to edit, while -u checks out an unlocked or read-only working file. 

# Additional Command-Line Options

In addition to -l and -u, `ci` can accept other very useful options: -r (for revision) and -f (force). Use -r to tell RCS which revision you want to manually. RCS assumes you want to work with the most recent revision: -r overrides default. The -f option forces RCS to overwrite the current working file.
