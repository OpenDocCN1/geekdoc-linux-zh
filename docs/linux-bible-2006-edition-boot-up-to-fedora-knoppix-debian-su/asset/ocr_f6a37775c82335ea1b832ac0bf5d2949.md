The likelihood of deadlocks, livelocks, or races occurring increases dramatically on multitasking (multuser) systems because the number of processes that are potentially competing for a finite number of resources is greater. Good design, careful analysis, and the judicious use of locks, semaphores, and other mutual exclusion (mutex) mechanisms, which mediate access to shared resources, can prevent or reduce their occurrence.

# Multiser by Design

Linux multiuser by design, an element of the Linux development model that has far-reaching consequences for developers. A program cannot assume, for example, that it has access to any resource such as a file, memory, peripheral devices, or CPU time; multiple programs might be attempting to print simultaneously or trying to allocate memory.

Similarly, a program cannot be written with the assumption that only one copy of the program is running at a time. So, if you are writing a program that creates working files in /tmp, you need to ensure that the temporary files created by Bobba's copy of the program are distinct from the temporary files created by Mary Beth's instance of the program. If you don't, hilarity will ensure (if not hilarity, least confusion and consternation).

Another common need is for programs to honor per-user configurations. At start-up, a program might apply reasonable global defaults and then read a user's configuration file to apply, a custom color scheme.

There are also a number of per-user settings, such as environment variables, that programs need to know how to accommodate. For example, the $MAIL environment variables which define the user's mail file is and the VISUAL environment variable defines the user's preferred full screen editor (which all Linux users know is). The $SPRINTER environment variable stores the name of the user's default printer, and $HOME identifies the user's home directory.

In a persistently multiuser system like Linux, and programmers must always take into account that most resources a program might want to use are shared. Likewise, they must also take into account that real-world usage scenarios (more formally known as use cases) assume that multiple instances of the program are running at the same time.
