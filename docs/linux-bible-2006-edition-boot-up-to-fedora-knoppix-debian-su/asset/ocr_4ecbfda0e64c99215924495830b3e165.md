# Part II ♦ Running the Show

```
-V verbose: print statistics
-d\ set SO_DEBUG socket option
-b ##
 set buffer size (if supported)
-f X
 format rate: k,K = kilo(bit,byte);m,M = mega;g,G = giga
Options specific to -t:
-# --number of source buffers written to network (default 2048)
-D
don't buffer TCP writes (TCP_NODELAY socket option)
-w --number of microseconds to wait between each write
Options specific to -r:
-B
for -s, only output full blocks as specified by -l (for TAR)
-T
"touch": access byte as it's read
-I If specify the network interface (e.g. eth0) to use
```

The first step is to start up a processor on the server machine:

```
# ttcp -rs
ttcp-r: buflin=8192, nbuf=2048, align=16384/0, port=5001 tcp
ttcp-s: socket
```

The -r flag denotes that the server will be the receiver. The -s flag, in conjunction with the -r flag, tells ttcp that we want to ignore any received data.

The next step is to have someone outside your data link, with a network link close to the same speeds, yet using a ttcp sending process:

```
# ttcp -ts server.example.com
ttcp-t: buflin=8192, nbuf=2048, align=16384/0, port=5001 tcp
- > server.example.com
ttcp-t: socket
ttcp-t: connect
```

Let the process run for a few minutes and press Ctrl+C on the transmitting side to stop the testing. The receiving side takes a moment to calculate and present the results:

```
# ttcp -rs
ttcp-r: buflin=8192, nbuf=2048, align=16384/0, port=5001 tcp
ttcp-r: socket
ttcp-r: accept from 64.223.17
ttcp-r: 210249 bytes in 70.02 seconds = 29.32 KB/sec ++
ttcp-r: 1226 0 calls, msec/call = 58.49, calls/sec = 17.51
ttcp-r: 0.0user 0.0sys 1:10real 0% 0+id 0maxrx 0+2pf 0+ocsw
```

In this example, the bandwidth between the two hosts was 29.32 kilobytes per second. On a linking setup to a DDoS, this number would be a mera fraction of the actual bandwidth data link is rated for.

If the data link is indeed saturated, the next step is to determine where the connections are coming. A very effective way of doing this is with the netstat
