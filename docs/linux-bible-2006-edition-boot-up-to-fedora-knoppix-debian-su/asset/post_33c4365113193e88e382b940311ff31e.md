During a DOS attack, the foreign address is usually the same for each connection. In this case, it is a simple matter of typing the foreign IP address into the search form at www.arin.net/whois/ so you can alert your ISP.

During a DDOS attack, the foreign address will be different for each connection. In this case, it is impossible to track down all of the offenders, because there will be thousands of them. The best way to defend yourself is to contact your ISP and see if it can filter the traffic at its border routers.

## Protecting Against Intrusion Attacks

Crackers have a wide variety of tools and techniques to assist them in breaking into your computer. Intrusion attacks focus on exploiting weaknesses in your security, so the crackers can take more control of your system (and potentially do more damage) than they could from the outside.

Fortunately, there are many tools and techniques for combating break-in intrusion attacks. This section discusses the most common break-in methods and the tools available to protect your system. The examples shown are specific to Fedora and other Red Hat Linux systems, the tools and techniques are generally applicable to any Linux or UNIX-like operating system.

## Evaluating Access to Network Services

Fedora, Red Hat Linux, and its UNIX kin provide many network services, and with many avenues for cracker attacks. You should know these services and how to limit access to them.

What do I mean by a network service? Basically, I am referring to any task that the computer performs which to send and receive information over the network using some predefined set of rules. Routing e-mail is a network service. So is serving Web pages. Your Linux has the potential to protect thousands of services. Many of them are listed in the /etc/services file. Look at a snippet of that file:

```
# /etc/services:
@ service-name port/protocol  [allases ...]  [ comment]
charg           19/tcp                         ttytst source
charg           19/udp                         ttytst source
ftp-data         20/tcp
ftp-data         20/udp
@ 21 is registered to ftp, but also used by fps
ftp              21/tcp
ftp              21/udp                         fsp fpsd
ssh              22/tcp                         # SSH Remote Login Protocol
ssh              22/udp                         # SSH Remote Login Protocol
telnet            23/tcp
telnet            23/udp
@ 24 - private mail system
smtp             25/tcp                         mail
```

After the comment lines, you will notice three columns of information. The left column contains the name of each service. The middle column defines the port number and protocol used for that service. The rightmost field contains an optional alias or list of aliases for the service.

As an example, the last entry in the file snippet. It describes the SMTP (Simple Mail Transfer Protocol) service, which is the service used for delivering e-mail over the Internet. The middle column contains the text 25/tcp, which tells you that the SMTP protocol uses port 25 and the Transmission Control Protocol (TCP) as its protocol type.

What exactly is a port number? It is a unique number that has been set aside for a particular network service. It allows network connections to be properly routed to the software that handles that service. For example, when an e-mail message is delivered from some other computer to your Linux box, the remote system must first establish a network connection with your system. Your computer receives the connection request, examines it, sees it labeled for port 25, and thus knows that the connection should be directed to the program that handles e-mail (which happens to be sendmail).

I mentioned that SMTP uses the TCP protocol. Some services use UDP, the User Datagram Protocol. All you need to know how TCP and UDP (for the purpose of this security connection) is that they provide different ways of packaging the information sent over a network connection. A TCP connection provides every detection and retransmission of lost data. UDP doesn't check to ensure that the data arrived complete and intact; it is as as fast way to send non-critical information.

## Disabling Network Services

There are hundreds of services (with official port numbers listed in /etc/services) that could potentially be available and subject to attack upon your Linux system, in reality only a few services are installed and only a handful of those are by default. In Fedora and RHEL systems, most network services are started by the xinetd process or by a start-up script in the /etc/init.d directory. Other services use the xinetd process instead of xinetd.

xinetd and inetd are daemons that listen on a great number of network port numbers. When a connection is made to a particular port, xinetd or inetd automatically starts the appropriate program for service and handles the connection to it.

For xinetd, the configuration file /etc/xinetd.conf is used to provide default settings for the xinetd server. The directory /etc/xinetd.d contains files xinetd what ports to listen on and what programs to start (the inetd daemon, uses only the /etc/xinetd.conf file). Each file in /etc/xinetd.d contains configuration information for a single service, and the file is usually named after the service it covers. For example, to disable the rsync service, edit the rsync file in the / directory and look for a section similar to the following:

```
service rsync {
    disable      = yes
    socket_type   = stream
    wait          = no
    user          = root
    server        = /usr/bin/rsync
    server_args   = -daemon
    log_on_failure += USERID
}
```

Note that the first line of this example identifies the service as rsync. This exactly matches the service name listed in the /etc/services file, causing the service to listen on port 873 for TCP and UDP protocols. You can see that the service is off by default (disable=yes). To enable rsync services, change the line to read disable = no instead. That, the disable line from the preceding example would look like this:

```
disable = no
```

The rsync service is a nice turn on if your machine is an FTP server. It allows people to use an rsync client (which includes a checksum-sum algorithm) to download files from your server. With that feature, you can restart a disrupted download without having to start from the beginning.

Most services are disabled by default, your computer is only insecure as you make it. You can double-check that insecure services, such as login and rsh (which are included in the rsh-server package in Fedora and RHEL systems), al also disabled by making sure that disabled = yes is set in the /etc/xinetd./login and rsh files.

You can make the remote login service active but disable the use of the /hosts.equiv and .hosts files, requiring login to always prompt for a password. Rather disabling the service, locate the server line in the rsh file (server = /usr/sbin/in.rsh) and add a space following by -L at the end.

You need to send a signal to the xinetd process to tell it to reload its configuration. The quickest way to do that in Fedora and RHEL systems is to restart the xinetd service. As the root user, you can trigger it from a shell:

```
# service xinetd reload
Reloading configuration: [ OK ]
```

You can also tell the xinetd process directly to reload the configuration file by sending it a SIGHUP signal. That works if you using the inet daemon instead (on systems such as Debian or Slackware) to replace the /etc/inetd.conf file. For example, this (as root) to have the inet daemon reload the configuration file:

```
# killall -s SIGHUP inetd
```

That's-you have enabled the rsync service. Provided that you have properly configured your FTP server, clients should now be able to download files from your computer via the rsync protocol.

## Securing Servers with SELinux

Red Hat, did a clever thing when it took its first swipe at implementing SELinux in Red Hat systems. Instead of creating policies to control every aspect of your Linux system, they created a "targeted" policy that focused on securing those services that are most vulnerable to attacks. They then set up securing services in a way that, if they were compromised, a cracker couldn't compromise mist of the system as well.
