
# Starting GDB

To start a debugging session, simply type gdb program, replacing program with the name of the program you want to debug. Using a core file is optional but will enhance GDB's debugging capabilities. Of course, you'll need a program on which to try out GDB debugging, and Listing 29-5 provides one: debugme.c.

## Listing 29-5: A Bug Program

```
/*
 * debugme.c poorly written program to debug
 */
#include <stdio.h>

#define BIGNUM 5000
#define SZ 100
void index_to_the_moon(int ary[]);

int main(int argc, char *argv[])
{
    int intary[100];
    index_to_the_moon(intary);
    return 0;
}

void index_to_the_moon(int ary[])
{
    int i;
    for (i = 0; i < BIGNUM; ++i)
        ary[i] = i;
}
```

Compile this program using the command `gcc -g debugme.c -o debugme`. Then, execute the program using the command `./debugme`.

```
$ ./debugme
Segmentation fault (core dumped)
$ file core
core: ELF 32-bit LSB core file Intel 80386, version 1 (SYSV), SVR4-style, SVR4-style, from 'debugme'
```

On most systems, when you execute `./debugme`, it immediately causes a segmentation fault and dumps core, as shown in the output listing.*

## Chapter 29: Programming Tools and Utilities

A core dump refers to an application failure and copying all data stored in memory for the application into a file named core in the current directory. That file can be used to help debug a problem with the application.

If you see the core dumped, try executing the shell command `ulimit -c unlimited`, which allows programs to drop a memory dump in their current working directory.

The program has a bug, so you need to debug it. The first step is to start GDB, using the program name, debugme, and the core file, core, as arguments:

```
$ gdb debugme core
```

After GDB initializes, the screen should resemble Figure 29-1.

As you can see near the middle of the figure, GDB displays the name of the executable that created the core file: '+'. Obviously, the displayed name is wrong; it should be debugme. The odd characters would give an experienced developer immediate that the program has a significant memory leak. In the next line, the text that reads "Program terminated with signal 1. Segmentation fault," explains why the program terminated. A segmentation fault occurs anytime a program attempts to access memory that doesn't explicitly belong to it. GDB also displays the function it was executing, index_to_the_moon.

If you don't like the licensing messages (they annoy me), use the -q (or --quiet) option when you want GDB to suppress them. Another useful command-line option is -d dirname, where dirname is the name of a directory, which tells gdb where to find source code (it looks in the working directory by default).

After you load the program and its core dump into the debugger, run the program in the debugger. To do so, type the command `run` at the GDB command prompt, (gdb), as the following example shows:

```
(gdb) run
Starting program: /home/www/code/debugme

Program received signal SIGSEGV. Segmentation fault.
0x0800483db in index_to_the_moon (ary=0xffffff4b0) at debugme.c:24
    ary[1] =
```

This output list shows that the segmentation fault occurred in the function index_to_the_moon at line 24 of debugme.c. Notice the line of the output: GDB displays the line of code, prefixed with the line number (24), which the segmentation fault occurred. It also shows the memory address (in hexadecimal) at which the fault occurred, 0xffff4b0.

You can pass any arguments to the run command that your program needs. Ordinarily, GDB creates a full simulated environment in which it uses the value of the environment variable $SHELL to create the environment. If you want, you can use GDB's set and unset commands before you run the program in the debugger.

## Inspecting Code in the Debugger

What is happening in the function index_to_the_moon that causes the error? You can execute the backtrace (or bt) command to generate the function trace that led to the segmentation fault. The backtrace doesn't usually show you what the problem is, but does show you more precisely where it occurred. Here is the function trace for the examples on your system:

```
(gdb) backtrace
#0 0x0800483db in index_to_the_moon (ary=0xfffffc0) at debugme.c:24
#1 0x0800a6 in main (arg=0x704, arg=0x69) at debugme.c:15
```

A backtrace shows the chain of functions that resulted in the error. The backtrace starts with the most recently called function—index_to_the_moon in this case which resides at the memory address (0x0800483db). The function index_to_the_moon() was called by the main() function. As you can see from the output, the backtrace continues the earlier examples of debugging debugme.c because you are still trying to identify where and why it crashed. Although in this example, the program crashed at the point when the counter i equal 24 (the expression $1 refers to an entry in GDB's value history, explained in a moment).

Where it crashes on your system depends on several variables. Those variables could include the system's memory layout, the process's memory space (especially the kernel's stack), the amount of available memory on your system, and other factors. The result of the second command `print(ary[i])` makes it pretty clear that the program does not have access to the memory location, although it has legal access to the preceding one.

The expression $1 is an alias that refers to an entry in value history. GDB creates value entries for each command that produces results. The alias numbers increment sequentially each time you execute a command that produces some sort of output. As a result, you can access these computed values using aliases rather than retrying the command. For example:

```
(gdb) print 1-5
$2 = 7
```

Notice that the alias incremented to $2. If you later need to use the value 7, you can use the alias $2. The value history is reset each time you start GDB and the values are not accessible outside of GDB. You are not limited to discrete values because gdb can display the addresses of data stored in an arbitrary region of memory. For example, to print the first 10 memory locations associated with ary, use the following command:

```
(gdb) print ary@10
$3 = {0xffff90, 0x04011580, 0x04011580, 0x0, 0x1, 0x2, 0x3, 0x4, 0x5}
```

The notation @10 means to print the 10 values that begin at ary. On the other hand, you want to print the first five values stored in ary beginning with the first element, the command for this would be:

```
(gdb) print ary[1]@5
$4 = {1, 2, 3, 4, 5}
```

Why go the trouble of printing variable or array values? Although it isn't necessary in this particular example because you know the trouble occurs, it is necessary to see the value of a variable at a particular point in a program's execution so you monitor what is happening to variables. In the case of arrays, a command that prints the values in an array enables you to confirm at glance the values are what ary[1]@5 in the preceding example, expect them to be. If the values don't match up with your expectations, that is a clue that some code is altering the array in a way you didn't intend. As a result, you can focus your bug hunting on a specific section of code.

GDB also can tell you the types of variables using the whatis command. GDB's whatis command is comparable to the man -f command, which searches the whatis database of system commands for short descriptions of those system commands (the manual page whatis database is totally separate from the whatis command used by GDB). While man's whatis database works on system commands, GDB's whatis describes the types of variables and other data structures used in a program.

```
(gdb) whatis i
type = int
(gdb) whatis ary
type = int *
(gdb) whatis index_to_the_moon
type = void (int *)
```

## Setting Breakpoints

As you debug problematic code, it is often useful to halt execution at some point. Perhaps you want to stop execution before the code enters a section that is known to have problems. In other cases, you can set breakpoints so that you can look at the values of certain variables at a given point. In other situations, you might find it useful to stop execution so you can step through the code one instruction at a time.

GDB enables you to set breakpoints on several different kinds of code constructs, including line names and function names, and also enables you to set conditional breakpoints, where the code stops only if a certain condition is met. To set a breakpoint on a line, use the following syntax:

```
(gdb) break linenum
```

To stop when the code enters a function, use the following:

```
(gdb) break functionname
```

In either case, GDB halts execution before executing the specified line number or entering the specified function. You can then use print to display variables, for example, or use list to review the code that is to be executed.
