The context switch between programs happens so rapidly that you have the illusion that your program is running all the time.

Task preemption happens automatically and unavoidably; very few processes escape exemption. What you might not realize, however, is that a process can voluntarily yield its CPU time. That is, while a process cannot request additional CPU time, it can voluntarily give it up. The implication for a developer is that you can delay executing blocks of code if they are noncritical or on input from other processes that are still running. The function that makes this possible is named `sched_yield()`.

Multitasking, while a boon for concurrent users, poses (at least) three potential problems for programmers: deadlocks, livelocks, and races.

- **Deadlocks**—A deadlock occurs when two or more processes are unable to proceed because each is waiting for one of the others to do something. Deadlocks happen in many ways. For example, an e-mail client is communicating with a mail server, waiting on the server to send a message. A deadlock occurs if the server is waiting for input from the e-mail client before sending the message. This type of deadlock sometimes occurs when one or more low-priority processes never get time on the CPU because they are crowded out by higher-priority processes. A common type of deadlock occurs when two processes are trying to send data to each other but cannot because their input buffers are full because they are so busy trying to send data that they never read any data sent by the other process. This type of deadlock is referred to as starvation.

- **Livelocks**—A livelock occurs when a task or process, usually a process, is unable to finish because its clients continue to create more work for it to do before the server can clear its queue. The difference between livelock and deadlock is that a deadlock process doesn't have any work; it is blocked or waiting for something. A livelocked process, on the other hand, has too much to do and never empties its queue.

- **Races**—A race occurs when the result of a computation depends on the order in which two events occur. Say, for two processes are accessing a file. The first process writes data to the file and the second process reads data from the file to calculate and display a summary value. If the reader reads the file after the writer completes, the reader calculates and returns the correct value. If the reader process reads the file before the writer completes, the reader will calculate and return an incorrect value.

## Chapter 28 Programming Environments and Interfaces

The likelihood of deadlocks, livelocks, or races occurring increases dramatically on multitasking (multuser) systems because the number of processes that are potentially competing for a finite number of resources is greater. Good design, careful analysis, and the judicious use of locks, semaphores, and other mutual exclusion (mutex) mechanisms, which mediate access to shared resources, can prevent or reduce their occurrence.

## Multiser by Design

Linux is multiuser by design, an element of the Linux development model that has far-reaching consequences for developers. A program cannot assume, for example, that it has access to any resource such as a file, memory, peripheral devices, or CPU time; multiple programs might be attempting to print simultaneously or trying to allocate memory.

Similarly, a program cannot be written with the assumption that only one copy of the program is running at a time. So, if you are writing a program that creates working files in /tmp, you need to ensure that the temporary files created by Bob's copy of the program are distinct from the temporary files created by Mary Beth's instance of the program. If you don't, hilarity will ensure (if not hilarity, least confusion and consternation).

Another common need is for programs to honor per-user configurations. At start-up, a program might apply reasonable global defaults and then read a user's configuration file to apply, a custom color scheme.

There are also a number of per-user settings, such as environment variables, that programs need to know how to accommodate. For example, the $MAIL environment variables which define the user's mail file is and the VISUAL environment variable defines the user's preferred full screen editor (which all Linux users know). The $SPRINTER environment variable stores the name of the user's default printer, and $HOME identifies the user's home directory.

In a persistently multiuser system like Linux, programmers must always take into account that most resources a program might want to use are shared. Likewise, they must also take into account that real-world usage scenarios (more formally known as use cases) assume that multiple instances of the program are running at the same time.

## Interprocess Communication

Interprocess communication (IPC) enables programs to share data and resources with a minimum amount of overhead and is used extensively on all Linux systems. It is especially common with daemons and server process that spawn child processes to handle client connections. IPC comes in three varieties: shared memory, semaphores, and message queues:

- **Shared memory**—Shared memory is just set aside for what the name suggests: a region or segment of memory specifically set for use by multiple processes. Because shared memory is never paged out to disk, it is an extremely fast for two processes to exchange data.

- **Semaphores**—Semaphores, briefly mentioned in the “Preemptive Multitasking” section, are flags that indicate a condition controlling the behavior of processes. For example, one process can set a semaphore to indicate a specific file is in. Before other processes attempt to access that file, they check the semaphore’s status and (or shouldn’t) attempt to access the file if the flag is set.

- **Message queues** —Message queues are first-in-first-out (FIFO) data structures that make it possible for processes to exchange short messages in a structure, ordered manner.

Message queues are not necessarily accessed. System V UNIX-style message queues are, but POSIX message queues enable readers to pull messages out of a queue in an arbitrary order.

Shared memory, semaphores, and message queues are idiomatic in the Linux development environment. They solve three distinct domains of problems that arise when multiple processes need to exchange data or share resources without having to resort to slow disks files. All of which is to say that you don’t always need IPC, but it sure is nice to have when you do need it.

## The Building Blocks Philosophy

The building blocks philosophy characterizes the Linux development expressed as a series of rules or principles:

- Do one thing very well.
- Whenever possible, accept input data from standard input and send output data to standard output.
- Keep individual programs as self-contained as possible.
- Remember that someone will use your program in ways you didn’t intend and for purposes that you never imagined.

The first rule means that programs should not try to be all things to people: a text editor doesn’t need to be able to send e-mails and a drawing program doesn’t also need to be able to function as a browser. Although it is less true today than it used to be, the best Linux programs don’t have every imaginable feature (also known as featuris). Rather, developers spend time perfecting the program’s intended purpose and making it possible for programs to interoperate.

The second rule allows you to create chains of commands, each of which uses the output of the previous command as its input. A typical use of this behavior is a command pipeline, as in the following contrived example:

```
$ cat /etc/passwd | cut -f 5 -d | tr [:lower:] [[:upper:] | sort | head -5
```

The first part of the command pipeline, cat /etc/passwd, writes the contents of the /etc/passwd file to standard output. The second part, cut -f 5 -d, cuts the fifth field of standard input (the contents of /etc/passwd), using the character (:) as the field delimiter (the fifth field of /etc/passwd is the GECOS name).

The third part, tr [:lower:] [[:upper:]], translates all lowercase characters in the standard input to uppercase characters. The next element, sort, performs an alphabetic sort on the first letter of its input before sending the sorted list to output. The final component, head -5, displays only the first five lines of its input to standard output. The output of this pipeline might resemble:

```
ADM
BIN
DAEMON
GAMES
LP
```

The following command pipeline should prove more useful: it e-mails the current uptime and load to the root user:

```
uptime | mailx -s "System Usage" root
```

The third rule, keeping programs self-contained, is related to the second. The concern behind is that programs designed for use in command pipelines make no assumptions about what their input might look like or any massaging of the output.

The cut command shown in the first command pipeline takes arbitrarily formatted input and allows the user to specify on which piece of data to operate (the fifth field in the example, where fields are colon-delimited) and then displays the requested data on standard output. cut doesn't do any post-processing of the output, allowing the user to do it as she pleases, possibly using another tool.
