
# Using ssh, scp, and sftp Without Passwords

For machines that you use a great deal (particularly machines behind a firewall on your LAN), it is often helpful to set them up so that you do not have to use a password to log in. The following procedure shows you how to do that.

These steps take you through setting up password-less authentication from one machine to another. In this example, the local user is che on a computer named host1. The remote user is also che on a computer named host2.

- 1. Log in to the local computer (in this example, I am on chester to host1).
Run Step 2 only once as on your local workstation. Do not run again unless you lose your ssh keys. When configuring subsequent remote servers, skip right to Step 3.

- 2. Type the following to generate the ssh key:
```bash
$ ssh-keygen -t dsa
```

- 3. Accept the defaults by pressing Enter at each request.

- 4. Type the following to copy the key to the remote server (replace chester with your username and host2 with the remote host name):

```
$ cd ~/.ssh
$ scp id_dsa.pub chester@host2:/tmp
chester@host2's password: *************
```

- 5. Type the following to add the ssh key to the remote user's authorization keys (the code should be wrapped on one line, not wrapped):
```bash
$ ssh chester@host2 'cat /tmp/id_dsa.pub >> /home/chester/.ssh/authorized_keys'
```

In the previous two steps you are asked for password. This is.

For the ssh daemon to accept the authorized_keys file you created, your home directories and file itself must have secure permissions. To secure that file and those directories, type the following:

```
$ ssh chester@host2 chmod 700 $HOME/.ssh
$ ssh chester@host2 chmod 600 $HOME/.ssh/authorized_keys
```

- 6. Type the following to remove the key from the temporary directory:
```bash
$ ssh chester@host2 rm /tmp/id_dsa.pub
```

You should not be asked for a password in the previous step.

# Securing Linux Servers

It is important to note that once you have this working, it will work regardless of how many times the IP address changes on your local computer. The IP address has nothing to do with this form of authentication.

Opening up your Linux system as a server on a public network creates a whole new set of challenges when it comes to security. Instead of just turning nearly all incoming requests, your computer will be expected to respond to requests for supported-services (such as Web, FTP, or mail service) by supplying information or possibly running scripts that take in data.

Entire books have been filled with information on how to go about securing your servers. Many rely on internet servers assign full-time administrators to watch over the security of their servers. So, think of this section as an overview of some of the kinds of attacks to look out for and some tools available to secure your Linux server.

# Controlling Access to Services with TCP Wrappers

Completely disabling an unused service is fine, but what about the services that you really need? How can you selectively grant and deny access to these services? For Linux systems that incorporate TCP wrapper support, the /etc/hosts.allow and /etc/hosts.deny files determine when a particular connection should be granted or refused for services such as login, ssh, telnet, finger, and talk.

Most Linux systems that implement TCP wrappers do for a set of services that are monitored by a single listening process called the Internet server. For Red Hat systems, the service is the xinet daemon, while in other systems (such as Debian) the inet daemon is used. When a service relies on TCP wrappers is requested from the server process, the hosts.allow and hosts.deny files are scanned and checked for an entry that matches the IP address of the connecting machine. Checks are made when connection occurs:

- If the address is listed in the hosts.allow, the connection is allowed and hosts.deny is not checked.

- If the address is in hosts.deny, the connection is denied.

- If the address is in neither file, the connection is allowed.

Keep in mind that the order in which hosts are evaluated is important. For example, you cannot deny access to a host in the hosts.deny file that has already been given access in the hosts.allow file.

It is not necessary (or even possible) to list every single address that may try to connect to your computer. The hosts.allow and hosts.deny files enable you to specify entire subnets and groups of addresses. You can even use the keyword ALL to specify all addresses. You can also restrict entries in these files so they apply only to specific network services. Look at an example of a typical pair of hosts.allow and hosts.deny files. Here's the /etc/hosts.allow file:

```
# hosts.allow This file describes the names of the hosts are
# allowed to use the local INET services, as decided
# by the /usr/sbin/tcpd server.
```

```
cups-lpd: 199.170.177.
innetd: 199.170.177. .linuxtoys
vsftpd:
```

Here's the /etc/hosts.deny file:

```
# hosts.deny This file describes the names of the hosts which are
# *not* allowed to use the local INET services, as
# decided by the /usr/sbin/tcpd server.
```

```
ALL: ALL
```

The preceding example is a restrictive configuration. It allows connections to the cups-lpd and telnet services from certain hosts, but then denies all connections. It also allows connections to the FTP service (vsftpd) as them. Let's examine the files in detail.

As usual, beginning with a # character and comments are ignored by xinetd when it parses the file. Each noncomment line consists of a comma-separated list of daemons followed by a colon (:) character and then a comma-separated list of addresses to check. In this context, a client is any computer that attempts to access a network service on your network.

A client entry can be a numeric IP address (such as 199.170.177.25) or a host name (such as jukebox.linuxtoys), but is more often a wildcard that specifies an entire range of addresses. A client entry can take four different forms. The online manual for the hosts.allow file describes them as follows:

- A string with a dot (.) character is matched if the host name and the last components of its name match the specified pattern. For example, the pattern .tue matches the host name wzv.win.tun.

- A string with a dot (.) character. A host address is matched if its first numeric fields match the given string. For example, the pattern 131.155 matches the address of (almost) every host on the Eindhoven University net-work (131.155.x.x).

A string that begins with an at (@ sign is treated as an NIS netgroup name. A host name is matched if it is a host member of the specified netgroup. Netgroup names are not supported for daemon process names or for client names.

An expression of the form n.n.n/m.m.m is interpreted as a net/mask pair. A host address is matched if it is equal to the bitwise and of the address and the mask. For example, the net/mask pattern 131.155.72/0/255.255.255. matches the range 131.155.72 through 131.155.254.

The example hostallow contains the first two types of client specification. The 199.170.177 will match any IP address that begins with that string, such as 199.170.177. The .linuxtoys.net will match host names such as jukebox.linuxtoys or picframe.linuxtoys.

Let's examine what happens when a host named jukebox.linuxtoys (with IP 199.170.179) connects to your system using the Telnet protocol. In this case, the Linux system is Fedora, which uses the xinetd daemon to listen for service requests with TCP:

1. xinetd receives the connection request.
2. xinetd compares the address and name of jukebox.linuxtoys to the rules in hostsallow. It starts at the top of the file and works its way down until it finds a match. Both the daemon (the program handling the network service on your Fedora box) and the connecting client's IP address or name must match the entry in the hosts.allow file. In this case, the second rule that encountered matches the request: in.telnetd:199.170.179.linuxtoys.net
3. The jukebox host is not in the 199.170.177 subnet, but it is in the linuxtoys.net. xinetd stops searching as soon as it finds this match.

How if jukebox connects to your box using the CUPS-ld protocol? In this case, none of the rules in hosts.allow; the only line that refers to the IP daemon does not refer to the 199.170.179 subnet or so xinetd connects to the hosts.deny file. The entry ALL: ALL matches, so tcpd denies the connection.

The ALL wildcard was also used in the hosts.allow file. In this case, we are telling xinetd to permit absolutely any host to connect to the FTP server on the Linux box. This is appropriate for running an anonymous FTP server that anyone can access. If you are not running an anonymous FTP server, you should not use the ALL flag.
