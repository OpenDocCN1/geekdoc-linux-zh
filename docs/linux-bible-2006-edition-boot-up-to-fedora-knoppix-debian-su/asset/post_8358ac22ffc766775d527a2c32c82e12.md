
## Chapter 29 Programming Tools and Utilities

RCS command-line options are cumulative, as you might expect, RCS does a good job of disallowing incompatible options. To check and lock a specific revision of howdy.c, you would use a command such as co -l -r2.1. Similarly, ci -u -r3 howdy.c assigns revision 3.1, and deposits a read-only revision 2.1 file back into your working directory.

The following example creates revision 2.1 of howdy.c. Make sure you have checked out and changed howdy.c somehow before executing this command.

```
$ ci -r2 howdy.c
RCS/howdy.c.v <- howdy.c
new revision: 2.1; previous revision: 1.2
enter log message, terminated with single '.' or end of file:
>> Added something
>>
done
```

This command is equivalent to ci -r2.1 howdy.c.

The next example checks out revision 1.2 of howdy.c, disregarding the presence of higher-numbered revisions in the directory.

```
$ co -r1.2 howdy.c
RCS/howdy.c.v --> howdy.c
revision 1.2
done
```

The handy command now discards all of the changes you've made and starts over with a new source file.

```
$ co -l -f howdy.c
RCS/howdy.c.v --> howdy.c
revision 2.1 (locked)
done
```

When used with ci, -f forces RCS to check in a file if it has not changed.

## Source Code Control with CVS

You may have noticed that RCS has some shortcomings that make it inadequate for use on large projects. Without some sophisticated wrapper scripts to provide the directory handling machinery, RCS doesn't work well with a single, centralized repository.

An RCS repository is always the current directory unless you exert yourself to a directory located elsewhere. More pertinent for Linux and other open source projects, RCS is utterly unsuitable for distributed development because it doesn't support network protocols. (That is, it doesn't work over the Internet.)

The Concurrent Versions System CVS supports both centralized repositories and network-based access. It is well-suited for use by multiple programmers, and a CVS repository can support multiple projects. To keep the discussion simple, however, the example in this chapter deals only with a repository accessed locally. The following steps resemble the process described earlier for RCS, but they are slightly more involved and obviously using CVS concepts.

- 1. Create a CVS repository:
- mkdir /space/cvs
- export CVSROOT=/space/cvs
- cvs init

The first command creates a directory /space/cvs to establish the repository. The second command defines the environment variable $CVSROOT makes CVS much simpler. The third command initializes the repository, which creates some administrative CVS needs to work properly.

- 2. Create a top-level working directory in to store your various projects and then cd into it:
- mkdir projects
- cd projects

- 3. Check out a copy of the CVS root directory into the directory you just created:
- cvs -d $CVSROOT co -l
- cvs checkout: Updating

The -d option tells CVS the directory containing the CVS repository ($CVSROOT, or /space/cvs); co means check out (as with RCS); the -l option, which stands for local, means to work in the current directory rather than recursing through subdirectories; and the . specifies the current directory.

- 4. Create a directory to hold a project and add it to the repository:
- mkdir hello
- cvs add hello
Directory /space/cvs/hello added to the repository

- 5. cd the new directory, copy your project files into it, and then add all files (and any directories that might be) to the repository:
- cd hello
- cp projects/*
- cvs add *

cvs add: scheduling file 'hello.c' for addition
cvs add: scheduling file 'msg.c' for addition
cvs add: scheduling file 'showit.c' for addition
cvs add: use 'cvs commit' to add these files permanently

- 6. Do as the instructions recommend: Execute the command `cvs commit` to make the added files and directories permanent. You'll first see a screen (which is actually a vi editor session) asking you to enter a log message. If you don't want to enter a log message, press `Esc`, type `ZZ` to save and exit. After you see the vi commit, the output should resemble the following:

```
$ cvs commit
cvs commit: Examining
RCS file: /space/cvs/newhello/hello.c.v
done
Checking in hello.c;
/space/cvs/newhello/hello.c.v <-- hello.c
initial revision: 1.1
done
RCS file: /space/cvs/newhello/msg.c.v
done
Checking in msg.c;
/space/cvs/newhello/msg.c.v <-- msg.c
initial revision: 1.1
done
RCS file: /space/cvs/newhello/showit.c.v
done
Checking in main.c;
/space/cvs/newhello/main.c.v <-- main.c
initial revision: 1.1
done
```

Notice that RCS file-naming conventions to work with files in the repository. This is because CVS is built on top of RCS and retains compatibility with the basic feature set. CVS handles files in and out differently than RCS. When checking out file, it is not necessary to specifically request a lock to get a writable copy of the file. To work on a file, you need to use the `checkout` or `co` command:

```
$ ~/projects
$ cvs -d /space/cvs checkout newhello
U newhello/hello.c
U newhello/msg.c
U newhello/main.c
```

The **checkout** command used in this example specifies the path to the repository using the `-d` option. This is unnecessary if you set the CVSROOT environment variable. After you have made changes to files, you can check them in using the `cvs commit` command (commit is comparable to RCS's `ci` command):

```
$ cd ~/projects/newhello
$ cvs commit
cvs commit: Examining .
[editor session]
Checking in main.c:
/space/cvs/newhello/main.c <- main.c
new revision: 1.2; previous revision: 1.1
done
```

When you check in a modified file, CVS opens an editor session to enable you to log a message that describes the changes. The editor used is the editor defined in the $EDITOR variable or default (usually vi editor) if $EDITOR is undefined.

To check out a specific version, or revision of a file, use the -r option following the checkout or co command, by revision number. For example, to check out revision 1.1 of the main.c file, use the following command:

```
$ cvs checkout -r 1.1 newhello/main.c
newhello/main.c
```

To see the differences between two revisions, use the diff command, using -r m,n where m indicates the revision number you want to check. If you specify -r only once, the indicated version will be compared against the working file (using the diff option). If you specify -r twice, the two versions will be compared against each other. The following example compares revision 1.2 of showit.c to the current working (the current revision in the working directory):

```
$ diff -r 1.2 main.c
Index: main.c
```

```
RCS file: /space/cvs/newhello/main.c
retrieving revision 1.2
retrieving revision 1.3
diff -r1.2 -r1.3
9,10,c
```

```
< char msg_hi[] = {"Hi, programmer!"};
< char msg_bye[] = {"Goodbye, programmer!"};
> char msg_hi[] = {"Hi, programmer!\n"};
> char msg_bye[] = {"Goodbye, programmer!\n"};
12c12
>    printf("%s\n", msg_hi);
>    printf("%s\n", msg_bye);
```

The diff output is easier to understand than you might expect. Lines that begin with < appear in the first file (revision 1.2 of main.c) but not in the second (revision 1.3 of main.c). Similarly, lines beginning with > appear in the second file, but not in the first. Each section of diff output begins with an alphanumeric sequence such as 9,10,c9 or 12c12.

The numeric values of the diff output indicate the lines in the first and second files to which an operation must be applied to get the second file from the first. The operation to perform, such as inserting, deleting, or changing lines, is specified by the alphabetic character. So, for example, the sequence 9,10c,9 means to create the second file from the first you have to change (c) lines 9 and 10 of the first file to 9 and 10 of the second file.

Finally, if you totally back all of your changes to your working files and revert to the most recent versions, use the update command. It updates the directory with the most recent versions updated in the repository, as shown in the following example:

```
$ cd ~/projects/newhello
$ cvs update
cvs: Updating .
U show.c
U msg.c
U hello.c
```

There's more to CVS than the few examples presented here. For additional information, visit the CVS home page on the Web at www.gnunu.org/cvs.

## Debugging with GNU Debugger

Software is buggy, and some programs have more bugs than other programs. While debugging sessions will never be aggravation-free, GDB's advanced features lighten the load and enable you to be more productive in squashing bugs.

Effective debugging requires that your source code be compiled with the -g option to create a binary with an extended symbol table. For example, the following command

```
$ gcc -g file1 file2 -o prog
```

causes prog to be created with debugging symbols in its symbol table. If you want, you can use GCC -ggdb option to generate still more (GDB-specific) debugging information. However, to work most effectively, this option requires that you have access to the source code for every library against which you link. While this can be very useful in certain situations, it can also be expensive in terms of disk space. In most cases, you can get by with the plain -g option.
