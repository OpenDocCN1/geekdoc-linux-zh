# REQUEST HANDLERS

For some phases, it makes sense to use only one of the modules present in the server. For others (like logging modules), all of the modules present in that phase can be invoked successively. Each module can have a handler for any phase that you want it be invoked. The Web server checks each module during a phase to see if it has a handler and should be invoked for that phase. The handler for the module can do one of three things:

+   - Act on the client request (process it or participate in its processing) and return an OK code when finished.

+   - Decline to participate by returning a DECLINED code. (In this case, the server completely skips the module for this request and moves on.)

+   - Return an error code (one of the HTTP errors), which causes the Web server to stop normal processing of the request and proceed to the error processing and logging functions.

Most of the time, a phase uses the first module it hits. However, the logging,ups, and non-access authentication checking (Step 4 in the preceding list) use all handlers that respond to the request. For example, all logging modules are always queried so that several different types of logging can be performed for each request as appropriate.

The response phase is unique because a single module can have several handlers (like functions) for that single phase. The correct handler is chosen according to the MIME type of the requested object (which is determined two steps earlier). One of the handlers in a response phase module can even handle any request using a wildcard as the MIME type to it responds: /*, but these will be used only if more specific handlers for the MIME type have failed or not found.
