# Answering More Complex Questions

Below are some additional questions you might ask about your site. These are all relevant questions, but you may have difficulty finding the answers. We have provided a little guidance on how you might go about getting some information about them.

The problem with these questions is that they make assumptions about users' actions based on limited data in a log file or they require an examination of multiple entries spread across a log file to get a single factor.

# HOW MANY USERS HAVE VISITED YOUR SITE?

Learning how many users have visited your site can be a challenge. Apart from the problems with proxy and caching servers, and the lack of validity in hits, it's hard to gather data when visitors use several systems to access your site or use browsers that don't pass on much information about the user at all.

Still, many of the better Web statistics programs do quite well at making an educated guess at the true number of visitors. This is done by collating all hits from a single hostname within an hour of each other, or counting the number of unique hostname accesses to any page with a .html extension (as not all users begin at your home page).

Knowing how many users visit your site gives you a true picture of the influence your Web site has on the overall effects of your organization. It tells you how much you can rely on your Web site to disseminate information to your users and how well your promotions about your site are reaching your target audiences.

# HOW LONG IS AN AVERAGE VISITOR SPENDING AT MY SITE?

Knowing how long visitors browse your site tells you how interesting your material is and how much influence the things on your site are likely to be with users. The more time they spend on your site, the more likely they'll act on the things they see.

Unfortunately, it's basically impossible to get true information about the time a user spends looking at your Pages. The reason is simple: The Web is designed to avoid tying up a server while someone is reading a Page. Once the page is downloaded, you have no idea how long a user looks at it or how many times she returns to that page (stored locally in the browser cache directory) and reviews it without ever requesting it from your Web server.

What can be done statistically (with moderate success, mind you), is to examine the number of hits to all html pages by a unique hostname within a center block of time (say, one hour). If you assign an average time to each html file based on its size (for example, every 16K of html file is assumed to be seven minutes of reading/skimming), then you can judge the amount of time spent browsing the site by the number and size of html pages downloaded from your server during a “browsing period” that is defined by the first and last request made by a given hostname within a given period (a single “browsing session”).

This number is not terribly scientific, but taking an average of figures arrived at in this manner will easily tell you whether visitors are stopping at your home page and never going any further, or whether they're spending a while looking over most of your site, downloading pages, and reading one they find.

> Note that this exercise isn't very useful if you have only one or two pages on your site.

# ARE PEOPLE TRYING TO BREAK INTO MY SITE?

Security is always a concern with Web sites. Other sections of this book address the topic more thoroughly, but statistics for your Web site can tell you some things because they record every transaction or attempted transaction.

Simple reviews of your error log and access log can give you a warning of people looking to cause you grief with their hacking. Use your statistical tools or the grep utility (with others) to review things like this:

- Is a single hostname listed in the error log more than ten times in a single day?

If someone is exploring your site for unlisted documents by trying various URLs, he'll get a lot of "Document Not Found" errors in the process. If he's trying to get into a password-protected document, he'll get a lot of "Access Allowed" errors.

- Is a single hostname listed in the access log more than ten times in a single day?

If he's trying to get into a password-protected document, he'll get a lot of "Access Allowed" errors.

# ARE PEOPLE RETURNING TO SITE AT REGULAR INTERVALS?

Repeat visits are key to success. Answering this question can tell you if your site is helping you achieve this goal.

# Understanding Server Log Files

If you reviewed Chapter 11, you may remember a little about the log files that are written by the Web server. Almost any Web server creates log files in the same format. This format, the Common Log Format, was defined by the early Web designers at CERN and the NCSA project. Every file you sent from the Web server generates a log entry. A log entry might look like this:

```
dynamo.target.org - [02/Sep/1997:14:02:22 -0800] GET /Index.html HTTP/1.0 200 44398
```

The entry contains the following fields:

- The hostname of the person requesting the file, as reported by the browser. Depending on how your configuration files are set, this might be recorded as the IP address of the user's machine instead of this hostname. An additional feature of Apache allows you to have the Web server do a reverse lookup of each hostname to be that every system that requests a file is really who it claims to be. This security feature uses a lot of processor and network bandwidth, however, and is not necessary on most sites.
- The username given to permit access to the requested file. This field is only used if a file has user-level authentication set in a <LIMIT> container in the access.conf file.
- User identification information, as returned from the requesting host, using identd security. This authorization information is rarely used.
- The date and time when the transfer was completed (recorded in Universal Time, with an offset hour based on your local time zone).
- The request string from the browser. This will usually be a GET command, which includes the name of the file to be sent and the pathname it was requested by the browser (thus relative links will not include a full path starting at your document root).
- The http protocol code that was sent with the data. For all entries in the access log, this will likely be 200, the code for "OK." Other codes, such as "File Not Found," "Insufficient Access Rights," "File Moved," and so forth, are considered error conditions and are recorded in the error log file.
