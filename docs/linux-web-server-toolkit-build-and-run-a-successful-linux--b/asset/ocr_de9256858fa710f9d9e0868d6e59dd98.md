Users are stored in databases. A default database is selected automatically as you work in the Access Control pages, and that default database is fine to use for most things. The only reason to have additional databases, which you can create and name, is to help you keep track of different sets of users that are granted access on your system for different purposes, or perhaps you track a large number of users.

For example, suppose you have a server that your clients access to view samples of your work on their projects. You might have a separate user database called Clients that contains all of these. A second database (or perhaps the default database) might contain internal users who have access to special areas where you can view project details or internal progress reports on the Web site.

The pages in the Access Control section of the Administration server for FastTrack might seem organized in a way that doesn't make sense, but I will describe them in the order they appear, so you can keep track of where they are. After you've read each of the 11 pages, you should have a good idea of how they all work together.

# Create User

From the Create User page, you add a new user to the database of users for your FastTrack Server access control. A user must be added to a database before you can specify access control to a file for that user, and before you can tell someone that username and password to gain access to the file.

Adding a username in this page is similar to adding a user to your OpenLinux system, but adding a user in Linux doesn't make that user available in the web server Access Control database (for more information, see the section on Import Users later in this chapter).

To add a user, fill in the fields shown in Figure 12-8. Enter a complete user name for your own information, then choose a login name. The login name is the name that must be entered by someone trying to access a page that you have protected with access control. Enter a password for this user, once each of two-password fields (they have to match). You must give the password to anyone who will access the protected pages.

If you have created groups, you can select which group this user is part of. Groups aren't needed, but placing users in groups and granting access based on group membership is an effective way to grant access to several people at once. You can't grant access based on which database a user is in. Groups cannot cross databases.

Finally, you can select which database this new user is part of. The default database is fine unless you created other databases for some reason (see the discussion of the Manage User Databases page that follows).
