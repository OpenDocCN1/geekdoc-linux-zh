# LANGUAGE DIRECTIVES

The following directives are also for content negotiation:

- AddLanguage en .en
- AddLanguage fr .fr
- AddLanguage de .de
- AddLanguage it .it
- LanguagePriority en de fr

The AddLanguage directive gives a standard Internet language code followed by the filename suffix used for that of type. The LanguagePriority directive gives an order that should be used instead in case of a conflict or a browser that can accept multiple languages.

The AddLanguage and LanguagePriority directives assume a browser is being used that can negotiate the language preferred by the user. The default srm.conf file contains several AddLanguage statements that are not included here. The LanguagePriority is arranged by default according to the largest markets in which Caldera is sold. You should rearrange these priorities to your area and target users.

Here's a simple example of how the language directives are used. Suppose you created an index.html file for your home page. When you translated it into German, Finally, you made a copy of the English version named index.html.en and a copy of the German version named index.html.de.

Now a browser asking for index.html, specifying German (with de as the Internet code for this) as the preferred language. The server notes from the AddLanguage directive that uses the extension .de, so it looks for index.html.de, find it, and sends it off. If English and German had both been acceptable, the English file would have been sent instead because of the LanguagePriority directive.

Content negotiation is a powerful feature of Web servers and its use will increase as browsers become more powerful. The ability to use scripts on your Web server (see Chapter 10) also requires some configuration of the srm.conf. This is discussed in the next section.

# Using Scripts

In Chapter 10, I described how to use scripts on your Web server. Scripts can be dangerous, as I repeatedly said. The srm.conf file includes a directive, ScriptAlias, that defines where scripts are located. If a user requests a file in a script directory defined by this directive, the Web server will attempt to run the file as a program instead of simply returning the contents of the file. The following is the default value of the directive:

ScriptAlias /cgi-bin/ /home/httpd/cgi-bin/

The default says that any document requested using a filename in the /cgi-bin directory will actually be located in /home/httpd/cgi-bin and should be executed instead of returned for display.

You can list several aliases anywhere on your server. Remember the items noted in Chapter 10 about using scripts and use the ScriptAlias directive with caution, noting the permissions of the directories you place in ScriptAlias directories and checking the files in that directory to see that they can be executed and provide valid results.

When you use the ScriptAlias directive, note that the “fake name” of the directory is listed first, followed by the real directory on the Web server where the scripts are located. This is the opposite of the ln command in UNIX used to create a symbolic link (file alias).

The remainder of the directives in the srm.conf default file are commented out. These lines are examples of more advanced features that are described later in this chapter.

# Chapter 11: Configuring the Apache Web Server

# Changing the Default Settings

The settings in the default srm.conf file should be sufficient for a standard Web server. Because the settings in srm.conf are informational in nature, they pose no security threat. However, they operate with other settings that do require vigilance, as you'll read in the next section on access.conf.

You might review the Indexno directive if you want to have indexing (automatic generation of directory listings) available if you are concerned that some common files in your directories are not shown in lists.

The AddEncoding directives can be altered to match the capabilities that you want to offer. Those listed in the default file are part of OpenLinux; you might find a Linux version of PKZip that would add a useful feature for non-UNIX browsers.

It is important that the directories under the ScriptAlias directive be listed in the access.conf file with restrictive rights.

The many other sample settings in the default srm.conf file are examples of advanced features described later in this chapter.

The srm.conf file defines what resources on your Web server are used to send information to browsers. The next section describes the third Apache configuration file, access.conf, which is used to manage the security of your Web server.

# Setting Up Security Options

The directives in the access.conf file are used to control who can access your Web server and how they can access it. The number of options available in this file is small compared to the other two configuration files discussed so far, but each directory on your Web site can have a set of separate set of options listed in this file.

Every directive in the access.conf file must be inside a pair of container tags that define a directory on your Web server. Most of these directories will be within the DocumentRoot area, but you also have a container for your script area and for any other areas that are accessed through links or aliases.

The default access.conf file on Linux includes containers for the DocumentRoot area (/home/httpd/html) and the script area (/home/httpd/cgi-bin). The access granted to these areas is described next, and then other possible options are presented.

# Understanding Document Tree Security

The first container in access.conf starts out with the following tag:

```
<Directory /home/httpd/html>
```

The directives discussed in this section are all included before it ends with </Directory> tag. The most restrictive set of options you can select is None, as follows:

Options None

The AllowOverride directive specifies which things can be overridden by an .htaccess file in a subdirectory of the document root. This example of the AllowOverride directive shows the most restrictive set you can select:

AllowOverride None

The order directive specifies whether to process the allow directive first or the deny directive first, as follows:

```
order allow,deny
allow from all
```

The order in which you use these directives is important. You can deny all hosts and then allow some hosts. If you reversed the order (allow some hosts, then deny all), the hosts listed as allowed would not have access.

With the default, any host can access the Web server. The other settings are restrictive enough to allow this without any real concerns.

# Understanding Script Directory Security

The Script directory, /home/httpd/cgi-bin/, has the same security as the Document tree, but with no allow directive explicitly included. It includes the following:

Options None
AllowOverride None

# Understanding the Options Directive

For each directory container, you can have an Options directive with one or more options after it. Table 11-1 describes each of the possible parameters for the Options directive.

TABLE 11-1 Possible Parameters for the Options Directive Within a Directory Container in access.conf

| Parameter | Description |
| :--- | :--- |
| Indexes | Allows a directory listing to be generated by the Web server and returned to the requesting user if no index.html or other configured default file is found. If Indexes are not allowed and no index.html exists, the user receives an error. |
| Includes | Including the Options option may let users see files intended to be viewed or it may reveal information about the server that poses a security risk. Allows files in this directory to server-side includes (SSI), a type of server preprocessing of html files which can present security risks. (Server-side includes are described in Chapter 10.) |
| FollowSymLinks | Allows files in this directory that are symbolic links to other files to be followed so the file link points to be sent. If this parameter is not included and the user requests a file that is a symbolic link, an error will be returned ("file not found"). |
| | Including this option allows users to access any part of your Web server outside the DocumentRoot area by a link to it. If a user can create or modify a file on your server, following a symbolic link can allow the user to get anything on your system. | |
