The main areas of configuration in this page are the processes/threads section, and the DNS section. The number of processes and number of threads used by the server (minimum and maximum) determine how much of your computer's time (CPU cycles, disk access time, and so forth) can be consumed by the Web server. It's important not to set these numbers too high if you're running other programs on the same computer, like a compiler, a database server, or even busy e-mail server. It's also important to raise the numbers if you are using this computer exclusively for a Web server. You want to make as many resources available as possible to improve performance of your server.

The second area is DNS, or domain name services. These resolve around looking up DNS information (hostnames) for incoming browser requests, and checking the validity of incoming DNS names for security purposes. The default values may suffice in this area for a very busy Web server. The more important consideration may be what information you wish to gather from your log files, as described in Chapter 13.

The effectiveness of both these performance tuning factors can be reviewed by clicking on the Server Status button which shows you a page with the real-time status of your Web server is performing. This status page is described later in this chapter.

## Network Settings

Network settings are the settings that you probably think of as the core configuration of your Web server. These include things like which user the server runs as, which port server listens to for incoming browser requests, and which IP address the Web server is bound to. These and a few other items make up the Technical Settings shown in the View Settings page (as described previously).

Each of the settings I just mentioned can be changed and they will immediately be active on the Web server that is currently running when the Apply button is clicked. Just remember that someone might be trying to access your Web server in the moment that you press the Apply button. Sometimes it's actually better to shut down your Web server before changing network settings such as the port number and IP address. The network settings that you can change are shown in Figure 12-7.

## Error Responses

HTTP, the Web protocol, uses a set of codes as responses to the requests that a Web server receives from a Web browser. If the code is 200, which indicates that everything went well (usually seen as 200 OK), the user never sees the response code. Other codes are considered warnings or errors and are usually displayed by the browser so that you can see them and evaluate how to solve the problem and get the requested document.

## Configuring Access Control

One of the most useful features of a Web server is its ability to control access to documents with a distinct username and password. You can require that a valid username and password be entered before any document is transferred to a browser. Although this is not a totally secure system, because the username and password cross the Internet as plaintext, it provides a very useful feature for many occasions when "unbreakable" security is not needed.

An example of using access control on a Web server would be a company producing materials for a client. The company can place samples or drafts on their Web site in an area set aside for the client. Only the client can access that part of the Web server because only the client is given the username and password that protects it.

![](img/e01f1106dd2902613fa07890c8baa7e6_352_0.png)

> The access control described in this section is a per-file or per-directory access control that is administered by the Web server (almost all Web servers offer this feature). It is completely different from other security features such as secure connections using SSL or HTTP.

Unfortunately, access control is sometimes one of the least used features of a Web server, simply because it seems hard to set up and manage. FastTrack takes the questions out of access control and makes it easy to use.

## Users and Groups

The first thing to know about access control is that it's based on users and groups. On Linux, you have a small database of users (actually a file with one line for each user, containing relevant facts) and a small database of groups (actually another file listing a group name and which users belong to the group).

Access control for your Web server is managed by a similar list of users and groups. You use the Access Control of the FastTrack Server to manage the lists of users and groups, and to specify which files they have access to.

Of course, if you don't use access control features, access to specific files and directories on your Web server is not controlled on a per-user basis at all. Instead, access is granted based on the rules for which host a user is accessing the data, and from similar security rules that don't require that someone know a valid username and password.

Users are stored in databases. A default database is selected automatically as you work in the Access Control. The only reason to have additional databases, which you can create, is to help you track different sets of users. For example, suppose you have a separate database called Clients that contains all users who access projects. A second database (or perhaps the default database) might contain internal users who view progress reports.

The pages in the Access Control section might seem organized in a way that doesn't make sense, but I will describe them in the order they appear. After you've read each of the pages, you should have a good idea of how they all work.

## Create User

From the Create User page, you add a new user to the database of users for FastTrack access control. A user must be added to a database before you can specify access control to a file, and before you can tell someone username and password to gain access to the file.

Adding a username in this page is similar to adding a user to your system, but adding a user in Linux doesn't make that user available in the web server Access Control database (for more information, see the section on Import Users later in this chapter).

To add a user, fill in the fields shown in Figure 12-8. Enter a complete username for your own information, then choose a login name. The login name is the name that must be entered by someone trying to access a page that you have protected with access control. Enter a password for this user, once each of two password fields (they have to match). You must give the password to anyone who will access the protected pages.

If you have created groups, you can select which group this user is part of. Groups aren't needed, but placing users in groups and granting access based on group membership is an effective way to grant access to several people at once. Groups cannot cross databases.

Finally, you can select which database this new user is part of. The default database is fine unless you created other databases for some reason (see the discussion of the Manage User Databases page that follows).
