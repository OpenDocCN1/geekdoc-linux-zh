# TRANSFERLOG

The TransferLog directive defines where the transfer log file is stored. Just like the error log, the transfer log is assumed to be located within the ServerRoot area unless the value of this directive starts with a forward slash. Again, the default here plus the aliased link in /etc/httpd/apache/logs serves both the Apache organization and the Linux standard, as follows:

```
TransferLog /var/log/httpd/apache/access_log
```

The transfer log is a file that contains a line for each file sent over your Web server in response to browser requests. This file becomes very large very quickly on busy sites. This file is also the subject of intense scrutiny by the statistics programs that count hits, examine who is visiting your site, and track other information. To some degree, you can determine what information is stored in this file. Details are provided later in this chapter.

The following is a sample of what a standard log entry looks like:

```
trumpet.infision.com - [05/May/1997:06:13:03 -0600] GET /doc/prodlist.html HTTP/1.0 200 77
```

### Rotating Log Files
It't take long for the log files on a busy Web site to become enormous. But they're too important just to discard. You need to save them for statistical review and study if security issues arise.

It's a simple matter to have a script or command run every night or every weekend that moves the existing log files to a saved location and starts new ones. You can place that script or command name in a "cron-job" using the at command or /etc/crontab file so that the script executes every day or every week automatically.

Consult the manual page for the logrotate command for more information (try man logrotate from any command prompt).

# PIDFILE

The PidFile directive defines where the PID file is stored. A program's PID is the process ID, a unique number generated by the operating system for every program running on the system. The directive is used as follows:

```
PidFile /var/run/httpd.pid
```

The PID file is a tiny file that contains the PID of the Apache server. Immediately after it starts, the Web server stores the PID file at the location specified by the PidFile directive.

Other applications can send signals to control the Web server if they can determine the PID of the Web server program. The PidFile directive defines a location for this important information to be stored.

# SCOREBOARDFILE

The ScoreBoard directive defines the location of the scoreboard. The scoreboard file is used by multiple Apache servers to communicate among themselves, as follows:

```
ScoreBoardFile /var/log/httpd/apache/apache_status
```

Because a master httpd starts new processes and needs to monitor busy they are, the scoreboard is used to facilitate that communication.

# SERVERNAME

The ServerName directive defines the name of the Web server. This directive allows you to set a name to send back to browsers making requests that is different from the name of the computer the Web server is running on. The directive is used as follows:

```
ServerName localhost
```

The ServerName directive is used in a few special circumstances. For example, if you have several computers servicing a busy Web site, the right router might slip the Requests among machines named web1, web2, and web3. You don't want the browser to think it's getting information from web1, web2, or web3; you want all requests to come to www. The ServerName directive allows you to set that machine name. Even if the real machine name was web3, you would set the ServerName directive to www. The default value of this directive in OpenLinux assumes you don't need to use the features provided by the ServerName directive.

# CACHOTIATEDDOCS

More and more gateways allow users to browse the Web use proxy gateway with caching to hold documents that are frequently requested on their local network. This reduces the number of times the gateway must actually go out on the network and get a document. The result is less waiting for the user and less traffic on the Internet.

But documents change frequently on the Web. The default for Apache is to instruct any proxy server capable of understanding that documents should not be cached. If you uncomment this directive, this instruction will not be sent to proxy servers. Your documents will be cached at proxy servers around the world when people request your documents.

If your documents are not likely to change often, for example, if your Web site is an archive of old literature, you can use the CacheNegotiatedDocs directive by removing the comment symbol #. This will save your visitors time if they visit your site frequently. For most business applications, caching is probably not helpful for keeping your customers informed, leave the CacheNegotiatedDocs directive as a default setting, as:

```
#CacheNegotiatedDocs
```

# TIMEOUT

The number of seconds that the Web server will wait for data passing between browser and Web server assuming the connection is dead and timing out is defined by the value of the Timeout directive, as:

```
# Timeout 400
```

The default value of 400 is about seven minutes. That's a pretty long wait but it allows for slow modems and busy connections.

A high timeout value is convenient for some users but it ties up resources on your Web server. The http process that's waiting can't serve another request in the meantime. If you have a busy Web server and think you might be short on resources at times, and if you won't have a lot of modern connections (though this is very hard to judge), then you could reduce this timeout value by half or more. A browser can request that a Web server maintain a persistent connection in order to improve the efficiency of a Web page transfer when the browser is making requests in rapid succession.

# KEEPALIVE

The KeepAlive directive determines how many requests can come in on one of these persistent connections. The KeepAliveTimeout directive determines how long the http server will wait between requests before dropping the connection and shutting down. The following is what those directives look like:

```
KeepAlive 5
KeepAliveTimeout 15
```

# LOAD-BALANCING DIRECTIVES

There are five directives that determine the load balancing of your Web server, as shown in the following:

```
MinSpareServers 1
MaxSpareServers 2
StartServers 1
MaxClients 15
MaxRequestsChild 30
```

Because Apache has a master server that spawns child processes - additional Apache servers to handle each request, you need to control these limits on your Web server according to the traffic that you anticipate and the capacity you have on your system.

The default directives just shown appear in the OpenLinux default httpd.conf file. They are different from the standard Apache defaults. The OpenLinux system uses the httpd server automatically for online help. If you intend to use the Apache server as an external web serving hundreds of documents on the Internet, you will want to reset the values of these parameters. (See the section on changing default settings for more information on this subject.)

The MinSpareServers directive determines the minimum number of Apache servers that are kept running, waiting for requests. The busier your site, the more servers you need to have waiting to accept requests without having to be started up after the request is received.

The MaxSpareServers directive determines the maximum number of Apache servers that can be started up. This keeps your system from being brought to its knees by a huge number of browser requests that spawn hundreds of servers more than your hardware can efficiently handle.

The StartServers directive tells the first Apache server how many additional web programs initiate to start. This is similar to the MinSpareServers; it gets gets off on the right foot.

The master copy of Apache that farms browser requests waiting in the wings to new servers if the MaxSpareServers number has been reached during a load spike. But if the MaxClients number of browser requests is reached, all connections will be refused until some of the existing requests have been serviced. Browsers that make a request when MaxClients have been reached will receive an error message from the server stating that no connections can be accepted and that they try again later.

Finally, the MaxRequestsChild tells how many browser requests a single Apache process can handle before it must be shut down and another started to replace it if the total number is less than MinSpareServers. This directive is to prevent a single Apache server from running too long and causing system problems.
