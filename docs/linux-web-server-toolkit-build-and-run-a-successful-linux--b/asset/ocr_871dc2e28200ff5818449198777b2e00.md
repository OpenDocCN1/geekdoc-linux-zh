# Chapter 4: Internet and UNIX Technologies

So how do these data exchange protocols work? Take example the Internet e-mail protocol, called Simple Mail Transport Protocol (SMTP). SMTP works this way: you write an e-mail message and hit Send. The message is sent by your mail server to another mail server on the Internet, where it is posted to the recipient's account as a new message.

However, your message may be passed between other servers on its way to the recipient's mail server. It may even be delayed for several days. The SMTP protocol is designed to handle the following aspects of Internet communications:

+   - Instantaneous delivery isn't required: no one is sitting waiting for the response, when someone requests a Web page or two people converse during an instant relay chat (IRC) session. E-mail can take up to five days on slow systems.

+   - Small messages: most e-mail messages are less than 1KB. Although I've burdened my system with many over 10MB, the protocol is less efficient sending those.

+   - One to one (sender and recipient): even if you address a message to many people, each message is a transaction from you to another. Compare this to the Web, which is a one-to-many transaction.

+   - Pushed from sender to recipient: regardless of whether your recipient wants a message from you, if you send an e-mail, it will be posted in her mailbox. Compare this to the Web, where the "recipient" (viewer) of a Web page must seek it out.

Another protocol you may be familiar with is the File Transfer Protocol (FTP). FTP servers contain archives of files, such as the latest Linux distribution. Users log in to the FTP server and download the files they want. The FTP protocol is designed differently from the SMTP protocol. FTP is optimized to handle the following aspects of Internet communications:

+   - Files transferred when the request is received: the receiver waits at the keyboard while the files are transferred.

+   - Large files: files of many megabytes are commonly transferred with FTP, and the protocol is designed to handle these efficiently.

+   - One to many: one server is open to everyone; many users retrieve the same files without a direct invitation.

+   - Pulled from the server by the recipient: the recipient goes after what he she wants, rather than the provider of information "pushing" the data to the recipient, as with an unsolicited e-mail.
