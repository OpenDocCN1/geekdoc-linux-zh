## Introduction to the Netscape API

The FastTrack server for OpenLinux has a comprehensive programming interface from which most of the server's functionality is derived. In fact, the FastTrack server uses this API to build the regular functions for the directives used in magnus.conf (the server configuration file) and obj.conf (the object configuration file). Using the application programming interface (API), you can create-plugins to insert into the directives in server configuration files.

Because the same API is used for your own applications and for the core of the FastTrack server, when you become familiar with the API, you also learn more how the server works. This means you can override the server functionality, add to it, or customize your own functions. Examples include creating functions that use a different type of database for access control (including working with an Oracle or NetWare NDS database on your OpenLinux system).

The FastTrack server can also use JavaScript or Java, JNI, and JavaScript. The API provides a lower-level interface for CGI, Java, and JavaScript. The API is a set of ANSI C functions and header files that use a common object model to interface with your own code.

# Linux Web Server Toolkit

Because it provides more features at a lower level, it's also not subject to the same restrictions – safeguards – as Java and JavaScript. That means that a plug-in you develop with the API can crash the Web server. Typical uses of API include:

- Customizing access control mechanisms
- Customizing error handling mechanisms
- Customizing request or error logging
- Initializing shared resources
- Modifications to the normal HTTP request-response process, including maintaining stateful systems

Although FastTrack provides several methods for programming or integrating programs with the Web server, the Netscape API is the fastest-executing, most powerful method available. CGI scripts in Perl or even C don't have as high performance, and Java or JavaScript won't even come close. For the best performance, the most flexibility, and the greatest power, use plug-in APIs.

Much like the UNIX model itself, API functions provide many small tools, carefully designed to do one task well. This provides a great deal of control over the server's behavior. Developers can implement their own systems for authentication, client tracking, access control, error logging, or other features.

## Using APIs to Your Advantage

The APIs for both Netscape and Apache are written in C, so any modules you want to write will be written in C as well. The following sections provide brief outlines of the functionality and operation of the Apache and Netscape APIs. You'll note from these outlines and also from the documentation included with the Apache and FastTrack servers that the functions available with the Apache system provide more flexibility and perhaps more power in the API, as well as more concrete examples, than the Netscape API.

The Netscape API, on the other hand, is not as rich, but probably easier to use. It doesn't advance as rapidly or for as deep or as wide an impact on the server's functionality. And, unfortunately, the Netscape Programmer's Guide has fewer code fragments to help you along the path than does the Apache documentation. That part is regrettable and not dictated by the commercial nature of the Netscape products.

Anyway, both APIs provide great capabilities and flexibility to you as you add features to your Web server. Use the information below to get a feel for the APIs, then refer to the documentation for each product for more complete information, including lists of functions and more technical detail than I can provide here.

## Programming with the Apache API

The Apache Web server is, as I've already said, the most widely used Web server in the world. Part of that is because it's free. But I think the more important factors are its robustness, speed, and leading-edge features.

Another part of that set of leading-edge features is the Apache API. As you'll note in the system documentation that you get with the Apache server on OpenLinux or from the Apache site (see http://www.apache.org), the API is continually being developed with new features available in every release. The documentation is always a little behind the breakneck pace of development, but you should still find ample material to keep you busy in the Apache online documentation.

This section only begins to explore the capabilities of the Apache API by defining the overall structure the API fits into. You'll need to get out your compiler and start coding to really see what can be done with it.

# HOW APACHE PROCESSES REQUESTS

The Apache Web server breaks down each request from a browser to a series of steps. The API has functions that handle each of these steps. As I mentioned earlier, you can replace the default functions or add additional ones to the standard functionality. There are more steps in this process than in the Netscape API. The steps are follows:

1. URI to Filename translate: Convert the requested URL/URI into a local filename by applying redirects, aliases, and so forth.
2. Authentication ID checking: Determine if the requesting user is who he says he is.
3. Authentication access checking: Determine if the requesting user is authorized to retrieve a document from the location requested.
4. Access checking: Types of access or authentication other than those described in Steps 2 and 3 above.
5. Determine the MIME type of the object requested (using the configuration files, file extension, and so forth.).
6. Fixups: This phase of the process isn't really used right now. Apache documentation includes it in flowcharts, but it's intended to be used for future extensions.
7. Response: Send a response document of some sort back to the requesting client.
8. Log the request to one or more log files based on the headers in the request and the action taken by the Web server.

Each of the phases in the preceding list can include one or more modules. For some, the standard Apache server connects with several modules; for others, the standard server includes only one module. For any of these phases, you can add a module to those included in that phase.

# REQUEST HANDLERS

For some phases, it makes sense to use only one of the modules present in the server. For others (like logging modules), all of the modules present in that phase can be invoked successively. Each module can have a handler for any phase that you want it be invoked. The Web server checks each module during a phase to see if it has a handler and should be invoked for that phase. The handler for the module can do one of three things:

- Act on the client request (process it or participate in its processing) and return an OK code when finished.
- Decline to participate by returning a DECLINED code. (In this case, the server completely skips the module for this request and moves on.)
- Return an error code (one of the HTTP errors), which causes the Web server to stop normal processing of the request and proceed to the error processing and logging.

Most of the time, a phase uses the first module it hits. However, the logging, fixups, and non-access authentication checking (Step 4 in the preceding list) use all handlers that respond to the request. The response phase is unique because a single module can have several handlers (like functions) for that single phase. The correct handler is chosen according to the MIME type of the requested object (which is determined two steps earlier). One of the handlers in a response phase module can even handle any request using a wildcard as the MIME type to it responds: /*, but these will be used only if more specific handlers for the MIME type have failed or not found.
