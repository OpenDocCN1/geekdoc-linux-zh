

有时你并不希望工作立即执行，而是希望在延迟一段时间后再执行。在这种情况下，你可以安排工作在未来的某个特定时间执行：

```c
schedule_delayed_work(work, delay);
```

在这种情况下，由 `&work` 表示的 `work_struct` 在未来至少 `delay` 个定时器滴答（timer ticks）内不会执行。使用滴答作为时间单位的内容在第 10 章中有详细介绍。

## 清空工作

排队的工作会在工作者线程下次唤醒时执行。有时，你需要确保在继续之前，给定的一批工作已经完成。这对于模块尤为重要，模块在卸载前几乎肯定会调用此功能。内核中的其他位置也可能需要确保没有待处理的工作，以防止竞态条件。

为了满足这些需求，有一个函数用于清空给定的工作队列：

```c
void flush_scheduled_work(void);
```

此函数会等待直到队列中的所有条目都执行完毕后才返回。在等待任何待处理的工作执行期间，该函数会休眠。因此，你只能在进程上下文中调用它。

请注意，此函数不会取消任何延迟工作。也就是说，通过 `schedule_delayed_work()` 安排的、且延迟时间尚未到期的工作，不会通过 `flush_scheduled_work()` 被清空。若要取消延迟工作，请调用

```c
int cancel_delayed_work(struct work_struct *work);
```

此函数会取消与给定 `work_struct` 关联的待处理工作（如果有）。

## 创建新的工作队列

如果默认队列无法满足你的需求，你可以创建一个新的工作队列和相应的工作者线程。由于这会为每个处理器创建一个工作者线程，因此只有当你的代码需要一组独特线程的性能时，才应创建独特的工作队列。

你通过一个简单的函数创建新的工作队列及关联的工作者线程：

```c
struct workqueue_struct *create_workqueue(const char *name);
```

参数 `name` 用于命名内核线程。例如，默认事件队列是通过以下方式创建的：

```c
struct workqueue_struct *keventd_wq;
keventd_wq = create_workqueue("events");
```

此函数创建所有工作者线程（系统中的每个处理器一个）并使它们准备好处理工作。

无论队列类型如何，创建工作的方式都是相同的。创建工作之后，以下功能类似于 `schedule_work()` 和 `schedule_delayed_work()`，区别在于它们作用于给定的工作队列，而不是默认的 `events` 队列。

```c
int queue_work(struct workqueue_struct *wq, struct work_struct *work);
```

```c
int queue_delayed_work(struct workqueue_struct *wq,
                       struct work_struct *work,
                       unsigned long delay);
```

最后，你可以通过调用函数来清空工作队列

```c
void flush_workqueue(struct workqueue_struct *wq);
```

如前所述，此功能的工作方式与 `flush_scheduled_work()` 完全相同，只是它在返回前等待给定的队列清空。

### 旧的任务队列机制

就像 BH 接口为软中断（softirqs）和任务（tasklets）让路一样，工作队列接口也是源于任务队列接口（task queue interface）的缺点。任务队列接口（在内核中通常简称为 `tq`），与 tasklets 一样，与进程意义上的任务（tasks）毫无关系。任务队列接口的用户在 2.5 开发内核期间被一分为二。一半用户转换为了 tasklets，而另一半继续使用任务队列接口。剩下的任务队列接口随后变成了工作队列接口。简要回顾存在了一段时间的任务队列，是一个有益的历史练习。

任务队列通过定义大量队列来工作。这些队列有名称，如调度器队列（scheduler queue）、立即队列（immediate queue）或定时器队列（timer queue）。每个队列在内核的特定时间点运行。内核线程 `keventd` 运行与调度器队列关联的工作。这是完整的工作队列接口的前身。定时器队列在每个系统定时器滴答时运行，而立即队列在多个不同的位置运行，以确保它是“立即”运行的（一种权宜之计）。还有其他队列。此外，你可以动态创建新队列。

所有这一切听起来可能很有用，但现实是，任务队列接口一团糟。所有队列基本上都是任意的抽象，散落在内核中，仿佛被抛向空中并停留在落地的地方。唯一有意义的队列是调度器队列，它提供了将工作推迟到进程上下文的唯一方式。

任务队列的另一优点是极其简单的接口。尽管队列众多且关于何时运行的规则随意，但接口尽可能简单。但仅此而已——任务队列的其他部分都需要移除。

¹ 下半部（Bottom-half）的命名显然旨在混淆新的内核开发者。说真的，这些名字很糟糕。

各个任务队列用户被转换为其他下半部机制。大多数切换到了 tasklets。调度器队列的用户保留了下来。最终，`keventd` 代码被泛化为我们今天拥有的出色的工作队列机制，任务队列终于从内核中移除。

### 我应该使用哪种下半部？

决定使用哪种下半部很重要。在当前的 2.6 内核中，你有三个选择：softirqs、tasklets 和工作队列。Tasklets 建立在 softirqs 之上，因此两者相似。工作队列机制则完全是一种不同的实体，建立在内核线程之上。

从设计上看，Softirqs 提供的序列化最少。这要求 softirq 处理器采取额外步骤以确保共享数据是安全的，因为两个或更多同类型的 softirqs 可能会在不同处理器上并发运行。如果相关代码已经是高度线程化的，例如在深入使用每处理器变量的网络子系统中，softirqs 是一个很好的选择。对于对时序敏感和高频使用的场景，它们肯定是速度最快的替代方案。

如果代码不是细粒度线程化的，Tasklets 更有意义。它们具有更简单的接口，并且由于同类型的两个 tasklets 可能不会并发运行，因此它们更容易实现。Tasklets 实际上是并发运行受限的 softirqs。除非准备好利用每处理器变量或类似魔术以确保 softirq 可以安全地在多个处理器上并发运行，否则驱动程序开发人员应始终选择 tasklets 而非 softirqs。

如果你的延迟工作需要在进程上下文中运行，三个选项中你唯一的选择是工作队列。如果进程上下文不是必须的——特别是如果你不需要休眠——softirqs 或 tasklets 可能更适合。工作队列涉及最高的开销，因为它们涉及内核线程，因此也涉及上下文切换。这并不是说它们效率低下，但考虑到每秒可能有数千个中断（如网络子系统中可能遇到的情况），其他方法更有意义。然而，对于大多数情况，工作队列就足够了。

在使用便利性方面，工作队列冠绝群雄。使用默认的 *events* 队列易如反掌。其次是 tasklets，它们也拥有简单的接口。排名最后的是 softirqs，它们需要静态创建，并且其实现需要仔细思考。

## 下半部之间的加锁

我们尚未讨论加锁，这是一个如此有趣且广泛的话题，我们将其留给接下来的两章。尽管如此，你需要理解，在使用下半部时，保护共享数据免受并发访问至关重要，即使在单处理器机器上也是如此。记住，下半部几乎可以在任何时刻运行。如果你对加锁的概念感到陌生，可能在读完接下来的两章后，你会想回来重读这一节。

Tasklets 的好处之一是它们相对于自身是序列化的：相同的 tasklet 不会并发运行，即使是在两个不同的处理器上。这意味着你不必担心 tasklet 内部并发问题。Tasklet 间并发（即，当两个不同的 tasklets 共享相同数据时）需要适当的加锁。由于 softirqs 不提供序列化（甚至两个相同 softirq 的实例可能同时运行），所有共享数据都需要适当的锁。

如果进程上下文代码和下半部共享数据，你需要在访问数据之前禁用下半部处理并获取锁。这样做既确保了本地和 SMP 保护，又防止了死锁。

如果中断上下文代码和下半部共享数据，你需要在访问数据之前禁用中断并获取锁。这也确保了本地和 SMP 保护，并防止死锁。

工作队列中的任何共享数据也需要加锁。由于工作队列在进程上下文中运行，加锁问题与常规内核代码没有不同。

第 9 章“内核同步简介”介绍了并发周围问题的背景，第 10 章涵盖了内核加锁原语。这些章节涵盖了如何保护下半部使用数据的方法。

## 禁用下半部

通常，仅禁用下半部是不够的。更常见的是，为了安全地保护共享数据，你需要获取锁并禁用下半部。这些方法（你可能在驱动程序中使用）在第 10 章中有介绍。然而，如果你正在编写核心内核代码，你可能只需要禁用下半部。

要禁用所有下半部处理（具体来说，所有 softirqs 以及因此所有 tasklets），请调用 `local_bh_disable()`。要启用下半部处理，请调用 `local_bh_enable()`。是的，函数名起错了；当 BH 接口被 softirqs 取代时，没人费心去改名字。表 8.4 是这些函数的总结。
