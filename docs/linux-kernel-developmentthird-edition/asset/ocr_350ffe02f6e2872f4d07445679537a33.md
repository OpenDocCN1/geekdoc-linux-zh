This is most likely not until the next interrupt occurs, which can equate to a lengthy amount of time before any new (or reactivated) sofi rqs are executed. Worse, on an otherwise idle system, it is beneficial to process the sofi rqs right away. Unfortu-nately, this approach is obivious to which processes are runnable. Therefore, although this method prevents starving user-space, it does starve the sofi rqs and does not take good advantage of an idle system.

In designing sofi rqs, the kernel developers realized that some sort of compromise was needed. The solution ultimately implemented in the kernel is to *not immediately* process reactivated sofi rqs. Instead, if the number of sofi rqs grows excessive, the kernel wakes up a family of kernel threads to handle the load. The kernel threads run with the lowest possible priority (nice value of 19), which ensures they do not run in lieu of anything impor-tant. This concession prevents heavy sofi riq activity from completely starving user-space of processor time. Conversely, it also ensures that “excess” sofi rqs do run eventually. Finally, this solution has the added property that on an idle system the sofi rqs are handled rather quickly because the kernel threads will schedule immediately.

There is one thread per processor. The threads are each named `kaofirqd/n` where *n* is the processor number. On a two-processor system, you would have `kaofirqd/0` and `kaofirqd/1`. Having a thread on each processor ensures an idle processor, if available, can always service sofi rqs. After the threads are initialized, they run a tight loop similar to this:

```
```
for (;;) {
    if (!sofirq_pending(cpu))
        schedule();

    set_current_state(TASK_RUNNING);

    while (sofirq_pending(cpu)) {
        do_sofirq();
        if (need_resched())
            schedule();
    }

    set_current_state(TASK_INTERRUPTIBLE);
}
```
```

If any sofi rqs are pending (as reported by `sofirq_pending()`), `kaofirqd` calls `do_sofirq()` to handle them. Note that it does this repeatedly to handle any reactivated sofi rqs, too. After each iteration, `schedule()` is called if needed, to enable more impor-tant processes to run. After all processing is complete, the kernel thread sets itself `TASK_INTERRUPTIBLE` and invokes the scheduler to select a new runnable process.

The sofi riq kernel threads are awakened whenever `do_sofirq()` detects an executed kernel thread reactivating itself.
