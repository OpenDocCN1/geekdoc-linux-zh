traffic light goes to green and all pedestrian lights go out.

This sounds straightforward on the face of it, but the traffic sensor needs to be
monitored through this sequence, to ensure that you don't miss any traffic
drive up and stop during the crossing sequence and allow the next crossing
turn too quickly. This means you can't just use a simple sleep delay to
control the sequence; what you need is a state machine — this is a way
of jogging two or more processes while making it look like they're happening at
the same time.

A state machine is an important technique — and one you will need as you take on more projects.

The idea of a state machine is that most things do not need the processor's full
attention. The LED blink program spends virtually all of the
sleep function, waiting for time to pass. Instead of turning that, the
idea of a state machine is to spend it after other tasks. In order to do this,
you have to have some idea of what your tasks need to incorporate
a variable that specifies what each task needs to be looked at next. This is made
possible by the time.point number (one with decimal places) method of the time library, which returns a floating-point number of the time (in seconds) that the Pi has
switched on. The thing is that you don't actually care what this number is,
because you use it to do the task.

Let's look at a simple example first — blinking two LEDs independently.

Now we'll describe how to blink these two LEDs at totally independent rates. The state of each task is given by a state variable, with the two values 0 or 1. The state variable shows if the light is on or off so that you know you need to do for the next stage of the blinking task. The time between each change of state of the LEDs is controlled by a variable that gives the time the change must occur. This time is calculated by adding the current time to the length of time you want to elapse before the next LED state change. This can be the same for all states or for each. The example in Listing 16-10 has the same time for the on/off times of LED1, but a separate/off time for LED2.

The program spends most of its time in the while loop in the main function, checking to see if it's time to call all of the two functions blink1 and blink2 (Note: You, of course, have as many functions as you want). When the functions are run, they do what they need to do for that task's current state, which, in our simple case, involves turning the LED on or off. Then you advance the state counter, and finally, the set this function/task needs to be done again. If the task is advanced at a constant rate (like the blinking LED1), this is done at the end of the function. If each state needs to last a specific length of time, it is set when the state is counted.

When you run the program, you see both LEDs blinking in unison; but as time goes by, they become increasingly out of sync until they are seen to be blinking alternately, and in another minute, they drift back into sync. This is because the full cycle of LED2 is 0.01 seconds longer than LED1.
