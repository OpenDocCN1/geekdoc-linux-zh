> NOTE PostgreSQL adds another layer of control to the database called the schema. A database can contain multiple schemas, each schema containing multiple tables.

By default, every database contains one schema, called public. If you're only going to have one application use the database, you're fine just using the public schema. If you'd like to really get fancy, you can create new schemas. For example, I'll just use the public schema for my tables.

# Creating user accounts

After creating the database, the next step is to create a user account that has access to it for your scripts. As you've already seen, user accounts in PostgreSQL is one of things that is significantly different from MySQL.

User accounts in PostgreSQL are called Login Roles. The PostgreSQL server manages Login Roles to the Linux system user accounts. Because of this, there are two common thoughts about creating Login Roles to run shell scripts that access the PostgreSQL database:

+   - Create a special Login account with a matching PostgreSQL Login Role to run all your shell scripts.
- Create PostgreSQL accounts for each Linux user account that needs to run shell scripts to access the database.

For this example I'll choose the second method and create a PostgreSQL account that matches my Linux system account. This way, I can run shell scripts that access the PostgreSQL database directly from my Linux user account.

First, you must create the Login Role:

```
test=# CREATE ROLE rich login;
CREATE ROLE
test=#
```

That was simple enough. Without the login parameter, the role is not allowed to log in to the PostgreSQL server, but this type of role is called a Group Role.
