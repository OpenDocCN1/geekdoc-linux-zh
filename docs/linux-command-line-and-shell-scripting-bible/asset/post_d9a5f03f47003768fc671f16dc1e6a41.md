
# Part II Shell Scripting Basics

Just as with a normal background process, the shell assigns the command job number, and the Linux system assigns a PID number. The difference is that when you use the nohup command, the shell ignores any SIGHUP signals sent by the terminal session if you close the session.

Because the nohup command disassociates the process from the terminal, the process loses its STDOUT and STDERR links. To accommodate any output generated by the command, the nohup command automatically redirects STDOUT and STDERR messages to a file, called nohup.out.

The nohup.out file contains all of the output that would normally be sent to the terminal monitor. After the process finishes running, you can view the nohup.out file for the output results:

```
$ cat nohup.out
This is a test program
Loop #1
Loop #2
Loop #3
Loop #4
Loop #5
Loop #6
Loop #7
Loop #8
Loop #9
Loop #10
This is the end of the test program
$
```

The output appears in the nohup.out file just as if the process ran on the command line!

> CAUTION If you run another command using nohup, the output is appended to the existing nohup.out file. Be careful when running multiple commands from the same directory, as all of the output will be sent to the same nohup.out file, which can be confusing.

# Job Control

Earlier in this chapter, you saw how to use the Ctrl-Z combination to stop a job running in the shell. After you stop a job, the Linux system lets you kill or restart it. You can kill the process using the kill command. Restarting a stopped process requires sending it a SIGCONT signal. The function of starting, stopping, and resuming jobs is called job control. With job control, you have full control over processes running in your shell. This section describes the commands to use to view and control jobs in your shell.

# Viewing jobs

The key command for job control is the jobs command. The jobs command allows you to view current jobs handled by the shell:

```bash
#!/bin/bash
echo "This is a test program"
count=1
while [ $count -le 10 ]
do
    echo "Loop #$count"
    sleep 10
    count=$((count + 1))
done
echo "This is the end of the test program"
```

```
$ ./test4
This is a test program
Loop #1
[1]+ Stopped ./test4
$ ./test4 > test4 &
$ jobs
[1]+ Stopped ./test4
[2]- Running ./test4 > test4 &
```

The script uses the $$ variable to display the PID that the Linux system assigns to the process. In the example, I start the first script from the command line, then stop it using Ctrl-Z. Next, I start another job as a background process using the ampersand symbol. To make life easier, I redirected the output of the script to a file so it wouldn't appear on the monitor.

After the two jobs started, I used the jobs command to view jobs assigned to the shell. The jobs command shows both the stopped and running jobs, along with their job numbers. The jobs command uses a few different command line parameters, shown in Table 13-2. You probably noticed the plus and minus signs in the output. The job with the plus sign is considered the default job. It will be referenced by any job commands if a job number wasn't specified in the command line. The job with the minus sign is the job that would become the default job when the current default job finishes. There will be only one job with the plus sign and one job with the minus sign at any time, no matter how many jobs are running in the shell.

TABLE 13-2
| Parameter | Description |
| :--- | :--- |
| -l | List the PID of the process along with the job number. |
| -n | List only jobs that have changed their status since the last notification from the shell. |
| -p | List only the PIDs of the jobs. |
| -r | List only the running jobs. |
| -s | List only stopped jobs. |

Here’s an example showing how the next job in line takes over the default status when the default job is removed:

```
$ ./test4
This is a test program 29075
Loop #1
[1]+ Stopped ./test4
$ ./test4
This is a test program 29090
Loop #1
[2]+ Stopped ./test4
$ ./test4
This is a test program 29105
Loop #1
[3]+ Stopped ./test4
$ jobs -1
[1] 29075 Stopped ./test4
[2]- 29090 Stopped ./test4
[3]+ 29105 ./test4
$ kill -9 29105
$ jobs -1
[1]- 29075 Stopped ./test4
[2]+ 29090 Stopped ./test4
$
```

In this example, I started, then stopped three separate processes. The jobs command listing shows the three processes and their status. Note that the default process (the one listed with the plus sign) is the last process started. I used the kill command to send a SKILL signal to the default process. In the next jobs listing, the job that previously had the minus sign is now the default job.

# Restarting stopped jobs

Under bash job control, you can restart any stopped job as either a background process or a foreground process. A foreground process takes over control of the terminal you're working on, and be careful about using that feature.

To restart a job in background mode, use the bg command, along with the job number:

```
$ bg 2
[2]+ ./test4 &
Loop #2
$ Loop #3
Loop #4

$ Jobs             ./test4
[1]+ Stopped
[2]- Running      ./test4 &
$ Loop #6
Loop #7
Loop #8
Loop #9
Loop #10
This is the end of the test program

[2]- Done          ./test4
$
```

Since I restarted the job in background mode, the command line interface appears, allowing me to continue with other commands. The output from the jobs command shows that the job is indeed running (as you can tell from the output now appearing on the monitor).

To restart a job in foreground mode, use the fg command, along with the job number:

```
$ Jobs
[1]+ Stopped      ./test4
$ fg 1
./test4
Loop #2
Loop #3
```

Since the job is running in foreground mode, I don't get a new line interface until the job finishes.

# Being Nice

In a multitasking operating system (which Linux is), the kernel is responsible for assigning CPU time for each process running on the system. Only one process at a time can actually be running on the CPU, as the kernel assigns CPU time to each process in turn.

The scheduling priority is an integer value from -20 (the highest priority) to +20 (the lowest priority). By default, bash shell starts all processes with a priority of 0. This means that a simple script that requires a little bit of time gets the same CPU slices as a complex mathematical algorithm that can take hours to run.

Sometimes you want to change the priority of a specific command, either lowering its priority so it doesn't take as much processing power from the CPU or giving it a higher priority so it gets more processing time. You can do this by using the nice command.

# The nice command

The nice command allows you to set the scheduling priority of a command as you start it. To make a command run with less priority, just use the -n option for nice to specify a new priority level:

```
$ nice -10 ./test4 > test4 & 
[1] 29476
$ ps a
F UID PID PPID PRI NI WCHAN STAT TTY TIME COMMAND
100 501 29459 29458 12 wait4 S pts/0 0:00 -bash
000 501 29476 29459 15 wait4 SN pts/0 0:00 /bin/bash
000 501 29490 29476 15 10 nanos SN pts/0 0:00 sleep 10
000 501 29491 29459 14 - R pts/0 0:00 ps ai
```

The nice command causes the script to run at a lower priority. However, if you try to increase the priority of one of your commands, you might be in for a surprise:

```
$ nice -10 ./test4 > test4 & 
[1] 29501
$ nice: cannot set priority: Permission denied
[1]+ Exit 1 nice -n -10 ./test4 >test4
$
```

The nice command prevents normal system users from increasing the priority of their commands. This is a safety feature to prevent a user from starting all of or her commands as high priority.
