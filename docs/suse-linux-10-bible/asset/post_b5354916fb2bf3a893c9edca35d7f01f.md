From this prompt, you can open another connection to a server using openserver or quit telnet command. For more information about what you can do in the telnet prompt, type help and press Return.

## Using Telnet for Testing

You can use Telnet for more than just a virtual terminal, however. We mentioned using telnet to test services that you have configured. Telnet provides a virtual terminal that opens a TCP connection to a specific port. This connection prints whatever text it is from the server (in this case, the telnet server) and sends any data type into the remote server.

Quite a few services work on notion of sending their data in plain text form for their protocol. The two main candidates are Hypertext Transfer Protocol (HTTP) and Simple Mail Transfer Protocol (SMTP).

To see a rundown of the SMTP protocol, we log in to the mail server on our local machine and send a test mail (see Listing 15-9).

### Listing 15-9: Using telnet as a Protocol Tester

```
bible:- # telnet localhost smtp
Trying 127.0.0.1...
Connected to localhost.
Escape character is '^'
220 bible.suse.com ESMTP Postfix
ehlo localhost
250-bible.suse.com
250-PIPELINING
```

```
250-SIZE 1024000
250-VRFY
250-ETRN
250 8BITIME
mail from: justin@bible
250 OK
rcpt to: justin@palmcoder.net
250 Ok
data
354 End data with <CR><LF>,<CR><LF>
This is a test mail that I am sending you.
Justin

250 Ok: queued as 6D5CF18490
```

We have used the SMTP protocol to specify that we are sending a mail to the user justin@palmcoder.net from the user justin@bible from the machine localhost (ehlo localhost). This is a standard SMTP transaction that can be used to quickly send an SMTP server's ability to send mail to a specific user.

We discuss mail servers and a further example of using Telnet to test a service in Chapter 17.

The command line, telnet localhost smtp, is the same command used previously with the addition of the port specification (smtp). The port you connect to can either be in text form (as we used) or in numerical format. The number for the SMTP port is 25.

From now on in the book, we will refer to TCP/IP ports and more. A TCP/IP port can be thought of as a virtual port that serves a specific purpose. Each port has a unique number and a number of well-known numbers have been reserved for specific purposes. For example, port 80 is HTTP, port 25 is SMTP, and port 21 is FTP. View the file /etc/services for more information on what well-known ports are.

If security is a concern for your organization, Telnet should not be used to transmit sensitive information. As all information is plain text, it is just not safe.

## Using SSH

SSH can be thought of as a secure extension using Telnet. It provides virtual terminal services that are encrypted to the user; this includes encrypting the password that the user sends to the server. However, SSH, is actually a technology that provide not only virtual terminal services, but also file transfer and tunneling services that provide extremely useful. In this section, we will talk first about the virtual terminal of SSH and then move onto public/private key use and tunneling data through an SSH secure.

## Using SSH for Virtual Terminals

Like its poorer cousin, the prime use of SSH is to log securely to servers. SSH does not provide you with a login and password prompt as Telnet does. SSH takes in the user authentication process when the connection is negotiated (you will see later). Because of this, SSH needs to know the username you want to connect to the server. If you use SSH to connect to a remote server, the SSH client will assume you want to connect to the server as your current (see Listing 15-10).

### Listing 15-10: Using SSH to Log in to a Remote Server as the Current User

```
just@ssh bible
The authenticity of host 'bible (192.168.0.1)' can't be established.
RSA key fingerprint is e3:0a:4b:1e:d5:55:24:e6:7d:5f:86:23:f2:1d:8a
Are you sure you want to continue connecting (yes/no)? yes
Warning: Permanently added 'bible,192.168.0.1' (RSA) to the list of hosts.
Password:
Last login: Wed May 12 13:30 2005
```

If you look at the output in the preceding listing, you notice quite an important thing happening when we attempted to log in the machine. We were told that the machine has not recognized and thus is not trusted. This is part of the security protocol. You will see this warning every machine you log in for the first time. If you want to proceed and log in to the server, but someone has maliciously tricked you into thinking you were connecting to your original server (in fact it was a bogus server with the same name), SSH knows that the fingerprint of the machine is bogus and warns you of this. As you can see, we were not asked for a username. If you want to connect to the SSH as another user, you have two options: either the -l switch to specify the user or more notation. For example:

```
root@server
Password:
Last login: Tue Jul 6 04:23 2005
```

Because we specified the username on the command line, we were asked for that and not ours. In this case, we logged in as root.

## Public and Private Keys

If you are bored of typing passwords, or you want to make the remote authentication secure, you can use public and private keys to identify yourself. A PPK (Public Private Key) pair consists of two keys:

- One key that you keep to yourself and share with no else (the private key).
- The other is a public key that you install on all servers you want to log in that can be read by anybody.

PPKs are useless if you do not have the pair of keys. Even if someone finds your public key, they cannot use it because is used only as the private key you kept secret. To create a PPK, you need to run the ssh-keygen command. The ssh-keygen commands a few arguments, but we will create a standard SSH key pair for purposes. Consider the example in Listing 15-11.

## Passphrases

You have two options for how you want to create your key pair — without a passphrase. A passphrase is a long string of characters that can be thought of as your password. A passphrase could be a sentence, a piece of text you can remember, and can contain spaces. This makes the PPK much more secure even if your private key has compromised, the user still needs to know your passphrase. If you do not set a passphrase, you can then log in to a machine without entering a password or a passphrase and rely on the security of the PPK and nothing else. If security is a big thing for you (and it should be), you should set a passphrase when asked.

### Listing 15-11: Creating a PPK Pair

```
just@ssh-keygen -t dsa
Generating public/private key pair.
Enter file to save the key (/home/ssh/id_dsa):
Enter passphrase (empty for no passphrase):
Enter same passphrase again:
Your identification has been saved in /home/ssh/id_dsa.
Your public key has been saved in /home/ssh/id_dsa.pub.
The key fingerprint is:
07:3d:01:94:6b:24:dd:a3:d4:b9:b5:bc:ac:ad:83:
```

In this example, we created a key pair using the DSA encryption algorithm. The SSH protocol has two levels, protocol 1 and protocol 2. Protocol 2 is inherently secure. Make sure to create an SSH v2 key pair, pass either dsa or rsa as the key type with -t on the command line.

Our keys are saved in ~/.ssh/, providing us with a means to copy our public key over to another server so that we can log in. In the case of DSA, our public key is id_dsa.pub and our private key is id_dsa.

> Note Your private key must be kept private from any other user at all costs, particularly if you choose not to enter a passphrase.

On the machine where we want to log in, we need to copy our public key over to the file ~/.ssh/authorized_keys (see Listing 15-12). The authorized keys files contain public keys for a specific user that will enable them to log in. Only this user will use the PPK pair; it is systemwide.

### Listing 15-12: Copying Our Public SSH Key to Another Server

```
just@scp ~/.id_dsa.pub 192.168.131.70:~/.ssh/authorized_keys
The authenticity of host '192.168.131.70' (192.168.131.70) can't be established.
RSA key fingerprint is e3:0a:4b:1e:d5:55:24:e6:7d:5f:86:23:f2:1d:8a.
Are you sure you want to continue connecting (yes/no)? 
Warning: Permanently added '192.168.131.70' (RSA) to the list of known hosts.
Password:
id_dsa.pub         100    0.6KB/s    00:00
```

We will talk about the scp (secure copy) command later in the chapter. For now, note that it uses an encrypted channel to send files to and from remote servers.
