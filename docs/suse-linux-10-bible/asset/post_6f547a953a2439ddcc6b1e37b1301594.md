
# Part IV ♦ Implementing Network Services in SUSE Linux

First, we look at the client side of things: we will assume that an NFS server is available and look how to mount a share that an NFS server is offering. At this stage all you need to know is that an NFS server is capable of offering one or more of its directories in such a way that other machines on the network can mount them. For example, if you know that the server has the directory /share available by NFS, you can mount the share on the client machine by a command as this:

```
root@client:~ # mount bable:/share /mnt
```

You should be able to change the directory to /mnt and see the files that exist in the directory /share on bable.

If this command hangs, its portmap might not be running on client: check this with portmap status. If necessary, issue the command portmap start or portmap restart. Of course, the reason for the problem might be on the server, in which case it is more likely that you will see an error like the following:

```
mount: RPC: Remote system error - Connection refused
```

# Mount NFS Filesystems at Boot Time

It is possible that you want to mount particular NFS filesystems at boot time. You may also want to allow non-root users on the client to mount NFS shares themselves. In either of these cases, you will need to include a suitable entry in the file /etc/fstab. Just as this file controls the local filesystems are to be mounted, you can also control the mounting of NFS shares.

For this example, the entry in /etc/fstab on the client:

```
bable:/test /testmount nfs user,mount,ro 0 0
```

any user on the client can mount (read-only) the specified directory from bable the specified point by issuing the command mount /testmount.

To force the directory to be mounted automatically, you may use the following:

```
bable:/test /testmount nfs rw 0 0
```

This line in /etc/fstab ensures that the NFS share is mounted read-write whenever the system boots, provided that the service nfs is set to start in runlevel 3 on the client. See Chapter 3 for more information about the use of /etc/fstab for setting mount options for filesystems.

# Using mount Options

Most of the control over how NFS behaves is based on the server; however, there are some options to the mount command that make a difference.

You may want to force a read-only mount (even if the server is offering the share-write). At the command line, you type:

```
root@client: ~ mount bible:share /mnt -o ro
```

In other words, mount the directory /share from the server bible (which is being available by the mount point /mnt, with the option (-o) to the mount command ro, which means read-only.

You can also specify a hard or soft mount:

- Hard mount—Ensures that in the event of the NFS server becomes unavailable, a program that is accessing the mount hangs but will be able to recover once the server comes back on line.
- Soft mount—The client will report an error to the requesting program; not all programs handle this correctly and there is a possibility of data corruption.

To specify a hard mount, you add the keyword hard to the options (after the -o) for the mount command. For example:

```
root@client: ~ mount bible:share /mnt -o ro
```

In fact, hard is the default so you do not need to specify it explicitly. The NFS HOWTO recommends the options hard unless there is a good reason to do otherwise. The option intr ensures that if the server is no longer responding, the program that is accessing the mount can be interrupted by a kill signal.

You can also try to force the connection to be carried over by the TCP transport rather than UDP using tcp to the list of options the mount command. UDP is the default, and NFS over UDP is stateless; this means that the server can be restarted without breaking the connection. However, it is less efficient if any packets are being dropped on the network, because if you use TCP, every packet is acknowledged and is resent if it does not arrive. With UDP, only the completion of the entire request is acknowledged.

Other options to the mount command are resize and wsize, which set block sizes in bytes reads and writes, respectively. Performance is expected to improve if these are set to 8,192 rather than the default of 1,024. The mount command looks like this:

```
root@client:~ # mount bible:/share/mnt -o resize=8192 wsize=8192
```

Under some circumstances, better performance may be achieved with different values, but if these parameters are too far removed from their defaults, problems occur.

![](img/e4e45c9f32e76fb35fabbd21a96f1a1e_630_0.png)

Increasing these values is recommended because Linux kernels perform read-ahead for values greater than the maximum page size, which on the x86 architecture is 4,096. A value of greater than 8,192 will improve NFS read performance. The value needs to be a multiple of 1,024, and should not be greater than 16,384.

# rcnf start and rcnfs stop

On a SUSE system, the operation of the NFS client is treated as a service and has its startup script in /etc/init.d and the related command rcnfs. The commands rcnfs start and rcnfs stop (run as root) start and stop the NFS client service and mount (if possible) any NFS shares are included in /etc/fstab. The unmounting fails if the mount point is not in. If the service nfs is not set to start in runlevels 3 and 5, the Network File Systems specified in /etc/fstab (as root) will not be imported until one of the commands rcnfs start -a is issued (as root).

If the NFS client service is set to start in runlevels it will take a long time to out if for some reason the server is unreachable; this can be avoided by adding the bg (background) option to /etc/fstab. An example might look like this:

```
bable:/test /testmount nfs user,mount,ro 0 0
```

any user on the client can mount (read-only) the specified directory from bable the specified point by issuing the command mount /testmount.

To force the directory to be mounted automatically, you may use the following:

```
bable:/test /testmount nfs rw 0 0
```

This line in /etc/fstab ensures that the NFS share is mounted read-write whenever the system boots, provided that the service nfs is set to start in runlevel 3 on the client. See Chapter 3 for more information about the use of /etc/fstab for setting mount options for filesystems.

# The NFS Server

Two NFS implementations are available on SUSE. One is kernel-based; the other is user space. If you use the kernel-based implementation, you need the package nfs-utils. If you install the user space, it does not depend on which implementation.

# The Exports File

The sharing of directories by NFS is controlled by the file /etc/exports, which contains a list of directories with details of how they may be exported and other options. A simple example as /exports might contain the following:

/test client (rw)

This will export the directory /test to the host client. The option rw (read-write) is set. If you restart the NFS server, you will see:

> Shutting down kernel based NFS: done
Starting kernel NFS exports: /etc/exports [8]: no 'sync' or 'async' option specified
for export "home/"
Assigning default behaviour ('async').done

To modify this, add sync or async to the options:

/test client (rw, sync)

The default option sync means that the NFS server waits for local disk writes to complete, minimizing the risk of data corruption if the server suddenly fails. If async is specified, the opposite is the case, meaning that if communication between client and server fails, corrupt data may be written to the client.

Note that there should be no space between the client name(s) and the options. If there is, the NFS server interprets the line differently; in the preceding example, it would offer /test to machine client with the default options and to any other machine with the options rw, sync. This is unfortunate because it is an easy mistake in creating the file. However, to indicate that you want to export to any machine you should preferably use the * notation.
