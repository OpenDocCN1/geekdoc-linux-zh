It may be unclear how this model helps abstraction and further the protocol. I hope that the following example will help you understand.

Suppose I am sitting in my garden on a sunny day in London (amazing, but we do get here!) writing this chapter. I am running a wireless network in my house, so I can check my email, surf the web, and listen to some music on my laptop. None of this would be possible without a layered architecture because I am using so many different protocols running over a wireless connection, which is then connected to an asymmetric digital subscriber line (ADSL) router, further connected to a firewall.

I am in my garden, and need to send a chapter to my editor at Wiley. To do this, I need to open an FTP connection to the Wiley server. Here is what happens.

I initiate an FTP connection, with the IP address of the server I want to connect to. My machine sees that the server I want to communicate with is not on its local network and sends the request over to my router, which needs to get to Wiley. My router knows does not specifically understand where the FTP server I need to talk to, so it sends the packet to its default router, and so on. It will carry on, with each you router getting closer and closer to the destination. When the packet hits Wiley's FTP server, TCP/IP creates a network so that the FTP server knows that specific connection is coming from my IP address.

When this connection is established, I have a virtual connection to the FTP server — that, according to my laptop I have a connection to Wiley, regardless that it is not a physical connection, but rather traversing many routers, the Atlantic, and many firewalls. This is transparent not only to the user, but also to the client machine. My FTP client does not care how a connection is made to Wiley; it is only concerned that my connection can be.

# Connection Versus Connectionless Protocols

The transport layer has two protocols used to transport data from A to B—TCP and UDP, which are connection- and connectionless-based protocols, respectively. Most TCP/IP application services use the reliable TCP protocols to transport data. TCP maintains a connection as long as is needed to fulfill a request. During this time, if a checksum error is found in a packet, the TCP protocol requests a retransmission. To the upper layers, this is transparent and guarantees data consistency. Short bursts are needed, or where the upper layers take loss or error, UDP can be used to reduce overhead, at the cost of data consistency. UDP is commonly used for Domain Name System (DNS) lookups (small packet size, the upper layer is capable of requesting data in the event of failure) and also for streaming Picture Experts Group (MPEG) streams. The MPEG protocol is able to deal with quite a high amount of data loss and errors itself.
