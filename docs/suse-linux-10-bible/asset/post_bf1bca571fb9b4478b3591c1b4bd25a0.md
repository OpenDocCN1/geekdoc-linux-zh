## Building the Kernel

Now, assuming the architecture is x86, you need to do the following:

```
root@bible: /usr/src/linux-2.6.5-7.79/ # make bImage
```

Historically, the b stands for big, and the z indicates that it is a compressed image. On other architectures, the command you need is different. Details specific to SUSE are available at www.suse.de/-agruen/kernel-doc.

This is where the real work gets done. In the 2.6 kernels, by default you will see less output on the screen before leaving (see Listing 29-2).

When the build process has completed successfully, you will see a message similar to this:

Root device is (3, 1)
Root sector is 512 bytes.
Setup is 5039 bytes.
System is 1426 kB
Kernel: arch/i386/boot/bImage is ready

You can navigate to that directory and see the file that has been created.

```
root@bible: # cd /usr/src/linux/arch/i386/boot/
root@bible: /usr/src/linux-2.6.5-7.79/arch/i386/boot/ # ls -1 bImage
```

You should see a brand-new file bImage with a timestamp showing that it has just been created.

When you've made the bImage, you have several more steps to perform:

- 1. Build the modules:

```
root@bz:~/usr/src/linux-2.6.5-79/ # make modules
```

Note if you simply issue the command make or make all, the bImage and the modules will be built in one step.

- 2. Install the kernel and the modules:

```
root@bz:~/usr/src/linux-2.6.5-79/ # make install
```

This copies the bImage file to the /boot directory. (Before you do this you may want to back up the old kernel, particularly if it has the same version number.)

```
root@bz:~/usr/src/linux-2.6.5-79/ # make modules_install
```

- 3. Create a new initramdisk to correspond to the new kernel:

```
root@bz:~/usr/src/linux-2.6.5-79/ # mkinitrd
```

- 4. Check that both old and new kernels are referenced in the GRUB menu so that you can go back to the old kernel if you need to. Edit the file /boot/grub/menu.1 to confirm this.

If you use LILO for booting, you need to edit /etc/lilo.conf to ensure that both the new and old kernels are included and run the lilo command.

## Rebuilding the km-* Packages

A number of packages have names beginning with km_. These packages contain source code for additional modules that you may need to compile separately to add support for things. For example, km_ocfs adds support for the Oracle Cluster File System (OCFS), and km_smartmodem package adds support for a certain class of winmods. You can find these packages by searching for “km_” in the YaST software.

To make use of these packages, you must have the source for the running kernel. When you install these packages, install the relevant source code to a directory under /usr/src/kernel-modules/. To add support for OCFS, change the directory /usr/src/kernel-modules/ocfs2/, and then issue the following commands:

```
# make -C /usr/src/linux KERNEL_SOURCE=$(uname -r)
```

Alternatively, you can issue this command:

```
# make -C /usr/src/linux SUBDIRS=$PWD
```

This runs the make command while referring to the current directory and installed as:

```
/lib/modules/<version-number>/extra/ocfs2.ko
```

You will find that the module has been built and installed as: If you install a new kernel, you will need to rebuild these modules from source.

## Kernel of the Day

The SUSE FTP server always has a so-called kernel of the day, which is the latest test kernel available for each architecture. This is available at http://ftp.suse.com/pub/kernel/kotd/. It goes without saying that these kernels should be used only with caution because they have not been officially released and are provided for testing purposes.

## The Kernel and Third-Party Software

Third-party software requires low-level kernel support only with particular kernel versions. In the worst case, this is because vendor ships binary-only modules, even when module source is built against the running kernel. This can be limited to very specific kernel updates which are recommended by SUSE (for security reasons) and vendors are slow to respond. The problem can be worse if you are trying to run two pieces of software at the same time. These problems persist until third-party vendors give a better understanding of the dynamics of Linux and release their code in a more flexible and open-way. 

When third-party modules load, you will see a message of the form:

```
Warning: loading <module file> will taint the kernel: non-GPL license - Proprietary. See http://www.kernel.org/linux/export-tainted for information about tainted modules
Module <module file> loaded, with warnings
```

This indicates that a module with a non-GPL license is being loaded into the kernel. This warning is not simply about ideology. When proprietary (particularly binary-only) modules are loaded, little can help debug any problems they may cause.

## Loading Kernel Modules

In the 2.6 kernel, kernel modules have filenames ending with .ko (rather than .so in 2.4). To check what modules are loaded:

```
root@bible: ~ # lsmod
Module         Size Used by
nis_cp437      6016 0
vnE            14208 0
```

## Kernel Parameters at Boot Time

You can pass parameters to the kernel at boot time either permanently by editing the GRUB configuration file or temporarily by typing at the boot prompt. These control the behavior of the kernel when it boots in various ways. Current versions of SUSE use showopts in the GRUB configuration file, which has the unfortunate effect of hiding the parameters that are being passed. Actually what this does is to hide the options that are listed before and those that appear after it.

If you remove showopts from the default entry line in /boot/grub/menu.1, then the next boot you will see exactly which boot parameters are being passed to the kernel when it loads. You will also be able to edit these parameters in the initial boot screen.

A list of supported parameters and their meanings are in the file:

```
/usr/src/linux/Documentation/kernel-parameters.txt
```

A few examples of parameters that you might want to pass at boot time are follows:

```
fat 43584 1 vfat
usb_storage 60096 0
nls_iso8859_1 4352 2
df 85380 0
nn__utf8 2304 0
```

Dependencies between modules are indicated in the last column of the output.

To load a module, you may use the following:

```
root@blog: ~ # modprobe tulip
```

To unload a module, you use the following:

```
root@blog: ~ # rmmod tulip
```

The automatic loading of modules is (now in 2.6 kernels) controlled by the file /modprobe.conf, which has replaced the /etc/modules.conf file.

The file /lib/modules/version-number-default/modules.dep contains a listing of all the dependencies between available modules. This file can be regenerated if necessary by the command depmod -a.
