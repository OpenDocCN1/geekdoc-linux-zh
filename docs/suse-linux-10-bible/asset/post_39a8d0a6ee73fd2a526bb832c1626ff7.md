## Setting Your First Rules

Before you touch setting up specific rules, you need to set the default policy for the firewall (see Listing 24-2).

### 24-2: Setting Initial Firewall Rules

```
iptables -P INPUT DROP
iptables -P OUTPUT ACCEPT
iptables -P FORWARD DROP
iptables -A INPUT -m state --ESTABLISHED,RELATED -j ACCEPT
iptables -A FORWARD -m state --ESTABLISHED,RELATED -j ACCEPT
iptables -A OUTPUT -m state --ESTABLISHED,RELATED -j ACCEPT
```

Here you set the default policy for all chains to drop. In this moment in time, all network connections, regardless of their originating address, will be dropped.

To set or change the policy of a chain, you need to specify this: policy (-P), chain (INPUT, OUTPUT, or FORWARD), and also what to do with the packet.

Knowing that any connection from the Internet is not needed and the sender has to wait for timeout, imagine running a scan of all available ports. If they have to wait for each, it will take a few hours to complete. It provides a kind of protection for users. This is also true for internal connection. If your users are interested in what they can connect to without reading the rules, they will wait. You have also configured the stateful firewall with -m state declaration. This tells the firewall that you will allow any established or related connections on the INPUT chain.

This may seem like quite a big hole, but bear in mind that it will allow only connections that have been established, not new connections. For state rules to kick in, you would have already had to allow a new connection through the chain.

Depending on how paranoid you are about security, you may not want to allow all new connections from the firewall. However, if you want to use the machine as a server, or want to be able to "bounce" to other hosts without the burden of setting up rules for every protocol or port, it is quite useful. At this point, your firewall is locked down with the exception of allowing outgoing connections.

When Adding a Rule, you need to specify as much information as possible to have full control over the TCP/IP packets you are allowing. At a minimum, you choose the chain, protocol, and destination port. With just this information you do not have a very good rule because it does not specify the interface you are allowing. Another option that can be set is the connection type:

- **NEW**: This is a new connection, no other traffic associated with this packet.
- **ESTABLISHED**: This packet is from a machine you already have a connection to, both send and receive data when a connection exists.
- **RELATED**: This packet is related to an existing connection. The FTP protocol, for example, makes a connection to the FTP server, and the FTP server actually makes a connection to the client. This connection from the client is a RELATED connection.

```
iptables -A INPUT -p tcp --dport ssh -i eth0 -j ACCEPT
```

In this example, you use netfilter you want to append (-A) a rule to the INPUT chain, specifying the TCP protocol (-p tcp), a destination port (-dport) of ssh (port 22), incoming (-i) on the eth0 interface, and finally that you want to ACCEPT (-j ACCEPT). The -j parameter means "jump to target." Remember that netfilter rules are in a chain, so you are saying, "Stop processing this chain because you have a match and jump to the target." In this case, ACCEPT.

The -dport parameter can take either a numerical port number or a service name that is specified in /etc/services.

Setting up a rule for connections, you really need to know how the protocol works. In the case of SSH, it is well known that it is a TCP protocol running on port 22. With this in mind, it is relatively easy to write a rule for it.

It is up to you how you want to write the rule regarding the state of the connection, because the initial INPUT state rule has allowed all ESTABLISHED and RELATED connections, you do not need to explicitly set the state to NEW because you have effectively allowed all connection types for SSH by not explicitly setting them.

> If you do not specify something explicitly with iptables, it is assumed that you want the default setting. For example, if you did not set the interface for the incoming connection, netfilter would have allowed an SSH connection on all network interfaces. This is indeed the same for the protocol type and the destination port. Be very careful when you write your rules, and make sure you explicitly set everything you want to control; otherwise you will probably let in more than you think.

For any incoming connections you want to have on a firewall, you can append a rule in the same way you do with the SSH connection.

## Order of Rules

You must be very conscious of the order you set rules in a chain because netfilter passes the TCP/IP packet through the rules in the order they are inserted into the kernel. If you want to insert a rule at the top of the list (that is, making it the first rule that is executed), you can use the -I (insert) parameter to iptables.

For example, if you are allowing SSH into your firewall from the Internet, you know that you do not want a specific IP address to have access to SSH, you have to insert the REJECT/DROP rule before the general SSH rule:

```
iptables -A INPUT -p tcp --dport ssh -i eth0 -j ACCEPT
iptables -I INPUT 1 -p tcp --dport ssh -s 192.168.1.10 -j DROP
```

In this example, using -s to specify source, we have inserted the DROP rule before the general ACCEPT rule. In essence, all TCP/IP packets sequentially go through every rule until they match a target.

## Network Address Translation

While one of the main uses of netfilter is its packet filtering functions, another important aspect of netfilter is its NAT functions. Network Address Translation (NAT) is the process whereby the source or destination IP of a packet is changed when it passes through the firewall.

- Chapter 6 contains more information about NAT.

## Source NAT

Source NAT (SNAT) works on packets forwarded through the firewall before a packet leaves for the outbound network. For this work, you must deal with the packets before any routing decisions have been made, and the POSTROUT chain must be used to implement Source NAT.

The main purpose of SNAT is to hide private networks behind a firewall with a public IP address. This drastically reduces the cost of acquiring public IP addresses and allows you to use non-routable addresses in your internal network.

The POSTROUT chain deals with any packets that are to be sent out to the network card. This includes any packets that are routed onto other destinations. In the case of SNAT, this is the only chain that you want to use, for example, it makes no sense to use NAT traffic coming into the INPUT chain.

In this scenario, all of the machines are behind a netfilter firewall that provides NAT. For SNAT to work, IP forwarding must be enabled. To do this, enter a 1 into /proc/sys/ipv4/forward.

```bash
echo 1 > /proc/sys/ipv4/forward
```

This will immediately enable IP forwarding on your Linux machine. This is a volatile operation, and once your machine has been rebooted, IP forwarding will be turned off by default.

To set IP forwarding by default, edit the file /etc/sysconfig/sysctl and change IP_FORWARD from no to yes and re-run SUSEconfig.
