The passwords are stored in plain text (we understand this will change in future versions), the file's ownership and permissions should be squid:root and 600. In other words, it should be readable and writeable by the Squid user and not-readable by anyone else.

Now when a client starts a session, Squid authenticates with the information in this file. However, this does not require a password to be sent over the network. Instead, the server and client each calculate an MD5 or one-way hash based on the password and the URL (and additional per-session information offered by the server). The client sends the result of its calculation to the server, which compares.

Most browsers will cooperate correctly with this form of authentication. However, we have some problems with Konqueror, Internet Explorer, Mozilla, Netscape, Galeon, and Firefox appear to work perfectly with it.

The other authentication methods that are shipped with Squid's package are all installed into /usr/bin/ and are mnt_auth, ntlm_auth, smb_auth, yp_auth, getpwname_auth, ncsa_auth, and squid_auth.

Thus, it is possible to use Windows, Samba, LDAP, or YP as the authentication method. However, for most of these, the remarks given about un-encrypted passwords crossing from the client to the server hold.

# Restricting Access by Hardware Address

You have already seen how you can specify network or specific IP addresses in the ACLs in the configuration file. You can also restrict access to particular MAC addresses:

```
acl biple arp 00:11:22:33:44:55
http_access allow biple
```

This pair of lines allows biple to access the proxy. This works only if biple is directly connected to the same physical Ethernet network as the server. You can add pairs of lines like the previous lines for each permitted machine on the network.

# The Squid Log

The main Squid log is by default at /var/log/squid/access.log. Exactly what is logged here depends on the options chosen in the configuration file. The options we are explained as comments in the standard configuration file shipped with the SUSE package. In particular, if you set

```
emulate_http_log on
```

in /etc/squid/squid.conf, the format of the log file will change to look like more Apache's access log. This can be seen in these sample entries:

```
1089560809.085 159 192.168.2.111 TCP_MISS/200 768 GET
http://www.grokdoc.net/images/button_hr.png - DIRECT/152.210.81 image/png
192.168.2.111 - [Jul/2004:16:57:54 +0100] GET
http://news.bbc.co.uk/news/shared/cns/news HTTP/1.1" 200 15258 TCP_HIT:NONE
```

The first shows the access time, with the first min (since January 1, 1970), and the second shows the Apache-like.

Squid logs are very long and difficult to read, so a number of Squid analysis tools are available. SUSE includes a tool called **sarg** (Squid Analysis Report Generator). If you want to use the **sarg** tool you must install it; it is not included in the Squid. The **sarg** tool can be set to run daily via a cron job and produce HTML reports through a browser, as is example in Figure 26-3.

# Using Squid as a Transparent Proxy

One of the difficulties in running a web proxy is that each client browser has to be configured to use it. A much neater solution is to force all attempts to access a web site to go through the proxy. This can be achieved quite simply by using iptables firewall rules on the machine where Squid runs.

What you want to do is intercept outbound packets to external hosts on port 80 (and others perhaps) and redirect them to port 3128. Squid will do the proxy. So you need iptables rules to do this:

```
iptables -t nat -A PREROUTING -i eth -p tcp --dport 80 -j REDIRECT --to-port 3128
```

This assumes that eth is the internal interface that is receiving the outgoing HTTP requests and the machine where Squid is running is set as the gateway for the client machines.

See also the discussion of firewall rules in Chapter 24. Note that SuSEfirewall2 is capable of setting up the necessary rules for a transparent proxy. SuSEfirewall2 is also discussed in Chapter 24.

The Squid configuration file should include the following lines:

```
httpd_accel host virtual
httpd_accel_port 80
httpd_accel_with_proxy on
httpd_accel_uses_header on
```

See also the LDP’s “Transparent Proxy with Linux and Squid mini-HOWTO” by Daniel Kiracofe at www.tld.org/HOWTO/TransparentProxy.html.

You cannot combine transparent proxy with authorization on the proxy. It has also been reported in some circumstances there can be problems with remote sites that require authentication.
