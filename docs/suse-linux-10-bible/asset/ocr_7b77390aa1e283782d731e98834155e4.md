# The Kernel and Third-Party Software

Third-party commercial software requires low-level kernel support is some-times run only or with particular kernel versions. In the worst case this is because the vendor ships binary-only kernel modules, even when a module source is shipped to be built against the running kernel, it can be limited to very specific kernel versions. This can be a real problem, particularly when a kernel update is recommended by SUSE (for example, security reasons) and vendors are slow to respond. The problem can be worse if you are trying to run two pieces of software at the same time.

Consider the following example of a kind of problem in a production environment: A customer needs to run a piece of proprietary software allowing multipath to storage area network (SAN) storage and at the same time needed to run a third-party clustering solution with kernel modules for its filesystem. Although both of these products supported the version of SLEs that the customer was running, when you looked at the small print, things were more difficult because one version of the kernel package among the previous updates by SUSE works with both products. And that kernel version was not the last and had been officially superseded by a security patch.

These problems persist until all third-party vendors give a better understanding of the dynamics of Linux and releasing that they code in a more flexible and open does not necessarily prevent them from making money from their products.

When third-party modules load, you will see a message of the form:

```
Warning: loading <module file> will taint the kernel: non-GPL license - Proprietary. [...nSee http://www.kernel.org/linux/#export-tainted for information about tainted modules
Module <module file> loaded, with warnings
```

This indicates that a module with a non-GPL license is being loaded into the kernel. This warning is not simply about software ideology. When proprietary (particularly binary-only) modules are loaded, little can be to debug any problems they may cause.

# Loading Kernel Modules

In the 2.6 kernel, kernel modules have filenames ending with ko (rather than so in 2.4). To check what modules are loaded:

```
root@bible: ~ # lsmod
Module         Size Used by
nis_cp437      6016 0
vnE            14208 0
```
