# Testing the LDAP Server

When the initial slapd.conf configuration has taken place, you need to start the LDAP server with rceld:

```bash
bible:/etc/ldapd # rceld start
Starting ldap-server
```

When started, you can use the ldapsearch command to bind (connect) to the LDAP server with the administrator account (see Listing 25-1). Unlike an anonymous bind, we are authenticating to the LDAP server.

> Tip: To start OpenLDAP automatically when the system boots, use chkconfig: chkconfig -f - ldap.

# Chapter 25 ◆ Working with LDAP in SUSE

You can connect to the LDAP server with an anonymous bind, which means you have not presented authentication credentials to the LDAP server, and you are limited in what you can read and write to the server based on the default access control (ACL) settings.

# Listing 25-1: Authenticating to the LDAP Server

```bash
bible:etc/ldap ldapsearch -x -D "cn=admin,o=Acme,c=UK" -W
Enter LDAP Password:
# extended LDIF

# LDAPv3
# base <> with scope sub
# filter: (objectclass*)
# requesting: ALL
#
# search result
search: 2
result: 2 No such object

# numResponses: 1
```

As you do not have anything in the LDAP server, you will not receive any responses.

The ldapsearch command is extremely powerful, not only for diagnostic purposes, but also for viewing data in the LDAP server. In Listing 25-1, we used the -D option to specify the bindDN with to connect to the LDAP server, as well as the -W option to tell ldapsearch to ask for the password.

We used the -x option to tell ldapsearch to do a simple bind to the LDAP server. If you do not use -x, you need to bind using a Simple Authentication and Security Layer (SASL) mechanism. We will not discuss SASL authentication in this chapter because this is just an introduction to LDAP. For more information on configuring OpenLDAP with SASL, refer to the OpenLDAP documentation in /usr/share/doc/packages/openldap.

# LDIF

An LDIF is a file containing LDAP data in a protocol defined fashion. You need to create an LDIF file that defines not only the data to be stored, but also the structure of the LDAP server. Use your favorite text editor to create the LDIF file. In Listing 25-2, we have created one you can work from that reflects the Acme organization.

# Listing 25-2: LDIF File for Acme

```text
dn=oAcme,c=UK
o: Acme
objectClass: top
objectClass: organization

d=ou=Sales,o=Acme,c=UK
ou: Sales
objectClass: top
objectClass: organizationalUnit

d=ou=Marketing,o=Acme,c=UK
ou: Marketing
objectClass: top
objectClass: organizationalUnit

d=ou=IT,o=Acme,c=UK
ou: IT
objectClass: top
objectClass: organizationalUnit

d=ou=HR,o=Acme,c=UK
ou: HR
objectClass: top
objectClass: organizationalUnit

d=ou=Services,o=Acme,c=UK
ou: Services
objectClass: top
objectClass: organizationalUnit
```

It is important when creating LDIF file that there are no trailing spaces after data in a record. It is a common mistake when people create an LDAP entry that there is a trailing space, and in the case of an LDAP entry, this will create an error when it is inserted into the LDAP server. Data that looks correct in the LDAP file will not be the same as it is in the LDAP server. also, the order of the LDAP entries is important.

Most of the entries are identical apart from the ou (organizational unit) they are defining. We will go through the file to help you understand what the entries mean.

Each entry has a specific DN that is unique across the tree. For example, the Architects' organizational unit tells us that the Architects are in the organizational unit of IT, in the Acme organization. Referring back to the organizational chart of Acme, you can see this reflected correctly. (We hope you see how easy it is to compile the initial population of the LDAP server when you have access to the organizational chart!)

Each entry defines the structure of the LDAP server and does not actually information that you are interested in at this part. Apart from the first entry, you are creating an organizational unit that will hold data about people in that department.

# Dissecting an Object

An entry is composed of the DN, the object being created (in this case, the organizational unit), and object class definitions. We talked about objects and restrictions on what can be stored in each.

The top entry is very special as it says that all objects should be defined by a class. It may seem bizarre that there is an object class that defines an object, but it means that the LDAP structure is totally modular and not hard-coded.

the organizationalUnit objectClass defines the object to be an organizational unit. There are many other objectClasses that define a massive set of objects that can be used to describe anything that would traditionally fit into an LDAP server. We will come across them throughout the chapter.

An object may be defined by multiple object classes to provide a large breadth of information. We will see this in practice when dealing with people, but for now, understand that it is not just one object class, one object.
