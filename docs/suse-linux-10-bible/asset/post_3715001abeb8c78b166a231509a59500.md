To create a configuration file for the domain that you are creating, copy the file /etc/xen/xmample1 to a file whose name represents the domain that you are creating. Next, edit this file using your favorite text editor and modify it to reflect appropriate values for the domain that you are creating. The key items that you want to associate are the following (listed in the order that you encounter in the sample configuration file):

- *kernel="/path/to/Xen/kernel" — The full path of the Xen-enabled kernel that you want to boot on the virtual machine which you are defining.
- *memory=amount-to-allocate-in-mb — The amount of memory that you want to allocate to the virtual machine that you are defining, in megabytes.
- *name="domain-name" — The name that you want to associate with the virtual machine. This can be any text string and not be related to your network domain. It is just a unique identifier for the virtual machine.
- *nics=number-of-NICS — The number of network interfaces that you want the virtual machine to create, excluding the loopback interface. The default value is 1, but we find it useful to set this value as a reminder of the number of network interfaces the virtual machine will export.
- *vif = 'mac-aa:00:00:00:00:01,bridge-xen-br0' — Specific information about each virtual network interface exported by the machine, consisting of a MAC address/Ethernet-device pair. Although technically optional, specifying an explicit MAC address for your virtual machine's Ethernet simplifies automatic network startup on systems such as SUSE, whose scripts typically refer to a specific MAC address. The Ethernet-device device on your host system that the bridge-tools package will automatically associate with the Xen virtual machine that you are defining.

- *disk = ['physical-partition-or-file-name,virtual-machine-partition-mode', 'phy:vdb0/vroot,w'] — Information about the disk that you want the virtual machine to be able to use or see. Each value contains the name of the physical disk or device that you are exporting to the virtual machine from the host system, the name of the device as seen by the virtual machine, and how the machine uses it. Possible values for physical-partition-or-file-name include values such as phy:hdd2/dev/hdd2 (the host system), phy:vdb0/root (the logical volume in volume group 0 on the host system), file:/home/xen/xen.img (a file on the host system that contains an image of a root partition), and so on. The virtual-machine-partition-name is the name of the device as seen by the virtual machine. This enables you to map partitions/files on the host system to explicit partition names on the virtual machine, which you can then identify and refer to in the etc/fstab on the virtual machine. The final value in each of these titles is mode, which indicates how the virtual machine will use the specified partition or partition image. Possible values for mode are r (for read-only) and w (for a writable partition or image).

- *root = /dev/boot-partition - The name of the root partition by the virtual machine and its write-mode. This value will be passed to the virtual machine's kernel when booting the virtual machine. Possible values for /dev/boot-partition are any of the partitions that you defined in the disk partition of your virtual machine configuration file. Possible values for mode are ro (read-only) and rw (read/write).

- *extra = "run-level" - Any argument that you want to pass to the kernel of the virtual machine when it boots. As previously mentioned, we typically use run-level 4 for the default level of Xen virtual machines, so you typically pass 4 to the kernel as an extra boot option. You could do the same by modifying the initrd file in the virtual machine's root, setting extra to 4, but we prefer to specify this on the host side that it is easily overridden and is clear to any user before they connect to a virtual machine.

After you've created your virtual machine's configuration file, you're ready to boot the machine.

# Starting, Stopping and Interacting with Xen Virtual Machines

Before you start a Xen virtual machine, Xen's main daemon (xend) must be running on your system. This daemon is usually started through the startup script /etc/init.d/xend, which was installed on your host system as part of the Xen package.

After you have started the Xen daemon, you can open a console to any of the virtual machines that you have defined by executing the xm command. If you are starting a Xen virtual machine for the first time, you must specify your configuration file on the command line using the xm command's -c option. For example, to start the Xen virtual machine defined in the Xen configuration file /etc/xen/xvh_vm_1.conf, you would type the following command as the root user or via sudo:

```
xm console -c /etc/xen/xvh_vm_1.conf
```

This command starts the specified virtual machine and displays its console in the window in which you executed the command. For this reason, you might find it inconvenient to start each virtual machine console session in its own xterm window, as in the following example:

```
xterm -e xm console -c /etc/xen/xvh_vm_1.conf &
```

This command opens a new xterm window and executes the specified xm console command within it. Figure 28-12 shows a SUSE system displaying an xterm containing a console to a Xen virtual machine running on that same hardware.

# Automating Domain Startup

SUSE includes a convenient mechanism for automatically starting Xen domains on a host system through the /etc/init.d/xend startup script. For example, to automatically start the Xen virtual machine defined in the configuration file /etc/xen/vbh_vm_1.conf, you would simply move this file to the /etc/xen/auto directory and add the /etc/init.d/xend startup script to the boot sequence to run on host system.

# More Information About Xen

Xen is still developed at the University of Cambridge's Computer Laboratory (www.cl.cam.ac.uk/Research/SRG/netos/xen). The developers of Xen have also started a company XenSource (www.xource.com) whose purpose is to commercialize Xen and use it in enterprise environments. Both of these sites provide a deal of information and other online resources to help you use Xen as a virtual solution to machine requirements.

Xen is an interesting and exciting technology that is easy to set up and use on SUSE Linux systems thanks to its built-in support in YaST and modern SUSE Linux distributions.

# User Mode Linux and FAmachine

SUSE has for some time included User Mode Linux (UML), which offers a way of running Linux on top of Linux as a user process. SUSE has more recently begun to package FAMachine, a similar project that comes from the University of Erlangen in Germany that has evolved to allow the running of some non-Linux guest systems and some integration with QEMU.

UML has had some popularity in recent years as a way for hosting companies to offer full Linux servers with root access to their customers. However, with the extraordinary growth and maturity of Xen, UML will be seen as largely superseded in this role. It remains an interesting way of running Linux on the desktop.
