It is important when creating LDIF file that there are no trailing spaces after data in a record. It is a common mistake when people create an LDAP entry that there is a trailing space, and in the case of an LDAP entry, this will create an error when it is inserted into the LDAP server. Data that looks correct in the LDAP file will not be the same as it is in the LDAP server. also, the order of the LDAP entries is important.

Most of the entries are identical apart from the ou (organizational unit) they are defining. We will go through the file to help you understand what the entries mean.

Each entry has a specific DN that is unique across the tree. For example, the Architects' organizational unit tells us that the Architects are in the organizational unit of IT, in the Acme organization. Referring back to the organizational chart of Acme, you can see this reflected correctly. (We hope you see how easy it is to compile the initial population of the LDAP server when you have access to the organizational chart!)

Each entry defines the structure of the LDAP server and does not actually information that you are interested in at this part. Apart from the first entry, you are creating an organizational unit that will hold data about people in that department.

# Dissecting an Object

An entry is composed of the DN, the object being created (in this case, the organizational unit), and object class definitions. We talked about objects and restrictions on what can be stored in each object, and the objectClass entry is what defines this.

The top entry is very special as it says that all objects should be defined by an objectClass. It may seem bizarre that there is an object class that defines an object must have a class, but it means that the LDAP structure is totally modular and not hard-coded.
