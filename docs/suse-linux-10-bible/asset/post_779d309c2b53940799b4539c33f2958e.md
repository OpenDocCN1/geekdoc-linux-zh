
When a BIND server has been configured as a forwarder, it automatically caches any answers it receives from the Internet DNS servers. No extra configuration is needed to enable this caching functionality.

When the forwards declaration is configured, start the nameserver with *rcnamed*:

```
bind:: # rcnamed start
Starting nameserver BIND 9
```

To automatically set named to start when you system boots, use *chkconfig* -a named.

Before you start testing the DNS server, you need to configure the DNS resolver. To do this, you need to edit the /etc/resolv.conf file. Change the nameserver entry to your newly created DNS server. In this case, this is 127.0.0.1.

```
search palmcoder.net
nameserver 127.0.0.1
```

When the DNS server is started, you can look up a host name on the Internet to check that the forwarder and DNS are working correctly. The *dig* program is used to query a DNS server for information (see Listing 21-1), and we use it throughout this chapter for this purpose.

## Using dig

The dig program is being phased in as a replacement for the *nslookup application. With dig, you can query specific record types in a DNS zone. To query a specific record type, use the -t option. For example:

- To query the MX record of palmcoder.net, use *dig -t mx palmcoder.net.*
- For a nameserver (NS), use *dig -t ns palmcoder.net.*
- For an address record (A), use *dig -a www.palmcoder.net.*.

Listing 21-1: Using dig to Test a DNS Server

```
bind:: # dig www.palmcoder.net
;; Warning: ID mismatch: expected 23997, got 50172
;; Warning: ID mismatch: expected 23997, got 50172
<<>> DIG 9.2.3 << www.palmcoder.net
;; global options: printcmd
;; answer:
;;>>HEADER<< opcode: QUERY, status: NOERROR, id: 23997
;; flags: gr rd ra; QUERY: 1, ANSWER: 2, AUTHORITY: 1, OPTIONAL: 0
```

Listing 21-1 (continued)

```
;; QUESTION SECTION:
www.palmcoder.net.             IN A

;; ANSWER SECTION:
www.palmcoder.net.             38396 IN CNAME
zen.palmcoder.net.             38400 IN A 212.13.208.115

;; AUTHORITY SECTION:
palmcoder.net.                 38400 IN NS zen.palmcoder.net.

;; Query time: 443 msec
;; SERVER: 127.0.0.1:853(127.0.0.1)
;; WHEN: Tue Jul 6 10:02:21 2004

```

In the past, the name resolver nslookup was used in place of dig; nslookup is now deprecated, but is included in most Linux distributions. If you want to do a quick name resolution, using nslookup hostname returns the IP address.

The output of dig can be confusing if you have never used it before, but its response to a name query is logical when you understand what DNS does. The output contains three basic parts:

- The first part of the response is the QUESTION section. The QUESTION is what was sent originally to the DNS server. In this case, you asked for A record of www.palmcoder.net. (Note that we talk about record types in the chapter).
- The second part is the ANSWER section. The answer is the response to your query. In this case, you have found the www.palmcoder.net is a CNAME of zen.palmcoder.net, and zen's address is 212.13.208.115.
- Finally, you have the AUTHORITY section. The authority is the controlling server's IP address in the NS record.

## Using host

A user-friendly replacement for the nslookup program that enables you to query the DNS information about a domain is host. Using host, you can query a specific domain record and by default look up the address mapping of a host name.

```
bind:~ # host www.palmcoder.net
www.palmcoder.net is an alias for zen.palmcoder.net.
zen.palmcoder.net has address 212.13.208.115
```

In this example, host has queried the nameserver that is authoritative for the palmcoder.net domain and has found that the host name www.palmcoder.net is actually a CNAME for zen.palmcoder.net with an address of 212.13.208.115.

If you want to find a specific DNS record for a domain, you use the -t option, specifying the record type:

```
bind:~ # host -t mx palmcoder.net
palcoder.net mail is handled by 10 mail.palmcoder.net
palcoder.net mail is handled by 20 pirhana.bymark.co.uk.
```

Here, host has queried the nameserver that is authoritative for palmcoder.net, asking for the MX record for the domain. It has found that there are two mail and pirhana.bymark.co.uk, with mail.palcoder.net taking precedence over pirhana.bymark.co.uk.

## Examining Record Types

Before we delve into creating a zone (an administrative domain) in DNS, we need to talk about record types. We briefly touched upon the fact that DNS provides not only host-to-IP address translation, but also mail server information. A record type tells what kind of information it is storing and is something you can explicitly query. For example, you query the MX record for a domain to find out which mail server to use when sending mail to the domain. Services that rely on DNS drastically reduce the amount of traffic produced because you only see the data you explicitly asked for, not the whole record. What makes this happen is the use of record types. With DNS, you have six record types to keep in mind:

- The Address record — The most common record in DNS is the Address record. An address record is used to translate a host name to an IP address.
- The Pointer record — A Pointer record is the reverse of an Address record. It translates an IP address to a host name.
- The CNAME record — If you want to create an alias of one host to another, a CNAME record is used.
- The MX record — An MX record is used to define the Mail Exchanger for the domain (or zone) you created.
- The NS record — The NS record is used to define the nameserver for the domain.
- The SOA record — The Start of Authority (SOA) is effectively the header for the zone. It contains information about the zone itself and is mandatory.

## Working with Zones

A zone is a description, or definition, of a domain (or subdomain). The zone is what makes up the database of records for a domain. /var/lib/named are text files containing the data for the zone. BIND defines its zones in /etc/named.conf by specifying the location of these files. In this section you will see how a DNS zone is constructed and what information you can store for a zone. We use palmcoder.net as an example of a zone (see Listing 21-2) and will go through the DNS records and explain their uses.

Listing 21-2: The palmcoder.net Zone

```
palmcoder.net.  IN  SOA  palmcoder.net. admin.palmcoder.net. (
                   2005072401
                   10800
                3600
                60480
                86400)
NS  zen
MX  10 mail
MX  20 pirhana.bymark.co.uk.

zen  A  212.13.208.115
www  NAME  zen
mail A  212.13.208.115
scpan NAME  zen
shuttle A  195.137.245
```

## The Start of the Authority

At the start of the zone, you have the SOA that is authoritative for the domain in question, palmcoder.net. Notice that palmcoder.net ends in a full stop (a period). This is extremely important in the zone file for any domain. As you saw in Figure 21-1, the top of the DNS tree is the root of the DNS tree. A full stop is the limiter for the DNS tree; following the palmcoder.net domain all the way up the tree, the full domain name is palmcoder.net (with the full stop). If a full stop is not found, in the zone record listed at the end in the example, the SOA's domain will be appended to the host name in the record.

## The SOA Server

The SOA can be further analyzed to break down the record's uses. After the definition of the domain you are managing, you need to define the server that is authoritative for the domain. It may seem bizarre, but you are referring to a name, not an IP address in this case, because BIND is aware that it needs to find the IP address for the server from its zone (it may sound like a vicious cycle, but it does work). In Listing 21-2, for example, the SOA for palmcoder.net is zen.palcoder.net.

## The Hostmaster

With most things on the Internet, it is common practice to provide a technical contact for the service. In this case, it is the email address justin.palcoder.net. You will notice that there is no @ in the email address, but a full stop (period). The hostmaster for the palmcoder.net zone is justin.palcoder.net (justin@palm-coder.net).

## The SOA Record

The brackets around the rest of the data dictate that everything else up to the closing-bracket is part of the SOA record. All time settings are in seconds.

## The Serial Number

The first entry is the serial number for the zone. This is one of the most important parts of the SOA because it must be changed any time you edit the zone file. The serial number tells other DNS servers that are querying your DNS server has changed. If you do not change the serial number, your changes will not get propagated through the system.

The general form of the serial number is the date, followed by an arbitrary number. For the 24th of July, you use 2005072401 (July 24, 2005). Notice that the date is in reverse, with the year (2005), month (07) and day (24), with an additional two digits able to repeat multiple changes in one day.

## The Refresh Rate

If you have a slave DNS server in your system (as a backup to your master), the refresh rate tells the slave server how often to check for updates to the zone. If you look back at Listing 21-2, you will see the refresh rate set to 10,800 seconds (3 hours).
