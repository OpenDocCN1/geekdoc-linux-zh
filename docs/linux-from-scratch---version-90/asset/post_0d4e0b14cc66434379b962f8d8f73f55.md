
## 7.3.3.2. A kernel module is not loaded automatically, and Udev is not intended to load it

If the “wrapper” only enhances the functionality provided by some other module (e.g., snd-pcm oss enhances the functionality of snd-pcm by making the sound cards available to OS applications), configure modprobe to load the wrapper after Udev loads the wrapped module. To do this, add a “softdep” to the corresponding /etc/modprobe/<filename>.conf file. For example:

```
softdep snd-pcm post: snd-pcm-oss
```

Note that the “softdep” command also allows pre: dependencies, or a mixture of both pre and post:. See the modprobe.d (5) manual page for more information on “softdep” syntax and capabilities.

If the module in question is not a wrapper and is useful by itself, configure the modules bootscript on your system. To do this, add the module to the /etc/sysconfig/modules file on a separate line. This works for modules too, but is suboptimal in that case.

## 7.3.3.3. Udev loads some unwanted module

Either do not build the module, or blacklist it in a /etc/modprobe.d/blacklist.conf file as done with the forte module in the example below:

```
blacklist forte
```

Blacklisted modules can still be loaded manually with the explicit modprobe command.

## 7.3.3.4. Udev creates a device incorrectly, or makes a wrong symlink

This usually happens if a rule unexpectedly matches a device. For example, a poorly-written rule can match both the SCSI device (as desired) and the corresponding SCSI generic device (incorrectly) by vendor. Finding the rule and making it more specific, with the help of the udevadm info.

## 7.3.3.5. Udev creates rules unnecessarily

This may be another manifestation of the previous problem. If not, and your rule uses sysfs attributes, it may be the kernel timing, to be fixed in later kernels. For now, you can work around it by creating a rule that waits for the used sysfs attributes and appending it to the /etc/udev/rules.d/10-wait_for_sysfs.rules file (create this file if it does not exist). Please notify the LDS Development list if you do so and it.

## 7.3.3.6. Udev does not create a device

Further text shows that the device is built statically into the kernel or loaded as a module, and that you have already checked that Udev doesn't create a misnamed device.

Udev has no information to create a device if a kernel driver does not export its attributes to sysfs. This is most common with third party drivers from outside the kernel. Create a static device node in /lib/udev/devices with the appropriate major/minor numbers (see file devices.txt inside the kernel documentation or the documentation provided by the third party driver vendor). The static device node will be copied to /dev by udev.

## 7.3.3.7. Device naming changes randomly after rebooting

This is due to the fact that Udev, by design, handles events and loads modules in parallel, and thus in an unpredictable order. This will never be “fixed”. You should not rely the kernel device name being stable. Instead, create your own rules that make symlinks with stable names based on stable attributes of the device, such as a serial number or the output of variety *id attributes installed by Udev. See Section 7.4, “Managing Devices” and Section 7.5, “General Network Configuration” for examples.

## 7.4. Managing Devices

### 7.4.1. Network Devices

Udev, by default, names network devices according to Firmware/BIOS data or physical characteristics the bus, slot, or MAC address. The purpose of this naming convention is to ensure that network devices are named consistently and not based on the time the network card was discoverd. For example, a computer having two network cards made by Intel and Realtek, the network card manufactured by Intel may become eth0 and the Realtek card become eth1. In some cases, after a reboot the cards get renamed the other way around.

In the new scheme, typical network device names would be something like enps0 or wlp3s0. If this naming convention is not desired, the traditional naming scheme or a custom scheme can be implemented.

#### 7.4.1.1. Disabling Persistent Naming on the lines Command Line

The traditional naming scheme using eth0, eth1, can be restored by using net.ifnames=0 on the kernel command line. This is most appropriate for systems that have only one device for the system. Laptops often have multiple ethernet connections that are named eth0 and wlan0 are also candidates for this method. The command line is passed in the GRUB configuration file. See Section 8.4.4, "Creating the GRUB Configuration"

#### 7.4.1.2. Creating Udev Rules

The naming scheme can be customized by creating Udev rules. A script has been included that generates the initial rules. Generate these rules by running:

```bash
bash /lib/udev/init-persistent-rules.sh
```

Now, inspect the /etc/udev/rules.d/70-persistent-net.rules file, to find out which name was assigned to which network device:

```bash
cat /etc/udev/rules.d/70-persistent-net.rules
```

> In cases such as when MAC addresses have been assigned to a network card manually or in a virtual environment like Qemu or Xen, the network rules file may not have been generated because addresses are not consistently assigned. In these cases, this method cannot be used.

The file begins with a comment block followed by lines for each NIC. The line for each NIC is a comment showing its hardware IDs (e.g. its PCI vendor and device IDs, if it's a PCI card), along with its driver in parentheses, if the driver can refer. Neither the hardware ID nor the driver is used to determine name to give an interface; this information is only for reference. The second line is the Udev rule that matches this NIC and assigns it a name.

All Udev rules are made up of several keys, separated by commas and optional whitespace. This rule's keys and explanation of each of them are as follows:

- SUBSYSTEM="net" - This tells Udev to match network interfaces.
- ACTION="add" - This tells Udev to act only when a device is added.
- DRIVERS="*" - This ensures the rule only matches devices that have drivers assigned.
- ATTR{address} - The value of this key is the MAC address.
- ATTR{type}="*" - This tells Udev to match by the device type.
- NAME - The value of this key is the name Udev will assign to the interface.

### 7.4.2. CD-ROM symlinks

Some software that you may want to install (e.g., various media players) expect the /dev/cdrom and /dev/dvd symlinks to exist, and point to a CD-ROM. Udev comes with a script that will generate rules for you, depending on the capabilities of each device, and you will need to decide which modes of operation you wish to have. The first can operate in "by-path" mode (used by default for USB and FireWire devices), where the rules depend on the physical path of the CD or DVD device. Second, it can in "by-id" mode (default for IDE and SCSI devices), where the rules depend on identification strings stored in the CD or DVD device itself. The path is determined by Udev's path_id script, and the identification strings are read from the hardware by its at_id or scsi_id programs, depending on which type of device you use.

There are advantages to each approach; the correct approach to use will depend on what kind of devices changes may happen. If you expect the physical path to the drive (that is, the ports and slots that it plugs into) to change, for example you may plan on moving the drive to a different IDE port or a different USB connector, then you use the "by-id" mode. On the other hand, if you expect the device's identification to change, for example you may replace it with a different device with the same capabilities and which is plugged into the system connectors, then you use the "by-path" mode.

> Important External devices (for example, a USB-connected CD drive) should not use by-path persistence, because each time the device is plugged into a new external port, its physical path will change. All-connected devices will have this problem if you write Udev rules to recognize by their physical path; the problem is not limited to CD and DVD drives.

If you wish to see the values that Udev scripts will use, for the appropriate CD-ROM device, the corresponding directory under /sys (e.g., this can be /sys/block/hdd) and run a command similar to the following:

```bash
udevadm test /sys/block/hdd
```
