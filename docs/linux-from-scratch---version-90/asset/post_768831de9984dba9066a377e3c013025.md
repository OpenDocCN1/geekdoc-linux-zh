
# LFS From Scratch - Version 9.0

LFS system itself will not take up much room. A large portion of requirement is to provide sufficient free storage as well as for additional capabilities after LFS is complete. Additionally, compiling can require a lot of disk space which will be reclaimed after the package is installed.

Because there is not enough Random Access Memory (RAM) available for compilation processes, it is a good idea to use a small disk partition as swap space. This is used by the kernel to store someunused-data and leave more memory available for active processes. The swap partition for an LFS system can be the same as the one used by the host system, in which it is not necessary to create another.

Start a disk partitioning program as cfdisk or fdisk with a command line option naming the hard disk on which the new partition will be--example /dev/sda for the disk drive. Create a Linux partition and a swap partition, if needed. Please refer to cfdisk (8) or fdisk (8) if you do not know how to use the programs.

> For experienced users, other partitioning schemes are possible. New LFS system can be on a software RAID array or LVM logical volume. However, some of these require an initramfs, which is an advanced topic. These partitioning methodologies are not recommended for first LFS users.

Remember the designation of the new partition (e.g., sda5). This book will refer to the LFS partition. Also remember the designation of the swap partition. These names will be needed later for the /etc/fstab file.

## 2.4.1. Other Partition Issues

Requests for advice on swap partitioning are often posted on the LFS mailing lists. This is a highly subjective topic. The default for most distributions is to use the entire drive with the exception of one small swap partition. This is not optimal for LFS for several reasons. It reduces flexibility, sharing data across multiple distributions or LFS builds more difficult, making backups more time consuming, and can waste disk space through inefficient allocation of file system structures.

### 2.4.1.1. The Root Partition

A root partition (not to be confused with the /root directory) of ten gigabytes is a good compromise for most systems. It provides enough space to build LFS and most of BLFS, but is small enough that multiple partitions can be easily created for experimentation.

### 2.4.1.2. The Swap Partition

Most distributions automatically create a swap partition. Generally the recommended size of the swap partition is about twice the amount of physical RAM, however this is rarely needed. If disk space is limited, hold the swap partition to two gigabytes and monitor the amount of swapping.

Swapping is never good. You generally tell if a system is swapping by listening to disk activity and observing how the system reacts to. The first reaction to swapping should be check for an unreasonable command such as trying to edit a five gigabyte file. If swapping becomes a normal occurrence, the best solution is to purchase more RAM for your system.

### 2.4.1.3. The Grub Bios Partition

If the boot has been partitioned with a GUID Partition Table (GPT), then a small, typically 1 MB, partition must be created if it does not already exist. This partition is not formatted, but will be available for GRUB using during installation of the boot loader. This partition will be labeled 'BIOS Boot' if using fdisk or have a code of EF02 if using gdisk.

# Note

The Grub Bios partition must be on the drive that the BIOS uses to boot the system. This is not necessarily the same drive where the LFS root partition is located. Disks on a system may use different partition table types. The requirement for this partition depends only on the partition type of the boot disk.

### 2.4.1.4. Convenience Partitions

There are other partitions that are not required, but should be considered when designing a disk layout. The following list is not comprehensive, but is meant as a guide.

- /boot – Highly recommended. Use this partition to store kernels and other booting information. To minimize potential boot problems with larger disks, make this the first partition on your first disk drive. A partition size of 100 megabytes is quite adequate.
- /home – Highly recommended. Share your home directory and user customization across multiple distributions or builds. The size is generally large and depends on available disk space.
- /usr – A separate /usr partition is generally used if providing a server for a client or diskless workstation. It is not normally needed for LFS. A size of five gigabytes will handle most installations.
- /opt – this directory is most useful for BLFS where multiple installations of packages like Gnome or KDE can be installed without embedding the files in the /usr hierarchy. If, 5 to 10 gigabytes is generally adequate.
- /tmp – A separate /tmp directory is rare, but useful if configuring a client dns. This partition, will usually not need to exceed a couple of gigabytes.
- /usr/src – this partition is very useful for providing a location to store BLFS sources and share them across LFS builds. It can also be used as a location for building BLFS packages. A reasonably large partition of 30-50 gigabytes allows plenty of room.

Any partition that you use automatically mounted upon boot needs to be specified in the /etc/fstab. Details about how to specify partitions will be discussed in Section 8.2, "Creating the /etc/fstab".

## 2.5. Creating a File System on the Partition

Now that a blank partition has set up, the file system can be created. LFS can use any file system recognized by the Linux kernel, but the most common types are ext3 and ext4. The choice of file systems can be complex and depends on the characteristics of.

- ext2 is suitable for small partitions that updated infrequently.
- ext3 is an upgrade to ext2 that includes journal.
- ext4 is the latest version of. It provides new capabilities including speed.

Other file systems, including FAT32, NTFS, ReiserFS, JFS, and XFS are useful for specialized purposes. More information about these systems can be found at http://en.wikipedia.org/Comparison_of_file_systems.

## 2.6. Setting The LFS Variable

Throughout this book, the environment variable LFS will be used several times. You should ensure that this variable is always defined throughout the build process. It should be set to the directory where you will be building LFS - we will use /mnt/lfs as an example, the directory choice is up to you. If you are building LFS on a separate partition, this directory will be the mount point. Choose a directory location and set the variable with the following command:

```
export LFS=/mnt/lfs
```

Having this set is beneficial in commands such as mkdir -v $LFS/tools can be typed literally. The shell will automatically replace "$LFS" with "mnt/lfs" (or whatever the variable was set to) when it processes the command line.

> Caution
Do not forget to check that $LFS is set whenever you leave and reenter the current working environment (such as doing a su to root or another user). Check that the LFS variable is set properly with:

echo $LFS
Make sure the output shows the path to your LFS system's build location, which is /mnt/lfs if the provided example was followed. If the output is incorrect, use the command earlier on this page to set LFS to the correct directory.

One way to ensure that the $LFS variable is always set is to edit .bash_profile in both your personal home directory and in /root/.bash_profile and ensure the export command above. In addition, the shell in /etc/passwd file for all users who need the LFS variable needs to be bash to ensure that the /root/.bash_profile is incorporated as part of the login process.

Another consideration is the method used to log into the host system. If logging in a graphical display manager, the user's .bash_profile is not normally used when a virtual terminal is started. In this case, add the export command to .bashrc for the root. In addition, some distributions have instructions to run the .bashrc instructions in a non-interactive bash invocation. Be sure to add the export command before the test for non-interactive use.
