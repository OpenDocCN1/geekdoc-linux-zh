
Look at the lines containing the output of various *_id programs. The "by-id" mode will use the ID_SERIAL if it exists and is not empty, otherwise will use a combination of ID_MODEL and ID_REV. The "by-path" mode will use the ID_PATH value. If the default mode is not suitable for your situation, then the following modification can be made to the /etc/udev/rules.d/70-persistent-rules file, as follows (where mode is one of "by-id" or "by-path"):

```
sed -i 's/link= /link=' /etc/udev/rules.d
```

Note that it is not necessary to create rules or links at this time because you have bound the host's /dev directory into the Linux system, and the rules and symlinks will be created the first time you boot LFS. However if you have multiple devices, the symlinks generated at that time may point to different devices than they should because devices are not discovered in predictable order. The assignments created when you boot LFS system will be stable, so this is only an issue if you use symlinks on both systems to the same device. If you need that, then inspect (and possibly edit) the generated /etc/udev.rules.d/70-persistent-rules file.

## 7.4.3. Dealing with duplicate devices

As explained in Section 7.3, "Overview of Device Handling", the order in which devices with the same function appear in /dev is essentially random. E.g., if you have a USB camera and a TV tuner, sometimes /video0 refers to the camera and /video1 refers to the tuner, and sometimes after a reboot the order changes to the opposite one. For all classes except sound cards and network cards, this is fixable by creating udev rules for custom names. For each of your devices that are likely to have this problem (even if it doesn't exist in your current distribution), finding the corresponding directory under /sys/class or block. For video devices, this may be /sys/class/videoX. Figure out the attributes that identify the device uniquely (usually vendor product IDs and/or serial numbers work):

```
adm /sys/class/video0
```

Then udev will create the symlinks,

```
# Persistent symlinks
KERNEL="video*", ATTRS{idProduct}="1910", ATTRS{idVendor}="0d81", SYMLINK+="webcam"
KERNEL="video*", ATTRS{device}="0x36f", ATTRS{vendor}="0x19e", SYMLINK+="tvtuner"
EOF
```

The result is that /dev/video0 and /video1 will still refer to the tuner and the webcam (and should never be used directly), but there are symlinks /dev/tvtuner and /dev/webcam that always point to the correct device.

## 7.5. General Network Configuration

### 7.5.1. Creating Network Interface Files

Which interfaces are brought up and down by the network script usually depends on the files in /etc/sysconfig/. This directory should contain a file for each interface to be configured, as ifconfig.xyz, where "xyz" describes the network card. The interface name (e.g., eth0) is usually appropriate. This file contains attributes to this interface, such as its IP address(es), subnet masks, and settings. It is necessary that the stem of the filename be ifconfig.

> **Note**
> If the procedure in the previous section was not used, udev will assign network interface names based on system physical characteristics as enp2s1. If you are not sure what your interface name is, you can run link or ls /sys/class/net after you have booted your system.

The following command creates a sample file for the eth0 device with a static IP address:

```
cd /etc/sysconfig/
cat > ifconfig.eth0 << "EOF"
ONBOOT=yes
INTERFACE=eth0
SERVICE=ipv4static
IP=192.168.1.2
GATEWAY=192.168.1.1
PREFIX=24
BROADCAST=192.168.1.255
EOF
```

The values in it must be changed in the file to match the proper setup.

If the ONBOOT variable is set to "yes" the System V network script will bring up the Network Interface Card (NIC) during booting of the system. If set to anything but "yes" the NIC will be ignored by the network script and not be automatically brought up. The interface can be manually started or stopped with the ifup and ifdown commands.

The IFACE variable defines the interface name, for example, eth0. It is required for all device configuration files. The filename extension must match this value. The FS-Bootscripts package has a modular IP assignment format, creating additional files in the /lib/services/ directory allows other IP assignment methods. This is commonly used for Dynamic Host Protocol (DHCP), which is addressed in the BLFS books.

The GATEWAY variable should contain the default gateway IP address, if one is present. If not, then comment out the PREFIX variable.

The PREFIX variable contains the number of bits used in the subnet. Each octet in an IP address is 8 bits. If the subnet mask is 255.255.255.0, it is using the first 24 bits to specify the network number. If the network is 255.255.255.240, it would be using the first 28 bits. Prefixes longer than 24 bits are commonly used by DSL and cable-based Internet Service Providers (ISPs). In this example (PREFIX=24), the netmask is 255.255.255.0. Adjust the PREFIX variable according to your subnet. If omitted, the PREFIX defaults to 24.

### 7.5.2. Creating the /resolv.conf File

The system will need some means of obtaining Domain Name Service (DNS) resolution to resolve Internet addresses and vice versa. This is best achieved by placing the IP address of the DNS server, available from your ISP or network administrator, into /resolv.conf. Create the file by running:

```
cat > /resolv.conf << "EOF"
# Begin /resolv.conf
domain <Domain Name>
nameserver <primary nameserver>
nameserver <secondary nameserver>
EOF
```

The domain statement can be omitted or replaced with a search statement. See the man page for resolv.conf for more details. Replace `IP address of nameserver` with the IP address most appropriate for the setup. If you only want one DNS server, remove the second nameserver line from the file. The IP address may also be a router on the local network. 

> **Note**
> The Google Public IPv4 DNS addresses are 8.8.8.8 and 8.8.4.4.

### 7.5.3. Configuring the hostname

During the boot process, the file /etc/hostname is used for establishing the system's hostname. Create the /etc/hostname file and enter a hostname by running:

```
echo "<hostname>" > /etc/hostname
```

`<hostname>` needs to be replaced with the name given to the computer. Do not enter the Fully Qualified Domain Name (FQDN).

### 7.5.4. Customizing the /hosts File

Decide on the IP address, fully-qualified domain name (FQDN), and possible aliases for use in the /etc/hosts file. The syntax is:

```
IP_address hostname.example.org aliases
```

Unless the computer is to be visible to the Internet (i.e., there is a registered domain and a valid block of assigned addresses—most users do not have this), make sure that the IP address is in the private address range. Valid ranges are:

| Private Network Address Range | Normal Prefix |
| :--- | :--- |
| 10.0.0.1 | 8 |
| 172.x.0.1 - 172.x.255.254 | 16 |
| 192.168.y.1 - 192.168.y.254 | 24 |

x can be any number in the range 16-31. y can be any number in the range 0-255. A valid IP address could be 192.168.1.1. A valid FQDN for this IP could be lfs.example.com.

Even if not using a network card, a valid FQDN is still required. This is necessary for certain programs to operate correctly. Create the /etc/hosts file by running:

```
cat > /etc/hosts << "EOF"
# Begin /etc/
127.0.0.1 localhost
127.0.0.1 <FQDN> <HOSTNAME>
192.168.1.1 <FQDN> <HOSTNAME> [alias1] [alias2 ...]
::1 localhost ip6-localhost ip6-loopback
ff02::1 ip6-allnodes
ff02::2 ip6-allrouters
# End /etc/hosts
EOF
```

The <192.168.1.1>, <FQDN>, and <HOSTNAME> values need to be changed for specific uses or requirements (if assigned an IP address by a network/system administrator and the machine will be connected to an existing network). The optional alias name(s) can be omitted.

## 7.6. System V Bootscript Usage and Configuration

### 7.6.1. How do the System V Bootscripts Work?

Linux uses a special booting named SysVinit that is based on a concept of run-levels. It can be quite different from one to another, so it cannot be assumed that things worked in one particular Linux distribution; they should work in the same LFS too. LTS has its own way of doing things, but it generally accepts standards.

SysVinit (which will be referred to as "init" from now on) uses a run-levels scheme. There are seven (0 to 6 run-levels (actually, there are more run-levels, but they are for special cases and generally not used). See init (8) (for more details), and each one of those corresponds to the actions the computer is supposed to perform when it starts up. The default run-level is 3.
