
## 5.33. Texinfo-6.6

The Texinfo package contains programs for reading, writing, and converting info pages.
Approximate build time: 0.2 SBU
Required disk space: 103 MB

### 5.33.1. Installation of Texinfo

Prepare Texinfo for compilation:

```
./configure --prefix=/tools
```

> Note
As part of the configure process, a test is made that indicates an error for TestXS_la-TestXS.lo. This is not relevant for LFS and should be ignored.

Compile the package:

```
make
```

Compilation is now complete. As discussed earlier, running the test suite is not mandatory for the temporary tools here in this chapter. To run the Texinfo test suite anyway, issue the following command:

```
make check
```

Install the package:

```
make install
```

Details on this package are located in Section 6.70.2, “Contents of Texinfo.”

## 5.35. Stripping

The steps in this section are optional, but if the LFS partition is rather small, it is beneficial to learn that unnecessary items can be removed. The executables and libraries built so far contain about 70 MB of unneeded debugging symbols. Remove them with:

```
strip --strip-debug /tools/lib/*
/usr/bin/strip --strip-needed /tools/bin/*
```

These commands will skip a number of files, reporting that it does not recognize their file format. Most of these scripts are instead of binaries. Also use the system command to include the strip binary in /tools.

Take care not to use --strip-needed on the libraries. The static ones would be destroyed and the toolchain packages would need to be built all over again.

To save more, remove the documentation:

```
rm -rf /tools/share/{info,man,doc}
```

Remove unused files:
at this point, you should have at least 3 GB of free space in $LFS that can be used to build and install Glibc and Gcc in the next phase. If you can build and install Glibc, you can build and install the rest too.

```
find /tools/(lib,libc) -name *.la -delete
```

## 5.36. Changing Ownership

> Note
The commands in the remainder of this book must be performed while logged in as user root and no longer as user fs. Also, double check that $LFS is set in root's environment.

Currently, the $LFS/tools directory is owned by the user lfs, a user that exists only on the host system. If the $LFS tools directory is kept as is, the files are owned by a user ID with a corresponding account. This is dangerous because a user account created later could give this same user ID and own the $LFS/tools directory and all the therein, exposing these to malicious manipulation.

To avoid this, you add the lfs user to the new LFS system later when creating the /etc/passwd file, try to assign it the same user and group IDs on the host system. Better yet, change the ownership of the $LFS/tools directory to root by running the following command:

```
chown -R root:root $LFS/tools
```

Although the $LFS/tools directory can be deleted once the LFS system has been finished, it can be retained to build additional LFS systems of the same book version. How best to backup $LFS/tools is a matter of personal preference.

> Caution
If you intend to keep the temporary for use in building future LFS systems, now is the time to back them up. Subsequent commands in chapter 6 will alter the tools currently in place, rendering them useless for future builds.

## Chapter 6. Installing Basic System Software

## 6.1. Introduction

In this chapter we are building the base site and starting the LFS system in earnest. That is, we root into the temporary Linux system, make a few preparations, and then begin installing the packages.

The installation of this software is straightforward. Although in many cases the installation instructions could be made shorter and more generic, we have opted to provide the full instructions for every package to minimize the possibilities for mistakes. The key to learning what a Linux system work is to know what each package is for and why you (or the system) may need it.

We do not recommend using optimizations. They can make a program run faster, but may also cause compilation difficulties and problems when running the program. If a package refuses to compile using optimization, to compile it without optimization and see if that fixes the problem. Even if the package does compile using optimization, there is the risk it may have been compiled incorrectly because of the complex interactions between the code and build tools. Also note that the -march and -mtune options are often outweighed by the risks. First-time builders of LFS the book have not been tested. This may cause problems with the toolchain packages (Binutils, GCC and Glibc). The small gains achieved in using compiler optimizations are outweighed by the risks. First-time builders of LFS are encouraged to build without custom optimizations. The subsequent system will still run fast and be stable at the same time.

The order that packages are installed in this chapter needs to be strictly followed to ensure no program acquires a path referring to /tools hard-wired into it. For the same reason, do not compile separate packages in parallel. Compiling in parallel may seem stable (especially on dual-CPU machines), but could result in a program containing a hard-wired path to /tools, which will cause the program to stop working when directory is removed.

Before the installation, each installation page provides information about the package, including a concise description of what it contains, approximately how long it will take to build, and how much disk space is required during this building process. Following the installation instructions, there is a list of packages and libraries (along with brief descriptions of these) the package installs.

> Note The SBU values and required disk space includes test data for all applicable packages in Chapter 6.

### 6.1.1. About libraries

In general, the LFS editors consider many libraries made obsolete in a modern Linux system. In addition linking a static library to a program can be detrimental. If an update to the library is needed to remove a security problem, all programs that use the static library will need to be linked to the new library. The use of static libraries is not always obvious, the relevant programs (and the procedures to do so) may not even be known.

In the procedures in Chapter 6, we remove or disable installation of most static libraries. This usually is by passing a --disable-static option to configure. In other cases, alternate means are needed. In a few cases, especially glibc and gcc, the use of static libraries remains essential to the general package building process.

For a more complete discussion of libraries, see discuss Libraries: Static or shared? in the BLFS book.

## 6.2. Preparing Kernel File Systems

Various file systems exported by the kernel are used to communicate to and from the kernel. These file systems are virtual in that disk space is used. The content of the file systems resides in memory.

By creating directories onto which the file systems will be mounted:

```
mkdir -pv $LFS/{dev,proc,sys,run}
```

### 6.2.1. Creating Initial Device Nodes

When the kernel boots, it requires the presence of a few device nodes, in particular the console and null devices. The device nodes must be created on the hard disk so they are available before udev has started, and additionally when Linux is started with init=/bin/bash. Create the devices by running the following commands:

```
mknod -m 600 $LFS/dev/console
mknod -m 666 $LFS/dev/null
```

### 6.2.2. Mounting /dev

The recommended method of populating /dev with devices is to mount a filesystem (such as tmpfs) on the /dev directory, and allows the devices to be created dynamically on that filesystem as they are detected. Device creation is generally during the boot process by Udev. Since this new system does not have Udev and has not been booted, it is necessary to mount and populate /dev manually. This is accomplished by binding mount the system's /dev directory. A bind mount is a type of mount that allows you to create a mirror of a device directory or mount point to some other location. Use the following command to achieve this:

```
mount -v --bind $LFS/dev
```

### 6.2.3. Mounting Virtual Kernel File Systems

Now mount the remaining kernel filesystems:

```
mount -vt devpts devpts $LFS/dev/pts -o gid=5,mode=620
mount -vt proc proc $LFS/proc
mount -vt sysfs sysfs $LFS/sys
mount -vt tmpfs tmpfs $LFS/run
```

The meaning of the mount options for devpts:

```
gid=5
```

This ensures that all devpts-created device nodes are owned by group ID 5. This is the ID we will use later on the tty group. We use the group instead of a name, since the host system might use a different ID for its tty group.

```
mode=620
```

This ensures that all devpts-created device nodes have mode 0620 (user readable and, group writable). Together with the option, this ensures that devpts will create device nodes that meet the requirements of grantpt(), meaning the Glibc pt_chown helper binary (which is not installed by default) is not necessary.
