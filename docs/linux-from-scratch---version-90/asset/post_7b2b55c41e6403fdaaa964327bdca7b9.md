
Finally the system has to be made bootable by Section 8.4, “Using GRUB to Set Up the Boot Process”.

## 6.4. Entering the Chroot Environment

It is time to enter the chroot environment to begin building and installing the final LFS system. As root user, run the following command to enter the realm that is, at the moment, populated with only the temporary tools:

```
chroot "$LFS" /tools/bin/env -i \
HOME=/root \\
TERM=$TERM \\
PS1=$(lfs chroot) \u:w\$ ' \\
PATH=/usr/bin:/sbin:/usr/sbin:/tools/bin \\
tools/bin/bash -login h
```

The -i option to the env command will clear all variables of the chroot environment. After that, the HOME, TERM, and PATH variables are set. The TERM=$TERM construct will set the TERM variable inside chroot to the same value as outside. This is needed for programs like vim and less to operate properly. If other variables are needed, such as CFLAGS or CXXFLAGS, this is a good place to set them again.

From this point on, there is no need to use the LFS variable anymore, because all work will be restricted to the LFS file system. This is because the Bash is told that $LFS is now the root (/) directory.

Notice that /tools/bin comes last in the PATH. This means that a temporary tool will no longer be used once its final version is installed. This occurs when the shell does “remember” the locations of executed binaries—for this reason, hashing is switched off by passing the +h option to bash.

Note that the bash prompt will say I have no name! This is normal because the /etc/passwd file has not been created yet.

> It is important that all the commands throughout the remainder of this chapter and the following chapters are run from within the chroot environment. If you leave this environment for any reason (rebooting for example), ensure that the virtual kernel filesystems are mounted as explained in Section 6.2.2, “Mounting and Populating /dev” and Section 6.2.3, “Mounting Virtual Kernel File Systems” and enter chroot again before continuing with the installation.

## 6.5. Creating Directories

It is time to create some structure in the LFS file system. Create a standard directory tree by issuing the following commands:

```
mkdir -pv /{bin,boot,etc/{opt,sysconfig},home,lib/firmware,mnt,opt}
mkdir -pv /media/{floppy,cdrom},sbin,srv,var/opt
install -dv -m 0750 /root
install -dv -m 1777 /tmp /var/tmp
mkdir -pv /usr/{,local}/{bin,include,lib,sbin,src}
mkdir -pv /usr/{,local}/share/{color,dict,doc,info,man}
mkdir -v /usr/{,local}/share/{misc,terminfo,zoneinfo}
mkdir -v /usr/libxec
mkdir -pv /usr/{,local}/share/man/{1..8}
mkdir -v /usr/lib/pkgconfig
```

```
case $(uname) - in
x86_64) mkdir -v /lib64 ;;
esac
```

```
mkdir -v /var/{log,mail,spool}
ln -sv /run /var/run
ln -sv /run/lock /var/lock
mkdir -pv /var/{opt,cache,lib/{color,misc,locate}}
```

Directories are, by default, created with permission mode 755, but this is not desirable for all directories. In the commands above, two changes are made—one to the home directory of user root, and another to the directories for temporary files.

The first mode change ensures that not just any can enter the /root directory—the same as a normal user would do with her home directory. The second mode change makes sure any user can write to the /tmp and /var/tmp directories, but cannot remove another user's files from them. The latter is prohibited by the so-called "sticky bit," the highest bit (1) in the 1777 bit.

### 6.5.1. FHS Compliance Note

The directory tree is based on the Filesystem Hierarchy Standard (FHS) (available at https://refspecs.linuxfoundation.org/fhs.shtml). The FHS also specifies the optional existence of some directories such as /usr/local/games and /usr/share/games. We create only the directories that are needed. However, feel free to create these directories.

## 6.6. Creating Essential Files and Symlinks

Some programs use hard-wired paths to programs which do not exist. In order to satisfy these programs, create a number of symbolic links which will be replaced by real files throughout the course of this chapter after the software has been installed:

```
ln -sv /tools/bin/{bash, cat, chmod, dd, echo, ln, mkdir, pwd, rm, stty} /bin
ln -sv /tools/bin/env, install, perl, printf /usr/bin
ln -sv /tools/lib/libgcc_s.so,.1} /usr/lib
ln -sv /tools/lib/libstdc++.{a,.6} /usr/lib

ln -sv bash /bin/sh
```

The purpose of each link:

- /bin/bash
Many bash scripts specify /bin/bash.
- /bin/cat
This pathname is hard-coded into Glibc configure.
- /bin/dd
The path to dd will be hard-coded into /usr/libtool utility.
- /bin/echo
This is to satisfy one of tests in Glibc's test suite, which expects /bin/echo.
- /bin/env
This pathname is hard-coded into some packages.
- /bin/install
The path to install will be hard-coded into /usr/lib/bash/Makefile.inc.
- /bin/ln
The path to ln will be hard-coded into /usr/lib/perl/5.30.0/<target-triplet>/Config_heavy.pl.
- /bin/pwd
Some configure scripts, particularly Glibc's, have this pathname hard-coded.
- /bin/rm
The path to rm will be hard-coded into /usr/lib/perl/5.30.0/<target-triplet>/Config_heavy.pl.
- /bin/tty
This pathname is hard-coded in Expect, therefore it is needed for Binutils and GCC suites to pass.
- /bin/perl
Many Perl scripts hard-code this path to perl program.
- /usr/lib/libgcc_s.so,.1
Glibc needs this for threads to work.
- /usr/lib/libstdc++.{a,.6}
This is needed by several tests in Glibc's test suite, as well as C++ support in GMP.
- /bin/sh
Many shell scripts hard-code /bin/sh.

Historically, Linux maintains a list of the mounted systems in the file /etc/mtab. Modern kernels maintain this list internally and exposes it to the user via the /proc filesystem. To satisfy utilities that expect the presence of /etc/mtab, create the symbolic:

```
ln -sv /proc/self/mount /etc/mtab
```

In order for root to be able to login and for the name “root” to be recognized, there must be the relevant entries in /etc/passwd and /etc/group files.

Create the /etc/passwd << "EOF" by running the following command:

```
cat > /etc/passwd << "EOF"
```

## Linux From Scratch - Version 9.0

The created groups are not part of any standard—they are decided on in part by the requirements of the Udev configuration in this chapter, and in part by convention employed by a number of existing distributions. In addition, some tests rely on specific users or groups. The Linux Standard Base (LSB), available at http://linuxbase.org/ recommends only that, besides the group root with a Group ID (GID) of 0, a group bin with GID 1 is present. All other group names and GIDs are chosen freely by the system administrator since well-written programs do not depend on GID numbers, but rather use the group's name.

To remove the "I have no name!" prompt, start a new shell. Since fact Glibc was installed in Chapter 5 and the /etc/passwd and /etc/group files have been created, user name and group name resolution will now work:

```
exec /tools/bin/bash --login +h
```

Note the use of the +h directive. This bash not to use its internal path hashing. Without this directive, bash would remember the path to binaries it executed. To ensure the use of the newly compiled binaries as soon as they are installed, the +h directive will be used for the duration of this chapter.

The login, agetty, and init programs (and others) use a number of log files to record information such as who was logged into the system and when. However, these programs will not write to the log files if they do not already exist. Initialize the log files and give them proper permissions:

```
touch /var/log/(btmp, lastlog, faillog, wtmp)
chgrp -v utmp /var/log/lastlog
chmod -v 664 /var/log/lastlog
chmod -v 600 /var/log/btmp
```

The /var/log/wtmp file records all logins and logouts. The /var/log/lastlog file records when each user logged in. The /var/log/faillog file records failed login attempts. The /var/log/btmp file records the bad login attempts.

> Note
The /run/utmp file records the users that are currently logged in. This file is created dynamically in the boot scripts.
