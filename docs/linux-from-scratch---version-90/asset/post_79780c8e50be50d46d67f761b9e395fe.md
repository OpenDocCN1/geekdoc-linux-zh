> Note For many modern systems with multiple processors (or cores) the compilation time for a package can be reduced by performing a "parallel make" by either setting an environment variable or telling the make program how many processors are available. For instance, a Core2Duo can support two simultaneous processes with:
```bash
export MAKEFLAGS='j 2'
```
or just building with:
```bash
make -j2
```
When multiple processors are used in this way, the SBU units in the book will vary even more than they normally would. In some cases, the make will simply fail. Analyzing the output of the build process will also be more difficult because the lines of different processes be interleaved. If you run into a problem with a build step, revert back to a single processor builder to properly analyze the error messages.

## 4.6. About the Test Suites

Most packages provide a test suite. Running the test suite for a newly built package is a good idea because it can provide a "sanity check" indicating that everything compiled correctly. A test suite that passes its sets of checks usually proves that the package is functioning as the developer intends. It does not, guarantee, that the package is totally bug free.

Some test are more important than others. For example, the test suites for the core toolchain packages—GCC, Binutils, and Glibc—are of the utmost importance due to their central role a properly functioning system. The test suites for GCC and Glibc can take a long time to complete, especially on slower hardware, but are are strongly recommended.

> Note Experience has shown that there is little to be gained from running the test suites in Chapter 5. There can be no escaping the fact that the host system always exerts some influence on the tests in that, often causing inexplicable failures. Because the tools built in Chapter 5 are temporary and eventually discarded, we do not recommend running the test in Chapter 5 for the average reader. The instructions for running those test suites are provided for the benefit of testers and developers, but they are strictly optional.

A common issue with running the test suites for Binutils and GCC is out of pseudo terminals (PTYs). This can result in a high number of failing tests. This may happen for several reasons, but the most likely cause is that the host system does not have devpts file system set up correctly. This issue is discussed in greater detail at http://www.linuxfrom.org/faq.html#no-ptys.

Sometimes package test suites will fail, but for reasons which the developers are aware of and have deemed non-critical.
Consult the logs located at http://www.linuxfromscratch.org/lfs/build-logs/9.0/ to verify whether or not these failures are expected. This site is valid for all tests throughout this book.

## Chapter 5. Constructing a Temporary System

### 5.1. Introduction

This chapter shows how to build a minimal Linux system. This system will contain just enough tools to start constructing the final LFS system in Chapter 6 and allow a working environment with more user convenience than a minimum environment.

There are two steps in building this minimal system. The first step is to build a new and host-independent toolchain (compiler, assembler, libraries, and a few useful utilities). The second step uses this toolchain to build the other essential tools.

The files compiled in this chapter will be installed under the $LFS/tools directory to keep them separate from the files installed in the next chapter and the host production directories. Since the packages compiled here are temporary, we do not want to pollute the soon-to-LFS system.

### 5.2. Toolchain Technical Notes

This section explains all the rationale and technical details behind the overall build method. It is not essential to immediately understand everything in this section. Most of this information will be clearer after performing an actual build. This section can be referred to at any time during the process.

The overall goal of Chapter 5 is to produce a temporary area that contains a known-good set of tools that can be isolated from the host system. By using chroot, the commands in the remaining chapters will be contained within that environment, ensuring a clean, trouble-free build of the LFS system. The build process has been designed to minimize the risks for new readers and to provide the most educational value at the same time.

> Note
Before continuing, be aware of the nature of the working platform, often referred to as the target triplet. A simple way to determine the name of the target triplet is to run the config.guess script that comes with the source for many packages. Unpack the Binutils sources and run the script: ./config.guess and note the output. For a 32-bit Intel processor the output will be i686-linux-gnu. On a 64-bit system it will be x86_64-linux-gnu.
Also be aware of the name of the platform's dynamic loader, often referred to as the dynamic loader (not to be confused with the standard linker that is part of Binutils). The dynamic loader provided by glibc loads the libraries needed by a program, prepares the program to run, and then runs. The name of the dynamic linker for a 32-bit machine will be ld-linux.so.2 (ld-linux-x86_64.so.2 for 64-bit systems). A sure-fire way to determine the name of the dynamic linker is to inspect a random binary from the host system by reading: read -l <name of binary> | grep interpreter and noting the output. The authoritative reference covering all platforms is the shlib-versions file in the root of the Glibc store

Some key technical points of how the Chapter 5 build method works:

- Slightly adjusting the name of the working platform, by changing the "vendor" field triplet way of the LFS_TGT variable, ensures that the build of Binutils and GCC produces a compatible cross-linker and crosscompiler. Instead of producing binaries for any other architecture, the cross-linker and cross-compiler will produce binaries compatible with the current hardware.

The temporary libraries are cross-compiled. Because a cross-compiler by its nature cannot rely on anything from its system, this method removes potential contamination of the target system by lessening the chance of headers or libraries from the host being incorporated into the new tools. Cross-comp also allows for the possibility of building both 32-bit and 64-bit libraries on 64-bit capable hardware.

Binutils is installed first because the configure runs of both GCC and Glibc perform various feature tests on the assembler and linker to determine which software features to enable or disable. This is more important than one might first realize. An incorrectly configured GCC or Glibc can result in a subtly broken toolchain, where the impact of such breakage might not show up until the end of the build of an entire distribution. A test suite will easily highlight this error after much additional work is performed.

Bin installs assembler and linker in locations /tools/bin and /tools/$LS_TGT/. The tools in one location are linked to the other. An important facet of the linker is its search order. Detailed information can be obtained from ld by passing the --verbose flag. For example, ld --verbose | grep SEARCH will illustrate the search paths and their order. It shows which files are linked by ld by compiling a dummy program and passing the --verbose switch to the linker. For example, gcc dummy -Wl,--verbose | grep succeeded will show all the files successfully opened during the linking.

The next package is installed. An example of what can be seen during its run of configure is:

```
checking assembler to use... /tools/i686-lfs-linux-gnu/bin/as
checking linker to use... /tools/i686-lfs-linux-gnu/bin/ld
```

This is for reasons mentioned above. It also demonstrates that GCC's configure script does not search the PATH directories to use. However, using the order of gcc itself, the same search paths are not necessarily used. To find which standard gcc will use, run: gcc --print-program-name=ld

Detailed information can be obtained from gcc by passing the -v option while compiling a dummy program. For example, gcc -v dummy gcc will show detailed information about the preprocessor, compilation and assembly stages, including gcc's included paths and their order.

Next installed Linux API headers. The standard C library (glibc) to interface with features that the kernel will provide.

Next package installed is Glibc. The most important considerations for building Glibc are the compiler, binary, and kernel headers. The compiler is not general one since Glibc will always use the compiler relating to the --host parameter passed to its configure script; e.g. in our case, the compiler is 1686-lfs-linux-gnu. The binary and kernel headers can be much complicated. Therefore, there are no risks and use the available configure switches to enforce the correct selections. After a run of configure, check the contents of the configure.make file in the glibc-build directory for all details. Note the use of CC="1686-lfs-linux-gcc" to control which binaries are used and of the --nostdinc and -isystem flags to control the compiler's search path. This highlights an important aspect of the Glibc package—it is very self-sufficient in terms of its build machinery and generally does not rely on defaults.

During the second phase of Binutils, we are able to utilize the --lib-path configure switch to control ld's library search path.

For the second pass of GCC, its sources also need to be modified to fetch GCC to use the new dynamic linker. To do so will result in the programs themselves having the name of the dynamic linker from the host system's /lib embedded into them, which would defeat the goal of getting away from the host. From this point onwards, the toolchain is self-contained and self-hosted. The remainder of the Chapter 5 packages all build against the new Glibc in /tools.
