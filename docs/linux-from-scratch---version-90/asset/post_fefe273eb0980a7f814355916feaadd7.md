# 6.3. Package Management

Some reasons why package management is mentioned in LFS or BLFS:

- Dealing with package management takes the focus away from the goals of these books—teaching how a Linux system is built.
- There are multiple solutions for package management, each having its strengths and drawbacks. One that satisfies all is difficult.

There are some hints written on the topic of package management. Visit the Hints Project and see if one of them fits your need.

## 6.3.1. Upgrade Issues

- If Glibc needs to be upgraded to a newer version (e.g. from glibc-2.19 to glibc-2.20), it is safer to rebuild LFS. You may have to rebuild all the packages in their dependency order, or we do not recommend it.
- If a package containing a shared library is updated, and if one of the library changes, then all the packages dynamically linked to the library need to be recompiled against the new library. (Note that there is no correlation between the package name and the name of the library). For example, a package foo installs a shared library with name libfoo.so.1. Say you upgrade the package to a newer version foo-1.2.4 that installs a shared library with name libfoo.so.2. In this case, all packages that are dynamically linked to libfoo.so.1 need to be recompiled to link against libfoo.so.2. Note that you should not remove the previous libraries unless the dependent packages are recompiled.

## 6.3.2. Package Management Techniques

The following are some common package management techniques. Before making a decision on a package manager, do some research on the various techniques, particularly the drawbacks of the particular scheme.

### 6.3.2.1. It is All in My Head

Yes, this is a package management technique. Some folks do not find the need for a package manager because they know the packages intimately and know what files are installed by each package. Some users also do not need any package management because they plan on rebuilding the entire system when a package is changed.

### 6.3.2. Install in Separate Directories

This is a simplistic management framework that does not need any extra package to manage the installations. Each package is installed in a separate directory. For example, package-libfoo-1 is installed in /usr/pkg/foofoo-1 and a symlink is made from /usr/pkg/libfoo to /usr/pkg/libfoo-1. When installing a new version of libfoo-1.2, it is installed in /usr/pkg/libfoo-1.2 and the previous symlink is replaced by a symlink to the new version.

Environment variables such as PATH, LD_LIBRARY_PATH, MANPATH, INFOPATH and CPPFLAGS need to be expanded using /usr/pkg/foo. For more than a few packages, this scheme becomes unmanageable.

### 6.3.3. Symlink Style Package Management

This is a variation of the previous package management technique. Each package is installed alongside the previous scheme. Instead of making the symlink, each file is symlinked into the /usr hierarchy. This removes the need to expand the environment variables. Though the symlinks can be created by the user to automate the creation, many package managers have been using this approach. A few of the popular ones include Stow, Epkg, Graft, and Depot.

The installation needs to be fake, so that the package that it is installed in /usr in reality it is installed in the /usr/pkg hierarchy. Installing in this manner is not a trivial task. For example, consider that you are installing a package libfoo-1.1. The following instructions may not install the package properly:

```
./configure --prefix=/usr/pkg/libfoo/1.1
make
make install
```

The installation will work, but the dependent packages may not link to libfoo as you expect. If you compile a package that you may notice it is linked to /usr/pkg/libfoo-1.1/lib/libfoo.so.1 instead of /usr/lib/libfoo.so.1 as you would expect. The correct approach is to use the DESTDIR strategy to fake installation of the package. This approach works as follows:

```
./configure --prefix=/usr
make
DESTDIR=/usr/pkg/libfoo/1.1 make
```

Most packages support this approach, but there are some who do not. For the non-compliant packages, you may either need to manually install the package, or you may find that it is easier to install some problematic packages into /opt.

### 6.3.4. Timestamp Based

In this technique, a file is timestamped before the installation of the package. After the installation, a simple use of the find with the appropriate options can generate a log of all the files installed after the timestamp file was created. A package manager with this approach is install-log.

Though this scheme has the advantage of being simple, it has two drawbacks. If, during installation, the files are installed with any timestamp other than the current time, files will not be tracked by the package manager. Also, this scheme can only be used when one package is installed at a time. The logs are not reliable if two packages are being installed on two different consoles.

### 6.3.5. Tracing Installation Scripts

In this approach, the commands that the installation scripts perform are recorded. There are two techniques that one can use:

The LD_PRELOAD environment variable can be set to point to a library prepared before installation, this library tracks the packages that are being installed by attaching itself to various executables as cp, mv and tracking the system calls that modify the filesystem. For this approach, all the executables need to be dynamically linked without the suid or gid bit. Preloading the library may cause unwanted side-effects during installation. It is advised that one performs some tests to ensure that the package manager does not break anything and loses all the appropriate files.

The second technique is to strace, which holds all system calls during the execution of the installation scripts.

### 6.3.2.6. Creating Package Archives

In this scheme, the package installation is faked into a separate tree as described in the Symlink style package management. After an installation, a package archive is created using the installed files. This archive is used to install the package either on the local machine or even be used to install the package on other machines.

This approach is used by most of the package managers found in commercial distributions. Examples of package managers who follow this approach are RPM (which, incidentally, is required by the Linux Base Specification), pkg-utils, Debian's and Gentoo's Portage system. A hint describing how to adopt this style of package management for LFS is located at http://www.linuxfromscratch.org/hints/downloads/files/fakeroot.txt.

Creation of packages that include dependency information is complex and beyond the scope of LFS.

Slackware uses a tar based system for package archives. This system purposely does not handle package dependencies as more complex package managers do. For details of Slack package management, see http://www.slackbook.org/html/package-management.

### 6.3.2.7. Deploying LFS on Multiple Systems

This scheme, unique to LFS, is devised by Mathias Benmann, and is available from the LFS Project. In this scheme, each package is installed as a separate user under the standard locations. Files belonging to a package are easily identified by the user ID. The features and shortcomings of this approach are complex to describe in this section. For the details please see the hint at http://www.linuxfromscratch.org/hints/downloads/files/more_control_and_pkg_man.txt.

One of the advantages of LFS is that there are no files that depend on the position of files on a disk system. Cloning an LFS build to another computer with the same architecture as the base system is as simple as tar on the LFS partition that contains the root directory (250MB uncompressed for a base LFS build), copying that network transfer or CD-ROM to the new system and expanding it. From point, a few configuration files will have to be changed. Configuration files that may need to be updated include: /etc/hosts,/etc/fstab,/etc/passwd,/etc/group, /etc/shadow,/etc/ld.so.conf,/etc/sysconfig/rc_site,/etc/sysconfig/network, and /etc/sysconfig/ifconfig.eth0.

A custom kernel needs to be built for the new system depending on differences in hardware and the kernel configuration.

> Note: There have been some reports of issues when copying between similar but not identical architectures. For instance, the instruction for an Intel system is not identical with an AMD processor and later versions of some processors may have instructions that are unavailable in earlier versions.
