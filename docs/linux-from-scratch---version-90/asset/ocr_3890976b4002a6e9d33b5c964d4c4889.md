# 6.3.2. Creating Package Archives

In this scheme, the package installation is faked into a separate tree as described in the Symlink style package management. After an installation, a package archive is created using the installed files. This archive is used to install the package either on the local machine or even be used to install the package on other machines.

This approach is used by most of the package managers found in the commercial distributions. Examples of package managers who follow this approach are RPM (which, incidentally, is required by the Linux Standard Base Specification), pkg-utils, Debian's and Gentoo's Portage system. A hint describing how to adopt this style of package management for LFS systems is located at http://www.linuxfromscratch.org/hints/downloads/files/fakeroot.txt.

Creation of packages that include dependency information is complex and beyond the scope of LFS.

Slackware uses a tar based system for package archives. This system purposely does not handle package dependencies as more complex package managers do. For details of Slack package management, see http://www.slackbook.org/html/package-management.html.

# 6.3.2.7. Deploying LFS on Multiple Systems

This scheme, unique to LFS, is devised by Mathias Benmann, and is available from the LFS Project. In this scheme, each package is installed as a separate user under the standard locations. Files belonging to a package are easily identified by the user ID. The features and shortcomings of this approach are complex to describe in this section. For the details please see the hint at http://www.linuxfromscratch.org/hints/downloads/files/more_control_and_pkg_man.txt.

One of the advantages of LFS is that there are no files that depend on the position of files on a disk system. Cloning an LFS build to another computer with the same architecture as the base system is as simple as tar on the LFS partition that contains the root directory (250MB uncompressed for a base LFS build), copying that network transfer or CD-ROM to the new system and expanding it. From point, a few configuration files will have to be changed. Configuration files that may need to be updated include: /etc/hosts,/etc/fstab,/etc/passwd,/etc/group, /etc/shadow, /etc/ld.so.conf, /etc/sysconfig/rc_site, /etc/sysconfig/network, and /etc/sysconfig/ifconfig.eth0.

A custom kernel needs to be built for the new system depending on differences in hardware and the kernel configuration.

> Note: There have been some reports of issues when copying between similar but not identical architectures. For instance, the instruction for an Intel system is not identical with an AMD processor and later versions of some processors may have instructions that are unavailable in earlier versions.
