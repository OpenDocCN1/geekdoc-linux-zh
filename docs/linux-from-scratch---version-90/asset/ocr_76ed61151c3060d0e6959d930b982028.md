# 7.6.2.1. Changing Run Levels

Changing run-levels is done with init <runlevel>, where <runlevel> is the target run-level. For example, to reboot the computer, a user could use the init 6 command, which is an alias for the reboot command. Likewise, init 0 is an alias for the halt command.

There are a number of directories under /etc/rc.d that look like rc?. (where ? is the number of the run-level) and rcsinit.d, all containing a number of symbolic links. Some begin with a K, the others begin with an S and all of them have two numbers following the initial letter. The K means to stop (kill) a service and the S means to start a service. The numbers determine the order in which the scripts run, from 00 to 99—the lower the earlier it gets. When init switches to another run-level, the appropriate services are either started or stopped, depending on the runlevel chosen.

The real scripts are in /etc/rc.d/init.d. They do the actual work, and links all point to them. K and S links point to the same script in /etc/rc.d/init.d. This is because the scripts can be called with different parameters like start, stop, restart, reload, and status. When a K is linked, the appropriate script is run with the start argument. When an S is encountered, the appropriate script is run with the start argument.

There is one exception to this explanation. Links that start with an S in the rc0 to rc6 directories will not cause anything to be started. They will be called with the parameter stop to something. The logic behind this is when a user is going to reboot or halt the system, something needs to be stopped. The system only needs to be stopped.

These are descriptions of what the arguments make the scripts:

+   start
The service is started.
stop
The service is stopped.
restart
The service is stopped and then started again.
reload
The configuration of the service is updated. This is used after the configuration file of a service was modified, when the service does not need to be restarted.
status
tells if the service is running and with which PIDs.

Feel free to modify the way your boot process works (after all, it is your own LFS system). The files given here are example of how it can be done.

# 7.6.3. Udev Bootscripts

The /etc/rc.d/init.d/udev initscript triggers any "coldplug" devices that have already been created by the kernel and waits for rules to complete. The script also notices the uevent handler from the default of /sbin/hotplug . This is because the kernel no longer needs to call out to an external binary. udev will listen on a network socket for events that the kernel raises.

The /etc/rc.d/init.d/udev_retry initscript triggers cases of re-triggering events for subsystems whose rules rely on filesystems that are not mounted the mounts script is run (in particular, /usr and /var may cause this). This script runs all those rules (if re-triggered) should succeed the second time. It is configured from the /etc/sysconfig/udev_retry file; any rules in this file that other comments are considered subsystem names to trigger retry time. To find the system of a device, udevadm info --attribute-walk <device> where <device> is an absolute path in /dev or sys as /dev/sr0 or /sys/class/rtc.
