# 7.3. Overview of Device and Module Handling

In Chapter 6, we installed the Udev package via eudev built. Before we go into the details regarding how this works, a brief history of previous methods of handling devices is in order.

Linux systems in general traditionally used a static device creation method, whereby a great many device nodes were created under /dev (sometimes thousands of nodes), regardless of the corresponding hardware devices actually existed. This was typically done via a MAKEDEV script, which contains a number of calls to the knod program with the relevant major and minor device numbers for every possible device that might exist in the world.

Using the Udev, only those devices which are detected by the kernel get device nodes created for them. Because these device nodes will be created each time the system boots, they will be stored on a dev.mps file system (a virtual file system that resides entirely in memory). Device nodes do not require much space, so the memory that used is negligible.

# 7.3.1. History

In February 2000, a new filesystem called devfs was merged into the 2.3.4 kernel and was made available during the 2.4 series of stable kernels. Although it was present in the kernel source itself, this method of creating devices dynamically never received overwhelming support from the core kernel developers.

The main problem with the approach adopted by devfs was the way it handled device detection, connection, and naming. The latter issue, that of device node naming, was perhaps the most critical. It is generally accepted that if device names are allowed to be configurable, then the device naming policy should be up to a system administrator, not imposed by any particular developer(s). The devfs filesystem also suffered from race conditions that were inherent in its design and could not be fixed without a substantial revision to the kernel. It was deprecated for a long period – due to a lack of maintenance – and was finally removed from the kernel in June,2006.

With the development of the unstable 2.5 kernel tree, later released as the 2.6 series of stable kernels, a new filesystem called sysfs came to be. The job of sysfs is to export the view of the system's hardware configuration to userspace processes. With this userspace-visible representation, the possibility of developing a userspace replacement for devfs became much more realistic.
