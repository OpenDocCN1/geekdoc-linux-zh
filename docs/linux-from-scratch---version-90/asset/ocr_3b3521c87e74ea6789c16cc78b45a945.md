The temporary libraries are cross-compiled. Because a cross-compiler by its nature cannot rely on anything from its system, this method removes potential contamination of the target system by lessening the chance of headers or libraries from the host being incorporated into the new tools. Cross-comp also allows for the possibility of building both 32-bit and 64-bit libraries on 64-bit capable hardware.

Binutils is installed first because the configure runs of both GCC and Glibc perform various feature tests on the assembler and linker to determine which software features to enable or disable. This is more important than one might first realize. An incorrectly configured GCC or Glibc can result in a subtly broken toolchain, where the impact of such breakage might not show up until the end of the build of an entire distribution. A test suite will easily highlight this error after much additional work is performed.

Bin installs assembler and linker in locations /tools/bin and /tools/$LS_TGT/. The tools in one location are linked to the other. An important facet of the linker is its search order. Detailed information can be obtained from ld by passing the --verbose flag. For example, ld --verbose | grep SEARCH will illustrate the search paths and their order. It shows which files are linked by ld by compiling a dummy program and passing the --verbose switch to the linker. For example, gcc dummy -Wl,--verbose | grep succeeded will show all the files successfully opened during the linking.

The next package is installed. An example of what can be seen during its run of configure is:

```
checking assembler to use... /tools/i686-lfs-linux-gnu/bin/as
checking linker to use... /tools/i686-lfs-linux-gnu/bin/ld
```

This is for reasons mentioned above. It also demonstrates that GCC's configure script does not search the PATH directories to use. However, using the order of gcc itself, the same search paths are not necessarily used. To find which standard gcc will use, run: gcc --print-program-name=ld

Detailed information can be obtained from gcc by passing the -v command line option while compiling a dummy program. For example, gcc -v dummy gcc will show detailed information about the preprocessor, compilation, and assembly stages, including gcc's included search paths and their order.

Next installed sanitized Linux API headers. The standard C library (glibc) to interface with features that the kernel will provide.

The next package installed is Glibc. The most important considerations for building Glibc are the compiler, binary, and kernel headers. The compiler is not general one since Glibc will always use the compiler relating to the --host parameter passed to its configure script; e.g. in our case, the compiler is 1686-lfs-linux-gnu. The binary and kernel headers can be much complicated. Therefore, there are no risks and use the available configure switches to enforce the correct selections. After a run of configure, check the contents of the configure.make file in the glibc-build directory for all details. Note the use of CC="1686-lfs-linux-gcc" to control which binaries are used and of the --nostdinc and -isystem flags to control the compiler's search path. This highlights an important aspect of the Glibc package—it is very self-sufficient in terms of its build machinery and generally does not rely on defaults.

During the second phase of Binutils, we are able to utilize the --lib-path configure switch to control ld's library search path.

For the second pass of GCC, its sources also need to be modified to fetch GCC to use the new dynamic linker. To do so will result in the programs themselves having the name of the dynamic linker from the host system's /lib embedded into them, which would defeat the goal of getting away from the host. From this point onwards, the toolchain is self-contained and self-hosted. The remainder of the Chapter 5 packages all build against the new Glibc in /tools.
