
# Caution

If the system has a separate /boot partition, the files copied below should go there. The easiest way to do that is to bind /boot on the host (outside chord) to /mnt/lfs/boot before proceeding. The root user in the host system:

```
mount --bind /boot /mnt/lfs/boot
```

The path to the kernel image may vary depending on the partition being used. The filename below can be changed to suit your taste, but the stem of the kernel file should be vmlinuz with the automatic setup of the boot process described in the next section. The following command assumes an x86 architecture:

```
cp -iv arch/x86/boot/bzImage /boot/vmlinuz-5.2.8-lfs-9.0
```

System.map is a symbol file for the kernel. It maps the entry points of every function in the kernel API, as well as the addresses of the kernel data structures for the running kernel. It is a resource when investigating kernel problems. Issue the following command to install the map file:

```
cp -iv System.map /boot/System.map-5.2.8
```

The configuration file .config produced by the make menuconfig step above contains all the configuration selections for the kernel that was just compiled. It is a good idea to keep this file for future reference:

```
cp -iv .config /boot/config-5.2.8
```

Install the documentation for the Linux kernel:

```
install -d /usr/share/doc/linux-5.2.8
cp -r Documentation/* /usr/share/doc/linux-5.2.8
```

It is important to note that the files in the kernel source directory are not owned by root. Whenever a package is unpacked as root user (which we did inside root), the files have the user and group IDs of whatever they were on the packer's computer. This is not a problem for any other package to be installed unless the source tree is removed after the installation. However, the Linux source tree is often retained for a long time. Because of this, there is a chance that whatever user ID the package used will be assigned to somebody on the machine. That person would then have access to the kernel source.

# Warning

The headers in the system's `include` directory (`/usr/include`) should *always* be the ones against Glibc was compiled with, the sanitised headers in Section 6.7, "Linux-5.2.8 API Headers". Therefore, they should *never* be replaced by either the kernel headers or any other kernel sanitized headers.

## 8.3.2. Configuring Linux Module Load Order

Most of time Linux modules are loaded automatically, but sometimes it needs some specific direction. The program that loads modules `modprobe` or `insmod`, uses `/etc/modprobe.d/usb.conf` for this purpose. This file needs to be created so that the USB drivers load in order; `ehci_hcd`, `ohci_hcd` and `uhci_hcd` have been built as modules, they will be loaded in the correct order; `ehci_hcd` needs to be loaded prior to `ohci_hcd` and `uhci_hcd` in order to avoid a warning appearing at boot.

Create a new file `/etc/modprobe.d/usb.conf` by running the following:

```
install -v -m755 -d /etc/modprobe.d
cat > /etc/modprobe.d/usb.conf << "EOF"
# Begin /etc/modprobe.d/usb.conf

install ohci_hcd /sbin/modprobe ehci_hcd; /sbin/modprobe ohci_hcd; true
install uhci_hcd /sbin/modprobe ehci_hcd; /sbin/modprobe -i uhci_hcd; true

# End /etc/modprobe.d/usb.conf
EOF
```

## 8.4. Setting Up the Boot Process

### 8.4.1. Introduction

Using GRUB incorrectly can render your system inoperable without an alternate boot device such as CD-ROM. This section is not required to boot off your LFS system. You may just want to modify your current boot loader, e.g. Grub-Legacy, GRUB2, or LILO.

Ensure an emergency boot disk is ready to "rescue" if the computer becomes unbootable. If you do not have a boot device, you can create one. In order for the procedure below to work, you need to jump ahead to LFS and install xorriso from the package.

```
cd /tmp
grub-mkrescue --output=grub-img.iso
xorriso -as cdrecord -v dev=/dev/cdrom blank=as grub-img.iso
```

To LFS systems that have UEFI enabled, the kernel needs to have been built with the CONFIG_EFI_STUB capability described in the previous section. However, LFS can be booted using GRUB without it. With this addition, the UEFI Mode and Secure Boot capabilities in the system's BIOS need to be found. For details, see lfs-uefi.txt at http://www.linuxfromscratch.org/downloads/lfs-uefi.txt

## 8.4.2. GRUB Naming Conventions

GRUB uses its own naming structure for devices and partitions in the form of (hdn,m) where n is the hard drive number and m is the partition number. The hard drive starts from zero, but the partition number starts from one for normal partitions and five for extended partitions. This is different from earlier versions where numbers started from zero. For example, partition sda1 is (hd0,1) and sdb2 is (hd1,2). In contrast, GRUB does not consider CD-ROM drives to be hard drives. For example, if using a CD on hdb and a second hard drive on hdc, that second hard drive would be (hd1).

## 8.4.3. Setting Up the Configuration

GRUB works by writing to the first track of the hard disk. This area is not part of any file system. The programs access GRUB modules in the boot partition. The default location is /boot/grub/.

The location of the boot partition is a choice that affects the configuration. One recommendation is to use a separate small (suggested size is 100 MB) partition for boot. By that way each LFS or commercial distro can access the same boot files and be made from any booted system. If you choose to do this, you will need to mount the separate partition, move all files in the current /boot directory (e.g the linux kernel you have built in the previous section) to the new partition. You will then need to unmount the partition and remount it as /boot.

Using the lfs partition will also work, but configuration for multiple systems is more difficult.

Using the above information, determine the appropriate designator for the root partition (or boot partition, if a separate one is used). For the example, it is assumed that the root (or separate boot) partition is sda2.

Install the GRUB files into /boot/grub and set up the boot track:

# Warning

The following command will overwrite the current boot loader. Do not run the command if this is not desired, for example, if you use a third party boot manager to manage the Master Boot Record (MBR).

```
grub-install /dev/sda
```

# Note

If the system has been booted UEFI, grub-install will try to install files for the x86_64 target, but those files have not been installed in chapter 6. If this is the case, add --target i386-pc to the command.

## 8.4.4. Creating the GRUB Configuration File

Generate /boot/grub/grub.cfg:

```
cat > /boot/grub/grub.cfg << "EOF"
# Begin /boot/grub/grub.cfg
set default=0
set timeout=5
ins ext2
set root=(hd0,2)
menuentry "GNU/Linux, Linux 5.2.8-lfs-9.0" {
    linux /boot/vmlinuz-5.2.8-1fs-9.0 root=/dev/sda2 ro
}
EOF
```

# Note

From GRUB’s perspective, the kernel files are relative to the partition used. If you used a separate /boot partition, remove /boot from the above linux line. You will also need to change the set root line to point to the boot partition.

GRUB is an extremely powerful tool and provides a tremendous number of options for booting with a variety of devices, operating systems, and partition types. There are also many options for customization such as graphical splash, playing sounds, mouse input, etc. The details of these options are beyond the scope of this introduction.

# Caution

There is a command, grub-mkconfig, that will write a configuration file automatically. It uses a set of scripts in /etc/grub.d/ and will destroy any customizations that you make. These scripts are designed primarily for non-source distributions and are not recommended for LFS. If you install a custom Linux distribution, there is a good chance that program will run. Be sure to back up your grub.cfg file.
