# 7.3.3.2. A kernel module is not loaded automatically, and Udev is not intended to load it

If the “wrapper” only enhances the functionality provided by some other module (e.g., snd-pcm oss enhances the functionality of snd-pcm by making the sound cards available to OS applications), configure modprobe to load the wrapper after Udev loads the wrapped module. To do this, add a “softdep” to the corresponding /etc/modprobe/<filename>.conf file. For example:

```
softdep snd-pcm post: snd-pcm-oss
```

Note that the “softdep” command also allows pre: dependencies, or a mixture of both pre and post:. See the modprobe.d (5) manual page for more information on “softdep” syntax and capabilities.

If the module in question is not a wrapper and is useful by itself, configure the modules bootscript on your system. To do this, add the module to the /etc/sysconfig/modules file on a separate line. This works for modules too, but is suboptimal in that case.

# 7.3.3.3. Udev loads some unwanted module

Either do not build the module, or blacklist it in a /etc/modprobe.d/blacklist.conf file as done with the forte module in the example below:

```
blacklist forte
```

Blacklisted modules can still be loaded manually with the explicit modprobe command.

# 7.3.3.4. Udev creates a device incorrectly, or makes a wrong symlink

This usually happens if a rule unexpectedly matches a device. For example, a poorly-written rule can match both a SCSI device (as desired) and the corresponding SCSI generic device (incorrectly) by vendor. Finding the rule and making it more specific, with the help of the udevadm info.

# 7.3.3.5. Udev creates rules unnecessarily

This may be another manifestation of the previous problem. If not, and your rule uses sysfs attributes, it may be the kernel timing, to be fixed in later kernels. For now, you can work around it by creating a rule that waits for the used sysfs attributes and appending it to the /etc/udev/rules.d/10-wait_for_sysfs.rules file (create this file if it does not exist). Please notify the LDS Development list if you do so and it.

# 7.3.3.6. Udev does not create a device

Further text shows that the device is built statically into the kernel or loaded as a module, and that you have already checked that Udev doesn't create a misnamed device.

Udev has no information to create a device if a kernel driver does not export its attributes to sysfs. This is most common with third party drivers from outside the kernel. Create a static device node in /lib/udev/devices with the appropriate major/minor numbers (see file devices.txt inside the kernel documentation or the documentation provided by the third party driver vendor). The static device node will be copied to /dev by udev.

# 7.3.3.7. Device naming changes randomly after rebooting

This is due to the fact that Udev, by design, handles events and loads modules in parallel, and thus in an unpredictable order. This will never be “fixed”. You should not rely the kernel device name being stable. Instead, create your own rules that make symlinks with stable names based on stable attributes of the device, such as a serial number or the output of variety *id attributes installed by Udev. See Section 7.4, “Managing Devices” and Section 7.5, “General Network Configuration” for examples.
