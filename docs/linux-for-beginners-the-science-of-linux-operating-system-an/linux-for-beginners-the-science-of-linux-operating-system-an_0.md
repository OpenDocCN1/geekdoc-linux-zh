## Linux 文件系统结构

### 文件：类型

Linux 文件系统的基础包括文件，文件无非是操作系统用于将信息存储在物理设备（如硬盘、软磁盘、CD-ROM 或 DVD）上的结构。自然地，文件可以包含你所喜的任何类型信息，从`PNG`或`JPEG`格式的图像到`HTML`格式的文本或网页。文件系统是允许 Linux 处理其包含的文件的结构。

所有 Linux 文件都有一个名称，该名称必须符合某些规则：

- 文件名长度介于 1 到 255 个字符之间
- 你可以使用除斜杠`/`之外的任何字符但不建议使用 Linux 中具有特殊意义的字符，如下：`= \ ^ ~ ' " \` *; -? [] ( )! & ~ <>`
- 要使用带有这些字符或空格的文件，必须在引号内输入文件名。
- 如果需要，也可以使用数字。
- 大写字母和小写字母被视为不同的，因此`letter.txt`不同于`Letter.txt`或`letter.Txt`。

与 Windows 类似，可以使用特定的“类型”标准来标记不同种类的文件，使用名称末尾的一系列字符指示文件的类型。因此，文本文件、`HTML`、`PNG`或`JPEG`图像分别具有扩展名`.txt`、`.htm`（或`.html`）、`.png`和`.jpg`（或`.jpeg`）。

尽管如此，Linux 仅区分三种类型的文件：

- 普通文件是指上述的文件
- 目录（或文件夹）是以结构化方式分组其他文件的特殊文件
- 特殊文件是 Linux 运行的基础，因为它们代表了连接到计算机的设备，如打印机。这样一来，在该文件中输入信息等同于向打印机发送信息。对于用户来说，这些设备与普通文件具有相同的外观和用法。

### 链接

链接是一种普通文件类型，为确定文件创建一个新名称。一旦创建了符号链接，它允许以相同的方式访问所链接的文件，就好像我们将其内容复制到另一个文件一样，但优点是它并没有真正被复制。当你想要一组人协作同一个文件时，符号链接特别有用，因为它们允许共享文件但集中进行修改。

作为一个示例，你可以假设存在一个名为`balance.1999.txt`的文件，并为其创建一个符号链接`balance.txt`。对`balance.txt`的任何访问都会被系统翻译，以便你访问`balance.1999.txt`。

### 路径

在任何现代操作系统中，文件结构都是层次化的并依赖于目录。通常情况下，文件系统结构类似于树形结构，每个节点由一个目录或文件夹组成，它包含其他目录或文件。在 Windows 中，每个磁盘驱动器被识别为一个基本文件夹并作为其他文件夹的根。在 Linux 上，有一个名为`/`的根目录，所有文件和目录都挂载其下，这与连接到计算机的设备无关。

文件或目录的路径是访问某个文件时必须遍历的目录序列，并用`/`分隔。路径有两种形式：

- 绝对路径，显示文件的完整路径，`/home/luis/Carta.txt`
- 相对于某个目录的相对路径，例如，如果我们找不到`/home`目录，相对于文件`Letter.txt`的相对路径就是`Luis/Letter.txt`。

为了使问题更加复杂，所有目录都包含两个特殊目录：当前目录由点`.`表示，父目录由冒号`..`表示。在`/home`目录中，你可以通过`/home/luis/Carta.txt`（绝对路径）或`/luis/Carta.txt`（相对路径）访问`Carta.txt`。在`Luis`目录中，可以使用`./Carta.txt`或直接使用`Letter.txt`。

Linux 文件系统遵循所有的 UNIX 规范，这意味着它具有一个确定的、与其他 UNIX 系统兼容且同质的结构。与 Windows 或 MS-DOS 不同，任何 Unix 系统上的文件系统并不直接链接到硬件结构，也就是说，它不取决于给定的计算机拥有 1、2 还是 7 块硬盘来创建`c:\`、`d:\`或`m:\`驱动器。

每个 UNIX 文件系统都有一个唯一的根或根源，用`/`表示。在此目录下，你将找到操作系统可以访问的所有文件。这些文件组织在不同的目录中，它们的使命和名称在所有 Unix 系统中都是标准的。

- `/`: 文件系统的根
- `/dev`: 包含代表物理安装在计算机上的设备的系统文件
- `/etc`: 此目录留用于系统配置文件。在此目录中，不应出现二进制文件（程序）。在此下，应该还有两个子目录：
    - `/etc/X11`: X Window 配置文件
    - `/etc/skel`: 在创建新用户时复制到该用户目录的基本配置文件
- `/lib`: 包含运行位于`/bin`中的程序所需的库（不是用户程序的库）
- `/proc`: 包含向系统内核发送信息或从系统内核接收信息的特殊文件（建议不要修改此目录及其文件的内容）
- `/sbin`: 包含只有超级用户或 root 可以访问的程序
- `/usr`: 这是系统最重要的目录之一，因为它包含了所有用户通用的使用程序。其结构通常如下：
    - `/usr/X11R6`: 包含运行 X Window 的程序
    - `/usr/bin`: 通用程序，包括`C` / `C++`编译器
    - `/usr/doc`: 通用系统文档
    - `/usr/etc`: 通用配置文件
    - `/usr/include`: `C` / `C++`头文件 (`.h`)
    - `/usr/info`: GNU 信息文件
    - `/usr/lib`: 程序的通用库
    - `/usr/man`: 可通过`man`命令访问的手册
    - `/usr/sbin`: 系统管理程序
    - `/usr/src`: 程序的源代码

除了上述目录，还有其他位于`/usr`目录下的目录，例如安装在系统中程序的文件夹。

- `/var`: 此目录包含关于程序的临时信息（这并不意味着你可以删除其内容，事实上不应该这样做）

## 第 1 章：操作系统基础概念

### 操作系统的概念、目的与功能

#### 操作系统的概念

我们现代操作系统的主要思想和起点是需要创建并将纳入计算机系统中使用（我们所说的计算机控制系统是指一套硬件和软件的集合）。计算机控制系统最初是为了解决用户的责任归属和实际问题而开发的。由于仅靠硬件很难实现这一点，因此创建了应用程序。这些程序需要硬件管理的通用操作、硬件资源的分配等。这些操作被归类在一个独立的软件层中，这被称为操作系统。

此外，操作系统的能力远远超过了应用程序所需的各种操作集合，但此类系统在应用程序和硬件之间的中间位置保持不变。

#### 操作系统的目的

操作系统为我们提供了一套控制系统，其次是其工作的效率和可靠性。第一个功能是操作系统作为扩展机器的特征，第二个是操作系统作为硬件资源的分配器。

#### 作为扩展机器的操作系统

使用操作系统时，应用程序程序员（通过他的程序和用户）应该感觉他们正在与一台先进的机器工作。硬件并不非常适合直接在应用程序中使用。例如，如果你考虑在相应控制器的命令级上与`I / O`设备工作，你会发现此类命令的集合是有限的，而且对于许多设备来说是原始的。操作系统隐藏了这种硬件接口，转而为程序员提供了一个使用高层概念（称为抽象）的应用程序编程接口。

例如，当处理磁盘工作时，一个典型的抽象是文件。处理文件比直接处理磁盘控制器要容易得多（不需要考虑移动驱动器头、启动和停止电机等），结果是程序员可以专注于其应用程序的本质。操作系统负责与磁盘控制器交互。抽象的强调使得 OS 代码和应用程序代码在迁移到新硬件时能够易于更改。例如，如果你在计算机上安装了新类型的磁盘设备（只要操作系统支持它），它的所有特性都将在操作系统层面得到考虑，而应用程序将继续像以前一样使用文件。系统的这种特性被称为硬件无关性。可以说操作系统为执行应用程序提供了一个硬件无关的环境。

#### 作为资源分配器的操作系统

操作系统必须高效地分配资源。它充当这些资源的管理者并根据需要向应用程序提供。资源分配有两种主要类型。在空间分配的情况下，资源访问将同时针对多个客户，他们每一个都可以使用资源（共享内存）。在时间分配的情况下，系统进行队列并允许它们在有限时间内使用整个资源。在分配资源时，OS 解决可能的冲突，防止程序未经授权访问这些资源，确保计算机的高效运行。

#### 现代操作系统的分类

根据其范围，对现代操作系统进行如下分类：

- **大型机（`mainframes`）**: 它们的设计主要特征是执行`I / O`：提供大量的外设（磁盘、打印机等）。此类计算机控制系统用于可靠地处理大量数据。操作系统应该有效地支持这一过程（批处理模式或时间分配）。此类类的示例是`IBM/390`。
- **服务器系统**: 下一类包括服务器操作系统。此类操作系统的主要特征是处理大量的用户请求。网络支持对它们起着重要作用。通用服务器（`UNIX`或`Windows`）现在常用于实现服务器。
- **个人操作系统**: 最大的类别之一是个人操作系统。在这一类中，一些操作系统（`Windows 95/98/Me`）是通用操作系统的简化版本。个人 OS 特别关注的是支持用户界面和多媒体技术。
- **实时操作系统**: 还有实时操作系统。在这样的系统中，必须保证操作在指定时间内完成。实时操作系统可以控制进程的运行。实时操作示例有`QNX`和`VxWorks`。
- **嵌入式操作系统**: 另一类是嵌入式操作系统。这些是用于微处理器、智能卡和其他设备的系统。此类系统提出了特殊要求：少量内存和对特定设备的支持。通用系统包括`Linux`和`Windows CE`。

#### 操作系统的功能组件

操作系统可以被视为一组组件，每个组件负责系统的特定功能。现代操作系统的最重要特征是实现它们的组件以及它们的关系取决于操作系统的架构。每个操作系统根据其可以处理的工作类型来将它们组织在一起。

#### 进程与流管理

正如我们提到的，操作系统最重要的功能之一是执行应用程序。代码和应用程序数据以特殊方式存储在计算机控制系统的磁盘上。文件系统创建执行进程的基本单元。操作系统在进程之间分配资源。这些资源包括 CPU 时间、内存、设备、磁盘空间。处理器之间的分配是必要的，因为在特定的时刻进程可以执行。为了实现这种效果，OS 为每个进程提供短暂的时间，随后将其切换到另一个进程；进程从中断的地方恢复执行。在多处理器系统中，进程可以在不同的处理器上并行运行。现代操作系统除了进程外还可以支持多任务，提供了多个指令（线程），它们像大多数进程一样并行运行。与进程不同，线程不提供资源保护（例如，它们共享进程的地址空间）。

#### 内存管理

执行代码时，处理器从计算机（主）内存获取指令和数据。这种内存显示为字节数组，每个字节都有一个地址。如所述，主内存是进程之间的一种资源。OS 负责内存分配。地址空间在进程期间受到保护，并在执行完成后释放。进程的可用内存可以在内存分配过程中变化。操作系统必须能够处理可用内存总量。为此，必须实现虚拟内存技术。这项技术允许在主内存中放置当前所需的指令和进程，而地址空间其余的内容存储在磁盘上。

#### I/O 管理

操作系统负责管理连接到内存的 I/O 设备。OS 对此类设备的支持通常在两个级别执行。低层包括设备驱动程序——控制特定类型设备并考虑其所有特性的软件模块。第二层包括一个方便在应用程序使用的通用 I/O 接口。OS 应该实现一个通 I/O 驱动接口，通过该接口与其他系统组件交互。此接口为新设备添加驱动程序变得简单。现代操作系统为特定外设提供了大量现成的驱动程序。OS 支持的设备越多，其实际使用的机会就越大。

#### 文件管理与文件系统

对于 OS 用户和程序员来说，磁盘空间作为一组组织成文件系统的文件提供。文件是文件系统上一组可以通过名称访问的文件。“文件系统”一词可以用于两个概念：以文件形式组织数据的一种原则，以及根据该原则组织的特定数据集（通常是磁盘的相应部分）。作为操作系统的一部分，它可以同时实现支持和接口化多个文件系统。文件系统在逻辑和物理层面都被考虑。

### 网络支持

#### 网络系统

现代操作系统适应了在网络上工作，它们被称为网络操作系统。网络支持使 OS 能够：

- 通过网络公开提供本地资源（磁盘空间、打印机等），即作为服务器运行。
- 通过网络引用其他计算机资源，作为客户端运行。

实现服务器和客户端的功能基于网络协议进行数据传输。

#### 分布式系统

网络操作系统不隐藏网络的存在。网络支持在它们中决定了系统结构并增强了其额外能力。分布式 OS 允许多台计算机并行工作池资源。分布式系统是使用多个处理器的 OS 两大类别。

#### 结论

现代操作系统的趋势之一是，在特权模式下内核的一小部分功能（微内核）被实现。其他 OS 功能由用户模式进程（服务器）执行。服务器负责文件系统。内核在系统组件之间通信并执行基本资源分配。为了执行系统调用，应用程序（客户端）访问内核。内核拦截它，将处理器切换到特权模式，执行操作，将处理器切换回用户模式并将结果返回应用程序。内核将其转发给客户端。客户可以是单个用户或其他单元。

微内核方法的优点是：

- 内核尺寸小，便于开发和调试
- 系统可靠性高，因为服务器在用户模式运行无法直接访问硬件
- 系统具有更大的灵活性和扩展性（不必要的组件不占用内存，系统功能的扩展减少到添加新的服务器）
- 适应网络条件的可能性（服务器和相关网络或在同一台计算机之间交换数据）

微内核方法的主要缺点是性能下降。在系统调用的情况下，处理器模式发生了切换（两次——在客户端和内核之间，两次——在服务器和微内核之间）。系统调用比用户实现的功能慢，因为处理器切换了两次。对于某些 OS，某些功能在用户模式下实现，因此不需要使用系统调用访问它。

## 第 2 章：操作系统架构

操作系统可以被视为一组组件，每个组件负责某些功能。此类组件的集合以及它们与外部环境交互的顺序由操作系统的架构决定。考虑架构的基本概念方法，以`Linux`为例考虑的实现。

### 系统架构的基本概念

#### 系统内核——特权模式与用户模式

负责 OS 最重要功能的基本组件通常位于内存中并在特权模式下执行，被称为操作系统的内核。当前的设计方法定义了内核的功能。OS 最重要的功能包括中断处理、内存控制、输出控制。内核的核心特征是它在特权模式下运行。为了确保高效的资源管理，操作系统对于应用程序拥有某些特权。它们必须支持两种模式——特权模式（内核模式）和用户模式（用户模式）。在内核和应用程序交互时使用不同的 CPU 模式。当需要执行内核实现的操作时，应用程序发出系统调用。内核拦截它，将处理器切换到特权模式，执行操作，将处理器切换回用户模式并将结果返回应用程序。系统调用比用户实现的功能慢，因为处理器切换了两次。对于某些 OS，某些功能在用户模式下实现，因此不需要使用系统调用访问它。

#### 操作系统架构的实现

考虑实现操作系统架构的几种方法。在实际 OS 中，它们通常使用这些方法的组合。

#### 单内核系统

所有基本功能集中在内核中的操作系统被称为单内核系统。在单内核实现中，OS 变得更高效（组件之间交互时处理器不切换模式），但可靠性较低（所有代码都在特权模式下执行，每个组件的错误都是致命的）。单内核并不意味着其所有组件都必须留在内存中。现代操作系统允许在内核空间中放置代码片段。内核模块的实现使得扩展成为可能（添加新功能只需在内存中加载相应的模块）。

#### 多级系统

组件形成层级结构（层），每一层都依赖前一层的功能。最底层直接与硬件交互，最高层实现系统调用。在传统的多级操作系统中，从顶到底部的控制传递实现为系统调用。顶层必须具有执行该调用的权利，这些权利通过硬件的支持进行验证。这种系统的示例是 60 年代开发的`Multics`操作系统。由于性能不佳，这种方法的实际应用今天受到了限制。层也可以在单内核中隔离；在这种情况下，它们通过程序支持并导致系统实现中断。在单内核系统中，内核决定了层级：

- 抽象意味着直接与硬件交互，释放系统其他组件免受这种交互
- 核心内核负责最基本、最简单的内核操作，例如将数据块写入磁盘。通过这些手段，带有资源管理的执行上层指令
- 资源管理工具（或资源管理器）实现基本 OS 功能（进程管理、内存、输入输出等）。在这一层，做出了最重要的资源管理决策，这些决策是由内核做出的。

该系统包含三个主要部分：进程管理子系统、文件系统和 I/O 子系统。

进程管理子系统控制进程的创建和删除、进程间的系统资源分配、进程间交互以及内存管理。文件子系统提供了一个单一接口，用于访问存储在磁盘驱动器和外设上的数据。这种接口是`UNIX`最重要的特性之一。它们使用相同的系统调用来与磁盘通信，或者输出到终端或打印机（程序处理打印机就像处理文件一样）。在这种情况下，文件系统将请求转发给 I/O 子系统的相关模块，而这些由这些模块——直接发送到外设设备。此外，文件子系统还控制文件访问权限，这在很大程度上决定了用户在系统上的权限。



I/O 子系统通过与设备驱动交互来执行文件系统请求。在`UNIX`中，设备分为两类：字符设备（例如打印机）和块设备（例如硬盘）。它们之间的主要区别在于块设备允许直接访问。为了通过缓冲区缓存提高块设备的效率——缓冲区缓存是一块存储最近从磁盘扫描的数据的内存区域。对这些数据的后续访问可以从缓存中检索。

## Linux 架构

Linux 有三个主要部分：

*   `Core`（内核）：实现操作系统的基本功能（进程管理、输入输出、内存等）。
*   `System libraries`（系统库）：为应用程序定义了一组标准函数（执行这些函数不需要切换到特权模式）。
*   `System utilities`（系统工具）：执行特定任务的应用程序。

### Linux 内核及其特性

`Linux` 实现了单内核技术。所有的内核数据和数据结构都位于同一个地址空间中。内核中有几个功能性组件：

*   `Process Scheduler`（进程调度器）：负责系统多任务能力的实现（中断处理、定时器操作、进程的创建和完成、上下文切换）。
*   `Memory Manager`（内存管理器）：为每个进程分配独立的地址空间并实现对虚拟内存的支持。
*   `Virtual File System`（虚拟文件系统）：提供与各种文件系统和 I/O 设备交互的通用接口。
*   `Device Drivers`（设备驱动程序）：提供对外设备的直接访问。通过虚拟文件系统接口进行访问。
*   `Network Interface`（网络接口）：提供对网络协议实现和网络设备驱动程序的访问。
*   `Interoperability Subsystem`（互操作子系统）：提供允许系统中不同进程相互通信的机制。

这些子系统的某些是系统的逻辑组件；它们与内核一起加载到内存并永久留在那里。其他子系统的组件（如设备驱动程序）的实现方式使得代码可以按需上传。为了实现这一点，`Linux` 支持内核模块的概念。

### 内核模块

`Linux kernel` 允许按需加载和卸载单独的代码段。这些段被称为`kernel modules`（内核模块），并在特权模式下运行。内核提供了许多优势：

*   代码模块可以在系统过程中加载到内存中，简化了内核组件（特别是驱动程序）的调试。
*   它们能够在运行时更改一组核心组件：当前未使用的组件不会被加载到内存中。
*   模块是规则的一个例外，即根据`Linux`许可证扩展内核功能的代码必须是开源。这允许硬件制造商为`Linux`开发驱动程序，即使他们无法访问源代码。

`Linux module support`（Linux 模块支持）包含三个部分：

*   `Module management tools`（模块管理工具）：使得将模块加载到内存并在模块与内核其余部分之间通信成为可能。
*   `Driver logging tools`（驱动日志工具）：允许模块向内核的其他部分报告新驱动程序的实现。
*   `Conflict resolution tools`（冲突解决工具）：允许设备驱动程序保留硬件资源并保护它们不被其他驱动程序意外使用。

如果需要，单个模块可以注册多个驱动程序（例如用于两种不同的访问机制）。模块可以提前下载——在系统启动时（`boot modules`）或触发其功能的程序运行时。加载后，模块代码与其他内核代码处于相同的地址空间。模块错误对系统是致命的。

### 系统库的特性

`Linux system libraries`（Linux 系统库）是动态库，只有在需要时才被加载到内存中。它们执行许多功能：

*   实现系统调用封装器。
*   扩展系统调用功能（例如库包括 C 语言 I/O 库，它基于系统调用实现了如`printf()`等函数）。
*   实现用户模式服务函数（排序、行处理等）。

### 用户应用程序

`Linux user applications`（Linux 用户应用程序）使用系统库中的函数，并通过系统调用与内核交互。

### 在 UNIX 和 Linux 中管理进程

#### 进程映像

在 UNIX 系统中，进程映像包含以下组件：

- 进程控制单元
- 进程执行的代码
- 存储临时数据的进程栈（过程参数、返回值、局部变量等）
- 整个进程通用的全局数据

#### 标识信息和进程安全属性

进程标识符 (`PID`) 在整个系统中是唯一的，用于访问该进程。`init`进程的标识符始终为 1。祖先进程的进程 ID (`ppid`) 在其创建时指定。如果进程`P`的祖先完成执行，该进程的祖先会自动变为`init`，因此`P`的`ppid`将变为 1。

进程具有`fl '`相关安全属性集：

- 真实用户和进程组标识符 (`uid`, `gid`) 对应于启动程序的用户，导致相应的进程出现在系统中
- 有效用户和进程组标识符 (`euid`, `egid`) 用于特殊的进程执行模式 - 由所有者拥有

#### 进程控制单元

考虑 Linux 中进程控制单元的结构。Linux 进程控制块通过`task_struct`数据结构显示。该结构中最重要的字段是包含以下信息的字段：

- 标识数据（包括`pid` - 进程标识符）
- 进程状态（执行中、等待中等）
- 指向祖先和后代结构的指针
- 进程创建时间和总执行时间（所谓的进程计时器）
- 处理器状态（寄存器内容和指令计数器）
- 进程安全属性 (`id`, `gid`, `euid`, `egid`)

注意，Linux 内核没有单独流的独立数据结构，因此处理器状态信息包含在进程的控制块中。除了上述内容，`task_struct`具有几个不同 Linux 子系统所需的自定义字段：

- 信号处理信息
- 进程调度信息
- 关于进程的文件和目录 floor ' '
- 管理内存子系统的数据结构

`task_struct`字段`data`可以被几个特殊用途进程共享，在这种情况下，这些进程实际上是线程。进程的控制单元存储在内核的特殊数据结构中。在内核 2.4 发布之前，该结构被称为系统进程表；它是一个数组，最大长度不能超过 4K。在核心进程中，它已被两个没有此类限制的动态数据结构取代：

- 哈希表（进程的`pid`作为哈希值），该结构允许你通过 ID 快速查找进程
- 环形列表（Ring list），该结构确保所有系统进程在循环中执行动作。

现在对最大进程数量的限制仅在`fork()`函数实现内部检查，并取决于可用内存量（例如，有信息表明在 512 MB 内存的系统中可以创建约 32000 个进程）。

Linux 中控制单元的实现与其在 UNIX 系统中的传统实现不同。在大多数 UNIX 版本（System V, BSD）中，进程控制块由两个数据层组成——进程结构 (`proc`) 和用户结构 (`u`)。

### 创建过程

#### Linux 中 fork() 的实现

在 UNIX 兼容系统中，进程创建一个已知的系统调用`fork()`。让我们考虑它在 Linux 中的实现。

1. 为新的进程控制块 (`task_struct`) 分配内存。如果内存不足，返回错误。
2. 将祖先数据结构中的所有值复制到后代数据结构中。之后，将值应与原始值不同的字段进行更改。如果用户超过了为其指定的进程数，或者系统中的进程数超过了最大可能值（取决于可用内存量），则进程创建停止并返回错误。
3. 使用特殊算法为进程生成标识符 (`pid`) 以保证唯一性。
4. 为后代复制必要的祖先数据结构（文件描述符表、当前目录信息、信号处理程序表等）。
5. 构建进程的地址空间。
6. 将进程数据结构放入系统进程的列表和哈希表中。
7. 将进程置于就绪状态。

#### 在应用程序中使用 fork()

考虑一个使用`fork()`系统调用创建进程的示例。POSIX 对`fork()`的描述如下：

```
#include <unistd.h>
pid_t fork();
```

由于执行`fork()`会导致祖先和后代的控制切换到操作符，在调用`fork()`后（两者都开始执行同一条指令），在程序员看来，祖先和后代之间唯一的区别在于代码返回的`fork()`。对于后代，`fork()`返回 0；对于祖先，返回创建的后代进程的 ID (`pid`)。如果由于某种原因没有创建后代，`fork()`将返回 -1。因此，`fork()`的正常代码如下：

```c
pid_t pid;
if ((pid = fork()) == -1){
    /* 错误，崩溃 */
}
if (pid == 0){
    // 是后代
}else{
    // 这是祖先
    printf (" Descendant started with code %d \n", pid);
}
```

一旦进程创建，它就可以通过系统调用`getpid()`获取标识信息，`getpid()`返回当前进程 ID，`getppid()`返回祖先的进程 ID：

```c
#include <unistd.h>
pid_t mypid, parent_pid;
mypid = getpid();
parent_pid = getppid();
```

#### 完成进程

为了结束进程，UNIX 系统使用`_exit()`系统调用。考虑在 Linux 中实现此系统调用。在其执行期间发生了以下动作。

1. 进程状态通过`TASK_ZOMBIE`展现。
2. 进程通知其祖先和后代它已结束（通过特殊信号）。
3. 在`fork()`调用期间分配的资源被释放。
4. 告知调度器可以切换上下文。

你可以使用`_exit()`系统调用或其库函数`exit()`来完成应用程序中的进程。该函数会关闭所有进程线程，正确释放所有资源，并调用`_exit()`实际完成退出。

```c
#include <unistd.h>
void _exit (int status); // status 指定返回码
#include <stdlib.h>
void exit (int status); // status 指定返回码
exit (128);
```

注意，当进程可以与其他进程结合使用资源时，最好不要调用`exit()`（例如，它是一个拥有祖先进程的子进程，且子进程继承了祖先进程的资源描述符）。这是因为在这种情况下，尝试在子进程中释放资源会导致祖先进程中的资源也被释放。你必须使用`_exit()`来完成这些进程。

### 等待进程完成



当进程完成后，其控制块不会立即从进程列表和哈希表中被移除，而是一直留在那里，直到另一个进程（祖先进程）将其移除。如果进程在系统中实际上缺失（它已结束），但只留下了控制单元，则该进程被称为`僵尸进程`（zombie process）。

### `waitpid()` 系统调用

你可以使用`wait()`系统调用从`Linux`中移除进程信息，但更多时候使用的是其更通用的版本——`waitpid()`。此调用检查对应进程的控制单元是否在系统中。如果是，且该进程不在僵尸状态（即它仍在运行），那么在`waitpid()`情况下进程将进入等待状态。当子进程完成后，祖先进程退出等待状态并移除子进程控制单元。如果祖先进程没有对子进程调用`waitpid()`，可能会长时间处于僵尸状态。

## 应用程序中进程的同步实现

让我们基于`waitpid()`实现同步执行。根据`POSIX`，该系统调用定义为：

```c
# Include <sys/wait.h>
pid_t waitpid ( pid_t pid, // 期望进程的 pid
int * status, // 子进程完成状态信息
int options ); // 默认为 0
```

`pid`参数可以设置为`0`，这意味着进程正在等待与祖先同组的进程；或者设置为`-1`，意味着期望任何子进程。以下是一个带有等待的同步执行实现示例：

```c
pid_t pid ;
if ((pid = fork ()) == -1)
    exit (-1);
if (pid == 0){
    // 子进程 - 调用 exec ()
}else{
    // 祖先进程 - 等待后
    int status;
    waitpid (pid, & status, 0); // 继续执行
}
```

`status`值提供了关于已完成子进程的更多信息。`<sys/wait.h>`中有许多宏：

- `WIFEXITED(status)`：当子进程正常完成执行时返回非零值。
- `WEXITSTATUS(status)`：子进程返回码（仅当`WIFEXITED()` != 0 时）。

获取子进程返回码的方法如下：

```c
waitpid (pid, & status, 0);
if (WIFEXITED (status))
    printf (" Descendant ended with code % d \n", WEXITSTATUS (status)) ;
```

## 5/7 信号

在多任务的情况下，需要向进程报告发生在系统或其他进程中的事件。`POSIX`定义的这种警报的最简单机制是`alerts`（信号）。进程在接收到信号后，立即响应其特殊调用函数——信号处理程序（`signal handler`），或者根据每个信号相关的信号编号（该编号在系统中是唯一的）执行默认操作。信号同时无法传输任何其他信息。

定时器是`UNIX`系统上进程间通信最简单的机制，但由于它们允许传输有限的数据，因此它们主要用于事件报告。

### 信号类型

根据情况，信号分为同步信号和异步信号。

- **同步信号**在活动进程流的执行期间发生（通常通过错误：访问错误的内存区域、不正确的浮点运算、执行错误的指令和处理器设计）。这些信号由操作系统内核产生，并立即发送给导致错误的进程线程。
- **异步信号**可以在执行过程的任何时间被进程接收：
  - 程序员可以使用系统调用向另一个进程发送异步信号，这在`POSIX`系统中被称为`kill()`，该调用的参数是信号值和进程标识符。
  - 信号也可能由某些外部事件（击键、终止等）引起。

在处理此类信号期间，系统必须中断当前代码的执行，执行处理器代码并返回到接收信号时正在执行的同一条指令。

### 信号布局

进程接收信号后可以通过以下三种方式之一做出响应（进程响应的方法称为信号警报处置）：

- 调用信号处理程序。
- 忽略信号，在这种情况下信号会“消失”且不采取任何操作。
- 使用默认分配（这是每个信号的默认设置，通常会终止进程）。

### 信号阻塞

进程不仅可以设置信号的位置，还可以决定其在该时刻接收特定类型信号的意愿。如果进程未就绪，它可以阻塞这些信号。如果要传递给进程的信号被锁定，系统将其放入队列，它将留在那里直到进程将其解锁。进程通过更改`进程信号掩码`（process signal mask，一个存储关于哪些信号可以立即传递给进程信息的特殊数据结构，通常存储在其控制块中）来锁定和解锁信号。子进程继承祖先的信号掩码。

### 信号示例

考虑`POSIX`定义并在`Linux`中支持的信号（括号旁给出了信号编号）。同步信号包括例如系统在记录受保护内存区域时产生的`SIGSEGV`（11）信号。

异步信号包括：

- `SIGHUP`（1）：挂断信号（例如，用户退出系统）。
- `SIGINT`和`SIGQUIT`（2,3）：来自键盘的程序中断信号（由用户按下 Ctrl+C 和 Ctrl+\ 产生）。
- `SIGKILL`（9）：立即终止程序（此信号无法更改位置）。
- `SIGUSR 1`、`SIGUSR 2`（10,12）：应用程序可以使用的用户信号。
- `SIGTERM`（15）：建议程序关闭（此信号与`SIGKILL`不同，可以被忽略）。

除`SIGSEGV`外，所有这些信号的默认操作都是终止程序（对于`SIGSEGV`会生成额外的内存转储`core dump`——一个存储进程地址空间镜像的文件，以供后续分析）。

## 设置信号布局

`sigaction()`系统调用用于设置信号处理处置。

```c
#include <signal.h>
int sigaction (int signum, // 信号编号
struct sigaction * action, // 新布局
struct sigaction * old_action); // 返回之前的处理处
```

该功能通过`sigaction`结构体描述，包含以下字段：

- `sa_handler`：信号处理函数的指针。
- `sa_mask`：信号掩码，指定在处理器内部哪些信号将被阻塞。
- `sa_flag`：额外的标志位。

将`sa_mask`和`sa_flag`置零（不阻塞任何信号）：

```c
struct sigaction action = {0};
```

`sa_handler`字段应设置为指向预先声明的函数，该函数格式如下：

```c
void user_handler (int signum){
    // 信号处理
}
```

此功能成为一个信号处理器。`signum`参数决定了向处理程序发送哪个信号（可以通过多次`sigaction()`调用为多个信号注册同一个处理程序）。注册后，当接收到相应的信号时，处理程序始终会被调用：

```c
#include <signal.h>
void sigint_handler (int signum){
    // SIGINT 处理
}
// ……
action.sa_handler = sigint_handler;
sigaction (SIGINT, & action, 0);
```

如果我们需要组织等待信号，最简单的方法是调用系统调用`pause()`。在这种情况下，进程进入待机模式，并在该模式中输出任何信号：

```c
// 请求处理程序协助 sigaction ()
pause (); // 等待信号
```

## 信号生成

让我们考虑如何向进程发送信号。这使用了`kill()`系统调用。

```c
#include <signal.h>
int kill (pid_t pid, // 进程 ID
int signum ); // 信号编号
```

例如，向命令行指定的进程`pid`发送`SIGHUP`信号：

```c
kill ( atoi ( argv [1], SIGHUP );
```

## 进程异步执行的组织

考虑如何使用信号处理来组织进程的异步执行。如你所知，调用`waitpid()`会导致子进程同步执行。而启动后代进程是异步的。在祖先进程中不对该后代调用`waitpid()`似乎是自然的。但后代进程完成后，它将变成一个僵尸进程。

为了避免这种情况，你必须利用祖先进程在后代进程结束时接收一个特殊的`SIGCHLD`信号这一事实。在信号处理器中调用`waitpid()`将从进程表中移除子进程信息，从而在系统中留下僵尸。

```c
void clear_zombie (int signum){
    waitpid (-1, NULL, 0);
}
struct sigaction action = {0};
action.sa_handler = clear_zombie ;
sigaction (SIGCHLD, & action, 0);
if ((pid = fork ()) == - 1)
    exit ();
if ( pid == 0){
    // 后代异步运行
    exit ();
}else{
    // 祖先进程没有 waitpid () 调用
}
```

## Linux 中的线程管理

### 多线程的基础支持

直到最近，`Linux`多线程的唯一支持是`clone()`系统调用，它使得基于现有进程创建新进程成为可能。该调用类似于`fork()`调用，但具有其他几个特性。

- 对于新进程，你需要指定一组特殊的标志位，以决定祖先和后代之间如何分配资源。可以共享的资源包括地址空间、打开的文件信息、信号处理程序。注意，在传统的`clone()`实现中，没有对进程标识符（`pid`）、祖先 ID 以及其他重要属性进行特殊处理。
- 新进程没有设置新栈（作为结果，调用`clone()`的两个进程可能会共享同一个内存区域，这对于通用堆栈来说是不可接受的）。

支持`clone()`意味着实现 1:1 多线程方案。

1. 系统中的主要实体是进程而非线程（在`Linux`中，内核提供的关于在内核上运行的指令被称为进程，而不是内核线程）。`Linux`传统的多线程实现规定将用户线程映射到内核中的进程。因此，单独查看`Linux`中的流数据结构是不切实际的——它与进程使用完全相同的`task_struct`结构进行显示。

## Linux 传统多任务支持的缺点

`Linux`内核中的多线程基础自`clone()`系统调用以来一直没有经历过原则性的变化。在此期间，`Linux`已从一个实验性系统演变为一个行业级系统，实现了企业级的重型应用。这种对系统的使用导致了多线程、高可靠性和可扩展性的实现。显然，`clone()`系统调用的实现无法满足这些需求。我们在 STI 内核中已经拥有完整的多线程处理设施。流控制是标准 POSIX 1996 对应 API 的一部分，名为流 POSIX。

## Linux 内核线程

除了用户进程和线程外，`Linux`还支持一种特殊的计划对象，被称为内核线程。这些流像普通进程和流一样被调度，每个流都有自己的 ID（`pid`）。内核线程与进程及用户线程的区别在于：

- 它们的流函数定义在内核代码中。
- 它们只在内核模式下运行。
- 无法访问在用户模式下分配的内存。

## 流管理软件接口

### 创建线程

要向当前进程添加新线程，`POSIX`使用`pthread_create()`函数，语法如下：

```c
#include <pthread.h>
int pthread_create (pthread_t * th, pthread_attr * attr,
void * (* thread_fun) (void * th, void * arg);
```

考虑此函数的参数：

- `th`是一个指向`pthread_t`类型预定义结构体的指针，该指针随后被传递给其他处理流的工作函数；然后调用 AI 来处理该流（线程句柄）。
- `Attr`是一个指向带有流属性的结构的指针（你需要传递一个空指针来使用默认属性；某些属性稍后会进行检查）。
- `thread_fun`是一个指向流函数的指针，其定义应描述为：

```c
void * mythread_fun (void * value) {
  // 执行流代码
}
```

- `arg`：传递给流函数的数据（在函数内部将获得该参数值）。

创建一个 POSIX 流的示例：

```c
#include <pthread.h>
// 流函数
void * thread_fun (void * num){
    printf (" stream number % d \n", (int) num);
}
// ……………………………
pthread_t th;
// 创建第二个线程
pthread_create (& th, NULL, thread_fun, (void *) ++ thread_num);
```

有两个线程在并行运行。新线程开始与创建它的线程并行运行。例如，如果线程是在`main()`函数内部创建的，那么将有两个线程继续执行：一个执行`main()`代码的原始程序，另一个新程序。

## POSIX 流的完成

要结束线程，只需到达其函数`thread_fun()`的末尾，或从其中调用`pthread_exit()`：

```c
#include <pthread.h>
void pthread_exit (void * retval);
```

`retval`参数指定返回码。这里是一个结束流的示例：

```c
void * thread_fun (void * num ){
    printf ("stream number % d \n", (int) num);
    pthread_exit (0);
}
```

应用程序启动有两种不同的情况：

- 执行返回语句或在`main()`结束时执行所有语句，这将完成包含所有线程的整个进程，此操作不会影响其他线程——它们将继续执行直到完成。
- 在`main()`函数内部执行`pthread_exit()`函数只完成初始线程，调用`pthread_exit()`仅用于等待线程（join）。

## 等待线程完成

要等待线程完成，请使用`pthread_join()`函数。它的语法如下：

```c
int pthread_join (pthread_t thread, void ** status);
```

该函数会阻塞调用它的线程，直到由`thread`指定线程完成其执行任务。如果`status`不是空指针，它将指向流在调用`pthread_exit()`后返回的数据。如果当调用`pthread_join()`时线程已经完成，则应立即读取其信息。

### 结论

- 进程和线程是实现代码执行的计算机系统活动资源。线程被称为一组顺序执行的命令。进程是一个或多个线程的集合，以及它们执行所需的地址空间。同一地址空间内的流可以共同共享数据，而对于不同进程的流，在没有特殊手段的情况下这将是不可能的。在传统系统中，每个进程只能执行一个线程。现代操作系统支持多线程概念。
- 在应用程序中使用线程意味着对其进行并行化——即同时使用不同代码段执行操作的能力。程序并行性反映了外部世界的异步本质，其源头是多个处理器上的代码执行、I/O 操作以及用户交互请求。调度允许应用程序实现这一过程并实现并行性。
- 进程地址空间中运行着用户线程，内核线程与内核工作。它们之间的关系决定了流模型的方案。在实践中，它们通常使用 1:1 方案，每个用户线程对应一个内核线程，内核本身负责管理用户线程。
- 流可能处于不同的状态（执行、就绪等）。从一个状态移动到另一个状态的原理取决于流规划和处理器时间规划。将进程从执行状态移动到任何其他状态涉及切换上下文——在保留处理器状态的同时将控制从一个线程转移到另一个线程。
- 系统中的每个进程和流都对应其控制单元——一个包含所有必要信息的数据结构。在创建过程中（通常通过系统调用`fork()`），会创建一个控制单元，分配内存并启动主流。创建流更快、也更容易，因为它们不需要为新地址分配内存。

# 第 4 章：进程与流规划

并行运行流的能力取决于可用处理器的数量。如果处理器是单的，在原则上是不可能并行执行的（任何时刻只能执行一个线程）。如果处理器数量`N > 1`，则只能为`N`个线程实现并行执行（每个处理器一个线程）。单处理器系统调度的主要目的是在单个处理器上安排多个线程，给系统用户一种它们正在同时运行的印象。如果当线程数量超过可用处理器数量时发生调度任务，此定义可以扩展到多处理器系统。考虑规划的基本类型、其原理和算法。

## 规划的一般原理

考虑规划的基础原理。

### 线程执行的特征

从调度的角度来看，流可以被描述为计算（CPU 使用）和 I/O 期间交替的循环。流仅执行处理器指令的时间间隔被称为 CPU 使用间隔（CPU 突发时间），流等待 I/O 的时间间隔称为 I/O 突发间隔。这些间隔中的大部分在 2 到 8 毫秒之间。

花费更多时间在计算上而在 I/O 上花费较少的流被称为处理器密集型（CPU 密集型）。它们积极使用处理器。它们的主要特征是花在计算上的时间，它们的 CPU 使用间隔较长。

花费大部分时间在等待 I/O 的流被称为输入/输出密集型（I/O 密集型）。此类线程对处理器的负载小得多，它们的处理器使用间隔的平均长度很小。处理器的时钟频率越高，可以归为此类类别的流就越多：处理器限制流（矩阵乘法）、I/O 限制流（I/O 密集型）和 CPU 使用（CPU 密集型）。

## 规划机制与策略

机制和策略应当区分。调度机制包括上下文切换工具、流同步工具等，而调度策略是确定何时切换上下文的工具。负责策略的部分被称为调度器，用于此的算法称为调度算法。规划策略有多种评估标准，其中一些适用于所有系统，另一些仅适用于批处理系统或交互系统。今天，最常用的三个标准来评估目标：

- 最小响应时间：这是交互式系统最重要的标准。响应时间是指运行流（或输入命令）到获得第一个响应之间的时间。对于现代系统，我们取了 50-150 毫秒的时间。
- 最大带宽：这是系统单位时间内可以执行的任务数（例如每秒）。这种标准适用于批处理系统；在交互式系统中，它可以用于后台任务。要增加带宽，你必须：



- 减少浪费的时间（例如切换上下文的时间）。
- 更高效地使用资源（确保处理器和 I/O 设备都不空闲）。
- 公平性：第三个标准意味着根据重要性分配 CPU 时间。公平性提供了这种分布，使得所有线程在执行中不断进展。注意，实现公平策略并不总是减少响应时间。

## 规划原理

流规划原理首先适用于具有 1:1 实现的多线程系统（这里只规划内核流），也适用于具有进程实现的系统。在后者的情况下，可以使用“进程”代替“流”，规划所需的信息可以存储在进程结构中。更复杂的调度原理用于用户线程数量与内核线程数量不匹配的系统（1:M 和 M:N）。它们需要两个调度器：一个内核级，另一个用户级。

## 规划类型

区分长期、中期和短期调度。

### 长期规划

长期规划意味着确定哪些程序应该在附近执行。这种调度被称为静态调度，因为它不取决于系统的当前状态。在批处理系统中，当预先知道需要完成哪些任务时，它起了重要作用。在交互式系统中（例如分时系统），加载进程是不可能的；因此通常使用简化的长期规划策略。系统允许在线程达到某些限制时创建新进程或导致错误。这种策略也基于用户的心理，当系统过载时可以中断工作。

### 中期规划

中期调度控制暂停的流在备用和返回之间的转换。就绪执行的线程组织在队列中。转换到挂起状态由以下因素引起：

- 等待 I/O 操作。
- 等待另一个线程的完成（连接）。
- 因为流需要同步而阻塞。

通常，为了正确的等待，除了就绪队列外，它们实现额外的队列。每个此类队列都与资源相关；这些队列被称为等待队列或阻塞队列。中期调度通过在这些队列和就绪队列之间移动线程来管理。

### 短期规划

短期规划或处理器调度（CPU Scheduling）是最重要的规划类型。它回答两个基本问题：

- 何时中断流？
- 就绪线程中哪一个在这一点应该转移处理器？

短期调度器是操作系统子系统，在活动流需要时中断并从队列中选择要执行的。由于执行频繁，还有一个调度器（Dispatcher）直接控制上下文切换。就绪流的格式取决于短期规划，可以按 FIFO 原则组织。所有的规划策略算法将在下方查看。

## 规划策略——抢占与非抢占式多任务

在考虑基本策略之前，让我们看看从一个线程转移控制到另一个的选项：

- 流进入备用状态（例如，在输入/输出期间）。
- 流完成后。
- 忙碌时显式将处理器交给其他线程。
- 中断（例如，定时器可以中断运行超过允许时间的流）。

取决于控制传输，流规划有两种主要的策略——抢占和非抢占式。在抢占式多任务中，流可能被临时中断并转移控制到另一个流，这在现代操作系统中是常见的，以便执行的。在非抢占式多任务中，控制传输是不实现的，流本身必须将控制交给操作系统或进入备用。如果线程忘记或失败，将会无限循环，其他线程将无法继续。自然地，非抢占式多任务在一般情况下系统非常不稳定（任何编写错误的应用程序都会导致整个系统死机）。

## 算法

调度算法允许从就绪线程中选择下一个执行的。根据执行的策略，算法被分为抢占和非抢占式。

### FIFO 规划

考虑最简单的（“幼稚”）算法，流按照它们在系统中出现的顺序执行，直到进入备用或完成。队列按照 FIFO 原则组织，因此该算法被称为 FIFO 算法。当新流在系统中创建时，其控制单元被添加到队尾。当处理器释放时，从队列头提供流。该算法有许多缺点：

- 定义上是不可逆的。
- 它的平均响应时间可能很大（例如，如果接收到一个长 CPU 使用间隔的流，其他流即使只使用短间隔也会等待）。
- 它受队效应的影响。队效应可以用这种情况解释：假设系统中有一个线程（我们称之为 `T_CPU`）受处理器能力限制，而许多 `T_io` 线程受 I/O 能力限制。早晚 `T_CPU` 线程将获得处理器并执行长时间间隔的指令。在此期间，其他 `T_io` 流将完成 I/O，在队列中等待空闲的 I/O 设备。当 `T_CPU` 最终阻塞并转移所有控制时，`T_io` 快速执行 CPU 范围然后移动 I/O。之后，`T_CPU` 将再次长时间占据处理器，等等。

### 循环规划

最容易理解且最公平的算法是循环规划（轮询调度）。在中世纪，“round-robin”一词源于请愿书上的圆圈签名，以便人们不知道是谁先签名的（这个名字表明对于这种算法所有流都是平等的）。每个流分配的允许运行的时间段被称为时间片（或时间量子）。当线程在时间量子耗尽后仍在运行时，它会被中断，处理器切换到执行另一个线程的指令。当它阻塞或完成执行直到时间量子耗尽时，处理器也被传递给另一个线程。整个系统的时间量子是相同的。这种算法非常容易实现。为此，就绪线程的顺序应该是循环列表。当流耗尽了它的量子时，它被移动到列表末尾，新流被提供。量子耗尽的检查由系统中断处理程序执行。影响算法运行的唯一特征是量子的长度。应该记住切换上下文的时间与响应许多交互式查询之间的平衡。任务量子过短会导致许多上下文切换，并将大量的 CPU 时间花在非有用工作上而在这些切换上。另一方面，过长的量子虽然节省了 CPU 时间，但也降低了交互式查询的响应时间，因为如果用户同时按下按键，线程将在就绪列表中。在无限长度的情况下，循环调度退化为 FIFO 算法（所有线程在阻塞或量子耗尽前执行）。

实践中，建议将量子的长度设置为 10-100 ms。注意，循环调度可能会“偏向”受处理器限制的流，这些流会完全利用它们的量子，直到量子耗尽。

### 优先级规划

循环调度假设所有流同样重要。否则，应使用优先级规划。基本思想是：给每个流一个优先级，最高优先流从就绪线程中执行。优先级可以是静态或动态的。实现方法之一是多队列，在这些情况下，具有不同优先级的多个组被组织。执行线程的决策如下：

- 如果有高优先级流，使用更简单的算法（如循环调度）而忽略其他流。
- 如果没有高优先级流，低优先级流被执行。这种情况会导致低优先级进程等待很长时间。解决饥饿问题有不同的方法：例如，调度器可以通过老化（aging）逐渐降低优先级，当它低于下一个优先级时，相反地增加优先级。

### 基于性能特征的规划

一类重要的优先级调度算法，其中对流的选择决策是基于对性能特征的知识或评估。首先，应该注意，“执行剩余时间”的算法是最短剩余时间优先（SRTF）。与 SRTF 的不同在于，当新线程的执行剩余时间比当前线程更短时，它会抢占处理器。SRTF 在理论上对于平均响应时间来说是最优的。遗憾的是，短期规划是不可能的，因为它无法准确预测流的行为性质。对于长期规划，通常使用调度器。可以使用以下公式来计算：

```text
tn+1 = a*tn + (1-a)*t
```

其中 `0 < a < 1`，`t_{n+1}` 是间隔长度的估计；`tn` 是上一个间隔长度的估计。最常用的值是 `a = 0.5`，这种情况下足够在估计值和实际值之间计算平均值。SRTF 的区别在于，当就绪线程的执行时间结束时，当前线程会被中断，新线程进入其位置。

### 多级反馈队列

带有反馈的多队列（多级反馈队列）调度算法可以减少任何其他算法。在组织结构上，该算法类似于多队列：有多个具有不同优先级的队列，只有当上层队列为空时运行低优先级队列。它们之间的区别是：

- 流允许跨级。
- 流根据优先级和使用间隔长度移动到低优先级队列（通常量子减半）。

不同的队列对应不同的长度——优先级越高，量子越短。如果流耗尽了它的量子，它移动到低优先级队列的末尾（带有量子）。结果是，短间隔流（如 I/O）留在高优先级，而长间隔流自动向下移动。

### 彩票规划

彩票规划（抽票调度）的想法是：

- 流接收大量的彩票，每张票都有权在 T 时间内使用处理器。调度器在 T 时间内随机选择一张彩票。赢得的流获得控制。

彩票规划允许：

- 模拟循环调度，给每个流相同数量的票。
- 根据优先级分配票数。
- 模拟 SRTF——短流比长流票多（如果流至少收到一张票，就不会饥饿）。
- 确保处理时间在线程之间分配——给每个线程与其所需的比例相对应的票数（例如，如果有三个流，需要流 A 占据 50%，B 和 C 各占 25%，可以给流 A 两张票，B 和 C 各一张）。
- 改变优先级，在运行时添加票数。

尽管这些任务大部分可以通过彩票规划解决，但只是近似，实践上相当满意。系统运行越久，结果越接近理论值（根据大数定律）。事实上，彩票规划利用了所有规划很大程度上是启发式的事实，因为无法准确预测系统中流的行为性质。

## Linux 中的规划实现

考虑 Linux 调度的两种方案：传统的（包括 2.4 及之前的内核）和 2.6 内核中引入的新的。Linux 内核在规划时不区分进程和流，因此确定地我们将继续讨论进程规划。系统中的所有进程可以分为三组：实时 FIFO 调度、实时循环调度和普通进程。

### 内核进程的实时调度

对于实时进程，只需说：

- 它们在规划时的优先级总是高于普通进程。
- FIFO 调度进程一直执行，直到它自己放弃处理器（例如由于挂起或终止）或被更高优先级的实时进程取代。
- 循环调度进程也一样，只是它在时间量子耗尽后会被进一步抢占。

### 传统调度算法

考虑一种调度普通进程的算法。算法的核心是将 CPU 时间分配给各个周期（epochs）。在周期内，每个进程都有一个时间量子，其长度在周期开始时计算。大多数情况下，不同进程具有不同长度的量子。当进程耗尽量子时，它会被抢占，在当前周期内不再执行，将管理交给另一个进程。然而，如果进程由于 I/O 或同步原因而暂停，其量子不被视为耗尽，调度器可以在当前周期内将其耗尽。当所有就绪进程都耗尽量子时，周期结束。此时，调度算法重新计算所有进程的量子并开始新周期。量子在周期开始时设置，其值可以通过 `nice()` 和 `setpriority()` 系统调用动态修改。子进程继承祖先的量子。有两种优先级类型：

- 固定优先级：实时进程在进程创建时设置。
- 动态优先级：普通进程取决于量子的剩余时间。描述最重要的字段是：
  - `Policy`：决定进程属于哪一类（普通、实时、FIFO 等）。
  - `Nice`：指定具体的值。
  - `Counter`：包含进程在量子耗尽前剩余的定时器中断次数。

### 调度器调用

```c
if (condVar > someVal) {console.log("xxx")}
```

1. `Stream T A` 读取了 `total _ amount`，其值等于 `100`。
2. `stream T B` 读取数值 `total _ amount`，同样也等于 `100`。
3. `Stream T A` 将第 1 步中的读取值 `total _ amount` 增加了 `1000`，接收到 `1100` 并将其存储在内存中。
4. `T B` 流将第 2 步中的 `total _ amount` 数值增加了 `100`，得到 `200`，并将其存储在全局内存中，覆盖了流 `T A` 保存的内容。

用户 A 的贡献完全丢失了。现在考虑另一种事件发生序列（选项 2）。

1. `Stream T A` 读取 `total _ amount`，将其增加到 `1000` 并在全局内存中记录数值 `1100`。
2. `Stream T` 在读取 `total _ amount`（其值为 `1100`）时，将其增加了 `100` 变为 `1200`，并将该值写入全局内存中。

结果，两项贡献都成功注册了。如你所示，执行上述最简单代码段的结果取决于系统中线程的执行顺序。这导致了以下结果：在一种情况下，代码可以正常工作，而在另一种情况下则不行，而且通常无法预测错误的发生。这种情况被称为 `race`（或 `race condition`，竞态），它是程序员面临的最复杂的 bug 之一。这种问题在实践中是不可避免的（因为要覆盖所有可能的流执行序列组合是不现实的，特别是当组合非常多时）。人们尝试将这些必要的问题绑定到同步流中。需要立即注意的是，并行计算的同步和组织问题是实际编程中最困难的问题之一。因此，多线程程序的开发和调试特别通常被视为一种并非所有程序员都掌握的“艺术”。

事实上，这种开发和调试并不是艺术，而是一门严谨的学科，遵循一个基本原则：因为对于多线程程序，传统的调试并不适用，程序员必须编写代码，使得在开发阶段就留出错误空间。让我们熟悉为了使生成的代码符合这一原则而必须遵循的规则。考虑解决竞态问题的主要方法。

### 竞态问题的方法

有时（但很少见）你可以直接忽略这些错误。当我们不感兴趣特定数据的准确记录，而是收集它们的统计数据时，这样做是有意义的，因为单个错误不会影响整体结果。例如，全局计数器是一个用于计算每天访问系统平均请求数的值，你可以忽略每隔几小时发生一次此类注册错误。遗憾的是，在大多数情况下，这种方法是不被接受的。

有时，使用全局数据并不是由任务的具体决定的。在这种情况下，直接的解决方案是为每个流创建数据的副本并仅对它们进行操作。在实践中，这种方法非常好，并且应该尽可能使用。例如，如果问题的细节允许为每个线程创建一个单独的计数器（或全局计数器数组，其中每个元素只由特定的流更改），那么这种数据结构的实现就能解决问题。同样，这种解决方案不能适用于所有情况（例如，在银行账户的情况下，不同的流最终必须以某种方式修改所有账户的总额）。

在所有其他情况下，必须保护更改免受其他流的影响。这是同步的主要任务。考虑解决它的不同方法。

### 临界区与锁

#### 临界区的概念

考虑使用一个简单的想法来解决竞态问题。很容易看出，我们错误的根源在于，从外部看，最简单的转账操作实际上分解成了几个操作，在这些操作之间存在任何其他流干扰的机会。在这种情况下，该操作被认为不是原子的而是分子的。

由此推导出，竞态问题的解决方案是将导致问题的代码段转换为原子操作，即保证在不受其他线程干扰的情况下完全执行的操作。这段代码被称为 `critical section`（临界区）：

```c
// 临界区开始
total_amount = total_amount + new_amount;
// 临界区结束
```

现在，当两个线程准备同时执行临界区的代码时，先开始的线程将在第二个线程开始执行之前完全执行其所有代码（第二个线程将等待直到第一个线程完成临界区的代码）。结果，我们保证程序中的选项 2 中有一系列事件序列，竞态将永远不会发生。

考虑临界区应该具备的属性：

- **互斥性（Mutual exclusion）**：在特定的代码段内，临界区只能执行一个线程。
- **进展性（Progesterone）**：如果多个线程在临界区的入口处，则必须要求其中一个进入其中（它们不能完全互相阻塞）。
- **有限模式（Limited mode）**：尝试进入临界区的进程，迟早会被要求进入其中。

简单的问题仍然是：“我们如何让系统将多个操作识别为一个原子操作？”解决此类任务的最简单方案是禁止在临界区的持续期间中断。这种方法虽然在原理上解决了问题，但在实践中无法应用，因为整个系统临界区中的循环程序可能会保持锁定中断状态，从而呈现出不利的条件。

#### 锁

更整洁的解决方案是使用 `locks`。锁是一种防止多个线程同时执行临界区代码的机制。使用锁分为两个步：`commit`（`lock`、`acquire_lock()`）和 `unlock`（`lock`、`release_lock()`）。在锁的情况下，会检查它是否已被另一个线程占用，如果是，该线程进入待机状态；否则，它强制锁定并进入临界区。离开临界区后，流移除阻塞。

```c
acquire_lock(lock); // 临界区
release_lock(lock);
```

因此实现了互斥属性，因此阻塞的另一个名称是 `mutex`，`mutual exclusion` 的缩写。

#### 阻塞实现的问题

考虑使用块变量实现临界区的简单方法。与每个临界区关联一个整数变量，该变量在冻结期间假设值为单位，在锻造后为零。该实现的代码如下所示：

```c
int lock = 0;
void aquire_lock (int lock) {
    // 如果 lock 不为空 (lock == 0)，将其锁定 (设置 lock = 1)
    // 并退出 - 我们在临界区
    // 否则等待锁被移除
    while (lock != 0); // (1)
    lock = 1; // (2)
}
void release_lock (int lock) {
    // 移除锁
    lock = 0;
}
```

这种实现的主要问题是，检查锁变量的值并更改它并不是单个原子操作的一部分。

### 流同步的基本机制

现代操作系统提供了大量的现成同步机制。同步机制是操作系统工具，帮助解决同步的主要任务——确保处理共享数据的流之间的协调。如果这些工具是构建多线程程序的最小单元，它们被称为 `synchronization primitives`（同步原语）。

同步原语分为以下主要类别：

- 多功能的、底层的，可以以不同的方式使用（`semaphores`，信号量）。
- 简单的、底层的，每个都适用于特定的解决方案。
- 高级通用的，通过简单的方式表示；此组包含了 `monitor`（监器）的概念，可以通过 `mutexes`（互斥锁）和条件变量来表示。
- 高级，适用于特定同步问题的解决（`阻塞读写` 和 `barriers` 屏障）。

让我们看看不同的机制并评估它们各自的优点以及可能的缺点。为了进一步说明这些材料，让我们取一个展示同步必要性的经典例子——生产者-消费者问题或有限缓冲区问题（`bounded buffer`）。

1. 当生产者或消费者正在操作缓冲区时，其他线程都应该等待其完成。
2. 当生产者试图将一个对象放入缓冲区而缓冲区已满时，它必须等待直到有可用空间。
3. 当消费者试图从缓冲区中取出一个对象而缓冲区为空时，它必须等待直到有对象可用。

## 信号量概念（Semaphores Concept）

`Semaphores` 由荷兰计算机科学专家 E. Dijkstra 于 1965 年提出的。`Semaphores` 是实践中使用的最古老的同步原语。`Semaphore`（信号量）是一个共享的、非负的整数计数器，需要设定一个初始值，并通过以下原子操作进行确定：

- **信号量减操作（`down`）**：如果信号量的值大于 0，则减 1；如果值为 0，则该流将进入等待状态，直到值大于 0（所有“在信号量处等待”或“在信号量处阻塞”的线程）。此操作也称为 `P` 或等待。以下是其伪代码：



```c
void down (semaphore_t sem){
    if (sem> 0)
        sem--;
    else 
        sleep ();
}
```

- **信号量加操作** (`up`)：将信号量的值加 1；当有流在信号量处等待时，其中一个流将离开等待状态并执行自己的操作。如果有多个线程在等待一个信号量，由于 `up` 操作的存在，其 `up` 值将保持不变，但其中一个线程将继续执行（在大多数实现中，该线程的选择是随机的）。此操作也称为 `V` 或信号。以下是其在文档中的代码：

```c
void up (semaphore_t sem){
    sem ++;
    if (waiting_threads ())
        wakeup (some_thread);
}
```

事实上，信号量的值决定了可以通过该信号量而不被阻塞的线程数量。当信号量的初始值设置为 0 时，它将阻塞所有线程，直到某个线程通过执行 `up` 操作来“打开”它。`up` 和 `down` 操作可以由任何访问该信号量的流执行。

# 信号量的用途 (Features Of Use Of Semaphores)

`Semaphores` 可用于解决两个不同任务之间的同步 `Liabilities`。

1. **互斥 (Mutual Exclusion)**：借助它们，可以组织互斥（以保护临界区域代码不被多个线程执行）。最方便的方法是使用`binary semaphore`（二进制信号量），它可以两个值：0 和 1。以下使用二进制信号量实现临界区域的示例：

```c
semaphore_t sem = 1; // 初始信号量是开启的
down (sem);// 临界区域
up (here);
```

2. **条件等待 (Condition Expectation)**：借助它们，你可以组织对某些条件完成的等待。假设需要组织等待一个线程完成另一个线程（`join` 操作的模拟）。在这种情况下，可以使用初始值为 0（关闭状态）的信号量。等待的流必须对该信号量执行 `down` 操作，而为了信号流的完成，其完成函数需要对该信号量执行 `up` 操作。以下是伪代码（`this_thread` 代表当前线程）：

```c
Void thread_init (){
    this_thread.sem = 0; // 在流执行开始时信号量是暴露的
}
void thread_exit (){
    up (this_thread.sem); // 唤醒挂起的流，如果有
}
void thread_join (thread_t thread){
    down (thread.sem); // 等待线程完成
}
```

# 使用信号量实现生产者-消费者问题 (Realization Of The Problem Of Producers-Consumers With The Help Of Semaphores)

首先，让我们定义解决此问题所需的同步动作。

1. 将直接更改缓冲区的操作（生产者——将对象放入缓冲区，消费者——从缓冲区中移除对象）放在临界区域中。

2. 根据要求 2 组织等待（生产者在缓冲区满时的等待）。在此，消费者必须通知等待中的生产者它已从缓冲区取走对象（即如果缓冲区是满的，现在变得不满了）。

3. 根据要求 3 组织等待（消费者在缓冲区为空时的等待）。在此，生产者必须通知预期缓冲区非空的消费者，并告知缓冲区之前是否是空的。

现在让我们来看我们需要的同步原语。每个同步操作都需要一个独立的信号量：

1. **锁 (to lock)**：为了使用临界区域，我们像以前一样使用二进制信号量。我们称之为 `to lock`。它将由生产者和消费者共同使用，保护其他线程对缓冲区的访问（再次，包括生产者和消费者）。

2. **空位计数 (empty items)**：为了组织生产者在缓冲区满时的等待，我们需要一个当前值等于缓冲区中可用空间数量的信号量。我们称之为 `empty_items`。生产者在尝试向缓冲区添加新对象之前，如果该信号量等于 0，则将其置为等待状态。消费者从缓冲区移除对象后，将通过通知生产者来增加信号量（并唤醒其中一个）。

3. **满计数 (full items)**：为了组织消费者在缓冲区为空时的等待，需要一个当前值等于缓冲区中位置数量的信号量。我们称之为 `full_items`。消费者在尝试从缓冲区中取对象之前，减少该信号量并进入等待状态。

以下是该问题的伪代码解决方案：

```cpp
semaphore_t lock = 1; // 用于临界区
semaphore_t empty_items = n; // 0 表示缓冲区满，从头为空
semaphore_t full_items = 0; // 如果为 0 表示缓冲区为空

// 生产者
void producer() {
    item_t item = produce(); // 创建 'item' 对象 
    down(empty_items); // 有空间存放 'item' 吗？
    down(lock); // 进入临界区
    append_to_buffer(item); // 将 'item' 对象添加到缓冲区中 
    up(lock); // 退出临界区
    up(full_items); // 通知消费者有一个新对象
}
 
// 消费者
void consumer() {
    item_t item;
    down(full_items); // 缓冲区不空？
    down(lock); // 进入临界区
    item = receive_from_buffer(); // 从缓冲区中取出 'item' 对象 
    up(lock); // 退出临界区
    up(empty_items); // 通知生产者位置
    consume(item); // 消费对象
}
```

## 互斥锁（Mutexes）

互斥锁的概念与之前定义的阻塞概念（第 5.2 节节）基本一致。被称为 `Mutex` 的同步原语防止一段代码在多个流中同时执行。事实上，互斥锁是操作系统级阻塞的实现。互斥锁正如其名称所示，消除了互斥。它的主要任务是在该代码已由一个线程执行时，阻塞所有尝试访问该代码的线程。互斥锁处于两种状态：空闲（free）和忙碌（busy）。初始状态为“空闲”，并有两个可能的原子操作。

* **获取互斥锁** (`mutex_lock(mutex)`)：如果互斥锁是空闲的，它变为忙碌状态，流继续执行（进入临界区）；如果互斥锁是忙碌的，流进入等待状态（称为“等待互斥锁”或“锁定互斥锁”），执行切换到另一个流。获取互斥锁的流被称为互斥锁的所有者：

```cpp
mutex_lock(mutex_t mutex) {
    if (mutex.state == free) {
        mutex.state = locked;
        mutex.owner = this_thread;
    } else {
        sleep();
    }
}
```

* **释放互斥锁** (`mutex_unlock(mutex)`)：互斥锁变为空闲；如果有多个流在等待它，将选择其中一个，让它开始执行，占用互斥锁并进入临界区。在大多数实现中，流的选择是随机的。只有所有者可以释放互斥锁。以下是该操作的伪代码：

```cpp
mutex_unlock(mutex_t mutex) {
    if (mutex.owner != this_thread)
        return error;
    mutex.state = free;
    if (waiting_threads())
        wakeup(some_thread);
}
```

某些实现提供了第三种操作尝试获取互斥锁（`mutex_trylock`）：如果互斥锁是空闲的，行为与 `mutex_lock` 类似；如果忙碌，则立即返回错误并继续执行。

这里是使用互斥锁实现临界区的简单示例。

```cpp
mutex_t mutex;
mutex_lock(mutex);
// 临界区
mutex_unlock(mutex);
```

二进制信号量与互斥锁的主要区别在于，`mutex` 的释放只能由其所有者完成，而信号量可以由访问它的任何流改变。

## 进程间

到现在为止，我们考虑的是单个进程内流的交互。这种交互的主要特征是它们之间数据交换的技术实现上非常简单——一个进程流使用同一个地址空间，因此可以自由地访问共享的变体数据，就像是它们自己的一样。由于数据交换的实现没有技术困难，在这种情况下需要解决的主要问题是流的同步。

另一方面，每个线程都在进程的地址空间内执行，因此组织不同进程流之间交互的任务通常是一个问题。这个问题本身就是进程间通信（`interprocess communication` 或 `IPC`）。对于不同进程的流，同步问题同样适用，但在大多数情况下，它们不是基于共享数据的概念（因为进程缺少默认数据）。此外，还增加了受保护地址空间之间交换安全的挑战。解决这一问题的方法定义了不同类型的进程间交互。

## 进程间交互的类型

进程间处理通过三种基本方法实现：消息传递、内存分配和显示内存。另一种 `IPC` 的方法是考虑之前讨论的信号技术。

### 扩展内存技术（映射内存）

在许多操作系统中，显示内存是其他类型进程间交互和系统决策的基础系统机制。当然，与文件系统接口结合使用的显示内存，在这种情况下指的是在内存中显示的文件（`memory-mapped files`）。这项技术是为了确保一个特殊的系统调用（通常是 `mmap()`）将进程地址空间的一部分唯一地包含该文件。之后，对此类内存的写入操作会导致显示文件的内容发生变化，这立即对所有访问该文件的应用程序可用。其他应用程序也可以在它们的地址空间中显示相同的文件，并通过它相互通信。

### 结论

* 一个交互进程的流可以访问托管在该进程地址空间中的共享数据。任何流都能随地更改这些数据，并由于结果取决于流的顺序而产生竞争状态。

* 流同步机制用于确保正确访问共享数据；主要任务是确保在特定时间只有一个流流可以访问此类数据，从而实现互斥。阻塞被用于组织互斥。

* 可以使用各种同步原语来解决同步问题。最简单的原语包括信号量、互斥锁、条件变量、读写锁和屏障（`barriers`）。

* 一种高级机制是监控器（`monitor`）概念，它结合了互斥锁和条件变量，并设置了它们交互的一些规则来保护共享数据。使用监控器是流同步最一致的方法。

# 第 6 章：内存管理

不同类型的内存被组织成层级结构。在这种层次结构的底层，有更便宜、更慢且容量更大的内存，随着层次结构向上移动，内存变得越来越贵、越来越快（容量也变小）。最便宜、最慢的设备是硬盘。它也被称为辅助存储。更快、更贵的内存存储在计算机的内存芯片上——称为主内存。更快的存储设施具有不同的处理器，且至少这些缓存是有限的。管理内存是一项相当困难的任务。所需的内存特性往往无法确定，而且为了不干扰用户工作，必须对不同类型的内存进行协调。因此，当前无法完全放入内存，未使用的代码可以存储在硬盘上。

## 虚拟内存基础

我们首先考虑引入虚拟内存的假设。在这种情况下，进程被加载到物理内存的连续部分。通过分析内存分配的特征，可能会出现以下问题：

* 如果物理内存比进程所需的内存要少，该怎么办？

* 当进程执行写入操作时，如果地址错误，该怎么办？

* 如果进程需要更多内存来执行，该怎么办？

* 当进程接收到物理地址信息时，应该如何转换地址？

* 如果分配给进程的内存不足，该怎么办？

直接将进程加载到物理内存无法提供这些问题的答案，显然需要内存翻译工具来允许进程使用不同的地址。在理解这些地址之前，让我们简要介绍一下编译和布局。

### 虚拟内存的概念

虚拟内存是一种在地址空间和物理内存之间进行转换的技术。虚拟内存确保内存是受保护的，且进程不需要是连续的。虚拟内存占据物理内存的某个空闲部分，通过分页（`paging`）技术进行地址转换。

### 虚拟内存的实现问题

由于分页在每次访问内存时都需要进行地址转换，由于内存是物理内存的空闲块被使用，而分段（`segmentation`）的实现会产生问题。

（注：原文中原文的实现 -> ，分段时，段段的的实现会产生问题。）

### 逻辑地址与物理地址

虚拟内存最重要的概念是逻辑和物理地址。

* **逻辑地址**：由运行的程序生成的地址。一组逻辑地址称为逻辑地址空间。

* **物理地址**：内存芯片操作的地址。现代计算机通过内存管理单元（`MMU`）负责将逻辑地址转换为物理地址。所有可用物理地址的总和称为物理地址空间。

### 基边界寄存方法

在实现虚拟内存时，需要保护内存、移动进程内存并在多个进程间共享内存。满足这些要求的简单方法之一是基边界寄存方法。对于每个进程，`CPU` 寄存器存储两个值：基地址（`base`）和边界（`bounds`）。每次对逻辑地址的访问都通过加上基地址转换为物理地址。如果收到的物理地址不在（`base + bounds`）范围内，则认为地址错误并产生错误。这是内存中进程动态移动的最简单示例。在本节中讨论的其他方法是不同的选项。例如，每个进程都有自己的基和边界寄存器。这种方法的优点包括简单性、硬件要求低（只有两个寄存器）和高效率。然而，由于许多缺点，今天实际上没有使用：地址空间映射到一个；不同进程无法共享内存。

### 内存分段

内存分段允许你将逻辑地址空间描述为一组变长块，称为段（`segments`）。每个段通常包含一个用途的数据，例如，一个可以有一个栈，另一个是程序代码等。每个段都有名称和长度。逻辑地址由段号和段内的偏移量组成。编译器通常为不同的应用程序创建单独的段（代码段、数据段、栈段）。当程序加载到内存时，它创建一个进程描述符表，表的每个元素对应一个段，并由基地址、限制值和保护属性组成。如果偏移量大于限制（或进程访问权限与段权限不匹配），硬件产生错误。当一切正常时，纯分段的基地址和偏移量的和会导致主内存中的一个物理地址。如果一个段被上传到硬盘，尝试访问会导致它从硬盘加载。

内存分段的益处：

* 有机会为进程组织多个独立的段并使用它们。

* 单个段可以被不同进程共享，它们的段描述表必须包含描述该段的相同元素。

* 地址空间不需要是连续的。

内存分段的缺点：

* 对每个段的要求会导致外部碎片。

* 不会产生内部碎片，因为段是变长的。

### IA32 架构中的分段实现

在 IA32 架构中，分段通过段选择器（`selector`）形成。段选择器存储在特殊寄存器中，并在切换上下文时由硬件自动加载。段选择器使用索引在页表中。线性地址被分为三个字段：

* **目录**：定义目录项，指向目标页表。

* **表**：页表元素，指向目标帧内存。

* **偏移量**：帧内的偏移量，与帧地址结合形成物理地址。

目录和表字段的大小为 10 位，页表包含 1024 个元素，偏移量字段的大小为 12 位，页和帧的大小为 4KB。一个低级表访问 4MB 内存（1MB 的帧），整个页目录拥有 4GB。所有层级的页表元素具有相同的结构。这里是以下元素字段：

* **存在标志（presence）**：如果页在物理内存中，则为 1；此标志表示页不在物理内存中，操作系统可以使用其他元素字段用于其目的。

* **高 20 位**：设置帧起始地址为 4KB 的倍数（可以指定 1MB 的不同地址）。

* **访问标志（Accessed）**：每次引用设备支持分页到相应的帧时置为 1。

* **更改标志（Changes）**：在每次事务中记录相应的帧时置为 1。

* **读写标志（read-write）**：访问页或页表的权限（读写或只读）。

* **特权标志（User/Supervisor）**：指定访问页所需的处理器模式。如果该标志为 0，则页只能从特权模式访问，如果单元从用户模式可用。

存在、访问和更改标志可用于操作系统组织虚拟内存。

### 分页组织

分页（`paging`）是另一种实现虚拟内存的内存技术。其核心思想是将内存块组织成固定长度的块，这些块被称为页（`pages`）。这是操作系统实现虚拟内存最常见的方法。

### 分页组织的基本原理

在分页组织的情况下，逻辑地址被分为两个部分：页号和偏移量。页号用作索引进入页表，页表包含关于物理内存帧的描述。当进程开始运行时，OS 计算页的数量并将页加载到物理内存。如果进程不使用某些内存块，所有低级页的内容可以临时存储在硬盘上。

### 分页组织与分段的比较分析

分页组织和分段有共同点。主要的区别在于：所有页具有固定长度，而段具有变长度。其他基础是：物理内存不需要连续性，可以将块卸载到磁盘，需要支持地址转换。

分页组织优于分段的优点：

* 主要由所有页具有相同长度决定。

* 内存分配的实现变得简单。

* 对于进程，所有页都可以维护一个空闲页列表，并在必要时从列表中选择第一个页。

* 与硬盘的通信也变得简单。

分页组织并非没有缺点：

* 首先，由于页大小总是固定的，这种方法会导致内部碎片，如果需要分配特定长度的内存块，其大小将是页大小的倍数。

* 每个专用块的未使用内存平均约为半页（类似于段）。

* 可以通过减少块的数量来减少这种碎片。

* 页表应该比段表大。例如，分配 100KB 的连续范围需要一个段元素来描述。

### 多级页表

为了处理大容量的逻辑地址空间，单个页表会非常大。例如，在 IA32 架构中，标准页大小为 4KB（地址内部需要 12 位），索引剩余 20 位，对应一个包含一百万元素的页表。为了避免这种页表，提出了分级页表。这项技术有两个主要优点：

第一，页表尺寸更小，因此搜索速度更快。

第二，并不是所有页表都需要在内存中。例如，如果进程不使用某些内存块，所有低级页的内容可以临时存储在硬盘上。

### IA32 架构中的页表实现

IA32 架构采用两层分页组织，从 Intel 8036 开始。顶层表称为目录，每个任务有一个单独的目录页，物理地址存储在特殊控制寄存中，并在切换上下文时由硬件自动加载。底层称为页表。线性地址分为三个字段：

* **目录**：定义目录项，指示目标页表。

* **表**：页表元素，指示目标帧内存。

* **偏移量**：帧内的偏移量，与帧地址结合形成物理地址。



目录和表字段的大小为 10 位，页表包含 1024 个元素，偏移量字段的大小为 12 位，页和帧的大小为 4KB。一个低级表访问 4MB 内存（1MB 的帧），整个页目录拥有 4GB。所有层级的页表元素具有相同的结构。以下是元素字段：

* 存在标志（`presence`）：如果页在物理内存中，则为 1；此标志表示页不在物理内存中，操作系统可以使用其他元素字段用于其目的。
* 高 20 位设置帧起始地址为 4KB 的倍数（可以指定 1MB 的不同地址）。
* 访问标志（`Accessed`）：每次引用设备支持分页到相应的帧时置为 1。
* 更改标志（`Changes`）：在每次事务中记录相应的帧时置为 1。
* 读写标志（`read-write`）：访问页或页表的权限（读写或只读）。
* 特权标志（`User/Supervisor`）：指定访问页所需的处理器模式。如果该标志为 0，则页只能从特权模式访问，如果单元从用户模式可用。

存在、访问和更改标志可用于操作系统组织虚拟内存。
