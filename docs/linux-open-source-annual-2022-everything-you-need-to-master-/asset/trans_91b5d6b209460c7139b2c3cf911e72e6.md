
## IPFire 网络配置

私有网络和红色网络指的是连接到互联网的那个网络。在实际操作中（如果你没有将 IPFire 部署在直接连接到你 ISP 的机器上），这两个网络都会通过你的家庭路由器连接，但你的绿色网络接口将连接（通过交叉线、无线或另一个路由器交换机）到你希望 IPFire 保护的机器。其理念是允许流量从绿色网络流向红色网络，但不允许反向流动。

必须为 IPFire 控制的网络设备设置 IP 地址。在上述配置中，我们的安全网络位于家庭 LAN 的“下方”，红色接口应当符合其余 LAN 的地址格式，例如 192.168.0.x 形式；而绿色接口在技术上可以设置为你想要的任何地址，但更合理的是使用另一个指定的私有地址，如 10.0.0.1 或（如果你偏好）192.168.1.1。红色接口（在此配置中）可以设置为通过 DHCP 接收 IP 地址，这提供了最简单的设置方式，但你可能随后需要配置静态 IP，否则在重启后你就要到处寻找你的 IPFire 实例了。使用静态 IP 时，你需要将网关设置为你家庭路由器的地址。如果你正在虚拟化环境中运行 IPFire，那么 DHCP 将使用你的 hypervisor 的 NAT 网络，这应该能正常工作。

除非你希望强制所有使用你私有网络的用户都使用静态 IP，否则绿色接口需要 DHCP 服务器。开启此功能并使用以下设置（或类似设置）：

- 起始地址：10.0.0.2
- 结束地址：10.0.11
- 主 DNS：10.0.0.1

如果你使用的是 *libvirt* 或 *VirtualBox*，这将无法正常工作，因为虚拟 NAT 设备拥有自己的 DHCP 服务器，这会干扰设置。因此，你需要为你希望 IPFire 保护的虚拟机设置静态 IP 地址。对于桌面发行版，最简单的方法是在 Network Manager 中设置静态 IP 配置（参见截图）。对于物理机器，你可以通过直接线缆连接（旧版 100mbit 网卡需要交叉线，千兆以太网网卡不需要）或经由交换机，将 IPFire 主机连接到绿色接口。

完成 IPFire 实例的初始设置，这应该就足够了。你应该能够访问 `https://10.0.1.444` 来从该机器连接到 IPFire。你首先会看到一个可怕的安全警告，因为 IPFire 使用自签名证书。请放心忽略它，我们保证。接下来你将看到一个登录框，你应该以 *admin* 身份登录，并使用你之前设置的密码。然后，IPFire 直观的 Web 界面将向你呈现。

![](img/3f314b57ad3c8b08d25e5d1ab47de56d_56_0.png)

默认情况下，IPFire 通过你的家庭路由器将 DNS 请求转发到红色接口上的 DNS 服务器，这很可能是你的 ISP。你可能希望使用公共服务，例如 CloudFlare 的 1.1.1.1 或 Google 的 8.8.8.8。你可以通过前往 Network > Domain Name System 来实现。取消勾选“Use ISP-assigned DNS”复选框，然后点击顶部的 Add 按钮。只需提供一个 IP 地址即可。

我们将设置一条简单规则，允许红色网络访问主机的 Web 界面。在现实生活中你通常不会这样做，但它展示了添加规则的操作流程。前往 Firewall > Firewall Rules 并点击 New Rule 按钮。在 Source 部分，选择 Standard Networks 选项并选择 RED。在下方勾选 Use NAT 复选框并选择 Destination NAT。在 Destination 部分选择 Firewall 选项并选择 GREEN - 10.0.0.1。在 Protocol 部分选择 TCP，在 Standard Networks 下拉框中选择 Any，并在 Source 部分的 External Port 框中输入 444。在 Additional Settings 框中，你可以选择记录、限制或速率限制这些连接，但我们不必为此费心，所以直接点击 Add。点击 Update，然后你应该能够从 LAN 上的任何位置连接到 IPFire 的 Web 界面。

![](img/3f314b57ad3c8b08d25e5d1ab47de56d_56_1.png)

使用 IPFire 时，防火墙规则看起来很简洁，而且 IPFire 界面在 Ubuntu 20.04 每日构建镜像中看起来很漂亮。

## 保护你的服务器

已被入侵或受到破坏的服务器在互联网上随处可见。不要让你的服务器成为其中之一。

无论你对 Linux 服务器做什么，你几乎肯定会对它们拥有 SSH 访问权限。事实上，这可能是你唯一的访问方式，因此确保其安全性是明智的。自然地，你已经在强密码，并且已经禁用了 root 账户的 SSH 访问权限（如果你为 root 设置了登录名）。后者非常重要，但在使用 *sudo* 提升权限的 Debian/Ubuntu 服务器上通常没有必要。在其他发行版上修正这一点只需在 `/etc/ssh/sshd_config` 文件中添加 `PermitRootLogin No` 并重启服务即可。但我们还能做得更多。既然我们之前研究过桌面环境中密码的替代方案，那么不妨研究一下服务器中的同一主题。除了密码，SSH 还允许你通过公钥登录。因此，通过在你登录所用的机器上生成密钥对，并将该密钥对的公钥部分复制到服务器上，你就不再需要使用密码了。你可能已经生成了密钥对，查找 `~/.ssh` 目录（在你的本地计算机上，而不是服务器上），然后查看其中名为 `id_rsa`（私钥）和 `id_rsa.pub`（公钥）的文件。如果这些文件已存在，你通常不希望 *覆盖* 它们，但如果你是很久以前创建它们、加了密码保护（可选但明智）然后忘记了密码（这种事会发生），那么你可能需要重新生成它们。

生成密钥对很简单，只需在你要登录的机器上运行：

`$ ssh-keygen`

你可以选择将文件保存到其他位置，但这样每次使用它时你都需要通过 `ssh -i` 提供路径。你还可以提供密码，这似乎有些反直觉，因为我们在这里谈论的是避免使用密码。其原理是，虽然你这里设置的密码可能会被暴力破解或被攻击者得知；但他们仍需访问密钥才能利用这一点。反过来，如果他们拥有密钥，他们仍然需要密码，因此这增加了一个额外的安全因素，而你付出的代价只是轻微的麻烦。

你可以手动将密钥添加到服务器，云服务商也会让你通过他们的管理界面完成此操作，但使用以下命令也就足够简单了（再次说明，所有这些操作都在“客户端”侧进行），将 `servername` 更改为你要登录的位置：

```
$ ssh-copy-id servername
```

这将提示你输入用户密码和密钥密码，然后将详细信息复制到服务器上的 `~/.ssh/authorized_keys` 文件。即使你在那里的用户名不同也没关系，一旦设置完成，你下一次登录时只需要密钥密码。

通常没有必要尝试管理多个 SSH ID。多个服务器的密钥可以妥善地存储在同一文件中。也不需要尝试将一个机器的 ID 复制到另一个机器（这行不通）。只需在你计划登录的每一台机器上设置不同的密钥对。除了使用密钥，建立 *Fail2Ban* 服务来防止针对 SSH 登录的暴力破解攻击（对于那些尚未享受按键登录便利的用户）和其他服务也是明智之举——这也是常见的安全防范基础。我们不会在这里详细介绍其设置方法（http://bit.ly/lxf262fail2ban 有一个很好的教程），但原理是反复尝试登录的 IP 地址将被阻止（使用 iptables）一段时间。这不仅增加了安全性，还防止了日志被失败的登录尝试淹没。

## Nextcloud 服务器审计

我们最喜欢且可以自行托管的工具之一是 *Nextcloud*。我们在 LXF Towers 经常使用它，因为 Linux 上的 Dropbox 客户端体验很糟糕。然而，强大的自托管能力伴随着巨大的责任，因此确保你的 *Nextcloud* 实例保持最新和安全至关重要。如果系统没有经常出故障，人们很容易忘记这些事项，而这确实曾经发生过。某种程度上是这样。我们以及其他优质 FOSS 提供商已在 Debian 上运行 *Nextcloud* 多年——这是一个强大的组合。Debian 会为关键修复执行无人值守更新，而手动的 Nextcloud 更新到 18.0.1 版本。
