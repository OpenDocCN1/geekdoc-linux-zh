# Including module-specific configuration files

The following lines allow Apache to load configuration files from the /etc/httpd/conf.d/ directory. This directory contains configuration files associated with specific modules.

```
# Load config files from the config directory "/etc/httpd/conf.d"
# Include conf.dconf
```

> CROSS-REFERENCE: The Configuring modules and related services (/etc/httpd/conf.d".conf") section, later in this chapter, describes some of the configuration files in the conf.d directory that may interest you.

# Choosing the server's user and group

The httpd daemon doesn't have to run as the root user; the fact that it doesn't run as root by default makes your system more secure. By setting User and Group entries, you can have the httpd daemon run with the permissions associated with a different user and group:

```
# If you wish httpd run as a different user or group, you must run
# httpd as root initially and it will switch.

# User/Group: The name (#number) of the user/group to run httpd as.
# On SCO (ODT 3) use "User nouser" and "Group nogroup".
# On HUX you may not be able to use shared memory as nobody, and
# the suggested workaround is to create a user and use that user.
# NOTE that some kernels refuse to setgid(Group) or semctl(IPC_SET)
# when the value of (unsigned)Group is above 60000;
# don't use Group -1 on these systems!
```

```
User apache
Group apache
```

By default, apache is defined as both the user and group for the server. If you change the User and Group directives, you should specify a privileged entity. This minimizes the risk of damage if your site is compromised. The first daemon process that started runs as root. This is necessary to bind the server to a low-numbered port and switch to the user and group specified by the User and Group directives. All other processes run under the user (UID) and group ID (GID) defined by those directives.

# Setting the main server's configuration

The second section of the httpd.conf file relates to directives handled by your main server (the one defined by the ServerName directive). In other words, these values are used by the default server and for all virtual hosts, unless they are explicitly changed for a virtual host. To change the same directives for particular virtual hosts, add them within virtual host containers.

# Setting an e-mail address

You can identify which users can send e-mail if there is a problem with your ServerAdmin directive.

```
# ServerAdmin: Your address, problems with the server should be
# e-mailed. This address appears on some server-generated pages, such
# error documents. e.g. admin@your-domain.com
#
ServerAdmin@you.address
```

The ServerAdmin directive can be set to any valid e-mail address. The default is root@localhost.

# Setting the server name

If your server is anything but your registered host or domain name, you should identify your server name here. As the comments point out, the ServerName directive should be set to a value other than the actual hostname of your machine. However, this name should still point to your machine in DNS if the server is a public Internet server. Frequently, www.linuxutoys.net, but its real name is al.linuxutoys.net. (for example, a machine may point to www.linuxutbox.linuxutys.net).

```
ServerName ebook.linuxutys.net
```

Apache tries to use your hostname as the ServerName, if you don't enter a valid server name. It is recommended that you explicitly enter a ServerName here.

# Setting canonical names

Use theCanonicalName directive to create a self-referencing URL, as follows:

```
## UseCanonicalName: Determines how Apache constructs self-referencing
# URLs and the SERVER_NAME and SERVER_PORT variables.
# When set "Off", Apache will use the Hostname and Port supplied
```

```
# by the client. When "On", Apache will use the value of the
# ServerName directive.
# UseCanonicalName Off
```

The UseCanonicalName directive provides a form of naming consistency. When it is set to
On, Apache uses the ServerName and Port directives to create a URL that references a file
on the same machine (for example, http://www.linuxtoys.net/docs/). When
UseCanonicalName is Off, the URL consists of whatever the client specified (for example,
the URL could be http://al.linuxtoys.net/docs/ or http://al/docs/ if the
client is within the same domain).

This can be problematic; when access-control rules require username and
password authentication: if the client is authenticated for host.linuxtoys.net but a
link sends him or her to www.linuxtoys.net (physically the same machine), the client will
be prompted to enter a username and password. It is recommended that
UseCanonicalName be set to On. In the preceding situation, the authentication would not
need to be repeated because the same server would be interpreted as
www.linuxtoys.net.

# Identifying HTTP content directories

There are several directives for determining the location of your server's content. The
main location for your web content is set to /var/www/html by the DocumentRoot
directive. Note that the trailing slash is not on the path name.

> (Note that location has changed from early versions of Red Linux. The location was
formerly in /home/http.)

```
# DocumentRoot: The directory out of which you will serve your
# documents. By default, all requests are taken from the directory, and
# symbolic links and aliases may be used to point to other locations.
DocumentRoot "/var/www/html"
```

# Setting access options and overrides

You can set access permissions for each directory in the web server's directory
structure. The default is fairly restrictive. Here is the default:

```
<Directory />
Options FollowSymLinks
AllowOverride None
</Directory>
```

This segment sets up a default block of permissions for the Options and AllowOverride
directives. The <Directory /...</Directory> tags enclose the directives that are to
be applied to the directory (which is /var/www/html by default, as defined by
DocumentRoot).

The Options FollowSymLinks instructs the server that symbolic links within the directory can be followed to allow content that resides in other locations of the computer. None of the other server features will be active in the / or any directory below that, without being explicitly specified later. Next, the following access options are specifically set for the root of your server (/var/www/html). (I removed the comments for clarity.)

```
<directory /var/www/html">
  Options Indexes FollowSymLinks
  AllowOverride None
  Order allow,deny
  Allow from all
</directory>
```

If you have changed the DocumentRoot earlier in this file, you need to change the /var/www/html to match that value. The Options set for directory are Indexes and FollowSymLinks. Those and other server features are described in Table 21-2. The AllowOverride directive instructs the server an .htaccess file (or value of AccessFileName) cannot override any of the special access features. You can replace None with any of the special access features described in Table 21-3.

# Table 21-2: Special Server Features for the Options Directive

| Feature | Description |
| :--- | :--- |
| ExecCGI | The execution of CGI scripts is permitted. |
| FollowSymLinks | The server will traverse symbolic links. |
| Includes | Server-Side Includes are permitted. |
| IncludesNOEXEC | Server-Side Includes are permitted, except the #exec element. |
| Indexes | If none of the files specified in the DirectoryIndex exists, a directory index will be generated by mod_autoindex. |
| MultiViews | The server allows content negotiation based on preferences from the user's browser, such as preferred language, character set, and media type. |
| SymLinksOwnerMatch | The server will traverse symbolic links only if the owner of the target is the same as the owner of the link. |
| None | None of the features above are enabled. |
| All | All the features above are enabled, with the exception of MultiViews. This must be explicitly enabled. |
