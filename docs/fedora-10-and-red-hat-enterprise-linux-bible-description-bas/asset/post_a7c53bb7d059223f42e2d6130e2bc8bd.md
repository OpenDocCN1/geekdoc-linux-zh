The example host.allow contains the first two types of client specification. The entry 199.170.177. will match any IP address that begins with that string, such as 199.170.177.25. The client entry.linuxxtoys.net will match hostnames such as jukebox.linuxxtoys.net or picframe.linuxxtoys.net.

Let's examine what happens when a host named jukebox.linuxxtoys.net (with IP address 199.170.179) connects to your Fedora system using the Telnet protocol:

- 1. xinetd receives the connection request.
- 2. xinetd begins comparing the address and name of jukebox.linuxxtoys.net to the rules listed in /etc/hosts.allow. It starts at the top of the file and works its way down the file until a match found. Both daemon (the program handling the network service on Fedora) and the connecting client's IP address or name must match the information in the hosts.allow file. In this case, the second rule that is encountered matches:

```
in.telnetd: 199.170.177., .linuxxtoys.net
```
- 3. Jukebox is not in the 199.170.177 subnet, but it is in the linuxxtoys.net domain. xinetd stops searching the file as if finds this match.

> CAUTION: While xinetd acts as a convenient example with xinetd, do not run the telnet service due to security concerns. Enable ssh for remote logins. See the later section on using the secure shell package for ssh.

How about if you connect to your box using the CUPS-lpd protocol? In this case, matches none of the rules in hosts.allow; the only line that refers to the lpd daemon does not refer to the 199.170.179 subnet or to the linuxxtoys.net domain. xinetd continues on the hosts.deny file. The entry ALL: matches anything, so tcpd denies the connection.

The wildcard will allow anyone to use the hosts.allow file. In this case, we are telling xinetd to permit absolutely anyone to connect to the FTP service on the Linux box. This is appropriate for running an anonymous FTP server that anyone on the Internet can access. If you are not an anonymous FTP site, you should probably not use the ALL flag.

A good rule of thumb is to make your hosts.allow and hosts.deny files as restrictive as possible and explicitly allow only those services you really need. Using the ALL flag for grant access to a particular service may be easier than tying in a long list of subnets, but better a few minutes spent on proper security measures than many hours recovering from a break-in.

> TIP: You can restrict access to services using various options within the /etc/xinetd.conf file, even to the point of limiting access to certain specific times of the day. Read the manual page for xinetd (by typing man xinetd at a command prompt) to learn more about these options.

# Chapter 14: Computer Security Issues

## Checking Log Files

Preparing your system for a cracker attack is only part of the battle. You must also recognize a cracker attack when it is occurring. Understanding the various log files in Fedora and RHEL record important events is critical to this goal. The log files for your Fedora or RHEL system can be found in the /var/log directory.

Because the system logs are plain text files, you can view the contents of logs directly using any text editor or command (such as less or more). The logwatch facility (which comes with Fedora and RHEL) sends daily details from your log files in an e-message to the root user. You can also add packages, such as syslog, to monitor your log files. (A description of logsentry is contained on the Wiley Web site for this book at www.wiley.com/go/fedorabible)

## Understanding rsyslog service

Most of the files in the /var/log directory are managed by the rsyslog service. The rsyslog daemon is the System Logging Daemon and acts as an extension of a previous logging system called syslog. It accepts messages from various other programs and writes them to its own log file because it is better than having every program you write directly to centrally manage how logs are handled. It is possible to configure rsyslog to record varying levels of detail in the log files. It can be told to ignore all but the most critical message, or to record every detail.

The rsyslog daemon can accept messages from other computers on your network. This is particularly handy because it enables you to the central management and reviewing of the log files from many systems on your network. There is also a major security benefit to this practice. If a system on your network is broken, the cracker cannot delete or modify the log files because those files are stored on a separate computer.

It is important to remember, however, that log messages are not by default, encrypted. Anyone tapping into your local network will be able to eavesdrop on those messages as they pass from one machine to another. Also, although the cracker may not be able to change old log messages, he will be able to affect the system that any new log messages should not be trusted.

It is not uncommon to run a dedicated loghost, a computer that serves no other purpose than to log messages from other computers on the network. Because this system runs no other services, it makes nearly impossible for a cracker to erase it or hide her tracks. It does not, however, that all of the log messages are safe after a cracker has broken into a machine on your network.

## Redirecting logs to a loghost with rsyslog

To redirect your computer's log files to another computer's rsyslog, you must make some changes to your local rsyslog's configuration file. The file you need to work with /etc/rsyslog.conf. If you are not already root, boot root and then open the /etc/rsyslog.conf file in a text editor (such as vi). You should see something similar to this:

```
#rsyslog v3 config file

# if you experience problems, check
# http://www.rsyslog.com/troubleshoot ####

#### MODULES ####

$ModLoad imsock.so # provides support for local system logging (e.g. via logger command)
$ModLoad imlog.so # provides kernel logging support (previously done by klogd)
##ModLoad imark.so # provides --MARK-- message capability

# Provides UDP syslog reception
$ModLoad impud.so
$UDPServerRun 514

# Provides TCP syslog reception
$ModLoad imtcp.so
$TCPServerRun 514
```

```
#### GLOBAL DIRECTIVES ####

# Use default timestamp
$ActionFormat
$ActionFileDefault

# File syncing is disabled by default
$ActionFileEnableSync
```

```
#### RULES ####

# Log all kernel messages to the console
kern.* /dev/console

# Log anything (except mail) of level info
*.info:mail.none /var/log/messages

# The authpriv file has restricted access
authpriv.* /var/log/secure

# Log all mail messages in one place
mail.* /var/log/maillog

# Log cron stuff
cron.* /var/log/cron

# Everybody gets emergency messages
*.emerg

# Save news of level crit in a special file
uucp.news.crit /var/log/spool

# Save boot messages also to boot.log
local.* /var/log/boot.log
```

```
# ### begin forwarding rule ###
# The statement between begin ... define a SINGLE forwarding
# rule. They belong together, do NOT split them.

# Remote Logging (we use TCP for reliable delivery)
#
# An on-disk queue is created for action. If the remote host is
# down, messages are spooled to disk and sent when it is up.
##workdirectory /var/spool # where to place spool files
$ActionqueueFileName default # unique name prefix for spool files
$ActionqueueMaxDiskSpace 1g # gb space limit (use as as possible)
$ActionqueueSaveShutdown # on save messages to disk to shutdown
$ActionqueueType LinkedList # run asynchronously
$ActionResumeCount -1 # infinite retries if host is down
# remote host is: name=ipv4:port, c.g. 192.168.0.1:514, port option
#.*=remote-host:514
# ### end of the forwarding rule
```

The most interesting part of the section marked RULES.

NOTE: Notice the dash (-) before the /var/log/logfile file Normally, each log file is synced after every logging. A dash preceding the full path to the log indicates that the file is not synced after each logging. While this might result in lost information if your machine crashes before the log is written, can result in better performance on your system if you use verbose logging.
