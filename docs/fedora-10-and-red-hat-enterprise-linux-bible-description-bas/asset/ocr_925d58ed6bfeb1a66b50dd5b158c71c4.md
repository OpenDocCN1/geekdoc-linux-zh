+   **Role-Based Access Control** — Using the RBAC model, SELinux lets each user operate in a specific role. The roles are arranged in a hierarchy, with specific permissions associated with each role provided by type enforcement.

In traditional Linux, a user is assigned a specific user ID (UID) and group ID (GID), which affords that user access to system resources. For instance, it gives the user certain rights to read, write, or execute files and directories based on whether that user's file or directory is part of a group assigned to that file or directory.

In SELinux, a data file, directory, or application can have many attributes associated with it. Those attributes might give you permissions to access the component that were available in traditional Linux security. At the same time, having access to the component wouldn't necessarily give control of that component in a way that could be exploited unless the security policy allows the user to do.

# Users in SELinux

The model that SELinux uses to define the rights that users have on an SELinux-enabled system can co-exist with the existing Linux user model, rather than replace it. With SELinux enabled, users still have their accounts defined before in the /etc/passwd file. A user who is also assigned a role in SELinux is referred to as a Defined User.

Special identities in SELinux include the system_u (which is the user identity assigned to system processes) and user_u (which is the assignment used to indicate if general users, in particular those without specific user identities, are allowed to use the feature in question). There is also a root identity, which is retained to allow compatibility with existing file contexts. This allows existing identities to remain valid if they have root as their user identity.

# Policies in SELinux

As noted earlier, with Fedora and RHEL the choice of turning either SELinux or turning it on. The values in the /etc/selinux/config file determine which type of policy is on (only the targeted policy is available by default, however a strict policy is also available) and when not SELinux is:

+   -enforcing**: The current SELinux policy is on and is enforced.
- **permissive**: The current SELinux policy is on, but not enforced (so you only see warning messages describing how the policy would be enforced).
- **disabled**: SELinux is off, so only standard Linux permissions are enforced (as they were always on systems not including SELinux).

Fedora and RHEL contain a compiled policy for the targeted policy they deliver. For example, in the current version of Fedora /etc/selinux/targeted/policy/policy.23 is the compiled policy set used when that policy is active.
