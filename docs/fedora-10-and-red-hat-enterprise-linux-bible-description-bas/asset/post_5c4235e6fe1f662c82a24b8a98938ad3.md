## Executing and debugging shell scripts

One of the primary advantages of shell scripts is that they can be opened in any text editor to see what they do. A big disadvantage is that large or complex shell scripts execute more slowly than compiled programs. There are two basic ways to execute a shell script:

- The filename is used as an argument to the shell (as in `bash script`). In this method, the file does not need to be executable; it just contains a list of shell commands. The shell specified on the command line is used to interpret the commands in the script file. This is most common for quick, simple tasks.
- The script may also have the name of the interpreter specified in the first line of the script preceded by `#!` (as in `#!/bin/bash`), and have its execution bit set using `chmod +x`. You can then run your script just like any other program in your path by simply typing the name of the script on the command line.

> CROSS-REFERENCE: See Chapter 4 for more details on chmod and read/write/execute permissions.

When scripts are executed in either manner, options to the program may be specified on the command line. Anything following the name of the script is referred to as a command-line argument.

As with writing software, there is no substitute for clear and thoughtful design and lots of comments. The pound sign (#) prefixes comments and can take up an entire line or exist on the same line after script code. It's best to implement more complex shell scripts in stages, making sure the logic is sound at each step before continuing. Here are a few good, concise tips to make sure things are working as expected during testing:

- Place an echo statement at the beginning of lines within the body of a loop. That, rather than executing the code, you can see what will be executed without making any changes.
- To achieve the same goal, you place dummy echo statements throughout the code. If these lines get printed, you know the correct logic is being taken.

- You could use `set -x` near the beginning of the script to display each command that is executed or run your scripts using `bash -x myscript`.
- Because useful scripts have a tendency to grow over time, keeping your code readable as you go along is extremely important. What do you do to keep the logic of your code clean and easy to follow?

## Understanding shell variables

Often within a shell script, you want to reuse items of information. During the course of processing the shell script, the name or number representing this information may change. To store information used by a shell script in such a way that it can be easily reused, you can set variables. Variable names within shell scripts are case-sensitive and can be defined in the following manner:

```
NAME=value
```

The first part of a variable is the variable name, and the second part is the value set for that name. Be sure that the NAME and value touch the sign, without any spaces. Variables can be assigned from counts, such as text or numbers. This is useful for initializing variables or saving lists for long counts. Here are examples where variables are set to a string of characters (CITY) and a numeric value (PI):

```
CITY="Springfield"
PI=3.1415265
```

Variables can contain the output of a command or command sequence. You can accomplish this by preceding the command with a dollar sign ($) and open parenthesis, and following it with a closing parenthesis. For example, `MYDATE=$(date)` assigns the output of the date to the MYDATE variable. Enclosing the command in backticks (````) can have the same effect.

> NOTE: Keep in mind that characters such as dollar sign ($), backtick (```), asterisk (*), exclamation point (!), and others have special meaning to the shell, as you will as you proceed through this chapter. To use those characters in an option to a command, and not have its special meaning, you need to precede that character with a backslash (\) or surround it in quotes. One place you will encounter this is in files created by Windows that include spaces, exclamation points, or other characters. In Linux, to properly interpret a file named `my big! file!`, either need to surround it in double quotes or type: `my\ big\ file!`

These are great ways to get information that can change from computer to computer or day to day. The following example sets the output of the `uname -n` command to the MACHINE variable. Then you use parentheses to set NUM_FILES to the number of files in the current directory by piping (|) the output of the `ls` command to the word count command (wc -1).

```
MACHINE=`uname -n`
NUM_FILES=$(/bin/ls | wc -1)
```

Variables can also contain the value of other variables. This is useful when you have to preserve a value that will change so you can use it in the script. Here BALANCE is set to the value of the CurBalance variable.

```
BALANCE=$CurBalance
```

> NOTE: When assigning variables, use only the variable name (for example, BALANCE). When referenced, meaning you want the value of, precede it with a dollar sign ($).

## Special variables

There are special variables that are commonly used in shell scripts. These are automatically set by the shell and provide information about the environment.

- $0: The name of the script or the command being executed.
- $1, $2, ...: The positional parameters passed to the script.
- $@: All positional parameters as individual arguments.
- *: All positional parameters as a single string.
- $?: The exit status of the last command executed.
- $#: The number of positional parameters.
- $PWD: The current working directory.
- $HOME: The home directory of the current user.

## Parameter expansion in bash

Parameter expansion allows you to manipulate strings and perform logic directly on variables. There are several ways to expand variables, as shown in the table below:

| Construction | Meaning |
|---|---|
| ${var:-value} | If var is unset or empty, expand to value |
| ${var#pattern} | Chop the shortest match for *pattern* from the front of var |
| ${var##pattern} | Chop the longest match for *pattern* from the front of var |
| ${var%%pattern} | Chop the shortest match for *pattern* from the end of var |
| ${var%%%pattern} | Chop the longest match for *pattern* from the end of var |

Try using the following commands to test how parameter expansion works:

```
$ THIS="Example"
$ THIS=$(THIS:-"Not Set")
$ THAT=$(THAT:-"Not Set")
echo $THIS
Example
echo $THAT
Not Set
```

In the examples here, the THIS variable is initially set to the word Example. In the next lines, THIS and THAT variables are set to their current values or to Not Set, if they are not set. Notice that I just set the string Example, when I echo it the value of THIS appears as Example. However, since THAT was not set, it appears as Not Set.

In the following example, MYFILENAME is set to /home/digby/myfile.txt. Next, the FILE variable is set to myfile.txt, and DIR is to /home/digby. The NAME variable, the file name is cut down to simply myfile, in the EXTENSION variable is set to txt. To try these out, you can type them at a shell prompt as in the previous example, then echo each value of variable to see how it is.

```bash
FILENAME="/home/digby/myfile.txt"
FILE=$($FILENAME##*)  # FILE becomes "myfile.txt"
DIR=$($FILENAME%%*)    # DIR becomes "/home/digby"
NAME=${FILE.*}          # NAME becomes "myfile"
EXTENSION=${FILE#.}     # EXTENSION becomes "txt"
```
