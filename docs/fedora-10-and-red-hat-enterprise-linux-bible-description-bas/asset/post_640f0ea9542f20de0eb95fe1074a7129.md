- ICMP rules — ICMP messages are really for reporting conditions of the server than for actually providing services. Packets from the Internet that are accepted for ICMP protocol requests in our example are for ICMP types 8 and 11. Type 8 service, which allows your computer to accept echo request messages, makes it possible for people to ping your computer to see if it is available. Type 11 relates to packets whose time live (TTL) was exceeded in transit, and for which you are accepting a Time Exceeded message that is being returned to you. (You need to use the traceroute command to find routes how you want.)

- FORWARD chain rules — Because this firewall is also acting as a router, FORWARD rules are needed to limit what will will pass between the two networks (Internet and local LAN). The first line forwards everything from the local LAN (-A eth1). The second line forwards everything from the Internet that is associated with an established connection (--state ESTABLISHED, RELATED).

- OUTPUT chain rules — These rules basically exist to prevent anyone from your local computer from spoofing IP addresses (that is, from saying packets are coming from somewhere they are not). According to these three rules, each packet output from your firewall must have just one of the addresses from the firewall's interfaces (127.0.0.1, 10.0.0.1, or 123.45.67.89).

- POSTROUTING chain rules — The POSTROUTING chain defines rules for packets that have been accepted, but need additional processing. This is where the actual network-address translation (NAT) works place. For all packets that go out to the Internet have addresses translated to that of the firewall's external interface (--to-source 123.45.67.89). In this case I used the Source Address Translation (SNAT) chain because I have a static IP address (123.45.67.89) associated with my computer. If I were using a dynamic IP address (via DHCP), I would use MASQUERADE instead of SNAT. I would also have to change any references to -d 123...89 to -i eth0. ## Understanding iptables

Now you've seen something about iptables rules look like and how you can get them, stepping back a bit and see how iptables works.

The iptables feature works by having IP packets (that is, network data) that enter or leave the firewall, traverse a set of chains that define what is done with the packet. Each rule you essentially does one of the following:

- Checks whether a criterion is met (such as a packet requests a particular service or comes from a particular address)
- Takes an action (such as dropping, accepting, or processing a packet)

Different sets of rules are implemented for different types of tables. For example, tables exist for filtering (filter), network address translation (nat), and changing packet headers (mangle). Depending on the packet's source and destination, it traverses different chains. Most of the rules you will create be the filter table (which is implied if no other table is given).

The chains associated with the filter table are INPUT, OUTPUT, and FORWARD. You can add user-defined chains as well. You will be most interested in adding or removing particular TCP and UDP services using the basic rules in the previous example. Assign ACCEPT to packets you want to go through and DROP to those you want to discard. You can also assign REJECT to drop a packet but return a message to the server, or LOG to neither drop nor accept the message, but log information about the packet.

A lot of great features are built into iptables. The following descriptions will tell you about some cool things you can do with iptables and give you some tips on using it.

## Allowing FTP and IRC services through an iptables firewall

With passive FTP, the FTP client sends its IP address and the port number on which it will listen for data to the server. If that client is on a computer that is behind your firewall, for which you are doing NAT, that information must be translated or the FTP server will not be able to communicate with the client.

iptables uses connection-tracking modules to track connections. Using this feature, it can look inside the data of each FTP packet (that is, not in the IP packet header), to get information it needs to do NAT (remember that computers from the Internet can't talk directly to your private IP addresses). To do FTP connection tracking (to allow FTP connections to your LAN, you need to have the following modules:

- nf_ip_conntrack
- nf_ip_conntrack_ftp
- nf_ip_nat_ftp

The same is true for chats and DCC sends, used to establish and monitor direct connections to IRC chats. Addresses and port numbers are stored within the IRC protocol packets, so those packets must be translated, too. To allow clients on your LAN to use IRC services, you need to load the following modules:

- nf_ip_conntrack_irc
- nf_ip_nat_irc

The default port for IRC connections is 6667. If you don't want to use the default you can add different ports when you load the connection-tracking modules:

```
modprobe nf_ip_conntrack_irc ports=6668,6669
```

## Using iptables to SNAT or IP Masquerading

As noted in the ipt, you can use Source Network Address Translation (SNAT) or IP Masquerading (MASQUERADE) to allow computers on your LAN with private IP addresses to access the Internet through your firewall. Choose SNAT if you have a static IP and MASQUERADE if the IP address is assigned dynamically.

When you use the MASQUERADE or SNAT rule, it is added to the NAT table and the POSTROUTING chain. For MASQUERADE you must provide the name of the interface (such as eth0,ppp0, slip0) to identify the route to the Internet or outside network. For SNAT you must also identify the actual IP address of the interface. Here is an example of a MASQUERADE:

```
iptables -t nat -POSTROUTING -o eth0 -j MASQUERADE
```

Here is an example of a SNAT rule:

```
iptables -t nat -POSTROUTING -o eth0 -j SNAT --to-source 12.12.12.12
```
