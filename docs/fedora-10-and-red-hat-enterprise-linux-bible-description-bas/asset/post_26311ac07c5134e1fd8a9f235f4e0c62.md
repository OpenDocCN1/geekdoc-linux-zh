## Adding user accounts

Ultimately, the e-mail received by your mail server is placed in a user's mailbox, where the user can pick it up and read it at or her leisure. Each of those user names must be added as a real user on your Fedora system. For example, to add the user chris to Fedora sendmail server, you could type (as root):

```bash
# useradd -s /sbin/nologin chris
```

This action creates a user account chris in the /etc/passwd file, sets the shell to /sbin/nologin, and creates a mail box for that user in /var/spool/mail/chris. The /sbin/nologin prevents the user from logging into a shell (which is a security practice when you only want a user to have mail or FTP access, for example). Sendmail can direct e-mail to that user's mailbox.

For that user to access his e-mail later from the POP3 client, he will need a password for his account. Set the password for that user with the passwd command as follows:

```bash
# passwd chris
user: chris
New UNIX password: ********
Retype new UNIX password: ******
password: all authentication tokens updated successfully
```

Make sure that the user has this account name and password so it can be configured into the user's e-mail client.

## Starting sendmail and generating database files

None of the configuration that you did to your sendmail.mc, virtuertable, access, domainable, and mailtable configuration files take effect until they are regenerated into database (.db) files. There are a few ways you can go about loading your configuration files into database files:

- **Starting sendmail** — Each time you reboot your computer or restart the sendmail daemon (service sendmail restart), all sendmail configuration files (including sendmail.mc) are compiled into database files that are ready to be used by the sendmail server. You can also rebuild the databases without stopping the sendmail daemon (including the /etc/aliases.db file) using the sendmail startup script. To simply rebuild the database:

```bash
# /etc/init.d/sendmail reload
```

This command rebuilds all the database files, including the /etc/aliases file. (If the reload doesn't update your sendmail.cf file, be sure the sendmail-cf package is installed: install sendmail-cf.)

- **Making the configuration files** — Using the make command, you can have some or all of the configuration files made into database files, so they become immediately usable by the sendmail daemon. To do that, change to the /etc/mail directory, and type either all or make with the target database file you are creating. For example:

```bash
# /etc/mail
# make virtuertable.db
```

You can replace virtuertable.db with access.db, domainable, mailtable.db, or sendmail.db. (Note that you use the .db target name and not the name of the original configuration file.) As mentioned, you can also use the make all command to rebuild all database files.

At this point, your sendmail server should be up and running. You can test your server by sending mail to it and checking log files to see how the server reacted. Make sure that your firewall allows requests on TCP port 25. Then check that your mail server is responding by typing the following:

```bash
# telnet 127.0.0.1 25
Trying 127.0.0.1...
Connected to localhost.localdomain (127.0.0.1).
Escape character is '^'.
220 toys.linuxtoys.net SMTP Sendmail 8.14.3/8.14.3;Sun, 16 Nov 2008 03:34:02 -0500
```

You can see that the sendmail daemon is running and responding to port number 25. Try typing HELO. (That's literally HELO and not HELLO.) When you are done, type QUIT to exit.

## Redirecting mail

At times, your e-mail users want to redirect mail to some place. The .forward file is a flexible way to handle this.

### The .forward file

One way to redirect mail is through the .forward file, which is a plain-text file located in the user's home directory. The format consists of a name followed by a colon, and then a list of addresses or a program.

- **Piping mail to a program** — You can pipe mail to a program for filtering or processing. For example:
  `user | /usr/bin/filter-script`
- **Forwarding to multiple addresses** — You can forward mail to multiple recipients by separating them with commas:
  `user1@example.com, user2@example.com`

### The aliases file

A more flexible method of handling mail is the /etc/aliases file. This file is system-wide and allows you to define aliases for many users. Some aliases are already set by default in /etc/aliases:

```bash
bin: root
daemon: root
lp: root
```

You can use the aliases file yourself to create mailing lists. Here's an example:

```bash
info-list: chris, tweaks, francois@spidermaker.com
```

In this example, any messages sent to info-list are distributed to chris, tweaks, and francois@spidermaker.com. Notice that the list can be a combination of local users and outside addresses.

One account can receive mail under several different names:

```bash
patterson: jkpat
```

This indicates that any mail addressed to patterson@mybox.com (just as an alias) will arrive in the mailbox of jkpat (an actual account).

Mail can be received under a name that isn't a valid (or reasonable) user name:

```
eric.foster-johnson@objectpartners.com:efjohnson
```

He may not want to type eric.foster-johnson as a user name, but that doesn't mean he cannot receive mail as such.

Messages intended for one user can be redirected to another account (or to several accounts):

```bash
oldemployee: bradford
consultant: bradford, jackson, patterson
users:include:/root/mail/lists/users
```

Here, any message for oldemployee@mybox.com will be delivered to the mailbox of user bradford. The users bradford, jackson, and patterson would receive any mail addressed to consultant. The third line indicates that the recipients of the “users” are specified in the file /root/mail/lists/users.

Mail can be sent directly to a file on the local machine:

```bash
acsp-bugs:/dev/null
trouble-ticket:/var/spool/trouble/incoming
```

In the first line, the fictional ACSP program is no longer used on the machine, there's no need to track its errors, so the mail is effectively ignored.
