## Introducing Postfix

Postfix is a Mail Transfer Agent that you can use in place of sendmail to handle mail service on your Fedora or Red Hat Linux system. There are several reasons Postfix proponents give using Postfix instead of sendmail for your mail service:

- * Postfix is designed to be easier to administer. Instead of using m4 syntax in the sendmail.mc file, Postfix uses types of directives used in the Apache Web server.
- * Postfix has multiple layers of security built in, including the ability to run in a chroot jail. It also filters sender-provided information before exporting that information into the Postfix environment.

Some of the configuration files and other components are different from those in sendmail, many are meant to replace sendmail components (such as aliases, access, and .forward files, as well as the /var/mail directory structure). To help you make the transition from Postfix to sendmail, Fedora and RHEL have configured the two packages to use the alternatives system. Chapter 10 describes how to use the Mail Transport Agent Switch to change from one transport to the other.

When you switch and start the Postfix daemon, as described in Chapter 10, Postfix takes over as the MTA replaces sendmail components with Postfix components, and some of the locations for mailboxes and log files. Postfix takes over mail transport based on configuration files in the /etc/postfix directory. The following is an overview of the defaults used by the Postfix service:

- * Mail configuration (/etc/postfix/main.cf) — The primary configuration file for Postfix. Identifies the locations of Postfix queues, commands, and aliases, as well as defining the host and domain names that Postfix is serving. If you do not add a fully qualified domain name to this file, Postfix will use your local hostname as the name of the mail service represents.
- * Mailboxes(/var/spool/mail) — Directory containing incoming mail files, with each user's mailbox represented by a file of the user's name. (This is the default spool directory used by sendmail.)
- * Mail queue(/var/spool/postfix) — Location of directories where mail messages are queued for delivery.
- * Mail log (/var/log/maillog) — Location of mail log files.

Although most options for Postfix are described in the /etc/postfix/main.cf file, you can see many more available options in the main.cf file in the same directory. Based on the default configuration in the main.cf file, here is how Postfix will handle inbound mail:

- * Outbound mail — The local hostname is addressed as the sending host for this computer. You might want to change it to the local domain name (set myorigin=$mydomain).
- * Incoming mail — Only mail destined for the local hostname is kept on the local server by default. Other mail is forwarded. To have all mail for your domain kept on the local server, add $mydomain to the destination line.

For complete information on configuring Postfix, refer to http://www.postfix.org/docs.html.

## Stopping Spam with SpamAssassin

Despite the fact that it is rude and undesirable, there are people who send thousands of unsolicited email messages (referred to as spam), hoping to get a few responses. Due to the economics of the Internet, spammers can send literally millions of messages. A very small number of respondents is enough to make a profit for the spammers. Furthermore, modern spam can be dangerous, including messages designed to fool users into entering user names and passwords (phishing) or messages that exploit vulnerable systems (particularly Windows systems).

Because Linux systems are often used as mail servers, tools for scanning mail messages for spam and viruses have become much over the years. In this chapter, I describe how to use ClamAV to deal with spam and viruses on your mail server. If this doesn't meet your needs, you might add ClamAV virus scanner to test mail messages for actual malware attachments. Here are a few links where you can learn ClamAV and how to use it with different mail software:

- * ClamAV (www.clamav.net) — Command-line virus scanner with database update features. The clamav package is in the Fedora repository (yum install clamav).
- * Klamav (http://klamav.sourceforge.net/klamavwiki/index.php) — The KDE version of ClamAV (yum install clamav).
- * Third-party ClamAV Apps (www.clam.net/3rdparty.html) — Find links to third-party software that works with ClamAV.

## Using SpamAssassin

With SpamAssassin, you can configure your incoming mail service to tag messages it believes to be spam so you and your users can deal with those messages as you choose.

There are several methods that SpamAssassin uses to identify spam:

- * Checking mail headers — Examining the headers of your incoming mail to look for spam.
- * Checking text — Examining the content of the message body.
- * Checking blacklists — Checking against known spam IP lists.
- * Checking signatures — Comparing message signatures against known spam patterns.

### Setting up SpamAssassin on your

To set up SpamAssassin, you first need to ensure the service is installed and configured. Here are the steps to get it running on your server:

1. Make sure that SpamAssassin is running. If it isn't, start it by typing the following:
```bash
# ckconfig spamassassin
```

2. Create an .procmailrc file (using any text editor). This file defines how to handle filtered mail. For example:
```bash
:0fw
/usr/bin/spam
```

3. Check the /etc/spamassassin/local.cf file. This file contains rules that are used system-wide, unless they are overridden by a user's individual $HOME/.spamassassin/user_prefs.cf file. Here are the contents of local.cf:

```
required_hits 5
report_safe 0
rewrite_header Subject [SPAM]
```

In SpamAssassin, a scoring system is used to guess whether a particular message is spam or not. The required_hits lines show that a score of 5 is needed to flag the message as spam. You should set it for a public mail server (such as higher for 8 or 10). Setting rewrite_header Subject [SPAM] has SpamAssassin add the text [SPAM] to the Subject line of finds.

Because false-positives occur, you risk your users from seeing an e-mail if they need to do system-wide filtering. To avoid this problem, the approach shown here lets the user decide what to do with an e-mail tagged as spam. Users can even adjust their threshold for when a message is believed to be spam.
