
# Chapter 10: Understanding System Administration

- /etc/alternatives — Contains links the alternatives facility uses to enable a system administrator to exchange one service with another in a way that is invisible to users.
- /etc/amanda — Contains files and directories that allow the amanda facility to do network backups of Linux and UNIX systems.
- /etc/cron* — Directories in this set contain files that define how cron runs applications on a daily (cron.daily), hourly (cron.hourly), monthly (cron.monthly), or weekly (cron.weekly) schedule.
- /etc/cups — Contains files that are used for the CUPS printing service.
- /etc/default — Contains files that set default values for various utilities. For example, the file for useradd command defines the default group number, home directory, password expiration date, shell, and skeleton directory (/etc/skel) that are used when creating a new user account.
- /etc/httpd — Contains a variety of files used to configure the behavior of Apache Web server (specifically, the httpd daemon process).
- /etc/init.d — Contains links to the run-level scripts. These scripts are linked from files in the /etc/rc? directories to where each service has a script started or stopped for the particular run. The ? is replaced by the run-level number (0 through 6).
- /etc/mail — Contains files used to configure your mail service.
- /etc/pcmcia — Contains configuration files that allow you to have a variety of PCMCIA configured for your computer. (PCMCIA slots are openings on your laptop that allow you to have card-sized cards attached to your computer. You can attach devices as modules and external CD-ROMs).
- /etc/postfix — Contains configuration files for the postfix mail transport agent.
- /etc/ppp — Contains several configuration files to set up Point-to-Point protocol (so that you can have your computer dial out to the Internet).
- /etc/rc?.d — There is a rc?.d directory for each valid system state: rc0.d (shutdown state), rc1.d (single-user state), rc2.d (multiseruser state), rc3.d (multiseruser networking), rc4.d (user-defined state), rc5.d (multiseruser, networking), and rc6.d (reboot state).
- /etc/security — Contains files that set a variety of security conditions for your computer. These files are part of the pam (pluggable authentication modules package.
- /etc/skel — Any files included in this home directory when a user is added to the system. By default, most of these files are dot (.) files, such as .kde (a directory for setting KDE desktop defaults) and .bashrc (for setting default values used by the bash shell).

- /etc/squid — Contains configuration files for the Squid proxy caching server.
- /etc/sysconfig — Imports system configuration files that are created and maintained by various services (including iptables, samba, and most networking services).
- /etc/uucp — Contains configuration files for Taylor UUOCP (a nonstandard version of the uuccp utility that is used to create modem, direct line, and other serial connections with other).
- /etc/vsftpd — Contains configuration files to set up the vsftpd FTP server.
- /etc/xinetd.d — Contains a set of files, each of which defines a network service daemon listens on a particular port. The xinetd daemon process receives a request for a service, it uses the information in these files to determine daemon processes to handle the request.

## Administrative log files

One of the things Linux does is well track of itself. This is a good thing when you consider how much can go wrong with a complex operating system. Sometimes you are trying to get a new facility to work and fails giving you the foggiest reason why. Other times you want to monitor your system to see if people are trying to access your computer. In any of those cases, you can use log files to help track the problem. The main utilities for logging and debugging for Linux are the syslog and klog. General system logging is done by syslog. Logging that is specific to kernel activity is done by klog. Logging is done according to information in the /etc/syslog.conf file. As root user, you can view log files with the less command or watch messages as they enter using the tail command (tail -f /var/log/messages).

You don't hear much about other logins (besides root) being used with Linux. was a fairly common practice in UNIX systems to have different logins that allowed administrative tasks among users. In any case, these administrative logins are available with Linux, so you may want to look into them because individual software packages such as bind, squid, and amanda set permissions for their log files based on their administrative logins.

## Understanding administrative logins

Here are some of the administrative logins that are configured automatically for Linux systems. By tradition, these logins are assigned numbers up to 100:

- This user can control printing features. Having a separate lp allows someone other than the super user to do things like remove lp spool files. The home directory for lp is /var/spool/lp.
- This user can work with e-mail features. The mail group has permissions to use mail files in /var/spool/mail (which is also the mail user's home directory).
- This user owns various commands (used as the primary method for dial-serial communications). It is the owner of log files in /var/log/uucp, spool files in /var/spool, administrative commands (such as uucch, uuico, and uuqt) in /usr/bin. The home directory for uucp is /var/spool/uucp.
- This user has many commands in /bin in traditional UNIX systems. This is not the case in Fedora and RHEL root tends to own most executable files. The home directory of bin is /bin.
- This user could do administration of news services, depending on how you set permission for /var/spool/news and other news-related resources. The directory for news is /etc/news.

## Using sudo for administrative privilege

One way to get full or limited privileges to any non-root user is to set up the sudo facility. That simply adding the user to /etc/sudoers and defining what privilege you want that to have. The user can run any command he or she is privileged to by preceding that command with the sudo command.

The following is an example of how to use the sudo facility to access any users that are added to the wheel group to have root privileges:

### As the root user

 /usr/bin/visudo

By default, the file is opened in vi, unless your EDITOR variable happens to be set to some other editor acceptable to visudo (for example, export EDITOR=ged). The reason for using visudo is that the command will lock /etc/sudoers file and do some basic sanity-checking of the file to ensure it was edited correctly.

NOTE: If you are stuck here, refer to the tutorial (Using the vi Text Editor) in Chapter 4 for help.

2. Uncomment the following line to allow users in the group named wheel to have root privileges over the computer:

```
%wheel ALL=(ALL) ALL
```

The previous line causes the user to be prompted for a password to be allowed to use administrative commands. To allow users in the wheel group to have privilege without using a password, uncomment the following line instead:

```
%wheel ALL=(ALL) NOPASSWD: ALL
```

3. Save the changes to the /etc/sudoers file.

4. Still as root user, open the /etc/group file in any text editor and add the users you want to have root privilege over the wheel. For example, if you want to add the users mary and jake to the wheel group, the line would appear as follows:

```
wheel:x10:root,mary,jake
```

At this point, the users mary and jake can run the sudo command to run commands, or parts of commands, that are normally restricted to the root user. The following is an example of a session by the user jake after he has been assigned sudo privileges:

```
[jake]$ sudo mount /mnt/win

We trust you have received the usual lecture from the local System Administrator. It usually boils down to these two things:

1) Respect the privacy of others.
2) Think before you type.

Password: ********
[jake]$ mount /mnt/win
mount: only root can mount /dev/sda on /mnt/win
[jake]$ sudo mount /mnt/win
[jake]$
```

In the preceding session, the user jake runs the sudo command so he can unmount the /mnt/win file system (using the um command). He is given a warning and asked to provide his password (this is jake's password, not the root password).
