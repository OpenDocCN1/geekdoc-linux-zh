# Verifying installed packages with rpm

If something in a software package not working properly, or if you suspect that your system has been tampered with, use the (-V) option of rpm can help you verify installed software against its original software package. Information about each installed package is stored on your computer in the RPM database. By using the verify option, you can check whether any changes were made to the components in the package.

> NOTE: verify option uses the uppercase letter (-V), while the verbose option uses the lowercase (-v).

Various file size and permissions are done during a verify operation. If everything is fine, there is no output. Any components that have changed when they were installed will be printed along information how they were changed. Here's an example:

```
# rpm -V ppp
S.5....T. c /etc/ppp/chap-secrets
S.5....T. c /etc/ppp/options
S.5....T. c /etc/ppp/pap-secrets
```

This output shows that the ppp package (used to dial a TCP/IP network such as the Internet) has three files changed since it was. The notation at the beginning shows that the file size (S), the MD5 sum (M) and the modification time (T) have all changed. The letter c shows these are all configuration files. By reviewing these files to see that the changes were the only that I made to get PPP working, I can verify that the software is okay.

The indicators you may see when you verify the contents of a configuration file:

- 5 (MD5 Sum) — An MD5 checksum indicates a change to the file contents.
- S (File size) — The number of characters in the file has changed.
- L (Symlink) — The file has become a symbolic link to another file.
- T (Mtime) — The modification time of the file has changed.
- D (Device) — The file has a device special file.
- U (User) — The user name that owns the file has changed.
- G (Group) — the group assigned to the file has changed.
- M (Mode) — If the ownership or permission of the file has changed.

> TIP: A utility is available to browse the contents of RPM files from Microsoft Windows. With the rpmbrowser.exe utility, you can list and extract files from an RPM distribution. This utility is available from winsite.com (search for rpmbrowser from http://www.winsite.com/search).

# Understanding software package names and formats

Whenever possible, you want to install the applications you use Fedora from software packages in RPM format (.rpm extension). However, if an RPM is not available, the software you want may come in other package formats.

Say you downloaded a file from the Internet that contains lots of names, numbers, dots, gzs, and tars. What does all that mean? Well, when you break it down, it's not really that complicated.

Most of the archives containing Linux applications follow the GNU-style package-naming conventions. The following example illustrates the packaging-naming format:

```
mywebapp-4.2.3-1.i86.rpm
mywebapp-4.2.3.tar.gz
mywebapp-4.2.3.src.tar.gz
mywebapp-4.2.3.bin.SPARC.tar.gz
mywebapp-4.2.3.bin.ELF.static.tar.gz
```

These examples represent different packages of the same application. The name of this package is mywebapp: a set of numbers that represent the version of the package. In this case, it is version 4.2.3 (the major version number is 4, followed by minor version number and patch level 2.3). After the version number is a dot, followed by some optional parts, which are followed by indicators of how the file is archived and compressed.

The first line shows a package that is in the RPM Package Management (.rpm) format. .i86 before the .rpm indicates that the package contains binaries that are to run Intel i386 architecture computers (in other words, PCs). The -1 indicates the build level (the same package may have been rebuilt multiple times to make minor changes). The sidebar "Using Binary RPMs versus Building from Source" for the pros and cons of using prebuilt RPM binary packages as opposed to compiling the program yourself.

# Using Binary RPMs versus Building from Source

Binaries created in RPM format are easily installed, managed, and uninstalled tools such as rpm and yum. This is the recommended installation method for Fedora and RHEL novices. Sometimes, however, building an application from source code may be preferable. Here are some arguments on both sides:

- Installing applications from a binary RPM archive is easy. After the application is installed, there are both shell commands and GUIs for managing, verifying, updating, and removing the RPM package. You don't need to know anything about Makefiles or compilers. When you install a binary RPM package, RPM tools even check to make sure that other packages the package depends on are installed. Because Red Hat has released RPM under the GPL, other Linux distributions also use it to distribute their software. Thus, most Linux distributions are, or will be, available in RPM format.
- Source code — Not all source code are made into RPM binaries. If you use RPM, you may find software that is several versions old, when you could simply download the latest source code and run a few commands. Also, by modifying source code, you can tailor the package to better suit your needs.

Refer to Appendix A for obtaining source code for Fedora RPM binary packages that come on the DVD with this book. You can modify that source code yourself and rebuild the RPM binaries. The rebuilt binaries can be tuned to your hardware and include the features you want with the package. For more information on RPMs, refer to the Red Hat RPM Guide by Eric Foster-Johnson (Red Hat Press/Wiley, 2003).

In the next two lines of the previous example, each file contains source code for the package. The files that make up the package were archived using the tar command (`.tar`) and compressed using the gzip command (`.gz`). You use these two commands (or just the tar command with the `-z` option) to expand and unpack the packages when you are ready to install them.

Between the version number and the `.tar.gz` extension there can be optional tags, separated by dots, which provide specific information about contents of the package. In particular, if the package is a binary version, this information provides details about where the binaries will run. In the third line, the optional `.src` tag was added because the developer wanted to differentiate between the source and binary versions of the package. In the fourth line, `.bin.SPARC` detail indicates that it is a binary package, ready to run on a SPARC
