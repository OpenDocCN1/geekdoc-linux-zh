
# Using a simple squid.conf

You can use the /etc/squid.conf file that comes with Squid to get started.
Although the file contains lots of comments, the actual settings in that file are quite manageable. The following paragraphs describe the contents of the default squid.conf file:

```
http_port 3128
```

The http_port identifies the port on which Squid listens for HTTP client requests. The normal port to use (which is the default) is 3128. Optionally, you can add a hostname (such as example.com:3128) or IP address (such as 10.0.0.1:3128) to limit allowed incoming requests to those made to a particular host or IP address.

```
hierarchy_stoplist cgi-bin ?
```

The hierarchy_stoplist tag indicates that when a string of characters appears in a URL, the content should be obtained from the original server and not from a cache peer. In this example, requests for the cgi-bin and the question mark (?) are all forwarded to the originating server.

```
acl QUERY urlpath_regex cgi-bin \\
cache deny QUERY
```

The preceding lines can be used to cause URLs containing characters to be cached. Those also with the previous line by not caching URLs containing the same strings (cgi-bin and ?) are all sought from the original server.

```
acl apache rep_header Server ^Apache
acl src 0.0.0.0/0.0.0
acl manager proto cache_object
acl localhost src 127.0.0.1/255.255.255
```

The acl tags allow you to create access controls. The first line in the preceding code creates an access list called apache and assigns response headers ^Apache to the apache acl. After that, the all acl is defined to handle all IP addresses. The next line assigns the manager acl to handle the cache_object protocol. The localhost source is assigned to the IP address of 127.0.0.1.

```
access_log /var/log/squid/access.log
```

The preceding line identifies the location of the Squid access.log file. As the name implies, this file contains messages about requests to access the Squid server.

Squid includes default settings for how long types of content in cache are considered to be fresh. The following refresh_pattern values are included in the squid.conf file:

```
refresh_pattern ^ftp: 1440 20% 10080
refresh_pattern ^gopher: 1440 0% 1440
refresh_pattern . 0 20% 4320
```

To make sure this simple Squid configuration is running, follow this procedure:

- 1. On the Squid server, restart the squid daemon. To do this, use /etc/init.d/squid restart. (If Squid is not running, use start instead of restart).
- 2. On the Squid server, start your connection to the Internet (if it is not already running).
- 3. On a client computer on your network, use Firefox (or another Web browser) to use the Squid server as a proxy (described later in this chapter). In Firefox, select Edit -> Preferences -> Advanced and click the Network tab, then choose Settings. From the Connection Setting window that pops up, select Manual proxy configuration. Add the Squid server's computer name and, by default, port 3128 to each protocol. You can also check the Use proxy server for all protocols option to use the same proxy for all service requests from the browser.
- 4. On the client computer, try to open any Web page on the Internet with the browser you just configured.

# Modifying the Squid configuration file

If you want to start a more complex set of access permissions for Squid, you should start with the default squid.conf configuration file (described earlier).

To begin, open the /etc/squid/squid.conf file (as the root user). You will see a lot of information describing the values that you can set in this file. Most of the tags that you need to configure Squid are used to set up caching and provide access to your proxy server.

> TIP: Don't change the squid.conf.default file! If you really mess up your squid.conf file, you can start again by making another copy of this file squid.conf. If you want to recall exactly what changes you have made so far, try the following from the /etc/squid directory:
```bash
# diff squid.conf squid.conf.default | less
```
This will show you the differences between your actual squid.conf and the version you started with.

# Configuring access control in squid.conf

To protect your computing resources from being used by anyone, Squid requires that you define which hosts have access to your HTTP (Web) services. By default, all hosts are denied access to Squid for the local host. With the acl tag, you can create access lists. Then, with the http_access tag, you can authorize access to HTTP (Web) services for the access lists you create.

The form of the access control list (acl) is:

```
acl name type string
ac name type file
```

The name is any you want to assign to the list. A acl is a string of text, and file is a file of information that applies to the particular type of acl. Valid acl types include dst, src, dstdomain, srcdomain, url_path, url_time, port, proto, method, browser, and user.
Several access lists are set up by default. You can use these assigned acl names to assign permissions to HTTP or ICP services. You can also create your own acl names to assign to those services. The default acl names from the /etc/squid/squid.conf that you can use or change:

```
acl all src 0.0.0.0/0.0.0
acld manager proto cache_object
acld localhost src 127.0.0.1/255.255.255
acld SSL_ports port 443
acld Safe_ports port 80
acld Safe_ports port 21
acld Safe_ports port 443
acld Safe_ports port 210
acld Safe_ports port 1025-65535
acld Safe_ports port 280
acld Safe_ports port 488
acld Safe_ports port 591
acld Safe_ports port 777
```

# Configuring access control in squid.conf

To protect your computing resources from being used by anyone, Squid requires that you define which hosts have access to your HTTP (Web) services. By default, all hosts are denied access to Squid for the local host. With the acl tag, you can create access lists. Then, with the http_access tag, you can authorize access to HTTP (Web) services for the access lists you create.

The form of the access control list (acl) is:

```
acl name type string
ac name type file
```

The name is any you want to assign to the list. A acl is a string of text, and file is a file of information that applies to the particular type of acl. Valid acl types include dst, src, dstdomain, srcdomain, url_path, url_time, port, proto, method, browser, and user.
Several access lists are set up by default. You can use these assigned acl names to assign permissions to HTTP or ICP services. You can also create your own acl names to assign to those services. The default acl names from the /etc/squid/squid.conf that you can use or change:

```
acl all src 0.0.0.0/0.0.0
acld manager proto cache_object
acld localhost src 127.0.0.1/255.255.255
acld SSL_ports port 443
acld Safe_ports port 80
acld Safe_ports port 21
acld Safe_ports port 443
acld Safe_ports port 210
acld Safe_ports port 1025-65535
acld Safe_ports port 280
acld Safe_ports port 488
acld Safe_ports port 591
acld Safe_ports port 777
```

When Squid tries to determine which a cache falls in, it goes from top to bottom. In the first line, all hosts (address/netmask are all zeros) are added to the acl group. In the second line, you create a group called manager that has access to your_object. The localhost is assigned to your loopback address. Secure socket layer (SSL) ports are assigned to the numbers 443 and 563, where Safe_ports are assigned to the numbers above. The last line defines a group called CONNECT (which you can use to allow access to ports).

To allow or deny HTTP services on the Squid server, the following definitions are set up:

```
http_access allow localhost
http_access deny manager
http_access deny !Safe_ports
http_access deny CONNECT !SSL_ports
http_access allow localhost
http_access deny all
```

These definitions are quite restrictive. The first line allows someone requesting cache objects (manager) from the local host to do so, but the second line denies anyone else making such a request. Access is not denied to ports defined as safe. Also, secure socket connections via the proxy are denied on all ports, except for SSL ports (SSL_ports). HTTP access is permitted only from the local host and to all other hosts.

To allow the client computers on your network to access your HTTP service, you need to create your own http_access entries. You probably want to do something more restrictive than simply saying http_access allow all. Here is an example of a more restrictive acl group and how to assign that group to HTTP access:

```
acl ourlan src 10.0.0.1-10.0.0.100
http_access allow ourlan
```

In the previous example, all computers at IP addresses 10.0.0.1 through 10.0.0.100 are assigned to the ourlan group. Access is then allowed for ourlan with the http_access line.
