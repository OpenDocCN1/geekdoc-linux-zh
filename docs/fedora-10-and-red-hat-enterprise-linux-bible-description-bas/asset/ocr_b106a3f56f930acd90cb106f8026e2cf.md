# Part III: Administering Fedora and RHEL

The example host.allow contains the first two types of client specification. The entry 199.170.177. will match any IP address that begins with that string, such as 199.170.177.25. The client entry.linuxxtoys.net will match hostnames such as jukebox.linuxxtoys.net or picframe.linuxxtoys.net.

Let's examine what happens when a host named jukebox.linuxxtoys.net (with IP address 199.170.179) connects to your Fedora system using the Telnet protocol:

+   1. xinetd receives the connection request.

+   2. xinetd begins comparing the address and name of jukebox.linuxxtoys.net to the rules listed in /etc/hosts.allow. It starts at the top of the file and works its way down the file until a match found. Both daemon (the program handling the network service on Fedora) and the connecting client's IP address or name must match the information in the hosts.allow file. In this case, the second rule that is encountered matches:

```
in.telnetd: 199.170.177., .linuxxtoys.net
```

+   3. Jukebox is not in the 199.170.177 subnet, but it is in the linuxxtoys.net domain. xinetd stops searching the file as if finds this match.

> CAUTION: While xinetd acts as a convenient example with xinetd, do not run the telnet service due to security concerns. Enable ssh for remote logins. See the later section on using the secure shell package for o sh.

How about if you connect to your box using the CUPS-lpd protocol? In this case, matches none of the rules in hosts.allow; the only line that refers to the lpd daemon does not refer to the 199.170.179 subnet or to the linuxxtoys.net domain. xinetd continues on the hosts.deny file. The entry ALL: matches anything, so tcpd denies the connection.

The wildcard will allow anyone to use the hosts.allow file. In this case, we are telling xinetd to permit absolutely anyone to connect to the FTP service on the Linux box. This is appropriate for running an anonymous FTP server that anyone on the Internet can access. If you are not an anonymous FTP site, you should probably not use the ALL flag.

A good rule of thumb is to make your hosts.allow and hosts.deny files as restrictive as possible and explicitly allow only those services you really need. Using the ALL flag for grant access to a particular service may be easier than tying in a long list of subnets, but better a few minutes spent on proper security measures than many hours recovering from a break-in.

> TIP: You can restrict access to services using various options within the /etc/xinetd.conf file, even to the point of limiting access to certain specific times of the day. Read the manual page for xinetd (by typing man xinetd at a command prompt) to learn more about these options.
