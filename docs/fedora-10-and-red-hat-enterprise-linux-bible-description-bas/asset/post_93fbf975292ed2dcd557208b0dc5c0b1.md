# Mounting noauto file systems

In /etc/fstab there can also be devices for other file systems that are not mounted automatically. For example, you might have multiple disk partitions on your hard disk or an NFS shared file system that you might want mount only occasionally. A noauto system can be mounted manually. The advantage is that when you type the mount command, you can type less information and have the rest filled in by the contents of the /etc/fstab. So, for example you:

```
# mount /oak/apps
```

With this command, mount knows to check the /etc/fstab to get the file system to mount (oak:/apps, nfs), and the options to use with the mount (in this case ro for read-only). Instead of typing the local mount point (/oak/apps), you could have typed the remote name oak:/apps instead, and had other information filled in.

> TIP: When naming mount points, including the name of the remote NFS server can help you remember where the files are actually stored. This may not be possible if you are sharing home directories (/home) or mail directories (/var/spool/mail).

# Using mount options

You can add mount options to the /etc/fstab (to a mount command line itself) to impact how the file system is mounted. When you add options to /etc/fstab, they must be separated by commas. The following are some options that are valuable for mounting NFS file systems:

- hard: With this option, if the NFS server disconnects or goes down while a process is waiting to access it, the process will hang until the server comes up. This option is helpful if it is critical that the data you are working with is not out of sync with the programs that are accessing it.
- soft: This is the default. If the NFS server disconnects or goes down, a process trying to access data from the server will time out after a set period of time.
- rsize: The number of bytes read at time from NFS server. The default is 1024. Using a larger number (such as 8192) will get you better performance on a network that is fast (such as LAN) and relatively error-free (that is, doesn't have a lot of collisions).
- wsize: The number of bytes written at time from NFS server. The default is 1024. Performance issues are the same as rsize option.
- timeout: Sets the time a timeout occurs where # represents a number in tenths of a second. The default value is 60. Each successive timeout doubles the value up to 60 seconds. You should increase this value if you believe that timeouts are occurring because of slow response from the server or a slow network.
- retrans: Sets the number of retransmissions before a major timeout. When a major timeout occurs, the process is either aborted (soft) or a Server Not responding message appears on your screen. The default is 3.
- time: Sets how many minutes to retry failed mount requests, where # is replaced by the number of minutes. The default is 10000 (which is about one week).
- background: If the first mount attempt times out, all subsequent mounts in the background. This option is very valuable if you are mounting slow or sporadically available file systems. By placing mount requests in the background, Fedora or RHEL can continue to mount other file systems instead of waiting for the current one to complete.

> NOTE: If needed mount point is missing, timeout occurs. For example, if you mount /usr/extra and NFS/extra is not yet mounted, /usr/extra will come up and mount on the next retry.
- foreground: If the first mount attempt times out, subsequent mounts in the foreground is the default behavior. Use this option if it is imperative that the mount must be successful before continuing (for example, if you are mounting /usr).
- no: Any of the options that don't require a value can have no prepended to the opposite effect. For example, nobind indicates that the mount should not be done in the background.

# Using autofofs to mount NFS file systems on demand

Recent improvements to auto-detecting and mounting removable devices have meant that you can simply insert or plug in devices to have them detected, mounted, and displayed. However, to make the process of detecting and mounting remote file systems automatic, you will still need to use a facility such as autofofs. If it is not installed, you can install the autofs package with the yum install autofs command.

# With the autofofs configured and turned on, you can cause any NFS shared directories to mount on. If you know the hostname and directory being shared by another computer, you can simply change (cd) to the autofofs mount directory (/net by default) and have the shared resource automatically mount and be accessible to you.

The following steps explain how to turn on autofofs:

1. As root user from a Terminal, open the /etc/auto.master file and look for a line that appears as follows:

```
/net      -hosts
```

This causes the /net directory to act as the mount point for NFS shared directories (If there is a comment character at the beginning of that line, remove it).

2. Start the autofofs service by typing the following as root user:

```
# service autofofs start
```

3. Set up the autofofs service to restart every time you boot your system:

```
# systemconfig autofofs on
```

Believe it or not, that's all you have to do. Provided that you have a connection to the NFS servers from which you want to share directories, you can try to access a shared NFS directory. For example, if you know that the /usr/local/share directory is being shared from the computer by your network shuttle, do the following:

1. Type the following:

```
$ cd /net/shuttle
```

If the named shuttle has any shared directories that are available to you, you will be able to successfully change to that directory. Another thing to note is that you could use an IP address instead of a hostname (for example, cd /net/10.0.0.1).

2. Type the following:

```
$ ls
usr
```

You should be able to see that the usr directory is part of the path to a shared directory. If there are shared directories from other top-level directories, you should see those as well (such as /var or /home). Of course, seeing any of those directories is dependent on how security is set up on the server.

3. Next, you could try going straight to the shared directory. For example:

```
$ cd /net/shuttle/usr/local/share
$ ls
info music television
```

At this point, the ls should reveal the contents of the /usr/local/share directory on the computer named shuttle. What you can do with that content depends on how it was configured for sharing.

# Unmounting file systems

After an NFS file system is mounted, unmounting it is simple. You use the umount command with either the local mount point or the remote file system. For example, here are two ways you could unmount maple:/home/files:

```
# umount maple:/home/files
# umount /media/files
```

Either will work. If maple:/home/files is mounted automatically (from a listing in /etc/fstab), it will be remounted the next time Fedora or RHEL. If it was a temporary mount (or listed as noauto in /etc/fstab), it will be remounted at boot.

> TIP: The command is not unmount, it is umount.

If you get the message device busy when you try to unmount a file system, it means the mount fails because the file system is being used. Most likely, one of the directories in the NFS file system is the current directory for your shell (or the shell of someone else on your system). The other possibility is that a command is holding an open file in the NFS file system. Check your Terminal windows and other shells, and cd out of the directory if you are in it, or just close the Terminal windows.

If an NFS file won't unmount, you can force unmount it (umount -f /media/files) or unmount and clean up later (umount -l/media/files). The -l option is the better choice because a forced unmount can disrupt a file modification that is in progress.
