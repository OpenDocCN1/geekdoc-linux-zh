## Configuring HTTP logging

You can set several relative values related to logging of Apache information. When a relative path is named, the directory set by ServerRoot (/etc/httpd/ by default) is appended (for example, /etc/httpd/logs/error.log). As shown in the following example, you can set the location of error logs, the level of log warnings, and log nicknames:

```
# ErrorLog: The location of the error log file.
# If you do not specify an ErrorLog directive within a <VirtualHost>
# container, error messages relating to that virtual host will be
# logged here. If you *do define an error logfile for a <VirtualHost>
# container, that host's errors will be logged and not here.

# ErrorLog/error_log

# LogLevel: Control the number of messages logged to the error_log.
# Possible values include: debug, info, notice, warn, error, crit,
# alert, emerg.

LogLevel warn

# The following directives define some format nicknames for use with
# a CustomLog directive (see below).
LogFormat "%h %l %u \%r\" %s %b %{Referer}i\"-%%%%{User-Agent}i" combined
LogFormat "%h %l %u \%r\" %s %b" common
LogFormat "%{Referer} -> %u" referer
LogFormat "%{User-agent}i"

# Location and format of the access logfile (Common Log Format).
# If you do not define any access logfiles within a <VirtualHost>
# container, they will be logged. Conversely, if you *do
# define per-<VirtualHost> access logfiles, transactions will be
# logged therein and *not* in this file.

# CustomLog logs/access_log common

# If you would like to have separate agent and referer logfiles,
# uncomment the following directives.
```

These lines deal with how server errors, client tracking, and incoming requests are logged. The ErrorLog directive, which can specify an absolute path to a name or path relative to the ServerRoot (which is /etc by default), where the server should show error messages. In this case the file is logs/error_log, which extends to /etc/http/logs/error_log (which in reality is a symlink to the error_log file in the /var/log/httpd directory).

The LogLevel controls the severity and quality of messages that appear in the log. Messages are ranged from the verbose debug log level to the particularly emerg log levels. The default value of warn is a good choice for normal use (it will only log significant events that eventually require operator intervention), but info and debug if access-control mechanism is used, or if the number of active servers have changed. With emerg, only critical system-level failures that panic conditions for the server are logged.

The level specified by the LogLevel directive indicates the least-severe message that will be logged — all messages at that severity and above are recorded. For example, if LogLevel is set to warn, the error log will contain messages at the warn, error, crit, alert, and emerg levels. The default value of warn is info and debug are perfect for testing a server's configuration or tracking down the exact location of errors.

The four LogFormat lines define (for later use) four types of log file formats: combined, common, referer and. You can also add a fifth format called combined. The tokens available within the LogFormat directive are described in Table 21-5. The LogFormat definitions can be modified to your own personal preference, and other custom formats can be created as needed.

| --- | --- |

| %b | The number of bytes sent to the client (excluding header information). |
| %(VAR)e | The contents of the environment variable VAR. |
| %f | The filename referenced by the requested URL. |

| Token | Description |

The common format includes the hostname or IP address, the username as reported by the ident daemon, the local time at which the request was made, the actual HTTP request, the response code, and the number of bytes transferred. This format is useful for storing connection-related entries in one file. The combined format includes all the information from the other log formats into one line. This format, which is defined by default, can be enabled (by removing the # character) to log the actual number of bytes (%I) and sent (%s), provided the mod_log module is loaded.

The CustomLog directive assigns one of the LogFormats to a filename, as specified in an absolute path or a relative name to the ServerRoot. The only uncomment definition assigns combined format to the /etc/http/logs/access_log. To retain or refer information, uncomment the definitions. You could also choose to uncomment the CustomLog logs/access_log combined and use the definition for the common format.

# Adding a signature

Any page generated by the Apache server can have a signature line added to the bottom of the page. Examples of server-generated pages include a directory listing, error page, a status page, or an info page. The ServerSignature directive can be set to On, Off, or Email. Here is how ServerSignature appears by:

```
# Optionally add a line containing the server version and
# host name to server-generated pages (error documents, FTP
# listings, mod_status and mod_info output etc., but not CGI generated
# documents).
# Set to "Email" to also include a mailto: link to the ServerAdmin.
# Set to one of: On | Off | Email
ServerSignature On
```

With ServerSignature On, a line similar to the following appears at the bottom of server-generated pages:

```
Apache/2.2.8 (Fedora) Server at toys.linxtoys.net Port 80
```

With ServerSignature set to Email, a link to the Web page's administrative e-mail account is added to the signature line (the server name becomes the link). If the directive is set to Off, the line does not appear at all. With SSL or webdav enabled, this information will appear in the server signature as well. In general, it's best to reveal as little information as possible on Internet-facing servers (so it may be best to leave these off).
