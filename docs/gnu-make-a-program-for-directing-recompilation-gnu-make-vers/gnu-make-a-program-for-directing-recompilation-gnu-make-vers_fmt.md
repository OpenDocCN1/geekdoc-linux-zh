## 1.2 问题与错误

如果你在使用 GNU `make` 时遇到问题，或者认为你发现了一个错误（bug），请向开发者报告；我们无法保证会采取任何行动，但我们可能想要修复它。

在报告错误之前，请确保你确实是发现了一个真实的错误。仔细重新阅读文档，查看它是否真的说明你可以执行你正在尝试的操作。如果你不确定是否应该执行某项操作，也请报告；那是文档中的一个错误！

在报告错误或尝试自行修复之前，请尝试将其隔离在能够重现该问题的最小制式文件（`makefile`）中。然后，将这个较小的 `makefile` 以及 `make` 输出给你的确切结果发送给我们。在生成此 `makefile` 时，请确保不要在命令中使用任何非免费或不寻常的工具：你几乎可以使用简单的 shell 命令来模拟此类工具的功能。最后，请务必解释你预期的发生情况；这将帮助我们判断问题是否真的出在文档中。

一旦你确定了精确的问题，请发送电子邮件至：

```
bug-make@gnu.org
```

请包含你正在使用的 `make` 版本号。你可以通过命令 `make --version` 获取此信息。请务必包含你正在使用的机器类型和操作系统。

# 第 2 章：Makefile 简介

## 2 Makefile 简介

你需要一个名为 `makefile` 的文件来告诉 `make` 要做什么。大多数情况下，`makefile` 告诉 `make` 如何编译和链接一个程序。

在本章中，我们将讨论一个简单的 `makefile`，它描述了如何编译和链接一个由 8 个 C 源文件和 3 个头文件组成的文本编辑器。`makefile` 还可以可以在被显式要求运行时运行杂杂命令（例如，删除某些文件作为清理操作）。要查看更复杂的 `makefile` 示例，请参阅附录 C [Complex Makefile]，第 157 页。

当 `make` 编译编辑器时，每个更改过的 C 源文件都必须重新编译。如果头文件发生了变化，为了安全起见，包含该头文件的每个 C 源文件都必须重新编译。每次编译都会产生一个与源文件对应的对象文件。最后，如果任何源文件被重新编译，所有的对象文件（新生成的或从之前的编译保存的）都必须链接在一起，以生成新的可执行编辑器。

### 2.1 规则的样貌

一个简单的 `makefile` 由具有以下形状的“规则”组成：

```
target ... : prerequisites
command
...
```

`target`（目标）通常是程序生成的文件的名称；目标的示例包括可执行文件或对象文件。`target` 也可以是要执行的操作的名称，例如 `clean`（参见第 4.4 节 [Phony Targets]，第 27 页）。

`prerequisite`（前提条件）是作为创建目标所需的输入文件。一个目标通常依赖于多个文件。



`command`（命令）是 `make` 执行的操作。一个规则可以有多个命令，每个命令单独占一行。请注意：你需要在每行命令的开头输入一个制表符（`tab character`）！这是一个会让疏忽者出错的模糊之处。

通常，命令位于一个带有前提条件的规则中，并在当任何前提条件发生变化时用于创建目标文件。然而，指定目标命令的规则可能没有前提条件。例如，与目标‘`clean`’相关的包含删除命令的规则就没有前提条件。

因此，规则解释了如何以及何时删除作为该特定规则目标的某些文件。`make` 执行前提条件上的命令以创建或更新目标。规则也可以解释如何以及何时执行某操作。参见第 4 章 [Writing Rules]，第 19 页。

`makefile` 可能包含规则之外的文本，但简单的 `makefile` 只包含规则。规则看起来可能比此模板中显示的稍微复杂一些，但它们大体都符合该模式。

## 2.2 简单的 Makefile

这是一个直观的 `makefile`，它描述了一个名为 `edit` 的可执行文件依赖于 8 个对象文件，而这些对象文件又依赖于 8 个 C 源文件和 3 个头文件。

在这个示例中，C 文件包含了 'defs.h'，但只有定义编辑命令的文件包含了 'command.h'，只有更改编辑器缓冲的底层文件包含了 'buffer.h'。

```
edit : main.o kbd.o command.o display.o \
    insert.o search.o files.o utils.o
    cc -o edit main.o kbd.o command.o display.o \
    insert.o search.o files.o utils.o

main.o : main.c defs.h
    cc -c main.c
kbd.o : kbd.c defs.h command.h
    cc -c kbd.o
command.o : command.c defs.h command.h
    cc -c command.o
display.o : display.c defs.h buffer.h
    cc -c display.o
insert.o : insert.c defs.h buffer.h
    cc -c insert.c
search.o : search.c defs.h buffer.h
    cc -c search.o
files.o : files.c defs.h buffer.h command.h
    cc -c files.o
utils.o : utils.c defs.h
    cc -c utils.o

clean:
    rm edit main.o kbd.o command.o display.o \
    insert.o search.o files.o utils.o
```

我们使用反斜杠加换行将每行拆分为两行；这类似于使用了一行长代码，但更容易阅读。

使用此 `makefile` 来创建一个名为 `edit` 的可执行文件，输入：

`make`

使用此 `makefile` 删除可执行文件和所有对象文件，输入：

`make clean`

```
edit : main.o kbd.o command.o display.o \
```

## 2.4 变量让 Makefile 更简单

在我们的示例中，我们必须在 '`edit`' 规则中列出两次所有的对象文件（如下）：

```
edit := main.o kbd.o command.o display.o \
    insert.o search.o files.o utils.o
    cc -o edit main.o kbd.o command.o display.o \
    insert.o search.o files.o utils.o
```

这种重复很容易出错；如果系统添加了新的对象，我们可能会将其添加到其中一个列表而忘记另一个。我们可以通过使用变量来消除风险并简化 `Makefile`。变量允许定义一次文本字符串，并在以后多次替换（参见第 6 章 [How to Use Variables]，第 55 页）。

每个 `Makefile` 的标准做法是名为 `objects`、`OBJECTS`、`objs`、`OBJ` 或 `OBJ` 的变量，它是所有对象文件的名称列表。我们会在 `Makefile` 中通过如下行定义这样的 `objects` 变量：

```
objects := main.o kbd.o command.o display.o \
    insert.o search.o files.o utils.o
```

然后，在每个想要放置对象文件名称列表的地方，我们都可以通过编写 `$(objects)` 来替换变量的值。

当你使用变量来定义对象文件时，完整的简单的 `Makefile` 如下：



```
objects = main.o kbd.o command.o display.o \
    insert.o search.o files.o utils.o

edit : $(objects)
    cc -o edit $(objects)
main.o : main.c defs.h
    cc -c main.c
kbd.o : kbd.c defs.h command.h
    cc -c kbd.c
command.o : command.c defs.h command.h
    cc -c command.c
display.o : display.c defs.h buffer.h
    cc -c display.c
insert.o : insert.c defs.h buffer.h
    cc -c insert.c
search.o : search.c defs.h buffer.h
    cc -c search.c
files.o : files.c defs.h buffer.h command.h
    cc -c files.c
utils.o : utils.c defs.h
    cc -c utils.c

clean:
    rm edit $(objects)
```

### 2.5 让 make 推断命令

没有必要显式写出编译每个 C 源文件的命令，因为 make 可以推导出它们：它有一条隐式规则，可以使用 `cc -c` 从同名的 `.c` 文件更新 `.o` 文件，例如，它将使用命令 `cc -c main.c main.o` 来将 `main.c` 编译为 `main.o`。因此，我们可以从对象文件的规则中省略这些命令。参见第 10 章 [使用隐式规则]，第 101 页。

当 `.c` 文件以这种方式自动使用时，它也会自动添加到依赖项列表中。因此，我们可以从依赖项列表中省略 `.c` 文件，并省略命令。

以下是完整的示例，包含了上述两个更改，并使用了上面建议的 `objects` 变量：

```
objects = main.o kbd.o command.o display.o \
  insert.o search.o files.o utils.o
```

```
edit : $(objects)
  cc -o edit $(objects)
```

```
main.o : defs.h
kbd.o : defs.h command.h
command.o : defs.h command.h
display.o : defs.h buffer.h
insert.o : defs.h buffer.h
search.o : defs.h buffer.h
files.o : defs.h buffer.h command.o
utils.o : defs.h
```

```
.PHONY : clean
clean
  rm edit $(objects) in actual.
```

这就是我们编写 Makefile 的方式（与 `clean` 相关的描述在别处。参见第 4.4 节 [伪目标]，第 27 页，以及第 5.4 节 [命令中的错误]，第 44 页。）

由于隐式规则非常方便，它们非常重要。你会经常看到它们。

### 2.6 另一种 Makefile 风格

当 Makefile 的对象通过隐式规则创建时，可以使用另一种 Makefile 风格。在这种风格的 Makefile 中，我们根据依赖项对条进行分组，而不是根据目标分组。它的样子如下：

```
objects = main.o kbd.o command.o display.o \
  insert.o search.o files.o utils.o
```

```
edit : $(objects)
  cc -o edit $(objects)
```

```
$(objects) : defs.h
kbd.o command.o files.o : command.h
display.o insert.o search.o files.o : buffer.h
```

在这里，`defs.h` 被给出所有对象文件的依赖项；`command.h` 和 `buffer.h` 是列出的特定对象文件的依赖项。

这种方式是否更好取决于个人喜好：它更紧凑，但有些人不喜欢它，因为他们认为将关于每个目标的所有信息放在一个地方更清晰。

### 2.7 清理目录的规则

编译程序并不是你可能编写规则的唯一事情。Makefile 通常除了编译程序外还会告诉如何执行其他几件事：例如，如何删除所有对象文件和可执行文件，以便目录保持“干净”。

以下是我们如何为示例编辑器编写清理 make 规则的：

```
clean:
rm edit $(objects)
```

在实践中，我们可能想以稍微复杂的方式编写规则，以处理意外情况。我们会这样做：

```
.PHONY : clean
clean:
-rm edit $(objects)
```

这可以防止 make 被一个名为 `clean` 的实际文件搞混，并导致它在出现 `rm` 错误的情况下继续执行。（参见第 4.4 节 [伪目标]，第 27 页，以及第 5.4 节 [命令中的错误]，第 44 页。）

这样的规则不应该放在 Makefile 的开头，因为我们不希望它默认运行！因此，在示例 Makefile 中，我们希望 `edit` 规则（重新编译编辑器的规则）保持默认目标。

由于 `clean` 不是 `edit` 的依赖项，如果我们提供不带参数的 `make` 命令，此规则将完全不会运行。为了让规则运行，我们必须输入 `make clean`。参见第 9 章 [如何运行 make]，第 89 页。

### 3.6 覆盖另一个 Makefile 的模式

有时，拥有一个与另一个 Makefile 类似的 Makefile 是很有用的。你通常可以使用 `include` 指令将一个包含在另一个，并添加更多目标或变量定义。然而，如果两个 Makefile 为同一个目标给出了不同的命令，make 不允许你这样做。还有另一种方法。

在包含的 Makefile（想要包含另一个的）中，你可以使用匹配任意模式的规则，为了重新构建任何无法从包含 Makefile 中的信息构建的目标，make 应该在另一个 Makefile 中查找。关于模式规则的更多信息，请见第 10.5 节 [模式规则]，第 109 页。

例如，如果你有一个名为 `Makefile` 的文件，显示了如何制作目标 `foo`（以及其他目标），你可以写一个名为 `makefile` 的文件，其中包含：

```

```

```make

	$$(MAKE) -f Makefile $$

```

如果你说 `make foo`，make 将找到 `GNUmakefile`，读取它，并发现要制作 `foo`，它需要运行命令 `frobnicate > foo`。如果你说 `make bar`，make 在 `GNUmakefile` 中找不到制作 `bar` 的方法，因此它将使用来自模式规则的命令：`make -f Makefile bar`。如果 `Makefile` 提供了一个更新 `bar` 的规则，make 将应用该规则。对于任何其他 `GNUmakefile` 不知道如何制作的目标，也是如此。

这种工作原理是，模式规则具有一个模式 `%` 的模式，因此它可以匹配任何内容。该规则指定了一个前提条件 `force`，以确保即使目标文件已存在也会执行这些命令。我们为 `force` 目标提供了空命令，以防止 make 搜索隐式规则来构建它——否则它会将相同的匹配规则应用到 `force` 本身，从而导致前提条件循环。

### 3.7 make 如何读取 Makefile

GNU make 分两个不同的阶段执行工作。在第一阶段，它读取所有的 makefile、包含的 makefiles，并内部化所有变量及其值、隐式规则和显式规则，并为所有目标及其前提条件构建依赖图。在第二阶段，make 使用这些内部结构来确定哪些目标需要重新构建，并调用执行这些操作所需的规则。

# 4 编写规则

规则出现在 Makefile 中，说明了何时以及如何重新制作某些文件，这些文件被称为规则的**目标**（通常每个规则只有一个目标）。它列出了作为目标前提的其他文件，以及用于创建或更新目标时使用的命令。

通过自动搜索多个目录来查找先置条件。当你在目录之间重新分配文件时，你不需要更改单个规则，只需要更改搜索路径。

### 4.3.1 VPATH：所有先置条件的搜索路径

make 变量 `VPATH` 的值指定了 make 应该搜索的目录列表。通常，这些目录预计包含不在当前目录中的先置条件文件；然而，VPATH 指定的是一个 make 应用于所有文件的搜索列表，包括作为规则目标的文件。

因此，如果一个文件被列为目标或先置条件，且在当前目录中不存在，make 会在 `VPATH` 中列出的目录中搜索同名文件。如果在其中一个目录中找到了该文件，则该文件可能成为先置条件（见下文）。规则可以像文件存在于当前目录一样，指定先置条件列表中的文件名。见第 4.3.4 节 [编写 Shell 命令]，第 25 页。

在 `VPATH` 变量中，目录名用冒号或空格分隔。目录列出的顺序是 make 在搜索时遵循的顺序。（在 MS-DOS 和 MS-Windows 上，使用分号作为 VPATH 中目录名的分隔符，因为冒号可以用于路径本身，位于驱动器字母之后。）

例如，

```
VPATH = src../headers
```

指定了一个包含两个目录 `src` 和 `../headers` 的路径，make 会顺序对它们进行搜索。

使用此 `VPATH` 值时，以下规则：

```
foo.o = foo.c
```

其解释方式类似于写成：

```
foo.o = src/foo.c
```

假设文件 `foo.c` 不在当前目录中，但在 `src` 目录中找到。

### 4.3.2 vpath 指令

与 `VPATH` 变量类似、但选择性更强的是 `vpath` 指令（注意是小写），它允许你为特定类的文件名指定搜索路径：即匹配特定模式的文件名。因此，你完全可以为一类文件名搜索某些目录，而为其他文件名搜索其他目录（或不搜索任何目录）。

`vpath` 指令有三种形式：

- `vpath pattern directories`：为匹配模式的文件名指定搜索路径目录。搜索路径 `directories` 是要搜索的目录列表，用冒号（MS-DOS 和 MS-Windows 上用分号）或空格分隔，与 VPATH 变量中使用的搜索路径相同。

- `vpath pattern`：清除与模式关联的搜索路径。



`vpath`：清除之前通过 `vpath` 指令指定的所有搜索路径。

`vpath pattern` 是一个包含 `%` 字符的字符串。该字符串必须匹配正在搜索的先置条件的文件名（类似于模式中的字符匹配任意零个或多个字符的序列（在模式规则中；见第 10.5 节 [定义和重新定义模式]，第 109 页））。

例如，`%.h` 匹配以 .h 结尾的文件（如果没有 `%`，则模式必须精确匹配先置条件，这通常并不常见）。

`vpath` 指令模式中的 `%` 字符可以用前面的反斜杠 (`\`) 进行转义。原本会转义 `%` 字符的反斜杠可以用更多的反斜杠进行转义。用于转义 `%` 字符或其他反斜杠的反斜杠在与文件名比较之前会从模式中移除。没有转义 `%` 字符风险的反斜杠则保持不变。

当先置条件在当前目录中不存在时，如果 `vpath` 指令的模式匹配先置条件的文件名，则搜索该指令中的目录，其方式类似于（且早于）`VPATH` 变量中的目录。

例如，

```
vpath %.h ../headers
```

告诉 `make` 如果在当前目录未找到文件，则在目录 `../headers` 中查找任何以 .h 结尾的先置条件。

如果多个 `vpath` 模式匹配先置条件的文件名，`make` 将逐个执行匹配的 `vpath` 指令，搜索每个指令中提到的所有目录。`make` 按照它们在 Makefile 中出现的顺序处理多个 `vpath` 指令；具有相同模式的多个指令之间是相互独立的。

因此，

```
vpath %.c foo
vpath %   blish
vpath %.c bar
```

将先在 `foo` 中查找以 .c 结尾的文件，然后是 `blish`，然后是 `bar`，然后：

```
vpath %.c foo:bar
vpath %     blish
```

将先在 `foo` 中查找以 .c 结尾的文件，然后是 `bar`，然后是 `blish`。

### 4.3.3 目录搜索是如何执行的

通过目录搜索找到先置条件时，无论何种类型（通用或选择性），定位的路径可能并非先置条件列表中实际提供给你的路径。有时，通过目录搜索发现的路径会被丢弃。

用于决定保留还是放弃通过目录搜索找到的路径的算法如下：

- 1. 如果目标文件在 Makefile 指定的路径不存在，则执行目录搜索。
- 2. 如果目录搜索成功，则保留该路径并将该文件暂存为目标。
- 3. 使用相同方法检查该目标的所有先置条件。
- 4. 在处理完先置条件后，目标可能需要也可能不需要重建：
  - 如果目标不需要重建，则在目录搜索期间找到的文件路径将用于任何包含该目标的先置条件列表。简而言之，如果 `make` 不需要重建目标，你就会使用通过目录搜索找到的路径。
  - 如果目标需要重建（已过期），则目录搜索期间找到的路径将被丢弃，并使用 Makefile 中指定的文件重建目标。简而言之，如果 `make` 必须重建，则目标将在本地重建，而不是在目录搜索找到的目录中重建。

这个算法看起来很复杂，但在实践中它恰恰是你想要的。

其他版本的 `make` 使用更简单的算法：如果文件不存在且通过目录搜索找到，无论目标是否需要构建，始终使用该路径。因此，如果目标需要重建，它将在目录搜索期间发现的路径处创建。

如果实际上这正是你对部分或所有目录所期望的行为，你可以使用 `PATH` 变量来指示这一点，或者 `-PATH` 具有与 `VPATH` 相同的语法和格式（即由空格或冒号分隔的路径列表）。如果在同时也出现在 `PATH` 中的目录中通过目录搜索发现了过期的目标，则该路径不会被丢弃。

### 4.3.4 编写 Shell 命令

当通过目录搜索在另一个目录找到先置条件时，这不会改变规则的命令；它们将按原写的方式执行。因此，你必须仔细编写命令，以便它们能在 `make` 找到先置条件的目录中查找。

这是通过自动变量 `$^` 实现的（见 [自动变量]，第 111 页）。例如，`$^` 的值是所有先置条件的列表，包括它们所在的目录名称，而 `$@` 的值是目标。因此：

```
foo.o : foo.c
  cc $(CFLAGS) ^ -o $@
```

### 4.3.5 目录搜索与隐含规则

通过 `VPATH` 或 `vpath` 指定目录搜索也会发生在考虑隐含规则期间（见第 10 章 [隐含规则]，第 101 页）。

例如，当文件 `foo.o` 没有显式规则时，`make` 会考虑隐含规则，例如编译 `foo.c` 的内置规则。如果该文件在当前目录缺失，则会对相应的目录进行搜索。如果 `foo.c` 存在于任何目录中（或在 Makefile 中提到），则应用 C 编译的隐含规则。

隐含规则的命令通常会使用自动变量；因此它们无需额外努力就能使用目录搜索找到的文件名。

### 4.3.6 链接库的目录搜索

目录搜索以特殊方式应用于与链接器使用的库。当你编写一个名称形式为 `-lname` 的先置条件时，这一特殊功能就会生效。（你可以判断出发生了异常，因为先置条件通常是文件名，而库的文件名通常看起来像 `libname.a`，而不是 `libname.o`）。

当先置条件的形式为 `-lname` 时，`make` 会对其进行特殊处理，在当前目录、由匹配的 `vpath` 搜索路径指定的目录以及 `VPATH` 搜索路径指定的目录中进行搜索，最后在 `/lib`、`/usr/lib` 和 `prefix/lib` 目录（通常为 `/usr/local/lib`，但 MS-DOS/MS-Windows 版本的 `make` 取决于 `prefix` 定义为 DJG 安装树的根目录）中搜索文件 `libname.so`。

# 第 4 章：编写规则

如果未找到该文件，则将在与上方相同的目录中搜索 `libname.a` 文件。

例如，如果你的系统上存在 `/usr/lib/libcurses.a` 库（且没有 `/usr/lib/libcurses.so` 文件），

```
foo foo.c -lcurses
cc $ -o $
```

当 `foo` 比 `foo.c` 旧或比 `/usr/lib/libcurses.a` 旧时，这将会导致执行命令 `cc foo.c /usr/lib/libcurses.a -o foo`。

虽然默认的待搜索文件集是 `libname.so` 和 `libname.a`，但此可以通过 `.LIBPATTERNS` 变量进行自定义。该变量中的每个单词都是一个模式字符串。当看到像 `-name` 这样的前提条件时，`make` 会将列表中每个模式中的 `%` 替换为 `name`，并使用该库文件名执行上述目录搜索。如果没有找到相应的库，则将使用列表中的下一个单词。

`.LIBPATTERNS` 的默认值为 `'lib%.so lib%.a'`，它提供了上述描述的默认行为。

你可以通过将此变量设置为空值来完全关闭库扩展。

### 4.4 伪目标 (Phony Targets)

伪目标（phony target）不是一个真实的文件名。它只是在收到显式请求时执行某些命令的名称。使用伪目标目标有两个原因：避免与同名文件冲突，以及提高性能。

如果你编写的规则其命令不会创建该目标，那么每当该目标需要重新制作时，这些命令都会被执行。这里有一个示例：

```
clean:
rm *.temp
```

由于 `rm` 命令不会创建一个名为 `clean` 的文件，可能永远不会存在这样的文件。因此，每当你说 `make clean` 时，`rm` 命令都会被执行。

如果此目录中任何操作创建了名为 `clean` 的文件，伪目标将停止工作。由于它没有前提条件，文件 `clean` 将不可避免地被认为是最新的，其命令将不会被执行。为了避免这个问题，你可以使用特殊目标 `.PHONY` 显式声明该目标为伪目标（参见第 4.7 节 [特殊内置目标]，第 30 页），如下所示：

- `.PHONY: clean`

一旦完成，无论是否存在名为 `clean` 的文件，`make clean` 都会运行命令。

```
SUBDIRS = foo bar baz

.PHONY: subdirs $(SUBDIRS)

subdirs: $(SUBDIRS)

$(SUBDIRS):
  $(MAKE) -C $$$

foo: baz
```

# 第 4 章：编写规则

在这里我们还声明了 `foo` 子目录在 `baz` 子目录完成之前不能构建；这种关系声明在尝试并行构建时尤为重要。

伪目标不应该是真实目标文件的前提条件；如果是 true 的，那么每当 `make` 尝试更新该文件时，它的命令都会运行。只要伪目标从不是真实目标的前提条件，伪目标的命令就只会在伪目标作为指定目标时执行（参见第 9.2 节 [指定目标的参数]，第 89 页）。

伪目标可以有前提条件。当一个目录包含多个程序时，在 makefile `.Makefile` 中描述所有程序是最方便的。由于默认情况下重新制作的目标将是 makefile 中的第一个，通常会将此伪目标命名为 `all`，并将所有单独程序作为其前提条件。例如：



```
all : prog1 prog2 prog3
.PHONY : all

prog1 : prog1.o utils.o
cc -o prog1.o utils.o

prog2 : prog2.o
cc -o prog2 prog2.o

prog3 : prog3.o sort.o utils.o
cc -o prog3.o sort.o utils.o
```

现在你只需要说 `make` 就可以重新制作所有三个程序，或者作为参数指定要制作的程序（例如 `make prog1 prog3`）。

当一个伪目标是另一个伪目标的前提条件时，它充当后者的子程序。例如，这里的 `make cleanall` 将删除对象文件、差异文件以及文件 `program`：

```
cleanall : cleanobj cleandiff
rm program

cleanobj :
rm *.o

cleandiff :
rm *.diff
```

### 4.5 无命令或前提条件的规则

如果一个规则没有前提条件或命令，且该规则的目标是一个不存在的文件，那么 `make` 将认为每当运行其规则时，该目标已更新。这意味着所有依赖于此目标的目标都将执行其命令。

一个示例将说明这一点：

```
clean FORCE
rm $(objects)
```

`FORCE`:

目标 `FORCE` 满足特殊条件，因此依赖于它的目标 `clean` 被强制运行其命令。`FORCE` 这个名字并没有特殊之处，但它是这种常用的名称。

正如你所看到的，这样使用 `FORCE` 的结果与使用 `.PHONY: clean` 相同。

使用 `.PHONY` 更加显式且高效。然而，其他版本的 `make` 不支持 `.PHONY`；因此 `FORCE` 出现在许多 `makefile` 中。参见第 4.4 节 [伪目标]，第 27 页。

### 4.6 用于记录事件的空目标

空目标是伪目标的一种变体；它用于通过其最后修改时间记录命令最后一次执行的时间。与伪目标不同，此文件可以存在；但它的内容并不重要，且通常为空。空目标的目的是执行一个你显式请求的操作。空目标应该有一些前提条件（否则没有意义）。其命令通常是 `touch` 以更新目标。这里有一个示例：

```
print: foo.c bar.c
touch
```

### 4.7 特殊内置目标名称

某些名称作为目标出现时具有特殊含义。

#### `.PHONY`

特殊目标 `.PHONY` 的前提条件被认为是伪目标。当需要考虑此类目标时，无论文件是否存在或其最后修改时间如何，`make` 都会无条件运行其命令。参见第 4.4 节 [伪目标]，第 27 页。

#### `.SUFFIXES`

特殊目标 `.SUFFIXES` 的前提条件是用于检查后缀规则的后缀列表。参见第 10.7 [旧式后缀规则]，第 117 页。

#### `.DEFAULT`

为 `.DEFAULT` 指定命令用于任何未找到规则（显式规则或隐含规则）的目标。参见第 10.6 节 [最后手段]，第 116 页。指定了 `.DEFAULT` 命令，每个作为前提出现但未作为规则目标的文件，都将代其执行这些命令。参见第 10.8 节 [隐含搜索算法]，第 118 页。

#### `.PRECIOUS`

`.PRECIOUS` 依赖的目标将受到以下特殊处理：如果在执行其命令期间 `make` 被杀死或中断，目标将不会被删除。第 5.5 节 [中断或杀死 make]，第 46 页。此外，如果目标是一个中间文件，在它不再需要时将不会被删除，正如通常执行的那样。参见第 10.4 节 [隐含规则链]，第 108 页。在这一点上它与 `.SECONDARY` 目标重叠。

你也可以列出隐含规则的目标模式（例如将 `%.o` 作为特殊目标 `.PRECIOUS` 的前提文件），以保留匹配该文件名的中间文件。

#### `.INTERMEDIATE`

`.INTERMEDIATE` 依赖的目标被视为中间文件。参见第 10.4 节 [隐含规则链]，第 108 页。没有前提条件的 `.INTERMEDIATE` 无影响。

#### `.SECONDARY`

`.SECONDARY` 依赖的目标被视为中间文件，不同之处是它们从不会被自动删除。参见第 10.4 节 [隐含规则链]，第 108 页。

没有前提条件的 `.SECONDARY` 会导致所有目标都被视为二级目标（即没有目标因为被认为是中间文件而被删除）。

#### `DELETE_ON_ERROR`

如果 `DELETE_ON_ERROR` 在 `Makefile` 的任何地方被提及目标，那么当规则的目标发生变化且其命令以非零退出状态结束时，`make` 将删除该目标，就像它接收到信号时一样。参见第 5.4 节 [命令中的错误]，第 44 页。

#### `IGNORE`

如果你为 `.IGNORE` 指定了依赖项，那么 `make` 将忽略这些特定文件在执行命令时产生的错误。`.IGNORE` 的命令是没有意义的。

如果作为没有依赖项的目标被提到，`.IGNORE` 表示忽略所有文件在执行命令时的错误。这种对 `.IGNORE` 的用法仅为了兼容历史版本。由于这会影响 `Makefile` 中的每条命令，因此并不有用；我们建议使用更具选择性的方法来忽略特定命令的错误。参见第 5.4 节 [命令中的错误]，第 44 页。

#### `SILENT`

如果你为 `.SILENT` 指定了依赖项，那么 `make` 将在执行重制这些特定文件之前不打印命令。`.SILENT` 的命令是没有意义的。

如果作为没有依赖项的目标被提到，`.SILENT` 表示在执行任何命令之前不打印它们。这种对 `.SILENT` 的用法仅为了兼容历史版本。我们建议使用更具选择性的方法静默特定命令。参见第 5.1 节 [命令回]，第 41 页。如果你想在某次运行 `make` 时静默所有命令，请使用 `-s` 或 `--silent` 选项（参见第 9.7 节 [选项总结]，第 95 页）。

#### `EXPORT_ALL_VARIABLES`

只需作为目标提及，即可告诉 `make` 默认将所有变量导出到子进程。参见第 5.6.2 节 [向子 make 传递变量]，第 47 页。

#### `NOTPARALLEL`

如果 `NOTPARALLEL` 被提及目标，则本次 `make` 调用将串串行运行，即使给出了 `-j` 选项。任何递归调用的命令仍将并行运行（除非其 `Makefile` 包含此目标）。它的任何依赖项将被忽略。

任何定义的隐式规则后缀如果作为目标出现，也被视为特殊目标，两个后缀的连接（例如 `.c.o`）也是如此。这些目标是后缀，是一种定义隐式规则的过时方法（但仍被广泛使用）。原则上，任何目标名称如果被拆分为两部分并将两部分都添加到后缀列表中，都是特殊的。在实践中，后缀通常以 `.` 开头，因此这些特殊目标名称以 `.` 开头。参见第 10.7 节 [旧式后缀规则]，第 117 页。

### 4.8 规则中的多个目标

具有多个目标的规则等于编写许多规则，每个规则都有一个目标，除外它们都完全相同。相同的命令适用于所有目标，但它们的效果各异，因为你使用 `$0` 在命令中替换实际的目标名称。该规则为所有目标贡献相同的依赖项。

这在两种情况下有用：

- 你想要依赖项但不需要命令。例如：

```
kbd.o command.o files.o: command.h
```

这为提到的三个对象文件中的每个文件提供额外的依赖项。

- 相似的命令适用于所有目标。命令不需要完全相同，因为自动变量 `$0` 可以用于在命令中替换要重制的特定目标（参见第 10.5.3 节 [自动变量]，第 111 页）。例如：

```
bigoutput : text.g
generate text.g -$(sub output,$0) > $0
```

等同于

```
bigoutput : text.g
generate text.g -big > bigint
littleoutput : text.g
generate text.g -little > littleoutput
```

我们假设假设程序 `generate` 生成两种输出，一个给定 `big`，另一个给定 `little`。参见第 8.2 节 [字符串替换与分析函数]，第 76 页，关于 `sub` 函数的解释。

假设你想根据目标来更改依赖项，就像变量 `$0` 允许你更改命令一样。你不能在普通规则中通过多个目标来实现这一点，但可以通过静态模式规则实现。参见第 4.10 节 [静态模式规则]，第 34 页。

### 4.9 同一个目标的多个规则

一个文件可以是多个规则的目标。所有规则中提到的依赖项将合并为该目标的依赖项列表。如果目标比任何规则中的任何依赖项都旧，则执行命令。

一个文件只能执行一组命令。如果有多个规则为同一个文件提供了命令，`make` 将使用最后给出的一组命令并打印错误信息。（作为一个特殊情况，如果文件名以 `.` 开头，则不打印错误信息。这种奇怪的行为仅是为了兼容其他实现……你应该避免使用它。）有时，让同一个目标调用在 `Makefile` 不同部分定义的多个命令是有用的；你可以使用双冒号规则（参见第 4.1 节 [双冒号]，第 37 页）来实现。



一个带有依赖项的额外规则可以一次性为多个文件提供额外的依赖项。例如，`Makefile` 通常有一个变量（如 `objects`），包含了正在构建的系统中所有编译器输出文件的列表。如果 `config.h` 变化，说明它们都必须重制的简单方法是写如下内容：

```
objects = foo.o bar.o
```

文件名（参见第 8.2 节 [字符串替换与分析函数]，第 76 页）：

```
files = foo.elc bar.o lose.o

$(filter %o,$(files)): %o: %c
$(CC) -c $(CFLAGS) $<$
$(filter %.elc,$(files)): %.elc
emacs -f batch-byte-compile $<
```

在此示例中，`'$(filter %o,$(files))'` 的结果是 `'bar.o lose.o'`，静态模式规则会导致这些对象文件每一个都通过编译对应的 C 源文件来更新。`'$(filter %.elc,$(files))'` 的结果是 `'foo.elc'`，因此该文件是根据 `'foo.elc'` 生成的。

另一个示例展示了如何在静态模式规则中使用 `$$`：

```
bigoutput littleoutput : %output : text.g
generate text.g -* $$
```

当运行 `generate` 命令时，`$$` 将展开为目标干部（stem），即 `'big'` 或 `'little'`。

### 4.10 静态模式规则与隐式规则

静态模式规则与定义为模式规则的隐式规则有许多共同点（参见第 10.5 节 [定义与重新定义模式规则]，第 109 页）。两者都包含一个目标的模式和一个用于构造依赖项名称的模式。区别在于 `make` 如何决定何时应用该规则。

隐式规则可以适用于任何匹配其模式的目标，但它只有在目标没有其他指定的命令时，且只有在可以找到依赖项时才会生效。如果出现多个隐式规则被认为适用，则只应用其中一个；选择取决于规则的顺序。

相比之下，静态模式规则适用于你在规则中指定的**精确列表**。它不会适用于任何其他目标，并且一如不变地适用于每一个指定的目标。如果存在两个冲突的规则都适用，且两者都包含命令，则这是一个错误。

出于以下原因，静态模式规则可能比隐式规则更好：

- 你可能希望为某些文件覆盖通常的隐式规则，这些文件的名称无法在语法上进行分类，但可以给出一个显式列表。
- 如果你无法确定你正在使用的目录的确切内容，你可能不确定哪些无关文件会导致 `make` 使用错误的隐式规则。选择可能取决于隐式规则搜索的顺序。使用静态模式规则则不存在不确定性；每条规则都精确适用于所指定的目标。

### 4.11 双冒号规则

双冒号规则在目标名称后使用 `::` 而不是 `:`。当同一个目标出现在多个规则中时，它们的处理方式与普通规则不同。

当一个目标出现在多个规则中时，所有规则类型必须相同：全都是普通规则，或者全都是双冒号规则。如果是双冒号规则，则每一条都是相互独立的。如果目标比该规则的任何依赖项都旧，则执行该双冒号规则的命令。如果该规则没有依赖项，则其命令将始终被执行（即使目标已经存在）。这可能导致执行没有、任何一个或所有双冒号规则。具有相同目标的双冒号规则实际上是相互分离的。每条双冒号规则都是单独处理的，就像具有不同目标的规则一样。一个目标的双冒号规则按照它们在 `makefile` 中出现的顺序执行。然而，双冒号规则真正有意义的情况是执行命令的顺序无关紧要的情况。双冒号规则有些晦涩，且并不经常有用；它们提供了一种机制，用于更新目标的方法取决于是哪个依赖文件导致了更新的情况，而这种情况非常罕见。每条双冒号规则都应该指定命令；如果没有指定，如果存在隐式规则，将使用隐式规则。参见第 10 章 [使用规则]，第 101 页。

### 4.12 生成依赖项

在程序的 `makefile` 中，你需要编写的许多规则通常只说明对象文件依赖于某些头文件。例如，如果 `'main.c'` 通过 `include` 使用了 `'defs.h'`，你会写道：

```
main.o: defs.h
```

你需要这条规则，以便 `make` 知道每当 `defs.h` 变化时都必须重新制作 `'main.o'`。你可以看到，对于一个大型程序，你需要在 `makefile` 中编写几十条这样的规则，并且在每次添加或删除 `include` 时必须非常小心地更新 `makefile`。为了避免这种麻烦，现代 C 编译器可以通过查看源文件中的 `include` 行来为你编写这些规则。通常这通过给编译器的 `-M` 选项实现。例如，命令：

```
cc -M main.c
```

生成输出：

```
main.o : main.c defs.h
```

因此，你不再需要自己编写所有规则。编译器会为你完成。注意，`makefile` 中提到 `'main.o'` 的此类依赖项永远不会被隐式规则搜索视为中间文件。这意味着 `make` 在使用该文件后不会将其删除；参见第 10.4 节 [隐式规则链]，第 108 页。

在旧的 `make` 程序中，传统做法是使用此编译器功能通过类似 `'make depend'` 的命令按需生成依赖项。该命令会创建一个名为 `'depend'` 的文件，包含所有自动生成的依赖项；然后 `makefile` 可以包含它们（参见第 3.3 节 [Include]，第 12 页）。在 GNU `make` 中，重新制作 `makefiles` 功能使得这种做法变得过时——你不需要显式让 `make` 重新生成依赖项，因为它会重新生成任何过期的 `makefile`。

### 5.5 中断或杀死 make

如果 make 在执行命令时接收到致命信号，它可能会删除该命令本应更新的目标文件。如果目标文件的最后修改时间自 make 第一次检查以来发生了变化，则会执行此操作。

删除目标的目的是确保在下次运行 make 时能够从头开始重新生成它。为什么要这样做呢？假设在编译器运行时你按了 Ctrl-c，它已经开始写入一个对象文件 'foo.o'。Ctrl-c 杀死编译器，导致产生一个不完整的文件且最后修改时间比源文件 'foo.c' 新。但 make 也会接收到 Ctrl-c 信号并删除这个不完整的文件。如果 不这样做，下一次调用 make 就会认为 'foo.o' 不需要更新——导致链接器在尝试链接一个部分缺失的对象文件时，给出一个奇怪的错误信息。

你可以通过让特殊目标 `.PRECIOUS` 依赖于目标文件来防止这种对目标文件的删除。在移除目标之前，make 会检查它是否出现在 `.PRECIOUS` 的先决列表中，并决定在发生信号时是否删除该目标。你可能这样做的一些原因可能是：目标是以某种原子方式更新的，或者仅用于记录修改时间（其内容并不重要），或者必须一直存在以防止其他类型的问题。

### 5.6 make 的递归使用

递归使用 make 意味着在 Makefile 中将 make 作为命令使用。当你为各种子系统分离 Makefile 以组合一个更大的系统时，这种技术非常有用。例如，假设你有一个名为 'subdir' 的子目录，它有自己的 Makefile，并且你希望父目录的 Makefile 在子目录上运行 make。你可以通过以下代码实现：

```
cd subdir && $(MAKE)
```

或者等效地（参见第 9.7 节 [选项摘要]，第 95 页）：

```
$(MAKE) -C subdir
```

你可以复制这个示例来编写递归 make 命令，但关于它们如何工作以及为什么，以及子 make 与顶层 make 之间的关系，有很多需要了解。

为了方便起见，GNU 为你将变量 `CURDIR` 设置为当前工作目录的路径。如果生效CC，它将包含新目录的路径，而不是原始路径。该值的优先级与它在 makefile 中设置时相同（默认情况下，环境变量 `CURDIR` 不会覆盖此值）。请注意，设置此变量对 make 的操作没有影响。

### 5.6.1 MAKE 变量是如何工作的

递归 make 命令始终应该使用变量 `MAKE`，而不是具体的命令名 'make'，如下所示：

```
cd subdir && $(MAKE)
```

该变量的值是调用 make 时的文件名。如果该文件名为 '/bin/make'，那么执行的命令就是 'cd subdir && /bin/make'。如果你使用特殊版本的 make 来运行顶层 makefile，那么在递归调用时将执行相同的特殊版本。

作为一个特殊特性，在规则的命令中使用变量 `MAKE` 会改变 '-t' (''--touch'')'-n' (''--just-print'')和'-q' (''--question'')选项的效果。使用 `MAKE` 的效果与在命令行开头添加一个 `+` 相同。请参见第 9.3 节 [代替执行命令]，第 91 页。

考虑上述示例中的命令 `-t`。'-t' 选项将目标标记为已更新，而不实际运行任何命令（第 9.3 节 [代替执行]，第 91 页）。遵循 '-t' 的通常定义，示例中的 `make -t` 命令将创建一个名为 'subsystem' 的文件，但这需要执行 'cd subdir && make -t' 命令行，而 '-t' 表示不执行。

这一特殊特性使其达到了你想要的结果：只要规则的命令行中包含变量 `MAKE`，标志 '-t'、'-n' 和 '-q' 就不作用于该行。尽管存在让大多数命令不运行的标志，但包含 `MAKE` 的命令行也会被正常执行。通常的 `FLAGS` 机制会将标志传递给子 make（参见第 5.6.3 节 [将选项传递给子 make]，第 49 页），因此你对触碰文件或打印命令的请求会传播到子系统。

### 5.6.2 将变量传递给子 make

顶层 make 的变量值可以通过环境通过显式导出（export）传递给子 make。这些变量在子 make 中被定义为默认值，但除非你使用第 9.7 节 [选项摘要]，第 95 页中的 '-e' 切换，否则它们不会覆盖子 make 使用的 makefile 中指定的内容。

要传递或导出变量，会将其名称和值添加到运行每个命令的环境中。子 make 反而使用环境初始化其变量值表。参见第 6.9 节 [来自环境的变量]，第 66 页。

除非显式请求，否则 make 仅在变量在环境中定义或在命令行上设置，且其名称仅由字母、数字和下划线组成时才会导出。特殊变量 `SHELL` 和 `MAKEFLAGS` 总是导出的。

如果你想导出所有变量，可以使用特殊目标 `.EXPORT_ALL_VARIABLES` 代替使用 `export` 指令。旧版本的 make 会忽略这一点，而 `export` 指令会导致语法错误。

如果你想导出带有非字母数字字符的变量，必须在 `export` 指令中显式提到它们。这是因为默认行为只导出由字母、数字和下划线组成的变量。

如果你不想导出变量，可以使用 `unexport` 指令。由于这是默认行为，只有在之前使用过 `export`（可能在某个包含的文件中）时才需要这样做。你不能单独使用 `export` 和 `unexport` 来让某些命令导出变量而另一些命令不导出。最后出现的 `export` 或 `unexport` 指令将决定整个 make 运行期间的行为。

作为一个特殊特性，变量 `MAKELEVEL` 在逐级向下传递时会发生。该变量的值是一个字符串，表示层级的十进制数字。顶层 make 的值为 '0'；子 make 为 '1'；子子 make 为 '2'，依此类推。增量发生在 make 为命令设置环境时。

`MAKELEVEL` 的主要用途是在条件指令中测试它（参见第 7 章 [Makefile 的条件部分]）。

你可以使用变量 `MAKEFILES` 导致所有子 make 命令使用额外的 makefiles。`MAKEFILES` 的值是一个由空白分隔的文件列表。该变量如果在外层 Makefile 中定义，将通过环境向下传递；然后它作为子 make 在读取常规或特殊文件之前读取的额外 makefile 列表。参见第 3.4 节 [变量 MAKEFILES]，第 13 页。


为了历史兼容性，还存在一个类似的变量 `MFLAGS`。它的值与 `MAKEFLAGS` 相同，不同在于它不包含行定义，且除非它为空，否则它总是以连字符开头（当 `MAKEFLAGS` 以没有单字母版本的选项开头时，例如 `--warn-undefined-variables`，它也会以连字符开头）。`MFLAGS` 传统被显式用于递归 make 命令，如下所示：

如果你在环境中设置了 `MFLAGS`，应确保不要包含任何剧烈影响 make 操作并破坏 Makefile 目的的选项。例如，`-t`、`-n` 和 `-q` 选项可能会产生破坏性后果。

## 5.7 定义命令序列 (Canned Command Sequences)

当相同的命令序列在多个目标中有用时，你可以使用 `define` 指令将其定义为命令序列，并在这些规则中引用该命令序列。命令序列实际上是一个变量，因此其名称不能与其他变量冲突。

以下是一个定义命令序列的示例：

```
define run-yacc
yacc $(firstword $)
mv y.tab.c $$
undef
```

这里 `run-yacc` 是被定义的变量名；`undef` 标记定义的结束；之间的行就是命令。`define` 指令不会展开命令序列中的变量引用和函数调用；`$` 字符、括号等都会成为你所定义变量的一部分。参见第 6.8 节 [定义变量]，第 65 页以获取 `define` 的完整解释。

此示例中的第一个命令在使用该序列的任何规则上运行 Yacc。Yacc 的输出始终是 'y.tab.c'。第二个命令将输出移动到目标文件名。

要使用命令序列，将变量替换到规则的命令中。你可以像替换其他变量一样替换它（见第 6.1 节 [变量引用基础]，第 55 页）。由于由 `define` 定义的变量会被递归展开，你在 `define` 内部编写的所有变量引用现在都会展开。例如：

```
foo:y
$(run-yacc)
```

当 `foo.y` 在 run-yacc 的值中出现时，它会被替换为 `$`，而 `foo.c` 会替换为 `$$`。这是一个真实的示例，但在实践中不需要，因为 make 有隐式规则根据涉及的文件来确定这些命令（见第 10 章 [使用隐式规则]，第 101 页）。

在命令执行中，命令序列的每一行都被处理为该行单独出现且前面有一个制表符。特别地，make 为每一行调用一个特殊的子 shell。你可以在命令序列的每一行使用影响命令行的特殊前缀字符（`$0`、`-` 和 `+`）。见第 5 章 [在规则中编写命令]，第 41 页。

例如，使用这个命令序列：

```
define frobicate
@echo "frobicating target $$
frob-step-1 $$ -o $$step-1
frob-step-2 $$step-1 -o $$$
undef
```

make 不显示第一行 echo 命令。但它会显示以下两个命令行。

另一方面，命令行命令行的前缀字符适用于序列中的每一行。因此，规则：

```
frob.out: frob.in
$(frobicate)
```

不会显示任何命令。（参见第 5.1 节 [命令显示]，第 41 页以获取 '@' 的完整解释）。

## 5.8 使用空命令

定义不执行任何操作的命令有时是有用的。这只需给出一个仅由空白字符组成的命令即可。例如：

```
target:
```

为 'target' 定义了一个空命令字符串。你也可以使用以制表符开头的行来定义空命令字符串，但这会引起困惑，因为这样的行看起来是空的。

你可能会奇怪为什么要定义一个不执行任何操作的命令字符串。唯一的用处是防止目标获取隐式命令（来自隐式规则或 .DEFAULT 特殊目标；见第 10 章 [隐式规则]，第 101 页，以及第 10.6 节 [定义最后的默认规则]，第 116 页）。

你可能倾向于为并非实际文件的定义空命令字符串，这些目标仅是为了让它们的先条件重新构建。然而，这不是最好的方法，因为如果目标文件确实存在，先条件可能无法被正确重新构建。参见第 4.4 节 [伪目标]，第 27 页以获取更好的方法。

# 第 6 章：如何使用变量

## 如何使用变量

变量是 Makefile 中定义的一个名称，用于表示一段文本，称为变量的值。这些值通过显式请求被替换到目标（targets）、前提（prerequisites）、命令（commands）以及 Makefile 的其他部分。（在 make 的版本中，变量被称为宏）。

Makefile 中所有部分的变量和函数在读取时都会展开，但规则中的 shell 命令、使用 `=` 定义变量的右侧部分，以及使用 `define` 指令定义变量的主体除外。

变量可以代表文件名列表、传递给编译器的选项、要运行的程序、查找源文件的目录、写入输出的目录，或你想象的任何其他内容。



变量名可以是任何不包含 `:`、`=` 或开头/结尾空格的字符序列。然而，应避免使用包含字母、数字和下划线以外字符的变量，因为它们在未来可能具有特殊含义，并且在某些 shell 中，它们无法通过环境传递给子 make（参见第 5.6.2 节 [将变量传递给子 make]，第 47 页）。

变量名是大小写敏感的。名称 `foo`、`FOO` 和 `Foo` 都指向不同的变量。

在变量名中使用大写字母是传统做法，但我们建议对 Makefile 内部用途的变量使用小写字母，并为用户可以通过命令行选项覆盖的参数保留大写字母（参见第 9.5 节 [覆盖变量]，第 93 页）。

有几个变量名是单个标点字符或几个字符。这些是自动变量，它们有特定的专门用途。参见第 10.5.3 节 [自动变量]，第 111 页。

### 6.1 变量引用的基础

要替换变量的值，写一个美元符号后跟括号内的变量名，或者：`$(foo)` 或 `${foo}` 都是对变量 `foo` 的有效引用。`'$'` 的这种特殊含义解释了为什么如果你在文件名或命令中想获得单个美元符号的效果，必须编写 `'$$'`。

变量引用可以使用于任何语文中：目标、前提、命令、大多数指令以及新变量值。这里有一个常见情况的示例，其中变量持有程序中所有对象文件的名称：

```
objects = program.foo foo.o utils
program : $(objects)
  cc -o program $(objects)

$(objects) : defs.h
```

变量引用通过严格的文本替换工作。因此，值

```
foo = c

prog.o : prog.foo $(foo) prog.$(foo)
```

可以用于编译 C 语言程序 `prog.c`。由于变量赋值中值之前的空格会被忽略，因此 `foo` 的值精确地为 `c`。（不要真的这样写你的 Makefile！）

美元符号后如果跟一个不是美元符号、左括号或左大括号的字符，会将该单个字符视为变量名。因此，你可以用 `$x` 引用变量 `x`。然而，这种做法被强烈不建议，除非是自动变量的情况（参见第 10.5.3 节 [自动变量]，第 111 页）。

### 6.2 变量的两种类型

GNU make 中的变量有两种方式获得值；我们称它们为变量的两种类型。这两种类型的区别在于如何定义它们以及在展开时的行为。

第一种类型的变量是**递归展开变量**。这类变量通过使用 `=` 的行（参见第 6.5 节 [设置变量]，第 62 页）或 `define` 指令定义（参见第 6.8 节 [逐字定义变量]）。你指定的值原样安装；如果它保留了对其他变量的引用，每当该变量被替换时（在展开某些其他字符串的过程中），这些引用就会被展开。当这种情况发生时，被称为递归展开。

例如，

```
foo = $(bar)
bar = $(ugh)
ugh = Huh?

all:echo $(foo)
```

将 echo `Huh?`： `$(foo)` 展开为 `$(bar)`，其展开为 `$(ugh)`，最后展开为 `Huh?`

这种类型的变量是其他版本 make 支持的。它有其优缺点。一个优点（我会说）是：

```
CFLAGS = $(include_dirs) -0
include_dirs = -Ifoo -Ibar
```

将按预期工作：`CFLAGS` 在命令中被展开时，它将展开为 `-Ifoo-Ibar -0`。一个主要的缺点是你不能在变量的末尾添加内容，例如：

```
CFLAGS = $(CFLAGS) -0
```

因为这会导致变量展开出现无限循环。（实际上会检测到无限循环并报告错误。）

另一个缺点是，定义中引用的任何函数（参见第 8 章 [文本转换函数]，第 75 页）会在每次变量展开时执行。这使得 make 运行得更慢；它使用通配符和 shell 函数来产生不可预测的结果，因为你无法容易控制何时调用它们或调用多少次。

为了避免递归展开变量的所有问题和不便，还有另一种类型：**简单展开变量**。

简单展开变量通过使用 `:=` 的行定义（参见第 6.5 节 [变量]，第 62 页）。简单展开变量的值会被扫描一次，在定义时就展开对其他变量的任何引用。简单展开变量的值是你所写的文本展开的结果。

这等同于

```
x := foo
y := later
```

上一个示例展示了两个层嵌套，但任何层数的嵌套都是可能的。例如，这里有三层：

```
x = y
y = z
z = u
a := $(($x))
```

最终，最内层的 `$(x)` 展开为 `y`，因此 `$(x)` 展开为 `$(y)`，接着展开为 `z`；现在我们有了 `$(z)`，它变成了 `u`。

变量名内部递归展开变量的引用将以通常的方式重新展开。例如：

```
x = $(y)
y = z
z = Hello
a := $(($x))
```

定义 `a` 为 `Hello`： `$(x)` 变成 `$(y)`， 变成 `$(z)`，最后变成 `Hello`。

嵌套的变量引用也可以包含修改后的引用和函数调用（见第 8 章 [用于转换的函数]，第 75 页），就像其他引用一样。例如，使用 `subst` 函数（见第 8.2 节 [字符串替换与分析函数]，第 76 页）：

```
x = variable1
variable2 := Hello
y = $(subst 1,2,$(x))
z = y
a := $(($($z))
```

最终定义 as 为 `Hello`。很难说有人会写出像这样复杂的嵌套引用，但它是可以的：`$(($($z))` 展开为 `$(y))`，然后变成 `$(subst 1,2,$(x))`。这从 `x` 中获取了值 `variable1`并通过替换更改为 `variable2`，使得整个字符串变成了 `$(variable2)`，这是一个简单的变量引用，其值为 `Hello`。

计算得的变量名不需要完全由单个变量引用组成。它可以包含多个变量引用，以及一些不变的文本。例如：

```
a_dirs := dira dirb
1_dirs := dirl dir2
a_files := filea fileb
1_files := file1 file2
```

```
objects = main.o
```

使用 `'::='` 定义的变量是递归展开的（见 6.2 节 [变量的类型]，第 56 页），这些定义可以包含变量引用，并在读取 `Makefile` 时展开。

对变量值的长度没有限制。当变量定义很长时，可以在方便的地方插入反斜杠换行符将其分成几行。这会让 `Makefile` 更加易读。

```
variable := value
```

### 6.6 向变量追加文本

向变量的值中添加更多文本是很有用的。你可以使用 `'+='` 这样做：

```
variable += more
```

大致等同于：

```
temp = value
variable = $(temp) more
```

当然，这并没有定义名为 `temp` 的变量。当变量的旧值包含变量引用时，这种方法就变得重要了。如下所示示例：

```
CFLAGS = $(includes) -0
```

```
...
```

```
CFLAGS += -pg # enable profiling
```

第一行定义了引用另一个变量 `includes` 的变量 `CFLAGS`。（`CFLAGS` 用于 C 编译规则；见 10.2 节 [隐式规则目录]，第 102 页）。使用 `'+='` 定义 `CFLAGS` 是一个递归展开变量，这意味着 `'$(includes) -0'` 在 `make` 处理 `CFLAGS` 定义时不会展开。因此，即使尚未定义，值也能生效。它只需要在任何不使用 `'+'` 的 `CFLAGS` 引用之前定义即可。如果我们尝试向 `CFLAGS` 的值追加内容，可能会这样做：

```
CFLAGS := $(CFLAGS) -pg # enable profiling
```

这接近，但不是我们想要的。使用 `':='` 会将 `CFLAGS` 重定义为简单展开变量；这意味着 `make` 在设置变量之前展开文本 `'$(CFLAGS) -pg'`。如果 `includes` 尚未定义，后来的定义不会产生任何影响。相反，通过使用 `'+='` 我们将 `CFLAGS` 设置为未展开的值 `'$(includes) -pg'`。因此我们保留了对 `includes` 的引用，如果该变量在以后任何时候被定义，引用 `'$(CFLAGS)'` 仍然使用其值。

### 6.7 覆盖指令 (override Directive)

如果变量通过命令行参数进行了设置（见第 9.5 节 [覆盖变量]，第 93 页），则 `Makefile` 中的普通赋值将被忽略。如果你即使在变量已通过命令行参数设置的情况下，仍想在 `Makefile` 中设置该变量，可以使用 `override` 指令，该指令的格式如下：

```
override variable = value
```

或者

```
override variable := value
```

若要在命令行上定义的值后追加更多文本，请使用：

`override variable += more text`

参见第 6.6 节 [向变量追加更多文本]，第 63 页。

引入 `override` 指令并不是为了在 `Makefile` 和命令行参数的战争中进行升级。它的发明是为了让你能够修改和增加用户通过命令行参数指定的值。

例如，假设你希望运行 C 编译器时总是想使用 `'-g'` 开关，但又允许用户像往常一样通过命令行参数指定其他开关。你可以使用这个 `override` 指令：

```
override CFLAGS += -g
```

你还可以将 `override` 指令与 `define` 指令结合使用。其用法正如你预期的那样：

```
override define foo
bar
def
```

关于 `define` 的信息请见下一节。

### 6.8 字面定义变量 (Defining Variables Verbatim)

另一种设置变量值的方法是使用 `define` 指令。该指令具有一种特殊的语法，允许在值中包含换行符，这对于定义一系列命令来说非常方便（见第 5.7 节 [定义预定义命令序列]，第 52 页）。

`define` 指令同一行后面是变量名，且没有其他内容。赋予变量的值出现在随后的几行中。值的结束由包含 `endif` 单词的行标记。除了这种语法上的差异，`define` 的工作方式与 `'='` 相同：它创建一个递归展开的变量（见第 6.2 节 [变量的两种类型]，第 56 页）。变量名可以包含函数和变量引用，这些引用在读取指令时会被展开，以找到实际要使用的名称。

```
define two-lines
echo foo
echo $(bar)
def
```

普通赋值中的值不能包含换行符；分隔 `define` 中行的换行符将成为变量值的一部分（位于 `endif` 之前的最后一个换行符不被视为值的一部分）。

上一个示例在功能上等同于：

```
two-lines = echo foo; echo $(bar)
```

因为用分号分隔的两个命令的行为类似于两个独立的 shell 命令。然而，请注意，使用两个独立的行 `make` 会调用两次 shell，为每行运行一个独立的子 shell。参见第 5.2 节 [命令执行]，第 41 页。

如果你想让通过 `define` 定义的变量优先高于命令行变量定义，可以使用 `override` 指令配合 `define` 使用：

```
override define two-lines
foo
$(bar)
def
```

参见第 6.7 节 [覆盖指令]，第 65 页。

### 6.9 环境中的变量

`make` 中的变量可以来自运行 `make` 的环境。`make` 在启动时看到的每一个环境变量都会转换为具有相同名称和值的 `make` 变量。但 `Makefile` 中的显式赋值或命令行参数赋值会覆盖环境。（如果指定了 `'-e'` 标志，则环境中的值将覆盖 `Makefile` 中的赋值。参见第 9.7 节 [选项摘要]，第 95 页。但并不是推荐的做法。）

通过在环境中设置变量 `CFLAGS`，你可以让大多数 `Makefile` 中的所有 C 编译都使用你偏好的编译器开关。对于具有标准或习惯含义的变量，这是安全的，因为你知道 `Makefile` 会将它们用于其他用途（但这并非完全可靠；某些 `Makefile` 会显式设置 `CFLAGS`，因此不会使用该值）。

`make` 递归调用时，在环境中定义的变量会传递给内部调用（见 5.6 节 [变量的使用]）。默认情况下，在环境中定义的变量赋值会传递给内部调用。

### 6.10 目标特定变量值 (Target-specific Values)

`Makefile` 中的值通常是全局的，这意味着无论在何处评估都是相同的（除非在目标处重置，见 10.5 [自动变量]，第 111 页）。目标特定值值允许你根据当前构建的目标为变量定义不同的值。这些值在目标脚本中是可用的。

按如下格式设置目标特定变量值：

```
target  ... : variable-assignment
```

或者按如下格式：

```
target  ... : override variable-assignment
```

多个目标值为目标列表中的每个成员单独创建一个目标特定变量值。变量赋值可以是任何有效的赋值形式：递归（`=`）、追加（`+=`）或条件（`?=`）。在目标赋值中出现的变量在目标上下文中评估；因此，任何先定义的目标特定变量将生效。

目标特定变量还有一个特殊特性：当你在定义一个目标特定变量时，该变量值对于该目标的所有依赖也有效（除非这些依赖项用自己的目标特定变量覆盖了它）。因此，例如这样的语句：

```
prog : CFLAGS = -g
prog : prog.o foo.o bar.o
```

将在 `prog` 的命令脚本中将 `CFLAGS` 设置为 `'-g'`，但它也会在创建 `prog.o`、`foo.o` 和 `bar.o` 的脚本中将 `CFLAGS` 设置为 `'-g'`。

### 6.11 模式特定变量值 (Pattern-specific Variable Values)

除了目标特定变量值（见 6.10 节 [目标特定变量值]，第 67 页），GNU `make` 支持模式特定变量值。在这种格式下，为任何匹配指定模式定义变量。以这种方式定义的变量搜索顺序位于显式定义的目标特定变量之后，在父目标的目标特定变量之前。

按如下格式设置模式特定变量值：

```
pattern ... : variable-assignment
```

其中 `pattern` 是一个 `%.pattern`。与目标特定变量值一样，多个模式值为每个模式单独创建一个模式特定变量值。变量赋值可以是任何有效的赋值形式。任何命令行变量设置将具有优先权，除非指定了 `override`。

例如：

```

```

将为匹配模式 `%.o` 的所有目标将 `CFLAGS` 设置为 `'-0'`。

## 第 7 章：Makefile 的条件部分

# 7 Makefile 的条件部分

条件语句根据变量的值决定 `Makefile` 的部分内容是被执行还是忽略。条件语句可以比较一个变量的值与另一个变量的值，或者一个变量的值与一个常量字符串的值。条件语句控制 `Makefile` 中实际能被“看到”的内容，因此它们不能用于控制执行时刻的 shell 命令。

### 7.1 条件示例

下面的条件示例告诉 `make`，如果变量 `CC` 等于 ‘gcc’，则使用一组库，否则使用另一组库。它的工作原理是控制使用哪两条命令行作为该规则的命令。结果是，当将 `CC=gcc` 作为一个参数时，`make` 不仅更改了使用哪种编译器，还更改了链接哪些库。

```
libs_for_gcc = -lgnu
normal_libs =

foo: $(objects)
ifeq ($(objects),gcc)
  $(CC) -o foo $(objects) $(libs_for_gcc)
else
  $(CC) -o foo $(objects) $(normal_libs)
endif
```

此条件语句使用了三个指令：一个 `ifeq`，一个 `else` 和一个 `endif`。`ifeq` 指令定义了条件并指定了条件。它包含两个由逗号分隔的参数，并用括号括起来。对两个参数都进行变量替换，然后进行比较。如果两个参数匹配，则执行 `ifeq` 之后的 `Makefile` 行；否则，这些行会被忽略。

`else` 指令在之前的条件失败时导致执行随后的行。在上面的示例中，这意味着每当不使用第一种备选时，就会使用第二种备选链接命令。在条件语句中，`else` 是可选的。

`endif` 指令结束条件语句。每个条件语句必须以 `endif` 结束。之后是无条件的 `Makefile` 文本。

如示例所示，条件语句是在文本层面工作的：条件语句的行根据条件被视为 `Makefile` 的一部分，或者被忽略。这就是为什么 `Makefile` 中较大的语法单元（如规则）可能会跨越条件语句的开始或结束。

当变量 `CC` 的值为 ‘gcc’ 时，上述示例产生以下效果：

```
foo: $(objects)
  $(CC) -o foo $(objects) $(libs_for_gcc)
```

当变量 `CC` 为任何其他值时，效果如下：

```
foo: $(objects)
$(CC) -o foo $(objects) $(normal_libs)
```

通过对变量赋值进行条件化然后无条件使用，也可以获得等的结果：



```

normal_libs =
ifeq ($(CC),gcc)
libs=$$(libs_for_gcc)
else
libs=$$(normal_libs)
endif
```

```
foo: $(objects)
$(CC) -o foo $(objects) $(libs)
```

没有 `else` 的简单条件语句语法如下：

复杂条件语句的语法如下：

```

```

## 第 8 章：文本转换函数

# 8 文本转换函数

函数允许你在 Makefile 中进行文本处理，以计算要操作的文件或要使用的命令。你在调用中使用函数时，给出函数名称以及供函数操作的文本（参数）。函数处理的结果将替换到调用处的 Makefile 中，就像变量一样。

### 8.1 函数调用

函数调用类似于变量引用。它看起来如下：

```
$(function arguments)
```

或者看起来如下：

```
${function arguments}
```

这里 `function` 是函数名；是 make 的一部分短名称列表。你也可以通过使用 `call` 内置函数来创建自己的函数。



参数是函数的参数。它们与函数名通过一个或多个空格或制表符分隔，如果有多个参数，则由逗号分隔。任何空白和逗号都不是参数值的一部分。每个参数的文本通过变量替换和函数调用进行处理，生成参数值，即函数作用的文本。替换按照参数出现的顺序进行。

逗号和不匹配的括号或花括号不能出现在参数的文本中；第一个参数的文本不允许出现领先空格。这些字符可以通过变量替换放入参数值中。首先定义值为孤立逗号和空格的变量，然后在需要这些字符的地方替换这些变量：

```make
comma := ,
empty =
space := $(empty) $(empty)
foo := a b c
bar := $(subst $(space),$(comma),$(foo))
# bar 现在是 'a,b,c'.
```

在这里，`subst` 函数通过 `foo` 的值将每个空格替换为逗号，并替换该结果。

## 8.2 字符串替换与分析函数

这里有一些操作字符串的函数：

```
$(subst from,to,text)
```

对文本 `text` 执行文本替换：`from` 的每个出现处都会被替换为 `to`。结果由该函数调用替换。例如，

```

```

替换字符串为 'fEEt on the strEEt'。

```
$(patsubst pattern,replacement,text)
```

在 `text` 中查找匹配 `pattern` 的由空格分隔的单词，并将它们替换为 `replacement`。这里，`pattern` 可以包含一个 `%`，它作为通配符，匹配单词内任意数量的字符。如果 `replacement` 也包含 `%`，则 `%` 将被替换为匹配 `pattern` 中 `%` 的文本。只有 `pattern` 和 `replacement` 中的第一个 `%` 会被这样处理；任何随后的 `%` 均保持不变。

`patsubst` 函数调用中的 `%` 字符可以通过前面的反斜杠（`\`）进行转义。用于转义 `%` 字符的反斜杠可以使用更多的反斜杠进行转义。转义 `%` 字符或其他反斜杠的反斜杠会在比较文件名之前从模式中移除，而那些没有转义 `%` 字符风险的反斜杠则保持原样。例如，模式 'the\weird\%pattern' 在操作性 `%` 字符之前有 'the\weird%'，之后有 'pattern'。最后两个反斜杠会被原样保留，因为它们不会影响任何字符。

单词之间的空格会被合并为单个空格字符；开头和结尾的空格会被丢弃。例如，


产生值 'x.c.o bar'。

### 8.4 foreach 函数

`foreach` 函数与其他函数非常不同。它导致某段文本被重复使用，每次都对其进行不同的替换。它类似于 shell `sh` 中的 `for` 命令以及 C-shell `csh` 中的 `foreach` 命令。

`foreach` 的语法为：

```
$(foreach var, list, text)
```

前两个参数 `var` 和 `list` 在执行任何操作之前会被展开；注意，最后一个参数 `text` 不会同时被展开。对于 `list` 展开值中的每个单词，由 `var` 展开值命名的变量将设置为该单词，并展开 `text`。推测 `text` 包含了对该内容的引用，因此它的每次展开都会是不同的。

结果是，`text` 展开的次数与 `list` 中由空格分隔的单词数相同。`text` 的多次展开连接在一起，中间留有空格，形成 `foreach` 的结果。

这个简单的示例将变量 `files` 设置为列表中目录中所有文件的列表：

```
dirs := a b c d
files := $(foreach $(dirs),$(wildcard $(dir)*)
```

此处 `text` 为 '$(wildcard $(dir)*'。第一次循环找到 `dir` 的值 'a'，因此它产生结果 '$(wildcard a/*)'；第二次循环产生结果 '$(wildcard b/*)'；第三次产生 '$wildcard c/*)'。

这个示例的结果与下例相同（除了设置 'dirs' 之外）：

```
files := $(wildcard a*) b* c* d*)
```

当 `text` 很复杂时，你可以通过额外的变量为其命名来提高可读性：

```
dirs_files := $(wildcard $(dir)/)
dirs := a b c d
```

```
$(foreach var, list, text)
```

```
files := $(foreach $(dirs),$(wildcard $(dir)*)
```

### 8.7 origin 函数

`origin` 函数与大多数函数不同，它不对变量的值进行操作；它告诉你是关于变量的信息。具体来说，它告诉该变量的来源。

`origin` 函数的语法为：

```
$(origin variable)
```

注意，`variable` 是要查询的变量名称；而不是该变量的引用。因此，在编写时你不需要使用 '$' 或括号。（不过，如果你想让名称成为一个常量，则可以在名称中使用变量引用。）

该函数的返回值是一个字符串，告诉变量 `variable` 是如何定义的：

- `'undefined'`
  - 如果变量从未被定义过。
- `'default'`
  - 如果变量有默认定义，这在 `CC` 等情况下很常见。见第 10.3 节 [隐式规则使用的变量]，第 106 页。注意，如果你重新定义了默认变量，`origin` 函数将返回后定义定义的来源。
- `'environment'`
  - 如果变量被定义为环境变量，且没有开启 `'-e'` 选项（见第 9.7 节 [选项摘要]，第 95 页）。
- `'environment override'`
  - 如果变量被定义为环境变量，且开启了 `'-e'` 选项（见第 9.7 节 [选项摘要]，第 95 页）。
- `'file'`
  - 如果变量在 makefile 中定义。
- `'command line'`
  - 如果变量在命令行中定义。
- `'override'`
  - 如果变量在 makefile 中通过 `override` 指令定义（见第 6.7 节 [override 指令]，第 65 页）。
- `'automatic'`
  - 如果变量是为每个规则的命令执行而定义的自动变量（见第 10.5.3 节 [自动变量]，第 111 页）。

这些信息主要的用途（除了好奇心外）是确定你是否想要信任某个变量的值。例如，假设

在 GNU make 中有一个名为 `'foo'` 的 makefile，它包含了另一个名为 `'bar'` 的 makefile。你希望在运行 `make -f bar` 命令时，在 `'bar'` 中定义一个 `bletch`，即使环境中已经包含了 `bletch` 的定义。然而，如果 `'foo'` 在包含 `'bar'` 之前定义了 `bletch`，则你不希望覆盖该定义。可以通过在 `'foo'` 中使用 `override` 指令来实现，使该定义优先于 `'bar'` 中的后定义定义；不幸的是，`override` 指令也会覆盖任何命令行定义。因此，`'bar'` 可以包含：

```
ifdef bletch
ifeq $(origin bletch) "environment"
bletch = barf, gag, etc.
endif
endif
```

如果 `bletch` 已经从环境中定义，这将会重新定义它。如果你希望在 `bletch` 来自环境时覆盖其之前的定义（即使在开启 `'-e'` 的情况下也是如此），你可以改写为：

```
ifeq "$(findstring environment,$(origin bletch))" ""
bletch = barf, gag, etc.
endif
```

在这里，如果 `$(origin bletch)` 返回 `'environment'` 或 `'environment override'`，则发生重新定义。见第 8.2 节 [字符串替换和分析函数]，第 76 页。

### 8.8 shell 函数

`shell` 函数与除通配符函数（见第 4.2.3 节 [函数 wildcard]，第 22 页）外的任何函数都不同，因为它能与 make 之外的世界通信。

`shell` 函数的作用与大多数 shell 中反引号（`` ` ``）的作用相同：它执行命令扩展。这意味着它接收一个作为 shell 命令的参数，并返回命令的输出。`make` 在将结果替换到周围文本之前对结果进行的唯一处理，是将每个换行符或回车换行符对转换为单个空格。如果它是结果中的最后一个内容，它还会删除末尾的（回车和换行符）。

通过调用 `shell` 函数运行的命令在函数调用展开时执行。在大多数情况下，这是在读取 makefile 时。例外是规则命令中的函数调用是在命令运行时展开的，这适用于包括 `shell` 函数在内的所有调用。

以下是 `shell` 函数的一些示例：

```
contents := $(shell cat foo)
```

将 `contents` 设置为文件 `'foo'` 的内容，用空格（而不是换行）分隔每行。

```
files := $(shell echo *.c)
```

将 `files` 设置为 `'*.c'` 的展开结果。除非 make 使用了非常奇特的 shell，否则结果与 `'$(wildcard *.c)'` 相同。

### 8.9 控制 Make 的函数



这些函数控制 `make` 的运行方式。通常，它们被用于向 `makefile` 用户提供信息，或者在检测到某种环境错误时让 `make` 停止。

`$(error text...)`

生成致命错误，其中消息为 `text`。注意，每当此函数被求值时，就会生成错误。因此，如果你把它放在命令脚本或递归变量赋值的右侧，它在生成错误之前不会被求值。

例如：

```
ifndef ERROR1
  $(error error is $(ERROR1))
endif
```

如果 `make` 变量 `ERROR1` 已定义，则会在读取 `makefile` 期间生成致命错误。例如，

```
.PHONY: err
err: $(error)
```

如果 `make` 变量 `ERROR1` 已定义，则会在读取 `makefile` 期间生成致命错误。

`$(warning text...)`

向标准错误打印警告消息，但不会停止执行。每当此函数被求值时，都会生成消息。

`$(info text...)`

向标准输出打印消息。每当此函数被求值时，都会生成消息。

`$(debug text...)`

向标准错误打印消息，但仅在开启 `-d` 选项时。每当此函数被求值时，都会生成消息。

# 第9章：如何运行 make

## 9.1 指定 Makefile 的参数

指定 `Makefile` 最简单的方法是将其名称作为第一个参数。如果文件名为 `Makefile`，`make` 会在当前目录下查找它。如果你想使用不同的文件，使用 `-f` 选项。

```
make -f myfile
```

`-f` 选项可以使用多次来指定多个 `makefile`，按照它们给出的顺序进行处理。

```
make -f file1 -f file2 target
```

位于选项后面的参数是待制作的目标。如果没有给出目标，默认目标是 `all`。

```
make target1 target2
```

如果指定了多个目标，`make` 会按照它们的顺序处理它们。任何不在 `makefile` 中的目标都将被视为错误。

## 9.3 执行命令

指定目标的一种用途是如果你只想编译程序的一部分，或编译多个程序中的一个。将你想要重新制作的文件指定为目标。例如，考虑一个包含多个程序的目录，其 `makefile` 开始如下：

```
.PHONY: all
all: size nm ar as
```

另一个用途是运行与伪目标（见第 4.4 节 [伪目标]，第 27 页）或空目标（见第 4.6 节 [记录事件的空目标文件]，第 30 页）相关的命令。许多 `Makefile` 包含一个名为 `clean` 的伪目标，它可以删除源文件以外的所有内容。当然，这只有在你显式请求 `make clean` 时才会执行。以下是一些典型的伪目标和空目标列表。见第 14.5 节 [标准目标]，第 138 页有关 GNU 软件软件包使用的所有标准目标的详细列表。

`mostlyclean`

类似于 `clean`，但它可能会克制而不删除一些人们通常不想重新编译的文件。例如，GCC 的 `mostlyclean` 目标不会删除 `libgcc.a`，因为重新编译它很少必要且耗费大量时间。

`distclean`

`realclean`

`clobber`

这些目标中的任何一个都可能被定义删除比 `clean` 更多的的文件。例如这将删除你通常为编译准备而创建的配置文件或链接，即使 `Makefile` 本身无法创建这些文件。

`install`

将可执行文件复制到用户通常搜索命令的目录；将可执行文件使用的任何辅助文件复制到它查找它们的目录中。

`print`

打印已更改源文件的列表。

`tar`

为源文件创建一个 `tar` 文件。

`shar`

为源文件创建一个 shell 归档（`shar` 文件）。

`dist`

为源文件创建一个发行文件。这可能是一个 `tar` 文件、shell 文件或上述任一内容的压缩版本，甚至是上述内容的多个组合。

`TAGS`

为此程序更新标签表。

`check`

`test`

对此 `makefile` 构建的程序进行自测试。

### 9.3 代替执行命令

`makefile` 告诉 `make` 如何判断一个目标是否是最新的，以及如何更新每个目标。但更新目标并不总是你想要的。某些选项为 `make` 指定了其他活动。

`-n`
`--just-print`
`--dry-run`
`--recon`

> "无操作"。该活动是打印将用于使目标保持新的而将使用的命令，但并不实际执行它们。

`-t`
`--touch`

> "触摸（Touch）"。该活动是将目标标记为新的，而不实际更改它们。换句话说，`make` 伪装编译了目标，但并没有真正改变它们的内容。

`'-q'`
`--question`

> "提问"。该活动是静地查找目标是否已经是新的；但在任何情况下都不执行命令。换句话说，既不会发生编译也不会产生输出。

`-W file`
`--what-if=file`
`--assume-new-file`
`--new-file=file`

"如果如果"。每个 `-W` 标志后面都跟着一个文件名。通过记录给定文件的存在时间来记录这些文件的修改时间，尽管实际修改时间保持不变。你可以将 `-W` 标志配合 `-n` 标志，查看如果你修改了特定文件会发生什么。

使用 `-n` 标志，`make` 会打印它通常会执行但并不执行的命令。

使用 `-t` 标志，`make` 会忽略规则中的命令，并（实际上）对每个需要重新制作的目标使用 `touch` 命令。为了速度，`touch` 命令也会被打印，不像 `-s` 或 `.SILENT` 所做的那样。它并不会实际调用 `touch` 程序，而是直接完成工作。

使用 `-q` 标志，`make` 不打印任何命令，但当且仅当所考虑的目标已经是新的时，退出状态码才返回零。如果退出状态为一，则需要进行某些更新。如果 `make` 遇到错误，状态为二，因此你可以区分错误和尚未更新的目标。

在 `make` 的单次调用中使用多个此类标志是错误的。

`-n`、`-t` 和 `-q` 选项不影响以 `+` 字符开头或包含字符串 `$(MAKE)` 或 `${MAKE}` 的命令行。请注意，只有包含 `+` 字符或字符串 `$(MAKE)` 或 `${MAKE}` 的行不受这些选项影响。同一规则中的其他行除非你用 `+` 切换它们或包含 `$(MAKE)` 或 `${MAKE}`，否则不会运行（参见第 5.6.1 节 [Make 变量的工作原理]，第 47 页）。

`-W` 标志提供了两个功能：

- 如果使用 `-n` 或 `-q` 标志，你可以看到如果你修改了某些文件 `make` 会做什么
- 在不使用 `-n` 或 `-q` 标志的情况下，当 `make` 实际执行命令时，`-W` 标志可以引导 `make` 好像某些文件已被修改，而不修改这些文件。

注意选项 `-p` 和 `-v` 允许你获取有关 `make` 或正在使用的 `makefiles` 的其他信息（参见第 9.7 节 [选项总结]，第 95 页）。

### 9.4 避免重新编译某些文件

有时你可能更改了源文件，但不想重新编译所有依赖于它的文件。例如，假设你对许多其他文件依赖的头文件使用了宏或声明。保守起见，`make` 假设头文件中的任何更改都需要重新编译所有依赖文件，但你清楚它们不需要重新编译，而且你不想浪费时间等待它们完成。

如果你在更改头文件之前预见了这个问题，可以使用 `-t` 标志。此标志告诉 `make` 不要运行规则中的命令，而是通过更改最后修改日期将目标标记为新的。

1. 使用 `-t` 标志通过更改其最后修改日期将目标标记为新的。
2. 使用 `-t` 标志将目标标记为新的。
3. 使用 `-t` 标志将目标标记为新的。

`-k` 标志表示真实目的是尽可能地测试程序中所作的更改，也许是为了发现几个独立的问题，以便你可以在下一次尝试编译之前修正所有问题。这就是为什么 Emacs 的 `M-x compile` 命令默认传递了 `-k` 标志的原因。

# 10 使用隐式规则

某些生成目标文件的标准方法被频繁使用。例如，生成目标文件的一种习惯方法是使用 C 编译器 `cc` 从 C 源文件生成。

隐式规则告诉了你如何使用常规技术，这样当你想要使用它们时，就不需要详细指定它们。例如，存在一条 C 编译的隐式规则。文件名决定了运行哪些规则。例如，C 编译通常读取一个 `'.c'` 文件并生成一个 `'.o'` 文件。因此，当 `make` 看到这种文件后缀组合时，它就会应用 C 编译的隐式规则。

隐式规则链可以顺序应用；例如，`make` 会通过 `'.c'` 文件从 `'.y'` 文件重新生成 `'.o'` 文件。参见第 10.4 节 [隐式规则链]，第 108 页。

内置隐式规则在命令中使用了几个变量，因此通过更改变量的值，你可以改变隐式规则的工作方式。例如，变量 `CFLAGS` 控制由 C 编译隐式规则传递给 C 编译器的标志。参见第 10.3 节 [隐式规则使用的变量]，第 106 页。

你可以通过编写模式规则来定义自己的隐式规则。参见第 10.5 节 [定义和重新定义模式规则]，第 109 页。

后缀规则是定义隐式规则的一种更有限的方法。模式规则更通用、更清晰，但为了兼容性保留了后缀规则。参见第 10.7 节 [旧式后缀规则]，第 117 页。

### 10.1 使用隐式规则

例如，假设 `makefile` 如下所示：

```
foo : foo.o bar
	cc -o foo.o bar $(CFLAGS) $(LDFLAGS)
```

由于你命名了 `'foo.o'` 但没有为它提供规则，`make` 将自动查找一条告诉它如何更新它的隐式规则。无论文件 `'foo.o'` 目前是否存在，这种情况都会发生。

如果找到了隐式规则，它可以同时提供命令和一个或多个前提条件（源文件）。如果你需要指定隐式规则无法提供的额外前提条件（例如头文件），你可能需要为 `'foo.o'` 写一条没有命令行的规则。



# 第10章：使用隐式规则

每条隐式规则都包含一个目标模式和前提条件模式。可能存在许多具有相同目标模式的隐式规则。例如，许多针对 `.o` 文件的规则：一条是从 `.c` 文件通过 C 编译器生成的；另一是从 `.p` 文件通过 Pascal 编译器生成的；以此此类推。实际应用的规则是那些前提条件存在或可以制作的规则。因此，如果你有一个文件 `foo.c`，`make` 将运行 C 编译器；否则，如果你有一个文件 `foo.p`，`make` 将运行 Pascal 编译器；以此此类推。

当然，当你编写 `Makefile` 时，你知道想要使用哪条隐式规则，你知道它会选择那一个，因为你知道哪些可能的前提条件应该是存在的。参见第 10.2 节 [隐式规则目录]，第 102 页，获取所有预定义隐式规则的目录。

上面提到，如果所需的前提条件存在或可被制作，则隐式规则适用。如果一个文件在 `Makefile` 中作为目标或前提条件被提到，或者可以递归找到制作它的隐式规则，则该文件就可以被“制作”。当一个隐含前提条件是另一个隐式规则的结果时，我们称为发生了*链链*。参见第 10.4 节 [隐式规则链]，第 108 页。

通常情况下，`make` 为每个目标搜索隐式规则，并为每个没有命令的双冒号规则搜索隐式规则。仅作为前提条件被提到的文件被视为规则未指定任何内容的目标，因此会对其进行隐式搜索。参见第 10.8 节 [隐式规则搜索算法]，第 118 页了解搜索执行的细节。

注意，前提条件不影响隐式规则搜索。例如，考虑这条显式规则：

```
foo.o: foo.p
```

对 `foo.o` 的前提并不并不意味着 `make` 会根据从 Pascal 源文件 `.p` 生成目标文件 `.o` 的隐式规则来重新制作 `foo.o`。例如，如果 `foo.c` 存在，则将使用从 C 源生成目标文件的隐式规则，因为它在预定义隐式规则列表中出现在 Pascal 规则之前（参见第 10.2 节 [隐式规则目录]，第 102 页）。

如果你不希望为没有命令的目标使用隐式规则，你可以通过编写分号来给该目标提供空命令（参见第 5.8 节 [定义空命令]，第 53 页）。

## 10.2 隐式规则目录

这里是预定义隐式规则目录，除非 `Makefile` 显式覆盖或取消它们，否则它们始终可用。参见第 10.5.6 节 [取消隐式规则]，第 116 页获取取消或覆盖隐式规则的信息。`-r` 或 `--builtin-rules` 选项会取消所有预定义规则。

并非所有规则都总是被定义：特殊目标 `.SUFFIXES` 的前提条件列表。默认后缀列表为:.out, .a, .ln, .o, .c, .cc, .C, .p, .f, .F, .r, .y, .l.

无论 Lex 文件生成的是 C 代码还是 Ratfor 代码，对所有 Lex 文件使用相同后缀 '.1' 的习惯使得 `make` 无法在任何情况下自动确定你正在使用哪种语言。当调用 `make` 将一个 '.1' 文件重命名为对象文件时，它必须猜测使用哪种编译器。它会猜测 C 编译器，因为这更常见。如果你正在使用 Ratfor，请确保通过在 `Makefile` 中提到 'n.r' 来让 `make` 知道。或者，如果你专门使用 Ratfor 且没有 C 文件，可以通过以下命令从隐式规则后缀列表中删除 '.c'：

-   `.SUFFIXES:`
  `.SUFFIXES: .o .r .f ...`

### 从 C、Yacc 或 Lex 程序生成 Lint 库

`n.ln` 是通过运行 `lint` 从 `n.c` 生成的。精确命令是 `$(LINT) $(CPPFLAGS) -i`。同样的命令也用于从 `n.y` 或 `n.l1` 生成的 C 代码。

### Tex 和 Web

`n.dvi` 是通过命令 `$(TEX)` 从 `n.tex` 生成的。

`n.tex` 是通过 `$(WEAVE)` 从 `n.web` 生成的，或者通过 `$(CWEAVE)` 从 `n.wi`（如果 `n.ch` 存在或可以生成）生成。

`n.p` 是通过 `$(TANGLE)` 从 `n.web` 生成的，而 `n.c` 是通过 `$(CTANGLE)` 从 `n.w`（如果 `n.ch` 存在或可以生成） 生成的。

### Texinfo 和 Info

`n.dvi` 是通过命令 `$(TEX2DVI) $(TEX2DVI\_FLAGS)` 从 `n.texinfo`、`n.texi` 或 `n.txinfo` 生成的。`n.info` 是通过命令 `$(MAKEINFO) $(MAKEINFO\_FLAGS)` 从 `n.texinfo`、`n.texi` 或 `n.txinfo` 生成的。

### RCS

如果有，将从名为 `n,v` 或 `RCS/n,v` 的 RCS 文件提取任何文件 `n`。使用的精确命令是 `$(CO) $(COFLAGSAG)`。如果 `n` 已存在且 RCS 文件更新，则不会从 RCS 提取。RCS 的规则是终端规则（参见第 10.5.5 节 [匹配模式规则]），因此 RCS 文件无法从其他源生成；它们必须实际存在。

### SCCS

如果有，将从名为 `s.n` 或 `SCCS/s.n` 的 SCCS 文件提取任何文件 `n`。使用的精确命令是 `$(GET) $(GFLAGS)`。SCCS 的规则是终端规则（参见第 10.5.5 节 [通配符规则]，第 114 页），因此 SCCS 文件无法从其他源生成；它们必须实际存在。

为了 SCCS 的方便考虑，文件 `n` 会从 `n.sh` 复制并设为可执行（对所有人）。这适用于已检入 SCCS 的脚本。由于 RCS 保留了文件的执行权限，因此你不需要在 RCS 中使用此功能。

我们建议你避免使用 SCCS。RCS 被广泛认为更优，而且是免费的。通过选择免费软件代替类似的（或更差的）专有软件，你支持了自由软件运动。

通常，你只想更改上表列出的变量，这些变量在后续章节中有介绍。

然而，内置隐式规则中的命令实际上使用了诸如 `COMPILE.c`、`LINK.p` 和 `PREPROCESS.S` 等变量，其值包含了上述列出的命令。

`make` 遵循一种约定：编译 '.x' 源文件的规则使用变量 `COMPILE.x`。同样，从 '.x' 文件生成可执行文件的规则使用 `LINK.x`；预处理 '.x' 文件的规则使用 `PREPROCESS.x`。

每个生成对象文件的规则都使用变量 `OUTPUT_OPTION`。`make` 定义该变量为包含 `-o $@`，或者为空，这取决于编译时选项。你需要 `-o` 选项来确保在在使用 `VPATH` 时（源文件位于不同目录，参见第 4.3 节 [目录搜索]，第 22 页），输出输出到正确的文件。然而，某些系统上的编译器不接受用于对象文件的 `-o` 开关。如果你使用这样的系统且没有使用 `VPATH`，某些编译将把你的输出放在错误的位置。该问题的一种可能解决方法是让 `OUTPUT_OPTION` 取值为 `; mv=$*`。

## 10.4 隐式规则链

有时文件可以通过隐式规则序列生成。例如，文件 `n.o` 可以通过先运行 Yacc 然后 `cc` 从 `n.y` 生成。这种序列被称为链。



如果文件 `n.c` 或在 `make` 中提到，就需要特殊的搜索：`make` 发现对象文件可以通过 C 编译生成；考虑如何制作 `n.c` 时，使用了运行 `Yacc` 的规则。最终 `n.c` 和 `n.o` 会被更新。

然而，即使 `n.c` 不存在且未被提到，`make` 也知道如何想象 `n.o` 和 `n.y` 之间缺失的链接。在这种情况下，`n.c` 被中间文件。一旦 `make` 决定使用中间文件，它就会像在 `make` 中被提到那样进入数据库，以及说明如何创建它的隐式规则。

中间文件的制作方式与其他文件一样使用其规则。中间文件在两个方面处理不同。

第一个区别是文件不存在时。如果普通文件 `b` 不存在，且 `make` 考虑依赖于 `b` 的目标，它总是创建 `b` 然后从 `b` 更新目标。但如果 `b` 是中间文件，`make` 可以置不管。除非 `b` 的某个前提条件比目标新，或者有其他更新目标的理由。

第二个区别是，如果 `make` 为了更新其他内容而创建了 `b`，它会在不再需要 `b` 后删除 `b`。

## 第 10 章：使用隐式规则

中间文件在 `make` 运行之前不存在，在 `make` 之后也不存在。`make` 会通过打印 `rm -f` 命令来向你报告删除操作，显示它正在删除哪个文件。

通常情况下，如果一个文件在 `Makefile` 中被用作目标或前提，它不能是中间文件。然而，你可以通过将其列为特殊目标 `.INTERMEDIATE` 的前提，显式地将一个文件标记为中间文件。即使该文件通过其他方式被显式提到，这依然有效。

你可以通过将中间文件标记为辅助文件（secondary file）来防止其被自动删除。这样做只需将其列为特殊目标 `.SECONDARY` 的前提。当一个文件是辅助文件时，`make` 将 `own` 该文件（因为它不存在），但 `make` 不会自动删除该文件。将文件标记为辅助文件也会将其标记为中间文件。

你可以将隐式规则的目标模式（例如 `%.o`）列为特殊目标 `.PRECIOUS` 的前提，以保留由那些目标模式匹配该文件名的隐式规则所生成的中间文件；参见第 46 页第 5.5 节 [中断](Interrupts)。

一个规则链可能涉及两个以上的隐式规则。例如，可能通过运行 `RCS`、`Yacc` 和 `cc` 从 `RCS/foo.y` 生成文件 `foo`。此时 `foo.y` 和 `foo.c` 都是在最后被删除的中间文件。

同一个隐式规则在链中不能出现多次。这意味着 `make` 甚至不会考虑诸如通过运行两次链接器从 `foo.o.o` 生成 `foo` 这种荒谬的事情。这一约束的额外益处是防止在搜索隐式规则时出现任何无限循环。

存在一些特殊的隐式规则用于优化某些本应由规则链处理的场景。例如，从 `foo.c` 生成 `foo` 可以通过单独的链编译和链接来处理，使用 `foo.o` 作为中间文件。但实际发生的情况是，针对这种情况的特殊规则使用单个 `cc` 完成了编译和链接。这种优化后的规则优于步步为营的链，因为它在规则的排序中排更靠前。

### 10.5 定义和重新定义模式规则

你通过编写模式规则（pattern rule）来定义隐式规则。模式规则看起来像普通规则，不同在于它的目标包含字符 `%`（恰好仅包含一个）。该目标被视为匹配文件名的模式；其中 `%` 可以匹配任何非空字符串，而其他字符只匹配它们本身。前提条件同样使用 `%` 来显示它们的名称如何与目标名称相关关系。

因此，模式规则 `%.o : %.c` 描述了如何从另一个文件 `stem.c` 生成任何文件 `stem.o`。

注意，模式规则中 `%` 的展开发生在任何变量或函数展开之后，而这些展开是在读取 `Makefile` 时进行的。参见第 55 页的第 6 章 [如何使用变量](How to Use Variables) 和第 75 页的第 8 章 [转换文本的函数](Functions for Transforming Text)。

#### 10.5.1 模式规则简介

模式规则在目标中包含字符 `%`（恰好仅包含一个）；否则它看起来和普通规则一模一样。目标是匹配文件名的模式；`%` 匹配任何非空字符串，而其他字符只匹配它们本身。

例如，`.c` 作为模式匹配任何以 `.c` 结尾的文件名。`.sc` 作为模式匹配任何以 `s` 开头、以 `.c` 结尾且长度至少为五个字符的文件名（必须至少有一个字符来匹配 `.`）。`%` 匹配的子字符串称为主干（stem）。

模式规则前提中的 `%%` 代表被目标中 `%%` 匹配到的主干。为了使规则生效，其目标模式必须匹配正在考虑的文件名，且其前提模式必须匹配已存在或可以生成的文件名。这些文件将成为目标的前提条件。

因此，如下形式的规则

`%.o : %c;`

指定了如何生成一个 `.o` 文件，并将另一个文件 `.c` 作为其前提，前提是 `.c` 存在或可以生成。

可能存在不使用 `%` 的前提条件；此类前提将附加到由该模式规则生成的每个文件上。这些不变的前提条件偶尔很有用。

模式规则可以没有任何包含 `%` 的前提条件，或者事实上可以没有任何前提条件。这种规则实际上是一个通用的通配符。它提供了一种生成匹配目标模式的任何文件的方法。参见第 116 页第 10.6 节 [最后手段](Last Resort)。

模式规则可以有多个目标。与普通规则不同，这并不等同于具有相同前提和命令的多个不同规则。`make` 知道该规则的命令是为了生成所有目标。命令只执行一次以生成所有目标。在搜索匹配规则的模式规则时，除了匹配所需目标的那个规则外，其他规则的目标模式是附带的：`make` 只关心为当前正在处理的文件提供命令和前提。然而，当该文件的命令执行时，其他目标会被标记为已更新。

模式规则在 `Makefile` 中出现的顺序非常重要，因为它们会被按顺序考虑。在同样适用的规则中，只会找到第一个。你写的规则优先级高于其他规则。但注意，一个前提实际存在或被提到的规则，其优先级始终高于必须通过链式其他隐式规则来生成的前提规则。

#### 10.5.2 模式规则示例

这里是 `make` 中预定义的一些模式规则示例。首先是将 `.c` 文件编译为 `.o` 文件的规则：

```make
%.o : %.c
    $(CC) $(CFLAGS) -c -o $@
```

定义了一个可以从 `.c` 文件生成任何 `.o` 文件的规则。这里使用的自动变量是 `$@` 和 `$<`。

这是另一个例子：

```make
%.o : %.c
    $(CC) $(CFLAGS) -c $<
```

同样定义了一个可以从 `.c` 文件生成任何 `.o` 文件的规则。这里使用的自动变量是 `$@` 和 `$<`。

#### 10.5.3 自动变量

假设你正在编写一个将 `.c` 文件编译为 `.o` 文件的模式规则：如何使用自动变量？以下是自动变量表：

| 变量 | 说明 |
| :--- | :--- |
| `$0` | 目标文件名。如果是归档成员，则是目标名称。 |
| `$@` | 目标名称，除非目标是归档成员。 |
| `$%` | 当目标是归档成员时的目标名称。 |
| `$<` | 第一个前提的文件。如果目标从隐式规则获取命令，这将是第一个前提。 |
| `$?` | 所有比目标新的前提的文件名，用空格分隔。 |
| `$$` | 所有前提的文件名，用空格分隔。 |
| `$+` | 类似于 `*`，但多次列出的前提会按其列出顺序重复。 |
| `$*` | 隐式规则匹配的主干。 |

在静态规则中，`%` 是文件名中匹配目标模式中 `%` 的部分。在显式规则中没有主干；`*` 无法通过这种方式确定。相反，如果目标名称以识别的后缀结尾，则 `$*` 将设置为减去后缀后的目标名称。

与其他 `make` 的实现类似。通常你应该避免使用 `$*`，除非在隐式规则或静态模式规则中使用。

如果显式规则中的目标名称不以识别后缀结尾，则该规则的 `$*` 被设置为空字符串。

即使在显式规则中，当你只想操作发生变化的先条件时，`$?` 也是有用的。例如，假设一个名为 `lib` 的存档应该包含几个对象文件的副本。此规则仅将更改的对象文件拷贝到存档中：

```
lib:foo.o bar.o lose.o
ar $*
```

在上述列出的变量中，四个值是单个文件名，三个值的值是文件名列表。这七个变量都有变体，可以获取文件的目录名或仅是目录内的文件名。变体变量通过分别追加 `D` 或 `F` 形成。在 GNU `make` 中，这些变体是半过时的，因为可以使用 `dir` 和 `notdir` 函数来获得类似的效果（参见第 8.3 节 [文件名函数]，第 80 页）。但请注意，`D` 变体省略了所有在 `dir` 函数输出中出现的末尾斜杠。以下是变量表：

- `$(D)` : 目标文件名的目录部分，已去除了斜杠。如果 `$0` 的值为 `dir/foo.o`，那么 `$(D)` 就是 `$dir`。如果 `$0` 不包含斜杠，则该值为 ''。
- `$(F)` : 目标文件名的文件-目录部分。如果 `$0` 的值为 `dir/foo.o`，那么 `$(F)` 就是 `foo.o`。`$(F)` 等于 `$(notdir $0)`。



- `$(*D)` `$(*F)` : 茎（stem）的目录部分和目录内的文件名部分；在本例中为 'dir' 和 'foo'。

- `$($D)` `$($F)` : 存档成员名的目录部分和目录内的文件名部分。这对于形式为 'archive(member)' 的存档成员目标才有意义，并且成员可能包含目录名时有用。（参见第 11.1 节 [作为目标的存档成员]，第 121 页。）

- `$(*D)` `$(*F)` : 第一个先条件的目录部分和目录内的文件名部分。

- `$($D)` `$($F)` : 所有先条件的目录部分和目录内的文件名部分的列表。

- `$(?D)` `$(??)` : 比目标新的所有 `$(?)` 先条件的目录部分和目录内的文件名部分的列表。

请注意，当我们谈论这些自动变量时，使用了一种特殊的样式约定；我们写“the value of '$'”而不是变量 `'<'`，就像我们为对象和 `CFLAGS` 等普通变量所写的那样。我们认为这种约定在这种特殊情况下看起来更自然。请不要假设它有深层意义；`'$'` 指的是变量 `'<'`，就像 `$(CFLAGS)` 指的是名为 `CFLAGS` 的变量一样。你也可以直接用 `$($<)` 代替 `$`。

### 10.5.4 模式如何匹配

目标模式由前缀和后缀之间的 `%` 组成，其中一个或两者都可能为空。只有当文件名以前缀开头并以后缀结尾且不重叠时，该模式才匹配文件名。前缀和后缀之间的文本被称为“茎”（stem）。因此，当模式 `%.o` 匹配文件名 `test.o` 时，茎为 `test`。模式规则的先条件通过用茎替换字符 `%` 转换为实际文件。因此，如果示例中其中一个先条件写为 `%.c`，它将扩展为 `test.c`。

当目标模式不包含斜杠时（它通常不包含），在与目标前缀和后缀比较之前，文件名中的目录名会被移除。在将文件名与目标模式进行比较后，目录名以及结束它们的斜杠会被重新添加到从模式规则的先条件模式生成的先条件文件名和文件名中。目录仅在为了查找要使用的隐式规则时被忽略，而在应用该规则时不会忽略。因此，`%*` 匹配文件名 `src/eat`，以 `src/a` 为茎。当先条件转换为文件名时，茎的目录会被添加到前面，而茎的其余部分将替换为 `%`。茎 `src/a` 配合先条件模式 `%*r` 得到文件名 `src/car`。

### 10.5.5 匹配任意内容的规则

当模式规则的目标仅为 `%` 时，它可以匹配任何文件名无论是什么。我们称这些为“匹配任意内容的规则”。它们非常有用，但 make 思考这些规则可能会花费大量时间，因为它必须考虑每个列为目标或先条件的 Find名的每一个规则。

假设 makefile 中提到了 `foo.c`。对于此目标，make 将考虑通过链接对象文件 `foo.c.o`来制作它，或者通过从 `foo.c.o` 一步进行 C 编译和链接，或者通过从 `foo.c.p` 进行 Pascal 编译和链接，以及许多其他可能性。

我们知道这些可能性是荒谬的，因为 `foo.c` 是一个 C 源文件，而不是可执行文件。如果我们真的考虑了这些可能性，它最终会拒绝它们，因为像 `foo.c.o` 和 `foo.c.p` 等文件并不存在。但由于这些可能性如此多，如果我们必须考虑它们，make 运行将会很缓慢。

为了提高速度，我们对考虑匹配规则的方式施加了各种约束。有两种不同的约束可以应用，每当你定义一个匹配规则时，必须选择其中一种。

一种选择是通过双冒号将匹配规则定义为终止的（terminal）。当规则终止时，除非先条件实际存在，否则不会生效。换句话说，终止规则之后不允许进一步的链式反应。例如，如果文件 `foo.c,v` 不存在，内置规则甚至不会考虑从 `foo.c,v.o` 或从 `RCS/s.c,o` 制作它。

### 10.5.6 取消隐式规则

你可以通过定义一个具有相同目标和先条件但命令不同的新规则来覆盖内置规则（或你定义的规则）。当新规则被定义时，内置规则将被替换。新规则在隐式规则序列中的位置取决于你编写规则的位置。

你可以通过定义一个具有相同目标和先条件但没有命令的模式规则来取消内置规则。例如，以下内容将取消汇编器：

```
%.o : %s
```

### 10.6 定义最后的默认规则

你可以通过编写一个没有先条件的终止任意模式规则来定义最后的隐式规则（参见第 10.5.5 节 [匹配任意内容的规则]，第 114 页）。这与任何其他模式规则都相同；唯一的特殊之处在于它可以匹配任何目标。因此，此类规则的命令将用于所有没有自己的命令且没有隐式规则适的目标和先条件。

例如，在测试 amfile 时，你可能不在乎源文件是否包含真实数据，只要求它们存在。这时你可能会这样做：

```
%:
touch $@
```

从而自动创建所有所需的（作为先条件的）源文件。

你也可以为没有任何规则（甚至没有命令）的目标定义使用的命令。你通过编写目标 `.DEFAULT` 来实现。此类规则的命令将用于所有未在任何显式规则的目标中出现、且没有隐式规则适用的先条件。

如果你使用了不带命令或先条件的 `.DEFAULT`：

```
.DEFAULT:
```
之前存储在 `.DEFAULT` 中的命令将被清除。然后 make 的表现就像你从未定义过 `.DEFAULT` 一样。

# 第 10 章：使用隐式规则

你可以使用一种最后手段规则来覆盖另一个 Makefile 的部分。参见第 3.6 节 [覆盖另一个 Makefile 的部分]，第 15 页。

### 10.7 旧式后缀规则

后缀规则（Suffix rules）是为 make 定义隐式规则的旧式方法。后缀规则已经过时，因为模式规则（pattern rules）更通用、更清晰。为了兼容旧的 makefile，GNU make 支持后缀规则。它们分为两种类型：双后缀规则和单后缀规则。

双后缀规则由一对后缀定义：目标后缀和源后缀。它匹配任何以目标后缀结尾的文件。对应的隐式依赖项通过将文件名中的目标后缀替换为源后缀来生成。一个后缀为 `.o` 和 `.c` 的规则等同于模式 `%.o:%c`。

单后缀规则由单个后缀定义，该后缀即源后缀。它匹配任何文件名，对应的隐式依赖项名称通过附加源后缀来生成。后缀为 `.c` 的单后缀规则等同于模式 `%:%c`。

后缀规则通过将每个规则的目标与定义的后缀进行比较来识别。当 make 看到一个已知后缀时，该规则被视为单后缀规则。当 make 看到一个由两个已知后缀拼接而成的目标时，该规则被视为双后缀规则。

例如，`.c` 和 `.o` 都在默认的已知后缀列表中。因此，如果你定义一个目标为 `.o` 的规则，make 将其视为源后缀为 `.c`、目标后缀为 `.o` 的双后缀规则。以下是编译 C 源文件的旧式规则定义：

```
.c.o:
$(CC) -c $(CFLAGS) $(CPPLAGS) -o $$ $<
```

后缀规则不能有任何自己的依赖项。如果它们有任何依赖项，它们将被视为具有奇怪名称的普通文件，而不是后缀规则。因此，规则如下：

```
.c.o: foo.h
$(CC) -c $(CFLAGS) $(CPPLAGS) -o $$ $< $
```

告诉的是如何从依赖项 `foo.h` 生成 `.c` 文件，这与模式规则完全不同：

```
%.o:%c foo.h
$(CC) -c $(CFLAGS) $(CPPLAGS) -o $$ $< $
```

告诉的是如何使用 `.c` 文件制作 `.o` 文件，并使得所有使用此模式规则的 `.o` 文件依赖于 `foo.h`。

没有命令的后缀规则也是没有意义的。它们不会没有命令的模式规则那样移除之前的规则（参见第 10.5.6 节 [取消隐式规则]，第 116 页）。它们只是将后缀或拼接的后缀作为目标进入数据库。

已知后缀只是特殊目标 `.SUFFIXES` 的名称。你可以通过编写一个为 `.SUFFIXES` 规则添加更多依赖项来添加自己的后缀，例如：

```
.SUFFIXES: .hack .win
```

这将 `.hack` 和 `.win` 添加到后缀列表的末尾。

如果你想消除默认已知后缀而不是仅仅添加，请编写一个没有依赖项的 `.SUFFIXES` 规则。通过特殊许可，这将消除 `.SUFFIXES` 的所有现有依赖项。然后你可以编写另一个规则来添加你需要的后缀。例如：

```
.SUFFIXES:
    # 删除默认后缀
.SUFFIXES: .c .o .h # 定义我们的后缀列表
```

`-r` 或 `--no-builtin-rules` 标志会导致默认后缀列表为空。

变量 `VARIABLE` 在 make 读取任何 makefile 之前定义在默认后缀列表中。你可以通过针对特殊目标 `.SUFFIXES` 的规则更改后缀列表，但这不会改变此变量。

## 10.8 隐式规则搜索算法

这里是 make 用于为目标 `t` 搜索隐式规则的步骤。该步骤适用于每个没有命令的双冒号规则、每个没有命令的普通规则的目标，以及每个不是任何规则的目标的依赖项。对于来自隐式规则的依赖项，在搜索规则链时，也会以递归方式执行该步骤。

该算法中没有提到后缀规则，因为一旦 makefile 被读入，后缀规则就会被转换为等价的模式规则。



对于形式为 `archive(member)` 的归档成员，将运行两次算法：第一次使用整个目标名称 `t`，如果第一次运行没有找到规则，则第二次使用 `(member)` 作为目标 `t`。
- 1. 将 `t` 拆分为目录部分 `d` 和结果 `n`。例如，如果 `t` 是 `src/foo.o`，则 `d` 是 `src/`，`n` 是 `foo.o`。
- 2. 创建所有目标匹配 `t` 或 `n` 的模式规则列表。如果目标模式包含斜杠，则与 `t` 匹配；否则与 `n` 匹配。
- 3. 如果列表中的任何规则不是通配规则（`match-anything rule`），则从列表中移除所有非终结的通配规则。
- 4. 从列表中移除所有没有命令的规则。
- 5. 对于列表中的每个模式规则：
    - a. 找到基干 `s`，它是 `t` 中被目标模式中的 `%` 匹配的非空部分。
    - b. 通过将 `s` 替换为 `%;` 计算依赖项名称；如果目标模式不包含斜杠，则在每个依赖项名称的前附加 `d`。
    - c. 测试所有依赖项是否存在或是否应当存在。（如果文件名在 `makefile` 中作为目标或显式依赖项提到，则我们说它应当存在。）
- 如果所有依赖项都存在或应当存在，且没有依赖项，则该规则适用。
- 6. 如果目前没有找到任何模式规则，则加大尝试。对于列表中的每个模式规则：
    - a. 如果规则是终结的，忽略它并继续处理下一个规则。
    - b. 计算“应当存在”的依赖项名称。
    - c. 测试所有依赖项是否存在或应当存在。
    - d. 对于每个不存在的依赖项，递归遵循此算法以查看该依赖项是否可以由隐式规则制作。
    - e. 如果所有依赖项都存在、应当存在或可以由隐式规则制作，则该规则适用。
- 7. 如果没有隐式规则适用，则 `.DEFAULT` 的规则（如果有）适用。在这种情况下，为 `t` 赋予 `.DEFAULT` 所拥有的命令。否则，`t` 没有命令。

一旦找到适用的规则，对于除了匹配 `t` 的模式以外的每个模式，模式中的 `%` 被替换为 `s` 并执行生成的文件。这些被输入数据库并标记为已更新。当为 `t` 执行模式规则的命令时，自动变量将被设置。参见第 10.5.3 节 [自动变量]，第 111 页。

# 第 11 章：使用 make 更新归档文件

## 11 使用 make 更新归档文件

归档文件是包含成员（`members`）的文件；它们由 `ar` 程序维护，其主要用途是链接库。

### 11.1 成员作为目标

归档文件的单个成员可以作为 `make` 中的目标或依赖项。你通过以下方式指定归档文件中的成员：

```
archive(member)
```

这种构造仅适用于目标，不适用于命令！你用于命令的大多数程序不支持这种语法，无法直接操作归档成员。只有 `ar` 和其他专门为归档设计的程序可以做到。例如，此规则通过拷贝文件 `hack.o` 在归档 `foolib` 中创建一个成员 `hack.o`：

```
foolib(hack.o) : hack.o
ar cr foolib hack.o
```

事实上，几乎所有的归档成员目标都以此方式更新，并且有一个隐式规则为你完成。注意：如果归档文件不存在，则需要 `ar` 的 `c` 标志。要在同一个归档中指定多个成员，你可以将所有成员名称写在括号内。例如：

```
foolib(hack.o kludge.o)
```

等同于：

```
foolib(hack.o) foolib(kludge.o)
```

你也可以在归档成员引用中使用 shell 通配符。参见第 4.2 节 [文件名中使用通配符字符]，第 20 页。例如，`foolib(*.o)` 扩展为所有以 `.o` 结尾的 `foolib` 归档成员；

## 11.2 归档成员目标的隐式规则

记得类似于 `a(m)` 的目标代表归档文件 `a` 中名为 `m` 的成员。当 `make` 为此类目标查找隐式规则时，作为一项特殊特性，它考虑匹配 `(m)` 的规则以及匹配实际目标 `a(m)` 的规则。这导致一个目标为 `(*)` 的特殊规则匹配。该规则通过将文件 `m` 拷贝到归档来更新目标 `a(m)`。例如，

它通过将文件 `bar.o` 复制到存档 `foo.a` 中作为名为 `bar.o` 的成员来更新存档成员目标 `foo.a(bar.o)`。

当此规则与其他规则链联时，结果非常强大。因此，在存在文件 `bar.c` 的情况下，执行 `make foo.a(bar.o)`（引号用于防止 `(` 和 `)` 被 shell 特殊解释为特殊字符）就足够在即使没有 `makefile` 的情况下也能运行以下命令：

```
cc -c bar.c -o bar.o
ar r foo.a bar.o
rm -f bar.o
```

在这里，`make` 将文件 `bar.o` 视为一个中间文件。参见第 10.4 节 [隐式规则链](Chains of Implicit Rules)，第 108 页。

这样的隐式规则使用自动变量 `$*` 编写。参见第 10.5.3 节 [自动变量](Automatic Variables)，第 111 页。

存档中的成员名不能包含目录名，但在 Makefile 中假装它包含目录名可能是有用的。如果你写存档成员目标 `foo.a(dir/file.o)`，`make` 将执行此命令进行自动更新：

```
ar r dir/file.o
```

其效果是将文件 `dir/file.o` 复制到名为 `file.o` 的成员中。在使用此类用法时，自动变量 `%D` 和 `%F` 可能会很有用。

### 11.2.1 更新存档符号目录

作为库使用的归档文件通常包含一个特殊成员 `..SYMDEF`，它包含了所有其他成员定义的外部符号名称目录。在你更新了任何其他成员后，需要更新 `..SYMDEF` 以使其能够正确汇总其他成员。这是通过运行 `ranlib` 命令实现的：

```
ranlib archivefile
```

通常，你会将此命令放在存档文件的规则中，并将存档文件的所有成员设为该规则的前提条件。例如：

```
libfoo.a:(x.o) libfoo.a(y.o) ...
ranlib libfoo.a
```

此举的效果是更新存档成员 `x.o`、`y.o` 等，然后通过运行 `ranlib` 更新符号目录成员 `..SYMDEF`。更新成员的规则此处未显示；你可能可以省略它们，并使用前节描述的将文件复制到存档的隐式规则。

在运行 GNU 程序时这是没有必要的，因为它会自动更新 `..SYMDEF`。

## 11.3 使用存档的危险

在使用并行执行（`-j` 选项；参见第 5.3 节 [并行执行](Parallel Execution)，第 43 页）和存档时，请务必小心。如果多个命令同时在同一个存档上运行，它们将无法相互感知并可能损坏文件。

未来的 `make` 版本可能会提供一种机制，通过对所有操作同一个存档文件的命令进行序列化来规避此问题。但目前，你必须通过其他方式编写 `makefile` 来避免这个问题，或者不使用 `-j`。

## 11.4 存档文件的后缀规则

你可以创建一种特殊的后缀规则来处理存档文件。请参见第 10.7 节 [后缀规则](Suffix Rules)，第 117 页以获取后缀规则的完整说明。存档规则在 GNU `make` 中已经过时，因为用于存档的模式规则是一种更通用的机制（参见第 11.2 节 [存档更新](Archive Update)，第 121 页）。但为了与其他方法兼容，它们被保留了下来。

要为存档编写后缀规则，只需编写一个使用目标后缀 `*.a`（存档文件的常用后缀）的后缀规则。例如，这里有一个从 C 源文件更新库存档的旧式后缀规则：

```
.c:a:
$(CC) $(CFLAGS) $(CPPFLAGS) -c $< -o $.*
$(AR) r $* $.*
$(RM) $.*
```

只有在你编写了以下模式规则时，它才有效：

```
%.o: %.c
$(CC) $(CFLAGS) $(CPPFLAGS) -c $< -o $.*
$(AR) r $* $.*
$(RM) $.*
```

事实上，这正是 `make` 在看到以 `.a` 为目标后缀的后缀规则时所做的事情。任何双后缀规则 `*.x.a` 都会被转换为目标模式为 `%.o` 前提模式为 `%.x` 的模式规则。

由于你想将 `*.a` 作为其他类型文件的后缀，`make` 也会以正常方式将存档规则转换为模式规则（参见第 10.7 节 [后缀规则](Suffix Rules)，第 117 页）。因此，双后缀规则 `*.x.a` 会产生两个模式规则：`%.o: %.x` 和 `%.a: %.x`。

# 第 13 章：不兼容性与缺失的功能

## 13 不兼容性和缺失的功能

其他各种系统的 make 程序支持一些 GNU make 未实现的功能。指定 make 的 POSIX 2.standard（IEEE 标准 1003.2-1992）并不要求这些功能中的任何。

- 形式为 `'file((entry))'` 的目标代表存档文件 *file* 的成员。该成员的选择不是通过名称，而是通过它是定义链接器符号 *entry* 的对象文件。

  此功能没有被放入 GNU make，是因为将存档文件表内部格式的知识放入 make 中是不符合模块化的原则。参见第 11.2.1 节 [更新存档目录]，第 122 页。
- 以字符 `'-'` 结尾的后缀（用于后缀规则）对 System V make 具有特殊含义；它们指向与不带 `'-'` 的时可以获得的文件相对应的 SCCS 文件。例如，后缀规则 `'.c'` 会从 SCCS 文件 `'s.n.c'` 生成文件 `'n.o'`。为了完全覆盖，需要一系列后缀规则。参见第 10.7 节 [旧式 S 规则]，第 117 页。

  在 GNU make 中，这一系列情况通过两个从 SCCS 提取的规则，结合规则链的通用功能来处理。参见第 10.4 节 [隐式规则链]，第 108 页。
- 在 System V make 中，字符串 `'$$'` 具有奇怪的含义：在具有多个目标的 make 的先决项中，它代表正在处理的具体目标。

  这在 GNU make 中没有定义，因为 `'$$'` 将始终代表一个普通的 `'$'`。

  通过使用静态模式规则可以获得部分功能（参见第 4.10 节 [静态模式规则]，第 34 页）。System V make 规则：

```
$(targets): $$.o lib.a
```

  可以用 GNU make 的静态模式规则替换：

```
$(targets): %.o lib.a
```

- 在 System V make 中，字符串 `'$$'` 具有奇怪的含义：在具有多个目标的 make 的先决项中，它代表正在处理的具体目标。

  此功能在 GNU make 中没有定义，因为 `'$$'` 将始终代表一个普通的 `'$'`。

  通过使用静态模式规则可以获得部分功能（参见第 4.10 节 [静态模式规则]，第 34 页）。System V make 规则：

```

```

  可以用 GNU make 的静态模式规则替换：


## 14 章：Makefile 规范

本章描述了编写 GNU 程序 Makefile 的规范。使用 `Automify` 将帮助你编写遵循这些规范的 Makefile。

### 14.1 Makefile 的通用规范

每个 Makefile 都应该包含这一行：

```
SHELL = /bin/sh
```

以免在 `SHELL` 变量可能从环境中继承的情况下出错。（在 GNU make 中这不是问题。）

不同的 make 程序具有不兼容的后缀列表，有时这会导致混淆或异常行为。因此，在特定的 Makefile 中显式设置你需要的后缀是一个好主，如下：

```
.SUFFIXES:
.SUFFIXES: .c .o
```

第一行清除后缀列表，第二行引入可能受隐式规则影响的所有后缀。

不要假设 `.` 在命令执行路径中。当你在 make 期间运行包的一部分程序时，请确保如果程序是作为 make 构建的则使用 `./`，如果文件是源代码不变的部分则使用 `$(srcdir)`。如果没有这些前缀之一，将使用当前搜索路径。

`./`（构建目录）和 `$(srcdir)/`（源码目录）之间的区别是重要的，因为用户可以使用 `--srcdir` 选项在独立的目录中构建。如下规则：

```
foo.1: man sedcript
sed -e sedcript foo.man > foo.1
```

当构建目录不是源码目录时将会失败，因为 `foo.man` 和 `sedscript` 在源码目录中。

在 GNU make 中，依赖 `VPATH` 来查找源文件在只有一个依赖文件的情况下是有效的，因为 make 自动变量 `$<` 将代表源文件，无论它在哪里。（许多 make 版本仅在隐式规则中设置 `$<`。）一个 Makefile 目标：

```
foo.o: bar.c
$(CC) -I-$(srcdir) $(CFLAGS) -c bar.c -o foo.o
```

应该写成

```
foo.o: bar.c
$(CC) -I-$(srcdir) $(CFLAGS) -c $< -o $$
```

为了让 `VPATH` 正常工作，当目标有多个依赖项时，显式使用 `$(srcdir)` 是让规则正常运行最简单的方法。例如，上述 `foo.1` 目标的写法如下：

```
foo.1 foo:man sedscript
s -e $(srcdir)/sedscript $(srcdir)/foo.man > $0
```

GNU 分发版通常包含一些不是源文件的文件——例如 Info 以及来自 Autoconf、Automake、Bison 或 Flex 的输出。由于这些文件通常出现在源代码目录中，它们应该始终出现在源代码目录，而不是构建目录中。因此，更新这些文件的 Makefile 规则应该使用源代码目录中的更新文件。

然而，如果一个文件没有出现在分发包中，那么 Makefile 不应将其放入源代码目录，因为在任何情况下，编译程序都不应该以任何方式修改源代码目录。

尝试让 build 和 install 目标（至少，以及它们所有的子目标）在并行执行 make 时能够正常工作。

## 14.3 用于指定命令的变量

`Makefile` 应该提供变量来覆盖某些命令、选项等。

特别地，你应该通过变量运行大多数工具程序。因此，如果你使用 `Bison`，应定义一个名为 `BISON` 的变量，其默认值设置为 `'BISON = bison'`，并在需要使用 `Bison` 时通过 `$(BISON)` 引用它。

文件管理工具如 `ln`、`rm`、`mv` 等不需要以这种方式通过变量引用，因为用户不需要将它们替换为其他程序。

每个程序名变量都应该带有一个选项，用于为程序提供选项。在程序名变量后附加 `FLAGS` 来获取选项变量——例如，`BINFLAGS`。`C` 编译器的 `CFLAGS`、`yacc` 的 `YFLAGS` 和 `lex` 的 `LFLAGS` 是此规则的例外，但我们保留了它们，因为它们是标准的。在任何运行预处理编译命令中使用 `CPPFLAGS`，并在任何运行链接的编译命令以及直接使用 `ld` 时使用 `LDFLAGS`。

如果为了正确编译某些文件必须使用某些 `C` 选项，不要将它们包含在 `CFLAGS` 中，以便能够指定 `CFLAGS` 本身。相反，安排独立于 `CFLAGS` 将必要的选项传递给 `C` 编译器，通过在编译命令中显式编写或通过定义隐式规则来实现：

```
CFLAGS = -G
ALL_CFLAGS = -I. $(CFLAGS)
.o: %.c -c $(CPPFLAGS) $(ALL_CFLAGS) $
```

一定要在 `CFLAGS` 中包含 `'g'` 选项，因为这对于正确编译不是必须的。你可以考虑一个仅建议的默认值。如果包设置成默认用 `GCC` 编译，那么你也可以在 `CFLAGS` 的默认值中包含 `'-O'`。

在编译命令中将 `CFLAGS` 放在最后，放在其他包含选项的变量之后，这样用户可以使用 `CFLAGS` 覆盖其他变量。

`CFLAGS` 应该在每次调用 `C` 编译器时使用，无论是编译还是链接阶段。

## 14.4 用于安装目录的变量

通常，`$(prefix)` 用于包含机器特定文件的目录（如可执行文件和库），而 `$(prefix)` 直接用于其他目录。

如果运行 `'make install'` 时使用的 `exec_prefix` 与编译程序时的不同，则应重新编译程序。

可执行程序安装在以下目录之一：

- `bindir`: 安装用户可以运行的可执行程序的目录。这通常应该是 `'/usr/local/bin'`，但应写为 `'$(exec_prefix)/bin'`。如果你使用 `Autoconf`，请写为 `'$(bindir)'`。

- `sbindir`: 安装可以在 shell 中运行但通常仅供系统管理员的可执行程序的目录。这通常应该是 `'/usr/local/sbin'`，但应写为 `'$(exec_prefix)/sbin'`。如果你使用 `Autoconf`，请写为 `'$(sbindir)'`。

- `libexecdir`: 安装供其他程序而非用户运行的可执行程序的目录。该目录通常应该是 `'/usr/local/libexec'`，但应写为 `'$(exec_prefix)/libexec'`。如果你使用 `Autoconf`，请写为 `'$(libexecdir)'`。

程序执行期间使用的数据文件分为两种方式：

- 某些文件通常被程序修改；另一些通常不被修改（尽管用户可能会编辑某些）。

- 某些文件是架构无关的，可以在站点的所有机器间共享；某些是架构相关的，可以在相同类型和操作系统的机器间共享；其他可能永远不在两台机器之间共享。

这产生了六种可能性。然而，我们反对使用架构相关的文件（对象文件和库之外）。将其他数据文件变为架构无关要干净得多，而且通常并不困难。

因此，以下是 `Makefile` 用于指定目录的变量：

- `datadir`: 安装只读独立数据文件的目录。这通常应该是 `'/usr/local/share'`；但应写为 `'$(prefix)/share'`。如果你使用 `Autoconf`，请写为 `'$(datadir)'`。作为特殊例外，见 ` '$(infodir)'` 和 ` '$(includedir)'`。

### sysconfdir

用于安装与单个机器相关的只读数据文件的目录——也就是说，用于配置主机的文件。邮件发送程序和网络配置文件、`'/etc/passwd'` 等。此目录中的所有文件都应该是普通的 `ASCII` 文本文件。该目录通常为 `'/usr/local/etc'`，但应写为 `$(prefix)/etc`。如果你正在使用 `Autoconf`，请将其写为 `$@sysconfdir@`。

不要在此目录中安装可执行文件（它们可能属于 `$(libexecdir)` 或 `$(sbindir)`）。也不要安装在正常使用过程中会被修改的文件（目的是更改系统配置的程序除外）。这些文件可能属于 `$(localstatedir)`。

### sharedstatedir

用于安装程序在运行时会修改的与架构无关数据的目录。这通常应该是 `'/usr/local/com'`，但应写为 `$(prefix)/com`。如果你正在使用 `Autoconf`，请将其写为 `@sharedstatedir@`。

### localstatedir

用于安装程序在运行时会修改的且与特定机器相关的数据文件的目录。用户永远不需要通过修改此目录中的文件来配置运行；请将配置信息放在进入 `$(datadir)` 或 `$(sysconfdir)` 的独立文件中。`$(localstatedir)` 通常应该是 `'/usr/local/var'`，但应写为 `$(prefix)/var`。如果你正在使用 `Autoconf`，请将其写为 `@localstatedir@`。

### libdir

用于安装对象文件和对象代码库的目录。不要在此处安装可执行文件，它们应该进入 `$(libexecdir)`。`libdir` 的值通常应该是 `'/usr/local/lib'`，但应写为 `$(prefix)/lib`。如果你正在使用 `Autoconf`，请将其写为 `@libdir@`。

### infodir

用于安装此包的 `Info` 文件的目录。默认情况下，它应该是 `'/usr/local/info'`，但应写为 `$(prefix)/info`。如果你正在使用 `Autoconf`，请将其写为 `@infodir@`。

`includedir` 用于安装用户程序通过 C 语言 `#include` 预处理器指令包含的头文件的目录。这通常应该是 `/usr/local/include`，但应写为 `$(prefix)/include`。如果你正在使用 Autoconf，请将其写为 `@includedir`。

`oldincludedir` 用于安装供 GCC 以外使用的 `#include` 头文件的目录。这通常应该是 `/usr/include`。如果你正在使用 Autoconf，你可以将其写为 `@oldincludedir`。

## 14.6 安装命令分类

在编写 `install` 目标时，必须将所有命令分为三类：普通命令、安装前命令和安装后命令。

普通命令将文件移动到正确的位置并设置模式。它们不能修改除所属软件包之外的任何文件。

安装前命令和安装后命令可能会修改其他文件；特别是它们可以编辑全局配置文件或数据数据库。

安装前命令通常在普通命令之前执行，安装后命令通常在普通命令之后运行。

### GNU make

大多数程序都不需要预安装命令，但我们保留了这一功能以备不时之需。

要将 `install` 规则中的命令分类为这三类，请在它们之间插入类别行。类别行指定了后续命令所属的类别。

类别行由一个制表符、对特殊 Make 变量的引用以及末尾可选的注释组成。你可以使用三个变量，每个对应一个类别；变量名指定了类别。在普通执行中，类别行是无操作（no-op），因为这三个 Make 变量通常在最后定义（你不应该在 Makefile 中定义它们）。

这里是三个可能的类别行，每行都带有一个解释含义的注释：

```
$(PRE_INSTALL)   # 后续为预安装命令。
$(POST_INSTALL)  # 后续为安装后命令。
$(NORMAL_INSTALL) # 后续为普通命令。
```

如果你不在 `install` 规则的开头使用类别行，则在第一个类别行出现之前，所有命令都将被归类为普通。如果你不任何类别行，则所有命令都归类为普通。

这些是卸载的类别行：

```
$(PRE_UNINSTALL)   # 后续为预卸载命令。
$(POST_UNINSTALL)  # 后续为卸载后命令。
$(NORMAL_UNINSTALL) # 后续为普通命令。
```

通常，预卸载命令用于删除 Info 目录中的条目。

如果 `install` 或 `uninstall` 目标具有作为安装子程序的依赖项，你应该每个依赖项的命令以类别行开头，并且主目标的命令也以类别行开头。这样，无论实际运行了哪个依赖项，都能确保每个命令都放置在正确的类别中。

预安装和安装后命令不应运行以下以外的任何程序：

```

grep expand false fgrep getopt grep gunzip gzip
hostname install-info kill ldconfig ls msum
mkdir mkfifo mkdn mv prentv pwd rmdir sed sort tee
test true uname xargs yes
```

错误消息均以程序名称（通常为 `'make'`）为开头，或者如果在 `Makefile` 中发现错误，则以包含问题的文件名和行号为开头。

- `'[foo] Error NN'`
- `'[foo] signal description`

- `'missing separator. Stop.'`
- `'missing separator (did you mean TAB instead of 8 spaces?). Stop.'`

这意味着 `make` 无法理解它刚刚读取的命令的任何内容。`GNU make` 寻找各种分隔符（`:`, `,`, `=`, `TAB` 字符等）来帮助判断它是哪种命令行。这意味着它没有找到有效的分隔符。

- `'commands commence first target. Stop.'`
- `'missing rule before commands. Stop.'`

这意味着 `Makefile` 中的第一项似乎是命令脚本的一部分：它以 `TAB` 字符开头，并且看起来不是合法的 `make` 命令（例如变量赋值）。命令行脚本必须与目标相关。

第二种格式如果行具有分号作为第一个非空白字符；`make` 将其解释为你遗漏了“目标:”部分。参见第 4.1 节 `[语法]`，第 19 页。

章节是不变的。要做到这一点，请将您的标题添加到修改版许可声明中的中的“不变章节”（Invariant Sections）列表中。这些标题必须与任何其他章节标题区分开来。

您可以添加一个名为“背书”（Endorsements）的章节，前提是该章节仅包含各方对您的“修改版”（Modified Version）的背书——例如，同行评审声明，或该文本已被某机构批准为该标准的权威定义。

您可以在修改版的“封面文本”（Cover Texts）列表末尾添加一段最多五个字的“前封面文本”（Front-Cover Text），以及一段最多 25 个字的“封底文本”（Back-Cover Text）。任何实体只能添加一段前封面文本和一段封底文本（或通过安排添加）。如果文档已经包含了针对相同封面的相同封面文本，且该文本是此前由您添加的或由您所代表的同一实体安排添加的，则您不能再次添加；但您可以替换旧的，前提是获得添加旧文本的前任出版者的明确许可。

文档的作者和出版者并不通过本许可允许将其姓名用于宣传，或主张或暗示对任何“修改版”的背书。

## 5. 合并文档

您可以将文档与其他根据本许可证发布的文档合并，并遵循上述第 4 节中定义的修改版条款，前提是您必须在合并中包含所有原始文档的所有未经修改的“不变章节”，并在其许可声明中将其列为您的合并作品的所有“不变章节”。

合并后的作品只需包含一份本许可证副本，多个相同的“不变章节”可以替换为一份副本。如果存在多个名称相同但内容不同的“不变章节”，请在每个此类章节的标题末尾用括号添加该章节的原始作者或出版者的名称（如果已知），否则添加一个唯一的数字，以此创建每个章节的标题。对合并作品许可声明中“不变章节”列表中的章节标题进行同样的调整。

在合并物中，您必须将各种原始文档中任何名为“历史”（History）的章节合并成一个名为“历史”的章节；同样，合并任何名为“致谢”（Acknowledgments）的章节以及任何名为“献辞”（Dedications）的章节。您必须删除所有名为“背书”（Endorsements）的章节。

# 6. 文档集

您可以由该文档和其他根据本许可证发布的文档组成一个集合，并将各种文档中的各个本许可证副本替换为包含在集合中的单一副本，前提是您遵循本许可证的规则，在各方面对每份文档进行逐字复制。

您可以从此类集合中提取单个文档，并根据本许可证对其进行单独分发，前提是您在提取的文档中插入一份本许可证副本，并在关于该文档逐字复制的所有其他方面遵循本许可证。

# 7. 与独立作品的聚合

将文档或其衍生版本与独立的文档或作品编译在存储或分发介质的卷中或其上，其整体并不被视为该文档的“修改版”，前提是未对该编译物主张编译版权。此类编译物被称为“聚合物”（aggregate），本许可证不适用于以此方式与文档一起编译的其他自包含作品，如果这些作品本身不是文档的衍生作品，则不会因为这样被编译而受到限制。

如果第 3 节的封面文本要求适用于这些文档副本，且文档少于整个聚合物的四分之一，则文档的封面文本可以放置在聚合物中仅包围文档的封面上。否则，它必须出现在围绕整个聚合物的封面上。

# 8. 翻译

翻译被视为一种修改，因此您可以根据第 4 节的条款分发文档的翻译。将“不变章节”替换为翻译文需要您的版权持有者的特殊许可，您可以在包含这些“不变章节”原始版本的基础上，包含部分或全部的翻译。您可以包含本许可证的翻译，前提是您也包含了本许可证的原始英文版本。如果翻译与本许可证的原始英文版本发生分歧，以原始英文版本为准。

# 9. 终止

除非本许可证规定，否则您不得复制、修改、分许可或分发文档。任何其他尝试复制、修改、分许可或分发文档的尝试均为无效，并将自动终止您根据本许可证享有的权利。然而，根据本许可证从您处获得副本或权利的方，只要这些方保持完全合规，其许可就不会终止。

# 10. 本许可证的未来修订

自由软件基金可能会随时发布 GNU 自由文档许可证的新修订版本。这些新版本在精神上与当前版本相似，但在细节上可能有所不同，以解决新的问题或关注点。请访问 `http://www.gnu.org/copyleft/`

每个版本的许可证都给出了一个不同的版本号。如果文档指定本许可证的某个特定编号版本“或任何后续版本”适用于它，则您可以选择遵循该指定版本或自由软件基金已发布（非以草案形式发布）的任何后续版本的条款和条件。如果文档未指定本许可证的版本号，您可以选择自由软件基金发布过的任何版本（非以草案形式发布）。

## D.1 如何在您的文档中使用本许可证

若要在您编写的文档中使用本许可证，请在文档中包含一份许可证副本，并并在标题页之后紧跟以下版权和许可声明：

版权所有 (C) 您的姓名。
根据 GNU 自由文档许可证第 1 版或自由软件基金发布的任何后续版本的条款，允许复制、分发和修改本文；并附带“不变章节”列表及其标题、“前封面文本”列表以及“封底文本”列表。

如果您没有“不变章节”，请写“无不变章节”（no Invariant Sections）而不是说明哪些是不变的。如果您没有“前封面文本”，请写“无前封面文本”（no Front-Cover Texts）而不是“封底文本”（Back-Cover Texts）。

如果您的文档包含非平凡的程序代码示例，我们建议根据您选择的自由许可证（如通用公共许可证）并行发布这些示例，以便允许在自由软件中使用。

# GNU Make

Make 工具实现了编译过程的自动化；当大型程序的源文件发生变化时，它特别有用。GNU Make 变得越来越流行，因为它能够满足自由软件系统黑客在系统管理方面的需求。它是一个小而功能强大的程序。

本教程由 Make 程序的作者编写，是权威性的，专为从初学者到专家的所有各个水平的用户而精心设计。它解释了基础知识以及进阶功能，并为专家准备了方便的快速参考附录。

本书将向你展示：

- 如何编写你自己的伪 Make 文件（makefakes）
- Make 的规则语法以及如何编写你自己的规则
- 如何配置 Make 工具以自动将二进制文件和源文件放在正确的位置
- 如何使用 Make 自动创建归档文件
- 定义、设置和使用 Make 变量
