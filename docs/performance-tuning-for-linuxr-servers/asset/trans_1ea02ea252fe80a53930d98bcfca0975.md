# Linux 2.6 的新特性

本研究仅参考对系统性能有深远影响的 Linux 2.6 新组件；它并不涵盖 Linux 2.6 的所有新特性。

## rmap 和 objrmap

Linux 2.6 内核的一个新 VM 特性被称为反向映射（rmap）。在 Linux 2.4 内核中，存在单个 pte 到 page 结构体的映射，这种技术对于进程寻址来说已经足够。然而，这种实现为页面置换算法带来了挑战，因为必须处理共享页面。在没有遍历系统中每个活动进程的页表的情况下，获取映射特定 page 结构体的 pte 列表是不可行的。给定一个物理内存页，rmap 允许 VM 识别正在使用该页面的进程。从实现角度来看，Linux 2.6 在 page 结构体中引入了一个联合体 pte 组件。当页面在进程之间共享时，会创建一个 pte 链并链接到此字段。slab 分配器管理 pte 链元素，每个节点可以定位多达 NRPTI 个 pte（NRPTI 与目标架构的 L1 缓存大小相关）。总结来说，2.4 内核逐个进程扫描所有页表，使适合页面的条目失效。新数据结构的引入使内核能够识别引用特定物理页的页表条目。这种实现的问题在于，所引入的方法内存密集，并且需要大量的维护。与 Linux 2.4 相比，诸如页故障、munmap 或 fork 等操作在执行速度上遇到了放缓。fork() 系统调用变慢，因为必须利用 rmap 为进程地址空间中的每个页面添加一个新的反向映射条目。基于对象的反向映射（ObjRMAP）的引入与 rmap 不同。在 ObjRMAP 中，page 结构体利用 mapping 文件指向 address\_space 结构，该结构描述了支撑特定页面的对象。address\_space 结构包含两个链表，其中包含每个在文件中具有映射的进程的 vm\_area\_struct (vma) 结构。vma 提供了定位页面虚拟地址所需的信息，该虚拟地址可用于识别正确的页表条目。基于对象的方法消除了 rmap 中找到的直接条目方法，page 结构直接指向页表条目。通过查阅 address\_space 以及 vma 结构来通过 ObjRMAP 识别页表条目需要更长时间，但与 rmap 实现相比，应以大大减少的开销系数完成。

## 大页支持

大多数现代计算机架构支持不止一种页面大小。例如，IA-32 架构支持 4KB 或 4MB 页面；Linux 操作系统仅将大页用于映射实际的内核映像。

大页的使用主要旨在为高性能计算（HPC）和其他内存密集型应用程序提供性能提升。任何内存访问密集型的、利用大量虚拟内存的应用程序都可以通过使用大页获得性能提升。（Linux 使用 2MB 或 4MB 大页，AIX 使用 16MB 大页，Solaris 使用 4MB。）大页的性能提升归因于转换后备缓冲器（TLB）缺失的减少，因为 TLB 能够映射更大的虚拟内存范围（通过增加 TLB 的覆盖范围）。大页还通过消除在 4KB 边界上重启预取操作的需要，改进了内存预取过程。

在 Linux 2.6 中，可用的大页数量可以通过 proc（`/proc/sys/vm/nr_hugepages`）接口进行配置。由于大页的实际分配取决于物理连续内存区域的可用性，建议系统在启动时启动分配。Linux 2.6 中核心大页实现被称为 hugetlbfs，这是一个基于 ramfs 的伪文件系统（实现在 `fs/hugetlbfs/inode.c` 中）。实现背后的理念是，大页用于支撑文件系统中的任何文件。实际的伪文件系统在系统启动时初始化，并注册为内部文件系统。进程可以通过 `shmat()` 接口建立由大页支撑的共享区域，或通过在使用大页文件系统中打开的文件上利用 `mmap()` 调用来访问大页。要操作使用大页的文件，必须首先挂载 hugetlbfs 文件系统。在挂载操作完成后，可以使用 `open()` 等标准文件操作调用设置文件描述符。如果使用 `mmap()` 系统调用打开文件，hugetlbfs 注册的 `mmap()` 函数会为进程创建适当的 vma 结构。建议使用 `/proc/meminfo` 接口，以确保大页的大小和数量如预期那样设置。碎片化可能会阻止分配过程成功完成。

## 页面分配与置换

Linux 2.6 中的物理页面分配仍然基于伙伴算法，但机制本身已扩展为类似惰性伙伴方案，该方案推迟合并部分。合并部分的缓冲区释放活动涉及一个两步过程，第一步是将缓冲区推回空闲列表。这使得缓冲区对其他请求可用。第二步涉及将缓冲区引用为空闲（通常在位图中）并合并缓冲区（如果可行）与相邻缓冲区。常规的伙伴系统实现在每次释放时执行这两个步骤。惰性伙伴方案执行第一步，但推迟第二步，并根据缓冲区类的状态执行它。所讨论的惰性伙伴概念的 Linux 2.6 实现利用每 CPU 页面列表。这些 pageset 包含两个页面列表（标记为热和冷），其中热页面最近被使用，预期它们仍然存在于 CPU 缓存中。在分配时，首先查询运行中 CPU 的 pageset 以确定页面是否可用；如果是，则相应地进行分配。为了确定何时应释放或分配 pageset，使用基于低水位和高水位的方案。当达到低水位时，分配一批页面并放置在列表上。当达到高水位时，同时释放一批页面。作为新改进实现的结果，自旋锁开销显著减少。

在 2.4 Linux 内核中，kswapd，一个全局守护进程，充当页面置换的激活器。kswapd 负责保持一定量的内存可用，并在内存压力下启动释放页面的过程。在 Linux 2.6 中，系统中每个节点都有一个 kswapd 守护进程。这种设计背后的理念是避免 swapd 不得不代表远程节点释放页面的情况。在 Linux 2.4 中，在从 LRU 列表移除页面前必须获取自旋锁。在 Linux 2.6 中，涉及 LRU 列表的操作通过 pagevec 结构进行。pagevec 结构要么将页面添加到 LRU 列表中，要么从 LRU 列表中移除页面，每次最多处理 PAGEVEC\_SIZE 个页面。在移除页面的情况下，获取 zone lru\_lock 锁，并将页面放置在临时列表中。在组装要移除的页面列表后，发起对 `shrink_list()` 的调用。现在，实际的释放页面过程可以在不获取 zone lru\_lock 自旋锁的情况下进行。在添加页面的情况下，通过 `pagevec_init()` 初始化新的页面向量结构。页面通过 `pagevec_add()` 添加到向量中，然后通过 `pagevec_release()` 提交以放置到 LRU 列表中。

## Slab 分配器

Linux，像大多数其他 UNIX 操作系统一样，提供了一个通用内存分配器，提供任意大小的内存分配。任何 slab 分配器的基本目标是高效地分配通常小于一页或不是一页大小的整数倍的小内存缓冲区。slab 分配器的另一个目标是有效操作经常分配和释放的内存对象，该过程可能导致内存碎片。slab 分配器允许缓存这些经常使用的对象（如 sock、inode 或 mm\_struct），从而最小化每次请求新对象时初始化和销毁这些基本实体的开销。Linux 2.6 中 slab 分配器的许多更改与地址锁竞争场景相关。此外，Linux 2.6 引入了 slab shrinker 回调特性。在 Linux 2.4 中，`kmem_cache_reap()` 在低内存情况下被调用。在 Linux 2.6 中，2.4 的设置已得到增强，缓存通过 `set_shrinker()` 注册 shrinker 回调。`set_shrinker()` 函数用一个指向回调的指针和一个指示重新创建对象复杂度的权重填充一个结构体。在页面回收场景中，每个 shrinker 被调用两次。第一次调用将 0 作为参数传递，表示回调应识别可以释放多少页面（如果正确调用的话）。接下来应用基本启发式方法来确定使用回调是否值得其成本。如果是，则以指示要释放对象数量的参数再次调用回调。
