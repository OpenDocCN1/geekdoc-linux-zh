
If it is different, it is most likely that the more holistic view is the one that will perform the worst. As with software design, integration building, automobile manufacture, and so on, there is distinct value in doing performance analysis on the various components before the greater whole. But they are not a replacement for doing full integration testing and performance analysis on the integrated system. As with automobile design, it is possible to design an engine that performs so well that it could push a car from 0 to 200 mph. But if the automobile’s components are not designed and tested to meet those same performance specifications, the end user of that automobile does not care how the vehicle performs and handles under that user’s workload.

## Network Benchmarks

This section discusses the following network benchmarks:

- Netperf
- SPEC SFS

### Netperf

Netperf is a fairly comprehensive set of network subsystem tests, including support for TCP, UDP, and DLPI (Data Link Provider Interface). Netperf is actually two executable programs: a client-side program, Netperf, and an accompanying server-side program, Netserver. Netperf can be automatically executed out of a system’s inet daemon; all command specification is done via the Netperf command-line interface. Netserver is opened over a standard TCP-based socket, using that communication channel to establish the subsequent tests. A secondary connection is opened between the client and server, depending on the test options selected, and performance statistics are returned to the client over this secondary connection. During a test, there should be no traffic (other than potential keep-alive packets) on the primary control channel. The analyst shuts off all other network traffic to the machine, so Netperf can measure the full capability of the network performance of a corresponding network fabric.

Netperf is primarily useful for measuring TCP throughput, which accounts for the majority of network traffic generated by modern applications. There are a couple of scripts that help automatically generate some basic tests covering socket size and send buffer size: `tcp_stress.script` and `tcp_stress2.script`. The first script runs Netperf with some specific socket sizes (56K, 32K, 8K) and send sizes (4K, 8K, 32K). The second script uses a socket size of 64K and send sizes from 1K up to 64K.

### SPEC SFS

SPEC ([http://www.spec.org/](http://www.spec.org/)) provides a benchmark for network file systems. It is primarily used today for benchmarking NFS v2 and v3, benchmarking both the UDP and TCP transports. SPEC SFS also provides a breakdown of all the common network file operations: creating directories, reading files, writing files, checking access rights, removing files, updating access rights, and so on. At the completion of the test, the throughput for each operation is generated. The test attempts to simulate a real-world workload with an appropriate mix of operations, so the results should be relevant to any reasonable NFS workload. A performance analyst may want to monitor the operations of her system against the published breakdown of operations as run by the SPEC SFS benchmark before drawing too many conclusions.

As with other SPEC-based tests, there are strict run rules, configuration requirements, data integrity requirements, and reporting requirements. It is still possible to use the test for internal testing and to use it to compare the results of various configuration changes to an environment.

### Java Benchmarks

Three commonly used benchmarks for comparing implementations of Java, Java settings, or Java on particular platforms are Volanornark (http://www.volano.com/benchmarks.html), SPECjbb, and SPECjvm. Volanornark is a benchmark designed to simulate the Volano chat room application written entirely in Java and has certain application characteristics that are similar to many Java applications. It simulates long-running network connections with lots of threads instantiated on the local operating system. Because that benchmark is sensitive to latency and response times are very important, and the Volanornark benchmark's goal is to see how many connections to the chat room can be maintained at a specified response time. Obviously, the more connections you can maintain with a reasonable latency, the less overhead the application implementation consumes. Volanornark can be implemented with both the server application and all clients running on the local firewall, separating the network component from the overall equation and focusing exclusively on the Java implementation and the underlying performance characteristics. However, a more realistic workload involves setting up clients on a network, driving a server. This helps isolate the application performance as well as overall Java performance. It also simulates a more reasonable customer deployment of Java in which Java is used as a client/server configuration.

Java, SPECjvm, and SPECjbb also add a new level of complexity over the benchmarks discussed thus far. Most of the preceding benchmarks can be significantly affected by system tuning. They are more likely to be affected by hardware configuration changes, total available system memory, and so on. For these benchmarks, the same operating system configuration options, hardware configuration options, and so on are often the primary factors. Java itself has configuration parameters governing the size of the heap it uses, the type of threads, and so on. Each of these configuration parameters interacts with the test and the underlying operating system in a somewhat unpredictable manner. As a result, benchmark publication efforts often run waves of tests, changing various configuration parameters at each level, so as to characterize the potential interactions of the configuration parameters. This technique is fairly common for finding the best results for a particular part of the system. However, a benchmark like this can also be used to model the impacts of various configuration changes. The benchmark in this case acts as a control against which to compare various changes.

Using the benchmark as a control allows the performance analyst to try out different versions of Java, different operating systems, and different configuration parameters for Java, and so on. This gives the performance analyst more insights into optimizing similar workloads.
