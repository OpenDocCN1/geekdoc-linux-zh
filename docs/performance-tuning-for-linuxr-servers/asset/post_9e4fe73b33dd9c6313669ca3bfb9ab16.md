
Iometer provides a slightly different view of performance tuning. Its goal is not to run a task and see how quickly it completes or completes in a period of time. Instead, it provides a steady-state workload and allows you to monitor various aspects of the system under load and see how the underlying system responds. In addition, you can vary the system parameters, configuration, and software installed and see how those changes affect the system. In other words, it provides many more tuning control points for analyzing changes in workloads than any of the other benchmarking tools. Iometer was publicly available as pgmeter, also known as Penguinometer. pgmeter is available at http://sourceforge.net/projects/pgmeter.

## tiobench

tiobench is a file system benchmark that is threaded and can generate tests using one or more simultaneous threads of I/O. This allows applications that generate I/O in parallel, either independently of each other (truly random) or with some coordination (for example, a database with multiple backends).

```
$ ./tiobench.pl

No size specified, using 1022 MiB
```

## dbench

dbench is a workload created to model another benchmark: NetBench. NetBench is the *de facto* industry standard benchmark for database performance. However, as with several benchmarks discussed later in this chapter, NetBench requires access to a large number of clients and a performance tuning team. With many benchmarks, the complexity of the benchmark makes it better suited to benchmark teams sponsored by vendors, usually after a product is generally available. NetBench is also poorly suited to help developers analyze code during the development cycle due to the time for testing and the complex testing environment required.

Many Linux developers prefer to analyze the performance of various aspects of their code as that code is developed. That analysis requires benchmarks that are easy to run, benchmarks that can be easily understood, and benchmarks that require minimal hardware configurations. dbench was written to support the Windows file system support for Linux and achieves those goals. Their goal was to use dbench to analyze their code for complex performance, and scalability on Linux.

dbench was developed based on a set of network traces captured while running NetBench. The theory was that if you can simulate the network traffic from accessing a network file system, you can generate effectively the same load with a program that does nothing except generate file system accesses. NetBench used a more brute-force approach where each network client was an individual computer, generating file system accesses. dbench simulates the file system accesses locally. By effectively simulating the file system traffic on the local machine, the server portion of the network is stressed in much the same way.

dbench effectively eliminates the need for a network in this case, simply simulating locally the traffic that would otherwise come through the network. This simplifies the overall analysis to a point that allows the developers to focus on a single component of the entire system-wide performance in a way that corresponds to a relatively standardized client load. In fact, with this level of simulation, it is now possible to simulate workloads even larger than the NetBench configuration, and with only a single machine.

As with any benchmark, it is important to understand exactly what the workload measured means for the performance analyst to understand how that measurement might relate to his own workload. As an example, NetBench workload that is very write intensive involves as much as 90% writes. Most real-user situations rarely have a need to write so much data as a percentage of data for a long period of time. However, writes tend to be more resource-intensive and harder to optimize than reads, making it useful for some worst-case analysis of a workload or an environment, but it is unlikely to be directly representative of typical user workloads.

dbench was originally written to model another benchmark. However, dbench is weak in a couple of properties that would make it a useful benchmark in isolation. In particular, dbench seems to have a very wide variation in the throughput results between runs, even when run repeatedly on identical conditions. This deviation in the average run results means that the test often needs to be run many times before a standard deviation for those results needs to be calculated. This means that running dbench from a development and stress perspective, as a multiplatform or multiconfiguration test, requires additional runs and more stringent analysis of the results. Also, absolute values are nearly meaningless because of these deviations. However, dbench remains a useful tool for generating stress, seeing how the system responds to the stress, and for providing some reasonable guidelines on the benefits of configuration changes, such as comparing different file system performance, strengths, and weaknesses, as well as an ability to compare the benchmark’s operation to that of the end-user workload under critical loads.

By using these two tests independently, it is possible to simulate the conditions under which the tested component is assumed to have no bottlenecks in individual subsystems without being dependent on bottlenecks or performance constraints in other subsystems. The various complex benchmarks discussed later in this chapter provide a single or small set of numbers to represent the overall throughput of these complex workloads, a combination of processing speed, network capacity, disk latency, file system performance, database server response times, and other factors that come together to yield a single throughput and/or latency result. But if a single component of the environment being tested fails, the overall number suffers, often without any direct feedback as to the cause of the issue. The analyst needs to look at the detailed statistics provided by the benchmark, understand what portions are most critical to the workload, and tune or otherwise correct that subsystem and rerun. This process can take days for an expert, and for the uninitiated, this process can take months.

It may appear that tests like dbench, tbench, and other component tests are "the only way to go." The initial answer is: Definitely! The analysis of the various components does not provide a comprehensive view of how those components interact. For instance, dbench only tests the underlying file system; knowing that component is working well, and tbench can help tune the networking component to work well. But if there are interactions between the underlying file system code, such as locking, scheduling, or latency issues, the overall result of a comparable system will not be accurately represented by these individual tests alone.
