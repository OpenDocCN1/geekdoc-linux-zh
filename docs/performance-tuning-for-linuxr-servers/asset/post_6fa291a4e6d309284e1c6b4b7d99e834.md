## libc bcopy unaligned

This section measures the rate at which the C library's bcopy(1) function can copy unaligned data. Unaligned data often requires more time to copy than aligned data. For instance, aligned data may be copied a double word at a time (64 bits at a time), but unaligned data may require one byte at a time. In particular, the bcopy(1) routine needs to ensure that it never attempts to read a byte that is not present in the page. This often makes an unoptimized bcopy(1) routine extremely slow. As the size of the data to be copied (in the first column) increases, the throughput of a good bcopy(1) implementation should directly approach that of the aligned bcopy(1) measurements that follow. A simplified implementation copying one byte at a time and be substantially slower for copying large blocks of data. An incorrectly optimized implementation may cause a segmentation fault via a reference to data that is not mapped into the application's address space.

## AIM7 and AIM9

AIM Technologies released two commonly used benchmarks in the mid-1980s. Caldera/SCO acquired AIM Technologies and released benchmarks under the GPL license in 1999. (See http://www.caldera.com/developers/community/contrib/aim.html for details.) Get it from ftp://ftp.sco.com/pub/opensource/ or http://sourceforge.net/projects/aimbench. Although both AIM7 and AIM9 are old, they are interesting primarily because they are freely available under the GPL in source form and provide a useful performance perspective for Linux systems and the workloads running on those systems.

### AIM7

(http://cvs.sourceforge.net/viewcvs.py/tp/benchmarks/)

The AIM7 benchmark is often referred to as the AIM Multiple User Benchmark because it focuses on systems that support multiple concurrent users running an intensive workload. It is somewhat dated compared to the tasks that multiple users run on a single system today; the test still stresses some underlying operating system capabilities in a fairly generic way. For instance, the AIM7 test focuses on running a large number of tasks simultaneously. This exercises the operating system's scheduler, as well as the process creation and process exit capabilities. The test attempts to use a reasonable approximation to the number of users in this synthetic workload; however, the amount of storage actually used by the benchmark is fairly low for the workload. The test minimizes the use of floating-point and complex mathematical operations, making it less useful as a benchmark for the computing needs of the scientific and technical communities. Other benchmarks focus on more commonly used matrix multiplication and other computation-intensive workloads. AIM7 spends a fairly high percentage of time sorting and searching through relatively large queues, but the amount of data is probably low by today's standards. Also, today's workload mix tends to offload operations like that to databases rather than brute-force search and sort algorithms. AIM7 also attempts to focus more on the system libraries and system calls than some other benchmarks do. As part of a comprehensive set of benchmarking, AIM7 provides useful input into the comparative performance of various UNIX systems that supply similar capabilities on different implementations of the operating system and on different hardware.

### AIM9

(http://cvs.sourceforge.net/viewcvs.py/ltp/benchmarks/)

AIM9 is referred to as the AIM Independent Resource Benchmark. It has a more component-oriented focus on benchmarking than AIM7, providing a view that is similar to that of lmbench in that it measures discrete capabilities such as additions per second or sorts per second, rather than AIM7, which provides a measure of more user-visible operations. AIM9 attempts to avoid measures that are impacted by the operating system subsystem or scheduler; instead it focuses on the processor-bound capabilities. AIM9 measures a slightly different set of underlying subsystems than lmbench. In particular, AIM9 has a larger focus on integer and floating-point calculations, while also providing another view of disk performance, and networking tests such as TCP, UDP, files, and pipes. The tests typically run for a short, fixed period of time and measure the number of operations completed during that time. The specific tests, the amount of time for each test to run, and a number of environmental factors, such as which compiler to use, can be easily reconfigured.

The performance of a system is more than the sum of its parts. The complex interactions of system calls, locking, network latency, application dependencies, and many other factors combine in ways that are often difficult to predict. Component viewpoints such as AIM7 and AIM9 may be important in understanding raw processor power, general operating system comparisons, and performance improvements for specific operations, but it is rarely possible to extrapolate the performance of a complex workload from such a narrowly focused benchmark. Understanding component limitations in terms of performance and throughput helps provide useful background when trying to analyze performance in real-world workload scenarios.
