dbench was originally written to model another benchmark. However, dbench is weak in a couple of properties that would make it a useful benchmark in particular, dbench seems to have a very wide variation in the throughput results between runs, even when run repeatedly on identical conditions. This deviation in the average run results means that the test often needs to be run many times before a deviation for those results needs to be calculated. This means that running dbench from a development and stress perspective can be used as a multiplatform or multiconfiguration test requires additional runs and more stringent analysis of the results. Also, absolute values are nearly meaningless because of these deviations. However, dbench remains a useful tool for generating stress, seeing how the stress, and for providing some reasonable guidelines on the benefits of configuration changes, such as comparing different file system performance, strengths, and weaknesses, as well as an ability to compare the benchmark’s operation to that of the end-user workload under critical.

By using these two tests independently, it is possible to simulate the conditions under which the tested component is assumed to have no bottlenecks in individual subsystems without being dependent on bottlenecks or performance constraints in other subsystems. The various complex benchmarks discussed later in this chapter provide a single or small set of numbers to represent the overall throughput of these complex workloads, a combination of processing speed, network capacity, disk latency, file system performance, database server response times, and other factors come to yield a single throughput and/or latency result. But if a single component of the environment being tested, the overall number suffers, often without any direct feedback as to the cause of the issue. The analyst needs to look at the detailed statistics provided by the benchmark, understand what portions are most critical to the workload and tune or otherwise correct that subsystem and rerun. This process can take days for an expert, and for the uninitiated, this process can take months, and so on can take months!

It may appear that tests like dbench, tbench, and other component tests are "the only way to go." The initial answer is: Definitely! The analysis of the various components does not provide a comprehensive view of how those components interact. For instance, dbench only tests the underlying file system component is working well, and tbench can help tune the networking component to work well. But if there are interactions between the underlying file system code, such as locking, scheduling, or latency issues, the overall result of a comparable system will not be accurately represented by these individual tests alone.
