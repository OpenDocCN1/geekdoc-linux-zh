
# How can that be?

For a moment, pretend that your hard disk is rectangular—tall and not so wide. Now picture your file and directory structure laid out one line after another, like so:

```text
/
/bin
/boot
/dev
/etc
/home
/initrd
/lib
/misc
/mnt
/opt
/proc
/root
/sbin
/tmp
/usr
/var
```

And all of this is on one hard disk. Now let’s suppose you had two hard disks. Linux puts some of the directories, in their entirety, on the second hard disk, like so:

```text
Disk 1:
/
/bin
/boot
/dev
/etc
/home
/initrd
/lib
/misc
/mnt
/opt

and

Disk 2:
/proc
/root
/sbin
/tmp
/usr
/var
```

To you, the user, does it really matter if `/tmp` is physically on Disk 1 or Disk 2? Of course not. You can still access it all through the folder structure. The arbitrary use of separate drive letters for different disks is due to a lack of planning back in the early days of DOS, and Windows users have been paying for that decision ever since.

In practical terms, which directories are on which disks is actually different. You’ll typically find `/home` (and maybe `/tmp` and `/var`) on a second disk if there’s one available. But the idea is the same. When you’re drilling down into `/home`, you don’t know (or care) whether you’re working with hard disk #1, #2, or if there’s a tiny little man with grey hair and a beard inside, furiously scribbling down data in a very small book. Linux handles the specifics of getting data from the hardware to you transparently.

If you want to learn more, there’s a long and involved description about how this works in Appendix A, “Partitions.”

## File managers

Now that you know something about your data and how the disk is structured, how do you go about working with it?

There have long been two schools of thought about using computer programs to work with data. One school of thought relies on the “noun-action” or “application-centric” paradigm, where you open up a program and then use that program to navigate to a piece of data, such as a memo or a spreadsheet. The other school of thought relies on the reverse— an “action-noun” or “document-centric” paradigm— where you navigate to your data, and then rely on the computer system to know which program to use to work with it.

Different kinds of data lend themselves to one approach versus another, so it’s actually common to use both methods at the same time. For instance, it’s common for an e-mail program to keep its data in a specific place. Thus, you would open your e-mail client and expect it to know where the data is. You wouldn’t navigate to a specific e-mail message and then launch your client from that message, because you’re probably going to want to work with more than one message.

The same goes for music jukebox programs. In order to listen to a bunch of music, you’d typically start your music player, and then create a new playlist or point to an existing playlist of music. You ordinarily wouldn’t navigate to a specific song and load it, since you’re probably going to want to work with (that is, listen to) more than one song.

On the other hand, when you’re working with, say, spreadsheets, it’s pretty common to navigate through your folders, find the spreadsheet you’re interested in, and then launch the computer program associated with that type of file.

In the early days of computers, the ability to associate a program with a type of file didn’t exist, but as character-based and graphical file managers became popular (after the introduction of hard disks, when people had more data on their hard disks than in their boxes and boxes of floppies), this technique became more and more common, until it’s now a standard technique on both Windows and Linux operating systems.

In the late 1980s, I began using a software tool that provided a graphical view of files and directories (and thus provided the ability to launch applications from within it), and have never looked back. I started with a couple of character-based programs that displayed directory structures in hierarchal diagrams, like so:

```text
c:\
 +-~Directory1
 | +~fileA
 | +-~fileB
 |
 +-~Directory2
 +-~Directory3
 +-~file1
 +-~file2
```

Once Windows hit, I started using Windows Explorer to navigate through the files on my system, and then started using PowerDesk as Explorer’s replacement once it was released. So I have a long-time bias toward using graphical file managers.

As with any software category, a number of graphical file managers are included with mainstream distributions of Linux. Fedora Core includes three popular file managers. Nautilus is the default graphical file manager for GNOME, Konqueror is the default graphical file manager for KDE, and Midnight Commander is a popular character-based file manager called from the command line.

I’ll discuss Nautilus and Midnight Commander briefly, and then spend more time with Konqueror, because it’s quickly become my personal favorite.

### Midnight Commander

Midnight Commander, or “MC” as it’s called by many folks, is a character-based file manager that mimics many of the functions that full-featured graphical file managers have. If you’re an old-time DOS user, you may notice a distinct similarity to the DOS Norton Commander, and for good reason.

To run MC, open a terminal window and type `mc`. MC will appear in a window as shown in Figure 6.

![](img/50a238d93c7edbdc4387d5ff7f6b7b3c_168_0.png)

**Figure 6. Midnight Commander is a popular character-based file manager.**

MC is terrifyingly robust, and packed with functionality. Because it’s not a GUI, it doesn’t require a lot of system resources. One could write a small book just on MC, but that’s beyond the scope of this discussion. Instead, I’ll just give you a quick tour.

Despite it being a character-based tool, MC is accessible via keyboard and mouse, as well as a combination of both, so it will work with you regardless of your own personal style.

The screen is divided into four areas, with the two directory panels taking up most of the real estate. The other two areas are the top line, which contains the menu bar, and the bottom couple of lines, which contain a shell command line and the function key labels.

The current directory is displayed in the left panel; you can scroll through it as well as navigate through higher and lower directories by clicking parent directories (denoted by `../`) and subdirectories (denoted by `/some_subdir`). The right panel is generally used as a target during commands that use one, such as copy and move (don’t worry, MC warns you if you use one beforehand).

You can configure how the panels display information, both in terms of sort orders as well as the types of information.

As you would expect, you can perform any type of file operation you can think of, including copying, moving, renaming, deleting, finding, zipping and unzipping, comparing, editing, executing, changing ownership or permissions—and you can do so in several different ways. The File menu provides access to all of these functions, as shown in **Figure 7**, while the function keys perform the more common commands.

![](img/50a238d93c7edbdc4387d5ff7f6b7b3c_169_0.png)

**Figure 7.** You can access many of Midnight Commander’s functions through the menu and keyboard shortcuts.

You can also access a "quick menu" by pressing the F2 (user menu) key, and you can customize this menu by editing one of the MC configuration files.

### Nautilus

It’s almost impossible not to get slightly acquainted with Nautilus (shown in Figure 1 earlier in this chapter), because it’s the default file manager used by GNOME, which in turn is the default desktop environment for Fedora Core.

Because many of the menu items and commands use Nautilus as their default engine (for example, opening the Home Folder from the Main Menu), it’s a good idea to learn a little bit about it.

Nautilus opens in a two-pane display, with the left pane showing treeview nodes for the current user’s home directory, the machine’s entire file system, and any removable storage devices. **Figure 8** shows the first two standard nodes, plus one for a CD-ROM.

![](img/50a238d93c7edbdc4387d5ff7f6b7b3c_170_0.png)

By default, you can navigate through the treeview on the left side, expanding and contracting nodes in order to show the contents of folders, and navigating through folders and files.

The first thing you’ll want to do is investigate the preferences for Nautilus so you can set it up to your own style. Click **Edit | Preferences** in the Nautilus menu to bring forward the File Management Preferences screen, as shown in **Figure 9**.

My preference is to smash lots and lots of data into the smallest space possible. On the Views tab, I set “View new folders using” to List View, I select the “Sort folders before files” check box, and I uncheck the “Show hidden and backup files” check box. I also make sure that the “Show only folders” check box is selected in the Tree View Defaults section at the bottom of the tab.

On the Behavior tab, I select the “Include a Delete command that bypasses Trash” check box because it’s nice to be able to delete a file completely with one keystroke or mouse click without being prompted.
