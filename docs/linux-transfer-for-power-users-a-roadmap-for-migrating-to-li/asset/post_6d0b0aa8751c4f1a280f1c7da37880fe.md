File extensions for some types of files are different: A compressed archive in Windows has a ZIP extension; in Linux, there are several, including bzip, gzip, tar, and gz, and sometimes a file can use multiple extensions on one file. That’s another thing: In Windows, the period is a separator between the file name and the extension; with Linux files, it’s not uncommon to run across a file with multiple periods in it, for any number of reasons.

The second big difference is that case matters. Sometimes, MYFILES.abc.xyz is different from myfiles.ABC.XYZ, much to the consternation of many new Linux users.

And the biggest difference is that on Linux, a file also can represent other entities, such as folders, disk drives, printers, processes, memory, the CPU, and everything else. Now wait, you say. How can that be?

The short answer is that a “file” actually consists of two parts: an entry in a table that points to the actual entity, and the actual entity itself—the chunk of data. The table of pointers is stored in one place on the computer’s disk, and the actual entity—the data itself—is elsewhere on the disk. So what we think of as a “file” is actually the “pointer.” What difference does it make if a pointer points to a bunch of 1’s and 0’s in a particular place on a disk or if it points to another type of object, like a hard disk?

## Symbolic links

Before I bring this section to a close, I need to mention one more special type of file in Linux called a “symbolic link,” or “symlink” for short. You’ll run across them all over the place, and while you can get by without knowing much about them, it’s best that you don’t take that shortcut. You’re a power user after all, right?

A symlink is essentially the Linux version of a Windows shortcut. That’s all. Nothing terribly magical or obscure.

Why use symlinks? Why not use the original file? One example is a symlink on a desktop that points to another file. Instead of making a second copy of the file and putting it on your desktop (which you certainly wouldn’t want to do, because then you’ve got two copies of a file), a symlink on the desktop allows you to work with the original file, whether that’s opening a document or executing a program.

Another example would be when you need a program accessible in one place (say, a certain directory), but there’s not enough room in that directory (because the directory is on a partition or disk that’s running out of room). So you can create a symlink in the directory where the program has to be accessible, and point the symlink to the program in another location.

Installation programs frequently use symlinks during the process of installing software as well as during upgrades—the symlinks are kept out of your way while the program is working, but *they* are *there*.

For example, when you install a new version of the Python programming environment, the old version is left where it was. The new one is not installed on top of the old one. Then, the “python” command is a symbolic link to the last Python interpreter you installed; if you need to run a specific version of Python, say version 2.2 after you’ve installed 2.3, you can do so by typing “python2.2” instead of just “python.”

See Chapter 14, “Under the Hood,” for information about how to create and work with symlinks.

### Where's the C: drive?

Having grown up with Windows, we've gotten used to a disjointed collection of objects representing our personal computer system, and think that it's the “right way.” Back in the old days before hard drives (or color monitors!), a personal computer usually had two floppy disk drives, and the operating system (MS-DOS or PC-DOS) referred to these drives as Drive A: and Drive B: When a hard drive was added to a personal computer, it naturally received the moniker of “Drive C:” When other storage devices, such as additional hard disks or removable media (such as tape backups, Bernoulli Boxes, Zip drives, and CD-ROMS) were added, they were also referred to with letters from the alphabet. A packed PC could easily have seven or eight drives, like so:

- Drive A:—floppy disk
- Drive B:—second floppy disk
- Drive C:—hard disk
- Drive D:—CD-ROM drive
- Drive E:—second hard disk
- Drive F:—Zip drive
- Drive G:—tape drive

In addition, if you're attached to a network, you will probably have randomly assigned network drives.

Computer components are all commonly organized in a tree structure, shown in **Figure 2**.

![](img/50a238d93c7edbdc4387d5ff7f6b7b3c_159_0.png)

The additional hard disk starts the schism of the interface to the computer. Some programs and data are stored on Drive C: while other data (and possibly some programs) are stored on Drive D:. However, it’s not clear what goes where; thus, a hardware issue that should be hidden from the user now becomes a usability issue for the user.

The tree structure now has two nodes (Drive C: and Drive D:) for data that is stored inside the computer. That distinction is actually an arbitrary choice, which is unnecessary, because it exposes the hardware setup to the user, they generally didn’t care. Imagine if you had separate names for each bank of physical RAM chips or SIMMs, and had to tell the computer which bank to load a program into?

Furthermore, in order to make things “easier” for the user, Microsoft started adding artificial interfaces to the tree structure. The Desktop node is simply a different view of some information in directories on Drive C:. The Control Panel, presumably an object of the same type as the drives displayed above it, is actually a launcher for a variety of programs. The My Digital Camera and MacroMedia FTP and RDS nodes also seem to be objects like the drives, but whether they are or not is suspect. Indeed, I don’t even have a digital camera attached to this computer—why is there a node for a nonexistent device?

So, as you can see, the interface that Windows uses for access to the components of a PC kind of falls short.

With Linux, everything on a computer is represented by a file: files, directories (or folders), and even devices such as disks, cameras, printers, and so on. It can take a bit of getting used to—you might think, how can a floppy disk be a file? The intellectual leap you need to take is that files can contain files. Thus, directories can contain files, and you can copy a file to a floppy disk, because the file represented by the floppy disk can contain files too. At best, though, it’s probably not worth it to worry about this distinction, any more to worrying about how the electricity passing through the chips in your computer knows where to go. Linux handles the details.

As a result, the tree structure for a Linux computer is considerably cleaner than a corresponding Windows computer. The top-level node, denoted by a single slash (/), is called “root,” and the rest of the tree flows out from the root. That’s why you don’t see separate nodes for Drive C:, Drive D:, and so on. The physical devices on a computer are all represented by files in the tree structure—there are no artificial or uneven interfaces. For example, a machine with two floppy disk drives would have two subdirectories under the /mnt directory: “/mnt/floppy1” and “/mnt/floppy2”. More on this shortly.
