### 02 Download access keys

On the following page, you will be able to view and download access keys for all of your new IAM users. Make sure you retain a copy of the keys in a safe place because this is the last time that you are offered to view this information. You can always create new keys later, but you cannot retrieve existing ones (nor can your users).
Make sure that you forward access keys to their respective owners in as safe a manner as possible – in person is probably best; do not rely on email.

### 03 Manage passwords

IAM supports two authentication methods: key pairs and a combination of a username and a password (a third method, signing certificates, is deprecated and should no longer be used). You can issue and invalidate both types of credentials as needed. In addition, AWS uses SSH keys to authenticate IAM users for access to AWS CodeCommit repositories.
When authorizing access with tools, such as a mobile app that uses Amazon’s RESTful APIs, your user will identify themselves with a key pair. A key pair consists of an access key and a secret key. Key pairs do not work for logging in to the AWS Management Console in a web browser. For this, each of your IAM users need a password, in addition to their username, and a sign-in URL that is specific to your AWS root account and shared among all users for simplicity.
In order to manage authentication methods for your IAM user, navigate to the Users section of the IAM console and click on the username in the list. Scroll down to the section Security Credentials/Sign-In Credentials and create a new password (Manage Password). On the following page, you can require the user to change the password at their next sign-in as an additional security precaution.
Click on Apply. Download the credentials and remember to hand them over to the user in as secure a manner as possible.

### 04 Manage key pairs

Should the need arise to manage key pairs, navigate to the Users section of the AWS Management Console for IAM, click on the username in the list and scroll down to the section Security Credentials/Access Keys. It is here that you can create new access keys and invalidate existing ones.
Before you delete existing access key pairs, you may want to make them inactive to see if removing them breaks any existing workflows. There is no way you can reinstate access keys once they have been deleted.

> **Old AWS accounts**
> *Order AWS accounts may still include root access keys. Amazon used to give these out, but for later users created they are treated like shared. These keys present a security risk. Make sure no user is using AWS accounts that are still using the old root access keys.*

### 05 Grant permissions to the IAM user

**Identity Federation**

See how users can be redirected to federated sign-in. For more details, see **Identity federation**. AWS account administrators can create IAM users and assign permissions to resources. For more details, see **Users and Groups**. AWS also supports external identity, SAML, and OpenID Connect.

**05 Grant permissions to the IAM user**
On AWS, you can grant or restrict users' access to your infrastructure and services by means of documents that are referred to as policies. An alternative method, access control lists (or ACLs for short), is deprecated and should no longer be used. In addition to policies, you can also use roles to manage the access privileges of individual services as well as access from other AWS accounts.

These policies can either be entity-based or resource-based. The former are attached to a user, or a group, in order to grant them specific privileges for clearly defined activities on all or some resources. The latter are attached to a resource to manage access.

In order to grant privileges to your IAM user, navigate back to the Users section of the IAM Console, click on the username, scroll down to the page to the Permissions section and then click on Attach Policy.

On the following page, the AWS Management Console will most likely present you with a mind-bending collection of possible policies: either AWS-Managed or Customer-Managed, or even both depending on how you set the filter. To simplify your search, you can also filter the list by using the search box. In order to assign any combination of policies to the user, you need to activate the appropriate policy entries in the list and click on Attach Policy. You will be able to view details of the policy as well as detach it, or even simulate it, on the next page.

When selecting which policies to attach to your users, you should be extremely cautious.

### 06 Obtain a sign-in link for IAM users

Navigate to the dashboard of the console. Directly underneath the welcome message, the console offers you the ability to create a customisable sign-in link for all IAM users. This link differs from the main sign-in URL that is available to the AWS root user. IAM users cannot sign in without knowing this link (in addition to their credentials).

Edit the link (your account's alias) to your heart's content, then copy it to your clipboard and save it. Alternatively, bookmark it. You will have to make this link known to each IAM user who is authorised to access your services.

When a user visits this link in a web browser, they will be prompted to sign in with their username and password.

Permissions for accessing the AWS Management Console are separate from user privileges and are never granted automatically. This can be frustrating at times, as your IAM users report an inability to interact with the console, then they are lacking console privileges and you will have to grant these to all users with a genuine need for them.

### 07 Sign out from your AWS root account (for good!)

If you are still authenticated as the AWS root of your account, now is the time to sign out. From this point on, you should never use AWS root account credentials, ever again. Any tasks that the root user can perform can also be performed by an IAM user, provided they are given sufficient privileges that are carefully tailored to the context of the current task. This is in order to minimise your exposure to sniffing and other types of attacks.

### 08 Sign in as an IAM user

In order to sign in with your user IAM credentials, you first need to navigate to the URL that you created in Step 6, and then enter your username from step 1 and your password from Step 3.

Once your ability to sign in has been confirmed, it is time to secure access to your (and every other users') account using multi-factor authentication.

### 09 Set up MFA authentication

Login credentials that consist of a username and a password can no longer be considered secure, not without MFA (multi-factor authentication). Brute-force attacks are rampant and frequently successful because encryption standards remain inadequate (or more accurately put: woefully outdated for the massive computational capabilities of the cloud). In order to combat the inadequacy of conventional login procedures, Amazon introduced multi-factor authentication (MFA) with the help of a token generator.

A token generator is a device – a mobile app or another piece of software – that is designed to provide an additional layer of security with the help of a one-time-use string of characters, the so-called token. A token can confirm the authorisation of its user to access AWS resources, but it requires prior registration with Amazon.

In order to register an MFA device, head over to the users section of the IAM service in the AWS Management Console, scroll down to the section Security Credentials > Sign-in Credentials and click on Manage MFA Device.

> "Login credentials that consist of a username and a password can no longer be considered secure"

### 10 Troubleshooting MFA

Should you be unable to sign in even though your MFA device appears to be working, the token generator may be out of sync with the AWS token verification system. All you need to do to restore access is synchronise them.

Should your MFA device stop working entirely for any reason (such as, most notably, wear and tear), you would not be able to sign in to the AWS Management Console of whatever account it was associated with. The device must be deactivated immediately and replaced as soon as possible. Obviously, you will also need to change your password just to be on the safe side – how to go about doing this is a whole different question. It depends whether the MFA was associated with the root account or with an IAM user.

If you’re experiencing problems related to an MFA device associated with an AWS root account, ask Amazon for help by submitting the form on this webpage: https://aws.amazon.com/forms/aws-mfa-support. You will need to provide a phone number and details regarding the issue.

IAM users should seek help from their AWS administrators (that’s probably you). Especially for mobile AWS administrators, an MFA token generator is highly advisable.
