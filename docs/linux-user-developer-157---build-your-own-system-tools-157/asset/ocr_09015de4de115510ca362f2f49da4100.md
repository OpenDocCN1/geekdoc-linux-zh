time for an embedded system to at least log the power failure. In Linux, they are also used to run a feature known as a "watchdog" that will fire periodically in a fashion that cannot be interrupted. If the kernel has become stuck in some interrupt management code with interrupts disabled (wherein the regular, up to 1,000 times per second, interrupt-based timer tick is no longer causing kernel housekeeping tasks to run), then the NMI watchdog can be a last-ditch attempt to detect this hang and at least reboot the system before it becomes completely wedged and unresponsive.

Since NMIs cannot be disabled and could arrive at any moment regardless of how prepared the kernel is, the code used to handle them in Linux is at its best described as "hairy". It has been subject to security concerns in the past and was again recently. As we have previously reported, Andy Lutomirski discovered a security exploit but had kept the precise details under an embargo until such time that OS vendors had time to address the problem with updates. He has since published the text of CVE-2015-3290 that describes the problem in detail. At a high level, it can be summarised as a potential flaw in the Intel "RET" (return from interrupt) instruction when returning from an NMI handler back to a user-space application that makes use of a 16-bit stack. Normally, user applications aren't 16-bit and they don't use 16-bit stacks, but support for such applications has remained in the kernel to support Legacy MS DOS applications without special emulation.

Linux has special code known as espfix64 for the case of returning from an NMI back to a 16-bit user-space application. That code is supposed to be atomic in nature (it either all happens or none of it does), but because NMIs can also be nested - another NMI can happen while one is already being handled - it is possible to arrange that the espfix64 code is interrupted while it is running, leaving it half completed. According to Andy, in this case "there is a two-instruction window in which the return context ends up with user-controlled RIP and CS set to __KERNEL_CS". This means that if a nest NMI is arranged for just the wrong moment, the espfix64 handler is interrupted and the next time it runs, it returns to user-space with the user-space task (process) having kernel-level privileged system access. A cunning workaround has been merged into Linux that abuses the way Intel CPUs handle a special flags register. This is in order to ensure atomicity of the return to 16-bit stack case, but is another reason for the recent effort to remove cruddy old support code for 16-bit applications that very few (if any) users are still running. As we noted before (in covering "RIP Virtual Mode 86 Support"), user-space level emulators exist for these 16-bit applications at this point and are preferable to retaining actual support for 16-bit applications in the Linux kernel itself.

# # Linux 4.3

**With the release of Linux 4.2, came the opening of the "merge window" (a period of time during which disruptive changes are accepted), for what will become Linux kernel 4.3.** Amongst the internally/developer visible changes is a switch to make Virtual Mode 86 (VM86 - as discussed in relation to NMIs) a Legacy feature, scheduled to be removed from future kernels. The main user-visible early feature merged thus far is support for a new "PIDs" controller for the cgroup/v2 (control group) subsystem. This is intended to reduce the risk of "fork bombs" (spawning many processes/tasks until the system runs out of resources to allocate additional processes/tasks) by imposing firm limits upon how many subprocesses members of a given cgroup can create once established. There has also been a major reworking of the Nouveau DRM driver, correcting some previously made design decisions and hopefully paving the way for more exciting improvements in the future.

That's all for this month. Tune in next time to learn about the features that land in Linux 4.3-rc1 (Release Candidate 1).
