我们前面提到过在系统初始化（引导）时创建的默认分区。在初始化过程中，所有已安装的处理器都被放入这个默认分区。如果没有通过psrset(1M)或psrset_create(2)显式创建其他分区（处理器集），系统就只维护内部默认集，该默认集对用户不可见。psrset(1M)会将系统上的所有处理器显示为由一个默认分区管理。默认分区是一个处理器集。内核为分区定义了三个可能的级别（cp_level）：CP_DEFAULT、CP_SYSTEM、CP_PRIVATE。引导时创建的默认分区当然就是CP_DEFAULT，并且它将是全系统中唯一的默认分区（只允许存在一个这样的分区）。在系统上创建的其他分区被设置为CP_PRIVATE。CP_PRIVATE级别目前尚未使用，但未来很可能会实现，作为创建内核内部（仅限内核）分区的一种手段。

我们为每个分区展示了一个调度队列。总结我们之前关于调度队列的讨论：Solaris内核维护着多个调度队列，即等待处理器处理的可运行内核线程队列。每个CPU对于优先级低于实时优先级的可运行线程，都有一组自己的调度队列。对于实时线程，维护着一个称为*内核抢占队列*的全系统队列。放置在该队列上的线程具有足够高的优先级，从而强制内核抢占，因此得名。如果创建了处理器集，那么每个处理器集（分区）都管理自己的内核抢占队列。这个按分区划分的队列是cpupart结构体的一部分，该结构体集成了一个disp结构（调度器——cpupart的cp_kp_queue成员）。队列链接就是在这里通过disp_q指针维护的。

用于CPU控制的内核支持函数分为CPU分区管理函数和每CPU控制函数，其中若干函数在系统引导期间执行，以构建和初始化所需的内核数据结构、插入所有链接，并将所有处理器置于在线状态。一旦系统启动并运行，之后对CPU的任何状态更改都很可能是用户发起操作的结果，例如动态重新配置操作、线程绑定或处理器集管理。

## 进程间通信

进程间通信（IPC）包括操作系统提供的各种设施，用于在同一系统上的进程和线程之间实现数据共享（共享内存段）、信息和数据交换（消息队列）以及对共享资源访问的同步（信号量）。将IPC与基于网络的设施（如套接字和RPC接口）进行对比，后者能够在分布式系统之间通过网络链路进行通信。早期的IPC设施起源于AT&T Unix System V，该系统在1983年左右增加了对共享内存、信号量和消息队列的支持。这一最初的三种IPC设施通常被称为System V IPC。随着时间的推移，从POSIX标准中演化出了一组类似的IPC特性，现在我们有了POSIX信号量、共享内存和消息队列。System V和POSIX IPC使用不同的API，并且在内核中的实现方式也不同，尽管对于应用程序来说它们提供了相似的功能。

其他进程间通信设施包括内存映射文件（mmap(2)）、命名管道（也称为FIFO）、Unix域套接字，以及最近新增的Solaris Doors，它为运行在同一系统上的线程提供类似RPC的设施。应用程序进行进程间通信的每种方法都提供了特定的特性和功能，这些特性和功能对于特定的应用程序可能有用，也可能没有用。应用程序开发人员需要自行确定需求是什么，以及哪种设施最能满足这些需求。

我们这里的目标不是提供有关使用这些接口进行编程的教程，尽管在描述某个特性或功能组件时有必要提及一些API。有多部著作讨论了编程和进程间通信，其中最著名的是W. Richard Stevens的*《UNIX网络编程——进程间通信》*，第2版，第II卷。

### 10.1 通用System V IPC支持

所有三种System V IPC设施共用一些数据结构和低级内核例程。在本节中，我们讨论这些公共部分，然后深入了解每种IPC实现的具体细节。公共接口和结构包括：

- **xxxid_ds 数据结构。**每种设施都有一个包含有关资源的各种信息的数据结构。该数据结构使用的命名约定在所有三组接口中都是相同的（参见表10-1）。
- **键和标识符。**要在进程之间共享IPC资源（这正是进程间通信的意义所在），进程在发出get调用时必须能够唯一地标识一个资源。IPC设施要求在xxxget(2)调用中提供一个键值，并根据传入的键值返回一个标识符。
- **ipcget()和ipcaccess()。**这些公共内核例程由IPC设施使用，用于获取标识符和检查访问权限。

#### 10.1.1 模块创建

System V IPC内核模块是作为可动态加载的模块实现的。每种设施在/kernel/sys目录中都有一个对应的可加载模块（shm_sys、sem_sys和msgsys）。此外，所有三种IPC方法都需要加载/kernel/misc/ipc模块，该模块提供了所有三种设施共享的两个低级例程。调用ipcaccess()例程来验证对特定IPC资源（例如共享内存段、信号量或消息队列）的访问权限。ipcget()代码根据在shmget(2)、msgget(2)和semget(2)系统调用中作为参数传入的键值，获取与产生该调用的特定IPC资源相关联的数据结构。

当首次创建IPC资源时，会分配一个称为*标识符*的正整数来标识该IPC对象。该标识符由键值派生而来。内核IPC xxxget(2)系统调用会对使用相同键值的进程或线程返回相同的标识符，这正是不同进程能够确保访问所需消息队列、信号量或共享内存段的方式。ftok(3C)文件到键接口是最常用的方法，让不同进程在调用某个IPC xxxget()例程之前获得正确的键。

与每个IPC资源相关联的是一个*id*数据结构，内核在首次以适当标志调用xxxget(2)系统调用时分配并初始化该结构。每种设施的xxxget(2)系统调用再次根据调用中传入的参数和权限，将标识符返回给调用应用程序。这些结构在名称上类似，并且定义在每种设施的头文件中（参见表10-1）。

**表10-1** *IPC ID结构名称*

| 设施类型 | xxxget(2) | ID结构名称 |
|---|---|---|
| 信号量 | semget(2) | semid_ds |
| 共享内存 | shmget(2) | shmid_ds |
| 消息队列 | msgget(2) | msgid_ds |

内核中可用的xxxid_ds结构数量是静态的，由每种设施的xxxmni内核可调参数决定，也就是说，msgmni、semmni和shmmni分别决定了可用的msgid_ds、semid_ds和shmid_ds结构的最大数量。这些结构的内核内存在IPC设施的初始化阶段根据结构大小和xxxmni值分配。

ID结构中的大多数字段对每种IPC类型都是唯一的，但它们都包含一个指向ipc_perm数据结构的指针作为第一个结构成员，该结构定义了对该资源的访问权限，就像对文件的访问由每个文件的inode中维护的权限定义一样。ipc_perm结构定义在/usr/include/sys/ipc.h中；它包含表10-2中列出的成员。

**表10-2** *ipc_perm数据结构*

| 成员名称 | 数据类型 | 描述 |
|---|---|---|
| uid | uid_t | 所有者的用户ID |
| gid | gid_t | 所有者的组ID |
| cuid | uid_t | 创建者的用户ID |
| cgid | gid_t | 创建者的组ID |
| mode | mode_t | 访问模式（权限位） |
| seq | ulong | 槽位使用序列号 |
| key | key_t | IPC键值 |

对于每个IPC资源，所有者和创建者的UID和GID是相同的。所有权随后可以通过控制系统调用进行更改，但创建者的ID永远不会改变。访问模式位与文件访问模式类似，区别在于IPC对象没有执行模式；因此，模式位定义了所有者、组和其他用户的读/写权限。seq字段被描述为槽位使用序列号，内核使用它在首次创建IPC资源时建立该资源的唯一标识符。
