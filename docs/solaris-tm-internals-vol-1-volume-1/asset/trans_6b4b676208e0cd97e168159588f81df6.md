
结构成员可以处于进程或线程级别。由于每个信号都有唯一的信号编号，我们使用一个宽度足够的结构成员，这样只需设置与我们要发送的信号编号相对应的位，即可表示每个信号。例如，设置第 17 位来发送信号 17，即 `SIGUSR2`（实际上对应第 16 位，因为位从 0 开始，而信号编号从 1 开始）。

由于在 Solaris 环境中现在可能有超过 32 个信号，`long` 或 `int` 数据类型不够宽，无法将每个可能的信号表示为一个唯一的位，因此我们需要一个结构。在 64 位 Solaris 7 中，`long` 是 64 位数据类型，但信号代码是在实现 64 位数据类型之前开发的。一些进程数据结构使用 `/usr/include/signal.h` 中定义的 `k_sigset_t` 数据结构来存储已发送的信号位。`k_sigset_t` 是两个无符号长整型数据类型（数组成员 0 和 1）的数组，提供 64 位的位宽，如图 8.21 所示。在 `signal.h` 中定义的 `sigset_t` 与 `k_sigset_t` 基本相同，只是其大小是后者的两倍（`sigset_t` 中有四个数组，而 `k_sigset_t` 中有两个）。

### 8.7.1 信号实现

我们对 Solaris 中信号实现的讨论反映了首次出现在 Solaris 2.5 中的代码。该讨论适用于从 Solaris 2.5 到 Solaris 7（含）的所有版本。

Solaris 环境的多线程架构在开发一种支持信号的方法时带来了一些有趣的挑战，该方法需要符合行业标准（如 POSIX）所定义的 Unix 信号语义。信号传统上经历两个明确的阶段：*产生*和*传递*。信号的*产生*是信号的起源点——发送阶段。当为该信号建立的任何处置（即使是被忽略）被调用时，信号就被称为已*传递*。如果信号被阻塞，从而推迟传递，则视为*挂起*。

在 Solaris 环境中，通过显式调用 `thr_create(3T)` 或 `pthread_create(3T)` 创建的用户线程各自都有自己的信号掩码。线程可以选择阻塞信号，而独立于同一进程中执行的其他线程；因此，在进程执行期间的不同时间，不同的线程可能可用于接收不同的信号。线程库（POSIX 和 Solaris 线程）提供了 `thr_sigsetmask(3T)` 和 `pthread_sigmask(3T)` 接口来建立每个用户线程的信号掩码。所有信号的处置和处理程序由进程中的所有线程共享，例如，一个 `SIGINT`（举例）在默认处置下会导致整个进程退出。由陷阱（`SIGFPE`、`SIGILL` 等）产生的信号被发送到导致陷阱的线程。异步信号（即所有未定义为陷阱的信号）被传递到找到的第一个未阻塞该信号的线程。

在 Solaris 环境中实现语义正确的信号的困难源于这样一个事实：用户级线程对内核不可见；因此，低级内核信号代码无法知道哪些线程阻塞了哪些信号，也无法知道信号应该发送到哪个线程。需要实现某种中介：一个既能看见用户线程信号掩码又能看见内核的东西。解决方案是线程库为链接到 `libthread` 的程序创建的一个特殊 LWP；这个 LWP 被称为 *aslwlp*（它实际上是一个 LWP/kthread 对，记住，它们总是成对出现）。aslwlp 的实现通过增加两个额外的步骤扩展了传统的信号产生和传递阶段：*通知*和*重定向*。

*产生* → *通知* → *重定向* → *传递*

向进程发送信号（*产生*）会导致 aslwlp 被通知，此时 aslwlp 会寻找一个可以接收该信号的线程。一旦找到这样的线程，信号就会被*重定向*到该线程，然后可以*传递*。此规则的例外是发送同步信号或陷阱信号（列在表 8-8 中）。陷阱信号（如 `SIGSEGV`）不会通过 aslwlp 传递，而是传递给导致陷阱的 LWP/kthread，然后从那里向上传递给用户线程。

在深入探讨信号传递的机制之前，我们应该先了解一下进程、LWP/kthread 和用户线程结构中用于支持信号的数据类型。
