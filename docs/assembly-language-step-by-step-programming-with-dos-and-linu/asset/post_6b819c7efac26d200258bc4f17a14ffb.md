Don't let the notion of a far pointer throw you. It's jargon you're going to hear again and again, and this was a good point at which to introduce it. A pointer is an address, quite simply. A near pointer is an offset address only, used in conjunction with some value in some segment register that presumably doesn't change. All pointers to objects inside a real flat model program are by definition near pointers.

A far pointer is a pointer that consists of both a segment value and an offset value, both of which may be changed at any time, working together. The video refresh buffer is not usually part of your data segment, so if you're going to work with it, you're probably going to have to access it with a far pointer, as we're doing here. Any time you need to reference something that exists outside the 64K boundaries of a real flat model program (as your system's text video buffer), you're going to work with a far pointer.

Note that most of Clear is setup work. The LES instruction loads both ES and DI with the address of the destination string. The screen atom character plus attribute value is loaded into AX.

The handling of CX deserves a little explanation. The value in BufLength is the size in bytes of the video refresh buffer. Remember, however, that CX is assumed to contain the number of times AX is machinened into memory. AX is a word, and a word is 2 bytes long. So, each time STOSW fires, 2 bytes of the video refresh buffer will be written. Therefore, in order to tell CX how many times to fire the gun, we have to divide the size of the refresh buffer (which is given in bytes) by 2, in order to express the size of the refresh buffer in words.

As I explained in Chapter 10, dividing a value in a register by 2 is easy. All you have to do is shift the value of the register to the right by one bit. What this the SHR CX,1 instruction divides: CX by 2.

# STOSW and the Direction Flag DF

Note the CLD instruction in the Clear macro. I've avoided mentioning it until now to avoid confusing. Most of the time you'll be using STOSW, you'll want to run it "uphill" in memory; that is, from a lower memory address to a higher memory address. In Clear, you put the address of the start of the video refresh buffer into ES and DI, and then blast/attribute pairs into memory at successively higher memory addresses. Each time STOSW fires a word into memory, DI is incremented twice to point to the next higher word in memory.

This is the logical way to work it, it doesn't have to be done that way. STOSW can just easily begin at a high address and move downward in memory. On each store into memory, DI can be decremented by 2 instead.

Which way STOSW fires—uphill successively higher addresses, or downhill successively lower addresses—is governed by one of the flags in the Flags register. This is the Direction flag DF. DF's sole job in life is to control the direction of certain instructions, like STOSW, can move in one of two directions in memory. Most of these (like STOSW) are string instructions.

The sense of DF is: When DF is set (that is, when DF has the value 1), STOSW and its fellow string instructions work downhill, from higher to lower addresses. When DF is cleared (that is, when it has the value 0), STOSW and its siblings work uphill from lower to higher addresses. This turn is simply the direction in which the DI is adjusted: When DF is set, DI is decremented. When DF is cleared, DI is incremented.

The Direction flag defaults to 0 (uphill) when the CPU is reset. It is generally changed in one of two ways: with the CLD instruction, or with the STD instruction. CLD clears DF, and STD sets DF. (You should keep in mind when debugging the POPF instruction can also change DF, by popping an new set of flags from the stack into the Flags register.) It's always a good idea to place the appropriate one of CLD or right before a string instruction to make sure that your machine fires in the right direction!

People sometimes get confused and think that DF also governs whether CX is incremented or decremented by the string instructions. So not! Nothing in a string instruction ever increments CX! You place a count in CX and it counts down, period. DF has nothing to say about it.

# The Semiautomatic Weapon: STOSW without REP

I chose to show you REP STOSW first because it's dramatic in the extreme. But even more, it's actually simpler to use REP than not to use REP. REP simplifies string processing from the programmer's perspective, because it brings the the instruction loop inside the CPU. You can use the STOSW instruction without REP, but it's a little more work. The work involves setting up the instruction loop outside the CPU and making sure it's correct.

Why both? Simply this: With REP STOSW, you can only store the same value into the destination string. Whatever you put into AX before executing REP STOSW is the value that gets fired into memory times. STOSW can be used to store different values into the destination string by firing it semiautomatically.

# Who Decrements CX?

Early in my experience with assembly language, I recall being confused about where and when CX is decremented. When you use STOSW (or any string instructions), CX is decremented automatically. But take away REP, and the automatic decrementing of CX stops. Obviously, something has to decrement CX, since CX governs how many times the string accesses memory. If STOSW doesn't do it—you guessed it—you have to do it somewhere else.

The obvious way to decrement CX is to use DEC CX. And the obvious way to determine if CX has decremented to 0 is to follow the DEC instruction with JNZ (Jump if Not Zero). JNZ tests the Zero flag ZF and jumps back to the STOSW until ZF becomes true. And ZF becomes true when a DEC causes its operand (here, CX) to become 0.

# The LOOP Instructions

With all in mind, consider the following instruction loop. Note that I've split it into three parts by inserting blank lines:

DoChar: stos    ; Note that there's no REP prefix!

```
add AL, '1'      ; Bump the character value in AL up by 1
aaa             ; Adjust AX to make this BCD addition
add AL, '0'      ; Basically, put binary 3 in AL's high nibble
mov AH, 07       ; Make sure our attribute is still 7
dec CX           ; Decrement the count by 1..
jnz DoChar      ...and loop again if CX > 0
```

Ignore the block of instructions in the middle for the time being. What it does is I suggested could do a little earlier: change each store of AX into memory. I'll explain in detail shortly. Look inside (for now) to see how the loop runs. STOSW fires, AX is modified, and then CX is decremented. The JNZ instruction tests to see if the DEC has forced CX to zero. If so, the Zero flag ZF is set, and the loop will terminate. But until ZF is set, the jump is made to the label DoChar, where STOSW fires yet again.
