Registers, if you recall, are special-purpose memory cubbyholes that exist inside the CPU itself, rather than in memory chips outside the CPU. DEBUG has a command that allows us to examine and change register values as easily as we examine and change

At the prompt, type R. (Think, Registers.) You'll see a display like

```
AX=0000 BX=0000 CX=0014 DX=0000 BP=0000 SI=0000 DI=0000 DS=0000 ES=0000 SS=0000 CS=0000 IP=0100
```

The bulk of the display consists of register names followed by equal signs, followed by the current values of the registers. The cryptic characters NV UP PL NC are the names of flags; we discuss them later in the book. The line beneath the register display is a disassembly of the byte at the address contained by the instruction pointer. (The instruction pointer is a register which is displayed by the R command, under the shorter name IP. IP's value in the preceding display—should be 0100, which is also the address of the.) This line will be useful when you're actually examining an executable file. In the case of SAM.TXT, the disassembly is misleading because SAM is not an executable program and contains nothing we intend to use as machine instructions. The hexadecimal 53H is a legal machine instruction—just as it is the ASCII for uppercase S. DEBUG doesn't know what kind of file SAM.TXT is. It could be a text file. If memory contains instead of machine instructions, the disassembly line should be ignored even though it will always be there. This is once again an example of the problems you can have in assembly language if you don't know what you're doing. Code and data look the same in memory. They are only different in how you interpret them. In SAM.TXT, the hex value 53H is the letter S; in an executable program, 53H would be the instruction PUSH BX. We make good use of the disassembly line later when we get down to real assembly language. For now, just ignore it. When DEBUG loads a file from disk, it places the number of bytes in the file in the CX register. CX is a general-purpose register but it is often used to contain such values and is therefore called the count register. Notice that the value of CX is 13H—just the number of bytes DEBUG reported when it wrote SAM.TXT out to disk in response to the W command. If we change the value in CX, we change the number of bytes DEBUG will write to disk. So let's fix SAM.TXT. In changing the word "man" to "mouse" we wrote two characters at the end of the sentence: the CR portion of the last line's EOL marker. We could start at address 012H and enter a period character (2EH). In doing so, however, we would overwrite the LF character, which is just as bad or worse. Unlike a text editor, DEBUG will not just overwrite the values to the right of the point where you wish to insert new values. DEBUG has no insert mode. You have to enter all three characters: the period, the CR, and the LF. We use the E command to enter, and then display a dump of the file again:

Now the file is repaired, and we can write it back to disk. Except—SAM.TXT in memory is two bytes longer than SAM.TXT on disk.

We need to tell DEBUG that it needs to write two additional bytes to disk when it writes SAM.TXT back out.

DEBUG keeps its count of SAM.TXT's length in the BX and CX registers. The count is actually a 32-bit number split between the two 16-bit registers BX and CX, with BX containing half of the 32-bit number. This allows us to load very large files into DEBUG, with byte counts that cannot fit into a single 16-bit register like CX. Sixteen registers can only contain values up to 65,535. If we wanted to DEBUG on an 80,000-byte file (which is not big at all these days, as go), we'd be out of luck if DEBUG only kept a 16-bit count of the file size in a single register.

But for small changes to files, or for working with small files, we only have to be aware of and work with the count in CX.
