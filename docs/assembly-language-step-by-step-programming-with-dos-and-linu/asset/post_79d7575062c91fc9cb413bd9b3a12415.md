## The Nature of a Megabyte

When running in segmented real mode, the x86 CPUs can use up to a megabyte of directly addressable memory. This memory is also called real mode memory. Modern x86 machines have a lot more memory than that—typically 32 MB or more. (My own machines have 256 MB of memory.) However, most x86 machines run in protected mode, which can address up to 4 gigabytes of memory. We return to protected mode in a big way towards the end of this book, in discussing Linux.

As I discussed briefly in Chapter 3, a megabyte of memory is actually 1 million bytes of memory, 1,048,576 bytes. It doesn't come out even in our base 10 because computers insist in base 2. Those 1,048,576 bytes expressed in base 2 is 10000000000000000000 bytes. (We don't use commas in base 2—that's yet another way to differentiate notation from decimal apart from the suffixed B.) That's 2²⁰, a fact that we'll return to shortly. The number 10000000000000000000B is so bulky that it's better to express it in the compatible (and much more compact) base 16, which we call hexadecimal. The quantity 2²⁰ is equivalent to 16⁶, and may be written in hexadecimal as 100000H. (If the notion of number bases still confounds you, I'd recommend another trip through Chapter 2, if you haven't been through it already. Or, even if you have.)

Now, here's a tricky and absolutely critical question: In a bank of memory containing 100000H bytes, what's the address of the very last byte in the memory bank? The answer is not 100000H. The clue is the flip side to that question: What's the address of the first byte in memory? That answer, you might recall, is 0. Computers always begin counting from 0. It's a dichotomy that will occur again and again in computer programming. The last in a row of four items is item number 3, because the first item in a row of four is item number 0. Count: 0, 1, 2, 3.

The address of a byte in a memory bank is the number of that byte starting zero. This means that the last, or highest, address in a memory bank containing 1 megabyte is 100000H minus one, or 0FFFFF. (The initial zero, while mathematically necessary, is there for the convenience of your assembler. Get in the habit of using an initial zero on any hex number beginning with the hex digits A through F)

The addresses in a megabyte of memory, then, run from 000000H to FFFFFH. In binary notation, that is equivalent to the range of 00000000000000000 to 111111111111111B. That's a lot of bits—20, to be exact. If you look back Figure 3.3 in Chapter 3, you'll see that a megabyte memory bank has 20 address lines. One of 20 bits is routed to each of those 20 address lines, so that any address expressed as 20 bits will identify one and only one of the 1,048,576 bytes contained in the memory bank.

That's what a megabyte of memory is: some arrangement of memory chips within the computer, connected by an address bus of 20-bit address is fed to those 20 address lines to identify 1 byte out of the megabyte.

## Backward Compatibility

Modern x86 machines have a lot more memory than that—typically 32 MB or more. (My own machines have 256 MB of memory.) The term real mode was coined as a contrast to protected mode, which is the much more powerful mode used in newer operating systems (such as Windows 9x and NT, as well as Linux) that allows the operating system much more control over what running on the machine can do. When you launch an MS-DOS window or “DOS box” under Windows 9x or NT, you’re creating what amounts to a little real mode island inside the Windows protected memory system. If you have a Windows machine, you should do all your assembly language for this book in an MS-DOS window, so that real mode conventions apply. (For Linux, obviously, this limitation does not apply!)

## 16-Bit Blinders

In real mode segmented model, an x86 CPU can “see” a full megabyte of memory. That is, the CPU chips themselves up so that they can use 20 of their 32 address pins and can pass a 20-bit address to the memory system. From that perspective, it seems pretty simple and straightforward. However, the bulk of all the trouble you’re likely to have in understanding real mode segmented model stems from this fact: whereas those CPUs can see a full megabyte of memory, they are constrained to look at that megabyte through 16-bit blinders.

You may call this peculiar. (If you do any significant amount of programming in this mode, you’ll probably call it much worse.) But you must understand it, and understand it thoroughly.
