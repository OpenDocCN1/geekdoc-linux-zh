
# PUSHAD was added with the 386, and it pushes all eight 32-bit general-purpose registers onto the stack in one blow.

All memory between SP's initial position and its current position (the top of the stack) contains real data that was explicitly pushed on the stack and presumably be fetched from the stack (we popped from the stack) later on. In real mode segmented model, the stack exists in a separate segment, and memory between SS and SP is considered free and available and is used to store new data that is to be pushed onto the stack. This is not the case in real flat model, where the stack shares the same segment as everything else in the program is using.

What can and cannot be pushed onto the stack is complicated and depends on what CPU you're using. None of the x86 CPUs can push 8-bit registers onto the stack. You can't push AL or BH or any other of the 8-bit registers. Segment registers and 32-bit extended general-purpose registers can be pushed in real mode, assuming you have a 386 or later CPU. Similarly, immediate data can be pushed onto the stack, but only if you have a 286 or later CPU. Keeping track of all this used to be a problem, but you're unlikely to be running code on CPUs earlier than the 386 these days.

Your morbid curiosity may be wondering what happens when SP runs out of room in its downward crawl and collides with SS. Nothing good, certainly—it depends heavily on how your program is laid out—but I would lay money on your program crashing and possibly taking the system down with it. (If you're working in a DOS box under Windows you at least won't crash the operating system. All bets are off for Windows 9!)

Stack crashes are serious business, at least in part there is only one stack in in real time. It's a little hard to explain (especially at this stage in our discussion), but this means that the stack set up for your own program must be large enough to support as well the needs of DOS and any interrupt-driven code (typically in the BIOS) that may be active while your program is running. If you don't fully understand how someone may be using your program's stack at the same time you are, give those others some extra room—and keep an eye on the proximity of SS and SP while you trace a program in DEBUG.

# POP Goes the Opcode

In general, what gets pushed must get popped, or you can end up in any of several different kinds of trouble. Getting a word off the stack is done with another trio of instructions, POP, POPF, and POPA. As you might expect, POP is the general-purpose one-at-a-time popper, while POPF is dedicated to popping the flags off the stack. POP 16 bytes off the stack into the eight general-purpose 16-bit registers. POPAD is the flip side of PUSH and pops the top 32 bytes off the stack into the eight general-purpose 32-bit registers.

- POPF : The top of the stack into Flags
- POPA : The top 16 bytes from the stack into AX, CX, DX, BX, SP, BP, SI, and DI
- POPAD : The top 32 bytes into EAX, EDX, EBX, ESP, EBP, ESI, and EDI
- POP SI : The top of the stack into SI
- POP CS : The top of the stack into CS
- POP [BX] : The top of the stack into memory at DS:BX

As with PUSH, POP-unit only operates on word-sized operands. Don't try to pop data from the stack into an 8-bit register such as AH or CL.

POP works pretty much the way PUSH does, but in reverse: The word of data is copied from the stack and placed in POP's operand, whatever you specified to be. Then, SP is incremented (rather decremented) by two bytes, so that in effect it moves two bytes away from SS.

It's significant that SP is decremented before placing a word on the stack at push time, but incremented after removing a word from the stack at pop time. Certain other CPUs work in the opposite manner, which is fine—just don't get confused. Unless the stack is empty, SP points to real data, not empty space.

Ordinarily, you don't have to remember that fact, as PUSH and POP handle it all for you and you don't have to manually keep track of what SP pointer is pointing to. It helps to know the sequence of events behind PUSH and POP—and that's an advanced topic that I won't be going into this book.

Each time one of the registers is pushed onto the stack, SP is decremented two bytes down toward SS. The first three columns show AX, BX, and CX being pushed onto the stack, respectively. In effect, CX was pushed onto the stack, and then immediately popped off DX.

That’s a roundabout way to copy the value of CX into DX. MOV DX,CX is lots faster and more straightforward. However, MOV will not operate on the Flags register. If you want to load a copy of Flags into a register, you must first push the Flags register onto the stack with PUSH, then pop the flags off the stack into the register of your choice with POP.

# Storage for Short Term

The stack should be considered a place to stash things for the short term. Items stored on the stack have no names, and in general must be taken off in the reverse order that they were put on. Last in, first out, LIFO!

One excellent use of the stack is to temporarily hold some value. While you're using the register, its value will remain safe on the stack. When you're finished using the register, you pop it off the stack.

# Using DOS Services through INT

I think of EAT.ASM as something of Tom Sawyer. It doesn’t do much, and it does what it does in Tom Sawyer fashion: All that EAT displays is character string on screen. The other part is the pair of invisible characters we call newline: carriage return (0DH) followed by line feed (0AH). (For more EOL and how you interact with text, see Chapter 4.) The EOL marker does nothing than return the display cursor to the left margin of the next line, so that any subsequent text will begin at the left margin.

Both parts of our advertising slogan are sent to the display at once, and via the mechanism: I explain in Chapter 4, DOS is both a god and a troll. It controls all the most important elements of the machine in godlike fashion: the disk drives, the printer, and (to some extent) the display. At the same time, DOS is like a troll living under a bridge to all parts of machine: You tell the troll what you want done, and the troll will go out and do it for you.

There is another troll guarding the other components of machine called the BIOS, to which we will return in a little while. DOS and BIOS offer services, which are simple tasks that your programs would have to do if the services were not provided. Quite apart from saving you the programmer lot of work, having DOS and BIOS services helps guarantee that certain things will be done in identical on all machines (especially in terms of disk storage) is a major reason software for DOS runs on so many different machines: All the machine-dependent stuff is done the same way.
