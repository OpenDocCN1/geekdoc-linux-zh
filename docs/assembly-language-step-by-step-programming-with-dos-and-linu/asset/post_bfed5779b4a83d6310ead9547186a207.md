## Memory Data or Immediate Data?

You may be wondering the variable identifier LRXY is for and where it is defined. It's for simple to hold the current X,Y coordinates for the lower-right corner of the screen. Where it is defined in the program's data segment, in the usual way variables are defined, and you'll see if you look ahead to the full listing of EAT3.ASM which follows.

The more interesting question is why. Most of the time I've used you values loaded into registers from immediate data, and this is often useful. The coordinates of the upper-left corner of the full screen, for example, are always going to be 0,0, and nothing will ever change that. The lower-right corner, however, is not necessarily 79,24.

The original 1981 vintage IBM MDA and CGA graphics adapters are capable of 80 by 25 text screens and no more. However, with EGA, it is possible to have an 80 by either 25 or 43 text screen, and the VGA introduced in 1987 with the PS/2 line can display either 25 or 50 lines, all 80 characters wide. The newer VGA video boards are capable of even different text modes, some of them with more than 80 characters in a visible line. If your program can determine what size screen is in force when it is invoked, it can modify its displays accordingly.

Avoid dropping immediate values into code (we call this hard coding) whenever you can. A better strategy, which I follow from now on, uses variables in the data segment initialized with currently correct values when the program begins running.

## Use Comment Headers!

As time goes on, you'll find yourself creating dozens or even hundreds of procedures as a means of not reinventing the same old wheel. The libraries of available procedures that most high-level language vendors supply with their compilers just don't exist with assembly language. By and large large, you create your own.

Keeping such a list of routines is no easy task when you've written them all yourself. You must document the essential facts about each individual procedure or you'll forget them, or remember them incorrectly and act on bad information. (The resultant bugs are often devilishly hard to find when you're sure you remember everything there is to know about that proc! After all, you wrote it!)

I recommend adding a comment header to every procedure you write, no matter how simple. Such a header should contain the following information:

- The name of the procedure
- The date it was last modified
- What it does
- What data items the caller must pass to make it work correctly
- What data is returned by the procedure, if any, and where it is returned (for example, in register CX)
- What other procedures, if any, are called by the procedure
- Any “gotchas” that need to be kept in mind while writing code that uses the procedure

A workable procedure header is this:

```
------------------------------------------------------------
; WRITELN -- Displays information to the screen via DOS
;      service 9 and issues a newline
;   Last update 9/11/99
; 
;  1 entry point:
;   Writeln:
;      Caller must pass:
;      DS: The offset of the string to be displayed
;      DX: The offset of the string to be displayed
;      String must be terminated by "$"
;   Action: Displays the string at DS up to the "*" marker
;      marker, then issues a newline. Hardware cursor
;      move to the left margin of the following
;      line. If the display is to the bottom screen
;      line, the screen will scroll.
;   Calls: Write
------------------------------------------------------------
```

A comment header does not relieve you of the responsibility of commenting the individual lines of code within the procedure. It's a good idea to put a short comment to the right of every line that contains a mnemonic instruction, and also (in longer procedures) a comment block describing every major functional block within the procedure.
