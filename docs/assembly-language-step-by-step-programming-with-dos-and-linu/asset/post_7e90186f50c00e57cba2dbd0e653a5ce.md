# The Swiss Army Compiler

The copy of EMACS that you will find on modern distributions of Linux doesn't have a whole lot of Richard Stallman left in it—it's been rewritten times by many other people over the past 20-odd years. Where the Stallman legacy persists most strongly is in the GNU compilers. There are a number of them, but the one that you must understand as thoroughly as possible is the GNU C Compiler, gcc. (Lowercase letters are something of an obsession in the Unix world, a fetish not well understood by a lot of people, myself included.)

Why use a C compiler for working in assembly? Two reasons:

- Most of Linux and all of the standard C library for Linux are written in C for. The C library is the only reasonable way to communicate with Linux from an assembly program. Gcc has a great deal of intimate knowledge of the standard C library that you'll need to learn if you choose not to use it. Love Linux, gcc. There's no way around it.

- More interestingly, gcc does much more than simply compile C code. It's a sort of Swiss army knife development tool. In fact, I might better characterize what it does as building software rather than simply compiling it. In addition to compiling C to object code, gcc governs both the assembly step and the link step.

Assembly step? Yes, indeed. There is a GNU assembler, gas. And a GNU linker. What does gcc control them like puppets on strings. If you use gcc (especially at the beginner level), you don't have to do much messing around gas and ld.

Let's talk more about this.

# Building Code the GNU Way

Assembly language is a departure from C work, and gcc is first and foremost a C compiler. So, we need to look first at the process of building C code. On the surface, building a C program for Linux using the GNU tools is pretty simple. Behind the scenes, however, it's seriously hairy business. While it looks like gcc does all the work, what gcc really does is act as master controller for several GNU tools, supervising a code assembly line that you don’t need to see unless you specifically want to.

Theoretically, this is all you need to do to generate an executable binary from C source code:

```bash
gcc eatc.c -o eat
```

Here, gcc takes the file eatc.c (which is a C source code file) and crunches it to produce the file. The (-o option tells gcc what to name the executable output file). Note well that in the Linux world, executable files typically do not have file extensions, as they do DOS and Windows. What might be eatc.com or eatc.exe under DOS is simply eat under Linux.

However, there’s more going on here that meets the eye. Take a look at Figure 12.1 as we go through it. In the figure, shaded arrows indicate movement of information. Blank arrows indicate program control.

The programmer invokes gcc from the shell command line. gcc takes control of the system and immediately invokes a utility called the C processor, cpp. The preprocessor takes the original C source code file and handles items like #includes and #defines. It can be thought of as a sort of macro expansion pass on the source code file, if “macro expansion pass” means anything to you. If not, don’t fret it—it’s C thing and not germane to assembly work.

When cpp is finished with its work, gcc takes over in earnest. From the preprocessed source code file, gcc generates an assembly language source code file with a .s extension. This is literally the assembly code equivalent of the C statements in the original .c file, in human-readable form. If you develop any skill in reading AT&T syntax and mnemonics, you can learn a lot from inspecting the .s files produced by gcc.

When gcc has completed generating the assembly language equivalent of the C source code file, it invokes the GNU assembler, gas, the .s file into object code. This object code is written out in a file with a .o extension.

The final step involves the GNU linker, ld. The .o file contains binary code, but it’s only the binary code generated from statements in the original .c file. The .o file does not contain the code from the standard C-library Source Code.

# We Use Assembly in Work

The process I just described, and we drew in Figure 12.1, is how a program is built under Linux, so we don't need to use assembly. However, if you want to write assembly yourself, you'll need to use an assembler. The most common assembler on Linux is gas, but there's another one called NASM that is much easier to use.

If you want to use NASM, the command looks like this:

```bash
nasm -f elf eat.asm -o eat
```

The -f elf tells NASM to produce output in ELF format, which is the standard format for Linux. The -o option tells NASM what to name the output file. The input file is eat.asm, which contains your assembly code.

If you want to use gas, the command looks like this:

```bash
as -m elf eat.s -o eat
```

The -m elf tells gas to produce output in ELF format. The -o option tells gas what to name the output file. The input file is similar.

# Why Not gas?

You might be wondering why, if there's a perfectly good assembler installed with every copy of Linux, I'm bothering to show you how to install and use another one. First of all, there is no gas like DOS as best I know, so you can't take your steps in assembly while working with DOS. But more important, gas uses a peculiar syntax that is utterly unlike that of all the other assemblers used in the DOS (MASM and TASM) and a whole set of instruction mnemonics unique to itself. I find them unintitive and hard to read. This is the AT&T syntax, because it was created by AT&T as a portable assembly notation to make Unix easier to port from one CPU to another. It's ugly because it was designed to be generic, and it can be recast for any CPU you come with. (Don't forget that Unix predicates the x86, and gas's predecessor is older than the x86).

If it were simple, I wouldn't mention gas at all, since you don't need to use it to write Linux code in NASM. However, one of the major ways you'll end up learning many of the standard library calls is by using them in short C programs and then inspecting the assembly output gcc generates (I have more to say about this later on.) What gcc generates when it compiles a C program is a file (with a .extension) of assembly source code using the AT&T syntax and mnemonics. It may not be necessary to learn the AT&T syntax thoroughly enough to write it, but it will be very helpful if you can pick it well enough to read it. I'll show you an example later on, and when I do I will summarize the important differences between AT&T and the NASM syntax and mnemonics, which are more properly coded the Intel syntax and mnemonics.
