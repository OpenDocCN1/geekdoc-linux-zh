
Code and data are two very different kinds of critters, but they interact in ways that make the game interesting. The code includes steps that place data into storage (MOVE instructions) and steps that alter data that is already in storage (INCREMENT and DECREMENT instructions). Most of the time you'll think of code as being the master of data, in that the code writes data into storage. Data influence code as well, however. Among the tests the code makes examine in storage, if a given data value exists in storage, the code may do one thing; if that value does not exist in storage, the code will do something else, as in JUMP BACK and JUMP A.

The short block of instructions marked PROCEDURE is a detour off the main stream. At any point in the program you can duck into procedure, perform its steps and tests, and return to the very place from which you left. This allows a sequence of steps and tests that is generally useful to exist in only place rather than as separate copy everywhere it is needed.

## Addresses

Another critical concept lies in the left side of the program. Each number is unique, in that a location tagged with that number appears only once inside the computer. This location is called an address. Data is stored and retrieved by specifying the data's address in the machine. Procedures are called by specifying the address at which they begin. The little box (which is also a storage location) marked PROGRAMTER keeps the address of the next instruction to be performed. The number inside the program counter is increased by one (we say, "incremented") each time an instruction is performed unless the instruction tells the program counter to do something. For example: Notice the JUMP BACK 7 instruction at address 0. When this instruction is performed, the program counter will back up seven counts. This is analogous to the "go back three spaces" concept in board games.

## Metaphor Check

That's about as much explanation of Assembly Language as I'm going to offer for now. This is still Chapter 1, and we are still in metaphor territory. People who have had some exposure to computers will recognize and understand more of what there's a real program going in there—and dare to figure out how! People with no exposure to computer innards at all shouldn't feel left behind for being utterly lost. I created Assembly Language solely to put across the following points:

- The individual steps are very simple. One single instruction rarely does more than a single byte from one storage to another, or compare the value contained in one storage to a value contained in another. This is good news, because it allows you to concentrate on the task accomplished by a single instruction without being overwhelmed by complexity. The bad news, however, is the following:

- It takes a lot of steps to do anything useful. You can often write a useful program in languages as Pascal or BASIC in five or six lines. You can actually create programs in Visual Basic without writing any code at all. (The code is still there... but all you're really doing is choosing chunks in a collection.) A useful assembly language program cannot be implemented in fewer than 50 lines, and anything challenging takes hundreds or thousands of lines. The skill of assembly language programming is structuring these hundreds or thousands of instructions can be read and understood.

- The key is understanding memory addresses. In languages as Pascal and BASIC, the compiler takes care of where something is located—you simply have to give that name and call it by that name whenever you want to look at it or change it. In assembly language, you must always be cognizant of where things are in your computer’s memory. So, in working through this book, pay special attention to the concept of addressing, which is nothing more than the art of specifying something. Assembly Language is peppered with addresses and instructions that work with addresses (such as MOVE data at B to C, which means move the data stored at register B to the address specified by register C). Addressing is by far the trickiest part of assembly language, but master it and you’ve got the whole thing in your pocket.

Everything I've said so far has been orientation. I've tried to give you a taste of the big picture of assembly language and how its fundamental principles relate to the life you've living all along. Life is a sequence of steps and tests, and so are board games—and so is assembly language. Keep those metaphors in mind as we proceed to get real by confronting the nature of computer numbers.

### The Return of the New Math Monster

The year 1966. Perhaps you were there. New Math burst upon the grade school curricula of the nation, and homework became a turmoil of number lines, sets, and alternate bases. Middle-class parents scratched their heads with their children over questions like, “What is 17 in Base Five?” and “Which sets does the Null Set belong to?” In very short order (I recall a period of about two months), the whole thing was tossed in the trash as quickly as it had been concocted by addlebrained educators with too little to do.

This was a pity, actually. What nobody seemed to realize at the time was that we were learning New Math—except that Old Math had never been taught at the grade school level either. Keeping wondering of what possible use it was to know the intersection of the set of squirrels and mammals was—the truth, of course, was that it was no use at all. Mathematics in America has always been taught as applied mathematics—arithmetic—heavy on word problems. If it won't help you balance your checkbook or proportion a recipe, it ain't real math.
