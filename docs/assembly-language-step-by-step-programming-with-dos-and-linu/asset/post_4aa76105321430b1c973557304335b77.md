## The Mechanics of Macro Definition

A macro definition looks a little like a procedure definition, framed between a pair of directives: %macro and %endmacro. Note that the %endmacro directive is on the line after the last line of the macro. Don't make the mistake of treating %endmacro as a label that marks the macro’s last line.

One shortcoming of macros vis-à-vis procedures is that macros can have only one entry point. A macro, after all, is a line of code that is inserted into your program in the midst of the flow of execution; execution has to go through the whole thing. The ClrSc described in the last section cannot be converted into a macro without splitting it into four separate invocations of VIDEO interrupt 10H. If the ClSc function (clearing the full screen for blanks for the normal video attribute) also were written as a macro, it would look like this:

```
%macro ClrSc
mov CX, 0        ; Upper left corner of full screen
mov DX, ABCD      ; Load lower-right XY coordinates into DX
mov AL, 0        ; 0 specifies clear entire region
mov BH, 07H       ; Specify "normal" attribute for blanked line(s)
mov AH, 06H       ; Select VIDEO service 6: Initialize/Scroll
int 10H           ; Call VIDEO
%endmacro
```

You can see that ClrSc has shed its RET instruction and its additional entry points, but from that, it’s exactly the same sequence of instructions. Functionally it works the same way, except every time you clear your screen, ClrSc’s six instructions are dropped into the source code.

Macros are called simply by naming them. Don’t use the CALL instruction! Just place the macro name on a line:

ClrSc

The assembler will handle the rest.

## Defining Macros with Parameters

So far, macros may seem useful but perhaps not especially compelling. What makes macros really sing is their ability to mimic high-level language subroutines and take arguments through parameters. For example, if you were to define a macro named GotoXY that would position the hardware cursor, you could pass it the X and Y values as arguments, separated by a comma:

```

```

You'd have to pinch yourself to be sure you aren't working in Basic, no? Macro parameters are, again, artifacts of the assembler. They are not pushed on the stack or set to COMMON or anything like that. The parameters are simply placeholders for the actual values (called arguments) that you pass to the macro through its parameters.

## Local Labels within Macros

A label in a macro is made by beginning it with two percent signs: "%%". When marking a location in the macro, the local label should be followed by a colon. When used as an operand to a jump or call instruction (such as JB and LOOP in the preceding), the local label is not followed by a colon. The important thing is to understand that unless the labels Tester and Bump were made local to the macro by adding the prefix %, there would be multiple instances of a label in the program and the assembler would generate a duplicate label error on the second and every subsequent invocation of the macro. All labels defined within a macro are considered local to the macro. Here's an example from the file MYLIB.MAC:

```
%macro UpCase 2 ; Target,Length
mov CX, $2 ; CX is acting as length counter for
mov BX, $1 ; String will be at DS:BX
%%Tester: cmp BYTE [BX],'a' ; Is string character below 'a'?
jb %%Bump ; If so, leave character alone
cmp BYTE [BX],'z' ; Is string character above 'z'?
ja %%Bump ; If so, leave character alone
and BYTE [BX],11011111b ; Char is lc alpha, force bit 5 to 0
%%Bump: inc BX ; Bump BX to point to next char in string
loop %%Tester ; And go back and do it again!
%endmacro
```
