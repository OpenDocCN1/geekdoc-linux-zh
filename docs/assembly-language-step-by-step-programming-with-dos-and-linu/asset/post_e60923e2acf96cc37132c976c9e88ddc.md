
DEBUG will respond by displaying the current value of AX (here "0000") and then, on the following line, a colon prompt. It will wait for you to enter a new numeric value for AX, or for you to press Enter. If you press Enter, the current value of the register will not be changed. In the preceding example, I typed "0A7B" (you don't need to type the H indicating hex) followed by Enter.

Once you do enter a new value and then press Enter, DEBUG does nothing to verify that the change has been made. To see the register AX, you must display all the registers again using the R command:

## Inspecting the Video Refresh Buffer with DEBUG

One good way to help your knowledge of memory addressing sink is to use DEBUG to take a look at some interesting places in the PC’s memory space.

One easy thing to do is look at the PC’s video display adapter’s text screen refresh buffer. A video refresh buffer is a region of memory with a difference: Any characters written to buffer memory are instantly displayed on the computer’s screen. This is accomplished electrically through special use of the information that comes out of the memory data pins. Precisely how it is done outside the scope of this book. For now, simply understand that writing a character to your text mode display screen (which is not the Windows graphical UI screen!) can be done by writing the ASCII code for that character into the code address in the video buffer portion of memory.

The text mode display buffer is the screen that appears when you’re running DOS or else working in a DOS window (or "DOS box") from within MS Windows. It consists not of icons or graphical images or figures but simple textual characters, arranged in a matrix typically 25 high and 80 wide. This used to be the mainstay of all computing; now, text screens seem downright outdated to most people.

As with any memory location anywhere within the PC, the video refresh buffer has a segment address. What that segment address depends on the kind of display installed in the PC. There are two possibilities, and which is easy enough to determine: if your PC has a color screen, the segment address of the video refresh buffer is 0B00H. If you have a monochrome screen (a situation now becoming vanishingly rare), the segment address is 0B00H instead.

It takes 2 bytes in the buffer to display a character. The first of the two (that is, first in memory) is the ASCII code of the character itself. For example, an A would require the ASCII code 41H; a B would require the ASCII code 42H, and so on. (The full ASCII code is set in Appendix-D.) The second of the two bytes is the character’s attribute. Think of this way: in the display of a character on the screen, the ASCII code says what and the attribute says how. The attribute dictates the color of a character and its background cell on color screen. On a monochrome screen, the attribute specifies whether a character is underlined or displayed in reverse video. (Reverse video is a character display mode in which a dark character is shown on a light background, rather than the traditional light character on a dark or black background.) Every character has an attribute byte and every attribute has its character byte; neither can exist alone.

The first character/attribute pair in the video refresh buffer corresponds to the character you see in the upper-left-hand corner of the screen. The next character/attribute pair in the buffer is the character on the second position on the top line of the screen, and so on. I’ve drawn a diagram of the relationship between characters on the screen and byte values in the video refresh buffer in Figure 6.11.

In Figure 6.11, the three letters “ABC” are displayed in the upper-left corner of the screen. Notice that the “C” is underlined. The screen shown in Figure 6.11 is a monochrome screen. The video refresh buffer begins at 0B00:0. The byte located at address 0B00:0 is ASCII code 41H, corresponding to the letter “A.” The byte at address 0B00:1 is the corresponding attribute value of 07H. The 07H value as an attribute dictates normal text in both color and monochrome displays, in which normal means white characters on a black background.

The first 160 characters (80 ASCII codes plus 80 attribute bytes) are shown as the first line, and the subsequent 160 characters are shown on the next line down the screen. You might rightfully ask what the locations that show no character at all are. The answer, of course, is empty space, whose ASCII code is 20H.

You can inspect the memory within the video buffer directly through DEBUG. Take the following steps:

- Clear the screen by entering CLS and pressing Enter.
- Invoke DEBUG.
- Decide where your video refresh buffer is located, enter the proper segment address into the ES register. Remember: Color screens use 0B800H segment address, while monochrome screens use 0B00H segment address. In the year 2000, it's a 98 percent chance that your screen is color and not monochrome. Note from the following dump that 0B00H must be entered into DEBUG as “B800”, without the leading zero. NASM (your assembler) must have leading zero, and DEBUG cannot have it. Sadly, no one ever said all of this business had to make sense.
- Dump the first 128 bytes of the video refresh buffer by entering ES:0 and pressing Enter.
- Dump the next 128 bytes of the video refresh buffer simply by entering the D command a second time (I won't say "press Enter" every time. It's assumed you must follow a command pressing Enter.)
