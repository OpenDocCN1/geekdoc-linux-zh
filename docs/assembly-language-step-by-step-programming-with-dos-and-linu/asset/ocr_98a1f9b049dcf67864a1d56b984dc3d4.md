# An Uneasy Alliance

One useful peculiarity of DEBUG illustrated here is that when begin a hex dump of memory at an address that is not evenly divisible by 16, DEBUG spaces the first byte of the dump over to the right so that paragraph boundaries still fall at the left margin.

Another peculiar thing to keep in mind while looking at the particular dump shown in the preceding is that only the first line of memory shown in the dump really exists. The segment 0FFFFH begins only 16 bytes before the end of real mode's megabyte of memory space. (See Figure 6.4 for a good illustration of this.) The byte at 0FFFF:000F is the last byte in real mode memory—and DEBUG is a real mode creature. Addresses from 0FFFF:0010 to 0FFFF:would require more than 20 address bits to express, so in real mode they may well as not. (They do not see them!)

DEBUG won't tell you that—it'll give you endless pages of zeroes for memory beyond the real mode megabyte pale. (Several readers told me that certain versions of DEBUG take a different approach, and wrap their display around to bottom of 0000:0000 once they run out of high memory. It is something to watch out for, and if memory beyond the F:000F point is not zeros, you're in fact seeing such a wrap to low memory.)

# Transferring Control to Machine
Instructions in Read-Only Memory

So we've looked at locations in memory as containers for data. All well and good—but memory contains machine instructions as well. A very effective illustration of a machine instruction at a particular address is also provided by the ROM BIOS—and right next to the BIOS revision date, at that.

The machine instruction in question is located at address 0FFFF:0. Recall that, by convention, the next instruction to be executed is the one whose address is stored in CS:IP. Run DEBUG. Load the value 0FFFFH into code segment register CS, and 0 into instruction pointer IP. Then dump memory at 0FFFF:0.

```
- r cs
CS 1980
:ffff
- r ip
IP 0100
:0
```
