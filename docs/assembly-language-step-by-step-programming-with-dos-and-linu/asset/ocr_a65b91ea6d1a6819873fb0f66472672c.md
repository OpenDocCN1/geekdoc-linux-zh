In short programs, this may not be a problem, and in situations where the code must be as fast as possible—as in graphics drivers—macros have a lot going for them.

# The Mechanics of Macro Definition

A macro definition looks a little like a procedure definition, framed between a pair of directives: %macro and %endmacro. Note that the %endmacro directive is on the line after the last line of the macro. Don't make the mistake of treating %endmacro as a label that marks the macro’s last line.

One shortcoming of macros vis-à-vis procedures is that macros can have only one entry point. A macro, after all, is a line of code that is inserted into your program in the midst of the flow of execution; execution has to go through the whole thing. The ClrSc described in the last section cannot be converted into a macro without splitting it into four separate invocations of VIDEO interrupt 10H. If the ClSc function (clearing the full screen for blanks for the normal video attribute) also were written as a macro, it would look like this:

```
%macro ClrSc
mov CX, 0        ; Upper left corner of full screen
mov DX, LRXY      ; Load lower-right XY coordinates into DX
mov AL, 0        ; 0 specifies clear entire region
mov BH, 07H       ; Specify "normal" attribute for blanked line(s)
mov AH, 06H       ; Select VIDEO service 6: Initialize/Scroll
int 10           ; Call VIDEO
%endmacro
```

You can see that ClrSc has shed its RET instruction and its additional entry points, but from that, it’s exactly the same sequence of instructions. Functionally it works the same way, except every time you clear your screen, ClrSc’s six instructions are dropped into the source code.

Macros are called simply by naming them. Don’t use the CALL instruction! Just place the macro name on a line:

ClrSc

The assembler will handle the rest.
