At the end of the line, ld spits out the fully linked and executable pro-gram file. At that point, the build is done, and gcc returns control to the Linux shell. Note that all of this is typically done with one simple com-mand to gcc!

# ## We Use gcc in Assembly Work

The process I just described, and drew out for you in Figure 12.1, is how a C program is built under Linux using GNU tools. I went into some detail here because we’re going to use part—though only part—of this process to make our assembly programming easier. It’s true that we don’t need to convert C source code to assembly code—and in fact, we don’t need gas to convert assembly source code to object code. But we need gcc’s expertise in linking. Linking a Linux program is much more complex than linking a simple DOS program. We’re going to tap in the GNU code-building process at the link stage, so that gcc can coordinate the link step for us.

When we assemble a Linux program using NASM, NASM generates a .o file containing binary object code. Invoking NASM under Linux is typically done this way:

```
nasm -f elflinux.asm
```

This command will direct NASM to assemble the file elinux.asm and generate a file called elinux.o. The “-f elf” part of it tells NASM to generate object code in the ELF format (the means Executable and Linking Format), so saying “ELF format” is redundant even though everyone does it rather than one of the numerous object code formats that NASM is capable of producing. The elinux.o file is not by itself executable. It needs to be linked. So, we call gcc and instruct it to link the program for:

```
gcc elinux.o -o elinux
```

What of this gcc to link and not compile? The only input file called out in the command is a .o file containing object code. This fact tells gcc all that needs to be done is to link the file with the C library to produce the final executable. The “-o elinux” tells gcc the name of the final executable file is to be “elinux.” (Remember that Linux does not use file extensions on executable files.)
