The next and stepi have shorthand forms: ni and si.

The difference between stepi and next may seem odd at first: Stepi executes the next machine instruction in the execution path, irrespective of which instruction it is, whereas next executes the next machine instruction in the execution path unless that instruction is a CALL instruction. If next executes a CALL instruction, it executes the whole of the subroutine invoked by that instruction without pausing.

Users of Borland's programming languages are probably familiar with two debugging commands built into Borland's interactive environments: Step Over and Trace Into. Trace corresponds to gdb's step command, and Step Over corresponds to gdb's next command.

The idea is this: While you're stepping along a program, you may wish to avoid climbing down into subroutines and stepping through them by instruction—unless you're debugging the subroutine. This is especially true of subroutines that are in fact calls into the standard C library. If you're hitting a bug, it's unlikely to be in the C library. (Suspect your own code in virtually every case. Those library routines are extremely robust!) So, assuming you can trust the C library functions your program is calling, you probably don't want to waste time going through an instruction at a time. The same may be true of subroutines in your own code library. You may have written them and proven them out long ago, so rather than go through an instruction at a time, you'd prefer to execute the whole subroutine at once.

If this is the case, you should single-step with next. When next encounters a CALL instruction, it executes CALL and all the instructions within the subroutine invoked by CALL instruction as though the whole subroutine was a single instruction. Boom! The subroutine has run, and you go on to the next instruction in the code execution sequence.

Stepi, on the other hand, treats all machine instructions identically: It follows the CALL instruction down into its subroutine and executes each of the subroutine's instructions in turn, coming back when the subroutine executes a RET instruction.
