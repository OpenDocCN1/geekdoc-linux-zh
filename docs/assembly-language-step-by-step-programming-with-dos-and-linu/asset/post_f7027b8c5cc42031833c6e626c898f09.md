
# Stringing Up

```
DoChar:  stos ; Note that there's no REP prefix!
      add    AL, '1' ; Bump the character value in AL up by 1
      aaa             ; Adjust AX to make this a BCD addition
      add    AL, '0' ; Basically, put binary 3 in AL's high nyble
mov    AH, 07 ; Make sure our attribute is still 7
```

```
loop DoChar ; Go back & do another until CX goes to 0
```

The LOOP instruction first decrements CX by 1. It then checks the Zero flag to see if the decrement operation forced CX to zero. If so, it falls through to the next instruction. If not (that is, ZF remains 0, indicating that CX was still greater than 0), LOOP branches to the label specified as its operand.

So, the loop keeps looping the LOOP counts down to 0. At that point, the loop is finished, and execution falls through and continues with the next instruction following the loop.

# Displaying a Ruler on the Screen

As a useful demonstration of when it makes sense to use STOSW-without REP (but with LOOP) let me offer you another item for your video toolkit.

The Ruler macro which follows displays a repeating sequence of ascending digits from 1 at some selectable location on your screen. In other words, you can display a sequence of digits like this at the top of a window:

```
123456789012345678901234567890123456789012345678901234567890
```

This might allow you to determine where the window line begins or some character falls. The macro allows you to specify how long the ruler is, in digits, and where on the screen it be displayed.

A call to Ruler would look like this:

```
Ruler VidOrigin,20,80,15,5
```

This invocation (assuming you had defined VidOrigin to be the address of the start of the video refresh buffer in your machine) places a 20-character long ruler at position 15,5. The “80 argument indicates to Ruler that your screen is 80 characters wide. If you have a wider or narrower screen, you would have to change the “80” to reflect the true width of your screen in text mode.

# ASSEMBLY LANGUAGE STEP-BY-STEP

Don't just read the code inside Ruler! Load it into a copy of EAT5.ASM, and display some rulers on the screen. You don't learn half much as just reading assembly code as you do by loading and using it!

```
; RULER -- Displays a "1234567890"-style ruler on-screen
; Last update 9/16/99
;
; Caller must pass:
; InAddress: The address of the start of the video buffer
; InLength: The length of the ruler to be displayed
; InScreenW: The width of the current screen (usually 80)
; InScreenY: The line of the screen where the ruler is
; be displayed (0-24)
; InScreenX: The row of the screen where the ruler should
; start (0-79)
; Action: Displays an ASCII ruler at ScreenY.
%macro Ruler 5,VidAddress,Length,ScreenW,ScreenX,ScreenY
, DI,[1] ; Load video address to ES:DI
mov AL,%5 ; Move Y position to AL
mov AH,%3 ; Move screen width to AH
imul ; Do bit-8 multiply*AH to AX
add DI,AX ; Add Y offset into vidbuff to DI
add DI,%4 ; Add X offset into vidbuff to DI
shl DI,1 ; Multiply by two for final address
mov CX,%2 ; CX monitors the ruler length
mov AH,07 ; Attribute 7 is "normal" text
mov AL,'1' ; Start with digit "1"
%DoChar: stosw
add AL,'1' ; Bump the character value in AL up by 1
aaa
add AL,'0' ; Adjust AX to make this a BCD division by binary 3 in AL's high nyble
mov AH,07 ; Make sure our attribute is still 7
loop %DoChar ; Go back & do another until BL goes to 0
%endmacro
```

Over and over the LOOP instruction, there's a fair amount of new assembly technology at work here could stand explain. Let's detour from the string instructions for a bit and take a closer look.

# Simple Primitives with IMPUL

Ruler can put its ruler anywhere on the screen, to a position passed as ScreenX and ScreenY. It's not using GotoXY, either. It's actually calculating a position in the video refresh buffer where the ruler characters must be placed—and then using STOS to place them there.

# Stringing Up

Locations in the text video refresh buffer are expressed as offsets from a single segment address that is either B000H or B800H. The algorithm for determining the offset in bytes for any X and Y values looks like this:

```
Offset = ((Y * width in characters of a screen line) + X) * 2
```

Pretty obviously, you have to move Y lines down in the screen buffer, and then move X bytes over from the left margin of the screen to reach your X,Y position.

The trickiest part of implementing the algorithm lies in multiplying the Y value. The trickiest part is that IMUL sets two flags in those cases where the product is larger than 8 bits. The flags involved are the Carry flag CF and the Overflow flag OF. For example, if you're multiplying two 8-bit operands and the product is larger than 8 bits, both CF and OF will be set. Otherwise, the two flags will be cleared.

Now why the final multiplication by 2? Keep in mind that every character in the screen buffer is represented by 2 bytes: One character byte and one attribute byte. So, moving X characters from the left margin actually moves X x 2 bytes into the screen buffer. You might think of an 80-character line on the screen as being 80 characters long, but it's actually 160 characters long in the screen buffer, to account for the invisible attribute bytes.

This multiplication by 2 is done by using the SHL instruction to shift DI to the left by one bit. As I explained in Chapter 10, this is exactly the same as multiplying DI by 2.

# The Limitations of Macro Arguments

There's another problem you will eventually run into if you're like most people. Given the macro header for Ruler:

```
@macro Ruler 5 ;VidAddress, Length, ScreenW,ScreenX,ScreenY
```

you might be tempted to write something like this:

```
mov   al,%5
imul  %3
```

No go! The assembler will call you out, complaining of an illegal immediate. What went wrong? You can freely use constructions like these:

```
mov   al,%5
add   di,%4
cmp   al,%2
```
