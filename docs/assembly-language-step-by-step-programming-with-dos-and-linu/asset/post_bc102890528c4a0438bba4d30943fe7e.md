To pull a 16-bit random number, call pull16. To pull an 8-bit random number, call pull8, and so on. The logic here should be easy to follow: Select a shift value, put it in ECX, push ECX on the stack, call rand, pop ECX from the stack, and shift the random number (which rand returns in EAX) by the value in CL—which, of course, is the lowest 8 bits of ECX.

Why does ECX go onto the stack? ECX is not one of the registers in the C calling conventions, and virtually all C library routines use ECX and trash it. If you want to keep a value in a cross to a library function, you have to save your value somewhere before the call, and restore it after the call is complete. The stack is the best place to do this.

I used the pull6 routine to pull random 6-bit numbers to select characters from a character table, thus creating a string of random characters. I padded the table to 64 elements with two additional characters (- and @ so that I wouldn't have to test each pulled number to see if it was less than 62. # Calls to Addresses in Registers

I use a technique in RANDTEST.ASM that sometimes gets forgotten by assembly newcomers: You can execute a CALL instruction to a subroutine address held in a register. You don't always have to use CALL with an immediate label. In other words, the following two CALL instructions are both completely legal and equivalent:

```
mov ebx, dword pull8
call pull8
call ebx
```

Why do this? You'll find your own reasons over time, but in general it allows you to treat subroutine calls as parameters. In RANDTEST.ASM, I factored out a lot of code into a subroutine called puller, and then called puller several times for different sizes of random number. I passed puller the address of the correct random-number subroutine to call by loading the address of that subroutine into EDI:

```
; Create and display an array of 8-bit random values:
mov edi, dword pull8 ; Copy address of random # subroutine into edi
call puller           ; Pull as many numbers as called for in [pulls]
```

Down in the puller subroutine, the code calls the requested random-number subroutine in this way:

```
puller:
    mov esi, dword [pulls] ; Put pull count into esi
.grab: dec esi          ; Decrement counter in esi
    call edi               ; Pull the value; it's returned in eax
    mov [stash+esi*4],eax ; Store random value in the array
    cmp esi,0              ; See if we've pulled enough yet
    jne .grab              ; Do another if esi < 0
    ret                    ; Otherwise, go home!
```

See the CALL EDI instruction! In this situation (where EDI was previously loaded with the address of subroutine pull8), what is called pull8—even though the label "pull8" is nowhere in subroutine puller. The same code in puller can be used to fill a buffer with all the different sizes of random numbers, by calling the subroutine address passed to it in EDI.

This technique was available in the 8086/8088, but was not often used in the older processors it was very slow. Since the 486, it's only slightly slower than calling an immediate label. Calling an address in a register gives you a lot of power to generalize code—just make sure you document what you're up to, since the label which you're calling is not contained in the CALL instruction.

# Local Labels

I haven't presented anything particularly long or complex programs in this book, so having problems with code labels conflicting with one another hasn't really been an issue. But as you begin to write "real" code for Linux, you will eventually be writing programs hundreds or even (with some practice and persistence) thousands of lines long. You will soon find that duplicate code labels will be a problem. How will you always remember that you already used the label loop on line 187 of a 1,432-line program?

You won't. And sooner or later, you'll try and use the label loop again. NASM will call you on it with an error.

This is a common enough problem (especially with obviously useful labels such as loop) NASM's authors created a feature to deal with it: local labels. Local labels are founded on the fact that nearly all labels in assembly work (outside of subroutines and major sections) are “local” in nature, by which I mean that they are only referenced by JMP instructions that—perhaps one or two instructions away. Labels are usually parts of tight loops and are not referenced from far away in the code.

Here's an example:

```
; Clear a buffer to nulls
Bufclr: mov ecx, BUFSIZE+5    ; Fill whole buffer plus 5 for safety
.loop:  dec ecx                   ; BUFSIZE is 1-based decrement first!
mov     [randchar+ecx],0        ; Mov null into the buffer
cmp     ecx,0                   ; Are we done yet?
nz     .loop                    ; If not, go back and pull another null
```

```
; Create a string of alphanumeric characters
Pulchr: mov ebx, BUFSIZE      ; BUFSIZE tells us how many chars to pull
.loop:  dec ebx                   ; BUFSIZE is 1-based, so decrement first!
mov     edi, dword pull6         ; For random in the range 0-63
call pull                    ; Get a random number from
mov     cl, [chartbl+eax]        ; Use name # as offset into table
                                 ; copy character from table into cl
```

```
mov [randchar+ecx],cl      ; Copy char from cl to character buffer
cmp     ecx,0                   ; Are we having fun yet?
nz     .loop                    ; If not, go back and pull another
```

You'll see that this code snippet the label loop has a period in front of it. This period marks it as a local label—and there are two labels here, each separate and distinguishable. Local labels are local to the first nonlocal (that is, the first label not prefixed by a period; we call this global) that precedes them in the code. In the preceding snippet, the first label .loop is local to the global label Bufclr. is not visible further up the source code past Bufclr, and once you get above Bufclr, there may be another local label called .loop, without any conflict with the two .loop labels.

Going down the source code from the global label Bufclr, the local label .loop is reference until the next global label, Pulchr, is encountered.

You'll see that Pulchr, there is another .loop, which does not conflict with the .loop that "belongs" to Bufclr. As long as a global label exists between the two of them, NASM has no trouble distinguishing them.

Some notes on local labels:

- In a library of subroutines, local labels are at least local to the subroutine in which they are defined. Each subroutine begins with a label (the name of the subroutine, which is a label), so a local label defined within a subroutine will at most be visible until the beginning of the next subroutine. You may, of course, have global labels within subroutines, which will confuse visibility of local labels even further.

- It's perfectly legal and often helpful to define global labels that are never referenced, simply to provide a context for local labels. If you're writing a utility program that executes in straight-through fashion without a lot of jumping or long-distance looping back, you may go a long way without needing to insert a global label. I like to use global labels to set off functional parts of a program, whether those labels are called or not. This allows me to use local labels freely within those major functional modules. As a stylistic convention, I mark such nonexistent global labels by using a capital letter for the first letter in the label. All labels meant to be referenced begin with lowercase letters. As a side benefit, these labels can be used as breakpoints when debugging with gdb.

- Local labels, unfortunately, are not accessible as breakpoints within gdb. I'm not entirely sure this is, but gdb will refuse to set a breakpoint on a local label.

- A rule of thumb that I use: Global labels and all references to them should occur within a single screen's worth of code. In other words, you should be able to see both a local label and everything that refers to it without scrolling your program editor. This is just a guide to help you keep sense in your programs, and I've found it very useful in my own work.

- If you're writing dense code with a lot of intermixed global and local labels, be careful that you don't try to JMP to a local label on the other side of a global label. This is one reason not to have 15 local labels called .loop within one part of a program—you can easily get them confused, and in trying to jump to one five instructions up, you may unknowingly be jumping to one seven instructions
