Lines like these tell us what files are required, but what must be
done with them. That's an essential part of the blueprint, and it's han-

together. Here's both lines for our simple example:

```
eatlinux: eatlinux.o
gcc eatlinux.o -o eatlinux
```

The second line is indented by custom. The first line tells us what file or files are
required to do the job. The second line tells us how the job is to be in:
this case, using gcc eatlinux.o into the executable file eatlinux.

Nice and neat: We specify which files are necessary and what has to be
done with them. The make mechanism, however, has one more very
important aspect: knowing whether the job as a whole actually has to be
done at all.

# When a File Is Up to Date

It may seem idiotic to have been done, and out so say, but once a file has
compiled or linked, it's been done, and it doesn't have to be done again
... until we modify one of the required source or object files. The
make utility knows this. It can tell when to compile or a task needs
to be done at all, and if the job doesn't have to be done, make will refuse
to do it.

How does make know if the job needs doing? Consider this dependency:

```
eatlinux: eatlinux.o
```

Make looks at this and understands that the executable file eatlinux
depends on the object file eatlinux.o, and that you can generate
eatlinux without having eatlinux.o. It also knows when both files were
last changed, and if the executable file eatlinux is newer than eatlinux.o,
it deduces that any changes made to eatlinux.o are already reflected in
eatlinux. (It can be absolutely sure of this because the only way to ge-
erate eatlinux is by processing eatlinux.o).
