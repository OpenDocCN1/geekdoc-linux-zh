Clear your calculator and let's get started:

+   1. Column 0 contains a 0; skip it.
2. Column 1 contains a 1. That means its value, 2, is present in the number. We punch 2 into the calculator.
3. Column 2 is 0. Skip it.
4. Column 3 contains a 1. The column's value is 23, or 8; add 8 to your tally.
5. Column 4 also contains a 1; 24 is 16, which we add to our tally.
6. Column 5 is 0. Skip it.
7. Column 6 contains a 1; 26 is 64, so add 64 to the tally.
8. Column 7 also contains a 1. Column 7's value is 27, or 128. Add 128 to the tally, and what do we have? That's the decimal value of 1101010B. It's as easy as that.

Converting from decimal to binary, while more difficult, is done exactly the same way as converting from decimal to hex. Go back and read that section again, searching for the general method used. In other words, see what was done and separate the essential principles from any references to a specific base like hex.

I'll bet by now you can figure it out without much trouble.

As a brief aside, perhaps you noticed I started counting columns from 0 rather than 1. A peculiarity of the computer field is that we always begin counting things from 0. Actually, to call it a peculiarity is unfair; the computer's method is the reasonable one, because 0 is a perfectly good number and should not be discriminated against. The rift occurred in our real, physical world, counting things tells us how many things are there, while in the computer world counting things is more generally done to name them. That is, we need to deal with number 0, and then number 1, and so on, far more than we know how many bits there are.

This is not a quib, by you. The issue will come up again and in connection with memory addresses, which I have said and will say again are the key to understanding assembly language.

In programming circles, always beginning counting from 0!
