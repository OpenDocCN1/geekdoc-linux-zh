
如果你将每个项目都限制在自己的目录，你就可以保留名为 "makefile" 的默认文件，而无需在每次重新构建项目时在 EMACS 中输入 make 文件的文件名。（而且由于目录中只有一个文件，你不必担心意外在错误的文件上调用它。我曾犯过错。如果你在这个问题上卡了壳，你很快就会怀疑自己的理智。）

这也允许你为测试文件、日志文件等使用标准名称，无论你在此时此刻正在处理其中的哪一个，这些名称都是相同的。如果所有文件都堆在一个巨大的目录里，你就必须记住一整套独特的名称，每个项目一个。何必费此精力呢？目录占用的磁盘空间很少，但在管理复杂性方面起着极其巨大的作用。

## 考虑 EMACS 主页

编程所需的所有各种步骤都可以直接在 EMACS 内部完成。你可以编辑源代码和 make 文件。你可以汇编译文件并将其链接以生成可执行文件。你可以运行可执行程序文件进行测试。你可以调用 GNU 调试器。你可以执行从像 bash 之类的 shell 内部发出的几乎任何 Unix 命令。为什么要花时间在 EMACS 之外像对待普通的文本编辑器一样反复进出呢？

关于 EMACS 的书已经不止一本。我推荐 Debra Cameron、Bill Rosenblatt 和 Eric S. Raymond 写的书籍《Learning GNU EMACS》（O'Reilly, 1996）。我唯一的抱怨是，它没有专门介绍 X Window 版本的 EMACS，但所有核心命令都是相同的。我不想重复该书中很多精彩的内容，而且 EMACS 在编辑方面是非常直观的。

关于 EMACS，需要理解的重要大观观点是，它是基于缓冲区（buffer）的，这些缓冲区可能与磁盘文件相关，也可能仅包含来自非磁盘文件的文本。当你打开一个文件时，EMACS 会打开一个缓冲区并将打开的文件加载到该缓冲区中。你也可以打开一个作为临时缓冲区（scratch buffer），在其中输入内容，将其部分剪切或复制到另一个缓冲区，然后直接杀死这个临时缓冲区（删除它）而不将其保存到磁盘。（EMACS 有专门的菜单项来杀掉缓冲区。）

当 EMACS 运行 makeset时，它会将 make 的输出以及 make 调用的工具的输出管道到一个新缓冲区。该缓冲区与任何其他 EMACS 缓冲区相同，如果你愿意，可以给缓冲区命名并保存到磁盘文件，作为 make 会话的记录。

在 EMACS 内部调用 GNU 调试器时也是同样的：gdb 的输出被管道到一个缓冲区，如果你选择这样做，可以将其保存到磁盘以便日后参考。

最重要的是，你可以从 EMACS 内部调用 Unix shell（我使用 bash），EMACS 将将其输出管道到一个新缓冲区，该缓冲区可以像缓冲区一样保存到磁盘。特别是在你学习期间，你几乎不需要任何操作是无法通过 EMACS 菜单或从 EMACS 内部打开的 shell 来完成的。

## 在 EMACS 内部打开 Shell

这同样值得解释，因为它比大多数编辑命令都不那么直观。目前 EMACS 没有在窗口中打开 shell 的菜单项。（本应该有的的！）要打开 shell，命令是 "Esc-x shell"。你先按 Esc 键，然后按小写的 x 键（不要同时按！），在窗口底部的命令行中，EMACS 将显示毫无帮助的字符串 "M-x"。这是它在 PC 上表示序列 x 的方式。（M 代表 "Meta"，这是某些古老且被人们刻意遗忘的哑终端上一个控制键的名称。）在可能缺少 Esc 键的其他计算机或终端上，可能有其他启动命令的方法。EMACS 的编写是为了可移植性。在字符串 "M-x" 之后，你必须输入 "shell" 并按回车。

EMACS 会在窗口中打开一个新的缓冲区，并开始将默认 shell 的 shell 输出管道到该窗口。窗口顶部将是你熟悉的 shell 提示符，等待你输入 shell 可执行文件，就像你在调用 EMACS 之前做的一样。你可以像在 shell 中执行那样，通过命名（通常前缀为 "./"）来调用你构建的可执行文件。

注意，你可以输入 "exit" 退出 shell，但窗口不会关闭。要关闭窗口，你可以使用 C-x C-frame。

## 第 13 章

## 为 Linux 编程

## 将你所学的知识应用于真正的模式操作系统

本章补充了 Linux 工作原理与 DOS 之间区别的本质内容。如果有一天这本书真的出了第三版（我希望会有），我正在考虑几乎完全地重写它。

在上一章中，我已经说得很清楚，Linux 从上到下都是一个 C 的世界。有些人认为，这意味着大多数 Linux 程序是用 C 语言编写的，创建 Linux 的人是 C 语言专家——事实如此——但还不仅如此。C 是为了 Unix 创建的，而 Unix 也是用 C 语言创建的。它们共同进化，并给彼此留下了不可灭的印记。即使 Linux 或其他种类的 Unix 用 Pascal 重新实现（在我看来这是一个非常好的主意），C 的风格仍然会存在，而且必须存在，否则我们所拥有的将根本不是 Unix 了。

### 库的主导地位

并不是所有的 C 文化都与汇编语言工作相关，但很大一部分是相关的。讽刺的是，对汇编工作影响最大的部分是标准 C 库的主导地位。Linux 和标准 C 库是不可分割的。库是应用程序和工具与 Linux 内核通信的方式。它们取代了我在早期章节中解释的 DOS INT21H 接口。

这基本上有三个原因：

- 可移植性。这不像以前那么重要了，对于我们这些认为 CPU 战争早已早已被英特尔获胜的人来说，它可能完全重要。但事实是，标准 C 库的创建是为了让 Unix 移植到其他处理器变得更容易。
- 复杂性管理。Linux 的复杂性至少比 DOS 高出一个数量级。它可以做更多事情，并且（得益于这种复杂性）以更强的健壮性和活性完成任务。许多复杂性可以对典型的终端用户工具和应用程序隐藏起来，而 C 库是实现这种隐藏最重要的手段。
