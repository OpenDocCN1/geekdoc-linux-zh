# New Features

The toolset is basically identical with the HPL 2.0 distribution. There are a few changes that are optionally compiled and disabled until you specifically request them. These new features are:

ASYOUGO: Provides non-intrusive performance information while runs proceed. There are only a few outputs and this does not impact performance. This is especially useful because many runs can go hours without any information.

ASYOUGO2: Provides slightly intrusive additional performance information because it intercepts until DGEMM.

ASYOUGO2_DISPLAY: Displays the performance of all the significant DGEMMs inside the run.

ENDEARLY: Displays a few performance hints and terminates the run early.

FASTSWAP: Inserts the LAPACK-optimized DLASWP into HPL’s code. This may yield a benefit for Itanium® 2 processor. You can experiment with this to determine best results.

HYBRID: Establishes the Hybrid OpenMP/MPI mode of MP LINPACK, providing the possibility to use threaded Intel MKL and prebuilt MP LINPACK hybrid libraries.

> WARNING. Use this option only with an Intel compiler and the Intel® MPI library version 3.1 or higher. You are also recommended to use the compiler version 10.0 or higher.

# Benchmarking a Cluster

To benchmark a cluster, follow the sequence of steps below (some of them are optional). Pay attention to the iterative steps 3 and 4. They make a loop that searches for HPL parameters (specified in HPL.dat) that enable you to reach the top performance of your cluster.

- 1. Install HPL and make sure HPL is functional on all nodes.

- 2. You may run nodeperf.c (included in the distribution) to see the performance of DGEMM on all nodes.

```
Compile nodeperf.c with your MPI and Intel MKL. For example:
mppiacc -o3 nodeperf.c -LMKLPATH $MKLPATH/libmkl_intel_lp64.a \ 
-W1,--start-group $MKLPATH/libmkl_sequential.a \ 
$MKLPATH/libmkl_core.a -W1,--end-group -lpthread
```

Launching nodeperf.c on all nodes is especially important in very large cluster.
Indeed, there may be a stray job on a certain node, for example, 738, which is running 5% slower than the rest. LINPACK will then run as slow as the slowest node. In this case, nodeperf enables quick identification of the potential problem spot without numerous small MP LINPACK runs around the cluster in search of the bad node. It may be zombie processes common after a bunch of HPL runs, there nodeperf facilitates finding the slow nodes. It goes through all the nodes, one at a time, and reports the performance of DGEMM followed by some host identifier. Therefore, the higher the DGEMM performance, the faster that node was performing.

- 3. Edit HPL.dat to fit your cluster needs.
Read through the HPL documentation for these ideas. However, you should try on at least 4 nodes.

- 4. Make an HPL run, using compile options such as ASYOUGO or ASYOUGO2 and ENDEARLY to aid in your search (These options enable you to gain insight into the performance sooner than HPL would normally give this insight).

# LINPACK and MP LINPACK Benchmarks

- Use MP LINPACK, which is a patched version of HPL, to save time in the search.

Using a patched version of HPL should not hinder your performance. That's why features that could be performance intrusive are compile-optional (and it is explained below) in MP LINPACK. That is, if you do not use the new options explained in Options to Reduce Search Times, then these changes are disabled. The primary purpose of the additions is to assist you in finding solutions.

HPL requires a long time to search for many parameters. In the MP LINPACK, the goal is to get the best possible number.

Given that the input is not fixed, there is a large parameter space you must search over. In an exhaustive search of all possible inputs is probably even large for a powerful cluster.

This patched version of HPL only improves performance as it proceeds, or terminates early depending on your desires.

Save time by compiling with -DENDERALLY-DASYOUGO2 (described in Options to Reduce Search Time) and using a negative threshold (do not use a negative threshold on the final run that you intend to submit as a Top500 entry). You can set the threshold in line 13 of HPL 2.0 input file.
If you are running problem to completion, do it with -ASYOUGO (see Options to Reduce Search Time).

- Using the quick performance feedback, return to step 3 and update until you are sure that the performance is as good as possible.

# Options to Reduce Search Time

Running huge problems to completion on large numbers of nodes can take many hours. The search for MP LINPACK is huge: not only can you run any size, but over block sizes, grid layouts, lookahead steps, using different factorization methods, etc. It can be a large waste of time to run huge problem to completion only to discover it 0.01% slower than your previous best. There are 3 options Use -ASYOUGO2 cautiously because it does have a marginal impact. To see DGEMM internal performance, compile with -ASYOUGO and -ASYOUGO2_DISPLAY. These options provide a lot of useful DGEMM information at the cost of around 0.2% loss. If you want to use the old HPL, simply omit these options and recompile from scratch (try "make clean_all").
