## Reconstructing the Subject File System Structure (Linux)

Going back to our able_3 case raw images, we now have the original image along with the partitions that we carved out (plus the original split images).

- able_3.part1.raw (1st Partition)
- able_3.part2.raw (2nd Partition)
- able_3.part3.raw (3rd Partition)

One of the benefits of Linux/Unix is the ability to separate the file system across partitions. This can be done for any number of reasons, allowing for flexibility where there are concerns about disk space or security.

For example, a system administrator may decide to keep the /var/log on its own partition. This might be done in an attempt to prevent rampant log files from filling the root (/) partition and bringing the system down. Several years later, finding the /boot directory in its own partition was common as well. This allows the kernel image to be placed near the "front" (in terms of cylinders) of a boot volume, an issue in some older loader boots. There are also a variety of security implications addressed by this setup.

So when you have a disk with multiple partitions, how do you find out the structure of the file system? Earlier in this paper we discussed the /etc/fstab file. This file maintains the information for each file system, including the partition; mount point, file system type, and options. Once we find this file, reconstructing the system is easy. With experience, you will start to get a feel for how partitions are set up, and where to look for the fstab. To make things simple, just mount each partition (loop, read only) and have a look around.

One thing we might like to know what sort of file system is each partition before we try and mount them. We can use the file command to do this²⁴. Remember from our earlier exercise that the file command determines the type of file by looking for "header" information.

²⁴ Keep in mind that the file command relies on the magic file to determine the file type. If this command does not work for you in the following, then it is most likely because the magic file on your system does not include headers for file system types.

Previously, we were able to determine that the partitions were "Linux" partitions from the output of dfdisk. Now file informs us that the file system type is ext4⁵. We can use this information to manage the partitions. Remember that you will need to root to mount the partitions, so to root first, mount and mount each partition, until you find the /etc directory containing the fstab:

```
barry@forensic1:~$ su -
Password:
root@forensic1:~# mount -t ext4 -o ro,loop ~berry/able_3/able_3.part1 /mnt/evid

If you do this for each partition in turn (either unmounting between partitions, mounting to a different mount point), you will eventually find the /etc directory containing the fstab file in able_3.part3.raw with the following important entries:

```
barry@forensic1:~/able_3$ cat /mnt/evid/etc/fstab
/dev/sda3      /ext4      defaults 1 1
/dev/sda1      /boot     ext4      defaults 1 2
/dev/sda2      /home     ext4      defaults 1 2
```

Now we see that the logical file system was constructed from three separate partitions (note that /dev/sda here refers to the disk when it is mounted in the original system):

Now we can create the original file system at our evidence mount point. Mount point /mnt/evid already exists. When you mount the root partition of able_3.raw on /mnt/evid, you will note that the directories /mnt/evid/boot and /mnt/evid/home already exist, but are empty. That is because we have to mount those partitions to access the contents of those directories. We mount the root file system first, and the others are mounted to that. Again, we must be root for this:

```
root@forensic1:~# mount -t ext4 -o ro,loop ~baby/able_3/able_3.part3.raw /mnt/evid
```

```
root@forensic1:~# mount -t ext4 -o ro,loop ~baby/able_3/able_3.part1.raw /mnt/evid/boot
```

```
root@forensic1:~# mount -t ext4 -o ro,loop ~baby/able_3/able_3.part2.raw /mnt/evid/home
```

We have now recreated the original file system:

```
barry@forensic1:~$ mount | grep evid
