While the access count at 0x04 is easy to decipher, the Windows date value is not. I use a small python script to decode the time value (the number of 100 nanosecond blocks since January 1, 2001). You can download the python script (winTime) using wget:

```
barry@forensic1:~.../Count/(values)$ wget http://www.linuxleo.com/Files/WinTime -O ~/WinTime.py
```

Since we are currently in the ntermount point, it is best to use the wget -O option to write the file to your home directory (~WinTime.py). You don't want to try and download the file to the current directory (it's our fused registry mount point).

Once you have the script, you can copy the hex value and provide it as an argument to WinTime.py. Be sure to remove the spaces from the value (we'll use an alternative way of getting this value from xxd later):

```
barry@forensic1:~.../Count/(values)$ python ~WinTime.py c03ac030f8bed201
Thu Apr 27 01:45:57 2017
```

If you did a full install of Slack, Python should already be on your system. Note the python commands points to the WinTime.py we previously named with wget -O - indicates the file is in our home directory. This leaves us with a last execution time of April 27 at approximately 01:45. A complete forensic education regarding registry entries, interpreting dates and timezone adjustment is far outside the scope of this guide, but make sure you take time settings, time zones and clock skew into account for any forensic examination where dates are meaningful. Read file dates and time stamps are one of the pitfalls of an amateur analysis. Read up on the subject complexity before making any interpretations.

Speaking of times, and how would we be finding the last write time of the UserAssist sub key itself? We've been looking at and decoding key values, but the last write time of a key is more akin to a property of the key itself. The registry file mount through refmount, the keys and sub-keys act as directories. If you run the ls -l command, you can see a date associated with the keys. Changes up to your script working directory /ntermount/Software/Microsoft/Windows/CurrentVersion/Explorer/. This would be four levels, or to the parent directory [..] times. Then run ls -l:

```
barry@forensic1:/ntermount/Software/Microsoft/Windows/CurrentVersion/Explorer/UserAssist/{F4E7C4B-2036-45F0-A9AB-443BCE33D9F}/Count/(values)$ cd ../..
$ ls -l
total 0
d-xr-xr-x 2 barry users 0 May 1 12:39 (values)/
```

```
dr-xr-xr-x 2 barry users @ Apr 30 15:45 Advanced/
d-xr-xr-x 2 barry users @ Apr 5 21:39 ApplicationDestinations/
...
d-xr-xr-x 2 barry users @ Apr 5 21:39 TypedPaths/
d-xr-xr-x 2 barry users @ Apr 5 21:35 User\Shell\
d-xr-xr-x 2 barry users @ Apr 5 21:36 UserAssist/
...
```

The time for the UserAssist "directory" is Apr 5 21:36. A more precise time can be shown with the stat command run on the directory:

```
$ barry@forensic1:~/ntermount/Software/Microsoft/Windows/CurrentVersion/Explorer
File: UserAssist/
Size: 0 Blocks: 0 IO Block: 4096 directory
Device: 25h/3d Inode: 0 Links: 2
Access: (0555/dr-xr-xr-x) Uid: ( 1000/ barry) Gid: ( 100/ users)
Access: 2017-04-05 21:36:50.0000000000 -0400
Modify: 2017-04-05 21:36:50.0000000000 -0400
Change: 2017-04-05 21:36:50.0000000000 -0400
Birth:
```

Here we get the more precise time of 2017-04-05 21:36:50.0000000000 -0400. Make particular note of the fact that the time zone is -0400. Because this is running within fuse, the times are shown in the host system time. The rest of the information is also largely useless as it is not really associated with the original source data. What we shown here is the last write time of the UserAssist key is 2017-04-05 21:36:50.0000000000 -0400. If we add four hours to the output, we get 2017-04-06 01:36:50.0000000000 UTC.

## Registry Parsing 2 – SAM and Accounts

Let's look at another registry file, the SAM. The SAM hive can have a great deal of information available if there are local accounts on the system. Again, we're not going to go through comprehensive analysis, we're just going to have look at a few values of the most important keys. We can get the SAM hive using the NTUSER.DAT, first searching for MFT entry using ls and then using icat to extract the file:

```
barry@forensic1:$ ls -F -278 NTFS_Pract_2017.E01 | grep Windows/System32/config/SAM
```

So our target MFT entry here is 178. Now we'll extract with icat and check the file type with the file command. The name we use on the extracted file is arbitrary. Consistency is a good idea, though we'll create mount point for the SAM and use regount to fuse the hive.

```
barry@forensic1~$ mkdir sammnt
barry@forensic1~$ regount NTFS_Pract_2017.E01 sammnt/
```

Since we already pulled the NTUSER.DAT file, let's look at the same account in the SAM file. If we change directories down to SAM/Account/Users, we will see the list of potential accounts:

```
barry@forensic1~/sammnt/SAM/Domains/Account/Users$ ls
000001F4/ 000001F5/ 000003E8/ 000003E9/ Names/
```

What we see in the output above are a series of sub keys (starting with 0000*) that represent the hex value of account ID. We can translate these with bc as we would have index. But let's do all at once for a loop to repeat the command across all the directories (but only those that are hex value):

```
barry@forensic1:~/sammnt/SAM/Domains/Account/Users$ for name in 0000*
> do
> echo "ibase=16;$name" | bc
> done
```

If you read up on Windows accounts, you'll see the system administrator (RID 500), the guest account (RID 501), and a pair of user accounts (1000 and 1001). There are a number of ways to associate the accounts with particular users, but we will simply navigate to the values under the 000003E8 sub key. We have three "files" to look at. A very quick peek at the bottom of the file shows the username associated with this account:

```
barry@forensic1~/sammnt/SAM/Domains/Account/Users/000003E8/(values)$ xxd
00000160: 0000 0001 0000 0102 0000 0000 0005
00000170: 2000 0000 2002 0000 0102 0000 0005
00000180: 2000 0000 2002 0000 4100 6200 6250 ... ...A.l.b.e.
00000190: 0200 7200 7450 0400 0102 0000 0780 ... ...r.t.e.
000001a0: 0300 0100 0300 0100 13c4 df66 671a 78d2 ... .og.p.
000001b0: 0300 0100 0300 0100 13c4 df66 671a 78d2 ... .n.
000001c0: 0000 0001 0000 0102 0000 0000 0005
000001d0: 2000 0000 2002 0000 0102 0000 0005
000001e0: 2000 0000 2002 0000 4100 6200 6250 ... ...A.l.b.e.
000001f0: 0200 7200 7450 0400 0102 0000 0780 ... ...r.t.e.
```

The highlighted text shows the account associated as Albert. The PasswordHint is fairly obvious. Unlike the UserAssist files, the SAM does not display any obvious data. Let's look at what happens when we run xxd with -ps (plain hexdump) -s8 (seek to byte 8):

```
barry@forensic1~/sammnt/SAM/Domains/Account/Users/000003E8/(values)$ xxd -ps -s8 -l8 F
678e5df77c1d21
```

We find the date extracted is exactly the format we need to pass to WinTime.py. To order the output, we'll use command substitution. This is done by using the back-tick (` `) symbols around the xxd command. This substitutes the output of xxd straight to the argument required for WinTime.py:

```
barry@forensic1~/sammnt/SAM/Domains/Account/Users/000003E8/(values)$ python ~/WinTime.py `xxd -ps -s8 -l8 F`
Sun Apr 30 21:23:09 2017
```

This can be taken step further. We have three separate date values to convert here. One is offset 8 (-s8 as we converted). The others are at offset 24 and 40. Sounds like a perfect candidate for our familiar bash for loop. We can use offsets 8, 24 and 40 as our variable, and pass those into our command substitution for WinTime.py. It should look something like this:

```
barry@forensic1:~/sammnt/SAM/Domains/Account/Users/(values)$ for offset 8 24 40
> do
> python ~/WinTime.py `xxd -ps -s$offset -l8 F`
> done
Sun Apr 30 21:23:09 2017
Thu Apr 6 01:35:34 2017
Sun Apr 30 21:23:01 2017
```

- Last Login: offset 8
- Password Set Date: offset 24
- Failed Login: offset 40
