We will run fdupes twice (always good practice). The first run will show all the duplicated files, each pair on a single line. Review the output to ensure there are no unexpected files, and then re-run the command with the --delete option.

```
barry@forensic1:~/carve$ fdupes -R photorec_out.1/ scalp_out2/
scalp_out2/00000000.jpg photorec_out.1/f0012156.gif
scalp_out2/00000003.jpg photorec_out.1/f0012206.jpg
scalp_out2/00000004.jpg photorec_out.1/f0012262.jpg
```

The options we use - -R for recursion. There are no sub folders in this example, but it never hurts to allow recursion. Particularly on large scale examinations we carve output in particular (different file types in different directories). We also use the -1 option to put matches on the same line. This is personal preference. Run without this option and you may see what you prefer.

Once the output has been reviewed, re-run the command with the --delete option to keep only the first file in each pair (or set). If you reviewed the output to delete, then you might want to add the -N option for "no prompt". Use at your own discretion. Without -N, if you have hundreds of pairs of matching files, you will need to confirm each deletion.

```
barry@forensic1:~/carve$ fdupes -R -N --delete photorec_out.1/ scalp_out2/
```

[+] scalp_out2/00000000.jpg
[-] photorec_out.1/f0012156.gif

[+] scalp_out2/00000003.jpg
[-] photorec_out.1/f0012206.jpg

[+] scalp_out2/00000004.jpg
[-] photorec_out.1/f0012262.jpg

The output above indicates that the first file has been kept [+] the second file deleted [-]. If there were more than one matching file in each set, then only the first one would remain. To better control this behavior, remove the -N option and you can select which files to keep. This concludes our carving section. We've learned how to carve files from unallocated space, view the files, and remove duplicates in an efficient manner.

## Application Analysis

We've now covered several of the layers discussed previously, including physical layers for disk information and partition layout; file system tools for gathering information; and to work on individual files to identify type of interest. We've even done data recovery at the physical layer – regardless of volume and file system. So now that we have recovered files, what we do with them?

This is where the Application Layer of our analysis comes. For our purposes here, the term "application" can be thought of as files created by the operating system or through user interaction (either with the operating system or external software).

In simple terms, application analysis can be as simple as viewing the file directly – we use **cat** and **grep** for text files, various image viewers like **feview** and **display** for pictures, and simple text viewers like **less** for ASCII files. Forensic analysis is much more than simply recovering and displaying the content. Digital forensics, however, needs to include other techniques:

- temporal analysis (when did it happen?)
- attribution (who made it?)
- activity mapping (how did it happen?)

Obviously we can get some of this information through the analysis we've done already, using **stat** for the location of files in a particular user's home directory. In order to dig a little deeper, we are going to look at some simple applications that will allow us to peer into the Windows Registry, Event logs, and other artifacts to obtain forensically useful information. We will be using these tools from the sleuth project.

You can read more about sleuth at https://github.com/sleuthkit/wiki. There are a couple of important notes on these libraries before we begin. First and foremost, make sure you understand that many of these libraries are in *alpha* or *experimental* status, meaning they are not fully matured, and as above clearly states, are subject to break or change. The projects we will look at are in alpha status. They have been tested with some sample files, but make sure that you test them in your own environment prior to use. These are excellent projects, and worth keeping up, but make sure you know what you are doing before using them in production. Using software that is clearly marked *alpha* or *experimental* is not recommended for production case unless you understand and test the output for yourself.

## Registry Parsing #1 - UserAssist

Let's start our exploration of application analysis by looking at specific Windows registry files. 

As usual, we start with the disclaimer that this section is not about learning registry forensics. It's about the tools. Of course you might gain some knowledge along the way, but if you want to go deeper into these registry files and learn more about the art of registry forensics, I strongly suggest you look to the excellent book by Harlan Carver (and browse his blog!). You might want to have a basic understanding of registry structure before you begin this exercise, so you have some context for what's to come. And of course there are other (faster and more comprehensive) ways to parse. For example, Harlan Carver's well-known RegRipper will run just fine on Linux.

Our real purpose in this section is to show you how to do this analysis at the byte level, using some Linux tools like xxd and tr, rather than relying on automated tools to do it for you. What we do here is not much different from what the Perl scripts in RegRipper do (although we simplify it somewhat).

First, we need to have a registry file to work on. We'll start with the NTUSER.DAT file from the Albert account in our NTFS file system (NTFS_Pract_2017.E01).

We need to make sure we obtain the correct NTUSER.DAT. There are a couple of ways we can locate and extract the file from a disk image. You can mount the image (in our case using mount), browse to the file and copying it out of the mounted file system. This requires a few more steps than we need to do, so we'll demonstrate it here with two simple location methods, and then extract the file with icat.

Since we are the Albert account, and we know that a specific user's NTUSER.DAT file is in the /Users/$USERNAME/ folder, we can use find to target the specific file by name. To run find, we use mmls as we did previously to find the offset to the file system in our image:
