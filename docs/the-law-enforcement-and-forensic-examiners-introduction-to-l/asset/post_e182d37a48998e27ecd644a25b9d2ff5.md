Remember that the mount command works on file systems, not disks. The file system in this image starts 2048 sectors into the image, so we use mount using an offset. Since we are also examining an EWF image, we'll need to use ewmount to fuse the image file. This all must be done as:

Back to our problem... To see why jet.jpg is missing, let's try another method of obtaining a file, the **fls** command. We can use the -f option to look only at directories, and -r to do it recursively. We'll also **grep** for jet.jpg. You could use the MFT record numbers to download the file, which is quicker and more efficient:

```
barry@forensic1:/NTFS_Pract_2017$ fls -o 2048 NTFS_Pract_2017.E01 | grep jet.jpg
39-128: Users/AlbertE/Pictures/jet.jpg
39-128: Users/AlbertE/Pictures/jet.jpg:unix.txt
```

In the output of **fls**, jet.jpg has two entries (39-128/39-128). Both entries have the same MFT record number but the attribute identifiers are different. This is an example of Alternate Data Stream (ADS). Accessing the standard contents (39-128) of jet.jpg is easy, since it is an allocated file. However, we can access either data stream, the normal data or the ADS, by using the Sleuth Kit **icat**, much as we did with the files in our exercises. We simply call icat with the complete MFT record entry to include the alternate identifier. Here we specify each of the data streams and send them to the **file** command using icat:

```
barry@forensic1:/NTFS_Pract_2017$ icat -o 2048 NTFS_Pract_2017.E01 39 | file -dev/stdin: MPEG sequence, v1, progressive Y'CbCr 4:2:0 video, CIF NTSC, NTFS 4:3, 29.97 fps, Constrained
```

In this first (default) stream, we simply use the MFT record 39 to pass the default data to file. For the second stream, we pass the full attribute (39-128):

```
barry@forensic1:/NTFS_Pract_2017$ icat -o 2048 NTFS_Pract_2017.E01 39-128 | file -dev/stdin: ASCII text, with CRLF terminators
```

This time we see it is ASCII text. Now we can just pipe the same to less (or just straight to STDOUT) to view:

```
barry@forensic1:~/NTFS_Pract_2017$ icat -o 2048 NTFS_Pract_2017.E01 39-128 | less
```

# Sleuth Kit Exercise #6 – Physical String Search & Allocation Status (NTFS)

We've already done a few string searches, all of them have been on EXT file systems. We make a lot of assumptions when we search for strings in an image. We assume the strings are accessible (not in a container that requires pre-processing), and we assume they will be in a character encoding that our search utility will find. This is not always the case. Most of the string searches we've done so far have resulted in matches that are found in regular ASCII text files. When we search for strings on Windows systems, for example, that won't always be the case. We'll need to deal with compressed and encoded formats, and additional application overhead and considerations, like compressed.

This exercise still simplifies that of, but it also serves to make you aware of some of the more complex issues that may arise when searching larger images with more complex content. It will also introduce you to some basic application file viewers.
