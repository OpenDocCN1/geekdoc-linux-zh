# Kernel Modules

As mentioned previously, the kernel provides the most basic interface between hardware and the system software and resource management. This includes drivers and other components that are actually small pieces of code that can be compiled as modules (loaded or unloaded dynamically) or compiled directly in the kernel image.

There may come a time when the kernel is less than an ideal module for a specific piece of hardware, perhaps causing it to fail to work, or in some cases work at less optimal performance. Wireless network cards can be a common example.

On one laptop, for the output (abbreviated) for the network interfaces, using lspci, might look like this:

```
root@forensic1:~# lspci | less
```

# Hotplug devices and Udev

Starting with kernel version 2.6.13, Linux device management was handed over to a new system called Udev. Traditionally, the device nodes (representing the devices, located in the /dev directory) using previous kernels were static, and that exists all times, whether in use or not. For example, on a system with static device nodes we may have a primary SATA hard drive that is detected by the kernel as /dev/sda. Since we have no IDE devices, no drive is detected as /dev/hda. But when we look in the /dev directory we use static nodes for all possible disk and partition names for /dev/hda. The device nodes exists whether or not the device is detected. In modern Linux systems, Udev creates device nodes "on the fly". The nodes are created as the kernel detects the device and the /dev directory is populated in real time. In addition to being more efficient, Udev also runs in user space. One of the benefits of Udev is that it provides "persistent mapping". In other words, you can write a set of rules that will allow Udev to recognize a device based on individual characteristics (serial number, manufacturer, model, etc.). The rule can be used to create a user-defined link in the /dev directory, so for example, my thumb drive can always be accessed through an arbitrary device name of my choice, like /dev/my-thumb, if so choose. This means I don't have to search through USB device nodes to find the correct device name if I have more than one external device connected. I can connect 4 USB devices and instead of searching through /dev/sdc, sdd, sde, and sdf - I just go to /dev/my-thumb. http://activated.net/udev_rules.html

On Slackware, Udev runs as a daemon from the startup script /etc/rc.d/rc.udev. We will discuss these startup scripts in more detail in this document. We will not do any specific configuration for Udev on our forensic computers at this time. We will discuss it simply because it plays a major part in device handling and also is of interest to forensic examiners who want to know what their system is doing. Udev does not involve itself in mounting or otherwise interacting with applications. It provides a hardware to kernel interface.

# Hot Plugging Devices and Desktops

One of the considerations when discussing Desktop Environments is whether or not the system will allow for desktop auto-mounting of removable media. KDE and GNOME are designed for a simple user experience and examiners need to be aware of how to control undesired behavior in a forensic environment. Once you've installed your system of choice, make sure you test what happens when "hot plug" a USB or other removable media device. XFCE is a lighter (read: lighter on resources) desktop. And although XFCE is also capable of automatically hot plugged devices, which allows for easier control of removable media on the desktop. By default, devices are NOT mounted in the XFCE environment.
