
## v4.33 A Comprehensive Beginner's Guide to Linux as a Digital Forensic Platform

Now we know the offset to the keyword within the actual volume, rather than the entire image. Let's find out what inode (meta-data unit) points to the volume data block at that offset. To find which inode this belongs to, we have to calculate the volume block address. Look the Sleuth Kit's fsstat output to see the number of bytes per block. We need to run fsstat on the file system at sector offset 10260.

```bash
barry@forensici:~/able2$ fsstat -o 10260 able2.dd
FILE SYSTEM INFORMATION
File System Type: Ext2

...
CONTENT INFORMATION
Block Range: 0 - 51299
Block Size: 1024
...
```

The abbreviated fsstat output shows us (highlighted in bold) that the data blocks within the volume are 1024 bytes each. If we divide the volume offset by 1024, we identify the data block that holds the keyword.

```bash
barry@forensici:~/able2$ echo "5308483/1024" | bc
5184
```

Able2.dd (entire image)

| 0 | 1 | 2 | 3 |
|---|---|---|---|
| ... 5184 | | vol. offset/vol. block size=val. block address (5308483/1024 = 5184) | |
| | Keyword Hit | | |

fsstat output shows each volume data block = 1024 blocks. Here are our calculations, summarized:

- offset to the string in the disk image (from our grep output): 10561603
- offset to the partition that contains the file: 10260 sectors * 512 bytes per sector
- offset to the string in the partition is the difference between the two above
- the data block is the offset in the file system divided by the block size (data unit size) 1024, from our fsstat output.

In short, calculation, taking into account all the illustrations, is simply:

```bash
barry@forensic1:-:/able2$ echo "(10561603-(10260*512))/1024" | bc
5184
```

Able2.dd (entire image)

![](img/993644c785d68ca888a5ade02ca8088d_230_0.png)

Note that we use groupings to group our calculations. We find the offset to the file system (10260*512), subtract that from the offset to the string (10561603) and then divide the whole thing by the data unit size (1024) obtained from fsstat. This (5184) is our data unit (not the inode!) that contains the string we found with **grep**. Very quickly, we can ascertain its allocation status using the Sleuth Kit command **blkstat:**:

```bash
barry@forensic1:-:/able2$ blkstat -o 10260 able2.dd 5184
Fragment: 5184
Not Allocated
Group: 0
```

The command **blkstat** takes a data block from a file system and tells us what it can about its status and where it belongs. We'll cover the **TSK blk** tools in more detail later. So in this case, **blkstat** tells us which word search for the string cybernetic resulted in a match in an unallocated block. Now we use **find** to tell us which inode (meta-data structure) points to data block 5184 in the second partition of our image:

```bash
barry@forensic1:-:/able2$ find -o 10260 -d 5184 able2.dd
10090
```

Excellent! The inode that holds the keyword match is 10090. Now we use **istat** to get the statistics of that inode:

```bash
barry@forensic1:~/able$ istat -o 10260 able2.dd 10090

Not Allocated
Group: 5
Generation Id: 3534950782
uid | gid: 4 / 7
mode: rw-r---
size: 3591
num links: 0
```

From the istat output we see that inode 10090 is unallocated (same as **blkstat** told us about the data unit). Note also that the first direct block indicated by our istat output is 5184, just as we calculated.

We can get the data from the direct blocks of the original file using less -r. Pipe the output through less so that we can read it easier. Note that our keyword is right there at the top:

```bash
barry@forensic1:~/$ icat -o 10260 able2.dd 10090 | less
/*

```

At this point, we have recovered the data we were looking for. We can run our icat command as above again, directing the output to a file (as we did with the rootkit file from our previous recovery exercise). We'll do that for possible later reference:

```bash
barry@forensic:~/able2$ icat -o 10260 able2.bd 10090 > 10090.recover
```
