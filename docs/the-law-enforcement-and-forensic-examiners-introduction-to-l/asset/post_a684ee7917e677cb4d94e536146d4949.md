
v.4.33 A Comprehensive Beginner's Guide to Linux as a Digital Forensic Platform

ddrescue is installed by default in Slack Linux (for full installations), but check your distribution of choice to determine availability.

The documentation for ddrescue is excellent. The detailed manual is in an info page. The command info ddrescue will give you a great start to understanding how this program works, including examples and the ideas behind the algorithm used. I'll run through the process here, but I strongly advise you to read the info page for ddrescue before attempting to use it on a case.

The first consideration when using any recovery strategy, is that the disk must be accessible by the Linux kernel. If the drive does not show up in the /dev structure, then there's no way to get tools like ddrescue to work.

Next, we have to make a plan to recover as much data as we can from a bad drive. The prevailing philosophy of ddrescue is that we should attempt to get all the data first. This differs from normal dd tools, which simply attempt to get all the data at one time in linear fashion. ddrescue uses the concept of "splitting the errors". In other words, when an area of bad sectors is encountered, the errors are split until the "good" areas are properly imaged and the unreadable areas marked as bad. Finally, ddrescue attempts to retry the bad areas by re-reading them until we get data or fail after a certain number of specified attempts.

There are a number of ingenious options to ddrescue that allow the user to try and obtain the most important part of the disk first, then move on until much of the disk is obtained possible. Areas that are imaged successfully need not be read more once. As mentioned previously, this is made possible by a robust map file. The map file is written periodically during the imaging process, so that in the event of any interruption, the session can be restarted, keeping duplicate imaging efforts, and therefore disk access, to minimum.

Given that we are addressing forensic acquisition here, if it means multiple runs, the following examples will be used to illustrate the most important options to ddrescue work for the forensic examiner. We will concentrate on detailing the map file used by ddrescue so that the user can see what is going on with the tool, and how it operates.

Let's look at a simple example of running ddrescue on a small drive without errors, the simplest is by providing the input file, output file and a name of our map file. Note that there is no if= or -f-. In order to get a good look at how the map file works, we'll interrupt our imaging process halfway through, check the map file to illustrate how an interruption is handled, and then resume the imaging.

```
root@forensic1:~# ddrescue /dev/sdd ddres.img.raw ddrescue.map
GNU ddrescue 1.21
Press Ctrl-C to interrupt
```

| :--- | :--- | :--- |
| ipos: 1085 MB, non-trimmed: | @ B, current rate: | 109 MB/s |
| opos: 1085 MB, non-scraped: | @ B, average rate: | 361 MB/s |
| non-tried: 1062 MB, errsize: | @ B, run time: | 3s |
| rescued: 1085 MB, errors: | @, remaining time: | 3s |
| percent reduced: 50.54% | time since last successful read: | 0s |

Copying non-tried blocks... Pass 1 (forwards)^C
Interrupted by user

Here used /dev/sdd as our input file, wrote the image to ddres.img.raw, and wrote the file to ddres.map. The output shows the progress of the imaging by default, using a running count of the data copied or "rescued", along with count of the number of errors encountered (in this zero), and an imaging speed. In this case, the process was interrupted at about 50% completion, with the ctrl-c key command.

Now we have a look at our map file:

```
root@forensic1:~# cat ddres.map
# Mapfile. Created by GNU ddrescue version 1.21
# Command line: ddrescue /dev/sdd ddres.img.raw ddres.map
# Start time: 2017-05-03 13:12:15
# Current time: 2017-05-03 13:12:28
# Copying non-tried blocks... Pass 1 (forwards)
# current_pos current_status
0x40B10000 ?
# pos size status
0x00000000 0x40B10000 +
0x40B10000 0x3F4EFE00 ?
```

The map file shows us the current status of acquisition. Lines starting with a # are comments. There are two sections of the note. The first comment line shows the current status of the imaging while the second section (two lines, in this case) shows the status of blocks of data. The values are in hexadecimal, and are used by ddrescue to keep track of areas of the target device that have marked errors, areas that have already been successfully read and written, and that remain to be read. The status symbols we will see here (taken from the info page) are as follows:

| Character | Meaning |
| :--- | :--- |
| ? | non-tried |
| * | bad area non-trimmed |
| / | bad area non-scraped |
| - | bad hardware block(s) |
| + | finished |

> ¹⁴ The ddres info page has a very detailed explanation of the map file structure.

In this case we are concerned only with the ? and the +. Essentially, when the copying process is interrupted, the log is used to tell ddrescue where the copying left off, and what has already been copied (or otherwise marked). The first section (status) alone may be sufficient in this case, since ddrescue only picks where it left off, but in the case of a disk with errors, the block section is there so ddrescue can keep track of what areas still need to be retried as good data is sought among the bad.
