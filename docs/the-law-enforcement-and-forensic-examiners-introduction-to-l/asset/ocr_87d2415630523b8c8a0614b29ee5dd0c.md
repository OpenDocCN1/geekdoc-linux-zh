ofsz=BYTES : output file size: When using either ofs or hofs, use this parameter to set the size of each split file that is created.
See the page for the various suffixes that can be defined as units. For example 26G would be 2(1024)(1024)(1024) bytes.

hash=ALGORITHM : hash algorithm: When specifying that we want the output bytes, this is the algorithm we use.

log=FILE : write a log to FILE: Log our acquisition to the file specified.

hlog=FILE : write our hashes to FILE: If we specify hashing with hof or ofs, write the hashes to the file.

If we redo our imaging of /dev/sd using dc3dd with simple if= and of=, as used with dd, the session would look something like this. Note that we are still in ~/case11images and that we are writing the log to the parent directory

```
root@forensic1:~case1/images# dc3dd if=/dev/sd of=case1.disk1.dc3dd.raw
```

dc3dd completed at 2017-04-24 16:49:44 -0400

Our file is still dc (if=/dev/sd), our output file is now
case1.disk1.dc3dd.raw (of=case1.disk1.dc3dd.raw). One of the first you notice right away is that dc3dd returns more information while the program is running. It gives you a nice progress indicator, unlike dd. The correct number of sectors for /dev/sd were captured (7812500), and there were no "bad" sectors detected. The start and stop timestamps are also added by default. If you specify a log file, this information is captured very nearly. We will look at the hashing options and logging in more detail in a little while.

This standard output and the availability of simple logging is one of the things that makes dc3dd a better candidate for forensic imaging compared to dd.
