# sleuth Kit Exercise 3 – Unallocated Extraction & Examination

As the size of media being examined continues to grow, it is becoming apparent to many investigators data reduction techniques are more important than ever. These techniques work on several forms, including hash analysis (removing "good" files from a data set, for example) and separating unallocated space from unallocated space, allowing them to be separately with specialized tools. We will be doing the latter in this exercise. The blcat command used earlier is part of the Sleuth Kit of tools for handling information at the “block” layer. The block layer consists of actual file system blocks that hold the information we are seeking. They are not specific to unallocated data, but are especially useful for working on unallocated blocks that have been extracted from image. The tools that manipulate this layer, as you would expect, include: blks, blkcalc, blkstat. The tool that starts us off is blks. This command "lists all the data blocks". If you were to use the -e option, the output would be the same as the output of dd for that volume, since -e tells blks to "copy every block". However, by default, blks will only copy out the unallocated blocks of an image. This allows us to separate allocated and unallocated blocks in our file system. We can use logical tools (find, etc.) on the "live" file system, and ensure recovery on only those blocks that may contain deleted orallocated content. Conversely, when we do a physical search of the output of blks, we can be sure that artifacts are found. To illustrate what we are talking about, we'll run the same exercise in TSK Exercise #2A, this time extracting the unallocated data from our volume of interest and comparing the output from the whole volume analysis. So, we will be working on able2.dd. We expect to get the same results in Exercise #2A, but this time by analyzing the unallocated space and associating the recovered data with its original location in the disk image. First we'll need to change into the directory containing able2.dd. Then we check the partition table and decide which volume we are examining so we know the -o (offset) value for our Sleuth commands. To do this, we run the mmls command as before:

In the command, we are using blkls on the second partition (-o 10260) within the able2.dd image, redirecting the output to a file called able2.blkls. The file able2.blkls will contain only the unallocated blocks from the target file system. In this case we end up with a file that is 9.3M in size.
