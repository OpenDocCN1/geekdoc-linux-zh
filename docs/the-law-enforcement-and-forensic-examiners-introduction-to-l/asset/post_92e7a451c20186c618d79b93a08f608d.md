Now we'll look at ewexport. This tool allows you to take an EWF file to a bit stream image, essentially removing the meta-data and leaving us in the raw format, with dd. It is interesting to note that ewexport can actually write to standard output, making it suitable for piping to other commands. Here, we use the command with several options that result in the EWF file exported to a raw image.

At this point, we've covered dd, dc33dd, ewfacquire and common methods for checking the integrity and exporting the collected images.

All of the tools we've covered so far are great for ideal situations, where our media behaves as we expect. In addition, they all have options or built in mechanisms that would allow our acquisition to read past (or accurately 'around') any non-fatal disk errors while syncing output to the resulting image might be usable. While many practitioners suggest these options as a default for reading dd commands, I tend to argue against it. Some of the reasons for this will become more apparent in the following section.

# Media Errors - ddrescue

Now that we have a basic understanding of media acquisition and the collection of evidence images, what do we do if we run into an error? Suppose you use dd and the command exits halfway through the process with a read error?

We can construct dd to attempt to read past the errors using the conv=noerror option. In basic terms, this is using the dd command to ignore the errors that it finds, and attempt to read past them. When we specify the noerror option it is a good idea to use the sync option with it. We will "pad" the dd output where errors are found and ensure that the output is "synchronized" with the original disk. Assuming that your drive is /dev/sdc, the command will look like something:

```
root@forensic1:~# dd if=/dev/sdc of=image.raw conv=noerror,sync
```

> I would like to consider forensic examiners using the conv=noerror,sync option, however. While dd is capable of reading past errors in many cases, it is not designed to actually recover any data from those areas. There are a number of tools out there are designed specifically for this purpose. If you need to use conv=noerror,sync, then you are using the wrong tool. That is not to say it will work as advertised (with some caveats), only that there are better options, or at least important considerations.

Which brings us to ddrescue.

Testing has shown that standard dd tools are simply inadequate for acquiring disks that have actual errors. This is NOT to say that dd, dc33dd and dcfdd... are not optimal for error recovery. You may be forced to use dd or dc33dd because of limits of external access or considerations of time. In dd because there are instances where it may be the only tool available to you. In those cases, understanding the use of command line options to optimize recovery is important for preservation. However, if there are options, then a different tool would make sense. This section is not meant to provide education on disks, media failure, or types is not meant to imply that any tool is better than other. I will simply describe the basic functionality and leave it to reader. First, let's start with some of the issues that arise with the use of common tools. For the most part, these tools take a “linear” approach to imaging, meaning that at the beginning of the input file and read by block until the end is reached. When an error is encountered, the tool will either fail with “input/output” error or if parameter such as conv=noerror is passed, it will ignore the errors and attempt to read through (skip) them, continuing to read by block until it comes across readable data again. Here is a simple dd command on a disk. The disk is 41943040 sectors:

```
root@forensic1:~# blockdev/sdf
41943040
```

```
root@forensic1:-# dd if=/dev/sdf of=dd.raw
dd: error reading '/dev/sdf': Input/output error
12840+0 records in
12840+0 records out
6574080 bytes (6.6 MiB, 6.3 MiB) copied, 0.15743 s,41.8 MB/s


The dd command above was only able to read 12840 sectors (which the dd output shows). The same command, this time using conv=noerror,sync will ignore the error, pad the error with null bytes, and continue on:

```
root@forensic1:-# dd if=/dev/sdf of=error.raw bs=512 conv=noerror,sync
dd: error reading '/dev/sdf': Input/output error
12840+0 records in
12840+0 records out
6574080 bytes (6.6 MiB, 6.3 MiB) copied, 0.163426 s, 40.2 MB/s

12841+0 records out

dd: error reading '/dev/sdf': Input/output error
```

What you end up with the end of this command is an image of the entire disk, but with the errors filled in (sync)d zeros to maintain correct offsets within file systems.

Obviously, simple failure (“giving up” when errors are encountered) is not good. Any data in reading areas beyond the errors will be missed. The problem with ignoring errors and attempting to read back them (using conv=noerror) is that we are stressing a disk that is already possibly on the verge of complete failure. The fact of the matter is that you may get few chances at reading a disk that has “bad sectors”. If there is an actual physical defect, the simple act of reading the bad areas makes matters worse, leading to disk failure before other viable areas of the disk are collected. If all of these, of course, to disks with “physical” storage. Solid state storage is another matter entirely.

So, when we use conv=noerror to an imaging command, we are actually asking our imaging tools to “gr through” the bad areas. Why not skip over the bad sections altogether, in many cases recovery may be unlikely? Instead we should concentrate on recovering data from areas of the disk that are good. Once the “good” data is acquired, we can go back and attempt to collect data from the error areas, with a recovery algorithm designed with purpose.

In a nutshell, that is the philosophy behind ddrescue. Used properly, ddrescue will read the “healthy” portions of a first disk, then fall back to recovery mode - trying some of very robust logging to read data from bad sectors. It does this using the log file as a map file), which allows it to resume an imaging at any point, given a map file to work from. This is an important (perhaps the most important) point about using ddrescue - that is, with a map file you never need to read already successfully recovered sectors. When ddrescue references the map file on successive runs, it fills in the gaps, it does not “redo” work again finished.
