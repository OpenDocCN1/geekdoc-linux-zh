The command uses tr to convert the set of control characters [:ctrl:] to newlines ('\n'). The input is taken from ewfmt/ewf1, and the resulting stream is piped through grep to search with -abi options to treat it like a text file (a), provide the byte offset (b) and make the search case insensitive (i). The output shows our offsets and string hints are now much more readable.

Now we run through the same set of commands we previously did. Calculating the sector the keyword is in, the offset in the volume, and finding which block and data entry is associated with the keyword hit.

We'll work with the first keyword hit (426596865:www.stopcyberbullying.org). The sector offset to our hit is found by dividing the byte offset by the sector size (512). We already know that there is only one partition in this image, we'll run mls to be sure. We also run fsstat to confirm the block size (which we already know from previous exercises is 4096). As expected, the keyword is in the only NTFS partition which resides at offset 2048 (sectors). We can complete the math and determine the block the keyword resides in all at once:

```
barry@forensic1:~/NTFS_Pract_2017$ echo "(42659865-(2048*512))/4096" | bc
103893
```

For review, this reads: "Take our offset to the keyword in our data (426596865), subtract the offset to the start of the partition (2048*512), and divide the resulting value by our file system block size (4096). Our file system block is 103893.

```
barry@forensic1:~/NTFS_Pract_2017$ blstat -o 2048 NTFS_Pract_2017.E01 103893

```
barry@forensic1:~/NTFS_Pract_2017$ find -o 2048 -d 103893 NTFS_Pract_2017.E01

```

We can see that blstat tells us the cluster (block) is unallocated, and find shows us that the meta-data structure (MFT entry) associated with that block (-d 103893) is 248-128-2.

# Bulk Extractor – Comprehensive Searching

In previous exercises, we discussed where simple text searches might be ineffective depending on character encoding and file formats. There are a number of character set aware tools out there that we can use to overcome many these issues, but detailed descriptions of character encoding and searches are not what we are aiming for. Instead we are to introduce a tool, bulk_extractor, that incorporates some excellent multi-format searching capabilities with some other useful functions. bulk_extractor was created by Simon Garfield at the National Postgraduate School. For those of you who have not already heard of or used bulk_extractor, it is one of those tools I rarely use on every case. Even when I have a targeted extraction or analysis to perform, bulk_extractor can always find additional information or, at the least, provide an excellent overview of user activity. It is particularly useful in situations you have been given (or acquired yourself) a high volume of media.

bulk_extractor differs from some other common tools in that it runs and searches independently of the file system. In this case, the content – whether allocated or unallocated, whole or fragmented, or even in compressed containers. bulk_extractor reads the data in blocks, without regard to the file system, and recursively searches those blocks for interesting features. Recursive in this case means the tool will, for example, decompress an archive to search the contents and extract text from PDF files to be further processed.

A user’s manual for bulk_extractor is available at:
