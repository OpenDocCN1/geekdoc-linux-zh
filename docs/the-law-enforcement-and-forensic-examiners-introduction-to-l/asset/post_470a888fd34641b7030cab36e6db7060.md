## Mount Multi Partition Images with kpartx

Up to this point we've moved a simple file system image with the mount command, we've moved a file system from a full disk image with a single partition, and we've learned about the loop device and how to specify its association with a specific partition.

Let's look at a disk image that has multiple partitions. Our previous method of identifying each partition by offset and size, and passing those parameters to the Setup command would work fine to mount multiple file systems within a disk image (using different loop devices for each, but wouldn't it be nice if we had a tool to do all of that for us?) kpartx is that tool.

In simple terms, kpartx maps partitions within an image to separate loop devices that can then be mounted as any other volume (assuming a mountable file system). It is part of the multipath-tools package for Slackware, and can be installed via sbtools or through the SlackBuild available at SlackBuilds.org.

Now we can run kpart on the image file and the partitions to check the partitions, and then to map them, only loop nodes. See the available options, run kpart by itself:

```
root@forensic:~# kpart
usage: kpart [-a|d] [-l] [-v] disk
-a add partition devmappings
-r readonly devmappings
-d del partition devmappings
-p set device name number
-f force partition table (GPT)
-v verbose
-s sync mode

The first command will list the partitions as they will appear (-l). After that add the mappings in the second command (-a) and create them with the read option as well (-r):

```
root@forensic:~# kpart -l gptimage.raw
loop0p1 : 204800 /dev/loop0 204800
loop0p2 : 2097152 /dev/loop1 206848
loop0p3 : 6084575 /dev/loop0 2304000
loop deleted : /dev/loop0
```

```
root@forensic:~# kpart -r -a gptimage.raw
```

Once we execute the command above, our mappings are created and we can now access each partition through the /dev/map/loop0X, where X is the number of the partition.

```
root@forensic1:~# ls -l /dev/map
total 0
------ 1 root root 236 May 13 control
crw-rw-rw 1 root root 7 May 13 12:58 loop01 -> ../dm-0
lrwx-rw-wx 1 root root 7 May 13 12:58 loop02 -> ../dm-1
lrwx-rw-wx 1 root root 7 May 13 12:58 loop03 -> ../dm-2
```

One thing to keep in mind is that the /dev/map/ nodes are actually symbolic links to /dev/dm-* nodes if you run the file command to try and detect the file type, it will simply say symbolic link. To use the file command, run it against the dm device. All operations that we use can be done on /dev/map/loop0X.

```
root@forensic1:~# ls -s /dev/map/loop01
/dev/map/loop01: symbolic link to ../dm-0
```

```
root@forensic1:~# ls -s /dev/dm-*

root@forensic1:~# mount /dev/map/loop01 /mnt/tmp

## Mounting Split Files with affuse

We are going to continue our exploration of mounting split files by addressing those occasions you might want to mount an image that has been split with dd3, etc. The Advanced Forensic Format (AFF) is an open format for forensic imaging, and the afflib package provides a number of utilities to create and manipulate images in AFF format. We won't cover those tools, or the AFF format in this document (at least not in this version), but we are interested in right now the affuse format.

affuse provides virtual access to a number of image formats, split files among them. It does through the File System in User Space interface. Commonly referred to as "fuse file systems", fuse allows us to create application file system access mechanisms that can bridge to the kernel and the normal file system drivers.

The afflib package is available as a SlackBuild for Slackware, and can be simply installed with sboinstall

```
root@forensic1:~# sboinstall afflib
```

afflib is library and set of tools to support Advanced Forensic Format (AFF).
