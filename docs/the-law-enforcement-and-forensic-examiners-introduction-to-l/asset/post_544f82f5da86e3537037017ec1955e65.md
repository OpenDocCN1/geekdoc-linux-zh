## Over the Wire - dd

The next step is to open a "listening" port on the collection computer. We will do this on our collection system with nc (netcat), making sure we have a mounted file system to store the image. In this case we are using an external drive mounted on /mnt/evidence to store our image.

```
root@forensic:~# nc -l -p 2525 | dd of=/mnt/evidence/net_img.raw
```

This command opens a netcat (nc) listening session (-l) on TCP port 2525 (-p 2525) and pipes any traffic that comes to that port to the dd command (with only the of flag), which writes the file /mnt/evidence/net_img.dd.

Next, on the subject computer (again note the command prompt “bootdisk”), we issue the dd command. Instead of giving the command output using of= we pipe the dd output to netcat (nc) and send it to our listening port (2525) on the collection computer at IP address 192.168.0.1.

```
root@bootdisk:-# dd if=/dev/sda | nc 192.168.0.1 2525
```

This command pipes the dd straight to nc, directing the image over the network to TCP port 2525 on the host 192.168.0.2 (our collection box's IP address). If you want to use dd options conv=noerror,sync bs=x, then you do that on the dd side of the pipe:

```
root@bootdisk:-# dd if=/dev/sda bs=4096 | nc 192.168.0.1 2525
```

Once the imaging is complete, we will see that the commands at both ends appear to "hang". After we receive our completion messages from dd on both boxes (in /root/), we can call the nc listening on our collection box with a simple ctrl+c. This should return prompts on both sides of the connection. You should check both hashes of the physical disk that was imaged on the subject computer and the resulting image on the collection box to see if they match.

```
root@forensic:-# sha2sum /mnt/evidence/net_img.raw
8f6cec10ae87dff4590ba09ba51385679
```

Our hashes match and our network acquisition was successful.

## Over the Wire - dc3dd

As discussed previously, there are a number of tools we can use for imaging that provide a more forensic oriented approach. dc3dd is a good choice for imaging as it is on local disks. You also have flexibility with dc3dd that even if your boot disk does not come with installed, you are still able to use all its features on the evidence collection computer.

dc3dd does all its imaging on the output side of the acquisition process (unless you are acquiring from file sets or some other non-standard source). This means we can use dd on our subject computer (using the boot disk) to acquire the disk and stream the contents across our netcat pipe, and still use dc3dd on our collection machine to handle hashing, sitting and logging. Most of dc3dd's options and parameters work on the output stream. So, while listening on the process system will use dc3dd commands, the subject system can use the same dd commands we used.

On the collection system, let's set up a listening process that uses dc3dd to split the incoming data stream into 2GB chunks and logs the output to nc.dc3dd.raw. As soon as we initiate our command, dd will start and waiting for input from the listening port (2525):

```
root@forensic:-# nc -l -p 2525 | dc3dd of=/mnt/evidence/nc.dc3dd.000sz=2G log=/mnt/evidence/nc.dc3dd.log
```

> ¹⁵PRO TIP: You can watch the progress of the imaging on your collection system by opening another terminal and "watching" the size of the file grow. Use watch -lh net_img.raw and ctrl-c when it's complete. watch will update the command -lh every two seconds until you stop it.

```

command line: dc3dd of=nc.dc3dd.000 ofsz=2G log=nc.dc3dd.log
sector size: 512 bytes (assumed)

```

The dc3dd output will start immediately, but stay at 0 bytes until it receives input through the pipe. As soon as you start the imaging process on the subject, you'll see the dc3dd command on the listening machine start to process the incoming data. Again notice we are using dd on the subject box to stream over the pipe. dc3dd takes over the collection machine to implement dc3dd options and logging.

```
root@bootdisk:-# dd if=/dev/sda | nc 192.168.0.1 2525
```

When the transfer is complete, we can look at the results and the dc3dd log on our machine:

## Over the Wire - ewquirestream

Last, but not least, we will cover a tool that will allow us to take a stream of input (with the same netcat pipe) and create an EWF file. ewquirestream acts much like ewquire (and is part of the same libewf package we installed previously), which allows for data to be gathered via standard input. The most obvious for this is data passing by netcat pipe.

In previous examples, once the data reached the destination collection computer, the listening netcat pipe pushed the output to the dd or dc3dd output string, and the file was written exactly as it came across, as a bitstream image.

But by using ewquirestream, we can create EWF files instead of a bitstream image. We simply pipe the output stream from netcat to ewquirestream. If we do not wish to have the program use defaults, then we use the command with options that define how we want the image made (sectors, hash algorithms, error handling, etc.) and what information we wanted. The command on the subject machine remains the same. The command on the collection system would look like this (utilizing many of the command defaults):

```
root@forensic:~# nc -l -p 2525 | ewquirestream -C 111-222 -D 'Subject drive' -e 'BarryGrundy' -E '1' -f encase6 -m fixed -M physical -N 'Imaged via network' -t /mnt/evidence/nc_ewf_image
```

Acquisition started at: May 06, 2017 09:40:22. This could take a while.

```
<-- output sits here until acquisition is started on the subject computer
```

...

This command takes the output from netcat (nc) and pipes it to ewquirestream.

- the case number is specified with -C
- the evidence description given with -D
- the examiner given with -E
- evidence number with -f encase6
- encase6 format is specified with -f encase6
- the media type is given with -m
- the media flags are given with -M
- notes are provided with -N
- the target path and file name is specified with -t /path/file.
