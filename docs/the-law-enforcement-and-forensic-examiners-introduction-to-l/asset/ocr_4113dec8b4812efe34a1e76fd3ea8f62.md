The find.txt file has a commented area (lines starting with #), and the actual output of the scanner itself, each "feature" on one line. There are three parts to the scanner output for each feature. The first is an offset. This offset can have multiple parts. In **bulk_extractor** this is referred to as the *forensic path*. This includes a disk offset to the data containing the feature, the scanner(s) that found it, and then the offset with data. The forensic path is followed by the feature itself, in this case "Uranium-235" search term. Finally we are given a bit of context. In other words, for our example:

44590125-ZIP-9745

Compressed data (ZIP) was found at disk offset
445901295. The (Uranium-235) was
found at offset 9745 in compressed data.

Uranium-235

The feature that was found (our search term)
The context the feature was found in.

ference between Uranium-235 and
Uranium-238

Using what we've learned previously about physical searching, let's have a quick look at the data found at that disk offset? Remember our formula for finding the offset in a file system when given we've seen this NTFS image before, so we already know the file system starts at offset 0248, so we'll calculate the file offset and run the **ifind** command we used several times to find out which MFT entry points to the data block. Finally we use the *icat* command and pipe the output to **file** by bc so we can identify the type:

```
bar@forensic1:~/bulk$ echo "((445901295-(2048*512))/4096))" | bc
108066
```

```
bar@forensic1:~/bulk$ ifind -d 108066 -o 2048
../NTFS_Pract_2017/NTFS_Pract_2017.E01
236-128-2
```

```
bar@forensic1:~/bulk$ icat -o 2048 ../NTFS_Pract_2017/NTFS_Pract_2017.E01
236 | file -
/dev/stdin: Microsoft Word 2007+
```
