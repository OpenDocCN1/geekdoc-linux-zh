## Direct Blocks:

```
barry@forensic1:~/able_3$  icat -o 104448 able_3.000 21 | xxd | head -n 5
<no output>
```

Here we have a different outcome. Inode 21 points to an unallocated file. In an ext4 file system, when the Direct Blocks are cleared, there is no longer a pointer to the data, so commands like icat will not work. Remember that icat works at the inode (file meta-data) layer. The icat command uses the information found in the inode to recover the file. In this case there is none. This does not mean we cannot recover the data that was there. On the contrary, there are a number of techniques we can use to recover the deleted files. But in this case it becomes difficult to recover the data and associate it with a particular file name and inode. While this sort of forensic analysis is outside the scope of our exercise, it highlights the difference between using tools on different file systems. Know your tools, their capabilities, and their limits. When test tools for, it is not enough to say "tool does not work". In this case it would be accurate to say that "icat works as expected on ext4 file system, but is limited on deleted entries".

## Physical Search & Allocation Status (ext2)

We did a very basic recovery of physical string search on fat_raw image earlier. This exercise is meant to take some of what we learned and apply it to a more complex disk image. In a normal examination, we are going to find out (if possible) what string result belonged to or not file is allocated or unallocated. That is the purpose of this exercise. Exercises like this highlight clearly the benefit of learning digital forensics tools like Sleuth Kit. Unlike GUI tools with menus and windows, TSK forces you to understand these concepts behind the tools. You cannot use TSK without understanding which tools to use and when. Back to our able2 image. This time we are going to do a search for a single string in able2.dd. In this case we will search the image containing our able2 image and use grep to search for:

```
barry@forensic1:~/2$ grep -abi cybernetic able2.dd
10561603: updated by Cybernetic for linux rootkit
55306929:Cybernetic presents...
55312943:Email: cybernetic@nym.net
55312975:Finger: cybernetic@nym.net
```

Recall that our grep command is taking the file able2.dd as text file (-a) and searching for the string cybernetic. The search is case-insensitive (-i) and will output the byte offset of any matches (-b). Our output shows that the first match comes at byte offset 1056103. Like in our first search, we are going to quickly view the match by our viewer xxd and the -s option to provide the offset given by grep. We will also use the head command to indicate that we only want to see a specific number of lines, in this case (-n 5). We just want to get a look at the context of the match before proceeding.

```
barry@forensic1:~/2$ xxd -s 10561603 able2.dd | head -n 5
00a2843: 002a 0975 6174 6574 6064 2062 7390 4379  .updated by Cy
00a2853: 62c6 726e 6574 696b 66f2 206c 696e berneretic for lin
00a2863: 7578 2072 06f6 746b 6974 0a20 2af2 0a0a ux rootkit. /*.
00a2873: 2369 6263 6c75 6475 203c 7379 7372 7479 #include <sys/ty
00a2883: 7065 73e2 6e83 0a23 696e 636c 7564 6520 pes. #include
```

We also have to keep in mind what we find that the offset is to the match in the entire disk (able2.dd is a full disk image), not in a specific file system. In order to use the Sleuth Kit tools, need to have a file system to target.

Let's figure out which partition (and file system) the match is in. Use bc to calculate sector of the image and therefore the original disk the keyword is in. Each sector is 512 bytes, by dividing the offset bytes by 512 tells us which sector:

```
barry@forensic1:~/able2$ echo "10561603/512" | bc
20628
```
