
## Hashing Media

One important step in evidence collection is verifying the integrity of your data both before the acquisition is complete. You can get a hash (MD5, or SHA) of the physical device in a number of different ways.

Linux can provide hashes using the following tools:

- md5sum - 128 bit checksum
- sha1sum - 160 bit checksum
- sha224sum - 224 bit checksum
- sha256sum - 256 bit checksum
- sha384sum - 384 bit checksum
- sha512sum - 512 bit checksum

In this example, we use the SHA. SHA is a hash signature generator that supplies a bit "fingerprint" of a file or disk (which is represented by a file-like device node). It is not feasible for someone to computationally recreate a file on the SHA hash. This means that matching signatures identify identical files. There has been a lot of talk in the digital forensic community over the years of (even recent) proof of "collisions" that render certain hash algorithms "obsolete." This guide is about learning the tools. Do your research and check your agency or community guidelines for additional information on which algorithm to select.

We can get an SHA hash of a disk by running the following command (note that the following commands can be replaced with md5sum if you prefer to use the MD5 hash algorithm, or any of the other above listed checksums):

```
root@forensic1:~ sha1sum /dev/sdc
5175ffff1366d1d5dd02e2956d132304e71677      /dev/sdd
```

or

```
root@forensic1:~ sha1sum /dev/sdc > case1/case1.disk1.sha.txt
```

The redirection in the second command allows us to store the signature in a file and use it for verification later on. To get a hash of a raw disk (/dev/sdc, /dev/sdd, etc.) the disk does NOT to be mounted. We are hashing the device (disk) not the contents. As we discussed earlier, Linux treats all objects, including physical disks, as files. So whether you are hashing a file or a hard drive, the command is the same.

### Collecting a Forensic Image with dd

Now that we have collected information on our subject media and obtained a hash of the physical disk for verification purposes, we can begin our acquisition.

dd is the very data copying utility that comes with a standard GNU/Linux distribution. There are no, doubt, better imaging tools out there for use with Linux, but dd is the only standby. We'll be covering some of the more forensic oriented tools in the following sections, but learning dd is important for much as soon as in. Like vi, you are bound to find dd on just any Unix machine you might come across. In some cases, the best imaging tool you have available just be the one you will always have access to.

This is your standard forensic image of a suspect disk. The dd command will copy every bit from the kernel areas of the media to the destination of your choice (physical device or file). There are a couple of concepts to keep in mind when using dd. Some of these concepts also apply to the other forensic tools we will cover. In very basic form, the dd command looks like this:

```
dd if=/dev/sdc of=evidence.raw bs=512
```

- Input file (if): this is the source media. What are we imaging.
- /dev/sdc
- Output file (of): this is the destination. Where are we placing the image/copy.
- evidence.raw
- Output can be a file (as above). This is common.
- Output can be a physical device. This is often referred to as a "clone".
- Disk image (/dev/sdx): We can use the name for the entire device node.
- Partition (/dev/sdx1): We can use the device name and the partition number to image a single partition/file system. # is the partition number (as returned fdisk -l, for example).
- Block size (bs): the size of the device being imaged. The kernel usually handles this. This may become a issue as block sizes change with the evolution of storage media. For our current target (/dev/sdc), the hdparm -I output is showing 512 bytes per sector (Logical/Physical Sector Size). Be aware of some newer devices that are 2048 bytes per sector.
- There is also set of options that are often used to avoid problems in case there are bad sectors on the disk.
- conv=noerror,sync
This option instructs dd to bypass copying sectors with errors AND pad those matching sectors in the destination with zeros. The padding keeps offsets correct in any file system data and perhaps still result in a usable image (or on this later). I'm not a fan of using this

As part of our organization, we'll make a new directory images in case1 directory. This is where we keep working copies of images. Normally, you would create images directly to either a larger drive that has been sanitized, or to a network storage volume that is used to maintain original copies. That will depend on your specific policies.

In this case, for illustration, we will image directly to our case1/images directory. I prefer keeping images separate as it allows protecting the directory of attributes that prevents changes or deletions to your working copy image files, once we've completed the imaging process.

To keep your dd command shorter, we'll change into our case1/images directory (case1/images) and write our output file here. Without needing to specify the directory (where we are writing to the current), we keep the command shorter and easier to read.

```
root@forensic1:~# cd case1/images
root@forensic1:~/case1/images# dd if=/dev/sdc out=case1.disk1.raw bs=512
71825000+0 records in
71825000+0 records out
400000000000 (40 GB, 37 GB) copied, 939.88 s, 42.6 MB
```

This takes your device /dev/sdc as the input file and writes the output file of called case1.disk.raw in the current directory /root/case1. The bs option specifies the block size. This is really not needed for most devices (hard drives, etc.) as the Linux kernel handles actual block size. It's added here for illustration, as it can be a useful option in many situations (discussed later).

Using dd creates an exact duplicate of the physical device file. This includes all file slack and unallocated space. We are not simply copying the logical file structure. Unlike forensic imaging tools, dd does not fill the image with any proprietary data or information. It is a simple stream copy from start to end. This has a number of advantages, as we will see later.

You can see from our output that the number of records (512 byte, in this case) as the number of sectors for this disk previously reported by hdparm -I, /dev/sdc matches. To verify your image, we can do the following. We want to recall the hash from the original device (/dev/sdc), which we stored in the file case1/disk1.sha.txt and compare that to the hash of the image we just made

```
root@forensic1:~/case1/images# cat ../case1.disk1.sha.txt
b3b506ea4c53b83495ac4b1956e0a250104f /dev/sdc
root@forensic1:~/case1/images# sha1sum case1.disk1.raw
b3b506ea4c53b83495ac4b1956e0a250104f /dev/sdc
```

## dd and Splitting Images

It has become common practice for digital forensics to split the output of imaging. We will first discuss split on its own, then in conjunction with dd.

For example, we have our 40GB image and now want to split it into 2GB parts. For this we use the split command. split normally works on lines of input (a text file). But if we use the -b option, we split to treat the file as binary input and lines are ignored. We can specify the size of the files we want along with the prefix we use. split -d gives us numerical numbering (*.01, *.02, *.03, etc.) for the output files as opposed to alphabetical (*.aa, *.ab, *.ac, etc.). The -a option specifies the suffix length. The command looks like:

```
split -d -a N <file to split> <prefix of output files>
```

where N is the length of the extension (or suffix) we will use and X is the size of the resulting files with a unit modifier (M, G, KM, KG, etc). For example, with our image of /dev/sdc, we can split it into 2GB parts using the following:

```
root@forensic:/case1/images# split -d -a 3 -b 2G case1.disk1.raw
case1.disk1.split
```

This will result in 20 files (2GB in size) each named with the prefix case1.split as specified in the command, followed by 000, 001, 002, and so on. The -a option with 3 specifies what we want the extension to be at least 3 digits long. Without -a 3, our files will be named *.01, .02, .03, etc. Using 3 digits maintains consistency with other tools. Note the trailing There be store archived images.
