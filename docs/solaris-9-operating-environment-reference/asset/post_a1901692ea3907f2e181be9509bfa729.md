In addition to dot, pdb keeps track of another global value called the increment. The increment represents the distance between dot and the address following all the data read by the last formatting dcmd. For example, if a formatting dcmd is executed with dot equal to λ and displays a that dcmd completes, it is still λ, the increment is set to 4. The + character (described in "Arithmetic Expansion (on page 823)") now evaluate to the value λ + 4 and could be used to reset the address of the next data object for a subsequent dcmd.

You can also use the /, , and ? formatting demands to search for a particular integer value in the virtual address space, physical address space, and objectfile, respectively, by specifying one of the following modifiers as the first format character and then specifying a value and optional mask. The value and mask are each specified as either immediate values or expressions enclosed in square brackets preceded by a dollar sign. If you specify only a value, mdb reads integers of the appropriate size and stops at the address containing the matching value. If you specify a value V and mask M, mdb reads integers of the appropriate size and stops at the address containing a X (X & M) == V. At completion of the demod, mdb returns to the address containing the match. If no match is found, dot is left at the last address that was read. The search modifiers are listed below.

- - Search for the specified 2-byte value.
- - Search for the specified 4-byte value.
- - Search for the specified 8-byte value.

Note that for both user and kernel targets, an address space is typically composed of a set of discontinuous segments. It is not legal to read from an address that does not have a corresponding segment. If a search reaches a segment boundary without finding a match, it aborts when the read past the end of the segment boundary fails.

# Execution Control

Starting in the Solaris 9 release, mdb provides features for controlling and tracing the execution of a live, running process. Currently, only the user process target provides support for execution control. mdb provides a simple model of execution control.

A target can be started from the debugger with ::run, or mdb can attach to an existing process with ::attach, or the -p command-line option.

You can specify a list of traced events. Each time a traced event occurs in the target process, the top thread that triggered the event is chosen as the representative thread, and control returns to the debugger. Once the target is running, you can regain control of the debugger by typing a user-defined interrupt character (typically, ?).

A software event is a transition in the target program that is observed by the debugger. For example, the debugger may observe the transition of a program counter to a register of interest (a breakpoint) or to a particular signal.

A software event is a description of a class of software events that is used by the debugger to instrument the target program to observe these events. We use ::events mdb to list the software events. A set of standard properties is associated with each event, as described in the following paragraph.
The debugger can observe a variety of different software events, including breakpoints, watchpoints, signals, faults and system calls. You can create new events with ::flitbp, ::bp, ::syscall, or ::probe. Each event has an associated callback (an mdb command string to execute as if it had been typed at the command prompt) and a set of properties. # Event Callbacks

Starting in the Solaris 9 release, the ::evset dmcmd and event tracing enable you to associate an callback (with the -c option) with each event. These callbacks are strings that execute when the event occurs. Before each callback is executed, the dot variable is set to the value of the program counter and the hits variable is set to number of times this specifier has matched. If the event callbacks contain one or more commands to continue the target (for example, :cont or :step), these commands do not immediately continue the target and wait for it to stop. Inside the event callback, mdb notes that a continue operation is now pending and return immediately. Following the execution of all event callbacks, the target resumes execution if matching event requested a continue. Conflicting continue operations requested, the operation with the highest precedence determines which type of continue. The order of precedence from highest to lowest is step.

# Thread Support

Starting in the Solaris 9 release, mdb provides facilities to examine the stacks and registers of each thread associated with the target. The persistent thread variable contains the representative thread identifier. The format of the thread identifier depends on the target. You can use the :regs and :fregs commands to examine the register set of the representative thread or another thread if its register is currently available. In addition, the register set of the representative thread is exported as a set of named variables. You can modify the value of one or more registers by applying the demd to the corresponding named name.

The mdb kernel exports the virtual address of the corresponding internal thread structure for a given identifier. The Solaris Modular Debugger Guide provides more information on debugging support for threads in the Solaris kernel. The mdb process target provides support for examination of threaded processes that use the native lwp_,/usr/lib/libthread.so or /usr/lib/libthread.so. When debugging a live user process, mdb detects when a single-threaded process opens or chooses libthread and automatically adjusts its view of the threading model on-the-fly. The process target thread identifiers correspond to either the lwpid_thread_t, or pthread_t of representative thread, depending on the threading model used by the application.
