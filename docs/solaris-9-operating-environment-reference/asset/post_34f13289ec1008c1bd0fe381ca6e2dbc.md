# priocntl — Display or Set Scheduling Parameters of Specified Process(es)

# Synopsis

```
/usr/bin/priocntl -l
/usr/bin/priocntl -d [-i itype] [idlist]
/usr/bin/priocntl -s [-c class] [class-specific options] [-i itype]
  [idlist]
/usr/bin/priocntl -e [-c class] [class-specific options] command
  [argument]
```

# Description

priocntl (priority control) command to assign processes to a priority class and to manage priorities within a class. You can also use priocntl to display the current configuration information for the system process or to execute a command with specified scheduling parameters.

Processes fall into distinct classes with a separate scheduling policy applied to each class. The process classes currently supported are:

- Real-time.
- Timesharing.
- Interactive.
- Fair-share (new in the Solaris 9 release).
- Fixed-priority (new in the Solaris 9 release).

The characteristics of these classes and the class-specific options they accept are described below. With appropriate permissions, the priontl command can change the class and other scheduling parameters associated with a running process.

The class-specific parameters to be set are specified by the class-specific options, as explained under the appropriate heading. If you use the -c class option, and idlist must specify a set of processes that are all in the same class; otherwise, an error occurs. If no class-specific options are provided, the class-specific parameters of the process are set to the default values for the class specified by -c class(or the default values).

The scheduling parameters of a process can be changed with priontl, the real or effective user ID or group ID of the working process; must match the real or effective user ID or group ID of the receiving process; otherwise, the effective user ID must be super. These are the minimum permissions required for all classes. An individual class can impose additional permissions requirements when setting processes to that class or when setting class-specific scheduling parameters.

With idlist specify a set of processes, priontl acts on the processes in the set in an implementation-order. If priontl encounters an error for one or more of the target processes, it may or may not continue through the set, the real or other, depending on the type of the error.

If the error is related to permissions, priontl prints an error message and then continues through the process set, resetting the parameters for all target processes for which the user has appropriate permissions. If priontl encounters an error other than permissions, it does not continue through the process but prints an error message and exits immediately.

# Real-Time Class

The real-time class provides a preemptive scheduling policy for processes requiring fast and deterministic response and user/application control of scheduling priorities. If the real-time class is configured in the system, it should have exclusive control of the highest range of scheduling priorities on the system. This ensures that a runnable real-time process is given CPU service before any process belonging to any other class.

Note — In the default configuration, a runnable real-time process runs before any other process. Therefore, inappropriate use of real-time processes can have a dramatic impact on system performance.

The real-time class has a range of real-time priority (rtpri) that can be assigned to processes within the class. Real-time priorities range from 0 to x, where the value of x is configurable and can be displayed for a specific installation that has already configured a real-time scheduler, with the following command:

```
castle% priontl -1
CONFIGURED CLASSES
=
```

SYS (System Class)
TS (Time Sharing)
Configured TS User Priority Range: -60 through 60
IA (Interactive)
Configured IA User Priority Range: -60 through 60
caste%

The real-time scheduling policy is a fixed-priority policy. The scheduling priority of a real-time process never changes except as the result of an explicit request by the user/application to change the rtpri value of the process.

For processes in the real-class time, the rtpri value is, for all practical purposes, equivalent to the scheduling priority of the process. The rtpri value completely determines the scheduling priority of a real-time process relative to other processes within its class. Numerically higher rtpri values represent higher priorities. Because the real-class controls the highest range of scheduling priorities in the system, it is guaranteed that the runnable real-time process with the highest rtpri value is always selected to run before any other process in the system.

In addition to controlling priority, priocntl controls the length of the time quantum allocated to processes in real-class. The time quantum specifies the maximum amount of time a process can consume assuming that it does not complete or enter a resource or event wait (sleep). Note that if another becomes runnable at a higher priority, the currently running process can be preempted receiving its full time quantum.

The following command displays the real-time priority and time quantum (in millisecond resolution) for each real-time process in the set specified by idtype and idlist.

```
priocntl -d [-i idtype] [idlist]
```

You can use any combination of -p and -t options with priocntl -s or priocntl -e for the real-class time. If you omit an option and the process is currently real-time, the associated parameter is unaffected. If you omit an option when changing the class of a process to real-time from other class, the associated parameter is set to a default value. The default value for rtpri is 0, and for the time quantum depends on the value of rtpri and on the system configuration; see rt_dtopt().

Using the -rtquantum, you can optionally specify a resolution with the -r option. If you specify no resolution, millisecond resolution is assumed. If you specify it must be integer between 1 and 1,000,000 inclusive and the resolution is used in microseconds. For example, specifying -r 100 sets the resolution to one-hundredths-of a second and the resulting time-quantum length to one-tenth-of-a-second (10/100). You can then specify very fine (nanosecond) resolution, the time quantum is limited by the system to the next integer multiple of the system clock's resolution. Requests for time quanta of 0 or greater than the (typically very large) implementation-specific maximum quantum result in an error.

You can use the real-time quantum-signal in the Solaris 9-release to notify runnable processes about the consumption of their time quantum. Those processes, which are monitored by the real-time quantum signal, receive the signal when the time quantum expires. The default value (0) of the time quantum tsig sends no signal delivery. A positive value triggers the delivery of the signal specified by the value. Kill (1) when operating on signals, the -tsig option is also able to handle symbolically signals like XCPU or KILL.

To change the class of a process to real-time (from any other class), you must have superuser privileges. To change the rtpri value or time quantum of a real-time process, you must either be superuser or currently be in the real-class (shell running).
