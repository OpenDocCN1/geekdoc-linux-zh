# srchtxt — Display Contents of, or Search for, a Text String in, Message Databases

# Synopsis

```
/usr/bin/srchtxt [-s] [-l locale] [-m msgfile, ...] [text]
```

# Description

Use the srchtxt command to display all the text strings in message databases or search for a text string in message databases (see mkmgs(1)). These databases are files in the directory /usr/lib/local/locale/LC_MESSAGES (see setlocale(3)), unless a file name given with the -m option creates a /. The locale is the name of the language in which the text strings are written. If you do not specify the -l option, the file accessed is determined by the value of the environment variable LC_MESSAGES. If LC_MESSAGES is not set, the files are accessed by the value of the environment variable LANG. If LANG is not set, the files accessed are in the directory /usr/lib/locale//LC_MESSAGES, which contains default strings.

If you specify no text argument, then all the text strings in the files accessed are displayed.

If you specify the -s option, the displayed text is prefixed by message sequence numbers. The message sequence numbers are enclosed in angle brackets: <msgnum>.

- - msgfile Name of the file where the displayed text occurred.
- - msgnum Sequence number in msgfile where the displayed text occurred. This display is in the format used by gettxt(1) and gettxt(3).

# Options

- - -s Suppress printing of the message number of the messages being displayed.
- - -l locale Access files in the directory /usr/lib/locale/LC_MESSAGES. If you also specify -m msgfile, locale is ignored for msgfiles containing a /.
- - -m msgfile Access files specified by one or more msgfiles. If msgfile contains a / character, then msgfile is interpreted as a path name; otherwise, it is assumed to be in the directory determined as described above. To specify more than one msgfile, separate the file names with commas.
- - - text Search for the text specified by text, and display each one that matches. text can take the form of a regular expression; see regexp(5).

# Examples

```
# srchtxt

<ibfirmware:2>
<ibfirmware:3>
<ibfirmware:4>
<ibfirmware:5>
<ibfirmware:6>

```

The following examples show use of srchtxt.

If msgfiles have been installed by mkmsg(1) in a locale named french, then you could display the entire set of text strings in the french locale (/usr/lib/locale/LC_MESSAGES/*) by typing:

```
cast srchtxt -l french
```

If a set of error messages associated with the operating system has been installed in the file UX in the french locale (/usr/lib/locale/french/LC_MESSAGES/UX), then, using the value of the LANG environment variable to determine the locale to be searched, you could search that file in locale for all error messages dealing with files.

```
cast% setenv LANG=french; export LANG
cast% srchtxt -m UX "[Ff]ichier"
```

If /usr/lib/locale/french/LC_MESSAGES/UX contained the following strings:
Erreur E/S\n
Liste d'arguments trop longue\n
Fichier inexistant\n
Argument invalide\n
Trop de fichiers ouverts\n
Fichier trop long\n
Trop de liens\n
Argument hors domaine\n
Identificateur supprim\n
Etreinte fatale\n

then the following strings will be displayed:
<UX:3>Fier inexistant\n
<UX:5>Trop de fichiers ouverts\n
<UX:6>Fichier trop long\n

If a set of error messages associated with the operating system has been installed in the file UX and a set of error messages associated with the database has been installed in the file ingress, both in the german locale, you could search for the pattern in both files UX and ingress in the german locale.

```
cast% srchtxt -l german -m UX "[Ff]ichier"
```

# ssh — Open Shell Client (Remote Login Program)

# Synopsis

```
/bin/ssh [-l login_name] [hostname | user@hostname] [command]
/bin/ssh [-c cipher_spec] [-x method] [-i identity_file] [-l login_name] [-o option] [-p port]
/bin/ssh [-L port:host] [-R port:host] [hostname | user@hostname] [command]
```

# Description

Use the ssh (Secure Shell), a program for logging into a remote machine and executing commands on that machine. ssh replaces rsh and provides encrypted communications between untrusted hosts over an insecure network. arbitrary TCP/IP ports can also be forwarded over the secure channel. ssh connects and logs into the specified hostname. Users must prove their identity to the remote machine with one of several methods, depending on the protocol used.

# SSH Protocol Version 1

For the first authentication method, if a user logs in from the remote machine and the user names are on both sides, the home directory on the remote machine contains a line containing the name of the client machine and the name of the user. This form of authentication is normally not allowed by the server because it is not.

The second (primary) authentication method is the password method combined that if the login would be permitted by $HOME/.ssh/authorized_keys, $HOME/.ssh/authorized_keys, /etc/ssh/known_hosts, and, additionally, the server can verify the client's host key (see /etc/ssh/known_hosts in "Edit Status" on page 1325), then only login is permitted. This authentication method closes holes for IP spoofing, DNS spoofing, and routing spoofing.

Note — /etc/hosts, $HOME/.ssh, and the login/rsh protocol in general, are inherently insecure and should be disabled if security is desired.

As a third authentication method, ssh supports RSA-based authentication. The scheme is based on public-key cryptography. Cryptosystems are available where encryption and decryption are done with separate keys, and it is not possible to derive the decryption key from the encryption key. RSA is one such system. The idea is that each user creates a public/private keypair for authentication purposes. The server knows the public key, and only the user knows the private key. $HOME/.ssh/authorized_keys lists the public keys that are permitted for logging in. When the user logs in, ssh tells the server which keypair it would like to use for authentication. The server checks whether this is permitted, and if so, sends the user (actually the ssh running on behalf of the user's key) a challenge in the form of a random number, encrypted by the user's key. The challenge can be decrypted with the private key, proving that the user knows the key but without disclosing the private key to the server.

ssh implements the RSA authentication protocol. The user creates or her RSA keypair by running ssh-keygen(1). This command stores the private key in $HOME/.ssh/id_rsa and the public key in $HOME/.ssh/id_rsa.pub in the user's home directory. The user should then append the contents of the identity.pub to $HOME/.ssh/authorized_keys on the remote machine (the file corresponds to the $/.ssh/hosts file, and has one key per line, though the lines can be very long). After this, the user can log in without giving the password. RSA authentication is much more secure than passwords.

Most convenient way to use RSA authentication is with an authentication agent. If other authentication methods fail, ssh prompts the user for a password. The password is sent to the remote host for checking. However, because all communications are encrypted, the password cannot be seen by someone listening on the network.

# SSH Protocol 2

When a user connects with the protocol 2, different authentication methods are available. At first, the client attempts to authenticate with the public key method. If this method fails, password authentication is tried.
The public key methods similar to RSA authentication, described in the previous section, that the DSA algorithm is used instead of the RSA algorithm. The client uses the private DSA key $HOME/.ssh/id_dsa to sign the session identifier and sends it to the server. The server checks whether the matching public key is listed in $HOME/.ssh/authorized_keys and grants access if the key is found and the signature is correct. The session identifier is derived from a shared Diffie-Hellman value and is known only to the client and the server.

Protocol 2 provides additional mechanisms for confidentiality (the traffic is encrypted with 3DES, Blowfish, CAST128, or Arfour) and integrity (hmac-sha, hmac-md5). Notice that protocol 1 has a strong mechanism for ensuring the integrity of the connection.

If public key authentication fails or is not available, a password can be sent to the remote host for proving the user's identity. This protocol 2 implementation does not support Kerberos or SSH authentication.

# Login Session and Remote Execution

When the user's identity has been accepted by the server, the server executes the given command or logs in to the machine and gives the user a normal shell on the remote machine. All communication with the command or shell is automatically encrypted.
