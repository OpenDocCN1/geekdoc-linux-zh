
Each of these rights can be granted to any one of four different categories.

- owner Grant a right to the owner of an object. The owner is the NIS+ principal identified in the owner field. The owner can be changed with the nischown(1) command. Note that if the owner does not have modification access rights to the object, he cannot change any access rights to the object unless he has modification access rights to its parent object.

- group owner Grant a right to the group owner of an object. This grants the right to any principal that is identified as a member of the group associated with the object. The group owner can be changed with the nischgrp(1) command. The object owner need not be a member of this group.

- world Grant a right to everyone in the world. This grants the right to all clients who have authenticated themselves with the service.

- nobody Grant a right to the nobody principal. This has the effect of granting the right to any client that makes a request of the service, regardless of whether the client is authenticated.

Note that for bootstrapping reasons, directory objects that are NIS+ domains, the org_dir subdirectory, and the cred table within that subdirectory must grant access to the nobody principal. This permission makes navigation of the namespace possible when a client is in process of locating its credentials. Granting this access does not enable the contents of other tables within org_dir to read (such as the entries in the password table) unless the table itself gives "real" access rights to the nobody principal.

## Directory Authorization

Additional capabilities grant access rights to clients for directories. These rights are contained within the object access rights (OAR) structure of the directory. This structure enables the NIS+ service to grant rights that are granted by the directory object obtained of a specific type.

An example of this capability is a directory object that does not grant access to all clients but does create access in the OAR structure for objects of type group to clients who are members of the NIS+ group associated with the directory. In this, the only objects that could be created as children of the directory would have of the type group.

Another example is a directory object that grants access only to the owner of the directory and then additionally grants access through the OAR structure for objects of type table, link, group, and private to any member of the directory's group. The group gains nearly complete access to the group with the exception of creating subdirectories. The creation of new NIS+ domains are restricted because creating both requires creating groups_dir and org_dir subdirectory.

> Note — There is no command-line interface to set or change the OAR of the directory object.

## Table Authorization

As with directories, additional capabilities are provided for granting access to entries within tables. Rights granted to a client by the access rights field in a table object to the table object and all of the entry objects "contained" by that table. If an access right is not granted by the table object, it can be granted by an entry within the table. This authorization holds for all rights except create.

For example, a table cannot grant access to a client performing an nis_list(3L) operation on the table. However, the access fields of entries within that table can grant read access to the client. Note that access rights in an entry are granted to the owner or group owner of the entry and not the owner or group of the table. When the list operation is performed, all entries to which the client has read access are not returned. Those entries that do not grant read access the search criteria grant access to the client making the request, no entries are returned and the result status NIS_NOTFOUND error code.

Access rights are granted by the fields in an entry are granted for the entry. However, in the table object, an additional set of access rights is maintained for each column in the table. These rights apply to the equivalent column in the entry. The rights are used to grant access when neither the owner nor the entry grants access. The access rights in a column specification apply to the owner or group owner of the entry instead of the owner and group owner of the table object.

When a read operation is performed, if read access is not granted by the table and is not granted by the entry but is granted by access in columns, that entry is returned with the correct values in columns and the string *NP in columns where read access is not granted.

As an example, a client who has performed a list operation on a table that does not grant read access to. Each entry object that satisfied the search criteria by the client is examined to see if it grants read access to the client. If it does, it is included in the returned result. If it does not, then each column is checked to see if it grants read access to the client. If any columns grant read access data in columns are returned. Those that do not grant read access have their contents replaced by the string *NP. If none of the columns grant read access, then the entry is not returned.

## Protocol Operation Authorization

NIS+ operations have implied access control through the permissions on the objects that they manipulate. For example, to read an entry in a table, you must read permission on that entry. However, NIS+ operations by default perform no access checking at all and so are allowed for everyone.
