The real-time scheduling policy is a fixed-priority policy. The scheduling priority of a real-time process never changes except as the result of an explicit request by the user/application to change the rtpri value of the process.

For processes in the real-class time, the rtpri value is, for all practical purposes, equivalent to the scheduling priority of the process. The rtpri value completely determines the scheduling priority of a real-time process relative to other processes within its class. Numerically higher rtpri values represent higher priorities. Because the real-class controls the highest range of scheduling priorities in the system, it is guaranteed that the runnable real-time process with the highest rtpri value is always selected to run before any other process in the system.

In addition to controlling priority, priocntl controls the length of the time quantum allocated to processes in real-class. The time quantum specifies the maximum amount of time a process can consume assuming that it does not complete or enter a resource or event wait (sleep). Note that if another becomes runnable at a higher priority, the currently running process can be preempted receiving its full time quantum.

The following command displays the real-time priority and time quantum (in millisecond resolution) for each real-time process in the set specified by idtype and idlist.

```
priocntl -d [-i idtype] [idlist]
```

You can use any combination of -p and -t options with priocntl -s or priocntl -e for the real-class time. If you omit an option and the process is currently real-time, the associated parameter is unaffected. If you omit an option when changing the class of a process to real-time from other class, the associated parameter is set to a default value. The default value for rtpri is 0, and for the time quantum depends on the value of rtpri and on the system configuration; see rt_dtopt().

Using the -rtquantum, you can optionally specify a resolution with the -r option. If you specify no resolution, millisecond resolution is assumed. If you specify it must be integer between 1 and 1,000,000 inclusive and the resolution is used in microseconds. For example, specifying -r 100 sets the resolution to one-hundredths-of a second and the resulting time-quantum length to one-tenth-of-a-second (10/100). You can then specify very fine (nanosecond) resolution, the time quantum is limited by the system to the next integer multiple of the system clock's resolution. Requests for time quanta of 0 or greater than the (typically very large) implementation-specific maximum quantum result in an error.

You can use the real-time quantum-signal in the Solaris 9-release to notify runnable processes about the consumption of their time quantum. Those processes, which are monitored by the real-time quantum signal, receive the signal when the time quantum expires. The default value (0) of the time quantum tsig sends no signal delivery. A positive value triggers the delivery of the signal specified by the value. Kill (1) when operating on signals, the -tsig option is also able to handle symbolically signals like XCPU or KILL.
