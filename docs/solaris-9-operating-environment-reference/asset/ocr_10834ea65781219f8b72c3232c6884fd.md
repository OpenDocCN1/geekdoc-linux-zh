/etc/cron.d/cron.deny.

+   * If neither file exists, starting with the Solaris 8 release, only a user with the
solaris.jobs authorization is allowed to submit a job.

Note that the rules for allow and deny apply to root only if the allow/deny files exist. allow/deny files consist of one user name per line.

# crontab Format

A crontab file consists of lines of six fields each. The fields are separated by spaces or tabs. The first five fields are integer patterns that specify the following:

+   * Minute (0-59).
* Hour (0-23).
* Day of the month (1-31).
* Month of the year (1-12).
* Day of the week (0-6=Sunday).

Each of these patterns can be an asterisk (meaning all legal values) or a list of elements separated by commas.

An element is a number or two numbers separated by a dash (meaning an inclusive range). Note that the specification of days can be made by two fields (day of the month and day of the week). Both are adhered to if specified as a list of elements.

The sixth field of a line in crontab is a string that is executed by the shell at the specified times. A % character in this field (unless escaped by \) is translated to a newline character.

Only the first (up to a percent %) or end of line) of the command field is executed by the shell. Other lines are made available to the command as standard input. Any line beginning with a hash (#) is a comment and is ignored. The file does not contain blank lines.

The shell is invoked from a HOME directory with an arg sh. Users who want to have .profile must explicitly do so in the crontab file. cron supplies a default environment for every shell, defining HOME, LOGNAME, SHELL(/bin/sh), TZ, and PATH. The PATH variable for cron jobs is /usr/bin; cron jobs defaults to /usr/bin:/usr/bin. You can set the PATH in /etc/default/cron; see crontab(1).

Warning — If you inadvertently use the crontab command with argument(s) to get out. Use Control-D. This key sequence removes all entries in your crontab file. Exit with Control-C.

If a different user modifies another user's crontab file, resulting behavior may be unpredictable. The privileged user should first invoke sum(1) with the other user's login before making any changes to the crontab file.

When updating a user's crontab with the crontab command, first check for existing crontab entries that may be scheduled close to the time of the update. Such entries can be lost if the update process completes after the scheduled event.
