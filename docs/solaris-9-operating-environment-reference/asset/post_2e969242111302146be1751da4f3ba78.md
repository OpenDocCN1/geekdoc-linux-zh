# Patch Application

If you specify -c, -e, -n or -u options, patch interprets information within each hunk as a difference, an ed difference, or a normal difference. In the absence of any of these options, patch determines the type of difference on the basis of the format of information within the hunk.

For each hunk, patch begins to search for the place to apply the patch at the beginning of the hunk plus minus any offset in applying the previous hunk. If lines matching the hunk context are not found, patch scans forward and backward by at least 1,000 bytes for a set of lines that matches the hunk context.

If no place is found and it is a context difference, patch does another scan, ignoring the first and last line of context. If that fails, the first two and last two lines of context are ignored and another scan is made. Implementations search more extensively for installation locations.

If no location can be found, patch sends the hunk to the reject file. The rejected hunk is written in context-difference format regardless of the format of the patch file. If the input was a normal or ed style difference, the reject file can contain differences with zero lines of context. The line numbers on the hunk in the reject file can be different from the line numbers in the patch file because they reflect the approximate locations for the failed hunks in the new file instead of the old one.

If the type of patch is an ed diff, the implementation can accomplish the patching by invoking the ed command.

# pathchk — Check Path Names

# Synopsis

```
/usr/bin/pathchk [-p] path...
```

# Description

The pathchk command checks that one or more path names are valid (that is, they could be used to access or create a file without causing syntax errors) and that they are portable (that is, no file-name truncation results). More extensive portability checks are provided by the -p option.

By default, pathchk checks each component of each path operand based on the underlying file system. A diagnostic is written for each path operand that:

- Is longer than PATH_MAX bytes.
- Contains any component longer than NAME_MAX bytes in its containing directory.
- Contains any component in a directory that is not searchable.
- Contains any character in any component that is not valid in its containing directory.

The format of the diagnostic message is not specified but indicates the error detected and the corresponding path operand.

It is not considered an error if one or more components of a path operand do not exist as long as a file matches the path name specified by the missing components could be created and such a file does not violate any of the checks specified.

# Options

- -p Instead performing checks based on the underlying file system, a diagnostic for each path operand that:

- Is longer than _POSIX_PATH_MAX bytes.
- Contains any component longer than _POSIX_NAME_MAX bytes.
- Contains any character in any component that is not in the portable file-name character set.

# Operands

- path A path to be checked.

# Usage

largefile(5) for the description of the behavior of pathchk when encountering greater than or equal to 2 Gbytes (2**31 bytes).

The following example verifies that a user-supplied path specifies a readable file and that the application can create a file extending the given path without truncation and without overwriting any existing file.

```
case $ - in
    "C*")
        reset=""
        reset="set C"
    set -C;
nesac
test -r "$path" && pathchk "$path.out" &&
rm "$path.out" > "$path.out"
if [ $? -ne 0 ]; then
    printf "%s not found or %s fails \ncreation checks. %s %s" "$0" "$path"
    reset # reset the noclobber option in case a trap
    # on EXIT depends on it
    exit 1
fi
```

```
$reset PROCESSING < "$path" > "$path.out"
```

The following assumptions are made in the previous example.

- * PROCESSING replaces the code that is used by the application to use $path once it is verified that $path.out works as intended.
- The state of the noclobber option is unknown when this code is invoked and should be set on exit to the state it was in when this code was invoked. (The reset variable is used in this example to restore the initial state.)
- The usage of rm "$path.out" > "$path.out". has already verified, at this point, that $path.out is not truncated.
- With the noclobber option set, the shell verifies that $path.out does not already exist before invoking rm.
- If the shell succeeds in creating $path.out, it removes it so that the application can create the file again in the PROCESSING step.
- If the PROCESSING step expects the file to exist already when it is invoked, replace rm "$path.out" > "$path.out" with > "$path.out", which verifies that the file did not already exist but leaves $path.out in place for use by PROCESSING.

# Description

The pax (portable archive exchange) command provides better portability for POSIX-compliant systems than the tar or cpio command. Use the pax command to copy files, special files, file systems that require multiple tape volumes, or files you want to copy and from POSIX-compliant systems. Disadvantages of the pax command are that it is not aware of file-system boundaries and that the full path-name length cannot exceed 255 characters.

# Modes of Operations

The action to be depends on the presence of the -r (read) and -w (write) options. The four combinations of -r and -w are referred to as the four modes of operation: list, read, write, and copy modes, which correspond to the form shown in the Synopsis.

- list

When you specify neither -r nor -w, write to the standard output the names of the members of the archive file read from the standard input with path names matching the specified patterns. If a named file is of type directory, write the file hierarchy rooted at that file as well.
