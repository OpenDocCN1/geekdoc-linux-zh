# Korn Shell wait

When the shell starts an asynchronous list, the process ID of the last command in each element of the asynchronous list becomes known in the current shell execution environment.

If you invoke the wait command with no operands, the command waits until all process IDs known to the invoking shell have terminated and exited with an exit status of 0.

If you specify one or more pid operands represent known process IDs, the wait command waits until all of them have terminated. If you specify one or more pid operands represent unknown process IDs, wait treats them as if they were known process IDs that exited with exit status 127. The exit status returned by the wait command is the exit status of the process requested by the last pid or job-id operand.

The known process IDs are applicable only for invocations of wait in the current shell environment.

# Operands

+   - pid: The unsigned decimal process ID of a command to be waited for.

+   - job-id: A job control ID that identifies a background process group to be waited for. The job ID notation is applicable only for invocations of wait in the current shell execution environment and only on systems that support the job control options.

# Usage

On most implementations, wait is a shell built-in command. If you call wait in a subshell or separate command execution environment, such as one of the following, it returns immediately because there are no process IDs to wait for in those environments.

```
(wait)
nohup wait...
 -exec wait \
```

# Examples

Although the exact value used when a process is terminated by a signal is unspecified, if it is known that a signal terminated a process, a script can still figure out which signal is using kill. The following example uses a script to identify the status.

```
sleep 1000&
pid=$$
 -kill $pid
wait
echo $pid was terminated by a SIG$(kill -1 $?) signal.
```

For /bin/ksh and /usr/pg4/bin/sh, if you run the following sequence of commands in less than 31 seconds, wait returns the exit status of the second sleep in the pipeline.

```
$ sleep 31 & 
sleep 257
[1] 450
$ jobs -1 %%
[1] + 450      Running sleep 257 | sleep 31 &
$ wait %1
```
