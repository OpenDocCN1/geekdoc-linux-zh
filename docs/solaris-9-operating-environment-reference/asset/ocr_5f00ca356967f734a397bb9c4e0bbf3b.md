# mdb

```
addr [len] ::wp [+ -dTest] [-rwx] [-c cmd] [-n count]
addr [len] :a [-c cmd...]
addr [len] :p [-c cmd...]
addr [len] :w [-c cmd...]
```

Set a breakpoint at the specified address. You can set the length of the watched region in bytes by specifying an optional repeat count preceding the demd. If you set no explicit length, the default is one byte. The :wp demand allows you to configure the watchpoint to trigger on any combination of read (-r), write (-w), or execute (-x). The -d, -D, -s, -t, -T, and -n options have the same meaning as for :evset demd on page 833. The :a demand sets a read watchpoint at the specified address. The :p demand sets an access watchpoint at the specified address. The :w demand sets a write access watchpoint at the specified address. The arguments following the a, :p, and :w demands are concatenated to form the callback string. If this string contains metcharacters, you must quote it. New in the Solaris 9 release.

```
::xdata
```

List the data buffers exported by the current target. Data buffers represent information associated with the target that cannot be accessed through standard target facilities (that is, an address space, symbol table, or register set). These buffers can be consumed by demd; for more information, refer to the Solaris Modular Debugger Guide.

Delete all event species from the list of traced event species. You can also delete event species with ::delete. New in the Solaris 9 release.

# Warnings

# Use of the Error Recovery Mechanism

The debugger and its mdb execute in the same address space, and it is possible that a buggy demd can dump core or otherwise behave. The mdb capability, described in "Signal Handling" on page 828, provides a limited recovery mechanism for these situations. However, mdb cannot know definitively whether the debugger has corrupted its own state or the debugger's global state. Therefore, a resume operation cannot guaranteed to be safe or prevent a subsequent crash of the debugger. The safest course of action following a resume is to save any important debug information and then quit and restart the debugger.

# Use of the Debugger to Modify the Live Operating System

The use of the debugger to modify (that is, write to) the address space of a live, running operating system is extremely dangerous and can panic a system if the user damages a kernel data structure.
