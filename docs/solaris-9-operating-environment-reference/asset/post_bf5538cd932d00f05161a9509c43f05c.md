# Timesharing Class

The timesharing policy provides for a fair and effective allocation of the CPU resource among processes with varying CPU consumption characteristics. The objectives of the timesharing policy are to provide good response time to interactive processes and good throughput to CPU-bound jobs while providing a degree of user or application control over scheduling.

The timesharing class has a range of timesharing priority (tspri) values which are assigned to processes within the class. User priorities range from -xo to +x where the value of x is configurable. You can display the priority for a specific installation with priocntl -l.

The user priority provides some degree of user or control over the scheduling of processes in the timesharing class. Raising or lowering the tspri value of a process in the timesharing class raises or lowers the scheduling priority of the process. However, a higher tspri value runs before one with a lower tspri value, because the tspri value is just one factor to determine the scheduling priority of a timesharing process. The system dynamically adjust the internal scheduling priority of a timesharing process based on other factors such as recent CPU usage.

In addition to the limits on user priority (displayed with priocntl -l), a per-process priority limit (tsprilim) specifies the maximum tspri value that can be set for a given process.

The priocntl -d [idtype] [idlist] command displays the user priority and user priority limit for each process in the set specified by idtype and idlist.

Any timesharing process can lower its own tspilim (or that of another process with the same user ID). Only a timesharing process with superuser privilege can raise tspilim. When changing the class of a process to timesharing from some other class, you must have superuser privilege to set the tspri to a greater value.

Any timesharing process can set its own tspri (or that of another process with the same user ID) to any value less than or equal to the tspilim. Attempts to set the tspri above the above (and/or the tspilim below the tspri value) sets the tspri equal to the tspilim.

You can use any combination of the -m and -p options with priocntl -s or priocntl -t for timesharing class. If you omit an option and the process is currently timesharing, the associated parameter is normally unaffected. The exception is that you can omit the p option and use -m to set the current tspri. In this case, the tspri is equal to the tspilim below set. If you omit an option when changing the class of a process to timesharing from some other class, the associated parameter is set to a default value. The default value for tsprilim is 0, and the default for tspri is to be equal to the tspilim value that is being set.

The timesharing user priority and user priority limit are inherited across the fork(2) and exec(2) system calls.

# Interactive Class

The interactive scheduling policy provides for a fair and effective allocation of the CPU resource among processes with varying CPU consumption characteristics while providing good responsiveness for user interaction. The objectives of the interactive policy are to provide good response time to interactive processes and good throughput to CPU-bound jobs. You can change the priorities of processes in the interactive class in the same way as in the timesharing class, although modified priorities continue to be adjusted for good responsiveness for user interaction.

In the default configuration, a runnable real-time process runs before any other process. Therefore, inappropriate use of real-time processes can have a dramatic negative impact on system performance.

If an idlist is present, it must appear after the last command and the elements of the list must be separated by white space. If no idlist is present, an idtype argument of pid, ppid, sid, class, uid, or gid specifies the process ID, parent process ID, process group ID, session ID, user ID, or group ID of the priocntl command itself.

The following command displays the class and class-specific scheduling parameters of the process(es) specified by idtype and idlist.
`priocntl -d [-idtype] [idlist]`

The following example uses the -d option with no arguments.
`$ priocntl -d`

| PID | IAUPRIM | IAUPRI | IMODE |
| :--- | :--- | :--- | :--- |
| 422 | 0 | 1 | |

`$ priocntl`
The following command sets the class and class-specific parameters of the processes to the values given on the command line.
`# priocntl -s [-class] [class-specific options] [-idtype] [idlist]`

The -c option specifies the class to be set. (The valid class arguments are RT for real-time, TS for timesharing, or IA for interaction). The iaupril interactive user priority is equal to tsupri. The interactive per-user priority limit, iaupril, is equal to tsuprilim.

Interactive processes that have the iamode (interactive mode) bit set are given a priority boost of 10, which is factored into when a process's priority is adjusted. This feature is used by the X Window System, which sets this bit for processes that run inside of the active window to give them a higher priority.

# FairShare Class

The fair-share scheduling policy—new in the Solaris 9 release—provides a fair allocation of CPU resources among projects, independently of the number of processes they use. Projects are given "shares" to control their entitlement to CPU resources. Resource usage is remembered over time, so that entitlement is reduced for heavy usage and increased light with respect to other projects. CPU time is scheduled processes according to their owners' entitlements, independently of the number of processes each project owns.

The FSS scheduling class supports the notion of per-user priority and priority limit for compatibility with the time-share scheduler. The fair-share scheduler tries to provide an evenly graded effect across the whole range of priorities.

# Fixed-Priority Class

The fixed-priority class—new in the Solaris 9 release—provides a fixed-priority preemptive-scheduling policy for processes requiring that the scheduling priorities not dynamically adjusted by the system and that the user or application has control of the scheduling priorities.

The fixed-priority class shares the same range of scheduling priorities as the timesharing class, by default. The fixed-priority class has a range of fixed-priority user priority (fsupri) values that can be assigned to processes within the class. User priorities range from 0 to x, where x is configurable. You can display the range for a specific installation with the priocntl -l command.

The user priority provides user and application control over the scheduling of processes in the fixed-priority class. For processes in the fixed-priority class, the fsupri value is, for practical purposes, equal to the scheduling priority of the process. The fsupri value completely completes the scheduling priority of a fixed-priority process relative to other processes within the class. Numerically higher fsupri values represent higher priority.

In addition to the strict limits on user priority (displayed with priocntl -l command, a process-priority limit (fsupril) sets the maximum fsupri value that can be set for a process.

Any fixed-priority class can lower its own fsuprim or that of another process with the same user ID. Only with superuser privilege can raise a fsuprim. When the class of a process is changed to fixed priority from some other class, superuser privilege is required to set the initial fsuprim to a value greater than zero.

Any fixed-priority class can lower its own fsupri (or that of another process with the same user ID) to any value less than equal to the process's fsupri. Attempts to set the fsupri above the fsuprim set the fsupril below the fsupri set the fsupri equal to the fsuprim.

In addition to providing control over priocntl provides control over the length of the time quantum allotted to processes in the fixed-priority class. The time quantum specifies the maximum time a process can run before surrendering the CPU, assuming that it does not complete or enter a resource or wait state (sleep). Notice that if another process becomes at a higher priority, the current running process can be preempted before receiving its full quantum.

You can use the -m, -p, and -t options with priocntl -s for currently fixed-priority class. If you opt and the process is currently fixed, the associated parameter is normally unaffected. The exception is that you can opt the -p and use the -m option to set a fsupril below the current fsupri. In this case, the fsupri is set equal to the fsupril that is being set.

If you opt when changing the class of a process to fixedpriority from some other class, the associated parameter is set to a default value. The default value for fsupri is 0 to set it equal to the fsuprim value that is in configuration. See fx-dbctl(4).

You can change the time quantum of processes in the fixed-priority class the same way as in the real-time class.
