# Limitations on Examining Crash Dump Files

mdb does not provide support for examining process cores that were generated by a release of Solaris preceding 2.6. If a corefile from one operating system release is examined on a different operating system release, the runtime-link debugging interface (librtld_db) may not be able to initialize. In this case, symbol information for shared libraries is not available. Furthermore, because shared mappings are not present in user corefiles, the text section and read-only data of shared libraries may not match the data that was present at the time it was dumped. Core files from Solaris Intel systems cannot be examined on Solaris SPARC systems, and vice versa.

# Relationship Between 32-bit and 64-bit Debugger

mdb provides support for debugging both 32-bit and 64-bit programs. Once it has examined the target and its data model, mdb automatically reexecutes if necessary. This simplifies the task of writing debugger modules, because modules use the same data model as the primary target. You can use the 64-bit debugger only to debug 64-bit target programs. The 64-bit debugger can be used only on a system that is running a 64-bit operating environment.

The debugger may also need to reexecute itself when debugging a 32-bit process that executes a 64-bit process or vice versa. The handling of this situation is discussed in more detail in the next section.

# Interaction with exec

When a process performs a successful exec(2), the behavior of the debugger is controlled by the :set -o follow_exec_mode. If the debugger and victim process have the same data model, then the stop and follow modes determine whether mdb automatically continues execution or returns to the debugger prompting the execution. If the debugger and victim process have a different data model, then the follow automatically reexecutes the mdb binary with the appropriate data model and reattaches to the process, still stop on return from the exec. Not all debugger state is preserved across this reexecution.

If a 32-bit process executes a 64-bit program, then stop returns to the command prompt but the debugger is no longer able to examine the process because it is now using the 64-bit data model. To resume debugging, execute the :release -a dcmdb, and then execute mdb -p to reattach the 64-bit debugger to the process.

If a 64-bit process executes a 32-bit program, then stop returns to the command prompt, but the debugger provides only limited capabilities for examining the new process. All built-in dcmds work as advertised, but loadable dcmds do not because they perform no data model conversion of structures. Release and reattach the debugger as described in the previous paragraph to restore full debugging capabilities.

# Interaction with Job Control

If the debugger is attached to a process that is stopped by job control (that is, it is stopped in response to SIGTSTP, SIGTIN, or SIGTOU, the process may not be able to be running again when it is continued by a continue dump). If the victim process is a member of the same session (that is, it shares the same terminal as mdb), mdb tries to bring the associated process group to the foreground and continue the process with SIGCONT. When mdb is detached from a process, it restores the process to the background before exiting. If the process is not a member of a same session, mdb cannot safely bring the process to the foreground, so it continues the process with respect to the debugger, but the process remains stopped by job control. mdb prints a warning in this case, and you must issue an fg command from the appropriate shell to resume the process.

# Process Attach and Release

When mdb attaches to a running process, the process is stopped and remains stopped until the continue dump is applied or the debugger quits. If you enable the -nostop option before attaching the debugger to a process -p or before issuing :a command, mdb attaches to the process but does not stop. While the process is still running, you can inspect it as usual (albeit with inconsistent results) and enable breakpoints or other tracing flags. If you execute the :c : dump will force the process to stop. While the process is running, mdb waits for the process to stop. If no traced event occurs, you can send an interrupt (:c) after :c or to force the process to stop and return control to the debugger.

mdb releases the running process (if any) when you execute the :r::release,run,sq, or :quit mdb or when the debugger terminates the process as result of EOF. If the process was originally created by the debugger with :r or is forcibly terminated by SIGKILL when it is released. If the process was already running before mdb was attached to it, the process is set running again when it is released. A process can be released and left stopped and abandoned with the :release -a option.

# Symbolic Debugging Information

The :offset, :print, and :sizeof dmcmds require one or more objects contained compressed symbolic debugging information for use with mdb. This information is currently available only for certain Solaris kernel modules.

# Options

- -A Disable automatic loading of mdb modules. By default, mdb tries to load debugger modules corresponding to the active shared libraries in the user process or corefile or to the loaded kernel modules in the operating system or an operating system crash dump.
- -f Force raw file debugging mode. By default, mdb tries to infer whether the object and corefile refer to a user executable and dump to a pair of operating system crash dump files. If mdb cannot infer the type, it opts to examining the files as plain binary data. The -f option forces mdb to interpret the arguments as a set of rows to examine. New in the Solaris 9 release.
- -F Forcibly take over the specified user process, if necessary. mdb refuses to attach to a user process that is already under the control of another debugging tool as truss(1). With the -F option, mdb attaches these processes anyway. This option can produce unexpected interactions between mdb and other tools to control the process.
- -I path Set the default path for locating macro files. Macro files are read by the $< mcdms. The path is a sequence of directory names delimited by colon (:) characters. The -I include path and -L library path can contain any of the following tokens.
    - %i Expand to the current instruction set architecture (ISA) name (sparc or sparcv9).
    - %o Expand to the old value of the path being modified. This token is useful for appending or prepending directories to an existing path.
    - %p Expand to the current platform string (either -i or the platform string stored in the process corefile or crash dump).
    - %r Expand to the path name of the root directory. With the -R option, you can specify an alternative root directory with the -R option. The root directory is derived dynamically from the path to the mdb executable.
    For example, if you execute /bin/mdb, the root directory is /. If you execute /net/hostname/bin/mdb, the root directory is derived as /net/hostname.
    - %t Expand to the name of the current target. This name is either the literal string proc (a user process or user process corefile) or km (a kernel dump or the live operating system).
