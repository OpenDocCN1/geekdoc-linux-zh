If a pseudo terminal has been allocated (normal login session), the user can disconnect with ~, and suspend ssh with ~Z. All forwarded connections can be listed with ~. If the session blocks while waiting for X11 or TCP/IP connections to terminate, ssh can be put in background with &, although you should not use this command while the server is active because it can hang the shell. All available escapes can be listed with ~?.

A single character can be sent as -- (or by following the tilde with a character other than those described above). The escape character must always follow a newline to be interpreted as. You can change the escape character in configuration files or on the command line.

If no TTY has been allocated, the session is transparent and you can reliably transfer binary data. On most systems, setting the escape character to none also makes the session transparent even if a TTY is used.

The session terminates when the command or shell in the remote machine exits and all X11 and TCP/IP connections have been closed. The exit status of the remote process is returned as the exit of ssh.

# X11 and TCP Forwarding

If the user uses X11 (the DISPLAY variable is set), the connection to the X11 display is automatically forwarded to the remote side so that any X11 programs started from the shell (or command) go through the encrypted channel and so that the connection to the remote X server is made from the local machine. The user should not manually display. Forwarding of X11 connections can be configured on the command line or in configuration files.

The DISPLAY value set by ssh points to the server machine, but with a display number greater than zero. This behavior is normal, because ssh creates a "proxy" X server on the server machine for forwarding connections over the encrypted channel.

ssh also automatically sets up Xauthority to create a random authorization cookie, stores it in ~/.xauthority on the server, and verifies that any forwarded connections carry this cookie and replace it with the real cookie when the connection is opened. The real authentication cookie is never sent to the server machine (and no cookies are sent in plain text).

If the user uses an authentication agent, the connection to the agent is automatically forwarded to the remote side unless disabled on the command line or in a configuration file.

Forwarding of arbitrary TCP/IP connections ensures the secure channel can be established either on the command line or in a configuration file. One possible application of TCP/IP forwarding is to secure a secure connection to an electronic pulse. Another possible application is going through firewalls.

# Server Authentication

ssh automatically maintains and checks a database containing identifications for all hosts it has been used with. RSA host keys are stored in ~/.known_hosts in the user's home directory. Additionally, the file /etc/ssh/known_hosts is automatically checked for known hosts. New hosts are added to the user's file. If a host's identification changes, ssh warns about this change and disables password authentication to prevent a Trojan horse from getting the user's password. Another purpose of this mechanism is to prevent man-in-the-middle attacks that could otherwise be used to circumvent the encryption. You can use StrictHostKeyChecking to prevent logins to machines whose host key is not known or has changed.
