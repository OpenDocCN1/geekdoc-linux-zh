# proc tools — Proc Tools

# Synopsis

```
/usr/proc/bin/pflags [-r] pid | core...
/usr/proc/bin/pcred pid | core...
/usr/proc/bin/imap [-srx1F] pid | core...
/usr/proc/bin/plld [-F] pid | core...
/usr/proc/bin/psig [-n] pid...
/usr/proc/bin/pstack [-F] pid | core...
/usr/proc/bin/ptiles [-F] pid...
/usr/proc/bin/pwdx [-F] pid...
/usr/proc/bin/pstop pid...
/usr/proc/bin/prum pid...
/usr/proc/bin/pwait [-v] pid...
/usr/proc/bin/ptree -a [pid | user...]...
/usr/proc/bin/ptime command [arg...]
/usr/bin/pargs [-aeFx] [core]
```

Note — Starting with the Solaris 8 release, all of the proc tools were moved from /usr/proc/bin to /usr/bin. The tools in /usr/proc/bin are new links to those in the /usr/bin directory.

# Description

The proc tools are commands that exercise features of /proc (see proc(4)). Most of them take a list of process IDs (pid). The tools that process IDs also accept /proc/nid as a process ID, so you can use the expansion /proc/* to specify all processes in the system.

Starting in the Solaris 8 release, you can also apply some of the proc tools to cores (see core(4)). Those commands that can be applied to corefiles accept a list of process IDs or names of corefiles, or both.

- pargs: Print the command arguments (argv[]) environment variables, and auxiliary vector. In the new Solaris 9 release.
- pflags: Print the /proc tracing flags, the pending and held signals, and /proc status information for each lightweight process (lwp) in each process.
- pcred: Print the credentials (effective, real, and saved UIDs and GIDs) of each process.
- pfiles: Report stat(2) and fcntl(2) information for all open files in each process.
- plld: List the dynamic libraries linked into each process, including shared objects explicitly attached by means of dlopen(3DL). See also ldd(1).
- pmap: Print the address space map of each process.
- prun: Set each process running (inverse of pstop).
- psig: List the signal actions of each process. See signal(3HEAD).
- pstack: Print a hex+symbolic stack trace for each lwp in each process.
- pstop: Stop each process (PR_REQUESTED stop).
- ptime: Time a command, such as the time(1) command, but using microsecond accounting for reproducible precision.
- ptree: Print the process trees containing the specified pid or users, with child processes indented from their respective parent processes. Take an argument of all digits to a process ID; otherwise, assume it is a user login name. Default is all processes.
- pwait: Wait for all of the specified processes to terminate.
- pwdx: Print the current working directory of each process.

The pfiles, pldd, pmap, and pwdx commands stop their target processes while inspecting them and reporting the results. While a process is stopped, it can do nothing.

# Options

- -a (ptree only): Include children of process 0.
- -a (pargs only): Print process arguments as contained in argv[]. New in the Solaris 9 release.
- -e (pargs only): Print process environment variables and values. New in the Solaris 9 release.
- -F: Force a grab of the target process even if another process has control.
- -l (pmap only): Print unresolved dynamic linker maps.
- -n (psig only): Display signal handler addresses instead of name. New in the Solaris 9 release.
- -r (plags only): If the process is stopped, display its machine registers.
- -r (pmap only): Print the process's reserved addresses.
- -s (pmap only): Print page size of hardware translations used. New in the Solaris 9 release.
- -v (pwait only): Report each termination to standard output.
- -x (pmap only): Print process resident/shared/mapping details.
- -x (pargs only): Print process auxiliary vector. New in the Solaris 9 release.

# Usage

The pfiles, pldd, pmap, and stack proc tools stop their processes while inspecting them and reporting the results. A process can do nothing while it is stopped. For example, if the X server is inspected by one of these proc running in a window under the X server's control, the whole system can become deadlocked because the proc tool would be trying to print its results to a window that cannot be logged. Logging from another system with rkill(1) and killing the offending proc tool would clear the deadlock in this case.

Exercise caution using the -F option. Imposing two processes on one victim process can lead to chaos. Safety is assured only if the primary controlling process, typically a debugger, has stopped the victim process and the primary controlling process is doing nothing at the moment of application of the proc tool in question.

Starting with the Solaris 8 release, some of the proc tools can also be applied to corefiles. A corefile is a snapshot of a process's state and is produced by the kernel before terminating a process with a signal or with the gcore(1) command. Some of the proc tools may need to derive the name of the executable corresponding to the process that dumped core or the names of shared libraries associated with the process. These files are needed, for example, to provide symbol information for pstack(1). If the proc tool in question is unable to locate the needed executable or shared library, some symbol information is unavailable for display. Similarly, if a corefile is examined on one different operating system, the runtime debugging interface (librt1d_db) may not be able to initialize. In this case, symbol information for shared libraries is not available.
