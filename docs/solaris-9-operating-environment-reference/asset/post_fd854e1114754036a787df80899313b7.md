gethrime()

    mutex_lock(&lock);
    if (this_time <= last_time) {
        this_time = ++last_time;
    } else
        last_time = this_time;
    mutex_unlock(&lock);
return (this_time);

# Grammar

Specify probes as a list of space-separated selectors. Selectors are of the form:
attribute=value

```
(see TNF_PROBE(3NF). The attribute= is optional. If you do not specify it, the default is keys=.
The attribute or value(generically called spec) can be any of the following:
```
IDENT | Any sequence of letters, DIGITS, _, \, ., % not beginning with a digit.
IDENT implies an exact match.
```

```
QUOTED_STR | Used to escape reserved words (any commands in the command language). QUOTED_STR implies an exact match and must be enclosed in single quotes ' ').
```

```
REGEXP | (1) regular expression pattern name. Enclose REGEXP in slashes / / . You can include a / a REGEXP by escaping it with a backslash \.
```

The following grammar explains the syntax.

```
selector_list := | /* empty */
selector_list selector
selector := | spec = opt */ /* white space around /
spec ::= | spec
spec ::= | IDENT |
QUOTED_STR |
REGEXP
```

The terminals in the above grammar are shown below.

```
IDENT = [a-zA-Z_\%]*([a-zA-Z0-9_\%]*)
QUOTED_STR = '\'[^']*' /* any string in single quotes */
REGEXP = '/[^*/' | /* a regex has to be in // // */
```

The following list shows the remaining grammar that is needed to understand the syntax of the command language (defined in next section).

```
filename := | QUOTED_STR /* QUOTED_STR defined above * /
spec_list := | /* empty */ /
spec_list spec /* spec defined above * /
fcn_handle := | &IDENT /* IDENT defined above * /
set_name := | SIDENT /* IDENT defined above * /n
```

# List History # list probes control history

The list history command displays a list of probe control commands previously issued in the tracing session, for example, connect, clear, trace, disable. Commands in the history are executed whenever a new shared object is brought into target program by diopen(3).

# Process Control

continue # resume the target process
quit kill # quit prex, kill target
quit resume # quit prex, continue target
quit suspend # quit prex, leave target suspended
quit # quit prex, continue or kill target

The default prex continues the target process if prex is attached to it. Instead, prex has started the target program, prex kills the process.

# dlopen'ed Libraries

Probes in shared objects that are brought in by dlopen(3) are automatically set up according to the common history of prex. When a shared object is removed by a dclose(3), prex again needs to refresh its understanding of the probes in the target program. This requirement implies that there is more work to do for dlopen(3) and they take slightly longer. If you are not interested in this feature and do not want to interfere with dlopen(3) and dclose(3), detach prex from the target to inhibit this feature.

# Signals to Target Program

prex does not interfere with signals that are delivered directly to the target program. However, prex receives all signals normally generated from the terminal, for example, Control-C(SIGINT), and Control-Z(SIGSTOP), and does not forward them to the target program. To signal the target program, use the kill(1) command from a shell.

# Interactions with Other Applications

Process managing simultaneously like dbx, truss(1), and prex cannot operate on the same target program simultaneously if one is controlled by another application. You can trace and debug a program serially by the following method: first, attach prex to target (or start through prex), set up the probes by using the command language, and then type quit. You can then attach dbx to the suspended process and debug it. You can suspend the target by sending it SIGSTOP signal, and then by typing resume to invoke prex. In this case, you should also send a SIGSIGNAL when invoking prex on the stopped process, or else dbx hangs.

# Failure of Event-Writing Operations

There are few failure points, as system call failures, that are possible when writing events to a trace file. These failures result in a failure code being set in the target process. The process continues normally, but no data records are written. Whenever you Control-C to prex to get a prex prompt, prex checks the failure code in the target and informs you if there was a tracing failure.

# Target Executing a fork or exec

If the target program does a fork(2), any probes that the child encounters log events to the same trace file. Events are annotated with a process ID, so it is possible to determine which process each event came from. If the target itself (not any children it may) does an exec(2), prex detaches from the target and exits. You can reconnect with prex -p pid
