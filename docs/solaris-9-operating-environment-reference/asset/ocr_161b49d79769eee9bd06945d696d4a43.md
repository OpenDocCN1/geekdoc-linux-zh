Processes with positive fsupri values receive time slices less frequently than normal, whereas negative nice processes receive time slices more frequently than normal. Notice that user priorities do not interfere with shares. That is, changing a fsupri value of a process is not going to affect your project's overall CPU use, which relates only to the amount of shares it is allocated compared to other projects.

You can change the priorities of processes in the fair-share class in the same way as you in the time-share class.

# Fixed-Priority Class

The fixed-priority class—new in the Solaris 9 release—provides a fixed-priority preemptive-scheduling policy for processes requiring that the scheduling priorities not dynamically adjusted by the system and that the user or application has control of the scheduling priorities.

The fixed-priority class shares the same range of scheduling priorities as the timeshares class, by default. The fixed-priority class has a range of fixed-priority user priority (fsupri) values that can be assigned to processes within the class. User priorities range from 0 to x, where x is configurable. You can display the range for a specific installation with the priocnl -1 command.

The user priority provides user and application control over the scheduling of processes in the fixed-priority class. For processes in the fixed-priority class, the fsupri value is, for practical purposes, equal to the scheduling priority of the process. The fsupri value completely completes the scheduling priority of a fixed-priority process relative to other processes within the class. Numerically higher fsupri values represent higher priority.

In addition to the strict limits on user priority (displayed with priocnl -1 command, a process-priority limit (fsupril) sets the maximum fsupri value that can be set for a process.

Any fixed-priority class can lower its own fsuprim or that of another process with the same user ID. Only with superuser privilege can raise a fsuprim. When the class of a process is changed to fixed priority from some other class, superuser privilege is required to set the initial fsuprim to a value greater than zero.

Any fixed-priority class can lower its own fsupri (or that of another process with the same user ID) to any value less than equal to the process's fsupri Attempts to set the fsupri above the fsuprim set the fsupril below the fsupri set the fsupri equal to the fsuprim.

In addition to providing control over priocnl provides control over the length of the time quantum allotted to processes in the fixed-priority class. The time quantum specifies the maximum time a process can run before surrendering the CPU, assuming that it does not complete or enter a resource or wait state (sleep). Notice that if another process becomes at a higher priority, the current running process can be preempted before receiving its full quantum.

You can use the -m, -p, and -t options with priocnl -s for currently fixed-priority class. If you opt and the process is currently fixed, the associated parameter is normally unaffected. The exception is that you can opt the -p and use the -m option to set a fsupril below the current fsupri. In this case, the fsupri is set equal to the fsupril that is being set.

If you opt when changing the class of a process to fixed-priority from some other class, the associated parameter is set to a default value. The default value for fsupri is 0 to set it equal to the fsuprim value that is in configuration. See fx-dbctl(4).

You can change the time quantum of processes in the fixed-priority class the same way as in the real-time class.
