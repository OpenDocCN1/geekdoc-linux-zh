## true, false — Provide Truth Values

# Synopsis

```
/usr/bin/true
/usr/bin/false
```

# Description

true does nothing, successfully. false does nothing, unsuccessfully. They are typically used in a shell script sh as:

```
while true
  do
    command
  done
```

which executes command forever.

# Exit Status

- - true: 0.
- - false: A non-zero value.

## truss — Trace System Calls and Signals

# Synopsis

```
/usr/bin/truss [-fcaeildD] [- [tVx] [!]syscall,...] [-s [!]signal,...]
-mM [!]fault,...] [-rw] [!]fd,...] [-uU] [!]lib,...[:] [!]func,...] [-o outfile command | -p pid
```

# Description

The truss executes the specified command and produces a trace of a system calls it performs, the signals it receives, and the system faults it incurs. Each line of the trace output reports either the fault or signal name or the system call name with its arguments and return value(s). System call are displayed symbolically when possible, using definitions from relevant system headers; for any path-name pointer

# Notes

Some of the system calls described in Section 2 differ from the actual operating system interfaces. Do not be surprised by minor deviations of the trace output from the descriptions in Section 2.

Every system fault (except a page fault) results in the posting of a signal to the lightweight process that incurred the fault. A report of received signal immediately follows each report of system fault (except a page fault) unless that signal is blocked. The operating system enforces certain restrictions on tracing of processes. In particular, any command file (a.out) cannot be read by a user who cannot be traced by that; commands can be traced by superuser; truss loses control of any process that performs exec(). such processes continue normally, independently. To avoid controlling processes, truss does not trace a process that detects it being controlled by another process through /proc interface. This allows truss to be applied to proc-based debuggers as well as another instance of itself. The trace output contains characters under the assumption that standard stops are every positions. The trace output for multiple processes or for a multithreaded process (one that contains more than one lightweight process) is produced in strict time. For example, read() on a pipe may be reported before the corresponding write(). For any lightweight process (contains only one), the output is strictly ordered. Not all structures in all possible system calls are displayed with the -v option.

# Options

For those options that take a list, you can use the name as shorthand to specify all members of the list. If the list begins with !, the meaning of the option is negated (for example, exclude instead of trace). You can specify multiple occurrences of the same name in list, subsequent options (those the right) override previous ones (those the left).

- -a Show the argument strings that passed in each exec(1) system call. Count traced calls, faults, and signals displaying trace line-by-line. Produce a summary report after command terminates or when interrupted. If you also specify -f, include all traced calls, faults, and signals for child processes.

- -d Include a timestamp on each line of trace output. The timestamp is a field containing seconds.fraction at the start of a line. This value represents a time in seconds relative to the beginning of trace. The first line of trace output shows the base time from Epoch (see time(2)) and as a date string (see ctime(3)). Report the times that the event occurred. For all system calls, the event is the completion of the system call, not the start of.

- -D Include a time delta on each line of trace output. The value is a field containing seconds.fraction that represents the elapsed time for event since the last reported event by LWP. Specifically, for system calls, this value is the time spent within the system call.

- -e Show the environment strings that are present in exec(1) system call.

- -f Follow all children created by fork(2) or vfork(2), and include their signals, faults, and system calls in the trace output. Normally, only the first-level command or process is traced. Include the process ID with each line of trace output to indicate which process executed the system call or received the signal.

- -i Do not interruptible sleeping system calls. Certain system calls, such as open(2) on terminal devices or pipes can sleep for indefinite periods and are interruptible. Normally, truss reports such sleeping calls if they remain asleep for more than one second. The system call is reported again a second time when it completes. The -i option reports such system calls only once, when they complete.

- -l Include the ID of the responsible lightweight process with each line of trace output. If you also specify -f, include both the process ID and the lightweight process.

- -m [fault],... Specify system faults to trace or exclude. Trace those system faults specified in the comma-separated list. You can specify faults by name or number (see <sys/fault.h>). If the list begins with not symbol (!), exclude the specified faults from the trace output. Default is -m!page.

- -M [fault],... Show machine faults that stop the process. Add the specified faults to the set specified by -m. If one of the specified faults is incurred, leave the process stopped and abandoned (see -T option). Default is -M!all.

- -o outfile Specify file to be used for the trace output. By default, the output goes to standard error.

## truss

- -p pid Interpret the arguments to truss as a list of process IDs for existing processes (see ps(1)) instead of as a command to be executed. truss takes control of each process and begins tracing it, provided that the user ID and group ID of the process match those of the user or that user is superuser. You can also specify processes by their names in the /proc directory, for example, /proc/12345.

- -r [!] Show the full contents of the I/O buffer for each read() on any of the specified file descriptors. Format the output 32 bytes per line, and show each byte as an ASCII character (preceded by one blank) or as a 2-character, C-language escape sequence for control characters such as horizontal tab (tab) and newline. If ASCII interpretation is not possible, show the 2-character hexadecimal representation. Show the first 12 bytes of the I/O buffer for each traced read() even in the absence of -r. Default is -all!

- -s [!],signal... Specify signals to trace or exclude. Trace signals specified in the comma-separated list. Report the receipt of each specified signal even if the signal is ignored (not blocked. Blocked signals are not received until they are unblocked.) You can specify signals by name or number (see <sys/signal.h>). If the list begins with not symbol (!), exclude the signals from the trace output. Default is -all.

- -t [!],syscall... Trace those system calls specified in the comma-separated list. If the list begins with not symbol (!), exclude the specified system calls from the trace output. Default is -tall

- -T [!],syscall... Show system calls that stop the process. Add the specified system calls to the set specified by -t. If one of the specified faults is encountered, leave the process stopped and abandoned. That is, leave the process and exit, but leave the process in the stopped state at completion of the system call in question. You can use a debugger, other process inspection tool, or truss (with the same or different options to continue tracing) the process. The default is -Tall!

You cannot restart a process left stopped in this way using kill -CONT because the process stopped on an event of interest through /proc, not by the default action of a stopping signal. See signal(5). You can use the prun(1) command described in proc(1) to set the stopped process running again.
