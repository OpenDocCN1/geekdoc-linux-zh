## Limitations

If the object file be examined depends on libraries, those dependencies must be recorded in it (with the compiler -l option).
If the object file be examined depends on other shared libraries, those libraries must be accessible via LD_LIBRARY_PATH or RPATH when you run appcert.
For checking 64-bit applications, the machine must be running the 64-bit Solaris kernel. See isalist(1). Also, the checks for static linking are currently not done on 64-bit applications.
appcert cannot examine the following elements:

- Object files that are complete or partially statically linked.
  Completely statically linked objects are reported as unstable.
- Executable files that do not execute permission set.
  These files are skipped. Shared objects without execute permission are skipped.
- Object files that are set root.
  Because of limitations in ldd(1), set root files are skipped. Copy and/or change permissions to check them.
- Non-ELF executables as shell scripts.
- Non-C language interfaces to Solaris; for example, C++ and Java.
  The code itself need not be in C as long as the calls to Solaris libraries are in C.

# Output Messages

## Private Symbol Use

Private symbols are functions or data variables in a Solaris library that are not intended for developer or external use. These symbols are interfaces that the Solaris libraries use to call and communicate with one another. They are marked in pvs(1) output with the symbol name SUMprivate.

Private symbols can change their semantic behavior or disappear altogether ("demoted" or "deprecated" symbols), so your application should not depend on any of them.

## Demoted Symbols

Demoted symbols are functions or data variables in a library that were once private to that library and have been removed (possibly scoped to the library) in a later Solaris release. If your application directly calls one of these demoted symbols, it will fail to run (relocation error), starting with the release in which the symbol was removed.

In rare cases, a demoted symbol returns in a later release. Nevertheless, the application will still not run on some releases.

Sun Microsystems, Inc., performed for the library scoping in the transition to Solaris 2.5.1 to 2.6. Because this completely internal interfaces were made invisible (that is, they cannot be dynamically linked against), a developer cannot accidentally or intentionally call these interfaces. For more information, you can see the Linker and Libraries Guide, in particular the chapter on versioning. You can find this document online at http://docs.sun.com.

## Unbound Symbols

Unbound symbols are library symbols (that is, functions or data) referenced by the application that the dynamic linker could not resolve with appccert.

> Note — appcert does not actually run your application, so some aspect of the environment that affects dynamic linking might not be properly.

Unbound symbols do not necessarily indicate a potential binary compatibility problem. They mean only when appcert was run, the runtime dynamic linker could not resolve

Unbound symbols might be the result of LD_LIBRARY_PATH not correctly. Make sure LD_LIBRARY_PATH is set so that all your binary objects can find all of the libraries they depend on (either through your product's owner, Solaris libraries, or those of a third party). Then rerun appcert.

You might find it useful to write a script that sets up the environment correctly and then runs appcert on the binaries you want to check.

Another reason for unbound symbols is that a shared object under test has not recorded its dependencies, that is, at time the -l option was not supplied to the compiler and ldd. The shared object requires that the executables that link against have the correct dependencies recorded.

Notice that such a shared object can be linked in the standard way (that is, specified at an executable's build) or dynamically opened (for example, an executable calls dlopen(), the shared object which may be running). Either case can give rise to unbound symbols when appcert is run. You can usually resolve the former by using LD_LIBRARY_PATH appropriately before running appcert. The latter (dlopen) is usually difficult to resolve. Under some circumstances, you might be able to set LD_PRELOAD appropriately to preload the needed libraries, but this procedure does not always work.

How do you know the environment has been set up so correctly that there will no unbound symbols? It must be set up so running ldd -r on the binary yields no found symbol or found errors. See ldd.so(1) and ldd(1) for more information on dynamic linking.

In any event, appcert flags unbound symbols as a warning in case they indicate a more serious problem. Unbound symbols can be an indicator of dependencies on demanded symbols that have been removed from a library or scoped to it. Dependencies on demanded symbols lead to serious stability problems.

However, setting up the environment properly allows you to record library dependencies at time whenever possible because it makes the binary object better defined and self-contained. Also recommended is to use the -z defopt when building shared objects, to force the resolution of all symbols during compilation. See ldd(1) for more information.

## No Found Bindings

appcert /bin/ldd -r on any binary object to be tested. It sets the environment variable LD_DEBUG="files,bindings". (See ldd(1) and ldd.so(1) for more information.) If that command fails for some reason, appcert has no dynamic symbol-binding information and finds no bindings.
appcert can fail if any of the following conditions is true:

- binary object does not have read permission.
- The binary object is suid or sgid and the user does not have sufficient privileges.
- The binary object is an executable without the execution permission bit.
- The binary object is a 64-bit application, but the kernel on the current machine supports only 32-bit applications.
- The binary object is completely statically linked.
- The binary object has no dependency information recorded.

Other cases as exist as well (for example, this flag means that appcert could not completely examine the object because of permissions or environment. Try to modify the permissions or environment so that the dynamic bindings can be recorded.

## Obsolete Library

An obsolete library is one whose use is deprecated and that might, in some future release, be removed from Solaris. appcert flags these because applications depending on them might not run in future releases of Solaris. All interfaces, including Private ones, in an obsolete library are frozen and will not change.

## Use of sys_errlist or sys_nerr

Direct use of the symbols sys_errlist or sys_nerr presents a risk in which reference might be passed the use of the sys_errlist array. These symbols are deprecated in 32-bit versions of Solaris and are absent altogether in 64-bit versions.

## Use of Strong. Weak Symbols

The "strong" symbols (for example, socket) associated with "weak" symbols (for example, socket) are reserved as private (their behavior could change in the future). Your application should directly reference only the weak symbol (usually the strong symbols begin with _).

> Note — Under certain build environments, the strong/private dependency recorded into your binary instead of the weak/public one, even though the source code does not appear to reference the private symbol. Nevertheless, you should take steps to trace down why this problem is occurring and fix the dependency.

# Bugs

The terms "public" and "private" as equivalent to "stable" and "unstable" are unfortunately somewhat confusing. In particular, experimental or evolving interfaces are Public in the sense that they are documented and their use is encouraged. But, they are unstable because an application built with them might not run on subsequent releases. Thus, they are classified as Private for appcert's purposes until they are no longer evolving. Convolving, obsolete interfaces eventually disappear, and so are unstable, even though they have been Public and stable in the past and are still treated as Public by appcert. Fortunately, these two situations are rare.
