```
[path] [-P prompt]
::set [-wF] [+-o option] [-s distance] [I path] [-L]
```

Get or set miscellaneous debugger properties. Specifying options, displays the current set of debugger properties. The ::set dcmd recognizes the following options.

- -F Forcibly take over the next user process that ::attach is applied as if mdb was executed with the -F option on the command line.
- -I path Set the default path for locating macro files. The path argument can contain any of the special tokens described for the -I command-line option in "Options" on page 852.
- -L Set the default path for locating debugger modules. The path argument can contain any of the special tokens described for the -I command-line option in "Options" on page 852.
- -o option Enable the specified debugger option. If you use the -o form, the option is disabled. The option strings are described along with the -o command-line option in "Options" on page 852.
- -P Set the command prompt to the specified prompt string.
- -s distance Set the symbol-matching distance to the specified distance. Refer to the description of the -s command-line option in "Options" on page 852 for more information.

```
[signal] [:sigbb [/-ddest] [-c cmd] [-n count] SIG...
[signal] :t [/-dDest] [-c cmd] [-n count] SIG...
```

Trace delivery of the specified signals. You identify signals with an optional signal number preceding the dcmd or with a list of signals numbers (see signal (3HEAD)) following the dcmd. -d, -D, -e, -s, -T, -c, and -n options have the same meaning as for -evset dcmd on page 833. The set of signals for the process that dumped core by default (see signal(3HEAD)) and SIGINT are traced. New in the Solaris 9 release.

- ::sizeof type Print the size of the specified type in bytes. The type parameter can make a C struct, union, fundamental integer type, or a pointer to any of types. The type name can use the backquote (\') scoping operator described in "Symbol Name Resolution" on page 826. ::sizeof dcmd can be used only with objects that contain symbolic debugging information for use with mdb. See "Symbolic Debugging Information" on page 852 for more information. New in the Solaris 9 release.

```
[address] ::stack [count]
[address] $c [count]
```

Print a C stack backtrack. If the dmd is preceded by an explicit address, display a backtrack beginning at this virtual memory address.
Otherwise, display the stack of the representative thread. Specifying an optional count value as an argument displays no more than count arguments for each stack frame in the output.

```
:step [over | out] [SIG]
:s [SIG]
:u [SIG]
```

step the target program one instruction. If you specify an optional signal name or number (see signal(3HEAD)), the signal is immediately delivered to the target as part of resuming its execution. When you specify the over argument, ::step steps over subroutine calls. The ::step out argument is the same as the ::next dmd. When you specify the optional out argument, the target program continues until the representative thread returns from the current function. If no target program is currently running, ::step starts a new program running as if ::run and stops at the first instruction. The ::u dcmd dmd is the same as ::step out. New in the Solaris 9 release.

```
[syscall] ::sysbp [+/-dbtest] [-io] [-c cmd] [-n count] syscall
```

Trace entry or exit from the specified calls preceding the dmd or a list of system call names or numbers (see <sys/syscall.h>) following the dmd. When you use the -i option (the default), the event specifiers trigger on entry into the kernel for each system call. When you specify the -o option, the event specifiers trigger on exit from the kernel. The -d,-e,-s,-t,-T,-C, and -n options have the same meaning as for the ::evsetd dcmd on page 833. New in the Solaris 9 release.

```
::typeset [+/- variable-name...
```

Set attributes for named variables. Specifying one or more variables defines them and sets them to the value of dot. Specifying the -t sets the user-defined tag associated with each variable. Specifying the +t option clears the tag. Specifying no variable names prints the list of variables and their values.

```
::unload module-name
```

Unload the specified dmd. You can print the list of active dmds with the ::dmods dcmd. Built-in modules cannot be unloaded. Modules that are busy (that is, provide dmds that are currently executing) cannot be unloaded.

```
::vars [-npt]
```

Print a listing of named variables. Specifying the -n option restricts the output to variables that currently have non-zero values. Specifying the -p option prints the variables in a form suitable for reprocessing by the debugger with the $ dcmd. You can use this option to record the variables to a macro file and then restore these values later. Specifying the -t option prints only the tagged variables. You can tag variables with the -t option of the ::typeset dcmd.

```
[::walk walker-name {variable-name}]
```

Walk through the elements of a data structure with the specified walker. You can list the available walkers with the ::walkers dcmd. Some walkers operate on a global data structure and do not require a starting address. For example, walk the list of proc structures in the kernel.

Other walkers operate on a data structure which you must explicitly specify. For example, giving a pointer to an address space, walk the list of segments. When used interactively, the ::walk dcmd prints the address of each element of the data structure in the default base. You can also use this dcmd to provide a list of addresses for a pipeline. You can use the backquote ('') operator described in "dcmd and Walker Name Resolution" on page 828 with walker-name. Specifying the optional variable-name assigns the specified variable the value returned at each step of the walk when mdb invokes the next stage of the pipeline.

```
::walkers
```

List the available walkers, and print a brief description of each.

Print the dcmd that exports the specified dcmds and walkers. You can use these dmcmds to determine which dcmd is currently providing the global definition of the dcmd or walker. See "dcmd and Walker Name Resolution" on page 828 for more information on global name resolution. Specifying the -v option prints the alternative definitions of each dcmd and walker in order of precedence.

# mdb

```
addr [len] ::wp [+ -dTest] [-rwx] [-c cmd] [-n count]
addr [len] :a [-c cmd]
addr [len] :p [-c cmd]
addr [len] :w [-c cmd]
```

Set a breakpoint at the specified address. You can set the length of the watched region by specifying an optional count preceding the demd. If you set no length, the default is one byte. The :wp demand allows you to configure the watchpoint to trigger on any combination of read (-r), write (-w), or execute (-x). The -d, -D, -s, -t, -T, and -n options have the same meaning as for ::evset demd on page 833. The :a demand sets a read watchpoint at the specified address. The :p demand sets an access watchpoint at the specified address. The :w demand sets a write watchpoint at the specified address. The arguments following the a, :p, and :w demands are concatenated to form the callback string. If this string contains metcharacters you must quote it. New in the Solaris 9 release.

```
::xdata
```

List the data buffers exported by the current target. Data buffers represent information associated with the target that cannot be accessed through target facilities (that is, an address space, symbol table, or register set). These buffers can be consumed by demd; for more information, refer to the Solaris Debugger Guide.

Delete all event species from the list of traced event species. You can also delete event species with ::delete. New in the Solaris 9 release.

# Warnings

# Use of the Error Recovery Mechanism

The debugger and its mdb execute in the same address space, and it is possible that a buggy demd can dump core or otherwise behave. The mdb capability, described in "Signal Handling" on page 828, provides a limited recovery mechanism for these situations. However, mdb cannot know definitively whether the debugger has corrupted its own state or the debugger's global state. Therefore, a resume operation cannot guaranteed be safe. The safest course of action following a resume is to save any important debug information and then quit and restart the debugger.

# Use of the Debugger to Modify the Live Operating System

The use of the debugger to modify (that is, write to) the address space of a live, running operating system is extremely dangerous and can panic a system if the user damages a kernel data structure.
