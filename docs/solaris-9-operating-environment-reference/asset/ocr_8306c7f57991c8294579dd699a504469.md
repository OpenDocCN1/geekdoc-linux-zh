# Usage

The operating system enforces certain restrictions on the tracing of processes. In particular, a user cannot track a command when the object file cannot be read by that user; setuid and setgid commands can be tracked only by a privileged user. Unless by privileged user, cputrack loses control of any process that performs an exec() of a setuid, setgid, or unreachable object file; such processes continue normally, independently of cputrack, from the point of the exec(().

Because cputrack runs one controlling process for each process it tracks, the system can run out of user process slots when you use the -f option.

The times cputrack prints correspond to the wall clock time when the hardware counters were actually sampled, instead of when the program told the kernel to sample them.

The time is derived from the same timestamp as gettime(3). The cputrack command attaches performance counter to each process it examines. This enables the counters to be multiplexed between different processes on the system, but you cannot use it at the same time as the cputstat(1M) command. Once an instance of the cputstat command is running, further attempts to run cputrack fail all instances of cputstat terminate.

Sometimes cputrack provides enough flexibility and prints sufficient statistics that you don't need to add selection code to an application. However, you occasionally want more control. Because the same performance counter is used by both the application itself and the LWP injected into the application by cputrack, an application can interact with the counter context to achieve some interesting capabilities. See pc_user_events(3CPC) for more information.

The processor cycles counted by the -t option applies to both user and system modes, regardless of the settings applied to the performance counters. The output of cputrack is designed to be read parsably by awk(1) and perl(1). Alternatively, you can construct tools directly using libcpc0(3LIB) and libcputrack(3LIB), which use the same APIs as cputrack. See cpc1(3CPC) for more information.

Although cputrack uses performance counter context to maintain performance values for each LWP, the events that are counted are inevitably impacted by other activities on the system, particularly for limited resources that are shared between processes (for example, cache misses). For such events, you may find it interesting to use cstat(1M) to observe overall system behavior.

> Warning — By running any instance of the cstat(1M) command, forcibly invalidate any existing performance counter context across the machine. In turn, all invocations of the cputrack command may exit prematurely with unspecified errors.

# Examples

# SPARC

In the following example, the cputrack command is used on a system with an UltraSPARC I processor. The counters are set to count processor clock cycles and instructions dispatched in user mode while the sleep(1cnt) is running.

```
mopoke* cputrack -c pic0=Cycle_cnt,pic1=Instr_cnt sleep 10
time lwp      event      pic0      pic1
1.019     tick      720627   248732
2.019     tick      0        0
```
