## Create a simple web application

The presented application will display the UNIX epoch time on a web browser using a separate URL – the application will support two URLs in total and a third bonus URL that catches everything else.

As you did before, you'll need to create a new Erlang project that will use Cowboy – the name of the project will be epoch, so please go ahead and create the *root* directory for the project by executing the **mkdir epoch** shell command.

Now, create a project similar to the project from the previous section before continuing. If you have trouble doing so, reread the previous section carefully.

So, after having a project that supports just one URL, it is time to start making changes to the files of the epoch project. However, before that, execute **make distclean** in order to clean up any unnecessary files and make sure that the epoch web application will use port number 1300.

![](img/fb76008333fb7aef815b136f9f1afe5f_52_0.png)

**Above** The Erlang code of the epoch_handler.erl module – its most important function is the **handle()** function that allows you to display the UNIX Epoch time in your browser on the local machine. The most interesting part of the project is where you define the different routes that will be handled by Cowboy:

```erlang
Routes = [[{'_',
    [
        ['/',  root_handler,  []],
        ['epoch', epoch_handler, []],
        ['_', cowboy_static, {priv_file,
        "static/error.html"}]
    }] ]
```

After defining the **Routes** variable, you should write the **Dispatch = cowboy_router:compile(Routes)** statement in order for Cowboy to actually activate the routes. Please note that the '_' at the beginning of the routes is for the web application to work on any host. The first route will catch the / URL and will just display a text message. The second route catches the **/epoch** URL and returns the current time in the UNIX epoch format. Each time you refresh the page, the output gets updated. The last route will catch all URLs that do not match any of the previous rules and is a static rule that presents an HTML webpage on your browser that contains an error message – the last route does not require the implementation of a handler because it uses the **cowboy_static** handler that is defined by Cowboy. Here, you just have to tell Cowboy where to find the HTML page you want to display. Please do not forget to create the **error.html** page and put it inside the */priv/static* directory; create the two modules for the two other routes and implement them – in this case the implementation of the two rules can be found in the **root_handler.erl** and **epoch_handler.erl** files that are located in the **src** directory. The Erlang code for the implementation of **root_handler.erl** is similar to the Erlang code found in the **hw_handler.erl** file you saw in the previous section.

Figure 4 shows the implementation of the Erlang function that returns the UNIX epoch time that can be found in **epoch_handler.erl**, as well as the rest of the module code. This is an exciting Erlang function for many reasons. The first reason is that in order to calculate the UNIX epoch time in Erlang, you will need to call `erlang:timestamp()` and use the first two of the three returned values in order to calculate the UNIX epoch time and save it to the `Epoch_time` variable.

Then, you construct the string that you want to send to the Cowboy `req:reply()` function and store it to the `TextToSend` variable.

Although what you see in this tutorial is the final version of the application, don't try to implement everything all at once because your code will most likely contain various types of errors – it is considered a good practice to create a dummy function for each route that will print a message in order to make sure that the route configuration of your project is correct and then start implementing and testing the routes one by one.

## Why are web apps important?

Web applications are important because they consume most of the internet traffic. This means that they must be developed to be *fast*, *robust*, *fault-tolerant* and *able to scale up*. Although Erlang fits all these requirements, it is not used very frequently for creating web apps, mainly because web developers do not know Erlang and functional programming in general.

The longer the performance of a website, the happier the visitors will be, which means that web apps are important and should be developed carefully. Additionally, a good web app would require fewer hardware upgrades and less maintenance.

Last but not least, if you are a developer who can create such well-behaved applications, you will always have things to do and it would be easier for you to choose to develop what interests you the most! So, *well-behaved web apps* will make the whole internet traffic faster, more secure. This means that if the websites of a company use a good web app, the internet presence of the company will be better and more visitors will stay on its website.

## Yawls web server

Yawls is another web server that is particularly good at serving web apps with dynamic content. As it is written in Erlang, Yawls is multithreaded by design and can work concurrently very efficiently.

Yawls works in two modes: *regular* mode, where it operates as a regular web server, and *embedded* mode, where it can run in an Erlang application. You can find more information about Yawls at [http://yawls.hyber.org/](http://yawls.hyber.org/).
