## From OVA to target vulnerable server

Now that you have your pen-testing machine already deployed, the next step will be to prepare your vulnerable server. This will be shared among all the users using their Kali VDIs. Web Security Dojo (see Resources) is a good starting point for web pen-testing. Download the OVA file, store it somewhere on your computer and extract the VMX file: `tar xvf Dojo-3.0.ova`. Because RAVADA VDI works with the QCOW2 format, you must convert the VMX file to QCOW2 first: `qemu-img convert -f vmmd -O qcow2 Dojo-3.0-disk001.vmdk Dojo-3.0-disk001.qcow2`. Now copy this file to `/var/lib/libvirt/images` on your RAVADA VDI server. Connect to the web GUI and log in as an admin user, then create a new VM as similar as possible to Web Security Dojo. Once the VM has been created, and from within a Secure Shell connection on your RAVADA VDI server, edit the VM settings in order to set where the Web Security Dojo QCOW2 disk image is located, use libvirt for that: `virds edit YOUR_VM_NAME`. Try to spot the `file` attribute within the XML code and replace it with the converted disk image you generated earlier:

Finally, remove the CD-ROM, swap entries and save the file. You can start the VM now to make sure everything is working fine. Because this is going to be your vulnerable server, you need to set a static IP to its virtual network adaptor. This way, every time the VM is started, the IP will hold. By default, all the VMs can communicate to each other by using the bridge device `virbr0`, which has no physical devices attached to it. This bridge provides internet connectivity by means of NAT and forwarding to every single new domain. By default, they will be all in the network address space 192.168.122/24. Using libvirt, set a MAC address for Web Security Dojo VM first: `virsh edit YOUR_VM_NAME`. Now look for the `<interface type="network">` XML snippet and add the MAC address this way:

```xml
<interface type='network'>
    <mac address='52:54:00:a7:49:04'/>
```

The last step will be to assign a static IP address to that MAC; you need to use `virsh` again to achieve that. Imagine you want to assign the IP address 192.168.122.250 to Web Security Dojo; do it like this:

```bash
virsh net-update default add ip=dhcp-host \
    '<host mac='52:54:00:a7:49:04' \
        name='WebSecurityDojo' ip='192.168.122.250' \
    />' \
    --live --config
```

Done! Now make sure the VM starts automatically at boot-time – inside the RAVADA VDI server CLI, run: `virsh autostart YOUR_VM_NAME`. Finally, you can start this VM from within the RAVADA VDI web GUI by clicking the ‘Start’ button. Log in as lud01 or lud2 and connect to your Kali virtual desktop. Open a new terminal and send some pings to the Web Security Dojo at domain to test the connectivity.

You can gain access to Web Security Dojo at any time and start any vulnerable service you want your trainees to exploit. Imagine you want them to exploit the H4CME CASINO web application: open the RAVADA VDI web GUI, log in as an admin user and then click ‘View’ to open a SPICE connection to the domain. Start H4CME CASINO from the menu ‘Targets > H4CME Casino Start’. Now you can get back to any Kali virtual desktop and start pen-testing this web application; all you need is to provide the correct URL: `http://192.168.122.250:3000`.

## Isolate the pen-testers

So far so good, but you don’t want your trainees to start pen-testing each other, do you? You must ensure that all the VDIs are well isolated and cannot be accessed from Web Security Dojo nor from one another. Using libvirt Network Filters, you can easily accomplish this. The pen-testing desktops should be able to send ICMP echo-requests to any host and receive their ICMP echo-reply counterparties, establish new TCP connections to any other host and send DNS queries. That’s about it. You can create your own filter for that purpose; open your favorite ASCII editor and enter this:

```xml
<filter name='isolated_vm' chain='ipv4'
    priority='700'>
    <rule action='accept' direction='out'
        priority='500'>
        <icmp type='8'/>
      </rule>
      <rule action='accept' direction='in'
          priority='500'>
        <icmp type='0'/>
      </rule>
      <rule action='accept' direction='out'
          priority='500'>
        <udp dportstart='53'/>
      </rule>
      <rule action='accept' direction='out'
          priority='500'>
        <tcp/>
      </rule>
      <rule action='drop' direction='inout'
          priority='500'>
        <all/>
      </rule>
    </filter>
```

![](img/fb76008333fb7aef815b136f9f1afe5f_42_0.png)

Save this file as `isolated_vm.xml` under `/etc/libvirt/nwfilter` on your RAVADA VDI server. Make it available. `virsh nwfilter-define isolated_vm`. Next, configure the virtual interface of all KALI domains with this new filter: `virsh edit YOUR_VM_NAME`. Add a reference to this filter within the `<interface>` description, as follows:

```xml
<filterref filter='isolated_vm'/>
```

Save it and voilà! From this moment on, any trainee will be able to connect to the internet and to any open port on the Web Security Dojo domain, but they won't have connectivity between them. Feel free to experiment with nwfilter rules (Again, see Resources).

From within your RAVADA VDI server, you can easily access any VM via its virtual serial console. This will help you recover access to the VM in case the SPICE connection stops working. This is described in the documentation (see Resources). However, don't forget to set up the VM accordingly by adding "console=ttyS0" to the grub.conf (/etc/default/grub on Debian-based systems) to make sure the system will spawn a serial console on /dev/ttyS0 every time it boots up.

## A bumpy road ahead of us ...

This is a great VDI project to start with. It is easy to install and set up and can be deployed quickly. However, it still has important flaws (as of this writing) that we hope will be fixed in upcoming releases. The database authentication mechanism lacks pseudorandom per-user salt generation; the SPICE protocol is not encrypted by default using a TLS channel (although, using TLS may decrease the VDI performance). A pseudorandom four-character temporary password is also generated to protect the remote SPICE connection to the desktop, which renders RAVADA VDI prone to brute-forcing attacks. But for our testing purposes it is perfect: you can start using it in order to deploy a whole pen-testing multi-user environment. And for all those flaws we just mentioned, well, there's always the possibility to create a git pull request! So, what are you waiting for? Time to get involved and get training!
