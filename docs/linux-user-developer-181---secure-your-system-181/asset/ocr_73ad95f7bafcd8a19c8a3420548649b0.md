# Microsoft Azure

There are only a handful of players approaching AWS's scale in the market – one of those is Microsoft, with its Azure platform. Microsoft Azure was announced in October 2008 and, like Amazon's service, has grown hugely thanks in part to Linux. Azure offers over 600 services, including virtual machines, serverless applications, file storage, database services and messaging systems. Azure is available in 38 regions around the world, two of which are based in the UK.

Some instance types have local storage (e.g, the i3.large instance is a powerful type with a 475GB SSD attached) while others use EBS (Elastic Block Storage). EBS provides persistent block storage for your instance, automatically replicated within your availability zone to protect against hardware failure. Magnetic, SSD and high-performance versions are available – again, of course, with varying costs. After selecting your machine type, you'll be prompted to configure an IAM role (that is, who has access) and also which VPC you wish the machine to be in. A VPC is a virtual private cloud dedicated to your AWS account. One is created by default, but you can create multiple VPCs. After your EC2 instance is created, it will be assigned an IP for external access (subject to your security group config), or you can assign it an 'Elastic IP' which, as the name suggests, is an IP that can be assigned to any instance. Understanding the EC2 process helps to comprehend how Lightsail is working behind the scenes. Each size of Lightsail instance is equivalent to an EC2 instance, storage in Lightsail is a specific size of EBS volume, the static IP is an Elastic IP, and the preconfigured OS or application stacks are AMI images. The benefit of Lightsail is a fixed cost, a barrier to entry to AWS for many users. What if you have resources in both Lightsail and other AWS services – can they communicate? Yes: in your Lightsail configuration you'll see an option for 'VPC peering' which enables intercommunication between Lightsail (which has set up another 'hidden VPC' behind the scenes) and your configured VPC.

# Choose your database

Once you've got a web server up and running, the next thing you'll want to think about is a database. As is often the case with AWS, there are a lot of different offerings to ponder. If you're looking for a traditional relational database on a managed service, you'll want to use Amazon RDS (Relational Database Service) which offers many of the most popular relational database engines. Amazon Elasticache provides in-memory caching via Memcached or Redis. You can host on your own EC2 instances too, but you won't then enjoy the managed nature of the Amazon services. One final option is third-party companies that host databases within the AWS cloud, such as the IBM-backed compose.io. Amazon RDS is incredibly useful because it takes away most of the difficult or tedious management tasks of a relational database. First and foremost, RDS manages backups, patching, automatic failure detection and recovery. RDS can automatically provision high availability with multiple instances in multiple availability zones, providing peace of mind with minimal effort. If you roll your own server, you are forced to scale instance sizes to increase the server power, but RDS allows you to increase CPU, memory and storage independently. Best of all, RDS is very cost-competitive with setting things up yourself – so why wouldn't you? The only thing RDS doesn't provide is shell access to the server although you probably shouldn't need it. You can use the tools you're familiar with to manage the RDS database, as well as benefiting from being within AWS with CloudWatch monitoring, VPC-based security and multiple region availability.
