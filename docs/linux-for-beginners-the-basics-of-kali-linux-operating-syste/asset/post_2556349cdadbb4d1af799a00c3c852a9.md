
# Process Termination

- The process informs the ancestors and descendants that it has ended (with the help of special signals)
- The resources allocated during the `fork()` call are released
- The scheduler is informed that the context can be switched

You can use either the `_exit()` system call or its `exit()` library function to complete the process in applications. This function closes all process threads, correctly releases all resources, and calls `_exit()` to actually complete it:

```c
#include <unistd.h>
void _exit(int status); // status specifies the return code

#include <stdlib.h>
void exit(int status); // status specifies the return code

exit(128);
```

Note that it is better not to call `exit()` when a process can use resources in conjunction with other processes (for example, it is a descendant process with an ancestor, and a descendant inherited resource descriptors from the ancestor). The reason is that in this case, trying to the release the resources in the offspring will result in them being released from the ancestors as well. You must use `_exit()` to complete these processes.

## Waiting For Process To Complete

When the process is completed, its control block is not immediately removed from the process list and hash and remains there until another process (ancestor) removes it from there. If the process is actually missing in the system (it is finished), but only its control unit remains, then the process is called a zombie process.

## Waitpid() system call

You can use the `wait()` system call to remove process information from Linux, but more often use the more versatile version of it - `waitpid()`. This call checks if the control unit of the corresponding process is in the system. If it is, and the process is not in the zombie state (that is, it is still running), then the process in the case of `waitpid()` will go to standby. When the descendant process is completed, the ancestor exits standby and removes the descendant control unit. If the ancestor does not call `waitpid()` for the descendant, it may remain in the zombie state for a long time.

### Synchronous Implementation Of Processes In Applications

Let's consider the synchronous execution of processes based on `waitpid()`. According to POSIX, this system call is defined as:

```c
#include <sys/wait.h>

pid_t waitpid(pid_t pid,        // pid of the expected process
               int *status,      // descendant completion status information
               int options);     // usually 0
```

The `pid` parameter can be set to `0`, which means that the process is waiting for the same group to which the ancestor belongs, or as `-1`, which means the expectation of any descendant. Here is an example of the implementation of synchronous execution with the expectation:

```c
pid_t pid;
if ((pid = fork()) == -1)
    exit(-1);
if (pid == 0)
{
    // descendant - call exec()
}
else
{
    // ancestor - wait for descendant
    int status;
    waitpid(pid, &status, 0);
    // continue execution
}
```

The `status` value gives you more information about the completed descendant process. There are a number of macros in `<sys/wait.h>`:

- `WIFEXITED(status)` - a non-zero value when the descendant has completed normally;
- `WEXITSTATUS(status)` - descendant return code (only when `WIFEXITED(status)` is non-zero).

The descendant return code is obtained as follows:

```c
waitpid(pid, &status, 0);
if (WIFEXITED(status))
   printf("Descendant ended with code %d\n",
   WEXITSTATUS(status));
```

## 5.3.7 Alerts

In the case of multitasking, there is a need to report processes about events occurring in the system or other processes. The simplest mechanism for this alert, defined by POSIX, is the *signals*. The process after receiving the signal immediately responds to its call special functions - a *handler* of the signal (signal handler), or action by default for this signal. Each signal is related to its number, which is unique in the system. No other information along with the signal can be transmitted.

Signals are the simplest mechanism for inter-process communication on UNIX systems, but since they allow the transmission of limited data, they are mainly used for event reporting.

### Types Of Signals

Depending on the circumstance, the signals are divided into synchronous and asynchronous. Synchronous signals occur during the execution of an active process stream (usually through an error - access to the wrong memory area, incorrect floating-point operation, execution of an instruction not in the processor design). These signals are generated by the OS kernel and immediately sent to the process whose thread was causing the error.

Asynchronous signals can be received by the process at any time of execution:

- A programmer can send an asynchronous signal to another process using a system call, which, on POSIX systems, is called `kill()`, the parameters of that call are the signal number and process identifier
- The signal may also be caused by some external event (keystroke, termination, etc.)

During the processing of such signals, the system must interrupt the execution of the current code, execute the processor code and return to the same instruction that was executed at the time of receiving the signal.

### Layout Of Signals

On receipt of the signal, the process can respond in one of the three ways (method of response is called signal disposition):

- Call the signal handler
- Ignore the signal, which in this case "disappears" and does not take any action
- Use the default action (this is the default setting for each signal, often ending the process)

The process can set individual disposition for each signal.

## Signal Blocking

The process can not only set the disposition of signals but also determine its willingness to receive signals of a certain type at that moment. If the process is not ready, it can block these signals. If a blocked signal is to be delivered to a process, the system queues it, where it will stay until the process unblocks it. The process blocks and unblocks signals by changing the *process signal mask* (a special data structure that stores information about what signals can be delivered to the process immediately, usually stored in its control block). Descendant processes inherit the ancestral signal mask.

## Examples Of Signals

Consider the signals defined by POSIX and supported in Linux (in parentheses next to the name, the signal number is given). By synchronous signals include, for example, the signal `SIGSEGV` (11) that generates the system while accessing a protected area of memory.

Asynchronous signals include:

- `SIGHUP` (1) - hanging up a communication line (e.g., user logs out of the system)
- `SIGINT` and `SIGQUIT` (2, 3) - program interrupt signals from the keyboard (generated by a user pressing Ctrl+C and Ctrl+\ respectively)
- `SIGKILL` (9) - immediate termination of the program (this signal cannot be caught, blocked, or ignored)
- `SIGUSR1`, `SIGUSR2` (10, 12) - user signals that can be used by applications
- `SIGTERM` (15) - request the program to shut down (this signal, unlike `SIGKILL`, may be ignored)

The default action for all of these signals, except for `SIGSEGV`, is to terminate the program (an additional memory dump (core dump) is generated for `SIGSEGV` - a file that stores the image of the process address space for later analysis).

## Setting The Signal Disposition

A `sigaction()` system call is used to set the signal disposition.

```c
#include <signal.h>

int sigaction(int signum,              // signal number
              const struct sigaction *act, // new disposition
              struct sigaction *old_act); // return the previous disposition
```

The disposition is described using the `sigaction` structure with the following fields:

- `sa_handler` - pointer to the signal handler function
- `sa_mask` - the signal mask that specifies which signals will be blocked inside the handler
- `sa_flags` - additional flags

Limit to zeroing `sa_mask` and `sa_flags` (without blocking any signal):

```c
struct sigaction action = {0};
```

The `sa_handler` field should be set as a pointer to a previously declared function that looks like this:

```c
void user_handler(int signum)
{
    // signal processing
}
```
