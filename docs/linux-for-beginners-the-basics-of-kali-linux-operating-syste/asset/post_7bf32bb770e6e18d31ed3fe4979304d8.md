
## Conclusions

- Processes and threads are the active resources of computer systems that implement code execution. The thread is called a set of sequentially executed processor commands. A process is a collection of one or more threads and the protected address space in which they are executed. Threads in the same address space can share data together, and for threads of different processes without special means, this is not possible. In traditional systems, each process can execute only one thread code execution of processes. Modern operating systems support the concept of multithreading.

- Using threads in an application means parallelizing it - the ability to perform actions simultaneously with different snippets of code. Program parallelism reflects the asynchronous nature of the outside world, its sources being code execution on multiple processors, I/O operations, user interaction, and client application requests. Multithreading allows applications to implement this course and achieve parallelism and efficiency.

- There are user threads running in the user mode in the process address space, and the kernel threads with which the OS kernel works. The relationship between them determines the scheme of implementation of the thread model. In practice, they often use the 1:1 scheme, when each thread of the user corresponds to one thread of the kernel, and the kernel itself is responsible for managing the threads of the user.

- The thread can be in different states (execution, waiting, readiness, etc.). The principles of moving from one state to another depend on the principles of thread planning and processor time scheduling. Moving the thread from execution state to any other state is about switching the context - transferring control from one thread to another while preserving the state of the processor.

- Each process and thread in the system corresponds to its control unit - a data structure containing all the necessary information. During the creation process (usually by the system call `fork()`) create one control unit, allocate memory and launch the main thread. Creating threads is faster and easier because they do not need to allocate memory to the new address space.

## Chapter 4: Process and Thread Scheduling

The ability to run threads in parallel depends on the number of processors available. If the processor is single, parallel execution is impossible in principle (only one thread can be executed at any one time). If the number of processors is N > 1, parallel execution can only be implemented for N threads (one thread per processor).

The main purpose of scheduling for a single-processor system is to arrange multiple threads on a single processor that would give the system user the impression that they are running at the same time. This definition can be extended to multiprocessor systems if a scheduling task occurs when the number of threads exceeds the number of available processors.

Consider the basic types of scheduling, their principles, and algorithms.

### General Principles of Scheduling

Consider the basic principles underlying scheduling.

### Features of Thread Execution

In terms of scheduling, threads can be depicted as a cycle of alternating computation (CPU usage) and I/O periods. The time interval during which the thread executes only the instructions of the processor is called the CPU usage interval (CPU burst), the time interval when the thread is waiting for I/O, the I/O burst interval. Most of these intervals are from 2 to 8 ms.

Threads that spend more time computing and less - on the I/O are referred to as *CPU bound*. They actively use the processor. Their main characteristic is the time spent on computing; the intervals of CPU usage for them are longer. Threads that take most of the time waiting for I/O are referred to as *I/O bound*. Such threads load the processor much less, and the average length of the processor usage interval for them is small. The higher the clock speed of the processor, the more threads can be attributed to the second category.

*   Processor-limited thread (matrix multiplication)
*   I/O restricted thread (text editor)
*   Interval I/O (I/O bound)
*   Interval CPU usage (CPU bound)

### Scheduling Mechanisms and Policy

The scheduling *mechanism* and *policy* should be differentiated. Scheduling mechanisms include context switching tools, thread synchronization tools, etc., and scheduling policies are tools for determining when to switch contexts. The part of the system that is responsible for policy is called the *scheduler* and the algorithm used for this - *scheduling algorithm*.

There are various evaluation criteria for scheduling policies, some of which apply to all systems, others to batch systems or interactive systems only. Today, three criteria are most commonly used to evaluate goal achievement.

- **Minimum response time.** This is the most important criterion for interactive systems. Response time refers to the time between running a thread (or typing an interactive command) and getting the first response. For modern systems, we have taken the time of 50-150 ms.

- **Maximum throughput.** This is the number of tasks that the system can perform per unit of time (for example, per second). Such a criterion is appropriate to apply in batch systems; in interactive systems, it can be used for background tasks. To increase throughput, you must:
    - Reduce wasted load time (for example, the time it takes to switch context)
    - Use resources more efficiently (to ensure that neither the processor nor the I/O devices are idle)

- The third criterion is *fairness*, which means that the CPU time is allocated according to its importance. Fairness provides such a distribution of processor time that all threads advance in their execution, and none stagnate. Note that implementing a fair scheduling policy does not always reduce the average response time. Sometimes this requires making the system less fair.

### Scheduling Principles

The principles of thread scheduling are applicable first of all to multithreaded systems with 1:1 scheme implementation (only kernel threads are scheduled here), as well as to systems with the implementation of process modules. In the latter case, the term “process” can be used instead of the term “thread” and the information necessary for scheduling can be stored in the structures of these processes. More complex scheduling principles are used in multithreaded systems for which the number of user threads does not match the number of kernel threads (Schemes 1:M and M:N). They require two schedulers: one for kernel-level operation, the other for user mode.

### Types of Scheduling

Distinguish between long-term scheduling, medium-term scheduling, and short-term scheduling.

#### Long-Term Scheduling

Long-term scheduling means determining which of the programs should be in the system to perform the load. This scheduling is also called static because it does not depend on the current state of the system. It played an important role in batch systems when it was known in advance what processes needed to be completed and the tasks could be scheduled. In interactive systems (e.g., systems with time-sharing) loading processes is principally engaged by users, and it is not subject to scheduling; so they usually use a simplified long-term scheduling strategy. The system allows you to create processes and threads to reach some maximum limit, and then further attempts to create a new process or thread will cause an error. This strategy is also based on the psychology of users, who, feeling uncomfortable in an overloaded system, can interrupt work with it, which leads to reduced load.

#### Medium-Term Scheduling

Medium-term scheduling controls the transition of suspended threads to the ready state and back. In the control unit which is ready for execution, threads are immediately organized in a structure called the queue of ready threads (or ready queue).

The transition to a suspended state can be caused by the following factors:

- Waiting for an I/O operation
- Waiting for the completion of another thread (joining)
- Blocking a thread because it needs to be synchronized with other threads

Usually, for the correct organization of this waiting, in addition to the queue of ready threads, they implement an additional set of queues. Each such queue is associated with a resource that may cause thread waiting (e.g., an I/O device); these queues are called *scheduling queues* or *waiting queues*. The mid-term scheduler manages all these queues by moving threads between them and the queue of ready threads.
