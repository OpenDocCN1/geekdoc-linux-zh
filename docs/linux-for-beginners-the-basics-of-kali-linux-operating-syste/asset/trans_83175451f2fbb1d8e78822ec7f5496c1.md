
## 使用信号量实现生产者-消费者问题

首先，让我们称一下解决此问题所需的同步操作。

- 1. 将直接缓冲区更改操作（对于生产者——将对象放入缓冲区，对于消费者——从缓冲区移除对象）放在临界区中
- 2. 根据要求 2 安排等待机制（缓冲区满时生产者的等待机制）。在此过程中，消费者必须通知等待的生产者，告知其已从缓冲区取走对象（即如果缓冲区原本是满的，现在已非满）
- 3. 根据要求 3 安排等待机制（缓冲区空时消费者的等待机制）。在此过程中，生产者必须通知正在等待的消费者，告知与其匹配的缓冲区非空（如果它之前是空的）

现在让我们看看所需的同步原语。每个同步操作都需要一个独立的信号量：

- 1. 为了使用临界区，我们像之前一样使用二元信号量。让我们称之为 `lock`。生产者和消费者都将使用它，以保护其他线程（再次说明，包括其他生产者和消费者）对缓冲区的访问
- 2. 为了在缓冲区满的情况下组织生产者的等待，我们需要一个信号量，其当前值等于缓冲区中的空闲位置数。让我们称之为 `empty_items`。生产者在尝试向缓冲区添加新对象之前，如果该信号量为 0，则将其减少至等待状态。消费者在从缓冲区移除对象后，会增加该信号量，从而通知生产者（并唤醒其中一个）
- 3. 为了在缓冲区空的情况下组织消费者的等待，需要一个信号量，其当前值等于缓冲区中的项目数。让我们称之为 `full_items`。消费者在尝试从缓冲区获取对象之前减少该信号量，进入等待状态

以下是该问题的伪代码解决方案：

```c
semaphore_t lock = 1; // 用于临界区
semaphore_t empty_items = n; // 0 表示缓冲区满，最初为空
semaphore_t full_items = 0; // 如果为 0，表示缓冲区为空

// 生产者
void producer ()
{
    item_t item = produce (); // 创建对象
    down (empty_items); // 是否有空间放置对象？
    down (lock ); // 进入临界区
    append_to_buffer (item); // 将对象 item 添加到缓冲区
    up (lock); // 退出临界区
    up (full_items ); // 通知消费者有新对象
}

// 消费者
void consumer ()
{
    item_t item;
    down (full_items ); // 缓冲区非空？
    down (lock ); // 进入临界区
    item = receive_from_buffer (); // 从缓冲区获取对象 item
    up (lock ); // 退出临界区
    up (empty_items ); // 通知生产者有空位
    consume (item ); // 消耗对象
}
```

## 互斥锁

互斥锁的概念在很大程度上与此前定义的阻塞概念相吻合（第 5.2 节）。被称为互斥锁（Mutexes）的同步原语能够阻止一段代码在多个流中同时执行。实际上，互斥锁是操作系统级阻塞的一种实现。顾名思义，互斥锁消除了互斥性（注：此处原文用词略有歧义，通常指实现互斥访问）。其主要任务是在代码已在某个线程中执行时，阻塞所有试图访问该代码的线程。互斥锁有两种状态：空闲和忙。初始状态为“空闲”，并支持两种可能的原子操作。

- **获取互斥锁**（`mutex_lock`）：如果互斥锁处于空闲状态，则将其置为忙，流继续执行（进入临界区）；如果互斥锁处于忙状态，则流进入待机状态（即“等待互斥锁”或“锁定在互斥锁上”），执行权交由另一个流。获取互斥锁的流被称为该互斥锁的所有者：

```c
mutex_lock ( mutex_t mutex )
{
    if (mutex.state == free)
    {
        mutex.state = locked;
        mutex.owner = this_thread;
    }
    else
        sleep ();
}
```

- **释放互斥锁**（`mutex_unlock`）：互斥锁变为空闲；如果有多个流在等待，则从中选择一个，该流开始执行，占用互斥锁并进入临界区。在大多数实现中，流的选择是随机的。只有所有者才能释放互斥锁。以下是该操作的伪代码：

```c
mutex_unlock (mutex_t mutex)
{
    if (mutex.owner != this_thread)
        return error;
    mutex.state = free;
    if (waiting_threads ())
        wakeup (some_thread);
}
```

某些实现提供了第三种操作：尝试获取互斥锁（`mutex_trylock`）：如果互斥锁空闲，则行为类似于 `mutex_lock`；如果忙，则立即返回错误并继续执行。以下是使用互斥锁实现临界区的最简单实现。

```c
mutex_t mutex;
mutex_lock (mutex);
// 临界区
mutex_unlock (mutex);
```

互斥锁与二元信号量的主要区别在于，互斥锁只能由其所有者释放，而信号量可以由任何有权访问它的流进行修改。

## 进程间通信

到目前为止，我们讨论的是同一进程内流之间的交互。这种交互的主要特征是数据交换在技术实现上的便捷性——一个进程中的流使用同一个地址空间，因此可以像访问自己的数据一样自由访问共享变量数据。由于数据交换在实现上没有技术困难，在此情况下需要解决的主要问题就是流的同步。

另一方面，由于每个线程都在进程的地址空间内执行，因此组织不同进程间流交互的任务往往是一个问题。这本身涉及进程间交互（进程间通信或 IPC）的问题。对于不同进程的流而言，同步问题同样相关，但在大多数情况下，它们并不基于共享数据的概念（因为进程之间默认不存在共享数据）。此外，还需要解决在受保护的地址空间之间安全交换数据这一挑战。解决方案的方法定义了不同类型的进程间交互。

## 进程间交互的类型

进程间交互的实现通过三种基本方法完成：*消息传递*、*内存分配*和*映射内存*。

另一种 IPC 方法是考虑此前讨论过的信号技术。

## 映射内存

在许多操作系统中，映射内存是其他类型的进程间交互和系统决策所基于的基本系统机制。当然，映射内存通常与文件系统接口结合使用，在这种情况下，我们谈论的是*映射到内存的文件*（内存映射文件）。

这项技术确保特殊的系统调用（通常是 `mmap()`）将进程地址空间的一部分唯一地映射到包含该部分的文件。此后，对该内存的写入操作会导致映射文件的内容发生变化，这立即对所有有权访问该文件的应用程序可见。其他应用程序也可以在其地址空间中映射同一个文件，并通过该文件进行通信。

## 结论

- 同一交互进程中的流可以访问托管在该进程地址空间中的共享数据。任何流都可以随时修改这些数据，从而导致竞争状态，其结果取决于流的执行顺序。
- 流同步机制用于确保对共享数据的正确访问；其中最主要的是确保互斥访问，即在特定时间只有一个流可以访问此类数据。使用阻塞来实现互斥。
- 可以使用各种同步原语来解决同步问题。最简单的原语包括信号量、互斥锁、条件变量、读写锁和屏障。
- 更高级的机制是监视器（monitor）概念，它结合了互斥锁和条件变量，并设定了一些规则来协调它们的交互，以保护共享数据。
