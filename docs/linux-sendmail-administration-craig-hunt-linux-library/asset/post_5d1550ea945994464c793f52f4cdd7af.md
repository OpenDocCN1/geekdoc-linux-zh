The first source file called by the generic-linux.mc file is predictably enough, the linux.m4 OSTYPE file. The contents of the linux.m4 file must be analyzed to fully understand the generic Linux Sendmail configuration.

## The Linux OSTYPE File

The OSTYPE file contains operating system-specific configuration values. The biggest-configuration variation between the different operating systems that run Sendmail is the location of files. Variables that define patterns are commonly stored in the OSTYPE file. Since this file is specific to the Linux operating system and this book is about running Sendmail on Linux, let's take a close look at the OSTYPE file.

The command OSTYPE(linux) loads a file named linux.m4 for the ostype directory. Listing 5.2 shows the contents of this OSTYPE file:

```
[craig$] cat ../ostype/linux.m4
```

The file begins with a copyright notice. The copyright is bracketed by a divert(-1) statement and a divert(0) statement, so it is treated as a comment and can be safely ignored. The VERSIONID macro can also be ignored.

> NOTE In the rest of this chapter, to reduce the size of the listings, the copyright statements that start the files are not printed, but you should be aware that they are.

The first real configuration command in the file is a define statement that assigns a value to the CONFEBINDIR parameter. This parameter stores the path of the directory that holds executable binary files. The Sendmail 8.11 default for CONFBINDIR is /usr/libexec. This define changes the setting to /usr/sbin. Both of these directories exist on Linux systems, but the /usr/sbin directory is the one that is more commonly used to hold system binary files, and in this case it is correct. The CONFBINDIR path is used to locate the smr mailer, which is frequently used as the prog mailer on Linux systems. (The prog mailer, Chapter 12, "Sendmail Security," describes the advantages of using the smr mailer.) A couple of quick commands on our Linux system show that the correct value for CONFBINDIR is /usr/sbin:

```
$craig$ ls /usr/libexec/smrsh
ls: /usr/libexec: No file or directory
$craig$ ls /usr/sbin/smrsh
/usr/sbin/smrsh
```

The second configuration command is also a define. This is a little more complex. This define is contained inside an ifdef. The ifdef has nothing to do with configuration Sendmail. It is a built-in m conditional command that checks whether or not a variable has already been set to a value. The ifdef command has three fields:

- * the name of the variable that is being tested
- the action to take if the variable has been set
- the action to take if the variable has not been set

In Listing 5.2, the ifdef tests the variable PROCMAIL_MAILER_PATH. If the variable has already been defined, nothing is done. We know this by the fact that the second field of the ifdef is empty—notice the two commas right in a row (,). If the variable has not been set, the define contained in the third field of the ifdef is executed. It is exactly what happens on our sample system, because we did not assign any value to PROCMAIL_MAILER_PATH in the macro configuration file.

The define assigns the variable PROCMAIL_MAILER_PATH the path value /usr/bin/procmail. This overrides the Sendmail default for PROCMAIL_MAILER_PATH, which is /usr/local/bin/procmail. A quick ls shows that the new value is correct for our sample system:

```
[craig]$ ls -l /usr/bin/procmail
-rwxr-xr-x 1 root root 68276 Aug 10 1999 /usr/bin/procmail
```

## Don't ifdef

I have a philosophical objection to having an ifdef inside the OSTYPE file. I understand why it had to be done: it was done to create an OSTYPE file that would work for all versions of Linux. However, that is my basic objection. If different Linux distributions require different OSTYPE settings, the developers of those distributions could create an OSTYPE file for their distribution that contains the correct setting. After all, that is what the OSTYPE file is for. There is no reason why there shouldn't be an ostype/redhat.m4 file, and an ostype/suse.m4 file, and an ostype/slackware.m4 file, and a file for any other distribution you can imagine. You'd think that distribution developers would want to put their names in the ostype directory, but the fact is that not a single Linux distribution has added OSTYPE to the ostype directory of the Sendmail source code distribution.

As Listing 5.2 shows, the last line in linux.m4 is a FEATURE macro. The feature that this macro adds to the configuration is local_procmail, which specifies that procmail will be used as the local mailer. As you'll see in Chapter 11, "Stamping Spam," procmail is a very powerful mailer. The fact that Linux uses procmail as the local mailer is a plus. The local_procmail feature accepts up to three optional arguments:

- The path to the mailer. The path value assigned to PROCMAIL_MAILER_PATH, which in Listing 5.2 is /usr/bin/procmail. The same effect could have been obtained with the following FEATURE command:

> FEATURE(`local_procmail`, `/usr/bin/procmail`)

- The command line for executing the mailer. The default is procmail -Y -a $h -d $u, where $h is replaced by the detail value if the user+address syntax is used, and $u is replaced by the username from the recipient address. $h and $u are the Sendmail variables that hold the hostname and the remote user's address in a standard delivery triple. In this case, however, procmail is being used as a local mailer, so there is no hostname and the sh variable is used to hold the detail value. (See Appendix C, "Sendmail Variables, Options, and Flags," for a full listing of the Sendmail variables.)
- The flags for mailer. The default is SPFhn9. (See Appendix C, "Sendmail Variables, Options, and Flags," for a full listing of mailer flags.)

> NOTE With the local_procmail feature, procmail is being used as a local mailer. The command-line arguments and mailer flags are those set by LOCALMAILER_FLAGS and LOCALMAILER_ARGS, not those set by PROCMAIL_MAILER_FLAGS and PROCMAIL_MAILER_ARGS, which are used by the MAILER (procmail) command—despite the fact that local_procmail uses the path from PROCMAIL_MAILER_PATH instead of LOCALMAILER_PATH. Oh well, no one said Sendmail was easy.

The linux.mx OSTYPE file defines the directory path for the program, for procmail, and a feature that uses procmail as the local mailer. Clearly, the OSTYPE file is a good place to look for file pathnames and mailer options. None of the settings in linux.m4 relate to the problem we saw when we tried to use the generic.cf file on our sample system, but everything in linux.m4 is worth understanding because all of these settings affect the configuration of a Linux system.

## The Generic DOMAIN File

The DOMAIN command is optional. It loads the m4 source file that you create to configure values specific to your domain or network. You don’t have to create a DOMAIN source file, but it is highly recommended that you do if you have any domain-specific processing.

Host and username processing, domain name masquerading, mail relay, and antispam features are the types of information normally found in a DOMAIN source file. Listing 5.3 shows the generic.m4 DOMAIN file used by the generic-linux.mc configuration.

### Listing 5.3 The Configuration Commands in domain/generic.m4

```
[craig]$ tail -6 generic.m4
VERSIONID($id: generic.m4,v 8.15 1999/09/04 00:51:09 ca Exp '$')
define('FORWARD_PATH', '$z/.forward.w+$h:$z/.forward+$h:$z/
forward. $z/.'dn1
forward $z/.'dn1

define('conMAX_HEADERS_LENGTH', '32768')'dn1
FEATURE(`redirect`)'dn1
FEATURE(`use_cw_file`)'dn1
EXPOSED_USER(`root`)'dn1
```
