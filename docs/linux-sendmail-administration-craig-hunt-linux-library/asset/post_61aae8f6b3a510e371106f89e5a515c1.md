
The protocols that are the basis of the global e-mail system are simple command/response protocols that are so easy to understand that a system administrator can manually interact with a mail server over a telnet connection. Internet mail is carried by the Simple Mail Transport Protocol. SMTP, which is implemented by the Sendmail program, moves mail from server to server. The MIME extensions and ESMTP permit the mail system to move any kind of data. IMAP and POP move the mail from the mailbox located on the server to the mail reader located on the user’s desktop. These protocols make it possible to move any type of data through the mail from any user to any other user in the world. Planning a complete enterprise e-mail architecture constructed from these protocols is the subject of our next chapter.

## Understanding E-Mail Architecture

The capabilities of the network protocols described in Chapter 1, “Internet Mail Protocols,” define the technical boundaries of the Internet mail architecture. The global scope of Internet mail makes it obvious that these protocols can create a flexible architecture supporting an enormous amount of e-mail traffic.

SMTP provides direct end-to-end mail delivery. This is one of its great strengths. In Chapter 1, telnet was used to simulate an SMTP connection for the purpose of examining the protocol interactions. Another thing the telnet test showed that SMTP runs over the reliable, connection-oriented TCP transport. Using TCP means that end-to-end mail delivery is guaranteed. The person at the remote end might not read your mail, you may accidentally address it to the wrong person, or the server may redirect your mail, but you can rely on the fact that your message arrives intact.

Because of the direct delivery model, SMTP systems like Sendmail can provide immediate feedback about delivery. Everyone, at one time or another, has sent a message and gotten an immediate response saying that user-so-and-so does not have an account on the remote host to which the mail was directed. This immediate feedback is available because the local system directly connects to the remote host, delivers the mail to that host, and accepts responses back from that host. If the response is an error, the error message is immediately returned to the sender.

Some mail systems use store-and-forward protocols like UUCP and X.400 that move mail toward its destination hop at a time, storing the complete message at each hop and then forwarding it on to the next system. The message proceeds in this manner, one hop at a time, until delivery is made. With a system like UUCP, your server will communicate directly with hosts that are directly attached to your server. UUCP is a particularly good example of the store-and-forward model because the traditional UUCP bang address format clearly shows the path that the mail takes to its destination. In the UUCP bang address format, each host in the forwarding sequence is explicitly named and the last value in the address is the name of the user to whom the mail is addressed. Direct delivery allows SMTP to deliver mail without relying on intermediate hosts. If the delivery fails, the local system knows it right away and can inform the user who sent the mail or queue the mail for later. The disadvantage of direct delivery is that it requires systems to be fully capable of handling mail. Sometimes that's not the case, particularly with small systems such as PCs or laptops. These systems are usually shut down at the end of the day and are frequently offline. To handle these cases, SMTP can simulate the store-and-forward model by delivering the message to a mail server instead of delivering it to the end system. The mail server is then responsible for moving the mail to the end system.

## The Role of DNS

The Domain Name System (DNS) tells the SMTP server when mail needs to be routed to the end system. All Internet connections depend on IP addresses. DNS is a distributed system that maps hostnames to IP addresses. However, DNS can do much more than just map addresses. Address (A) records are only part of it. Some knowledge about DNS is needed to fully understand e-mail architecture. DNS records have the same format:

- The name field contains the name of the host to which the record applies.
- The type field contains the record type.
- The data field contains the IP address, for example.

Forty possible record types are used to build DNS databases. Of these records, one of the most important is the Mail Exchange (MX) record. MX records tell Sendmail where to deliver mail. The name field contains the domain, and the data field contains the hostname of the server to which the mail should be delivered. Two MX records define the mail servers for the foobirds.org domain:

```
foobirds.org. MX 10 wren.foobirds.org.
foobirds.org. MX 20 parrot.foobirds.org.
```

The name field contains the domain foobirds.org., meaning that these records pertain to the entire domain. If mail is addressed to user@foobirds.org, the mail is directed by these records. This is a popular configuration, particularly combined with the ability of the mail server to masquerade the name in outbound mail, as if the mail sent by the local user came from user@domain, which creates a balanced scheme for both inbound and outbound mail.

> **NOTE** See Chapter 9, "Special m4 Configurations," for detailed information about masquerading.

The first MX record says wren is the mail server for foobirds.org domain with a preference of 10. The second MX record identifies parrot as a mail server for foobirds.org with a preference of 20. The lower the preference, the more preferred the server is. The record with the preference of 10 is used before the record with the preference of 20, meaning wren is the preferred server for the foobirds.org domain and parrot is the backup server.

A backup mail exchange server is used only when the preferred server is down or offline. The backup server holds the mail and periodically sends it to the preferred server. When the preferred server comes online, the backup server sends the mail to the preferred server. At that point, the backup server's job is done. A backup mail exchange server never deals directly with the recipient. Its only job is to get the mail to the preferred server.

The MX records redirect mail addressed to the domain foobirds.org, but they do not redirect mail addressed to an individual host. Therefore, if mail is addressed to jay@hawk.foobirds.org, it is delivered directly to hawk; it is not sent to a mail server. This is a very flexible configuration that permits people to use e-mail addresses of the user@domain when they like, or to use direct delivery to an individual host when they want that.

Some systems are not capable of handling direct-delivery e-mail. An example is a Microsoft Windows system that doesn't run an SMTP mail daemon. Mail addressed to such a system would not be successfully delivered, and worse, would probably be reported to you as a network error! To prevent this, MX records are generally assigned to these individual hosts to redirect mail addressed to the hosts to a valid mail server. Here are two examples:

- puffin.foobirds.org. MX 5 wren.foobirds.org.
- robin.foobirds.org. MX 5 wren.foobirds.org.

These MX records redirect mail addressed to puffin or robin. In both cases, only one mail server is named for each host. With these records, mail addressed to daniel@puffin.foobirds.org is delivered to daniel@wren.foobirds.org. Sendmail does not need to select a server. All of the mail goes to wren.
