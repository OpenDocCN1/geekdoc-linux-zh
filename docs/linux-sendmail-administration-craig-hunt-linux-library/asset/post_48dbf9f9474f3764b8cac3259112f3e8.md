
from foobirds.org if MASQUERADE_AS(`foobirds.org`) is used with the default settings. But if FEATURE(`limited_masquerade`) is also used, the mail goes out as mail from bridal-gowns.com, unless you explicitly add bridal-gowns.com to class M.

Use MASQUERADE_DOMAIN to add individual values to class M. For example, to add hawk.foobirds.org to class M, adding the m4 macro to the macro configuration file:

```
MASQUERADE_DOMAIN(`hawk.foobirds.org`)
```

The MASQUERADE_DOMAIN is most useful when only a few values need to be added to class M and when those values change infrequently. Use the MASQUERADE_DOMAIN_FILE to load class M from a file when you have more than a few domain names you wish to masquerade. Assume that you want to load class M from a file named /etc/mail/masquerade-domain-names. You could add the following m4 macro to the configuration file:

```
MASQUERADE_DOMAIN_FILE(`/etc/mail/masquerade-domain-names`)
```

As the name MASQUERADE_DOMAIN implies, the values stored in class M do not have to be hostnames; they can be full domain names. By default, the hostname portion of the input address must exactly match a value in class or class M to be rewritten to the masquerade value. Thus, if class M contains terms.foobirds.org, the input address kerstan.terms.foobirds.org is rewritten unless the address kerstan.sooty.terms.foobirds.org is not rewritten. This means that if the name of the domain is found in class or M use FEATURE(`masquerade_entire_domain`) to change this default behavior so that every component of a domain in class or class M is masqueraded. If masquerade_entire_domain is specified and class M contains terms.foobirds.org, the input address kerstan.terms.foobirds.org is rewritten and so the address kerstan.sooty.terms.foobirds.org. # Chapter 9 Special m4 Configurations

The EXPOSED_USER macro is not the only way to handle duplicate usernames. The EXPOSED_USER macro works for names like root, which have special meaning on all Linux systems, but it may not be the solution you want when the duplicate usernames are real users. Rewriting usernames is our next topic.

# Masquerading Usernames

Transforming the user portion of an outbound address requires a database. Unlike hosts that can be masqueraded as a single value, each username requires a unique value. The user database and the genericstable, both described in Chapter 6, can be used to rewrite usernames. The user database, usually named /etc/mail/userdb.db, handles both inbound and outbound addresses while the aliases database does not work well with masquerading. For that reason, it is not covered. See Chapter 6 for details of the user database. The genericstable, on the other hand, is an excellent corollary to masquerading. The genericstable handles the user portion of the outbound address while masquerading handles the host portion.

The input address passed to the genericstable for processing must either have no host portion or a host portion that matches a value in class G. Use the GENERICIS_DOMAIN macro to add individual values to class G. Class G performs the same function for the genericstable as class M for masquerading. To configure the genericstable to be compatible with masquerading, class G should contain the same values as class M.

If you plan to add more than a few values to class G, load class G from a file using the GENERICIS_DOMAIN_FILE. Use the same file for class G that you use for class M if you want to make masquerading compatible. For example, you might have the two macros in your configuration:

```
MASQUERADE_DOMAIN_FILE(`/etc/mail/masquerade-domain-names`)
GENERICIS_DOMAIN(`/etc/mail/masquerade-domain-names`)
```

Also like values in class M, values in class G require an exact match. The generics_entire_domain feature to override this default behavior. The generics_entire_domain acts exactly like the masquerade_entire_domain feature described in the previous section. When generics_entire_domain is used, the values in class G are treated as domain names and any host whose these domains is considered a match for class G.
