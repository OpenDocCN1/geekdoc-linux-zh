
# Chapter 6 Using Sendmail Databases

There are more databases available for Sendmail than you will ever use. A couple of little or no value to Linux sites—the bitdomain database converts addresses for a network that no Linux uses and the uuucdomain database converts UUCP “bang” addresses, the old hostuser email addresses, and almost no one uses them. Other available databases have overlapping functions that might mean you don't need to use both of them at all. The redhat.mc configuration delivered by the RPM contains fewer than half of the defines and features listed above, and that probably has more database capabilities that you will really need. To help you evaluate which databases you need, we'll examine all of them in more detail.

## The Cr, Cw, and Ct Files

The first three databases we cover are not, in the strict sense of the word, databases. They are disk files used to load sendmail.cf variables. The “cr” and “cw” files perform important roles in configuring Sendmail, but changes in the security atmosphere of the network mean that the “ct” file no longer has a useful role.

The file that loads the t class is often called the “ct” file because the traditional name of this file was /etc/sendmail.ct. In Sendmail 8.11 the default name of this file is /etc/mail/trusted-users, but the function of the file remains the same. It is used to add usernames to the list of users who are trusted to send mail under other user's name. By default, ct class contains the usernames daemon, root, and uucp.

You will never need the /etc/mail/trusted-users file, and there are some reasons why you won't. First, it is a bad idea to let people send out mail under other people's names. In general, you don't want to expand the list of trusted users. Second, if you decide absolutely must add usernames to the trusted user list, for example, you might want to add the username “mail” to the trusted user list. You could edit the macro configuration file to add the FEATURE(use_ct_file) command, rebuild sendmail.cf file, and create a trusted-users file containing the single word mail1. But why would you? You could easily edit the macro configuration file to add the define'CONTRUSTED_USERS, ‘mail!’ command, rebuild the sendmail.cf file, and be done with it. Not is only this second approach slightly easier, it is safer because there is one fewer file created and thus fewer file where the permissions could be set incorrectly.

> WARNING Despite this example, neither CONTRUSTED_USERS nor use_ct_file is recommended because you shouldn't add any users to the trusted user list. Trusting users is a bad idea in this age of spammers and security crackers.

Unlike the "ct" file, which is never used, the "cr" file is used. The "cr" file is really named the relay-domains file. Sendmail always uses the data it finds in the relay-domains file. The purpose and structure of that file is the next topic.

## The relay-domains File

When mail arrives at a Sendmail server, it is either accepted, rejected, or relayed. If it is addressed to the server itself, by any name that the server accepts as its own, the mail is accepted for local delivery, meaning that the mail is placed in the mailbox of a local user or routed as one of the Sendmail databases. If the mail is not addressed to the server itself, the mail is either rejected or relayed. Mail is relayed by re-sending it to the delivery address. Prior to Sendmail 8.9, all addressed to another host that received by a Sendmail server was relayed. Now, no mail is relayed unless you explicitly tell Sendmail to relay it. This was a big headache for many system administrators who were using a Sendmail server to relay outbound mail for their PCs. But the change was necessary. Spammers were exploiting the relay feature of Sendmail to hide the source of spam. Now all administrators must pay the price of spam, and that is the extra work necessary to create an explicit relay configuration.

One way to explicitly enable decaying is to list the names of hosts allowed to relay mail in the /etc/mail/relay-domains file. Sendmail copies anything written in that file to the class variable R. Any host listed in class R is allowed to relay mail. Listing 6.2 shows the contents of a simple relay-domains file.

### Listing 6.2 Using the relay-domains File

```
[root]# cat /etc/mail/relay-domains
ibis.foobirds.org
[root]# ps -ax | grep sendmail
542 ?  S  0:00 sendmail: accepting connections
[root]# kill -HUP 542
[root]# sendmail -bt
ADDRESS TEST MODE (ruleset 3 NOT automatically invoked)
ter <ruleset> <address>
=$R
ibis.foobirds.org
> ^D
```

AIGHUP signal is passed to the Sendmail process to ensure that it reaches the hostnames from relay-domains into class R. The test in Listing 6.2 shows that class R was fully modified.

NOTE The hosts listed in relay-domains and class R are the sources of relayed mail; they are not the destinations. Class w, covered in the next section, contains destination command hostnames. Class R contains command hostnames.

Listing 6.2 adds only one domain name to class R. It is possible to add a limited number of domains to class R from inside the Sendmail configuration using the RELAY_DOMAIN macro. For example, the following command placed inside the Sendmail configuration would have the same effect as the relay-domains file shown in Listing 6.2:

```
RELAY_DOMAIN(`ibis.foobirds.org`)
```

However using the relay-domains file is simpler than using the RELAY_DOMAIN macro. The RELAY_DOMAIN command requires modifying the Sendmail macro configuration and running m4 to build the new sendmail.cf file. Using the relay-domains file does not. By default, Sendmail checks for a file /etc/mail/relay-domains and adds the names it finds to class R. No modifications to the configuration are required. You would need to place a command in the macro configuration only if you wanted to change the default filename of the relay-domains. There are two ways this can be done:

```
define(`CONF_FILE`, `path` ) This define command sets the path to the file loaded into class R. It defaults to /etc/mail/relay-domains, which means that if you have not explicitly set any value.
```
define(`CONF_FILE`, `/etc/mail/hosts`)
```

```
RELAY_DOMAIN(`etc/for`)
```

There are three commands relating to setting relay values, RELAY_DOMAIN, RELAY_DOMAIN_FILE, and CONF_FILE. But you don't need to use any of them. Just create a file /etc/mail/relay-domains and put the names of the hosts for which your server should relay in that. The "cr" file is a default. On the other hand, the "cw" file, which is discussed next, its is as important as that of the "cr" file.

## The local-hostnames File

In Chapter 5, both the generic Linux and the Red Hat configuration contain the FEATURE(use_cw_file) command. That feature reads the /etc/mail/local-hostnames file and adds the hostnames there to class w. By default, class w contains localhost, the special address 127.0.1, and full domain names, and unqualified hostnames. Anything you put in local-hostnames is added to these default values.

The system checks w to decide whether or not it should accept inbound mail for local delivery. The Sendmail server only accepts mail for local delivery that is addressed to the server. Yet many systems use the Sendmail as a mailbox to collect and hold. If the mail that the server collects and hold is literally addressed to another system, the name of that system needs to be added to class w, the other system's hostname is treated by Sendmail as if it were alias for.

Assume that robin.foobirds.org is a PC that uses the server wren.foobirds.org as a mailbox to collect and hold. An MX record is placed in the DNS server that directs robin's mail to wlen.
