# Stopping Spam

SPAM® is a world-famous canned luncheon meat from Hormel Foods. In a classic Monty Python comedy skit, John Cleese plays a waiter reciting a menu. In the first recitation the menu has one SPAM® selection but each iteration of reciting the menu more and more of the items become SPAM® until he finally describes the menu as “Spam, spam, spam, spam, and spam.” Similarly, e-mail replicates itself through every possible mailing list until you find yourself with a mailbox full of exactly the same message repeated over and over again. This is mindless repetition that gives spam e-mail its name.

Spam e-mails are the unsolicited advertisements you receive trying to sell you a college diploma, pheromones that women can’t resist, or pornography if those pheromones don’t work. I’m sure you know what I mean everyone attached to the Internet gets tons of this stuff. One of your tasks as the administrator of a mail server is to reduce the amount of junk mail moving through the network. The techniques used for that task are the topic of this chapter.

# Don’t Be a Spam Source

To paraphrase Polonius’ famous injunction against money lending, “Neither a spammer nor a victim be.” While it is clear that you do not want to be a victim of spam, you may bristle at the suggestion that you might be a spammer. Yet your server may unwittingly contribute to the spam problem, either from a bad user who is an intentional spammer, or from configuration problems that allow your server to be exploited by remote spammers.

# Chapter 11 Stopping Spam

Your first duty in the spam war is to make sure that your system is not a source of spam. A Sendmail system can be a source of locally generated spam or it can be a relay for spam generated elsewhere. You need to respond to both possibilities.

# Define an Acceptable Use Policy

To locally prevent generated spam, you need to make sure that everyone using your server knows that sending unsolicited advertisements from your server is not permitted. Write an acceptable use policy (AUP) that tells people what type of use is allowed and what is not allowed. If you're not sure what an acceptable use policy should look like, ask your ISP for a copy of their policy or check a national ISP. A copy of the Uunet acceptable use policy is available at www.uu.net/support/policy/, or check out the Sprintlink acceptable use policy at www.s.net/acceptableuse.htm.

Technical people are not interested in policy matters, so writing a policy may not appeal to you. You may not have the authority to write a policy. Nevertheless, someone has to do it. If you're working in a small organization, you're probably the person responsible for this type of thing. Write the policy and get the backing from management that you need to enforce. If you are part of a large organization, you may already have a policy. The government agencies and businesses that I work with always have an acceptable use policy. These organizations and many lawyers think it is a necessary component of limiting an organization's liability. If your organization has an acceptable use policy, make sure it includes language that clearly condemns spam. Without a written policy that all users must agree to, you may not have the authority to stop spammers from your system.

# Run the Identification Daemon

Running the auth server (inetd) also helps to discourage home-grown spammers. The identification daemon monitors port 113. If it gets a request from a remote system, it tells that system the name of the user running the current connection process to system. This allows remote mail servers to put a real username on the Receiver: header in email. Many Linux systems provide this service by default, as the grep of /etc/services and inetd.conf in Listing 11.1.

**Listing 11.1** Checking that inetd Is Configured

```
[craig]$ grep ^auth /etc/services
auth    113/tcp    ident      # User Verification
[craig]$ grep ^auth /inetd.conf
auth stream tcp nowait nobody  /usr/sbin/in.inetd in.inetd -t113
```

Listing 11.1 shows that identd is preconfigured to run inetd on a Caldera 2.3 server system. Many Linux systems run identd on demand from inetd or xident. A few run identd as part of the boot; for example, Red Hat changed to running identd at boot time as part of release 6.2. A quick ps command can check if the identd daemon is running on your Linux system. If your system doesn't run identd by default, either at boot time or on demand, add it to your configuration.

When identd is running, the remote server can query any TCP connections from your server by sending the username and destination port pair to the identification server. Your system responds by sending the username associated with the connection or an error. Spammers do not like to have their real usernames known. Providing their names to their victims makes it hard for spammers to stay in business.

> If you masquerade usernames for security reasons, your security people may not want you to run identd because it will expose the real usernames. However, masquerading should be used to create consistent, readable addresses, I recommend running identd if you masquerade user names.

# Properly Configure Mail Relay

In addition to discouraging local users from generating spam, you need to discourage remote users from using your server as a tool for distributing spam. Nobody likes spammers and the people know it. They do their best to hide the true source of the spam by relaying their junk mail through other people's servers. If your mail server allows relaying, spammers will make use of it.

To discourage, the default configuration of Sendmail from version 8.9 handles local mail but does not relay messages for any outside sources. Blocking relaying in most works because most systems are not mail servers—they're desktop or Unix systems dedicated to a single user. Because the user's mail originates from the system that is running identd, the mail is handled as local mail and relaying for outside systems is not required. Also, the definition of local mail is fairly broad. As we saw in Chapter 6, “Using Sendmail Databases,” every host listed in class is considered to be the local host. Therefore, the default configuration works in many cases.

# Relaxing Relay Restrictions

However, blocking all relaying doesn't work in every case, particularly if the system is a mail server. Most of the mail server delivers originates on its clients—this might be

![](img/9639113aa446fb8976cb3d377f7aafdd_324_0.png)

Windows clients that can't run their own Sendmail program. Blocking relaying at the server causes the client to get an error. For example, a client running Netscape would get a pop-up box saying “An error occurred while sending mail. The mail server responded: Relaying denied. Please check the recipients and try again.” There is nothing wrong with the recipients. What’s wrong is that the user configured the “Outgoing mail server” with the name of your server, and your server is running the default Sendmail configuration, which denies relaying.

To create a mail server, you must allow some level of relaying. Use the Sendmail feature that relaxes the restrictions just enough to get the job done. Don’t overdo it, or you will open the door to spammers. There are several relay features from which you can choose.

Class R can be used to extend relay services to specific clients. As described in Chapter 6, there are three ways to store hostnames in class R. Individual values can be stored in class R using the RELAY_DOMAIN macro. A file can be loaded into class R either the confRFILE option or the RELAY_DOMAIN_FILE macro. “The relay-domains File” of Chapter 6 for more information about these commands.
