Don't confuse the sshd_config file with the ssh_config file. The former controls the OpenSSH server, whereas the latter controls the SSH client program, ssh.

In addition to configuration lines, the sshd_config file holds comments, which are denoted by hash marks (#). Most sample configuration files include a large number of SSH options that are commented out; these lines specify the default values, so uncommenting the lines without otherwise changing them will have no effect. If you want to change an option, uncomment the line and change it. Most options' default values are suitable for most systems. The following list includes some that you may want to check and, perhaps, change:

- **Protocol** This option specifies the protocols OpenSSH understands. Possible values are 1 and 2. You can configure OpenSSH to support both protocols by separating them by a comma, in 1, 2 or 2,1, which are equivalent. Given the fact that OpenSSH protocol level 1 has compromised, the safest configuration is set to Protocol 2. This limits the server's ability to communicate with older clients, though.

- **PermitRootLogin** By default, this option is set to yes, which enables OpenSSH to accept direct logins by root. This is safer than a similar configuration over Telnet, but by added of security, set this value to no. The result will be that anybody wanting to perform work as root will need first to log in as an ordinary user, which means an intruder who has secured the root password will also need a regular username and its password. (If the computer is configured to allow an ordinary user to work sudo, a compromise of that user's account would also effectively be a compromise of the root account.)

- **X1Forwarding** This option specifies whether OpenSSH's X tunneling features should be active. If you want to enable remote users to run X programs via SSH, you must set this option to yes. Doing so slightly degrade the security of the client's X display, depending on certain other options; however the default value of no.

For information about additional options, consult the man page for sshd_config. If you make changes to the SSH configuration, remember to restart it using the server's SysV startup script.

## SSH Keys

Part of SSH's security involves encryption keys. Each server and each user has a unique name, or key, for identification purposes. In fact, SSH uses a security system involving two keys: a public key and a private key. These keys are mathematically linked in such a way that data encrypted with a particular public key may be decrypted only with the matching private key. When establishing a connection, each side sends its public key to the other. Thereafter, each side encrypts data with the other's public key, ensuring that the data can be decrypted by the intended recipient. In practice, this is just the first step of the process, but it's critical. What's more, SSH clients retain the public keys of servers they contacted. This enables them to spot changes to the public key. Such changes can be signs of tampering, if a client detects such a change, it will warn the user of this.

Most OpenSSH server scripts include code that for stored public and private keys, and if they're not present, generate them. In total, four keys are needed: public and private keys normally stored in /etc/ssh and called ssh_rsa_key and ssh_dsa_key for private keys, with .pub extension added for public. Some systems add ssh_rsa_key and its associated public key. If your system doesn't have these keys and you can't get the SSH server to start, you can try generating keys using the ssh-keygen command:

```
# ssh-keygen -q -t rsa -f /etc/ssh/ssh_host_key -C '' -N ''
# ssh-keygen -q -t rsa -f /etc/ssh/ssh_host_rsa_key -C '' -N ''
# ssh-keygen -q -t dsa -f /etc/ssh/ssh_host_dsa_key -C '' -N ''
```

Each of these commands generates both a private key (named in the -f parameter) and a public key (with the same name but with .pub appended). Don't run these ssh-keygen commands if the SSH key files already exist. Replacing the working files will cause clients who've already connected to the SSH server to complain about the changes and possibly refuse to establish a connection.

> Be sure the private keys are suitably protected; if an intruder obtains one of your keys, the intruder can impersonate your system. Typically, these files should have 0600 (-rw-------) permissions and are owned by root. The public keys (.pub filename extensions) should be readable by all users, though.

When you configure a client system, you might want considering a global cache of host keys. As noted, the SSH program records host keys for each individual user (It stores these in ~/.ssh/known_hosts). When you set up the client, you can populate the global ssh_known_hosts file, which is normally stored in /etc or /etc/ssh. Doing so ensures that the public key list is as accurate as the sources you use to populate the global file. It also eliminates confirmation messages when users connect to the hosts whose keys you've selected to include in the global file.

How do you create this file? One simple way is to copy the file from a user account that has been used to connect to the servers you want to include. For instance, you can type cp /home/ecernarn/.ssh/known_hosts /etc/ssh/ssh_known_hosts to use ecernarn's file.

> In the past, you could review SSH's known hosts file in a text editor, Today, though, OpenSSH 4.0 and newer support hashing of the data in this file. When this feature is enabled, the information hashed (that is, encrypted using a one-way encryption algorithm) and stored in hashed. The idea is that you'll still be able to authenticate SSH servers to which you connect, by a hash of the stored hostname but if an intruder steals your known file, the intruder will be unable to determine the identities of the computers to which you've been connecting. An unfortunate side effect of hashing is that you can't tell what servers.

## Controlling SSH Access

You can limit what an SSH server handles in various ways. The most obvious and basic method is password authentication. The usual authentication authentication is to employ a username and password, much as Telnet does. The ssh client program serves the username automatically or as part of the command line, so you won't see a username prompt when logging in via ssh.

Beyond password authentication, SSH supports other types of limitations:

- **TCP Wrappers** If you run SSH from a super server or if the server was compiled with TCP Wrappers, you can use theetc/hosts.allow and /etc/hosts.deny to limit access by IP address. If you launch SSH via a system startup script, this approach works only if the server was compiled to support it. This support may or not be present in your distribution's standard SSH package.

- **Firewalls** With all servers, you can restrict access by using a firewall. SSH uses TCP port 22. Technically, this's not an SSH feature, but it's certainly useful for protecting an SSH server.

- **etc/nlogin** If this file is present, SSH honors it. As described earlier, this file's presence means that only root user may log in. When a non-root user tries to log in locally, the file's contents are displayed as an error message; however, OpenSSH does not.
