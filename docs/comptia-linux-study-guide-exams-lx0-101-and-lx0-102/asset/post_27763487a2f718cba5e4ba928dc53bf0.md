
## Alternative to Partitions: LVM

An alternative to partitions for some functions is logical volume management (LVM). To use LVM, you set aside one or more partitions and assign them MBR partition type codes of 0x8e (or an equivalent on GPT disks). You use a series of utilities, such as pvcreate, vgcreate, lvcreate, and lvscan, to manage the partitions (known as physical volumes in this scheme), to merge them into volume groups, and to manage logical volumes within the volume groups. Ultimately, you access the logical volumes using names assigned to them in /dev/mapper directory, as /dev/mapper/myvol-1. The biggest advantage to LVM is that it allows you to easily resize your volumes without worrying about the positions or sizes of surrounding partitions. In a sense, the logical volumes are like files in a filesystem; the filesystem (or volume group, in the case of LVM) manages the allocation of space when you resize files (or logical volumes). This can be a great boon if you are not sure of the optimum starting sizes of your partitions. You can easily add disk space, in the form of a new disk, to expand the size of an existing volume group.

On the downside, LVM adds complexity, and not all Linux distributions support it out of the box. If LVM configuration spans multiple disks, a failure of one disk will put all your volume group at risk. It is safer to configure a system with at least one filesystem (dedicated to /boot, root filesystem (/) in its own partition, reserving LVM for /home, /usr, and other filesystems.

Despite these drawbacks, you might consider investigating LVM further in some situations. It's likely to be useful if you want to create an installation with many specialized filesystems and you want to retain the option of resizing those filesystems in the future. A second situation is when LVM is handy if you need to create very large filesystems that are too large for a single physical disk to handle.

## Mount Points

Once a disk is partitioned, an OS must have some way to access the data on the partitions. In DOS and Windows, this is done by assigning a drive letter, such as C: or D:, to each partition. (DOS and Windows use partition type codes to decide which partitions get drive letters and which to ignore.) Linux, though, uses a unified directory structure. Each partition is mounted at a mount point in that. A mount point is a directory that's used as a way to access the filesystem on the partition, and mounting the filesystem is the process of linking the filesystem to the mount point.

For instance, suppose that a Linux system has three partitions: the root (/) partition, /home, and /usr. The root partition holds the basic system files, and all other partitions are accessed via directories. If /home contains users' sally and sam, those directories will be accessible as /home/sally and /home/sam; this partition is mounted at /home. If this partition were unmounted and remounted at /users, the same directories would become accessible as /users/sally and /users/sam.

## Designing a Hard Disk Layout

Partitions can be mounted just anywhere in the Linux directory tree, including directories on the root partition as well as directories on mounted partitions. For instance, if /home is a separate partition, you can have a /home/morehomes directory that serves as a mount point for another partition.

The upcoming section "Mounting and Unmounting Filesystems" describes the commands and configuration files that are used for mounting partitions. For now, you should be concerned only with what constitutes a good filesystem layout (that is, what directories you should split off into their partitions) and how to create these partitions.

## Partitioning a Disk

The traditional Linux tool for disk partitioning is called fdisk. This tool name is short for fixed disk, and the name is the same as a DOS and Windows tool that accomplishes the same task. (When I refer to the DOS/Windows tool, I capitalize its name, as in FDISK. This tool's name is always lowercase.)

Although fdisk is the traditional tool, several others exist. One of these is GNU Parted, which can handle several different partition table types, not just the MBR that fdisk handle. If you prefer fdisk to GPTed but must use GPT, you can use GPT fdisk.

## Real World Scenario

## When to Create Partitions

One problem with splitting off lots of partitions, particularly for new administrators, is that it can be difficult to settle on appropriate sizes. As noted in Table 3.4, the appropriate size of various partitions can vary substantially from one system to another. For instance, a workstation is likely to need a fairly small /var (say, 100MiB), but a mail or news server may need a /var that is gigabytes in size. Guessing wrong isn't fatal, but it is annoying. You'll need to resize your partitions (which is tedious) or set up symbolic links between partitions so that subdirectories are on other. LVM can simplify such after-the-fact changes, but as noted earlier, LVM adds its own complexity.

For this reason, I generally recommend that new administrators use simple partition layouts. The root (/) partition is required, and swap is a very good idea. Beyond this, /boot can be kept on hard disks of more 8GB with older distributions or BIOS which is seldom needed since 2000. As data (in home or elsewhere), most Linux installations in 2012 require 5–25GB, so appropriate size for /home is relatively easy for new administrators to guess, or you can devote all your disk space after creating root (/) and swap to /home. Beyond these points, I recommend that new administrators proceed with caution.

As you gain more experience with Linux, you may want to break out other directories into their own partitions on subsequent installations or when upgrading disk hardware. You use the du command to learn how much space is used by files within any given directory.
