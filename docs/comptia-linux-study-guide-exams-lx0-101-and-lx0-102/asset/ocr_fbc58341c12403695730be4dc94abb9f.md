# Using X for Remote Access

Ordinarily, Linux is configured in such a way that its X server responds only to local access requests as a security measure. Thus, if you want to run programs remotely, you must make some changes to Linux lower its defenses—but not too far, let you anybody access the X server, which could result in security breaches.

# Using Remote X Clients

Suppose your local network contains two machines. The computer called zeus is a powerful machine that has important programs, like a word processor and data analysis utilities. The computer called apollo is a much less powerful system, but it has an adequate monitor and keyboard. Furthermore, you want to sit at apollo and run programs that are located on zeus. Both systems run Linux. To accomplish this task, follow these steps:

+   1. Log into apollo, and if it's not running X, start it.

+   2. Open a terminal (such as an xterm) in apollo's terminal. This command tells apollo to accept for display in its X server that originates from zeus.

+   3. Type xhost in apollo's terminal. You might use Telnet or Secure SSH (SSH), for instance. The result should be the ability to type commands in a shell on zeus.

+   4. Log into zeus from apollo. On zeus, export DISPLAY=apollo:0.0. (This assumes you're using bash; if you're using tcsh, the command is setenv DISPLAY apollo:0.0.) This command tells zeus to use apollo for the display of X programs. (Chapter 9, "Writing Scripts, Configuring and Using Databases," describes environment variables, such as DISPLAY, in greater detail.)

+   5. Type whatever you need to run programs at the zeus command prompt. For instance, you could type office to launch LibreOffice. You would see the programs on apollo's display, but they are running on zeus—their computations use zeus's CPU, you can read files off access, and so on.

+   6. After you're done, log off zeus and log off xhost on apollo. This tightens security so that a misclient on zeus won't be able to modify your display on apollo.

Sometimes, you can skip some of these steps. For instance, depending on how it's configured, SSH can forward X connections, meaning that SSH intercepts attempts to display X information and passes these requests to the system that initiated the connection. When this happens, you can skip steps 3 and 5, as well as the xhost command in step 7. (See the Real World Scenario sidebar "Encrypting X Connections with SSH.")
