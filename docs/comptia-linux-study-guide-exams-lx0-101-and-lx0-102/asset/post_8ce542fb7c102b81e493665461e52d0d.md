**Monitoring Log Files** In addition to checking the last few lines of a log file, tail can monitor a file on an ongoing basis, echoing lines to the screen as they are added to the file. You do this with the -f option to tail, as in `tail -f /var/log/messages`.

**Advanced Log Analysis Tools** Various packages exist expressly for the purpose of analyzing logs. For instance, there's Logcheck, which is part of the Sentry Tools package (http://sourceforge.net/projects/sentrytools/). This package comes with some distributions, such as Mandriva and Debian. Unfortunately, it requires a fair amount of customization for your own system, so it's most easily implemented if it comes with your system, preconfigured for its log file.

Log file analysis is a skill that's best learned through experience. Many log files are cryptic, and they can be cryptic in different ways for different programs. For instance, consider these entries:

- - Apr 14 23:17:00 speaker /USR/SBIN/CRON[60266]: (george) CMD=/usr/bin/fetchmail -home/george/.fetchmailrc /dev/null
- Apr 14 23:17:52 speaker sshd[60331]: Accepted publickey for george from fffff:192.168.1.3 port 48139 ssh

These lines relate to two entirely events, but they have a similar format. Both entries begin with a time and the name of the computer on which the activity occurred (speaker in example). Next each line is an identifier for the program that logged the activity, with its PID number: `/USR/SBIN/CRON[60266]` and `sshd[60331]` in this example. Note that these names are generated by the programs that create the activity, so they aren't necessarily consistent or even accurate. For instance, there is no /USR/SBIN/CRON program, but there is `/usr/sbin/bin/cron`. (Recall that Linux has a case-sensitive filesystem.)

All of this information helps identify what logged the log data and when it did. The rest of the entry contains the actual log data. The first entry identifies a run on behalf of george—specifically, cron ran the name of a configuration file via the -f option, and redirected the output to /dev/null. The second entry (sshd) identifies a login from 192.168.1.3 on port 48139, again involving the **user george**.

You can use these entries to help identify malfunctioning services, security breaches, and doing so, though, requires at least some familiarity with the normal log file contents and other system details. For instance, in the preceding example, if your system has no george account, these entries should be suspicious but you must be familiar enough of the entries to spot that george is a username (or able to work it out). You must also know that your system should have no george account.

Overall, you should probably examine your log files from time to time to become familiar with their contents. This will help you spot abnormalities when the system begins misbehaving or when you use log files to track down an unwelcome visitor.

# Maintaining the System Time

Linux depends on its system clock more than many OSs. Tools such as cron and at (described later, "Running Jobs in the Future") run programs at specified times, the development tool uses files time stamps to determine which ones need attention, and so on. Thus, you should be familiar with how Linux deals with time, how to set the time zone, how to set the clock, and how to keep the clock accurate.

# Linux Time Concepts

The x86 and x86-64 computers that most run Linux, as well as most other computers of this general class, have two built-in clocks. The first of these, sometimes called the hardware clock, maintains the time while the computer is turned off. When you boot Linux, it reads the hardware clock and sets the software clock to the value it retrieves. The software clock is what Linux uses for most purposes while it's running.

Most desktop OSs, such as Windows and pre-X Mac OS, set their clocks to the local time. This approach is simple and convenient for people who are dealing mainly with local time, but for purposes of networking, it's inadequate. When it's 4:00 a.m. in New York, it's 1:00 a.m. in Los Angeles, network protocols that rely every on time can become confused (or at the very least, confusing log entries) when they operate across time zones. Linux, or other Unix-like OSs, set their clock to Coordinated Universal Time (GMT)—the time in Greenwich, England, unadjusted for daylight saving time. This approach means Linux systems in New York and Los Angeles (and London and Tokyo) are all correct. When communicating with users, these systems need to know their time zone. For instance, when you type ls -1 to see a list complete with time stamps, Linux reads the time stamp in UTC and adds or subtracts the appropriate amount of time so that the time stamp appears in your local time. Course, all of this means that you must be able to set the computer's time zone. Linux's internal use of UTC can change the hardware clock. For the most part, this configuration works well but you may have to watch the clock the first time you reboot in the spring or fall because of daylight saving time.

Both the hardware clock and the software clock are notoriously unreliable on standard x86 and x86-64 hardware; both clocks tend to drift, so your clock can easily end up several minutes off. To deal with this problem, Linux supports various network protocols for setting the time. The most popular of these is the Network Time Protocol (NTP), which is described in the upcoming section “Using NTP.”

# Manually Setting the System Time

You can manually set your system’s clock—or more precisely, because clocks, as noted earlier, Linux maintains two clocks: the hardware and software clock. The main tool to set the software clock is date, which has the following syntax when setting the clock:

```
date [-u|--utc] [[CC]YY][[MMDDhhmm]][[.ss]]
```

Without any options, this command sets the current date and time. This format contains a month, a day, and a minute at a minimum, all in two-digit codes (MMDDhhmm). You can optionally add a 2- or 4-digit year and the seconds within a minute if you like. For instance, to set the time to 3:02 p.m. on October 27, 2013, you’d type the following command:

```
# date 10271502223
```

By default, you are specifying the time in local time. If you want to set the clock in UTC, include the -u, --utc, or --universal option.
