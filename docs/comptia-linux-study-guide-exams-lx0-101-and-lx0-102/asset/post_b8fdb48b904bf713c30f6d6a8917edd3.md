The options to GID can modify its operation:

- **Specify a GID**: Specify the new group ID using the -g GID option. groupmod returns an error if you specify a new ID that's already in use, unless you include the -o parameter, in which case you create two groups that share a GID.
- **Specify a Group Name**: Specify a new group name with the -n newgroupname option.

One of the most common group manipulations you perform is not handled through groupmod; it's done with usermod. Specifically, usermod enables you to add a user to a group with its -G parameter, the following command allows sally to be a member of the users, project1, and project4 groups, and removes it from all other groups:

```bash
# usermod -G users,project1,project4 sally
```

> Be to list all the user's current groups in addition to any groups to you want to add the user. Omitting any of the user's current groups will remove the user from those groups. You can discover the groups to which a user belongs along the groups command, as in sally. To avoid accidentally omitting a group, many system administrators prefer to modify the /etc/group file in a text editor or use passwd. Both options enable you to add users to groups without specifying their existing group memberships.

# Gpasswd

The passwd command is the group equivalent to passwd. The passwd command also enables you to modify other group features and to assign group administrators—users who perform some group-related administrative functions for their groups. The basic syntax for this command is as follows:

```bash
passwd [-a user] [-d user] [-R] [-r] [-A user,...] [-M user,...] group
```

The options for this command modify its actions:

- **Add a User**: -a user adds the user to the specified group.
- **Delete a User**: -d user deletes the user from the specified group.
- **Disallow newgrp**: -R option configures the group to not allow anybody to become a member through newgrp.
- **Remove Password**: -r removes the password from a group.
- **Add Group Administrators**: The root user may use the -A user,... parameter to specify group administrators. Group administrators may add members and remove members from a group and change the group password. Using this parameter completely overwrites the list of administrators, so if you want to add an administrator to an existing set of group administrators, you must specify all of their usernames.
- **Add Users**: -M user[...] options like -A, but it also adds the user(s) to the list of group members.

If entered without any parameters except, gpasswd changes the password for the group. Group passwords enable you to control group membership in a group, as granted by newgrp. Ordinarily, members of a group may use newgrp to change their current group membership (affecting the group they create). If set, even those who are not members of a group may become temporary group members; newgrp prompts for a password that, if entered correctly, gives the user temporary group membership.

Unfortunately, password entry by non-group members sometimes does not give group membership—the system responds with an access denied error message. The R-option also sometimes doesn't work correctly—group members whose primary group membership is with another group may use newgrp to set their primary group membership.

# Directly Managing Group Configuration Files

Group information is stored primarily in the /etc/passwd file. Like account configuration files, the /etc/passwd file is organized as a set of lines, one line per group. A typical line in this file resembles the following:

```
project1:x:501:sally,sam,ellen,george
```

Each field is separated from the others by a colon. The meanings of the first fields are as:

- **Group Name**: The first field (project1 in the preceding example) is the name of the group.
- **Password**: The second field (x in the preceding example) is the group password. Distributions that use shadow passwords typically place an x in this field; others place the encrypted password directly in this file.
- **GID**: The group ID (number in this example's case, 501) in this field.
- **User List**: The final field is a comma-delimited list of group members.

Users may be members of a group based on their /etc/passwd primary group specification. For instance, if user george is listed as her primary group, he need not be in /etc/passwd. If user george uses newgrp to change to another group, he won't be able to change back to project1. Systems with shadow passwords use another file, /etc/shadow, to store shadow password and information for group administrators, as described earlier in "Using gpasswd."

> If you configure Linux to use a network database, /etc/group file is present and may define groups for the system's basic operation. With /etc/passwd and /etc/shadow, though, important user groups are likely to be defined only on account server.

![](img/35f616c7eba4e79e12bfd762129c5d27_401_png)

Deleting groups is done via groupdel command, which takes a single parameter: group name. For instance, groupdel removes project1. You can also delete a group by editing the /etc/group file (and /etc/shadow, present) and removing the relevant line for group. It's generally better to use groupdel because groupdel checks whether the group is user's primary group. If it is, groupdel refuses to remove the group; you must change the user's primary group first. With users, deleting groups can leave orphaned files on the computer. You can locate them with find command, which is described in detail in Chapter 4. For instance, if deleted group used a GID of 100, you can find all the files on the computer with the following command:

```bash
# find -gid 100
```

Once you've found any files with deleted group's ownership, you must decide what to do with them. In some cases, leaving them alone won't cause any immediate problems; but if ID is ever reused, it can lead to confusion and security breaches. Therefore, it's usually best to delete the files or assign them other ownership using chown or chgrp.

# Tuning User and System Environments

User environments are controlled through shell configuration files. For bash, these files include /etc/profile, /etc/bashrc, ~/.profile, ~/.bashrc, ~/.bash_profile, and . The files in /etc are global configuration files, which affect all users; those in users' home directories (which are usually copied from skeleton directory at account creation, as described earlier) affect individual users' accounts and can be customized by users. These files control the environment variables—named variables that hold data for the benefit of many programs. For instance, you might set the EDITOR variable to the name of your favorite text editor. Some (but not all) programs that launch pay attention to this environment variable and the editor you specify.

As a system administrator, you can change the system-wide configuration files to add, remove, or change the environment variables that all users receive. Generally speaking, you should do so because the documentation for a specific program indicates that it uses particular environment variables. You can also see all current environment variables by typing env. The list is long, so you may want to pipe it through less, as in env | less.

# Using System Log Files

In addition to setting default environment variables and otherwise modifying users' text-mode login environment by adjusting their configuration files, you can adjust the default set of files created by useradd. As described earlier, in “Adding Users,” useradd copies files from the skeleton directory (/etc/skeleton) by default into a newly created home directory. Typically, /etc/skeleton contains a handful of user configuration files, such as .bashrc. You can add files (and directories) to this directory, including configuration files, a README file for new users, and anything else you like. Because these files are copied into users directories and given ownership of the copies, users can read, change, and delete these copies of these files. Thus, you shouldn't place any options in these files that are sensitive from a security point of view or that should not be able to change (In truth, unless you place in global configuration files they can be edited individually via manual commands or other configuration files, too.) Also, be aware that any change you make to the global files won't automatically be moved into users' copies of these files; changes will affect all the files received by new users. This makes the global files (such as /etc/profile) preferable to /etc/skeleton for any changes you want to implement system-wide, particularly if you expect to modify changes.

![](img/35f616c7eba4e79e12bfd762129c5d27_403_0.png)

Various programs set environment variables themselves, and some are maintained automatically by bash. For instance, bash sets the PATH environment variable, so you shouldn't try to set it in a configuration script. Also, be aware that adjusting the configuration files affects only bash. If a user's default shell is something else or if a user doesn't have a text-mode shell (say, if the user logs into X and launches programs from a GUI menu), setting environment variables in the configuration files will do no good.

# Using System Log Files

Linux maintains log files that record various key details about system operation. You may be able to begin using log files immediately, but knowing how to change the log file configuration can also be important. You do this by configuring syslog daemon (a daemon is a program that runs continuously in the background waiting for an event to trigger it to perform some action). Some servers and other programs perform their logging and must be configured independently of syslog. You may even want to configure one computer to send its log files to another as a security measure. You should also be aware of issues surrounding log file rotation; if your computer doesnt properly manage existing log files, they can grow to consume all your available disk space, at least on the partition on which they are stored.
