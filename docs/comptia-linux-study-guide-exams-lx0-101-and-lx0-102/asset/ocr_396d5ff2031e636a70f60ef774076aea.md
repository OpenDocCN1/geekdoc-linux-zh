# Administering Local Security

Memory Limits The -v option sets the total amount of virtual memory available to the shell, -s sets the maximum stack size, -m sets the maximum resident set size, -d programs' data set size, and -l sets the maximum size that may be locked into memory.

Hard and Soft Limits The -H and -s modify other options, causing them to be set as hard or soft limits, respectively. Hard limits may not be subsequently increased, but soft limits may be. If neither option is provided, ulimit sets both the hard and soft limits for the feature specified.

Current Settings Passing -a causes ulimit to report its current settings.
The ulimit command is often found in system or user bash startup scripts, typically by ulimit -c 0, in order to prevent creation of core files, which can sometimes clutter a filesystem. If your users perform software development, you may want to ensure that you do not set this limit, or at least set it as a soft limit (in ulimit -Sc) so users may override it when necessary.

Because ulimit is a built-in command, its utility as a security limit tool is limited. If users have access to GUI tools or can log into the system in any way that bypasses bash (via SSH, depending on how it is configured), restrictions imposed by ulimit become meaningless. Thus, you should treat ulimit as a way to prevent problems of accidental, rather than intentional, abuse of the system.

One particularly radical approach to security is to use the /etc/nlogin file. If this file is present, only root may log into the computer. Other users are shown the contents of this file when they attempt to log in. In many respects, this is like setting critical system limits to 0 for all other users. This is most likely to be used on dedicated server systems that have no regular console or shell users.

# Locating SUID/SGID Files

Chapter 4, “Managing Files,” describes the SUID and SGID bits. In brief, these are special flags that may be applied to executable programs, causing Linux to treat the program as if it were run by the program's owner (for SUID) or by the group's (for SGID) rather than the individual who actually ran the program. For instance, if a program's SUID is set and if the program is owned by bruce, the program, when run by anyone, will have access to all the files owned by bruce and otherwise behave as if hadce run it.

The SUID and SGID bits are frequently associated with the root account in order to enable them to perform tasks that require special privilege. For instance, the password program (described in Chapter 7) is SUID root may only modify the Linux password database. For an ordinary user to change a password, such mechanism must exist to run a process as root. That mechanism, in the case of passwd, is the SUID bit.
