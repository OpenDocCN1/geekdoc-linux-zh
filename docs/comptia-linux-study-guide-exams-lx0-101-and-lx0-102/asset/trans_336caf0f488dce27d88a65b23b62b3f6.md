

# 软件包概念

Linux 软件包管理工具通过跟踪已安装的软件来构建和修改这个“纸牌屋”。系统维护的信息通过以下几种方式避免了问题的产生：

**软件包 (Packages)** 软件包系统维护的最基本信息是关于软件*软件包*的信息——即安装在计算机上的文件集合。软件包通常以单文件形式分发，类似于[tarballs](https://www.example.com)（使用 tar 工具创建并使用 gzip 或 bz2 通用压缩的归档文件）或 zip 文件。一旦安装，大多数软件包由几十个或数百个文件组成，且软件包系统会跟踪所有这些文件。软件包还包含了额外信息，有助于软件包管理系统执行后续的任务。

**已安装数据库 (Installed Database)** 软件包系统维护着一个已安装文件的数据库。该数据库包含了通过软件包系统安装的每个文件的信息、每个文件所属的软件包名称以及额外信息。

**依赖关系 (Dependencies)** 软件包系统维护的最信息类型之一是*依赖信息*——即软件包之间的相互需求。例如，如果 SuperProg 依赖 UltraLib 来执行工作，软件包数据库就会记录此信息。如果你在未安装 UltraLib 的情况下尝试安装 SuperProg，软件包系统将不允许你操作。同样，如果你在安装 SuperProg 的情况下尝试卸载 UltraLib，软件包系统也将不允许你操作。（你可以覆盖这些限制，正如后文“强制安装”部分中描述的那样。尽管这样做是不尽人意的。）

**校验和 (Checksums)** 软件包系统维护关于文件的校验和和各种辅助信息。这可以用于验证已安装软件的有效性。此功能具有局限性；它旨在帮助你防止磁盘错误、文件意外覆盖或其他非系统级问题。在检测入侵方面，它的作用非常有限，因为入侵者可以使用软件包系统来安装被修改过的软件。

**升级与卸载 (Upgrades and Uninstallation)** 通过跟踪文件和依赖关系，软件包系统允许进行易的升级和卸载：告诉软件包系统升级或移除某个软件包，它就会替换或移除软件包中的每个文件。当然，这假设升级或卸载不会导致依赖关系问题；如果会导致，软件包系统将拦截该操作。

**二进制创建 (Binary Creation)** RPM 和 Debian 系统都提供了从源码创建二进制软件包（直接安装的包）的工具。如果你在特殊的 CPU 上运行 Linux，此功能将特别有用：即使开发者没有为你的 CPU 提供明确支持，你也可以下载源码并创建二进制软件包。从源码创建二进制软件包比通过传统方式编译源码具有优势，因为你随后可以使用软件包管理系统来跟踪单个文件，以此此类推。

RPM 和 Debian 系统都提供了所有基本功能，尽管它们的操作细节有所不同。这两个系统在某种意义上是互兼容的，因为它们的软件包文件和已安装数据库是不同的；你不能直接在基于 Debian 的系统上安装 RPM 软件包，反之亦然。存在转换格式的工具，开发者正在研究更好地整合这两种格式的方法。大多数发行版只安装一个软件包。虽然可以安装多个，但某些程序（如 *alien*）需要两者才能实现完整功能。同时使用两个系统安装软件是不可接受的，因为如果你使用 Debian 软件包安装了一个库，然后尝试安装一个依赖该库的软件包，RPM 将不会意识到该库已经安装并返回错误。

# 使用 RPM

Linux 世界流行的软件包管理器是 RPM 管理器 (RPM)。RPM 也可用于非 Linux 平台，尽管在 Linux 世界之外似乎使用较少。RPM 系统提供了前一节“软件包概念”中描述的所有工具，例如一个允许识别冲突和特定分部所有权的数据库。

# RPM 发行版与规范

Red Hat 为其自己的发行版开发了 RPM。然而，Red Hat 在通用公共许可协议 (GPL) 下发布了该软件，其他人可以在自己的发行版中自由使用它——而这恰恰发生了。某些发行版（如 Mandriva 和 Yellow Dog）基于 Red，因此它们将 RPM 作为许多其他部分的一部分。其他的（如 SUSE）借用了 Red Hat 的模板，但它们使用 RPM。当然，所有 Linux 发行版共享许多组件，即使是那些并非基于 Red Hat 的组件在很多方面也与它非常相似。因此，使用 RPM 的发行版组显示出巨大的变异，但它们都提供相同的基本工具，如 Linux 内内核、shell、X Server 等。

Red Hat 分为了三个发行版：Fedora 是家庭用户、学生和预算有限的企业用户青睐的可下载版本。Red Hat 的名称现在保留给该发行版的付费版本，更正式名称为 Red Hat Enterprise Linux (RHEL)。CentOS 是面向企业用户的免费分发版本。

# 使用 RPM

RPM 是一个跨平台工具。如前所述，某些非 Linux Unix 系统可以使用 RPM，尽管大多数系统不将其作为主要的软件包分发系统。RPM 支持任何 CPU 架构。Red Hat Linux 至少支持五种 CPU：x86、x86-64（又 AMD64、EM64 和 x64）、IA-64、Alpha 和 SPARC。如前提到的，Yellow Dog 是一个 PowerPC 发行版（它运行在基于 Apple PowerPC 的 Mac 和某些非 Apple 系统上），而 SUSE 可用于 x86、x86-64 和 PowerPC 系统。在大多数情况下，源码 RPM 是可以传输的——你可以使用源码为 x86、AMD64、PowerPC、Alpha、SPARC 或你喜欢的任何平台构建软件包。某些程序由架构无关脚本组成，因此无需重新编译。还有文档和配置包适用于任何 CPU。

RPM 软件包的命名规范如下：

```
packagename-a.b.c-x.arch.rpm
```

文件名的每个部分都有特定含义：

**软件包名称 (Package Name)** 第一部分 (packagename) 是软件包的名称，例如 rpm 或 samba-the Samba file and print server。注意同一个程序在不同的发行管理器可能有不同的名称。

**版本号 (Version Number)** 第二部分 (a.b.c) 是版本号，例如 3.6.5。版本号不需要用点分隔，但这是最常见的格式。版本号由程序分配。

**构建号 (Build Number)** 版本号后面的数字 (x) 是构建号（也称为维护者）。这代表了软件包维护者所做的更改。这些更改可能代表修改的启动脚本或配置文件、位置更改、添加文档，或者附加原始程序的补丁以修复错误或提高与 Linux 发行版的兼容性。许多发行管理器会在代码中添加字母以将它们的软件包与其他区分开来。注意这些数字在软件包管理器之间是不可比较的——George 构建的第 5 版本并不比 Susan 构建的第 4 版本更好。

**架构 (Architecture)** .rpm 扩展之前的最后一个部分 (arch) 是软件包的架构。i86 代码很常见；它代表为任何自 8038 的 CPU 编译的文件。某些软件包包含了针对 Pentium 或更新型号的优化（1586 或 1686），而非 x86 二进制软件包使用对应 CPU 的代码，例如 PowerPC 使用 ppc，x86-64 使用 x64。脚本、文档和其他架构无关的软件包通常使用 noarch 架构代码。该规则的主要例外是源码 RPM，它们使用 src 架构代码。
