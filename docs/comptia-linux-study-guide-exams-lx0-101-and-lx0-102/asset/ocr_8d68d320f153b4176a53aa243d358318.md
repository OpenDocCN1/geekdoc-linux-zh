# Package Dependencies and Conflicts

If you are using dpkg, you can use the --ignore-depends-package, --force-deps, and --force-conflicts parameters to overcome dependency and conflict problems in Debian-based systems. Because there's deviation in package names and requirements among Debian-based systems, these options are less often needed on systems.

# Upgrading or Rebuilding the Dependent-on Package

Officially, the proper way to overcome a package dependency problem is to install, upgrade, or replace the dependent-upon package. If a program requires, Qt 4.8 or greater, you should upgrade an older version (such as 4.4) to 4.8. To perform such an upgrade, you'll need to download and install the appropriate package. This usually isn't too difficult if the new package you came from a Linux distribution, especially if you use a meta-package such as Yum or APT; the appropriate dependent-upon package should come with the same distribution.

One problem with this approach is that packages installed for different distributions sometimes have differing requirements. If you run Distribution A and install a package that was built for Distribution B, the package will express dependencies in terms of Distribution B's files and versions. The appropriate versions may not be available in a form intended with Distribution A; and by installing Distribution B's versions, you can sometimes cause conflicts with other Distribution A packages. Even if you install the upgraded package and it works, you may run into problems in the future when it comes to install some other program or upgrade the distribution as a-whole—the upgrade installer may not recognize Distribution B's package or not be able to upgrade to its own newer version.

# Rebuilding the Problem Package

Some dependencies result from the libraries and other support installed on the computer that compiled the package, not from requirements in the underlying source code. If the software is recompiled on a system that has different packages, the dependencies will change, rebuilding a package from source code can overcome at least some dependencies.

If you use an RPM-based system, the command to rebuild a package is straightforward. You call `rpmbuild` (or rpm with old versions of RPM) with the name of the source package and use `--rebuild`, as follows:

```
# rpmbuild --rebuild packageName-version.src.rpm
```

Of course, to do this you must have the SRC for the package. When you execute this command, rpmbuild extracts the source code and executes whatever commands are required to build a new package--or sometimes several new packages. (One source RPM can build multiple binary RPMs.) The compilation process can take anywhere from a few seconds to seconds, depending on the size of the package and the speed of your computer. The result should be one or more new binary RPMs in /usr/src/distname/RPMS/arch, where distname is a distribution-specific name (such as redhat on Red Hat or packages on SUSE) and arch is your CPU architecture (such as i386 or 1586 for x86 or ppc for PowerPC). You can move these RPMs to any convenient location and install them just as you would any others.
