**Monitoring Log Files** In addition to checking the last few lines of a log file, tail can monitor a file on an ongoing basis, echoing lines to the screen as they are added to the file. You do this with the -f option to tail, as in `tail -f /var/log/messages`.

**Advanced Log Analysis Tools** Various packages exist expressly for the purpose of analyzing logs. For instance, there's Logcheck, which is part of the Sentry Tools package (http://sourceforge.net/projects/sentrytools/). This package comes with some distributions, such as Mandriva and Debian. Unfortunately, it requires a fair amount of customization for your own system, so it's most easily implemented if it comes with your system, preconfigured for its log file.

Log file analysis is a skill that's best learned through experience. Many log files are cryptic, and they can be cryptic in different ways for different programs. For instance, consider these entries:

+   - Apr 14 23:17:00 speaker /USR/SBIN/CRON[60266]: (george) CMD=/usr/bin/fetchmail -home/george/.fetchmailrc /dev/null
- Apr 14 23:17:52 speaker sshd[60331]: Accepted publickey for george from fffff:192.168.1.3 port 48139 ssh

These lines relate to two entirely events, but they have a similar format. Both entries begin with a time and the name of the computer on which the activity occurred (speaker in example). Next each line is an identifier for the program that logged the activity, with its PID number: `/USR/SBIN/CRON[60266]` and `sshd[60331]` in this example. Note that these names are generated by the programs that create the activity, so they aren't necessarily consistent or even accurate. For instance, there is no /USR/SBIN/CRON program, but there is `/usr/sbin/bin/cron`. (Recall that Linux has a case-sensitive filesystem.)

All of this information helps identify what logged the log data and when it did. The rest of the entry contains the actual log data. The first entry identifies a run on behalf of george—specifically, cron ran the name of a configuration file via the -f option, and redirected the output to /dev/null. The second entry (sshd) identifies a login from 192.168.1.3 on port 48139, again involving the **user george**.

You can use these entries to help identify malfunctioning services, security breaches, and doing so, though, requires at least some familiarity with the normal log file contents and other system details. For instance, in the preceding example, if your system has no george account, these entries should be suspicious but you must be familiar enough of the entries to spot that george is a username (or able to work it out). You must also know that your system should have no george account.

Overall, you should probably examine your log files from time to time to become familiar with their contents. This will help you spot abnormalities when the system begins misbehaving or when you use log files to track down an unwelcome visitor.
