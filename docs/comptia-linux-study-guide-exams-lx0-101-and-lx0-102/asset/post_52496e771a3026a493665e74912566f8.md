
# Using System Log Files

Record logger

- PID: The -i option returns the process ID (PID) of the logger process along with other data.

Output to Standard Error: You can echo data to standard error, as well as the log file, by the -s option. An interactive script might use this feature to alert users to problems.

Log Using Datagrams: The -d option causes logger to use datagrams rather than a stream connection to the system socket. This is an advanced feature that you should use only if you're instructed to do so in documentation or if you understand the networking issues.

Log a File: You can log contents of a file using the -f option. Be cautious with this option; if file is big, your system log file can grow to ridiculous size!

Identify a Priority: The -p pri option specifies a priority, as described earlier.

By default, logger includes its name in the log file as a tag. You can change this with the -t tag option. This is useful if you want to identify a script or program that created the log entry and doesn't record the fact that logger was involved in the process.

Specify a Socket: Ordinarily, logger calls the system log tools to do its job. You can log directly to a network socket using the -u socket if you prefer.

Specify a Message: If you don't specify a file using -f file, logger will log whatever type other options as the message to be logged. If you don't provide a message on the command line, logger accepts your input on subsequent lines as information to be logged. You should terminate input by pressing Ctrl+D.

As an example, suppose you want to log the message "shutting down for system maintenance" to the system log. You can do so by typing the following command:

```
$ shutting down for system maintenance
```

The result will be an entry like the following, probably in /var/log/messages:

```
Jul 29 14:09:50 nessus logger: shutting down for system maintenance
```

Parameters changes the details of what gets logged, as described. You can place a call to logger in a script as a way of documenting the script's activities. For instance, a system backup script might use logger to record details as its start and stop times and the number and size of the files it has backed up.

# Rotating Log Files

Log files are to retain information about system activities for a reasonable period of time, but system logging daemons provide means to control the size of log files. Left unchecked, log files can grow to consume all the available space on the partition on which they reside. To avoid this, Linux employs log file rotation tools. These tools rename and optionally compress the current log files, delete old log files, and force the logging system to begin using new log files.

The most common log rotation tool is a package called logrotate. This program is typically called on a regular basis via a cron job. (The section “Running Jobs in the Future” describes cron jobs in more detail.) The logrotate program consults a configuration file called /etc/logrotate.conf, which includes several default settings and typically refers to files in /etc/logrotate.d to handle specific log files. A typical /etc/logrotate.conf file includes comment lines, denoted by hash marks (#), as well as lines to various options, as illustrated by Listing 7.1.

# Listing 7.1: Sample /etc/logrotate.conf File

```
# Rotate logs weekly
weekly
# Keep 4 weeks of old logs
rotate 4
# Create new log files after rotation
create
# Compress old log files
compress
# Refer to files for individual packages
include /etc/logrotate.d
# Set miscellaneous options
notifempty
nomail
nolddir
# Rotate wtmp, which isn't handled by a specific program
/var/log/wtmp (
monthly
create 0664 root utmp
rotate 1
}
```

The lines in Listing 7.1 set options that are fairly self-explanatory or are well explained by the comments that immediately precede them—for instance, the weekly line sets the default log rotation interval once a week. If you see an option in your file that you don't understand, consult the man page for logrotate.

Because log rotation is handled by cron jobs that typically run late at night, it won't happen if a computer is routinely turned off at the end of the day. This practice is common with Windows workstations but with servers. Linux workstations should either be left running overnight as a general practice or be special tools to enable log rotation despite routine shutdowns. The anacron utility, described in the upcoming section “Using anacron,” is particularly well suited to the latter task.

The last few lines of Listing 7.1 demonstrate the format for the definition of a specific log file. These definitions begin with the filename for the file (multiple filenames may be listed, separated by spaces), followed by an open curly brace {. They end in a close curly brace }. Intervening lines set options that may override the defaults. For instance, /var/log/tmp definition in Listing 7.1 sets the monthly option, which tells logrotate to rotate this log file once a month, overriding the default weekly option. Such definitions are common in the individual files in /etc/logrotate.d, which are typically owned by the packages which process log files. The following are examples of features that are often set in these definitions:

**Compression Options**: Compression Options As noted, compress by default.

**New Log Files**: New Log Files As noted, create by default.

**Time Options**: Time Options daily, weekly, monthly.

**Size Options**: Size Options kilobytes, megabytes, gigabytes.

**Rotation Options**: Rotation Options rotate, size, size.
