# Understanding Network Packets

Modern networks operate on discrete chunks of data. Suppose you want to send a 100KB file from one computer to another. Rather than sending the file in one burst, your computer breaks it down into smaller chunks. The system might send 100 packets of 1KB each, for instance. This way, if there's an error sending one packet, the computer can resend just that packet rather than the entire file. (Many protocols include error-detection procedures.)

When the recipient receives packets, it must hold them on to and reassemble them in the correct order to re-create the data stream. It's not uncommon for packets to be delayed or lost in transmission, so error-recovery procedures are critical for protocols that handle large transfers. Some types of error recovery are handled transparently by the networking hardware.

There are several types of packets, and which can be stored within each other. For instance, Ethernet includes its own packet (known as a frame), and the packets generated by networking protocols that run atop Ethernet, such as those described in the next section, are stored within Ethernet frames. All told, a data transfer can involve several layers of wrapping and unwrapping. With each layer, packets from the adjacent layer may be merged or split up.

# Understanding Network Protocol Stacks

It's possible to think of network at various levels of abstraction. For instance, at one level, a network carries data packets for a specific network type (such as Ethernet); the data packets are addressed to specific computers on a local network. A description, while useful for a local network, isn't very useful for understanding higher-level network protocols, such as those that handle email transfers. These high-level protocols are typically described in terms of commands sent back and forth between computers, frequently without reference to packets. The addresses used at different levels also vary, as explained in the upcoming section "Using Network Addresses."

A protocol stack is a set of software that converts and encapsulates data between layers of abstraction. For instance, the stack can take the commands of transfer protocols, and the email messages that are transferred, and package them into packets. Another layer of the stack can take these packets and repackage them into Ethernet frames. There are several layers to any protocol stack, and they interact in highly specified ways. It's often possible to swap out one component for another at any given layer. For instance, at the top of each stack is a program that uses the stack, such as an email client. You can switch from one client to another without much difficulty; both rest atop the same stack. Likewise, if you change a network card, you change the driver for that card, which constitutes a very low layer in the stack. Applications above that driver can remain the same.

Each computer in a transaction requires a compatible protocol stack. When they communicate, the computers pass data down their respective stacks and send data to the partner system, which passes the data up its stack. Each layer on the receiving system sees the data as packaged by its counterpart on the sending computer.

Protocol stacks are frequently represented in graphics like Figure 8.2, which shows the configuration of the TCP/IP protocol stack that dominates the Internet today. As shown in Figure 8.2, clients at the application layer initiate data transfers. These requests pass through the transport, internet, and link layers on the client, whereupon they leave the client system and pass to the server system. (This transfer involve a lot of complexity not depicted in Figure 8.2.) On the server, the process reverses itself, with the server program running at the application layer replying to the client program. This reply reverses the journey, traveling down the server computer's stack, across the network, and up the stack on the client. A full-fledged network connection can involve many back-and-forth data transfers.

When spelled with an uppercase I, the word Internet refers to the globe-spanning network of networks with which you are familiar. When spelled with a lowercase i, the word internet refers to any collection of networks. An internet in this sense could be a couple of small networks in somebody's basement. Networking protocols such as TCP/IP can connect any internet up to and including the Internet.

Each component of the sending system is equivalent to a layer on the receiving system, but these layers have different models of network card at the link, or you can use entirely hardware such as Ethernet and Token Ring if some intervening system translates between them. The computers may run different OS. What is important is that the stacks operate in compatible ways. Linux was designed with TCP/IP in mind, and the Internet is built atop TCP/IP. Other protocol stacks are available, and you may occasionally run into them. In particular, NetBEUI is the original protocol for Windows, AppleTalk was Apple's initial protocol, and IPX/SPX was Novel's favored stack. All three are fading in importance, but you may still need to use them in some environments. Linux supports AppleTalk and IPX/SPX but not NetBEUI.

# Knowing TCP/IP Protocol Types

Within TCP/IP, several different protocols can be classified as falling on one of four layers of the TCP/IP stack, as shown in Figure 8.2. The most important internet- and transport-layer protocols are the building blocks for application-layer protocols with which you interact more directly. These include:

- **IP**: The Internet Protocol (IP) is the core protocol in TCP/IP networking. It is an internet-layer (as a network-layer or layer 2) protocol. IP provides a “best effort” method for transferring data between—that is, the packets are not guaranteed to reach their destinations. Other components of the TCP/IP stack must deal with these issues and have their own ways of doing so. IP is also the portion of TCP/IP with which IP addresses are associated. (The Coming of IPv6 sidebar describes a change in the IP portion.)

- **ICMP**: The Internet Control Message Protocol (ICMP) is a simple protocol for communicating data. ICMP is often used to send error messages between computers—to signal that a requested service is not available. This is often done by modifying an IP packet and returning it to its sender, which means ICMP is technically an internet-layer protocol, although it relies upon IP. In most cases, you won't use programs that generate ICMP on demand; they are created behind the scenes as you use other protocols. One exception is the ping program, which is described in more detail in "Testing Connectivity."

- **UDP**: The User Datagram Protocol (UDP) is the simplest of common transport-layer (layer 3) TCP/IP protocols. It doesn't provide sophisticated procedures to correct for out-of-order packets, guarantee delivery, or otherwise improve the limitations of IP. This can be a fact, but it also means that UDP can be faster than more sophisticated tools that provide improvements to IP. Common application-layer protocols that are built atop UDP include the Domain Name System (DNS), the Network File System (NFS), and streaming-media protocols.

- **TCP**: The Transmission Control Protocol (TCP) may be the most widely used transport-layer in the TCP/IP stack. Unlike UDP, TCP creates full connections with error checking as well as other features. These features simplify the creation of network protocols that exchange large amounts of data, but the features come at a cost: TCP imposes a small performance penalty. Most of the application-layer protocols with which you may be familiar, including the Mail Transfer Protocol (SMTP), the Hypertext Transfer Protocol (HTTP), and the File Transfer Protocol (FTP), are built atop.

You may notice that the TCP/IP stack is built up of two of the stack's protocols: TCP and IP. This is because these two protocols are so important for TCP/IP networking generally. TCP/IP, though, is much more than these two protocols; it includes additional protocols, most of which (below the application layer) are rather obscure. On the other hand, a TCP/IP exchange does not use both TCP and IP—it could be a UDP or ICMP exchange, for instance.

# The Coming of IPv6

The IP portion of TCP/IP has been version 4 for many years. A major upgrade to it is underway, and it goes by IP version 6. Its most important improvements over IPv4 include the following:

- IPv4 supports a theoretical maximum of 4 billion addresses. Although this may sound like plenty, those addresses have not been allocated as efficiently as possible. Therefore, as the Internet has expanded, the number of truly available addresses is shrinking at a rapid rate—in fact, the global pool is already exhausted, although IPv4 addresses remain available from local registries in many parts of the world, as of late 2012. IPv6 raises the number of addresses to $2^{128}$, or $3.4\times10^{38}$. This is enough to give every square millimeter of land surface Earth $2.2\times10^{18}$ addresses.
- IPv6 makes multicasting—the simultaneous transmission of data from one computer to multiple recipients—part of the basic IP specification, compared to an optional (albeit commonly implemented) part of IPv4.
