### Extracting Data from RPMs

Occasionally you may extract data from RPMs without installing the package.
For instance, this can be a good way to retrieve the original source code from a source
RPM for compiling the software without using the RPM tools or to retrieve fonts or
other-program data for use on a non-RPM system.
RPM files are actually modified cpio archives; converting the files into cpio files is relatively straightforward, whereupon you can use cpio to retrieve the individual files.
To do this, you need to use the rpm2cpio program, which ships with most Linux distributions. (You can use this tool on distributions that don't use RPM.) This program takes
a single argument—the name of the RPM file—and outputs the cpio archive on standard out. So if you want to create a cpio archive, you must redirect the output:

```
$ rpm2cpio samba-3.6.5-86.fc17.1.src.rpm > samba-3.6.5-86.fc17.1.src.cpio
```

> The redirection operator (>) is described in more detail in Chapter 1,
"Exploring Linux Command-Line Tools," as is the pipe operator (|), which
is mentioned shortly. Chapter 4, "Managing Files," describes cpio in more detail.

You can extract the data using cpio, which takes the -i option to extract an
archive and --make-directories to create directories:

```
$ cpio -i --make-directories samba-3.6.5-86.fc17.1.src.cpio
```

### Using RPM

Alternatively, you can use a pipe to link these two commands together without creating an intermediary file:

```
$ rpm2cpio samba-3.6.5-86.fc17.1.src.rpm | cpio -i --make-directories
```

In either case, the result is an extraction of the files in the archive in the current directory. In the case of binary packages, this is likely to be a series of subdirectories that mimic the layout of the Linux root directory—that is, usr, libc, etc., and so on, and precisely which directories are included in the package. For a source package, the result of the extraction process is likely to be a source code tarball, a .spec file (which holds information RPM uses to build the package), and perhaps few some patches.

![](img/35f616c7eba4e79e12bfd762129c5d27_109_0.png)

When you're extracting data from an RPM file using rpm2cpio and cpio, create a holding subdirectory and extract the data into this subdirectory. This practice will ensure that you can find all the files. If you extract your files in your home directory, some might get lost among your other files. If you extract files as root in the (/) directory, you could conceivably overwrite files that you want to keep.

Another option for extracting data from RPMs is to use alien, which is described later in “Converting Package Formats.” This program can convert an RPM into a Debian package or a tarball.

### Using Yum

Yum (http://yum.baseurl.org), mentioned earlier, is one of several meta-packagers—it enables you to install a package and all its dependencies using a single command. When using Yum, you don't even need to search in or download the package files, because Yum does this for you in one or more repositories—Internet sites that hold RPM files for a particular distribution.

Yum originated from the obscure Yellow Dog Linux distribution, but it's been adopted by Red Hat, CentOS, Fedora, and some other RPM-based distributions. Yum is not used by RPM-based distributions; though SUSE and Mandriva have just two, each their own meta-apts. Debian-based distributions generally employ the Advanced Package Tools (APT), as described later in “Using apt-get.” Nonetheless, because of the popularity of Red Hat, CentOS, and Fedora, knowing Yum can be valuable.

The best way to use Yum is with the yum command, which has the following syntax:

```
yum [options] [command] [package...]
```

Which options are available depend on the command you use. Table 2.3 describes common yum commands.

### TABLE 2.3 Common yum commands

| Command | Description |
| --- | --- |
| install | Installs one or more packages. |
| update | Updates specified packages to the latest version. |
| check-update | Checks if updates are available. |
| upgrade | Works like update, but handles obsolete packages. |
| remove | Deletes a package from the system. |
| list | Lists installed packages. |
| provides | Displays what a package provides. |
| search | Searches package names for a keyword. |
| info | Displays information about a package. |
| clean | Cleans up Yum cache. |
| shell | Enters the Yum shell. |
| deplist | Displays dependencies of package. |
| localinstall | Installs specified local files. |
| localupdate | Updates specified packages using local files. |
| deplist | Displays dependencies of package. |

### Using RPM

In cases, using Yum is easier than using RPM directly, because Yum finds the latest available, downloads it, and installs any required dependencies. Yum has its limits, though; it's only good as its repositories.

![](img/35f616c7eba4e79e12bfd762129c5d27_111_0.png)

If you use Yum to automatically upgrade all packages on your system, you're effectively giving control of your system to the distribution maintainer. Although Red Hat or other distributions are unlikely to break into your computer in this way, an automatic update with minimal supervision could easily break something.

- 1. Log into the Linux system as a normal user.
- 2. Acquire a package to use for testing purposes. You can try using a package from your distribution that you know you've not installed; but if you try a random package, you might find it's already installed or has unmet dependencies. This lab uses as an example the installation of zsh-4.3.1-fc17.x86_64.rpm, a shell that's not installed by default most systems, from the Fedora 17 DVD into Fedora 17 system. You must adjust the commands as necessary if you use another RPM file.
- 3. Launch an xterm from the desktop environment's system if you use a GUI login.
