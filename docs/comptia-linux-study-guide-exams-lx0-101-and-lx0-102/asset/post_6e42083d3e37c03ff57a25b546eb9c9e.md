Routing Information You can use the --route or -r parameter to obtain a routing table listing similar to what the route command displays.

Keep in mind that netstat is a very powerful tool, and its options and output aren't entirely consistent from one distribution to another. You may want to peruse its man page and experiment with it to learn what it can do.

## Examining Raw Network Traffic

One network troubleshooting tool is tcpdump. This utility is a packet sniffer, which is a program that can intercept network packets and log or display them on the screen. Packet sniffers are useful diagnostic tools because they enable you to verify that a computer is actively receiving data from other computers. They also enable you to examine the data in its raw form, which can be useful if you understand enough of the protocol’s implementation details to spot problems.

![](img/35f616c7eba4e79e12bfd762129c5d27_468_0.png)

Although packet sniffers are useful diagnostic tools, they can also be abused. For instance, unscrupulous individuals can run packet sniffers to capture passwords that others send over the network. Depending on your network configuration, this trick can work if the packet sniffer isn't running on either the sending or the receiving computer. For this reason, many organizations have policies forbidding the use of packet sniffers except under limited circumstances. Thus, before running a packet sniffer, you should obtain written permission to use such a program from an individual who is authorized to grant such permission. Failure to do so can lead you into serious trouble, possibly up losing your job or even being sued.

## Diagnosing Network Connections

In its most basic form, you can use tcpdump by typing its name:

```bash
tcpdump
tcpdump: verbose output suppressed, use -v or -vv for full protocol decode listening on eth0, link-type EN10MB (Ethernet), capture size 96 bytes
19:31:55.032759 IP speaker.example.com.631 > 192.168.1.255:UDP, - length: 139
19:31:55.050400 IP nessus.example.com.35313 > speaker.example.com:42676+? 275.1.168.192-in-addr. (44)
19:31:55.060886 IP speaker.example.com.domain > nessus.example.com.35313:42676 Ndomain* 0/1 (010)
```

The first thing to note about this command is that you must run as root; ordinary users aren't allowed to monitor network traffic in this way. Once it runs, tcpdump summarizes what it does and then begins printing lines, for each packet it monitors. (Some of these lines can be quite busy and so may take more than one line on your.) These lines include a time stamp, a stack identifier (IP in all of these), the origin name or IP address and port, the destination name or IP address and port, and packet-specific information. Ordinarily, tcpdump keeps displaying packets indefinitely, so you must terminate it by pressing Ctrl+C. Alternatively, you can pass it with the -c option to display n packets and quit.

Even basic approach can be very helpful. For instance, consider the preceding example of three packets, which was captured on nessus.example.com. This computer successfully received one packet (addressed to 192.168.1.255) from speaker.example.com, sent a packet to speaker, and received a packet directed at nessus.example.com rather than as a broadcast. This sequence that at least minimal communication exists between these two computers. If you were having problems establishing a connection, you could rule out whole range of possibilities, such as faulty cables or a firewall that was blocking traffic.

If you need more information, tcpdump provides several options that enhance or modify its output. It includes -a to display packets in ASCII, -D to display a list of interfaces, -n to display addresses numerically, -v (and -vv) to display additional packet information, and -w to write the captured packets to the specified file. Consult tcpdump's man page for more details on these.

## Using Additional Tools

In addition to specialized network programs, you can use some common programs as debugging tools. One of the most useful of these may be Telnet. This program is mainly a remote login tool; type the program followed by the name of a remote system to receive a login prompt on that system:

```bash
$ telnet speaker
Trying 192.168.1.1...
Connected to speaker.
Escape character is '^'.
speaker login:
Password:
Last login: Mon Apr 25 21:48:44 from nessus.example.com
Have a lot of fun...
harry@speaker:>
```

Telnet is a poor choice as a remote login protocol because it's entirelyencrypted. As a general rule, you should remove Telnet from your system and never use the telnet client. It can be a useful lowest-denominator for sufficiently protected networks, and the telnet client is also a handy tool for debugging, as described next. Chapter 10 describes SSH, which is a much safer alternative to Telnet.

You can use Telnet to debug remote protocols; if you give it a port number after the hostname, the telnet program connects to that port, enabling you to interact with the server:

```bash
$ telnet speaker 25
Trying 192.168.1.1...
Connected to speaker.
Escape character is '^'.
220 speaker.example.com ESMTP Postfix
HELO nessus.example.com
250 speaker.example.com
```

After connecting, I sent a HELO code, which is used by SMTP to identify a client; the remote system responded with 250 code, which indicates an accepted command. Of course, to use Telnet in this, you must know a great deal about the protocol. Even without this knowledge, you can use Telnet to test whether a server is running: If you try to connect but get a Connection refused error message, you know that remote server isn't running or is inaccessible for some reason (say, because it's blocked by a firewall). If you get in (to the Escape character shown in the earlier example or beyond), the server is running, although it may not be working correctly. This works only for protocols that use TCP. Some tools use UDP instead, and Telnet won't connect with them.

Sometimes the File Transfer Protocol (FTP) can be a useful diagnostic tool, as well. This program, as its name suggests, allows you to transfer files between systems. To use it, type the program followed by the FTP server's name. You'll then see a log prompt and be able to issue FTP commands:

```bash
$ FTP speaker
+   Connected to speaker.
220 (vsFTPD 1.2.1)
Name (speaker:harry): harry
530 Please login with USER and PASS.
SSL not available
331 Please specify the password.
Password:
230 Login successful.
Remote system is UNIX.
Using binary mode to transfer files.
ftp> get zathras.wav
local: zathras.remote: zathras.wav. Consider using PASV.
200 PORT command successful.
150 Opening BINARY mode data connection for zathras.wav (109986 bytes).
226 File send OK.
109986 bytes received in 0.104 secs (MB/s)
ftp> quit
221 Goodbye.
```

This example retrieves a single file, zathras.wav, from the remote computer. The basic ftp client displays a file size, transfer time, and transfer rate (MB/s—in other words, 1 x 10^3 KiB/s, or 100 KiB/s). This is a useful way to test transfer speed, although you'll get more reliable results with files that are several hundred kilobytes or larger in size. In addition to get, you can issue commands as put to upload a file; ls to display the remote system's directory contents; cd to change directories on the remote system; delete to remove a file; and quit or exit from the program. You can use the help or ? to see a list of available FTP commands.

Like Telnet, FTP is a poor choice of protocol for security reasons. The SSH protocol that can substitute for Telnet can also handle FTP duties. One important exceptions to the rule not to use FTP: anonymous FTP sites are a common method of distributing public files on the Internet. You can download Linux itself from anonymous FTP sites. These sites typically take a username of anonymous and password (your email address is the conventional reply) and give you read access to contents. In most cases, you can't upload files to anonymous FTP sites, and you can access only a limited number of files.
