service ftp

```
{
    socket_type = stream
    protocol    = tcp
    wait        = no
    user        = root
    server      = /usr/sbin/in.ftpd
    server_args = -1
}
```

One additional xinetd.conf parameter is commonly present: disable. If you include the line `disable = yes` in a server definition, xinetd ignores the entry. Some server packages install startup files in /etc/xinetd.d that have this option by default; you must edit the file and change it to `disabled = no` to enable the server. You can also disable a set of servers by listing their name in the defaults section of the main xinetd.conf file on a line called disabled, as `disabled = ftp shell`.

As with inetd, after you make changes to xinetd's configuration, you must restart the super server. You do this by typing a command similar to the one used to restart inetd. With that command, you can use reload or restart, with similar effects:

```bash
# /etc/init.d/xinetd restart
```

## Controlling Access via xinetd

Security is handled on a server-based basis through the use of configuration parameters in /etc/xinetd.conf or server-specific configuration files. Some of these options are similar to the function of hosts `allow` and `deny`:

**Network Interface** The bind option allows xinetd to listen on only one network interface for the service. For instance, you can specify `bind=192.168.1.7` on a router to listen only on the Ethernet card associated with that address. This feature is extremely useful in routers but isn't useful for computers with no network interface. You can however use this option to bind a server only to the loopback interface, 127.0.0.1, if a server should be available only locally. You might do this with a configuration tool like Samba. A synonym for this option is `only`.

**Allowed IP or Network Addresses** You can use the `only` option to specify IP addresses, networks (as in `192.168.0.0/24`), or computer names on that line, separated by spaces. The result is that xinetd will accept connections from these addresses, like TCP Wrappers' `allow`.

**Disallowed IP or Network Addresses** The `no_access` option is the opposite of `from`; you list computers or networks that you want to blacklist. This is similar to the `hosts.deny` file of TCP Wrappers.

**Access Times** The access_times option sets times during which users may access the server. The time range is specified in the form hour:minute using a 24-hour clock. Note that this option affects only the times during which the server will respond. If `access_times` option is set to `08:00-17:00`, nobody may continue using the system well beyond that cutoff time. You should enter these options into /etc/xinetd.d files that correspond to the servers you want to protect. Place the lines between the opening brace `{` and closing brace `}` for the service. If you want to restrict all xinetd-controlled servers, you can place the entries in the defaults section in /etc/xinetd.conf.

Some servers provide access control mechanisms similar to those of TCP Wrappers. For instance, Samba provides allows options that work like hosts files. These options are most common on servers that are awkward or impossible to run via inetd or xinetd.

## Configuring Firewall

Although the exam objectives don't mention firewalls, you should be familiar with the concept. A firewall is a computer or software that restricts access to other computers or runs on a single computer to protect it alone. Broadly speaking, two types of firewalls exist: packet-filter firewalls, which work by blocking or permitting access based on low-level information in individual data packets (such as source and destination IP addresses and ports), and proxy filters, which partially process transactions (such as page retrieval) and block or deny access based on high-level features (such as the filename of an image).

In Linux, the kernel includes packet-filter firewall capabilities, which can be programmed via iptables. You can set rules by typing iptables followed by various options that define specific restrictions, such as limits on the IP addresses that may access a specific network port. Creating an effective firewall requires learning iptables and writing a script that can be repeatedly used to set rules.

Many distributions make things easier by providing a generic script that you can configure using a GUI tool. These tools are generally designed for protecting a single computer against unwanted outside access. Check your distribution's GUI system administration options for a firewall configuration tool. You may be able to set security based on a few levels (high, medium, and low security, for instance) or in a somewhat more refined manner.

Linux can also function as a firewall that protects an entire network; however, such a configuration is likely to require in-depth knowledge of iptables, as well as topics such as configuring Linux as a router.

## Unused Servers

Quite a few servers ship with Linux distributions, which can be a great advantage—you don't need to hunt for servers you want to run. On the other hand, this very advantage can be a drawback; if you're not careful, you can end up running a server and not even realize it's installed! For this reason, you should periodically search for servers and shut down any that you find aren't really needed. You must begin this task by locating unused servers. Several tools to do this exist, such as netstat, lsof, and many network scanners. You can also search your local configuration files for clues about what may be running. Disabling unused servers can be done by uninstalling the package or by reconfiguring.

## Using netstat

One way to begin network security is to look for network activity or open ports on a computer. One tool that can help in this respect is netstat. The program is the Swiss army of network status tools; it provides many options and output formats to deliver information about routing tables, interface statistics, and so on.
