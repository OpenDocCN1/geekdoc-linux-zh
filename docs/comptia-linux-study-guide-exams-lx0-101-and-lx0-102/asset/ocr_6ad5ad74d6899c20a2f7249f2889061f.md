# Chapter 9 • Writing Scripts, Configuring Email, and Using Databases

At each step in a relay chain, email is altered. Most important, each server adds a header to the email, which is a line that provides information about the message. In particular, mail servers add Received: headers to document the path the mail has taken. In theory, this enables you to trace the mail back to its source. Unfortunately, spammers and other email abusers have learned to forge emails, which greatly complicates such analysis.

Because an SMTP server can function as both a server (receiving mail from other systems) and a client (sending mail to other systems), you must deal with both sides of the equation. For the most part, this chapter and the exam don't cover all these details, just a few of them. Sometimes a computer never runs in one role or the other, which can simplify matters—but you must be careful not to accidentally configure the computer incorrectly. In particular, relay configurations, in which a mail server relays mail from anybody, and this security implications of running an SMTP server can be secured in "Securing Your Email Server."

On Linux, email is still holding messages for each user, typically in a file at /var/spool/mail1—instance, /var/spool/mail1/ mail for the user bent. Some email servers store mail in subdirectories of the users' home directories, though this incoming mail file or directory is referred to as the user's spool.

> You may recall the userdel command, in Chapter 7, includes options related to the handling of users' mail pools. If you delete a user account but leave the user's mail pool intact, the mail can still be accessed. If the mail software stores mail in /var/spool/mail/, leftover mail can cause problems if you re-use an old username. Email can be sent as received. The traditional Linux approach to sending email is to have a program contact the mail server to send email. The local mail server contacts its outgoing server, as in Figure 9.1. Most Linux clients (aka mail user agents, or MUAs), as well similar programs on other platforms, provide the option to directly contact a remote SMTP server when sending email. Such a configuration slightly simplifies the email path but can make operation unreliable if the local network goes down. If your email client talks to an SMTP server that runs locally, the email can be queued for delivery by the SMTP server even if the network is temporarily down.
