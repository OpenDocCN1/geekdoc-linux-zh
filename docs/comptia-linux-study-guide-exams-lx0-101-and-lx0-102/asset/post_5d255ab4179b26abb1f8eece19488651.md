
# Package Concepts

Linux package management tools are intended to build and modify this house of cards by tracking what software is installed. The information that the system maintains avoids problems in several ways:

**Packages** The most basic information that package systems maintain is information about software *packages*—that is, collections of files that are installed on the computer. Packages are usually distributed as single files that are similar to [tarballs](https://www.example.com) (archives created with the tar utility and universally compressed with gzip or bz2) or zip files. Once installed, most packages consist of dozens or hundreds of files, and the package system tracks them all. Packages include additional information that aids in the subsequent duties of package management systems.

**Installed Database** Package systems maintain a database of installed files. The database includes information about every file installed via the package system, the name of the package to which each of files belongs, and additional information.

**Dependencies** One of the most important types of information maintained by the package system is *dependency information*—that is, the requirements of packages for one another. For instance, if SuperProg relies on UltraLib to do its work, the package database records this information. If you attempt to install SuperProg when UltraLib isn't installed, the package system won't let you do so. Similarly, if you attempt to uninstall UltraLib when SuperProg is installed, the package system won't let you do so. (You can override these prohibitions, as described later in "Forcing the Installation." Doing so is undesirable, though.)

**Checksums** The package system maintains checksums and assorted ancillary information about files. This can be used to verify the validity of the installed software. This feature has limits; it's intended to help you prevent disk errors, accidental overwriting of files, or other non-system problems. It is of limited use in detecting intrusions, where an intruder could use the package system to install altered software.

**Upgrades and Uninstallation** By tracking files and dependencies, package systems permit easy upgrades and uninstallation: tell the package system to upgrade or remove a package, and it will replace or remove every file in the package. Of course, this assumes that the upgrade or uninstallation doesn't cause dependency problems; if it does, the package system will block the operation.

**Binary Creation** Both the RPM and Debian systems provide tools to create binary packages (those that are installed directly) from source code. This feature is particularly helpful if you're running Linux on a peculiar CPU: you can download source code and create a binary package even if developers didn't provide explicit support for your CPU. Creating a binary package from source has advantages over compiling source in more conventional ways, because you can then use the package management system to track individual files, and so on.

Both the RPM and Debian systems provide all basic features, although the details of their operation differ. These two systems are incompatible with one another in the sense that their package files and installed databases are different; you can't directly install an RPM package on a Debian-based system or vice versa. Tools to convert formats exist, and developers are working on ways to better integrate the two formats. Most distributions install one package. It's possible to install more than one, though some programs (such as *alien*) require both for full functionality. Using both systems to install software is inadmissible because if you install a library using a Debian package and then try to install an package that relies on it, RPM won't realize the library is already installed and will return an error.

# Using RPM

The most popular package manager in the Linux world is RPM Manager (RPM). RPM is also available on non-Linux platforms, although it seems less used outside the Linux world. The RPM system provides all the tools described in the preceding section, "Package Concepts," such as a database that allows for identifying conflicts and ownership of particular particles.

# RPM Distributions and Conventions

Red Hat developed RPM for its own distribution. Red Hat released the software under the General Public License (GPL), however, others have free to use it in their own distributions—and this is precisely what happened. Some distributions, such as Mandriva and Yellow Dog, are based on Red, so they use RPM as many other parts. Others, such as SUSE, borrow from the Red Hat template but they use RPMs. Of course, all Linux distributions share many components, even those that weren't originally based on Red Hat are very similar to it in many ways. As a result, the group of RPM-using distributions shows substantial variability, but all of them provide the same basic tools, such as the Linux kernel, shells, an X server, and so on.

Red Hat has splintered into three distributions: Fedora is the downloadable version favored by home users, students, and businesses on a tight budget. The Red Hat name is now reserved for the pay version of the distribution, known more formally as Red Hat Enterprise Linux (RHEL). CentOS is freely distributable version intended for enterprise users.

# Using RPM

RPM is a cross-platform tool. As noted earlier, some non-Linux Unix systems can use RPM, although most don't use it as their primary package-distribution system. RPM supports any CPU architecture. Red Hat Linux is available for at least five CPUs: x86, x86-64 (aka AMD64, EM64, and x64), IA-64, Alpha, and SPARC. As mentioned earlier, Yellow Dog is a PowerPC distribution (it runs on Apple PowerPC-based Macs and some non-Apple systems), and SUSE is available on x86, x86-64, and PowerPC systems. For the most part, source RPMs are transportable across architectures—you can use the same source to build packages for x86, AMD64, PowerPC, Alpha, SPARC, or any other platform you like. Some programs are composed of architecture-independent scripts and so no recompilation. There are also documentation and configuration packages that work on any CPU.

The convention for naming RPM packages is as follows:

```
packagename-a.b.c-x.arch.rpm
```

Each of the filenames has a specific meaning:

**Package Name** The first component (packagename) is the name of the package, such as rpm or samba-the Samba file and print server. Note that the same program may have different names by distribution managers.

**Version Number** The second component (a.b.c) is the version number, such as 3.6.5. The version number doesn't have to be period-separated numbers, but that's the most common format. The program assigns the version number.

**Build Number** The number following the version number (x) is the build number (also known as the maintainer). This represents minor changes made by the package maintainer, not by the program. These changes may represent altered startup scripts or configuration files, changed locations, added documentation, or patches attached to the original program to fix bugs or to make the program more compatible with the Linux distribution. Many distribution managers add a letter to the code to distinguish their packages from others. Note that these numbers are not comparable across package managers—George's build 5 of a package is not an improvement on Susan's build 4 of the same package.

**Architecture** The final component preceding the .rpm extension (arch) is the package's architecture. The i86 code is common; it represents a file compiled for any CPU from the 8038 origin. Some packages include optimizations for Pentiums or newer (1586 or 1686), and non-x86 binary packages use codes for their CPUs, as ppc for PowerPC CPUs or x86-64 for. Scripts, documentation, and other CPU-independent packages generally use the noarch architecture code. The main exception to this rule is source RPMs, which use the src architecture code.
