
## Chapter 2 • Managing Software

![](img/35f616c7eba4e79e12bfd762129c5d27_128_0.png)

Although alien requires both RPM and Debian package systems, it doesn't use the database-features of these packages unless you use the --install option. The presence of a foreign package manager isn't a problem as long as you don't use it to install software that might duplicate or conflict with your package manager.

The basic syntax of alien is as follows:

```
alien [options] file[...]
```

The most important options are --to-deb, --to-rpm, --to-slp, and --to-tgz, which convert to Debian, RPM, Stampede, and tar format, respectively. (If you omit the destination format, alien assumes you want a Debian package.) The --install option installs the converted package and removes the converted file. Consult the alien man page for additional options.

For instance, suppose you have a Debian package called `someprogram-1.2.3-4_1386.deb`, and you want to create an RPM from it. You can issue the following command to create an RPM called `someprogram-1.2.3-5.1386.rpm`:

```bash
# alien --to-rpm tarball.gz
```

If you use a Debian-based system and want to install a tarball but keep a record of the files it contains in your Debian package database, you can do so with the following command:

```bash
--install binary-tarball.tar.gz
```

It's important to remember that converting a tarball converts the files in the directory structure of the original tar using the system's root directory as the base. Therefore, you may need to unpack the tarball, juggle files around, and repack to get the desired results prior to installing with alien. For instance, suppose you have a binary tarball that creates a directory called `program-files`, with bin, man, and lib directories under this. The intent may have been to unpack the tarball in /usr or /usr/local and create links for critical files. To convert this to an RPM, you can issue the the following commands:

```bash
# tar xvf program.tar.gz
# mv program-files usr
# tar cvf program.tgz usr
# rm -r usr
# alien --to-rpm program.tgz
```

By renaming the program-files directory to usr and creating a new tarball, you created a tarball that, when converted to RPM format, will have files in the locations you want—usr/bin, /usr/man, and /usr/lib. You might need to perform more extensive modifications, depending on the contents of the original tarball.

## Package Dependencies and Conflicts

Although package installation often proceeds smoothly, sometimes it doesn't. The usual sources of problems relate to unsatisfied dependencies or conflicts between packages. The RPM and Debian package management systems are intended to help you locate and resolve problems, but on occasion (particularly when mixing packages from different vendors), they can actually cause problems. In either event, if you manage to recognize these errors and know how to resolve them.

If you use a meta-packager, such as Yum or APT, for all your package management, you're much less likely to run into problems with package dependencies and conflicts. These problems are most likely to arise when you install lone packages, especially those from unusual sources.

## Real and Imagined Package Dependencies Problems

Package dependencies and conflicts can arise for a variety of reasons, including the following:

- **Missing Libraries or Support Programs**: One of the most common dependency problems is caused by a missing support package. For instance, all KDE programs rely on Qt, a widget set that provides assorted GUI controls. If Qt isn't installed, you won't be able to install any KDE packages using RPMs or Debian packages. Libraries—support code that can be used by many different programs as if it were part of the program itself—are particularly common sources of problems in this respect.
- **Incompatible Versions or Support Programs**: Even if a library or support program is installed on your system, it may be the wrong version. For instance, if a program requires Qt 4.3, it won't do much good. Fortunately, Linux-naming conventions enable you to install multiple versions of a library in case you have programs with competing requirements.
- **Duplicate Files or Features**: Conflicts arise when one package includes files that are already installed and belong to another package. Occasionally, broad features conflict as well, as in two Web server packages. Feature conflicts are usually accompanied by name conflicts. Conflicts are most common when mixing packages intended for different distributions, because distributions split files across different ways.
- **Mismatched Names**: RPM and Debian package management systems give names to their packages. These names don't always match across distributions. For this reason, if one package checks for another package by name, the first package may not install on another distribution, even if the appropriate package is installed, because that target has a different name.

## Workarounds for Package Dependency Problems

When you encounter an unmet dependency or conflict, what can you do about it? There are several approaches to these problems. Some of these approaches work well in some situations but not others, so you should review the possibilities carefully. The options include forcing the installation, modifying your system to meet the dependency, rebuilding the package from source code, and finding another version of the package.

## Forcing the Installation

One approach is to ignore the issue. Although this sounds risky, it's appropriate in some cases involving failed RPM or Debian dependencies. For instance, if the dependency is on a package that you installed not by compiling the source code, you can safely ignore the dependency. When using rpm, you can tell the program to ignore failed dependencies by using the --nodeps parameter:

```bash
# rpm -i apack.rpm --nodeps
```

You can force installation over other errors, such as conflicts with existing packages, by using the --force parameter:

```bash
# rpm -i apack.rpm --force
```

![](img/35f616c7eba4e79e12bfd762129c5d27_130_0.png)

> Do not --nodeps or --force as a matter of course. Ignoring the dependency checks can lead you into trouble, so you should use these options only when you need to do so. In case of conflicts, the error messages you get when you first try to install without --force will tell you which packages' files you'll be replacing, so be sure you back them up or are prepared to reinstall the packages in case of trouble.

## Package Dependencies and Conflicts

If you are using dpkg, you can use the --ignore-depends-package, --force-deps, and --force-conflicts parameters to overcome dependency and conflict problems in Debian-based systems. Because there's deviation in package names and requirements among Debian-based systems, these options are less often needed.

## Upgrading or Rebuilding the Dependent Package

Officially, the proper way to overcome a dependency problem is to install, upgrade, or replace the dependent-upon package. If a program requires Qt 4.8 or greater, you should upgrade an older version (such as 4.4) to 4.8. To perform such an upgrade, you'll need to download and install the appropriate package. One problem with this approach is that packages installed for different distributions sometimes have differing requirements. If you run Distribution A and install a package that was built for Distribution B, you can sometimes cause conflicts with other Distribution A packages. Even if you install the upgraded package and it works, you may run into problems in the future when it comes to upgrading the distribution as whole.

## Rebuilding the Problem Package

Some dependencies result from the libraries and other support installed on the computer that compiled the package, not from requirements in the underlying source code. If the software is recompiled on a system that has different packages, the dependencies will change; rebuilding a package from source code can overcome at least some dependencies.

If you use an RPM-based system, the command to rebuild a package is straightforward. You call rpmbuild (or rpm with old versions of RPM) with the name of the source package and use --rebuild, as follows:

```bash
# rpmbuild --rebuild packageName-version.src.rpm
```

Of course, to do this you must have the SRC for the package. When you execute this command, rpmbuild extracts the source code and executes whatever commands are required to build a new package--or sometimes several new packages. (One source RPM can build multiple binary RPMs.) The compilation process can take anywhere from a few seconds to minutes, depending on the size of the package and the speed of your computer. The result should be one or more new binary RPMs in /usr/src/distname/RPMS/arch, where distname is a distribution-specific name (such as redhat on Red Hat or packages on SUSE) and arch is your CPU architecture (such as i386 or i5886 for x86 or ppc for PowerPC). You can move these RPMs to any convenient location and install them just as you would any others.
