
# Chapter 10 • Securing Your System

Although no Linux distribution sets the SUID bit on rm by default, the SUID bit can be set inappropriately. This can happen by accident (say, a mistyped command by root), by malice (a cracker gains access to the system), or because of a subtle misconfiguration by the distribution maintainer (the SUID bit set unnecessarily on a program for which it’s less inappropriate than rm). Even if the SUID or SGID bit is set, a bug in the program can become more serious because the bug executes as root. If the bug enables users to write files, for example, any user can exploit the bug to overwrite system configuration files. For these reasons, you should periodically review your system for all the SUID programs and, if appropriate, change their configuration.

To do this you can use the find command, which is described in detail Chapter 4. In particular, you can use the -perm option, which searches for the specified permission mode. To search for SUID and SGID files, you should pass a mode of +6000. The symbolic representation for the SUID and SGID bits is 6000, and the plus (+) tells find to locate any file with any of the specified bits. (You can search for SUID files alone by adding +6000 or SGID by adding +2000.) You may also want to use -type f, which restricts the search to regular files. (Directories use the SUID and SGID bits differently, as described in Chapter 4.) To search the entire computer for SUID and SGID programs, you should type:

```
# find -perm +6000 -type f
```

The result is a list of files, one per line, that have either the SUID or the SGID bits. Programs that are likely to be present in this list include su, ping, mount, password, umount, and sudo. These programs have a legitimate reason to be configured. Systems have additional SUID and SGID programs, some of which may seem trivial. For instance, some games are associated with the games and set the SGID bit. This configuration enables users to modify the games system-high files. If you have doubts about whether the program really needs SUID or SGID status, you should investigate further. Verifying the package integrity using your package management tools and perform a Web search on the program name “SUID” or “SGID,” as appropriate. You can also try changing the SUID status of the program using chmod, as described in Chapter 4, and see if it still works when run by a normal user.

Programs that are SUID or SGID root, but that shouldn’t, be a sign of system compromise. Crackers might reconfigure programs in order to more easily do their dirty work. If you find such programs, investigate the overall integrity of the system. On the other hand, if a distribution maintainer sets the SUID or SGID bit unnecessarily, this isn’t for concern about a break-in, although you may want to fix the matter. Likewise, accidental misconfiguration by you or another administrator isn’t cause massive system upheaval—but you’ll need to dig a bit deeper to ascertain whether such change was accidental or a sign of a deeper problem.
