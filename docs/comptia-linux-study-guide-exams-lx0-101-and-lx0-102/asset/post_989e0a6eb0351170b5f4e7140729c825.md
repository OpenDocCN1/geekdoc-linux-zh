
# Configuring SATA Disks

SATA is a newer interface than PATA, and SATA has largely displaced PATA as the interface of choice. New motherboards typically host four or more SATA interfaces and frequently lack PATA interfaces.

SATA disks connect to their motherboards or controllers on a one-to-one basis—unlike with PATA, you cannot connect more than one disk to a single cable. This simplifies configuration; there aren't jumpers to set, and you won't be concerned with the position of the disk on the cable.

As the word in serial of SATA implies, SATA is a serial bus—only one bit of data can be transferred at a time. SATA transfers more bits per unit of time, though faster than PATA (1.5–6Gbps for SATA vs. 128–1064Mbps for PATA, but these are theoretical maximums that are unlikely to be achieved in real-world situations). Because of SATA's serial nature, SATA cables are much thinner than PATA cables.

Modern firmware detects SATA disks and provides information about them just as for PATA disks. However, older BIOSs are likely to be more limited. This is particularly true if your motherboard does not provide SATA support or you use a separate SATA controller card. You may be able to boot from an SATA disk in cases if your controller card supports this, or you may need to use a PATA boot disk.

Most Linux drivers treat SATA disks as if they were SCSI disks, so you should read the next section, "Configuring SCSI disks" for information about device naming. Some drivers treat SATA disks like PATA, so you may need to use PATA names in some rare cases.

# Configuring SCSI Disks

There are many types of SCSI definitions, which use a variety of cables and operate at various speeds. SCSI is traditionally a parallel bus, like PATA, although the latest variant, Aerial SCSI (SAS), is a serial bus. SCSI has traditionally considered a superior bus to PATA; however, the cost difference has risen dramatically over the past decade or so, so few people use SCSI on older systems or on very high-end systems.

SCSI supports up to 8 or 16 devices per bus, depending on the variety. One of these is the SCSI host adapter, which is either built into the motherboard or comes as a plug-in card. In practice, the number of devices you can connect to a SCSI bus is much restricted by cable-length limits, which vary from one SCSI variety to another. Each device has its own ID number, typically assigned via a jumper on the device. You must ensure that each device's ID is unique. Consult your documentation to learn how to set the ID.

If your motherboard lacks built-in SCSI ports, others won't want SCSI devices. You can still boot from a SCSI hard disk if your SCSI host adapter has its own firmware that supports booting. Most high-end SCSI host adapters have this support, but low-end SCSI host adapters don't. If you use such an adapter, you can still attach SCSI hard disks to the adapter, and Linux can use them, but you will need to boot from a PATA or SATA hard disk.

# Configuring Hard Disks

SCSI IDs aren’t used to identify the corresponding device file on a Linux system. Hard drives follow the naming /dev/sdx (where x is a letter from a), SCSI tapes are named /dev/stx and /dev/sdx (where x is a number from 0 up), and SCSI CD-ROMs and DVD-ROMs are named /dev/sccdx or /dev/srx (where x is a number from 0).

SCSI device numbering (or lettering) is usually assigned in increasing order based on the SCSI ID. If you have one hard disk with a SCSI ID of 2 and another hard disk with a SCSI ID of 4, they will be assigned to /dev/sda and /dev/sdb. The real danger is if you add a third SCSI drive and give it an ID of 0, 1, or 3. This new disk will be /dev/sda (for an ID of 0 or 1), bumping up one of the existing disks’ Linux device identifiers. For this reason, it’s usually best to give hard disks the lowest possible SCSI IDs so that you add future disks using higher IDs.

The mapping of Linux device identifiers to SCSI devices depends in part on the design of the SCSI host adapter. Some adapters result in assignment from SCSI ID 7 and working down to 0 rather than reverse, with Wide SCSI device numbering from there to IDs 14 through 8.

Another complication is when you have multiple SCSI host adapters. In this case, Linux devices assign files to all of the disks on the first adapter, followed by all on the second adapter. Depending on where the drivers for the SCSI host adapters are found (compiled into the kernel or as modules) and how they’re loaded (for modular drivers), you may not be able to control which adapter takes precedence.

Remember that some non-SCSI devices, such as USB devices and SATA disks, are mapped to the Linux SCSI subsystem. This can cause a true SCSI hard to be assigned a higher device ID than you’d expect if you use “pseudo-SCSI” devices.

The SCSI bus is logically one-dimensional—that is, every device on the bus along a single line. This bus must not fork or branch in any way. Each end of the SCSI bus must be terminated. This refers to the presence of a serial resistor that prevents signals from bouncing and forth along the SCSI chain. Ensure your SCSI host adapter and SCSI devices' learn how to terminate them. Remember that both ends of the SCSI chain must be terminated, but mid-chain must not be terminated. The SCSI host qualifies as a device, so if it is at the end of the chain, it must be terminated. Termination is a true hardware requirement; it doesn’t apply to SATA or USB devices, though they use Linux SCSI drivers.

Incorrect termination often results in bizarre SCSI problems, such as an inability to detect SCSI devices, poor performance, or unreliable operation. Similar symptoms can result from the use of poor-quality SCSI cables or cables that are too long.

# Configuring External Disks

External disks come in several varieties, the most common of which are USB, IEEE-1394, and SCSI. SCSI has long supported external disks directly, and many SCSI host adapters have both internal and external connectors. You configure external SCSI disks just like internal disks, although the physical details of setting the SCSI ID number and termination may differ; consult your devices manuals.

Linux treats external USB and IEEE-1394 disks just like SCSI devices, from a software point of view. Typically, you can plug in the device, and use it as /dev/sdx device node appear, and use it as you would a SCSI disk. This is the case for both external hard disks and media such as solid-state USB drives.

External disks are easily removed, and this can be a great convenience; however, you should never unplug an external drive until you've unmounted the disk in Linux using the unmount command, as described in Chapter 5. Failure to unmount a disk is likely to cause damage to the filesystem, including lost files. In addition, although USB and IEEE-1394 buses are hotpluggable, many SCSI busses are not, so connecting or disconnecting a SCSI device while the computer is running is dangerous. (Inserting or ejecting a removable SCSI disk, such as a Zip disk, is safe, however.)

# Designing a Hard Disk Layout

Whether your system uses PATA, SATA, or SCSI disks, you must design a disk layout for Linux. If you are using with Linux preinstalled, you may not need to deal with this immediately; sooner or later you'll have to install Linux on a new computer or one with existing OS or upgrade your hard disk. The next few pages describe the x86 partitioning schemes, Linux mount points, and common choices for a Linux partitioning scheme. The upcoming section "Creating Partitions and Filesystems" covers the mechanics of creating partitions.

# Why Partition?

The first issue with partitioning is the question of why you should do it. The answer is that partitioning provides a variety of advantages, including the following:

- **Multi-OS Support** Partitioning enables you to keep the data for different OSs separate. In fact, many OS can't easily co-exist on the same partition because they don't support each other's primary filesystems. This feature is obviously important if you want the computer to boot multiple OSs. It can also be used to help maintain an emergency system—you can install a single OS twice, using the second installation as an emergency maintenance tool for the first in case problems develop.
