## Extracting Information about the Boot Process

Certain Linux kernel and module log information is stored in what is called the kernel ring buffer. By default, Linux displays messages destined for the kernel ring buffer during the boot process—they’re messages that scroll past too quickly to read. (Some distributions hide most or all of these messages unless you select a special option during the boot process.) You can inspect this information with this command:

```
# dmesg
```

This command generates a lot of output, so you may need to pipe it through the less pager or redirect it to a file. Here are examples of these commands:

```
# dmesg | less
# dmesg > boot.messages
```

![](img/35f616c7eba4e79e12bfd762129c5d27_292_0.png)

> Many Linux distributions store the kernel ring buffer to /var/log/dmesg soon after the system boots. Because new information is logged to the kernel ring buffer as the system operates and because the kernel ring buffer’s size is finite, you may need to consult this log file to learn about the boot process after the system has been operating for a while. Also, because the kernel ring buffer is held in memory, its contents are cleared and generated anew every boot of the computer.

Another source of logging information is the system logger (syslogd). The most useful file to look at is usually /var/log/messages, but /var/log/syslog and other log files in /var/log can also help find information.

> Some Linux distributions also log boot-time information to other files. Debian uses a daemon called bootlog that, by default, log any messages that go to /dev/console to /var/log/boot file. Fedora and Red Hat use syslog services to log information to /var/log/boot.log.

## Locating and Interpreting Boot Messages

### Understanding the Boot Process

### Look for Hardware Type Names
Many boot messages, particularly in the kernel ring buffer, relate to hardware. Searching for the name of the hardware type, as SCSI or USB, if you're having problems with these subsystems. Remember that Linux treats many disk devices as SCSI disks, too!

### Look for Hardware Chipset Names
Linux drivers log messages along with their drivers names, which are usually based on the chipset in. If you know your hardware well enough to know the chipset name, search for it or a subset of it. For instance, searching for 8169 may turn up messages to a RealTek8169 Ethernet interface. Similarly, you can search for higher-level kernel module names, such as reiserfs for messages from the ReiserFS filesystem driver.

### The Study from a Working System
Familiarize with the contents of the kernel ring buffer and log files if you expect a system is functioning correctly, you'll find it easier to identify problems when they occur.

Sometimes, a system won't boot at all. In this case, kernel boot messages (which ordinarily go into the kernel ring buffer) are displayed on the screen, which can help you identify the cause of a failure. Modern Linux distributions hide these messages by default, but you can reveal them by pressing the Esc key during the boot process. Once the kernel process has completed, other systems take over, and the last few messages displayed on the screen can provide clues—instance, if the last message mentions starting a particular server, it's possible that the server is hanging or chainloads interrupting the boot process. You may be able to disable the server using a single-user boot mode and bypass the process.

## The Boot Process

The process of starting an x86 computer from its initial state when the power is turned on to having a working operating system is complex because of the modern personal computers have evolved. The steps a computer goes through order to boot an operating system are follows:

- 1. The system is given power, and a special hardware circuit connects the CPU to load a predetermined address and execute the code in that location. The firmware (BIOS or EFI) resides at that location, so the CPU runs the firmware.
- 2. The firmware performs tasks. These include checking for hardware, configuring hardware, and looking for a boot loader.
- 3. When the boot loader takes over from firmware, it loads the kernel or chainloads to another boot loader, described earlier in this chapter.
- 4. Once the kernel takes over, it performs tasks as initializing devices, mounting the root partition, and finally loading and executing the initial program for your system. By default, this is the program /bin/init.
- 5. The initial program gets the process ID (PID) of 1 because it's the first program to run on the system. In a traditional Linux boot system, /bin/init reads the /etc/initt file to determine what other programs to run. On systems that use the newer Upstart or systemd startup, /sbin/init reads other configuration files.

How the init program and the initialization scripts work is covered, in "Dealing Runlevels and the Initialization Process."

> If you would like more details about this boot process, read http://www.linuxdevcenter.com/pub/a/linux/excerpts/linux_kernel1/how_computer_boots.html This page describes the process from the computer being powered up to the kernel being loaded and launching /sbin/init.

## Dealing with Runlevels and the Initialization Process

Linux relies on runlevels to determine what features are available. From 0 to 6, and each one is assigned a set of services that should be active. Upon booting, Linux enters a predetermined runlevel which you can set. Knowing what these functions are, and how to manage runlevels, is important if you are to control the Linux boot process and ongoing operations. To this end, you must understand the purpose of runlevels, be able to identify the services that are active in a runlevel, be able to adjust these services, be able to check your default and current runlevels, and be able to change the default and current runlevels.

> The next few pages describe the traditional System V (SysV) initialization system. Upstart and systemd differ from this, although they provide enough compatibility features that many of the tools and concepts described with respect to SysV also apply to newer systems. Upstart and systemd provide their own additional tools, though.

## Runlevel Functions

Earlier in this chapter, I described single-user mode. To get to this when booting Linux, you use the number 1, the letter S or s, and the system single-is is an option passed to the kernel by the boot loader. Single-user mode is an available runlevel for your system. Available runlevels on most systems are the 0 through 6. The letters S and s are synchronous with runlevel 1 as far as many utilities are concerned. Runlevels 0, 1, and 6 are reserved for special purposes; the remaining runlevels are available for whatever purpose your distribution prefer. Table 5.1 summarizes the conventional uses of the runlevels.

### 5.1 Runlevels and their purposes

| Runlevel | Purpose |
| :--- | :--- |
| 0 | A transitional runlevel, meaning that it is used to shift the computer from one state to another. Specifically, it shuts down the system. On modern hardware, the computer should power down. |
| 1, s, or S | Single-user mode. What services, if any, are started at this runlevel varies by distribution. It's typically used for low-level system maintenance that may be impaired by normal system operation, such as resizing partitions. |
| 2 | On Debian and its derivatives, a full multi-user mode with X running and login. Most other distributions leave this runlevel undefined. |
| 3 | On Fedora, Mandriva, Red Hat, and most other distributions, a full multi-user mode with a console (non-graphical) login. |
| 4 | Usually undefined by default and therefore available for customization. |
| 5 | On Fedora, Mandriva, Red Hat, and most other distributions, the same behavior as runlevel 3 with the addition of having X with an XDM (graphical) login. |
| 6 | Used to reboot the system. This runlevel is also a transitional runlevel. Your system is completely shut down, and then the computer reboots. |

> Dont configure your default runlevel to 0 or 6. If you do, your system will immediately shut down or reboot once it finishes powering up. Runlevel 1 could conceivably be used as a default, but chances you'll want to use 2, 3, or 5 as your default runlevel.

Identifying the Services in a Runlevel

There are two ways to affect what programs run when you enter a new SysV runlevel. The first is to add or delete entries in your /etc/initabb file. A typical /etc/initabb file contains many entries, and for a couple of special cases, inspecting or changing the contents of this file is best left to experts. Once all the entries in /etc/initabb for your runlevel are executed, your boot process is complete, and you can log in.
