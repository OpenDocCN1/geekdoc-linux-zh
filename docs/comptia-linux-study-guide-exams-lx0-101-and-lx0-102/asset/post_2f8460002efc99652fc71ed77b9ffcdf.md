As an example of mail in action, consider the task of sending a quick email message. Suppose you want to send to two recipients informing them of a meeting. You can do so as follows:

```
$ mail -s "Meeting reminder" -c benf@example.com sally@example.com
Remember the meeting at 4:00 today!
Cc: benf@example.com
```

After you type mail, the program waits for input standard input, but there's no prompt. You signal the end of the message by pressing Ctrl+D. This example shows a single-line message. After you Ctrl+D, the program displays the Cc: line to verify this option. You can still change the address at this point, but if you don't want to, you can press the Enter key and the message will be on its way.

To use mail in a script, you can use redirection to pass the contents of a file to be mailed:

```
mail -s "Automated alert!" < /tmp/alert.txt benf@example.com
```

This line, if included in a script, sends the contents of /tmp/alert.txt to benf@example.com with the specified subject.

You can use mail to read incoming email, but only if it's stored on a local mail pool. In this case you'll normally use mail interactively. Type mail, and you'll see the contents of your mail pool. Each message has a header line that lists the sender, date, and subject, among other things:

0046 sally@luna.edu Sun Jan 13 18:27 116/4262 Priorities

This is message 46; it's from sally@luna.edu; it arrived on January 13 at 18:27 (6:27 pm); it has 116 lines and 426 bytes (including headers); and its subject is Priorities. To read a message, type its number. You can delete the message by typing d or reply to it by typing r.

As a practical matter, people prefer to use more-sophisticated mail readers for their day-to-day mail reading. You'll probably find mail more useful for the scripted sending of email than for reading email or sending personal email.

# Checking the Email Queue

An email server manages a queue of email messages that it must deliver. This queue is similar in some respects to the queue of print jobs that the Linux printing system handles, as described in Chapter 6. Instead of sending jobs to a printer, the email server sends messages to another computer or stores them in local users' mail pools. This task may simple, but it can be surprisingly complex. The server may be asked to deliver many messages in a short period of time, and it may need to delay delivery of some messages while it works on others. Furthermore, any number of problems can lead to temporary or permanent inability to deliver messages. When a problem seems to be temporary, such as a network routing failure, the email server must store the message and deliver it later again. A Linux computer's email queue may contain undelivered messages. Knowing how to identify these messages and manage the queue can help you Linux computer's email subsystem working smoothly.

The mail-q program is the main tool to help in email queue management. This program was originally part of the sendmail package, by Postfix, Exim, qmail, and other Linux SMTP servers have all implemented compatible commands. Unfortunately, command options differ between implementations. The basic command, without any options, describes the contents of the email queue on all systems:

```
$ mailq
--Queue ID---- --Arrival Time----Sender/Recipient----
5842F963* 440 Fri Jan 18 13:58:19 sally@example.com
ben@luna.edu
```

- 0 Bytes in 1 Request.

This example, taken from a running Postfix, shows one message in the queue, along with relevant identifying information. The display format varies from SMTP server to another. In most cases, typing mailq is equivalent to typing sendmail -bp.

If your network connection goes down temporarily or if an upstream email server goes down for a while, messages can pile up in the queue. Your SMTP server will ordinarily attempt delivery at a later date; but if your network connection comes up again and you want to clear the queue immediately, you can do. Typing sendmail -q will do the job with most SMTP servers, and some have other equivalent commands, such as postqueue in Postfix or run in Exim.

All email servers offer a wide variety of options to prioritize email delivery, accept messages on the command line, delete specific messages from the queue, debug email connections, and so on. Unfortunately, commands and procedures to use these features vary from one email server to another. Thus, you should consult your server's documentation to learn how to use these features.

# Redirecting Email

Email aliases allow one to stand for another one. For instance, all email servers are supposed to maintain an account called postmaster. Email to this account should be read by somebody whose responsibility is for maintaining the system. One way to do this is to set up an alias the postmaster to the name of a real account. You can do this by editing the aliases file format is fairly straightforward. Comment usually resides in /etc or sometimes in /etc/mail/. Comment lines begin with hash marks (#), and other lines take the following form:

```
name: addr1[addr2,...]
```

The name that leads the line is a local name, such as postmaster. Each address (addr1, addr2, and so on) can be the name of a local account to which the messages are forwarded, the name of a local file in which messages are stored (denoted by a leading slash), a command through which messages are piped (denoted by a vertical bar character), the name of a file contents are treated as a series of addresses (denoted by a leading :include: string), or a full email address (such as freeexample.com).

A typical default configuration includes a few useful aliases for accounts such as postmaster. Such configurations map most of these aliases to root. Reading as root is inadmissible, though so increases the chance of a security breach or other problem because of a typo or bug. Thus, you may want to set up an alias like the following:

```
root:username
```

This redirects all root's mail, including mail directed to root via any alias, to username, which can take any of the forms just described (it's most likely to be a username or a remote email address). Some servers, including sendmail, Postfix, and qmail, require you to use /etc/aliases to a binary file that can be processed more quickly. To do so, use the newaliases command:

```
# newaliases
```

Another approach to redirecting mail is to do so on the user level. In particular, you can edit the /.forward file in a user's home directory to have mail for that user sent to another address. Specifically, the /.forward file should contain the new address—either a username on the current computer or an entire email address on another computer. This approach has the advantage that it can be employed by individuals—say, consolidate email from multiple systems into one account without bothering system administrators. A drawback is that it can't be used to set up aliases for accounts or accounts that lock home directories. The /.forward file can also be changed or deleted by the account owner, which might not be desirable if you want to enforce a forwarding rule that the user shouldn't be able to override.
