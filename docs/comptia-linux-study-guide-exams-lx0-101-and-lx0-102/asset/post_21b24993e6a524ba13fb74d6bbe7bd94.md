Various measures were taken to combat this problem, one of which was the development of the Filesystem Standard (FSSTND), which was first released in early 1994. The FSSTND standardized several specific features, such as the:

- Standardized the programs that reside in /bin and /usr/bin. Differences on this score caused problems when scripts referred to one location or the other.
- Specified that executable files should not reside in /etc, as had been previously before.
- Removed changeable files from the /usr directory tree, enabling it to be mounted read-only (a useful security measure).

There are three major versions of FSSTND: 1.0, 1.1, and 1.2. FSSTND began to rein in the chaos in the Linux world in 1994. By 1995, however, FSSTND's limitations were becoming apparent. Thus, a new standard was developed: the Filesystem Hierarchy (FHS). This new standard is based on FSSTND and extends it substantially. The FHS is more than a Linux standard; it may be used to define the layout of files on other Unix-like OS.

One important distinction made by the FHS is between shareable and unsharable files. Shareable files may be reasonably shared between computers, such as user data files and program binary files (of course, you don't need to share such files, but you may do so). If files are shared, they're normally shared through an NFS server. Unsharable files contain system-specific information, such as configuration files. For instance, you're not likely to share a server's configuration file between computers.

A second important distinction in the FHS is between static files and variable files. The former doesn't change except through direct intervention by the system administrator. Most executables are examples of static files. Variable files may be changed by users, automated scripts, servers, or the like. For instance, users' home directories and mail queues are composed of variable files. The FHS tries to isolate each directory into one of this 2 × 2 (shareable/unsharable × static/variable) matrix. Figure 4.2 illustrates these relationships. Some directories are mixed, but in these cases, the FHS tries to specify the status of particular subdirectories. For instance, /var is variable, and it contains some shareable and unsharable subdirectories, as shown in Figure 4.2.

Like the FSSTND, the FHS comes in numbered versions. Version 2.3, the latest version as I write this, was released in January 2004. The URL for FHS's official Web page is http://www.pathname.com/fhs/.

Some Linux vendors—most notably Fedora—are beginning to make changes that deviate from the FHS. For instance, Fedora 17 and later now place all binaries in /usr/bin and /usr/sbin. The /bin directory is a symbolic link to /usr/bin, and /sbin to /sbin. This layout complicates some types of configurations, such as those that require a separate /sbin partition.

# Important Directories and Their Contents

The FHS defines some directories precisely, but details for others are left unresolved. For instance, users files are normally in the /home directory, but you may have reason to call this else or use two or more separate directories for users' files. Overall, the most common directories defined by the FHS or by convention are the following:

- Every Linux filesystem tree has its roots to a single directory, known as / (pronounced, and often referred to, as root filesystem or directory). All other directories branch off this one. Linux does not use drives; every filesystem is mounted at a point within another partition (/ or something else). Critical subdirectories, such as /etc and /sbin, must reside on the root partition, but others can be on separate partitions.

- /boot directory contains static and unreachable files related to the initial booting of the computer. Higher-level startup and configuration files reside in another directory; /etc. Some systems impose particular limits on /boot. For instance, x86 BIOSs and older versions of the Linux Loader (LILO) may require that /boot reside below the 1,024 cylinder of the disk. Similarly, EFI boot methods work best with a /boot partition that uses ext2 or ReiserFS. These requirements sometimes, but not always, necessitate that the /boot be a separate partition.

- /bin This directory contains critical executable files, such as /ls, cp, and mount. These commands are accessible to all users and constitute the most important commands that ordinary users use. You will not find commands for big application programs in /bin (although the Vi editor is located here). The /bin directory contains static files. In some sense the /bin files are shareable, they're so important to the basic operation of a computer, the directory is almost never shared—any potential clients must have their local /bin directories.

- /sbin This directory is similar to /bin, but it contains programs that are normally run only by the system administrator—tools like fdisk and fsck. It's static and theoretically shareable, but in practice, it makes no sense to share it.

- /lib this directory is similar to /bin and /sbin, but it contains program libraries, which are made of code that is shared across many programs and stored in separate files to save disk space and RAM. The /lib/modules directory contains kernel modules—drivers that can be loaded and unloaded as required. Like /bin and /sbin, /lib is static and theoretically shareable, although it isn't shared in practice.

- /usr this directory holds the bulk of a Linux computer's programs. Its contents are shareable, so it can be read-only and may be shared with other Linux systems. For these reasons, many administrators split /usr into a separate partition, although so isn't required. (Fedora's recent changes make this difficult with distribution, though.) Some subdirectories of /usr are similar to their namesakes in the root directory (such as /usr/bin and /usr/lib), but they contain programs and libraries that aren't absolutely critical to the basic functioning of the computer.

- /usr/local this directory contains subdirectories that mirror the organization of /usr, such as /usr/local/bin and /usr/local/lib. The /usr/local directory hosts files that a system administrator installs locally—for instance, packages that are compiled on the target. The idea is to have an area safe from automatic upgrades when the OS is upgraded. Immediately after Linux is installed, /usr/local should be empty except for some subdirectories. Some system administrators split this into its own partition to protect it from reinstallation.

- /usr/X11 this directory hosts files related to the X Window System (X for short), Linux's GUI environment. Like /usr/local, this directory contains subdirectories similar to /usr, such as /usr/X11/bin and /usr/X11/lib. Although commonly used years ago, most modern distributions have moved the contents of this directory to others, such as /usr/bin.

- /opt this directory is similar to /usr/local in many ways, but it's intended for add packages that don't ship with the OS, such as commercial word processors or games. Typically, these programs reside in subdirectories in /opt named after themselves, such as /opt/app. The /opt directory is shareable. Some system administrators break it into a separate partition or make a symbolic link to a subdirectory of /usr/local and make a separate partition.

- /home this directory contains users' data, and it's shareable and variable. Although the /home directory is considered optional in FHS, it's a matter of the name being optional. For instance, if you add a new user to support additional users, you might leave the existing /home intact and create a new /home2 directory to house the new users. The /home directory often resides on its own partition.

- /root this is the home for the root user. Because the root account is critical and system-specific, this variable directory isn't really shareable.

- /var this directory contains transient files of all types—system log files, print spool files, mail news and so on. Therefore, the directory's contents are variable. Some subdirectories are shareable, but others aren't. Many system administrators put /var in its own partition, particularly on systems that have a lot of activity in /var, like Usenet news or mail servers.
