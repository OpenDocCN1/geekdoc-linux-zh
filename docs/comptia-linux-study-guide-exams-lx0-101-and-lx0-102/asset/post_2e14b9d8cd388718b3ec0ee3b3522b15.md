
# Setting Up inetd

You control servers that launch via inetd through the /etc/inetd.conf file in /etc/inetd.d. The /etc/inetd.conf file consists of a series of lines, one for each server. A typical line resembles the following:

```
ftp stream tcp nowait /usr/sbin/tcp /usr/sbin/in.ftpd -l
```

This and several subsequent examples refer to in.ftpd, an FTP server that was once quite popular but that's been replaced on many systems by other FTP servers. Some of these servers cannot be run from a super server.

Instead of using a monolithic /etc/inetd.conf file, versions of inetd enable you to split the configuration into several files in the /etc/inetd.d directory. Doing so enables you to easily add or delete servers by adding or deleting configuration files. For, the following paragraphs refer only to /etc/inetd.conf, and the description applies to files in /etc/inetd.d, as well.

Each line in /etc/inetd.conf consists of several fields separated by one or more spaces.
The meanings of these fields are as follows:

- **Service Name** The first field (ftp in the preceding example) is the name of the service as it appears in the /etc/inetd.services file.
- **Socket Type** The socket entry defines the type of connection to expect—a reliable two-way connection (stream), a less reliable connection with less overhead (dgram), a low-level connection to the network (raw), or others. The different types are highly technical; your main concern in editing this entry should be to correctly type the value specified by the server's documentation.
- **Protocol** This is the TCP/IP transport-layer protocol used, usually tcp or udp.
- **Wait/No Wait** For dgram socket type, this entry specifies whether the server connects to its client and waits (nowait) or processes all its packets and times out (wait). Servers that use other socket types should nowait in inetd.
- **User** This is the username to run the server. The root and nobody are common choices, but others are possible as well. As a general rule, you should run servers with a low-privilege user whenever possible as a security precaution. Consult the server's documentation for details.
- **Server Name** This is the filename of the server. In the preceding example, the server is specified as /usr/sbin/tcpd, which is the TCP Wrappers binary. As described shortly in “Controlling Access via TCP Wrappers,” this program is an security tool and should be included in the list of launching programs via inetd.
- **Parameters** Everything after the server name consists of parameters that are passed to the server. If you use TCP Wrappers, you pass the name of the true target server (such as /usr/sbin/in.ftpd) in this field, along its parameters.

The hash (#) is a comment symbol for /etc/inetd.conf. Therefore, if a server is running in inetd and you want to disable it, you can place a hash mark at the start of the line. If you want to add a server to inetd.conf, you need to create an entry for it. Most servers that can run from inetd include sample entries in their documentation. Many distributions ship with inetd.conf files that include entries for common servers as well, although of them are commented out; remove the hash mark at the start of the line to activate the server.

After modifying inetd.conf, you must restart the inetd server. You can generally restart it by your startup script, as described in Chapter 5, "Booting Linux and Editing Files." On most computers, typing something similar to the following should work:

```
# /init.d/inetd restart
```

Alternatively, you can tell inetd to reload its configuration by using a reload parameter rather than restart. The restart option shuts down the server and then starts again. When you use reload, the server never stops running; it rereads the configuration file and implements all changes. As a practical matter, the two are similar. Restart is more likely to correctly implement changes, but it is also more likely to persist across connections.

Instead of using the SysV startup scripts, you can use kill or killall (described in Chapter 2, "Managing Software") to signal this to many servers, including inetd, to reload their configuration files. For instance, you can type kill -1 -HUP pid if you know the ID (PID) of inetd, or you can type killall -HUP inetd to have all instances of inetd reload their configuration files (Ordinarily, only one instance of inetd runs on a system.). In practice, this should work much more like the reload option on the SysV startup script—in fact, scripts often use this technique to implement this option.

It's generally wise to disable as many servers as possible in inetd.conf (or the inetd configuration files, if you don't understand what a server does, disable it). This will improve the security of your system by eliminating potentially buggy or misconfigured servers from the equation.

# Controlling Access via TCP Wrappers

The TCP Wrappers provide a program known as tcpd. Instead of having inetd call a server directly, inetd calls tcpd, which does two things: checks whether a client is authorized to access the server, and if the client has this authorization, tcpd calls the server program.

TCP Wrappers are configured through two files: /etc/hosts.allow and /etc/hosts.deny. The first of these specifies computers that are allowed; the second, hosts.deny lists computers that are not permitted. If a computer is listed in both files, hosts.allow takes precedence.

Both files use the same format:

```
daemon-list : client-list
```

The daemon-list is a list of servers, usually using names from /etc/services. Wildcards are also available, such as ALL for all. The client-list is a list of computers to be granted or denied access. You can specify these by name or IP address or network.

The pages for hosts.allow and hosts.deny (they're actually the same document) provide additional information about more features. You should consult them as you build TCP rules.

> Remember that not all servers are protected by TCP Wrappers. Normally, only those servers that inetd runs via tcp are protected. Such servers often include, but are not limited to, Telnet, FTP, rlogin, finger, POP, and IMAP. A few servers can independently parse the TCP Wrappers configuration file; consult the server's documentation if in doubt.

# Configuring xinetd

xinetd program is an extended super server. It provides the functionality of inetd security options that are similar to those of TCP Wrappers. Modern versions of Fedora, Mandriva, Red Hat, SUSE, and a few other distributions use xinetd by default. Other distributions may use it in the future. If you like, you can replace inetd with xinetd on any distribution.

# Setting Up xinetd

The /etc/xinetd.conf file controls xinetd. On distributions that use xinetd by default, this file contains only global default options and a directive to include files stored in /etc/xinetd.d. Each server runs via xinetd then installs a file in /etc/xinetd.d with its own configuration options.

Whether the entry for a server goes in /etc/xinetd.conf or a file in /etc/xinetd.d, it contains information similar to the inetd.conf file. The xinetd configuration file, though, appears across multiple lines and labels it explicitly. Listing 10.1 shows an example that's equivalent to the earlier inetd.conf entry. This entry provides precisely the same information as the inetd.conf entry except that it doesn't include a reference to /usr/sbin/tcpd, the TCP Wrappers binary. Because xinetd includes similar functionality, it is generally not used with TCP Wrappers.
