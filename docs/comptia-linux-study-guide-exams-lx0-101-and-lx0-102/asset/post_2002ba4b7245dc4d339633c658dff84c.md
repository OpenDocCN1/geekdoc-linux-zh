Your default /etc/sudoers file probably several examples. Consider the following lines:

```
## Storage
Cmnd_Alias STORAGE = /bin/fsdisk, /bin/sfdisk, /bin/parted,
/bin/partprobe, /bin/mount, /bin/umount
## Processes
Cmnd_Alias PROCESSES = /bin/nice, /bin/kill, /usr/bin/kill, /usr/bin/killall
%sys ALL = STORAGE, PROCESSES
%disk ALL = STORAGE
%wheel ALL=(ALL) ALL
```

This example defines two command aliases, STORAGE and PROCESSES, each of which stands for a set of commands. Users who are members of the sys group may use both commands; users who are members of the disk group may use the STORAGE commands but not the PROCESSES commands; and members of the wheel group may use all commands, whether or not they're explicitly mentioned in /etc/sudoers.

Some distributions, such as Ubuntu, make heavy use of sudo; these distributions are designed to be administered exclusively via sudo, and they set up an /etc/sudoers file that provides at least one user access to all system utilities. Other distributions rely on sudo, although you can tweak your sudo configuration to enable administration via sudo if you like.

# Setting Login, Process, and Memory Limits

Sometimes you may want to impose limits on how many times you may log in, how much CPU time they consume, how much memory they can use, and so on. Imposing such limits is best done through Pluggable Authentication Modules (PAM) module called pam_limits. Most Linux distributions use this module as part of their standard PAM configuration, so chances you won't need to add it; however, you will still need to configure pam_limits. You do so by editing your configuration file, /etc/security/limits.conf. This file contains fields (denoted by a hash mark,) and limit lines that consist of four fields:

domain type item value

Each of these fields specifies a particular type of information:

The Domain The domain defines the entity to which the limit applies. It can be a username; a group name, which takes the form @groupname; or an asterisk (*) wildcard, which matches everybody.

Hard or Soft Limits The field specifies the limit as hard or soft. A hard limit is imposed by the system administrator and cannot be exceeded under any circumstances, whereas a soft limit may be temporarily exceeded by a user. You can also use a dash (-) to signify that a limit is both hard and soft.

The Limited Item The item specifies what type of item is being. Examples include core (the size of files), data (the size of a program's data area), fsize (the size of files created by the user), nofile (the number of open files), rss (the number of simultaneous logins), nproc (the number of concurrent processes), maxlogins and priority (the process priority). The data, rss, stack items all relate to memory consumed by a program. These and other measures of data capacity are measured in kilobytes.

The Value The final fields specifies that value's to be applied to the limit.

As an example, consider a system on which certain users should be able to log in and perform a limit of actions not stayed in indefinitely and consume amounts of CPU time. You can use a configuration like this:

```
@limited cpu 2
```

This configuration applies a hard CPU limit of two minutes to the limited group. Members of this group can log in and run programs; but if one of them consumes more than two minutes of CPU time, it will be terminated.

> CPU time and total system access time are entirely different things. CPU time is calculated based on the time the CPU is actively processing a user's data. idle time (for instance, when a user's shell is active but no CPU-intensive tasks are running) Then, a user can log in and remain logged in for hours even with a very low hard CPU limit. This limit is intended to prevent problems caused by users who run CPU-intensive processes on systems that shouldn't be used for such purposes.

Another way to set limits on system resource is via the ulimit command. This command is a bash built-in command, so it affects only bash and programs launched from it. The ulimit syntax is as follows:

```
ulimit [options]
```

The options define what being limited:

Core File Limits The -c option limits the size of core dumps, which are files created for debugging purposes in certain types of program crashes.

File Limits The -f option limits the size of files that may be created by the shell, and -n limits the number of open file descriptors. (Most systems do not honor the -n limits, though)

Process Limits The -u option limits the number of processes a user may run, and -t limits the total CPU time in seconds.

Memory Limits The -v option sets the total amount of virtual memory available to the shell, -s sets the maximum stack size, -m sets the maximum resident set size, -d programs' data set size, and -l sets the maximum size that may be locked into memory.

Hard and Soft Limits The -H and -s modify other options, causing them to be set as hard or soft limits, respectively. Hard limits may not be subsequently increased, but soft limits may be. If neither option is provided, ulimit sets both the hard and soft limits for the feature specified.

Current Settings Passing -a causes ulimit to report its current settings.
The ulimit command is often found in system or user user startup scripts, typically by ulimit -c 0, in order to prevent creation of core files, which can sometimes clutter a filesystem. If your users perform software development, you may want to ensure that you do not set this limit, or at least set it as a soft limit (in ulimit -Sc) so users may override it when necessary.

Because ulimit is a built-in command, its utility as a security limit tool is limited. If users have access to GUI tools or can log into the system in any way that bypasses bash (via SSH, depending on how it is configured), restrictions imposed by ulimit become meaningless. Thus, you should treat ulimit as a way to prevent problems of accidental, rather than intentional, abuse of the system.

One particularly radical approach to security is to use the /etc/nlogin file. If this file is present, only root may log into the computer. Other users are shown the contents of this file when they attempt to log in. In many respects, this is like setting critical system limits to 0 for all other users. This is most likely to be used on dedicated server systems that have no regular console or shell users.

# Locating SUID/SGID Files

Chapter 4, “Managing Files,” describes the SUID and SGID bits. In brief, these are special flags that may be applied to executable programs, causing Linux to treat the program as if it were run by the program's owner (for SUID) or by the group's (for SGID) rather than the individual who actually ran the program. For instance, if a program's SUID is set and if the program is owned by bruce, the program, when run by anyone, will have access to all the files owned by bruce and otherwise behave as if had run it.

The SUID and SGID bits are frequently associated with the root account in order to enable them to perform tasks that require special privilege. For instance, the password program (described in Chapter 7) is SUID root may only modify the Linux password database. For an ordinary user to change a password, such mechanism must exist to run a process as root. That mechanism, in the case of passwd, is the SUID bit.
