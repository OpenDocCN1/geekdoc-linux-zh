# EXERCISE 8.2 (continued)

To study and modify your system's network configuration, follow these steps:

- 1. Log into the Linux system as a normal user.
- 2. Launch an xterm from the desktop environment's menu system, if you used a GUI login method.
- 3. Acquire root privileges. You can do this by typing su in an xterm or using sudo (if it's configured) to run commands in the following steps.
- 4. Type ifconfig displays information about your local network settings for all your network interfaces. Most systems have both the loopback interface (lo) and an Ethernet interface (eth0). Look for a line in the Ethernet section that contains the string addr=: The following 4-byte number is your IP address. Write it down, as well as your netmask (Mask): Study the other information in that output, too, as the number of received (RX) TX packets, the number of errors, the number of collisions, and the Ethernet adapter's hardware address.
- 5. Type -n. The output is your system's routing table information. This normally includes information about the loopback network address (127.0.0.1/24), the local network address, and a default route (as the route for 0.0.0.0). Some systems may display either or additional lines, depending on local configuration. The default route includes an IP address under the Gateway column. Write down that data.
- 6. Use ping to test connectivity to local and remote computers. (This command is described in more detail in "Testing Basic Connectivity.") You need the name or IP address of at least one local computer and at least one distant computer (by your local router). Type ping address, where address is the name or IP address of each test machine. Perform this for localhost or 127.0.0.1, your own machine (the IP address you noted in step 4), your local router (the IP address you noted in step 5), and a distant computer (if you connected to the Internet, you can use an Internet-accessible site, such as www.org). All of these pings should be successful. However, some computers are configured to ignore packets by ping. Some of these tests may fail if you are not using Linux. You can learn the configuration of local computers from your administrators, or for Internet sites, you may simply try another site if the first one you test fails.
- 7. Bring down the local Ethernet connection by typing ifconfig eth0 down.
- 8. Repeat steps 4-6. Note that the eth0 interface is no longer shown when you type ifconfig, all routes associated with it have been removed from the routing table, and pinging systems from the interface no longer works (Linux retains some information about its Ethernet Link, so you may still be able to ping the computer itself via its eth addr.).
- 9. Bring the local connection back up by typing ifconfig eth0 up address mask, where address is the original IP address and mask is the original netmask, as identified in step 4.
- 10. Repeat steps 4-6. Note that the ifconfig command automatically added back your local network to the route but that the default route is still missing. As a result, you can't contact any systems that are located off the local network. If your DNS server is such a system, this means your ability to connect even local machines by name may be impaired as well.
- 11. Restore the default route by typing route default gw gateway, where gateway is the router you identified in step 5.
- 12. Repeat steps 4–6. If your network configuration is typical, all connectivity should be restored. (Some more exotic systems may still be lacking routes.)

# Real World Scenario Using PPP with DSL

Broadband users, and particularly those with Digital Subscriber Line (DSL) connections, sometimes have to use a variant of PPP to make their connections. PPP is a login-based way to access the Internet–you use PPP to initiate a connection to a remote computer, which includes an exchange of username and a password. A decade ago, PPP was used in dial-up access (and it's still used in this capacity), but some DSL providers adopted PPP for their own purposes. In the case of DSL, this configuration method is called PPP over Ethernet (PPPoE).

In many cases, the simplest way to use a PPPoE configuration is to purchase a broadband router. This device attaches to the DSL modem and makes the PPPoE connection. The broadband router works just like an ordinary Ethernet or Wi-Fi router, as far as the local computers are concerned, so you configure Linux as you would on any other local network.

If you must connect a Linux system directly to a DSL network that uses PPPoE, you must use a Linux PPP client. Most Linux distributions ship with such clients, but configuration details vary from one distribution to another. Your best bet is to look for your distribution's GUI network configuration tool; chances are, you'll be able to find a set of options that are clearly labeled as applying to DSL or PPPoE.

# Diagnosing Network Connections

Network configuration is a complex task, and unfortunately, things don't always work as planned. Five of these are ping, traceroute, tracepath, netstat, and tcpdump. Each of these exercises the network in a particular way and provides information that can help you track the source of a problem. You can also use some common network programs that aren't primarily debugging tools in your efforts.

# Testing Basic Connectivity

The most basic network test is the ping command, which sends a simple ICMP packet to a system (via IP address or hostname) and waits for a reply. In Linux, ping continues sending packets every second until you interrupt it with a Ctrl+C keystroke (You can specify a limited number of tests via the -c). Here's an example of its output:

```
$ ping -c 4 speaker (192.168.1.1) (64) bytes of data.
64 bytes from example.com (192.168.1.1): icmp_seq=1 time=0.194ms
64 bytes from example.com (192.168.1.1): icmp_seq=2 time=0.203ms
64 bytes from example.com (192.168.1.1): icmp_seq=3 time=0.229ms
64 bytes from example.com (192.168.1.1): icmp_seq=4 time=0.217ms
--- speaker statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 842ms
rtt min/avg/max/dev = 0.194/0.210/0.229/0.022 ms
```

This command sent packets and waited for their return, which occurred quite quickly (in an average of 210ms) because the target system was on the local network. By pinging both local and remote networks, you can isolate where a problem occurs. For instance, if you can ping local computers but not remote systems, the problem is most probably your router configuration. If you can ping by IP address but not by name, the problem is with your DNS.

# Tracing a Route

A step up from ping is the traceroute command, which sends a series of test packets to connect your system to a target system. The result looks like this:

```
$ traceroute -n 10.1.0.43 (10.1.0.43), 30 hops max, 52 bytes
1 192.168.1.1 1.021 ms 36.539 ms 0.971 ms
2 10.0.88.1 17.250 ms 9.959 ms 9.637 ms
3 10.9.8.173 8.799 ms 19.501 ms 10.884 ms
4 10.9.8.13 21.059 ms 9.231 ms 103.068 ms
5 10.9.14.44 8.554 ms 12.982 ms 10.029 ms
6 10.1.0.44 10.273 ms 9.987 ms 11.215 ms
7 10.1.0.43 16.360 ms * 8.102 ms
```

The -n option to this command tells it to display targets' IP addresses rather than hostnames. This can speed up the process, particularly if you're having DNS problems, and it can sometimes make the output easier to read—but you may want to know the hostnames of problem systems because that can help you pinpoint yours for a problem.

This sample output shows a great deal of variability in response times. The first hop, to 192.168.1.1, is purely local; this router responded in 1.021, 36.519, and 0.971 milliseconds (ms) to these probes. (Presumably the second probe caught the system while it was else.) Probes of most sequences are in the 8–20ms range, although one is at 103.068ms. The final system has only two times; the probe never returned, as the asterisk (*) on these lines indicates.

Using traceroute, you can localize problems in network connectivity. Highly variable times and missing times can indicate a router that is overloaded or has an unreliable router on the list. If you see a dramatic jump in times, it typically means the physical distance between routers is greater. This is common in intercontinental links. Such jumps don't necessarily signify a problem unless the two systems are close enough that a huge jump isn't expected.

What can you do with the traceroute output? Most immediately, traceroute is helpful in determining whether a problem in network connectivity exists in a network where you're responsible. For instance, the variability in the first hop of the preceding example can indicate a problem on the local network, but the last packet with the final destination most likely not a problem. If the trouble link is within your jurisdiction, you can check the status of the system, nearby systems, and the network segment in general.

> Some routers are configured in a way that traceroute isn't a useful tool; these block all traceroute data, either to themselves only or for all packets that pass through them. If your traceroute output contains one or two lines of asterisks but everything else seems OK, chances are you've run into such a system.
