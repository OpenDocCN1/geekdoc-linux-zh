# Configuring SSH

On the client side, you must establish a special SSH connection to the remote computer. You do this with the normal ssh client program, but you must pass it several parameters. An example will help illustrate this use of ssh:

```
# ssh -N -L 142:mail1.luna.edu:143 benf@mail1.luna.edu
```

The -N and -f options tell not to execute a command and to execute in the background after asking for a password, respectively. These options are necessary to create a tunnel. The -L option specifies the local port to listen, the remote computer to connect to, and the port on the remote computer to connect to. This example uses the local port 142 and connects to port 143 on mail1.luna.edu. (You're likely to use the same port number on both ends; I changed the local port number in this example to clearly distinguish the local and remote port numbers.) The final parameter benf@mail1.luna.edu in this example) is the username and computer to which the tunnel goes. Note that computer need not be the same as the target system specified via -L.

> NOTE If you SSH on the client system to a privileged port (that is, one numbered below 1024), you must execute the ssh program as root, as shown in the preceding example. If listening to a non-privileged port is acceptable, the ssh can run as a normal user.

With the tunnel established, you can use the client program to connect to the local port specified by the first number in the -L parameter (port 142 in the preceding example). For instance, this is intended to forward IMAP traffic, so you'd configure a mail reader to retrieve IMAP email from port 142 on localhost. When the mail reader does this, ssh kicks in and forwards traffic to the SSH server, which passes the data to the SSH server's local port 143, which is running the real IMAP server. All of this is hidden from the email reader program; as far as it's concerned, retrieving email from a local IMAP server.

# SSH Security Considerations

SSH is intended to solve security problems rather than create them. Indeed, on the whole thing SSH is superior to using Telnet for remote logins, and ssh can also take over FTP functions and other protocols. Thus, SSH is a security plus compared to using less-secure tools.

Like all servers, though, SSH can be a liability if it used unnecessarily or inappropriately. Ideally, you should configure SSH to accept protocol level 2 connections and refuse direct root logins. If X forwarding is unnecessary, you should disable this feature. If possible, use TCP Wrappers or a firewall to limit the machines that can contact an SSH server. With all servers, you should keep SSH up to date; there's always the possibility of a bug causing problems.
