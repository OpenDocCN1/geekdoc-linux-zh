
# Understanding syslogd

Most Linux systems employ a special daemon to handle log maintenance in a unified way. The traditional Linux system logger is syslog, which is often installed from a package called syslog-log. The syslog daemon handles messages from servers and other user-mode programs. It's usually paired with a daemon klogd, which is generally installed from the same syslog package as syslog. The klogd daemon handles logging of kernel messages.

Other choices for system loggers exist. For instance, syslog-ng is a replacement that supports advanced filtering, and metalog is another option. Recent versions of Fedora and Ubuntu use rsyslog. This chapter describes the traditional syslog logger. Others are similar in principle, and in some specific features, but differ in many details.

The basic idea behind a system logger is to provide a unified means of handling log files. The daemon runs in a background and accepts data from servers and other programs that are configured to use the log daemon. The daemon can then use information provided by the server to classify the message and direct it to an appropriate log file. This configuration enables you to consolidate messages from various servers in a handful of standard log files, which can be easier to manage and maintain potentially dozens of log files from the various servers running on the system.

In order to work, of course the log daemon must be configured. In the case of syslogd, this is done through the /etc/syslog.conf file. (The rsyslog configuration file is /etc/rsyslog.conf and is similar to syslog.conf.) The next section describes the syslog.conf file's format in detail.

# Setting Logging Options

The format of the /etc/syslog.conf file is conceptually simple but provides a great deal of power. Comment lines, as in many Linux configuration files, are denoted by a hash mark (#). Non-priority action take the following:

facility.priority action

In this line, the facility is a code for the program or tool that generated the message to be logged; the priority is a code for the importance of this message; and the action is a remote computer, or other location to accept the message. The facility and priority are often referred to collectively as the selector.

Valid codes for the facility are auth, authpriv, cron, daemon, lpr, mail, news, security, syslog, user, uucp, and local0 through local7. Many of these names refer to specific servers or program classes. For instance, mail servers and other mail-processing tools typically log using the mail facility. Most servers that aren't covered by more-specific codes use the daemon facility. The security facility is identical to auth, but auth is the preferred name. The facility is reserved for internal use. An asterisk (*) refers to all facilities. You can specify multiple facilities in one selector by separating the facilities with commas (,).

Valid codes for the priority debug, info, notice, warning, warn, error, err, crit, alert, emerg, and panic. The warning priority is identical to warn, error is identical to err, and emerg is identical to panic. The error, warn, and panic priority names are deprecated; you should use their equivalents instead. Other than these identical pairs, priorities represent ascending levels of importance. The debug level logs the most information; the emerg level logs the least. The emerg priority logs the most important messages, which indicate very serious problems. When a program sends a message to the system logger, it includes a priority code; the logger logs the message to a file if configured to log messages of that level or higher. If you specify a priority code of all, the system will log messages that are classified as alert or emerg but not crit. An exception to this rule is if you precede the priority code by an equal sign (=), as in crit, which describes what to do with messages of priority crit. For instance, crit causes messages below crit to be logged. A priority of * reverses the meaning of a match and refers to all facilities.

You can specify multiple selectors for a single action by separating the selectors with a semicolon (;). Note that commas are used to separate multiple facilities within a single selector; whereas semicolons are used to separate multiple selectors for a while. Examples of completes answer shortly.

Most commonly, the log is a filename, located in the /var/log directory tree. The messages, syslog and secure files in this directory contain many important log files, although not distributions use all of these. Other possible locations include a device filename for a console (such as /dev/console) to display data on the screen, a remote machine preceded by an @ to log to the specified system, and a list of individuals who would see the message if they're logged in. For some of these options, an asterisk (*) means logged-in users.

Some examples help clarify these rules. First is a fairly ordinary and simple example:

```
mail.*    /var/log/mail
```
This line logs all entries identified by the originating program related to mail to the /var/log/mail file. Most of the entries in a default /etc/syslog.conf resemble this one. Together, they typically cover all of the facilities mentioned earlier. Some messages may be handled by multiple rules. For instance, another rule might look like this:

```
*emerg
```
This line sends all emerg-level messages to the consoles of all users who are logged into the computer using text-mode tools. If this line or the earlier mail.* selector are both present, emerg-level messages related to mail will be logged to /var/log/mail and displayed on users' consoles.

A more complex example logs kernel messages in various ways, depending on their priorities:

```
kern.*                /var/log/kernel
kern.crit               @logger.pangea.edu
kern.crit               /dev/console
kern.info;kern.err      /var/log/kernel-info
```

The first of these rules logs kernel messages to /var/log/kernel. The second line sends critical messages to /logger.pangea.edu. (This computer may be configured to accept remote logs, which is topic not covered in this book.) The third line sends a copy of critical messages to /dev/console, which causes them to be displayed on the computer's main-text console display. Finally, the last line sends messages between info and err priority to /var/log/kernel-info. Because err is the lowest priority, these four lines cause all messages to be logged twice or three times: once to /var/log/kernel as well as either to the remote system or the console or /var/log/kernel-info.

Most distributions ship with reasonable logger settings, you may want to examine these settings and adjust them. If you change, you may need to change some other tools. For instance, all major distributions ship with tools that rotate logger files. If you change the files to syslog messages, you may need to change your log file rotation scripts as well. This topic is covered in the next section.

In addition to the system logger's options, you may be able to set logging options in individual programs. For instance, you may tell programs to record more or less information or to log at varying priorities. Some programs also provide the means to log via the system logger or via their own mechanisms. Details vary from one program to another, so you should consult the program's documentation for details.

> Most programs that use the logger daemons are servers and other system tools. Programs that run locally log data via the system daemon, although there are some exceptions to this rule, such as the Fetchmail program for retrieving email from remote servers.

# Manually Logging Data

For the most part, the system logger accepts entries from system tools, such as servers. Occasionally, though, you may want to manually create a log entry or a script to do so. The tool for this job is known as logger, and it has the following syntax:

```
logger [-isd] [-f file] [-p pri] [-t tag] [-u socket] [message ...]
```
