## Creating User cron Jobs

To create a user cron job, you use the crontab utility, not to be confused with the /etc/crontab configuration file. The syntax for crontab is as follows:

```
crontab [-u user] -l | -e | -r] [file]
```

If given without the -u user parameter, crontab modifies the cron job file (or user crontab) associated with the current user.

> The word crontab has three related but distinct meanings: It can refer to the crontab program, to the /etc/crontab file, or to the file that holds user jobs. This multiplicity of meanings can be obviously confusing. In this book, I refer to the program by using a monospaced code font, and I include the complete path to /etc/crontab, and I do not use monospaced font when referring to crontabs. A user's crontab file can define multiple cron jobs.

The crontab utility may become confused by the use of su to change the current user identity, if you use this command, it's safest to use -u user, even when you're modifying your crontab.

If you want to work directly on a crontab, use the -l, -r, or -e option. The -l causes crontab to display the current crontab; -r removes the current crontab; and -e opens an editor so that you can edit the current crontab (Vi is the default editor, but you can change this by setting the VISUAL or EDITOR environment variable).

Alternatively, you can create a cron job configuration file and pass the filename to crontab using the file parameter. For instance, crontab -u taker my-cron causes the crontab program to use my-cron for taker's jobs—that is, it copies taker's my-cron file into the directory where it stores crontabs, making a few changes along the way.

Whether you create a cron job and submit it via the file parameter or edit it via -e, the format of the crontab file is similar to that described earlier. You can set environment variables by the form VARIABLE=value, or specify a command preceded by five fields or wildcards when the job is to run. In a user cron job, you do not specify the username to execute the job, as you do with system cron jobs. That information is derived from the owner of the crontab. Listing 7.2 shows a sample user crontab file. This file runs two programs at different intervals: the fetchmail program runs every 30 minutes (on the half hour mark), and clean runs on Mondays at 2:00 a.m. Both programs are specified via complete paths, but you can include the PATH environment variable and omit the complete path specifications.

Ultimately, your crontab files are stored in /var/spool/cron, /var/spool/cron/crontabs, or a similar directory. Each file in this directory is named after the user it runs; for example, tbaker's file may be called /var/spool/cron/tbaker. You shouldn't directly edit the files in this directory; instead, use crontab to make changes. Access to the cron facility may be restricted in several ways:

**Executable Permissions** The permissions on the cron and crontab programs may be restricted using standard Linux mechanisms, as described in Chapter 4. Not all distributions configure themselves this way, but to be sure, users who should be able to schedule cron jobs should check the owner and permissions on /sbin/cron programs.

**Allowed Users List** The /etc/allow contains a list of users permitted to access cron. If this file is present, only users whose name appears in the file may use cron; all others are denied access. If this file isn't present, anybody may use cron, assuming access not restricted by executable programs.

**Disallowed Users List** The /etc/deny file contains a list of users who should be denied access to cron. If this file is present, any user whose name appears in the file is denied access to cron, but all others may use it, assuming executable permissions and disallowed-users list restrict access. ## EXERCISE 7.2 Creating Cron Jobs

Cron jobs can be a useful way to run programs at regular times. In this exercise, you'll create a simple user cron job that will mail you the output of ifconfig command on a daily basis. This exercise assumes you're authorized to use cron as an ordinary user. To configure your cron job, follow these steps:

- 1. Log into the Linux system as a normal user.
- 2. Launch an xterm from the desktop environment's menu, if you use a GUI login.
- 3. Create and edit a file called cronjob in your home directory. Use your favorite text editor for this purpose. The file should contain the following lines:

```
SHELL=/bin/bash
MAILTO=yourusername
0 12 * * * /sbin/ifconfig
```

Be sure to type these lines exactly; a typo will cause problems. One exception: Substitute your email address on the Linux system or elsewhere for username; cron uses the MAILTO environment variable to determine how to email the output of cron jobs.

- 4. Type crontab cronjob to install the crontab file as a cron job. Note that this method replaces any existing crontabs that might exist. If you've already defined user crontabs for your account, you should edit your existing crontab file to add the line ifconfig rather than create a new file, or type crontab -e to edit its copy from the crontab storage directory.
- 5. Wait for noon (12 in the cron time format). When this time rolls around, you should have a new email waiting for you with the contents of ifconfig output.

Instead of waiting for noon, you can substitute a time that's a couple of minutes in the future. Remember that cron specifies minutes first, followed by the hour in a 24-hour format. For instance, if you create the file at 3:52 p.m., you might enter 54 as the first two numbers on the final line of the file; this will cause the cron job to execute at 15:54 on a 24-hour clock, or 3:54 p.m.

## Using anachron

Cron is a great tool for performing tasks, such as rotating log files, on systems that are most or all of the time; it is a much less useful tool on systems that are frequently shut down, such as notebook computers or even desktop systems. Frequently, late-night cron jobs are not executed on such systems, which can lead to bloated log files, cluttered /tmp directories, and other problems.

One solution to these problems is anachron cron to ensure that regular maintenance jobs are executed at regular intervals. It works by keeping a record of programs it should execute and how frequently it should, in days. When anachron runs, it checks to see when it executed each of the programs it is configured to manage. If a period greater than the program's execution interval has passed, anachron runs the program. Typically, anachron runs itself from a cron job. You can then configure your regular system cron as anachron jobs and be sure they'll execute on systems that are regularly shut for long stretches of time.

Like cron, anachron is controlled through a configuration file named itself: /etc/anachrontab. This file consists of three types of lines: comment lines (denoted by a leading hash mark, #), environment variable assignments (as in SHELL=/bin/bash), and job definition lines.
