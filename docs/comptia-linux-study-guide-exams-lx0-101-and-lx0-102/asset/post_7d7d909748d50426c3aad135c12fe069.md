
# Using GRUB 2 as the Boot Loader

In principle, configuring GRUB 2 is much like configuring GRUB Legacy; however, some important details differ. First, the GRUB 2 configuration file is /boot/grub/grub.cfg. (Some distributions place this file in /boot/grub2, enabling simultaneous installations of GRUB Legacy and GRUB 2.) GRUB 2 adds a number of features, such as support for loadable modules for filesystems and modes of operation, that aren't present in GRUB Legacy. (The insmod command in the GRUB 2 configuration file loads modules.) GRUB 2 also supports conditional logic statements, enabling loading modules or displaying menu entries only if particular conditions are met.

If you merely want to add or change a single OS entry, you'll find the most important changes are to the per-image options. Listing 5.2 shows GRUB 2 equivalents to the image shown in Listing 5.1.

## Listing 5.2: GRUB 2 image configuration examples

```bash
# Kernel Image Options:
#
entry "Fedora (3.4.1)" {
set root=(hd0,1)
linux /mlinuz-3.4.1 root=/dev/sda5 mem=4096M
initrd-3.4.1
}
entry "Debian (3.4.2-experimental)" {
set root=(hd0,1)
linux (hd0,1)/bzImage-3.4.2-experimental ro=/dev/sda6
}
#
# Other operating systems
#
entry "Windows" {
set root=(hd0,2)
chainloader +1
}
```

Important changes compared to GRUB Legacy include the following:

- The title keyword is replaced by menuentry.
- The menu title is enclosed in quotation marks.
- An opening curly brace { follows the menu title, and each entry ends with a closing curly brace }.

The set keyword precedes the root keyword, and an equal sign (=) separates root from the partition specification.

The rootroverify keyword has been eliminated; you use root insert.

Partitions are numbered starting from 1 rather than 0. A similar change in disk numbering is not implemented. This change can be confusing if you are using GRUB Legacy, but it makes partition numbering mix-ups when "translating" from Linux-type partition numbering less likely. The most recent versions of GRUB 2 support a more complex partition identification scheme to specify the partition table type, as in (hd0,gpt2) to specify that the second GPT partition should be used, or (hd1,mbr3) to specify that the third MBR partition

GRUB 2 makes further changes, in that it employs a set of scripts and other tools that help automatically maintain the /boot/grub.cfg file. The intent is that system administrators never need to edit this file. Instead, you would edit files in /etc/default/grub, to change your GRUB 2 configuration. After making such changes, you must rebuild the grub.cfg file, as described shortly.

Files in /etc/grub.d control GRUB OS probers. These scripts scan the system for particular OSs and add GRUB entries to /boot/grub.cfg to support those OSs. You can add custom kernel entries, such as shown in Listing 5.2, to the 40_custom file to support your own locally compiled kernels or unusual OS that GRUB doesn't automatically detect.

The /etc/default/grub file controls the defaults created by the GRUB 2 configuration. For instance, if you want to adjust the timeout, you might change the following line:

```bash
GRUB_TIMEOUT=10
```

A distribution that's designed to use GRUB 2, such as Ubuntu, will automatically run the configuration scripts after certain actions, such as installing a new kernel with the distribution's package manager. If you need to make changes, you can type update-grub or grub-mkconfig > /boot/grub/grub.cfg after editing /etc/default/grub or files in /etc/grub.d. This command re-reads these configuration files and writes a fresh file to /boot/grub/grub.cfg (Some installations use use 2 in command names, as in grub-2-mkconfig).

Unlike GRUB Legacy, GRUB 2 is designed to work with both BIOS and EFI-based computers, as well as with a few more-exotic firmware types. When you first install Linux, the installer should set up GRUB correctly, using grub-install in the way described for GRUB Legacy. On EFI-based computers, GRUB 2's grub-install should install the EFI binary file where it belongs; but if you have problems, you may need to use efibootmgr, as discussed earlier with reference to GRUB Legacy.

# Using Alternative Boot Loaders

Although GRUB Legacy and GRUB 2 the Linux boot loader arena today are the only boot loaders covered on the exam, there are several others that you may encounter and that deserve mention:

- Syslinux: The Syslinux Project (http://www.syslinux.org) is actually a family of BIOS-based boot loaders, each of which is smaller and more specialized than GRUB Legacy or GRUB 2. The most notable member of this family is OLISINUX, which is a boot loader for optical disks, which have unique boot requirements. The EXTLINUX boot loader is another member of this family; it can boot Linux from ext2, ext3 or ext4 filesystem.

- LILO: The Linux Loader (LILO) was the most common boot loader in the 1990s. It is primitive and limited by today's standards, and it works only on BIOS-based computers. For more information on LILO, you can go to http://featream.net/projects/lilo/

- ELILO: The EFI Loader (ELILO); http://elif.sourceforge.net is the oldest boot loader for EFI-based computers. It's similar to LILO in its features and functionality and is used by some distributions (not notably, OpenSUSE) as the default boot loader on EFI-based computers.

- The Linux Kernel: Since version 3.3.0, the Linux kernel has incorporated an EFI boot loader for x86 and x86-64 systems. On an EFI-based computer, this feature enables the kernel to serve as its own boot loader, eliminating the need for a separate tool like GRUB 2 or ELILO.
