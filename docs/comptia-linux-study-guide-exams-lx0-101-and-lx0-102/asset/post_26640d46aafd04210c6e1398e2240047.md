```
$ newgrp project2
```

If the user typing this command is listed as a member of the project2 group in /etc/, the user's current group membership changes. Thereafter, files created by that user will be associated with the project2 group. Alternatively, users can change the group associated with an existing file by the chgrp or chown command, as described in Chapter 4, "Managing Files."

This group structure enables you to design a security system that permits collections of users to work on the same files while simultaneously keeping other users of the same computer from prying into files they should not be able to. In a simple case, you may create groups for different projects, classes, or workgroups, with each user restricted to one of these groups. A user who needs to access multiple groups can be a member of each of these—for instance, a student who takes two classes belongs to the groups associated with each class, or a supervisor may map to all the supervised groups.

## Mapping UIDs and GIDs to Users and Groups

As mentioned earlier, Linux defines users and groups by numbers, referred to as user IDs (UIDs) and group IDs (GIDs), respectively. Linux tracks users and groups by these numbers, not by name. For instance, the user may be tied to UID 523, and may be UID 609. Similarly, the project1 may be GID 512, and project2 may be GID 523. For the most part, these details take care of themselves—you use names, and Linux /etc/passwd or /etc/group to locate the number associated with the name. You may occasionally need to know how Linux assigns numbers when you tell it to do something. This is particularly true when you're troubleshooting or if you have to manually edit /etc/passwd or /etc/group.

Linux distributions reserve the first 100 user and group IDs for root (both the user and the group). The most important of these is 0, which is used by accounts and groups that are associated with specific Linux utilities and functions. For instance, UID 2 and GID 2 may be the daemon account and group, respectively, which are used by various servers; and UID 8 and GID 12 may be the mail account and group, which can be used by mail-related servers and utilities. Not all account and group numbers from 0 to 99 are in use; usually, only one or two dozens are. You can check your /etc/passwd and /etc/group files to determine which.

> Aside from UID 0 and GID 0, UID and GID numbers are not fully standardized. For instance, UID 2 and GID 2 map to the daemon account and daemon group on Red Hat and SUSE, on Debian UID 2 and GID 2 map to the bin account and bin group; the daemon account and group correspond to UID 1 and GID 1. If you need to refer to a particular user or group, use the name rather than number.

The first normal user account is usually assigned a UID of 500 or (more often) 1000. When you create additional accounts, the system typically locates the next-highest unused number; the second user you create is UID 1001, the third is 1002, and so on. When you remove an account, that account's ID may be reused, but the automatic account-creation tools don't do so if subsequent users are in use, leaving a gap in the sequence. This gap causes no harm unless you have many users that you run out of IDs (The limit is 6,536 users with the 2.2.x kernels and more than 4.2 billion by the 2.4.x and later kernels, including root and other systems). The limit can be set in configuration files or because of limits programs. In fact, reusing an ID number can cause problems if you don't clear away the old user's files—the new user will become the owner of the old user's files, which can lead to confusion.

Account numbering limits are set in the /etc/login.defs file. In particular, UID_MIN and UID_MAX define the minimum and maximum values for user accounts. In modern distributions, these values are generally 1000 and 6000, respectively.

Typically, UID 1000 is users—the default group for some distributions. But on a very small system with few users, you'll probably want to create your own groups. Because distributions have different ways of assigning users to groups, it's best that you familiarize yourself with your distribution's way of doing this and plan your group-creation policies with this mind. For instance, you may want to create your own groups within certain ranges of IDs to avoid conflicts with the distribution's default. It's possible to create multiple usernames that use the same UID or multiple group names that use the same ID. In some sense, these are different entries in /etc/passwd or /etc/group, so they have different home directories, different passwords, and so on. But they're treated identically in terms of file permissions. Unless you have a compelling reason to do so, you should avoid creating multiple users or groups.

Intruders sometimes create accounts with UID 0 to give themselves root privileges on the systems they invade. Any account with a UID of 0 is effectively the root. If you spot a suspicious account in your /etc/passwd file, your system has probably been compromised.

## Managing User Accounts

How frequently you do user maintenance depends on the nature of the system. Some systems, such as personal workstations change rarely. Others, such as multi-user servers that serve heavy user turnover, may require daily maintenance. The latter situation would seem require more knowledge of account configuration, but even in a seldom-changing system, it's useful to know how to add, modify, or delete accounts quickly and correctly when you need to so.

This chapter describes the traditional text-based tools for account creation and maintenance. Most Linux distributions ship with GUI tools that accomplish the same goals but vary from one distribution to another, so they're hard to summarize for Linux as a whole. The example also emphasizes that text-based tools provide the greatest flexibility and are more broadly applicable, but you can certainly use GUI tools if you like.

## Adding Users

Adding users can be accomplished through the useradd utility (This program is called adduser on some distributions.). Its basic syntax is as follows:

```
useradd [-c comment] [-d home-dir] [-e expire-date] [-f inactive-days] [-g group,...]] [-m -k skeleton-dir] [-p password] [-u UID] [-r] [-n] username
```

Some of these parameters modify settings that are valid only when the system uses shadow passwords. This is the standard configuration for most distributions today.

In its simplest form, you may just type `useradd username`, where username is the username you want to create. The rest of the parameters are used to modify the default values for the system, which are stored in the file /etc/login.defs.

The parameters for the useradd command modify the program's operation in various ways:

- **Comment**: The -c comment passes the comment field for the user. Some administrators store public information such as a user's office or phone number in this field. Others store just the user's real name or no information at all.
- **Home Directory**: You specify your account home directory with the -d home-dir parameter. This defaults to /home/username on most systems.
- **Account Expiration Date**: Set the date on which the account will be disabled, expressed in the form YYYY-MM-DD, with the -e expire-date option. (Many systems accept alternative forms, such as MM-DD-YYYY, as well.) The default is an account that doesn't expire.

## Managing Users and Groups

**Inactive Days** An account becomes completely disabled a number of days after a password expires. The -f inactive-days parameter sets the number of days. A value of -1 disables this feature and is the default.

**Default Group** Set the name or GID of the user's default group with the -g default-group option. The default for this varies from one distribution to another.

**Additional Groups** The -g group[,...] parameter sets the names or GIDs of one or more groups to which the user belongs. These groups need not be the default group, and you can specify more than one by separating them with commas.

**Home Directory Options** The system automatically creates the user's home directory if -m is specified. Normally, default configuration files (including directories) are copied from /etc/skle/, you may specify any template directory with the -k skeleton-dir option. Many distributions use -m as the default when running useradd.

**No Home Directory Creation** The -M forces the system to not automatically create a home directory, if /etc/login.def specifies that this action is the default. You might use this option, often in conjunction with -u (described shortly) and -d (described) if a new account is for a user taking over the home of an existing user—because a new user is replacing one who is leaving.

**Encrypted Password Specification** The -p encrypted-password parameter preserves the encrypted password for the system. The encrypted-password value is added, unchanged, to /etc/passwd or /etc/shadow file. This means that if you type an unencrypted password, it won't work as you expect. In practice, this parameter is most used in scripts, where you can encrypt a password (using crypt) and then send the result through useradd. The default value disables the account, so you must run passwd to change the user's password.

**Default Shell** Set the name of the user's default login shell with the -s shell option. On most systems, this is /bin/bash, but you can specify any shell or even a program that is not a shell. For instance, some systems use a shutdown script that calls /sbin/shutdown. Logging into this account immediately shuts down the computer.

**UID** The -u parameter creates an account with the specified user ID (UID). This value must be a positive integer, and it's normally greater than 1000 for user accounts. (Some distributions permit account UIDs as low as 500.) System accounts typically have less than 200, and less than 100. The -o option allows the number to be reused so that two usernames are associated with a single UID.

**System Account Creation** The -r parameter specifies the creation of a system account—an account with a value less than UID_MIN, as defined in /etc/login.def. The useradd command does not create a home directory for system accounts.

**No Group** In some distributions, such as Red Hat, the system creates a group with the same name as the specified username. The -n parameter disables this behavior.
