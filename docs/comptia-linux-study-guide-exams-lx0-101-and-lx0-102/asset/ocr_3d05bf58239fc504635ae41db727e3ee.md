# 80 Chapter 2 • Managing Software

In principle, the routines in a library can be linked into a program's main file, just
all the object code created by the compiler. This approach, however, has certain
problems:

+   - The resulting program file is huge. This means it takes up a lot of disk space, and it
consumes a lot of RAM when loaded.

+   - If multiple programs use the library, as is common, the program-size issue is multiplied
several times; the library is effectively stored multiple times on disk and in RAM.

+   - The program can't take advantage of improvements in the library without recompiling
(or least relinking) the program.

For reasons, most programs use their libraries as shared libraries (aka dynamic
libraries). Instead, the executable includes references to shared library files, which can be loaded
along with the main file. This approach helps keep program size down, enables
sharing of the memory consumed by libraries across programs, and enables programs to
take advantage of improvements in libraries by upgrading the library.

> Shared libraries are similar to the dynamic link libraries (DLLs) of
Windows. Windows DLLs are usually identified by .DLL extension
s; in Linux, shared libraries usually have a .so or .version
extension, where version is a version number. (.so for shared
object). Linux static libraries (used by linkers for inclusion in programs
when dynamic libraries aren't to be used) have .a file extensions.

On the downside, shared libraries degrade program load slightly if the library
isn't already in use by another program, and they can create software management
complications:

+   - Shared libraries can be incompatible with some or all programs that use the
library. Linux uses numbering schemes to enable you to keep multiple versions
of a library installed at once. Upgrades that cause problems over overwrite
older versions, whereas major upgrades get side by side with their counter-
parts. This approach minimizes the chance of problems, but sometimes changes that
shouldn't cause problems do cause them.

+   - Programs must be able to locate shared libraries. This requires adding configura-
files and environment variables. If it's done wrong or if a program overrides the
defaults and in the wrong place, the result is usually that the program won't run
at all.

+   - The number of libraries for Linux has risen dramatically over time. When they're used
in shared format, the result can be a tangled mess of package dependencies, particularly if
y use programs that rely on many or obscure libraries. In most cases, this issue boils
down to a package problem that can be handled by your package management tools.
