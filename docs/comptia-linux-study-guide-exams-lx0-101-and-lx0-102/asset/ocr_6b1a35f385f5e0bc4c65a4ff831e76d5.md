# Chapter 7 • Administering the System

In most cases, servers and other programs log data either do so via the system logging daemon or ship with a configuration file that goes in /etc/logrotate.d to handle the server's log files. These usually do a reasonable job, but you may want to double-check them. For instance, you might discover that your system is configured to keep too many or too old log files for rotation, in which case adjusting the rotation option is in. You should also check the /var/log directory and its subdirectories every now and then. If you see numbers of files accumulating or files growing to unacceptable size, you may want to check the corresponding logrotate configuration files. If an appropriate file doesn't exist, use a working file as a template, modifying it for the new file. Pay particular attention to the prerot and postrot scripts; you may need to consult the documentation for the program you're creating to learn how to force that program to begin using a new log file.

In most cases, log files remain on the computer that recorded them. Sometimes, you want to copy files off-site. The easiest way to do this is to reconfigure the log daemon to send the messages you want to another system, as described in “Setting Logging Options.” Another possibility is to create a cron job (described later, in “Running Jobs in the Future”) to copy files to another network share, or other network tool. You can also manually copy log files onto removable disks, if you like. There are few technical reasons to archive log files for more than a few weeks—only if a problem escapes your notice for a long time they will be useful. Managers and lawyers may need to keep them around for the long term for business or legal reasons.

# Review Log File Contents

Log files do no of good if they simply accumulate on the system. Their purpose is to be used as a means of identifying problems or documenting normal activity. When a server isn't responding to you, or when a customer refuses logs it should be accepting (or accepting logs if she is refusing), or when a system's network interface isn't coming up (up to three types of problems), you should check your log files as part of troubleshooting procedures. Log files can also be useful in troublesome situations, as helping you to identify the load on a server so to plan upgrades. Several procedures, many of which involve tools elsewhere in this book, can help you access your log files:

Paging Through Whole Log Files You can use a pager program, as described in Chapter 1, “Exploring Linux Command-Line Tools”, to view the entire contents of a log file. A text editor can also fill the same role.

Searching for Keywords You can use grep (described in Chapter 1) to pull lines that contain keywords out of log files. This can be particularly handy when you don't know which log file is likely to have an entry. For instance, typing grep eth0 /var/log/* locates all lines in all files that contain the string eth0.
