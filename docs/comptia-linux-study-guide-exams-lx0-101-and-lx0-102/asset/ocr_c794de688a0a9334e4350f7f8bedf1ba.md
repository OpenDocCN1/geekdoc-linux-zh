The key to NTP is that each server can deliver to an expanding number of clients. For instance, if a stratum 1 has 1,000 clients, each of which has 1,000 clients, and so on, stratum 3 will consist of 1,000 systems, and stratum 4 will contain 1,000,000,000 systems. Each increase in the stratum number slightly decreases the accuracy of the time, not by much; even a stratum 4 server's clock should be accurate to under a second, which is enough for almost all purposes. More important, if you run a network, you can set one computer as an NTP server and set all other computers' clocks from that one. Even if your primary NTP server's clock is off by a second, all the clocks on your network should be within a tiny fraction of each other, which is the most important consideration for time-dependent network protocols like Kerberos.

NTP works by measuring the round-trip time for packets between the server and the client. The two systems exchange packages with embedded timestamp; the client adjusts its time so that it is synchronized with the source's time stamp adds a bit to the time reported by the source to account for the packet's estimated time. For this reason, when you select an NTP source (described next, in "Locating a Time Source"), you should pick one with the shortest possible network time delay, all other things being equal. In truth, several measures of reliability exist, and the NTP protocols try to take them all into account.

The main Linux NTP server functions as both a server and a client; it sets its clock based on the time of its source and enables other systems to set their clocks from its. Even the end points in the NTP hierarchy (the stratum 4 and 3 servers in stratum 7.1) run the full NTP server package. The reason is that this software runs constantly and can monitor for and adjust the clock drift that's common in .drift file and other clocks' clocks, resulting in a program that simply sets the clock and ignores it until the next time the program is run. In other words, NTP does not reset the system clock periodically; the server improves the accuracy of the system clock. In part, this is done through .drift, which is usually stored in /var/lib/ntp but is sometimes stored in /etc. This file holds information about the server clock's inaccuracies and can be used to correct for them. A full NTP server, even when it's functioning only as an NTP client, periodically checks with its source systems to keep the system time correct and to update the .drift file.
