
hwclock [options]

You can specify options to accomplish several goals:

- **Show the Hardware Clock** View the hardware clock, pass the -r or --show option. The time is displayed in local time, even if the hardware clock is set to UTC.

- **Set the Hardware Clock Manually** To set the hardware clock to a date you specify, you need two options: --set and --date=newdate. The newdate is in the format that the date program accepts.

- **Set the Hardware Based on the Software Clock** If you set the software clock, you can synchronize the hardware clock to the same value with the --systoch option.

- **Set the Hardware Clock Based on the Hardware Clock** If your hardware clock is accurate but your software clock isn't, you can use the --hwclock option to set the software clock to the hardware clock's value. This option is often used in SysV startup script to set the system clock when you compute the first boots.

- **Specify UTC or Local Time** You can tell Linux to treat the hardware clock as storing UTC by using the --utc option or to treat it as holding local time by using the --localtime option. The default is whichever was last used when the hardware clock was set.

Ordinarily, you won't use hwclock directly often. You may need to use a daylight shift if you maintain your hardware clock in local time, but most distributions scripts manage this task automatically. You may also want to use it once in a while to keep the hardware clock from drifting too far from an accurate time; but again, many distributions do this automatically as part of the system procedure.

# Using NTP

Typically, a clock on an isolated computer needn't be set with any great precision. It doesn't really matter if the time is off by a few seconds, or a few minutes, so long as the time is reasonably consistent on that computer for the purpose of cron, other scheduling tools, and time stamps. Sometimes, though, maintaining a truly accurate system time is important. This is true for a few scientific, business, and industrial applications (such as astronomical measurements or determining the start and stop times for broadcasts). In a networked environment, maintaining the correct time can be more important. Time stamps on files may become confused if a server and its clients have different times, for instance. Worse a few protocols, such as the Kerberos security suite, embed time stamps in their packets and rely on those time stamps for normal system functioning. If two computers using Kerberos have wildly different times, they may not be able to communicate. For these reasons, several protocols exist to synchronize the clocks of multiple systems. Of these, NTP is the most popular and flexible, so I describe it. You should first understand the basic principles of NTP operation. You can then go on to configuring an NTP server for your network and setting up other systems as NTP clients.

# Understanding NTP Basics

One of the most popular, flexible, and accurate time tools is NTP. This protocol creates a tiered hierarchy of time sources, as illustrated in Figure 7.1. At the top of the structure are one or more highly accurate time sources—typically atomic clocks or radio receivers that pull their times from broadcast time signals based on atomic clocks. These are referred to as *stratum* 0 time servers, they aren't directly accessible to any but the *stratum* 1 time servers to which they're connected. These stratum 1 computers run NTP servers that deliver the time to *stratum* 2 servers, which deliver the time to *stratum* 3 servers, and so on, for an arbitrary number of strata.

The key to NTP is that each server can deliver to an expanding number of clients. For instance, if a stratum 1 has 1,000 clients, each of which has 1,000 clients, and so on, stratum 3 will consist of 1,000 systems, and stratum 4 will contain 1,000,000,000 systems. Each increase in the stratum number slightly decreases the accuracy of the time, not by much; even a stratum 4 server's clock should be accurate to under a second, which is enough for almost all purposes. More important, if you run a network, you can set one computer as an NTP server and set all other computers' clocks from that one. Even if your primary NTP server's clock is off by a second, all the clocks on your network should be within a tiny fraction of each other, which is the most important consideration for time-dependent network protocols like Kerberos.

NTP works by measuring the round-trip time for packets between the server and the client. The two systems exchange packages with embedded timestamp; the client adjusts its time so that it is synchronized with the source's time stamp adds a bit to the time reported by the source to account for the packet's estimated time. For this reason, when you select an NTP source (described next, in "Locating a Time Source"), you should pick one with the shortest possible network time delay, all other things being equal. In truth, several measures of reliability exist, and the NTP protocols try to take them all into account.

The main Linux NTP server functions as both a server and a client; it sets its clock based on the time of its source and enables other systems to set their clocks from its. Even the end points in the NTP hierarchy (the stratum 4 and 3 servers in stratum 7.1) run the full NTP server package. The reason is that this software runs constantly and can monitor for and adjust the clock drift that's common in .drift file and other clocks' clocks, resulting in a program that simply updates the clock.

# Locating a Time Source

You may think that locating an NTP server with low stratum number is ideal. However, it's true that the closest server in a network may not be the closest in a geographic sense. For instance, a national ISP may route all traffic through just one or two hubs. The result can be that traffic from, Atlanta, Georgia, to Tampa, Florida, may through Chicago, Illinois. Such a detour is likely to increase round-trip time and decrease the accuracy of NTP. In such a situation, a user in Atlanta may be better off using a Chicago NTP server than one in Tampa, even though Tampa is closer geographically.

To locate an NTP server, you should consult one:

- **Your ISP**: Many Internet service providers (ISPs), including business networks and universities, operate NTP servers for their users. These servers are usually close to you in a network sense, making them good choices. You should consult your ISP or the networking department at your organization to learn if such a system is available.

- **Your Distribution's NTP Server**: Some distributions operate NTP servers for users. If you are close to these servers in a network sense, they can be good choices; however, if aren't the case, you may want to look elsewhere.

- **Public NTP Server**: Lists of public NTP servers are maintained at http://support.ntp.org/bin/view/Webhome. These servers can be good choices, but you'll need to contact the site you choose to obtain permission to use it.

- **Public NTP Pool**: The pool1.ntp.org subdomain is dedicated to servers that have volunteered to function as public NTP servers. You can end up using different servers each time you launch NTP. Thus, using the public NTP pool can be a bit of a gamble, but the results are usually good enough for casual users or if you don't want to spend time checking and maintaining your configuration. To configure your NTP server to use either the pool1.ntp.org subdomain name or a numbered host within that domain, such as 0.pool1.ntp.org. You can narrow the list geographically by adding a geographic name to the domain name, as in north-america.pool1.ntp.org for servers located in North America. Consult http://support.ntp.org/bin/view/NTpoolServers for details.

# Maintaining the System Time

To maintain the system time, you can use the NTP daemon, `ntpd`. This daemon runs in the background and periodically synchronizes the clock with NTP servers. You can also use `ntpdate` to manually set the clock once, but `ntpdate` is not recommended because it doesn't keep the clock synchronized.
