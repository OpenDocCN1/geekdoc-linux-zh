
# Task 7.1: Using file to Identify File Types

One of the most undervalued commands in UNIX is file, which is often neglected and collecting dust in some corner of the system. The file command is a program that can easily offer you a good hint as to the contents of a file by looking at the first few lines.

Unfortunately, there is a problem with the file command: It's not 100 percent accurate. The program relies on a combination of the permissions of a file, the filename, and an analysis of the first few lines of the text. If you had a file that started looking out like a C program or had executed permission enabled, file might well identify it as an executable program rather than an English text file.

![](img/f32f6f53c129de2ebafcd2b4ff01b1c9_138_0.png)

You can determine how accurate your version of file is by checking the size of database file types. You can do this with the UNIX command wc -l /etc/*. The number of entries in the database should be around 100. If you have many less than this number, you're probably going to have trouble. If you have considered more, you might have a very accurate version of file at your fingertips! Remember, however, even if it's relatively small, file can still offer invaluable suggestions regarding file content anyway.

- 1. Start logging in to your account and using the ls command to find a file or two to check.

```
% ls -F
Archives/
Info/old/
OWL/ PubAccessLists.Z rumors.260ct.Z
LISTS/ bin/ rumors.5Nov.Z
Mail/ educ src/\News/ mailing.bitnet.Z
```

Next, simply enter the file command, listing each of the files you'd like to analyze:

```
% file LISTS rumors.260ct.Z src
LISTS: ascii text
educ: ascii text
rumors.260ct.Z: block compressed 16 bit code data
src: directory
```

From this example, you can see that file correctly identifies src as a directory, offers considerable information on the compressed file rumors.260ct.Z, and tags both LISTS and educ as plain ASCII text files.

# Looking into Files

ASCII is the American Standard Code for Information Interchange and means that the file contains the letters of the English alphabet, punctuation, and numbers, but not much else. There are no multiple typefaces, italics, or underlined passages, and there are no graphics. It is the lowest common denominator of text in UNIX.

![](img/f32f6f53c129de2ebafcd2b4ff01b1c9_139_0.png)

- 2. Now try using the asterisk (*)

```
% file *
Global.Software: English text
Interactive.Unix: mail folder
Mail: directory
News: directory
Src: directory
bin: directory
history.usetenet.Z: compressed data block compressed 16 bits
```

The asterisk is a special character in UNIX. By itself, it tells the system to replace it with the names of all the files in the current directory.

This time you can begin to see how file can differentiate files. Using this command, I am now reminded that the file Global.Software is English text, but Interactive.Unix is actually an electronic mail message (file can't differentiate between a single mail message and a multiple-message folder, so it always err on the side of saying that the file is a mail folder)

- 3. Mail folders are actually practical for the file command. One of the systems I use, the file command doesn't know what mail messages are, so asking to analyze mail folders in demonstration of how accuracy is related to the size of the file database.

On a Sun system, I asked file to analyze two mail folders, with the following results:

```
% file Mail/mailbox Mail/sent
Mail/mailbox: mail folder
Mail/sent: mail folder
```

Those two files on a Berkeley UNIX system, however, have very different results when analyzed:

```
% file Mail/mailbox Mail/sent
Mail/mailbox: ASCII text
Mail/sent: shell commands
Mail/sent: English text
```

Not only does the Berkeley version of UNIX not identify the files correctly, it doesn't even misidentify them consistently.

![](img/f32f6f53c129de2ebafcd2b4ff01b1c9_139_1.png)

- 4. Another example of the file command's limitations is how it interacts with file permissions. Use cp to create a new file and work through this example to see your file command interprets the various changes.

```
% cp _char test
% file test
test: shell commands
% chmod +x test
% file test
test: shell script
```

Adding execute permission to this file caused it to behave as a shell script rather than shell commands.

Don't misinterpret the results of these examples as proof that the file command is useless and that you shouldn't use it. Quite the opposite is true. UNIX has neither a file-naming convention (DOS has its three-letter suffix) nor indication of file ownership by icon (Macintosh does this with creator information added by each program). As it turns, vital that you have a tool for helping ascertain file types without actually opening the.

# Task 7.2: Exploring UNIX Directories with file

Now that you know how to work with the file command, it is time to wander through the UNIX file system, learning more about types of files to be found in specific directories. Your system might vary slightly—it'll certainly have more files in some directories than what I'm showing here in the examples, but you'll quickly see that file can offer some valuable insight into the contents of files.

- 1. First things first. Take a look at the files in the very top level of the system, / (root):

```
% cd /
% ls -CF
-No _rm__ star      flags/      rhf/       user/
OLD/        core        gendix stand/      user/
archive/    dev/        lib*       sys/       user/
ats/        diag*      found-found tftpboot  user/
backup/                     mnt/        tmp/        users/
bin/        etc/        net/        usera/      usr/
% file boot gendix
```

The most important word to see in this output is executable. This example is from a Sequent computer running DYNIX, based on Berkeley 4.3 It is the same machine that has problems identifying mail folders.

When a program dies unexpectedly in UNIX, the operating system tries to leave a snapshot of the memory that the program was using, to aid in debugging. Wading through these files can be difficult—it's usually reserved for a few experts at each site, where there is still some information inside. The best, simplest, is to check it with the file command. You can see in the preceding listing that file recognized the file as a crashed program memory image and further extracted the name of the program that originally failed, getty, causing the program to fail. When this failure happens, UNIX creates an image of the program in memory at the time of failure, which is called a core dump.

The fourth of the listings offers an easy way to understand symbolic links, indicated in -CF output with the special suffix #, in the preceding example with tftboot*. Using file, you can see that the file tftboot in the root directory is actually a symbolic link to a file with the same name elsewhere in the file system,/usr/tftboot.

There are differences in output formats on different machines. The following example shows what the same command would generate on a Sun Microsystems workstation, examining analogous files:

```
% file boot core kadb tamp
boot: sparc executable
core: core file from "popper"
```
