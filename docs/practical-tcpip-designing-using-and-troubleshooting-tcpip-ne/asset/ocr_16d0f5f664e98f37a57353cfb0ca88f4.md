We said that specific well-known ports are allocated to particular services (e.g. port 80 is for HTTP Web servers), which is how clients specify the service they want and servers recognize what service the client is asking for. In more detail, what happens in normal running is:

+   - on the server machine, the administrator specifies in a configuration file which services are to be run

+   - at boot time, the system reads the configuration file(s) and starts the specified servers, so all the configured servers run as long as this machine is up and running

+   - when a server starts up it tells TCP that it wants to receive connections coming in on a specific port, and then waits, listening on that port, for TCP to pass connections to it as they arrive

+   - there are listeners only on the ports the server applications are configured for. For example, if we don't run a Web server on our machine, there will be no listener on port 80. You can list all the listeners using `netstat -l` as we saw in Module 10.5. If a client tries to connect to a port that isn't being listened for, you get an error message like:


While the port the server listens on is usually its well-known port number, it doesn't have to be. As far as TCP is concerned, the well-known ports are just a convention. It makes life easier for users because they can assume the port number for a service is the well-known one, and applications can use this by default, but TCP internally doesn't care which port any service uses. +   - to run multiple, different copies of the same server.
