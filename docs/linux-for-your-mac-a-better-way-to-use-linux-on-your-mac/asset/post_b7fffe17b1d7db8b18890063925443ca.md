
## Managing Processes

One of the greatest things about using Linux is that the operating system is designed to isolate and protect the kernel from disruptive processes. Through the use of signals, permissions, scheduling, and memory management, your Linux sessions are generally quite safe from any program that has run amok and crashed. If you lose control of a program, you can generally get to another shell prompt and quickly kill it.

When each program starts, the kernel assigns a process ID number to the command. You can see a quick snapshot of these processes in memory by using the `ps` command, like this:

```
$ ps aux

root 2 0.0 0.0 0 0 ? SW Apr02 0:00 [kflushd]
root 3 0.0 0.0 0 0 ? SW Apr02 0:00 [kupdated]
root 4 0.0 0.0 0 0 ? SW Apr02 0:00 [kpiod]
root 5 0.0 0.0 0 0 ? SW Apr02 0:01 [kswapd]
root 6 0.0 0.0 0 0 ? SW Apr02 0:00 [khbubd]
root 244 0.0 0.3 1356 644 7 S Apr02 0:00 /usr/sbin/syslogd
root 248 0.0 0.5 1736 1076 7 S Apr02 0:00 /usr/sbin/klogd
```

Note that not all the processes are shown here, but one thing Linux users can be sure of is that everything starts with just one command named `init`. The `init` command, launched after Linux boots, spawns a whole series of new processes to get your system up and running. You can verify this by using the `ps` or `pstree` command (included with SuSE and LinuxPPC). For example, on a graphical login-based Linux PPC system running X and the `twm` window manager, `pstree` reports:

As you can see, *init* is responsible for the entire system. Each software program in memory, every telnet session, and every login can be tracked and viewed. In the above example, you can identify and control nearly every process, such as the *xclock* client:

```
# ps aux | fgrep xclock
bball 1018 0.0 0.6 3892 1740 ? S Apr06 0:00 xclock -geometry
```

Here you can see that the process (the *xclock* client) is owned by the user named *bball*, and its process ID is 1018. The *ps* command gets its information from various files in a directory with a name of the process ID. Taking a peek at /proc/1018 reveals:

There is one place you can go for current, definitive information about Linux’s memory, process management, and other features. As one old sage once said, “Use the source, Luke.” In other words, install and read the source code for the Linux kernel!

The Linux shell's `kill` command can be used to stop Linux processes. Use this command with its `SIGKILL`, or `-9` signal, along with the process's ID number, like this:

```
$ kill -9 1018
```

Using the previous example, after you (root or the user *bball*) pressed *Enter*, the *xclock* client would disappear from memory. If a program spawns a number of processes and can be identified by name (such as *httpd*), try using the *killall* command, followed by the process name. For example to kill all instances of your Web server, try:

```
# killall httpd
```

If you do not have permission to kill the process, the command will report an error.

To see an ongoing motion picture of processes in memory, use the `top` command, which can be used at the console or during an `X` session. Start the command like this:

```
$ top
```

After you press *Enter*, you will see a screen, as shown in *Figure 14.16*.

![](img/1ea833f5a3e3c1547e3dd2891f52804a_380_0.png)

After you press Enter, a list of processes will be shown. To sort the processes according to memory size, type Shift+M. To get help, type a question mark. You can also use top to kill any processes you own.

Killing processes is a drastic solution. Fortunately, Linux includes another program you can use to assign a CPU priority. The `nice` command can be used to run another command with a higher or lower scheduling priority. This means that if you know a program will take a long time to run, or require numerous system resources, but is not important, you can run the program with a lower priority. See the `nice` command manual or GNU info page for more information.

Other graphic process control clients are included with X, KDE, and GNOME. The X11 xosview client can display (but not control) the system load, CPU usage, memory, swap memory, paging, and network information. To control processes using a graphical client, try KDE’s kpm (process management client shown in Figure 14.17), or GNOME’s gtop client (a system monitor program with a unique memory graphing capability).

## Basic Security Issues

Here are some basic Dos and Don’ts for administering a Linux system. A few simple rules can make the difference between happiness and heartache when using Linux.

- Do change your root password(s) often.
- Do check the Web pages of your Linux system’s distribution for system fixes and updates.

![](img/1ea833f5a3e3c1547e3dd2891f52804a_381_0.png)

**Figure 14.17** *The kpm KDE client not only shows currently running processes, but also presents graphs of the system’s load.*

- Do enforce password expiration if supported, and you run a multi-user system. The command to use (on SuSE Linux systems) is the `chage` command.
- Do formulate a backup plan based on worst-case scenario.
- Do perform backups on a regular basis.
- Do restrict physical access to your computer.
- Do use a firewall or some other protection for any computer attached directly to the Internet.
- Do use a mix of letters and characters in passwords.
- Don’t install more software than you need.
- Don’t just turn off your system while Linux is running. This can harm the filesystem integrity of any mounted filesystem. Read the manual page for the `fsck` command, which is used on non-journaling (non-reiserfs) filesystems.
- Don’t log in and use Linux as the root operator unless you’re performing system maintenance. Use the `su` or `sudo` system.
- Don’t turn on any services that you do not use or do not need. Edit `/etc/inetd.conf` to turn off unneeded services.
- Don’t use passwords that are common words. Especially words that are in the system dictionary (`/usr/dict/words`).
- Don’t write down passwords.

## Upgrading the Linux Kernel

Although many PowerPC Linux users are quite happy to use Linux, the kernels and software as distributed on a vendor’s CD-ROM, there may be a time when, as system administrator, you will be asked to update the current Linux kernel. This is most often done to enable new hardware features or correct serious errors or problems on a system. You can also recompile kernel modules at the same time.

In order to recompile the kernel, you must have a working C development system installed, along with the proper programming tools, such as the `gcc` compiler, `make`, and assorted assemblers and linkers. You must have a copy of the kernel source headers (include files) installed, as well as a copy of the source tree of your currently running kernel. You should also check that the source for any or all modules or other devices, such as PCMCIA drivers are also installed.
