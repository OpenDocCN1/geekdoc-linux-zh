Note that not all output is shown, as many other services may be initially started on a system. Here you can see that various services have started. But how does the `init` command start these services? Understanding how Linux starts these services and the relationship between various runlevels can help you diagnose problems when booting, or help overcome problems in initializing hardware items, such as network interface cards.

## Introduction to Runlevels

For example, when you boot `LinuxPPC 2000 Q4` directly to a graphical login running the `X Window System`, Linux has booted to runlevel `5`, which supports multiple users, multi-tasking, network operations, and X. Conversely, on a SuSE Linux PPC system, this runlevel is designated as runlevel 3! Regardless of the numbering scheme, which is outlined in your system's initialization table, the `/etc/inittab` method of starting the services is about the same on all Linux systems. For example, under LinuxPPC 2000 Q4, runlevels are defined as the following:

```
# Default runlevel. The runlevels used by RHS are:

# 0 - halt (Do NOT set initdefault to this)

# 1 - Single user mode

# 2 - Multiuser, without NFS (The same as 3, if you do not have networking)

# 3 - Full multiuser mode

# 4 - unused

# 5 - X11

# 6 - reboot (Do NOT set initdefault to this)
```

As you can see, your Linux system is in runlevel 0 when shutting down, runlevel 6 when rebooting, or in 1, 2, 3, or 5 when starting. Runlevel 1, or maintenance mode, is usually used by the root operator for major maintenance operations. This runlevel should rarely be used, and will rarely be encountered unless a problem occurs during booting (remember that most Linux users aim to keep the system up and running for as long as possible). Under SuSE Linux, runlevels are defined as:

```
# /sbin/init.d/rc takes care of runlevel handling

#

# runlevel 0 is halt

# runlevel S is single-user

# runlevel 1 is multi-user without network

# runlevel 2 is multi-user with network

# runlevel 3 is multi-user with network and xdm

# runlevel 6 is reboot
```

These runlevels correspond to directories under the `/etc/rc.d/` (for Red Hat-based systems) or `/sbin/init.d` (for SuSE Linux) directories, which contain numbered scripts. The main control scripts reside under the `init.d` directory. For example, under a Red Hat-based system, the directories look like:

```
$ ls /etc/rc.d
init.d  rc.local  rc.sysinit  rc1.d  rc3.d  rc5.d
rc      rc.news   rc0.d       rc2.d  rc4.d  rc5.d
```

Note that the `rc_X.d` directories correspond to a `x` (0 through 6) runlevel. Under each `rc_X.d` directory, you find symbolic links to scripts under the `init.d` directory that control a particular process, service, or software package, according to the runlevel. For example, when Linux boots to runlevel 3, the system state which uses a text-only console, the symbolic links under /etc/rc.d/rc3.d to /etc/rc.d/init.d scripts are used:

```
K83ypbind --> ../init.d/ypbind

K84ypserv --> ../init.d/ypserv

K92anacron --> ../init.d/anacron

K92ipchains --> ../init.d/ipchains

K96irda --> ../init.d/irda

S10network --> ../init.d/network

S11portmap --> ../init.d/portmap

S14nfslock --> ../init.d/nfslock

S18autofs --> ../init.d/autofs

S20random --> ../init.d/random

S25netfs --> ../init.d/netfs
```

Note that not all the links are listed here. But the names of the links are important, and the order in which the links are executed is also important. Links with names beginning with K indicate a service to be stopped, while names beginning with S indicate services to be started. The numbering in the name determines when an action takes place when moving to the runlevel. The files for runlevel 3 above show that when the Linux system is in a particular state (such as starting, restarting, or shutting down) and going at a particular runlevel, the proper set of scripts are executed in a particular and proper order (even though many Red Hat Linux-based systems continue to start, then delay networking if PCMCIA services are used; a better approach is to start PCMCIA, then start networking service).

After Linux finishes executing the various scripts, other services may be started or stopped, depending on entries in other files, such as /etc/sysconfig or /etc/rc.d/rc.local (for Red Hat systems), or /etc/rc.config or /etc/rc.d/boot.local (for SuSE Linux). Initialization scripts that are executed directly before login may be ideal locations for local customization of your system, such as to configure key-board keys to emulate mouse buttons.

## Starting and Stopping Services

Determining what services to start as Linux boots is generally determined by values embedded in various system configuration files under the /etc directory. As mentioned before, SuSE Linux uses a system-wide configuration file named `rc.config` that is then polled by a shell script named `suSeConfig`. This shell script, in turn, reconfigures that system and automatically builds the appropriate dependencies and symbolic links for each runlevel.

Under LinuxPPC 2000 and other Red Hat-based systems, the superuser can use the graphical utilities such as the `ntsysv` (console-based) or `tksysv` (X11-based) commands to reconfigure services and runlevels. In turn, these commands use the `chkconfig` command to rebuild script dependencies.

For example, under LinuxPPC 2000, the `ntsysv` command may be started (by root) from the console command line or the command line of an X11 terminal like this:

```
# ntsysv
```

## System Service Scripts

Starting and stopping services while using Linux can only be accomplished by the root operator, also known as the superuser. Although the superuser can kill running processes to stop services, a better approach, which nearly all Linux distributions respond to immediately, is to manually intervene by calling system service scripts with a keyword such as *start*, *stop*, or *restart*. This approach allows the root operator to bring a service down, make a quick change to a configuration file, and then bring a service back up while Linux is running, and with little disruption to operations.

For example, stopping Web service under SuSE Linux can be accomplished by using the *apache* script like this:

```bash
# /etc/rc.d/init.d/apache stop
Shutting down service httpd				done
```

Under LinuxPPC 2000, the root operator can accomplish the same thing by using the *httpd* script like this:

```bash
# /etc/rc.d/init.d/httpd stop
Shutting down httpd:				[ OK ]
```
