## Using X11 on a Network

X was built from the ground up to work over a network. As you learn more about using Linux and the X Window System, you will find newer, faster, and more efficient ways to work over a network. This section introduces a few basic ideas you can use if you use a Macintosh running Linux on a network.

Most PC users sit down at their computers, then launch and run programs from the computer’s hard drive. This is the only way to use Linux and X if the computer is not attached to a network. However, if the computer is on a network, you can log in at another computer on the network to do work.

This book was developed and written using Linux running on a variety of computers, both Intel- and PowerPC-based models. Most of the work was done on an Apple G4 Cube running SuSE PPC Linux. However, the word processor used for development was Sun Microsystems' StarOffice, running on a headless (no monitor) home-built, Intel-based server. Work was accomplished using KDE 2.0 running on the Cube, while StarOffice was running in the X display. StarOffice, which has been released as open source, has yet to make a debut on PPC Linux. However, efforts at http://www.openoffice.org may soon bring about a version for the PowerPC, and a Mac OS version is planned for Summer 2001.

When you use X11, the X server handles all display issues. This allows X to easily display programs running on remote hardware. This means that you can use clients locally, on hardware that may not otherwise support the client. This can be handy, especially if there are problems due to memory, hard drive or platform restriction.

### Using the DISPLAY Environment Variable

The DISPLAY environment variable has an in-memory value assigned to every instance of an X server on your computer, and contains a host name, a display number, and a screen number. You need to know this information if you want to use X effectively on a network.

When you launch X and start your session, your DISPLAY will have this value:

```
yourcomputerhostname:0.0
```

If you examine the env command's output, the variable could also look like this:

```
:0
```

or this:

```
:0.0
```

After logging into a remote computer using the telnet command, you should see:

```
[bball@green bball]$ env | egrep DISPLAY
DISPLAY=cubie.home.org:0
```

Here you can see your local host name (cubie), display (0) and screen number (assumed to be 0, as none is shown). Remember, this refers to the local display, and not that of the remote host, which is named green. You can then sit down and launch a graphical client on the remote computer, such as the xv graphic utility, and it will appear locally on your display.

The **DISPLAY** variable must be properly defined in order for remote applications to appear on your display. If not, you will see:

```
[bball@green bball]$ xv
xv: Can't open display
```

To fix this, use the remote shell’s facilities to create the correct **DISPLAY**:

```
[bball@green bball]$ export DISPLAY=cubie.home.org:0
```

This example (for the *bash* shell) will create the **DISPLAY** variable. You can then launch the remote client.

### Using the xhost Client

You must have a properly defined **DISPLAY** variable, and the remote host must have permission to display clients on your server before you log in! If permission has not been granted, and you log into the remote computer and try to launch a client, you will see something like this:

```
[bball@cello bball]$ netscape
Xlib: connection to "cubie.home.org:0.0" refused by server
Xlib: Client is not authorized to connect to Server

Error: Can't open display: cubie.home.org:0
```

In this example, the user *bball* has logged into the host named *cello* and attempted to launch *netscape* without authorizing *cello* access to *cubie.home.org*’s X server. To fix this problem, use the *xhost* command at *cubie* before logging into *cello* like this:

```
[bball@cubie]$ xhost + cello.home.org
cello.home.org being added to access control list
```

After you press **Enter**, the user *bball* can then log into *cello* and launch *netscape*. After the remote session ends, you should then remove access, like this:

```
[bball@cubie]$ xhost - cello.home.org
cello.home.org being removed from access control list
```

You can set your session to allow all hosts by using *xhost* without a hostname like this:

```
$ xhost +
```

To deny all hosts access to your session, use the *xhost* client with a minus (-) like this:

```
$ xhost -
```

Be careful when using the *xhost* command; you should only allow other hosts access to your session on a limited basis and for a limited time.

## Remote Launching of Clients

By combining proper access permissions and use of the `DISPLAY` variable, you can also launch a local client and have it available for use on a remote display. Use the `-display` X Toolkit option, along with the remote computer's display name like this:

```
[bbail@cube] $ xcalc -display cello:0.0 &
```

In this example, the user `bbail` has launched the X calculator, `xcalc`, which will appear on the display attached to the host named `cello`. As you can see, using X on a network can be fun, flexible, and a great way to accomplish work.

## Serial Port and Modem Setup

Until the communications revolution is complete and everyone has ultra-high-speed broadband access to the Internet, most users will continue to connect to the Internet using a dial-up connection through an ISP (*Internet Service Provider*). In order to successfully connect to your ISP, you will need to be aware of your PowerPC's hardware capabilities and be able to recognize and configure Linux to work with and use your system's serial port or internal modem.

Fortunately, most modern Linux distributions and Internet connection utilities are able to recognize, configure, and report on any modem or serial port. After booting Linux, use the dmesg command to check for any found serial or modem ports, like this:

```
$ dmesg | fgrep tty
tty00 at 0xd415b020 (irq = 22) is a 28530 ESCC (cobalt modem)
tty01 at 0xd4162000 (irq = 23) is a 28530 ESCC (IrDA)
```

This example shows that two serial ports were found and may (possibly) be used. Linux denotes serial communications ports as /dev/ttyx where x is often a number between zero and three. In this example (using a TiBook running LinuxPPC 2000 Q4), the internal modem is correctly identified and has been assigned /dev/tty0. You can then use the ln command (as root) to create the symbolic modem link, like this:

```
# ln -s /dev/ttyS0 /dev/modem
```
