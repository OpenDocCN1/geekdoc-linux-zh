
```
find: /usr/share/zope/Extensions: Permission denied
find: /usr/share/zope/import: Permission denied
find: /usr/share/zope/lib: Permission denied
...
find: /usr/lib/ircd: Permission denied
cat: /usr/share/themes/PixmapEngine: No such file or directory
cat: Example/gtk/gtk/README: No such file or directory
cat: /usr/X11R6/lib/SpectCl/bin/README: No such file or directory
cat: /usr/lib/X4.0/Help/TclTk/README: Is a directory
```

In this example, the standard output or result is a sorted list of words, perhaps the imperfect beginning of a personal dictionary. Further filtering or cleaning will definitely be needed.

However, what about those annoying error messages? They represent the standard error output from the `find` and `cat` commands, but are not saved in the resulting file. Is there some way to handle the messages and save them as well? Of course!

Under Linux shells, the `stdin`, `stdout`, and `stderr` are assigned numbers or *file descriptors*. Using the above example (and the `bash` shell), you can save the error output in a file by specifying where to send the output like this:

```
$ find /usr -name README -print 2>errors.txt | \
  xargs cat 2>errors.txt | tr " " "\n" | sort | \
  uniq >out.txt 2>>errors.txt
```

In this example, you will not see any error output to the console, and each command will append any error messages to the file named `errors.txt`.

## Background Processing

Another great feature of using Linux and the shell is the ability to run commands in memory, or as a *background process*. To do this, use the shell's background operator, the ampersand (`&`), at the end of a command line. This is a handy way to have control of the command line returned immediately while another program (or programs) is running.

Our example from the previous section, which created a crude sorted word list and file of error messages, took about one minute on an Apple G4 Cube. Rather than waiting for the task to complete, the entire task could have been committed to memory as a background process like this:

```
$ find /usr -name README -print 2>errors.txt | \
  xargs cat 2>errors.txt | tr " " "\n" | sort | \
  uniq >out.txt 2>>errors.txt &
(1) 31895
```

Note that in this example, the shell returned a number in brackets `(1)`, along with another number. The first number is called a job number, and is returned by the shell. The second number is a process id, and is returned by the Linux kernel. Knowing these numbers is important, because you can use either number to control the program in the background. This process is known as job control.

You can observe a list of running processes by using the `ps` command like this:

```
$ ps

772 tty1 00:00:00 bash
779 tty1 00:00:00 startx
780 tty1 00:00:00 tee
789 tty1 00:00:00 xinit
793 tty1 00:00:01 ksmserver
879 pts/0 00:00:00 cat
18158 pts/2 00:00:00 bash
21300 pts/2 00:00:00 telnet

31861 pts/6 00:00:00 ah
31865 pts/6 00:00:00 less

```

You can observe a list of current jobs by using the shell's `jobs` command like this:

```
$ jobs
[1]+ Stopped pine -z
[2]- Running find /usr -name . . .
```

In this example, two jobs are present, with one job suspended. Read on to learn more about using the shell and background tasks.

## Handling the Foreground and Background

One way to return a running background task, especially if you are using `bash`, is to use the `fg` (or foreground) built-in command. Using our previous example, type the command at the shell command line while the program is running in the background like this:

```
$ fg
find /usr -name README -print 2>errors.txt | \
xargs cat 2>>errors.txt | tr " " "\n" | sort | \
uniq >out.txt 2>>errors.txt
```

The command line will immediately return. If you want to halt the program, press `Ctrl+C`. You can also kill the process in memory by using the shell's job number with the shell's `kill` command like this:

```
$ kill %1
```

In this example, the percentage sign signifies a job number, and is followed by the job number originally returned by the shell. You can also kill a task in memory (although crudely) by using the shell's `kill` command and a program's process id, like this:

```
$ kill 31095
```

> Note that the process id returned by a complex pipe may only refer to the first process id returned by the shell. Other parts of the command line may still be running in memory. It is best to use the shell's job number to halt running programs when numerous commands are in a pipe. If only a single command is running, then killing its process will work.

![](img/1ea833f5a3e3c1547e3dd2891f52804a_122_0.png)

The shell may also be used to suspend, and then retrieve a running application. For example, start the `pine` email program (with its `-z` or suspend-enable option) like this:

```
$ pine -z
```

The program will start and display its menu. To suspend `pine`, you can then press `Ctrl+Z`, and you will see:

```
Pine suspended. Give the "fg" command to come back.
[1]+  Stopped        pine -z
$
```

The shell prompt will reappear, and other programs may be started. To return to using `pine`, use the shell's foreground command `fg`, like this:

```
$ fg
```

`Pine` will reappear.

## History Editing

The shell history feature provides a way to quickly scroll through or jump to previously used commands. Used command lines are generally stored in a shell's history file. For `bash`, this is the file named `.bash_history` in your home directory.

Use the Up and Down arrow keys to scroll through previous commands. If you use the `!c` built-in command, you can edit the history list. By default, `bash` will remember 500 commands. This value may be changed, however, by defining or editing the value of the `HISTSIZE` environment variable.

![](img/1ea833f5a3e3c1547e3dd2891f52804a_123_0.png)

> If you use your shell's history feature often, one helpful bit of information to have in the shell's prompt is the current command number. See “Customizing the Shell Prompt” below to learn how to put the `!n` value (which represents the history number of the command) in your shell `PS1` environment variable.

## Regular and Extended Expressions

If you are new to Linux, you may not have much experience in using wildcard characters or search patterns in a task known as using *regular or extended regular expressions*, or *globbing*. You will use these expressions on the command line in conjunction with searching, editing, and navigation commands, such as `ls`, `find`, and `sed`. You will also use them with the `grep` family of commands: `agrep`, `egrep`, `grep`, and `fgrep`.

There is not enough room in this chapter (or book) to fully cover using these commands and expressions. For the most part, many Linux users are quite content to learn simple uses for regular expressions, such as `.` to match any single character, `?` to match three characters (note: likely OCR error in original text, standard meaning is 'any single character' or specific pattern, keeping original intent of simple wildcard usage), or extended regular expressions like `*[a-z][0-9]*` for matching embedded letters and numbers.

More complex, extended regular expressions, use general-purpose search characters. These are known as *metacharacters* and are used for crafting search expressions; *quantifiers* (single or multiple character-matching expressions), *anchors* (positional characters, such as specifying the beginning or end of a line), *escape characters* (for specifying end-of-line, carriage-returns, etc.), and *alternation* (which provides for Boolean logic).

![](img/1ea833f5a3e3c1547e3dd2891f52804a_123_1.png)

> For a simple introduction to using regular expressions, read the `ed` or `grep` manual pages, where you will find different examples and uses for complex search strings.

The best way to learn how to use expressions in searching is to read a command's manual page, and to practice. While the `ls` command can use expressions for searching, you'll find meatier tasks when searching through text files using one or more `grep` commands. While the `grep` and `fgrep` commands may be used for sophisticated searches, the most complex and capable family member is the `egrep` command.
