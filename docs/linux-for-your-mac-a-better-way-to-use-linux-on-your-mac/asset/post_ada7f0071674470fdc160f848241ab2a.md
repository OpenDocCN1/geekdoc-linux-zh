## Editing /etc/fstab

Your system's filesystem table, `/etc/fstab`, is a listing of known storage or removable device media, along with associated device names, *mount points* (where the device will appear in your filesystem), mounting options, and check options. You will also find virtual filesystems listed there, which can be used for your system's process table `/proc`, and USB devices, `usbdevfs`.

For example, here is a sample filesystem table (on an Apple G4 Cube running SuSE Linux):

```
/dev/hda10    /mac        hfs     ro,noauto,user        0 0
/dev/hda11    /           ext2    defaults                1 1
/dev/hda12    swap        swap    defaults                0 0
/dev/hda13    /d2         ext2    defaults                1 2
/dev/cdrom    /cdrom      auto    ro,noauto,user,exec     0 0
proc          /proc       proc    defaults                0 0
usbdevfs      /proc/bus/usb     usbdevfs  defaults        0 0
devpts      /dev/pts    devpts  defaults                0 0
```

The first column shows the associated device. In this example, the root, or `/` directory is on `/dev/hda11`. A small Mac OS partition, represented by `/dev/hda10` will, if mounted, appear at the `/mac` directory. The `/dev/cdrom` device (which is actually a symbolic link and could be `/dev/sr0` or `/dev/hdb`) will be mounted at the `/cdrom` directory. As you can see, the second column designates a mount point. SuSE Linux distributions use this directory by default, whereas Red Hat-based Linux distributions will use the `/mnt/cdrom` directory. A second Linux volume is `/dev/hda13`, which is designated `/d2`. You can tell this, because the third column shows the filesystem type used for the device.

The `proc`, `usbdevfs`, and `devpts` entries are virtual filesystems that only appear while Linux is running. They contain files that are used by the kernel, device drivers, modules, and other utilities for information. For example, you can see a list of mounted filesystems by looking at the `/proc/mounts` file like this:

```
$ cat /proc/mounts
/dev/root / ext2 rw 0 0
proc proc proc rw 0 0
/dev/hda13 /d2 ext2 rw 0 0
usbdevfs /proc/bus/usb usbdevfs rw 0 0
devpts /dev/pts devpts rw 0 0
//gigi/public . smbfs rw 0 0
```

This example shows that a root, process, second volume, USB, device, and Samba `smbfs` file systems are mounted. You can get nearly the same information by using the `df` command like this:

```
$ df
Filesystem 1k-blocks Used Available Use% Mounted on
/dev/hda11 6102696 5300008 492668 91% /
/dev/hda13 7133580 657616 6113576 10% /d2
usbdevfs 1783395 1783395 0 100% /proc/bus/usb
//gigi/public 18940416 6287672 12652544 33% /d2/gigi
```

This example shows the devices that are mounted and where they are located. It also shows how much room remains on the device. The `df` command is used to show and display the free space remaining on mounted file systems. The `usbdevfs` filesystem has no room left because it expands and contracts dynamically, and is a virtual filesystem.

The fourth column in the `/etc/fstab` entry lists desired options used in the mount command. Some of these options include:

| Option | Description |
| :--- | :--- |
| auto | Automatically attempt to recognize and mount according to `/etc/fstab` entry |
| defaults | Mount using the rw, suid, dev, exec, vauto, nouser, and async options |
| exec | Allow launching of binary files from filesystem |
| noauto | Filesystem must be mounted with the mount command |
| noexec | Do not allow execution of binaries from filesystem |
| nosuid | Do not allow set-user-identifier |
| nouser | Only root may mount or unmount filesystem |
| ro | Mount the filesystem read-only |
| rw | Allow read-write operations on filesystem |
| user | Allow non-root user to mount filesystem |

These options can be handy, especially if you use Linux and your Mac as a standalone workstation. For example, the following filesystem table entry for a CD-ROM allows you to easily mount and unmount a CD-ROM without having to resort to using the `su` command to acquire root status:

```
/dev/cdrom    /cdrom    auto    ro,noauto,user,exec    0    0
```

In a multi-user environment, however, you will most likely want to configure your filesystem table to ensure more strict access and security on what devices may be mounted or unmounted.

The fifth column entry is used by the `dump` command as a flag during backup operations. A value of 0 means that the contents do not need to be backed up. The sixth column is used by the `fsck` command, and is a flag used to tell the command the order in which the filesystems are checked. Obviously the root filesystem needs to be checked first, so this column’s value is usually 1 (see the `/dev/hda1` entry in the previous example).

You must be the root operator in order to edit your system’s `/etc/fstab` table. Use your favorite text editor (not a word processor) and make sure to disable word wrap. The text-based `vi`, `emacs`, and `pico` editors may be used. If you use the `pico` editor, include its `-w` option like this to disable word wrap:

```
# pico -w /etc/fstab
```

## Adding NFS Mount Points

The NFS filesystem and service is used to automatically or manually mount and access remote hard drives across a network. Using NFS is a handy way to quickly provide local storage hosted by remote computers, and even filesystems of software. In order to use NFS, you must have NFS service installed and running on both computers, and have properly configured the remote and local computers to use NFS. In this example, there are two computers: `green`, an Intel-based PC server running Mandrake Linux; and `cubie`, an Apple G4 Cube running SuSE PPC Linux.

On `green`, ensure that all required NFS daemons and services are installed and running. You can do this quickly by using the `nfs` startup script (as root) like this:

```
# /etc/rc.d/init.d/nfs status
```

Next, edit the file `/etc/exports`. This text file is a simple list of locally mounted filesystems that are available for export via NFS. This file could look like:

```
/d3/arc val0 (rw)
/d4/backup dell(rw)
/music 192.168.2.38(ro)
/bcmn/ftp/pub 192.168.2.42(ro)
/d3 cubie (rw,no_root_squash)
```

In this example, the `/d3/src` directory is available to the host named _via_, and provides read-write access. The next entry, `/d4/backup`, is available to the host named _del_, again for read-write access. The `_/music_` entry however, is only available to a host with an IP address of 192.168.2.38 (in reality, the host named _del_) and only for read access. The `/home/ftp/pub` directory (a handy place for a Red Hat Linux installation CD-ROM) is available to a host with an IP address of 192.168.2.42, and only for read access. Finally, an entry for _cubie_ shows that the `/d3` volume will be made available for read and write access (at least by root).

Save the file, then, as root, restart NFS services on the host _green_ to export the new mounting point:

```
# /etc/rc.d/init.d/nfs restart
Shutting down NFS services:                [ OK ]
Shutting down NFS mountd:                [ OK ]
Shutting down NFS quotas:                [ OK ]
Shutting down NFS statd:                [ OK ]
Starting NFS services:                [ OK ]
Starting NFS statd:                [ OK ]
Starting NFS quotas:                [ OK ]
Starting NFS mountd:                [ OK ]
Starting NFS daemon:                [ OK ]
```

> If you have trouble starting or restarting NFS services, first make sure that the portmap service is installed and running.

Next, on host _cubie_, create a mount point for the remote directory. This can be created anywhere on your filesystem, although the traditional mounting points are generally found under the `/mnt` directory. For our purposes here, let us assume that _cubie_ does not have a `/d3` mount point. Therefore, the root operator will first use `mkdir` to create the mount point:

```
# mkdir /d3
```

Next, root will use the _mount_ command to mount the remote directory. Include the _nfs_ filesystem type, along with the hostname, remote, and local directory like this:

```
# mount -t nfs green:/d3 /d3
```
