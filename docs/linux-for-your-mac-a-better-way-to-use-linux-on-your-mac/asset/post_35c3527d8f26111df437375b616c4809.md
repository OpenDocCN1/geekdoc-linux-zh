
You can then get help on a particular built-in command by again using the help operator and the name of the command:

```
$ help time
time: time [-p] PIPELINE

Execute PIPELINE and print a summary of the real time, user CPU time, and system CPU time spent executing PIPELINE when it terminates.

The return status is the return status of PIPELINE. The ‘-p’ option prints the timing summary in a slightly different format. This uses the value of the TIMEFORMAT variable as the output format.

times: times

Print the accumulated user and system times for processes run from the shell.
```

Another *bash* feature is expansion, particularly command completion. For example, if you type the first few letters of a command's name, then press the Tab key twice, *bash* will provide a list of commands matching the letters like this:

```
$ xp
xp-mapedit xpcd xpirot xplot xpot
xp-replay xpfx xpilots xpix xprompt
xpaint xpet xpinguin xpmtree xprop
xpanex xphoon xpipeman xpshow xpuzzle
xpat2 xpicted xplg xpmtoppm xpyraminx
```

Nearly every *shell* uses important configuration files, also known as *resource* files, and *bash* is no exception. In each user's home directory, you will find at least two (and perhaps three) files:

```
$ ls -af
.bash_history .bashrc /
```

The *.bash_history* file is a *text* file containing a list of previously used command lines. This file is used to display previous commands at the shell prompt ($) when you press the Up or Down arrow keys. The *.bashrc* file contains settings you can customize for your console sessions:

```
$ cat .bashrc
…
#export EDITOR=/usr/bin/pico
#export NNTPSERVER=news.suse.de
…

# try to set DISPLAY smart (from Hans):
# if test -z "$DISPLAY" -a "$TERM" = "xterm" -a -x /usr/bin/who; then
WHOSTI="/usr/bin/who am i"
_DISPLAY=$(expr "${WHOSTI}" : '.*(\([0-9]\.[0-9]\.[0-9]\.[0-9]\))\([0-9]\.[0-9]\)[0-9]\.[0-9]')
if [ "${_DISPLAY}" != ":0.0" -a "$DISPLAY" != ":0.0" -a "${DISPLAY}" != ":0.0" ]; then
export DISPLAY="${_DISPLAY}";
fi
unset WHOSTI _DISPLAY
fi
...
export DISPLAY LESS PS1 PS2
...
```

Note that not all the contents of the .bashrc file are shown here. In this example, taken from a default SUSE 7.0 PPC Linux install, two environment variable definitions are inactive because they are commented out using a pound sign (#), which is similar to a REM statement in BASIC (Beginner's All-purpose Symbolic Instruction Code). This first definition for EDITOR defines the default system text editor, while the second defines the hostname for the default Usenet news server used for reading newsgroup discussions.

The next section uses a somewhat complicated method of determining the user, host name, and DISPLAY value, which is then used for the shell prompt. (You will learn more about text editors and networking later in this book in Chapters 6 and 8).

Another file that may be used for settings is a file named .profile, which is generally read when a user first logs in. In addition to locally configurable shell resource files, every Linux distribution also includes skeletal system-wide default shell settings, usually in a file under the /etc or /etc/skel directory. For some systems, this file is named profile. In other systems, such as SUSE, the default user settings are derived from a series of system configuration values in /etc/rc.config, then read in to create /etc/profile. In this case, according to SUSE, you should put custom system-wide changes (and custom aliases) into /etc/profile.local.

## ksh

The public-domain ksh shell closely mimics a large subset of AT&T's UNIX KornShell, ksh. This shell has many of the same features as bash, and is generally found under the name ksh on many Linux distributions.

### ksh or ksh?

The original KornShell was first developed by David G. Korn in 1983 while at AT&T Bell Laboratories. Other versions followed in 1986, 1988, and 1993. The current ksh shell is known as *ksh93*. The public-domain version of ksh included with many Linux systems, (also known as *pdksht*), closely follows the 1988 version of the KornShell.

The good news is that as of March 1, 2000, AT&T decided to open and release the source to *ksh93*, and to make various binary distributions available for download (see the section “Resources” at the end of this chapter for the Web site).

Two other famous shells mimicked by *bash* and *tcsh* on Linux systems are the Bourne shell by Steven Bourne at AT&T Bell Laboratories, and the C shell, programmed by Bill Joy while at the University of California.

Like *bash*, the *ksh* shell will use a custom resource file named `.profile` in a user’s home directory, with system-wide defaults located in `/etc/profile`.

## tcsh

The *tcsh* shell, created by more than fifty developers, closely mimics the original C shell crafted by Bill Joy for BSD (*Berkeley Software Distribution*) UNIX. Paralleling the other shells detailed in this section, *tcsh* hosts all the features one would expect of a modern shell. This includes job control, aliases, history, command-line editing, command completion, and more.

System-wide defaults are stored in `/etc/csh.cshrc`/`/etc/csh.login` (which contains values read in by *csh* after a user logs in), and `/etc/csh.logout` (read in after a user logs out). Custom files in a user’s home directory are `.cshrc`, `.tcshrc`, `.login`, and `.logout`.

## zsh

The Z shell, known as *zsh*, was written by Paul Falstad while at Princeton, and is based on *sh*, also known as the Bourne shell (named after its developer, S.R. Bourne). Like other shells discussed here, *zsh* has many, if not more, features than one may need for conducting productive sessions at the Linux console.

The *zsh* shell has one of the most complete feature sets of all shells, including advantages over *bash* such as logout actions. Like *pksh*, it has nearly complete compatibility with the 1988 version of the KornShell.

System-wide resource files are located under the `/etc` directory (with names beginning with a `.`,), while local files are located in a user's home directory. The `.zlogin` and `.zlogout` monitor log in and out, while the `.zprofile` file is used when first logging in. Basic resources are stored locally in a file named `.zshrc`.

## ash and sash

The **ash** and **sash** shells are designed to support minimal shell operations and do not provide all the features of previously discussed shells. Nevertheless, shells such as **sash** can be quite important and almost necessary during certain Linux sessions, particularly when using Linux in single user mode or during filesystem repair operations.

The **ash**, developed in 1989 by Kenneth Almquist, is a minimalist **sh** shell clone that supports simple shell scripting. On the other hand, **sash** (which stands for Standalone Shell) is used from a foreign media with limited filesystem space after booting Linux. Because **sash** does not require external software libraries to run (in other words, it is linked statically, not dynamically), it may be used from a floppy diskette or other small media and does not require a mounted root filesystem.

An important feature of **sash** is its wealth of built-in commands, many of which generally require much additional hard drive space and software libraries. These commands are listed in Table 5.3.

As is evident in Table 5.3, the **sash** command is an indispensable tool. Should you use this shell and its built-ins in lieu of normal Linux commands? Probably not, because the feature sets of the built-ins do not match the feature sets of standalone Linux commands. However, in a pinch, **sash** can be a real lifesaver.

## Changing and Authorizing Shells

Now that you know a bit more about the shells available for Linux, how do you know what shell you are using and how do you change your default shell?

First, please consider using the default shell, **bash**. Although some Linux distributions allow you to specify a different shell to use for Linux, **bash** is the best choice because it has the flexibility to provide nearly all the services of any shell described in the chapter (with a few exceptions). However, if you have a desire to use a different shell, the choice is yours.

One way to determine the default shell specified for your Linux sessions is to examine the `/etc/passwd` file. This file contains a list of system users and services, along with other pertinent information.
