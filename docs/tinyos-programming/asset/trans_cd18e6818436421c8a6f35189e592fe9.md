## Consequences

适配器允许组件在最初计划之外的情况下被重用，而无需更改原始实现。

在许多情况下，使用适配器的组件不能在同一应用程序中独立使用，因为适配器已经在处理其事件。如同装饰器模式，Placeholder模式（第10.5节）可以帮助确保这一点。

如果适配器不包含特定于某个被适配组件的假设或行为，它就可以用于适配其使用的接口的许多不同实现。与装饰器一样，适配器通常是通用组件以允许重用。

添加额外的层来在接口之间转换可能会增加应用程序的资源消耗（ROM、RAM和执行时间）。

## 11 Concurrency

到目前为止，我们看到的代码是分阶段的并在任务中运行（同步）。这种编程模型足以满足几乎所有应用级代码。高性能应用程序和低级设备驱动程序有时需要额外的功能和并发模型。本章描述了两种这样的额外机制：异步代码和资源锁。异步代码是nesC语言的特性，而资源锁是一组TinyOS组件和机制。

### 11.1 Asynchronous code

任务允许软件组件模拟硬件的分阶段行为。但它们的用途远不止于此。它们还提供了一种在系统中管理抢占的机制。因为任务相对于彼此是原子运行的，所以仅在任务中运行的代码可以相当简单：没有其他执行突然接管并在你之下修改数据的危险。然而，中断正是这样做的：它们中断当前执行并开始抢占式运行。

#### 11.1.1 The async keyword

正如我们在第5章中所见，nesC区分同步（sync）和异步（async）代码。能够从中断处理程序抢占式运行（因此相对于任务是异步的）的命令和事件，必须在声明命令或事件的接口中以及在实现命令或事件的模块中都用async关键字标记。作为结果，async命令或事件，或从async命令或事件可达的函数只能调用或触发async命令和事件（nesC会在你违反此规则时提醒你）。这条规则意味着，只需查看接口或模块即可清楚哪些代码是同步的，哪些是异步的。例如，Send接口是纯同步的，因为没有命令或事件被标记为async：

```
interface Send {
  command error_t send(message_t* msg, uint8_t len);
  event void sendDone(message_t* msg, error_t error);
}
```

```
command error_t cancel(message_t* msg);
command void* getPayload(message_t* msg);
command uint8_t getPayloadLength(message_t* msg);
}
```

interface Leds {

所有中断处理程序都是自动async的，因此它们在其调用图中不能包含任何sync函数。中断处理程序执行sync函数的唯一方法就是发布一个任务。从async上下文发布任务是允许的，但由此产生的任务在同步上下文中运行。

例如，考虑一个位于UART之上的数据包层。当UART接收到一个字节时，它会触发一个中断。在中断处理程序中，软件从数据寄存器中读取该字节并将其放入缓冲区。当接收到数据包的最后一个字节时，软件需要发出数据包接收信号。但Receive接口的receive事件是sync的。因此，在最后一个字节的中断处理程序中，组件会发布一个任务来发出数据包接收信号。

#### 11.1.2  The cost of async

这就引出了一个问题：如果任务引入延迟，为什么还要使用它们？为什么不让所有东西都async呢？原因很简单：竞争条件，特别是*数据竞争*。抢占式执行的基本问题是它可以在正在进行的计算之下修改状态，这可能导致系统进入不一致的状态。例如，考虑这个命令toggle，它翻转状态位并返回旧值：

```
bool state;
async command bool toggle() {
  if (state == 0) {
    state = 1;
    return 1;
  }
}
```
