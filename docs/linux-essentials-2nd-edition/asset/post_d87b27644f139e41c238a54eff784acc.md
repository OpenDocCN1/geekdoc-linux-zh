Given the number of ps options, users can have different ways to use the program, typing ps usually produces the desired information, including PID values and command names (including command-line options) for all processes on the computer. Adding u (as ps ax) adds usernames, CPU loads, and a few other tidbits. The sheer scope of the information produced, can be overwhelming. One way to narrow this scope is to pipe the results through grep, which eliminates lines that do not include the search criterion you specify. For instance, if you want to find the PID number for the get process, you can do this by:

```
$ ps ax | grep
27946 pts/8      Sl      0:00 edit
27950 pts/8      S+      0:00 grep-colour=auto grep
```

This command reveals that grep it has a PID value of 27946. This is usually the most important information when you use ps, since you'll use the PID value to change a process's priority or terminate it.

# Using to Identify Processes

Although ps can return process priority and CPU use information, the program's output is usually sorted by PID number, and it provides information at only a single moment in time. If you want to locate CPU memory-hogging processes quickly, or if you want to study resource use over time, top is a more appropriate tool. This program ver 9.4 shows top running in a GNOME Terminal window.

By default, top sorts entries by CPU use, and it updates every few seconds. You'll need to be familiar with the purposes and normal habits of programs running on your system in order to determine if a CPU-hungry application is misbehaving; the legitimate needs of different programs vary so much that it's impossible to give a simple rule for judging when a process is consuming too much CPU.

You can do much with top than watch it update its display. When it's running, you can enter any of several single-letter commands, some of which prompt you for additional information, as summarized in Table 9.1. Additional commands are described in top's main page.

One of the pieces provided by top is the load average, which is a measure of the demand for CPU time by applications. In Figure 9.4, you can see the current load average and two previous measures. Load averages can be interpreted as follows:

- - A system with no programs are consuming CPU time has a load of 0.
- - A system with one program running a CPU-intensive task has a load of 1.
- - Higher load averages on a single-CPU system reflect programs competing for available CPU time.
- - On a computer with multiple CPUs or cores, load averages can reach the number of CPUs or cores before competition for CPU time begins.

Most computers sold today are multicore models, but single-core models dominated the marketplace prior to 2006. For instance, a load average of 4.0 on a system with a four-core CPU reflects processes demanding exactly as much CPU time as the computer has available.

The load average can be useful in detecting runaway processes. For instance, if a system normally has a load average of 0.5 but suddenly gets stuck at a load average of 2.5, a couple of CPU-hogging processes may have hung—that is, become unresponsive. Hung processes sometimes needlessly consume a lot of CPU time. You can use top to locate these processes and, if necessary, stop them.

# Measuring Memory Usage

Processes consume system resources, the most important of these being CPU time and memory. As already noted, top sorts your processes by CPU time by default, so you can identify processes that are consuming the most CPU time. You can press the M key within have have it sort by memory usage, thus identifying the processes that are consuming the most memory. With CPU time, you can't say that a process is consuming too much memory because it's at the top of the list, though; some programs legitimately consume a great of memory.

Nonetheless, sometimes a program consumes too much memory, either because of inefficient coding or because of a memory leak—a type of program bug in which the program requests memory from the kernel and fails to return it when it's done with the memory. A program with a memory leak consumes increasing amounts of memory, sometimes to the point where it interferes with other programs. As a short-term solution, you can usually terminate the program and launch it again, which resets the program's memory, something like draining a sink that's filled with water. If you want to study the computer's overall memory, the free command is useful. This program generates a report on the computer's status:

```
$ free
```

| Mem | used | free | shared | cached |
|---|---|---|---|---|
| | 791488 | 7734456 | 180432 | 190656 | 3244720 |
|/+ buffers/cache: | 4299080 | 3615808 | | | |
| Swap: | 6291452 | 1030736 | 5266716 | | |

The Mem line reveals total access memory (RAM) statistics, including the total memory in the computer (minus whatever is by the motherboard and kernel), the amount of memory used, and the amount of free memory. This example shows that most of the computer's memory is in use. Such a state is normal, since Linux uses unused memory as buffers and caches, which helps speed disk access. The Mem: line isn't the most useful; instead you should examine the buffers/cache: line, which shows the total memory used by the computer's programs. In this example, 2299080 KiB of 7914888 KiB is in use. In other words, a bit half of the computer's memory is in use by programs, so there should be no memory-related problems.

The Swap line reveals how swap space is used. Swap space is disk space that's set aside as an adjunct to memory. Linux uses swap space when it runs out of RAM, or when it determines that RAM is better used for caches than to hold currently inactive programs. In this example, 1030736 KiB of swap is in use, with 6291452 KiB total, 526716 free. Swap space use is generally quite low, and if it rises very much, you can suffer performance problems. In the long run, increasing the computer's RAM is generally the best solution to such problems.
