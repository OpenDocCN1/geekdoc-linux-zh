# Chapter 14 · Setting Ownership and Permissions

Restoring the file and setting the sticky bit enables you to see the effect:

```
$ ls -l
total 0
drwxrxrwt 2 root 80 Dec 14 18:25 subdir
$ ls -l subdir/
total 304
-rw-r--r-- 1 root 240268 Dec 14 18:25 f1701.tif
$ rm subdir/f1701.tif
rm: cannot remove subdir: Operation not permitted
```

In this example, although kirk has full read/write access to subdir, kirk cannot delete another user's files in that directory.

You can identify a directory with the sticky bit by a small change in the symbolic mode by ls -l. The world execute bit is shown as a rather than an x. In this example, the result is that subdir's permission appears as drwxrwxrwx rather than drwxrwx.

![](bbox=[0.39, 0.475, 0.19, 0.57])

The sticky bit is particularly important for directories that are shared by many users. It is a standard feature on /tmp and /var/tmp, for instance, since many users store temporary files in these directories, and you would not want one user be able to delete another user's temporary files. If you want users to collaborate on a project to be able to write files into each others' home directories, you might consider setting the sticky bit on those home directories, or on the subdirectories where users are sharing files.

# Using Special Execute Permissions

As described earlier in this chapter, the execute bit enables you to identify programs as such. Linux then allows you to run these programs. Files run using your own credentials, which is generally a good thing—associating processes with specific users is a key part of Linux's security model. Occasionally, though, programs need to run with elevated privileges. For instance, the password program, which sets users' passwords, must run as root to root, and in some cases to read, the configuration files it handles. Thus if users are to change their own passwords, password must have root privileges even when ordinary users run it.
