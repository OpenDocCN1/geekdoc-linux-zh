# Using Special Permission Bits and File Features

When you investigate the Linux directory tree, you will encounter certain file types that require special attention. Sometimes, you may just want to be aware of how these files are handled, since they deviate from what you might expect based on the information presented in earlier chapters. In other cases, you may need to adjust how you use ls or other commands to deal with these files and directories—for example, when using the sticky bit, using special execute permissions, hiding files from view, or obtaining long listings of directories.

# Using Sticky Bits

Consider the following commands, typed on a system with a few files and subdirectories laid out in a particular way:

```
$ whoami
kirk
$ ls -l
total 0
drwxrxrx 2 root root 80 Dec 14 17:58 subdir
$ ls -l subdir/
total 2350
-rw-r--r-- 1 root 2404268 Dec 14 17:59 f1701.tif
```

These commands establish the current configuration: The effective user ID is kirk, and the current directory has one subdirectory, called subdir, which root owns to which kirk, like all of the system’s users, has full read/write access. This subdirectory has one file, f1701.tif, which is owned by root and to which kirk has no access. You can verify that kirk cannot write to the file by attempting to do so with the following command:

```
$ touch subdir/f1701.tif
touch: cannot touch 'subdir/f1701.tif': Permission denied
```

This error message verifies that kirk could not write to subdir/f1701.tif.
The file, you might think, is safe from tampering. Not so fast! Try this:

```
$ rm subdir/f1701.tif
$ ls -l subdir/
total 0
```

The rm command returns no error message, and a subsequent check of subdir verifies that it's not empty. In other words, kirk could delete the file even without permission to it! This may seem like a bug—after all, if you can't write to a file, you might think that you shouldn't be able to delete it. Recall, however, directories are just a special type of file, one that holds other files' name pointers to their lower-level data structures. Thus modifying a file requires write access to the file, but creating or deleting a file requires write access to the directory in it resides. In this example, kirk has write access to the subdirectory, but not to the f1701.tif file within that directory. Thus kirk can delete the file but not modify it. This result is not a bug; it's just a counterintuitive feature.

Although Linux filesystems are designed to work this way, is always desirable. The way to create a more intuitive result is to use a sticky bit, which is a special filesystem flag that alters this behavior. With the sticky bit on a directory, Linux will permit you to delete a file only if you either own it or the containing directory; write permission to the containing directory is not enough. You can set the sticky bit with chmod in either of two ways:

### Using an Octal Code By prefixing the three-digit octal code described in this chapter with another, you can set any of three special permissions, one of which is the sticky bit. The code for the sticky bit is 1, so we would use an octal code that begins with 1, as in 1755, to set the sticky bit. Specifying a value of 0, as in 0755, removes the sticky bit.

# Restoring the file and setting the sticky bit enables you to see the effect:

```
$ ls -l
total 0
drwxrxrwt 2 root root 80 Dec 14 18:25 subdir
$ ls -l subdir/
total 304
-rw-r--r-- 1 root 240268 Dec 14 18:25 f1701.tif
$ rm subdir/f1701.tif
rm: cannot remove subdir: Operation not permitted
```

In this example, although kirk has full read/write access to subdir, kirk cannot delete another user's files in that directory.

You can identify a directory with the sticky bit by a small change in the symbolic mode by ls -l. The world execute bit is shown as a t rather than an x. In this example, the result is that subdir's permission appears as drwxrwxrwx rather than drwxrwx.

The sticky bit is particularly important for directories that are shared by many users. It is a standard feature on /tmp and /var/tmp, for instance, since many users store temporary files in these directories, and you would not want one user be able to delete another user's temporary files. If you want users to collaborate on a project to be able to write files into each others' home directories, you might consider setting the sticky bit on those home directories, or on the subdirectories where users are sharing files.

# Set User ID (SUID) The user ID (SUID) option tells Linux to run with the permissions of whoever owns the file. For instance, if a file is owned by root and has its SUID bit set, it runs with root privileges. This is often called SUID, which is indicated by an s in the owner's execute bit, in rwsxr-x.

# Set Group ID (SGID) The group ID (SGID) option is similar to the SUID option, but it sets the group of the running program. This is often called SGID, which is indicated by an s in the group execute bit, in rwxrsr-x.

You can set these bits by using chmod:

### Using an Octal Code In the leading digit of a four-digit octal code, the value 4 sets the SUID bit, 2 or 6 sets both bits. For instance, 4755 sets the SUID bit, but not the SGID bit, on an executable file.

### Using a Symbolic Code Use the s symbolic code, in conjunction with u to specify the SUID bit, g to specify the SGID bit, or to set both bits. For instance, chmod u+s myprog sets the SUID bit on myprog, whereas chmod ug-s myprog removes both the SUID and SGID bit.

Normally, you don't need to set or remove these bits; when necessary, the package manager sets these bits correctly when you install or upgrade a program. You might need to alter these bits if they've been mistakenly set or removed from files. In some cases, you might want to use source code or adjust these values on program files that you compile from source. Be cautious when doing so, though. If you set the SUID bit on a garden-variety program, it will run with increased privileges. If the program contains bugs, those bugs will be able to do more damage. If you accidentally remove these permissions, the results can be just as bad—programs like passwd, sudo, and all rely on their SUID bits being set, so removing this feature can cause them to stop working.

# Hiding Files from View

If you're using Windows, you may be familiar with the concept of a hidden bit, which hides files from view in file managers, the Windows DIR command, and in most programs. If you're looking for something analogous in Linux, you won't find it—at least not in the form of a dedicated feature. Instead, Linux uses a file-naming convention to hide files from view: most tools, like ls -l, hide files and directories from view if their names begin with a dot (.).
