Introduction
If you can't think like a hacker, it will be harder to defend yourself from crackers. This is the premise of ethical hacking.
A security breach can cause massive damage to businesses, potentially stealing information and money, cause damage to your image, downtime, and many other losses.
Due to these risks, companies from various areas, such as banks, telecommunications, large corporations in general, have been looking for professionals and companies specialized in ethical hacking.
An ethical hacker (or pentester, as it is also commonly called), is a security professional specializing in offensive security, that is, more focused on vulnerability identification processes and, consequently, on the development of security methods and protection. What does he do? Generally speaking, get paid to try to break into systems to detect vulnerabilities. Their function is to find security vulnerabilities that a malicious hacker could potentially exploit. To do so, they need to develop skills in system penetration techniques.
But these professional penetration testers must follow a code of ethics to guide everything they do. The EC-Council, creators of the Certified Ethical Hacker (CEH) exam, has one of the best codes of ethics available.
Patience, persistence, and perseverance are important qualities for ethical hackers due to the time frame and level of concentration required to succeed in most attacks. Web and database programming skills, as well as in-depth knowledge of computer networking, are very useful for hackers to perform ethical hacking and vulnerability testing.
Based on this fundamental knowledge, an ethical hacker will use specific techniques that will allow him to invade and detect system vulnerabilities. Most ethical hackers become a penetration testing professional by learning these techniques in two ways: either by learning hacking skills on their own or by taking formal classes. Many, like Roger Grimes, coauthor of this text, have done both.
Although sometimes mocked, self-taught, ethical hacking courses and certifications are often the gateways to good work as a penetration tester.

Chapter 1: An Overview of the Linux System
Although you may not realize it, Linux is a standalone implementation of the UNIX operating system. Linux itself is a kernel, not a complete operating system. Complete systems built around the Linux kernel use the GNU system, which offers a shell, utilities, libraries, compilers, and tools, as well as other programs such as text editors. For this reason, Richard M. Stallman of the GNU project asks users to refer to the complete system as GNU / Linux. In the appendix, there is more information about the GNU project.
Linux development started from a personal project by a student at Helsinki University in Finland called Linus Torvalds. He intended to create a more sophisticated operating system than Minix, a relatively simple UNIX whose source code he had available. Linux follows the US government standard, POSIX. POSIX is the UNIX Application Programming Interface (API) standard, references for developers in the UNIX-like family. Since the introduction of Linux on October 5, 1991, by Linus Torvalds, a large number of people involved in programming have started to develop Linux. The name Linux derives from the junction Linus + UNIX = Linux.
Portability
Linux is a top ported kernel's operating system, It runs on systems from iPaq (a portable computer) to IBM S/390 (an enormously expensive mainframe), although this type of portability was not one of the primary goals of Linus Torvalds. His effort was to make his system portable enough to ensure ease for the compilation of applications on this system from different sources. Therefore, Linux initially became popular to some extent due to the power to get everyone's favorite GPL or other fonts to run on Linux.
Distributions
The complete operating system (GNU / Linux) is considered a Linux Distribution. It is a collection of free (and sometimes non-free) software created by individuals, groups, and organizations around the world, with the kernel at its core. Today, companies like Red Hat or SuSE, as well as community projects with Debian or Gentoo, compile the software and provide a complete system, ready for installation and use. In addition, there are personal projects such as Patrick Volkerding that provides a Linux distribution, Slackware.
As soon as Linus Torvalds made Linux available, he only made the kernel available with a few basic commands. The user himself should pack up the other programs, compile them, and configure them. To avoid this work, the availability of pre-compiled programs for the user just to install was then started. This is how MCC (Manchester Computer Center), the first Linux distribution made by the University of Manchester, came into being. Some distributions are larger, others smaller depending on the number of applications and their quality. Some smaller size distributions fit on a 1.44 MB floppy disk; others need multiple CDs. All of them have their audience and their nature, the small ones (which occupy a few floppy disks) are used for recovery of damaged systems or for monitoring of disks computer network. What makes the difference is how the applications are organized and preconfigured.
Linux Basics
Startup and Shutdown
They correspond respectively to the procedures of turning the computer on and off. The first concerns the supply of power for the operation of the machine's electronic circuits and requires no major precautions from the user. On the other hand, the Shutdown process requires caution, as improper shutting down of the computer can cause damage to the operating system by destroying the internal tables it needs to function. When the computer "hangs," therefore, turning it off should be the last choice. One option is to start another session, check where the problem is, and end the locked session with an appropriate command.
Section Opening on Linux
To use Linux, you first need to enter your username and password, which are read and verified by the login program. In UNIX, a password file is used to store information having a line for each user, containing their alphabetic and numeric identification, their encrypted password, their home directory, and other information. When the user identifies himself, the login program encrypts the password just read from the terminal and compares it to the password file password to give the user permission. This user information file is usually found in the file:
/ etc / passwd. The encrypted passwords came in the file / etc / shadow
User, Root, Groups, access, Protection
The principle of UNIX file system security is based on users, groups, and other users.
  • User: is the person who created the file. The owner of the File
  • Group: It is a category that brings together several users. Each user can be part of one or more groups, which allow access to files that belong to the corresponding group. By default, the initial user group is the same as your username. The group id is called gid (group id).
  • Other: This is the category of users who do not fit as file owners or groups.
Access permissions for owners, groups, and other users are independent of each other, thus allowing a different level of access.
The root account is also called a superuser. This is a login that has no security restrictions. The root account should only be used for system administration. Use the normal user account instead of the root account to operate your system. One reason to avoid using root privileges is because of the ease of irreparably damaging the system.
Session, Login, Password, Logout
On Linux, the system is logged in with a login and password, where login is the username and password is a security password. Once logged in, the user logs into their account and opens a session where they interact directly with the Shell. Logout (to clear the account) is done via the 'exit' command.
Virtual Consoles
Terminal (or console) is the keyboard and display connected to your computer. Linux makes use of its multiuser feature, mainly using "virtual terminals." A virtual terminal is a second work session completely independent of others that can be accessed on the local computer or remotely via telnet, rsh, rlogin, etc.
On Linux, in text mode, you can access other virtual terminals by holding the <ALT> key and pressing <F1> to <F6>. Each function key corresponds to a terminal number from 1 to 6 (the seventh is used by default by the graphical environment X). Linux has more than 63 virtual terminals, but only 6 are initially available for RAM saver reasons. If you are using graphics mode, you must hold <CTRL> + <ALT> while pressing a key from <F1> to <F6>.
A practical example: If you are using the system in Terminal 1 with any login and want to login as root to install a program, just open a virtual terminal and perform the desired task.
File System
Files are central to UNIX in a way not found on other operating systems. Commands are executable files, usually found in predictable locations in the directory tree. System privileges and permissions are controlled largely through files. I / O devices and I / O files are not distinguished at the highest levels. Even inter-process communication occurs through file-like entities. All system security depends largely on the combination of ownership and safeguards set on your files and your user accounts.
The Hierarchical System, Directory Tree, Branch Assembly
UNIX has a hierarchical directory organization in a format known as the file system. The base of this tree is a directory called `root directory`. On UNIX systems, all available disk space is combined into a single directory tree below /, where the physical location where a file resides is not part of the UNIX specification.
Basic File Types: Plain Files Directory
The files are where the data is recorded. A file can contain text, song, program, etc. Every UNIX system recognizes at least three file types:
  • Common Files: Used to store data. Users can append data directly to common files, such as through an editor. Executable programs are also stored as common files.
  • Directory Files: A directory file contains a list of files. Each entry in the list consists of two parts: the file name and a pointer to the actual file on disk. On the other hand, directories behave exactly like common files, except that some commands used for handling common files do not work for directory files.
  • Special Files: These files are used to refer to physical devices such as terminals, printers, disks. They are read and written as common files, but such associations cause the physical device attached to it to activate.
Linux is case sensitive, meaning it is case sensitive in files. The directory, like any other file, is also case sensitive. In the same directory, there cannot be two files with the same name or a file with the same name from a subdirectory. Directories on Linux are specified by a "/."
NOTE: We are used to seeing filenames as name.ext, where ext is the extension of the file type, for example .txt, .html, .doc. However, on Linux names do not have to follow this rule. Names can be made up of various extensions, such as list.ord.txt, names.may.class, books.my.ord.txt.
Linux organizes your system through inodes. Inodes are disk data structures that describe and store file attributes, including its location. Some inode fields are: user, group, file type, creation time, access, mode (modification), number of links, size and address on disk.
There are mechanisms that allow multiple names to refer to a single file on disk.
These mechanisms are the links. There are two types of links: hard link (or symbolic) or soft link.
  • Hard link: associates two or more file names as the same inode. Hard links share the same block of data while functioning as independent directory entries.
  • Soft link: These are files pointers that point to another file name in the file system.
File Access Permissions
The UNIX system provides an easy means of controlling how system users can access all three file types. This is to allow or restrict access to important system files and to ensure the privacy of every user who has an account on the system. The system differentiates three classes of users. First, every file has an owner, designated in the system by the user. The owner has full control over the restriction or permission to access the file at any time. In addition to individual ownership of the file, it is possible for one or more system users to own the file collectively in a group property type. A user who does not own the file may have access to it if they belong to the user group that has permission for this. However, this user cannot restrict or allow access to the file. Users who do not own or belong to a group that has access to the file from the last category, known simply as "others."
  • The owner (designated by u, user): who created the file.
  • Group (called g, from group): The group consists of one or more users who can access the file.
  • Other (referred to as o by others): Refers to any other system user.
The Unix system also allows three modes of file access: reading, writing and execution. The three access modes are relatively logical, but the meaning of these three access modes is different for directory files. The user with reading permission can read the directory contents, for example, with the command "ls." The user with write permission can use some privileged programs to write to a directory. Write permission is required to create or remove files from the directory.
A user must have execute permission on a directory to have access to the files allocated there. If a user has read and write permission on a common file that is listed in a directory but does not have to execute permission for that directory, the system will not let him read or write the contents of that common file.

Processes
Processes and Subprocesses
A process generally is a simple program that runs on its own virtual address space. It is different from a command or job, which can consist of multiple processes performing a single task on UNIX systems. Simple commands, for example, the execution of `ls' are simple processes. But a complex command comprising pipes execute a single process per pipe section as a rule. To track the status of each process, the system creates a PID (Process ID) for each open process.
There are elements called execution control guides that help control program execution.
  1. Fork: It is the system call whose execution creates a process (identical) to the one that called it. Parent process: Process that generates a new process.
  2. Child Process: Process generated by the parent process.
  3. Pid (Process ID): This is a number that uniquely identifies each process and is used to refer to it.
  4. Parent Process ID (PPid): This is the Pid of the parent process.
Process Control
There are some topics that will allow the user to perform some interesting tasks, such as:
  • execute more than one process at a time;
  • run a process at a low priority.
If you are using a program that will take a long time to finish, and you want to start working on another task, you can call your program to run in what is known as the background. This can be done by placing at the end of the command line the `& 'symbol. You can also, while the program is running, press CTRL + Z. With that, the command will be suspended, and the system will drop the prompt.
We call foregrounding the act of making a program run in the foreground. In this mode, processes can interact with users and display execution on the monitor.
When the nice command is placed before a command line, the time devoted by the CPU execution of that task is reduced, so that it does not delay so much more important processes. That is, the priority of that process is reduced. This command should be used when there are other, more important processes running on the system.
Other process-related commands:
  • jobs lists the background jobs.
  • fg [job] takes the job to the foreground. bg [job] takes the job to the background.
  • ps shows the processes that are running on the computer.
  • top continuously shows the status of each process running on the computer.
  • kill [Pid] terminates the process.

Chapter 2: Users, Groups, Permissions and Users Administration
Administrator Tasks
The administrator of any type of server must be a specialized person, who knows his equipment, his applications, and his users as well as possible, keeping up with technological advances, reviews and patches of installed programs and the needs of your company.
Planning and Forecasting Needs
One of the main functions in the administration of computer systems is the detailed planning of management tasks, which can avoid unpleasant surprises when executing them.
The systems analyst should advise the administrative staff of his company on technological needs in the acquisition of computer equipment, estimating the resources required by users in relation to the economic possibilities of the company.
Once the equipment is received, an installation plan must be carried out, including at least the following information:
  • Documentation and study of available resources.
  • Forecast of possible extensions.
  • Fill in the application for registration in the corporate computer network and activation of the connection parameters.
  • Documentation of needs of the operating environment (UPS, air conditioning, etc.).
  • Documentation on registration, configuration, installation, and update of the operating system, the required applications, and the own programs by the services that the new equipment must provide.
  • Creation and publication of applications for opening and modifying user accounts, program installation, resource improvement, etc.
Documentation
The system manager also undertakes to carry out internal documentation for the Calculation Center, which must describe the following needs:
  • Updated registry of users and groups of the system.
  • Utilization policies and permissions for each user group.
  • Description of the common procedures to be performed by system operators (backups, account management, reports, etc.).
  • Complete and updated records of changes in the server configuration (operating system, applications, files, etc.).
  • Periodic collection and archiving of data on the performance of the system and its components.
Automation
The IT staff of a company must periodically execute the functions defined in the action plan. The programmer needs to automate most of these repetitive procedures to avoid typographical or conceptual errors and to improve the overall treatment of applications.
At least the following tasks must be automated on each server:
  • Checking the free space on the disks.
  • User account management and periodic review of disk quotas.
  • Procedures for creating, checking, and restoring backup copies, according to the action plan.
  • Check and record the overall performance of the system and the computer network.
  • Specific jobs (reports, service management, documentation creation, etc.).
  • Creation of security alerts (change checking, intrusion detection, etc.).
Inform Users
The system administrator must also keep their users informed and give them operation and good use guides, which can avoid errors caused by ignorance.
It is also necessary to report on the changes that may affect each user group, indicating the following information:
  • The nature of the changes that will be made in the system and their temporal evolution.
  • When each modification will be made.
  • What results are expected with the operation, and what are the results.
  • Estimated time and real-time of the duration of the operation.
  • Possible impact on users (new configuration, system shutdown, etc.).
  • Contact information to collect questions and queries.
On the other hand, the person in charge of the system must know the general behavior of its users deeply, recording their queries, their suggestions and the performance and resource usage data. This allows us to offer better quality in the services offered.
System Security Control
Depending on the type of information processed by the system, the administrator must define their security policies, both for the server and for the corporate network, since users have the right to the privacy and integrity of their data.
The means must be put in place to avoid possible attacks or computer failures that affect - or even paralyze - the normal operation of the machine.
You should never have the presumption that a system is completely secure or that it can only be attacked from outside. Therefore, the superuser must perform the following operations:
  • Activate and review historical records of incidents.
  • Perform periodic reviews of possible unwanted changes in the system.
  • Installing the devices and applications that ensure the safety of the computer network and the servers (firewalls, filters, intrusion detections systems, access card readers etc.).
Failure Forecast
Finally, the company must put the necessary physical means in place to prevent and correct possible computer failures.
Environmental changes (electrical, temperature, humidity...) are some of the most important and expensive aspects of error prevention. 
The following topics should be emphasized:
  • Have the correct electrical installation, which prevents unexpected drops and rises in voltage, as well as installing uninterruptible power supplies (UPS) that protect the company's critical services (communications cabinets, servers, etc.).
  • Have an adequate air conditioning system that filters and regulates the temperature and humidity of the environment, without affecting the health of the operators.
  • Have adequate lighting, which does not affect the computer power line.
  • Maintain an adequate infrastructure in the computer network, with convenient and restricted access to communications devices.
Other possible causes of failures that are more difficult to predict are:
  • Saturation or failure of system resources (processors, memory, disks, etc.). The need to request the extension or replacement of the affected components must be weighed.
  • Programming failures, both in the S.O., as in the installed applications or in the own programs. The administrator must stay informed about the updates and patches that he has to install.
  • Human errors of the administrator himself, of the operators, of the technical service or of the end-users.
Permissions and Users Administration
The administration of user and group accounts on Linux is a fundamental task of any system administrator. In this chapter, we will show you how to create, modify, and delete user accounts and groups in Linux. This also includes how to set permissions for these groups and users to access files and directories as they need.
Introduction To User Administration
The internal database of users in GNU / Linux is related to two files:
/ etc / passwd contains the names of the users
/ etc / shadow contains the password encrypted with SHA512
A good security policy is to change passwords periodically. By doing this, even if they can decrypt our passwords, doing so will require much more time and, hopefully by the time they manage it, we will have changed it again.

Password
As indicated above, the keys of local Linux users are stored, encoded, in the inaccessible / etc / shadow file.
The coding algorithms of the keys are "one-way," that is, they prevent the direct decoding of the keys. Therefore, when a user enters the system, the password is encrypted and compared with the valid encrypted key. If the result is correct, the user can connect.
Linux can use the Crypt coding algorithm, used in the old Unix systems, and named for the C language function that performs the calculations. This method is insecure because it uses weak 56-bit encryption keys, and passwords can only have a maximum of 8 characters.
The new Linux also supports more powerful coding algorithms such as MD5 or SHA, much more robust and that allow more extensive and difficult to find keys. The MD5 algorithm uses 128-bit keys, while SHA512 - by default in Fedora 13 and Ubuntu 10.04 - increases this length to 512 bits.

Permissions
One of the main elements of security in Unix is ​​ the proper use of permissions to access files and directories. Every user - not just the administrator - must be clear about the most basic concepts to prevent another user from reading, modifying, or even deleting data of interest.
What is the use of something that belongs to something or someone? The operating systems allow users to access resources or execute commands taking into account a permissions policy. These permissions are managed by the root user (system administrator).
The administrator user - having full control of the system - can also perform operations on the files and directories of any user (a technique that can be used to prevent a user from accessing their own personal directory).
We can divide the permit policy into three broad categories. The classification of these is as follows:
  1. Permissions applied owner user (Owner)
  2. Permissions applied to the group (Group)
  3. Permissions applied to the other (Other) users of the system not contemplated in 1 or 2.
According to these categories, we can apply to each of these three permissions: read (read), write (write), and execute (execution). In particular:
  • r: indicates that the user has read permission. You can execute read commands such as ls, cat, etc.
  • w: indicates that the user has to write permission. This will allow you to edit text files, for example.
  • x: indicates that you have execution permissions. You can run a script.

Chapter 3: Special Permits and ACL In More Depth
It is often necessary to allow a common user to run a binary that is owned by another user with the latter's permissions. It can also happen that a particular program must run with administrative privileges no matter who runs it. For these situations, we have the special SUID and SGID permits (Set User ID and Set Group ID). This topic, together with the possibility of restricting access to files and directories and establishing special attributes for these will be the objectives of this chapter.
SUID, SGID, And Sticky Bit
If a program has the SUID permission and root is the owner of that file, the process that results from executing it will have superuser permissions and will have the same root accesses throughout the system. This emphasizes the need to restrict files that have this special permission to the minimum possible.
Typically, the only program that has SUID is passwd, which allows each user of the system to change their own password (by default, not that of others) without having to rely on an administrator for it.
The same applies to SGID in a file, although it provides access for a process to run with the privileges of the group that owns that file.
To add the SUID to the executable.sh file, we can use two alternatives. One of them is to add a 4 at the beginning of the permissions to be assigned (if we express them in octal) or use u + s as we see below.
chmod 4755 executable.sh 
chmod u + s executable.sh
To set the SGID over another executable.sh the procedure is similar:
chmod 2755, otherexecutable.sh 
chmod g + s otherexecutable.sh
We can see both cases in the following image, where the SUID and the SGID are indicated with a letter s in the list of permits corresponding to the owner or the group, respectively.
In addition to the / usr / bin / passwd file, it is also likely that there are others that have the SUID permission depending on the software that we have installed on our computer (incidentally, another binary that usually has the SUID bit is at / bin / at). In addition to these two examples, the binary corresponding to the X Window system (without the s at the end) also has such permission (for obvious reasons, all users must be able to log in to a graphical environment).
Search for Files with Elevated Permissions
As system administrators, we will be interested in identifying all the files that have the SUID or SGID permissions, and restricting them to the minimum necessary. Once identified, we can proceed to remove them or change their permits to others less potentially dangerous to the integrity of the system.
To perform this task, we can use find and the possibility of using the permissions of a file as search criteria. The following two examples allow you to find all the files that have either of the two special permissions.
find / usr / bin -type f -perm -u + s
find / usr / bin -type f -perm -g + s
As a consequence, we will see the result of the two commands above in a CentOS 7 system (the output may vary in other distributions).
Alternatively, we could save the output of the two previous commands in text files and after a while, execute them again. In this way, we could compare them with the diff command and make sure that the special permissions have not been set in any other program since the last revision.
Sticky Bit
In a Linux system, there may be directories in which all system users can create, modify, and delete files. As examples, we can name / tmp and any shared directory (think, for example, in the common space that can be accessed by several users on an FTP server). The sticky bit applied to a directory is a special permission that only the owner of a file contained in the directory or the owner of the directory can delete it.
To illustrate, we will create the directory / tests and assign 777 permissions:
mkdir / tests
chmod 777 / tests
As a next step, let's add an empty file called example1.txt:
touch / tests / example1.txt
With another user account now let's try to delete the file:
rm / tests / example1.txt
Next, we can appreciate the above commands and confirm that example1.txt was deleted
Let's see what happens if we try to repeat the previous steps after having assigned the sticky bit over / tests:
chmod + t / tests
touch / tests / example2.txt
rm / tests / example2.txt
As we can see, the presence of the sticky bit this time prevents a user who is not the owner of the directory from deleting a file that is not his property.
In general, to enter a directory (using the cd command) and perform operations within it, it is necessary to have read and execute permissions on that directory and its parents. To delete a file, you need to have write permissions on the parent directory, and execution permissions on all parent directories up. For example, to delete the file /dir1/example.txt, it is necessary to have executed permissions on /, on / dir1, and on the latter, also write permissions.
Access Control Lists: ACLs
Directories and files have the permission sets configured for the file owner, the file owner group, and all the other users of the system. But, these permissions have their limitations. We cannot configure different permissions to different users on the same directory or file, for example. In order to do so, access control lists were created, more commonly known by the acronym ACL (Access Control Lists).
It is important to clarify that to use ACLs, and the file system must be mounted with the respective option. By default, ext4 systems are mounted with this functionality. We can verify this with the tune2fs command followed by the -l option and the file system to verify, for example, tune2fs -l / dev / sda1.
There are generally two sorts of ACLs:
  • Access ACLs: list of access permissions for specific files and directories.
  • Default ACLs: This type only can be linked with a directory. If a relevant file connected to a directory doesn't have an ACL, inherit the rules from the default directory ACL.
We can configure ACLs:
  • By user
  • By per group
  • For users who are outside of the user group of the file
  • Through the mask of effective rights
The setfacl command configures ACLs for directories and files. The -m option is used (or its equivalent --modify) for modification of the ACL of a directory or file. This tool is responsible for carrying out the change of ACL permissions (represented by <groups>) on a file or directory (<object> in the example below). Its syntax is as follows:
setfacl -m <roll> <object>
Consider an example to illustrate. John and John users are members of the family group. Therefore, both have read and write access to the file / common / archivaltest
With the traditional permission scheme, it becomes somewhat complicated to assign different levels of access to this file for each user. To remedy this situation, we can use access control lists. Suppose we want John to continue to have write permissions, but that only can read. To achieve that goal, we will create a read-only ACL in / common / archival test for the latter as follows:
setfacl -m u: john: r / common / testfile
With getfacl / common / testfile we can verify that the ACL has been applied. Now let's focus the result of trying to write to the same file after the change.
To eliminate the ACL we will use:
setfacl -x u: john / common / testfile
After which the user will again have write permissions on / commons / proof. In the case that we have created more than one ACL on the same file, we can remove them all together using setfacl -b followed by the path to the file.
Default ACLs are assigned by adding the -d:
setfacl -dm g: family: r / common option
In this way, any file that is added into / common later will inherit the same rule (family group members can read them, but not write to them).
Special Attributes
In addition to the read, write, and execute permissions associated with the owner, the owner group, and the rest of the system users, Linux allows us to set other attributes in files and directories. These properties are specific to the type of file system. In this section, we will talk about some of the ones we can find in file systems of the extended type (we will use as an example ext4). By using these attributes, we can prevent, among other things, that a file is deleted or renamed, or that content is deleted from it.
To see the full list of special attributes available, we can consult the chattr man page. If we want to see which attributes are set in a file or directory, we will use lsattr followed by the path to that object.
To start, we will create two files called test1.txt and test2.txt in our current directory. In each of them, we will then add the following content:
echo "I am the file test1.txt"> test1.txt
echo "I am the file test2.txt"> test2.txt
Now we are interested in establishing the following special attributes:
  • append-only, represented with a
  • immutable, represented by an i.
  • These attributes allow us, respectively:
  • add content to the file, but do not delete anything.
  • Prevent it from being deleted, renamed, edited, or a link added to it.
With an account with superuser permissions, let's add the append-only attribute to test1.txt and also the immutable to test2.txt:
chattr + test1.txt
chattr + i test2.txt
Now let's go back to our common user account and see what happens when
1) we try to add and delete test content1.txt,
2) do the same with test2.txt,
3) delete, rename, edit, or create a test link2 .txt.
The operations that failed cannot be performed while the mentioned attributes are present. Finally, to remove them, we must do (also as root):
chattr-test1.txt
chattr -i test2.txt
The use of file attributes can help us prevent, for example, that an intruder who has gained access to our system can modify or delete system logs (if such files have the corresponding attributes!)
It is also possible to copy default ACLs from one directory to another. Many times when we work, we find that one directory has many access control rules applied, and we want to replicate this in another directory. For this, we will use getfacl and setfacl simultaneously:
getfacl directory1 | setfacl -b -n -M - directory2
The above command copies the ACL from directory1 to directory2 using the -M option that allows the getfacl output to be transformed into setfacl input. In addition, remember that -b indicates that the ACLs of the second directory should be cleaned (if they exist) and through -n we establish new ACLs for it.

  • Checking the file system registry.
  • Live defragmentation without the need to disassemble the file system.

  • Increase the speed of access to data.
  • Increase storage capacity, combining smaller capacity disks into a single larger logical disk.
  • Improve fault tolerance of discs.

Security, benefits and costs are increased.
The total capacity is approximately the total sum of the capacity of the disks minus 1.

It is a RAID 5 with 2 check bands.
It further increases the security of the system and its costs.
The total capacity with respect to RAID 5 is somewhat reduced.

Chapter 6: Package Management
In Linux, the words program and package are often used interchangeably, although strictly speaking, they are not the same. However, for our current purposes, we can consider them equivalent. That way, when we refer to package management, we will be talking about programs. With that in mind, let's enter the exciting world of Linux software management.
Essential Concepts
Let's start by defining package management as the set of tasks for installing, updating, and uninstalling software resources on our system. Today, software distribution on Linux is done in three main ways:
  • Repositories : they are central servers, generally maintained by a particular distribution, by the community, or by other third parties, where a collection of software is available for installation via the Internet or a local network. In simple terms, a repository in Linux (also called software source) is a collection of programs compatible with a given distribution. A repository can reside on a remote server (which is the most common) or on one (or several) local storage devices.
  • Precompiled files : they are compatible executable files for a particular distribution and can be installed both through the network and locally with a command-line tool (in a few minutes, we will see this in more detail).
  • Source code : it is the initial form by which software was distributed in Linux at the beginning. Although it has been surpassed by the previous two, it is still used to offer end users the possibility of compiling a given program with particular options. This software distribution method is also used to make a more up-to-date version available to the public that has higher performance than those present in the repositories.
Each distribution has different utilities for package management. Some of them (such as yum or apt-get, for CentOS and Debian, respectively, together with the members of each family) have the ability to install together with a program given their dependencies, that is, those additional packages that are necessary for the operation of the first. For that reason, they are more commonly known as package managers. Others, such as dpkg (Debian and derivatives) and rpm (CentOS and family), only install the program present in the .deb file or .rpm but without installing dependencies.
More On Repositories
For practical reasons, not all available repositories are included in the initial installation of distribution but can be added later when needed.
All distributions maintain their own official repositories and also have others that are maintained by the community or private users (in the latter case it is usually repositories that contain a few packages). In addition, repositories are often classified according to the type of software they contain.
Although each distribution differs slightly from the others in the way it handles its repositories, the principle of operation is the same:
  1. The repositories in which you want to find software for our system are configured.
  2. Before using the newly configured repositories, it is necessary to update the local package index in a way that reflects the contents of the repositories.
  3. The package manager of each distribution is used to find information about a given package or directly to install it.
To avoid congesting a single repository, around the world, there are several identical replicas or mirrors of the central repositories of each distribution.
In Debian, the list of repositories is maintained in the file /etc/apt/sources.list and in files located within /etc/apt/sources.list.d. In either case, the file format is the same as shown below, taking as an example the Debian mirror provided by the UBA (University of Buenos Aires, Argentina):
deb http://ftp.ccc.uba.ar/pub/linux/debian/debian/ stable main contrib no n-free
deb-src http://ftp.ccc.uba.ar/pub/linux/debian/debian/ stable main contri b non-free
Let's now see in detail how the lines above are composed:
  • deb and deb-src indicate whether the repository contains precompiled binary packages or source packages (which contain everything necessary for one to compile a particular program), respectively.
  • Next, we find the path to the repository.
  • Then the word stable appears (or the codename of the stable version, such as stretch as of today).
  • Finally, we have the list of components of the repository (the three do not necessarily have to appear):
  • main: contains software compatible with the Debian Free Software Policies.
  • contrib: contains software compatible with the Debian Free Software Policies, although its dependencies are generally included in non-free (see below).
  • non-free: software not compatible with the Debian Free Software Policies.
On the official Debian project site, you can consult the list of mirrors by country. We can choose the country in which we live or use the main content distribution network (CDN).
In CentOS or similar, the repositories are configured using individual files within /etc/yum.repos.d. Take as an example CentOS-Base.repo.
In the previous example we can distinguish that the configuration of a repository consists of:
  • The name (base).
  • A list of mirrors (mirrorlist) from which the closest one will be selected geographically, or a fixed repository (baseurl).
  • The indication, if needed, uses the public key of the repository.
  • The path to the public key file.
When we add a new repository to CentOS, we will be asked to confirm that we want to install in our equipment the GPG key that said repository provides for security reasons.
Sometimes it will be necessary to manually add a third-party repository. Generally, we will have to resort to this option when we want to install a more recent version of a program than the one available in the official repositories of the distribution.

Chapter 7: RAID in More Depth
RAID is the acronym for Redundant Array of Independent Disks. It consists of a storage solution that combines two or more disks in the same logical drive in order to provide data redundancy and / or increase the performance of reading or write operations. However, both features depend on the way in which the disks have been organized in what is called a given level (can be thought of as a type) of RAID.
RAID allows access to the entire array of disks as a single set, even if there are several physical disks or partitions at a low level. Using the online RAID Calculator, we can visualize the capacity of an array according to the RAID level used and confirm the type of fault tolerance it provides.
Regardless of the level of RAID, we have chosen or how reliable the storage technology we use to implement it is, a RAID array does not replace the need for an appropriate backup strategy - even if it provides data redundancy.
Three Levels Of RAID In Linux
Although there are more options according to the needs we have, to introduce the topic, we will present only the three most commonly used RAID levels RAID 0, RAID 1, and RAID 1 + 0 or RAID 10. In the illustrative images, the written data blocks on discs are indicated as A1, A2, A3, and so on.
RAID 0
Also known by its English name stripe (because it distributes the data evenly between two or more disks, as shown in the following image), this RAID level provides an increase in the performance of reading operations, but it does not provide fault tolerance. It requires at least two disks to be implemented, and the resulting size is equal to the sum of the size of each disk.
RAID 1
Better known as a mirror, this disk array provides data redundancy by writing them simultaneously on two disks, separately as the image indicates. This allows if one of the disks experiences a failure, the same information is available on the other. However, it impacts negatively on the writing performance since data has to be written twice. By replacing the defective disk with a new one, the arrangement can be rebuilt, and the information copied to it. It requires at least two disks to be implemented, and the resulting size is equal to the smallest disk.
As we can see in the diagram above, the data blocks A1, A2, A3, and A4 are written on both devices (hence the term mirror used to describe this RAID level).

After having created our RAID (whatever the level may be), it is time to create a file system on it and to mount it to be able to use it. Chapter 8: LVM (Logical Volume Management) In Broader Spectrum
LVM is a set of tools that allow the management of storage units called logical volumes. Perhaps its most distinctive feature is that it provides flexibility to manage system storage so that it can be easily expanded when the need requires it.
An additional advantage of LVM is that it allows you to take snapshots of the logical volumes, which can function as backup copies or be used for migrations, tests, restorations, etc., without affecting the operation of the system as a whole.
Traditional Partitioning vs. LVM
The most used distributions nowadays install on logical volumes by default. What are the reasons why the traditional partitioning versus LVM (Logical Volume Management) has lost ground?
To begin, remember that at least in MBR, there is a limitation on the number of primary partitions per disk. In case we need to resize one of them, great care is required. Although we can shrink a partition to give space to another one that has been left small, this procedure causes the following inconveniences:
  • Causes downtime. This means that while we are resizing the partitions, no one else can use the equipment. If it is our personal team, the only ones affected would be us. But if we are talking about a server that other users need to access, this alternative may not be viable.
  • Requires backup copies. If no extra space is available on any partition, there will be no choice but to add another disk to the computer. If we want to use the new device for / home (for example), this will involve moving all user files from the previous location to the new one. Why is this inconvenient? Depending on the size of the backup, the restoration will add time to the downtime we talked about in the previous point.
On the other hand, the resizing of the logical volumes under LVM can be done without interrupting the normal operation of the equipment. In addition, the procedure is much faster than traditional partitioning. The changes are available to users immediately without the need to restart any service.
LVM Structure
A logical volume is - broadly speaking - a storage device that may have been created on the union of 1) whole disks or 2) partitions thereof using the logical volume manager. Unlike traditional partitioning, LVM provides us with the flexibility to easily resize logical volumes. Let's look a little more in detail what the process is about.
The LVM structure consists of the following components:
  • Two (or more) hard drives or partitions on which physical volumes (PVs) of Physical Volume will be created. In this chapter we will use 3 500 MB disks represented by / dev / sdb, / dev / sdc, and / dev / sdd to create three PVs. It is important to clarify that we can create each of them on the entire disk directly or partition it first. If we choose the second option, we must indicate that the partition is of type 8e (Linux LVM). In this opportunity, we will create the PV on the entire disk without partitioning.
  • A volume group (VGs, from Volume Group) is created from one or more physical volumes. For simplicity, we can consider a group of volumes as a storage unit (similar to an entire disk in traditional partitioning).
  • In each VG, we can create several logical volumes, which can be considered as analogs of traditional partitions.
Logical Volume Creation
To create physical volumes on the disks mentioned above, we will do the following:
pvcreate / dev / sdb
pvcreate / dev / sdc
pvcreate / dev / sdd
We should see the following confirmation message after executing each command.
To show the attributes or view information about a physical volume, we can use the pvdisplay and pvs commands, respectively, followed by the PV path (pvdisplay / dev / sdb or pvs / dev / sdb, for example). If we omit the latter, we will see the list of all physical volumes that exist in our system.
Now is the time to create the volume group (we will call it vgcourse). We will only use / dev / sdb and / dev / sdc, for now, to show later how easy it is to extend a VG by adding an additional device (/ dev / sdd). Then we will use vgs and vgdisplay to see the details of the volume group we just created.
vgcreate vgcourse / dev / sdb / dev / sdc
Let us take into account that the storage space available in the course is now 2 * 500 MB = 1 GB. This fact allows us to see another of the advantages of LVM: we can create a storage unit of considerable capacity using smaller disks or partitions.
To create a first 600 MB size LV called lvadmin on video, and we must do the following (if we omit -n lvadmin, the name of the LV will be automatically assigned by lvcreate):

Operations
To add a PV to a VG, we will use the vgextend command followed by the name of the VG and finally the PV:
vgextend vgcourse / dev / sdd
By using the vgs command (or vgdisplay, for more details) followed by the name of the volume group, we can see its size after adding the physical volume.

So far, we have talked about executing commands one by one from the terminal. However, Bash allows us to execute a series of commands from a single line, and even do so under certain conditions. Chapter 10: Rsyslog And Scheduled Tasks
In a Linux system, there are many routine tasks that must be carried out periodically: updating the file database using updatedb, backup copies, cleaning temporary files, to name a few examples. In Linux, we have a utility called cron that allows us to perform repetitive tasks automatically and periodically, to record the result in a log, and to report any anomaly to the administrator. If we only need to execute one task in the future for once, at least it will be more useful. These will be the main topics of this chapter, together with the system event log using the classic rsyslog and journald, the tool provided by systemd.
How To Use cron
To begin, let's clarify that cron is actually composed of two separate utilities:
  • crond is the service that “wakes up” every minute and checks if there are tasks to be executed in the table of scheduled tasks.
  • crontab is the program that allows us to edit the table (which actually consists of a plain text file) of scheduled tasks.
Unless the administrator has configured it differently, all users can automate their own tasks by creating a personal table. As we said earlier, scheduled task tables are plain text files. Typically, these files are saved in / var / spool / cron, and on each line of these are the details of what the task is to be executed, when, and using what system account. For this reason, each scheduled task is generally called crontab entry, or crontab entry.
Create And Schedule A Task
To create a scheduled task, we will use the command
crontab -e
Next, the text editor that we have configured by default will be opened, with which we must write (in the first free line of the file that is opened) using the following format:
minute hour day_of_month day_of_the_week command
Where:
  • minute (0 to 59)
  • time (0 to 23)
  • month_day (1 to 31)
  • month (1 to 12)
  • week_day (0: Sunday to 6: Saturday)
For example, to execute the / bin / updatedb command every Monday of September at 1:55 p.m., we would add the following line in the crontab of a user who has permission to execute such a program:
55 13 * 9 1 / bin / updatedb
When we place the command in the crontab file, it is advised to write the full path to the executable.
Let's analyze the previous line:

System Event Logs
Most (if not all) of the services running on a Linux system originate some type of registration as a result of its operation. Whether it is error messages, login events, or even purely informative issues, it is important that we know where they are stored. This will allow us to examine them when necessary in search of important information.
A log message usually has information about system security, although it may contain any information. The date and time of the shipment are included with each message.
The protocol used for the transmission of these messages is called rsyslog, as is the application that handles such sending. It replaced syslog in this function as the de facto standard in most distributions over a decade ago. The protocol itself is very simple. It consists of a server running the related service, also called rsyslog (rsyslog daemon), that records plain text messages (less than 1024 bytes) sent by each application.
Although rsyslog has some security problems, its simplicity has led many devices to implement it, both for sending and receiving. This makes it possible to integrate messages from several types of systems in a single central repository (even from different computers).
Let's look at the following lines in the configuration file /etc/rsyslog.conf where the lines that start with # are ignored by the service.
  • kern. * Indicates all kernel messages, whatever the severity they are.
  • .info; mail.none; authpriv.none; cron.none is used to record all informational messages (info) regardless of the resource that issues them (hence the use of the wildcard at the beginning) with the exception of those whose origin is mail, authpriv, and cron.
  • All authpriv (private authentication) messages must be saved in / var / log / secure, while for mail and cron the destination must be / var / log / maillog and / var / log / cron, respectively. As in the first example, the use of * after the point tells us that this rule applies to any type of event regardless of its severity.
The sign - in front of / var / log / maillog (and others) was used in previous versions to skip synchronization with the file immediately after each writes a Today is an unused option.
The examples just analyzed will help us explain the structure of the message in the next section.
Message Structure
The message sent by rsyslog consists of three fields:
1. Priority
2. Header
3. Text
Among the three previous fields should not add more than 1024 bytes, but there is no minimum length. Let us now see in a little more detail the meaning and possibilities of each one of them:
  • The priority indicates both the resource (origin) of the message and the severity of the message. It usually follows the convention taken from RFC 3164. The most common resources are auth, authpriv, cron, daemon, kern, lpr, mail, and local0 to local7 for user-defined messages. The severity (in order of importance) can be debugged, info, notice, warn, err, crit, alert, and emerge. By default, all messages of the specified severity and greater will be recorded according to what is indicated.
  • The header indicates both the date and time of the message and the server (name of the computer from which it originates) and, together with the explanatory text, constitutes the information stored in the log file.

logger -p local1.notice "This is a warning"

It will keep messages in /var/log/mi.log (destination for local1.notice and severity) messages. This is a warning.

Alternatively, system messages can be sent to:
  • another machine, to store them remotely. For this, it is necessary to indicate in the field of action the name or address of said system preceded by two @ signs instead of a path to a local log file. This is useful if we have a secure machine, which we can rely on (connected to the network). In this way, a copy of the messages of our system would be stored there, which could not be modified if someone could log in to the machine that is generating them. This requires that the remote system be enabled to take messages from other computers.
  • a script that is executed every time a message of a certain type originates. In this case, we must place the ^ sign in front of the full path to the script.

Under systemd, the service responsible for collecting and storing messages from the kernel and other sources is called journald. Chapter 11: Disk Quotas
Storage is a resource that must be granted and carefully monitored, more especially on a Linux system used as a mail or web server, to name two examples. Apart from the problem that may not be able to save new files, a system with little available space will soon experience performance problems. For that reason, limits should be set per file system (more frequently called quotas for users and groups) to disk usage and the number of files that users can create.
Previous Steps
Before starting, it is important that we consider the following useful points (both are related to the two methods of quota allocation):
  • A disk block corresponds to 1 KB. A block fee would correspond to the total blocks that can be used in the system. Recall that the files are saved in disk blocks. In this way, a 100-byte file will occupy a block of 1 KB on the hard disk since the block is the smallest unit of fractionation.
  • An inode (or index node inode in English) is a number that acts as a pointer for the file system and indicates in which specific blocks of the disk the data of a file is found. Also, the inode in your reference stores information about permissions, owner, attributes, etc. It could be seen in a simple analogy that an inode is like a unique serial number for each system file, and through this number, the system retrieves its data (blocks) and its attributes (permissions, owner, dates, etc.).
A fee for inodes would indicate the total number of inodes to which the user is entitled. In other words, one could say that this would represent the total files that the user can create. Keep in mind that this does not change the fact that users could still create symbolic links on existing files that do not increase the amount of inodes. Anyway, for simplicity, we can see it as a 1 inode = 1 file.
The first step to enable quotas in a file system is to mount it with the usrjquota or grpjquota options (for the user or group quotas, respectively) using a line in the / etc / fstab file.
To illustrate, given the logical volumes / dev / vgcareerlinux / lvadministrador and / dev / vgcareerlinux / lvredes existing and previously formatted with ext4, let's enable group quotas in the first and user quotas in the second.
While we can specify in each / etc / fstab each logical volume (such as any storage device) through its device identification (/ dev / vgcareerlinux / lvadministrador and / dev / vgcareerlinux / lvredes in this case), it is more prudent and stable to specify them through your UUID. Remember that we can find out this data using the blkid command followed by the identification of the formatted device:
blkid / dev / vgcareerlinux / lvadministrator
blkid / dev / vgcareerlinux / lvredes
We will copy the UUID of each volume and insert the following lines in / etc / fstab with the help of the echo command:
echo "UUID = 7457567b-28f3-46c5-9f92-d74780536188 / srv / admin ext4 defaults,
grpjquota = aquota.group, jqfmt = vfsv0 0 0" >> / etc / fstab
echo "UUID = 01be396e-1a2e-4070-87c9-4b41f0c091d0 / srv / networks ext4 defaults, usrjquota = aquota.user, jqfmt = vfsv0 0 0" >> / etc / fstab
The mount options usrjquota = aquota.user and grpjquota = aquota.group represents the files that keep user and group information within the root of each mount point. On the other hand, jqfmt = vfsv0 enables the use of journaling with quotas in version 2.
The next step is to disassemble (if they were already mounted; otherwise omit the following two commands) and reassemble the file systems identifying them by their mount point as specified in / etc / fstab:
umount / srv / admin
umount / srv / networks
mount / srv / admin
mount / srv / networks
Now we must ensure that the usrjquota and grpjquota options are present at the output of the mount command. To be able to visualize the lines that are of our interest, we will use grep:
mount | grep vgcareerlinux
Finally, with the following commands we can initialize and enable disk quotas by users and groups, respectively (which will require that we have previously installed the quota package):
quotacheck -avmug
ls / srv / networks
ls / srv / admin
quotaon -vu / srv /
quotaon networks -vg / srv / admin
The first command will initialize the quota table and create the special files aquota.user and aquota.group. As for the options, these indicate the following:
  • -verifies all file systems by quotas.
  • -u checks support for user fees.
  • -g does the same for groups.
  • -m prevents the system from being traced as read-only.
  • -v reports the operation as it progresses through visible messages in the terminal.
Then, with quotaon, we will enable the functionality in the mentioned file systems. The use of ls will simply allow us to verify that the files containing the information of users and groups have been created correctly.

Let's now see how to set disk quotas by specific users and groups. We will use as an example a user called a student, to whom we will grant an initial quota of 10 MB (unreal, by the way, but it will suffice for our demonstrations) using the command

  • soft is the lower limit of blocks that the user can have before receiving a warning. If, after 7 days (grace period by default) after receiving it, no space has been released, the soft limit becomes hard (see below).
  • hard is the upper limit of the use of the device. Above this value, you cannot continue writing on it until you free up space.

When using the soft limit, two situations can occur: 1) If a grace period is not established, the user can continue using blocks or inodes until the hard limit is reached, which will be his absolute limit of use. 2) Otherwise, you will be allowed to continue using blocks or inodes until the grace time is over or the hard limit is reached, whichever comes first.

Chapter 12: Startup and Services
Boot Process
During the machine startup process, the necessary checks are carried out to configure and activate all the services defined by the system administrator. It is essential to know this procedure and prepare the necessary changes according to the planning made for that computer.
The boot process of a Linux server based on x86 architecture (Intel, AMD) comprises the following steps :
After checking the devices of the machine, the BIOS executes the first step of the system loader, located in the boot sector of the first hard disk. GRUB is the loader currently used in Linux.
  • The boot loader executes the second step of the process, located in the / boot partition.
  • The Linux kernel and its additional modules are loaded into memory, and the root partition is mounted in read-only mode.
  • The kernel takes control of the boot sequence and executes the boot process (/ sbin / init.
  • This initiation program loads all defined services runs the initiation and configuration programs and mounts the defined partitions. / sbin / init reads the information from the configuration files (/ etc / inittab in Fedora SysVinit or /etc/event.d/* in Ubuntu Upstart). The process first loads the basic services and then those associated with the boot level chosen by the administrator.
  • The system startup is finished by presenting the user with the connection process (login) or the graphical environment (usually GNOME or KDE).
SysVinit, implemented by default in Fedora and many other Linux distributions, is a sequential boot process (based on System V Init), which is slow and presents certain problems for using new devices (such as USB file systems).
Ubuntu uses Upstart, an event-controlled process that is still under development and can emulate the operation of SysVinit.
There are also other alternatives under development based on parallel (init-NG) or event-driven methods (Solaris Service Management Facility or Apple launchd).
The GRUB Charger
As described in the previous section, a boot loader program is responsible for starting an operating system.
The main loaders used by Linux support the definition of an execution menu for the different operating systems installed on the computer and start them at certain execution levels.
The GNU Unified Startup Loader (GRUB) allows the user to choose the operating system and the kernel with which they want to work.
GRUB has 2 modes of operation:
  • Direct mode is used to load the Linux kernel without any intermediaries.
  • The chained mode is used to load other operating systems and points to the first boot sector of the partition, where the system startup files are located.
GRUB offers the user a valid operating environment to perform configurations prior to the start of the operating system, being able to directly access its control file /boot/grub/grub.conf or /boot/grub/menu.lst.
The orders for the GRUB configuration define the characteristics of the boot menu, indicating the different system load options, the default option, time limits, graphic environment, etc.
The following example presents the configuration of a menu to boot Ubuntu 10.04 Lucid with a kernel version 2.6.32-22 in the second partition of the first disk, and Windows XP in the first partition.
boot=/dev/sda default=0 timeout=5
title Ubuntu 10.04 LTS, kernel 2.6.32-22-generic
kernel /boot/vmlinux-2.6.32-22-generic root=/dev/sda2 ro quiet initrd /boot/initrd.img-2.6.32-22-generic
quiet
title Windows XP SP3 root (hd0,1) makeactive chainloader +1
When the machine is turned on, GRUB presents the user with a selection menu, and the user can edit the different options before starting the corresponding operating system.
GRUB 2 is a development version, included in the new Linux distributions, which means a redefinition of the loader, to allow its use in different architectures, access local file systems, including a complex scripting language, etc.
The Nucleus
Unix operating systems are based on a layer structure, where the internal layers provide basic services to the external ones. The Kernel is the main part of the operating system, performs the basic control functions, and provides the essential services to manage the operating system.
The Linux kernel consists mainly of the components described in the following table.
Memory Manager:
Responsible for assigning memory areas and paging spaces to processes, kernel modules and cache area.
Process Manager:
The essential part that creates activates and terminates processes; Implement the rules of multitasking.
Device Drivers:
They manage the communication of the system with each of the connected devices. The kernel is configured in the boot process to load the modules necessary to control the specific devices of each machine.
Virtual file system manager:
Intermediate layer that allows uniform access to file systems, maintaining a homogeneous directory tree.
Network Manager:
Abstract layer for general access to the computer network, regardless of the type of devices used and the architecture of the network.
Being Linux, an operating system based on open-source, the administrator can redo the kernel, including or eliminating operational features, according to their needs. The process to recompile the Linux kernel is increasingly easy to perform, as it is configured through menus with a large number of options.
To increase the performance of the system, it is convenient to have a small core, but that can handle all the basic functions of the system. The management of additional devices and functions can be controlled by the core modules.
Modules
Linux kernel modules are objects compiled in C language that control specific elements or functions.
The basic modules for the control of the connected devices are loaded in the operating system startup process. The rest of the modules that the system manager considers necessary should be listed in the configuration files, as well as the optional parameters that these require in order to obtain optimum server operation.
Version 2.4 of the Linux kernel uses a single file /etc/modules.conf, while version-based distributions 2.6 of the kernel locate several files (one per module or group of modules) in the /etc/modprobe.d directory.
In the configuration files, the associations (aliases) between real and virtual modules are specified. Virtual modules are the interfaces between the system and the modules that control real devices; they are responsible, for example, for managing the network, special file systems, exclusive sound card capabilities, etc.

Operation Parameters
The new versions of the Linux kernels support the configuration and customization of its operating parameters, which affect the behavior of its components, such as: increasing the máximum number of open files (fs.file-max) or activate the ability to forward packets to create firewalls (net.ipv4.ip_forward).
Modifications in the predefined environment for the kernel will be reflected in the file corresponding to the modified feature, located in the virtual / proc / sys file system.
The configuration file of the kernel operating parameters is /etc/sysctl.conf and can be edited by the system manager to include the changes at the next system startup. Also, the changes are activated automatically by executing the sysctl -p command.

Boot Levels In Sysvinit
Many Linux distributions, such as Fedora, use a sequential boot process inherited from Unix System V, known as SysVinit.
Boot levels serve to allow SysVinit to operate in different ways according to the needs of the administrator. Simply by changing the boot level, the operating system can enter maintenance mode and then return to multi-user mode.

The init command reads the configuration scripts stored in the /etc/rcN.d subdirectory, corresponding to the selected execution level. The mode of operation is as follows:
  • Stop in sequence the processes corresponding to the KNNservice files, NN being the sequence order (2 digits) for that service (it is executed: /etc/rcN.d/KMM stop service).
  • Start the file processes sequentially SNN service (runs: /etc/rcN.d/SMM start service).

Jobs in Upstart
Upstart [viii] is a non-sequential event-based boot process that has been included by default as of Ubuntu version 6.10.
A job is a task or service that can be executed or stopped when an event is triggered, and that can also generate new events to manage other jobs that depend on it.
A boot system of this type has the advantage of being able to launch the necessary tasks when the system recognizes the corresponding devices, without having to wait to finish the execution of previous tasks. Therefore, a kind of task execution tree can be defined.
Upstart can emulate the way SysVinit works, defining execution levels for general system services. Ubuntu 8.10 Intrepid defines level 2 by default, in addition to maintenance levels (0, 1 and 6)
The following example shows the file /etc/event.d/rc2, which configures the job to define execution level 2.
start on runlevel 2 stop on runlevel [!2] console output
script
set $(runlevel --set 2 || true) exec /etc/init.d/rc 2
The administrator can define the starting order of the services, similar to SysVinit, including symbolic links to the corresponding scripts in the /etc/init.d/rcN.d directory or by executing the update-rc.d command.
The execution format to start or stop a service is as follows:
/etc/init.d/ Service { start |stop |restart |reload |status }

Basic Process Control
The process can be understood as any program or command in execution. A process has the following characteristics:
  • Each process consists of code, data and stack zone.
  • The processes exist in a tree hierarchy (several children, one parent).
  • The system assigns a unique process identifier (PID) at the start of the process.
  • The task scheduler allocates a time-share for the process based on its priority (only root can increase the priority of a process).
  • Each process stores its identifier (PID) of its parent process (PPID), the owner and group of the process, and the environment variables.
The superuser must maintain control of the system at all times, making periodic reviews of the processes that are running on the server, which can avoid problems and abuses that affect the normal operation of the machine.
