
# Recovering from a System Compromise

The realization that you have been attacked and your system has been compromised is a very humbling experience. You will suffer an attack at least once in your career, however, you should be prepared to deal with the situation. Here are five steps you should follow to recover from attacks with minimal damage and maximum protection from future incidents:

- 1. Quarantine the compromised systems.
- 2. Gather evidence.
- 3. Report the incident.
- 4. Back up system data.
- 5. Reload the compromised systems.

The following sections discuss each of these steps in detail.

# Quarantining the Compromised Server

Once you have confirmed that a machine has been compromised, you should remove it from your network and isolate it, either without a network or on a quarantined network whose sole purpose is to examine compromised systems. This stops any hacker activity in its tracks and prevents the perpetrators from cleaning up after themselves (important for step 2). Additionally, if a hacker has installed a network sniffer, a worm, or any other code that can potentially affect other systems on your network, quarantining that server prevents that from doing any damage.

# Disable User Accounts

You should also disable any compromised user accounts at this point to prevent hackers from breaking into other systems using those same accounts. Make sure you-disable accounts on all servers as well as central authentication services like NIS and Kerberos.

# Gathering Evidence

Make copies of log files, changed configuration files, exploited code, and anything else that would indicate the presence of a hacker. If any user accounts were compromised, thoroughly investigate the contents of their home directories and search the entire file system tree for files owned by those users. You would be surprised at the places a hacker will store files once or she has root access. Some hackers have used such obscure locations as a hidden directory in /dev—the last place anyone would look for a file. Hackers have also created directories that look like “...", which will appear next to “.” and “..” (current and parent directories) in a directory listing.

# Make a Permanent Copy of the Evidence

If possible, you should make a hard copy of any evidence or burn it to a CD-ROM. You might need such a permanent copy of the evidence later, for legal purposes.

# Reporting the Incident

At this point, you should take some time to report the incident to your local security administrator, who should be designated in your security policy (you learn about security policies in Chapter 16, "Computing Policies and Agreements"). If your organization isn't large enough to warrant a security administrator, report the incident to your manager and CTO or CIO. You might also consider reporting the incident to the CERT® (Computer Emergency Response Team) Coordination Center, which collects statistics on current and past security incidents. Those reports can help investigators track down the instigator of the attack. A form for report can be found at http://www.cert.org/reporting/incident_form.txt.

# Internal Response Teams

Universities and other large organizations may choose to form their own CERT-like organization to deal with their security issues internally before utilizing external resources.

# Backing Up System Data

Back up any critical system data and configurations onto tape or CD-ROM and mark it as quarantined or tainted data. You may need to retrieve an old configuration from this backup to re-create the compromised system.

# Don't Copy Tainted Data!

Never directly copy a file from a quarantined system or backup! You run the risk of tainting a system with potentially harmful configurations. Retype any configurations by hand instance.

# Reloading the Compromised Systems

Once a system has been compromised, it should be considered dead for all intents and purposes. Never reinsert a compromised system back into production! Wipe its disks clean and reload the operating system from scratch to eliminate any remaining damage from that system. Then, apply any patches or configuration changes necessary to plug up the hole that allowed the compromise in the first place.

You also should take some time to analyze what allowed the break-in to occur in the first place and implement new practices to ensure it does not happen again. For example, if your system was compromised because you neglected to install the latest security patches announced the month before, you could make it policy that all security patches should be tested and installed within a week of their announcement.

# Securing Data with Encryption

Encryption is one of the most important technologies that facilitate security on systems and on the Internet. The concept of encryption is fairly simple: scramble data such that only an authorized party can unlock it. But encryption has a variety of different applications, including authentication, data security, and data integrity, all of which are critical in today's publicly accessible networks. This section defines some of the important concepts in encryption and explains how it is used in the real world.

# Public Key Encryption Versus Symmetric Key Encryption

Two major forms of encryption are in use today: symmetric key encryption and public key encryption. Symmetric key encryption is the form most people are familiar with; it uses a symmetric key to both encrypt and decrypt data, so both the sender and recipient of the data must have a copy of the key. Symmetric key encryption is very effective and fast, but its major flaw lies in key distribution; you must distribute the key to authorized recipients without the possibility of anyone seeing it. Though you can accomplish this distribution through any number of means, as a rule, you should never transmit a key over a clear channel. Ciphers are symmetric key encryption mechanisms. Hundreds of ciphers are now available on the Internet, including the following:

- DES (Data Encryption Standard)
- Triple DES
- AES (Advanced Encryption Standard)
- Blowfish
- Arcfour

Public key encryption solves the key management problem that plagues symmetric keys. Also called asymmetric encryption, public key encryption uses two different keys for encryption and decryption, called a key pair. The key pair consists of a public and private key that are mathematically related such that only the private key can decrypt data encrypted with the public key, and vice versa. The private key should be kept secret at all times, but the public key can be distributed freely without fear of compromising the security of your encrypted data.

Traditionally, the public key is used to encrypt data that is sent to the recipient holding the private key, who is theoretically the only one who can decrypt it. The only downside to key encryption is its speed.

# Signing Data

Data can also be encrypted with the private key—this is known as “signing” the data. Recipients of a signed message can use the freely available public key to decrypt it. If it successfully decrypts, the recipient knows the message from the true owner of the key.

# Real-World Example: Encryption on the Web

The web uses an encryption mechanism called SSL (Secure Sockets Layer) that is actually a hybrid of symmetric key and public key encryption. Public key encryption is used to verify the authenticity of the server and is then used to securely transmit a session key, at which point symmetric key encryption takes over.

# One-Way Hashes

One-way hashes are not a form of encryption, but rather a way of mathematically obfuscating data into a “hash” so that it is computationally infeasible to decode the original data from the hash. Hashes are like a jigsaw puzzle—without the picture on the box, it is extremely difficult to put the pieces together to reveal the image.

No two messages result in the same hash. Mathematically, it is possible for two messages to produce the same hash, but it is highly unlikely to occur in practice. One-way hashes have two main functions in Unix: checksums and password verification.

# One-Way Hashes for Checksums

When you download a file from a remote Web site, how do you know it has not been tampered with? Many sites nowadays, especially those containing software and source code, provide checksums for each file available on their site. After downloading a file, you can compute its checksum and compare it to the checksum on the Web site. If the checksums do not match, the file (or checksum) has been tampered with, and you should discard that file.

One of the most common-way hash mechanisms is called MD5. You can see MD5 in practice on Apache’s Web site, http://www.apache.org. Suppose you wanted to download and compile Apache 1.3.24, which you wanted to be certain that the file was authentic. After downloading the file apache_1.3.24.tar.gz, you could view another file on the site called apache_1.3.24.tar.gz.md5, which contains an MD5 checksum of the file.
