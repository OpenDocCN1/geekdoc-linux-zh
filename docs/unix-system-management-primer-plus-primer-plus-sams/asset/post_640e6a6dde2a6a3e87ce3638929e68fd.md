
# UNIX SYSTEM MANAGEMENT PRIMER PLUS

Programs that need the CPU to perform calculations are called CPU-bound processes. The CPU is the bottleneck for such processes. On the other hand, a mail hub that processes mail for thousands of users will most likely be I/O-bound, because the majority of its activity is based on disk reads and writes; processor has little impact on this application.

It is easy to tell if a process is CPU-bound. If a process consistently suffers a decrease in performance when other applications use the CPU, that process is most likely CPU-bound. You can use tools such as to check for CPU-bound processes (you learn more about I/O-bound processes in Gauging Storage Performance and Capacity), later in this chapter.

## Tracing Processes

Many kernels support the tracing of a running process's system calls. Tracing is an incredibly useful tool, especially when a process is misbehaving, because you can see exactly what the process is trying to do. For example, on a Solaris server with a 15-minute load average of 1.30, you can trace the system calls for all the processes that are using up to 30% of the CPU by the truss command, as shown:

```
# truss -d -p 260
Base time: 101611736.3879 [ Thu Mar 14 22:08:56 EST 2002 ]
260:     0.0015 write(11,"0FF@060101010101010",...)      = 2047
260:     0.0023 write(11,"0FF@060101010101007",...)      = 2047
260:     0.0039 write(11,"0FF@0601010101004C3",...)      = 2047
260:     0.0035 write(11,"0FF@0601010101010r a",...)      = 2047
260:     0.0041 write(11,"0FF@0601010101010101",...)      = 2047
260:     0.0045 times(0xFFFECCFB)                                 = 127596336
260:     0.0049 write(11,"1089@060101010101010",...)      = 137
260:     0.0098 read(8,"10 y0101010101010003 ...",...)      = 121
260:     0.0103 times(0xFFFEB020)                                 = 175906337
260:     0.0109 write(11,"0FF@06010101010106081",...)      = 2047
260:     0.0115 write(11,"0FF@06010101010102C U",...)      = 2047
260:     0.0121 write(11,"0FF@0601010101010101",...)      = 2047
```

In 0.015 seconds there were 16 writes, 13 of them were 2KB writes. Although unusual, this is a significant amount of activity for a short period of time. Now know that Oracle is performing a lot of individual write operations to disk, and that is one piece of evidence you can use to diagnose the cause of the high load. In this case, the writes were caused by the DBA bulk-loading large amounts of data into a database. Even though the process was writing to disk, it was CPU-bound by the large number of calls to the write function; if it wrote in chunks larger than 2KB, the process would have less time calling the write function and more time actually writing to disk. truss is only available on Solaris: Table11.1 lists the truss commands for several other Unix systems.

## Gauging Storage Performance and Capacity

The performance of storage devices, hard disks in particular, is vital to the performance of a system because absolutely everything is stored there. Swap space is located on disk as well—a poorly performing partition can severely degrade the performance of a system.

To fully understand how to assess and optimize storage performance and capacity, you must first understand certain basic concepts and terms, including storage capacity, disk architecture, bandwidth, latency, sequential and random access, block and character I/O, and inodes. After defining each of these items, the following sections also discuss some of the most useful tools and techniques for examining disk performance and capacity.
