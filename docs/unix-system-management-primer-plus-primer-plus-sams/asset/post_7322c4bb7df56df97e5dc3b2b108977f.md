# Alternative Authentication Methods

Authentication represents the most glaring security hole in most organizations. Many sites simply require a username and password for user authentication, and that is sufficient for most sites. However, when you think about how easy it is for someone to guess a password, sniff a network connection, or even just look over your shoulder while you are typing a password, quickly understand that usernames and passwords are not the most secure authentication mechanism by any means.

Unix, like most operating systems, is capable of supporting alternative authentication methods. This section documents some of the more common methods in practice.

# Pluggable Authentication Modules

Red Hat Linux, HP-UX, and Solaris support pluggable authentication modules, or PAM. PAM separates authentication mechanisms from the application code so you can change how your users without changing a line of code. Authentication code comes in the form of shared objects that are dynamically loaded by the application. A configuration file called pam.conf controls which authentication mechanisms are associated with which applications. Many of the functions documented in this section of the chapter are available as PAM modules. You can read more about PAM at http://www.sun.com/software/solaris/pam.

# One-Time Passwords

When you are traveling and have no access to encryption software such as SSH or a VPN, your last resort for remote access is Telnet. However, typing a password over a clear channel can be very dangerous, because anyone might be listening. One-time passwords, or OTP, solves this problem.

One-time passwords are used once and only once for the same account, and prevent anyone from sniffing a valid password off of the network. Typically, a user prints out a list of passwords generated by the OTP system and uses those passwords one by one in order. You also can use the OTPs in conjunction with regular passwords to provide two-factor authentication.

# Protect Your One-Time Passwords

Just because each password can only be used once is no reason to guard one-time passwords any less securely than regular passwords. Keep printed lists of passwords safe and away from the prying eyes of others.

The two most popular OTP systems are OPIE and S/Key (OPIE is actually an improvement over S/Key). You can read more about these technologies at http://www.inner.net/-cmetz/opie and http://citeseer.nj.ee.com/34338.html.

# Time-Based Passwords

An improvement over the one-time password scheme is the time-based password scheme. Here, your password is based on the current time, which facilitates the use of a token that displays your current password, called a PIN in this context. This PIN is usually a random number based on a seed shared with the authentication server. The functionality of this system depends on the accuracy and synchronization of the clocks in the token and the authentication server as a common random number seed.

Most time-based authentication systems utilize two-factor authentication, requiring a separate password as well as the PIN displayed on the token. These systems hold a distinct advantage over one-time passwords, because you never have to go back to the server to get more pass—your current password is always displayed on your token.

One of the most recognized companies in field is RSA, and their SecurID system uses cryptographic tokens for time-based two-factor authentication. You can read about this technology at http://www.rsasecurity.com/products/secured.

# Certificates

Digital certificates use public key encryption to provide authentication. If you recall from the discussion of public key encryption, a private key can be used to privately “sign” a document—“if the corresponding public key can decrypt the document, it is certain that it was encrypted using the private key. A digital certificate in its simplest form is a document that is signed with special key, usually belonging to a trusted third party called a certificate authority (CA). When you send the certificate to a server trying to authenticate you, this entire public key infrastructure, or PKI, depends on the proper behavior of certificate authorities and your trust in PKI has been the subject of numerous papers, talks, and conferences since the mid-1990s.

The problem with digital certificates is that they are just single documents, much like a password. If a third party manages to get hold of your certificate, they can potentially impersonate you just as they can with your password. Digital certificates are only secure in a two-factor authentication system where they are supplemented with a password or other authentication mechanism.

# Kerberos

All of the secure authentication mechanisms described so far have either encrypted passwords or avoided sensitive passwords over the network. Kerberos is a radically different mechanism that does not send passwords over the network at. Instead, Kerberos uses your password as a key to decrypt service tickets, which are used in place of a password to authenticate to services such as Telnet and FTP. The only time you actually enter a password is when you log in.

Kerberos is a "trusted third party" system; it depends on a key distribution center (KDC) to hold copies of the passwords, or keys, for each user, as well as keys for each service. A service ticket is an identifier that is encrypted with both the service and the user's key. When a user wishes to use a ticket to connect to a service, the ticket is decrypted with the user's key, resulting in data encrypted with the service key. The ticket is then sent to the server where it uses its key to decrypt and retrieve the user's identity. This double encryption is what makes Kerberos work.

The most important factor of Kerberos is the KDC. As a trusted third party and holder of all the keys, the KDC must remain physically secure and isolated from network attacks. If a KDC is compromised, you don't lose the KDC—your entire infrastructure is compromised.

Kerberos has one significant disadvantage—all network services, both clients and servers, which have code to support TCP. Although various implementations of Telnet, FTP, and SSH support Kerberos, there are many more that do not. For this reason, Kerberos is often limited to universities and other organizations that have the time and resources to rewrite source code.

A more detailed discussion of Kerberos is beyond the scope of this book, but the following Internet resources provide more information:

- Kerberos FAQ: http://www.nrl.navy.mil/CCS/people/kenh/kerberos-faq.html
- Kerberos Usenet Newsgroup: comp.protocols.kerberos

## Simple Ways to Improve Your Security

Now that you are familiar with many of the security issues with Unix systems, you are ready to learn the following simple techniques for securing your systems:

- Minimizing the number of setuid programs on your system
- Removing world-writable permissions
- Installing TCP wrappers
- Removing unnecessary services from inetd
- Requiring secure passwords
- Monitoring the integrity of your file systems

Each of these techniques—applicable to any Unix operating system, so you should find them useful for every system you administer. The following sections discuss these techniques in detail.

# Minimizing the Number of setuid Programs

setuid programs execute with the permissions of the owner of the executable file, so when setuid programs are owned by root, they execute with root privileges. This gives programs a tremendous amount of power, any bugs or buffer overflows could potentially lead to unintended root access, like a shell or the ability to execute a command as root.

Eliminating unnecessary setuid programs should be one of your first priorities after loading an operating system. Table 13.2 shows the number of setuid root programs in some standard Unix distributions—the numbers are scary.

Table 13.2 Number of setuid Programs in Some Standard Unix Distributions

| Distribution | Setuid Root Programs |
|---|---|
| Red Hat Linux 7.0 | 27 |
| FreeBSD 2.9 | 40 |
| Solaris 8 | 74 |

> You can find setuid root programs by running the following find command as root:
find / -perm -4000 -user root

Most setuid root programs nowadays require that level of privilege to function normally, but more often those commands are run only by an administrator logged in as root. For example, fsdump and fsrestore on Solaris are programs that dump and restore UFS files. Very few sites would actually allow a non-administrator to run these commands—if you are only going to run them as root, why make them setuid and increase your exposure to exploits?

# Find Out Who Is Using setuid Programs

Before removing the setuid bit on any program, make sure that no regular users or non-root cron jobs rely on it; you may end up breaking a critical system process. Check all of the crontabs in /var/spool/cron (Red Hat Linux) and /var/spool/cron/crontabs (Solaris) and preannounce any changes you are making to verify that nobody is using the commands that you are changing.
