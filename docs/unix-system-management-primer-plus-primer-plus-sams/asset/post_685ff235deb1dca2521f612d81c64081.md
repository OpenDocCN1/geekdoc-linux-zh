But hardware is only part of location redundancy; you must have a copy of your data at the other site. The traditional way to accomplish this is by restoring from backup tapes, but this technique presents the following three problems:

- Transporting the tapes to the hot site takes time.
- Restoring the tapes might take hours.
- The restored data is not current—it is probably missing data that changed just a few hours before the restore.

These are probably acceptable risks to most organizations. But for those organizations, who have a lower tolerance for downtime and data loss, such as banks and insurance companies, the following sections will discuss alternative methods of replicating data to alternative sites and how to provide access to the data at those sites.

# Remote Mirroring

Remote mirroring solves the problem of long tape backup, time-consuming restore, and stale backup at the hot site. Remote mirroring typically involves using one storage device to propagate incremental changes in its data in real time (or near real time) to a second storage device in a remote location. Sending only incremental changes over the network ensures that this solution will work with limited bandwidth, such as that of a T1.

Initially, you must seed the secondary device with a full copy of your data, but all subsequent updates will be incremental. Several hardware and software products can provide this functionality:

- SnapMirror from Network Appliance
- Symmetricrix Remote Data Facility (SRDF) from EMC
- HP MirrorDisk/UX
- Oracle Advanced Replication

Remote mirroring can be an expensive alternative to tape restores. But the time you save by not having to perform a restore and the ability to transfer data with no loss of currency may justify the cost.

# Content Distribution

One of the most popular applications on the Internet today is multimedia. News and sports sites use audio and video clips extensively, and those sites must potentially be available to millions of clients at one time. Multimedia transfers, with pictures, movie, and audio clips, can consume megabytes and gigabytes of bandwidth; very companies have the resources to maintain a network capable of handling that much traffic. Content distribution is one solution for providing high availability for these types of services.

Content distribution spreads bandwidth demands over multiple channels by distributing content in multiple physical locations. Optimally, content distribution uses different providers over different Internet backbones, allowing more users to access the content than would be possible over a single network link. This approach also prevents a disaster at one site from denying all access to your content.

With multiple sites, you can use DNS round robin, intelligent DNS, HTTP redirection, and distributed content services to optimize network traffic. The following sections discuss these techniques in more detail.

# DNS Round Robin

In an earlier section of this chapter, you learned about DNS round robin techniques, and content distribution is a wonderful application of these techniques. To put DNS round robin to work in this manner, create a pool of A records using the name you want clients to see, such as when. Then, assign each server in each location A record in the pool. DNS takes care of the rest by globally distributing your services automatically.

# Intelligent DNS

Intelligent DNS is a broad term used to describe name services that are aware of the availability of services behind the IP addresses. Much as a traditional load balancer detects and removes a downed server from a load-balanced pool, intelligent DNS can remove records from a server when a particular server becomes unavailable. Even more advanced servers can return different records, depending on the clients' IP address. You could send requests from the east coast of the United States to Web servers in Philadelphia, for example, and requests from the west coast to servers in San Francisco.

There isn't much hardware or software that supports this kind of service yet, but F5 Labs has already made some advances in this arena. In addition to the BigIP, F5 Labs also offers the 3-DNS controller. The 3-DNS controller is a dedicated DNS server that can detect failures and alter DNS zones appropriately to ensure only available servers are contacted. It also offers other balancing schemes in addition to round robin, like the BigIP.

# Time-to-Live Management

Load balancing using DNS can be a tricky business because of client caching. Each zone has a time to live (TTL) that specifies how long clients should cache records from that before requesting new records from the server. If changes are made on the server side, a large TTL can prevent those changes from being seen for quite some time. If availability is critical, try lowering TTL times for specific zones or records (5 or 10 minutes is reasonable) to reduce the amount of time it takes for your changes to propagate.

# HTTP Redirection

One of the simplest and easiest content distribution mechanisms is HTTP redirection. When a user requests the content from one site, an HTTP redirect is sent back to the client with the URL of a convenient location from which the user can retrieve the content. The user's browser then requests the content from the new location.

All modern Web servers contain redirect functionality; you can even redirect based on client IP using Apache's mod_rewrite. For example, to redirect requests for /docs on one server to the remote URL http://www.example.com/mysite, you could add the following lines to your Apache http.conf file:

```apache
<Directory /docs>
<RewriteEngine on
RewriteCond %{ADDR} ^10.1.*
RewriteRule * http://www.example.com/mysite [R]
</Directory>
```

HTTP redirection isn't a perfect solution because it still relies on a central server that the client must initially contact before redirected to a closer server. But this is not an issue.

# Distributed Services

Some companies have high bandwidth requirements. One example of distributed services is Akamai. If you visit www.akamai, you will see that Akamai has servers on many locations. This allows them to serve content from locations close to the user. If you use these methods, you can provide high availability for your own services.

# Using Redundant Servers

Your names probably includes several addresses that you consider critical to your business. Addresses of Web servers, name servers and MX records, for example, are addresses you live without. Eventually these addresses will need to be changed (due to an upgrade or a relocation, for example), and you can't afford to make a mistake when handling these changes.

DNS relies on caching name servers to the Internet to cache records from authoritative name servers. These records are cached for, at most, the time to live (TTL) for the zone in question; during time the authoritative server is not contacted for cached records. This lack of contact means that a caching name server could potentially ignore all changes for a zone until the TTL expires, which could have disastrous consequences if you make a mistake in a zone with a TTL.
