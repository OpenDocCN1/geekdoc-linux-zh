# Solaris Buffer Overflow Protection

Solaris 2.6 and later are able to detect, log, and prevent attempts to execute code on the stack. This eliminates many but not all, buffer overflows. Just put the following lines in /etc/system, reboot, and watch your system logs:

```
set noexec_user_stack=1
set noexec_user_stack=1
```

When a user runs a program that executes code on the stack, that program is killed and a message like the following is sent to syslog:
myprog[6617] attempt to execute code on stack by uid 1000

# Bad Path Verification

Bad path verification is one of the most common Unix programming errors. For example, here is part of a Web server CGI script written in Perl that displays the contents of any log file in /var/log. depending on your form input:

```
open(FILE, "/var/log/$logname") or die $!;while (defined($line = <FILE)) {
	print $line;
}
close(FILE);
```

You could easily insert "...", the parent directories, and move up the tree to display any file the Web server has permission to read, such as /etc/passwd. The string ../etc/passwd causes the script to move up two directories to read the passwd quite easily.

# IP Spoofing

Network traffic is not immune to exploits; in fact, the entire IP protocol, when not encrypted through IPSec or other mechanisms, is quite vulnerable. IP spoofing is one of the easiest ways to exploit a network; it works by fabricating IP packets on a system with forged source addresses. Hackers typically use this exploit to accomplish one of the following goals:

- Gain access to a system that uses address-based access mechanisms
- Conceal the actual source of an attack
- Launch a distributed denial-of-service attack against the spoofed source address

An address-based access system like rhosts mechanism is not of much use if the source IP address can be forged. Adding to this concern is the unnerving fact that attacks using spoofed source addresses are nearly impossible to trace back to their true source.

Luckily, routers provide a mechanism to avoid both of these situations. By installing a router or firewall in your system, you can deny all inbound packets with a source address of one of your internal networks. After all, if your internal network is 192.168.1.0, you never should receive a packet from the outside with the same address. In fact, you should configure your routers to deny all packets from public networks that have source addresses in the Internet Assigned Numbers Authority private network ranges or your own public addresses. These are summarized in Table 13.1.

# TABLE 13.1 IANA Private Networks

| Network | Address Range |
| --- | --- |
| 10.0.0.0/8 | 10.0.0.0 – 10.255.255.255 |
| 172.16.0.0/12 | 172.16.0.0 – 172.31.255.255 |
| 192.168.0.0/16 | 192.168.0.0 – 192.168.255.255 |

You can configure your router or firewall to allow only outbound packets whose source addresses match your internal networks. This configuration prevents IP spoofing originating from your network, but you must also depend on others to implement simple safeguards, as packets can be spoofed from other networks as well.

This kind of router configuration has become very common, especially in ISPs, relegating the majority of IP spoofing issues to internal networks. However, the Internet in its current incarnation does not allow administrators to easily detect whether an arbitrary packet has been spoofed or not, so there will always be some risk involved when opening up sensitive systems to the Internet.

# Denial-of-Service Attacks

A denial-of-service attack is one of the more malicious things that can happen to an organization. These attacks can bring down a server—or an entire site—to the point of being unusable. Denial-of-service attacks usually consist of a flood of requests for a service that eventually exhausts all available resources on one or more systems.

# SYN Flooding Attack

One of the most prevalent attacks in the late 1990s was the SYN flood attack, to which many organizations without firewalls remain vulnerable. The SYN flood takes advantage of the TCP three-way handshake in Figure 13.1.

# FIGURE 13.1

The TCP three-way handshake sets the stage for SYN flood denial-of-service attacks.

![](img/894492738e879267320b8d6f9a044180_399_1.png)

The three-way handshake involves the following basic steps:

- To initiate a TCP connection, the client sends a SYN packet to a server.
- The server allocates the resources for the connection and sends back an ACK.
- The client then sends a SYN/ACK, a packet with both the SYN and ACK bits set, and the three-way handshake is complete.

# Chapter 13 • IMPLEMENTING SYSTEM SECURITY

The SYN flood attack utilizes a client that sends thousands of SYN packets to a server with a spoofed IP address. As part of the three-way handshake, the server responds to the source address with an ACK, but because the source address is spoofed, the server never gets a SYN/ACK back to complete the connection. leaves resources allocated for the connection in a state of limbo; Until the attempted connections time out, the client can continue flooding the server with thousands of SYNs, eventually consuming all of the network resources on the system, making new connections impossible.
