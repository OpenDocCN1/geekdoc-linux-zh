# Viewing Changes Between Revisions

One of the most powerful features of RCS is its ability to display the differences between any two versions of a file. The rcsdiff command displays output similar to that of the Unix diff command. Specify the two versions with distinct -r flags; lines starting with "<" mark lines in the version specified by the first -r flag, and lines starting with ">" mark those from the version in the second -r flag. Compare versions 1.1 and 1.3 of the httpd.conf file used in previous examples, type the following command:

```bash
bash rcsdiff -r1.1 -r1.3 httpd.conf

diff -r1.1 -r1.3
==================================================================

< Port 80

> Port 8080
```

# Real-World Example: RCS Recovers Critical Files

An administrator was making changes to his DNS configuration when he accidentally deleted the master copies of all the production zones files. After a few deletes, he remembered that the files were all checked into RCS. He listed all the .v files in the RCS directory and checked them out (without the -l flag) one by one until all of the files were back where they belonged. RCS is not a backup tool, but it served as one in this case!

As a Unix system administrator, you are responsible for scheduling all system activities. # Viewing Changes Between Revisions

One of the most powerful features of RCS is its ability to display the differences between any two versions of a file. The rcsdiff command displays output similar to that of the Unix diff command. Specify the two versions with distinct -r flags; lines starting with "<" mark lines in the version specified by the first -r flag, and lines starting with ">" mark those from the version in the second -r flag. Compare versions 1.1 and 1.3 of the httpd.conf file used in previous examples, type the following command:

```bash
bash rcsdiff -r1.1 -r1.3 httpd.conf
==================================================================
RCS file: RCS/httpd.conf,v
retrieving revision 1.1
retrieving revision 1.3
diff -r1.1 -r1.3
==================================================================
237c237
< Port 80

> Port 8080
```

In addition to comparing checked-in versions, you can compare changes you have made in a checked-out file to the most recently checked-in version. This feature enables you to view your changes before officially checking them into the repository. You can display this comparison by omitting the -r flags.

# Real-World Example: RCS Recovers Critical Files

An administrator was making changes to his DNS configuration when he accidentally deleted the master copies of all the production zones files. After a few deletes, he remembered that the files were all checked into RCS. He listed all the .v files in the RCS directory and checked them out (without the -l flag) one by one until all of the files were back where they belonged. RCS is not a backup tool, but it served as one in this case!

# System Activity Schedules

As a Unix system administrator, you are responsible for scheduling all system activities. You are also responsible for ensuring that all users affected by the activity are notified in advance of when the activity will occur. Determining the right time for issuing the notification and the best method for circulating it takes careful thought and planning.

Suppose you need to reboot your company's corporate Web servers to apply patches. You schedule the reboot a week from today to give everyone adequate time to respond and notify clients of the potential outage. A week is more than adequate lead time for a change, but few people will remember this announcement a week later when the outage occurs.

It may not be your responsibility to make sure everyone remembers what you've told them about upcoming activity, but any help you can provide in this area helps to minimize problems resulting from users being unprepared for the activity. One resource that you can offer is a system activity schedule that documents all scheduled maintenance activities. Users can check this schedule at their leisure to find out when you have system activities. If they've lost that email you sent out last week, they will still have fast, easy access to the information.

# INTERNAL COMMUNICATION

Relational naming conventions assign related names to related machines. These naming schemes aren't terribly practical, theyre common in internal networks. At the University of Michigan, the login server pool was named after classic video games, lab workstations were named after types of bread, and mail servers were named after monsters from old movies (Godzilla, Mothra, and so). In addition to their entertainment value, relational names are easy to remember and communicate. It is much easier to say "pacman" than it is to say aa-login2

# Dual Names

Some organizations use DNS tricks to provide relational naming internally while providing the public with more appropriate functional or geographic names.

# Naming Conventions

Even hostnames can be a form of communication, albeit a subtle one. Hostnames should be self-documenting as possible, so you can determine their function.

- Functional naming is useful for devices that have specific purposes—a Web server, for example, web1, web2, and web3, while your name servers are called ns1 and ns2.
- Geographical naming is useful in organizations with multiple locations. Large ISPs often use geographical naming, especially backbone providers. For example, an ISP's core routers in Philadelphia, Pennsylvania and Ann Arbor, Michigan might be called phl-core1 and aa-core1

# Summary

This chapter has introduced several effective mechanisms by which a system administrator can communicate with him or her coworkers. Writing documentation—including procedures, diagrams, and host lists—is the first step in establishing communication. Change management is the next step; this process implements approval, notification, and auditing for all changes on your systems, help stabilize your systems and minimize the number of surprises that result from unannounced changes. Finally, revision control is used by system administrators to track changes to configuration files. The most popular revision control tool is RCS, which is available on all Unix systems.

System administrators are not traditionally known as effective communicators, but it is a required skill that becomes more important as you move up in your organization. Administrators who can properly document their procedures, interact with other departments to communicate changes, and maintain control of their own infrastructure will find themselves in much better standing in their own department as well as in other areas within their organization.
