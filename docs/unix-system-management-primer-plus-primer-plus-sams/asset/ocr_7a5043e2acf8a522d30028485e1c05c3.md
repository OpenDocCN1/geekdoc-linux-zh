+   Variable load tests introduce as much load as possible in a fixed amount of time, and measure performance based on the average number of requests filled in that time frame. This measurement is useful for determining a system's breaking point, or level of stress that causes the system to stop functioning within specifications. For example, if your manager asks you the maximum number of requests your Web server can serve in, you could run a load test for five minutes with a program that does nothing but request pages from your Web server. The program would report back the number of requests it was able to process in those five minutes. Multiplying that by 288 (12 5-minute intervals per hour * 24 hours per day = 288) converts to that requests-per-day.

# Static Versus Dynamic Web Content

When load testing Web servers, you should test requests for both static and dynamic content. Static content is the content on your site that doesn't change, which mostly consists of HTML and image data served from files. Dynamic content can change from request to request, and usually depends on user input; a user might enter an account number into a form, for example, to view the current bank statement. Dynamic requests place more load on a Web server than static because generating dynamic pages consumes server time, CPU cycles, and memory. Limiting a test to static pages makes the site appear to perform better than it would in practice, and limiting the test to dynamic pages makes it appear to perform worse.

Accurate load tests must also simulate human-interaction. Although a computer has the ability to scan Web pages and fill out submit forms of forms per second, for example, humans cannot possibly do this. When a person fills out a form on a Web page, he takes the time to read the instructions on the page, type the information into the form fields, and verify what they typed before clicking Submit button. This could take anyplace from a couple of seconds to a few minutes.

What this means for a Web site is that 5,000 concurrent sessions, do not translate to 5,000 concurrent requests to the Web site. If each user takes 20 seconds to read a page, fill out variant fields, and click the Submit button, that translates into an average of 333 concurrent connections. Logs are the best source of data for this information, since you can see the timestamp on log entry to calculate the time between requests from us. In this example, the user from IP address 192.168.1.66 took 20 seconds to fill out a form and submit it:

```

192.168.1.66 - [13/Apr/2002:18:05:22 -0400] "POST /cgi-bin/parseform HTTP/1.0"
```

# Misleading IP Addresses

Just because two consecutive connections come from the same IP address does not mean that they were made by the same client. Many organizations use network address translation (NAT) to hide their private network behind one public IP address. Without some form of authentication, there is no way to prove two connections from the same client.
