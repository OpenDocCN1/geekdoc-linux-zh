# Never Transmit Root Passwords over a Clear Channel

Even the most carefully chosen root password can be compromised if it is sent over the net-work in the clear. One of the first things a hacker will do after obtaining root privileges on a server is to set up a network sniper to learn usernames and passwords for future access. If you Telnet from a compromised system to a remote system and type the root password while sniffing is running, you have just given away the root password to another machine.

# Hacker Network Damage

A hacker with root privileges can do more than just sniff passwords from the network. He or she can trace processes, read from arbitrary locations in memory, and even “sniff” the console keyboard to learn what passwords are being entered.

# Reserving UID (User Identification) 0 for the root Account Only

The real administrative privilege of the root account does not lie in the name root, it lies in the user identification (UID) of 0 assigned to the account. Some experienced administrators choose to create additional accounts with UIDs of 0 for other people to use, thinking that those UIDs provide a way to audit the use of root privileges. This configuration presents several problems.

The first of these problems is that the administrators are allowing other users to become root, which is quite dangerous for the reasons described in the previous sections. Second, instead of maintaining just one root password, the administrators now have to worry about two passwords, and they may not know who has knowledge of that second password. There are much better ways to delegate and audit root authority, as you will see later in the section, “Delegating Authority.”
