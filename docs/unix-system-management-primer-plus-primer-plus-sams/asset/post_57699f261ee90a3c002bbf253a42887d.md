
# Aliases

The aliases section of sudoers allows you to define named lists of users, hosts, and commands for future reference. There are four types of aliases lists:

- User_Alias Users who can run commands with sudo
- Runas_Alias Users a command can run as
- Host_Alias Hosts on which you can run commands with sudo
- Cmd_Alias Commands that can be run with sudo

An alias is defined as follows:
Alias_Type NAME = item1, item2, ..., itemN

As an example, you can define a list of commands that a backup operator would run with this line:
Cmnd_Alias BACKUP_COMMANDS = /usr/lib/ufs/fsdump, /usr/lib/ufs/ufsfs, /usr/bin/tar

### Allow Users to Run Every Command in a Directory
You can include all of the commands in a directory Cmnd_Alias by appending a slash to the directory name (for example, /usr/local/bin/). This is much easier than typing each individual command into the sudoers file.

# Defaults

The defaults section allows you to alter sudo's default settings in some very flexible ways. sudo contains too many default settings to list here, but some of the more interesting ones are as follows:

- timestamp_timeout Time between password requests
- logfile Path to file to send logs (sudo logs to syslog by default)
- mailto Address to send error and warning messages (these messages are sent to root by default)

Defaults are set like many aliases; for example, the following configuration sets the timestamp to 15 minutes instead of the default 5 minutes:

```
Defaults timestamp_timeout=15
```

# User Specification

The user specification section is where you actually specify what commands a user can run, and as what user person can run the commands. The syntax in this section can be a bit confusing, but it basically looks like this:

```
ID HOST = (USER) COMMANDS
```

A typical entry would be as follows:

jeff server1 = (root) /bin/ls, /bin/kill

This entry allows the user jeff to run the commands ls and kill as root on the system named server. You can also substitute the keyword ALL for usernames, servers, and commands. To allow the user jeff to run these commands on any server, you could use the following configuration:
jeff ALL = (root) /bin/ls, /bin/kill

If it is more convenient for you, you can use Unix groups instead of usernames or user aliases; just prepend a percent sign to the group name. To let the backup group run as root the commands you put into your BACKUP_COMMANDS a few sections after, the following entry would do:
%backup ALL = (root) BACKUP_COMMANDS

# A Full sudo Configuration

A complete sudo file might look something like this:

- User_Alias ADMINS = jeff, mike, chad, steve, george, jay
- User_Alias WEBMASTERS = dave, kevin
- User_Alias DBAS = jason, has
- Runas_Alias ADMIN_ACCOUNTS = root, operator
- Runas_Alias DBA_ACCOUNTS = oracle
- Host_Alias WEBSERVERS = apple, orange, pear
- Host_Alias DATABASES = banana, peach, kiwi
- Cmd_Alias BACKUP = /usr/lib/ufsdump, /usr/lib/ufsrestore, /usr/bin/tar
- Cmd_Alias MAINTENANCE = /sbin/init, /usr/sbin/shutdown, /usr/bin/reboot
- Cmd_Alias WEBPROGS = /usr/local/apache/bin/
- Defaults logfile=/var/log/sudo.log
# Allow users in the Unix group to run anything as any user
%wheel ALL = (ALL)
# Allow admins to perform backup and maintenance tasks on all machines
ADMINS ALL = (ADMIN_ACCOUNTS) BACKUP, MAINTENANCE
# Allow DBA's to perform maintenance tasks on the database servers and
# Run Oracle scripts as oracle user. We can assign multiple permissions to a single user alias by separating them with a colon.
DATABASES = (ADMIN_ACCOUNTS) MAINTENANCE : \
DBAS DATABASES = (DBA_ACCOUNTS) /usr/app/oracle/product/8.1.7/bin/
# Allow webmasters to run Apache maintenance script in /usr/local/apache/bin/
WEBMASTERS WEBSERVERS = (ADMIN_ACCOUNTS) /usr/local/apache/bin/

Due to the ease of host hosts, you can install this single file on multiple servers, easing the administrative burden of maintaining multiple sudo files.

# Solaris 8 Role-Based Access Control

Solaris 8 introduced a relatively new form of access control to the Unix world called role-based access control, or RBAC. RBAC allows users to assume roles that are in turn permitted to perform tasks. Users can use these roles, like switching to another user, and gain the privileges associated with the role.

# UNIX SYSTEM MANAGEMENT PRIMER PLUS

For example, a backup operator can su to a backup role and be allowed to run fsdump as root to back up a file system. Although this example works like a sudo, RBAC support is also built into certain commands, so you can assign specific authorizations to roles, not just certain commands. For instance, you can assign the solaris.jobs.admin authorization to a role, and that role would be able to read and edit anyone's crontab on the system using the crontab command. RBAC integration like this is limited; currently, only the following Solaris applications and commands have built-in RBAC support:

- Solaris Management Console
- at
- atq
- batch
- crontab
- allocate
- deallocate
- list_devices

Until more commands have integrated RBAC support that normally require root privileges, such as shutdown, reboot, useradd, and passwd, RBAC offers little more than the convenience of a built-in sudo.

# Using Unix Group Permissions to Edit Files

Ironically, most tasks that users believe they have root access to perform roles can actually be performed with some clever manipulation of group permissions. Processes that require root privileges need the privileges to read or edit root-owned files. However, if files are not critical to system stability, you can assign a new group to the file and enable group read and write permissions. This group permission allows root as well as the people in that group to read and write to the file.

A good example of where group permissions are useful is the Apache Web server's main configuration file, httpd.conf. The default permissions on this configuration look like this on Hat Linux:

```
-rw-r--r-- 1 root root 33998 Jul 17 2001 httpd.conf
```

The file is readable by everyone, but writable only by root. This setup requires you to give your Webmaster root privileges, possibly through sudo, to edit the file. Unless your Webmaster is the system administrator, who probably don't want to give him or her root privileges. You could change the ownership to the Webmaster or create a new account for him or her to su, but these methods are neither flexible nor efficient.

The most reasonable solution is to create a Unix group that is allowed to edit Web server configurations; you can then change the group and permissions on the file so that anyone in the web group can write to it, as follows:

# Chapter 13 • IMPLEMENTING SYSTEM SECURITY

```
# chgrp web httpd.conf
# chmod g+w web
# ls -l httpd.conf
-rw-rw-r-- 1 root      web 33998 Jul 17 2001 httpd.conf
```

Users need special privileges over membership in the web group to edit this file. This arrangement is much more secure than giving your Webmaster privileges just to edit a file.

The setgid bit plays an important role in group permissions. Normally to run programs with specific group permissions, the setgid causes all new file objects created within a directory to inherit the group ownership of that directory. This type of permission is important for shared directories where many people with different group memberships are making changes to the same files. Instead of giving these people access or forcing them to chgrp files as they are created, you can use the setgid method to ensure that files are owned by the appropriate group.

# Group Ownership on BSD

Directory inheritance of group ownership is the standard behavior on BSD variants of Unix. The setgid method forces this on System V like Solaris and the Red Hat Linux.

Consider the following as an example:

```
drwxwsxr-x 2 jeff      shared 4096 Apr 19 10:22 shared1
drwxrwsxr-x 2 jeff      shared 4096 Apr 19 10:22 shared2
```

Both directories are owned by the user jeff and the group shared, and writable by the group shared. The shared2 directory has its setgid bit set by running chmod+s shared2. Assume these directories are being used to share source code among developers in the shared group. What happens when the user scott, who belongs to the shared group but primary group is staff, creates a file in each of these directories?

```bash
bash groups
staff shared
bash touch shared1/file1
bash touch shared2/file2
bash ls -l shared*
shared1:
total 0
-rw-rw-r-- 1 jeff      staff       0 Apr 19 10:32 file1
shared2:
total 0
-rw-rw-r-- 1 jeff      shared     0 Apr 19 10:33 file2
```

The file created in shared1 has a group of staff, scott's primary group. That behavior is normal on System V, where the primary group of the user who creates a file object becomes the default group of the newly created object. But you don't want that arrangement here, because members of the shared group must be able to edit this file.
