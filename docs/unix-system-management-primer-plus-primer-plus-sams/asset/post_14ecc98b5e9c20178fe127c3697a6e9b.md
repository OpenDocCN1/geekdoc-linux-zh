## Check Usage on Dual-Processor Systems

Don't forget the CPU column in top reports total CPU usage across all of the processes. A process that is consuming 50% of CPU time on a dual-processor machine may not be as dormant as you might think—it actually may be consuming 100% of a single CPU's resources.

On a multi-CPU machine with n processors, a single threaded process can consume more than in the previous example, of most the processes were sleeping—a state in which the processes are blocking, waiting for I/O or a resource to become available. Processes consume no CPU time while they are sleeping. The top output identifies currently executing processes by listing the CPU on which executing is a list of common process states reported by the top command on Solaris:

```
cpu               Process is currently executing on a CPU
run               Process is on the run queue
```

## Use prstat on Solaris

Solaris 8 comes with its own top-like called prstat. This CPU-specific monitor incurs less overhead than top, and can report additional details, such as how many threads exist for a particular process. On a heavily loaded server, you see processes in the run state. This means that the processes are in the run queue waiting for a CPU to become available. ## Using time to Monitor Process CPU Usage

The time command runs a command specified on the command line and reports back the real, user, and system time used by that command (real time is actual clock time). Although not terribly useful for active processes, time can help you test programs before they run to gauge their CPU usage. You can also insert command into startup scripts to automatically profile applications as they start. To profile the CPU usage of calculating the MD5 checksum for the Linux kernel source, you can do the following:

```
$ bash md5sum linux-2.4.17.tar.bz2
0628d142eb6fc31856d7a60df3a082 linux-2.4.17.tar.bz2
```
real 0m.356s
user 0m.280s
sys 0m.070s

Here, you see that most of md5sum's time is spent in user space doing the actual calculations. The 0.07 second in system space is most likely time spent opening, closing, and reading the file from disk.
