Regression tests themselves work very well, but they're valuable only if you keep them to date. As features are added, changed, or removed from a product or system, your testing procedures must reflect these changes. Testing a feature that no longer exists is pointless, and will give you false positives, while failing to test new features leaves your system at risk. The best way to keep everything in synch is to make regression testing a regular part of your change management procedures. See Chapter 14, “Internal Communication,” for more information on change management.

# Detecting Changes

The results from a regression test should match previous results exactly. When results change, you know that some component or function within the system has changed as well.

# Evaluating Regression Test Results

Although regression tests themselves involve complex testing procedures, the results of each test should be summed into one of two simple methods: pass or fail. Using these simple results makes it easy to see exactly what works and what doesn't work, rather than the effort involved in poring over a bunch of complex or vague comments. Notations of failures, definitely should include commenting how each test failed. These comments make it easy for the developers or administrators to find and fix the problems in the test.

# Regression Test Example

The most pervasive example of a regression test on Unix occurs when you compile a new version of Perl. The Perl distribution comes with a suite of tests that verify the functionality of every standard Perl operation that is implemented on your system. One of the tenets of Perl is that it strives to function in the same way on every operating system, and thousands of regression tests verify this before you install it. If any regression tests fails, you can report those failures to the Perl developers who (one hopes) will fix the problem.
