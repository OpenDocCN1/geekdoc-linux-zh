
# Removing World-Writable Permissions (find Command)

World-writable files and directories have the other bit set in their permissions, allowing anyone to write to them. This permission can have the following consequences:

- Users can change the contents of another user's files or even a system configuration file.
- In world-writable directories, users can delete or rename other users' files.
- Users can fill up file systems like / and /var to capacity.
- Users can use world-writable directories as personal file stores that may not count against their quota.

To remove these permissions, you must first locate the directories and files that have them. The following find command locates all world-writable files and directories on a system, ignoring symbolic links:

```
# find / -perm -+w -type l
```

# Don't Change Permissions on /dev Device Files

Most files in /dev need to have world-writable permission. Don't change permissions on these unless you know exactly what you are doing.

Some directories like /tmp and /var/tmp are meant to store files from any user temporarily, as they need to be world writable. However, in a standard world-writable directory, users can delete or rename other users' files, which is an unacceptable situation. The sticky bit (the "t" at the end of the permissions output in ls) alleviates this problem by preventing other users from deleting or renaming files they do not own. Note the "t" in the permissions for /tmp in ls output:

```
drwxrwxrwt  3  root  1024 Apr 20 16:53 /tmp
```

If you need to create a world-writable directory for any reason, activate the sticky bit by typing chmod +t directory.

# Installing TCP Wrappers

The TCP Wrappers package is briefly discussed in Chapter 15, "Interacting with Users." This software allows you to "wrap" almost any network service to provide address-based security. For example, you can choose to allow only your internal network to Telnet to your servers, and deny everyone else. You can also log attempts to access your services and even launch supplementary processes for each connection. TCP Wrappers is installed by default on Linux distributions and OpenBSD; for other operating systems, you can download it from ftp://ftp.cerias.purdue.edu/pub/tools/unix/netutils/tcp_wrappers.

# Implementing TCP Wrappers

You can implement TCP Wrappers in two ways. Programs can support it natively or you can run it as a process through inetd, after which the software spawns the program it is wrapping. SSH and wu-ftpd are two of the few mainstream applications that support TCP Wrappers natively—you do not have to run them out of inetd to enjoy the benefits of TCP Wrappers. For most other applications, such as telnetd and ftppd, you need to run them out of inetd.

Configuring TCP Wrappers in inetd is easy. Each service in inetd's configuration file inetd.conf is represented on one line. If you are interested in the sixth field of each line, which contains the path to the server program, TCP Wrappers replaces this program with its own program called tcpd. tcpd is responsible for reading the TCP Wrappers configuration files, deciding whether the incoming connection to a particular service is allowed, and taking appropriate action.

If you want to wrap the Telnet service, you must change its inetd.conf entry from:

telnet stream tcp nowait /usr/sbin/in.inetd telnet

telnet stream tcp nowait /usr/sbin/tcpd in.telnetd

assuming the path to the tcpd program is /usr/sbin/tcpd. Use the last field to tell tcpd which server program to run if the connection is permitted. For existing services, you can usually leave the current value intact.

After editing inetd.conf, restart inetd by sending a HUP signal to the inetd process (kill -HUP PID), and your configuration will be activated.

Red Hat Linux and some other Linux distributions have moved to xinetd, a radically different version of inetd. Instead of using a single configuration file, xinetd has the ability to break up the configuration into multiple files; Red Hat Linux uses one file for each service. Red Hat's installation of xinetd supports TCP Wrappers by default; all you need to do is discover the names of the services to use in the TCP Wrappers configuration by looking in each xinetd configuration file. The service name is specified after the service keyword. For example, the service configuration looks like this:

```
service telnet {
    disable = no
    = REUSE
    flags == stream
    socket_type = no
    wait == root
    user == root
    server == /usr/sbin/in.telnetd
    log_on_failure += USERID
}
```

# Configuring the hosts.allow and hosts.deny Files

The TCP Wrappers configuration files are /etc/hosts.allow and /etc/hosts.deny. TCP Wrappers uses the following logic to determine whether to allow a connection, stopping at the first match:

- If the connection matches a service/client pair in hosts.allow, access is granted.
- If the connection matches a service/client pair in hosts.deny, access is denied.
- Otherwise, access is granted.

The syntax of hosts.allow and hosts.deny files is simple:
service : client_address_list [ : option ] ...

# Enable the Extended Access Control Language

TCP Wrappers supports an extended version of its access control language used in the hosts.allow and hosts.deny files. This support is enabled by default on many systems, but if you are compiling TCP Wrappers from scratch, you should add -PROCESS_OPTIONS to your compile flags. Some options discussed in this section of the chapter are available only in the extended language.

In this example, the service is the service for which you are controlling access, such as telnet or ftp. The client_address_list is a list of one or more client addresses for which this rule applies. You can also specify various options after this second field to control logging, IND support, banners, and so on. Separate each option with a colon, and in the rest of the configuration.

To allow Telnet connections from 192.168.1.2, make the following entry in hosts.allow:

```
telnetd: 192.168.1.2
```

Note that the service name is the name of the daemon process specified in inetd.conf. You can also specify networks by omitting fields from IP addresses. For example, when denying FTP access from 192.168.2.0, add the following line to hosts.deny:

```
telnetd: 192.168.1.1
```

You can list multiple addresses in a single entry by separating them with a comma.

You can use hostname and domain instead of IP addresses to configure TCP Wrappers. If you use domains, precede them with a dot (\.) so that they do not match a substring of another longer domain name (for example, "example.com" instead of "example.com"),

# Beware of Hostname Spoofing

Anyone with control of reverse DNS (address to name mappings) for their network can spoof a host-name for any of their addresses. For this reason, you should only use domain names in your TCP Wrappers configuration as a last resort.

The ALL keyword is used a wildcard for both services and clients. As an example, you can use ALL to deny all services unless explicitly permitted by placing the line in hosts.deny:

ALL: ALL

Unless a service/client pair is explicitly specified in hosts.allow, TCP Wrappers falls to this catch-all entry in hosts.deny.

You can supplement ALL with the EXCEPT keyword, which allows you to make exclusions from the wildcard. Using this method, you can logically say something like "allow all services except Telnet from 192.168.1.2 and 192.168.1.3," which is much easier than listing every permitted service. The configuration for this example appears as follows in hosts.allow:

ALL EXCEPT telnet: 192.168.1.2

TCP Wrappers drop all denied connections to syslog by default. The logs look like this:
Apr 10 14:45 app inetd[7536]: refused connect from 127.0.0.1

You can specifically specify the syslog and log level to use with the severity option. This technique is useful if you want to isolate the logs for certain services or log-allowed connections. The following configuration from hosts.allow sends logs for denied telnet connections to the daemon.info facility:

telnet: ALL: severity daemon.info

You can then use an application like logferrer (see Chapter 6, "Monitoring Services") to watch for these kinds of logs and notify you of attempts to connect.

# Spawning External Programs from Within TCP Wrappers

The ability to spawn external programs for matching connections is a useful feature of TCP Wrappers. System administrators use this feature to set booby traps or trigger notifications of connections made from a specific location. This feature is especially useful for tracking potential attackers.

The spawn option runs an external command of your choice in a subshell, so you can specify arguments, redirect output, pipe to other commands. If you suspect a user that always Telnets from 192.168.0.2 has been trying to hack into your system, you could set up the following configuration to send an email when a user connects from that address:
telnet: 192.168.0.2: spawn (echo "They're back!" | mail root) &

Now you will know exactly when a connection is made from that address and you can monitor the user's activities as appropriate.

# Removing Unnecessary Services for inetd

inetd is the Unix "super server," listening for requests for various network services and launching the appropriate programs in response. Unfortunately, Unix distributions activate every service in inetd by default. Most of these services are unnecessary and are even vulnerable to various remote exploits.
