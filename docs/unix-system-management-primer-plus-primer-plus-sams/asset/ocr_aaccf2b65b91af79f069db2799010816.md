# Service Checking Issues with DNS

The problem with DNS-based round robin load balancing is service checking. A name server could easily send a request to a server that is unresponsive, conveying an outage to a fraction of the clients; a system administrator has to manually remove unresponsive server addresses from a pool of R records to the pool to full availability. This inconvenience is a small price to pay for a free and universally supported load-balancing scheme.

# Real-World Example: Load-Balancing Login Servers

A large Midwestern university deployed a 16-server Unix login service to its 60,000 students, staff, and faculty. At peak times, 3,000 users logged into the server to run applications, compile programs, read news, or chat on IRC. Each server was a 17MHz Sun Enterprise 1 with enough capacity to handle 200 users per machine at peak times. The system administrators deployed a DNS round load-balancing scheme with 16 A records under the name "login." This solution worked very well balancing the load of incoming users among the 16 machines but suffered when a server went down. One of every 16 connections hit the dead server, requiring the user to try again. Administrators had to manually remove the A record of the downed server from the pool to prevent users from connecting to it; when the server became available again, the administrators added its A record back to the pool.
