# Data Redundancy Using Snapshots

Many modern Unix file systems and device drivers support the use of snapshots to provide data redundancy. A snapshot is a point-in-time read-only copy of a file system located on the same disks as the file system. A snapshot is not, however, a real copy of the original file system. If that were the case, using snapshots would consume twice much disk space as a split mirror configuration. snapshots copy the pointers to data blocks in a file system and copies the original file system data to the snapshot only if it changes on the original file system—this is called a copy-on-write mechanism. If you change a block of data in the original file system, only a block of data is consumed in snapshot.

Data that never changes is never duplicated by snapshots; the only extra storage snapshots require is the data block pointers and changed data. The fact that very little data copying takes place up front means that snapshots can be created almost instantaneously—you can't get a faster online backup.

These reduced storage requirements allow the creation of multiple snapshots for the same file system. You can take a snapshot every night, every hour, whatever works for you, and keep all of that data. The only limiting factor is the amount of data that changes in the original file system

The following Unix file systems support snapshots:

+   * UFS (Solaris 8 and later)
* ReiserFS (Linux)
* Veritas VxFS (Solaris, HP-UX, Linux)
* IBM's JFS (AIX, Linux)
* SGI's XFS (IRIX, Linux)

These popular volume managers provide block devices that support snapshots of any type of data, and are not file system specific:

+   * Linux LVM
* Veritas Volume Manager (Solaris, HP-UX)

These file servers and disk arrays can also take snapshots:

+   * Network Appliance Filers running Data ONTAP
* HP SureStore Array
