# Ensuring Hardware Has Adequate Capacity

When you upgrade hardware, the new hardware should have the capacity to perform all of the tasks running on the existing hardware. It means it should have enough CPU, memory, disk space, and I/O and network bandwidth to the job. Usually, upgraded hardware provides this capacity by its very nature—if hardware upgrade doesn't improve the system's capacity or performance in some way, shape, or form, it isn't much of an upgrade.

# Moore's Law Influences the Price of Upgrades

Price also plays a role. Moore's law (proposed by Gordon Moore, cofounder of Intel Corporation) predicts that processor speeds double every 18 months, and while some would argue that we are approaching the limits of what is possible using current technologies, it holds true through the time of the writing. Combining Moore's law with ever-failing memory and disk prices (you can now buy a DIMM for pennies per megabyte), the price-to-performance ratio is constantly decreasing in the consumer's favor. This means that for the same amount of money you spent on a server yesterday, you are likely to get a more powerful server for the same amount of money next year.

Not all upgrades increase capacity by adding higher-capacity hardware. Some upgrades divide the existing system into smaller, lower-capacity clusters to increase parallelism and resource contention. For example, a large-CPU database server hosting 24 Oracle databases, and reaching its capacity limits, might be replaced with smaller servers; each of these smaller servers might offer better performance hosting three or four databases than the old server was capable of hosting all 24 databases. This configuration eliminates a single point of failure, if the original database server failed, all 24 databases would become unavailable. In the new scenario, if one failed, only three or four databases would be affected.

# Real-World Example: Spreading the Wealth

A large ISP secured a Sun Enterprise 6000 (E6000) server to host its customer and billing databases in early 1999. After several upgrades, the server had 10GB of RAM, 16 processors, and over 250GB of local disk space. By November 1999, that server was running over 20 instances of Oracle, and memory and CPU usage skyrocketed with each instance added. Because there was only one server, the E6000 also represented a single point of failure, if the server went down, all customer billing and registration services were no longer an option. The IT staff decided to split the workload into six separate Enterprise 420R servers, each with 450MHz processors and 4GB of RAM, with the data stored on a storage area network (SAN). This configuration immediately increased the performance of the billing and registration services, both explicitly (more RAM and CPU), and implicitly (fewer databases per CPU, and the physical separation of databases reduced resource contention). Increasing capacity was as easy as installing an additional E420R or adding space to the SAN.
