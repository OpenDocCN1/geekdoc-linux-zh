# Chapter 4 • TESTING SYSTEMS

On a smaller scale, the results of configuration changes or simple hardware installations should also be tested to make sure they produce the intended results. If you install a new 256MB RAM module in a server, verify the amount of memory reported by the system when it is rebooted; do not assume the memory is there.

You can also consider testing that makes no contribution to the goals of your system. Although FTP servers come standard with every Unix distribution, you do not need to test the functionality of your FTP server if you never plan on using it. In fact, you may want to disable the FTP server altogether, to prevent it from being used.

# Real-World Example: Missing Memory

To improve an organization's system, administrators upgraded several servers from 512MB to 1GB by inserting additional memory modules. The servers booted normally after the upgrade and all servers were started. Shortly afterwards, users noticed that the servers were excruciating slowly and modified system administrators. Administrators eventually found that the servers reported only 256MB of RAM—instead of doubling the memory, the administrators' efforts seemed to have cut the memory in half. This memory shortage occurred because the new RAM was incompatible with the motherboard and therefore prevented the system from properly recognizing some of the existing modules. If administrators verified the available RAM immediately after installing the new modules, they would have noticed the problem instead of waiting for users to complain.

# Conducting Unit Tests

With many system components and functions to test, it is often difficult to figure out where to begin testing. The most efficient way to go about unit testing is to test the results of each task along the way as you install, configure, and deploy your server. Certain tasks might have dependencies on others and discovering problems early on will minimize the amount of backtracking you have to do when new problems arise. A system administrator's job is mostly task oriented, so there's no rulebook for unit testing. In general, however, the process involves the following four steps:

+   1. Document the goals and consequences of a test.
2. Define testing parameters and procedures.
3. Perform the test.
4. Verify the results of the task and remedy any side effects.

In Step 1, you should document the ultimate goal of a test and any side effects that may occur in the process. Testing cannot always be done in closed environments—it is possible that a test can adversely affect other processes or data, and you should note those potential problems here and how to fix them after the test is performed.

Step 2 defines how you will perform the test, including any commands you will use and what the expected results are.
