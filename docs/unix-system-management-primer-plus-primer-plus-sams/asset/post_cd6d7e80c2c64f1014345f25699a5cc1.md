## Writing System Documentation

Few (if any) system administrators would rather spend time documenting their systems than actually designing, deploying, and maintaining those systems. Nevertheless, documentation is a necessity. System administrators are human, and they easily forget details of procedures they last implemented months ago. System administrators aren't the only people using their system; other administrators, users, or even auditing firms may, at some point, need to view a system's architecture and procedures.

Every IT organization develops its own specifications for system documentation, but most system administrators document the following three types of information:

- Network maps draw the network architecture and are used by administrators to locate, identify, and trace paths between devices within the network.
- Host functionality data documents the services running on a network and the systems that host and use those services; this documentation is useful for planning system maintenance or tracking the score of failures.
- Procedural documentation records the "how to" of processes used to maintain and run each system and service, so both system administrators and users have clear step-by-step instructions for performing critical tasks.

The sections that follow describe these types of documentation in more detail.

## Targeting Documentation to Audience Expertise and Needs

As you saw in the preceding section, writing useful system documentation involves more than simply jotting down your instructions for using the system. System documentation contains different types of information, and it's also used by people with varying levels of expertise. These people use system documentation for different reasons, as well, so system documentation must be written to address the technical proficiency and needs of its target audience. In general, system administrators must craft documentation to be useful to the three types of users:

- Other system administrators or technical staff, who use system documentation for maintaining the devices and services for which they are responsible. Communicating with technical staff is easy for system administrators, because this audience understands technical jargon and is familiar with most processes.
- Nontechnical staff often use system documentation as a reference for the technical side of their organization. They also turn to documentation for step-by-step procedures for technical tasks necessary in the course of their jobs. Writing for nontechnical staff can be more difficult, because you cannot assume that they understand jargon and processes. This documentation must clearly explain processes in easy-to-follow steps and simple terms. These readers understand terms and acronyms specific to your organization, however including code names for products and server names, enabling them to use these terms freely in this type of documentation.
- Clients and customers need system documentation if they have access to their technology (for example, if they use mail servers to store and read their email), and they use it primarily for step-by-step procedures and contact information. You must be carefully to write clear, jargon-free documentation for these readers. Assume that any or all of these readers have no technical background and are unfamiliar with any of your company's internal practices and terminology. This documentation must be well-written, easy to use, and complete in its instructions and information.

## Use Caution with Sensitive Documentation

Many pieces of technical documentation, especially network diagrams and internal contact information, might be proprietary information and highly confidential to your organization. Consult your management or your legal department before giving this information to outside parties. They may ask outside parties to sign a nondisclosure agreement, which legally prohibits them from disclosing the sensitive information to anyone else.

For a clear picture of how documentation is crafted to address a specific audience, you can compare different types of system documentation. Here is an example of some casually written documentation for technical staff:

1. SSH to apple.
2. Watch the few lines of the syslog messages for errors.

This may seem like a very simple procedure to you, and the technical staff who use this documentation may have no problem understanding its instructions. For someone who does not know what SSH is, however, these two simple steps would be quite confusing. The following procedural documentation would be more appropriate for a nontechnical audience:

1. Double-click on the SSH icon on your desktop.
2. Enter apple in the hostname field and click OK.
3. Enter your username and then password. These are the same ones you use to log in to your computer.
4. When you use bash, tail -f /var/log/messages and press Enter. This action displays the last few lines of the log file and any other logs that arrive from now on. Notify system administrators if you see any lines starting with ERROR.

## Document Formatting Conventions

A nontechnical audience may not be able to identify the parts of your procedures unless you include a list to explain the font or format. Use a fixed-width font like Courier for commands and output, the characters will align as they would on the readers' screens.

## Network Diagrams

Network diagrams are maps showing how every device on the network fits together. Without them, figuring out one particular machine on the network would require examining the network interfaces on that machine, tracing cables back to a switch, mapping that switch port back to a VLAN, and so. With a diagram, system administrators and technicians can quickly see the path two machines must take to communicate with each other, including firewalls, routers, and switches they must traverse; this information is invaluable when designing a network problem.

System administrators maintain two basic types of network diagrams: physical and logical. A physical diagram shows the actual physical connections between each device on your network. Physical diagrams also provide information about other physical aspects of each device, including network interfaces, switch ports, cable types, cable identifiers (if you label your cables), and the make and model of each device.

Physical network diagrams are useful for the following purposes:

- Identifying to which port a device is connected
- Surmising the physical location of a device
- Identifying the make and model of a device
- Planning a build-out of a new or existing network

A logical network diagram shows the layout of devices relative to its network, and includes few, if any, physical details about a device.

In practice, logical diagrams tend to be more useful than physical diagrams, because after you have installed a device on your system, all you care about is its IP address, the network on it resides, and its access to other networks. You can manage all of those issues through software, without physical intervention.

Logical diagrams are useful for the following purposes:

- Identifying on which network(s) a device resides
- Identifying all devices on a particular network
