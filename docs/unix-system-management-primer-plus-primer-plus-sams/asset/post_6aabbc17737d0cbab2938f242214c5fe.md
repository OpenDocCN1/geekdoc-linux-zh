
For example, if you mistype the new IP address of a recently moved Web server in a zone with three-hour TTL, you fix the error five minutes later, caching name servers that asked for the address in those five minutes will hang onto that bad address for three hours. Even more frustrating is the fact that you have little control over the behavior of such caching servers.

The only control you have is the TTL of the zone in question. TTLs are between one and twenty-four hours, which is a long time to wait for changes to propagate. You could permanently set it to something small like five minutes, but may significantly increase traffic and load on your authoritative name servers and waste bandwidth.

The best solution in this case is to temporarily reduce the TTL to five minutes for the duration of your change and testing procedures. That way, you can back out any changes in a couple of minutes rather than a couple of hours. When testing, you can reset the TTL to your normal value.

The key to this is remembering that the TTL is part of the zone itself, so too will be cached; Therefore, any changes you make to the TTL must be at least one TTL length ahead of time. If the TTL is three hours, you should change its value at least three hours before you make your other changes so the new value is guaranteed to be seen by all caching servers. The TTL is stored in a zone's statement of authority (SOA); BIND 8.2 and higher require you to set a minimum TTL in the SOA and the $TTL directive which specifies the default TTL for all records, as shown in Listing 10.2.

## Using Redundant Mail Hubs

SMTP is another essential service, as it is responsible for sending, routing, and receiving email across the Internet. While mail agents like sendmail will queue outgoing messages on a mail hub for later delivery when destinations are unavailable, this queue is not infinite in size; mail will eventually be lost if the queued messages take up all available space on the mail hub.

An MX record, or mail exchange, is a DNS resource record that specifies where mail for a particular domain should be routed. Multiple MX records can be specified for one domain with varying priority levels to provide a simple form of redundancy. MX records with higher priority are preferred over ones with lower priorities. Lower priority MX records will be used only if the higher priority records are unavailable. Many administrators choose to use their ISP's hub as a lower priority MX record so mail has some place to go if their mail hub or network goes down.

## Prioritizing MX Records

MX records with a lower number in the priority field are preferred over MX records with a higher number. This may be the opposite of what you would expect.

If MX records have the same priority, RFC 1123 requires one example to be chosen at random by a mail transfer agent because sendmail. This can be more efficient than using multiple A records for a DNS root record when one server in a pool of mail goes down, only the MX record for server is skipped, not the single MX record representing the entire pool of mail hubs, which are still available. ## Gauging CPU Performance and Capacity

The CPU is the heart of any system and as such plays a central role in the system's overall performance. Many aspects of a system can affect its processors, so CPU tuning and capacity planning can be a complex task. The next sections detail the nature of CPU usage and how to use tools to diagnose CPU problems and plan for the future.

## Interpreting Load Averages

Many users and administrators associate a high load average with overworked CPUs, yet they don't know what a load average really is. A load average is number of runnable processes active on the system over a set of time. Runnable processes currently running and those on the run queue. Run queues are kernel structures that hold pointers to processes that are able to run but are not currently running on any CPU.

## Not All Processes Are Included in a Load Average

The run queue used to calculate a load average does not include processes that are blocking (usually waiting for I/O) or swapped out to disk. The existence of these processes is not related to a CPU's performance.

The uptime command is universal to all Unix flavors and can be used to examine the load averages for a machine, as follows:

```
$$ sh sh uptime
7:02pm up 143 day(s), 13:44, 0 users, load average: 1.87, 0.92, 0.81
```

## An Alternate Way to Report Load Averages

Load averages are also reported in the first line of the output of the w command.

The three averages reported in the example represent the load over a period of 1, 5, and 15 minutes respectively (when read from left to right). The 1-minute load average is representative of the short-term processing load, while the 15-minute average is a long-term load measurement. During bursts of CPU activity, high 1-minute load averages alongside low 15-minute averages can occur.

A load average is significant in terms of the number of processors on a machine. In general, a load average that is less than the number of installed processors means that a system has adequate processor power. A four-processor machine with a load average of 3.5 is not overloaded—it's fully utilizing its resources.
