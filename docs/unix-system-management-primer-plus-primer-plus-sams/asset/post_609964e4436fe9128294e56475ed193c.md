## Host Functionality

Servers today are so powerful and have so many resources available to them that it makes sense for some of them to be dedicated to more than just one task. Dedicating a dual 900MHz Sun Enterprise 280R as a mail server for 25 people, for example, isn't a very efficient use of resources. You might find underutilizing a server in your system, simply because the server was available at the time you set up the network. In time, you can choose to run a few more services on that machine that has extra resources available. A gradual increase in server workload is a common occurrence in many IT organizations. As you change server load, however, you must properly document what services you've added to each server. Otherwise, you can forget what service is running on each server—a sure cause of headaches during a crash or maintenance event that requires quickly determining which services are down.

Host functionality documentation, which many call a functionality matrix, documents the services running on each system on a network. Host functionality documentation also indicates systems use services. No standard format dictates how this data should appear, but it should be easy to read, to search through, and (most importantly) kept up to date. You can put a matrix into a spreadsheet like the one shown in Figure 14.3. A quick glance at this document tells you what services are running on each machine, and what services would be affected if any machine were to fail.

Maintaining your host functionality documentation in a relational database such as Oracle or MySQL provides even more convenience. You can query the database for exactly the information you want to see about your services, and even cross-reference your query with other data in the database.

If you included the IP addresses of each server in the functionality matrix, for example, could you query for a list of services that would be affected if the 172.16.5.0/24 were unreachable; the database would provide an immediate response. Querying for functional dependencies saves a significant amount of time when you are planning for maintenance or reviewing system vulnerabilities. One such query might look like this:

```
SQL> select service from functionality_matrix where network = 172.16.5.0;
```

## Procedural Documentation

The bulk of documentation that a system administrator produces is procedural in nature; procedural documentation describes the step-by-step processes for performing daily operational tasks. Some examples of this kind of documentation include instructions for the following:

- Restoring a file from backup tapes
- Loading Solaris 8 onto a new server
- Making a change in DNS
- Adding a new user

Procedural documentation is very technical in nature, but it must be simple, accurate, and complete even that the most junior system administrator can execute each step flawlessly. Procedural documentation is used by people who are unfamiliar with (or not remember) the individual tasks and machines for which you are responsible; if the documentation is inadequate, these individuals won't be able to manage system administration tasks in your absence. For this reason, badly written procedural documentation can be responsible for triggering outages.

Following is an example of a poorly written procedure for updating a DNS zone:

- Log in to the master DNS server.
- Check out the appropriate zone file.
- Make changes as appropriate and increment the serial number.
- Check in the zone file.
- As root, run make install.
- Check the log file to make sure nothing goes wrong.

This procedure doesn't contain any specific information; it lists what is to be done, but it doesn't explain how to do any of the listed steps. For example, which server is the master DNS server? Where do the zone files live? Where is the log file? Even a senior administrator would have trouble updating a DNS zone using this documentation. Here's a more useful list of steps for this procedure:

- Log in to apple with your own account.
- Change directories to /usr/local/dns.
- Check out the appropriate zone file from RCS using the command -l zone-file.
- Edit the zone file, make the appropriate changes, and remember to increment the serial number in the SOA at the top of the file.
- Check the zone file back into RCS using the command ci -u zone-file.
- Become root using su.
- Verify that your current directory is /usr/local/dns and run make install.
- Run tail -f /var/log/messages to verify that no errors occurred after the zone was reloaded.

## Change Management

As the system administrator of a Unix network system, you are responsible for deciding what changes to make to that system to keep it up to date and functioning at peak efficiency. You are also responsible for scheduling system changes and for communicating information about upcoming changes to the system's users. All of these responsibilities fall under the general category of change management. Change encompasses the approval, documentation, and auditing of all your systems. Even the slightest change to a running system can have a huge impact on a production service. Although you, as the system administrator, may think a change you are making is urgently necessary, others using the system might not think so. Change management ensures that ample communication passes between the people making and those affected by the changes. This communication can take the form of a simple announcement from IT staff or a complex approval chain with management sign-off that could take days.

### Change Approval

An approval process prevents any change from occurring before it is thoroughly analyzed by peers, clients, and management, and given the necessary approval. System administrators at smaller organizations may be able to get away with a casual email asking for any objections to a change. Here's an example:

From: Mike Admin
To: IT Department
Subject: new web server

Hey guys,

I'll be putting new web server into production tomorrow at 5 AM. I don't expect to have any downtime whatsoever. If anyone has any concerns, please let me know by end of business day.

However, larger organizations, especially those with auditing requirements, need more rigid change controls. In those situations, change requests go through a strict approval process in which every department might be affected by the change is required to sign off on the proposal. This type of approval process can be long and arduous, especially if conducted through phone calls and email.

Change approval tools help manage the process. Remedy, described in Chapter 5 as a trouble ticket management system, provides change management functionality using an interface similar to the one it uses for trouble ticket management. For change management, instead of escalating trouble tickets to support staff, Remedy escalates change tickets through the approval chain until the status is marked as approved. At that point, the person who issued the change proposal is notified that he or she can proceed with the change.
