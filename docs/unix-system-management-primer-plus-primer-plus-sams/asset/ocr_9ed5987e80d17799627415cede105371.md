A server's load isn't always linked to the number of incoming connections it's receiving. The nature of the server load can determine which load-balancing scheme will work best for that system. For example, a round robin scheme works well for HTTP if all requests require equal processing power. If requests demand dynamic pages with CGI scripts or Java servants, the picture changes completely. Although a server uses minimal resources to serve one static HTML page, a page dynamically generated by running a CGI script might require significant processing power, depending on the application.

A round robin scheme won't work to balance the load in this situation, you can't predict the timing of any particular connection. Least-connections load-balancing schemes won't work here, because the number of connections has no direct relationship to the load on any particular machine. The load-balancing scheme for this particular service must gauge server load, and then distribute new requests to the servers with the least amount of load. To accomplish this, the scheme could query the machines during their CPU, memory usage, disk activity, and so on, but that process would be intensive. Further, query results that indicate stress on a Linux server might not have the same meaning when applied to a server running another operating system, or so Solaris.

Using a response time load-balancing scheme is the best approach in these situations. By measuring response time, the load-balancing hardware and software can route new connections to servers that are working under the lowest load at any given time. Response time can be measured in two ways, as follows:

+   - An active measurement occurs when the load balancer periodically makes a request from each server and measures the time it takes to receive a valid response. Active measurement takes some processing time from the load balancer; and, because the load balancer typically makes the same request each time, this measurement isn't always accurate.
- The load balancer passively measures response time by observing the communication between the various clients and the servers. This method requires less processing time and provides measurements for a variety of request types. Passive measurement depends on client requests, however, the load balancer can't make accurate balancing decisions until it has been able to measure the response times for several requests.

> Find the Cause of Slow Response Times
Don't always assume that response time is due to poor performance. Your service could be blocking while waiting for a response from another service. For example, sendmail may hang for several seconds during an SMTP connection if DNS is unavailable for it perform name resolution.

# Weighted

Load balancers sometimes have to work with a nonhomogeneous pool of servers; some servers might have one CPU, some might have two, some might have 1GB of RAM, and some might have 2GB. Machines with different hardware perform differently, so the load balancer can't consider them equal players when deciding where to send the next network request.
