# Chapter 6 • MONITORING SERVICES

One of the most useful implementation of these variables is to have syslog-ng put log into automatically created directories named after the current year and month. Using these directories is like having an automatic log archiving system; here's how to do it:

```
destination mail { file("/var/log/syslog-ng/$YEAR$MONTH/mail") group(wheel)
perm(0640); };
destination cron { file("/var/log/syslog-ng/$YEAR$MONTH/cron") group(wheel)
perm(0640); };
destination auth { file("/var/log/syslog-ng/$YEAR$MONTH/auth") group(wheel)
perm(0640); };
destination kernel { file("/var/log/syslog-ng/$YEAR$MONTH/kern") group(wheel)
perm(0640); };
destination daemon { file("/var/log/syslog-ng/$YEAR$MONTH/daemon") group(wheel)
perm(0640); };
destination firewall { file("/var/log/syslog-ng/$YEAR$MONTH/firewall") group(wheel)
perm(0640); };
```

# Log Paths

Log paths begin with the entire configuration, linking sources, filters, and destinations into one cohesive logging system. Each log path specifies from which syslog-ng should log messages, filters to categorize the messages, and destinations to specify what action to take for each filtered message. Writing these is relatively simple, as follows:

```
log { source(src); filter(f_mail); destination(mail); }
log { source(src); filter(f_cron); destination(cron); };
log { source(src); filter(f_firewall); destination(firewall); };
log { source(src); filter(f_auth); destination(auth); };
log { source(src); filter(f_kern); destination(kern); };
log { source(src); filter(f_daemon); destination(daemon); };
```

# Appropriate Use of syslog-ng

syslog-ng is easy, but keep in mind that although it can be installed on all of your machines, it is most useful on a central log server. The stock syslog provided with your operating systems should be redirect all log messages to your new syslog-ng log server (see previous section). The configuration to do this on Solaris is:

```
# send all syslogs to syslog server
*.emerg;*.alert;*.crit;*.err;*.warning;*.info @syslog-server
```

# Application Logs

Not all utilities and applications use syslog as a logging mechanism. In fact, the client-server aspect of syslog adds a lot of overhead to a system that produces massive amounts of logs, such as a Web server taking 500 hits per minute. In such a situation, it makes sense to store the logs on the local file system. Application logs grow out of control if not monitored properly. On a system with many logs, placing the logs under one common subdirectories, such as /var/log, lets you know exactly where all of the log files are located. Using a common subdirectory also simplifies log archiving. You learn more about log management in next section of this chapter.
