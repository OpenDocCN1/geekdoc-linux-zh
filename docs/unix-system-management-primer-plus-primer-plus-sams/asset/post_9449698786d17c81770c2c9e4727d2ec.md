The scan rate specifies how many pages per second the Solaris pagedaemon is scanning for page-out eligibility. On Solaris 7 and earlier, if this number remains higher than 200 for extended period of time, the system needs more memory. However, on Solaris 8 the scan rate should always be zero in all but the direct of memory conditions; Solaris 8 introduces the file system free, a list of free memory dedicated to file caching. Heavy file system activity will never force a process out of memory on Solaris 8; if the scan rate is above zero, it means other processes are forcing page outs, and this is a definite indicator of a memory shortage.

# Tools to Monitor Process Memory Usage

After you have determined the memory usage of the overall system, you can examine the per-process utilization. This will help you identify the individual applications or commands that are consuming the memory on a system. There are many tools to help us gather this information, from which we have seen before: top, ps, and pmap.

# Using top to Monitor Process Memory Usage

top is very good at reporting memory usage for individual processes as well as total memory utilization. In the following example, top is run on an Oracle database server and shows the top 15 processes sorted by memory size (RES). It also shows the real memory (RAM) and swap utilization.

Per-process memory consumption is reported by SIZE and RES columns. SIZE is the total size of the process, including the text (code), data (allocated data), and stack. RES is the resident size of the process, or how much physical RAM is being used by the process (resident size). You may have noticed that the total size of the processes listed in the top exceeds the total physical memory on the system, approaching the total size of swap. These numbers are displayed the fact that the system reports 712MB of free memory and 8GB of free swap. An efficient virtual memory subsystem is important as it allows some parts of a process to be shared with other processes, such as executable code and shared libraries. Most of the reported memory usage by each process is actually shared among all of them.

# Using ps to Monitor Process Usage

Although not overly verbose, ps can provide some simple size usage statistics for a process. On a System V platform (Solaris) -l can show the size of a process in pages in the SZ field, as follows:

```bash
bash$ -lp 382
FS UID PPID C PRI NI SZ WCHAN TTY TIME CMD
8 S 0 382 1 40 20 423 ?? 0:05 http
```

The pages command is used to determine the size on Solaris, in which this case is 8KB. The total size of the http process is 423 × 8KB = 3384KB. The BSD version of ps provides some more useful information akin to the output of top: ps will display the resident size as well as the total size of process, just like top. On Solaris, the BSD version of ps is located at /usr/uc/ps; on Linux, ps will behave with BSD semantics if you use BSD-style arguments like awk. Note how the size SZ in the following calculation:

```
jhorwitz@nause[build|$] /usr/uc/ps ps 382
USER PID %CPU %MEM SZ RSS TT S START TIME COMMAND
root 382.0 0 4.3 172 S Aug 08 0:04 /usr/local/apache/
```

# Using pmap to Monitor Memory Usage
