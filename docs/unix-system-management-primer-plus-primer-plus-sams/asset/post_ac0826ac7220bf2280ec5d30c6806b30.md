
# Note Change Implementation Time

The time a change is made might be very different from the time it takes effect. For example, if you install a new version of Perl in your master software repository at 10:00 a.m., but it is not distributed to your systems until some automated process runs at 2:00 a.m. the next morning, your systems will not see the change you made until 2:00 a.m. Make sure your change log notes both the time you made the change and the time it will be implemented in the system.

# Configuration Management with Revision Control Tools

Unix has included revision control tools for decades now, and programmers have traditionally used these tools to manage changes to source code. System administrators quickly caught on to the potential of revision control tools, however, and began to use them for managing changes to the operating system or configuration files. Revision control, also called "version control", performs the following three functions for system administrators working with configuration files:

- * Versioning distinguishes and organizes multiple versions of the same file on the system. Each committed file change results in a new version, and file versioning ensures that you can find and view all versions of it. Versioning enables system administrators to revert to a previous configuration or see what has changed between versions.
- Auditing is another feature of version control. When a change is committed to a file, the revision control tool makes a record of the transaction that typically includes the date and the identification of the user who made the change. Most tools also request a log entry, so the administrator can document the reasons for the configuration file changes.
- Access control ensures that only one person can make changes to a configuration file at any time. That avoids the need for merging two or more sets of potentially conflicting versions of configuration file changes. Revision management tools use application-level file locking, a primitive form of access control that requires users to "check out" a file to edit. When the file is checked out, other users are locked out from using it. The user then must "check in" the change file, which commits the changed version to the repository and unlocks it for use by others.

# Log Entries Should Ask, "Why?"

Most revision control tools can detect changes made to files in their repositories. Log entries record the reasons for changes to the configuration files, rather than detailing the changes themselves. When you write log entries, therefore, remember to describe why you made the change, instead of describing the change you made to the configuration file.

# Checking In Files

Checking a file into RCS commits your changes to the RCS repository and creates a new version of the file. Checking in a file is also the first action you must perform to create an RCS repository. A repository can be a single file under RCS control, or it can be a directory of different files. RCS keeps master copies of each file in the repository, including all versioning information, with a suffix of .v. These files should never be edited directly. For example, checking in the file resolv.conf would result in the file resolv.conf, which would contain all versioning information for resolv.conf.

# Create an RCS Directory for Version Masters

To keep the .v files separate from working files, create a directory called RCS in your current directory. RCS will store the .v files for your working directory in the RCS directory. With the versioning files stored in a separate directory, you're unlikely to accidentally edit or remove them.

# Never Edit .v Files!

Never edit a file ending in .v. You could permanently corrupt the versioning information in the checked-in file.

Checking a file in RCS using the -u flag unlocks the file in the repository after checking it in, so that others can check out the file for editing. When you check in a file for the first time, ci asks for a description of the file, as follows:

done

To keep the .v files separate from working files, create a directory called RCS in your current directory. RCS will store the .v files for your working directory in the RCS directory. With the versioning files stored in a separate directory, you're unlikely to accidentally edit or remove them.

# Never Edit .v Files!

Never edit a file ending in .v. You could permanently corrupt the versioning information in the checked-in file.

Checking a file in RCS using the -u flag unlocks the file in the repository after checking it in, so that others can check out the file for editing. When you check in a file for the first time, ci asks for a description of the file, as follows:

```bash
bash$ ls -l
total 40
drwx-xr-x 2 jeff jeff 4096 Apr 6 12:41 RCS
-rw-r--r-- 1 jeff jeff 33988 Apr 6 12:39 httpd.conf
bash$ ci -u httpd.conf
RCS/httpd.conf,v <-- httpd.conf
enter description, terminated with single '.' or end file:
```

# Checking Out Files

Check out files in RCS using the co command. The -1 flag locks the file from subsequent check-outs until you check back into the repository with your changes. When you check out a file from an RCS repository in your current directory, an editable version of the file appears in your current directory, as follows:

```bash
bash$ co - httpd.conf
RCS/httpd.conf,v -> httpd.conf
revision 1.2 (locked)
done
```

What happens if someone else tries to check out the file for editing while you have checked it out? Since you used the -1 flag, RCS doesn't allow that person to check out the file.

```bash
bash$ co -1 httpd.conf
RCS/httpd.conf,v -> httpd.conf
revision 1.2 (locked)
done
```

# Check In Files Immediately

Get into the habit of checking in files after you make changes. Checking in a file unlocks it, giving others a chance to make changes.

However, other users can still check out the file while you are editing the new version.

```bash
bash$ co httpd.conf
RCS/httpd.conf,v -> httpd.conf
revision 1.2
done
```

# Chapter 14 • INTERNAL COMMUNICATION

RCS checks out most recent version of by default, but if you have a specific version in mind, you can check it out using the -r flag:

```bash
bash$ co -r1 httpd.conf
RCS/httpd.conf,v -> httpd.conf
revision 1.2 (locked)
done
```

Never put a space between the -r flag and version number. Otherwise, RCS will try to check out a file by the name of.

# Breaking Locks

Occasionally a user might forget to check in a file—or might go on vacation in the middle of checked-out file. When a file remains checked out, the file is locked and other users are prevented from editing the file. Frankly, RCS provides a mechanism for breaking the lock on a file; RCS -u breaks the lock on a file, but it asks you to supply a reason for the break; RCS -u then sends mail to the user holding the lock, as shown:

```bash
$ bash -u httpd.conf
RCS file:httpd.conf,v
Revision 1.2 is already locked by jeff.
Do you want to break the lock? [ny](n): y
State the reason for breaking the lock:
(terminate with single './' or end of file)
>> need to add a virtual server for a client
>> .
1.2 unlocked
done
```

The message sent to the user looks like this:

Date: Sat, 6 Apr 2002 12:56:00 -0500
From: mike
Subject: Broken lock on httpd.conf,v

Your lock on revision 1.2 of file /usr/local/apache/conf/RCS/httpd.conf,v
has been broken by mike for the following reason:

need to add a virtual server for a client

![](img/894492738e879267320b8d6f9a044180_444_1.png)

# Check with the Lock Owner Before Breaking Locks

Always check with the owner of an RCS lock before breaking it. Someone could have made significant changes to a file and simply stepped out for a bite to eat. By breaking the lock and making your changes to that file, you could effectively erase or obsolete the other person's changes.
