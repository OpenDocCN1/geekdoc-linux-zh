# Types of System and Product Tests

Testing in its simplest form verifies that an action produces its intended result. When you turn on a server's power switch, for example, you expect the server to power on, boot up, and start its applications. Examining individual functions in this simple form of testing is called unit testing. Unit testing is important in the initial stages of system testing, when missing or failing components can prevent entire systems from functioning (you learn more about unit testing in later sections of this chapter).

When unit testing has determined that individual portions of a system are working properly, you can test higher-level aspects of the system, such as its compatibility with other systems and applications and its performance under stress (referred to as load testing). System administrators, developers, and quality assurance (QA) staff typically perform performance tests and load tests, as discussed in this chapter. Quality assurance staff also conduct regression tests on systems that have undergone changes or upgrades, in order to verify that all system functions perform as they prior to the changes. Regression testing reveals problems introduced by system changes and should be part of an IT department's overall management plan.

When these tests come, you may choose to allow the actual users to test the service you are offering. Predeployment user tests of systems and products often occur in two rounds: alpha and beta tests. Users are the most qualified people to test a product's usability—how it can be used by an actual user. A service might be functionally sound and perform well, but if the service is hard to use, it won't be received by users. You learn more about conducting and interpreting end user testing in the chapter.

# Quality Assurance Teams

Many software companies have a separate quality assurance team whose primary role is to test the functionality, performance, and usability of the company's software. Quality assurance testing is especially useful in larger projects where developers may not have time to adequately test their code.

# Scheduling Tests

Schedules are usually tight in IT environments, where a new service might need to be designed and rolled out in a matter of days. No matter how rushed the schedule might be, it must include time for testing. Often, testing is overlooked until the last minute, making it difficult or impossible to complete; as a system administrator, you are responsible for ensuring that the testing is built into the schedule from the project's beginning.

Testing timelines to parallel the project as much as possible to prevent a backlog at the end. You can conduct small-scale tests, such as unit tests, as implement individual functionalities into the system. Largescale load and usability tests must test the service as the whole or large portions of the service; conduct these tests at milestones. This testing plan ensures that the bits and pieces of a system are working properly, and then tests how they work together.
