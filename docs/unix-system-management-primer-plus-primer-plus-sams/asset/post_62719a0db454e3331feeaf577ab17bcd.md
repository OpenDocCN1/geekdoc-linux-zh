## Scheduling Tools

Most process automation is facilitated by one or more scheduling tools that determine when each process should run. All Unix distributions provide at least two tools: at and cron. You can schedule one-time jobs that occur in the future with at, while cron recurring jobs. Knowing how to use these utilities enables you to use the other automation mechanisms discussed in this chapter.

## One-Time Scheduling with at

When you want to schedule a command to execute once sometime in the future, whether it is 5 minutes or 6 months from now, at is the command you should use. at has a very simple and flexible syntax, allowing you to run multiple commands and specify the scheduled date and time in plain English. For example, to kill process ID 19072 at 5:30 p.m., you could type

```bash
# at 5:30 pm
at> kill -9 19072
at> <EOT>
commands will be executed using /bin/sh
job 1017441000.a at Fri Mar 29 17:30:00 2002
```

![](img/894492738e879267320b8d6f9a044180_357_0.png)

> Mark the end of your command list by pressing CTRL-D. This will produce the <EOT> in the previous output, which means "End Transmission".

If you specify a time already occurred, at schedules the command for the next day at the same time. You can also use relative times.

```bash
# date
Thu Mar 28 21:00:39 EST 2002
# at now + 1 hour
at> reboot
at> <EOT>
commands will be executed using /bin/sh
job 1017370846.a at Thu Mar 28 22:00:46 2002
```

![](img/894492738e879267320b8d6f9a044180_357_1.png)

> The commands run from at under the current shell of the calling user. You can use -c (csh), -k (ksh), or -s (sh) to at to use a different shell.

After you submit a job, it joins the at queue for future execution. You have several options for manipulating the jobs in the queue. You can use the at -l command to list the at jobs submitted by the current user; root user can list jobs of other users by appending the username to the command. at -r job-id removes a pending job, where job-id as the identifier you submit a job (at job-id does the same thing on Red Hat Linux).
Only root can remove jobs owned by others.

## Periodic Scheduling with cron

Although at can run a command once at a scheduled time, cron executes periodically according to schedules that you set in the crontab. A crontab is a file that stores scheduled cron jobs; crontab -e launches an editor to edit your crontab for the current user, and root can edit any user's crontab by appending -u username to the command (no -u is required in the System V crontab on Solaris). A typical crontab entry in Solaris 8 looks like:

```bash
10 3 * * 0,4 /etc/cron.d/logchecker
10 3 * * 0 /usr/lib/newsyslog
15 3 * * 0 /usr/lib/fs/nfs/nfs.nd
1 2 * * * [ -x /usr/lib/sbin/rtc ] && /usr/sbin/rtc -c /dev/null 2>&1
30 3 * * * [ -x /usr/lib/gss/gsscred_clean ] && /usr/lib/gss/gsscred_clean
```

The crontab is made up of fields, listed in Table 12.1.

### TABLE 12.1 crontab Field Descriptions, in Order from Left to Right (When Read from the crontab)

| Field | Format |
|---|---|
| Minute | Integers from 0–59 or * |
| Hour | Integers from 0–23 or * |
| Day of month | Integers from 1–31 or * |
| Month of year | Integers from 1–12 or * |
| Day of week | Integers from 0–6 (0=Sunday) or * |
| Command | The commands to execute |

Each field can contain multiple values separated by commas, and the asterisk is used to indicate possible values of the field. Alternatively, vixie-cron, which is available on most Linux distributions, allows you to specify time intervals as well as absolute times using a slash followed by the interval. For example, to run the command /usr/local/bin/cleanup every 5 minutes, you could type

```bash
*5 * * * * /usr/local/bin/cleanup
```

while a System V crontab would be forced to specify each time individually, as follows:
0,5,10,15,20,25,30,35,40,45,50,55 *usr/local/bin/cleanup

## Automating Root Logins

Most administration tasks require root privileges. Tasks are easy on a single machine, but the situation becomes more complex in multis environments where where one may need to run or copy a file as root. In interactive situations, the administrator can simply log in using root password; this option, however, doesn't work for automated processes. You don't need to put a password in a script.

## Using the Berkeley r-commands Without a Password

One of the oldest methods for executing commands on a remote system is using the Berkeley r-commands, named for their remote access capabilities. Three of the r-commands can perform tasks on remote systems:

- rcp—copy a file to or from a remote system
- rlogin—log in to a remote system
- rsh—run a command on a remote system

The r-commands allow you to log in or run processes on a remote machine without a password, even as root. Two configuration files on the remote server control your access: /etc/hosts.equiv and .rhosts. Both files contain lines of trusted hosts and users in the following

hostname is the name of the host from which password-less logins are allowed; username is the optional name of a user allowed to log in from that host. More than one username can be specified for the same host; if none are specified, all users are allowed to log in without a password. The only requirement for using r-commands is that the UIDs of the users are identical on both machines. A + can be substituted for either the hostname or username to match any in front of that host or user to deny access for that host or user.

/etc/hosts.equiv applies the access rules to all users on the machine; .rhosts lives in a user's home directory and only controls access to that particular account. For added security, /etc/hosts.equiv file must be owned by root and .rhosts must be owned by the user attempting access. This entire authentication mechanism is often referred to as a “hosts” authentication mechanism.

A few configuration examples might help.

To allow Jeremy from server1 to access his own account remotely, add the following to Jeremy's .rhosts file:

```
server1
```
