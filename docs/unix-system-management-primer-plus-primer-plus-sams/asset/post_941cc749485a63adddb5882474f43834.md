Load balancing on any Unix system involves choosing the right load-balancing scheme for your services, and installing appropriate load-balancing hardware or software.

## Load-Balancing Schemes

There are many ways to balance load across servers, each of which has its own advantages. Not all balancing schemes are appropriate for all applications, so it's important to understand how each method operates. Some of the more common load-balancing hardware techniques include the following:

- Round robin
- Least connection
- Response time
- Weighted

Each of these techniques is discussed in detail in the sections that follow.

## Round Robin

A round robin scheme provides the simplest method of load balancing. In a round robin scheme, the administrator creates a pool of servers and lists them in a specific order. Requests to that pool go to each server in turn, cycling back to the first server when the end of the list is reached (see Figure 10.1).

Round robin is best used for network applications with short-lived connections. HTTP is a stateless protocol that well suited for round robin. A request comes in for a URL, the load balancer sends the request to the next server in the pool, the server responds to the request, and the connection is closed. Ideally, the combination of short sessions and an even distribution of requests guarantees that each server will be handling roughly the same number of requests as every other server.

Longer sessions, on the other hand, aren't a good fit with round robin load balancing. Because the amount of time each session exists is unpredictable (possibly seconds, minutes, even days), there's no guarantee that the number of connections to one particular server will be comparable to the number of connections on another server. You may end up with one server handling 500 long-lived requests, while other servers are handling 50 or 60 at one time.

## HTTP Persistence Issues

Many Web servers and load-balancing hardware support HTTP persistence to keep requests from a client pinned to a particular server. HTTP uses a single TCP connection, and these connections can hang for several minutes before closing. When HTTP persistence is used in a round robin server, individual servers can become flooded with these open connections, a condition that defeats the purpose of load balancing. For such situations, least-connections configuration (which you will learn about in this chapter) is preferable.

The domain name, or DNS, is a basic implementation of round robin that is part of the very fabric of the Internet itself. Although not necessarily part of load-balancing hardware, DNS bears mentioning here in our discussion of round robin.

When a program needs to translate a name into an IP address, the request usually ends up at a name server. The IP address is stored in an A-standard DNS resource record. The name server returns an A record to the client program. Because the name service can return more than one A record, DNS uses a round robin system to distribute responses among all of the A records.

The most widely used name server in today is BIND, the de facto standard name server on Unix. A BIND server cycles through multiple A records in robin fashion if they exist, and then returns the list of A records in a different order for each request, leaving it to the client to choose which record to use. Most Unix clients use the first record returned and discard the others. This pattern results in an even distribution of addresses among all of the clients, balancing the load across each of the servers.

## Least Connections

Another popular load-balancing scheme is the method of least connections. The least-connections method of load balancing directs new requests for a service to the server with the least number of current connections. This allows more stressed servers to complete their work without having to deal with new requests.

This strategy assumes that the load on any particular server is directly related to the number of connections to that server. Figure 10.2 is a simple graphical example of how least-connections works.

## FIGURE 10.2

The least-connections scheme ensures that the server with the least number of active connections will receive the next request. In this figure, the next request will go to server3 because it currently has only one connection.

![](img/894492738e879267320b8d6f9a044180_277_0.png)

The least-connections method is best suited for session-oriented services with longer-lived connections. SMTP (Simple Mail Transfer Protocol) fits nicely into this category. The duration of an SMTP connection depends on many factors, including the size of a message, the number of recipients, and the bandwidth from the client machine. Some connections last less than a second, others last several minutes. This variability prohibits load balancing with a simple robin scheme, which depends on a uniform connection length for success. Least-connections load balancing, however, makes sure that heavily loaded SMTP servers are not overwhelmed by new connections.

## Response Time

In Chapter 6, you learned about response time to measure service performance. In fact, response time provides one of the most universal measures of performance, and it's also a useful tool for load balancing. You can use service performance measurement to determine which servers in a load-balanced pool are ready to accept new connections, and should be left alone to handle their current payload. Response time load-balancing schemes often work where other schemes can't.
