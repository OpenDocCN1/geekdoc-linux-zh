The program includes a high-level language used to dictate configuration changes, and it manages the actual platform-dependent implementation of those changes. This section gives a brief introduction to cfengine's capabilities and configuration. ## cfengine 2

The examples in this section are based on cfengine 1, which is the most widely used version of us writing. cfengine 2 will have been released by the time this book goes to print, but most of the configuration examples listed here are very basic and still work.

## The Many Forms of cfengine

You can run cfengine from the command line, from cron, or as a daemon. The minimum requirement for running cfengine is a valid configuration file, which is described in the section "Configuring cfengine". Some of cfengine's more useful flags are listed here:

- -- dry-run or -n
  Performs a dry run of the configuration making any changes.
- -- file filename or -f filename
  Specifies the cfengine configuration file.
- -- parse-only or -p
  Parses the configuration file but does not perform any actions. Use this flag to check the syntax of a configuration file.
- -- verbose or -v
  Produces verbose output, which is useful for auditing changes and debugging.

## Running cfengine from the Command Line

To invoke cfengine on the command line, become root and run the following:
`cfengine -f cfengine.conf`

Assuming your configuration file was named cfengine.conf, this would run through the actions in the configuration and make changes as appropriate on the local system. This is the simplest use of cfengine.

## Using cfengine as a Front End for cron

cfengine is capable of restricting actions to specified timeframes, making a very front to cron. As you see, cfengine can do the work of a complex script in just one line, which means you will not have to write, maintain, and distribute many maintenance scripts to your systems.

You can easily set up cfengine as a front end for cron; the only decision you need to make is the granularity of your scheduling. Should actions be able to run every minute, or are 15-minute intervals adequate? The overhead involved in this use of cfengine is configuration file parsing, so you have nothing to lose by scheduling cfengine to run often. Scheduling cfengine to run every 15 minutes from cron is easy, as follows:

```
0,15,30,45 * * * /usr/local/bin/cfengine -f cfengine.conf
```

## Running cfengine in Daemon Mode

cfengine version 1 includes a daemon that runs on each system using cfengine's control. This is controlled by another program called cfr, a trust mechanism similar to that of hosts, but uses its own format. See the cfengine documentation for more details about configuring.

## Configuring cfengine

cfengine provides a rich configuration language that can be used to perform tasks from mass transfer of files across the network. This section introduces the important concepts in cfengine configuration and how to perform some basic tasks. The documentation on Web site is highly recommended as a supplement to this section.

## Defining Actions

The cfengine configuration file is usually named cfengine.conf and is divided into sections identified by the name of an action followed by a colon. Actions are predefined and considered the commands of cfengine language. For example, the copy action copies files, and the edits action makes changes to lines in configuration. cfengine version 1 uses total actions; some of the most useful includes:

| Action | Description |
| :--- | :--- |
| classes | Defines classes representing groups of hosts |
| control | Defines variables |
| copy | Copies files and sets ownership and permissions |
| edits | Performs various edits on file, substituting for regular expressions |
| files | Modifies file attributes as owner, group, and permissions |
| links | Creates and removes hard and symbolic links |
| processes | Manages processes by signaling or restarting them |
| shellcommands | Runs shell commands |
| tidy | Finds, reports on, and removes files matching criteria |

The only required action is control, in which you define variables and set defaults. The syntax for defining variables is as follows:
`name = ( value )`

The actionsequence is a required part of configuration, and determines the order in which other actions executes. If you want actions to execute in that order, you would define actionsequence as follows:

```
control:
  actionsequence = ( copy files shellcommands )
```

Other actions have different syntaxes. For example, the copy action allows you to set file attributes such as source and destination paths, owner, group, and permissions.

```
copy:
  /usr/repo/files/group dest=/etc/group owner=root group=sys mode=644
```

A different action can be further divided into editfiles, which are used to perform in-place editing of files. This use of editfiles comments out the finger from files.

```
editfiles:
  CommentLinesMatching = "*finger*"
```

## Using Classes

Each action can be further divided into classes, which are Boolean (either true or false) variables set by cfengine. Classes represent the various states of cfengine, including the host on which it is running and the current time. Classes even be created on the fly after completing an action. Actions are only invoked when the classes they are listed under are defined, which makes it very easy to make different changes based on hostname, date, or even the completion of a previous action.

cfengine provides a default set of classes to represent things like the hostname and the time of day. Some of these classes include the following:

| Class | Description |
| :--- | :--- |
| any | This class is always defined, and any actions listed under it will always be executed. |
| hostname | This class is named after the host on which cfengine is currently running. |
| platform | This class is named after the platform on which cfengine is running (such as sun4, linux). |
| YrXXXX | The current year (such as Yr2002). |
| Month | Named after the current month |
| Day | Named after the day of the week |
| DayXX | The day of the month (such as Day26) |
| HrXX | Hour of the day in 24-hour time (such as Hr20) |
| MinXX | Minute of the hour that cfengine was started |
| MinXX_XX | The 5-minute interval in the hour cfengine was started (for example, 12:07 would result in a class called Min12_5) |

Defining your own class is easy; just define each class under the classes action, as you would define a variable in the control action. Here's how to define classes of machines like this list of Web servers:

- classes:
  webservers = ( grumpy dopey sneezezy doc )

To limit an action to a certain class, simply precede it with the class name followed by two colons. Listing 12.1 shows a typical cfengine configuration file that copies /etc/group to all servers and httpd. Apache is restarted when httpd.conf is updated on the Web servers. It also comments out lines in /etc/inetd.conf that begin with "finger",

## LISTING 12.1 A Simple cfengine Configuration File

```
# simple cfengine.conf

# define classes
classes:
  webservers = ( grumpy dopey sneezezy doc )

# define the order of our actions
control:
  actionsequence = ( copy editfiles shellcommands )

# copy files
copy:
  any:
    # copy /etc/group to all servers
    /usr/repo/files/group dest=/etc/group o=root group=sys mode=644
  webservers:
    # copy Apache configuration to just the web servers
    /usr/repo/files/httpd.conf dest=/usr/local/apache/conf/httpd.conf \
    o=root group=root mode=644 define=restart_httpd

# edit configuration files
editfiles:
  CommentLinesMatching = "^finger"
```
