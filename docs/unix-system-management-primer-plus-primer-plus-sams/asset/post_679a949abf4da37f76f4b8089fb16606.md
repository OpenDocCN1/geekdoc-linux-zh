# Chapter 4 • TESTING YOUR SYSTEMS 101

## Pad Your Schedule for Unforeseen Events

Always add in a few days to your deployment schedule to account for resolving problems such as compatibility issues.

## Determining What to Test

If you change a component of a system that interacts with any other component of that system or systems, you should verify that those components are still compatible with each other. Too often, a system administrator will install an application, make a configuration change, or apply a patch without testing to see how it affects other applications and systems.

Determining what interactions to test can be difficult because many aspects of a Unix system relate to each other and to other systems on a network. The most effective way to test interactions is to create a dependency tree for the component you are changing; list the things that depend on the changed component (dependent), as well as the things on which component relies (dependencies).

Hardware and software documentation should list many of the dependencies, such as required operating system versions, patch levels, and any required third-party software. However, determining the dependent components lies mostly on your shoulders because only you know how components of your system are being used. For example, if you have upgraded to a newer version of the Perl interpreter over your server, what other software have you installed that depends on uses Perl?

In general, the following common occurrences should warrant compatibility tests:

- Operating system upgrades and patches.
- Application upgrades and patches.
- Shared library changes.
- Replacing old or broken hardware with hardware of a different make or model. This includes cables.
- Configuration changes for major subsystems. For example, changing /etc/nsswitch.conf to use DNS for hostname lookups instead of local host files.

## Conducting Compatibility Tests

Procedures for a compatibility test are highly dependent on the components you are testing. For example, if you replace an Ethernet card in a server with one from a different vendor, you could verify that the server (a dependent component) detects the network interface using ifconfig -a; you then could attempt to ping another server on its network ( functionality of the ping command is dependent). You could also use netstat to check for network errors, which might indicate compatibility issues.

On a larger scale, if you reconfigure a server to authenticate your user accounts against your Windows 2000 domain controller instead of the Unix /etc/passwd file, you would want to verify that every application that depends on the system's authentication subsystem successfully authenticate using Windows usernames and passwords. You may find that although Windows allows usernames of up to 20 characters, certain Unix applications do not accept usernames longer than 8 characters. This is a serious compatibility issue that could cause you to back out of your new authentication mechanism completely.

As you can see, the tests for these two examples were vastly different due to the nature of their dependent components. Generally, you will want to perform unit tests (as described in earlier sections of the chapter) to test all of the functionalities between the changed component and its dependencies.

## A Compatibility Test Example

The IT department at a small company was using Request Tracker (RT) version 1 for trouble ticket management (see Chapter 5, "Support Administration," for more information on RT). RT v1's limitations forced the company to consider an upgrade to RT version 2. The system administrator wasted time and upgraded to version 2 without reading any of the known bugs listed in its documentation.

Right away, users experienced problems—pages would periodically come up blank and searches on existing tickets produced no results. Eventually, the system administrator read the product documentation and saw that RT 2 was not compatible with Perl 5.6.0, the version installed on that system.

Not wanting to revert to RT version 1, he compiled and installed Perl 5.6.1, which was documented to work with RT 2. Instead of replacing the current version of Perl, he installed it in a nonstandard location so it would not interfere with other programs using Perl—the last thing he wanted

The administrator reconfigured RT to use the new version of Perl and redeployed it. It functioned normally, without any blank pages or empty searches.

This example demonstrates the results of a simple software incompatibility, how it was remedied, and how a simple task like reading product documentation could have prevented this situation from happening at all. Note how the system administrator left the current version of Perl alone so as not to disturb the system further—considering the number of Perl scripts on the system, this could have introduced even more compatibility issues.

## Read the Product Documentation

Always read the documentation, especially the sections on requirements and known bugs, for any product you want to install on your systems.

## Load Testing

Load tests measure the performance of a system under stress. These tests try to mimic the worst of conditions the system might experience in production, and they attempt to answer the following questions:

- Can the system function normally within the required performance specifications?
- At what point does the system not meet the requirements?
- Does load increase linearly or geometrically as you add stress to the system?

## Determining Load Test Parameters

A load test stresses a system and monitors its performance under this load. The numbers a load test reports back to mean nothing, however, without context. In general, you structure the load test with the following specifications to obtain valuable results:

- The mechanism used to stress the system
- How much load to introduce into the system
- The units in which performance will be measured (for example, pages served per second on a web server)
- Range of acceptable performance levels

These specifications enable you to assess the level of performance exhibited by the system under a certain type of load, based on your range of acceptable performance.

## Conducting Load Tests

Specific load test procedures, like the procedures for other system tests, vary according to the application you are testing. There are two major types of load tests:

- Constant load tests: The load is kept at a fixed level. This is useful for determining if the system can handle a specific load over time.
- Variable load tests: The load changes over time. This is useful for finding the breaking point of the system.

The mechanism used to stress the system, how much load to introduce into the system, the units in which performance will be measured, and the range of acceptable performance levels are all important to consider.

## Static Versus Dynamic Content

When load testing servers, you should test both static and dynamic content. Static content is the content on your site that doesn't change, which mostly consists of HTML and image files. Dynamic content can change based on user input and places more load on server time, CPU cycles, and memory. Limiting a test to static pages makes the site appear better than in practice, and limiting the test to dynamic pages makes it appear worse.
