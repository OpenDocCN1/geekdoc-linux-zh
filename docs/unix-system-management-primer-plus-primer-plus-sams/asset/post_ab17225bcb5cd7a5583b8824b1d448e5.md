
# UNIX SYSTEM MANAGEMENT PRIMER PLUS

Root account management also poses a security risk for your users and any sensitive data stored on a system, as root is free to view or modify any local files and sniff network traffic flowing and out of the machine. As a system administrator, you need to become familiar with the techniques for properly managing your root account, as discussed in the sections that follow.

# Limiting Access to Root Passwords

Guard your system's root account password carefully. Reveal the root password only to the people responsible for administering a system. The password is necessary for installing software, changing system configuration files, and similar administration tasks. Technicians can perform most privileged tasks using group permissions or by installing programs to run commands on behalf of a regular user (you learn more about these techniques in "Delegating Authority" later in this chapter).

# Choosing Secure Root Passwords

One of the most important things you can do to protect your root accounts is to secure passwords for them. A secure password is one that casual users can't easily guess and isn't susceptible to "dictionary attacks" using variations on random words. The root password should contain a combination of letters, numbers, and punctuation, and should be at least six characters long—though eight or more is better.

If you are responsible for more than one system, as many system administrators, you may want to consider creating a root password scheme. This scheme combines a fixed string of characters with the names of your systems to create root passwords for each individual system. The alternative is to use a completely different password for each server, but remembering all of the passwords can be difficult. Using a root password scheme, each machine has a different root password, but those are easy to remember because they are based on one fixed string of characters.

For example, you could choose the string uif4e! (Unix is for everyone); and form passwords by surrounding it with the first and second letters of a system's hostname. The root password on a system named apple, for example, would be uif4eip!, while the password on orange would be uif4eir. If someone managed to guess the password on apple, it would be useless on orange, minimizing the damage caused by a cracked root password.

# Disguise Your Password Scheme

Someone who happens to guess or otherwise discover a root password based on a system may be able to infer the secret just from that discovery. You can make your schemes less obvious by using characters other than the first letter of the hostname and embedding those characters within the scheme's string instead of surrounding it.

# Never Transmit Root Passwords over a Clear Channel

Even the most carefully chosen root password can be compromised if it is sent over the network in the clear. One of the first things a hacker will do after obtaining root privileges on a server is to set up a network sniper to learn usernames and passwords for future access. If you Telnet from a compromised system to a remote system and type the root password while sniffing is running, you have just given away the root password to another machine.

# Hacker Network Damage

A hacker with root privileges can do more than just sniff passwords from the network. He or she can trace processes, read from arbitrary locations in memory, and even “sniff” the console keyboard to learn what passwords are being entered.

# Reserving UID (User Identification) 0 for the root Account Only

The real administrative privilege of the root account does not lie in the name root, it lies in the user identification (UID) of 0 assigned to the account. Some experienced administrators choose to create additional accounts with UIDs of 0 for other people to use, thinking that those UIDs provide a way to audit the use of root privileges. This configuration presents several problems.

The first of these problems is that the administrators are allowing other users to become root, which is quite dangerous for the reasons described in the previous sections. Second, instead of maintaining just one root password, the administrators now have to worry about two passwords, and they may not know who has knowledge of that second password. There are much better ways to delegate and audit root authority, as you will see later in the section, “Delegating Authority.”

# Limiting Remote Access to the Root Account

Chapter 12, “Process Automation,” explains a number of methods for executing remote commands as root. This capability is extremely useful to a system administrator, but it must be handled with care. Executing remote commands as root allows root access without a password. You can minimize your risk when implementing root access in the following ways:

- Limit remote access to a single machine, creating a single heavily secured gateway into remote root accounts.
- Require root access on the gateway system in order to gain root access on remote systems. This precaution adds another layer of security to the gateway and ensures that system administrators can take advantage of root access.
- Use strong authentication methods like SSH's public key authentication in addition to any trusted host mechanisms. This two-layer access security reduces the risk of someone spoofing your identity.

# Delegating Authority

This chapter has spent a lot of time stressing the importance of protecting root privileges at costs. There are times, however, when delegating this authority to normal users is appropriate and even necessary. You can use any of several tools and methods to delegate this authority safely, including aliases and defaults, controlling access over Solaris 8, and using Unix Group Permissions. The sections that follow offer detailed information about using each of these techniques to delegate access authority and other privileges.

# Unix System Privileged Accounts

root may not be the privileged account on a Unix system. For example, all Web servers recommend they be run as a user other than root, as do the MySQL database server and various other applications. The users under which these applications run can be considered privileged with respect to those particular applications.

# Using sudo to Run Commands as Another User

sudo, which is short for "superuser do," is a command that allows a user to run commands as another user, though system administrators usually use it to delegate root privileges for specific tasks. It is the most popular third-party tool among administrators for delegating privileges. sudo supports the following features:

- Central configuration file
- The ability to restrict which commands can be run on a per-user, per-group, and per-host basis
- Password authentication
- Verbose logging for command auditing

You would want to use sudo to delegate authority in the following situations:

- Backup operators need root access to run dump and restore commands.
- A DBA needs to reboot database servers but does not have the root password.
- You have instructed a junior administrator to handle user account creation but not want to give him or her the root password.
- You want to audit the commands as root.

sudo requires a user to enter his or her password for authentication before running the command. This password protection prevents someone from wandering over your computer while you are away running commands as root. To minimize the hassle of entering a password for every command, sudo maintains a timestamp file for each user that allows users to run commands for a default of five minutes without re-entering a password.

You can see a good example of how sudo works by running the id command, which displays the UID of the user command.

```
$bash id
uid=1000(jeff) gid=1000(jeff) groups=jeff, 0(wheel)
bash-2.05$ sudo id
```

We trust you have received the usual lecture from the local System Administrator. It usually boils down to these two things:
1) Respect the privacy of others.
2) Think before you type.

```
Password:
uid=0(root) gid=0(wheel) groups=1000(jeff), 0(wheel)
bash$ sudo id
uid=0(root) gid=0(wheel) groups=1000(jeff), 0(wheel)
```

Note how the second instance of sudo does not require a password. If five minutes had passed between the two commands, sudo would have asked for a password.

If a user is not permitted to run a command, the following error is displayed:

```
$bash$ sudo id
jeff is not in the sudoers file. This incident will be reported.
```

# Specify Your Identity

By default, sudo assumes you want to execute commands as root. If you want to run a command as another user, specify that user by adding the -u flag to the sudo command.

The sudo configuration file is /etc/sudoers, and should only be edited with the visudo command. As crontab does for user crontab files, visudo checks the syntax of the sudoers files and reports any errors with the configuration. sudo has the following three main parts:

- Aliases
- Defaults
- User specification
