Options can be global or specific to individual log files. Global options are listed on lines themselves, while individual log files options can be specified as such:

```
log-path {
  options
}
```

Following are some of the options you might find useful:

| daily|weekly|monthly | Defines how often to rotate logs |
| :--- | :--- | :--- |
| compress (nocompress) | Compresses (or doesn't compress) rotated logs with gzip |
| create [mode] [owner] [group] | Creates a new log file after rotation; ownership and permissions are optional parameters |
| include path | Includes directives from another configuration file or a directory of configuration files |
| rotate num | Specifies how many archived files to keep |
| size=num[km] | Rotates files when a log reaches this specified size (in kilobytes or megabytes) |
| prerot ... endscript | Runs the shell commands between prerorate and endscript before a log is rotated |
| postrotate ... endscript | Runs the shell commands between postrotate and endscript after a log is rotated |

You can find a comprehensive list of options in logrotate's page.

You may notice that the standard logs found in /var/log, such as messages and mailog, are not mentioned in logrotate.conf at all, yet they are always rotated. The configurations for these and other logs are contained in files the /etc/logrotate.d directory and are appended to the main configuration with the include /etc/logrotate.d directive. The file /etc/logrotate.d/syslog contains all of the configurations necessary to rotate the logs from syslog, as well as entries like this:

```
/var/log/messages {
  postrotate
  /bin/kill -HUP 'cat /var/run/syslog.pid 2> /dev/null 2> /dev/null || true
endscript
}
```

Note how the postrotate commands restart syslog after the log is rotated so it reopens the new log file. Taking care of all of these rotation tasks from a single configuration file makes the process simple and convenient.

# Should You Rotate Based on Size or Age?

Logs are generally rotated based on either their size or age. Which of these criteria is the better basis for your log rotation strategy depends on available disk space and your retention policy. If you are concerned about disk space, you should rotate your logs based on their size—that you may have a predictable amount of logs at all times. On the other hand, you may have a retention policy for calls on log archives of up to several months or years. In that case, you could rotate log files based on age and set the number of saved logs to a number that your retention policy—this would provide you with a consistent timeline of logs. Of course, nothing beats trial and error, over time, you will learn approximately how long it takes for a log to reach a certain size. Logs that do not grow much and are not rotated will be small, but they will also contain very stale data (often months or old), while logs that grow quickly often contain more data is convenient to work with. Make sure to consider these trends along with your disk space and retention policies when deciding your criteria for log rotation. Of course, you could implement a combination of these schemes, for example, you could rotate logs that are larger than 50MB or older than two months.

# Authentication, Authorization, and Accounting

Before diving into the details of security, you first must understand the concept of authentication, authorization, and accounting—often referred to as AAA. The AAA concept is the basis for all Unix system access mechanisms, and access control plays a major part in system security. You will see the components of AAA reflected in many of the security tools and methodologies discussed throughout this chapter.

Authentication is the process of identifying yourself to a system. Most systems require an authenticator, which is usually a combination of an identifier and a secret code or component, the latter of which is known only to the owner of the account. The identifier and secret element usually take the form of a username and password, but alternatives such as electronic certificates, smart cards, and biometrics are also common.

Authentication only proves a user's identity to the service being accessed; it does not authorize the user to use the service. Additional mechanisms must be in place to associate user identity with the rights that user has for that. These mechanisms fall under the general title of authorization.

For example, one may prevent a user with a valid Unix account on a server from accessing that server's FTP service by adding his or her username to the file /etc/ftusers. This enables a user to successfully authenticate to the FTP server using the correct username and password, but it denies FTP server access to that user. In this example, authentication is successful, but authorization fails.

Accounting provides logging and summary information for the authentication and authorization mechanisms, as well as any application-specific usage data. Accounting is important for auditing access to a system and assessing charges to accounts based on usage. Without accounting, you would have no idea who is or has been logged into your system.
