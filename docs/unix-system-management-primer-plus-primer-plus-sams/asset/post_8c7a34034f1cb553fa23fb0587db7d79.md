# Using Multiple Network Paths

A network is just as likely to fail as any other component in your infrastructure. You can easily understand the potential for network failure when you consider the number of parts in a network that could fail, including cables, routers, switches, NICs, and telco lines. Highly available networking can be achieved by configuring redundant network paths between your critical systems and between your systems and the Internet.

# Provider Redundancy

Sites with a single telco to the Internet risk losing connectivity if that line goes down. Many time connectivity problems lie with your provider or the phone company, leaving your business in the hands of a potentially overworked and under-responsive staff if disaster strikes. One way around this situation is to use multiple providers for your Internet connectivity. Many ISPs use several links to different major, tier-1 backbone providers such as UUENet, AT&T, and Sprint to provide virtually uninterrupted connectivity. An ISP's routers will simply reroute traffic to other network paths when one becomes unavailable.

Other businesses can also take advantage of this kind of redundancy by receiving connectivity from two or more ISPs. This provider redundancy is transparent to Internet users in the office—when one link goes down, the router sends traffic through another link. Incoming traffic is a bit tricky. Different providers will assign you pools of IP addresses, so traffic destined for your office addressed to an unavailable link will be lost. The easiest way around this problem is to use DNS to temporarily change the IP addresses assigned to the well-known names for your mail hubs, Web servers, and other public hosts. # Use Modems as a Last Resort

Many routers support modem expansion cards or offer a serial port for a modem connection. You can use this as a last resort when you need Internet connectivity but your provider's telecommunications lines are down. However, since you are only given one IP address when dealing in, a modem is not a solution for making available multiple public services like web servers DNS servers, and mail hubs.

# Local Network Redundancy

An outage caused by a broken switch or network card on your LAN can be as noticeable to your users as a major backbone outage. There are two solutions to this problem: trunking and multipathing. Trunking combines multiple network links to form a larger, faster, and more reliable link. Multipathing utilizes separate network links to provide alternate paths for traffic.

# Trunking

A trunk combines two or more physical network links to form one larger capacity link. For example, a trunk could be formed using four fast Ethernet interfaces to create a single 400Mb link between two fast switches. Trunking contributes to high availability in multiple ways, by increasing bandwidth and by providing link and interface redundancy. If one of the trunked interfaces goes down, all lose is bandwidth—the actual link remains up using the other interfaces.

![](img/894492738e879267320b8d6f9a044180_292_1.png)

# Truths About Trunking

Trunking offers real benefits, but you should be aware of a few important details when using this option. First, the multiple links and interfaces only provide redundancy protection against individual network card or port failures. The link as a whole is still vulnerable to switch and server failures. Second, a trunk increases bandwidth only between the two sides of the connection. A 200Mb trunk from a server to a 100Mb switch will provide the increased bandwidth only to the switch itself. In order for another server to enjoy that extra bandwidth, it would have to be trunked on the same switch.

# IP Multipathing

IP Multipathing refers to the use of multiple switches to provide a failover option when one switch fails. When a switch fails, all of the devices connected to that switch become unavailable, causing a major outage. IP multipathing provides switch redundancy to eliminate these outages. Each interface on the host is plugged into a different switch, creating multiple paths to from the server.

In a common implementation of IP multipathing, the IP address of the host is bound to one of network interfaces until software on the server side detects a link failure on that interface. At that point, the system chooses another interface with an active link for failover, and subsequently binds the IP address to it, creating an alternate path for traffic to take.

# Multipathing Requires Extra Hardware

Multipathing does require additional hardware to provide the infrastructure for the additional paths, including switches, cables, and network cards; take that extra cost into account when considering this network redundancy solution.

# Storage Multipathing

“multipathing” is also used in storage nomenclature. A SAN typically has more than one path (via fiber channel) to a disk array; multiple fiber-channel cards and switches implement multiple paths, in an arrangement analogous to the IP multipath implementation.

# Using Server Clusters

Server failure is another threat to high availability. In previous sections of this chapter, you've learned about using redundancy to promote high availability by providing better performance and failure recovery. The high-availability techniques you've read about have applied to telco lines, ports, NICs, cables, and switches. Server clustering is a high-availability technique used to provide redundancy for server operations.

A server is a much more complex system component than a NIC or a switch. As a general-purpose machine, a server can perform several tasks at any time. Fault-tolerant servers duplicate internal subsystems to prevent any failure from taking down the machine. An increasingly popular approach for providing server redundancy is server clustering, in which several servers can take over for a single server.

Configuring and running a cluster is beyond the scope of this book, but as a Unix system administrator, you should understand some basic concepts of clustering and the software that supports it.

# Failover Clustering

A failover cluster consists of a single active server and one or more standby servers; if the active server fails, a standby server takes over. Using failover clustering requires extra software and support in the kernel to be able to transition the exact state of one machine to another. Adding redundancy to the cluster is as easy as buying another server.

# Use Identical Hardware in Failover Clusters

Try to use identical hardware for each server in your cluster. This ensures that performance for your applications will be the same on the standby server as it is on the active server. Some clustering software may require identical hardware.

Unix vendors that offer failover clustering include:

- Sun Microsystems: Sun Cluster (Solaris)
- Veritas: Veritas Cluster Server (HP-UX and Solaris)
- Hewlett Packard: MC/ServiceGuard (HP-UX and Linux)

# Parallel Clustering

Parallel clustering pools the resources of many machines to create one large parallel server. Parallel clustering provides dramatic server performance enhancements, when properly optimized, complex calculations that would take days on a single-CPU server might take minutes when executed in a large cluster with multiple CPUs and massive amounts of memory. If one server in a parallel cluster fails, the system loses processing power only; other processing continues and the clustering software relocates the job scheduled on the failed server to another available server.

Unix vendors that offer parallel clustering solutions include:

- The Beowulf Project (Linux)
- IBM: Eserver Cluster Edition (AIX and Linux)
- SGI: Advanced Clustering Environment (IRIX and Linux)
