# Distributed Service Outages

A running joke among system administrators offers this definition of a distributed service:

A distributed service is one in which a server you have never heard of, in a place you've never been, can cause the machine on your desktop to crash.

As Homer Simpson likes to say, “It’s funny because it’s true.” Distributed service outages differ from other kinds of outages in one important way: Although most outages on server A result from a failure on server A, a distributed service outage can occur when a failure on server B causes a failure on server A.

A distributed service (all jokes aside) is one that resides on a remote system but is critical to the functioning of another system. DNS (domain name system) and NFS (network file system) provide critical name resolution for Internet applications, but it resides on remote servers. NFS servers to resolve clients, some of which are critical to the operation of those clients. If DNS servers become unavailable, NFS applications will grind to a halt. A failed NFS server sharing could could render of all outages unavailable to its clients.

To better understand the dynamics of distributed service outages, consider the example of the NFS server. Instead of installing gigabytes of software on each system in your infrastructure, you can install the software once on an NFS file server and share it with the other servers. Now imagine that you have installed shells on NFS server—shells as bash and that are not available by default on your other servers. If the file server becomes unavailable, so the shells. If the shells are unavailable, users can't log in to any of your. A failure on the file server has caused an outage on your other servers.

Perhaps the most frustrating aspect of a distributed outage is that the remote server is failing may be under somebody else's control. You might be responsible for Web servers, but maybe an entirely different team in your company administrators the DNS servers that just went down. Although you have done nothing wrong and your servers are functioning normally, somebody's servers that you rely on can cause an outage in your system, and there's nothing you can do but complain and wait.

# Real-World Example: A Distributed File System

AFS is a large-scale distributed file system often found at universities. Files are stored located on any number of file servers anywhere on the network. At one university, the popular program Pine was installed in an AFS volume, along with all of the other shared applications over 60,000 students, staff, and faculty used every day. Pine was the university's primary email program at the time. AFS servers were running on aging hardware, and as were constantly crashing due to ever-increasing load. The administrators responsible for the machines running Pine were fed up with the outages, especially when the volume housing Pine became unavailable. To resolve this problem, the administrators installed locally on each server, making the most popular application available regardless of AFS volume unavailability. Working with multiple copies of the program was less convenient. But the administrators preferred that small hassle to repeatedly explaining outages that weren't caused by any factor within their control.
