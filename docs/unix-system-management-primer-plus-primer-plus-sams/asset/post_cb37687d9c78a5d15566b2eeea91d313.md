# Ignore the First Line of vmstat Output

The first line of output from vmstat contains averages of all statistics since the system was booted and should be thrown out, no matter how valid it looks. Subsequent lines contain current information.

The first thing administrators try to discover when a system is overloaded is to identify what is using all processing power. This method determines whether a user process or the kernel is responsible for the usage. The following sections will contain this in detail.

# Tracking User vs System Performance

A CPU is not responsible for running processes—the kernel also needs CPU resources, often some of the tasks performed by the kernel can consume CPU usage:

- Excessive paging and swapping
- Software parity calculations
- Allocating and freeing large amounts of memory
- Network traffic

Fortunately, you can determine how much of a processor's time is spent in the kernel and how much is spent executing processes in user space. The us and vmstat output show the percentage of time spent in user space and system (kernel) space respectively.

| 6 0 191512 839368 25 11 57 0 0 0 0 0 6 | 758 347726 1022 94 6 |

After discarding the first (as you learned in the earlier example), you can see that 94% of the CPU's processing resources are dedicated to user processes, and only 6% handle kernel code. This distribution of processing power is what you want from a system; it should spend its time running applications, not stuck in the kernel. The last column of this output, id, is the percentage of time that the CPU is idle (in this case).

Another column to pay attention to is cs, for context switches. A context switch is the transition from user-level code execution to kernel code execution and vice versa. Noting context switches is important, because the system generates a significant penalty with each context switch (such as when an Intel x86 processor must switch back and forth from protected mode). Typically, two events invoke a context switch on a Unix system:

- System calls are the entry into the kernel from user space. When a process needs to open a file, write data to disk, or reboot the system, it uses a system call to tell the kernel to perform these tasks on its behalf. After the task is complete, successful or not, control is passed back to the process in user space.
- Interrupts are more than system calls. The system generates an interrupt when traffic arrives on a network interface, a key is hit on the keyboard, or a timer expires.

## Compare Like Data

When you have determined that user processes are responsible for high load, it's not hard to figure out what processes are causing that load. However, if the kernel is the culprit, it's much harder to find out. In that case, you could trace the process to see exactly what it is trying to do.

## Using ps to Monitor Usage by Process

Using ps to look for CPU-intensive processes can be a cumbersome task when there are hundreds of processes on the system in the first place. In such circumstances, it would be nice to let the computer do the work for you, and the top command makes that possible.

For example, on a heavily loaded database server, ps gave the following output for one of the Oracle processes over several seconds:

| PID | TIME CMD |
|---|---|
| 121 ? | 100:45 oracle |
| 121 ? | 100:46 oracle |
| 121 ? | 100:46 oracle |
| 121 ? | 100:46 oracle |
| 121 ? | 100:47 oracle |
| 121 ? | 100:47 oracle |
| 121 ? | 100:47 oracle |
| 121 ? | 100:47 oracle |
| 121 ? | 100:47 oracle |
| 121 ? | 100:48 oracle |

The Oracle process, having already used over 100 minutes of CPU time, increases slowly and consumes an additional second of CPU time over a 4-second interval. This equates to 25% of a CPU's time, so this process should definitely be investigated.
