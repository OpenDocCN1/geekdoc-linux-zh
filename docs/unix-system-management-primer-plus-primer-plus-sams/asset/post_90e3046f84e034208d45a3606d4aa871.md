Experimentation is also a valuable method to determine the average end user response. This is especially true if you don't have pre-existing logs. Try using the site yourself and see how long it takes for you to fill out each form.

To understand the load-testing process in action, return to the bank Web-server example. Nearest Integer Savings is pleased with the deployment of its new online banking servers, but you must now test the servers to determine whether they can handle the load they are expected to carry.

The marketing department estimates that up to 5,000 customers might register and use the new service at the same time, following major advertising campaigns; then usage should level off at a peak of 3,000 concurrent users. The system must serve each page in less than 7 seconds (an average standard for how long the end user will wait for a page to load). Load the Web servers by introducing an artificial representative load on the system.

## Functioning Within Specifications

The first phase of the load test in this example determines whether the bank's Web server functions within specifications—in other words, can it serve in 7 seconds or under with 5,000 concurrent user sessions? You can't expect to have 5,000 people available to use the site at any given time, so use one of the countless load simulator tools online.

For this phase of the test, you will test the site with up to 333 concurrent connections (the average number you've calculated on user practice calculations, system logs, and so on). In this example, you test with the load-simulator tool Siege, an open source tool (http://joedog.org/siege) Siege can submit all kinds of HTTP requests concurrently and report the results at the end of the test.

Begin the test by establishing a baseline against which you will compare future results. Tell Siege to request a minimal amount of dynamic pages, say 30 seconds of 3 concurrent requests with a random delay of up to 20 seconds between requests to simulate human interaction. Here's the output:

```bash
bash siege -u -t 30s -d 20 -c 3
```

The important statistics to check here are the response time, transaction rate, and concurrency. In this run, the average request took 0.30 second to return a response—a relatively speedy response time. There were 2.27 transactions per second with an average of 0.68 transaction running concurrently. Turn to the Siege documentation to interpret the numbers.

Siege documentation recommends that the number of concurrent transactions should never exceed half of the total number of transactions processed; otherwise, severe performance degradation will be seen. This makes sense; if there is more than one transaction queued up while another is being served, the system won't be able to process transactions enough to keep the queue from growing. Your test results show that the system is well under that threshold in this particular run. You've produced a good baseline; it shows how our servers perform under a very nominal load.

Next, the system at half of the maximum projected load. Here's how the site performed with 167 concurrent connections:


Your system is still in good shape; all transactions were successful and the number of concurrent transactions is still less than half of the total number of transactions. However, the system's response time has dramatically increased to 6.51 seconds, close to our 7-second limit. You must now test the server's performance under the required maximum load, as follows:

There were no transaction failures and concurrency is still less than half of the total number of transactions, but the response time is way over the 7-second ceiling. Your system clearly doesn't meet its performance goals.

# When Your System Fails the Test

When your system fails this phase of the load test, you must determine the reason for the failure. Are the CPUs too slow? Does the system need more memory? Is the database performing up to speed? Does the system need more servers? You learn how to investigate system failures and under-performance issues in Chapter 11, "Performance Tuning and Capacity Planning."

## Determining the Breaking Point

The second question we ask during a load test is "When does the system not meet the requirements?" In other words, what is the breaking point—the point at which response time or other performance parameters fall below the minimum performance specification set for your system? Judging from the Final Siege in the previous section, the bank's web server is close to the breaking point, a load of 167 concurrent connections. At that load, response time was 6.51 seconds, less than half a second under the 7-second standard for this response time.

But "close" isn't good enough for load testing. You need to determine the exact number of connections at which your system reaches the 7-second standard, the breaking point. You could test this by performing several trials, but that process would be too time-consuming. A more palatable solution is to take a few sample data points from previous runs and plot them on a graph with connections on the x-axis and response time on the y-axis. You can then tell through interpolation the approximate connection threshold by drawing a best-fit line through (or a spreadsheet do for you) the points on the graph and the 7-second value of the y-axis. If the points look more like a curve, draw the curve manually. In this example, you need more samples to increase the graph's accuracy and see an obvious pattern:

```bash
siege -u http://www -t 30s -d 0 -c 84
** Siege 2.09
```

## More Data Points Equals Greater Accuracy

When plotting a graph to look for patterns, you should plot as many data points as possible. An ample number of data points reveals the true pattern of the graph and produces more accurate results.

## Identifying Linear Versus Geometric Relationships Between Load Increases and System Stress

In the last phase of load testing, you must determine whether the load increases linearly or geometrically as you add stress to the system. The relationship between the inputs to your system and its resulting performance is important, both for the testing phase and capacity planning down road. In the previous section, you could interpolate the number of connections it took to reach the 7-second response time because that relationship was linear; the response time always increased by the same amount for each concurrent connection added to the system.
