## Choosing the Right Compiler Options

Many administrators build a significant number of third-party applications from source code such as Perl and Apache. One of the easiest ways to boost performance is to use the compiler's optimization features when building these packages. Though you can choose from many compilers for Unix systems, this section focuses on the GNU C compiler, because it is universal to all Unix systems. Most techniques for the GNU C compiler apply to every compiler.

## Using Generic GNU C Compiler Optimization

The GNU C Compiler, or GCC as it is commonly known, is a generic compiler that is available on all platforms. Because GCC is a generic compiler, its default optimizations are common to all platforms. These optimizations include the following:

- Using register variables: This stores variables directly on the processor instead of memory.
- Loop unrolling: this repeats lines of code inside a loop where possible to reduce the number of iterations.
- Function inlining: this integrates a simple function directly into the calling code, eliminating the overhead of calling the function.

You can activate these individual optimizations by using special flags to the gcc program, including -funroll-loops and -inline. But those flags can be difficult to remember and certain combinations can produce strange side effects that cause a program to fail when run. For this reason, GCC offers the O0 flag, which can specify different levels of optimization with a single flag. The format of this flag is -On, where n is an optional number between 0 and 3 (it is the same as -O1). Compiling a program with the highest level of optimization is as simple as following:

```bash
bash$ gcc -O3 -o foo foo.c
```

An in-depth discussion of compiler optimizations is beyond the scope of this book. Consult a text on compilers or the GCC manual page for more information.

## Using GNU Configure

A large percentage of application source code is configured using GNU Configure. To specify the optimization for these applications, put the appropriate flags in the CFLAGS environment variable before running the configure script.

## Using Machine-Specific GNU Compiler Optimizations

GCC also has the ability to use optimizations on the machine to which you expect the application to run. For example, applications running on the Pentium Pro and later Pentium processors can greatly benefit from the -march=686 and -mfpu=686 flags. Those flags use processor-specific instructions in the final binary executable that can significantly increase the speed of the application when compared to an executable using the lowest common denominator instruction set. Using these flags is especially important when compiling a Linux kernel, where every ounce of optimization can improve the performance of your system.

Remember one caveat when using machine-specific optimizations on any compiler: the code produced is nonportable. Executables are only guaranteed to run on identical or compatible processors. If an application is compiled with Pentium optimizations, it will most likely not run on an older x86 system that doesn't understand some of the instructions or registers available on Pentium. This problem usually doesn't manifest itself in the other direction—a program built with Pentium optimizations will run on Pentium because the instruction set is backward compatible.

## Real-World Example: Optimization Mishaps

A junior administrator was busy compiling in preparation for an operating system upgrade when he came upon the Ghostscript interpreter. He used the -O3 flag when compiling many applications before. After the compilation completed successfully, the administrator tested the executable and each time core-dumped with a segmentation fault. After hours of looking for similar problems, he recompiled using the -O2 flag, reducing the optimizations. This version of the executable worked fine! Certain parts of the code did not optimize properly under -O3, but without those optimizations, the program worked flawlessly. You cannot predict when these failures will occur, but it is easy to experiment with.

## Setting Process Priorities

One of the oldest methods of performance tuning is setting process priorities. A priority determines a process's relative importance to other processes running on the same system; when two processes vie for time on the same CPU, the higher priority process will get to use the CPU first. The priority of a process in Unix is traditionally known as its "nice" value, named for the nice command used to make a process play nicely with others; if one process is causing sluggishness by taking up its CPU time, the nice value can be adjusted to lower its priority. Nice values range from -20 to 19, with lesser values having higher priority. The default value is zero.

## Changing Nice Values

Any user can increase the nice value of his own processes, but only root can decrease the nice value of a process. This means that when a user increases the nice value of a process, he cannot decrease it back to its original value. You can set a process's nice value on the command line before the process is run, in order to tune down the CPU usage of processes you know will cause problem. For example, the following command clears old files from temporary directories:

```bash
find /var/tmp -mtime +14 -type f -exec rm -f {} \+
```

top can verify the nice setting (Solaris), as shown here:

You can prioritize processes using the renice command. The following command increases the nice value of the sleep process by 5:

```bash
renice -n 10 16165
```

This command changes the process's nice value by 10:

```bash
renice -n -10 16165
```

## Other Scheduling Implementations

This chapter discusses the renice command because it is universal to all Unix systems. However, many operating systems have their own priority scheduling mechanisms; Solaris is one of the many powerful scheduling implementations, but it is beyond the scope of this discussion. See the Solaris manual pages for prioritycntl and dispadin for more information on that implementation.

## Using Multiple Processors

Administrators increase performance by adding processes to a system, but they achieve significant benefits only if the applications running on the system are able to take advantage of multiple CPUs. The key to performance on a multiprocessing system for a single application is the system's ability to have two or more tasks running concurrently; to do that, the application must be multithreaded. There are three types of programs with respect to multithreading:

- Single-threaded programs: Single-threaded programs, such as ls, cat, and most everyday commands have a single thread of execution within their scope. Multiple processors are of no benefit to these individual programs, as there is only one thread of execution.
- Multiprocess programs: Multiprocess programs spawn—which is known as forking in the Unix world—child processes to handle concurrent requests. Apache is a perfect example of an application that uses this strategy. When Apache is started, multiple processes are forked, and the original process handles each incoming connection. Each child process is single-threaded and can handle only one request at a time, but the concurrent processing of all processes makes the Web server much scalable, even on a single-processor system. If another processor is added, you can achieve true concurrency, where one process is executing on one processor while another is executing on the other.
- True Multithreaded Programs: A multithreaded program can have multiple threads of execution within a single process. Unlike a process, creating a thread requires very little overhead, although threads execute independently of each other, each thread still has access to global data structures within the process. Most importantly, multiple threads within the same process can run concurrently on different processors, bringing the benefit of multiprocessing to single processes.
