Geometric relationships can be more difficult to extrapolate. In this kind of relationship, consecutive results vary by a constant ratio. So, instead of having a constant increase in response time for each additional connection, the response time would increase in larger and larger amounts as connections are added, reaching the breaking point sooner. This would produce a graph curving upward to the right rather than a straight line. Making accurate predictions with such a graph is difficult unless you plot enough data to reveal an obvious pattern. Not all relationships between load increase and system stress are purely linear. Nature of stress on the system causes the test relationship to become geometric. Some relationships are neither linear nor geometric, making it impossible to extrapolate anything from the test data. Only by testing can you find out what these relationships are and what you can do with them.

## Real-World Example: Load Testing

A small market research company was expecting its usage to double in less than two months. The system administrator quickly assessed the situation and determined that two processors could not handle the load reliably. Before deployment, the administrator performed a load test on the new servers. Many samples were taken, and a linear relationship was observed between the number of connections and server response time. After plotting, the administrator discovered that although the old site could handle 100 concurrent connections and still respond within 7 seconds, the new site could handle 450 concurrent connections and keep response time within 7 seconds. Doubling the resources more than quadrupling the capacity of the site, new servers could grow.

## Regression Testing

Regression testing is one of the primary tools of any quality assurance (QA) team. Begin regression testing by establishing a baseline of functionality of an existing system. Then compare the baselines against the functionality of a new system. Regression testing is not intended to measure performance; you are not trying to beat the numbers from the last test. Instead, a regression test makes sure that everything still functions as it did before so you know nothing will break when the new system is deployed.

## Conducting Regression Tests

Regression testing is an art, especially for larger projects. In preparing for the test, the system must account for all features of a project, and preparing an accurate baseline is the most critical part of the test, as the baseline is the data to which all other results are compared. Before new hardware or software is deployed, you must conduct regression tests to compare the new components' functionality against the baseline. Everything within the system should function as it once did, and if something does not work as it did before, the assembly line should shut down and the problem should be investigated.

Regression tests themselves work very well, but are valuable only if you keep them up to date. As features are added, changed, or removed from a product or system, your testing procedures must reflect these changes. Testing a feature that no longer exists is pointless and will give you false positives, while failing to test new features leaves your system at risk. The best way to keep everything in sync is to make regression testing a regular part of change management. See Chapter 14, “Internal Communication,” for more information on change management.

## Detecting Changes

The results from a regression test should match previous results exactly. When results change, you know that some component or function within the system has changed as well.

## Evaluating Regression Test Results

Although regression tests themselves involve complex testing procedures, the results of each test should be summed into one of two simple methods: pass or fail. Using these simple results makes it easy to see exactly what works and what doesn't work, rather than the effort involved in poring over a bunch of complex or vague comments. Notation of failures should definitely include how each test failed. These comments make it easy for the developers or administrators to find and fix the problems in the test.

## Regression Test Example

The most pervasive example of a regression test on Unix occurs when you compile a new version of Perl. The Perl distribution comes with a suite of tests that verify the functionality of every standard Perl operation that is implemented on your system. One of the tenets of Perl is that it strives to function in the same way on every operating system, and thousands of regression tests verify this before you install it. If any regression test fails, you can report those failures to the Perl developers who (one hopes) will fix the problem.

# Perl Runs Thousands of Tests

Perl 5.6.1 runs 13,145 individual tests after compiling a typical Solaris 8 system.

The testing process is by typing `making test` in the Perl source directory. Perl runs each test in sequence and reports the results as ok, failed, or skipping test on this platform (this latter result applies to any operations that are not implemented on your particular system). At the end, Perl reports the number of successful and failed tests for your review. If the results are acceptable, you can proceed with the installation. ## Alpha and Beta Testing

Every test described up to this point is performed by internal staff, including the QA department, the people who develop the applications, and the administrators who maintain the systems. However, none of this internal testing assesses how the system or application will perform or be perceived in the real world. When your internal testing is complete (unit tests, load tests, regression tests, and any other tests you decide to perform), it's time to test the system with real users; these are the alpha and beta tests.

## Recruiting Users for Your Tests

User recruitment is the most critical part of alpha and beta testing. To recruit users, tell them of the test and offer an incentive for their participation. Typically, technically oriented and computer savvy users are the most likely to jump at the opportunity to test a new product. This type of user, however, might not represent the majority of your product's ends, especially in the world of ISPs.
