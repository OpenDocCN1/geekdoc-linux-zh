/backups 192.168.0.0/255.255.255.0(rw, sync)

This is a straightforward share for the /backups directory by the systems with the noted IP network address and subnet mask. The rw and sync mean that the share is read-write and reads and writes are done synchronously. Other options are shown in the main pages for the mount command and /etc/exports file.

Generally, NFS directories would rarely ever be exported with the noroot_squash option, as that would allow administrative access to the shared directory. That root user could be a local user on a system that has an IP address in the address range associated with the network address and subnet mask similar.

In contrast, if the packages for NFSv4 are installed, you can set up a server similar to the following, which authenticates specifically assigned by the Kerberos server:

```
/backups gss/krb5 (sync, rw)
```

Once configured on the NFSv4 server, users on Kerberos-authorized client systems will be able to connect to the server. Users would either need root administrative privileges or require appropriate configuration changes to the /etc/fstab file. These changes should include the krb55 option.

## Keeping vsFTP Very Secure

This section is an extension of Chapter 5, which addresses basic network permissions for the secure File Transfer Protocol (vsFTP) service. While many FTP server options are available, vsFTP server is used by Red Hat, SUSE, Debian, and the developers of the Linux kernel.

To review, the vsftpd configuration file is vsftpd.conf. The directory varies by distribution. For example, it's in the /etc/vsftpd for Ubuntu and the /etc/vsftpd/directory for Red Hat. If an option is not described in this server, review Chapter 5. For a full list of available vsFTP directives, check the Web site associated with vsFTP developers: http://vsftpd.beasts.org/.

## Configuration Options for vsFTP

For many users, a vsFTP server can be a terrific convenience. The FTP protocol is still perhaps the most efficient way to upload and download large files. But such a service comes with risks. To end that, you must regulate and isolate the directories where vsFTP stores files for anonymous uploads and downloads. The developers behind different Linux distributions configure any directory in different locations, such as /var/ftp/, /srv/ftp/, and /home/ftp/. The following directive sets up a specific directory for anonymous access to the vsFTP server:

```
anon_root = /secure
```

![](img/c0608a8c8a0777903dfec4ff61fdffa1_250_0.png)

Unless otherwise configured, vsFTP is actually run as one of the internet server services described in Chapter 7. It's safer to run vsFTP as its service, with its own control script in the /etc/init.d/ directory. Both Ubuntu and Red Hat versions of vsFTP make this possible with the following directive:

- listen = yes

If, however, the FTP server is to work on an Internet Protocol version 6 (IPv6) network, you could configure the following alternative directive. Just be aware that vsFTP won't work with both versions of the listen directive:

- ipv6 = yes

Frequently, administrators like you are responsible for transmitting corporate or organizational policies regarding the use of services like vsFTP. If the following directive is enabled, vsFTP looks for a hidden .message file in each directory unless overridden by a message_file directive.

- dirmarge_enable = yes

Given the popularity of many anonymous FTP services, logging information about uploads and downloads may be useful. It's activated with the xfer_log_enable directive shown next. While the default log file is /var/log/vsftpd.log, it can be changed with the xfer_log_file directive. If you do change the file in the /etc/logrotate.d/ directory; otherwise, the size of this file could easily overwhelm many systems.

- xfer_log_enable = yes

One option for uploads is to change the ownership of such files to a specific user, such as nobody or another user with minimal privileges. That can reduce the risk of an uploaded script or binary file that otherwise affects the security of the FTP server. Of course, this assumes user nobody is properly configured in the shadow password suite (or other database) with appropriate minimal privileges.

- chown_uploads = yes
- chown_username = nobody

If you want to specifically set a nonprivileged user, the following directive can help:

- priv_user = nobody

A couple of additional options can work sort of screensavers; the following options end the connection if no commands or additional file transfers are detected in the given number of seconds. Some administrators may prefer to reduce the value of the idle_session_timeout directive.

- idle_session_timeout = 600
- data_connection_timeout = 120

Generally, secure FTP servers do not allow connections based on the American standard code for information interchange (ASCII), as that can lead to denial-of-service (DoS) attacks.

## Additional vsFTP Configuration Files

Two other configuration files are used directly for the vsFTP service: ftpusers and user_list. The list of users in these service is based on the default set of service users. In other words, it includes users with user IDs (UIDs) below 100, 500, or 1000, depending on the distribution. If a black-hacker breaks into one of these accounts, he may be able to obtain administrative privileges (or more) through these accounts. These files can help prevent black-hackers from using these privileges at least on the vsFTP server.

If more services are installed on the local system, you may see additional service users in the shadow password suite. In that case, you should add those users to the appropriate files. Red Hat systems specifically cite /etc/vsftpd/ftusers in the pluggable authentication module (PAM) configuration file, /etc/pam/vsftpd.

> Security Enhanced Linux (SELinux) provides additional protection for vsFTP. Directories shared with FTP servers should be labeled with the public_content_t type. If you use a directory for uploads, you'll need to configure that directory with the public_content_rw_t type. The same options work for directories associated with rsync servers.

## Linux as a More Secure Windows Server

In Chapter 5, you will read how Linux can share specific directories using Samba. This section focuses on the global settings associated with Samba, including how it can be set up as a Primary Domain Controller (PDC), or its cousin, the Backup Domain Controller (BDC). With the right options, the PDC database of usernames and passwords can be maintained on a Linux server.

Samba is the Linux implementation of Microsoft's Server Message Block protocol. As this evolved into the Common Internet File System (CIFS), Samba has kept pace. As case generally does not matter at the Microsoft command line, the value given to most Samba directories can be upper or lower case. For example, security = USER works as security = user.

Not all Samba directives are described in this book. For a more complete list, see the Samba documentation at http://www.samba.org/samba/man/pages/3/conf.html. When Samba 4 is officially released, there will likely be some more added options.

Administrators who believe in Linux are likely to accept that a Windows system, if substituted for a Linux system, is more secure. Some professionals may disagree with that assessment. However, Linux systems maintained as PDCs are more secure, as Samba developers monitor and maintain services while Windows developers no longer do so.

> Because PDCs are on the Microsoft Windows NT 4 Server operating system, Microsoft has not supported PDCs on networks. However, PDC on Linux servers configured with the Samba server are still supported. As long as Windows XP clients are supported, Microsoft should support those systems as PDC clients. However, since this is a book on Linux, no claims are made with Microsoft security support.
