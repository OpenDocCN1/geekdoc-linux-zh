
Many hosts require relatively few iptables commands. For example,
a bastion host with a Web server that also supports SSH-based remote administration
could work with the following rules:

```bash
iptables -A INPUT -j RH-Firewall-1-INPUT
iptables -A FORWARD -j RH-Firewall-1-INPUT
iptables -A RH-Firewall-1-INPUT to -j ACCEPT
iptables -A RH-Firewall-1-INPUT -p icmp --icmp-type -j ACCEPT
iptables -A RH-Firewall-1-INPUT -m state
  --state ESTABLISHED,RELATED -j ACCEPT
iptables -A RH-Firewall-1-INPUT -m state
  --state NEW -m tcp -p tcp --dport 22 -j ACCEPT
iptables -A RH-Firewall-1-INPUT -m state
  --state NEW -m tcp -p tcp --dport 80 -j ACCEPT
iptables -A RH-Firewall-1-INPUT -j REJECT
  --reject with icmp-host-prohibited
```

If your systems support Internet Protocol 6 (IPv6) networking, be sure to
make similar changes to the associated configuration. On Red Hat systems, that file
is /etc/sysconfig/ip6tables.

From this point, the firewall becomes much more complex. Additional changes,
discussed next regulate different kinds of network packets in detail.

## Additional iptables Rules

The iptables rules listed at the end of the previous section may be too simple. Several
additional rules of interest may prevent denial of service (DoS) attacks, prevent attempts
to connect from private IP address blocks, and slow attempts to attack SSH services.
From the literature in the "References" section at the end of this chapter, you should
come up with additional rules for the local configuration.

Denial of Service Rules. Three rules that can prevent or at least slow DoS attacks
are described in the "Linux Packet Filtering HOWTO" available from http://www.iptables.org/documentation/HOWTO/packet-filtering-HOWTO.html. While the references there are
to the older Linux 2.4 kernel, the description associated with the iptables command
lies today.

The following command limits accepted tcp packets to one per second:

```bash
# iptables -A RH-Firewall-1-INPUT -p tcp
  --syn -m limit --limit 1/s -j ACCEPT
```

Incidentally, this command is no longer necessary. You can get equivalent
protection from a kernel setting. Just activate the boolean option in the
/proc/sys/net/ipv4/tcp_cookies file. In other words, change the value
of the file from 0 to 1).

Next, the limit connection attempts from port scanners:

```bash
# iptables -A RH-Firewall-1-INPUT -p tcp
--tcp-flags SYN,ACK,FIN,RST RST -m limit --limit 1s/s -j ACCEPT
```

Note how access is limited. In other words, this iptables rule accepts one packet with TCP flags per second.

Change Default Rules. The noted changes to default iptables commands may be for naught unless default rules for packets that are input and forwarded are changed. On a Red Hat system, examine the /etc/sysconfig/iptables file. The default as shown here for these packets is permissive

```bash
: ACCEPT [0:0]
: FORWARD ACCEPT [0:0]
```

These options should be changed to the following:

```bash
: INPUT DROP [0:0]
: FORWARD DROP [0:0]
```

Restrict the ping and Related Messages. The U.S. National Security Agency has specific recommendations on how to manage packets associated with the ping command, along with related packets associated with the ICMP protocol. Their first recommendation is to remove the rule from the minimal firewall configuration shown earlier:

```bash
iptables -A RH-Firewall-1-INPUT -p icmp
--icmp-type any -j ACCEPT
```

This rule accepts all ICMP packets, exposing the local system to so called "ping storms" of packets that deny service to others. The following alternatives legitimate responses when local users run the ping command:

```bash
iptables -A RH-Firewall-1-INPUT -p icmp
--icmp-type echo-reply -j ACCEPT
```

```bash
iptables -A RH-Firewall-1-INPUT -p icmp
--icmp-type destination-unreachable -j ACCEPT
```

```bash
iptables -A RH-Firewall-1-INPUT -p icmp
--icmp-type time-exceeded -j ACCEPT
```

The responses are implied by the packets attached to the --icmp-type switch: for example, echo-reply accepts ICMP messages that respond to a ping command. If you want to allow others to ping your system, with the limits, the following command rule limits responses to ping commands to one per second.

```bash
iptables -A RH-Firewall-1-INPUT -p icmp
--icmp-type echo-request -m limit 1/s --limit 1s -j ACCEPT
```

![](img/c0608a8c8a0777903dfec4ff61fdffa1_214_0.png)

If you don't have local systems to respond to ping command requests, substitute the following command rule:

```bash
iptables -A RH-Firewall-1-INPUT -p icmp
--icmp-type echo-request -j DROP
```

Block Information from Suspicious IP Addresses. When communicating on the Internet, if you identify a packet with a source IP address that should be on a private network, suspicious. Such addresses may be an attempt by a black-hat hacker to hide the identity of his system. To that end, secure firewalls will drop packets with a source IP address associated with private network, or any other address that should not be assigned to a regular system. For IPv4 addresses, such rules should include the following:

```bash
iptables -A RH-Firewall-1-INPUT -i eth0
--s 10.0.0/8 -j LOG --log-prefix "Dropped private class A address"
iptables -A RH-Firewall-1-INPUT -i eth0
--s 172.16.0/12 -j LOG --log-prefix "Dropped private class B address"
iptables -A RH-Firewall-1-INPUT -i eth0
--s 192.168.0/16 -j LOG --log-prefix "Dropped private class C address"
iptables -A RH-Firewall-1-INPUT -i eth0
--s 224.0.0/4 -j LOG --log-prefix "Dropped multicast address"
iptables -A RH-Firewall-1-INPUT -i eth0
--s 240.0.0/8 -j LOG --log-prefix "Dropped class E address"
```

If you set up IPv6, corresponding rules should be added to the corresponding configuration file.

Slow Attacks on SSH Sessions. With port scanners and a little work, a black-hat hacker should find it easy to identify open ports. That can be slowed down with the following:

```bash
iptables -A RH-Firewall-1-INPUT -i eth0 -p tcp
--dport 22 -m state NEW -j SSH_RULE
iptables -A SSH_RULE -i eth0 -p tcp
--dport 22
-m state NEW -m recent --update --seconds 60
--count 3 --name SSH -j DROP
```

![](img/c0608a8c8a0777903dfec4ff61fdffa1_215_0.png)

The first command specifies that the firewall jumps to to the SSH_RULE firewall rule. The second command limits the number of login attempts to three; after three failures, the external user has to wait 60 seconds to try again. That should discourage users who are just trying a few dictionary words with a typical username.

## The iptables Service

On Red Hat systems, there is an iptables service in the /etc/init.d/ directory normally started during the boot process. It reads options from /etc/sysconfig/iptables configuration file. On Ubuntu systems, when an iptables firewall is configured, additional configuration may be required to make sure the firewall starts during the boot process. The results may be similar. For example, the aforementioned ufw package also installs a ufw script in /etc/init.d/ .

If you prefer to create a custom firewall, you can use the iptables-save and iptables-restore commands. When applied to a specific file, these commands can save current rules and restore them from a given file. Such commands can be added to appropriate network configuration scripts to make sure the firewall is started during the boot process.
