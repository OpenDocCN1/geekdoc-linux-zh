# CHAPTER 14 Detecting and Responding to Security Breaches

# Best Practices: Security Breach Detection and Response

You need to plan in case of a security breach. It's best if you have a baseline system ready to go to take the place of at least one critical system on the local network. Of course, unless you know the cause of the breach, replacing a compromised system could prove foothold. If there's a flaw with the configuration of the system, you should update that gold baseline.

To understand when there might be a problem, regular performance audits are appropriate. Systems that deviate significantly from baseline performance with respect to CPU and RAM usage may suspect. Because you can't spend all day on watch, the system status tool can help. If an issue arises, commands like l1sof, ldd, and trace can help check processes.

Good security requires the cooperation of users. It helps security policies are kept as simple as possible. Appropriate policies with respect to users fall into the areas of physical access. Internet browsing, e-mail, and remote access. Even then, it helps to have educational materials available. While Linux users are generally more aware of computers, they may not realize that Linux systems can be infected and be carriers of malware for other operating systems.

Good security means you know who is logging into systems on the local network. Such information is available with commands like who and, and historically based on the auth and auth directives. In the associated log files, you can track access by administrative and remote users, along with administrative jobs.

As a security professional, you should monitor what is seen from user accounts. Downloaded packages and source code in user home directories may be signs of unauthorized changes from a regular user. Just as many may be the existence of executable files in user home directories. However, you may not want to prevent some users from setting their own scripts.

To plan for a security breach, when the cause is not obvious, you may need policies that support a temporary increased level of vigilance. Once a suspected system is identified, don't turn it off until you can copy volatile data such as the contents of RAM.

Part of the plan includes the tools, including live Linux CDs with forensic commands. Options such as the Sleuth Kit and Master Key Linux support to compromise systems from their CD/DVD drives. Once volatile data is recovered, various options are available to duplicate and diagnose issues on compromised hard drives.

When a Linux system issue arises, it's not always related to the configuration of a Linux system. It could be a physical security issue. If there is a confirmed problem, you'll need to identify compromised systems and if possible have gold substitutes in place. Backup and recovery tools such as dd and rsync can be used on compromised hard drives. And don't forget the tools and commands associated with reading encrypted filesystems.
