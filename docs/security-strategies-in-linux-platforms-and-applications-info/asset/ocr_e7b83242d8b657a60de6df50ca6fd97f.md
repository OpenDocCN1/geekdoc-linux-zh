# Make Sure SSH Stands Secure

Previous chapters included a number of references to SSH. In this section, you'll see how to best secure SSH clients and servers. One of the benefits of SSH is encryption. However, until an SSH connection is made, transmissions are still sent in clear. So a black-hat hacker may be able to determine that an SSH connection is being established and eavesdrop on any communications that take place before the user initiates the SSH connection.

In addition to using SSH to configure interactive username/password connections, you may also automate the SSH connection process through the use of public/private key pairs.

# The Secure Shell Server

The standard SSH server configuration file is ssh_config, in the /etc/ssh/ directory. It works well on its own. In most distributions, all you need to do is install the server with a package name opens-server and make sure it's running. You should be able to connect from a remote system with commands described in the next section on the SSH client.

# Port 2

Because SSH version 1 has known security weaknesses, most administrators encourage the use of SSH version 2. However, the default SSH server accepts both versions of SSH. Therefore, some sshd_config files limit access to SSH version 2 with the following directive:

```
Protocol 2
```

Assuming you accept the use of SSH version 2, other directives associate with SSH version 1 are ignored (and as such will not be covered here). The ListenAddress directive can limit the networks configured for SSH. For example, the following directive looks for and listens to network cards with the noted IP address:

```
ListenAddress 192.168.10.1
```
