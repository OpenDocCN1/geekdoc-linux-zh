
# Monitor Security Reports

Information associated with security reports on Linux was covered in Chapter 11. The developers behind various Linux distributions maintain security reports for all supported packages on their distributions. In general, when a security report is released, an updated package should be available for installation through standard repositories.

In principle, all security reports should be addressed. As discussed in Chapter 11, you might choose to avoid installing a security update if it affects a support contract, adversely affects a critical software application, or adversely affects important hardware. If you make that choice, the risks will continue until the update is installed. If that choice is related to the support level associated with third-party software, you could ask for help from the vendor firm. But it may say so.

If you choose to avoid the installation of an update, be sure to keep track of the security report. If an affected system is compromised, look at what happened. If the compromise matches the information listed in the security report, you are to reconsider the installation. If the issue is related to third-party software, you can go back to an alternative.

## Work Through Updates

Not all updates are security related. Some updates address bugs. Other updates may affect individual packages, or they may address the Linux kernel.

If you're responsible for a group of Linux systems, it may be appropriate to set up a dedicated repository. As discussed in Chapter 11, patch management supports the development of independent repositories, which can be based on libraries released by your preferred distribution. Red Hat Enterprise Linux (RHEL) supports mirrors of their repositories over networks. If you choose a custom group of updates—say, only for security—that group of packages can be organized into a unique repository.

## Recalibrate System Integrity

Every time there is an update, you'll need to test changes. Once verified, the next step is to update the baseline using an integrity-checking tool of your choice, as AIDE or Tripwire. That database documents the current state of any baseline. Deviations from that baseline are found in AIDE or Tripwire, which document unexpected changes to critical files.

## Redundancy Help Ensure Availability

When problems arise with a system, it's helpful to have a replacement available and ready for use. The problem could be simple, such as a failing hard drive or overloaded system.

## A Physical Baseline

Virtualization has some ways revolutionized the concept of baseline. Before virtualization, baseline meant stacks of hard drives, or at least images ready to be written to physical devices. But not all systems should be virtualized. Physical baseline are important too. For example, some administrators believe that the demands of database servers make them poor candidates for virtualization. Other administrators have similar beliefs with respect to suites such as Microsoft Exchange. Multiple virtual guests on a single virtual host do have latency with respect to Central Processing Unit (CPU); in other words, they are slower. The amount of latency, however, is highly debatable. So at least in the future, some enterprises will continue to use physical systems for dedicated services.

To end, baseline can still be stored as a virtual image. With the dd command, administrators can create image files from the hard drives of their choice. When new copies of the baseline are required, the dd command can also be used to duplicate that image to a new physical device. For example, the following command writes the golden.img file:

```bash
dd if=golden.img of=/dev/sdb
```

## Virtual Baseline Host

If you're taking advantage of virtual machines, baseline systems fall into two categories: virtual hosts and virtual guests. Virtual hosts are physical systems, typically configured with multiple and/or-core CPUs. Multiple virtual guests can run on each virtual host. Each virtual machine system is a guest. To understand the requirements for baseline virtual host, you need to get into the hardware requirements for different virtual guests.

## Hardware Requirements for Virtual Host

The following is a brief overview of how you can measure the hardware requirements for the virtual host and all virtual guests on that host. This section addresses basic requirements. For detail, refer to the documentation for the virtualization technology of your choice. Some of these options were briefly discussed in Chapter 2. As noted in previous chapters, major Linux distributions are moving toward the Kernel-based Virtual Machine (KVM) system.

## PART 3 | Building a Layered Linux Strategy

Conservatively, a virtual baseline includes sufficient RAM, CPU, and hard drive space for the maximum requirements of each component virtual machine. In practice, multiple virtual machines can share RAM and CPU. In other words, properly configured systems don't normally use all their allocated RAM and CPU; you can effectively configure multiple virtual machines to overbook RAM and CPU.

However, KVM does have the following limits with respect to hosts and guests:

- Virtual host—KVM can manage up to 256 CPU cores and 1 TB of physical RAM.
- Virtual guest—KVM can support virtual machines with up to 16 CPU cores and up to 256 GB of RAM.

In other words, baseline virtual hosts may require a large number of CPUs and a lot of RAM. But such requirements do not necessarily apply to local hard drive storage, as the space required for each virtual guest can be configured on remote storage systems including network attached storage (NAS), direct attached storage (DAS), and storage area network (SAN) systems.

To understand "overbooking," consider the following example. As you consider 10 virtual guests that require 512 MB of RAM each, Assume the virtual host requests 1 GB of RAM. In the most heavily loaded situation, the system would require about 6 GB of RAM.

If the virtual guests are properly configured, however, they'll need the maximum amount of RAM only. So it is possible that the noted configuration would work on a virtual host with only 4 GB of physical RAM. The hypervisor—also referred to as virtual machine monitor—supports sharing of available RAM and CPU resources by multiple operating systems. In the rare cases every virtual machine is at maximum capacity, the virtual host would use configured swap space.
