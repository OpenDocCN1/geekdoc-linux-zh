# Remember the Dynamic Data

With the chain of custody in mind, you're ready to use the techniques described earlier in this chapter to save any dynamic data on a suspect system. To recall, you'll want to save any data that might otherwise disappear when a computer is powered down. At minimum, all data in volatile memory, which is generally limited to RAM. If you have forensic tools that can also save data from the swap partition, by all means do. Otherwise, the live CD forensic tools earlier can be started without using the swap partition, and can therefore save that data after the computer and/or drive media are powered down.

And in the spirit of the chain of custody, you'll want to document every step taken to save that data.

# Preserve the Hard Disks

One approach is to boot the compromised system and a diagnostic system in a simple network. You should then be able to use the network connection to copy the volumes of the troubled system. Alternatively, you could use a live CD to copy data from a hard disk directly to an image file. Techniques described earlier were based on the use of dd and dd_rescue commands.

Once the image file is saved, it can be mounted with the loopback device. For example, if the image of the hard disk is saved as the evidence .img file, you can mount that file on an empty /test/ directory with the following command:

> Use the original hard disk of the compromised system in any analysis. Commands like dd and dd_rescue are designed to create a bit-by-bit duplicate of an original disk. Physical write blockers can protect the integrity of the hard disk as evidence. Use for a forensic toolkit is the SysAdmin Audit Security (SANS) Institute.

```
# mount -o loop image.img /test/
```

Alternatively, there are methods available to set such image files in virtual machines. When such machine is configured without an external network connection, it's another way to record and/or test the data on the systems in isolation.

# Disaster Recovery from a Security Breach

The response to a security breach depends on what happened. In general, you'll want to have baseline systems ready to go in case of a security issue. When appropriately configured, they can be put in place of compromised systems. Ideally, before you put that into place, you should determine whether there's a flaw in that baseline system.

When data is needed from compromised systems, that can be another matter. In that case, you need to know what has been compromised. During forensic analysis of a compromised system, you should be able to review the differences with the original configuration with tools such as AIDE or Tripwire. Reviewing the differences could help you identify what went wrong. It should identify files that have been changed or added by a black-hat hacker.
