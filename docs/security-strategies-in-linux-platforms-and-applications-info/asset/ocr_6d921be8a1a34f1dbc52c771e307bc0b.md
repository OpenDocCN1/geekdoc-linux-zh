# Share with Developers

In general, the developers behind open source software want to hear about any problems and successes with their software. In many cases, however, they are overwhelmed with requests. In such cases, developers frequently review messages on mailing lists to get a sense of user response to their work.

In addition, the developers behind many applications maintain online bug reporting tools. For Red Hat distributions, the Web site is https://bugzilla.redhat.com/. For Ubuntu distributions, the Web site is https://launchpad.net/. The developers behind many applications and services have their own bug reporting tools

In general, developers suggest that you share their databases before reporting a bug. It's quite possible that someone has encountered the same or a similar problem and has already reported it. If you monitor, you'll get a chance to add an e-mail address to the reporting list to help you monitor the status of the bug.

While the reporting systems vary, you'll generally need the following information to report a bug:

+   **Package name/version number**—To find the package name and version associated with a file, you can run the `rpm -qf` or `dpkg -S` commands with the path to the file.

+   **Applicable hardware**—The behavior of a package may vary with different CPUs.

+   **A descriptive summary**—Developers behind many distributions have to deal with literally thousands of bug reports. An accurate, descriptive summary can help draw appropriate attention to your problem.

+   **Steps to reproduce the bug**—To confirm the problem you're having, developers need to know what happened. If you can document the steps taken to reproduce the bug and encounter the condition a second time, developers will know that you are serious.

+   **Applicable log files**—Error messages frequently appear in log files. It is appropriate to include short excerpts in the main body of a bug report. Huge log files should not be copied verbatim. If appropriate, they should be included as an attachment to the report.

Sometimes, the reported bug is just a misunderstanding. Do not be offended if developer highlights your bug report as a duplicate of another. If it turns out you made a mistake by creating the bug, it should be no big deal. However, repeated false reports from the same user are frequently noticed. In other words, developers and others are less likely to respond to users who continuously "cry wolf."

# Share on Mailing Lists

When sharing a problem on mailing lists, it's helpful to use the same principles when reporting a bug. Make sure you've done appropriate research. Create a descriptive summary for a mailing list title. Cite the steps to reproduce the bug. As applicable, cite the package, version number, and associated hardware.
