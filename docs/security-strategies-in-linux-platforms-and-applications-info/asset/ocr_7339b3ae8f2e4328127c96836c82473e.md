5. Set up a checksum file with a command like md5sum or sha1sum so others can verify the integrity of the file.

6. Repeat the process with the current hardware and kernel routing tables, using the arp -n route -Cn commands on the mounted forensic CD/DVD. It should document all connections from the troubled system.

7. Get the same information for network connections and associated processes with the netstat -atump command.

8. Now you'll review the process in detail, with the current contents of the RAM, as connected to the /proc/kcore file. So once again, use the netcat command, nc, to open communications from a remote system listening (-1) on a specific port such as 11111:

```
(diagnostic system) # nc -l 11111 > kernel_core
```

9. Use the dd command from the forensic CD/DVD on the troubled system to dump the contents of the kernel core: when coupled with the nc command, information can be forwarded to the remote listening system, with a timeout of 3 seconds (-w 3).

```
(troubled system) # /media/cdrom/dd < /proc/kcore
~/media/cdrom/nc diagnostic_ip_address 11111 -w 3
```

10. Set up a checksum file with a command like md5sum or sha1sum in the /proc/ directory, especially modules.

11. Repeat the process with the key files in the /proc/ directory. List other dynamic files from the /proc/ directory in Table 14-1.

12. Get a list of current processes and associated files with the output of the lsof -npl command. This keeps IP addresses, port numbers, and UID numbers in numeric format. In other words, they're not converted to hostnames, protocol names, and usernames. Of course, get the standard perspective of currently running processes with the ps ax ps a1 commands

13. Get a copy of currently mounted filesystems from the /etc/mtab file, along with the filesystems that should be mounted from the /etc/fstab file. If there's a difference between the list of mounted filesystems and the list of filesystems that should be mounted during the boot process, that may be worth investigating.
