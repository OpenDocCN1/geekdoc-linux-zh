# A BIND Database

A standard authoritative BIND database should include records for all IP addresses on a domain. Such records are stored in what as zone files.

If the functionality of a DNS server is split as described earlier in stealth configuration, you will see two zone file databases. One database, for the DNS server within the internal network, would include IP addresses for all systems on the network. The second database, for the authoritative only DNS server in the DMZ, would include the the information required for communications from outside systems. Specifically, that database would include the IP address of any other DMZ DNS servers, any other public servers such as Web servers, and any e-mail servers for delivery.

# DNS Targets to Protect

To summarize, when configuring an authoritative DNS server for a public system, you will protect zone files and zone updates, as well as cache poisoning. These are three different concepts explained in previous sections.

- Zone files—A complete zone file would include hostnames and IP-address data on all systems on the local domain, a database of systems from which a black-hat hacker can pick and choose for attacks. Public zone files should be limited to that information required for Internet communications, including Web servers and e-mail servers.
- Zone updates—Slave DNS server relies on a master DNS server for data. A black-hat hacker who is able to configure a slave DNS server could get the network DNS data.
- Cache poisoning—Data forwarded from DNS servers maintained by black-hat hackers could redirect your customers to malicious web sites.

# Mail Transfer Agents: sendmail, Sendmail, Postfix, and More

The alphabet associated with many Linux services continues with various e-mail services. E-mail client applications such as Evolution and Thunderbird are known as mail user agents (MUAs). Services such as fetchmail collect e-mail from networks are known as mail retrieval agents (MRAs). E-mail services that send mail along to client applications are known as mail delivery agents (MDAs). When e-mail client send messages for delivery, they use mail transfer agents (MTAs) such as sendmail, and Postfix.

![](img/c0608a8c8a0777903dfec4ff61fdffa1_292_0.png)

Yes, there is a difference between sendmail and Sendmail. The lower-case sendmail application is the open source MTA that is installed by default on Red Hat systems. it's an open source project sponsored by the Sendmail consortium. The upper-case Sendmail application is a commercial product used by enterprises; for example, it's the MTA engine behind Google's Gmail.

Sometimes, mail submission agents (MSAs) are integrated with MTAs in services such as sendmail and Postfix. When MSAs and MTAs work together, the MSA can focus on authenticating users and the MTA can prevent relaying from users who don't have local e-mail addresses.

In any case, MTAs such as sendmail and Postfix are configured primarily for the Simple Mail Transfer Protocol (SMTP) and the submission protocol on ports 25 and 587, respectively, MDAs as Dovecot can be configured to manage traffic using the Post Office Protocol version 3 (POP3) and the Internet Message Protocol (IMAP), along with the related protocols in their names: POP3S and IMAPS.

# Source sendmail

The open source sendmail MTA is the default outbound e-mail for any Linux distributions. When installed, configuration files can be found in the `/etc/mail/` directory. Because the main configuration file (`sendmail.cf`) includes nearly 2,000 lines, it's a highly customizable system. But the main configuration file is so large, it intimidated many Linux administrators. Complexity can be a drawback to security. If you don't understand a security update, the changes you make to the sendmail software may not address the security issue.

Complexity led to the development of the sendmail macro configuration file, `sendmail.mc`. It's written in a format that is easy to explain. The `dnl` directives in that file are comment characters. All information after the `dnl` on a line is ignored. Some important security-related directives from the default version of the configuration file are described here. First, any you include directives the contents of the filename described.

Next, the VERSIONID directive provides a comment on the file. In some cases, it may be based on the actual version of the released sendmail software, which is something that you want to avoid providing a black-hat hacker. To that end, the following directive may be:

```
VERSIONID(`setup for linux')`dnl
```

One odd format in sendmail configuration files is the quotes. Such quoted directives have a back quote (````) at the start and a regular single quote (`'`) at the end of the quote. Any define options that follow specify parameters such as files or limits. For example, the following directive specifies the name of the file with user aliases:

```
define(`ALIAS_FILE`, `/etc/aliases')`dnl
```
