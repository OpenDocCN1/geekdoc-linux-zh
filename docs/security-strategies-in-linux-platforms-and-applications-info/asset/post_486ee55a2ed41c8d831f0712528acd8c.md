## Distribution-Specific Linux Kernels

For most users, it's best to stick with the binary kernel released for a Linux distribution. That distribution-specific kernel has been compiled and built with the intended hardware in mind, and in many cases has been labeled as such. For example, the standard kernel for Ubuntu's Server Edition has a name with -server extension, such as vlinux-2.6.31-14-server. If the kernel is not needed, it may be optimized for certain purposes—for example, high availability or database systems.

When security issues appear with a Linux kernel, most popular Linux distributions release updates fairly quickly. They do the work to compile the kernel for you. Your compiled kernel packages will even automatically update Linux boot loaders. All you need to do is download and install the updated kernel.

## Custom Linux Kernels

If you choose to customize a Linux kernel, you'll need to get into its nuts and bolts. In Chapter 10, you'll discover that the Linux kernel is quite customizable. A standard Red Hat Enterprise kernel includes about 3000 different kernel options. If you want to preview some of these options, look for a config file in the /boot directory of a Linux system. It is a text file. These options are divided in a number of categories. One standard customization is shown in Figure 2-1.

## Linux Kernel Options

Linux kernel security options range far and wide. Direct options may enable features such as AppArmor, SELinux, and iptables-based firewalls. Indirect options may make it easier for malicious users to break into your systems, as listed in Linux HOWTO, include the following:

- CONFIG_FIREWALL for network firewalls
- CONFIG_IP_MASQUERADE for IP address masquerading to help protect your systems on a LAN
- IP_FORWARDING to set up a system as a gateway

These are just a few of the options described in Chapter 10.

## Security in the Boot Process

In Chapter 3, you'll read about security challenges associated with the boot process, starting with the server room. These challenges include the ways a malicious user can boot a fully functional version of Linux on your servers from a live CD with root administrative access. Even without a live CD, some distributions allow a user to boot Linux with full administrative privileges—without a password. For the purposes of this chapter, the boot process ends once the Linux kernel is loaded on the system. As you'll see in the next major section, the startup process continues by loading preconfigured services.

## Physical Security

Physical security goes beyond locks in the server room. It also involves security for CD/DVD drives and universal serial bus (USB) ports. While a live CD may in some cases be an excellent way to recover from problems on a server or workstation, access to such systems should be limited. Live CDs provide password-free access to the administrative account. Therefore, a malicious user with a live CD may be able to do anything that an administrator can do to your system.

## The Threat of the Live CD

> NOTE
> While the live CD is an excellent option for some system rescues, many distributions leave options known as rescue or recovery mode through their installation CDs. Generally, it's best to solve boot problems with the rescue mode from that distribution's installation CD. On the other hand, some live CDs even include security tools that can be used by white-hat hackers to test or by black-hat hackers to break into a system. For more information, see Chapter 13.

It's not enough to set up usernames and passwords on your systems. A black-hat hacker with physical access may be able to boot a live Linux distribution such as Kali, Ubuntu, or CentOS directly on your servers. It doesn't matter if the Linux distribution differs from that on the hard drive. It also doesn't matter if the Linux kernel on the CD has a different version number. Many live CDs provide a graphical interface (GUI), making it relatively easy for less-experienced black-hat hackers to break into your system.

All that's needed is boot access from a CD/DVD drive or USB port. Once booted, a live CD provides-free administrative access to any system. At that point, it's easy to access hard drives on the local system.

## Boot Process Security

> NOTE
> Of course, a black-hat hacker could disable BIOS/UEFI passwords by removing the associated battery. That's one reason many servers can and should be locked. Anyone with physical access to your systems may be able to access boot menus, such as those available through a BIOS or UEFI menu. These menus should be password protected. Network access to the UEFI menu should be disabled. If possible, these menus should be used to exclude all options but the hard drive with the operating system from the boot process.
