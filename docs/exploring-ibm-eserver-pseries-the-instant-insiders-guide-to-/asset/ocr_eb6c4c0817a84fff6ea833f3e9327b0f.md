A single application program can be designed and tuned to an SMP architecture that it will subdivide and run on multiple processors in the SMP system at the same time (App1a and App1b in Figure 1.32). However, this takes special design and coding on the part of the programmers, so today, more often than not, programs will be left to run as much as they do on a uniprocessor (App2 and AppN), not that this is bad (indeed, SMP systems allow many of these independent applications to run at the same time, each scheduled to a single CPU). However, in this example, App should be able to achieve greater overall throughput than it had been limited to a single processor. Often this throughput is well worth the coding effort for database developers. If you are purchasing a database, however the development and tuning has already been done for you. Often, database users will be able to bring forward all of their investment in queries, screens, reports, and so on. They may require only a minor modification or recompilation when moving the uniprocessor version of the database to the SMP version.

As one might expect, this architecture, which processors are running independent (App2 and AppN) or coordinated (App1a and App1b), can lead to several bottlenecks in performance as programs contend for vital resources such as memory or disk storage. Additional complexities develop as processors start to cache data. Let's go back to our example in which variable X, stored in main memory, has been modified by App1a and is still resident in the cache of CPU1. Now App1b needs to read variable X, CPU2 must now talk to each other and main memory to be sure to get the correct value of variable X into the cache on each processor. The coordination of current versus stale data between processors is known as cache coherency and is a prerequisite for a chip design to be considered for use in an SMP system. All the processors used in pSeries systems are cache coherent.
