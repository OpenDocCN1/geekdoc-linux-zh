# Exploring IBM @serverpSeries

High Availability Cluster Multiprocessing configurations with more than two pSeries systems are possible. The HACMP program can support up to 32 servers per cluster. Because the HACMP program allows the user to define (through AIX shell scripts) the actions to be taken in the event of various failures, configurations can be tailored to specific environments. The High Availability Subsystem component of the HACMP program provides base services for cluster membership, system management, cluster configuration integrity and control, and base recovery services for failover and recovery. The current Resource Manager component provides shared access to disk, file system, network, or application services.

HACMP configurations can be built with a number of different networks (Ethernet, Token-Ring, ATM) and using either SCSI or SSA disks (Chapter 2). Recent enhancements to HACMP increase availability further allowing system administrators to reconfigure cluster resources making the cluster unavailable.

# HACMP/XD (Extended Distance)

HACMP/XD, an optional feature of HACMP Version 5.1, provides long-distance data mirroring, fallover, and resynchronization. HACMP/XD allows widely separated pSeries systems to operate in a fashion similar to that just described. It provides real-time mirroring of user data between systems connected by local or long-distance networks, bringing a complete disaster recovery capability to a pSeries cluster placed in two widely separated geographic locations. Support for IBM Enterprise Storage System (ESS) peer-to-peer remote copy (PPRC) means that HACMP supports failover of disks that are synchronous pairs within an ESS unit, as well as between physically separate disk storage subsystems. HACMP/XD's support for IP (Internet protocol) based mirroring provides data mirroring across unlimited distances. Figure 4.9 shows a conceptual model.

Data mirroring with HACMP/XD can be synchronous, ensuring real-time data consistency, or asynchronous, for maximum performance while maintaining sequential data consistency. In a synchronous configuration, the data is written first to the remote site, then the local site. No input is handled until both writes complete. With asynchronous mirroring, the data is written first to the local site, then to the remote site. Input can continue at the local site while the previously entered data is being mirrored.
