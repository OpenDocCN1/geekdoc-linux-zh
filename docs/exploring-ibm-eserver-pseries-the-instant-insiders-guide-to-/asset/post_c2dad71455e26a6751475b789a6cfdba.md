
We also see that even for pSeries that use the same POWER4+ processor speed, the benchmark results are not exactly equal. For example, compare the 1.45 GHz p630 and p650 or the 1.7 GHz p655 and p690. These variations may be due to system designs or compiler variants.

Since the SPECint2000 and SPECfp2000 benchmark programs do not provide meaningful data for comparing SMP systems, the council developed a benchmark called SPECrate. For SPECrateint2000 and SPECfp2000, several copies of a given benchmark may be executed. This method is particularly suitable for multiprocessor systems. The results, called SPECrate, explain how many of a particular type can be executed in a given time. SPECrate_int2000 is a geometric average of the 12 SPEC rates from SPEC integer tests (SPEC2000). SPECrate_fp2000 is the geometric average of the 14 SPEC rates from the SPEC floating-point tests (SPECfp2000). Because of the different units, the values of SPECint2000 and SPECrate_int2000 and SPECrate_fp2000 cannot be compared directly.

Let’s summarize to this point. The SPEC currently supports the 2000 version of its suite. It contains both floating-point and integer workloads, which run on an SMP system, must be calculated differently, yielding “rate” measurements.

In 1995, the SPEC council implemented another variation of its benchmark called the SPECBase. Again, there are both floating-point and integer versions, along with wide rates for SMP systems. Remember that the SPEC benchmarks are actually a collection of programs. These programs get compiled on the pseries system and are executed. Here’s where the SPECBase allows only a limited set of compiler options when IBM, or any other vendor, compiles the programs that make up the benchmark. For example, no preprocessors are allowed that scan the source code looking for particular types of loops. Therefore, SPECBase removes any advantages that a vendor might have in its compiler technology. This gives the user a bit more of an apples-to-apples hardware stick to use when comparing hardware from different vendors.

In summary, SPEC started with SPECint and SPECfp. SPEC then added the “rate” designation for SMP systems. Finally, the “base” indicates of only a limited set of compiler directives. All of this yields different performance measurements that are available for the comparison of pSeries systems among themselves and with competitive systems.

## IBM @serverSeries—An Overview 77

In most commercial environments, one finds application programs such as order entry, accounts payable, accounts receivable, and so on. In these environments, pSeries systems are usually shared by more than one user in a local area network configuration involving PC workstations. Commercial applications typically move large amounts of information between disk storage and main memory. To evaluate the relative performance of the various pSeries models and other selected computers, the Transaction Processing Performance Council has several benchmarks that can be used.

The primary benchmark for comparing on-line transaction processing performance is called TPC-C. It measures such factors as interactive response time and system throughput and the overall workload that the system can handle. The TPC-C unit of measure is expressed as transactions per minute (tpmC). TPC-C is intended to simulate a "real-world" order entry environment, with mix of read-only and update-interactive transactions. It relies on a relational database and uses client/server configurations.

Figure 1.23 shows the tpmC ratings for few pSeries servers. It is a requirement of the council that the $/tpmC be shown with the format. A result can’t just advertise some huge tpmC result without also telling how much power costs. The $/tpmC metric is the rated price/performance of a system’s five-year cost of ownership, which includes hardware, software, and maintenance divided by the throughput, tpmC. Both tpmC and $/tpmC may be freely compared with published TPC-C metrics of both systems, both IBM and non-IBM. Since benchmarks do change occasionally, one must be careful to compare within the same value of a given benchmark. The current TPC-C benchmark is Version 5; comparisons between systems different TPC-C versions are not valid. All of the results in Figure 1.23 are Version 5 of the TPC-C.

Referring to Figure 1.23, it is clear how technology is improving and how rapidly prices of UNIX servers are coming down. But the price per tpmC is about 70% less. This significant advantage occurred in two years and is indicative of the rate of technological development and the impact of market forces.

## A Closer Look 79

Many elements together provide the functions and performance of pSeries computers. Not only must each element be highly efficient, but each must be able to “keep up” with all other elements that make up the computer system. It doesn’t matter how fast a processor is, for example, the I/O subsystem is the “bottleneck” that limits the overall speed at which the computer can perform work. A high-speed Fibre Channel adapter will be handicapped if the expansion slot in which it resides is unable to keep up with information flow rates. pSeries designers use computer modeling and other tools to simulate various design approaches with the goal of achieving computer systems with balanced performance.
