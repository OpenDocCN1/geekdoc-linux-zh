"Availability" is a term used to describe the degree of access a computer user has to a computing resource. For example, an environment in which the users are frequently prevented from logging on to a computer system because of computer system failures, communications network failures, scheduled maintenance, or any other reason is said to have poor availability. An environment in which the needed computing resources seem always to be available to the users is said to have very good availability.

Now let's consider a LAN environment in which we have one server and a group of client computers/users that rely heavily on the server. These clients might be workstations or a network computer that cannot perform any useful work without the server's help, or might be workstations that frequently need the server's help to do useful work. If the server has a hardware or software failure, the server goes down. When the server goes, the users are immediately and unexpectedly unable to do useful work until the server is fixed.

The degree of pain felt when a group of users is interrupted varies widely from one environment to another. If the users are simply doing word processing, being down for four hours might not be a problem, because the letters can go out in tomorrow's mail rather than today's. However, if the LAN is supporting the front desk of a large resort hotel, for four hours of downtime mean hours of delay for check-ins, check-outs, reservations, wake-calls, and room service—and a hotel full of angry guests. When you are selecting and configuring servers in a LAN, you must consider the availability requirements of the environment.

Many things have been done in the design of both hardware and the AIX operating system to maximize the reliability and availability of pSeries systems. Still, computer systems fail, and it is difficult to predict exactly when the failure will occur—and, of course, there is always the risk of software errors in the applications being run that could cause system outages. If failures are critical to the particular business being served, steps should be taken to increase the availability of computer resources. There are two basic techniques or approaches to increasing the availability of LAN resources: Rely on a specially designed fault-tolerant computer that has redundant hardware elements, or make the resource available from more than one computer in the LAN. Now let's see what happens when one of the pSeries systems (server A) fails. When server A fails, the HACMP program in server B detects that the HACMP program in server A has stopped its periodic messages. First, server B tries to contact the alternate Ethernet adapter in server A in case the problem is simply a failure in the primary Ethernet adapter. If connection is reestablished between the two servers via server A's alternate Ethernet adapter, then no further action is required. However, let's say server A has a complete system failure. In that case, when server B finds that it cannot reestablish communication with server A, server B automatically takes over for server A. First, server B programs its alternate Ethernet adapter to assume the identity (network address) of server A's Ethernet adapter. Thus, all communications intended for server A will not automatically go to server B. Then, server B takes control of server A's disk drives in the 2104. This allows server B to make the database of server A available to the LAN clients normally assigned to server A. In effect, server B becomes server A and the clients on the network get uninterrupted access to the resources of both servers (high availability). In fact, except for short “stall time” as the switchover is made, the clients know that server A failed.

This is one simple example (mutual takeover) of how HACMP configurations can be used to improve the availability of LAN resources in the event of server failure. The AIX mirroring function described in Chapter 3 can be used in conjunction with HACMP configurations to automatically respond to a disk drive failure by switching to an up-to-date copy of the information on another drive.

The HACMP software can also be configured so that both systems access the same data concurrently (concurrent access). Refer to Figure 4. With concurrent access, both server A and B would access a single database residing on the 2104's disk drives. This can provide a higher level of performance than a single server might deliver. This can impose overhead that can lower the overall performance of the cluster. A concurrent access cluster can provide very fast takeover for a failing server because the same data is available via a different server to all client machines.

High Availability Cluster Multiprocessing configurations with more than two pSeries systems are possible. The HACMP program can support up to 32 servers per cluster. Because the HACMP program allows the user to define (through AIX shell scripts) the actions to be taken in the event of various failures, configurations can be tailored to specific environments. The High Availability Subsystem component of the HACMP program provides base services for cluster membership, system management, cluster configuration integrity and control, and base recovery services for failover and recovery. The current Resource Manager component provides shared access to disk, file system, network, or application services.

HACMP configurations can be built with a number of different networks (Ethernet, Token-Ring, ATM) and using SSA disks (Chapter 2). Recent enhancements to HACMP increase availability further making the cluster.

## HACMP/XD (Extended Distance)

HACMP/XD, an optional feature of HACMP v5.1, provides long-distance mirroring, fallover, and resynchronization. HACMP/XD allows widely separated pSeries systems to operate in a fashion similar to that just described. It provides real-time mirroring of user data between two separated geographic locations. Support for IBM Enterprise Storage System (ESS) peer-to-peer remote copy (PPRC) means that HACMP supports synchronous pairs within an ESS unit, as well as physically separate disk subsystems. HACMP/XD's support for IP (Internet protocol) based mirroring provides data mirroring across unlimited distances. Figure 4.9 shows a conceptual model.

Data mirroring with HACMP/XD can be synchronous, ensuring real-time data consistency, or asynchronous, for maximum performance while maintaining sequential data consistency. In a synchronous configuration, the data is written first to the remote site, then the local site. No input is handled until both writes complete. With asynchronous mirroring, the data is written first to the local site, then to the remote site. Input can continue at the local site while previously entered data is being mirrored. Each site in this geographic cluster can be a single system or multiple systems, with the entire geographic cluster containing no more than eight nodes.
