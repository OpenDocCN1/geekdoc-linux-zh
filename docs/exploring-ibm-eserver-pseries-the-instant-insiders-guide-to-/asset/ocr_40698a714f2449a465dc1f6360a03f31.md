Now let's see what happens when one of the pSeries systems (server A) fails. When server A fails, the HACMP program in server B detects that the HACMP program in server A has stopped its periodic messages. First, server B tries to contact the alternate Ethernet adapter in server A in case the problem is simply a failure in the primary Ethernet adapter. If connection is reestablished between the two servers via server A's alternate Ethernet adapter, then no further action is required. However, let's say server A has a complete system failure. In that case, when server B finds that it cannot reestablish communication with server A, server B automatically takes over for server A. First, server B programs its alternate Ethernet adapter to assume the identity (network address) of server A's Ethernet adapter. Thus, all communications intended for server A will not automatically go to server B. Then, server B takes control of server A's disk drives in the 2104. This allows server B to make the database of server A available to the LAN clients normally assigned to server A. In effect, server B becomes server A and the clients on the network get uninterrupted access to the resources of both servers (high availability). In fact, except for short “stall time” as the switchover is made, the clients know that server A failed.

This is one simple example (mutual takeover) of how HACMP configurations can be used to improve the availability of LAN resources in the event of server failure. The AIX mirroring function described in Chapter 3 can be used in conjunction with HACMP configurations to automatically respond to a disk drive failure by switching to an up-to-date copy of the information on another drive.

The HACMP software also be configured so that both systems access the same data concurrently (concurrent access). Refer to Figure 4. With concurrent access, both server A and B would access a single database residing on the 2104's disk drives. This can provide a higher level of performance than a single server might deliver. This is especially true when you consider up to eight systems share disks. However, database applications on the servers must coordinate (via locking) their activities on the shared database. This can impose overhead that can lower the overall performance of the cluster. A concurrent access cluster can provide very fast takeover for a failing server because the same data is available via a different server to all client machines.
