# ## Terminating a server process

The C code used for sending is `killProcess` (available in FileSys along with other scripts for this tutorial). The calling process has a signal handler; this feature ensures it stops once it receives the USUSR - with the help of a signal handler; additionally, it increases the counter every time it receives the HIGHUP signal.

The script writes the PID in the `/tmp` directory to find it - it is also logged in a locked file of the process. With the help of the locking file, we can make sure that only one instance of the server is running at any time.

The C code implements here for the purpose of writing the log file:

```
#define LOGFILE "/tmp/1.pid"
#define SIGHUP (SIGUSR1)
int fd = open(LOGFILE, O_RDWR|O_CREAT, 0644);
char buffer[32];
if (fd < 0) {
    exit(1);
}
truncate(fd, 0);
sprintf("%d", getpid());
write(fd, buffer, strlen(buffer));
close(fd);
```

You should be familiar with the presented code if you've been following the tutorials in our Programming series.

# ## Log files

This part will teach you how to send information from a server to the syslog service and to log files. Despite the obvious fact that it is good to keep log files, log files are necessary for server processes because there is no other way for a proper server to send information to the outside world, as it has no terminal to send output.

As you might have guessed, there are system calls that will help you: open takes three parameters and returns a connection to the system logger for a process. Please see its

man for more information about its parameters. Although the call to `open()` can be omitted, it is highly recommended to use it. The `close()` function closes a previously opened connection to the system logger. The `syslog()` call allows you to create a new log message which is distributed by the syslog service for delivering and writing log messages. There is also `syslog3()` which is improved and more reliable version of `syslog()`. All three systems mean that the priority and message can be set via `setlogmask()` system call which calls `syslog()` to be logged and returns the process log priority. If you use log files, they can be used if you are not developing server processes. Generally, using a log file is better than writing out to screen for two reasons: because the output does not get lost and free to print important and output on screen if you need it. Another side effect is that you can use various tools like grep and awk, which cannot be done when messages are printed on a terminal window. You can see an example with the firstのである functions acting in action.

# ## Running a process in the background

If you put a special command (@) at the end of the command the shell will automatically execute the command in the background. Additionally, the shell will finish and return the prompt with a return status of 0. This is bad if you need the shell that was used for executing the command, to complete or wait. Another unwanted side effect is that the original process might be terminated asynchronously.

The hook invokes it with its arguments and sends the SIGHUP signal to it. If you combine name with hup then you can run the command in the background. When you log out, the command continues running. The process is handled by the background. Linux then allows the process to complete or run in the background.

Despite this, it is a better practice to design and develop a program from the server without commands. This method is not necessary here. You can use the job command to get a list of all processes running in the background of the current session.
