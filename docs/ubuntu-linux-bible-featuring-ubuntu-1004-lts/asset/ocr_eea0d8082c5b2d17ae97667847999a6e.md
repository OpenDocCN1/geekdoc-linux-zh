The design and implementation of RPCs make NFS platform-independent, interoperable between different systems, and easily ported to many computing architectures and operating systems. RPCs are a client/server communication method that involves issuing RPC calls with various parameters on client systems, which are actually executed on the server. The client doesn't need to know whether the procedure is being executed locally or remotely—it receives the results of an RPC in the same way that it would receive the results of a local procedure.

The way in which RPCs are implemented is extremely clever. RPCs work using a technique called marshalling, which essentially means packing all of the arguments to the remote procedure in a mutually agreed-upon format. This mutually agreed-upon format called External Data Representation (XDR), provides a sort of "Esperanto" that enables systems with different architectures and byte-orders to safely exchange data with each other. The client's RPC subsystem then sends the system-independent packet to the appropriate server. The server's RPC subsystem receives the packet and unmarshals it to extract the arguments to the procedure in its native format. The RPC subsystem executes the procedure locally, marshalls the results into a return packet, and sends this packet back to the client. When this packet is received by the client, its RPC subsystem unmarshals the packet and sends the results to the program that invoked the RPC, returning this data in the same fashion as any local procedure call. Marshalling and unmarshalling, plus the use of the common XDR data representation, make it possible for different types of systems to transparently communicate and execute functions on each other.

RPC communications are used for all NFS-related services, including communications related to the authentication services used by NFS (the Network Information System, NIS or NIS+), mount requests, status information, and requests made to the NFS daemon daemon. To enable clients to contact so many different services without requiring that each client communicates through a specific, well-known port, NFS lets services dynamically bind to any port as they register with their central coordination service, the portmapper daemon. The portmapper always runs on port 111 of any host that supports RPC communications and serves as an electronic version of directory assistance. Servers register RPCrelated services with the portmapper, identifying the port that the service is listening on. Clients contact the portmapper to determine the port that they are looking for.

Communication failures occur with any networked communication mechanism, and RPCs are no exception. As mentioned at the beginning of this section, UDP does not provide delivery guarantees or packet sequencing.
