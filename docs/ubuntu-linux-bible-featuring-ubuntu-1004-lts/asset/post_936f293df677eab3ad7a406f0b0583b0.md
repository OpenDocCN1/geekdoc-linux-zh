
# Part III: Ubuntu for System Administrators

If your BIND server does not start correctly, the first place to look for information is the system log file on your Ubuntu system, /var/log/syslog. By default, BIND logs a variety of events to this file when you start or the named process, when events such as file reloads occur while the named process is running, and so on. A sample section of the /var/log/syslog showing BIND messages is as follows (I removed the timestamp and host information that would normally begin each line):

```
named[20897]: starting BIND 9.3.2 -u bind
named[20897]: found 1 CPU, using 1 worker thread
named[20897]: loading configuration from /etc/bind/named.conf
named[20897]: /etc/bind/named.conf:60: missing ';' before end of file
named[20897]: loading configuration: failure
named[20897]: exiting (due to fatal error)
```

In this case, you can see that there is a missing semicolon on line 60 of my named.conf file. After correcting one error in a configuration file, you usually want to check the configuration file again, to make sure you've eliminated all of the errors, not just one. The Ubuntu bind package includes a utility called named-checkconf that does just this. Running this utility provides an easy way of checking the syntax of a BIND configuration file without restarting the named process over and over, checking the log time, fixing one problem or the other, and so.

The following is another common message that you may see in /var/log/syslog:

```
named[20222]: zone vonhagen.org/IN: loading master file: not found
```

Oddly, the fact that the zone vonhagen.org could not be found is not a fatal error, so the BIND server is running—it just isn't providing any name information for the vonhagen domain. Aside from syntax errors in the filename, the most common cause of this error message is forgetting to provide the full pathname for an included file. As mentioned previously, BIND on Ubuntu systems is configured to use the directory /var/cache/bind as its working directory. It will look for files without full pathnames in that directory instead of looking in /etc/bind.

The named-checkconf file checks the syntax of your /etc/bind/named.conf file and other configuration files that it includes does not validate the contents or syntax of your zone files. Luckily, Ubuntu's bind package includes another utility, named-checkzone. Although it provides several options, the most common way of using the named-checkzone is to provide its two mandatory arguments: the name of the zone that a file describes, and the name of the file that describes that zone. This can be a standard zone file or a reverse lookup file because both of these are different types of zone files that have logical purposes and contexts. Sample error output from running this utility follows:

```
# named-checkzone vonhagen.org vonhagen.zone
dns_data_fromtext: vonhagen.zone:8 near '*': extra input text
vonhagen.org/IN: loading master file vonhagen.zone: extra input text

# named-checkzone 168.192.in-addr.addr 168.192.in-addr.addr
168.192.in-addr.addr/11: unknown RR 'ubuntu32.vonhagen.org.
168.192.in-addr.addr/IN: loading master file: unknown class/type
```

# Chapter 32: Setting Up a DNS Server

Don't worry—I mangled copies of these files to illustrate common errors! The ones showed earlier in this chapter are still valid.

The first error, "extra input text," indicates a parser error when trying to read one of the records in this file—in this case, the SOA record. To generate this error message, I removed the closing parenthesis in the SOA record, which causes the parser to continue on to the next line and report that it found, unexpected text in the next line which began with an @ symbol.

The second error, "unknown RR type 'ubuntu32.vonhagen.org' and "unknown class/type," are somewhat more insidious. These also indicate parser errors in reading one of the records, in this case on line 11. This is the name server declaration in my reverse lookup file. As I mentioned earlier in this chapter, the DNS parser is very finicky. Although it is clever about using default values whenever, you still have to be careful about how you use white space in the file. In this case, I had removing the leading @ symbol and deleted all of the white space at the beginning of this record, so that the IN was at the beginning of the line, without any white space preceding it, which was interpreted as the root name of my name server, the NS entry was used as the record, and the name of my server, ubuntu32.vonhagen.org, was interpreted as a record type specification. Attempting to resolve this problem also displayed the message "zone 168.192.11.addr.arpa/no NS records," which was caused by a similar parser error that I stumbled over to route to a valid name server.

Trying to resolve parser errors in zone files can be frustrating. Worst case, you can fall back to providing an explicit value for every possible field, verifying that the file works, and simplifying the file until it looks the you want it to. Examples, such as those provided in this chapter, are always useful for the purpose of comparison.

Parser and syntax errors can prevent your configuration from being read at all or from being interpreted correctly. However once these files are read and interpreted correctly, they may still not work correctly. The most common problem with any zone file is forgetting to append a period to the end of a name that you intended to be a fully qualified domain name or putting a superfluous period at the end of a name. Names that do not end with a period are assumed to be local names to which the root name for the zone or the IP range should be appended. For example, if the name of your name server is ns1, the root name for vonhagen.org, and the IP address of your name server is identified in the zone or reverse lookup file, then either ns1 or ns1.vonhagen.org, are acceptable as the name of the name server. The first is a short name that does not end with a period, which means appended to it. The second is a fully qualified domain name that ends with a period, so nothing will be appended to. However, the entry ns.vonhagen.org is completely wrong because it does not end with a period, and the DNS parser replaces it with ns1.vonhagen.org.vonhagen.org, which probably doesn't exist in your domain.
