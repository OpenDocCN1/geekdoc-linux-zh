6. The sixth field is actually a set of five parameters, separated by white space and enclosed within one set of parentheses. Many people, including myself, use semicolons (a comment character) to append text descriptions of each field that make it easier to see what each value means during future updates. The following are the five values that must supply:

- Serial Number: This is an unsigned integer that should be changed each time you modify a zone or reverse lookup file. This value is usually constructed by concatenating the four digits for the current year, two digits for the month, two digits for the current day, and two final digits for a version number between 01 and 99. This makes it easier to decipher when the file was last modified and allows up to 99 revisions per day, which should hold just about anyone.
- Refresh interval: Identifies the amount of time in seconds after which slave DNS server will update your zone and reverse lookup information from the master server for that.
- Retry: Identifies the time interval in seconds after which a slave DNS server whose refresh interval has expired failed to contact its master server will try to reconnect that master server. This value should obviously be much smaller than the refresh interval.
- Expiration: Identifies the time interval between successful refreshes after which the zone data maintained by a slave server is no longer considered authoritative.

Slave servers stop responding to DNS requests if this time period has passed and the master server still cannot be contacted.

- Negative cache TTL: The amount of time that a negative response, such as a non-existent domain response, will be cached by the DNS server. Versions of BIND prior to version 9 used this value to represent the default TTL for a zone or reverse lookup file, which is now specified using $TTL (as described earlier).

# Creating Zone Files

A basic zone file consists of four blocks of information:

- The $TTL and SOA statements described in the previous section
- An entry that defines the name server for that zone
- An entry that defines the mail server for that zone
- Entries for all the hosts in the zone that map hostnames to their associated IP addresses and identify any aliases (CNAMEs) that are associated with those hosts

A name server entry looks like the following:

```
@ IN NS ubuntu32.vonhagen.org.
```

This entry identifies the root name of the zone using the @ symbol shortcut as was used in the SOA record, the fact that this is an Internet class record (IN), the specific type (NS, for "name server"), and the hostname of the name server. The IP address of the name server is typically provided later in the zone file if it is in the same domain or subdomain. With other Internet name entries in this file, the name of the name server must end with a period or the zone name will be appended to it. I use the @ shortcut to refer to the root domain in NS records because, frankly, this makes it easier for me to use a generic template for all of my files.

A mail server entry is very similar to a name server entry except that it uses the MX (Mail Exchange) record type to identify a mail server, and you can optionally precede the name server with a weight allows to identify higher-priority mail servers. Lower values have higher priority. This is meaningless when you have only one mail server, but providing a value makes it easier for you to remember that this feature is available as your network and number of mail servers expand. A sample mail server entry looks like the following:

```
@ IN MX 10 mail.vonhagen.org.
```

The IP address of the mail server is typically provided later in the zone file if it is in the same domain or subdomain. With other Internet name entries in this file, the name of the name server must end with a period or the zone name will be appended to it. I also use the shortcut to refer to the root domain in NS records because, frankly, this makes it easier for me to use a generic template for all of my files.

After the name server entry, the rest of the zone consists of A and CNAME records, which map hostnames to IP addresses and aliases. These records look like the following:

```
@ IN A 192.168.1.10
@ IN CNAME www.vonhagen.org.
```

# Chapter 32: Setting Up a DNS Server

Setting up a DNS server is a complex task, but it is essential for any functional network. In this chapter, we will walk through the process of configuring a primary DNS server using Ubuntu. We will use BIND, which is the most widely used DNS software available.

A DNS server acts as a phonebook for the internet, translating human-readable domain names like vonhagen.org into IP addresses that computers use to communicate. To get started, you need to understand the zone files and reverse lookup files.

Creating a zone file is half the battle. Once you've created a zone file, you have to create a parallel file that identifies how to map addresses back, which is known as reverse lookup. These files are discussed in the next section.
