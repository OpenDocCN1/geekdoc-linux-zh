## Overview of the Network File System

The Network File System (NFS) is a network filesystem that provides transparent access to files residing on remote disks. Network filesystems are commonly referred to as distributed filesystems because the files and directories that they provide access to be physically located on many different computer systems that are distributed throughout your home, academic environment, or business. Developed at Sun Microsystems in the early 1980s, the NFS protocol has been revised and enhanced several times between then and now, and is available on all Linux, UNIX, and UNIX-like systems (including Mac OS X), and even for Windows systems from many third-party software vendors. The specifications for NFS have been publicly available shortly after it was first released, making NFS a de facto standard for distributed filesystems.

NFS is the most common distributed filesystem in today, largely because it is free and available for almost every type of modern computer system. NFS enables file servers to serve centralized sets of files and directories to multiple clients. Good examples of files and directories that you may want to store in a centralized location but simultaneously available to multiple computer systems are users' home directories, site-wide sets of software development tools, and centralized data resources such as mail queues and the directories used to store Internet bulletin boards.

The following are some scenarios for using NFS:

- Sharing common sets of data files: Sharing files that everyone on your network wants to access, whether they are audio files, business data, or research data, is the most common use of any type of networked filesystem.
- Explicitly sharing home directories: Suppose that the home directories for all of your users are stored in the /export/home on your NFS file server, which is automatically mounted as /home on all of your UNIX and UNIX-like systems at boot time. Users can then log in on any NFS client system and instantly see their home directory, which would be transparently made to them over the network. If you want to have a local /home directory for some users and an NFS-mounted home directory for others, you could mount /export/home (perhaps /home/remote or something similarly evocative) and manually configure specific users to have home directories located in this directory.

## Tip

An alternative to the previous bullet is to automatically mount networked home directories using an exported NFS directory that is managed by an NFS automount daemon known as autofs on Linux systems. Whenever access to a directory by an automount daemon is requested by a client, the automount automatically mounts that directory on the client system. Automounting simplifies the contents of your server's /etc/exports file by enabling you to only export the parent directory of all home directories on the server, and letting the automounter manage that (and therefore its subdirectories) on each client. See the sidebar in this chapter for general information on automounting, a complete discussion which is outside the scope of this chapter.

The way in which RPCs are implemented is extremely clever. RPCs work using a technique called marshalling, which essentially means packing all of the arguments to the procedure in a mutually agreed-upon format. This mutually agreed-upon format called External Data Representation (XDR), provides a sort of "Esperanto" that enables systems with different architectures and byte-orders to safely exchange data with each other. The client's RPC subsystem then sends the system-independent packet to the appropriate server. The server's RPC subsystem receives the packet and unmarshals it to extract the arguments in its native format. The RPC subsystem executes the procedure locally, marshalls the results into a return packet, and sends this packet back to the client. When this packet is received by the client, its RPC subsystem unmarshals the packet and sends the results to the program that invoked the RPC, returning this data in the same fashion as any local procedure call. RPC communications are used for all NFS-related services, including communications related to the authentication services used by NFS (the Network Information System, NIS or NIS+), mount requests, status information, and requests made to the NFS daemon. To enable clients to contact so many different services without requiring that each client communicates through a specific, well-known port, NFS lets services dynamically bind to any port as they register with their central coordination service, the portmapper daemon. The portmapper always runs on port 111 of any host that supports RPC communications and serves as an electronic version of directory assistance. Servers register RPCrelated services with the portmapper, identifying the port that the service is listening on. Clients contact the portmapper to determine the port that they are looking for.

RPCs are known as Remote Calls (RPC), which use either User Datagram Protocol (UDP) or Transmission Control Protocol (TCP). The design and implementation of RPCs make NFS platform-independent, interoperable between different systems, and easily ported to operating systems.
