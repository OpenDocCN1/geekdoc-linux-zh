```
password [success=1 default-ignore] pam_unix.so obscure sha512
password requisite pam_deny.so
password required pam_permit.so
```

This invokes the pam_unix.so module to check /etc/passwd for a valid user and test the password for that user against the encrypted password entry found in the file /etc/shadow. The obscure argument specifies that when changing a password, certain checks will be performed, such as verifying that the new password is not a palindrome or rotated version of the old password, that the new password does not differ from the old one in terms of case, and that the new password is not "similar" to the old one. (I personally have never looked at the code to see how similarity is determined, but its rules seem to be fairly obscure). The sha512 option specifies the encryption algorithm that will be used to encrypt the password. The PAM must succeed but is not sufficient by itself to enable a user to log in. If this rule succeeds, the other rules in file are not invoked. If the first rule fails, the second rule immediately returns failure to prevent authentication. The third rule puts a positive return on the password stack if one is already present, but should not be.

# Note

Some other password checking and password-strength PAMs are listed in the file /etc/pam.d/common-password but commented out. You may not want to uncomment them comment out the original pam_unix.so entry, for example, you want to take advantage of the dictionary checks performed by the pam_cracklib.so module, which are irritating but ensure that a password is not a word that is commonly found in a dictionary.

Once all the PAMs specified in the /etc/pam.d/login file (and files that it included) have completed successfully, the login process continues, the user's login session is created, and any other startup actions in the user's login configuration files are executed.

The PAM authentication process can be complex and conducive to migraine headaches. Even though it is a pain, security is one of any sysadmin's most important responsibilities. You rarely, ever, want to muck with the PAM configuration files on a home Linux system, but you may want to modify them (and certainly understand them) when using Ubuntu in an enterprise or academic environment. If there's any consolation, think how the complex code to implement all of this would have been without the flexibility that PAMs provide.
