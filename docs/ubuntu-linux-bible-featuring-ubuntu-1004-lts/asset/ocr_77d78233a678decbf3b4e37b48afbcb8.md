The first error, "extra input text," indicates a parser error when trying to read one of the records in this file—in this case, the SOA record. To generate this error message, I removed the closing parenthesis in the SOA record, which causes the parser to continue on to the next line and report that it found, unexpected text in the next line which began with an @ symbol.

The second error, "unknown RR type 'ubuntu32.vonhagen.org' and "unknown class/type," are somewhat more insidious. These also indicate parser errors in reading one of the records, in this case on line 11. This is the name server declaration in my reverse lookup file. As I mentioned earlier in this chapter, the DNS parser is very finicky. Although it is clever about using default values whenever, you still have to be careful about how you use white space in the file. In this case, I had removing the leading @ symbol and deleted all of the white space at the beginning of this record, so that the IN was at the beginning of the line, without any white space preceding it, which was interpreted as the root name of my name server, the NS entry was used as the record, and the name of my server, ubuntu32.vonhagen.org, was interpreted as a record type specification. Attempting to resolve this problem also displayed the message "zone 168.192.11.addr.arpa/no NS records," which was caused by a similar parser error that I stumbled over to route to a valid name server.

Trying to resolve parser errors in zone files can be frustrating. Worst case, you can fall back to providing an explicit value for every possible field, verifying that the file works, and simplifying the file until it looks the you want it to. Examples, such as those provided in this chapter, are always useful for the purpose of comparison.

Parser and syntax errors can prevent your configuration from being read at all or from being interpreted correctly. However once these files are read and interpreted correctly, they may still not work correctly. The most common problem with any zone file is forgetting to append a period to the end of a name that you intended to be a fully qualified domain name or putting a superfluous period at the end of a name. Names that do not end with a period are assumed to be local names to which the root name for the zone or the IP range should be appended. For example, if the name of your name server is ns1, the root name for vonhagen.org, and the IP address of your name server is identified in the zone or reverse lookup file, then either ns1 or ns1.vonhagen.org, are acceptable as the name of the name server. The first is a short name that does not end with a period, which means appended to it. The second is a fully qualified domain name that ends with a period, so nothing will be appended to. However, the entry ns.vonhagen.org is completely wrong because it does not end with a period, and the DNS parser replaces it with ns1.vonhagen.org.vonhagen.org, which probably doesn't exist in your domain.
