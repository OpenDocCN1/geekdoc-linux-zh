## Working with Text Files

Most of us are used to working with files in various application-specific formats, often identified by their file extension or a special icon on our graphical desktops. We're all familiar with the doc files produced by graphical word processors such as Microsoft Word, xls files produced by spreadsheets as Excel, fm files produced by FrameMaker, ppt files produced by PowerPoint, and all of these files contain application data in a specific, often binary, format that lets the associated application make the best possible use of these files, but which often makes them hard to use with any other application than the one that created them.

At the other end of the spectrum from these application-specific files is the lowest-common-denominator file format known as text files, or to be a bit specific, ASCII text files. The contents of these files consist of only the standard letters, numbers, punctuation, and symbols that you find on a computer keyboard. The nice thing about these types of files is that they are easy to read, to process, and easy to work with in general.

Regardless of what you use your Ubuntu Linux system for, you will almost end up editing a text file one of these days. If you write code, it is almost certainly in standard text files because they provide a lowest-common-denominator format that can be processed by any compiler. If you're a writer, you may want to use text files because you can work with them on any system, with any editor or word processor—so you can work on them just as easily as your Ubuntu Linux system as you can on your Mac OS X system.

An even more critical point is that most system-level Linux utilities use one or more files to hold their configuration and initialization information. Even though Linux utilities can also be configured using a graphical interface, editing a text file is often faster and simpler than locating and starting the right graphical tool, finding the correct tab or panel, and so on.

# Introduction to Linux Text Editors

The first versions of UNIX for the PDP-11 were distributed by Bell Telephone Laboratories included a small, line-oriented text editor called ed, which was written by Ken Thompson (who is still there, most recently working on the Go programming language at Google). Various people enhanced ed, most notably George Coulours at Queen Mary College (QMC) in the United Kingdom, who added interactive support for editing single lines as part of his editors (editor), which he brought with him to the University of California at Berkeley (UCB) in 1976. At the same time, Ken Thompson had to go to UCB for a year or so, and while there had begun with Bill Joy and Chuck Haley on the UNIX enhancements that would eventually make up the Berkeley Standard Distribution (BSD).

Haley and Joy hacked ed for a while, revising it into and then a bunch of others, working their way through the alphabet "visual" they arrived at, which was still line-oriented. In 1976, Joy created vi (which stands for "visual") a screen-oriented editor that shared the command set, thanks to motivation provided by several ADM-3A terminals that were donated to UCB. The flexibility provided by vi in terms of using the entire screen, thanks to the /etc/termcap (terminal capabilities) file, was a huge step in diverging detailed knowledge about the hardware from editor under UNIX has never been seen.

Around the same time, on the other side of the country, a bunch of Lisp and ITS/TOPS-20 TECO hackers at the MIT Artificial Intelligence (AI) Lab were enhancing an aging line editor for their PDP-10 systems as Text Editor and Corrector (TECO). With inspiration from graphical editing work being done at Stanford's AI Lab, Richard Stallman (leader of GNU and FSF fame) and Guy Steele created a version of TECO which users could add their own commands. They also created and aggregated a set of TECO commands into a single package that provided support for screen-oriented editing using TECO. The TECO commands consisted of a set of macros (sequences of commands that executed together), so the set of macros became known as MACRO, or more, EMACS.

This was all well and good if you had happened to be using a DEC PDP-10, and Emacs would be an interesting footnote if it not for the efforts of Dave Conroy, who wrote a version of Emacs called MicroEm for just about anything, and James Gosling (leader of Java fame), who wrote a version of Emacs for UNIX systems in 1981. Unlike the Emacs macros that were their inspiration, these were actual compiled programs that ran on specific systems as compiled binaries. Gosling's version of Emacs, cleverly named Gosling Emacs or simply gacs, served as the original foundation for an open source version of Emacs for UNIX. Richard Stallman began writing GNU Emacs in 1984. For legal reasons, Stallman replaced all of the Gosling Emacs code in GNU Emacs and replaced Gosling's MockLisp Emacs configuration language with a full-blown Lisp interpreter to parse configuration files and other startup data.

**Note**
Over the years, several alternative expansions of the EMACS acronym have been offered to replace the original "Editing MACROs." Some of my favorites are "Escape Meta Alt Control Shift," referring to the heavy dependence of Emacs on the Ctrl and Esc keys in its command set, and "Eight Megabytes And Constantly Swapping," which was funnier when 8 MB was a lot of memory for a computer, and referred to its large requirements (for the time). I think the door opener I use today has more than 8 MB of memory.

## Modal versus Modeless Editors

As mentioned earlier in this chapter, among Linux and UNIX systems, there is no more entertaining or long-running flame war than the debate over which editor is better — vi or Emacs. If all of the characters expended on this topic had been given to random typists, they would have indeed produced the works of Shakespeare. As a new Ubuntu fan, you will eventually hear something about this, so this sidebar gives you a little background.

The basic difference between how you use vi and how you use Emacs boils down to the following: Emacs is known as a modeless editor (which is therefore known as insert mode), where any standard characters that you type are always inserted into whatever you're editing whereas vi is what is known as a editor in which Insert mode is just one available mode. Both Emacs and vi are extremely configurable, although vi does not provide an internal implementation of Lisp to "simplify" creating your own functions. On the other hand, because vi does not provide an internal implementation of Lisp, its mail client, newsgroup reader, and even a few games. On the other hand, you may be looking for a text editor, not a one-stop computing environment.
