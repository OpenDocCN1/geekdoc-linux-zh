
## Accepting Mail for an Entire Domain

As mentioned earlier, the mydestination parameter identifies what the mail host will deliver locally. The default Postfix configuration file accepts mail for localhost.localdomain, localhost, the actual hostname of the machine, and whatever you specified as the name of the machine on the configuration screen shown in Figure 30-2 (if that differs from the actual hostname of your machine). To make your new Postfix mail server a valid final destination for all your domain, you must add the name of your domain to the list of destinations in your machine.cf file. Because I specified ubuntu.vonhagen.org as my mail name, myydestination parameter currently looks like the following:

```
mydestination = ubuntu.vonhagen.org, ubuntu,
               localhost.vonhagen.org, localhost
```

I can add my domain name to this list or the name of my domain and leverage the value of that parameter to provide this information. I would add the mydomain parameter setting and update the value of the mysestination parameter, which together would look like the following:

```
mydomain = vonhagen.org,
mydestination = ubuntu.vonhagen.org, ubuntu,
               localhost.vonhagen.org, localhost, $mydomain
```

As with other configuration file changes, I would then either restart the Postfix server using sudo /etc/init.d/postfix restart or use the sudo postfix reload command to cause the active Postfix daemon pick up my changes to the configuration file.

## Tip

When you make the changes suggested in this section, you may also want to change the value of the myorigin parameter during installation, myorigin is set to whatever you specified as the name of the machine, which is useful because that value was also used in the value for your mysestination parameter, which would correctly handle the case in when someone sends mail to root@ubuntu.vonhagen.org. However, after installation, it is more useful to have myorigin be the same as the value of mydomain.

## Activating Qpopper for POP/POP3 Support

Qpopper (www.eudora.com/products/unsupported/index.html) is a popular, free POP/POP3 server from the folks at Qualcomm, who both sell and give away the PC and Macintosh MUA, Eudora. I like Qpopper because it supports the vanilla Linux/Unix mailbox format Postfix uses by default on Ubuntu. (When using the mbox mailbox format, all messages are stored in a single file, and each message begins with the string "From user@domain,") followed by the timestamp of the message.) I suggested that you install Qpopper in the section on Chapter 30: Setting Up a Mail Server on installing Postfix—if you didn't and to activate POP3 support on your new mail server, install it now and then proceed with this section.

## Note

As mentioned before, POP/POP3 and IMAP are alternative protocols for accessing your e-mail, and both can be used with Postfix as long as you install an appropriate server for that protocol on your mail server. Qpopper is fast, lightweight, and well-supported. If you want to support both POP/POP3 and IMAP, the Cyrus IMAP (http://asr.web.cmu.edu/cypress/) and Courier IMAP (http://www.courier-mta.org/imap/) are popular and both available in the Ubuntu repositories. However, configuring the Cyrus IMAP server can be tricky, and the Courier IMAP supports only the Linux/Unix mailbox format, where each message is stored in a single file, which is not the default behavior of Postfix on Ubuntu. Once Qpopper, which is fast, easy, and “just works.” ■

Ubuntu’s Qpopper package provides a ready-to-run Qpopper daemon that is suitable for use with the inet or xinetd services daemons that are discussed in the Chapter of 23 of “Software Development on Ubuntu”, entitled “Configuring the svnserver Server.” Both of these start various network services in response to specific types of incoming requests. If you have not already installed one of these, I suggest that you install the xinetd services daemon. You can then integrate Qpopper with xinetd by creating the following file with your favorite text editor and saving it as /etc/xinetd.d/pop3:

```
service pop3
{
    port        = 110
    socket_type = stream
    protocol    = tcp
    wait        = no
    user        = root
    server      = /usr/sbin/in.qpopper
}
```

You can then restart the xinetd services daemon using the command sudo /etc/init.xinetd restart, and Qpopper will be working correctly on your system. You can test that Qpopper is responding correctly to incoming POP/POP3 requests by configuring your M to point at your new mail server using the POP/POP3 protocol and checking your mail, or you can do so from the command line using the telnet command to connect to port 110 (the POP/POP3 port) and seeing if you can log in, as in the following example:

## Adding Spam Filtering and Virus Scanning to Postfix

Now that you have a running mail server and are receiving incoming connections from other mail servers, you will quickly find that an incredible amount of the mail that you receive is spam (also known as UCE, Unsolicited Commercial E-mail). Some of that mail is going to contain virus-laden attacks. You may also, unfortunately, receive a virus from friend who forwards something you thought was cute, but actually contains a virus payload. If you are lucky, whoever was hosting your mail before you switched to your own mail server filtering much of this, and you may not even know how bad things are in e-mail land. That you're hosting your mail server, you will quickly see that spam and virus-laden mail is an epidemic. No wonders it takes so long for me to connect to Amazon.com from the office since....

Aside from the fact that you're now aware of the spam/virus epidemic, it is also your responsibility to do something about it you're responsible for your mail server. Luckily, there are some great ways to configure Postfix to automatically handle much of this for you. If you installed all of the packages that I suggested back in the section "Installing Postfix and Friends," you've already installed the Postfix greylist service and MailScanner. MailScanner scans incoming mail and rejects spam that Postfix can identify, and then it can invoke other packages, such as SpamAssassin (http://spamass.apache.org), another package that does an even better job of spam detection, and ClamAV (http://clamav.net), which is an excellent open source antivirus package. All that remains to do is integrate these packages and Postfix.

At this point, you may be wondering why you should bother with an antivirus package on Linux because Linux systems are essentially virus-free. I suggest that you integrate an antivirus package as a matter of course because some of your mail server may also need to read mail on the Microsoft Windows machines that they use for playing games. More seriously, you may be setting up a mail server in a SOHO, SMB, enterprise environment in which many of your users need to use Microsoft Windows systems. Either way, installing an antivirus package when you configure your mail server is preventative medicine. It costs you nothing, and if it saves one person the agony of getting a virus on his or her system and having to remove it, it's worth your while.
