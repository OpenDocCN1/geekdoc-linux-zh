As another way of dealing with potential communication and system failures, NFS servers are stateless, meaning that they do not retain information about each other across system restarts. If a server crashes while a client is attempting to make an RPC to it, the client continues to retry the RPC until the server comes back up or the number of retries exceeds its configured limit, at which time the operation fails. Stateless operation makes the NFS protocol much simpler because it does not have to worry about maintaining consistency between client and server data. The client is always right, even after rebooting, because it does not maintain any data at that point.

Although stateless operation simplifies things, it is also extremely noisy, inefficient, and slow. When data from a client is saved back to a server, the server must write it synchronously, without returning to the client until all the data has been saved to the server's disk. As described in the next section,"Comparing Versions of NFS," newer versions of NFS do some caching to return the client applications as quickly as possible. This caching is done by the rpcbind (RPC Input/Output daemon), which stores writing to NFS servers in the hopes that it can bundle groups of them together and optimize the client's use of the network. In the current standard version of NFS (NFS version 4), cached client-writes are still essentially dangerous because they are stored in memory and will therefore be if the client crashes before the write completes.

In a totally stateless environment, a server crash would make it difficult to save data that was being modified on a client back to the server once it were available again. The server would have no way of knowing which file modified the data belonged because it had no persistent information about its clients. To resolve the problem, NFS clients obtain file handles from a server for the file that they are associated with. If a server crashes, clients retry their write operations until the server is available or their time-out periods are exceeded. If the server comes back up in time, receives the modified data and the file handle from the client, and can use the file handle to figure out which the modified data should be written to.

NFS 4 provides client-side caching, which can significantly improve performance by reducing the number of calls that need to be made to an NFS server to retrieve data, and which helps prevent data loss if a server is unavailable for a short period of time. However, this is not sufficient to insulate NFS clients from performance problems if they must execute binaries located on an NFS server as part of the client's reboot process. If the server is unavailable, the client cannot boot. For reason, most NFS clients must contain a full set of system binaries, and typically only share user-oriented binaries and data via NFS.
