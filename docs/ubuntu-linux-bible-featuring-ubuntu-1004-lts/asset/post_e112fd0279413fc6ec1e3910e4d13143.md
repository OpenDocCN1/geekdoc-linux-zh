
# Chapter 34: Setting Up an NFS Server

NFS has been around almost since the beginning of UNIX, appearing on Sun Microsystems workstations in the early 1980s. This section provides an overview of the differences between the four versions of NFS, and to illustrate that NFS is by no means done deal. Even though NFS versions 3 and later use TCP as their network transport mechanism, the idea of idempotent requests is still part of the NFS protocol to guarantee compatibility with NFS version 2 dealing implementations.

As another way of dealing with potential communication and system failures, NFS servers are stateless, meaning that they do not retain information about each other across system restarts. If a server crashes while a client is attempting to make an RPC to it, the client continues to retry the RPC until the server comes up or the number of retries exceeds its configured limit, at which time the operation fails. Stateless operation makes the NFS protocol much simpler because it does not have to worry about maintaining consistency between client and server. Although stateless operation simplifies things, it is also extremely inefficient and slow. When data from a client is saved back to the server, the server must write it synchronously without returning to the client until all the data has been saved to the server's disk.

In newer versions of NFS, some caching is done to return the client as quickly as possible. This caching is done by the rpcbind (RPC-Output daemon), which stores writing in memory and will therefore be lost after reboot. In a totally stateless environment, a server crash would make it difficult to save data that was modified on a client back to the server once it were available again. The server would have no way of knowing which modified data belonged to. To resolve the problem, NFS clients obtain file handles from server and can use the file handle to figure out which modified data should be written to. NFS 4 provides client-side caching, which can significantly improve performance by reducing the number of calls that need to be made to the server to retrieve data, and helps prevent data loss if the server is unavailable for a short period.

## Comparing Versions of NFS

The following list identifies the four versions of NFS and highlights the primary features of each:

- **Version 1:** The original NFS protocol specification was used internally at Sun during the development of NFS and is now only of historical interest.
- **Version 2:** NFS 2 was the first version of the NFS protocol that was released for public consumption. Version 2 used UDP as its transport mechanism and defined a 32-bit file handle and therefore imposed a maximum file size limitation on files. Version 2 also limited data transfer sizes to 8 KB.
- **Version 3:** NFS 3 addressed many of the shortcomings and ambiguities in the NFS 2 specification and took advantage of the technological advances in networking and system architecture after version 2 was released. Version 3 added TCP as a transport mechanism, making it the default if both the client and server support it; increased the maximum data transfer size between client and server to 64 KB; and was a 64-bit implementation, effectively removing file size limitations. Version 3 also added a few new protocols to the original version specification. To improve performance by decreasing network traffic, version 3 introduced the notion of bundling writes from the client to the server and also returned file attributes with each RPC call, rather than requiring a separate request for this information.
- **Version 4:** Much of the NFS 4 protocol is designed to position NFS for use in Internet and Web environments by increasing persistence, performance, and security. Version 4 adds persistent, client-side caching to reduce network traffic and decrease the chance of data loss in a reboot, and adds support for ACLs and extended file attributes in NFS filesystems. Version 4 also adds an improved standard API for increased security through a general RPC security mechanism known as Remote Procedure Call Security Generic Security Services (RPCSEC_GSS). This mandates the use of the Generic Security Services Application Programming Interface (GSS-API), specified in RFC 2203 to select between available security mechanisms provided by clients and servers.

The version of the NFS server that is shipped with Ubuntu provides support for NFS versions 4 and 2.

## NFS Users and Authentication

NFS uses the user ID (UID) and group ID (GID) of each user from a system's password file (/etc/passwd) to determine who can write to and access exported files and directories, based on the UID and GID on the file server. This means that all of your users should have the same UID and GID on all systems to which NFS directories such as home directories are exported.

In small networks, it is often sufficient to make sure that you create the same users and groups on all of your systems, or make sure that the password and group files on your file server contain the correct entries for all of the users and groups who will access any directory that they export.

In larger networks, this is impractical, so you will want to consider network-oriented authentication mechanisms, such as Kerberos, which is discussed in Chapter 27, or the traditional Network Information System (NIS), which was developed by Sun Microsystems for use with NFS. Unfortunately, discussing NIS installation and setup on Linux systems is a history lesson rather than something modern systems actually do; it is outside the scope of this chapter. If you need to use NIS on Linux, you can find a variety of excellent information about it online in documents such as the NIS HOWTO (www.linux-nis.org/nis-howto/), which is even available in multiple languages.

# Installing an NFS Server

You can use the Synaptic Package Manager, the Adept Package Manager, or the command-line package management utilities described in Chapter 19 to install the packages required to run and monitor an NFS server on your Ubuntu system. You must install both the nfs-common and nfs-kernel-server packages on any system where you want to run an NFS server—only the nfs-common package is required on a system on which you want to mount NFS-ystems. (Installing the nfs-kernel-server package on a system will automatically install the nfs-common package as a requirement.) Once the installation completes, you're ready to configure your server to share data from your system with any system that supports NFS.
