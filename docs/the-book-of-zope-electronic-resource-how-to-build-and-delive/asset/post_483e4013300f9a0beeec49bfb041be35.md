# 6 USERS, ROLES, AND SECURITY

This chapter will look at the Zope security structure. We will create and edit new users using both the Management screen and DTML. We will also create new roles and take a closer look at the various permissions that Zope provides for users. Finally we will explore Zope’s procedure to authenticate users.

## 6.1 Zope’s Security Structure

One of the most important and powerful security functions provided by Zope is its ability to define roles, which can then be used to assign and remove user permissions.

> NOTE This book uses the terms “rights” and “permissions” synonymously.

The following examples demonstrate the use of roles and permissions:

- A group of developers is working together on different parts of a Zope project. You want to ensure that individual team members cannot change parts of the project that are outside their area of responsibility.
- Large companies consist of several departments in which various have overall responsibility. If this type of company wants to establish an Internet presence, care must be taken to ensure that no individual user in a group (in this case, a department) can make changes in another department's areas, and if problems arise, it is easy to determine who is responsible.

These are only two of the many ways that Zope's roles and permissions allow you to achieve the desired distribution of responsibility and control.

### 6.1.1 User Roles

Each user has a specific role (or roles) within Zone, regardless of whether that works directly managing Zone or merely with pages published by Zope on the Internet or intranet. Through those roles, each user is assigned specific permissions and access rights. Roles may have been previously created, or they can be created as needed by authorized users.

### 6.1.2 Zone Roles: Anonymous, Manager, Owner

The roles already present in Zone are Anonymous, Manager, and Owner. New roles can be created and assigned only by users who have the rights or permissions needed to do.

The permissions assigned to each role (and hence each user assigned to that role) determine what the user can carry out with regard to the objects and management functions in Zone. Permissions determine whether and where users can view, create, or modify Zone objects or perform management tasks.

### 6.1.2.1 Anonymous

By default, Zope automatically assigns the Anonymous role to all users who have not explicitly logged in. Users assigned the Anonymous role can only view pages for which the View permission has been assigned to the Anonymous role, which by default is all Zone objects except the Control_Panel folder.

Of course, the permissions for the Anonymous role can be expanded to include actions other than View, which we'll describe in Section 6.1.4. In addition, when you create a new user in Zone (see Section 6.2.1), you specify the role(s) assigned to that user and define new roles and permissions.

By default, the role Anonymous has the Access contents information and View permissions for all objects. (In section 8.3.4, "Assigning Permissions for login_html," we will remove this permission from the Anonymous role for a specific object to restrict anonymous users' access to that object.)

### 6.1.3 Assigning and Creating Roles

You can manage every object by typing the suffix /manage after the object's URL, provided your role authorizes you to do so. (We will discuss how to create roles in 6.2.3). If, for example, you need to manage the DTML document my_document in the folder my_folder, simply enter the following URL:

```
http://localhost:8080/my_folder/my_document/manage
```

To see the third tier rendered of the DTML document, omit the suffix /manage from the end of the URL. To view an object, your role must have the permissions for that.

### 6.1.3.1 View Management

Whenever a user tries to perform an action, maje checks if the proper permissions are assigned to the user's roles. If a user tries to perform an action for which that is not currently authorized, maje will first ask to authenticate or log in. In response, the user must enter a username and password that maje recognizes as belonging to a role with permission to perform the action. If the username and password are invalid or do not correspond to a user with the proper permissions, maje generates an Unauthorized error message.

### 6.1.4 Assigning Permissions Using Acquisition

As explained in section 2.5, acquisition plays a pivotal role in maje. Like other attributes of objects, as such properties, permissions settings can be acquired by an object from its parent objects, all the way up to the root folder.

It works like this: Imagine a folder as an object with a long list of permissions—such as Access contents information, Add Database Methods, and so—shown in the Security screen. Each permission has a checkbox to the left of it, in the Acquire permission settings column, as shown in Figure 6-2.
