

尽可能简单。其主要功能是进行通信。计算机提供的所有不同功能都是通过微内核通信通道可用的服务。在微内核方法中，你应该将问题空间划分到没有复杂部分的地步。

我认为这是愚蠢的。是的，它使每一个部分都变得简单。但交互使得它比许多服务包含在内核本身中（如 Linux 那样）要复杂得多。想想你的大脑。每个部分都是简单的，但部分之间的交互构成了一个高度复杂的系统。这是“整体大于部分之和”的问题。如果你把一个问题一分为二，并说这两半的复杂程度是原来的一半，你就忽略了必须加入两半之间通信复杂性的事实。微内核背后的理论是将内核分成五十个独立的部分，每个部分的复杂度是原来的五十分之一。但随后每个人都忽略了部分之间的通信实际上比原始系统更复杂这一事实——更不用说这些部分本身仍然并不简单。

这是反对微内核的最大论点。你试图达到的简单性是虚假的简单性。

Linux 起初要小得多，也简单得多。它不强制模块化，因此你可以比在 Minix 上更直接地做很多事情。我对 Minix 的原始问题之一是，如果有五个不同的程序同时运行并且它们都想读取五个不同的文件，任务将被序列化。换句话说，五个不同的进程会向文件系统发送请求：“请允许我从文件 X 读取？”处理读取的文件系统守护进程会处理其中一个并返回，然后处理下一个并返回，依此类推。

在 Linux（这是一个整体式内核）中，你有五个不同的进程，每个都执行进入内核的系统调用。内核必须非常小心以确保它们不会相互混淆，但它自然地扩展到任意数量的进程执行它们想做的任何事。这使得 Linux 更快、更高效。

Minix 的另一个问题是，你获得了源代码，但许可证不允许你做很多事。以 Bruce Evans 为例，他对 Minix 进行了重大手术，使其更实用。但他不能直接整合他的改进。他只能制作补丁。从实用角度来看，这是完全的灾难。他在法律上无法提供可启动映像供人们轻松升级。因此，用户必须经过多步过程才能获得可用的系统，这非常不实用。

### 1. 微内核与整体式系统

大多数较旧的操作系统是整体式的，即整个操作系统是一个单一的 a.out 文件，在“内核模式”下运行。该二进制文件包含进程管理、内存管理、文件系统和其他部分。此类系统的例子包括 UNIX、MS-DOS、VMS、MVS、OS/360、MULTICS 等等。

替代方案是基于微内核的系统，其中操作系统的大部分作为单独的进程运行，主要在内核之外。它们通过消息传递进行通信。内核的工作是处理消息传递、中断处理、低级进程管理，以及可能的 I/O。这种设计的例子包括 RC4000、Amoeba、Chorus、Mach，以及尚未发布的 Windows/NT。

虽然我可以在这里长篇大论地谈论这两种设计的相对优点，但只需说，在实际设计操作系统的人中间，这场辩论基本上已经结束了。微内核已经胜出。MINIX 是一个基于微内核的系统。文件系统和内存管理是单独的进程，运行在内核之外。I/O 驱动器也是单独的进程。LINUX 是一个整体式系统。这是向 20 世纪 70 年代的巨大倒退。

### 2. 可移植性

MINIX 被设计为具有合理的可移植性，并从 Intel 系列移植到 680X0（Atari、Amiga、Macintosh）、SPARC 和 NS32016。LINUX 与 80x86 紧密绑定。这不是前进的方向。

别误会我，我对 LINUX 并不不满。它将把所有希望将 MINIX 变成 BSD UNIX 的人从我背上移除。但诚实地说，我建议那些想要一个*现代* *自由*操作系统的人四处看看，寻找基于微内核、可移植的操作系统，比如 GNU 或类似的东西。
