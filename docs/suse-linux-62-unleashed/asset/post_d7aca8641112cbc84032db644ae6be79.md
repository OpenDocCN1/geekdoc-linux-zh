sendmail passes addresses to rulesets according to a built-in order. Rulesets also call other rulesets not in the built-in order. The built-in order varies depending on whether the address being handled is a sender or receiver address and which mailer has been chosen to deliver the letter.

Rulesets are announced by the S command, which is followed by a number to identify the ruleset. sendmail collects subsequent R (rule) lines until it finds another S operator or the end of the configuration file. The following example defines ruleset 11:

Ruleset 11

```
S11
R$+ $: $$22    call ruleset 22
```

This ruleset does not do much that is useful. The important point to note is that sendmail collects ruleset number 11, which is composed of a single rule.

# sendmail’s Built-in Ruleset Processing Rules

sendmail uses a three-track approach to processing addresses: one to choose a delivery agent, another to process sender addresses, and another for receiver addresses.

All addresses are sent through ruleset 3 for preprocessing into a canonical form that makes them easy for other rulesets to handle. Regardless of the complexity of the address, ruleset 3’s job is to decide the next host to which a letter should be sent. Ruleset 3 tries to locate that host in the address and mark it within angle brackets. In the simplest case, an address like joe@gonzo.gov becomes joe@gonzo.gov.

Ruleset 0 then determines the correct delivery agent (mailer) to each recipient. For example, a letter from betty@whizer.com to joe@gonzo.gov (an Internet site) and pinheadzi (an old-style UUCP site) requires two different mailers: an SMTP mailer for gonzo.gov and an old-style UUCP mailer for pinhead. Mail selection determines later processing of sender and recipient addresses because the rulesets in the S= and R= mail flags vary from mailer to mailer.

Addresses sent through ruleset 0 must resolve to a mailer. This means that when an address matches the lhs, the rhs a triple of the mailer, user, and host. The following line shows the syntax for a rule that resolves to a mailer:

```
Rhs $ mailer $@ $: your comment here...
```

The mailer is the name of one of the mailers you've defined in an M command—for example, smtp. The host and user are usually possess macros taken from the lhs match (see "The-Right-Hand Side (rhs) of Rules") later in the chapter).

After sendmail selects a mailer in ruleset 0, it processes sender addresses through ruleset 1 (often empty) and then sends them to the ruleset using the S= flag for that mailer.

Similarly, sendmail sends recipient addresses through ruleset 2 (often empty) and then to the ruleset mentioned in the R mail flag.

Finally, sendmail processes all addresses in ruleset 4, which (among other things) removes the angle brackets inserted by ruleset 3.

Why do addresses differ S= and R flags? Consider the previous example of the letter sent to joe@gonzo.gov and pinhead@ziippy. If Betty@whizzer.com sends the mail, the line address must appear in a different format to each recipient. For Joe, it should be a domain address, betty@whizzer.com. For Zippy, because pinhead expects old-style UUCP addresses, the return address should be whizzerbetty. Joe's address must also be rewritten for the pinhead UUCP parser, and Zippy's copy must include an address for Zippy that his mailer can handle.

# Processing Rules within Rulesets

sendmail passes an address to ruleset and processes it through each rule by line. If the lhs of a rule matches the address, it is rewritten by the rhs. If it doesn't match, sendmail continues to the next rule until it reaches the end of the ruleset. At the end of the rule, sendmail returns the address to the calling ruleset or to the next ruleset in its built-in execution sequence.

If an address matches the lhs and is rewritten by the rhs, the rule is tried again—an implicit loop (but see the " $: and $$: Altering a Rule's Evaluation" section for exceptions).

As shown in Table 9.1, each rule is introduced by the R command and has three fields—the left-hand side (lhs, or matching side), the right-hand side (rhs, or rewriting side), and an optional comment—which must be separated from one another by tab characters:

| Lhs | rhs | comment |
| :--- | :--- | :--- |

# Parsing: Turning Addresses into Tokens

sendmail parses addresses and the lhs of rules into tokens and then matches the address and the lhs token by token. The macro $ contains the characters that sendmail uses to separate an address into tokens. It's often defined like this:

![](img/cbac72550c7126a22162e94d91a0c360_328_0.png)

```
# address delimiter characters
Do::%@![/]
```

All the characters in $ are both token separators and tokens. sendmail takes an address
such as rae@rainbow.org and breaks it into tokens according to the characters in the o
macro, like this:

- * "rae", "@", "rainbow", "\.", "org"

sendmail also parses the lhs of rewriting rules into tokens so they can be compared one
with the input address to see whether they match. For example, the lhs-
@rainbow.org is parsed as follows:

- * "$", "@", "rainbow", "\.", "org"

(Don't worry about the $ - just yet. It's a pattern-matching operator, similar to a shell
wildcard, that matches any single token and is covered later in the section "The Left-Hand
Side (lhs) of Rules." Now you put the two together to show how sendmail decides
whether an address matches the lhs of a rule:

- * "rae", "@", "rainbow", "\.", "org"
- * "$", "@", "rainbow", "\.", "org"

In this case, each token from the first line matches that of the second, thanks to the pattern-
matching operator ($ -), so the entire address matches and sendmail will use the rhs to
rewrite the address.

Consider the effect (usually bad) of changing the value of $. As shown previously,
sendmail breaks the address rae@rainbow.org into five tokens. However, if the $
character were not in s$, the address would be parsed quite differently, with only three
tokens:

- * "rae", "@", "rainbow", "\.", "org"

You can see that changing $ has a drastic effect on sendmail's address interpretation,
until you know what you're doing. Even then, you probably
want to change it correctly.

# The Left-Hand Side (lhs) of Rules

The lhs is a pattern against which sendmail matches the address. The lhs can
contain ordinary text or any of the pattern-matching operators shown in Table 9.2.

### 9.2 lhs Pattern-Matching Operators
| :--- | :--- |
| $- | Match exactly one token. |
| + | Match one or more tokens. |
| $* | Match zero or more tokens. |
| $@ | Match the null input (used to call). |

The values of macros and classes are matched in the lhs with the operators shown in Table 9.3.

### 9.3 lhs Macro and Class-Matching Operators
| :--- | :--- |
| $* | Match the value of macro X. |
| $=C | Match any word in class c. |
| $-C | Match if token is not in class C. |

The pattern-matching operators and macro- and class-matching operators are necessary because rules must match many different addresses. For example, a rule might need to match all addresses that end with gonzo.gov.

# The Right-Hand Side (rhs) of Rules

The rhs of a rule tells sendmail how to rewrite an address that matches the lhs. The rhs can include text, macros, and positional references to matches in the lhs. When a pattern-matching operator from 9.2 matches the input, sendmail assigns it to a numeric $ corresponding to the position it matches in the lhs. For example, suppose the address joe@pc1.gonzo.gov is passed to $1 in the following rule:

```
R$ @ $+          $: $1 < @ $2      focus on domain
```

In this example, joe matches $* (one or of anything), so sendmail assigns the string joe to $1. The @ in the address matches the @ in lhs, but constant strings are not assigned to positional markers. The tokens in the string pc1.gonzo.gov match $+ and are assigned to $. The address is rewritten as $1@$2, or joe@pc1.gonzo.gov.

# $ and @@: Altering a Ruleset's Evaluation

Consider the following rule:

```
R$$: $1 < @ $j > local domain
```

After rewriting an address in the rhs, sendmail tries to match the rewritten address against the lhs of the current rule. Because $* matches zero or more of anything, what prevents sendmail from going into an infinite loop on this rule? After all, no matter how the rhs rewrites the address, it will always match $$.

 $: prefix to the rhs comes to the rescue, telling sendmail to evaluate the rule only once.
