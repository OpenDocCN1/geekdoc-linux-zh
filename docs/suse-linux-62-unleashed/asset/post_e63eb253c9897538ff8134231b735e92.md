Because TXT records are free, you're not forced to place contact information there. As a result, the RP record was created, which explicitly states that this is the person responsible for the specified host. For example:

domain.cxm. IN RP heidis.domain.cxm.

The first column states the domain for which the responsible party is set. The second column, IN, defines this record to use the Internet class. RP designates this to be a responsible party record. The fourth column specifies the email address of the person who is actually responsible. Notice that the @ symbol has been replaced by a period in this address, much as in the SOA record. The last column specifies a TXT record that gives additional information. In this example, it points back to the TXT record for domain.cxm.

# PTR: Pointer Record

The pointer record, also known as the reverse resolution record, tells named to turn an IP address into a hostname. PTR records are a little odd that should not be in the same SOA as your A records. Instead, they appear in an in-addr.arpa subdomain SOA.

A PTR record looks like the following:

```
2.42.168.192. IN PTR mtx.domain.cxm.
```

Notice that the IP address to be-reversed is in reverse order and is suffixed with a period.

# Configuring DNS Server Master Zones

As mentioned earlier, DNS comes in three flavors:

- Master (also called primary)
- Slave (also called secondary)
- Caching only

We discussed creating a caching-only server earlier in the chapter. Caching-only servers cannot answer queries, but can only pass those to other servers with master or slave zones that are authoritative over the domain in question. However, all DNS servers should be configured to perform caching functions.

# Networking and Internet Services

Let's turn our attention to adding DNS server master zones. A DNS server master zone can answer queries about its domain without querying other servers because its data resides on the local hard disk. A DNS server master zone is considered to have the most-to-date records for all the hosts in that domain.

## Local Domain Resolution

Earlier in the chapter you created a caching-only DNS residing on the hypothetical host numark at address 192.168.42.1 in domain.cxm. Assume that this same subnet host mtx at 192.168.42.2. It's an easy task to add local domain resolution, using master zones. The following is the basic procedure:

1. Add master zone "domain.cxm" to named.conf, pointing to zone data file named.domain.cxm.
2. Create zone data file named.domain.cxm, resolving both hosts—sendmail and www.
3. Add resolution from 192.168.42.2 to mtx in the previously created named.192.168.42.42.
4. Restart named.
5. Test and troubleshoot.

## Add Zone "domain.cxm" to named.conf

Add the following code to /etc/named.conf:

```
zone "domain.cxm" {
    # DNS for all hosts this domain
    type master;                #file on this host
    file "named.domain.cxm";    #dns name file for domain
};
```

This says to refer any name or FQDN in domain domain.cxm to the data name-d.domain.cxm, which, due to the type master; statement, is input to the DNS server, not output from it and not an intermediate file. Note that the text to the right of the pound signs (#) are comments. Next, create file named.domain.cxm.

## Create Zone Data File named.domain.cxm

Create the following /var/named/named.domain.cxm:

```
@    IN SOA numark.domain.cxm. hostmaster.domain.cxm. (
                   199702703 ; Serial
                   28800      ; Refresh
                   14400      ; Retry
                   360000    ; Expire
                   86400      ; Minimum)
```

numark mtx www Nameserver numark.domain.cxm has authority over @, which is the zone in named.conf. The information between parentheses contains details explained in this chapter. A single nameserver (NS) for @ is set to domain.cxm. (domain.cxm) is at numark. numark handles the (MX) for domain.cxm. numark and mtx addresses 192.168.42.1 and 192.168.42.2, respectively. Alias refers to numark, which by previous line is set to 192.168.42.1.

The IN NS and IN MX statements have no identifier in column 1. IN lacking a name defaults to the identifier of the last statement, which in this case is the top line. The preceding zone data file is built for simplicity. Real-life servers have ns IN A 192.168.42.1 line so they can call nameserver in all files. That way, if nameserver is changed from numark to mtx, the only required change in any file is the ns IN A line. Note that syntax is important, because zone file syntax is different from boot syntax. All names must be in column 1. All periods (.) are vital because a name ending in a period is considered absolute, while a name ending in a period is relative to the @ symbol, which is substituted by the domain from the named.conf record.

# Add 192.168.42.2 to named.192.168.42.2

You must be able to resolve 192.168.42.2 back to mtx, so add the following to zone data file named.192.168.42.2:

```
2 IN PTR mtx.domain.cxm.
```

After it finishes, test it. First, try telnetting in and making sure you get the login prompt within a second or two. If telnet hangs, investigate your reverse DNS zones and reverse DNS data files.

Next, try running the following commands:

```
ping 192.168.42.1
ping 192.168.42.2
```

Do each ping from each server. If any IP ping fails, there's a network connectivity problem that must be solved before you attempt to activate. Once connectivity is proved, do the following:

```
ping numark
ping mtx
ping numark.domain.cxm
ping mtx.domain.cxm
ping www.domain.cxm
```

Each of the preceding ping commands should succeed and deliver the right IP. If each of these commands succeeds, try the following:

```
nslookup numark
nslookup mtx
nslookup numark.domain.cxm
nslookup mtx.domain.cxm
nslookup www.domain.cxm
nslookup 192.168.42.1
nslookup 192.168.42.2
```

Each command should quickly deliver the expected results. If you have sendmail up and running, test the IN MX statements with email operations.

Troubleshooting is essentially a process of elimination. Try to determine whether it's the forward or reverse lookups that are giving you problems. Try to narrow it down to a single domain, server, or use ping to make sure you have network connectivity.

# Adding Virtual Domain Resolution

1. Not all IP addresses denote actual hardware. Some are alias addresses intended to represent websites. Generally speaking, these websites are granted IP addresses. Following are the steps to add a virtual domain (in the existing subnet):
2. Create the zone in named.conf.
3. Create a new zone data file.
4. Add an IN PTR line to the existing reverse DNS file for the subnet.
5. Restart named.

In the following example, add domain vdomain.cxm at IP address 192.168.42.101, which can be added by the following command:

```
# /sbin/ifconfig eth0:0 192.168.42.101 mask 255.255.255.0
```

This IP is made into a virtual host website in /etc/httpd/conf/httpd.conf, so all it needs is a domain name. Assuming you want to give 192.168.42.101 the name vdomain.cxm, add the following zone to named:

```
zone "vdomain.cxm" {
  #DNS for virtual domain
  type master;                #file on this host
  file "named.vdomain.cxm";    #dns file for domain
}
```

As you can see, the zone data is named vdomain.cxm. Create that file as follows:

```
@ IN SOA numark.domain.cxm. hostmaster.domain.cxm. (
    199702700 ; Serial
    28800      ; Refresh
    14400      ; Retry
    360000    ; Expire
    86400      ; Minimum

    IN NS numark.domain.cxm.
```

```
@ IN A 192.168.42.101
www IN CNAME @
```
