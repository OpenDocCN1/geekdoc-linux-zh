
Sometimes you might want a ruleset to terminate immediately and return the address to the calling ruleset or the next ruleset in sendmail's built-in sequence. Prefacing a rule's rhs with $66 causes sendmail to exit the ruleset immediately after rewriting the address in the rhs.

## $$>: Calling Another Ruleset

A ruleset can pass an address to another ruleset by using the $> prefix to the rhs. Consider the following rule:

```
R$ $: $66 call ruleset 66
```

The $1hs matches zero or more of anything, sendmail always does the rhs. As you learned in the preceding section, the $: prevents the rule from being evaluated more than once. The $66 $1 calls ruleset 66 with $1 as its input address. Because the $1 matches whatever was in the $1, this rule simply passes the entirety of the current input address to ruleset 66. Whatever ruleset 66 is passed to the next rule in the ruleset.

## Testing Rules and Rulesets: The -bt, -d, and -c Options

Debugging sendmail.cf can be a tricky business. Fortunately, sendmail provides several ways to test rulesets before you install them.

> Note
The examples in this section assume that your system has a working sendmail. If not, running these examples again after you have installed V.8 sendmail.

The -bt option tells sendmail to enter its rule-testing mode:

```
$ /usr/sbin/sendmail -bt
ADDRESS TEST MODE (ruleset 3 NOT automatically invoked)
Enter <ruleset> <address>
```

> Note
Notice the warning ruleset 3 NOT automatically invoked. Older versions of sendmail ran ruleset 3 automatically when in address test mode, which made sense because sendmail sends all addresses through ruleset 3 anyway. V.8 sendmail does not, but invoking ruleset 3 manually is a good idea because later rulesets expect the address to be in canonical form.

## SMTP and Protocols

The > prompt sendmail is waiting for you to enter one or more ruleset numbers, separated by commas, and an address. Try your login name with rules 3 and 0. The result should look like this:

```
> 3,0 joe
rewrite: ruleset 3 input: joe
rewrite: ruleset 3 returns: joe
rewrite: ruleset 0 input: joe
rewrite: ruleset 3 input: joe
rewrite: ruleset 3 returns: joe
rewrite: ruleset 2 input: joe
rewrite: ruleset 3 returns: joe
rewrite: ruleset 0 returns: $ local: joe >
```

The output shows how sendmail processes the input joe in each ruleset. Each line of output is identified with the name of the ruleset processing, the input address, and the address that the ruleset returns. The > is a second prompt indicating that sendmail is waiting for another line of input. When you're done testing, just press Ctrl+D.

Indentation and blank lines show the flow of processing in this example:

```
rewrite: ruleset 3 input: joe
rewrite: ruleset 3 returns: joe
```

```
rewrite: ruleset 0 input: joe
```

```
rewrite: ruleset 3 input: joe
rewrite: ruleset 3 returns: joe
```

```
rewrite: ruleset 6 input: joe
rewrite: ruleset 6 returns: joe
```

```
rewrite: ruleset 0 returns: $ local: joe
```

The rulesets called were 3 and 0, in order. Ruleset 3 was processed and returned the value joe, and then sendmail called ruleset 0. Ruleset 0 called ruleset 3 again and then ruleset 6, an example of how a ruleset can call another one by using $. Neither ruleset 3 nor ruleset 6 rewrote the input address. Finally, ruleset 0 resolved to a mailer, as it must.

## Networking and Internet Services

Often you need more detail than -bt provides—usually just before you tear out a large handful of hair because you don't understand why an address doesn't match the lhs of a rule. You can remain hirsute because sendmail has verbose debugging built into most of its code.

You use the -d option to turn on sendmail's verbose debugging. This option is followed by a numeric code that indicates which section of debugging code to turn on and at what level. The following example shows how to run sendmail in one of its debugging modes and the output it produces:

```
$ /usr/sbin/sendmail -bt -d21.12
ADDRESS TEST MODE (ruleset 3 NOT automatically invoked)
Enter <ruleset> <address>
3,0 joe
rewrite: ruleset 3 input: joe
-- trying rule: $* < > $*$
-- rule fails
-- trying rule: $* < $* < $* < > $* *
-- rule fails
```

-d21.12 in the preceding example tells sendmail to turn on level 12 debugging in section 21 of its code. The same command with the option -d21.36 gives more verbose output (debug level 36 instead of 22).

> Note
You can combine one or more debugging specifications separated by commas, as in -d21.12,14.2, which turns on level 12 debugging in section 21 and level 2 debugging in section 14. You can also give a range of debugging specifications, as in -d1-10.35, which turns on debugging in sections 1 through 10 at level 35. The specification -d0-9.10 turns on all sections of V.8 sendmail's debugging code at the highest levels and produces thousands of lines of output for a single address. The -d option is not limited to use with sendmail's address testing (-bt). You can also use it to see how sendmail processes rulesets while sending a letter, as the following example shows:

```
$ /usr/sbin/sendmail -d21.36 joe@gonzo < /tmp/letter
[lots and lots of output...]
```

Unfortunately doesn't tell you which numbers correspond to sections of code. Instead, the author suggests keeping such documentation current by looking at the code to discover the correct debugging formulas. The function parse() is the one to look for. For example, suppose you want to turn on debugging in sendmail's address-parsing code. The source file parseaddr.c contains most of this code, and the following command finds the allowable debugging levels:

```
$ egrep parse() parseaddr.c
if (parse(20, 1))
if (parse(24, 4))
if (parse(22, 11))
```

The egrep output shows that debugging specifications such as -d20.1, -d24.4, and -d22.1 (others) will make sense to sendmail. Note the book only carries up to sendmail-8.8; small differences in detail could exist but it is still a good reference. The -c option enables you to test configuration files before you install them, which is always a good idea. If you want to test a different file, use -C/path/to/file. You can combine it with the -bt and -d flags. For an example, a common invocation for testing new configuration files is:

```
/usr/sbin/sendmail -Ctest.cf -bt -d21.12
```

> Caution
For security, sendmail drops its superuser permissions when you use the -c option. You should perform testing of configuration files as the superuser to ensure your testing is compatible with sendmail's normal operating mode.

## Automatically Generating the sendmail.cf File

Likely, no one has to manually edit a sendmail.cf file. There are several configuration files in the /usr/share/sendmail directory. The /usr/share/sendmail/README file is worth reading. It contains information on the different features that you can add into your file, as well as other important information, including a description of the anti-spam features that made it into the later versions of sendmail.

Creating a sendmail.cf for your site is a matter of changing to the cf directory and selecting an appropriate template. The ls should produce a list similar to:

```
[root@gonzo /usr/share/sendmail]# cd cf
[root@gonzo /usr/share/sendmail]# ls
```

| Build.mc | generic-solaris.cf | mailpool.cs.mc |
| Makefile | generic-bsd4.cf | generic-solaris2.mc | python.cs.mc |
| chez.cs.mc | generic-bsd4.mc | generic-sunos4.cf | s2k-osf1.mc |
| clientproto.mc | generic-hpux10.cf | generic-usonos4.mc | s2k-ultrix4.mc |
| cs-hpux10.mc | generic-hpux10.mc | generic-ultrix4.cf | tcpproto.mc |
| cs-hpux9.mc | generic-hpux9.cf | generic-solaris4.mc | ucbarpa.mc |
| cs-osf1.mc | generic-hpux9.mc | huginn.cs.mc | ucbvx.mc |
| cs-solaris2.mc | generic-nextstep3.3.mc | knecht.mc | uucproto.mc |
| cs-sunos4.1.mc | generic-osf1.cf | mail.cs.mc | vangaugh.cs.mc |
| cs-ultrix4.mc | generic-osf1.mc | mail.eecs.mc | |

These are all the different files you can choose to create your cf. I suggest copying it to another name as:

```
[root@gonzo /usr/share/sendmail]# cp python.cs.mc gonzo.mc
```

I will now give you a brief explanation of various directives you may find in the sample mc files:

```
divert(-1)
include('../../m4/cf.m4')
```

These are the directives that the m4 processor needs to process the file. You will find entries in some of the other files.

```
define('conf_USER_ID','8:12')
OSTYPE('linux')
define('UUC_RELAY')
define('BITNET_RELAY')
```

The define indicates that you want to change a setting in sendmail, such as maximum hops allowed for a message or the message size. In this case you're defining which UID and group to run the sendmail program as it is not in privileged mode (running as root).
