
# Building Large Applications

C programs can be broken into any number of files, as long as no single function spans more than one file. To compile this program, you compile each source file into an intermediate object before you link all the objects into a single executable. The -c flag tells the compiler to stop at this stage. During the link stage, the object files should be listed on the command line. Object files are identified by the .o suffix.

# Making Libraries with ar

If several different programs use the same functions, they can be combined into a single library archive. The ar command is used to build a library. When this library is included on the compile line, the archive is searched to resolve any external symbols. Listing 25.4 shows an example of building and using a library.

# LISTING 25.4 Building a Large Application

```
$ gcc -c sine.c
$ gcc -c cosine.o
$ gcc -c tangent.c
$ ar c libtrig.a sine.o cosine.o tangent.o
```

```
$ gcc -c mainprog.c
$ gcc -o mainprog.o libtrig.a
```

Large applications can require hundreds of source code files. Compiling and linking applications can be a complex and error-prone task of its own. In the next section, you'll read about the make utility, a tool that helps developers organize the process of building the executable form of complex applications from many source files.

# Building Programs with make

The make command is only one of several programming automation utilities included with SuSE Linux. You'll find others, as pnake (the BSD make), make (a template-based makefile generator, usually for building X11 applications), autotake, and autoconf (which builds shell scripts to configure program source code packages).

> For a bit more information about make and building makefiles when developing Motif clients for the X Window System, see the section "Motif Programming," later in the chapter.

The make command's roots stem from an early version of System V UNIX. The version included with SuSE Linux is part of the GNU utilities distribution. make is used to automatically handle the building and install of a program, which can be as simple as

```
# make install
```

The magic of make is that it will automatically update and build applications. You create this magic through a default file named Makefile. However, if you use make's -f option, you can specify any Makefile, such as MyMakefile, like this:

```
# -f MyMakefile
```

A Makefile is a text file that can contain instructions about which options to pass to the compiler preprocessor, the compiler, and the linker. The Makefile can also specify which source files need to be compiled (and the compiler command line) for a particular code module, and which code modules are needed to build the program—a mechanism called dependency checking.

Make can also aid in the portability of your program through the use of macros. This allows users of other operating systems to easily configure a program build by specifying local values, such as the names and locations, or pathnames of required software tools. In the following, macros define the name of the compiler (CC); the installer program (INS); where the program should be installed (INSDIR); where the linker should look for required libraries (LIBDIR); the names of required libraries (LIBS); a source code file (SRC); the intermediate object code file (OBS); and the name of the final program (PROG):

```
# a sample makefile for a skeleton program
CC= gcc
INS= install
INSDIR = /usr/local/bin
LIBDIR = -L/usr/X11/lib
LIBS = -L1m -LSM -LICE -Lxt -LX11
SRC= skel.c
OBJS= skel.o
PROG= skel
```

```
skel: ${OBJS}
$(CC) -o ${PROG} ${SRC} ${LIBDIR} ${LIBS}
```

```
install: ${PROG}
$(INS) -g root -o root ${PROG} ${INSDIR}
```

Using this approach, you can build the program with this:

```
# make
```

To build a specified component of your makefile, use a target definition on the command line. To just build the program, use make with the skel target like this:

```
# make skel
```

If you make any changes to any element of a target object, such as a source code file, make will rebuild the target. To build and install the program in one step (using the example), specify the install target like this:

```
# make install
```

Larger software projects may have any number of traditional targets in the makefile, such as:

- *test*—To run specific tests on
- *archive*—To archive the project
- *bugreport*—To report bugs

# Managing Projects with RCS and CVS

If you have some previous UNIX experience, you may be familiar with the Revision Control System (RCS) and Concurrent Version System (CVS). RCS is used to track changes to individual files, while CVS is an extension that allows you to track multiple files together.

RCS uses a single file for each file to store its history. CVS uses a directory to store the history of all files in the project. This makes it much easier to manage projects that span many files.

The RCS commands are:

- ci—Check in
- co—Check out
- ident—Attribute information
- rsclean—Clean up
- rcsdiff—Compare versions
- rcsmerge—Merge versions
- rcslog—Log history

The CVS commands are:

- checkout—Check out versions
- update—Update with changes
- add—Add new files
- import—Add files to repository
- remove—Delete files
- commit—Publish changes

Both RCS and CVS are used to manage versions of software projects. They allow you to track changes, compare versions, and revert to previous states if necessary. This is essential for any professional software development project.

Source code control with CVS requires the use of at least six commands on the command line:

- checkout—Check out versions
- update—Update with changes
- add—Add new files
- import—Add files to repository
- remove—Delete files
- commit—Publish changes

RCS and CVS may be used for more than software development. These tools may also be used for document preparation and workgroup editing of documents and will work with any text files. Both systems use registration and control files to accomplish revision management. Both systems offer the opportunity to revisit any step or branch in a revision history and restore to previous states if necessary. This is essential for any professional software development project.

Tracking information is usually contained in separate control files, and each document within a project may contain information automatically updated with each change to a project using keyword substitution. CVS can use keywords similar to RCS, which are usually included inside C comment strings (/**) near the top of a document. A sample of the available keywords includes:

- $Author$-Username of person performing last check-in
- $Date$-Date and time of last check-in
- $Header$-Insert the pathname of the document’s RCS file, revision number, date and time, and state.
- $ID$-Same as $Header$, but without full pathname
- $Name$-A symbolic name (see the co man page).
- $Revision$-The assigned revision number (such as 1.1).
- $Source$-RCS file’s full pathname.
- $State$-The state of the document, such as Exp for experimental, Rel for released, or Stab for stable.
