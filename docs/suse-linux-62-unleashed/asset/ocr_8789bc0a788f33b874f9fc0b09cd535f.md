These keywords may also be used to insert version information into compiled programs using character strings in program source code. For example, given this extremely short program named foo.c:

```
/* $Header */
#include <stdio.h>
static char rscid{} = '$Header$';
main() {
    printf('Hello, Linus!');
}
```

the resulting $Header$ keyword may expand in an RCS document to this:

$Header: /home/bball/sw/RCS/foo.c,v1.1 1999/04/20 15:01:07 root Exp $

Getting started with RCS is as simple as creating a project directory and an RCS directory under the project directory, and then creating or copying initial source files in the project directory. You can then use ci to check in commands. Getting started with CVS requires you to initialize a repository by first setting the CVSROOT environment variable with the full pathname of the repository and then using the init command option with the cvs command, like this:

```
# cvs init
```

You'll find documentation for RCS in various man pages and under the /usr/doc/packages/rcs-5.7 directory.

# Debugging Tools

Debugging is a science and an art unto itself. Sometimes, the simplest tool—the code listing is best. At other times, however, you need to use other tools. These of three tools include lint, gprof, and gdb. Other tools include escape, xref, and cb. Many UNIX commands have debugging uses.

lint is a traditional UNIX command that examines source code for possible problems, but it is not included with most Linux distributions. The code might meet the standards for C and compile cleanly, but it might not execute correctly. lint checks type mismatches and incorrect argument counts on function calls. lint also uses the C preprocessor so you can use command-like options similar to those you use for gcc. The GNU C compiler supports extensive warnings (through the -Wall and -pedantic options) that might eliminate the need for a separate lint command.
