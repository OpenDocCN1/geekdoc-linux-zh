On a properly configured DNS, the result should look something like the following:

```
# nslookup mtx.domain.cxm
Server: numark.domain.cxm
Address: 192.168.42.1
```

The two-argument version specifies the IP address of the DNS server as second argument. In the absence of the second argument, the first server line in /etc/resolv.conf is used. Here's a two-argument example:

```
# nslookup mtx.domain.cxm 192.168.42.1
```

This command returns the exact output as the one-argument version. The two-argument version is used when reverse DNS isn't functioning correctly, or if /etc/resolv.conf has been temporarily renamed or deleted.

# traceroute

The traceroute utility enables you to determine the path a packet is taking across your network and into other networks. This is very useful for debugging network connection problems, especially when you suspect the trouble is located in someone's network.

Using the ICMP protocol (same as ping), traceroute looks up each machine along the path to a destination host and displays the corresponding name and IP address for that. Along with each name is the number of milliseconds that each of the three tiers took to get to the destination.

Preceding each name is a number that indicates the distance to that host in hops. The number of hops to a host indicates the number of intermediate machines that had to process the packet. As you can guess, a machine that is one or two hops away is usually much closer than a machine that is 30 hops away.

To use traceroute, give the destination hostname or IP address as a command line argument. For example:

```
traceroute www.hyperreal.org
```

should return something similar to the following:


If you see start characters (such as *) of a hostname, that machine is probably unavailable. This could be due to a variety of reasons, with network failure and firewall protection being the most common. Also, be sure to note the time it takes to get from one site to another. If you feel that your connection is excessively slow, it might be just one connection in the middle that is slowing down and not the site itself.

# DNS Server Configuration Files

DNS server is a potentially complex system configured by a surprisingly straightforward set of files. These files consist of a single boot file and several zone data files, each of which is pointed to by a zone record in the boot file. This section discusses these files and their features, syntax, and conventions.

# The DNS Boot File: /etc/named.conf

The /etc/named.conf file is read when named is started.

Boot file comments can be done in three different ways:

/* C style comments can comment out multiple lines */
// C++ style comments comment one line
# Shell script comments function like C++ style

Other statements take the form

keyword { statement; statement; }

Because everything in this file is brace, space-, and semicolon-delimited, multiple line breaks do not affect its functionality.

# Caution

Bugs caused by syntax errors in named files are hard to detect. Often there are no symptoms, and even when symptoms are observable, the messages are cryptic and hard to trace. So it is imperative to check the files carefully. The two most common starting keywords in named.conf are options and zone. A named.conf that does reverse DNS on its loopback and does forward DNS on domain.com.

# Example named.conf File

```
options {
    directory "/var/named";      # referred files in /var/named
    type hint;                   # hints for caching
    file "named.cache";           # root servers file in /var/named/named.cache
}

zone "127.0.0.in-addr.arpa" { # reverse on loopback
    type master;
    file "named.local";
}

zone "192.168.0.in-addr.arpa" { # reverse on subnet
    type master;                   # file is on host
    file "named.192.168";      # dns file
};

zone "domain.com" { # DNS for all hosts
    type master;             # file is on host
    file "named.domain.com"; # dns file for domain
};
```

The options section holds information that is global to the entire server. It contains a single piece of information, the directory statement, which tells named the location of any filenames mentioned in the configuration. zone is the caching zone. A caching zone isn't a master or slave, but rather a set of hints for the server to use; hence the type statement. The file for zone is named.cache, which was created by SuSE installation. File named.cache contains a list of all the root servers on the Internet. These root servers are needed to prime named's cache. You can get the latest list of root servers from INTERNIC

```
ftp://rs.internic.net/domain/named.cache
```

Each zone has statement indicating master, slave, or hint, and a file statement pointing to the file containing data for the zone. Files of type slave have nested sections. This will be demonstrated in the “Adding a Slave Server” section later in this chapter.

Each zone defines a zone of authority, which is usually a domain, subdomain, or in the case of reverse DNS, a subnet. Every zone defines a file from which it derives its information. Every zone has a type.

# notify

Another statement appearing frequently in zones and the options section is the notify statement, which can be notify or notify no. The default is yes, so there's no reason to put in notify except for documentation. If notify is yes, the zone's slaves are informed of zone changes so they can initiate a zone transfer. If it's no, no notification is given. notify no is often inserted to prevent bogus domains (such as domain.com) from hitting real nameservers. Note that if a notify statement appears in the options section, it serves as the default for all zones but is specified to be overridden by any specific notify statement. The current version of named will not turn off notify if it's turned on in the options section.

# forwards

With a forwarders statement in the options section, you can specify one or more nameservers to send queries that can't be resolved locally:

img/cbac72550c7126a22162e94d91a0c360_280_0.png

```
options {
    forwards { 192.168.42.10; 192.168.42.20; };
}
```

This sends unresolved queries to the two servers mentioned instead of sending them to local caching DNS. This can be advantageous when there's a premium on outside traffic. All internal servers resolve outside names via one or two servers, those servers build huge caches, meaning that more queries are resolved inside the building walls. Otherwise, all the servers might be making identical queries to the outside world.

If for some reason the forwarder cannot answer the query, the query is tried via the normal server caching DNS. To absolutely forbid any non-local query from a DNS server, place a forwarder-only statement right below the forwarders statement. Doing this makes the forwarder server(s) a single point of failure, so it's not recommended.

# DNS Zone Data Files

Zone data files are pointed to the file statements in the boot file's zone sections and contain all data about the zone. The first thing to understand is that the syntax of a zone data file is totally different from the syntax of the boot file named.conf.

# Zone Data File Syntax Is Totally Different from Boot File Syntax

It's important to remember that the syntax of the zone data files is not the same as that of the DNS boot file (named.conf). The zone data file comment character is the semicolon. For each line, DNS will fail if the name data item has spaces before it.

> Note
The name data item is normally the first on the line and must not be preceded with spaces. Occasionally, however, the name data item can be absent from the line, giving the appearance of space before the first data item. What's really happening is that the name data item was left off the line, allowing it to default to the name data item in the nearest previous line containing a name data item. For all practical purposes, the next data item after the name is either the word IN or a number representing a “Time To Live” (followed by IN). Knowing this can help you avoid much confusion.
