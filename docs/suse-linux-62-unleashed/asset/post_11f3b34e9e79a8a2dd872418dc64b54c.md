
These keywords may also be used to insert version information into compiled programs using character strings in program source code. For example, given this extremely short program named foo.c:

```c
/* $Header */
#include <stdio.h>
static char rscid{} = '$Header$';
main() {
    printf('Hello, Linus!');
}
```

the resulting $Header$ keyword may expand in an RCS document to this:

$Header: /home/bball/sw/RCS/foo.c,v1.1 1999/04/20 15:01:07 root Exp $

Getting started with RCS is as simple as creating a project directory and an RCS directory under the project directory, and then creating or copying initial source files in the project directory. You can then use ci to check in commands. Getting started with CVS requires you to initialize a repository by first setting the CVSROOT environment variable with the full pathname of the repository and then using the init command option with the cvs command, like this:

```bash
# cvs init
```

You'll find documentation for RCS in various man pages and under the /usr/doc/packages/rcs-5.7 directory.

## Debugging Tools

Debugging is a science and an art unto itself. Sometimes, the simplest tool—the code listing is best. At other times, however, you need to use other tools. These of three tools include lint, gprof, and gdb. Other tools include escape, xref, and cb. Many UNIX commands have debugging uses.

lint is a traditional UNIX command that examines source code for possible problems, but it is not included with most Linux distributions. The code might meet the standards for C and compile cleanly, but it might not execute correctly. lint checks type mismatches and incorrect argument counts on function calls. lint also uses the C preprocessor so you can use command-like options similar to those you use for gcc. The GNU C compiler supports extensive warnings (through the -Wall and -pedantic options) that might eliminate the need for a separate lint command.

![](img/cbac72550c7126a22162e94d91a0c360_796_0.png)

> If you'd like to explore various C syntax-checking programs, navigate to http://metalab.unc.edu/pub/Linux/devel/c. One program that closely resembles the traditional lint program is lclint, found in the iclint-2.2a-src.tar.gz file.

The gprof command is used to study where a program is spending its time. If a program is compiled and linked with -p as a flag, an out file is created when it executes, with data on how often each function is called and how much time is spent in each function. gprof parses and displays this data. An analysis of the output generated by gprof helps determine where performance bottlenecks occur. Whereas using an optimizing compiler can speed up your program, taking the time to use gprof's analysis and revising bottleneck functions will significantly improve program performance.

The third tool is a symbolic debugger. When a program is compiled with -g, the symbol tables are retained and a symbolic debugger can be used to track program bugs. The basic technique is to invoke gdb after a core dump and get the source line where the core dump occurred and the functions that were called to reach that. Often, it is enough to identify the problem. It is not the limit of gdb, though.

gdb also provides an environment for debugging programs interactively. Invoking gdb with a program enables you to set breakpoints, examine variable variables, and monitor variables. If you suspect a problem near a line of code, you can set a breakpoint at that line and run the program. When the line is reached, execution is interrupted. You can check variable values, examine the stack trace, and observe the program's environment. You can single-step through the program, checking values. You can resume execution at any point. By using breakpoints, you can discover many of the bugs in your code that you've missed.

cpp is another tool that can be used to debug programs. It performs macro replacements, includes headers, and parses the code. The output is the actual module to be compiled. Normally, though, cpp is invoked directly.

## New Features of the egcs Compiler System

The egcs (pronounced "eggs") was originally an experimental version of gcc. Since its first release in late summer 1997, egcs has incorporated many features from gcc, such as a built-in FORTRAN end. Although some Linux developers may have felt that development of egcs represented a fork (or split) in gcc development, Cygnus stated that cooperation between the developers of gcc and egcs would prevent it. The hope, according to Cygnus, was that the new compiler architecture and features of egcs will be the best compiler in the world. In 1999, egcs officially became part of future GCC software, and according to Cygnus, the egcs team will be responsible for rolling out future GCC releases. The egcs compiler system is now the default C and++ compiler.

## Motif Programming

This section introduces you to the OSF/Motif programming libraries. You need to have the GNU gcc or egcs compiler system and associated headers, libraries, and utilities installed on your system. You also need X and Motif installed on your system if you want to run any Motif clients, including mwm. ## What Is Motif?

First of all, you should understand that, unlike the FreeX86 distribution of X, Motif is not free—you must pay for a distribution. There are Motif distributions for Linux on the Intel, SPARC, and Alpha platforms. You must purchase a version for your computer and operating system if you want to build Motif clients and distribute them. If you want other people to run your clients, you can build the clients in either shared library or static versions, for people who either have or don't have Motif.
