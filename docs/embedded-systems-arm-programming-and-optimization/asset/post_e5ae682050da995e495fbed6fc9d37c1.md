### 3.6.9 Converting from floating-point to fixed-point arithmetic

This section describes a method for converting the image transformation code
described earlier in the chapter to fixed point. The code uses high-level
language to perform the fixed-point arithmetic.

Begin by changing the type of the arrays `src_pixel`, `frac`, and `weights`
to `int`. Then define two parameters that can be used to adjust the
position of the radix point (m) and its corresponding numerical 
significance ($2\textsuperscript{m}$)).

```c
#define FRACBITS 8
```

```c
#define FRAC_SIG 256
```

The rotation transformation requires the use of sine and cosine functions,
and there are no fixed-point versions of these in the POSIX standard math
library. Although it is possible to implement them or use a third party
library, doing so will have negligible impact on performance since the
program calls functions once per frame computing the transformation
matrices. As such, the program can calculate these values using floating
point and convert the floating-point values to fixed point.

To do this, define a fixed-point version of the transformation matrix by
declaring new variables `c_row_fp` and `c_col_fp` as 2-element arrays of
type `int`.

After the call to `calc_coeffs()`, add the following code to convert the
floating-point transformation matrix to fixed point. To convert, multiply
the floating-point values where $f=$the number of bits to the right of
the radix point, converting the result to an integer as shown below:

```c
c_row_fp[0] = (int)(c_row[0] * (float)FRAC_SIG);
c_row_fp[1] = (int)(c_row[1] * (float)FRAC_SIG);
c_col_fp[0] = (int)(c_col[0] * (float)FRAC_SIG);
c_col_fp[1] = (int)(c_col[1] * (float)FRAC_SIG);
```

The inner loop begins by multiplying the destination pixel location at row
$j$ (or $x=j, y=i$) by the transformation matrix. No time int-float
casting is necessary.

The following lines map each pixel location in the transformed image to a
(fractional) pixel location in the source image. Each line adds two products
of a (32,8) transformation matrix value (`c_row_fp`) and a (32,0) loop
counter value. When added, the two (32,8) products produce a (32,8) sum,
which is stored in the `src_pixel` array.

```c
src_pixel[0] = c_row_fp[0] * -(rows/2) +
nc_row_fp[1] * (j-cols/2)); // (32, FRACBITS)
src_pixel[1] = c_col_fp[0] * -(rows/2) +
c_col_fp[1] * (j-cols/2));
```

After this convert `src_pixel` to a (32,0) type and round down by shifting
right by the number of fractional bits.

```c
src_pixel_int[0] = (src_pixel[0]>>FRACBITS)+(rows/2); // (32,0)
src_pixel_int[1] = (src_pixel[1] >> FRACBITS) + (cols/2);
```

Use bitwise AND operation to extract the fractional portion of `src_pixel`.
To extract the $m$ bits from some value, perform a bitwise-AND with $2\textsuperscript{m}-$:

```c
frac[0] = src_pixel[0] & (FRAC_SIG-1); // (32, FRACBITS)
frac[1] = src_pixel[1] & (FRAC_SIG-1);
```

When calculating the weights, subtract the fractional point of each source
pixel location from 1. Since it must be expressed in the fixed-point format
as the fractional values computed (32,m) produces the defined value for
$2\textsuperscript{m}$. Multiplying two (32,m) produces a (32,2) product.

```c
weights[0] = (FRAC_SIG-frac[0]) * (FRAC_SIG-frac[1]); // (32,2x
// FRACBITS)

weights[1] = (FRAC_SIG-frac[0]) * (frac[1]);
weights[2] = (frac[0]) * (FRAC_SIG-frac[1]);
weights[3] = (frac[0]) * (frac[1]);
```

Extract the RGB values of the four source pixels as before. When calculating
the interpolated color values, you must remember to shift the final value, which
is in (32,0) format, $2m$ bits to the right to compute the final (32,0)
color value.

```c
red = (r[0]) * (weights[0]) +
(r[1]) * (weights[1]) +
(r[2]) * (weights[2]) +
(r[3]) * (weights[3])) >> FRACBITS);
```

```c
green = ((g[0]) * (weights[0]) +
(g[1]) * (weights[1]) +
(g[2]) * (weights[2]) +
(g[3]) * (weights[3])) >> FRACBITS*2;
```

```c
blue = ((b[0]) * (weights[0]) +
(b[1]) * (weights[1]) +
(b[2]) * (weights[2]) +
(b[3]) * (weights[3]) >> FRACBITS*2;
```

### 3.7 FIXED-POINT PERFORMANCE

As compared to floating point, using fixed point reduces the latency after each
arithmetic instruction at the cost of additional instructions required for rounding
and radix point management, although if the overhead contains sufficient instruction
level parallelism of these additional instructions on throughput may not be
substantial.

On the other hand, for graphics applications like the image transformation that
require frequent conversions between floating point and integer, using
fixed point may result in a reduction of executed instructions.
