ARM allows a flexible second operand, meaning that arithmetic instructions allow the second operand register to be shifted or rotated prior to being used in the instruction's operation. For example:

```
adr r1,r2,r3,lsl #2
```

...would left-shift the contents of register r3 before adding it to the contents of register r2, and:

```
adr r1,r2,r3, as r4
```

...would arithmetically right-shift the contents of register r3 by a number of bits specified by the low-order byte of the contents of register r4 adding them to the contents of register r2.

The list of valid shift operations is:

- asr: arithmetic shift right, store the last bit shifted out in the carry flag (if instruction uses the S suffix)
- lsl: logical shift left, store the last bit shifted out in the carry flag (if instruction uses the S suffix)
- lsr: logical shift right, store the last bit shifted out in the carry flag (if instruction uses the S suffix)
- ror: rotate right, place original bit n-1 into the carry flag;
- rrx: rotate exactly one bit (this operation does not accept a shift amount), treat the register as a 33-bit register with the carry flag acting as the LSB.

These operations also have their own corresponding instructions, when using these as instructions the flexible second operand is not available. In other words, the following instruction is not allowed:

```
asr r1,r2,r3, asr #4
```

## 1.5.2 Status register

ARM v6/v7 maintains a status register called the CPSR (current program status register) that holds four status bits, negative (N), zero (Z), carry (C), and overflow (O). These bits can be used for conditional execution of subsequent instructions.

The bits are set to the most recently executed ALU instruction that includes the special "s" suffix. For example, the "adds" instruction will modify the status bits but the "add" instruction will not.

Nearly all ARM instructions can include an optional condition code that determines if the instruction will be executed or skipped over. In other words, an instruction whose condition code is evaluated to false will not change the state of the processor, such as writing a register to changing the PC.

For example, the ldreq instruction will only execute if the Z-bit in the CPSR is set, which will be the case if the most recent computational instruction resulted in a result of zero.

For example, the sequence:

```
subs r2,r2,#1
streq r3, [r0]
```

...will decrement register r2 and store r3 only if the new value of r2 is zero.

The compare (cmp) instruction can be used to set the status bits without any other side effect.

For example:

```
cmp r2,r3
streq r4, [r0]
```

...will store register r4 only if the contents of registers r2 and r3 are equal.

When combining the condition code and the "s" suffix, the condition code comes first, for example

```
addeqs r0,r0,r1
```

## 1.5.3 Memory addressing modes

Like other load-store architectures, the only ARM instructions that access off-chip memory are load and store instructions. There are several available *addressing modes*, or ways that the off-chip memory address can be specified by the programmer or compiler.

Let us begin by examining the format of load and store instructions.

To load from memory, use the ldr instruction *mnemonic* followed by the target register and the memory address:

```
<register>, <memory address>
```

To store to memory, use the str instruction mnemonic followed by the source register and the memory address:

```
<register>, <memory address>
```

Notice that, unlike most instructions, in the store instruction the destination location (the memory address) is given second.

The ldr and str instructions can also exchange non-32-bit values (such as bytes and halfwords) in memory by using an optional type modifier following the mnemonic:

```
ldr/strd load/store double (64 bits)
ldrsh load signed halfword (16 bits)
```

### Table 1.2 ARM Memory Modes
| Example Instruction | Effective Address Calculation |
|---|---|
| ldr r0, [r1] | address = R[r1] |
| ldr r0, [r1], #4 | preincrement: address = R[r1] + 4 |
| ldr r0, [r1], #4! | postincrement: address = R[r1] + 4, R[r1] = R[r1] + 4 |
| ldr r0, [r1, r2] | address = R[r1] + R2 |
| ldr r0, [r1, r2, #4] | address = R[r1] + R2 × 4 |
| ldr r0, [r1, r2, lsl #2] | address = R[r1] + R2 × 4 (shift the address left 2 bits) |
| ldr r0, [pc, #8192] | address = PC + 8192 |
| ldrh/strh load/store halfword (16 bits) | |

## 1.5.4 GNU assembler

This textbook uses the GNU assembler to illustrate the ARM instruction set. The GNU assembler uses a different assembly language than ARM’s own assembler. For example, in the GNU assembler:

- labels that denote instruction locations for branch targets end with a colon (e.g., "loop: ldr r2,[r3]")
- assembler directives begin with a period (e.g., ".text")
- comments begin with an ampersand and (e.g., "& outer loop")

Other notable characteristics of ARM assembly include:

- destination registers are generally listed to the list of source registers r0 through r15 (e.g., "add r1, r2, r3 & add contents of r2 and store in r1")
- immediates, which are constant values encoded directly within an instruction, are denoted with a hash symbol (e.g., "add r1, r2, #12")
- constants that are defined using the "=" directive are preceded by a sign when used (e.g., "add r1, r2, =N")

## 1.6 ASSEMBLY OPTIMIZATION1: SORTING

The next two sections walk through ARM assembly programming, optimization, and performance analysis for two examples. The first example is bubble sort.

### 1.6.1 Reference implementation

Begin by writing a reference implementation in C in the file bubble_sort.c:

```c
#define N 32768

int data[N];

int main() {
    int i,j,temp;

    for (i=0; i<(N-1); i++) {
        for (j=0; j<(N-1); j++) {
            if (data[j]>data[j+1]) {
                temp=data[j];
                data[j]=data[j+1];
                data[j+1]=temp;
            }
        }
    }
    return 1;
}
```

The first three lines allocate an array of 32K integers in global memory. For now the program will not initialize this array.

Recall that the bubble sort compares each pair of values $n-1$ times, where $n$ is the number of elements. After each comparison, the values are swapped if they are in unordered order. Each individual value can move at most one position toward the beginning of the array per iteration of the outermost loop, which can be thought of as bubbles slowing to the top of a liquid.

Save this file as bubble_sort.c and compile with gcc, using the "-O3" flag to tell the compiler to use maximum optimization:

```bash
gcc bubble_sort.c -O3 -o bubble_sort
```

Execute and time the program:

```bash
time ./bubble_sort
```

On an ARM Cortex A15, the program requires 4.0 s of user CPU time to execute. From this it is possible to make rough estimations regarding the efficiency of the compiler.

The program compares $n^2=2^{15}\times 2^{15}$ pairs of values, meaning the processor needs approximately $4.0^{30}=3.7$ cycles per comparison.

At our clock rate of 2.3 GHz (usually found in /sys/devices/system/cpu0/cpufreq/cpuinfo_max_freq), this translates into

$2.3e9\times 3.7e-9=8$ cycles per comparison

This includes both the time required to execute the comparison instructions and the time needed for the transactions (cache stalls). Is this reasonable?
