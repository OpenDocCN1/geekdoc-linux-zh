# CHAPTER 5 Embedded Heterogeneous Programming with OpenCL

Most smartphone and tablet users take for granted their ability to encode and decode high definition video and render three-dimensional (3D) graphics in real time. These tasks would not be possible without the help of specialized coprocessors such as graphical processing units (GPUs).

Even the high-performance quad-core ARM Cortex A15—with its single instruction, multiple data (SIMD) units, out-of-order superscalar architecture, and advanced caches—is not capable of performing these tasks on its own. For this reason, all modern system-on-chip (SoC) coprocessors contain a diverse set of specialized coprocessor technologies. The most advanced of these support general purpose programming using Open Computing Language (OpenCL).

For example, the Xilinx Zynq implements its dual ARM Cortex-A9 processors with an integrated Programmable Gate Array (FPGA) fabric which can be used to implement custom circuits at high throughput and low latency.

Another example is the Texas Instruments Keystone II, which supplements its quad Cortex A5 processors with eight Digital Signal Processor (DSP) cores that have Very Long Instruction microstructure that offer peak floating-point throughput of 16 Gflops.

Smartphone and tablet SoCs include coprocessors that are generally classified as GPUs. Unlike desktop and server GPUs whose market is dominated by NVIDIA, AMD, and Intel, the market for low power mobile GPUs is still competitive, diverse, and vibrant:

- ARM Mali GPU
- Imagination PowerVR GPU
- Broadcom VideoCore GPU
- Qualcomm Adreno GPU
- NVIDIA Kepler GPU

Embedded GPUs generally share the same memory system as their host CPU so they do not have advantage in memory bandwidth but are not subject to GPU overhead.

# 5.1 GPU Microarchitecture

General purpose programming for embedded GPUs is still relatively new and the associated runtime libraries and compilers are immature. This chapter uses the ARM Mali-T62 GPU as found on ODROID-X3 as a case study. Like other embedded GPUs, the ARM Mali supports general purpose programming using OpenCL, which is an independent framework for writing performance oriented, data parallel code for a wide variety of microarchitectures.

There are several challenges when programming embedded GPUs. First, as with heterogeneous platform—a platform comprised of a set of different processors—the programmer must manually identify which components of the application to map to coprocessors. Even after carefully implementing these components, the programmer must adjust parameters that affect performance in ways specific to the processor. Luckily, OpenCL provides mechanisms to allow the programmer to query the runtime environment to get hints on how to set these parameters for the specific processor used.

This chapter revisits Horner’s method kernel to illustrate the concepts and performance factors involved in OpenCL programming. Recall that our Horner’s method kernel performs the following loop:

```
1 for i = 0 to n-1
2 sum = coeff[0]
3 for j = 1 to 
4 sum = sum * input_val[i]
5 sum = sum + coeff[j]
6 endfor
7 endfor
```

The performance bottleneck in this code is the dependency between lines 4 and 5. In Chapter 2 we addressed this using two different approaches: software pipelining, which focused on the inner loop, and explicit SIMD parallelism, which focused on the outer loop.

| Lane 2 | it 2, In 4 | it 6, In 4 | it 10, In 4 | it 14, In 4 | it 6, In 5 | it 10, In 5 | it 14, In 5 |
| Lane 3 | it 3, In 4 | it 7, In 4 | it 11, In 4 | it 15, In 4 | it 3, In 4 | it 7, In 5 | it 11, In 5 | it 15, In 5 |

Figure 5.1 Pipeline execution. "it" for "iteration number" and "in" for "line number". The four-cycle latency between lanes 4 and 5 of iteration 0 is hidden by instructions from other iterations.

GPUs can use both approaches simultaneously without assembly language or intrinsics by combining SIMD datapaths with dynamically leaving instructions from different iterations of the outermost loop in the same execution pipeline. This allows GPUs to use instructions from other threads to hide the latency required by data dependencies and load instructions, providing parallelism. On the other hand, instruction executed can perform one operation from multiple iterations of the root, providing data-level, or SIMD parallelism.
