GPUs can use both approaches simultaneously without assembly language or intrinsics by combining SIMD datapaths with dynamically leaving instructions from different iterations of the outermost loop in the same execution pipeline. This allows GPUs to use instructions from other threads to hide the latency required by data dependencies and load instructions, providing parallelism. On the other hand, instruction executed can perform one operation from multiple iterations of the roost, providing data-level, or SIMD parallelism.

Returning back to our example, the GPU is executing the inner loop. Also, as multiply from line 4 requires a four-cycle latency. Normally this requires three stalls after each time line 4 is executed. Instead of issuing stalls, the GPU will issue three instructions, one from each of three other iterations of the outer loop. This way, the GPU can keep the pipeline without needing to insert any stalls. The GPU may have four lanes, meaning that it can issue one instruction from each of four iterations of the outer loop in each cycle.

Figure 5.1 shows how a four-SIMD lane would execute this loop assuming it was processing 16 iterations of the outer loop. Notice that the latency required by the dependency between lines 4 and 5 can be covered by instructions from the other iterations. In order to support the resulting throughput, GPUs contain many parallel functional units and extremely large registers.

# 5.2 OpenCL

Like OpenMP, OpenCL presents the programmer with a multi-threaded programming model. In OpenCL, threads are called work-items. As with OpenMP, a thread, or work-item, is a serial stream that works cooperatively with others to advance the objective of the program.
