
# Create databases, queries, and forms

## Data Master

![](img/e39350c3a7c0d527d71b0e4097a0ba66_39_0.png)

We show you how to set up a database in LibreOffice Base and search it with SQL queries embedded in forms.

By Robert Großkopf, Kerstin Großkopf, and Joe Casad

**B**ase is the relational database for the LibreOffice suite. A database is a tool that organizes data into a structured and easily accessible form. You might be thinking “I thought that is what the LibreOffice Calc spreadsheet does,” and, if so, you would be correct. A database and a spreadsheet both store data in a structured form. A spreadsheet is more useful for some kinds of problems, such as a financial ledger. A database, on the other hand, is designed for easy search and data entry, and it scales more easily to larger datasets.

A database is meant for situations where the user has a collection of discrete data objects or records with similar attributes. The classic example is something like a library card catalog – a series of similar items with a similar collection of fields, showing the title, author, catalog number, and a description of the book.

Base provides an easy user interface for creating and managing a database. Base Version 6.1 is transitioning to the Firebird database engine. Previous versions of Base used the HSQL engine. You can also use Base to connect to existing database files in a number of different formats. According to the LibreOffice project, “LibreOffice Base natively supports some flat file database formats, such as the dBASE format. You can also use LibreOffice Base to connect to external relational databases, such as databases from MySQL or Oracle…”

The Base user interface supports a number of wizards and design aids that make it easy to create a database or build a form to enter data into a database. When you launch Base for the first time, the Create Database wizard will ask you if you want to create a new database. The Base main window is shown in Figure 1. Icons along the left side make it easy to create tables, queries, forms, and reports.

A database begins with a design. A database design includes many considerations and can be a complicated task, depending on the nature of your data. For the purposes of this tutorial, in the interest of maximizing the information within the available space, I will describe a typical database scenario and take you through the steps of designing and building the database, then setting up forms and queries. For additional information on working with Base, see the LibreOffice Getting Started Guide [1] and the Base Handbook [2].

### Designing a Database

The example in this article is a simple database for storing an inventory of equipment for a company. Table 1 shows the basic database fields. The *Article* is a description of the object. The database also includes information on the room where the object is located, the rack or cupboard number where the object is stored, as well as the category of the object, the number of objects at the location, and the URL to a digital image of the object.

| TABLE 1: DATABASE FIELDS | | |
| :--- | :--- | :--- |
| **Field Name** | **Field Type** | **Description** |
| Article | Text [VARCHAR] | Object description |
| Image | Text [VARCHAR] | Image of the object linked to the database by its URL |
| Room | Text [VARCHAR] | Room name |
| Cupboard | Small Integer [SMALLINT] | Cupboard number |
| Rack | Small Integer [SMALLINT] | Rack number |
| Number_Needed | Small integer [SMALLINT] | Number of required objects |
| Category | Text [VARCHAR] | Article type (e.g., electronics, optics, etc.) |

![](img/e39350c3a7c0d527d71b0e4097a0ba66_40_0.png)

The data in Table 1 could all reside in one table, however, if some fields occur multiple times with the same data, it is often more efficient to split the reoccurring data into a separate table and connect it to the main table by a unique *ID* field assigned as a primary key (Table 2).

A simple inventory database could be compiled with just the following three tables: Every *Article* would be assigned no more than one *Category* and one *Place* (*Room*, *Cupboard*, and *Rack*). In database-speak, this is known as a many-to-one (n:1) relationship, which suffices as long as something is assigned only once. For this example database, however, each article can have multiple storage options and *vice versa* – that is, a many-to-many (n:m) relationship. To ensure this connection, an additional table has a new *ID* created from the *ID* from *Article* and *ID* from *Place*, both primary keys, and with *Number_Needed* moved over from the *Article* table (Figure 2).

| TABLE 2: DATABASE TABLES | | |
| :--- | :--- | :--- |
| Article ID | Category ID | Place ID |
| Article | Category | Room |
| Image | | Cupboard |
| Number_Needed | | Rack |

### Creating the Database

These tables are now created one by one in an internal Firebird database:

-   Start the Database Wizard in LibreOffice with *File* | *New* | *Database*.
-   Select the *Create a new database* radio button and choose *Firebird Embedded* from the drop-down.
-   Click *Finish* to save a database file that does not need to be registered. After naming and saving the file, a multi-table window opens; starting in the Tables section and in the Tasks pane, choose *Create Table in Design View*. (To get this one, you need Java. Go to *Tools* | *Options* | *Advanced* to see the Java runtime environments that are present on your system and choose one of them.)

A blank database table should open in which you can enter the names of fields in the Field Name column and the kinds of fields in the Field Type column.

The field type for all *ID* fields and all fields connected to an *ID* field should be type *Integer*. For each *ID*, set *AutoValue* to *Yes*, in the Field Properties section (Figure 3); so the field will be incremented automatically and set as the primary key of the table. To do so, mark the first key with the left mouse key, hold “Shift” and mark the next.

For the *Article* field, set *Entry Required* to *Yes* under Field Properties. Save each table with its name (i.e., *Article*, *Category*, or *Place*). In the rel_Article_Place table that establishes the many-to-many relationships, you need to create two primary keys (see Figure 2).

After saving every table, open *Tools > Relationships* and create the connections by selecting and dragging from the primary key (*ID*) to the foreign key, as in Figure 2.

### Data Entry Form

Entering data directly into the table works pretty well with a table like *Category*, which only has one field other than the automatically numbered *ID*. In the *Place* table, all rooms, cupboards, and racks also can be filled in directly. The *Article* and rel_Article_Place tables, on the other hand, are more difficult to fill because both tables have fields for which the primary key is set as a foreign key in a different table. Therefore, both of these tables are good candidates for an input form.

To create a form, click on *Forms* in the sidebar and choose *Use Wizard to Create Form*. A window with a sidebar shows eight steps for creating a form.

1.  **Field selection.** The wizard opens with the Article table already chosen in a drop-down in the main wizard window. All fields should show in the main form, so use the double-arrows to transfer them from the left box (list of available fields) to the right box (list of fields to appear in the form).
2.  **Set up a subform.** Unfortunately, this step does not yet work automatically with the newly built in Firebird database, so you have to choose tables and link fields in the next steps yourself. Choose *Subform based on manual selection of fields*.
3.  **Add subform fields.** Choose the rel_Article_Place table in the drop-down and move all fields to the rightmost box.
4.  **Get joined fields.** Link the *ArticleID* field of the subform (rel_Article_Place table) with the *ID* field of the main form (Article table).
5.  **Arrange controls.** The wizard now helps you lay out the interface in one of four formats. You can leave the entry form as a table, present the data entry cells in columnar form with labels to the left or on top, or arrange the form in *Blocks – Labels Above*. In this example, I display the main form in columns with labels on top, and I leave the subform as a *Data Sheet*. Now all places mentioned by an *Article* can appear in a form view.
6.  **Set data entry.** Leave this step as is.
7.  **Apply styles.** This step is a matter of taste. As shown in Figure 4, the background for the form is set to *Light Gray* and the border to *Flat*.
8.  **Set name.** The form is now usable, but has a number of weaknesses; therefore, after entering a name, choose *Modify the form* and click *Finish*.

The following weaknesses can now be resolved:

-   The *Image* field shows only the path to the image, not the image itself.
-   The *ID* field is editable (although not visible here). A write protection should prevent modification of the primary key.
-   The *CategoryID* field shows the foreign key value (the Category table ID), not the *Category* value itself.
-   In the table foreign field (the sub-form) the foreign key value of *PlaceID* is shown instead of the contents of the *Place* table *ID*.
-   The display of *ArticleID* is not necessary because the value is already shown in the *ID* field of the main form.

If the form is not editable, close then re-open the form by right-clicking the form name and choosing *Edit* in the context menu. The fields will now be edited in the same order as arranged in the table.

Right-click again and choose *Control* to get the Properties dialog. In the *General* tab, click *Scale > Keep Ratio* in the drop-down so the image will not appear distorted.
