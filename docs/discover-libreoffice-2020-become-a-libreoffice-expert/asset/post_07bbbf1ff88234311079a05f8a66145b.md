That leads to the code of inspect.py, shown in Listing 3. This version of the code solves the initial problem of changing every occurrence of "Linux" with "Windows," and its work is split into four steps:

1. Read the contents of content.xml into a string variable. You have already seen this done in Listing 2.
2. Build the XML namespace dictionary. A dictionary is a variable that can be used like an array, but with strings instead of numbers as index values. So while an array `["First entry", "Second entry", "Third entry"]` stores the following mapping:
   0 -> "First entry"
   1 -> "Second entry"
   2 -> "Third entry"
   
   a dictionary `{"first":"one", "second":"two"}` stores this mapping:
   "first" -> "one"  "second" -> "two"
3. In the third step, I access the XML element tree, starting at the root element, `root.findall("//", ns)` finds all elements (including those without any readable content), but in the next line I check the text attribute, which is void (false) if there is no text. Note how this `findall` call takes an extra argument: the second argument is the namespaces dictionary.
4. The last step creates a new zip file: the `zipfile` module is not able to modify existing files (which would otherwise be the obvious thing to do: Remove the old /content.xml and add the new version to the zip file). Instead I create a new zip file and then copy all files from the old to the new zip file, with the exception of /content.xml. It is added at the end (in lines 35–36). (The `with` keyword enables a Python feature that automatically closes the opened file when you leave the with block.)

Line 27 contains a modification: The old text (`x.text`) is replaced with a new version (`x.text.replace("Linux", "Windows")`) – this is the place where you can modify the script to do whatever you like.

We did not use the more specific `root.findall('.//text:p') + root.findall('.//text:span')` because it would present the elements in the wrong order (first all the `text:p` and then all the `text:span` elements).

Since the script filters further for the existence of some text (content), it does not matter.

And that’s it. With some small changes, you can let the script evaluate more command-line arguments and turn it into a universal search and replace tool. Create a for loop (like in `loggrep.py` in Listing 2) to apply your changes to several files at once.

### LISTING 3: inspect.py

```python
#!/usr/bin/env python

from zipfile import ZipFile, ZIP_DEFLATED
from sys import stdout, argv    # command line arguments
from xml.etree import ElementTree as et
from re import findall

filename, outputfilename = argv[1], argv[2]

# Step 1: Read /content.xml inside zip file
inZipf = ZipFile(filename, 'r')
content = inZipf.open("content.xml", 'r').read()  # access /content.xml

# Step 2: Build the XML namespace dictionary
ns = {}                                            # {} = empty dictionary
for namespace in findall('xmlns:.*=".*"', content):
    namespace = namespace.split(":")[1]            # get rid of "xmlns:"
    nsurl = namespace.split("=")[1]                # cut " in front/back
    nsurl = nsurl[1:-1]                            # add to dictionary AND
    ns[namespace] = nsurl                          # register for ElementTree module
    et.register_namespace(namespace, nsurl)

# Step 3: Access the XML tree
root = et.fromstring(content)
for x in root.findall("//", ns):
    if x.text:                                     # any text inside?
        x.text = x.text.replace("Linux", "Windows") # modify the content

# Step 4: Create output file
with ZipFile(outputfilename, "w") as outZip:        # open zip file for writing
    outZip.comment = inZipf.comment                 # copy archive comment
    for file in inZipf.infolist():                  # copy all files except /content.xml
        if file.filename != "content.xml":
            outZip.writestr(file, inZipf.read(file.filename))
with ZipFile(filename, mode="a", compression=ZIP_DEFLATED) as outZip:
    outZip.writestr("content.xml", et.tostring(root)) # add new content.xml

# Clean up
inZipf.close()                                       # not really needed...
```

To avoid ambiguity, you can prefix each tag with a namespace identifier. So `<title>` from the XHTML world could become `x:title`, and `<title>` from the DC world could become `<dc:title>`. Those namespaces have to be declared in the header of the XML file. For the XHTML/DC example, this could look as follows:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<myroot
 xmlns:x="http://www.w3.org/1999/xhtml"
 xmlns:dc="http://purl.org/dc/terms/">
...
</myroot>
```

It is possible to have one namespace that works without a prefix, but in case of LibreOffice documents, every namespace is assigned a prefix. Python's `xml.etree.ElementTree` implementation expects that you use a dictionary that translates from prefixes to URLs. Python programs for an early version of this article contained a rather long code block that manually created this dictionary (Figure 6), because LibreOffice uses 38 different namespaces at once. However, since all the information on namespaces is also stored in the root element, it makes more sense to parse it and auto-generate the dictionary.

Building the dictionary works by searching for the pattern `xmlns:name="url"` which is more flexible. The name `<dictionary>` makes sense. For example, an English-German dictionary might be stored in a Python dictionary as `en_de = {"one": "eins", "two": "zwei", "three": "drei", ...}`, and `en_de("one")` will return "eins". and then splitting each matching string and stripping away the parts which are not needed (the `"` signs).

### DATA IN CALC SHEETS

The XML for a Calc sheet must follow different rules than the XML for a Writer document: After all, Calc requires a strict ordering of each sheet into columns and rows. Figure 7 shows a fragment of a Calc file’s content.xml, which I have reformatted (line breaks and indentation) for better reading.

There is some redundancy in how Calc stores the cell contents. When you enter the number 6 in a cell and then format it as a currency cell, the entry will be stored as:

```xml
<table:table-cell
office:value-type="currency"
office:currency="USD"
office:value="6"
calcext:value-type="currency"
<text:p>6,00</text:p>
</table:table-cell>
```

Actually, this redundancy is helpful: Calc stores the value (6) and formatting hints (currency, USD) in attributes of `<table:table-cell>`, and the content of that tag is a `<text:p>` tag, which holds the readable (formatted) representation as it appears when editing.

The same happens for a formula, such as:

```xml
<table:table-cell
 table:formula="of:SUM([.B3;.B4])"
 office:value-type="currency"
 office:currency="USD"
 office:value="11"
 calcext:value-type="currency"
<text:p>$11.00</text:p>
</table:table-cell>
```

Here, the real content (from Calc’s point of view) is the formula, which is stored as `of: =SUM([.B3;.B4])`. However, the text field shows `$11.00`, because the cell has also formatted as US Currency. Modifying Calc cells is beyond the scope of this article (since you would have to get the dependencies right), but it is possible: The `xml.etree.ElementTree` module lets you inspect element attributes, too.

Searching a document is no problem; `loggrep.py` shows the matches inside `<text:p>` tags:

```bash
$ ./loggrep.py l1 calc-test2.ods
calc-test2.ods:t11.00/<text:p>
```
