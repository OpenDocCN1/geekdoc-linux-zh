
# Linux 备份与恢复指南

ccurley at trib dot com

想象你的硬盘驱动器刚刚变成了一个非常昂贵的冰球拍。想象一下你的家里经历了一场火灾，你的电脑箱现在看起来就像萨尔瓦多·达利会画出来的作品。现在该怎么办？

全恢复（Total restore），有时称为裸机恢复（bare metal recovery），是在灾难性故障后重建计算机的过程。为了进行全恢复，你必须拥有完整的备份，不仅是你的文件系统，还包括分区信息和其他数据。本 HOWTO 是一个分步教程，旨在教你如何备份 Linux 计算机以便能够裸机恢复，以及如何进行该裸机恢复。它包含了一些相关的脚本。

## 1. 引言

正常的裸机恢复过程是：从产品磁盘安装操作系统。安装备份软件，以便你可以恢复数据。然后通过验证你的配置文件、权限等来获得恢复功能。本 HOWTO 中解释的过程和脚本将恢复从生产计算机备份的文件。当你恢复系统时，你的配置将保持完整，这将为你节省大量时间。

## 2. 概述

下面所示的过程并不简单，并且对你的数据造成危险。在需要之前请进行练习！我就是这么做的，并且在一台牺牲计算机上进行了练习！

本 HOWTO 的目标计算机是一台 Pentium 电脑，在一个 IDE 硬盘上安装了 Red Hat 7.1 Linux 服务器或工作站。目标计算机并没有大量数据，因为它被设定为一个“牺牲性”的测试平台。我不想在生产环境计算机和生产数据上测试这个过程。此外，在开始测试之前，我进行了全新的安装，以便在需要时可以随时重新安装到已知的配置。

### 注意

示例命令在大多数情况下将显示我为了恢复目标系统必须输入的内容。你可能需要使用类似的命令，但使用不同的参数。确保你复制的是自己的系统，而不是测试计算机的设置，这取决于你。

基本步骤列在 W. Curtis Preston 的著作《Unix Backup & Recovery》（O'Reilly & Associates, 1999）中，我在《Linux Journal》中对该书给予了好评。然而，这本书在特定的、实时的问题上略显单薄。例如，你究竟要备份哪些文件？你需要保留哪些元数据，以及如何保留？

在开始该过程之前，在本 HOWTO 中记住一个事实：你需要使用典型的备份工具（如 Amanda, BRU, tar, Arkeia 或 cpio）备份你的系统。那么问题是，如何从烧毁的硬件恢复到运行恢复程序并恢复你数据的程度。

基于 Red Hat 包管理器 `RPM` 的 Linux 发行版用户也应该保存普通备份的 RPM 元数据类似于：

```bash
bash# rpm -Va /etc/rpmVa.txt
```

在你的备份脚本中使用此命令，将为你裸机恢复后提供一个比较基础。

要实现这一点，你需要：

- 你的硬件重新运行，根据需要更换组件。BIOS 应该正确配置，包括日期时间和以及硬盘参数。目前没有考虑到更换硬盘。
- 一个并口 Iomega-ZIP 驱动器或等效设备。你需要至少 30 MB 的空间。
- 你的备份介质。
- 一个允许你运行恢复软件的最小 Linux。

要达到这一点，你需要至少两个阶段的备份，可能需要三个。具体备份什么以及在哪个阶段备份，取决于你的恢复过程。例如，如果你正在恢复一台服务器，在恢复过程中可能无法联网。因此，只在常规备份中备份网络部分。

你将分阶段进行恢复。在第一阶段，我们构建分区、文件系统，并从 ZIP® 磁盘恢复一个最小文件系统。第一阶段的目标是能够启动一台带有网络连接、磁带驱动器、恢复软件或第二阶段所需的任何东西的运行计算机。

第二阶段（如果有必要）包括恢复备份软件和任何相关的数据库。例如，假设你使用 Arkeia 正在构建一个用于裸机的 ZIP® 磁盘。Arkia 在服务器硬盘上保留了一个巨大的数据库。你可以从磁带恢复该数据库。相反，使用 tar 和 gzip 备份整个目录 `/usr/bin`，并通过 nfs 或 ssh 保存到另一台计算机。第一阶段（我们在下方定义）不包含 X，所以如果你希望将 X 作为你的备份程序，你需要做一些工作。某些恢复需要 X。当然，如果你使用某些备份程序，你需要做一些工作。你需要找到所需的目录和文件。如果你使用 tar, gzip, cpio, mt 或 dd 等恢复工具，它们将从 ZIP® 磁盘保存并恢复。

最后阶段是从磁带或其他介质的全恢复。在完成该阶段后，你应该能够启动一个完全恢复并运行的系统。

#### 2.1. 局限性

HOWTO 局限于创建一个最小备份，即使是简述也不详尽。你仍然需要进行一些研究、编辑和测试。这里的脚本完全按照源硬盘上的状态恢复分区数据。如果在相同的计算机或硬盘上进行恢复，这样很好，但并非如此。在读完 HOWTO 的其余部分后，有两种解决方法：

- 编辑分区表。我做过几次。你也可以添加或删除分区（但也要使用分区表的脚本）。
- 构建一个新的分区表，并从那里开始。这就是 `restore_metadata` 没有调用 `fdisk` 的原因。另一个是我不知道哪些硬盘。这里显示的脚本只处理 ext2、FAT12 和 FAT16。在执行这些脚本之前，你需要其他工具来备份和恢复未涵盖的文件系统。分区看起来很有用。

> 警告 按计划进行常规备份。如果不这样做，本 HOWTO 是没用的。

自己构建一个救援磁盘。它有详细的文档，并将许多工具打包到一个磁盘中。有一个活动列表，我的几个问题得到了快速回答。接下来，确定如何备份操作系统。我遵循了 Preston 的建议并使用了并口 ZIP 驱动器。硬盘获得了大约 90 MB 的可用存储空间。我需要大约 85 MB 来备份我的桌面，所以 100MB ZIP 驱动器可能会挑战运气。

## 4. 创建阶段1备份

制作生产备份后，你需要保留分区信息以便重建分区。

`make.fdisk` 脚本扫描硬盘分区信息并将其保存到两个文件中。其中一个可执行脚本，命名为 `make.dev.x`。另一个 `dev.x`（其中 "x" 是设备文件名，例如 `hda`）包含 `fdisk` 的命令。你通过将关联设备文件作为 `make.fdisk` 的参数来指定为哪个硬盘构建脚本（以及相应的文件名）。例如，一个典型的 IDE 系统：

```bash
bash# make.fdisk /dev/hda
```

输出脚本 `make.dev.hda` 和 `fdisk` 的输入文件 `dev.hda`。

此外，当 `make.fdisk` 遇到 FAT32 分区时，它会将分区的引导区保存在名为 `dev.xy` 的文件中，其中 x 是设备名（例如 `sdc`），y 是分区号。引导区是分区的第一个扇区（512）。该扇区在重建分区的同时在 `make.dev.hda` 脚本中恢复。

幸运的是，硬盘价格下降的速度比选举后公众对政客的信任还要快。因此，输出文件是文本且容易很好。现在，这是在较大的分区上重建的唯一方法（参见待办事项 http://example.com/to-do-list）。



其他元数据保存在 `save.metadata` 脚本中。脚本将分区信息保存在 ZIP 磁盘根目录下的 `fdisk.hda` 文件中。打印此文件和你的 `/etc/fstab` 是个主意，这样当你需要手动恢复分区数据时就有纸质。你可以通过在两个控制台之间切换来保存它，在其中一个运行 `fdisk` 并根据需要 `cat /etc/fstab` 或 `fdisk.hda`。然而，这样做容易出错。

你还需要为你的恢复方法保留文件。例如，如果你使用 `nfs` 保存数据，你需要保留 `hosts`、`devs` 等。此外，如果你正在使用任何基于网络的恢复过程（如 `Amanda` 或 `Quick Restore`），你需要保留网络文件，如 `HOSTNAME`、`hosts` 以及相关的软件树。

处理此类类似问题最简单的方法是保留整个 `etc` 目录。

像 100 MB ZIP 驱动器是不可能装下现代 Linux 发行版的服务器安装的。我们必须比简单的保留全部更具选择性。我们需要哪些文件？

- `boot` 目录。
- `/etc` 目录及其子目录。
- 启动时需要的目录。
- `/dev` 中的设备文件。

要确定启动所需的目录，我们需要查看启动文件 `/etc/rc.sysinit`。它设置了唯一的路径如下：

```
PATH/bin:/sbin:/usr/bin:/usr/sbin
export PATH
```

尝试表明，我们还需要其他目录，例如 `/dev`。在 Linux 中，如果没有设备文件，你什么也做不了。

在阅读 `save.metadata` 脚本时，请注意我们并不一定是在保存使用绝对路径调用的文件。

在获得可用的备份脚本之前，我们可能需要进行多次备份、测试裸机恢复、从 CD 重新安装并再次尝试。在我编写此 HOWTO 期间，我经过五次这样的迭代才成功完成恢复。这就是为什么尽可能使用脚本的原因之一。请务必彻底测试！

## 5. 启动 tomsrbt

在开始恢复过程之前，要做的第一件事是验证硬件时间是否设置正确。请使用 BIOS 设置进行此操作。时间设置得多精确取决于你的应用程序。对于恢复来说，时间误差在几分钟内就足够准确了。这将允许时间敏感的事件在你最终启动恢复后的系统时，能够从之前中断的地方继续。

在启动 `tomsrbt` 之前，请确保你的 ZIP® 驱动器连接在并行端口上，即 `/dev/lp0` 或 `/dev/lp1`。启动软件将自动为你加载并行端口 ZIP® 驱动程序。

下一步是设置视频模式。我希望屏幕上显示的内容尽可能多。在选择视频模式的选项时，使用 6， 80 列 60 行。你的硬件可能无法处理那么高的分辨率，所以请进行尝试。

一旦 `tomsrbt` 启动并且你有了控制台，请挂载 ZIP® 驱动器。仅以只读方式挂载可能是一个好主意：

```
# mount /dev/sda1 /mnt -ro
```

检查它是否在位：

```
# ls -1 /mnt
```

然后切换到 ZIP® 驱动器上脚本所在的目录。

```
# cd /mnt/root.bin
```

现在运行分区信息的脚本，例如：

```bash
# .make.dev.hda
```

此脚本将执行：

- 清除硬盘的前 1024 字节，销毁任何现有的分区表和主引导记录 `MBR`。
- 根据你运行 `make.fdisk` 时收集的信息重新创建分区。
- 根据情况创建 `ext2` 文件系统分区和 Linux 交换分区。
- 创建某些类型的 FAT 分区。
- 为你创建挂载点和 `ext2` 分区。

> 注意

如果你有其他操作系统需要恢复，现在是进行操作的好时机。首先，重启 `tomsrbt` 以完成 Linux 部分。你必须挂载刚刚构建的分区。创建一个新的、独立的脚本，将这些分区挂载到 `make.dev.x` 脚本的末尾。

一旦你创建了所有目录并将分区挂载到它们上，就可以运行 `restore.metadata` 脚本。这将把 ZIP® 驱动器的内容恢复到硬盘。

## 5. 启动 tomsrbt

你应该能看到 ZIP® 磁盘根目录的目录列表，然后是恢复中的归档文件列表。`tomsrbt` 上的 `tar` 会告诉你 `tar` 的块大小为 20，这没关系。你可以忽略它。请确保 `lilo` 输出了它的结果：

```
Added linux *
```

随后将是 `df -m` 命令的输出。

如果你通常直接启动到 X，可能会遇到一些问题。为了安全起见，请临时更改启动运行级别。在 `/target/etc/inittab` 中，找到类似下面这一行：

```
id:5:initdefault:
```

将其更改为：

```
id:3:initdefault:
```

现在，你可以优雅地重启了。如果你还没有这样做，请从软驱驱动器取出 `tomsrbt` 软盘，并给电脑一个“三指礼”（或其等效操作）：

```
shutdown -r now
```

电脑将关机并重启。

## 6. 第二阶段恢复

当电脑重启时，回到 BIOS 验证时钟是否大致正确。

一旦验证时间正确，退出 BIOS 并重启到硬盘。。你可以直接让电脑按照正常顺序启动。你将看到很多错误信息，大部分是“我找不到某某！哇！”之类。如果你到目前为止工作都做得正确，那么这些错误信息就无关紧要。你不需要 `linuxconf` 或 `apache` 来完成你需要做的工作。

### 注意

作为替代方案，你可以启动到单用户模式（在 `lilo` 提示符处输入 `linux single`），但你必须手动配置网络并设置 `sshd` 或任何你恢复系统所需的守护进程。你的具体操作方式取决于具体的系统。

你应该能够登录到 `root` 控制台（没有 X 用户——抱歉）。你现在应该可以使用网络了，例如通过 `nfs` 挂载你的系统备份。

如果你按照我为 `Arkeia` 建议的两个阶段备份，现在可以恢复 `Arkeia` 的数据库和可执行文件。你应该能够运行

```
/etc/rc.d/init.d/arkeia start
```

并启动服务器。如果你在安装了 X 的另一台电脑上安装了 GUI，现在可以在另一台电脑上登录 `Arkeia`。

> 注意

恢复时，请仔细阅读文档。例如，除非使用 `-k` 选项，否则 `tar` 不覆盖文件。

这是正常的，因为 `tar` 正在覆盖你在第一阶段恢复的文件。

然后你重启。在关机过程中，你将看到很多错误信息，例如“没有此 pid”。这是过程的正常部分。关机代码使用了未启动的守护进程的 pid 文件。

你的系统应该正常启动，错误信息比以前少得多，理想情况下完全没有错误。在 RPM 系统上测试恢复效果好坏的“酸测试”方法是验证所有包：

```
rpm -Va
```

某些文件（如配置和日志文件）会在正常过程中发生变化，你应该在报告中将它们手动过滤掉。你可以将输出重定向到文件，并与备份时制作的文件 `etc/rpm.txt` 进行对比，从而大幅加快这一步骤。Emacs 用户应该检查它的差异功能。

现在你应该已经运行了。是时候测试你的应用程序了，特别是那些作为守护进程运行的。应用程序越复杂，可能需要的测试越越多。如果你有远程用户，在测试期间使用系统禁用他们，或将其设置为“只读”。这对于数据库尤为重要，可以防止任何损坏或数据丢失恶化。

如果你通常启动到 X 且在上面禁用了它，请在重新启用之前测试 X。通过将 `/etc/inittab` 中的该行改回来重新启用：

```
id:5:initdefault:
```

你现在应该准备好战斗了——还需要一些止痛片和沙发。

## 8. 应用程序特定说明

我在下方列出了关于备份特定应用程序的注意事项。

### 8.1. Squid

`Squid` 是一个 http 代理和缓存服务器。由于它在硬盘上保留了大量临时数据，备份这些数据没有意义。请在你的第二阶段备份脚本中相应的 `tar` 命令中插入 `--exclude /var/squid/squid`。然后，让 `squid` 为你重建目录。在第二阶段恢复脚本的末尾添加命令以进行初始化。这是我通过 `ssh` 恢复到 `restore.tester` 的做法：

```bash
ssh $target 'mkdir /var/spool/squid ; chown squid:squid /var/spool/squid; /usr/sbin/squid -z;touch /var/spool/squid/.OPB_NOBACKUP'
```

最后一个命令创建了一个长度为 0 的文件 `OPB_NOBACKUP`。这是为了 `Arkeia` 的考虑，告诉 `Arkeia` 不要备份此目录。

### 8.2. Arkeia

`Arkeia` 是一个运行在多种平台上的备份恢复程序。你可以将 `Arkeia` 作为裸机恢复方案的一部分，但有两个注意事项。



第一个是最问题的，因为在没有更优雅解决方案的情况下，你必须在恢复时在导航器中手动选择要恢复的目录。原因是显然，Arkeia 没有任何恢复磁盘上已存在文件的机制（不类似于 `tar -p` 选项）。如果你直接允许全量恢复，恢复将崩溃，因为 Arkeia 会覆盖在恢复时正在使用的库，例如 `lib/libc-2.1.so`。在执行时选择要恢复的目录是最好的，因此我不建议这样做。

第二个是你必须备份 Arkeia 的数据字典和/或程序。要做到这一点，请修改 `save.metadata` 脚本，将 Arkeia 添加到保存的目录列表中：

```bash
## Arkeia specific:
tar cf - /usr/knox | gzip -c $zip/arkeia.tar.gz
```

你必须备份数据字典，因为 Arkeia 不会备份数据字典。这是我对 Arkeia 的不满之一，我通过使用 The TOLIS Group 的 BRU 将数据字典保存到磁带来解决这个问题。

## 9. 关于灾难恢复的一些建议

你应该为每台计算机准备一个 ZIP® 磁盘和打印件，并将它们存放在安全位置。离地备份的主要目的是实现灾难恢复，将恢复到替换硬件是灾难恢复的一部分。你应该在离地备份存储处保留此指南的副本，以及一些软盘和可能的 ZIP® 驱动。

您可以在任何媒介上复制和分发本文文档，无论是商业性的还是非商业性的，前提是所有副本都必须包含本许可、版权声明以及说明本许可适用于本文文档的许可公告，并且您没有在本许可的条件的基础上添加任何其他条件。您不得使用技术措施来阻止或控制对您制作或分发的副本进行阅读或进一步复制。然而，您可以接受作为副本交换的报酬。如果您分发了足够数量的副本，则还必须遵守第 3 节中的条件。

您还可以在上述相同条件下借出副本，并公开展示副本。

## 3. 大批量复制

如果您出版了超过 100 份本文文档的打印副本，且文档的许可声明需要封底文本（Cover Texts），则你必须将副本装在封底内，并在封面上清晰、易读地载所有这些封底文本：封面的“封面文本”和底面的“封底文本”。两个封底都必须清晰、易读地标识您为这些副本的出版者。封面必须呈现完整标题，且标题中的所有文字均同等突出且可见。您还可以在封面上添加其他材料。只要更改仅限于封底，且保留了文档标题并满足任一封面的要求的文本，在其他方面均可视为逐字复制。

如果任一封面的要求的文本过多，无法清晰容纳，您应将列出的前面的文本（在合理范围内容纳的数量）放在实际封面上，并将剩余部分延续相邻页面。

如果您出版或分发了超过 100 份不透明副本（Opaque copies）的本文文档，您必须在每个不透明副本中包含一份机器可读的透明副本（Transparent copy），或者在每个不透明副本中说明一个公共可访问的计算机网络位置，该位置包含一份完整的、未添加额外材料的文档透明副本，普通用户可以使用公共标准网络协议匿名免费下载。如果您使用后一种方案，在开始大批量分发不透明副本时，必须采取审慎的步骤，以确保您的透明副本在指定位置保持可访问，直到您最后一次向公众分发（直接或通过您的代理或零售商）该版本的不透明副本后至少一年。

建议您在重新分发任何大量副本之前尽早联系文档的作者，以便他们有机会为您提供文档的更新版本。

## 4. 修改

您可以在上述第 2 节和第 3 节的条件下复制和分发本文文档的修改版本（Modified Version），前提是您完全按照本许可发布修改版本，使修改版本充当文档的角色，从而许可任何拥有该版本副本的人对修改版本进行分发和修改。此外，您必须在修改版本中完成以下事项：



- 在标题页（以及封面，如有）上使用任何不同于文档标题以及之前的版本标题（如果有之前的版本，它们将列在文档的“历史”部分）的独特标题。如果该版本的原作者许可，您可以使用该标题作为前一个版本的标题。

- 在标题页上注明：修改版本的出版者名称，作为出版者。
- 保留文档的所有版权声明。
- 在其他声明旁边为您的修改添加适当的版权声明。

# 6. 文档集合

您可以制作一个由本文档和其他根据本许可发布的其他文档组成的集合，并将各个文档中本许可的单独副本替换为该集合中包含的一份单一副本，前提是您在所有其他方面都遵循本许可中对集合中每份文档进行逐字复制的规定。

您可以从此类集合中提取出单份文档，并根据本许可对其进行单独分发，前提是您在提取的文档中插入本许可的副本，并在关于该文档的逐字复制的所有其他方面均遵循本许可。

# 7. 与独立作品的聚合

将本文档或其衍生版本与其他单独独立的文档或作品汇编在存储或分发介质的卷中，整体上不视为本文档的“修改版本”，前提是未对该编译作品主张编译版权。此类编译作品被称为“聚合”（aggregate），本许可不适用于与本文档编译在一起的其他自包含作品，只要这些作品本身不是本文档的衍生作品，且因为因此被编译而受到本许可限制。

如果第 3 节的封面文本（`Cover Text`）要求适用于这些本文档副本，那么如果本文档少于整个聚合的四分之一，则本文档的封面文本可以放置在仅围绕聚合内本文档的封面上。否则，它们必须出现在围绕整个聚合的封面上。

# 8. 翻译

翻译被视为一种修改，因此您可以根据第 4 节的条款分发本文档的翻译版本。将“不变部分”（`Invariant Sections`）替换为翻译需要其版权所有者的特殊许可，但您可以在包含这些不变部分原始版本的同时，包含部分或所有不变部分的翻译。您可以包含本许可的翻译版本，前提是您也包含本许可的原始英文版本。如果翻译版本与本许可的原始英文版本发生冲突，则以原始英文版本为准。
