The problem is now that it can receive a new window size (i.e. a transmit credit) only together with a new packet. There is no acknowledgement, because it cannot send more data, which means the sender now depends on whatever other end sends. If the receiver does not have data to send, or if it was also granted a window having size null, then the communicating partners would wait eternally to be able to continue sending.

To solve this problem, the Transmission Control Protocol includes a mechanism known as zero-window probing. This mechanism is based on an additional timer, the probe timer. When this timer expires, a TCP packet is sent the advertising window has-size null. This packet consists of only a packet header: it does not carry payload, because data must not be transmitted in this situation.

The communication peer acknowledges this packet, and if the other end was able to remove its congestion, to some extent, in the meantime, a larger window is granted with this acknowledgement, so that the transmission of data can be resumed. If the window size occurs again, then the communication peers wait until the probe expires sending another probe.

void tcp_send_probe0(struct sock *sk)
{
    struct tcp_opt *tp = &(sk->tp_pinfo.af_tcp);
    int err;
    err = tcp_xmit_wakeup(sk);
    if (tp->packets_out || !tp->send_head) {
        /* Cancel probe timer, if it is not required. */
        tp->probes_out = 0;
        tp->backoff = 0;
        return;
    }
    if (err <= 0) {
        tp->backoff++;
        tp->probes_out++;
        tcp_reset_xmit_timer(sk, TCP_TIME_PROBE, min(tp->rto << tp->backoff, TCP_RTO_MAX));
    }
}
```

tcp_send_probe0(struct sock *sk) uses tcp_wakeup to generate and send a zero-window probe packet. If the probe timer is no longer needed, been from the fact that there is currently nothing to be sent (tp->send_head == NULL), or if there are still packets currently under way and their ACKs could contain new credits, it is not restarted, and the probes_out and backoff parameters are reset.
Otherwise, these parameters are incremented after a probe packet has been sent, and the zero-window probe timer is restarted, so that it expires again after some time. This time is tp->rto*2^tp->backoff or a maximum of TCP_RTO_MAX (120 seconds).

/* This routine sends a packet with out sequence
* It assumes the other end will try to ack it. */
static int tcp_xmit_probeb(struct sock *sk, int urgent)
{
    skb = alloc_skb(MAX_TCP_HEADER, GFP_ATOMIC);
    /* Reserve space for headers and set control bits. */
    skb_reserve(skb, MAX_TCP_HEADER);
    skb->csum = 0;
    TCP_SKB_CB(skb)->flags = TCP_FLAG_ACK;
    TCP_SKB_CB(skb)->sacked = urgent;
    /* Use a previous sequence. This should cause the other
    * end to ack. Don't queue or clone skb, just send it. */
    TCP_SKB_CB(skb)->seq = urgent ? tp->snd_una : tp->snd_una - 1;
    TCP_SKB_CB(skb)->end_seq = TCP_SKB_CB(skb)->seq;
    TCP_SKB_CB(skb)->when = tcp_timestamp;
    return tcp_transmit_skb(sk, skb);
}
```

tcp_xmit_probeb(sk, urgent) creates a TCP segment without payload, because the transmit window has size null and data currently not sent. alloc_skb() procures a socket buffer having length MAX_TCP_HEADER. As mentioned, no payload is sent, and the packet consists only of the TCP header.

The trick of this routine utilizes the fact that an old sequence number (i.e. a previously acknowledged sequence number) is written to the packet. tp->snd_una holds the first so far unacknowledged sequence number, means that tp->snd_una - 1 meets this purpose. The old sequence number causes the counterpart to send an acknowledgement. With this ACK, it also sends the current transmit window size, which is now, it is hoped, larger than null.

In the next line, the last sequence number is set to the first sequence number of this packet, which results in payload size end_seq - seq = 0. Subsequently, a timestamp is added to the segment, and the segment is sent by tcp_transmit_skb().

tcp_ack_probe(sk, ack) is invoked in tcp_ack() when a TCP segment with the ACK flag set is received and if it is suspected to be a reply to a zero-window probe segment. Depending on whether the segment opens the window (the first packet in the transmit queue affects the transmit window), tcp_clear_xmit_timer stops the zero-window probe timer or tcp_reset_xmit_timer restarts this.

### Protection Against Wrapped Sequence Numbers (PAWS)

The PAWS mechanism prevents a byte-sequence overflow, which would lead to inconsistencies occurring in connections with too large a bandwidth/delay product (i.e. when there is an excessive amount of data “in the pipe”).

The byte-sequence numbers of a TCP connection are of length 32 bits. With a sufficient transmission rate and an accurately large packet round-trip time, byte-sequence numbers can reach the end of the byte-sequence-number range within the time that a segment is delayed in router queues and thereby cause a byte-sequence-number overflow. In this case, the byte-sequence numbers take the initial value of the byte-sequence-number range. In this situation, the TCP protocol cannot identify delayed sequence duplicates if their byte-sequence numbers are within the window and consequently cannot drop them.

The PAWS mechanism was introduced to solve this problem. We use the Timestamps option, to protect the TCP protocol within a connection from problems caused by several segments having the same byte-sequence numbers. The PAWS mechanism operates basically by attaching timestamps to TCP segments and dropping a segment as a duplicate if its timestamp is smaller than the timestamp of the segment received last, which causes the receive window to move forward. (See Section 24.4.1).
