### 17.5.3 The DVMRP Routing Algorithm

The Distance Vector Multicast Routing Protocol (DVMRP) is the oldest multicast routing protocol; it was defined initially in [WaPD88] and extended later [Pau00]. DVMRP was the multicast routing protocol used as basis for MBone, and it has since remained the most popular... determines the shortest path to the sender. This means that it extends the principles of the RIP distance unicast routing protocol [Malk98] to multicasting capabilities.

DVMRP supports both physical network devices and tunnels as potential routes to forward multicast packets, mainly because these capabilities were required when MBone was introduced. This section briefly explains the approach of DVMRP, including a practical example.

### How DVMRP Works

To build a distribution tree, DVMRP in its current version uses a principle called Reverse Path Multicasting. The shortest path to the sender is learned when a multicast router receives a packet in a network adapter. If this route leads to the network device that received the packet, then it is forwarded to all neighboring multicast routers except for the interface that received the packet. Otherwise, the packet is discarded, because it doesn't arrive on an optimal route, which means that it is assumed that it does not originate from the direct path to the sender. More specifically, it is assumed to be a duplicate that might previously have been received. A multicast router is not able to see whether it has already received a packet or the packet is arriving for the first time. This is why packets are accepted only if it can be assumed they originate directly from the sender. This approach avoids a large number of duplicates—created by a routing principle flooding. Figure 17-15 shows how DVMRP works.

A unicast routing protocol is used to determine the shortest path to the sender. In this, the routed daemon does not use the kernel's unicast routing table, but instead builds separate tables. The routing information stored in these tables is exchanged between DVMRP routers in the network.

Though Reverse Path Multicasting enables multicast packets to be distributed across the entire network without creating duplicates, it doesn't consider whether a specific subnet in the multicast tree is interested in the packets of a group. Groups are simply distributed, which means they load the network with undesired packets. This is the reason why the method was extended to pruning. When a subnet of a router does not receive data for a specific multicast group, then the router can return a prune message to the higher-layer multicast router in the multicast tree. If this router doesn't have interested computers for a patch, an excessive number of packets from being forwarded in networks where there are no receivers. In addition, graft messages can be used to include a router or subnetwork in the distribution tree dynamically.

## 17.6 MULTICAST TRANSPORT PROTOCOLS

So far, we have actually discussed only unreliable and connectionless multicast transmissions based on UDP. This type of transmission is the most frequently used application multicast, mainly because it is much easier to handle. Nevertheless, there are application cases for connection-oriented and reliable multicast communication, and so extensive research is undertaken in this field.

Because the tasks involved in the reliable and connection-oriented transmission of multicast data correspond mainly to the tasks of a transport protocol and these work on on top of the IP multicast, a layer-3 service, the protocols developed so far are normally called multicast transport protocols. The most important tasks of a transport protocol, including connection management, flow control, error correction, and congestion control, are relatively complex and expensive for unicast communication, and point-to-multoint communication adds special problems to this situation. For example, consider the sender imputation problem, which occurs when many receivers return acknowledements for received data packets to the sender, overloading the sender with an enormous volume.

We will not discuss multicast transport protocols any at this point, because there is currently no protocol used as a standard under Linux. We do list few protocols and research projects here. Some of these protocols have been implemented and evaluated. However, none of these protocols is especially suited for all multicast applications; each one has specific benefits and drawbacks.

- Real-Time Transport Protocol (RTP)—for real-time and multimedia applications.
- Scalable Reliable Multicast (SRM)—currently used by White Board.
- Uniform Reliable Group Communication (URGC)—supports reliable and in-order communication.
- Muse—an application-specific protocol.
- Multicast File Transfer Protocol (MFTP)—works much like File Transfer Protocol (FTP).
- Local Group Concept (LGC)—uses local groups to prevent implosion.

## CHAPTER 18 Using Traffic Control to Support Quality of Service (QoS)

### 18.1 INTRODUCTION

In the Linux world, the *term traffic control* represents all the possibilities to influence incoming and outgoing traffic. In this context, we normally distinguish between two definitions, although it is often difficult to draw a clear line between:

- Policing: "Policing" means that data streams are monitored and that packets not admitted by a specified strategy (policy) are discarded. Within a networked computer, this can happen in two places: when it is receiving packets from the network (ingress) and when it is sending packets to the network.
- Traffic shaping: "Traffic shaping" refers to a targeted-influence on mostly outgoing traffic. This includes, for example, buffering of outgoing data to stay within a specified rate, setting priorities for outgoing data, and marking packets for service classes.

The traffic-control framework developed for the Linux operating system creates a universal environment, which integrates different elements for policing and traffic shaping that can be interconnected. These elements can even be dynamically loaded and unloaded as module during active operation. We describe this framework in detail below, but limit the discussion of implementation of elements in this framework to a single example. Subsequently, we will describe configuration options in the user space.
