## 17.5.2 Accessing MBone over the routed daemon

The routed daemon is a tool you can use to connect to MBone. It enables you to build tunnels to other MBone nodes and ensure connectivity. In addition, this daemon enables routing for multicast packets within or at the boundaries of a multicast network. The standard implementation of multicast in UNIX uses the Distant Multicast Routing Protocol (DVMP); see Section 17.5.3).

Like daemons, routed operates in the user-address space and can be started and stopped at runtime. It communicates with the kernel over specific interfaces, which will be included in the course of this chapter. The routed daemon can be changed at runtime, so we can implement different routing algorithms. The routed daemon is not the only multicast routing daemon for Linux, but it is the most popular and the most frequently used.

### How Routed Operates

Multicast packet forwarding is separate from selecting of forwarding routes; the kernel is responsible for forwarding, and the routing daemon determines the routes. Again, this shows a known principle, the separating of the data path from the control path. To determine routes, the routed daemon obtains information about all incoming multicast packets, including their destination and origin. Using this information, it computes the multicast routing tables and passes them to the kernel over a specific interface. This means that the daemon tells the kernel how it should forward packets from a specific sender to a specific group. The paths or routes for multicast packets are stated in the form of virtual network devices, which were introduced in Section 17.4.2.

### Interface Between the Multicast Daemon and the Kernel

The routed daemon communicates with the Linux kernel over a special socket. The kernel obtains routing information for multicast packets by setsockopt() calls over a raw socket. routed daemon uses the IPPROTO_ICMP protocol to open the socket ahead of time. Within the kernel, a reference to the socket used by routed to communicate with the kernel is stored in the variable mroute_socket.

If mroute_socket contains the value NULL, then no instance of the mrouted daemon is running yet; otherwise, an instance is already active, and the socket is denied. This allows you to check for whether an attempt is made to create a second instance of the daemon and to ensure that the commands to multicast routing information in the kernel originates from the mrouted socket.

The options available to change the multicast routing table are handled by the function ip_mroute_setsockopt() (defined in ipv4/ipmr.c). MRT_INIT has to be the first option or the first command we send to the socket. All other commands (MRT_DONE, MRT_ADD_VIF, MRT_DEL_VIF, MRT_ADD_MFC, MRT_DEL_MFC, and MRT_ASSERT) are ignored; they return the result -EACCESS if the socket was not previously reserved by MRT_INIT.

The following subsections describe the most important functions and structures available in the Linux kernel for tasks handled by the multicast routing daemon. These functions and structures are declared primarily in the file ipv4/mroute.c. Subsequently, we use a few examples to show how the daemon and the kernel exchange data by use of ioctl() commands and socket options.

### Kernel Functions Used by mrouted

| Function | Location | Description |
| :--- | :--- | :--- |
| ip_mroute_setsockopt() | net/ipv4/ipmr.c | ip_mroute_setsockopt(sk,opt_name,opt_val,opt_len) accepts commands from the mrouted daemon and processes them, including, for example, the creating and deleting of virtual network devices (VIFs) and entries in the multicast routing table (MFC). ip_mroute_setsockopt() is invoked by ip_setsockopt() in net/ipv4/sock.c, because these are socket options. |

In addition to the sk socket and the actual command, opt_name, this function can accept other parameters, including additional information (opt_val), if required for the command, and the length of this information (opt_len). In summary, this function can accept the following commands and additional information:

- MRT_INIT: This command sets the variable mroute_socket. It takes the value NULL by default, and it returns -EADDRUSE error if another instance of mrouted (another multicast routing daemon) is already running. Otherwise, mroute_socket obtains a pointer to the socket to send MRT_INIT. This command must be the first command for mrouted, because all other commands check on whether they originate from the socket specified in mroute_socket. If an error occurs, then -EACCESS is returned, and the command is not executed.

Before we use a socket, we have to route the protocol option IPPROTO_IGMP to create the socket. Otherwise, an -ENOPTS error is returned, opt_val has to point to an integer value with the value one; the result will again be a new or an error (then, -ENPROTOOPT).

- MRT_ADD_VIF: This command instructs the kernel to create a new virtual network device (VIF). The additional information this command takes a pointer to a structure (see Section 17.5.2) in opt_val, which is passed to the kernel because it includes all parameters. These parameters include an index of the virtual network device, the address of the network device, and the flag that states whether this network device is a tunnel (VIF_TUNNEL). If this is the case, then the kernel uses the function ip_new_tunnel() to create a new tunnel. Otherwise, ip_dev_find() is used to search for the corresponding network device. If MRT_INIT initializes the socket, -EACCESS is returned. Other errors that can potentially occur are -EINVAL, -EFAULT, -ENFILE, -EADDRUSE-if opt_val is an invalid structure; if the structure cannot be copied from the user space; if the VIF index is outside the valid range; or if the network device already exists, respectively. In the creating of a virtual network device, a new vif_device structure is added to its list (vif_table), and the information for this is taken from the mctl structure.

- MRT_DEL_VIF: This command is used to remove the entry for a virtual network device from the list of virtual network devices (vif_table). The parameters used here are identical to those used in MRT_ADD_VIF. However, only the VIF index is evaluated.

- MRT_ADD_MFC: This command instructs the kernel to add a new entry in its multicast routing table (multicast forwarding cache) or if an entry matching the searched key exists, to update this entry. For this purpose, an mctl structure (see error: -EINVAL) has been completed, ipmr_mcache_find() (see below) checks the MFC cache to see whether a corresponding entry exists. If this is the case, then this entry is added to the new values; otherwise, a new entry is created. When a new cache entry is created, an mfc_mcache structure is allocated at the same time, and all relevant information is taken from the mctl structure and transmitted. In this case, the entries in the field mfc_ttls having the value null are mapped to 255. The reason is that the validation process need only test whether the value is smaller than 255 or to see whether a packet is to be routed to a VIF.

- MRT_DEL_MFC: This command instructs the kernel to remove an entry from the MFC. The kernel uses the function ipmr_mfc_delete() to delete an entry from the MFC.
