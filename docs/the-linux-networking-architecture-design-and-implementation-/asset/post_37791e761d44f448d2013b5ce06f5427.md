## 19.3 The Netfilter Architecture of Linux 2.4 (393)

In this example, rather than calling the function output_maybe_reroute() immediately, the packet-filtering functions registered with the hook NF_IP_LOCAL_OUT are processed first to find an IP packet. The values that filter functions return are defined in <linux/netfilter.h>. If all functions return the value NF_ACCEPT, then the "okay" function okfn() at this hook (i.c., output_maybe_reroute() in this case) is invoked. If, however one of the filter functions returns NF_DROP, then the packet is dropped, and okfn() is not invoked.

More specifically, the NF_HOOK macro has the following arguments:

- pf (protocol family): this is the identifier of the protocol: PF_INET for IP Version 4, PF_INET6 for IP Version 6.
- hook: this is the identifier. All valid identifiers for each protocol family are defined in a header file (<linux/netfilter_ipv4.h>).
- skb: this is a pointer to the sk_buff structure with the packet to be handled.
- indev(device): this is a pointer to the net_device structure of the device that received the packet. It is set to NULL in the above example, because the packet is an outgoing packet.
- outdev(device): this is a pointer to the net_device structure of the device that should be used by the packet to leave the local computer. In the above example, the device used has been determined first by one of the routing table (rt).
- okfn() (okay function): this function is invoked when all filter functions registered with this hook returned NF_ACCEPT, thereby okaying the packet's transit.

### 19.3.2 Registering and Unregistering Packet-Filter Functions

The packet-filter functions that are all hooked into the netfilter hooks are so-called hook functions of the type nf_hookfn. The signature of a hook function is defined in <linux/netfilter.h> as follows:

```
typedef unsigned int nf_hookfn(
    struct sk_buff **skb,
    const struct net_device *in,
    const struct net_device *out,
    int (*okfn)(struct sk_buff *skb));
```

The parameters (for the protocol family identifier) correspond exactly to those of the NF_HOOK macro (see Section 19.3.1), and they are passed by this macro to the packet-filter functions. [Russ000] includes a sample showing how a packet-filter function is implemented, with detailed explanations.

The return value of a packet-filter function specifies what should happen to the packet. It is of type unsigned int and can take any of the following values, defined in <linux/netfilter.h>:

- NF_DROP (0): The active rules list processing is stopped, and the packet is dropped.
- NF_ACCEPT (1): The packet is passed to the next packet-filter function in the rules list. Once the end of the list has been reached, the packet is released by okfn() for further processing.
- NF_STOLEN (2): The packet filter function withholds the packet for further processing, so that the active rules processing is stopped. In contrast to NF_DROP, however, the packet does not have to be explicitly dropped.
- NF_QUEUE (3): The function nf_queue() (net/core/netfilter.c) puts the packet in a queue from which it can be removed and processed (e.g., by a user space program). Subsequently, nf_reinject() has to be invoked to return the packet to the Linux kernel for further processing by netfilter.
- NF_REPEAT (4): In contrast to NF_ACCEPT, rather than a continuation of processing at the next packet-filter function, the current function is invoked again.

The fields of this structure have the following meaning:

- list: the nf_hook_ops structures are maintained in a linked list within the Linux kernel.
- hook(): this is a pointer to the actual packet-filter function of the type nf_hookfn.
- hooknum: the protocol family identifier (e.g., PF_INET or PF_INET6) and the hook identifier (e.g., NF_INPUT) are used to determine the hook for this packet-filter function.
- priority: Packet-filter functions within the rules are sorted by the priority field in ascending order, so that they will be invoked in order when a packet transits. Priority values are defined as follows, e.g., in <linux/netfilter_ipv4.h>:
```
enum nf_ip_priorities {

NF_PRI_CONNTACK = -200,
NF_PRI_MANGLE = -150,
NF_PRI_NAT_DST = -100,
NF_PRI_FILTER = 0,
NF_PRI_NAT_SRC = 100,
NF_PRI_LAST = INT_MAX,
};
```

### 19.3.3 Comparing iptables and ipchains

The most important differences between netfilter and the old ipchains are doubtless that the facts mentioned in 19.2.2 were removed: New packet filter functions can easily be integrated into the Linux kernel by use of the interface introduced in 19.3.2. In addition complex functions, such as the support of transparent proxies or address-translation modules (NAT), are now implemented as independent modules. The changes to the existing network code to integrate a new hook are limited to single call of the NF_HOOK macro. (See Section 19.3.1).

Moreover, the netfilter architecture changed the path packet streams. In contrast to ipchains, iptables now handle each packet based on exactly one of three hooks: INPUT, FORWARD, or OUTPUT. The routing decision is made early, before the transit through the INPUT or FORWARD hook, so that forwarded packets do not have to traverse all hooks (See Figure 19.3). In ipchains (Figure 19.2), all packets had to traverse the input list before a routing decision was made; given this decision, packets were redirected to a local process or to the forward list. This modification simplifies the rules-listing handling, no undesired dependencies between them occur, and reduces the processing cost in the kernel, so that packets are handled faster.

And finally, there was a slight change to the syntax of the iptables command-line tool used to manage rules lists, compared to the older ipchains. Table 19.1 gives an overview of the most changes. Most options and parameters are identical. However, iptables rules use uppercase letters; also, DENY was renamed to DROP, and MASQ replaces the former MASQUERADE.
