## 8.3.3 Initialization

When the PPP module ppp_generic_o is loaded, then ppp_init first registers a character-oriented device with the major number 108, which is normally embedded /dev/ppp into the system. In the next step, the module uses ppp_async_init() to register a new TTY line discipline (see Section 7.2.1) by the name 'ppp' for the asynchronous PPP driver (ppp_async.). This TTY line discipline is an intermediate layer between the device and the underlying device and the ppp_async_c module, which facilitates access to all incoming data packets. Once the /dev/tty device and the PPP TTY line discipline have been registered, the first initialization phase is completed.

The second phase is initiated by the calling of ppp. After a brief test of its version number matches the kernel driver version, it opens the device /dev/ppp. It then opens a file descriptor, which is required to communicate with the generic PPP driver: at first, however, the reference pointer USAGE_COUNT of the PPP device increments.

Next, a user needs to establish a physical connection (e.g., the chat program could dial the number of a dialup server). If this action was successful, then ppp uses the system ioctl(tty_fd, TIOCSREED, N_PPP) to change the TTY line discipline to N_PPP. It then uses ioctl(ppp_fd, PPPOCNEWUNIT) to request the generic PPP driver to create a new network device and then uses ioctl(fd, PPPOCGCATATCH) to bind the new network device to the underlying TTY device.

These steps complete the establishment of the actual PPP connection: now the PPP protocols, as LCP, can start authenticating the user and configure higher layers (see Section 8.4).

## 8.3.4 Transmitting IP Packets

The generic PPP driver accepts packets for transmission over two routes: the network layer sends payload packets over the matching network device (pppX), and the PPP daemon controls packets over the character-oriented device /dev/ppp.

Each data packet to be sent to the function ppp_start_xmit() by the network layer is in an sk_buff buffer. (See Section 4.1) This function adds a 2-byte PPP header (see Figure 8-2) to the beginning of the packet and stores the packet in the transmit queue ppp_xq. The very same thing happens in ppp_write(), the function that accepts packets from ppp.

Finally, the function ppp_xmit() is invoked in each case. It takes packets from the transmit queue and forwards them to the function ppp_send_frame() for further processing. Depending on the setting, the packet headers might be compressed by the Van-Jacobson method and the deflate and BSD-Compress method might be used for payload compression. After a forwarding to the function ppp_send_async() of the asynchronous PPP driver (or to the corresponding function of the synchronous PPP driver), the generic PPP driver has completed its processing.

## 8.3.5 Detecting Frame Boundaries

Frame synchronization (framing) is implemented as a TTY line discipline in the asynchronous PPP driver (drivers/net/ppp_async.c) and follows the standard specified in [Simp94b]; Basically, this is an easily modified and streamlined HDLC (High Level Data Link Control; see [ISO93]).

Section 7.1.1 briefly explains why framing is necessary: an asynchronous TTY device (eg., a modem connection) can process only unstructured byte streams and full packets, so it is necessary to mark the beginning and end of a packet. PPP, this is done by use of the special character PPP_FLAG with the binary representation 01111110.

Of course, the remaining data stream should not inadvertently contain such special characters. To prevent special characters from occurring, we use character stuffing. This means that all payload bytes by a control character, such as PPP_FLAG, are prefixed by the character PPP_ESCAPE, or 01111101. There are more control characters; we see include/linux/ppp.defs for a complete list.

Framing and character stuffing are properly implemented in the function ppp_async_encode(). A bit vector in the field xaccm in the struct async_struct is used to detect the characters that should have a PPP_ESCAPE prefix. Each of the 32 × 8 bits in this vector corresponds to one of the 256 available-bit characters. The following program dump from drivers/net/ppp_async.c shows how we can convert payload into a data stream:

```
#define PUT_BYTE(ap, buf, c, iscl) do {
    if ((iscl && c < 0x20) || (ap->xaccm[c] & (1 << (c & 0xf))))
        *buf = PPP_ESCAPE;
    *buf = c ^ 0x20;
} while (c);
```

In this code, iscl is a flag set for special LPC commands, which have to work even when the bit vector->xaccm not yet been initialized or has been wrongly initialized.

To protect against transmission errors, a 2-byte checksum (Frame Check Sequence–FCS) is appended to the PPP packet before the closing end character (PPP_FLAG). If the packet was fully converted into a data stream, then the driver of the underlying TTY device, is called by tty->driver.write(), assumes the remaining work.

## 8.3.6 Receiving PPP Packets

Receiving PPP packets over the asynchronous PPP driver works much like sending packets, just in opposite direction: Incoming data is first sent to the function ppp_async_ctty_receive() of the asynchronous PPP driver by the driver of the TTY device. Then the function ppp_async_input() searches for boundaries and undoes character stuffing. The function checksum (FCS: see Section 8.3.5) is correct. Finally, the restored packet is passed to the function ppp_input() of the generic PPP driver.

Next, if the packet was compressed, it is now unpacked in the function ppp_receive_nonmp_frame() (or, in the case of multilink PPP, ppp_receive_mp_frame()). On the basis of the protocol identifier in the first two bytes of the packet (see Figure 8-2), a decision is made about whether the packet should be passed to the network layer in an sk_buff structure or added to the receive queue pppd->rq, from which it can be read by pppd over the device /dev/ppp.

## 8.4 IMPLEMENTING THE PPP DAEMON

As mentioned repeatedly in previous sections, the largest part of the implementation effort takes place in the PPP daemon, ppppd. One of the reasons is that it processes all subprotocols to control the PPP connection. To maintain expandability, utmost care was taken to keep the implementation highly modular, and it has a clearly defined interface for subprotocol implementations.

## 8.4.1 Managing Subprotocols

```
struct protocol pppd/pppd.h
```

The core of the pppd interface for subprotocols is the potent structure, which is defined in the file pppd/pppd.h. It includes mainly entries for callback functions, which are always called when pppd receives a packet that it allocates to this subprotocol: given the protocol ID:

```
struct protocol {
    /* PPP protocol number */
    /* Initialization procedure */
    void (*init)_P(int unit);
    /* Process a received packet */
    void (*input)_P(int unit, u_char *pkt, int len);
    /* Process a received protocol-reject */
    void (*protrej)_P(int unit);
    /* Lower layer has come up */
    void (*lookup)_P(int unit);
    /* Lower layer has gone down */
    void (*lowdown)_P(int unit);
    /* Open the protocol */
    void (*open)_P(int unit);
    /* Close the protocol */
    void (*close)_P(int unit, u_char *reason);
    /* Print a packet in readable form */
    int (*printpkt)_P(u_char *pkt, int len,
        void (*printer)_P(void *void, char *, ...),
        void *arg);
    /* Process a received data packet */
    void (*datainup)_P(int unit, u_char *pkt, int len);
};
```
