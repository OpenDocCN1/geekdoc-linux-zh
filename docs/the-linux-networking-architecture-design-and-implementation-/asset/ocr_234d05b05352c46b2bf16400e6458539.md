rt_intern_hash() is used to integrate the rtable structure, which is almost complete, in the hash table of the routing cache. It also supplies the return value of ip_route_input_slow(), which then is complete.

```
ip_route_output()                               include/net/route.h
```

According to a comment in the route.h header file, where it is implemented as an inline function, the function ip_route_output() goes to be replaced by ip_route_output_key().Actually, however, it is invoked in many different positions within the network implementation as the main routing interface (e.g., by the IP function ip_queue_xmt() [see Section 14.2.2] or by udpsendmsg()) [Section 25.3] for packets created by UDP.

Its only function is to create an rt_key with the source and destination addresses, the TOS value, and other device from the passed parameters and to invoke the function ip_route_output_key(), which will be described next. The last parameter is the pointer struct rtable**arp, which serves to return the result; it is also passed to ip_route_output_key().

```
ip_route_output_key()                               net/ipv4/route.c
```

The task of ip_route_output_key() is to determine a routing entry for the rt_key structure passed. The procedure is similar to that of ip_route_input(): the routing cache is searched for a matching entry, and the process branches by ip_route_output_slow() only if no such entry is found. Rather than the inter interface, the output interface is used for hash computation and comparisons.

```
ip_route_output_slow()                               net/ipv4/route.c
```

ip_route_output_slow() is invoked if no entry for the locally created IP packet exists in the routing cache. This function runs a FIB query, enters the routing cache, and returns the new entry. In addition, it handles special cases for fib_lookup() alone is not sufficient.

With ip_route_output_key(), the only input parameter is an rt_key structure. This structure is initially copied to a new structure of the same type, which can then be modified without losing the information passed. The iif and scope information is not considered; instead, the loopback device is always assumed for iif, and scope is set to either RT_SCOPE_LINK or RT_SCOPE_UNIVERSE, depending on the RTO_ONLINK flag in the to element.

The input parameters are first checked for errors or special cases. For example, for multicast addresses, a route is created immediately without FIB query if a valid source address is specified, which can be used to identify a output device.
