Any further handling of packets is done only in the BR_STATE_FORWARDING state. If an input port is in another state, then the packets are rejected. To be able to forward a packet, a decision has to be taken as to whether the packet should be forwarded at all and, if so, over which port. br_fd_get() searches the forwarding table for an entry with the specified destination address. If it concerns the MAC address of an adapter of the bridge instance, then the packet is passed to the higher layers and not forwarded. If the destination is not the bridge, then the function br_forward() forwards the packet over the appropriate output port. Notice that the packet is passed to br_forward(), even if the input port was identified as the destination port, where it will eventually be verified and filtered. If no entry is found in the forwarding table, then the packet is flooded to all outputs (br_flood()).

- br_forward()

br_forward() is invoked either by br_handle_frame() or several times by br_flood(). The purpose of this function is to output data packet on the specified port. To this end, the function dev_queue_xmit(), described in Section 6.2, is used. Before, however, there are two checks (br_should_forward()). The output port must be in the BR_STATE_FORWARDING state and second, it must not be identical with the input port of the packet. Otherwise, the packet would be transferred twice within the local area network.

- br_flood()

br_flood() is invoked by br_learn() or br_forward() when a packet be sent to all ports except the input port, for some reason. br_flood() simply invokes the function br_forward() for each entry in the bridge structure. As mentioned earlier, this checks for the port's forwarding state and for mismatch between input and output adapters.

- br_pass_frame()

Transparent bridges are normally invisible to the other stations in a LAN network; they forward data packets on the data-link layer or filter packets. When we use Linux system as a bridge, we will probably want to use it for other purposes. This is possible with the bridge implementation discussed here. When the bridge receives a packet with the destination address of one of its adapters, it is passed to the higher layers by br_pass_frame().

br_fdb_get() searches the forwarding table in the hash table of the specified bridge instance for a MAC destination address. ### 12.4.4 Learning MAC Addresses

The learning of new MAC addresses is a characteristic of a transparent bridge. It can be achieved only provided the port is in learning or forwarding state (See Section 12.2). As described earlier, the learning function is invoked for each data packet. The source address is added to the forwarding table. If an address already exists in the table, then the information in the net_bridge_fdb_entry structure is updated and the pointer is returned.

- fdb_insert() // net/bridge/fdb.c

fdb_insert() includes the entire learning function of the transparent bridge. The MAC address is entered in the forwarding table for each incoming packet in the BR_STATE_LEARNING and BR_STATE_FORWARDING states. To this end, the hash value of the MAC address is calculated (br_hash()), and the hash row is searched for the appropriate entry. If this entry is found, both the entry for the input adapter and the aging timer are updated. This means that the bridge will learn when a station has moved. If no entry can be found in the hash row, fdb_insert() creates a new net_bridge_fdb_entry structure and uses hash_link() to add it to the hash row.

- fdb_cleanup() // net/bridge/fdb.c

The forwarding table should be updated when a station is no longer active or the network has seen such an action because it responds actively to a station's packets by remembering the origin of a packet. This means that, when a station has not sent anything for a certain period of time, the bridge assumes that the station was deactivated or moved. For this purpose, the gc_timer is set in the bridge instance. This timer starts the function br_fdb_cleanup() periodically in a specific interval, gc_interval. It checks all entries in the hash table of a bridge instance and removes all entries with an aging value exceeding timeout.

### 12.4.5 Implementing the Spanning-Tree Protocol

This section describes how the spanning-tree protocol according to IEEE 802.1d and the relevant functions are implemented. The spanning-tree protocol is used to prevent cycles in a redundant LAN network. The algorithm operates in a decentralized way: Each station has to work out the current state in the LAN network from the information contained in control packets (BPDUs). For example, each bridge initially assumes that it is the root bridge, and probably has to learn that this is not so from incoming BPDU.

For this reason, the implementation of the spanning tree protocol is based on the fact that the "best" configuration is stored in each port. This means that each new incoming message is verified to see whether the information it contains is better than the information currently stored, so that the currently best configuration is accepted. By comparing the configuration message most recently received with the information available on the bridge itself, it is easy to figure out the root bridge, the root port, and the designated ports.

This also means that all steps are executed consecutively for each configuration message with better information. This means that the root bridge is defined in all bridges to then take the cost for all bridges, and subsequently the knowledge of the immediate neighbors is added, and so on, until the configuration messages have visited the entire LAN network so that the bridges can make their optimal choice for the LAN. This shows clearly that a real-world implementation does not necessarily have to correspond to the theoretical model to be efficient.

One major benefit of this implementation is that relatively few configuration messages must be exchanged. How fast a tree structure can build depends on the bridges that send their configuration messages first. It is normally beneficial when bridges with smaller identifiers or higher priorities send configuration messages earlier. However, bridges do not immediately change from the blocking into the forwarding state; they take various intermediate states where no data packets may be forwarded, so the probability of temporary cycles is low.
