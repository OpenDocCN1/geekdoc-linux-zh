The functionality of a module is registered and initialized in the module’s method init_module(). As described earlier, it is called directly after successful int- gration of the module in the kernel. Init_module() should run all initialization tasks, such as reserving memory, creating entries in the /proc directory, initializing data struc- ters, registering and unregistering the functionality, and so on.

Upon successful execution of init_module(), the functionality of the module should be known in the kernel, and all initialization steps required for it should have run. However, if something goes wrong during the initialization, all actions done to this point should be undone in any event. The when init_module() returns with an error, the code object of the module is removed from the kernel address space, and all attempts to access methods of the module lead to a memory error. Once you have called run cleanup_module(), there should be no more ref- erences by the kernel or other modules to the module concerned. Otherwise, this would lead to a memory access error, causing the computer to crash.

The method cleanup_module() is only called if the reference counter (use counter) of the module is equal to zero. Otherwise, it is assumed that the module’s func- tionality is constantly used, so that it cannot be removed. The macro MOD_IN_USE can be used to check the counters.

A good example for the reference counter is a module-based network driver. As the relevant network device is opened, it is possible to access the driver’s methods (and thus the module’s methods) asynchronously. For this reason, the reference counter (for module-based drivers) is always increased by the macro MOD_IN_USE_COUNT in the method dev->open(). When the network device is closed, MOD_DEC_USE_COUNT de-crements the reference counter by one.
