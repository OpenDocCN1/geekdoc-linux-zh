### Transmitting over NET_SOFT-IRQ

The NET_SOFTIRQ is an alternative for sending packets. It is marked for execution (_cpu_raise_softirq()) by the method netif_schedule(). netif_schedule() is invoked whenever a socket buffer cannot be seen over the normal transmission process, described in the previous section. This problem can have several causes:

- Problems occurred when a packet was forwarded to the network adapter (e.g., no free spaces).
- The socket buffer has to be sent later, to honor special handling of packets. In the case of traffic shaping, packets might have to be delayed artificially, to maintain a specific data rate. For this purpose, a timer is used, which starts the transmission of the packet when the transmission time is reached. (See Figure 6–4).

Now, if NET_TX_SOFTIRQ is marked for execution by netif_schedule(), it is started at the next call of the CPU scheduler.

```
net_tx_action()
```

net_tx_action() is the handling routine of the NET_TX_SOFTIRQ software interrupt. The main task of this method is to call the method qdisc_restart() to start the transmission of the packets of a network device.

The benefit of using the NET_TX_SOFTIRQ software interrupt is that processes can be handled in parallel in the Linux network architecture. In addition to NET_RX_SOFTIRQ, which is responsible for the main protocol handling, the NET_SOFT-IRQ can also be used to increase the throughput considerably in multiprocessor computers.

# MANAGING LAYER-3 PROTOCOLS

The previous section of this chapter described the path of a packet between a network adapter and the interface to higher protocol instances. This section discusses this interface in detail. First, we will explain how new protocols can be added because only protocols of the network layer (IP, ARP, IPv6, IPX) are added to the Linux network architecture over this interface, it is also referred to as the interface to the network layer or layer-3 protocols in the following discussion.

In the Linux kernel, we distinguish between two types of layer-3 protocols, where the first type is used mostly for analysis purposes:

- A protocol receives all packets arriving at the interface to the layer-3 protocols.
- A protocol receives only packets with the correct protocol identifier (e.g., 0x0800 for the Internet Protocol).

The simple linked list, ptype_all, stores the protocols that should receive all socket buffers. The hash table, ptype_base, manages all layer-3 protocols.

- **type**: This field specifies the protocol identifier (i.e., constants listed in Figure 6–6). If ETH_P_ALL is stated in this field, the packet is added to the list ptype_all when it is registered. Otherwise, it receives only packets with protocol identifier.

dev_add_pack(pt) registers with the Linux network architecture the layer-3 protocol represented by the packet_type structure pt. If the field type has the value ETH_P_ALL, then the protocol is added to the list ptype_all. Otherwise, it is inserted in the appropriate row of the hash table ptype_base. From now on, all received packets with protocol identifier type are delivered to this protocol instance

```
dev_remove_pack() net/core/dev.c
```

dev_remove_pack(pt) removes the protocol with the packet_type structure pt. Depending on the identifier in the type field, it is removed from the data structure, provided that the protocol type is not ETH_P_ALL and the protocol was not registered for one single network device.

If a value in the length or protocol field is greater than the maximum frame length (1536 bytes), then it is assumed that it is an 802.3-compatible Ethernet adapter. As mentioned earlier, the 802.3 protocol integrates the protocol-control information of the LLC layer in the protocol field of the 802.3 frame, thus sparing any need for a separate LLC packet header. This means that the field value contains the protocol identifier of the layer-3 protocol and is registered in skb->type.

Older Ethernet adapters store the length of the frame rather than the protocol identifier of the layer-3 protocol in the length or protocol field.

eth_type_trans() does not verify the LLC-PDU any further, but returns ETH_P_802_2 as the layer-3 identifier. The 802.2 LLC instance is treated as a layer-3 protocol. (See Section 6.3.) It is also registered as a layer-3 instance in the hash table ptype_base. This though conflicts with the layer model, it allows a simpler implementation in this case, because Ethernet adapters use the integrated LLC variant mentioned previously, and 802.2 is an exception-class. Finally, the demultiplexing to the layer-3 protocol takes place in the handling routine of the 802.2 protocol (p8022_rcv(), /net/802/p8022.c).

Layer-3 protocols can register themselves with the 802.2 protocol by use of the method register_8022_client(). For example, the SNAP protocol extension (net/802/snap.c) can register itself with register_8022_client(0xAA, snap_rcv). From then on, the method snap_rcv(), which links to the corresponding layer-3 protocol, is invoked for all SNAP frames.
