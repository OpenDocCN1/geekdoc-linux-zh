
## 15.3.2 Operation of the Address Resolution Protocol (ARP)

Given that the ARP cache and other neighbour tables have been built as discussed in the previous section, this section describes how the Address Resolution Protocol (ARP) in the Linux kernel operates. We first discuss the routes ARP packets take across the kernel and how the ARP instance operates. Figure 15-7 shows the routes of ARP request and ARP reply packets.

Incoming ARP PDUs `arp_recv()` handles incoming ARP packets on layer 3. ARP packets are packed directly in layer-2 PDUs; so separate layer-3 protocol definition `(arp_packet_type)` was created for the Address Resolution Protocol. This information and the protocol identifier ETH_P_ARP from the LLC header are used to identify the packet that is an ARP PDU and to treat it as such.

```
arp_recv()
```

Once a computer has received it, an ARP PDU is passed to the ARP handling routine by the `NET_RX` software interrupt `(net_rx_action)`, `arp_recv()` first checks the packet for correctness, verifying the following criteria—the packet is dropped if one of these conditions is:

- Is the `net_device` structure a correct network device (`in_dev == NULL`)?
- Are the ARP PDU length and the addresses it contains correct `(arp->arp_hin != dev->addr_len)`?

The arp_pl field should have value 4. Otherwise, the packet does not originate from a request for the layer-2 address of an IP address or a reply, respectively. Currently, the Linux kernel supports only address resolutions based on the Inter-Protocol.

The packet is dropped if one of these conditions (in brackets) is true. If the ARP packet is correct, it is checked to see whether the MAC type specified in the packet complies with the network device. For example, if the ARP packet arrived in an Ethernet card, then the protocol type in the ARP packet should be either ARPHD_ETHER or ARPHD_IEEE802. Interestingly, the Ethernet hardware identifier is also used for token ringing and FDDI network devices.

Subsequently, all packets are filtered, if they are not ARP request nor ARP PDUs or if they probe for the layer-2 address of a loopback address (127.x.x) or a multicast IP address.

Further handling of a packet differs only slightly for an ARP request or ARP reply. Both types are entered in the ARP cache, or neigh_lookup() returns a reply PDU to the requesting computer. An additional step for this, the arp_send() function is used to compose an ARP reply packet (as shown below). One peculiarity here is that the computer can act as ARP proxy for other computers, in addition to listening to ARP requests with its own. For example, the firewall does not admit ARP requests. Consequently, this computer has to accept packets for other computers without the senders’ knowledge. The computer acting as a firewall identifies itself to the ARP mechanism as these other computers. The work of the ARP proxy is done by arpd (ARP daemon).

```
neigh_lookup() net/core/neighbour
```

This function is required to search the ARP cache for specific entries. If the neighbor we look for is found in the hash table, a pointer to the neighbour structure is returned, and the reference counter of ARP entry is incremented by one.

```
arp_send() net/ipv4/arp.c
```

The arp_send() function includes all parameters to be set as arguments in an ARP PDU. It uses them to build an ARP packet with all fields properly set. The Hardware type field and the layer-2 address are set in relation to the corresponding network device. The Internet Protocol is the only layer-3 protocol supported, so the fields for layer-3 protocol type and the length of a layer-3 address always have the same values. Finally, the layer-2 packet header is appended, and the complete packet is sent by dev_queue_xmit().

### neigh_update(state)

The neigh_update(state) is used to set a new state (new_state). This has no effect for neighbour entries in the NUD_PERMANENT and NUD_ARP states, no state transitions are allowed from these states to another state. (See Figure 15–6.)

If the state be NUD_CONNECTED, then connect() is invoked to set the output() to neigh_connected_output(). If this is not the case, the function neigh_suspect() has to be invoked to obtain the opposite effect.

If the old state be invalid (if (old & NUD_VALID)), there may be packets waiting for this neighbor in the ARP queue. As long as the entry remains in NUD_VALID state and packets are still waiting in the queue, these will now be sent to the destination state.

### Handling Unresolved IP Packets So far, we have looked only at the case where an ARP PDU was received in the computer and some action was taken in response. This section discusses how and when the Address Resolution Protocol resolves addresses. We know from Chapter 14 that an IP packet is generated by the ip_first_output() function. The netfilter POST_ROUTING handles the last steps of this function in ip_finish_output2(). In the latter, the function pointer hh_output() is invoked for packets to a destination point in the layer-2 header cache. In contrast, the pointer dst->neighbour->output() is used for network devices without layer-2 header cache. The function pointers hh_output() and output() of the neigh_options hide these between two pointers. If the ARP is valid, then the pointers point to dev_queue_xmit(). (See Figure 15–5.) If there is no address resolution, then the output() pointer of the neighbour options is normally used to point to neigh_resolve_output(). Of course, the IP packet can be sent immediately if the network device does not use ARP, so the pointer points to dev_queue_xmit().

The benefits of function pointers become obvious at this point again. The protocol status—entry in the ARP cache, in this case—does not have to be checked every time; instead, we simply invoke the output() method. This means that the fast transmit function is invoked, or the address method is used, depending on the entry's state. In summary, function pointers represent an elegant method of implementing protocols.

### neigh_resolve_output() net/core/neighbour.c

neigh_resolve_output(skb) is the second function that can be referenced by the output() function pointer. In contrast to neigh_connected_output(), it cannot be assumed in this that the stored address resolution is valid. For this reason, neigh_event_send() is used first to check the state the neighbour is in or whether the packet specified by skb can be sent to the destination without without address resolution. If so, then dev->hard_header() creates a layer-2 PDU, and neigh->ops->dev_queue_xmit() sends the packet. If the network device supports a layer-2 cache, and no entry exists for it, then neigh_hh_init() creates this entry.

If the packet cannot yet be sent—for example, because the neighbor entry is in the NUD_STALE or NUD_INCOMPLETE states—then neigh_send_event() stores the packet in the arp_queue of the neighbour entry.

### neigh_event_send() net/neighbour.c

The return value of neigh_event_send(neigh, skb) is a Boolean showing whether the packet specified by skb can be sent to the destination (return 0) or the address resolution is currently invalid (1), which means the packet should not be sent. The value 0 is returned immediately for neighbors in the NUD_NOARP, NUD_PERMANENT, and NUD_REACHABLE states; otherwise, the function __neigh_event_send() is invoked, which does the following for the others:

- NUD_NONE: New neighbor entries in this state are initially set to NUD_INCOMPLETE. Next, the timer of this neighbor is set, and neigh->ops->solicit() starts the first attempt to resolve the address.
- NUD_FAILED: A value of 1 is returned immediately, because the attempt to resolve the address failed. No packets can be sent to this state.
- NUD_INCOMPLETE: Packets sent for computers in the NUD_INCOMPLETE state are stored in the arp_queue of the neighbour entry. Subsequently, the value 1 is returned until the neighboring station can be reached or the attempt is considered to have failed.
- NUD_STALE: In this case, the neighbor entry's state changes to NUD_DELAY, and the timer is set to expires = now + delay_probe_time. The timer's handling routine, neigh_timer_handler(), will then check the state of this entry as the specified time has expired.

The function returns 1 if none of the above states are applicable.

### neigh_connected_output() net/neighbour.c

This function is the fastest possibility for neigh->output() to use without sending a layer-2 header. It is used only by neighbors in the NUD_REACHABLE state and for network devices that do not support hardware caches. First, dev->hard_header() is invoked to create the layer-2 PDU; then, neigh->ops->queue_xmit() sends this PDU.

### arp_solicit() net/ipv4/arp.c

arp_solicit() is the actual function used to obtain the MAC address of a neighboring computer. It is used to send ARP requests.
The probes timer in the neighbour structure stores the number of requests sent so far (i.e., the number of unsuccessful attempts since the neighbour entry was in the NUD_REACHABLE state).
arp_solicit() checks for how many ARP requests have been sent. If the limit has not been exceeded, an ARP request is sent by the arp_send() function. The ARP_REQUEST parameter specifies the packet type.
