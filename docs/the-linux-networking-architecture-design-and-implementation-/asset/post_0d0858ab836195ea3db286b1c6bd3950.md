### 2.3.2 Spinlocks

Spinlocks are also busy-wait locks because of the way they work. When a critical section begins and the lock—in this case the spinlock—has already been set, then the processor waits actively until the lock is removed. This means that the processor continues locking the variable in a continuous loop until the locking variable is released by the locking activity.

Though this wastes computing time because the processor seems to continually test the locking variable "meaninglessly," it can prove more effective to continually test the lock for a brief moment and then it can enter the critical section upon its release rather than calling the scheduler and grant the computing time to another activity. A lot of time can elapse until the waiting activity will get its turn after the lock's release. In addition, a change of activity caused by calling the scheduler could eventually take more computing time than a brief wait in the busy wait loop. For we observe the principle that spinlocks represent the best locking method for small critical points (i.e., with short locking times).

In the Linux kernel, spinlocks are implemented by the variable `spinlock_t`, which consists of a single integer locking variable. To use a spinlock, you have to create and initialize the `spinlock_t` structure, in the following example:

```c
#include <linux/spinlock.h>
spinlock_t my_spinlock = SPIN_LOCK_UNLOCKED;
/* You can also use spinlock_init(&my_spinlock) instead of an assignment in the definition. */
```

You can now use a set of different functions to request, set or release spinlocks. Each of these functions is especially suited for certain application cases. First, let's look at how we set a spinlock:

- `spin_lock(spinlock_t *my_spinlock)` tries to set the spinlock my_spinlock. If it is not free, we have to wait or test until it is released. The free spinlock is then returned immediately.
- `spin_lock_irsave(spinlock_t *my_spinlock, unsigned long flags)` works similarly to `spin_lock()`, but it additionally prevents interrupts and stores the current value of the CPU status register in the variable flags.
- `spin_lock_irq(spinlock_t *my_spinlock)` works similarly to `spin_lock_irq()`, which does not store the value of the CPU status register. It assumes that interrupts are already being prevented.
- Similar to `spin_lock()`, `spin_lock_bh(*my_spinlock)` tries to set the lock, but it prevents bottom halves (see Section 2.2.5) from running at the same time.

The following functions can be used to mark the end of the critical section, depending on the application. Each of them releases an occupied spinlock.

### 2.3 Locking—Atomic Operations

- `spin_unlock(spinlock_t *my_spinlock)` releases an acquired spinlock.
- `spin_unlock_irqrestore(spinlock_t *my_spinlock, unsigned long flags)` releases the specified spinlock and allows interrupts, if there were any activated when the CPU status register was saved to the variable; otherwise it does not allow interrupts.
- `spin_unlock_irq(spinlock_t *my_spinlock)` releases the specified spinlock and allows interrupts.
- `spin_unlock_bh(spinlock_t *my_spinlock)` also releases the lock and allows immediate processing of bottom halves.

The functions introduced above can be used to protect critical sections to avoid undesired side effects on the critical sections from occurring. The example shown in Figures 2-2 and 2-4 can be used as follows, where the use of a spinlock prevents undesired side effects:

```c
#include <linux/spinlock.h>
spinlock_t *my_spinlock = SPIN_LOCK_UNLOCKED;
// Activity A
spin_lock(&my_spinlock);
skb_a->next = queue->next;
queue->next = skb_a;
spin_unlock(&my_spinlock);
...
// Activity B
spin_lock(&my_spinlock);
skb_b->next = queue->next;
queue->next = skb_b;
spin_unlock(&my_spinlock);
```

The following useful functions are available to handle spinlocks, in addition to the methods used to set and release spinlocks:

- `spin_is_locked(spinlock_t *my_lock)` polls the current status of the lock, without changing it. For a set lock, a value unequal to zero is returned; for a free lock, zero is returned.
- `spin_trylock(spinlock_t *my_lock)` sets the spinlock if it is currently unoccupied; otherwise it immediately returns a value unequal to zero.
- `spin_unlock_wait(spinlock_t *my_lock)` waits for the lock to be released, if the lock is occupied.

### 2.3.3 Read–Write Spinlocks

Spinlocks represent a simple and useful element to protect parallel operations on common data structures from undesired effects. However, they slow down the progress of activities because these activities have to wait for locks to be released. Waiting is not always necessary in certain situations. For example, there are data structures with frequent reads but few writes (a well-known example for this situation would be the list of registered devices which is rarely changed during the system's runtime).

During accessing of such a shared data structure, it is absolutely necessary to use a lock, but reading activities do not have to be stopped. For this reason so-called read–write spinlocks are used. They allow several read activities to enter the critical section while there is no write activity operating on it. As soon as an activity occupies the lock with writing, all read activities must wait until it is released.

When we are adding a new device in our example, the undesired effect demonstrated in Figures 2-2 and 2-4 could occur. For this reason, we use read–write spinlocks to protect the shared list. The data structure `rwlock_t` is used to implement read–write spinlocks. The following functions are available to set and release read–write spinlocks. Note that we distinguish them according to whether the lock should be entered for read or for write purposes. RW lock functions come in different variants with regard to how they handle interrupts and bottom halves (...bh.). We will not repeat the description of these differences here because their behavior corresponds to `spin_lock()` functions.

- `read_lock()` accesses the critical section for reading purposes. If it contains no activities or only reading activities, then the section is accessed immediately. If there is a write activity in the critical section, then we have to wait.
- `read_unlock()` leaves the critical section for reading purposes only. If there is no read activity in that section, then it can access.
- `write_lock()` tries to occupy the critical section for writing purposes. If there is already a write or read activity in the critical section, then the activity waits for all activities to leave that section. Subsequently, it puts an exclusive lock on the critical section.
- `write_unlock()` releases the (write) lock and thus the critical section.

### 2.3.4 Semaphores

In addition to active locks, there is a way to avoid waiting until a critical section can be accessed when a lock is set. Instead of waiting, the activity releases the CPU by calling the scheduler. This means that the computing time can be used by other activities. This concept is known by the term semaphore or mutex in computer science. The Linux kernel offers semaphores. However, they are not frequently used in the Linux architecture. Therefore, instead of describing here, we refer our readers to [BBDK+01].

## 2.4 Kernel Modules

We explained in Section 2.1 the drawback that all functionality of operating system kernels, including the Linux kernel, is accommodated in a large kernel, making this kernel big and inflexible. To add a new functionality to the operating system kernel, you first have to create and install a new kernel. This is a rather cumbersome task and can also be expensive, because running applications have to be interrupted and the system has been restarted. Moreover, using an operating system kernel that includes all possible kinds of functions, drivers, and protocols is not recommended either, because the kernel would become huge and consume an unnecessary amount of memory. In addition, there are always new functionalities we would like to integrate into the kernel, or newer versions of existing functionalities where errors have been removed. In fact, we can assume that the set of functions of an operating system kernel will change over time. For this reason, monolithic kernels have to be continually updated—with the principles described above.

Linux is based on the monolithic approach, but it uses a different method to solve the problems noted since kernel Version 2.0. Note that it does not use the microkernel-based approach, which also has drawbacks. The solution is kernel modules. These modules can be easily added to the kernel at runtime if they have belonged to the monolithic kernel since the system started. When the functionality of a module is no longer needed, then it can be removed and the memory space it used is freed.

We saw in Figure 2–1 in which components of the kernel we can use modules: device drivers, file systems, network protocols, and network drivers. The use of modules is actually not limited to these components. Modules can normally be used on an individual basis. However, adding some functionality means that you need a corresponding kernel interface to inform the rest of the kernel about the new components. The interfaces of the Linux network architecture and the possibilities to expand it by new functionalities are one of the central issues of this book.

When compiled as kernel modules, new functionalities can be added and removed once you don't need them anymore. (See Section 2.4.1.) This means that the principle of modularity is very similar to the flexibility of kernels, the only difference being that Linux modules run in the kernel address space, while components of microkernels run in the user address space.
