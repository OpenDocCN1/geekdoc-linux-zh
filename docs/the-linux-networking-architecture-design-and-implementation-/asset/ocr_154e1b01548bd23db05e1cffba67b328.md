PF_NETLINK sockets reside underneath the BSD sockets, where they register themselves exactly as PF_INET sockets. For registering PF_NETLINK sockets over the function sock_register(&netlink_family_ops), the function netlink_create() function with (both in/netlink/af_netlink.c) is first registered as create() function with the BSD socket. The latter function handles all initializations; requires the proto_struct structure.

Now, when data is sent to the kernel of a PF_NETLINK socket, the function netlink_sendmsg() (net/netlink/af_netlink.c) invokes the function netlink_unicast(). The vector struct sock nl_table[MAX_LINKS] serves to manage socket structures that use a common protocol (e.g., NETLINK_ROUTE structures having the same protocol are distinguished by the process ID of the requesting application, which is copied into the proto.af_netlink->pid field of the socket structure).

This function uses the function netlink_lookup() to access the socket structure that contains the desired value in its protocol field (e.g., NETLINK_ROUTE) and belongs to the requesting process. Subsequently, it has to wait until the field proto.af_netlink->state is deleted (access synchronization). Next, the sk_buffer structure is positioned in the receive queue of the socket structure., and finally, sk->data_ready() is used to access the responsive function (input).

In the case of RT Netlink sockets, the function rtnetlink_rcv() is invoked here. This function is called by rtnetlink_init() (net/core/rtnetlink.c) when the system is started: rtnetlink_init() uses rtnetlink_kernel_create() to set the function pointer data_ready() of the socket structure for NETLINK_ROUTE to the function netlink_data_ready() (net/netlink/af_netlink.c) and the structure within the proto.af_netlink->data_ready() to the function rtnetlink_rcv(). At first sight, the naming convention of this function is confusing, because it is used for transmission, from the socket's view, but serves to receive data from the user space, from the kernel's view.

On the basis of the values defined for nmsg_type in include/linux/rtnetlink.h, the elements to be addressed within the kernel are now selected. Once again, we distinguish by family and type. The type is identical to the type specified at the BSD socket mentioned above.RT_NETLINK defines every additional types, which are exported from include/linux/rtnetlink.h); the RT_NETLINK supports defines with peculiar message formats and attributes them to a family (e.g., rtm_family to manage the routing table, tcm_family for traffic control messages). Each of these defines its own structure, which determines the format of messages. These RT Netlink messages are within the data range of PF_NETLINK message, which means that they are transparent for a PF_NETLINK socket.
