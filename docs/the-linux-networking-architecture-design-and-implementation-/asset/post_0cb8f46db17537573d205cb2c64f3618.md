### 11.1.3 Data Packets

We distinguish between asynchronous connectionless (ACL) and synchronous connection-oriented (SCO) data packets. Both data types are sent when the tasked dev->tx packet becomes active, and then the function hci_sched_acl() (net/bluetooth/hci_core.c) is executed. If flow control for ACL data runs between HCI and the Link Manager, then we first have to check whether ACL data may be sent.

Flow control is used to prevent the transmit buffer of the Bluetooth device from overflowing. This can happen, for example, when an application sends data faster than the Bluetooth device can transport it—for, because the communication partner is temporarily unreachable. The initial size of the output buffer can be derived from event packets of type Number of Completed Packets, described above. HCI assumes that the free output buffer becomes smaller with each packet it passes to the Link Manager. The actual current size can be learned only upon receipt of a new link packet.

Flow control in the Bluetooth protocol of the Linux kernel is handled by the function hci_sched_acl(). In turn, this function invokes the function hci_low_acl_sent():

```
hci_low_acl_sent()
net/bluetooth/hci_core.c
```

First, this function finds out the total number, num. of all connections known to the specified network device. For each connection (represented by the structure hci_conn), the field acl_sent includes the number of ACL data packets sent over this connection. This field is incremented during a transmission, but decremented by the number of acknowledged packets over this connection when the described event packet Number of Completed Packets is received. In addition, the function hci_low_acl_sent() identifies the connection with the smallest number of ACL packets sent, which has to be smaller than 0xffff. If none of the connections meets these conditions, the function's return value is set to null. If there is such a connection, the total number of acknowledged packets (acl_cnt entry in struct hci_dev) is divided by the number (num) of connections. The result is returned by the parameter quote, and the identified connection is the return value of the function. The number of acknowledged packets forms the transmit credit, which is distributed over all ready-to-send connections.

```
hci_sched_acl();
net/bluetooth/hci_core.c
```

Using the quote calculated by the function hci_low_acl_sent(), this function tries to send ACL data packets over the specified connection (by using the function hci_send_frame()). ACL data packets may be sent as long as the queue is not empty, as long as the number of ACL packets to be formed from one sk does not exceed the transmit credit of the Bluetooth device, and as long as quote is not null. Both and the transmit credit stored in the hci_dev structure are decremented by each packet sent. At the same time, the number of packets sent over this connection is incremented.


Only the transmit credit for SCO packets, included in the field sco_cnt of struct hci_dev, is considered in the case of SCO data packets. There is no distribution over several connections. SCO data packets are simply sent until the credit is used.

### 11.1.4 Accessing the Host Controller Interface

The functionality of the Host Controller Interface (HCI) in Linux is available in different ways. Figure 11–1 shows that HCI can be accessed directly from the user space over a socket. This is normally a socket of the PF_BLUETOOTH socket family with protocol BTPROTO_HCI and type SOCK_RAW. These sockets are created in the file net/bluetooth/hci_sock.c. The socket interface is used to supply the BSD socket functions. An application can use these functions to send and receive data directly from HCI and to the network.

Alternatively, an application can use ioctl() to access the Bluetooth device (e.g., open, close, or reset the device).

For higher protocols to be implemented in the Linux kernel, HCI functions are available over the macro EX_SYMBOL. For example, the L2CAP protocol used in the next section includes these functions to register and deregister the HCI device (hci_register_dev() and hci_unregister_dev()) and interfaces to higher protocols. For example, the functions hci_register_proto() and hci_unregister_proto() serve to register the higher-layer (e.g.,L2CAP) that supplies a receive function or other functions to the HCI. The function hci_register_notifier() is used by the higher-layer protocol to register itself with the notifier of the device. (See Chapter 5.) The function hci_connect(), which sends a packet from HCI to the Link Manager (net/bluetooth/hci_core.c), is used to establish a connection.

## 11.2 L2CAP

Logical Link Control and Adaptation Protocol (L2CAP) handles tasks on data link layer in the Bluetooth protocol stack. It establishes ACL connections for the next layer, but does not transport pure audio data, which is transported over SCO connections. In particular, the L2CAP protocol is responsible for multiplexing data streams from higher layers to an ACL connection, because there is always at most one ACL connection between two devices. To multiplex several data streams, L2CAP uses the abstraction of the channel. Each channel is allocated to one specific protocol. There are connection-oriented channels for point-to-point communication and connectionless channels used for group communication. A simple signaling method is used to establish a L2CAP connection.
