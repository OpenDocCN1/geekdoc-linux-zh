
# Interface to the Application Layer

The socket implementation uses the proto structure, which is defined in net/ipv4/udp.c for UDP to access the functionality of transport protocols:

```c
struct proto udp_prot = {
  name: "UDP",
  close: udp_close,
  connect: udp_connect,
  disconnect: udp_disconnect,
  ioctl: udp_ioctl,
  setsockopt: ip_setsockopt,
  getsockopt: ip_getsockopt,
  sendmsg: udp_sendmsg,
  recvmsg: udp_recvmsg,
  backlog_rcv: udp_queue_rcv_skb,
  hash: udp_v4_hash,
  unhash: udp_v4_unhash,
  get_port: udp_v4_get_port,
};
```

The elements missing here (e.g. bind and accept), compared to the complete proto shown in Section 26.3.1, are initialized to zero, which means that no transport-protocol-specific handling of the corresponding events is.

Socket-state information is stored in the sock data structure mentioned in Section 26.3.1. The simplicity of UDP means that no protocol-specific additional data is required, so there is no UDP-specific part of the tp_pinfo field.

Most of the functions referenced in the proto structure are not very complex, so we will discuss them here briefly:

- **udp_close():** During the closing of a UDP socket, only the function inet_sock_release(2) (net/ipv4/af_inet.c), which is the same for all PF_INET sockets, is invoked to release the socket data structure. From there, udp_v4_unhash() is invoked (as described).
- **udp_connect():** UDP is a connectionless protocol, the connect() system call at the application layer interface, which is used in connection-oriented protocols to establish a connection, has a slightly different meaning: It can be used to define the destination of all UDP packets sent over a socket, so that it doesn't have to be specified each time. Accordingly, the address and destination port are stored in the sock data structure within udp_connect(). The fact that this optional definition has taken place is registered by entering the state identifier TCP_ESTABLISHED, which is "borrowed" from TCP, in the state field of the sock structure. In addition, a routing cache entry is constructed using ip_route_connect() and stored in the sock structure. This entry is used when packets are being sent, so that some overhead is avoided.
- **udp_disconnect():** The state is set to TCP_CLOSE, the destination address and destination port are deleted, and a stored routing cache entry is released.

# User Datagram Protocol (UDP)

- **udp_ioctl():** The ioctl() system call can be used here to poll the lengths of transmit and receive queues.

- **ip_setsockopt() and ip_getsockopt():** There are no socket options on the UDP level, these two entries refer directly to the general handling routines of the IP level. (See also setsockopt.)
- **udp_sendmsg() and udp_recvmsg():** These two functions implement the sending and receiving of UDP packets. Section 25.3 will discuss them in more detail.
- **udp_queue_rcv_skb():** This function will be discussed with the description of udp_recvmsg() in Section 25.3.2.

- **udp_hash():** During the receiving of UDP packets, a decision must be made about which socket packets should be assigned to, so that they can be placed in the socket's receive queue to be fetched by the user process later. To facilitate this assignment to the socket, the sock structures of all UDP sockets are registered in a hash table, struct sock "udp_hash[UDP_HTABLE_SIZE]". The port number modulo UDP_HTABLE_SIZE is used as hash value.

Within the proto structure, the hash entry could reference a function that enters a socket into the hash table. However, the socket had already been entered into the table by udp_get_port() (described later) when the port number was assigned to the table, so udp_hash() is actually not needed and is never used.

- **udp_unhash():** This function is invoked when a socket is released, to remove the sock structure from the hash table.

- **udp_get_port():** This function is invoked by the FE_INET implementation in net/ipv4/af_inet.c, whenever a local port number has to be assigned to a socket. The desired port number passed here can also be zero. In this case a free port is selected, with a position in the hash table where as few sockets as possible are linked.

The IP interface used to accept UDP packets received by the IP layer is defined by the inet_protocol structure described in Section 14.2 in connection with the function add_protoctl() and shown in Figure 14–5. It is contained in net/ipv4/protocol.c for UDP and all protocols running directly on top of IP: as follows:

```c
static struct inet_protocol protocol = {
    handler:           udp_rcv,
    err_handler:       udp_err,
    next:              IPPROTO_PREVIOUS,
    protocol:          IPPROTO_UDP,
    name:              "UDP"
};
```

The function udp_rcv() serves to receive incoming packets: Section 25.3.2 will discuss it in more detail. udp_err() handles ICMP error messages carried by the IP layer.

The function udp_sendmsg() is invoked over the socket interface whenever a UDP packet has been sent: The different kinds of systems calls all lead to this function. Its parameters are a socket structure with the state of the sending PF_INET socket, a pointer to a msg structure that specifies the receiver and payload, and the length in octets.

First, a locally created header structure takes the destination address and the destination port from the msg_name element of the msg structure. The destination doesn't have to be specified explicitly only if a default address has previously been assigned to this socket via udp_connect(). In this case, the information from the socket structure is used. The source address and the source port derive from the sock structure. Additionally, they are stored in an cookie structure. This structure, which we will not describe here in detail, serves later on to the addresses, the device identifier, and the IP options (if applicable) to the Internet Protocol.

Any control messages in the msg_control element of the msghdr structure are processed by calling the function ipc_msg_send(), and the results are registered in the cookie structure. Control messages can be used to modify the address or to pass IP options, which will then also be registered in the cookie address. If no IP options are specified, the IP options stored in the socket structure will be used.

A routing cache has to be procured, so it is also necessary to handle the source routing IP options before; the address of the first intermediate station might need to be instead of the destination address.

If the socket had previously obtained a routing cache by udp_connect(), and if the corresponding destination address has not been changed in the process of udp_sendmsg(), then this routing cache is now checked. If this produces a negative result, or if the destination address was changed, then ip_route_output() is used to produce a new routing cache entry (which is stored in the socket structure).
