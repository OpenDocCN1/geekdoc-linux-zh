When a bridge is initialized, the bridge timer is also initialized. This timer is a timer_list type (see Section 2.7.1): it invokes the br_tick() function each second. This function is used to control all timer functions of the bridge instance and the spanning-tree protocol. This means that each bridge instance uses only one system timer. All internal time-controlled processes run over this timer. More information in the later subsection Timer Handling.

Processing BPDUs The function br_handle_pdu() of br bridge_frame() is invoked as soon as a BPDU is received. When topology-change packets (TCN) arrive, br_received_tcn_bpdu() assumes all further handling. When configuration packets (Config BPDU) arrive, the packet content is copied into a br_config_bpdu structure, and some of the fields are converted into the internal representation. For example, time values are stored in jiffies rather than in ticks. Subsequently, the BPDU is handled by the function br_received_config_bpdu().

Steps of the Spanning-Tree Algorithm The individual steps of the spanning-tree algorithm were described in Section 12.2.4. As mentioned in that section, the spanning-tree mechanism runs for each configuration message that receives something in the current configuration.

Whether a new configuration message has information that is better than that currently stored is a decision implemented by policy, such as the selection of a root port and the naming of a designated port. Notice that these actions normally use few comparisons.

```
br_received_config_bpdu() net/bridge/br_stp.c
```

This function initially invokes br_is_root_bridge() to check whether it has the root bridge itself. Notice that the bridge does not have a global view of the LAN internetwork, as mentioned earlier. Could be other bridges that classify themselves as the root bridge. This situation will change gradually as the spanning-tree algorithm runs its steps, and one bridge will eventually become the only root bridge.

When a new configuration message is better than the current information (a result of calling br_supersedes_port_info()), then the following things happen:

+   First, the invocation of br_record_config_information() causes the data of the configuration BPDU to be written to the net_bridge_port structure.
nNext, the br_configuration_update() function is invoked. It selects the root ports and designated ports. This action could cause the information structures of the bridge and its ports to change.
Subsequently, br_port_state_selection() recognizes the state of a port. The hello timer is stopped, if the bridge before the new information was stored, but now if it is no longer the root bridge. If a change to the topology is discovered in addition, then the topology_change_timer is stopped, the tcn_timer is started, and a topology-change message is sent (br_transmit_tcn()).
