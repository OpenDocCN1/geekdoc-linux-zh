
fib_info structure does not contain any backward references to its position within the routing-table data structures. Instead, the fib next and fib prev pointers serve to arrange all existing fib_info structures to form a doubly linked list, which is hooked into a global variable, fib_info_list. When creating a new entry, the fib_create_info(), which is invoked by tb_insert(), first checks for whether an identity exists in the list. Rather than duplicating an entry, it would merely increment the reference counter fib_clintref. This means that fib_node structures can reference one fib_info structure. When a fib_node is freed, the reference counter has reached null.

In contrast to fn_zone and fib_node, the fib_info structure becomes visible to the outside again: It is declared in include/net/ip_fib.h and its contents are read directly in some places (e.g., in net/ipv4/route.). All operations to manage fib_info structures that go beyond the plain reading of a data element are implemented in the file net/ipv4/fib_semantics.c, however.

## Managing and Initializing Memory
The FIB implementation is initialized in ip_fib_init()(net/ipv4-frontend). If route-based routing is not used, the function fib_hash_init() is invoked directly for the two tables table_local and table_main held in global variables. This function occupies memory for a fib_table and sets the enclosed pointers to the fn_hash functions. The structure of the type fn_hash, which contains the hash table, is initialized to null.

In contrast, if route-based routing is used, routing tables are not previously initialized. The global array that references the tables is created as a memory area initialized to when the kernel loaded. When a routing table is accessed via an element of the array, it is checked whether the table already exists, and if this is not the case, it is created by fib_hash_init().

The function fib_hash_init() also ensures that a slab cache (see Section 2.6.2) called "ip_fib_hash" exists. This slab caches memory for fib_node structures, which are allocated in the function fib_hash_insert() to create new entries when needed.

## Managing Hash Structures
The functions that access fn_zone and fib_node structures, are used internally to manage routing-tables using hash tables, which are collected in the file net/ipv4/fib_hash.c. They are invoked by all other FIB functions to access fn_zone and fib_node structures.

Encapsulation of these internal structures allows them to be reimplemented, if necessary, using other data structures offering a more efficient search process, without the need to effect changes in other places.

The most important functions in net/ipv4/fib_hash.c are as follows:

- fn_rehash_zone() enlarges the hash tables, if necessary.
- fn_new_zone() creates a new fn_zone structure and sorts it into the zone list based on its prefix length.
- f_hash_lookup() handles the main task in a FIB query: The fn_zone structures in a routing table are walked through the sequence of descending prefix length, and the hash table is searched for an entry matching the key passed as an argument.
- fn_hash_select_default() selects one out of several default routes, considering whether the intermediate system specified as the next router is currently reachable.
- fn_hash_insert(), fn_hash_dump() serve to insert, delete, and display entries over the RT netlink interface.
- fn_hash_flush() removes all fib_info structures of a zone that are premarked as invalid.
- fn_hash_get_info() serves to display routing tables over the proc file system.

## Interfaces to the User-Address Space
From within the user-space, you can manage routing tables both over the traditional ioctl(1) interface and over RT netlink.

For the RT netlink interface, the functions inet_rtm_newroute(), inet_rtm_delete(), and inet_dump_fib() from net/ipv4/fib_frontend.c are registered in the table inet_rtlink_table[] in net/ipv4/devinet.c so they can be invoked to add, delete, or output a routing table and handle corresponding messages.

ioctl() system calls are handled by ip_rt_ioctl(net/ipv4/fib_frontend.c), which is invoked by the general routine that handles ioctl() calls at PF_INET sockets. (See Chapter 26.) The parameters for the call are converted into an RT netlink message by fib_convert_entry() and passed to inet_rtm_newroute() or inet_rtm_delete() for further handling.

## Proc File System
The contents of the pseudo file /proc/net/route, which can be used to view the main routing table, are created by the function (net/ipv4/fib_frontend.c) fib_get_procinfo(), using proc_create()... The function creates a header line and uses the function pointer tb_get_info() from the main table, which normally points to fn_hash_get_info(ipv4/net/fib_hash.c), to output the data. All, fib_node structures in fib_zone_list are visited, and the appropriate data is eventually output by fib_node_get_info() (net/ipv4/fib_semantics.c).

### Interfaces to the Forwarding Functions
This describes several operations in addition to those discussed in Section 16.3.1, which are used by the functions in net/ipv4/route to access the FIB.

```
fib_validate_source()
```

The fib_validate_source() serves to check the source addresses of IP packets within a forwarding process. This check can be implemented elegantly by an FIB query, using fib_lookup() for the opposite direction (i.e. with source and destination addresses swapped): If the entry found is not of the type RTN_UNICAST or RTN_LOCAL, for example, which means that the address is assigned to a local interface), then this is not a valid source address for an incoming packet.

If the output interface noted in an FIB query matches the actual interface, then the validation is completed successfully. This is the only acceptable result when reverse-path filtering is active.

If the actual input device does not currently have an address, then the above check is considered successful, even if the FIB query returns no result. If the output device does not match the actual input device, then another FIB query is done with the actual input device specified as a fixed output device. If this query either a result of the type RTN_UNICAST or no result at all, then the check is considered to have been successful.

```
fib_select_multipath()
```

When a routing-table with several routes is used in a forwarding process, the function fib_select_multipath() is invoked to select one of these routes. This decision is made randomly (the jiffies counter is used rather than a "real" random number generator), taking weights assigned to each of these routes into account.

```
ip_dev_find()
```

To find the network interface that belongs to an IP address passed as parameter, ip_dev_find() uses the function pointer tb_lookup() to search the local table. The result has an entry of the type RTN_LOCAL, and a reference to the wanted net_device structure can be taken from the entry.
