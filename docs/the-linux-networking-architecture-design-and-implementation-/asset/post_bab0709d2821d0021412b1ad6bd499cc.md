
All segments arriving over an established connection are subject to the following checks by the PAWS algorithm [JaBB92]:

The RST flag should not be set.

The TCP partner instance should have received a valid Timestamp option (i.e., the tp->ts_recent variable contains a valid value).

If an incoming segment contains the Timestamp option, and if its timestamp, tp->rc_tsval, is smaller than the timestamp stored last, tp->ts_recent, this segment should be dropped. This check is done in the tcp_paws_discard() function below, which is invoked in Slow Path in the tcp_rc_established() function. (See Section 24.2.1).

```c
extern __inline_ int tcp_paws_discard(struct tcp_opt *tp, struct sk_buff *skb)
 return ((u32)(tp->ts_recent - tp->rc_tsval) > TCP_PAWS_WINDOW &&
        xtime.time_sec < tp->ts_recent_timestamp + TCP_PAWS_24DAYS &&
        !tcp_disordered_ack(tp, skb));
```

The second condition checks the validity of the tp->ts_recent timestamp. There is a very small probability that an extremely long time has passed the time when the timestamp was taken from a received segment, which is stored in the tp->ts_recent timestamp variable. This means that, if more than 24 days have passed this time, the ts_recent timestamp is considered invalid. [Stevc94b] includes an example for such a situation.

If the TCP connection is not in the ESTABLISHED state, then the PAWS check on incoming packets is done in the tcp_paws_check() method (net/ipv4/tcp_input.c).

The PAWS mechanism requires the use of the timestamp option as monotonically increasing values. In addition, it requires that the timestamp increase at least once per period and the time in which it repeatedly takes the same value is greater than the maximum segment lifecycle.

The Timestamp option is a prerequisite for the PAWS algorithm and additionally is used to determine the packet round-trip time (RTT) and the retransmission timeout; we need to introduce it.

## The Timestamp Option

This option offers TCP a way to continually probe and adapt the packet round-trip time (RTT) in each segment. The connection option allows you to set a timestamp in each segment. The receiver returns this timestamp in the acknowledgement segment, allowing the sender to compute the round-trip time for each acknowledgement received. A timestamp is a monotonically increasing value taken from a timer. Figure 24–14 shows the format of the timestamp option in the TCP packet header [JaBB92].

The timestamp option was introduced to make possible a more exact measurement of the packet round-trip time. When setting a segment, the sender sends the current timestamp in the TSval field. The receiver returns this timestamp in the Tsecr field of the ACK segment, together with the timestamp it set. Because the receiver returns the timestamp it received together with the acknowledgement for data accepted to the sender without considering the timestamp’s value, the timestamp unit is not relevant for the receiver. In particular, no timer synchronization between the communicating TCP instances is required [Sev94a]. This means that the sender can pack the estimated round-trip time for each acknowledgement received; this calculation is done in the method tcp_rtt_estimator() of the TCP instance in the Linux kernel.

Notice that only a single timestamp variable per connection is used, to minimize the number of states the communicating TCP instances have to maintain. The value of this variable is updated by the following algorithm:

- TCP holds the value for the timestamp to be sent in the next acknowledgement in the tp->ts_recent parameter.

- When an incoming TCP segment with the timestamp option set in the tcp_rcv_established() method is handled, then the routine tcp_ts_replace_recent() checks on the tcp->rcv_tsval timestamp contained in the tp->ts_recent value should be accepted. If so, this is done by the tcp_store_ts_recent() method. In fast path, acceptance of the timestamp is checked directly.

- When a TCP segment with the timestamp option should be sent, the value of the timestamp received is copied from the tp->ts_recent value to the Tsecr field when the packet header is assembled in tcp_transmit_skb().

The above algorithm shows the following behavior when segments are delayed or lost:

- When acknowledements are delayed by the receiver, the timestamp in the acknowledgement refers to the first of the segments being acknowledged.

- When an incoming segment belongs to the current window, but arrives out of order (which implies that an earlier segment was lost), the timestamp of the earlier segment is returned as soon as it arrives, rather than the timestamp of the segment arrived out of order.

The timestamp option can be negotiated by the same principle used for the window scaling option during connection-establishment phase. A TCP instance can set the timestamp option in the initial SYN segment (i.e., in a segment with the SYN bit set and).

### 24.4.2 Detecting, Avoiding, and Handling Congestions

The congestion control mechanism of TCP aims to prevent the network from being overwhelmed with data. Congestion control is different from flow control; while flow control prevents the sender from overwhelming the receiver, congestion control prevents the sender from overwhelming the network. The primary mechanism for detecting congestion in TCP is packet loss, which can be detected either through timeout or through the receipt of duplicate acknowledgments.

There are several algorithms used for congestion control in TCP, each of which attempts to estimate the available bandwidth of the network and adjust the transmission rate accordingly. The most common algorithms are slow-start, congestion avoidance, fast retransmit, and fast recovery.

Slow-start is used at the beginning of a connection or after a timeout event. During this phase, the congestion window is doubled every Round Trip Time (RTT), which allows the sender to quickly reach the available capacity of the network. Congestion avoidance is used once the congestion window reaches a certain threshold. During this phase, the congestion window is increased linearly every RTT, which allows the sender to carefully probe for additional available bandwidth.

Fast retransmit and fast recovery are used to handle packet loss detected through duplicate acknowledgments. Fast retransmit allows the sender to retransmit a lost segment without waiting for a timeout. Fast recovery allows the sender to continue sending data after the fast retransmit, rather than returning to slow-start.

The congestion control algorithms are implemented in the TCP stack and can be tuned depending on the operating system. In Linux, the default algorithm is Reno, but other algorithms like Cubic and BBR are also available.
