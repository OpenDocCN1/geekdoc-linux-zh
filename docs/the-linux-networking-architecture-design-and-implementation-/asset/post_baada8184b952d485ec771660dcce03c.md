# 19.2 The ipchains Rule Syntax

This section describes the ipchains program, which is used to manage rules lists.
The basic structure of a rule definition is given by the following form: ipchains -<operation> <chain> <criterion> <branch destination> -j command-line options of ipchains and iptables, before we describe the options in detail.

Operation: We can use one of the keywords listed in Table 19–1 to specify how we want the entering rules list to be manipulated. We use APPEND to build a list, which means that the new rule we just defined is appended to the end of a list. To generate a user-defined rules list, we use NEW. User-defined rules behave like subfunctions of the respective lists. This means that, when they are, evaluated with regard to the current packet and then packet is returned to the calling rules list, if none of the other rules applies to the packet.

# 19.2.2 Drawbacks of ipchains

## 19.2.2 Drawbacks of ipchains

The most important problems with ipchains were:

- ipchains have no uniform interface, which made it difficult to add new rules.
- The integration of rules into the kernel was expensive.
- The use of rules for NAT in ipchains was complicated.
- The use of rules for transparent proxies in ipchains was difficult.

- The use of rules for filtering packets in ipchains was complex. own- The use of rules for state tracking in ipchains was not available.

# THE NETFILTER ARCHITECTURE OF LINUX 2.4

Linux 2.4 divides the packet-filtering into two large blocks: the netfilter hooks and the rules lists. The hooks are located at different points in the network stack, where packets can be processed. The rules lists are used to define what should be done with each packet at each hook.

# Netfilter Hooks in the Linux Kernel

As mentioned briefly in 19.2.2, the netfilter architecture includes a uniform interface, reducing the cost to implement new functions. An integer identifier is allocated to each of these netfilter hooks. The identifiers of all hooks for supported protocol are defined in the protocol-specific header file <linux/netfilter_ipv4.h>. The following hooks are defined for IP Version 4 in <linux/netfilter_ipv4.h>:

- NF_IP_ROUTING (0): Incoming packets pass this hook in the ip_recv() function (see Section 14.2.1) before they are processed by the routing code. Prior to that, only a few consistency checks with regard to the version, length, and checksum fields in the IP header are done.

Meaningful opportunities to use this hook result whenever incoming packets are caught before they are processed—to detect certain types of denial-of-service attacks that operate on poorly built IP packets, or for address-translation mechanisms (NAT), or for accounting functions (counting of incoming packets).

- NF_IP_LOCAL (1): All incoming packets addressed to the local computer pass this hook in the function ip_local_deliver(). At this point, the iptables module hooks the INPUT rules list to filter incoming data packets. This corresponds to the input rules list in ipchains.

- NF_IP_FORWARD (2): All incoming packets not addressed to the local computer pass this hook in the function ip_forward()—that is, packets to be forwarded and leaving the computer over a different network interface. This includes any packet the address of which was modified by NAT. At this point, the iptables module hooks the FORWARD rules list to filter forwarded data packets. This corresponds to the forward rules list in ipchains.

- NF_IP_LOCAL_OUT (3): All outgoing packets created in the local computer pass this hook in the function ip_build_and_send_pkt(). At this point, the iptables module hooks the OUTPUT rules list to filter outgoing data packets. This corresponds to the output rules list in ipchains.
