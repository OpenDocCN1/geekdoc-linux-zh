
## 21.3.4 Initializing an Address-Binding Process

```
ipt_snat_target(), ip_dnat_target()          net/ipv4/netfilter/ip_nat_rule.c
```

ipt_snat_target() and ipt_dnat_target() functions are registered branch destinations for the nft table, nat. This process is processed only if the first packet of a new session flow was registered in ip_nat_fn(). The table uses lists to identify session flows subject to source NAT or destination NAT.

Initially, either of the two functions use ip_conntrack_get() to find the corresponding connection entry of the connection-tracking module and invokes the ip_nat_setup_info() function to do a new address binding. The result of this invocation, the address information of the newly assigned binding, is passed to the calling function.

```
ip_nat_setup_info()                               net/ipv4/netfilter/ip_nat_core.c
```

This function is invoked by the handling functions for the SNAT and DNAT branch destinations and essentially does three things:

- When the get_unique_tuple() (see below) is invoked, it searches for a free address available to do the translation. If no free address is available, then the value NF_DROP is returned and the packet is dropped.

- To other address translations into account, the entry for the reverse direction inverted by invert_tuplepr() is used as the basis rather than the connection-tracking address for the forward direction of the session flow, because the reverse direction entry already includes the translated addresses, in contrast to the forward direction.

- Invoking the ip_conntrack_alter_reply() function causes the reverse direction of a connection entry to be altered so that reply packets are allocated properly to the correct connection, despite its translated address.

- Finally, the new address binding is added to the substructure of the ip_nat_info connection entry. The mapping rules (e.g., transformation of source address and source port) are generated from comparing the original ip_conntrack_tuple structure with the new structure, supplied by get_unique_tuple().

```
get_unique_tuple()                               net/ipv4/netfilter/ip_nat_core.c
```

This function is invoked by ip_nat_setup_info() to search for a free address within a specified address range (represented by a structure of the ip_nat_multi_range).

If the function is invoked at the NF_IP_POST_ROUTING hook (i.e., to map the source address), then invoking the function find_appropriate_src() checks whether an address binding exists for the source address (IP address, protocol number, and protocol-specific part) in the bysource hash table for that packet. If this binding is within the specified address range, it is returned as a new address.

In all other cases, the combination of IP address and protocol number least used within the specified address range is determined by the function find_best_ips_proto_fast(). This function iterates over possible IP addresses in the address range and uses the byiproproto hash table to check the number of bindings existing at this IP address. If it finds an appropriate IP address, it lets the function ip_nat_used_tuple() check whether this address is unique, and if the IP_NAT_RANGE_PROTO_SPECIFIED flag is set, whether the protocol-specific part is within the address range (with the help of the protocol-specific function, proto->in_range). If this is the case, the tuple is returned. If this is not the case, both the new address and address range are passed to the protocol-specific function, proto->unique_tuple(). Now, this function attempts to vary the protocol-specific part (e.g., TCP port number or ICMP ID). If this attempt is unsuccessful, the function uses find_best_ips_proto_fast() to select the next IP address, and the checking starts over again. Eventually, if no combination can be found, value 1 is returned, and the packet is dropped.

## 21.3.5 The Actual Address Translation

```
do_bindings() net/ipv4/filter/ip_nat_core.c
```

This function applies the addresses specified in the ip_nat_info structure to a packet. To this end, it searches the info->manips list for all bindings that belong to the matching direction and the matching hook. It invokes the manip_pkt function to do the appropriate transformations. This function transforms the IP addresses, recalculates the checksum in the IP header, and invokes the proto->manip_pkt() function for the protocol-specific part, which does the actual translation and computes checksum, if present.

Finally, do_bindings() invokes a helper module, if present (e.g., for correct FTP handling—Section 21.1.7).

## 21.4 INTERFACES TO EXTEND THE NAT MODULE

The NAT module offers various extension options. These extensions are actually independent modules that can use the registration functions of the NAT module to register and unregister themselves. The following extensions are possible:

- Transport protocols (e.g., TCP): To use a new protocol, we have to write two extension modules—one for connection tracking and one for NAT.
- Helper modules (helpers): To be able to handle application protocols, such as FTP (see Section 21.1.7), properly, we can register helper modules. Again, this requires one helper each for connection tracking and NAT.
- Configuration-tool extensions: In addition, the iptables configuration tool has to be extended by the corresponding command-line parameters for each new protocol and each new helper module. We will not discuss this further.

### 21.4.1 Transport Protocols

The ip_nat_protocol_register() and ip_nat_protocol_unregister() functions can be used to register a new protocol or unregister an existing one. When registering a new protocol, we have to pass a pointer to a ip_nat_protocol structure.

```
struct ip_nat_protocol               net/ipv4/netfilter/ip_nat_protocol.h
struct ip_nat_protocol
{
	/* Internal use only */
	struct list_head list;

	/* Name */
	const char *name;

	/* Protocol number */
	unsigned int prot;

	/* Function invoked by manip_pkt to manipulate the protocol-specific part */
	void (*manip_pkt)(struct iphdr, size_t len);

	/* Checks whether the protocol-specific part is within the interval */
	int (*in_range)(struct ip_conntrack_tuple *tuple, int type, unsigned int min, unsigned int max);

	/* "core function". Invoked by unique_tuple() (see 21.3.4) to obtain a tuple by altering the protocol-specific part */
	int (*unique_tuple)(struct ip_conntrack_tuple *tuple, int type, unsigned int min, unsigned int max);

	/* Invoked when the protocol-specific information in match and mask should be output in text form */
	int (*print)(char *buffer, struct ip_conntrack_tuple *match);

	/* Invoked when the protocol-specific information in match and mask should be output in text form */
	int (*print_range)(char *buffer, struct ip_conntrack_tuple *mask);
};
```

### 21.4.2 Helper Modules

name is a character string containing the name of the protocol.

prot is the protocol number that will be entered in /etc/protocols.

manip_pkt is a pointer to a function invoked by the manip_pkt function of the NAT module to manipulate the protocol-specific part of a packet (See Section 21.3.5).

in_range is a pointer to a function that checks whether the protocol-specific part of an address (e.g., TCP) is within the interval [min,max]. The value of type shows whether the source or destination address will change; the function returns 1 if the condition is met, otherwise 0.

unique_tuple is a pointer to the module's "core function". It is invoked by unique_tuple() (see 21.3.4) to obtain a tuple by altering the protocol-specific part. The value of type shows whether the source or destination address should change; the protocol-specific part of tuple is set to the value of the original tuple.

The protocol-specific part generally is altered by a simple scheme (e.g., by incrementing the port number for TCP). Subsequently, the function ip_nat_used_tuple() is used to see whether the new address is still free. If so, the flag IP_NAT_PROTO_SPECIFIED is set, then range contains information about the range in which the protocol-specific part should be.

The two functions, print() and print_range(), are invoked when the protocol-specific information in match and mask should be output in text form. This information text should be written to the buffer, and the number of output characters should be returned. For example, tcp would invoke this function to out the port numbers.

A helper is a function invoked by the NAT module from within the do_bindings() function, once an address binding has been added (see Section 21.3.5). This allows us to verify the payload of a packet and to modify address transmitted in that packet—for example, to detect PORT commands over an FTP control connection.

```
struct ip_nat_helper               linux/netfilter/ipv4/ip_nat_helper.h
struct ip_nat_helper
{
    /* Internal use only */
    struct list_head list;

    /* Mask of things we will help with: vs. tuple from server */
};
```
