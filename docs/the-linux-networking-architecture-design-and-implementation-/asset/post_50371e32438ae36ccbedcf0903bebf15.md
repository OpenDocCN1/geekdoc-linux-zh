The following discussion considers only udp_getfrag(), because udp_getfrag_nosum() provides the same functionality, but is simpler for omitting the checksum calculation.

For each IP fragment it generates, ip_build_xmit invokes the callback function udp_getfrag() to get the required payload. A pointer to the udphdr structure filled by udp_sendmsg() is one of the parameters passed here, in addition to the desired destination address, and the desired data quantity.

The actual bulk of the work is done by the function csum_fromend(), defined in net/core/uvec.c. This function not only copies the data referenced by the uvec structure directly from the user address location, but also computes the checksum. The result of the checksum calculation is stored in the weck element of the udphdr structure in each step. The next step uses this result as a starting value, so that the checksum extends over the entire data.

The first fragment has to be created last, because it contains the UDP header with the checksum. It is left to ip_build_xmit() to ensure the correct order: udp_getfrag() recognizes the first fragment by the offset value zero. It extends the checksum calculation to the packet header and the IP pseudo header, and eventually it completes the packet header by inserting the checksum, before it finally copies it to the beginning of the packet.

# Receiving UDP Datagrams

```
udp_recv() net/ipv4/udpc
```

Once IP has received a UDP packet, it passes this in the form of an sk_buf pointer to udp_recv() for further processing. After the packet length has been checked and the checksum has been computed over the pseudo header (if the packet header includes no checksum, or if the checksum was computed by the interface hardware, this is registered in the sk_buff), udp_recv() directly forwards multicast and broadcast packets to udp_mcast_deliver(), which is deferred further down.

The most important task is to allocate the packet to a socket, so that it can be placed into that socket's queue until it is fetched by the user. This task is handled by the function udp_v4_lookup() (or udp_v4_lookup_longway()) invoked by udp_recv(). This function looks up the udp_hash table and selects the socket with the most specific information with regard to addresses, destination port, and input interface from the sockets linked in the entry and matching the packet.

> A checksum is computed if the flag no_check in the socket structure is null, which is the case by default. This flag can be set via the socket option SO_NO_CHECK on the SOL_SOCKET level.

```
udp_mcast_deliver()                               net/ipv4.udpc
```

Like udp_v4_lookup(), udp_mcast_deliver() searches for a matching receiver. However, it does not select the single socket matching best, but all sockets with a matching destination port—if this information is included—matching addresses and input interface correspond to the packet. All these sockets receive a copy of the packet. The copies are created using skb_clone() and delivered as in udp_queue_rcv_skb().

```
udp_recvsmsg()                               net/ipv4.udpc
```

If a user processes one of the system calls to receive packets, the socket interface it maps to a call of the function udp_recvsmsg(). This removes sk_buff structure from the receiver queue of the socket passed as a parameter, interprets as UDP packet, and returns the payload contained (and information from the packet header, if necessary) in the form of an msghdr structure passed by the receiver. If the queue is currently empty, either the process has to be waiting state, or the call has to be terminated with an appropriate fetch, depending on the specification.

The process of fetching sk_buff structures from receiver queues, of waiting for their arrival, and copying the data are part of not only UDP, but also required in several other places. Therefore, the file net/core/datagram.c contains generic functions for these purposes, which are used by udp_recvsmsg():

- skb_rcv_datagram() serves to fetch an sk_buff. This is done by skb_dequeue() (or skb_peek(), if the provided flags show that the packet should be read, but not removed). If an sk_buff is actually available, then it is returned; otherwise, if blocking is permitted, the function wait_for_packet() implemented in the socket registers the process as a waiting process with the socket and invokes schedule() to temporarily obtain control.

- skb_copy_datagram_ioc() (or skb_copy_and_datagram_iovec()) are invoked by udp_recvsmsg() to copy the payload into the packet into the skb_iov element of the msghdr structure to compute and verify the checksum in the process, applicable.

- skb_free_datagram() is used to release the sk_buff structure after the address information has been copied in udp_recvsmsg() and for example, IP options have been taken over into a control message (by calling the function ip_cmsg_recv()).

## The Concept of Sockets

### 26.1 INTRODUCTION

The abstraction of sockets was introduced (based on the BSD version of UNIX, where this interface was used for the first time; also called BSD sockets) to facilitate programming of networked applications. An application can use this uniform interface to send or receive data over a network. This interface looks alike for all protocols, and the desired protocol socket is selected to match three parameters: family, type, and protocol. Chapter 27 gives a complete overview of all available protocol families (family). It also discusses how applications can use the socket interface. In contrast, this chapter gives an overview of the socket implementation in the Linux kernel.

Figure 26–1 gives an overview of how the socket support is integrated into the protocol implementations in the Linux kernel. The BSD socket interface provides a uniform interface upwards to the applications; different protocol families are distinguished by protocol-specific sockets. One of the most important protocol families, PF_INET (protocol family) will be described in the following section. In addition, PF_PACKET sockets in recent Linux versions provide an elegant way to send data by directly accessing a device. For example, the use of packet socket was introduced in Chapter 9. Section 26.3 describes the packet socket in more detail. In contrast, the Netlink sockets do not serve for data transmission over a network, but to configure various parts of the architecture. The part to be configured is selected over the protocol variable, as shown in Figure 26–1.

## 26.2 BSD SOCKETS

The Linux kernel offers exactly one socket-related system call, and all socket calls of applications are mapped to this call. The function as long sys_socket_call(int call, unsigned long *args) is defined in net/socket.c. Moreover, number is assigned in include/asm/unistd.h (#define __NR_socketcall 102) and added to a table with system calls in arch/i86/kernel/entry.S. The socket function to be addressed can be stated in the call parameter of a call. The admissible parameters are defined in include/linux/net.h: SYS_SOCKET, SYS_BIND, SYS_CONNECT, SYS_LISTEN, SYS_ACCEPT, SYS_GETSOCKET, SYS_GETPEERNAME, SYS_PAIR, SYS_SEND, SYS_RECV, SYS_SENDTO, SYS_RECVFROM, SYS_SHUTDOWN, SYS_SETSOCKOPT, SYS_GETSOCKETOPT, SYS_SENDMSG, SYS_RECVMSG. From within libraries in the user space, the sys_socketcall() with a specific parameter is mapped to an independent function (e.g., sys_socketcall(SYS_SOCKET,...)) becomes the call socket(...).
