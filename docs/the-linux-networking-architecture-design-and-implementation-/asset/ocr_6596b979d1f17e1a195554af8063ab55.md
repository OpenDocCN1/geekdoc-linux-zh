integrates the protocol-control information of the LLC layer in the protocol field of the 802.3 frame, thus sparing any need for a separate LLC packet header. This means that the field value contains the protocol identifier of the layer-3 protocol and is registered in skb->type.
Older Ethernet adapters store the length of the frame rather than the protocol identifier of the layer-3 protocol in the length or protocol field. For this reason, the protocol-control information of the LLC layer has to be contained in the payload of the Ethernet frame (i.e. an explicit LLC packet header based on the 802.2 standard, SSAP and DSAP—see Figure 6–7).

eth_type_trans() does not verify the LLC-PDU any further, but returns ETH_P_802_2 as the layer-3 protocol identifier. The 802.2 LLC instance is treated as a layer-3 protocol instance. (See Section 6.3.) It is also registered as a layer-3 instance in the hash table ptype_base. This though conflicts with the layer model, it allows a simpler implementation in this case, because Ethernet adapters use the integrated LLC variant mentioned previously, and 802.2 is an exception-class. Finally, the demultiplexing to the layer-3 protocol takes place in the handling routine of the 802.2 protocol (p8022_rcv(), /net/802/p8022.c).

Layer-3 protocols can register themselves with the 802.2 protocol by use of the method register_8022_client(). For example, the SNAP protocol extension (net/802/snap.c) can register itself with register_8022_client(0xAA, snap_rcv). From then on, the method snap_rcv(), which links to the corresponding layer-3 protocol, is invoked for all SNAP frames.
