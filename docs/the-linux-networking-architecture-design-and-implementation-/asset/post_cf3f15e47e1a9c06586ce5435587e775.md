Specifying the Transmit Credit

The flow-control mechanism is effective in many places within a TCP instance. A detailed description of all of these situations would go beyond the scope and volume of this chapter, especially because Section 24.2 discussed several flow-control aspects. This section explains how the explicit credit for a partner instance is specified in each TCP segment sent.

```c

static __inline__ u16 tcp_select_window(struct sock *sk) {
    struct tcp_opt *tp = &(sk->tp_pinfo.of(tcp));
    u32 cur_win = tcp_receive_window(tp);
    u32 new_win = __tcp_select_window(sk);
}
```

tcp_select_window(sk) is invoked in the tcp_transmit_skb() method when a TCP segment is sent (except for SYN and ACK-ACK segments) to specify the size of the transmit credit (i.e., the advertised window). The current advertised window size is initially specified by the tcp_receive_window(). Subsequently, the __tcp_select_window() function is used to see how much buffer space is available in the computer. basis for determining the new transmit credit to the partner instance. However, as specified in RFC 793, care should be taken not to reduce a previously granted credit.

Once the advertised window has been computed, the credit is stored in the tcp_opt structure of the connection (tp->rcv_wnd). Also the tp->rcv_wup is updated; it stores the current value of tp->rcv_nxt when computing and sending the new credit. The reason is that each segment arriving after the advertised window has been sent has to be charged against the credit, just as happens in tcp_receive_window().

In addition, another TCP algorithm is used in this method, namely algorithm known as window scaling, which will be introduced in the next section. This algorithm had to be introduced to make it possible to work meaningfully with 16-bit number for the transmit and receive windows. It specifies the window size to the left. The value F in tp->rcv_wscale corresponds to advertised window increase by factor 2.

```c
tcp_receive_window() net/tcp.c
/* Compute the actual receive window we are currently advertising
* recv_nxt can be after the window if the peer pushes more data
* than the offered window.*/
static __inline__ u32 tcp_receive_window(struct tcp_opt *tp) {
    s32 win = tp->rcv_wup + tp->rcv_wnd - tp->rcv_nxt;
    if (win < 0)
        win = 0;
    return (u32) win;
}
```

This method calculates how much is left of the transmit credit granted in the last segment, taking the quantity of data received since into account. Slightly rewriting the equation, we can clearly identify the objective of this computation:

```c
s32 win = tp->rcv_snd - (tp->rcv_nxt - tp->rcv_wup);
```

The difference in brackets is the quantity received since the last window update: minus the sequence number of the next packet expected when sending the credit, which was stored in the tp->rcv_snd variable. This means that the resulting value, win, is the data quantity that can now be received against the credit last, corresponding to the actual size of the receive window.

```c
u32 tcp_select_window(struct sock *sk)
{
  // free_space is being computed
  free_space = tcp_space(sk);
  (..)
  if (free_space < tp->rcv_mss)
    return 0;

  window = tp->rcv_snd;
  if (((int) window) <= (free_space - ((int) mss)) ||
      ((int) window) > free_space)
    window = ((unsigned int) free_space)/mss;

  return window;
}
```

The _tcp_select_window() method is used to check how much memory of this connection is available for the receive buffer and what size can be selected for the receive window.

In the first step, tcp_space() determines how much buffer memory is available. After a few adaptations of the determined buffer space, it finally checks if there is enough buffer space for a TCP segment with maximum size (tp->rcv_mss). If this is not the case, this would mean that a Silly Window Syndrome (SWS) [Sext9a] has occurred. To avoid SWS, no credit smaller than the negotiated maximum segment is granted in such case.

If the available buffer space is larger than the maximum segment size, then the computation of the new receive window is continued. The window variable is set to the value of the credit last granted (tp->rcv_snd). If the old credit is larger, or by more than one segment size, than the available buffer, window is set to the smallest multiple of a maximum segment size (MSS) of the free buffer space (free_space). The value for window calculated in this way is returned as a recommendation for the new receive credit.

# Chapter 24 Transmission Control Protocol (TCP)

The Window-Scaling option can be used to increase the value range for the flow-control transmit window from 2¹⁶ to 2¹⁶⁺F, where F is the exponent specified by this option. The window-based flow-control method used in the TCP protocol uses the 16-bit Window field in the TCP header. This field is used to grant credits of up to 65535 bytes (the unit of the Window field is 1 byte, excluding window scaling). However, connections with a large path capacity (bandwidth times round-trip time) require a larger transmit credit to be able to send continuously. For example, if you consider a connection having transmission rate of 10 Mbps and round-trip time 100 ms, then a constant data flow requires a transmit window of at least 10 ms = 125000 bytes.

The window-scaling TCP option was introduced in [JaBB92] to solve this problem. Window scaling expands the TCP window from 16 to 30 bits. To ensure backward compatibility, the size of the Window field remains 16 bits; the option changes the base unit of the Window field to 2^F. Figure 24-13 shows the packet-format of the window-scaling option used by the TCP instances to negotiate the F parameter [Stev9a]. The Shift Count field includes the scaling factor for the receiver. If the F of the Shift Count field is unequal to zero, the base unit used to compute the receive window is 2^F.
