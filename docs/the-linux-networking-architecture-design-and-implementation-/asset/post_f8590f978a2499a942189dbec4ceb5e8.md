
To hide the characteristics of the underlying transmission technology, the LLC layer should offer three services, regardless of this technology:

- Unreliable datagram service (LLC type 1): This very simple service offers no flow control or error control, so it doesn't guarantee that data is transmitted. The removal of errors is left to the protocols of the higher layers.
- Connection-oriented service (LLC type 2): This service establishes a logical connection between the sender and the receiver, and it supports flow control and error control.
- Reliable datagram service (LLC type 3): This service combines LLC types 1 and 2—it is connectionless, but it supports both flow control and error control.

The very simple service (LLC type 1) is used mainly in local area networks, possibly for its simplicity. No connection has to be established, and the higher-layer protocols offer an integrated error-handling feature (e.g., TCP in the transport layer). The protocol header of the LLC type-1 protocol consists of three fields:

- DSAP and SSAP specify the service access points in the sender and receiver. It is unclear why protocol identification is stated for both the sender and receiver. Both fields have a width of eight bits, so very few protocols can be defined.
- The Control field always takes the value 0x03 for LLC type 1. This corresponds to Unnumbered Information Frame in the HDLC protocol, on which LLC protocols are based.

One major drawback of this solution is that many organizations try to integrate their proprietary standards into MAC PDUs. To ensure that duplicate assignments by different organizations are prevented, IEEE invented a packet format for the LLC, which allows each organization to define its own packet. This packet format is called SNAP extension.

In SNAP extension, the SSAP and DSAP fields take 0xAA, indicating that they expand the LLC header by five bytes. These five bytes can be divided into part for the organization and another part for the actual protocol identification.

This section gives an overview of the processes on the data-link layer. We will explain what activity forms play an important role on this layer and how transition between them occurs. Section 6.2.1 describes the process involved when a packet arrives, and Section 6.2.2 discusses how a packet is sent. First, however, we introduce the activity forms and their tasks in the Linux network architecture.

Figure 6–2 gives an overview of the activity in the Linux network architecture. As compared with earlier kernel versions, Version 2.4 and up introduced significant performance improvements. Mainly, the use of software interrupts, as compared with bottom halves, means a performance increase in multi-processor systems. As shown in Figure 6–2, we can distinguish between the following activities:

- Hardware interrupts accept incoming data packets from the network adapters and introduce them to the Linux architecture (per Chapter 5). To ensure that the interrupt can terminate as quickly as possible (see Section 2.2), incoming data packets are put immediately into the queue of the processing CPU, and the hardware interrupt is terminated. The software interrupt RX_SOFTIRQ is marked for execution to handle these packets further.

- The software interrupt RX_SOFTIRQ (for short, RX_SOFTIRQ) assumes subsequent (non-critical) handling of incoming data packets. It manages nearly the entire handling of protocol instances on layers 2 through 4 (for packets to be delivered locally) or on layers 2 and 3 (for packets to be forwarded). This means that most of the protocol instances introduced in Chapters 7 through 5 run in the context of RX_SOFTIRQ.

Packets incoming for an application are handled by RX_SOFTIRQ up to the kernel boundary and then forwarded to the waiting process. At this point, the packet leaves the kernel domain.

Packets to be forwarded are put into the outgoing queue of a network device over the layer-3 protocol used (or by bridge implementation). If the RX_SOFTIRQ has not yet used more than one tick to handle network protocols, then it tries immediately to send the next packet. If the soft interrupt was able to send a packet successfully, it will handle it to the point where it is passed to the network adapter. (See Chapter 5 and 6.2.2.)

- The software interrupt TX_SOFTIRQ (for short, TX_SOFTIRQ) also sends data packets, but only provided that it was marked explicitly for this task. This case, among others, occurs when a packet cannot be sent immediately after it was put in the output queue—example, because it has to be delayed for traffic shaping. In such a case, a timer is responsible for marking the TX_SOFTIRQ for execution at the transmission time and transmitting the packet.

This means that the TX_SOFTIRQ can transmit packets in parallel with other activities in the kernel. It primarily allows the transmission of packets that had been delayed.

Data packets to be sent by application processes are handled by system calls in the kernel. In the context of a system call, a packet is handled by the corresponding protocol instances until it is put into one of the output queues of the sending network device. With RX_SOFTIRQ, this activity tries to pass the next packet to the network adapter immediately after the previous one.

Other activities of the kernel (tasklets, timer handling routines, etc.) do various tasks in the Linux network architecture. However, unlike the tasks of the activities described so far, they cannot be classified, because they are activated by other activities upon demand. In general, these activity form run tasks at a specific time (timer handling routines) or at a less specified, later time (tasklets).
