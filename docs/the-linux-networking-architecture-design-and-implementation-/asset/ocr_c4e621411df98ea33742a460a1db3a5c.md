The Token_Bucket belongs to the operative component class, which means it has a packet input and out n packet outputs. In this example, these are the Conform and Non_Config outputs.

When an instance of the Token_Bucket component receives a packet, the receive handling routine is invoked. In the example: the parameters get the socket buffer, skb, and a pointer to the data in the component instance (bhvr). At the very beginning, a pointer to the instance's private data is set from this pointer, which requires a type cast. The function has to be reentrant, it must operate on its own private data or local variables.

Subsequently, computations along the token bucket algorithm (see Section 18.6.1) are done, and statistic variables are updated. From these computations determines the output should be used to forward the socket buffer (i.e., the kind of handling to follow). If no instance is appended to the corresponding, the function returns KIDS_ACCEPT result, which means the packet was processed and should not be forwarded to the head. The counter is KIDS_DROP; it tells the head it should drop the socket buffer.

However, if a component instance fails at the desired output (data->...bhvr != NULL), then that instance's handling routine is invoked (data->...func()), and a pointer to the data of the subsequent instance is passed to this handling routine, in addition to the socket buffer. The return value of the subsequent instance is used immediately for the return value of the token-bucket instance.

Linux KIDS handles packets in component chains via these nested function calls. Figure 22–6 shows this once more schematically. A description of the enqueuing and dequeuing hooks would go beyond the scope and volume of this chapter. We refer our readers to [Wehr01].

> Of course, as an alternative, the token bucket could evaluate the call's result, however, this is not implemented. In the case of a packet marked to be dropped (KIDS_DROP), for example, it could put the packet back into the bucket.
