# Debugging in the Linux Kernel

Debugging is a helpful step when writing reliable software. This is normally not a big problem when one writes simple applications. There are appropriate tools, such as the gdb debugger and its graphic variant, ddd, and other useful tools (e.g., strace), to track system calls.

However, the prerequisites are different for debugging an operating-system kernel. Remember that it is the very task of an operating system environment to run applications and to catch as many exceptions as possible to ensure that the work of other applications is not at risk. The best known error in programs is a NULL pointer that references the memory NULL rather than a valid memory address. When an application wants to access this page or run the statement at this location, the operating system should catch this error and output a message (i.e., segmentation fault or memory protection violation). The faulty application can then be checked by step in a debugger to find the faults in the source code.

Unfortunately, it's not so easy to check an operating system for itself. The reason is that, when a NULL pointer occurs in the system itself, there is no way to stop the computer from crashing. It is often impossible to find the exact location of an error or even the faulty component. Despite these circumstances, this chapter introduces several ways to track the process of a problem in the kernel to discover potential sources of error.

In addition to prevent NULL pointer dereferences, it is also important to obtain information about the functionality of algorithms and kernel components at runtime, to be able to check for correct operation. In the selecting of an operating system, its correctness is as important.

### B.1 LOG OUTPUTS FROM THE KERNEL

One of the most common techniques is the output of kernel messages. The following sections introduce several methods methods to create outputs from the kernel and make them visible.

#### B.1.1 Using printk() to Create Outputs

The printf() function is normally used in conventional writing of C programs—the standard input/output library <stdio.h>, which is not available in the Linux kernel. For this reason, the Linux developers simply implemented print() and integrated it into the kernel as the printk() function. Other functions borrowed from the standard libraries help the handling of character strings (lib/string.h).

printk() offers almost the same functionality as printf() and has a similar syntax. A special property of printk() is the classification of messages to be output by different debugging levels. The syslog and klogd daemons can be used to store and output messages or send them to specific addresses.

Alternatively, there are eight debugging levels, from KERN_DEBUG to KERN_EMERG—the highest level (system unless). These debugging levels are defined in <linux/kernel.h>. Depending on the DEFAULT_CONSOLE_LOGLEVEL variable, messages are output on the current console. The administrator can use the command syslog -c to modify the value.

printk() itself uses the printf() function to generate the output string. The reason is why the syntax of the two functions and parametering of the variables to be output is identical. sprintf() will be introduced in Section B.2.

#### B.1.2 The syslog Daemon

While the operating system is running, there are often situations where programs have to log error messages or specific information. In text mode these messages are simply at the console (stdout or stderr). A popup window is normally created for window-based applications (X11). The operating kernel and processes working directly for it, such as daemons or child processes of the init process, have no allocation to a console.

This approach can cause problems in a multiuser environment. On the one hand, messages can be read by anyone; on the other hand, the person in charge (normally the administrator) might be looking at something else and not pay attention to the message.
