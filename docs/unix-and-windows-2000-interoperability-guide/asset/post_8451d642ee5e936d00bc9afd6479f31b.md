You cannot export a directory and its parent if they are on the same disk or logical volume. The same goes for directory (/) and one of its subdirectories. For example, you cannot export the root directory (/) and /opt if both reside on the same disk or logical volume. If two directories reside in the same tree but on different disks or logical volumes, then you can export both as long as you do so explicitly in /etc/exports.

## 11.3.2.1 Symbolic Links

Watch for symbolic links when exporting file systems on HP-UX (or any UNIX system, for that matter). A symbolic link is a file name that points to a file located elsewhere. If the link points to a file outside the file system being exported, the Windows 2000 Client NFS client will not be able to access the file, even though an icon for the link appears in Windows Explorer.

## 11.3.2.2 Permissions

Regular HP-UX file and directory permissions override any export permissions. Therefore, even if you export a file system as read-write, only users with the right HP-UX permissions actually read or write data on a mounted file system. You can also specify access permissions on the mount operation on the client side. If the mount permissions differ from the export permissions, the more restrictive permissions take precedence.

## 11.3.1 Mounting a File System

Before a user can mount a file system, you should set up User Name Mapping and then direct Client for NFS to use the name mapping server. To do the latter, open the Services for UNIX Administration MMC, and select Client for NFS, as shown in Figure 11-6.

On the Authentication page, provide the name of your User Name Mapping server. When a user tries to access an NFS resource, Client for NFS sends his or her Windows user name to the User Name Mapping server. This server checks to see if the user has been mapped to a UNIX account. If so, the server returns the UID and GID to Client for NFS, which then embeds them into the NFS request. If there is no mapping for the user account, Client for NFS assigns –2 for the UID and –1 for the GID, establishing anonymous access.

### 11.4.1.2 Logging, Locking, and Client Groups

The SFU Administration MMC also enables you to configure logging, locking, and client groups. You can easily configure the logging of the following events:

- Mount: Users making mount and unmount requests.
- Locking: Users locking and unlocking files.
- Read: Users making requests to read a file.
- Write: Users making requests to write to a file.
- Create: Users making requests to create a file.
- Delete: Users making requests to delete a file.
- All: All of the above.

Just click on the Logging tab to configure logging. In the Locking tab you set the number of seconds users have to reestablish locks after a server reboot or you can manually release locks on specified clients.

UNIX and Windows 2000 servers differ in how they handle locks. According to SFU Help, UNIX computers follow advisory locking for all lock requests. This means that the operating system does not enforce lock semantics on a file, and applications that check for the existence of locks can use these locks effectively. However, NFS implements mandatory locks even for those locking requests that are received via NFS through the SMB protocol and to applications accessing the files locally. Mandatory locks are enforced by the operating system.

Client groups are groupings of clients so that you can apply NFS permissions—root access, for example—to the group as a whole rather than to individual systems. If you have a set of computers from which you do system administration and you want all systems to have root access to the NFS server, then you can create a client group, say admin_nodes, and assign access to the NFS export. Click on the Client Groups tab to create client groups and remove them from those groups.
