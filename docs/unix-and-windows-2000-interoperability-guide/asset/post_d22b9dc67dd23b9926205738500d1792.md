## 6.1.4 DNS Name Registration

Microsoft’s DNS and recent versions of BIND now support dynamic updates of the DNS database. Traditionally, DNS entries have been updated manually. But now you have in, in effect, a form of name registration that has long been a feature of WINS. We will come back to this topic later in this chapter. For now, let’s move on to NetBIOS name registration and resolution.

## 6.1.5 NetBIOS

NetBT is Microsoft's implementation of NetBIOS over TCP/IP, but we will assume you use TCP/IP and the more commonly used term NetBIOS instead. NetBIOS-based applications use NetBIOS to locate resources, establish connections, and receive data, and terminate connections. These services are the name service, the session service, and the datagram service. Because NetBIOS uses names to identify network resources, the name service is particularly important, since it manages the registration and resolution of names. The name service uses UDP port 137. The session service establishes, maintains, and terminates reliable, point-to-point connections between NetBIOS applications. A NetBIOS session must be established before any SMB (Server Message Block, the file-sharing protocol) transactions can take place. The session service uses TCP port 139. The datagram service, using UDP port 138, handles messages that do not require a session.

NetBIOS identifies network resources by names, not addresses. These names are 16 characters long and usually contain a computer name, a user name, or a domain name. You can specify the first 15 characters of these names, the sixteenth character is reserved to specify the specific network component addressed. For example, the NetBIOS name for the service (identified by 0 hex) for the computer JETHRO<00>. The domain master browser (identified by 1 hex) for the domain CLAMPETT is CLAM-PET<1B>. On Windows 2000 systems, you can view which names a computer has registered by typing nbtstat -n at a command prompt.

## 6.1.6 NetBIOS Name Registration

How are the names created? Usually, they are created when a service starts, like at system startup and when a service starts, its associated name is registered either by network broadcast or by consulting a NetBIOS name server (usually WINS). If a client is not configured to register its name with a name server, it will send a name broadcast called a Name Registration Request at startup on the local subnet. After a few tries, if no other client has contested the name, the client's name is officially registered on the subnet (can be seen by running nbtstat -n command). If the system is a WINS client, it sends a Name Registration Request directly to the WINS server, which does the job of ensuring the uniqueness of the name before entering it into its database. Since broadcasts are normally confined to subnets, it is wise to use WINS to enable internetwork registration.

## 6.1.7 NetBIOS Name Resolution

How a system resolves NetBIOS names to IP addresses depends on its node type. Systems are one of five node types:

| Node Type | Description |
| :--- | :--- |
| B-node | Broadcasts to resolve names. |
| P-node | Queries WINS to resolve names. |
| M-node | Broadcasts first, then queries WINS if that fails. |
| H-node | Queries WINS first, then broadcasts if that fails. |
| Enhanced | Uses the local LMHOSTS file DNS, in addition to the other types. |

By default, Windows 2000 systems are configured as B-node unless you specify a WINS server, in which case they become H-node. A Windows DHCP client can obtain its node type from a DHCP server. As with name registration, name resolution is greatly facilitated when you employ WINS in your environment.

If you configure your Windows 2000 system to be a WINS client and it becomes an H-node, the following name resolution process takes:

1. The client checks the NetBIOS cache to see if there is a matching entry for the target system. The cache can be preloaded with contents of the LMHOSTS file. See the comments in that file for more information.
2. If that fails, it contacts the WINS server via a directed datagram, a routable message sent directly to the WINS server.
3. If that fails, it resorts to broadcasting on the local network.
4. If that fails, it checks the LMHOSTS file, if enabled.

This process generally reduces broadcast traffic and the need for maintaining LMHOSTS files. Remember, beginning with Windows 2000, this process takes place only after the DNS name resolution failures.

## 6.2 HP-UX

### 6.2.1 Computer Names

You can set the name of an HP-UX system upon installation or by running the /sbin/set_parms hostname command. This host name can be a simple computer name of up to 64 characters, or it can be an FQDN. If it is not an FQDN, you must provide the domain option in the /etc/resol.conf file (See the next section, "Lookup Process.") UNIX systems do not have NetBIOS computer names unless they install a file-sharing package, if not all, such packages allow you to make a UNIX system a WINS client. In some, such as Advanced Server/9000, you also have the equivalent of a NetBIOS name cache.

## 6.2.2 Lookup Process

HP-UX systems can consult any of the following to resolve host names and IP addresses: a local /etc/hosts file, an NIS hosts map, or DNS. Which of these sources is consulted, and in order, is determined by the name service switch.

- /etc/hosts. The /etc/hosts file has the same syntax as the HOSTS file on Windows 2000 systems. Its usefulness is primarily for small networks that have little or no to communicate beyond the local LAN. Unlike the Windows 2000 HOSTS file, a UNIX /etc/hosts file's contents are not preloaded into a DNS cache.
- NIS. The NIS map is available to all NIS clients of a particular domain. There is one copy per NIS domain, making maintenance of host name information easier. However, like /etc/hosts files, NIS maps do not scale well if your systems need to communicate with others outside your LAN. Many UNIX systems now support NIS+, though it is recommended that you use one or the other of NIS or NIS+.
- DNS. DNS, usually in the form of the Berkeley Internet Name Domain (BIND) service, is available for larger scale name resolution.

### 6.2.2.1 The Name Service Switch

The name service switches when a system will search for key pieces of information, including host names and their IP addresses. You configure this switch by editing the /etc/nsswitch.conf.

A default version of /etc/nsswitch.conf contains the following lines:

```
passwd:          files nis
group:           files nis
hosts:           dns [NOTFOUND=return] nis [NOTFOUND=return] files
networks:        nis [NOTFOUND=return] files
protocols:       nis [NOTFOUND=return] files
rpc:             nis [NOTFOUND=return] files
publickey:      nis [NOTFOUND=return] files
netgroup:        nis [NOTFOUND=return] files
automount:       files nis
aliases:         files nis
services:        nis [NOTFOUND=return] files
```

The first field indicates the information database to consult. To configure the name resolution process, you change the hosts line. HP-UX default is to consult DNS. If the service is not configured, NIS is consulted. If DNS is not configured, /etc/hosts is consulted. If DNS does not find the host, then the lookup stops (indicated by NOTFOUND=return). This is the default behavior if /etc/nsswitch.conf does not exist. The syntax of /etc/nsswitch.conf is:

```
database:       name_service [ status = action status = action ... ]
```

The status keyword is what is returned by a name service query, which can be one of the following values:

- SUCCESS: The requested information was found.
- NOTFOUND: The name service responded but did not find an entry for the request.
- UNAVAIL: The name service wasn't available.
- TRYAGAIN: The name service was busy.

The action keyword determines what action to take given the status of a response. The continue action means to try the next name service in the list. The return action means to end the lookup process.

Therefore, as an example, if you want your system to consult /etc/hosts first, and then DNS if /etc/hosts does not find the requested information, then your hosts line in /etc/hosts.conf would look like this:

```
hosts: files [NOTFOUND-continue] dns [NOTFOUND-return] UNAVAIL-return
```

If this seems too complicated to figure out, use SAM. Select Networking and Communications→Name Service Switch. You will see a window like the one depicted in Figure 6–4. Just select the hosts line, choose Actions→Configure Name Service Switch, and use the interface to select the order and criteria for name lookups.
