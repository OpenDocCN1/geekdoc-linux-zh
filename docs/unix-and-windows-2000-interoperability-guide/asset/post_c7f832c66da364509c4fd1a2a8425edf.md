
## 11.2 NFS and Windows 2000 Issues

These basic concepts, then, are quite similar. The differences, are both numerous and substantial, as we shall see in the course of this and the next chapter. In order to share files between UNIX and Windows systems, we will have to either modify, or adjust the NFS protocol to make it compatible with Windows systems or adapt the CIFS protocol to make it compatible with UNIX. In this chapter, we concentrate on NFS, as provided by Windows Services for UNIX, and how to make it work on Windows systems.

### 11.2.1 Local File Systems and NFS

Between UNIX (including UNIX clones) and Windows 2000, there are a number of different file systems in existence. HP-UX has Hierarchical File System (HFS) and NTFS. Solaris has UFS. Linux has ext2. Windows 2000 has File Allocation Table (FAT), FAT32, and NTFS. Practically all operating systems support CD-ROM File System (CDFS). However, NFS was designed after UNIX file system semantics. All UNIX file systems store information about each file, the metadata, in inodes. Instead of inodes, NFS manipulates nodes, which contain similar information, such as the UID of the owner of the file, the GID associated with the file, and the permission bits. Other file systems, such as FAT and NTFS, have different structures. To accommodate different file systems, NFS employs a file system interface as the Virtual File System (VFS)/Virtual File Node (VNODE), which separates the file system interface from the specific file system implementation. While the VFS interface works, some NFS operations, such as symlink(), which creates a symbolic link to a file on a remote host, do not work—for example, if the remote file system is FAT. Also, since NTFS file attributes differ from those in UNIX file systems, there must be some mechanism to map these attributes.

### 11.2.1 NTFS, FAT, and CDFS

FAT and CDFS do not provide any security mechanism. CD-ROM file systems are readonly. To make FAT file systems writable over NFS, you must grant read/write access when mounting the file system. FAT file systems also have no concept of file ownership. Therefore, if you grant read/write access to a FAT file system exported by NFS, all users have full access to the file system. The only way to protect your exported FAT file system is to mount it as readonly.

### 11.2.2 NTFS

File and directory permissions differ between UNIX systems and NTFS. For example, UNIX does not have the Take Ownership permission. Somehow, NTFS permissions on a Server for NFS resource need to be mapped in such a way that the UNIX client can understand them. Fortunately, NFS handles this transparently.

### 11.2.2 User Authentication and Authorization

The NFS protocol utilizes the Remote Procedure Call (RPC) mechanism to perform operations. RPC is a mechanism whereby a client application passes a set of arguments to the local RPC library, which packages the arguments and sends them to a server. The server processes the call and returns the results to the client. NFS-RPC procedures can obtain and set file attributes, read and write data from or to files, and create and remove directories. Each RPC request that a client sends to a server must include UNIX credentials—the UID and GIDs—of the user initiating the request. The NFS server uses these credentials to determine what level of file access, if any, the user has.

The problem here is that Windows 2000 does not use UIDs and GIDs to authenticate and authorize users. It uses SIDs and security descriptors instead. Even if you install Server for NIS, which can incorporate UNIX attributes such as UIDs and GIDs into Active Directory, Windows running Server for NIS still need have some kind of mapping between UIDs/GIDs and security descriptors in order to determine access. To accomplish this mapping, you must use the User Name Mapping Service, a component of Windows Services for UNIX (SFU).

Also, keep in mind that with NFS, user authentication actually takes place at the client when a user logs in. The RPC request contains the UID and GID of the user initiating the request. The user cannot initiate a request unless he or she has logged in, and after that, the client does the work. The NFS server simply accepts the UID and GID of the RPC request as value and uses them to determine file access.

If you want to access NFS files systems from an HP-UX system on a Windows 2000 system, you must configure the HP-UX system as an NFS server and install Client for NFS on Windows 2000. But first you set up User Name Mapping.

### 11.3.1 Setting Up User Name Mapping

In order for NFS to validate an RPC request containing a UNIX UID and GID, it needs to find the equivalent user in Active Directory. The only way to accomplish this is to use some form of mapping of UNIX and Windows users. The same is true for Client for NFS. Since this client runs on a Windows 2000 system, there must be a way to provide the UNIX NFS server with a UNIX-style UID and GID if anonymous users are not allowed.

User Name Mapping provides the means for both Server for NFS and Client for NFS to obtain UIDs and GIDs for their use in their transactions. This service runs on only one system in the network (on a domain controller if you want to map domain accounts to UNIX accounts), providing a single mapping source for Windows components. When Server for NFS needs to find the equivalent Windows user for a given UID, it consults User Name Mapping before processing the request. When Client for NFS needs to insert a UID/GID combination into its RPC requests for a Windows user, it consults User Name Mapping before sending the request.

If a user accounts in both a UNIX network and a Windows 2000 domain, and those names are identical, User Name Mapping maps the names automatically with no administrator intervention. This is known as simple mapping. If you have users with accounts in both the UNIX and Windows 2000 worlds those differ, you must manually map these users using the User Name Mapping MMC. This is known as advanced mapping. Figure 11-1 shows the page of the User Name Mapping MMC that addresses simple and advanced mapping.

At this point you are provided with a window requesting information about what file systems to export and what the options are. A sample is shown in Figure 11-4.

You might want to consider Hewlett-Packard's Configuring and Administering NFS for more detail on export options. The default options include the following:

- **Option for Unknown User ID.** By default, this option will map anonymous users to the user nobody. Any NFS request not containing user credentials is considered to be from an anonymous user. The nobody user in HP-UX is listed in /etc/passwd as having a UID of -2, this value is sometimes represented as 65534 (the 16-bit unsigned representation of -2).
- **Allow Asynchronous Writes.** An asynchronous write occurs when an NFS server returns a response to a client before writing the data to disk. The default is not to allow such writes.
- **Permission for File Access.** The default is to allow read/write access for all systems. You can specify other kinds of access to different systems, though.
- **Specify Root User Access.** Normally, any NFS request containing root user credentials is mapped to the anonymous user, for security reasons. If you want root access from your administration system, you need to specify it here. Otherwise, the default is that no systems are granted root access.

If you accept the defaults, you will export the file system you specify with anonymous users given the UID of 65534 (-2).
