The first field in this file indicates the name that the application uses to identify itself to PAM, such as login. This name is usually the name of the command invoked by the user. The second field is the keyword for the type of authentication service, account for account management, auth for authentication, password for password management, and session for session management. The third field is a keyword specifying how to handle multiple definitions for the same application. If this keyword is required, as in this example, then the test for this module must succeed before moving on successive tests. If optional, the test for the module can fail. If sufficient, then further tests are performed if the first test succeeds.

The "pluggable" portion of PAM is specified in the fourth field, the dynamically loadable object invoked to provide a particular type of authentication. In the example above, each application under service calls /usr/lib/security/libpam_unix.1, the standard HP-UX model, to handle authentication. For PAM NTLM, this object is /usr/lib/security/libpam_ntlm. For PAM Kerberos, it is /usr/lib/security/libpam_krb5. For more information, see the following pages: pam(3), pam.conf(4), pam_update(5), and pam_user_conf(4).

## 8.2.4 PAM NTLM

Using PAM NTLM, anyone logging into an HP-UX 11 system can be authenticated by Windows or Windows 2000 server. PAM NTLM is part of HP’s CIFS/9000 Client product. This product enables HP-UX users to manage shares from Windows servers using the Common File System (CIFS) protocol, an alternative to NFS on Windows servers. To access these shares, you must either run the cifslogin utility or use PAM for authentication. PAM NTLM authenticates users using encrypted passwords and supports the ability to change passwords on Windows 2000 using the HP-UX passwd command.

The PAM NTLM configuration file is /etc/cifsclient/pam/smb.conf. Before you configure PAM, you must set the workgroup and password server parameters in this file to reflect your Windows 2000 domain name and domain controller. For example, if your domain is called BOOK and your domain controller is W2KSERV, then your configuration file will look like this:

```

```

Once you have configured /etc/opt/cifsclient/pam/smb.conf, you then change parameters in /etc/pam.conf. For each application, you must specify the /usr/lib/security/libpam_ntlm.1 authentication mode. On one of my systems, for example, I configured PAM to use NTLM for CDE login (dtlogin), CDE actions (dtaction), and password management. Furthermore, my /etc/pam.conf looks like the following:

```
#
# PAM Configuration
#
# Account Management
#
dtaction account required /usr/lib/security/libpam_ntlm.1
dtlogin account required /usr/lib/security/libpam_ntlm.1
ftp account required /usr/lib/security/libpam_unix.1
login account required /usr/lib/security/libpam_unix.1

OTHER account required /usr/lib/security/libpam_unix.1
#
# Authentication Management
#
dtaction auth required /usr/lib/security/libpam_ntlm.1
dtlogin auth required /usr/lib/security/libpam_ntlm.1
ftp auth required /usr/lib/security/libpam_unix.1
login auth required /usr/lib/security/libpam_unix.1
suth auth required /usr/lib/security/libpam_unix.1
OTHER auth required /usr/lib/security/libpam_unix.1
#
# Password Management
#
dtaction password required /usr/lib/security/libpam_ntlm.1
dtlogin password required /usr/lib/security/libpam_ntlm.1
login password required /usr/lib/security/libpam_unix.1
passwd password required /usr/lib/security/libpam_ntlm.1
OTHER password required /usr/lib/security/libpam_unix.1
#
# Session Management
#
dtaction session required /usr/lib/security/libpam_ntlm.1
dtlogin session required /usr/lib/security/libpam_ntlm.1
login session required /usr/lib/security/libpam_unix.1
OTHER session required /usr/lib/security/libpam_unix.1
```

As you can see, the dtaction and dtlogin applications specify libpam_ntlm. This permits me to log into CDE (See Figure 8–2.) Once I have logged in, I can run the passwd command: If I do so, passwd will change my password on the Windows 2000 domain controller. If I want to access a share on a Windows 2000 server, I do not have to run the cflogin utility first because I will have already been authenticated via NTLM. In other words, my interactive login takes place at the CDE login screen; my network login (remote login) takes place behind the scenes, as described in the Windows 2000 section of this chapter.

Using NTLM in this manner provides a single sign-on capability in that a single Windows 2000 domain controller maintains login and password management. However, it would be incorrect to think that you have a unified user account management system. In order for you to do anything on your HP-UX system (commands, utilities, applications), you have to have a user account on that system. To log in you have to have another account on your Windows 2000 domain controller. In other words, if you have a new user to your network, you will have to create an HP-UX account and a Windows 2000 domain account. To make this form of interoperability easier, you should keep the user names the same on both systems. Otherwise, you have to maintain a user map file. This maps HP-UX user names to Windows 2000 domain user names so that when you log in to HPUX, PAM NTLM knows what Windows 2000 user name to use when authenticating. You will probably need to have this file regardless of whether user names match in at least one case—the administrative account—you will have two different names: root for HP-UX and administrator for Windows 2000.

For more detailed information, see the PAM NTLM Release Note (available at docs.com).

## 8.3 PAM Kerberos

HP-UX supports Kerberos, based on PAM Authentication System v5, in the form of a PAM module. This PAM integrates HP-UX login with any Windows 2000 Client.

### 8.3.1 Configuring an HP-UX KDC and Application Server

You need to install MIT Kerberos version 1.x to make an HP-UX system either a KDC or an application server. Doing so will provide you with important documentation and tools (such as kadmin and ktutil). You can get MIT's distribution at web.mit.edu/kerberos/www/. You need to configure the following files for KDCs:

- /usr/local/var/krb5dc/kdc.conf
- /etc/pam.conf
- /etc/krb5.conf
- /etc/services

#### 8.3.1.1 /usr/local/var/krb5dc/kdc.conf

This file contains KDC configuration parameters and is for KDCs only. The following is a sample kdc.conf found in the release note. Modify it to suit your environment.

```
[kdcdefaults]
kdc_defaults = 88,750

[realms]
REALM.HP_COM = {
database_name = /usr/local/var/krb5dc/principal
admin_keytab = /usr/local/var/krb5dc/kadm5.keytab
acl_file = /usr/local/var/krb5dc/kadm5.acl
dict_file = /usr/local/var/krb5dc/kadm5.dict
key_stash_file = /usr/local/var/krb5dc/.k5.REALM.HP.COM
kadmind_port = 749
max_life = 10h 0m 0s
max_renewable_life = 7d 0h 0s
master_key_type = des-cbc-crc
supported_enctypes = des-cbc-crc:normal
}
```

There are additional steps to making an HP-UX system a KDC. For more information, both the Installation Guide that comes with the MIT distribution and HP's PAM Kerberos Release Note (available at docs.com), However, it is probably best to use a Windows 2000 domain controller as a KDC, since Kerberos is installed and a realm configured by default.
