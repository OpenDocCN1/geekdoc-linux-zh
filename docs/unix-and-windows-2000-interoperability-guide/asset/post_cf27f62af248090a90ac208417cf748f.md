
## 11.5.1 User Mapping

Key to the successful working of NFS, wherever it's configured, is the correct use of the User Mapping Service. First and foremost, you need to use Advanced Mapping in this service to map the root user on HP-UX systems to the Administrator account on Windows 2000. Even if you export directories with root access, you must map these accounts in order for the permissions to work properly. The combination of mapping the root and Administrator accounts and the exporting of directories with root access provides administrators appropriate rights.

For other user accounts, it helps to have your HP-UX user names and Windows 2000 user names match each other exactly. If you create an account on Windows 2000 with Server for NIS running, this is done for you automatically, provided you ensure that the UNIX attributes tab is properly configured. ## 11.5.2 Exporting Directories

After ensuring that User Mapping is correct, export your directories with the appropriate options, particularly if you need root access. Also, remember that, unlike Regular shares, NFS shares are case-sensitive. For example, if you export a directory with an NFS share named Home, the client must mount the directory with the name Home, not..

## 11.5.3 Local Permissions

To ensure proper access to directories, be sure that the local file system permissions are correct. On Windows 2000, this means that you should export directories only from NTFS volumes. If you have exported and mounted file systems with read/write permission, the local file system permissions may still prevent users from working properly with their mounted files and directories.

## 11.5.4 Overall Experience

Both Client for NIS and Server for Windows worked well, the client's connection with the HP-UX server was a bit slow (two to three seconds), and this was on an isolated network. Here, read and write performance was satisfactory after connection.

I did find, however, that having Windows 2000 configured as an NFS server was often tricky, involving the coordination of Server for NIS, User Name Mapping, and Server for NFS. For HP-UX users who need more than occasional access to files stored on a Windows 2000 server, it might be better to use a CIFS on the HP-UX system, which we will look at in the next chapter.

## CIFS File Sharing

The Common Internet File System (CIFS) is a file and print sharing protocol that runs natively on Windows-based computers. Originally called the Server Message Block (SMB) protocol—which many still refer to it as—CIFS is a NetBT application, enabling file and print sharing using the NetBIOS API running on top of the TCP/IP protocol suite. Because it is IP-based, CIFS can run across routers and WANs, making it a useful file sharing tool for the Internet. In functionality, it resembles NFS but differs considerably in its actual implementation.

## 12.1 CIFS Versus NFS

We looked at NFS in Chapter 11, "NFS File Sharing." As stated in The Design and Implementation of 4.4BSD Operating System (Musick, et. al.), pp. 312, 313

- The protocol is designed to be stateless. Because there is no state to maintain or recover, NFS can continue to operate during periods of client or server failures. Thus, it is much more robust than a system that operates with state.
- NFS is designed to support UNIX file system semantics. However, its design allows it to support the possibly less rich semantics of other file system types, such as MS-DOS.
- The protection and access controls follow the UNIX semantics of having the process present a UID and set of groups that are checked against the file's owner, group, and other access modes. The security check is done by file system-dependent code that can do more.

- The protocol design is transport independent. Although it was originally built using UDP datagram protocol, it was easily moved to TCP stream protocol. It has also been ported to run over numerous non-IP-based..

- Common Internet File System (CIFS) is both connection-oriented and stateful. It is connection-oriented in that it requires an SMB session to be set up before any file system command is issued. It is stateful in that the client retains state information to recover from a server at the point of failure. CIFS is designed to be a cross-platform protocol, but being the native sharing mechanism for Windows-based systems, it meshes easily with Windows file systems. The protection and access controls follow the Windows schema of having the server issue a request for credentials that can be used for the entire SMB session. This contrasts with NFS, where each request is independent, with credentials accompanying each request.

Other differences include the simple fact that NFS supports file sharing only, while CIFS supports file sharing, print sharing, and messaging. Also, CIFS supports opportunistic locks (oplocks). An SMB application can obtain an oplock on a file and then read and buffer the file's contents, which can improve performance. NFS does not support oplocks. In fact, it does not work well with any kind of locking, for as stated in Hal Stern and Mike Loukides' Managing NFS and NIS. p. 134. "Locking is a stateful operation and does not mesh well with the stateless design of NFS."

## 12.2 The Case for CIFS

You can examine these and other technical differences to decide which of these technologies are "better." In fact, there are folks out there who would just do that. However, beyond the technical differences, there is a lot of hype about the merits or deficiencies of NFS and CIFS. Those who don't like Microsoft (including the vendor who invented NFS, who will remain nameless) often trash CIFS because of its Microsoft origins. Old technology and out of step with the needs of the Internet. However, I will make the case that a CIFS-based technology is a better way to achieve interoperability with NFS. And I do so from an administrator's point of view.

In my experience, Windows-based systems completely dominate the business desktop. UNIX remains strong in the server market: application servers, file servers, Web servers. The only area where I've seen UNIX-based systems dominate the desktop is in scientific and engineering, graphics-intensive applications whose performance needs are met only by RISC-based UNIX systems. But even here, more and more of such applications are porting, or even rewriting, their applications for Windows NT and Windows 2000.
