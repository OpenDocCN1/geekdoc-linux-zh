## 8.1.1 Interactive Logon

Interactive logon is getting access to your local system. It begins with the Secure Attention Sequence (the CTRL+ALT+DEL keys). Executing this sequence signals the Winlog process (winlog.exe), which has been running since system startup, to call the Graphical Identification and Authentication (GINA) DLL. GINA displays the Log On to Windows dialog box, collects the user information for log on, and sends it to the Local Security Authority (LSA). This dialog box provides you with the opportunity to log on to the local computer or to a domain. The LSA is responsible for verifying your user credentials, which include the user name and password. (See Figure 8-1 for a depiction of receipt of these credentials). LSA runs a module (or “package”) based on which authentication protocol is in use. Windows 2000 supports two authentication protocols for network logins: NT LAN Manager and Kerberos v5. These protocols also support remote logons as well, but for now we concentrate on how they handle interactive logons.

## Windows 2000

### 8.1.1.1 NTLM

NTLM is the default for pre-Windows 2000 systems and is still supported for mixed environments and for logging on using local accounts. It uses the MSV1_0 authentication package and the Net Logon service.

MSV1_0 takes the clear text password issued by the user, encrypts it, and then converts it into a LAN Manager password and a Windows NT password. If the account is local, MSV1_0 queries the local SAM to validate the password. If the account is a domain account, MSV1_0 passes the password to the local Net Logon service. Net Logon then sets up a secure communication with the authenticating server's Net Logon service. The authenticating server then takes over the task of validating the user against its SAM (which is also the domain's SAM). The domain's SAM sends a Security Identifier (SID) for the user to the LSA, with SIDs for the user's groups, which then creates the access token based on this information for the logon session. The access token also contains the user's privileges and is attached to every process the user creates.

### 8.1.1.2 Kerberos

For authenticating domain users, Windows 2000 uses the Kerberos v5 authentication protocol for default. However, users running pre-Windows 2000 systems will continue to be authenticated using NTLM.

MIT developed the Kerberos authentication system, and its Web site is still one of the best sources on the protocol. We will describe Kerberos only in its most basic form in this chapter; it is possible to visit www.mit.edu/kerberos/ for more information. MIT Kerberos is available for free download. Kerberos on Windows 2000 is an integral part of the operating system.

The name Kerberos comes from Greek mythology: it was the name of the three-headed watchdog of Hades. In keeping with this heritage, the Kerberos authentication system consists of three main parts: the application client (e.g., ftp), the application server (e.g., ftpd), and the key distribution service running on a separate, physically secure server that acts as an intermediary between the application client and the application server. The key distribution service, as the name implies, dispenses keys to both clients and servers. These keys are used to encrypt and decrypt messages that verify the identity of the parties involved. The key distribution service runs on the Key Distribution Center (KDC). The KDC provides clients with tickets, which give them access to services.

The KDC maintains a database of security principals. A security principal is anything that has an account in it: user, group, computer, or service. The database of security principals maintained by the KDC constitutes its realm, more or less the equivalent of a Windows 2000 domain. It should be no surprise, therefore, that the KDC runs as a Windows 2000 domain service on each domain controller, using Active Directory (not SAM) as its account. The account database contains, among other things, an encryption key for all users, derived from their logon passwords. This encryption key is often referred to as the long-term key.

All Windows 2000 domain controllers are peers; therefore more than one KDC can exist in a domain. According to the Microsoft Windows 2000 Server Distributed Systems Guide, p. 659, "Windows 2000 does not, however, implement the Kerberos protocol. Instead, it replicates the information store for Active Directory by using a multicast replication protocol over a secure channel between replication masters."

The Authentication Service Exchange: The Authentication Service (AS) Exchange is where the KDC provides the client logon key and a Ticket-Granting Ticket (TGT) for use with other services. When a user logs onto a Windows 2000 domain from a Windows 2000 workstation (defaulting to Kerberos authentication), the workstation's LSA converts the user's password to an encryption key and saves the result in the credentials cache, a protected area of volatile memory. The LSA (via the Kerberos client) performs the AS exchange. The KDC verifies the user and returns the session key and the TGT. The TGT is encrypted with the KDC's key, and the session key is encrypted with the user's key. The client then stores the TGT in the credentials cache.

When the user wants to access a service, the client presents the TGT to the KDC to request a service ticket. This is the TGS exchange. The KDC verifies the TGT and returns a service ticket, which is encrypted with the service's key, and a session key, which is encrypted with the user's key. The client then presents the service ticket and an authenticator to the server. The server decrypts the service ticket with its own key and verifies the authenticator with the session key. If valid, the server grants access to the service.
