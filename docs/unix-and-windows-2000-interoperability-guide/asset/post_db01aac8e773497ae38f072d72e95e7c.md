## 7.2.2 Security Problems

The ability of BIND 8.1.2 running on HP-UX11 to handle dynamic updates is great, but there is a caveat. As of this writing, the Internet Software Consortium (ISC) has announced at least two serious bugs binding BIND version 8.1.2: the "solinger" bug and the "fdmax" bug. (See www://isc.org/products/BIND/bin.8.html). For this reason, the ISC recommends that you upgrade to least BIND 8.2.2 patch level 5, which Hewlett-Packard does not support at this time. By the time this is published, HP will very well do so. But to do so, you must integrate BIND with Active Directory.

According to Microsoft’s Microsoft Windows 2000 Server TCP/IP Core Networking Guide, p. 406. "Windows 2000 secures dynamic updates through the Generic Service Application Program Interface (GSS-API, specified in RFC 2708 rather than Domain Name Systemic Extensions (RFC 2535) or Secure Domain Name System Dynamic Update (RFC 2137). This means that in any given event Windows 2000 secure dynamic updates are incompatible with BIND's DNSSEC (DNS Security Extensions). BIND version 8.2 supports, though incompletely, DNSSEC. Complete will be available with BIND version 9.

## 7.2.3 Active Directory and DNS

Windows 2000 can store a primary DNS zone in Active Directory, making the data therein Active Directory objects. Therefore, in addition to normal DNS zone transfers, you can have information replicated through the Active Directory replication process. The advantage of integrating DNS with Active Directory is that you can have multimaster replication, with multiple domain controllers updating the zone. (See Microsoft Windows 2000 Server TCP/IP Networking Guide, p. 376) With traditional DNS, only a primary server can update the database.

According to the Microsoft Windows 2000 Server TCP/IP Networking Guide, p. 429, for the domain controller to work properly, the primary DNS server is authoritative for the names that are to be registered by the Netlog on the domain, must support the service location record (SRV). Furthermore, as we have already seen, BIND 8.1.2 on HP-UX does not support SRV records. Because you would have to manually update the primary zone when you configure Active Directory if you use an older version of BIND, Microsoft recommends that your DNS support dynamic updates. ISC has published on its Web site, www.microsoft.com/resources/bind-faq.html, the following statement regarding BIND and Active Directory:

Windows 2000 and BIND

BIND, by default, checks all records to ensure that only host names are used where host names are expected. Windows 2000 uses a subzone "dcs" to hold the Active Directory data. While this subzone cannot clash with any host name, it also makes it impossible to put hosts within this subzone without an illegal name. The use of such names will be rejected by default by BIND. To work around this we recommend that Active Directory be a separate zone (e.g., dcs.example.com), which should be reasonable as the Windows 2000 servers create this data and should not have interoperability problems with other machines.

```
zone "dcs.example.com" {
    type master;
    file "dcs.db";
    check-names ignore;
    allow-update {localnets};
};
```

## 7.3 Conclusion

I have demonstrated that it is possible to integrate DHCP and DNS with both HP-UX and Windows 2000. However, much of what was presented was proof-of-concept. Whether you choose to implement dynamic updates depends on how secure you want your environment to be. If you want to implement secure updates immediately, Windows 2000 offers this capability, which means you might have to convert from BIND to Windows 2000 DNS in your environment, something that may be expensive and time consuming. If you choose to keep BIND, you can still avoid using dynamic updates and maintain your IP addresses manually. Something to keep in mind is that traditionally mobile clients, such as laptops, really need DHCP. Such systems should not require IP registration because they are stateless. For a more complete discussion of clients, consult Robert W. Lucke's book, Designing and Implementing Computer Workgroups (Prentice Hall, 1999). In other words, evaluate carefully your need to implement dynamic updates until the security incompatibilities between Windows 2000 and BIND are resolved.

## User Authentication

Before we look at the interoperability of applications, we need to look at the issue of user authentication. We do this because most, if not all, of these applications require some kind of verification that the users are who they say they are. For example, if you use the Telnet application on a Windows 2000 computer to connect to a UNIX system, you are asked to provide a user name and password. You are already authenticated by Windows 2000, but you need authentication from the UNIX system. If you install a Telnet-server on a Windows 2000 system and wish to connect to it via Telnet, you will go through an authentication process there as well. So it is a good idea to examine how authentication takes place in both Windows 2000 and UNIX (again using HP-UX as our example), so that we have some idea of what's going on when you issue a user name and password.

This chapter examines authentication only, not authorization. Authentication is the process of verifying the identity of a user to the system. From the system's standpoint, authentication answers the question, “Do I know you?” If it does, you have access to the system. If not, you do not have access. Authorization is the process of determining what an authenticated user can do. The system knows who you are and grants you access; exactly what you can perform on the system is a matter of authorization.
