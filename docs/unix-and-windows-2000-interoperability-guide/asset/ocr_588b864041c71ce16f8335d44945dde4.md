You can also see the order of lookups by using the policy subcommand when nslookup in interactive mode. For example,

```
# nslookup
Using /etc/hosts on: hpux1

> policy
#Lookups = 2
files [RCCR]  dns [RRRR]

> exit
```

HP-UX also allows you to keep your options for the nslookup command in a file in your home directory called .nslookup. Type man nslookup on the command line for more information.

# 6.4 Name Resolution Issues in a Mixed Environment

# 6.4.1 The HOSTS Versus the LMHOSTS File

The format of the Windows 2000 HOSTS file and the UNIX /etc/hosts file is the same: IP address followed by host and alias names. If you employ DNS (as most sites do now), the question often asked is “Should I maintain a HOSTS file (Windows 2000 or UNIX)?” The answer to that is, “It depends.” A hosts file is handy as a fallback mechanism, which your DNS server become unavailable for some reason. It can also be useful if you want to Telnet to UNIX systems on a network where IP addresses are not entered into DNS.

If you have a system providing NetBIOS services and you have NetBIOS over TCP/IP enabled, the Windows 2000 HOSTS file will not help you. In this case, you might need to put its IP address and name into the LMHOSTS file and preload them with #PRE directive and/or make these systems (and your clients) are WINS clients.

# 6.4.2 The NetBIOS Legacy

There is a good chance that Windows 2000 systems will coexist with legacy Windows systems for a while. Also, your UNIX interoperability tools may continue to run NetBIOS. For these reasons it will be necessary to manage NetBIOS resolution and all that it entails: name cache, LMHOSTS, and WINS. However, you can greatly simplify your life by maintaining a WINS server in your organization and making all your clients WINS clients. This is also true of UNIX systems running NetBIOS. Such as Samba can make a WINS file and print a WINS client, which in turn will enable it to show up in browse lists.
