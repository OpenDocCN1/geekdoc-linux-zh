## 1.4 The Elements of UNIX

So, we now know, more or less, the origins of UNIX. As you can see, there is no such thing as the UNIX operating system. For convenience, I use one form of UNIX for this book, namely HP-UX version 11. HP-UX is based on the System V Release 4 operating system and includes important features from the Fourth Berkeley Software Distribution. Most HP-UX commands are the same as most UNIX implementations. However, you may have to consult the man pages for your particular system.

All UNIX implementations share some general characteristics, and what follows is a brief description of these characteristics. If you are mostly a DOS/Windows person, you should read through this section before looking at later chapters.

### 1.4.1 The Kernel

Every UNIX system has a file, loaded into memory upon system startup, called the kernel. HP-UX calls this file /stand/unix; Red Hat calls it /boot/mlinux. In one sense, the kernel can be considered the operating system itself, since it talks directly to the hardware, handles processes, interrupts, and the like. However, most people think of an operating system as being more than just the kernel; it also includes utilities, compilers, libraries, and editors. So, in another sense, the kernel can be thought of as the memory-resident portion of the operating system.

But there is no doubt that the kernel controls the interaction between user programs and the hardware. You, as a user, do not access the kernel directly. Instead, you run a command or an application that can do so by making a system call, one of the kernel routines residing in memory. To access certain pieces of the hardware, such as a tape drive, the driver for that device must be built into the kernel and must have at least one device file serving as a kernel pointer to the driver somewhere on disk.

Traditionally, UNIX systems have drivers for all the devices you use to be built directly into the kernel, creating a single, monolithic kernel. Adding new devices to this kind of kernel requires you to compile a new one that includes the new drivers, moving it into the appropriate location on disk, and then rebooting. Recently, however, UNIX systems have seen the emergence of dynamically loadable kernel modules, modules that can be added to the running kernel to support devices that may be used only sparingly. Having dynamically loadable kernel modules keeps the size of the kernel proper small, using fewer computing resources. HP-UX 11 supports modules.

### 1.4.2 The Shell

A shell is an interface between you, the user, and the kernel. It enables you to “do things” with the system. Traditionally, UNIX users have thought of the shell as a command-line interpreter. In other words, the shell would provide a command prompt, waiting for you to issue some kind of command. The command may be a built-in shell command (thus residing in memory when the shell is loaded) or it may be found on disk. If you are a long-time DOS user, then you know that your shell is COMMAND.COM. More recently, however, the shell can take the form of some kind of graphical user interface (GUI), enabling you to carry out functions without having to issue something on a command line. However, even these functions require a traditional shell to execute.

There are many shells to UNIX users. Each flavor of UNIX usually has what is known as the default shell, the shell used by system management scripts. The default shell is available. Available shells include the Bourne shell, the C Korn shell, the POSIX shell, and BASH (the Bourne-again shell, similar to the Bourne shell). Each shell has its own built-in commands, scripting language, command prompts, and special features. Which one you use is up to you, to keep you from having to learn all the shells and then choosing, the following:

- The Bourne shell is nearly universal on all versions of UNIX but is being obsolete on HP-UX because it lacks many features contained in the POSIX and Korn shells.
- The Korn shell is a superset of the Bourne shell, with some nifty features like history recall and editing.
- The POSIX shell is the default shell on HP-UX, and is similar to the Korn shell.
- BASH is the default shell for Linux and combines the best features of the Bourne and C shells. It is not available on HP-UX.
- The C shell incorporates a command history buffer, C language-like syntax, and control facilities. It is offered on all UNIX systems.

### 1.4.2.1 Terminal Emulators

So, how do you access a shell? When you create a UNIX account, one of the things you must specify is the path name of the shell that will run when the newly created user logs in. On older UNIX systems, you logged into some kind of text-based terminal, after which the login prompt disappeared and a blank screen with either a $ or a % command prompt took its place. This is frequently still the case on large server systems, however fancy graphics displays are usually unnecessary. If you use a current UNIX workstation, however, you are likely to login to some kind of graphical user interface based on the X Window System. Here, once you login, you get a number of windows, including something usually called a terminal emulator. A terminal emulator mimics one of the other terminals, most often the DEC v100 terminal.

Figure 1–1 displays an example of an *xterm*, a v100 emulator. This example comes from a Linux system; therefore the default shell is BASH. The default prompt for BASH is $bash$, but here it has been set to reflect the current user name and base name of the current working directory. Of course, *xterm* can run any of the other shells, and there are other terminal emulators out there, depending on the flavor of UNIX you run.

### 1.4.2.2 Entering Commands

If you want to administer a UNIX system efficiently, with lots of power and flexibility at your fingertips, then it is a good idea to master one of the shells. Although some folks might scoff at a command-line method of system administration, you can do much more, and do so quickly, you get a good start at it. This is one of the golden rules of UNIX system administration.

When you type a command, remember that in UNIX all names are case sensitive. So, if you type LS, thinking that it is the same as the ls command, you will be sorely disappointed. Also, most UNIX options are preceded by a minus sign (-). For example, the command -l at a command prompt will give you a detailed listing of the files and directories contained in your working directory. Finally, like DOS, UNIX has the concept of a command path, so if you get some kind of "not found" message after typing a command (assuming you spelled it correctly and had the right case), then you will have to find the full path name of the command and type.

### 1.4.2.3 Getting Help

At a shell prompt, you can get online documentation of any command by using the man command. For example, if you wanted more information on the ls command, you would type man ls at the command prompt. This will provide you with the official "manual page" (hence the name of command) for that command. So, if I say, "Check the man page for the chown command for more information," I mean to type man at the command line. A word of warning about man pages, however: they are written so that only programmers can understand. Once you slog through enough of a man page to get the basic idea of what a command can do, scroll to the bottom of the page and look at the examples that are usually provided. Doing so can save you a lot of time in trying to get something done.

### 1.4.2.4 A Note on File Editing

Effective UNIX system administration depends not only on using a command-line stuff, it also requires a good deal of text editing. With the exception of AIX, which has a configuration database somewhat analogous to Windows 2000's Registry, UNIX systems configure data from text files. To customize UNIX, you edit files. Usually, a vendor's system management tool will do a lot of it for you, but sooner or later, you will have to edit a file yourself. There are frequent debates about the merits and demerits of the various UNIX editors, vi and emacs are the most popular. Which one you choose does not really matter. Although the fancy GUIs that UNIX systems today usually have very easy-to-use editors, using something like vi, though archaic at first glance, managing a mixture of UNIX systems a lot easier.
