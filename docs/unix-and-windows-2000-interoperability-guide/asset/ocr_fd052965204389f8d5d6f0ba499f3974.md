# Server NIS

When an administrator creates an NIS domain account, or she creates an entry in the NIS master server's /etc/passwd and /etc/group files. The administrator then runs the shell script ypmap to update the maps. To replicate the changes of these maps to the slave servers, or she then uses a utility called ypush. The exact process can vary according to implementation and can be customized: Make a change to the configuration file, update the map, “push” to the slave servers.

Network Information Service Plus (NIS+), is the next generation of NIS. Like NIS, it is a distributed database system that allows you to maintain commonly used configuration information on a master server and propagate the information to all the hosts in your network. However, it is not an enhancement to NIS; it is a whole new service. The Windows 2000 Server for NIS does not support NIS+. But this should not be a problem, since NIS implementations are for more common.

# 10.3.2 What Server for NIS Can Do

Server for NIS can make a Windows 2000 domain controller serve as an NIS master server for a domain (or multiple domains) with UNIX slave servers and clients. It can also turn a domain controller into a slave server, as long as the master is a Windows 2000 system running Server for NIS. The reason for this is that Server for NIS stores maps in Active Directory, and the information of which is automatically replicated in Active Directory. UNIX slave servers obtain copies of Server for NIS maps via the usual UNIX protocols.

Storing maps in Active Directory is a key feature of Server for NIS. In addition to replication, you have strong security mechanisms in place. Perhaps most though, is the unification of Windows and UNIX user accounts in Active Directory. We have seen, and will see in later chapters, that interoperability schemes typically require duplicate user accounts: one for UNIX, one for Windows. These accounts must be identical to the letter and case for these schemes to work. Server for NIS will take any NIS object that has a corresponding Windows object, such as adds UNIX attributes to the Windows object. It does so by creating an auxiliary class for the Active Directory User group. In this auxiliary class are attributes corresponding to the fields of /etc/passwd. There are attributes for the user identifier (UID), the group identifier (GID), home directory, login shell, geccos information, as well as others. This effectively unites the UNIX and Windows 2000 user databases.

Server for NIS stores the user's password in UNIX format in the msSFPassword attribute. When a user sets or changes his or her password while working on a Windows 2000 system, Server for NIS stores the UNIX-style encrypted password in this attribute. As long as the user makes a password change on a Windows 2000 system, the Windows and NIS passwords are synchronized. If a user changes his or her password on a UNIX system using a utility like ypasswd, the password is changed only in this attribute, with no effect on the Windows password. Thus, we still have a dichotomy in user accounts, which can be resolved only with the separate Password Synchronization feature of SFU.
