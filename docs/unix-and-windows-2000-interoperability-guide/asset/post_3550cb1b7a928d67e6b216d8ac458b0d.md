The resolver submits names to DNS in the following manner (taken from Hewlett-Packard's Installing and Administering Internet Services, pp. 65–67).

- If the target name ends with a dot, BIND looks it up as, without appending any domains to it.
- If the name to be queried contains at least the number of dots specified by the ndots option in the /etc/resolv.conf file, BIND looks it up as, before appending any domains to it. (The default value of ndots is 1, so if the target name contains at least one dot, it will be looked up as, before any domains are appended to it.)
- If the target name consists of a single component (no dots), and you have set up a host aliases file, BIND looks up in your aliases file to translate the alias to a fully qualified host name. You can create a host aliases file for frequently typed host names, like the following example:

```
john zircon.chem.purdue.edu
melody fermata.music.purdue.edu own```

The aliases (the first field on each line) must all be one word, with no dots. To use the file, set the HOSTIALASES environment variable to the name of the file, as in the following example:

```
export HOSTIALASES=/home/andrea/myalaises
```

- If the input host name does not end with a dot, BIND looks it up with domain names appended to it. The domain names BIND appends to it can be configured in four places: the LOCALDOMAIN environment variable, the hostname command, the search option in the /etc/resolv.conf file, and the domain option in the /etc/resolv.conf` file. If a user has used the LOCALDOMAIN variable, as in the following example,

```
export LOCALDOMAIN=nmt.div.inc.com
```

the LOCALDOMAIN variable overrides the host name and any search or domain option in /etc/resolv.conf for BIND requests made within the context of the user's shell environment. The target host name is looked up in each of the domains in the variable, in the order they are listed.

If the local host name is set to an FDN, and the search and domain options are not specified in /etc/resolv.conf, the host name is looked up in the domain configured in the fully qualified host name.

The search option specifies a list of domains to search. You can set the search option to list any of domains, but the first domain in the list must be the domain of the local host. BIND looks up host names in each domain, in the order they are listed. BIND uses the search option only if the LOCALDOMAIN variable is not set.

The domain option specifies the local domain. If you use the domain option, BIND will only search the specified domain to resolve host names. BIND uses the domain option for host name lookups only if the LOCALDOMAIN is not set and the search is not specified. (Do not use the domain and search options together in the same /etc/resolv.conf file. If you do, the one that appears last in the file will be used, and any previous ones will be ignored.)

## 6.3 Nlookup Differences

The nslookup command works much the same way in both Windows 2000 and HP-UX. You can run it in interactive or non-interactive mode to query Internet domain servers. A key difference, however, is that in Windows 2000 nslookup queries DNS servers only, whereas in HP-UX it can also query /etc/hosts and NIS. Since NIS is not a Windows 2000 name service, you might expect it to consult the HOSTS file. This is not the case, however.

HP-UX, on the other hand, will follow the service switch, and nslookup will follow the directives of /etc/nsswitch.conf file. Therefore, if you follow the following entry:

```
hosts: files [NOTFOUND-continue] dns [NOTFOUND-return. UNAVAIL-return]
```

then nslookup will consult /etc/hosts first and DNS. For example,

```
# nslookup hp.com
Using /etc/hosts on: hpx11
```

## 6.4 Name Resolution in a Mixed Environment

### 6.4.1 The HOSTS Versus DNS

The format of Windows 2000 HOSTS is the same. If you employ DNS (as most sites do), the question often asked is “Should I maintain a HOSTS file (Windows 2000 or UNIX)?” The answer to that is, “It depends.” A hosts file is handy as a fallback mechanism, when DNS becomes unavailable.

If your current implementation of DNS does not support dynamic updates, you should disable client-side registration by clearing the Register this connection's addresses in DNS box in the Advanced TCP/IP Settings. (See Figure 6–5.) This will keep your DNS servers from being bombarded with registration requests from your clients.

### 6.4.2 The NetBIOS Legacy

There is a good chance that Windows 2000 systems will coexist with legacy Windows systems for a while. Also, UNIX interoperability tools may continue to run NetBIOS. For these reasons it can greatly simplify your life by maintaining a WINS server and all your clients WINS. This is also true of UNIX systems running NetBIOS.

### 6.4.3 The DNS Server

UNIX systems typically employ some version of BIND as their DNS server. Windows 2000 DNS is a different piece of software. While both BIND and Windows 2000 DNS are RFC-compliant, there are some important differences between the two:

- Dynamic updates
- WINS and DNS integration
- Active Directory support

### 6.4.3.1 Dynamic Updates

Windows 2000 DNS supports dynamic updates, which is the ability to register new systems and their IP addresses in the DNS database. BIND version 8.1.2 or later also supports dynamic updates; however, many UNIX systems still run BIND 4.9.7, which does not.

### 6.4.3.2 WINS

Windows 2000 DNS can be configured to query a WINS server should it fail to find a client's request. The DNS server then passes on the response to the client on behalf of the WINS server. The resource records that support this functionality—WINS and WINS-R—are found only in Windows 2000 DNS servers.

### 6.4.3.3 Active Directory

If your DNS service not run on a Windows 2000 server, then you must make sure that the service supports the SRV (service location) resource record in order to support Active Directory. BIND 4.9.6 and later support SRV resource records. According to Microsoft, if you use a third-party server, however, you cannot use the DNS console or Dnscmd.exe.
