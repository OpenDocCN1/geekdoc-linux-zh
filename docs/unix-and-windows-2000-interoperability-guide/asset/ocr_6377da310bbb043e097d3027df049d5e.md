# 10.3.1 Background

Windows Services for UNIX includes software called NIS Server. So what is NIS? NIS is Network Information Services, developed by Sun Microsystems in the 1980s to centralize data in UNIX groups. As long as UNIX systems worked like mainframe systems, that, serving multiple users from terminals, there was no need for something like NIS. But with the advent of the UNIX workstation in the 1980s, you suddenly had multiple users of multiple systems. Each system had its own database, its own hosts file, its own services file. For a subgroup of such systems to function properly, administrators had to ensure that each machine had identical versions of each of the configuration files. Even a small subgroup of, say, 10 machines, made administration cumbersome. But as groups expanded in size, it became ever more likely that a few systems would not be “sync” with the others.

NIS attempts to avoid this problem by providing uniform configuration information to all systems in a particular workgroup, called a domain. In this general sense, NIS domain demands Windows NT servers maintain key information such as user and group accounts in the form of maps. NIS client systems obtain such information by consulting either the master server or a slave server. An administrator can modify the master server’s maps, and master servers can replicate their maps to slave servers. There is only one master server and any number of slave servers per NIS domain.

Windows NT domains maintain key configuration information in domain controllers. Clients obtain this information from either Primary Domain Controllers (PDCs) or Backup Domain Controllers (BDCs). Administrators can modify network information on PDCs, and BDCs replicate their information to BDCs. There is only one PDC and number of BDCs per NT domain. As we know, Windows 2000 domains maintain network information in Active Directory, maintained by domain controllers in a peer-to-peer fashion, so the analogy starts to break here. However, I think you get the idea.

Rather than go into all the ins and outs of NIS, let’s use a basic example to illustrate how it works. The most common use of NIS is the centralization of user and group data. Without NIS, a system authenticates a user by consulting the /etc/passwd and /etc/group text files. With NIS, a system consults the user and group map made by an NIS master server on the network. The master server creates these maps using local /etc/passwd and /etc/group files. Therefore, the contents of these files on the master server are the domain’s user and group information. When you configure a master server, the contents of /etc/passwd and /etc/group are translated into databases (or maps) with names like passwd.byname.dir, passwd.byname.pag, and group.byname.dir. Therefore, an NIS client will authenticate a user by consulting these maps rather than /etc/passwd and /etc/group. (Administrators frequently query their clients to consult both.)
