The client stores both the session key and the ticket to the service in its credentials cache (after decryption, of course). It then requests a connection on the server by sending the application request (KRB_AP_REQ) containing an authenticator encrypted with the session key for the service, the ticket for the service, and an indication as to whether mutual authentication is required. The server decrypts this message and extracts the user's authorization data and session key.

The KDC provides the user's authorization data, including SID information, when the user requests a TGT. It also provides authorization when it grants a session ticket. After verifying the client's credentials, the Kerberos package on the server passes the authorization data on to the LSA. The LSA in turn builds an access token to determine authorization.

Remember that with the NTLM protocol, the server must contact the domain controller to authenticate a user. With Kerberos, the server does not do this. Instead, the client obtains a ticket for the service from the KDC, and the server determines the validity of the ticket without having to consult a domain controller. The process that makes all this possible can be quite complex, but is the basic difference between NTLM and Kerberos authentication.

# 8.2 HP-UX

Traditional HP-UX user authentication follows that of nearly all UNIX-based systems. In the early days of UNIX, you had a single user database contained in the /etc/passwd file. Users accessed this single database from text-based terminals. When the system started, it started a getty (get terminal) process, which displayed a simple login screen. This is as good as any mention to a little but irritating divergence between UNIX systems and Windows 2000 systems, namely the terminology referring to gaining access to the system. UNIX systems have a process called login, which is actually a program; not a program. Windows 2000 calls the login process, which would provide a command-line interface (a shell) and a user environment. As long as you had a single system with multiple terminals, you had an easy-to-manage multiuser system.

However, around the mid-1980s, things began to change with the introduction of the UNIX workstation. Each workstation had its own /etc/passwd file—its user database. As all applications were local, and as long as each user had their own workstation with no need to access any other system, these were still fine. But you all had to set up one user account per system. But users wanted to transfer files from one system to another; administrators wanted to share applications over the network. As a result, you had to ensure each user had an account on each system, something became increasingly difficult as the number of systems multiplied. The most popular mechanism to man-age user accounts from a single source has Network Information Services (NIS).
