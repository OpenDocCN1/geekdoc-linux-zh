The client stores both the session key and the ticket to the service in its credentials cache (after decryption, of course). It then requests a connection on the server by sending the application request (KRB_AP_REQ) containing an authenticator encrypted with the session key for the service, the ticket for the service, and an indication as to whether mutual authentication is required. The KDC provides the user's authorization data, including SID information, when the user requests a TGT. It also provides authorization when it grants a session ticket. After verifying the client's credentials, the Kerberos package on the server passes the authorization data on to the LSA. The LSA in turn builds an access token to determine authorization.

Remember that with the NTLM protocol, the server must contact the domain controller to authenticate a user. With Kerberos, the server does not do this. Instead, the client obtains a ticket for the service from the KDC, and the server determines the validity of the ticket without having to consult a domain controller. The process that makes all this possible can be quite complex, but is the basic difference between NTLM and Kerberos authentication.

## 8.2 HP-UX

Traditional HP-UX user authentication follows that of nearly all UNIX-based systems. In the early days of UNIX, you had a single user database contained in the /etc/passwd file. Users accessed this single database from text-based terminals. When the system started, it started a getty (get terminal) process, which displayed a simple login screen. This is as good as any mention to a little but irritating divergence between UNIX systems and Windows 2000 systems, namely the terminology referring to gaining access to the system. UNIX systems have a process called login, which is actually a program; not a program. Windows 2000 calls the login process, which would provide a command-line interface (a shell) and a user environment. As long as you had a single system with multiple terminals, you had an easy-to-manage multiuser system.

However, around the mid-1980s, things began to change with the introduction of the UNIX workstation. Each workstation had its own /etc/passwd file—its user database. As all applications were local, and as long as each user had their own workstation with no need to access any other system, these were still fine. But you all had to set up one user account per system. But users wanted to transfer files from one system to another; administrators wanted to share applications over the network. As a result, you had to ensure each user had an account on each system, something became increasingly difficult as the number of systems multiplied. The most popular mechanism to manage user accounts from a single source has Network Information Services (NIS).

### 8.2.1 Basic Authentication

The file `/etc/passwd` is a list of users known to the system. Each line of this file contains, among other things, a user's login name, encrypted password, user identifier (UID), and default group identifier (GID). Each UID is a simple integer and is unique so that the operating system can distinguish between users. If your system is part of a network (and most are these days), you must ensure that all UIDs are unique across the network. The `/etc/passwd` file does not contain passwords; instead, it contains encrypted passwords created as password keys using a one-way hashing function `crypt()`. Crypt uses an algorithm based on the Data Encryption-Standard (DES) of the National Institute of Standards and Technology. More common these days is for a UNIX system to store the encrypted passwords in a separate file, usually called `/etc/shadow` (as in “shadow password file”). Only the root user can read this file. Otherwise, ordinary users can obtain a list of the encrypted passwords, and using special programs, possibly determine the actual passwords themselves.

### 8.2.2 Network Authentication

In the UNIX world, network authentication is simply the act of making information available to others. The exact process of how this works varies by vendor and is documented in countless books. However, the key point is that even though /etc/passwd exists on the local machine, the system consults NIS to find out if the user exists on the local machine, not the the, exists on the network server. The local system simply accepts this assertion if the information is correct.

### 8.2.3 Pluggable Authentication Modules

HP-UX 11 supports Pluggable Authentication Modules (PAM). These modules make it possible to use mechanisms other than /etc/passwd or NIS to authenticate users. Other authentication methods include NTLM, Kerberos, and the Distributed Computing Environment (DCE). You configure PAM by editing the /etc/pam.conf file for one or more of four services:

- Authentication—Used to verify the identity of a user and to set the user-specific credentials.
- Account management—Used to determine whether the current user's account (not password) is valid. This includes checking for password and account expiration, as well as verifying access hour restrictions.
- Session management—To set up and terminate login sessions.
- Password management—To change a user's authentication token or password.

In /etc/pam.conf you specify what happens when you invoke a particular application for each of these services. As an example, pam.conf may look like the following:

```
# PAM Configuration
# Account Management
#
account required /usr/lib/security/libpam_unix.1
dtlogin account required /usr/lib/security/libpam_unix.1
ftp account required /usr/lib/security/libpam_unix.1
login account required /usr/lib/security/libpam_unix.1
su account required /usr/lib/security/libpam_unix.1
OTHER account required /usr/lib/security/libpam_unix.1
# Authentication Management
#
auth required /usr/lib/security/libpam_unix.1
dtlogin auth required /usr/lib/security/libpam_unix.1
ftp auth required /usr/lib/security/libpam_unix.1
login auth required /usr/lib/security/libpam_unix.1
su auth required /usr/lib/security/libpam_unix.1
OTHER auth required /usr/lib/security/libpam_unix.1
# Password Management
#
password required /usr/lib/security/libpam_unix.1
dtlogin password required /usr/lib/security/libpam_unix.1
login password required /usr/lib/security/libpam_unix.1
passwd password required /usr/lib/security/libpam_unix.1
OTHER password required /usr/lib/security/libpam_unix.1
```
