In contrast to these points, let's start with the fact that Common Internet File System
(CIFS) is both connection-oriented and state-full. It is connection-oriented in that it requires an
SMB session to be set up before any file system command is issued. It is state-full in that the cli-
entains sufficient state information to recover from a server at the point of failure.
CIFS is designed to be a cross-platform protocol, but being the native file sharing mechanism for
Windows-based systems, it meshes easily with Windows file systems. The protection and access
controls follow the Windows schema of having the server issue a request for credentials from the
client that can be used for the entire SMB session. This contrasts with NFS, where each request
is independent of others, with credentials accompanying each request. (Also important is here
the the fact that while CIFS requires a connection-oriented transport protocol, such as TCP, NFS com-
runs over the connectionless User Datagram Protocol (UDP).

Other differences include the simple fact that NFS supports file sharing only, while CIFS
supports file sharing, print sharing, and messaging. Also, CIFS supports opportunistic locks
opllocks). An SMB application can obtain an oplock on a file and then read and buffer the
file's contents, which can improve performance. NFS does not support oplocks. In fact, it
does not work well with any kind of locking, for as stated in Hal Stern and Mike Loukides'
Managing NFS and MIS. p. 134. "Locking is a stateful operation and does not mesh well with
the stateless design of NFS.
