# Configuring Persistent System Journals

To configure systemd-journald to preserve system journals persistently across reboot, set Storage to persistent in the /etc/systemd/journald.conf file. Run the editor of your choice as the superuser to edit the /etc/systemd/journald.conf file.

```
[Journal]
Storage=persistent
...output omitted...
```

After editing the configuration file, restart the systemd-journald service to bring the configuration changes into effect.

```
root@host ~# systemctl restart systemd-journald
```

If the systemd-journald service successfully restarts, you can see that the /var/log/journal directory is created and contains one or more subdirectories. These subdirectories have hexadecimal names in their length and contain *.journal files. The *.journal files are the binary files that store the structured and indexed journal entries.

```
root@host ~# ls /var/log/journal
73ab642e278e4be9bf80e8071a8cd5
root@host ~# ls /var/log/journal/73ab642e278e4be9bf80e8071a8cd5
system-journal en-1000.
```

While the journals persist an extended number of entries, the output of the journalctl command includes entries from the current system boot as well as the previous ones. To limit the output to a system boot, use the -b option with the journalctl command. The following journalctl command retrieves the entries limited to the first system boot:

```
root@host ~# journalctl -b 1
...output omitted...
```

The following journalctl retrieves the entries limited to the second system boot. The following argument is meaningful only if the system has been rebooted for more than twice:

```
root@host ~# journalctl -b 2
```

The following journalctl command retrieves the entries limited to the current system boot:

```
[root@host ~]# journalctl -b
```

> NOTE
When debugging a system crash with a persistent journal, it is usually required to limit the journal query to the reboot before the crash happened. The -b option can be accompanied by a negative number indicating how many prior system boots the output should include. For example, journalctl -b -1 limits the output to only the previous boot.

# SETTING LOCAL CLOCKS AND TIMEONES

Correct synchronized system time is critical for log analysis across multiple systems. The Network Time Protocol (NTP) is a standard way for machines to provide and obtain correct time on the Internet. A machine may get accurate time from public NTP services on the Internet, such as the NTP Pool Project. A high-quality hardware clock to ensure accurate time to clients is option.

The timedatectl command should provide an overview of the current time-related system settings, including current time, time zone, and NTP synchronization settings of the system.

```
[user@host ~$] timedatectl
Local time: Fri 2019-04-05 16:10:29 CDT
Universal time: Fri 2019-04-05 21:10:29 UTC
RTC time: Fri 2019-04-05 21:10:29
Time zone: America/Chicago (CDT, -0500)
System synchronized: yes
TP service: active
RTC in local TZ: no
```

A database of time zones is available and can be listed with the timedatectl list-zones

```
[user@host ~$] timedatectl list-zones
Africa/Abidjan
Africa/Accra
Africa/Addis_Ababa
Africa/Algiers
Africa/Asmara
Africa/Bamakako
```

Time zones are based on the public time zone database that IANA maintains. Time zones are named on continent or ocean, typically but not always the largest city within the time zone region. For example, of the US Mountain time zone is America/Denver.

Selecting the correct name can be non-intuitive in cases where inside the time zone have different daylight saving time rules. For example, in the USA, most of the Arizona (US Mountain time) does not have a daylight saving adjustment at all and is in the time zone America/Phoenix.
