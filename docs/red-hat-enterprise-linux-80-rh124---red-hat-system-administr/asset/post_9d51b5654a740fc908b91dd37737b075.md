
## CHAPTER 6 | Configuring and Securing SSH

- 6. Confirm that you can successfully log in to server as root using the password of the superuser.

- 6.1. Open an SSH session to server as root using the redhat password.

```
[operator2@server ~]$ ssh root@server
root@servera's password: redhat
...output omitted...
[root@server #]
```

Notice that the preceding ssh command used the password of the superuser for authentication because SSH keys do not exist for the superuser.

- 6.2. Log out of server.

```
[root@server #] exit
logout
Connection to server closed.
[operator2@server ~$]
```

- 7. Confirm that you can successfully log in to server as operator3 using the password redhat.

- 7.1. Open an SSH session to server as operator3 using the redhat password.

```
[operator2@server ~]$ ssh operator3@server
operator3@server's password: redhat
...output omitted...
[operator3@server ~$]
```

Notice that the preceding ssh command used the password of operator3 for authentication because SSH keys do not exist for operator3.

- 7.2. Log out of server.

```
[operator3@server ~]$ exit
logout
Connection to server closed.
[operator2@server ~$]
```

- 8. Configure sshd on server to prevent users logging in as root. Use redhat as the password of the superuser when required.

- 8.1. Open an SSH session to server as operator2 using the SSH keys.

```
[operator2@server ~]$ ssh operator2@servera
...output omitted...
[operator2@servera ~]
```

- 8.2. On server, switch to root.

```
[operator2@servera ~]$ su -
Password: redhat
[root@servera #]
```

- 8.3. Set PermitRootLogin to no in /etc/ssh/sshd_config and reload ssh. You may vim /etc/ssh/sshd_config to edit the configuration file of ssh.

```
...output omitted...
PermitRootLogin no
...output omitted...
[root@servera #] systemctl reload ssh
```

- 8.4. Open another terminal on workstation and open an SSH session to server as operator2. From serverb, logging in to servera as root. This should fail because you deleted root user login over SSH in the preceding step.

> NOTE: For your convenience, password-less login is already configured between workstation and serverb in the classroom environment.

```
[student@workstation ~]$ ssh operator2@serverb
...output omitted...
[operator2@serverb] ssh root@servera
root@servera's password: redhat
Permission denied, please try again.
root@servera's password: redhat
Permission denied, please try again.
root@servera: Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
```

> By default, the ssh command attempts to authenticate using key-based authentication first and then, if that fails, password-based authentication.

- 9. Configure ssh on servera allow users to authenticate using SSH keys, rather than their passwords.

- 9.1. Return to the first terminal that has the root user's shell active on servera. Set PasswordAuthentication to no in /etc/ssh/sshd_config and reload ssh. You may vim /etc/ssh/sshd_config to edit the configuration file of ssh.

```
...output omitted...
PasswordAuthentication no
...output omitted...
[root@servera ~]# systemctl reload sshd
```

- 9.2. Go to the second terminal that has operator2 user's shell active on serverb and logging in to servera as operator3. This should fail because SSH keys are not configured for operator3, and the sshd service on servera does not allow the use of passwords for authentication.

```
[operator2@serverb ~]$ ssh operator3@servera
operator2@servera: Permission denied (publickey, gssapi-keyex, gssapi-with-mic).
```

> NOTE: For granularity, you may use the -o PubkeyAuthentication=no and -o PasswordAuthentication=yes options with the ssh command. This allows you to override the ssh command's defaults and confidently determine that the preceding command fails based on the settings you adjusted in /etc/ssh/sshd_config in the preceding step.

- 9.3. Return to the first terminal that has the root user's shell active on servera. Verify that PubkeyAuthentication is enabled in /etc/ssh/sshd_config. You may use vim /etc/ssh/sshd_config to view the configuration file of sshd.

```
...output omitted...
#PubkeyAuthentication yes
...output omitted...
```

Notice that the PubkeyAuthentication line is commented. Any commented line in this file uses the default value of a parameter. The public key authentication of SSH is active by default, as the commented lines indicate.

- 9.4. Return to the second terminal that has operator2 user's shell active on serverb and logging in to servera as operator2. This should succeed because the SSH keys are configured for operator2 to log in to serverb.

```
[operator2@serverb ~]$ ssh operator2@servera
...output omitted...
[operator2@serverb]
```

- 9.5. From the second terminal, exit the operator2 user's shell on servera and serverb.

```
[operator2@serverb ~]$ ssh operator2@servera
...output omitted...
[operator2@serverb]
```

- 9.6. From the first terminal, exit the root user's shell on servera.

```
[root@servera #] exit
logout
Connection to server closed.
```

- 9.7. From the first terminal, exit the operator3 user's shell on serverb.

```
[operator3@server ~]$ exit
logout
Connection to server closed.
```
