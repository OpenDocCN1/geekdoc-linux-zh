
For example, two variables that affect the shell history and the history command are NHISTFILE and HISTFILESIZE. If HISTFILE is set, it specifies the location of a file to save shell history when it exits. By default it is the user's `/.bash_history`.
HISTFILESIZE variable specifies how many commands should be saved in that file from the history.

Another example is PS1, which is a variable that controls the appearance of the shell prompt. If you change the value, it will change the appearance of your shell prompt. A number of special character expansions supported by the prompt are listed in the "PROMPTING" section of the `bash(1)` page.

```
[user@host ~]$ PS1="\bash"
$ bash PS1="\u@\w \$ "
[user@host ~]
```

Two items to note about the above example: first, because the value set by PS1 is a prompt, it is usually always desirable to end the prompt with a space. Second, regardless of the value of a variable contains some form of shape, including a space, a tab, or a return, the value must be surrounded by quotes, either single or double: this is not optional. Unexpected results will occur if the quotes are omitted. Examine the PS1 example above and note that it conforms to both recommendation (trailing space) and rule (quotes).

## CONFIGURING PROGRAMS WITH ENVIRONMENT_VARIABLES

The shell provides an environment to the programs you run from that. Among other things, this environment includes information on the current working directory on the file system, command-line options passed to the prompt, and the values of environment variables. The programs may use these environment variables to change their behavior or their default settings.

Shell variables that are not environment variables can only be used by the shell. Environment variables can be used by the shell and by programs from that shell.

> NOTE NHISTFILE, HISTFILESIZE, and PS1, learned in the previous section, do not need to be exported as environment variables because they are only used by the shell itself, not by the programs that run from the shell.

You can make any variable defined in the shell into an environment variable by marking it for export with the export command.

```
[user@host ~]$ EDITOR=vim
[user@host ~]$ export EDITOR
```

You can export a variable in one step:

```
[user@host ~]$ export EDITOR=vim
```

Applications and sessions use these variables to determine their behavior. The shell automatically sets the HOME variable to the file name of the user's home directory when it starts. This can be used to help programs determine where to save files.

Another example is LANG, which sets the locale. This adjusts the preferred language for program output; the formatting of dates, numbers, and currency; and the sort order for programs. If it is set to en_UTF-8, the locale will use US English with UTF-8 Unicode encoding. If it is set to something else, for example fr_UTF-8, it will use French UTF-8 encoding.

```
[user@host ~]$ date
Tue Jan 22 16:37:45 CST 2019
[user@host ~]$ export LANG=fr_FR.UTF-8
[user@host ~]$ date
mar. Jan. 22 16:38:14 CST 2019
```

Another important environment variable is PATH. The PATH variable contains of colon-separated directories that contain programs:

```
[user@host ~]$ echo PATH
/home/user/.local/bin:/bin:/usr/bin:/usr/share/Modules/bin:/usr/local/bin:/usr/local/sbin:/usr/sbin
```

When you run a command like ls, the shell finds the executable file ls in each of directories in order, and runs the first matching it finds. (On a typical system, this is /usr/bin/ls.)

You can easily add additional directories to the end of your PATH. For example, perhaps you have executable programs or scripts that you want to run like regular commands in /home/user/sbin. You can add /home/user/sbin to the end of your PATH for the current session like this:

```
[user@host ~]$ export PATH=${PATH}:/home/user/sbin
```

To list all the environment variables for a particular shell, run the env command:

```
[user@host ~]$ env
...output omitted...
LANG=en_UTF-8
HISTCONTROL=ignored
HOSTNAME=example.com
XDG_SESSION_ID=4
...output omitted...
```

## Setting the Default Editor

The EDITOR environment variable specifies the program you want to use as your default editor for command-line programs. Many programs use vi or vim if it is not specified, but you can override this preference if required:

```
[user@host ~]$ export EDITOR=nano
```

## SETTING VARIABLES AUTOMATICALLY

If you want to set shell or environment variables automatically when your shell starts, you can edit Bash scripts. When Bash starts, several files contain commands that initialize the environment. The scripts run depend on how the shell started, whether it is an interactive login shell, an interactive non-login shell, or a shell script. Assuming the default /etc/profile and ~/.bash_profile, if you want to make a change that affects all your interactive accounts at startup, edit the .bashrc file. For example, you can set that account's default editor to nano by editing the file:

```
.bashrc
# Source global definitions
if [ -f /etc/bashrc ]; then
  /etc/bashrc
fi

# User specific environment
PATH="$HOME/.local/bin:$PATH"
# User specific aliases and functions
export EDITOR=nano
```

> NOTE The best way to adjust settings that affect all user accounts is by adding a file with a name ending in .sh containing the changes to /etc/profile.d directory. To do this, you need to be logged in as the root user.

## UNSETTING AND UNEXPORTING VARIABLES

To unset and unexport a variable, use the unset command:

```
[user@host ~]$ file=tmp.zsh
[user@host ~]$ unset file
[user@host ~]$ echo file
```

To unexport a variable without unsettling it, use the export -n command:

```
[user@host ~]$ export -n PS1
```
