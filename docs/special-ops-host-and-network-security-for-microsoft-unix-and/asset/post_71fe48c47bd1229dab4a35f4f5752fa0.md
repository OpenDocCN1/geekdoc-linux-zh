## Locating Possible Interactivity

The basis of Web application hacking lies primarily in altering or manipulating interaction between the client and the application. The next logical step in the methodology is therefore to find those areas of possible interactivity. A typical example of this is locating forms within Web pages. Forms are probably the most likely method of passing arguments to a Web application.

A form is easily spotted within a Web page and is enclosed by the <FORM> tags. Let's take a look at the following form and identify the key elements:

```
 <FORM METHOD="POST" ACTION="http://www.sensepost.com/special_ops/login.asp">
<!-- body of the form --

<INPUT TYPE="TEXT" NAME="USERNAME" SIZE="20">
<INPUT TYPE="PASSWORD" NAME="PASSWORD" SIZE="20">
<INPUT TYPE="SUBMIT" VALUE="LOGIN" NAME="LOGIN">
<!-- body of the form ends --
</FORM>
```

The first line can be considered as the definition of the form. It can be broken down as follows:
METHOD="POST"

The METHOD can be either a GET or a POST. The main difference between the way that form data is passed to the CGI program. If the GET method is used, the form data is simply appended to the end of the URL that is requested from the server. The CGI at the server end accesses the data sent by querying the QUERY_STRING environment variable. If our example form use of an HTTP GET to pass details to the server, the following would be an accurate representation of the submission:

```
GET /special_ops/login.asp?USERNAME=Haroon&PASSWORD=secret&SUBMIT=
HTTP/1.0
```

Accept: image/gif, text/html, /*
Accept-Language: en-us
User-Agent: Mozilla/4.0 (compatible; MSIE 5.0; Windows NT 5.0; .NET CLR 1.0.3705)

The GET method is normally frowned upon, because form information may be truncated (there is a limitation on the permissible length of a URL) and because it presents such obvious tampering capabilities.

```
POST /special_ops/login.asp HTTP/1.0
Accept: image/gif, text/html, /*
Accept-Language: en-us
Content-Type: application/x-www-form-urlencoded
User-Agent: Mozilla/4.0 (compatible; MSIE 5.01; Windows NT 5.0; .NET CLR 1.0.3705)
Host: www.sensepost.com
Content-Length: 31
USERNAME=Haroon&PASSWORD=secret
```

In the form above, we made use of three types of input, the TEXT, PASSWORD, and SUBMIT types. Other types of input can be CHECKBOX, RADIO, TEXTAREA, OPTION, and HIDDEN.

The interactivity that an attacker is searching for be contained within a form, but using the GET request could be nested within a normal-looking, clickable link on a Web page, such as the innocent-looking link that reads Next. It could be as follows:

```
<A href="http://www.sensepost.com/special_ops/login.asp?USERNAME=Haroon&PASSWORD=secret">Next</A>
```

Finding areas of interactivity reinforces the previous step of the methodology, viewing the source for revealing information. The next step involves pinpointing the weaknesses in how the application was designed.

## Pinpointing Attack Vectors

In order to determine how an attacker could exploit the application, you first need to have a complete understanding of the application itself. You need to fully understand what the application does, what it was designed to do, and with this

![](img/729efc56f204a2ebffb8295c3a2dfdfb_600_0.png)

information in mind, what an attacker could possibly do. By understanding the original intent of the application, you place yourself to identify potential weaknesses in how it was designed.

Most of these weaknesses fall into one of the following:

- Directory traversal
- Command execution
- Cross site scripting
- Parameter passing
- Database query

Information gathering is often overlooked, but it can be a powerful starting point. By returning such verbose error message (for a simple file not found error), the Web application has revealed a great deal of information to a potential attacker. The path /psis/imgview/inc/, for example, might never have been undiscovered. Simply browsing to this directory reveals an additional flaw, that the directory is indexable with no default document, once more giving a potential attacker more information than necessary.

This case can then be taken further by downloading and browsing the previously unseen source code with a view towards locating potentially vulnerable scripting.
