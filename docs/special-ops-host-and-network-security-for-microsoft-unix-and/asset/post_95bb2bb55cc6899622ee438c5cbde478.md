
# VLAN Jumping

This attack is a little more sophisticated than the others mentioned far. Frankly, our friends have not automated this through a simple interface yet, so the use of this exploit in the wild has been infrequent. The goal of this attack is for the user to see all the traffic from each of the different VLANs and subnets. The malicious user will try to convince the upstream switch that their workstation is also a switch with trunking enabled. This will work on several different brands of switches, but can easily be mitigated.

There are a couple methods for the user to jump from one VLAN to another. Starting with the most basic, the user will need to convince the switch that their workstation is a switch through the use of the Dynamic Trunk Protocol (DTP). Trunking and DTP are used to pass all VLAN traffic and information to other connected switches.

In a previous section, we talked about using VLANs to separate users and department subunits. It was also mentioned that although users may be in the same department, they might be physically located in another building. So the use of VLANs would have to span many switches. Trunking and DTP are the method in which this is done.

So in this basic attack, a malicious user will need to craft a packet that makes the upstream switch think that the device is another switch with trunking enabled. When this happens, all traffic from various VLANs will be transferred through the link to this host, giving the user access to all of the traffic on that switch. Although this attack is basic in nature, it can easily provide all of the data to the network.

The slightly more complicated attack is a variation on this theme. A malicious user will use two headers of 80.1q encapsulation within their packet to fool the switch. When the packet is transmitted to the first switch, the switch will peel off the 80.1q header and pass it to the next upstream switch. The second switch will receive what looks like an 80.1q trunk packet from the downstream switch (because of the second 80.1q header) and pass it on to the destination address. In this manner, the malicious user can send illegitimate traffic through multiple VLANs to the target host. Two switches have to be in use for this to work.

# VLAN Jumping Tools and Use

Currently there are no known tools that can automate these attacks, but it is possible to modify the packet contents to achieve the hack. The amount of work it would take to accomplish this, it does not seem feasible that a large attack could be used on a network. However, understand that new tools come out nowadays for automating attacks like these, and probably won't be too long before someone finds a way to accomplish this.

# Defending Against VLAN Jumping

The easiest way to mitigate the basic VLAN attack is to set all user and server ports to "DTP Off." This will disable the ability for a normal user to trick the switch into becoming a trunk on that particular port. Secondly, you will want to make sure that all of your legitimate trunking ports are in their own VLAN and are not part of any of the departmental subnets you have set up.

# Cisco Discovery Protocol Denial of Service

Cisco Discovery Protocol (CDP) is an administrative protocol that works at Layer 2 of the IP Stack, using Cisco routers to share information with neighboring routers. Information disclosed in these transmissions include Cisco IOS version, IP address, and any other management information such as IP address, duplexes, device capabilities (router or switch), and native VLANs. Although this information is dangerous enough in the hands of an attacker, there are more serious consequences with this protocol.

The vulnerability, first disclosed by FX Phenolit, can cause any one of these three symptoms to your Cisco device:

- There is a device reboot after 3–5 CDP frames are received.
- The device stops functioning after 1,000+ frames are received.
- All available device memory is used to hold CDP neighbor information.

In all of these circumstances, this attack will cause a denial of service (DoS) on your Cisco device.

# CDP Denial of Service Tools and Use

To make waters worse, a simple tool is in the work crew at Phenolit. This tool will effectively cause a denial-of-service condition on all vulnerable Cisco devices on your network. The tool is called Phenolit IRPAS and can be downloaded from Phenolit at www.phenolit.de/irpas. The tool currently works only on Linux-based machines. The following is some sample usage, taken from the Phenolit Web site, which will cause the DoS condition on your Cisco devices:

```
Brian# ./cdp -i eth0 -m0 -n 100000 -l 1480 -r -v
```

This command will send the maximum sized CDP frame with random data link addresses to all hosts within your multicast domain. Nothing else is needed to potentially cause a large outage on your network segments.

# Defending Against CDP Denial of Service

Mitigating your risk against this attack is quite simple: Disable CDP on all of your Cisco routers and switches, or update to the latest version of Cisco IOS. However, if you are still running a version of IOS prior to 12.0, the command to disable this feature is the following:

```
BRIAN(config)# #no cdp run
```

This will disable CDP on your device and protect against this attack. Remember, that CDP is used in some applications, such as CiscoWorks 2000, so there may be a use for the protocol in your environment. If this is the case, weigh the risks versus the rewards of running this protocol and determine what your ultimate goals are.

More information on this vulnerability can be found at the Phenolit de Web site (www.phenenoit.de/stuff/CiscoCDP.txt) and the Cisco Web site (www.cisco.com/public/issue).

# Applying Defense in Depth

As you have learned, defense in depth means we go beyond perimeter defenses but we should deploy security measures throughout our infrastructure. As easy as it is for an attacker to get through one layer, we must present malicious users with another layer to thwart these attempts. Focusing only on network defenses loses two types of attackers: those that break into your physical building and those that work on a daily basis.

So where do you begin?

I understand that applying the defense strategies and concepts presented in this chapter could take a very long time. As the size of your network goes up, so does the complexity and the amount of segments you need to secure. To started, I suggest you begin to determine which are most critical devices. This could be done in many ways.

So what do you do?

Possible solutions would be the deployment of IPSec on critical servers (such as between a Web server and backend database server) to encrypt the data transmission. Also, IPSec filtering can be used to protect servers from subnets or IP addresses that should not have access to a particular service or the server. These tools, with other intrusion detection systems, will help alleviate some of the risk past the second layer. Also, keep in mind the use of physical controls to make sure that employees or thieves don't walk off with your servers. Physical controls are as important as any technological security defense you put into.
