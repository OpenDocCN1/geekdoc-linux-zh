# Acquiring an Account

Assume that your SQL Server hunt was successful and you are now armed with a collection of IP addresses, instance names, and TCP ports. Now is time to acquire some security context so that you can gather information about the server, such as its version information, databases, tables, and other information that would help make the decision about which is the juicier target: the SQL Server data or the operating system.

# Sniffing Packets

Native SQL Server passwords are notoriously weak within SQL Server (due to weak policies) and in transit (due to poor obfuscation). Time to get your favorite packet sniffer and start capturing traffic to from your target (assuming you have this level of connectivity). Passwords transmitted over the wire are trivially obfuscated so that a simple game can turn them into plaintext. The password is converted to Unicode and XORed with A5 before being transmitted over the wire. In order to get the plaintext, simply XOR "obfuscated" byte by A5 to produce the original character (you will have to reverse the two hex characters so that 07 becomes 70, for example).

Even if you cannot sniff any accounts on the wire, it may be useful to simply monitor the SQL Server passing over the wire. Assuming no encrypted netlibs are used, it may be possible to get a great deal of information by monitoring the data on the wire. This data can include database names, parameters passed to system stored procedures, usernames, and other sensitive information.

# Brute Forcing Accounts

Another method of gaining access is to pray upon the weak passwords that are frequently used in SQL Server and attack accounts directly. If you are aware or can guess the naming convention for SQL Server accounts, there should be no problem. Assuming that you cannot do this, simply attack the System Administrator account (sa) directly since the account must exist.
Obviously, if the server is in Windows Authentication mode, you'll need to have some operation system context first.

There are several tools for brute forcing accounts. Most all of them involve the use of a dictionary of passwords to compare each user account. Table 12.4 outlines each of the available tools for SQL Server penetration testing that should exist in every toolbox and are best for a given situation.

# Finding Application Configuration Files

Often, the connection information for applications that use SQL Server is stored in places accessible to those determined to find it. Common places to look are the system Registry, "include" pages in Web-based applications (db_connect.inc for example), and configuration files for application servers, as global.asa (for Active Server Pages) or web.config (for ASP.NET). If you can gain access to these files, you may find the connection details you need to directly log into the application.

# WARNING

Microsoft's installation routines have had a number of issues related to passwords being left in the open by temporary files used installation. It is a good idea to go beyond any installation or service pack to make sure any messes are cleaned up (problematic files have been sqlsqp and setup.is). There are a number of Knowledge Base articles related to these issues—make to address them before considering any installation complete.

# Escalating Your Privileges

Privilege escalation (PE) can occur as either an increased level of privilege inside an existing application or the ability to step out the bounds of the current application to execute code of your choosing. PE can be achieved through bugs in an application server (SQL Server), through bugs in the application that runs on top of SQL Server, or even such devices as Trojan horse.

# Exploiting Unpatched Vulnerabilities

Although it is useful for us to quickly review some of the more popular vulnerabilities that have occurred in SQL Server, it should be noted that a fully patched SQL Server should be impervious to. When you have determined the service pack level of a SQL Server (using the @version system variable), you can compare it against vulnerability databases such as the one at SecurityFocus (http://online.securityfocus.com/cgi-bin/sfonline/vulns.pl).
