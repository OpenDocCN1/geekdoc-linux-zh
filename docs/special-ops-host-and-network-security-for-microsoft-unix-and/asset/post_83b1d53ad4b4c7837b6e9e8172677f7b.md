Making searches in authenticated mode reveals much more. For the same Active Directory catalog where only 62 entries were visible to an anonymous user, now 1,300+ entries are visible. It is possible to search for specific types of entries or only in certain subtrees, such as CN=Users, DC=width, DC=home. This specifies only subtrees that hold user-related information. Configuration or Schema subtrees could be very interesting; for example: CN=Configuration, DC=width, DC=home, "CN=Schema, DC=width, DC=home. Note that although a privileged user by default can only browse this information, some entries may have been added by an administrator in a Schema subtree, for example, without assigning proper access rights to them, so that it is possible to modify them. This can lead to a complete disaster. If an Active Directory schema is damaged, this always leads to a malfunction. The only thing that can be done to fix the problem is to assign proper access rights to all objects created. This is a flaw not in Directory itself, but in LDAP usage of access rights. The point is, although we may not be authorized to view an entry in the directory, we are always informed of its existence. # Rogue DHCP Servers

DHCP servers are widely used in Windows networks because they help in simplification of IP addresses to clients (and even servers sometimes). But imagine that there is a false DHCP server up and running in your network. What damage could it cause? If you are not using DNS services, it could simply lead to assigning clients with wrong addresses, fast exhaustion of pools, and so on. When Dynamic DNS is used, the situation becomes even worse—as an attacker registers addresses on the DNS database, the number of incorrect address resolution replies by the DNS server grows.

Windows 2000 offers some kind of remedy for this—each DHCP server running on a Windows platform must be authorized in Active Directory before it starts distributing IP leases to clients on the network. This action can be performed by Enterprise Admins only and by selecting **Authorize** in the DHCP console. After that, the information about this server is stored in Active Directory (in `CN=NetServices, CN=Services, Configuration,<name of the forest>;branch;<name of the forest>` is a root domain name similar to `DC=what, DC=home`). The DHCP regularly checks Active Directory if it is allowed to function. Unfortunately, this is true only for Windows 2000-based DHCP servers. If somebody joins a Linux-based server, for example, it will function. Worse, if the attacker creates a key with the name `DisableRouteDetection` (type `REG_DWORD`, value=`0x1`) in the branch `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\DHCPServer\Parameters` of system registry, on a Windows 2000 DHCP server, this will turn off any attempt by the server to check for authorization, and it will start functioning. Now it is possible to create IP address collisions. In some of your servers use dynamic addresses (which is understandable, because with DDNS each server can change its IP and still be available on the network.

![](img/729efc56f204a2ebffb8295c3a2dfdfb_297_0.png)

This case illustrates one common principle of network security: It is impossible to ensure client-side security (make a server ask for authorization) from the server side (Active Directory). Thus, as an application of the above principle, always use static addresses for mission-critical servers and be careful with Dynamic DNS, securing it to the highest extent possible. Securing DDNS is reviewed in the “Hardening Active Directory” section in this chapter.

# Active Directory Dos with Group Policy Files

The example we just explained shows why it is crucial to secure all Active Directory–related files properly and be careful about assigning administrator privileges to people’s accounts. Consider the following situation: All computers in the network are up and running—this is good, but

- No administrators can log in to any of the domain controllers interactively.
- It is impossible to connect to domain controllers via any tools–Active Directory Management and other Microsoft Management Console (MMC)–connected tools.
- No network links are accepted by domain controllers.
- Web sites work slowly and do not allow any people to log on.

Pretty scary situation, isn't it? This can be resolved by restoring domain controllers from backups using usual Active Directory administration procedures—a long and costly process (although there is an easier way to fix). If you wonder how difficult it was to do so much damage, some changes in two files on one of the controllers. Active Directory with its distributed nature and replication capabilities did the rest. The attacker (a disgruntled system administrator for example) had to have administrator rights on the controller to cause all problems, but this does not lessen the importance of the attack method. The attacker simply changed two policy files (Default Domain Policy and Default Domain Controller Policy). They are stored as text files in a replicated SYVOL directory and as objects in Active Directory. Each of these files (GptTmpl.inf) has sections with the following (many lines are skipped for the sake of brevity):

```
[Privilege Rights]
SeMachineAccountPrivilege = *S-1-5-11
```
