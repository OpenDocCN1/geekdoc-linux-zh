# Auditing for Possible Security Breaches

Auditing Exchange 2000 is essential. If you are not currently auditing your E2K system, you may not even realize you are having security problems. Still worse, you may discover that you have a security problem, and you may not even be able to track it down. Auditing breaks down into a couple of categories. These are Windows 2000 event auditing, Exchange 2000 event auditing, and auditing the usage of Internet protocols.

# Windows 2000 Event Auditing

One of the essential security auditing tools that you need to take advantage of is the built-in Windows 2000 event auditing that you can turn through the Local Security Policy or collectively for an entire OU of computers through an Active Directory Group Object. Figure 7.24 shows the typical audit policy events that I like to configure.

The events that I choose to audit typically tell me when someone accesses the server, makes security- or account-related changes to the server, and when someone may have restarted the server. Table 7.12 shows the events that I tend to log along with an explanation.

### Table 7.12 Recommended Audit Policy Events

| Policy | Explanation |
|---|---|
| Audit account logon events | Audits logons using domain accounts. Audits changes to accounts, such as passwords being reset or group membership changes. The audit event does not always generate the detail I would like, like if an account is enabled or disabled, just that the account is changed. |
| Audit logon events | Audits logons using accounts that are local to the member server |
| Audit policy changes | Audits policy changes such as changing the audit policy |
| Audit system events | Audits events such as system shutdown or restart |

> Windows 2000 event logs can grow to quite a significant size quickly. The default size for these logs is 512KB, and they overwrite data that is only older than seven days. Administrators frequently ignore the warning that an audit log is full and later wonder why they don't complete information in their audit logs. Increase the size of your audit logs to a useful and reasonable size. For a typical Exchange 2000 server hosting 1,000 mailboxes, I don't believe it is unreasonable to have log files of 20,480KB (20MB) or even larger. I highly recommend increasing all of your servers' maximum event log sizes to at least 20MB.

Although I am not a fan of configuring an audit policy that covers every activity that occurs on a server, I also shy away from minimal auditing and auditing that examines only failures. Each additional audit policy you place on the server increases the load on the server by some amount, and it increases the size of the security log files. If you are truly concerned about logging events that may affect the security of your system, you will log not events where someone has tried and failed to accomplish something, this has been my philosophy.

# Exchange 2000 Event Auditing

There are also a few events you should enable for Exchange. Figure 7.25 shows the Diagnostics Logging page for an Exchange server. In Exchange 5, you could find the Diagnostics Logging page in a couple of different locations, but in Exchange 2000, these events are centrally located on a single page. To enable any type of diagnostics logging for Exchange, you must configure the Diagnostics Logging page for each server. Figure 7.25 shows the Diagnostics Logging page.

# Figure 7.25 Diagnostics Logging for Exchange

![](img/729efc56f204a2ebffb8295c3a2dfdfb_392_0.png)

In order to accurately track usage of the Exchange 2000 mailboxes, there are a number of event types I recommend you enable. Table 7.13 has a list of these categories and the location in which you will find them.

### Table 7.13 Diagnostics Logging Categories for Exchange 2000

| Category | Explanation |
|---|---|
| ExchangeS | Mailbox | Logons | Tracks access to mailboxes |
| | Access Control | Logs events when users attempt to access a mailbox to which they have no permissions or insufficient permissions |
| ExchangeS | Mailbox | Send As | Logs events when users use the Send As permission |
| ExchangeS | Public Folder | Logons | Tracks access to the public folder store |
| ExchangeS | Public Folder | Access Control | Logs events when users attempt to access a public folder to which they have no permissions or insufficient permissions |
| ExchangeS | System | Virus Scanning | Logs events related to virus scanning programs that are AVAPI 2.0-compliant |
| IMAP4 | Connections | Logs information about IMAP4 connections such as IP address |
| IMAP4 | Authentication | Logs information about IMAP4 client authentication |
| POP3Svc | Connections | Logs information about POP3 connections such as IP address |
| POP3Svc | Authentication | Logs information about POP3 client authentication |

Although these are not the only categories of events you can log with Exchange 2000, I consider these to be the bare essential events from a security perspective. Many organizations have requirements for logging additional information such as X,400 MTA connections, and transport-related events. The categories in the preceding table should be set to at least minimum.

When you are scanning your event logs looking for possible intrusions or things that don't look right, the event IDs in Table 7.14 may be helpful. These are by no means the events you should be looking at, but they will help you narrow down the events that indicate when a user is accessing the store.
