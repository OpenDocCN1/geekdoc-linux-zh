Now if you have your URLScan.ini file configured to reject .dll files and deny X-Vermeer-Content-Type headers, the request will be rewritten to the following:

```
GET /<Rejected-By-UrlScan>?~/_vti_bin/_vti_aut/author.dll HTTP/1.1
MIME-Version: 1.0
User-Agent: MSFrontPage/4.0
Accept: auth/synchronic
Content-Length: 0
Content-Type: application/x-www-form-urlencoded
Connection: Keep-Alive
```

The IIS log file, if recording query strings, will appear as follows:

```
2002-07-17 01:47:15 127.0.0.1 - W3SWC1 M1 127.0.0.1 80 GET
<Rejected-By>
UrlScan=~/_vti_bin/_vti_aut/author.dll 404
```

Notice that the rejected resource was <Rejected-By-UrlScan>, the default value for RejectResponseURL.

You can also set RejectResponseURL to the special value /* to cause URLScan to log requests in the URLScan.log file, but still allow the requests to go through.This is particularly useful when installing IISScan to identify potential problems with the configuration.

+   **UsePathReject** This setting changes the ways URLScan handles requests by having it the Win32 error code ERROR_FILE_NOT_FOUND and returning SF_STATUS_REQ_ERROR to IIS. This will cause IIS to immediately reject the request without any further processing. Note that doing this will prevent any further processing by ISAPI filters, custom IIS error handling, and recording the request in IIS logs. However, the rejected request will still be recorded in the URLScan.log file. The benefits of this setting are that the IIS logs do not contain all the URLScan recorded URLs and results in faster processing of rejected URLs.
