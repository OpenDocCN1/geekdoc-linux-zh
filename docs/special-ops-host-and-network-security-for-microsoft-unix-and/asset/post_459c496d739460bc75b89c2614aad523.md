# MAPI Clients and Firewalls

MAPI clients such as Outlook 97, 98, 2000, and 2002 require special considerations when accessing an Exchange server through a firewall. The Outlook client requires access to three ports when it connects to the Exchange server. The first port is the RPC end-point-mapper (port 135), the second is the directory service, and the third is the information store. The problem is that "directory service" and information store ports are dynamic, meaning they change when Exchange 2000 is restarted. MAPI clients use port 135 to "look up" the port numbers for the directory service and the information store.

Since the ports are dynamically assigned, we have to statically map these ports. In general, I think there is good practice during setup of Exchange servers to statically map the directory service and information store ports.

Most firewall and infrastructure administrators will become nervous if you tell them you must open up the RPC end-point mapper (TCP port 135). After all, there have been a couple of publicized denial-of-service vulnerabilities against this port over the years. Unless you are opening these ports for your data center or backup firewall, you might want to consider letting remote MAPI clients access the network through a VPN rather than opening ports through the firewall. After all, if they are a remote MAPI client, that requires they have some version of Outlook installed and configured, so the probability of being able to configure a VPN connection is good.

# Accessing the Exchange 2000 Directory Service

However, MAPI clients do not know this. When a MAPI client first loads, it contacts what it thinks is the Exchange 5.x directory service via MAPI over RPC. Each time the Exchange 2000 System Service starts, it dynamically picks an unused port above 1,024. This is not very practical when configuring a firewall server restarts. You would have to change the port number each time the Exchange server restarts. You can statically map the ports that NSPI and DSProxy use by creating a Registry value called TCP/IP port of type REG_DWORD and a value called TCP/IP port of type REG_DWORD. Create these values in the following registry:

```
\HKLM\System\CurrentControlSet\Services\MSExchange\Parameters
```

When you put in this value, make sure you realize that the default is hexadecimal; I click the decimal button so that I don't have to convert the port numbers I'm entering. This is done by picking values like 4000 and 4001.

# Where Are My Mail Notifications?

One of the most common questions that I get asked about Outlook clients sitting outside a tightly locked firewall is why new mail is not immediately arriving in the client’s inbox. New mail notifications are sent via UDP packet from the Exchange server to the Outlook client. Unfortunately, the client, not the Exchange server, picks this port at startup, thus it cannot be statically mapped at the Exchange server.

The only solution to this quandary is to configure the firewall to allow all outbound communication on UDP port 1,024 and above to leave the firewall when it comes from the Exchange server. This may not be a desirable solution. Thus, if you choose not to open these outbound ports, the client will simply have to manually poll the Exchange server (pressing the F5 key) for new mail or simply wait until the Outlook client polls the Exchange server manually (about once an hour).
