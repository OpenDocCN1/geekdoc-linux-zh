# Introduction

The Domain Name System (DNS) is a distributed resource used by most network applications. DNS data is generally trusted implicitly; therefore can jeopardize the integrity of network traffic and allow attackers to play man-in-the-middle with all traffic. DNS security depends on the client, server, and their respective trust relationship. Securing the DNS structure varies according to its active role and requirements. Server responsibilities can be classified as three types (see Table 8.1). Depending on the need of the server, one specific role should be chosen; in particular situations, multiple roles can be supported on one physical server. Running an individual server for DNS role is ideal, specifically in a large production environment. After understanding the individual roles and mechanics between server, an administrator can securely and reliably maintain multiple roles on a single system. DNS security is custom for each server, type of communication, and common distribution, all of which will be explained in this chapter.

# Table 8.1 General DNS Server Categories

| Server Type | Definition |
|---|---|
| Root | Any server that acts as a central lookup for other servers to depend on, and does not rely on other servers zone information |
| Authoritative | Any server that hosts and returns zone information publicly |
| Resolver | A server that performs domain queries for end users but does not host zone information |

# History

DNS is the naming standard for IP-based networks. The concept of an IP naming convention was first released in 1971 by Paul Karp in the Request for Comments (RFC) 226. He conceived an original naming system by the name of "host mnics." This is more well known today as Internet domain names. RFC 226 was not a scalable solution, it was used for several years. The first DNS concept with commercial motivation was RFC 795 by Dr. David Mills in 1981, where he forced the first draft of a central naming convention "designed to scale to hundreds." Since that, DNS has changed dramatically, though the concept has remained the same. The political push and shove regarding ownership and responsibility almost led to the demise of commercial ownership. Many risks developed and occurred during the growth period of DNS, some of which are still possible.

Eugene Kashureff is founder of AlterNIC and one of many contributors to the increasing power of DNS. Kashuffer was financially hurt by the domain name sales monopolization by Network Solutions Inc (NSI). Due to the loss of control, he decided to override NSI. In July 1997, he altered the DNS for the primary Web registration (at the time intern.net), forwarding traffic destined for intern.net to his anti-NSI site AlterNIC. Kashureff’s stunt temporarily aborted global Web site purchasing and registrations at NSI. Almost simultaneously, he corrupted the master zone files for .com, .net, and .org, halting the use of lookups for many hours. Both security failures were felt globally and affected the integrity of the Internet.

The level of social engineering and lack of DNS integrity displays the minimal control on the Internet and the DNS. Since 1997, many changes have taken place, including system redundancy and central authentication, though both proved to be insufficient. In January 2001, an anonymous attacker fooled Verisign, a major DNS registrar and central authentication point, and the parent company of Network Solutions. The attacker complied with the current security checks and still received a valid certificate trusted Microsoft Corporation ActiveX. Attacks like these show the holes in the current system we depend on, showing failures can occur even when securing the dependencies of the Internet we all rely on. DNS operation is normally usual as any other resource, though with the correct modifications and administrative know-how, a root, authoritative, or resolver DNS server can be fault tolerant, secured, and reliable.

Due to the historical issues of DNS, security clearly must be up to the administrator. Trusting the DNS hierarchy is necessary; server vulnerabilities on the other hand can be removed with the proper steps. This chapter gives a clear guide to understanding DNS hacking, eliminating vulnerabilities, and employing a minimalist mindset in how to configure your DNS server.
