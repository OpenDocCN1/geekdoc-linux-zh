# Attacking and Defending DNS • Chapter 8

Common cache poisoning affects DNS resolver servers. When an end user submits a DNS query, (for example, hacker.com) to a resolver, the resolver server attempts to find an answer to the authoritative server for hacker.com (ns1.hacker.com). The cache poisoning occurs when the resolver server receives an authoritative DNS response from an authoritative server that includes extra information. This extra commonly is an extra authoritative record, which says ns1.hacker.com is authoritative for the yahoo domain. From this point forward, all queries on yahoo.com will be sent to ns1.hacker.com. This is due to the resolver blindly caching the falsified results from ns1.hacker without verifying them.

A second, more difficult cache poisoning technique is also possible. Because DNS operates over UDP, a DNS query packet attack is possible where an attacker guesses the query or transaction ID number (see Figure 8.6). If an attacker can guess this sometimes easily spoofed packets and forged data can be accepted by a resolver server and the forged data injected into its cache table.

# Buffer Overflow

Just like any other application, DNS is susceptible to memory overflows. The authoritative undergrowth buffer overflow by Aleph One is recommended reading on the subject (www.insecure.org/stf/smashhack.txt). By its nature, authoritative DNS servers are available to interact with anyone on the Internet, so DNS has been a popular target of buffer overflow vulnerabilities. Due to BIND's overwhelming popularity as a DNS daemon, it has several overflow vulnerabilities over the years. The latest discovery was found by the ISS X-force Team (www.iss.net). ISS discovered that if an attacker can get a target server to cache a malformed SIG record, a overflow could be achieved.

This particular BIND vulnerability is due to a flaw in the datagram_read() function of BIND. Transaction signature (TSIG) records are initially checked by ns_find_tsig(); when ns_find_tsig() approves the record that contains a signature, find_key() checks to see if the key is valid. The possibility of a buffer overflow occurs when a transaction signature is discovered by a key NULL. In this case, msgen computes the beginning of request before the signature. An attacker can include his own extra code after the signature, which will be executed without error due to the false judgment of length by msgen. Although no public exploit code has been released, it has been proven successful and provided remote root of a target server.
