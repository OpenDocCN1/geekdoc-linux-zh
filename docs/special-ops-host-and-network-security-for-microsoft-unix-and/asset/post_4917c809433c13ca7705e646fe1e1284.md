
# LDAP

Lightweight Directory Access Protocol (LDAP) is a protocol that enables clients to access information within a directory service. LDAP was created after X.500, a directory service standard protocol, because of the overhead and subsequent slow response of heavy X.500 clients, hence the name lightweight. LDAP clients are able to access Active Directory, which opens Active Directory up to clients other than those that access Windows 2000 in a standard fashion.

You have noticed that even the naming scheme of Active Directory follows LDAP principles. Microsoft produced a very good tool called LDAPexe (it is included in the Windows 2000 Resource Kit), which allows a low-level browsing of Active Directory contents through the LDAP interface. Figure 6.3 is an example of some information (the most interesting items are in bold) produced during the anonymous connection to Active Directory server—a domain controller for the witt.home domain. You will see that the extent of the information given by Active Directory is much bigger and can be used for pre-attack reconnaissance.

> Note Lightweight Directory Access Protocol operates on TCP port 389 by default.

# DNS Integration with Active Directory

Active Directory is tightly integrated with DNS that Microsoft did not name it Active instead! DNS is required on the network for Active Directory to be installed and function. This is a major change for those who are migrating from non-Transmission Control Protocol/Internet Protocol (TCP/IP) networks. There are two impacts on the DNS service when employing Active Directory:

- In order for clients to log on a domain managed by Active Directory, DNS is required to locate the DCs. The NetLogon service requires a DNS server that supports the service records (SRV RRs) because SRRs both register and identify the DCs in the DNS namespace.
- Active Directory can store DNS zone information and replicate throughout the entire natively, without the zone transfer process. However, this requires that Windows 2000 DCs are also DNS servers.

Here is an example of an SRV RR that will look for a service from one of two different servers:

```
ldap.tcp.wit.home SRV 0 0 389 dns1.root.com
SRV 1 0 389 dns2.branch.root.com
```

DNS servers for the zones that the RRs for an Active Directory must be compatible with Active Directory, or Active Directory will not function. Even one DNS server is incompatible for that zone, problems ensue. For example, if a secondary DNS server for AD.DOMAIN.COM is not compatible because it does not support SRV RRs, at any point in time on the network could query the incompatible DNS server and not find the SRV RRs needed to locate Active Directory (because they are eliminated automatically from secondary zone due to not being understood). This situation is worse if the incompatible DNS server is primary for the domain, then all zone update the secondary servers with a database that does not include SRV.
