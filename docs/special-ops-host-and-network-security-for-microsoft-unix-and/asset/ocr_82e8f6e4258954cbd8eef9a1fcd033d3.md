The GUID/session ID in the example is D7A9CDC-4923-478F-93FD-6D7CE699F44A and the customer's login ID is 555555555. A GUID-session ID is recorded on the system on a successful login and is deleted when the user logs off the system (after a session timeout). Attempting to send a request to the server therefore would need an attacker to obtain both the victim's login ID and their GUID, the GUID in this case being a random 512-bit string. One checked not only for valid GUIDs but to make sure that the application also mapped GUIDs to customer IDs.

We therefore logged in with valid credentials, but attempted to manipulate the subsequent commands sent to the application by maintaining our valid GUID, but altering our customer ID Tools such as WebSleuth (https://www.geities.com/dzie/sleuth) or the @stake WebProxy at times like this, allowing us to make modifications to the form before we post.

Unfortunately, this did not achieve favorable results when attempting to check our balance. That is, we used our GUID, and someone's account number and requested a full balance sheet. The application returned an error message indicating that some checksum had obviously picked up our "hackery"
