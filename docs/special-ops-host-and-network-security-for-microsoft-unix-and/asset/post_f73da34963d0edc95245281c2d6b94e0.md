# Non-Executable Stacks and BSD

Currently, non-executable stack support is almost non-existent in the BSD Unix area. The only BSD operating system that currently supports a non-executable stack is OpenBSD. As of the 3.2 release of OpenBSD, the non-executable stack is a standard feature of the operating system. More information is available through the OpenBSD homepage at www.openbsd.org.

# Kernel Modules

Modern Unix systems use make of kernel modules. Modules are in theory an excellent idea—kernel modules, however, are prone to abuse.
As previously mentioned, the de facto method of placing a backdoor on a system through the use of a kernel module. Many systems provide the ability to limit the loading of kernel modules. Some systems allow the disabling of kernel modules altogether.

# Kernel Modules and Linux

Systems that allow the disabling of kernel modules usually require the kernel to be recompiled statically. Disabling kernel modules in Linux requires changing all compatibility-enabled modules to statically compiled options, and disabling load-able kernel module support.

# Kernel Modules and BSD

FreeBSD allows the disabling of kernel module support after the system has bootstrapped. By setting the kernel to run at securelevel 1 or higher, attempts to load modules after the system has bootstrapped will fail. OpenBSD and NetBSD are identical.

# Service Configuration

We mentioned previously that systems start a large number of default services by default. An example of this can be seen in Figure 14.8. This is a dangerous configuration to place on any network. Many services started by default, have had in the past, security issues that could allow an attacker to gain unauthorized access. This also extends to processes on the host by default. As we can see in Figure 14.9, a number of default processes are also started that may have security implications.

By this, it is entirely necessary to disable some, if not all services started on the host. The location and starting of services is usually unpredictable by either the init or inetd process. To eliminate potentially risky services started by default, we must edit the init and inetd configurations.

Most runs are controlled by inetd by the inetd configuration file, typically /etc/inetd.conf. Many of the services started via inetd are obscure, and sometimes there is fear about breaking a system by disabling all the running services. A rule of thumb: if you do not know the purpose of a service, do not run it.

Typically, the safest best is to create a backup of the inetd.conf file, named something like inetd.conf.bak. Edit the inetd.conf file to disable all unnecessary services. Unless the system is rebooted after configuring the inetd.conf file, the inetd service either be restarted by the HUP signal, or killed afterwards.

Some variation occurs between the methods in which init starts in BSD and Sysv systems use a set of flat files. The command to start the service is contained in the flat file, or a master configuration file is used to specify whether or not the service will be started. In FreeBSD, for example, the default configurations are all contained in the /etc/defaults/rc.conf file. From this file, the following files get attributes for the initialization of the system:

- /etc/defaults/rc.conf
- /etc/rc.local
- /etc/rc.d/*
