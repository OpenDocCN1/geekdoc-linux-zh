# ## 4.5.2 Authentication

The previous section spoke of UIDs and ownership without any mention of how identity is established. The identity of a process is almost always inherited from the parent process (or in the case of set UID feature described in Section 2.2.5, the ownership of a file).

In rare cases a process has authorization to change the identity of a process or the ownership of a file, but it will do so only if the requesting agent satisfies an authentication protocol.

First, a claim is made as to the identity. (We do not deal with systems where the identity is derived rather than asserted.) Authentic-ation is then based on different methods of validation. These methods are based on

+   - What you *know*
+   - What you *have*
+   - What you *are*

# ### What you know

In the case of a user logging into the system, a login program will ask for a user name and password. If the password is correct, it will create a shell process for that user with that user's UID.

# ### What you have

A locked front panel is a good example of a system requiring presentation of some object. You can access protected functions, such as the restart button, only after you've proved your identity by using the key.

# ### What you are

The third class of authentication systems rely on biometric charac-teristics which tend to be unique for each person. Commonly used charac-teristics are fingerprints or retinal patterns, but other systems measure hand shape, voiceprint, keystroke latencies, the dynamics of your hand-writing, etc.
