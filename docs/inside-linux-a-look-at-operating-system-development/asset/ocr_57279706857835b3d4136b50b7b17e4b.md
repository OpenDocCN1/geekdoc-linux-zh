If we project the claims for a resource, say number 1, from both processes, we can identify a shaded area which is a forbidden system state because of the mutual exclusion requirement. We can then do this for resource 2 as well. These areas combine to form a complex shaded polygon representing forbidden combinations of process states.

If the system state “bumps into” this polygon, it can only move along the edge by scheduling the non-blocked process to proceed. If the system state does this at one of the dark edges within the dotted region, it can only move towards the corner and eventual deadlock. Therefore the area formed by extending the polygon to the left and downward to form a convex corner (shown by the dotted line) identifies an unsafe region of computation. As long as the system doesn't enter this region, deadlock will not occur.

Deadlock avoidance examines each resource request to see if granting it would move the system state into the unsafe region. It requires all processes identify which resources they will be using at some future time.

# **Deadlock recovery**

The ugly truth is that many system kernels, including Unix and Linux, do not formally prevent, avoid, or detect deadlock. It is up to the designer of the individual processes to care for this problem.

Fortunately, this is not the large problem one would expect because there are few non-shareable resources and they are usually hidden, e.g., the printer behind the printer spooler.

Recovery, when applied, usually involves killing one or more processes and restoring their resources to the system pool.

In the case of Linux, memory (actually the combined physical memory and swap space) is the most significant non-shareable resource. \*Hold* and *wait* is avoided by a model which returns a failure signal instead of blocking the calling process.
