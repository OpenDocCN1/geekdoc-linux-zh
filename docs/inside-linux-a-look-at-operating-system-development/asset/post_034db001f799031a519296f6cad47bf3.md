## Linux's ISR implementation
In brief form, Linux takes the following steps to honor an IRQ:

- an interrupt request is posted
- when priorities permit, processor honors IRQ
- control passes through vector table to the ISR
- the ISR performs necessary tasks
- the return from the ISR may check for scheduling requests

There are actually two types of interrupt service: fast and normal. When a device is first initialized, the driver calls the **request_irq** kernel subroutine. This subroutine sets the actual interrupt vector, a look-up table used by the hardware, to point to either **do_IRQ** or **do_fast_IRQ**. **request_irq** also modifies the **irq_action** table to point to the device's second level interrupt service routine. When an interrupt occurs, **do_IRQ** or **do_fast_IRQ** will perform some housekeeping and then call the device's ISR.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_147_0.png)

**Fast interrupt** services are used when the driver interrupt service routine is small enough. The driver initialization declares it wishes to use fast interrupt service. `do_fast_IRQ` saves the minimum necessary context of the interrupt program. It then calls the ISR with the IRQ number as an argument. When the ISR returns, the saved context is restored and the interrupt service completes with an `iret` command.

The line printer driver follows this model. The main part of the driver, `lp_write_interrupt`, attempts to write characters to the printer, but when it is blocked, it will call `interruptible_sleep_on`, which passes control to other processes. It will be awakened when the interrupt service routine signals that the printer is again ready to accept data.

The interrupt service routine is quite simple. Besides some necessary validation, its sole purpose is to wake up `lp_write_interrupt` which is stuck in the kernel trying to write data to the printer.

```c
static void
lp_interrupt(int irq, struct pt_regs *regs)
{
    struct lp_struct *lp = &lp_table[0];
    while (irq != lp->irq) {
        if (++lp >= &lp_table[LP_NO])
            return;
    }
    wake_up(&lp->lp_wait_q);
}
```

**Normal interrupt** service saves the entire context of the interrupted program. It then calls the ISR with the IRQ number and a pointer to the saved registers as arguments. The ISR responds to the interrupt by tending to some peripheral or processor condition and then returns through a part of the kernel code which first dispatches *bottom half* code and then reschedules processes if appropriate.

The bottom half code is a logical extension of the ISR, but it is executed with interrupts enabled and therefore other critical interrupt requests can be serviced. Because the bottom half code is run with

The mouse driver offers one example of normal interrupt service. This is still a very simple device because the device and the user process are somewhat isolated from one another. The interrupt service routine accesses several device registers and updates a structure containing the current mouse position. Reading the mouse simply returns the contents of this structure, there is no need to co-ordinate with the interrupt service routine. Because the interrupt service routine takes a bit longer to execute, it uses the normal type of interrupt service.

The serial driver shows another aspect of the normal interrupt service, the “bottom half” code. Like the mouse driver, the serial driver takes an interrupt whenever new data are received. It places incoming characters in a dynamic buffer area called the “flip queue” and signals that other code should continue the processing. Signalling is done through the `queue_task` and `queue_task_irq_off` kernel subroutines. (The term “bottom half” comes from the idea that it is at the bottom half of the device driver.)

The utility of this scheme is that *any* kernel subroutine can be established as bottom half code. As drivers are initialized, they can establish work queues and they can create entries which can be placed on the queue. In the case of the serial driver, the code which runs as the bottom half is common to a large number of serial hardware device drivers. This higher level driver takes care of all terminal I/O processes the data which was put in the flip queue. That code will eventually call `wake_up`

to let a user process resume execution.

When all interrupts have been serviced the system scans the queues for requests to execute bottom half code.

The critical differences are: fast interrupts are faster, but because they don't preserve the entire context, they are slightly limited in coding style, and normal interrupts are slower, but they have few restrictions on coding style and they can cause processes to be rescheduled.

## 5.2.4 Scheduling
Throughout the operation of a multitasking system, decisions are being made on several levels regarding what processes should be executing. We can easily identify three levels, short term, medium term, and long term, and discuss each separately.

### Short Term
Processes shift between three major states: running, ready, and blocked. Blocked tasks lack access to resources such as memory, disk data, access to a peripheral, etc. They will continue when that resource becomes available. Ready tasks lack only a processor on which to execute. The system will select them to become the running process. Running tasks are actually executing — on most architectures only one per system is allowed. They will wait for some resource, they will relinquish control, or they are preempted by the system.

Processes change state as a result of actions by the running process or an ISR. In a co-operative multitasking system the running process continues until either:

- it blocks because it must wait for a resource or
- it voluntarily relinquishes control of the system.

These actions may be hidden from the application programmer deep within the run-time library; but to the system kernel it's all the same. The important characteristic of co-operative multitasking is that a context switch does not occur except at the direction of the running process.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_151_0.png)

Preemptive multitasking differs in that an ISR can cause a process not only to shift from blocked to ready, but from ready to running as well! This means that the running process can be interrupted at almost any moment and it will be set aside (as a ready process) for some indeterminate interval. (Implementations may show a transition directly from blocked to running, but a two-stage transition from blocked to ready to running can be regarded as equivalent.)

The kernel keeps track of blocked tasks by placing them on queues, one queue for each different condition for which a process could wait. This is typically done within a device driver, where a call to `select_wait`, `sleep_on`, or `interruptible_sleep_on` causes the current process to be placed on a queue which is built into that driver. At some later time, the driver will call `wake_up` to remove the process from that queue and move it to the ready process queue.

It's hard to catalog all the possible queues in the kernel, because there can be any number of them and there is no central registry of them. The address of each queue for which a process is waiting is shown in the WCHAN field of output of the `ps -l` command.
