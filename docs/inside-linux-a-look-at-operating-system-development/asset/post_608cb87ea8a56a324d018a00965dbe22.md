```c
void P(int *X) { while (request_semaphore_fails) relinquish; }
void V(int *X) { release_semaphore; }
```

This is really only a variant implementation of busy waiting, but it is a large improvement, because it lets other tasks run until the semaphore can be acquired.

The *relinquish* operation passes control to other tasks without any indication of when the blocked process should continue. Because of this shortcoming, it burdens the system kernel with continuing context switches and unneeded tests on the semaphore. If the blocked process is the highest priority process in the system, it will still block other tasks.

A more complete solution places the P and V operations inside the kernel. This permits the kernel to move a process from the running state to the block state, and to enter the process onto the appropriate queue. The system then can ignore that process until the V operation changes the process to ready and shifts it from a wait queue to the ready queue.

## Monitors

Semaphores are the assembly language of mutual exclusion. That is, they are primitive and difficult to use.

It is clear that the problem they address is in the access to shared data, not the concurrent execution of code.

Monitors are an invention which brings together the critical sections of code and the shared data which must be accessed in a mutually exclusive manner.

The first step in this solution is to hide the data from the user, presenting instead subroutines which are the only method of access to the data. This results in something which the programmer cannot directly manipulate, but can manipulate in a strictly controlled manner, hence they are called *abstract objects*. (Actually, there are two classes of subroutines, those which are visible to the user and those which are used internally. This point is important, as we’ll see in a moment.)

The programmer no longer needs to recall what fields must be initialized upon allocation, how to locate some specific object, and what procedures are to be used to deallocate an object. (The alert reader will recognize that these characteristics are found in C++.)

Since such an abstract object has close control over the allocation and initialization of data, there is an opportunity to create multiple semaphores, one per shared data object. The next step is to automatically insert P and V operations at the start and end of those subroutines which manipulate shared data.

This automatic insertion was done in Modula-2, but has been deprecated in Modula-3 because the granularity of such a method is too large. The current design leaves it to the designer of the abstract object to identify where semaphores should be placed.

## Deadlock

Whenever there are two or more processes, they can enter into a deadlock (or deadly embrace). When this happens, those processes are effectively stopped, never to resume unless extraordinary action is taken.

### Necessary conditions

Deadlock occurs when four conditions are met:

- *mutual exclusion*— there must be mutually exclusive access to resources,
- *no preemption*— processes cannot be forced to relinquish resources,
- *hold and wait*— processes holding one resource try to acquire another, and
- *circular wait*— there is a cycle of processes such that each is waiting for one resource and another process wants the resource it is holding.

(Although *circular wait* presupposes *hold and wait*, they are listed separately because it eases later analysis.) Figure 5.13 shows the smallest example of deadlock. The circular wait is made more obvious because of the convention which draws arrows leading from the resource (the small dot) to the process holding it, and from the process to the resource type it has requested.

### Prevention, Avoidance and Recovery

Given this model of deadlock, it’s possible to build a system which cannot deadlock, or will not deadlock, or can recover from deadlock.

#### Deadlock prevention

It is possible to prevent deadlock by ensuring at least one of the necessary conditions does not apply.

If all resources were shareable, mutual exclusion would not be required. Although some resources are fundamentally nonshareable, the system should ensure that as many resources as possible are presented as shareable. Hiding a line printer behind a printer spooler is an example of this approach.

It’s also possible to attack deadlock from the no preemption condition. Each process could be required to be able to safely relinquish its resources at the time it requests more. If a request results in blocking, the rest of the resources are made available to other processes. (It does, unfortunately, not prevent starvation—where a process is constantly denied one resource or another needed to proceed. It should be noted that starvation is a probabilistic effect—the process could at any instant get its needed resources.)

The hold and wait condition can be avoided by forcing all resource allocations to be done at one point in a process’ execution. Although it is wasteful, it does ensure that deadlock cannot occur. (This condition also leads to the possibility of starvation.)

The most practical method of preventing deadlock is to prevent the circular wait.

Processes can prevent the circular wait by always requesting resources in the same order, as if from a list. (For best performance, the ordering should be from those resources most likely needed early in a process' life to those resources most likely needed late in a process' life.)

#### Deadlock avoidance

All of the above methods are static in that they do not depend on what other processes are doing. Deadlock avoidance relies on a dynamic analysis of when it is safe to allocate a resource.

One can visualize deadlock in terms of processes moving into a corner out of which they cannot escape. This idea can be shown graphically in two dimensions for two processes. The surface represents the possible progress of the two processes. As the system proceeds, one process or the other makes some progress.

This progress is shown as the jagged line in Figure 5.14 which starts at the origin and should end up in the upper right corner. Because of the non-preemption requirement, this progress is always forward and thus the line moves either upward or to the right.

If we project the claims for a resource, say number 1, from both processes, we can identify a shaded area which is a forbidden system state because of the mutual exclusion requirement. We can then do this for resource 2 as well. These areas combine to form a complex shaded polygon representing forbidden combinations of process states.

If the system state “bumps into” this polygon, it can only move along the edge by scheduling the non-blocked process to proceed. If the system state does this at one of the dark edges within the dotted region, it can only move towards the corner and eventual deadlock. Therefore the area formed by extending the polygon to the left and downward to form a convex corner (shown by the dotted line) identifies an unsafe region of computation. As long as the system doesn't enter this region, deadlock will not occur.

Deadlock avoidance examines each resource request to see if granting it would move the system state into the unsafe region. It requires all processes identify which resources they will be using at some future time.

#### Deadlock recovery

The ugly truth is that many system kernels, including Unix and Linux, do not formally prevent, avoid, or detect deadlock. It is up to the designer of the individual processes to care for this problem.

Fortunately, this is not the large problem one would expect because there are few non-shareable resources and they are usually hidden, e.g., the printer behind the printer spooler.

Recovery, when applied, usually involves killing one or more processes and restoring their resources to the system pool.
