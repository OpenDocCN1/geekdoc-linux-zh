
It’s possible for the system to perform *compaction*, but such an operation must be carefully evaluated with respect to its cost and benefit. Compaction shifts one or more processes so that all the free space is contiguous. It is an expensive operation because processes must be stopped while they are shifted and all the addresses inside the process must be changed to refer to the new addresses.

## Memory Overlays

Another extension to non-mapped memory relies on partitioning a program into components such as:

- Common
- Initialization
- Main subroutine
- Shutdown

At the start, only the Common component is loaded. When it starts, the Initialization code is loaded into an *overlay* area; when the Initialization is finished, the Main subroutine overlays the Initialization code; when the Main subroutine is finished, the Shutdown code overlays the Main subroutine code. The benefit to overlays can be seen in Figure 4.14 where it is obvious that the whole program cannot fit into memory, but the critical parts can be loaded as they are needed.

> Some systems perform the partitioning through an automatic mechanism while others require explicit programmer declarations.
>
> Some systems make the overlay operation a transparent part of a subroutine call while others require explicit system calls to load an overlay.

### Mapped

If the programs do not co-operate, through malice or by mistake, they may corrupt one another by writing into the other's space. A number of methods have been developed to provide hardware-based protection.

Most of these rely on some mapping from the *logical address* generated by the program to the *physical address* used to access memory. When the *logical address* is not always mapped to some *physical address*, it is referred to as a *virtual address*.

### Base & Bounds

As mentioned earlier, the most simple program loading is to a known base address. A simple hardware mechanism, outlined in Figure 4.15, can be used to “trick” the program into running as if it were loaded into a different location. This relocation hardware relies on two internal registers: the “Base address” establishes the base address of a chunk of physical memory and the “Boundary value” holds the size of that chunk. As the processor generates a “Logical address” (for instruction fetch, data storage, stack, etc.), the hardware simultaneously adds that address to the base address and compares it with the boundary value. If the logical address is positive and doesn’t violate the size limit, the physical address is used to access memory. If the logical address is negative or too large, the memory access is regarded as an error.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_111_0.png)

Figure 4.15: Hardware memory mapping

With this hardware in place, the system and the program have different images of memory. With multiple programs running, the system must also change the base and bounds registers when it switches among the programs. As shown in Figure 4.16a, the system can see all of memory, but Figures 4.16b and 4.16c show the user programs only see the portion starting at the base address and the size given in the bounds register—and they see this memory as starting at location 0.

If you’ve noticed, the user program can no longer directly access the system kernel or run-time library. This is not a flaw because there exist special instructions which allow the execution to switch from code in a user program to code in the system kernel.

### Segmented Memory (Multiple Base & Bounds)

Some shortcomings to a single base and bound system are that all of the process memory must reside in a *contiguous* area of physical memory and that all of the process memory is *equally accessible*.

As the processor executes a program, it really references memory for several different uses. The processor can be extended to take advantage of this characterization of memory by using different base and bound register sets to access separate memory *segments*. To the user process, an arbitrary pointer to memory now has two components: the segment number (which yields a base and bound pair of registers) and the offset within a segment. Figure 4.17 shows how segment 0 can be used to address the run-time library, segment 1 can be used to address the program code, segment 2 can be used to address the heap, segment 3 can be used to address the stack, and (hypothetically) segment 4 could be used to address memory shared with another process, etc.

Since different memory segments serve different purposes, it’s quite reasonable to *restrict access* to a specific purpose. That is, a code segment can permit instructions to be fetched for execution but they cannot be read as data; a data segment can be restricted to read-only access.

This finer control over access permits processes to share code without the danger of the code becoming corrupted. Co-operating processes can share some data without yielding full access to all data to the other process.

This has been taken to an extreme on some systems where the two components (segment number and offset) are taken as a single object to be passed about and used as a pointer. In these systems, the number of segments can be quite large, perhaps as many as one for each array, etc.

### Paged Memory

Segmented memory provides good access control and, if pointers consisting of segment number and offset are used directly by the processor, a large address space becomes available to the user.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_113_0.png)

Figure 4.16: Mapping memory with base and bounds register

While segmented memory makes better use of physical memory than either non-mapped memory or single base and bounds remapping, it is still restrictive because the size of memory segments cannot be changed with ease.

The memory fragmentation problem shown in Figure 4.13 is not really solved by hardware support for segmented memory. The mapping hardware only relieves the system kernel from relocating (patching) the program and data when they are loaded into the system. Although memory is accessed indirectly through mapping hardware, each segment must reside in contiguous memory. This requirement for contiguous memory also makes it very difficult to extend a memory segment (such as one used for the stack or heap memory).

![](img/bd9544b8c1ad3b1347c84630c5d698e1_114_0.png)

Figure 4.17: Mapping memory with multiple segments

Both of these problems are addressed with a paged memory system. Paged memory can be thought of as a variation of segmented memory, where memory references consist of a page number and an offset instead of a segment number and offset. Because all pages are the same modest size, there is no need to validate the offset. There is, however, a need to validate the page number.

In Figure 4.18, the page number part of the logical address is compared with a limit and if it is within an acceptable range, it is used to index into a page table. The Nth page table entry contains a frame number, which, when combined with the offset part of the logical address, becomes the address in physical memory. Additional bits in the page table entry (not shown in this figure) can indicate the access permissions for that page.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_115_0.png)

Figure 4.18: Mapping memory through page table

The big advantage in a paged memory system is that the pages need not map to contiguous physical memory. When a new process is loaded into memory, its size in pages must be satisfied by that number of free frames, but the frames need not be contiguous.
