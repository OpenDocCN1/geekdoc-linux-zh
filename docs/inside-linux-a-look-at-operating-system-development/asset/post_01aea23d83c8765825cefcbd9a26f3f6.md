
### 1.4.4 Linux Doesn't Have User Threads

A thread is a process-like entity which shares much of its context with its siblings. Switching among sibling threads involves less overhead than switching between processes. This lower overhead means that threads can more easily exploit the parallelism *within* a program.

The utility of threads and the pending approval of a POSIX standard for threads have made them more visible to the user community.

Until recently, implementations of threads for Linux operated entirely as user code. There have been several different implementations, none of which have been made part of standard distributions.

The kernel has been evolving towards support for user threads.

Threads are explored more completely in Section 5.2.3.

### 1.4.5 Linux Doesn't Have Streams

As data flow between user applications and the outside world, several transformations are applied, e.g., tabs are expanded to the appropriate number of spaces, parity is added to each character, packets of data have checksums applied, etc. In the past, these transformations have been built into the drivers. This made it difficult to install different transformations on a per-line or per-application basis.

*Streams*, as introduced to Unix by designers at AT&T Bell Laboratories, give programs greater control over these transformations[42].

Although the user community has shown great reluctance to shift Linux to this method, there is a (slowly progressing) project[28] to develop streams for Linux. Their hope is to make the use of streams a user option.

### 1.4.6 Linux Doesn't Have Symmetrical Multi-processing (SMP)

Multiprocessing involves the use of multiple processors in a single system. Sometimes the extra processors have a dedicated function, such as that of an intelligent peripheral controller. Another configuration has multiple processors connected so that each has the same relation to the system as the others, hence “symmetrical”. There is no master-slave relationship among the processors.

As mentioned in Section 1.3.1, had Linux been written as a micro-kernel, it would have been fairly straightforward to extend to symmetrical multiprocessor systems.

Instead, a small project group has extended the existing monolithic kernel by adding carefully placed semaphores (see Section 5.2.4) to protect shared data within the kernel. In addition, extra steps were required to identify and initialize the processors at the time the system is started. From a practical standpoint, this may lead eventually to a higher performance system than could be achieved via a micro-kernel.

So, although no fully supported release exists, support for SMP is now a configuration option in the development kernel releases. Until such time as this project is complete, information is available on the web.[29]

### 1.4.7 Linux Has No Support For Real-Time Scheduling

Section 4.1.3 notes that “real-time” is a somewhat slippery term, but most everyone agrees Linux doesn't have it.

The resolution of the clock is quite good, but the delivery of a signal from **setimer** has limited resolution. More importantly, any process can suffer severe arbitrary delays due to virtual memory paging and the scheduler behavior is not precisely defined. As a consequence, processes cannot guarantee to meet any deadline.

Recent changes proposed for the kernel will correct these handicaps with little expense to general system performance.

It is also possible that, in some cases, real-time performance can be faked by putting more into specialized device drivers.

### 1.4.8 Linux Is Becoming Bloated

The original Unix kernel was under strong size limitations. The PDP-11 hardware offered only a 64 Kbyte virtual address space, of which 8 Kbytes referred to device registers. As a consequence, the kernel could not expand without limits to offer new features. When Unix was ported to the DEC VAX and other architectures, this constraint was removed and Unix quickly grew much larger. Fortunately, the fundamentally simple design was not lost.

The Linux kernel has undergone a similar metamorphosis. Because it was the creation of one individual, it was based on a simple, consistent design. It has been rapidly expanding as new features are added. These features have caused the kernel to suffer a 2:1 expansion in the past three years. The kernel modules mentioned in Section 1.3.1 offer a partial solution to this problem in that only those features which are desired are loaded into memory.

In his classic analysis of large software development projects, *The Mythical Man Month*, Fred Brooks noted what he called the *second system effect*. This occurs when the designers pile features into their second system—features which they wisely left out of the first system because of concerns about size or their ability to implement them. Only experience with building a second system teaches the proper balance between what is needed and what is wanted or can be provided.

Brooks’ book has been reprinted with additional comments on the past twenty years, in which he names a related phenomenon, *featuritis*[7]. He notes that unless the system designers have a firm sense of the user community, new features will be added without limit.

Linux is suffering from *featuritis*, but because of its open and dynamic nature, truly bad features are purged. Furthermore, users can put experimental features into the system without relying on a “feature czar” deciding what is important. If an experimental feature proves useful, it will migrate to the kernel as a loadable module or as a compile-time selection for the kernel.

## Chapter 2
### Prologue to Linux

Linux did not appear out of thin air. It is the outcome of years of computer system development. If we look back, we can identify a number of seminal ideas that have been incorporated into Linux from other systems.

### 2.1 Multics

In 1964-1965, General Electric, Bell Telephone Laboratories, and Project MAC at MIT entered into a partnership to build an operating system for a large computer. This system was to be known as Multics—an acronym for Multiplexed Information and Computing Service.

Official support for this operating system has now been withdrawn by all of the original parties, but there still exist a few operational Multics sites. There is also a group of Multics fans and users which supports a net news group[1].

A number of books and papers have been written about Multics, most significantly *Organic*[k37]. Some of these explore the demise of Multics. None suggests Multics had fundamental design problems and most extol a number of original ideas that are slowly making their way into other operating systems.

Although Multics has not inherited the full utility of security rings as used by Multics, they are mentioned here because they, along with an elaborate procedure-calling mechanism, were used to provide both great power and great security to the system.

This led naturally to a layered model of an operating system, which in turn led to the natural conclusion that the interactive user’s access to the system kernel did not have to be integral to the system kernel.

### 2.1.2 Shell

Up to this time, installing a new command line interpreter was a difficult venture. With Multics, a system administrator, or even the user, could specify how terminal interaction was to be interpreted because command interpretation was performed by a separate program—called the shell.

### 2.1.3 File System

Files on the Multics system were accessed via high-level operations that concealed the block structure of the disk. The user simply invoked an operation (read/write/etc.) with a file handle, buffer, and byte count as arguments.

Files were organized by a tree-like structure of directories, subdirectories and ultimately, files.

File data were uninterpreted by the system kernel. Although the applications could apply any interpretation desired (records, numbers, etc.), the system kernel only manipulated streams of bytes.

As a natural side effect, text files were treated as a stream of characters with a single end-of-line character separating lines. As a result, user programs could rely on easy access to data.
