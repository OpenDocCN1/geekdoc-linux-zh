The SYMBOLS table contains a list of names, each with its type, value, and other information, describing entry points, global variables, etc. Entries referring to specific locations in the TEXT, DATA and BSS areas are called definitions. Other entries, called external references, refer to locations which are not defined within, but must be elsewhere defined. The initial purpose of the symbol table has been extended, through the use of new types, to support debugging information. These references and definitions are indicated by the dashed lines in Figure 7.2.

Addresses in both the TEXT and DATA areas are relative to the base of those areas. Relocation information, which is held in the final two parts of the object file, describes all the addresses in a way which allows a linker to modify the text and data when the areas are shifted to a non-zero base address. This relationship is shown by the dotted lines in Figure 7.2. An executable a.out file can be stripped of all but the HEADER, TEXT, and DATA areas. This makes the file smaller, but it prevents debugging.

The object files have the same format as the executable file, except some of the symbols describe unresolved external references. The linker is used to combine two or more object files into one executable file as shown in Figure 7.3. The text and data areas are concatenated and the relocation information used to adjust addresses. Symbol tables are merged, as are relocation tables, and a consolidated header is formed; external references are resolved as matching definitions are found.

## Dynamic Linking

Until recently (the last ten years for many Unix systems and the last two years for Linux), the linker would build an executable image which had resolved all external references. That has changed, and for over a year Linux systems have had dynamic linking.

Dynamic linking and shared libraries, while distinct concepts, are invariably associated in practice.

A typical program is full of rarely used code because a careful programmer writes to cover all cases, but most cases never (or rarely) occur. It's really unfortunate to have to bind a subroutine's code or some global data storage to the user's program just because that rarely used code refers to the external subroutine or global variable. The resulting executable image uses more disk storage, takes longer to load into memory, uses valuable memory, and may be out-of-date.

Dynamic linking (also called dynamic loading) avoids three of these four problems and helps deal with the fourth problem.

The trick to dynamic linking is to substitute a library full of *stubs* for the full library. The linker will *bind* these stubs to the user program so that a call to a function, say *printf*, goes to the stub instead of the function. The code in the stub loads the full library code and, after patching a jump-table to avoid further loading, transfers control to the full library code.

The stub code is smaller than the full library code, so the executable file is smaller and it will take less time to load into memory.

Because the full library is referenced only when the program finally executes, changes to the full library effect all programs, not just programs built after the library changed.

Finally, because the library calls are made indirectly through the stubs, the library code can reside in memory accessible to many processes. (It is because the library code may already be present in memory that the terms “linking” and “loading” can apply to the same program at different occasions.)

Library code can be shared without the dynamic linking described above. In this case, the user’s program is linked to well known addresses. If the library code isn’t already in memory when the user program is loaded, the library is loaded as well.

## COFF

COFF was a short-lived attempt to generalize object file formats. It has been supplanted by ELF on Linux, but it is still used by SCO.

## ELF

ELF, which stands for Executable and Linking Format, is a portable object file format which is supported by many different system kernels running on the Intel 386, 486, Pentium and compatible architectures. This format differs from the a.out format in that it supports an arbitrary number of parts and these parts are clearly defined in the format instead of being “understood” to have some specific form. Most importantly, the ELF format has better support for dynamic and shared libraries.

We’ve seen in “Dynamic Linking” on page 200 how the a.out format can be extended and made to support dynamic linking. The many steps needed to build the stubs were omitted, but rest assured, the process is quite untidy.

The ELF format, by contrast, requires only $N+1$ steps to build a shared library from $N$ object files, and one additional option to bind that library to the executable.

$N$ distinct steps are used to build each object file out of the corresponding source file. The only unusual feature is that the option `-fPIC` is given to the compiler to ensure the code in the object file is position independent.¹ The $N+1st$ step collects all the objects into the library. The compiler is given an option `-shared` and the output file name has a `.so` extension.

When the executable is built, the only necessary extra argument is the name of the new library.

At this point, it should be admitted that the work done by the system isn’t really that much less than for the a.out format, but the ELF format allows all the steps to be more easily integrated into the compiler.

**For example**: Suppose we wanted to encrypt all our alphanumeric output using a dynamically linked library routine. Such a routine would be called to process each character or string to be printed.

Three entry points `set_key`, `encrypt` and `decrypt`—are defined in `cry.c` as outlined below:

```
void set_key(char * key) { ... }
char * decrypt(char *inout) { ... }
char * encrypt(char *inout) { ... }
```

> ¹ Position independent code is designed to contain only relative addresses. That is, instead of using an absolute address to refer to code or data, it uses an address relative to the start of the code or a base register. As a result, the code can be mapped to any virtual address without the need to apply relocation.

The object file cry.o is compiled with the command

```
gcc -fPIC -c cry.c
```

and then built into a sharable library with the command

```
gcc -shared -o libcry.so cry.o
```

The user program, in this case yet another "hello world" example, is compiled from the source.²

```
#include <stdio.h>
#include "cry.h"
#define BUFISIZE

int main (int argc, char **argv)
{
  char ostr[BUFISIZE];

  strncpy(ostr, "hello world\n", BUFISIZE);
  set_key(argv[1]);
  (void) printf(encrypt(ostr));

  return 0;
}
```

and then an executable is built with the command

```
gcc -o hw.dynamic hw.o /file_pathname/libcrys.so
```

(The library location must be given as an absolute pathname or it must reside in some place well-known to the loader.)

It gets interesting when the cryptographic routines are modified and recompiled. Although the linker (which is sort of built into the compiler) referenced the library when it built the executable, it does not have to do so again when the library is rebuilt. This short-cut is because the library was first referenced mostly to determine that the three routines were defined in the library. Once that determination was made, there is no more need for the executable to track the exact contents of the changing library. This is because *every time* `hw.dynarmic` is executed the most current version of `libcry.so` is used to provide the library code.

There is a trap for the unwary in this process: the program will pass invalid data if the subroutines change their calling arguments. For example, if a math function was changed from “the $N$th power of $M$” to “$N$ to the $M$th power”, the program would get the wrong results unless it changed the order in which the arguments are passed.

The routine `readelf`, distributed in recent Linux CD-ROMs, can be used to explore more about what data are held in an ELF file.

## Kernel implications

Why are these formats important to the kernel? First, the kernel must recognize the different executable file formats. Second, the run-time code must support these conventions.

## Executable file types

From the very first days of Unix, the first word an executable file contained was a magic word which the kernel used to determine how the executable was to be handled. By the seventh edition, this was enhanced to support direct execution of shell scripts. In the current Linux systems, if the word contains the value `0xc231 0x2f`, the hex values for the characters “#!”, the file is identified as a script file. Additional text on the first line identify what program is to interpret the rest of the file.

The a.out format has several variants. The oldest magic word, `0407`, comes from the PDP-11 implementation of Unix. This specific value, when decoded as an instruction, means “jump over the rest of the header to the eighth word of the code”. Thus a type `0407` code file was directly executable at address zero.

Other magic word values have been added for other forms of memory management.
