
ELF files begin with the magic word 0x7f 0x45 and continue spelling out “ELF” followed by version numbers and such.

The Linux kernel has been designed for easy expansion of support for various object file formats. If it fails to find the #! magic word, it enters a loop which calls a test routine for each supported object file format. If any test routine succeeds, the appropriate code is used to load the executable.

## Example

At the beginning of Chapter 5 we glossed over how the “hello world” program shown in Figure 5.1 would be turned into an executable image. In this section we will follow the steps in a bit more detail.

To begin with, although command `gcc hello1.c` produces a file titled `a.out`, the user should be aware that the name is only a convention, not an indication of the type of the file. Depending on compiler options or defaults, this file can just as easily be in ELF or `a.out` format.

The `gcc` command hides several subordiant commands which can be invoked by the main command: the preprocessor, `cpp`, the compiler proper, `cc1`, the assembler, `as`, and the linker, `ld`.

The preprocessor has no real knowledge of C. It is a simple macro preprocessor which acts on simple directives such as `#include`, `#define`, and `#ifdef`. Its output stream has substituted all the macro definitions and symbolic constants and has stripped all the comments out of the way for the compiler.

The compiler reads the clean C code and produces assembler code. This process can involve several distinct phases of optimization to produce faster and smaller code.

The assembler reads the assembler code and produces an object file which has a multitude of unresolved references to externally defined symbols.

The linker gathers code from one or more libraries to satisfy the unresolved references.

The resulting `a.out` files are dramatically different. The size difference of 15388 to 3916 is because the larger `a.out` format file has all the library code bound to it by default and the ELF format file relies on dynamically linked library code.

A key point to all this is that there is no real magic to a compiler — although I will admit a good compiler involves artistry and science, a modest compiler can be understood by many. And a modest compiler can be written and installed by anyone.

### 7.1.3 Interpreters

So far, we’ve looked at what system support is required for languages which are assembled or compiled and built into a binary executable form. We’ll now look at two features which provide system support for interpreters: direct execution and recursion.

It’s worthwhile to first review the different forms of interpretation.

One form is derived from an interactive system which is extended to read from files as well as terminals. The language looks like technical prose with words which look like those of a natural language, e.g., “if”, “then”, “else”, “while”, “for”, etc. The advantage to such a language is that

- it can be read on a display or print-out and comprehended by the programmer
- it can be prepared with a text editor
- some interpreters allow interactive use which facilitates testing

Another form relies on the representation of commands and data in a binary form that is unrelated to the display of natural language.

In both cases, the interpreter can be nearly identical — only the front end which parses the source needs to be different.

FORTH is a good example of a language which has both kinds of interpreters. The binary form of FORTH is quite compact, which is appropriate when it is used in an embedded system. The more natural language form of the language is used when these programs are being developed.

All Unix-like systems have at least the shell, a command interpreter of the first kind, and almost all distributions have other utilities, such as editors, which read commands from a terminal. Since Unix-like systems support redirection, it can be claimed that they support command files.

Actually, most such utilities recognize an argument naming a file which contains commands.

This sets the stage for a kernel extension to support direct execution of scripts.

## Direct Execution of Scripts

The POSIX 1003.1-1988 standard says:

> Some systems can *execv* scripts. This functionality is outside the scope of this standard, since it requires standardization of the command interpreter language of the script and/or where to find a command interpreter. These fall in the domain of the P1003.2 standard[3].

That document notes that “The internal format of an executable file is unspecified”, but then goes on to describe how the shell shall

> ...execute the utility ...equivalent to calling the POSIX.1 *execv*() function.... If the *execv*() function fails..., the shell shall execute a command equivalent to having a shell invoked with the command name as its first operand, along with any remaining arguments passed along[4].

In this way, even if the kernel doesn’t recognize shell scripts, the shell is expected to extend the system’s functionality. But this puts the burden on the shell to figure out how to handle an executable shell script. Since none of the POSIX standards define precisely the internal format of an executable file, there is nothing to prevent the kernel from directly executing a class of shell scripts.

Do you recall how Linux looks for a magic word at the beginning of an executable file? If the Linux kernel discovers the value 0x23 0x21, the hex values for the characters “#!”, it creates an alternate command line and processes it for execution. This alternate command line is built from the original command line and the first line of the script as follows: split the command line into parts, the script name and each of the script arguments; split the first line of the script into two parts, the interpreter name and the interpreter arguments; combine them in the order—interpreter name, interpreter arguments (as one argument), the script name, and the script arguments.

For example, if the command line

```
% alpha beta gamma
```

calls a script named **alpha** with arguments **beta** and **gamma** and that script starts with the line

```
#!delta epsilon zeta
```

the interpreter will be called as if the command line contained

```
% delta `epsilon zeta` `alpha` `beta` `gamma
```

Note that all of the interpreter arguments are combined into a single argument to the interpreter. The interpreter will then open the script file and process the commands contained therein.

## PERL, SED, AWK, etc.

Although the shells are the most obvious candidates for interpreters of executable scripts, others exist. **perl** is another good choice because it automatically processes files in its argument list. Because the system creates and then processes an alternate command line which contains the script file's name in the argument list, **perl** automatically processes the script file. For example, when you execute a **perl** script named **my_perl_script** with **#!/bin/perl** on the first line, **perl** will be run as if it had been invoked with the command **perl my_perl_script**.

This automatic script file processing is a little more tricky for programs which were not designed as interpreters. The **sed** editor, for instance, expects file names in its argument list to contain text to be edited. There is an option -f which says the next argument is a command file. This behavior allows one to build an editor script in the following form:

```
#!/usr/bin/sed -f
s/good/bad/g
/mediocre/d
```

Since *awk* uses the *-f* option in the same way as *sed*, we can write an *awk* script in the form:

```
#!/usr/bin/awk -f
{print $2; sum++}
END {print sum}
```

### Recursion

Another note should be made about shells as interpreters of scripts: each script is processed independently and, therefore, it is possible to have nested and recursive script invocation.

No specific extension is necessary to support this feature, it is a natural side-effect of the ease with which processes can be created and controlled.

Other systems do not invoke a new process and therefore scripts cannot nest or be called recursively.

## 7.2 Editors

Editors have little to do with system kernels, except perhaps *emacs* which aspires to *be* an operating system. However, they do place some interesting demands on the system.

This change has placed a burden on the system kernel to provide different modes of communication with these peripherals.
