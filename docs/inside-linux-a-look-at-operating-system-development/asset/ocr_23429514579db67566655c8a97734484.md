When processes take pages from other processes, load balancing is a somewhat autonomic result (which is difficult to control), but when each process pages against itself, load balancing must be done as a distinct operation which explicitly changes the resident set size of each process.

As mentioned earlier, Linux processes pages against each other. Therefore, the load control management is somewhat *ad hoc* and ill defined. Section 5.2.4 discusses the consequences of this approach.

# **Storage management**

Physical memory is not the only resource which the virtual memory system must manage; it must also keep track of the pages stored on disk.

Conservatively designed systems will allocate space on disk to match the growth in process’ virtual space, ensuring that there will always be room to save pages. Although this appears to be a good idea, it forces an unnecessary duplication of data—every resident page of memory has a corresponding disk block. This duplication is not only wasteful of storage, it limits system performance.

The **fork** call creates a child process which is an exact image of the parent process. While this suggests a great deal of copying must be done, Linux performs the duplication by sharing pages of memory between the child and the parent. This sharing of pages means the kernel has only to copy the page table from the parent to the child—the data in the pages need not be copied. Then, because the parent and the child must really have independent memory images, the parent’s and child’s page table entries are marked *copy-on-write*. The copy-on-write mark says that if either the parent or the child write to a page, that page is first copied to a new frame of memory. In this way the parent and child continue to share all those pages which contain the same contents, but they get distinct pages when the pages differ in contents.

You can see that process creation does not allocate any disk space and allocates only a few pages to hold the per process data.
