
Although the computer hardware was fixed by design, the system could be extended by the addition of support software. If the computer couldn't multiply, the programmer could call a subroutine to perform the multiplication. If the card punch required tricky timing, the programmer could call a subroutine that used the correct delays.

This collection of specialized support subroutines has become what we now call the run-time library and the system kernel. Some of the subroutines may be bound to the application program as part of the compilation, others when the program is loaded into memory, still others as each subroutine is called, or at the point of each subroutine call.

## 4.1 Scheduling

A run-time library, along with a simple program loader, was the extent of early system kernels. The hardware was designed to read one card from the hopper into a fixed memory location and transfer control to that location. The first few cards held the program loader and the run-time library. The user program followed. When the user program was done, the system would halt and the next user program would be loaded.

A modest design change placed the program loader in charge of loading one job after another from an input stream (card reader or tape drive), executing it and going to the next job. As long as the card hopper or the tape drive was full, the system would be busy doing useful work.

This change was the start of the evolution of the operating system. Before this time, the support code in the run-time library was there to aid one program. After this time, the support code in the scheduler was there to aid all programs.

Unfortunately, input and output operations (I/O) are typically much slower than the processor. Thus, while the system is waiting for I/O to complete, the computing logic is idle—and while computation is being performed, the I/O mechanism is idle. Figure 4.1a shows how jobs alternate between computing and performing I/O. When the processor starts I/O, it uses a polling loop to determine when the I/O is done. A polling loop is a cycle of “are you done?”—“no”—“are you done?”—“no”—“are you done?”—“no” that continues until the peripheral finally responds “yes”, at which time more I/O can be started or the computation can proceed. Really tricky code could use a cycle of “are you done?”—“no”—do useful work—“are you done?”—“no”—do useful work—“are you done?”—“no”—do useful work, but it is still difficult to get the most out of the system.

### 4.1.1 Multitasking

Since the user can't always arrange to have alternate work to do while I/O is in progress, later versions of batch operating systems were extended to serve concurrent batch jobs. Since one design goal for a system kernel is to maximize processor use, the scheduler switches between jobs whenever the active job must wait for I/O to complete. Figure 4.1c shows how the execution of two jobs can be overlapped so that their total running time is reduced. In this simple example, you can see that both computing and I/O are nearly continuous. The terms *co-routine* and *co-operative multitasking* are applied to a scheme where each job runs until it has to wait for I/O to complete (or it reckons it has had its fair share) and then control is passed to another job.

#### Co-operative Multitasking

Traditionally, programs were executed as subroutines under the control of a master program: one after another or concurrently, but always independently of one another. Conway introduced a critical notion that two programs can work in co-operative alternation. “... co-routines are subroutines all at the same level, each acting as if it were the master program when in fact there is no master program”[10]1.

The initial parallelism is often established by a subroutine call (shown as the first dark arrow in Figure 4.2) from the parent routine (P1) to the child routine (P2). Thereafter, instead of performing some form of *return* statement, the programs perform a *resume* statement (shown as the lighter arrows in the figure) whenever they wish to pass control back to the other routine. This statement preserves the state of the program so that it can later continue where it left off. The trampoline code in Figure 5.5 gives some idea of what the *resume* statement does. Control bounces from one program to another each time a *resume* statement is executed. At the very end, the child process issues a *return* statement (shown as the second dark arrow in the figure) to return to the parent without preserving its own state.

Implicit in most uses of the term co-routine is the idea these programs would work on some common problem by exchanging data. This combined concept is now well known by the name *producer–consumer*, whereby one program produces data to be placed in a buffer and another program consumes the data from the buffer.

#### Preemptive Multitasking

A batch of jobs, where it doesn’t matter if one job or another is delayed for a bit, are perfect candidates for co-operative multitasking. But if the jobs are expected to offer any interactive response, the system will have to switch from one job to the next, even when the jobs don’t request the switch. This *preemptive multitasking* allows each user’s program to run either until it waits for some I/O to complete or until a “time quantum” expires. Selecting the proper quantum is not easy. With too large a quantum, the interactive performance appears erratic; with too small a quantum, too much overhead is generated.

Because it is possible to overload a processor, such that system overhead consumes all its power, a high level scheduler decision may limit the number of users or user programs on the system.

These two issues of performance tuning—short term and long term scheduling—will be discussed later in Section 5.2.4.

### 4.1.2 Priority Scheduling

A number of scheduling algorithms have been designed, most of which have some sense of process priority. This allows the system or user to designate a process as “really important” or “non-critical”. Section 5.2.4 explores this topic in more detail.

### 4.1.3 Real-Time Scheduling

Any formal definition of real-time scheduling will make note of a “strict requirement to meet deadlines”, but that’s really insufficient. Consider a payroll accounting system—everyone agrees it’s not real-time, but you better get those checks out on time! There appears to be an implicit, or at least rarely uttered, element to the definition: “deadlines are often less than a second in the future”.

Real-time scheduling comes in three flavors. *Hard real-time* systems, such as used in airplane flight control software, are designed so that no processes can inappropriately block another. Some of this can be done by strict (and fast) priority based scheduling, but it also often relies on strict bounds on process execution times.

Some systems go so far as to avoid the use of interrupts because unexpected delays of millisecond duration can occur. Instead, the system runs in a polling loop, calling each process as a co-routine (see Section 4.1.1) and each process must return within some fixed time. Some of these processes perform computations and others tend to peripheral I/O.

*Soft real-time* systems can tolerate modest delays. An example of such a system would be a “high-tech home” with window shades which respond to time-of-day, sunlight, and room temperature and a sprinkler system which relies on moisture sensors, clocks, and motion detectors (to avoid ruining the lawn party). If some operation is delayed by a second, perhaps as much as a minute, no harm is done.

Since a soft real-time system can work with context switching overhead, it’s possible to have lower priority processes doing non-real-time work. This means that these systems often have disk storage, network connections, interactive user command loaded processing, and (gasp) even *virtual* memory.
