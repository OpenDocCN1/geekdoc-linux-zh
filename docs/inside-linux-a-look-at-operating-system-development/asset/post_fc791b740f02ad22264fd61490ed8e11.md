
## 5.4.2 Thrashing and Level Of Multiprogramming

At the time of this writing, Linux newsgroups are discussing at length the problem with run-away processes which steal resources from other processes. (Linux, like most other Unix implementations, uses a form of global replacement.)

![](img/bd9544b8c1ad3b1347c84630c5d698e1_195_0.png)

Figure 5.30: Process memory requirements

If we look at the behavior of a single process in a virtual memory system shown in Figure 5.30, we see there are limits associated with a minimum number of page faults and a minimum number of allocated frames. If a process doesn't get some minimum number of frames, it may *never* finish. This is because any given instruction can address several different pages. If these pages are not all in memory, that instruction will never complete. (And if only $N$ frames are available, the process may crawl along because it may have to load a different set of $N$ pages for each instruction.) We also see that there is a point, $M_i$, where making more frames available to process i will not reduce the number of page faults it suffers.

Many systems exhibit a load-performance curve, shown as a dotted line in Figure 5.31, wherein a greater presented demand results in more work getting done—up to some limiting value. Other systems, virtual memory being one of them, follow the same curve for a while, then abruptly taper off. This load-performance curve is shown as a solid line in Figure 5.31. The base cause for this abrupt drop is that the system crosses a demand threshold beyond which it is spending more time servicing the requests to load a different page than it is executing the user processes. When the system is in this latter mode of operation, it is said to be *thrashing*.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_196_0.png)

Figure 5.31: Thrashing

These two curves are clearly related. If the present demand for pages, $\Sigma M_{i}$, is less than the available memory, the performance curve will follow the dotted line. But when that demand exceeds what the system can provide, the various processes start to page. The difference between $M_{1}$ and $N$ determines how quickly the performance drops off. When all processes are allocated $N$ or fewer pages, the system is effectively stopped.

The goal for system management is therefore to allocate $M_{i}$ frames to each process and to keep $\sum M_{i}$ less than the size of available memory.

### Working Set

Denning calls the collection of frames being accessed by a process, $W(t, \Delta)$, its *working set*[12]. The working set is a function of $t$, the current process' execution time. The working set is also a function of how large an interval, $\Delta$, is considered.

This leads to a better statement of system management goals—we have to ensure every process has $|W_{i}(t, \Delta)|$ frames allocated to it and we have to keep $\sum|W_{i}(t, \Delta)|$ less than the available memory to avoid thrashing.

Over time, the size of the working set will establish different plateau values. The dashed and dotted lines in Figure 5.32 represent the contribution to the working set size made by different parts of a program. During the transition from one part of the program to another, these contributions sum to produce the solid line which has peaks between the plateaus.

We would like to use the working set to develop a measure of how much memory is needed by all the processes. But once again, implementation of such a theoretical concept requires approximation, compromise and judgment.

One way to estimate the working set size is to monitor the page fault frequency (PFF) of a process. For a fixed frame allocation, changes in the PFF are closely correlated with changes in the working set size. If the PFF is stable, the process is at a plateau. If the PFF changes, the process is shifting to a different plateau or has established a different plateau. The PFF algorithm does not satisfy the inclusion property, but, except for a few anomalies, it behaves within about $10 \%$ of a proper working set algorithm.

The system can treat the currently allocated memory (resident set size) as an approximation to the working set size when the page fault frequency is not quite zero.

### Load Control

Even with an effective way to determine or estimate the working set size of all processes, there remains the problem of keeping \(\Sigma|W_i(t, \Delta)|\) less than the memory size.

This is deemed the "load control" problem and it is one of the most difficult issues in tuning system kernel performance. The difficulty lies in the trade-offs one must make in denying frames to one or more processes. (Load control is also known as balance set management[31].)

We have seen how frame allocation algorithms are used to force pages out of memory on a one-by-one basis. Load control is used to swap entire processes out of memory.

Swapping in a virtual memory system is motivated somewhat differently than the swapping described in Section 4.4.3. In that case, the system was forced to swap a process' state to special storage because all the processes didn't fit in memory. In this case, all the processes fit in virtual memory, but their presence causes thrashing.

In a virtual memory system, the decision to swap need not be a binary (on-off) one, the system can treat a swapped-out process as the limiting case of a reduced resident set size. The real distinction is that a process which is swapped out no longer generates any demands for pages.

When processes take pages from other processes, load balancing is a somewhat autonomic result (which is difficult to control), but when each process pages against itself, load balancing must be done as a distinct operation which explicitly changes the resident set size of each process.

As mentioned earlier, Linux processes pages against each other. Therefore, the load control management is somewhat *ad hoc* and ill defined. Section 5.2.4 discusses the consequences of this approach.

### Storage Management

Physical memory is not the only resource which the virtual memory system must manage; it must also keep track of the pages stored on disk.

Conservatively designed systems will allocate space on disk to match the growth in process’ virtual space, ensuring that there will always be room to save pages. Although this appears to be a good idea, it forces an unnecessary duplication of data—every resident page of memory has a corresponding disk block. This duplication is not only wasteful of storage, it limits system performance.

The **fork** call creates a child process which is an exact image of the parent process. While this suggests a great deal of copying must be done, Linux performs the duplication by sharing pages of memory between the child and the parent. This sharing of pages means the kernel has only to copy the page table from the parent to the child—the data in the pages need not be copied. Then, because the parent and the child must really have independent memory images, the parent’s and child’s page table entries are marked *copy-on-write*. The copy-on-write mark says that if either the parent or the child write to a page, that page is first copied to a new frame of memory. In this way the parent and child continue to share all those pages which contain the same contents, but they get distinct pages when the pages differ in contents.

You can see that process creation does not allocate any disk space and allocates only a few pages to hold the per process data.

So when is space on the disk used? It is used whenever the system needs to load or create a page of memory and no frame is available to hold it. Once the kernel selects a victim page, that page is written to disk and the frame is available for a new page.

This approach yields high performance at a cost: because there is no assurance of a place on disk for each page of memory, it is possible to run out of storage for all the virtual memory. In matters such as this, Linux and most other Unix systems are a bit sloppy. Most users are willing, albeit unknowingly, to sacrifice some reliability for much greater performance. In this instance, it’s possible that the parent or child could fail at some later time when it attempts to write to a page and neither a physical frame nor disk swap space are available to save a copy. That program would fail and yield its allocation of physical memory and swap space back to the system.

## 5.4.3 Disk Caching

The other major use of memory is as a buffer for disk I/O.

All disk I/O pass through a uniform buffer mechanism which attempts to hold copies of disk data as long as possible—even after it has been written to disk. This provides the user with quick access to the data if a read is issued for disk data which is already held in the buffer.

The system balances the use of memory for buffer with the need for frames to hold virtual memory pages. Of course, virtual memory needs have precedence, but the kernel will attempt to use all the rest of the memory for buffering.

## 5.5 Security

The basic system security relies on several elements: processes are owned by a user and can belong to several different groups. The file system limits access to files, directories and devices based on a processes ownership and group membership. Each process has independent virtual address space (which can contain memory segments which are explicitly shared with other processes), but access to physical memory is generally forbidden.
