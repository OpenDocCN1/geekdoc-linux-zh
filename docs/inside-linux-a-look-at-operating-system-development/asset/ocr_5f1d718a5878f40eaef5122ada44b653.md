fails to do so. The loop can be trivially extended to relinquish control if it would block.

```c
void P(int *X) { while (request_semaphore_fails) relinquish; }
void V(int *X) { release_semaphore; }
```
```

This is really only a variant implementation of busy waiting, but it is a large improvement, because it lets other tasks run until the semaphore can be acquired.

The *relinquish* operation passes control to other tasks without any indication of when the blocked process should continue. Because of this shortcoming, it burdens the system kernel with continuing context switches and unneeded tests on the semaphore. If the blocked process is the highest priority process in the system, it will still block other tasks.

A more complete solution places the P and V operations inside the kernel. This permits the kernel to move a process from the running state to the block state, and to enter the process onto the appropriate queue. The system then can ignore that process until the V operation changes the process to ready and shifts it from a wait queue to the ready queue.

# Monitors

Semaphores are the assembly language of mutual exclusion. That is, they are primitive and difficult to use.

It is clear that the problem they address is in the access to shared data, not the concurrent execution of code.

Monitors are an invention which brings together the critical sections of code and the shared data which must be accessed in a mutually exclusive manner.

The first step in this solution is to hide the data from the user, presenting instead subroutines which are the only method of access to the data. This results in something which the programmer cannot directly manipulate, but can manipulate in a strictly controlled manner, hence they are called *abstract objects*. (Actually, there are two classes of subroutines, those which are visible to the user and those which are used internally. This point is important, as we’ll see in a moment.)
