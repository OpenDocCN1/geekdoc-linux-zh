
There is a single privileged user, called root, which can override some restrictions in the system. Section 2.2.5 discussed how processes can acquire root privileges through the SUID feature.

The current Linux kernel is a monolith, i.e., it is a single large program, not a micro-kernel which relies on passing messages among user and kernel processes. When a user process makes a system call, the thread of control acquires increased privileges, but it does so only when trusted kernel code is executed.

We should expect to see some shift in the Linux security model. It will rely on the access control lists being added to the file system. This change will reduce the number of instances where root privileges are used to access some user’s files. The classic problem program, sendmail, must have root privileges so that it can write to the users’ mail spools. If the mail spool files could be tagged with an entry which says “sendmail can append”, a large class of problems would disappear.

This addresses a recurring problem with common operations: processes running with root privileges can be subverted, at which time the damage they can cause is unlimited. If these processes were not quite so omnipotent, the damage they could cause would be limited.

Capability lists and access control lists were described in greater detail in Section 4.5.1.

## 5.6 Standards

Section 5.1.1 discussed how an operating system is defined by interfaces rather than implementation and it showed how these interfaces can be developed into standards.

POSIX is one of the many standards which defines a portable operating system, but it is of particular interest because it was developed by IEEE and has been adopted by ANSI[^1].

It defines an operating system which is independent of hardware platform and it is expected to be met by many different manufacturers.

As mentioned in Section 1.2.8, Linux is in nearly complete conformance with the POSIX standards. New extensions, such as for real-time scheduling, are being added almost as quickly as the standards are ratified. Sections 1.2.9 and 1.2.10 have noted how this conformance has aided in the porting of tools and applications to Linux.

One of the flaws with POSIX is that the standard cannot be freely copied and, therefore, it is not in everyone's hands. Contrast this to the Internet RFCs (request for comments), which define such things as the TCP/IP protocols and have unlimited distribution.

## 5.7 Bootstrapping the Kernel

A system kernel comes into operation in stages. Although the following sequence is not strictly universal, it is common enough that most systems have a counterpart to each step.

### 5.7.1 Processor Start

It doesn't matter if the processor has a complex instruction set (CISC) implemented by internal microcode or a reduced instruction set (RISC) implemented by logic gates; at sometime the processor must complete its initialization and begin “earning its keep”. While computers may display something of their internal state during start (for the sake of the user), they will eventually fetch their first instruction. Back in the olden days (was it really less than twenty years ago?) a user would enter an address via switches on a front panel and strobe that value into the register holding the instruction pointer. Nowadays, the single chip processors are designed to fetch their first instruction from one well known address. The Intel x86 family of computers favor 0xFFFFFFF0, the Motorola M68K family of computers favor address 0. The system designer merely has to ensure there is memory at that location with the appropriate bootstrap routine. This is most often done by attaching a read-only memory (ROM) at that location.

### 5.7.2 ROM

The system ROM provides the next level of bootstrapping. It is often accompanied by some kind of long-term memory which holds configuration information. This can be electronically erasable programmable read-only memory (EEPROM) or low-power CMOS (complementary metal oxide semiconductor) RAM memory with an auxiliary battery. The ROM has several primitive device drivers and a small control program which will attempt to load a larger bootstrap program from one of a list of peripherals. The configuration information can control the choice and sequence of peripherals.

The bootstrap program in ROM can be quite large. But because it is installed when the system is constructed and because it has to be general purpose in utility, it can do little to directly load the large system kernel.

That step is left to the program in the “boot blocks” of the disk storage.

#### BIOS

The Basic Input/Output System (BIOS) of the IBM PC compatible machines provides the bootstrap code outlined above. One interesting aspect of this design is that some of the device drivers are not part of the ROM on the main printed circuit card (motherboard), but rather they are in ROM on various peripheral interface cards. The main code on the motherboard “discovers” this additional code and incorporates it into its basic operations. In this way, unusual programming requirements of new disk drives are hidden from the standard BIOS code.

### 5.7.3 LILo or DOS & LOADLIN

Each system design has a convention for the size and location of the boot blocks. Typically, the bootstrap code in the ROM will load primary bootstrap code from the first few sectors of a disk to some low memory location. Control is transferred to that code, but because the primary bootstrap is small (often 1 Kbyte or less), it usually loads additional (secondary) bootstrap code from disk. The secondary bootstrap is then used to load the kernel.

The code in the Linux loader (LILo) closely follows this model, with the variation that the secondary bootstrap can be used to load one of several kernel images[2].

LILO is a suite of programs including the installation utility `/sbin/lilo` and the primary and secondary bootstrap programs `/boot/boot.b`. `/sbin/lilo` extracts the primary bootstrap program code from `/boot/boot.b` and writes it, along with data describing important disk addresses, onto the disk's boot sectors. The primary and secondary bootstrap programs perform the actual loading of the system.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_204_0.png)

The BIOS loads the 512 bytes of primary bootstrap to location 0x7C00. The primary bootstrap relocates itself to 0x9A000 and it then calls upon the BIOS to load up to 8 kbytes of the secondary bootstrap starting at 0x9B000.

(By using the drivers within the BIOS, the primary and secondary bootstraps avoid the need to containing any device dependent code at all. This elegant technique is marred by an unfortunate problem: the parameters passed for a BIOS disk read are not sufficient to reference high numbered cylinders. Therefore, LILO cannot load sectors which are located in disk cylinders above 1023.)

The secondary bootstrap presents messages from `/boot/message` and reads options and image names from `/boot/map`. After some optional interaction with the user, it loads a kernel image from the locations given in the pointer part of `/boot/map`.

It is important to note that the bootstrap code cannot locate the kernels without help from /sbin/lilo. This is an important step which is sometimes forgotten by neophytes.

The installation part of LILO, /sbin/lilo, reads a configuration file which describes the kernel images, image names, peripheral options, and other bootstrap options.

- It uses this information to locate the secondary bootstrap file boot.b and message when they are not in the default directory /boot.
- It then builds /boot/map which holds pointers to the kernel images.
- Finally it builds the primary bootstrap sector by copying some code from /boot/boot.b and loading pointers to /boot/boot.b, /boot/map, and /boot/message.

(In all the above examples, all occurrences of /boot/ describe the default location. All of these can be overridden by entries in the configuration file. For example, I have a special partition, mounted at /work, where I do all my kernel development. This partition contains an alternate directory /work/boot/ which is cited in the configuration file.)

If one wishes to boot one of two completely distinct Linux systems held in two different partitions, one must first mount the “other” partition on the active partition with a command such as

```
mount -t ext2 /dev/hda2 /mnt
```

prior to running /sbin/lilo. This is because /sbin/lilo locates the kernel images in terms of file names at the time the command is run. The configuration file then needs entries such as:

```
image = /vmlinuz
    root = /dev/hda1
    label = std.linux
image = /mnt/vmlinuz
    root = /dev/hda2
    label = new.linux
```
