
Most inefficient to have the client process wait for each display operation to complete before issuing another request. Instead, the client issues a stream of commands which can accumulate in a buffer. On occasion, the client issues a special command which says “make sure everything in the buffer is sent on the network”. This allows for efficient use of the network. At the same time, the server will be sending events to the client such as saying a mouse button was pressed at location $(X, Y)$.

Because the client and server can be on opposite ends of the network, the server has to direct its commands to some address. This address is most commonly given by the value of the “DISPLAY” environment variable. It can also be specified on the command line, usually as an argument to the **-display** option, or as a resource (discussed later in Section 3.2.6).

When a client opens a window, a request to the server contains hints, among which are the size and location of the window. These are honored unless overridden by a special client called the window manager. Once the window is opened, the client could issue further requests to resize the window, move it around the screen, etc. This is almost never done, as these tasks are left to the control of a window manager such as described in Section 3.2.3.

The boundary between command line interfaces and GUIs becomes muddled when the user uses a command line interface in a window emulating a terminal screen. In such a case, it’s best to realize that the terminal emulator, such as xterm, is a client program which is causing the server to open a window and display characters on it. The terminal emulator opens what is called a *pseudo-terminal* which allows the terminal emulator to play the role of a serial peripheral to application programs.

Pseudo-terminals are similar to the named pipes described in Section 5.3.3. The critical difference is that they can accept *ioctl* control calls which are normally used only on peripheral devices.

The shell that is started by the terminal emulator cannot tell it is not connected to a real terminal. The system uses pseudo-terminals in a similar manner to connect a telnet session to a shell.

### 3.2.2 The X Server

When the server is started, it takes over the console, keyboard and mouse and waits for commands over the network to cause things to be displayed or to report events. In Linux, the server maps the display device's memory directly into the server's address space. This somewhat unorthodox device access is necessary to meet the rather high performance access needed.

The server passively waits for client requests. It does not need to honor requests from every source. It can be configured to honor requests only from specific hosts or to honor requests only on connections which were opened with the presentation of some authorization name and data. One current authorization scheme uses a “magic cookie”, a long, randomly generated binary password, generated by the server and passed to authorized clients by a display manager.

In the case of a single workstation or personal computer, the client and server processes reside on one machine, but they retain their independence. This independence means that when that system is connected to the network, it suddenly acquires the ability to serve clients throughout the network.

The display area can contain a number of overlapping windows. As the mouse is moved, the server will move the cursor which floats at the very top. The X Window System model is based on the idea that events (such as mouse motion, button presses, or keystrokes) drop from the cursor at the active point down through this stack of windows. Each window is supported by a client process which ultimately is executing a loop which looks for events. If the event is of no interest to this window (client), it is passed on to the next lower window. Unwanted (or unrecognized) events fall through to the root window where they are processed.

## The X protocol

The server and clients are protected from one another by a protocol which specifies the messages to be sent to and from the server. The message types can be grouped into fourteen categories:

- Colors and Colormaps
- Cursors
- Drawing Graphics
- Events
- Fonts and Text
- Graphics Context
- Images
- Interclient Communication
- Keyboard and Pointer
- Security
- Window Characteristics
- Window Manipulation by the Client
- Window Manipulation by the Window Manager
- Miscellaneous

## 3.2.3 Window Manager

It would be a great bother to have each client process keep track of all the things which can be done to a window after it is open. There is little sense in duplicating this function in all the different clients. It is best to leave this job to a single specialized client.

Usually there is one client, called a window manager, which takes control of the root window (the one which is linked to the entire display) and controls size and position of the other windows. Since the root window is the bottom-most window, all unprocessed events end up being sent to the window manager.

For instance, clicking the right button while the ALT key is down causes an event to fall through any xterm windows to the root window. My window manager, ovlwm, responds by popping up a menu which gives me the opportunity to move the xterm window, iconify it, push it to the bottom, refresh it, or to quit displaying that window. Other window managers may ignore this event.

One can use X without a window manager, but it is very inconvenient to do so. Without the ability to relocate, resize and iconify windows, the user is entirely subject to the hints offered when each window is first opened.

The window can also display a command bar or support pull-down menus which can be used to start application programs.

Significant characteristics of the various window managers are:

- **fvwm** Featherweight (or Frugal) Virtual Window Manager (derived by Robert Nation from twm)
    - resize displayed—yes
    - resize by—drag corner
    - move by—drag side or title
    - 3-D borders—yes
- **twm** Tab (or Tom's) Window Manager (by Tom LaStrange of Evans and Sutherland)
    - resize displayed—yes
    - resize by—click icon and push side or corner
    - move by—drag title bar
    - 3-D borders—No
- **ctwm** extension to twm with virtual workspaces, options for motif-like look and feel
- **olwm** Open Look Window Manager (derived from Sun Microsystems)
- **olvwm** Open Look Virtual Window Manager (extends olwm)
    - resize displayed—no
    - resize by—drag corner
    - move by—drag side

gwm called the EMACS of window managers because of its extensibility

But this list cannot be anywhere complete because almost all of these features can be reconfigured by changing the appropriate configuration file. These configuration files are often collections of triples: user action, context, and result. For instance, pressing the left mouse button when the pointer is on the title bar of a window causes that window to be raised to the top, or pressing the right mouse button while the control key is pressed with the pointer in an xterm window presents a font selection window. (In this latter case, the configuration is specific to the X terminal emulation, not a window manager.)

## 3.2.4 File Manager

One of the hottest GUI applications is the file manager. This program reduces the need for a command line interpreter because it allows one to start programs by clicking on an icon or dragging and dropping one file's icon onto another icon.

One tool distributed with Linux is xfm, a file manager which has been under development for over five years by Simon Marlow, Albert Graef and others. Graef writes:
