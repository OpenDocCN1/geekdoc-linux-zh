This user community subjects the code to study and test according to the user expectations and, on rare occasion, the specifications. Since the entire program, in its source form, is exposed to the world, there is a rush to find and fix flaws that is rare in commercial software development settings.

As a bonus, or perhaps as a side-effect, there is a certain amount of self-selection among the programmers. No one is directed to “design and code” something outside of their experience. Instead, changes are made because the contributor has some expertise to share.

Finally, releases are not subject to external synchronization. Instead, they are made as soon as fixes or enhancements are completed. Thus Linux is *robust* but constantly changing.

Some people are scared by a constantly changing system. They’d rather have a system with well known flaws and well known work-arounds. The danger with this approach is that on flag-day, when a major new release is finally installed, a large number of surprises ambush the users. For this reason, some users stick with years-old system releases. With Linux the changes are modest from one release to another. A cautious user can follow the crowd at a distance, upgrading to new versions at a modest rate, and have the assurance that no problems lie in ambush.

This process of following the leaders is encapsulated in the dual track for releases. Section 9.1 describes this process in greater detail.

# 1.2.3 Linux Offers High Performance

The best performance is achieved when the application is executed with no system kernel overhead. Certainly this holds for what are called “embedded systems”, where the system’s function is limited and rigidly defined.

Unfortunately this doesn’t apply when the system is intended to be general purpose. In that case, there’s always some overhead—the trick is to keep it small.

Linux does a good job at that because there is constant pressure (and continual changes) to reduce the overhead of Linux system calls.
