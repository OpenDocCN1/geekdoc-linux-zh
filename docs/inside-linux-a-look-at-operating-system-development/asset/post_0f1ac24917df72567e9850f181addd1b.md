
### 2.2.4 File System

As with Multics, the Unix file system is a hierarchy of directories containing directories, plain files and special files for peripheral access. All input and output (I/O) is performed via system calls such as open, close, seek, read, and write.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_53_0.png)

Figure 2.2: File system hierarchy

Unix file system entries are each defined by an inode, described more fully in Section 5.3.1. This structure contains information about the

- type
- ownership
- access control
- creation, modification, and access times
- size
- location

If the type is a plain file, “location” refers to a hierarchy of direct and indirect pointers to disk blocks containing file data. This scheme provides higher performance for small files than a fully indirect scheme would provide, yet can describe files larger than can be stated in the bits used in the “size” parameter.

The inode of a *directory* refers to structured data held in the same kind of hierarchy of disk blocks as a plain file. This data consists of the names and inode numbers of plain files, special files and directories.

Because it is the inode which really establishes file data, it is trivial to have multiple directory entries referring to the same inode and thus to the same file. This reference is permitted for file types, but prohibited for directory types because of the confusion it would engender when searching a file system.

Until recently, directory data could be read just like data in other files, but because directories on networked file systems are not quite the same as directories on a local disk, this ability has been removed to enforce consistent directory access.

*Special files* to access peripherals come in two categories: block I/O entries and character I/O entries. Block I/O refers to random disk access. Character I/O entries are used to access the terminal, keyboard, display, modem, etc. Ken Thompson wrote

> In retrospect, the names [block I/O and character I/O] should have been ‘structured I/O’ and ‘unstructured I/O’, respectively[51].

If the type is a peripheral, either block I/O or character I/O, a major and minor number is given in place of pointers to disk blocks. The peripheral type selects which look-up table (block or character) to use. The major number indexes the appropriate table to identify which device driver will service the system call. The minor number identifies which specific device, such as a serial communication port or disk partition, is the subject of the I/O function.

Few user programs access block I/O devices directly because they usually contain the traditional file system and are accessed through the file system functions.

### 2.2.5 SUID

Another significant idea first seen in Unix, and issued U.S. patent number 4,135,240, is the “Set User ID bit” associated with each file.

Unix programs are started by issuing the **execve** system call. The arguments to this call are the name of the file containing that program and the arguments to be passed to that program. The file must be marked as executable in the access control bits. In any event, the new process will normally run with the same privileges as the calling process. Section 5.2.2 discusses this further.

If the file has the **SUID** access control bit set, the new process will take on the identity and privileges of the owner of the file. In this way, a Unix user can amplify or change access rights for another user. (The Linux system changed this rule slightly. An SUID shell script is too easily subverted by crackers. For this reason, Linux does not support SUID shell scripts, only binary executables. System V has added the same restriction.)

One classic example using this feature is the **ps** command. Many implementations of this command need read-access to kernel memory, something not normally allowed an ordinary user. The file containing this command is owned by **root**² with the SUID access bit set. When it is run, it acquires root access to the kernel memory. (The **/proc** file system renders this specific example obsolete in Linux, but the general need remains.)

Another example, valid for Linux and all Unix systems, is the **passwd** program. The basic user account information is maintained in a password file which is read-only to all but the root user. The **passwd** program can override these permissions and modify the user's entry in the password file because it acquires root user privileges through the SUID feature.

Access permissions are also based on group membership. There is a feature called “set group id” (**SGID**) which is an analog of the SUID feature that sets the group of the executing process.

As a precaution, the SUID and GUID bits are automatically cleared when the file is modified or when the owner or group is changed; the chance of accidentally conveying privileges to other processes is reduced. Page 153 has a brief discussion of how the execute and SGID bits apply to directories.

### 2.2.6 Philosophy

All these specific features led to a clear philosophy of how Unix tools should be designed as outlined by McIlroy *et al*:

- Make each program do one thing well. To do a new job, build afresh rather than complicate old programs by adding new “features”.
- Expect the output of every program to become the input to another, as yet unknown, program. Don’t clutter output with extraneous information. Avoid stringently columnar or binary input formats. Don’t insist on interactive input.
- Design and build software, even operating systems, to be tried early, ideally within weeks. Don’t hesitate to throw away the clumsy parts and rebuild them.
- Use tools in preference to unskilled help to lighten a programming task, even if you have to detour to build the tools and expect to throw some of them out after you’ve finished with them[35].

Although this prescription hasn’t been universally followed, it still influences how many new tools are built.

## 2.3 Minix and Other Pedagogical Systems

There has been a long recognized need in the teaching of operating systems: a concrete example which students can examine in detail. In 1968, E.W. Dijkstra described a small system kernel, T.H.E, designed from theoretical foundations and built as an adjunct to university research[15].

In 1977, John Lions used Unix as the basis of a class and textbook on operating systems[32]. Unfortunately, because of licensing restrictions, his book containing the Unix operating system source code was formally available only to a small university community. (It has received a wide distribution by samizdat³ publication.)

Two other books have since described Unix in detail. One focused on the AT&T version and the other focused on the BSD version[5, 30]. Although neither included the system source, both offered detailed operational details and data structure descriptions.

In 1983, the TUNIS system implemented a Unix-like system using Concurrent Euclid[23]. The source was made available for student examination and modification. Minix was another such Unix-like system designed for pedagogical use[9].

Niklaus Wirth's Modula has been used to build tiny system kernels. We'll see in Section 5.2.4 how certain language features support this effort.

In 1987 Andrew Tannenbaum created the Minix⁴ operating system. Its primary utility was as a pedagogical tool to show in detail how an operating system works. It was superior to previous efforts in that it was self hosted, i.e., it could be used to further develop itself because it had its own editor, compiler, etc., and it ran on a modestly sized personal computer. The source for Minix was widely distributed as an adjunct to Tannenbaum's textbook[49].

### 2.3.1 Intel Platform

One of the most significant features of Minix is that it was developed for operation on the PC architecture. The Intel 8086 and descendants comprise one of the most popular series of computers yet developed. The total number of systems containing one of these processors far outnumber the mini-computers which early Unix systems required.

The ubiquitous PC was also inexpensive, often less than $1000 for a minimally configured system. This put Minix within the reach of frugal departments and students.

A slightly more expensive platform, one with an Intel 386, was chosen as the basis of the first Linux development.
