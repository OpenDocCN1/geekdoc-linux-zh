### Medium Term

Short term scheduling deals with the immediate decision: “which process should be executing at this instant?” Medium term scheduling is concerned with how the system can be tuned to yield better performance. Most commonly, this scheduling is done by adjusting the priority of each process on a regular basis. Since Unix-like systems are often used for interactive work, interactive processes are generally given higher priority and compute-bound jobs are given lower priority. The definitions of interactive and compute-bound is a bit fuzzy, but the idea is a process which tends to block for keyboard or other I/O is regarded as interactive and a process which tends to use its entire time slice is regarded as compute-bound. There is also a bias towards smaller processes based on the hope that they’ll get their work done and get out of the system. (One method of identifying small processes is to integrate the memory use over time.)

The medium term scheduler can take more severe action by swapping a process out of memory to disk. This swapping would be done because of thrashing resulting from memory oversubscription. (Although Linux does not swap processes at this time, Section 5.4.2 discusses thrashing in greater detail.)

### Long Term

This is most commonly found in batch processing systems. The long term scheduler decides when additional jobs should be admitted to the system.

Some interactive systems make a similar judgement to allow more users to use the system. An example familiar to many is the mechanism within the ftp daemon which limits the number of users who can connect and transfer files.

In either case, the long term scheduling decisions are performed by a process running outside of the kernel.

## 5.2.5 Virtual Machine/Operating System Emulation

A virtual machine is an execution environment in which a program cannot tell it is not running on the base hardware. (An application of this idea is discussed in Section 4.3.2.)

The advantage to a virtual machine system is that the emulation software can adjust or modify what the program sees. For instance, the virtual machine can appear to possess peripherals which do not exist in the actual hardware.

One of the difficulties in developing an operating system is that an entire machine has to be devoted to its development. Whenever a new version of the system is ready, the current version of the system must be shut down before the new version can be tested.

A virtual machine provides a perfect environment in which to test or run other system kernels. It also provides an avenue for supporting programs written for different system kernels.

### DOSEMU

No matter how wonderful Linux is, there are some applications which are not available to run directly on a Linux system. These applications include many which are available to the MS-DOS user. The natural response of the Linux community, given that they couldn’t port the applications because of license or trade secret restrictions, was to introduce an MS-DOS-like environment to Linux.

**dosemu** runs as a privileged Linux process—one which can access some of the special registers in the processor. This permits dosemu to emulate enough of the x86 hardware to trick a copy of MS-DOS into thinking it has full access to the x86 hardware. Thus, “dosemu” is somewhat of a misnomer because it does not emulate MS-DOS, “intelemu” might have been a better term.

When **dosemu** starts execution, it loads a configuration file which specifies where MS-DOS can be found. When MS-DOS is started, it communicates with the user through an emulated keyboard and emulated display which are in turn mapped to the real keyboard and the real display or an X window.

The hardware emulation is sufficiently complete that MS Windows 3.1 has been run under Linux.

### WINE

By contrast, WINE does not rely on a virtual machine system. One could say that it is a “virtual system kernel” because application programs cannot tell if they are running on MS Windows or WINE.

It still needs to operate in privileged mode, but it has the advantage that a well-behaved program does not attempt to execute privileged instructions. Instead, user programs execute a trap instruction, much like a Linux program system call. As a result, WINE merely has to slide in between the user program and the Linux kernel. It then maps user program requests into the appropriate Linux kernel calls.

### Executor

In contrast, the Executor program is not a virtual machine environment because it doesn’t use an architecture to emulate itself. Instead it qualifies as a system emulator which offers sufficient fidelity to support most every application which runs on a Macintosh. See the web or ftp sites for details.

## 5.3 Input/Output

The programmer’s view of Linux system I/O is given by the system calls an application program can make. Although the documentation on these calls refer to “files”, the named objects can be regular files, directories, symbolic links, block special devices, character special devices, sockets, and fifos.

A regular file is an abstraction which gives a name to a collection of data typically stored on a disk. In addition to the **read** and **write** system calls which are used to access the data, programs use **open**, **close**, **lseek**, **creat**, **link**, and **unlink** to manipulate the files.

Associated with files and directories are the concepts of ownership and access rights. Additional information, such as time of access, size, and special modes of operation are also attached to each file and directory. Functions including stat, fstat, and lstat reveal this file description information to the programmer. We'll see in Section 5.3.1 that it is possible to have more than one file name refer to the same file, a sort of “aliasing”.

Symbolic links are another form of aliasing which have their own merits and shortcomings. For symbolic links, the calls symlink and readlink are used to create and examine symbolic links.

A directory is a place in which to store a collection of file names. Directories are scanned with readdir calls and they are created and deleted with the mkdir and rmdir calls.

Although the special device files (both character and block) aren’t really files, they are accessed as a part of the file system. The programmer uses the same basic I/O calls, read, write, etc., on these files to access peripherals. In order for this to work, they must have a presence in some directory. The mknod system call is used to create a file system entry which holds information about the device. The catch-all function, ioctl, is used for all the fussy, funny things one needs to do to a peripheral device which have nothing to do with reading or writing characters.

Sockets are a way to represent one side of a network connection. Additional specialized calls, including socket, accept, listen, bind, connect, send, recv, sendto, recvfrom, sendmsg, recvmsg, select, shutdown, getsockopt, and socketpair, are provided to create, use, and remove sockets.

A named pipe (a first-in-first-out buffer which behaves like a character device) is created with the mkfifo system call.

Before examining how these system calls work, we’ll first pause a moment and look at how one of the file systems is structured.

### 5.3.1 File System Structure

Actually, one really shouldn’t write of the file system structure, because Linux supports many different file system formats, including ext2, minix, xia, hpfs, ISO9660, and nfs. (Section 5.3.2 shows how the system can keep track of the different file system types.)

We'll look at the details of the ext2 file system because it has a number of performance enhancing features and because it is used by most Linux systems.

There are six major elements to a disk containing an ext2 file system:

- Partition table
- Inodes
- Data
- Directories
- Bitmaps
- Superblock

The partition table describes how the whole disk is to be split into several smaller disk-like entities. Each partition is distinct from the other and the device driver “understands” this in a way which allows each partition to be treated as a separate device. When Linux runs on an Intel 386, 486, Pentium or compatible system, the partition table is the same as used by MS-DOS.

Since it is possible to use the entire disk for a file system, partitioning is not really essential to the file system and thus there is no need to discuss partition tables further. The term “partition” will be used to refer to either a partition or an entire disk, as the context requires.

Often partitions are used to isolate one category of use from another, e.g., the basic system is placed in one partition, users’ home directories are placed in another partition, the spool area used by printers, and netnews is placed in another partition, and yet another partition can contain an MS-DOS file system. This allows MS-DOS, MS Windows and Linux to reside on different partitions of the same disk as well as being allowed to spread across several disks.
