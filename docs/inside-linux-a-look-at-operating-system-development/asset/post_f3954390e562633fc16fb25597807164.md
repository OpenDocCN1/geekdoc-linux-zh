
## How commands are processed

An experienced user is aware that the shells provide the elements of a full featured programming language. In the following sections we'll explore the most common features of shell programming languages.

The shell interprets the input by first breaking it into distinct *tokens*—basically words and punctuation symbols—and then matching the tokens with patterns of the language definition (called its *syntax*).

Simple shells read lines, then expand file names, substitute variables, and note I/O redirection (as described below). The shell then interprets the first token as the command name and the rest of the tokens are passed as arguments to that command. A basic command such as **date** causes the system to search for an executable program with that name. It executes that command and then presents a new prompt.

A slightly more complex command includes arguments which are passed to the program. For instance, the command `echo 'hello world'`, causes the string argument “hello world” to be passed to the echo program. The command then echoes its arguments to the display.

Yet another enhancement permits the shell to redirect a command's output to a file. The command `echo 'hello world' > tmp.file` will redirect the output to the file instead of the display.

More complex shells allow multiple commands to be joined on one line and one command to cross line boundaries. Tokens such as “(”, “;”, “)”, “>”, “|”, and “$” are used to group, separate, and modify commands. The shell then nibbles at the tokens, using “(” and “)” to group collections of commands and (“;”, “|”), etc. to separate commands.

For instance, the input line

```
(date; echo 'hello world') > tmp.file
```

is first split into the tokens “(”, “date”, “;”, “echo”, “hello world”, “)”, “>”, and “tmp.file”. The “;” token separates two distinct commands. The shell executes the command date and then executes the command echo with the argument hello world. Because the tokens “(” and “)” surround both of these commands, the output of both are redirected, because of the “>”, to the file tmp.file.

Generally the shell will split strings into distinct tokens wherever it sees what is called whitespace (one or more blanks or tabs) unless some special quoting mechanism is used. You can see that something special has already happened because the pair of “" caused the string of characters “hello world” to be treated as a single token. You will also notice that there was no whitespace after the “(” or on either side of the “)” or the “>”. This is because the shell also recognizes a number of characters as appropriate for delimiting a token without the need for whitespace.

### Filename expansion

Most shells support additional special characters, most importantly as wild card characters in file names. For instance “*” stands for “zero or more characters” in a file name.

When the shell discovers a string with one of these characters in it, it replaces that token with a sorted list of all the file names which match that string pattern. If the files “at”, “bad”, “bat”, “cat”, “flat”, “rot”, and “rat” are in the current directory, the string “*at” is expanded to “at bat cat flat rat” and then tokenized into the list “at”, “bat”, “cat”, “flat”, and “rat”. Almost every shell has the “*” wild card character. Different shells have different additional rules for wild card expansion.

Some shells have argument expansion rules which do not depend on file names, but rather they create arguments according to a pattern-matching rule. For example, the C shell expands “{a,b}{0,1}” into the list “a0”, “a1”, “b0”, and “b1”, even if files by those names do not exist. A slightly different input, “[a,b]0,1”, would expand into the same list only if those files existed locally. That is, the tokens “[” and “]” are an extension of the wild card mechanism, but the tokens “{” and “}” provide an entirely different way to build strings.

### Internal vs. external commands

Shells have a few built-in commands—the list varies from one shell to another. The rest of the commands are located in files containing executable machine code or shell scripts. Commands are known by the name of the file in which they are stored. When the user enters what looks like a command, and the command is not known internally, the shell will look in one or more likely directories for an executable file by that name. The list of places the shell looks is called the *search path*.

### Search path

The shell searches the directories in the order they are listed in the search path and uses the first file it finds with that name and the correct permissions. If no file is found with that name and the correct permissions, the shell may issue a warning naming the first file with that name but wrong permissions, or it may say nothing at all.

All this searching can slow down execution, so some shells cache the names of executable files in the search list so that the search does not have to repeat for each command entered.

An important aspect of the search path is that a command name can match the name of several executables in the search path, but the first one found in the order of the search path is the one which is used.

Internal commands are directly executed by the shell, but when an external command is executed, it is done so as a child process of the shell. This gives the shell control over the process executing the command.

### Redirection and pipes

Both internal and external commands are subject to redirection and piping. Redirection permits the shell to send the output from a process to a file instead of the display and it permits the shell to send commands to a process from a file instead of the keyboard. Piping allows the shell to send the output of one process as input to another process.

Redirection is based on the idea that a process inherits a standard input port and a standard output port from its parent process. In the case of interactive sessions such as the shell, these are connected to the keyboard and display respectively, but the process does not know this with certainty. It only knows that there are input and output streams of data.

When the shell sees a “>” or “<”, it uses the next token as a source or destination file name and it removes those tokens and the file names from the command line. The rest of the command line is processed as before, but the command is started only after its output and input are redirected. Section 5.3.3 shows how this redirection is accomplished.

The shell splits the command line into parts at each “|” token and decodes each part as a separate command. When the shell starts the processes, it connects the output of the process to the left with the input of the process on the right via a pipe. When processes are used in this manner, they are called filters. The details of this special kind of redirection is left to Section 5.3.3.

Linux (and Unix) processes have an additional output port called “standard error”. Advanced shells have extensions to separately redirect the standard error data stream, or to combine it with the standard output data stream. The Georgia Tech new shell described on pages 157–160 shows a powerful extension of this basic idea.

### Basic interaction with the shell

The most common use of the shell is as a command line interpreter. In this mode of operation, the shell reads input from the keyboard and writes the results to the display. Normally, the shell processes input a line at a time, but in some circumstances, it will read multiple input lines before taking action. This provides the basic subroutine calling mechanism.

### Substitution of variables
