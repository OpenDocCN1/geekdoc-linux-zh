# ### Naming

One basic issue is the question of “how much of the network is visible to the user?”

It’s possible to design a system such that the user cannot tell where a file is located. The competing notion is to make the file’s location part of the file’s name. We’ll see examples of each in the following paragraphs.

A somewhat parallel issue is how the name of a file changes as the user’s location changes. With peer-to-peer file sharing, it’s possible to have a file local to one user and remote to another. If the file naming is independent of location, scripts which refer to such a file need not change because they are executed on different systems. Of course, this means the local user will be required to use the same longer name which everyone else uses. Systems such as Netwrok File System and the Newcastl connection support both naming conventions.

# ### Level of implementation

The network file access can be supported from within the kernel or it can be provided by some user level program. Kernel support generally implies higher performance, while user level support provides greater flexibility. (It’s worth noting that opposite decisions can be made at either end of the client/server connection.)

# ### Peer-to-peer

Some models of network file access have a single file server and all other systems are clients. Other models allow for full symmetry so that any system can act as a client, a server, or both a client and a server.
