
### 3.1.2 Application Programs

The shells are not the only programs which process user commands. Application programs receive user commands via three paths: the command line, the environment, and the standard input. The command line and environment variables are used to pass information to the command which generally apply to the entire operation of the command. For example, the **sort** command can be told to treat upper and lower case characters as equal with the `-f` command line option and the **man** command can be provided a special search path via the **MANPATH** environment variable.

The processing of the standard input stream is much more specialized. The various text editors give proof of that.

#### Command line parsing

One of the more unfortunate characteristics of Linux, Unix, and Unix-like systems is that each command seems to have a different syntax and meaning for command line options. This is a natural result of an underlying philosophy: the shell has no business interpreting command line arguments. As a consequence, each command applies its own syntax rules and, for a long time, used its own code to parse the command line. This approach has been changing over the last decade---ever since the **getopt** library routine was first offered.

The **getopt** routine formalized the convention that single-letter options have a leading “-” and that they may be grouped together provided that only the last one takes an additional argument. Long option names (as used by the **GNU** utilities) have a leading “--” and must stand alone in the command line. Anything past the last option is a general argument---a list of file names is a common example.

There still exist a number of commands which do not conform to this new syntax. This is for reasons of backward compatibility.

The meaning assigned to the options remains confused and is unlikely to change. Thus `-f` means *fold* for the **sort** command, *do not sort* for the **ls** command, *whatis* for the **man** command, etc.

The only hope in this respect is a move towards longer option names. Instead of relying on a single letter, options are being defined for longer strings. This conflicts with the ability to group several options together, but that is a price well worth paying for the sake of consistency.

All Linux commands are invoked indirectly (through run-time library functions) or directly by calling the C function

```
int execve (const char \*filename,   const char \*argv [],   const char \*envp []);
```

The commands are integer valued functions taking three arguments

```
int main (int argc, char \*argv[], char \*envp[]);
```

The call can be from within a shell, in which case the user only sees the command name and a list of arguments. Likewise, the command can be a shell script, in which case the argument list and environment are converted into named variables which can be manipulated as described in Substitution of variables on page 44 and used in expressions as described in Selection and Iteration on pages 47 and 49. The important point is that every process starts with these two arrays of pointers to strings.

### Environment variables

The environment variables are structured as a set of name-value pairs. The library function getenv can be used to search the set for the value of a specified name. It will return a pointer to the value (which may be an empty string), or NULL if it is not defined. Shell scripts can easily determine if a name is defined, and if so, what its value is.

### Standard input

User programs can also read commands from the user's keyboard (or other redirected source).

Normally the keyboard input is pre-processed within the kernel so that the user program doesn't have to bother figuring out how to delete characters or words, how to echo characters, how escape characters work, etc. This is called *cooked* mode.

Although shell scripts generally read a line at a time, other programs have a mechanism to read each character as it is entered—called raw mode. The pre-processing is quite useful when entering shell commands or text, but editors and the like would just as soon not require the user to press <ENTER> after each command—especially considering many of the commands consist of a single keystroke.

### 3.2 Graphical User Interface

There exist menu-based tools, such as curses, which can paint the screen with arbitrary mapping of characters and allow the user to move a box cursor about to select options, but this is regarded as passé.

Almost all computer systems sold today have some kind of pixel addressable display (usually in color) and a pointing device such as a mouse. These displays support a graphical user interface (abbreviated GUI and pronounced "goopy") which presents icons which can be clicked on to select options or execute programs. The practice is to "click, double-click, or drag-and-drop" to cause things to happen.

Linux uses the X Window System, also called X-Windows or just X, to provide such a graphical interface. X is the system of choice for all of the most powerful systems and it is now available on the personal computer. X was an outcome of Project Athena at MIT sponsored by DEC and IBM. They were joined by other industry leaders—including Hewlett-Packard, Sun Microsystems, and AT&T—in forming a consortium which provides sponsorship for continuing development.

X relies on what many regard as an unusual twist to the client/server model—the display, keyboard, and mouse are under the control of what is called a server and the client is an application program somewhere on the net. This model has confused a great number of people because they draw an incorrect analogy with the networked file system client/server model. They think they, not their programs, are the client. Thus they think X is backwards. If they were to realize that their program is the client, the client/server model is entirely consistent.

This network based client/server model has led to one interesting outcome—the development of X terminals. These are small computer systems with a processor, a keyboard, a bit-mapped display, a network connection, and several megabytes of memory, dedicated to function only as an X server. Because of this very focused design, these systems can be built at a lower cost than that of an engineering workstation. Since most computer programs spend a great deal of time waiting for a user to issue commands, a compute server (a high-performance computer shared by many users) can be used to execute many X client programs. These programs can then display results on the appropriate X terminal.

A variant to this theme employs the many personal computers on the net as X servers.

The utility of the X model becomes more apparent when one considers a configuration where clients of different types hosted on different machines all can interact with the user through the X server. One can use a large-scale computer to perform simulations and plot the output, another system can be used simultaneously for text editing and type-setting, and the workstation's computer can be managing the windows.

One can also have a more realistic visual appreciation for a multi-tasking system by displaying multiple active windows, one per active process. It's quite easy to monitor the progress of an application when its results are scrolling on a window to the side of the display.

### 3.2.1 The X Client

This term is really just a fancy name for an application with a graphical user interface. Many X clients are modest extensions of existing character-based applications, while others fully exploit the graphical capabilities of the system.

I'll refrain from commenting on the design of such applications beyond pointing out that with all GUI (graphical user interface) systems, the designer must be very careful to offer some mechanism to get at the uncommon features and options, as well as the common and popular parts.¹

X clients rely on an extensive library of structures and functions to manipulate the extensive details of the X protocol. Additional layers of libraries provide more isolation from tedious and bothersome details. They also provide a bridge for the *semantic gap* between what the user wants and what the system offers.
