We’ve seen in “Dynamic Linking” on page 200 how the a.out format can be extended and made to support dynamic linking. The many steps needed to build the stubs were omitted, but rest assured, the process is quite untidy.

The ELF format, by contrast, requires only $N+1$ steps to build a shared library from $N$ object files, and one additional option to bind that library to the executable.

$N$ distinct steps are used to build each object file out of the corresponding source file. The only unusual feature is that the option `-fPIC` is given to the compiler to ensure the code in the object file is position independent${}^{1}$. The $N+1st$ step collects all the objects into the library. The compiler is given an option `-shared` and the output file name has a `.so` extension.

When the executable is built, the only necessary extra argument is the name of the new library.

At this point, it should be admitted that the work done by the system isn’t really that much less than for the a.out format, but the ELF format allows all the steps to be more easily integrated into the compiler.

**For example**: Suppose we wanted to encrypt all our alphanumeric output using a dynamically linked library routine. Such a routine would be called to process each character or string to be printed.

Three entry points `set_key`, `encrypt` and `decrypt`—are defined in `cry.c` as outlined below:

```
void set_key(char * key) { ... }
char * decrypt(char *inout) { ... }
char * encrypt(char *inout) { ... }
```

> ${}^{1}$Position independent code is designed to contain only relative addresses. That is, instead of using an absolute address to refer to code or data, it uses an address relative to the start of the code or a base register. As a result, the code can be mapped to any virtual address without the need to apply relocation.
