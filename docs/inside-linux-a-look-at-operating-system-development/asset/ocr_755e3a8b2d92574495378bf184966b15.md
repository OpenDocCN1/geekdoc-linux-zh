(Virtual memory is anathema to real-time processing because a process is interrupted when it references a missing page. These interruptions, called page faults, delay a process until the kernel move data from disk to memory. With soft real-time systems, the real-time tasks are locked into physical memory so as to avoid delays due to page faults. Only those processes which are not designated “real-time” are affected by delays due to paging. See Section 4.4.4 for more discussion about virtual memory.)

In a similar vein, a hard real-time system may allow lesser priority tasks to run, provided the system can force control back to the critical tasks in time to insure their deadlines are met.

When resolution and consequences are left unmentioned, only *hype* is left. Until detailed descriptions of context switch time, interrupt latencies, priority scheduling algorithms, and execution speed are given, you can't really count on having real-time behavior. Be wary of such systems.

# 4.1.4  Linux As a Real-Time System

Someday Linux may be able to claim to be a real-time system. Features have been developed to support this goal. System calls for memory locking and scheduler control have been added to the development kernel.

These enhancements mean Linux is rapidly approaching the level of soft real-time support, but there are some tricky issues yet to be resolved. Markus Kulm¹ warns that a process is not awakened from an interrupt, but rather it is only made runnable, i.e., it may not run immediately after the interrupt completes. He also warns that some interrupt handlers may have to be rewritten and that there are some places in the kernel where interrupts are disabled for extended intervals.
