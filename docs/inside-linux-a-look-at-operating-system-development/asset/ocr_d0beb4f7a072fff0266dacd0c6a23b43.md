Over this past decade, this situation has undergone a reversal. First, the thirty-two-year-old decision to code Multics in PL/I and then the successful rewrite of Unix in C twenty-three years ago have finally persuaded most everyone that the proper high-level language is sufficient to the demands. Then, the fact that modern compilers do such a good job *optimizing*, machine code generated by a high-level language compiler is normally superior to that produced from an assembly language program.

The reason for this quality is that computers are now able to do what Turing hoped for nearly fifty years ago. They are able to keep track of more details (such as the interrelationships of register use and data storage requirements) with greater accuracy than any assembly language programmer.

The shift to higher-level programming languages has actually helped the process of optimization because, as the programmer shifts away from a viewpoint which is hardware aware, fewer simplifying assumptions are made about how to allocate resources. The compiler is then free to do things which, although uncommon, result in better (faster and/or smaller) code. For example, although the programmer may have declared a variable, there is no need for variable to ever be stored in some memory location—the compiler may have determined that the variable can reside in a register throughout its useful lifetime, after which the value is discarded.

A bonus which comes with this shift towards higher level languages is that the *semantic gap* between the problem and the programming language is reduced.
