There is a single privileged user, called root, which can override some restrictions in the system. Section 2.2.5 discussed how processes can acquire root privileges through the SUID feature.

The current Linux kernel is a monolith, i.e., it is a single large program, not a micro-kernel which relies on passing messages among user and kernel processes. When a user process makes a system call, the thread of control acquires increased privileges, but it does so only when trusted kernel code is executed.

We should expect to see some shift in the Linux security model. It will rely on the access control lists being added to the file system. This change will reduce the number of instances where root privileges are used to access some user’s files. The classic problem program, sendmail, must have root privileges so that it can write to the users’ mail spools. If the mail spool files could be tagged with an entry which says “sendmail can append”, a large class of problems would disappear.

This addresses a recurring problem with common operations: processes running with root privileges can be subverted, at which time the damage they can cause is unlimited. If these processes were not quite so omnipotent, the damage they could cause would be limited.

Capability lists and access control lists were described in greater detail in Section 4.5.1.

Section 5.1.1 discussed how an operating system is defined by interfaces rather than implementation and it showed how these interfaces can be developed into standards.

POSIX is one of the many standards which defines a portable operating system, but it is of particular interest because it was developed by IEEE and has been adopted by ANSI<sup>24</sup>.

It defines an operating system which is independent of hardware platform and it is expected to be met by many different manufacturers.
