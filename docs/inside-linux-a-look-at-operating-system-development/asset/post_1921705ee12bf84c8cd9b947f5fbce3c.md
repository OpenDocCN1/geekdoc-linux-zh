### 3.2.5 Startup

One can start the X server and clients explicitly, and it's instructive to do so. If you enter the command X after logging into Linux at the console, the screen will flash and, after a moment, it will present a background with a single X as the cursor (or pointer).

This is rather boring because, until you start a client, all you can do is move the pointer around the screen.

If you can get access to the system from another session, you can start one or more clients. Then X becomes useful, especially if one of the clients is a window manager.

There are easier ways to start X. xinit is a program used to start the X server and run a client program or startup script. By default it starts the server program called X in the user's search path and then it looks for and executes a script .xinitrc in the user's home directory. (Note the leading "." in the file name.)

If no script is found, xinit starts a client program called xterm in the user's search path. (xterm is a terminal emulator program which normally opens a window 80 characters wide by 24 lines deep.) By default, xterm starts a user shell which can be used to issue commands to load a resource database, initialize a window manager, start other windows, etc.

The .xinitrc script contains commands to start several processes, such as xterm sessions, in the background and ends with a command to start a window manager in the foreground. The last command is done in foreground because the xinit program terminates the server when the .xinitrc file (or the substitute xterm session) is finished. With the last command in foreground, .xinitrc doesn't finish until the last command finishes.

### Display manager

All these examples so far presuppose the user is already logged into the system. It's also possible to start the X server when the system is booted. In this case, the system behaves much like an X terminal.

A display manager is used to manage one or more X terminals (stand-alone X servers which offer no additional computing resources) or general X servers. It can be thought of as a super window manager which, instead of controlling windows on one server, ensures servers are running and a login window is present whenever the server is not being used.

### 3.2.6 Resources

X programs are customizable in a zillion (10$^{largenumber}$) different ways, which makes it difficult to remember and enter the options in any reliable manner.

As with most Linux programs, the X programs can use both command line options and the environment variables to modify their operation. Another mechanism, that of a resource list, provides more convenient operation.

While many of the X utilities scan configuration files to locate resource definitions, X has extended the idea of configuration files to a generalized database which may be consulted by all X programs.

Any X utility can use the database to locate the necessary properties by sending a query to the X server via library functions. The reply is a “best match” found in the database. (The xrdp program is used to load initial values to the X server. The editres and appres programs can be used to change or display the resources associated with a program.)

Resource definitions take the form:

`name : value`

where “name” has a rather complex form

`object SEP subobject [SEP subobject]* SEP attribute`

where SEP is a “.” or “*”.

Each component of a resource name, the objects and subobjects, refer either to classes or instances of those classes. A class name refers to a class of objects or subobjects, such as buttons or colors, while an instance name refers to a specific object or subobject, such as the delete button or the border color. By convention, class names begin with uppercase letters and instance names begin with lowercase letters. When the “.” is used to separate the objects, the resource is said to be tightly bound. This means that a scans of the data base will require an exact match. When the “*” is use to separate the objects, the resource is said to be loosely bound. Such a resource will be offered as a response to a query which doesn’t match exactly.

These two categories of distinction, class vs instance and loose vs tight, are used to qualify which matching resource is returned in response to a query. The four (or more) possible resources names are chosen by the rules that

-   instance names take precedence over class names
-   tight bindings take precedence over loose bindings

This hierarchy of choice allows a user to specify general characteristics, such as text fonts are to be helvetica, and then override them with more localized characteristics, such as menu fonts are to be Times Roman.

One disappointment is that one cannot determine exactly which resources are used by a given X program. Furthermore, resources which an X program discovers in configuration files are not loaded into the database. This can make it somewhat difficult to determine what really is happening in a system.

### 3.2.7 Fonts

Bitmapped displays offer us new possibilities and new problems. In the past, characters were defined by the hardware. Now they are defined by tables in files. One of the many resource categories deals with the fonts used in the several different parts of a window. An elaborate schema has been defined to allow the client (user application) to specify the desired font with as much or as little precision as desired.

Through the X protocol, the server will advise the client of its ability to honor the client's request use a given font for display.

### 3.2.8 Keyboard Mapping

Another area of great flexibility in X is in the mapping of keystrokes to arbitrary characters. Although an ordinary keyboard has about a hundred keys, it's possible to create many times more distinct characters by using combinations of the different SHIFT, CONTROL, and ALT keys.

This flexible mechanism for binding keys to meanings allow the application designer to rely on lots of specialized keys.

## Chapter 4

## System Kernel Requirements

Chapter 1 listed a number of features possessed by Linux, Chapter 2 has noted some of its antecedents, and Chapter 3 looked at how a user interacts with Linux. In this chapter, we will develop a list of requirements for a system kernel. A checklist, if you will, of what we’ve come to expect of a system kernel. In broad terms, a system kernel must maximize processor availability, protect users from mishap and attack, and provide interactive response and background processing. We can refine some of these requirements by tracing the development of what we call “system kernels” and the rest by noting shortcomings of different systems.

It would be a gross understatement to say the earliest computers were unwelcoming in their operation. Setting aside issues of large physical size, small storage size, modest speed, and low reliability, they still had a large number of architectural shortcomings. The high cost of logic meant they lacked instructions to perform even such common operations as multiplication. Operators had to load individual words of memory via front-panel switches and read results as strings of bits or digits on a display.

Better input/output devices soon appeared, but more importantly, it didn’t take long for the designers to realize the computer itself could be used to make its operation more user-friendly. In 1947, Alan Turing wrote, “There need be no real danger of it ever becoming a drudge, for any processes that are quite mechanical may be turned over to the machine itself[22].”
