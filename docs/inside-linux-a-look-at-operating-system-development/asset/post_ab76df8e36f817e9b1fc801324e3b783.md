Although LILO is described as a Linux loader, it can also load MS-DOS. I've configured my system to boot Linux by default, but it pauses for a few seconds to allow me to override that selection and boot MS-DOS instead.

`/sbin/lilo` does not build pointers to the MS-DOS kernel in the way it does for the Linux kernels. Instead it tells the secondary bootstrap to pass control to another bootstrap program, commonly held in `/boot/chain.b`, which in turn knows how to load and start the normal MS-DOS booting. Another bootstrap program, `/boot/os2d.d.b`, can boot OS/2 from a second hard disk.

## LOADLIN

Cautious users need not disrupt the master boot records (MBR) of their system with the Linux bootstrap loaders. Instead, they can use an MS-DOS-based utility called LOADLIN. LOADLIN runs in the so-called real mode of the x86 family (or with some effort from the v86 mode). It locates the Linux kernel, shifts itself to higher memory (0x90000+), loads the Linux kernel into lower memory, disables all MS-DOS operations, and passes control to Linux.

This places MS-DOS and LOADLIN in the roles of tertiary and quaternary bootstrap code respectively.

### 5.7.4 Network System Startup

It's possible to use the network to load Linux. Some utilities such as etherboot or nfsboot rely on existing bootstrap ROMs, while others use special ROMs.

In any case, the program in the bootstrap ROM broadcasts a request on the local area network (LAN) for help. A server system recognizes the request and replies with an image to load.

Once the kernel is loaded, the system startup proceeds normally, with the use of the NFS-mounted file system instead of hard disk-mounted file system as the only unusual aspect.

# Networks

It isn't clear whether network support belongs inside or outside the kernel. Arguments can be made for either case. In the case of Linux (and most Unix systems), major elements of the networking code reside inside the kernel and other elements are user-level programs.

## 6.1 User Process vs. Kernel Feature

Although it is not really necessary to access the network hardware from within the kernel, it does improve performance quite a bit to put the lower layers in the kernel. Layers will be discussed in the next section, but suffice it to say that the closer the code is to manipulating the raw hardware, the stronger the case for kernel mode code.

As the layers move away from the hardware, it becomes more practical to execute the code as a user process.

## 6.2 Advantages of ISO OSI Model

The International Standards Organization (ISO) developed a model called the Open Systems Interconnect Reference Model. It describes a network in terms of seven layers such that any layer is described in terms of its interface with adjacent layers.

- *Application Layer* consists of application programs that use the network
- *Presentation Layer* standardizes data presentation to the applications
- *Session Layer* manages sessions between applications
- *Transport Layer* provides end-to-end and error detection and correction
- *Network Layer* manages connections across the network
- *Data Link Layer* provides reliable data delivery across the physical layer
- *Physical Layer* defines the physical characteristics of the network media

This model is quite useful in that it captures what has been learned about implementing networks—keep the pieces (layers) small enough so that they can be understood, analyzed, and implemented correctly. Figure 6.1 captures the essence of this idea by showing how each layer adds or subtracts its own header (PREFIX), which can sometimes contain some trailing bytes as well (SUFFIX), without disturbing the encapsulated data.

The data from the application layer are surrounded by control bits from the presentation layer, which are in turn surrounded by control bits from the session layer, etc. Upon receipt, the outermost bits are stripped off by the data link layer, the next outermost bits are stripped off by the network layer, etc. Each layer is concerned only with the control bits (often seen as a header) for its layer and is oblivious to what is contained inside. The advantage in this idiom is that a different instance of a layer can be substituted without disrupting other layers, e.g., the Ethernet Data Link and Physical layers can be replaced by Token Ring without affecting the other layers. The physical layer is not shown in this figure because it rarely adds any header. Instead it describes how a stream of bits are represented as some kind of signal,

The ISO OSI model was created after the start of the Internet, so it should come as no surprise to discover that the Internet cannot be described exactly in terms of this reference model. Nonetheless, the model of layering protocols around/within other protocols has proved to be most useful.

## 6.3 The Internet Model

There is no universal agreement on how to describe the Internet implementation in terms of the reference model, but nearly everyone agrees the seven layers are a bit excessive. Generally the seven layers are reduced to the four layers corresponding to the major parts of most implementations.

- **Application** — the Application, Presentation, and Session layers of the OSI model
- **Transport** — roughly the Transport layer of the OSI model
- **Internetwork** — roughly the Network layer of the OSI model
- **Network Access** – the Physical and Data Link layers of the OSI model combined into one layer

Linux implements the transport, internetwork, and network access layers inside the kernel. The transport layer is used by processes which implement the application layer. Other special processes use the network and network access layers to implement higher level protocols (which are experimental in nature or don’t require especially high performance). It was mentioned earlier, but it bears restatement: there can be many different implementations of any given layer. For instance, implementations of the Application, Transport, Internetwork, and Network Access layers could consist of telnet, TCP, IP, and Ethernet in one case and http daemon, UDP, IP, and SLIP in another.

The Internet protocols are defined by a number of standards with the humble phrase "Request for Comments" in their titles. Each addresses some topic as a position paper, protocol specification, or catalog. They are now published by the Network Working Group and many RFCs are available on CD-ROM or by ftp on the Internet as text or Postscript files.

The following three subsections discuss common configurations for the Transport and Application protocols. After this first look at the middle part of this model, we’ll look at the top and bottom ends. Application and Network Access.

### 6.3.1 TCP/IP

The *Transmission Control Protocol* (*TCP*), defined in RFC 793, and the *Internet Protocol* (*IP*), defined in RFC 791, are regarded as the core of the Internet.

The IP protocol ensures that datagrams (or packets)—a collection of bytes as shown in Figure 6.2—are routed from the source node to the destination node. Critical parts of the protocol are that:

- Each datagram holds 32-bit source and destination addresses. This is sufficient to address 4,294,967,296 different nodes.
- Each datagram identifies the protocol to be used to process the data contained within.
- Datagrams can be broken into smaller datagrams while in transit. The identification, length, flags, and fragment offset can be used to reassemble these fragments at the destination.
- A checksum ensures that the data are not corrupted.
