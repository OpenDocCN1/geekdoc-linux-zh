# **Avoiding busy waiting**	All of the above examples implement *spin-locks*, semaphores with some form of busy waiting. If the waiting intervals are short enough, and if one has some kind of multiprocessor, busy waiting isn't that harmful. In many cases it is more efficient than any other semaphore implementation. Unfortunately, when these preconditions are not met, disaster easily results.

# **Short delay, multiprocessor**	This is the most benign use of busy waiting. One processor may be blocked, which blocks one processor while the process' time slice is expired, but other tasks on other processors will be able to execute (and presumably, they will be able to clear the semaphore).

Lamport has shown benefit in exploiting the likelihood that a semaphore will be free[28]. His algorithm, shown in Figure 5.12, can securely enter a critical section after only five references to shared memory. This means that rarely needed semaphores, i.e., those which rarely result in blocking, have little cost to system performance.

There are some subtle hardware issues to consider with high-performance, cache-memory systems. Schimmel offers a much more complete discussion of the changes needed to code used on multiprocessor systems[45].

# **Short delay, uniprocessor**	Software based semaphores are still appropriate if the semaphore is rarely used or the critical section is very small. The danger is that the algorithm presented above offers no chance for the semaphore to be cleared. Control *must* be passed to other tasks.

# **Long delay**	If a process is blocked at a semaphore, the blocked process will waste processor power during its slices of time until the semaphore is released. Other tasks will be able to run on that processor only when the blocked process' time slice expires and a preemptive context switch occurs.
