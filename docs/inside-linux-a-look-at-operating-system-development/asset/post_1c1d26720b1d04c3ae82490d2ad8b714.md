```c
semaphore_N = 1;
void P(int *X) { while (*X <= 0) ; (*X)-- ; }
void V(int *X) { (*X)++ ; }
```

The argument to each of these operations is the semaphore (from Greek words for sign ($\sigma\epsilon\mu\alpha$) and bearer ($\phi\acute{o}\rho\varepsilon\acute{\upsilon}\sigma$)) associated with the specific data being protected.

The idea is that when the first process enters its critical section, this semaphore value is reduced to zero. If a second process attempts to enter its critical section before the first process restores the semaphore value to 1, the second process will wait until the first process restores the semaphore value to 1.

There are two significant flaws with these definitions. The first is that both the P subroutine and the V subroutine themselves contain references to shared data (the value X). This means that P and V require P and V to operate -- a recursive spiral from which the implementation must escape. The second is that the P operation uses a busy wait which doesn't relinquish control to another process.

Nevertheless, this was a remarkable contribution. It provided designers with a simple mechanism to ensure consistent results: implement P and V correctly and wrap critical sections with P and V.

Let us see how the two flaws can be addressed.

### Making P and V correct

The programmer's favorite approach is to make it the hardware designer's problem. We'll first look at how hardware can support implementations of semaphores and then how software alone can be used.

### Processor implementation

A number of systems provide instructions which automatically update a word in memory. These instructions not only cannot be interrupted, but they hold the bus so that another processor cannot modify the word.

For example, the Motorola MC68040 and the IBM 370 architectures offer a *test-and-set instruction* which reads a value from memory, compares it to zero (and sets a condition code) and sets it unconditionally to one. Our semaphore operations would now look like:

```c
semaphore N = 0;  
void P(int *X) { while (test_and_set(*X) == 1) ; }  
void V(int *X) { *X = 0 ; }
```

Another common atomic read-modify-write instruction is the *swap instruction* found in the SPARC and the Motorola MC88100 processors. By swapping whatever is in memory with the value 1, one can mimic the test-and-set instruction above. (You'll note that because of the RISC architecture, the compiler will have to store the returned value and then explicitly test it.)

```c
semaphore N = 0;  
void P(int *X) { while (swap(*X,1) == 1) ; }  
void V(int *X) { *X = 0 ; }
```

The DEC PDP-11 has *increment* and *decrement* instructions with atomic read-modify-write behavior. The condition code is set based on the value written. The following code has a counting semaphore which can also control the number of processes permitted to enter the critical section. The semaphore is merely set to the negative of the number of processes permitted in the critical section. A positive value represents the approximate number of processes waiting to enter the critical section. (If you’ve ever been to a *very* popular drinking or dancing establishment, you’ll see this as an analog to the bouncer counting patrons entering and exiting.)

```c
semaphore_N = -1;
void P(int *X) { while (!increment(*X)) decrement(*X);}
void V(int *X) { decrement(*X) ; }
```

### Memory implementation

The Sequent Balance and Symmetry systems provide a bank of semaphore memory which aid processors without atomic read-modify-write instructions. When the processors read from these special locations, a test-and-set operation is performed *in the memory* and the appropriate value is returned. The process which *acquired* the semaphore must later write to that location to release the semaphore.

The Tera MTA provides a semaphore per word of memory called the “*empty*/*full*” bit. The system has the usual *load* and *store* instructions. It also has *load_if_full* and *then mark empty* and *store_if_empty* and *mark full*. These special instructions effectively perform a busy-wait if the memory word’s semaphore is in the wrong state.

### Software implementations

Not all systems provide such convenient support for semaphore implementations. In those cases, the programmer must rely on software implementations of semaphores which require only shared memory.

One example is Dekker’s algorithm, but this algorithm was improved by Peterson and others to operate in an environment with two or more *competing* processes and to operate without busy-waiting[11, 38]. The basic form of most of these are:

- 1. place a claim for the semaphore and then
- 2. check for claims made by other processors.

If no other claims are found, the critical section may be entered. If there *are* other claims, additional steps must be performed to determine when the critical section is free.

### Avoiding busy waiting

All of the above examples implement *spin-locks*, semaphores with some form of busy waiting. If the waiting intervals are short enough, and if one has some kind of multiprocessor, busy waiting isn't that harmful. In many cases it is more efficient than any other semaphore implementation. Unfortunately, when these preconditions are not met, disaster easily results.

#### Short delay, multiprocessor

This is the most benign use of busy waiting. One processor may be blocked, which blocks one processor while the process' time slice is expired, but other tasks on other processors will be able to execute (and presumably, they will be able to clear the semaphore).

Lamport has shown benefit in exploiting the likelihood that a semaphore will be free[28]. His algorithm, shown in Figure 5.12, can securely enter a critical section after only five references to shared memory. This means that rarely needed semaphores, i.e., those which rarely result in blocking, have little cost to system performance.

There are some subtle hardware issues to consider with high-performance, cache-memory systems. Schimmel offers a much more complete discussion of the changes needed to code used on multiprocessor systems[45].

#### Short delay, uniprocessor

Software based semaphores are still appropriate if the semaphore is rarely used or the critical section is very small. The danger is that the algorithm presented above offers no chance for the semaphore to be cleared. Control *must* be passed to other tasks.

#### Long delay

If a process is blocked at a semaphore, the blocked process will waste processor power during its slices of time until the semaphore is released. Other tasks will be able to run on that processor only when the blocked process' time slice expires and a preemptive context switch occurs.

#### The solutions

The examples above do not offer any way for control to switch to another process if a semaphore is busy. Such a switch can come in two forms: one keeps most of the semaphore in user space, the other integrates the semaphore within the kernel.

```c
int intend_to_enter[NUM_THREADS+1];
int  requested_by, in_critical_section;

start:
    intend_to_enter[current_proc] = true;
    requested_by = current_proc;
    if (in_critical_section != 0){
        intend_to_enter[current_proc] = false;
        await (in_critical_section == 0);
        goto start;
    }
    in_critical_section = current_proc;
    if (requested_by != current_proc){
        intend_to_enter[current_proc] = false;
        for(j = 1; j <= NUM_THREADS; j++){
            await (intend_to_enter[j] == false);
        }
        if (in_critical_section != current_proc){
            await (in_critical_section == 0);
            goto start;
        }
    }

/* critical section code */

in_critical_section = 0;
intend_to_enter[current_proc] = false;
```
