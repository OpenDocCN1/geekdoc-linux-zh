# 4.1.1 Multitasking

Since the user can't always arrange to have alternate work to do while I/O is in progress, later versions of batch operating systems were extended to serve concurrent batch jobs. Since one design goal for a system kernel is to maximize processor use, the scheduler switches between jobs whenever the active job must wait for I/O to complete. Figure 4.1c shows how the execution of two jobs can be overlapped so that their total running time is reduced. In this simple example, you can see that both computing and I/O are nearly continuous. The terms *co-routine* and *co-operative multitasking* are applied to a scheme where each job runs until it is has to wait for I/O to complete (or it reckons it has had its fair share) and then control is passed to another job.

# Co-operative Multitasking

Traditionally, programs were executed as subroutines under the control of a master program: one after another or concurrently, but always independently of one another. Conway introduced a critical notion that two programs can work in co-operative alternation. “... co-routines are subroutines all at the same level, each acting as if it were the master program when in fact there is no master program”[10]1.

The initial parallelism is often established by a subroutine call (shown as the first dark arrow in Figure 4.2) from the parent routine (P1) to the child routine (P2). Thereafter, instead of performing some form of *return* statement, the programs perform a *resume* statement (shown as the lighter arrows in the figure) whenever they wish to pass control back to the other routine. This statement preserves the state of the program so that it can later continue where it left off. The trampoline code in Figure 5.5 gives some idea of what the *resume* statement does.
