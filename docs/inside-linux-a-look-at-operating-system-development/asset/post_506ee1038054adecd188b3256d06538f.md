
format an output string, compute the sine of an angle, open a display window, etc., instead of rewriting these subroutines each time they are needed.

The executable image is created and moved to memory in stages: first the program source is compiled to an object file, then the necessary libraries are consulted to provide the support code. These subroutines can be bound to the user code in several different ways and at different times. The linker can bind the library code to the user program (1) while the executable is being built, or the loader can bind the library code to the user program (2) when it is loaded into memory, or the loader can bind the library code to the user program (3) at each reference to the library code. This last method of binding is called “dynamic linking”, “dynamic loading”, or sometimes “dynamic libraries”.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_48_0.png)

By delaying binding until the program is executing, dynamic linking provides an opportunity to (1) use only the latest version of the library and (2) share the library code among programs.

An early version of dynamically linking to libraries can be attributed to Multics.

Linux has supported dynamically linked libraries for some time. Details are discussed in Section 7.1.2.

### 2.1.5 System Kernel Written In a High Level Language

This was a mixed blessing. It was widely held that programmer productivity was higher for high-level languages than for assembly languages (since verified by Jones[26] and others). The Multics project would gain tremendously by using PL/I instead of using an assembler.

However, PL/I is a *very* complex language. Since there was no PL/I compiler for the GE 635/645, one had to be written. Because of failures by sub-contractors, a real compiler wasn't ready until 1970, but a back-up plan produced a limited compiler in 1966.

It's worth noting that the early implementations of Unix systems were in assembly language. There was a B interpreter on the PDP-7, but a C compiler as we know it didn't appear until 1972—well after Unix had been implemented on the PDP-11. And it wasn't until 1973, with the addition of data structures, that it was possible to re-write Unix in C.

## 2.2 Unix

In 1969, Bell Telephone Laboratories withdrew from the Multics project. A number of conjectures have been offered for this action, but it is clear that this large time-share system offered limited value to Bell Labs. The hardware was very expensive and the performance was very low.

Whatever the reason, a number of participants remained interested in creating a versatile operating system. Their informal discussions included the essentials: simple process creation, file system structure, user level command interpreter, and tasking model. These discussions led to small test programs which grew into bigger projects and finally into Unix.

Ritchie and Thompson describe Unix as:

> a general-purpose, multi-user, interactive operating system for the larger Digital Equipment Corporation PDP-11 and the Interdata 8/32 computers. It offers a number of features seldom found even in larger operating systems, including:
> - A hierarchical file system incorporating detachable volumes
> - Compatible file, device, and inter-process I/O
> - The ability to initiate asynchronous processes
> - System command language selectable on a per-user basis
> - Over 100 subsystems including a dozen languages
> - High degree of portability[43]

Since Unix was used to develop Unix (once the bootstrap phase was complete), the developers built tools that aided them in building a better operating system. These tools included editors, compilers, compiler development tools, macro processors, and command line interpreters.

Building such tools was interesting, but Unix had to pay its way. The first official use of Unix was to do text processing for the patent application office at Bell Labs. For this reason, text processing tools were developed early in Unix’s life. By this, I mean tools to fill text, justify lines, highlight and underline words, build indexes and tables of contents, etc. Additional tools could locate strings of text from files, sort files on a line by line basis, extract information for reports, etc.

### 2.2.1 Low Cost Hardware

In 1960, Digital Equipment Corporation (DEC) introduced the PDP-1. At a price of $120,000 (compared to millions for other systems), it was a bargain. DEC firmly established itself in the field with further low-cost systems.

Unix was first implemented on a cast-off PDP-7, but once the basics were demonstrated, official support (in the form of $10K) was found to purchase a PDP-11/20.

For years, Unix was associated with the PDP-11. Although there were other inexpensive mini-computers on the market, the main point is that Unix was not initially targeted for the mainframe computers of the day.

(The reader should not assume that Unix is only for low cost systems. It has since become the favored operating system for high-end systems. For example, Unix will be the primary system interface for the Tera MTA to be shipped in 1996. The MTA design has an upper performance limit of 256 GFlops.)

### 2.2.2 Redirection

Redirection is a useful side-effect of the “Compatible file, device, and inter-process I/O” cited above. Since a program uses the same calls to write to a file, a terminal, or a printer, it is a simple matter to allow that output to be redirected without the knowledge of the program. At the shell (command interpreter) level, this is expressed by the notations `program > new destination file` and `program < new source file`. The program is unaware its input or output has been redirected.

### 2.2.3 Pipes

Pipes are a software construct used to direct data flow from one program to another.

Long before the invention of pipes, two programs could interact when the output of one was used as the input to the second. Commercial data processing was quite accustomed to this model, even when punch cards were the dominant form of storage. The operator just had to shift the cards from the output hopper to the input hopper.

But this early form of program interaction suffered two handicaps: the specification of this operation on the command line(s) is messy and one has to complete one program before the other can start. Typical data processing leads to the command sequence:

```
command1 > temp_file
command2 < temp_file
```

where the output from `command1` is to be used as the input to `command2`.

A pipe permits the user to effectively combine these two command sequences into the one line:

```
command1 | command2
```

which still says the output from `command1` is to be used as the input to `command2`, but an internal buffer, rather than a file, is to be used to convey the data. Furthermore, the two commands execute simultaneously.

It is worth noting that the implementation of pipes in MS-DOS doesn't support simultaneous execution. The first MS-DOS program runs to completion, writing to a hidden file; then the second program starts, using that hidden file for input. The only benefit is the more convenient notation.

Unix fully supports the idea that two programs can work in cooperation using a buffered communication path to carry output from one program to become input to another program. This is explored more fully in Section 3.1.1.

### Binary infix notation

When Unix was being initially designed, some initial discussions suggested commands themselves should be considered binary operators. For example, the command line:

```
inputfile sort paginate print
```

would print a paginated sorted image of the input file. Since redirection was already an established Unix feature, this form was transformed to something like:

```
sort inputfile > paginate > print
```

where the destination of a redirection was executed if it was a command or it was used as a destination if it was a file.

These experimental forms quickly moved to the use of a distinct character, “|”, which joined two programs such that the output of one program is to be the input of the next program.

```
sort inputfile | paginate | print
```
