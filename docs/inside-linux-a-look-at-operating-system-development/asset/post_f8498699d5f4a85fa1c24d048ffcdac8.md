## 5.2 Process Control

Processes can be regarded as the raison d’être of a system kernel. We’ve seen how most everything else can be accomplished in a run-time library.

### 5.2.1 The Nature Of a Process

The classic definition of a process is “a program in execution”. The snapshot of this process in Figure 5.3 shows several components defining the state of the running program’s execution. These components are explained in the following paragraphs.

Besides the code component (which, incidentally, may be shared with other processes), the state of a process is defined by the value of all its data.

The operating system requires a modest amount of data to control each process. Although these data are maintained in an area of memory generally not accessible to the process, they are an essential part of the process state. They are used to record resource consumption (for billing and management), control peripherals and file access, manage the rest of the process’ memory, point to *semaphores* controlling access to critical sections, etc.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_138_0.png)

REGISTERS are the most volatile part of the process state. In addition to the instruction pointer (IP)⁴, the processor holds a number of accumulator registers, index registers, and status registers. When the process is running, the registers are undergoing constant change. When the process stops running, the values of the registers are saved so that they may be restored to the registers when the process resumes execution. A reference to the value of a register means either the value in the register when the program is running or the saved value when the program is not running.

Almost all computers have a region of memory called a STACK. A special index register, called the stack pointer, is often used to access this memory. The stack is heavily used during subroutine calls: first the arguments which don’t fit in registers are pushed onto the stack, then the return address is pushed onto the stack, finally space is reserved on the stack for temporary storage to be used by the subroutine. Each such chunk (arguments, return address, local variables) is called a *stack frame*. This stack growth is supported in the system kernel by extending the stack component as needed. (Shown by the arrow in the open side of the stack component.) Some systems will reclaim this space as subroutines return and the stack shrinks; others do not.

At least that is the general idea. Many Unix implementations rely on a common architectural feature: there are multiple modes of operation and the user mode can be switched without affecting the privileged mode of operation. We’ve seen in Section 5.1.2 how a system call leads to a privileged mode of operation. Once in this privileged mode, the kernel code can change the parameters of the user mode of operation as easily as it can switch the stack pointer from one process’ stack to another. The real distinction among processes is held in the other registers, including the stack pointer and the memory management registers.

In the implementation of Linux for the x86 architecture, the bounce point uses a single instruction which saves all the registers in the current task state segment (TSS) and retrieves new register values from the new TSS. Because the instruction pointer (IP) is one of those registers, and the same trampoline code is used for all context switching, the instruction pointers saved in all the TSSs have the same value.

## User Threads

A thread is a process-like entity which shares much of its context with its siblings. Because of this sharing, switching among sibling threads involves less data manipulation and therefore less time than for heavyweight processes. (If threads cost as much as processes to context switch, there would be no use for threads.) The switching between threads can be co-operative or preemptive, but in any event, the whole process is subject to preemptive scheduling.

This low cost switching makes threads ideal for a tightly-coupled set of subroutines working on a common problem, perhaps created implicitly out of the source program. Little performance is lost, yet the programmer is able to express a solution which better matches the problem.

Threads can be implemented in several ways—entirely as user code, with kernel support, or entirely within the kernel.

The pthreads project has developed user level multithreading for Linux. It is derived from a portable implementation, called C-threads, which runs on a number of Unix systems.
