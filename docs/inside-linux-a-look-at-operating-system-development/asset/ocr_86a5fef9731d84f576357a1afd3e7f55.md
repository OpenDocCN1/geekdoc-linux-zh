ELF files begin with the magic word 0x7f 0x45 and continue spelling out “ELF” followed by version numbers and such.

The Linux kernel has been designed for easy expansion of support for various object file formats. If it fails to find the #! magic word, it enters a loop which calls a test routine for each supported object file format. If any test routine succeeds, the appropriate code is used to load the executable.

# Example

At the beginning of Chapter 5 we glossed over how the “hello world” program shown in Figure 5.1 would be turned into an executable image. In this section we will follow the steps in a bit more detail.

To begin with, although command gcc hello1.c produces a file titled a.out, the user should be aware that the name is only a convention, not an indication of the type of the file. Depending on compiler options or defaults, this file can just as easily be in ELF or a.out format.

The gcc command hides several subordiant commands which can be invoked by the main command: the preprocessor, cpp, the compiler proper, cc1, the assembler, as, and the linker, ld.

The preprocessor has no real knowledge of C. It is a simple macro preprocessor which acts on simple directives such as #include, #define, and #ifdef. Its output stream has substituted all the macro definitions and symbolic constants and has stripped all the comments out of the way for the compiler.

The compiler reads the clean C code and produces assembler code. This process can involve several distinct phases of optimization to produce faster and smaller code.

The assembler reads the assembler code and produces an object file which has a multitude of unresolved references to externally defined symbols.

The linker gathers code from one or more libraries to satisfy the unresolved references.

The resulting a.out files are dramatically different. The size difference of 15388 to 3916 is because the larger a.out format file has all the library code bound to it by default and the ELF format file relies on dynamically linked library code.
