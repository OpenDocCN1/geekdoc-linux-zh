
There is sufficient redundancy in the file system that common failures can be discovered by examining a file system before it is mounted. For instance, the inodes can be examined to build trial copies of the bitmaps, and discrepancies with the bitmaps on disk indicate some failure. Similar checks will discover duplicate references to data blocks, cycles in the directory structure, and inodes which have been allocated but are not linked to the directory structure.

The Berkeley Fast File System offered a number of significant improvements to state-of-the-art in Unix file system implementations. One of the major new features was that it split the partition into several chunks called block groups, each with an almost file system-like structure. Each block group held a copy of the superblock and a share of the data blocks, inode table entries, and the associated bitmaps.

This meant that not only could a file's data blocks be clustered in a neighborhood, but its inode and bitmaps could be in the same part of the disk. This change allows the kernel to further exploit the nature of references to file system data, called locality of reference, whereby references which are close in time tend to be close in location.

The ext2 file system follows the Berkeley Fast File System model for block groups. Figure 5.19 illustrates how the partition is split into block groups, each of which contains a replicated superblock (SB), some portion of inodes and data blocks, and bitmaps (BM) showing which inodes and data blocks are in use.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_173_0.png)

Figure 5.19: ext2 file system structure

Additional operational data include the maximum and current counts of inodes and data blocks and the size of data blocks and data block fragments.

The mkefs utilities (one for each file system type) are among the few utilities which directly access the raw disk. `mke2fs`, unless directed otherwise by command line options, starts with basic information about a partition and determines the number of block groups and inodes to be allocated. A few of these parameters can be changed after the file system is created. These include how often a file system check is recommended, how many blocks are reserved for root-only use, and how errors are to be treated.

## 5.3.2 File System Implementation

Linux differs from early Unix implementations in that it has fewer hard limits and fixed tables in the kernel. For instance, the maximum number of open files in the system is set at the start, but only as a variable which could be later changed. Likewise, the mount points are held in a linked list of dynamically allocated structures. Along this vein, the number of files which a process can have open is set by a parameter which is part of the file system. (This is the POSIX behavior.)

All this means it's a bit more difficult to point to a declaration in the kernel and say “That is where all the details are stored.” But there are a few fixed points. In the case of I/O, there are two tables in `linux/fs/devices.c`, `chrdevs` and `blkdevs`, which hold details of operations supported by each of the devices in the system.

### Run-Time Library I/O Support

It should be mentioned in passing that the run-time library provides a layer on top of the basic file operations. Some of the most important functions in this library, such as `printf` and `scanf`, provide buffering and formatted I/O. The basic calls, such as the `read` and `write` discussed below, side-step this formatting and buffering.

### Virtual File System

This term describes a method of accessing all the different file systems supported by Linux in a uniform manner. There is no single file system, but it appears that way to the programmer.

Every time a file name is processed, the kernel identifies the partition in which it resides. It thereafter calls upon file system dependent routines to perform details which vary from one file system implementation to another.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_175_0.png)

Figure 5.20: File system layers

This, and other indirection inside the kernel file system code, becomes the “virtual file system”.

The utility of this is the ease with which new file system implementations can be added to the kernel. The only time the file system type is visible is when a partition is mounted. Thereafter, the file system specific code is accessed indirectly through pointers in inodes. This hierarchy is suggested in Figure 5.20.

### The open call

The `open` call turns a pathname[^1] and access arguments into a file descriptor, a small, non-negative integer which is used as an argument to the other I/O calls. This is done in two steps.

[^1]: This is the *entire* file name, including any leading directories, not just the root part.

The `namei` function within the kernel first takes the leading part of the file pathname and returns the inode of the parent directory. (If that directory cannot be located, the open fails.) If the pathname starts with “/”, the search is started from the inode noted as that process’ root directory, if not, the inode noted as the current working directory is used as the starting point.

Each directory in the search path must be accessible to the process, i.e., the program need only reference specific directories or files within each directory in the search path. This capability is noted by execute bits which apply to the user, members of the group, or others. The permission conveyed by these execute (access) bits is distinct from the permission to read the contents of a directory conveyed by the read bits.

Once that parent directory’s inode is identified, the desired directory’s or file’s inode is found or created.

When files are created, they normally acquire the owner and group of the process which created them. But if they are created in a directory which has the SGID bit set, files acquire the group of the directory in which they are created. [^2]

[^2]: I’ll leave it to others to determine if giving different meanings to the execute and SGID bits is good practice or not.

The rest of the code in `sys_open` and `do_open` notes the inode and other information in a structure, and a pointer to that structure is placed in the file descriptor table.

### Other I/O calls

The file descriptor is used to index into a per-process set of structures that hold information about that file’s use as well as an indirect index into a system wide set of structures regarding that file.

It indexes into a per-process table which in turn leads to an element of a linked list of structures, one per open file on the system.

These structures are accessed through one level of indirection—the virtual file system mentioned above.

Once a file has been opened, the application program moves to the desired offset (using `lseek`) and reads or writes a stream of bytes. The system kernel imposes no structure on the file, e.g., lines or records. This allows (requires) the application to interpret the data as appropriate.

The file system dependent code will ensure that data blocks will be allocated (and so noted in the bitmap) and data will be written to the correct place on the disk. In a similar manner, that code will locate the correct data block for read operations.

### Device handlers

Just as files can be opened, closed, read and written, the user can access devices using the same system calls.

The devices appear as entries in the file system, typically with names such as /dev/hda0, /dev/sda0, /dev/cr0, /dev/tty0, etc. Because the file type is character or block I/O, some of the rest of the fields in the inode have different meanings. For instance, instead of showing the file's length, the inode holds what is called the major number and minor number for the device. The major number identifies which device driver inside the kernel will process the system calls and the minor number identifies which port, partition, or other subcategory of the device is being accessed.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_177_0.png)

Although the file system code is normally the only code which accesses the disk, privileged users have direct access to block I/O (structured I/O) devices as well as character I/O (unstructured I/O) devices. More commonly, device access is to serial ports, keyboard and console, tape drive, floppy drive, line printer, etc.
