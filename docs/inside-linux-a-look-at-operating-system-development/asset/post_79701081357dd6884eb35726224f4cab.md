### 4.5.2 Authentication

The previous section spoke of UIDs and ownership without any mention of how identity is established. The identity of a process is almost always inherited from the parent process (or in the case of set UID feature described in Section 2.2.5, the ownership of a file).

In rare cases a process has authorization to change the identity of a process or the ownership of a file, but it will do so only if the requesting agent satisfies an authentication protocol.

First, a claim is made as to the identity. (We do not deal with systems where the identity is derived rather than asserted.) Authentication is then based on different methods of validation. These methods are based on:

- What you *know*
- What you *have*
- What you *are*

#### What you know

In the case of a user logging into the system, a login program will ask for a user name and password. If the password is correct, it will create a shell process for that user with that user's UID.

#### What you have

A locked front panel is a good example of a system requiring presentation of some object. You can access protected functions, such as the restart button, only after you've proved your identity by using the key.

#### What you are

The third class of authentication systems rely on biometric characteristics which tend to be unique for each person. Commonly used characteristics are fingerprints or retinal patterns, but other systems measure hand shape, voiceprint, keystroke latencies, the dynamics of your hand-writing, etc.

### Combined methods and secondary methods

These methods can be combined to build more robust systems. There are also systems which use secondary methods of authentication, so called because one of the primary methods of authentication must be used to acquire them.

**Bank cards**  
Bank cards combine what you have and what you know. Teller machines require the user to present a card and then provide a personal identification number (PIN). Neither of these alone is sufficient.

**Where you are**  
Some systems permit privileged access only from a terminal in a secure area. Since primary methods of authentication are used to secure that area, access from that terminal is a secondary method of authentication.

In the case of many systems, physical possession of the hardware is regarded as authentication for the most privileged (root) account, or at least physical possession permits an intruder to override authentication systems. **Linux users beware! Your system can be compromised by anyone who has physical access to your system.** At the very least, an intruder could reset the processor. A more sophisticated intruder could reboot the system in single user mode, add entries in the password file, reboot the system and enjoy the newly created accounts. These steps can be made more difficult by using an encrypted file system, such as mentioned on page 82, to deter the single user mode of operation mentioned above. It would also be possible to design bootstrap procedures which required passwords, but this hasn't yet been done.

**What you have/know—part 2**  
Authentication systems such as Kerberos<sup>8</sup> issue a ticket (or key) which then is presented as authentication to ordinary applications which have been modified to accept the ticket. These systems use one or more of the primary methods of authentication before issuing the ticket. Thereafter the ticket is considered sufficient for authentication in lieu of further login steps. Kerberos' principal advantage is that it is designed to be secure even when used on unsecure links. Some call these tickets “magic cookies”.

The programmer sees a system kernel from a different perspective, one based on the system calls which can be made from within a program. ## 5.1 User Interface

Every computer has some undesirable aspect to it, e.g., it has a difficult-to-program peripheral interface, it is missing a time-of-day clock, it has a limited command set, etc. Pity the poor programmer who has to use such a bare-bones system! Fortunately these rough edges can be smoothed with the use of a system kernel with a good run-time library. The programmer can then call subroutines to perform high level abstractions, such as “set clock” or “read from a file” without becoming involved in the details of device registers, command sets, file system implementation, etc.

From the programmer’s viewpoint, it doesn’t matter if the calls are to a run-time library or to the system kernel. It’s even possible that subroutines could be moved from the run-time library to the system kernel or from the system kernel to the run-time library without the knowledge of the user.

Although all that matters to the user is that there is a well defined set of calls to perform the desired operations, the compiler writer and the system implementor must know these details. In addition, the location of the boundary is important to security—the kernel is often permitted to do things a user must not.

Unix was designed so that the data used to control the process are out of sight from the process. Richie and Thompson noted that:

> there are no “control blocks” with a complicated structure partially maintained by and depended on by the file system or other system calls. Generally speaking, the contents of a program’s address space are the property of the program, and we have tried to avoid placing restrictions on the data structures within that address space[43].

This isolation model is followed in Linux.
