## Network Files

There is really no need for the file data to reside on the same computer upon which the application is running. The concept of a file system as “a provider of file data” can be abstracted to the extent that the user of that data cannot easily tell where the data are physically stored.

### Issues

When considering files on a network, there are some issues which we must keep straight in our minds. At the minimum, we must distinguish remote file transfer from remote file access. The former copies a file from one system to another using some special application package. The latter is intended to make the access of network files transparent to the user.

This dichotomy is spoiled by the presence of so-called *file caching* systems which may copy an entire file and keep the copy, but the access is *as if* it were to a remote file.

### Naming

One basic issue is the question of “how much of the network is visible to the user?”

It’s possible to design a system such that the user cannot tell where a file is located. The competing notion is to make the file’s location part of the file’s name. We’ll see examples of each in the following paragraphs.

A somewhat parallel issue is how the name of a file changes as the user’s location changes. With peer-to-peer file sharing, it’s possible to have a file local to one user and remote to another. If the file naming is independent of location, scripts which refer to such a file need not change because they are executed on different systems. Of course, this means the local user will be required to use the same longer name which everyone else uses. Systems such as Network File System and the Newcastle connection support both naming conventions.

### Level of implementation

The network file access can be supported from within the kernel or it can be provided by some user level program. Kernel support generally implies higher performance, while user level support provides greater flexibility. (It’s worth noting that opposite decisions can be made at either end of the client/server connection.)

### Peer-to-peer

Some models of network file access have a single file server and all other systems are clients. Other models allow for full symmetry so that any system can act as a client, a server, or both a client and a server.

Normally a directory entry "." refers to the current working directory and ".." refers to the parent of the current working directory. The only exception is when "." is used at the root directory; for practical reasons this also refers to the root directory.

The Newcastle design changes part of this last convention, so that a leading "/..//" in a file name indicates network access. Since most systems at the time of its distribution had only static linking, utilities had to be rebuilt to use the Newcastle connection[8]. This disadvantage was balanced by the fact that the kernel did not have to be modified.

### Network File System

Sun Microsystems developed a remote access file system which has become the standard among Unix-based systems. The client side is implemented inside the kernel, which yields slightly better performance and the file naming mechanism keeps all “network awareness” from the user program.

Most of the performance comes from the integration of internal buffering with the actual network file system.

The file naming mechanism is just a generalization of the local file system. File systems which are exported from a remote system are mounted as if they are local disk partitions.

One common use is for a file server to hold all user home directories and to export them to all client systems where they are mounted as “home”. In this way the location is transparent to all users and all user home directories have the same name regardless of the system from which they are accessed.

The design of NFS prompted a significant change in most kernels. Whereas before the file system and the kernel were very tightly coupled, the introduction of NFS prompted the creation of a virtual file system layer which redirected file manipulation system calls to the local file system code or the network file system code. (This was discussed in Section 5.3.2.)

## 5.3.5 Peripheral Access

Linux permits peripherals to be accessed as devices named in the file system. For instance, when the open system call is applied to /dev/tty0, /dev/lp, /dev/mouse, and /dev/ttyS0, the user gets direct access to the first virtual console, the printer, the mouse and the first serial line, respectively. The user can then use read and write for input and output, and the special system call ioctl is used for special operations.

Non-portable (and privileged) code can access some devices by way of reading and writing device registers through the I/O port or memory windows. While it may provide higher performance, such practices are discouraged.

Video I/O is commonly performed in this manner, although the GGI[23] project intends to offer a more protected access to the display.

## 5.4 Memory Management

Once the system kernel has been loaded, all unused memory becomes a resource which can be shared among the processes. (In the case of some micro-kernel systems, the rest of the kernel will provide additional processes competing for the dynamically allocated memory.) Memory use falls into two general categories: that which is visible to the processes and that which is used on behalf of the processes.

### 5.4.1 Virtual Memory

Any virtual memory system must be built from a set of resource allocation policies which decide when to bring a page into memory (Fetch), where to put it (Placement and Replacement), when to write dirty pages to storage (Cleaning), how much physical memory a process is allowed (Allocation), and how many processes can share the system (Load Control).

#### Fetch

The most common fetch policy is *demand paging*. This policy loads a page only when it is required. Locality of reference suggests that if a page is needed in memory, its neighboring pages may be needed as well. However, *prepaging* hasn't proven to be that useful except when restoring a process which was swapped out.
