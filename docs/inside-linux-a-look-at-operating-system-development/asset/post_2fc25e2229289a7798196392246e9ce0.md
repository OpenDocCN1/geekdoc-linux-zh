
## 2.3.2 Source Distribution

Another, even more significant, feature of Minix was that it was distributed in source form. This allowed, even encouraged, students to modify the system.

This concept has been extended so that Linux source is not only published, but it is permitted in commercial applications without payment of any royalty.

## 2.4 Others

A number of other historical systems have made contributions which have become an essential part of Linux.

### 2.4.1 Multi-User (Timesharing)

In the mid to late 1960s, while major computer centers were focusing on wringing the most performance out of rigidly structured batch processing environments, the Compatible Time-Sharing System (CTSS) and the Dartmouth Time Share System offered interactive access to computing to a large community of simultaneous users.

The intent of these services was to parcel out the power of the system to a number of users with varying needs for the system. Users were able to use the computer for more than compiling and computing—they could use it for editing files, communicating with other users, etc.

This model of service prompted the development of Multics, Unix and Linux⁵.

### 2.4.2 Virtual Memory

Virtual memory is not really a new idea, having first appeared in the Atlas system[17].

Main memory has always been at a premium. Some visionaries saw that this shortage could be hidden from the programmer by automatic mechanisms which shuffle memory images to and from a slower storage medium such as disk.

The idea was somewhat slow in spreading to all systems, but almost all computers built today have some mechanism to permit or support virtual memory. (The exception is for processors used in embedded systems, i.e., those which have a specific control function which can reside entirely in main memory. Your microwave oven control is an example of such an embedded system.) In most cases, hardware support for virtual memory consists simply of a mechanism to stop and restart a “faulting” instruction. The details of moving memory images is left to specialized software. At the extreme, virtual memory support on the PRIME system was implemented entirely in firmware. We’ll take a detailed look at virtual memory in Section 5.4.

An aphorism for the computer age says “Virtual” means never knowing where your next byte is coming from.”

### 2.4.3 Filename Expansion In Command Lines

Unix systems have long possessed a feature called *globbing* as part of the command line processing. Globbing replaces special regular expression patterns with file names which match the patterns. Another term for this is “wild card substitution”.

The SDS-940, and later the Tenex operating system on the DECSystem-10s, added interactive file name expansion. This permitted the user to type part of a file name and then, by using a reserved character such as tab, have the system fill out the rest of the file name or produce a list of possible file names.

This new feature was first introduced to Unix users as a patch to the C shell, but it is now part of a number of shells found in Linux distribution kits.

### 2.4.4 Bit-Mapped Display

The Alto and Dorado systems were designed at Xerox PARC in 1974 to use a bit-mapped display for flexible user interaction[50, 29]. This spawned a number of successful follow-on projects such as the AT&T Bell Laboratories’ Blit and the Apple Lisa[39]. These in turn have prompted a number of commercially successful products, e.g., the Apple Macintosh, Microsoft Windows, and the X Window System used in Linux and Unix workstations from DEC, HP, IBM, Sun, Silicon Graphics and others.

### A note about earlier display devices

In 1947, Dr. F.C. Williams developed a method of storing data using dots on a cathode ray tube [22]. Although data storage was the primary purpose of this device, it also proved a useful (and for a while the only) way of reading results on the Manchester University research computer. But with only 1024 bits of display, the idea never caught on and core memory quickly rendered this storage mechanism obsolete.

For some time thereafter, CRTs were relegated to one of two categories: vector display or character display.

- A vector display draws each character as a series of strokes. Circuits direct the electron beam to the right place on the screen and other circuits turn the beam on or off as needed. Using this method, characters can be placed at arbitrary locations on the screen and can be rotated and sized with little additional effort.
- The character display uses raster scanning of the entire screen with a series of horizontal lines. The beam is turned on and off according to entries in a look-up table, building images of characters out of fragments of a number of adjacent lines.

Both of these methods have a major shortcoming: they are unable to display arbitrary data. The bit-mapped display was the answer. Like the character display, it operates on a rasterized scan of the screen. The difference is that each pixel (picture element—a dot on the screen) is individually addressable—often with multiple bits of precision to offer grey scale or color control.

It's interesting to note that bit-mapped displays are practical only because memory prices have dropped low enough. In contrast to the system designed by Dr. Williams, memory now drives the display instead of the display being the memory.

It's also interesting to note that Linux easily supports all three kinds of CRT displays, as well as the hard-copy terminals which were so essential to the first Unix systems.

## Chapter 3

### User Interface

A typical computer user's view of an operating system is based on the commands entered on a keyboard or through a graphical user interface involving windows, icons, mouse motion, pointers, and button presses. For that reason, we will first explore Linux from this user perspective. This will develop into a more formal characterization of operating systems in the next chapter and then Part II will look at Linux from the programmer's perspective.

### 3.1 Command Line Interface

Of all methods of user interaction, the command line interface is easiest to implement. It also provides great utility while using modest computer resources. For that matter, the command line interface is still closest to the original spirit of Unix development noted in Section 2.2.6: write programs that handle text streams, because that is a universal interface.

Linux has several different shells and hundreds of application programs which interact with the user via an alphanumeric display and keyboard. Each of these shells and programs has a different command line interface because Linux, like most other Unix and Unix-like systems, does not have a uniform command language. This has led to situations where different utilities give opposite meanings to different commands, e.g., vi interprets "quit" to mean finish without updating the file and "exit" to mean finish after updating the file, while mail interprets "quit" to mean finish after updating the mail queue and "exit" to mean finish without updating the mail queue.

1. The distinction between a shell and anything else is largely a matter of intent. Anyone can write and install a shell on a Linux system.

Linux, Unix, and other Unix-like systems have been properly criticized for this confusion, but the best we can hope for is a gradual convergence towards consistent interpretations. We must remember that the command language at any moment is a function of which program is in control of the terminal.

### 3.1.1 Shells

A shell is almost always the primary interface between Linux and the user.

There are over a dozen different shells, each having a language which differs from the others in a number of subtle ways. These language differences (or improvements as claimed by some) are called *syntactic sugar* by many, suggesting the differences have little substance, but they make the use a lot “sweeter”. Although the differences don’t significantly extend the ultimate ability of the languages, there are strong adherents for different languages. This is because some more conveniently express what the programmer intends and others provide a comfortable, stable work place.

I’ll try to stay out of this religious battleground and instead try to focus on the major elements common to most of the languages. There are two major shell families, named after the first of their lines—the Bourne shell and the C shell. When appropriate, examples for each will be given.

The novice user sees the language in terms of single line commands. At this most basic level, the shell serves to let the user invoke the execution of application programs, one at a time. Some of these programs can be rather extensive, e.g., a database client or server, a text editor or formatting utility, compilers and linkers, or terminal emulators. Other commands are more mundane, e.g., display the date, list the directory contents, move or copy a file, or assign a value to a variable.
