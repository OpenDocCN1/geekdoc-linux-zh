
Virtual memory is anathema to real-time processing because a process is interrupted when it references a missing page. These interruptions, called page faults, delay a process until the kernel moves data from disk to memory. With soft real-time systems, the real-time tasks are locked into physical memory so as to avoid delays due to page faults. Only those processes which are not designated “real-time” are affected by delays due to paging. See Section 4.4.4 for more discussion about virtual memory.

In a similar vein, a hard real-time system may allow lesser priority tasks to run, provided the system can force control back to the critical tasks in time to insure their deadlines are met.

When resolution and consequences are left unmentioned, only *hype* is left. Until detailed descriptions of context switch time, interrupt latencies, priority scheduling algorithms, and execution speed are given, you can't really count on having real-time behavior. Be wary of such systems.

## 4.1.4 Linux As a Real-Time System

Someday Linux may be able to claim to be a real-time system. Features have been developed to support this goal. System calls for memory locking and scheduler control have been added to the development kernel.

These enhancements mean Linux is rapidly approaching the level of soft real-time support, but there are some tricky issues yet to be resolved. Markus Kulm¹ warns that a process is not awakened from an interrupt, but rather it is only made runnable, i.e., it may not run immediately after the interrupt completes. He also warns that some interrupt handlers may have to be rewritten and that there are some places in the kernel where interrupts are disabled for extended intervals.

## 4.3 Peripheral Management

Scheduling can be characterized as “processor management”. In the examples in the previous sections, the focus was on keeping the processor busy and preventing processes from interfering with one another. A system kernel must also ensure peripherals are used easily and effectively. Part of this duty can be relegated to run-time libraries, but ultimately the system kernel is involved. Section 5.3 discusses some of the implementation details.

One of the most significant design decisions is where the boundary (between the system kernel and the run-time library) should be placed.

### 4.3.1 Shared File System

The most common design is to have the system kernel deal with the mapping of file names to directory entries and disk block addresses. This design makes it much easier for processes (and their users) to share the file system space.

For instance, as I compose this book, I have multiple processes running, each manipulating the various source and result files. One is a terminal session used to compose the text, another is a terminal session to edit the bibliography, another process is used to view the PostScript output and yet another to view the HTML output. Each of these processes is independent of the other, but they have access to a shared file system.

This sharing can go further, where the processes are not only independent, but are being run by different users. A shared file system would permit David to share his compiler, Ellen to share her editor, Francis to offer an accounting package, etc. All they have to do is set access permissions to allow others to execute their programs.

The design of a shared file system has many opportunities for interaction among the user processes. Some implementations make the whole file system a single critical section, but better systems are designed with finer granularity. The benefits are generally regarded as worth the additional effort.

### Elements of a File System

What distinguishes a file system from a raw disk is its structuring of the data, i.e., it keeps track of the locations of multiple files and directories.

**Files—A Most Basic File System** The most basic file system splits the disk into uniform chunks and the user identifies them by an index. (This crude system has actually been used in the distant past.)

**Directories—A Larger File System** Clearly this leads to the idea of the directory, a mechanism by which files are identified by a name rather than a number. The simplest organization has a fixed length directory with fixed length entries. A directory entry has the name of a file, its starting location and its size. File data are stored in contiguous disk blocks. Empty spaces on the disk can be identified by special directory entries or by a method of elimination. A rough sketch of this is shown in Figure 4.10.

| Directory | File 1 | Unused | File 3 |
| :--- | :--- | :--- | :--- |
| File 3 | Unused | File 4 | File 6 |
| File 6 | File 5 | Unused | File 2 | Unused |

When files are created, the user must specify their maximum size so that the system can find an empty space big enough. When the file is closed, the system completes the bookkeeping by noting the final size and perhaps creating an empty space entry for what wasn't used. It is difficult to anticipate the length of most files, so the maximum size is not really indicative of the final file size. It also becomes ever more difficult to find space for a file as the filespace becomes fragmented.
