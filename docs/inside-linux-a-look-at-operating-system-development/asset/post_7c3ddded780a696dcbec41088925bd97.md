### Other uses for Physical Memory

An outstanding feature of Linux is that it puts all physical memory, except that used to hold the kernel code, into a common pool. Memory is taken from this pool to provide frames for the virtual memory system and buffer blocks for disk caching.

The results can be surprising to the uninitiated: when compiling a large program (such as the kernel) on a memory-rich system, one will find the disk rarely operates for the second and successive iterations. This is because all the disk data have been cached in memory. The system can just copy data between the cache buffer block and the user program instead of performing disk I/O.

### 1.2.8 Linux Is an Open System

This term requires some explanation because there are several meanings of open system. The first (and formal) sense is that a system conforms to published standards. This is intended to ensure that programs written to those standards can be ported to other open systems. The second (and often implied) sense is that there are no hidden elements. Some systems fail to meet this second meaning because, although they provide all the features of a standard, they provide some additional features which can only be exploited by the knowledgeable. Linux comes closer to meeting the POSIX[3] standards than any other operating system, and if there’s any doubt, all the source code is available for inspection by any interested party. These standards are discussed further in Section 5.1.1.

### 1.2.9 Linux Has a Large Development Toolset

Unix has been under development for over twenty-five years. During most of this time, it has been used by its developers for further development. This has led to Unix being the best tool for developing Unix.

Linux has followed the same path in its short life. Netnews, a network based bulletin board system, has been used to great advantage because it encourages the convenient discussion of problems. Since Linux is self-hosted, developers find it easy to add fixes for problems which get in their way.

Linux has benefited greatly from the Free Software Foundation^5 GNU (GNU’s Not Unix) project. This project set out to replace Unix with a system free of the licensing constraints. Although FSF has recently released the HURD kernel, a large number of tools, including superior compilers and editors, have been released over the past years. Since these tools were written with an open system in mind, it was a simple matter to incorporate these tools into the Linux distribution. Most of these tools are of the system development and text processing flavor.

The GPL, which was designed to promote free software, has sparked a remarkable amount of commercial development. Enlightened hardware vendors have contributed drivers for their hardware with the understanding that this will promote sales of their devices. Software developers have found it easy to port their suites of Unix-based applications to Linux—thanks to Linux’s almost complete POSIX compliance. The GPL means they have the entire source at hand so they can fix any part of Linux which they find deficient. The GPL then ensures that these fixes will be shared with the rest of the Linux community.

### 1.2.10 Linux Offers Application Programs

This ability is the single most critical element in Linux’s general acceptance. After all, if Linux only serves the developers of Linux, the user population will be rather modest.

As mentioned above, Linux has a Unix-like interface (that is almost completely POSIX compliant) so any program written for Unix can be easily ported to Linux. In addition, most commercial software producers have shifted their programming from assembly language to C or C++, making it easier to port their products to Linux.

### 1.2.11 Linux Uses Cost Effective Hardware

The personal computer hardware market is both very competitive and very large. Although Linux is dramatically different from the most common commercially produced operating systems, it can share the cost and performance benefits of the mass production of the hardware. Linux is not limited to the x86 architecture. A list of other systems is given in Section 1.4.1. The hope is that these architectures will also offer good price/performance ratios.

## 1.3 Fundamental Shortcomings

Linux is not perfect. It has some shortcomings and it is lacking some popular features. (I treat these as distinct characteristics because some popular features aren’t that beneficial.)

### 1.3.1 Linux Is Not a Micro-kernel

The term “micro-kernel” suggests that there is an even more fundamental kernel-like element within the kernel. The basic premise to a micro-kernel is that the kernel can be built from many nearly-orthogonal specialized kernel processes. These processes communicate by passing messages through the micro-kernel to one another.

The MERT system was developed at Bell Laboratories according to these principles[33]. Others have followed, including a successful commercial product, QNX^6, which has been in production since 1980; Plan 9^7 from the creators of Unix at AT&T Bell Laboratories; and VSTa^8, a copylefted^9 system originally written by Andrew Valencia.

MACH^10 is a micro-kernel-based operating system from Carnegie Mellon University which has been under development since 1985. It has explored a number of ideas including

- kernel level support for light-weight threads
- support for multi-processors
- support for different operating system interfaces, including BSD Unix and Linux^11

Parts of MACH have been incorporated into other operating systems including DEC’s OSF/1 for the DEC Alpha, IBM’s OS/2 for the RS6000, NexT OS, and the HURD^12. Further research and development on MACH is being done by the Open Software Foundation (OSF)^13.

The micro-kernel approach has the advantage of enforcing good modular design. If the design is done right, it can be extended to support multiple user threads and symmetrical multiple processors.

There are two important points which must be made about the previous sentence. First, one can have a multi-threaded kernel and support multiple processors without a micro-kernel. This is the case for almost all commercial systems.

Second, although it’s easy to implement user threads and symmetrical multiprocessor with a micro-kernel, it is hard to do this well. The problem is that careful attention must be paid to the design, otherwise bottlenecks will limit system performance.

The down side to a micro-kernel is that a message passing kernel can often (but not always) take more resources than a monolithic kernel because message passing uses more instructions than subroutine calls. In the case of a multiprocessor system, this is a reasonable trade-off because of the improved performance. In the case of a uniprocessor, the required effort can be daunting. Nevertheless, there is discussion of how one might build a new Linux using this technology.

In the meantime, the Linux kernel has the ability to load separately compiled modules into the kernel. This means that the kernel can be changed to support the actual hardware configuration without costly shutdown/reboot cycles. A developer can follow a modify-compile-load-test-unload-modify cycle in driver development. The latest efforts include tracking dependencies between modules and even automatic load-on-demand of modules.
