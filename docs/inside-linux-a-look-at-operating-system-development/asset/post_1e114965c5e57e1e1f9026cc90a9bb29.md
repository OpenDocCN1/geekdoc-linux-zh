**Hardware support** The careful reader may have noticed a likely disadvantage to a paged memory system: each memory reference appears to generate another reference to get the page table entry. Some systems, such as the DEC PDP-11, hold the entire page table in registers. This is practical because the PDP-11 has a small address space (64 Kbytes) holding only eight pages (of 8 Kbytes each). (To be precise, the PDP-11 memory management is an analog of paged memory and segmented memory. Each page also has a valid length, just like the memory segments mentioned earlier.)

It is much more typical to store the page table in memory and then rely on *translation look-aside buffers* (*TLBs*) held in a special *associative memory* which caches a subset of the page table entries. (Associative memory is addressed by part of its contents, in this case the logical address, to provide a value, in this case the physical address.) ## 4.4.3 Swapping

It often happens that there is simply not enough memory to meet the needs of all the processes. System kernels have responded to this problem by providing swapping and/or virtual memory.

One simple solution to a shortage of memory is to *swap out* the entire process, i.e., copy it to special storage. This swapping frees up memory which then can be used to start new programs or to swap in a previously suspended process, i.e., copy it from special storage. This special storage has in the past been smaller high-speed disk or drum storage, but nowadays is typically a reserved section of an ordinary disk.

The selection of the process to swap out or to swap in is part of a long-term scheduling decision. Such a decision is based on a process’ priority, deadline, processing category, peripheral access, etc. This is discussed further in Section 5.2.4.

A system which provides only swapping can easily find itself spending most of its I/O bandwidth saving and reloading processes and the processor will often be idle while waiting for some process to be loaded. This wait occurs because the *entire* process is moved for each swap in or swap out operation. Still, this occasional waiting is usually better than waiting for one process to finish before starting another process.

## 4.4.4 Virtual Memory

Most systems now offer some form of *virtual memory*, which is similar to swapping on a paged system. The difference is that it does not swap the entire process at one time. Instead, individual pages are loaded to memory as they are needed and they are shifted back to storage when they become inactive. It’s even possible that some pages are never loaded to memory.

Virtual memory requires some additional hardware support, specifically (1) the page table shown in Figure 4.20 needs at least one more bit in each entry of the page table to show the map is valid/invalid and (2) the processor must be able to suspend or abort and restart instructions which make reference through an invalid page. Although the first part is simple to add, the second is quite difficult, especially in light of the techniques used to extract higher performance in the processor, e.g., instruction look-ahead, out-of-order execution, etc. Almost all virtual memory systems have additional status bits associated with each page. One, called the *modify* bit (or *dirty* bit), is automatically set if the page is ever modified. The rest, called *reference bits*, are set to record the use of the page.

The processor will treat a reference to page **G** in process 2 in Figure 4.19 as a *page fault*. The processor stops that process until that page can be mapped to a frame of memory (by loading it from disk). After the system updates the page table, it will let that process resume execution.

The system uses the modify bit and the reference bits to decide what frames should be written to disk and what frames should stay resident.

Additional bits can be used to control access to a page. For instance, a "read-only" bit could be used to mark code pages which are being shared.

If there is no page image in special storage, the system may abort the user process or it may create a zero filled page. The latter is common when more stack or dynamic data memory is needed.

This is more fully discussed in Section 5.4.1.

## 4.5 Security

Any multi-user system (and any cautious single user system) has mechanisms to limit what processes can do. These mechanisms must protect against:

- unwanted access of data
- unwanted destruction of data
- denial of service
- system corruption
- circumvention of accounting

One should realize that the above problems can occur because of errors as easily as malicious acts. Thus, these issues are properly the domain of all systems, not just networked or multi-user systems.

In addition, one should realize that security is most importantly a mind-set, not a set of programs and procedures. Security can be lost through willful or uncaring acts by users and system administrators.

That being said, we can now discuss what basic mechanisms are available to protect a system. Most basically, they control what can be done by whom.
