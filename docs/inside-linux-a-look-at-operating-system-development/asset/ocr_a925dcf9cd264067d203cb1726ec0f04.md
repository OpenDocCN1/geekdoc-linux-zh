This short-cut is because the library was first referenced mostly to determine that the three routines were defined in the library. Once that determination was made, there is no more need for the executable to track the exact contents of the changing library. This is because *every time* `hw.dynarmic` is executed the most current version of `libcry.so` is used to provide the library code.

There is a trap for the unwary in this process: the program will pass invalid data if the subroutines change their calling arguments. For example, if a math function was changed from “the $N$th power of $M$” to “$N$ to the $M$th power”, the program would get the wrong results unless it changed the order in which the arguments are passed.

The routine `readelf`, distributed in recent Linux CD-ROMs, can be used to explore more about what data are held in an ELF file.

# ## Kernel implications

Why are these formats important to the kernel? First, the kernel must recognize the different executable file formats. Second, the run-time code must support these conventions.

# ## Executable file types

From the very first days of Unix, the first word an executable file contained was a magic word which the kernel used to determine how the executable was to be handled. By the seventh edition, this was enhanced to support direct execution of shell scripts. In the current Linux systems, if the word contains the value `0xc231 0x2f`, the hex values for the characters “#!”, the file is identified as a script file. Additional text on the first line identify what program is to interpret the rest of the file.

The a.out format has several variants. The oldest magic word, `0407`, comes from the PDP-11 implementation of Unix. This specific value, when decoded as an instruction, means “jump over the rest of the header to the eighth word of the code”. Thus a type `0407` code file was directly executable at address zero.

Other magic word values have been added for other forms of memory management.
