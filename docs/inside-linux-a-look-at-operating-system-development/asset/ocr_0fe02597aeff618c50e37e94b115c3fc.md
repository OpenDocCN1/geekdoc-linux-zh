A key point to all this is that there is no real magic to a compiler — although I will admit a good compiler involves artistry and science, a modest compiler can be understood by many. And a modest compiler can be written and installed by anyone.

# 7.1.3 Interpreters

So far, we’ve looked at what system support is required for languages which are assembled or compiled and built into a binary executable form. We’ll now look at two features which provide system support for interpreters: direct execution and recursion.

It’s worthwhile to first review the different forms of interpretation.

One form is derived from an interactive system which is extended to read from files as well as terminals. The language looks like technical prose with words which look like those of a natural language, e.g., “if”, “then”, “else”, “while”, “for”, etc. The advantage to such a language is that

+   - it can be read on a display or print-out and comprehended by the programmer
+   - it can be prepared with a text editor
+   - some interpreters allow interactive use which facilitates testing

Another form relies on the representation of commands and data in a binary form that is unrelated to the display of natural language.

In both cases, the interpreter can be nearly identical — only the front end which parses the source needs to be different.

FORTH is a good example of a language which has both kinds of interpreters. The binary form of FORTH is quite compact, which is appropriate when it is used in an embedded system. The more natural language form of the language is used when these programs are being developed.

All Unix-like systems have at least the shell, a command interpreter of the first kind, and almost all distributions have other utilities, such as editors, which read commands from a terminal. Since Unix-like systems support redirection, it can be claimed that they support command files.
