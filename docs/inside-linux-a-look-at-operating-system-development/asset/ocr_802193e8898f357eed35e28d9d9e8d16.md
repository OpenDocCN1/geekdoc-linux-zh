# ## 5.1 User Interface

Every computer has some undesirable aspect to it, e.g., it has a difficult-to-program peripheral interface, it is missing a time-of-day clock, it has a limited command set, etc. Pity the poor programmer who has to use such a bare-bones system! Fortunately these rough edges can be smoothed with the use of a system kernel with a good run-time library. The programmer can then call subroutines to perform high level abstractions, such as “set clock” or “read from a file” without becoming involved in the details of device registers, command sets, file system implementation, etc.

From the programmer’s viewpoint, it doesn’t matter if the calls are to a run-time library or to the system kernel. It’s even possible that subroutines could be moved from the run-time library to the system kernel or from the system kernel to the run-time library without the knowledge of the user.

Although all that matters to the user is that there is a well defined set of calls to perform the desired operations, the compiler writer and the system implementor must know these details. In addition, the location of the boundary is important to security—the kernel is often permitted to do things a user must not.

Unix was designed so that the data used to control the process are out of sight from the process. Richie and Thompson noted that

> there are no “control blocks” with a complicated structure partially maintained by and depended on by the file system or other system calls. Generally speaking, the contents of a program’s address space are the property of the program, and we have tried to avoid placing restrictions on the data structures within that address space[43].

This isolation model is followed in Linux.
