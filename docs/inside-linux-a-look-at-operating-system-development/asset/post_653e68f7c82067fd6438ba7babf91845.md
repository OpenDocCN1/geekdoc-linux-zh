
Many Unix implementations rely on a common architectural feature: there are multiple modes of operation and the user mode can be switched without affecting the privileged mode of operation. We've seen in Section 5.1.2 how a system call leads to a privileged mode of operation. Once in this privileged mode, the kernel code can change the parameters of the user mode of operation as easily as it can switch the stack pointer from one process' stack to another. The real distinction among processes is held in the other registers, including the stack pointer and the memory management registers.

In the implementation of Linux for the x86 architecture, the bounce point uses a single instruction which saves all the registers in the current task state segment (TSS) and retrieves new register values from the new TSS. Because the instruction pointer (IP) is one of those registers, and the same trampoline code is used for all context switching, the instruction pointers saved in all the TSSs have the same value.

## User Threads

A thread is a process-like entity which shares much of its context with its siblings. Because of this sharing, switching among sibling threads involves less data manipulation and therefore less time than for heavyweight processes. (If threads cost as much as processes to context switch, there would be no use for threads.) The switching between threads can be co-operative or preemptive, but in any event, the whole process is subject to preemptive scheduling.

This low cost switching makes threads ideal for a tightly-coupled set of subroutines working on a common problem, perhaps created implicitly out of the source program. Little performance is lost, yet the programmer is able to express a solution which better matches the problem.

Threads can be implemented in several ways—entirely as user code, with kernel support, or entirely within the kernel.

The pthreads project has developed user level multithreading for Linux. It is derived from a portable implementation, called C-threads, which runs on a number of Unix systems.

Another port, called PCthreads, has been made available via ftp.

An experimental version of kernel-supported user threads was released in September 1995, but it did not track later kernel releases. Instead, a non-standard system call, clone, is slowly being extended and refined. It will serve as the basis of kernel based user threads, so it is unlikely user-level threads will ever be implemented entirely within the kernel.

Because threads are subordinate to processes, the description of their state differs from that shown in Figure 5.3. The most significant change is that the heap space and stacks are equally visible to all threads. When there is but one thread of execution in a process, there need be only one stack and it can grow towards the heap. With multiple threads of execution, there must be multiple stacks—one per thread.

Because of the ease of implementation (the virtual memory part doesn’t need as much change), the thread stacks are typically allocated out of heap space. These stacks cannot be extended as easily as the single stack shown in Figure 5.3.

Because the per-thread stacks cannot easily grow, many implementations require that they be pre-allocated with some maximum size. Other implementations check at the time of each subroutine call to see that the next stack frame will fit. If it cannot, another chunk of heap space is allocated and the stack is continued in that new space. As the nested subroutines return, these chunks are deallocated. (This is sometimes called *stack unwinding*.)

If the threads are implemented entirely as user code, the hidden system data (which holds information about open files and such) applies to all the threads and the saved registers belong to the thread which was running when the process was suspended. (Registers belonging to other threads are stored on the stacks or a thread control table using the techniques shown in Figure 5.5.)

### Threads in the kernel

Linux does not have kernel processes *per se*. Whenever a user process makes a system call, it **does not** wait for completion of the system call. Instead, that execution sequence acquires amplified access rights by way of the system call. It executes kernel code until the system call completes or, if the system call cannot immediately complete, the calling process is suspended and another user process gets to resume execution. The newly resumed process takes up from where it had been suspended.

If threads are implemented entirely as user code, when one thread is suspended, all threads in that process are suspended. It is upon this issue that most implementations of user threads are driven to some form of kernel support.

With kernel support, the kernel has some sense that there are multiple threads in a user process. As a consequence, it is the kernel which switches from one thread to another, as well as from one process to another. System calls are implemented to allow one thread in a process to be suspended without blocking other threads in that process.

### Re-entrant code

Code shared among threads must be careful with its use of C language *static* data. If care is not exercised, data can easily be corrupted when a partial operation is interrupted by another thread executing the same code. Code which can be interrupted and re-entered by another thread is said to be re-entrant.

Code shared among Linux processes need not be re-entrant in the fullest sense because the processes don't share any of the data space. Code shared among threads must be re-entrant.

It may not be obvious to the casual reader, but this constraint is of great importance.

The POSIX standard for C describes a number of features to be supplied by a library. Functions such as printf are typically defined with static variables which point to buffers.

These libraries have to be rewritten to permit re-entrant use. Otherwise data could become scrambled when multiple threads write to the same I/O stream. Such modified libraries are called thread safe.

## Thread creation model

A new thread can be created as a child of a parent process or it can be created out of entirely different code.

### Child

If a thread is created in a manner similar to the way in which a Linux process is created, normal scoping rules for variable access will permit either thread (the parent or child) to access variables higher up the stack. Figure 5.7 shows the memory layout schematically. The child's stack is shown with a dotted line at its start, indicating that it is somehow linked to the dotted line in the parent's stack. The parent's stack just continues growing, but its size at the time of the thread creation is noted by the dotted line.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_145_0.png)

The data sharing requires some kind of synchronization when threads finish. When the child thread completes, a lock is removed from the parent's stack. When the parent's stack would shrink smaller than that level shown by the dotted line, the parent thread is blocked until the child finishes.

Were this synchronization not performed, a child thread could access data which is invalid because the parent thread has returned past that point.

### Independent

If the new thread is not coupled to the parent, it normally can only access global data, traditionally held in heap storage. The new thread will not normally access (and cannot easily access) data held on other threads' stacks.

### Co-ordination and rendezvous

The parent thread and all its children are said to be independent, but they are typically working in co-operation towards some goal. This means that they need some mechanisms for co-ordination. The two mechanisms in common use are signals and semaphores.

In the Unix implementations, signals are one-shot events (software interrupts) which do not accumulate and which cause a waiting process to proceed. They convey a modest amount of information—the signal number. Signals can be lost should another signal arrive before the first is handled by the receiving process, i.e., signals aren't counted. Some Unix implementations of signals have subtle race conditions wherein a signal handler can drop a signal or fail to prepare to catch the next signal. The POSIX standards have addressed this latter shortcoming, but there is still the basic problem that signals aren't counted. Semaphores have a much more formal use, described in Section 5.2.4. They can be used among threads as well as among processes to coordinate execution.
