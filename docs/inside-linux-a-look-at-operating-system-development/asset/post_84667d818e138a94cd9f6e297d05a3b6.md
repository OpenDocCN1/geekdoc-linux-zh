
### 8.1.3 Storage

#### Disks

- **IDE and EIDE** The Intelligent Drive Electronics interface was developed as the cost of disk-resident electronics dropped. The IDE interface provides low-cost access to disks from the personal computer. The original protocol was rather limited, e.g., only a single drive could be accessed and the data transfer rates were small. The Enhanced IDE has addressed some of these problems, resulting in quite respectable performance.

- **SCSI** The Small Computer Systems Interface defines a bus which can be used to exchange data among eight units. Typically one of these is a computer interface, allowing for up to seven peripheral units. Although these units are often individual disk drives, each unit supports up to eight Logical Unit Numbers (LUNs). This is especially convenient when a unit has multiple drives, such as a CD-ROM jukebox.

#### Tapes

Although Linux has some support for the traditional 9 track tape, most users rely on some form of tape cartridge.

- **QIC** The Quarter Inch Cartridge tape has been an industry standard for many years. There are three or four common cartridge sizes, each with a variety of tape lengths. One can store from 100 Mbyte to 1 Gbyte on these drives.
- **8 mm** This is the same format as the small video tape. The dominant manufacturer in this market, Exabyte, provides drives which can store 2–5 Gbytes of data on a single tape.
- **4 mm** This is the same format as the Digital Audio Tape. Several manufacturers cooperated in creating the standard for recording data on these tapes. While these drives hold less data than the 8 mm drives, some features such as “fast seek” are a bonus.

### 8.1.4 Asynchronous Communication

- **individual ports** Almost every personal computer comes with one or two asynchronous ports. These are typically driven by single chip controllers, such as the 8250, 16450 and 16550, which provide character buffering, bit stream serialization and modem control. They are often limited to speeds below 50 Kbits/sec.
- **multiplexor ports** Larger systems have a single interface card which provides support for a number of serial ports. These cards offer higher performance and a smaller burden to the system (in terms of interrupts/char, number of control ports, and number of interrupt vectors).

### 8.1.5 Network Communication

Until recently, the standard network connection for Linux systems took two forms:

- Ethernet
- serial async (SLIP or PPP)

The Ethernet offers 10 Mbit/sec speeds, but is limited to a maximum of 500 meters (or a bit more with the use of bridges). The serial async connection has no such distance limits, but performs no better than 28.8 Kbit/sec.

Linux now supports, or will soon support, direct connections to:

- Token Ring
- ISDN
- Frame Relay

These will offer higher bandwidth than the serial async connections.

### 8.2 Support of Unusual Peripherals

- **CD-ROMs** This device is not really that unusual, but the story behind the creation of the SCSI driver is interesting. Part of the driver depends on code common to all disks, but part of the protocol must deal with the different request-reply sequences that are device dependent. Someone posted a query about the CD-ROM sequence in a news group, someone else posted a list based on his work on a driver for MS-DOS, then someone else posted a patch file for the driver which incorporated this sequence. All of this discourse occurred within 48 hours—perhaps a record for adding support for a new device!
- **CD-ROM jukebox** This is a popular device for holding large collections of software on-line. Jukeboxes with SCSI interfaces are trivially added to Linux systems. The only requirement is that the kernel must be configured to support multiple LUNs (logical unit numbers). Once this is done, each LUN behaves as a distinct SCSI device. References to a LUN automatically trigger the jukebox to load the appropriate CD-ROM.
- **CED 1401** This laboratory interface has a package<sup>1</sup> for user program control.
- **Precision clocks** There is great advantage in keeping the system’s clock correct. If the system is constantly connected to the Internet, the ntp<sup>2</sup> utilities can be used to synchronize the system’s clock against other standards. As a bonus, this same software has support to talk to a number of specialized clocks which receive broadcast radio signals or have a precision time source inside.
- **Frame grabbers** A television camera, a frame grabber, and software<sup>3</sup><sup>4</sup> are sufficient to give the Linux user access to images.
- **GPIB** Another interface for laboratory instrument control is the General Purpose Interface Bus, defined by the IEEE488 standard. There is at least one driver<sup>5</sup> for this interface.
- **MIDI** Although this is not normally a part of Unix systems, the common availability of this interface for the PC has led to the early inclusion of a driver in the kernel.

Now that loadable driver modules are a configurable feature of the Linux kernel, users find adding new drivers to be reasonably straightforward—especially if they can be derived from existing drivers.

## Chapter 9

# Distribution of System

Kernels, kits and disks are generated by authors, assemblers and publishers respectively.

For a while, the Linux kernel was distributed only by way of a few ftp sites, and users were expected to get the rest of the system directly from wherever the parts were located. This distribution has been superseded by more formal mechanisms. Although the kernel versions are still being distributed on a regular basis by ftp, others have stepped in to build distribution kits. Each kit contains the kernel, a suite of tools ported to Linux, and several floppy disk images needed to bootstrap the system. Initially these distribution kits were distributed via ftp as well, but a number of publishers have collected one or more of these kits, along with an even larger suite of tools, to be published on compact disks.

### 9.1 Dual Tracked Kernel Releases

Initial releases of the Linux kernel were numbered 0.xx to indicate they were not really ready for prime time. This numbering scheme had some limitations, but questions such as “Does 0.11 come before or after 0.2?” were safely avoided and the numbering quickly arrived at a limiting value of 0.99. That version was widely distributed and it was regarded as the first full-featured version of the Linux kernel. There was by then a sizable community of users who depended on a stable version of the kernel. Although there were many patches and sub-patches to this version (often arriving daily), the basic version 0.99 was suitable for release. The great release took place at the start of 1994 when Linus Torvalds identified a stable patch level, 0.99pl14r, cleaned up a few last problems, and called it good. This operation was called a code freeze and resulted in version 0.99pl15, which held steady long enough for bug fixes, but no enhancements, to arrive.

Part of the code freeze and the great release was the recognition that Linux had become a suitable foundation for production systems— systems devoted to doing useful work instead of being the direct object of a programmer’s interest. This posed a dilemma: how could Linux continue to evolve and yet be stable? The solution was simple: have two development paths starting from the same point. The even numbered releases (1.0.0, 1.0.1, etc.) followed a slow, careful evolution of a production system and the odd numbered releases (1.1.0, 1.1.1, 1.1.2, etc.) were to be fast-changing, development systems. Version 0.99pl15, with a few fixes, was the basis of these two systems. Some important fixes moved 1.0.0 to 1.0.8 in the early months of 1994, but the production versions saw only a few more changes during the rest of the year. By contrast, the development system underwent over ninety-five changes in a year.

In early 1995 a second major release occurred. Again, the stable and well-tested features of the development versions (up past 1.1.95) have been incorporated in production releases, which are not expected to exceed 1.2.14. Its twin, the development version, is the basis of yet more development work and has undergone over sixty changes in a year.

One thing that also happened with the first great release was that the release itself no longer held a catalog of its changes. This shortcoming was corrected when Russ Nelson<sup>1</sup> volunteered to distribute a change summary shortly after each patch was distributed. Michael Elizabeth Chastain<sup>2</sup> has since volunteered to take up the duty. An archive is maintained on Nelson’s system<sup>3</sup>.
