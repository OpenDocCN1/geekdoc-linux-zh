## Page Replacement

Virtual memory almost always leads to *over-allocation* of physical memory. i.e., the sum of pages of all processes exceeds the number of frames in the system.

When the system discovers there are no free frames, it can either suspend or abort the needy process (a bad idea) or it can swap out another process (slightly less desirable) or it can free some other frames to make room in main memory.

In the latter case, a *page replacement* algorithm is used to determine which is to be the *victim* frame. The most efficient algorithm is the one which results in the lowest *page-fault rate*.

## Optimal Algorithm

If the algorithm could see into the future, it could just replace the page which will not be used for the longest period of time. Obviously a page which will no longer be used is the best choice to be used for the incoming page. Less obvious is which page to choose among those which will be needed sometime in the future. Consider just three pages, P1—the needed page, P2—a resident page needed in the near future, and P3—the resident page needed the farthest in the future. We see that if P2 is chosen to be victim, P1 may still be active when P2 needs to be brought back into memory, but if we chose P3 to be the victim, P1 may no longer be needed when P2 has to be brought back into memory.

## 5.4. MEMORY MANAGEMENT

Although the optimal algorithm has no physical implementation, it is useful for post hoc comparison against actual implementations. One needs only to collect a reference string showing the order of references to memory pages by the system. The optimal page replacement algorithm and proposed page replacement algorithms can then be applied to this reference string to determine the page-fault rate that each algorithm would have generated. With enough data collection based on a good mix of user programs, such comparison will reveal good algorithms.

**FIFO algorithm** The simplest algorithm to implement just notes the order that pages are brought into memory and chooses the oldest page in memory to be the victim. In doing so, we are hoping it will no longer be needed. This is clearly true if it held some initialization code. It is clearly false if the page holds some global variable that was initialized at the start of the program and is still being used.

The FIFO algorithm exhibits a curious phenomenon called *Belady's anomaly*. Normally, we would expect performance to increase (page faults to decrease) as the number of memory resident pages increases. As shown in Figure 5.28, applying the FIFO algorithm to the reference string 1 2 3 4 1 2 5 1 2 3 4 5 with more frames can yield more page faults!

This problem leads directly to a goal called the *inclusion property*, which states that a larger memory shall hold all the pages that a smaller memory would hold at any point in the system’s execution history. The LRU algorithm described below satisfies this property.

**LRU algorithm** Execution traces show that when programs reference some location, that location is more likely to be referenced again in the near future and other portions of code and data remain unused for significant periods. Although the choice of the oldest page in memory (as is done by the FIFO algorithm) might appear to be a good idea, it ignores any *locality of reference*, i.e., the tendency of the system to refer to pages which it has recently referenced. (The danger is that the oldest page in memory may also hold global data which is being constantly used or common code that is regularly executed.)

This fact suggests we can do better than FIFO by choosing instead the page which has been *least recently used* (LRU). Even if we cannot tell what a page’s use will be in the future, we can base our guess on what it has been doing in the past. With LRU we are predicting that the most recently used page is most likely to be used again in the near future.

Even though the LRU algorithm doesn't need to forecast the future (like the Optimal algorithm), it is almost as difficult to implement as the Optimal algorithm.

**Time stamp** One way to implement LRU is to attach to each page an age register which notes the most recent reference to that page. The system maintains a counter that is incremented at every memory reference. The value of the counter is loaded into the age register each time that page is referenced. A simple scan of all the LRU registers will then show the page which was least recently used.

**Stack** The same effect can be achieved by maintaining a stack of page numbers. When a new page is loaded, it is added to the stack top. When a page is referenced, it is moved to the stack top. The bottom of the stack then holds the least recently used page.

**LRU approximation algorithm** Although simple to describe, the hardware implementation of LRU is terribly expensive. We therefore resort to methods which approximate the behavior of the LRU algorithm (which is itself an approximation to the Optimal algorithm).

Some of these can be viewed as a very low precision version of the two implementations outlined above—sometimes with only one bit of information.

**Reference Bits** While a counter provides strict ordering of pages by the time of their use, reference bits provide an approximate ordering. With a seven bit register, a value 1111111 says the page has been used during each of the past seven intervals. When it is no longer used, it will take on values,

- 0111111
- 0011111
- 0001111
- 0000111
- 0000011
- 0000001
- 0000000

during successive intervals. If a page’s register value is interpreted as an unsigned integer, pages with the largest values have been used the most in recent times. (Note that this ordering will likely yield multiple pages of the least recently used category. Some form of tie-breaker algorithm will have to be used to select the victim page.)

**Second Chance** The list of pages can be assembled into a circular queue. Whenever a page is needed, a search is initiated. If a page is found which has not been referenced (the single reference bit set) since it was last considered, it is made the victim. If a page has been referenced, it is ignored for the moment and its reference bit is cleared (it is given a second chance).

Only after all pages have been checked will a second-chance page be selected for use.

If a page is busy enough, it will always be referenced before it suffers a second chance selection.

**Enhanced Second Chance** Since the virtual memory is certain to have a modify bit, it can be used with a single reference bit to yield a four-level preference.

- (0,0) Neither used nor modified—a great victim.
- (0,1) Not recently used, but modified—it will have to be written to disk before it can be reused.
- (1,0) Recently used, but not modified—it may soon be used again.
- (1,1) Recently used and modified—it is the worst choice as a victim.

Scanning a list will yield both victim candidate pages and pages which should be flushed to storage. This leads to a prioritized flow of pages from memory to disk.

## Page Buffering

Dirty pages, those with the modify bit set, are a hindrance to easy selection of victim pages. Even if a page hasn't been used for a long time, it cannot be used to hold a new page until it is written to storage.

A page buffering algorithm takes needed pages from a pool of clean pages and then initiates the write of a dirty victim page. That dirty page is then moved to the pool for later use.

This basic algorithm can be extended to write dirty pages to storage whenever the disk is not otherwise in use.

Once the page has been written to storage, it becomes a better candidate for replacement. (This is especially true if the page is category (0,1) in the Enhanced Second Chance algorithm mentioned above.)

## Frame Allocation

So far this discussion has not considered how many frames a process can have. If there is but one process, the answer is clearly “all which will fit”. But with any multiprogramming, there will be contention for the memory and the system must determine how many frames are to be allocated to each process.

The simplest algorithm would allocate up to *m/n* frames to each process, where there are *n* processes contending for *m* frames. This algorithm is clearly wasteful if some processes don't need *m/n* frames.

A better allocation would give each process *m × sᵢ/Σsᵢ*, where *sᵢ* is the memory need of the *i*th process.

Both of these algorithms are static—they don't change the per-process allocation over time. They are said to perform *local replacement*, where each process pages against itself. Algorithms which perform *global replacement* will take pages from other processes.

There is a clear trade-off: with local replacement, a process may be unnecessarily limited, but it cannot harm other processes and with global replacement a process can get what it needs, but a run-away process can harm other processes.

In either case, the number and size of processes can affect how the system behaves.
