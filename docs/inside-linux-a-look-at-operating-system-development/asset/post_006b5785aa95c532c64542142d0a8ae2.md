### 6.3.2 UDP/IP

A large number of applications rely on using the IP protocol with the User Datagram Protocol (UDP), defined in RFC 768. As can be seen from Figure 6.5, the UDP datagram has fewer control elements. This is because it is connectionless, i.e., there is no sense of a long term connection between the sending and receiving processes. The non-electronic analog is communication via postcards. As with postcards, there is no assurance of reliable delivery and, for this reason, the application process may want to impose its own scheme of acknowledgment and retransmission. But then some applications, such as status reporting, can work quite well with occasionally lost data.

### 7.1 Languages

#### 7.1.1 Assemblers and Compilers

Computers decode instructions from bit patterns stored in memory. The instructions of early computers had somewhat regular structure due to the constraints of the decoding logic. This allowed early programmers to work with *machine code* by specifying the bit patterns of each word of instruction memory. This method of programming was soon replaced by one which used symbolic names which had some mnemonic content. An *assembler* was created to convert the program text into the machine code needed by the computer. The assembler improved programmer productivity and accuracy.

##### Assemblers

Assemblers grew in complexity by offering a growing set of features. Assembler directives could be used to reserve blocks of storage, skip blocks of memory, identify types of code, and most importantly, define and apply macros.

A macro is a text fragment which is to be substituted for another text fragment according to some rule. For example, the fragments

```text
#define MAJOR(a) (int)((unsigned short)(a) >> 8)
#define MAX_BLKDEV 64
```

say that the text

```text
if (MAJOR(dev) >= MAX_BLKDEV)
```

should be replaced by

```text
if ((int)((unsigned short)(dev) >> 8) >= 64).
```

Assembly language, even when supported by a large set of predefined macro definitions, is still a difficult tool with which to write programs. The programmer is forced to tend to a huge number of details which have nothing to do with the problem at hand. For example, the programmer must recall what information is being held in which register at what time.

##### Compilers

This problem of keeping track of details has led to the design of ever higher level languages. Early languages focused on the data transformation found in an algebraic expression and converted them into the appropriate machine language sequence. These languages had rather primitive constructs for declaring data storage requirements and for controlling the sequence of the program. They placed severe limits on how data could be identified and how subroutines could be used.

Over time the languages have grown in sophistication so that programs can be analyzed by a special calculus and claims about the program can be tested in a symbolic manner.

For several decades, there had been a trade-off when deciding to use a high-level language. It had been commonly held that the machine code generated by a compiler wasn’t as good as that produced by an assembly language programmer. In addition, the languages were unable to express some ideas very well. So even though the high-level language programmer could encode a larger part of an algorithm per day, many still relied on assembly language for “critical” applications.

Over this past decade, this situation has undergone a reversal. First, the thirty-two-year-old decision to code Multics in PL/I and then the successful rewrite of Unix in C twenty-three years ago have finally persuaded most everyone that the proper high-level language is sufficient to the demands. Then, the fact that modern compilers do such a good job *optimizing*, machine code generated by a high-level language compiler is normally superior to that produced from an assembly language program.

The reason for this quality is that computers are now able to do what Turing hoped for nearly fifty years ago. They are able to keep track of more details (such as the interrelationships of register use and data storage requirements) with greater accuracy than any assembly language programmer.

The shift to higher-level programming languages has actually helped the process of optimization because, as the programmer shifts away from a viewpoint which is hardware aware, fewer simplifying assumptions are made about how to allocate resources. The compiler is then free to do things which, although uncommon, result in better (faster and/or smaller) code. For example, although the programmer may have declared a variable, there is no need for variable to ever be stored in some memory location—the compiler may have determined that the variable can reside in a register throughout its useful lifetime, after which the value is discarded.

A bonus which comes with this shift towards higher level languages is that the *semantic gap* between the problem and the programming language is reduced.

#### 7.1.2 Linkers and Loaders

Figure 2.1, repeated in Figure 7.1, shows how the executable image is created and moved to memory in stages. The previous section looked at how assemblers and compilers are used to build object files.

Once the assembler or compiler has produced an object file, the job

![](img/bd9544b8c1ad3b1347c84630c5d698e1_221_0.png)

Figure 7.1: Getting instructions into memory

is only half done. The object file contains what are called external references. These external references are recorded wherever the user program calls upon some library function or refers to some global data.

Each machine code instruction, be it a jump, subroutine call, memory load or store, is stored with the target address of zero. An additional entry at the end of the object file describes the instruction format, points to this machine code, and names the required address. When the linker or loader binds the appropriate library code to the object file, it will fix up these references by replacing the zeros with the addresses in the proper form.

The linker, called ld, is invoked from the command line or it is called by the last stage of the compiler. (It is unfortunate that the program, which does linking, is called the loader, but we’ll just have to live with that unfortunate misnomer.)

##### a.out/jump-table

The older style executable files (called a.out) contain six distinct elements shown in the left part of Figure 7.2. When the program is executed, the system loads the TEXT (which contains the executable code) and DATA (which contains pre-defined data) parts into memory. (Shown by the solid lines.) BSS, which stands for “block started by symbol”, is a value in the header which specifies the amount of additional memory which must be allocated for global data (with no pre-defined value).
