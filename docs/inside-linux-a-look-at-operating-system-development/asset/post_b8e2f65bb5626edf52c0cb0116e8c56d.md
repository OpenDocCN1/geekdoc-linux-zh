
## 5.1. USER INTERFACE

### 5.1.1 Defining System Calls

Writing a standards document is not an easy task. The standard must find a balance between describing what must be done without describing how it should be implemented. In addition, it is very easy to rely on unwritten assumptions which may not be shared by someone who later reads the standard. Thus, it is probably not a good idea to have the same person define the calls and implement the system. It is also a good idea to open the documentation process to a large number of people with differing viewpoints. The resulting contrasts will highlight elements of the standard which must be clarified.

One major issue in writing a standard is deciding if the standard is to be *permissive* or *restrictive*. A permissive standard describes a set of behaviors that are sufficient and necessary to claim conformance. Such a standard allows extensions. A restrictive standard describes a set of behaviors that must be met exactly to claim conformance. Such a standard prohibits extensions.

There are several schools of thought with respect to extensions. When applications rely on extensions to the system kernel, those applications may be “locked into” that specific implementation. Programmers who rely on a wonderful extension provided by one vendor will later discover that they will have to incur large reprogramming costs to shift to a different vendor.

Another danger in a permissive standard is found in hidden features that are known only to a select few. “Undocumented calls” are an effective way to bind several applications together or to bind an application with an operating system. A competitor is then obliged to duplicate both applications or the application and the operating system. (These hidden features appear to be among the difficulties encountered on the WINE project.)

If extensions are disallowed or not used (or not provided), applications will be held back by old standards. For instance, there are millions of users still enduring short file names required by MS-DOS. Other users enjoy using the longer file names permitted by Unix, Macintosh, Windows NT, and other systems.

### POSIX

POSIX (the IEEE² Standard Portable Operating System Interface for Computer Environments) describes system calls in terms of C language data definitions and subroutine calls.

The POSIX standard is permissive in that it allows the system to offer additional features not required by the standard. The POSIX standard urges, but does not require, non-standard features to be documented.

There is a subtle point that must be noted: the standard does not describe the system, but rather it says a conforming implementation “shall support all required interfaces defined within this standard. These interfaces shall support the functional behavior described herein[3].” As a result, a *strictly conforming* POSIX application (one which does not use features outside the standard) will need no modification to run on the system.

### A cautionary example

Even though standards may not exhaustively describe the system’s behavior, a careful programmer pays attention to the standard. Relying on the apparent behavior of the system can lead to trouble when moving an application to a different implementation of the same system.

A case in point relates to the `timeout` value in the `select` call available on a number of Unix systems. This call allows the program to wait for I/O activity on any of a number of ports or the expiration of a timeout.

The documentation for this call often contains the comment in the BUGS section:

> select() should probably return the time remaining from the original timeout, if any, by modifying the time value in place. This may be implemented in future versions of the system. Thus, it is unwise to assume that the timeout pointer will be unmodified by the select() call.

The Linux system documentation further warns:

> The Linux behavior with respect to timeout differs from other unices [sic] that don't modify it.

Although disappointing, it should be no surprise to discover a number of programs fail when run on Linux systems. They were written from the experience that the timeout value would remain unchanged and the expectation that this would always be so.

### Language independent standards

The initial POSIX standard was defined in terms of the C language. Additional standards have been developed describing the portable operating system in terms of other languages. There is an effort to do this in a manner which is independent of any language by the use of careful non-language specific descriptions of the data being passed and the actions performed³.

However, examples in this book will be in terms of C, since this language is most widely available on Linux systems and because the language independent standard is neither complete nor easy to use.

### 5.1.2 Implementing a Call

When examining the implementation of a system call, one should recognize that two activities are taking place. The first is the amplification of privilege and the second involves the transfer of control to a system code.

### User side

It was noted in Section 5.1 that the major feature which distinguishes system calls from run-time library calls is that the kernel can do things which are not permitted to an ordinary user. In order to do this, control must pass to code which has greater access rights. There are three common methods of accessing this code:

- data are exchanged between the user process and a privileged process,
- a special function call is made which specifies both an address and a segment number, or
- a trap is generated.

The first of these methods is commonly used in micro-kernel and distributed operating system designs. Data can be exchanged by passing messages, through a rendezvous call, or through shared memory.

The latter two are basically identical in operation. In the case of a call, the function is named as a call address and in the case of a trap, the system function is identified by an argument on the stack or in a register. The outline of the Linux system call is illustrated in Figure 5.2.

Regardless of the details, system calls are described as and accessed through ordinary function calls. In the case of Linux, `/usr/lib/libc.a` provides the interface between the application program and the kernel. The program listed in Figure 5.1 finds declarations for all these functions by use of the `#include <unistd.h>` statement.

There is some modest cost in calling a subroutine to call the kernel. A slightly higher performance could be achieved if the compiler could emit the code to call the kernel directly, but this is balanced by a strong likelihood that registers would have to be preserved anyway. There is also an advantage in that system calls and run-time library subroutines are bundled in a single library. This makes it easier to shift a system call to a run-time subroutine and *vice versa*.

The subroutine calling convention for the Intel x86 family is to push all the arguments on the stack. The system call convention is to put the subroutine number in register `EAX` and up to five arguments in registers `EBX`, `ECX`, `EDX`, `ESI`, and `EDI`.

Each of the system call subroutines is defined via a macro which preserves necessary registers, copies the arguments from the stack to registers, loads the subroutine number and does a trap (`int 0x80`).

Upon return from the system call, the return value is tested for an error condition, a global variable called errno may be set, and the return value is put in EAX. *Because of the need to access specific machine registers, this is one of the few places at the user level where assembly language must be used.*
