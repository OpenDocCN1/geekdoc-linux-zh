
For a different type of file system, the kernel must be given at least three pieces of information before it can mount a partition:

- the name of the partition
- where it is to be mounted
- the file system type to expect

You'll notice that the kernel must know the file system type so that it can associate the correct code with that partition.

In the examples above, the partition holding the basic system would be mounted as /, the root directory. The partition containing users' home directories would then be mounted on /home, the spool partition would be mounted on /var/spool, and the MS-DOS partition on /dos.

This system has great utility to a system administrator who wishes to ensure that one user group will not intrude on another group by using up all of a disk.

## Inodes

An inode defines a file. Foremost, it shows the file's type—ordinary file, directory, special device file, etc. It records who owns the file, both individually and by group, and it contains information about when the file was created, last accessed, and last modified. Inode entries referencing data files or directories contain information about file size and pointers to the data. The inodes are grouped together on the disk and are indexed as elements of a table. (The reader may wish to look at /usr/src/linux/include/ext2_fs.h for details.)

If we look inside an inode, we also see a link counter, fields to support an access control list, and performance enhancing information such as a block counter and fragment description data.

As shown in Figure 5.15, the data are referenced by twelve direct pointers to disk blocks containing file data, one indirect pointer (to a block containing pointers to disk blocks containing file data), one double indirect pointer (to a block containing pointers to disk blocks containing pointers to disk blocks containing file data) and one triple indirect pointer (to a block containing pointers to disk blocks containing pointers to disk blocks containing pointers to disk blocks containing file data).

![](img/bd9544b8c1ad3b1347c84630c5d698e1_168_0.png)

Note that individual disk blocks are listed, even if they are contiguously located. That is at variance with systems which point to file extents. With four byte pointers and 512 byte data blocks, this yields a maximum file size of $512 \times (10 + 128 \times (1 + 128 \times (1 + 128)))$ or 1,082,201,088 bytes. By increasing this to a 4096 byte data block, the maximum file size can grow to $4096 \times (10 + 1024 \times (1 + 1024 \times (1 + 1024)))$ or 4,402,345,713,664 bytes, but because the size field of the inode is 32 bits, the real file size is limited to 4,294,967,295 bytes. In fact, this smaller limit means that current file systems, which use 4096 byte blocks, never use the triple indirect pointer.

Since we now have disks which can hold more than four gigabytes, we should expect future file systems will expand the size field. System calls and utilities will then have to undergo a corresponding change.

## Data

The blocks containing the data are rather ordinary. As has been suggested by the inode structure, data blocks can be scattered throughout the partition. One performance enhancing aspect is that the system attempts to cluster blocks to improve access performance. Each contiguous chunk in a file is better than holding the same data in non-contiguous blocks because a single disk transfer can load or store all the data.

A space saving enhancement uses a single data block to hold the contents of several small files. Any of these files that would be extended beyond their fragment are copied to whole blocks and the fragments can be reclaimed.

A final enhancement has been proposed to hold very small files, less than 50 bytes, in the inode where the pointers to data blocks are now held. Internally, this will be a distinct file type, but to the outside world it will appear as an ordinary data file. This enhancement improves performance and saves disk space.

## Directories

Both ordinary data files and directories are collections of text and data, but directories are the exception to the rule that Unix files are uninterpreted by the system kernel. Each directory contains names of a number of files and directories and the inode of each. A special call `readdir` is used to access directory entries. Linux and many recent Unix systems actually forbid accessing a directory with `read` calls. Earlier versions of Unix implemented `readdir` as a library call.

The system uses the name to look up the inode when a file is opened or created. Thereafter the inode is used internally to access the file. Because the name is not held in the inode, it is possible to have multiple directory entries, and thus file names, referring to the same file. It is not possible to say which is the “true” name of the file.

Although a file’s inode number can be made visible to the user via the stat system call, the inode number is not used to identify the file. The directory entries are the only way by which the user can identify and access a file.

Early Unix systems had fixed size directory entries, so that the physical structure of a directory was much like the conceptual model shown in Figure 5.16. The careful reader will have noticed that both the first and third entries point to the same inode. Neither entry can be regarded as the “true” entry because there is no way to tell which was created when the file was created and which was created later by the link system call.

![](img/bd9544b8c1ad3b1347c84630c5d698e1_170_0.png)

This is a good place to explain that deleting a file is done by the unlink system call. This call clears a directory entry and decrements a counter held in the inode. Only when the counter goes to zero is the file actually deleted.

It is slightly more subtle than that. A file is created with a link count of two — one count for the directory entry pointing to it and the second count to remember the file is currently open. The counter is incremented each time it is linked to a new directory entry. The counter is also incremented each time the file is opened and decremented each time the file is closed. This ensures a file will not be deleted while it is accessible to a running program. This also means a file can have a legitimate existence without a directory entry pointing to it. Such a file will disappear when the last program closes its access to the file. (Files are automatically closed when a process terminates, even if it doesn't do so explicitly.)

In the past decade, almost all Unix and Unix-like implementations have come to support long file names in their file systems. In the earliest versions of Unix, the directory entries had a fixed size of 16 bytes, such as shown in Figure 5.17, permitting a two byte mode (i#) and file-names of up to 14 characters.

| i# | name | i# | name |
|---|---|---|---|
| i# | name | i# | name |
| i# | name | i# | name |

Figure 5.17: Short filename directories

Directory entries now have a form shown in Figure 5.18. As before, there is an inode number associated with each entry, but there are two additional fields in a directory entry. The name can now be variable length (as indicated by len) and a variable length gap (derived from next) can appear between each entry. As a consequence, the entries have become more complex and programmers now rely on a library function named readdir, to read each entry. (There is also a readdir system call which supports the library function.) Some Unix and Unix-like systems, including Linux, no longer permit a read operation to access the directories.

### Bitmaps

There are two distinct bitmaps: one for inodes and one for data blocks. Each bit is used to mark the use of an inode or data block. When the system needs an inode or disk block, it looks in this map instead of scanning a linked list of inodes or data blocks. The slightly more complex code is justified by the higher performance it offers.

Although file data are not necessarily located in adjacent data blocks, performance is significantly improved by placing all of a file's data in nearby data blocks. The data block bitmap is especially important because it allows the system to find such blocks with only modest effort.

### Superblocks

The superblock anchors the files in a disk partition. (Actually it locates the inodes, bitmaps and data blocks, but that's effectively the same thing.) Because of its critical nature, it is replicated several times within the partition.

The superblock holds several categories of data, including both information for installation and information used for the moment-to-moment operation of the file system.

Among the installation data, there is a sixteen bit field which holds a value which identifies a valid superblock. If it is not present, the superblock is rejected as invalid although sometimes a redundant copy of the superblock will be sufficient to recover the file system. Other fields are used to estimate the possibility that the file system could have been corrupted, e.g., if it was not tagged as having been shut down cleanly, or if it was last checked more than some interval ago, or if it has been mounted more than some number of times without a check, the user is prompted to check the file system. There is also a revision level to ensure that the current kernel can properly manipulate this partition.
