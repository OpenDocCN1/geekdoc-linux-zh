
Downgrading to a Working Version

When the problem is a clear regression (where the former version worked), you can try to downgrade the package. you will need a copy of the old version. If you have access to the old version in one of the repositories configured in APT, you can use a simple-liner command to downgrade (see section 8.2.2.2, "Installing Packages with APT" [page 177]). But with Kali's rolling release, you will only find a single version of each package at any time.

You can try to find the old .deb file and install it manually with dpkg. Old .deb files can be found in places:

- in APT's cache in /var/cache/apt/archives/
- in the pool directory of your usual Kali mirror (removed and obsolete packages are kept for three days to avoid problems with users not having the latest packages)
- in http://snapshot.debian.org if the affected package was provided by Debian and not by Kali; this service keeps historical versions of all Debian packages

Dealing with Maintainer Scripts Sometimes the upgrade gets interrupted because of the package maintainer scripts fails (usually, it is the postinst). In those cases, you can try to diagnose the problem, and possibly work it out, by editing the problematic script.

Here we rely on the fact that maintainer scripts are stored in /var/lib/dpkg/info/ and that we can review and modify them.

Since maintainer scripts are usually simple shell scripts, it is possible to add a -x line just after the shebang line and arrange them (with dpkg --configure -a for postinst) to see precisely what is happening and where it is failing. This output can nicely complement any bug report that you might use.

With this newly gained knowledge, you can either fixing the problem or transform the failing command into a working one (for example adding | true at the end of the line).

Note that this does not work for a failing precept since that package is executed even before the package gets installed so is not yet in its final location. It works for prerm and although you need to execute a package removal (respectively upgrade) to trigger them.

## The dpkg Log File

The dpkg tool keeps a log of all of its actions in /var/log/dpkg. This log is extremely verbose, since it details all the stages of each package. In addition to offering a way to track dpkg's behavior, it helps to keep a history of the development of the system: you can find the exact moment when each package has been installed or updated, and this information can be extremely useful in understanding a recent change in behavior. ## Reinstalling Packages with --reinstall

When you mistakenly damage your system by removing or modifying certain files the easiest way to restore them is to reinstall the package. Unfortunately, the packaging system finds that the package is already installed and politely refuses to reinstall it. To avoid this, you would use the --reinstall option of apt and apt-get commands. The following command reinstalls postfix if it is already present:

```
# apt --reinstall install postfix
```

The aptitude command line is slightly different but achieves the same result with aptitude. The dpkg command does not prevent installation, and is rarely called directly.

## Do Not Use --reinstall to Recover from an Attack

Using apt --reinstall to restore packages modified during an attack will certainly not recover the system as it was. After an attack, you can't rely: apt might have been replaced by malicious programs, the attacker might have altered or created files outside control of dpkg. ## Leveraging --force-* to Repair Broken Dependencies

If you are not careful, the use of --force-* option or some other malfunction can lead to a system where the APT family of commands will refuse function. In effect, some of these options allow installation of a package when a dependency is not met, or when there is a conflict. The result is an inconsistent system from point of view, and the APT commands will refuse to execute any action except those that bring the system back to a consistent state. This usually results in a message like this, obtained after installing a new version of libc6:

```
You might want to run 'apt-get -f install' to correct these.
The following packages have unmet dependencies:
desktop: Depends: libc6 (>= 2.5) but 2.3.6-ds1 is installed
Unmet dependencies. Try using -f.
```

If you are a cautious administrator you may choose to ignore dependency or conflict and use the corresponding --force-* option. In this case, if you want to be able to continue you must delete or modify the dependency, this manipulation is an ugly hack and should never be used except in extreme case. Quite a more fitting solution is to recompile the package that is causing the problem or use a new version (potentially corrected) from backports (backports are newer versions especially recompiled to work in an older environment).

## 8.2.7. Frontends: aptitude and synaptic

APT is a C++ program whose code mainly resides in the libapt-pkg shared library. Thanks to shared library, it opened the door for the creation of user interfaces (frontends), since the shared library code can easily be reused. Historically, apt-get was only designed as front-end for libapt-pkg but its success tends to obscure this fact. Over time, despite the popularity of command line interfaces like apt and apt-get, various graphical interfaces were developed. We will take a look at two of these interfaces in this section: aptitude and synaptic.

### Aptitude

Aptitude, shown in Figure 8.1, "The aptitude package manager" [page 191], is an interactive program that can be used in semi-graphic on the console. You can browse the list of installed and available packages, look up all the information, and select packages to install or remove. The program is designed specifically to be used by administrators as its default behavior is much more intelligent than APT's, and its interface easier to understand.
