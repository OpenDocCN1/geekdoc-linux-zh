Downgrading to a Working Version When the problem is a clear regression (where the former version worked), you can try to downgrade the package. you will need to copy of the old version. If you have access to the old version in one of the repositories configured in APT, you can use a simple-liner command to downgrade (see section 8.2.2.2, "Installing Packages with APT" [page 177]). But with Kali's rolling release, you will only find a single version of each package at any time.

You can try to find the old .deb file and install it manually with dpkg. Old .deb files can be found in places:

+   - in APT's cache in /var/cache/apt/archives/
- in the pool directory of your usual Kali mirror (removed and obsolete packages are kept for three days to avoid problems with users not having the latest packages)
- in http://snapshot.debian.org if the affected package was provided by Debian and not by Kali; this service keeps historical versions of all Debian packages

Dealing with Maintainer Scripts Sometimes the upgrade gets interrupted because of the package maintainer scripts fails (usually, it is the postinst). In those cases, you can try to diagnose the problem, and possibly work it out, by editing the problematic script.

Here we rely on the fact that maintainer scripts are stored in /var/lib/dpkg/info/ and that we can review and modify them.

Since maintainer scripts are usually simple shell scripts, it is possible to add a -x line just after the shebang line and arrange them (with dpkg --configure -a for postinst) to see precisely what is happening and where it is failing. This output can nicely complement any bug report that you might use.

With this newly gained knowledge, you can either fixing the problem or transform the failing command into a working one (for example adding | true at the end of the line).

Note that this does not work for a failing precept since that package is executed even before the package gets installed so is not yet in its final location. It works for prerm and although you need to execute a package removal (respectively upgrade) to trigger them.

# The dpkg Log File

The dpkg tool keeps a log of all of its actions in /var/log/dpkg. This log is extremely verbose, since it details all the stages of each package. In addition to offering a way to track dpkg's behavior, it helps to keep a history of the development of the system: you can find the exact moment when each package has been installed or updated, and this information can be extremely useful in understanding a recent change in behavior. Additionally, with all versions being recorded, it is easy to cross-check the information with the changelog. Debian.gz for packages in question, or even with bug reports.
