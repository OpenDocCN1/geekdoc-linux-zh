## Retrieving Sources from Git

You might have noticed that the apt source invocation tells you about possible Git repository used to maintain the package. It might point to Debian repository or Kali repository. All Kali-specific packages are maintained in Kali repositories hosted at git.kali.org/packages/. You can retrieve the sources from those repositories with git clone https://gitlab.kali.org/packages/source.

Contrary to what you get with apt source, the obtained tree will not have patches applied. Have a look at debian/patches to learn about possible changes made by Kali.

### 9.1.2. Install'ing Build Dependencies

Now that you have the sources, you still need to install build dependencies. They will be necessary to build the desired binary packages but are also required for partial builds that you might want to test the changes while you make them.

Each source package declares its build dependencies in the Build-Depends field of debian/control file. Let's instruct apt to install them (assuming you are in a directory containing an unpacked package):

sudo apt build-dep ./

### 9.1.3. Making Changes

We can't cover all the possible changes that you want to make to a given package in this section. This would amount to teaching you all the nitty gritty details of Debian packaging. However, we will cover the three use cases presented earlier and will explain some of the unavoidable parts (like maintaining the changelog file).

The first thing to do is to change the package version number so that the rebuild packages can be distinguished from the original packages provided by Kali or Debian. To achieve this, we usually add a suffix identifying the entity (person or company) applying the changes. Since busy is my IRC name, we use it as a suffix. Such a change is effected with the dch command (Debian Changelog) package, with a command such as dch --local busy invokes an editor (sensible-editor, which runs the editor assigned in the VISUAL or EDITOR environment variables, or /usr/bin/editor otherwise), which allows you to document the differences introduced by this rebuild. This editor shows that dch really did change debian/changelog file:

$ dch --local busy

## Applying a Patch

In one of our cases, we have downloaded the pyrit source package and we want to apply a patch that we found in the upstream git repository. This is a common operation and it should always be simple. Unfortunately, patches can be handled in different ways depending on the source package format and on the Git packaging workflow.

**With an Unpacked Source Package** run apt source pyrit and you have a pyrit-0.4.0 directory. You can apply your patch directly with patch -p1 < patch-file:

```
$ apt source pyrit
[...
$ cd pyrit-0.4.0
$ wget https://github.com/JPaulMora/pyrit/commit/14
→ ec99174b8e8fd2022b6a97c57e19633f12a0-0 /tmp/pyrit-patch
[...]
$ patch -p1 </tmp/pyrit-patch
patching file cpyrt/pcktools.py
```
