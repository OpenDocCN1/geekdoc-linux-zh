## 10.3. Extending and Customizing Kali Linux

Sometimes you need to modify Kali to make it fit your local needs. The best way to achieve this is to maintain your own repository hosting the modified versions of the Kali packages you had to fork, as well as supplementary packages providing custom configuration and extra software (not provided by Kali).

### 10.3.1. Forking Kali Packages

Please refer to section 9.1 for explanations about this topic. All packages can be forked if you have a good reason but you must be aware that forking a package has a cost since you have to update it every time Kali publishes an update. Here are some reasons why you might want to fork a package:

- To add a patch to fix a bug or add a new feature. In most cases, you will want to submit that patch to the upstream developers so the bug is fixed or the feature is added.
- To compile it with different options (though better to discuss this with Kali developers to see if they can enable the desired options).
- To modify a configuration file. You have multiple options like using configuration management to automatically install a modified configuration file or putting a file in a configuration directory (when available) or divert the original configuration file.
- To update to a newer upstream version. Again, it is better to work with developers to update the package directly in Debian or Kali.

By contrast, here are some bad reasons to fork a package along with suggestions of how to handle your problem:

- kali-meta: this source package builds all the kali-linux-* packages and notably kali-linux-full, which defines what packages are installed in the default Kali ISO image.
- desktop-base: this source package contains various miscellaneous files that are used by default in desktop installations. Consider forking this if you would like to show your organization's brand in the default background or change the theme of the desktop.
- kali-menu: this package defines the structure of the Kali menu and provides .desktop files for all applications that should be listed in the Kali menu.

### 10.3.2. Creating Configuration

Now we have touched on Salt booting and discussed configuration management with SaltStack as well as package forking, it is time to wrap these processes into a practical example and extend the scenario by creating a custom configuration package to deploy a custom configuration to multiple machines automatically.

In this example, you will create a custom package that sets up and utilizes your own package repository and GPG signing key, distributes a SaltStack configuration, pushes a custom background, and provides default desktop settings in a unified way to all your Kali installations. This may seem a daunting task (especially if you glance through the Debian Maintainer Guide) but fortunately for you, a configuration package is mainly a sophisticated file archive and turning it into a package is rather easy.

The offsec-defaults package will contain a few files:

- etc/apt/sources.list.d/offsec.list: a sources.list entry for APT, enabling the company's internal package repository
- etc/apt/trusted.gpg.d/offsec.gpg: the GPG key used to sign the company's internal package repository
- etc/salt/minion.offsec.conf: a SaltStack configuration file to indicate where to find the Salt master
- /usr/share/images/offsec/background.png: a nice background image with the Offensive Security logo
- /usr/share/glib-2.0/schemas/90_offsec-defaults.gschema.override: a file providing default settings for the GNOME desktop

First create an offsec-defaults-1.0 directory and put all the files in that directory. Then run dh_make --native (from the dh-make package) to add Debian packaging instructions, which are stored in the debian/ subdirectory.
