As a more concrete sample, you could easily set up a distributed Nmap scan with dnmap. After installing the package on all the minions, you start the server in a first terminal:

```
server# salt '*' pkg.install dnmap
[...]
server# vim dnmap.txt
server# dnmap_server -f dnmap.txt
```

Assuming that the IP is 1.2.3.4, you can now tell all minions to start a client process that connects to the server:

```
server# salt '*' cmd.run_bg template='dnmap_client -s 1.2.3.4 -a {{grains.id}}
kali-scratch:

pid:
17137
[]]
```

Note that the example uses cmd.run_bg to run the dnmap_client command in the background. Don't wait until it finishes, for it is a long-running process. Unfortunately, it doesn't kill itself properly when you interrupt the server so you might have to clean it up:

```
server# salt '*' cmd.shell -f dnmap_client
```

# 10.2.3. Salt States and Other Features

While remote execution is an important building block, it is only a tiny fraction of what SaltStack can do.

When setting up a new machine, you often run many commands and tests to determine the details of the system prior to installation. These operations are formalized in re-usable configuration templates called state files. The operations are described in state files can then be performed with a single state.apply salt command.

To save time, you can rely on ready-to-use state files that have been created by the community and are distributed in "Salt formulas":

+   - https://docs.saltstack.com/latest/topics/development/conventions/formulas.html

There are many other features that can be combined:

+   - Scheduled execution of actions
- Defining actions in response to events triggered by minions
- Collecting data out of minions
