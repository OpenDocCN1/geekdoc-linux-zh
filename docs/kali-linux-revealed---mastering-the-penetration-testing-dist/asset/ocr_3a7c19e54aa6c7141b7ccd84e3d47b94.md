If you find an existing bug report, subscribe to and possibly add supplementary information. Do not post comments as "Me too" or "+"; they serve no purpose. But you can indicate that you are available for further tests if the original submitter did not offer this.

If you have not found any report of your problem, go ahead and file it. If you have found related tickets, be sure to mention them.

Ensure You Use the Latest Version It is very frustrating for developers to receive bug reports for problems that they have already solved or problems that they can't resolve with the version they are using (developers almost always use the latest version of their product). Even when older versions are maintained by the developers, the support is limited to security fixes and major problems. Are you sure that your bug is one of those?

That is why, before filing a bug report, make sure that you are using the latest version of the problematic system and application and that you can reproduce the problem in situation.

If Kali Linux does not offer the latest version of the application (neither in kali-rolling nor in bleeding-edge, see 8.1.3.3,"The Kali-Bleeding-Edge Repository"[page 174]), you have alternative solutions: you can try a manual installation of the latest version in thru-way aerial machine, or you can review the upstream ChangeLog (or Git history) to see that there hasn't been any change that could fix the problem you are seeing (and then file the bug you did not try the latest version).

Do Not Mix Issues in a Single Bug Report File one bug report per issue. That way, the subsequent discussions not get too messy and each bug can be fixed according to its own schedule. If you don't that, either the single bug needs to be repurposed multiple times and can only be closed when all issues have been fixed, or the developers file the supplementary reports that you should have created in the first place.
