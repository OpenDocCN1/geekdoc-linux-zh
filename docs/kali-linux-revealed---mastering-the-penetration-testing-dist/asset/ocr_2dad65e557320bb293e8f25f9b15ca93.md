# 5.4. Managing Services

Kali uses systemd as its init system, which is not only responsible for the boot sequence, but also permanently acts as a full featured service manager, starting and monitoring services.

systemd can be queried and controlled with systemctl command. Without any argument, it runs the systemctl list-units command, which outputs a list of the active units. If you run systemctl status, the output shows a hierarchical overview of the running services. Comparing both outputs, you immediately see that there are multiple kinds of units and services that are only one among them.

Each service is represented by a service unit, which is described by a service file usually shipped in /lib/systemd/system/, or /run/systemd/system/, or /etc/systemd/system/; they are listed by increasing order of importance, and the last one. Each is possibly modified by service-name.*.conf files in the set of directories. These units are plain text files whose format is inspired by the well-known \*.ini files of Microsoft Windows, with value pairs grouped between [section] headers. Here we see a sample service file for /lib/system/ssh.service:

[Unit]

```
Description=Secure Shell server
After=network.target audit.service
ConditionPathExists=!/etc/ssh/sshd_not_to_be_run
```

[Service]

```
Environment=/etc/default/ssh
ExecStart=/usr/sbin/sshd -D $SSHD_OPTS
ExecReload=/bin/kill -HUP $MAINPID
KillMode=process
Restart=on-failure
RestartPreventExitStatus=255
Type=notify
```

[Install]

```
WantedBy=multi-user.target
Alias=sshd.service
```

Target units are another part of systemd's design. They represent a desired state that you want to attain in means activated units (which means a running service in the case of units). They exist mainly as a way to group dependencies on other units. When the system starts, it enables the units to reach the default.target (which is a symlink to graphical.target, and which in turn depends on multi-user.target). So all the dependencies of those targets get activated during boot.
