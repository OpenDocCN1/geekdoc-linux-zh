Issues related to system administration are specifically excluded from POSIX.1, as are implementation details. After all, an application program does not know how to create a new device special file and does not care how the open() function (which opens a file) works internally. By avoiding implementation issues, the standard allows systems that are not based on UNIX to conform to POSIX.1.

The POSIX.1 committee was responsible for codifying existing practice, not engineering a new version of the UNIX system. During the development of the POSIX.1 standard, partitions of BSD and System V were forced to reconcile differences. In some cases this meant standardizing on behavior one or the other version. In some cases the working group decided that both the BSD and System V implementations of some features were deficient and created new interfaces (such as terminal control) based on existing practice but with new syntax and semantics. No compromise seemed to be reachable, the working group adopted optional behavior. For example, BSD had job control at least since release 4.1, whereas SVR3 does not support job control. POSIX.1 makes job control an option.

One compromise took a unique form. POSIX.1 specifies for file archives. On UNIX System V, the preferred archive format is cpio (page 1124). On BSD the preferred format is tar (page 1343). POSIX.1 requires that both formats are supported, in slightly modified forms. Because the specification of utilities is outside the scope of POSIX.1, neither the cpio nor the tar is mentioned; only the file formats for the archives are part of the standard. POSIX.1 requires that the implementation provide unnamed archive creation and reading utilities. See page 1439 for a discussion of the pax utility specified by POSIX.2.

The POSIX.1 standard is available from the American National Standards Institute (ANSI) or from the IEEE. In addition, the standard has been adopted as an international standard by the International Standards Organization (ISO) and the International Electromechanical Commission (IEC), which jointly coordinate international computing standards.

# Appendix D The POSIX Standards

# POSIX.2

POSIX.2, the shell and utilities standard, is most important for users, as opposed to application developers. Its principal purpose is to specify the semantics of the shell (based on the Korn Shell) and a collection of utilities that you can use to develop portable shell scripts. A secondary purpose is to promote user portability. This term refers to a standard specification for utilities, such as vi, man, and others, that are not useful for scripts but are typically used interactively.

POSIX.2 is independent of POSIX.1, and a system can claim conformance to POSIX.2 without claiming conformance to POSIX.1. This is not true of most of the other POSIX standards, which take POSIX.1 as a base. In practice you can expect virtually all UNIX systems to comply with both POSIX.1 and POSIX.2 within a few years. Many non-UNIX systems will also comply, making them “UNIX-like,” at least on the outside. Although it has not formally certified, GNU/Linux conforms to the requirements of POSIX.2 in many respects. For example, the GNU Bourne Again Shell page states: “It is intended to be a conformant implementation of the IEEE POSIX Shell and Tools specification."

# Localization

One of the most important features of POSIX.2 is that it is fully localized. That is, it describes the behavior of the shell and utilities in the context of different character sets and locale-specific information (such as date and time formats). For example, the grep utility has a -option that causes grep to ignore case in determining matches. POSIX.2 specifies what this means for alphabets in which the uppercase mapping is either defined or not one-to-one.

The general idea behind localization is that every process executes in a particular locale. The POSIX.2 defines a locale as “the definition of the subset of the environment of a user that depends on language and cultural conventions.” The locale describes how the process should display or interpret information that depends on the language and culture, including character set and the method of writing times, dates, numbers, and currency amounts. Localization is not unique to POSIX.2; both the C standard and POSIX.1 support it to a limited degree. However, POSIX.2 is much more specific in its description of how locale-specific information is provided to the system and how it affects the system’s operation.

An important feature of POSIX.2 locales is that they are fragmented into categories. The standard specifies six locale categories and defines six environment variables corresponding to these categories (Table D-2).

## ## Environment Variable Table D-2

| Environment Variable | Description |
|---|---|
| LC_TYPE | Describes which characters are considered alphabetic, numeric, punctuation, blank |
| LC_COLLATE | Describes the order of characters |
| LC_TIME | Describes abbreviated and full names for months and days |
| LC_NUMERIC | Describes the character to separate groups |
| LC_MONETARY | Describes the currency symbol and fractional digits |
| LC_MESSAGES | Describes the diagnostic messages |

Two more environment variables (LC_ALL and LANG) interact with these six. If LC_ALL is set, then its value is used in place of all. If LANG is set, then its value is used in place of any LC_* that is not set.

# The POSIX Shell

POSIX.2 specifies the syntax and semantics of a shell command language. The POSIX shell is generically named sh which is most closely based on the Korn Shell. The GNU/Linux Z Shell (Chapter 15) also resembles ksh. The POSIX shell is almost a subset of the 1988 version of ksh. Both the GNU/Linux zsh and newer versions of ksh have been designed as supersets of the POSIX shell. If you want to write shell scripts that are portable across all POSIX implementations, you should try to avoid using constructs that are not supported by the POSIX shell.
