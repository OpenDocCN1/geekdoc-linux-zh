PAM provides authentication for a variety of system-entry services (login, ftp, and so on). You can take advantage of PAM's ability to authenticate system-entry services with different authentication mechanisms, such as RSA, DCE, Kerberos, and smart cards.

From login using us su to shutting the system down, whenever you are asked for a password (or not asked for a password because the system trusts that you are who you say you are), PAM makes it possible for systems administrators to configure the authentication process and makes the configuration process exactly the same for all applications that PAM use to do their authentication.

The configuration files stored in /etc/pam.d describe the authentication procedure for each application. These files usually have names that are the same as similar to the name of the application they configure. For example, authentication for login is configured in /etc/pam.d/login. The name of the file is the name of the PAM service that the files configure. Occasionally one file may serve two programs.

# Do Not Lock Yourself Out of Your System

Editing PAM configuration files correctly takes care and attention. It is easy to lock yourself out of your computer with a single mistake. To avoid this type of problem, always keep backup copies of the PAM files you edit, test every change thoroughly, and make sure that you can still log in once the change is installed. Keep a Superuser session open until you are done. When a change fails and you cannot log in, use the Superuser to replace the newly edited files with your backup copies.

PAM warns you about any errors it encounters, logging them to the /var/log/messages or /var/log/secure files. Look inside these files if you are trying to figure out why a changed PAM file is not working properly. In order to prevent possibly giving unnecessary information to a malicious user, PAM sends error messages to a file rather than to the screen.

There is no relationship between PAM services and the /etc/services files. The name of the PAM service is an arbitrary string that each application gives to PAM; PAM then looks up the configuration file with that name and uses it to control how it authenticates. There is no central registry of PAM service

# Configuration File, Module Type, and Control Flag

Following is an example of a PAM configuration file. Comment lines begin with a pound sign (#):

```
$ cat /etc/pam.d/login
#%PAM-1.0
auth      required      /lib/security/pam_securetty.so
auth      required      /lib/security/pam_stack.so service=system-auth
auth      required      /lib/security/pam_nologin.so
account   required      /lib/security/pam_stack.so service=system-auth
password  required      /lib/security/pam_stack.so service=system-auth
session   required      /lib/security/pam_stack.so service=system-auth
session   optional      /lib/security/pam_console.so
```

The first line is a special comment; it will become significant only if another PAM format is released. Do not use # other than this in the first line of the preceding example.

The rest of the lines tell PAM to do something as part of the authentication process: account, auth, password, or session (Table 17-19). The second is a control flag (Table 17-20), which indicates what the rest of the line contains the pathname of a PAM module and any arguments for that module. The PAM library itself uses the /etc/pam.d files to determine which modules delegate work.

| Module Type | Description | Controls |
|---|---|---|
| auth | Authentication | Proving that the user is authorized to use the service. This may be done using passwords or another mechanism. |
| account | Account management | Determining whether an already authenticated user is allowed to use the service he/she is trying to use. (That is, has the account expired? Is the user allowed to use this service at this time of day?) |
| password | Password changing | Updates authentication mechanisms such as user passwords. |
| session | Session management | Setting things up when the service is started (for example, when the user logs in) and breaking them down when the service is terminated (for example, when the user logs out). |

# Control Flag

You can use one of the Control Flag keywords listed in Table 17-20 to select control flags.

| required | |

Success is required for authentication to succeed. Control and a failure result are returned after all the modules in the stack have been executed. The technique of delaying the report to the calling program until all modules have been executed may keep attackers from knowing what caused their authentication attempts to fail and tell them less about the system, making it more difficult for them to break in. |

| requisite | |

Success is required for authentication to succeed. Further module processing is aborted, and control is returned immediately after a module fails. This technique may expose information about the system to an attacker. On the other hand, if it prevents a user from giving a password over an insecure connection, it might keep information out of the hands of an attacker. |

| sufficient | |

Success indicates that this module type has succeeded, and subsequent required modules of this type are executed. Failure is not fatal to the stack of this module type. This technique is generally used when one form or another of authentication is good enough: If one fails, PAM tries the other. For example, when you use rsh to connect to another computer, pam_hosts first checks to see whether your connection can be trusted without a password. If the connection can be trusted, the pam_hosts module reports success.

| optional | |

Result is generally ignored. An optional module is relevant only when it is the only module on the stack. PAM uses each of the module types as requested by the application.

# Example

Part of the login service's authentication stack follows as an example:

```
$ cat /etc/pam.d/login
#%PAM-1.0
auth      required      /lib/security/pam_securetty.so
auth      required      /lib/security/pam_stack.so service=system-auth
auth      required      /lib/security/pam_nlogin.so
```
