
# Chapter 17 Red Hat Linux System Administration

## Keeping the System Secure

No system with dial-in lines or public access to terminals is absolutely secure. You can make your system as secure as possible by changing the Superuser password frequently and choosing passwords that are difficult to guess. Do not tell anyone who does not absolutely need to know the Superuser password. You can also encourage users to choose difficult passwords and change them periodically.

By default, passwords on Red Hat Linux use MD5 (page 1478) hashing, which makes them more difficult to break than DES (page 1409) encrypted passwords. It makes little difference how well encrypted your password is if it is easy for someone to find out or guess what it is.

A password that is difficult to guess is one that else would not be likely to choose. Do not use words from the dictionary (spell forward or backward); names of relatives, parents, or friends; or words from a foreign language. A good strategy is to choose a couple of short words, include some punctuation (for example, put a ^ between them), mix the case, and replace a couple of the letters in the numbers. If these were not printed in this book, an example of a good password would be C&yGram5 (candygrams). Ideally you would use a random combination of ASCII characters, but that would be difficult to remember.

You can use one of several excellent password-cracking programs to find users who have chosen poor passwords. These programs work by repeatedly encrypting passwords from dictionaries, phrases, names, and other sources. If the encrypted password matches the output of the program, the program has found the password of the user. Two programs that crack passwords are crack and cops. And many other security tips and programs are available from CERT (www.cert.org), which was originally called the computer emergency response team. Specifically look at www.cert.org/tech_tips.

Make sure that no one except Superuser can write to files containing programs that are owned by root and run in setuid mode (for example, mail and sudo). Also make sure that users do not transfer programs that run in setuid mode and are owned by root the system by mounting tapes or disks. These programs can be used to circumvent system security. Refer to chmod in Part III for more information about setuid mode. One technique that prevents users from having set files is to use the -nosuid flag to mount, which you can set in the sections of the fstab file. Refer to "/etc/fstab" on page 959.

The BIOS in many machines gives you some degree of protection from an unauthorized person modifying the BIOS or restarting the system. When you set up your BIOS, look for a section named Security. You can probably set up a BIOS password.

## Monitoring Disk Usage

Sooner or later, you will start to run out of disk space. Do not fill up a disk; GNU/Linux can write to files significantly faster if at least 5 percent to 30 percent of the disk space in a given filesystem is free. The result is that using more than the maximum optimal disk space in a filesystem can degrade system performance.

When the filesystem becomes full, it can become fragmented. This is similar to the DOS concept of fragmentation but is not nearly as pronounced and is typically not on modern GNU/Linux filesystems; by design GNU/Linux filesystems are resistant to fragmentation. Keep your filesystems from running full capacity, and you may never need to worry about fragmentation at all. If there is no space on filesystem, you cannot write to it at all.

To check on fragmentation, you can mount the filesystem and run fsck on. As part of fsck execution, fragmentation is computed and displayed. You can defragment a filesystem by backing it up; using mkfs (page 1057) to make a clean, empty image; and restoring the filesystem. The utility that you use to do your backup and restore is irrelevant and completely up to you. You can use dump/restore, tar, cpio, or a third-party backup program.

Linux provides several programs that report on using how much disk space on what filesystems. Refer to the du, quot, and df utilities the size of free utility in Part III. In addition to these utilities, you can use the disk quota system to manage disk space.

The main ways to increase the amount of free space on a filesystem are to compress files, delete files, grow filesystems, and condense directories. This section contains some ways to maintain a filesystem so that it does not get overloaded.

## Files That Grow Quickly

Some files, as log files and temporary files, grow automatically over time. Core dump files take up space and are rarely needed. Also, users occasionally run programs that accidentally generate huge files. As the system administrator, you must review these files periodically so that they do not get out of hand.

If a filesystem is running out of space (that is, over a period of an hour rather than weeks or months), first figure out why it is running out of space. Use a ps -ef command to determine whether a user has created a runaway process that is creating a huge file. In the output of ps, look for a process that has used a large amount of CPU time. If such a process is running and creating a large file, the file will continue to grow as you free space. If you remove the huge file, the space occupied will not be freed until the process terminates, so you need to kill the process. Try to contact the user running the process, and ask the user to kill it. If you cannot contact the user, log in as root and kill the process. Refer to kill in Part III for more information.

You can also truncate a large log file rather than removing it, although you can deal with this situation with logrotate. For example, if the log/messages file has become very large because syslog daemon is misconfigured, you can use the following:

```bash
cat /dev/null > /log/messages
```

If you remove /log/messages, you have to restart syslogd. Without restarting syslogd, the space on the filesystem is not released.

When no single process is consuming the disk space but has instead used up gradually, locate unused files and delete them. You can archive them using cpio, dump, or tar before you delete them. You can safely remove most files that have not been accessed for several days. The following command performs this without removing necessary files (such as /dev/core, which is a symbolic link to /proc/kcore):

```bash
find -type f -name core | grep '8 core file' | sed 's/.*://$ | xargs rm -f
```

The find command lists all ordinary files named core and sends its output to xargs, which runs rm on each of the files. The file utility displays a string that includes 8 core file for files created as the result of a core dump. These files need to be removed. The grep command filters out from lines that do not contain this string. Finally, sed removes everything following the colon so that all is left on the line is the pathname of the core file; xargs removes the file.

Look through the /tmp and /var/tmp directories for temporary files and remove them. Keep track of disk usage in /var/mail, /var/spool, and /var/log.

## logrotate: Manages Log Files

Rather than deleting or truncating log files, you may want to keep the contents around a while in case you need to refer to them. The logrotate utility helps you manage system log (and other) files automatically by rotating (page 1490), pressing, mailing, and removing each as you specify. The logrotate utility is controlled by the /etc/logrotate.conf file, which sets default values and can optionally specify files to be rotated. logrotate.conf has an include statement that points to unit-specific specification files in /etc/logrotate.d. Following is the default logrotate.conf:

```bash
# cat /etc/logrotate.conf
# see "logrotate" for details
# rotate log files weekly
```

```bash
# keep 4 weeks worth of backlogs
rotate 4
```

```bash
# create (empty) log files after rotating old ones
create
```

```bash
# uncomment this if you want your log files compressed
compress
```
