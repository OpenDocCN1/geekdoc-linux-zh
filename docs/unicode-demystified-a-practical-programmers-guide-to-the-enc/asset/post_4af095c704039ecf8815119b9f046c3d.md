When it needs to map a number to the corresponding group name, a utility encounters the plus sign (+) and knows to query the NIS server at that point for the answer. You can display the **group** database with the ypcat utility:

```
$ ypcat group
```

pubs::141:alex,jenny,scott,hls,barbara
...

Or you can search for a particular group name by using ypmatch:

```
$ ypmatch puts group
pubs::141:alex,jenny,scott,hls,barbara
```

You can retrieve the same information by filtering the output of ypcat grep, ypmatch is more efficient because it searches the database directly, using a single process. The NIS database name is not the full pathname of the file it replaces; the NIS database name is the same as the simple filename (group, not /etc/group). The ypmatch utility works only on the key for the table (the group name in case of groups). When you want to match members of the group, the group number, or other fields of a map (such as the full name in the passwd map), you need to use ypcat with grep.

With DNS, ordinary users not be aware that NIS is managing system configuration files. Setting up and maintaining the NIS databases is a task for the system administrator; individual users and users on single-user GNU/Linux systems rarely need to work directly with NIS.

# NFS: Network Filesystem

NFS lets you work locally with files that are stored on a remote computer's disks. The remote system is the fileserver (server); the local system is the client. The client requests of the server.

Unfortunately NFS is based on the trusted-host paradigm (page 373) and there has all the security shortcomings that plague services based on this paradigm.

NFS is configured by the person responsible for the system. When you work with a file, you may not be aware of where the file is physically stored. In many computer facilities today, user files are commonly stored on a central fileserver equipped with many large-capacity disk drives and devices that quickly and easily make backup copies of the data. A GNU/Linux system may be diskless, where a floppy disk (or CD-ROM) is used to start GNU/Linux and load system from another machine on the network. The Linux Terminal Server Project (LTSP.org) Web says it all: "Linux makes a great platform for deploying diskless workstations that boot from a network server. The LTSP is about running thin client computers in a GNU/Linux environment." Because a diskless workstation not require a level of computing power, you can give older, retired computers a second life by using them as diskless systems.

Another type of GNU/Linux system is the datalystem, in which the client has a disk but stores no user data (only GNU/Linux and the applications are kept on the disk). Setting up this type of system is a matter of choosing which filesystems arely remotely mounted.

You can even netboot (page 1481) some machines. Red Hat includes the PXE (Preboot Execution Environment) server package for booting Intel machines. Older machines with netcard-mounted boot ROMs sometimes use tuff (file transfer protocol) for netbooting. Non-Intel architectures have historically included netboot capabilities that Red Hat supports. The Linux kernel contains the ability to be built to mount root (/), using NFS.

Of the many ways to set up your system, the one you choose depends on what you want to do. See the Remote-boot mini HOWTO for more information.

The df utility displays a list of the filesystems available on your system, along with the amount of disk space, free and used, on each. Filesystem names that are pended with hostname: are available to you through NFS.

Refer page 1147 in Part III for more information on the physical location of your files should not matter to you; all the standard GNU/Linux utilities work with NFS the same way they operate with local files. At times, however, you may lose access to your remote files: Your computer may be up and running, but a network problem or a remote server crash may make these files temporarily unavailable: When you try to access a remote file, you will get an error message, such as NFS not responding. When your system can contact the remote server again, you see a message, such as NFS OK.

With distributed computing you can log in on any machine on the network, and all startup scripts easily available. Whichever machine you log in, your home directory will be waiting for you. Having all machines mount all the time can be problematic. Suppose that machine A mounts some filesystems from machine B and B mounts from machine A. What happens when you bring one of these down for maintenance or it crashes? In what order do you reboot when they depend on each other to up? In a large network you can have one machine mounting disks from tens or hundreds of others for software files and home directories. One way around this problem is to mount filesystems only on demand. GNU/Linux machines mount is handled by the autofs system (the automount daemon), which is replacing the older, less efficient amd (automount daemon). Because autofs runs in kernel space (and runs in user space), you need to have support for it in the kernel. For example, when you issue the command /home/auto map finds that alex is a key that says to mount frank/homes, and mounts the remote filesystem. Once the filesystem is mounted, is displays the list of files you want to see. If after this mounting you give the command /home, shows that alex is present within the /home directory. The df utility shows that alex is mounted from frank. By the default automount daemon automatically unmounts this filesystem after five minutes of inactivity.

Automounting filesystems is similar in concept to MS Windows neighborhood. When you know there are NFS servers named frank, zach, and madison, you can see all the filesystems that are exported by each using to display (/net/frank, /net/adapters, and /net/madison). Once these systems mounted, you can browse through them if you have permission. The GNU/Linux automount facility is flexible and powerful. Refer to autofs: "Automatically Mounts Filesystems" on page 979 and the automount man page for more information.

# Internet Services

GNU/Linux Internet services are provided by daemons that run continuously or by daemon that is started automatically by the xinetd daemon (page 397) when a service request comes in. The /etc/services file lists network services (for example telnet, ftp, ssh) and their associated numbers. A service that uses TCP/IP or UDP uses an entry in this file. IANA (Internet Assigned Numbers Authority) maintains a database of all permanent, registered services. The /etc/services file usually lists a small, commonly used subset of services. Go to www.rfc.net/rfc1700.html for more information and a complete list of registered services.

Most of the daemons (the executable files) are stored in /usr/bin. By convention the names of many daemons end with the letter d to distinguish them from units. The prefix in. or rpc is often used for names. Look at /usr/sbin/ to see a list of many the daemons on your system. Refer to “rc Scripts: Start and Stop System Services” on page 944 and service: Configures Services 1 on page 945 for information about starting and stopping these daemons.

For example, when you run ssh, your local system connects the ssh daemon (sshd) to the remote system to establish the connection. The two systems negotiate the connection according to a fixed protocol. Each system identifies itself to the other, and then they take turns asking each other specific questions and waiting for valid replies. Each network service follows its own protocol.

In addition to the daemons that support the utilities described up to this point, many other daemons support system-level network services that you will not interact with. Some of these daemons are listed in Table 9-4.

| Daemon | Used For By | Function |
| --- | :--- | :--- |
| apmd | Advanced power management | Reports and takes action on specified changes in system power, including shutdowns. Very useful with machines, such as laptops, that run on batteries. |
| atd | at | Executes a command once at a specific time and date. See cron for periodic execution of a command. |
| automount | Automatic mounting | Automatically mounts filesystems when they are accessed. Automatic mounting is a way of demand-mounting remote directories without having to hard-configure them into /etc/fstab. |
