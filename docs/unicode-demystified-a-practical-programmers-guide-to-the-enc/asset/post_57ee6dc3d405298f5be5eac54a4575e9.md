# Figure 13-7 A case flowchart

The case structure is

``````
case test-string in
  pattern-1)
    commands-1
    ;
  pattern-2)
    commands-2
    ;
  pattern-3)
    commands-3
    ;
esac
```

# Chapter 13 Programming the Bourne Shell

The following case structure uses the character that the user enters the string. If the test-string has a value of A, the structure executes the command following the pattern A. The right parenthesis is part of the case control structure, not part of the pattern. If the test-string has a value of B or C, the structure executes the command following the matching pattern. The asterisk (*) indicates any string of characters and serves as a catchall when there is no match. If no pattern matches the test-string and if there is no catchall (*) pattern, control passes to the command following the esac statement, without the case structure taking any action. The second sample execution of case1 shows the user entering a lowercase b. Because the test-string does not match the uppercase B or any other pattern in the case statement, the program executes the following catchall pattern and displays a message:

```
$ case1
echo "Enter A, B, or C: "
read letter
case "$letter" in
A)
    echo "You entered A"
    ;;
B)
    echo "You entered B"
    ;;
C)
    echo "You entered C"
    ;;
*)
    echo "You did not enter A, B, or C"
    ;;
esac
```

```
$ case1
Enter A, B, or C: B
You entered B
$ case1
Enter A, B, or C: b
You did not enter A, B, or C
```

The pattern in the case structure is analogous to that of an ambiguous file-referencing. The pattern can include any of the special characters and strings shown in Table 13-2.

# Pattern table 13-2

| Pattern | Description |
| :--- | :--- |
| * | Matches any string of characters. Use it for the default case. |
| ? | Matches any single character. |

# Pattern (Continued)

| Pattern | Description |
| :--- | :--- |
| [...] | Defines a character class. Any characters enclosed within brackets are tried, one at a time, in an attempt to match a single character. A hyphen between two characters specifies a range of characters. |
| \| | Separates alternative choices that satisfy a particular branch of the case structure. |

You can use the case control structure to take various actions in a script, depending on how many arguments the script is called with. The following script, safedit, uses a case structure based on the number of arguments. safedit script saves a backup copy of a file you are editing with:

```
$ cat safedit
#!/bin/bash
PATH=/bin:/usr/bin
script=$(basename $0)
case $# in
0)
    vi $0
    exit 0
    ;
1)
    if [ -f "$1" ]
    then
        vi "$1"
        exit 0
    fi
    if [ -r "$1" -w "$1" ]
    then
        echo "$script: check permissions on $1" >&2
        exit 1
    else
        editfile=$1
    fi
    if [ ! -w "$editfile" ]
    then
        echo "$script: backup cannot be created in working directory" >&2
        exit 1
    fi
    *)
    echo "Usage: $script [file-to-edit]" >&2
    exit 1
    fi
esac
tempfile=/tmp/$.script
cp $1 $tempfile
if [ -e $tempfile ]
then
    mv $tempfile bak.$(basename $tempfile)
    echo "$script: backup file created"
else
    echo "$script: edit error--copy of original file is in"
fi
```

If you call safedit without any arguments, the case structure executes its first branch and calls vi without a filename. Because an existing file is not being edited, safedit does not create a backup file (See the :w command on page 426 for explanation of how to exit from vi when you have called it without a filename.). If you call safedit with one argument, the script runs in the second branch of the case structure and verifies that the file specified by $1 does not exist or is a file for which the user has read and write permission. The safedit script also verifies that the user has write permission for the working directory. If the user calls safedit with more than one argument, the third branch of the case structure presents a usage message and exits with status 1.

In addition to the use of a case structure for branching on the number of command line arguments, the safedit script introduces several other features. At the beginning of the script, the PATH variable is set to search /bin and /usr/bin. This ensures that the commands executed by the script are standard utilities which are kept in those directories. By setting PATH inside a script, you can avoid the problems that might occur if users have set up PATH to search their own directories first and have scripts or programs with the same names as utilities the script uses. Second, the following line creates a variable named script and assigns the simple filename of the script to it:

# Control Structures 657

The basename utility sends the simple filename component of its argument to standard output, which is assigned to the script variable using command substitution. No matter which of the following commands the user calls the script with, the output of basename is the simple filename safedit:

```
$ /home/alex/bin/safedit memo
$ safedit memo
$ safedit memo
```

After the script variable is set, it is used in place of the filename of the script in usage and error messages. By using a variable that is derived from the command invoked the script rather than a filename that is hardcoded (typed directly) into the script, you can move the script or rename it, and usage and error messages will still provide accurate information.

A third significant feature of safedit is the use of the $$ variable in the name of a temporary file. The statement before the esac statement creates and assigns a value to the tempfile variable. This contains name of a temporary file that is stored in the /tmp directory, as are many temporary files. The temporary filename begins with the PID of the current shell and ends with the name of the script. The PID is used because it ensures the filename is unique, and safedit will not attempt to overwrite an existing file, as might happen if two people were using safedit at the same time and not using unique filenames. The name of the script is appended so that, should the file be in /tmp for some reason, you can figure out where it came from.

The PID is used in front of rather than after $$ in the filename because of the 14-character limit on filenames on some filesystems on older versions of UNIX. GNU/Linux systems do not have this limitation. Because the PID ensures the uniqueness of the filename, it is placed first so that it cannot be truncated.(If the $$script component is truncated, the filename is still unique.) For the same reason, when a backup file is created inside the if structure a few lines down in the script, the filename is composed of the string bak followed by the name of the file being edited. On an older system, if bak were used as a suffix rather a prefix and the original filename was 14 characters, .bak might be lost, and the original file would be overwritten. The basename utility extracts the simple filename of $$safedit before it is prefixed with .bak.
