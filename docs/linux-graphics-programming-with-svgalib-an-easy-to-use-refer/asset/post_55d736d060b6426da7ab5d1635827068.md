## Pseudo Screen Savers

One nifty device you'll find in Windows, Macintosh, and, yes, even the X Windowing System is the *screen saver*. The original concept of the screen saver was to (obviously) save your monitor's screen from burning out. The problem was that back in the old days (and even today, to a lesser extent), if a monitor displayed the same image for a long enough period of time, that image would become permanently etched onto the screen. This was especially prevalent in terminals used for data entry. (If you've ever seen one of these monitors at a garage sale, you know exactly what I mean. There's nothing worse than trying to type when you've got the remnants of some ancient word-processing program obstructing your view.)

To combat this, the screen saver was developed. The concept was simple enough: After a certain period of inactivity, the screen would "blank" itself out. And that was a *true* screen saver. Later on, of course, we had the flying toasters and geometric eye candy that were designed to amuse more than they were ever intended to prevent burn-in.

As you probably know, Linux has the basic screen-blanking facility built into the kernel. This is accessed with a simple command, such as the following:

```
/bin/setterm -blank 15
```

With that, your screen will go blank after 15 minutes of inactivity. The actual code to make it happen is contained in /usr/src/linux/drivers/char/console.c.

Don't go hacking that file just yet, though. Any attempt to execute an SVGAlib program there will crash your system, for the same reasons that you have to use ifbcon to show graphics on startup (the kernel's in protected mode). You'll get colors on your screen, all right, but probably not the ones you want.

I'm not about to go into the intricacies of integrating a screen saver into your kernel (for the same reasons I cut short my discussion on boot-time graphics), but I will show you how to make a "fake" screen saver. (Fake, you say? What's the problem?) Well, it's fake because you have to start it yourself.

Bear with me. The fake screen saver (or self-displaying graphic) is an excellent vehicle to start learning about netpbm (pbm stands for Portable Pixmap). Netpbm is an improvement on the original pbmpls package, created by Jef Poskanzer, and is filled with tons of great code. The package contains a number of utilities that will break down a graphic file into a regular text file, and that text file will be filled with the RGB values of every pixel in the image. (To learn more about graphic files, see Chapter 9.)

Without knowing anything about the layout of a BMP file, for example, I can type this:

```
bmptopnm sample.bmp > netpnm.output
```

That will give me a text file (netpnm.output) that looks something like this:

```
P3
256 416
255
142 160 195 142 160 195 142 160 195 166 173 219
166 173 219 166 173 219 166 173 219 166 173 219
166 173 219 166 173 219 166 173 219 166 173 219
166 173 219 166 173 219 166 173 219 166 173 219
```

This is a portable bitmap, containing, as I said, the RGB value of every pixel in the image. Now, what do with it?

You can use the scripting language Perl to quickly read the output file and, then, using that data, compose the source to an SVGAlib program. In other words, you can use Perl to write your "self-displaying graphic" software. Listing 6.9 shows how this might be done.

### Listing 6.9 Parsing bmptopnm's output.

```perl
#!/usr/bin/perl

open (INFILE, "<netpnm.output");
open (OUTFILE, ">svgaffiche.c");

# The next three lines bypass the header info.
$garbage = <INFILE>;
$garbage = <INFILE>;
$garbage = <INFILE>;

$x = 0;
$y = 0;

while (<INFILE>)
{
    @rgb = split (/ /, $_);
    for ($i = 0; $i < @rgb; $i++)
    {
        ($r, $g, $b) = split (/ /, $rgb[$i], 3);
        print OUTFILE "gl_setpixelrgb($x, $y, $r, $g, $b);\n";
    }
    if (@rgb < 6)
    {
        $x = 0;
        $y++;
    }
}

close (OUTFILE);
close (INFILE);

0;
```

You can then use the output of this program to build your self-displaying graphic. Of course, this will be a minimum of 64,000 gl_setpixelrgb() statements, so you might be able to optimize the process by combining adjacent pixels with the same color values into a gl_hline() command.

### What Is A Font?

Some might argue that fonts aren't really a part of graphics, but I disagree. Fonts appear on the screen, and they comprise a significant portion of graphical programs, so I feel their inclusion here is appropriate. In this chapter, I'll cover what fonts are and how they work with SVGAlib. You'll then learn how to utilize existing fonts and create your own, either by hand or with the assistance of a "font generation" program. Also, you'll see what work is being done to bring SVGAlib's fonts up to speed with those found in X Windows and other operating systems.

First of all, what is a font? A font can be defined as a collection of typewriter-rewritten characters, all with a consistent design or style. For example, the words in this book are written in Times New Roman, a standard word processing font. Thousands of other fonts (or typefaces) are available, and many can be found on the Web, free of charge. Others are created by professional designers and cost several hundred dollars each. Regardless of your preference, you can almost always find a font to fit your needs. What's more, there's virtually no limit to the number of possible fonts—you're only limited by your imagination in creating new and unusual character sets.

Fonts are stored in data files, which are then accessed by executables at runtime. The application reads the data contained in the font file and uses that information to produce, or render, the visible characters on your screen. Figure 7.1 shows two rendered SVGAlib fonts.

### Two Styles Of Fonts: Bitmapped And Scalable

Fonts come in two varieties: bitmapped and scalable. One is easy to comprehend, and the other is a little more difficult. *Bitmapped* fonts are the easy ones, and they’re similar to bitmapped graphics. Drawn on a grid, or *matrix*, they always look the same, because a bitmapped font’s data file contains an exact rendering of each character. It’s similar in that respect to a graphic file or even a photograph. When the font is accessed, the “picture” of each character is loaded into memory and then displayed verbatim on the screen. It’s almost a case of cut and paste. Bitmapped fonts can’t be altered by the program (at least, not very easily), so they can’t be resized. If you want a larger or smaller version of the same font, you’ll have to redraw the entire character set completely; it’s not a simple matter of readjusting the *point size*. Naturally, that creates some work for the programmer. Another drawback is that bitmapped fonts often appear choppy or jagged, as shown in Figure 7.2. Nevertheless, their simplicity lies in the fact that however the font’s characters appear in the file, that will be the way in which they’re displayed.

The second variety of font is known as *scalable*. This is a more advanced way of storing a font’s information. Rather than having an exact picture of each character, the font’s “stylistic information” is stored in its data file. That information includes the angles of each character’s curves, and how they’re proportioned. If a bitmapped font can be compared to a bitmapped graphic, a scalable font can be compared to a vectorial graphic. (See Chapter 9 for an in-depth discussion on graphic file formats.) Because no actual picture exists, the rendering program must create each character, or *glyph*, on the fly. That creates some processing overhead, but the end result is well worth it. ### Point Size

Font height is measured in *points*, a unit of measure equal to 1/72nd of an inch. Point size in bitmapped fonts can’t be adjusted as it can with scalable fonts.
