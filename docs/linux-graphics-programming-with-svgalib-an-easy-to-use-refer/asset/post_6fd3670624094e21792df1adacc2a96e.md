
## Refresh Rate

  The number of times per second your monitor is reenergized. Your screen is constantly losing its charge and must therefore be refreshed. Measured in hertz, display systems typically range from 56Hz to well over 100Hz. A minimum of 70Hz is recommended to help prevent eye strain.

## Compilation

  Now you're actually ready to build SVGAlib. Type **make install**, and the binaries will compile and copy to the appropriate directories, as defined in **Makefile.cfg**.

  Assuming all went well, you can complete your installation with **make demoprogs**. This will compile several demonstration programs, including **vgtest**, which will be placed in the **/demos** and **/threeDKit** subdirectories.

> **Note**
>
> You *must* compile and install as root. If you don't, nothing bad will happen during compilation, but certain tools will fail to become **setuid** root and won't work properly as a result.

## Printing The Man Pages

  If you'd like to have a clean version of the *man* pages to print, simply run **make ascii** in the **/doc** subdirectory. This can be done at any time, because it isn't directly related to your compilation and installation process. The resultant three files will be named *svgalib.ascii*, *vgagl.ascii*, and *3d.ascii*.

## Setting Up libvga.config

  The final step in configuring SVGAlib for your system is to edit **/etc/vga/libvga.config**. It may look intimidating, but all you need to do for now is define your monitor's settings, your chipset (that is, VGA card), and what kind of mouse you have (if any). If you don't know your monitor's refresh rate, you can usually get this setting from the manufacturer's Web site. Failing that, you can try some of the sample listings.

  I won't include the entire file here, but I will show some excerpts in regard to the mouse, monitor, and chipset.

## Horizontal Sync

  The number of lines illuminated on a video screen in one second. For example, a resolution of 400 lines refreshed 60 times per second requires a scan rate of 24kHz plus overhead (time to bring the beam back to the beginning of the next line). This is the same as the horizontal sync frequency in your TV.

> **Note**
>
> If you don't declare your chipset in libvga.config, SVGAlib will do its best to autodetect it for you. Simply listing `vga` will force your card to use low resolution (read: safe) modes.

## SVGAlib Basics

  SVGAlib is a library of functions that makes graphics possible on Linux. It’s necessary because standard (ANSI) C can only give you text. You may find this surprising, given the number of graphical applications coded in C, but nonetheless it’s true. In order to display output other than text, C must link to an external set of OS- and machine-specific functions. These external functions handle the actual process of writing to the VGA card.

  You can think of SVGAlib as a device that bridges the gap between standard C and the machine language functions necessary to display graphics on the screen. What does the name mean? Of course, SVGA refers to *SuperVGA graphics adapters* (video cards) and their attendant displays, and *lib* means that it's a *binary library* that can be linked to programs written in C.

  Let's talk a bit more about how C links to and utilizes external, or *shared*, libraries.

## The Concept Of A Shared Library

  If you've ever looked inside your */lib* directory, you've undoubtedly seen files with names such as *libso.5* and *libm.so.4*. Have you ever wondered what these files were all about? Quite simply, they're your *shared libraries*, and most of your C programs use them.

  Shared libraries allow you to develop enormously functional programs that don't take up a lot of disk space and that do things (such as displaying graphics) that aren't supported by standard C. This arrangement is made possible by *ld*, the dynamic linker. When you compile a program, *ld* links any external functions referenced in your code to the shared libraries. Your code remains small because the library routines always stay separate. A good analogy to this would be a company that subcontractors some of its work to other, more specialized companies. Rather than having a huge office staff, our imaginary company saves money by outsourcing its invoicing, customer support, and janitorial work to other local businesses. In this regard, dynamic linking can be considered a form of outsourcing. Space is saved, because several programs can share the same code.

  Shared libraries can be distinguished by their names, which are written in the format *“library.so.version”*. For example, *libvga.so.1* is SVGAlib's shared library. Most of these libraries can be found in */lib*. Makes sense, doesn't it?

  Sometimes, though, you don't want to farm out your work. A *statically linked* program contains all its own code internally. This is useful for debugging, or if you need to write a program that will be used on a system that’s “library deprived.” Statically linked programs are large but independent.

  You can tell a static library because it ends with a “*a*.” For example, *libvga.a* is SVGAlib's static library. You can find this and most of the other static libraries in */usr/lib*.

  While we're at it, let's examine another important issue: A dynamically linked program depends on the existence of the shared libraries with which it was linked at compile time. If you're feeling bored sometime, try erasing some of your libraries and see what happens. (Hint: Don't do it! Vital programs such as *cp* and *mv* will stop working, and you'll be out of business.) To find out whether a specific program uses shared libraries, type `ldd name_of_program`. For example, if you're in the SVGAlib demo directory, typing `ldd fun` yields this:

```text
libvga.l.so.1 -> /lib/libvga1.so.1 (0x40009000)
libvga.so.1 -> /lib/libvga.so.1 (0x40018000)
```
