## An Easy Way To Copy Sprites

Instead of redrawing a sprite every time you want to place it somewhere different, wouldn’t you like to just be able to use **gl_putbox()**? The only problem is that if your background uses more than one color, **gl_putbox()** will leave a telltale border around your image. An **irregular putbox** function isn’t available (one that inserts a nonrectangular shape), but you can achieve the same effect with **gl_putboxmask(int x, int y, int w, int h, void \*dp)**.

### Sprite

An independent graphical object. A sprite is generally a character image, but it can be any other moving portion of the screen. Sprites can move without affecting other parts of the screen and are routinely used in games.

This works identically to gl_putbox(), except it only copies the foreground colors. The background (color 0) is left untouched.

You can draw your sprites on a color 0 background, perhaps on a vgaI virtual screen, and then use another palette color besides 0 for black. So long as you never use the background color on the screen (using your other black instead), gl_putboxmask() will make your sprite transfers fast and efficient. ## Scrolling

There are umpteen thousand tutorials involving scrolling—every book on computer graphics seems to have one—and most seem to involve assembly language. The one you’ll see here uses vgaI exclusively, and it’s the easiest (conceptually) that you’ll ever encounter.

### What Is Scrolling?

Scrolling is simply when the background slides left or right, up or down to allow you to explore “worlds” that are larger than one screen. As your “character” moves, the background will scroll along, keeping you in the middle of the screen. This technique is employed in almost every Nintendo game—think of Super Mario Bros. or any other game viewed from the side.

There are basically two ways to scroll. The first method involves keeping the entire playing area in a frame buffer and sliding that back and forth as needed. The second involves calculating the new screen areas as they’re needed, but that’s a little slower. There’s always a trade-off between memory consumption and speed. I’m going to show you the fast, memory-hungry method using vgaI’s internal frame buffer.

In the past, you've learned how to make a virtual screen the same size as the physical screen. If your screen were 320 pixels by 200 pixels (that is, if it used a matrix of that size), your frame buffer would be identical. The trick here, however, is that you can store the elements of a virtual screen into multiple locations with gl_getbox(), thereby making the frame buffer any size you'd like.

Now, let's create a frame buffer that accounts for five physical screens simultaneously. This will allow a character to move smoothly through 1,280 horizontal pixels. It'll be, in essence, a virtual screen mode of 1,280 by 200.

What I'm going to do is create five separate memory locations. To accomplish this, I'll draw a scene into vgagl's frame buffer and then proceed to copy that entire page to the first memory location with gl_getbox(). I'll then redraw the frame buffer (which is itself a memory location) with the contents of the second screen, and that, too, will be copied—this time to the second main memory buffer. Make sense? I'll repeat this for all five “virtual” screens.

As the game is being played, the character's position is always recorded. Whenever a new bit of background area is needed, it can be easily transferred back to vgagl's frame-buffer from the appropriate memory area, and then copied to the physical screen with gl_copyboxfromcontext().
