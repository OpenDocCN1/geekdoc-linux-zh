# Graphics On Startup

One thing that I find really appealing about the Macintosh (and Windows 9x, too, for that matter) is that you get graphics immediately upon startup. This looks so much more professional to me than what you get with Linux. Although I'll admit that the text information that Linux displays during boot up is often useful, it isn't going to do much for selling Linux to the masses—something many seem to have on their mind as of late.

I cannot accurately describe what an enormous pain in the rear it has been trying to make this work. I have neglected my family, my job—yes, even other *paying* projects—in my search for this, the Holy Grail of Linux graphics. And I'm duty-bound to tell you the disheartening truth: It can't be done within the confines of SVGA1ib.

However, it *can* be done—and I'll have to bite my tongue as I write this—if you use the fbcon video drivers now standard in the kernel, due to the efforts of the GGI project.

The problem is twofold:

- The kernel cannot use the standard libc.
- Your video card must go into a graphics mode *before* the kernel enters protected mode.

Add to that the fact that I'm not a kernel hacker. However, all is not lost. The GGI people have created a kernel framebuffer device (which Dr. Michael Weller suggested years ago, thank you very much), and the following subsections explain what you have to do to make it work.

## Step 1: Recompile The Kernel

When you run **make config**, enable the prompt for development and/or incomplete drivers. Then, select the following in the Console Drivers menu:

- VGA Text Console
- Video Selection Support
- Support For Frame Buffer Devices (Experimental)
- VESA VGA Graphic Console
- Advanced Low Level Drivers
- Select Mono, 2bpp, 4bpp, 8bpp, 16bpp, 24bpp, and 32bpp packed pixel drivers

## Step 2: Make Sure Your VGA Card Is VESA 2 Compliant

Oh, what a nightmare. Any respect I had developed for the GGI people was lost at this point. One of the great things about SVGALib is that it allows you to use generic video cards without any finagling. For example, I have generic S3 ViRGE cards in many of my machines. They work well, and the price is right. But, unfortunately, they only conform to version 1.2 of the VESA BIOS Extensions, and their firmware cannot be upgraded.

### Here’s The Word From S3 (Diamond)

If you require a VESA 2 driver and it’s not contained in your board manufacturer’s BIOS, there’s a Universal VESA BIOS Extension package (also called UniVBE) available from Stichtech Software called *Display Doctor 5.3a* (you may download a temporary shareware version from www.stichtechsoft.com). The Stichtech Display Doctor is recognized as an industry-leading VESA 2 driver package.

Also, Dietmar Meschede (a halloved S3 customer from Germany) distributes a freeware VESA driver package he wrote that provides VESA 2 support for most S3 chips. Meschede’s driver, S3VBE318.ZIP, is available through all of S3’s online services.

However, S3 does not guarantee that these or any VESA packages will function properly on all systems.

Generic S3 BIOS code contains VESA 1.20 support, and some new S3-based adapters may also have VESA 2 functionality. Because of this, S3 does not provide a “VESA driver” or, more precisely, a VESA BIOS extension TSR program.

It's claimed that a card with VBE 1.2 will use too much of the kernel's memory, whereas a 2.0 card is much more efficient. Therefore, the great GGI project has ignored 1.2 cards altogether. This, I think, is a crock. And I'm certainly not going to put any time into improving their product.

Therefore, with my tail tucked firmly between my legs, I headed down to the local computer superstore to buy a new adapter. And when I got home, I had to turn around and return it, because it, too, failed to live up to VESA's heightened 2 standard. Finally, I ended up with Creative's 3D Blaster Savage 4, which, thankfully, finally did the trick.

> **Note**
> There is a driver that can be used in conjunction with a VBE 1.2 S3 chipset that can be loaded at boot time—if you're using loadlin. It functions much in the same way as a TSR (Terminate and Stay Resident program) would do in DOS. However, I (along with many people) use Lilo under Linux, so this is useless for me.

## Step 3: Reconfigure /etc/lilo.conf

You'll now need to modify your */etc/lilo.conf* file (assuming you're using LILO) to include the VGA=ASK parameter. (This is required for you to be able to select the modes you wish to use.) Then, rerun LILO.

When you reboot, you'll be given the option to press Return/Enter to see a list of available text modes. Note that none of these will give you graphics. Instead, you'll have to enter a mode number based on Table 6.1.

Using this table, you should be able to select a mode that meets your needs. For example, if you want a 640x480x256 mode, you enter 0301 at the prompt (omitting the x). If all goes well, you'll see a nice little penguin logo. If not, you'll be given an error and will be prompted for another mode, meaning that your card is most likely non-VBE 1.2 compliant. What fun!
