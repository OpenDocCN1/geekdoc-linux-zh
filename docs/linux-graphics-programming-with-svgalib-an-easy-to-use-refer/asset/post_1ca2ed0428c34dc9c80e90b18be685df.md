
From this output, you can infer that **fun** (one of the SVGAlib demo programs) requires four external libraries. Sometimes, though, you’ll see the following:

```text
statically linked (ELF)
```

This, of course, means that the program is statically linked and doesn’t depend on any external files.

## The Vgagl Library

There’s one more shared and/or static library that you’ll get with any SVGAlib installation—vgagl. This is a higher-level library that allows you to perform more advanced functions, such as drawing shapes with a single command. It also allows the use of a *framebuffer*, which is like an invisible screen. The idea is this: You draw to the invisible screen and then transfer your drawing to the visible (real) screen in one fell swoop, thus eliminating the annoyance of screen flicker. It has other uses as well, which I’ll discuss when we get into coding.

Hopefully, these sections have made it easy for you to understand how SVGAlib connects to your programs. When you build a program with SVGAlib, you link to it, just like you link to libc.so.5 or glib.

## Different Libraries That Produce Graphics

SVGAlib isn’t the only graphical library, but, in my mind, it’s the best. Other libraries, such as consoles, allow you to move your cursor around the screen and change your colors, but I don’t consider that to be true graphical output. Aaalib lets you turn graphic files into ASCII art, but again, it’s still displayed as text. The only serious contender to SVGAlib is X Windows.

### Differences Between SVGAlib And The X Windowing System

Readers of this book may already be familiar with XFree86, otherwise known as the *X Windowing System*. But how are X and SVGAlib different, you might ask? They both run on Linux, and they’re both used to display graphics.

The key difference is that XFree86 is a *server application* (or a *daemon*), such as syslogd and named (and all the other programs that end with d and pop up when you boot up your system). Unlike SVGAlib, the X server must be running in the background to process requests. This means that you can’t call XFree86 from a shell script; it has to be started first. Generally, if you plan on using XFree86 applications, you’ll need to have your X server running at all times.

X graphics programs (or clients) work by sending their data to the XFree86 server, which then passes the data on to the video card for display. No X client program accesses the video card directly like we do with SVGAlib.

## Advantages of SVGAlib

Here's a list of some of the advantages SVGAlib offers:

-   ***Speed***—SVGAlib sends data straight to your VGA card. SVGAlib is like a giant retail superstore that bypasses the middleman to bring you the lowest prices (or, in this case, the best speed). This is especially important in realtime games such as Quake, Doom, and flight simulators.
-   ***Ease of use***—As far as programming goes, the functionality of SVGAlib can't be beat. For the end user, there's no startup time; programs execute instantly. SVGAlib also uses your entire screen and makes it very easy to dictate the display resolution. Many of us prefer this to partial windows and the gimmick of a panning display.
-   ***Comprehensiveness***—You're spared the task of downloading a new server every time you change your hardware. This may not be a major issue, but it's still an annoyance that X saddles you with.

Nevertheless, some people will never be happy with SVGAlib. Here are some reasons why:

-   ***Portability***—SVGAlib functions will only work with SVGAlib and are therefore useless outside of the *Linux environment*. Some people consider this a weakness. They point out that an application written for X Windows doesn't have to be rewritten for another flavor of Unix. This is true, but code written for X on Unix isn't compatible with Microsoft Windows or Macintosh, either, so some amount of rewriting is inevitable. Besides, MS Windows applications work only on one platform, and no one complains about that. This brings to mind Java, the fantastic, solve-all-your-problems, hardware-independent language of the mid 90's. Of course, the reality is a little different. All that these "universal" languages manage to do is make your life more difficult. You're going to have to face the fact that some amount of rewriting is necessary if you migrate to another platform. Besides, given the inavailability of Linux, why would you want to?
-   ***Perceived security hole with setuid requirement***—In order to access a hardware device on Linux, you must be logged in as root, or else you must be running a *setuid root process*. Because SVGAlib achieves speed by accessing your video card directly, all SVGAlib programs must be *setuid* root if they're to be run by nonroot users. This alarms some people, but the simple fact is that root privileges are relinquished immediately after initialization, meaning there's no reason to be concerned. As a matter of fact, my system has been hacked a few times, but it was never on account of SVGAlib.
-   ***Inability to display multiple windows simultaneously***—People get really hung up on this one, and I don't know why. This isn't so much a design flaw as it is a matter of the necessary application having yet to be written. And why hasn't it been done? Perhaps because no one cares. I don't. If you need to do multiple activities simultaneously, you can use your virtual terminals. If multiple windows are important to you, there's an outfit in Redmond, Washington that has a product that you might find appealing.
-   ***Fewer video cards supported***—I feel this is the only legitimate argument against SVGAlib, but it's less and less of an issue all the time. Hopefully the publication of this book will result in more drivers being coded. However, SVGAlib still supports a respectable number of chipsets, and more drivers are being written all the time. Let's not forget that X has had a major head start in this department. The recent addition of a VESA driver was a big improvement for SVGAlib. Also, if the *UDI (Uniform Driver Interface)* ever becomes a reality, this problem will evaporate overnight—or at least, that's what the marketing people will have us believe.
-   ***Availability of applications***—Unfortunately, because X is available for more systems and has been around for a much longer time than SVGAlib, there are many more applications available to be run under it. That doesn't mean that SVGAlib itself is inferior; it just means that there are fewer programs available. We hope this will change in the near future, as more and more people begin coding for SVGAlib.
-   ***Networked graphics***—Because X uses a graphics server, the X client can be on a separate machine. This is something you can't do with SVGAlib (yet). However, X can't help you if you're using an MS Windows client, and this configuration is becoming more and more popular.

## The Problem With Networked Graphics

The process of displaying graphics on a remote computer is not as easy as it might first appear. The problem lies in the fact that not every computer uses the same display adapter. Computer A can easily write to its own card, but Computer B likely has a different card and will have all sorts of trouble if Computer A attempts to write to it.

The solution is to send the graphics *data* from A to B and then to allow B to do it's own rendering. This is how Web browsers work.

## Virtual Network Computing

There is a new way to defeat the networked graphics problem with SVGAlib, however; you can use *VNC. It's something like a multiplatform version of Norton's PC Anywhere.
