### Screen Fades

One neat effect is the *screen fade*. Instead of suddenly blanking out the screen, you can apply an artistic touch to your applications and gradually fade them away. This is particularly effective when used to transition smoothly to different levels in a game. Naturally, there are a number of different methods to accomplish this, so I’ll cover a few. You decide which you like the best.

#### The Snowstorm

The easiest-to-conceive-of method for clearing the screen in a nonimmediate manner is to plot a number of random points. The screen will eventually be covered by the color of your choice, which effectively erases the old image. This can be likened to a snowstorm, or a barrage of bullet holes if your "points" are large enough. Listing 6.1 shows the bare bones of this technique, which uses the rand() function found in <unistd.h>. Let's assume that your color is predefined.

**Listing 6.1 Clearing the screen (one pixel at a time).**

```c
int i,
    x = vga_getxdim(),
    y = vga_getydim();

vga_setcolor(color);

for (i = 0; i < (x * y); i++)
{
    vga_drawpixel(rand()%x, rand()%y);
}
```

If this routine were performed in a 320x200 screen mode, it would loop 64,000 times. In reality, however, that wouldn't be enough, because you tend to get the same numbers over and over with rand(). Therefore, you should consider looping four or five times for every point in your matrix. Alternately, you can just "blackwash" (like whitewash) the entire screen with vga_clear() after you've exceeded a certain number of repetitions. To create a solid color other than black, you can simply use gl_clearscreen(int c).

To make the process faster, consider drawing multiple pixels during each loop. This would fill the screen in a lot less time, as well as give you an opportunity to draw complex shapes instead of simple points. Finally, you might give some serious thought to using vga! functions instead of vga_drawpixel().

#### A Few Words About Rand()

As shown in Listing 6.1, rand() is used to return a pseudo random number. (The number isn't "genuinely" random because it's produced by an algorithm and not by mystical quirks of fate.) The algorithm used to produce rand()'s output depends on an initial "seed" number (that is, one from which to base the rest). If you don't provide the seed, you'll end up with a predictable and repetitive sequence.

The srand() function is, as you've probably guessed, used to seed the random number generator. It requires an integer input, so many people use the time of day. Such usage might look like this:

```c
srand((unsigned) time((time_t *)NULL));
```

Using the time() function in **`<time.h>`** does provide an easy way to obtain a fresh seed number for virtually every run. I find, however, that you'll get a more evenly distributed set of "random" numbers if you provide **`srand()`** with your current process ID. This is easily accomplished using the **`getpid()`** function from **`<unistd.h>`**. Best of all, that's something you can't do in Windows.

You'll only need to seed the generator once per run. Therefore, you should do it before entering into any loop that involves **`rand()`**. Here's all you have to do:

```c
srand(getpid());
```

Now, you should be aware that the number returned by **`rand()`** is enormous. To get a useful range of integers, divide **`rand()`**'s output by **`RAND_MAX`** (defined as 2,147,483,647 on my system), like so:

```c
num = (float) rand() / RAND_MAX;
```

Then all you have to do is multiply the resultant number by your desired range. For example, if you want a number from 1 to 8, do this:

```c
num = 8 * (float) rand() / RAND_MAX;
```

Finally, remember that the range of numbers produced by **`rand()`** starts with 0. If you actually want a number between 1 and 8 (and not 0 to 7), simply add 1 to your result, as follows:

```c
num = (8 * (float) rand() / RAND_MAX) + 1;
```

A much cleaner way would be to perform the operation like I did in Listing 6.1, which I'll repeat here:

```c
num = rand()%8 + 1;
```

#### Cinematic Screen Fade

Although the first example did clear the screen, it was more of a "blakout" than a fade. To achieve a "true" fade, all you need to do is slowly darken the colors in your palette. When their RGB values have all been reduced to 0, your fade has been accomplished. An example of this procedure can be found in Listing 6.2.

**Listing 6.2 Cinematic screen fade.**

```c
int i,
    j,
    r,
    g,
    b,
    num = vga_getcolors();

for (i = 0; i < 64; i++)
{
    for (j = 0; j < num; j++)
    {
        vga_getpalette(j, &r, &g, &b);
        r -= 1;
        g -= 1;
        b -= 1;
        if (r < 0)
        {
            r = 0;
        }
        if (g < 0)
        {
            g = 0;
        }
        if (b < 0)
        {
            b = 0;
        }
        vga_setpalette(i, r, g, b);
    }
}
```

You may have noticed that i is a value from 0 to 63, and not 0 to 255, as you might have expected with RGB colors. This is because `vga_getpalette()` and `vga_setpalette()` normally work on the 64-shade scale. To jump to 255 shades, you’ll need to first declare the following:

```c
vga_ext_set(VGA_EXT_SET, VGA_CLUT8);
```

Of course, some VGA cards (especially older ones) can’t handle `vga_ext_set()` or `vga_accel()`, so I prefer to avoid those functions.

For variety, note that vgaGL’s `gl_getpalettecolor(int c, int *r, int *g, int *b)` and `gl_setpalettecolor(int c, int *r, int *g, int *b)` accomplish exactly the same thing as `vga_getpalette()` and `vga_setpalette()`. What’s more, they also use the 0-to-63 color scale by default—something that you might find to be counterintuitive.

Now then, there’s only one problem with the cinematic screen fade: ironically, it’s too darned fast. Unless you have an ancient processor, the effect rips right past your eyes, leaving almost everything to the imagination. How, then, can it be slowed down? Because `sleep()` only works in one-second increments, it’s virtually useless here, unless you want the “molasses" fade. Given that fact, you might be tempted to hard-code a delay, using something along the lines of this:

```c
for (k = 0; k < 100000; k++) { }
```

But wait! That might look good on your machine, but how might it look on someone else’s computer, which may well have a faster (or slower) processor? As processors continue to improve, your code will almost assuredly become obsolete. Doing it that way would be shooting yourself in the foot. Instead, it's time to delve into the black art of subsecond delays.

#### Subsecond Delays

Actually, it’s not that big of a deal. I prefer to use usleep(unsigned long usec), which lets me pause in microsecond intervals (millionths of a second), but there’s also nanosleep(const struct timespec *req, struct timespec *rem), which allows pauses in the billionths of a second. The point I wanted to make previously was merely that you shouldn’t rely on empty loops for delays.

USleep() is defined in <unistd.h>, whereas nanosleep() is in <time.h>. You might prefer to investigate nanosleep(), because according to the man page, it “has the advantage of not affecting any signals, it is standardized by POSIX, it provides higher timing resolution, and it allows [you] to continue a sleep that has been interrupted by a signal more easily.” Well said. As for me, I prefer the simplicity of usleep().

#### Screen Fades With Vgafl

Listing 6.3 demonstrates the same cinematic fade routine shown in Listing 6.2, but modified to use vgafl and usleep(). Because vga_getcolors() is no longer useful, you can use the COLORS constant defined in <vgafl.h> to get the same value. Here’s the syntax:

```c
#define COLORS (currentcontext.colors)
```

I also shortened the range of shades some; you may have noticed that the screen became sufficiently dark before the RGB values hit true black (0, 0, 0), so it’s pointless to spiral down through every last value. Again, the 0-to-63 shade scale is the default, unless you employ vga_ext_set().

**Listing 6.3 A more realistic fade.**

```c
int i,
  j,
  r,
  g,
  b;

for (i = 64; i > 5; i--)
```
