
To ensure that polygon corners are handled right, both start and end points must be drawn (in `ROP_XOR` mode). Accordingly, it's best to use `ACCEL_DRAWLINE` instead of `ACCEL_POLYLINE`. Finally, skip drawing all horizontal lines (which would confuse `ACCEL_SCREENCOPYMONO`).

- Set foreground and background colors, raster operation, and bitmap transparency to the values you want for your polygon.
- Use `ACCEL_SCREENCOPYMONO` to copy the offscreen pattern to the screen.

The raster operations and the transparency that are signaled to be supported for `ACCEL_POLYFILLMODE` by `vga_ext_set()` are actually meant to apply to the last `ACCEL_SCREENCOPYMONO` call.

Because this polygon drawing uses more screen read/write operations, it's probably slower than using `ACCEL_DRAWHLINELIST` or `ACCEL_POLYHLINE` for drawing a polygon scanline by scanline. However, it's easier to use and it will work mostly without intervention of the CPU, which can then do other calculations.

> **Note**
>
> *It's unspecified if the left or right endpoints of the scanlines are drawn, and most cards (such as Mach32) will omit them on one end, at least. Because of that, you should always draw the boundary line in the fill color (or another color) after filling the polygon.*

### `vga_accel(ACCEL_SETMODE, mode)`
Sets the blit strategy. There are two choices for `mode`, namely `BLITS_SYNC` and `BLITS_IN_BACKGROUND`. The first ensures that a `vga_accel()` call only returns when the accelerator has finished its operation. The second allows for an immediate return, thus allowing parallel operation of the CPU and the accelerator. Consecutive accelerator operations will wait for each other to complete (and block if necessary). However, direct screen memory access (done implicitly by calls to some SVGA/ib functions) may find any intermediate state in VGA memory or even corrupt the running accelerator operation.

### `vga_accel(ACCEL_SYNC)`
Waits for the accelerator to finish when in `vga_accel(BLITS_IN_BACKGROUND)` mode.

### `vga_accel(ACCEL_SETOFFSET, int address)`
Sets a screen offset as `vga_setdisplaystart()` does. The same restrictions for this function, as reported by `vga_getmodeinfo()`, apply to `address`. Whenever the video screen offset is modified, the accelerator's offset will follow. However, you can modify it later with this function.

The following mode values are defined for `vga_accel(ACCEL_SETTRANSPARENCY, int mode, ...)`:

- `vga_accel(ACCEL_SETTRANSPARENCY, ENABLE_TRANSPARENCY_COLOR, int color)`—Whenever one of the `vga_accel()` operations would draw a pixel in color `color`, no operation is performed and the destination pixel is left unchanged. In fact, that color is defined to be transparent.
- `vga_accel(ACCEL_SETTRANSPARENCY, DISABLE_TRANSPARENCY_COLOR)`—Disables the previous functionality.
- `vga_accel(ACCEL_SETTRANSPARENCY, ENABLE_BITMAP_TRANSPARENCY)`—In the bitmap-expanding operations `ACCEL_PUTBITMAP` and `ACCEL_SCREENCOPYBITMAP`, whenever a nonzero bit is encountered, no drawing operation is performed. The 0 bits do not draw in the background color. Instead, they're defined to be transparent.
- `vga_accel(ACCEL_SETTRANSPARENCY, DISABLE_BITMAP_TRANSPARENCY)`—Disables the previous functionality.

The following mode values are defined for `vga_accel(ACCEL_SETRASTEROP, int mode)`:

- `vga_accel(ACCEL_SETRASTEROP, ROP_COPY)`—Straight copy. Pixels drawn by `vga_accel()` replace the destination.
- `vga_accel(ACCEL_SETRASTEROP, ROP_OR)`—Logical OR. Pixels drawn by `vga_accel()` are logical (bitwise) ORed to the destination.
- `vga_accel(ACCEL_SETRASTEROP, ROP_AND)`—Logical AND. Pixels drawn by `vga_accel()` are logical (bitwise) ANDed to the destination.
- `vga_accel(ACCEL_SETRASTEROP, ROP_XOR)`—Logical exclusive OR. Pixels drawn by `vga_accel()` are logical (bitwise) exclusive ORed to the destination (bits set in the drawn pixels flip those bits in the destination).
- `vga_accel(ACCEL_SETRASTEROP, ROP_INV)`—Inversion. Pixels drawn by `vga_accel()` are inverted. Whatever color is drawn is actually ignored. Any pixel that would be overwritten is simply inverted (bitwise) instead.

Note that a 0 returned by `vga_accel(ACCEL_SETTRANSPARENCY, int mode, ...)` and `vga_accel(ACCEL_SETRASTEROP, int mode)` simply means that the set function is available (and therefore probably some of the listed features) but only partial functionality may be available. The `VGA_AVAIL_ROPMODES` and `VGA_AVAIL_TRANSMODES` subfunctions of `vga_ext_set()` allow you to check for valid parameters. The `VGA_AVAIL_ROP` and `VGA_AVAIL_TRANSPARENCY` subfunctions return which of the `vga_accel` operations are actually affected by these set functions.

Instead of calling `vga_accel()` for each operation to find out if it's supported, you can make the following call:

```c
#include <vga.h>
int vga_ext_set(VGA_EXT_AVAILABLE, VGA_AVAIL_ACCEL)
```

When the logical bitwise and the return value with one of the following predefined (one bit set only) integer constants is nonzero, the corresponding operation is available: `ACCELFLAG_FILLBOX`, `ACCELFLAG_SCREENCOPY`, `ACCELFLAG_PUTIMAGE`, `ACCELFLAG_DRAWLINE`, `ACCELFLAG_SETFGCOLOR`, `ACCELFLAG_SETBGCOLOR`, `ACCELFLAG_SETTRANSPARENCY`, `ACCELFLAG_SETRASTEROP`, `ACCELFLAG_PUTBITMAP`, `ACCELFLAG_SCREENCOPYBITMAP`, `ACCELFLAG_DRAWHLINELIST`, `ACCELFLAG_SETMODE`, and `ACCELFLAG_SYNC`.

In addition, calling

```c
#include <vga.h>
int vga_ext_set(VGA_EXT_AVAILABLE, VGA_AVAIL_TRANSPARENCY);
```

or

```c
int vga_ext_set(VGA_EXT_AVAILABLE, VGA_AVAIL_ROP);
```

does not list the supported values for raster operations and transparency but instead returns the `ACCELFLAG_` values for the accelerator operations that respond to the raster operation’s transparency settings.

The availability of the operations will usually depend on the current video mode selected. You should try not to use them, or check for availability prior to selecting the mode you want to use with `vga_setmode()`. See the `vga_accel()` man page for more details.

## Accelerator Interface (Old Style)

These functions pertain to the accelerator interface:

> **Note**
>
> These are old-style functions to access the accelerator of an SVGA card. Before calling them, you should check for the availability of these functions in the mode that you're using with `vga_getmodeinfo()`.

For new applications, you might be better off using `vga_accel()` instead. The old `vga_bitblt()`, `vga_bitwait()`, `vga_fillblt()`, `vga_hlinelblt()`, and `vga_imagemblt()` interface was originally designed for the Cirrus chipsets. Then Mach32 added support, too, but it has problems resembling the unintuitive Cirrus interface. Then these new ideas were rejected, and `vga_accel()` was designed. Now Cirrus and the Chips & Technologies chipsets give limited `vga_accel()` support but no longer have this old-style support. Mach32 is left to use the unintuitive Cirrus interface. At some future point, the functions might be added for Mach32, too (which should be rather simple), so new applications should use the newer and probably more efficient interface.

It would be fatal if the accelerator were to be used while the console is switched away. Therefore, you should use `vga_lockcv()` and `vga_unlockcv()` to avoid this, although good implementations of the accelerator functions (such as Mach32) will already ensure that the `testaccel()` demo utilizes the old-style accelerator functions.

### `void vga_bitblt(int srcaddr, int destaddr, int w, int h, int pitch)`

bitblt (copy rectangular area in video memory) addresses are offsets into video memory (up to 2MB). The pitch is the logical width of the screen. Height `h` is in pixels, and width `w` is in bytes.

### `void vga_fillblt(int destaddr, int w, int h, int pitch, int color)`

Fills a rectangular area in video memory with the single color `color`. The argument `destaddr` is an offset into video memory (up to 2MB). The pitch is the logical width of the screen. Height `h` is in pixels, and width `w` is in bytes.

### `void vga_hlinelistblt(int ymin, int n, int *xmin, int *xmax, int pitch, int c)`

Arguments `*xmin` and `*xmax` are pointers to arrays of `n` integers. There are `n` horizontal lines drawn, for `i` in 0 to (`n` - 1), a horizontal line will be drawn from pixel (`xmin[i]`, `ymin` + `i`) to (`xmax[i]`, `ymin` + `i`) using color `c`. Pixel (0,0) is considered to be at the absolute beginning of the SVGA memory (as if `vga_setdisplaystart(0)` were called).

### `void vga_imageblt(void *srcaddr, int destaddr, int w, int h, int pitch)`

Writes a rectangular pixmap from system memory to video memory. The argument `destaddr` is an offset into video memory (up to 2MB). The pitch is the logical width of the screen. Height `h` is in pixels, and width `w` is in bytes.

This fills the given box with the data in memory area `*srcaddr`. The memory buffer must contain the pixels in the same representation as used in the VGA memory, starting at the top-left corner, from left to right, and then, line by line, from up to down, without any gaps and interline spaces.

### `void vga_bltwait(void)`

This waits for any accelerator operation to finish. Although already implemented, this isn't very useful; old style functions don't allow for parallel operation of the accelerator. A limited use might be to wait for a running operation to complete in a `signal()` handler.
