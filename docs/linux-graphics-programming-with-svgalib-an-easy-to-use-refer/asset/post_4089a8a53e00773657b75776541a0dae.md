### Customizing *sk_savers*() And *sk_setregs*()

These functions should save and restore the original state of the SVGA card (generally speaking, this will be text mode) so that the card can be restored to a previous mode no matter what a program does (that is, no matter how badly it bombs). Your objective is to restore text mode properly.

Any registers changed by the driver should be saved, as well as registers that might be changed by other programs (X, SVGATextMode, and so on). Listing 20.3 details *banshee_saveregs*().

#### Listing 20.3 The complete *banshee_saveregs*().

```c
typedef struct {
    unsigned int pllCtrl0, pllCtrl1, dacMode, dacAddr,
                vidProcCfg, vidScreenSize, vgaInit0,
                vgaInit1, vidDesktopStartAddr,
                vidDesktopOverlayStride;
} *HWRecPtr;

static int banshee_saveregs(unsigned char regs[])
{
    HWRecPtr save;

    banshee_unlock();

    save=(HWRecPtr)(regs+62);

    regs[BANSHEEREG_SAVE(0)]=svgalib_inCR(0x1a);
    regs[BANSHEEREG_SAVE(1)]=__svgalib_inCR(0x1b);
    save->pllCtrl0=inl(banshee_io_base+0x40);
    save->pllCtrl1=inl(banshee_io_base+0x44);
    save->dacMode=inl(banshee_io_base+0x4c);
    save->dacAddr=inl(banshee_io_base+0x50);
    save->vidProcCfg=inl(banshee_io_base+0x5c);
    save->vidScreenSize=inl(banshee_io_base+0x98);
    save->vgaInit0=inl(banshee_io_base+0x28);
    save->vgaInit1=inl(banshee_io_base+0x2c);
    save->vidDesktopStartAddr=inl(banshee_io_base+0xe4);
    save->vidDesktopOverlayStride=inl(banshee_io_base+0xe8);

    return BANSHEE_TOTAL_REGS - VGA_TOTAL_REGS;
}
```

If you decide to use source from an X driver, you can usually find what you're looking for in the XXXSave() and XXXRestore() functions. All you have to do then is convert the functions from XFree86 notation to SVGA/Alib notation. Remember while you're doing this that the X functions need to save the VGA state, which is usually accomplished by calling the vga() function. In SVGA/Alib, however, the chipset_saveregs()/setregs() functions don't need to do that. Rather, they only save extended VGA info.

For the MilleniumII driver, the interesting X functions are MGA3026Save() and MGA3026Restore(). Listings 20.4 and 20.5 show the original MGA3026Restore() and then the translated milleniumII_setregs(), respectively.

### Customizing sk_initializemode()

This is the trickiest function in the entire process. If you're using the XFree86 source, try to translate the appropriate function from X to SVGAlib. As an example, in the MillenniumII's case, you'd use *MGA1064Init(mode)*. For other real-life examples of how translations like this are accomplished, we recommend that you study the *nv3.c* driver, which came from *nv/ nv3driver.c* in *X*, or else *apm.c*, which in turn was derived from *X*'s *apm/apm_driver.c*. If you're creating a completely new driver from the manufacturer's specifications, the information you need is usually explained in the spec book.

### Customizing sk_unlock()

This, in turn, is the simplest function. The skeleton driver includes the necessary VGA unlocking part. If you have the manufacturer's specifications, they usually explain how to unlock the extended features. On the other hand, if you're using the *X* source, it's usually found in the *EnterLeave() function*.

### Customizing sk_test()

This function checks to see whether the appropriate chipset is actually present in your machine.

If all you're intending to support is one chipset from a single manufacturer (and it's mounted on a *PCI* or *AGP* card), you can use the test function provided with the *skeleton.c* driver. (To take advantage of this, make sure you've properly defined the *VENDOR_ID* and *CARD_ID* constants.) Otherwise, the specifications provided by the chipset manufacturer *should explain how to recognize whether you have the right chipset*. If they don't, try customizing the *XXXXProbe()* function from the *XFree86* source.

### Customizing sk_setdisplay() And sk_setlog2width()

Standard *VGA* chipsets include these settings, but they have a limited range (*start < 65,536*, and *width < 2,048 bytes*). On the other hand, an *SVGA* chipset either defines extra bits for the increased range or will have completely new registers. In the case of the former, the *skeleton.c* driver contains material pertaining to setting the standard *VGA* registers. The extra bits are either defined in the manufacturer's specifications or in the *XXXXAdjust()* function found in *XFree86* (see *mx.c* for example of this).

In the latter case, erase the part of the function that involves setting the *VGA* registers (for an example of this, see *rgex.c*). Note that none of the *SVGAlib* demo programs test these functions, so if you want to check and see if they work, you'll have to use an outside program such as *seejpeg*. (When running *seejpeg*, try to view an image larger than the screen.)

### Customizing sk_init()

This one shouldn't need much in the way of changes. Possible exceptions might include checking the memory size (which is found in the manufacturer's specifications or in *XXXXProbe()*) or perhaps setting *MMIO* (if other functions use it).

## Step Three

When your customizations are finally complete, you'll need to go back and change all the sk\_ function prefixes to chipset\_ (where chipset is the name of the chipset in question). This change includes all the sk\_ functions—even those you haven't touched.

Once you have that done, you'll be ready to integrate your driver into SVGA\_lib. To do so, you'll need to edit the following files:

- Makefile.cfg
- src/Makefile
- src/driver.h
- src/vga.c
- src/vga.h

You can easily see what changes are needed in those files by following the example of SVGA\_lib's existing drivers.

## Step Four

This is where the fun begins, and I know it's the step you've all been eagerly anticipating—debugging. Actually, this is the part where you'll stay up until 4:00 in the morning, cursing under your breath.

Generally speaking, a new driver will never work as intended when you first plug it in. You'll certainly want to iron out the kinks before you go “live” and offer your driver for global distribution (at least, I hope so). With that in mind, Matan Ziv-Av has passed along a few pointers, which I've summarized in the following paragraphs.

The process of setting screen modes can be broken down into two distinct elements: setting the timings and setting the memory organization. Knowing this, you can usually pinpoint a driver problem by watching the screen. If the wrong screen is displayed or if some or even all of the pixels are miscolored, you'll know you have a problem with your memory organization. However, if the display looks “stormy,” you've got a timing problem.

If the problem involves memory organization, you might see whether the card will work in linear mode. To test this, try running the testlinear and linear2 demo programs, both of which can be found in SVGA\_lib's demos subdirectory.

On the other hand, if the problem involves timing, having a digital monitor that displays both horizontal and vertical timings can be of great value. If the horizontal frequency is right but the vertical is wrong, the problem is with the vertical timing. However, if both the horizontal and the vertical frequencies are off, the problem lies with either the clock frequency or the horizontal frequency.
