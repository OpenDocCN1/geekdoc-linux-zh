**User Feedback** If you're not paying attention to your users, you aren't doing your job as a Linux administrator. In many cases the sole purpose of the Linux operating system is to support users by providing network services, database services, disk space, and other services. Users can provide invaluable feedback for troubleshooting your system.

As an administrator, you don't have the time to run and evaluate every program that a Linux system can provide; however, Linux users do use the services of the Linux system and can provide feedback about problems and performance issues.

Some user problems are solved through user education. If users are new to Linux they should be educated to differences from other operating systems. For example, unlike many other operating systems, commands in the Linux operating system can be case sensitive.

There is one sure thing when it comes to users and your operating system: If things are not running well, you can depend on users to let you know about it. A user expects to have a responsive operating system and will let you know when it is sluggish. After a slow system is identified, the user should be queried about how they were using the system. If they typically run a CPU- or memory-intensive job, consider upgrading the computer. If the user experiences delays with a disk-intensive program, the file system needs to be evaluated. Network delays can cause a user to perceive the Linux system as slow. Many different things can cause a slow system. User feedback can guide you to the right resource to check.

**Information from Configuration Files** Most services on a Linux operating system use configuration files to provide startup information. Configuration files are changed occasionally after initial setup, but usually these files are static. Part of your documentation should be listings of configuration files. A copy of a configuration file can be invaluable to set services back to their original condition if a system has to be reinstalled or if an intrusion has been detected or is suspected.

Configuration files can be compared to earlier versions to help track down problems with the affected systems. For example, if a user complains that their login looks different, a copy of their _.bash_profile_ file can be used to restore settings.

**Information about Processes** What processes should be running on your computer? So many processes run on systems that it is very difficult to answer that question. The *ps* and *top* programs can provide valuable information about running processes.

A copy of the *ps* command result should be saved as part of system documentation. If there are complaints about system performance, this listing can help evaluate if processes are running that should not be. A list of commonly running processes will help track down programs that were executed by system intruders as well.

The results of the *top* command at various loads and times can provide valuable information about poorly running systems. A listing comparison to current values will help determine where the problems exist.

## SOFTWARE ERRORS

Software errors are the most difficult errors to troubleshoot. A software error can appear to be a hardware error, can hang up a system, or can do really odd things that make diagnosis very difficult. Software errors can be caused by file system problems, configuration problems, or development problems.

On some operating systems other than Linux, the solution to software problems is to restart the computer system. Sometimes you have to restart a Linux operating system as well, but usually any software issues can be solved by stopping and restarting the affected process.

Typically, well-known and tested Linux applications run for long periods of time with no problems. Some Linux systems running today have not been rebooted in months, and can possibly run several more months without having to restart.

### File System Problems

File system problems can cause software to fail. For example, if a file system loses information about a configuration file, the software may not start or it may start with default options. File system problems can cause data files or application files to be damaged, or directories to be corrupted.

**RAID** The best solution to file system problems is to have redundant disk drives. Usually this is done with some kind of Redundant Array of Inexpensive Disks (**RAID**) implementation. RAID can be software- or hardware-based. Hardware-based RAID is accomplished at the hardware level and does not take any processing power away from the Linux operating system. Software-based RAID relies on the computer’s processing power to accomplish its tasks.

There are six levels of RAID implementation. The most commonly used levels are RAID 0, 1, and 5.

**RAID 0** RAID 0 uses disk striping. One of the real bottlenecks of computer systems is the time it takes to read or write data from or to a hard drive. Disk striping is a technique for spreading data over multiple disk drives. Data is broken up and written to multiple disks concurrently, speeding up the read/write process. Disk striping stores data in one place only and does not offer any protection from disk failure. RAID 0 offers the highest possible performance.

**RAID 1** RAID 1 uses disk mirroring. Disk mirroring is a technique that writes the same data to multiple disks. If a disk malfunctions, the system can retrieve the data from the redundant disk. Disk mirroring is used when the data stored is critical and must be accessible at all times. Disk mirroring is slow on a single device, but on multiple hard disks is barely noticeable. RAID 1 offers good read performance, which will improve with the number of mirrors. Often it is possible to set read policies to optimize read performance within specific environments.

**RAID 2** RAID 2 spreads both data and parity information across multiple physical disks. RAID 2’s data-striping technique doesn’t use disk space efficiently and provides little disk space savings compared with full mirroring. RAID 2 implementations are uncommon.

**RAID 3** Similar to RAID 2, RAID 3 implements data striping but maintains all parity information on one disk for better performance. RAID 3’s disk usage, however, is still inefficient, making RAID 3 implementations rare.

**RAID 4** RAID 4 uses the same data-striping methodology as RAID 2 and RAID 3, but provides better performance by using larger disk blocks. RAID 4 also provides the same single-disk parity storage as RAID 3. RAID 4 is inefficient for transaction-based processing.

**RAID 5** RAID 5 allows you to use multiple hard disks, providing some redundancy (by writing data and parity information) and disk striping. RAID 5 requires three or more disk drives. If one of the disks fails, all data are still intact. If a spare disk is available, the data will be reconstructed with little or no down time. RAID 5 offers pretty good read performance, but typically poor write performance because of the parity calculation required. This problem is somewhat mitigated with modern hardware RAID controllers featuring large amounts of read cache.

RAID disk drives are often hot-swappable. This means that a disk drive can be replaced without having to shut down the computer system.

Some implementations use **RAID 0+1**, RAID level 0 combined with RAID level 1. This provides redundancy and striping by writing all data to four or more drives. RAID 0+1 provides higher performance than RAID 5.

**Disk Backup** One inexpensive solution to file system failure is to make sure you always have a backup. RAID provides high availability, but at a higher cost. Disk backup provides data availability, but at a much slower rate if something goes wrong. (Chapter 6 discussed disk backups.) Tape backups are more associated with providing disaster recovery capabilities.

The typical backup hardware is a tape drive; however, smaller installations also use removable hard drives, optical disks, and high-capacity floppy disk devices.

**Tape drives** are the slowest backup devices; but tape media is the least expensive per megabyte. Tape drives offer huge amounts of readily available storage area, allowing backup of local and remote computer systems. Many tape drive systems can contain several tapes at once and have multiple drives to allow access to vast volumes of storage capacity.

The new LTO-2 tape drives are faster than most magnetic disk drives in sequential I/O. They can sustain 30 MB/sec. The biggest advantage of disk drives is that they are random access devices. Tape media has a much longer shelf life than can be expected from a disk drive.

Tape devices are accessed through device files. For SCSI drives the file-names are /dev/stX, where X is the number of the device. EIDE drives are named /dev/htX.

**Hard drives** are the fastest backup devices and the most expensive. Even though the cost of hard drives has dropped significantly, the cost per megabyte is still quite high. Hard disk backups are good for small immediate backup needs. For example, if you need to reinstall a program on a system, you might back it up to a hard drive before installing.

**Optical drives** are slightly faster than tape and have a longer storage life. The cost of optical media has dropped to a price comparable to that of tape. With newer drive systems supporting “juke box” technology (the capability to have a large volume of optical media available), this is a viable option.

**High-capacity floppy drives** provide up to 200 MB of storage on a floppy cartridge about the size of a standard floppy disk. The storage speed is about the same as that of tape drives, but the media is considerably more expensive. A common type of high-capacity floppy drive is the Zip™ drive from Iomega.

Generally, the backup device of choice is the tape drive. Even in a home system, a tape can be installed for less than one hundred dollars; and tapes are reusable, making the long-term cost minimal. However, many newer machines are equipped with CD-R or CD-RW drives, and the CD-R media is inexpensive. On a single-machine system, the CD-R is a good choice for a backup.

There are three basic types of backups: full, incremental, and differential. Full backups copy the entire volume of data and mark the files as having been backed up. Incremental backups copy only those files that have changed since the last backup and then mark the files as having been backed up. Differential backups copy only the files that were changed since the last backup and do not mark the files as having been backed up.

It is a good idea to keep multiple backups of your systems. Most administrators follow a three-backup pattern with daily backups. The pattern is to perform a full backup at a scheduled time once a week. You should perform incremental backups daily during the week, rotating the tapes over several days or weeks. At the end of the second week, start over with a new set of tapes for the full backup. At the end of the third week, do a full backup with another set of tapes. At the end of the fourth week, overwrite the first week’s full backup tapes. Rotate the tapes every week thereafter. Your backup rotation requirements may be different, but you get the idea: Never have only one backup.

It is a good idea to have at least one full backup set offsite. If disaster does strike and you lose the entire facility, you will have at least one surviving backup set that you can use to get your system up and running.
