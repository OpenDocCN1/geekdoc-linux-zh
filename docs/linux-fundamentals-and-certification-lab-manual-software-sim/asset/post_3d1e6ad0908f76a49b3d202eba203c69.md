
The RSA method is used to generate digital certificates. A digital certificate is used to verify that an individual is who they claim to be. Certificates are generated and maintained by certificate authorities (CA) using the public/private key pair.

# NOTE

You can learn more about the Rivest-Shamir-Adleman algorithm at www.rsasecurity.com/rsalabs/faq/.

Certificate authorities can be “in-house” or remote trusted sites. The only difference between certificates generated locally and those generated by trusted authorities is the level of trust. For example, if users are connecting remotely and sending information to other users on the same system, local certificates ensure that the information is from the individual indicated. However, if users are dealing with another company, the certificate may need to be verified by a third-party source. Third-party certificate authorities, such as Verisign (www.verisign.com) or Thawte (www.thawte.com), provide assurance to both parties that information sent between them is from who they say they are.

A user that wants a certificate must contact a certificate authority to request a certificate. The certificate authority will verify who the individual is and issue a certificate with a level of confidence applied to it. The confidence level depends on how much research the certificate authority did to verify the individual’s identity. If the CA verifies only by listing the individual’s address and phone number, then the certificate has a very low confidence level. However, if the CA does a background check of the individual, the certificate has a higher confidence level. Usually, certificates with the highest confidence level that are issued by third-party CAs are expensive.

A certificate is essentially a digital signature. Digital signatures are unique and so secure that legislation has recently passed that legitimizes digital signatures. This means that a digital signature is as legitimate as a written signature.

In asymmetric encryption, a private key is used to digitally sign a document, which is then sent to the intended recipient. The recipient of the document uses the sender’s readily available public key to verify that the message is legitimate. Something encrypted by a private key can be read only by a public key, and something encrypted by a public key can be read only by the associated private key.

Remember that a network provides many open doors to the Linux operating system. The starting point of any security policy is to secure each and every individual host. # BIOS and Boot Loader Security

You are already familiar with login passwords. But are you aware that the system is up and running, even if you don’t log in? The Linux operating system loads from the init process, which, in turn, loads a lot of other processes, the last of which is to request the user authentication. It makes no difference whether the authentication is local or remote.

**BIOS Security**   BIOS security enables you to require a password to turn on the computer system. When the computer powers up, the first thing it does is load the BIOS. This is before the boot loader takes over. The BIOS on a computer system can be configured to require a password to prevent unauthorized user access from those with physical access to the machine.

The BIOS has boot settings to specify which devices the operating system will be loaded from. Loading the operating system from the hard drive only can prevent someone from using a floppy disk or CD-ROM to start the system in an attempt to steal resources.

If the BIOS is not secure, the system can be set to boot from a floppy disk or CD-ROM, making it much easier for an unauthorized user to gain access. The BIOS password is not 100 percent secure because the manufacturer provides a method of password recovery should the user forget it. This means that anyone with physical access to the computer can gain access to its data.

**Boot Loader Security**   Both GRUB and LILO provide password protection if selected. Without password protection of the boot loader, an unauthorized user can enter single-user mode. Single-user mode allows access to the operating system as root user.

GRUB, while providing a much richer boot loader, also presents a much greater security threat. The GRUB console can be used to change the system’s configuration or gather information about the system. If the system is set to dual-boot and access is gained to DOS or some older version of Windows that does not support any security features, the system is compromised.

During installation, you are given the opportunity to create a boot loader password. If you do not set a password at that time, you can use the following procedure to enter one afterward.

**Setting a GRUB Password**   GRUB will accept a plain-text password or a hashed password. Plain-text is readable by anyone. A hashed password is relatively safe. MD5, message digest 5, is used by GRUB to provide a unique sequence of characters that can only represent the text it was generated from. MD5 is a one-way hash function, which means that it takes a message and converts it to a fixed string of digits.

To encrypt a password, use the `/sbin/grub-md5-crypt` command. When prompted for a password, enter the new GRUB password and press Enter. This will return the MD5 hash of the password you entered.

```
# /sbin/grub-md5-crypt
Password:
Retype password:
$1$fpbA50$PoYiovj9mJPFyJFM41X611
#
```
