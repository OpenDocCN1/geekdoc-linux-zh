# MANAGING CRON JOBS

Many tasks can be performed when system usage is low. For example, you may want to run a backup of user files at 2:00 am when most users are not connected to the system. An administrator could be available during late hours to run the job; however, a better solution would be to have the job run automatically at the given time. A system administrator can use automated tasks to perform almost any task at any given time.

cron jobs are used to run jobs that are repeated regularly. If a job needs to be run only once at a specific time, the **at** or **batch** command can be used. The **at** command accepts read commands from standard input or from a file and then executes the commands at a specified time using the environment variable shell of the requesting user.

# Understanding cron

*cron* is an acronym for *command run on and* is a Unix scheduler. *cron* is a daemon that can be used to execute scheduled tasks. *cron* is also a service, meaning that once started, it remains running while the system is up. *cron* responds to the system or individual users based on time. A *cron* can be scheduled to run hourly, daily, weekly, or monthly. *cron* wakes up once a minute, examines its configuration file(s) for changes, and executes commands if the time matches.

cron jobs are used by the system and by users. *System cron jobs* are *cron*s that are used to perform systemwide periodic jobs. For example, the */tmp* directory can grow in size and get cluttered with files that are no longer needed. A system *cron* will check the */tmp* directory daily and clean it up.

*User cron jobs* are *cron*s that are created for individual users. These could be anything from reminders of appointments to periodic backups of data files.
