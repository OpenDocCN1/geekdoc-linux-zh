### PACKAGES

The Linux operating system gets its name from the Linux kernel. The total operating system is made up of many other programs that do everything from providing the user interface to retrieving the time from remote time servers. These programs are presented in the form of packages to install on the specific Linux distribution you are using.

The term *packages* in Linux operating systems refers to applications bundled into an archive and ready to install. This section discusses packages in general terms, but covers Red Hat Package Manager (RPM) in detail. RPM is used by many Linux installations, including Red Hat, SuSE, Mandrake, and others.

#### Package Concepts

A package is an archive of files. Archived files in Windows typically use the *zip* format. Linux packages are similar in functionality, but a little different in implementation. An RPM file, for example, when installed will first check to make sure dependencies are in place. In other words, the RPM package will check that any files it depends on are installed first.

Packages contain precompiled software that is ready to install on a Linux operating system; however, some applications for Linux are distributed as source code. Source code must be compiled into binary code before it can be run on a Linux system. Packages are compiled for different Linux distribution versions and are ready to install. Precompiled programs are generally smaller than the source code, making them easier to transfer over a network.

Without packages that are configured for your specific computer and operating system, you would have to compile the programs and then install them into the correct locations. If you later decide to update the programs, it is up to you to make sure all files are updated, in the correct location, and not duplicated.

Binary files are compiled to work with specific computer resources. Resources include the processor and system libraries. Processors are designed with a unique micro-code that controls all the functions of the computer system. Each processor type must have source code compiled with the system libraries designed specifically for that processor.

One of the most important day-to-day jobs of an administrator is managing packages. When a new program update is released the administrator must find the program, determine the version, and install the update if needed. Packages and package management programs make the job of managing the software much easier.

### Package Formats

Most programs are made up of many files, including documentation files, support files, and program files. Keeping all the files together during transport was easy when there were only a few files, but with new computer resources that enable operating systems to provide many more services, programs have gotten very large. To ease the burden of administrators "keeping up," all these files are combined into a single container that works much like a subdirectory on a file system. The combined files are often compressed to decrease the disk space required and to make them easier to transmit over a network.

These compressed containers are called packages. A single package can contain one or even hundreds of files. Your Linux installation probably contains over a hundred packages.

There are several package formats. Some packages are proprietary to Linux distributions, such as RPM and DEB (Debian GNU/Linux Package Manager). Others are common to all distributions, such as TAR, GZ, and TAR.GZ.

The common package formats are more difficult to manage. Basically, all these packaging tools do is package and compress the application. After an application has been installed from a TAR, GZ, or other common package, the user still has to do a lot of work to get the application to work. Information about the package, such as version number and date compiled, must be maintained by the administrator manually.

Packages created by the tar program are called **tar balls**. Tar balls are basically just repositories for program files and contain none of the extras provided by RPM or DEB package management files. However, they are universally accepted by Linux and Unix systems.

Package formats such as RPM and DEB provide other information besides the program and documentation files. These package types provide a way to store information about the package required during installation or uninstallation. This information includes version number, build number, date and time last compiled, and other information that is useful if the package needs to be updated or uninstalled.

RPM and DEB package management programs use an installed database to maintain package information. The database for RPM files is stored in the /var/lib/rpm directory, and the DEB database is stored in the /var/lib/dpkg directory. These directories contain several files that include the following:

![](img/37f079cee226b270f2e09b37a2e4a05d_142_0.png)

- **Dependencies:** This database contains information about what is needed when a file is installed or updated. This information is used to ensure that programs on which the new package is dependent are already installed. If the dependent files are not installed beforehand, the new package is blocked from installation. The management system also uses the database to prevent removal of a package that is a dependency of others.

- **Package data:** This database includes the build date, version number, date compiled, and other information. The information is retained in the database even if the package is removed.

- **File data:** The database contains information of all installed files. With the rpm command in Linux you can query the package database and determine to which package a file belongs. The database also stores information about the file ownership and permissions. This information is stored only for installed packages and is not maintained for user-defined files.

Using a package management system, the database will be updated as packages are added, removed, or updated. The database can be queried for package information, allowing the package management system to check program dependencies during operations.

Packages installed without using a package management system are not identified in the database. Some applications are easily installed by an administrator without using a package management system. These applications usually contain only a few files and can easily be copied to the correct directories for installation. Using a package management system, however, provides a way to document installation, giving the administrator a convenient way to track even the simplest packages.

Typically, only one package management system is used on a Linux operating system. It is possible to install both RPM and Debian package management systems on a single computer; however, one of the jobs of a package management system is to determine dependencies when installing packages. If two package systems are used, this service is not possible.

### Building Packages

Some programs are distributed only as source code in tar ball form. It is feasible to compile the source code and install the application to the correct directories; however, this requires an administrator to document the application manually. Usually, programs that are compiled from source code go into the /usr/local directory. RPMs and DEBs typically do not use this directory, making it easier to keep the self-compiled programs separate from the precompiled packages.

Compiling and building packages makes it possible to make changes to programs. Customizing applications requires some programming knowledge, but can allow programs to run on your Linux system that may not be available in precompiled formats.

Building packages is very important in the enterprise environment, where a systems administrator may be managing hundreds of servers. If you must compile a package from source to achieve some sort of customization it should be done only once. The resulting binaries should be packaged and distributed in package form.

Tools can be used to automate the distribution of packages. Yum is an example of such a tool. Red Hat’s up2date is another.

To standardize program installation, it may be desirable to build a package rather than manually install a program. Building an RPM or DEB package is beyond the scope of this text. Building packages requires creating special files to control the RPM or DEB package, and then commands to build the package.

Helper programs are available for building and converting packages. For information on the package converter Alien, go to www.kitenet.net/programs/alien/.

### Installing and Removing Packages

Working with packages changes the Linux operating system. The change may be very subtle, but it is still a change. Before experimenting with packages, you may want to set up a test machine to use rather than a production system.

Before installing, removing, or updating packages, make sure that you will not be interfering with currently installed software that is being used. If you are not the only person using the Linux system, you should check with the system administrator before changing the system.

### TAR FILES

Tar is the Linux program for dealing with GNU’s version of tar. Tar is an archiving program designed to store and extract files from an archive file known as a tar file or tar ball. Tar was originally designed to archive to tape (Tape ARchive), but is now used to archive almost anything to disk.

The term for removing files from an archive is *unzipping* or *extracting*. *Unzipping* files is a common administrative task. Most files transmitted over a network are archived. Archiving files reduces administrative work by combining multiple files into one file and typically, through compression, reduces the amount of network bandwidth required.

The common extensions of a zipped file are:

- .gz,
- .tar
- .tar.gz
- .tar.z
- .z
