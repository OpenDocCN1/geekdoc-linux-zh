
As you monitor system processes, you may find that some processes are taking too much CPU time. How much time is too much, you can learn only from experience on the particular machine the processes are running on. However, some problems with processes taking too much time are obvious. For example, if a process owned by jsmith takes 70% of CPU time consistently, you may have a problem with that process. The **renice** program can be used to change the priority of a process without disrupting its operation.

The **renice** command alters the priority of a running process. Priorities can be altered for a PID, process group (pgrp), or username. The syntax of renice is **renice priority [[-p] pid ...] [[-g] pgrp ...] [[-u] user ...]**, where pid is a list of process IDs, pgrp is a list of process group IDs, and user is a list of usernames. For example, to use renice to change the priority of the user jsmith to a lower value of 5, use the **renice +5 -u jsmith** command.

You can also change priority on more than one user or PID. For example, to change the priority of PID 14343 and the users jsmith and dangle to 10, use the **renice +10 14343 -u dangle jsmith** command. This command changes the priority of PID 14343 and all the processes owned by dangle and jsmith to 10.

## Killing, Suspending, and Restarting Processes

Processes don't always do what you expect. The reason may be a *bug* in the program or a hardware failure. For example, you may have written a script that performs a loop and contains a programming mistake causing the loop to never terminate. Examine the following script:

```
# cat forever_loop
#!/bin/bash
I=0
J=10
until [ $I -ge $J ]; do
	echo The value of I is $I
	sleep 1
done
#
```

![](img/37f079cee226b270f2e09b37a2e4a05d_312_0.png)

This bash script contains one until loop that just echoes the value of a variable, I. The loop checks that the value of I is greater than or equal to the value of J, and when the statement is true, it terminates. The problem with the script is that the value of I never changes; therefore, the condition will never be met, causing the script to run until terminated.

The resulting output of this script is:

*   The value of I is 0
*   The value of I is 0
*   The value of I is 0
*   The value of I is 0
*   The value of I is 0
*   The value of I is 0
*   The value of I is 0

This output will continue until you kill or suspend the script. Fortunately, you can suspend a script by using the Ctrl+Z key combination. Pressing Ctrl+Z will display the following:

```
The value of I is 0
The value of I is 0
[1]+  Stopped          ./forever_loop
#
```

If you look at the processes that are running, you will see that the **forever_loop** process has a state of T. State T means that the process is traced, or suspended. View the currently running processes to get the PID and STATE of forever_loop.

```
# ps a
  PID TTY      STAT   TIME COMMAND
15040 pts/1    S      0:00 -bash
15205 pts/1    T      0:02 /bin/bash ./forever_loop
15232 pts/1    R      0:00 ps a
#
```

A suspended process can be either continued or killed. To continue a suspended process, use the **fg** or **bg** command. The fg command continues a process in the foreground. Processes can be run in the background by using the bg command. To continue the currently suspended job, use the **fg** command:

![](img/37f079cee226b270f2e09b37a2e4a05d_313_0.png)

> To explicitly start a process in the background, add an ampersand (&) to the end of the command line. For example, to start a program called parse_names in the background, use the **parse_names &** command.

In the example above, instead of continuing the **forever_loop** process, you will probably terminate it instead. You can usually interrupt a process running in the foreground using the Ctrl+C (break) key combination, but that doesn’t work with a process running in the background. A background process must be terminated with the **kill** command.

The kill command sends a signal to a process. The syntax of the kill command is **kill [signal] pid**, where **signal** is a number or name indicating what to do with the process and **pid** is the process ID.

The signal can tell the process to terminate, terminate immediately, reread the configuration files, or perform other actions. To see a complete list of signal options use the **man 7 signal** command. The most commonly used signals are 1 (SIGHUP), 9 (SIGKILL), and 15 (SIGTERM).

**SIGHUP** tells the process to hang up, reread its associated configuration files, and restart. This signal is usually used with services that are running as daemons. Most other applications will ignore this signal. For example, to send the SIGHUP signal to the 10841 PID, use the **kill -HUP or kill -1 10841** command.

**SIGKILL** sends an immediate termination signal. This tells the process to immediately terminate, without closing files or performing any other normal housekeeping routines. SIGKILL should only be used if absolutely necessary. The **forever_loop** script can easily be killed with the **SIGKILL** signal because it does not have any associated data files that need to be maintained. To kill the **forever_loop** use the **kill -kill 15205 or kill -9 15205** command. (The PID number is from the previous listing.)

**SIGTERM** sends a signal for a normal program termination. This is the default action of the **kill** command. If the program has any open files it has the chance to close them before terminating the process. To kill the **forever_loop** gracefully, use the **kill -term 15205 or kill -15 15205** command.

## MORE ADMINISTRATIVE TASKS

Another program that can be used to manage processes is the **killall** command. This command uses the same signals as the **kill** command, but allows you to use the process name rather than just the PID. Again, the default signal is SIGTERM.

## CONFIGURING SYSTEM QUOTAS

There never seems to be enough disk space. Even with the availability of inexpensive high-capacity disk drives, the demand for more disk space always seems to grow. On a home-use Linux system the hard disk is often dual-installed with the Windows operating system, and this arrangement uses twice as much disk space as Linux alone. On a small business system, the operating system, applications, and data often take large amounts of space and hard drives are quickly used. On an enterprise-wide system, sometimes hundreds of users are given disk space to use and, if usage is left unchecked, this disk space will quickly fill up.

For example, the home space of users on the systems managed at a local university was recently audited and found to contain an average of 1.7 GB of information. Some users’ home space contained over 20 GB. The amount of free disk space available was quickly becoming nonexistent.

Ideally, on a multisuer, multitasking system, restricting the amount of disk space allowed to each user will bring disk usage under control. Restricting disk space usage enables an administrator to more easily track the amount of disk space used and to plan for future hardware upgrades.

Chapter 7 discussed how to determine who is currently logged into the system and who has logged in before using the **who**, **last**, and other commands. Usually, when a user logs in to the system, he or she is given disk space to use. With only a few users the amount of disk space used may be minimal, but on systems with many users the amount of disk space needed may be huge and therefore need to be managed.

*Disk* space is managed on Linux systems using *quotas*. *Quotas* enable an administrator to limit the amount of space made available to each user or group of users that log on to the system. Usage of disk space can be strictly enforced, or, in most cases, excessive disk usage is just reported to the root user and the user is not prevented from using the space.
