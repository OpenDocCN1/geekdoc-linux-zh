Any time you install or upgrade software you should track changes to configuration files. Well-written software should not change anything significant, but not all software is well written. It is best to make a backup of the system before installing new software. Backup is covered later in this chapter.

How you test the software depends on what the software does, who will use the software, and even when the software will be executed. For example, if the software to be tested is network capable and supports several hundred users, the testing methods will be somewhat different than if the software is not networkable and only one user will be running it. More information on testing and monitoring can be found in Chapter 13.

# Testing on a Production System

After you have finished testing on a test system, it is time to test in the production environment. Before you install any new software, *back up* the computer completely. If something goes wrong with the new software roll-out, the computer can be restored and more testing can be done to determine what the problem was.

Plan your installation or upgrade. The plan should include a schedule of events, test criteria, and expected test results. The plan should also include monitoring criteria. Program performance can be evaluated with log files and other tools. Monitoring tools are covered in more detail in Chapters 11 and 13.

Many organizations have a scheduled time to perform installs and upgrades on the computer system. Choose a time that will be least disruptive to the users of the Linux system. When scheduling time, include time to restore the system if needed.

![](bbox=[0.286, 0.51, 0.943, 0.545])

> One of the issues with a new software installation is getting the users of the software on board. Users should always be informed of what is happening with the system. It is good practice to establish a formal change management system in which management, users, and IT staff discuss, approve, and schedule proposed changes.

After the new software is installed, tests should be performed to ensure the software is functioning properly. There may not be time to fully test the software. At the very least, make sure the program is running and responding at a minimal level.

# Reconfiguring the Boot Loader

![](bbox=[0.207, 0.77, 0.268, 0.788])

When a computer starts up, the first program it runs is the BIOS, which is resident in a ROM chip. The BIOS checks and initializes the hardware, then looks for a program located on the first sector of the floppy or hard drive. This is the Master Boot Record (MBR) program. The MBR either locates the active partition and loads the first sector of that partition, or it loads information from a partition and then uses that information to load an operating system on any partition. The information loaded is the boot loader that is to be used.

![](bbox=[0.207, 0.818, 0.268, 0.835])

The boot loader's job is to load and then transfer control to an operating system kernel, which takes over the rest of the operating system load. Boot loaders are designed to work with more than one operating system.

The two primary boot loader programs used today in Linux are Linux Loader (LILO) and Grand Unified Bootloader (GRUB). Both programs work in a similar fashion. LILO is older and the most commonly used, but Linux distributors like Red Hat have changed their default boot loaders to GRUB, which offers the same feature set as LILO.
