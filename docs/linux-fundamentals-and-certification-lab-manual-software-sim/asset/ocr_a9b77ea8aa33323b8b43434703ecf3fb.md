Do you need a personal firewall? A personal firewall is another line of defense against those that are trying to break into your system. If you are participating in a private network in which all hosts are trusted, you probably don't need a personal firewall. If you are connected to a large public network, such as the Internet, you do. Testing the packets that are directed to your computer on a public network will probably show that your computer is assaulted from a number of sources. These could be anything from a ping request to an attempted login.

A personal firewall examines packets as they arrive and then allows or denies the traffic based on a set of rules. The rules can be customized to allow traffic from networks, from individual computer systems, or based on the type of packet.

As with any security measure, with a personal firewall you give up some of your freedom to protect your assets. For example, you would probably need to refuse Telnet connections because they are too easily cracked. Telnet was nice to use because it was supported by hundreds of applications, was easy to implement, and fast. An alternative to Telnet is SSH, which, while easy to use, is slower because of the security it provides.

Firewall applications are available, such as NetBSD, Sygate, and Trustix; however, most personal firewall applications are based on the netfilter/iptables that is built into Linux. netfilter/iptables is the framework inside the Linux 2.4.x kernel that enables packet filtering, network address translation (NAT), and other packet manipulation. netfilter/iptables is discussed in more detail in the Firewalls section later in this chapter.

# SERVER SECURITY

+   Objective 4.11
If your Linux system is acting as a server, its security becomes much more important. A server may provide services such as remote disk space, DNS, and e-mail for many users.

+   Objective 4.12
Therefore, a server must be protected, similar to a workstation. Critical services must be updated to ensure that any discovered vulnerabilities are patched, boot loader passwords should be used, root access to processes should be limited, and so on.

# Securing Services

The most secure services on a server are those that are not running. The first step in securing services is to audit what services are available and stop those that are not needed or are not secure. For example, enabling sshd and disabling telnet is a good idea because SSH is secure, whereas Telnet is not.

One way to view the services running on the system is to use the ps command. To view the services running on the Linux server, use the ps -xf | more command (Figure 12–9).
