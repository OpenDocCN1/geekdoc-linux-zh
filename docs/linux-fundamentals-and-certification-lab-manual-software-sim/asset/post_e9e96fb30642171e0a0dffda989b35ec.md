
## ADMINISTRATIVE TASKS

### NOTE

The name of the package is not the same as that of the RPM file. After the package is installed, the package is referred to with its configured name. In the case of the `tftp-server-0.32-4.i386.rpm` file, the package name is `tftp-server`, the version is 0.32, and the release is 4.

### Removing an RPM Package

After a program is no longer needed, it should be removed from the Linux system because every unused program takes up system resources. At a minimum the resources used are disk space, but some programs may be running and using CPU cycles and memory.

The syntax for removing an RPM package is similar to that of a query, `rpm -options rpm_package_name`, where `rpm_package_name` is the name of the package to be removed. For example, to remove the tftp-server program (Figure 6-7), use the following command:

```
rpm -e tftp-server
```

A query done after the package removal informs the user that the package in question is not installed.

### Listing the Files in an RPM Package

Listing the files within a package tells you not only what files are within the package, but their location in the file system. The syntax is similar to other RPM commands, `rpm -options package_name`, where `package_name` is the name of the installed package. To view the files within an RPM package named tftp-server (Figure 6-8), use the `rpm -ql tftp-server` command.

#### NOTE

Sometimes it is convenient to list files in an RPM before installing it. The following command will work for that purpose:

`rpm -qlp /path/to/rpm/program.rpm`

### Checking the Signature of an RPM Package

Red Hat uses Pretty Good Privacy (PGP) for identifying files. PGP is a technique for encrypting messages so that they can be read only by using a specific key. PGP is based on the public-key method, which uses two keys, a public and a private key. Information encrypted with the private key can be read only with the public key. This public key is distributed freely and is used only to read a digital signature, or byte sequence, within a file. If the signature matches, the file assigned to it is the original and unchanged file.

GNU publishes the GNU Privacy Handbook, which outlines the GNU Privacy Guard (GnuPG or GPG) project, an implementation of PGP. GnuPG includes tools for key pair generation, exchanging and verifying keys, encrypting and decrypting documents, and authenticating documents with digital signatures. Information about GnuPG can be found at http://www.gnupg.org.

The syntax of the command used to check the digital signature of a package is `rpm --checksig package_name`, where *package_name* is the name of the installed package. To check the digital signature of the package tftp-server, type the command `rpm --checksig tftp-server`.

This command requires that GnuPG be configured to run on the Linux system and be able to find a key ring with the appropriate keys. This command should be run before installing a new RPM package. An imported public key is carried in a header, and key ring management is performed exactly like package management. For example, all currently imported public keys can be displayed by typing the command `rpm -qa gpg-pubkey \*`.

### RPM Package GUI

Package management requires root access. The root user has unfettered access to the system and should be used with care. As mentioned in Chapter 4, the su command login is a better choice.

Red Hat Linux has a package management system that can be accessed through the GUI (Figure 6–9). This system allows you to add or delete packages provided with the Red Hat Linux distribution. It looks similar to the package management tool that is displayed during installation. All available packages are displayed, arranged in groups. Each group can be expanded and individual packages selected. If a package is unselected, the package is removed. Dependencies are maintained. If a package is selected for installation or removal, the operation is allowed only if dependencies are met.

The GUI package manager can be started from the command line by typing the command `redhat-config-packages`.

## VALIDATING INSTALLED PACKAGES

The old adage “you get what you pay for” is never more true than when used to describe Linux applications. Some packages are great and perform the work of other applications costing hundreds or even thousands of dollars; however, some packages are developed and then distributed over the Internet freely without much testing to prove their worth.

A Linux administrator cannot afford to install applications on the operating system and then forget them. Often, many users are dependent on the services provided by the installed programs and if the services fail, productivity can suffer, system performance can drop, and many other undesirable consequences may result. It is up to the administrator to maintain and monitor the programs installed on the system.

### Verifying Programs on a Test System

It is unwise to test a new program on an active production system. Some software can cause a system to fail completely, causing down-time of the Linux operating system. Even a simple upgrade can cause the entire operating system to fail. For this reason it is a good idea to test new software on a *test system*.

In a perfect world, the test system would be exactly the same type and size of computer system as the production system. And in a small shop with limited needs, a duplicate computer can be used as a test system with minimal cost. In a medium to large size business, however, the cost of providing two production quality machines and using only one for production is prohibitive. More likely, the test system will be an older system or, at most, a system of much lower quality. This makes testing the performance of programs in these systems very difficult.

At the very least, the test system must have the same version of operating system as the production system. Linux distribution versions can be very different, even within the same distributor. Kernel changes, updated libraries, and updated drivers can cause problems with some software.

If you have access to a test system that rivals your production system, testing software is much easier and more likely to provide accurate results. The best scenario is to install a mirror image from the production environment on the test system. After the production system is duplicated, the new software can be installed and then monitored and evaluated.

Make sure you read the latest documentation for the software to be installed, especially documentation concerning your Linux distribution. Often special instructions are given to install software libraries or change configuration files. Usually the documentation is included with the software or is available online from the software distributor.

Any time you install or upgrade software you should track changes to configuration files. Well-written software should not change anything significant, but not all software is well written. It is best to make a backup of the system before installing new software. Backup is covered later in this chapter.

How you test the software depends on what the software does, who will use the software, and even when the software will be executed. For example, if the software to be tested is network capable and supports several hundred users, the testing methods will be somewhat different than if the software is not networkable and only one user will be running it. More information on testing and monitoring can be found in Chapter 13.

### Testing on a Production System

After you have finished testing on a test system, it is time to test in the production environment. Before you install any new software, *back up* the computer completely. If something goes wrong with the new software roll-out, the computer can be restored and more testing can be done to determine what the problem was.

Plan your installation or upgrade. The plan should include a schedule of events, test criteria, and expected test results. The plan should also include monitoring criteria. Program performance can be evaluated with log files and other tools. Monitoring tools are covered in more detail in Chapters 11 and 13.

Many organizations have a scheduled time to perform installs and upgrades on the computer system. Choose a time that will be least disruptive to the users of the Linux system. When scheduling time, include time to restore the system if needed.

![](img/37f079cee226b270f2e09b37a2e4a05d_151_0.png)

> One of the issues with a new software installation is getting the users of the software on board. Users should always be informed of what is happening with the system. It is good practice to establish a formal change management system in which management, users, and IT staff discuss, approve, and schedule proposed changes.

After the new software is installed, tests should be performed to ensure the software is functioning properly. There may not be time to fully test the software. At the very least, make sure the program is running and responding at a minimal level.

### Reconfiguring the Boot Loader

![](img/37f079cee226b270f2e09b37a2e4a05d_151_1.png)

When a computer starts up, the first program it runs is the BIOS, which is resident in a ROM chip. The BIOS checks and initializes the hardware, then looks for a program located on the first sector of the floppy or hard drive. This is the Master Boot Record (MBR) program. The MBR either locates the active partition and loads the first sector of that partition, or it loads information from a partition and then uses that information to load an operating system on any partition. The information loaded is the boot loader that is to be used.

![](img/37f079cee226b270f2e09b37a2e4a05d_151_2.png)

The boot loader's job is to load and then transfer control to an operating system kernel, which takes over the rest of the operating system load. Boot loaders are designed to work with more than one operating system.

The two primary boot loader programs used today in Linux are Linux Loader (LILO) and Grand Unified Bootloader (GRUB). Both programs work in a similar fashion. LILO is older and the most commonly used, but Linux distributors like Red Hat have changed their default boot loaders to GRUB, which offers the same feature set as LILO.
