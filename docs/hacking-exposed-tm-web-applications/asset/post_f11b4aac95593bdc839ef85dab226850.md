However, IIS 5's default configuration makes this approach difficult (another good reason to upgrade from NT 4!). To explain why, we first need to delve into a little background on IIS's processing model. Bear with us; the result is worth it. The IIS process (inetinfo.exe) runs as LocalSystem and uses impersonation to revert requests (Most Web servers run as something other than the privileged user on the machine, best practices. Components of IIS 6 can run as nonprivileged accounts.) IUSR is used for anonymous requests.

The RevertSelf API call made in an ISAPI DLL can cause commands to run as SYSTEM. In essence, RevertSelf acts the current thread to "revert" from IUSR context to the context under which inetinfo runs—SYSTEM. Actually, it's little more complicated than that. ISAPI extensions are wrapped in the Web Application Manager (WAM) object, which can run within the IIS process or not. Running "out-of-process" extracts a slight performance hit, but prevents unruly ISAPI applications from crashing IIS process and is, therefore, a more robust way to run ISAPI applications. Although proved to boost performance, interesting security implications arise from this:

- If in-process, WAM runs within IIS process (inetinfo.exe) and RevertSelf gets SYSTEM.
- If out-of-process, WAM runs within a separate process (mts.exe) and RevertSelf gets the IWAM user, which is only a guest.

This setting is controlled within the IIS Admin tool by selecting the Properties of a Web Site, navigating to the Home Directory, and adjusting the Application Protection pull-down menu. IIS 5 sets this parameter to Medium out-of-the-box, which runs ISAPI DLLs out-of-process (Low would run them in-process).

Thus, privilege escalation via RevertSelf would seem impossible under IIS 5 defaults—ISAPI applications run out-of-process, and RevertSelf gets the IWAM user, which is only a guest.

Things are not quite what they seem, however. In February 2001, security programmer Horowitz found an interesting mechanism for bypassing the Application Protection setting, not noting what was its configuration. While the IIS configuration database (called the Metabase), he noted the following key:

```
LM/W3SVC/InProcessIsapiApps
Attributes: Inh(edit)
User: Server
Data Type: MultiSZ

Data:
C:\WINNT\System32\idq.dll
C:\WINNT\System32\inetsrv\httext
```

```
C:\WINNT\System32\inetsrv\httpd.dll
C:\WINNT\System32\inetsrv\ssinc.dll
C:\WINNT\System32\mswpr.dll
C:\Program Files\Shared Web Server\Extensions\40\isapi\_vti_auth.dll
C:\Program Files\Shared Web Server\Extensions\40\isapi\_vti_admin.dll
C:\Program Files\Shared Web Server\Extensions\40\isapi\shtml.dll
```

Rightly thinking he had struggled on special built-in applications that always run in-process (no matter what configuration), Horitz wrote a proof-of-concept ISAPI DLL called RevertSelf and named it one of the names in Database listing previously shown (for example, idq.dll). Horitz built functionality into the DLL that added the current user to the Administrators group. Sure enough, the technique worked. However, the false DLL didn't have to be copied over the "real" existing built-in DLL—simply by placing it in any executable directory on the system and executing it via the browser anonymously, IUSR and IWAM were added to Administrators. Horitz appeared to have achieved the goal: privilege escalation on IIS 5.0. Dutfully, he approached Microsoft and informed them, the issue was patched in MS001-026 (post-SP2) and made public in August 2001.

Several ISAPI DLLs were posted to the Internet after the release of the advisory. One called iscrack.dll, worked somewhat like upload.asp and cmd.asp, providing a form-based input for attackers to enter commands to be run as SYSTEM. With our previous example, an attacker could rename iscrack.dll to one of the InProcessisApps (say, idq.dll), upload the Trojan DLL to C:\inetpub\scripts using upload.asp, and then execute it via the browser using the URL:

```
http://victim.com/scripts/idq.dll
```
