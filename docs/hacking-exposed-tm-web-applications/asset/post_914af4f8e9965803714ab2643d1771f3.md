# DENIAL OF SERVICE AGAINST WEB SERVERS

Web servers are probably the most picked-on systems on the Internet—probably because they make up the vast majority of Internet-connected potential targets. Thus, if you run a Web site, it's likely that you will face up to the realities of denial of service (DoS) someday. Here, we will briefly discuss possible Web server DoS attacks and countermeasures.

# TCP Connect Floods

Because a Web server needs to listen on at least one TCP port in order to provide service, they make a ripe target for simple resource consumption attacks. One of the most effective DoS attacks against a Web server is thus a simple TCP connect flood. Web servers perform a process or thread to handle incoming HTTP requests, and if enough requests can be generated in a short amount of time, system resources can be overwhelmed.

One tool that used to get great success when performing DoS testing against clients carries the unfortunate apt Portack (where the four letters refer to a particularly crude English lexitive). When configured, Portack can flood a Web server with TCP connections, and it keeps reconnecting on socket until the Web server can no longer service legitimate requests. Given a handful of beefy attack machines and a decent network pipe, we see this attack case fits for small to medium-sized Web servers.

# TCP Connect Flood Countermeasures

The easy answer to resource consumption attacks is adding more resources until the other side runs out. Of course, this is easier said than done on a tight budget, but you may be surprised by what you get from your company if you point out the effects that a DoS Web site can have on customers.

Only slightly crafty are DoS attacks that exploit vulnerabilities in Web software. One good example is the IIS 5 WebDAV Propfind, discovered by Guninski in 2001. In essence, it involves padding an XML WebDAV request with an overlong value that causes IIS to restart. Here is the format of a sample

```
PROPFIND / HTTP/1.1
Host: 192.168.234
Content-type: text/xml
<?xml version="1.0"?>
<a:propind xmlns:a="DAV" xmlns:u="over">
<a:prop><a:displayname></u:prop></a:prop></a:propind>
```

The value may be greater than 128,000 bytes. The first time such a request is sent, IIS responds with an HTTP 500 error. Upon the second request, the service is started. Obviously, if several such requests are made to an IIS 5 server continuously, it can prevent the service from serving valid requests. We developed a proof-of-concept Perl script called v5.pl that needs two requests, sufficient enough to restart the service once.

Clearly, such behavior is undesirable from an availability standpoint, but also considers its utility to attackers who need to restart the service to implement some additional attack. One example might be an IIS privilege escalation exploit that requires the IIS's access token to be reset. WebDAV Propfind Could also be used for such purposes.

It's noteworthy that IIS 5 implements an automatic restart following a crash of this nature, one of the hidden benefits of migrating to Win2000 (older versions of IIS simply fail).

# Countermeasures for Specific DoS Vulnerabilities

Take a two-pronged approach to combating specific DoS vulnerabilities. One, get relevant patches. Disable any unnecessary Web server functionality. We'll use the IIS 5 WebDAV Propfind DoS as an example again to illustrate our points.

On the front patch, we'll slip in our usual recommendation that Web servers should avoid the cutting edge when it comes to vendor patches. If you haven't patched it, someone will find it. The specific patch for the IIS 5 WebDAV Propfind DoS can be found in Security Bulletin MS01-016.

As disabling unnecessary functionality, IIS 5's WebDAV feature can be disabled according to Microsoft Knowledge Base Article Q241520 (see "References and Further Reading" at the end of this chapter). You can also disable it using the IISLockdown tool (see the previous discussion in this chapter). Note that disabling WebDAV prevents WebDAV requests from being processed by IIS, and this could cause the loss of such features as:

- Web folders
- Publishing to the Web site using Office 2000 (but not via FrontPage Extensions)
- Monitoring on IIS 5.0 server via Digital Dashboard

Per our recommendations earlier in this chapter, we strongly believe that all extended IIS functionality should be disabled unless absolutely necessary, WebDAV.
