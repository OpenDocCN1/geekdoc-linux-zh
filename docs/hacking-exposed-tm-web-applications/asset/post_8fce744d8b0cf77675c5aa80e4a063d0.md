# Hacking Exposed Web Applications

One of the most challenging aspects of Web application security testing is to understand the variety of technologies that comprise a typical commercial Web site. We have presented a solid methodology for testing the security of Web apps in this book, but the real skill of application testing often lies in persistence, and wisdom gleaned from experience. For example, there are few, straightforward techniques for testing directory vulnerabilities (see Chapter 6)—but what files you try to access? The answer differs on the operating system and application. Maybe the application survey (see Chapter 4) did not reveal any 'secret' or administration directories—but notice that the application uses 'sec' in front of variable directories. If you tried looking for /sec/admin instead of /admin/?

The chapter is an amalgamation of our best Web hacking stories designed to present some of those 'real-world' lessons we've learned from our years of Web testing. We thought it would be a nice idea to cover the many aspects of Web application security in the previous pages, and we hope that it gives readers greater insight into the art (as opposed to the science) of Web application hacking. Enjoy!

> Obviously, the names and exact technical details in this chapter have been changed to protect the confidentiality of the relevant parties.

# CASE STUDY #1: FROM THE URL TO THE COMMAND LINE AND BACK

Our first case study deals with a bank that opted to host its online banking services with an Application Service Provider (ASP). The banking application, also developed by the ASP, had few security holes, plus a script that was writable to allow a directory traversal attack.

```
/openserv/HB/dimlDisplay.cgi?DIML_FILE=SummaryDetail.diml
```

This allowed us to escape the Web document root and browse the file system. In this case, the Web platform was iPlanet server on Solaris:

```
/openserv/HB/dimlDisplay.cgi?DIML_FILE=../../../../etc/passwd%00SummaryDetail.diml
```

Note that the SummaryDetail.dim file is appended to the URL. This is required because the application apparently has a .dim extension before dumping the /etc/passwd (or any other) file. Once /etc/passwd was discovered, the next step was to examine each user's home directory for .profile, .kshrc, and .kshenv files. These files contain information such as the location of secret PGP keys. It revealed roots located in ineffective chroot environments: /home/jail/usr/bank/AXIS.cfg.

One unique thing about the directory traversal exploit is that it enabled us to view directory contents as well as files. We were able to poke around the Web server's directories and discover Web server configuration files (magnus.conf for i). We discovered that the ASP was using hosting sites for over dozen banks—on the same Web server! More importantly, we found a directory that contained the administration scripts for the Web server.

The initial survey of the Web application identified an administration interface in the /admin URI. Unfortunately, the server seemed to use proper ACLs that limited access to specific IP addresses for this directory. We verified this by viewing the configuration file for the /admin site.

What we also discovered in the file system with our friendly DIML_FILE parameter was that some older shells had never been removed. UNIX shells are the antithesis of secure CGI programs. A command shell is intended to be a powerful, complex interface to the operating system. Consequently, there are numerous methods for executing arbitrary commands or otherwise breaking out of the shell. One script presented a set of options for the user to generate a customized http log report:

```
/cgi-bin/admin/allstats.cgi
```

This form POSTed a long string of parameters starting with:

```
server_name=...
```

These arguments were passed to the a_form.cgi script. We verified this by checking the "action" tag:

```
/cgi-bin/admin/a_form.cgi
```

If we passed the data to run: server_name=... argument list, the a_form.cgi produces this output:

```
<Attempting to analyze -n https-80-bank-64 -x
-i /u/webs/logs/https-80-bank-64/access -c hnrfeuokc -t
s5m5h24 -1 c55h5 ptl 2>&</p>
```

The arguments are actually being passed to a script called analyze. The script was also nice enough to echo the command line. It was time to see what analyze could do. First, we tried to pass the ls command to the script:

```
/cgi-bin/admin/a_form.cgi?server_name=ls...
```

which returned:

Attempting to run: <code>./analyze -n ls -x /u/webs/logs/https-80-bank-64/access -c hnrfeuok -t s5m5h24 -l c+5h5 -p ctl 2>&1</code>

No luck here, but we can be sure that the n option is assigned the server_name variable. After a few modifications to the server_name, we find a combination that works:
/cgi-bin/admin/a_form.cgi?server_name=%0als0a...

which returns:

<h1 align=center>Starting analysis</h1>
<p>Attempting to run: code>./analyze -n ls -i /u/webs/logs/https-80-bank-64/access -c z -t z -l z -p c 2>&1</code
<p>This may take a bit.</p><p size=4>
./analyze: option requires an argument -n
Usage: /analyze [-n name] [-x] [-r] [-p order] [-i file] [-o file]
[-c opts] [-t opts] [-l opts]

For a list of all options, see:
./analyze -h | more

```
a_form.cgi
admin-log.1999-09
admin-log.2001-09
admin.css
admin.exec
admindb.cfg
admindb.cgi
allstats.cgi
```

The %0a character represents a newline character. The %0als%0a places the ls command on one line, but more importantly the command actually executes. At this point, we can execute any command under the Web server. The success of this test relied on extra characters (%00 and %0a) in order to be successful.

## Case Study #1 Countermeasures

The Web application had several problems, most of which could be easily fixed:

- Incorrect chroot Environment (Host): A UNIX chroot environment places a program and all its support files in a specific directory. The goal is to “jail” the program in this directory and not permit it to access other users' directories, the /var directory, or the system's /etc directory. For example, the Web server was installed in the /home/jail directory and should not have been able to escape.
- Directory Traversal (Web): The dimlDisplay.cgi file accepted filenames as arguments. It would have been better to apply strong input validation, or create an array of acceptable filenames and pass an array index on the URL.
- Legacy Scripts (Web): The /cgi-bin/admin scripts had not been used for several months, but remained on the server. On the other hand, they were written in UNIX shell (ksh), which was a security faux pas from being ignored.

# CASE STUDY #2: XOR DOES NOT EQUAL SECURITY

Case number two involves a major legal services firm who sought to migrate much of their document processing capabilities to an Online application (let's call them Acme, Inc.). Imagine the cost savings, their thinking went, if we could exchange documents with our clientele in electronic format directly through a Web interface—all of these copiers, scanners, printers, fax machines, cabinets, and so on would all go the way of the dinosaur. Of course, due to the sensitive nature of the legal documents they were entrusted to handle by their clients, security had to be a priority in the design of the application, not only in relation to external intruders, but also other authorized users (that is, clients). The application was based on Microsoft IIS and Active Server Pages (ASP). A client arranges to have a user account set up via an out-of-band mechanism (e-mail or a phone call), and then gains access to a virtual directory on Acme's Internet-accessible application where they can exchange digital files with Acme. Although all the interaction with the server occurs over SSL, the account is accessible via a simple username/password mechanism.
