As the program goes through the loop of buffer overflow tests, the target application returns errors. These errors might be "password incorrect," but some of them might indicate conditions for the "user" argument. The rule of thumb buffer overflow testing is to follow basic differential analysis. Send a normal request to an application and record the output. Send the first buffer to the application, record its output. Send the second buffer, record its output. And so on. When the output changes, examine the differences. This helps you track the specific attack (such as 7,809 slashes on the URL are not).

In some cases, the buffer overflow attack can enable the attacker to execute arbitrary commands on the server. This is a more difficult task to produce once, but simple to replicate. In other cases, security auditing in the first case, unsophisticated script runner in the second.

> Most of these buffer overflow attacks are performed "blind." Without access to attach a debugger or view log system information, it is very difficult to craft a buffer overflow that results in system command execution. The FrontPages Extension overflow on IIS, for example, could not have been crafted without full access to a system for testing.

## Canonicalization (dot-dot-slash)

These attacks target template files or otherwise reference alternate files on the Web server. The basic form of this attack is to move outside of the Document root in order to access system files, that is "../../../../../../boot.ini". The actual server (IIS and Apache, for example) is (hopefully) smart enough to stop this. Older versions of Compaq Insight Manager, however, happily allowed users to escape the Web document root.

## Hacking Exposed Web Applications

A Web application's security is always reduced to the lowest common denominator. Even a robust web server fails due to an insecurely written application. The biggest victims of canonization attacks are applications that use templates or parse files from the server. If the application does not limit the types of files that is exposed fair game. This type of functionality is evident from the URL:

```
/menu.asp?dimdisplay-menu.html
/webacc70User?login=html
/SWeditServlet?station_path=%z&publication_id=2043&template=login.htm
/Get.asp?scripts/Client/login.js
/includes/printable.asp?Link=customers/overview.htm
```

This technique will succeed against Web servers when the Web application uses templating techniques. In this case, the canonization is placed within the argument of the URL. For example, the login page of Novel's Web-based Groupwise application has "servlet/webacc?User.login=html" as part of the URL. The target is the "User.html=parameter. The attack becomes "servlet/webacc?User.html=../../Access/webacc.cfg%00". This directory traversal takes us out of the Web document and into configuration directories. The login page is a window to the target server—and we do not have to lose it!

- Many embedded devices, media servers, and other Internet-connected devices have rudimentary Web servers. When confronted by one of these servers, always try a simple directory traversal on the URL to see what happens. All too often security pleads second to application size and performance!

Let's take a closer look at the Groupwise example. A normal HTTP request returns:

```
$ /get.victim.com /servlet/webacc?user.html=login

</HEAD>
<!.login.html>
```

The first alert that goes off is that the webacc servlet is taking an HTML file (login.html) as a parameter. This is the perfect indication that the application is parsing file contents. so, let's see what if we rename the file to something that we know does not exist. Our goal is to generate an error since the application won't be able to find the file. Hopefully, the error gives us some useful information:

$ /getit.sh www.victim /servlet/webacc?user.html=gor-gor

templates/gor-gor/login.htt.Cannot load file: c:\Novell\java\nservlets\com\novell\webacc\templates\gor-gor/login.htt.

We now install the full path of the application. Additionally, we discover the login.html file is appended by default. This makes sense, since the application might need a default template if no user.html argument is passed. The login.html file, however, gets in the way of a good and proper directory traversal.
