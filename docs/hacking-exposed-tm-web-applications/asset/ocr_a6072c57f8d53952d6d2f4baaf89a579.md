> Look for ODBC errors in the HTML output, on the URL, and within comments or hidden fields. Some error-handling routines might pretend to mask raw error output, but still track the error for the developers to debug.

If the triggers a VBScript error or no at all, move on to the next parameter. A vulnerable SQL statement shines like a crazy diamond:

```
http://www.victim.com/SiteAdmin.asp?SiteID=12
```

Microsoft OLE DB for ODBC Drivers (0x80040E14) [Microsoft][ODBC SQL Server Driver][SQL Server]Unclosed quotation before the string ',@UserID=182'
/SiteAdmin.asp, line 7

The unclosed quotation mark indicates a vulnerable query. Plus, the error provides us with a name and the specific UserID we have been assigned. Any information about the database structure helps immensely. We will hold off on a full-fledged SQL attack. The "@UserID" looks like part of a parameter list, which would mean we need to test our conclusion. Let's see what the comment (--) generates. 

```
http://www.victim.com/SiteAdmin.asp?SiteID=12--
```

Microsoft OLE DB for ODBC Drivers (0x80040E14) [Microsoft][ODBC SQL Server Driver][Procedure 'getAdminHome' expects parameter '@UserID', which was not supplied.
/SiteAdmin.asp, line 7

At this point we know that SiteAdmin.asp is vulnerable to SQL injection. The double-dash allows us to process the remainder of the query as a comment. We have verified that the data are being passed to a stored procedure named getAdminHome1. It will be tough to launch a successful attack. Stored procedures expect a predetermined number of arguments and pigeonhole those arguments in specific parts of the query. We cannot merely rewrite the procedure's parameter list. For example, if our original UserID 182 and UserID 180 is an admin, we might be tempted to rewrite the UserID parameter:

```
http://www.victim.com/SiteAdmin.asp?SiteID=12,@UserID=180--
```
