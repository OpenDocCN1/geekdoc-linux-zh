### Cookie Manipulation with Achilles

| Popularity: | 7 |
| Simplicity: | 5 |
| Impact: | 2 |
| Risk Rating: | 5 |

The easiest way to hijack cookies is to sniff them off the network and then replay them to the server, spoofing anyone's identity. Of course, obtaining the necessary network access to permit sniffing cookies is a challenge, so attackers will likely adopt more clever mechanisms.

> Don't discount cookie sniffing—on large corporate networks, Web browsing traffic passes many other potential eavesdropping points on its way to the Internet!

One of our favorite tools for implementing more targeted cookie attacks is Achilles, which we've discussed often in this book. To review, Achilles is a proxy server that intercepts web communications and allows editing of the traffic. You run Achilles on your machine and set your web browser to use it as a proxy. Voila—all communications between you and the Web pass through Achilles. Set Internet Explorer to use the default local proxy port on your machine, select Tools | Options, click the LAN settings, and then select localhost and 5000 in the Proxy box as shown in Figure 12-6.

Once this is done, open Achilles as shown in Figure 12-7 and start the proxy by clicking the button with the "play" icon. Now browse to any site in your browser and then examine Achilles interface. You can see the data sent by the browser in Achilles data window, down as shown in Figure 12-7. By clicking the Send button, the request will be sent to the server. You can then repeat this process with the response sent by the server, the next request from the web browser, and so on.

As you see in Figure 12-7, one of the values stored in the cookie is the IDUSER token. This value is stored in cleartext in the cookie, and is easily manipulated using Achilles. Before this request is sent to the server, we can simply edit the ID=USER value so it reads ID=ADMIN (or something similar—it may take a few guesses to get it right). When we click Send in Achilles, an initial request has now the context of ID=ADMIN (whatever it may be, but we're betting it means something for this app!)

The preceding example used a relatively straightforward way of user ID values, we've seen numerous variations on this. When auditing a Web app for related issues, some key flags to look for include (for example, "USER=JDOE"), anything with a substring of ID (for example, "ID=JDOE" or "SESSIONID=BLAHBLAH"), admin (for example, "ADMIN=TRUE"), session (for example, "SESSION=BLAHLAH"), cart (for example, "CART=FULL"), and expressions as TRUE, FALSE, ACTIVE, and INACTIVE.

## Cookie Cutting Countermeasures

Once again, we've divided our discussion into client- and server-side recommendations.

**Client-Side Countermeasures** In general, users should be aware of sites that use cookies for authentication and storage of sensitive data. Also remember, if you visit a site-that uses cookies for authentication, they should use SSL to encrypt the initial post of your username and password so that it doesn't show up as plaintext in a sniffer.

One tool to help in this regard is Cookie! from Kookaburra Software at http://www.kookurra.com/. It can help to warn you when Web sites attempt to set cookies, enabling you to see what's behind the scenes so you can decide whether you want to allow such activity, or to use Microsoft's Internet Explorer built-in screening, go to the Internet Options control panel, click the Security tab, and select Internet Zone | Custom Level | Prompt for persistent and per-session cookies. Netscape browser cookie behavior is set via Edit | Preferences | Advanced, and checking whether We Are forcing A Cookie or Disable Cookies. Note that in IE 6, the settings for controlling cookies have been moved to the Privacy tab of the Internet Options control panel, which is shown in Figure 12-8. For those cookies that you accept, check them out if they are written to disk, and see if it is storing any personal information about you.

Another issue for users is to consider the patch level of their Web clients. Some time ago, Bennett Hazelton and Jamie McCarthy of Peacefire posted a script at http://www.peacefire.org/security/iecookies that extracted cookies from the client.
