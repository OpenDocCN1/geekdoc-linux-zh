For the most part, Web applications seem to handle state in a particular manner throughout the site. For example, an application might rely solely on cookie values, in which the state might be populated with cookie names and values such as Role=manager, UID=12345, or IsAdmin=false. The matrix helps even more when the application does not use straightforward names. # THE METHODOLOGY

A lot of what you need to know to perform attacks will be obtained from previous chapters. The site duplication and analysis of the Web site will help in determining how to change the HTTP request to subvert the application. In general, you will want to modify input fields that relate to user, username, access group, cost, filenames, identifiers, and so on. Where these reside is application dependent. Within the HTTP protocol, there are only a few fields where values can be passed. These are cookies, the query string, and in a POST request, and hidden tags. We will discuss each of them individually. For each, we will describe the data format and, more importantly, how it can be changed to hack the app. While working under the premise that if it is some kind of input, you can change it—it’s just a matter of how, what tool to use, and what to change it.

Authorization takes whenever the application pulls from the database or accesses a Web page. Can the user access the piece of information? How does the application identify the user (is it based on authentication, the URL, session management)? Some common areas to check within an application

+   Profiles Is there an area where a user can view their profile information (name, address, and so on)? What parameters or cookie values do the profile rely on? Does the parameter have to represent a user, a user ID number, or a seemingly random number? Can the values be changed to view someone’s profile?
