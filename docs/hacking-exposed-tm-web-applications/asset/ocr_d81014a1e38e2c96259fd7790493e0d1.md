# Chapter 5: Authentication

The final section of the server.cfg file, [DEBUG], contains debugging directives for the tool. These are more useful for developing and improving APS as opposed to security testing for a Web application. However, the DEBUG and BIN_DEBUG options can be helpful for tracking a Web session in order to go back through the contents at a later time as part of the source-sitting phase, you should have a properly configured server.cfg file. Running APS is simple:

```
$ python main.py
NTLM authorization Proxy Server v0.9.7 at "lothlorien:80"
2001 (C) by Dmitry Rozman
```

Now, you can use any tool that normally breaks against NTLM authentication. For example, here is how you would run get through the proxy. APS is listening on port 80 at the host 192.168.10.23 and the target application that uses NTLM authentication at http://www.victim.com:

```
$ export http_proxy=http://192.168.10.23:80/
$ wget -r http://www.victim.com/
```

It's honestly simple!

> Wget the http_proxy environment variable by default. Setting this variable depends on your command shell, but most likely uses the export or setenv command. "--proxy=on" to make sure you uses the proxy.

NTLM Authorization Proxy Server and SSL There will be other cases where the Web application requires an SSL connection. In this case, you will need to set up an SSL proxy using tunnel or openssl. The first step is to set the PARENT_PROXY and PARENT_PROXY in APS's server.cfg. In the following example, the target is still www.victim.com, the SSL proxy (using tunnel) on port 80 at host 192.168.10.20, and the Authorization Proxy Servers listens on port 80 at host 192.168.10.10. You will have to go through a few steps to get this to work, hopefully the convoluted method pays off when you run get (or any other tool) through the proxy.

Here is the SSL proxy setup. Remember to use the -c option because ssl is accept-clearttext and outputting traffic in SSL:

```
$ stunnel -p clientcert.pem -f 80 -r www.victim.com:443 -c

```
