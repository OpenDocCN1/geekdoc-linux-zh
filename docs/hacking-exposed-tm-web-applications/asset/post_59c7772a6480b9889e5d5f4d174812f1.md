# Hacking Exposed Web Applications

To properly perform authorization is one of the biggest mistakes people make when building web applications. In Chapter 5, we discussed the importance of authenticating users. This part of security is simple and understood by everybody—you want to have passwords to restrict access. However, once logged in, many systems rely on the default functionality and user interface of the Web browser to "restrict" access. If users are only presented a single link to view their profile, that does not mean it's possible to view other profiles or administration functions. By changing the URI, POST data, tags, and cookies, we see how an attacker can exploit sites that do not perform proper authorization. That is, the system does not check if a user is authorized to access the data.

Authorization occurs when a user has authenticated to the application. Authorization determines if the user can log in to the application. Authorization determines parts of the application the user can access. The objective of attacking these types of attacks would be the ability to view other users' data, and performing transactions on behalf of other users. It is sometimes possible to change to an administrative user and gain access to administrative pages.

Authorization can also be attacked at the Web server level. In these instances, the Web server itself may be misconfigured and permit access to files outside of the document root. These files can contain sensitive configuration information, including passwords. Another type of authorization attack is viewing a page's source code as opposed to its dynamically generated output. Gaining access outside the Web document root may be as simple as sending a URL-traversal characters (../../..). Viewing source code may be as simple as sending a URL-encoded suffix, as in the case of servlet engines that mishand ".js%70". In any case, the goal is to access restricted information.

# THE ATTACKS

Now that we know what we want to achieve, how do we perform hacks authorization? The technique is actually quite simple, the only catch being if the application permits it or not. You basically need to ask the Web server, "Show me the data for account X!" If the Web application is properly designed, it will happily offer up the information. There are some concepts to keep in mind when testing an application's access controls.

- Horizontal Privilege Escalation: Access to peer user's information. For example, an online banking application might control access based on the user's social security number. It might be possible to change the SSN in order to view someone's account, but administrating the application (such as creating, deleting, or modifying accounts) would require a different exploit. This attack targets functionality available to the user's level, but against data that are restricted.

- Vertical Privilege Escalation: Access an elevated user’s information. For example, the application could have a vulnerability in the session management that allows you to enter the administrator portion. Or the administrator’s password could be to guess. This attack targets functionality and data not available to the user’s level.

- Arbitrary File Access: Normally, include files with database credentials, or outside of the Web document root are restricted from application users. Different input validation attacks combined with a misconfiguration of the server can prevent a malicious user to access these files. Usually, these attacks target the Web server, but applications that use insecure templating methods create vulnerabilities within the application as well.

Each type of privilege access shares the same test method. If authorization to another user’s profile information can be gained by changing a cookie value, then it may also be possible to gain administrator privileges from the same value. In case, the between horizontal and vertical privilege escalation would be blurred. On other occasions, the application’s role-base privilege control could block a vertical escalation.

# THE METHODOLOGY

A lot of what you need to know to perform attacks will be obtained from previous chapters. The site duplication and analysis will help in determining how to change the request. In general, you will want to modify input fields that relate to user, username, access group, filenames, and so on. Where these reside is application dependent. Within the HTTP protocol, there are only a few fields where values can be passed. These are cookies, the query string, and in a POST request, hidden tags. We will discuss each of them individually. For each, we will describe the data format and, more importantly, how it can be changed. While working under the premise that if it is some kind of input, you can change it—it’s just a matter of how, what tool to use, and what to change.

Authorization takes whenever the application pulls from the database or accesses a Web page. Can the user access the piece of information? How does the application identify the user (is it based on authentication, the URL, session management)? Some common areas to check within an application

- Profiles: Is there an area where a user can view their profile information (name, address, and so on)? What parameters or cookie values do the profile rely on? Does the parameter have to represent a user, a user ID number, or a seemingly random number? Can the values be changed to view someone’s profile?
