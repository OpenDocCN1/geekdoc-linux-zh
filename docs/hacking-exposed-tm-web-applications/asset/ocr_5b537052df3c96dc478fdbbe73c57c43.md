The drawback of a session database is that a single value is passed to the client. If this value is nonrandom or easily determined, a malicious user could guess valid session IDs. Additionally, this method should only be used over SSL in order to maintain the security of the session ID.

# SESSIONID ANALYSIS

Testing a session ID does not have to be an active attack. Depending on the state information is passed, encoded, or encrypted, you could gather a wealth of information about the application (internal parameters or variables), other users (profile information in the state values), or the server (IP address, state name). Any data gathered about the application provides more clues to the application's internals or how to exploit a vulnerability.

# Content Analysis

The first thing is to determine what you're up against. Is state information passed along several variables, or just one? Is it based on a numeric value, or a string? Can you predict what the next value is going to be? Is the string encrypted, or just encoded? Can you decode it? Can you decrypt it?

There are a lot of questions we need to ask about the state information. This section will point you in the right direction for finding out what's being passed by the application.

# Deterministic Values

State information could contain usernames, ID numbers, or several other items to the application. There are also other items that tend to make up session tokens. Since a session commonly ties one client to one server at a point in time, there are nonapplication data that you can find.
