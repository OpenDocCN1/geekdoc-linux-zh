The main element of a DISCO file is contractRef, which has two attributes, ref and docRef, which point to the WSDL and documentation files for a given web service. Furthermore, the discoveryRef element can link the given DISCO document to other DISCO documents, creating a web of related DISCO documents spanning multiple machines and even multiple organizations. Thus, disco files often provide an interesting treasure trove for malicious hackers.

In its .NET Framework SDK, Microsoft published a tool called disco.exe that connects to a given DISCO file, extracts information about the Web services discovered at the specified URL (writing output to a file called results.disco), and downloads all the .disco and .wsdl files that were discovered. It can also browse an entire site for DISCO files and save them to the specified output directory using the following syntax:

```
C:\disco /output http://www.victim.com/service.asmx Microsoft (R) Web Services Discovery Utility Microsoft (R) .NET Framework, Version 1.0.37050] Copyright (C) Microsoft Corporation 1998-2001. All rights reserved.
```

Disco found at the following URLs:
http://www.victim.com/service.asmx?wsdl
http://www.victim.com/service.asmx?disco

The following files hold the content at the corresponding URLs:
C:\output.wsdl <- http://www.victim.com/service.asmx?wsdl
C:\output\disco <- http://www.victim.com/service.asmx?disco
The file C:\output\discomap holds links to each of these files.

In most prospective clients won't know the exact address of the .disco file, so DISCO also makes it possible to provide hints in the root's default page. If the root's default page is an HTML document, the <LINK> tag can be used to redirect the client to the :disco file:

```
<HTML>
<HEAD>
<link type='text/xml' rel='alternate' href='math.disco'/>
</HEAD>

</HTML>
```

If the root's default page is an HTML document, you can use the xml-stylesheet processing to accomplish the same thing:

```xml
<?xml-stylesheet type="text/xml" alternate="yes" href="math.disco"?>
```

## Hacking Exposed Web Applications

Although DISCO is probably going to be supplanted by the more widely accepted UDDI specification, no doubt developers will implement DISCO for its less complex, lighter-weight approach to publishing Web services. Combined with its ready availability in Microsoft's widely deployed technologies, DISCO or something like it will probably provide a good target for malicious hackers seeking information about Web services.

## DISCO and WSDL Countermeasures

Assuming that you're going to publish some information about your Web service, the best thing to do to prevent DISCO or WSDL disclosures from becoming serious issues is to prevent sensitive or private data from entering the XML. Authenticating access to the directory where the file exists is also a good idea. The way to ensure that DISCO or WSDL information doesn't end up in the hands of intruders is to avoid creating the relevant .wsdl, .disacom, .disco, and .xsd files for the service. If these files are available, they deserve to be published!

## BASICS OF WEB SERVICE SECURITY

As we've seen, there are potential security vulnerabilities associated with various aspects of Web services technologies. Let's summarize some of these points and introduce new ones as we take a look at Web services security from end to end.

## Similarities to Web Application Security

Web services are in many ways like a discrete Web application. They are comprised of scripts, executables, and configuration files that are housed in a virtual directory on a Web server. Thus, as you might expect, many of the vulnerabilities we've discussed throughout this book also apply to Web services.

One of the first and most obvious security issues becomes readily apparent with a cursory glance at Figure 10-1: Web services must be accessible across organizational boundaries, and in particular, the firewall. Furthermore, they expose business contracts to a wide audience via protocols as WSDL, DISCO, and UDDL. So, like Web applications, traditional TCP/IP security leaves firewalls little security for Web services.

Another apparently apparent issue is the reliance on lower-layer services like Web servers to support the basic infrastructure of Web services. As we saw in Chapter 3, Web servers have a long and colorful record of security vulnerabilities, and Web applications that are built on overly configured or unpatched servers are merely moments away from being hacked.

With Web applications, some of the most serious exposures will come from inappropriate information disclosure or poor authorization within Web services. Web services are just as vulnerable to inappropriate information disclosure as Web applications are to revelation of their respective script and authorization configuration files. Path information disclosed in these attacks may also lead to the dreaded directory traversal attack.
