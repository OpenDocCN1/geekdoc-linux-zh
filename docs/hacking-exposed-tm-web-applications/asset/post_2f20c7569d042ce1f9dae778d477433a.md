Not all ISAPI DLL security flaws are as high as the printer buffer overflow. In this section, we will discuss an example of source disclosure vulnerability related to an ISAPI DLL bug. Source disclosure encompasses a large class of issues that allow remote clients to view information that would normally not be authorized to see.
The+.html is a classic example of source disclosure that works against IIS 4 and 5. By adding +html to an active file request, IIS 4 and 5 serve up fragments of the source data from the file rather than executing it. This is an example of a misinterpretation by an ISAPI DLL named ISM. The .dll extension maps files to DLL, which serves the file's source by mistake. Here's a sample file called htr.txt that you can pipe through network to exploit this vulnerability—note the +html appended to the request:

```
GET /site1/global.asa+.HTTP/1.0
[CRLF]
[CRLF]
C:\>nc -rv www.victim.com 80 < htr.txt
www.victim.com [10.0.0.10] 80 (open)
HTTP/1.1 200 OK
Server: Microsoft-IIS/5.0
Date: Thu, 25 Jan 2001 00:50:17 GMT
<-- filename = --> ("Profiles_ConnectString") \
  "DSN=profiles;UID=Company_user;Password=secret"
```

## Countermeasures for ISAPI DLL Security Flaws

We recommend a multifaceted approach to identifying and preventing security issues with ISAPI DLLs, and discuss each aspect of our approach below.

### Remove Unused Extension Mapping The flaws at the root of the .printer buffer overflow and the .ht source include bug in ISAPI DLLs that should be disabled by removing the application mapping for the relevant DLLs to .printer and .ht files (and optionally deleting the DLLs themselves). This prevents the vulnerabilities from being exploited because the DLLs won't be loaded into the IIS process when it starts up. Because of the many security issues associated with ISAPI DLL mappings, this is one of the most important countermeasures to implement when securing IIS.

To unmap DLLs from file extensions, right-click the computer you want to administer, select Properties, and then the following items:

- Master Properties
- WWW Service
- Edit
- Properties of the Default Web Site
- Home Directory
- Application Settings
- Configuration
- App Mappings

At this final screen, remove the mapping for .printer to msw3prt.dll, as shown in Figure 3-1.

Use IISLockdown and UrlScan In 2001 Microsoft released a tool called IISLockdown (see the References and Further Reading). As its name implies, IISLockdown is an automated, template-driven utility for applying security configurations to IIS. It configures various settings related to the following items:

- Internet Services Allows disabling of the four services (WWW, FTP, SMTP, and NNTP) as appropriate for the role of the server.
- Script Maps Allows disabling of ISAPI DLL mappings as appropriate for the role of the server.
- Additional Security A catchall section that includes removal of default virtual directories like IIS, IISHelp, Scripts and so on; NTFS ACLs to prevent anonymous users from running system utilities like cmd.exe and writing to content directories; and disables WebDAV.
- UrlScan A template-driver filter that intercepts HTTP requests and rejects them if they meet certain criteria

This is a fairly comprehensive list of IIS-specific configuration issues, but there are some omissions. Lockdown does nothing about installing Service Packs and Hotfixes, it does not touch any other aspects of the Windows operating system that may be vulnerable, and it doesn't set up appropriately configured firewall.

Since most of the IIS Lockdown Wizard can be configured manually, we think one of the most compelling features of IIS Lockdown is UrlScan. In fact, UrlScan can be extracted from the IIS Lockdown Installer (iislockd.exe) by running the Installer with the command line:

```
iislockd.exe /q /c /t:\download_files
```

Once extracted, UrlScan can be manually installed on the server(s) that require protection (namely, running iislockd.exe without arguments will automatically install UrlScan from within the IIS).

UrlScan consists of two files, UrlScan.dll and UrlScan.ini, which must be installed in IIS so it can intercept HTTP requests after IIS receives them, and UrlScan.ini is the configuration file that determines what HTTP requests the UrlScan API filter will reject. Rejected requests will be logged to a file called UrlScan.log in the same directory as UrlScan.dll and UrlScan.ini (log files may be named them UrlScan.MMDDYY.log if per-day logging is configured).
