# Other Protocols

HTTP is deceptively simple—it’s amazing how much creative people have gotten out of its basic request/response mechanisms. However, it’s not always the best solution to problems of application development, and still more creative people have wrapped the basic in a diverse array of dynamic functionality.

One simple example is to do with non-ASCII-based content requested by a client. How does a server fulfill a request, if it only knows how to speak ASCII over HTTP? The versatile Multipart Mail Extensions (MIME) is used to transfer binary files over HTTP. MIME is outlined in RFC 2046. This allows a client to request any kind of resource with near assurance that the server will understand what it wants and return the object to the client.

Of course, applications can also call out to any of the other Internet protocols, such as e-mail (SMTP) and file transfer (FTP). Many Web applications rely on embedded link to communicate with clients.

Finally, work is always afraid to add new protocols to the HTTP suite. One of the most significant new additions is Web Distributed Authoring and Versioning (WebDAV). WebDAV is defined in RFC 2518, which describes several mechanisms for authorizing and managing content on remote web servers. Personally, we don’t think this is a good idea, as protocol that involves writing data to a Web server is trouble in the making, we’ll see it time and again in this book.

Nevertheless, WebDAV is backed by Microsoft and already exists in their widely deployed products, so a discussion of its security merits is probably moot at this point.

Despite all the free functionality available with current Web browsers, its the HTTP/HTML functionality is the hacker's best friend. In throughout this book, we will eschew using Web browsers, preferring to perform our tests with tools that make RAW connections. A great deal of information lies underneath the pretty presentation of a Web browser, and in some cases, they surreptitiously reformat some requests that might be used to test Web security (for example, Microsoft's Internet Explorer strips out dot-slashes before sending a request). Now, we can't have that happening during a serious security review, can we?

# The Web Server

The Web server is most simply described as an HTTP daemon (service) that receives requests for resources, performs some basic parsing on the request to ensure the resource exists (among other things), and then hands it off to the Web application logic (see Figure 1-1) for processing. When the logic returns a response, the HTTP daemon returns it to the client.

There are many popular Web server softwares available today. In our consulting work, we see a large amount of Microsoft IIS, the Apache Software Foundation's Apache HTTP Server (commonly called "Apache"), AOL/Netscape's Enterprise Server, and Sun's iPlanet. To get an idea of what the Web is running on its servers at any time, check out the Netcraft service at http://www.netcraft.com.

Although an HTTP server seems like a simple thing, once again must point out that numerous vulnerabilities in Web servers have been uncovered over the years. So many, in fact, you could argue that Web vulnerabilities drove hacking and security to international prominence in the 1990s.

# Web Servers vs. Web Applications

Which brings up the off-blurred distinction between Web servers and Web applications. In fact, many people do not distinguish between the Web server and the applications that run on it. This is a major oversight—we believe that vulnerabilities in either the server or elsewhere in the application are important, and we will continue to make this distinction throughout this book.

While we're at, let's make sure everyone understands the distinction between two classes of vulnerabilities, network and system-level vulnerabilities. Network and system-level vulnerabilities operate below the Web server and Web application. They are problems with the operating system of the Web server, or insecure services running on a system sitting on the same network as the Web server. In each case, exploitation of vulnerabilities at the network or system level can also lead to compromise of a Web server and the Web service on. This is why firewalls were invented—to block access to everything but the Web service so that you don't have to worry so much about intruders attacking these points.

We bring these distinctions so that readers learn to approach security holistically. Wherever a vulnerability exists—be it in the network, system, Web server, or application—there is potential for compromise. Although this book deals primarily with Web applications and a little with Web servers, make sure you don't forget the other holes as well. The other books in the Hacking Exposed series cover network and system vulnerabilities in great detail.

# The Web Application

The core of modern Web site is its server-side logic (although client-side logic embedded in the Web browser still does heavy lifting). This so-called “n-tier” architecture extends what would normally be a previously unsophisticated thing like a HTTP server and turns it into a dynamic engine of functionality that almost passes for a seamless, stateful application that users can interact with in real time.

The concept of “n-tier” is important to an understanding of a Web application. In contrast to the layer presented in Figure 1-1, the Web app layer itself be comprised of many distinct layers.
