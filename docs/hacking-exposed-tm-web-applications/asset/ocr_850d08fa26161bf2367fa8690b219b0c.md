# # Restarting IIS

The next step is to restart IIS, which is critical to successfully installing UrlScan.

> NOTE ISAPI filters like UrlScan are loaded into memory only during IIS startup, every time you make modifications to UrlScan.dll or UrlScan.ini, you must restart IIS.

On IIS 4, you typically need to manually stop and start each IIS service that requires UrlScan protection. Typically, this is the only World Wide web service, or W3SVC, which can be stopped by typing the following at a command prompt:

```
net stop w3svc /Y
```

To start the w3svc, then type:

```
net start w3svc
```

On IIS 5, the iisreset command can be used. Simply type isreset at a command prompt, and all services will be restarted. Here is a simple batch file that gracefully stops IIS services, backs up the W3SVC logs, and starts IIS again:

```
@echo off
isreset /STOP /NOFORCE
if errorlevel == 1 goto EXIT
copy %systemroot\system32\LogFiles\W3SVC1 d:\backup\W3SVC1
isreset /START
:EXIT
```

This script may prove useful if you need to gracefully restart IIS.

# # Adjusting UrlScan Priority

Finally, when the UrlScan filter is loaded, you need to adjust the priority, if necessary. Return to the ISAPI Filters in the IISAdmin tool (the scene depicted in Figure D-8). If UrlScan is not at the top of the list, and does not have a priority of High, you should consider it. UrlScan will intercept all incoming requests before they are passed to any other DLLs. Use the arrow buttons on the left side of this screen to adjust UrlScan's priority until it looks something like Figure D-9.

There are some cases where UrlScan should not be loaded first, depending on what products you may be running on the Web server. To that, the only exception we are aware of occurs if you use FrontPage Server Extensions (FPSE). In this case, you may need to move the UrlScan filter below the FPSE ISAPI filter (fpsexed.dll), and change its priority to Low.
