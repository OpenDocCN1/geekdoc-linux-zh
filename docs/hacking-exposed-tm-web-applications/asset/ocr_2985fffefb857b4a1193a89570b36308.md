If no response is received, the scanner assumes that the port is open. This approach to UDP scanning leads to false positives on Internet-connected networks because ICMP Unreachable messages are typically quenched by routers. A better way to perform UDP scanning is to actually record a valid response from the remote UDP service. however, this requires the scanner to understand how each UDP service works, how to generate a valid request, and how to provide a valid response. This is not too difficult for half dozen or so services we've specified in Table 2-2, but as of this writing, we are not aware of any UDP scanning tools that make this approach except for Foundation's FindScan technology.

# Dealing with Virtual Servers

One issue that can skew the outcome of server discovery is load balancing and virtual servers.

We allied sites to load balancing in Chapter 1, and it is an architecture employed by large Web sites. If multiple servers scan the canonical name will not include data from every server in the farm, but rather only the one that is queued up to respond at the time of the scan. Subsequent scans may be directed to other servers.

This is not necessarily an impediment to Web application security review, as we re only interested in the security of each individual server in the farm. However, a comprehensive review will take this factor into consideration. It only takes one bad apple to poison the whole barrel. One simple way to identify individual load-balanced servers is to first identify the IP address of the canonical name, and then scan a range of IPs around that. For example, you could ping the canonical name like:

```
C:\ping victim.com [192.168.10.15] with 32 bytes of data:
```
