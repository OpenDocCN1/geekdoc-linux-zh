# Hacking Exposed Web Applications

Although DISCO is probably going to be supplanted by the more widely accepted UDDI specification, no doubt developers will implement DISCO for its less complex, lighter-weight approach to publishing Web services. Combined with its ready availability in Microsoft's widely deployed technologies, DISCO or something like it will probably provide a good target for malicious hackers seeking information about Web services.

# SAMPLE WEB SERVICES HACKS

OK, enough background. How do web services fare when under real-world attack? This section will discuss a recent example from our consulting work in which we encountered and assessed a preproduction Web service. It is a classic information-gathering attack that leads to larger compromise, and our goal in discussing it is to illustrate the possibilities that Web services may present to malicious hackers. Web services (.asmx) may cough up DISCO and/or WSDL information by appending special arguments to the request. For example, the following URL would connect to a Web service and render the service's human-readable interface:

```
http://www.victim.com/service.asmx
```

DISCO or WSDL information can be displayed by appending ?disco or ?wsdl the URL as shown below:

```
http://www.victim.com/service.asmx?disco
```

or

```
http://www.victim.com/service.asmx?wsdl
```

Figure 1-4 shows the result of such an attack on a Web service. The data in this example is quite benign (as you might expect from a service that wants to publish information about itself), yet we've seen very bad things in such output—SQL Server credentials, paths to service files and directories, and all of the goodies that Web devs love to stuff into their config files. The WSDL info is much more extensive—as we've discussed, it lists all service endpoints and data types. What could a hacker ask for before beginning malicious input attacks?
