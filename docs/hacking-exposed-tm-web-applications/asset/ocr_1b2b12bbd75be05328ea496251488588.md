This allowed the gateway to do things like cache commonly requested Internet content, thus saving bandwidth, increasing performance, and so on. A gateway that makes requests on behalf of a client system has traditionally been called a proxy. Proxies largely help as advertised, saving bandwidth and decreasing server load, but have at least one side effect: state management or security mechanisms based on client IP address to get all fouled when traversing a proxy, since the source address of the client is always the proxy. How do you tell one client's request from another? Even worse, when implemented in arrays AOL, one client request may come out of one proxy, and a second request may come out of another. Home point: don't rely on client-side information when designing Web application state management or security measures.

# Load Balancers

As you imagine, someone came up with a similar idea for the server side of the Web equation. Load balancers perform like reverse proxies, managing the incoming load of client requests and distributing them across a farm of identically configured servers. The client neither knows nor cares if one fulfills its request or another. This greatly improves the scalability of Web architectures, which a theoretically unlimited number of Web servers can be employed to handle ever-increasing numbers of client requests.

Load balancing algorithms can be categorized into static (where requests are routed in a predetermined fashion such as round-robin) or dynamic (where requests are shunted to servers based on some variable factor like connections or fastest link). The load balancer itself typically takes on a canonical name like www.company.com, and then routes to virtual servers, which may or not be Internet-accessible addresses. Load balancing implementations we commonly see in our work include Cisco Local Director and F5's Big-IP. Another implementation is the Network Load Balancer (NLB) scheme from Microsoft. It is based on a physical layer broadcasting rather than request routing. In some ways, it's sort of Ethernet's collision detection avoidance architecture. It works like this: An incoming request is broadcast to the entire farm of Web servers. From an internal mechanism, only one of the servers will respond. The rest of the client's requests are not routed to there, like other load balancing schemes. Microsoft's Application Center product uses this approach, and we think it's elegant even when we haven't seen it deployed much. Scalability is greatly enhanced because the balancing device doesn't have to route packets; it only broadcasts them.

Whatever the technology employed, load balancers tend to make life harder for hackers. Because a given request always get sent to the same server, scanning techniques can yield unpredictable results. We'll discuss this in more detail in Chapter 2.
