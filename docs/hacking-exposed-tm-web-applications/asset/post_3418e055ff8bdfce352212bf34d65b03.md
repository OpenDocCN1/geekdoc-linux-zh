In step 4, following successful login, Passport's login servers set a series of cookies on the client. The important cookie is the MSPAuth cookie, which is the authentication ticket.

```
HTTP/1.1 200 OK
Set-Cookie: MSPAuth=Thu, 01 Jan 1970 00:00:00 GMT;domain=.passport.com;path=/
Set-Cookie: MSPProf=Thu, 01 Jan 1970 00:00:00 GMT;domain=.passport.com;path=/
```

Finally, in step 5, the client gets back to the original resource on the Partner site (which Passport's login servers remember from the original query string):

```
GET /my.aspx HTTP/1.0
Host: my.msn.com
Cookie: MSPAuth
```

Although this seems like a few round trips, it happens quickly and transparently to the user, depending on the speed of the Internet connection.

To sign out, the user clicks on Passport “Sign Out”, and is again redirected to login.passport.com, which then deletes the cookies (sets them to NULL) and returns the client to the Partner site:

## Attacks Against Passport

There have been a few attacks against Passport since its introduction in 1999. In 2000, David P. Kuhn and Ariel D. Rubin published a paper entitled *Risks of the Passport Single Sign-On Protocol* that described a series of attacks generic to basic features like SSL, Netscape browser cookies, Javascript, and DNS sniffing. They also pointed out that anyone can spoof a Passport page and harvest member credentials (the “fake” attack), and speculated that Partner site keys were transmitted over the Internet in a vulnerable fashion. The entire paper known issues with Internet authentication services and demonstrates real research into problems with Passport information.

In August 2001, Chris Mitchell published a paper on a vulnerability in Internet browsers prior to version 5.5 that allowed malicious sites or e-mail messages to read cookies on client machines. He also noted that if a Passport member opted to save his or her Passport cookies locally, an attacker that leveraged this vulnerability could be used to steal Passport cookies and masquerade as the victim. The IE hole has subsequently been fixed, and Chris rightly comments that users do not select the “Sign me in automatically” option when using Passport (which sets a persistent cookie on the user’s machine).

Later in 2001, security researcher Marc Spectre posted an analysis called “Microsoft Passport Trouble”, in which he describes an exploit that would allow him to steal authentication cookies using script injection on pages that use Passport authentication. Microsoft has since fixed the problem, but this attack is an excellent example of how to steal authentication cookies.

The common theme of all of these attacks suggests that one of the greatest dangers in using authentication is replay attacks using authentication cookies from unsuspecting users’ computers. Of course, assuming an attacker could steal authentication tickets would probably defeat most authentication systems out of the gate.

Like any other authentication system, Passport is also potentially vulnerable to password guessing attacks (the minimum password length is six characters, with no requirements for different case, numbers, or special characters). Although there is no permanent account lockout feature, after a certain number of failed login attempts, an account will be temporarily prevented from logging in (this lasts “a few moments” according to the error message). This is designed to add significant time to password guessing attacks. Attackers may attempt to reset their passwords during a block, but must answer a “secret question” set by the Passport account owner during registration.

Despite these issues, Passport is a strong option for Web sites that don’t mind if else owns their customers' authentication credentials.

## ATTACKING WEB AUTHENTICATION

So far, we’ve described the major authentication mechanisms in the Internet. How are such mechanisms attacked? In this section, we discuss techniques that can be used to exploit common vulnerabilities in Web authentication and conclude with recommendations on how to avoid these pitfalls.

A quick note before we begin—that authentication exists for an application suggests that the application developer has created some security infrastructure to prevent the casual hacker from easily accessing other users' data. Hence, attacking Web authentication is not going to be a walk in the park. As always, however, it’s the implementation that brings down the house, as we will see next.

## Password Guessing

Although not the sexiest of attacks, password guessing is the most effective technique to defeat Web authentication. Assuming there isn’t some flaw in the selection of authentication protocol or its implementation, the most vulnerable aspect of most authentication systems is user password selection.

Password guessing can be carried out manually or via automated means. Manual password guessing is tedious, but when human intuition frequently beats automated tools, especially when customized error pages are used in response to failed forms-based login attempts. When performing password guessing, our favorite choices are shown in Table 5-3.

| Attack Type | Description |
| :--- | :--- |
| Dictionary attack | Using a pre-defined list of common passwords or words. |
| Brute force | Trying every possible combination of characters. |
| Credential stuffing | Using leaked usernames and passwords from other sites. |
| Social engineering | Tricking the user into giving up their password. |

Password guessing can be performed against almost all types of Web authentication covered in this chapter. We will discuss two that attack Basic and Forms-based auth presents, but tools to attack Digest and NTLM are also feasible.
