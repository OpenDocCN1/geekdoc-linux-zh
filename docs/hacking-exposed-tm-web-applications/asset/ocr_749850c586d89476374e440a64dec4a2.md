# Similarities to Web Application Security

Web services are in many ways like a discrete Web application. They are comprised of scripts, executables, and configuration files that are housed in a virtual directory on a Web server. Thus, as you might expect, many of the vulnerabilities we've discussed throughout this book also apply to Web services.

One of the first and most obvious security issues becomes readily apparent with a cursory glance at Figure 10-1: Web services must be accessible across organizational boundaries, and in particular, the firewall. Furthermore, they expose business contracts to a wide audience via protocols as WSDL, DISCO, and UDDL. So, like Web applications, traditional TCP/IP security leaves firewalls and screening routers little security for Web services.

Another apparently apparent issue is the reliance on lower-layer services like HTTP servers to support the basic infrastructure of Web services. As we saw in Chapter 3, Web servers have a long and colorful record of security vulnerabilities, and Web applications that are built on overly configured or unpatched servers are merely moments away from being hacked. With Web applications, some of the most serious exposures will come from inappropriate information disclosure or poor authorization within Web services. Web services are just as vulnerable to inappropriate information disclosure as Web applications are to revelation of their respective script and authorization configuration files. Path information disclosed in these attacks may also lead to the dreaded directory traversal attack, which is ultimately a problem with authorization across the service or application.

Finally, our description of the language franca of Web services, SOAP, illustrates the applicability of Web application techniques to Web services hacking. For the most part, you can hack Web services in the same way you hack Web applications—following the methodology outlined in this book. One key difference when using SOAP is that communication is implemented using XML payloads in HTTP POST. But this is only a minor barrier—once you get the format down, attackers can change the input in the many ways we've illustrated throughout this book. Even—Web services are designed to publish information about each of their endpoints and data types they accept through WSDL. Talk about wearing a target on your back.
