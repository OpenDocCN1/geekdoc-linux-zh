## BASIC URLSCAN DEPLOYMENT

This section is for readers who want to spend as little brainpower as possible deploying UrlScan. Of course, it glosses over a number of important details about the tool, and may not result in the optimal results for your Web application or service. It also requires that you use Microsoft’s IISLockdown tool, which may make changes on your server. These steps will get you UrlScan up and running quickly, with minimal investment of gray matter. If you want to have greater control over the installation, skip to the section "Advanced UrlScan Deployment" in this chapter.

The easiest way to deploy UrlScan is to simply run the IISLockdown wizard and follow the prompts. The first several options deal with configuration of local Internet services, and don't pertain to UrlScan. However, we'll walk you through these because you'll need to understand them in order to get to the point where UrlScan can be installed.

> If you are not sure IISLockdown settings are appropriate for you, don't you rerun the wizard and it will give you the option to undo all changes (except services that are removed!). This will also disable (but not uninstall) UrlScan.

The first prompt in the IISLockdown wizard is to select a server template. Templates are simply a way to allow you to tailor the security settings of the system to its role. Figure D-2 shows the most secure template available, "Static Web server", but it configures the server quite restrictively (for example, ASP scripts cannot be run by a server configured with this template). If you are only serving static HTML files, this is the way to go. Otherwise, you will need to select the template from the list that matches your server’s role. Since most of the templates are designed around Microsoft products, just pick the product you are using. However, be aware that these other options do not disable additional features that are shut off by the Static Web Server template, and may result in security exposures. This is the classic trade-off of security versus functionality.

We recommend you select the "View templates" option on this screen, as shown in Figure D-2. This will present you with a list of services that will be enabled or disabled in the next screen in the IISLockdown wizard, which is shown in Figure D-3.

This shows the services that IISLockdown will enable and disable, according to the template that you have selected in the previous selection. It's probably safe to accept these configurations by clicking "Next", but we wanted to highlight the option to "Remove unselected selections" on this screen. We think it's a good idea to select this option to ensure that these services can never be enabled without reinstallation, but be aware that any service uninstalled via this screen cannot be rolled back using the IISLockdown tool. Every other setting configured by IISLockdown can be rolled back, but not uninstalled services—you'll have to manually reinstall them using the appropriate installation media.

The next step in the IISLockdown wizard specifies which script maps should be disabled. We discussed the importance of script mappings in Chapter 3—basically, they provide a link between a file extension and a set of code on the server, so that when clients request a file with that extension, they can run the linked code. These code modules have traditionally been the source of many security vulnerabilities, so disabling script maps prevents attackers from simply requesting a file with a certain extension in order to exploit a vulnerability. We advise following the recommended script mappings shown on this screen, they are based on the server template selected in the first step. You may optionally disable more script mappings here if you know what you're doing. Figure D-4 shows the script mappings screen from the IISLockdown wizard with all mappings, which is the default with the Static Web Server template.

IISLockdown then presents a list of all the options that have been selected, and asks once more if you want to complete the wizard. If you select “Next,” the wizard will implement all of the configurations you’ve selected, including the installation of UrlScan. By default, UrlScan is installed into the directory %windir\system32\netsrv\urlscan, but you should rarely ever have to go here after you have configured the first time.

At this point, your server is configured according to the settings using IISLockdown, and UrlScan is installed and enabled using those same settings (there is some degree of redundancy, which makes for good security “defense-in-depth”). You could leave well enough alone at this point, but we think you should take two additional steps to ensure that your server is protected as well as it should. First, you should specify an alternate server name in the UrlScan configuration file, and then you should update UrlScan to the most recent version. We’ll describe those steps next.

To specify an alternate server name, open the file %windir%system32\inetsrv\urlscan\urlscan.ini in a text editor like Notepad, and look for the line that:

AlternateServerName=

After the sign on this line, enter whatever server name you desire. Here's something that will confuse the average attacker or Internet worm:

AlternateServerName=Webserver 1.0

This changes the banner presented by your web server to "Webserver 1.0," which prevents attackers from easily discovering what type of server you are running using the banner-grabbing techniques outlined in Chapter 2. Once you make this change, you will need to restart the IIS service. You can do this manually, or simply go on to the next step, updating URLScan, which restarts IIS for you. If you leave this setting at its default (i.e., not defined), and the RemoveServerHeader setting equals 1 in the [Options] section of UrlScan.ini, IIS will return its true banner for each request.
