# Transport: HTTP

As we mentioned, Web applications are largely defined by their use of HTTP as the medium of communication between client and server. Stateless, ASCII-based protocol defined in RFC 1945 (version 1.0 is a relatively version 1.1 is covered in RFC 2616). It typically operates over TCP port 80, but can exist on any unused port. Each of its characteristics—simplicity, statelessness, text base, TCP operation—is what we are briefly since is so central to the (in)security of the protocol. The discussion below is a very broad overview; we advise readers to consult the RFCs for more exacting detail.

HTTP’s simplicity derives from its limited set of basic capabilities, request and response. HTTP defines a mechanism to request a resource, and the server returns that if it is able. Resources can range from static text pages to dynamic video content. Here is a simple example of an HTTP GET request and a server’s HTTP 200 OK response, demonstrated using the netcat tool. First, the client (in this case, netcat) connects to the server on TCP 80. Then, a simple request for the URI /test.html is made, followed by two carriage returns. The server responds with a code indicating the response was successfully retrieved, and forwards the server’s data to the client.

HTTP is thus like a hacker’s—there is no need to understand cryptic syntax in order to generate requests, and likewise decipher the context of requests. Practically anyone can become a fairly proficient hacker with very little effort.

Furthermore, HTTP is stateless—no concept of session is maintained by the protocol itself. If you request a resource and receive a valid response, then another, the server regards this as a wholly separate unique request. It does not maintain anything like a session or otherwise attempt to maintain the integrity of a link with the client. This also comes handy for hackers, as there is no need to plan multistage attacks to emulate maintenance mechanisms—a single request can bring a Web server or application to its knees.

HTTP is also an ASCII text-based protocol. This works which anyone can read. There is no need to understand binary encoding or translators—everything a hacker needs to know is available within each request and response, in cleartext.

Finally, HTTP operates over a well-known TCP port. Although it can be implemented on any other port, all web browsers automatically attempt to connect to TCP 80, first so every Web server lists on that port as well (see our discussion of SSL/TLS in the next section for one above this). This has great ramifications for the vast majority of networks that sit behind those massive devices called firewalls that are supposed to protect us from all of the outside world. Firewalls and other security devices are rendered defenseless against Web hacking when configured to allow TCP 80 through one or more servers. And what do you guess is the most common firewall configuration on the Internet today? Allowing TCP 80, of course—if you want a functional Web site, you’ve gotta make it accessible.

Of course, we’re oversimplifying a great deal here. There are several exceptions and qualifications that one could make about the previous previous discussion of HTTP.

# SSL/TLS

One of the most obvious exceptions is that many Web applications today tunnel HTTP over another protocol called Secure Socket Layer (SSL). SSL can provide for transport-layer encryption, that an intermediary between client and server can't read cleartext HTTP right off the server. Other than "wrapping" HTTP in a protective shell, SSL does not extend or substantially alter the basic HTTP request-response mechanism. SSL does nothing for the overall security of a Web application other to make it more difficult to eavesdrop on the traffic between client and server. An optional feature of the SSL protocol called client-side certificates is implemented, the additional benefit of mutual authentication can be realized(the client's certificate must be signed by an authority trusted the server). However, if any sites on the Internet do not today. 
The latest version of SSL is called Transport Layer Security (TLS). SSL/TLS typically operates via TCP port 443. That's all we're going to say about SSL/TLS for now, but it will come up in further discussions throughout this book.

# State Management: Cookies

We dvelte a bit on the fact that HTTP is stateless, but a number of mechanisms have been conceived to make it behave like a stateful protocol. The most used mechanism today uses data called cookies that can be exchanged as part of the HTTP request/response dialogue to the client and application they are actually connected via virtual circuit (this mechanism is described more fully in RFC 2965). Cookies are best thought of as tokens that servers hold to a client allowing the access to the Web site as they present the token for each request. They can be stored in memory or permanently written to disk. Cookies are not perfect (especially implemented poorly) and there are issues relating to security and privacy associated with them, but no other mechanism has become more accepted.

# Authentication

On the heels of stateless comes the concept of authentication. What's the use of keeping track of state if you don't even know who's using your application? HTTP can embed several types of authentication protocols. They include

- Basic Cleartext username/password, Base-64 encoded (trivially decoded).
- Digest Like Basic, but passwords are scrambled so that the cleartext version cannot be derived.
- Form-based Custom form is used to input username/password (or other credentials) and is processed using custom logic on the back end. Typically uses a cookie to maintain "logged on" state.
- NTLM Microsoft's proprietary authentication protocol, implemented within HTTP request/response headers.
