# File System Traversal Countermeasures

A number of countermeasures can mitigate directory traversal vulnerabilities in IIS.

# Keep up with Security Patches

**Keep up with Security Patches** This sort of fundamental error in basic IIS functionality is best addressed with a patch. There is really no other way to fix it (although we will discuss several steps that you can take to mitigate the risk shortly). The fixes for the Unicode and double decode patches can be found in Microsoft Security Bulletins MS008-086 and MS011-026. Again, amass itself is not included in SP2.

> MS011-026 also changes the InProcess|sap|Apps Metabase setting so privilege escalation Trojan DLLs that can revertToSelf can't be used to escalate privileges on IIS 5.

As always, we recommend the use of an automated tool like the Network Hotfix Checking Tool (hfetch) to help you keep up to date on IIS patches.
In addition to the patch, IIS administrators can engage in other best practices to protect themselves proactively with Unicode, double decode, and future vulnerabilities like them. The following set of recommendations is adapted from Microsoft's recommendations in MS00-078 and amplified with our own approach.

**Install Your Web Folders on a Drive Other than the System Drive** As you have seen, directory traversal exploits like Unicode are restricted by URL syntax that currently hasn't implemented the ability to jump across volumes. Thus, by moving the IIS Web root to a volume with powerful tools like cmd.exe, such exploits aren't feasible. On IIS, the

physical location of the Web root is controlled by the Internet Services Manager (iis.mssc) by selecting Properties of the Default Web Site, choosing the Home Directory tab, and changing the Local Path setting.

Make sure when you copy your Web roots over the new drive that you use a tool like Robocopy from the Windows 2000 Resource Kit, which preserves the integrity of NTFS ACLs. Otherwise, the ACLs will be set to the destination, that is, Everyone: Full! The Robocopy /SEC switch can help you prevent this.

**Use UrlScan to Normalize Requests with URL Encoding** As noted in our previous discussion of UrlScan, the UrlScan.ini configuration file can be configured to normalize HTTP requests containing suspicious encoding before sending them to IIS. Setting the following values in UrlScan.ini achieves this:

- * NormalizeUrlBeforeScan=1 ; 1, canonicalize URL for processing
- * VerifyNormalization=1 ; 1, canonicalize URL twice and reject request
- if if a change occurs

Remember to restart IIS if you make changes to UrlScan.ini to load the changes.

**Always Use NTFS for Web Volumes and Set ACLs Conservatively!** With FAT and FAT32 file systems, file- and directory-level access control is impossible, and the IUSR account will carte blanche to read and upload files. When configuring access control on Web-accessible NTFS directories, use the least-privilege principle. IIS 5 also provides the Permissions Wizard that walks you through a scenario-based process of setting ACLs. The Permissions Wizard is accessible by right-clicking the appropriate virtual directory in the IIS Admin console.

**Move, Rename, Delete, or Restrict Any Powerful Utilities** Eric Schultze and David LeBlanc of Microsoft Corp. Recommend at setting the NTFS ACLs on cmd.exe and other powerful executables to Administrator and SYSTEM:Full Control only. We have publicly demonstrated that this simple trick stops Object-type sheigans cold because IUSR no longer has permissions to access cmd.exe. Schultze and LeBlanc recommend using the built-in cacs tool to set these permissions. Let's walk through an example of how cacs might be used to set permissions on executable files in the system directory. Because many executable files are in the system folder, if you use a simpler example of files sitting in a subfolder called test1 using cacs in display-only mode, we can see the existing permissions on our files are pretty clear

```
C:\cacs /t
C:\test1 (OI) (CI)
C:\test1.exe Everyone:Full
C:\test1.txt Everyone:Full
C:\test2 (OI) (CI)
C:\test1\test2.exe Everyone:Full
```

Let’s say you want to change permissions on all executable files in test1 and all subdirectories to System:Full. Here’s the command using cacs:

```
C:\cacs test1*.exe /T System:Full
Are you sure (Y/N)?
processed file: C:\test1.exe
processed file: C:\test1\test2.exe
```

Now run cacs to confirm your results. The .txt files in all subdirectories have the original permissions, but the executable files are now appropriately:

```
C:\cacs test1 /T
C:\test1 (OI) (CI)
C:\test1.exe NT AUTHORITY\SYSTEM
BUILTIN\Administrators:Full
C:\test1.txt Everyone:Full
C:\test1\test2 (OI) (CI)
C:\test1\test2.exe NT AUTHORITY\SYSTEM
BUILTIN\Administrators:Full
C:\test1\test2.txt Everyone:Full
```

Applying this to a typical server, a good idea would be to set ACLs on all executables in %systemroot% directory to System:Full, Administrators:Full, like:

```
C:\cacs %systemroot%*.exe /T System:Full Administrators:Full
```

This blocks unmodified from using these executables and helps prevent exploits like that rely on unprivileged access to these programs. Of course, such executables may also be moved, renamed, or deleted. This puts them out of reach of hackers with ease.

> NOTE The IISlock tool automates assigning ACLs to system utilities. See the previous section on ISAPI flaws.

Remove the Executive and Guests from Write and Execute ACLs on the Server IUSR and IWAM members of these groups. Be extra sure the IUSR and IWAM accounts don't have write access to any files or directories on your system—you’ve seen even a single writable directory can lead to!

**Know What It Looks Like You Have Been Under Attack** As always, treat incident response as seriously as prevention—especially with fragile servers. To identify your servers have been the victim of a directory traversal attack, remember the four P’s: ports, processes, file system and Registry footprint, and por over the logs.

Using the netstat utility on a victimized Web server is great to identify any strange connections to high ports on the Web server. As we have seen, these are likely connections to netcat shells. Outbound connections are much harder to differentiate from legitimate connections with Web clients.

Hosts of exploits based on the Unicode technique are circulating on the Internet. We already discussed files like sensepost.exe, uncodader.asp, upload.asp, load.inc, and cmddasp.asp play central roles in exploiting the vulnerability. Although trivially renamed, at least you’ll keep the kids kiddies at bay. Especially if you see some exploits files with names like root.exe (a renamed command), e.asp, dl.exe, regula.exe, regit.exe, restsec.exe, makeini.exe, newgina.dll, firedaemon.exe, mtask.exe, sud.exe, and sud.bak.

Interestingly, a clear difference exists between the existence of the Unicode and double decode exploits in the IIS logs. Double decode strings are actually entered into the logs using %255c:

```
http://victim.com/scripts/../%25c..%255c/system32/cmd.exe?c+dir+c:\
```

appears in the IIS logs:
21:48:03 10.0.2.18 /scripts/../%5c..%5cwin/system32/cmd.exe 200

This enables one to search more easily on the %5c string to identify attempts to abuse this vulnerability. Remember, there are many possible Unicode and double decode strings like %c0%af and %255c—don’t use one or two to grep your logs.
