Table 6-3 shows the result of the manual tests. We skipped a few numbers for each power of two (4, 8, 16, 32) returns a different menu. This makes sense in a way. The application could be using an 8-bit bitmask to pull a particular menu. For example, the menu appears in binary as 00000100 and the delete user appears as 01000000. A bitmask is merely one method of referencing data. There are two points to this example. One, examine all of an application's parameters in order to test the full measure of its functionality. Two, look for trends within the application. A trend being a naming convention or a progression as we've shown here.

There's a final attack that we haven't tried yet—enumerating session management is described in detail in Chapter 7, but we should mention that the previous scripts can be easily modified to enumerate valid sessions.

Before we finish talking about curl, let's explain why this attack worked:

+   Poor session handling The attack triggered the session cookie value and the r value in the URL; the application did not correlate either with the user ID number. In other words, once we were authenticated to the application, all we needed to remain authenticated with the session and valid. The uid and userID values were used to check authorization, whether or not the account could access a particular profile. By not tying the authorization tokens (uid, userID) to the authentication tokens (sess, r), we were able to impersonate other users and gain privileged access. If the application had the uid value matched the session value from the session was first established, then the application would have stopped the attack because the impersonation attempted the wrong sess for the corresponding uid.

+   No forced session timeout The application did not expire the session token (sessid) after six hours. This is a tricky point to bring up, because technically the session was active the entire time as intended 100,000 users. However, applications can still enforce hard limits on a session, such as one hour, and request the user to reauthenticate. This would not have stopped the attack, but it would have been mitigated. This would protect users in shared environments such as university computer labs from someone taking their session.

# Countermeasures

The methods to attack authorization derivation from input validation, SQL injection, or poor session management. As such, applying countermeasures to those potential vulnerabilities is the fortunate side effect of blocking authorization attacks as well.
