# 202 Hacking Exposed Web Applications

Input validation attacks attempt to submit data that the application does not receive. Normally, an application will perform some type of sanity check on user input. This check is to ensure that the data is useful. More important checks are necessary to prevent the data from crashing the server. Less stringent checks are required if the data is only limited to a specific length.

The credit card field is for an application's shopping cart. First of all, the credit card number will only consist of digits. Furthermore, most credit card numbers are only 16 digits long, but few will be less. So, the first validation routine will be a length check. Does the input contain 14 to 16 characters? The second check will be for content. Does the input contain anything that is not a number? We could add another check to the system determines whether the data represents a reasonable credit card number. The value "0000111222" is definitely not a credit number, but what about "44357861269388? A simple function can determine if a 16-character value passes the checksum of valid credit card numbers. Publishers available routines determine the validity and type of a 15-character credit card number that starts with a 3 and where the second digit is a 4 or a 7.

Data validation can be complex. The application programmers have to exercise a little foresight to figure out all the possible values that a user might enter into a form field. We mentioned simple checks for credit card validation. These tests can be programmed in JavaScript, but what about over SSL?

# EXPECTING THE UNEXPECTED

One of the biggest failures in "secure" input validation is the routines in JavaScript and placing them in the browser. At first, it may seem desirable to use any client-side scripting language for the validation routine. They are simple and are widely supported between Web browsers (although are individual quirks). Most importantly, they move a lot of processing from the Web server to the end-user's system. This is really a Pyrrhic victory for the application. The Web browser is an untrusted, uncontrollable environment. A user can modify any information from going and going to another Web server—including validation routines. It is much cheaper to buy the hardware for additional server-side processing than to wait for a malicious user to compromise the application with a simple "%0a".

The types of input validation attacks usually fall into one of three categories:

+   **Unexpected Input** This includes formatting characters, cross-site scripting attacks that collect users' passwords, or any character that causes the application to generate informational errors.

+   **Command Execution Characters** These may be specific to the operating system, such as inserting a semicolon to run arbitrary commands on a UNIX Web server. Or, they could attack the application by inserting SQL, JavaScript, or ASP code into arbitrary files.
