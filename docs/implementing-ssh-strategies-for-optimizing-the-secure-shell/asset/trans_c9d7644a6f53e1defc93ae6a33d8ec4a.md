

# 使用 SSH Communications' SSH 服务器进行文件共享

与 OpenSSH 一样，在 SSH 中，为了以补充 SSH 的方式提供 SFTP 子系统的使用，必须在操作系统上创建有效账户。这是因为 SSH Communications' SSH 服务器也使用操作系统账户，而不是其专用的 SSH 账户。既然情况如此，在操作系统上拥有账户意味着该账户拥有操作系统上所有文件的权限，这些权限由 NTFS 权限允许，例如 \winnt、\winnt\system32 和 \winnt\repair。如果 SFTP 服务器的目的仅限于文件共享，所有 SSH 账户仍然会对操作系统的其他部分拥有权限，因为它们是操作系统账户。

在文件服务器环境中，您可能希望用户能够访问一个根文件夹用于整个组织的通用文件共享，但不希望他们接触到操作系统的目录或用于 SFTP 访问的整个目录结构。例如，您可能希望用户能够下载指定目录（如 d:\share）中的文件，但不希望所有人都能下载 \winnt\repair\sam 的副本。在这种情况下，应该使用 SSH Communications' SSH 服务器的 SFTP 访问控制功能。为了让系统上的所有账户仅能访问 d:\share 文件夹（这可能是公司文件服务器），请完成以下步骤：

- 1. 启动 \h Programs \h SSH Secure Shell Server \h Configuration。
- 2. 高亮 SFTP Server 部分。
- 3. 在 Accessible directories 选项中，选择 New (insert) 图标。
- 4. 输入 CorpFileServer=D:\share（语法为 虚拟目录=实际目录）。
- 5. 选择 Apply。

现在，操作系统或域中的所有账户都可以对 d:\share 目录进行 SFTP 访问。除了列出的虚拟目录外，所有账户将无法访问操作系统的其他任何部分。此外，除了虚拟目录外，用户的家庭目录也可以被访问，在 User home directory 文本框中由 %D 变量列出。在这个例子中，除了公司文件服务器目录外，用户的家庭目录也是可以访问的，如图 8.10 所示。

现在，尽管拥有 NTFS 权限，所有账户仅能通过 SFTP 访问 d:\share。当使用 SSH 或 SFTP 子系统时，SSH Communications' SSH 服务器的访问控制列表会覆盖 SSH 服务器上的 NTFS 权限。除了普通用户访问外，您可能希望允许管理员账户或等效的特权用户通过 SFTP 获得更多访问权限。为了在限制一般 SFTP 用户仅能访问指定虚拟目录的同时，赋予特权用户更多访问权限，请完成以下步骤：

- 1. 高亮 SFTP server 下的 Power Users 部分。
- 2. 选择 Insert 图标以添加目录。
- 3. 输入 C:=C: 和 D:=D:
- 4. 选择 Apply。
- 5. 在 Power Users 文本框中，输入 administrator（或您希望授予进一步访问权限的任何其他账户）。
- 6. 选择 Apply。

现在，管理员账户对 SSH 服务器拥有完整的 SFTP 访问权限，而普通用户仍被限制在 d:\share 目录中，如图 8.11 所示。

与 VShell 不同，SSH Communications' SSH 服务器不提供针对 SFTP 子系统的这种特定访问权限。例如，如果您希望允许所有用户仅访问 SFTP 子系统而没有 Shell 访问权限，在 SSH Communications' SSH 服务器版本 3.2.3 中没有明显的方法来实现这一点。虽然您可以通过 SSH 服务器允许或拒绝用户账户或主机，但这是一种全有或全无的值，没有诸如“仅限 SFTP”等特定选项。这使得 SSH Communications' SFTP 子系统比 OpenSSH 稍好，但提供的控制能力不如 VShell。例如，使用 SSH Communications' SSH 服务器，可以将操作系统的某些目录暴露给 SFTP 用户，从而限制对敏感目录（如 winnt\system32）的访问。此外，高级特权用户可以比一般账户拥有更多访问权限，授予更高级别的目录访问权限。然而，在企业文件服务器模型中，对 SSH 服务器的命令行或端口转发访问是极不受欢迎的，也是一种安全威胁。在 SSH Communications' SSH 服务器的默认安装中，没有简单的方法将某些用户限制为仅使用 SFTP，同时允许其他用户访问 SFTP 和终端会话。

SSH Communications' SSH 服务器提供了使用 SFTP 将操作系统账户限制在特定目录的能力，而不需要 NTFS 权限。但它不提供对命令行或端口转发访问的其他限制。因此，虽然它可能仍然是 SFTP 的好解决方案，但可能不是文件服务器的最佳选择。然而，它是所有用户或企业文件服务器进行通用文件共享的非常出色的解决方案。有关安全文件服务器的更多信息，请参阅第 10 章。

## 使用 SSH Communications' SSH 服务器授权用户

在所有 SSH Communications' SSH 服务器安装中，除非明确拒绝，否则操作系统上的所有用户都被允许登录该服务。使用 SSH Communications' SSH 服务器，尽管账户在系统中存在，但可以允许特定账户登录或简单地拒绝它们，如我们上一个例子所示。这使得 SSH Communications' SSH 服务器架构能够将拥有 SSH/SFTP 访问权限的用户限制在特定账户列表中。此列表可以包含所有账户（这是默认值），或者账户的子集。例如，如果有 500 个账户可以访问运行 SSH 的机器（可能是通过使用域架构），但其中只有 88 个账户需要访问操作系统本身，SSH Communications' SSH 服务器可以通过指定授权的登录账户名称和/或账户变量来允许或拒绝 SSH/SFTP 访问。如果 SFTP 子系统的目的是允许工程部所有用户访问、上传和下载文件到操作系统，将 'Engineering' 组添加为唯一可以使用 SSH 或 SFTP 的组是一个相对简单的过程。此外，如果工程账户仅需访问 d:\share 目录，SSH Communications' SSH 服务器是一个强有力的替代方案。例如，假设工程部需要传输文件，如编译的二进制文件、源代码或配置文件到 d:\share 目录。如果他们使用 SSH 进行安全终端访问，而他们使用 SMB 或 FTP 进行文件传输将是事倍功半的。他们从加密的 Ssh 连接中获得的安全性会被 SMB 或 FTP 会话的不安全性所抵消。在这种情况下，SSH Communications' SSH 服务器的 SFTP 子系统是 SMB 和 FTP 的绝佳替代品。

## 安全聊天

聊天在计算机网络环境中的应用正变得越来越流行。虽然聊天最初用于与邻居进行办公室八卦，但现在它被用于在员工之间传播合法的公司信息。通过让员工能够以轻松、简单且最重要的快捷方式相互协作，聊天提供了巨大的灵活性，从而完成更多工作。
