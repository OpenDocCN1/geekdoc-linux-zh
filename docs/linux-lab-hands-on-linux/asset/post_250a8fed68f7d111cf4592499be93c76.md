### Compilation and Installation

Do not change the default sound configuration; the sndconfig command expects all modules to be present when it runs.

Create subdirectory configuration files: Propagate the configuration defined in the .config file and the top level Makefile to subdirectory configuration files with make dep.

- 6. `make dep`

Compile the Kernel: Linux kernels are generally loaded from gzip-compressed images, one type of which is built with make bzImage. After compilation, the compressed image can be found at `/usr/src/linux-2.6.26.x/arch/i386/boot/bzImage`.

- 7. `make bzImage`

Compile the Kernel Modules: Kernel modules, although compiled from the same source files as the base kernel, are compiled with a separate make invocation. Generally, the vast majority of the kernel exists as kernel modules, and this can be a very lengthy step. During long compilations, `/usr/src/linux-2.6.26.x/Documentation` is used.

- 8. `make modules`

Install the kernel: Although there are no restrictions on the name and location of the kernel, Red Hat suggests installing it into the `/boot` partition.

- 9. `cp /usr/src/linux-2.6.26.x/arch/i386/boot/bzImage /boot/vmlinuz-2.6.26.x-22exmp`

Install the kernel Modules: Modules are installed by the modules_install make invocation into the `/lib/modules/version` directory.

- 10. `make modules_install`

### Initial Ramdisks

Sometimes it is desirable to have certain kernel components as modules, even if they are required at boot time. The most common example is modular SCSI drivers. Because the kernel needs to load the modules before a file system is present, they are stored in a ram disk image, called an initrd. The kernel can then load the modules from the ram disk at boot time. *mkinitrd* examines the kernel’s module library intelligently, selects any modules that might be needed at boot time (usually SCSI drivers or software RAID modules), creates a ramdisk image, and packs the modules into the ram disk. The *initrd* image should then be stored somewhere accessible at boot time, namely, the `/boot` directory.

- 11. `mkinitrd /boot/initrd-2.6.26.x-22exmp.img 2.6.26.x-22exmp`

**System Map**: A symbol table for the various kernel procedures is created when the kernel is compiled, and located in the file `/usr/src/linux-2.6.26.x/System.map`. A copy of this table is needed to interpret the debugging information to debug a kernel during a kernel panic, and should be stored along with the kernel.

- 12. `cp /usr/src/linux-2.6.26.x/System.map /boot/System.map-2.6.26.x-22exmp`

**Configuration file (optional)**: Keeping a copy of the configuration file used to compile a kernel can be useful in keeping track of which capabilities were enabled for which kernels.

- 13. `cp /usr/src/linux-2.6.26.x/.config /boot/config-2.6.26.x-22exmp`

### Patching the Kernel

If you have already downloaded the main source code tree, you can save both bandwidth and time by downloading and applying patches. Patches contain only changes to the underlying files from one kernel version to the next. For example, if you downloaded the 2.6.26.8 kernel source code tree, you do not need to download the 2.6.26.9 source code; only the patch, which is named, in this case, `patch-2.6.26.9.tar.bz2`, should be downloaded. Alternatively, if you have the source code for version 2.6.26.5, you need to download four patches (`patch-2.6.26.6.tar.bz2`, `patch-2.6.26.7.tar.bz2`, `patch-2.6.26.8.tar.bz2`, `patch-2.6.26.9.tar.bz2`) and apply them in sequential order. The following procedure illustrates the process:

```bash
$ bunzip2 -c patch-2.6.26.NN.bz2 | patch -p0
```

Replace NN with the patch number of each patch you want to apply. In terms of the example used in this chapter, because I downloaded the full 2.6.26.8 source code tree, I apply the 2.6.26.9 patch:

```bash
$ bunzip2 -c patch-2.6.26.9.bz2 | patch -p0
patching file linux/CREDITS
patching file linux/Documentation/Configure.help
patching file linux/Documentation/DMA.txt
patching file linux/Documentation/SubmittingDrivers
...
patching file linux/net/ipv4/af_inet.c
patching file linux/net/netlink/netlink.c
patching file linux/net/pscnack.c
patching file linux/net/unix/af_unix.c
patching file linux/net/wanrouter/wanrouter.c
patching file linux/net/wanrouter/wanproc.c
patching file linux/net/x25/af_x25.c
```

The exact list of file names varies from patch to patch, and some patches change more files than others. The end result, however, is a kernel source tree updated to the latest version. Finally, execute the following two commands to ensure you are working with a pristine source tree:

```bash
$ cd linux
$ make mrproper
```

### Kernel Compilation: The Fourth Stage

#### Configuring GRUB

GRUB, the Grand Unified Bootloader, is the default bootloader in Red Hat Linux 7.2. The following listing shows a typical GRUB configuration file (usually `/boot/grub/grub.conf`):

```text
default=0
timeout=10
splashimage=(hd0,0) /grub/splash.xpm.gz
title Red Hat Linux (2.6.26-2)
root (hd0,0)
kernel /vmlinuz2.6.26-2 ro root=/dev/sda2
initrd /initrd2.6.26-2.img
```

To activate the new kernel, add the following lines below the existing entries:

```text
title Test Kernel (2.6.26.x)
root (hd0,0)
kernel /vmlinuz2.6.26.x ro root=/dev/sda2
initrd /initrd2.6.26.x.img
```

Modify the root device (`/dev/sda2` in this example) to reflect your system. This single change is all you need to do to make GRUB aware of the new kernel - GRUB reads this file at boot time and uses it to build a menu of options.

### Booting the Custom Kernel

After you have updated GRUB's menu file, reboot, select the new kernel from GRUB's menu, press the ENTER key, and, if everything has gone well, your Red Hat Linux system should boot your new kernel. Execute the following command to make sure you've booted the new kernel:

```bash
$ uname -a
```

### CONCEPT

NS-2 is an open-source simulation tool that runs on Linux. It is a discrete event simulator targeted at networking research and provides substantial support for the simulation of routing, multicast protocols, and IP protocols, such as UDP, TCP, RTP, and SRM over wired and wireless (local and satellite) networks. It has many advantages that make it a useful tool, such as support for multiple protocols and the capability of graphically detailing network traffic. Additionally, NS-2 supports several algorithms in routing and queueing. LAN routing and broadcasts are part of routing algorithms. Queueing algorithms include fair queueing, deficit round-robin, and FIFO.

#### Advantages of NS-2

- Simulate different scenarios with existing protocols (TCP/UDP)
- Wired Routing protocols - Distance Vector and Link State (with the link state patch)
- Ad-Hoc Routing protocols - DSR, AODV, TORA
- You can modify NS-2 to implement your own versions of the preceding protocols or even code totally new protocols
- Graphic visualization - using "NAM" (Network Animator)
- NS-2 can also be used to write applications, such as FTP, ECHO

#### Platforms used for NS-2

NS-2 is available on several platforms such as FreeBSD, Linux, SunOS, and Solaris. NS-2 also runs on Windows.

### Packages Required to run NS-2

NS-2 requires the following packages to run:
