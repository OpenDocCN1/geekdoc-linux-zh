
## Understanding Process Scheduling

Process scheduling is the core of the Linux operating system. The process scheduler has the following responsibilities:

- Allows processes to create new copies of the process which are saved in the memory.
- Determines which process will have access to the CPU and effect the transfer between running processes
- Receives interrupts and route them to the appropriate kernel subsystem
- Sends signals to user processes
- Manages the timer hardware
- Cleans up process resources when a process finishes executing

The process scheduler also provides support for dynamically loaded modules. These modules represent kernel functionality that can be loaded after the kernel starts executing. This loadable module functionality is used by the virtual file system and the network interface.

The process by which a computer is turned on and the Linux/UNIX operating system starts functioning is called booting. It consists of the following steps:

- Finding the kernel of the operating system. How this is achieved is usually particular to the type of hardware used by the computer.
- Starting the kernel operation and particularly looking for all the hardware devices that are connected to the machine.
- Starting the processes that include a number of steps to configure various services necessary for the system to work.

## Exploring Boot Sequence

The following are the boot sequence...

- Basic Input/Output System (BIOS) Initialization
- Master Boot Record (MBR) Boot Loader
- Kernel Initialization
- init Initialization

Let’s discuss these sequences in the following sections.

### BIOS Initialization

- Peripherals detected
- Boot device selected
- First Sector of boot device read and executed

## BIOS - Starting the Boot Process

BIOS is the interface between the hardware and the software on a very basic level. BIOS provides the basic set of instructions used by the operating system. A successful boot depends on the BIOS, which provides the lowest level of interface to peripheral device and controls. BIOS first runs a power on self-test (POST), and then it looks for peripherals and a device to boot from. The hardware configuration information is permanently stored in a small area (usually 64 bytes) of Complementary Metal Oxide Semiconductor (CMOS). CMOS is powered by a small battery located in your motherboard. This battery allows CMOS to retain its settings even when the computer is turned off and disconnect from power.

At the end of POST, a boot device is selected from the list of detected boot devices. Any modern BIOS will allow you to set the desired order of preference for the boot device from a list. Boot devices can include: the floppy drive, hard drive, CD-ROM, network interface, Zip drive or other removable media.

The BIOS reads and executes the first physical sector of the chosen boot media on the system. Usually this is contained in the first 512 bytes of the HD.

### MBR

When allocating disk space for the partitions, the first sector, or data unit, for each partition is always reserved for programmable code used in booting. The very first sector of the hard disk is reserved for the same purpose and is called the **master boot record (MBR)**. When booting from a hard disk, the PC system BIOS loads and executes the boot loader code in the MBR. The MBR then needs to know which partitions on the disk have boot loader code specific to their operating systems in their boot sectors and then attempts to boot one of them.

### GRUB Linux Boot Loader

Fedora/Red Hat Linux is supplied with the GRUB boot loader; therefore, it cannot entirely fit in the 512 bytes of the MBR. The GRUB MBR boot loader merely searches for a special **boot partition** and loads a **second stage boot loader**. The second stage boot loader then reads the data in the /boot/grub/grub.conf configuration file, which lists all the available operating systems and their booting parameters. When data reading from the grub.conf file is complete, the second stage boot loader then displays the familiar Fedora branded splash screen that lists all the configured operating system kernels for your choice. Grub is versatile boot loader and can be configured to support booting into many different operating systems, such as Windows and FreeBSD.

The grub.conf file for a system that can boot both Fedora Linux and Windows XP is given as follows:

```
default=0
timeout=10
splashimage=(hd0,0)/grub/splash.xpm.gz
title Fedora Core (2.6.8-20)
root (hd0,0)
kernel /vmlinuz-2.6.8-20 ro root=LABEL=/
initrd /initrd-2.6.8-20.img
title Windows XP
rootnoverify (hd0,1)
chainloader +1
```

## Kernel Initialization

Various functions performed by the kernel at the time of booting are listed as follows:

- Device detection
- Device driver initialization
- Mount root filesystem read only
- Loads initial process (usually *init*)

### Examining kernel Initialization

Although, they generate good output, much of the kernel initialization activities take place so quickly that if you do not watch carefully during boot, you may miss them. A good way to “freeze time” and examine this output is to view /var/log/dmesg , which contains a snapshot of these kernel messages taken after control is passed to *init*. Review of this output will reveal the basic initialization steps of the Linux kernel:

Device drivers compiled into the kernel are called, and will attempt to locate their corresponding devices. If successful in locating the device, the driver will initialize and usually log output to the kernel message buffer.

If essential (needed for boot) drivers have been compiled as modules instead of into the kernel, then they must be included in an *initrd* image, which is then temporarily mounted by the kernel on a RAM disk to make modules available for the initialization process.

After all the essential drivers are loaded, the kernel will mount the root filesystem read-only.

The first process is then loaded (usually *init*) and control passed from the kernel to init process.

## init Initialization

Various tasks performed by the init process are listed as follows:

- init reads its config : /etc/inittab
  - initial run-level
  - system initialization scripts
  - run-level specific script directories
  - trap certain key sequences
  - define UPS power fail/restore scripts
  - spawn gettys on virtual consoles
  - initialize X in run-level 5

init is the parent of all processes. This is easily shown by running the *pstree* command

```
[root @netmon opt]#pstree
init+---apmd
  |-atd
  |-automount
  |-crond---crond
  |-gdm---X
```
