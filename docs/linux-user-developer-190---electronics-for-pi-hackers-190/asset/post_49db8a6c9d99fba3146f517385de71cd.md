## Build programs with GNU Make: unusual uses

GNU Make is such a powerful program that it can often be put to good use for purposes other than builds. So far in this series, we've learned the basics of using Make to automate builds, as well as more advanced concepts and techniques for handling parallel projects. In this tutorial, it's time to take a different approach to Make. We're going to show how it can be used in ways much different from the ones we've seen before.

We'll give two case studies, starting with a Makefile that can be used to copy files from one directory to another. We'll then build on Make's capabilities for parallel processing.

Each of these case studies uses the full capabilities of Make; each will make full use of one specific feature. The goal is to help you think of Make as a powerful automation suite that you can use in your day-to-day Linux administration and not just for a tool for software builds. Since Make is present by default on many Linux distributions, it provides a portable alternative to unusual uses. We hope that after this article, you'll come up with some unusual uses of Make.

This works for a small website, but before long we have a large project with multiple files in directories, of all time might be taken to copy to the server. It would be enough to write a script to copy, but if we make a change to one file we don't have to copy the whole thing; we only want to copy the files that we have changed.

The answer to this problem is to build a sync utility that tells which files have changed since the last push, and copies only those files to the server. The entire operation of Make is made around modification times of files, it makes sense to use it as a tool to build a sync utility.

In order to test out, we'll use a shell script that simulates the process of copying files to the server. You can find this script on server.copy.sh. The script asks for a password, and if the password is correct it copies the given files to a server. The password is swidth, though you can find it here: 

```bash
$ index.html style.css
$ /server.copy index.html
Password: swidth
index.html copied to server:
script.js copied to server: 
```

We use one (only) auxiliary file .last_push, the last function of which is the record of the last time we pushed to our local repository. In the time, before we push the changes to the server, we run the command `touch last_push`.

We copy the files to the server when any of them have changed since the last time we did a push. This suggests that the files we want to push to the server all be prerequisites for the last_push.

```make
FILES = *.html *.css *.js
last_push = $(FILES)
```

The recipe for last_push should contain the command `touch last_push`, in order to update the timestamp. We should also make it responsible for pushing all the files to the server. The key to doing this is using the automatic variable `$`, which is populated with the list of all prerequisites of the current rule that are newer than that rule; in this case, precisely the list of files that have been modified since the last time pushed to the server.

# Figure 1

```make
FILES = *.html *.css *.js
LAST_PUSH = .last_push
SCP = ./server_copy.sh
PHONY: push
push: $(LAST_PUSH)
	$(SCP) $(FILES)
	touch $(LAST_PUSH)
```

```make
.last_push : $(FILES)
	./server.copy $$
	touch .last_push
```

The complete make, using variables to make it maintainable, is using Figure 1. You can run it using `make sync`.

```bash
$ make push
./server.copy index.html script.js
Password: swidth
index.html copied to server:
style.css copied to server:
touch .last_push
```

Now, if we have multiple files, the one that is copied:

```bash
$ make push
./server.copy index.html
Password: swidth
index.html copied to server:
touch .last_push
```

Lastly, we need to verify the value of the files in order to find all the files we want to be able to copy across. We can do this programmatically, using a shell function to call the utility from the shell. The function will search through the directory and its subdirectories that are in html, css, or js.

```make
FILES = $(find . -name *.html -o -name *.css -o -name *.js -o -name *.jpg)
```

Here, we use the function `$(shell ......))` which we can now add other files with the same extensions and our sync utility still be able to copy them.

# Parallel processing

One of the most powerful features of Make is capacity for parallel processing. By default, Make executes its rules sequentially, but unless we use, we can do this automatically, using the operating system task scheduler, to ensure which work works concurrently, and which needs to be executed in order.

To enable this we run make with the -j if we specify a number of jobs - make -j will limit the number of jobs that can be executed at the same time. If we run -j without specifying a number, the number of threads run concurrently in unlimited mode.

A command-line switch to use advantage -j 1, which makes Make to limit the number of threads it runs concurrently if the system is under high load. The level of load that is measured by experiencing us the load average when we run our uptime make command.

```bash
$ uptime
10:37:13 59 min, 3 users
average: 0.31, 0.34, 0.53
```
