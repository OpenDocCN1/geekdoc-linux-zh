
## Joins

A join is a method by which we perform a query and produce a result that combines the data from two tables. SQL supports several types of joins but we're going to focus on the most commonly used type called inner join. We can think of an inner join as the intersection of two tables. In the example below, a file join_demo.sql, we will produce a query result that matches our earlier example when we added columns to the Package_Descriptions table.

```sql
-- join_demo.sql
-- Demonstrate join by selecting columns from 2 tables

.header on
.mode column
.width 20 35 -10

SELECT Package_Descriptions.package_name AS Package,
    description AS Description,
    count AS Files,
    tot_size AS Size
FROM Package_Descriptions
INNER JOIN Package_Stats
ON Package_Descriptions.package_name = Package_Stats.package_name
```

Since package_name is a column in both the Package_Descriptions and Package_Stats tables, we must precede it with the name of the respective table to avoid ambiguity.

## Views

The join example above is a pretty useful query for our tables, but due to its complexity it's best executed from a file rather than an ad hoc query. SQL addresses this issue by providing a feature that allows a complex query to be stored in the database and used to produce a virtual table that can be used with simple query commands. In the following example we will create a view using our INNER JOIN query to create a virtual table Stats that we can use as the target of subsequent queries.

```sql
-- view_demo.sql

DROP VIEW IF EXISTS Stats;
CREATE VIEW Stats
AS
SELECT Package_Descriptions.package_name AS Package,
description AS Description,
count AS Files,
tot_size AS Size
FROM Package_Descriptions
INNER JOIN Stats
ON Package_Descriptions.package_name =
Package_Stats.package_name
ORDER BY Package;
```

Once we create it, we can treat Stats as just another table in our database even though it does not really exist.

## Indexes

It's been said that most important features of a database system are "performance, performance, and performance." While this is not exactly true (things like data integrity and reliability are important), complex operations on large databases can get slow, so it's important to make things as fast as we can. One feature we can take advantage of is indexes. An index is a data structure the database maintains that speeds up searches. It's a sorted list of rows ordered by one or more columns. Without an index, a table is sorted by values called rowid. The values in this column start with 1 and increment each time a row is added to the table. Here we see a query that selects the 100th row from the Package_Stats table.

```sql
.header
.mode column
.width 20 -5 -8
> SELECT * FROM Package_Stats WHERE rowid = 100;
package_name      count  min_size  max_size avg_size
cups-server-common  595 199640 0 370070 3355294
```

Our database can locate this row in the table very quickly because it already knows where to find 100th row. However, if we want to search for the row that contains cups-server-common SQLite must examine every row in the table. To facilitate tuning, SQLite provides a way to see what strategy is used during a query.

```sql
.width -8 -5 -4
> EXPLAIN QUERY PLAN
SELECT * FROM Package_Stats WHERE package_name = 'cups-server-common';
0  0  SCAN Table Package_Stats
```

SQLite performs a sequential scan of the table during this query. To create an index to allow faster searches of package_name we can do the following:

```sql
> CREATE INDEX idx_package_name ON Package_Stats (package_name);
```

After doing this, we'll look at the query plan and see the difference.

```sql
> EXPLAIN QUERY PLAN
SELECT * FROM Package_Stats WHERE package_name = 'cups-server-common';
0  0  0 SEARCH Table Package_Stats USING INDEX idx_package_name
```

Whenever we search for a package name, SQLite will use the index to get directly to the row rather than looking at every row for a match. Why don't we index everything? The reason is that indexes impose overhead every time a row is inserted, deleted, or updated. Indexes are used on tables that are read more than written. We probably won't see much of a performance improvement when searching the Package_Stats table because it's not that big, but on a large table the improvement could be substantial. We can see the index when we examine the table schema.

```sql
.schema Package_Stats
CREATE TABLE Package_Stats (
  package_name VARCHAR(60),
  count        INTEGER,
  tot_size     INTEGER,
  min_size     INTEGER,
  max_size     INTEGER,
  avg_size     REAL
);
CREATE INDEX idx_package_name ON Package_Stats (package_name);
```

SQLite also has a command:

```sql
> .indexes
idx_package_name
```

Another benefit of using an index is that it's sorted order (that is how it performs searches quickly). The side effect is that when an index is used during the query the results of the query will be sorted as well. To demonstrate, we will create another index for the Package_Stats table, this time using the tot_size column. Note that when we perform a select on column, the results are in ascending order.

```sql
> CREATE INDEX idx_tot_size ON Package_Stats (tot_size);
.width 5 -column 8
> SELECT * FROM Package_Stats WHERE tot_size > 100000000;
```
