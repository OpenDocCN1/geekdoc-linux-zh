An index is a data structure the database maintains that speeds up database searches. It's a sorted list of rows in a table ordered by elements in one or more columns. Without an index, a table is sorted by values in a hidden column called rowid. The values in this column are integers that start with 1 and increment each time a row is added to the table. Here we see a query that selects the 100th row from the Package_Stats table.

```
sqlite>.header
sqlite>.mode column
sqlite>.width 20 -5 -8 -0 -8
sql> SELECT * FROM Package_Stats WHERE rowid = 100;
package_name      count  min_size  max_size avg_size
cups-server-common  595 1996400 0 370070 3355.294
```

Our database can locate this row in the table very quickly because it already knows where to find the 100th row. However, if we want to search for the row that contains package name cups-server-common SQLite must examine every row in the table to locate the matching row. To facilitate performance tuning, SQLite provides a way to see what strategy is used during a query.

```
sqlite>.width -8 -5 -4 5
sqlite> EXPLAIN QUERY PLAN
...> SELECT * FROM Package_Stats WHERE package_name = 'cups-server-common';
selectid  order  from  detail
0  0  0  SCAN Table Package_Stats
```

We can see the SCAN Table Package_Stats SQLite performs a sequential scan of the table during this query.

To create an index to allow faster searches of package_name we can do the following:

```
sqlite> CREATE INDEX idx_package_name
...> ON Package_Stats (package_name);
```

After doing this, we'll look at the query plan and see the difference.

```
sqlite> EXPLAIN QUERY PLAN
...> SELECT * FROM Package_Stats WHERE package_name = 'cups-server-common';
selectid  order  from  detail
0  0  0  SEARCH Table Package_Stats USING INDEX idx_package_name
```

Hereafter when we search for a package name, SQLite will use the index to get directly to the row rather than looking at every row for a match. Why don't we just index everything? The reason is that indexes impose overhead every time a row is inserted, deleted, or updated since indexes must be kept up to date. Indexes are used on tables that are read more than written to.

We probably won't see much of a performance improvement when searching the Package_Stats table because it's not that big, but on a large table the improvement could be substantial.
