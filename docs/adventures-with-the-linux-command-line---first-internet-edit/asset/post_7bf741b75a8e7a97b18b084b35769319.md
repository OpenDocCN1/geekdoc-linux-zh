# 4 More Redirection

As we learned in Chapter 6 of TLCL, I/O redirection is one of the most useful and powerful features of the shell. With redirection, our commands can send and receive streams of data to and from files and devices, as well as allow us to connect different programs together. In this adventure, we will look at redirection in a little more depth to see how it works and discover some additional features and useful techniques.

## What's Going On

Whenever a new program is run on the system, the kernel creates a table of file descriptors for the program to use. By convention, the first three descriptors (0, 1, and 2) are used as standard input (stdin), standard output (stdout), and standard error (stderr). Initially, all three descriptors point to the terminal device (which the system treats as read/write), so that standard input comes from the keyboard and standard output go to the terminal.

When a program started as a child process of another (for instance, when we run an executable in the shell), the newly launched program inherits a copy of the parent's descriptor table. Redirection is the process of manipulating file descriptors so that input and output can be routed to different files. The shell hides the presence of descriptors in common redirections such as:

```
command > file
```

Here we redirect standard output to a file, but the syntax of the redirection operator includes an optional file descriptor. We could write the above statement this way and would have exactly the same effect:

```
command 1 > file
```

As a convenience, the shell assumes we want to redirect standard output if the file descriptor is omitted. Likewise, the following two statements are equivalent when referring to standard input:

```
command < file
command 0 < file
```

## Duplicating Descriptors

It is sometimes desirable to write more output stream (for example output and error) to the same file. To do this, we would write something like this:

```
command > file 2>&1
```

We add the file descriptor to the first redirection to make things clearer:

```
command 1> file 2>&1
```

This is an example of duplication. When we read this statement, we see that descriptor 1 is changed from redirection to the terminal device to pointing file. This is followed by the second redirection that causes descriptor 2 to become a duplicate of descriptor 1 (i.e., points to the same file). When we look at this, it's easy to see how the order of redirections is important. For example, if we reverse the order:

```
command 2>&1 1> file
```

file descriptor 2 becomes a duplicate of descriptor 1 (which points to the terminal) then descriptor 1 is set to point to file. The final result is descriptor 1 points to file while descriptor 2 still points to the terminal.

## exec

Before we go any further, we need to take a brief detour and talk about a shell builtin we didn't cover in TLCL. This builtin is named exec and it does some interesting things. Its main purpose is to terminate the shell and launch another program in its place. This is often used in startup scripts that initiate system services. However, it is not common in scripts used for other purposes.

Usage of exec is described below:

```
exec [program] [redirections]
```

program is the name of the program that will start and take the place of the shell. redirections are the redirections to be used by the new program.

One feature of exec is useful for our study of redirection. If program is omitted, any redirections are performed on the current shell. For example, if we included this beginning of a script:

```
exec 1> output.txt
```

from that point on, every command using standard output would send its data to output.txt. It should be noted that if this trick is performed by a script, it is no longer possible to redirect script's output at runtime using the command line. For example, if we had the following script:

```bash
#!/bin/bash

# exec-test - Test external redirection and exec
exec 1 > ~/fool.txt
echo "Boo."

# End of script
```

and we tried to invoke it with redirection:

```
me@linuxbox ~ ./exec-test > /foo2.txt
```

The attempted redirection would have no effect. The "Boo" would still be written to the file fool.txt, not foo2.txt as specified in the command line. This is because the redirection performed inside the script via exec is performed after the redirection on the command line, and thus takes precedence.

Another way we can use exec to open and close additional file descriptors. While most often use descriptors 0, 1, and 2, it is possible to use others. Here are examples of opening and closing file descriptor 3:

```bash
# Open fd 3
exec 3 > some_file.txt

# Close fd 3
exec 3>&-
```

It's easy to open and use file descriptors 3-9 in the shell, and it's even possible to use file descriptors 10 and above, though the bash may page counts against it.

So why would we want to use additional file descriptors? That's a little hard to answer. In most cases we don't need to. We could open several descriptors in a script and use them to redirect output to different files, but it's just as easy (using shell variables, if desired) the names of the files that we want to redirect since most commands are going to send their data to standard output anyway.

There is one case in which an additional file descriptor would be helpful. It's the case of a filter program that accepts standard input and sends its filtered data to standard output. Such programs are quite common, for example sort and grep. But what if we want to create a filter program that also writes on the terminal display while it was filtering? We can't use standard output to do it, because standard output is being used to output the filtered data.
