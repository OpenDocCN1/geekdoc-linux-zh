# Schemas

The design of a database is called its *schema* and it can be simple, containing just a single table or two, or it can be complex, containing many tables with complex interrelations between them.

Let's imagine a database for a bookstore consisting of three tables. The first is called *Customers*, the second is called *Items*, and the third is called *Sales*. The *Customers* table will have multiple rows with each row containing information about one customer. The columns include a customer number, first and last names, and the customer's address. # Keys

Now we are wondering what the *Cust* and *Item* columns are for. They serve as keys to uniquely identify a row and facilitate interrelations between tables. Keys have some special properties. They must be unique (they can appear only once in a table and specifically identify a row) and must be immutable (they can never change). If they can't meet these requirements, they cannot be keys. Some database implementations have methods of enforcing these requirements during creation and keys can be formally specified. In the case of our bookstore database, the *Cust* column contains the keys for the *Customers* table and the *Item* column contains the keys for the *Items* table.
