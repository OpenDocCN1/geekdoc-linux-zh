Worth emphasizing is that all special characters are ignored by the shell if they appear within single quotes. That explains how the following works:

```
$ files/users/steve/bin/progl
$ echo $file
/users/steve/bin/progl
$ echo '$file'
not interpreted
$file
$ echo *
addresses into lotsaspaces names nu phonebook stat
$ echo '*'
$ echo ' < > | ; ( ) { } >> &'
< > | ; ( ) { } > " &\n$
```

Even the Enter key will be retained as part of the command argument if it's enclosed in single quotes:

```
$ echo 'How are you today,
> John'
How are you today,
John
$
```

After parsing the first line, the shell sees that the > quote isn't matched, so it prompts the user (with ~) to type the closing quote. The > is known as the secondary prompt character and is displayed by the shell whenever it's waiting for you to finish typing a multi-line command.

Quotes are also needed when assigning variables containing whitespace or special characters to shell variables, though there are nuances, demonstrated:

```
$ messages='I must say, this is fun'
$ echo $message
I must say, this is fun
$ text='means all files in the directory'
$ echo $text
```

names nu phonebook stat means all files in the directory
$

The quotes are needed in the first statement because the value being stored includes spaces.

The second sequence with the variable text highlights that the shell does filename substitution after variable substitution, the * is replaced by the name of all files in the current directory after the variable is expanded, but before the echo is executed. Annoying!

How do you fix this sort of problems? Through the use of double quotes.
