
# The Login Shell

In the old days, terminals were physical devices that were connected to the Unix hardware through a direct wire. Nowadays, however, terminal programs let you stay within your Linux, Mac or Windows environment and interact with the system over the network in a managed window. Generally you launch a program such as Terminal or xterm, then connect to remote systems as needed using programs as `ssh, telnet, or rlogin`.

For each physical terminal on a system, a program called getty will be active. This is depicted in Figure 2.2.

![](img/dc544c8aef1333b25eff1c794c2e5ec2_59_0.png)

Figure 2.2 The getty process

The Unix system—more precisely a program called `init`—automatically starts up a getty program on each terminal port whenever allowing users to log in. `getty` is essentially a device driver, letting the `login` program display the message `login:` at its assigned terminal and for someone to type in something.

If you connect via a program like `ssh`, you'll be assigned a pseudo-terminal or pseudo-tty, in Unix parlance. That’s why when you typed in `who` you saw entries like `pty3` or `pty1`.

In both instances, the program that reads your account and password information, and the program that validates it and invokes whatever login programs are needed for you to “log in” if everything checks out and is correct.

As soon as someone types in some characters followed by the `Enter` key, the login program finishes the process of logging in (see Figure 2.3).

When login begins execution, it displays the string Password: at the terminal and waits for you to type your password. After you have typed it and pressed Enter (you won't see any output as type, for security reasons), login then proceeds to verify your login name and password against the corresponding entry in the file /etc/passwd. This file contains an entry for each user account that specifies, other things, the login name, home directory, and program to start up when user logs in. The last bit of information (the login shell) is stored as the last colon of each line. If nothing follows the colon, the standard shell /bin/sh is assumed by default.

If you log through a terminal, the data handshake might involve a program like ssh on the server, and if you're opening a window on your Unix computer, it will just let you in without having to type in your password!

But back to the password file. The following three lines show typical lines from /etc/passwd for three users of the system: sue, pat, and bob:

```
sue*:15:47:/users/sue
pat*:99:7:/users/pat:/bin/ksh
bob*:13:100:/users/data/data/bin_data_entry
```

After login validates an encrypted version of the password you typed in in the encrypted password for the specified account stored in /etc/shadow, it checks for the name of the login program to execute. In many cases, this will be /bin/sh, /bin/ksh, or /bin/bash. In other cases, it may be a special custom-designed program or /bin/nologin for accounts that don't include interactive access (common for file ownership management). The idea underlying all of them is that you can set a login account to automatically run any program whatsoever whenever someone logs to the system. The shell is the program most often selected because of its general utility, but it's not the only game in town.

# Typing Commands to the Shell

When the shell starts up, it displays a command prompt—typically a dollar sign $ at your terminal and waits for you to type in a command (Figure 2.6, Steps 1 and 2). Each time you type in a command and press the Enter key (Step 3), the shell analyzes what you typed and proceeds to carry out your program (Step 4).

If you ask the shell to invoke a program, it searches the disk, stepping through all the directories you've specified in your PATH until the named program. When the program is found, the shell creates a clone of itself (known as a subshell) and asks the kernel to replace the subshell with the specified program; then the shell "goes to sleep" until the program has finished (Step 5). The kernel copies the specified program into memory and begins its execution. This copied program is called a process; in this way, the distinction is made between a program that is kept in a file on the disk and a process that is in memory and being executed, line by line.

If the program writes output to standard output, that output will appear at your terminal unless redirected or piped into another command. Similarly, if the program reads from standard input, it will wait for you to type in that input unless redirected from a file or piped from another command (Step 6).

When the command finishes execution, it vanishes and control once again returns to the login shell, which prompts for your next command (Steps 7 and 8).

That's why so many variations or “flavors” of the shell exist today, including the older Bourne shell, developed by Stephen Bourne; the Korn shell, developed by David Korn; the “Bourne again shell,” mainly used on Linux systems; and the C shell, developed by Bill Joy. were all designed to serve specific purposes and have their own capabilities and personalities.

# Program Execution

The shell is responsible for the execution of all programs that you request from your terminal.

Each time you type in a shell, the shell analyzes the line and determines what to do. As far as the shell is concerned, each line follows the same basic format:

```
program-name arguments
```

The line that is typed to the shell is known more formally as the command line. The shell scans this line and determines the name of the program to be executed and what arguments to pass to the program.

The shell uses special characters to determine where the program starts and ends, and where each argument starts and ends. These characters are collectively called whitespace characters, and are the space character, tab character, and the end-of-line character, known more formally as the newline character.
