
but it also goes about its normal function of matching any lines to standard output, even though we're really not interested in that.

Since we're not interested in seeing the result of the command, just testing the exit code, we can dispose of grep's output by redirecting it to the system's "garbage can," /dev/null. This is a special file on the system that anyone can read (from an immediate end of file) or write to it. When you write to it, the bits vanish, as if it were a massive black hole!

```
who | grep "$user" > /dev/null
```

That'll solve the superfluous output problem.

The second problem with on appears when the program is executed with the argument ann. Even though ann is not logged on, grep matches the characters ann for the user Joanne. We need a more restrictive pattern, which you learned how to do in Chapter 3 where we talked about regular expressions. Because who lists each username in column one of the output, we can anchor the pattern to match the beginning of the line by preceding the pattern with the character ^

```
who | grep "^$user" > /dev/null
```

But that's still not enough. Search for a pattern like bob and grep still matches a line like


What you need to do is also anchor the pattern on the right too. Realizing that who ends each username with one or more spaces, the further modified pattern

```
"$user "
```

now only matches lines for the specified user. Problem two fixed!

## The test Command 

Though the previous example used a pipeline to test the if statement, a built-in shell command test is much more commonly used for testing one or more conditions. Its general format is

```
test expression
```

where expression represents the condition you're testing. test evaluates expression, and if the result is true, it returns an exit status of zero, otherwise the result is false, and it returns a nonzero status.

## String Operators

As an example, the following command returns a zero exit status if the shell variable name contains the characters julio:

```
test "name" = julio
```

The operator is used to test whether two values are identical. In this case, we're testing to see whether the contents of the shell variable name are identical to the characters julio. If it is, test returns an exit status of zero; nonzero otherwise.

Note that test must serve all operands ($name and julio) and operators (=) as separate arguments, meaning that they must be delimited by one or more whitespaces.

Getting back to the if command, echo the message "Would you like to play a game?" if name contains the characters julio, you would write your command like this:

```
test "name" = julio
then
echo "Would you like to play a game?"
fi
```

When the if command executes, the command that follows the if is executed, and its exit status is evaluated. The test command is passed three arguments $name (with its value substituted, of course), =, and julio. test then evaluates whether the first argument is identical to the third argument and returns a zero status if it is and a nonzero status if it is not. The exit status returned by test is tested by the if statement. If it's zero, the commands between then and fi are executed; If exit status is nonzero, the echo command is skipped.

As demonstrated above, it's good programming to enclose shell variables that are arguments to test inside a pair of double quotes (to allow variable substitution). This ensures that test sees the argument even if its value is null. For example, consider the following

```
$ name=
$ test $name = julio
sh: test: argument expected
$
```

Because name was null, only two arguments were passed to test: because the shell substituted the value of name before parsing the command line. In fact, after $name was substituted by the shell, you typed the following:

```
test = julio
```

When test executed, it saw only two arguments (see Figure 7.1) and therefore issued the error message.

By placing double quotes around the variable, you ensure that test sees the argument because quotes act as a "placeholder" when the argument is null.

```
$ test "$name" = julio
$ echo $?
```

Other operators can be used to test strings. There are a number of them, as summarized in Table 7.1.

Table 7.1 String Operators

| Operator | Returns TRUE (exit status of 0) if |
| :--- | :--- |
| string_1 = string_2 | string_1 is identical to string_2 |
| string_1 != string_2 | string_1 is not identical to string_2 |
| string | string is not null |
| -n string | string is not null (must be seen by test) |
| -z string | string is null (and must be seen by test) |

You've seen how = operator is used. The != operator is similar, except it tests two strings for inequality. That is, the exit status from test is 0 if the two strings are not equal, and nonzero if they are. Let's look at three similar examples.

```
$ day="monday"
$ test "$day" = monday
$ echo $?
0
$
```

The test command returns an exit status of 0 because the value of day is equal to the characters. Now look at the following: If you wanted these two values to be considered equal, omitting the double quotes would have caused the shell to "eat up" the trailing space, and test would have never seen it:

```
$ day="monday"
$ test $day = monday
$ echo $?
0
$
```

Although this seems to violate our rule about always quoting shell variables that are arguments to test, it's better to omit the quotes if you're sure that the variable is not null (and not composed entirely of whitespaces characters). You can test to see whether a shell variable has a null value with the operator listed in Table 7.1:

```
test $day*
```

This returns TRUE if day is not null and FALSE if it is. Quotes are not necessary here because test doesn't care whether it sees an argument in the shell case. Nevertheless, you are better off using them as well if the variable consists entirely of whitespaces characters, the shell will get rid of the argument if it's not enclosed in quotes.

```
$ blanks="  "
$ test $blanks          Is it not null?
$ echo ?               False—it's null
1
$ test "$blanks"      And now?
$ echo ?               0
$                       True—it's not null
```

In the first case, test was not passed any arguments because the shell ate up the four spaces in blanks. In the second case, test got one argument consisting of four space characters which is not null. In case we seem to be elaborating the point about blanks and quotes, realize that this is a frequent source of shell programming errors. It's good to really understand the principles to save yourself a lot of programming headaches in the future.

There is another way to test whether a string is null, with either of the last two operators listed previously in Table 7.1. The -n operator returns an exit status of zero if the argument is not null. Think of this operator as testing for nonzero length. The -z operator tests the argument that follows to see whether it is null and returns an exit status of zero if it is true. Think of this operator as testing to see whether the following argument has zero length. So the command

```
test -n $day*
```

returns an exit status of 0 if day contains at least one character. The command

```
test -z $dataflag
```

returns an exit status of 0 if dataflag doesn't contain any characters.
