
# The trap Command 259

As an example of the trap command, the following shows how you can remove some files and then exit if someone tries to interrupt the program from the terminal:

```
trap 'rm $WORKDIR/work1$$ $WORKDIR/data$$; exit' INT
```

Once this trap is executed, the two files work1$$ and data$$ will be automatically removed if a SIGINT (signal number 2) is received by the program. If the user interrupts execution of the program after this trap is executed, you can be assured that these two temporary files will be removed, not left around in the file system. The exit that follows the rm is necessary because without execution would continue in the program at the point that it left when the signal was received.

Signal 1-SIGHUP or HUP is generated for hangup: originally related to dialup connections, but more generally refers to an unexpected disconnect like the Internet connection dropping. You can modify the trap to also remove the two specified files in this case by adding a SIGINT to the list of signals:

```
trap 'rm $WORKDIR/work1$$ $WORKDIR/data$$; exit' INT HUP
```

Now these files will be removed if the line hangs up or if the user interrupts processing with the DELETE key or Ctrl+c.

The sequence to trap (also known as the trap handler) must be enclosed in quotes if it contains more than one command. Also note that the shell scans the command at the time that the trap gets executed and also when one of the listed signals is received.

In the preceding example, the value of WORKDIR and $$ will be substituted at the time that the trap command is executed. If you wanted this substitution to occur at the time that the trap was defined:

```
trap 'rm $WORKDIR/work1$$ $WORKDIR/data$$; exit' INT HUP
```

The trap can be used to make your programs more friendly too. In a further revision to the rolo program in the next chapter, the Ctrl+c interrupt signal will be caught by the program and return the user to the main menu, not have the program quit completely.

# trap with No Arguments

Executing trap with no arguments results in the display of any trap handlers you have defined or modified:

```
$ trap 'echo logged off at $(date) >>$HOME/logoffs' EXIT
$ trap                             List changed traps
trap - 'echo logged off at $(date) >>$HOME/logoffs' EXIT Log off
$ Ctrl+c
login: steve Log back in
Password:
$ cat $HOME/logoffs See what happened
logged off at Wed 2 15:11:58 EDT 2002
$
```

A trap was set to be executed whenever the shell exited—signal 0, EXIT—was received by the shell. Because this was set in the login shell, the trap handler is used when you log off to write the time you logged off to the file $HOME/logoffs. The command is enclosed in single quotes to prevent the shell from executing date when the trap is defined.

The trap command is executed with no arguments which lists the new action to be taken for signal 0 (EXIT). When steve logs off and back on, the file $HOME/logoffs verifies that the echo command was executed and the trap worked.

# Ignoring Signals

If the command listed for trap is null, the specified signal is ignored when received. For example, the command

```
trap " SIGINT"
```

specifies the interrupt signal is to be ignored. You might want to ignore certain signals when performing some operation that you don't want.

Note that trap lets you specify signal by name, by shortened name (INT) or by the full signal name (SIGINT). We encourage you to use mnemonic names to help produce readable code, but it is, of course, to which you prefer.

In the example, the first argument must be specified as a null value for a signal to be ignored and is not equivalent to writing the following, which has a separate meaning of its own:

```
trap 2
```

If you ignore a signal, all subshells also ignore that signal. If you specify a signal handler action, however, all subshells automatically take the default action on receipt of signal, not the new code sequence.

Suppose you execute the command

```
trap " 2"
```

and then start a subshell, which in turn executes other programs as subshells. If an interrupt signal is generated, it will have no effect on the shells or subshells that are executing because they will ignore the signal by default.

If instead of executing the previous trap you execute

```
trap : 2
```

and then execute your subshells, the current shell will do nothing on receipt of an interrupt (it will execute the null command), while subshells will be terminated (the default action).

# Resetting Traps

After you've changed the default action to be taken on receipt of a signal, you can change it back again with trap if you simply omit the first argument; so

```
trap HUP INT
```

resets the action to be taken on receipt of the SIGHUP or SIGINT signals back to the default behavior for the shell.

Many shell programs also use a construct like this

```
trap /bin/rm -f $tmpfile; exit INT QUIT EXIT
```

to ensure that the rm command won't produce an error message if the temporary file hasn't been created upon. The trap handler removes the temporary file if it exists and does nothing if it doesn't.

# More on I/O

You know about the standard constructs <, >, >> for input redirection, output redirection, output redirection with append, respectively. You also know that you can redirect standard error from any command by writing 2> instead of >.

```
command 2> file
```

Sometimes you may want to redirect standard error in your program. With a slight variation on the above, you can redirect standard output to standard error by writing & the file descriptor that follows. Descriptor 0 is standard input, descriptor 1 is standard output, and descriptor 2 is error. It's important to remember that no space is permitted between the > and &.

To write a message to standard error:

```
echo "Invalid number of arguments" >2
```

You may want to redirect both standard output (often "stdout") and standard error ("stderr") from a program into the same file. If you know the name of the file, this is straightforward:

```
command > foo 2>> foo
```

Here both stdout and stderr will be written to foo. You can also write

```
command > foo 2>&1
```

to achieve the same effect; standard output is redirected to foo, and standard error is redirected to standard output (which has already been redirected to foo). Because the shell evaluates redirection from left to right on the command line, the last example won't work properly if the stderr sequence appears first on the command line

```
command 2>&> foo
```

because you will first redirect standard error to standard output then standard output to foo.

You can also dynamically redirect standard input or output in a program using the exec command:

```
exec < datafile
```

redirects standard input from the datafile. Subsequent commands executed read from standard input will read from datafile instead. The command

```
exec > /tmp/output
```

does the same thing with standard output: all commands that subsequently write standard output will write to /tmp unless explicitly redirected elsewhere. Naturally, standard error can be reassigned as well:

```
exec 2> /tmp/errors
```

All subsequent output to standard error will go to /tmp/errors.

# <&- &&

The sequence &- has the effect of closing standard output. If preceded by a file descriptor, the associated file is closed instead. So writing

```
ls <&
```

causes the output from ls to go nowhere because standard output is closed by the shell when ls is executed. Not hugely useful, we admit!

# In-line Input Redirection

If the << characters follow a command in the format

```
command <<word
```

the shell uses the lines that follow as the input for command, until a line that contains just is found. Here's a simple example:

```
$ wc -l << ENDOFDATA
```

Use lines up to ENDOFDATA as standard input

```
> here's a line
> and another
> and yet another
> ENDOFDATA
3
```
