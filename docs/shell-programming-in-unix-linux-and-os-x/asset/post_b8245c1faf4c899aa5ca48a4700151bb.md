# HOME

Your home directory is where you're placed whenever you log on to the system. A special variable called HOME is automatically set to this directory when you log on:

```
$ echo $HOME
/users/steve
$
```

This variable can be used by your programs to identify your home directory and is widely used by other programs in Unix for just this purpose. It's also used by the cd command as the desired destination when you cd with no arguments:

```
$ pwd
/users/src/lib/ibc/port/stdio
$ cd
```

> Where am I?

```
$ pwd
/users/steve
$
```

> There's no place like home

You can change your HOME variable to do anything you want, but be warned that doing so may affect the operation of any programs that rely on it:

```
$ HOME=/users/steve/book
```

> Change it

```
$ pwd
/users/steve
$ cd
/users/steve/book
$
```

> See what happened

You can change your HOME, but you really shouldn't unless you're prepared to have a lot of things go wacky rather quickly.

Uh oh, that's not good. What happened?

Whenever you type the name of a program, a shell searches a list of directories until it finds the requested program. When the program is started up, this list of directories to search for user commands is stored in a shell variable PATH and it is automatically set when you log on. To see what it is set to at any point, use echo:

```
$ echo $PATH
/usr/bin/
$
```

Chances that your PATH has a somewhat different value, but don't worry about that—it's just variations in system configuration. The important thing to notice is that directories are separated by a colon (:) and the shell searches them in order, left to right, to find requested commands or programs.

In the preceding example, directories are listed: /bin, /usr/bin, and . (which, you recall, is the current directory). Whenever you type the name of a program, the shell searches the directories listed in PATH until it finds a matching executable file. Type in rolo and the shell first looks for /bin/rolo, then /usr/bin/rolo, finally, . in the current directory. As soon as it finds a match it executes, but if the shell doesn't find rolo any of the directories specified in PATH, it issues a "not found" error.

To have the current directory searched anything else, put at the start of PATH:
.:/bin:/usr/bin

Warning! For security reasons, it's not a good idea to have your current directory searched before the system ones.

This is to avoid a Trojan attack: Imagine that someone creates their own version of a command like su (which allows you to switch to root or superuser status by prompting for the admin password) in a directory then waits for any user to change to that directory and run the command. If PATH specifies the current directory searched first, then the modified version of su will be executed. The problem is, this version prompts for the password, emails it to the malicious user, deletes itself, and prints out an innocuous error message. Reinvoked, password retyped, it all works fine and the administrator account has just been compromised without the user realizing anything has occurred! Sneaky, eh?

The period for specifying the current directory is optional but useful as a visible reminder. For example, a PATH of

```
:/bin:/usr/bin
```

is equivalent to the previous one; however, throughout this text we'll specify the current directory with a path for clarity.

Worried about Trojan horses now? Don't fret, you can always override the search specified by PATH by specifying an explicit path to the program to be executed. For, if you type /bin/date, the shell goes directly to /bin to execute date. PATH in this case is ignored, as it is if you type in

```
../bin/rolo
```

or

```
./rolo
```

Now you understand why you couldn't execute rolo from your HOME directory: /users/steve/bin wasn't included in PATH so the shell couldn't find rolo. A simple matter to rectify: You can simply add this to PATH:

```
$ PATH=$PATH:/bin:/users/steve/bin
$
```
