## Your Current Directory

Your current directory is also part of your shell environment. Consider this small shell program called cdtest:

```bash
$ cat cdtest
cd /users/steve/bin
pwd$
```

The program uses cd to move to /users/steve/bin and then invokes pwd to verify that the change was made. Let's run it:

```bash
$ pwd
/users/steve
$ cdtest
/users/steve/bin
$
```

Now for the $64,000 question: If you invoke pwd, will you be in /users/steve or /users/steve/bin?

```bash
$ pwd
/users/steve
$
```

It turns out that the cd in cdtest had no effect on your current directory. Because the current directory is part of the environment, when a cd is executed from a subshell, it only affects the directory of the subshell. There is no way to change the current directory of a parent shell from a subshell.

When cd is invoked, it changes your current directory and also sets the PWD variable to the full pathname of the new current directory. As a result, the command

```bash
echo $PWD
```

produces the same output as the pwd command:

```bash
$ pwd
/users/steve
$ echo $PWD
/users/steve
$ cd bin
$ echo $PWD
/users/steve/bin
$
```

cd also sets OLDPWD to the full pathname of the previous directory, which can be useful in certain situations.

## CDPATH

The CDPATH variable works like the PATH variable: it specifies a list of directories to be searched by the shell whenever you execute cd command. This search is done only if the specified directory is not given by a full pathname and if CDPATH is not null. If you type

```bash
cd /users/steve
```

the shell changes your directory directly to /users/steve; but if you type

```bash
cd memos
```

the shell looks at your CDPATH variable to find the directory. And if your CDPATH looks like this:

```bash
$ echo $CDPATH
:/users/steve:/users/steve/docs
$
```

the shell first looks in your current directory for a directory, and if not found looks in /users/steve for a directory, and if not found tries /users/steve/docs in last effort to find the directory. If the directory is not relative to one, the cd command prints the full path to let you know where it's taking

```bash
$ cd /users/steve
$ cd memos
/users/steve/docs/memos
$ cd bin
/users/steve/bin
$ pwd
/users/steve/bin
$
```

Like the PATH variable, use of the period for specifying the current directory is optional,
:/users/steve:/users/steve/docs

is equivalent to
:/users/steve:/users/steve

Judicious use of CDPATH can save you a lot of typing, especially if your directory hierarchy is fairly deep and you find yourself moving around it (or if you're frequently moving into other hierarchies as well). Unlike PATH, you'll probably want to put your current directory first in the CDPATH list. This gives you the most natural use of CDPATH; if the current directory isn't listed, you may end up in an unexpected directory!

Oh, and one more thing: CDPATH isn't set when you log in; you need to explicitly set it to sequences of directories you'd like the shell to use when searching for the specified name.

## More on Subshells

You know that subshell cannot change the value of a variable in a parent shell, nor can it change its current directory. Suppose that you want to write a program to set values for some variables that you use whenever you log on. For example, assume that you have the following file called vars:

```bash
$ vars
BOOK=/users/steve/book
UUB=/usr/spool/uuc
DOCS=$usr/steve/docs/memos
DB=$usr2/data
$
```

If you invoke vars, the values assigned to these variables will essentially vanish after the program has finished executing because vars is run in a subshell:

```bash
$ vars
$ echo $BOOK
```

## . Command

To address this dilemma, there's a built-in shell command called . (pronounced "dot") whose general format is

- file

and whose purpose is to execute the contents of file in the current shell. That is, commands from file are executed by the current shell as if they were typed, not within a subshell. The shell uses your PATH variable to find file, just like it does when executing other programs.

```bash
. vars
$ echo $BOOK
/users/steve/book
$
```

> Execute vars in the current shell

Hoorah!

Because a subshell is not spawned to execute the program, any variable that gets assigned a value is retained after the program completes.

If you have a program called db that has the following commands:

```bash
$ cat db
DATA=$usr2/data
RPTS=$DATA/cripts
BIN=$DATA/bin
```

```bash
cd $DATA
$
```

executing db with the "dot" command will do something interesting.

```bash
$ pwd
/users/steve
$ . db
$
```

This time the shell program defines the three variables DATA, RPTS, and BIN in the current shell and moves to the $DATA directory.

```bash
$pwd
/usr2/data
$
```

If you work on multiple projects, you can create programs like db to customize your environment as needed. In that program, you can also include definitions for other variables, change prompts, and more. For example, you might change your PS1 prompt to DB—to let you know that your database variables have been set up. You could change your PATH to a directory that has programs set to the database and your CDPATH so that the related directories will be easily accessed with the cd command.

On the other hand, if you make these sorts of changes, you might want to execute db in a subshell rather than the current shell because the latter leaves all the modified variables around after you've finished your work.

The best solution is to start a new shell from inside the subshell, with all the modified variables and updated environment settings. Then, when you're finished working, you can "log out" the new shell by pressing Ctrl+d.

Let's take a look at how this works with a new version of db:

```bash
$ cat db
#
# Set up and export variables related to the data base
#
```

```bash
HOME=/usr2/data
BIN=$HOME/bin
RPTS=$HOME/rpts
DATA=$HOME/rawdata
```

```bash
PATH=$PATH
CDPATH=$HOME:$RPTS
```

```bash
PS1="DB: "
```

```bash
export HOME BIN RPTS DATA PATH CDPATH PS1
#
```
