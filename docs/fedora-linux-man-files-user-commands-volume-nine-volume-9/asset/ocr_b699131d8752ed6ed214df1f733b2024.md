# ## CONCEPTS

systemd provides a dependency system between various entities called “units” of 12 different types. Units encapsulate various objects that are relevant for system boot-up and maintenance. The majority of units are configured in unit configuration files, whose syntax and basic set of options is described in (5), however so are created automatically from other configuration, dynamically from system state or programmatically at runtime.

Units may be “active” (aning started, bound, plugged in, …, depending on the unit type, see below), or “inactive” (aning stopped, unbound, unplugged, …), as well as in the process of being activated or deactivated, i.e. between the two states (these states are called “activating”, “deactivating”).

A special “failed” state is available as well, which is very similar to “inactive” and is entered when the service failed in so way (process returned error code on exit, or crashed, or an operation tid out). If this state is entered, the cause will be logged, for later reference. Note that the various unit types may have a nuer of additional substates, which are mapped to the five generalized unit states described here.

The following unit types are available:

+   1. Service units, which start and control daemons and the processes they consist of. For details see (5).
+   2. Socket units, which encapsulate local IPC or network sockets in the system, useful for socket-based activation. For details about socket units see (5), for details on socket-based activation and other forms of activation, see (7).
+   3. Target units are useful to group units, or provide well-known synchronization points during boot-up, see (5).
+   4. Device units expose kernel devices in systemd and may be used to implent device-based activation. For details see (5).
+   5. Mount units control mount points in the file system, for details see (5).
+   6. Automount units provide automount capabilities, for on-demand mounting of file systems as well as parallelized boot-up. See (5).
+   7. Snapshot units can be used to temporarily save the state of the set of systemd units, which later may be restored by activating the saved snapshot unit. For more information see (5).
+   8. Timer units are useful for triggering activation of other units based on timers. You may find details in (5).
+   9. Swap units are very similar to mount units and encapsulate more swap partitions or files of the operating system. They are described in (5).
