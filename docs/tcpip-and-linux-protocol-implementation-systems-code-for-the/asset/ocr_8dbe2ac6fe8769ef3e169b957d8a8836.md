/*
* (dat, protocol) are always specified,
  so that we are able to hash them.
  * src mask may be exact, or be wildcard, so that
  we can keep a hash table one wildcard entry.
  * source port (or flow label) is important only if src is given.

IMPLEMENTATION.

We use two level hash table: The top level is keyed by
destination address and protocol ID, every bucket contains a list
of "rsvp sessions", identified by destination address, protocol and
DPI="Destination Port ID": triple (key, mask, offset).

Every bucket has a small hash table keyed by source address
(cf. RSVP flows) and one wildcard entry for wildcard reservations.
Every bucket is again a list of "RSVP flows", selected by
s address and SPI="Source Port ID" here rather than
"security parameter index": triple (key, mask, offset).

NOTE 1. All the packets with IPv6 extension headers (but AH and ESP)
and all fragmented packets go to the best-effort traffic class.

NOTE 2. Two "port id" seems, rfc2207 requires
only one "Generalized Port Identifier". So that for classic
ab, esp (and udp, spi) both spi could coincide or one of them
should be wildcard.

At first sight, this redundancy is just a waste of CPU
resources. But DPI and SPI the possibility to assign different
priorities to GPIs. Look also note at 4 about tunnels below.

NOTE 3. One complication is the case of tunneled tunnels.
We implement it as follows: if the first lookup
matches a special session with "tunnelhdr" value not zero,
flow doesn't contain the true flow ID, but the tunnel (1...256).
In this case, we pull tunnelhdr by restart lookup
with tunnel ID added to the list of keys. Simple and stupid spi(8)
It's enough for PIM22 and IP.

NOTE 4. Two GPIs make it possible to parse GRE packets.
Fe. DPI can select ETH_P_IP (and necessary flags to make
tunnelhdr correct) in GRE protocol field and SPI matches
GRE key. Is it not nice? spi(8)
