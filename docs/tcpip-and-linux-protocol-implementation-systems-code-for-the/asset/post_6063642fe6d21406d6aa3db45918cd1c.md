**Layers: Physical, network and application.** Inevitably, the complexity of such a system of components is best understood by introducing some systematic way of categorizing its modularization. The natural way that designers tend to do this is by *layering*. In a network, it is clear that the physical link and its framing rules for packets that the standard and network interface card dictate is a given. The Internet Protocol **has to be fitted on top of this**. By this we mean that the Internet is an overlay on a service made out of lots of differing kinds, and in general, users of the Internet Protocol layer don't really care what the details of the link layers are. This is an example of *information hiding*.

The idea of layers occurring in programming as well as in design. When a design is layered, however, this does not mean that the implementation must strictly follow the same boundaries. For example, the application may actually care what the size of the physically largest packet a link can transmit.

**Names, addresses, routes.** These are confusing concepts—in a way we often define examples of these in the context of one layer, to redefine them differently at layers:

- **A name** tells you what it is: e.g., "Crowcroft" or "Gower".
- **An address** tells you where something is: e.g., "192.168.1".
- **A route** tells you how to get there: e.g., "go in the stairs, up left, and stop."

**Security.** Security is generally concerned with defending against attacks such as denial of service. It is hard for software to defend against physical attacks. However, we can provide methods to reduce the chances of logical attacks such as theft of identity, or privacy cannot be completely ruled out, but there are a variety of techniques for making it expensive (i.e., computationally hard). The ones implemented in Linux kernel and supporting software relevant to lower levels are discussed in Chapter 10. However, we would advise users to read a good book on security (for example, firewalls) before embarking on any.

**Accounting.** If you are providing a service, you may want to account for usage. There are few tools for doing this at the microscopic level—one advantage of Linux is that it is relatively easy to build on these and accumulate statistics.

# 1.3.1 A Note on Programming Languages and Methodologies

Most of the Internet is programmed in C. This is especially true of lower-level protocols and systems. Most operating systems today are written in C, although many applications are programmed in higher-level languages. There are several reasons for using C. Partly historic: previous systems were written in assembler, but this is completely non-portable and extremely hard to maintain. C reveals enough of the underlying hardware to allow the programmer access to specific memory locations and structures, as well as interfacing to assembler, while offering enough high-level tools (functions, modules, and so on) to retain some degree of maintainability. It is possible to write highly portable C, but it is also possible to write non-portable code. It is also possible to write very obscure code (there are competitions!), but luckily, the influence of several decades of experience has led to programming styles and conventions that make C code quite easy to comprehend.

These styles and conventions vary from community to community; however, in the Linux system there are some fairly strong agreements on how code should be written, laid out, and integrated. One of the key advantages of open source approaches to systems development is that people learn by examples. The Linux kernel benefits additionally from strong central control over what is allowed into a release. A different model pertains with the large number of Linux distribution companies now in the world, where it is up to those organizations to maintain consistency.

More importantly, in general over the last few years, the practice of object oriented (OO) design and programming has become widespread. There was a trend towards C++ or even Objective C for a while, but these proved more complex than necessary. For application (and high-level network) programming, Java is now in the ascendancy. However, the techniques can be applied manually in C, and we will see that this is widespread throughout the Linux kernel code. In fact, there is a school of thought that it has always been the case amongst good programmers to use patterns in OO programming.

For example, for a modular kernel, it is required to package code with a standard set of methods (or functions and arguments and their types), and little means of modifying the internals of that module—this allows for device drivers, protocols within a layer, and even larger units of operating system functionality such as filesystems and schedulers. At design time, this leads to safer code. At implementation time, it leads to extensibility. At build (link) time, this allows the system to be statically configured. Finally at run time it allows a system to be configured dynamically as needed. This means that the system can be as small as needed. It has a side effect on the design, which is, usually, systems as this are highly regular. That means that once a programmer has learned how to do something, it represents a general lesson.

In kernel code, logging is absolutely essential. A single line at the start of the module is only enough if there are indications throughout the changes referencing the author too.

**Automatic processing.** There are a number of programs that are used to process code (e.g., generating call graphs). Some of these rely on conventions for placing open braces at the start of a line, for example.

**Maintenance.** Code should contain enough comments that you can figure out its basic operation quickly, but not so many that you cannot find the actual statements. It is conventional to comment code in English. The bulk of Linux code is written by people who choose names for variables communicate use and function (to some extent, scope).

**Portability.** Be pedantic about types. Be extra pedantic about commenting the mapping between data structures and wire formats. Be clear about byte order and alignment of fields.

**Risk.** There are no reasons for deliberate obfuscation of statements—for example, if you have a complex logical expression, bracket it to make it clearer rather than relying on (possibly incorrect) memory of operator precedence.

In an ideal world, all code is accompanied by separate documentation as well, written at the same time as the code (e.g., as dictated by the extreme programming style). Such documentation should include examples of use and examples of test output. The world is unfortunately less than 100% ideal.
