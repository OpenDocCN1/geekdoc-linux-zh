# 5.4 Device Level, Bottom Up, One Level Up

Moving up one level from generic interrupts, we take a look at network device support.

For years, operating systems have provided a standard abstraction/interface for classes of device, so that higher-level operating system (and application) software can be common across all devices. UNIX traditionally divides devices into two classes, (low rate, interactive, and serial line, typically) and block (disk, display, and so on). It's possible to squeeze network devices into the block mode paradigm, but its messy. Linux adds a third type of device—a network. This is discussed in some detail in Chapter 2.

Typically, a device has a name to place it in the file namespace, but also has an identifier: UNIX has major/minor numbers. A driver is a structure (class) with a set of entry points (functions/methods). At boot (or module load) time, the device is initialized by calling its init() function—this resets the device, installs all relevant interrupt handlers, and so on. It then registers with the OS. The rest of the time, we manage I/O with a device with open, close, queue_xmit, and interrupts/notifications.

# TCP/IP and Linux Protocol Implementation

Device driver details manage specifics like:

- Bus interface/memory/I/O address of device registers
- DMA and timer chip use
- IRQS, and so on

Notice the asymmetry of input and output—output is requested, whereas input arrives unexpectedly (i.e., at this level we could never sensibly implement a device driver by polling Input results in packets being queued, and netif_rx() called to find out which higher-level protocol function to dispatch.

The traditional cach interface is via the ioctl() call. This allows one to set and get a number of network-specific device control parameters—for example:

- Link up/down
- Broadcast address
- ARP (see Chapter 6)
- MTU
- Statistics, and so on

We can see this by saying ifconfig <dev>. The command netstat -i will tell you what devices you have. We look at this further in Chapter 6.

Address resolution is either done algorithmically, through a table, or through a helper that runs the Address Resolution Protocol (ARP). ARP is invoked when the IP address is known but the destination layer (strictly, Media Access Control) is unknown. ARP is demultiped in netif_rx() for input frames—it makes sure it enters table and maintains these so that they expire when not used in a timely fashion. It can be overridden by configuration management.

In general, output is multiplexed by (IP, or other). Output demultiplex, by looking at and using the right higher level (from inside netif_rx()), from input discussed, buffer disciplines are asymmetric: for output, the high level allocates buffer and a stack of routines, and for input, the low level has a pool, hands up to the upper level, which, when done with buffer, frees. What if the packet is not for us? Basically, it will bridge, route or intensive (it requires the Ethernet interface to be in promiscuous mode, which is expensive). We don't discuss this further.

Routing is a built-in part of Linux and requires forwarding table, as is discussed in more detail in Chapters 8 and 9. Discard is often the most common case and requires efficient handling, mainly from the implementation of network monitoring and firewall mechanisms, which are discussed in Chapter 10.

Most hardware (at the driver level) batches packet handling to reduce interrupt count to less than one. This is good for performance, although results potentially in bursts of packets arriving at the higher levels (or forwarding). This doesn't cause problems often in the common cases, and can be controlled using network schedulers and shapers, as discussed in Chapter 9.
