# 4.4 Using the Socket API

Communication between separate processes involves moving data between one address space and another—in former times, this was known as crossing protection boundaries. Because of this, the various communications facilities are named under this confusing use of the word domain (it has *nothing* to do with the domain name system at all).

The example C code in Figure 4.2 illustrates the use of INET domain socket, with stream semantics. This basically makes use of TCP code in the kernel—in the example here, communication is between a parent and child process, so the socket is simply being used to replace a pipe.

**Figure 4.2** Socket programming i—main: pix/sock.c.

```c
#include <stdio.h>
#include <sys/types.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <netdb.h>
#include <errno.h>
extern int errno;

int child_pid; /* Handy handle */

main(int argc, char *argv[])
{
    long host = 0;
    short port;

    if (argc < 3) {
        printf("What host (%s:%d)?\n", host, port);
exit(-1);
    }

    host = inet_addr(argv[1]);
    port = (short)atoi(argv[2]);

    if ((child_pid = fork()) == 0) {
        client(host, port); /* Child */
    } else {
        server(port); /* Parent */
    }
}
```

The fork() call sets up the second process (child) so that now have two processes, one of which is a client, the other a server. They then set up a connection-oriented socket to communicate with other.

**Figure 4.3** Socket programming ii–client: pix/sock.c.

```c

short port;

    char buff[80];

    where.sin_port = htons(port);
    ret = connect(asock, &where, sizeof(struct sockaddr_in));
    check(ret, "connect");

    while ((len = read(asock, buff, 1)) > 0) {
```

The client side is the proactive end that takes the initiative and opens the connection. The server side is (hopefully) already sitting there (listening) for an inbound connection, which it accepts.

**Figure 4.4** Socket programming iii-server: pix/sock.c.

```c
server(port)
short port;
{
    char buff[80];
    int len;
    int status;
    int asock, ns; /* Socket descriptor thing */
    struct sockaddr_in where;
    int thing = sizeof(struct sockaddr_in);
    asock = socket(AF_INET, SOCK_STREAM, 0);
    check(asock, "socket");
    where.sin_family = AF_INET;
    where.sin_addr.s_addr = INADDR_ANY; /* System Knows *
    where.sin_port = htons(port);
    status = bind(asock, &where, sizeof(struct sockaddr_in));
    check(status, "bind");
    status = listen(asock, 1);
    check(status, "listen");
    ns = accept(asock, &where, &len);
    check(ns, "accept");
    while ((len = read(ns, buff, len)) > 0) {
        write(2, buff, len); /* Write to terminal */
    }
    shutdown(asock, 0);
    printf(stderr, "\nParent gone\n");
    wait(status); /* Wait for child to finish */
    exit(0);
}
```

## 4.4.1 Polling a Socket

It is often useful to check if data is available on an interface without actually waiting until it is. This is known as polling. The way it is done from the UNIX filesystem and socket API is via the select() system call. This takes a mask parameter that allows one to poll several file descriptors simultaneously. This is very useful for programs that wish to provide the appearance of concurrent user interface and network I/O, for example, network management programs, or networked graphics.
