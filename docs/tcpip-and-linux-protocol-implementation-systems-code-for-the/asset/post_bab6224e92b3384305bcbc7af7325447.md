
## 2.2.3 MultiDevice

Modern computers support a massive range of devices. As well as traditional keyboards, screens, and storage devices, we have a range of network interface types, including fixed and wireless, and a number of multimedia devices (audio, video capture, 3D, and so on).

At the lowest level, the operating system needs to manage input and output from devices. There is a surprising amount of commonality in the functions required to match the OS to different hardware. A large percentage of the code associated with any operating system is device driver. Device drivers hide the specifics of a particular hardware and provide standard programming interfaces to the application. Linux supports the concept of modules, which allows on-demand loading of code for devices.

All UNIX systems identify the kind of device by a unique number called major and minor number. Major numbers are allocated by authority, while minor numbers are allocated as needed (e.g., through configuration). Linux divides devices into three basic classes:

- Character. These devices are typically serial lines (traditionally for keyboard-type input but also parallel interfaces, mouse, sound cards, frame buffers, and so on).
- Block. These are for storage-type devices (floppy, hard disks, and optical disks). Most file systems support these.
- Network. This is a special case where Linux differs from other systems in its treatment of device type, as networking is a main topic of this book, discussed in detail later.

The critical difference between character and block devices, and network devices, is that the network device usually has another intelligent end rather than just dumb computer.

What makes devices similar? The ability to read and write data to a device is common. What makes devices different? A number of things ranging from performance (data rate, latency, and so on), and most importantly management complexity.

## TCP/IP and Protocol Implementation

As discussed before, operating system services are layered. Applications access files, which reside within user space, but make use of block devices to access storage devices. Applications may carry out interprocess communication via protocols that (largely) reside in kernel space, but make use of network devices to access local area networks. The exception to this pattern is that applications wishing to interact with users via keyboard and screen generally use frame buffer for output and input directly, as this is generally done by the system which requires a special process to manage the frame buffer.

Now we introduce the idea of interrupts. In the context of I/O, interrupts are no less important in computer science. Interrupts are concerned with associating one end of a channel with a short descriptor. In the filesystem, this is done by mounting the device which attaches to the root of the hierarchy. In the driver namespace, a driver is associated with a specific device through major numbers. Processes are associated with a process identifier through the /proc mechanism. In the communications world, we associate a channel with endpoints through some addressing system, of which later.

At the lower level, device drivers may use a number of different programming techniques to move data to and from memory. The simplest technique is called polling and depends on continuous access to device to see if it has data ready. Few devices work like this in real systems. More commonly the device has a modicum of intelligence and can use interrupts to notify the processor that data is ready. Processor families have different hardware techniques for providing interrupt-handling facilities. Typically most systems provide some number of channels; on the PC these are known as interrupt requests, or IRQs. There may be more devices than IRQs, in which case the devices have to share interrupts and a processor has to be programmed to distinguish which device interrupted. Each IRQ is associated with an interrupt service routine (ISR). Typically the operating system installs code at a set of addresses is where the interrupts are vectored to.

## Introduction to the Linux Operating System

Think of an interrupt as an unsolicited procedure call with a few side effects. These side effects are important (they involve changing processor mode from user to kernel, example). We will see later how they work and how we synchronize processes, kernel tasks, and interrupt handlers. Many devices have enough intelligence to move data to and from memory via controllers—this is direct access which is typically set up by device drivers to take more work away from the CPU and to get some measure of parallelism between normal work and I/O work. Most faster (block and network) devices work this way.

Linux has one more trick up its sleeve with regard to interrupt handling. Interrupt service routines have a critical time when they must respond to a device, at least initially. However there may be a lot of housekeeping work which can be done with more slack. Linux ISRs schedule the later work to be dealt with what is known as a bottom half. The bottom half routines often involve moving data to application space, rescheduling processes and so on. A list of bottom half routines is scanned, and any ready routines are called explicitly in the last stages of system calls. In symmetric multiprocessor Linux, bottom halves have been re-engineered using a more general mechanism, which we'll look at later on.

The fact that an interrupt changes processor mode (typically from user to kernel) and therefore allows code in an ISR to access privileged resources makes it the ideal way to implement system calls. System calls have also been known as traps for this reason: they are like a trapdoor down the user space into the cellar that is the kernel. Most UNIX implementations vector all the system calls through one IRQ and then use a jump table to access the actual system call code. System calls rigorously check the validity of parameters (e.g., data buffer addresses and lengths thereof, for read and write must reside within the user's process address space). System calls may de-schedule a user process if necessary.
