
## 2.2.1 MultiUser

Since then the 1970s, there has been a saying that "Everything in UNIX is a file." What is meant by this is that the standard abstraction for any object on the system is provided by the overloading of the concept of a file.

Of course, normally, files are stored on disk. Files are organized in filesystems (and Linux supports a few different ones) consists of a way of organizing storage devices (file-stores), a way of organizing files within a naming hierarchy (directories, files within directories, and so on), and a way of formatting data files within files (UNIX has traditionally kept this as simple as can be). UNIX unifies the view of a number of objects in the system by using the filename space to name, and therefore provide access to, devices and devices (in modern UNIX systems) processes, as well as to simple stored data. This makes system programmers' tasks easier—there are fewer interfaces than in other families of operating systems. We will see throughout how the book makes access to the communications facilities straightforward. We also see that in some cases, this unification comes at cost—sometimes the analogy between a file and some other type of object stretches the use of the system call interface in some other odd ways, and this shows in the use of some of the parameters.

An important aspect of the filesystems is the identification of ownership of files. In any, whether it is a normal plain file, a directory, a handle on a device, or even a process, there are fields that show the ownership of the file and the permissions associated with different users (user, group, others). This data is stored with files on disk, and is kept in memory when a file is opened by a program—the data structure that stores all is called an inode. At the root of all things, all files have an inode number.

Traditional interaction between the user and the system was via command line interfaces (the shell). Of course, in modern systems, we expect to use a graphical user interface (GUI). The underlying system for this on UNIX is X-Windows, which for 20 years now has provided networked graphical interfaces to programs running on remote systems. GUI comes into play when multitasking systems—it is common for many classes of user to combine and overlap a number of loosely related tasks (e.g., editing and previewing a letter, or programming, debugging and viewing documentation, or browsing the net and taking notes). A windowing system combined with a tasking system is essential to the modern user. Let's look a bit further at tasks.

## 2.2.2 MultiTasking

Main Street shops sell computers that execute nearly 1,000 million instructions per second. Yet of the time, the user is sitting in front of his computer (or holding his laptop) thinking deep thoughts about what to type next. In the meantime, the computer might well get on with something useful. In the early Introduction to the Linux Operating System days of computing, people would hardwire it into the operating system some useful in the idle loop such as computing the next few million decimal places in π. Nowadays, we do the same thing more flexibly—for example, screen savers may download data from the radio telescopes around the world and find some meaningful signal in the noise (Search for Extraterrestrial Intelligence, or SETI). Multitasking is the ability of the operating system to provide the illusion of serving many masters at once. The illusion is easiest to see as a user you perform some background task such as printing. The two tasks, a foreground one (e.g., an editor) and a background one (e.g., printing) are carried out by the system by alternating between the programs, running part of one, part of the other, and so on. Programs that have started and not finished are known as processes. All processes have a process ID.

A system that has enough cycles per second to fool a user in this way, and enough memory to hold the code and data for multiple processes, is relatively simple. The key idea is that a process can be described by taking a snapshot of the state of the process and the code at any instant (between one instruction and the next)—this snapshot is known as the context. The operating system can save the context of a running program into some special location in memory, and switch to another process by restoring its context—this is just a case of loading all the registers with the last values that this other process had, and setting the CPU’s program counter to the next address to start getting code. From the part of the operating system that carries out this context switching is handled by the scheduler. When there are several processes to choose from, the scheduler may make use of all sorts of bookkeeping data to base the decision on Linux. This can be very useful for specialists such as real-time systems (e.g., in physical process control systems in factories, where time is of the essence).

Multitasking is really essential for providing a clean programming abstraction for an open platform where users can run different applications in a windowing environment. Multitasking is also non-optional when building network servers. Nowadays, a server (e.g., a Web server) may receive many requests nearly simultaneously, and will need to schedule dealing with servers in many different ways. There are several ways that can be done, but a multitasking system is really one of the simplest. We will see later on in this book that there are reasons why general multitasking is sometimes a little too slow for high-throughput web serving.

General purpose servers are very common in the networking business—they provide a number of networked services such as network time (via Network Time Protocol) to synchronize the clocks on a remote computer, network printing, email, logging, file serving, and so on. The general term used for programs that provide useful services on a UNIX system is daemon.

Processes are associated with users, just as files are. In UNIX, processes are created in an ancestor-descendant way from a primordial TCP/IP and Linux Implementation process that starts when booting. Children inherit parent's identity. To change identity, a process may set its user ID, although this sounds draconian, but is in fact, quite general. The kernel also keeps track of time. For example, the filesystems provide a hierarchical organization of directories. This is useful for users and applications as a navigation aid. To keep brief, the current working directory is part of the state associated with a process. In keeping with the simple (but effective) approach to control, UNIX allows a process to change its view of the root of the filesystem. Processes start with three standard channels to the outside world: input, output, and errors. These are associated with the controlling terminal or tty (of course a process is at liberty to detach from a controlling terminal so that it can run in background). A group of processes controlled by the same terminal are managed together. In networking, since one can manage the state of the group, particularly through the use of signals. Signals provide a way for the operating system to notify of a process an event. This originates from the requirement for raising exceptions (software interrupts) in a task: for an extreme example, many UNIX systems can use a signal to all processes when the power is about to die. Nowadays, signals are used for many asynchronous communications, alongside more normal file, pipe, and socket communication tools, of which we will see more.

The kernel and user process may use signals to communicate (albeit abruptly) with another process. If a process wishes to communicate in a civilized manner, with another process on the same machine, there are several choices. If the programmer wants a record of the communication, the simplest technique is to use files. UNIX does not restrict the reading and writing of files by default to a specific process, but there are tools to control access to files and provide synchronization. A more common technique is the use of a pair of file-like channels, called a pipe. Finally, the programmer might use full-fledged communications channels as a socket, which can be used for purely local, or inter-machine, inter-process communication.

To summarize, we can take the view from below as the operating system context, or the view from above, application/user context. The viewpoints are like a dual personality, or the subconscious and conscious.¹
