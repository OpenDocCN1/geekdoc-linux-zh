TCP and TCP-like transport protocols, we can imagine using loss (e.g., via RED; see Section 9.10) to provide some level of control of best effort, achieving more scalable and accurate traffic management and congestion control.

**Packet size.** Path MTU discovery (see Chapter 6) reveals the smallest maximum transfer unit that the links on a given route support. The application may use smaller packets, but using larger packet sizes than the MTU (incurring fragmentation) is regarded as a bad idea. The users' packet size choice, and the MTU, may be used by routers to help with buffer allocation, and are also vital parameters to the delay evaluation process in admission control.

**Data rate.** This is the key performance parameter, but how can we specify this for applications that are not a fixed (constant bit rate) rate? Data applications are inherentlyy. Voice and other multimedia sources use variable-rate compression and silence suppression, so they do not send at a single rate. How do we capture the rate information?

We can specify the mean data rate, and the peak rate, and the length of time a source spends sending at the peak rate. How do we then allocate resources? If we allocate at peak rate, we waste resources when an application sends slower. If we allocate less resources, we take a risk.

Real-time flows may be a constant bit rate, but can also be a variable bit rate. Given an application flow is made up of a number of application data units (ADU) and we can specify a rate in terms of these. We would like the API for this to be both application-friendly as well as technology-neutral.
