We can trace the path of this request through the Linux kernel to the IP layer, and then the response from the IP layer back to the application.
The socket is first created and connected (udp_connect, see Figure 7.6), which as this is a datagram socket, does not result in any traffic across the network, but a modification of the kernel structures. Specifically, a routing table entry is created for this destination address and this entry is added to the socket structure.
The application library now builds a DNS request packet and passes this to the kernel with the sendmsg call. This is passed on udp_send in net/ipv4/udp. One of the operations of sendmsg is the calculation of the UDP checksum. This checksum provides for rudimentary error checking at the receiver, and is calculated over the entire UDP packet and also some fields from the IP layer (a fake header) (see RFC 768). The checksum value is the one complement of the sum of all the 16-bit words to be checked. This is inserted into the checksum field. At the receiver, the stack can simply add the values together, and an all ones indicates a correct packet. The packet is passed to the datagram (IP) layer via the ip_build_xmit() call. Note that the call to ip_build_xmit()'s second parameter is a function pointer. This pointer can take one of two values depending on whether the packet's checksum is to be calculated or not. In either case, the purpose of this function is to copy the data from user space directly, and if necessary calculate the checksum as the data are copied. A further optimization here would be to copy the data from user space directly to the interface adapter card.
