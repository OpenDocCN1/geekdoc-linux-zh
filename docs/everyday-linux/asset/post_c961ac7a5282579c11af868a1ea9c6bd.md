
So if I want to unmount the drive which I just mounted previously, I simply type `umount /dev/hdb1` or `umount /mnt/win`. It’s that easy.

## Killing Processes

All programs have the potential to “hang”, that is, to stop running or freeze. In Linux, there are two ways to take care of this problem. The first is to right-click the program in question and then click on the option labeled “nuke.” This sends a “kill” to the program (which is running as a *process*), and it terminates immediately.

The second way is to do this from the command line. We must use two commands to do this, however. The first is the `ps` command. This is an older command (which you can kind of tell because it’s so short) that stands for “list processes.”

Each time you run a program on your computer in Linux, it is assigned a number. This is known as its process number, and when you do a listing of all the processes using the `ps` command, you will see a list of numbers followed by the commands that are running. This list might look something like this:

```
PID      TT     TIME     COMMAND
11008    p1     0:00.12  -bash (bash)
11037    p1     0:00.21  slirp -P
11040    p6     0:00.12  -bash (bash)
11139    p6     0:00.02  ps
```

The PID is the process ID number. TT is an abbreviation for TTY, and it tells which terminal you’re on. (I have processes running on tty1 and tty6.) STAT tells the status of the program running—you really don’t need to worry too much about this, but the man page for `ps` will tell you what the letters and symbols mean. TIME is the CPU time that the process is taking up, and COMMAND tells which command is running.

For example purposes, let’s suppose that my `slirp -P` is hung and will not terminate using normal termination commands. To kill it, I would use the `kill` command. The syntax for the `kill` command is as follows: `kill [ -#] [ pid]`. You don’t have to include the `kill` level if you don’t want to, but it does serve a purpose, which we’ll get to after we kill the `slirp` process. The pid is the process ID number; in this case, the pid is 11037. To kill the process, then, we’d simply type `kill 11037`. The process will then terminate, and `slirp` will no longer be running.

The numbers that are associated with the `kill` command (the `[-#]` in the syntax) are used as “termination signals.” A termination signal can tell a process how to terminate. In addition, termination signals can “hit harder” than a regular `kill` command, so if you have problems getting a process to terminate, you can use a stronger termination signal to kill the process.

The most commonly used termination signal is `-9`, which is used to kill not only the process that you specify, but all processes that it spawns; in other words, you are killing a parent process and its children. In my process list above, which I gleaned from a telnet session to my ISP, you noticed I was running `bash` twice. When you run a command interpreter, you also run programs from the command interpreter. So a child process of the `bash` shell that I’m running might be the slirp command below it.

To kill both of them, I would type `kill -9 11008`. This says, “kill the process ID 11008 and all of the processes spawned underneath it.” This includes the slirp process, 11037.

In addition to using these two commands, `ps` and `kill`, you have at your disposal two other programs—`top` and `gtop`. `Gtop` is the `GNU` version of `top`, and it runs graphically—it’ll probably be easier to use, and you’ll find that it is likely more convenient than using the command line version.

`Top` is little more than a glorified version of `ps`. It will list all of the processes on the computer that are presently running. You can look at individual users or all of the users at once if you so desire. You will be able to kill processes, *renice* them (change their priority), and see how they draw upon system resources. Both `top` and `gtop` are very useful tools, and you’ll probably prefer using them to play with processes instead of `ps` and `kill`.

## Making Minicom Usable for Everyone

One of the first things we mentioned about using the command line was in Chapter Five, when we mentioned `Minicom` as an alternative connection program for users who had a text-based Internet or BBS connection. Unfortunately `Minicom` isn’t usable by anyone but `root` when you installed Red Hat Linux. If you’ve got a lot of users on the system or you just want to be able to dial into a text-based connection, you should follow this procedure to allow everyone to use `Minicom`.

To do this, you must be `root`. If you’re using your personal account, you can simply use the `su` command to become `root`.

The first thing you should do is type **minicom -s** at the prompt. This tells Minicom to start up in a setup mode. You need to save the settings in a .dll file. The text menu that appears has this option available. Use your arrow keys to move through the list, and when you read the item that says, “Save config as a .dll” press the enter key. You can then exit Minicom.

The next step is to make sure that all users can read and write to the modem device. To do this, type in **chmod 766 /dev/modem** at the prompt. This tells the computer to allow everyone to read and write to the modem device and gives full permissions to the owner (who is root).

Then type **exit** to leave the superuser’s environment. You should be back to your regular user. To make sure, type **whoami**. Your username should appear. If it doesn’t, type in exit and check again. Repeat this process until your own username appears.

Then you should be able to run Minicom, either by typing in the command **minicom** at the command prompt or by running it from the main menu’s “Internet” submenu.

## Why the Command Line?

Since most of this is still probably not familiar to you, you might be asking yourself the purpose of the command-line interface. Aside from the obvious reason that the X-Window System requires it to operate, of course, the command-line interface is quite useful.

The more familiar you get with the command line, the more efficient you will be at systems administration. You will also be able to correlate actions in the X-Window System to the same commands on the command line (finding files, for example, or editing some of your network settings).

The command line is more technically oriented than the standard point-and-click method of adding users or editing the system profiles, but when you become proficient at using the command line, you’ll find that it takes you less time to make certain changes with the command line than it does using the X-Window System.

Another good reason to have the command line available is that it is a fallback measure if the X-Window System fails. On rare occasions, you will find a bug somewhere in the system that might temporarily disable your graphics cards ability to render the GUI environment of the X-Window System properly. Usually just typing startx will fix the problem, but if you have to reboot or edit a configuration file located in the /etc directory, you should know how to do it.

Also, we shouldn’t forget that there are some commands which cannot be run solely from the X-Window System and must be run from the command line (such as Xconfigurator, or some of the console multimedia programs).

## In Closing

It’s also important that you feel comfortable with experimenting with the command-line interface. You can even create a test account for experimentation purposes; as long as you don’t use the root account, you can’t really damage the system severely.

Experimentation is one of the best ways of learning how to use your Linux system. Some procedures are cookie-cutter in nature and require no improvisation; others, however, may require a more creative attack, and you can always experiment a little bit to see how things really work.
