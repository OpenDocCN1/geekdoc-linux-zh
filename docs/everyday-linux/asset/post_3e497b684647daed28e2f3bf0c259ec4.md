
That command will give the owner read and write permission to the file (6), his group read permission (4), and everyone else no permission (0).

It will take some practice to become fully used to using numbers for permissions, so we'll supply you with a list of commonly used permissions for handy reference when you need it.

## Permission List

Here's a list of commonly-used permissions:

- **700** User has all permissions (read, write, and execute), and no one else has any permissions for the file.
- **744** User has all permissions, and everyone else can read the file.
- **544** User can execute and read the file, but not modify (write to) it; everyone else can read the file. This is a permission usually used with scripts that you won't be changing.
- **644** User can read and write to file, all others can read. This is probably the most common setting, and it is usually the default setting for newly created files.
- **600** User can read and write to file, no one else has any permission to the file.
- **775** User and group can read, write, and execute the file; everyone else can read and execute the file. This is useful for maintenance scripts which need occasional revision.

Now that we've looked at changing permissions, we'll also look at changing groups and the ownership of a file. Sometimes this is necessary to both protect your files and make sure that they reach the intended audience.

## Changing the Group Ownership of a File

The stated purpose of myfile was a memo to the administration group, yet its grouping is in wheel. To ensure that everyone in the admin group (which is the administration group) can read the file, we need to change the grouping of the file.

To do this, we use the chgrp command. Right now, the file listing for myfile should look something like this:

```
-rw-r---- emetsger wheel myfile
```

We need to change the group from *wheel* to *admin*. The syntax for the command we're going to use is as follows:

```
chgrp group filename
```

This is a fairly easy command to use, as you can see. Simply type in the command (chgrp), then the group to which you want to give the file, and then the filename itself. In our example, this would be *chgrp admin myfile*. An updated file listing of *myfile* would look like this:

```
-rw-r---- emetsger admin myfile
```

Now that we've changed the grouping, it might be convenient to change the owner of the file, as well. This will prevent you from making undo modifications to the file, and it can also, as our example will show, make the file look as though it came from the system administrator (that is, root), rather than from a regular user account.

## Changing the File's Owner

To change the file's owner, you use the *chown* command. The syntax for this command is *chown owner filename*. You would use this command to give a file to another user.

This is useful for when you create those memos yourself that should appear to be from root. In our example above, you should type the command

```
chown root myfile
```

to give the file to the root user. This means that you will no longer retain ownership permissions of the file: this is not something you can undo unless you change the ownership of the file using the super user.

That brings us to the next thought: using root to change the ownership of a file. When you do random systems administration tasks, you will find that you'll create a number of files, remove others, etc. One such task, often, is cleaning out e-mail boxes that have gotten too full. Text-based e-mail programs won't be able to open the box since there are too many messages, so you'll be forced to delete the box and then create another. If you create a mailbox that is owned by root, however, the user you create the mailbox for will not be able to access it. You have to change the ownership of the mailbox from root to the owner.

Some of these administration tasks may become monotonous and dull, which is where the next topic comes into play. You can automate certain tasks using what are known as *shell scripts*.

## Shell Scripting

Fans of the batch file in DOS will be pleased to know that they can recreate a few good memories using *shell scripts*. For those of you less familiar with the good old days in which DOS was king and all else was subversive, let’s take a small look at batch files.

You are probably familiar with the autoexec.bat file in your C:\ directory if you run Windows. This is a file that is automatically executed (hence "autoexec") every time your computer starts. Its analog is the file .bashrc (or whatever else your shell executes when you log in). What the autoexec.bat file does is run a few programs or checks when you start your computer. It might install a terminate-stay-resident program (a TSR program) that will check for viruses or a program called “doskey” that will allow you to page through a list of commands you’ve typed in. It may also make sure that your file listings are sorted every time you type in the dir command.

However, you can also create your own batch files that will perform other tasks. A popular one was called “move.bat.” Moving a file involves copying a file from one location on the hard drive to another and then removing it from the first location. MS-DOS versions before 6.0 did not have a move command; you would have to copy a file from one location to another and then delete it manually. (The move command copies a file and then deletes it.) Some users, myself included, found the lack of a move command to be slightly annoying, so we created a batch file that would perform the same tasks.

You can do the same thing in Linux. This is called *shell scripting*. The shell scripting language is very powerful and can be complex. However, we’ll create a simple shell script right here.

First, make sure that you’re using a terminal. You’ll see the terminal prompt noted above, though it will be your username in the prompt, not mine.

The second item of business will be to create a directory to store the scripts in. Type `mkdir bin` at the prompt. If you type in `ls`, you will notice that your file listing now has the `bin/` directory in it.

Then type `pico` at the prompt.

This is your first time to see a text editor in the command-line interface. This text editor is known as the Pine Composer (pico for short). It is a quite user-friendly text editor, at least in comparison to others such as vi and emacs. If it seems sparse and difficult to use, don't worry. We'll be navigating it together.

Type in `ls -FC` in the blank window. This is the command that we wish to execute.

Hit control-x. (This means that you hold down the CTRL key and press the x key. This is often abbreviated as ^X.) A prompt will appear that asks you what you want to call the file. You should type in `bin/l`. When you press enter, it will save the file and exit the Pico editor.

Now you're confronted with the prompt again. Type in `l`. You'll see the product of your first shell script—you'll see a file listing that is in three columns with files and directories clearly demarcated. It's a handy file to have. When you're done looking at the results, type `exit` to quit using the terminal.

This is your first taste of shell scripting. What we've done is, in reality, very, very simple, and not too useful. It would be far easier to edit your .bashrc file and include the line `alias ls='ls -FC'`, which will create an *alias*. An alias is simply a substitution of sorts; every time you type in "ls," the computer will substitute "ls -FC" in its place.

However, now you can see that you can play with shell scripts. Look in the resources section at the back of this book, and you'll find a few FAQs that will educate you a little more in the field of shell scripting. Shell scripts can become very long and complicated, doing far more than we've just done, so don't pass this off as a little thing.
