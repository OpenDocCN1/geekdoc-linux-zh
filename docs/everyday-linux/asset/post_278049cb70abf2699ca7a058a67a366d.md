
An example command line involving pipes would look something like this:

```
mycommand < inputfile | nextcommand >> output
```

This takes the contents of inputfile and uses them as the input for mycommand. We then take that output and use it as the input for nextcommand and append the results to the file output.

## Running Processes in the Background

UNIX was the first truly multi-tasking operating system. It allowed you to run one program in the background and start another program to work with. This allowed people to find files while editing documents or debug programs while coding another application.

To run commands in the background, you simply affix an ampersand (&) to the end of the line. For instance,

```
find / -name myfile* -print >> filesearch &
```

will search for all files starting in the root directory with "myfile" in the name and print them to a file. By adding the ampersand to the end of the line, you tell the computer to run this as a *background process*. While you're finding the file, you can perform other tasks, such as editing a file or calculating values in a spreadsheet. You might also want to play music while you work; running the mpg123 program in the background will allow you to do this.

## The Command Line in Relation to Your Computer

When we talked about the file system, we mentioned the File Hierarchy Standard as a way of knowing exactly where some files and directories would be located. While there is no prescribed method of establishing a relationship for the command line and your computer, there is a certain pecking order.

Your computer is at the top of the pecking order; it controls how power is distributed and performs the tasks given to it by programs. It is the most basic level of your system. After the computer comes the *operating system*, which provides a way for the devices in your computer to interact with the computer itself. It also allows for outside interaction from you in the form of commands and such. It does this by way of a command interpreter or shell. You interact with the shell using the command line.

The command line is really a function of that *command interpreter* or shell. The term “command interpreter” is a little more descriptive, since what a shell actually does is parse commands so that the operating system can understand them. The operating system will then send them via devices attached to the computer to the computer, which will then perform the requested task, using the operating system and shell to output any results.

You interact with the operating system through the command line either directly or indirectly. The X-Window System, for instance, is dependent upon the shell to execute its own commands. If the X-Window System ever aborts and drops you to a shell prompt, you will notice that there are a lot of commands on the screen (and likely many error messages, too). So even when you’re dealing with Linux through a graphical user interface (GUI) such as the X-Window System, you are indirectly making use of the command-line interface.

You could compare our terminal window access to the command line to the DOS mode or prompt in Windows9x. Unlike Windows, however, Linux makes use of numerous different shells. This allows users to pick which command interpreter they wish to use, and upholds the spirit of customization and choice that the Linux world is founded upon. The default shell used by Red Hat Linux is the Bourne-Again Shell (bash). Others, such as the C Shell (used and developed by C programmers, named csh), the Korne Shell (ksh), the Bourne Shell (sh), the Z Shell (zsh), and more, are used by millions of Linux users worldwide. The three most popular are bash, csh, and ksh.

The difference between each of these shells is how they interpret commands that you send to the shell. Some shells also come with special functions. The C Shell, for instance, is used primarily by programmers who wish to take advantage of its special environment.

You should probably keep using bash until you’re more familiar with how to use the command line.

## Permissions Revisited

One of the more useful commands in Linux is the `chmod` command. It is a program that will change the permissions of any file. We looked at it briefly before in reference to learning the basics of how to use your computer. Now we'd like to examine it in a fuller context.

The reason that we're examining groups and permissions with reference to the command line is because that's the way that most people will modify permissions and groups. It's also going to help you become more comfortable with using the interface.

Make sure that you're in a terminal window. The first thing we'd like to do is actually create a file so that you have something to run some experiments on.

### Creating a File

To create a file, we'll use a text editor like Pico. (Real UNIX enthusiasts will tell you that Pico is a bad editor because it's too easy to use. Real UNIX buffs use vi. I don't recommend it for beginners.) Type in `pico` at the prompt to run Pico. A blank screen will appear with a few commands listed at the bottom and a title of NEW BUFFER at the top. Just type in whatever you'd like. Gibberish will do just fine, especially if your brain has been reduced to mush after too much work with Linux.

When you're finished typing hit `^X` (control-x). Pico will ask you if you want to save the file, and if so, what you want to call it. Use something like “myfile” for the present. That's the filename I use in our examples.

Once you hit `^X`, Pico will vanish, and you will be dropped back to the prompt. Now it's time to start playing with the permissions.

### Looking at the File Permissions

If you type `ls -l` at the prompt, you will get an updated file listing. Among your files should be the new file, and it will probably look something like this:

```
-rw-r--r--  emetmger   wheel myfile
```

Presently, the file permissions are set such that the owner can both read and write to the file. The members of the owner's group, wheel, can read the file, as can every other user on the system.

If you had written a memo, say, to people in the wheel group who were going to be doing some administration work, for security purposes you might want to deny access to users who weren’t in the wheel group.

You can change permissions by two different methods, one using numbers and the other letters. We’re going to look mostly at the number format, not the letter format, since the letters are relatively long-winded. Numbers are far more convenient and, in reality, quite simple to use.

In our previous example using “myfile,” the permissions for our newly created document would be 644. The first number applies to the owner of the file, so the owner has a permission level of 6 to myfile. The second applies to the owner’s group, so the wheel group has a permission level of 4. The third applies to everyone else.

These three numbers are composed by adding permission values for each user. For instance, a read bit has a value of four, a write bit a value of two, and an execute bit a value of one.

Let’s do some math with the numbers 644. A six is composed of two and four (2+4=6); since a two means that you have write access, and four means you have read access, a six means that you have both. The fours are relatively simple; they both mean that you have read access. A zero in any category means that the users in that category have no rights to the file.

### Changing the Permissions

To change the permissions, we’ll be using the chmod command. The syntax of chmod is as follows:

```
chmod permissions filename
```

The command and the filename are relatively easy to decipher. The permissions, on the other hand, will probably give you a little more trouble. Our previous example with myfile suggested that this was a memo that we didn’t want just anyone to be able to read; this means that we need to remove everyone else’s read permission from the file.

What you should type is this:

```
chmod 640 myfile
```
