## Modern FTP clients

Access to an anonymous FTP server with programs as Netscape Communications, gftp (the GNOME FTP client), gmc, and kfm is much easier than with the ftp command: you simply specify the address of an FTP server instead of the WWW address. Please take care to use the correct syntax (here, an example for the RedHat FTP server):

```
ftp://redhat.com
The FTP executes the login procedure for anonymous and displays a list of all files and directories in which you have only access to the requested file.
```

If you do not want to use an FTP server as anonymous, many FTP clients recognize the following syntax:

```
ftp://server@username
Subsequently, you are automatically prompted to enter your password.
```

## 9.7 telnet and rlogin

telnet and rlogin are amongst the most impressive tools. They allow you to work on a remote computer as if it were standing in front of you. This obviously assumes that both computers are networked and support telnet and rlogin. If you have a computer with an Internet connection in your university or company, you can log into it from your Linux computer at home and start to read your email, check whether a longer job is still running or needs to be restarted with a different set of parameters, and both telnet and rlogin are usually used in text mode, even a slow modem connection is sufficient to allow you to work in a reasonable way.

For the user, telnet and login look pretty much the same. The programs differ internally through the protocols they use. Both programs (telnet, rlogin) are passed the complete name of the computer on which you want to work. When the computer has found in the network, you log in with username and password. (When login is configured correctly and the computer knows you, no password is needed.) For logging out,

```
kofler@saturn$ telnet jupiter.galactic.network
Trying 192.168.1.2..
Connected to jupiter.galactic.network.
Escape character is '^'.
Red Hat Linux release 4.2 (Kernel 2.0.29) on i386
```

```
jupiter.galactic.network login: kofler
Password: ********
Last login: Fri 07:17:23 from saturn
kofler@jupiter$ exit
logout
Connection closed by host.
```

In principle, you can also start X programs during a telnet/rlogin session. The X programs are executed on the remote computer (fully exploiting, for example, the existing hardware), but they are displayed on the local X server and also receive keyboard and mouse input from there. Since now the whole X protocol must be transmitted through the network, working in this way with a modem connection requires more patience than you are likely to invest. Further details regarding the security mechanisms of X (xhost DISPLAY variables) can be found on page 257.

## 10 Email

This chapter deals with the basics, configuration, and operation of an email system. While the usage of email is extremely easy, its optimum configuration may be difficult.

### 10.1 Basics

Email stands for electronic mail and denotes the sending of messages (letters) over the Internet. It is one of the oldest and still one of the most important applications of the Internet. Originally, email was only designed for sending 7-bit ASCII texts. Today, email also copes with foreign language special characters and HTML texts. Furthermore, any type of file (images, and so on) can be sent via email.

If you use email in conjunction with PPP/SLIP, you can configure your email system as a so-called offline system. The name refers to the fact that email is read or written while there is no connection to the network. For transmitting messages to or from the provider, a brief Internet connection must be established. This method has the advantage of saving you a lot of telephone costs. You only need to establish a connection to the provider for a short period required for collecting new mail or for sending the mail messages you have written.

Some email programs can also be configured in a way that a continuous network connection must be open for their operation. This variation can certainly be viable in local networks: this book, however, limits itself to offline configuration.

In the context of this chapter, we will deal with the following aspects of email:

- Internals of mail programs under Linux (page 342): even if you already have some experience with email, you will still find a lot of valuable information here.
- Working techniques for handling mail programs (page 345): this section is mainly addressed to email novices. It describes some basic terms and techniques, such as utilization of folders and address books, sending of binary files via email, and so on.
- Configuration and operation of stand-alone systems (page 348): these are programs which execute all email functions themselves (receiving, writing, and sending). This category of email programs includes Netscape and KDE Mail. These programs are very easy to configure and to use.
- Setup of a Unix email system (page 359): instead of carrying out all functions with a single program, you can distribute these tasks between several programs. Configuration requires a little more effort, but it provides better possibilities for automation and other email clients (such as pine).

## Internals of mail management

The typical email configuration on a Windows PC uses one program (for example Netscape or Outlook) for all email tasks, that is, for both reading and writing, as well as receiving and sending of messages. In practice, the email system works as a stand-alone system.

The typical email configuration on a Unix is the exact opposite – here, different programs are used for the individual tasks:

- First, there is a so-called mail transport agent, which deals with sending and forwarding of email. Usually, the sendmail program is used for this purpose; occasionally, also smail. The program runs in the background and is constantly on.
- Second, there is a vast choice of mail user agents (which are often called mail clients). These programs represent the user interface for the end user, allowing email to be read and written. Each user can make use of an email client of his or her choice, for example pine, Elm, Macs, or Netscape. All email clients assume incoming email is available in the /var/ spool/mail/name directory, and that email messages to be sent can simply be passed on to the local transport agent.
