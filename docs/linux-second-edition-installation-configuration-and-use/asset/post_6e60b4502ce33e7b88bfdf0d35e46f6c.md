When handling directories, the two files (they are actually links) . and .. are very important. . refers to the current directory, .. to the next one above.

Wildcards are not evaluated by the command in which they occur, but by the shell in which the command is called. In addition to the wildcards described above, bash, the most used shell under Linux, recognizes a lot more special characters that have a special effect when executing a command (see 3).

## Complications using wildcards

On the surface, handling wildcards looks easier than it actually is. If you experience problems with wildcards, you should simply carry out some experiments with wildcards. This command displays all file names included in a wildcard combination, without any further effects on files or file names.

One problem is * not only includes files, but also directories.* * not only shows all in the current directory, but also the contents of all subdirectories in *. For the ls command, this problem can be circumvented by specifying the -d option: other commands, however, do not have an option.

If you want to operate on all directories (but not on normal files), the wildcard combination /* does the trick: this includes all * files which contain a reference to themselves as a subdirectory — and this is the case for directories. (Internally, directories are considered a special form of file — thus the quotes.)

```
user$ echo * /
```

The fact that the command but the shell is responsible for the evaluation of wildcards has some advantages, but also drawbacks. With, a command such as ls -R *, it is impossible to search for *.tex files in subdirectories as well. The -R for the ls command performs a recursive search of subdirectories and can be compared with the /S option of the DOS command DIR.

The reason is quite simple: the shell expands the pattern *.tex for the current directory and passes ls the list of files. If you do not have any directories with the extension .tex, ls has finished — the -R option cannot do anything about it. Recursive search is only possible in directories that have been passed as parameters.

Linux provides the much more flexible find command to search for files. The example below shows a list of all *.tex files in the current and all subordinate directories.

```
user$ find -name "*.tex"
```

The same must be attributed to the failure of the attempt to delete * files in all subdirectories. The command rm -f * fails in spite of the -r option for recursive elaboration of subdirectories. The reason: * is already expanded by bash – the current directory. Subdirectories are only considered if they have a name that ends in ". (The exact opposite is intended, is to delete all files ending in from ordinary directories.)

Deletion of all backup files in subdirectories is only achieved with the following-command. Here, the list of all files in question is built with find and then passed to rm via command substitution $(command).

```
user$ rm $(find -name '*')
```

If we are dealing with a very large number of files, an error will occur during the execution of the command containing all * becomes so long that it exceeds the maximum command line length. In such cases, find must be used with the -exec option – see page 454.

One of the most dangerous Linux commands is rm -rf *: this recursively deletes all files and all directories (starting with the current directory)

One further difference from MS-DOS comes when you try to execute a command of the kind mv *.x (for example, to rename *.x files to *.y). Under Linux, this is not possible with one command. The reason for this restriction is the same as above: the shell substitutes with the list of all files that correspond to the pattern. For *.y, there are no valid file names. The mv command is therefore passed a list of several files *.peter.x *.y and quite understandably, mv can do little with this.

A concrete example: assume that the current directory only contains the files mark.x, peter.x and sandra.x. When you execute mv *.x *.y, the shell substitutes pattern *.x with the three files. The shell does not find any matching files for *.y and passes the pattern as is. Only now is the mv command started. It is passed the following parameters:

```
mv mark.x peter.x sandra.x *.y
```

Even if we passed mark.x peter.x sandra.x peter.y the result would not be the desired one. mv is simply unable to rename several files at a time. Either several files are moved into another directory, or one file is renamed, mv may have some resemblance to the DOS command RENAME, but nothing more.

## Wildcards for advanced users

Unix experts have obviously found a solution to this problem as well: they use the sed stream editor. Because of the rather complicated handling of examples, such as the following should actually be used for shell programming. Here is a brief description of how this works: ls provides the list of files that to be renamed and passes it to sed. sed converts this into a list of cp commands, using the s command (regular find and replace) and passes this list to a new shell, sh, which finally carries out the commands. The line below copies all *.xxx files into *.yy files.

```
user$ ls *.xxx | sed 's/\(.*\)\xxx$/cp \&1.yyy/' | sh
```

Another alternative would be the formulation of a small loop, first orientation is given by the following:

```bash
user$ for i in *.xxx; do
    cp "$i" "${i%.xxx}.yyy"
done
```

## Hidden files

Under Unix, files starting with dot are considered hidden. Most commands ignore them by default. To see them, use the -a option:

```
user$ ls -a
```
