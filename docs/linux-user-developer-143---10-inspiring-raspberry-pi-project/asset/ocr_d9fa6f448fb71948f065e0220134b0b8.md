# 05  **Session ID management**

Cookies act as the carrier to transport the session IDs between the client (generally a web browser) and the server, as does the URL rewriting mechanism. Having secured the container, we can now explore ways to secure the payload as well:

+   * Always generate the session IDs after a successful authentication, and maintain a note of the IDs generated. The idea here is to never accept an ID that has not been generated by the application.
+   
+   * It is also necessary to always treat the session IDs as untrusted, similar to any other user input, and to validate and verify the IDs before processing them.
+   
+   * Session IDs should be renewed in case there is a change in the privilege level of the user. This way session fixation attacks can be mitigated, as the session ID has changed after the login and the attacker no longer knows it.

+   * For further information on session ID management, you can read more on the OWASP site: https://www.owasp.org/index.php/Session_Management_Cheat_Sheet.

# 06  **Database handling**

Databases are the primary components of any web application. We need them to store data, and so they are inevitably the prime targets of attackers. Now, databases can't be accessed easily; malicious access is difficult to obtain. But what if this malicious access is from your own application? It's not as strange as it sounds; the database queries that form the business logic of your application are one of the most vulnerable points for attacks – courtesy of SQL injection attacks. Typically, such attacks are carried through injecting a piece of SQL query to the application via user input fields like text boxes etc. The OWASP cheat sheet on SQL injection attacks mentions three major solutions for this, which we will explore in the next steps.
