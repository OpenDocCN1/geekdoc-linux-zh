# 08 Escaping user input

This approach needs the user input to be manually – or sometimes with the help of DBMS escaping mechanisms – escaped for valid strings, thus minimising any chance of malicious input being sent to the database. This option may sometimes prove insufficient, but can be useful in cases where you want better performance or are rewriting a legacy code and want to finish with lesser effort. PHP provides automatic input escape mechanism called magic_quotes_gpc which you can use before sending the input to back end, but it would be better to use the escaping mechanism provided by your database, since the query comes to the database, and the database would know better about what is a valid query. MySQL provides the mysql_real_escape_string() method to escape the input. Check your database documentation to find the escape function supported.

# 09 Cross site-scripting prevention

Such attacks work by injecting a malicious script, in the form of JavaScript, Flash or even HTML, to a genuine website. When the user accesses the site, the browser has no idea whether the script is genuine or not, and executes it. Once executed, they can access the cookies, session data or other sensitive information stored in the browser, since they are sent via a genuine website that the user tried to access. OWASP suggests treating the web pages as templates with certain slots for the untrusted data. For example, suppose you are creating the home page, on the top left you have a slot for the username, which is retrieved by the application and displayed to the user during the rendering of the web page.

Untrusted data in HTML tags and attributes: When you need to insert untrusted data in the HTML tags, make sure it is escaped before being used. For example, characters such as <, >, & etc should be changed to &lt; &gt; &amp; respectively. You can have a look at the ESAPI reference implementation of HTML entity escaping and un-escaping. Here is a sample usage of the API:

```
String safe = ESAPI.encoder().encodeForHTMLAttribute() request.getParameter("input" ) ;
String safe = ESAPI.encoder().encodeForCSS() request.getParameter("input" ) ;
```

Untrusted data in HTTP GET parameter: URLs like 'http://mysite.com(value=data)' can be a target. In such cases, make sure to escape all the characters with an ASCII value less than 256 using the %HH escaping format. The ESAPI for URL validation looks like this:

```
String safe = ESAPI.encoder().encodeForURL() request.getParameter("input" ) ;
```

Untrusted data in CSS: In cases where you need to put untrusted data in CSS, it is important that you take care that it is done only in a property value and nowhere else. Especially when you need to pass a URL check if it starts with 'http'. Then, except for alphanumeric characters, escape all the other characters with an ASCII value less than 256.

# 10 Safe URL redirects

Phishing is slowly turning out to be a big threat for user security. More so because it is not related to a website directly except for its look and feel. Attackers can easily put up similar looking websites at similar sounding web addresses to trap users, who think that they have approached a genuine site, then proceed to provide their authentication details. While many times such attacks are out of scope from your application perspective, you should make sure that nowhere in your application are the URL redirects compromised, as attackers generally try to implant malicious URLs to the valid applications. You should usually avoid redirects – even if it can't be done, at least do not take URL inputs from the users without proper validation.
