# ## 01 Authentication implementation

This is the process of verification of an entity, usually done via user ID and password combination. The OWASP cheat sheet on authentication has several recommendations. The major ones among them are:

+   - A User ID should always be case insensitive. This can help avoid confusion around names. Enforce password length and password strength. A password of fewer than ten characters is generally considered weak. However, the maximum length should be high; if you keep the maximum length low, it may prevent users from choosing the password they can easily remember. Users should also be forced to use small letters, special characters, digits, etc. in passwords.
+   
+   - Storage and transmission of passwords should always be over TLS, making sure that there is no eavesdropping.
+   
+   - The HTTP and HTML response for an authentication error should always be generic. It should not leak any info about the account status as well.

# ## 02 Forgot password feature

Passwords will always be forgotten and you must provide a way of resetting them. Most of you will acknowledge that it is a good idea to send users their old passwords via a side channel. The OWASP cheat sheet offers this password-reset strategy.

+   - Gather identity data and security related questions.
+   
+   - Verify the security questions.
+   
+   - Use a side channel to send an authentication token. The side channel may be an email or SMS sent to the users.
+   
+   - Allow password changes on the basis of the token received via the side channel.

Again, in case of any errors during password reset, you may also follow the rule of generic error messages.

# ## 03 Session management

A session lets you authenticate and track user activity on the website. It is generally implemented via a sequence of HTTP request and response pairs. Sessions are one of the primary points prone to exploitation. The OWASP cheat sheet on session management highlights several practices to make sure a session doesn't get compromised. First among them is that you should usually try to use the inbuilt session management mechanism available with the web development framework. Almost all the major platforms – PHP, J2EE, ASP, .NET, etc – have their session management mechanism available. Using this, not only faster, but also makes sure you use a solution that is extensively tested. Note that it is always good to use the latest version so that any recent vulnerability found is already patched. Let's now take a look at more specific details about handling cookies.

# ## 04 Cookie management

Sessions management generally uses cookies or URL rewriting (or both combined) as the underlying mechanism. And as we can see from recent stats, cookies are increasingly gaining popularity because of their flexibility and robustness. If you decide to use cookies, you may keep in mind these points:

+   - Secure and HttpOnly attributes: Add the cookie attributes secure and HttpOnly, as this makes sure the cookie is always sent only via Https connections and doesn't allow scripts to access the cookie. This will reduce the chances of cookie being intercepted.
+   
+   - Domain and Path attributes: Set these to indicate the exact browser where the cookie should be sent, so that it only reaches the desired destination and not anywhere else.
+   
+   - Expire and Max-age attributes: Set these to make the cookie non-persistent, so that it is wiped off once the browser instance is closed.
