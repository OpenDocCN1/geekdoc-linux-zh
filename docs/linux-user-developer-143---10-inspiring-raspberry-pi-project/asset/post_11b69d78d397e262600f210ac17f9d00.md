**15 Break it down**

Programming, in its essence, is breaking down complex tasks into simple parts. Implementing these parts varies with a language's syntax and capabilities, but the initial analysis can be put into comments.

FizzBuzz is a simple program – counting out integers, but replacing every number in the 3 times table with “Fizz”, and every multiple of 5 with “Buzz” – based on a children's game. Nevertheless, the majority of CS graduates applying for coding jobs couldn't implement it even in pseudocode.

LUGO readers should have little problem here – we're confident – so let's get scripting.

![](img/daaca9116bc2b1db669c224de81abc7c_28_1.png)

**16 Testing, testing**

The script has to loop through 100 consecutive numbers. It's best to start with the loop – when we know that's okay, we can move the done and exit to the end, and start on the number replacement.

![](img/daaca9116bc2b1db669c224de81abc7c_28_2.png)

**17 FizzBuzz!**

Divisible by both 3 and 5 is the first to test for – otherwise testing for just one will replace the number with whichever we test for first. `&&` is the logical operator and, which is used to check both conditions are true.

![](img/daaca9116bc2b1db669c224de81abc7c_28_3.png)

**18 Double parentheses**

Fizz is simply checking for divisibility by 3. Note the double parentheses around the arithmetic expression – allowing C-style arithmetic operations, such as `(n++)`.

**19 Remainder 0**

Add an `n%5` for buzz, and don't forget to test the script at each change. The modulo operator – `%` – common to many languages, shows the remainder result of an integer division.

**20 Just a number**

If none of the fizz/buzz cases have been met, the remaining option is just to print the number. Now we end the conditional with `fi`, and the loop with `done`. It works – but one result per line is not good formatting...

![](img/daaca9116bc2b1db669c224de81abc7c_28_4.png)

**21 Pretty printing**

Replacing `echo` with `printf` – again, familiar from C programming – means we can incorporate tabs and newlines into the script, useful for outputting in tabular form. We put newlines for both Buzz and FizzBuzz.

![](img/daaca9116bc2b1db669c224de81abc7c_28_5.png)

Such a mixture of program logic and formatting may make the purists shudder – but on a small program like this we're interested in results. And re-factoring to a larger prototype can wait until you've transferred it to another language.

Software development has grown leaps and bounds over the years; there are new programming languages, development models, application areas and even new vulnerabilities coming up everyday. Speaking specifically about vulnerabilities, most of them (even if newly found) are still based on some of the basic attacks like SQL injection and cross scripting, among others. Such issues can almost always be avoided if a secure coding practice is followed. It's much better to avoid security holes in the first place, rather than fix them once they're already been exploited. As they say, you always need to be one step ahead.

OWASP, or the open web application security project, is an open source forum that can help you tighten your security. To make things clear, OWASP is not software or a tool that can clean your code of vulnerabilities without input from yourself. OWASP is rather a set of best practices compiled by security experts the world over, which can be followed while writing code. So, when you look up OWASP, it's like being guided by thousands of experts collectively - only for free! OWASP is primarily divided into guides: e.g. development guides, testing guides, top ten projects, etc. and cheat sheets. Guides provide full-blown details of various aspects of security, relevant to the topics they cover, while cheat sheets have direct, to-the-point information. So, cheat sheets can be used in cases where you need concise information about security aspects of a particular feature such as, for example, a password reset feature.

## 01 Authentication implementation

This is the process of verification of an entity, usually done via user ID and password combination. The OWASP cheat sheet on authentication has several recommendations. The major ones among them are:

- A User ID should always be case insensitive. This can help avoid confusion around names. Enforce password length and password strength. A password of fewer than ten characters is generally considered weak. However, the maximum length should be high; if you keep the maximum length low, it may prevent users from choosing the password they can easily remember. Users should also be forced to use small letters, special characters, digits, etc. in passwords.
- Storage and transmission of passwords should always be over TLS, making sure that there is no eavesdropping.
- The HTTP and HTML response for an authentication error should always be generic. It should not leak any info about the account status as well.

## 02 Forgot password feature

Passwords will always be forgotten and you must provide a way of resetting them. Most of you will acknowledge that it is a good idea to send users their old passwords via a side channel. The OWASP cheat sheet offers this password-reset strategy.

- Gather identity data and security related questions.
- Verify the security questions.
- Use a side channel to send an authentication token. The side channel may be an email or SMS sent to the users.
- Allow password changes on the basis of the token received via the side channel.

Again, in case of any errors during password reset, you may also follow the rule of generic error messages.

## 03 Session management

A session lets you authenticate and track user activity on the website. It is generally implemented via a sequence of HTTP request and response pairs. Sessions are one of the primary points prone to exploitation. The OWASP cheat sheet on session management highlights several practices to make sure a session doesn't get compromised. First among them is that you should usually try to use the inbuilt session management mechanism available with the web development framework. Almost all the major platforms – PHP, J2EE, ASP, .NET, etc – have their session management mechanism available. Using this, not only faster, but also makes sure you use a solution that is extensively tested. Note that it is always good to use the latest version so that any recent vulnerability found is already patched. Let's now take a look at more specific details about handling cookies.

## 04 Cookie management

Sessions management generally uses cookies or URL rewriting (or both combined) as the underlying mechanism. And as we can see from recent stats, cookies are increasingly gaining popularity because of their flexibility and robustness. If you decide to use cookies, you may keep in mind these points:

- Secure and HttpOnly attributes: Add the cookie attributes secure and HttpOnly, as this makes sure the cookie is always sent only via Https connections and doesn't allow scripts to access the cookie. This will reduce the chances of cookie being intercepted.
- Domain and Path attributes: Set these to indicate the exact browser where the cookie should be sent, so that it only reaches the desired destination and not anywhere else.
- Expire and Max-age attributes: Set these to make the cookie non-persistent, so that it is wiped off once the browser instance is closed.
