Once the mail arrives at its final destination, you use your email client to retrieve it. If you haven't already viewed the message you sent to yourself earlier, find it in the /var/spool/mail directory of your system, in a file that has your user name. One method to view the message is to simply issue the command `cat /var/spool/mail/username` (substitute the appropriate username).

"But wait! you proclaim. "What is all other stuff at the top of the message?"

That "stuff" is heading information added by sendmail, for RFC 1869, which describes SMTP. Each SMTP server, from the SMTP server you connected to the last SMTP server to handle the message, adds its own heading information, but you can always see the route your message took. Most email clients hide that information from you, but you can configure them to show headers, if you wish.

Using the cat command to view your message isn't very practical, since each incoming message is appended to this file, so you'd be seeing the same messages over and over. Instead, you can access your messages using your email client. On your local machine, you can configure your client to manipulate the mail spool file directly. If your mail was located on another machine, you would not have access to the mail spool file. Instead, your email client would connect to a POP server.

Like SMTP servers, POP servers are software that listen on a TCP/IP port (in this case, 110) and allow connections from client software. Unlike SMTP, which requires no user or password information, POP will connect to your client immediately and ask it for identity (with USER and PASS commands) before proceeding. Once your identity has been authenticated, the POP server will respond to commands from your client. These include instructions to the POP server to send all of your waiting messages, send one of the waiting messages, or delete a message, unless you've configured your email client to keep the messages on the server.

You can experiment with POP servers by issuing the following command:

```
telnet yourPopServer 110
```

Once connected, issue USER username, then issue password for your account. The HELP command will give you a list of commands that the POP server understands.

Once you've received your messages, they exist nowhere but in your local mailbox. This isn't much of a problem, unless you use multiple computers. Then, it seems that the email you want to review is always "where you aren't." Sure, with a little creativity, you can configure all of your computers to leave messages on the server. The better solution, is to use IMAP. This is typically no more complicated than using your email client to use IMAP (assuming your ISP provides one) instead of a POP server. The difference, though, is that the mail is left at the server. This is much more convenient for a user who has many computers, since the mail is in one place. Most ISPs do not offer IMAP simply because of the space requirements on their end. They're more than happy when you connect and delete your messages from their disk drives. Fail to do that too long, and people who send you messages will start getting them bounced back.

No discussion of Internet email would be complete without a MIME, the Multipurpose Internet Mail Extension. You have probably attached some kind of file to an email message before. Unless the attachment was text, it was using MIME.

When email was first created, the messages were pure ASCII text. Although a byte is one eight-bit character (for a total of 256 characters), ASCII only defined the first 128. The upper characters were "extended" for printing cute symbols on printers, or for printer-control characters, or for some of the characters used in non-English languages. Actually, only the lower seven bits would be passed through email systems.

Today, it's not at all unusual to send pictures and other files that have ASCII values that are in the upper 128 characters. These binary files wouldn't be able to pass normally through the email system without MIME. Simply put, MIME maps the non-routable characters in binary files into roughly two-byte strings that are routable. These pass flawlessly through email systems.

Most clients take care of the conversion for you automatically. If you attach a picture to one of your emails, the client will convert it, and the recipient's email client will convert it back. If you look at the raw data in your file, you'll see how this is done, assuming that you've ever received a MIME-encoded attachment (which you probably have).

## Exercise 2: Send Manual Email

In this exercise, you'll use the telnet utility to connect to an email server and send someone an email. To complete this exercise you'll need the following:

- The domain name of an email server
- A sender email address
- A receiver email address (which can be the same as the sender, if need be)

- 1. Telnet to an email server, replacing servername in the following with your actual email server:

```bash
$ telnet smtp.servername.net 25
```

You should get a 220 response message if all went well

- 2. Identify yourself, replacing username with your actual user name:

```
HELO username
```

- 3. Say who the mail is from, replacing me@myisp.net in the following with your email address:

```
mail from: me@myisp.net
```

You should get a 250 message saying "Sender ok."

- 4. Say who the email is sent to, replacing you@yourisp.net with the receiver's email address:

```
rcpt to: you@yourisp.net
```

You should get a 250 message saying "Recipient ok."

- 5. Enter the data command. You should get the following 354 message:

```
Enter mail
```

- 6. Enter the following email message, terminating the message with a dot on a line by itself:

```
From: me@myisp.net
: you@yourisp.net
Subject: Chapter 11 email test
This is a test message from me
```

You should receive a 250 message saying "Message accepted for delivery."

- 7. Enter the quit command. You should receive the following 221 message:

```
... closing connection, Connection closed by foreign host.
```

- 8. Verify that the email was successfully sent.
    - a) If you were the recipient, use your email client.
    - b) If someone else was the recipient, ask that individual to check his or her email.

- 9. Repeat steps 1 through 8, but this time send a message to elvis@greland.com and take note of how the server handles the email address.
