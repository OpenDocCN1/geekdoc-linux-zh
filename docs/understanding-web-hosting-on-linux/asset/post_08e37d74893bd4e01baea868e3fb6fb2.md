The mappings between the drive, partitions, and entries in /dev are done automatically during system startup. This mapping assumes that the drive is the master drive on the primary IDE channel. If it were the slave drive on the primary IDE channel, it would be /dev/hdb. The references to the primary and secondary drives on the secondary IDE channel would be /dev/hdc and /dev/hdd1, respectively. In either case, an IDE-ROM drive would be skipped as one of these. And the floppy drive? If it were the standard 1.44 Mb floppy (which, to Windows, you would find it at /dev/hd0).

You might be wondering why hda three and four have been skipped in the sequence. The reason is that only two of the primary partitions have been created. First is /dev/sda1 and the second is /dev/sda2, which has been marked as an extended partition and encompasses the remainder of the drive. Any logical partitions created within an extended partition will be numbered with five, thus creating the missing partitions.

Now that you have some idea of how Linux maps the physical drives and partitions, let's see how it refers to whenever data is to be written or read. To make the partition accessible, the mount command must be issued. This command associates a partition with a specific device, grafting it into the directory tree off a directory called a mount point. This can be done manually, or automatically at system startup by adding entries into a configuration file called /etc/stab.

In Figure 3.2, the second partition has been dedicated to swap space, and therefore does not appear anywhere than in /dev. The other two partitions, however, have been grafted into the tree structure. Partition 1 has been mounted in the Linux file system as /boot, which is read as "the directory appearing under the root directory." Partition 3 is mounted as /, the root partition. In the directory hierarchy, /boot and /dev are both subordinate to /.

If you are familiar with the Windows naming convention, you might find the Linux convention somewhat disconcerting. Once you become accustomed to it, however, you'll find it not only natural, but also much more flexible—even elegant. Refer to "An Introduction to Disk Partitions" in the appendix of the Official Red Hat Linux Reference Guide.

There is one restriction when dealing with the contents of /boot. Most PCs have trouble booting systems where the kernel (stored in /boot) falls outside of the 1,024 cylinders of the disk drive. In this mind, it's best to create a small (20 Mb or so) partition to serve as the partition containing /boot. This will ensure that the PC will be able to successfully load the kernel when the time comes.

The simple three-part partitioning strategy discussed in this section is one recommended by Red Hat, primarily because it is fairly simple to understand. The next section discusses an alternative that is more complicated, but provides better flexibility. In this strategy, the disk partitioning and formatting is done during the installation of Red Hat, and you will not be required to manually invoke either fdisk or mk2fs. Instead, the graphical installer will handle these details for you, insulating you from the decidedly user-friendly fdisk program by replacing it with the kinder, Disk Drill. If you ever need to do any partitioning on an active system, you will need to learn the mechanics of fdisk, Disk Drill is available only during system installation. Once your system is up and running, you can read more about fdisk by accessing its man page (discussed in chapter 4).

# Planning Your Backup and Recovery Strategy

One aspect of configuring any system is considering the ramifications if the worst happens and shiny, new disk drive decides to quit. (Actually, the question isn't/the drive will quit, but rather when it will.) How are you going to get your system operating again? Even if it happens across one-in-a-million drive that possesses the secret to immortality, you will eventually want to upgrade the operating system to a newer level as your needs change or when helpful functions are added to Linux. Planning strategy for recovery or upgrade is much easier before the start installation. The layout of a Linux system allows your plan for recovery for upgrading as well. Let's look at some of the factors you should consider when planning your system.

Have you ever noticed how recovery and backup tools are available for the Windows platform? An entire industry has built around these functions to compensate for what we believe are serious flaws in Windows' design. On the first list of biggest mistakes would have to be the concept of the system registry. This is a binary file that Windows uses to store configuration information about itself. Everything you've ever configured on your system has affected the registry. Lose or corrupt that file, and you and your system are down for count. The only way to make manual edits to the registry is with one of the Microsoft-supplied programs REGEDIT or REGEDIT32. However, both of these require GUI interfaces to operate. If your system fails to boot, you are out of luck. To make matters worse, Microsoft has application program interfaces (APIs) to allow software tools to use the registry for the same purpose. If that gets corrupted, but your system still starts, your applications might not work like they used to. A deal! You get two opportunities to optimize your system for the price of.

Another flaw in Windows is the way application software and operating software are segregated—or rather, not segregated. It appears as if Windows goes out of its way to ensure that application software gets mingled with operating system software. Load any application software on your system, and you really find your hard drive. Sure, if the software's authors choose to use the standard Windows ShieldGuard, you can uninstall it.
