
## History Repeats Itself

Another useful feature of bash is its ability to retrieve, edit, and re-execute previously entered commands. By simply pressing the Up arrow key, you retrieve the last command executed. If you keep pressing the Up arrow, bash will continue to retrieve the commands executed. If you are looking for commands past the terminal screen, use the Down arrow to go in reverse direction. Once you've retrieved the command you want, you can edit it with the help of the Home, End, Delete, Backspace, and arrow keys, and press enter to execute the modified command.

If you type two exclamation points, bash will retrieve and immediately execute the previously entered command. If you type one exclamation point followed by a number n, bash will retrieve and execute the command entered n times again. Perhaps the coolest feature of bash history, though, is the search-and-execution flow. If you type an execution point followed by a string, bash will scan history for the command that contained that string, and then execute it. Suppose you would like to use the `date` command to set your system date to equal that of an Internet time server. Instead of trying to remember the URL for the time server, you simply type the following:

- !?date

Bash pulls from history and executes something like this:

```
rdate -s tock.usno.navy.mil
```

To delve a little deeper into the mechanics of bash history, consider the results of the following command:

```
$ set | grep HIST
HISTFILE=/home/donat/.bash_history
HISTSIZE=1000
HISTSIZE=1000
```

The **set** command is discussed later in this chapter, but from the list, you can see that the user's personal history file is `/home/donat/.bash_history`. The history file is simply a text file, so you can open it with your favorite text editor or use `less` to display its contents:

```
$ less /home/donat/.bash_history
```

The history file will become especially handy when you start to create bash scripts to automate the execution of a series of bash commands under a single, home-grown, custom Linux command, as covered in the next chapter.

## I/O Redirection and Piping

Enough of the history lesson. It's time to move on to another bash power feature: input/output redirection and piping. In a few commands already shown in this chapter, you've seen the pipe operator (|) used. Let's review these commands:

```
$ cat /etc/passwd | grep username: cut -d : -f 7
$ ls | less
$ set | grep HIST
```

The simplest of these three commands is ls. When you execute this command, the | operator tells bash to pipe the output from ls into the less command. You already know that less shows the contents of a file one at a time. The file, in this case, is a virtual one created from the output of the ls command.

## stdin, stdout, and stderr Files

In UNIX, all programs have three standard files: stdin, stdout, and stderr. Unless qualified, all the standard output file (stdout) is your terminal session. When you run the ls command by itself, the | operator tells bash to pipe standard output to the standard input of less. The less command, when it doesn't have a file name as argument, displays the data from stdin.

The other commands that used the pipe operator, cat and set, work similarly. The set command lists all the environment variables currently set on your system. (You'll find out about environment variables later in this chapter.) The standard output of set, in this case, is piped to the grep command. The grep command is a simple utility that scans for strings. The argument to grep in this example is HIST, so the set command pipes the entire list of environment variables (about two dozen) to grep, which then lists to its standard output all the environment variables with the string HIST in them. Note that the standard output for grep, in this case, was not piped, so it simply went to the terminal session. Alternatively, grep's standard output had been piped to the less command:

```
$ set | grep HIST | less
```

The cat command in the example also piped to grep, the standard output of which was piped to a powerful command called cut. We'll leave it up to you to research cut but, to summarize, it removes elementary sections of a text line, resulting in standard output that contains only meaningful pieces of data. In this case, the line was an entry from the password file and all piece of information we are interested in (with pieces determined by the colon separator) is the seventh—the user's default shell.

## Redirection

Whereas the pipe operator allows you to force the standard output from one command to the standard input of another command, the redirection operators in Table 12.1 allow you to force standard output and errors to a particular file.

### Table 12.1: Input/Output Redirectors

| Redirector | Function |
|---|---|
| >file | Redirects standard output to the specified file. |
| 2>file | Redirects standard error to the specified file. |
| >>file | Redirects standard output to the specified file, appending existing data. |
| 2>> | Redirects standard error to the specified file, appending existing data. |
| &file | Redirects both standard output and standard error to the specified file. |
| <file | Redirects standard input to the specified file. |
| <<text | Redirects standard input until a line matching is found. |
| cmd1 | cmd2 |

The command cmd1 | cmd2 uses the output of cmd1 as the input to cmd2.

The command cmd1 > file redirects the standard output of cmd1 to the file. If the file already exists, it is overwritten.

The command cmd1 >> file redirects the standard output of cmd1 to the file, but if the file already exists, the data is appended.

The command cmd1 2> file redirects the standard error of cmd1 to the file. If the file already exists, it is overwritten.

The command cmd1 2>> file redirects the standard error of cmd1 to the file, but if the file already exists, the data is appended.

The command cmd1 &file redirects both the standard output and standard error of cmd1 to the file.

The command cmd1 < file redirects the standard input of cmd1 from the file.

The command cmd1 <<text redirects the standard input of cmd1 until a line matching text is found. The following example shows how to use this:

```bash
cat << EOF
this is a test
of the here-document
EOF
```

The output of the command above is as follows:

```
this is a test
of the here-document
```

## UNIX Filters

The most frequent use of redirection is for standard output. Table 12.2 shows a few the more common UNIX filters.

| Utility | Purpose |
|---|---|
| cat | Copy stdin to stdout. |
| grep | Search for strings in stdin. |
| sort | Sort lines in input. |
| cut | Extract columns from input. |
| sed | Perform editing operations on input. |

Each of the filters in Table 12.2 defaults to the terminal as **stdin**. For instance, if you enter the **sort** command with no arguments, it will accept input from the terminal. The following example shows what happens if you enter **sort**, then four lines that contain the numerals 4, 3, 2, and 1, and finish by pressing Ctrl-D:

```
$ sort
4
3
2
1
1
2
3
4
```

The sort utility, by itself, is not all useful. When you redirect or pipe standard input or output to it, however, it becomes very useful. For instance, you could quickly sort the entries in a password file as follows:

```bash
$ sort < /etc/passwd
```

If reason for sorting the password file was to find a specific user, **grep** would even be better:

```bash
$ grep username < /etc/passwd
```

The output from this command contains the complete line from the password file. If you want one section of a line, such as the section that contains the user's default shell, you'd use the **cut** utility. For instance, at the beginning of this chapter, you saw the following command:

```bash
$ cat /etc/passwd | grep Username:| cut -d : -f 7
```

This uses **cat** to pipe the contents of /etc/passwd to **grep**. The **grep** utility finds the lines containing the specified user name, and pipes it to **cut**. The **cut** utility then extracts the seventh field, as determined by colon separators, and lists it to standard output, the screen. Although this process seems complicated, it illustrates how filters can be combined to create useful and powerful utilities—in a single bash statement.
