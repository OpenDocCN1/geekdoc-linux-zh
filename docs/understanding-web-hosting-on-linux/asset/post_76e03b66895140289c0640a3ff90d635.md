As the years passed, ARPANET morphed and began a slew of "somethingNETs": MILNET (Military Network), BITNET (Its Time Network), CSNET (Computer Science Network), and a host of others were built by specific groups for specific purposes. The standard communication protocols we use today (such as email and FTP) were developed so that users in one network could communicate with users in another (internetworking, as it were), creating the noun that describes the glue that puts networks together: the Internet.

The modern Internet is actually quite young; it didn't extend past universities until the mid-1990s. In fact, the system known as the "Worldwide Web" didn't get released until 1991. Prior to that, hobbyists exchanged information via a piece of software known as a bulletin board system (BBS), which served calls coming into the modems to the computer on which the BBS software ran. A user navigated it via textual menus, not the familiar browsers we use today. Typically, BBS would offer a file-exchange area (where we'll leave to your imagination what kinds of files were exchanged) and a message board (similar to the USENET networks). Sometimes, sessions were provided.

Most BBSs were small-time operations that could handle no more than 16 callers simultaneously, since each user would use one line and modem. Computer hardware was not as powerful or inexpensive as it is, the small-time operator could afford a massive BBS system. Typically, BBS operators funded their operation through the subscription fees paid by members, which were limited to the local calling areas of their service. Soon, companies like CompuServe, SpyNet, and America Online (AOL) began to offer functions equivalent to those of the local BBS, but on a much greater scale, covering a large geographical system. As these big stars started to provide local access in more numbers and more communities, the smaller operators became extinct. In its truth, though, the Internet made the services provided by companies like CompuServe look stale and archaic. AOL is still going strong, though one of its main services is a portal to the Internet, which it would have surely defied.

# TCP/IP Primer

By now, you've already been introduced to the concept of TCP/IP addresses. They are 32-bit numbers that you type into the networking-parameters boxes during installation. You might be saying, "Huh? I never typed in any 32-bit numbers." Actually, though, you did. To make it easier to work with these addresses, they are typically broken down into four, eight-bit octets, separated by decimal points, providing numbers in the range 0.0.0.0 through 255.255.255.255.

An IP address is further broken down into two parts: the network address and the node address. Networks are grouped by class based on how much of the address is given to the network address and how much to the node portion. The zero in the following examples represents the node address.

Class-A networks are defined using the first octet. X.0.0.0 where X can have a value of one through 127, inclusive. There aren't many class-A addresses available, so only the biggest users can score one. Class-B networks use the first two octets for their definition, X.Y.0.0, where X has a value between 128 and 191. Class-C networks, which are what most end-users, use the first three octets, X.Y.Z, and with an X value between 192 and 223. The two node addresses of zero and 255 are reserved; Compared to class-A networks, many more class-C network addresses are available, but each can have only 254 nodes. (Remember: zero and 255 are reserved.) In addition, some addresses ranges are reserved. For example, the 127.X.X.X is reserved for a loopback device, for testing computers with Internet connections.

Assume for the moment that you have two computers connected by a single Ethernet hub. The first computer is FTP and HTTP (Web) server. This is a simple workstation that is a client to the first. For these computers to talk to each other via TCP/IP, they must have the same network address, and each must have a unique node address. In the case of a class-C network, this means that the first three octets match, but the fourth octet must be unique.

Assuming everything is configured and properly, the question then becomes, "How does the server know which client is requesting when a connection is made?" The answer is: logical ports. Within each TCP/IP packet is embedded not only the source and target (the sender and receiver) IP addresses, but also a from- to port number. TCP/IP has provisions for 65,536 logical ports. Logical ports use 1,024 as well-known ports, because the function of each has been defined in the IP specifications. In the case of the first computer in our example, the FTP server normally would be listening on port 21 (the FTP port), and the HTTP server normally would be listening on port 80.

These ports are not carved in stone. In fact, you may adjust your server configurations to effectively change the port on which the server listens for a connection. However, if you deviate from the well-known ports to your own definitions, you'll need to specify the port number when making a connection request. For example, if you've configured your HTTP server to listen on port 2000, you'll need to add "2000" to any URL that points to your custom server. Otherwise, your browser won't be able to connect. For example, "http://www.yourdomain.com" would become "http://yourdomain.com:2000" when attempting to connect to your server. A list of services and the ports on which they listen is on your computer (at /etc/services); you can browse this if you are curious.

At this point, you probably be wondering yourself, "How is this relevant to my server? In a URL, so why should I know this material?" Our answer is simple: You should know the basics so that you can more easily configure your server. But don't fret; the worst is over. There are just a few more terms with which you should become familiar.

You have already heard the term IP address, which is the unique address (on your network) assigned to your computer. The network administrator assigns the address and provides you a number in conjunction with another number, the network mask, or subnet mask. The mask indicates which of the bits comprise the network address. Each bit that is set to a one is part of the network address. Those that are set to a logical zero are considered part of the node address. This topic can become quite esoteric, so I'll leave you the admission to always double-check IP addresses and masks. An error in the IP address could cause your computer to conflict with another that has the same IP address, which can lead to some serious problems that are hard to troubleshoot. An error in the network mask can lead to the inability of your computer to communicate with any others. This error isn't nearly as difficult to find, however.

Another term of interest is gateway. As mentioned earlier, two computers communicate with one another only if they are on the same network. If they are on different networks (say, your local network and the (Internet), your communications will be brokered by a device that has at least two interfaces: one on the network to which you are connected and another on another network. The gateway address given to you by your network administrator is the address to which it will send packets for a computer that is not on your local network.

The next term to know is Domain Name System, or DNS. The simplest way to explain DNS is the analogy of IP addresses and phone numbers. If you know someone's phone number, you can easily call that person. If you don't know the phone number, but you know the person's name, you can call directory assistance to get the number.

DNS is the directory assistance of the Internet. When you enter a URL like "http://yourdomain.com" into your Web browser, it will first look in its own book (the file /etc/hosts) to see if it knows that. If not, it will connect to a DNS server to retrieve the number. If the DNS system knows it, it will return the number to your computer, which will use to make the connection. If the name is unknown, the DNS server will return an error message to that effect, which you will see as a "Host Unknown" message from your browser.

The list of servers you'll call for your request is in the file /etc/resolv.conf. If you look there, you'll see up to three "nameserver xxx.xxx.xxx.xxx" entries which will be searched in the order they appear. Typically, you will be given two server addresses—primary and secondary. If the primary one fails, the secondary will provide DNS services until the primary comes back online.

The final term is Dynamic Host Configuration Protocol, or DHCP. In nutshell, it refers to a protocol by which a computer that has been turned on is automatically configured with the IP/netmask, and gateway addresses. It does this by broadcasting a DHCP request to the network (using a different type of address because you don't know anything about the network at this point) and waiting for a response from a DHCP server in which all of the network parameters are provided. The DHCP server has a pool of available addresses from which it will choose one to send to the client. Once it does, the address is to be leased, which means the server will not assign it to another client. The lease has a fixed, so the client will occasionally be polled to see if the lease should be renewed. If the client responds, the lease is renewed. If not, the lease is cancelled and the address is placed back in the pool.
