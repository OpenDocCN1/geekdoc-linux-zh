Stdin can also be the output from a script or other executable, which is then sent as input into a second script or executable. This process, and often, is repeated several times before a result is displayed to the user on stdout. Stdout is normally the screen, or in the case of a headless server (without a monitor plugged in) the serial port, which can be connected to a KVM switch, Cisco local directory, or other sort of rack-mounted device. Like stdout, the default location of stderr is the screen, and as indicated (which is the case vast majority of the time), stderr is defined by the process. For example, an Apache Web server may direct stderr to /var/apache/messages/logs.

This will obviously vary from one process to another, and may require some additional understanding of the /dev (device) directory and sockets. This information is out of scope for this project, but should not be overlooked by the investigator.

The cmdline file in the PID directory also contains some useful information. It is usually only a single line entry, but that single line contains the command-line entry used to initiate the process.

As a forensic note, it is important to remember that this information can be altered by a skilled attacker who has elevated to root privileges, and should only be used in context of the penetration. For example, during the course of your analysis, you found a process with a PID of 936, you would look in /proc expecting to find an entry for 936, and as expected, you do. In the /proc entry you see the exe link, which you know to mean that the binary that has launched the process has been unlinked or deleted from the file system. In your next step, you check the cmdline file, expecting to find the same entry you saw in the exe link, but it is different. You check your output from "ls" command you issued earlier and find a process within the cmdline file is running rather than the one found in the link. The attacker thinks he is pretty slick and has effectively confused you to the point that you no longer know what is going on, however you have read this paper, and know what to do next. Move to the fd directory under the same PID and find several /dev entries, an open socket, and a file that is marked (deleted). You have found that the process that is running is sending its output to a file marked for deletion...very clever, but not recoverable.
