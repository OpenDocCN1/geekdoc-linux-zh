
# Understanding Unix : Chapter 27

```bash
cat: foo: Permission denied
ubuntu@ubuntu:~$ chmod u+r foo # Add back user/owner permission
ubuntu@ubuntu:~$ ls -l foo
-r--r--r-- 1 ubuntu ubuntu 0 2008-04-14 20:25 0
ubuntu@ubuntu:~$ cat foo # And now we can read again, but it's a blank file
ubuntu@ubuntu:~$
```

In addition to this read, write, and execute permissions we've explored in the example, *nix also has the notion of “set UID” and “set GID” permissions for files. There is no analogous file attribute in New Technology File System (NTFS) or File Allocation Table (FAT) in Windows. What these executable files change the effective user ID or group ID to something that program is executed. The security ramifications of this can be serious, these are very important in forensic analysis, because these permissions allow an executable to run as another user, regardless of who runs the program. For instance, many commands that require privileged access to hardware are set user ID root, indicated by “s” in the “user/owner” position of the permissions:

```bash
ubuntu@ubuntu:~$ ls -l /bin/ping
-rwxr-xr-x 1 root root 30856 2007-07-06 02:40 /bin/ping
```

When /bin/ping is run by any user, it runs as the superuser (root).

One thing you don't want to find on a system is an Set User ID (SUID) root copy of /bin/bash, or any other shell. The ramifications are somewhat obvious. Any user who would execute such a shell may become root. Modern shells have built-in protections against this classic attack, but all the SUID root copies of shells should be a red flag to a forensic investigator.

This type of file permissions is very important. File permissions are defined in terms of:

- Owner permissions (u, can the user/owner read, write, or execute this file?)
- Group permissions (g, can the group read, write, or execute?)
- World permissions (o, can others on the system read, write, or execute?)
- SUID/SGID permissions (s, when this executes, will we change the effective user ID or group ID?)

Read and write permissions are fairly intuitive. Execute permissions, on the other hand, don't really exist in the Windows world. *nix, if a file is to be interpreted as a shell script or an executable program, the execute bit must be set for a role to which the user belongs.

![](img/fd8e85097b37559dbc07dc22fd8cb1fe_35_0.png)

For example, the humble “ls” command is an executable binary format file, executable by everyone:

```bash
ubuntu@ubuntu:$ ls
/bin/ls
ubuntu@ubuntu:~$ /bin/ls
/bin/ls: ELF 32-bit LSB executable, Intel 80386, version 1 (SYSV), for GNU/Linux
2.6.8, dynamically linked (uses shared libs), stripped
ubuntu@ubuntu:~$ ls -l /bin/ls
-rwxrxr-x 1 root 78004 2007-09-29 12:51 /bin/ls
```

For directories, the execute bit takes on a slightly different meaning. If you attempt to list a directory that does not have its execute set for a role to belong to, the directory listing will be denied:
`etc/passwd`

With that brief introduction to file permissions behind us, we can return to user authentication. Here’s what /etc/passwd looks like: a colon-delimited text file in the format of:
`username:passwordfield:UID:GID name:home directory:default shell.`

```bash
ubuntu@ubuntu:$ cat /etc/passwd | head -14
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/bin/sh
bin:x:2:2:bin:/bin/sh
sys:x:3:3:sys:/dev:/bin/sh
sync:x:4:65534:sync:/bin:/bin/sync
games:x:5:60:games:/usr/games:/bin/sh
man:x:6:12:man:/var/cache:/bin/sh
lp:x:7:7:lp:/var/spool/lpd:/bin/sh
mail:x:8:8:mail:/var/mail:/bin/sh
news:x:9:9:news:/var/news:/bin/sh
uucp:x:10:10:uucp:/var/spool/uucp:/bin/sh
proxy:x:13:13:proxy:/bin:/bin/sh
www-data:x:33:33:www-data:/var/www:/bin/sh
backup:x:34:34:backup:/var/backups:/bin/sh
```

The second field we see is an x is a password field. When shadow files are being used (as is the case in all modern *nix), the x represents a shadowed password entry and tells Linux to look in the shadow file for the password hash.

Local authentication isn't the only game in the Linux town though. Linux, via pluggable authentication modules (PAM), supports a dizzying array of methods including NIS, AFS, Kerberos, and more. You can configure PAM to authenticate against these sources. For example, /etc is a directory where all configuration files are found. You won't see this file on a LiveCD, but it generally exists on an installed version of Ubuntu. The contents of /etc vary among distributions.
