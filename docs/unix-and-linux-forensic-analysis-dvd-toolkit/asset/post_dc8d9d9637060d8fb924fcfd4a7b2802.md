
## The /Proc File System

dumping strings (cat /proc/kcore) to more advanced techniques can detect more rootkits. To collect this data, you'll need external storage that is slightly larger than the system's memory. You do not want to dump this to screen; you'll need to send it directly to a file for later.

```
cat /proc/kcore
```

## modules

As the name implies, this file lists all modules loaded into the kernel. This is good information to collect as part of any investigation and may prove useful if you find yourself dealing with a rootkit that may alter binary to omit reporting it, yet cat /proc/modules will reveal its presence.

## mounts

This file lists all of the current mounts on the system. This data is useful for several reasons: primarily to identify any external storage you are using, other network shares that are mounted, and verifying that mounts that should be read-only are appropriately.

```
rootfs rw 0
/dev/root ext3 rw,data=ordered 0
/dev tmpfs rw 0
/proc proc rw 0
/sys sysfs rw 0
/proc/bus/usb usbfs rw 0
/dev/devpts devpts rw 0
/dev/sda1 boot ext3 rw,data=ordered 0
/dev/shm tmpfs rw 0
none /proc/sysfs/binfmt_misc binfmt_misc rw 0
/var/lib/nfs/rpc_pipes rpc_pipes rw 0
none /proc/fs/vblock vblock rw 0
/etc/auto.misc autofs rw,fd=6,pggrp=1998,timeout=300,minport=5,maxproto=5,indirect 0
/hosts autofs rw,fd=11,pggrp=1998,timeout=300,minport=5,maxproto=5,indirect 0
/mnt/ rw 0
```

## partitions

This file presents a limited amount of information about the partitions present and the number of blocks allocated to them. This is all of the information available elsewhere on the 2.6 kernel (see SysFS), but it's better to have duplicated data than not enough. Additionally, on a 2.4 kernel, this file will contain the data found in /proc/diskstats.

| major | minor | #blocks | name |
| --- | --- | --- | --- |
| 8 | 0 | 8388608 | sda |
| 8 | 1 | 200781 | sda1 |
| 8 | 2 | 8185117 | sda2 |
| 253 | 0 | 7602176 | dm-0 |
| 253 | 1 | 524288 | dm-1 |

## sys/

The /proc/sys directory contains a number of files that control kernel features. These can be written to, changing system behaviors on the fly. Never echo data into a file in /proc unless you are absolutely certain of what you are doing (or on a test machine that you're okay with bricking). It is highly unlikely that you will need to delve into this area of /proc during the course of an incident.

## uptime

This file will tell you two things: how long the system has been running, and how much of time spent idle. The latter we don't care about, but the former we do, for one very important reason. If you are told that the incident you are investigating occurred three days ago, and the system shows an uptime of 97,000 seconds (27 hours), you know that the machine has at the very least rebooted, which is important information to be aware of during an incident response engagement.

## version

This file provides more detailed kernel version information than you can get with a standard name -a, to include the gcc version used to compile the kernel.

```
Linux version 2.6.23.1-42fc8 (kojibuilder@xenbuilder4.fedora.phx.redhat.com) (gcc
version 4.1.2 20070925 (Red Hat 4.1.2-33)) #1 SMP Tue Oct 30 13:55:12 EDT 2007
```

## Process IDs

This is the information the /proc system is designed to provide access to, and is naturally the most vital area for investigation. Each of the numerous directories corresponds to the ID of a particular process. If you are familiar with UNIX systems, you’ll know that PID 1 belongs to the ‘init’ process. Now, let's examine the entries that are of importance to us during an investigation.

## cmdline

The command line used to launch the process. In our case it is:

```
init [5]
```

indicating that the system was booted into runlevel 5 (graphical multi-user, with networking).

## cwd

This is a link the processes' current working directory (cwd).

## environ

This file contains the environment variables for the process. This may not be of consequence in most investigations, but may come into play if you are dealing with a local privilege escalation attack. There are many cases where overly long or otherwise malformed environment variables can be used to exploit root processes, and this could be apparent in the environ proc entry for the compromised PID. environ is a multi-line non-terminated file. What this is more than using newline characters to indicate the end of a line, a null character is used; using "cat" to dump the output isn't the easiest way to deal with this data. Piping cat's output to xargs -0 -n 1 will print the output in a more digestible format, like so:

```
root@localhost 1]# environ | xargs -0 -n 1
HOME=/linux
```

## exe

This is a symbolic link to the actual executable of the process, in this case /sbin/init. If we had two processes named 'init', PID 1 and one PID 2, we'd be able to tell which is which.
