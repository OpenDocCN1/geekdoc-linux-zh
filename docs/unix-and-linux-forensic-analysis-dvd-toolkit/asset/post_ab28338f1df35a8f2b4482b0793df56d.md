## Shell History

Knowing who has done what is always of the utmost concern in any investigation. Fortunately for us, by default, Linux keeps a trail of user activity in the shell history, located in the /home/<user> directory. Remember, the shell history is only a record of one side of the conversation. It does not show you what the system responded to the particular command. So while gathering information about what was typed at the command line is a good gathering technique, like anything else, it should be used in conjunction with other data retrieved from the investigation.

In my examples, I am again using an Ubuntu 7.10 (Gutsy) distribution. To find the history files that exist on my system, I simply type:

```
locate bash_history
```

Understand that this command will only give you the .bash_history files. There are other shells which will create other history files. The most popular shells store their history files in the following locations with the /home/<user> directory:

- BASH: .bash_history
- C-Shell: history.csh
- Korn: .sh_history
- POSIX: .sh_history
- Z-Shell: .history

Again, by default, most Linux variants maintain a 500-line command history. To view the current command history of a system, type:

```
echo $HISTSIZE
```

Like else in Linux, this environment variable is configurable within the .profile of the individual user. If you find that the HISTSIZE has been modified from the default value, take note of it, and follow up with the customer's system administrator to find out if this was a configuration change on their part, or something that was done maliciously by an intruder (especially if the value has been set to zero).

Included on your tools disk are two scripts I have written to make parsing through user shell history files a bit easier. The first script is called "history_search.sh."

It takes the commands from all of the user history files on the local host, regardless of which shell has been used, removes the duplicate entries, and puts them into a single file in the current working directory called "outfile". You can use this file to review all of the commands used on the target host and determine if any of them requires further investigation. For example, if a command is found such as, "msf", indicating that the Metasploit Framework was invoked from the command line, you can then use the second script, "user_driller.sh" to find out which user(s) typed in this specific command. This script will create a directory driller in a user-specified location; however, the default is the current working directory.

> NOTE: One the limitations of the shell history files is that other than the Media Access Control (MAC) time, there are no timestamps within the file itself. While knowing what was typed in be useful for formulating an idea of what may have happened on the host, other correlative measures will have be taken to determine when these specific actions took place. Also tying a username to a command, or series commands only shows which username was used, not necessarily which user was actually using that account. A good hacker will likely use an existing user account to perform his nefarious tasks. This means that log file correlations will be of the utmost importance for you to be able to piece together the different aspects of the investigation.

## Logged on Volatils

When analyzing volatile data it is import to know which users are currently logged onto a system. Understand that most intruders are not so dumb as to create a user ID called "hacker." They will than likely use an existing user ID to conduct their illicit activities. They just like with shell history, additional chronological correlations will have to be made to determine the activities were part of normal business operations, or if they were the work of an intruder.

The output from the "who" and "w" commands are shown below in Figure 4.8. The results from the "w" may require a bit more information to fully comprehend what the user is looking at.

## Figure 4.8 Output from "who" and "w"

![](img/fd8e85097b37559dbc07dc22fd8cb1fe_95_0.png)

The header is pretty self explanatory. The fields shown are the current time, how long the system has been running, how many users are currently logged on, and the system load. However, starting at the usernames, let's go into a bit more depth on each of the items listed actually:

- **User**: Username
- **TTY**: Teletype. In the old days of computing, terminals were keyboards that were attached directly to printers called "tty." Where tty is either zero or a positive integer signifies a login from the console. Where tty is either pts or tty, it signifies a login over the network.
- **From**: This field shows where the user is logging in. In Figure 4.8, the "0" and ":0" indicates that am logged in from the console. For example, I was SSH'd into another box on the network, then that IP address or fully qualified domain name (FQDN) would appear in place of "0".
- **Login**: This is pretty self explanatory. It shows the time of the last login.
- **Idle**: This shows how long has been since the last activity. This information can be of specific note if you see users with long idle times.
- **JCPU**: The JCPU time is the time used by all processes attached to the tty. does not include past jobs, but does include currently background jobs.
- **PCPU**: The PCPU time is the time used by the current process named in the "what" field.
- **What**: What is the process that the user is currently running.

## Network Connections

Recall from the introduction, I referred to the lack of information sometimes called "negative evidence." While the data to prove negative evidence is mainly found in the customer's network, the local connections can prove to be equally useful. By running the netstat command with "-an", you can see which connections are being made to and from the host as well as on which port is being used and the state of that connection (either LISTEN, ESTABLISHED, or CLOSE_WAIT).
