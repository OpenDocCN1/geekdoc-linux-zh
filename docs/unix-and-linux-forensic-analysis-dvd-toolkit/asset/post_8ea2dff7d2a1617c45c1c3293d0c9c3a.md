Naturally when working on a potentially compromised box, it'd be folly to trust the output of the binaries installed on that machine. Having a CD that includes statically linked versions of these commands and running those binaries instead of the (possibly modified as part of a rootkit) installed versions is always a wise idea.

Finally, two command-line features of modern *nix that Windows might overlook are filename completion and command completion. Try it! Start typing a filename and hit that TAB. Hit again if nothing happens. When you see that long filename get completed, or a list of possible completions appear instantly, you'll wonder how you ever lived without it. Incidentally, Windows cmd.exe has filename completion, but you may have to tweak a registry entry to enable it. Also, prior command history is available often with hitting the up arrow, which can save a lot of retyping. Windows also has a similar feature.

# Highlights of The Linux Security Model

Linux and *nix are a lot pickier about security than Windows. Security permeates the design of the operating system in *nix rather than a bit of an afterthought sometimes it feels like Windows. For instance, in the *nix world, there is no such thing as your default user as Administrator. If you want to do something that will dramatically change your system, you need to do it as the administrative user, and anyone that does 100 percent of their work logged in as root is considered, well, a bit of a dangerous duty. And happily, since the operating system was designed with this model in mind from the ground up, it is not painful to run this. Any of you who have ever tried to make Windows actually usable running as a Limited User know.

User accounts in Linux fall into three categories: they are either the super (normally named root), system accounts (such as mail, uuc, bin, lp, nobody, apache), or normal user accounts (james, todd, chris). In *nix, root is akin to Administrator in Windows.

Authentication in *nix can be done in a lot of different ways, but the simplest (and default) setup is local authentication. User accounts are stored in a plain text file /etc/password and passwords are stored in their hashed form in /etc/shadow (or /etc/security/shadow in some *nix). All users can read /etc/password, but, so that no user can grab the hashes to stop cracking passwords, only root and the shadow group can read /etc/shadow. Have a look for yourself:

```
ubuntu@ubuntu:~$ ls -l /etc/shadow /etc/passwd
-rw-r--r-- 1 root 1426 2008-03-23 14:27 /etc/passwd
-rw-r--r-- 1 root 877 2008-03-23 14:27 /etc/shadow
| | |
  | --- owner/user permission bits
  | group permission bits
      world/other permission bits
```

Above, we see the long format listing for shadow and passwd files. The listing serves as our first introduction to *nix file permissions. The permissions on the left show what the owner, group, and others can do. r is read, w for write, x for execute. In this example, /etc/passwd has -rw-r--r which is (readable) by its owner (root), group, and others. It is only writable by its owner (root). Anyone wanting to change /etc/passwd will need root privileges (either “su -” to switch to user root, or be in the admin group or just prepend with sudo). File permissions can also be expressed numerically. The chmod and umask commands are where you'll find this most frequently -rw-r-- can be expressed as 644. In binary, the execute bit is the least significant (2^0 = 1), the write bit is the most significant (2^1 = ), and the read bit is the third position (2^2=4). For owner, read and write bits are set corresponding to 4+2=6. For group and world, we'll create a blank file named foo, and exercise different ways to modify the file permissions with chmod. # is the comment character in *nix shell, the shell ignores everything after a comment character. We'll use this to annotate commands in examples.

```
ubuntu@ubuntu:~$ touch foo
ubuntu@ubuntu:~$ ls -l foo
-rw-r--r-- 1 ubuntu ubuntu 0 2008-04-14 20:25 foo
ubuntu@ubuntu:~$ chmod go-r foo # remove group and other permission
ubuntu@ubuntu:~$ ls -l foo
-rw------- 1 ubuntu ubuntu 0 2008-04-14 20:25 foo
ubuntu@ubuntu:~$ chmod 644 foo
ubuntu@ubuntu:~$ ls -l foo
-rw-r--r-- 1 ubuntu ubuntu 0 2008-04-14 20:25 foo
ubuntu@ubuntu:~$ chmod 777 foo # set read write and execute bits (dangerous)
ubuntu@ubuntu:~$ ls -l foo
-rwxrxr-x 1 ubuntu ubuntu 0 2008-04-14 20:25 foo
ubuntu@ubuntu:~$ chmod 000 foo # strip all the permissions
ubuntu@ubuntu:~$ ls -l foo
---------- 1 ubuntu ubuntu 0 2008-04-14 20:25 foo
ubuntu@ubuntu:~$ cat foo  # Can't even read our own file now
```
