## Mount points: What the Heck are They?

We've mentioned file system and mount several times. A mount point is simply an empty directory we create somewhere in the file hierarchy where we will access an internal disk partition, flash drive, or external hard drive. In Windows parlance, “c:\ can be thought of as the mount point for the first partition of the drive window recognized during boot. While the Windows ARC name for drive is something cryptic and awful like multi(X):disk(Y)disk(Z)partition, Windows kindly mounts that piece of hardware to a friendly mount point of c:\ that looks nicer at the command prompt and in Windows explorer. Likewise, Windows likes to mount the secondary master to d:\ than having to refer to the CD-ROM drive with a long nasty series of parentheses and digits. *unix eschews drive letters and instead allows you the flexibility to hang a drive nearly any directory name you like. This allows for /var to have its own file system if you like, your logs won't wedge your system if they fill the disk. You can dedicate a partition to /home so Joe User doesn't wedge the system downloading a bunch of movies from bittor. Instead, he'll fill up the disk that /home is mounted to. Users will still hate him, but at least running the daemons (think Windows “services”) will be able to write to their logs and e-mail will still get delivered.

Linux stores this disk device to file system to directory-name mapping information in what's known as “mount table.” The command allows you to list it out, and you have manual control over which devices are mounted by Linux:

```
ubuntu@ubuntu:~$ mount
proc /proc type proc (rw)
sysfs / /sys type sysfs (rw)
tmpfs / /lib/modules/2.6.22-14-generic/volatile type tmpfs (rw,mode=0755)
tmpfs / /lib/modules/2.6.22-14-generic/volatile type tmpfs (rw,mode=0755)
varrun /var/run type tmpfs (rw,noexec,nosuid,nodev,mode=0755)
varlock /var/lock type tmpfs (rw,noexec,nosuid,nodev,mode=1777)
udev /dev type tmpfs (rw,mode=0755)
devsm /dev/shm type tmpfs (rw)
devpts /dev/pts type devpts (rw,gid=5,mode=620)
tmpfs /tmp type tmpfs (rw,nosuid,nodedev)
```

The mount table tells you the device you've mounted, the mount point to it's mounted, the file system type it's being interpreted as, and any mount options, such as rw (mounted for read/write access).

You can mount disks in mode "ro" for read only; something you may desire for doing forensic investigation, for instance (though it's hard to beat the assurance that with a parallel ATA drive connected that the write wires are physically disconnected). Consult the mount page for details, which we'll wet your appetite with some examples.

One thing that's nice about LiveCD is that you can use it to peek into the event of a Windows disk if/when Windows is misbehaving or can't be trusted in the event of a malware infection. The way to do this is to mount your internal hard drive. In *nix, with utilities like mount and finger installed by default, you'll just have to get to use these things.

To mount your local drive read-only, you'll first create a mount point (empty directory), and then we'll attempt to mount it:

```
ubuntu@ubuntu~$ ls /dev/sd*
/dev/sda /dev/sda
```

```
ubuntu@ubuntu~$ mkdir /mnt/mywindrive
mdir: cannot create directory '/mnt/mywindrive': Permission denied
ubuntu@ubuntu~$ # Doh! Mortals don't have write permission to /mnt
ubuntu@ubuntu~$ sudo mkdir /mnt/mywindrive
```

```
ubuntu@ubuntu~$ ls /mnt
mywindrive
```

```
ubuntu@ubuntu~$ sudo mount -o ro -t auto /dev/sda1 /mnt/mywindrive
ubuntu@ubuntu~$ mount
proc on /proc type sysfs (rw)
sysfs on /sys type sysfs (rw)
tmpfs on /lib/modules/2.62.22-14-generic/volatile type tmpfs (rw,mode=0755)
tmpfs on /lib/modules/2.62.22-14-generic-volatile type tmpfs (rw,mode=0755)
varrun on /var/run type tmpfs (rw,noexec,nosuid,mode=0755)
varlock on /var/lock type tmpfs (rw,noexec,nosuid,mode=0777)
udev on /dev type tmpfs (rw,mode=0755)
devshm on /dev/shm type tmpfs (rw)
devpts on /dev/pts type devpts (rw,gid=5,mode=620)
tmpfs on /tmp type tmpfs (rw,nosuid,nodev)
/dev/sda1 /mnt/mywindrive type fuseblk(ro,nosuid,nodev,allow_other,blockSize=4096)
```

In all likelihood, if you have a relatively "normal" Windows PC that hasn't partitioned creatively or installed to non-default disk, your Windows partition is likely named /dev/sda. In our example, we listed out all of the Linux populated into /dev/sd* upon bootup for reassurance. If you see /dev/sda1 and /dev/sda2 though, you may have an OEM PC that includes a “service partition” for recovery, /dev/sda1. If you are using a different Linux and do not have any devices starting with sd, /dev/sda might be where you'll find your internal hard drive's first partition. Incidentally, other than Linux, the hard device naming is entirely different, so you'll have to let your fingers do the Googling for information on those when you encounter them. Next, we created the mount point including a directory in /mnt. In the mount command itself, we specified the read only option just to be safe, and allowed mount to determine the file system type of your partition. The last line of the “mount” command reveals that it mounted only (ro option happily displayed) with a type of fuseblk. Fuse is used by NTFS to bring reliable write capability to Linux (ntfs-3g). Finally note that the external drive was mounted noisy, which is why we don't want to hoist the SUID bits of any file system on our machine because a file is trusted as the superuser on many. Now hang out ubuntu:~$ ls /mnt/mywindrive/

```
AUTOEXEC.BAT      pagefile.sys
boot.ini          IO.SYS          Program Files
CONFIG.SYS        RECYCLER
cygwin            Documents and Settings msw.dll  swtools
drivers           System Volume Information
drive.log         NTDETECT.COM    DvrData
ntldr             WINDOWS
```

So, you've mounted a NTFS volume in Linux Beta that you can't mount a native ext3 partition in Windows without a lot more (and third-party software). Finally, to unmount, it's simply the “umount” command with the mountpoint named. A quick verification that it's gone is always reassuring:

```
ubuntu@ubuntu~$ sudo umount /mnt/mywindrive/
unknown@ubuntu~$ mount
proc on /proc type proc (rw)
sysfs on /sys type sysfs (rw)
```

A common mistake is to try to mount a drive while still cd'd into mount point. Linux doesn't like this more than Windows does when you try to eject a thumb drive that you're still browsing in Windows Explorer. To remedy, simply cd out of the mount point, close any programs that might be accessing the drive in, and retry the um command.

## File Systems

In Windows, life is rather simple in the file system realm. You had only two--disk file system to worry about (FAT and NTFS), and a few generations with each. The FAT side of the house (which you only seem to find on removable drives these days), FAT32 rules the root. We fondly recall the old days of FAT16 and its 2-4GB maximum partition size. FAT32 gives us a more volume size to play with up to 2–8TB, but is hamstringed by 4GB file sizes that cause video and database masters to wrinkle their noses. In addition, none of the FAT variants supported a notion of file permissions, which made them a non-starter for the enterprise.

NTFS and its five revisions since the days of Windows NT 3.1 addressed the permissions concern, as it has very flexible support for file access control lists (ACLs). NTFS also added journaling to the filesystem, which makes the NTFS file system more robust against corruption caused by power interruptions or the dreaded yanking of an external drive without properly ejecting it. As such, we don't have to run scandsk or chkdsk often as we recall calling back in the old days of Windows 95/98. More interestingly to forensic investigators was NTFS's inclusion of alternate data streams (ADS) where the bad guys can hide data from priming eyes.

In Linux, things are more complicated on the filesystem front because it supports many file systems. Linux's list of supported file systems includes FAT16, FAT32 in a few flavors, and NTFS in a few flavors. Linux's native file system is ext2.
