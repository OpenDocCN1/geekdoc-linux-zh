
higher-than-normal privilege, however: setUID and setGID executables. These are executables that have the SUID or GUID bit set. When executed, rather than running with the privileges of the user that launched the program, run with the privileges of the user or group that owns the file. Generally, SUID/SGID root executables are the most worrisome, but depending on the environment you are working in, other users or groups may be of concern as well. A security vulnerability or misconfiguration in a SUID/SGID executable can lead to an elevation of privileges on the local system. Locating these files is very important.

The “find” command is your best friend when you need to quickly locate files based on very specific criteria.

```
find / -perm -4000 -type f -xdev -print > suid.txt
find / -perm -2000 -type f -xdev -print > sgid.txt
```

These commands will begin at the system root (/) and find all files with permissions (-perm) of 4000 or 2000 (setUID and setGID, respectively) that are normal files (-type f) and print their full path to standard output, which is redirected to the names. We specify normal files to exclude block devices, characters devices, sockets, and other similar items. The -xdev flag ensures that find won't descend into directories you may search, on file systems such as NFS/SMB mounts, mounted CD/DVDs, and any external storage you may have mounted. Unfortunately, this will also prevent from descending into directories you may want to search, for example, a system that has /var /tmp on separate partitions /. In this case, you may want to substitute “-type f” for -xdev. For more options, check the file man page.

## Recently Modified/Accessed/Created Files

If you have suspected some time frame for a compromise may have occurred, you can easily look for all files modified, accessed, or created around or since that date. For example, if a system administrator noticed unauthorized outbound IRC connections beginning five days ago, you could do the following:

```
find / -mtime 5 -xdev > modified.txt
find / -atime 5 -xdev > accessed.txt
find / -ctime 5 -xdev > created.txt
```

While it is certainly trivial to modify the timestamp of a file on a Linux system using the (“touch” command), this is another place where attackers sometimes simply make the effort. The output of these files may be a little noisy, but they should provide a starting point.

## Modified System Files

Identifying system files that have been modified since they were installed by your package manager, isn’t difficult. For RPM–based systems:
...

```
rpm -V -a
```

And for .deb systems, you can use debs:

```
debs -ca
```

A couple of caveats are needed here. First, the fact that a particular file has been modified doesn’t necessarily indicate a compromise, especially if it is a configuration file, as these are likely to be modified. The second, absence of modification does not mean a system should be given a clean bill of health. On a live, compromised system, an attacker may have modified the command you are running, the database it is reading from, or the kernel itself. These commands provide you pieces of data that you’ll need to put together to form the picture.

## Out-of-Place inodes

This is a somewhat esoteric trick, but it can be used effectively in some scenarios. First described (to my knowledge) in “Forensic Discovery,” the authors noted that inodes are typically allocated in sections, and outlying inodes may be used to find replaced binaries and trace them back to their creation location. You can find the node number of a file using the -i flag:

```
[root@localhost /bin]# ls -fi
```

## File Analysis

We can plainly see that the ls binary number is not in line with the other items in the /bin directory. So where did this invade from?

```
find -xdev -print | xargs ls -id | sort -n
164017 /tmp/toolkit.tgz

164019 /tmp/.toolkit/ls
164020 /tmp/.toolkit/.chroot
```

We can be pretty certain at this point that “ls” wasn't modified as part of a system update.
