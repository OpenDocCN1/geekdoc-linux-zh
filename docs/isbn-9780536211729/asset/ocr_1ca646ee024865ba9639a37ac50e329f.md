# 3.4.1.7 Executables and Dynamic Libraries.

When an ftp user uses the command or its synonym is, ftpd invokes the ls Linux command to generate the data that ftpd sends back to the user. The problem is that the ftpd daemon is running in a chrooted environment (where it normally does for anonymous FTP access), it does not have access to /bin/ls nor to any dynamic libraries that ls would use. The solution is to put ls in ~ftp/bin and provide any dynamically linked libraries that it might need in ~ftp/lib. Most distributions such as Red Hat do and Red Hat even offers an anonymous FTP RPM containing these programs and dynamic libraries.

All needed files should be installed on your system already if you asked for the appropriate packages to be loaded. Slackware builds a special statically linked program that is installed as libraries. ~ftp/bin/ls so that the SysAdmin does not need to bother with dynamic libraries. Red Hat does not do this but it puts tar and gzip in there so that ftpd automatically can convert between compressed and uncompressed files and tar and untar data too. It includes the shell, she.

I worry that the presence of this apparently unrestricted shell opens a security hole. I might prefer the Slackware solution. Of course, because it is Linux, you can put the Slackware ~ftp/bin program on your otherwise Red Hat system, after removing the Red Hat programs and dynamic libraries from ~ftp/bin and ~ftp/lib, and it should work just fine. This is assuming that the version of the Slackware ls program is compatible with the version of the Red Hat kernel. This is usually not a problem and if it is then it will refuse to run.

I have compiling a complex CGI C program on Slackware and running it on many different versions of Red Hat and Mandatory for six years to work around a bug in Red Hat's ctime() library, now fixed.
