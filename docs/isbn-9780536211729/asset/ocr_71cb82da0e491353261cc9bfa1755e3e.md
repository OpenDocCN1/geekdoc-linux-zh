Many of the system break-ins relating to Linux Web servers happen via insecure CGIs. All it takes is one buggy CGI and most systems will be broken.

# D. Implement “Rings of Security” in CGIs.

Try to design your application so that even if a vulnerability is found, the system is protected from major damage. One solution is to have CGIs just front ends for a solidly written running server on a different machine. The more hurdles a kernel must jump to reach the goal, the more likely it is that he will stumble.

Consider using the SubDomain kernel module for WireX. It allows kernel-based access control lists on a per-program basis to add additional limits to what any given program may do. It can prevent many of the recent security breaches, such as the named bug and the Dansie “fiasco,” both discussed elsewhere in the book. Its object is only about 24 KB and is easy to install; WireX is generous with its allowance for free use. Its developer previously StackGuard. It is available at:

```
www.wirex.com/subdomain.html
```

# E. Watch for bug reports in third-party-supplied CGIs and inspect their code.

If using third-party-supplied CGI scripts (such as shopping carts), subscribe to their mailing lists and watch for security bulletins. If possible, get the source code and review it. If you do not know the language, people who do and have them review it.

In the spring of 2000 Joe Harris made a posting to Bugtraq, claiming that a popular Perl-based shopping cart program, Dansie, has a back door. Harris claimed that this back door allows anyone who knows the secret form name (URL on the server’s system) to execute any Linux command as the user running the shopping cart software.
