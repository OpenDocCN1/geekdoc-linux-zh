In other words, some of the contextual knowledge usually associated with the upper TCP Transport layer, or the UDP Application layer, is brought down to the filter layer.

After the exchange is initiated and accepted, subsequent packets are identified as part of the established exchange. Associated ICMP messages are identified as being related to a particular exchange.

For session monitoring, the advantages of maintaining state information are less obvious because TCP maintains state information by definition. For UDP, the immediate advantage is the capability to distinguish requests from other data. In the case of an outgoing DNS request, which represents a new UDP exchange, the context of an established session allows an incoming UDP response from the host and the original message sent to, within a certain time-limited window. Incoming datagrams from other hosts or ports are not allowed. They are not part of the established state for this particular exchange. When applied to TCP and UDP, ICMP messages are accepted if the error message is related to the particular session.

In considering packet flow performance and firewall connectivity, the advantages are more obvious for TCP flows. Flows are primarily a firewall performance and optimization technology. The main goal of flows is to allow bypassing the firewall inspection path for a packet. Much faster TCP packet handling is allowed because the remaining filters can be skipped if the TCP packet is immediately recognized as part of an allowed, ongoing connection. For TCP connections, flow state can be a major win in terms of filtering performance. Also, standard TCP protocol rules can be collapsed into a single allow rule. The number of filters is reduced (theoretically, but not necessarily in practice).

The disadvantage is that maintaining a state requires more memory than standard firewall filters alone. With 70,000 simultaneous connections, for example, would require tremendous amounts of memory to maintain state information for every connection. State maintenance is often done in hardware for performance reasons, where associative table lookups can be done simultaneously or in parallel. Whether implemented in hardware or software, state engines must be capable of reverting a packet to the traditional path if memory is not available for the state table entry.

Also, creation, lookup, and teardown take time. State maintenance is a loss for ongoing exchanges as an FTP transfer or a UDP streaming multimedia session. Both types of data flow potentially represent large numbers of packets (and filter match tests). State maintenance is not a firewall performance for a simple DNS or NTP client/server exchange, however. State buildup and teardown can easily require as much processing—and more memory—simply traversing the filter rules for these packets.

The advantages are also questionable for firewalls that filter web traffic. Web client/server exchanges tend to be brief and ephemeral.
