## Service Ports: The Door to the Programs on Your System

What happens? As shown in Figure 4.6, a web server is running on a machine somewhere, waiting for a connection request on TCP service port 80. You click on the link for a URL in Netscape. Part of the URL is parsed as a hostname, the hostname is translated into the web server's IP address; and your browser is assigned an unprivileged port for the connection, TCP port 14000) for the connection. An HTTP message for the web server is constructed. It is encapsulated in a TCP message, wrapped in an IP packet header, and sent out. For our purposes, the header contains the fields shown in Figure 4.6.

Additional information is included in the header that is not visible in the packet-filtering level. Nevertheless, describing the sequence numbers associated with the SYN and ACK flags clarifies what's happening during the three-way handshake. When the client program sends its first connection request, the SYN flag is accompanied by a synchronization sequence number. The client is requesting a connection with the server and passes along a starting sequence number it will use as the starting point to number all the rest of the data bytes the client will send.

The packet is received at the server machine. It's sent to service port 80. The server is listening to port 80, so it's notified of an incoming connection request (the SYN synchronization request flag) from the source IP address and port socket pair (your IP address, 14000). The server allocates a new socket on its end, (web server address, 80) and associates it with the client socket.

Two fields not visible to the packet-filtering level are included in the SYN-ACK header. Along with the ACK flag, the server includes the client's sequence number incremented by the number of contiguous data bytes received. The purpose of the acknowledgment is to acknowledge the data referred by its sequence number. The server acknowledges this by incrementing the client's sequence number, effectively saying it received the data, and sequence number plus one is the next data the server expects to receive. The client is free to throw its copy of the original SYN message away now that the server acknowledges receipt of it.

The server also sets the SYN flag in its first message. As with the client's first message, the SYN flag is accompanied by a synchronization sequence number. The server is passing along its own sequence number for its half of the connection.

This first message is the only message the server will send with the SYN flag set. With this and all subsequent messages have the ACK flag set. The presence of the ACK flag in all servers, compared to the lack of ACK flag in the client's first message, will be a critical difference when we get to the information available for constructing a firewall.

Your machine receives this message and replies with its own acknowledgment, after which the connection is established. Figure 4.8 shows a graphical representation of this. From here on, both the client and the server set the ACK flag. The SYN flag will not be set by either program.

With each acknowledgment, the client and server programs increment their partner process's sequence number by the number of contiguous data bytes, plus one, indicating receipt of that, and indicating the next data byte in the stream they expect.

## PACKET-FILTERING CONCEPTS

What is a firewall? Over the years, the term has changed in meaning. According to RFC 2647, "Benchmarking Terminology for Firewall Performance," a firewall is "a device or group of devices that enforces an access control policy between networks." This definition is very broad, purposely so in fact. A firewall can encompass many layers of the OSI model and may refer to a device that does packet filtering, performs inspection and filtering, implements a policy on an application at a higher layer, or does any of these and more.

A stateless firewall usually performs packet filtering based solely on the IP layer (layer 3) of the OSI model, though sometimes higher-layer protocols are involved in this type of firewall. An example of this type of device might include a border router that sits at the edge of a network and implements one or more access lists to prevent types of malicious traffic entering the network. Some might argue that this type of device isn't a firewall at all. However, it appears to fit within the RFC definition.

A border access list might implement many policies depending on which interface the packet was received on. It's typical to filter certain packets at the edge of the network connecting to the Internet. These packets are discussed later in this chapter.

As opposed to a stateless firewall, a stateful firewall is one that keeps track of the packets previously seen within a given session and applies the access policy to packets based on what has already been seen for the given connection. A stateful firewall implies the basic packet filtering capabilities of a stateless firewall as well. A stateful firewall will, for example, keep track of the stages of the TCP three-way handshake and reject packets that appear out of sequence for handshake. Being connectionless, UDP is somewhat trickier to a stateful firewall because there is no state to speak. A stateful firewall tracks recent UDP exchanges to ensure that a packet that has been received relates to a recent packet.

An Application-level gateway (ALG), sometimes referred to as an Application-layer gateway, is yet another form of firewall. Unlike the stateful firewall, which has knowledge of the Network and possibly Transport layers, an ALG primarily handles layer 7, the Application layer of the OSI model. ALGs typically have deep knowledge of the application data being passed and can look for any deviation from the normal traffic for the application in question.

An ALG will typically reside between the client and the real server and for all intents and purposes, mimic the behavior of the real server to the client. In effect, local traffic never leaves the LAN, and remote traffic never enters the LAN.
