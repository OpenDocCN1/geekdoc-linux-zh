It is worth the time spent configuring the /etc/syslog.conf file so that you can more easily spot evidence of crackers by separating this evidence into files separate from routine entries. It is important, too, to spend the time to set up programs to scan the log files automatically for these cracking attempts, because people are notoriously bad at such mundane tasks. Note that the two fields must be separated by tabs, not spaces, for them to be interpreted correctly.

In distributions, this file has a line similar to

```
*.info:mail.none;auth.none;authpriv.none    /var/log/messages
```

that dumps every message into the log file. If this line (or something similar) is missing, I certainly recommend adding it. It causes all messages of severity info or greater to be logged here except that no mail, auth, or authpriv messages will be logged because they are located elsewhere.

Because there need to be so many mail messages and they are largely uninteresting, you normally dump them into a separate file thus:

```
mail.info /var/log/mail
```

The following entry will log all security-related messages that might indicate problems:

```
*.warn;authpriv.notice;auth.notice    /var/log/secure
```

You probably also want to log “routine” security messages, such as successful logins, in case you later discover that there was a compromised account and you want to find when it was used.

```
authpriv.debug;auth.debug    /var/log/secure.ok
```

> There are many parts of “Finding and Repairing the Damage” on page 479 that are useful, so looking at this section now might be helpful.

Many times, you happen to notice something as unusual entries in a log file are the first indications that someone has broken into your system. Crackers know this too! Any decent cracker simply will edit your log files with vi or emacs to remove the evidence of their visits. This is quite easy and typically is done before logout.

There are two situations that need to be considered. The first is where the attempted break-in fails. This could be handled by mailing a copy of each important log file to your e-mail account on a different system periodically and then truncating the log file. Truncating means removing the information from the file and making it zero without actually removing it, important because the file may be held open by other processes.

Typically, you would do this via a cron job. The following script could be placed in your /usr/local/bin directory for forecasts mode 700 and owned by root. The name was made somewhat ordinary deliberately.

```
#!/bin/sh
cd /var/log/
for f in crit messages syslog secure secure.ok \
daemon ftpd/xferlog lpr cron mail
do
  if [ -s $f ]; \
then
    Mail -s "LOG: $f" \\
      jimjoyce@othersys.vault.com < $f
      # Save if mail fails
    cp $f $f.old
    cp /dev/null $f
fi
```

In this example, you directly specify the SysAdmin's e-mail address. However, if the system administration duties are shared, or if the SysAdmin goes on vacation, it would be much better to e-mail to root or some other official address and redirect e-mail destined for that address to one or more of the SysAdmins or for the one to check for e-mail frequently. Most shells and mail alerting programs (like xbiff) can monitor multiple mailboxes.

You could also arrange the script to be invoked daily at 7 A.M. via a crontab entry by root thoroughly:

```
-crontab -l > /tmp/foo22
cat >> /tmp/foo22
00 07 * * * /usr/local/bin/forecasts
control-D
crontab /tmp/foo22
/bin/rm /tmp/foo22
```

By emailing an account on a different system, a cracker would need to break into two different systems to erase her tracks. By picking said other system to be one with very tight security, possibly on a different network or organization, which would make her job impossible.

There is a small race condition in the script in the event that a log entry is generated the instant it is running. Allowing for 0.1 seconds for the script to run and 86,000 seconds in a day, this window will lose significant entry about every million days.

In newer distributions of Linux there is the logrotate program that works with the daemons themselves to rotate the log files periodically without race conditions. In other words, because log files tend to grow to be very large, the logrotate program periodically rename each one to a backup name and then will ask its daemon to start using a new copy of the log file.

You could get more elaborate by using grep or awk to filter out the many unwanted entries. Using Logcheck or other automatic filtering program would be even better, though a periodic scan of the raw log files is still recommended. Logcheck is discussed in “Using Logcheck to Check Log Files You Never Check” page 346.

The logrotate program is driven by a powerful configuration file with the unexpected name of /etc/logrotate.conf. You can add the filtering and mailing commands discussed to this file easily.

### 8.3 Using Logcheck to Check Log Files You Never Check

| DANGER LEVEL |

The Logcheck program analyzes a system's most massive log files, extracts anything that might indicate (1) an attack, (2) a security violation, or (3) other abnormality (listed in order of severity), generates a report summarizing these events, and informs the SysAdmin via email. For those that do not check their log files on a daily or hourly basis (which is almost everyone), this does work. It is invoked from each system's root crontab, typically either or hourly. It is important to recognize that this is an Intrusion Detection System (IDS) that does not operate in real time. Even if it is invoked, it still gives a cracker an average of 30 minutes to damage under the best circumstances and an entire weekend under the worst circumstance.

In its standard form from Psionic, it provides a “general feel” for what type of activity your static firewall has been triggered by, and also shows what Portsentry² has triggered

1. Snort is recommended as a full real-time IDS. Snort should be used in connection with Logcheck, instead of it.
2. Portsentry is Psionic's excellent capability. It is discussed in “Using Portsentry to Lock Out Hackers” on page 351. If it finds principal advantages over my Cracker Trap is that it will detect scans and that it can take less effort to configure (Stealth TCP scans are only when the Cracker sends only the first of the packets a client needs to establish a TCP connection or defective packets are sent.) The Cracker Trap has better notification. Frequently, I will install both on a firewall to get the best coverage and for an extra layer of security.
