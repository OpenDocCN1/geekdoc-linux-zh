The rest of this section will address CGI problems specifically.

A CGI program will allow anyone to access your Web site, good intentions or not. Other “accepted” servers, such as sendmail and named, will also talk with anyone, the scope of a client may request is far smaller. While latter servers have shared their story of serious security bugs, that keep up-to-date (as discussed in “Old Software Versions (#3) on page 25) have minimal risk. Here are a few hard rules that will help you make your Web site secure.

## A. Never, ever, run your server as a privileged user (as root).

Even some documentation for various products there to seduce you into running Apache as root. You will get hacked if you do.

## B. Know your data (that is supplied by Web clients).

- Establish maximums and minimums for data entry values and lengths of fields.
- Decide what controls are acceptable in each field. The malicious will send control characters and non-ASCII bytes. Expect that crackers will use the `%` encoding to generate these evil characters. `%` encoding is a `%` followed by two hexadecimal characters that will be mapped to the equivalent ASCII character. Unless you stop them, they will use this method to secure your CGI programs with arbitrary binary files. This makes it easy to overflow input buffers and drop machine code (instructions) directly into CGI programs.

Thus, you need to check for illegal characters before and after `%` conversion. I have seen this latter attempt used against our sunset CGI program, fortunately without success.

- Double-check each entered value. A surprising number of shopping cart packages accept the price of items in the form and believe the price in the filled-out form sent by the user. All a user needs to do is alter this form and give himself a discount. Very little skill is required for a user to exploit this. It has been reported that Cart32 versions 2.5a, 2.6, and 3.0 have this “price in the form” bug; even though this was widely known for four months, the vendor has chosen not to repair this problem.
- If possible, enumerate the allowed values instead of using ranges.
- Understand that even an evil Web client can send any bytes back to your server. The cracker might copy and alter your Web form so that, even if your form pops up a list of the member European Union countries, she could supply:

```
crash_with_a_long_name_having_control_characters
```

- Use a secure language. Client-supplied data should never be handed directly to a shell script; there are too many opportunities for a cracker to get a shell or to exploit a buffer overflow vulnerability. You know how bash or csh react to buffer overflows? Neither do I, so you must not trust them in situations where a buffer overflow is possible.

For many, secure language will be C, Perl, or Python. If that does not fit all, what is use for each CGI, consistent with programmer skills. Perl does not fit as well as it has a number of features to enable safer CGI programs. These include the “tainted data” feature, the -w flag to warn you about things that you are creating but not using, and the strict capability that is discussed in [http://www.cpan.org/doc/manual/strict.html](http://www.cpan.org/doc/manual/strict.html).

Even more can be achieved with perlsec, discussed in [www.perl.com/CPAN-local/doc/manual/html/pod/perlsec.html](www.perl.com/CPAN-local/doc/manual/html/pod/perlsec.html).

## C. Analyze CGIs for vulnerabilities.

When writing CGI programs, look at what the cracker will do to break them. Check for buffer overflows using good programming techniques. For example, when using C, make use of the `fgets()` routine which allows the programmer to specify how large a buffer has been allocated and not overflow it. An easy way to determine if the line is larger than the buffer is to see that it does not end with a newline character, as this example illustrates.

## The Seven Deadly Sins

```c
#include <stdio.h>
#include <string.h>

int c;
char buf[200];

if (!fgets(buf, sizeof buf, stdin))
    error();
else if (!strchr(buf, '\n')) {
    /* Read rest of long line. */
    while ((c = getchar()) != EOF
        && c != '\n');
}
overflow();
```

Do not use the `gets()` routine because it does not do any checking for buffer overflows; use `fgets` instead. Many of the other popular C string functions have similar weaknesses. The `strcpy()` function, for example, "lets" you copy a large buffer into a small buffer, overwriting unallocated memory. The `strncpy()` function is a good replacement for it.

```c
strncpy(dest_buf, source_buf, sizeof dest_buf);
dest_buf[sizeof dest_buf - 1] = '\0';
```

To detect a problem, one possibility is:

```c
if (strlen(source_buf) >= sizeof dest_buf)
    error();
else
    strcpy(dest_buf, source_buf);
```

Check for escape sequences, the possibility of a client issuing commands (by inserting spaces, quotes, or semicolons); binary data, calls to other programs, etc. Often it is safer to have a list of allowed characters rather than trying to determine each unsafe character.

The following code may be used to process a field that the client should supply their name in. In this example, the calling process supplies a NUL-terminated string and this returns 0 if the string is a legal name and -1 otherwise. The second argument specifies the maximum legal string allowed, including the terminating NUL byte. Note that the routine must be careful to ensure that its buffer does not overflow. I chose clear code over slightly more efficient code.

```c
#include <string.h>

char okname[] = "abcdefghijklmnopqrstuvwxyz"
               "ABCDEFGHIJKLMNOPQRSTUVWXYZ";
/* Return 0 on legal names, -1 otherwise. */
legal(char *name, int maxlen) {
    if (!name || !*name
    || strlen(name) >= maxlen)
        return -1;
    while (*name)
        if (!strchr(okname, *name++))
            return -1;

    return 0;
}
```

Many of the system break-ins relating to Linux Web servers happen via insecure CGIs. All it takes is one buggy CGI and most systems will be broken.

## D. Implement “Rings of Security” in CGIs.

Try to design your application so that even if a vulnerability is found, the system is protected from major damage. One solution is to have CGIs just front ends for a solidly written running server on a different machine. The more hurdles a kernel must jump to reach the goal, the more likely it is that he will stumble.

Consider using the SubDomain kernel module for WireX. It allows kernel-based access control lists on a per-program basis to add additional limits to what any given program may do. It can prevent many of the recent security breaches, such as the named bug and the Dansie “fiasco,” both discussed elsewhere in the book. Its object is only about 24 KB and is easy to install; WireX is generous with its allowance for free use. Its developer previously developed StackGuard. It is available at: [www.wirex.com/subdomain.html](www.wirex.com/subdomain.html).

## E. Watch for bug reports in third-party-supplied CGIs and inspect their code.

If using third-party-supplied CGI scripts (such as shopping carts), subscribe to their mailing lists and watch for security bulletins. If possible, get the source code and review it. If you do not know the language, find people who do and have them review it.
