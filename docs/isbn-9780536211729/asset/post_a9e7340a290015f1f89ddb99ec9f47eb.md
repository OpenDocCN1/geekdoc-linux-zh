
## Using PortSentry to Lock Out Hackers

To install the downloaded 1.1 version, do the following:

```bash
tar -xovf portsentry-1.1.tar.gz
cd portsentry-1.1
```

Have a look at the LICENSE and README* files. Improvements in the 1.1 version include support and bug fixing for the 2.4 kernel, IP Tables, and netmask support. The README, COMPAT file lists the compatible platforms, which include Linux, popular versions of UNIX, and OSX for the Mac.

Follow these steps to configure and invoke PortSentry:

- **portsentry_config.h**. If any of these are not to your liking, now is the best time to change them. The `/etc/hosts.deny` file is only used if you have selected TCP Wrappers for the Adaptive Firewall option instead of more effective methods, such as IP Tables. If you want to get fancy, you could change the `SYSLOG_FACILITY` to `DAEMON` to, perhaps, `LOG_LOCAL0`, edit `/etc/syslog.conf` to place these messages in a separate file and monitor them carefully. While "An Example for Automatic Paging" on page 358 explains how to do this, a better solution would be to set `KILL_RUN_CMD` to generate e-mail to your pager.

- **portsentry.conf**. It is not a shell script but will rule that many lines beginning with the # character and blank lines are ignored. The = is used to assign a quoted value to a variable. You will want to specify what TCP and UDP ports to trigger and what action to take. While this file is reasonably well-commented, it is important to note that PortSentry only uses the variables that apply to the mode of protection selected by command-line flags. It has suggested values that form a good starting point for customizing it for your site. You may need to adjust, depending on what services you offer on your system. If it will be running on the firewall, you probably offer only SSH and Ident.
  - If you are using basic port-bound or the stealth mode, then you will need to set the `TCP_PORTS` variable to the TCP ports to listen for attacks, and you will need to set the `UDP_PORTS` variable for UDP ports. This is a comma-separated list; spaces and tabs are not allowed. Only the basic mode will actually bind to these ports. The stealth mode will open a raw socket, analyze all incoming traffic containing this system's destination address (and broadcast packets), and react to those in the port list. If you select the basic mode, there is a limit on the number of open ports. On Linux 2.2 and 2.4 kernels, this limit is normally 1024 open ports. On many UNIX systems, it is 64 per process, including regular files and I/O devices to open.
  - If you will be using advanced stealth mode, this allows listening on a large range of ports that can number in the thousands because it does not bind to the individual ports. For this list, specify the highest port number to monitor with the `ADVANCED_PORTS_TCP` and `ADVANCED_PORTS_UDP` variables. List the ports to ignore, either because you will have a real service on them or because you want to ignore the chatter on them, using the `ADVANCED_EXCLUDE_TCP` and `ADVANCED_EXCLUDE_UDP` variables. While the documentation gives dire warnings about listening on ports above 1023, I have not found this to be a problem. Of more importance is the fact that a number of vulnerable and commonly attacked services are above this number.

I prefer the advanced stealth mode to the others and find that the following works on a firewall:

```bash
# Watch 1080 for socks, 2049 for NFS, and 6000 for X
ADVANCED_PORTS_TCP="6010"
ADVANCED_PORTS_UDP="1024"
# Default TCP Ident and NetBIOS service
ADVANCED_EXCLUDE_TCP="113, 139, 37"
# Default UDP route (RIP), NetBIOS, DHCP, NTP, bootp broadcasts.
ADVANCED_EXCLUDE_UDP="520,138,137,67,123,127"
```

The `IGNORE_FILE` variable's name lists hosts packets you want to ignore completely. If you will be blocking attackers, these will be systems you trust a lot (both the honesty of your Sysadmins and their ability to resist being breached) that need access through your firewall. These might include the SysAdmins' work and home systems if they are well secured. Unlike the Tracer Trap, PortSentry will not even warn you if these systems attack you. This is a strong argument for PortSentry's Adaptive Firewall attack being to invoke the Tracer Trap. The latter will work about tested systems attacking without locking them out. This file is machine generated by `ignore.csh`, and should not be edited directly if you invoke `ignore.csh`.

The `RESOLVE_HOST` variable normally is set to "1" (quotes included) to attempt to resolve the name of the attacking system. This will tell you about the circumstances of the attack. If the host name has random characters in it, it is probably someone's compromised DNS server. If its name is `ns2` or `dns3`, then it is probably someone's. If its name is `www`, you are probably dealing with a compromised web server. If you have a slow DNS server, set it to "0".

The `BLOCK_TCP` and `BLOCK_UDP` variables determine whether PortSentry will operate as an Adaptive Firewall and block. "1" to have PortSentry do the blocking, "2" to have invoke only the command specified in `KILL_RUN_CMD` (invoke the Tracer Trap or your own custom IPT/IP chains, or an interface to another firewall for blocking), and "0" to not block. All modes except the Basic TCP mode are subject to forced source IP-address mode DoS attacks. In reality, these are so rare for all the best-known sites that Sysadmins would not worry about the risk.

The `KILL_ROUTE` variable specifies how PortSentry should block the attacker if you selected "1" for each `BLOCK_TCP` or `BLOCK_UDP`. Use the IP Tables or IP methods for Linux. For UNIX, using the route command may be your only option. The downside of a route command is that you will get already blocked for subsequent attacks, except for TCP basic mode. With IP Tables or IP Chains, unless you specify logging, you will not be bothered again, nor will they be able to get packets in.

The major downside to silent Tables/Chains blocking is that if someone repeats his attack so frequently that a significant percentage of your bandwidth is used, you will not know it. Any of the following will work, depending on which packet filtering you are using:

```bash
KILL_ROUTE=/bin/iptables -I INPUT 1 -s $TARGET -j DROP
KILL_ROUTE=/bin/ipchains -I input 1 -s $TARGET -j DENY
KILL_ROUTE=/bin/ipchains -I input 1 -s $TARGET -j DENY -l
```

If `KILL_RUN_CMD` is specified, its value will be fed to a command line. If you specify a mail command, you will get instant notification of an attack. You can specify your own blocking action here. What is the difference between your own blocking command in `KILL_ROUTE` and specifying it in `KILL_RUN_CMD`? Nothing but philosophy. To generate e-mail, this is typical:

```bash
KILL_RUN_CMD=echo /sbin/iptables -I INPUT 1 -s $TARGET \\
-j DROP >> /etc/rc.d/fw.trouble
KILL_RUN_CMD=echo /sbin/ipchains -I input 1 -s $TARGET \\
-j DENY >> /etc/rc.d/fw.trouble
```

Where PortSentry's `KILL_RUN_CMD` can be used to add an IP or IP Chains blocking rule, it will be lost when the system is rebooted. I see no reason to unblock attacking systems for most installations. Using `KILL_RUN_CMD` to invoke the Cracker Trap's block command will block an attacker permanently as it will update the `/etc/rc.d/fw.trouble` file. If you do not want to use the Cracker Trap, the same effect can be obtained by copying the skeleton `fw.trouble` file from the `book/crackertrap` directory on the CD-ROM and set `KILL_RUN_CMD` to either of the above.

You probably do not want to use the `\` instead have a single long line in `portsentry.conf`. Finally, adding the following to the end of the `/etc/rc.d/rc.local` file:

```bash
/etc/rc.d/rc.local
```

This will load the rules of the permanently blocked systems.

- **Deal with portsentry.ignore** to list any trusted IPs that are ignored. This is where you would list the PortSentry system's interfaces, including the loopback device's IP, and Sysmins' work and home systems, if thoroughly secured. Starting with version 1.1, a mask may be used, specifying the number of network bits. You may want to list the appropriate range for your DMZ and you may not.

You may want to list your internal network's range and you may not. It is a case of security versus convenience. Start by not listing any of these, except your "big money" systems and monitor PortSentry closely. Recently, one client's mail server tried to forward spam to the firewall and got locked out, so we decided to make it trusted until the spam was delivered and trusted.

If some of your trusted IPs are dynamic, you will need to alter this file when they change. Typically, this will be an issue for home systems, either as the PortSentry system itself or to trust them. The trusting of other home systems may not be a problem if one can drop the connection and get a new one on reconnection. If the `ignore.csh` script is invoked, it will overwrite the `portsentry.ignore` file to contain the PortSentry system's IPs for its interfaces. If you edit `ignore.csh` and add the lines:

```bash
if (-f /etc/rc.d/friends.ignore) then
    cat /etc/rc.d/friends.ignore >> $SENTRYDIR/$TMPFILE
endif
```

after the line that has the pattern `'0.0.0.0'`, then you can create the file `/etc/rc.d/friends.ignore`, chmod it to mode 600, and list trusted systems there.

- **Build and install.** Issue the following command to see what systems know how to build for:

```bash
make
```

For Linux (except Debian), issue the command:

```bash
make linux
```

For Debian Linux, issue the command:

```bash
make debian-linux
```

Install with:

```bash
make install
```
