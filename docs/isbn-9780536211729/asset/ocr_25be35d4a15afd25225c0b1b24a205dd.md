The EXPN command is similar to the VRFY command in that EXPN will expand (reveal) the actual delivery addresses of mail aliases and mailing lists. This will allow the collection of e-mail addresses in case you later decide to block access to the alias from the Internet. For example, to see what the alias mailing list expands to, assuming it exists, issue the following request to sendmail:

EXPN all all

This EXPN is disabled with the "noexpn" privacy option.
Similarly, the "restrictmailq" privacy option should be specified to prevent Mail from telling anyone who asks what is in the mail queue. It will only let those in the same group as the mail queue see this data.

The "needmailhelo" privacy option will require the client system to identify itself with a HELLO command before mail will be accepted from. The HELLO command will cause the sending system's host name and numeric IP address to be logged via syslog. If the sending system is running (the auth service), the user name or UID will be logged. Thus any shenanigans can be traced back to the perpetrator. If the perpetrator owns the sending system, he can send fake data, of course.

By default, Sendmail will not enforce a limit on the number of children that the daemon fork, when listening on port 25. This allows a DOS attack by sending many messages to your system in a short period of time that the process table or the number of open file descriptors is saturated.

Certainly, an attacker can start one TCP connection to port 25, having the program sleep, start a second TCP connection to port 25 to spawn a second child, and repeat. An attacker could use multiple compromised systems.

The antidote to this DOS is to add the

```
confMAX_DAEMON_CHILDREN
```

define to /etc/sendmail.mc, specifying the maximum number of children you will allow at one time. This will add the

```
O MaxDaemonChildren=25
```

line to the generated sendmail.cf file. See Table 3.1.
The sendmail program has a problem with several other parts of Linux, including named, ftppd, and the typical telnet configuration file. This problem is that sendmail happily tells any computer that asks what is its version number. This makes it easier for crackers to know which vulnerabilities to apply.

Again, back around 1980 it was a good idea to help debug compatibility problems between systems. Today it is a poor idea. It allows crackers to attack the world's mail processes, and wait for new vulnerabilities to be discovered in particular versions. Then, they instantly know which systems they can break into.

The solution is another "one-liner." Change the greeting message to not include the "$v" macro that tells Sendmail's version or the "$z" macro that reveals the sendmail.cf
