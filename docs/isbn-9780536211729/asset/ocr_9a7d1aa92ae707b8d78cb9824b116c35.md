+   3. Also, it verifies that the source port is less than 1024, which only root can open on a Linux or UNIX system. The only way that the daemon knows which user on the requesting system is making the request that rsh sets-UID to root and determines the real UID of the account invoking it, looks up this UID in /etc/passwd to find the user name, and sends this to the other system.

In the Linux and UNIX world, only root is allowed to open a port number less than 1024 so the daemon insists that the requesting system be using such a low port number. This might be called the "big system idea." It sounds secure.

# 3.5.2 R* Insecurity

Security can be broken in a number of ways.

+   1. The cracker can install a bogus .hosts. This is a classic case where both the ideas presented in "Understanding Linux Security" on page 12 come into play. The cracker is stuck in a maze of twist little passages. If she wants to break into joe's account she knows she needs to find a series of passages that get her to install a bogus .hosts file.

Joe's home directory is writable by all (or can be made so) she might be able to find a suitable file. In older versions of .rsh it did not care about garbled lines as long as a line matches the invoking system's name.

Suppose joe had a mail folder from a security mailing list showing cracker sites. All the cracker had to find any random account to use and mv this folder to .hosts. This random account might be an incorrectly configured FTP anonymous or a badly written Web server CGI sniffer.

+   2. If the intruder can access the initiating system or if it is not Linux or UNIX, the UNIX/Linux security model (that only root can operate from a port number less than 1024) fails. There is another here, which is the security level of remote systems that you are considering granting access to your system.

+   3. The intruder can configure his system to pretend to be of a trusted system, for example, zoro.com, for some techniques for doing this. In many cases this is quite easy.

+   4. The intruder can compromise the DNS that the server relies on. That DNS may be on a system different from the system serving rsh.

The best solution to rsh is to disable it. The "Host masquerades" cannot be adequately defended if there are any untrusted systems on the LAN and rsh is at risk for suffering the session being sniffed. SSH was created explicitly to solve these problems. Have your users make use of it.

Still, if your LAN is secure from internal attacks and sniffing, then TCP Wrappers around .rsh can be secure. The rcp program allows copying files between systems and operates in the same way as rsh and it has the same problems and solutions. Have your users use the scp command in the SSH package.
