There is great debate over whether it is advisable to compile a custom kernel or stick with the "stock" kernel that comes with a Linux distribution. The debate also includes whether it is inherently better to compile a monolithic kernel (in which everything is compiled into the kernel) or use a modular kernel. With any debate, there are pros and cons to each method. On the one hand there are those who (almost always) build their own kernel, sometimes called "rolling their own." On the other hand, there are those who rarely or never roll their own kernel. There are those who always build monolithic kernels and others who use modular kernels.

Building a custom kernel has a few advantages. First is the capability to compile in only the exact drivers and options necessary for the computer to run. It is great for a server such as a firewall where the hardware rarely, if ever, changes. Another advantage to compiling a custom kernel, if you choose a monolithic kernel, is the capability to completely prevent some types of attacks; attacks against monolithic kernels are possible, they are less common than attacks against modular kernels. Furthermore, when you roll your own kernel you are not confined to the kernel version by the distribution. This enables you to use the latest and greatest kernel, which may include bug fixes for your hardware. Finally, with a custom kernel you can apply additional security enhancements to the kernel itself.

Building a custom kernel is not without its own pitfalls. After you roll your kernel, you can no longer use the distribution's kernels and updates, but it's likely that the distribution uses an earlier version of the kernel that may reintroduce bugs fixed in your custom system. Using a stock kernel also makes it easier to support from the vendor for kernel issues.

As alluded to earlier, I rarely roll my own kernel for production server machines. The situations in which direct support is an absolute requirement are the only exceptions. These are few and far between. I believe the capability to customize the kernel to the computer and add greater security through additional patches outweighs the need to use official kernel updates from the distribution.

### 7.1.2 Source and Destination Addressing Options

A packet's source address and destination address can both be specified in a firewall rule. Only packets with that specific source or destination address match the rule. Addresses may be a specific IP address, a fully qualified hostname, a network (domain) name or address, a limited range of addresses, or all-inclusive.

#### IP ADDRESSES EXPRESSED AS SYMBOLIC NAMES

Remote hosts and networks may be specified as fully qualified hostnames or network names. Using a hostname is especially convenient for firewall rules that apply to an individual remote host. This is particularly true for hosts whose IP address can change or invisibly represent multiple IP addresses, such as ISP mail servers sometimes do. In general, however, remote addresses are better expressed in dotted quad notation because of the possibility of DNS host spoofing.

Symbolic hostnames can't be resolved unless DNS traffic is enabled in the firewall. If hostnames are used in the firewall rules, those rules must follow the rules enabling DNS traffic, unless /etc/hosts contains entries for the hostnames.

Furthermore, some distributions such as Red Hat use a boot environment that installs the firewall rules before starting the network or any other services, including BIND. If symbolic host and network names are used in the firewall script, those names must have entries in /etc/hosts to be resolved.

iptables allows the address to be suffixed with a bit mask. The mask's value can range from 0 through 30, indicating the number of bits to mask. As discussed in Chapter 4, "Preliminary Concepts Underlying Packet-Filtering Firewalls," bits are counted from the left, or most significant. This mask specifies how many of the leading bits in the address must exactly match the IP address specified.

An example using masking is to allow connections to a particular service to be made only between your machine and your ISP's server machines. Let say that your ISP addresses in the range of 192.168.24.0 through 192.168.27.255 for its server address space. In this case, the address/mask pair would be 192.168.24/22. As shown in Figure 7.1, the first 22 bits of all addresses in this range are identical, so any address matching the first 22 bits is only accepted when offered from machines in the address range 192.168.24.0 through 192.168.27.255.

![](img/7d04225c75a86d3cf4bd6077596f35b2_293_0.png)

| Decimal | Binary |
|---|---|
| 192.168.24.0 | 11000000.10101000.00010000.00000000 |
| 192.168.27.255 | 11000000.10101000.00011011.11111111 |

| Bit | 31 | 24 | 21 | 10 | 8 | 0 |
|---|---|---|---|---|---|---|

**Figure 7.1** The matching 22 bits in the masked IP address range 192.168.24.0/22.

A mask of 0, /0, means that no bits in the address are required to match. In other words, no bits need to match, using /0 is the same as not specifying an address. Any unicast address matches, iptables has a built-in alias for 0.0.0/0, any/0. Note that any/0, whether implied or stated, does not include broadcast addresses.

### 7.2 Initializing the Firewall

A firewall is implemented as a set of packet-filtering rules defined by options on the iptables command line. iptables is executed once for each individual rule. (Different firewalls can range from a dozen to hundreds.)

The iptables invocations should be made from an executable shell script, not directly from the command line. You should not invoke specific iptables rules from the command line because this could cause your firewall to accept or drop packets inappropriately. When the chains are initialized and the default policy enabled, all network services are blocked until acceptance filters are defined to allow the individual service.

Ideally, you should execute the shell script from the console. But the brave execute the shell script from either a remote machine or a Windows xterm session. Not only is remote network traffic blocked, but also the local interface used by Windows is blocked until access to the interface is explicitly granted. Ideally, Windows should not be running or even installed on a firewall. It is a typical example of software that is not necessary and has been used as a means to exploit servers in the past.

As someone who manages Linux computers that are geographically up to thousands of miles away, I may activate a firewall script only from a remote location. In these instances, it is advisable to do two things: First, change the default policy to ACCEPT for the first or first few executions of the firewall. Do this to debug the syntax of the script itself. After the script is syntactically correct, change that policy back to DROP.

A second and just as important tip for working with firewall scripts from remote locations is to create a cron job to stop the firewall at some point in the near future. Doing so will effectively allow you to enable the firewall and perform some testing but also enable remote access if the script fails completely.
