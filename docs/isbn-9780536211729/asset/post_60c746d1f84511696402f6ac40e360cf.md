
For using a different mail delivery program, such as Postfix, qmail, or mail, either update its aliases or resort to editing the systems/linux/logcheck.sh.

While the original logcheck.sh sent e-mail to "root," I find the use of the alert and alertaliases more configurable. This is because there is no root account and because the person to receive Logcheck e-mail may be different than the person who receives the occasional error message from root. Psionic intended each SysAdmin to edit the logcheck.sh script itself, but I don't like customizing scripts for each system as it makes installing an updated version of the script on many systems an inefficient process.

Now, to root and install the logcheck.sh script in /usr/local/etc and compile and install the logtail program with the command

```
make linux
```

Before going to "production," test Logcheck by invoking it directly with the invocation

```
/usr/local/etc/logcheck.sh
```

If the system has been running for a long time with no trimming of the log files it could take 10–60 seconds to run the first time. Logcheck tracks how large each log file is when it is being processed, remembers the next time, and does the equivalent of a tail command using its logtail program. The implementation is very efficient: if 10 lines of new text have been added to a 10MB log file then it does a seek to the start of those 10 new lines rather than reading the 10MB. Invoke Logcheck a second time to convince you of this. Check your e-mail and pager and ensure that it works. If it complained in each e-mail about the same missing log file that does not exist in your distribution of Linux, simply create the zero-length file with the touch command and chmod to 600.

If you have running IP Tables or IP Chains without Logcheck or other monitoring, you will probably be surprised by the large number of dropped packets. If Windows and DHCP on your network then there will be a lot of chatter that will not be of interest. This could be dealt with by editing your firewall and logging off of the rules that drop these packets. It could take some time to tune the rules to avoid all of this, but this will save you over the long run. You will discover that you have been the subject of numerous attacks that did not work (if they worked, you already know). You may discover that your ISP is wanting your bandwidth with all sorts of pings, and similar requests to your firewall or servers.

5. In configuring clients around the world, I have noticed about half of the ISP's unintentionally waste clients' bandwidth and the time of those involved in configuring firewalls with things as undesired routing protocol (RIP) packets (on UDP port 520) and ident (on TCP port 113) in response to DNS or SMTP requests. These can and should be dropped or rejected.

The UDP requests certainly should not be trusted, as UDP packets are spoofable and most ISPs do not use the simple antispoofing techniques discussed in this book. The request most likely are due to someone at the ISP not thinking about bandwidth issues during configuration.

Edit foo2's last line if you are not paid enough to be paged every hour in the middle of the night and weekend. The unedited last line will look like

The second space-separated field is a list of what hours the command should be run. 9-17 for anyone who can leave this behind at 5 P.M. For an additional check at 8 P.M., use 9-17,20. The fifth field specifies the days when your script should be run, with 1-5 indicating during the week. PortSentry is Psionic's Intrusion Detection System (IDS) that also can act as an Adaptive Firewall. It is an excellent product that I have used with great success for several years. Though it is not GPL, individuals and companies may install it for internal use. It allows you to monitor a user-configurable list of TCP and UDP ports for attempted access by possible crackers. When a cracker knocks one of these monitored ports, a variety of actions can be taken, including notifying you of what system touched what port and locking system out of your network temporarily or permanently.

It is capable of detecting stealth attacks, such as the common cracker technique of sending the initial SYN packet, waiting for a SYN-ACK to indicate that a process is listening on the port, and never sending the third packet of the initial TCP three-way handshake, the ACK packet. As in physics, two objects may not occupy the same space. Therefore, you will not want PortSentry listening on a port where a “real” server will be bound to that same system. An invocation of PortSentry can listen to either TCP or UDP ports list:

- Basic port-bound mode (-tcp or -udp). PortSentry will be bound to the specified list of ports and listen for connections and react. Because the Linux or UNIX kernel handles the initial three-way handshaking for TCP, this method will not detect TCP scans or various other stealth scans, such as the FIN, Null, or Xmas scans.
- Stealth scan mode (-stcp or -udp). PortSentry will open a raw socket to listen in Promiscuous mode and trigger if any port within the specified range that not already have a connection listening on it is attacked. Stealth scans will be detected.
- Advanced stealth scan mode (-atcp or -udp). PortSentry will open a raw socket to listen and trigger if any port within the specified range that not already have a connection listening on it is attacked. Stealth scans will be detected. The advantage of the advanced stealth scan mode over the previous mode is that it will detect crackers client-side random high port numbers that might open, in the hope of hijacking existing connections. It is also very sensitive, some might call it a trigger if a suitably large range of ports is specified. Another advantage is that crackers will see the port as closed or filtered, not open as would be the case with Basic TCP mode.

The downside is that it allows a cracker to do a DoS attack by spoofing a source address. While PortSentry's limited documentation experience expresses great concern about this, unless you are a very well-known site, this is a very unlikely prospect. It may happen unintentionally to internal users on occasions (every few months) but this requires only restarting PortSentry.

Most SysAdmins find advanced stealth mode to be most suitable and will want to run both a TCP and a UDP version. It will detect connect(), SYN (half open), FIN, XMAS, NULL, any TCP scan, and all UDP scans, except small fragments. (Firewall should be configured to defrag all packets to protect against fragmentation attacks, as discussed in "Fragmentation Attacks" on page 567). The two stealth modes are available only on Linux at this time, according to the documentation.

PortSentry will notify you of any attack using the syslog facility; this assumes you will see the log in a timely manner, notice the problem, and react. Psionic's Logcheck (now LogSentry) program works for your purpose, with the limitation that it may be invoked manually every hour or so and can have false positives. It was covered in "Using Logging to Check Files You Never Check" on page 346. An alternative is to use PortSentry's KILL_RUN_CMD capability to let it send you e-mail immediately upon detecting an attack. PortSentry also offers the very valuable Firewall capability by interfacing with IP Tables, IP Chains, TCP Wrappers, or by invoking any user-specified command in KILL_RUN_CMD. This can be used to interface with the Cracker Trap.

Normally, when running on a firewall, PortSentry will detect only attacks against the firewall itself or broadcast destinations that include the firewall. However, port redirection may be used on the firewall to redirect packets for the monitored ports on other systems back to the firewall allow PortSentry to react.
