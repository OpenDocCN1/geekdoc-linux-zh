What is the future of Linux security? Linux has the advantage of starting with a well-designed security model, and most of the code is well written. This includes the ability to offer privileged limits for ordinary users and separate subsystems so that one can simply remove or not use those needed. This causes any vulnerabilities in subsystems to be nonissue. A code audit of all the code that comprises Linux has been ongoing for several years; the problems discovered de facto.

Some troublesome subsystems that used to run as root, such as the Domain Name Service (DNS) daemon (named), can and should be run as ordinary users in rooted environments. This way, if a buffer overflow or some other vulnerability is encountered, only that subsystem is compromised, not the whole system. Additionally, security features have recently been built into Linux at the application layer. Apache has some features that limit what ordinary HTML can do. Sendmail has a restricted shell for running programs. This shell limits the instructions contained in the aliases file or a user's .forward file are allowed to do. Sendmail will refuse to trust data in group-writable or world-writable directories to prevent SysAdmin's configuration error from leading to a compromise, unless it overridden explicitly.

A major criticism of Linux (and UNIX before it) is that many interesting things require root access to function and thus a single bug in a program running with root permissions can compromise the whole system. Starting in 2001, work to resolve this started in the form of the kernel's evolving Capabilities. This allows one to permit only a subset of root's capabilities (even those of an ordinary user) to various programs. A classic case is that of a server that wants to listen on a well-known port number, one below 1024. Only root is allowed to start listening on such a port because clients trust such a server with passwords and data.

Some programs, such as named and Apache, can be told to open their assigned port early on and then give root permissions. This is done to prevent a bug later in the program leading to a root compromise. An even better solution is to use Capabilities to grant them root's permission only to the port. While you can use this facility now, expect to see it become standard on releases in the near future.

For early versions of Red Hat, the user was set to nobody. In later versions, "apache" user and group were created to better separate the Web-server user's access from other users and especially from root. It is critical to remember, though, if this system's primary function is to be a Web server, the gold is owned by the apache user and its security is as important as root's.

Instructions for keeping your DNS daemon (named) in check are in the section "DNS (named, a.k.a. BIND)" on page 149. You will find instructions for setting up named to run as a regular, nonprivileged user, so if it is compromised, the damage will be compartmentalized.
