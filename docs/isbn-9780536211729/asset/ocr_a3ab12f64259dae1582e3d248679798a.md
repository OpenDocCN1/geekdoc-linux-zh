The Ping of Death exploit gives an idea of how the simplest protocols and message interactions can be used by the creative hacker. Not all attacks are attempts to break into your computer. Some are merely destructive. In this case, the goal is to crash the machine. (System crashes might also be an indicator that you need to check your system for installed trojan programs. You might have been duped into laying a trojan program, the program itself might require a system reboot to activate).

ping is a very useful basic networking tool. You might not want to disable ping. In today's Internet environment, conservative folks recommend disabling incoming ping or at least limiting from whom you accept echo requests. Because of ping's history of involvement in DOS attacks, many sites no longer respond to external ping requests from any selected sources. This has always seemed to be an overreaction to the relatively small threat of a DoS over ICMP when compared to the more ubiquitous and dangerous threats against applications and other protocols within the stack.

Dropping ping requests isn't a solution for the victim host, however. Regardless of how the recipient of the flood still reacts to the packets, the system (or network) can still be overwhelmed by the process of inspecting and dropping a flood of requests.

# UDP FLOOD

The UDP protocol is especially useful as a DoS tool. Unlike TCP, UDP is stateless. Flow-control mechanisms aren't included. There are no connection state flags. Datagram sequence numbers aren't used. No information is maintained on what packet is expected next. There is not always a way to differentiate client traffic from server traffic based on port numbers. Without state, there is no way to distinguish an expected incoming response from an unsolicited packet arriving unexpectedly. It's relatively easy to keep a system busy responding to incoming UDP probes that have no bandwidth is left for legitimate network traffic.

UDP services are susceptible to these types of attacks (as opposed to connection-TCP services), many sites disable all UDP ports that aren't absolutely necessary. As mentioned earlier, almost all common Internet services are TCP-based. The firewall we'll build in Chapter 7, "Building and Installing a Standalone Firewall," carefully limits UDP to only remote hosts providing necessary UDP services.

The classic UDP flood attack involves two machines or works in the way the smurf ping flood does (see Figure 5.10). A single spoofed packet from the attacker's UDP echo port, directed to the host's UDP chargen port, can result in an infinite loop of network traffic. The echo and charge services are network test services. charggen generates an ASCII string, echo returns the data sent to the port.
