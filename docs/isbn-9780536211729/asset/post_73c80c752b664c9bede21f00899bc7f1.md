
## 2.6 Forgiveness Is Better than Permission

In the context of `find` commands, the `!` symbol means NOT, so that this clause will be true only when the portion immediately following the `!` is false. The `-fstype proc` condition would be true only for files that are on a file system of type proc. In other words, this ignores pseudo files on `/proc`. Recall that the `/proc` file system does not exist on disk. Rather, it is generated dynamically by the kernel to get and set certain kernel parameters.

The `-perm` operator is short for permissions and allows selection depending on a file's permissions. If its argument starts with a `-`, it will be true for a given file if all of the permission bits are specified. Thus, the following command:

```
-perm -2
```

will be true for each file that is world-writable. This allows you to detect this potential security problem. If the argument to `-perm` starts with a `+`, it will be true if any of the bits, instead of all of them, are true. If there is no leading `-` or `+`, `-perm` will be true if a file's permissions exactly match the argument.

The `-ls` option causes the equivalent of `ls -l` to be done on each matching file and is a recent feature. The `-ls` option gives more information than `-print`.

Some of the later examples use `-mount` to follow subdirectories on file systems other than those containing the starting directories on the command line.

### Common Problems Found

Here are some of the problems I found:

- In addition to maintaining my regular account, I maintain an alternate account for experimenting with safety. This alternate account's home directory was 777 (world-writable).
- I didn't have enough space under `/home` (before my disk upgrade) to fit either the kernel source or Doemu, so I moved them to other file systems, leaving behind a symlink to their real locations. Unfortunately, the new directories were 777, which risked any user who got herself just a guest account modifying the kernel or Dosemu (which runs as root) and waiting for me to recompile the kernel or invoke Dosemu to take over my machine.
- How could this have happened? Many package files are world-writable. Additionally, on my root account, I have the `umask` set to `0` so that when I am copying system files around, I would not accidentally strip permissions that some files should have.
- Because the home directories do not allow write or read access to others, a subdirectory having these permissions did not represent a risk. When the directory was moved out from under the protection of the home directory, this vulnerability was created.
- `/dev/sda*` was mode 666. If I had five SCSI disks, anyone would have full access to the fifth one. I have no idea how this happened.

### Processing Results

The command then pipes both standard output and standard error to the `mail` command to mail the results to the system administrator's account. Because `find` takes many minutes to run on the entire file system, it is often preferable to mail the results to yourself and do something else while `find` runs.

When I go through such a purification ritual, I will usually redirect the output into a file as `foo`, or pipe the output to `tee` and specify the output file to `tee`. Everyone who knows this `find` script is shocked at the results. Even though I run a tight ship, I was surprised by how many problems this found on my laptop. This was particularly surprising because it does not have many packages installed on it, because it originally had a 300 MB disk.

After `find` puts the suspicious file names in a file, I edit the file down to those files that actually have a problem, prepend the following to each line (with a space after the `w`):

```
chmod o-w
```

and then I do:

```
sh foo
rm foo
```

or:

```
csh foo
rm foo
```

This removes write permission for others from the files.

As an alternative, either of the two following commands will find all world-writable files (except directories with the sticky bit on and character devices) and for each one, will ask you if you want the world-writable bit (002) turned off.

Note that you do not check the `/proc` file system.

Note that the `-ok` action is like `-exec`: it first prompts you with the name of the command (the first argument to `-ok`) and the name of the file being processed, and waits for you to type a line. If the line begins with `y` or `r`, the command is executed; otherwise it is not. Rereading the `find(1)` manual page might prove value. The first assumes that `/home` is a separate file system and will not check file systems other than `/home`. The second form is preferable for general use.

```
find / -home -mount -perm -002 \( -type f \
-o -type d -o -type p -o -type b \ \
\ ! -type d -o ! -perm -1000 \ \
-ls -ok chmod o-w '{}' \;
```

```
find / ! -fstype proc -perm -002 \( -type f \
-o -type d -o -type p -o -type b \ \
\ ! -type d -o ! -perm -1000 \ \
-ls -ok chmod o-w '{}' \;
```

### Periodic Checks and Tips

I suggest repeating one of the `find` operations discussed in this chapter periodically, possibly monthly or weekly via `cron`.

**TIP**

You might want to invoke the `find` command using an account other than root. Then, if a particular directory is mode 700, `find` will not descend into it. Thus, you will not be bothered by any files underneath a directory that may be world-writable but not in danger because the 700 on that directory will keep anyone else from getting to the files underneath.

You might want to redirect standard error to `/dev/null` so you will not be bothered by warnings of permission denied on directories that you are denied access to, because they clearly are protected.

Note that this trick will detect the subtle and rare problem of a directory with mode 711 that allows someone to access files (and subdirectories) if she knows the names, but neither `ls` nor `find` can obtain a list of the files in their directory. If someone is using this technique, she probably knows what she is doing. You can find such directories for closer inspection, if you want, by invoking each of these commands in turn.

```
find / ! -fstype proc -perm -001 -perm -004 -type d -ls
find / ! -fstype proc -perm -010 -001 -type d -ls
```

Deciding which files must remain world-readable is harder than the world-writable problem because many files should be world-readable, as shell scripts in the binary directories, man pages, libraries, `/etc/passwd` and `/etc/group`, `/etc/hosts`, and `/etc/resolv.conf`. Certainly, on a secure system, users' files generally should not be world-readable and perhaps not even group-readable. This is where your file system is useful.

The following command will find all world-readable files under `/home` and under `/usr/oracle`, where there be database-related files. This command does not check `/usr/oracle/bin` where Oracle-related programs are kept. It makes use of the `-path` option to match `/usr/oracle/bin` and the `-prune` option to skip it. It similarly ignores `/home/ftp`. It does not pipe standard error, if you can, you desire.

```
find /home /usr/oracle -path /usr/oracle/bin -o \
-path /home/ftp \
-prune -perm 4 -ls \
2>&1 | Mail -s 'world readable' your_address
```

You will also want to check set-UID and set-GID programs and evaluate whether these permissions are appropriate. The following two commands will do this. Although they can be combined into one, because set-GID programs are rarer than set-UID programs, it is best to separate them.

```
find / ! -fstype proc -perm -4000 -ls 2>&1 | \
  Mail -s 'set-UID' your_address
find / ! -fstype proc -perm -2000 -ls 2>&1 | \
  Mail -s 'set-GID' your_address
```

Csh users should use the following instead:

```
find / ! -fstype proc -perm -4000 -ls & | \
  Mail -s 'set-UID' your_address
find / ! -fstype proc -perm -2000 -ls & | \
  Mail -s 'set-GID' your_address
```

There are many other types of suspicious files that can be found with `find` commands. One would be to find files with a numeric UID or GID that is not in `/etc/passwd` or `/etc/group`. These might be cracker files or files owned by users long since removed and forgotten. The following command will list these:

```
find / ! -fstype proc \( -nouser -o -nogroup \) -ls
```

The following command will find files that are hidden from ordinary view beginning with a ".". Expect to see `.profile` and similar, but crackers create a file of one of these names in their login directory.

```
find / ! -fstype proc \( -name '.*' ! -name '..' \) -ls
```

The next command will find all files owned by a specified user. It should be used after removing an account. When I do, I am reminded of users who have mailboxes, files in stalled print queues, etc.

```
find / ! -fstype proc -user dbcooper -ls
```

The following command will find files in each user's directory that they do not own and could be the result of someone being up to no good. If `ftp` is under `/home`, expect files owned by root. User collaboration might result in one user's directory having files owned by another user, but this situation is rare on many systems. A similar test for group ownership may be done.

```
csh
cd /home
foreach i ( * )
  echo Testing $i
  find $i ! -user $i -ls
end
exit
```

The `find` command is one of the most powerful and innovative features of UNIX and Linux. Often its use can solve difficult problems that have no other easy solution.
