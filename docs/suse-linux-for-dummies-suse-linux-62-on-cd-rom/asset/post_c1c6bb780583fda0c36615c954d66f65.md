I imagine that you are in a foreign country and don't know the language, so you hire an interpreter to accompany you on your visits to customers. You tell the interpreter what you want to do and where you want to go. The interpreter then decides what steps to take (hire a taxi or take the subway, for example), and in what order. When it's time for you to talk to customers, the interpreter takes the statements you give in your language and de changes them into the native language.

Shells (also known as interpreters) do much the same thing. They take the English-like commands you type in, gather resources (such as file names and memory), and supply lower-level computer statements to do what you want.

Many shells have evolved throughout the history of UNIX and Linux. Their history and derivation is discussed in the sidebar titled "The Bourne-again shell," which appears later in this chapter. For now, I'd like to simplify the issue of which shell is best and suggest a shell for your use.

I recommend bash because it is widely available and has more features than you will ever need as a user. If you go on to become more of a programmer or if you like investigating shells, you might try the popular zsh or the even more popular Tcl/Tk or Python, which have a graphical interface.

## Bashing Ahead!

The first thing to do in this chapter is to make sure that you are using the bash shell. If you are using Linux without X Window System and you are logged in as a general user (versus logged in as the superuser, root), you're probably at a shell prompt. If you're using X Window System, you must log in and use the window manager to launch a terminal emulator window, which probably contains a shell prompt. If you are not familiar with how to do this, check out Chapter 11.

Your shell prompt should look something like this:

```
username@hostname:~ >
```

The most important element is the > at the end of the line. This is the prompt and is the shell's method of saying, "Okay, I'm finished with the last thing," The ~ tells you that you are in your home directory.

```
username@hostname:~ ~ bash
```

## Linux is at your command

Commands in Linux usually consist of three major parts:

- The command name
- Options to the command (telling the command how to change actions for a specific execution)
- Input or output files, which supply data or give the command a place to output data, respectively

Commands can contain one, two, or all three parts, but the first part — the command name — always has to be present.

## Regular expressions: wildcards and one-eyed jacks

If you had to type every filename for every command, Linux would still be useful. But something that makes Linux more useful is the capability to use a few special characters — pattern-matching characters, wildcards, or regular expressions — to supply filenames. Just as wildcards can be substituted for any card of your choice in a poker game, Linux pattern-matching characters can be substituted for filenames and directory names, like DOS wildcards.

Three of these special pattern-matching characters follow:

- * (asterisk)
- ? (question mark)
- \ (backslash)

The asterisk matches at least one character or any characters in any file-name. For example, * matches the following filenames:

```
a
ac
bce
moody
```

```
ls -1 *
```

When bash looks at that line, it performs the following steps:

1. bash creates a new environment for the ls command and determines what should be standard input and standard output. Standard input is normally the keyboard, and standard output is normally the screen.
2. bash expands * to match all filenames in that directory. By expanding the filenames, we mean that certain special characters are used to identify groups. When these characters are used, the computer sees what match and supplies the filenames to the command.
3. Next, bash searches the PATH variable looking for a command called ls. The PATH variable holds names of directories that contain commands you may want to execute. If the command is not in the list, you have to explicitly tell the shell where it can find the command by typing a complete or relative pathname to the command.
4. bash executes the ls command in the new environment, passing to the command -1 argument and all the filenames, expanded, owing to the use of the * character in the command.
5. After ls runs, bash returns to the current environment, throwing away all the side effects that occurred in the new environment, such as an environmental variable changing its value.
