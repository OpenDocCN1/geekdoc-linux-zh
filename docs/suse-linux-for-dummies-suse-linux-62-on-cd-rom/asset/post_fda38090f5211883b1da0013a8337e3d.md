## Copying permissions/distribution policy

Most Linux code is given away by the copyright holder through the GNU Public License, or what is commonly called copyleft. The copyleft stipulates that those holding a copy of the code can use it for whatever purpose they want, as long as they make the code freely available to anyone who wants it. If they change the code, they must make the changed code (including the source code) freely available to those who want it.

Sometimes, other copying and distribution policies are associated with the command or program that the manual page is describing. These policies could include the following types of permissions, which you may

- Use but not redistribute the code
- Use the code, but no source code is available
- Use and distribute the code as shareware, by paying a fee for continued use
- Have limited use, such as educational or personal (but not commercial) use
- Use the code on one machine only

If you've bought the operating system, or a layered product distribution (a distribution that includes both the operating system and a commercial application), or from a CD-ROM vendor, their overall distribution policy is usually the strictest of any one on the CD-ROM (that is, you are limited to installing it on one machine because of its licensed software), so you don't have to worry as long as you follow its overall licensing.

## POSIX compatibility/standards conformance

In the dark days of computer science, each vendor went off to develop its own operating system, with its own set of commands and programming interfaces. This created a Tower of Babel (not to be confused with the Tower of Hanoi, which is a puzzle game) among computer users and programmers. When UNIX systems first appeared, however, they were portable across different types of hardware, and you could have the same operating system, commands, and programming interfaces whatever you were programming a Digital Equipment Corporation system, a Sun Microsystems computer, an IBM computer, or others. A little later, vendors bringing out their versions of UNIX, some using System V as a basis, others BSD (as the Berkeley version was called). Some vendors, such as Sun Microsystems, started out with BSD and switched to System V (to the chagrin of their users).

In 1988, the IEEE developed the POSIX standard for operating systems. The IEEE is a great organization, but perhaps the greatest thing they did was not start from scratch with this specification, but rather to build on UNIX. The interfaces were taken from the existing System V and Berkeley versions of UNIX.

If an operating system is POSIX compatible and a program is written to POSIX standards, the program should be able to run on the operating system with no problems, and users should be able to use that operating system with little or no retraining from the last POSIX operating system they learned.

Although much work still has to be accomplished in defining what POSIX is and in vendors implementing POSIX, POSIX compliance and certification are worthy goals.

Other standards should be implemented and met by manufacturers, distribution makers, and developers (not necessarily in that order) — standards for network communication, the way data is put on the CD-ROM, and so on. There are both formal standards and informal de facto standards, both of which help your system work better with the next system.

Linux was built with POSIX compatibility as a goal, and it follows many of the other standards. This makes it easy to port code from one set of POSIX-compatible interfaces to another and from one POSIX-compatible operating system to another. It also allows Linux to interoperate with other operating systems. Many Linux people are active in standards bodies, and the move toward standards is generally supported in the Linux community.

## Files

In addition to the startup or configuration files mentioned previously, sometimes the command or program that the manual page is describing using other files in the system and temporary files for holding intermediate work. Such files are listed in this section of the man page. If a command does not work, perhaps one of these files is missing, the wrong file permissions (or the directories they are in have the wrong permissions), is owned by the wrong person, or has corrupt data.

## Future work

The future work section lists the author's plans for the command or program that the manual page is describing, often in an attempt to generate interest and help from other people.

## See also/related software

The see also/related software section lists programs associated with the command or program that the manual page is describing. Often, several programs make up a system of programs to do a particular task. Some programs have similar capabilities, but are not quite the same. Some programs are the antithesis of the program you are looking at (for example, cut and paste). The see also often gives you an overall picture of the program is supposed to do or leads you to the right program for the job.

## Finding the Right man Page

If you do not know what command you are looking for, use the apropos command followed by the word you are interested in. The apropos command searches all the man pages looking for that word, and lists the man command names along with one-line descriptions of all the commands that contain that word. You should probably pipe the output of the apropos command into the command:

```
[maddog@localhost] > apropos print |
```

Note that apropos matches on partial words (called strings), which is why we suggest print print instead of printer. The shorter your keyword, the more matches the command will find.

Second, after you have the pages you want to look at, execute the man command for each. From the one-line description, you can probably decide which commands fit your needs.

Third, look at the description, which will give you a better idea of what the command can do. If you're still not sure about the command's functionality, look at the also section, to see any other commands fit the bill.

After that, skip the synopsis section — it's usually a reminder of how to type the command — and go directly to the options section. Read the options section, trying to apply the options to the basic description.

## Other places to look for help

You can find help in several other places on the system. One place is the /usr/doc directory.

In addition to man pages, the info pages were created as a replacement to man pages but are not very popular and have not fully replaced man pages. Some habits die hard, I guess. To access an info page for a particular command, type the info followed by the command you want information on; for example, see the info page for the tar command, type tar

Note: Some system administrators conserve space by not loading /usr/doc on their systems. With the abundance of inexpensive disks, this is false economy. Documentation such as that found in /usr/doc can be put on one system and made available to everyone through the magic of the Network File System (NFS). Tell your system administrator to do that.

To exit the page, press the Ctrl and C keys simultaneously.

After you've read several man pages, you'll notice that the same options appear for similar commands.

All this is pretty much passive work. To find out what a command really does, you should try it out. Create a small test file using an editor, or use an existing file, such as the /etc/passwd file, as input.

Do not do this as root. You may inadvertently erase part of the operating system. It is best to do this experimentation as a unprivileged, normal user.
