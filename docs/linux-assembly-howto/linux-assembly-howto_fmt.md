## 2.1. 优缺点

### 2.1.1. 汇编的优点

汇编可以表达非常底层的内容：

- 你可以访问依赖机器的寄存器和 I/O

- 你可以控制关键区域中的代码行为，否则这些区域可能会在多个软件或硬件设备之间导致内联死锁

- 你可以打破常规编译器的约定，这可能允许某些优化（例如临时打破关于内存分配、线程、调用约定等规则）

- 你可以使用不兼容的约定在代码片段之间构建接口（例如，由不同的编译器产生，或通过低级接口分离）

- 你可以访问处理器中不寻编程方式（例如，在 Intel PC 上使用 16 位模式来处理启动、固件或遗留代码）

- 你可以为紧凑循环生成相当快速的代码，以对付糟糕的非优化编译器（但话如此，可用的优化编译器并不多！）

- 你可以为紧凑循环生成完美调优的优化代码以应对糟糕的编译器

### 2.1.2. 汇编的缺点

汇编是一种非常底层的语言，这意味着：

- 编写汇编代码非常耗时

- 它容易出错

- 你的代码难以维护

- 汇编代码无法移植到其他架构

- 小小的算法改变就可能完全使现有的汇编代码失效

- 在任何情况下，你可能需要手动编写汇编

## 2.2.2. 带有优化编译器的语言

像 ObjectiveCAML、SML、CommonLISP、Scheme、ADA、Pascal、C++ 等语言都提供了免费的优化编译器。这些编译器可以处理你程序的大部分，而且对于紧凑循环，其效果往往比手写的汇编代码更好。这让你能够关注更高级别的细节，同时在设计达到稳定设计后，它们并不会阻止你针对上述顾虑获取几个百分比的额外性能。当然，大多数这些语言也有相应的商业化优化编译器！

## 2.2.3. 加速代码的通用步骤

为了加速代码，你应该针对性能分析工具持续识别为瓶颈的程序部分进行优化。

因此，如果你认为某部分代码运行太慢，你应该：

- 首先尝试使用更好的算法；

- 然后尝试编译它而不是解释它；

- 然后尝试启用并调整编译器的优化选项；

- 接着尝试向编译器提供优化提示（例如：在 LISP 中输入类型信息；在 GCC 中指定寄存器使用；大多数编译器中的大量选项等）；

- 最后可能回退到汇编编程

最后，在结束编写汇编之前，你应该检查生成的代码，以确认问题是否真的出在代码生成上，因为事实可能并非如此：编译器生成的代码可能比你写的更好，特别是在现代多流水线架构中！程序的某些部分本质上就是如此。在具有快速处理器的现代架构上，最大的问题由于内存访问、缓存缺失（cache–misses）、TLB 缺失（TLB–misses）和页错误（page–faults）；寄存器优化变得毫无用，重新思考数据结构和线程以实现更好的内存访问局部性会更有利。这时，完全不同的方法可能会有所帮助。

## 2.2.4. 检查编译器生成的代码

检查生成的汇编代码有很多原因。你可以对这类代码进行以下操作：

- 检查生成的代码是否可以通过手写汇编（或通过调整开关）进行增强

- 如果是如此，从生成的代码开始对其进行修改，而不是从头开始

- 更通俗地说，将生成的代码作为存根（stubs），这至少可以确保你的汇编例程与外部交互的方式是正确的

- 跟踪编译器中的 Bug（希望越少越好）

生成汇编代码的标准方法是使用 `-S` 标志调用编译器。这适用于 Unix 编译器，包括 GNU C 编译器 (`GCC`)，但结果因人而异 (YMMV)。对于 `GCC`，使用 `-fverbose-asm` 选项可以产生更易读的汇编代码。当然，如果你想获得良好的汇编代码，别忘记你常用的优化选项和提示！

## 2.3. Linux 与汇编

你可能已经注意到，通常情况下，在 Linux 编程中不需要使用汇编语言。与 DOS 不同，你不需要用汇编编写 Linux 驱动（实际上，如果你真的想做，你是可以的）。而且有了现代优化编译器，如果你是为了针对不同 CPU 进行速度优化，用 C 编写要简单得多。然而，如果你正在阅读这些，你可能某些理由使用汇编而不是 C/C++。

你可能需要使用汇编，或者你可能想使用汇编。简而言之，深入汇编领域的主要实际（需要）理由是代码量小和对 libc 的独立。实际（想要）且最常见的理由仅仅是一个老怪黑客，他有着了二十年用汇编完成一切的习惯。

然而，如果你正在将 Linux 移植到某些嵌入式硬件，你对整个系统的尺寸可能非常严苛：你需要将内核、libc 以及所有（文件）实用工具压缩到几百 KB 以内，而每一字节的成本都是昂贵的。一种可能的方法是用汇编重写（或全部重写）系统的部分，这将为你节省大量空间。例如，用汇编编写的简单 httpd 可以少于 600 字节；你可以将一个包含内核、httpd 和 ftpd 的服务器装进 400 KB 以内……考虑一下。

## 3.1. GCC 内联汇编

众著名的 GNU/C++ 编译器 (`GCC`) 是 GNU 项目的核心 32 位优化编译器...

`/usr/lib/gcc-lib/i486-linux/2.7.2.3/specs` 或你系统上的其他位置（尽管最好不要添加 `-Wall` all）。可以通过 `gcc -v` 找到系统上 GCC specs 文件的确切位置。

### 3.1.4. 宏支持

`GCC` 允许（并要求）你在内联汇编代码中注册约束，这样优化器就能始终获这些信息；内联汇编实际上是由模式组成的，而不是强制性的、确切的代码。

因此，你可以将汇编代码放入 CPP 宏和内联 C 函数中，这样任何人都可以在任何 C/函数宏中使用它。内联函数解析宏的速度非常快，但使用起来更简洁。请注意，在所有情况下，代码都会被复制，因此在作为代码时应只定义局部标签（`:` 风格）。然而，宏允许将非局部标签的名称作为参数传递（否则，你应该使用额外的元编程方法）。此外，请注意传播内联汇编代码可以防止其中出现潜在错误；注意内联汇编代码中的寄存器约束。

最后，C 语言本身可以被视为汇编编程的一种良好抽象，它为你省去了大部分汇编的麻烦。

## 3.2. GAS

`GAS` 是 GNU 汇编器（GNU Assembler），`GCC` 依赖于它。

### 3.2.1. 在哪里找到它

在发现 `GCC` 的相同位置找到它，在 binutils 软件包中。最新版本的 binutils可以通过 http://sources.redhat.com/binutils/ 获取。

### 3.2.2. 什么是 AT&T 语法



由于 GAS 是为了支持 32 位编译器而发明的，因此它使用了标准的 AT&T 语法，这种语法类似于标准 m86 汇编器的语法，并在 UNIX 世界中是标准。这种语法并不比 Intel 语法差，也不比更好。它只是不同。当你使用它时，你会发现它比 Intel 语法更有规律，有点无聊。

以下是关于 GAS 的一些注意事项：

- 寄存器名称以 `%` 为前缀，因此寄存器是 `%ax`、`%edx` 和 `dl`，而不仅仅是 `dl`。这使得在汇编源文件中直接包含外部 C 符号成为可能，而没有任何混淆的风险，也不需要下划线内核。
- 操作数的顺序是（源操作）在前，目标操作在后，这与 Intel 目标操作在前、在后的约定相反。因此，Intel 语法中的 `mov eax, %edx`（将寄存器 ed 的内容移动到 eax）在 GAS 中将是 `mov %edx, %ax`。
- 操作数的大小通过指令名称的后缀指定。后缀 `b` 代表（8位）字节（byte），`w` 代表（16位）字（word），`l` 代表（32位字）。然而，上述指令的正确语法应该是 `movl %edx, eax`。Gas 不要求严格的 AT&T 语法，因此当可以从寄存器操作数推算出大时，后缀是可选的，并默认为 32 位（带有警告）。
- 立即数操作数以 `$` 前缀标记，例如 `add $5, %ax`（将立即值 5 加到寄存器 `%ax`）。
- 缺少操作数前缀表示它是内存内容；`mov $foo, %eax` 将变量 `foo` 的地址放入寄存器 `%eax`，`mov foo, %eax` 将变量 `foo` 的内容放入 `%eax`。
- 索引或间接寻通过将索引寄存器或内存单元地址括在括号中来实现，`testb $0x80,17 (%ebp)`（位于 %ebp 指向的单元偏移 17 处的字节值的高位）。

注意：有少数程序可以帮助你在 AT&T 和 Intel 汇编语法之间转换源代码；其中一些能够进行双向转换。

GAS 具有 TeXinfo 格式的全面文档，这些文档至少随源码发行提供。浏览提取的 `.info` 页面一直可用。以前有一个名为 `gas.doc` 的文件。在疑问的情况下，终极文档是源码本身！一个你特别感兴趣的章节是机器依赖（Machine Dependencies）：i386依赖（i386-Dependent）：再次，Linux 的源码提供了示例；参见 `linux/arch/i386/` 下的文件：`kernel/*.S`、`boot/*.S`、`math/*.S`。

如果你正在编写某种汇编语言，可能会看到其他语言（OCaml、Gforth 等），或者线程包（QuickThreads、LinuxThreads 等），或其他任何内容。最后，编译 C 程序可能会为你展示你需要的语法。需要帮助吗？

Binutils (2.9+) 现在支持 i386 16 位模式（寄存器和寻址）。使用 `.code16` 和 `.code32` 来切换模式。此外，几位作者使用的一种巧妙技巧是强制 GCC 生成 16 位代码，使用前缀。此外，虽然 GCC 识别 `.s` 文件为原始汇编，但在传递给 GAS 之前它也会识别 `.s` 文件。再次参见 Linux 源码。

## 3.2.5. 宏支持

GAS 包含了一些功能，如 TeXinfo 文档详细所示。GAS 还有 GASP（GAS 处理器），它将所有通用宏汇合在一起。它像 `CPP` 和 `M4` 一样工作。它没有细节说明，但带有你可能喜欢的文档。GASP 看起来像是一个普通的宏汇编器。

## 3.3. NASM

Netwide Assembler 项目提供了用 C 编写的酷 i386 汇编器，足以支持所有语法和对象格式。

### 3.3.1. 在哪里找到 NASM

`http://nasm.sourceforge.net`、`http://www.cryogen.com/nasm/` 以及 `devel/asm/` 目录下的二进制发布。在 Red/Debian 发行版中也提供 `.rpm` 或 `.deb` 包。

### 3.3.2. 它做什么

语法是 Intel 风格的。集成了全面的宏支持。支持的对象格式有 `bin`、`aout`、`coff`、`elf`、`as86`、`obj` (DOS)。

NASM 可以作为 BCC 编译器的后端（包含文件）。除非你使用的是 16 位（这本 HOWTO 范围之外），否则绝对应该使用 NASM 而不是 AS86 或 MASM，因为它运行在所有平台上。

- NASM 带有一个反汇编器 `NDISASM`。它的手写解析器使其比 GAS 快得多，尽管它并不支持无数不同的架构。如果你喜欢 Intel 风格语法而不是 GAS 语法，那么它应该是首选。注意：有少数程序可以帮助你在 AT&T 和 Intel 汇编语法之间转换代码，其中一些能够进行双向转换。

## 3.4. AS86

AS86 是一种 8086 汇编器，支持 16 位和 32 位，并带有宏支持。它大部分使用 Intel 语法，但在寻址模式上略有不同。

### 3.4.1. 获取 AS86

当前版本为 0.16，可以在 `http://www.cix.co.uk/~mayday/` 找到，带有链接器 (`ld86`) 的 bin86 包，或者作为独立的存档。

完全过时的 AS86 版本 0. 由 HJLu 发布，用于编译 2.4 之前的 Linux 内核，名为 bin86 的包，在任何 GCC 仓库中可用。但我建议不要用于编译以外的任何用途。此版本只支持一种修改过的文件格式，GNU binutils 或任何东西不支持，并且在 32 位模式有一些 bug，所以最好只用它编译 Linux。

### 3.4.2. 在哪里找到文档

查看源码包中的 man page 和 `as.doc`。在疑问的情况下，源码本身就是良好的文档：它们注释不多，但编程风格非常直接。你可以尝试查看 as86 在 ELKS、LILO 或 Tunes 0.0.0.25 中的用法……

### 3.4.3. 使用 BCC 使用 AS86

这是使用 BCC 将 `.s` 汇编转换为 a.out `.o` 对象和 `.l` 列表的 GNU Makefile：

```
.o: %.s
bcc -3 -G -C -A -A1 -AS* -o $* $<
```

如果你不需要任何列表，删除 `%.1`、`-A1` 和 `-AS*`。如果你需要 a.out 以外的东西，可以检查 BCC 输出支持的其他格式，并/或使用 binutils 包中的 `objcopy` 工具。

## 3.5. 其他汇编器

还有其他具有各种有趣且卓越功能的汇编器，你可能也感兴趣。

它们可能处于不同的开发阶段，可以是非经典的/高级的或其他任何形式。

### 3.5.1. YASM

YASM 是在 GNU GPL 下对 NASM 汇编器的完全重写（部分使用“新的”BSD 许可证）。它从底层开始设计，允许支持多种语法（例如 NASM、TASM、GAS 等）以及多种输出对象格式。 整体设计中的另一个主模块是优化器模块。

它看起来很有前景；它正在大力开发，你可能想参与。参见 `http://www.tortall.net/projects/yasm/`

### 3.5.2. FASM

FASM（flat assembler）是一种快速、高效的 80x86 汇编器，运行在“实实模式”下。与许多其他 80x86 汇编器不同，FASM 只要求源代码包含它真正需要的信息。它本身非常小且快速。它运行在 DOS/Windows/Linux 上，并可以产生平坦二进制、DOS EXE、Win32 PE 和 COFF 输出。参见 `http://fasm.sourceforge.net`。

### 3.5.3. OSIMPA (SHASM)

osimba 是一个针对 Intel 8038 及其后续处理器的汇编器，完全用 GNU Bash 解释器 shell 编写。osimba 的前身是 shasm。osimba 经过了大量的清理，可以创建实用的 Linux ELF 文件，具有各种类高级语言的扩展和程序员便利命令。

它的运行速度（课程）比其他汇编器慢。它有自己的语法（并使用自己的名称作为 x86 机器码），并包含了相当不错的文档。你可以查看一下：`ftp:/linux01_gwd/pub/clLeNUX/interim/`。你可能不会经常使用它，但至少它可以作为一个你兴趣的来源。

### 3.5.4. TDASM

表驱动汇编器 (`TDASM`) 是一个适用于任何汇编语言的免费可移植汇编器。通过一个定义编译过程的表，应该可以将其作为编译器到任何目标微处理器上。

你可以在 `http://www.penguin.cz/~-niki/tdasm/` 获取。

### 3.5.5. HLA



HLA 是一种高级汇编语言。它使用类似于 Pascal、C/C++ 以及其他高级语言的高级语言进行变量声明、过程声明和过程调用。它使用修改过的汇编语言来处理标准的机器指令。它还提供了几种层级语言风格的控制（`if`, `while`, `repeat...until` 等），帮助你编写更具可读性的代码。

HLA 是免费的并提供源码，有 Linux 和 Win32 版本。在 Win32 上你需要 `MASM` 和 32 位的 `MS-link`；在 Linux 上你需要 `GAS`，因为 HLA 产生汇编后的汇编代码，并使用它进行汇编和链接。

## 3.5.6. TALC

TALC 不是免费的基于 ASM/Win32 的编译器（然而，它支持 ELF 输出，它不是吗？）。

TAL 代表类型汇编语言 (`Typed assembly Language`)。它通过类型注解、内存原语和一组类型规则扩展了传统的无类型汇编语言，以保证 TAL 程序的内存安全、控制流和类型。此外，这些结构足够强大，可以编码大多数源代码执行程序特性，包括记录和结构、高阶和多态函数、异常、抽象数据类型、子类型和模块。同样重要的是，TAL 足够灵活，可以接受许多低级编译器优化。因此，TAL 是类型导向编译器的理想平台，旨在产生可验证的安全代码，用于移动代码应用程序或可扩展的操作系统内核。

## 3.5.7. Free Pascal

- `NASM`

- `MASM`

- `TASM`

- `AS` (`aout.coff, elf32`)

Linux 汇编语言 HOWTO

MASM 和 TASM 的输出没有另外两个那样经过调试，但有时可能很有用。

该汇编器的外观和感觉基于 Turbo Pascal 内部的 BASM，且 IDE 支持高亮，FPC 可以与 `gcc` 完全集成（在 C 级别，而不是 C++ 级别）。

使用一个虚拟的 RTL，人们可以生成纯汇编程序。

## 3.5.8. Win32forth

Win32For 是一个免费的 32 位 ANS 系统，可以在 Win32s、Win95、Win/NT 下成功运行。它包含一个集成在反射式 FORTH 语言中的免费 32 位汇编器（前缀或后缀语法）。宏处理通过反射式 FORTH 的全部威力完成；然而，唯一支持的输入输出上下文是 Win32For 自身（不导出 `.obj` 文件，但当然可以添加该功能）。可以在 `http://ftp.forth.org/pub/Forth/Compilers/native/windows/Win32For/` 找到。

Terse 是一个编程工具，为 x86 家族提供了最紧凑的汇编器！然而，它是完全专有的软件。据说某处有一个免费克隆项目，但在“语法应归原作者所有”的无理借口后被放弃了。因此，如果你正在寻找一个巧妙的编程项目来重启黑客活动，如果你喜欢那种语法，我邀请你开发一个针对 NASM 的 tersse 前端（tersese-frontend）。

### 5.1.3. 直接 Linux 系统调用

通常你会听人说 C 库 `libc` 是唯一途径，而系统调用是不调用的。这在某种程度上是正确的。通常情况下，你必须知道 `libc` 并不安全，在大多数情况下它只进行检查，然后调用内核并设置 `errno`。你可以在程序中这样做（如果需要的话），你的程序将减小几十倍，这也会提高性能，仅仅是因为你没有使用共享库（静态二进制执行文件更快）。或者，在汇编编程中不使用 lib 更多是一个出于情趣或考量的个人偏好/信仰问题，而非实际性问题。请记住，Linux 的目标是符合 POSIX 标准，lib 也是。这意味着任何 lib “系统调用”的语法与真实内核系统调用的语法完全匹配（反之亦然）。此外，GNU `glibc` 随着版本的更新变得越来越慢，消耗也越来越多；因此，使用直接系统调用的情况变得非常普遍。但抛弃 lib 的主要缺点在于你可能需要自己实现几个 `libc` 函数（而不仅仅是系统调用封装器，如 `printf()` 等），你准备好了，不是吗？

以下是直接系统调用的优缺点总结。

**优点：**

- 尽可能的体积；压榨出系统的最后一个字节
- 尽可能快的速度；从你喜爱的基准测试中运行出循环
- 完全控制：你可以根据特定的语言或内存需求或任何需求来调整你的程序/库
- 不受 lib 编写技巧的污染
- 不受 C 调用约定的污染（如果你正在开发自己的语言或环境）
- 静态二进制执行文件使你独立于 lib 的升级或崩溃，独立于指向解释器的悬空 `!` 路径（且速度更快）
- 仅仅是为了好玩（你不觉得写汇编程序很有趣吗？）

**缺点：**

- 如果你电脑上的任何其他程序都使用了该 lib，那么重复代码实际上会浪费内存，而不是节省内存。
- 在许多静态二进制文件中冗余实现的服务是内存浪费。但你可以将你的 lib 替代品变为共享库。
- 通过某种字节码、字码或结构解释器来节省空间，比用写来写一切要好得多（解释器本身可以是 C 也可以是汇编）。保持库精小的最佳方法不是拥有多个二进制文件，而是让一个解释器进程处理带有 `#` 前缀的文件。这就是 OCaml 在代码模式下（与原生代码相反）使用时的工作方式，并且与使用 lib 兼容。这也是 Christian 使用 Perl Powers 实现 unix 工具的方法。最后，最后一种让事物保持精小的方法，它不依赖于硬编码路径的外部文件（无论是库还是解释器），就是只保留一个二进制文件，通过指向同一二进制文件的命名良好的硬链接或软链接将以最优空间提供你所需的一切，且没有子程序或未二进制文件的冗余；它将根据 `argv[]` 分发其特定行为；如果未使用可识别的名称调用，它必须默认设为 `a`，并且可能还可以作为解释器使用！
- 你无法从 Linux 系统调用中从 lib 提供的许多功能获益：即手册页第 3 节中描述的功能，如 `malloc`、线程、密码、高级网络管理等。
- 因此，你可能需要实现 lib 的大部分部分，从 `printf()` 到 `malloc()` 再到 `getbyname`。有了冗余的编辑，这有时会非常无聊。有些人已经实现了 lib 的“轻量级”替代品——去看看它们吧！

## 6.2. Hello, world!

### 6.2.1. 程序布局

程序可以分为若干部分：`.text` 用于代码（只读），`.data` 用于数据（读写），`.bss` 用于未初始化数据，以及一些用户定义的部分，但实际上只有少数其他部分。现在我们将展示你的第一个程序。代码如下：

```
section .data

msg      db          "Hello, world!",0xa

len     equ        $ - msg
```

### 6.2.2. NASM (hello.asm)

```
:start:

    mov edx, len        ; 第三个参数：消息长度

    mov ecx, msg        ; 第二参数：要写入的消息的指针
```



```assembly
mov ebx, 1          ; 第一个参数：文件句柄 (stdout)

mov eax, 4          ; 系统调用号 (sys_write)

int 0x80            ; 调用内核

mov ebx, 0          ; 第一个参数：退出代码

mov eax, 1          ; 系统调用号 (sys_exit)

int 0x80            ; 调用内核
```

### 6.2.3. GAS (hello.S)

```assembly
.data # 段声明

msg .ascii "Hello, world!\n" # 我们亲爱的字符串

len - . msg # 我们字符串的长度

.text # 段声明

.global _start # 我们必须导出入口点

_start:

    mov $len, %edx      ; 第三个参数：消息长度

    mov $msg, %ecx      ; 第二参数：要写入的消息的指针

    mov $1, %ebx       ; 第一个参数：文件句柄 (stdout)

    mov $4, %eax       ; 系统调用号 (sys_write)

    int 0x80           ; 调用内核

    mov $0, %ebx       ; 第一个参数：退出代码

    mov $1, %eax       ; 系统调用号 (sys_exit)

    int 0x80           ; 调用内核
```

## 6.3. 构建可执行文件

### 6.3.1. 生成目标代码

构建可执行文件的第一步是从源码编译（或汇编）目标文件：

对于 `nasm` 示例：

```bash
$ nasm -f elf hello.asm
```

对于 `gas` 示例：

```bash
$ as -o hello.o hello.S
```

这产生了 `hello.o` 文件。

### 6.3.2. 生成可执行文件

第二步是通过调用链接器从目标文件生成可执行文件本身：

```bash
$ ld -s -o hello.o
```

这最终构建了 `hello` 可执行文件。

## 8.7. 我不理解如何使用系统调用！

来自 Patrick Model 的回答：

当你调用 `sys_open` 时，你会得到一个文件描述符，它实际上是你的进程所拥的所有打开的文件描述符表中的索引。`stdin`、`stdout` 和 `stderr` 分别是 0、1和2，因为从那里开始它们按此顺序为你的进程打开。此外，请注意，你打开的第一个文件描述符（在没有关闭任何这些描述符之前）总是3，并从那里开始递增。

理解了索引方案就能解释 `select` 是什么了。当你调用 `select` 时，你是在表示你在等待某些文件描述符可读、某些可写，并监控某些除了这些以外的。你的进程最多可以打开 1024 个文件描述符，因此 `fd_set` 只是一个位掩码，用于描述哪些文件描述符对于每个操作是有效的。明白的吗？

由于你打开的每个 fd 都是索引，且在每个 `fd_set` 中它只需要开启或关闭，因此 `fd_set` 结构只需要 1024 位。1024 / 32 = 32 个 long 就足够表示该结构。

现在，来看一个松散的例子。
假设你想从一个文件描述符读取（不带超时）。

- 分配与 `fd_set` 等效的内存。

```assembly
.data
my_fds times:32 dd 0
```

- 打开你想读取的文件描述符。

- 设置 `fd_set` 结构中的位。

首先，你需要确定 32 位双字 dword 中的哪一位。在设置位时，`bts` 会对 32 取模。这就是为什么你首先需要确定要从哪个 dword 开始。

```assembly
mov edx,0
mov ebx,32
div ebx
lea eax,my_fds
bts ebx[eax*4],ed
```



- 对任何你想读取的文件描述符重复最后一步。

- 如果你想从这两个 `fd_set` 执行操作，则对整个练习重复一遍。

这就留下了公式中的另外两个部分——`n` 参数和超时

如果任一封面所需的文本量过多而无法清晰地容纳，你应该将第一部分（按合理顺序列出）放在实际封面上，并确保其余部分位于相邻页面上。如果你出版或分发超过 100 份的文档不透明副本，你必须在每份不透明副本中包含一份机器可读的透明副本，或者在每个不透明副本中说明一个包含文档透明副本的公共可访问网络位置，该副本不包含添加材料，且公众可以使用标准网络协议免费下载。如果你使用后一种方案，则在你开始批量分发不透明副本时，必须采取合理谨慎的步骤，以确保该透明副本在你最后一次向公众分发（直接或通过你的代理或零售商）不透明副本后至少一年内在该位置保持可访问。

建议（而非要求）你在重新分发任何大量副本之前联系文档作者，以便他们有机会为你提供文档的更新版本。

- D. 保留文档的所有版权声明。
- E. 在任何版权声明旁边添加你修改的版权声明。
- F. 在版权声明之后立即包含下附所示所示的允许根据本许可使用修改版本的许可声明。
