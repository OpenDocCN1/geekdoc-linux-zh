# 1. UNIX
## 1.1. Windows NT 是一个 32 位的操作系统（OS）。32 位操作系统意味着什么？
32 位操作系统运行在至少 32 位的处理器上，并通常为程序提供一个平坦的 32 位虚拟地址空间。运行在 32 位操作系统上的程序通常会使用 32 位作为其基本字长。例如，一个整数将是一个 32 位的值而不是 16 位的值。“32 位操作系统”这一术语也隐含了多种技术，例如抢占式多任务和进程隔离，这些技术在大多数 32 位操作系统中都是常见的，但并非所有 32 位操作系统所固有的。
## 1.2. 描述程序、进程和线程。
程序是存储在磁盘普通文件中的指令和数据集合。在文件的 `i-node` 中，该文件被标记为可执行，且文件内容根据内核建立的规则进行安排。这是内核关心的文件内容的另一个案例。
程序员可以以他们选择的任何方式创建可执行文件。只要内容遵守规则且文件被标记为可执行，程序就可以运行。在实践中，通常过程是这样的：首先，用某种编程语言（例如 `C` 或 `C++`）编写的源程序输入到普通文件中，通常称为文本文件，因为它是按文本行排列的。接下来，创建一个名为 `object file`（目标文件）的另一个普通文件，其中包含源程序的机器语言翻译。这项工作由编译器或汇编器（它们本身也是程序）完成。如果这个 `object file` 是完整的（没有缺失子程序），它会被标记为可执行并可以直接运行。如果不完整，则使用 `linker`（在 UNIX 术语中有时称为“加载器”）将此 `object file` 与之前创建的其他文件绑定，这些文件可能取自称为库的类文件集合。除非 `linker` 无法找到它正在寻找的内容，否则它的输出是完整且可执行的。
为了运行程序，首先请求内核创建一个新进程，进程是程序执行的环境。进程由三个段组成：指令段、用户数据段和系统数据段。在 UNIX 术语中，指令段被称为“文本段（text segment）”。程序被用于初始化指令和用户数据。在初始化之后，进程开始偏离它正在运行的程序。虽然现代程序员通常不修改指令，但数据确实会被修改。此外，进程可能会获取程序中不存在的资源（更多内存、打开的文件等）。
在进程运行时，内核会跟踪它的线程，每个线程都是通过指令的一条独立控制流，所有线程都可能读取和写入进程数据的相同部分。然而，每个线程都有自己的栈（stack）。当你编程时，你从一个线程开始，除非你执行特殊的系统调用来创建另一个，否则你只能得到一个线程。因此，初学者可以将进程认为是单线程的。并不是每个 UNIX 版本都支持多线程。它们是一个被称为 `POSIX Threads` 或“pthreads”的可选功能的一部分。
从同一个程序可以初始化多个并发运行的进程。然而，这些进程之间没有功能上的关系。内核可能通过安排此类进程共享指令段来节省内存，但涉及的进程无法检测到这种共享。相比之下，同一进程中的线程之间存在很强的功能关系。
进程的系统数据包括属性如当前目录、打开的文件描述符、累积的 CPU 时间等。进程不能直接访问或修改其系统数据，因为它们在它的地址空间之外。相反，有各种系统调用来访问或修改属性。
进程由内核代表正在执行的进程创建，该进程成为新子进程的父进程。子进程继承父进程的大多数系统数据属性。例如，如果父进程打开了文件，子进程也将打开这些文件。这种继承对于 UNIX 的运行是至关重要的。这与线程创建新线程不同。同一进程中的线程在大多数方面上是平等的，没有继承关系。所有线程对所有数据和资源都有等的访问权限，而不是它们的副本。
应用程序由一个或多个进程组成。简单来说，进程是一个正在执行的程序。一个或多个线程在进程上下文中运行。线程是操作系统分配处理器时间的基本单位。线程可以执行程序代码的任何部分，包括当前由另一个线程执行的部分。
每个进程都提供运行程序所需的资源。进程具有虚拟地址空间、可执行代码、指向系统对象的打开句柄（handles）、安全上下文、唯一进程标识符、环境变量、基本优先级、最小和最大工作集大小以及至少执行线程。每个进程启动时带有一个线程（通常称为主线程），但可以从它的任何线程创建额外的线程。
线程是进程中可以调度执行的实体。进程的所有线程共享其虚拟地址空间和系统资源。此外，每个线程维护异常处理程序、调度优先级、线程本地存储、唯一线程标识符以及系统用于保存线程上下文直到被调度的结构。线程上下文包括线程的机器寄存器、内核栈、线程环境块以及位于进程地址空间的用户栈。
Microsoft Windows 支持抢占式多任务，这创造了多个进程的多个线程同时执行的效果。在多处理器计算机上，系统可以同时执行与计算机上处理器数量相当的线程。
作业对象（job object）允许将进程组作为一个单元进行管理。作业对象是命名的、安全的、可共享的对象，控制与其关联的进程的属性。对作业对象执行的操作会影响与作业对象关联的所有进程。

## 1.4. 轻量级进程和重量级进程有什么区别？
轻量级进程和重量级进程指的是多处理系统的机制。
在轻量级进程中，使用线程来划分工作负载。在这里，你会看到一个进程在 `OS` 中执行（针对此应用程序或服务）。该进程将拥有一个或多个线程。该进程中的每个线程共享相同的地址空间。因为线程共享其地址空间，线程之间的通信是简单且高效的。每个线程可以比作重量级场景下的进程。
在重量级进程中，创建新进程来并行执行工作。在这里（对于同一个应用程序或服务），你会看到多个进程在运行。每个重量级进程都有自己的自己的地址空间。这些进程之间的通信将涉及额外的通信机制，如 `sockets` 或 `pipes`。
轻量级进程的优点来自于资源的节约。由于线程使用相同的代码段、数据段和 `OS` 资源，因此使用的总体资源较少。
缺点是现在你必须确保系统是线程安全的。你必须确保线程不会互相干扰。幸运的是，`C++` 或 `Java` 提供了必要的工具允许你这样做。
## 1.5. 什么是协程（fiber）？
协程是一个执行单元，必须由应用程序手动调度。协程运行在调度它们的线程上下文中。每个线程可以调度多个协程。通常情况下，协程对于良好的多线程应用程序并不提供优势。然而，使用协程可以使得那些设计为调度自己线程的应用程序更易移植。
## 1.6. 什么是多任务处理？
多任务操作系统将可用的处理器时间分配给需要它的进程或线程。该系统设计为抢占式多任务；它为执行的每个线程分配一个处理器时间片。当当前执行的线程时间片耗尽时，它会被挂起，允许另一个线程运行。当系统从一个线程切换到另一个线程时，它会保存被抢占线程的上下文，并恢复队列中下一个线程的保存上下文。
时间片的长度取决于操作系统和处理器。由于每个时间片都很小（大约 `20` 毫秒），多个线程似乎在同时执行。这在多处理器系统中实际上是事实，其中可执行的线程被分布在可用的处理器之间。然而，在应用程序中使用多个线程时必须小心，因为如果线程过多，系统性能可能会下降。

同一个物理设备可以同时拥有块特殊文件和字符特殊文件，事实上，磁盘通常都是如此。内核中的文件系统代码通过块特殊文件访问普通文件和目录，以获得缓冲区缓存（buffer cache）带来的优势。有时（主要是在高性能应用中），需要更直接的访问。例如，数据库管理器可以完全跳过文件系统，使用字符特殊文件来访问磁盘（但不是文件系统正在使用的同一区域）。大多数 UNIX 系统都有一个用于此目的的字符特殊文件，它可以使用直接内存访问（DMA）在进程的地址空间和磁盘之间直接传输数据，这可以带来数量级的性能提升。更健壮的错误检测是另一个优势，因为缓冲区缓存的间接性往往导致错误检测难以实现。
特殊文件有一个 i 节点（i-node），但磁盘上没有 i 节点可以指向的数据字节。相反，i 节点的这部分包含一个设备编号。这是内核使用的一个表中的索引，用于查找一组被称为设备驱动程序（device driver）的子程序。
当执行系统调用以对特殊文件进行操作时，会调用相应的设备驱动程序子程序。随后发生什么完全设备驱动程序的设计者；由于驱动程序运行在内核中而不是作为用户进程，它可以访问——并可能修改——内核的任何部分、任何用户进程以及计算机本身的任何寄存器或内存。向内核中添加新的设备驱动程序相对容易，因此这提供了一个钩子，除了与新类型的 I/O 设备建立接口外，还可以做许多事情。它是让 UNIX 实现其设计者从未预想过的功能的最流行的方法。可以将其看作执行“疯狂操作”的许可方式。
## 1.49. 什么是信号（signals）？
内核可以向进程发送信号。信号可以由内核本身产生，从进程发送到自身，从另一个进程发送，或代表用户发送。
信号是一种用于通知进程某些条件已发生的技术。例如，如果一个进程执行除以零的操作，一个名为 `SIGFPE`（浮点错误）的信号会被发送给该进程。进程有三种处理该信号的方案：
1.  忽略信号。对于表示硬件异常的信号（如除以零或引用进程地址空间之外的内存），不建议这样做，因为其执行结果是未定义的。
3.  提供一个在信号发生时被调用的函数。通过提供我们自己的函数，我们将知道信号何时发生，并可以按意愿处理它。
内核产生的信号示例是段错误信号（segmentation-violation signal），当进程尝试访问其地址空间之外的内存时发送该信号。
进程发送给自身的信号示例是中止信号（abort signal），由 `abort` 函数发送，用于终止一个会产生核心转储（core dump）的进程。
一个进程发送到另一个进程的信号示例是终止信号（termination signal），当多个相关进程中的某一个决定终止整个家族时发送该信号。
最后，用户产生的信号示例是中断信号（interrupt signal），当用户输入 `Ctrl-c` 时，发送给该用户创建的所有进程。
大约有 28 种信号（某些 UNIX 版本多几个或少几个）。对于除了 `kill` 和 `stop` 信号外的所有信号，进程都可以控制接收到信号时发生什么（注：原文为 `kill` 和 `stop`，此处根据上下文可能的误误）。它可以接受默认操作，这通常会导致进程终止；它可以忽略信号；或者它可以捕获信号并在信号到达时执行一个名为信号处理程序（signal handler）的函数。信号类型（例如 `SIGALRM`）作为参数传递给处理程序。然而，处理程序没有直接的方法确定是谁发送了信号。当信号处理程序返回时，进程在中断处继续执行。内核留两个信号未使用。这些信号可以供应用程序用于用途。
## 1.50. 描述进程 ID（process-IDs）、进程组（process groups）和会话（sessions）。
每个进程都有一个进程 ID，这是一个正整数。在任何时刻，这些 ID 保证是唯一的。除了一个进程外，每个进程都有父进程。
进程的系统数据还记录了它的 `parent-process-ID`，即其父进程的 `process-ID`。如果进程因为父进程在它之前终止而变成孤儿进程，它的 `parent-process-ID` 将改为 `1`（或其他固定数字）。这是启动时创建的初始化进程（`init`）的进程 ID，它是所有其他进程的祖先。换句话说，初始化进程收养了所有孤儿进程。
有时程序员选择一组相关进程来实现子系统，而不是单个进程。UNIX 内核允许这些相关进程被组织成一个进程组。进程组进一步被组织成会话。
会话的成员之一是会话首（session leader），每个进程组的成员是进程组首（process-group leader）。对于每个进程，UNIX 都会跟踪其进程组首和会话首的进程 ID，以便进程能够在层次结构中定位自己。
内核提供了一个系统调用来向进程组的每个成员发送信号。通常，这用于终止整个组，但任何信号都可以通过这种方式广播。
UNIX Shell 通常为每次登录创建一个会话。它们通常为流水线中的进程形成单独的进程组；在这种语境下，进程组也被称为作业（job）。但这只是 Shell 喜欢处理的方式；内核允许更大的灵活性，以便单次登录中可以形成任意数量的会话，且每个会话可以以任何喜欢的方式形成进程组，只要维持了层次结构即可。
工作原理如下：任何进程都可以从其会话中退出，然后成为自己的会话首（仅包含一个进程的进程组）。随后，它可以创建子进程来完善新的进程组。会话内部可以形成额外的进程组，并将进程分配给这些组。分配也可以更改。因此，单个用户可能运行，例如，一个包含 10 个进程的会话，这些进程被组织成，例如，三个进程组。
会话（以及其中的进程）可以有一个控制终端（controlling terminal），它是会话首打开的第一个终端设备；随后会话首成为控制进程。通常，用户进程的控制终端是用户登录时使用的终端。当形成新会话时，新会话中的进程不再拥有控制终端，直到打开一个终端为止。没有控制终端是所谓“守护进程”（daemons，如 Web 服务器、cron 设施等）的典型特征，它们一旦启动，就会脱离启动它们时的任何终端运行。“Demon”和“daemon”是同一个词的两种拼写方式，但前者指恶灵，而后者指代一种介于神与人之间的超自然生物。行为不端的的守护进程可能被恰切称为 demons。
可以组织这些结构，使得会话中只有一个进程组（前台作业）可以访问终端，并在前台和后台之间移动进程组。这被称为作业控制（job control）。尝试访问终端的后台进程组会被挂起，直到它被移动到前台。这防止了它从前台作业中窃取输入或在前台进程组的输出上乱涂乱画。

## 1.51. 权限
`user-ID` 是一个正整数，与密码文件（`/etc/passwd`）中的用户登录名关联。当用户登录时，`login` 命令会将此 ID 设置为创建的第一个进程（即登录 shell）的 `user-ID`。从该 shell 派生的进程会继承这个 `user-ID`。
用户还被组织成组（不要与进程组混淆），这些组也有 ID，称为 `group-IDs`。用户的登录组 ID 会成为其登录 shell 的 `group-ID`。
组定义在组文件（`/etc/group`）中。在登录状态下，用户可以切换到其所属的另一个组。这会改变处理请求的进程的 `group-ID`（通常是 shell，通过 `newgrp` 命令完成操作），然后该 `group-ID` 会被所有派生进程继承。由于用户可能是多个组的成员，因此进程还有一个附加 `group-IDs` 列表。对于大多数用途，当涉及进程组权限时，这些 ID 也会被检查，因此用户不需要不断手动切换组。
这两个用户和组登录 ID 称为 `真实用户 ID`（real user-ID）和 `真实组 ID`（real group-ID），因为它们代表了真实用户，即登录的用户。每个进程还关联了两个 ID：`有效用户 ID`（effective user-ID）和 `有效组 ID`（effective group-ID）。这些 ID 通常与相应的真实 ID 相同，但正如我们稍将看到的，它们也可能是不同的。
`有效 ID` 始终用于确定权限。`真实 ID` 用于计费和用户间的通信。一个表示用户的权限，另一个表示用户的身份。

## 1.52. 进程间通信
在最古老的 UNIX 系统（1980 年以前）中，进程可以通过共享文件偏移量、信号、进程跟踪、文件和管道进行相互通信。随后增加了命名管道（FIFOs），接着是信号量、文件锁、消息、共享内存和网络套接字。这十一种机制中没有哪一种是完全满意的。这就是为什么有十一种的原因！数量甚至更多，因为信号量、消息和共享内存每个都有两个版本。有一组来自 AT&T System V UNIX 的非常古老的集合，被称为“System V IPC”，另一个要新得多，来自 20 世纪 90 年代初成立的一个实时标准小组，被称为“POSIX IPC”。几乎每一个版本的 UNIX（包括 FreeBSD 和 Linux）都拥有这套最古老的十一种机制，而主要的商业 UNIX 版本（例如 Sun 的 Solaris 或 HP 的 HP/UX）则拥有全部十四种机制。
共享文件偏移量很少用于进程间通信。从理论上讲，一个进程可以将文件偏移量定位到文件中的某个虚构位置，然后第二个进程就可以发现它指向何处。该位置（例如 0 到 100 之间的一个数字）就是通信的数据。由于进程之间必须存在相关关系才能共享文件偏移量，它们还不如直接使用管道。
当进程只需“提醒一下”另一个进程时，有时会使用信号。例如，打印缓存程序每当打印文件被缓存时，就可以向实际打印进程发送信号。但信号传递的信息不足，在大多数应用中没有帮助。此外，信号会中断接收进程，使得编程变得比接收者在准备就绪时获取通信更加复杂。信号主要用于终止进程或指示非常异常的事件。
通过进程跟踪，父进程可以控制子进程的执行。由于父进程可以读写子进程的数据，两者可以自由地通信。进程跟踪仅供调试器使用，因为它对于通用用途来说太复杂且不安全了。
文件是进程间通信最常见的形式。例如，人们可以用一个运行 `vi` 的进程写一个文件，然后用一个运行 `python` 的进程执行它。然而，如果两个进程并发运行，文件是不方便的，原因有两个：首先，读取者的速度可能快于写入者，导致看到文件结束符，并认为通信已结束（这可以通过一些巧妙的编程来处理）。）。其次，两个进程通信的时间越长，文件就越大。有时进程会通信几天或几周，传递数十亿字节的数据。这会迅速耗尽文件系统。
使用空文件作为信号量也是一种传统的 UNIX 技术。这利用了 UNIX 创建文件方式的某些特性。
最后，是通常被推荐的一种：管道解决了文件的同步问题。管道不是普通文件类型；尽管它有一个节点（i-node），但没有指向它的链接。读取和写入管道与读写文件有些相似，但存在一些显著的差异：如果读取者领先于写入者，读取者将阻塞（停止运行一段时间），直到有更多数据。如果写入者领先读取者太远，它将阻塞，直到读取者有机会赶上，这样内核就不会排队过多的数据。最后，一旦某个字节被读取，它就永远消失了，因此通过管道连接的长运行进程不会填满文件系统。

但是，管道有三个主要缺点：
1. 首先，通过管道通信的进程必须是相关的，通常是父进程子进程或两个兄弟进程。对于许多应用来说，这种限制太严格了，例如当一个进程是数据库管理器而另一个是需要访问数据库的应用程序时。
3. 第三个缺点是管道可能太慢。数据必须从写入的用户进程拷贝到内核，然后再传给读取者。没有执行实际的磁盘 I/O，但仅拷贝操作对于某些关键应用来说可能花费太长时间。正是因为这些缺点，才演化出了更复杂的方案。
命名管道（也称为 FIFOs）被引入以解决管道的第一个缺点。FIFO 代表“先进先出”。命名管道以特殊文件的形式存在，任何具有权限的进程都可以对其打开读或写。命名管道很容易编程。命名管道有什么问题？它们没有消除管道的第二个和第三个缺点：大写入可能会发生交织，而且它们有时太慢。对于最关键的应用，可以使用较新的进程间通信功能（例如消息或共享内存），但远没有现在这么简单。
命名管道是一种用于在无关进程之间传输数据的特殊文件。一个或多个进程对其写入，而另一个进程从其读取。命名管道在文件系统中可见，可以使用 `ls` 查看，像其他文件一样。命名管道可以在无关进程之间传递数据，而普通的（未命名）管道只能连接父子进程（除非你非常努力）。命名管道是严格单向的，即使在匿名管道是双向的系统中也是如此。
信号量是一种防止两个或多个进程同时访问资源的计数器。文件也可以用于信号量，但对许多应用来说开销太大了。UNIX 有两种完全不同的信号量机制，一个是 System V IPC 的部分，另一个是 POSIX IPC 的部分。
文件锁实际上是特殊的信号量，防止两个或多个进程访问文件的同一部分。它通常只在进程进行检查时有效；这种较弱的形式被称为建议锁。更强的形式是强制锁，无论进程是否检查都有效，但它是非标准的且仅在某些 UNIX 系统可用。
消息是可以发送到消息队列的小量数据（例如 500 字节）。可以是不同类型。任何具有相应权限的进程都可以从队列接收消息。它有很多选择：第一条消息、特定类型的第一条消息，或者一组类型的第一条消息。与信号量一样，有 System V IPC 消息系统调用，以及完全不同的 POSIX IPC 系统调用。


共享内存可能提供了所有进程间通信中速度快的一种。同一块内存被映射到两个或多个进程的地址空间中。一旦数据被写入共享内存，读取者就可以立即获取。使用信号量或消息来同步读取者和写入者。确实，共享内存有两个版本。
最棒的是：网络进程间通信，它使用了一组被称为 `sockets` 的系统调用。（该组中的其他系统调用名称如 `bind`、`connect` 和 `accept`。）与我们讨论过的所有其他机制不同，你通过 socket 通信的进程并不一定运行在同一台机器上。它可能在另一台机器上，也可以在局域网或互联网的任何地方。那台机器甚至不需要运行 UNIX。它可以运行 Windows 或任何系统。就此而言，它也可以是一个网络打印机或收音机。
## 1.53. UNIX 的不同版本有哪些？
肯·汤普（Ken Thompson）和丹尼斯·里奇（Dennis Ritchie）于 1969 年在 AT&T 贝尔实验室作为研究项目开始了 UNIX，不久后它开始在 AT&T 内部被广泛使用（例如，用于电话维修呼中心的自动化）。当时的 AT&T 并不从事商业计算机的生产或商业软件的制定，但到 20 世纪 70 年代初，它开始向大学提供教育目的的 UNIX，前提是源代码仅向拥有自己许可的其他大学公开。到 20 世纪 70 年代后期，AT&T 也开始向商业供应商授权源代码。
许多（如果不是绝大多数的话）被授权者都对 UNIX 进行了自己的修改，将其移植到新硬件上，添加设备驱动程序，或仅仅进行调。也许最重要的两个变化发生在加利州大学伯克利分校：网络系统调用（`sockets`）和对虚拟内存的支持。结果，全世界的大学和实验室都使用了伯克利系统（称为 `BSD`，即 `Berkeley Software Distribution`），尽管他们仍然是从 AT&T 获取许可的。一些商业供应商，特别是太阳公司（Sun Microsystems），也是从 BSD UNIX 开始的。太阳公司的创始人比尔·乔（Bill Joy）是 BSD 的主要开发者。

## 1.85. 定义并讨论以下各情况的安全影响：根目录在 $PATH 变量中的当前目录（“.”）、“r”命令（`rlogin`、`rcp` 等）、`/bin/vi` 上的 setUID 位
如果一个管理员是从 DOS 或 Windows 世界过来的，当他尝试执行当前工作目录中的二进制文件并收到“未找到命令”的错误时，他可能会感到惊讶。与 DOS 和 Windows 不同，当前工作目录默认不在用户的 `$PATH` 中。这意味着为了运行程序 `/home/bin/program`，你必须在命令行中输入完整路径名，或者 `cd` 到 `/home/bin` 并输入 `./program`，或者将 `/home/bin/` 添加到你的 `$PATH` 变量中。
在 UNIX 系统可以实现这种 Windows 功能。在 UNIX 中，可以使用点（`.`）引用当前工作目录。为了让 UNIX 命令行像 Windows 命令行一样工作，你可以执行命令 `PATH=.:$PATH`。这将当前目录设置为 shell 在你发布命令时搜索二进制文件的第一个地方。
然而，这是一个巨大的安全风险。在 UNIX 这种多用户环境中，你必须始终意识到其他人也在使用同一个系统。如果 root 用户以这种方式修改了他的 `$PATH`，那么恶意用户可以在 `/tmp` 目录下创建一个名为 `ls` 的文件。这个文件可以是一个 shell 脚本，可以执行任何操作，甚至是删除整个系统。如果该文件被设置为可执行，并且 root 用户切换目录到 `/tmp` 并发布 `ls` 命令，那么执行的就是恶意脚本（以 root 身份），而不是系统的 `/bin/ls`。
“r”命令多年来在 UNIX 系统上一直很流行。这些命令的存在是为了让用户通过使用多个系统进行远程访问。这些命令有两个固有的缺陷，使得它们在安全环境中变得毫无用处。首先，所有这些命令都通过网络以明文形式传输数据。任何在同一网段运行数据包嗅探的人都能看到所有数据。其次，这些命令的身份验证系统是基于对 IP 地址的限制和允许。伪造 IP 地址太容易了，这意味着对这些服务的非法访问变得简单。
为了实现这些命令提供的功能，但以安全的方式进行，请安装 OpenSSH 软件包。该包是 `ssh`（安全外壳）应用程序及类似程序的开源实现。`ssh` 不仅加密通过网络发送的所有数据，它还支持更高级的身份验证机制，例如公钥/私钥认证。
谨慎使用 setUID 位是非常重要的。UNIX 权限模型是基于父子关系的。当父进程派生子进程时，子进程继承父进程的权限。例如，如果一个应用程序提供了生成 shell 的选项，那么该程序永远不能被分配 setUID 位。如果是这样，它派生的 shell 将具有 root 权限，赋予任何用户对系统的完全访问权限。同样，像 `vi` 编辑器这样的应用程序永远不能设置 setUID，因为这将允许任何用户修改系统上的任何文件，完全绕过了 UNIX 安全模型。

## 1.106. 描述简单邮件传输协议。
SMTP（简单邮件传输协议）是一种用于发送和接收电子邮件的 TCP/IP 协议。然而，由于它在接收端队列消息的能力有限，它通常与另外两种协议之一——`POP3` 或“互联网邮件访问协议”（Internet Message Access Protocol）配合使用，后者允许用户将消息保存在服务器邮箱中，并定期从服务器下载。换句话说，用户通常使用一个使用 `SMTP` 发送邮件的程序，并使用 `POP3` 或 `IMAP` 接收已经在本地服务器上收的消息。大多数如 `Eudora` 等邮件程序允许你同时指定 `SMTP` 服务器和 `POP` 服务器。在基于 UNIX 的系统上，`sendmail` 是最广泛使用的电子邮件 `SMTP` 服务器。一个商业软件包 `Sendmail` 包含一个 `POP3` 服务器，还提供了 Windows NT 版本。
`SMTP` 通常实现为在传输控制协议端口 `25` 上运行。
简单邮件传输协议（SMTP）记录在 `RFC 821` 中，是互联网的标准主机间邮件传输协议，传统上运行在 `TCP` 端口 `25` 上。换句话说，UNIX 用户可以输入 `telnet hostname 25` 并连接到 `SMTP` 服务器（如果存在的话）。
`SMTP` 使用一种 20 世纪 80 年代流行的非对称请求-响应协议风格，现在仍偶尔可见，最常见于邮件协议中。该协议的设计对计算机或人类都同样有用，尽管对人类来说并不那么宽容。从服务器的角度来看，提供了一套清晰的命令，并在 `RFC` 中有良好的文档说明。对于人类来说，所有命令都由换行符明确结束，并且 `HELP` 命令列出了所有命令。从发送者的角度来看，命令回复始终以文本行的形式出现，每行都以一个标识操作结果的三位代码开头，接着是一个指示后面还有其他行的延续字符，然后是旨在向人类提供信息的任意文本信息。
如果邮件交付失败，`sendmail`（最重要的 `SMTP` 实现）会将邮件消息放入队列并在稍后重试发送。然而，它使用退避算法（backoff algorithm），且不存在轮询所有互联网主机以获取邮件的机制，`SMTP` 不提供任何邮箱功能，也没有邮件传输之外的任何特殊功能。由于这些原因，`SMTP` 不是位于高度不可预测线路（如调制解器）后主机的良好选择。可以指定连接更好的主机作为 `DNS` 邮件交换器，然后安排中继方案。目前有两种主要的可用配置。一种是在交换主机上配置 `POP` 邮箱和 `POP` 服务器，让所有用户使用支持 `POP` 的邮件客户端。另一种可能性是安排从交换主机到另一个本地 `SMTP` 交换主机的定期 `SMTP` 邮件传输，后者一直在缓存所有的输出邮件。当然，由于这种解决方案不允许全天候的互联网访问，因此并不受欢迎。
`RFC 1869` 定义了 `SMTP` 扩展功能，创建了扩展 SMTP（ESSMTP）。`ES` 在定义上是可扩展的，允许向 IANA 注册新的扩展。目前最重要的扩展是交付状态通知（DSN），定义在 `RFC 1891` 中。

`boot block`（在 Intel 平台上称为主引导记录）存储启动系统所需的信息。数据从扇区（或柱面组）`0` 开始，可以位于硬件能够启动的任何磁盘。例如，如果你在基于 x86 的系统上使用 Linux，且你的系统 `BIOS` 支持从 USB 驱动器启动，你可以可以使用移动 USB 驱动器作为你的启动设备。
`super block` 包含关于文件系统本身的信息。这些信息包括：
2. 文件系统标签
4. 逻辑块大小
没有 `superblock`，文件系统将无法。由于其重要性，当在磁盘上创建文件系统时，会在磁盘的不同部分创建多个 `superblock` 副本，以防主 `superblock` 损坏。
`logical block` 是文件系统中可以存储的最小数据单元。特定文件系统的 `logical block` 大小在创建该文件系统时确定。逻辑块的常见大小有 `8K`、`4K`、`2K`、`1K` 和 `512 bytes`。如果你保存的文件小于 `logical block size`，该文件仍将占用一个 `logical block` 的空间。
`inode`（或索引节点）包含除文件名外的所有关于文件的信息。每个 UNIX 系统都有 `inode`，包含内容如下：
2. 最后访问时间、最后修改时间、创建时间
4. 权限和所有权
分配给文件系统的 inode 数量在创建文件系统时是固定的。

## 1.143. 为什么通常会有两个 bin 目录，/bin 和 /usr/bin？
UNIX 文件系统的设计目标是供多个系统共享。在共享环境中，没有必要在多个系统之间重复数据。UNIX 系统上的 `/usr` 分区设计设计为供客户端共享。这通常通过客户端系统将服务器的 `/usr` 分区挂载为自己的分区来实现。这样，所有客户端都可以访问相同的程序，而无需系统管理员在多个系统上维护副本。
由于这一事实，`/usr` 分区中的文件绝不能被视为关键系统文件。如果客户端由于某种原因需要从网络启动，如果它的 `/usr` 分区是从中央服务器挂载的，它将无法访问该分区。如果客户端系统需要某种系统修复能力，则该程序必须位于 `/bin` 目录中。按照惯，`/bin` 目录是每个系统本地的。
因此，有两个 bin 目录的原因是：`/bin` 包含了对系统正确运行至关重要的本地系统级二进制文件，而 `/usr/bin` 包含了重要性较低且对系统基本功能运行并非至关重要的二进制文件。

$op = shift;

    die $@ if $@;
    rename($was,$_) unless $was eq $_;

## 1.247. 为什么我在执行“rsh host command”时会收到[一些奇怪的错误信息]？

我们讨论的是远程 shell 程序 `rsh`，有时也叫 `remsh` 或 `remote`；在某些机器上，有一个名为 `rsh` 的受限 shell，那是另一回事。

这里有一个例子。假设你的 `.cshrc` 文件中有：

```bash

```
你会得到一些类似这样的奇怪信息：

```text
% rsh some-machine date
stty: : Can’t assign requested address
Where are you?
Tue Oct 1 09:24:45 EST 1991
```

当你运行某些也会读取你的 `.cshrc` 的 `at` 或 `cron` 任务时，可能会遇到类似的错误。

幸运的是，修复方法很简单。在你的 `.cshrc` 中可能有很多操作（例如 `set history=N`）在交互式 shell 中根本是不值得做的。你需要做是在 `.cshrc` 中用以下代码将它们括起来：

```bash
if ( $prompt ) then
    ...
endif
```
并且由于在非交互式 shell 中 `prompt` 不会被设置，涉及的操作只会在交互式 shell 中执行。你可能还希望将某些命令移动到 `.login` 文件；如果这些命令只需要在登录会话开始时执行（检查新邮件、读取新闻等），那么将它们放在 `.login` 中更好。

## 如何构建一个通可以匹配除 `.` 和 `..` 之外所有文件的 shell 通配符模式？

你可能认为这很简单。

*   `*` 匹配所有不以 `.` 开头的文件；
*   `.*` 匹配所有以 `.` 开头的文件，但这包含了特殊条目 `.` 和 `..`，通常你并不需要它们；
*   `.[!.]*`（仅限较新的 shell；某些 shell 使用 `^` 代替 `!`；POSIX shell 必须接受 `!`，但也可能接受 `^`；所有可移植应用程序不应在 `[` 之后紧跟未加引号的 `^`）匹配所有以 `.` 开头且后续为非 `.` 的；遗憾的是，这将漏掉 `..foo`；
*   `.??*` 匹配以 `.` 开头且长度至少为 3 个字符的文件。这巧妙地避开了 `.` 和 `..`，但也漏掉了 `.a`。

所以为了安全地匹配除 `.` 和 `..` 之外的所有文件，你必须使用 3 个模式（如果你没有像 `.a` 这样的文件名，可以省略第一个）：

`.[!.]* .??* *`

或者你可以使用一两个外部程序并使用反引号替换。这很好：

```bash
ls -a | sed -e ‘^\.$/d’ -e ‘^\.\.$/d’
```

（或在某些 Unix 版本中使用 `ls -A`）

但即使它也会处理包含换行符、IFS 字符或通配符的文件时出错。

## 1.251. 如何在 Bourne shell 脚本找到最后一个参数？

如果你确定参数数量最多为 9 个，可以使用：

```bash
eval last=\${$#}
```

在兼容 POSIX 的 shell 中，它适用于任意数量的参数。以下方法也始终有效：

```bash
for last
do
  :
done
```

这可以泛化为：

```bash
for i
do
  third_last=$second_last
  second_last=$last
  last=$i
done
```

现在假设你想从列表中删除最后一个参数，或者反转参数列表，或者直接访问第 N 个参数，无论 N 是多少。这里是仅使用 shell 内置结构来实现此点的基础，而无需创建子进程：

```bash
t0= u0= rest=‘1 2 3 4 5 6 7 8 9’ argv=
for h in ‘‘ $rest
do
  for t in “$t0” $rest
  do
    for u in $u0 $rest
    do
      case $# in
      0)
        break 3
      esac
      eval argv$h$t$u=\$1
      argv=“$argv \$argv$h$t$u\”“ # (1)
      shift
    done
    u0=0
  done
  t0=0
done
# 现在恢复参数
eval set x “$argv”     # (2)
shift
```

这个示例适用于前 999 个参数。足够了吗？仔细观察标记为 (1) 和 (2) 的行，并让自己相信无论它们包含什么奇怪的字符，原始参数确实被恢复了！

现在要找到第 N 个参数，可以使用：

```bash
eval argN=\$argv$N
```

要反转参数，必须将标记为 (1) 的行改为：

```bash
argv=“\"$argv$h$t$u\” $argv”
```

如何删除最后一个参数留作练习。

如果你允许使用子进程（可能执行非内置命令），可以更方便地设置 `argvN` 变量：

```bash
N=1
for i
do
  eval argv$N=$i
  N=`expr $N + 1`
done
```

反转参数还有更简单的方法，甚至不需要创建子进程。如果你想删除最后一个参数，也可以采用这种方法，但这种情况下你无法直接引用第 N 个参数了，因为 `argvN` 变量是反序设置的：

```bash
argv=
for i
do
  eval argv$#=$i
  argv=“\"$argv$#\” $argv”
  shift
done
eval set x “$argv”
shift
```

## 1.279. 解释 `kill()` 及其可能的返回值。

此调用有四种可能的结果：

- `kill()` 返回 0。这意味着存在一个具有给定 `PID` 的进程，系统允许你向其发送信号。该进程是否为僵尸取决于系统。
- `kill()` 返回 -1，`errno == ESRCH`，表示不存在具有给定 `PID` 的进程，或者安全增强导致系统拒绝其存在。（在某些系统上，该进程可能是僵尸进程。）
- `kill()` 返回 -1，`errno == EPERM`，系统不允许你杀死指定的进程。这意味着要么该进程存在（再次，它可能是僵尸进程），要么存在严苛的安全增强（例如，你的进程被允许向*任何人*发送信号）。
- `kill()` 返回 -1，且 `errno` 为其他值，那么你遇到麻烦了！最常用的技巧是假设成功或带有 `EPERM` 的失败意味着进程存在，而任何其他错误意味着它不存在。

如果你是专门为提供 `/proc` 文件系统的系统（或所有此类系统）编写，存在另一种替代方案：检查 `/proc/PID` 是否可能有效。
