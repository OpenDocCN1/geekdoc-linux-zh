Sraight SQL and anonymous blocks of PL/SQL code cannot be easily pinned using the DBMS_SHARED_POOL package. If you work in a development environment and your application issues sraight SQL statements or anonymous blocks of PL/SQL code, you may be able to improve the application's Library Cache hit ratio by rewriting these SQL statements as PL/SOL stored procedures or packages, which can then be pinned. You can identify the SQL statements contained in large, anonymous PL/SQL blocks by querying the SQL_TEXT column of the V$SQLAREA view for those SQL statements whose COMMAND_TYPE is 47 (i.e., PL/SOL execute):

```
SQL> SELECT SUBSTR(sql_text,1,45), LENGTH(sql_text)
"STMT_SIZE"
2   FROM v$sqlarea
3   WHERE command_type = 47
4   ORDER BY LENGTH(sql_text) DESC;
```

In order to improve the Shared Pool's hit ratios, Oracle recommends considering rewriting any anonymous PL/SQL block that exceeds 500 characters as a stored procedure or package instead.

# When to Pin

To get the maximum benefit from pinning, the objects to be pinned should be loaded into memory right after instance startup. This is usually accomplished through the use of a SQL script that is manually executed immediately after the instance is started, or automatically upon instance startup by an AFTER STARTUP ON DATABASE database trigger. While some application vendors supply scripts for pinning their frequently used packages, many do not. In these cases, you will have to write a script yourself, consisting of an EXECUTE DBMS_SHARED_POOL.KEEP command for each package you wish to pin.
