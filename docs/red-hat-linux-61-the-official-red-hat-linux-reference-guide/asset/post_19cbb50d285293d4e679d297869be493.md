## 11.1.2. Mail Access Protocols

There are two primary protocols used by email client applications to retrieve email from mail servers: the Post Office Protocol (POP) and the Internet Message Access Protocol (IMAP).

Unlike SMTP, both of these protocols require connecting clients to authenticate using a username and password. By default, passwords for both protocols are passed over the network unencrypted.

### 11.1.2.1. POP

The default POP server under Red Hat Linux is `/usr/sbin/ipop3` and is provided by the imap package. When using a POP server, email messages are downloaded by email client applications. By default, most POP clients are automatically configured to delete the message on the email server after it has been successfully transferred; this setting usually can be changed.

POP is fully compatible with important Internet messaging standards, such as Multipurpose Mail Extensions (MIME), which allows for email attachments.

POP works for users who have only one system on which to read email. It also works well for users who do not have a persistent connection to the Internet or the mail server. For those with slow connections, POP requires client programs to download the entire content of each message. This can take a long time if any messages have large attachments.

The most current version of the POP protocol is POP3. There are, however, a variety of lesser-used POP variants:

- POP — POP3 with MDS. An encoded hash of the user's password is sent from the email client to the server rather than unencrypted.
- KPOP — POP3 with Kerberos authentication. See Chapter 7 for more information.
- RPOP — POP3 with RPOP authentication. This uses per-user ID, so RPOP is more secure than standard POP.

For added security, it is possible to use Secure Socket Layer (SSL) encryption for client authentication and data transfer sessions. This can be enabled by using the `/usr/sbin/stunnel` service. Refer to Section 11.5 for more information.

### 11.1.2.2. IMAP

The default IMAP server under Red Hat Linux is `/usr/sbin/imap` and is provided by the imap package. When using an IMAP server, email messages remain on the server where users can read or delete them. IMAP also allows client applications to create, rename, or delete directories on the server to organize and store email.

IMAP is particularly useful for users who access email using multiple machines. For convenience, IMAP applications are capable of caching copies of messages locally, so the user has the ability to browse messages without downloading them.

IMAP, like POP, is fully compatible with important Internet messaging standards, such as MIME, which allows for email attachments.

For added security, it is possible to use SSL encryption for client authentication and data transfer sessions. This can be enabled by using the imaps service or by using the /usr/sbin/stunnel program. Refer to Section 11.5 for more information.

Other IMAP clients and servers are available, many of which extend the IMAP protocol and provide additional functionality. A comprehensive list can be found online at http://www.imap.org/products/list.htm.

## 11.2. Program Classifications

In general, all email applications fall into at least one of three classifications. Each classification plays a specific role in the process of moving and managing emails. Most users are aware of the specific email program they use to receive and send messages; each one is important for ensuring that mail arrives at the correct destination.

### 11.2.1. Mail Transfer Agent

A Mail Transfer Agent (MTA) transfers emails between hosts using SMTP. A message may involve several MTAs as it moves to its intended destination.

While delivery between machines may seem rather straightforward, the process of deciding which particular MTA can accept a message for delivery is quite complicated. In addition, due to problems from spam, the use of a particular MTA is usually restricted by the MTA's configuration or by the lack of access to the MTA's network.

Many modern email clients can act as an MTA when sending mail. However, this action should not be confused with the role of a true MTA. The reason email client programs are capable of sending out email (like an MTA) is the host running the application does not have its own MTA. This is particularly true for email programs on non-Unix based operating systems. However, these client programs only send outbound messages to MTAs they are authorized to use and do not directly deliver the message to the recipient's email server.

Since Red Hat Linux includes two MTAs, Sendmail and Postfix, email client programs are often required to act as an MTA. Red Hat Linux also includes a special purpose MTA called Fetchmail. For information on Sendmail and Fetchmail, refer to Section 11.3 Mail Transport Agents.

### 11.2.2. Mail Delivery Agent

A Mail Delivery Agent (MDA) is invoked by the MTA to file incoming email in the user's mailbox. In many cases, the MDA is actually a Local Delivery Agent (LDA), such as mail or Procmail.

Any program that actually handles a message for delivery to the point where it can be read by an email client can be considered an MDA. For this reason, some MTAs (such as Sendmail and Postfix) can fill the role of an MDA when they append new email messages to a local user's mail spool file. In general, MDAs do not transport messages between systems nor do they provide user access; MDAs distribute and sort messages on the local machine for an email client application to access.

### 11.2.3. Mail User Agent

A Mail User Agent (MUA) is synonymous with an email client application. An MUA is a program that, at the very least, allows a user to read and compose email messages. Many MUAs are capable of retrieving messages via the POP or IMAP protocols, setting up mailboxes to store messages, and sending outbound messages to MTA.

MUAs may be graphical, such as Mozilla Mail, or have a very simple, text-based interface, such as mutt or pine.

## 11.3. Mail Transport Agents

Red Hat Linux includes two primary MTAs, Sendmail and Postfix. Sendmail is configured as the default MTA, although it is easy to switch the default MTA to Postfix.

> For information about how to switch the default MTA from Sendmail to Postfix, see the chapter Mail Transport Agent (MTA) Configuration in the Red Linux Customization Guide.

Red Linux also includes a special purpose MTA called Fetchmail, which is used to deliver email from a remote MTA to a local MTA.

This section details Sendmail and Fetchmail.

### 11.3.1. Sendmail

Sendmail's core purpose, like other MTAs, is to transfer email among hosts, usually using the SMTP. However, Sendmail is highly configurable, allowing control over almost every aspect of how email is handled using the protocol. Many system administrators elect to use Sendmail as their MTA due to its power and scalability.

### 11.3.1.1. Purpose and Limitations

It is important to be aware of what Sendmail is and what it can do as opposed to what is not. In days of monolithic applications that fulfill multiple roles, technically, this is true, as Sendmail can mail to users' directory and deliver inbound mail. However, most users actually want much more than simple email delivery. They want to interact with their email through an MUA that can POP or IMAP to download their messages to their local machine. Or, they may prefer a Web interface to gain access to their mail.

It is beyond the scope of this section to get into all that Sendmail should or be configured to. With hundreds of different options and rule sets, volumes have been dedicated to explaining everything that can be done and how to fix things that go wrong. Refer to the Section 11.6 Additional Resources for a list of Sendmail resources.
