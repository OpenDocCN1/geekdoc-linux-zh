## 10.7. Adding Modules

The Apache HTTP Server provides Dynamically Shared Objects (DSOs) or modules, which can easily be loaded at runtime as necessary.

The Apache Project provides complete DSO Documentation at online http://http.apache.org/docs-2.0/dso.html or if the package is installed, documentation about DSOs can be found at http://localhost/mod/

For the Apache HTTP Server to use a DSO, it must be specified in a LoadModule directive within /etc/http/conf/http.conf; if the module is provided by a separate package, the line must appear within the modules file in the /etc/http/conf.d/ directory. Refer to Section 10.5.15 LoadModule for more about the LoadModule directive.

If adding or deleting modules from http.conf, Apache HTTP Server must be reloaded or restarted, as covered in Section 10.4 Starting and Stopping httpd.

If creating a new module, first install the httpd-devel package as it contains the includes, the header files, as well as the Apache Extension (/usr/bin/apxs) application, which uses the includes and header files to compile DSOs.

After writing a module, use /usr/bin/apxs to compile the module sources outside the Apache source tree. For more information about using the /usr/bin/apxs command, refer to the Apache documentation online at http://apache.org/docs-2.0/dso.html and the apx, man page line

Once compiled, put the module in the /usr/lib/httpd/ directory. Then add a LoadModule line to the http.conf, using the following structure:

```
LoadModule <module-name> <path/to/module.so>
```

In the above example, change <module-name> to the name of the module and <path/to/module.so> to the path to the DSO.

## 10.8. Virtual Hosts

The Apache HTTP Server's built in virtual hosting allows the server to serve different information based on IP address, hostname, or port being requested. A complete guide to using virtual hosts is online at http://apache.org/docs-2.0/vhosts/

### 10.8.1. Setting Up Virtual Hosts

To create a virtual-based host, it is best to use the virtual host container provided in httpd.conf as an example.

The virtual host read example as follows:

```
#NameVirtualHost *
#
#<VirtualHost *>
# ServerName webmaster@dummy-host.example.com
# DocumentRoot /www/docs/dummy-host.example.com
# ServerName dummy-host.example.com
# ErrorLog logs/dummy-host.example.com-error_log
# CustomLog logs/dummy-host.example.com-access_log common
#</VirtualHost>
```

To activate a native virtual host, uncomment the NameVirtualHost line by removing the hash mark (#) and replace the asterisk (*) with the IP address assigned to the machine.

Next, configure a virtual host, by uncommenting and customizing the <VirtualHost> container.

On the <VirtualHost> line, change the asterisk (*) to the server's IP address. Change the Server-Name to a valid DNS name assigned to the machine, and configure the other directives as necessary.

The <VirtualHost> container is highly customizable and accepts almost every directive available within the main server configuration.

> Tip
> If configuring a virtual host to listen on a non-default port, that port must be added to the Listen directive in the global settings section of the /etc/httpd/conf/http.conf file.

To activate a newly created virtual host the Apache HTTP Server must be reloaded or restarted. Refer to Section 10.4 Starting and Stopping httpd for instructions on this.

Comprehensive information about configuring and creating name-based and IP address-based virtual hosts is provided online at http://httpd.apache.com/docs-2.0/vhosts/.

### 10.8.2. The Web Server Virtual Host

By default, the Apache HTTP Server is configured as both a non-secure and a secure server. Both the non-secure and secure servers use the same IP address and host name, but listen on different ports: 80 and 443 respectively. This enables both non-secure and secure communications simultaneously.

One aspect of SSL enhanced HTTP transmissions is that they are more resource intensive than the standard HTTP protocol, so a secure server can never serve as many pages per server. For this reason it is often a good idea to minimize the information available from the secure server, especially on high traffic site.

> Important
> Do not use name-based virtual hosts in conjunction with a secure Web server as the SSL handshake occurs before the HTTP identifies the appropriate name-based virtual host. Name-based virtual hosts only work with the non-secure Web server.

The configuration directives for the secure server are contained within virtual host tags in the /etc/httpd/conf.d/ssl.conf file.

By default, the secure and non-secure Web servers share the same DocumentRoot. It is recommended that the DocumentRoot be different for the secure Web server.

To stop the non-secure server from accepting connection comment the line in httpd.conf which reads Listen 80 by placing a hash mark (#).
