## 9.2. autofofs

One drawback to using /etc/fstab is, regardless of how infrequently a user may access the NFS mounted file system, the system must dedicate resources to keep that in place. This is not a problem with one or two mounts, but when the system is maintaining mounts to dozens systems at one time, overall system performance can suffer. An alternative to /etc/fstab is to use the kernel-based mount utility, which will manage NFS file systems automatically, saving resources.

The autofofs script, located in the /etc/rc/init.d/, is designed to control automount while mount can be specified in the command line, it is more convenient to specify the mount, hostname, exported directory, and options in files rather than typing them all by hand. By running autofofs as a service that starts and stops in designated runlevels, the mount configurations in the various files can be automatically implemented.

The autofofs configuration files are arranged in a parent-child relationship. A configuration file (/etc/auto.master) refers mount points on your system that are linked to a particular map type, which takes the form of other configuration files. For NFS exports it is to use a file as the map type for the particular mount point. The auto.master file contains lines referring to each of the mount points, organized like this:

```
<mount-point>                                 <map-type>
```

The <mount-point> element of this line indicates the location of the mount on the file system. The <map-type> relates to the way in which the mount point will be mounted. The most common method for automount NFS exports is to use a file as the map type for the particular mount point. The map file, usually named auto.<mount-point>, where <mount-point> is the mount point designated in auto.master, contains lines that like this:

```
<directory>  <mount-options> <host>:<exported-file-system>
```

The <directory> refers to the directory within the mount point where the exported file system should be mounted. Like a standard mount command, the hosting export file system, as well as the file system exported, are required in the <host>:<exported-file-system>. To specify particular options to use when mounting the exported file system, place in the <mount-options> section, separated by commas. For NFS mounts that use autofofs, place -fstype=nfs in the <mount-options> section.

While autofofs configuration files can be used for a variety of mounts to many types of devices and files, they are particularly useful in creating NFS mounts. For example, some organizations store a user's directory on a central server via NFS. Then, they configure the auto.master file on each of an auto.home file containing the specifics for how to mount the /home/directory via NFS. This allows the user to access personal data and configuration files in their /home/directory by logging in anywhere on the internal network. The auto.master file in this situation would look similar to:

```
/home                               /etc/auto.home
```

This sets up the /home/ mount point on the local system to be configured by the /etc/auto.home file, which may look similar to:

- -fstype=nfs,soft,intr,rsize=8192,wsize=8192 server.example.com:/home

This line states that any directory user tries to access the local /home/directory (due the asterisk*) should result in an NFS mount on the server.example.com system within its exported /home/ file system. Mount options specify that each /home/ directory NFS mounts should use a particular collection of settings. For more information on mount options, including the ones used in this example, see Section 9.3 Common NFS Mount Options.

## 9.3.3. Common NFS Mount Options

Beyond mounting a file system via NFS on a remote host, a number of different options may be specified at the time of the mount that can make it easier to use. These options can be used with manual commands, /etc/fstab settings, and autofs, and other methods.
The following options are the most popular for NFS:

- hard — specifies whether the program using a file via NFS connection should stop and wait (hard) for the server to come back online if the host serving the exported file system is unavailable, or if it should return an error (soft).
- If hard specified, the user cannot terminate the process waiting for the NFS communication to resume unless intr option is also specified.
- If soft, the user can set an additional timeout=<value> option, which specifies the number of seconds before the error is reported.
- intr — allows NFS requests to be interrupted if the server goes down or cannot be reached.
- nolock — is occasionally required when connecting to older NFS server. To require locking, use the lock option.
- noexec — does not permit the execution of binaries on the mounted file system. This is useful if the system is mounting a non-Linux file system that contains incompatible binaries.
- nsuid — does not allow set-user-identifier or group-identifier bits to take effect.
- rsize=8192 and wsize=8192 — may speed up NFS communication for reads (rsize) and writes (wsize).
- nfsvers=2 or nfsvers=3 — specify which version of NFS to use.

## 9.4. Securing NFS

Administered an NFS server can be a challenge. Many options, including what few mentioned in this chapter, are available for exporting or mounting NFS shares. Consult the following for more information.

### 9.4.1. Host Access

NFS controls who manage the exported file system. To limit the potential risks, administrators can allow only read-only access to the file system. By using IP addresses in /etc/exports, this kind of attack is more difficult. Wildcards be used sparingly when granting NFS shares as the scope of the wildcard may encompass more systems than intended. For more information on securing NFS, refer to the chapter titled *Server Security in the Red Hat Linux Security Guide*.

### 9.4.2. File Permissions

Once the NFS file system is mounted read-write by a remote host, the only protection each shared file has its permissions. If two users share the same userid value the same file system, they will be able to modify others files. Additionally, anyone logged in as root as the client system can use su to become a user who can access particular files via the NFS share. For NFS and userid conflicts, refer to the chapter titled *Managing Accounts and Groups in the Red Hat Linux System Administrator*.

The default behavior when exporting a file system via NFS is to root squashing. This sets the userid of root user on their local machine to a value of the server’s nobody account. Never turn off root squashing.

If exporting an NFS share read-only, consider using the all_squash option, which makes every user accessing the exported file system take the userid of the nobody user.
