## Boot Process, Init, and Shutdown

An important and powerful aspect of Red Hat Linux is the open, user-configurable method it uses for starting the operating system. Users are free to configure many aspects of the boot process, including specifying the programs launched at boot-time. Similarly, system shutdown gracefully terminates processes in an organized and configurable way, although customization of this process is rarely required.

Understanding how the boot and shutdown processes work not only allows customization of Red Hat Linux, but also makes it easier to troubleshoot problems related to starting or shutting down the system.

## 1.1. The Boot Process

Below are the basic stages of the boot process for an x86 system:

- 1. The system BIOS checks the system and launches the first stage boot loader on the MBR of the primary hard disk.
- 2. The first stage boot loader loads itself into memory and launches the second stage boot loader from /boot/ partition.
- 3. The second stage boot loader loads the kernel into memory, which in turn allows necessary modules and mounts the partition read-only.
- 4. The kernel transfers control of the boot process to the /sbin/init program.
- 5. The /sbin/init program loads all services and user-space tools, and mounts partitions listed in /etc/fstab.
- 6. The user is presented with a login prompt for the freshly booted Linux system.

Because configuration of the boot process is more common than the customization of the shutdown process, the remainder of this chapter detail how the boot process works and how it can be customized to suit specific needs.

## 1.2. A Detailed Look at the Boot Process

The beginning of the boot process varies depending on the hardware platform being used. However, once the kernel is found and loaded by the boot loader, the default boot process is identical across all architectures. This chapter focuses on the x86 architecture.

### 1.2.1. The BIOS

When an x86 computer is booted, the processor looks at the end of memory for the Basic Input/Output System or BIOS and runs it. The BIOS controls not only the first step of the boot process, but also provides the lowest level interface to peripheral devices. For this reason it is written into read-only, permanent memory and is always available for use.

Other platforms use firmware to perform low-level tasks roughly equivalent to those of the BIOS on an x86 system. For instance, Itanium-based computers use the Extensible Firmware Interface (EFI) Shell, while Alpha systems use the SRM console.

Once loaded, the BIOS tests the system, looks for peripherals, and then finds a local device with which boot the system. Usually, it checks diskette drives and CD-ROM drives present for bootable media, then, failing that, looks to the system's hard drives. In most cases, the order of the drives searched while booting is controlled with a setting in BIOS, and it looks on the master IDE device on the primary IDE bus. The BIOS then loads whatever program is residing in the first sector of this device, called the Master Boot Record or MBR. The MBR is only 512 bytes in size and contains machine instructions for booting the machine, called a boot loader, along with the partition table. Once the BIOS finds and loads the boot loader program into memory, it yields control of the boot process to.

### 1.2.2. The Boot Loader

This section looks at boot loaders for the x86 platform. Depending on the system's architecture, the boot process may differ slightly. See Section 1.2.2.1 Boot Loaders for Other Architectures for a brief overview of non-x86 boot loaders.

Under Red Hat Linux two boot loaders are available: GRUB or LILO. GRUB is the default boot loader, but LILO is available for those who require or prefer it. For more information about configuring and using GRUB or LILO, see Chapter 2 Boot Loaders.

Both boot loaders for the x86 platform are broken into two stages. The first stage is a small machine code binary on the mbr. Its sole job is to locate the second stage loader and load the first part of it into memory.

GRUB is the newer boot loader and has the advantage of being read ext2 and ext3 partitions and its configuration file — /boot/grub/grub.conf — at boot time. See Section 2.7 GRUB Menu Configuration for information on how to edit this.

LILO, the second stage loader uses information on the MBR to determine the boot options available to the user. Any means that a configuration change is made or is manually upgraded, the /sbin/lilo -v command must be executed to write the appropriate information to the MBR. For details on doing this, see Section 2.8 LILO.

> Tip
> If upgrading the kernel using the Red Hat Update Agent, the boot loader configuration file is updated automatically. More information on Red Hat Network can be found on the following URL: https://rhn.redhat.com.

Once the second stage loader is in memory, it presents the user with the Red Hat Linux initial graphical screen showing the different operating systems or kernels which have been configured to. On this screen you can use the arrow keys to choose which operating system or kernel they wish to boot and press [Enter]. If no key is pressed, the boot loader will load the default selection after a configurable period of time has passed.

> Note
> If Symmetric Multi-Processor (SMP) kernel support is installed, there will be more than one option present the first time the system is booted. In this situation, LILO will display linux, which is the SMP kernel, and linux-up, which is for single processors. GRUB displays Red Hat Linux (<kernel-version>), and Red Hat Linux (<kernel-version>), which is for single processors.

If any problems occur using the SMP kernel, selecting a non-SMP kernel upon rebooting.

Once the second stage boot loader determines which kernel to boot, it locates the kernel binary in the /boot/ directory. The kernel binary is named using the following format — /boot/vmlinuz-<kernel-version> file (where <kernel-version> corresponds to the kernel version specified in the boot loader settings).

For instructions on using the boot loader to supply command line arguments to the kernel, see Chapter 2 Boot Loaders. For information on changing the runtime at the GRUB or LILO prompt, see Section 2.10 Changing Runtimes at Boot Time.

The boot loader places the appropriate initial RAM disk, called an initrd, into memory. The initrd is used by the kernel to load drivers necessary to boot the system. This is particularly important if SCSI hard drives are present or if the systems use the ext3 file system.

> Warning
> Do not remove the /initrd/ directory from the file system for any reason. Removing this will cause the system to fail with a kernel panic message.

Once the kernel and the initrd image are loaded into memory, the boot loader hands control of the boot process to the kernel.

For a more detailed overview of GRUB and LILO loaders, see Chapter 2 Boot Loaders.

### 1.2.2.1. Boot Loaders for Other Architectures

Once the Red Hat Linux kernel loads and hands off the boot process to the init command, the same sequence of events occurs on every architecture. So the main difference between each architecture's boot process is in the application used to find and load the kernel.

For example, the Alpha architecture uses the aboot boot loader, while the Itanium architecture uses the ELILO boot loader.

Consult the Red Hat Linux Installation Guide specific to these platforms for information on configuring their boot loaders.

### 1.2.3. The Kernel

When the kernel is loaded, it immediately initializes and configures the computer's memory and configure the various hardware attached to the system, including all processors, I/O subsystems, and storage devices. It looks for the compressed initrd image in a predetermined location in memory, decompresses it, mounts it, and loads all necessary drivers. It initializes virtual devices related to the file system, such as LVM or RAID before mounting the initrd disk image and freeing up all disk memory once occupied.

At this point, the kernel is loaded into memory and operational. However, since there are no user applications that allow meaningful input to the system, much can be done with it.

In order to set up the user environment, the kernel executes the /sbin/init program.
