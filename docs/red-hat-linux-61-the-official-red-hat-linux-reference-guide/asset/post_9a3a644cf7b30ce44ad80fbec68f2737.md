
# Chapter 17. Kerberos

Whenever the user needs access to a network service, the client software uses the TGT to request a new ticket for that service from the TGS. The service ticket is then used to authenticate the user to that service transparently.

> Warning
> The Kerberos system can be compromised by sending a password in plain text. Any user on the network authenticates against a non-kerberos service by sending a password in plain text. Therefore use of non-kerberos services is discouraged. Such services include Telnet and FTP. Use of other encrypted protocols, such as SSH or SSL secured services, however, is acceptable, though not ideal.

This is only a brief overview of how Kerberos authentication on a network works; seeking an in-depth look at Kerberos authentication should refer to Section 17.7 Additional Resources.

> Note
> Kerberos depends on certain network services to work correctly. First, Kerberos requires synchronization between the machines on the network. Therefore, a clock synchronization program should be set up for the network, such as ntp. For configuring ntp, see /usr/share/doc/ntp-<version-number>/index.html for details on setting up Network Time Protocols.
> Also, certain aspects of Kerberos rely on the Domain Name Service (DNS); be sure the DNS entries and hosts on the network are all properly configured. See the Kerberos V5 System Administrator's Guide, provided in PostScript and HTML formats in /usr/share/doc/krb5-server-<version-number> for more information.

# 17.4. Kerberos and PAM

Currently, kerberos services do not make use of Pluggable Authentication Modules (PAM) — kerberos services bypass PAM completely. However, applications that use PAM can make use of Kerberos for authentication if the pam_krb5 module (provided in the pam_krb5 package) is installed. The pam_krb5 package contains configuration files that allow services to use login and gdm to authenticate users and obtain initial credentials using their passwords. If access to network services is always performed by kerberos services or services that use GSS-API, such as IMAP, the network can be considered reasonably safe.

Administrators should be careful not to allow users to authenticate to most network services using Kerberos. Many protocols used by these services do not encrypt the password over the network, destroying the benefits of the Kerberos system. For example, users should not be allowed to authenticate using their Kerberos passwords over Telnet.

The next section describes how to set up a basic Kerberos service.

# 17.5. Configuring a Kerberos 5 Server

When you are setting up Kerberos, install the server file. If you need to set up slave servers, the details of setting up relationships between master and slave servers are covered in the Kerberos 5 Installation Guide located in the /usr/share/doc/krb5-server-<version-number> directory.

To configure a basic Kerberos server, follow these steps:

1. Be sure you have clock synchronization and DNS on your server before configuring Kerberos 5. Particular attention to time synchronization between the Kerberos server and its various clients. If the server and client clocks differ by more than five minutes (this default is configurable in Kerberos 5), Kerberos clients will not be able to authenticate to the server. This clock synchronization is necessary to prevent an attacker from using an old Kerberos ticket to masquerade as a user.

You should set up a Network Time Protocol (NTP) mapping client/server network if you are not using Kerberos. Hat Linux includes the ntp for easy installation. /usr/share/doc/ntp-<version-number>/index.htm for details on setting up Network Time protocol and for additional information on NTP.

2. Install the kb5-libs, kb5-server, and kb5-workstation packages on the dedicated machine which will run the KDC. This machine needs to be very secure — if possible, you should not run any services other than the KDC.

If you would like to use a graphical user interface to administer Kerberos, you should install the gnome-kerberos package. It contains kb5, a GUI tool for managing tasks.

3. Edit the /etc/kerberos/krb5.conf and /var/kerberos/krb5kdc/krb5.conf configuration files to reflect your realm name and domain-to-realm mappings. A simple realm can be constructed by replacing instances of EXAMPLE, example.com with your domain name — by changing to keep uppercase and lowercase names in the correct format — and changing the KDC from Kerberos, example.com to the name of your Kerberos server. By convention, all realm names are uppercase and all DNS hostnames and domain names are lowercase. For full details on the files, see respective pages.

4. Create the database using the kb5_util utility from a prompt:
`/usr/kerberos/sbin/kb5_util create -s`

The create command creates the database that will store keys for your Kerberos server. The -s switch forces creation of a file in which the master server key is stored. The Kerberos server (krb5kdc) will prompt the user for server password (which can be used to regenerate the key) every time it accesses. Most organizations have administrative access to the Kerberos database and their level of access.

5. Edit the /var/kerberos/krb5kdc/kadm5.acl file. This file is used by kadmin to determine which principals have administrative access to the Kerberos database. Most organizations will be set by a single line:
*admin@EXAMPLE.COM*

Most users are represented in the database by a single principal (with a NULL, or empty, such as joe@EXAMPLE.COM). With this configuration, users with a second principal with an instance of admin (for example, joe/admin@EXAMPLE.COM) will be able to wield power over the Kerberos database.

Once kadmin is started on any of the clients or servers in the realm, you will be able to access its services by naming kadmin. However, only users listed in the kadm5.acl file will be able to modify the database in any way, except for changing their own passwords.

> Note
> The admin utility communicates with the kadmin server over the network, and they use Kerberos to handle authentication. Of course, you need to create the first principal before you can connect to the server to administer it. The first principal with kadmin.local command, which is specifically designed to be used on the same host as the KDC and does not use Kerberos for authentication.

By typing kadmin.local command at the KDC terminal to create the first principal:

```
/usr/kerberos/sbin/kadmin.local -q "addprinc username/admin"
```

6. Start Kerberos using the following commands:
- /sbin/service krb5dc start
- /sbin/service kadmin start
- /sbin/service krb524 start

7. Add for your users using the addprinc command with kadmin, kadmin and kadmin.local are command line interfaces to the KDC. Such, many commands are available after launching the kadmin program. See the kadmin page for more information.

8. Verify that your server will issue tickets. First run kinit to obtain a ticket and store it in a credential cache file. Next, use klist to view the list of credentials in your cache and use kdestroy to destroy the cache and its contents.

![](img/31025704b51d5760c0228ff0f3db98bf_249_0.png)

> Note
> By default, kinit attempts to authenticate using the login name of the account you used when you first logged into your system (the Kerberos server). If that system user name does not correspond to a principal in the Kerberos database, you will receive an error message. If that happens, supply kinit with the name of your principal.

Once you have completed the steps above, the Kerberos server should be up and running. Next, we will set up a client.

# 17.6. Configuring a Kerberos 5 Client

Setting up Kerberos 5 client is less involved than setting up a server. At a minimum, install the client packages and provide each client with a ker5.conf configuration file. Kerberized versions of rsh and rlogin will require some configuration changes.

1. Be sure you have synchronization between the Kerberos client and the KDC. See 17.5 Configuring a Kerberos 5 Server for more information. Additionally, verify that DNS is working properly on the Kerberos client before configuring the Kerberos client.

2. Install the kb5-libs and kb5-workstation packages on all the client machines. You must supply a version of /etc/ker5.conf for each client; this can be the same as ker5.conf file used by the KDC.

3. Be a workstation in the realm that allows users to connect using Kerberos rsh and rlogin, that workstation will need to have the xinetd package installed and its own principal in the Kerberos database. The kshd and klogind server programs will also need access to the keys for their service's principal.
Using kadmin, add a principal for the workstation on the KDC. The instance in this case will use the -randkey option to kadmin's addprinc command to generate a random key:
addprinc -randkey host/blah.example.com
Now you have created the principal, you can extract the keys for the workstation by running kadmin on the workstation itself, and using the ktadd command within kadmin:
ktadd -k /etc/ker5.keytab host/blah.example.com
