### 11.3.2.7. Special Options

These options are occasionally useful for overriding defaults found in the `.fetchmailrc` file.

- -a — Tells Fetchmail to download all messages from the remote server, which are newer or previously viewed. By default, Fetchmail only downloads new messages.
- - Causes Fetchmail to leave the messages on the remote server after downloading them. This option overrides the default behavior of deleting messages after downloading them.
- `<max-number-bytes> — Tells Fetchmail not to download messages over a particular size and leave them on the remote server.
- --quit — Quits the Fetchmail daemon process.

More commands and `.fetchmailrc` options can be found in the `fetchmail` page.

## 11.4. Mail Delivery Agents

Red Hat Linux includes two primary MDAs, Procmail and mail. Both of the applications are considered Local Delivery Agents and both move from the MTA's spool file into the user's mailbox. Procmail provides a robust filtering system.

This section details only Procmail. For information on the `mail` command, consult its page.

Procmail delivers and filters email as it is placed in the mail spool file of the localhost. It is powerful, gentle on system resources, and widely used. Procmail can play a critical role in delivering email to be read by client applications.

Procmail can be invoked in several different ways. When an MTA places an email into the mail spool file, Procmail is launched. Procmail then filters and moves the email so the MUA can find it, quickly. The MUA can be configured to execute Procmail any time a message is received so messages are moved to their correct mailbox. By default, the presence of a `.procmailrc` file in the user's home directory will invoke Procmail when an MTA receives a new message.

The actions Procmail takes with an email are dependent upon instructions from particular `recipes`, or rules, that are matched by the program. If a message matches the recipe, the email will be placed in a certain file, deleted, or otherwise processed.

When Procmail starts, it reads the message and processes the body from the header information. Next, Procmail looks for system-wide environmental variables and `/etc/procmailrc` and `rc` files in the `/etc/procmailrc` directory. Then it looks for a `.procmailrc` file in the user's home directory to find rules specific to that user. Many users create additional `rc` files of their own for Procmail that are referred to by their `.procmailrc` file, which may be turned on or off quickly if a mail problem develops.

In most configurations, the decision of whether to start and attempt to filter the email is based on the existence of a user's `.procmailrc` file. To disable starts, save the work of the `.procmailrc` file, move it to a similar file name using the `mv ~/.procmailrc ~/.procmailrcSAVE` command. When ready to test Procmail, change the name of the file back to `.procmailrc`. Procmail will begin working again immediately.

### 11.4.1. Procmail Configuration

Procmail configuration files, most notably the user's .procmailrc, contain important environmental variables. These variables tell Procmail which messages to sort, what to do with the messages that do not match any recipes, and so on.

These environmental variables usually appear at .procmailrc in the following format:

```
<env-variable>=<value>"
```

In this example, <env-variable> is the name of the variable and <value> defines the variable. Many environment variables are not used by most Procmail, and many of the most important variables are already defined by a default value. Most of the time, the variables will be:

- DEFAULT — Sets the default mailbox that messages do not match any recipes will be placed. The DEFAULT value is the same as $ORGMAIL.
- INCLUDER — Adds additional .rc files containing more recipes for messages to be checked against. This breaks up the Procmail recipe into individual lists that fulfill roles, such as blocking spam and managing email lists, that can then be turned off or by using comment characters in the user's .procmailrc.
For example, a user's .procmailrc file may look like this:
MAILDIR=$HOME/Msgs
INCLUDER=$MAILDIR/lists.rc
INCLUDER=$spam/spam.rc
If the user wants to turn off filtering of their email but leave spam control in place, they could comment out the first INCLUDER line with a hash character #.
- LOCKSLEEP — Sets the amount of time, in seconds, between attempts by Procmail to use a particular lockfile.
- TIMEOUT — Sets the amount of time, in seconds, that must pass after a lockfile was modified before Procmail assumes the lock is old and can be deleted. The default is 1024 seconds.
- LOGFILE — The location and file to contain any Procmail information or error messages.
- MAILDIR — Sets the working directory for Procmail. If so, all other Procmail paths are relative to this directory.
- ORMAIL — Specifies the original mailbox, or another place to put the messages if they cannot be placed in the default or recipe-required location. By default, value of /var/sp/mail/$HOME is used.
- SUSPEND — Sets the amount of time, in seconds, that Procmail will pause if a necessary resource, such as swap, is not available.
- SWITCHRC — Allows a user to specify an extra file containing additional Procmail recipes, much like the INCLUDER option, that recipe checking is actually stopped on the referring configuration file and only the recipes on the SWITCHRC-specified file are used.
- VERBOSE — Causes Procmail to log more information.

Other important environment variables are pulled from the shell, such as LOGNAME, which is the login name; HOME, which is the location of the home directory; and SHELL, which is the default shell.

A comprehensive explanation of all environments variables, as well as their default values, is available in the procmailrc man page.

### 11.4.2. Procmail Recipes

New users often find the construction of recipes the most difficult part of learning to use Procmail. To some extent, this is understandable, as recipes do their message matching using regular expressions, which is a particular format used to specify qualifications for a matching string. However, regular expressions are not very difficult to construct and even less difficult to understand when read. Additionally, the consistency of the Procmail recipes is wherein, regardless of regular expressions, makes it easy to figure out what is happening.

A thorough explanation of regular expressions is beyond the scope of this section. The structure of Procmail recipes is more important and useful. Procmail recipes can be found at various places on the Internet (http://www.linux.org/procmail/links.html). The proper use and adaptation of regular expressions depend upon an understanding of Procmail. Introductory information specific to basic rules can be found in the grep man page.

A Procmail recipe takes the following form:

```
:<flags>: <lockfile-name>
```

- * <special-condition-character> <condition-1>
- * <special-condition-character> <condition-2>
- * <special-condition-character> <condition-N>

```
<special-action-character> <action-to-perform>
```

The first two characters in a Procmail recipe are a colon and a zero. Various flags can be placed after the zero to control what Procmail does when processing this. A colon after the <flags> section specifies that a lockfile is created. If a lockfile is to be created, specify its name in the <lockfile-name> space.

A recipe can contain several sections to match the message. If it has none, every message matches the recipe. Regular expressions are used, they must all match in order for an action to be performed. Conditions are checked after the flags set in the recipe's first line. Optional action characters placed after the * can further control the action-to-perform. Special action characters may also be used before the action is specified.

The <action-to-perform> specifies what is to happen to a message if it matches one of the conditions. There can be only one action per recipe. In many cases, the name of a mailbox is used here to direct matching into another program, effectively sending the email.

#### 11.4.2.1 Delivering vs. Non-Delivering Recipes

The action used if a recipe matches a message determines whether the recipe is delivering or non-delivering. A delivering recipe contains an action that writes the message to a file, sends the message to another program, or forwards the message to another email address. A non-delivering recipe covers any other actions, such as when a nesting block is used. A nesting block is an action contained in braces that designates additional actions to perform on messages that match the recipe's conditions.

Delivering recipes that match cause Procmail to perform the action and stop comparing the message against any other recipes. Messages that match conditions in non-delivering recipes continue to be compared against other recipes in the current and rc files. In words, non-delivering recipes use the message to continue through the recipes after the action is taken on it.
