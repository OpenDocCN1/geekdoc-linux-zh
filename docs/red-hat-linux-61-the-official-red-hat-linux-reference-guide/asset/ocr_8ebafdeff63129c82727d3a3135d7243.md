# 9.4.1. Host Access

NFS controls who manage an exported file system based on the host mount request, the user that will actually use the exported file system. Access control is not possible for users, other than file and directory permissions. In others, once a file system is exported via NFS, any user on remote host can access the shared data. To limit the potential risks, administrators can allow only read-only or accessing users to a common user and groupid. These solutions may prevent the NFS share from being used in the way it was originally intended.

Additionally, if an attacker gains control of the DNS server used by the exporting NFS file system, the system with a particular hostname or fully qualified domain name can be pointed to an unauthorized machine. At this point, the unauthorized machine is system permitted to mount the NFS share, no username or password information is exchanged to provide additional security for the NFS mount. The risk holds true to compromised NIS servers, if NIS netgroups are used to allow certain hosts to mount NFS share. By using IP addresses in /etc/exports, this kind of attack is more difficult.

Wildcards be used sparingly when granting NFS shares as the scope of the wildcard may encompass more systems than intended.

For more information on securing NFS, refer to the chapter titled *Server Security in the Red Hat Linux Security Guide*.

# 9.4.2. File Permissions

Once the NFS file system is mounted read-write by a remote host, the only protection each shared file has its permissions. If two users share the same userid value the same NFS file system, they will be able to modify others files. Additionally, anyone logged in as root as the client system can use su to become a user who can access particular files via the NFS share. For NFS and userid conflicts, refer to the chapter titled *Managing Accounts and Groups in the Red Hat Linux System Administrator*.

The default behavior when exporting a file system via NFS is to root squashing. This sets the userid of root user on their local machine to a value of the server’s nobody account. Never turn off root squashing.

If exporting an NFS share read-only, consider using the all_squash option, which makes every user accessing the exported file system take the userid of the nobody user.
