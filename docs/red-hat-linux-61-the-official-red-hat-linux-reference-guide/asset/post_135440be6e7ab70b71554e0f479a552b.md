### 7.3.10. DRI

The optional DRI section specifies parameters for the Direct Rendering Infrastructure (DRI). DRI is an interface which allows multiple 3D applications to take advantage of 3D hardware acceleration capabilities into most modern video hardware. In addition, DRI can improve 2D performance via hardware acceleration, if supported by the video card's driver.

This section is ignored unless DRI is enabled in the Module section.

The following example illustrates a typical DRI section:

```
Section "DRI"
Group 0
Mode 0666
EndSection
```

Since different video use DRI in different ways, do not alter the values for this section first referring to the /usr/X11R/lib/X11/doc/README.file.

### 7.4. Fonts

Red Linux uses two methods to manage fonts and display under XFree86. The new Config font subsystem simplifies font management and provides advanced display features, such as antialiasing. This system is used automatically for applications programmed using the Qt 3 or GTK+2 graphical toolkit.

For compatibility, Red Hat includes the original font subsystem, called the core X font system, which is over 15 years old, is based around the X Font Server (xfs).

This section discusses how to configure fonts for X using both systems.

### 7.4.1. Fontconfig

The Fontconfig subsystem allows applications to directly access fonts on the system and Xft or other rendering mechanisms to render Fontconfig fonts with advanced antialiasing. Graphical applications can use the Xft library with Fontconfig to draw text to the screen.

Over time, the Fontconfig/Xft font subsystem will replace the core X font subsystem.

> Important

The Fontconfig font subsystem does not work for OpenOffice.org and Abiword, which use their own font rendering technology.

It is important to note that Fontconfig shares the /etc/fonts/fonts.conf configuration file, which replaces the /etc/X11/XftConfig. The Fontconfig configuration file should not be edited by hand.

Tip

Due to the transition to the new font system, GTK+ 1.2 applications are not affected by any changes made via the Font Preferences dialog (accessed by selecting Main Menu Button [on the Panel] -> Preferences = Font). For these applications, a font can be configured by adding the following lines to the file ~/.gtkrc-mine:

```
style "user-font" {
  fontset = "<font-specification>"
  widget_class ** style "user-font"
}
```

Replace <font-specification> with a font specification in the style used by traditional X applications, such as -adobe-helvetica-medium-r-normal-*-120-*-*-*. A full list of core fonts can be obtained by running xfonts or created interactively using xfont

### 7.4.1.1. Adding Fonts to Fontconfig

Adding new fonts to the Fontconfig subsystem is a straightforward process.

1. To add fonts systemwide, copy the new fonts into the /usr/share/fonts/local/ directory.
   To add for an individual user, copy the new fonts into the .fonts/ directory in the user's home directory.
2. Use the fc-cache command to update the font information cache, as in the following example:
fc-cache <path-to-font-directory>
   In this command, replace <path-to-font-directory> with the directory containing the new fonts (either /usr/share/fonts/local/ or ~/.fonts/).

Tip

Individual users may also install fonts graphically, by browsing to fonts:/// in Nautilus, and dragging the new font files there.

Important

If the font filename ends with a .gz extension, it is compressed and cannot be used until compressed. To do this, use the gunzip command or double-click the file and drag the font to a directory in Nautilus.

### 7.4.2. Core X Font System

For compatibility, Red Hat Linux provides the core X subsystem, which uses the X Font Server (xfs) to provide fonts to X applications.

The Free86 server looks for a font specified in the FontPath entry under the Files section of the /etc/X11/xf8Config configuration file. Refer to Section 7.3.1.4 Files for more information on the FontPath entry.

The Free86 server connects to the xfs server on a specified port to acquire font information. For this reason, the xfs service must be running in order to start. For configuring services for a particular runtime, refer to the chapter titled Controlling Access to Services in the Red Hat Linux Customization Guide.

### 7.4.2.1. xfs Configuration

The /etc/rc.init.d/xfs script starts the xfs server. Several options can be configured in the /etc/X11/xfs.config file.

The following is one of the more common options:

- alternate-servers — Specifies a list of alternate servers to be used if this font server is not available. A comma must follow every font server in the list.
- catalogue — Specifies an ordered list of fonts.
- client-limit — Specifies the maximum number of clients.
- clone-self — Allows the font to clone itself.
- default-size — Specifies the default size.
- default-resolutions — Specifies a list of resolutions.
- defer-glyphs — Specifies whether to defer glyphs.
- error-file — Specifies the path to error log.
- port — Specifies the port.
- use-sys — Specifies whether to use the system.

### 7.4.2.2. Adding Fonts to xfs

To add fonts to the core font subsystem (xfs), follow these steps:

1. If it does not already exist, create a directory called /usr/share/fonts/local/:
   mkdir /usr/share/fonts/local/
2. Copy the new fonts into the /usr/share/fonts/local/:
   cp /usr/share/fonts/local/
3. Update the font information by the following command:
   fc-cache -d /usr/share/fonts/local/
4. Restart the xfs server using the following command:
   service xfs restart

### 7.5. Runlevels and X

In most cases, the default installation of Red Linux configures a machine to boot into graphical environment, known as runlevel 5. It is possible, however, to boot into text-only mode called runlevel 3.

For more information about runlevels, refer to Section 1.4 SysV Init.

### 7.5.1. Runlevel 3

When in runlevel 3, the best way to start an X session is to log in and type startx. The startx command is a front-end to the xinit command which launches the X server and connects X clients to applications. Because the user is already logged in at runlevel 3, start does not launch a display manager or authenticate users. Refer to Section 7.5.2 for more information about display managers.

When startx is executed, it searches for a .xinitrc file in the user's home directory to define the desktop environment and possibly other client applications to run. If no .xinitrc is present, it will use the default /etc/X11/init/xinitrc file instead.

The default xinitrc script then loads user-defined files and default system files, .Xresources, .Xmodmap, and .Xkbmap in the user's home directory and XResources, Xmodmap, and Xkbmap in the /etc/X11/init/. The Xmodmap and Xkbmap files, if they exist, are used by the xmodmap utility to configure the keyboard. The XResources files are read to assign specific preferences to applications.

After these options, the xinitrc script executes all scripts, located in the /etc/X11/init/xinitrc.d/. One important script in this directory is xinput, which configures settings with the default language.

Next, the xinitrc script tries to execute Xclients in the user's home directory and /etc/X11/init/Xclients if it cannot be found. The purpose of the Xclients file is to start desktop environment or, possibly, just a window manager. The .Xclients script in the user's home directory starts the user-specified desktop environment in the .Xclients-default file. If .Xclients does not exist in the user's home directory, the default then /etc/X11/init/Xclients script attempts to start another desktop environment, trying GNOME first and KDE by twm.

The user is returned to a text mode session after logging out of X from runlevel 3.
