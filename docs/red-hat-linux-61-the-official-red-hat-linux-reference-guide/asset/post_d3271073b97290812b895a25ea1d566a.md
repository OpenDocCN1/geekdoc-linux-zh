## Chapter 12. Berkeley Internet Name Domain (BIND)

### 12.3. Zone Files

Zone files contain information about a particular namespace and are stored in the named working directory, `/var/named/` by default. Each zone file is named according to the file option in the zone statement, usually in a way that relates to the domain and identifies the file as containing data, such as example.com.zone.

Each zone file may contain directives and resource records. Directives tell the nameserver to perform tasks or apply special settings to the zone. Resource records define the parameters of the zone and assignments to individual hosts. Optional, but resource records are required to provide nameservice to a zone.

All directives and resource records should go on their own individual lines.
Comments can be placed after semicolon characters (;) in zone files.

### 12.3.1. Zone File Directives

Directives begin with the dollar sign ($) followed by the name of the directive. They usually appear at the top of the zone file.
The following are commonly used directives:

- $INCLUDE Configures named to include another zone in this zone file at the place where the directive appears. This allows additional zone settings to be stored apart from the main zone file.
- $ORIGIN Appends the name to resource records, such as with the hostname and nothing more.

For example, a zone file may contain the following line:
$ORIGIN example.com
Any names in resource records that do not end in a trailing period (.) will have example. appended to them.

Note
The use of the $ORIGIN directive is unnecessary if the zone is specified in /etc/named.conf because the zone name is used as the value for the $ORIGIN directive by default.

- $TTL Sets the Time to Live (TTL) value for the zone. This is the length of time, in seconds, a resource record is valid. Each resource record can contain its own TTL value, which overrides this directive.

Increasing this value allows nameservers to cache the zone information for a longer period of time, reducing the number of queries for the zone and lengthening the amount of time to proliferate resource record changes.

### 12.3.2. Zone Resource Records

The primary component of a zone file is its resource records.
There are many types of zone resource records. The following are used most frequently:

- A Address record, which specifies an IP address to assign to a name, as in this example:
<host> IN A <IP-address>
If the <host> is omitted, then an A record points to a default IP address for the top of the namespace. This system is the target for all non-FQDN requests.

Consider the following A record examples for the example.com zone:

```
IN A 10.0.1.3
server1 IN A 10.0.1.5
```

Requests for example.com are pointed to 10.0.1.3, while requests for server1.example.com are pointed to 10.0.1.5.

- CNAME — Canonical name record, maps one name to another. This type of record is also known as an alias record.

The next example tells that any requests sent to the <alias-name> will point to the host, <real-name>. CNAME records are most commonly used to point to services that use a common naming scheme, such as www for Web servers.

```
<alias-name> IN CNAME <real-name>
```

In the following example, an A record binds to an IP address, while a CNAME record commonly used hostname to it.

```
server1 IN A 10.0.1.5
www IN CNAME server1
```

- MX — Exchange record, which where numerical ranking is sent to a mail server controlled by this zone go.

```
IN MX <preference-value> <email-server-name>
```

In this example, the <preference-value> allows numerical ranking of the mail servers for a namespace, giving preference to some email systems over others. The MX record with the lowest <preference-value> is preferred over the others. However, multiple servers can share the same value to distribute mail traffic among them.

The <email-server-name> may be a hostname or FQDN.

```
IN MX 10 mail.example.com.
IN MX 20 mail2.example.com.
```

In this first example, mail.example.com email server is preferred to mail2.example.com when receiving email for the example.com domain.

- NS — NameServer record, which announces the authoritative nameserver for a particular zone.

This is an example of an NS record:

```
IN NS <nameserver-name>
```

The <nameserver-name> should be a FQDN.

Next, two nameservers are listed as authoritative for the domain. It is not important whether the nameservers are slaves or if one is a master; both are still considered authoritative.

```
IN NS dns1.example.com.
IN NS dns2.example.com.
```

- PTR — PointTeR record, designed to point to another part of the name.

PTR records are used reverse for name resolution, as they point IP addresses to a particular name. See Section 12.3.4 Reverse Name Resolution Zone Files for more examples of PTR records in use.

- SOA — Start Of Authority record, proclaims authoritative information about a namespace to the nameserver.

Located after the directives, an SOA resource record is the first record in a zone file.

The following example shows the basic structure of an SOA record:

```
@ IN SOA <primary-nameserver> <hostmaster-email>
<serial-number>
<time-to-refresh>
<time-to-retry>
<time-to-expire>
<minimum-TTL>
```

The # symbol replaces the ORIGIN directive (or the zone's name, if the ORIGIN directive is not set) as the name defined by the SOA resource record. The primary nameserver is authoritative for this domain used for the <primary-name-server>, and the email of the person to contact this name is substituted for the <hostmaster-email>.

The <serial-number> is incremented every time the zone file so changed is named named which it will know that it needs to reload this zone. The <time-to-refresh> tells all servers to wait before asking the master nameserver if any changes have been made to the zone. The <serial-number> value is used by the slave to determine if it is using outdated zone data and should refresh. The <time-to-expire> tells the slave how long to wait before it considers the zone data stale. The <minimum-TTL> is the minimum interval between refreshes.

### 12.3.3. Example Zone File

Seen individually, directives and resource records can be difficult to grasp. However, when placed together in a single file, they become easier.

The following example shows a basic zone file.

```
$ORIGIN example.com
$TTL 86400
@ IN SOA dns1.example.com. hostmaster.example.com. (
    2001062501 ; serial ; refresh after 6 hours
    21600 ; retry after 1 hour
    3600
    604800 ; expire after 1 week
    86400 )

IN NS dns1.example.com.
IN NS dns2.example.com.

IN MX 10 mail.example.com.
IN MX 20 mail2.example.com.

IN A 10.0.1.5
server1 IN A 10.0.1.5
server2 IN A 10.0.1.7
dns1 IN A 10.0.1.2
dns2 IN A 10.0.1.3

ftp IN CNAME server1
mail IN CNAME server1
mail2 IN CNAME server2
www IN CNAME server2
```

### 12.3.4. Reverse Name Resolution Zone Files

A reverse name zone file is used to translate an IP address in a particular namespace into a FQDN. It works similarly to a standard zone file, except that PTR records are used to link the IP addresses to a fully qualified name.

A PTR record looks like this:

```
<last-IP-digit> IN PTR <FQDN-of-system>
```

The <last-IP-digit> relates to the name in an IP address that should point to a particular system's FQDN.

In this example, IP addresses 10.0.1.20 through 10.0.1.25 are pointed to corresponding FQDNs.

```
$ORIGIN 10.0.1.in-addr.arpa
$TTL 86400
@ IN SOA dns1.example.com. hostmaster.example.com. (
    2001062501 ; serial ; refresh after 6 hours
    21600
    3600
)
```
