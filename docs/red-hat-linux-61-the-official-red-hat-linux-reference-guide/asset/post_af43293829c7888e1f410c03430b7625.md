
## 11.4.2.2. Flags

Flags are very important in determining how or if a recipe's conditions are compared to a message.
The following flags are commonly used:

- A—Specifies that this case is only used if the previous recipe without an A or a flag also matched this message.
- To ensure that the action on this last matching recipe was successfully completed before allowing a match on the current recipe, use the A flag instead.
- B—Parses the body of the message and looks for matching conditions.
- b—Uses the body in any resulting action, such as writing the message to a file or forwarding it. This is the default behavior.
- c—Generates a copy of the email. This is used with delivering recipes, since the required action can be performed on the message and a copy of the message can continue being processed in the rc files.
- D—Makes the egreg comparison case-sensitive. By default, the comparison process is not case-sensitive.
- E—While similar to the A flag, the conditions in it are only compared to the message if the preceding recipe without an E did not match. This is comparable to an else action. Use the e flag if this recipe is checked before the preceding recipe acted but failed.
- f—Uses the pipe as a filter.
- H—Parses the header of the message and looks for matching conditions. This occurs by default.
- h—Uses the header in a resulting action. This is the default behavior.
- w—Tells Procmail to wait for the specified filter or program to finish, and reports whether or not it was successful before considering the message. To ignore "Program failure" messages when deciding whether a filter or action succeeded, use the W option instead.
Additional flags can be found in the procmail page.

## 11.4.2.3. Specifying a Local Lockfile

Lockfiles are very useful with Procmail to ensure that more than one process does not try to alter a certain message at the same time. Specify a local lockfile by placing a colon (:) after any flags on a recipe's first line. This creates a lockfile based on the destination file name plus whatever has been set in the LOCKEXT global environment variable.
Alternatively, specify the name of the lockfile to be used with this recipe after the colon.

## 11.4.2.4. Special Conditions and Actions

Particular characters used before Procmail recipe conditions and actions change the way they are interpreted.
The following characters may be used after the * character at the beginning of a recipe's condition line:

- !—In the condition line, this character inverts the condition, causing a match to occur only if the condition does not match the message.
- !Checks to see if the message is under the specified number of bytes.
- Checks to see if the message is under a specified number of bytes.

The following characters are used to perform special actions:

- ! In the action line, this character tells Procmail to forward the message to the specified addresses.
- $ Refers to a variable set earlier in the rc file. This is often used to set a common mailbox it is referred to by various recipes.
- | The pipe character tells Procmail to start a specific program to deal with this message.
- ( and ) Constructs a nesting block, used to contain additional recipes to apply to matching messages.

If no special character is used at the beginning of the action line, Procmail assumes the action line is specifying a mailbox where the message should be written.

## 11.4.2.5. Recipe Examples

Procmail is an extremely flexible program, that matches messages with specific conditions and then performed detailed actions on them. As a result of this flexibility, composing a Procmail recipe from scratch to achieve a certain goal can be difficult for new users.

The best way to develop the skills to build Procmail recipe conditions comes from strong understanding of regular expressions when looking at many examples built by others. The following very basic examples serve as a demonstration of the structure of Procmail recipes and can provide the foundation for more intricate constructions.

A basic recipe may not even contain conditions, as is illustrated in the following example:

```
:0
new-mail.spool
```

This basic recipe could be placed at the end of all rc files to direct messages to a default location. A more complicated example might grab messages from a particular email address and throw them away, as can be seen in this example.

```
:0
* From: spammer@domain.com
/dev/null
```

With this example, any messages sent by spammer@domain.com are immediately moved to /dev/null, deleting them.

> Caution: Be careful that a rule is working correctly before moving messages that are matched to /dev/null, are permanently deleted. If the recipe conditions catch inadvertently unintended messages, they disappear without a trace, making it hard to troubleshoot the rule.

A better solution is to point the recipe's action to a special mailbox, which can be checked from time in order to look for false positives, or messages that inherently matched the conditions. Once satisfied that no messages are accidentally matched, delete the mailbox and direct the action to send the messages to /dev/null.

Procmail is primarily used as a filter for email, automatically placing it in the right place to prevent manual sorting. The recipe grabs email sent from a particular mailing list and puts it in the correct folder.

```
:0:
* ^(From|CC|To).*tux-lug
tuxlug
```

Any messages sent from the tux-lug@domain.com mailing list will be placed in the tuxlug-box automatically for the MUA. Note that the condition in this example will match the message if it has the mailing list's address on the From, CC, or To lines.

Consult the Procmail online resources available from Section 11.6 Additional Resources for more detailed and powerful recipes.

## 11.4.2.6. Spam Filters

Because it is called by Sendmail, Postfix, and Fetchmail upon receiving new emails, Procmail can be used as a powerful tool for combating spam.

This is particularly true when Procmail is used in conjunction with SpamAssassin. When together, these applications can quickly identify spam, or sort or destroy them.

SpamAssassin uses header analysis, text analysis, blacklists, and a spam-tracking database to quickly and accurately tag spam.

The easiest way for a user to use SpamAssassin is to place the following line near the top of the ~/.procmail file:

```
INCLUDESRC=/etc/mail/spamassin/spamassassin-default.rc
```

The /etc/mail/spamassin/spamassassin-default.rc contains a simple Procmail rule that activates SpamAssassin for all incoming email. If an email is determined to be spam, it is tagged in the header as the title is prefixed with.

## 11.5. Mail User Agents

There are scores of mail programs available under Red Hat Linux. There are full-featured, graphical client email programs, such as Mozilla Mail or Ximian Evolution, as well as text-based email programs like mutt and pine.

For instructions on these applications, refer to the chapter titled Email in the Red Hat Started Guide.

The remainder of this section focuses on securing communication between the client and server.

### 11.5.1. Securing Communication

Popular MUAs with Red Hat Linux, such as Mozilla Mail, mutt, and pine, offer SSL-encrypted email sessions.

Like any other data that flows over a network unencrypted, important email information, such as usernames, passwords, and messages, may be intercepted and viewed by users on the network. Additionally, since the standard POP and IMAP protocols pass authentication unencrypted, it is possible for an attacker to gain access to user accounts by collecting usernames and passwords.

### 11.5.1.2. Secure Email Clients

Most MUAs designed to check email on remote servers support SSL encryption. In order to use SSL when retrieving email, it must be enabled on both the client and server.

SSL is easy to enable on the client-side, often with the click of a button in the MUA's configuration window or via an option in the MUA's configuration file. Secure IMAP and POP have known port numbers (993 and 995, respectively) that the MUA will use to authenticate and download messages.

### 11.5.1.2. Securing Email Client Communications

Offering SSL encryption to IMAP and POP users on the email server is a simple matter.

First, create an SSL certificate. This can be done two ways: by applying to a Certificate Authority (CA) for an SSL certificate or by creating a self-signed certificate.
