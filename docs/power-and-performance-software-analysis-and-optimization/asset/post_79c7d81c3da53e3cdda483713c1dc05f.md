Using this information, it is possible to rearrange a data structure's memory layout to improve locality. As always, any changes should be measured and verified with benchmarking to ensure that they actually improve performance. For example, consider the following structure:

```c
struct bad_locality {
  int x;
  char strdata[252];
  int y;
};
```

In this example, assume that profiling has identified that code utilizing this structure is suffering from performance penalties due to cache replacements, where caches are loaded and prematurely evicted. Also assume that the accesses to this structure frequently use bad_locality.x and bad_locality.y, together and don't use bad_locality.strdata. Now the output from pahole, which has been adjusted to fit the page width of this book, for this structure:

```c
struct bad_locality {
  int x;              /* 0 4 */
  char strdata[252];  /* 4 252 */
  /* cacheline 4 boundary (256 bytes) -- */
  int y;              /* 256 * */
```

> /* size: 260, cachelines: 5, members: 3 */
/* last cacheline: 4 bytes */

Notice that bad_locality.x and bad_locality.y are separated by four cache lines. Because of this, two separate cache lines, one for each member, will need to be loaded to complete any operation over integers. Also, the gap between the two cache lines grows, the probability of both cache lines being present in the L1 cache decreases simultaneously, potentially increasing the time required to fetch these elements from memory. On the other hand, by rearranging this, so that bad_locality.x and bad_locality.y share a single cache line, the number of cache lines that need to be loaded is halved. In other words, the struct would be rearranged into:

```c
struct better_locality {
  int x;
  int y;
  char strdata[252];
}
```

Another situation to consider is the behavior of a memory layout when grouped together as an array. Continuing with the previous example, how the better_locality struct will behave when stored in an array of few thousand elements, back-to-back.

Assume that the first elements aligned to the cache size, and therefore starts on the first byte of a new cache line. This first element will consume four whole cache lines and 4 bytes of the fifth cache line, that is 260 mod 64 = 4. As a result, the second element will start at the fifth byte of the cache line which was partially used by the first element. Since this second element starts at an offset of 4 bytes in the first cache line, it will require another 4 bytes in its last cache line, that is (4 + 260) mod 64 = 8, and so on. This trend will continue, with each element shifting the next element over to the right until a multiple of the cache size is reached, at which 64/(260 mod 64) = 16, will result in better_locality.x and better_locality.y being split between two cache lines. While in this example, this phenomenon may seem to be very inconvenient, the pattern illustrated here, where elements in an array have position shifted due to the previous elements, can play havoc with variables that strict alignment requirements.

There are three obvious approaches to resolving this issue. The first trades for size of speed by adding extra padding to each struct. Since this example is keeping better_locality.y would be sufficient to ensure they never were separated. This could also be achieved by padding the structure with 60 bytes, so it wouldn't use any partial cache lines, that is, sizeof(struct better_locality) mod 64 = 0.

The second possibility, rather than adding padding to increase the size of each array element, would be to decrease the size. Naturally, the feasibility of this approach would depend on whether the reduction in range affects correctness. In the example, this could be accomplished by reducing both integer fields to shorts, removing 4 bytes from the character array, or a combination of both.

The third possibility would be to split the structure into two distinct structures, one containing the integer fields, and one containing the character array. This option relies on the assumption that better_locality.x and better_locality.y are used together, and that are not used with best_locality.strdata. In the case where this assumption holds, this option most likely will provide the results.

Parallelism, the act of performing two or more operations simultaneously, is a topic that has generated lots of interest within the last decade. Part of this stems from the simplification of uniprocessor (UP) to widely available symmetric systems (SMP). Another part of this interest stems from the simplification of general purpose computing (HPC) to vector processing.

Unfortunately, one hazard of the modern hype is the misconception that parallelism makes everything fast. On the contrary, many tasks will run slower than serial code. It is important to keep in mind that properly parallelizing requires careful analysis of threads and processes. The decision between these two techniques revolves around whether address space should be shared or isolated. In Linux, both threads are created with the clone(2) call, and processes can also be created with the fork(2) call.

The concept of pipes and filters, that is, filters being the applications and pipes being the glue that connects simplistic ones is a fundamental aspect of the UNIX philosophy. Every filter, whether executed interactively in a terminal or nonactively in a shell script, is executed by creating a new process. This is achieved via the(2) call, which duplicates the process. To change this, the execve(2) system replaces the current process with the image specified.

Since the workflow of creating a new process and then immediately loading an executable before starting a different command is incredibly complex, the Linux kernel is highly optimized. That being said, process creation is still very expensive. In this situation, because execve(2) immediately replaces the current process with a new image, the copying of the parent into the child is unnecessary. In order to avoid these unnecessary data copies, Linux processes are created with Copy on Write (COW). With COW, rather than performing a deep copy of the parent into the child, the child resources point to the parent but are marked as read-only. If the child process doesn't perform any modifications to the address space, no copies are formed.
