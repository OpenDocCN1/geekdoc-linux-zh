## 11.3.4 DEVICE STATS

As mentioned earlier, PowerTOP can aggregate power consumption data from a variety of sources, including actual power meters, the RAPL interface introduced in Second Generation Intel Core processor, and software modeling. The software models provided with PowerTOP are based on actual data collected with a power meter. This power information shows how different devices power consumption scales with utilization, which is another aspect of the system monitored by PowerTOP. By combining these two aspects, PowerTOP is able to estimate the actual power drain per device. It is important to recognize that these are estimates, and measuring consumption precisely requires a hardware meter.

Figure 11.4 illustrates an example Device Stats.

## 11.3.5 TUNABLES

PowerTOP automatically checks the system configuration in order to detect any misconfigurations that might hurt power efficiency. Using the Up and Down Arrow keys, it is possible to scroll through each item. With an item marked highlighted, pressing the Enter key calls PowerTOP to attempt to modify the misconfigured item to a more appropriate value. This is accomplished by writing to files in sysfs and is not a persistent modification. This functionality is for testing the impact of various configurations, since PowerTOP is not designed for configuring system settings each boot. Instead, a daemon called tuned can be used to automatically set the desired configuration at boot. The tuned daemon is packaged with a tool powertop2tuned that runs PowerTOP and then translates its suggestions into a custom tuned profile.

## 11.3.6 LATENCYTOP

Similar to PowerTOP, LatencyTOP is a monitor, also written by Arjan van Ven, for measuring the duration that user applications spend in blocked state. In order to instrument the kernel to obtain this data, the kernel must be built with Latency support. Most Linux distributions only enable these options for their debug kernels.

```bash
$ grep LatencyTOP /boot/config-$(uname -r)
CONFIG_HAVE_LATENCY_SUPPORT=y
```

LatencyTOP communicates with user space through proc filesystem. Accessing this information requires root privileges. Data collection is enabled or disabled by writing "1" or "0" into /proc/sys/kernel/latency. Once data collection is enabled, latency statistics for the entire system are accessed through /proc/latency_stats. Additionally, the latency statistics for each process can be accessed via the latency file within processes' directory, for example, /proc/2145/latency.

The first line of each files is a header, which identifies the LatencyTOP version. This header is then followed by zero or more data entries. Each of these entries take the form of three integers followed by a string. This string contains the function stack, starting from the right, each function call separated by a space. This call only tracks kernel functions, so the function on the right is always a system call. The first integer represents the number of times this function call has occurred. The second integer represents the total microseconds of latency caused by this call stack. The third integer represents the largest latency in microseconds of one invocation of this call stack (van de Ven, 2008).

For example:

```bash
# cat /proc/630/latency
Latency Top version : v0.1
1 881 poll_schedule_timeout do_sys_poll Sys_poll system_call_
fastpath
1 9 futex_wait_queue_me futex_wait_futex Sys_futex system_call_
fastpath
```

In this example, the process has two system calls, poll(2) and futex(2). Each of these calls occurred once, with the invocation of poll(2) blocking for 881 µs, and the invocation of futex(2) blocking for 9 µs.
