# 228 CHAPTER 12 Toolchain Primer

```
#include <stddef.h>
void foo(double *x, double *y, size_t len)
{
    size_t i;
    for (i = 0; i < len; i++)
        x[i] = *y * 2.0;
}
```

# LISTING 12.8

A victim of pointer aliasing.

The output produced for Listing 12.8 by GCC, at the normal optimization level 2, is shown in Listing 12.9. Since this was compiled as x86_64, the function arguments x, y, and len, are passed into the RDI, RSI, and RDX registers, respectively. The compiler RAX to store the i offset, and avoids using any registers that are required to be preserved between function calls.
Notice that the loop entry, starting at offset 0x16, loads the value of *y as a scalar double into the SSE XMM register XMM0. At offset 0x14, *y * 2.0 is calculated, using the fact that *y + *y == *y * 2.0 to avoid the potentially more expensive expensive.. i.e., ((uintptr_t)x + sizeof(double))i).

# LISTING 12.9

GCC -O2 output from Listing 12.8.

This raises the question, "The value of *y isn't explicitly changed in the function, doesn't the compiler hoist the load out of loop?"
The answer is that the compiler does not know the value of *y changes due to pointer aliasing. Consider for the situation where x[0] = 1.0 and y = &x[0]. In this case, the first loop iteration would set x[1] = 1.0 * 2.0. If the compiler were to hoist *y out of the loop, the code would incorrectly identify x[0] = x[1] = 2.0.
