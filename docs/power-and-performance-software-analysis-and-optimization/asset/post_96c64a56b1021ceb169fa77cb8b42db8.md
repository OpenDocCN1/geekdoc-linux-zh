## 11.1 GNU Profiler

The GNU profiler, gprof, provides basic algorithmic analysis capabilities. Unlike most of the other monitors in this book, gprof depends on the compiler to instrument the executable to be profiled. This extra code, added automatically by the compiler, performs the actual data collection and outputs it to a file. The gprof(1) tool is then used to translate the collected data in this file into a text-based report.

Since grep depends on the compiler to insert the necessary profiling code, this profiling method relies on compiler support. At the time of this writing, all major toolchains support this feature. To use gprof with GCC or LLVM, the code must be compiled and linked with the -pg compiler flag. To use gprof with ICC, the code must be compiled and linked with the -p compiler flag.

Once the instrumented executable has been built, run the test workload. When its execution completes, the profiling data will be saved into a binary file named gmon.out. Multiple runs of the instrumented binary will overwrite this file, each time resulting in loss of data from the previous run. In order to combine the results of multiple runs without data loss, the data from each run must be summarized into a master file, gmon.sum. This is accomplished by using the --sum flag with gprof(1) and providing gmon.sum, if it exists, as an input file, along with the current run. Finally, once the desired data has been collected, the binary file, gmon.out, the default if no specific file is specified, is converted into a text report by gprof(1) tool. For example, to produce an executable over two runs:

```bash
$ gcc test.c -o test -pg
./test
$ gprof --sum test
./test
$ gprof --sum test gmon.out gmon.sum
```

The generated report, printed to stdout, is divided into two parts, a flat profile and a graph. The profile lists functions where the most time was accounted for. ## 11 Other Helpful Tools

One of the major limitations of gprof is its lack of the ability to profile code located in dynamically linked libraries. A simple workaround is to statically link the executable to be profiled when compiling with gprof instructions.

### 11.2 Gcov

The GNU code coverage tool, gcov, isn't much of a profiling tool. Instead, its primary tool is to measure the code coverage achieved by unit tests; however, the tool is worth mentioning since it provides one piece of information: the percentage of times each conditional branch was taken. This is especially useful for routine error handling branches, to judge which branches are frequently taken and which are skipped.

Similar to gprof, gcov also relies on the compiler to instrument the application's executable, but the compiler flag used is different. At the time of running, gcov is only well supported by GCC. Both ICC and LLVM provide their own coverage tools, which are incompatible; however, it may provide more information from them.

In order to enable coverage instrumentation with GCC, the application executable must be compiled and linked with the `--coverage` compiler flag. The instrumented executable is then run. The code inserted into the instrumented executable will generate two binary files for each source file, a `.gno` and `.gcda`. For instance, `foo.c` will have a corresponding `foo.gno` and `foo.gcda` file.

These files are converted into a text report by running `gcov()` with the desired source file as an argument. Rather than printing the results to `stdout`, a new text file will be created reporting the coverage for the source file passed as an argument. The name of this file is the source file name, a `.gcov` suffix appended. Continuing the previous example, `gcov foo.c` will generate a text file report in the file `foo.c.gcov`.

For example:

```bash
$ gcc test.c -o test --coverage
./test
$ gcov -b test.c
```
