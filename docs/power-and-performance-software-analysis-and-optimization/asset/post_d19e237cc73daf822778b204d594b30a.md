## 11.5 SYSPROF

Sysprof is a monitor that measures how time is spent in each function call. Time per function is reported with two different metrics, cumulative time and self time. Cumulative time measures the time spent within a function, including all function calls invoked from that function. Self time measures the time spent within a function, excluding all function calls invoked from that function, i.e., the cost of the function itself. This level of detail makes Sysprof very useful for algorithmic analysis.

### 11.5.1 COLLECTION

Originally, Sysprof had its own kernel module, which is called sysprof-module, for collecting data. Starting around 2009, Sysprof began leveraging the kernel's perf counter interface, thus obviating the need for a separate module. At the time of this writing, Sysprof unconditionally uses the software counter PERF_SW_CPU_CLOCK, PERF_HW_CPU_CYCLES, as also implemented. Reading through the log, it appears that hardware counters were disabled due to issues with some hardware platforms not working properly. If desired, renewing the hardware counters appears

There are two methods for collecting data in Sysprof, the GTK GUI and the command-line interface. Both methods require the associated permissions for opening an event file descriptor, as configured via the `perf_event_paranoid`, as described in Chapter 8.

The GTK GUI is invoked by the sysprof command. Figure 11.6 is a screenshot of the interface. Through collecting system-wide results, click the Start button in the menubar. As samples are collected, the sample count will increment. Once operation being profiled is complete, stop the collection by selecting the Profile button in the menubar. At this point, the three views, labeled Functions, Callers, and Descendants, will populate. These results can be saved for later inspection via the Save under the Profiler menu.

The Descendants view organizes results as a hierarchical tree of modules, with each module representing a different process. The root of this tree, which will always have a total time of 100%, is labeled “Everything.” The root's children correspond to a process running on the system. The cumulative time represents percentage of time sampled was spent in the given process during data collection. Each process's children represents a function call, and each function call's children represent calls from that function. Double-clicking on a node will update the related Functions and Callers views, based on the selected node.

The Functions views display a sorted list of the functions that consumed the most time. By default, the Functions view sorts based on the total time, which highlights the hottest call chains. # CHAPTER 12 Toolchain Primer

A toolchain is a set of tools for building, inspecting, and modifying software. All of the optimization techniques explained in this book, in one way or another, rely on support from the toolchain. The major components of a toolchain include, but aren't limited to, a compiler, assembler, and a linker.

The compiler is responsible for parsing source files written in a high-level language, such as C. The files are first translated into an intermediate language, used internally to the compiler. This intermediate language allows for the compiler to analyze program flow and optimize accordingly. After the optimization phase, the compiler outputs assembly code, which is passed directly to the assembler.

The assembler is responsible for translating instruction mnemonics, into human-readable assembly, into opcodes expected by the processor. Unlike the compiler, the assembler's output typically has a one-to-one relationship with the assembly source, except in the case of pseudo-instructions, which may translate to multiple, or zero, instructions. The output produced by the assembler is a binary file.

Finally, the linker is responsible for combining the sections from each binary object file, resolving symbol references, and producing the final output, whether an executable or library. The exact layout of the output can be controlled by a linker script, which, each section, defines the ordering, offsets, and virtual memory addresses.

While these tools are used time source code is built into an executable or library, there are many other pieces of the toolchain. Some tools for inspection of object files, such as nm and objdump, which display the information encoded in the object file in a human-readable form. Other tools allow for the modification of object files, such as strip and objcopy.

In Linux, there are three major toolchains: the GNU compiler toolchain (GCC), the Low Level Virtual Machine toolchain (LLVM), and the Intel® C and C++ Toolchains (ICC).

GCC is the most common toolchain, without a doubt, consisting of projects including creating and modifying binary objects, the GNU compiler collection, which provides the compiler and frontends for multiple programming languages, the GNU debugger , as well as other build tools, such as GCC autotools, and GNU Make. In fact, many open source projects, such as the Linux kernel, rely on many GCC-specific behaviors and extensions, that most of the other toolchains strive to maintain at least some level of compatibility with.

Another common toolchain present on Linux is LLVM. While a younger project than GCC, LLVM has been progressing rapidly and has attracted attention for its modular design and static analysis capabilities.
