
Depending on the testing infrastructure of the codebase, this step can be as simple or as complex as required. Some codebases maintain a significant number of unit tests for ensuring correctness. In this case, depending on the test coverage and level of detail, it may be enough to leverage the existing tests. Other codebases do not have elaborate testing practices, so it may be necessary to write custom tests. When in doubt, the author recommends always overtesting, and perhaps being overly cautious, to not being cautious and potentially introducing functionality or, or even worse, security bugs.

One advantage of the setup described in Section 4.4 is that the conditions for designing reproducible performance experiments, such as isolating the code of interest, removing unnecessary dependencies, and having both versions together, yields itself well to functionality testing.

What the author prefers to do, if possible, is write two programs when creating the first program evaluates the performance while the second program evaluates the current correctness. Once these programs have been written, both performance and correctness can be checked by simply running each program, and regressions with correctness can hopefully be found quickly.

In order to ensure that both the testing and performance program are leveraging exactly the same code, the author recommends the implementations in separate source files, which are built into separate object files. Each of the previously mentioned two programs uses the symbols exported within each implementation's object file.

## 4.9 STEP B: PERFORMANCE REGRESSION TESTING

What was once problematic become problematic again. In order to recognize this, the early experiment should be run periodically to ensure that the performance doesn't regress back to where it was before the performance work was conducted. This parallels unit testing, where a bug is discovered, it should be added to the test suite to ensure that the functionality never regresses.

Another advantage of lower performance tests, such as the reproducible experiment from Section 4.4, is how well they complement higher performance tests. The higher level tests function as the canary in the coal mine, detecting performance regressions, while the lower level tests help isolate aspect of the code registered.

## 5.1 CHOOSING A METRIC

In Chapter 4, the importance of measurement was highlighted throughout the workflow. In the early stages, measures such as defining the problem, the focus rests on choosing the proper measure of performance. These measures are referred to as metrics.

Many different metrics exist, but there are two popular categories for performance metrics, either metrics that measure the cost of performing an operation or metrics that measure how often that operation occur during a given interval. In the first category, when measuring time, are often referred to as measuring latency. In the second category they are often referred to as measuring throughput.

To illustrate this point, consider two metrics for graphics rendering performance, time and frame rate. Since the time metric measures the cost, in time, of performing one operation, rendering a frame, it would fall into the first category. Since the frame rate, measured in frames per second, how many operations, frame renders, can occur for a given interval, one second, it would fall into the second.

When selecting a metric, it is important to choose a metric at an appropriate level of detail, which is dictated by the component being measured. For example, when comparing the performance of two algorithms for a CPU pipeline, clock cycles is an appropriate level of detail. The other hand, when comparing graphics rendering performance, clock cycles would probably be too low-level of a detail.

All metrics fall into one of three categories in terms of their interpretation, higher is better (HIB), lower is better (LIB), or nominal is better (NIB). As the reader might expect, when comparing two measurements for an HIB metric, the higher value is the better performing. HIB and LIB metrics are far more common than NIB metrics, which neither too high of a value nor low of a value is ideal.

## 5.2 DEALING WITH EXTERNAL VARIABLES

As mentioned in Section 4.4, it is important when benchmarking to reduce exposure to external variables that can impact performance. When designing an experiment, there are two types of external variables to consider, the controllable and the uncontrollable.

Controllable external variables are simply variables whose effects can be completely mitigated, and thus won't affect performance measurements.
