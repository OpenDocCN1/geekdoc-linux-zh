For example, rather than worrying about specifying the exact sampling interval, selecting the proper sampling interval for an advanced-hotspots analysis on an application that takes 5 min to run is as simple as specifying amplxe-cl -collect advanced-hotspots -target-duration=short.

The default data collection configuration only monitors the process given on the command-line. For some cases, this is acceptable, but for others a more global view of the system is required. In this case, the analyze-system argument expands data collection to every process on the system. This argument can be combined with a not executable, like sleep(1), in order to ascertain which processes on the system are consuming CPU time. Additionally, VTune supports a -duration=nsec argument that essentially does the same thing. In other words, amplxe-cl-collect bandwidth-analyze-system sleep 15 is essentially the same as amplxe-cl-collect bandwidth-analyze-system -duration 15.

The -call-stack-mode argument filters functions should appear in the stack traces. There are three valid values for mode. The first mode, user-only, only records functions present within the profiled execution. As a result, kernel functions do not appear in the trace. This is the default mode. The second mode, user-plus-one, records all of the functions that would be recorded in user-only mode, but also kernel functions directly invoked by the application. As a result, the internal kernel stack invokes the kernel, but filters out any of the internal kernel call chains. The third mode, all, records all functions, both within the application and the kernel.

Additionally, inline functions can be included within the call stack via the -inline-mode-on, or excluded via -inline-mode-off, command line argument.

By default, all data collection is performed on the local system; however, VTune supports data collection over the SSH and ADB (Android Debug Bridge) protocols. For this type of writing, the ADB protocol is only supported in the version of VTune provided with Intel® System Studio. With remote data collection, the collect action will be specified on the host system, and then the results will be copied back to the host system for local analysis.

In remote data collection to work, the data collection kernel modules that described in Section 7.1 must be installed and enabled on the remote system. When profiling a remote embedded device, the collect drivers on the host system, and add them to the system image that will be provisioned on the device. Additionally, in order to fit within size constraints, it is possible to skip the installation of the graphical interface tools and libraries. Within the VTune tarball, there is a directory named CLI_Install. This directory contains the scripts and files required for a manual installation, consisting of only the command-line tools and data collection drivers. These files can either be installed directly into the system image for the remote device before provisioning, or physically copied onto the remote device and installed manually.
