### 8.2.4 PER TIMEART

Perf timechart is a tool to graphically describe the interactions on the system. Interactions include those between the processes, cores, and sleep states. Timechart commands are multiplexed through the perf timechart command. First, events are collected using the record command, which takes a command to run, similar to perf record. Next, perf timechart is run without any arguments. This generates a SVG timeline, named output.svg, of system events. That is,

```
$ perf timechart record <command>
$ perf timechart
```

For example, running perf timechart on a gzip compression workload:

```
$ perf timechart gzip -c -6 /dev/shm/linux-31.5.tar /dev/null
[ perf record: Woken up 3 times to write data ]
[ perf record: Captured and wrote 0.883 MB perf.data (-38600 samples) ]
$ perfchart
```

Written 16.2 seconds of trace to output.svg

The output for this example can be seen in Figure 8.4.

The advantage of using a vector image format is the ability to provide scalable detail. Viewing the graph at different sizes, is, zooming in and out, shows different levels of detail. For instance, zooming on the CPU bars shows different color bars representing the transitions in CPU state, as the idle state. In properly utilize the zoomable levels of detail, make sure to view the SVG in an SVG editor or viewer, as inkscape, and not one that converts the vector image to a bitmap for viewing.

The downside to the zoomable detail is the size of both the file and timeline. In order to keep the results manageable, the author recommends avoiding the use of timechart on running processes.

The timeline highlights the interactions between various processes. At the top of the graph is a series of bars representing CPU state. At a high level of detail, these bars show what the CPU is doing at that moment in time. These include Running, Idle, Deeper Idle, Deep Sleep, Waiting for CPU, and Blocked on IO. Increasing the level of detail, is, zooming into the image, reveals more information about the state. This is shown in Figure 8.5. Below the CPU state are bars representing processes on the system at the given time. Similar to the CPU bars, these bars also show the individual process state with the same color-coded categories.

Ftrace is a debugging infrastructure within the Linux kernel that exposes the kernel's internal behavior. This data allows for the analyst to gain insights into what paths are being executed, as well as helping to isolate which kernel conditions are contributing to performance issues. Ftrace is an abbreviation of “function tracer”, yet it is capable of monitoring more than just function calls. Ftrace can also monitor static and dynamic tracepoints within the kernel, referred to as events. Static tracepoints are predefined events, created by the various subsystems, monitoring the occurrence of interesting events. By tracing these events, developers can better understand how their code interacts with the kernel, and subsequently the hardware.

For example, at the time of this writing, the Intel® i915 graphics drivers expose thirty static tracers. Most focus on recording the operations on the i915 GEM memory objects, such as i915_gem_object_create, i915_gem_object_evict, and i915_gem_object_destroy. The other i915 tracers focus on recording when the driver updates registers, i915_reg_rw, or important rendering events, such as i915_flip_request and i915_flip_complete.

Aside from these static tracepoints, ftrace also supports dynamic tracepoints. Dynamic tracepoints allow for custom tracepoints to be inserted almost anywhere at runtime. In order to accomplish this, tracepoints are not defined as high level events, but instead as memory offsets from exported kernel symbols. Additionally, the state at each dynamic tracepoint can be recorded by specifying a list of register names, memory labels, and stack offsets for the relevant data at the tracepoint location. Because of this, utilizing dynamic tracepoints requires at least some basic knowledge about the code which is being traced.

Whereas the performance tools discussed in Chapters 7 and 8, Intel® VTune Amplifier and perf utilize statistical sampling in order to attribute events to their relevant hotspots, trace instruments log the pertinent information when an event occurs. The Linux kernel trace infrastructure is optimized such that tracepoints, even though compiled into the kernel, have very low overhead, typically just a branch, in the case where they are disabled at runtime. This contributes greatly to the usefulness of glace, because this low overhead encourages Linux tracing to enable tracepoints within their default kernel configurations. Otherwise, significant tracepoint overhead, with the tracepoint disabled, would delegate them to use only debug kernels.

At the time of this writing, common Linux distributions, such as Android, Fedora, and Red Hat Enterprise Linux, enable tracing infrastructure in their default kernel configurations. The main kernel configuration required for it is CONFIG_TRACE. Other configuration options provide fine-grained control over what tracing functionality is available. Options include CONFIG_FUNCTION_TRACER, CONFIG_FUNCTION_GRAPH_TRACER, CONFIG_STACK_TRACER, CONFIG_FTRACE_SYSCALLS, and so on. For example, checking the default kernel configuration for x86_64 on Fedora 20:

```
$ grep CONFIG_TRACE /boot/config-uname -r'
CONFIG_TRACE=y
CONFIG_FTRACE_SYSCALLS=y
CONFIG_FTRACE_COUNT_RECORD=y
# CONFIG_FTRACE_STARTUP_TEST is not set
$ grep CONFIG_FUNCTION /boot/config-uname -r'
CONFIG_FUNCTION_TRACER=y
CONFIG_FUNCTION_GRAPH_TRACER=y
CONFIG_FUNCTION_PROFILER=y
```

## 9.1 DEGFS

The ftrace API is exposed through the debugfs memory-backed file system. As a result, unlike the other performance tools discussed in this book, all of the functionality of ftrace can be accessed without any dedicated tools. Instead, all operations, such as selecting which data to report, starting and stopping data collection, and viewing results, can be accomplished with the basic utilities, such as cat(1) and echo(1).
