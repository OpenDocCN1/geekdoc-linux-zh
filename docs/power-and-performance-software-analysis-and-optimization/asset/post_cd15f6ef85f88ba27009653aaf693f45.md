The second technique, using the mmap(2) system call, allows an application to map files or anonymous pages into the process's address space. This then returns a pointer to the beginning of the file's memory address, allowing for the application to manipulate it, like would incur any data in memory. Now that our microbenchmark has accounted for variance in items 1 through 4, it's time to look controllable sources of variance during the actual rendering measurement. Variance can be introduced by CPU power-saving features, such as P and C states, as well as some features designed to improve CPU performance, for example, Intel® Turbo Boost and Intel® Hyper-Threading Technology. Often these can be temporarily disabled in the BIOS. The author does not recommend disabling them for any longer than the test duration.

The variance introduced via P states and Intel Turbo Boost from the instance, of varying clock frequencies between measurement runs. For instance, the clock speed 800 MHz for one run, and 1.6 GHz for another. In the deeper C states, such as C6, the caches are powered down and thus invalidated, previously warm cache to turn cold. If P states cannot be disabled, the Linux kernel's cpufreq scaling driver, CONFIG_CPU_FREQ, can be used in conjunction with the performance governor. This will keep the CPU frequency constant between tests.

Another source of variance is CPU migrations, where the process moves from executing on one processor to another, again leading to situations where the cache suddenly changes. Migrations can be avoided by pinning the process to an individual CPU. This can be done either with the taskset command or programmatically via the sched_setaffinity system call.

Variance can also be introduced by running the benchmark on a system running other processes that are consuming significant amounts of resources. This type of system is often referred to as a noisy system. These other processes can lead to issues such as increased CPU migrations or thermal issues. One way to mitigate this issue is to boot the Linux kernel in user mode, by adding “single” to the kernel command-line, or by adding init=/path/to/shell to the kernel command-line. Once the system has booted to this minimal configuration, the benchmark can be without interference from other processes. If the benchmark requires other processes to run, such as a graphical application requiring an instance of Xorg running, those will need to be started manually.

## 5.2.2 UNCONTROLLABLE EXTERNAL VARIABLES

As mentioned in Section 4.4, it is important, in benchmarking, to expose external variables that can affect performance. However, when designing experiments, it is also necessary to recognize that many external factors are outside of our immediate control.

Since these factors cannot be mitigated, they must be accounted for in the design of the experiment. To accomplish this, the benchmark should be run multiple times, and then multiple data points should be analyzed to quantify the effects of the external variables on the scales.

The number of data points required to be collected, in order to provide an accurate measurement, depends on how significantly the benchmark is affected by the uncontrollable variables. As a general rule of thumb, measurements at a smaller level of granularity require more runs than at a higher granularity. When in doubt, the author errs on the side of collecting too many data points, which wastes time but provides a more accurate measurement, rather than too few, which saves time but provides a potentially misleading measurement.

As in statistics, the distinction is between calculations involving the population and involving samples. The population represents the entire set of elements, whereas samples involve a subset of the population. To calculate the population mean of a benchmark would require averaging the result of every single run ever, an infinite set. Due to the impossible nature of this task, a sampling of the population is used. Statistics are calculated from the sample set in order to reason about the properties of the population. The law of large numbers dictates that as the number of data points within the sample increases, the sample’s behavior approaches the behavior of the total population (Renze and Weisstein, 2014).

The most common statistic for summarizing performance samples is the mean. The population mean is denoted μ, whereas the sample mean is denoted as x. While most readers will be familiar with the algorithm for calculating the mean, in Equation 5.1 for completeness.

$$
\bar{D} = \frac{1}{n} \sum_{i=0}^{n-1} d_i \quad (5.1)
$$

However, it's important to understand that the sample mean only estimates the population mean, given the snapshot available. The variance is typically expressed as its root, the standard deviation. The reason for reporting the standard deviation, as opposed to the variance, is that the standard deviation is in the same units as the mean, making it easier to reason about (Miller and Miller, 1998). The population variance is denoted $\sigma^2$, whereas sample variance is denoted $S^2$.

$$
S^2 = \frac{1}{n-1} \sum_{i=0}^{n-1} (d_i - \bar{D})^2 \quad (5.2)
$$

As an aside, the reader may be wondering the dividend in Equation 5.2 The key insight is that the sample variance estimates the population variance. Estimators can be categorized as unbiased, that is the expected value of the statistic equals the estimated value, or biased. A statistic with the unbiased property is preferable to a statistic with the biased property (Miller and Miller, 1998). Because the sample mean, the population mean, is used for calculating the variance, dividing the sample variance by $n$ yields a biased estimator, whereas dividing by $n-1$ yields an unbiased estimator. For more information, see "Bessel's Correction" (Weissstein, 2014).

Note that in the variance formula, Equation 5.2, that each value subtracted by the mean makes the calculation susceptible to floating catastrophic cancellation, when a datum and the mean are very close. As the two close numbers are subtracted, the valid bits are cancelled out, leaving the number to be dominated by rounding errors (Goldberg, 1991). In order to prevent this, the author uses a different formula, first introduced by Welford(1962), which is less susceptible to catastrophic cancellation.
