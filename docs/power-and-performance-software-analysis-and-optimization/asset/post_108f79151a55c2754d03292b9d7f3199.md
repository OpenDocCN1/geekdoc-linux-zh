## 8.1.6 READING SAMPLING EVENTS

While counting events provides an estimate of how well a given snippet is performing, sampling events provides the ability to estimate which instructions are responsible for the generated events. Continuing the trivial microbenchmark example shown in Listing 8.2, consider if the measuring code were rewritten to determine which branches were mispredicted. Listing 8.3 is written to leverage the Intel® Last Branch Record (LBR), which stores information about the sampled branches.

On line 93, the perf_attr.sample_type field specifies what should be recorded for each event. In this situation, there are two items specified. The first, the instruction pointer, identifies which branch was mispredicted. The second, the LBR branch stack, lists the recently encountered branches and whether they were correctly predicted. Notice that in the function signature on line 29, the result structure corresponds to this field.

On line 105, the resulting event file descriptor is mapped into the virtual address space of the process. As events occur, the kernel writes the collected samples into these pages. Starting on line 45, the actual memory data is parsed. The first memory mapped page contains a header, which specifies information about the following event data. This data is defined by the perf_event_header structure. The following data, starting at the second memory mapped page, is a ring buffer. There are two fields in the header that contain the read and write offsets into it. The valid unread buffer starts at the data_tail field and the end of the valid buffer is defined by the data_head field. If the pages were writable, the new entries are marked as read, by the user space process, writing the new value to the data_tail field.

After accessing the data_tail, a memory barrier is utilized to ensure that the data written by the kernel to the memory mapped pages is visible to the user space process. This memory barrier is implemented on line 19, and utilizes the LFENCE instruction, that is, a load fence.

int _perf_event_open(struct perf_event_attr *attr, pid_t pid, int cpu,
    int group_fd, unsigned long flags)
{
    return syscall(__NR_perf_event_open, attr, pid, cpu, group_fd,
        flags);
}
static inline void rmb(void)
{
    _asm __volatile__ (
        "lfence"
        "memory"
    );
}
static void process_sample(struct {
    struct perf_event_header hdr;
    uint64_t ip, bnr;
    struct perf_event_branch_entry lbr[];
} *data) {
    size_t i;
    printf("SAMPLE %p\n", data->ip);
    printf("\t%%s PRIX64 :s Branches in Stack\n", data->bnr);
    for (i = 0; i < bnr; i++) {
        printf("\ttFrom: %s PRIX64 :%s\n", data->lbr[i].from);
        if (data->lbr[i].mispredicted) printf(" mispredicted");
        printf(" predicted\n", data->lbr[i].predicted);
    }
    printf("\n");

Looking at these results, a couple of different branches are highlighted. The results seem to corroborate the earlier hypothesis that the branch predictor was adept at predicting the microbenchmark workload. The branches with an instruction point around 0x400000 are clearly the user application's branches, which addresses such as 0xffffff812e are clearly branches in kernel code. Notice that on line 97 of Listing 8.3, perf_attr.exclude_kernel is set. As a result, even if one of the kernel branches was mispredicted, it would not appear in the sample data. At the time, the LBR records all branches, which is why both user and kernel space addresses appear in the branch stack.
