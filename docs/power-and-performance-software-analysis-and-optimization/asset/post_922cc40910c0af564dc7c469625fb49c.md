If the return value of the function is an integer, it is passed between the two functions in the EAS register. The register used for returning a floating point value depends on the architecture. Because decl x86 was established before SIMD was ubiquitously available, floating point values are returned in sr(0), that is, the top of the x87 floating point stack. On x86_64, floating point values are returned in the XMM0 register, as x86_64 requires the presence of SSE2.

Note that the 32-bit ABI requires floating point values to be returned at the top of the x87 stack, for some small functions, consisting of only one or two SIMD instructions, the cost of translating from x87 to SSE and back may outweigh any performance gains by utilizing SSE. When in doubt, measure.

For both x86 and x86_64, the caller of the function is responsible for cleaning up the stack after the function has returned. This is accomplished by incrementing the stack pointer off elements that were pushed onto the stack. The x86 ABI requires that the stack be word-aligned before a function call; however, GCC performs, and elects, a 16-byte stack alignment (Whaley, 2008). The x86_64 ABI requires that the stack be aligned 16-bytes to a function call, which is, excluding the instruction pointer pushed onto the stack by the CALL instruction.

Finally, the calling conventions also specify which registers must be preserved across function calls, and which registers are available as scratch registers. Understanding the purpose of the general purpose registers, will help plan movement in order to avoid a lot of unnecessary register copies. For the ABI, function invocation must preserve the EBP, EBX, EDI, ESI, and ESP registers. For the x86_64 ABI, function invocation must preserve the RBP, RBX, R12, R13, R14, and R15. In other words, before these registers can be used, their inherited values must be pushed onto the stack, and then popped back returning to the calling function. In order to save stack space and the extra instructions, putting data in scratch registers, which aren't required to be saved, over preserved registers, if possible.

## 12.3 CPU DISPATCH

As mentioned in Section 12.1, only the instructions in the software's hardware requirement can be enabled for the compiler to freely generate.

Sometimes, this is a non-issue, the software being compiled isn't intended to be distributed to other computers. A source-based Linux distribution, such as Gentoo, is a prime example. One why Gentoo users are able to achieve better performance than binary-based distributions is that their CFLAGS can be set to optimize for their exact configuration.

This comes as a stark contrast to software that is distributed in an already-compiled binary format. Whereas the Gentoo user's applications and libraries are compiled to target their individual system, a binary-based distribution, such as Fedora, has to compile its applications to run on the minimum hardware requirement.

One ramification of this is that, depending on how often the minimum hardware configurations are increased, many hardware resources, and subsequent performance opportunities, remain unexploited. This is especially concerning when the trend of introducing specialized instruction set extensions in order to improve performance.

To summarize the problem succinctly, the majority of users modern microarchitectures, such as the Second, Third, or Fourth Generation Intel Core™ processors, and yet running software that is essentially optimized for the fifteen year Intel® Pentium® Pro processor.

Obviously, this situation is less than optimal, but luckily there is a solution. The however, is a bit more complicated than just enabling a compiler far. Instead, it involves targeting specific areas that can benefit from use of newer instructions, providing multiple implementations for those areas, and ensuring that the proper implementations run on the proper architectures.

The tools and techniques introduced in Part 2 aid the first aspect, finding the areas that can benefit, and the rest of the chapters in Part 3 aid with the second aspect, creating the optimized implementations. The rest of this section will focus on the final aspect, ensuring that the proper implementations run on the proper architecture.

### 12.3.1 QUERYING CPU FEATURES

The first step in selecting the proper implementation of a function at runtime is to enumerate the processor's functionality. For the x86 architecture, this is accomplished with the CPUID instruction. Since the kernel also uses this information, a cached version is also available through procfs.

#### CPUID

CPUID, the CPU identification, allows the processor to query, at runtime, the processor's supported features. Due to the large amount of information available, information is cataloged into topical “leaves.” A leaf is selected by loading the corresponding leaf number into the EAX register before invoking CPUID. The basic leaf numbers start at 0, whereas the extended leaf numbers start at 0x80000000.

Since CPUID has been updated with new features since its introduction, when using a potentially unsupported leaf, it’s necessary to first verify that the leaf is supported. This is achieved by querying the first leaf, either zero for the basic information leaf or 0x80000000, and checking the value of the EAX register, which is set to the maximum supported leaf.

Some leaves have sub-leaves, which can be selected using the ECX register. The resulting data is returned in the EAX, EBX, ECX, and EDX registers. A comprehensive list of these leaves and their subsequent meanings can be found in Volume 2 of the Intel Developer's Manual, or under Instruction Set Reference for CPUID.

Consider Listing 12.1, which uses CPUID to check whether the processor supports the Intel® AVX extensions. Line 10 selects the Basic Information Leaf, as described in the SDM, contains other data, a bit to indicate whether AVX is supported by the processor. Line 11 executes CPUID, and thus loads the relevant information described in the leaf into EAX, EBX, ECX, and EDX registers. Line 12 masks out of all the bits except 28 into the appropriate register. Technically, if we were concerned about returning the exact bit, we would right-shift the bit into the least significant position; however this is unnecessary since C interprets zero as false, and all other values as true, and it is simply enough to return a non-zero value for the truth case.

```text
+   1 .text
2 # ECX Bit 28 : AVX extensions
3 #define AVX_MASK (1 << 28)
4 #
5 /* int cpu_has_avx(void); { */
6 global cpu_has_avx;
7 cpu_has_avx:
8 pushl %ebx # Preserve EBX on stack
9 mov $0x01, %eax # 01H = Basic Information Leaf
10 cpuid # Clobers EAX, EBX, ECX, and EDX
11 and $AVX_MASK, %ecx # Clears all bits except 28
12 mov %ecx, %eax # return AVX_MASK if supported, or O
13 popul %ebx # Restore EBX to original value
14 ret
```

Another consideration for using CPUID is its associated cost. CPUID is a serializing instruction that flushes the processor's execution pipeline, hence using in conjunction with RDTSC and RDCP to accurately measure clock cycles while accounting for instruction pipelining, as described in Section 5.3.1 of Chapter 5. As such, using CPUID frequently degrades performance, and this should be avoided in performance-sensitive contexts.

In Listing 12.1, we were only interested in checking for Intel AVX support; however, if we were interested in checking for multiple pieces of information, it would be best to perform as few times as necessary, as dictated by the information learned.
