Mesa provides the GLX interface, which allows for interaction between OpenGL and the X server. This example, allows OpenGL to render to an X window map, which can then be composed onto the screen. Using DRI to allow the X for routine drawing calls is referred to *direct rendering*. On the other hand, GLX is allowed to route OpenGL functions through the X server, which is referred to as *indirect rendering*, and is painfully slow. Indirect rendering is almost always a sign of a missing or misconfigured driver. This can be checked with `glxinfo` command:

```
$ glxinfo | grep direct
direct rendering: Yes
```

Mesa provides a series of debugging options, which are enabled via environmental variables. Some of the environmental variables are part of Mesa, and some part of the Intel® GPU driver in Mesa. For example, every time a frame is rendered, Mesa will print the FPS to `stdout` if the `LIBGL_SHOW_FPS` environmental variable is set.

The Intel driver checks for one or more comma-separated flags. Each flag corresponds to debug information, which will be printed to `stdout`. These flags allow for functionality like printing debug messages, disassembling shaders during compilation, printing statistics and so on (Bollet et al., 2014). Other flags, `perf`, `perfmon`, and `stats`, focus on detecting performance issues. The full list of environmental variables, and their meanings, can be found at http://www.mesa3.org/envars.html.

# 20: cairo and pixman

While the X server provides two-dimensional drawing commands, like XDrawline(3), these are avoided for performance reasons. Instead, the cairo library is used, which aside from X11 pixmaps via XLib and XCB, is also capable of drawing surfaces like PDF, PNG, PS, and SV.

One of the great features of the cairo library is that any application using it can automatically produce a trace of cairo. This trace, consisting only of the cairo workload, can be shared and replayed, without output. Additionally, the trace can be benchmarked different backends, such as rendering to an in-memory image or X pixmap. This allows developers to determine how their applications are using cairo, the cost of various operations, and easily reduce performance improvements. These traces are collected by using cairotrace. In order to collect enough information for benchmarking, use the `cairo-trace foo` will execute application foo and then store the trace in a file named `foo.<pid>.trace`. On the other hand, adding the `--profile` argument will also enable LZMA compression, so the resulting trace will be named `foo.<pid>.lma`.
