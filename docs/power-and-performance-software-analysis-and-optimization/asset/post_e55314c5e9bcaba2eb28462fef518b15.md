While it may be tempting to display a lot of extra data, this can often lead to confusion when others need to interpret the results. If the extra data is really useful, consider only printing it in a “verbose mode; and keeping the default output clean, simple, and straightforward. Remember, these experiments may be run by others, even when you're available for clarifications, and decisions might be influenced by the misinterpreted results, so always aim to keep things simple and straightforward.

Second, the experiment should be designed to allow others to easily reproduce the problem and validate progress. Ideally, this involves stripping out code and dependencies that are not relevant to the problem. For instance, if optimizing a client's search functionality, there is no point keeping the code to handle the IMAP protocol as part of the experiment. Pull out just the necessary search code and write a separate program to benchmark that algorithm on a fixed workload.

Third, the experiment should aim to reduce unnecessary variables that could affect performance or variance. Chapter 5 covers how to reduce common variables such as disk and network I/O costs, and other variables have the potential to increase variance and therefore lead to misleading results. Remember, the goal is to clearly show the performance in a reproducible way. By reducing variables, time is saved that would otherwise be spent debugging disparities between different hardware and software configurations.

The author imagines that some readers are wondering how these variables can be removed; after all, aren't they part of the code's performance characteristics? The answer to this question lies in what aspect of the system is being measured and optimized.

For example, a comparison of the throughput of two algorithms $A_\alpha$ and $A_\beta$ for a given CPU. Assuming that fetching data from memory, algorithm $A_\alpha$ achieves a throughput of 2500 MB/s, while algorithm $A_\beta$ achieves a throughput of 3500 MB/s. Now consider if both algorithms are required to fetch data from a hard drive that can provide data at least 150 MB/s.

For a comparison of which algorithm was capable of the higher throughput, the presence of the disk in the experiment would provide misleading results, as both algorithms would have a throughput of about 150 MB/s, and thus the I/O bottleneck would mask the performance difference. On the other hand, for a comparison of algorithm made the best usage of the limited throughput, the disk would be a needed part of the experiment.

For every test, each component under test needs to be placed in a reproducible state, or as close as possible. This needs to be a careful decision, one with planning on what reproducible state is, how to enter it, and an understanding of the potential impact on measuring the result of the tests.

Fourth, the experiment must accurately represent the actual performance characteristics. This is something to be especially critical when writing microbenchmarks, because subtle differences in cache state, branch prediction history, and so on, can drastically change performance characteristics. The best way to ensure this remains true is to periodically validate the accuracy of the models against the real codebase.

Fifth, at this stage, these workloads are selected for exercising the problematic algorithms. Ideally, these workloads should be as realistic as possible. However, as more and more software deals with personal information, care must be taken to avoid accidentally leaking sensitive data. Consider the ramifications if an email provider published a performance containing the private emails of its customers. The author imagines that upon reading this, some are thinking, “I'll remember not to publish that.” The flow in this logic is that the entire purpose of creating these kinds of experiments is to share them, and while you might remember, a colleague, years later, may not.

To avoid this entire problem, the author recommends studying real workloads, extracting the important parts, and substituting any sensitive content with synthetic content, taking care to ensure that the data is similar. Going back to the email workload example, perhaps create a bunch of emails from fictitious email addresses, replacing the English text message bodies with excerpts from Shakespeare.

Finally, while not an absolute requirement, the author also likes to keep a unit test with the benchmark to provide a method for verifying correctness. This is a convenient time to handle early testing, because the old and new implementations are both present, and thus they can be run on the same input and tested on identical outputs.

As mentioned earlier, performance work rarely exists in a vacuum. Interacting with others is even more important when working on, or interacting with, open source projects.

The main objective of this stage is to gather information about possible solutions. Whether that simply involves checking out the tree history, or chatting up the project developers is completely up to the reader's discretion. As such, when to communicate with the project upstream can occur at any phase. Some developers prefer submitting fully tested patches, and thus hold off any communications early, getting other developers involved in the effort. Projects typically have preferences themselves.

Regardless of the development method chosen, the author considers it crucial to contribute changes to the upstream project. This consideration doesn't stem from an ideological position on open-source software. In fact, the author is pragmatic about using the proper tools for the job, regardless of their development model. Instead, this suggestion comes from the realization that maintaining separate code, divergent from the project's official codebase, can quickly become a significant maintenance burden.

One of the powerful advantages of open source, although proprietary code is starting to move in this direction well, as is the rapid development model. As a result, maintaining a separate out-of-tree code branch will require keeping up with rapid development model, and will require a significant investment in frequently rebasing the code, handling conflicts that are introduced by other patches, and performing separate testing. The consequences of not fulfilling this investment is bit rot, leading to code abandonment.

On the other hand, patches integrated upstream benefit from all the testing of the developers and other users, as well as any further improvements made by the community. Any future patches that introduce conflicts with the upstream code would be a regression, and the burden of resolving them would lie with the author of the offending patch, rather than with the reader's. While upstreaming may seem to be more work, it's an up-front cost that definitely saves time and effort the rest of the long run.

While every open source project runs differently, with its own preferences, the rest of some projects provides some hints for getting results.

### 4.5.1 WHO

Consider the analogy of open source project releases to a river: The "source" of the river, that is, its original project. This includes the project's developers, who write the actual code, and produce releases. These releases "flow" down the river, being consumed and modified by each interested party before making their way to the "mouth" of the river, the end user. At any point in the river, upstream refers to any point closer to the "source", while downstream refers to any point closer to the "mouth".

The majority of open source code consumed by the end user doesn't come from the original project, but rather is the version packaged, in formats like RPM and ebuild, by their Linux distribution. Linux consumes projects from upstream and integrate them together to produce a cohesive deliverable, which flows downstream.

As a result of these modifications, the same version of a project on two distributions might be drastically different. Things become even more complicated, because some distributions, notably enterprise distributions, backport features and bugfixes in older stable releases, making release numbers potentially misleading.

Due to all, it is important, when attempting to reach out to a project, to determine the proper community to contact. Typically, the first step is to determine whether the project is reproducible with the original project release, that is, checking at the "source" of the river. If so, the project would be the correct path to contact. If not, further investigation is required into where the offending was introduced. This process is simply a matter of working downstream until finding the first codebase reproduces the problem.
