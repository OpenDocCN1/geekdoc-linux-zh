Unfortunately, compiling intrinsics with GCC can be somewhat annoying. This sterns from the fact that certain instruction sets can only be generated by the compiler when they are explicitly enabled in CFLAGS. However, when the instruction sets are enabled in the CFLAGS, they are enabled to be generated *everywhere*, that is, there is no guarantee that all of the instructions will be protected by a *CPUID* check. For example, compiling Intel AVX2 without -mavx2 compiler flag will result in compilation failure.

In order to bypass this problem, intrinsic functions should be isolated to separate files. These files must only contain functions that are dispatched based on the sets of CPUID. This is the only way to guarantee that all instruction extensions are properly dispatched at runtime.

Each instruction set extension typically has its own header file. However, since the instruction sets build upon one another, the main top level headers functions are x86intrin.h, which is typically located in the include /usr/lib/gcc.

The functions that correspond to a specific instruction can be determined by the related instruction documentation in the Intel Software *Developer's Manual*, under the instruction reference. Each instruction supports a corresponding intrinsic function has a section Intel C/C++ Compiler Intrinsic Equivalents, which lists the intrinsic signature.

Intrinsics that support SIMD registers add new variable types for representing wider widths. For instance, __m128 represents a 128-bit SSE register, while __m128i represents a 128-bit SSE register packing integers.

As discussed in Chapter 1, the instruction pointer contains the address of the next instruction to be executed. After the current instruction is executed, the instruction pointer increments to the next instruction, and so on. A branch introduces a deviation from this incremental behavior. Instead of incrementing to the next instruction, the branching instruction loads the instruction pointer to the address of an instruction at a different code.

Every branch can be classified as either conditional or unconditional. As the names imply, a conditional branch may or not change the instruction flow, while an unconditional branch will always change the flow. Most tend to associate the concept of branching with the first category, conditional branches, since these are the most visible forms. This kind of branch corresponds to the conditional and looping constructs exposed by programming languages, such as if or for statements. The other kind of branch, an unconditional branch, corresponds to control flows, such as calling or returning from a function.
