In an ideal world, all data could be stored in the fastest memory available to the system, providing uniform performance to all segments of data. Unfortunately, currently isn't feasible, forcing the developer to make tradeoffs with which data elements are prioritized for faster access. Giving preference to one chunk of data comes with the opportunity cost of potentially having given preference to a different data block.

Section 1.1 in Chapter introduced the fundamentals of a tiered storage hierarchy. This hierarchy is organized such that each level is faster, but more expensive and less dense, the level below it. This concept is illustrated in Figure 14.1.

If data are uniformly distributed, the probability of a data access to every address or block was equal, then performance would suffer immensely. Luckily, the principle of temporal data locality observes that previously accessed data is likely to be accessed soon after. Leveraging this observation, which is not a law, it is possible to improve performance by caching recently used data from a slower medium in a faster medium.

The effectiveness of such a cache is typically measured by the percentage of cache hits. A cache hit is a data access that was satisfied by the cache. A cache miss is a data access that was not satisfied from the cache, and therefore had to access one or more tiers of storage.

While this chapter primarily focuses on a particular caching layer, the CPU cache implemented in hardware, caching occurs throughout the storage hierarchy, in both hardware and software. For example, the Linux kernel will prefetch the contents of a file from a disk drive, placing the data into memory pages. These memory pages are then put into the kernel's page cache, when an application requests them, they are immediately available. For more information on this feature, read the related documentation for the `readahead(2)` system call, which allows the developer to request this behavior.

When optimizing an application that is suffering from high latency accesses, consider adding cache in a higher tier of storage. Analyzing the data access patterns provides insight into whether a cache can improve performance. So, the next step involves selecting algorithms for determining what data is stored in the cache, how low entries are kept, and the search algorithm for finding entries.

# 14.1 PROCESSOR CACHE ORGANIZATION

The overarching storage hierarchy can also be seen in the organization of the processor cache. The cache is divided into multiple levels, with the highest tier providing the fastest access and the smallest density and with the lowest tier providing the slowest access and the largest density. The lowest cache tier the processor supports is referred to as the Last Level Cache (LLC). A miss results in access to physical memory. The number of cache levels and their capacities depends not only on the microarchitecture, but also on the specific processor model.

# 14.1 Processor cache organization 253

The highest tier is the Level 1 (L1) cache. Originally, this cache was introduced in the 80486 as a unified cache, meaning that it stored instructions and data. Starting with the P6 microarchitecture, there are two separate L1 caches, one dedicated to storing instructions and one dedicated to data. A cache that only stores instructions is referred to as an icache. Conversely, a cache that only stores data is referred to as a dache. The P6 microarchitecture also added a Level 2 (L2) cache. Both L1 and the L2 caches are duplicated per-core, and shared between the core's Hyper-Threads. On the other hand, the unified Level 3 (L3) cache is an unresource, i.e., it is shared by all of the processor's cores.

When the execution unit needs a load of memory, the L1 cache is searched. In the case where the needed memory is found, it is simply copied from the cache. On the other hand, in case of a L1 cache miss, the L2 is searched next, and so on. This process repeats until data is found in one of the caches, or a cache miss in the LLC forces the memory request to access physical memory. In the case where the data request miss was satisfied from a different cache level, the data is loaded into the L1 first, and is provided to the processor.

At this point, the reader may be wondering how such large caches are searched so quickly. An exhaustive iterative search wouldn't be capable of meeting the performance requirements needed from the cache. In order to answer this question, the internal organization of cache must be explained.

Architecture uses a-way associative cache. A set is a block of memory, comprised of a fixed size memory chunks, each referred to as a cache line, form the basic building block of the cache. The number of ways indicates how many cache lines are in each set (Gerber et al., 2006).

To reduce the number of entries, the architecture uses set-associative mapping. A memory address is mapped to a specific set in the cache, and the data can be stored in any of the ways within that set. This reduces the search space compared to a fully associative cache, while providing more flexibility than a direct-mapped cache.

The number of ways in a set significantly impacts the performance of the cache. A higher number of ways can reduce the miss rate, but it also increases the complexity and power consumption of the cache hardware. Most processors use a balance of the number of ways to optimize performance and efficiency.

### 14.1.1 CACHE LINES

Fundamentally, the concept of cache line represents the smallest unit of data that can be transferred between main memory and the cache. When the processor requests a single byte, it actually fetches the entire cache line containing that byte. This takes advantage of spatial locality, the principle that data near the recently accessed data is likely to be accessed soon.

The size of a cache line is typically 64 bytes on modern processors. If a data structure spans across two cache lines, the processor must perform two separate fetches to retrieve the data, which can impact performance. Therefore, it is often beneficial to align data structures so that they fit within a single cache line.

# 14.2 QUERYING CACHE TOPOLOGY

The configuration of the cache, including the number of cache levels, size of each level, number of sets, number of ways, and cache line size, can change. Some of these aspects, like the cache line, lock fluidity, while other aspects, such as the size of each cache level, change per processor model. Because of this, when writing software that optimizes based on these factors, it makes sense to automatically detect these values at runtime rather than hard-coding them.
