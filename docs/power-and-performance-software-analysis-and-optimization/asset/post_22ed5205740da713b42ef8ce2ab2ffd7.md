Additionally, there are two status registers, the instruction pointer and the flags register.

The instruction pointer, IP, is often referred to as the program counter. This register contains the address of the next instruction to be executed. Until 64-bit mode, the instruction pointer was not directly accessible to the programmer, that is, it wasn't possible to access it the the other general purposes. Despite this, the instruction pointer was indirectly accessible. Whereas the instruction pointer could not be modified by a MOV instruction, it could be modified by any instruction that alters the program flow, such as the CALL or JMP instructions.

Reading the contents of the instruction pointer was also possible by taking advantage of how x86 handles function calls. Transfer from one function to another occurs through the CALL and RET instructions. The CALL preserves the current value of the instruction pointer, pushing it onto the stack in order to support nested function calls, and then loads the instruction pointer with the new address, provided as an operand to the instruction. This value on stack is referred to as the return address. Whenever the function finishes executing, the RET instruction pops the address off the stack and restores it into the instruction pointer, thus transferring back to the function that initiated the function call. Leveraging this, the programmer can create a special function that would simply copy the return value of the stack, load it into one of registers, and then return. For example, when using Position-Independent-Code (PIC), which is discussed in Chapter 12, the compiler will automatically add functions that use this technique to obtain the instruction pointer. These functions are called _x86.get_pc_thunk_bx(), _x86.get_pc_thunk_dx(), and so on, depending on which register instruction pointer is loaded.

The second status register, the EFLAGS register, is comprised of 1-bit status and control flags. These bits are set by various instructions, typically arithmetic or logic instructions, to signal certain conditions. These condition flags can then be checked in order to make decisions. For a list of the flags modified by each instruction, see the Intel SDM. The 8086 defines the following status and control bits in EFLAGS:

# 1.1.3 INSTRUCTIONS

Continuing the scenario described in the introductory section, and deasserted, the processor initializes the program registers when the #RESET pin is asserted and deasserted, their predefined values. This includes the predefined value of the instruction pointer, providing the BUI the first fetch to decode and for the execution unit.

This location is always the last 16 bytes in the physical address space. For a 16-bit processor with 20-bit physical addresses, this is 0xFFFF0. This provides enough room for a JMP to the BIOS's real initialization code.

To understand the reasoning behind this, consider that the first instructions executed, are responsible for initializing the system and preparing a standard execution environment before booting the operating system, belong to the BIOS. The BIOS is mapped into the physical address space, is stored in a ROM, located on the motherboard, connected with a Low Pin Count (LPC) bus. This ROM is mapped to the very top of the physical address space, such that the last byte of the ROM is the very top. Therefore, differently ROMs have different starting addresses within memory. For example, a 1-KB ROM would start at 0FFFF – 0xFF00 + 1 = 0xFFC00, whereas a 4-KB ROM would start at 0FFFF – 0xF000 + 1 = 0xFF000. These first instructions executed, the last bytes of the BIOS ROM, are the only others guaranteed to contain valid code, and it belongs to the BIOS; it is guaranteed to know where in physical memory the rest of the initialization code resides.

From this point, the processor continues its loop of fetching new instructions, decoding these instructions, and executing those instructions. Each instruction defines an operation that transitions the state machine from one to another. Each individual instruction is comprised of one or more forms, that is, various encodings handling different operand types. An operand is simply a parameter for the instruction, defining what aspect of the state should be acted upon.

The 8086 has instructions comprising of about one hundred unique instructions, not accounting for different forms. These instructions can be divided into five logical groupings. For a full reference of the available instructions, along their meanings and operands, see the Intel SDM.

# Data movement

The first group contains instructions that move data from one operand to another. This includes instructions like MOV, which can move data from one operand to another, PUSH and POP, which pushes an operand onto the stack or pops the top of the stack into the operand, and XCHG, which atomically swaps the contents of two operands.

# Integer arithmetic

The second group contains instructions that perform integer arithmetic. This includes instructions that perform the standard familiar arithmetic operations, such as ADD, SUB, MUL, and DIV.

Additionally, x86 supports instructions for performing these operations with "carry" or "borrow." This is used for implementing these operations over an arbitrarily large number of bytes. In the case of a carry, the bit in EFLAGS is flagged for the next instruction to interpret. For example, add ADC with carry, instruction uses this bit to determine whether the result should be incremented by one, to borrow the bit carried from the previous ADC operation.

Typically each of these instructions sets the relevant status bits in the EFLAGS register. This often obviates the need to use an explicit comparison instruction for some checks, like checks for zero, or less than zero. Instead, the flag can simply be reused from the arithmetic operation.
