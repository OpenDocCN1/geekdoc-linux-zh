Each of the entries in the `dynamic` section marked DT_NEEDED are loaded by the dynamic linker and searched for the necessary symbols. At link time, the linker creates a .hash section, which consists of a hash table of the symbols exported by the current file. This hash table is used to accelerate the search process at runtime.

Unlike objects, which are always loaded at a fixed address known as build time, shared objects can be loaded at any address. Otherwise, it would be possible for conflicts where two objects expect to be loaded at the same address.

In order to handle this, the symbols in shared objects are `relocatable`. The ELF format supports many types of relocations; a description of each kind can be found within the ELF specification. While the programmer isn't required to manually handle these relocations, it is important to understand what happens behind the scenes, because it impacts performance and security.

When relocating code, the linker uses a dummy base address, typically zero, with each symbol value set to the appropriate offset from the base address of the symbol's section. Each one of these addresses is loaded by the linker, which creates an entry in that's section relocation section. This entry contains the relocation type, which determines how the address needs to be updated with the real address. The location of the code to be updated is offset by `section_name` or `rel.section_name`, where `section_name` is the section containing that relocation.

At runtime, the dynamic linker iterates the relocation section. For each entry, the real address is calculated and corresponding code is patched with the resulting address. This has three major ramifications. First, a significant number of relocations can hurt load performance. Second, the code pages in memory must be writable, as the dynamic linker needs to update them with the relocations, and security is reduced. Third, the code pages are modified by the relocations, they can't be shared between processes, since each process will have different addresses, and this leads to increased memory usage.

Obviously binding a large number of symbols before execution begins can be devastating to the application's load time. Even worse, there is no guarantee that all of these resolved symbols will actually be needed during execution.
