
## 9.1 DebugFS

The first step in utilizing the API is to mount the debugfs file system. Traditionally, Linux distributions automatically mount debugfs under sysfs, at /sys/kernel/debug. Checking whether debugfs is already mounted is simple as querying the list of mounted file systems, either with the mount(1) command, or by looking at /proc/mounts or /etc/mtab. For example:

```
$ mount | grep debug
debugs on /sys/kernel/debug type debugfs (rw,relative)
$ grep debugfs /proc/mounts
$ debugfs /sys/kernel/debug debugfs rw.relative 0 0
$ grep debugfs /etc/mtab
$ debugfs /sys/kernel/debug debugfs rw.relative 0 0
```

Additionally, the file system can be manually mounted with:
`$ mount -t debugfs nodev /mnt/location`

Once the file system is mounted, a `tracing/` subdirectory is available. The directory holds all of the files for controlling trace. Some files are read-only, designed for extracting information from the API about the current configuration or results. Other files allow both reading and writing, where a read queries an option's current value, whereas a write modifies that value. Note: that debugfs provides visibility into the kernel, accessing this directory, and by utilizing the tool, requires root.

```
$pwd
$ /sys/kernel/debug/tracing
$ ls
available_events  max_graph_depth  options  stack_trace  buffer_size_kb  print_formats  current_trace  enabled  instances  total_size_kb  free_buffer_size  snapshot_thresh  kprobe_events  kprobe_profile
```

### 9.1.1 TRACERS

A tracer determines what information is collected when tracing is enabled. The list of tracers enabled in the kernel can be obtained by reading the contents of available_tracer file. If the desired tracer is missing from this list, it wasn't compiled into the kernel. In this case, rebuild the kernel after adding the relevant option.

A Tracer is selected by writing its name into the current_tracer file. This file is also writable, and readable, to get the currently selected tracer. For example:

```
# cat available_tracer
function_graph nop
# cat current_tracer
function
# echo function > current_tracer
```

One tracer has been selected, data collection can now begin. The file tracing_on controls whether the results of the tracer are being recorded. Note that this is not the same as disabling the tracers, but merely their overhead. The results of data collection are available in trace and trace_pipe files. The trace file is used for processing all the data at once, whereas trace_pipe is used for processing the data piecemeal. As a result, the end of the file is marked with EOF, whereas trace_pipe is not. More importantly, data read from trace_pipe is consumed and removed from the tracing ring buffer. On the other hand, read(2) to the trace file are destructive. In order to clear the contents of the trace file, perform a write operation, such as using echo(1), The contents don't matter.

### Available tracers

The tracing subsystem has been receiving a significant amount of attention recently. As a result, it tends to advance quickly, adding new features and tracepoints. Rather than trying to provide a comprehensive list of the available tracers and their usage, this section introduces a couple of the most commonly used. Despite this rapid change, the files exported through debugfs fall under the ABI. In order to avoid breaking user applications that depend on formatting, this content should not change.

### function and function_graph

The function and function_graph tracers record every function call that occurs in kernel space. Function calls from user space are omitted. For these tracers to be enabled, the kernel must be configured with CONFIG_FUNCTION_TRACER and CONFIG_FUNCTION_GRAPH, respectively. Listing illustrates the default output of the function tracer. Note that the author has removed extra lines to better fit the output within the page margin. Additionally, the output has been shortened from well over three thousand lines. The first lines of this trace consist of a header, providing an explanation of the fields. It also reports the number of entries present in the buffer. Moving beyond the header, the difference between these two numbers corresponds to the number of entries lost.

Whereas the function tracer only instruments function calls and reports each function caller and callee pair, the function_graph tracer instruments both calls and function events, allowing for more detailed reporting of the function call hierarchy. This difference is striking when comparing the function call fields between the two function tracers. Notice that these function calls are structured in an almost C-like format, with a function's direct and indirect calls nested within its braces.

Once again, the first few lines constitute a header, although the function_graph header is more abbreviated due to the simplicity of its fields. Notice that instead of absolute timestamps, time is expressed as a duration of each function. The total duration in a function, including all subcalls, is the line corresponding to the closing brace.
