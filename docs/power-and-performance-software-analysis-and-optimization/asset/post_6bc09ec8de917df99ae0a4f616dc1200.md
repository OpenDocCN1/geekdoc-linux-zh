## 5.3 TIMING

In order to write benchmarks, it is necessary to understand how to take accurate measurements. One of the most commonly taken measurements is that of time, that is, how long a snippet of code takes to execute a given workload. The process for measuring time seems like it should be fairly straightforward, computer timers are actually a fairly complex subject.

When using timers, or taking any other measurement, it is necessary to always be aware of the measurement resolution, that is, smallest measurable unit. For instance, if two algorithms are being measured, and the first algorithm runs for 1 ms and the second runs for 100ms, but the timer used for measurement only has a resolution in seconds, then both algorithms will be recorded as taking zero seconds and the significant differences between the two will be lost.

Another important aspect to consider is whether the timer is monotonically increasing. A monotonically increasing timer always returns a result that is greater than or equal to returned results, and thus ensures that the timer never moves backwards. A timer without this guarantee could yield misleading results. In the best case, the backwards movement would lead to an arithmetic underflow when comparing the second reading against the first, and thus the results would be obviously wrong. In the worst case, the backwards movement would be enough to not cause an underflow, but would still provide an inaccurate reading, and thus the results would be silently corrupted.

It is also important to determine whether the timer measures wall time or process time. The wall time measures the total time that has elapsed during measurement period. On the other hand, the process time only measures time accounted to the process being measured. For instance, if the execution of one process takes a total of 30 seconds, with 10 seconds of time spent with the core executing a different process, the wall time would be 30 seconds, and the per-process time would be 20 seconds.

### 5.3.1 CPU CYCLES

At the processor level, the CPU keeps track of time by counting the number of clock cycles. A cycle represents one iteration of the CPU core's loop for fetching, decoding, executing, and retiring instructions. Because the CPU is a pipeline, each of these phases occur concurrently. During one cycle, 16 words of instructions are fetched, instructions from the previous cycle's fetch are decoded, or continue decoding, instructions decoded from an earlier cycle are executed, or continue executing, and instructions from an even earlier cycle are retired. The frequency of a processor estimates the number of cycles that can occur at a frequency of 1.0 GHz, which is Hertz. For example, a processor that operates at a frequency of 1 GHz would perform one billion cycles per second.

The cycle count can be accessed either through the time-stamp counter via PMU events. This section focuses on the time-stamp counter. For more information on the PMU events, see Chapter 6.

The time-stamp (TSC) counter is a MSR, IA32_TIME_STAMP_COUNT_MSR, which holds the 64-bit number of clock cycles since the processor was booted. Originally, the TSC incremented at the actual CPU frequency, however on modern Intel processors the TSC is invariant. Unlike the other methods for accessing the cycle count, the TSC does increment while the processor is halted. The TSC is monotonically increasing, except in the case of 64-bit overflow.

Access to the TSC is provided via RDTSC and RDCP. Since the behavior for these instructions is for both 32 and 64-bit, the top 32 bits of the 64-bit counter are stored in the EDX, while the lower 32 bits are stored in the EAX register. The RDTSC instruction returns the contents of the current hardware thread's 32-bit IA32_TSC_AUX_MSR in the ECX register. Linux sets this MSR to the hardware logical id number, allowing for the code to detect CPU migrations.

Due to the out-of-order execution of modern CPU pipelines, it is necessary to verify that the TSC only counts the instructions that are being benchmarked. In order to accomplish this, it is necessary to add two serialization points into the pipeline. A serialization point, in the form of a serialization instruction, will ensure that all previous instructions have finished executing, and that all future instructions have not started execution.

The RDTSC instruction performs no serialization, while the RDENCE instruction verifies that all prior instructions have finished executing, but makes no guarantee about future instructions. In order to ensure accurate results, a fully serializing instruction, typically CPUID, is used. Listing 5.2 demonstrates two small inline functions for accessing the TSC, along with their serializing CPUID instructions on lines 8 and 26. Note that line 9 uses a regular RDTSC instruction, since it is protected by the prior CPUID, whereas line 23 uses RDCP instruction to ensure that the benchmarked code has finished execution before making the measurement. The final CPUID instruction on line 26 ensures that no later instructions begin before the TSC has been read.

Notice that since TSC is a MSR, and therefore duplicated per hardware, and increments at a fixed rate regardless of the core state, the cycle count corresponds to the wall time, not the process time.

```
#include <inttypes.h>
static inline uint64_t start_cycle(void) {
    unsigned int a, d;
    register unsigned __asm__ __volatile (
        "cpuid\n\t"
        "rdtsc\n\t"
        : "=a" (a), "=d" (d)
        :
        : "ebx", "ecx", "ecx"
    );
    return ((uint64_t)d << 32) | a;
}
static inline uint64_t stop_cycle(register unsigned high, register unsigned low) {
    register unsigned __asm__ __volatile (
        "rdtsc\n\t"
        "mov %%ax, %%[low]\n\t"
        "cpuid\n\t"
        : [high] "=r" (high), [low] "=r" (low)
        :
        : "eax", "ebx", "ecx"
    );
    return ((uint64_t)high << 32) | low;
}
```

### 5.3.2 CLOCK TIME AND UNIT

As mentioned previously, the processor has no concept of time outside of clock cycles. Therefore, all the interfaces for accessing time in the human units of time, are provided by the operating system, rather than the instruction set. The Linux kernel has a few different options for a clock timer.

Traditionally, the Linux kernel ticked, that is, it would program the hardware timer to generate an interrupt at a given frequency, representing one tick. Each of these interrupts would cause the kernel to pause the current user space program, perform some accounting, and then choose the next process to run. This would occur at an interval selected at time, via the CONFIG_HZ Kconfig option. The possible configuration options for x86 were 1000, 350, 250, and 100 Hz. For instance, a kernel configured with HZ=1000 would receive 1000 tick interrupts every second, limiting the resolution of the timers to 1 ms.
