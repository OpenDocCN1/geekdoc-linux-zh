# 11.3 PowerTOP

PowerTOP is a monitor, written by Arjan van de Ven, for measuring the system's behavior with regards to power consumption. This includes monitoring the number of processor wakeups, the P and C state residency, GPU state, and system settings. Additionally, PowerTOP is also capable of monitoring device power consumption through another power meter, RAPL, or software modeling. For its software modeling, PowerTOP records power consumption and utilization information over time, providing more accurate estimates as more results are collected. These collections are stored in /var/cache/powertop. By monitoring device power consumption for the system, PowerTOP can also estimate the cost of individual applications.

PowerTOP provides an interactive ncurses-based interface, as well as the ability to collect data and generate a report noninteractively. The noninteractive reports collect data for a predefined period of time, and then generate a report in either HTML or CSV format. By default the noninteractive mode will occur for 20 seconds and then produce a HTML report, in the file powertop.html. A custom period can be specified with the --time=parameter, which expects an integer representing the number of seconds for collection. A CSV report can be generated with the --csv=filename parameter, where filename represents the file for storing the report. Additionally, the HTML report file, powertop.html, can be similarly modified with the --html=filename parameter.

The ncurses interface is divided into five windows, each displaying a different metric. These windows are traversed with the Tab and Shift-Tab combinations. The contents of the current window can be shifted by the arrow keys. The data can be refreshed manually by pressing the "r" key. Finally, PowerTOP can be quit by pressing the Escape key.

## 11.3.1 OVERVIEW

In "Performance Is Power Efficiency" section of Introduction, the concept of "race to idle" was used as a technique for improving power consumption. This concept, bursting to complete work quickly, is only applicable if the work can be completed quickly. Longer running tasks, such as daemons, should be written to the processor to take advantage of these deep sleep states.

As described in "C states" section of Chapter 3, for the processor to enter deep sleep, it must be halted, and therefore not executing instances. Each C state has an entry and exit latency, it is the job of the intel_idle driver in the Linux kernel to request the deepest C state that meets the latency requirements again. When the kernel is kicked, only waking up when needed, it is crucial that user space applications are carefully aware about how they wake the system from slumber. PowerTOP reports these occurrences in order to allow the user to identify misbehaving applications that are impacting power consumption.

## 11.3.2 IDLE STATS

By monitoring the core and package residencies in the various idle states, it is possible to quantify how-efficient the software is allowing. Additionally, it can identify problems within the system's configuration. The lack of the ability to enter a deeper sleep state, that is, a residency of zero, can be indicative of a misbehaving driver. Consider that the integrated graphics hardware is present within the processor package, that is, its an uncore resource. Since all core and uncore resources within the associated idle state, which provides the largest power reductions, a misbehaving driver or incorrect configuration that doesn't allow the GPU to enter a RC6 state can drastically affect power and additionally affect the ability of the processor to utilize turbo modes.

It is important to note that just PowerTOP displays idle state does not mean the underlying hardware necessarily supports that. So a zero residency in the deepest sleep state does not necessarily indicate an issue.

11.2 shows an example of the idle state residencies for a Second Generation Intel® Core™ processor laptop. Notice the processor topology, starting from the left: one package, which depends on four cores, which in turn depend on eight hardware threads. Additionally, the GPU residencies can be found at the bottom of the window, which may require scrolling with arrow keys. Notice that the deepest package idle state has a nonzero residency, and each of the cores and the GPU have high residency percentages in the deepest available states. Additionally, take notice of the zero residency in the RC6p and RC6pp states. These residencies are not an error in the configuration, since RC6 support was introduced with the Third Generation Intel® Core™ processors and RC6pp was introduced after that.
