## 12.4.2 USING THE APPROPRIATE TYPES AND QUALIFIERS

As shown in Section 12.4.1, providing the proper hints to the compiler can aid in optimization. In many cases, these are handled by the compiler through types and their qualifiers.

### Signed versus unsigned

Types come in two flavors, signed and unsigned, as specified by the corresponding signed and unsigned qualifiers. If no qualifier is given, a signed type is assumed. As the reader is properly aware, signed types reserve a bit, the most significant, to store whether the value is positive or negative. Integers on int Architecture are stored in two's complement format. On the other hand, unsigned types do not reserve a sign bit, but are instead treated as positive, increasing the potential range of values that can be stored and also providing defined behavior in case of overflow and underflow. Adding these stronger constraints allows the compiler to optimize these types more aggressively in some situations.

### Const

The const qualifier informs the compiler that the type modified by the qualifier will not change. This actually serves two purposes, as it can enable additional optimizations as well as causing compiler errors if an attempt is made to modify a constant variable.

An important aspect of the const qualifier is that it can modify either a value or pointer. For instance, the const int type represents a signed integer value while the const char *const represents a constant pointer. On the other hand, a pointer that never changes, points to a character whose value never changes.

Marking strings as const can cause strings to move from the ELF.data section to the .rodata section. This also enables string merging, where two constant strings that overlap can be merged into one string. For instance, the strings const *str0="testing123" and const *str1="123". The second string, only requires changes: "2","3", and "0" the NULL sentinel. These four characters can be found as the last four characters in the first string, str0, and therefore only the first string needs to be stored, with second simply pointing at the last 4 bytes of the first. This size optimization can only occur when both strings are marked as const.

### Volatile

The volatile qualifier informs the compiler that the modified variable may be updated in ways the compiler doesn't have visibility into. The canonical example of this is a pointer to a memory mapped device, where the value may not be the same value read from that address. Without this qualifier, the compiler would incorrectly optimize away memory accesses due to its limited understanding of the situation.

The problem with the volatile qualifier is that it forces the compiler to disable every memory optimization. Fetched memory accesses can't be reused or cached, resulting in a significant degradation in performance. Only use this qualifier if it is absolutely necessary.

## 12.4.3 ALIGNMENT

On Intel Architecture, unaligned memory accesses are less significant than they used to be. Since memory accesses are satisfied by fetching cache lines, the only big penalty for an unaligned access is if it splits a cache line, resulting in two cache lines needing to be loaded, and then the relevant values fetched. For the most part, the majority of important alignments will be automatically by the compiler.

## 12.4.4 LOOP UNROLLING

Loop unrolling is a technique for attempting to minimize the cost of loop overhead, as branching on the termination condition and updating counter variables. This occurs by manually adding the necessary code for the loop to occur multiple times within the loop body. The potential for performance improvement comes from the reduced loop overhead, since less iterations are required to perform the same work, and also depending on the code, better pipelining.

While loop unrolling can be beneficial, excessive unrolling degrades performance. Because modern processors execute out-of-order in many loops unrolling effectively occurs in hardware, with better scheduling of resources can be performed at compile time. Additionally, the compiler may automatically perform loop unrolling.

Since loop unrolling is a tradeoff between code size and speed, the effectiveness of loop unrolling is highly dependent on the loop unrolling factor, that is, the number of times the loop is unrolled. As the factors increase, code size increases, leading to potential issues with the front end, such as icache misses. The only way to determine the best unrolling factor is through measurement.
