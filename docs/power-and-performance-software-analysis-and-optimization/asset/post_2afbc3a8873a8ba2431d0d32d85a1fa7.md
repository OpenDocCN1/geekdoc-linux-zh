
In many ways, programming the GPU is very similar to programming the CPU, although the instruction set and data state are different. The graphics hardware executes instructions stored in a ring buffer. Since there is only one ring buffer for the GPU, accessing elements within this buffer requires locking, making direct access from user space too expensive. Aside from entries that directly contain instructions, the ring buffer also contains pointer entries. These pointer entries reference a chunk of memory, known as a batchbuffer, that is comprised of GPU instructions. Upon encountering one of these pointer entries in the ring buffer, the GPU loads all the instructions contained within the batchbuffer, and then continues with the next entry in the ring buffer. In many ways, this flow mimics a function call, where the execution flow temporarily changes, and returns to its original context after execution. Unlike directly updating the ring buffer, a batchbuffer can be generated by the CPU without interrupting it. Batchbuffers are generated by user space applications and are then passed to the kernel's DRM infrastructure, which handles inserting them into the GPU buffer.

In order to facilitate this interaction between the graphics memory and processor memory, a new API for managing memory objects was created. API, known as the Graphics Execution Manager (GEM), provides an interface for synchronizing and destroying resources, including batchbuffers, as well as texture and vertex data. Similar to the DRM interface, the GEM API is exposed through a series of ioctl(2) calls performed on the relevant DRM device file (Packard, 2008).

Originally, the X server also required to set the display mode, which is the screen's resolution, color depth, and so on. As a result, the resolution at boot time and for virtual terminals was typically not the native screen resolution. This was remedied with Kernel Mode Setting (KMS) support, which moves the functionality for setting the display mode from the X server to the kernel. This is accomplished by reading the EDID information from the attached monitors and setting the display's resolution accurately.

## 10.1.3 HIGHER LEVEL SOFTWARE INFRASTRUCTURE

The higher level graphics stack is partitioned into a series of libraries and applications, such as the actual X server. Each of these provide a different set of functionalities, such as pixel management or the OpenGL implementation.

## 3D: Mesa

The OpenGL and EGL implementations are provided by the Mesa library. This library exposes the OpenGL API to user applications, and then translates those function calls into the appropriate GPU batchbuffers. Using libdrm, Mesa submits these instructions into the kernel for execution by the GPU. As a result, supported graphics hardware must provide a driver within Mesa. This driver is responsible for implementing a compiler that targets the GPU instruction set. Additionally, the GPU-specific kernel DRM driver must implement validation, to ensure that the instructions passed from user space to kernel space are valid.

Mesa provides the GLX interface, which allows for interaction between OpenGL and the X server. This example, allows OpenGL to render to an X window map, which can then be composed onto the screen. Using DRI to allow the X for routine drawing calls is referred to as *direct rendering*. On the other hand, GLX is allowed to route OpenGL functions through the X server, which is referred to as *indirect rendering*, and is painfully slow. Indirect rendering is almost always a sign of a missing or misconfigured driver. This can be checked with `glxinfo` command:

```
$ glxinfo | grep direct
direct rendering: Yes
```

Mesa provides a series of debugging options, which are enabled via environmental variables. Some of the environmental variables are part of Mesa, and some part of the Intel® GPU driver in Mesa. For example, every time a frame is rendered, Mesa will print the FPS to `stdout` if the `LIBGL_SHOW_FPS` environmental variable is set.

The Intel driver checks for one or more comma-separated flags. Each flag corresponds to debug information, which will be printed to `stdout`. These flags allow for functionality like printing debug messages, disassembling shaders during compilation, printing statistics and so on (Bollet et al., 2014). Other flags, `perf`, `perfmon`, and `stats`, focus on detecting performance issues. The full list of environmental variables, and their meanings, can be found at http://www.mesa.org/envars.html.

## 20: cairo and pixman

While the X server provides two-dimensional drawing commands, like XDrawline(3), these are avoided for performance reasons. Instead, the cairo library is used, which aside from X11 pixmaps via XLib and XCB, is also capable of drawing surfaces like PDF, PNG, PS, and SV.

One of the great features of the cairo library is that any application using it can automatically produce a trace of cairo. This trace, consisting only of the cairo workload, can be shared and replayed, without output. Additionally, the trace can be benchmarked different backends, such as rendering to an in-memory image or X pixmap. This allows developers to determine how their applications are using cairo, the cost of various operations, and easily reduce performance improvements. These traces are collected by using cairotrace. In order to collect enough information for benchmarking, use the `cairo-trace foo` will execute application foo and then store the trace in a file named `foo.<pid>.trace`. On the other hand, adding the `--profile` argument will also enable LZMA compression, so the resulting trace will be named `foo.<pid>.lma`. This trace file can then be replayed using the `cairo-perf-trace` command. Whereas this is typically available in the software repositories of the major Linux distributions, cairo-perf-trace command found in the cairo source tree, under the perf directory.

The Pixman library provides software implementations for various image and pixel operations, such as composing images. Pixman is used by cairo and the X server as a software fallback when hardware-accelerated implementation of the operation is available. When a Pixman function appears as a hotspot in profiling, the first step is to determine whether hardware-acceleration is being used. Graphics hardware often has limitations on the image formats, image sizes, and operations that can be accelerated. As a result, detecting software fallback and correcting the code to avoid these limitations, and therefore software routines, improve performance.

## 10.2 buGle

The buGle library is an instrument shim, designed for collecting OpenGL traces and statistics. Using the LD_PRELOAD mechanism, the buGle library is loaded before the dynamic linker begins resolving symbols for the application. Because buGle provides all of the symbols that are typically provided by libGL.so or libEGL.so, the OpenGL function calls for a dynamically linked application, are resolved by the dynamic linker to the buGle instruments. These instrumented functions invoke the original libGL.so or libEGL.so functions, but additionally keep track of any desired OpenGL state, such as the function calls made, their durations, and their result.

As a result of this implementation, buGle allows for data collection to be performed on unmodified, dynamically linked, binaries. At the same time, this implementation also has the downside of requiring buGle to remain synchronized with the current OpenGL and ES implementations.

The recording and reporting capabilities of buGle are grouped together into filters. Each filter, such as stats_basic, trace, and showerror, corresponds to what aspects of OpenGL are traced, and therefore subsequently reported. Filters export counters, which can be combined and operated in order to generate custom statistics that can also be displayed.

The definition of one or more enabled filters, along with any custom reporting and statistics, is referred to as a chain. The chain utilized at runtime for tracing is selected the BUGLE_CHAIN environmental variable. Custom chains are defined in the $HOME/filters file, while custom statistics are defined in the $HOME/bugle/statistics file.

Some of the more common filters are:

- - checks Records warnings, and skips the erroneous function call, on
- - showc Records OpenGL errors, that is, glGetError()
- - trace Records every GL function executed, with the function parameters
- - stats_calltimes Records the duration of each OpenGL function call per frame
