Using this information, it is possible to rearrange a data structure's memory layout to improve locality. As always, any changes should be measured and verified with benchmarking to ensure that they actually improve performance. For example, consider the following structure:

```
struct bad_locality {
  int x;
  char strdata[252];
  int y;
};
```

In this example, assume that profiling has identified that code utilizing this structure is suffering from performance penalties due to cache replacements, where caches are loaded and prematurely evicted. Also assume that the accesses to this structure frequently use bad_locality.x and bad_locality.y, together and don't use bad_locality.strdata. Now the output from pahole, which has been adjusted to fit the page width of this book, for this structure:

```
struct bad_locality {
  int x;              /* 0 4 */
  char strdata[252];  /* 4 252 */
  /* cacheline 4 boundary (256 bytes) -- */
  int y;              /* 256 * */
```

> /* size: 260, cachelines: 5, members: 3 */
/* last cacheline: 4 bytes */

Notice that bad_locality.x and bad_locality.y are separated by four cache lines. Because of this, two separate cache lines, one for each member, will need to be loaded to complete any operation over integers. Also, the gap between the two cache lines grows, the probability of both cache lines being present in the L1 cache decreases simultaneously, potentially increasing the time required to fetch these elements from memory. On the other hand, by rearranging this, so that bad_locality.x and bad_locality.y share a single cache line, the number of cache lines that need to be loaded is halved. In other words, the struct would be rearranged into:

```
struct better_locality {
  int x;
  int y;
  char strdata[252];
}
```
