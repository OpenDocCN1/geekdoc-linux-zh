Kerberos works by sending messages back and forth between the client and the server. The actual password (or even a hash of the password) is never sent. That makes it impossible for someone to intercept it. What happens instead is the username is sent. The server looks up the stored hash of that password, and uses as an encryption key to encrypt data and send it back to the client. The client takes the password the user entered, and uses that as a key to decrypt the data. If the user entered the wrong password, then it will never get decrypted. This is a clever way to verify the password without ever being transmitted. Authentication happens with UDP (User Datagram Protocol) on port 88.

After the user's username is sent to the authentication service (AS), as AS will use the hash of the user password that is stored as a secret key to encrypt the two messages that get to the client:

+   * Message A: Contains Client/TGS (Ticket Granting Service) session keys encrypted with secret key of client
* Message B: Contains TGT (Ticket Granting Ticket) that includes client ID, client network address, and validity period

Remember, both of these messages are encrypted using the key as generated.

Then the user attempts to decrypt message A with the secret key generated by the client hashing the user's entered password. If entered password does not match the password AS found in the database, then the hashes won't match, and the decryption won't work. If it does work, then message A contains the Client/TGS session key that can be used for communications with the TGS. Message B is encrypted with the TGS secret key and cannot be decrypted by the client.

Now the user is authenticated into the system. But when the user actually requests a service, some more message communication is required. When requesting services, the client sends the messages to the TGS:

+   * Message C: Composed of the TGT from message B and the ID of the requested service
* Message D: Authenticator (which is composed of the client ID and the timestamp), encrypted using the Client/TGS session key

Upon receiving messages C and D, the TGT retrieves message B out of message C. It decrypts message B using the TGS secret key. This gives the “Client/TGS session key”. Using this key, the TGS decrypts message D (Authenticator) and sends the two messages to the client:

+   * Message E: Client-to-server ticket (which includes client ID, client network address, validity period, and client/server session key) encrypted using the service’s secret key
* Message F: Client/server session key encrypted with the Client/TGS session key
