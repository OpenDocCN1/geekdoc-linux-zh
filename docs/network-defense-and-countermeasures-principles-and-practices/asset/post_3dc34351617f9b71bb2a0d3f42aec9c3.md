
## CHAP

CHAP is actually a three-part handshaking (a term used to denote authentication processes) procedure. After the link is established, the server sends a challenge message to the client originating the link. The originator responds by sending back a value calculated using a one-way hash function. The server checks the response against its calculation of the expected hash value. If the values match, the authentication is acknowledged; otherwise, the connection is usually terminated. This means that the authorization of a client connection has three stages. Figure 7-3 illustrates them.

What makes CHAP particularly interesting is that it periodically repeats the process. This means that even after a client connection is authenticated, CHAP repeatedly seeks to re-authenticate that client, providing a robust level of security.

> FYI: What Is a Hash Function? The term hash function comes up a bit in discussions of encryption and authentication. Having a solid understanding of what it is therefore important. Discussed in Chapter 6, "Encryption Fundamentals," a hash function (h) is a transformation. This transformation takes a variable-sized input (n) and returns a fixed-length string. The fixed-length string that is returned is the hash value h(n). Expressed as a mathematical equation, this is h(n). More details about hash functions are available at the following websites:

## L2TP

Layer 2 Tunneling Protocol is an extension or enhancement of Point-to-Point Tunneling Protocol that is used to operate virtual networks. As its name suggests, it operates at the data link layer of the OSI model (like PPTP). PPTP and L2TP are considered by many experts to be less secure than IPSec. However, seeing IPSec used together with L2TP to create a secure VPN connection is not uncommon.

Like PPTP, L2TP supports EAP and other authentication methods for a total of six:
- EAP
- CHAP
- MS-CHAP
- PAP
- SPAP
- Kerberos

EAP and CHAP were discussed in the previous section. The following section discusses the remaining.

## MS-CHAP

As the name suggests, MS-CHAP is a Microsoft-specific extension to CHAP. Microsoft created MS-CHAP to authenticate workstations. The goal is to provide functionality available to remote users while integrating encryption algorithms used on Windows networks. Wherever possible, MS-CHAP is consistent with standard CHAP. However, some basic differences between MS-CHAP and standard CHAP include the following:
- The MS-CHAP response packet is in a format designed for compatibility with Microsoft products.
- MS-CHAP does not require the authenticator to store clear-text or reversibly encrypted passwords.
- MS-CHAP provides authenticator-controlled password-changing mechanisms. These mechanisms are compatible with Windows.
- MS-CHAP defines failure codes that are returned in the message field if authentication fails which Windows software is able to interpret.

## PAP

Password Authentication Protocol (PAP) is the most basic form of authentication. With PAP, a user's name and password are transmitted over the network and compared to a table. Typically, the passwords stored in the table are encrypted. However, the transmissions of the passwords are in clear text, unencrypted. The main weakness with PAP is that this method is no longer used and is only presented for historical purposes. Figure 7-4 shows this authentication.

## SPAP

Secure Password Authentication Protocol (SPAP) is a proprietary version of PAP. Most experts consider SPAP somewhat more secure than PAP because the username and password are both encrypted when they are sent, unlike with PAP. Figure 7-5 illustrates this.

![](img/b9022ea8d49ef539d37d0ec09f73f71c_204_1.png)

SPAP encrypts passwords, someone capturing packets will not be able to read the password. However, SPAP is still susceptible to playback attacks (that is, a person records the exchange and plays the message back). Playback attacks are possible because SPAP always uses the reversible encryption method to send the passwords over the wire.

## Kerberos

Kerberos is one of the most well-known network authentication protocols. It was developed at MIT and its name stems from the three-headed dog that guards the gates. Kerberos is ubiquitous, and it is also asked on a number of security-related certification exams (Security+, CISSP, CASP, etc.). So, it is a good idea to have a fundamental understanding of Kerberos. This section provides a brief overview sufficient for most industry certification exams.

Kerberos works by sending messages back and forth between the client and the server. The actual password (or even a hash of the password) is never sent. That makes it impossible for someone to intercept. What happens instead is the username is sent. The server looks up the stored hash of that password and uses it as an encryption key to encrypt data and send it back to the client. The client takes the password the user entered and uses that as a key to decrypt the data. If the user entered the wrong password, it will never get decrypted. This is a clever way to verify the password without ever being transmitted. Authentication happens with UDP (User Datagram Protocol) on port 88.

After the user's username is sent to the authentication service (AS), AS will use the hash of the user password that is stored as a secret key to encrypt two messages that get to the client:
- Message A: Contains Client/TGS (Ticket Granting Service) session keys encrypted with secret key of client
- Message B: Contains TGT (Ticket Granting Ticket) that includes client ID, client network address, and validity period

Remember, both of these messages are encrypted using the key as generated.

Then the user attempts to decrypt message A with the secret key generated by the client hashing the user's entered password. If entered password does not match the password AS found in the database, then the hashes won't match and the decryption won't work. If it does work, then message A contains the Client/TGS session key that can be used for communications with the TGS. Message B is encrypted with the TGS secret key and cannot be decrypted by the client.

Now the user is authenticated into the system. But when the user actually requests a service, some more message communication is required. When requesting services, the client sends the messages to the TGS:
- Message C: Composed of the TGT from message B and the ID of the requested service
- Message D: Authenticator (which is composed of the client ID and the timestamp), encrypted using the Client/TGS session key

Upon receiving messages C and D, the TGT retrieves message B out of message C. It decrypts message B using the TGS secret key. This gives the “Client/TGS session key”. Using this key, the TGS decrypts message D (Authenticator) and sends the two messages to the client:
- Message E: Client-to-server ticket (which includes client ID, client network address, validity period, and client/server session key) encrypted using the service’s secret key
- Message F: Client/server session key encrypted with the Client/TGS session key
