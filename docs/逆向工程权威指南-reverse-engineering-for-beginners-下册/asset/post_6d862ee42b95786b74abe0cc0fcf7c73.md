## 81.2 V$TIMER

调试 Oracle 启动以后，无论查询 `V$TIMER` 表，这个表都不会是空的。当然，不要在实用的服务器上进行测试。这种调试不大，或许没有实用。不过，当我们要找到指令时，我们可以采用这样的步骤：

```sql
SELECT * FROM V$FIXED_DEFINITION WHERE VIEW_NAME='V$TIMER';
SELECT SECCS FROM GV$TIMER WHERE INST_ID = USERENV('Instance');
SELECT * FROM V$FIXED_DEFINITION WHERE VIEW_NAME='GV$TIMER';
SELECT INST_ID, TIMER FROM V$TIMER;
```

`V$TIMER` 算得上是最频繁的视图之一，以秒为单位，记录实际运行时间。这个值起点计数的具体数值与操作系统相关。它会在溢出时（大约 7 天后）变为 0。上述内容自官方文档。有趣的是：Win32 版本的程序和 Linux 版本的返回时间显然不同的。我们能否找到返回值的数量？

## 指令清单 81.14 tracer output

`ID=2428(0) oracle.exe!memset(0, 0xd7c5f0) (called from oracle.exe!table_fetch)`
`ID=2428(0) oracle.exe!memset(0, 0xd7c5f0) (called from oracle.exe!table_fetch)`

上述数据在 SQL*Plus 看到的数据一样。它是函数的第二个参数。然后我们再分析 Linux x86 程序里的 `ksugcs()` 函数：

```assembly
ksugcs proc near
var_4 = dword ptr -4
arg_0 = dword ptr 8

push   ebp
mov    ebp, esp
push   esi
mov    [ebp+var_4], ebx
mov    eax, [ebp+arg_0]
call   $+5
pop    ebx
nop
mov    ebx, offset _GLOBAL_OFFSET
mov    dword ptr [eax], 0
call   GetTickCount
push   0Ah
push   edx
push   eax
call   __divdi3
mov    ebx, [ebp+var_4]
add    esp, 10h
mov    esp, ebp
pop    ebp
ret
```

`ksugcs` 函数调用了 `GetTickCount()`，然后把返回值乘以 10。在 Win32 版本的程序中，这个则是：

```assembly
_ksugcs proc near      ; CODE XREF: _dbResetCount+15, _dbRunActions+1528
db     66h
nop
push   ebp
mov    ebp, esp
mov    eax, [ebp+8]
mov    dword ptr [eax], 0
call   ds:__imp__GetTickCount
mov    edx, eax
mov    eax, 0xCCCC
mul    edx
shr    edx, 3
mov    eax, edx
mov    esp, ebp
pop    ebp
ret
```

Win32 的结果就是 `GetTickCount()` 函数的十分之一。这就是 Oracle 在 Win32 下和 x86 返回不同结果的根本原因，因为它使用了不同的操作系统函数。“call memset”里有一个“drain”。这个关键字有“表中的某个特定函数的返回值”的含义。前面用过的工具能够处理 `table_registry_0`。因此，我们可以用它分析“列”的值与函数数量之间的关系：

| Table Name | Value | Description |
| :--- | :--- | :--- |
| V$TIMER | call_v_timer_c | table_fetch |
| V$TIMER | call_v_timer_c | table_fetch |
| GV$TIMER | call_v_timer_c | table_fetch |
| DRN (drain) |

上述信息的 OPN 代表“Open”和“DRN”。DRN 当然是“drain”的意思。
