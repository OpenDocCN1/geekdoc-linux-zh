在Windows安装程序的标准链接DLL中，多个文件的地址表（Input Address Table, IAT）都是PE文件的头部。这个头部是为了优化的考虑而刻意设计的。当运行一个可执行文件时，exe文件并不会一次性全部加载到内存中（否则大型安装程序的加载速度就显得太慢了），而且在访问过程中被映射到内存里。它的目的就是加速exe文件的加载速度。

# 6.2.8 资源数据

文件中的资源段的索引不是资源就是图表、图形、字符串以及属性框等界面的支持：该资源与主程序共享一份编译，大部分是为了方便实现多语言支持：操作系统需要根据用户的设置来可以选择相应的资源或或文件。

而这也带来了一个副作用：由于PE文件的二进制比较难以编辑，不具备PE文件知识的人可能可以借助工具（ResHack）直接修改资源源。相关的介绍可以参考书籍68.2.11。

# 6.2.9 .NET

.NET程序并不会编译成机器码，而是会被编译成一种特殊的字节码。严格地说，这种文件由字节结构组成，并不是有意义的X86指令流。但是这种程序的入口（OEP）确实是一个X86跳转：

```
jmp mscore.dll!\ExeMain
```

NET格式的PE文件由mscore.dll处理，它们是NET程序的加载器。在Windows操作系统之前，NET程序是通过上述JMP指令交给mscore.dll处理的。自Windows XP系统起，操作系统的加载器会自动识别NET格式的文件，正常加载NET程序。有关信息请访问：

```
https://msdn.microsoft.com/en-us/library/xh0859k0(vs=110).aspx
```

# 6.2.10 TLS线程

这个段里存储了TLS数据（第65章）的初始化数据（如果需要的话）。启动一个新的线程时，TLS的数据是通过该段的数据来初始化的。

此外，PE文件的规范约定了“TLS ”的初始化函数，即TLS callbacks/TLS回调函数。如果程序声明了TLS回调函数，那么TLS回调函数会先于OEP执行。这项技术广泛应用于PE文件的压缩和加密处理。
