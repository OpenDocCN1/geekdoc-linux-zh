
实际上，只要查看WRK[1]v1.2的源码就会发现：这部分指令确实来自于手写的汇编语言源文件WRK-v1.2\base\ntos\ke\i386\cpu.asm。

[1] WRK是Windows Research Kernel（Windows研究内核）的缩写。

# 第62章 魔数与程序调试

通常来说，逆向工程的主要目的是理解目标程序处理数据的具体方法。这些数据可能来自于某个文件或者来自于网络通信，不过数据的出处无关紧要。手工跟踪一个值是一项非常费力的事情。为了完成这个任务，一个简单的方法是使用自己的特有魔数，虽然这个办法不是百分之百可靠的。

在某种意义上，魔数的作用和X光的造影剂十分相似；在病人的血液里注入造影剂后，医生就能增强X射线的观察效果，清晰观察病人的内部情况。借助造影剂的作用，从而在X光下清晰观察血管内的循环，从而更加准确地判断器官是否存在结石或者肿瘤等。

尽量“眼睛”。在观测32位数据时，我们可以将魔数设置为0xBADFOOD (BADFOOD)，或者0xA1101979（某人的生日，例如“1979年11月10日”）。我们可以将这样的魔数数值写入我们我们要查询的程序中。

接着，我们可以利用tracer的代码覆盖率模式（code/oc模式）跟踪程序，再利用grep或者直接搜索文本文件（跟踪的结果文件），我们就能容易发现这些调用的点及处理方法。

## 63.4 快照对比

这种内存“快照”技术可以凸出内存中的数据，过去常见于作弊领域。如果你在32位程序（这些通常不大，而游戏本身占据内存）启动一个游戏，就可以看到部分帧。现在有32位程序，就可以将所有的内存做一个镜像。把镜像作为保存后，你可以先开枪，这时剩余数量就会显示为99。这时再对整个内存空间做一个镜像。考虑到这些32位程序都是汇编语言编写，而且都是全局变量。基于以上的对比结果，我们可以分析出内存存放着数量。对于这个突破，我们就可以在32位程序（需要反汇编）搜索时引入了这些指令，就不会发现程序总数的减少。然后我们将游戏修改指令，保证游戏总数不受影响。

# 第64章 参数的传递（调用规范）

## 64.1 cdecl

这是C/C++语言中最常用的参数传递方法。调用函数时，被调用函数传递参数：以“最后（右侧）”的参数、倒数第二至第一个参数的顺序传递。被调用函数退出后，应由调用函数调整ESP、将栈恢复成函数的原始状态。

```
push arg3
push arg2
push arg1
call function
add esp, 12
```

## 64.2 stdcall

这种调用方式与上面提到的cdecl类似，有一点不同：被调用函数在返回之前执行“RET x”指令清理参数，而不会使用单纯的“RET”指令直接返回。这里的x的数值计算方式是：x=参数个数*指针的大小（x86架构中的值是4，而在x64中是8）。这样调用函数本身不需要调整指针，因此调用函数不会使用“add esp, x”。

```
push arg3
push arg2
push arg1
call function

function:
... do something ...
ret 12
```

此类约定在Win32的标准库文件中十分常见。然而因为Win64系统遵循调用约定的是Win64规范，所以Win64的库文件里不会出现stdcall的标志性操作指令。以书8.1节中的函数为例，我们给其中的函数增加__stdcall限定符即可强制使用stdcall调用约定：

```
int __stdcall f2 (int a, int b, int c)
{
    return a*b+c;
}
```

它的编译结果与本书8.2节相似，但是最后的指令从RET变成了RET。遵循stdcall约定之后，指针SP就不再由调用方更新了。这样一来，我们就可以通过函数尾部的RET指令直观地推算出外部参数的个数。计算方法就是：N除以4（对于x86）。

```
_a$ = 8
_b$ = 12
_c$ = 16
_f2@12 PROC
    push ebp
    mov ebp, esp
    mov eax, DWORD PTR _a$[ebp]
    mov eax, DWORD PTR _b$[ebp]
    mov eax, DWORD PTR _c$[ebp]
    add eax
    pop ebp
    ret 12      ; 0x000000CH
_f2@12 ENDP

push 3
push 2
```
