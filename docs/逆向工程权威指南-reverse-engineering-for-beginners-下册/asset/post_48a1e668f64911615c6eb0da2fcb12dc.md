
许多情况下，我们能够判断出汇报错误的函数以及引发它们报错的具体条件。有意思的是，有些注重版权保护的程序刻意在出错的时候临时调整错误信息或错误代码。毕竟，开发人员不会希望别人轻易就能摸清他的防盗措施。

本书的7.2演示了一个对错误信息加密的程序。

## 57.3 可疑的魔数字字符串

一些经常被用在后门程序中的魔数字字符串看起来就很可疑。比如说，我们注意到一个关于TP-Link WR7400家用路由器存在了后门的报道（参见 http://sekurak.jp/tp-link-httpftp-backdoor/）。当有人访问该URL，才会触发这个后门：

```
http://192.168.0.1/userRpmNatDebugRpm26525557/start_art.html
```

事实上，字符串userRpmNatDebugRpm26525557一定存在于固件中的某个文件。然而在这个后门事件发生之前，Google搜索不到任何信息，当然这个后门曝光后的情况完全相反。像这种后门类的字符串，查找RFC资料你也找不到它。再怎么调整字符序，它也不会和数学算法占用。它也不是错误信息或者调试信息。因此，尽快定位类似的可疑字符串是一个好主意。

字符串通常采用Base64编码。因此把文件中的字符串全都进行解码处理，再扫一遍就知道哪个文件含有这个字符串了。

更准确来讲，这种隐藏后门的方法被称为“不公开即安全（security through obscurity）”，也就是见光死。

## 第59章 常数

人类在现实生活中喜欢使用整数。编程人员也是人，他们同样喜欢选用10、100、1000这样的整数。

熟悉的反汇编工程师都会明白，与之对应的十六进制数的关系是：10=0xA;100=0x3E8而10000=0x2710。然而，在二进制层面这些数字都不算太“整”。

从二进制层面来看，更为常用的整数是0xAAAA(1010101010101010)和0x55555555(0101010101010101)这类特征明显的常量。以常数0x55AA为例：引导区、主引导区MBR以及IBM兼容扩展的ROM（只读存储单元）等关键字都会使用这个常量。

一些特殊，则是某些加密，常常使用某些特殊的常数，如果我们使用调试工具就能很容易发现这些点。

以MD5算法为例，其内部变量初始值则是：

```
var int h0 := 0x67452301
var int h1 := 0xEFCDAB89
var int h2 := 0x98BADCFE
var int h3 := 0x10325476
```

也就是说，如果某段代码连续出现了上述四个常量，那么这段代码可能就是MD5的算法相关。

另外的例子则是CRC16/32的算法，其预置的常数表如下所示。

### 59.1 魔数

很多文件文件中使用特定的魔数来表示格式，这些魔数可以是一个字符或者多个字节的组合（Magic number）。我们熟知的，所有的Win32以及MS-DOS的可执行文件的开头都是“MZ”这两个字符。标准的MIDI文件以“Magic”这4个字符开头。因此，某些使用MIDI文件的程序基本上都会检测目标文件的4个字符不是“Magic”。如果程序用来，可能是下面这样的：（注：buf是内存区的起始地址）

```
cmp [buf], 0x6468544D ; "Magic"
```

比较函数同样用来验证文件头中的魔数。常用的函数有：比较内存的memcmp函数，或者CMPSB类的指令（可以参考附录A.6）。一旦某程序开始检测文件的魔数，我们就可以确定它加载了某种类型的文件。不仅如此，还可以解读文件以及使用缓冲区的方法等。
