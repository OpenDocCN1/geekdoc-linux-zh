## 6.2.6 重定向Relocations (relocs)

至少在Hiew中，它也可以表示为FIXUP-s。

重位段是MS-DOS时代一直存在于可执行文件的实体段，几乎所有的可执行文件都有这个段。

前文知道，程序可能会被加载到模块的基地址。但是如何处理全局变量等共享数据呢？程序必须通过地址来访问此类数据，然而程序又不能事先知道共享数据的存储地址，为了解决这个问题，我们推出了“位置无关代码/PIC”（详情请阅67.1）的解决方案。不使用PIC来并是不行的。

> 是，我们推出了基于“重定向”的地址重定向技术。重定向表记录了该文件被加载到不同基地址时需要修正的地址所指引。

如果PE文件声明了一个地址为0xA10000的全局变量，那么这个变量的指令地址大致上将会是：

```
A1 00 01 00    mov    eax, [00000000]
```

此时，模块的基地址是0x400000（默认链接器地址），全局变量的相对虚拟地址RVA是0xA10000。

如果这个模块被加载到基地址为0x500000的基地址，那么这个全局变量的真实地址应当被调整为0x510000。

在上述opcode中，变量地址应该是0xA1（MOV EAX 指令）之后的几个字节。为了让操作系统在重定向时正确处理该地址，PE文件的重定向表必须收集这四个字节的相对地址。

当操作系统的加载器需要这个模块加载到不同的基址时，它会遇到一张重位表中所所有基址，这些基址所指向的数据作为模块的地址指针，减去初始基址（这样就能获得RVA，也就是相对虚拟基址），并加上新的基址。

如果模块被加载到它的原始基址上，那么操作系统就不会进行重定向处理。

所有全局变量的处理过程都是如此。

重定向的数据结构并不唯一，Windows for x86程序的重定向一般采用IMAGE_REL_HIGHLOW的数据结构。

## 6.2.7 导出和导入

我们知道，任何执行文件都必须或少地调用由操作系统的提供者或者DLL动态库。

广泛地，由于某个模块（来说是DLL）声明的所有函数，最终会被其他模块（.exe文件或其他的DLL）的指令来调用，只是调用方式不同而已。

为此，每一个DLL动态库文件都有“导出/exports”表。导出表声明了该模块的函数名称和基址。

同时每一个exe和DLL文件还有一个“导入”表。这个表声明执行该模块所需的函数名称、以及对应的DLL的文件。

在加载可执行文件主体的之后，接着在DLL的导出列表中查找所需的函数地址，最后把这些地址写到，模块的IAT中。

由此可见，操作系统的加载器的进程过程中要对比大量的函数名称。但是字符串搜索的效率不会太高。后来又引入了“排序”或“命中”（对应相关数据结构的Hints或Ordinal表）的导出符号表示法，把函数名称排列为排序，以此解决脱序操作的效率问题。

因此，DLL只需要在导出表里标注函数的函数“序号”。这显著提升了DLL文件的加载速度。

举例来说，调用MFC的程序就能通过“序号”调用mfc.dll动态链接。而这种程序就不需要导入表（Import Address Table, IAT）中使用字符串。

## 6.2.8 导入段

编译器通常会给导入表及其相关内容分配一个单独的section（例如idata），但这次不是一个强制规定。导入段涉及大量的术语，因此理解起来困难。本节将通过典型的例子演示。

导入段的主体是IMAGE_IMPORT_DESCRIPTOR。它记录着PE文件要导入哪些库。在其元素中：

- Name存储着字符串
- OriginalFirstThunk字段是INT地址
- FirstThunk字段存储的是IAT指针

IAT表的每个成员都是由操作系统解析出来的相对地址（RVA）。
- Hint字段是一个16位整数，“序号”。在加载模块时，如果可以通过序号查找所需函数名，那么操作系统加载器就不进行字符串对比。

外部函数至少有两种调用方法：

① 代码通过call imp形式调用外部函数。从某种意义上，引入函数的地址全部存储到全局空间。考虑到当前可能会挂载与相同的基地上，那么只要把外部函数的目标地址直接连接到重定向就好了。但是引入函数的地址全部重定向到重定向，会显著增加重定向的数据量。进一步来说，重定向越大，程序的执行效率越低。

② 第二种方法是对于每个函数进行处理。在调用外部函数时，跳转到“重定向值+函数RVA”。这种方法也称为thunks。调用外部函数时，程序可以查找对应的函数，这种方式本身就能进行寻址，因此不必还原RVA。编译器可以选择这两种方法之一。如果外部函数的频率足够高，那么链接器完全可以通过thunk调用外部函数。在足够情况下，链接器不需要创建thunk。

③ 它就可以PE文件的外部函数替换为另一个DLL的函数。此时生成的指令是：

```
MOV EAX, (dllfunction)
JMP EAX
```

这种存储的是外部函数的第一个地址。换而言之，在调用DLL时，加载器程序代码的位置直接替换为函数的地址。需要注意的是代码段都是可读的。因此我们需要在代码段中增加一个标记IMAGE_SCN_MEM_WRITE。这样的，在调用时可能会发生错误（禁止访问）。

如果程序只查询一套DLL，而且这些DLL文件里的函数名和地址保持不变，还能进一步提高加载的速度。在现在的PE文件中，Thunk组里可以写入外部函数的地址。需要注意的是IMAGE_DESCRIPTOR结构体的timestamp字段。如果这个字段没有，则链接器将DLL文件的版本设置为当前值。如果有它们，那么程序将不做额外处理，加载速度可能会快。这就是所谓的“old-style binding（静态绑定）”。

Windows的SDK中有一个BIND.EXE的工具可以进行这项设置。在In-Depth Look into the Win32 Portable Executable Format建议，终端用户应该在安装程序后尽快进行这种。

PE文件的打包/加壳可能是压缩/导入的。在这种情况下，Windows无法加载所有的DLL。应该由加密程序负责加载外部者。一般使用LoadLibrary()和GetProcAddress()来完成这项任务。

标准链接DLL中，多个文件的地址表（Input Address Table, IAT）都是PE文件的头部。是为了优化的考虑而刻意设计的。当运行一个可执行文件时，exe文件并不会一次性全部加载到内存中（否则大型程序的加载速度就显得太慢了），而且在访问过程中被映射到内存里。它的目的就是加速exe文件的加载速度。

## 6.2.12 Windows SEH

Windows操作系统中，结构性异常机制（Structured Exception Handling, SEH）是用来处理异常的。它是语言无关的，与C++面向对象编程（Oriented Object Programming, OOP）无关联。本节讲解SEH的特性。每一个运行都有一个SEH链，线程信息块（Thread Information Block, TIB）有SEH的最后一个。当出现异常时（比如地址访问正确或程序主动用RaiseException()回调），就会出现异常处理时CPU的状态。操作系统会在TIB中寻找SEH的最后一个（包含寄存器的值），此时异常处理就会开始检查是否应对这种异常。如果答案是肯定的，那么异常处理就会接手。如果异常处理无法处理这种情况，就会通知操作无法处理，此操作就会逐一尝试异常处理链中的程序，直到能够应对这种异常的程序为止。在异常处理链的末尾有一个大的异常处理程序；它显示一个标准的对话框，通知用户已崩溃，崩溃时CPU的状态是什么，用户是否愿意把这些信息发送给开发者。
