
由ARP层处理。当然，IP地址被映射到IP层，所有与TCP/UDP相关的组件则映射到TCP/UDP层。最后，SSH、FTP、Telnet等应用程序由应用层表示。

![](img/f332344337ca8bf6846cb313a66ee0b3_139_0.png)

图 4-12 System z上Linux的网络通信层

图 4-13将System z上Linux的网络通信层与OSI参考模型进行了比较。OSI参考模型中的硬件层由HW、VM、QDIO和QETH层组成。OSI模型中的数据链路层由ARP层表示。此外，ARP层的一部分以及IP层共同构成了OSI的网络层。OSI传输层实现为TCP/UDP层，最后，System z上Linux网络通信模型中的应用层代表了OSI参考模型中的会话层、表示层和应用层。

## 问题诊断流程图

在尝试缩小问题范围时，分析现有信息至关重要。第126页的图 4-14展示了一个高层流程图，说明了如何做到这一点。该流程图描述了一种可用于本地系统问题诊断的方法。通常，当出现问题时，首先要做的是捕获尽可能多的错误日志。在某些情况下，错误消息可能会被覆盖。因此，一旦有错误消息可用，立即尝试捕获它们非常重要。检查错误消息有助于我们将问题缩小到某一层或至少一组层。当一个正在运行的系统突然停止工作时，在跳进配置文件进行编辑之前，重要的是要调查在问题发生前系统是否做出了任何更改。在大多数情况下，我们会注意到有变更发生，并且导致了错误。如果问题出现在新安装的系统上，值得检查所有配置是否有错误。有时，在System z服务器之外的网络层做出的更改也可能给运行在System z服务器上的系统带来问题。因此，与网络支持人员的良好协调也是排除网络故障的重要因素。在某些情况下，可能需要使用网络数据包跟踪工具来缩小或隔离问题。通常，如果是永久性的通信问题，相对于间歇性问题而言，更容易识别和修复。间歇性问题可能需要更多时间来排除故障，并且在修复后可能需要持续观察一段时间，以确保问题确实已解决。

![](img/f332344337ca8bf6846cb313a66ee0b3_141_0.png)

图 4-14 本地系统的问题诊断

在某些情况下，可能没有太多有用的信息可供分析以进行问题诊断。在这种情况下，最好执行特定命令并分析其输出以进行问题诊断。图 4-15展示了一种使用ping命令来缩小某些层问题的简单但常见且强大的方法。如图表所示，如果ping命令的结果是成功的，那么我们可以确定网络电缆已连接，网络接口处于活动状态，并且IP通信（网络层）正在进行。在这种情况下，可以确定问题位于IP层之上的某处。

![](img/f332344337ca8bf6846cb313a66ee0b3_142_0.png)

图 4-15 使用ping命令缩小问题所在的层

另一方面，如果ping失败，则显然在TCP/UDP层本身之下存在某些问题。这可能是硬件问题，例如电缆未连接等。在这种情况下，显然第一级故障排除应从IP层及以下开始。

现在，我们讨论如何在每一层进行调查以缩小问题范围。

## IP层的调查

由于ping命令的简单性，在排除故障时，通常最好从IP层开始，然后根据情况向上或向下缩小范围。

图 4-16总结了在IP层进行调查时可以执行的一些常见任务。
