I.I Linux Administration Introduction



Linux is an operating system or kernel created by Linus Torvalds with other contributors, released on September 17, 1991, and distributed under an open-source license means programmers can use the Linux Kernel to design their own custom operating systems. 

Linux is the preferred operating system for production servers and critical systems. It has over 300 popular distributions that are being used all around the globe.

The most popular choices among Linux distributions are Red Hat, CentOS, Fedora, Ubuntu, and Debian. Ubuntu and Debian distros are used by the majority of home or desktop users. Red Hat Enterprise Linux and CentOS are two popular choices for server operating-system. 

Most web servers, mobile phones, personal computers, supercomputers, and cloud servers are powered by Linux due to their high stability, high security, and open-source environment. 

The job of a Linux systems administrator is to manage computer system operations such as maintenance, optimization, user account creation or reporting, and taking backups using Linux tools and command line interface tools.

System administration has become a powerful standard for any organization and institute that requires a solid IT foundation. I.II RHEL vs CentOS



RHEL

Red Hat Enterprise Linux (RHEL) is Red Hat’s official distribution. Red Hat support services, Service Level Agreements (SLAs), and certifications are based on RHEL. 

RHEL aims to be an enterprise-level, stable, and secure operating system. RHEL major versions have a support cycle length of seven years with an option to extend up to ten years, thus being a more stable and secure operating system. Although the source code of RHEL is freely available, Red Hat restricts the redistribution of their officially supported versions of RHEL. 

To deploy RHEL on a server or workstation, you have to purchase a subscription from Red Hat and renew it every year. This subscription entitles you to additional items, such as support and patches.

CentOS

is a community-developed and supported alternative to RHEL. It is similar to Red Hat Enterprise Linux but lacks enterprise-level support. As such, it is downstream from RHEL. CentOS is more or less a free replacement for RHEL with a few minor configuration differences. You can download it directly from the official website. CentOS Linux version numbers reflect the release date of the RHEL on which it is based. 

Although you get CentOS for free, for companies that think in terms of the lifespan of their servers and software for several years, the difference between CentOS and RHEL can be significant. An important difference between RHEL and CentOS is the access to repositories. A repository is the installation source used for installing software. If you are using free software such as CentOS, the correct repositories are set up automatically. But if you are using Red Hat Enterprise Linux with a subscription, you’ll get access to the Red Hat repositories on the Red Hat Network (RHN).

CentOS Stream

Year (2020) RedHat announced that it was changing how CentOS work. These updates shifted CentOS Linux from a stable distribution that comes from a rebuild of Red Hat Enterprise Linux (RHEL) to a rolling release Linux CentOS Stream distribution.

That makes CentOS Stream the upstream, public development branch for RHEL, which you can consider as a midstream between Fedora and RHEL as it contains content planned for upcoming RHEL minor releases. The updates are not batched up into minor releases, but rather are released as they are ready.

I.IV Creating an RHEL Virtual Machine



To create an RHEL VM, use the following procedure:

1. Start VirtualBox  


2. From the Menu bar, click Machine > New, Or Press Ctrl+N, Or from the Toolbar, click Tools > New to start the virtual machine wizard.  


3. Give your virtual machine a name. If you give it RHEL, the version will automatically default Type to Linux and Version to Red Hat (64-bit), then click Next.  


4. Select the amount of memory your Virtual Machine will use. When we choose the operating system in the previous step, VirtualBox automatically recommends the proper amount of memory to use. Note that using RAM lower than 4 GB is not recommended. At least choose 4 GB, then press Next.  


5. Select Create a new virtual hard disk, then click Create. This opens a second wizard to create a new virtual hard disk, choose VDI.


6. Click Next and select Dynamically allocate Memory. Selecting a memory size of 20 GB or more is recommended. Select either Fixed-Size Storage or Dynamically Expanding Storage depending upon your needs. Fixed-size storage is going to be the size of the virtual hard disk on the host Operating System (a virtual disk of 20 GB will be 20 GB on the host Operating System's hard disk). A dynamically expanding storage will be only the size of RHEL on your hard disk but will grow in size as files are added to it until it reaches its limit.  


7. Click Next, select the size of the virtual hard disk to be 20GB.


8. Click Create, and you should see your RHEL virtual machine in the list.

Installing RHEL using the graphical user interface

RHEL 9 Install

After downloading the RHEL 9 ISO file, you can install RHEL 9 on physical as well as virtual hardware.

First, install RHEL physically, this can be done using an installation DVD or a Bootable RHEL USB.

Creating a bootable RHEL USB stick from Microsoft Windows is very simple and we're going to cover the process in the next few steps.


Requirements:

● An 8GB or larger USB stick.

● Microsoft Windows 10 or later.

● Rufus, a free and open-source USB stick writing tool.


To install Rufus, go to Google search, search for Rufus, go to Rufus's website, then click the download button. After downloading Rufus, perform these steps to configure your USB device in Rufus:

1. Start Rufus.  


2. Insert your USB stick.


3. Rufus will update to set the device within the Device field.  


4. If the device is incorrect, select the correct one from the device field's drop-down menu.


5. For best compatibility with newer hardware, keep the Partition scheme and target system type set as Master Boot Record (MBR) partition scheme for Unified Extensible Firmware Interface (UEFI). However, if you need to use the USB stick with older hardware, change this to MBR Partition Scheme for BIOS or UEFI.


6. To select the RHEL 9 ISO file, click the optical drive icon alongside the enabled Create a bootable disk using ISO Image. This will open a file requester from which you can navigate and select the ISO file.  


7. Leave all other parameters with their default values and click Start to initiate the writing process.


8. If prompted that there are files to download, agree to the download. Click Yes.


9. If you receive an alert that the download failed or the attempt to connect to the server failed. Click OK. Press the log button to show the log. From log, copy the downloading address and paste it in the Internet explorer, then press Enter. As you will see, to access the address, you need to turn on TLS 1.0, TLS 1.1, and TLS 1.2. Click on the Change Settings button, then search for TLS. Click the three TLS checkboxes. Then click OK. Close internet explorer and try again. Click the Start button. Then click Yes.

  

10. You will then be alerted that Rufus has detected that the RHEL ISO is an isohybrid image which means the same image file can be used as the source for both a DVD and a USB stick without requiring conversion. Keep Write in ISO Image mode selected and click on OK to continue.


11. Rufus will warn you that all data on your selected USB device is about to be destroyed. This is a good moment to double-check you've selected the correct device before clicking OK. After checking, click the Ok button.

The ISO will now be written to your USB stick, and the progress bar in Rufus will give you some indication of how long this will take. With a reasonably modern machine, this should take around 3 minutes. Rufus will complete the writing process and silently drop back to its default window.

Congratulations! You now have RHEL 9 on a USB stick, bootable, and ready to go.

Once you set up your USB drive to be bootable with RHEL, you can then reboot your system (catch the boot menu and boot from USB).

If your computer doesn't automatically boot from USB, try holding F12 when your computer first starts. With most machines, this will allow you to select the USB device from a system-specific boot menu. 


Second, install RHEL 9 using VirtualBox

You can install RHEL 9 using VirtualBox, I recommend you do this to keep your old Operating System as it is, so you can switch back to your old Operating System any time you want without any difficulties, and if you want to install RHEL 9 directly to your machine, there is no problem you can follow the same steps.

Select the virtual hard drive, for new Linux users Click on the chosen local hard disk, then select Automatic from the Storage Configuration Section and click on Done. For more advanced users you can select Custom from the Storage Configuration Section and click on Done. Then, make sure that the disk you want to use is selected and click Done to proceed. Choose the LVM Partition scheme then click the + sign to add a new Mount Point. LVM is short for "Logical Volume Management". You can think of Logical Volumes as "dynamic partitions", meaning that you can create/resize/delete LVM "partitions" from the command line while your Linux system is running without needing to reboot the system to make the kernel aware of the newly-created or resized partitions.


14. For setting up the environment required in this book, I recommend using the following disk layout (based on a 40GB hard disk). You will need to configure (Recommended partitioning scheme):

● A /boot partition, recommended size at least 1 GiB, then click add mount point button. Under device type choose Standard, and Under File system choose XFS File system. Then click on Update settings. 


Note that, unlike other mount points, using an LVM volume for /boot is not possible. /boot must be located on a separate disk partition.


The XFS file system is a highly scalable, high-performance file system that supports file systems up to 16 EiB (exbibyte - approximately 16 billion GiB), files up to 8 EiB (approximately 8 billion GiB), and directory structures containing tens of millions of entries. XFS supports metadata journaling, which facilitates quicker crash recovery. The XFS file system can also be defragmented and resized while mounted and active. This file system is selected by default and is highly recommended.


● Click the + sign to add a new Mount Point / for the root partition, recommended size of 10 GiB, then click add mount point button. Under device type choose LVM, and Under File system choose XFS formatted logical volume. 


● Click the + sign to add a new Mount Point swap, with a size of 4GB logical volume that is used as swap space, recommended size of at least 2 GiB. Then click add mount point. Under device type choose LVM, and Under file system choose swap.


● Click the + sign to add a new Mount Point /home for the user home partition, here I will leave the desired capacity blank to take all the remaining sizes from the 20GB, recommended size at least 1 GiB, then click add mount point button. Under device type choose LVM, and Under File system choose XFS formatted logical volume.


● Click on the done button.


● You will see a summary of the changes we have made. Check the summary then click the accept changes button to write your configuration.


15. Click on Network & Host Name, which is off by default, switch it on. Type in a hostname and click on Apply. Then, click on Done. 


16. To install RHEL 9 server with a graphical user interface, don’t do anything else. But, if you want to install RHEL 9 headless server, click on Software Selection, then select Server and click on Done. Here, I will leave it with the graphical user interface. 


17. If you want to set up your time zone, click on Time & Date, select your Region and City and click on Done.


18. Click on Kdump to configure Kdump. Kdump is used to set up a process that is started with your server to allow you create a memory core dump in case the kernel crashes. If your server does have enough RAM available, that will result in Kdump being active automatically. If your server is low on memory, you won’t have it running by default. As Linux kernel crashes don’t occur very frequently, and setting up Kdump is not a part of the RHCSA or RHCE objectives, you can disable kdump and click the Done button. 


19. Click on Begin Installation, and the installation should start.


20. To enter the root password. Click on the Root Password button. Type your root password, confirm it, then click on Done. 


21. To create a new login user, click on User Creation. Type in the new user's personal information. You can check the Make this user administrator checkbox to make this user administrator. Here, I will leave it as a normal user. Type the new user password, confirm it, then click on Done. Note that logging in with administrator privileges has a lot of risks.


22. Once the installation is complete, click on Reboot.

Click on Force Umount, then click on Machine > Reset to reset the VM. Click on Reset to confirm the action, and the VM should boot from the virtual hard drive.

What is cloning?

Cloning is creating a full copy or a linked copy of an existing Virtual Machine. This copy is called a clone. You might use a cloned Virtual Machine to experiment with a Virtual Machine configuration, to test different guest Operating System levels, or to back up a Virtual Machine.


Clones can be full or linked depending on the amount of data copied from the source to the destination machine.


A full clone is an independent copy of a virtual machine that shares nothing with the parent virtual machine after the cloning operation. The ongoing operation of a full clone is separate from the parent virtual machine.

It does not share virtual disks with the parent virtual machine, so it generally performs better than linked clones, but it takes longer to create than linked clones. Creating a full clone can take several hours or even days if the files included are large.


A linked clone is a copy of a virtual machine that shares virtual disks with the parent virtual machine in an ongoing manner. It is a fast way to convert and run a new virtual machine. You can create a linked clone from the current state or a snapshot of a powered-off Virtual machine. This method saves disk space and lets multiple virtual machines use the same software installation.


All files available on the source machine at the moment of the snapshot continue to remain available to the linked clone. Ongoing changes to the virtual disk of the parent do not affect the linked clone, and changes to the disk of the linked clone do not affect the source machine, but a linked clone must have access to the source, and without access to the source, you cannot use a linked clone.

II.I Access a shell prompt and issue commands with the correct syntax



1.1 Terminal vs Shell 

Before starting, let me tell you the difference between a terminal and a shell. 

A terminal refers to the program that runs a shell. While a shell is a program that processes commands and returns the output.

The shell is much more than just a command interpreter, it is also a programming language of its own with complete programming language constructs such as conditional execution, loops, variables, functions, and many more. That is why the GNU Linux shell is more powerful compared to the Windows shell.

Note that

● Different shells for Linux are available, but bash is the common shell. So, when I am talking about “the shell” in this book, I will be talking about the bash shell.


If you are managing a Linux system, terminal access is essential. If your system defaults to the multi-user.target, you will get a login prompt and you will directly access the text mode or the command-line interface (CLI). To get a prompt enter your username and password. 

Notice, that Linux doesn't display any password placeholder characters.


In the case of the system defaults to the graphical.target, you will get a GNOME login window. Select your username to be prompted for your password, then press the Sign In button to get to the desktop. To get to the command prompt Click on the Activities menu in the upper-left, then click on the Terminal icon in the side menu in the GNOME shell. This will launch the GNOME Terminal, and you will get a command prompt. Or Click on Activities, click on Show Applications, then click on All, and from Utilities click on Terminal.


The terminal window is your control panel for the system. Almost everything that follows is done using this simple but powerful text tool. A terminal window should always show a command prompt when you open it. Once you launch the Terminal, you would find something like “Sam@rhel.server:~$” written on it.


Sam@rhel.server:~$


● Sam: is the name of the user.

● rhel.server: is the computer name or the hostname which we added during the installation.


Important

● The hostname helps identify a computer over the network. In a server environment, the hostname is essential. You can use the command ‘echo $HOSTNAME’ to check your hostname.


The telda ~ sign

The telda ~ sign shows that the user is working in the home directory, you can check the current path using the pwd command. 


Notice, that if you change the directory this sign will vanish. For example, if we moved from /home directory to /bin directory using the 'cd' command. The ‘~’ sign will be changed with the current directory name. It will appear again when moving back to the home directory either by using the command cd /home/username or by typing the command cd only, or by typing the command cd ~.


The $ sign

The $ sign suggests that you are working as a standard user. But if you switched to the root user by using the ‘su‘ command a # will be displayed and the username will be changed to root.


1.2 Commands entered at the shell prompt have three basic parts:

● Command to run.

● Options to adjust the behavior of the command.

● Arguments that are typically targets of the command.


The command is the name of the program to run. It may be followed by one or more options, which adjust the behavior of the command or what it will do. Options normally start with one or two dashes (e.g., - a or - - all) to distinguish them from arguments. Commands may also be followed by one or more arguments, which often indicate a target that the command should operate on.


1.3 Kinds of Commands:

●        Aliases

●        Internal commands

●        External commands


Alias

A shell alias is a shortcut to reference a command. It can be used to avoid typing long commands. For common patterns, it can reduce keystrokes and improve efficiency. A simple example is setting default options on commands to avoid having to type them each time a command is run. Some aliases are provided by default; You can type alias on the command line to get an overview. 

To define an alias, use:

alias newcommand=’oldcommand’, as in the default alias ll=’ls -l --color=auto’.


Notice, aliases are executed before anything else.


Internal Commands vs External commands

Bash built-in commands (also known as "internal commands") are part of the shell itself. Each built-in command is executed directly in the shell itself, instead of an external program that the bash would load and run. You can show the list of built-in commands using the help command.


An example of an internal or built-in command is the alias command, while the top command is an example of an external command.

To find out whether a given command is an internal built-in or external, you can use the type command. For example: 

$ type -a cd

$ type -a top


The PATH Environment Variable 

The $PATH is an environmental variable that tells the shell which directories the executable programs are located in when a user enters a command. To show the PATH variable content type:

$ echo $PATH


The which command

To find out which exact command the shell will be using, you can use which command. For instance, to find out where the shell will get the ls command from, run:

$ which ls


Notice that, for security reasons, the current directory is not in the $PATH variable and that Linux does not look in the current directory to see whether a specific command is available from that directory. That is why you need to start a command that is in the current directory but nowhere in the $PATH by including ./ in front of it. Where the dot stands for the current directory. By running it as ./, you’ll tell bash to look for the command in the current directory. 


Note that

● You can get an overview of the current variables defined in your shell environment by using the env command.


When you want the system to execute a command, you rarely have to give the full path to that command. For example, we know that the ls command is in the /bin directory (you can check with which -a ls), yet we don't have to enter the command /bin/ls for the computer to list the content of the current directory.


The PATH environment variable takes care of this. This variable lists those directories in the system where executable files can be found, and thus saves the user a lot of typing and memorizing locations of commands.

So, the path naturally contains a lot of directories containing bin somewhere in their names, to check the type. 

$ echo $PATH  


These paths are subsequently searched for the required program. As soon as a match is found, the search is stopped, even if not every directory in the path has been searched. If you use programs in other directories more frequently, you can change your path to look in your directories, for example, to add your /home/Downloads directory:

$ export PATH=$PATH:/home/Downloads


Here Changes are not permanent! When using the export command in a shell, the changes are temporary and only valid for this session (until you log out). Opening new sessions, even while the current one is still running, will not result in a new path in the new session.


To make it permanent you need to add:

export PATH=$PATH:/path/to/dir to your home/sam/.profile file or home/sam/.bashrc file.


For example, to add home/Downloads to the PATH variable in the home/sam/.bashrc file. Here, I will use the nano editor to open the .bashrc file for editing $ nano .bashrc, and at the end of this file add:

export PATH=$PATH:/home/Downloads


Notice, I put $PATH to keep the old PATH as it is or it will be removed and you will only see the /home/Downloads path. Press Ctrl+X. Followed by pressing Y to confirm saving. Now, press Enter to confirm using the same name and exit.


Depending on what you're doing, you also may want to symlink to binaries:

$ cd /usr/bin

$ ln -s /path/to/binary binary-name


This will not automatically update your path for the remainder of the session. To do this, you should run:

$ source ~/.bashrc

or

$ source ~/.profile


Notice, sometimes you will need to log out and log in again to see the effect.


Important

● In case you want the updates to be working for all users or the root user, you will do the same steps but on the /etc/profile file or the /etc/bashrc file.



1.4 Environment Configuration Files

Generally, environment variables can be in three categories:



1. Local Environment Variables

These environment variables last only for the current session and are not in the configuration files. For example, you can use the export command on the terminal to set a temporary environment variable. That variable will be accessible on that terminal and vanish when you close it.

$ export NAME="sam"

$ echo $NAME


2. User Environment Variables

These variables are defined for a particular user and are loaded every time this user logs in using a local terminal session or a remote login session. These variables are typically set in and loaded from the following configuration files: .bashrc, and .bash_profile files present in the user’s home directory.


3. System-wide Environment Variables

These are the environment variables available system-wide for all the users on that system. These variables are present in system-wide configuration files present in the following directories and files: /etc/environment, /etc/profile, /etc/profile.d/, /etc/bashrc. These variables are loaded every time the system starts and a user logs in, either locally or remotely.


The /etc/profile file

is a system-wide environment and startup program, for login setup. The file content is executed as a shell script only when a login shell is created.


To add a variable in the /etc/profile file, open it using your preferred text editor:

# vim /etc/profile


Press I to enter the insert mode, then type the following:

$ export NAME="sam"


Press ESC to switch to the command mode, then type "wq" to save and exit.


To read and execute the  /etc/profile file content in the current shell, run:

# source /etc/profile


To verify, run:

# echo $NAME


Note that

● Creating a shell script (a file with extension .sh) in /etc/profile.d directory instead of editing the /etc/profile file is recommended.


The /etc/environment file

is a system-wide configuration file used to set environment variables and is not a shell script.

Note that if you run a non-interactive command with OpenSSH, you will see variables from the /etc/environment but not from the /etc/profile.


The /etc/bashrc file

is used for system-wide functions and aliases and is executed for both interactive (A shell you use to type commands) and non-interactive shells (A shell running a script).

4.1 Accessing the Remote Command Line with SSH

What is Secure Shell (SSH)?

Secure Shell (SSH) is a cryptographic network protocol for operating network services securely over an unsecured network. SSH provides a secure channel over an unsecured network by using a client-server architecture. 

Note that

● SSH runs at TCP/IP port 22.

● Typical applications include remote command line, login, and remote command execution, but any network service can be secured with SSH. 

● Graphical applications can also be run securely over SSH from a remote location.

● SSH was designed as a replacement for unsecured remote shell protocols such as Telnet.


What is the OpenSSH secure shell (SSH)?

OpenSSH is an open-source implementation of the SSH protocol that is used in Linux systems. The OpenSSH Secure Shell (ssh) is used to securely run a shell on a remote system. If you have a user account on a remote Linux system providing SSH services, ssh is the command normally used to remotely log into that system. The ssh command can also be used to run an individual command on a remote system.


Secure Shell examples

Let’s take some examples of using the ssh command for remote login and remote execution:

The ssh command syntax used to log into a remote machine is very simple:

$ ssh user_name@hostname/IPaddress

As you see, the ssh command syntax consists of three different parts:

●    ssh command instructs the system to establish an encrypted secure connection with the host machine.

●    user_name represents the account that is being accessed on the host.

4.4 Configuring SSH Key-based Authentication


Objective

SSH key-based authentication

SSH keys provide an easy and secure way of logging into your server without a password by using public key authentication. It allows users to authenticate using a private-public key scheme. You will first need to generate two keys on your local system, a private key ~/.ssh/id_rsa and a public key ~/.ssh/id_rsa.pub, which are generated using the ssh-keygen command. The private key file is used as the authentication credential, you can consider it as a password, which must be kept secret and secure on your local system. The public key is copied to systems that you want to log into and is used to verify the private key. 


To generate the public and private keys type:

# ssh-keygen

Or you can specify the type of the generated key with the -t option.

# ssh-keygen -t rsa


Note that

● If the ssh-keygen command is invoked without any arguments, it will generate an RSA key.


The utility will prompt you to select a location for the keys that will be generated. By default, the keys will be stored in the .ssh directory within your user’s home directory. Press ENTER to accept the default.


Important

● It is best to stick with the default location to allow your SSH client to automatically find your SSH keys when attempting to authenticate. 


Note that

● If you had previously generated an SSH key pair, you may see a prompt to Overwrite. If you choose to overwrite the key on the disk, you will not be able to authenticate using the previous key anymore.


Next, you will be prompted to enter an optional passphrase which must be provided to access your private key. In the event the private key is stolen, it is very difficult for someone other than the issuer to use it when protected with a passphrase. This adds enough of a time buffer to make a new key pair and remove all references to the old keys before the private key can be used by an attacker who has cracked it. If you do not want to set a passphrase, you can press ENTER twice to bypass this prompt.

Note that

● It is always wise to passphrase-protect the private key since the key allows access to other machines. However, this means the passphrase must be entered whenever the key is used, making the authentication process no longer passwordless. 


Once the SSH keys have been generated, they are stored by default in the .ssh/ directory of your home directory as follows:

●       ~/.ssh/id_rsa : identification (private) key with Permissions 600.

●       ~/.ssh/id_rsa.pub : public key with Permissions 644.

If the file permissions aren’t set to these values, you can change them using the chmod command.

Also, it is better to change the ~/.ssh directory permission to 700 using the chmod command.

$ chmod 700 ~/.ssh


Before key-based authentication can be used, the public key ~/.ssh/id_rsa.pub needs to be copied to the destination system in the ~/.ssh/authorized_keys file. This can be done using the command ssh-copy-id. The syntax is:

$ ssh-copy-id username@remote_host

Or you can specify the pasting location on a remote machine by using the command:

$ ssh-copy-id -i ~/.ssh/id_rsa.pub root@rhel.server


Type in the password and press ENTER. The utility will connect to the account on the remote host using the password you provided. It will then copy the contents of your ~/.ssh/id_rsa.pub key into the ~/.ssh/authorized_keys file in the remote system account.

Note that

● When copying the key to another system using ssh-copy-id, it copies the ~/.ssh/id_rsa.pub file by default.

● It is recommended to change the ~/.ssh/authorized_keys file permission to 600 using the chmod command.


After finishing the previous, try logging into the remote server using SSH keys:

$ ssh root@rhel.server


How to copy a public ley (~/.ssh/id_rsa.pub) to your server

Use the scp command to copy the id_rsa.pub (public key) from your local system to rhel.server remote server as authorized_keys file, this is known as, “installing the public key to server”:

$ scp ~/.ssh/id_rsa.pub sam@rhel.server:~/.ssh/authorized_keys

Another option is to use the ssh-copy-id command as follows from your local workstation:

$ ssh-copy-id sam@rhel.server

$ ssh-copy-id -i ~/.ssh/id_rsa.pub rhel.server

II.IX Create hard and soft links



What is a Link?

A link is a way of matching two or more file names to the same set of file data. There are two ways to achieve this, they behave similarly, but are not the same. 


Link types

1.    Hard link

A hard link associates two or more file names with the same inode. Each regular file is in principle a hard link. Hard links share the same data blocks on the hard disk, while they continue to behave as independent files.

There is an immediate disadvantage that is hard links can't span across partitions since they refer to inodes, and inode numbers are unique within a given partition.

2.    Soft link or Symbolic link (or for short symlink)

A soft link is a small file that is a pointer to another file. A symbolic link contains the path to the target file instead of a physical location on the hard disk. Since inodes are not used in this system, soft links can span across partitions.


Note that

● Removing the target file for a symbolic link makes the link useless.

● Symbolic links are always very small files, while Hard links have the same size as the original file.


Creating Symbolic Links

The command used to create links is ln. To create symlinks, you need to use the -s option.

The syntax for creating a symlink is: 

$ ln -s targetfile linkname

For Example, to create a symlink for the /usr/users/test/Downloads directory in the current directory with the name Downloads:

$ ln -s /usr/users/test/Downloads Downloads


To verify:

$ ls -l

In this example, I created a link in the current directory to a directory on another part of the system.

II.X List, set, and change standard ugo/rwx permissions



Linux File System Permissions


Objective

After completing this section, you should be able to explain how the Linux file permissions model works.


Linux file system permissions

Access to files by users is controlled by file permissions. The Linux file permissions system is simple but flexible, which makes it easy to understand and apply to handle most permission cases easily.


Files have three categories of users to which permissions apply. The file is owned by a user, normally the one who created the file. The file is also owned by a single group, usually the primary group of the user who created the file, but this can be changed.


Different permissions can be set for the owning user, the owning group, and for all other users on the system that are not the user or a member of the owning group. 

Note that

● The most specific permissions apply. So, user permissions override Group permissions, which override other permissions.

Effects of permissions on files and directories:

● r (read) Contents of the file can be read. Contents of the directory (file names) can be listed.

● w (write) Contents of the file can be changed. Any file in the directory may be created or deleted.

● x (execute) Files can be executed as commands. Contents of the directory can be accessed (dependent on the permissions of the files in the directory).


Note that

● Users normally have both read and execute on read-only directories, so that they can list the directory and access its contents. 

● If a user only has read access on a directory, the names of the files in it can be listed, but no other information, including permissions or timestamps, are available, nor can they be accessed. 

● If a user only has execute access on a directory, he cannot list the names of the files in that directory, but if he already knows the name of a file that he has permission to read, then he can access the contents of that file by explicitly specifying the file name.


Viewing file/directory permissions and ownership

You can view file/directory permissions and ownership using the ls -l command.

For example:

$ ls -l test

$ ls -l /home


Note that

● You can add the -d option to the ls command to prevent the descent into the directory and see the expanded listing of the directory itself.

● Linux permissions only apply to the directory or file that they are set on and permissions on a directory are not inherited automatically by the subdirectories and files within it. However, permissions on a directory may effectively block access to its contents. 


Managing File System Permissions from the Command Line


Objective

After completing this section, you should be able to change the permissions and ownership of files using command-line tools.


Changing file/directory permissions

You can use the chmod command to change permissions from the command line. The chmod command takes permission instructions followed by a list of files or directories to change. The permission instruction can be issued either using the symbolic method or the numeric method.


1. The Symbolic method keywords: 

● The Symbolic method keywords are (u, g, o, a) characters and are used (for the user, group, other, and all).

● The (+, -, = ) signs are used (for add, remove, and set exactly).

● The (r, w, x) characters are used (for read, write, and execute).


Note that

● With the symbolic method, it is not necessary to set a completely new group of permissions.

● With the symbolic method, you can use three symbols, + to add permissions to a set, - to remove permissions from a set, and = to replace the entire set for a group of permissions.

● The permissions are represented by a single letter: r for read, w for write, and x for execute.


2. The Numeric method:

● In the Numeric method, each digit represents an access level: user, group, other.

● Each # represents the sum of permissions granted (r, w, and x) for each access level. Where # will = 7 if full permission is granted (rwx) as it will be the sum of 4 for r, 2 for w, and 1 for x.

● Using the Numeric method, permissions are represented by a three-digit octal number (or four, when setting advanced permissions).

● A single octal digit can represent the numbers from 0 to 7, exactly the number of possibilities for a three-bit number.


Convert between Symbolic and Numeric Representations of Permissions

In the three-digit octal (numeric) representation, each digit stands for one group of permissions, from left to right user, group, and other. In each of these groups, start with 0. If the read permission is present, add 4, add 2 if the write permission is present, and add 1 for execute permission.


Notice that, numeric permissions are often used by advanced administrators since they are shorter to type and pronounce, while still giving full control over all permissions.


If a file permissions are shown like this:

- rwx r-x --- 

For the user, rwx is calculated as 4+2+1=7. For the group, r-x is calculated as 4+0+1=5, and for other users, --- is represented with 0. Putting these three together, the numeric representation of those permissions is 750.

This calculation can also be performed in the opposite direction. 


If a file permissions are shown like this:

640

For the user permissions, 6 represents read (4) and write (2), which displays as rw- . For the group part, 4 only includes read (4) and displays as r--. The 0 for other provides no permissions (---) and the final set of symbolic permissions for this file is - rw- r-- ---.


Let’s take some examples:

● To remove read and write permission for group and other on test using the symbolic method:

$ chmod g-rw test

$ chmod o-rw test


● To add execute permission for everyone on the file test using the symbolic method:

$ chmod a+x test


● To set read, write, and execute permission for user, read and execute for the group, and no permission for other on the directory testdir using the numeric method:

$ chmod u=rwx test

$ chmod g=rx test

$ chmod o-rwx test

OR

$ chmod u=rwx,g=rx,o-rwx test

OR

$ chmod u=rwx,g+rx-w,o-rwx test


Note that

● The chmod commands support the -R option for recursively setting permissions on an entire directory tree.

● When using this option, be sure to use the uppercase X permissions instead of the lowercase x permission to indicate that execute permissions should only be set on directories, and not regular files. For example, the following command will recursively set read and write access on sampledir and all its children for their group owner, but will only apply to execute permissions to directories, not regular files: $ chmod -R RW sampledir



Changing file/directory user or group ownership

A newly created file is owned by the user who creates the file. By default, the new file has group ownership which is the primary group of the user creating the file. Since Red Hat Enterprise Linux uses user private groups, this group is often a group with only that user as a member. To grant access based on group membership, the owner or the group of a file may need to be changed.

File ownership can be changed with the chown command. For example, to grant ownership of the file test to sam, the following command could be used:

# chown sam test


The chown command can be used with the -R option to recursively change the ownership of an entire directory tree. This command will grant ownership of sampledir and all files and subdirectories within it to tom:

# chown -R tom sampledir


The chown command can also be used to change group ownership of a file by preceding the group name with a colon ( : ). For example, this command will change the group sampledir to developers:

# chown :developers sampledir


The chown command can also be used to change both owner and group at the same time by using the syntax owner:group. For example, to change the ownership of sampledir to test and the group to developers, use the command:

# chown test:developers sampledir

To verify:

# ls –l sampledir


Note that

● Only the root can change the ownership of a file. Group ownership, however, can be set by the root or the file's owner. 

● The root can grant ownership to any group, while non-root users can grant ownership only to groups they belong to.

● Instead of using the chown command, you can use the chgrp command to change the group ownership using the syntax: $ chgrp group filename



The chgrp command

# chgrp group file

This command works the same as changing ownership with the chown command, including the use of the -R option to affect entire directory trees, and in this case, the syntax will be:

# chgrp –R group dir


Managing Default Permissions and File Access


Objectives

After completing this section, you should be able to configure a directory in which newly created files are automatically writable by members of the group which owns the directory, also using special permissions and default umask settings.


Special Permissions

The setuid (or setgid) permission on an executable file means that the command will run as the user (or group) of the file, not as the user that ran the command. An example is the passwd command.


The sticky bit for a directory sets a special restriction on the deletion of files. Only the owner of the file (and root) can delete files within the directory. An example is the /tmp directory.


Lastly, setgid on a directory means that files created in the directory will inherit the group affiliation from the directory, rather than inheriting it from the creating user. This is commonly used on group collaborative directories to automatically change a file from the default private group to the shared group.


Effects of Special Permissions on Files and Directories


Setting Special Permissions

● Symbolically:

setuid = u+s; setgid = g+s; sticky = o+t


● Numerically:

It will be the fourth preceding digit:

setuid = 4; setgid = 2; sticky = 1


Let’s take some examples:

● To add the setgid bit on the directory sampledir:

$ chmod g+s sampledir


● To set the setgid bit, and read/write/execute for user and group on directory sampledir:

$ chmod g+srwx sampledir


Default File Permissions

The default permissions for files are set by the processes that create them. For example, text editors create files so they are readable and writeable, but not executable by everyone.


Additionally, binary executables are created executable by the compilers that create them. The mkdir command creates new directories with all permissions set-read, write, and execute.


Important

● Before the mask is applied, a directory has permissions 777 or (rwxrwxrwx), and a plain file has permissions 666 or (rw-rw-rw-).


Then umask value will be subtracted from these default permissions after the function has created the new file or directory. Thus, a directory will have permissions of 775 by default, a file 664, if the mask value is (0)002.


These permissions are not typically set when new files and directories are created. This is because some of the permissions are cleared by the umask of the shell process.


The umask command without arguments will display the current value of the shell’s umask:

$ umask


Every process on the system has a umask, which is an octal bitmask that is used to clear the permissions of new files and directories that are created by the process.


If a bit is set in the umask, then the corresponding permission is cleared in new files. Instead of adding the symbolic values to each other, as with chmod, for calculating the permission on a new file they need to be subtracted from the total possible access rights.  

For example, the previous umask, 0002, clears the write bit for other users. The leading zeros indicate the special, user, and group permissions are not cleared. A umask of 077 clears all the group and other permissions of newly created files.

You can use the umask command with a single numeric argument to change the umask of the current shell. The numeric argument should be an octal value corresponding to the new umask value. If it is less than 3 digits, leading zeros are assumed.

The system default umask values for Bash shell users are defined in the /etc/profile and /etc/bashrc files. You can override your system defaults as a user in your  .bash_profile and .bashrc files.


Important

● A directory gets more permissions by default, it always has the execute permission. If it wouldn't have that, it would not be accessible. You can try this out by chmodding a directory 644!

● If you log in to another group using the newgrp command, the mask remains unchanged. Thus, if it is set to 002, files and directories that you create while being in the new group will also be accessible to the other members of that group; you don't have to use chmod.

● The root user usually has stricter default file creation permissions.

Conditional execution

Conditional execution means that you can choose to execute code only if certain conditions are met. Without this capability, all you would be able to do is execute one command after another.


Conditional execution syntax:

[ condition-to-test-for ]

Let’s take an example:

[ -e /etc/group ]

This tests if the /etc/group exists, and if it does this returns a true, command exit status of 0. If it doesn't exist, the command exits with the exit status of 1. The spaces around the symbols are required.

File test operators:

● -d FILE

True if the file is a directory

● -e FILE

True if the file exists

● -f FILE

True if the file exists and it's a regular file

● -r FILE

True if the file is readable by you

● -s FILE

True if the file exists and it's not empty

● -w FILE

True if the file is writable by you

● -x FILE

True if the file is executable by you


String test operators:

● -z STRING

True if the string is empty

● -n STRING

True if the string is not empty

● STRING1 = STRING2

True if the strings are equal

● STRING1 != STRING2

True if the strings are not equal


Arithmetic tests:

● arg1 -eq arg2

True if the arguments are equal

● arg1 -ne arg2

True if the arguments are not equal

● arg1 -lt arg2

True if the arg1 is less than arg2

True if arg1 is less than or equal to arg2

True if arg1 is greater than arg2

III.II Use Looping constructs (for, etc.) to process file, command line input



What is a loop?

A loop is a block of code that repeats (iterates) a list of commands as long as the loop's control condition is true.

for loops

Syntax:

for arg in [list]

During each pass through the loop, arg takes the value of each successive variable in the list.


Basic looping construct:

for arg in [list]

do

command(s)

done


Note that

● You can quote arguments in [list] to prevent possible word splitting.

● Each [list] element may contain multiple parameters.

● A variable may supply the [list] in a for loop.

● The argument list may contain wild cards.

● If do is on the same line as for, there needs to be a semicolon after the list, for example: for arg in [list]; do


For example, to iterate through an array of values until the list is exhausted:

#!/bin/bash

for i in 1 2 3 4 5

do

echo "This is iteration number $i"

done


while

The while construct tests for a condition at the top of the loop, and it keeps iterating as long as that condition is true (returns an exit state of 0). In contrast to the for loop, the while loop finds use in situations where the number of loop iterations is not known in advance.


Basic while construct:

while [condition]

do

command(s)

done

OR

while [ condition ]; do commands; done


Note that

● If do is on the same line as while there needs to be a semicolon after the condition test.

● A while loop may have multiple conditions. Only the final condition determines when the loop terminates.


For example, to read a file with a while loop by iterating over it line by line:

#!/bin/bash

file=test.txt

while read -r line;

do

echo $line

done < "$file"


until

The until construct tests for a condition at the top of the loop, and continues iterating as long as that condition is false, you can consider it as the opposite of the while loop.


Basic until construct:


until [condition-is-true]

do

command(s)

done


Note that

● If do is on the same line as while, there needs to be a semicolon after the condition test, for example: until [condition-is-true]; do


For example, to use until loop to display numbers 0 through 4:

#!/bin/bash

x=0

until [ ! $x -lt 5 ]

do

echo $x

x=`expr $x + 1`

done

II.IV Processing output of shell commands within a script



How to redirect shell command output

Shell scripts provide a powerful feature, the ability to redirect the output from commands and scripts and send it to files, devices, or even as input to other commands or scripts.


Types of output

Commands and scripts in a shell can generate two basic types of output:

1. STDOUT: The normal output from a command/script (file descriptor 1)  

2. STDERR: The error output from a command/script (file descriptor 2)


Note that

● By default, STDOUT and STDERR are sent to your terminal's screen.

● By default, STDIN reads input from the keyboard (file descriptor 0).

● A file descriptor is a unique identifier for a file or other I/O resource.

How to redirect shell output

There are multiple ways to redirect output from shell scripts and commands:

1. Redirect STDOUT

To redirect the standard output to a file, use the following syntax:

$ command > filename

OR

$ command 1> filename

To append the standard output to a file, use the following syntax:

$ command >> filename


Note that

● If you omit the file descriptor, STDOUT is used by default.

2. Redirect STDERR

To redirect stderr (standard error) to a file, use the following syntax:

$ command 2> filename

To suppress the error messages from being displayed on the screen, redirect stderr to /dev/null. The syntax is:

$ command 2> /dev/null


Important

● To append data to an existing file, use the append parameter >>. Otherwise, it will overwrite the existing file data.

3. Redirect STDOUT and STDERR

Another common situation is to send both STDOUT and STDERR to the same file:

To redirect both stderr and stdout (standard output) to a file, use the following syntax:

$ command &> filename

OR

$ command > filename 2>&1

In this example, all output (normal and error) is sent to the same file.

The 2>&1 construction means "send the STDERR to the same place you are sending the STDOUT."

To append both stderr and stdout (standard output) to a file, use the following syntax:

$ command &>> filename

To redirect stdout to the file output and then redirect stderr to stdout to the file errors, use the following syntax:

$ command > output 2>errors

To redirect stdout to the file output and stderr to the file error, use the following syntax:

$ command 2>error 1>output

4. Constructing pipelines

Redirection controls channel output to or from files while piping sends channel output to another process.


Examples of process piping redirection

Piping a long output to less command

For example:

$ ls -l /usr/bin | less


Note that

● The -l option is used for long listing format.

● The less command allows for back-and-forth movement in the file. Also, it is not necessary to read the entire input file before starting, so with large input files, it starts faster than text editors.


Using the tee command for Piping 

The tee command displays or redirects the intermediate result which is usually blocked by pipes. For example, to list information about the current directory files on the terminal while simultaneously being stored in a file, use:

$ ls -l | tee /tmp/output

II.V Processing shell command exit codes



What is an exit code in the Linux shell?

The exit code is the code returned to a parent process by an executable. The standard exit code is 0 for success and any number from 1 to 255 for anything else.


Note that

● If exit codes are not set the exit code will be the exit code of the last run command.


How to get the exit code of a command?

To get the exit code for the last run command, use: 

$ echo $?

If it was successful without any errors, the exit code will be 0. If not, the exit code will be 1.


What is an exit code in Linux Shell?

Exit code (return code) is the code returned from a command or script to a parent process after execution. The standard exit code is 0 for success and any number from 1 to 255 for anything else.


Note that

● You can benefit from exit codes to adapt scripts if a process or command succeeds or fails.

● If no exit codes are set, the exit code will be the exit code for the last run command.


Customize the return code

How to use exit codes in scripts?

To use exit codes in scripts, you can use an if statement to see if an operation was successful.

For example:

#!/bin/bash

cat /etc/passwd

if [ $? -eq 0 ]

then

echo "You have root permission!"

exit 0

else

echo "Permission denied!" >&2

exit 1

fi


Notice that

● If the command runs successfully, the exit code will be 0, and "You have root permission!" will be printed on the terminal.


How to set an exit code?

To set an exit code in a script use exit followed by the number you want to return.

For example:

1. Create a test.sh file:

$ vim test.sh

2. Add the following lines:

#!/bin/bash

exit 5

3. Save and quit

4. To verify, use the following command:

$ sh test.sh

$ echo $?

The result should be 5.


Test the return code with a shell script

If you need to test the exit (return) code of a command you called in your shell script, you need to check the $? variable value immediately after executing the command, by assigning it to another variable, then showing that variable value.


Note that

● You can use the errno command to list all the standard error codes: $ man errno

IV.I Boot, reboot, and shut down a system normally



How to boot, shut down, and suspend your system from the Linux command line


Important

● Sometimes, restarting the system is a key component of troubleshooting.


Boot the System

Simplified overview of the entire Linux boot and startup process:

1. You power up the system.   

2. The firmware (BIOS or UEFI) does minimal hardware initialization and hands over control to the boot loader.  

3. The boot loader starts, and the Master Boot Record (MBR) or GUID Partition Table (GPT) loads.  

4. The operating system selection menu appears.  

5. The boot loader loads the selected kernel.  

6. The kernel loads an initial RAM disk that loads the system drives and mount the root filesystem.  

7. Once the kernel is set up, it launches systemd as PID 1.  

8. systemd mount the host’s file systems and start services.  

9. The default.target file loads.  

10. The user is prompted to authenticate.  

11. The system launches to the default.target (providing either a command-line interface or graphical environment).


Reboot the System

Restarting the computer helps solve many problems and may be necessary to finish some configurations. However, restarting is considered downtime on the server and should be avoided if possible.


Important

● Try using the systemctl restart service_name to restart the services instead of restarting the whole system. However, sometimes a restart is required.

You can restart the system using either of these commands:

# systemctl reboot

OR

# reboot

Shutdown the System

To shut down the system, you can either use the systemctl utility, or call the shutdown command directly.

$ systemctl poweroff

OR

$ shutdown


Note that

● The shutdown command schedules a system shutdown after 1 minute, and you can use the "shutdown -c" command to cancel. While the poweroff command directly turns off the system.

● The shutdown command has two options: --halt and --poweroff. The --halt option stops the operating system while the --poweroff option shuts down the system.


Shutting down the system using the shutdown command

The advantage of using the shutdown command is:

●        The support for time argument

●        The option to cancel the shutdown


One of the main benefits of the shutdown command is that you are able to define a shutdown delay to give users time to save their work and log off the system. You can schedule a time that suits your needs by using the format hh:mm (24-hour time designations). Let’s take some examples:

To shut down the system and power off the machine at a certain time, you can use the command:

# shutdown --poweroff hh:mm

Where hh:mm is the time in 24 hour clock format.

To shut down and halt the system after a delay without powering off the machine, you can use the command:

# shutdown --halt +m

Where +m is the delay time in minutes.

To halt the system at 10pm, type:

# shutdown --halt 22:00

To halt the system after a five-minute delay, type:

# shutdown --halt +5

You can attach a message to all users by entering it after setting the time. For example, if you want all users to know that the system will shutdown in 10 minutes:

# shutdown --halt +10 “Attention! The system will be closed within ten minutes.”

Also, you can cancel a pending shutdown using the command:

# shutdown -c

IV.IV Identify CPU/memory intensive processes and kill processes



What is a process?

An instance of a running program is called a process. Every time you run a shell command, a program is run and a process is created for it. 


Note that

● Processes are also frequently referred to as tasks.

● Several processes may be associated with the same program.


The lifecycle of a process

A new process (referred to as a child) is normally created when an existing process (referred to as a parent) makes an exact copy of itself in memory (using the fork() ). The child process will have the same environment as its parent, but only the process ID number is different. Every new process is assigned a unique process ID (PID) for tracking and security. The process ID (PID) and the parent's process ID (PPID) are elements of the new process environment. 


Note that

● Parent processes – are processes that create other processes during run-time.

● Child processes – are processes created by other processes during run-time.


Any process may create a child process. All processes are descendants of the first system process, which is systemd(1) on a Red Hat Enterprise Linux system. 


The systemd process is the mother (or parent) of all processes on the system, it’s the first program that is executed when the Linux system boots up; it manages all other processes on the system. It is started by the kernel itself, so in principle, it does not have a parent process.

The systemd process always has a process ID of 1. It functions as an adoptive parent for all orphaned processes. You can use the pidof command to find the ID of a process. The syntax is:

$ pidof [options] program


The Fork and exec functions

Through the fork routine, a child process inherits security identities, previous and current file descriptors, port and resource privileges, environment variables, and program code. A child process may then exec its program code. Normally, a parent process sleeps while the child process runs, setting a request (wait ) to be signaled when the child completes. Upon exit, the child process has already closed or discarded its resources and environment; the remainder is referred to as a zombie. The parent, signaled awake when the child exited, cleans the remaining structure, then continues with its program code execution.


Process states

In a multitasking operating system, each CPU or CPU core can be working on one process at a single point in time. As a process runs, its immediate requirements for CPU time and resource allocation change. Processes are assigned a state, which changes as circumstances require. Process states define what the process is doing and what it is expected to do in the near time. The performance of the system depends on a major number of process states.


From birth (spawn) to death (kill/terminate or exit), the process has a life cycle going through several states. Some processes exist in the process table even after they are killed/died, those processes are called zombie processes.


Broadly process states are:

● Running or Runnable

● Sleeping or waiting

● Stopped

● Zombie


Let's dive into each state!

Process state: Running

Kernel-defined state name TASK_RUNNING

The healthiest state of all. It indicates a process is active and serving its requests. The process is properly getting system resources (especially CPU) to perform its operations. The Running process is a process that is being served by the CPU currently. It can be identified by state flag R in ps or top commands output as you will see later in this section in listing processes.


Process state: Runnable

The process state Runnable is when a process has got all the system resources to perform its operation except the CPU. This means the process is ready to go once the CPU is free. Runnable processes are also flagged with the state flag R.


Process state: Sleeping

The Sleeping process is the one that waits for resources to run. Since it’s on a waiting stand, it gives up CPU and goes to sleep mode. Once its required resource is free, it gets placed in the scheduler queue for the CPU to execute.



There are three types of sleep modes: Interruptible, Uninterruptible, and Killable


● Interruptible sleep mode

Kernel-defined state name TASK_ INTERRUPTIBLE

In this mode, the process is waiting for some conditions: hardware request, system resource access, or signal. When an event or signal satisfies the condition, the process returns to Running. These processes are shown with state S in ps or top output.

● Uninterruptible sleep mode

Kernel-defined state name TASK_ UNINTERRUPTIBLE

Process in this sleep mode gets its timeout value before going to sleep. Once the timeout sets off, it awakes. Or it awakes when waited-upon resources become available for it. It can be identified by state D in outputs.

● Killable sleep mode

Kernel-defined state name TASK_ KILLABLE

This sleep mode is identical to the uninterruptible D state but modified to allow the waiting task to respond to a signal to be killed (exited completely). This process flag is K but utilities frequently display Killable processes as D state.


Process state: Stopped

The process state Stopped has two Kernel-defined states and both have the same T flag (state):

1. TASK_ STOPPED

TASK_STOPPED: The process has been Stopped (suspended), usually by being signaled by a user or another process. The process can be continued (resumed) by another signal to return to Running.


2. TASK_TRACED

TASK_TRACED: A process that is being debugged is also temporarily Stopped and shares the same T state flag.


Process state: Zombie

The process state Zombie has two Kernel-defined states:

1. EXIT_ZOMBIE - Z state flag

EXIT_ZOMBIE: A child process signals its parent as it exits. All resources except for the process identity (PlD) are released. It can be identified by state Z in outputs.


2. EXIT_DEAD – X state flag

EXIT_DEAD: After the parent receives the exit signal from the child process, the parent cleans up (reaps) the remaining child process x structure and removes the process slot in the process table, the process is now released completely. This state will never be observed in process-listing utilities.


Note that

● The process can stay in zombie mode if its parent died before it releases the child process’s slot in the process table. It can be identified with Z in outputs.


The complete life cycle of a process can be circled as:

1. Spawn  

2. Waiting  

3. Runnable  

4. Running  

5. Stopped  

6. Zombie  

7. Removed from the process table

Monitoring Process Activity

Let’s understand two important phrases in a Linux system:

1. System load/CPU Load  

2. Load average


1. System load/CPU Load

The system load is a measurement of the computational work the system is performing. This measurement is displayed as a number. A completely idle computer has a load average of 0. Each running process either using or waiting for CPU resources adds 1 to the load average. So, if your system has a load of 4, then four processes are either using or waiting for the CPU.


2. Load average

The load average is useful to understand how your system is performing. If it’s overloaded, you may need to deal with a process that’s wasting resources, provide more hardware resources, or move some of the workloads to another system.


The easiest, most standardized way to see your load average is to run the uptime command in a terminal. This command shows your machine’s load average as well as how long it’s been powered on.

Here’s an example load average readout:

From left to right, these numbers show you the average load over the last one minute, the last five minutes, and the last fifteen minutes:

●Load average over the last 1 minute: 1.02

●Load average over the last 5 minutes: 0.70

●Load average over the last 15 minutes: 3.09


What Do the Numbers Mean, Exactly?

Let’s use the above numbers to understand what the load average means. Assuming you’re using a single-CPU system, the numbers tell us that:

● Over the last 1 minute: The computer was overloaded by 2% on average. On average, .02 processes were waiting for the CPU. (1.02)

● Over the last 5 minutes: The CPU idled for 30% of the time. (0.70)

● Over the last 15 minutes: The computer was overloaded by 209% on average. On average, 2.09 processes were waiting for the CPU. (3.09)

● On a system with two CPUs, this would be complete usage, two different processes were using two different CPUs the entire time.

What are signals in Linux?

Signals are software interrupts sent to a program to indicate that an event has occurred. Events that generate a signal can be an error, an external event (e.g., an expired timer), or by explicit request (e.g., a signal-sending command).


Process control using signals 

The fundamental signals used by system administrators for process management.

IV.V Adjust process scheduling



The Nice Number

The priority or importance of a job is indicated by its nice number. A program with a high nice number is friendly to other programs, other users, and the system; It is not an important job. The lower the nice number, the more important a job is and the more resources it will take without sharing.


Making a task nicer by increasing its nice number is only useful for processes that use a lot of CPU time (e.g., compilers). Processes that always use a lot of I/O time are automatically given higher priority by the system (which means a lower nice number). For example, keyboard input always gets the highest priority in the system.


Defining the priority of a program is done with the nice command. Also, you can use the renice command to change the niceness of a running command. 


To start a process with a niceness value other than the default value, use the following syntax:

$ nice -n nice_value process name


If there is some process already running on the system then you can Renice its value using the syntax:

$ renice nice_value -p pid


To change Niceness, you can use the top command to determine the PID (process id) and its Nice value. Then use the renice command to change the value. Or you can directly renice the process with top running.


A common practice is to use the top utility to find processes that are consuming too much memory or processing power and then act on those processes in some way:

● A process consuming too much CPU can be reniced to give it less priority to the processors.

● A process consuming too much memory can be killed.



With top running, here’s how to renice a process:

1. Note the Process ID (PID) of the process you want to renice.

2. Press R.

3. When the PID to renice message appears, type the process ID of the process you want to renice. 

4. When prompted to Renice PID to value, type in a number from -19 to 20. 


Note that

● The default nice value of all the processes is 0, but if you start the command with nice it'll be 10.

● NI – is the nice value, which is a user-space concept.

● PR or PRI – is the process’s actual priority, as seen by the Linux kernel.


How to Calculate PR or PRI Values?

● Total number of priorities = 140

● Real-time priority range (PR or PRI): 0 to 99

● Userspace priority range: 100 to 139

● Nice value range (NI): -20 to 19

PR = 20 + NI

PR = 20 + (-20 to + 19)

PR = 0 to 39 which is the same as 100 to 139

$ scp -r backup sam@server1:/home/sam/

What is LVM?

LVM stands for Logical Volume Manager. It is a form of storage virtualization that provides system administrators with a more flexible approach to managing disk storage space than traditional partitioning by creating a layer of abstraction over physical storage.


LVM is based on three main concepts:

1. Physical volume (pv): a partition or whole disk.

2. Volume group (vg): a collection of physical volumes (PVs).

3. Logical volume (lv): lv is part of vg that represents a mountable storage device. You can create a file system on the lv.


Note that

● A pv can only belong to one vg.

● An lv can only belong to one vg.

● You can increase the lv size if you have space available in the linked vg file.

● If you don't have any space available on vg, you can add a new disk as pv, add it to vg, then you can increase your lv size.

● Creating or expanding logical volumes does not require any downtime.


To list information about all available block devices:

Note that

● The lsblk command lists the size of the partition while df lists the size of the filesystem.

V.V Configure systems to mount file systems at boot by universally unique ID (UUID) or label



Mounting file systems

You can mount file systems on your system to access data on them.


On Linux, file systems on different partitions and removable devices can be attached to a mount point in the directory tree and then detached again. 


Note that

● While a file system is mounted on a directory, you can't access the original content of that directory.

● Linux does not prevent you from mounting a file system to a directory with a file system already attached to it.


To mount a device, you can identify it with any of the following:

● Universally unique identifier (UUID)

● Volume label (LABEL)

● Full path to a non-persistent block device (ex., /dev/sdb1)



The /etc/fstab file

The file systems table (fstab) file is designed to create a rule where certain file systems are detected and then mounted automatically in the order the user wants each time the system boots. The table itself is a 6-column structure, where each column defines a specific parameter and must be set up in the correct order. 


The columns of the table are as follows from left to right:

1. Device: The given name or UUID of the mounted device.

2. Mount Point: The directory where the device is/will be mounted.

3. File System Type: Shows the type of filesystem in use.

4. Options: lists active mount options. If using multiple options, they must be separated by commas.

5. Backup Operation: This is a binary system where 1 = dump utility backup of a partition. 0 = no backup. Note that, this is an outdated backup method and should NOT be used. 

6. File System Check Order: Here we can see three possible outcomes. 0 means that fsck will not check the file system. Numbers higher than this represent the check order. The root file system should be set to 1 and the other partitions should be set to 2.


To list the UUID and Label attributes, run:

$ lsblk --fs storage-device



Mounting a file system with the mount command

procedure

1. Make sure that no file system is already mounted on your chosen mount point:

$ findmnt mount-point

# mount device mount-point

# mount UUID= afa5d5e3-9050-48c3-acc1-bb30095f3dc4 /mnt

● If mount cannot automatically recognize the file system type, you can specify it using the --types option: # mount --types type device mount-point



Moving a mount point

VI.II Mount and unmount network file systems using NFS



Mounting Filesystems

Once a disk has been partitioned, Linux accesses the data on the partitions using a unified directory tree where each partition is mounted at a mount point in that tree.


A mount point is a directory that is used as a way to access the filesystem on the partition, and mounting the filesystem is the process of associating a certain filesystem (e.g., a partition,) with a specific directory in the directory tree.


You can mount the file system either persistently across reboots (by editing the /etc/fstab file) or temporarily (by using tools such as mount).


To mount a file system temporarily, you can use the following syntax:

# mount -t type device directory -o options


Note that

● You can use the mount command without any options or arguments to show the currently mounted filesystems: # mount

● type: is the file system type (e.g., ext4, vfat, xfs)

● device: is the device name (e.g., sdb1)

● directory: is the mount point (directory) name (e.g., /mnt, /media)

● If only a directory or device is specified, mount will try to find a mount point and if it can't find any, then it looks for a device in the /etc/fstab file, and finally tries to complete the mount process.


Most used mount options

● async: allows asynchronous I/O operations on the mounted file system.

● exec: is the opposite of noexec.

● nouser: prevents any users (other than root) to mount and unmount the filesystem. It

● user: is the opposite of nouser.

● ro: mounts the filesystem read-only.

Procedure

As you see in the previous examples, the /etc/fstab file is used to control how different filesystems are treated each time they are introduced to a system. It consists of a series of lines each containing six fields; The fields are separated by a space or one or more tabs. 


Note that

● The line that begins with the hash sign (#) is a comment and is ignored.


Each line in the /etc/fstab file has the following format:

<file system> <mount point> <type> <options> <dump> <pass>

Where:

● <file system>

The first column specifies the mount device (by their labels or UUIDs).

● <mount point>

The second column specifies the mount point (directory).

● <type>

The file system type code (e.g., xfs). The file system type code can be auto which lets the kernel auto-detect the filesystem type.

● <options>

One (or more) mount option(s).

● <dump>

You are more likely to leave this set to 0 (otherwise set it to 1) to disable the dump utility to back up the file system at boot (Dump software was once a common backup tool, but is less common today.)

● <pass>

This column specifies whether the integrity of the file system should be checked at boot time with fsck. A value of 0 means that fsck should not check a file system. The higher the number, the lower the priority. Thus, the root partition is likely to have a value of 1, while all other partitions that need to be checked should have a value of 2.

VI.IV Create and configure set-GID directories for collaboration



Objective

In this section, you will learn how to use the setgid command to apply setgid permission to a directory.


By default, file permissions prevent the user from accidentally deleting or overwriting other users' files. However, there are use cases where multiple users need to access (read, write or delete) other users' files. Applying the setgid permission to a directory will cause all files created in that directory to be owned by the directory group instead of the owner group.


Note that

● # - Requires executing certain commands with root privileges either directly as a root user or using the sudo command.

● $ - Requires certain commands to be executed as a normal, unprivileged user.


Let’s take an example

If you have two teams (mancity, liverpool), each team has a specific group with the team’s name, and you have a shared group (shared) for the two teams.


First, we create the objects needed. Let’s create the project directory:

# mkdir -p /teams/liverpool


And our two users, user1 and user2, using the useradd command:

# useradd user1

# useradd user2


We also need to create a user group that will allow collaboration between its members:

# groupadd users


Next, we set this group as the owner of the liverpool directory, recursively:

# chown -R :users /teams/liverpool


Next, we add our users to the players group:

# usermod -a -G users user1

# usermod -a -G users user2

We added the group as a secondary group.


To finish the basic setup, we need to add full permission to the group on the directory:

# chmod 770 /teams/liverpool


And with that, we completed the basic setup. Both users can write to the directory, the files created will be owned by the user, and the owner group will be the user's primary group.

To verify:

# stats /teams /liverpool


Now, for both users to be able to work on (copy, edit, read, delete) each other's files, you need to set the setgid flag on the shared directory (/team/liverpool).



Setting the setgid flag

To set the setgid flag, using the chmod command, run:

# chmod g+s /teams/liverpool 

Notice the “s” flag at group permissions.

To verify:

# stat /teams/liverpool


Now, both user1 and user2 can modify other files in the /teams/liverpool directory.


Note that

● If you want the users group members to be able to see each other’s files but not to delete them, you can use the sticky bit permission on the /teams/liverpool directory: # chmod +t /teams/liverpool

VI.V Configure disk compression



Virtual Data Optimizer (VDO) 

The Virtual Date Optimizer (VDO) is a block virtualization technology that provides inline deduplication, thin provisioning, and compression of data at a block device level. It reduces disk space usage on block devices, and minimizes the replication of data, saving disk space and even increasing data throughput. When you set up a VDO volume, you specify a block device on which to construct your VDO volume and the amount of logical storage you plan to present.


In RHEL 8, VDO can be applied to a block device, and then normal disk operations can be applied to that device. LVM for example can sit on top of VDO:

Physical disk (PV) > VDO > Volume group (VG) > Logical volume (LV) > file system


When to use VDO?

You can use VDO for any of the following requirements:

● Provide Thin-Provisioned Storage

● Compress data at a block device level.

● Use logical size 10 times the physical size for VMs and containers.

● Use a logical size of 3 times the physical size for object storage.


VDO Requirements and Recommendations

● Ensure that underlying block devices are > 4GiB.

● Install vdo and kmod-kvdo.

● Running the udevadm settle command will wait for the system to register the new device name.

● Include the x-system.requires=vdo.service mount option in the /etc/fstab file.


Configuration Steps on RHEL 8

1. Install vdo (and if not installed by default kmod-vdo):

# yum install vdo


2. Start the service:

# systemctl start vdo.service


3. Create the volume:

# vdo create --name=[name] --device=/dev/[device] --vdoLogicalSize=[VDO logical size] --sparseIndex=enabled --vdoSlabSize=[slab size]


Note that

● Using --sparseIndex=disabled will enable ‘dense’ indexing.

● Make sure to use the option to not discard blocks.


4. Create a file system:

# mkfs.ext4 -E nodiscard /dev/mapper/[name]

# mkfs.xfs -K /dev/mapper/[name]


5. Update the system with the new device

# udevadm settle


6. Mount the device

# mount /dev/mapper/[name] /mount/point


To add it to /etc/fstab, you will need to add additional params so that systemd waits for VDO to start before mounting:

# /dev/mapper/vdo-device /mount/point [fstype] defaults,_netdev,x-systemd.device-timeout=0,x-systemd.requires=vdo.service 0 0


Note that

● x-systemd.device-timeout=

Configure how long systemd should wait for a device to show up before giving up on an entry from /etc/fstab. Specify a time in seconds or explicitly append a unit such as "s", "min", "h", "ms".

● To Check for real physical space usage:

# vdostats --human-readable



In RHEL 9, VDO is sit on top of LVM:

Physical disk (PV) > Volumegroup (VG) > Logical volume (LV) > VDO > file system


Steps to create a deduplicated and compressed logical volume on RHEL 9﻿


1. Install the vdo and kmod-kvdo packages:

# yum install vdo kmod-kvdo


2. Create the VDO LV:

# lvcreate --type vdo --name vdo-name --size physical-size --virtualsize logical-size vg-name


3. Create a file system on the VDO LV:

- For the XFS file system:

# mkfs.xfs -K /dev/vg-name/vdo-name

- For the ext4 file system:

# mkfs.ext4 -E nodiscard /dev/vg-name/vdo-name


4. Mounting an LVM-VDO volume permanently at boot:

- For the XFS file system, add the following line to the /etc/fstab file:

/dev/vg-name/vdo-name mount-point xfs defaults 0 0

- For the ext4 file system, add the following line to the /etc/fstab file:

/dev/vg-name/vdo-name mount-point ext4 defaults 0 0

VI.VII Diagnose and correct file permission problems



Managing file permissions

File permissions control the ability of user and group accounts to view, modify, access, and execute the contents of files and directories.


Each file or directory has three levels of ownership:

● User owner (u).

● Group owner (g).

● Others (o).

● All (a)


You can set the following permissions for each ownership level:

● Read (r).

● Write (w).

● Execute (x).


To add or remove permissions you can use the following signs:

● + to add the permissions on top of the existing permissions

● - to remove the permissions from the existing permission

● = to remove the existing permissions and explicitly define the new ones


Note that

● Execute permission for a file allows you to execute that file. While the execute permission for a directory allows you to access the contents of the directory.

● When you create a new file or directory, the default set of permissions is assigned to it automatically.

● The default permissions for a file or directory are based on two factors, the base permission and the user file-creation mode mask (umask).


The Base file permissions

When you create a new file or directory, the base permission is assigned to it automatically. Basic permissions for a file or directory can be expressed in symbolic or numeric (octal) values.


Directory Base Permission

The directory base permission is 777 (drwxrwxrwx), which gives everyone (u, g, o) permission to read, write, and execute (r, w, x). Meaning that user, group, and other can list the directory contents, create, delete, and edit items within. 


Note that

● Individual files within a directory can have their permission which may prevent you from editing them, even though there is unrestricted access to the directory.


File Base Permission

The base permission for a file is 666 (-rw-rw-rw-), which gives everyone read and write permission, meaning that the file owner, group, and others can read, edit, and delete the file.


Let's take an example:

Permissions on a file or directory

To show the permissions on a file or a directory, run:

$ ls -l


Permissions on a file

Assuming that we get the following permissions on a file test:

-rwxrw----. 1 sam sam 2 Mar 5 09:15 test

● The first "-" indicates that it is a file. If it was a directory it would be "d".

● The user permissions "rwx" indicates that the owner (u) has permission to read, write, and execute the file.

● The group permissions "rw-" indicates that the group (g) has permission to read and write but not execute the file.

● The other's permissions "---" indicate that other users have no permission on the file.

● The dot "." indicates that the SELinux security context is set for the file.

To show permissions on the directory sample, run:

$ ls -dl sample

Assuming that the result we get is:

● The "d" indicates it is a directory.

● The user permissions "rwx" indicates that the directory owner has the permissions to read, write, and access the contents of the directory sample.

● The group permissions "r--" indicates that the group has permissions to read (list the items within the directory), but not write (w) or access the contents (x) of the directory.

● The other's permissions "---" indicates that other users have no permission to read (r), write (w), or access the contents (x) of the directory.

● The dot "." indicates that the SELinux security context is set for the directory sample.

Permissions for Files and Directory


User file-creation mode mask (umask)

The user file-creation mode mask (umask) is the variable you can use to control setting file permissions for newly created files and directories. 


The umask automatically removes permissions from the base permission value [0777 ( rwxrwxrwx ) for directories and 0666 ( rw-rw-rw- ) for files] to increase the overall security of a Linux system. You can set the umask value using the symbolic method or the octal method.


Note that

● The default umask for a standard user is 0002. With this mask the default directory permissions are 775, and the default file permissions are 664.

● The default umask for the root user is 0022. With this mask the default directory permissions are 755, and the default file permissions are 644.

● The first number of the umask represents special permissions (Sticky bit, SGID bit, or SUID bit). If the first digit is set to 0, the special bit is not set.

● The last three numbers of the umask represent the permissions removed from user owner (u), group owner (g), and others (o), respectively.

● To display the current value of the umask in symbolic mode, run: $ umask -S

● To display the current value of the umask in the octal mode, run: $ umask


Procedure to set up default umask

You can set up the umask value for all users in the /etc/bashrc or the /etc/profile file. And to set the umask value for the current user, you can edit the ~/.bashrc file in the current user's HOME directory to override the default system settings.


To set the umask for the current shell session using symbolic values, use the syntax:

$ umask -S <level><operation><permission>

For example, to set the umask to u=rwx,g=rwx,o=rwx, run:

$ umask -S a=rwx


Note that

● The a option is used to set permissions to all levels of ownership.

● Any permission not specified after the equals sign (=) is automatically prohibited.

● The umask is only valid for the current shell session.


To set the umask for the current shell session using octal values, use the syntax:

$ umask octal_value

For example, to set the umask to u=7,g=7,o=7, run:

$ umask 777


Note that

● The umask is only valid for the current shell session.

You can change the default bash umask for standard users by modifying the /etc/bashrc file as root.

if [ $UID -gt 199 ] && [ “id -gn” = “id -un” ]; then

else  

umask 022


4. Save and quit.

1. As root, open the /etc/login.defs file in the editor:

# vim /etc/login.defs


2. Replace the default octal value (0700) with another octal value:

HOME_MODE 0700


3. Save and quit.


4. If HOME_MODE is not set, modify the UMASK to set the mode for the newly created home directories. Replace the default octal value (022) with another octal value:

UMASK 022


5. Save and quit.


Note that

To determine whether you are executing a command in a login or a non-login shell, use the echo $0 command:

● If the output of the echo $0 command returns bash, you are executing the command in a non-login shell. The default umask for the non-login shell is set in the /etc/bashrc configuration file.

● If the output of the echo $0 command returns -bash, you are executing the command in a login shell. The default umask for the login shell is set in the /etc/login.defs configuration file.

● To display the default bash umask for the non-login shell, run: $ grep umask /etc/bashrc

● To display the default bash umask for the login shell, run: $ grep "UMASK" /etc/login.defs


To change the permissions for a file or directory, use the syntax:

$ chmod <level><operation><permission> filename

Replace <level> with the level of ownership you want to set the permissions for (u, g, o, a). Replace <operation> with one of the signs (+, -, =). Replace <permission> with the permissions you want to assign (r, w, x). Replace the filename with the name of the file or directory. 


For example, to grant everyone permission to read, write, and execute (rwx) the file sample, run:

$ chmod a=rwx sample

To verify:

$ ls -l sample


Note that

● To see the permissions for a particular directory, run:

$ ls -dl directory-name

● To remove the permissions to read, write, and execute (rwx) the sample file from group owner (g) and others (o), run:

$ chmod go= sample Or $ chmod go-rwx sample



Changing file permissions using octal values

You can use the chmod utility with octal values (numbers) to change file permissions for a file or directory.


To change the file permissions for an existing file or directory, use the syntax:

$ chmod octal_value filename


Note that

● The namei command is very useful as it can display all permissions of a file under the path. You have to run it as a user with access to get the desired output.

For example:

# namei -ol /tmp/

The -o option is used to show the owner and group name of each file.

The -l option is used to show the long listing format.

● To change the user owner and group owner of the file or directory, use the syntax:

# chown Username:Groupname Filename

● To change the group owner of the file or directory, use the syntax:

# chgrp Groupname Filename



Special Permissions


Setting special permissions

1. Using the symbolic method

To set SGID on the directory sample, run:

$ chmod g+s sample

To verify:

$ ls -ld sample/


To set SUID bit on a file test, run:

$ chmod u+s test

To verify:

$ ls -l test


To set up a Sticky Bit permission on the sample directory, run:

$ chmod +t sample/

To verify:

$ ls -ld sample/


2. Using the numerical method

The digit used is calculated similarly to the standard permission digits:

● SUID = 4

● SGID = 2

● Sticky = 1

The syntax is:

$ chmod X### file | directory

Where X is the special permissions digit.


To set SUID bit on a file test, run:

$ chmod 4770 test

To verify:

$ ls -l test


To set the SGID bit on the file test, run:

$ chmod 2700 test

To verify:

$ ls -ld test

$ chmod 1770 sample/

To verify:

$ ls -ld sample/



Managing the Access Control List

ACLs contain rules that allow us to apply a more specific set of permissions to a file or directory without changing the underlying ownership and permissions.


There are two types of ACLs:

1. Access ACLs: Access ACLs are used for setting permissions on any file or directory.  

2. Default ACLs: Default ACLs are used for setting access control lists on a specific directory only.


Note that

● The ACL applies to existing files and will not apply to newly created files.

● You can use a default ACL on a directory if you want it to apply to new files as well.


Displaying the current Access Control List

To display the current ACL for a particular file or directory, use the syntax:

$ getfacl file-name | dir-name


Setting the Access Control List

To set the ACL for a file or directory, use the following syntax as root:

# setfacl -m u:username:symbolic_value file-name|dir-name

OR

# setfacl -m g:groupname:symbolic_value file-name|dir-name


Setting Default ACLs

To set the default ACLs for a specific directory, use the following syntax as root:

# setfacl -m d:u:username:symbolic_value dir-name

OR

# setfacl -m d:g:groupname:symbolic_value dir-name


Notice that, no need for the -R option because this will apply to the newly created files.


Note that

● The -R option is used to apply operations to all files and directories recursively.

● The -m option is used to modify the ACL of a file or directory.

● The u option is used to add a user.

● The g option is used to add a group.

● The d option is used for setting the default.


Removing ACLs

● To remove a username entry from a file's or directory's ACL, you can use:

# setfacl -x u:username file-name|dir-name

OR

# setfacl -x u:username:symbolic_value file-name|dir-name


● To remove a named group entry from a file's ACL:

# setfacl -x g:groupname file-name|dir-name

OR

# setfacl -x g:groupname:symbolic_value file-name|dir-name


Note that

● The -x option to remove only specified ACLs from a file or a directory.

● You can use the -b option to remove all ACLs from a file or a directory: # setfacl -b file-name|dir-name

Scheduling Tasks

Automate your Linux system tasks with cron

Cron allows system administrators to schedule and automate tasks with ease and precision.


The crontab file has the following syntax:

minute(0-59) hour(0-23) day_of_month(1-31) month_of_year(1-12) day_of_week(0-7) command_to_run(or path to script)


Note that

● A cron daemon (crond) is a system-managed executable that runs in memory and from which users can schedule tasks. 

● Any user can schedule cron jobs or tasks on the system.

● The task runs under the user account from which it was created.

● In day_of_week both 0 and 7 are Sundays.

1. To install the cronie package, run:

# dnf install cronie


2. To enable and start the crond service, run:

3. To verify that the crond service is started and enabled, run:

# systemctl status crond.service

To show your configured cron tasks, run:

$ crontab -l


To show the scheduled tasks of a particular user, use the following syntax as root:

# crontab -u username -l


Creating and Editing Cron Tasks

To create or edit cron tasks, you can use any of the following methods:

First method

By editing your crontab file (it will be opened in a vim editor), using the command:

$ crontab -e


Second method

Using the System-Wide Cron Schedule.

● /etc/cron.d

● /etc/crontab

● /etc/cron.daily

● /etc/cron.hourly

● /etc/cron.monthly

● /etc/cron.weekly


Third method

If you have sudo privileges, you can edit another user’s crontab with the following command:

$ sudo crontab -u username -e


Note that

● The syntax of system-wide crontab files is slightly different than user crontabs. It contains an additional mandatory user field that specifies which user will run the cron job.

* * * * * <username> command(s)


Remove Crontab Entry

Using crontab with the -r option will remove complete scheduled tasks without confirmation:

# crontab -r


You can add the -i option to prompt for confirmation before removing the tasks:

# crontab -i -r



Scheduling a Job to Run at a Specific Time using at

To schedule a one-time task (job), to run once at a specific time, use the at utility. The jobs are then executed by the atd service.

# atq

3. Delete the scheduled job by running the command:

# atrm 25

VII.IV Configure time service clients



Configure chrony as an NTP client or server in Linux

In Red Hat Enterprise Linux (RHEL), the chronyd daemon provided by the chrony package is the default NTP client. And it can be configured as a server to provide accurate time to computer systems in your internal network.


The Network Time Protocol (NTP) protocol is a cross-platform protocol designed to synchronize the clocks of computers over a network. It commonly synchronizes a computer to Internet time servers or other sources. Also, it can be used as a time source/server for client systems.


Chrony works both as an NTP server and as an NTP client, which is used to synchronize the system clock with NTP servers and can be used to synchronize the system clock with a reference clock (e.g a GPS receiver). It is also used to synchronize the system clock with a manual time input, and as an NTPv4 server or peer to provide a time service to other computers in the network.


Install and configure the NTP server and client using the chrony package

Test environment:

NTP Server - RHEL: 192.168.69.10

NTP Client - RHEL: 192.168.69.15


Install Chrony in RHEL

1. To install the chrony suite, use:

# dnf install chrony


Note that

● The chrony suite consists of chronyd, and chronyc

● chronyc is a command line interface program that can be used to monitor the performance of chronyd and to change various operating parameters while it is running.


2. To start the chronyd service and enable it to auto start at system boot, use:

# systemctl start chronyd

# systemctl enable chronyd

OR

# systemctl enable chronyd --now


3. To verify the running status of the chronyd service, use:

# systemctl status chronyd


Configure the NTP Server Using Chrony

Procedure to set up your RHEL NTP server as a master NTP time server:

1. Open the /etc/chrony.conf configuration file using a text-based editor:

# vim /etc/chrony.conf


2. Then look for the allow configuration directive and uncomment it and set its value to the network or subnet address from which the clients are allowed to connect:

allow 192.168.69.0/24


3. Save and quit, by typing ":wq" in vim command mode followed by Enter.


4. Restart the chronyd service to apply the recent changes:

# systemctl restart chronyd


5. Open access to the NTP service in firewalld configuration to allow incoming NTP requests from clients:

# firewall-cmd --permanent --add-service=ntp

# firewall-cmd --reload


Configure the NTP Client Using Chrony

Procedure to set configure chrony as a direct NTP client in your RHEL server:

1. To install the chrony package, use:

# dnf install chrony


2. To start the chronyd service and enable it to auto start at system boot, use:

# systemctl start chronyd

# systemctl enable chronyd

OR

# systemctl enable chronyd --now


3. To verify the running status of the chronyd service, use:

# systemctl status chronyd


4. To configure your system as a direct client of the NTP server. Open the /etc/chrony.conf configuration file with a text-based editor:

# vim /etc/chrony.conf


5. Comment out the default NTP servers.


6. Specify the NTP servers your client-server should ask for the current time. You can specify the servers using the server or pool directive:

server 192.168.69.10


Note that

● You can add the iburst option that allows chronyd to make the first update of the clock sooner. For example, server 192.168.69.10 iburst

● The server directive allows you to specify a single NTP server as a time source.

● The pool directive allows you to specify a pool of NTP servers.


7. Save and quit, by typing ":wq" in vim command mode followed by Enter.


8. Restart the chronyd service for the recent changes to take effect:

# systemctl restart chronyd


9. Run the following command to show the current time sources:

# chronyc sources


10. You can run the following command on the server to display information about NTP clients accessing the NTP server:

# chronyc clients


Note that

● To set the hardware clock, use: # hwclock

● To set the system clock, use: # timedatectl  OR  # date

● To select the current timezone, use: # tzselect

RHEL Application Streams

RHEL 8 came with a new feature called Application Streams (AppStreams), where multiple versions of packages are provided, with a known support period. These modules can be thought of as packages that represent an application, a set of tools, or a runtime language.


Each of these modules can have different streams, which represent different versions of the software, giving the user the option to use whichever version suits their needs. Each module will also contain installation profiles, which help define a specific use case, and will identify which packages are installed on the system.


Components made available as Application Streams can be packaged as:

● RPM packages

● Modules

● Software Collections


Note that

● Application Streams are delivered through the AppStream repository.

● Each Application Stream component has a given life cycle, either the same as the RHEL release or shorter.

● Application Streams are available for RHEL 8 and 9.

● New versions of most Application Streams will become available as needed during the Red Hat Enterprise Linux 9 life cycle. 

● Lifecycles will align to the upstream support life or product needs as required.

● Multiple versions of the same Application Stream may be available at the same time with overlapping support durations.


Rolling Streams

● Rolling Application Streams include tools and applications that move very fast and are updated frequently.

● Rolling Application Streams are fully supported for the full life of the RHEL major release.


Dependent Application Streams

● Only dependent application Streams are supported and used by depending Application Streams and are not independent.


Releases and Support

● Red Hat will support Application Streams for the specified lifecycle, after which customers are encouraged to either upgrade to a later release or continue to self-support without official Red Hat support.



Guide to Managing Package Module Streams in RHEL

Modularity and AppStreams

Modularity and AppStreams provide users with access to newer versions of software while being supported for a longer period.


Note that

● Modularity allows a single repository to host multiple versions of an application’s package and its dependencies.

● RHEL 8 & 9 content is distributed through two main software repositories, BaseOS and AppStream.


BaseOS

● The BaseOS repository provides the core operating system content for RHEL as RPM packages.

● The BaseOS components have a similar lifecycle to that of previous RHEL versions.


AppStream

● The Application Stream repository provides content with different life cycles as traditional packages and modules.

● Application Stream contains the necessary parts of the system, as well as a wide variety of applications that were previously available as part of Red Hat's suite of software and other products.

● The Application Stream repository contains two types of content, Modules, and traditional RPM packages.


Module

● A module describes a set of RPM packages that belong together.

● Modules can contain several streams to make multiple versions of applications available for installation.

● Enabling a module stream gives the system access to the RPM packages within that module stream.


Module Streams

● Each module can have one or more module streams, which hold different versions of the content.

● Each of the streams receives updates independently. Think of the module stream as a virtual repository in the Application Stream's physical repository. 

● For each module, only one of its streams can be enabled and provide its packages.


Module Proﬁles

● Each module can have one or more proﬁles.

● A proﬁle is a list of certain packages to be installed together for a particular use case such as for a server, client, development, minimal install, or other. 

● Installing a particular module proﬁle simply installs a particular set of packages from the module stream. Note that, you can subsequently install or uninstall packages normally. 

● If you do not specify a proﬁle, the module will install its default proﬁle.


Managing Modules Using YUM or DNF

● To handle modular content, yum and dnf modules commands have been added. Other than that, yum and dnf works with modules as with regular packages.


Listing Modules

To display a list of available modules, use the yum module list:

$ yum module list  

OR

$ dnf module list  


Let's take an example to show all the options:

# yum install @module: version/profile


● @module - defines which module we are going to use.

● :version - specifies which stream we are going to use for the specified module.

● /profile - tells us which profile to use. If no profile is specified, the default one is used. If no default is defined, then the module is only enabled but no packages are installed.


Note that

● You can use the hint at the end of the output to help determine which streams and proﬁles are enabled, disabled, installed, and which are the default settings.


To list the module streams for the postgresql module and retrieve their status:

$ yum module list postgresql  


To list the packages installed by the default module stream:

$ yum module info postgresql  


To display information about packages installed by each of the module's proﬁles, you can use the --profile option. For example:

$ yum module info --profile perl:5.24



Enabling Module Streams and Installing Modules

Module streams must be enabled to install their module. To simplify this process, when a module is installed it enables its module stream if necessary. Module streams can be enabled manually using yum module enable and providing the name of the module stream.


Note that, only one module stream may be enabled for a given module. Enabling an additional module stream will disable the original module stream.


To install the postgresql module, using the default stream and proﬁles:

$ sudo yum module install -y postgresql  


Note that

● The same results could have been accomplished by running: $ yum install @postgresql  

● This command will install the default, PostgreSQL 10 module.

● The @ notation informs yum that the argument is a module name instead of a package name.


To verify the status of the module stream and the installed proﬁle:

$ yum module list perl 



Removing Modules and Disabling Module Streams

Removing a module removes all of the packages installed by proﬁles of the currently enabled module stream and any further packages and modules that depend on these. 


Packages installed from this module stream not listed in any of its proﬁles remain installed on the system and can be removed manually.


Note that

● Switching the stream enabled for a module is equivalent to resetting the current stream and enabling the new stream. It does not automatically change any installed packages. You have to do that manually. 

● Directly installing a module stream that is different than the one that is currently installed is not recommended, because upgrade scripts might run during the installation that would break things with the original module stream. That could lead to data loss or other conﬁguration issues. 


To remove an installed module, for example (postgresql), use:

$ sudo yum module remove -y postgresql


After the module is removed, the module stream is still enabled. To verify the module stream is still enabled, use:

$ yum module list postgresql 


To disable a module, for example (postgresql), use:

$ sudo yum module disable postgresql



Switching Module Streams

Switching module streams generally requires upgrading or downgrading the content to a different version.


To ensure a clean switch, you should remove the modules provided by the module stream ﬁrst. That will remove all the packages installed by the proﬁles of the module, and any modules and packages that those packages have dependencies on.


To enable a different module stream and install the module, for example ( perl:5.24):

$ sudo yum module install perl:5.24

The new module stream will be enabled and the current stream disabled.

VII.VII Modify the system bootloader



What is a bootloader?

The boot loader is a small program that loads the Linux kernel in memory and executes it.


Why use a bootloader?

It is needed to run the startup process, initialize the hardware, and pass control to the kernel, which initializes the operating system.


What is GRUB2?

GRUB2 is the latest version of GNU GRUB, the GRand Unified Bootloader. Starting RHEL7 GRUB2 is the bootloader. The GRUB2 configuration file is /boot/grub2/grub.cfg.



The GRUB2 Configuration File /boot/grub2/grub.cfg

The GRUBv2 configuration is read on boot from /boot/grub2/grub.cfg. This file is not to be edited by hand but is modified based on the contents of the /etc/default/grub file and the files found inside the /etc/grub.d directory.


You can use the grub2-mkconfig command as root to generate grub.cfg file. This command uses the template scripts in the /etc/grub.d directory and menu-configuration settings taken from the /etc/default/grub file when generating the grub.cfg file.


Note that

● The /etc/grub2.cfg file is a symbolic link to the /boot/grub2/grub.cfg file.



The /etc/default/grub File

GRUB2 menu-configuration settings are taken from /etc/default/grub when generating the grub.cfg file.


To show the contents of the /etc/default/grub file, use:

# cat /etc/default/grub


Example of the grub file output:


GRUB_TIMEOUT=5

GRUB_DISTRIBUTOR="$(sed 's, release .*$,,g' /etc/system-release)"

GRUB_DEFAULT=saved

GRUB_DISABLE_SUBMENU=true

GRUB_TERMINAL_OUTPUT="console"

GRUB_CMDLINE_LINUX="resume=/dev/mapper/rhel-swap rd.lvm.lv=rhel/root rd.lvm.lv=rhel/swap rhgb quiet"

GRUB_DISABLE_RECOVERY="true"

GRUB_ENABLE_BLSCFG=true


Note that

● If you change any of these parameters, you must run the grub2-mkconfig command as root to re-generate the /boot/grub2/grub.cfg file:

# grub2-mkconfig -o /boot/grub2/grub.cfg

OR

# grub2-mkconfig -o /etc/grub2.cfg



Values are described as follows:

● GRUB_TIMEOUT: The time in seconds after the menu is displayed to boot the default entry unless a key is pressed. The default is 5. Set to 0 to boot immediately without displaying the menu, or to -1 to wait until the user makes a selection.

● GRUB_DISTRIBUTOR: Set by distributors of GRUB and is used to generate more informative menu entry titles. The example evaluates to CentOS Linux Server.

● GRUB_DEFAULT: The default menu entry to boot. Requires an integer value that indicates which OS or kernel entry in the GRUB initial screen should be selected to boot by default. A value of 0 boots the first menuentry. A value of 1 boots the second menuentry. A value of saved instructs GRUB2 to load the last successfully loaded operating system. 

● GRUB_DISABLE_SUBMENU: By default, the grub2-mkconfig command generates a top-level menu entry for the kernel with the highest version number and puts all other found kernels or alternative menu entries for recovery mode in a submenu. Setting GRUB_DISABLE_SUBMENU=true disables this.

● GRUB_TERMINAL_OUTPUT: The terminal output device. When specifying multiple devices, separate the valid terminal output names with spaces.

● GRUB_CMDLINE_LINUX: Kernel boot parameters. More information on kernel boot parameters is provided in the next slide.

● GRUB_DISABLE_RECOVERY: By default, two menu entries are generated for each Linux kernel: one default entry and one for recovery mode. Setting GRUB_DISABLE_RECOVERY=“true” disables this.

How to change interface settings?

Previously, NetworkManager stored new network configurations to /etc/sysconfig/network-scripts/ in the ifcfg format. Starting with RHEL 9.0, RHEL stores new network configurations at /etc/NetworkManager/system-connections/ in a key file format. The connections for which the configurations are stored to /etc/sysconfig/network-scripts/ in the old format still work uninterrupted. Modifications in existing profiles continue updating the older files. 


Previously, NetworkManager stored new network configurations to /etc/sysconfig/network-scripts/ in ifcfg format. Starting with RHEL 9.0, RHEL stores new network configurations in /etc/NetworkManager/system-connections/ in a key file format. Connections for which configurations are stored in /etc/sysconfig/network-scripts/ still work without interruption. 


Note that

● While the ifcfg- and key file formats do not have the same syntax, they mostly represent similar data about the interface configuration.

● Modifications to existing profiles continue to update older files.

● You can keep using ifcfg files in /etc/sysconfig/network-scripts, but you need to be aware that, NetworkManager will prioritize key files.



Changing interface settings

Whether you decide to continue using ifcfg-rh files (although this is not recommended) or use key files, you can change interface settings (such as IP addresses) in one of the following two ways with administrator privileges:


1. Tool based

You can use tools like nm-connection-editor (GUI), nmcli (CLI), nmtui (GUI), gnome-control-center (GUI), cockpit (GUI), and nmstate (CLI).


Note that

● nmstate is not installed as a part of the default installation. To install nmstate package, you can use the following command: $ sudo dnf install nmstate -y


2. File based

You can also use a text editor to edit the key file in /etc/NetworkManager/system-connections or the ifcfg-rh file in /etc/sysconfig/network-scripts, and then notify NetworkManager of the changes.


Important

● It is highly recommended to set a static IP address on your Linux system, especially on servers. The main benefit of a static IP address is that it persists across reboots.



Configure IP Networking with nmcli Command

With the nmcli (network manager command-line interface) utility, you can show, create, edit, enable, and disable network interfaces or connections. It is especially useful for servers and systems without a GUI (graphical user interface).

The OBJECT can be:

● Device or network interface.

● NetworkManager’s connection.

● NetworkManager’s stats.

Configuring a static IP using the nmcli utility

Assuming we have a static IP address with the following values:

● IP address: 192.168.69.10/24

● Default gateway: 192.168.69.1

● Preferred DNS: 8.8.8.8, 8.8.4.4

How to Configure IPv6 Network on RHEL?

IPv6 was designed to overcome the limitations of IPv4. It aims to solve IPv4 address exhaustion by utilizing a much wider network address space. An IPv6 address is a 128-bit alphanumeric value that identifies an endpoint device in an IPv6 network consisting of 8 colons separated groups of 4 hex digits each.


An example of an IPv6 address is: 

2001:0db8:85a3:0000:0000:8a2e:0370:7334


Note that

● IPv6 is usually enabled by default on RHEL 8 & 9.



To check if IPv6 is enabled on your system, you can use either of these methods:

First method

$ sudo sysctl -a | grep ipv6.*disable

OR

$ cat /sys/module/ipv6/parameters/disable


The value 0 indicates that IPv6 is active on your node. A value of 1 shows that IPv6 is disabled. 


Second method

On RHEL 8

By viewing your network interface at the /etc/network-scripts/ directory. For example to view the network configuration of the interface enps02:

$ cat /etc/sysconfig/network-scripts/ifcfg-enps02

Then look for the following IPv6 options:

IPV6INIT=yes - Enable IPv6 on this interface.         

IPV6_AUTOCONF=yes - This enables the IPv6 auto-configuration for the interface. 

IPV6_DEFROUTE=yes - This interface is the default route for IPv6 traffic. 

IPV6_FAILURE_FATAL=no - This interface is not disabled if configuration fails.


On RHEL 9

By viewing your network interface at the /etc/NetworkManager/system-connections/ directory. For example to view the network configuration of the interface enps02:

$ cat /etc/NetworkManager/system-connections/enps02.nmconnection

Then look for the following IPv6 options:

[ipv6]

method=auto OR manual

As a system administrator, you can control allowing or restricting network access to some services or IP addresses using the firewalld service.

Enable and Start the firewalld Service

To enable the firewalld service, use:

$ sudo systemctl enable firewalld


To start the firewalld service, use:

$ sudo systemctl enable firewalld --now


To verify the status of the firewalld service, use:

$ sudo systemctl status firewalld



Configuring Rules using Firewalld


Adding a TCP/UDP Port

To add the TCP port (22), use:

$ sudo firewall-cmd --add-port=22/tcp --permanent


To add the UDP port (23), use:

$ sudo firewall-cmd --add-port=23/udp --permanent

To verify:

$ sudo firewall-cmd --list-all


Note that

● You have to specify the protocol type (TCP or UDP) after the port number.

● We use the --permanent flag to ensure that the rules persist after a reboot.


Blocking a TCP/UDP Port

To block the TCP port (22), use:

$ sudo firewall-cmd --remove-port=22/tcp --permanent

What is a multi-user system? 

Linux is a multi-user system. An operating system is considered a "multi-user" if it allows multiple people to use a computer and does not affect each other's "items" such as files and preferences.


To show information about the currently logged-in user, run:

$ id


To show information about a specified user, you can use the syntax:

$ id username


To view the user associated with a file or directory, use:

$ ls -l


By default, systems use the /etc/passwd file to store information about local users. 


To show the content of the /etc/passwd file, use:

# cat /etc/passwd


The format of /etc/passwd follows (seven colon-separated fields):

1. Username: is a mapping of a UID to a name.  

2. Password: is where passwords were kept in an encrypted format. Now, they are stored in the /etc/shadow file.   

3. UID: is the user ID.  

4. GID: is the user's primary group ID number.   

5. GECOS: is usually used to record general information about the account or the user such as the user's real name and phone number.  

6. /home/dir: is the path to the user's home directory.  

7. Shell: is the path to the shell used.



Managing Local User Accounts 


Manage users via command line tools

When managing users via the command line, the following commands are used: useradd, usermod, userdel, or passwd. Affected files include /etc/passwd, which stores user account information, and /etc/shadow, which stores secure user account information.


Create a Local User Account

You can use the useradd utility to create a new user and add him to the system using the syntax:

# useradd [option(s)] username


Note that

● To display the basic options that can be used with the useradd command to override the defaults, use:

$ useradd --help

● In most cases, the same options can be used with the usermod command to modify an existing user:

$ usermod --help


The /etc/login.defs file

Some of the default settings, such as the default password aging rules and the range of valid UID numbers, are read from the /etc/login.defs file.


To view the /etc/login.defs, use:

$ less /etc/login.defs


Note that

● The values in this file are used only when creating new users. Any change to this file will not affect any existing users.


Procedure

1. To create a standard user account with its UID, automatically create a home directory (/home/username/) where default user settings will be stored, and set the default shell to /bin/bash, run the following command at a shell prompt as root:

# useradd username


2. To unlock the account to make it accessible, you need to set the new user password by using the command:

# passwd username


To view created user line in the /etc/shadow file, use:

# grep username /etc/shadow


Note that

● Any UID below 1000 is reserved for system accounts, services, and other special accounts.

● Regular users' UIDs and GIDs are above 1000.

● The root account has the overwhelming privilege of having UID = 0 and GID = 0.

● A User Private Group with the same name as the created user is automatically created.

● The GID of the User Private Group is equal to the UID.

# useradd -M username

# useradd -m -k directory username


The -e option

# useradd -e YYYY-MM-DD username

# useradd -s login_shell username

# useradd -s /sbin/nologin username


Note that

● A user without a login shell cannot log into the system and therefore cannot run any command interactively on the system.

● Make sure there is a nologin shell in the /etc/shells file.


The -u and -g option

You can use the -u and -g options to create a local user account with a given UID and GID by using the syntax:

# useradd -u UID -g GID username


The -G option

Forcing Linux system password changes with the chage command


The chage command

Since password aging requires users to change their password periodically, you can use the chage command to change the user's password expiration information. The syntax is :

# chage [options] username


Some common chage command options include: 

The -d option

You can use the -d option to force a password update on the next login by using the syntax:

# chage -d 0 username


The -l option

You can use the -l option to list a username's current settings by using the syntax:

# chage -l username


The -E option

You can use the -E option to specify the account expiry date by using the syntax:

# chage -E YYYY-MM-DD 


The -m option

You can use the -m option to specify the minimum number of days between password changes by using the syntax:

# chage -m min_number_of_days username

To verify, use:

# chage -l username


The -M option

You can use the -M option to specify the maximum number of days between password changes by using the syntax:

# chage -M max_number_of_days username

To verify, use:

# chage -l username


Also, you can set the minimum and the maximum number of days in one line by using the syntax:

# chage -m min_number_of_days -M max_number_of_days username

To verify, use:

# chage -l username



The /etc/shadow file format

Password expiration information is stored in the /etc/shadow file. The format of the /etc/shadow file follows (nine colon-separated fields):

$ less /etc/shadow


1. Name: is the login name and must be a valid account name on the system.   

2. Password: is the encrypted password. A password field that starts with an exclamation mark means that the password is locked.   

3. Lastchange: is the date of the last password change, represented as the number of days since 1970.01.01.   

4. Minage: is the minimum number of days before a password may be changed, where 0 means "no minimum age requirement."   

5. Maxage: is the maximum number of days before a password must be changed.   

6. Warning: is the warning period that a password is about to expire. Represented in days, where 0 means "no warning given."   

7. Inactive: is the number of days an account remains active after a password has expired. A user may still log into the system and change the password during this period. After the specified number of days, the account is locked, becoming inactive.   

8. Expire: is the account expiration date, represented as the number of days since 1970.01.01.  

9. Blank: is a blank field that is reserved for future use. 



The /etc/login.defs file

The /etc/login.defs file provides default user account settings. Default values include:

● Location of user mailboxes.

● Password aging controls (PASS_MAX_DAYS, PASS_MIN_DAYS, PASS_MIN_LEN, PASS_WARN_AGE).

● Values for automatic UID selection (UID_MIN, UID_MAX).

● Values for automatic GID selection (GID_MIN, GID_MAX).

● User home directory creation options.

● Umask value.

● The encryption method used to encrypt passwords.

To view the /etc/login.defs file, use:

# cat /etc/login.defs


In RHEL 9, you can set the password minimum length using the following procedure:

1. Open the /etc/security/pwquality.conf file in the edit mode:

# vim /etc/security/pwquality.conf

2. Set the minlen value to the required length.

3. Save and quit.


Note that  

● In RHEL 9, the /etc/login.defs file [PASS_MIN_LEN, PASS_MAX_LEN, PASS_CHANGE_TRIES, PASS_ALWAYS_WARN] are not supported.

● In RHEL 9, you can use the /etc/security/pwquality.conf file to set the password minimum length using the minlen variable.

● The /etc/security/pwquality.conf file provides a way to configure default password quality requirements for system passwords. This file is read by the libpwquality library and utilities that use this library to check and generate passwords.



Restricting access

You can use the usermod command to "lock" an account with the - L option.

The syntax is:

# usermod -L username

# usermod -L -e YYYY-MM-DD username

IX.III Create, delete, and modify local groups and group memberships



What is a group in Linux? 

Linux groups are a mechanism for managing a group of users of a computer system. Like users, groups have a name and a number which is a GID. Local groups are specified in the /etc/group file.


To show the groups on your system, use:

$ cat /etc/group


User's Primary Group

Every user has one primary group. For local users, the primary group is a newly created group with the same name as the user and is defined by the GID number which is the same number as the UID, and the user is the only member of this User Private Group (UPG). Normally, the primary group owns new files created by the user. 


Supplementary groups

A user may not be a member of any Supplementary Group and may be a member of one or more Supplementary Groups. Supplementary group membership is used to help ensure that users have access permissions to files and other resources on the system. 


Note that

● The users that are supplementary members of local groups are listed in the last field of the group's entry in the /etc/group file. 



Managing Local Group Accounts

IX.IV Configure superuser access



Gaining Superuser Access

The root user has the power to override normal privileges on the file system and is used to manage and administer the system.


Important

● The root user has unlimited power to damage the system by removing files and directories, user accounts, adding backdoors, and others.

● It is recommended to Log in as a regular user and escalate privileges to root only when needed.



Switching users with the su command 

The su command allows the user to switch to a different user account. If no username is specified, you will be switched to the root account.


To switch to another user account, use the syntax:

$ su username OR # su username

OR

$ su - username OR # su - username


To switch to the root account, use the syntax:

$ su

OR

$ su -


To run a command as root without switching to the root account, use the syntax:

$ su -c ‘command’ 

OR

$ sudo command


Note that

● The main difference between su and su - is that using su - initializes the shell environment as if it was a clean login as the user specified while using su only starts the shell as that user with the current environment settings.

● When running the su username command as root "#", there is no need to enter the account password.



Running commands as root with the sudo command

The sudo command allows the user to be allowed to run the command as root, or as another user, depending on the settings in the /etc/sudoers file.

To view the /etc/sudoers file, run:

# cat /etc/sudoers


The easiest way to give a user sudo access, without modifying the  /etc/sudoers file is to use the usermod command to add the user to the wheel group by using the syntax:

# usermod -aG wheel username

OR

# usermod -aG wheel user_id


To verify that the user is in the group wheel, use:

$ id username

What enables all users in the group wheel to run any command with sudo is that the default /etc/sudoers file contains the following line:

%wheel ALL=(ALL) ALL


Note that

● sudo requires users to enter their password for authentication, not the root password.

● Commands executed using sudo are logged by default to the /var/log/secure file.

● When using sudo, every 5 minutes, you need to type the password once.


Using sudo without a password

You can also configure sudo to not require a password to verify your identity (not recommended).


To do this, you need to edit the /etc/sudoers file as root.

Procedure

1. Run visudo as root to edit the /etc/sudoers file:

# visudo /etc/sudoers


Note that

● The advantage of using visudo is that it will validate the changes to the file.


2. The default /etc/sudoers file contains two lines for the group wheel. Uncomment the NOPASSWD line and comment out the wheel line without NOPASSWD. After making the changes, it should look like this:

# %wheel ALL=(ALL) ALL

%wheel ALL=(ALL) NOPASSWD: ALL


3. Save and quit.


Enable sudo during system installation

During the installation of the RHEL system, you can enable sudo for the user that you created during the installation. By checking the "Make this user an administrator" checkbox on the user creation screen where you enter the username and password. This will make this user a member of the wheel group during installation.

Disallowing Root Access

As an administrator, you have different methods to choose from to disallow root login. Let's take a look at some of them.


1. Changing the root shell

As a system administrator, you can prevent users from logging in directly as root by setting the root account's shell to /sbin/nologin in the /etc/passwd file.


Warning

● Programs that do not require a shell are not prevented from accessing the root account (e.g., sudo, FTP clients, Email clients).


2. Disabling root access using any console device (tty)

As an administrator, you can disable root logins in the console by editing the /etc/securetty file. This file lists all devices that the root user is allowed to log into. If the file does not exist at all, the root user can log in through any communication device on the system. This is dangerous because the user can log into their machine as root using Telnet, which transmits the password in plain text over the network.


To prevent the root user from logging in, remove the contents of this file using the following command as root:

# echo > /etc/securetty


Warning

● A blank /etc/securetty file does not prevent the following programs from accessing the root account: [su, sudo, ssh, scp, sftp]


3. Disabling root SSH logins

To prevent root logins via SSH, use the following procedure:

1. Open the /etc/ssh/sshd_config file in edit mode:

# vim /etc/ssh/sshd_config


2. Change the following line:

#PermitRootLogin yes

to be as follows:

PermitRootLogin no


3. Save and quit.


4. Restart the sshd service:

# systemctl restart sshd


Warning

● Preventing root access using the OpenSSH suite of tools does not prevent the following programs from accessing the root account: [ssh, scp, sftp]

What is a firewall?

A firewall can be defined as a network security system that controls, regulates, protects, filters, or blocks network traffic as it passes in and out of a Linux-based environment.


What is firewalld?

The firewalld daemon is the firewall management tool for Linux operating systems.


What is firewall-cmd?

The firewall-cmd is the command line client of the firewalld daemon. It provides an interface to manage the runtime and permanent configurations.



How to start, stop, restart firewalld service on an RHEL?

The firewalld package is installed by default on RHEL. If not, you can install it using the following command:

# yum install firewalld -y


To start and enable firewalld, use:

$ sudo systemctl start firewalld

$ sudo systemctl enable firewalld

OR

$ sudo systemctl enable firewalld --now


To stop and disable firewalld, use:

$ sudo systemctl stop firewalld

$ sudo systemctl disable firewalld


To check the firewalld status, use:

$ sudo firewall-cmd --state


To show the status of the firewalld service, use:

$ sudo systemctl status firewalld


To reload a firewalld configuration when you make change to rules, use:

$ sudo firewall-cmd --reload


The firewalld components

The main components of a firewalld are:

● Service

● Zone

● Ports


To show the current configurations of the firewall, use:

# firewall-cmd - -list-all


To show the list of services supported by firewalld, use:

$ sudo firewall-cmd --get-services

OR

$ ls -l /usr/lib/firewalld/services/


To show all firewalld zones, use:

$ ls -l /usr/lib/firewalld/zones/

OR

$ firewall-cmd --get-zones


To show services allowed in a specified zone (e.g, public):

$ sudo firewall-cmd --list-services --zone=public


The firewalld predefined zones

● block: Reject all incoming network connections.

● dmz: Classic demilitarized zone (DMZ), provides limited access to your LAN and only allows selected incoming ports.

● drop: Drop all incoming network connections.

● external: Useful for router type of connections.

● home: Useful for home computers. It allows only selected TCP/IP ports.

● internal: Used on internal networks.

● public: Used when you do not trust any other computers and servers on the network.

● trusted: Accept all network connections.

● work: Used for use at your workplace where you trust your co-workers and other servers.


Setting Default Firewalld Zone

X.II Create and use File Access Control Lists (ACLs)


What are ACLs?

ACLs refers to a specific set of rules that you can use to apply a more specific set of permissions to a file or directory without (necessarily) changing the underlying ownership and permissions. They are invaluable for getting finer control over your Linux file system permissions.



Reviewing the basics

The Linux file system has three types of permissions:

● user (or user owner).

● group (or owner group).

● other (everyone else).


With these permissions, we can grant three types of access:

● read

● write

● execute


Viewing the current ACL

To view the current ACL, use:

# getfacl file/directory



Setting an ACL

The syntax for setting an ACL is:

# setfacl [option] [action/specification] file/directory


Note that

● action: You can set and remove ACLs using setfacl, with either the -m or -x options respectively.

● specification: this can be the user or group followed by the permissions you want to set.

● option: you can use the -d (defaults) option to set the default ACL for a file/directory.



List of commands for setting up ACL:

1) To add permission for a user, use the syntax:

# setfacl -m "u:user:permissions" /path/to/file


For example:

To set the ACL for the sample directory as follow:

The user sam has read, write, and execute permissions on the directory sample, use:

# setfacl -m u:sam:rwx sample


2) To add permissions for a group, use the syntax:

# setfacl -m "g:group:permissions" /path/to/file 


For example:

To set the ACL for the sample directory as follow:

The group admin has read, write, and execute permissions on the directory sample, use:

# setfacl -m g:admin:rwx sample


3) To allow all files or directories to inherit ACL entries from the directory it is within, use the syntax:

# setfacl -dm "entry" /path/to/dir

OR

# setfacl -d -m "entry" /path/to/dir


For example:

To set the default ACL for the sample directory as follow:

The group admin has read, write, and execute permissions on the directory sample, use:

# setfacl -dm g:admin:rwx sample


4) To remove a specific entry, use the syntax:

# setfacl -x "entry" /path/to/file


5) To remove all entries, use the syntax:

# setfacl -b path/to/file



To View ACL on a file or directory, use the syntax:

# getfacl file/directory


For example, to view the default ACL info for the directory sample:

# getfacl sample


Note that

● When you set a default ACL to a directory, its contents will inherit the ACL unless overwritten otherwise.

X.III Configure key-based authentication for SSH



What is Secure Shell (SSH)?

Secure Shell (SSH) is a secure network protocol that encrypts traffic between two endpoints. It is the most used remote access protocol in the world. It securely allows users to connect, transfer files, and manage remote devices over a network.



SSH Authentication Methods

SSH uses two authentication methods. 


First method: SSH password-based authentication

It is the traditional method, where you need the username and password for the account you want to log in to anytime you need to access a system. 


Second method: SSH public-key authentication

It is best to use it if you need to connect to several systems regularly. In this method, you generate a public key and a matching private key. The private key file acts as a password and should remain secure. However, the public key is copied to the target systems that you connect to regularly. You put the public key in your account's home directory on the target server. When you try to log in, the keys are verified, and access is granted.



Configure SSH key-based authentication on RHEL

Procedure

Step 1: Generate the SSH Key Pair ssh-keygen without a password

Procedure

1. To generate an SSH key pair, use:

$ ssh-keygen

2. Press Enter to save the (id_rsa) key in the default path.

3. Press the Enter key twice to skip entering the passphrase.



ssh-keygen with a password

Procedure

1. To generate an SSH key pair, use:

$ ssh-keygen

2. Press Enter to save the (id_rsa) key in the default path.

3. Type the passphrase, then press Enter.

4. Type the passphrase again to confirm, then press Enter.


Note that

● Your identification key (id_rsa) and public key (id_rsa.pub) will be saved in your (~/.ssh/) directory.

● You can choose between adding or not adding a password with the private key.

● The generated keys will have the following permissions:

● Private key: 600

● Public key: 644


Step 2: Copy Public SSH Key to Remote RHEL

For this to work, you need to share your public key with the remote machines you are trying to connect to using SSH.

1. To share your public key with the remote machines, use:

$ ssh-copy-id -i ~/.ssh/id_rsa.pub user@destination

OR

$ ssh-copy-id user@destination


2. You will be prompted to enter your user password on the remote machine. Type it, then press Enter.


Note that

● The public key (id_rsa.pub) will be copied to the authorized_keys file in the ~/.ssh directory of the remote user's home directory.

● The destination can be a hostname or IP address.

● In RHEL 9, root login over SSH is disabled or denied by default.



Enable Root Login on RHEL

1. Edit the default SSH configuration using your preferred editor:

# vim /etc/ssh/sshd_config   


2. Set the PermitRootLogin attribute to yes:

PermitRootLogin yes


3. Save and quit.


4. Restart the sshd service:

# systemctl restart sshd


Step 3: Verify SSH Public Key Authentication

To verify SSH public key authentication, use:

$ ssh user@destination


To verify the presence of the authorized_keys file, use:

$ ls -l ~/.ssh

X.IV Set enforcing and permissive modes for SELinux



What is SELinux?

Security-Enhanced Linux (SELinux) is a Linux kernel security module for Linux systems that provides a mechanism for Linux administrators to have more control over who can access the system.


How does SELinux work?

SELinux defines access controls for applications, processes, and files on a system. It uses security policies, which are a set of rules that tell SELinux what can or can’t be accessed, to enforce the access allowed by a policy. 


SELinux Modes

SELinux supports three modes, enforcing, permissive, and disabled. 

● Enforced: In this mode, the security policy is applied. Policy-violating actions are prohibited and a corresponding event is logged in the audit log.

● Permissive: In this mode, the policy is not enforced and therefore access is not denied. Only actions violating the policy are recorded in the audit log.

● Disabled: In this mode, no rules from the SELinux policy are applied and your system is not protected (not recommended).


Note that

● SELinux can be enabled or disabled. When enabled, SELinux supports two modes enforcing and permissive.


What is the default SELinux mode?

Enforcing mode is the default mode.


Viewing SELinux Current State and Mode

To check the current SELinux mode, you can use either the getenforce or sestatus commands.


To show the current SELinux status and the SELinux policy used, run:

$ sestatus


To get the current mode of SELinux, run:

$ getenforce


Note that

● When systems run SELinux in permissive mode, users and processes might incorrectly label file-system objects.

● File-system objects created while SELinux is disabled are not labeled.

● Unlabeled file-system objects or incorrectly labeled causes problems when changing to enforcing mode because SELinux relies on correct labels.


Important

● To avoid problems caused by incorrectly labeled and unlabeled files when changing from the SELinux disabled state to permissive or enforcing mode, you can use either of these ways:


First method:

1. Enable SELinux in permissive mode.


2. Directly create /.autorelabel file as root:

# touch /.autorelabel


3. Reboot the system:

# reboot


Second method:

1. Enable SELinux in permissive mode.


2. Run the following command to create the /.autorelabel file automatically:

# fixfiles -F onboot


3. Reboot the system:

# reboot


Note that

● You need to make sure the system boot in the permissive mode after creating the /.autorelabel file before turning it to enforcing mode to avoid system failure.



Changing SELinux states and modes temporary 

You can use the setenforce command to modify the mode SELinux is running in. The syntax is:

# setenforce [ Enforcing | Permissive | 1 | 0 ]


To set SELinux mode to permissive temporary, use:

# setenforce Permissive

OR

# setenforce 0


To confirm the current SELinux mode, use:

# getenforce


To set SELinux mode to enforced temporary, use:

# setenforce Enforcing

OR

# setenforce 1


To confirm the current SELinux mode, use:

# getenforce



Setting individual domains to permissive mode

You can set individual domains to permissive mode while the system runs in enforcing mode. The syntax is:

# semanage permissive -a domain


For example, to make the httpd_t domain permissive, use:

# semanage permissive -a httpd_t


To view a list of domains set to permissive mode, use:

# semodule -l | grep permissive



Disable permissive domains

To disable a specified permissive domain, use the syntax:

# semanage permissive -d domain 


For example, to disable the httpd_t permissive domain, use:

# semanage permissive -d httpd_t


And to disable all permissive domains, use:

# semodule -d permissivedomains


To confirm the removal, use:

# semodule -l | grep permissive


To see all policy modules, use:

# semodule --list-modules=full


Note that

● Changes made by the setenforce command are only valid until the next reboot.



Changing SELinux states and modes permanently 

To change the SELinux mode permanently, you need to change the SELINUX value in the /etc/selinux/config file as follows:


Switch to permissive mode permanently 

Procedure

1. Open the /etc/selinux/config file in editing mode using your favorite text editor:

# vim /etc/selinux/config


2. Set the SELINUX value to permissive, as follow:

3. Save and quit.


4. Reboot the system:

# reboot


5. To confirm switching to permissive mode, run:

$ getenforce


Switch to enforcing mode permanently 

Procedure

1. Open the /etc/selinux/config file in editing mode using your favorite text editor:

# vim /etc/selinux/config


2. Set the SELINUX value to enforcing, as follow:

SELINUX=enforcing


3. Save and quit.


4. Reboot the system:

# reboot


5. To confirm switching to enforcing mode, run:

$ getenforce


Disabling SELinux

Procedure

1. Open the /etc/selinux/config file in editing mode using your favorite text editor:

# vim /etc/selinux/config


2. Set the SELINUX value to disabled, as follow:

SELINUX=disabled


3. Save and quit.

Enabling SELinux on systems that previously had it disabled

Procedure

5. To confirm switching to permissive mode, run:

$ getenforce


6. Switch to enforcing mode.


7. Reboot the system:

# reboot

$ getenforce

X.V List and identify SELinux file and process context



SELinux Contexts – Labeling Files

A Context in SELinux is defined as information about a process or file from which SELinux can make access control decisions. When running SELinux, all files and processes are labeled with a security context representing security-related information. For files, this context is stored in the extended attributes of the file system. 


Note that

● SELinux problems often stem from mislabeling the file system.

● Access control decisions about processes, Linux users, and files are based on the SELinux context information.


SELinux contexts follow the SELinux syntax:

user:role:type:level


The four SELinux attribute fields:

● User: It is the user's context. Each Linux user is mapped to an SELinux user with an SELinux policy, which is used in the context of SELinux for session processes to define allowed roles and levels. To view a list of mappings between SELinux and Linux user accounts, use:

# semanage login -l

● Role: It is the context of the specified role. The role acts as an intermediary between domains and SELinux users. Defines process domains and the types of files that can be accessed. 

● Type: It flags the type of operation allowed on this object. The type defines a domain for a process and a type of file. To get a list of the available SELinux types, use:

# seinfo --type

● Level (Optional): This entity represents Multi-Level Security (MLS) and Multi-Category Security (MCS). The security levels are defined by terms such as high, low, etc.


Note that

● The SELinux context is a combination of these four features. With their help, SELinux grants or denies access to the file or process to the specified user.

● The most important of these SELinux attribute fields is the SELinux type. Since most target SELinux policy rules use SELinux types to define the permissible interaction between one object and another.


Viewing SELinux Context

SELinux contexts follow the SELinux user:role:type:level syntax.


To view SELinux context for files, use:

$ ls -Z

OR

$ ls -Z filename


To view SELinux context for directories, use:

$ ls -dZ filename


To view the SELinux context for processes, use:

$ ps -Z

OR

$ ps -eZ


To view SELinux context for users, use:

$ id -Z


Note that

● By default, newly-created files and directories inherit the SELinux type of their parent directories.

● SELinux provides multiple commands for managing the file system labeling, such as chcon, semanage fcontext, restorecon, and matchpathcon.


How to List All SELinux Contexts?

To list all the SELinux contexts in RHEL, you can pick any of the following four methods:


Method # 1: Using the semanage command

To list the SELinux contexts for all the files and processes in your RHEL system using the semanage command, run:

$ sudo semanage fcontext -l

You can specify a certain type of content with the help of the grep command:

$ sudo semanage fcontext -l | grep context_type


Important

● This command needs the root user privileges to run.


Method # 2: Using the ls command

To list the SELinux contexts for all the files and processes in your RHEL system using the ls command, run:

$ sudo ls -lZ /root


Important

● To access the root directory, you must have root user privileges.


Method # 3: Using the ps command

To list the SELinux contexts for all the files and processes in your RHEL system using the ps command, run:

$ sudo ps axZ


Important

● This command needs the root user privileges to run.


Method # 4: Using the id command

To list the SELinux contexts for all the files and processes in your RHEL system using the id command, run:

$ id -Z

SELinux File Context

All files and directories get labeled with an SELinux context when running SELinux.


Restore Default SELinux File Contexts

To restore the default SELinux file contexts, use the following syntax:

# restorecon -R file|directory


Make temporary label changes

As part of troubleshooting or testing, we can temporarily change the context.



The chcon command

The chcon command changes the SELinux context of the files temporarily. When using chcon, users provide all or part of the SELinux context to change it. 


To change the file context type, use:

$ chcon -t context_type filename|directory


To change the context type of a directory and its contents, use:

$ chcon -R -t context_type directory


To check the context, use:

$ ls -lZ directory


To switch the context back to the default context type (to relabel), use:

$ sudo restorecon -R -v directory


To check the context, use:

$ ls -lZ directory



Make label changes permanent

To make the changes permanent, use the semanage fcontext command. 

The syntax is:

$ sudo semanage fcontext -a -t context_type directory


To show the context of the newly created files and directories, use:

$ sudo semanage fcontext -C -l


To apply the changes to the context (to relabel), use:

$ sudo restorecon -R -v directory


Note that

● The -a adds a record to the file /etc/selinux/targeted/contexts/files/file_contexts.local

● The -t defines the type.



Remove SELinux Context

To remove the new SELinux context, use:

$ sudo semanage fcontext -d directory


To apply the changes (to relabel), use:

$ sudo restorecon -R -v directory; 


To verify that the context returned to default_t, use:

$ ls -lZ directory


Important

● An incorrect file type is a common cause of SELinux denying access.

X.VIII Diagnose and address routine SELinux policy violations



Policy Violation

Linux has a lot of ways to secure your computer. SELinux is one of these ways. When a policy is written for a particular process, and SELinux is in Permissive or Enforcing mode, all actions that the SELinux policy does not allow will result in a violation.


SELinux Policy Violations Troubleshooting Key Questions

There are a few questions you should have answers to when troubleshooting SELinux policy violations:

● Is this an actual SELinux issue?

● When did this happen?

● Did this issue happen before?

● Can this be a permissions issue?

● Can this be a misconfiguration?

● What do the log files show?


Main Log Files

The main log files for checking system security-related issues are:

● /var/log/audit/audit.log - For SELinux.

● /var/log/messages - For Linux system messages.

● /var/log/secure - For general messages and SELinux messages.


Viewing Log Files

To view any of these log files, use:

$ sudo tail -f log_file 


Note that

● By default, the tail command prints the last 10 lines of the specified file, then terminates.

● The -f option updates the output automatically.



Investigate SELinux Policy Violation

The most common reasons why SELinux denies an action are:

● Incorrect SELinux context labeling of files, directories, and processes.

● Restricted processes are configured differently than expected by the default SELinux policy.

● There is an error in the SELinux policy or process.


Identifying SELinux denials

When SELinux denies an action, an Access Vector Cache (AVC) message is logged to the /var/log/audit/audit.log and /var/log/messages files or the journald daemon logs it. If you suspect that SELinux denied an action that you attempted to do, follow these basic troubleshooting steps.


Troubleshooting SELinux AVC Messages on the Command Line

Because the SELinux decisions, such as allowing or disallowing access, are cached, and this cache is known as the Access Vector Cache (AVC), we use the AVC and USER_AVC values for the message type parameter.

Procedure

1. To query Audit logs, use the ausearch tool to find any recent AVC messages and confirm that SELinux denies the action:

# ausearch -m AVC,USER_AVC -ts recent


Note that

● The -m option specifies the type of information ausearch returns.

● The -ts option specifies the timestamp (e.g., recent, today).

● The -ts recent returns AVC messages from the last 10 minutes.


2. Use the journalctl tool to view more information about the AVC message:

# journalctl -t setroubleshoot --since= [time]

Replace [time] with the time from the AVC message found in the first step. 


Or you can filter logs from journald to show sealert related logs by running the command:

# journalctl | grep sealert


3. Use the sealert tool to perform an additional check of the AVC message:

# sealert -l [message_ID]

Replace [message_ID] with the number of the AVC message. 


4. Perform actions according to suggestions provided by sealert. For example, use the restorecon utility to fix incorrectly labeled files or enable particular Booleans. 


Or run the command # sealret -l UUID for advice on troubleshooting the specific issue (you get the UUID from the result of the command # journalctl | grep sealert command).


5. Repeat the action you attempted to do before SELinux denied it to confirm that the error is fixed.

XI.I Getting Started with Containers



What is a container?

A container is a lightweight executable unit of software that packages code and its dependencies, such as specific versions of the programming language runtimes and libraries required to run the program so that the application runs quickly and reliably across computing environments.


Why use containers?

Containers have many advantages over the previous generation of virtualization technology. It requires fewer system resources because it does not include operating system images. They share the host operating system, applications, and dependencies, so the size of container images is generally measured in megabytes.


Multiple containers can run on the same machine and share the operating system kernel with other containers, each running as separate processes in user space. They are faster, lightweight, and easier to manage and automate than virtual machines (VMs).


What are the pros and cons of containers?

Container Pros:

● Containers are more lightweight than VMs.

● Containers require fewer resources to deploy, run, and manage.

● Containers run fast in milliseconds.

● Containers run as isolated processes in user space.

● Multiple containers can run on the same machine and share the OS kernel with other containers.

● Containers are scalable and portable.


Container Cons:

● All containers must run on the top of the same OS.

● Containers may be less secure than VMs since the underlying OS is shared.


What are container tools?

Container tools are a set of command line tools provided by Red Hat that are used to manage containers. They include:

● podman - for directly managing pods and container images (run, stop, start, ps, attach, exec, and so on)

● buildah - for building, pushing, and signing container images.

● skopeo - for copying, inspecting, deleting, and signing images.

● runc - for providing container run and build features to podman and buildah.

● crun - an optional runtime that can be configured and gives greater flexibility, control, and security for rootless containers.


Note that

● Podman is a daemon-less container engine that runs and manages OCI containers either in root or rootless mode. It uses the same commands and options that are used in Docker.

● Because these tools are OCI-compliant, they can be used to manage the same Linux containers that are produced and managed by Docker and other OCI-compliant container engines.



Getting container tools

To install the container-tools meta-package which contains the Podman, Buildah, Skopeo, CRIU, Udica, and all required libraries, you can use the following procedure:

1. To register RHEL:

# subscription-manager register

Enter your username and password. They are the same as your login credentials for the Red Hat Customer Portal.


2. To auto-subscribe to RHEL, run:

# subscription-manager attach --auto


3. To install the container-tools meta-package, run:

# dnf install container-tools


4. To install the podman-docker package (optional), run:

# dnf install -y podman-docker

XI.II Find and retrieve container images from a remote registry



What is a container image?

A container image is a lightweight, static, independent, executable file that is pulled from the registry server and includes the dependencies needed to run an isolated process on the IT infrastructure as a mount point when the container is started.


Container Image Format

Almost all major tools and engines use the format defined by the Open Container Initiative (OCI). This image format defines layers and metadata within a container image. Manages certain specifications and projects related to container image storage, distribution, and implementation. The OCI image format defines a container image made up of tar files for each layer and a manifest.json file with the metadata.


Working with container images

You can use podman to pull, inspect, tag, save, load, redistribute, and define the signature of a container image.


What are Container Registries?

You can think of a container registry as a place for developers to store and distribute named container images and share them with other systems. The same image may have several different versions, which are determined by their tags located in the same repository.



Public vs. private registries

There are two types of container registries: public and private.


Public registries

Public registries are commonly used by individuals or small teams who want to get up and running with their registries as quickly as possible because they are easy to use, which is why they are so popular among newcomers. Where anyone can push and pull container images.


Private registries

In environments where privacy is a concern, private registries are better suited because they provide a way to integrate security and privacy into enterprise container image storage, whether hosted remotely or on-premises.


Red Hat Registries

The registries that Red Hat provides are:

● registry.redhat.io (requires authentication)

● registry.access.redhat.com (requires no authentication)

● registry.connect.redhat.com (holds Red Hat Partner Connect program images)


Default Registries on RHEL

The default list of registries is defined in the registries.conf file located in the /etc/containers/ directory. In that file, registries are defined by three sections:

● [registries.search] - This section defines the default registries that the podman can search for container images. It searches for the desired image in registry.access.redhat.com, and docker.io registries.

● [registries.insecure] - This section identifies registries that do not implement TLS encryption (insecure registries). By default, no entries are selected.

● [registries.block] - This denies access to the specified registries from your local system. By default, no entries are selected.


Note that

● As a regular user, you can specify the registries.conf file in the $HOME/.config/containers/ directory to override system-wide settings.



Searching Container Images from a Remote Registry

To search a remote registry for a container image, use the following syntax:

$ podman search registry/image


For example, to search for the ubi8 image in the registry.access.redhat.com registry, use:

$ podman search --list-tags registry.access.redhat.com/ubi8


You can also enhance your search with filters. For example, to search for the official httpd image, use:

$ podman search httpd --filter=is-official



Pulling Container Images from a Remote Registry

To get container images from a remote registry, use the following syntax:

# podman pull <registry>[:<port>]/[<namespace>/]<name>:<tag>


● <registry> refers to the remote host or registry that provides a repository of container images on the TCP <port>.

● <namespace> and <name> collectively define a container image based on the <namespace> in the registry.

● <tag> option specifies the version of the container image.


For example, to pull the dotnet-60 image, run the command:

# podman pull registry.redhat.io/ubi8/dotnet-60


The registry.redhat.io/ubi8/dotnet-60 container image is identified by:

● <registry> – registry.redhat.io

● <namespace> – ubi8

● <name> – dotnet

● <tag> – 60


Note that

● If there are multiple versions of the same image, you can add a tag to explicitly specify the image name. 

● By default, Podman uses the :latest tag if no tag is specified.


Listing Container Images

To list the container images existing on your system, use:

$ podman images

XI.V Build a container from a Containerfile



What is a Containerfile?

A Containerfile is a configuration file that automates the steps of creating a container image.


How to Create a Containerfile?

A Containerfile is a simple text file with instructions on how to build your images. To create a Containerfile, use the following procedure:

1. Create a file Containerfile and open it in edit mode:

$ vim Containerfile


2. Press "I" to enter vim insert mode, then add the instructions:


Containerfile popular instructions:

● FROM – This instruction defines the parent image for subsequent instructions. FROM clause must be the first entry in a Containerfile. It can come after a comment. 

● ARG – It defines variables used during the build once you run Docker build command on the file.

● CMD – This sets the command executed upon container creation. When you have more than one command defined, it runs the last command. 

● LABEL – The label instruction defines metadata information for the image. You can add as many labels as you see fit in the form of key-value pairs. For example, image metadata could include the version number, author information, description, etc. 

● RUN – Sets the instructions to be executed during the image build.

● USER – This instruction sets the username or UID of the user when running the image or instructions in a Containerfile such as CMD, RUN, and ENTRYPOINT. 

● ENTRYPOINT – It defines the commands podman executes upon container creation. Options are overridable in the command line during container startup. 

● ADD – This instruction copies files and directories from the specified source to a specified destination. The source can be a local path or an external URL. If the files are archives, podman automatically unpacks them into the image.

● VOLUME – The volume instructions allow you to create mount points from host machine directories or other containers. 

● EXPOSE – This instruction tells podman which port to listen on during runtime. 

● ENV – It sets environment variables.

● WORKDIR – sets the current working directory. If the directory specified does not exist, podman will automatically create one.


3. Type ":wq" in vim command mode followed by Enter to Save and quit.



How to Build a Container Image from a Containerfile?

To build a container image from a containerfile, use either of the following commands:

● The podman build command:

$ podman build -t repository/tag .

● The buildah bud command:

$ buildah bud -t repository/tag .


For example, to build the container image using the local Containerfile, use either of the following commands:

$ podman build Containerfile

OR

$ buildah bud Containerfile


You can use the -t option to specify the name which will be assigned to the resulting image, and the -f option to specify the Containerfile which contains instructions for building the image:

$ podman build -t=imageName -f=Containerfile


To list the available images to confirm the image creation, use:

$ podman ps


Note that

● Buildah is an efficient way to create OCI images, while Podman allows you to manage and maintain those images and containers in a production environment using standard container CLI commands. 

● Podman uses Buildah’s build functionality under the covers to create a container image. 

● The path to the source repository defines where to find the context of the build. 

● The Containerfile and Dockerfile support the same syntax.

● A container image can be built using instructions from one or more Containerfiles and a specified build context directory. 

● The build context directory can be specified as the http(s) URL of an archive, git repository, or Containerfile. 

● If no context directory is specified, then Podman will assume the current working directory as the build context, which should contain the Containerfile. 

● If the URL is a Containerfile, it is downloaded to a temporary location and used as the context. 

● If the URL is an archive, it is downloaded to a temporary location and extracted before being used as the context. 

● If the URL is a Git repository, the repository is cloned locally to a temporary location and then used as the context. 

● The -t option specifies the name which will be assigned to the resulting image if the build process completes successfully. If imageName does not include a registry name, the registry name localhost will be prepended to the image name. 

● The -f option specifies a Containerfile which contains instructions for building the image, either a local file or an http or https URL. If more than one Containerfile is specified, FROM instructions will only be accepted from the first specified file.


To Build an image using a URL to a Containerfile:

$ podman build https://192.168.69.15/podman/Containerfile


To build an image using a Git repository:

$ podman build https://github.com/sample/test


To build an image using a URL to an archive:

$ podman build -f dev/Containerfile https://192.168.69.15/podman/context.tar.gz


Note that

● Supported compression formats are xz, bzip2, gzip, and identity (no compression).


Let's take an example:

Performing a health check using a Containerfile

You can set a health check by using the HEALTHCHECK instruction in the Containerfile using the following procedure:

1. Create a Containerfile:

$ vim Containerfile


2. Add the following instructions:

FROM registry.access.redhat.com/ubi8/httpd-24

EXPOSE 8080

HEALTHCHECK CMD curl http://localhost:8080 || exit 1


3. Save and quit.


4. Build the container and add an image name:

$ podman build --format=docker -t hc-container .


5. Run the container:

$ podman run -dt --name=hc-container localhost/hc-container


6. Check the status of the hc-container container:

$ podman ps


7. Check the health status of the hc-container container using the following command:

$ podman healthcheck run hc-container

XI.VI Perform basic container management such as running, starting, stopping, and listing running containers



Running Container Images

Use the podman run command to run a process in a new container. If the image is not already loaded, the podman run command will pull the image and all of the image's dependencies from the repository before the container starts from that image.

The syntax is:

$ podman run [options] image [command [arg …]]


Popular options used with the podman run command:

● The --attach (-a) option runs the container in foreground mode.

● The --detach (-d) option run the container in the background as a service and print the new container ID. You can reattach a detached container with the podman attach command. 

● The -it option is used to access the shell for interactive processes.

● The -i option creates an interactive session.

● The -t option allocates a pseudo-tty and attaches to the standard input of the container. 

● The -e=env option set environment variables. It allows arbitrary environment variables that are available for the process to be launched inside of the container. If an environment variable is specified without a value, Podman will check the host environment for a value and set the variable only if it is set on the host.  

● The --expose=port option exposes a port or a range of ports.

● The -h=name option sets the container hostname that is available inside the container.

● The --ip=ipv4 option specify a static IPv4 address for the container. This option can only be used if the container is joined to only a single network.  

● The --ip6=ipv6 option specify a static IPv6 address for the container. This option can only be used if the container is joined to only a single network 

● The -l=key=value option adds metadata to a container.

● The --mount=type=TYPE,TYPE-SPECIFIC-OPTION[,…] option attaches a filesystem mount to the container. 

● The --name=name (-n) option assigns a name to the container.

● The --privileged option grants extended privileges to the container. A privileged container is given the same access to the system as the user running the container. Note that, rootless containers cannot have more privileges than the account that launched them. 

● The -p=[[ip:][hostPort]:]containerPort[/protocol] option publishes a container’s port, or range of ports, to the host. 

● The -q option suppresses output information when pulling images

● The --read-only option mounts the container’s root filesystem as read-only. 

● The --restart=policy option restarts the policy to follow when containers exit. The restart policy will not take effect if a container is stopped via the podman kill or podman stop commands. Note that, the --restart option will not restart containers after a system reboot. 



Valid policy values are:

● no: Do not restart containers on exit. 

● on-failure[:max_retries]: Restart containers when they exit with a non-zero exit code, retrying indefinitely or until the optional max_retries count is hit. 

● always: Restart containers when they exit, regardless of status, retrying indefinitely. 

● unless-stopped: Identical to always. The --rm option automatically removes the container when it exits. 

● The --rmi option removes the image unless another container is using it.

● The --stop-timeout=seconds option sets the timeout to stop a container. The default is 10. 

● The --systemd=true | false | always option run container in systemd mode. The default is true. This allows systemd to run in a confined container without any modifications. Note that on SELinux systems, systemd attempts to write to the cgroup file system. Containers writing to the cgroup file system are denied by default. The container_manage_cgroup boolean must be enabled for this to be allowed on an SELinux separated system, use the following command: 

# setsebool -P container_manage_cgroup true 

● The -v=[[SOURCE-VOLUME|HOST-DIR:]CONTAINER-DIR[:OPTIONS]] option creates a bind mount. If -v /HOST-DIR:/CONTAINER-DIR is specified, Podman bind mounts /HOST-DIR from the host into /CONTAINER-DIR in the Podman container. The OPTIONS is a comma-separated list.

● The -w=dir option set the working directory inside the container. The default working directory for running binaries within a container is the root directory (/). 



Listing Running Container Images

Use the podman ps command to list created and running containers. 

The syntax is:

$ podman ps [options]


To list created and running containers, use: 

$ podman ps


To show all the containers created by Podman, use:

$ podman ps -a



Starting Container Images

Use the podman start command to start one or more containers. You may use container IDs or names as input.

The syntax is:

$ podman start [options] container …


For example, to start the httpd container, use:

$ podman start httpd



Stopping Container Images

Use the podman stop command to stop one or more containers. You may use container IDs or names as input.

The syntax is:

$ podman stop [options] container …


For example, to stop the httpd container, use:

$ podman stop httpd


To stop all running containers, use: 

$ podman stop -a


Note that

● This does not include paused containers.

XI.VIII Configure a container to start automatically as a systemd service



Running Containers as Systemd Services with Podman

Running a podman container as a systemd service makes it manageable in the same way other services and features are managed in a RHEL system.


Starting Containers with systemd as root

By setting up a systemd unit file on the host computer, you can make the host automatically start, stop, check the status, and manage a container as a systemd service.


Running containers as a systemd service mean that containers will start automatically when the system boots.


Procedure

1. Pull the image you want to run on your system using the syntax:

# podman pull <registry-URL>/<image-name>


For example, to pull the redis image, use:

# podman pull docker.io/redis


2. If SELinux is enabled on your system, you have to set the container_manage_cgroup boolean to on to run containers with systemd.

# setsebool -P container_manage_cgroup on


3. Run the image as a container, giving it the name you want to use in the systemd service file using the syntax:

$ podman run -d --name <Container-Name> <Image-Name> 


For example, to run the redis image as a container and add a name myredis to it, use:

# podman run -d --name myredis -p 6379:6379 redis


You can combine steps 1 and 3 using the following syntax:

# podman run -d --name container-name <registry-URL>/<image-name>


4. To confirm that the container is running, use:

# podman ps


5. Configure the container as a systemd service by creating the unit configuration file redis-container.service in the /etc/systemd/system/ directory.

# vim /etc/systemd/system/redis-container.service


6. Add the following sections:

[Unit]

Description=Redis container

[Service]

Restart=always

ExecStart=/usr/bin/podman start -a myredis

ExecStop=/usr/bin/podman stop -t 3 myredis

[Install]

WantedBy=local.target


7. Save and quit.


Instead of using steps 5, 6, and 7, you can use the following command to create the unit configuration file redis-container.service automatically:

# podman generate systemd --name redis --files --new


8. To enable the container service to be able to start automatically at boot, use:

# systemctl enable redis-container.service


9. To start the container service immediately, use: 

# systemctl start redis-container.service


You can combine the previous two steps in the following command:

# systemctl enable redis-container.service --now


10. To check the status of the service, use:

# systemctl status redis-container.service


Note that

● To stop the container.service, use:

# systemctl stop container.service



Starting Rootless Containers with systemd

Rootless containers are containers that can be created, run, and otherwise managed by unprivileged users.

Procedure

1. Pull the image you want to run on your system using the syntax:

$ podman pull <registry-URL>/<image-name>

2. If SELinux is enabled on your system, you have to set the container_manage_cgroup boolean to on to run containers with systemd.

XI.IX Attach persistent storage to a container



It is wise to configure permanent external storage for the running containers on the host. Doing this provides a backup in case the container crashes or is accidentally removed.

Procedure

1. To configure permanent external storage on the host, you will need to map a directory on the host to a directory on the container using the syntax:

$ podman run -it -v /HOST-DIR:/CONTAINER-DIR <registry-URL>/<image-name> command --privileged


For example, to amp the host directory /var/lib/containers/backup to the container directory /mnt and start an interactive bash shell, use:

$ podman run -it -v /var/lib/containers/backup:/mnt registry.redhat.io/ubi8/ubi /bin/bash --privileged


Note that

● The -it option is used to access the shell for interactive processes.

● The --privileged option grants extended privileges to the container. A privileged container is given the same access to the system as the user running the container.

● The -v /HOST-DIR:/CONTAINER-DIR option bind mounts /HOST-DIR from the host into /CONTAINER-DIR in the Podman container.


2. Create a sample file /mnt/sample.txt for testing: 

$ echo "Persistent container storage test file" > /mnt/sample.txt


3. To confirm the file creation on the container, use:

$ cat sample.txt


4. To confirm the file creation on the host, exit the container:

$ exit


5. Then run the following command:

$ cat /var/lib/containers/backup/sample.txt
