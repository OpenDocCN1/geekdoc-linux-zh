Chapter 1: Introduction to Kernel

What is Kernel?
For a vehicle, the engine is the most important part; we can’t imagine a vehicle without an engine.  The heart is also the same. A human can live without eyes, legs, and hands but can’t live without “Heart”.
In a computing system, a kernel is the heart of an operating system, and kernel is responsible to manage & run core functionalities and features of an operating system.

Types of Kernel
There are different types of car engines available, VEE, INLINE, STRAIGHT, and more; every type of engine has several different approaches, pros, and cons. Kernels also have a different type; based on purpose and targeted mechanism.  Examples of some kernels are monolithic, micro, modular, and others.
Table 1.1: Kernel type with examples

Micro Kernel
Micro Kernel uses the approach of the ultimate minimum set-up required for scheduling, memory management, and inter-process communication. This type of kernel vastly reduces the amount of memory required for kernel use. But what does it mean by the minimum size of the kernel? The fact of a minimum size of the kernel means that the amount of extra communication required by device drivers reduces the maximum data flow through the kernel, but frankly along with also decreases kernel response time to interrupts.

Monolithic Kernel
Monolithic Kernel type of kernel has all required functionality inside the kernel, in kernel memory space owned by the kernel. For example, schedulers, device drivers, memory management, etc. This type of kernels typically has the highest data throughput of all kernels.

Modular Kernel
Modular kernel merges the good points of kernel-level drivers and third-party drivers. In this type of kernel, some parts of the system core will be located in independent files called modules and these modules can be added to the system at run time. For example, only loading drivers if a device is found. Another example only loads a filesystem if it gets requested.

Exo Kernel
Exo-Kernel type of kernel is the smallest that offers process protection and resource handling.

The relation between Kernel and Operating System
Suppose, think of a house along with two rooms; there is a corridor between two rooms to communicate with.
In a similar pattern, the Operating system works as a house. It has two parts or a room. One for user space programs and other for kernel space programs where system call interface works as a communication channel between them.

Kernel space and protection rings
Kernel space programs have outmost access to system H/W, memory and these should not be accessible by userspace programs; otherwise, disaster will happen. The operating system maintains some protection rings to overcome these disasters.
Here in the following figure, the protection ring architecture of x86 CPU shown. Four levels defined here, from level0 to level3.
Level 0: Protection ring level 0 is the most privileged where kernel space programs run.
Level 1: At protection ring level 1 device driver, the guest operating system resides here.
Level 2: I/O privileged code and other similar privileged code runs at the protection ring level.
Level 3: Userspace programs and libraries run at protection ring level 3. 
Kernel vs. operating system
Kernel
Operating system
The kernel is the core of the operating system.
The operating system consists of user space and kernel space. 
The kernel is pretty smaller in size compared to the operating system.
The operating system is pretty large compared to kernel.
Kernel works as an interface between software and hardware.
The operating system works as an interface between user and hardware.
The kernel works closer to the hardware and it provides low-level services like:
  • System calls
  • Memory management
  • Network management
  • Device driver
  • File management
  • Process management    
The operating system includes applications like user interfaces.
Kernel space vs. Userspace?
Kernel space is the place where the kernel code stored, it executes here and provides its services. On the contrary,  user space is that set of memory locations where user processes run. Userspace processes can access kernel space routines through system calls.
MicroKernel vs. Monolithic Kernel
The two most popular types of kernels are microkernel and monolithic kernel. Here we will discuss differences between them. First of all, services. Services are kept in separate address space in microkernel where in monolithic kernel services are kept in the same address space.  If services are crashed, it does not affect micro kernel core as it runs in separate address space but monolithic core crashes. In microkernel, execute quite slower compared to monolithic kernel.  Microkernels are smaller in size compared to monolithic ones. Another point, microkernels are easy to extend.

Linux Kernel
Linux inherits the “Monolithic” type of kernel.  This kernel was first released by Linus Torvalds in 1991.  The Linux kernel is a relatively small part of the full Linux System and it is the core that is responsible for how well the system will work.  Since 2005, Linux kernel uses the Git source code management system.

Linux Kernel Directory / Source Structure
From the top level of the source tree /usr/src/linux we will see several directories:

arch
  • This part contains all of the architecture-specific kernel code.
  • This directory has further subdirectories, for example, i386 and alpha for one per supported architecture.

include
  • This directory contains most of the include files needed to build the kernel source code.
  • It has also subdirectories for every supported architecture.

init
  • This part contains the initialization code for the kernel.
  • This directory is a pretty important place for developers who need to know how the kernel works.

mm
  • This part holds all of the memory management relevant code.

drivers
  • This directory contains all system’s device drivers.
  • They are further sub-divided into classes of device drivers, for example, block device driver, char device driver, network driver.

ipc
  • This part holds the kernels inter-process communications code.

modules
  • This part used to hold built modules.

fs
  • This directory contains file system code.

kernel
  • This directory contains the main kernel source code.

net
  • This directory contains kernel's networking code.

lib
  • This part holds the kernel's library code.

scripts
  • This part holds the scripts that are used when the kernel is configured.

Chapter 4: Understanding System Call Interface

Introduction to System Call Interface
The system call interface provides a layer between kernel space functions and userspace functions. This layer provides authentication to userspace processes to execute kernel space routines.  In simple words, a system call is just a userspace request for a function or service of kernel space.

Syscalls  / System Calls
Syscalls / System Calls are accessed via a function call. Usually this function calls are defined in the C library. Syscalls accept variety to arguments (zero to many) as input returns a value and performs one or more tasks. Ideally a system call should have exactly one purpose.

System Call Numbers
Each system call is assigned a 32-bit system number, which is unique; and it is used to refer C specific system call. Linux kernel maintains a table called sys-call-table to store all registered system calls.

Parameters in System Call
While calling system calls, it may require to pass parameters to them.  Here, parameters are stored in registers. On x86-32 bit system, the registers are ebx, ecx, edx, esi and edi. But the scenario may happen when more than 5 parameters need to be passed. Then a single register is used to hold a pointer to user-space where all the parameters are stored. And the return value is sent to the user-space also via register.

Advantages of System call
The system call interface approach has couple of advantages. For example,
  • Secured : If userspace processes/programs could directly read and write to the kernels address space, system security will be nullified.  Userspace functions have limited access to the resources/hardware of the system due to implementation of system call.
  • Faster performance : System call interface provides a faster performance to the system.
  • Portability : System call interface makes user space application more portable. Due to any change in the kernel side, userspace programs don’t need to change.
  • Easier Implementation : System call interface makes user space application development easier; here they do not need to think about low-level functionality of the system.

Disadvantages of system call
To develop or implement a new system call, it needs to have a unique system call number officially assigned to you. More pain points, all architecture needs to separately register the system call. So, if you want to implement a simple task, then system call is pretty time consuming and the maintenance quite complex.

Add the new system call into the System Call Table
A table named for 32 bit system is syscall.tbl and in 64 bit systems syscall_64.tbl file.
I edit the table by nano arch/x86/entry/syscalls/syscall_64.tbl and scroll down till I find the number of the last system call before those starting from 512.
In my case, that’s 331. So new system call’s number would be 332.
Now add the following line after the 331st system call.
332 64 hellosys sys_hellosys
Add the new System Call in the System Call Header file
Now edit include/linux/syscall.h and add the following line at the end of the file before #endif statement.
asmlinkage long sys_hellosys(void);

Recompile the kernel
$ make –j4 modules_install install

Chapter 5: Understanding Kernel Module

What is Kernel Module?
To add some functionality to the Linux kernel needs a long and tiresome approach. At first, need to add source file in the kernel source tree. Then compile the kernel. If there is no compile error, then build the kernel. If no build error happens, then reboot the machine to get effected result.
This approach is quite complex and time-consuming. If any system problem occurs, then it becomes hard to debug; because it is really hard to notify in which of the base kernel caused the trouble. Thus kernel development process becomes quite hard to maintain.
To solve this issue Loadable Kernel Module (LKM) feature appeared. LKM was first introduced in kernel version 1.2 in 1995.

What is Loadable Kernel Module?
Loadable Kernel Module is a small piece of software that can be added or removed into the kernel without the need of rebooting system. Loadable Kernel Modules are used to add or modify functionality to the system without performance penalty, time consumption, and system crash penalties.
Loadable Kernel Module works on the current process like statically linked kernel functions.

Advantages of Loadable Kernel Modules
Loadable Kernel Modules are not time wasters. They save a lot of time. Because to add/modify, recompile and build Loadable Kernel Module, we don’t need to rebuild the kernel.
Due to the Loadable Kernel Module approach Linux kernel is still small and easier to maintain.
Another advantage of the Loadable Kernel Module is better memory optimization. When the system booted, all parts of the base kernel stay loaded all the time while Loadable Kernel Modules are loaded when they are needed.

Disadvantages of Loadable Kernel Modules
As Loadable Kernel Modules have higher access permissions to the system, they will become a higher security threat if programs used in the wrong way. Although this security threat can be solvable by allowing only signed modules.

Security concern of Loadable Kernel Module
Several LKM security issue arises. For example, Sangram Gayal explains the Linux kernel privileged process Hijacking Vulnerability.
Rainer Winchmann provides analysis on Linux Kernel Rootkit.
How to minimize these security risks:
-          Buffer overrun is one of the most common sources of security risks in LKM. Proper use of buffer overrun will minimize this risk.
-            Proper input filtering
-            Proper checking of memory initialization and de-initialization
-          Enforcing signed modules : LKMs have full access to a low level and critical kernel space resources, sticking with the signed module option will make the utmost safety.

Chapter 7:
Writing Loadable Kernel Module

Write a simple Loadable Kernel Module
Writing Loadable Kernel Module (LKM) is pretty simple. Every LKM must have at least two functions:
  1. Startup function
  2. End Function
Create a directory called “LKM” inside home directory and then create hellolkm.c inside the LKM directory.
$ cd ~
$ mkdir LKM
$ cd LKM
#include <linux/kernel.h>
#include <linux/module.h>
//// end of header include section
#define __KERNEL__
#define MODULE
#define LINUX
//// end of macro define section
int init_module(void)
{
​ printk(KERN_DEBUG “Hello LKM”);
​ return 0;
}
//// end of init section
void cleanup_module (void)
{
​ printk(KERN_DEBUG “Goodbye LKM”);
}
//// End of cleanup section
MODULE_LICENSE (“BSD”);
//// End of module licensing section
In header include section, kernel.h included for printk() function and moulde.h included to load module into kernel dynamically.
In the macro add section, macro __KERNEL__ added to hide kernel source programs from user space programs.
I have used function init_module(), which works as an initialization function. It prints Hello LKM in the console and KERN_DEBUG macro used. To understand KERN_DEBUG option, please check the debugging chapter.
Then I have used function cleanup_module(), which works as a cleanup or end function of a module.
At the end, MODULE_LICENSE macro used to provide licensing information of this module.
Makefile
Now I will create a makefile to build this module.
$ vi Makefile
obj-m = helloLKM.o
KERNELDIR := */lib/module
WORKNIGDIR := $(shell pwd)
all:
make –c $l
clean:
here kernel directory is the directory of the kernel source.  I have used shell uname –r which search recursively and gets the name of current kernel.
The make –c $(KERNELDIR) “make” will change this directory while building source code and move back to this directory while build finished.
M = $(WORKINGDIR) uses the path of the working directory where the module is located. Here, WORKINGDIR := $ (shell pwd) which means absolute path of current directory.
And, finally, the clean tag which will remove all the generated files.
Now I will compile, build and run the module.
At first, compile
$ make
This command will create module helloLKM.ko in the working directory.
To view information about helloLKM.ko,
$ modinfo helloLKM.ko
Now, I can this load this module, but to do this, I need to change user priority level to superuser. Then I can use insmod or modprobe command to load module.
$ su insmod helloLKM.ko
$ su modprobe helloLKM.ko
To check whether the module loaded successfully, I can check this log.
$dmesg | tail -1
Hello LKM
And you can unload the module
$ rmmod helloLKM
or
$ modprobe –r helloLKM 
To check whether unloaded perfectly, check using dmesg
$ dmesg | tail -1
Goodbye LKM

Initialization and Clean Macro
Before kernel version 2.4, it was mandatory to use init_module() for module initialization and cleanup_module() for cleanup purpose.
But from kernel version 2.4, it is allowed to use any name but we need to use extra macro so that system can understand which one for initialization and which one for cleanup.
static int entrance()
static int out()
module __init (entrance);
module __exit(out);
You can use __init() and __exit() macro before function name.
#include <linux/kernel.h>
#include <linux/module.h>
//// end of header include section
#define __KERNEL__
#define MODULE
#define LINUX
//// end of macro define section
Static int entrance(void)
{
​ printk(KERN_DEBUG “Hello LKM”);
​ return 0;
}
//// end of init section
static int out(void)
{
​ printk(KERN_DEBUG “Goodbye LKM”);
}
//// End of cleanup section
module __init (entrance);
module __exit(out);
MODULE_LICENSE (“BSD”);
//// End of module licensing section

Command-line arguments in LKM
To take command line arguments, LKMs need to use MODULE_PARAM () macro and variables should be called global.
The MODULE_PARAM() macro takes 2 arguments: a variable name and variable type.
There is another relevant macro MODULE_PARAM_DESC() which is used for documenting module arguments. It takes two parameters: variable name and variable description.
Supported data types in command-line arguments
  • Bool
  • Byte (single)
  • Character pointer
  • Array
  • Short int
  • Unsigned short int
  • Int
  • Unsigned int
  • Long int
  • Unsigned long int

Chapter 8:
Kernel Debugging

Oops?
In our conversation, when we utter “Oops”? When something bad happened, right?
Kernel issues an Oops while something bad happened. Oops, the process involves several steps:
  • Step 1: Print error message
  • Step 2: Dumps contents of the register
  • Step 3: Outputs a backtrace
Note: What is Backtrace?
You can say a backtrace is a list of the function call, especially those are active currently in a thread. The common or usual way of inspecting a backtrace of a program is to use outside or external debuggers. But in many cases, it is useful to obtain a backtrace programmatically from within a program.
While an Oops occurs, the kernel tries to resolve the issue and try to resume control of the system. But the kernel is not always lucky to resume control of the system. In several aspects/scenarios kernel cannot control the system for example, when Oops occurred in the interrupt context or in the idle task or init task. In such cases kernel panics, instantly halts the system. If Oops occurred in another context, another process, then kernel kills the process and tries to continue executing.
.

Debugging the kernels issues/bugs
Debugging kernel space issues are quite harder, a lot harder compared to debugging user space applications and libraries. Because on the kernel side, it's quite time-consuming to reproduce the bug or understand the wrong flow of the code or even risky. A minimal mistake can shut down the whole system. To debug kernel side issues, you need a better understanding of the operating system and kernel.
If you can duplicate or reproduce the issue or bug, then it becomes pretty easier to solve the problem. Otherwise, you have to analyze the source code and need to find the flow of the source code.
The bug happens inside the kernel due to many reasons. Common traits are, managing hardware in the wrong manner, incorrect implementation of source code, for example, buffer overrun, etc.

Printing for debugging
While we debug user space programs we use print() or similar method or function. In kernel side, here have a similar kind of function names printk()
The printk() function has been defined at linux/kernel.h library.
  • The printk() function is quite robust – because it is callable from anywhere.
  • Also, it can be called at any time; even it can be called simultaneously on multiple processors where no need the caller to hold a lock.
  • Another important feature of printk() is log level. Before printing the contents of printk() to console kernel checks the log level.

The printk() log level priorities
There are eight (08) priority levels of printk() defined in <linux/kernel.h>. There are listed here
KERN_EMERG
  • A massive and deadly emergency condition, which may related system halt or crash.
KERN_ALERT
  • An urgent issue, which may need immediate action.
KERN_CRIT
  • Critical conditions, often relevant to serious hardware or software failures.
KERN_ERR
  • Error condition for example hardware difficulties, software difficulties are reported with log level.
KERN_WARNING
  • Warning level message.
KERN_NOTICE
  • The current situation may be normal, but still worthy to note.
KERN_INFO
  • An informational message is reported in this log level.
KERN_DEBUG
  • A debug message, generally for debugging purposes this log level used.
Now a question in your mind arises, if you do not specify a log level, what will be happened? The default value of DEFAULT_MESSAGE_LOGLEVEL will be used, which is currently KERN_WARNING.

Loading and Unloading LKMs

Loading and Unloading Linux Kernel Modules (LKMs) on demand
Linux kernel has an amazing feature, it can automatically load and unload LKMs which helps to avoid wasting of kernel processes and memory. But to use this support or feature, we need to enable kmod module when we configure the kernel before we compile it.
Most of the distributions like Redhat, Debian, Ubuntu, CentOS, etc. comes with kmod enabled. The kmod feature or support comes with libkmod.so library.
Contents of libkmod library
-           insmod
-           rmmod
-           depmod
-           modprobe
-           modinfo
-           lsmod
-           kmod

insmod
insmod being used to insert a module into the Linux kernel.
Note: insmod requires passing it the full pathname and list of modules (dependent modules) in the right order. If we consider nfs.ko, it requires the following module with the relevant order.
  1. nfs_common.ko
  2. auth_rpcgss.ko
  3. fscache.ko
  4. lockd.ko
  5. sunrpc.ko

rmmod
The rmmod unloads a module from the Linux kernel. If we want to unload or remove a module then we have to run the following command:
$ rmmod modulename
For example, we have a module vfat, we need to unload it. Then command will be
$ rmmod vfat
Note: There is another way to unload or remove module in Linux kernel. That is modeprobe –v –r. Here for removing vfat, the command will be
$ modprob –v –r vfat
Where, r is the short form of remove and v for verbose.

depmod
The depmod works with existing sets of modules. It creates a dependency file based on the symbols it find in the existing sets of modules mentioned in the command lines or from the directories specified in the configuration file.
The depmod creates a “Makefile” like dependency file, which is used by modprobe to automatically load the correct module or stack of modules.
Note: The depmod file can be found at /lib/modules/kernel-version/modules.dep

modinfo
The modinfo program shows information about a Linux kernel module. It shows the following information regarding each module:
  1. Module author
  2. License
  3. Parameters
  4. Dependencies
  5. Module description
  6. Full path of the module along with the file name

lsmod
The lsmod program shows the kernel modules currently loaded by Linux system or Linux kernel system. It shows these data or contents by analyzing /proc/modules.
The lsmod program shows the following information:
  1. Name of the module
  2. Size of the module in byte, not how much memory used in kernel.
  3. Each module use count and a list of referring modules.

modprobe
The modprobe program adds or removes a module from the Linux kernel. It looks at the modules directory /lib/modules for all the modules. The modprobe program expects the up-to-date module.dep file which is generated by depmod.
How it works? Just call
$ modproble module_1
This command loads module_1 in kernel.

How kmod works?
What happens while Linux kernel tries to access certain modules or resources but gets those resources unavailable? Does kernel return an error instantly? No. Instantly kernel does not return any error rather, calls kmod. While kernel calls kmod, it tries to load dependent modules and tries to make the resources available.
If kmod gets success, then no problem, the Linux kernel continues working. But if kmod fails, then Linux kernel returns an error.
The beautiful thing is, any kernel space programs can request to load any LKMs by calling kmod. But to use kmod, programmers need to include <linux/kmod.h> in their kernel module to get this functionality. And to request a module to be loaded, programmers need to call request_module function.
int request_module (const char *module_name);
Couple of things we should know about this request_module function:
  1. The request_module function is asynchronous
  2. The request_module function returns negative number on failure or zero on success.
  3. The caller modules must check that the service they requested whether is now available, programmers should not blindly invoke it.
  4. And more importantly, if module auto-loading support is disabled, then this request_module function becomes a no-operation.

Introduction to Device Drivers

Introduction to device driver
Most of the Linux kernel’s source code are in its device drivers. The drivers directory contains all of Linux’s device drivers source codes. This directory has the following parts
  1. /block
    • The block device drivers resides here.
    • Block devices include both IDE and SCSI based devices.
  2. /char
    • The char device drivers resides here. Example, tty.
  3. /cdrom
    • In this directory all of the CDROM code for Linux resides.
  4. /pci
    • PCI pseudo-drivers resides in this directory.
  5. /scsi
    • All of the drivers for the scsi devices supported by Linux resides here.
  6. /net
    • Network device drivers resides here.
  7. /sound
    • All sound card drivers resides here.

What is device driver?
A device driver is ultimately designed and developed to control or operate a specific type of hardware that is attached with the system. In other words, device driver consists of a bunch of source code which tells the system how to communicate, operate or control hardware. The kernel uses device driver to control or communicate hardware without knowing any details of the hardware, for example, how hardware operates. A device driver uses bus system of the computer to communicate with the device or through other communication system to which the hardware being connected.

When a kernel calls device driver?
  • To check whether the device available or not.
  • To handle device specific input/output calls.
  • To perform user space requests to the sysconfig utility.
  • To check whether data is ready or not through handling interrupts.
  • To set/reset and initialize/reinitialize the device.
  • To perform Input / Output operations from user space standard library Input / Output calls.

Device driver working procedure with User Space, Kernel Space and Hardware Space:
  • In user space, any source program or library are unable to communicate with hardware directly, so they make calls to the kernel space source programs.
  • Although kernel has the supreme power mode in the system, kernel doesn’t try to access hardware directly, rather kernel follow a convention. Kernel uses device driver to communicate with hardware.
  • A device driver in kernel space, responsible to communicate with the hardware or device, for example, opening the device, reading and writing to the device through a bus to peripheral device registers and then closes the device.
  • In hardware space, a bus works as a transmission path or communication path along with access protocols between the processor and device controller. When a device driver reads data from or writes data to the hardware registers of a controller, the data travels across the bus. 
  • In hardware space, a controller works as a physical interface for controlling one or more devices.

Every device driver contains two numbers: major number and minor number. The major number is used to distinguish the driver and same major number used to indicate that it is controlled by the same driver.
Using different minor number, multiple device drivers can be created in one drive. The major number and minor number, both numbers are being used to determine a device driver together.

brw-rw----  1 root disk 9,   0 May 17 10:15 sda

Here, the major number of sda and sda1 is 9, and minor numbers are different, 0 and 1.

Any interface under /dev/xxx “everything is about file”, so the operation of the device driver is actually the operation of the file.
The APIs of a device driver we can think all about file operations and the device driver is used to define/open/read/write etc. functionalities.

Indentation
One of the most important rules, as tabs are 8 characters long, so indentations will also be 8 characters long. 
Now, some programmers will claim that having 8-individual indentations makes the code move too far to the right, and makes it difficult to examine on an 80-individual terminal screen.
The solution to that is that if you need extra than 3 degrees of indentation, you need to repair your source code.
The 8-char indents make things simpler to read, and feature the added advantage of caution you when you’re nesting your functions too deep.

case '6':

​ break;

case '8':

-           In a single line don’t do multiple assignments. Kernel coding should be super simple, easier to read, and understand.
-           Make your expressions easy to understand.
-           Don’t leave whitespace at the end of the line.
-           In a single line don’t put multiple statements.

Breaking long lines
It is strongly preferred that you should limit the length of lines to 80 columns. Never break this rule.
Any statement longer than 80 columns must be broken into several parts, exception: exceeding 80 columns significantly increases the readability of your source code and does not hide any information.

Placement of spaces
-          Use a space after keywords (exceptional keywords those look somewhat like functions and usually used with parentheses, for example, alighnof, _attribute, sizeof, typeof)
-           Don’t use spaces inside parenthesized expressions.
use a space after these keywords:
case, for, do, while, do while, if,
but not with sizeof, typeof, alignof, or __attribute__. E.g.,
s = sizeof(struct file);

C styling placement of braces are highly suggested.
if ( input > N) {

input + N;

and

Naming Local and Global Variables
C programmers do not use a cute name like Pascal and Modula-2 programmers. While Pascal programmers use VariableTemporaryCounter, c programmers use tmp. Compared to VariableTemporaryCounter, the tmp variable name is much easier to write and not hard to understand.
In C, local variables should be short, easy to write, and simple. For example, tmp can be any type of variable that holds temporary value. For the integer loop counter, you don’t need to use loop_counter_integer; rather i is enough.
For global variables, you need to use a descriptive name. For example, count_active_students are suggested, not cntastu.

Functions
Functions will do just one thing and will do that well, and functions name should be short and sweet.
Include parameter names with their data types in function prototypes; it is preferred in Linux although it is not required by the C language. Why it is preferred in Linux? Because it is a pretty simple way; to add valuable information for the reader.
How many local variables you should declare in a function? They should not exceed 5 ~ 10. If you need more variables then this suggestion, then re-think the function and split it into more functions.
Early research found the working memory cut-off to be about seven items, but recent research shows that mind’s limit four things at once. This study published in the journal Proceedings of the National Academy of Sciences.
Functions should have one blank line before the next source code. (Exceptional: EXPORT macro. It should follow immediately after the closing function brace line).

Comments are good, you can tell WHAT your code does, but you should not comment HOW. It is a waste of time to explain your badly written code in your comment; rather it’s much better to write the self-explanatory code.
Write comments at the head of the function, where you should tell people what the function does.
The preferred style for long (multi-line) comments is:
/*

*

The use of comment for data is extremely important, whether the data are basic types or derived types.
Use just one data declaration per line, don’t use multiple data declaration per line. This approach you to provide small comments on each item, explaining the data and it’s used.

Macros and Enums
Macro names defining labels in enums, constants should be capitalized.
#define MAX 999
More rules regarding macros
-           Macros resembling functions may be named in lower case.
-           Macros with multiple statements preferably enclosed in a do-while block.
-           Macros should not affect control flow.

Printing kernel messages
-            Make your kernel messages clear, unambiguous, concise, and simple.
-            Kernel messages should not have to be period terminated.
-           Make your kernel messages matched with the right device and driver, and also tagged with the right level (error level, warning level, and information level). For example, dev_err(), dev_warn(), dev_info().
-            A good debugging message can be a huge help for remote troubleshooting.

Memory allocation
Linux kernel provides a couple of general purpose memory allocators:
-           kmalloc()
-           kzalloc()
-           kmalloc_array()
-           kcalloc()
-           vmalloc()
-           vzalloc()
In these memory allocators, the preferred form of passing a size of a struct is the following:
p = kmalloc(sizeof(*p), …);
