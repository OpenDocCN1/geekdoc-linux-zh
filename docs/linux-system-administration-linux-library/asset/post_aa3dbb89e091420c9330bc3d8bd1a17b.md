
The dump commands for the Sunday would be something like this, assuming you need to back up /, /usr, and /var to a SCSI tape unit at /dev/nst0:

```
# dump out /dev/nst0 /
# dump out /dev/nst0 /usr
# dump out /dev/nst0 /var
```

The dump commands for each of the remaining days of the week would look like this:

```
# dump 5uf /dev/nst0 /
# dump 5uf /dev/nst0 /usr
# dump 5uf /dev/nst0 /var
```

You could also use any non-0 dump level for the incremental backups. A level of 5 gives you the flexibility of performing an unscheduled differential backup by using a higher level, should there be some critical files to back up. You can also perform an incremental backup that resets the normal incremental file count should you make a lot of changes early in the week that you don't want to subsequently back up. Of course, if you deviate from your usual backup schedule, you should carefully label your tapes to prevent confusion.

## Dumping Remotely

It's possible to specify a remote backup server with dump by modifying the form of the dump device filename. Instead of a simple device file, you must specify the backup server's name, a colon, and the device filename on that server, thus:

```
# dump out server:/dev/nst0 /usr
```

On some networks, though, this can result in a slow backup. A better option might be to pipe the backup through rsh:

```
# dump out -usr | rsh server
```
this is that the backup server must be running rsh (or .rsh), the remote shell daemon. This utility has great potential as a security problem, particularly on any system that's connected to the Internet. What's worse, you must normally run rsh with the -h parameter to allow root access, which increases the potential for security problems. On the whole, it's best to use this access method only when the backup server is well-protected behind a firewall. Ideally, the backup server should have no other network duties, should have no users aside from those necessary to maintain it, and should be devoid of any software that a cracker might find useful in penetrating the network, should the worst occur.

Historically, remote use of dump has been through a separate rdump utility. On most Linux systems today, rdump is a symbolic link to the ordinary dump utility, which has acquired dump's network functionality.

## restore

Use the restore utility to extract a backup that was made with dump. restore has two modes: interactive and noninteractive. The interactive mode allows you to select one or more files to restore, while the noninteractive mode restores the entire backup. You must use a nonwinding tape device if you have multiple archives.

### Restoring Interactively

Let's assume you need to restore /usr/local/bin from the backup we made earlier with dump. Load the appropriate backup tape and run the following command:

```
# restore -i -f /dev/nst0
```

The -i flag tells restore to start an interactive session. When this command executes, you will get a restore> prompt. Use the ls command to select files to restore.

```
restore> ls
```
Since we know the directory exists, we can add what we want to:

```
restore> add
```

### Noninteractive Restore

To restore in batch, first change the location where you want. If the tape contains multiple archives, you may use the -s option. For example,

```
restore> extract
```
this is on the tape.
