# Configuring POP and IMAP

Fortunately, setting up the POP and IMAP protocols is not very difficult. Compared to sendmail, the POP and IMAP servers require very little in the way of configuration. If you're building a departmental mail server, though, you may need to configure user accounts, and this may require some thought. It's also possible to use a Linux system as a POP or IMAP client. In many cases, you do via MUAs; however, there's a special program that lets you grab POP or IMAP mail and serve it through a regular Linux mail queue.

# Running POP and IMAP Daemons

The first step to running POP and IMAP is to install the appropriate server package. In Red Hat 7.0, it's called imap-4.7c2-12, and it includes servers for both POP and IMAP. Other distributions ship with similar packages.

> NOTE Just sendmail isn't the only SMTP server, the POP and IMAP servers included in the imap-4.7c2-12 package aren't the only POP and IMAP servers. You'll likely need to look for an alternative if you use qmail as your MTA, because qmail stores e-mail in different locations than do most other MTAs, which confuses POP and IMAP servers. The gmail Web site links to alternative POP and IMAP servers that work with qmail. Exim and Postfix are compatible with the standard imap package, however.

The POP and IMAP daemons are normally run from a super server, as described in Chapter 15. Red Hat 7.0 and Mandrake 7.2 use the inetd server, but most other distributions in 2001, as well as earlier versions of Red Hat and Mandrake, use inetd. The configuration of these programs differs.

If your distribution uses inetd, the /etc/inetd.conf file probably contains the following lines relating to POP and IMAP servers:

```
pop-2 stream tcp nowait root /usr/sbin/tcp ipop2d
pop-3 stream tcp nowait root /usr/sbin/tcp ipop3d
imap stream tcp nowait root /usr/sbin/tcp ipapd
```

Chapter 15 includes a discussion of the /etc/inetd.conf file format. For the moment, though, it's sufficient to know that these three lines indicate servers for POP-2, POP-3, and IMAP protocols. Whenever a connection is attempted to the appropriate port, inetd launches the ipop2d, ipop3d and imamd programs to handle the task.

By default these three lines are commented out—that is, they're preceded by pound signs (#) to deactivate the servers. Once you've installed a POP or IMAP server, you must do two things to activate it if you're using inetd:

- 1. Uncomment the appropriate server lines in /etc/inetd.conf. For example, if you want to use IMAP but not POP, uncomment only the imap line.
- 2. Restart inetd by typing /etc/rc.d/inetd restart.

If your distribution uses xinet rather than inetd, the procedure is somewhat different. Both Red Hat and Mandrake ship with imap packages that install xinet start-up scripts in the /etc/rc.d/xinet directory. These scripts are called imap, imaps, ipop2, ipop3, and pop35. The script name that is end for secure versions of the protocols, which use encryption to protect the password from sniffing. By default, all of these protocols are disabled when installed. To enable one or more protocols, follow these steps:

- 1. Open the script corresponding to the protocol you want to enable in a text editor and edit the line reading disable = yes so that it reads disable = no. Save the file.
- 2. Repeat step 1 for any additional protocols you wish to.
- 3. Restart xinetd by typing /etc/rc.init/xinet restart.

Once you've done this, your system will be configured as a server for whichever pull mail protocols you've selected. You can test the server by using an appropriate MUA on another computer or by using a Telnet program to test the server manually, as shown in Listings 17.2 and 17.3.

# Setting Up Mail-Only Accounts

Ordinarily, Linux accepts mail only for recipients who have an account on the server. For example, if mail is addressed to nemo@pony.express.com, and if pony.express.com has no user called nemo, the server bounces the mail—the sender receives back a message that includes an error message stating that nemo isn't a valid recipient. Therefore, you must normally create user accounts for all e-mail recipients, even if the computer is used only as a mail server.

> **NOTE** There are exceptions to this rule. For instance, it's possible to configure mail aliases, where one e-mail address corresponds to a different username.
Most systems preconfigured with certain aliases for critical accounts such as postmaster, which is the user responsible for mail server configuration.

If a computer is to function as a mail server from which users access their mail only using a pull mail protocol, and if you don't want to grant users access to the system using normal command shells, you should adjust users' /etc/passwd entries so that the shells point to something useless. A normal user's /etc/passwd entry looks something like this:

```
george:x:502:100:George W. :/home/george:/bin/bash
```

The final component of this line—/bin/bash in this example—tests Linux what to run when the user logs through Telnet or SSH, or at the console. You can change this entry to something that won't grant you useful access, as /dev/null or /bin/false. The account becomes useless for shell access, but it can still be used for pull mail retrieval.

> **TIP** Instead of specifying a completely useless program as a shell, you may want to specify the passwd program. Doing so allows users to change their passwords by using a Telnet or SSH program to log on to the server. Once the password has changed, it is immediately logged off.

If you use a utility such as useradd to create accounts, you can create them using “dummy” shells to begin with. With useradd, use the -s parameter to specify the shell, so you can add -s /dev/null to create an account that uses /dev/null for its shell from the start. If you prefer GUI configuration tools, you may be able to accomplish the same goal. In fact, Red Hat's Linuxconf includes an option to create mail-only accounts, as shown in Figure 17.2.
