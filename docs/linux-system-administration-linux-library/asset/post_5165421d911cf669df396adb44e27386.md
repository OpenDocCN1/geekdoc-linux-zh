
# X Concepts

The terminology of the client/server relationship is confusing to most Linux newcomers, because most people think of servers as running on powerful computers that are located remotely. In most cases, it's the client that runs on the computer at which the user sits. This relationship is reversed in the case of X. To understand and remember this, it's helpful to think about it from the application's point of view. To the X, the server provides network services, just like a file server or Web server. The fact that there's a human seated in front of the X server is irrelevant to the program.

NOTE one product, the Virtual Network Computing (VNC) server (http://www.uk.att.att/vnc/), can be used to remotely access a Linux computer as much as can be done through an X server. In VNC's model, however, the server runs on the same computer as do the X programs; the user runs a small program that communicates with the VNC server. Effectively, VNC adds an extra layer to the line of communications, in the process reversing the X client/server relationship that it's more intuitively reasonable to most users.

Even if you use X locally, on a single computer, the network-centric design of X has important consequences. These include:

- X can be configured to use a font server (briefly described) to handle font rendering. Some distributions, including Red Hat 7.0, use a font server by default. You can, however, use a single font server for all the computers on your network, which can simplify font administration.

- All network servers, X uses assorted security measures. On some distributions (but not Red Hat), you may find that you cannot run X-based programs if you use su to acquire root privileges. If your security is lax, users of other computers may be able to sniff on your display or display their own programs on your screen.

- X properly relies upon certain environment variables to tell what display to use. These variables are normally set correctly in Linux installations, but these settings may become damaged. You must also change them if you want to use a remote display.

- X is typically slower than any GUI environments. The need to process display data through network protocols, even when the display is local, causes some slowdown. This effect can be quite modest on modern hardware, but you might notice it with some applications or on older hardware.

On the whole, X's network-centric nature makes for a great deal of flexibility in a network environment. You can run the same programs from many computers, while running these programs on just one computer. The complexity and speed hit of X can be a drawback on an isolated workstation, however.

# X Security

If you're using X only locally, chances are your distribution has configured X in a reasonable way. On some distributions, however, you may need to loosen security a bit if you want to use X programs after you've used su to acquire root privileges. If you want to run X programs remotely, you'll need to make a couple of adjustments.

To use an X server, the client computer has to know which X server to use. This is done by the DISPLAY environment variable, which you can set using the following command (assuming you're using the bash shell):

```bash
$ export DISPLAY=hostname:displaynum
```

In this command, hostname is the name of the computer on which the X server runs (that is, the computer at which you're sitting), and displaynum is the number of the display. displaynum is normally 0 or .0 for the primary X display, but it may be a higher number if the computer runs multiple X servers, as described shortly in "X Virtual Consoles." It's important to realize that you issue this command on the computer that holds the X programs you intend to run, not on your local computer.

Most X servers are configured by default to refuse connections except from the local system. Some distributions also refuse connections except from the user who's logged on locally. When this happens, you won't be able to use X programs after you use su to acquire root privileges. There are various ways to tell X to be more lenient in connections it accepts. The simplest is to use the xhost command, which uses the following syntax:

```bash
xhost [hostname]
```

To add a client to the list of allowed hosts, use +hostname; to remove a client, use -hostname. If you omit the hostname, the X server accepts or refuses all connections, no matter the client. Unlike the DISPLAY environment variable, this command must be issued on the X server—the one at which you sit.

TIP If you regularly run programs on a variety of Linux computers, you can add appropriate xhost commands to your .xsession or other startup file (described later) to allow these connections by default. You can use localhost as the hostname. As an example, consider the following: you're sitting at localhost and want to run a program located at remote. Assuming both computers are Linux or Unix boxes, you would follow these steps:

1. Log in to remote.
2. If X isn't already running, start it by typing startx.
3. Issue the command xhost +localhost.
4. Use Telnet or Secure Shell (SSH) to log in to localhost from remote.
5. Type export DISPLAY=remote:0.
6. Run whatever programs you want to run using localhost.
7. When you're done, type xhost -remote to remove localhost from host.

If your computer sits behind a firewall, especially one that uses IP masquerading, you may not be able to follow these steps because the client won't be able to reach the firewall to connect to your X server. There are two common workarounds to this problem:

- Use VNC, mentioned earlier, which reverses the client/server configuration so the server falls outside the firewall. Assuming the firewall doesn't block VNC connections, you can use a local VNC client and run the VNC server on the remote system. Use VNC documentation for details of its use.

- Use SSH can be configured to tunnel X connections through its own connection. When this happens, the SSH server looks for X connection attempts from local programs and passes them to the system on which the SSH client (and X server) runs. When properly configured, this works automatically, so skip steps 3, 5, and 7 from above. If this doesn't work initially, check the file /etc/ssh/ssh_config on the client; its Forward11 line should read yes. The server /etc/ssh/sshd_config file should include a line that reads Forward11 yes.

# Virtual Consoles

Chapter 10 described the use of virtual consoles for text-mode logins. If you use a text-mode login, you can hit Alt+F1 through Alt+F6 to switch between different screens, each of which can display a different login session. You can therefore use one to log in with your normal username, another to log in as root; and log in multiple times as one user and switch easily between different programs. If you are running X, you can switch to a virtual text-mode console by pressing Ctrl+Fn, where n is the console number.

Virtual consoles are not restricted to text-mode logins. When X runs, by default, it takes over an unused virtual console (typically console 7). You can therefore switch back to X from a text-mode console by pressing Alt+F7 (if X is running). Of potentially greater interest, it is possible to run multiple X sessions, each in its own console. You can switch between them by pressing Ctrl+Alt+Fn, where n is a number from 7 up. To launch a second X session, follow these steps:

1. If you're already running X, press Ctrl+Alt+F1 to go to a text-mode login prompt. Log in.
2. Type startx :1 vt8 to start X on virtual terminal 8. You should see X up.
3. Press Ctrl+Alt+F7 to switch back to your original X session or Ctrl+Alt+F8 to switch to the new one.

Why would you want to start a new X session? After all, window managers support multiple workspaces, so you can easily keep lots of windows on different screens. You can use su within an xterm to launch programs as different users. Using multiple X sessions has certain advantages, however:

- You can run different window managers in different sessions. This isn't ordinarily a compelling reason to run multiple sessions, but it can be useful if you want to evaluate a window manager or if you need to use one for some programs and prefer another over other programs.

- You can start X in different resolutions. Your normal setup might be 1280x1024 resolution, but if you need to test software at 800x600, you can run a separate 800x600 session. You can use the -bpp (for XFree86 3.x) or -depth (for XFree86 4.0) parameter to startx, along with an appropriate XF8Config setting (as described above), force X to start at a given resolution when you start at a given bit depth. For example, the following command starts XFree86 4.0 at 32-bit color depth, which you can associate with a specific resolution:

```bash
startx :1 -depth 32
```
