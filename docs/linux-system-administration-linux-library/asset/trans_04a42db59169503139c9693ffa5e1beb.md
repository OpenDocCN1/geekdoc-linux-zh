# 检查操作系统更新

软件安装中一个特别关键的方面是保持系统处于最新状态。正如本文所述，操作系统更新对于保持您的系统安全且无错误至关重要。大多数发行版供应商都维护网页或 FTP 站点，你可以从那里下载操作系统更新，还有其他网站可以让你检查以获取更新的软件。

# 操作系统更新的重要性

1999 年底，人们发现了一个名为 DNS 服务器的漏洞，它运行在许多 Linux 系统上并包含在 BIND 包中。该漏洞允许任何具有相应知识的人入侵运行该服务器的计算机并获取 root 权限。在接下来的几个月里，无数系统被攻破，因为脚本小子（知识匮乏但运行预包好的入侵脚本的恶少年分子）入侵了在许多版本 Linux 版本上运行标准 BIND 包的计算机。然而，在这一时期的大部分时间里，修复后的 named 版本在这些发行版的网页上是随处可见的。如果管理员能花五分钟定位、获取并安装更新后的服务器，他们将节省数小时重建被攻破系统的沮丧时间。

当然，现在的 Linux 发行版不再分发那个受损的 named 版本；它们的软件包已经更新并修复了该漏洞。这个故事的重点并不是 1999 年的 named 版本不可信；而是人们必须防范事实：重要的程序有时包含会打开系统安全漏洞的漏洞。你可能在明天今天运行的服务器上发现安全问题。如果你的系统曾连接到互联网，在那种情况下，它极有可能被攻破。（许多运行适当监控软件的系统管理员在 2000 年初和中期显示，其 DNS 端口遭受的探测数量异常，其中大多数尝试几乎可以确定是试图通过 named 漏洞入侵这些系统。）鉴于安全漏洞是随处可见的，保持你的系统服务器和其他程序更新到最新状态至关重要。

安全问题不仅限于服务器。在本地用户运行的非服务器程序中偶尔也会发现漏洞。如果你的系统有多个用户，这些漏洞可以被利用来获取 root 访问。源自内部的渗透并不会让你的任务变得更容易：你必须清理问题，最可能是通过删除所有数据并从备份恢复或重新安装操作系统。

除了安全相关问题外，漏洞有时还会影响系统稳定性或特定程序的可靠性。通过将有漏洞的程序更新到更稳定的版本，你可以为你自己和用户节省大量的沮丧。幸运的是，大多数核心 Linux 程序都经过了充分测试，包含很少显眼的问题。尽管如此，小问题偶尔还是会出现，因此更新你的系统可能是非常值得的。

偶尔，你可能需要升级整个系统。例如，你可能正在运行 Red Hat 6.1 并想要升级到 Red Hat 7.0。这种重大升级通常是为了新功能而不是微小的 bug 修复。例如，Red Hat 7.0 使用的是 xinetd 和 XFree86 4.0，而不是 inetd 和 XFree86 3.3。如果你需要 xinetd 和 XFree86 4.0 提供的功能，这些更改就非常重要。大多数发行版都提供了升级整个操作系统的方法，通常通过常规安装程序。这些程序会处理并替换每个更新的包，然后重启进入更新后的操作系统。

# 检查操作系统更新

**警告** 所有的包更新，特别是整个系统的更新，都有可能引入问题。更新产生的最常见故障与配置文件有关，因为更新经常用默认文件替换你精心调优的配置文件。因此，你应该始终备份软件包。在整个操作系统更新的情况下，备份 /etc 目录以便在需要时还原原始文件。你的管理员日志文件对于让你的系统重新工作也至关重要，特别是当更新的包需要不同格式的配置文件时，例如从 inet 到 xinetd 的变化就是如此。关于你如何配置一个包的良好记录可以帮助你让其替代品正常工作。

你的发行维护者通常是 lib、XFree86 和主要服务器等更新的最佳来源。通过使用发行维护者提供的更新，你可以合理地确保更新不会与自带的其他包发生冲突或产生问题。在如下情况下，你可能需要在其他地方寻找更新。

**不可用的更新** 如果你的发行版维护者更新缓慢，当你得知重要包存在问题时，你可能别无选择地查看其他。

**之前的更新** 如果你之前使用其他来源更新过某个包，你可能希望坚持使用该来源，而不是回到发行维护者的包。假设你已经解决了任何兼容性问题，如果退回到原始供应商，可能会觉得很麻烦。

**包替换** 你可能决定用另一个提供类似功能的不同程序来替换标准包。例如，如果你在 Red Hat 7.0 系统上使用 Postfix 替换 sendmail，你将在 Red 的网站上找不到 Postfix 的更新。

**包添加** 就像替换的包一样，你无法找到未随原始发行版发布的程序的更新。例如，你必须转向 Appix (http://www.appix.com) 获取 AppixWare 更新。

**内核更新** 正如早些时候在“获取内核”中描述的，Linux内核可以通过预包文件进行更新，但从原始源代码自行编译内核通常更有益。
