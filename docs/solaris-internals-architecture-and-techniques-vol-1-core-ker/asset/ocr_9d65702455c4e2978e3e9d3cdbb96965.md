door_return(3X) is part of the doors API and is typically called at the end of the function exported by the door_create(3X) call.

+   - door_return(3X) returns processor control to the thread that issued door_call(3X) and causes the server thread to sleep, waiting for another invocation of the door function.
- When entered (remember, we're in the kernel now, not in the doors library), door_return(1) allocates a door_data structure for the calling thread and links it to the kernel's t_door pointer.

This sequence is done if the current thread's t_door pointer is NULL, signifying a door_data structure has not yet been allocated.

The next bit of code in door_return(1) applies to argument handling, return data, and other conditions need to be dealt with when a kernel thread issues door_call(3X). We're still in the create phase, so a bit later we'll revisit what happens in door_return(1) as a result of door_call(3X).

Continuing with the create in the door_return(1) kernel function:

+   - The kernel door_release_server(1) code is called to place the current thread on the list of threads available to execute before door calls into the server.
- The kernel thread linked to the process's p_server_thread link, and cv_broadcast(1) is done on the door condition variable, door_cv, causing any threads blocked in door_call(3X) to wake up.

At this point, the door create is essentially completed.

+   - A call into the shuttle code puts the kernel to sleep on a shuttle synchronization object (shuttle_swt(1)); the thread is placed in a sleep state and enters the dispatcher through shuttle_swt(1).

We directly explain shuttle synchronization objects. Typically, execution control flow is managed by the kernel dispatcher (Chapter 5), using condition variables and sleep queues. Other synchronization primitives, mutex locks, and reader/writer locks are managed by turnstiles, an implementation of sleep queues that provide a priority inheritance mechanism.

Shuttle objects are a relatively new (introduced in Solaris 2.5, when doors first shipped) synchronization object that allows very fast transfer of control of a processor from one kernel to another without incurring the overhead of the dispatcher queue search and normal kernel thread processing. In the case of a door_call(), control can be transferred directly from the caller (or a client in this case), to a thread in the door server pool, which executes the door function on behalf of the caller. When the door function has completed, control is transferred directly back to the client (caller), all the kernel shuttle interfaces to set state and to enter the dispatcher at the appropriate places. This direct transfer of processor control contributes significantly to the IPC performance.
