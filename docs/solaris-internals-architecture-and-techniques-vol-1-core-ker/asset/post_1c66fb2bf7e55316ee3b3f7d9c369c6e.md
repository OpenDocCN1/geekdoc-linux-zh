## 10.4.2 Kernel Implementation of Message Queues

We'll walk through the kernel flow involved in the creation of a message queue and the sending and receiving of messages, since these represent the vast majority of message queue activities.

- The creation of a message on behalf of an application calling the msgget(2) system calls with a call to the kernel ipcget() routine. An ipc_perm structure will be available for every message queue identifier (msgid).
- Once a structure has been allocated, if ipcget() returns successfully, the application code has a valid message queue identifier, can send and receive messages, and can run message control(msgctl(2)) operations.

A message send (msgsnd(2)) call requires the application to construct a message, setting a message type field and creating the body of the message (e.g., a text message).

- When the code path for the message send kernel support is first entered, the code does general housekeeping—such as incrementing process statistics to announce a message queue system call is being executed. The cpu_sysinfo structure maintains a msq counter that reflects the total number of message queue systems executed.
- The code verifies the calling process's access permissions to the message queue and tests the message size again against the msgmax tunable.
- Next, the code copies the message type field from the user address space to a designated area in the kernel.

The rest of the message send flow is represented in pseudocode.

```
if (message queue EID no longer exists)
    return EIDM error
if (current bytes + bytes in new msg > msgmax)
    if (IPC_NOWAIT)
        return EAGAIN
    else
        set MSGWAIT flag in msqid_ds.msg_perm.mode
        call cv_wait_sig() /* put the caller to sleep until space is
        available on the queue */
        /* on wakeup, code will validate msqid, and set EIDM if it is
        removed */
    allocate space for message from resource map (msmap)
    if (space not available)
        if (IPC_NOWAIT)
            return EAGAIN error
    else
        call cv_wait_sig() /* sleeping for space */
    /* once the wakeup is issued, the message on the queue *
    the necessary resources are
    copy message data from user space to kernel space * (map area)
    increment message size
    msqid_ds.msg_cbytes += new message size
    msqid_ds.msds_lpid = PID of caller
    msqid_ds.msds_stime -= current time

    update message header msq_type, msg_ts (text size) and msg_spot (location pointer)
    adjust the queue pointer (msg_first, msg_next, msg_last)

```

The msgrcv support code is a little less painful, now since we're looking for a message on the queue (as opposed to putting one on the queue). Kernel resources do not need to be allocated for messages involving the general flow of the kernel path for receiving messages involves checking permissions for operation in a loop through all the messages on the queue.

- If the requested message type matches a message on the queue, the code copies the message type to the user-supplied location and copies the data to the user-supplied location.

- Next, the code updates the msqid_ds structure field, subtracts the message size from msg_cbytes, sets PID in msg_lrpid, sets time in msg_rtime, frees the message resources, frees the message header (msg structure), and frees the resource map entry.
- If the code looped through all messages and found no matching type, it returns a No Message error.

When the sequence is completed, the application code will have the message type and data in a buffer area supplied in the msgrcv(2) system call.

The only remaining callable routine for applications to use is the msctl(2) system call. The control functions are straightforward; they typically involve either retrieving or setting values in a message queue's ipc_perm structure.

- Whenctl(2) is invoked with the IPC RMID flag, meaning the caller wishes to remove the message queue, the POSIX library marks the message queue for deletion. The kernel will then remove the queue when all processes currently using it have closed the object.

## 10.5 POSIX IPC

The evolution of the POSIX standard resulted in three types of interfaces: semaphores, message queues, and shared memory. All of the POSIX IPC functions are either directly or indirectly based on memory mapped files.

### POSIX IPC

| Semaphores | Message Queues | Shared Memory |
| :--- | :--- | :--- |
| sem_open | mq_open | shm_open |
| sem_close | mq_close | shm_close |
| sem_unlink | mq_unlink | shm_unlink |
| sem_init | mq_getattr | shm_getattr |
| sem_wait | mq_send | shm_send |
| sem_trywait | mq_receive | shm_receive |
| sem_post | mq_notify | shm_notify |
| sem_getvalue | mq_getvalue | |

The POSIX library provides non-cancel wrappers for these functions.

- posix_obj_open()... Opens a POSIX object. If the O_CREAT flag is set, it will fail if the object already exists unless O_EXCL is also set.
- posix_obj_name()... Qualifies the path name of a POSIX object. It ensures the path begins with a / character and strips other slash characters.
- posix_open_nc()... A non-cancel version of the open function.
- posix_close_nc()... A non-cancel version of the close function. It disables thread cancellation before calling the actual close(2) system call.
- posix_obj_lock()... Locks a POSIX object for exclusive access using the lockf(3C) interface.
- posix_obj_unlock()... Unlocks a POSIX object using lockf(3C) with the F_UNLOCK flag.
