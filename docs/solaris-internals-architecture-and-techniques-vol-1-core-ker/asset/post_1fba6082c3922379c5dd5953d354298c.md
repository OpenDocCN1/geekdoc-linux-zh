- ts_exitclass, rt_exitclass — Remove the class-specific data structure (tsproc or rtptroc) from the linked list and free.

- ts_fork, rt_fork, sys_fork — Process fork support code. Allocate a class-specific data structure (tsproc or rtptroc), initialize it with values from the parent thread, and add it to the linked list. The SYS fork is a no-op. It is called from the lwcreate() and lwfork() kernel functions as part of the fork(2) system call when a new process is created.

- ts_forkset, rt_forkset, sys_forkset — Called from the kernel (common fork) in support of fork(2) system call. It is the last thing done before the fork(2) returns to the calling parent and the newly created child. The xx_fork functions resolves the run order of the parent and child, since it is desired that the child first runs until the new object can be exc'd and set up its own address space mappings to prevent the kernel from needlessly duplicating copy-on-write pages. In the TS class, the child is placed at the back of the dispatch queue and the priority gives up over the processor. This is handled in another class routine, ts_setrun.

- ts_parms, ia_parms, rt_parms — Get the current priority and max priority for a thread. The functions are called from the itctl(2) system call. ts_upri and ts_uprim from the class-specific structure (tsproc, ia) are returned. IA classes also return the ia_name field. For RT threads, the rt_pri and rt_quantum from the rtptroc structure are returned.

- ts_parset, ia_parset, rt_parset — Set the priority of a thread on the basis of passed input arguments. A user parameter data structure is defined for each scheduling class: iaparms, tparams, and rtparams. For IA and TS class, a user priority and priority limit value can be set. The system checks the user priority or priority limit when it() is executed to ensure the values within the boundary values for the class and also checks credentials to ensure the caller has permission to allow the thread's priority. Valid user-supplied priorities for TS/IA classes are set in the ts_upri field in the tsproc structure and factor in priority adjustments on the thread.

RT classes do not support the notion of user-supplied priorities in the same manner as TS/IA class threads. User-supplied priorities for TS/IA threads nudge the actual thread priority in one direction or another, a user-supplied priority for RT class directly maps to the RT's global priority. Details are provided in “Thread Priorities” on page 39.

## Overview

- ts_swapin — Calculate the effective priority of a thread to determine the eligibility of its associated LWP for swapping in.(Kernel threads are not swappable; LWPs are.) ts_swapin is called by the memory scheduler (sched()). The function() might be called from the clock interrupt handler if memory is tight.

Basically, the scheduler (which should really call the swapper) loops through all the active processes and, for each process, executes an inner loop, which walks the linked list of kernel threads, calling swapin for each thread. The effective priority for each kernel thread is based on the amount of time the thread has been swapped out, the user mode priority of the thread, and the address space size. Smaller addresses are more desirable to swap in, since, if we are running the memory scheduler at all, memory must be tight. The address space is based on the process p_swrss (resident size before last swap), which is, of course, processwise.

ts_swapin returns the effective priority of the thread back to the caller, sched(), which then sets a process-level priority that is based on kthread effective priority in the list. Note that RT and SYS classes do not get swapped out, so there's no need for a swap-in.

- ts_swapout — Calculate the effective priority of a thread for swapping out of its associated LWP. Called by the memory scheduler (sched()), the swap function is passed a pointer to a thread and a flag to indicate whether the memory scheduler is hardware or soft mode (called from a similar loop in sched(), as described above). Soft means awefree (free memory is less than desired free), so only threads sleeping longer than maxslp (20 seconds) are marked for swapping. Hard-swap mode means afree has less than mindesfree for an extended period of time (30 seconds), an average of two threads are on the dispatch queues, and the paging (page +out) rate is high. (Chapter 12 for discussions about awefree, min,free, etc.)

The code is relatively simple; if in soft mode, set effective priority to 0. In hardware mode, calculate an effective priority with a small address space that have been in memory for a relatively long amount of time there are swapped out first. A time in the kthread structure, t_stime, is set by the swapper when a thread is marked for swap-out, as well as swap-in. The timestamp maintained in this field is compared to the current time in ts_swapin and ts_swapout to determine how long a thread has either swapped or swapped out.

- rt_swapri, sys_swapri — Stub functions, designed to establish an effective priority for RT and SYS classes. They are not called from anywhere in the kernel.

- ts_trapret — Trap return code, called on return to user from a systemcall or trap and designed to readjust the thread's priority.

- ts_preempt, rt_preempt — Called when a kernel thread needs to be preempted and must be placed on a dispatch queue. A TS thread interrupted in kernel mode is given a SYS class priority so it returns to execution quickly. Preemption is discussed in more detail shortly.

- ts_setrun, rt_setrun — Set a kernel thread runnable, typically called when a thread is removed from the sleep queue. Place the thread on a dispatch queue. For TS threads, readjust the global dispatch priority if the thread has been waiting (sleeping) in an orordate amount.

- ts_sleep — Prepare a thread for sleep. Set the thread's priority of wait time or if a kernel priority is requested (the thread's t_kpri_reg flag). A kernel priority (SYS class priority) is set if the thread is holding an exclusive lock on a memory page or an RW write lock.

- ts_tick, rt_tick — Tick processing for the thread, called from the clock interrupt handler (see “System Clocks and Timers” in Chapter 1). CPU execution for TS and IA classes is detected in the scheduling-specific data structure linked to the kernel thread, ts_timeleft in the tsproc structure is decremented in the ts_tick function for an executing thread that is not running at a SYS class priority. TS and IA classes will have their priority elevated for a short time by getting a SYS class priority. A thread's execution time for threads running in the SYS class is not tracked because SYS classes, by definition, run until they voluntarily surrender the processor.

The ts_timeleft value is used to determine if the thread has used up its CPU quantum. If it has, the thread's priority is recalculated and the thread is placed on the appropriate dispatch queue. If it has not, a check is made to determine if a higher-priority thread is waiting for a processor; if that condition is true, then the code simply returns, leaving the thread to continue on the processor. The kernel also tells for a scheduler activation, known as preemption control, in the tick handler; that topic is discussed shortly.

The rt_tick handler for RT classes is similar. If an RT class does not have an infinite time quantum and has used its allotted CPU time or if a thread with a higher priority is sitting on a dispatch queue, the RT class is forced to surrender the CPU. Preemption control is not implemented for RT threads.

- ts_wakeup, rt_wakeup — Called when a thread is coming from a sleep queue and must be placed on a dispatch queue. TS/IA class threads at a SYS priority are placed on the appropriate queue; otherwise, the priority is recalculated before queue placement. RT class threads are simply placed on a queue.

- ts_donice, rt_donice, sys_donice — Called when a nice(1) command is issued on the thread to alter the priority. Adjust the priority according to the nice value for TS/IA threads. nice(1) is not supported for RT and SYS
