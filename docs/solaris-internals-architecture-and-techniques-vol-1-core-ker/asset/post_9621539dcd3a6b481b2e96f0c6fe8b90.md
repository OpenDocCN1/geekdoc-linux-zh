
# Solaris threads

Solaris threads provide the thr_sigsetmask(3T) and pthread_sigmask(3T) interfaces for establishing per-user thread signal masks. The disposition and handlers for all signals are shared by all the threads in a process, such that a SIGINT (for example), with the default disposition in place, will cause the entire process to exit. Signals generated as a result of a trap (SIGPE, SIGILL, ...) are sent to the thread that caused the trap. Asynchronous signals, which are all signals not defined as traps, are delivered to the first thread that is not blocking the signal.

The difficulty in implementing semantically correct signals in the Solaris environment arises from the fact that user-level threads are not visible to the kernel; however, the low-level kernel signal code has no way of knowing which threads have signals blocked and, therefore, no way of knowing which signal should be sent to. Some sort of intermediary phase needs to be implemented: something that had visibility both to the user thread signal masks and to the kernel. The solution came in form of a special LWP that the library creates for programs that are linked to libthread; this LWP is called the aslp (it's actually an LWP/thread pair; remember, they always travel in pairs). The implementation of the aslp extends the traditional signal generation and delivery phases, by adding two additional stages: notification and redirection.

Generation -> Notification -> Delivery

Sending a (generation) to a process causes the aslp to look for a thread that can take delivery of the signal. Once a thread is located, the signal is redirected to that thread and can then be delivered. The exception to this rule is the sending of synchronous or trap signals (listed in Table 8-8). A trap signal, such as SIGSEGV, is not channeled through the aslp, but rather delivered to the LWP/thread that caused the trap, and from there to the user thread.

Before we delve into the mechanics of signal delivery, we should look at the data types used to support signals in the process, LWP/kthread, and user thread structures.

The sigqueue structure provides a framework for a linked list of siginfo structures, maintained at the process level, and for multithreaded processes at the LWP/kthread level. siginfo stores various bits of information for many different types of signals. Within the structure are several unions (and in some cases, nested unions), so the available data depends on how the structure is instantiated during runtime. In the interest of readability, not all union declarations are shown.

The siginfo data is available to processes (well, programs) that need to know more about the reason a signal was generated. The sigaction(2) system call programmatically provides this information. An optional SA_SIGINFO flag in the sa_flags field of the sigaction structure results in two additional arguments being passed to the signal handler (assuming of course that the dispatch position has been set up to catch). The first argument is always the signal number. A non-NULL second argument is a pointer to a siginfo structure (described in Table 8-10), and a third argument is a pointer to a ucontext_t structure, which contains hardware context information (stack pointer, signal mask, and general register contents) about the receiving process when the signal was delivered. The siginfo data can be useful for debugging when a trap signal is generated; for example, in the case of a SIGILL or SIGFPE, more information about the underlying reason for the trap can be gleaned from the kernel puts into siginfo when getting ready to send a signal. (See the sigaction(2), siginfo(5), and ucontext(5) manual pages.)

At the process level, there are three sigset_t structures (Figure 8.22):

- The p_sig field has a bit set for each signal pending
- The p_ignore represents signals with the disposition to ignore
- The p_siginfo array contains information in siginfo about the signal.

The siginfo structure is embedded in the sigqueue structure, a linked list of which is rooted in the process sigqueue pointer. sigqueue structures are allocated from a pool pointed to by p_sighdr. The pool of sigqueue structures is allocated the first time a sigqueue(2) system call is executed by the process. Thirty-two (the default) sigqueue structures are linked to the available pool. An additional pool is rooted at p_notify. (The notify(2) system call is not currently exposed as an API in Solaris—it's used internally within the POSIX message queue facility.) Signals that have reached the notification phase—they've been generated but not yet delivered—are represented in the p_notmsgs field, along with a condition variable, p_notifyf, for synchronization with the alsdw and the process.

In the embedded uarea, several maps are maintained for flagging signal-related events or forcing a particular behavior, settable by sigaction(2) system call. An array of pointers to signal dispositions: u signal[MAXSIG], contains one array entry per signal. The entries in the array may indicate the signal to be ignored (SIG IGN) or the default action is set (SIG DEF). If the signal is to be caught, with a handler installed by signal(3) or signification(2), the array location for the signal points to the function to be invoked when the signal is delivered. The uarea signal fields are described in the following list. The described behavior occurs when a signal corresponding to a bit that is set in the field is posted.

- u_sigstack Flags an alternate stack for handling the signal. Assumes sigstack(2) has been called to set up an alternate stack. If one has not been set, the signal is handled on the default stack. By sigaction(2), with SA_ONSTACK flag in sa_flags of signal structure.
- u_reseethand Resets the default to disposition (SIG DEF) when the handler is entered for the signal. The signal will not be blocked when the handler is entered. As set, by SA_RESEHANDLER in sa_flags.
