## 3.4.2 Synchronization Object Operations Vector

Each of the synchronization objects discussed in this section—mutex locks, reader/writer locks, and semaphores—defines an operations vector that is linked to kernel threads that are blocking on the object. Specifically, the object-operations vector is a data structure that exports a subset of objects required for kthreads sleeping on the lock. The generic structure is defined in `/usr/include/sys/subject.h`.

- The following data structure is used to map synchronization object type numbers to the synchronization object's sleep queue number or the syn object's owner function.

```c
typedef struct {
    sobj_ops *ops;
    sobj_type type;
    kthread_t (*sobj_owner)();
    void (*sobj_unsleep) (kthread_t *);
    void (*sobj_change_pri) (kthread_t *, pri_t);
} sobj_ops;
```

Header File `<sys/subject.h>`

The structure shown above provides the object type declaration. For each synchronization object, a type-specific structure is defined: `mutex_sobj_ops` for mutex locks, `rw_sobj_ops` for reader/writer locks, and `sema_sobj_ops` for semaphores. The structure also provides three functions that may be called on behalf of kthread sleeping on the object:

- owner: returns the ID of the thread that owns the object.
- unsleep: transitions the thread from sleep state.
- change_pri: changes the priority of the thread (See "Priority Inheritance" on page 88).

We will see how references to the lock's operations structure is implemented as we move through lock implementations in the following sections. It is useful to note that our examination of Solaris locks offers a good example of some trade-offs involved in software engineering. Building the various components that make the Solaris kernel is a series of design decisions when performance is measured against complexity. In areas where performance is critical, simplicity might be sacrificed in favor of performance. Much of the lock code is written in assembly for speed; the latter is easier to code and maintain but is slower. In some cases, a simpler design will be favored over assembly code.

## Mutex Locks

Mutual exclusion, or mutex locks, are the most common type of synchronization primitive used in the kernel. Mutex locks serialize access to critical data; threads must acquire the mutex before they can read or write the data. The thread holding the lock must release it when it has finished working in the protected region.

## 3.5 Overview

If a thread attempts to acquire a mutex that is being held, it can basically do one of two things: it can spin or it can block. Spinning the thread enters a tight loop attempting to acquire the lock. The term spin lock is often used to describe this type of mutex. Blocking means the thread is placed on a sleep queue while the lock is being held, and the kernel sends a wakeup to the thread when the lock is released. There are pros and cons to both approaches.

The spin approach has the benefit of not incurring the overhead of context switching required when a thread is put to sleep, and also has the advantage of relatively fast acquisition when the lock is released since there is no context-switch operation. It has the downside of consuming CPU cycles while the thread is in the spin loop not really doing any useful work.

The blocking approach has the advantage of freeing the processor to execute other threads while the lock is held; it has the disadvantage of requiring context switching to get the waiting thread off the processor and a new runnable onto the processor. There's also a little more lock acquisition latency since wakeup and context switching are required before the blocking thread can become the owner of the lock it was waiting for.

In addition to the issue of what to do if a requested lock is being held, the question of lock granularity needs to be resolved. Let's take a simple example. The kernel maintains a process table, which is a linked list of process structures for each of the processes running on the system. A simple table-level mutex could be implemented so that if a thread needs to manipulate a process structure, it must first acquire the process table mutex. This level of locking is very coarse. It has the advantages of simplicity and minimal lock overhead. It has the obvious disadvantage of potentially poor scalability since only one thread at a time can manipulate objects on the process table. Such a lock is likely to have a great deal of contention (a hot lock).

The alternative is to implement a finer level of granularity: a lock-per-process table entry. With a lock on each process table entry, multiple threads can be manipulating different structures at the same time, providing concurrency. The disadvantages are that such an implementation is more complex, increases the chances of deadlock situations, and necessitates more overhead because there are more locks to manage.

In general, implements relatively fine-grained locking when possible, largely due to the dynamic nature of scaling locks with kernel structures. The kernel implements two types of mutex locks: spin locks and adaptive locks. Spin locks, as we discussed, spin in a tight loop if a desired lock is held when a thread attempts to acquire the lock. Adaptive locks are the most common type of lock used and are designed to dynamically either spin or block when a lock is being held, depending on the state of the holder. We already discussed the trade-offs of spinning versus blocking. Implementing a locking scheme that only does one or the other can severely impact scalability and performance. It is much better to use an adaptive locking scheme, which is precisely what we do.

The mechanics of adaptive locks are straightforward. When a thread attempts to acquire a lock and the lock is being held, the kernel examines the state of the thread that is holding the lock. If the lock holder (owner) is running on a processor, the thread attempting to get the lock will spin. If the thread attempting to get the lock will block. This policy works quite well because the code is such that mutex hold times are very short (by design, the goal is to minimize the amount of code to be executed while a lock is held). So, if a thread is holding a lock and running, we know that minimally context switch is involved in less time than it takes context-switch off and again so, it's worth spinning.
