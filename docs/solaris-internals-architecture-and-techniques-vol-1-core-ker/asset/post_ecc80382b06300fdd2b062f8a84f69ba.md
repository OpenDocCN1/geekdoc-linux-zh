Note that the example output from the callout function in crash(1M) is not a complete listing. Note, that the ARGUMENT, TIME, and ID columns are 8-byte (64-bit) data types. On a 32-bit kernel, they are 32-bit data types.

- polltime — A real-time callout. From the poll(2) system call and based on the poll interval. polltime() wakes up a thread waiting on a poll event.
- realexpire — A real-time callout. Used in the real-time timer interval support when a timer is set. Callouts are derived from timer value. realexpire() generates the SIGALRM to the process.
- setrun — A real-time callout. Placed on the callout queue by sleep/wakeup code (variables) to force a thread wakeup when the sleep event has time value; for example, an aiowait(2) can specify a maximum tick count to wait for the I/O to complete. aiowait(2) with a timeout specificity a timed timeout variable, which in turn places a setrun() event on the callout queue to force a thread wakeup if the timer expires before the I/O has completed.
- schedpaging — A normal callout. Part of the paging subsystem in the VM system, to manage the pageout rate.
- mi_timer_fire — A normal callout. Part of the STREAMS-based TCP/IP protocol support. mi_timer_fire() generates regular message block processing through a STREAMS queue.
- sigalarm2proc — A normal callout. The alarm(2) system call places sigalarm2proc on the callout queue to generate a SIGALRM when the timer expires.
- ts_update — A normal callout. Checks a list of timeshare and interactive class threads and updates their priority as needed.
- seg_update — A normal callout. Used by the address space segment reclaim thread to free pagelocked pages that have not been used in a while and reclaim them.
- kmem_update — A normal callout. Performs low-level kernel memory allocation

This is by no means complete list of all the kernel functions placed on the callout queue, and of course you will typically see several of the same functions on the callout queue at the same time, with different IDs and timeout values.

## 2.6 The System Clock

The Solaris kernel relies on hardware interrupts for general housekeeping chores that need to be done at regular intervals. For example, the system clock triggers the dispatcher to recalculate process priorities at regular intervals and also initiate callout queue processing.

The kernel (software) sets up the programmable interrupt generator (hardware) to generate a callout interrupt at regular intervals, by deferred 100 times per second. The clock interrupts at interrupt level 10 (SPARC); nothing else on the system generates interrupts at this level. With each callout, a handler is entered. It performs the following functions:

- Sets available kernel anon space (anon_free) value, for tracking and reporting.
- Sets free memory (freemem) value, for tracking and reporting.
- Adjusts the time of day clock for possible jitter.
- Calculates CPU usage (user, system, idle, and wait I/O) and system dispatch (run queue) size.
- Does clock-tick processing for the thread running on the CPU (except the CPU).

### 2.6.2 High-Resolution Interrupts

By default, a system clock interval of 10 milliseconds (100 interrupts per second) is used. You can set a kernel parameter, hires_tick, in the /etc/system file to increase the clock interrupt frequency to 1000 interrupts per second (hires_tick=1 in /etc/system). Increasing the clock frequency results in the system entering the dispatcher (among other things) more frequently. Exercise great care if you are considering high-resolution ticks—they can reduce system performance dramatically. As with any system tunable, this setting should never, ever be made on a production system without extensive testing first.
