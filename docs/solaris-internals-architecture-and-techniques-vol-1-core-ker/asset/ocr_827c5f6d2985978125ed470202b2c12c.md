Since a vast majority of customers that purchase Sun servers use them for database applications and since database applications make extensive use of shared memory, addressing this issue with ISM was an easy decision.

Solaris implements memory page locking by setting some bits in the memory's page structure. Every page of memory has a corresponding page structure that contains information about the memory page. Page sizes vary across different hardware platforms. UltraSPARC-based systems implement an 8-Kobyte page size, which means that 8 Bytes is the smallest unit of memory that can be allocated and mapped to a process's address space.

The page structure contains several fields, among which are two fields called p_cownt and p_lockcnt, that are page-on-write and page lock count. Copy-write tells them that this page can be shared as long as it is read, but once a write to the page is executed, the system is to make a copy of the page and map it to the process that is doing the write. Lock count maintains a count of how many times page locking was done for this page. Since many processes share mappings to the same physical page, the page can be locked from several sources. The system maintains a count to ensure that processes have mappings from other processes. The system's pageout, which runs if free memory gets low, checks the status of the page's p_cownt and p_lockcnt. If either is nonzero, the page is considered locked in memory and thus not marked as a candidate for freeing. Shared pages using the ISM facility do not use the copy-on-write lock (that would work for a nonshared page after a write). Pages locked through ISM implement the p_lockcnt page structure.

Even though ISM locks pages in memory so that they'll never be paged out, Solaris treats ISM segments as it treats non-ISM segments and ensures that there is sufficient backing store in swap before completing the page mapping on behalf of the requesting process. While this seems superfluous for ISM pages (allocating disk space for pages that can't be swapped), it makes the implementation clearer. Solaris 2.6 changes this somewhat, and in Solaris 2.6 swap is not allocated. The effect is allocation of shared segments using ISM requires sufficient available swap space, at least until Solaris 2.6. Using ISM requires setting a flag in the shmat(2) system call. Specifically, the SHM_MMU flag must be set in the shfig argument passed to shmat(2), to instruct the system to set up the shared segment as intimate memory. Otherwise, the system will create the shared segment as a non-ISM segment.

In Solaris releases to and including Solaris 7, there is not an easy way to tell whether or not a shared segment is an ISM segment. It can be done without root permission and use of (ISM) utility.
