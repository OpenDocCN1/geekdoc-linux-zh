
## 13.4 File System I/O

Two distinct methods perform file system I/O:

- read(), write(), and related system calls
- Memory-mapping of a file into the process's address space

Both methods' calls are implemented the same way: a file is mapped into an address space and then paging I/O is performed on the pages within the mapped address space. Although it may be obvious that memory mapping is done when we memory-map a file into a process's address space, it is less obvious that the read() and write() system calls also map a file before reading or writing. The major differences between these two methods are where the file is mapped and who does the mapping; a process calls mmap() to map the file into its address space for memory mapped I/O; and the kernel maps the file into the kernel's address space for read and write. ### 13.4.1 Memory Mapped I/O

A request to memory-map a file into an address space is handled by the file system vnode method vop_map() and the seg_vn segment driver (see "The seg_map Segment" on page 549). Process requests that a file be mapped into its address space. Once the mapping is established, the address space represented by the file appears as regular memory and the file system can perform I/O by simply accessing that memory.

Memory mapping of files hides the real world of reading and writing the file because the seg_vn memory driver quietly works with the file system to perform the IOs without the need for process-initiated system calls. I/O is performed, in units of pages, upon reference to the pages mapped into the address space; reads are initiated by a memory access; writes are initiated by the VM system finding dirty pages in the mapped address space.

The system call mmap() calls the file system for the requested file with vop_map() vnode method. In turn, the file system calls the address space function for the current address space, and the mapping is created. The flags passed into the mmap() system call are reduced to the subset of all file permissions. If mandatory locking is set for the file, then mmap() returns an error.

Once the mapping is created in the process's address space, file pages are read when a fault occurs in the address space. A fault occurs the first time a mapped segment is accessed because at this point, no physical page of memory is at that location. The memory management unit causes a hardware trap for that memory segment; the memory segment calls its fault function to handle the I/O for that address. The segvn_fault routine handles a fault for a file mapping in a process address space and then calls the file system to read the page for the faulted address, as shown below.


For each page fault, seg_vn reads in an 8-Kbyte page at the fault location. In addition, seg_vn initiates a read-ahead of the next eight pages at each 64-Kbyte boundary. Memory mapped read-ahead uses the file system cluster size (used by the read() and write() system calls) unless the segment is mapped MA_SHARED or memory advice MADV_RANDOM is set.

Recall that you can provide providing advice to the pages in a memory mapped segment by using the madvise system call. The madvise system call and (as in the example) the advice information is used to decide when to free behind the file is read.

Modified pages remain unwritten until disk the fsflush daemon passes over the page, at which point they will be written to disk. You can also use the memctl() call to initiate a synchronous or asynchronous write of pages.

### 13.4.3 The seg_map Segment

The seg_map segment maintains mappings of files into the kernel's address space. The maximum size of the seg_map differs among hardware architectures, it is only a fraction of the total physical memory, and contains only a small proportion of the total file system cache. Note that though the size of the seg_map segment is fixed, the pages which it references can be stolen by the page scanner, and as a result, only a portion of the seg_map segment may be resident (especially on machines where the seg_map segment is close to the size of memory).

A single seg_map segment is created at boot time. The segment is sized according to a table of machine types (see Table 13-9) and is capped at the amount of free memory just after the kernel has booted. For example, if the machine is an Ultra-1 or sun4 architecture, the maximum size of the seg_map is 256 Mbytes. A 64-Byte machine booting the Solaris kernel will most likely end up with a seg_map segment about 50 Mbytes in size, as 50 Mbytes was the free memory when the system was being booted. A 512-Megabyte sun4 system will have a seg_map size of 256 Mbytes, since free memory will be much larger than 256 Mbytes while it is booting.
