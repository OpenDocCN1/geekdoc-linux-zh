
- *u_sigrestart - If inside system call when the signal is received, restarts the system call. This behavior does not work for all system calls, only those that are potentially "slow" (e.g., I/O-oriented system calls—read(2), write(2), etc). Interrupted system calls typically result in an error, with the errno being set to EINTR. Set by SA_RESTART in sa_flags.
- *u_sigodefer - Does not block subsequent occurrences of the signal when it is caught. Normally, a signal is blocked when it has been delivered and a handler is executed. Set by SA_NODFER in sa_flags.
- *u_sigmask[] — Signals that have been caught and are being held while a handler is executing.
- *u_sigaction[] — Signal dispositions.

The LWP stores the current signal in lwp_cursig and stores a pointer to a sigqueue structure for the siginfo data in lwp_curinfo, which is used in the signal delivery phase.

Other fields include a stack pointer in an alternate stack, lwp_sigstack, is set up by a call to sigaltstack(2). It is sometimes desirable for programs that do their own stack management to handle signals on an alternate stack, as opposed to the default use of the kernel's runtime stack (SA_ONSTACK through sigaction(when the handler is set)). The kernel maintains two k_sigset_t members: t_sig and t_hold. t_sig has the same meaning as p_sig the process level, that is, a mask of pending signals; t_hold is a bit mask of signals to block.

In addition, t_queue points are placed on an enqueue for siginfo data. A signal's siginfo structure will be placed either on the process p_sig or the kread's t_queue is used in the case where a non-NULL pointer has been passed to the kernel signal code, indicating a directed signal, for example, a multithreaded process with more than one LWP.

Finally, for multithreaded processes, the user thread (not to be confused with the kernel thread) maintains signal for pending signals (t_psig), sent signals (t_ssig), bounced signals (t_bsig—on bounced signals later), and signals to be blocked (t_hold). There is also a siginfo structure for deferred signals, referenced as t_si.

Clearly, there appears to be a little redundancy in the signal support structure members that exist within the context of a process. This redundancy is due to the requirements for the multithreaded model and the fact that different signals get to different places, depending on the signal itself and the source. Earlier in the discussion, we provided several examples of why some signals are sent and why they are received. Asynchronous signals could originate from one or various places in the kernel. Signals that are sent from user (e.g., kill(1), kill(2), sigqueue(2)) are sent to the process. Some signals that originate in the kernel are directed to a particular LWP/kthread; for example, the kernel clock interrupt handler may send a SIGPROF or SIGVTAL directly to a LWP/kthread. The pthread_kill(3) and thr_kill(3) threads interfaces provide for sending asynchronous signals to a specific user. The STREAMS subsystem sends SIGPOLL and SIGURG to the process when appropriate (e.g., polled event occurs or urgent out-of-band messages).

Regardless of the size, the signal delivery mechanism through the operating system is the kernel sigproc() function, which takes up to four arguments: a process counter, a thread pointer, the signal number, and an optional flag, fromuser, which indicates whether the source was the kernel or user. Signals that should be directed to a kthread/LWP call sigtopproc() with a valid thread pointer. A NULL thread pointer indicates the signal should be posted to the process. Let's take a look at the code flow of sigproc().

```
sigproc(proc pointer, kthread pointer, int signal, fromuser flag)
    if (signal == SIGKILL) /* kill signal */
        if (skilled in p_flags)
            Set kthread pointer to NULL
    else if (signal == SIGCHLD) continue /* job control */
        Discard queued siginfo structs for preventing STOP SIGNALS
        (SIGSTOP, SIGSTP, SIGTOU, SIGTIN)
    if (process has an aslw thread) /* multithreaded processes */
        Clear SIGSTOP, SIGSTP, SIGTOU, TTIN in aslw t_sig
        if (process has more than one kthread)
            Loop through kthread linked list
                Delete signal structs for STOP, TSTP, TTU, TTIN
            else /* process has one kthread */
                Clear STOP, TSTP, TTU, TTIN in p_sig
    Clear p_stopsig
    if (process is multithreaded)
        Loop through kthread linked list
            if (thread is tscheduled due to TSSTART)
                Set kthread t
                Call setrun() /* get the thread running /-
        End loop
    if (signal is STOP or TTU or TTIN)
        Set thread pointer to the process aslw thread
        Delete any siginfo structures for queued SIGINT
    if (process is multithreaded)
        Clear pending SIGINT in aslw
        Clear pending SIGINT in p_notifs
        Loop through list of kernel threads
            Delete queued SIGINT siginfo structures
            Clear pending SIGINT in t_sig
        End loop;
    else /* process is not multithreaded */
        Clear pending SIGINT in p_sig
    if (signal is discardable)
        return
    if (process has an aslw kernel thread)
        Set signal bit in aslw t_sig
        Call sat_signal()
    else if (process is multithreaded)
        Set the signal bit in process p_sig
        Loop through linked list of kernel threads
            if (eat signal)
                break out of loop
            if (signal == SIGKILL)
                Try to run a kthread so signal can be delivered
    End Loop
```

## The High-Level Signal Flow

This signal flow explains why zombie processes cannot be killed (any horror movie fan knows you can't kill a zombie). A process must be executing in order to take delivery of a signal. A zombie process is, by definition, a process that has been terminated. It exists only as a process table entry, with all its execution state having freed by the kernel.

A lot of the upfront work in `sigtoproc()` deals with job control and terminal I/O signals. In compliance with the POSIX specifications, this behavior is documented in the `signal(5)` manual page, which we summarize here: Any pending SIGCONT signals are discarded upon receipt of a SIGSTOP, SIGSTP, SIGTIN, or SIGTOU, regardless of the disposition. The inverse is also true; if any of those four signals are pending when a SIGCONT is received, they are discarded, again regardless of the disposition. In both cases, the posted signal will be delivered followed by the flow described in "Synchronous Signals," below.

### 8.7.1.1 Synchronous Signals

Synchronous signals, or trap signals, originate from the kernel trap handler. When executing instruction stream causes one of the events described in Table 4.2, it is detected by the hardware, and execution is redirected to a kernel trap handler. The trap handler populates a `siginfo` structure with invokes the `trapcleanup(1)` function, where the function determines whether to stop the kthread/LWP because of a debugger "stop on fault" flag. The entry point into the kernel signal subsystem is through the `trapsig()` function, which is executed next. If the signal is marked or the disposition has been set to ignore, then `trapsig()` unmasks the signal and sets the disposition to default. The `siginfo` structure is placed on the kthread's `t_sigqueue` list, and `sigtopproc()` is called to post the signal.
