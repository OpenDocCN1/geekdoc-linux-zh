+   * u_sigrestart - If inside system call when the signal is received, restarts the system call. This behavior does not work for all system calls, only those that are potentially "slow" (e.g., I/O-oriented system calls—read(2), write(2), etc). Interrupted system calls typically result in an error, with the errno being set to EINTR. Set by SA_RESTART in sa_flags.

+   * u_sigodefer - Does not block subsequent occurrences of the signal when it is caught. Normally, a signal is blocked when it has been delivered and a handler is executed. Set by SA_NODFER in sa_flags.

+   * u_sigmask[] — Signals that have been caught and are being held while a handler is executing.

+   * u_sigaction[] — Signal dispositions.

The LWP stores the current signal in lwp_cursig and stores a pointer to a sigqueue structure for the siginfo data in lwp_curinfo, which is used in the signal delivery phase.

Other fields include a stack pointer in an alternate stack, lwp_sigstack, is set up by a call to sigaltack(2). It is sometimes desirable for programs that do their own stack management to handle signals on an alternate stack, as opposed to the default use of the kernel's runtime stack (SA_ONSTACK through sigaction(when the handler is set)). The kernel maintains two k_sigset_t members: t_sig and t_hold. t_sig has the same meaning as p_sig the process level, that is, a mask of pending signals; t_hold is a bit mask of signals to block.

In addition, t_queue points are placed on a enqueue for siginfo data. A signal's siginfo structure will be placed either on the process p_sig or the kread's t_queue is used in the case where a non-NULL pointer has been passed to the kernel signal code, indicating a directed signal, for example, a multithreaded process with more than one LWP.

Finally, for multithreaded processes, the user thread (not to be confused with the kernel thread) maintains signal for pending signals (t_psig), sent signals (t_ssig), bounced signals (t_bsig—on bounced signals later), and signals to be blocked (t_hold). There is also a siginfo structure for deferred signals, referenced as t_si.

Clearly, there appears to be a little redundancy in the signal support structure members that exist within the context of a process. This redundancy is due to the requirements for the multithreaded model and the fact that different signals get to different places, depending on the signal itself and the source. Earlier in the discussion, we provided several examples of why some signals are sent and why they are received. Asynchronous signals could originate from one or various places in the kernel. Signals that are sent from user (e.g., kill(1), kill(2), sigqueue(2)) are sent to the process. Some signals that originate in the kernel are directed to a particular LWP/kthread; for example, the kernel clock interrupt handler may send a SIGPROF or SIGVTAL directly to a LWP/kthread.
