
Other data the dispatcher needs for queue management and thread scheduling maintained in the dispatch queue structure includes the following.

- disp_lock — A synchronization lock to protect fields in the structure.
- disp_npr1 — The number of priority levels in the queue.
- disp_q — The pointer to the dispatch queue (pointer to a dispq_t structure).
- disp_q_limit — Another pointer to a dispq_t structure, set to point to the end of the queue.
- disp_qactmap — A bitmap indicating which queues actually have runnable threads in them. Using the bitmap in conjunction with disp_maxrunpri the dispatcher code can traverse the queues with extreme speed and efficiency, searching for the best runnable thread.
- disp_maxrunpri — The priority of the highest-priority thread on the queue.
- disp_max_unbound_pri — The priority of the highest-priority unbound thread on the queue.
- disp_nrunnable — Total number of runnable threads on the queue.
- disp_cpu — A pointer back to the cpu structure that owns this queue.

The dispatch queue entry itself is a small, three-member data structure, defined as a dispq_t structure. It contains a pointer to the first kthread on the queue (dq_first), a pointer to the last kthread on the queue (dq_last), and a count of kthreads on the queue (dq_runcnt). Each per-priority queue maintains a count of threads on the queue, and the sum of all per-priority queues is represented in disp_nrunnable.

Finally, there's the disp_queue_info structure. An array of these structures is created at boot time, for each processor on the system. Each array member (disp_queue_info structure) contains a pointer to one per-dispatch queue (disp_t) embedded in the cpu structure. There are two additional disp_t pointers, olddisp and newdisp, and storage space for an old and new queue bitmap field, oldqactmap and newqactmap, for queue manipulation and maintenance. The number of global priorities in the queue is also maintained in old_globalpris. As we move through the algorithmic flow of the dispatcher code, we'll see how these structures and members are used. ## 9.2.2 Thread Priorities

The operating system uses a global priority scheme to assign priorities to kernel threads; the priorities are derived from a dispatch table according to the scheduling class it belongs to. As we see, each scheduling class has a range of priorities assigned to it. As scheduling classes load into the system, the kernel must ensure that every priority level across loaded scheduling classes has a unique priority number.

The range of priorities for the TS/IA class is 0–59, which corresponds to global priorities 0–59 since the TS/IA class is the lowest class on the system. SYS priorities range from 0–39 and are assigned global priorities 60–99 since SYS class sits directly over the TS/IA class. If the RT class is not loaded, interrupt priorities range from 0–9, occupy global priorities 100–109. Without the RT class loaded, there the interrupt thread priorities are bumped up to global priorities 160–169, and the RT global priority range is 100–159. This protocol is represented in Figure 9.2 on page 348 and Table 9-1 on page 345.

During dispatcher initialization, the kernel calculates the maximum sys priority value and the total number of priority scheduling classes as loaded. These values are recalculated if scheduling classes are loaded following initialization, for example, if the RT class is loaded sometime after the system has booted. The calculated values are stored in the system structure's v_nglobpris and v_maxsyspri field.

```
# /etc/crash
dumpfile = /dev/mem, namelist = /dev/ksyms, outfile = stdout
> v

v_nglobpris: 170
v_maxsyspri: 99
```

Newly created threads inherit their priority and scheduling class from the parent process (parent thread, actually—remember, non-read threads have one LWP/kthread pair). Recall from the previous chapter, the forkwp() kernel thread calls lwp_create(), which in turn calls thread_create(). thread_create() is passed as arguments a thread state (TS_STOPPED—the initial state of a thread) and priority, which is established by the calling thread. The other applicable kthread structure members are initialized toward the end of the forkwp() code, including the allocation of the class-specific data structure (e.g., tsproc). completes the setup of the dispatcher data for the new thread, initializing the class data structure for the thread and putting it on the linked list of class structures.

The kernel thread structure fields relevant to thread priorities are t_epri, which is the actual global dispatcher priority for the thread, t_ reflects an inherited priority, and t_kpri_req, which is a flag to indicate to the dispatcher that a SYS priority is requested for the other. Other thread-priority-related data is maintained in the class-specific data structure linked to the kthread: tsproc for TS/IA threads, rtproc for PT threads. For TS/IA threads, the kernel provides a facility for user-level priority adjustments, similar in concept to the traditional nice(1) command. Unix systems provide a nice(1) command that allowed users to adjust the priority of the processes they owned. Non-root users could only make their own process worse (they could be nice to the other users of the system), and root could make priorities better with nice(1). Solaris supports nice(1) for compatibility, the proper way to adjust user-level priorities is to use the proccntl(1) command. Issuing proccntl(1) with the -1 (lowercase l) flag displays the range of user priorities.

```
# proccntl -1
CONFIGURED CLASSES
==========

SYS (System Class)
TS (Time Sharing)
    Configured TS User Priority Range: -60
IA (Interactive)
    Configured IA User Priority Range: 60
RT (Real Time)
    Configured RT Priority: 59
```

The user-level priority for RT threads is the easy case, which is why we talked about that first. User-level tweaking of SYS class thread priorities does not exist. Which brings us back to TS/IA class threads can run at different scheduling classes and priorities. Multithreaded processes can have LWP/kthread pairs in the TS, IA, SYS, and RT class. The priocntl(1) command, however, does not provide level of granularity for control. priocntl(1) provides for scheduling class and priority only on a per-process level, not LWP/kthread.
