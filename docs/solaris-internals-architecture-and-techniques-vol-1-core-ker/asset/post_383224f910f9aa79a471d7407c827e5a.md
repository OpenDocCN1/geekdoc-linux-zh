
## 9.3.3 The Sleep Process

Now that we introduced condition variables and sleep queues, let's tie them together to form the complete sleep/wakeup picture in Solaris. The interfaces to the sleep queue (sleepq_insert(), etc.) are, for the most part, called only from the condition variables and turnstiles subsystems. From a hierarchical perspective, you could view the sleep/wakeup implementation, as depicted in Figure 9.12 on page 399, where a well-defined and limited set of interfaces manipulate kernel threads on the sleep queues.

The process of putting a thread to sleep begins with one of cv_wait(), cv_wait_sig(), cv_wait_sig_swap(), cv_timedwait(), or cv_timedwait_sig(). Each of these functions is passed the condition variable and a mutex. They all call cv_block() to prepare the thread for sleep queue insertion. cv_wait() is the simplest condition variable interface; it grabs the lock for kthread and invokes the class-specific sleep routine (ts_sleep()). The timed variants of the cv_wait() routines take an additional argument, ensuring that the thread will be woken up when the time value expires if it has not yet been removed from the sleep queue. cv_timedwait() and cv_timedwait_sig() use the kernel callout factory for handling the timer expiration. The realtime_timeout() interface is used and places a high-priority timeout on the kernel callout queue, along with the thread address and time value. When the timer expires, extrun followed by the class-specific function (e.g., rt_setrun()), executes the sleeping thread, running it and placing it on a dispatch queue.

The sig variants of the condition variable code, cv_wait_sig(), cv_timedwait_sig(), etc., are designed for potentially longer-term waits, where it is desirable to tell the caller if a signal has been posted before the actual wakeup event. They return 0 or cv_wait_sig_swap(), can be used if it is safe to swap out the sleeping thread while it's sleeping. The various condition-variable routines release the mutex after cv_block() returns, and they reacquire the mutex before the function returns.

- cv_wait() - Calls cv_block(). Then, cv_wait() enters the dispatcher with switch() when cv_block() returns.
- cv_wait_sig() - Checks for SC_BLOCK activation (lat if LWP in the process is blocking). If false, cv_wait_sig() calls cv_block_sig(). On return from cv_block_sig(), it tests for a pending signal. If a signal is pending, cv_wait_sig() calls extrun(); otherwise, it switches. If an SC_BLOCK activation is true, cv_wait_sig() removes the thread timeout and returns -1, unless a signal is pending, then returns 0.
- cv_wait_sig_swap() - Essentially the same as cv_wait_sig() but flags the thread as swappable.

## The Kernel Sleep/Wakeup Facility

- cv_timedwait() — Tests for timer expiration on entry. If the timer has expired, cv_timedwait() returns -1. It calls realtime_timeout() to set callout queue entry, calls cv_block(), and checks the timer on return from cv_block(). If the timer has expired, cv_timedwait() calls setrun(); otherwise, it calls swwtch().
- cv_timedwait_sig() — Tests for timer expiration. If the timer has expired, cv_timedwait_sig() returns -1 unless a signal is pending; then, it returns 0. If neither condition is true, cv_timedwait_sig() calls realtime_timeout() to set the callout queue entries and for an SC_BLOCK activation. If false, cv_timedwait_sig() calls cv_block_sig(). On return from cv_block_sig(), it tests for a pending signal. If a signal is pending, cv_timedwait_sig() calls setrun(); otherwise it calls swwtch(). If an SC_BLOCK activation is true, cv_timedwait_sig() removes the thread timeout and returns -1 unless a signal is pending; then, it returns 0.

All of the above entry points into the kernel variable code cv_block() and cv_block_sig(), which just sets the T_WAKEABLE flag in the kernel thread and then calls cv_block(). cv_block() does some additional checking of various state flags and invokes the scheduling-specific sleep function through the CL_SLEEP() macro, which resolves to ts_sleep() for a TS or IA class thread. The intention of the ts_sleep() code is to boost the priority of the thread if such a boost is flagged. As a result, the kthread is placed in an optimal position on the sleep queue for early wakeup and quick rescheduling when the wakeup occurs. Otherwise, the priority is reset according to how long the thread has been waiting to run.

The assignment of a SYS priority to the kernel thread is not guaranteed every time ts_sleep() is entered. Flags in the thread structure, along with kthread's class-specific data (ts_data in the case of a TS class thread), specify whether a kernel block priority is required. A SYS priority is flagged if the thread is holding either a reader/writer lock or a page lock on a memory page. For most other cases, SYS priority is not required and thus will not be assigned to the thread. RT class threads do not have a class sleep routine; therefore no priority adjustment work to do. ## Header File <sys/subject.h>

If you take a look at /usr/include/subject.h, you'll find a definition for synchronization object operations.

```
typedef struct _sobj_ops {
    syncobj_t sobj_type;
    kthread_t (*sobj_owner)();
    void (*sobj_unsleep)(kthread_t *);
    void (*sobj_change_pri)(kthread_t *, pri_t, pri_t);
} sobj_ops_t;
```

This is a generic structure that is used for all types of synchronization objects supported by the operating system. Note the enumerated members in the same header file; they describe... This object provides a placeholder for a few routines specific to the synchronization object that may require invocation while the kernel thread is sleeping. In case of condition variables (example), the sobj_ops structure is populated with the address of the cv_owner(), cv_unsleep(), and cv_change_pri() functions, with the sobj_type set to SOBJ CV.

With the kthread's wait channel and synchronization object pointers set appropriately, the correct sleep queue is located by the hashing on the condition variable address to insert into the sleepq head. Next, the cv_waiters field in the condition variable is incremented to reflect another kernel blocking on the object, and the thread state is set to TS_SLEEP. The sleep_insert() function is called to insert the kernel into the correct position (based on priority) in the sleep queue. The kthread is now on a sleep queue in a TS_SLEEP state, waiting for a wakeup.

## 9.3.4 The Wakeup Mechanism

For every cv_wait() (or variant), a corresponding wakeup calls using cv_signal(), cv_broadcast(), or cv_unsleep(). In practice, cv_unsleep() is not called in current versions of Solaris. cv_signal() wakes up one thread, and cv_broadcast() wakes all threads sleeping on the same condition variable. Here is the sequence of wakeup events.

- The cv_broadcast() function simply locates the address of the sleep queue by invoking hash function on the address of the condition variable, which was passed to cv_broadcast() as an argument, clears the cv_waiters field in the condition variable (all the threads are getting a wakeup, so the condition variable should reflect zero threads waiting on the condition variable), and calls sleepq_wakeall(chan).
