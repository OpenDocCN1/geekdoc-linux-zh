We alluded earlier to a default partition, created at system initialization (boot) time. All installed processors are placed in this default partition during the initialization process, and if no other partitions (processor sets) are explicitly created by prset(1M) or prset_create(2), the system simply maintains the internal default set, which is not made visible to users. prset(1M) will allow all processors on the system as unassigned; available to be configured into a processor set. The kernel defines three possible levels for partitions (cp_level): CP_DEFAULT, CP_SYSTEM, CP_PRIVATE. The default partition created at boot time is, of course, CP_DEFAULT and only one such partition is allowed. Additional partitions created on the system are set to CP_PRIVATE. The CP_PRIVATE level is not currently used but will be implemented in the future as a means of creating internal (kernel only) partitions.

# Kernel Processor Control and Processor Sets

We show dispatch queue for each partition. To summarize our earlier discussion of dispatch queues; the kernel maintains several queues of runnable threads waiting for a processor. Every CPU has its own set of dispatch queues for runnable threads below priority. For real-time threads, a systemic queue, known as the priority queue, is maintained. Threads placed on this queue are at high enough priority to force kernel prepayment. If processor sets (partition) are created, then each processor is part of the cpupart structure, which integrates a dispatcher—the cp_queue member of cpupart).

Kernel support functions for CPU control are split between CPU management and per-CPU control functions, several of which are executed during system boot to build and initialize the required kernel data structures and bring all processors online. Once the system is up and running, any state changes to CPU will likely be the result of a user-initiated procedure, such as thread binding.

# INTERPROCESS COMMUNICATION

Interprocess communication (IPC) encompasses facilities provided by the operating system to enable sharing of data (shared memory), the exchange of information and data (message queues), and synchronization of access to shared resources (semaphores) between processes and threads on the same system. Contrast to networking-based facilities such as sockets which enable communication over a network, early IPC facilities originated in AT&T Unix V which added support for shared memory, semaphores, and message queues around 1983. This original set of IPC features is generally known as System V IPC. Over time, a similar set of IPC features evolved from POSIX standards, and we now have POSIX semaphores, shared memory, and message queues. System V and POSIX IPC use different APIs and are implemented differently in the kernel, although they provide similar functionality. Other facilities for interprocess communication include memory mapped files (mmap()), named pipes (also known as FIFOs), and Unix domain sockets, which provide RPC-like facility for threads running on the same system. Our goal here is to provide a tutorial on programming with these interfaces, although UNIX Network Programming—Interprocess Communication, 2nd edition, Volume II, by Richard Stevens.

## 10.1 Generic System V IPC Support

Several data structures and low-level routines are common to all System V IPC facilities. In this section, we cover those common areas and then get into the specifics of each IPC implementation. Common interfaces and structures include:

- ipcid structures: Each facility has a data structure that contains various bits of information about the resource. The naming convention used for the data structure is the same across all sets of interfaces (see Table 10-1).
- Keys and identifiers: To share IPC resources across processes (which is the whole point of interprocess communication), a process must be able to uniquely identify a resource when it issues a call. The IPC facilities require a key value in the ipcget(2) call and return an identifier based on the passed key value.
- ipcget(): These common kernel routines are used by the IPC facilities to get the identifier and check access permissions.

### 10.1.1 Module Creation

The System V IPC kernel modules are implemented as dynamically loadable modules. Each facility has a corresponding loadable module in the /kernel/sys directory (shmsys, semys, and msgs). In addition, all IPC methods require loading of the /kernel/misc/ipc module, which provides low-level routines shared by all facilities. The ipcaccess() routine is called to verify access permissions to a particular IPC resource, for example a shared memory segment, semaphore, or message queue. The ipcget() code fetches a data structure associated with a particular IPC resource that generated the call, based on a key value passed as an argument in shget(2), msgget(2), and semget(2) system calls.

When an IPC resource is initially created, a positive integer known as an identifier is assigned to identify the IPC object. The identifier is derived from a key value. The kernel ipcget(2) system call will return the same identifier to processes or threads using the same key value, which is how different processes can sure to access the desired message queue, semaphore, or shared memory segment. ftok(3), or file-to-key interface, is the most common method of having different processes obtain the correct key before they call one of the ipcget(2) routines.

Associated with each IPC resource is an id data structure which the kernel allocates and initializes the first time ipcget(2) system call is invoked with the appropriate flags set. The ipcget(2) system call for each facility returns the identifier to the calling application, again based on arguments passed in the call and permissions. The structures are similar in name and defined in the header file for each facility (see Table 10-1).

The number of ipcid structures available in the kernel is static and determined by each facility's kernel tunable parameter, which is: msgmn, mni, and shmmn determine the maximum number of msgid_ds, semid_ds, and shmid_ds structures available, respectively. Kernel memory for these structures is allocated during the initialization phase of the IPC facility, based on the structure size and ipcmni value.

Most fields in the ipc are unique for each IPC type, but they all include the first member a pointer to an ipcperm structure, which defines the access permissions for that resource, much as access to files is defined by permissions maintained in each file's inode.
