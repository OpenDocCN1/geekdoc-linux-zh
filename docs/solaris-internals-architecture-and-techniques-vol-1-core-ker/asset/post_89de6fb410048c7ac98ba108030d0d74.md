The ufs_inactive() routine attempts to free inodes with no pages in the page cache in preference to inodes that still have pages in the page cache. The goal—to keep as many file pages in the page cache as possible—is realized by the following procedure: inodes that have pages associated with them are placed at the tail of the idle queue, and inodes with no pages are placed at the head of the idle queue. When inodes are removed from the idle queue, they are removed from the tail of the queue, and inodes with no pages are taken first.

The UFS idle thread is awakened when the size of the idle queue exceeds one-fourth of the system-tunable parameter ufs_ninode. When the thread wakes up, it attempts to remove half the inodes from the idle queue, to discard all of the pages associated with the inode, and to free the kernel memory used to store the in-memory inode. Inodes that are removed from the idle queue update kernel statistics in the virtual memory system; you can obtain the statistics with sar. The statistics show how many inodes have pages associated with them in the page cache are freed. Note that the %ufs_ipf column in the sar output for this example shows that almost no inodes have freed associated pages.

# UFS Implementation

## 14.3.4 UFS Directories and Path Names

The file system directory and path-name code are responsible for managing the on-disk directory format and translating file-name lookups into inode references. Four vnode methods implement directory and path-name services: vop_lookup(), vop_readdr(), vop_mkdir(), and vop_rmdir().

Path names are converted to vnode references by the file-system-independent lookup() function. The lookup() function calls into the file system's vop_lookup() method. Directories are traversed by means of the vop_readdr() method; they are created and deleted with the vop_mkdir() and vop_rmdir() methods.

### 14.3.4.1 ufs_lookup()

The ufs_lookup() function traverses the directory to find a matching path name and returns a reference to a vnode for the file. For example, the open system call for a UFS file translates the path name of the file into a vnode by calling lookup(), which calls ufs_lookup() for each component of the path name. Opening /etc/passwd causes vop_lookup() to be called for the root directory /, the etc subdirectory, and the password file passwd.

The ufs_lookup() implementation first searches the directory name lookup cache (DNLC), using dnl_lookup(), to check if an entry exists in the DNLC. If not, the directory is read and searched for the path name. Once located, the path name is entered into the DNLC with dnl_enter(), and an open vnode is returned to the caller.

### 14.3.4.2 ufs_readdr()

The ufs_readdr() method reads chunks of UFS directories from disk and returns them to the caller. The ufs_readdr() method is typically called as a result of the readdir() system call. The raw UFS directory is cached in the file system cache (compared with the DNLC, which caches the inode and path name information for individual files).

# SOLARIS FILE CACHE

One of the most important features of the file system is its ability to cache data, but in Solaris the file cache is implemented in the virtual memory system. In this section, we explain how file caching works and explore the interactions between the file system and the virtual memory.

## 15.1 Introduction to Caching

Traditional Unix implements file caching by keeping copies of recently read disk blocks in the buffer cache. Figure 15.1 shows an example in which the file system caches data through the buffer cache. The file system retrieves the block from disk the first time and caches it in the memory. The old way, the operating system invoked the file system, which looked up the physical block number and retrieved that block from the buffer cache.

![](img/a86367b95bf21add858c99948ac951c6_635_0.png)

Figure 15.1 The Old-Style Buffer Cache

Typically, the old buffer cache is sized statically by kernel configuration. Changing the size of buffer cache requires a kernel rebuild and a reboot.

### 15.1.1 Solaris Page Cache

Solaris has a new method, the page cache, of caching data. The page cache was developed at Sun in SunOS 4 in 1985 and is used by System V Release 4. Page cache derivatives are now also used in Linux and Windows NT. The page cache has two major differences from the old caching method. First, it is dynamically sized and can use all memory that is not being used by applications. Second, it caches files rather than disk blocks. The key difference is that the page cache is a virtual file cache rather than a physical block cache. A virtual file cache allows the operating system to retrieve file data by simply looking up the file and offset. The old way, the operating system invoked the file system and retrieved the physical block.

Figure 15.2 shows the new page cache. When a Solaris process reads a file the first time, file data is read from disk through the file system into memory in page-sized chunks and returned to the user. The next time the same segment of file data is read, it can be retrieved directly from the page cache without a logical-physical lookup through the file system. The old buffer cache is still used in Solaris, but only for internal file system data (which is just the metadata items) that is only known by physical block numbers—direct/indirect blocks and inodes. All file data is cached through the page cache.

![](img/a86367b95bf21add858c99948ac951c6_636_0.png)

Figure 15.2 The Solaris Page Cache

The page cache is implemented in the virtual memory system; in fact, the virtual memory system is architected around the page cache principle. Each page of the physical memory is identified the same as file and offset. Pages associated with files point to regular files, whereas pages of memory associated with process private-memory space point to the swap device.
