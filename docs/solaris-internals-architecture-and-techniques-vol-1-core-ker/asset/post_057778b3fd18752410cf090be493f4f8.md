The TS, IA, and RT scheduling classes are implemented as dynamically loadable kernel modules. The kernel binaries for the TS class are located in the /kernel/sched directory; the IA and RT classes reside in the /usr/kernel/sched directory. Note that most of the support functions for IA classes are handled by the TS class code. There are only a few IA-class-specific routines. The SVS class is an integral part of the kernel and is not built as a dynamically loadable module. The core dispatcher class is also an integral part of the kernel and is loaded with the initial unix and genunix objects at boot time.

From an architectural perspective, the scheduling class implementation follows an object-oriented design similar to the vfs/vnode architecture described in Chapter 10. As the vfs/vnode implementation defined file-system-dependent and file-system-independent routines use macro calls that resolved the file-system-specific code (e.g., VFS_OPEN() -> ufs_open() for a UFS file, the kernel dispatcher comprises scheduling-class-specific and scheduling-class-independent functions; it also uses system-defined macros to resolve a class-specific routine.

## Overview

In Solaris, a system class array is initialized at boot time, each entry in the array is a sclass structure, one for each of the loaded scheduling classes. The sclass structure, shown in Figure 9.3 on page 356, contains the following structure members:

- * cl_name — Pointer to the class name (e.g., TS for timeshare).
- * cl_init — Pointer to the class-specific initialization function (e.g., ts_init() for initialization of the timeshare class).
- * cl_funcs — Pointer to a class functions; a kernel structure containing pointers to the class-specific functions (e.g., fork, stop, sleep, preempt.).
- * cl_lock — A kernel lock for synchronized access to the class structure.
- * cl_count — a counter maintaining a count of threads attempting to load the class.
- * cl_size — The size in bytes of the class data maintained on a per-thread basis. The size of the structure referenced through the kernel threads t_clidata pointer.

The init routine is called at boot time for all the preloaded scheduling classes. By default, the timeshare and system classes are loaded. The interactive class is dynamically loaded when X Server and Window Manager are started. Only the real-time class is not loaded in a default environment. When a thread is set to the real-time class, with the proccnt(1) command or proccnt(2) system call, the real-time class module is dynamically loaded by the operating system. (Operations vector table is a generic term that describes an array of pointers to functions, which is precisely what the class functions cl_funcs structure is.)

The class functions structure bundles together function pointers for all of the class-specific (scheduling-class-dependent) kernel routines. They essentially fall into one of categories: class management and thread control. The kernel switches in to the appropriate routine for a specific scheduling class, essentially the same method used in the vfs/vnode structure. A set of macros is defined; the macros resolve to the class-specific function by indexing through either the current kernel thread pointer or the system class. Both the system class and kthread structure maintain a pointer to the class functions structure. For example, the class-specific interclass and exitclass functions are indexed through the system class. (The functions must be called to enable a thread to enter or exit the scheduling class because the kernel thread link to the class operations table would not be in place.)
