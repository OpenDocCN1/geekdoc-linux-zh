Access to the kernel data required to satisfy the client requests is synchronized with the proc structure's mutex lock, plock. This approach protects the per-process or LWP kernel data being accessed by more than one client at a time.

Writes to procfs files are much less frequent. Aside from the directives to create data files on command, writes are predominantly to the process or LWP control file (ctl) to issue control messages. Control messages (documented in proc(1)) include stop/start messages, signal tracing and control, fault management, execution control (e.g., system call entry and exits stops), and address space monitoring.

**Note:** We've discussed I/O operations on procfs files in terms of standard calls because those are currently the only way to access the /proc files from developer-written code. However, there exists a set of interfaces specific to procfs that are used by the proc(1) commands that ship with Solaris. These interfaces are bundled into libproc.so library and are not currently documented or available for public use. The libproc.so library is included in /usr/lib distribution, but the interfaces are evolving and not yet documented. Plans are under document these libproc.so interfaces and make them available as a standard part of Solaris APIs. The diagram in Figure 8.20 shows more than one path into procfs. Typical developer-written code makes use of the shorter system call path, passing through the vnode layer as previously described. The proc(1) command is Multithreaded Architecture built largely over libproc.so. The need for a set of interfaces specific to procfs is twofold: an easy-to-use set of routines for development reduces the complexity of using a powerful kernel facility; especially a multithreaded process, requires a layer of code that really belongs at the application programming interface (as opposed to kernel level). The developer controls a process by writing an operation (optional) to the first 8 bytes of the control file (or 16 bytes if it's LP64). The control file write path is through the vnode layer and ultimately terminates procfs. The implementation allows multiple control messages (operations and operands) to be sent to the control file in a single write. The pwrichtctl() code breaks multiple messages into distinct operation/operand pairs and passes them to the control() function, where the appropriate flags are set at the process or LWP level as a notification that a control mechanism has been injected (e.g., stop on event). Table 8-3 lists the possible control messages (operations) that are currently implemented. We include them here to provide context for the subsequent descriptions of control functions, as well as to illustrate the power of proc(1) manual page and /usr/include/sys/procfs.h.

## Table 8-3 procfs Control Messages

| Control Message | Operand (arg) | Description |
| :--- | :--- | :--- |
| PCSTOP | n/a | Requests process or LWP to stop; waits for stop. |
| PCDSTOP | n/a | Requests process or LWP to stop. |
| PCSTOP | n/a | Waits for the process or LWP to stop. No timeout implemented. |
| PCTSTOP | timeout value | Waits for stop, with millisecond arg. |
| PCRUN | long | Sets process or LWP runnable. Any arg can specify clearing of signals or faults, setting step mode, etc. |
| PCSIG | n/a | Clears current signal from LWP. |
| PCFAULT | n/a | Clears current fault from LWP. |
| PCSIGSIG | siginfo_t | Sets current signal from siginfo_t. |
| PCKILL | long | Posts a signal to process or LWP. |
| PCUNKILL | long | Deletes a pending signal from the process or LWP. |
| PCSHOLD | sigset_t | Sets LWP signal mask from arg. |
| PCTRACE | sigset_t | Sets traced signal set from arg. |
| PCFAULT | flyset_t | Sets traced fault from arg. |
| PCSENTRY | sysset_t | Sets tracing of system calls (on entry) from arg. |
| PCSEXIT | sysset_t | Sets tracing of system calls (on exit) from arg. |
| PCSET | long | Sets mode(s) in process/LWP. |
