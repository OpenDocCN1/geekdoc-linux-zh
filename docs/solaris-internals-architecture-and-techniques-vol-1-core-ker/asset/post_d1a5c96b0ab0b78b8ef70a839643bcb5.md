## 4.2.5 Creating Kernel Structures, Resources, and platmod, and the CPU Components

With all the core binary objects (unix, krtld, genunix, kernel module) loaded into memory and linked, krtld passes control to unix, which is loaded near the top of physical memory space, to take over execution. The Solaris kernel is now running, the Memory Management Unit (MMU) is enabled (the code is generating virtual addresses and working in virtual address space), and the first 16 megabytes of memory are mapped. unix does some low-level setup of processor registers, begins hand-crafting kernel thread 0, and calls an architecture-specific startup function, mlset(1). mlset() completes the initialization of kernel thread 0 and LWP 0, builds the first process (p0), and begins mapping system devices to device information in the OBP space.

The EEPROM on SPARC systems, which holds the OBP code, is one of the early devices mapped. That is, the eep occupies a part of the system's physical address space, much like a physical device. A kernel software layer is initialized, very similar to a device driver, allowing other areas of the kernel to call into the PROM. Calls into the PROM are required during the boot process for a variety of reasons, such as the retrieval of hardware and version information.

With the mlset() work done, the kernel main() function is entered, which is where the code begins a sequence of function calls into the higher-level areas of the kernel to continue the initialization process. The main() function is part of the kernel hardware-independent code. It immediately calls into hardware-specific routines for specific initialization steps, then returns to the common code to complete the boot process.

## Kernel Bootstrap and Initialization

The platform-specific startup() function does some preliminary initialization: determining available physical memory after the core kernel is loaded, setting up the kernel address space symbols, and allocating memory page structure. The kernel memory allocation (KVM) subsystem and the kernel kstat (kernel statistics) framework are initialized Once these steps are completed, the operating system banner is displayed on the console:

SunOS 5.7 Version Generic 64-bit [UNIX(R)] System V Release 4.0
Copyright (c) 1983-1998, Sun Microsystems, Inc.

Additional platform-specific checking is done on processor types, firmware versions, etc., and the kernel mod_read_system_file() function is called to read the /etc/system file and populate internal data structures with the parameters and values in /etc/system.

The kernel creates a linked list of sysparam data structures, such that each entry on the /etc/system file has a corresponding data structure in the list. The sysparam structure is defined in /usr/include/sys/sysconf.h, and is shown below:

```
* For each entry in /etc/system a sysparam record is created.
struct sysparam {
    struct sysparam *next;      /* pointer to next *
    int sys_type;               /* type of record */
    int sys_op;                 /* operation *
    char *sys_modname;          /* module name (null if param in kernel) *
    char *sys_ptr;              /* pointer to device, etc. *
    unsigned long_t sys_info;  /* additional information */
    char *sys_config;           /* configuration data */
    int sys_len;                /* len of data */
    unsigned long *addrp;      /* pointer to valocced addresses *
};
```

### Header File <sys/sysconf.h>

The fields in the sysparam structure are generally self-explanatory. Space is defined for parameter-specific information, the parameter type (e.g., a module entry or an entry to set a value), and the necessary pointer to maintain the linked list. The mod_read_sys_file() code walks through each line to determine the entry types and setting the appropriate values in the sysparam structure that correspond to the line entry in /etc/system. When mod_read_sys_file() is finished, a list of populated sysparam structures is established in kernel memory.

Before mod_read_sys_file() returns, the code sets the maxusers value. The maxusers parameter is calculated on the basis of the amount of physical memory installed on the system, where maxusers equals the number of megabytes of RAM, to a maximum value of 1024 (which equates to 1 gigabyte of RAM–on-system items with greater than 1 gigabyte of physical memory, maxusers will be 1024).

maxusers is set in /etc/system, that value is used, up to a maximum value of 2048; any /etc/system maxusers value larger than 2048 results in maxusers setting to 2048. Once maxusers is established, the startup code sets other ker-limits, based on maxusers in the kernel param_calc() function.

- maxpid — Maximum process ID value. If pidmax is set in /etc/system, the pidmax value will be tested against a minimum reserved_procs (5 in Solaris 2.5.1, 2.6, and 7) and a maximum value (30,000 in all three releases). If pidmax is less than reserved_procs or greater than 30000, it is set to 30000. Otherwise, the user-defined value is set.
- maxnproc — Maximum number of processes, systemwide, set as (10 + 16 * maxusers).
- maxprucs — Maximum processes per non-root user, set as (maxnproc-reserved_procs), reserved_procs has a default value of 5.
- ufs inode and nsize — High limits for the UFS inode cache and directory name. (See "The Directory Name Lookup Cache (DNLC)") on page 557). Both of these caches are set to the same value, (4 (max_nproc + maxusers) + 320).
- ndquot — The number of UFS disk quota structures, systemwide, set as ((maxusers * 40) / 4) + max_nproc.

As you can see, maxusers is not really the maximum number of users the system can support. It's simply a parameter that can be set to drive the number of several configurable kernel resources that indirectly affect the load or volume of users system can handle. Many things factor in to the user load capabilities of system, not the limit of what constitutes a user, what a user does, and how a kernel connects to the system.

Other kernel parameters that are related to the STREAMS subsystem and miscellaneous areas of the system are also set at this time. These parameters use hard-coded default values that are not driven by the maxusers parameter unless value has been set in /etc/system.

- nstrpush — Number of STREAMS modules that can be contained (pushed) on a single STREAM; set to 9.
- strmsgs — Maximum size of a STREAMS message; set to 64 Kbytes.
- strctlsz — Maximum size of a STREAMS control message.
- groups max — Maximum number of groups a user can belong to; set to 16.
- rstown — A boolean that forces POSIX chown(1) behavior, where process must have an effective UID of 0 (root) to change file ownership; set to 1 (true) by default.

- rlimit — hz, hires_hz, tick — Clock frequency. hz is set to 100, hires_hz to 1000, tick to 0. hz and hires_hz should not be altered. You can set hires_tick to 1 in /etc/system. Doing so results in an value of 1000 (every millisecond) versus the default of 100 (every 10 milliseconds).
- autoup — Age in seconds of a dirty page before flush will write it to disk; set to 30.
- rlimits — Per-process resource limits. Default values are set. Per-process file descriptor limits can be set through /etc/system, with rlim_fd max for the maximum value and rlim_fd_cur for the current value (current can never exceed the maximum).

Moving along with the system initialization process: The system device name is established in the /devices directory, based on the device tree created by the OBP. The system call table is initialized, and the kernel loads the device driver classes file, /etc/driver_classes. System parameters are set in the var structure; most of these are values that we have previously discussed (e.g., max_nprocs), and others are not used in the Solaris kernel (var is somewhat outdated SV4 holdover). You can examine the relevant data in var with the sysctl(1M) command or with the var function in crash(1M).

Kernel module occurs at various points in the boot process. During the platform-specific startup, several core modules, such as the swap, specs, profs and tod (time-of-day clock driver), are initialized. Other module loading occurs when a specific kernel subsystem is initialized, the scheduling classes are loaded during the dispatch(1) function, which initializes the kernel dispatcher subsystem. These module loads (and dispatch()) occur before the platform-specific startup returns to the main() function. Other loadable modules are platform specific are loaded a little later in the process. Examples include modules specific to the UltraEnterprise E3500 (E6500 servers that support support environmental monitoring and specific control functions).

Additional virtual memory support is initialized (the HAT layer and segment drivers); the specs and swaps file system support modules are loaded and initialized; the root, swap and dump devices are configured; and the kernel table is set for foreload through the /etc/system file are loaded; and traps were handled through the trap table set in the OBP up to this point.
