The acquisition of a RW lock and subsequent behavior if the lock is held straightforward and similar in many ways to what happens in the mutex case. Things get interesting when a thread calls rw_exit() to release a lock it holds—there are several potential solutions to the problem of determining which thread gets the next lock. We saw with mutex locks that a change was made for Solaris 2.6 (previous releases) to Solaris 7 in the wakeup mechanism. A wakeup is issued on all threads that are waiting, waiting for the mutex in Solaris 7, and from empirical data that this solution works for reasons previously discussed. With RW locks, we're dealing with potentially longer hold times, which could result in more sleepers, a desire to give priority over readers (why let a reader in a thread is apparently waiting to change the data?), and the potential for the priority inversion problem described in “Turnstile and Priority Inheritance” on page 88.

For rw_exit(), which is called by the lock holder when it is ready to release the lock, the simple case is that there are no waiters. In this case, the wrlock is cleared if the holder was a writer, or the hold count is decremented to reflect one less reader. The more complex case of the system having waiters when the lock is released is dealt with in the following manner:

- The kernel does a direct transfer of ownership of the lock to one or more of the threads waiting for the lock when the lock is released, to the next writer or a group of readers if more than one reader is blocking and no writers are blocking.

This situation is very different from the case of the mutex implementation, where the wakeup is issued and a thread must obtain lock ownership in the usual fashion. Here, a thread or wakeup up owning the lock they were blocking on.

The algorithm used to figure out who gets the lock next addresses several requirements that provide for generally balanced system performance. The kernel needs to minimize the possibility of starvation (a thread never getting the resource it needs to continue executing) while allowing writers to take precedence whenever possible.

- rw_exit_wakeup() resets for the simple case and drops the lock if there are no waiters (clear wrlock or decrement the hold count).

- When waiters are present, the code grabs the kernel (sleep queue) associated with the lock and saves the pointer to the kernel head of the next waiter that was on the turnstile's sleep queue (if one exists).

The turnstile sleep queues are organized as a FIFO (first in, first out queue), so the queue management (turnstile code) makes sure that the thread that was waiting the longest (the first in) is the thread that is selected as the next writer (first out). ## Reader/Writer Locks

The remaining bits of the algorithm go as follows:

- If a writer is releasing the write lock and there are waiting readers and writers, readers of the same or higher priority than the highest-priority blocked writer are granted the lock.
- The readers are handed ownership, and then woken up by the turnstile_wakeup() kernel function in Solaris 7.
- These readers inherit the priority of the writer that released the lock if the reader thread is of a lower priority (inheritance is done on a per-reader basis when more than one thread is being woken). Lock ownership handoff is relatively simple operation. For read locks, it's a matter of setting the hold count in the lock to reflect the number of readers coming off the turnstile, issuing the wakeup of each reader.
- An exiting reader always grants the lock to a waiting writer, even if there are higher-priority readers.

It is possible for a reader freeing the lock to have waiting readers, although it may not be intuitive, the multiple reader design of the lock. If a reader is holding the lock and a writer comes along, the rw bit is set to signal that a writer is waiting for the lock. With allant, subsequent readers cannot get the lock–we want the holding readers to finish so the writer can get the lock. Therefore, it is possible for a reader to execute rw_exit() with waiting writers and readers. The “favor writers but be fair to readers” policy above was first implemented in Solaris 2.6.

| rw_waiters | holder count |

**Figure 10 Solaris 2.6 Reader/Writer Lock**

Note that the lock fields are functionally identical to those in Solaris 7, just implemented differently. rw_wwwh provides a writer, write-wanted bit, and a count of readers holding the lock. rw_waiters points to the turnstile holding the waiters. The rw_wlock field serves as the actual write lock (bit 2) and dispatcher lock to synchronize access to the waiters and wanted bits. (Dispatcher locks are described in “Dispatcher Locks” on page 6.)

| rw_wlock | |

**Figure 11 Solaris 2.5.1 RW Lock Structure**

Solaris 2.5.1 defines several RW lock types, stored in the type field when the lock is initialized. In practice, the RW_DEFAULT type is used almost the time, except some device drivers specify an RW_DRIVER lock. Other types include locks designed to gather statistics. Such locks are only used internally and are not implemented on production releases. Their enablement requires a specific compile-time flag set.

The rwlock is essentially the same as that of the Solaris 2.6 implementation, serving as dispatcher lock to synchronize access to waiters and wanted bits and the actual lock. The owner field contains the address of the kernel thread that owns the lock. wanted, when set, signifies that a thread is waiting for a rw lock, and holdcnt represents the number of kernel threads holding the lock or -1 to signal that the lock is currently held. Solaris 2.5.1 implements a separate union in the RW lock structure for wanted and holdcnt.

The next salient differences in the Solaris 2.5.1 RW lock implementation are that the code is written in C (no assembly language entry points), and mutex locks are used to protect the internal data in the lock code. An array of mutex locks, rw_mutex[], is initialized at system boot with a fixed number (32) of mutex locks. During execution, a hash function indexes into the array, hashing on the address of the RW lock being requested (or released).

When the various RW lock functions are entered, a mutex is retrieved from the rw_mutex[] array, based on the address of the RW lock passed in the calling function. The mutex_enter() call is made to acquire the mutex to do an RW lock operation before the code executes, and the mutex is released when the function is ready to exit.

Kernel threads call rw_enter() to acquire a RW lock, passing the address of the lock and a flag that tells whether a reader or writer is required.

Here's the sequence for a read lock request:

- If a read lock is requested, the mutex lock is acquired to protect the RW lock code and a test for either the RW lock being held (holdcnt is -1) or a writer writing (wanted is set) is made. If neither is true, the caller can obtain a read lock.
- The holdcnt is incremented, and the calling thread has its t_kpri_req flag set to tell the dispatcher that a kernel (SYS) priority is requested.
- The mutex is released and the code returns to the caller.
- If a writer is holding the lock or a write lock request is pending, the thread is set to block. The mutex is released, and the cpu_sysinfo.rw_rdfails counter is incremented.

Setting this flag boosts the priority of the thread holding the lock if it's a timeshare or interactive class thread, with the intent to expedite the execution while it's holding the lock and minimize the hold time.

You can examine this counter with mpstat(1M). The sw column displays the sum of all failed reader and writer lock attempts.

- The code tests the lock's waiters field, which contains the ID of a turnstile if there are already waiters. No waiters means we must allocate a turnstile from the free pool; one more waiters means we just need to locate the turnstile holding the other waiters and put the lock on sleep queue.
- Before putting the thread on the turnstile and changing the thread state to sleep, the code tests the lock again (it may have been released by now). If it is available, the path previously described for an available lock is taken. Otherwise, the turnstile block code is called to place the thread on the sleep queue.
- The priority inversion condition is tested with the pi_willto() code, and the swtch() function is called for entry to the dispatcher.
