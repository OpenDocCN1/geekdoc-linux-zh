The new memory architecture first introduced with SunOS 3.2 allows a new way of doing file I/O, that is, by mapping a file directly into the process's address space. The mmap system call allows us to map a range of a file into a process's address space; then, the file can be accessed by references to memory locations with C pointers. This approach allows us to do I/O on the file without the overhead of the read and write system calls and without handling the data twice. Figure 11.4 illustrates the process.

![](img/a86367b95bf21add858c99948ac951c6_544_1.png)

Figure 11.4 Memory Mapped File I/O

The function definition for the mmap(2) system call is shown below.

```
void *mmap(void *addr, size_t len, int prot, int flags, int infd, off_t offset);
```

# Header File <sys/mman.h>

The mmap system call is called with an open file handle, the offset and length of the file being mapped, the address and length at which the file should be mapped in a process's address space, a flag for options, and a protection type indicating what memory protection should be used for the mapping, as shown below.

```c
if ((addr = mmap((NULL,0), length, PROT_READ,
      MAP_SHARED, fd, offset)) == NULL) {
    perror("mmap failed");
    return(1);
}
```

The operating system uses the memory map function to map executable files and shared libraries into a process's address space. You can list the mappings for a process with the mmap(1) command.

# 11.5.1 Mapping Options

Certain flags allow different options to be passed to mmap to control how a file is mapped into the process's address space (see Table 11-7). These are passed through the flags argument.

# Memory Mapped I/O

# Table 11-7 Solaris 7 mmap Flags from <sys/mman.h>

| Type | Description |
| --- | --- |
| MAP_FIXED | Maps at the address supplied. |
| MAP_NORESERVE | Does not reserve swap space for this mapping. |
| MAP_SHARED | Changes are reflected across all mappings. |
| MAP_PRIVATE | Changes are not reflected; a copy of the page is made so that the changes are local |

The MAP_FIXED option requests the file be mapped exactly at the address supplied by *addr*. If MAP_FIXED is not set, the system uses *addr* to derive an address used to map the file. The address chosen will be an area of the address space that the system deems suitable for a mapping of *len* bytes. If MAP_FIXED is not set and *addr* is 0, the system chooses the address to map the file range into. If MAP_NORESERVE option is specified, no swap space is reserved for mapping. Without this flag, the creation of a MAP_PRIVATE mapping reserves swap space equal to the size of the mapping. When writing into a MAP_NORESERVE segment, if space is available, the write succeeds and a private copy of the written page is created; if space is not available, the write fails and a SIGBUS or SIGSEGV signal is delivered during writing.

# 11.5.1 Mapping Files into Two or More Processes

A file can be mapped into more than one process when another process calls mmap on the same file with an overlapping range. The system does this by mapping the same pages into each address space. When this mapping occurs, the memory is shared between the processes, and by default, each process sees all modifications made by another process. This behavior can be an alternative method of sharing memory. In fact, the POSIX interprocess communication facility for shared memory is built on mapping files. Options MAP_SHARED and MAP_PRIVATE can be passed to mmap to allow different semantics, rather than the default of sharing everything. If MAP_SHARED is specified, write references will change the memory that is shared by all processes with mappings. If MAP_PRIVATE is specified, the initial write creates a private copy of the memory, and from this point on, the process will have a private copy of that page of the mapping.

# 11.5.2 Permission Options

The address range is created in the process's address space with the permissions provided with the *prot* argument. The permissions control whether a process can read, write, or execute memory within the memory range. The protection/permission options are shown in Table 11-8.

# Table 11-8 Solaris mmap Protection Options from <sys/mman.h>

| Type | Description |
| --- | --- |
| PROT_READ | Data can be read. |
| PROT_WRITE | Data can be written. |
| PROT_EXEC | Data can be executed. |
| PROT_NONE | Data cannot be accessed. |

If we examine the mappings for ksh from our previous pmap example, we can see that the first portion of ksh is mapped read-only/execute, and the second half is mapped read/write/execute.

```
00010000  192K read/exec    /usr/bin/ksh
00048000   8K read/write/exec /usr/bin/ksh
```

If a process were to attempt to write to the memory range between 0x010000 and 0x04000, a SIGSEGV would be sent to the process to notify that a segmentation violation occurred. Incidentally, the first segment is the text portion of the process, which is always read-only, and the second mapping is the data section for uninitialized variables, both of which are shared among processes. The second segment is mapped read/write with MAP_PRIVATE; so, if a process updates an initialized variable (say, i=1), that variable does not change across all ksh processes. Rather, a copy-on-write operation creates a local page, which is used to hold a page-length mapping for the file at that location, private to the process.

# 11.5.2 Providing Advice to the Memory System

We can advise the memory system about the pages of memory within the range of the mapping using the madvise system. The madvise system allows us to tell the memory system if we don't need a range of memory or if we are going to access the memory in a sequential or random order. This information allows the memory system and file systems to proactively read in portions of the file with the range of memory.

```c
int madvise(caddr_t addr, size_t len, int advice);
```

Header File <sys/mman.h>

The advice is given for a memory range and is specified with the advice argument. The arguments may be one of MADV_DONTNEED, MADV_WILLNEED, MADV_SEQUENTIAL, or MADV_RANDOM.

# 11.5.2.1 The MADV_DONTNEED Flag

When we map a file into a process's address space and read the file by touching memory locations, we allocate physical memory for that range and fill the memory with the respective range of the file. Once we are done with that range of the file, we may never want it again in which case we can let the operating system know that this memory range is no longer needed. This notification is especially important since the memory is not freed when we unmap the memory segment. The MADV_DONTNEED flag allows us to give back memory for a given range. The following example shows how this can be done.

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>
#include <sys/macros.h>
#include <sys/types.h>
#include <fcntl.h>
#include <sys/mman.h>

void main(int argc, char ** argv)
{
    int fd;
    caddr_t addr;
    off_t size;
    off_t length;
    off_t offset;
    off_t chunk = 1<<30;

    if (argc != 1) {
        (void) fprintf(stderr, "Usage: mmap_out filename\n");
        exit(1);
    }
    if ((fd = open(argv[1], O_RDONLY)) < 0) {
        perror("Open failed");
        exit(1);
    }

    size = lseek64(fd, (off_t)0, SEEK_END);
    /*
     * mmap a chunkwise segment and issue madvise(DONTNEED)
     * against it.
     */
    for (offset = 0; offset < size; offset += chunk) {
        length = MIN(size - offset, chunk);
        if ((addr = mmap64((caddr_t)0, length, PROT_READ|PROT_WRITE,
                            MAP_SHARED, fd, offset)) == NULL) {
            perror("mmap failed");
            exit(1);
        }
        (void) madvise(addr, length, MADV_DONTNEED);
        (void) munmap(addr, length);
    }
}
```
