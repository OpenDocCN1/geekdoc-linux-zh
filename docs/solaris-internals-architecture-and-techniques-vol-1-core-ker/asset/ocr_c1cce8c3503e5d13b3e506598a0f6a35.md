Processes are put in the IA class by an IA-specific routine, ia_set_process_group(), which is called from a STREAMS ioctl(strioctl I/O controls, supported by all character device drivers when a TTY is taken by a new process group. It is rooted in the STREAMS-based terminal driver code. If you were to boot your Solaris desktop system and not starting a window system, you would not have any IA processes running (Just TS and the SYS class Solaris daemons). When the windowing system starts, it takes over control of the “terminal,” in the case of a desktop is a keyboard, mouse, and the graphics card interface to the monitor.

The takeover gets the set-process-group ioctl, which ultimately calls the CL_SET_PROCESS_GROUP macro. This macro resolves to the ia_set_process_group() IA-class function since the caller is an active process (the windowing system sees to that). All the processes associated with the windowing system are in the IA class. Since processes and threads inherit their scheduling class from the parent, newly created processes (terminal windows, applications) are also put in the IA. IA classes are given a priority boost of 10, which is factored in the thread's user mode priority when calculation is done, that time a thread's priority is adjusted. Recall that the user priority is the sum of ts_cuppri, ts_upri, and ts_boost. (ts_boost has a fixed value of 10 for IA class threads.)

Processing for an RT class is much simpler; RT priorities are fixed, they do not get better or worse during the execution of the thread. The only way the priority of an RT class changes is if it is explicitly changed as the result of pricntl(). When a thread enters the scheduling class (rt_enter()) through pricnt(), the RT class priority, rt_pri in the rtproc structure, is set to the default of 0 unless a priority has been specified; in that case, rt_pri will reflect the requested priority (provided rt_quantum value from the RT dispatch table corresponds to the row number, as indexed by the priority). For example, the default RT class priority of 0 defines a time quantum of 1000, which translates to 1000 milliseconds, or 100 clock ticks (see description of RES in “Dispatch Tables” on page 356).

If the thread is currently running on a processor, the thread's global priority is set in ts_pri, and the code looks at the dispatch queue to determine whether the current thread has a priority greater than the highest-priority thread sitting on a dispatch queue. If it does, rt_time is left to rt_quantum, and the thread is allowed to continue running; otherwise, it is forced to surrender the processor.
