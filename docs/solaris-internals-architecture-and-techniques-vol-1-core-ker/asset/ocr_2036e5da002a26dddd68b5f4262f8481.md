# 6.2.4.2 Object Caching

The slab allocator makes use of the fact that the time objects are heavily allocated and deallocated, and many of the slab allocator's benefits arise from resolving the issues surrounding allocation and deallocation. The allocator tries to defer most of the real work associated with allocation and deallocation until it is really necessary, by keeping the objects alive until memory needs to be returned to the back end. It does this by telling the allocator what the object is being used for, so that the allocator remains in control of the object's true state.

So, what do we really mean by keeping the object alive? If we look at what subsystem uses objects for, we find that a memory object typically consists of two components: the header or description of what resides within the object and associated locks; the actual payload that resides within the object. A subsystem typically allocates memory for the object, constructs the object in some way (a writer heads inside the object or adds it to a list), and creates locks required to synchronize access to the object. The subsystem must deconstruct the object, release locks, and return the memory to the allocator. When finished with the object. In a short, subsystem typically allocates, constructs, deallocates, and frees the object.

If the object is being created and destroyed often, then a deal of work is expended constructing and deconstructing the object. The slab allocator does away with extra work by caching the object in its constructed form. When the client asks for a new object, the allocator creates or finds an available constructed object. When the client returns an object, the allocator does nothing other mark the object as free, leaving all of the constructed data (header information and locks) intact. The object can be reused by the client subsystem without needing to construct or deconstruct—the construction and deconstruction is only done when the cache needs to grow or shrink. Deconstruction is deferred until the allocator needs to free memory to the back-end allocator.

To allow the slab allocator to take ownership of constructing and deconstructing objects, the client subsystem must provide a constructor and destructor method. This service allows the allocator to construct new objects as required and then deconstruct objects later, asynchronously to the client's requests. The kmem_cache_create() interface supports this feature by providing a constructor and destructor function as part of the create request.

The slab allocator also allows slab caches to be created with no constructor or destructor, to allow simple allocation and deallocation of simple raw memory objects.
