# Kernel Bootstrap and Initialization

+   * hz, hires_hz, tick — Clock frequency controls. hz is set to 100, hires_hz to 1000, hires_tick to 0. hz and hires_hz should not be altered. You can set hires_tick to 1 in /etc/system. Doing so results in an value of 1000, causing the system to generate a clock interrupt 1000 times a second (every millisecond) versus the default of 100 times a second (every 10 milliseconds).
* autoup — Age in seconds of a dirty page before flush will write it to disk; set to 30.
* rlimits — Per-process resource limits. Default values are set. Per-process file descriptor limits can be set through /etc/system, with rlim_fd max for the maximum value and rlim_fd_cur for the current value (current can never exceed the maximum).

For a complete list of tunable parameters, see [5]. See also Appendix A, “Kernel Tunables, Switches, and Limits”

Moving along with the system initialization process: The system device name is established in the /devices directory, based on the device tree created by the OBP firmware. The system call table is initialized, and the kernel loads the device driver classes file, /etc/driver_classes. System parameters are set in the var data structure; most of these are values that we have previously discussed (e.g., max_nprocs), and others are not used in the Solaris kernel (var is a somewhat outdated SV4 holdover). You can examine the relevant data in the var with the sysctl(1M) command or with the var function in crash(1M).

Kernel module occurs at various points in the boot process. During the platform-specific startup, several core modules, such as the swap, specs, profs and tod (time-of-day clock driver), are initialized. Other module loading occurs when a specific kernel subsystem is initialized, the scheduling classes are loaded during the dispatch(1) function, which initializes the kernel dispatcher subsystem. These module loads (and dispatch()) occur before the platform-specific startup returns to the main() function. Other loadable modules are platform specific are loaded a little later in the process. Examples include modules specific to the UltraEnterprise E3500 (E6500 servers that support support environmental monitoring and specific control functions).

Additional virtual memory support is initialized (the HAT layer and segment drivers); the specs and swaps file system support modules are loaded and initialized; the root, swap and dump devices are configured; and the kernel table is set for foreload through the /etc/system file are loaded; and traps were handled through the trap table set in the OBP up to this point. The system displays the memory values for actual, installed physical memory
