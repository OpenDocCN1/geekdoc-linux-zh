Note the flags field, which is the cpu_flags member. This example represents the state after bootstrap of a CPU that has not flagged its state altered explicitly. Following initialization, the set cpu_flags bits are CPU RUNNING, CPU READY, CPU EXISTS, and CPU ENABLE. Below is an example of the use of psinfo(1M) and psadm(1M) to display CPU status and take a CPU offline.

```
# psinfo
0 on-line since 04/26/00 14:39:27
1 on-line since 04/26/00 14:39:31
# psadm -f 1
# psinfo
0 on-line since 04/26/00 14:39:27
1 off-line since 04/26/00 21:48:51
```

Another look at the CPU structures with adb(1), specifically the structure for CPU ID 2 (the CPU taken offline), shows that the CPU states (cpu_flags) are CPU RUNNING, CPU READY, CPU QUIESCED, CPU EXISTS, and CPU OFFLINE. Taking the CPU offline results in the CPU_QUIESCED and CPU OFFLINE flags setting the CPU ENABLE flag cleared. This demonstrates that the CPU state flags may not always appear as expected if examined online or with debugger. You might expect that taking the CPU offline would result in CPU RUNNING or CPU_READY to be cleared. The dispatcher uses CPU_QUIESCED and CPU_OFFLINE bits to determine if a CPU is active and should participate in kernel threads.

Solaris 7 added the ability to remove a CPU from the interrupt pool, meaning that an administrator can call psadm(1) to tell the kernel not to send interrupts; instead the kernel should keep the processor online so it will continue to schedule threads. This functionality is mostly useful when used in conjunction with processor binding (binding a process or kernel thread to processor) for real-time applications that require some bounded dispatch latency for scheduling. Using psadm(1) to disable interrupts on a processor results in the CPU ENABLE flag being cleared; the other flags remain set. Table 9-5 summarizes the CPU state flags.

| State | Flags |
|---|---|
| After boot/initialization | RUNNING, READY, EXISTS, ENABLE |
| Interrupts disabled | RUNNING, READY, EXISTS |
| Offline | RUNNING, READY, QUIESCED, EXISTS, OFFLINE |
| Offline and interrupts disabled | RUNNING, READY, QUIESCED, EXISTS, OFFLINE |

Note that there is no difference in the CPU state if the CPU is offline (psadm -f) or if the CPU is offline and interrupts are disabled (psadm -f -i). Offline implies that interrupts are disabled for a CPU. Processor control can happen at several levels. Under normal circumstances, the kernel initializes processors at boot time, and those participate in interrupt handling, cross-call activity, and kernel thread scheduling. Processor state changes, online-to-offline and interrupt enable/disable, are driven by command or can be done programmatically by system calls. Additionally, processor management, the creation and management of processor sets, thread-to-binding, etc., are also done either at command or programming level. The commands and APIs used for processor control and management are summarized in Table 9-6.

### Table 9-6 Processor Control Interfaces

| Command (1M) or Interface (2) | Description |
|---|---|
| psinfo(1M) | Displays processor status and information. |
| processor_info(2) | Gets processor type and status. |
| psadm(1M) | Changes processor state (offline/online, disable/enable). |
| p_online(2) | Programmatically changes processor state (online/offline, disable/enable). |
| pbind(1M) | Binds (or unbinds) a process to a CPU. |
| processor_bind(2) | Binds (or unbinds) a process from a CPU. |
| psrset(1M) | Creates, manages processor sets. Binds/unbinds processes to/from a processor set. |
| pset_bind(2) | Binds/unbinds a process or LWP to/from a processor set. |
| pset_info(2) | Gathers information about a processor set. |
| pset_create(2), pset_destroy(2), pset_assign(2) | Creates or destroys a processor set. Assigns a CPU to a processor set. |

The commands listed in Table 9-6 are built on the system calls created for processor control and management listed in the same table. State changes discussed in the previous pages are driven by psadm(1M) or the p_online(2) system call.

## 9.5.2 Processor Sets

The Solaris enables processor sets to be configured, where some number of processors (one or more) are grouped into a processor set for resource management and application binding. Processes can be bound to a processor set or a single processor. Internally, processor sets are referred to as CPU partitions. Some future release may possibly distinguish between a processor partition in the kernel and a processor set as seen by users of the system. Up to including Solaris 7, processor sets and processor partitions are the same thing.

Processor binding can happen in two ways: using the traditional bind commands or interfaces for processors that have not been configured into a processor set, or by using processor sets and the associated bind methods specific to processor sets.

The original (and still supported) method of binding a process to a CPU was through the pbind(1M) command and processor_bind(2) system call. Bindings created with each method result in the LWPs of the process scheduling only on the CPU that the process is bound to. It is not an exclusive binding; other LWPs in the system may get scheduled on the CPU. It is also possible that other CPUs will do processing on behalf of the bound LWPs. If an LWP issues an I/O, the I/O may be processed on another CPU, interrupting the process when the I/O is complete. Using the command interface, pbind(1M), we can bind the process level. The kernel supports LWP-level binding, where different LWPs in the same process could be bound to different CPUs. This binding can be done programmatically with processor_bind(2), by which you can specify an LWP ID.

Solaris 2.6 added processor sets, and with processor sets another method of binding processes to CPUs. Recall that a processor set is a user-level abstraction of a grouping of processors. In the kernel, all processors in the same set are part of the CPU partition. Once a processor set is created (prset_id), the processors in the set are no longer available for running all kernel threads systemwide. Rather, they will only run kernel threads (LWPs) that have been bound to the processor set with prset(1M) or pset_bind(2).
