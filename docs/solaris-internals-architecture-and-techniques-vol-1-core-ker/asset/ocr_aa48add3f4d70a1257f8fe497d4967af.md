In this example, VOP LOOKUP() will resolve to the procs pr_lookup() function, which will access permissions check and vector to the appropriate proc function based on the directory file type, for pr_lookup_piddir() to perform a lookup on /proc/<PID> directory. Each of the pr_lookup_xx() directory functions does some directory-type-specific work and calls prgetname() to fetch the name.

prgetname() creates the prnode (which includes the embedded vnode) for the /proc file and initializes all of the prnode and vnode files. For /proc and LWPID directories (/proc/<PID>, /proc/<PID>/lw/<LWP>), the prcommon structure is created, linked to the prnode, and partially initialized. That for /proc directory files, the vnode type will be changed from VPROC (initially) to VDIR, to correctly reflect the file type as a directory (it is a procs directory, a directory file nonetheless).

Once the path is fully constructed, the VOP_OPEN() macro invokes the file-system-specific open() function. The props open() code does some additional prnode and vnode file initialization and file access touching for specific file types. Once open() completes, control is returned to vn_open() and ultimately a file descriptor representing a procs is returned to the caller.

The reading of a procs data object is similar in flow to the open scenario, where the execution of a system call on a procs file will ultimately cause the code to enter the procs read(). The procs implementation defines a data-object-specific read function for each of the file objects (data structures) available: pr_read_psinfo(), pr_read_pstatus(), pr_read_lwpsinfo(), etc. The specific file is entered from prread() through an array of pointers indexed by the file type—the same method employed for the described lookup operations.

The Solaris 7 implementation of procs, which are both 32-bit and 64-bit executables can run on a 64-bit kernel, provides 32-bit versions of the data files available in the /proc hierarchy. Each structure that describes the contents of a /proc file, a 32-bit equivalent is available in a 64-bit Solaris 7 kernel (e.g., lwpstatus and lwpstatus32, psinfo and psinfo32). In addition to the 32-bit structure definitions, each of the pr_read_xx() functions has a 32-bit equivalent which precisely details the data model of the calling process. Procs users are not exposed to the multiple data model implementation in the 64-bit kernel. When read() is entered, it checks the data model of the calling process and invokes the correct function required by the data model of the caller. An exception to this is the address space (/proc/<PID>/as) file; the caller must be the same data model. A 32-bit binary cannot read the file as a 64-bit process. A 32-bit process can read the file as file of another 32-bit process running on a 64-bit kernel.
