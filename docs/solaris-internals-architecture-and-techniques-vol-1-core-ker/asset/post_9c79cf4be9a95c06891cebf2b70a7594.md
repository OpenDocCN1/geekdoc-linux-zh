## 5.4.2 Copy-on-Write

The copy-on-write process occurs when a process writes to a page that is mapped with MAP_PRIVATE. This process prevents other mappings to the page from seeing changes that are made. seg_vn implements a copy-on-write by setting the hardware-MMU permissions of a segment to read-only and setting the segment permissions to read-write. When a process attempts to write to a mapping that is configured this way, the MMU generates an exception and causes a page fault on the page. The page fault handler in seg_vn looks at the protection mode for the segment; if it is mapped private and read-write, the handler initiates a copy-on-write.

The copy-on-write unmaps the shared vnode page where the fault occurred, creates a page of anonymous memory at that address, and then copies the contents of the old page to the new anonymous page. All of this happens in the context of the page fault, so the process never knows what's happening underneath.

The copy-on-write operation behaves slightly differently under different conditions. When memory is low, rather than creating a new physical memory page, the copy-on-write steals the page from the offset of the file underneath and renames it to the new anonymous page. This only occurs when free memory is lower than the system parameter minfree.

## 5.4.3 Page Protection and Advice

The seg_vn supports memory protection modes on either the whole segment or individual pages within a segment. Whole segment protection is implemented by the seg_vn data structure member, prot; its enablement depends on the boolean switch, pageprot, in the seg_vn data structure. If pageprot is equal to zero, the entire segment's protection mode is set by prot; otherwise, page-level protection is enabled.

Page-level protection is implemented by an array of page descriptors pointed by the vpage structure, shown below. If page-level protection is enabled, the vpage points to an array of vpage structures. Every possible page in the address space has one array entry, which means that the number of vpage members is the virtual address space size divided by the fundamental page size (8 Kbytes by UltraSPARC).

```c
struct vpage {
    uchar_t nvn_prot;      /* see <sys/mman.h> prot flags */
    uchar_t nvn_advice;     /* pplock <sys/mman.h> madvise flags */
};
```

## 5.5 Anonymous Memory

At many points we mentioned anonymous memory. Anonymous memory refers to pages that are not directly associated with a vnode. Such pages are used for a process's heap space, its stack, and copy-on-write pages. In Solaris kernel, two subsystems are dedicated to managing anonymous memory: the anon layer and the swap system.

The anonymous memory allocated to the heap of a process is a result of zero-fill-on-demand (ZFOD). The ZFOD operation is how we allocate new pages. ZFOD occurs when we touch a memory address for the first time, and a new page of memory is dynamically allocated at that address. ZFOD is the method used for heap space and stack. A page fault on a segment of this type will be recognized as ZFOD, and a new zeroed anonymous page is created at the fault location. The seg_vn fault handler, segvn_fault, handles the fault and creates ZFOD.

The seg_vn allocates anonymous memory to the segment by calling into the anonymous memory interfaces and attaching anonymous maps to the amp (anonymous map pointer) in the segvn_data structure. Figure 5.12 shows the seg_vn segment with anonymous maps allocated to it.

Every allocated page-sized piece of virtual memory in the segment is assigned an anonymous map. For example, when a segment is created, there are no anonymous slots, but the first time a zero-fill-on-demand page fault occurs, a slot is allocated for the page corresponding to the address within the segment where the fault occurred. At that time, a physical page is attached to the slot.

### 5.5.1 The Anonymous Memory Layer

Anonymous pages are created through the anon layer interfaces. The first time a segment receives a page fault, it allocates an anon map structure (which describes where to find the anon header) and puts a pointer to the anon header into the amp field of the anonymous map. It then allocates slot array array enough to hold the number of potential pages in the segment. The slot array is either a single or double indirection, depending on how many slots are required.

32-bit systems require double indirection for segments larger than 16 bytes; 64-bit systems, because of larger pointer sizes, require double indirection for segments larger than 8 bytes. When we use single indirection, the anon header array_chunk directly references the slot array. When we use indirection, the array is broken into chunks: 2048 slot chunks for 32-bit systems and slot chunks for 64-bit systems.


Each anon slot points to an anon structure, which describes the virtual page of memory corresponding to the page-sized area in the address space. SVR4 implementations imply it, or NULL if there was no physical page associated with it. However, the Solaris implementation does things differently. Recall that all physical pages have a vnode and offset. The Solaris kernel identifies that physical page, which points to the swap vnode, and offset assigned to the page. Note that this is not the swap device actual vnode and offset; rather, it is a vnode and offset pointing to the swapfs file system (which we'll discuss shortly). The anon structure also contains space for other information of interest to swapfs.
