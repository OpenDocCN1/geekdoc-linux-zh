## Kernel Bootstrap and Initialization

- */platform/<arch>/kernel/unix* — The platform-dependent component of the core kernel.
- /platform/sun4u/kernel/genunix — A genunix binary optimized for UltraSPARC, but independent of the system (box) type. Only Ultra-SPARC-based systems load this particular binary.
- /kernel/genunix — Platform-independent (generic) core kernel code. Only non-UltraSPARC-based systems load this file.

Note that only one genunix binary gets loaded at boot time: either the UltraSPARC version on sun4u hardware or the /kernel/genunix image on all other SPARC systems. These objects contain all the low-level kernel services and other facilities that need to be memory resident to initialize the system and support the dynamic load environment.

Included within the unix and genunix images are the memory management routines, callback and out facilities, clock and timer support, kernel memory allocator, module facility, the kernel runtime linker, synchronization primitives, thread and lightweight process code, and device driver interfaces.

## 4.2 Kernel Bootstrap and Initialization

The boot process loads the binary objects that make up the Solaris kernel from a bootable disk into physical memory, initializes the kernel structures, sets tuneable parameters, starts system daemons, and brings the system to a known, usable state. The basic steps involved in booting are as follows:

1. The boot(1M) command reads and loads the bootblock into memory.
2. The bootblock locates and loads the secondary boot program, ufsboot, into memory and passes control to it.
3. ufsboot locates the core kernel modules and the required runtime linker into memory and passes control to the loaded kernel.
4. The core kernel locates and loads mandatory kernel modules from the root directory and executes the main startup code.
5. The kernel startup code executes, creating and initializing kernel structures, resources, and software components as specified in the /etc/initstab file.

The preliminary steps shown above are based on a local disk. A network boot uses a different secondary boot program: inetboot instead of ufsboot. Our continuing discussion is based on local disk.

### 4.2.1 Loading the Bootblock

The initial stage of the boot process requires support from system firmware, typically called PROM, such that a bootable device can be addressed and that some minimal I/O functionality exists for the reading of a primary bootblock.

Sun SPARC-based systems implement system firmware known as the OpenBoot PROM (OBP), written in the Forth language. The OBP firmware provides Power-On Self-Test (POST) functionality for hardware testing, provides Non-Volatile RAM (NVRAM) for setting system parameters (e.g., the default boot device), builds a device tree that reflects the hardware configuration of the system, and provides bootstrap support. Intel-based systems use BIOS-based firmware that provides similar functionality. Our coverage focuses on SPARC-based systems, although much of the initialization process is hardware independent once the secondary boot phase has completed and the kernel is loaded.

On a system that has completed its POST tests, the boot process is initiated either with an explicit boot(1M) command at the OBP prompt, or if the autoboot NVRAM variable is set to true, initiating an automatic boot when the system is powered up. The boot(1M) command supports several options, including specifying a booting device and file other than the default, flagging a boot into the kernel debugger (kadb), running the boot in a more verbose mode for more output. Refer to the manual page on boot(1M) for specifics.

On SPARC using the default UNIX file system (UFS) for the root system (a.k.a. the system disk), the bootblock is located on physical disk sectors 1-15, as shown in Figure 4.2. The blocks are labeled as 0 through 16 to distinguish from file system blocks. Physical sectors on a disk are 512 bytes in size, whereas file system blocks are typically a grouping of some number of physical disk sectors (16 in UFS, for a default file system size of 8 KB).

Figure 4.2 Bootblock on a UFS-Based System Disk

Sector 0, the Virtual Table Of Contents (VTOC), contains the disk partition information: the starting and ending block numbers for each of eight possible on-disk partitions. Sector 16 is where a UFS puts the primary superblock (file system metadata).

The Solaris environment provides an installboot(1M) command, which adds or restores a bootblock to a system partition. The bootblock code is maintained in the /usr/platform/<arch>/lib/fs/ufs/bootblock file. The installboot(1M) utility uses dd(1) to copy this to the specified disk partition. The size of the superblock is constrained (it cannot be larger than 7680 bytes—15 sectors at 512 bytes), so it is the bare minimum amount of code required to read a directory in a UFS, locate a file, and load it into memory.

### 4.2.2 Loading usboot

The secondary boot filename, usboot, is hardcoded in the bootblock code for a UFS boot; the full path for usboot is /platform/<arch>/usboot. Note that the references to <arch> in this field, you should substitute the output from uname -m (e.g., sun4m, x86). In early Solaris versions (up to Solaris 2.4), usboot was located in the root directory, /.

### 4.2.3 Locating Kernel Images and Linker

ufsboot, once loaded, locates the kernel image, unix, and the required runtime linker, krtld. The full path of the first kernel loaded by ufsboot is /platform/<arch>/kernel/unix (e.g., /platform/sun4u/kernel on UltraSPARC-based systems). The unix file is an Executable and Linking Format (ELF) binary file, the industry-standard format for binary files. In an ELF file, specific bits of header information need to be examined. ufsboot knows about ELF headers—how to extract the dependencies.

### 4.2.4 Loading Kernel Modules
