The actual number of locks that exist in a running system at any time is dynamic and scales with the size of the system. Several hundred locks are defined in the kernel source code, a lock count based on static source code is not accurate because locks are created dynamically during normal activity—when kernel threads and processes are created, file systems are mounted, network connections are made, files are created and opened in the kernel data structures that provide the abstractions (processes, files) provided by the kernel, and thus the number of locks will scale up linearly as resources are created dynamically.

This design speaks to one of the core strengths of the Solaris kernel: scalability and scaling synchronization primitives dynamically with the size of the kernel. Dynamic lock creation has several advantages over static allocations. First, the kernel is not wasting time and space managing a large pool of unused locks when running on a smaller system, such as a desktop or workgroup server. On a large system, a sufficient number of locks is available to sustain concurrency for scalable performance. It is possible to wait literally thousands of locks in existence on a large, busy system.

# 3.4.1 Synchronization Process

When executing a kernel thread attempts to acquire a lock, it will encounter one of possible lock states: free (available) or not free (owned, held). A requesting thread gets ownership of an available lock when the lock-specific get function is invoked. If the lock is not available, the thread most likely needs to block and wait for it to come available, although, as we will see shortly, the code does not block (sleep), waiting for a lock. For those situations in which a thread will sleep while waiting for a lock, the kernel implements a sleep queue facility, as turnstiles, for managing threads blocking on locks.

When a kernel thread has completed the operation on the shared data protected by the lock, it must release the lock. When a thread releases a lock, the code must deal with one of two possible conditions: threads are waiting for the lock (such threads are termed waiters), or there are no waiters. With no waiters, the lock can be released. With waiters, the code has several options. It can release the lock and wake up the blocking threads. In that case, the first thread to acquire the lock (sleep queue), based on priority or sleep time, and wake up only that thread. Finally, the code could select which thread should get the lock next, and the lock owner could handle the lock off to the selected thread.
