The real differences exist in the semantics of using one interface or the other, and the system libraries that must be linked in. The Solaris interface definitions are shown below.

# Header File <sys/async.h>

The routines enable the calling process or to continue processing after it issues a read or write. The thread that issues the asynchronous read or write receives notification through a signal (SIGIO) either upon completion of the I/O operation or upon occurrence of an error condition. The implementation is based on the calling thread passing a data structure to the asynchronous I/O read or write call. The call result is set in one of the structure members; the calling program must test the result to determine if the I/O was successful or if an error was encountered. The passed structure provides space for storing the error number in the event of an error.

# 11.4.1 File System Asynchronous I/O

Asynchronous I/O is implemented by means of a user-land thread library for regular file systems and a private kernel interface (kernel asynchronous I/O) for raw disk devices. The implementation of the aioread(3) and aiowrite(3) creates a queue of I/O requests and processes them through user-level threads. When the aioread(3) or aiowrite(3) is entered, the system puts the I/O in a queue and creates an LWP (a thread) to do the I/O. The LWP returns when the I/O is complete (or an error occurs), and the calling is notified by a special signal, SIGIO. The programmer must put a signal handler in place to receive the SIGIO and take appropriate action. Such action must minimally include the return status of the read or write by reading the appropriate structure members (the structures are different between the libaio and libposix4 interfaces).

As an alternative to the signal-based SIGIO notification, you can call aiowait(3) after issuing aioread(3) or aiowrite(3). This calls the calling thread to block until the pending async I/O has completed. You can set a time-value and pass it as an argument to aiowait(3) so that the system waits for a specified amount of time, as shown below.

```
aio_result_t *aiowait(const struct timeval *timeout);
```

# 11.4.2 Kernel Asynchronous I/O

Although the threads implementation of asynchronous I/O worked well for many applications, it didn't necessarily provide optimal performance for applications that needed heavy use of the async I/O facilities. Conventional database systems, for example, use the async I/O interfaces extensively. Overhead associated with the creation, management, and scheduling of user threads motivated the design of an implementation that required less overhead and provided better performance and scalability. A review of the existing async I/O architecture and subsequent engineering effort resulted in an implementation called kernel I/O, or kaio.

Kaio first appeared in Solaris 2.4 (with a handful of revised patches) and has been available, with some restrictions, in every Solaris release since. The restrictions have to do with which devices and software support and which ones not. The good news for applications is that the presence or absence of kaio support for a combination of storage devices, volume managers, and file systems is transparent. If kaio support exists, it will be used. If it doesn't, the original library-based async I/O will be used. Applications do not change in order to take advantage of kaio. The system figures out what is available and enters the appropriate code path.

What kaio, as the names imply, is implement async I/O inside the kernel rather than in user-land with user threads. The basic sequence of events is:

- When an application calls aioread(3) or aiocwrite(3), the corresponding library routine is entered.
- Once entered, the library routine first tries to process the request with kaio. A kaio initialization is executed and creates a "cleanup" thread, which is intended to ensure that no remaining memory segments have been allocated but not freed during the async I/O process.
- Once that is complete...

Support for kaio requires specific async I/O read and write routines at the device-driver level. The Solaris kernel provides this support in the SCSI driver for all currently shipping Sun storage products and the Solstice DiskSuite (SDS) device drivers. These products include the fiber-based storage products, which implement the SCSI protocol over the Fibre connect.

Kaio only works when the target of the async I/O is a character device-special file. In other words, kaio only works on raw disk I/O. Additional support has been added with the host-based volume management software for creating RAID volumes on SPARC/Solaris servers: Sun Enterprise Volume Manager, based on Veritas, and Solstice DiskSuite. RAID devices created with either Veritas or DiskSuite have raw device entry points through the /dev/vx/rdsk and /dev/md/rdsk for these device-special files, and the async/O-specific routines include kaio. You can also use the kaio test below to establish whether your device supports kaio.

If kaio support is available, here is what happens:

- The kernel allocates an aio structure from the queue (or creates a new one in kernel memory with kmem_alloc) and calls the strategy routine in the appropriate driver.
- Inside the driver, the required data structures are set up to do the I/O, and an async/O-specific routine, physio, is entered.
- The strategy routine is called to do the I/O.
- The physio routine waits for the driver strategy to complete.
- The aio routine sets up the signal mechanism, then calls the driver strategy without waiting for the I/O to complete.

The presence of ENOTSUP error signals that kaio support is unavailable. That is, when the libaio (or libposix for the POSIX interfaces) makes a kaio system call, the kaio returns an ENOTSUP error if kaio is not supported. If kaio support is not available, the code path then is very different:

- Generally, the original user-thread asio facility performs the I/O in an async I/O queue and hands off the aiore and aiwrite to a worker thread that was created when the libaio library was initialized (or on after this example).
- The thread assigned to do the I/O on behalf of the calling process uses the read(2) and write(2) system calls to enter the kernel.

Essentially, the thread-implementation of async/O makes the I/O appear asynchronous to the calling process by creating a thread to do the I/O and allowing the caller to return to other work without waiting. The implementation uses the traditional synchronous Solaris system calls (pread(2) and write(2)) to do the I/O.

In either case (kaio or non-kaio), the underlying mechanics of doing the actual I/O are no different than if the I/O was initiated by a simple read(2) or write(2). Once the read or write has been completed, the result (error or success) is set in a data structure that was passed by the code that initiated the I/O, and a signal (SIGIO) is sent to the calling process to indicate that the I/O has completed or cannot be completed because of an error condition. It is up to the programmer to write a handler for the SIGIO signal and deal with the condition as required by the application.
