# Table 10-3 Shared Memory APIs

| System Call | Arguments Passed | Returns | Description |
| --- | --- | --- | --- |
| shmget(2) | key, size, flags | Identifier | Creates a shared segment if one with a matching key does not exist, or locates an existing segment based on the key |
| shmat(2) | Identifier, address, flags | Pointer | Attaches shared segment to process address |
| shmddt(2) | Address | 0 or 1 | Detaches a shared segment from a process's address space |
| shmctl(2) | Identifier, command, structure | 0 or 1 (success or failure) | Control call—gets/sets permissions, gets stats, destroys identifier

The shared memory kernel module is not loaded automatically by Solaris at runtime; none of the System V IPC facilities are. The kernel will dynamically load a required module when a call that requires the module is made. If the sys and ipc modules are not loaded, then the first time an application makes a shared memory system call (e.g., shmget(2)), the kernel loads the module and executes the system call. The module remains loaded until it is explicitly unloaded by the modload(1M) command or until the system reboots. This behavior explains an FAQ on shared memory manage: why; when the ipcs(1M) command is executed, it comes back with this status:

```
$ ips
IPC status from <running system> as of Mon 1 17:15:56 2000
Message Queue facility not in system.
T  ID  KEY MODE      OWNER GROUP
Shared Memory: 0 0x05110705 --rw-r--r-- root
Semaphores:
```

The facility not in system message means the module is not loaded. You can tell the operating system to load the module during booting by using the forced directive in /etc/system file.

```
forload: sys/msgsys
```
