The kernel generic exec, gexec() is now called; here is where we switch to the object-file-specific exec routine through the exec[] array. The correct array entry for the type of file being exec is determined by a call to the kernel vn_rdwr() (vnode read/write) routine and a read of the first four bytes of the file, where the file magic number is stored. Once the magic number has been retrieved, the code looks for a match in each entry in the exec[] array by comparing the magic number of the exec file to the exec magic field in each structure in the architecture. Prior to entering the exec switch table, the code checks permissions against the credentials of the process and the permissions of the object file being exec'd. If the object file is not executable or the caller does not have execute permissions, exec fails with an EACCESS error. If the object file has the setuid or setgid bits, the effective UID or GID is set in the new process credentials at this time.

Note that Solaris 7 implements two ELF entries, one for each data model supported: 32-bit LP32 ELF files and 64-bit LP64 ELF files. Let's examine the flow of the exec() function, since that is the most common type of executable on Solaris systems.

Upon entry to the elfexec() code, the kernel reads the ELF header and program header (PHT) sections of the object file (“The Multithreaded Process Model” on page 262 for an overview of the ELF header and PHT). These two main header sections of the object file provide the system with the information it needs to proceed with mapping the binary to the address space of the newly forked process. The kernel next gets the argument and environment arrays from the exec(2) call and places both on the user stack of the process, using the exec_args() function. The arguments are also copied into the process uarea's u_psargs[] array at this time.
