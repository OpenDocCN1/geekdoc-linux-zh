
The system allocates kernel memory for some number of shmid_ds structures at boot time, as determined from the shared memory tunable shmnmi. All together, only four tunable parameters are associated with shared memory. They are described in Table 10-5.

## Table 10-5 Shared Memory Tunable Parameters

| Name | Default Value | Minimum Value | Maximum Value | Data Type | Description |
|---|---|---|---|---|---|
| shmax | 1048576 | 1 | 4,294,967,295 (4 GB) | unsigned int | Maximum size in bytes of a shared memory segment |
| shmin | 1 | 1 | 4,294,967,295 (4 GB) | unsigned int | Minimum size for a shared segment |
| shmmi | 100 | 1 | 2147483648 (2 GB) | int | Maximum number of shmid_ds structures, systemwide. |
| shmseg | 6 | 1 | 32767 (32K) | short | Max processes per process |

When the system first loads the shared memory, it allocates kernel memory to support the shmid_ds structures and other required kernel support structures. Each shmid_ds structure is 112 bytes in size and has a corresponding kernel mutex lock, which is an additional 8 bytes. Thus, the amount of kernel memory required by the system to support shared memory can be calculated as ((shmmax * 112) + (shmmi * 8)). The default value of 100 for shmnmi requires the system to allocate 112.8 Kbytes of kernel memory for shared memory support. The system makes some attempt to protect itself against allocating too much kernel memory for shared memory support by checking for the maximum available kernel memory, dividing by 4, and using the resulting value as a limit for allocating resources for shared memory. Simply put, the system will not allow more than 25 percent of available kernel memory allocated.

The preceding description applies to Solaris 2.4, 2.5.1, and 2.6. Prior releases, up to and including Solaris 2.4, did not impose a 25 percent limit check. Not did they require the additional 8 bytes per shmid_ds for a kernel mutex lock, which shared memory using very coarse-grained locking in the earlier releases and only implemented one kernel mutex in the shared memory code. Beginning in Solaris 2.5, finer-grained locking was implemented, allowing for greater parallelism of applications using shared memory.

It should be clear that one should not set shmnmi to an arbitrarily large value simply to ensure sufficient resources. There are limits to how much kernel memory the system supports. On sun4m-platforms, the limits are on the order of 128 Mbytes for releases prior to Solaris 2.5, and 256 Mbytes for Solaris 2.5. On sun (SS1000 and SC2000), the limits are on 576 Mbytes in Solaris 2.5 and later. On UltraSPARC (sun4u-based) systems, the kernel has its own 4-Gbyte address space, so it is much less constrained. Still, keep in mind that the kernel is not pageable, and thus whatever kernel memory is needed remains resident in RAM, reducing available memory for user processes. Given that Sun systems today with very large RAM capacities, characteristic of the kernel may not be an issue, but it should be considered nonetheless.

Note that the maximum value for Table 10-5 is 2 Gbytes. This is a theoretical limit, based on the data type (a signed integer), and should not be construed as something configurable today. Applying the method from above, you see that 2 billion shared memory identifiers would require over 200 Gbytes of kernel memory! Assert to test the ability of the number of shared memory identifiers required by the application, and set shmmi to that value plus 10 percent or so for headroom.

The remaining three memory tunable parameters are quite simply.

shmmax defines the maximum size a shared segment can be. The size of a shared segment is determined by the second argument to the shget(2) system call. When the call is executed, the kernel checks to ensure that the argument is not greater than shmmax. If it is, an error is returned. Setting shmax to its maximum value does not affect the kernel size—no kernel resources are allocated on the basis of shmmax, this variable can be tuned to its maximum value of 4 Gbytes (0xffffffff) on a 32-bit Solaris system, and on a 64-bit Solaris 7 system. The /etc/system entry examples that follow two ways of setting the 4-Gbyte limit for a 32-bit system and setting something larger on a 64-bit Solaris 7 system, in this case, a 10-Gbyte memory shared segment.

```
set shmsys:shinfo_shmmax=0xffffffff
set shmsys:shinfo_shmmax=2429367295
set shmsys:shinfo_shmmax=1000000000
```

The shmin tunable defines the smallest possible size a shared segment can be, as the size argument passed to the shget(2) call. There's no compelling reason to set this tunable from the default value of 1.

Lastly, shmseg defines the number of shared segments a process can attach (map pages) to. For application purposes, and this tunable determines how many mapped memory segments a process can attach.
