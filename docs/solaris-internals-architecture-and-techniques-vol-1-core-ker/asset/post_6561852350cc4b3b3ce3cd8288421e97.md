
- ts_maxwait — Used in conjunction with ts_wait. They attempt to compensate threads that have been preempted and waited a (relatively) long time before using their time quantum. When a thread begins execution, a field, called ts_dispatch, in the class-specific structure linked to the thread (Figure 9.3 on page 356) counts the number of seconds that have elapsed since the thread began executing. This value is not reset if the thread is preempted (involuntarily relinquish the processor). Once per second, a kernel routine executes to increment the ts_dispatch field for all TS and IA classes. If the value of ts_dispatch for the thread is greater than that of ts_maxwait, the thread priority is set to the value of ts_wait, a higher priority for the thread since this circumstance it must have been preempted and never had a chance to use its time quantum.

- ts_wait — The new priority for a thread that has waited longer than ts_maxwait to use its time quantum. Interesting to note is the default values in the TS and IA dispatch tables inject a 0 in ts_maxwait for every priority except the highest (59). So, just one increment in the ts_dispatch field will cause the thread priority to be readjusted to ts_wait, except for priority 59 threads. The effect is that all the highest priority (59) timeshare have their priority bumped to the 50–59 range (ts_wait) every second.

This process has the desirable effect of not penalizing a thread that is CPU-bound for an extended period of time. Threads that are CPU hogs over time, end up in the 0–9 priority range as they keep using their time quantum because of priority adjustments by ts_gexp. Once, they will get bumped back up to the 50–59 range and will only migrate back down if they sustain their CPU-bound behavior.

Priority 59 threads are handled differently. These threads are already at the maximum (highest/best) priority for a timeshare thread, so there's no way to bump their priority with ts_maxwait and make it better. The ts_update() routine, which is the kernel code segment that increments the ts_dispatch value and readjusts priorities by means of ts_wait, reorders the linked list of threads on the dispatch queues after adjusting the priority. The reordering after adjustment puts threads at the front of their new dispatch queue for that priority. The threads on the priority 59 linked list would end up reordered but still at the same priority.

Experimentation has shown that this approach has two results: some percentage of priority 59 threads never get process time, and the ts_update() puts on the front of the dispatch queue following adjustment scheduled more frequently. When the ts_maxwait value is set to 32000 the queue is never reordered by ts_update() and every thread has a short fault at getting scheduled.

You can apply user-supplied values to the dispatch tables by using the dispatch(1) command or by compiling a new /kernel/sched/TS_DPBL loadable module and replacing the default module. The ts_dptbl(4) manual page provides the source and the instructions for doing this. Either way, any changes to the patch tables should be done with extreme caution and should be tested extensively before going into production—we’ve seen dispatch table “tweaks” drastically affect the performance of a system, not always for the better.

## Overview

The interactive class (IA) uses the timeshare dispatch table. This is not necessarily intuitive; you specify the TS or IA table to the dispadmin(1) command, and the command output header will indicate either “Interactive Dispatcher Configuration” or “Time Sharing Dispatcher Configuration,” depending on what was specified on the command. Both classes use the same dispatch table; thus, any changes made for one class affect the other. The IA class was added to make the Solaris window-based desktop environment provide snappier performance. To enhance performance, all processes started under the windowing system (OpenWindows or CDE) are put in the IA class, and the priority of processes attached to the window that has the current input focus (the active window—the one used by the user) is boosted. The procedure uses most of the TS infrastructure with just a few IA-specific routes, which we discuss in the next section.

## 9.2 The Kernel Dispatcher

The dispatcher is the kernel code segment that manages queues of runnable threads, called dispatch queues; places the highest-priority runnable thread on a processor for execution; and manages the recalculation of thread priorities that are based on execution time, sleep time, and spent on the queue waiting for a processor. The context switching of threads and off processors is driven by the dispatcher code.

Early versions of Solaris 2 implemented a simple, global dispatch queue that was shared by all processors on a multiprocessing system. Scalability and dispatch latency, especially for real-time threads, was less than optimal because of the coarse-grained locking. A single scheduling lock for the dispatch queue needed to be acquired for a processor to insert or remove a kthread from the queue, which became a point of contention on busy multiprocessing systems. A new design was done for Solaris 2.3, and since release, Solaris implements multiple dispatch queues, one for each processor, and a global queue for threads that run at a priority high to cause kernel preemption. These threads are real-time and interrupt threads (although interrupt threads are not placed on a dispatch queue—they on a linked list of every CPU structure).

### 9.2.1 The Solaris Dispatcher

The RT dispatch table contains two columns: the rt_quantum field, which is the time quantum for processor execution, and rt_globpris, which is the system-wide global priority, calculated dynamically. The rt_quantum field has the same meaning as the ts_quantum field in the TS table, that is, the amount of time a thread at this priority is allowed to run before being scheduled. Also as with the TS table, the PRIORITY column produced by dispatchmin(1) equates to the row number of the dispatch table entry, which is the same as the class-specific priority level and is not the same as rt_globpris, the global priority.

```
# dispatchmin -c RT

  1000                          1

                             58
  100                           59
```
