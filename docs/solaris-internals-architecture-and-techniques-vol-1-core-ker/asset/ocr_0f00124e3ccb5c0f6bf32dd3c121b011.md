# Scheduler Activations

Chapter 1 that Doors provides a process-to-process procedure call facility, where a server process can establish a door to a function in the process and client processes can make door calls into the server door. Essentially, a process can execute a call to a function that is part of another process's address space, pass the function arguments, and get a return value as if the function was part of the calling process. Doors provide a very fast and efficient method of interprocess communication, making them ideal for scheduler activations as a facility for the kernel calling up into the user threads library (upcall).

These facilities are put in place when a multithreaded process first begins with the creation of the primordial thread, to (thread zero), which triggers the creation of several threads required to support threaded processes, such as the SIGWAITING signal handler, dynamiclwps(). The to initialization code calls an sc_init() routine that sets up the shared memory pages and the upscale call. sc_init() calls door_create() to establish a door for kernel-to-user upcalls, then sc_setup() to complete the initialization of the scheduler-activations support.

Most of the setup work and support for scheduler activations in the kernel is done the lwp_schedctl() system call, a new system call created for scheduler activations. Note that lwp_schedctl() is not a public interface; the invocation of lwp_schedctl() by an application program is not supported. The call itself is not documented in the section 2 manual pages for that reason. When invoked from sc_setup(), lwp_schedctl() creates the shared memory pages, which are mapped to the kernel and the user process and locked in memory so they cannot be paged out.

# 9.4.2 LWP Pool Activation

LWP pool activation refers to the fast and efficient replenishment of LWPs to a threaded process that has all LWPs in a blocking or sleeping state, potentially leaving runnable threads without an execution resource. This condition is tested for and handled when the condition variables are entered to put an LWP/kthread to sleep. The cv_wait_sig(), cv_timedwait(), and cv_wait_sig_swap() routines invoke a call to schedctl_check(), with the SC_BLOCK flag as an argument, to determine if an activation exists for the LWP/kthread. This is done in conjunction with a subsequent call to schedctl_block(), which determines if all LWPs in the process are blocked.

schedctl__check() tests the thread's t_schedctl pointer and the passed flag, SC_BLOCK in this case. If an activation has been established, the kthread's t_schedctl references an sc data structure, which contains links to the shared memory page pool and state flags. For a threaded application, t_schedctl will have been set during the initialization process, and sc_flags (in sc_data as referred by t_schedctl) will have the SC_BLOCK flag set.
