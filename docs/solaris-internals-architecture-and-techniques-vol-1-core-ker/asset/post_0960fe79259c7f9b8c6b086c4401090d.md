## 10.6.1 Doors Overview

Figure 10.6 illustrates broadly how doors provide an interprocess communication mechanism.

![](img/a86367b95bf21add858c99948ac951c6_505_0.png)

Figure 10.6 Solaris Doors

The file abstraction used by doors is the means by which client threads retrieve the proper door handle required to use a door_call(3X). It is similar to the methodology employed when POSIX IPC facilities are used; a path name in the file system name space is opened, and the returned file descriptor is passed as an argument in the door_call(3X) to call into the desired door. An argument structure, door_arg_t, is declared by the client and used for passing arguments to the door server function being called. The address of the door_arg_t structure is passed as the second argument by the client in door_call(3X).

On the server side, a function defined in the process can be made available to external client processes by creation of a door (door_create(3X)). The server must also bind the door to a file in the file system name space. This is done with fattach(3C), which binds a STREAMS-based or file descriptor to a file path name. Once the binding has been established, a client can open it to the path name and use the returned file descriptor in door_call(3X).

## 10.6.2 Doors Implementation

Doors are implemented in the kernel as a pseudofile system, doors, which is loaded from the /kernel/sys directory during boot. Within a process, a door is referenced through its door descriptor, which is similar in form and function to a file descriptor, and, in fact, the allocation of a door descriptor in a process uses an available file descriptor slot.

The major data structures required for doors support are illustrated in Figure 10.7

![](img/a86367b95bf21add858c99948ac951c6_506_0.png)

Figure 10.7 Solaris Doors Structures

The two main structures are door_node, linked to the process structure with the p_door_list pointer, and door_data, linked to the door_node with the door_data pointer. A process can be a door server for multiple functions (multi-doors). Each call to door_create(3X) creates another door_node, which links to an existing door_node (if one already exists) door_data is created as part of the setup thread during create the process, which we're to walk about. door_data includes a door_arg structure, which manages the argument list passed in through door_call(3X), and a link to

door descriptor (door_desc), used for passing door descriptors when a door function is called.

To continue: A call to door_create(3X) enters the libdoor.so library door_create() entry point (as is the case with any library call).

- The kernel door_create() is invoked from the library and performs the following actions:
- Allocates kernel memory for door_node and initializes several fields of door_node and the door vnode (part of the door_node structure).
- Links the door_target field to the process structure of the calling kernel thread.
- Sets door_pc, a function pointer, to the address of the function served by the door (the code that will execute when a client calls door_call(3X)).
- Sets door_flags as directed by the caller.
- Initializes the vnode lock (v_lock) and condition variable (v_cv). Initializes several other fields in vnode to specify the vnode type (VDOR) and references to vnode virtual file system (VFS).
- Adds the door_node to the process's list (p_door_list) and allocates a file descriptor for the door by means of the kernel alloc() function, which allocates a file structure and user descriptor.
- The kernel door_create() now completed, the code returns to libdoor.so.
- The library makes sure that the calling process has been linked with the threads library, libthread.so and returns an error if the link has not been made. door server requires linking with libthread.so because the door uses the threads interfaces to create and manage a pool of door threads.
- The last thing the library-level door_create() code does is call thr_create(3T) to create a server thread for the door, as execution resource for calls into the function exported by the door.
- thr_create(3T) creates a detached, bound thread that executes the library door_create() routine, which disables cancellation of the current thread (pthread_setcancel(3T)) and enters the kernel.

door_return(3X) is part of the doors API and is typically called at the end of the function exported by the door_create(3X) call.

- door_return(3X) returns processor control to the thread that issued door_call(3X) and causes the server thread to sleep, waiting for another invocation of the door.
- When entered (remember, we're in the kernel, not in the doors library), door_return(3X) allocates a door_data structure for the calling thread and links it to the kernel's t_door pointer.

This sequence is done if the current thread's t_door pointer is NULL, signifying a door_data structure has not yet been allocated. The next bit of code in door_return(3X) applies to argument handling, return data, and other conditions to be dealt with when a kernel thread issues door_call(3X). We are still in the create phase, so a bit later we'll revisit what happens in door_return(3X) as a result of door_call(3X).

Continuing with the create in the door_return(3X) kernel function:

- The kernel door_release_server(1) code is called to place the current thread on the list of threads available to execute before door calls into the server.
- The kernel thread linked to the process's p_server_thread, and cv_broadcast(1) is done on the door condition variable, door_cv, causing any threads blocked in door_call(3X) to wake up.

At this point, the door create is essentially completed.

- A call into the shuttle code puts the kernel to sleep on a synchronization object (shuttle_swt(1)); the thread is placed in a sleep state and enters the dispatcher through shuttle_swt(1).

We directly explain synchronization objects. Typically, execution control flow is managed by the kernel dispatcher (Chapter 5), using condition variables and sleep queues. Other synchronization primitives, mutex locks, and reader/writer locks are managed by turnstiles, an implementation of sleep queues that provide a priority inheritance mechanism.

Shuttle objects are a relatively new (introduced in Solaris 2.5, when doors first shipped) synchronization object that allows very fast transfer of control of a processor from one kernel to another without incurring the overhead of the dispatcher queue search and normal kernel thread processing. In the case of a door_call(), control can be transferred directly from the caller (or a client in this case), to a thread in the door server pool, which executes the door function on behalf of the caller. When the door function has completed, control is transferred directly back to the client (caller), all the kernel shuttle interfaces to set state and to enter the dispatcher at the appropriate places. This direct transfer of processor control contributes significantly to the IPC performance.

Kernel threads sleeping on shuttle objects have a 0 value in their wait channel field (t_wchan) and a value of 1 in t_wchan. The thread's t_subj_ops (synchronization operations table) pointer is set to the shuttle object's operations structure (shuttle_sops); the thread's state is, of course, TS_SLEEP, and the thread's T_WAKEABLE flag is set.

Getting back to door creation:

- A default of one server thread is created unless there are concurrent invocations, in which case thread will be created for each door call. The API allows for programs creating their own separate, private pool of door threads that have different characteristics than the default thread properties.
- The doors library will create a bound, detached thread with the default thread stack size and signal deployment by default.

This completes the creation of a door server. A server thread in the pool is left sleeping on a shuttle object (shuttle_swt()), ready to execute the function.

Application code that creates a door to a function (becomes a door server) typically creates a file in the file system to which the door descriptor can be attached, using the standard open(2) and fattach(3C) APIs, to make the door easily accessible to other processes.

fattach(3C) is implemented with a pseudo file system called namesfs, the file system. namesfs allows the mounting of file systems on nondirectory points, as opposed to the traditional mounting point to be a directory file. Currently, fattach(3C) is the only client of namesfs; it calls the mount(2) system call, passing namesfs as the file name character string and a pointer to a namesfs file descriptor. The mount(2) system call enters the VFS switch table through the VFS_MOUNT macro and enters the mount code, nm_mount().

With the door server in place, client processes are free to issue a door_call(3X) to invoke the exported server function.
