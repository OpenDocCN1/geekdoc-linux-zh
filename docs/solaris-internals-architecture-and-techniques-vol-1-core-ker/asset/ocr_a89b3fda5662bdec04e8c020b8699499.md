A quick Solaris 7 implementation note: Before setting up the user stack with the argv[] and envp[] arrays, Solaris 7, booted as a 64-bit kernel, must first determine if a 32-bit or 64-bit binary is being execd(a 32-bit Solaris 7 system can only run 32-bit binaries). This information is maintained in the ELF header, where the 32-system checks the e_ident[] array for either ELFCLASS32 or ELFCLASS64 identity. With the data model established, the kernel sets the initial size of the exec file sections to 4 Kbytes for the stack, 4 Kbytes for growth (stack increment), and 1 Mbyte for the argument list (ELF32) or 2-Mbyte argument list size for ELF64.

Once the kernel has established the process stack and argument list, it calls mapelfexec() to map the various program segments into the process address space. mapelfexec() walks the Program Header Table (PHT), and for each PT LOAD type (a loadable segment), mapelfexec() maps the segment into the process's address space. mapelfexec() bases the mapping on the p_files and p_mem sections of the header that defines the segment, using the lower-level, kernel address space code. The program loadable segments have been mapped into the address space, the dynamic linker (for dynamically linked executables), referenced through the PHT, is also mapped into the process address space. The elfexec code checks the preq resource limit RLIMIT VMEM (max virtual memory size) against the size required to map the object file and runtime linker. An ENOM error is returned in the event of an address requirement that exceeds the limit.

All that remains for exec(2) to complete is some additional housekeeping and structure initialization, which is done when the code returns to exec(). This last part deals with clearing the stack again and setting the system disposition to default for any signals that had a handler installed by the parent process.
