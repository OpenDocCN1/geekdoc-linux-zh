The O_RSYNC flag provides for read synchronization and is used in conjunction with the O_SYNC or O_DSYNC flags. With the O_SYNC flag, file integrity (data and inode) is enforced. With the O_DSYNC flag, data integrity is enforced, meaning that any pending writes to the file are completed before the read is done. If O_RSYNC and O_SYNC are both set, pending I/Os are completed and the inode information is updated before the kernel processes the read request. A read issued on a file without any of the O_SYNC flags simply implies that a read from a buffer may be reading data that has not been written to the disks. The open(2) and fcntl(1) manual pages do not explicitly state that O_RSYNC must be used with either O_SYNC or O_DSYNC, though it is somewhat implied.

The various data flags have no corresponding flags at the inode layer. The inode maintains flags to indicate synchronous operations in the kernel file system code (e.g., ufs_read(), ufs_write()), based on the status of the O_SYNC flags in the file structure for the file. They are used by the kernel in the lower-level I/O routines. Solaris provides two library routines—fdasync(3R) and fsync(3C)—that applications can call, for data integrity synchronization, before issuing a read or write. These calls allow for per-file synchronization of data to disk, and return only when the write to nonvolatile storage has been completed.

## 11.3.2 Other File Flags

Other flags are maintained in the per-process file descriptor and the flags that are used at the file descriptor level are mostly for the operating system to use—they are not user settable.

One such flag is FEXEC: the close-on-exec flag. This flag notifies the operating system to close the file descriptor in the new process if a process executes exec(2) call. Normally, all open files are inherited by child processes, which is not always the desired behavior. The kernel implements FEXEC with a simple close_exec() kernel routine called from exec(2). close_exec() walks through the file descriptor array and closes any file with the FEXEC flag set. The fcntl(2) sets, clears, and examines the descriptor's flag field. Currently, FEXEC is the only flag that can be set, or cleared.

## 11.3.2.6 The dup System Call

dup(2) system call allows us to duplicate a file descriptor, such that two descriptors point to the same file entry. We indicated earlier that an open(2) call will fetch a new file descriptor and result in a new file structure allocated, even if the process already has the same file opened. dup(2) duplicates a file descriptor and will result in a new u_entry structure for the file descriptor. The difference is that the uf_pointer, which points to file structure, will point to the same file structure as the dup'ed file descriptor. A new file structure is not created, as would be the case with a second open(2) of the same file.

dup(2) is useful for situations where the programmer wants multiple references to the same file to share the same view of the current file offset. Since the current file pointer (byte offset) is maintained in the file structure, dup'ed descriptors share a common view of the file's offset.

Consider a test program, ofd (code not shown), that does two opens of the same file. The second open sets the O_SYNC flag (which we added only to demonstrate how these file structure flags can be examined). After the two opens, a dup(2) is executed to duplicate the second file descriptor. Below is some output and an example of using /usr/proc/bin/pfiles to look at a process's open files.

## 11.3.2 The read and pwrite System Calls

The POSIX standard provides two interfaces, shown below, for performing basic read and I/O. These interfaces are similar to the read() and write() system calls but allow a file offset to be part of the system call.

```
size_t pread(int fild, void *buf, size_t nbyte, off_t offset);
size_t pwrite(int fild, const void *buf, size_t nbyte, off_t offset);
```

### Header File <unistd.h>

With pread(2) and pwrite(2), a read or write can be initiated at a specific offset with only one system call, rather than the traditional method that uses both the seek() and read() system calls.

## 11.3.2.8 The readv and writev System Calls

The readv(3) and writev() system calls, shown below, are similar to the read(3) and write() system calls, allow the transfer to occur to and from a range of memory addresses, rather than a single memory buffer. This technique is often referred to as scatter/gather I/O.

```
size_t readv(int ildes, const struct iovec *iov, int iovcnt);
size_t writev(int ildes, const struct iovec *iov, int iovcnt);
```

### Header File <unistd.h>

Each I/O requests an array of iovec structures and a number of iovec structures. The total size of the I/O is the sum of the size of all of the iovec structures. The iovec structure is shown below.

```
struct iovec {
    addr_t iov_base;
    int iov_len;
};
```

### Header File <unistd.h>

Each iovec structure provides the base address of the memory buffer and the length in bytes of the buffer. As a result, the I/O transfer is read or written to the process's memory space in the specified pattern and to or from the file in a sequential manner.

## 11.4 Asynchronous I/O

Asynchronous I/O interfaces have been available in Solaris for some time. A specific set of interfaces in the Solaris libraries provides a means by which applications issue I/O requests and not have to block or cease working until the I/O has completed. (Don't confuse that behavior with the behavior of an I/O request if the data integrity flags are not set in the file descriptor. See "Data Integrity and Synchronization Flags" on page 488.)

Two sets of interfaces do asynchronous I/O in Solaris: the aioread(3) and aiowrite(3) routines; and the POSIX-equivalent routines, ai_read(3R) and write(3R), which are based on the POSIX standards for real-time extensions. Real-time applications must, by definition, deal with an unpredictable flow of external interrupt that require predictable, bounded response time.
