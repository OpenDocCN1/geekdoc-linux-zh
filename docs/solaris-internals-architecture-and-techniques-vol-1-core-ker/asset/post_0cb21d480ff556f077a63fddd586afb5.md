## 8.5 Process Termination

The termination of a process results from one of three possible events. First, the process explicitly calling exit(2) or _exit(2) causes all the threads in a multi-threaded process to exit. (The threads libraries include exit(3) and pthread_exit(3) interfaces for programmatically terminating an individual thread without causing the entire process to exit.) Second, the process simply completes execution and falls to the end of the main() function—which is essentially an implicit exit. Third, a signal is delivered, and the disposition for the signal is to terminate the process. This disposition is the default for some signals (like “Signals” on page 320). There is actually one other possibility: a process can explicitly call the abort(3) function and cause a SIGABRT signal to be sent to the process. The default disposition for SIGABRT is to terminate the process and create a core file.

Regardless of which event causes the process to terminate, the kernel exit function is ultimately freeing whatever resources have been allocated to the process state, such as address space mappings, open files, etc., and setting the process state to SZOMB, or the zombie state. A zombie process is one that has exited and requires the parent process to issue a wait(2) system call to gather the exit status. The only kernel resource that a process in the zombie state is holding is the table slot. Successful execution of a wait(2) call frees the process table slot. Orphaned processes are inherited by the init process solely for this purpose.

An exception to the above scenario is possible if a parent process uses the sigaction(2) system call to establish a signal handler for the SIGCHILD signal and sets the SA_NOCLDWAIT flag (no child wait) in the sa_flags field of the signal structure. A process is sent a SIGCHILD signal when one of its child processes terminates. If a process installs a SIGCHILD handler as described, the kernel sets the SND_WAIT bit in the calling (parent) process's p_flag field, signifying that the parent process is not interested in obtaining status information on child processes that exited. ## 8.5.2 Deathrow

exitlwps() does one last bit of work before it returns to exit(). It places a zombie's kernel threads on deathrow.

The kernel maintains a list, called deathrow, of LWPs and kernel threads that have exited, in order to reap a terminated LWP/kthread when a new one needs to be created (fork()). If an LWP/kthread is available on the list of zombies, the kernel does not need to allocate the data structures and stack for a new kthread; it simply uses the structures and stack from the zombie kthread and links the kthread to the thread that issued the fork(2).

A kernel thread, thread_reaper(), runs periodically and cleans up zombie threads that are sitting on deathrow. The list of zombie threads on deathrow is not allowed to grow without bounds (no more than 32 zombies), and the zombies are not left on deathrow.
