The programmer must create and initialize the sembuf structure, setting the semaphore number (specifying semaphore in the set), the operation (more on that in a minute), and the flag. The value of sem_op determines whether the semaphore operation will alter or read the value of a semaphore. A nonzero sem_op value either negatively or positively alters the semaphore value. A zero sem_op value will simply do a read of the current semaphore value.

The semop(2) manual page contains a fairly detailed flow in the DESCRIPTION section on what the operation will be for a given sem_op value and a given flag value.

# 10.4 System V Message Queues

Message queues provide a means for processes to send and receive messages of various size in an asynchronous fashion on Solaris System. With all the other IPC facilities, the initial call when message queues are used is an ipcget, in this case, msgget(2). The msgget(2) system call takes a key value and some flags as arguments and returns an identifier for the message queue. Once the message queue has been established, it is a simple matter of sending and receiving messages. Applications use msnd(2) and msgrcv(2) for those purposes. The sender simply constructs the message, assigns a message type, and calls msnd(2). The system will place the message on the appropriate message queue until msgrcv(2) is successfully executed. Sent messages are placed at the back of the queue; thus the queue is implemented as a FIFO (First In, First Out).

The message queue facility implements a message type, which is user (programmer) defined. So, programmers have some flexibility, the kernel has no embedded or predefined knowledge of different message types. Programmers use the type field for priority messaging or directing a message to a particular recipient.

Lastly, applications use the msgctl(2) system call to get or set permissions on the message queue and to remove the message queue from the system when the application is finished with it. For example, msgctl(2) offers a clean way to implement an application shutdown procedure, because the system will not remove an empty and unused message queue unless it is explicitly instructed to do so or the system is rebooted.

# 10.4.1 Kernel Resources for Message Queues

Like the IPC facilities previously discussed, the message queue facility comes in the form of a dynamically loadable kernel module, /kernel/sys/msgs, and depends on the IPC support module, /kernel/misc/ipc, to be loaded in memory.
