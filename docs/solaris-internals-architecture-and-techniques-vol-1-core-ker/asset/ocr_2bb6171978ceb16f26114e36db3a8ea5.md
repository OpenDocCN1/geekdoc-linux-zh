The calculation of the user mode priority (between steps 2 and 3), which is done
whenever a TS/IA thread priority adjustment is required, is simple arithmetic,
ming the ts_cpupri, ts_upri, and ts_boost values. ts_boost is used for
IA class threads means of boosting the priority by a value of 10. ts_umdpri is
set to the sum of ts_cpupri, ts_upri, and ts_boost and is tested against some
bound values; it cannot be greater than the maximum TS/IA class priority, 59,
or less than 0.

The other relevant step taken in the return code fork is the setting of the
ts_timeleft and ts_dispatch fields in the kthread's tsproc structure.
ts_timeleft tracks execution time when the kthread is running on a processor
or is decremented in the clock tick handler (if the thread is actually running on
processor, of course). When ts_timeleft counts down to 0, the kthread has
its quantum and is context-switched off the processor. ts_dispatch tracks
how much the thread has spent switching on a dispatch queue, waiting to
context-switched onto a processor for execution. For all threads on a dispatch
queue, ts_dispatch is updated once a second by the ts_update() thread, which
is out of the fallout queue from the clock interrupt handler (more on this in a
minute).

When the priority work has been done and t_pri in the kernel head has a
valid dispatch priority, the thread is ready to be placed on a dispatch queue; such
placement is ultimately done by one of the dispatcher queue management func-
tions, setfrontdq() or setbackdq(). How these functions work and whether a
kthread ends up at the front or back of a queue matters we'll get into just a
bit.
