For objects greater than 1/8th of a page, a different scheme is used. Allocating objects from within a page-sized slab is efficient for small objects but not for large objects. The reason for the inefficiency of large-object allocation is that we could fit only one 4-Kyte buffer on an 8-Kyyte page—two 4 Kyte buffers would need just over 8 Kytes. For large objects, we allocate a separate slab management structure from a separate pool of memory (another slab allocation cache, the kmem_slab_cache). We also allocate a buffer control for each page in the cache from another cache, the kmem_bufct1_cache. The slab/bufct1/buffer structures are in the slab layer in Figure 6.5 on page 224.

The slab layers solve another common memory allocation problem by implementing slab coloring. If objects all start at a common offset (e.g., 512-byte boundaries), then accessing data of each object could result in the same cache line being used for all of the objects. The issues are similar to those discussed in “The Page Scanner” on page 178. To overcome the cache line problem, the allocator applies an offset to the start of each slab, so that buffers within the slab start at a different offset. This approach is also shown in Figure 6.5 on page 224 before the actual buffer. Slab coloring results in much better cache utilization and evenly balanced memory loading.

## 6.2.4.8 Slab Cache Parameters

The slab allocator parameters are shown in Table 6-12 for reference only. We recommend that none of these values be changed.

| Parameter | Description | 2.7 Def. |
|---|---|---|
