```
# adb -k /dev/ksyms /dev/mem

We can see that this system, the segmap segment has been created at boot as 0x7432000 bytes, or 121,839,616 bytes. This system is a 128-Mbyte Ultra-1, and we can see that free memory was smaller than the 256-Mbyte maximum segment size for the sun4 architecture. Hence, the segment was created at whatever the size of free memory was at that point. Once segmap is created, the segment interfaces are called directly from the file system code during the read and write operations.

The segmap driver divides the segment into block-sized slots that represent blocks in the files it. The segmap block size for the Solaris kernel is 8,192 bytes. A 128-Mbyte segmap segment would, for example, be divided into 128-MB/8-KB slots, or 16,384 slots. The segmap driver maintains a hash list of its page mappings so that it can easily locate existing blocks. One list entry exists for each slot in the segmap segment. The structure for each slot in a segmap segment is defined in the <vm/segmap.h> header file, shown below.

/
* Each smap struct represents a MAXSIZE-sized mapping to the
* <sm_vp, sm_off> given in the structure. The location of

* mapping. Structure rearranged for 64-bit sm_off.

struct map {
    struct vnode *sm_vp; /* vnode pointer (if mapped) */
    /*
     * These 3 entries can be coded as

     */
    struct sm *sm_hash; /* hash pointer */
    struct sm *sm_next; /* next pointer */
    struct sm *sm_prev; /* previous pointer */
    ushort_t sm_off; /* file offset for mapping */
    ushort_t sm_bitmap; /* bitmap for locked translations */
    ushort_t sm_refcnt; /* reference count for uses */
};
struct smfree {
    struct smap *sm_free; /* free list array pointer */
    kmutex_t sm_mtx; /* protects smap data of this color */
    kcountvar_t sm_free_cv; /* someone wants a slot of this color */
    ushort_t sm_want;
};
```

The smap structures are:

- sm_vp — The file (vnode) represents slots (if not empty)
- sm_hash, sm_next, sm_prev — Hash list reference pointers
- sm_off — The file (vnode) offset for a block-sized chunk in this slot in the file
- sm_bitmap — Bitmap to maintain translation locking
- sm_refcnt — The number of references to this mapping caused by concurrency

The important fields in the smap structure are the file and offset fields, sm_vp and sm_off. These fields identify which page of a file is represented by each slot in the segment.

| :--- | :--- |

| get_re | The number of times getmap found a valid mapping for the file and offset already in the segment. |

| get_unused_nofree | Not used—always. The number of times a request for a slot was made and none available on the free list of slots. This number is usually zero because each slot is put on the free list when release is called at the end of I/O. |

| rel_write | The slot was released as a result of a write call. |
| rel_free | The slot was released, and the VM system may need to free it and retain its file/offset information. These pages are placed on the cache tail so that they are not the first to reused. |
| rel_abort | The slot was released and asked to be removed from the segmap segment as a result of a aborted write. |
| rel_dontneed | The slot was released, and the VM system told the page it won't be needed again. These pages are placed on the cache head so they will be reused. |

our example segmap statistics show us that 15,257,790 times a slot was reclaimed out of a total 16,109,564 getmap calls, a 95% reuse with the correct file and offset, or a 95% cache hit ratio for the file system pages in segmap. Note that the actual page-to-cache hit ratio may be higher even if we are in segmap, we could still have the pages in the page cache and only need to reload the address translations for the file. A lower segmap hit ratio and high page-to-cache ratio is typical of large memory machines, in which segmap is limited to only 256 megabytes of potential gigabytes of memory.

Writing is a similar process. Again, segmap getmap is called to retrieve or create a mapping for the file and offset, the I/O is done, and the segmap slot is released. An additional step is involved if the file is extending or a new page is being created within a hole of a file. This additional step calls the segmap_pagecreate function to create and lock the new pages, then segmap_pageunlock() to unlock the pages that were locked during the page_create.

The segmap cache can grow and shrink as pages are paged in and out as pages are stolen by the page scanner, but the maximum size of the segmap cache is capped at an architecture-specific limit.

# 13.5 Path-Name Management

But a few of the vnode methods operate on vnode pointers, rather than path names or file descriptors. Before calling file system vnode methods, the vnode framework first converts path names and file descriptors into vnode references. File descriptors may be directly translated into vnodes for the files they referenced, whereas path names must be converted into vnodes by a lookup of the path-name components and a reference to the underlying file. The file-system-independent lookup() function converts path names to vnodes. An additional wrapper, lookupname(), converts path names from user-system calls.

# 13.5.1 The lookup() and lookupname() Methods

Given a path, the lookupname() method attempts to return a pointer to the vnode that path represents. If the file is already opened, a new reference to the file is established, and if not, the file is first opened. The lookup() decomposes the components of the path name, separating them by "/" and, calls the file-specific vop_lookup() method for each component of the path name.

If the path begins with "/", path-name traversal starts at the user's root directory. Otherwise, it starts at the vnode pointed to by the user's current directory. lookup() traverses the path one component at a time, using the vop_lookup() vnode method, vop_lookup() takes a directory vnode and a component as arguments and returns a vnode representing that component.
