The fork(2) and exec(2) system calls are used extensively in the various software components that come bundled with Solaris as well as in hundreds of applications that run on Solaris. (However, more and more Solaris daemons and applications are being threaded with each release, which means the programs use threads as an alternative to multiple processes.)

The fork(2) system call creates a new process. The newly created process is assigned a unique identification (PID) and is a child of the process that called fork; the calling process is the parent. The exec(2) system call overlays the process with an executable specified as a path in the first argument to the exec(2) call. The model, in pseudocode format, looks like this:

```c
main(int argc, char *argv[], char *envp[]) {
  pid_t child_pid;
  child_pid = fork();
  if (child_pid == -1)
    perror(fork()); /* fork system call failed */
  else if (child_pid == 0)
    exec(/path/to/new_binary,argv); /* in the child, so exec */
  else
    wait(pid > 0); /* we are in the parent */
}
```

The pseudocode above calls fork(2) and checks the return value from fork(2) (pid). Remember, once fork(2) executes successfully, there are two processes: fork returns a value of 0 to the child process and returns the PID of the child to the parent process. In the example, we called exec(2) to execute new_binary once in the child. Back. In the parent, we simply wait for the child to complete (we'll get) back later to this notion of “waiting”.

A couple of different flavors of fork(2) are available to take different code paths in the process creation flow. The traditional fork(2) duplicates the entire parent process, including all the threads and LWPs that exist within the process when the fork(2) is executed.

With Solaris 2.X and threads support some variant of fork(2); fork1(2). Linking with ent fork1(2), call only the thread that issues the fork1(2) call and its associated support structures are replicated. This call is extremely useful for multithreaded programs that also do process creation because it reduces the overhead of replicating a few or hundreds of threads in the child. If an exec(2) call is planned following the fork(2), as is typically the case, the exec(2) code frees all one LWP/kthread, which makes the use of fork(2) somewhat superfluous in a multithreaded process. Note that linking fork to a particular threads library modifies fork’s behavior. Linking with the Solaris threads library (-thread compilation flag) results in the described replicate results in a call to fork(2) replicating only the calling thread. In other words, linking with -lpthread (POSIX threads library) and calling fork(2) results in fork1(2) behavior.

Finally, there’s vfork(2), which is described as a “virtual memory efficient” version of fork. A call to vfork(2) results in the child process “borrowing” the address space of the parent, rather than the kernel duplicating the parent’s address space for the child, as it does in fork(2) and fork1(2). The child’s space following a vfork(2) is the same address space as that of the parent. More specifically, the physical memory pages of the new process’s (the child) address space— the implication here is that the child must not change any state while executing in the parent’s address space until the child exits or executes an exec(2) system call—once an exec(2) call is executed, the child gets its own address space. In fork(2) and fork1(2), address space of the parent is copied for the child by means of the kernel address space duplicate routine (the kernel as_dup(1)).

For some applications, the use of vfork(2) instead of fork(2) can improve application efficiency noticeably. Applications that fork(2)/exec a lot of processes (e.g., mail servers, Web servers) do not incur the overhead of having the kernel create and set up a new address space and all the uniting segments with each fork(2) call. Rather, address spaces are built as needed following the exec(2) call.
