
## 5.4 EXTERNAL SERVICES CONSUMPTION

In many cases, you will have to use external services (APIs, Web Services, etc.) in your application. .NET Core has dedicated packages and functionalities for this purpose.

For simplification, we will consider the consumption of REST (Representational State Transfer) services, as that is the most common service type you will encounter in your developments. REST is a protocol based on the HTTP request protocol with the associated verbs:

- **GET**: Used for data retrieval.
- **POST**: Used for adding data from the client to the server.
- **PUT**: Used for updating the data on the server.
- **DELETE**: Used for deleting data on the server.

As one of the key design goals for .NET Core is to minimize the size of the installation, you will have to add the required dependency (package) to your project.

![](img/3d310cc066dda6e2dfa67a650614076f_80_0.png)

Once you have added the required dependency, you can start the process of using the REST service. You can achieve that through three basic steps (this sample illustrates the consultation of a service):

1. Building the request.
2. Processing the request and retrieving data (results).
3. Processing the results.

### 5.4.1 Building the Web request

First, you will have to specify the endpoint address. Once this is done, you will instantiate the `HttpClient` class to perform the web request. This API supports only async methods (which is useful when working on the network). The web request will be performed by an async method (see sample code for the REST Client).

### 5.4.2 Processing the request and retrieving data

The call to the web request will be done with the `await` keyword (as this is an async method).

### 5.4.3 Processing JSON result

Once you have retrieved the data from the REST service (HTTP status 200), you will have to convert the JSON result into an exploitable C# object. To do that, you have to write a class for the type of object matching the JSON result format you expect.

> **TIPS:** In Visual Studio, use the menu *Edit / Paste Special / Paste JSON as Classes* for generating C# objects from JSON data.

### 5.4.4 Sample code for a REST client

Here is a snippet illustrating the use of a REST web service in your .NET Core 3 application.

**ProgramRESTClient.cs**

```csharp
BasicHttpBinding basicHttpBinding = null;
EndpointAddress endpointAddress = null;
ChannelFactory<IAService> factory = null;
IAService serviceProxy = null;

try
{
    basicHttpBinding = new BasicHttpBinding(BasicHttpSecurityMode.Transport);
    basicHttpBinding.Security.Transport.ClientCredentialType = HttpClientCredentialType.Basic;
    endpointAddress = new EndpointAddress(new Uri("https://uri.com/api"));
    factory = new ChannelFactory<IAService>(basicHttpBinding, endpointAddress);
    factory.Credentials.UserName.UserName = "usr";
    factory.Credentials.UserName.Password = "pass";
    serviceProxy = factory.CreateChannel();

    using (var scope = new OperationContextScope((IContextChannel)serviceProxy))
    {
        var result = await serviceProxy.getSomethingAsync("d").ConfigureAwait(false);
    }
    factory.Close();
    ((ICommunicationObject)serviceProxy).Close();
}
catch (MessageSecurityException ex)
{
    throw;
}
catch (Exception ex)
{
    throw;
}
```

## 5.5 THREADING GUI

As we have seen in the previous chapter, the reactivity of an application is a crucial metric of the user's global quality perception of a desktop application.

Good reactivity in an application can be reached by giving each heavy processing task and User Interface task its own thread. Thus, the main process is never overloaded, and the application continues to respond to the user (reactivity), regardless of the previous instructions.

There are several methods for achieving this threading, depending on the type of solution you want to use for developing your multiplatform application (Console, XAML, HTML, Native UI, etc.).

The threading of long and complex tasks in your application can be done in a progress window where you display a gauge (or other progress indicator) control and propose to the user the option to cancel the operation in progress.

![](img/3d310cc066dda6e2dfa67a650614076f_83_0.png)

But most of the time, threading does not have its own window and reports to the application the status of the operation through some kind of information bar. This can be done by using delegates and common threading techniques (as illustrated in the following sample).

The following simple .NET Core 3 WinForms example illustrates how it can be done by the use of delegates:

![](img/3d310cc066dda6e2dfa67a650614076f_84_0.png)

## 5.6 Using unmanaged dependencies

Multiplatform development with .NET Core 3 will sometimes imply the use of platform-specific dependencies (.dll files with Windows, .so files with Ubuntu, .dylib files with macOS).

The capability for the developer to access unmanaged methods from his .NET Core 3 program is mandatory for conducting many types of projects.

You have to keep in mind that, in the multiplatform context, you have to get the native library file (or its equivalent for the platform) for each platform, in our case Linux, macOS, and Windows. So, verify if the library you plan to use for your multiplatform project will be available for each OS you target before actually using it in your development on the Windows platform.

For example, many system functions are accessible only through native APIs. For doing so, you should know basic concepts for the use of unmanaged code with .NET Core 3 (which is managed code):

- P/Invoke
- Marshalling
- Establishing the running OS

### 5.6.1 P/Invoke

P/Invoke is an acronym for Platform Invocation Services. This mechanism allows the developer to use external unmanaged dependencies in his managed code (.NET Core).

Here is a sample of the use of P/Invoke for retrieving the current process ID (pid):

**For Linux (ubuntu):**

```csharp
using System.Runtime.InteropServices;

namespace PInvokeSample
{
    public static class Program
    {
        [DllImport("libc.so.6")]
        private static extern int getPid();

        public static void Main(string[] args)
        {
            int pid = getPid();
            Console.WriteLine(pid);
        }
    }
}
```

**For Windows:**

```csharp
using System.Runtime.InteropServices;

namespace PInvokeSample
{
    public static class Program
    {
        [DllImport("Kernel32.dll")]
        private static extern uint GetCurrentThreadId();

        public static void Main(string[] args)
        {
            int pid = GetCurrentThreadId();
            Console.WriteLine(pid);
        }
    }
}
```

For this sample code, which retrieves the current process ID, it is better to make a copy of the dependencies in the folder of the application. A tricky part for using system native libraries in your code is to retrieve the location of these libraries in each system. That's a point where you can encounter many troubles, and the copy of the libraries in the project folder (or in a subfolder in the project) can help you to solve most of these issues. You also have to verify that the paths of the program context contain the required libraries for the OS where your application should be executed.

In the previous sample, we can see that the native calls are changing according to the OS. In this case, multiplatform development means producing the code for each platform's specificities.

If you want to use native functions that are not already written and accessible in the system API of the OS, you have to develop your own libraries (one version for each OS).

Here are some reference links about the system APIs for each OS:

- **Windows:** [http://pinvoke.net](http://pinvoke.net)
- **Linux (ubuntu):** [http://kernel.org/doc/html/latest](http://kernel.org/doc/html/latest)
- **macOS:** [https://developer.apple.com/library/archive/navigation/](https://developer.apple.com/library/archive/navigation/)
