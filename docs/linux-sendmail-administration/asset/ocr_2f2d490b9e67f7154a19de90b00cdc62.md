# Chapter 6 Using Sendmail Databases

Returning error messages are not the only thing that can be done with the mailertable that replicates a feature of the virtertable. It is possible to use the mailertable to route mail for a virtual domain. For example, the following entry routes mail addressed to anyone in the bridal-g.com virtual domain to the user account jill:

```
.bridal-gowns.com local:jill
```

The advantage of using the mailertable for virtual domains is that, if you are already using the mailertable for some other purpose, you can do everything in one configuration. The disadvantage is that you cannot specify individuals in the virtual domain, only domain names, and you don't get the cool features of the virtertable, such as the ability to capture and reuse users with the %1 variable. Personally, I prefer virtertable.

One other thing you can do with the mailertable is to route it out all of the mail to a central mail server. Suppose you had a Red Linux client system that you wanted to configure all of your mail to mailserver.foobirds.org. You could create a custom max configuration on the client with a define command that sets SMART_HOST to mailserver.foobirds.org, or you could simply create a mailertable with a single entry:

```
smtp:mailserver.foobirds.org
```

SMART_HOST is a variable in the marco configuration that can be set to the name of a mail server that handles outbound mail for the client. The mailertable entry does essentially the same thing. The dot (.) in the first field matches all domain names. This means that all non-local mail will be sent through the esmtp mailer to mailserver.foobirds.org for delivery. This is exactly what we want for our imaginary client, and is exactly what the SMART_HOST define have given us. But this is simpler.

Once a mailertable source file is built, it must be processed through makemap. By default, Sendmail exports the mailertable database to be in hash database format.

The likelihood that you will need to deal with a server that cannot handle internet is remote. Time has already solved most of the incompatibilities that made the mailertable and the wide variety of mailers necessary. The other uses of the mailertable can be performed by other databases.
