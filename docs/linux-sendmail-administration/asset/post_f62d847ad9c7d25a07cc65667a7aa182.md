
# The Generic Linux Configuration

The first source file called by the generic-linux.mc file is predictably enough, the linux.m4 OSTYPE file. The contents of the linux.m4 file must be analyzed to fully understand the generic Linux Sendmail configuration.

## The Linux OSTYPE File

The OSTYPE file contains operating system-specific configuration values. The biggest configuration variation between the different operating systems that run Sendmail is the location of files. Variables that define pathnames are commonly stored in the OSTYPE file. Since this file is specific to the Linux operating system and this book is about running Sendmail on Linux, let's take a look at the OSTYPE file.

The command OSTYPE(linux) loads a file linux.m4 from the ostype directory. Listing 5.2 shows the contents of this OSTYPE file:

### 5.2 The linux.m4 OSTYPE File

```
[craig]$ cat ../ostype/linux.m4
divert(-1)
#
# Copyright (c) 1998, 1999 Sendmail, Inc. and its suppliers.
# All rights reserved.
# Copyright (c) 1983 Eric P. Allman. All rights reserved.
# Copyright (c) 1988, 1993
# The Regents of the University of California. All rights reserved.
#
# By using this file, you agree to the terms and conditions set
# forth in the LICENSE file which can be found at the top level of
# the sendmail distribution.
#
#
divert(0)
VERSIONID(`$Id: linux.m4,v8.11.16.1 2000/05/09 18:48:58 gshapiro
Exp ($)
define(`/confEBINDIR`, `/usr/sbin`)
define(`/PROCM_MAILER_PATH`, `
define(`/PROCM_MAILER_PATH`, `/usr/bin/procmail`))
FEATURE(local_procmail)
```

The file begins with a copyright notice. The copyright notice is bracketed by a divert(-1) statement and a divert(0) statement, so it is treated as a comment and can be safely ignored. The VERSIONID macro can also be ignored.

> **NOTE** In the rest of this chapter, to reduce the size of the listings, the copyright statements that start the files are not printed, but you should be aware that they are there.

The first real configuration command in the file is a define statement that assigns a value to the confEBINDIR parameter. This parameter stores the path of the directory that holds certain executable binary files. The Sendmail 8.11 default for confEBindir is /usr/libexec. This define changes the setting to /usr/sbin. Both of these directories exist on Linux systems, but the /usr/sbin directory is the one that is more commonly used to hold system files, and in this case it is correct. The confEBINDIR path is to locate the smrh mailer, which is frequently used as the prog mailer on Linux systems. The smrh uses an unrestricted shell by default. Chapter 12, "Sendmail Security," describes the advantages of using the smrh mailer.) A couple of quick ls commands on our sample Linux system show that the correct value for confbinder is /usr/sbin:

```
[craig]$ ls /usr/libexec/smrh
ls: /usr/libexec/smrh: No such file or directory
[craig]$ ls /usr/sbin/smrh
/usr/sbin/smrh
```

The second configuration command is also a define. This is a little more complex. This define is contained in an ifdef. The ifdef has nothing to do with configuring Sendmail. It is a built-in mdef conditional command that checks whether or not a variable already been set to a value. The ifdef command has three fields:

- the name of the variable is being tested
- the action to take if the variable has been set
- the action to take if the variable has not been set

In Listing 5.2, the ifdef tests the variable PROC_MAILER_PATH. If the variable has already been defined, nothing is done. We know this by the fact that the second field of the ifdef is empty—notice the two commas in a row (,,). If the variable has not been set, the define contained in the third field of the ifdef is executed. This is exactly what happens on our sample system, because we did not assign any value to PROC_MAILER_PATH in the macro file. The define assigns the variable PROC_MAILER_PATH the path value /usr/bin/procmail. This overrides the Sendmail default for PROC_MAILER_PATH, which is /usr/local/bin/procmail. A quick ls shows that the new value is correct for our sample system:

```
[craig]$ ls -l /usr/bin/procmail
-rwxr-xr-x 2 root root 68276 Aug 10 1999 /procmail
```

I have a philosophical objection to having ifdef inside the OSTYPE file. I understand why it had to be done: it was done to create an OSTYPE file that would work for all versions of Linux. However, that is my objective. If different Linux distributions require different OSTYPE settings, the developers of such distributions should create an OSTYPE file for their distribution that contains the correct setting. After all, that is what the OSTYPE file is. There is no reason why there shouldn't be an ostype/redhat.m4 file, and an ostype/use.m4 file, and an ostype/slackware.m4 file, and a file for any other distribution developers would want to put their names in the ostype directory, but the fact is that no single Linux developer has added an OSTYPE file to the directory of the Sendmail distribution.

As Listing 5.2 shows, the last line in linux.m4 is a FEATURE macro. The feature that this macro adds to the configuration is local_procmail, which will specify that procmail will be used as the local mailer. You will see in Chapter 11, "Stopping Spam," procmail is a very powerful mailer. The fact that Linux uses procmail as the local mailer is a plus. The local_procmail feature accepts up to three options:

- The path to the mailer. The default is the path assigned to PROC_MAILER_PATH, which in Listing 5.2 is /usr/bin/procmail. The same effect could have been obtained with the following FEATURE command: FEATURE(`local_procmail`, `/usr/bin/procmail`)
- The command line for executing the mailer. The default is procmail -a -h $u, where h is replaced by the detail if the user+address syntax is used, and $u is replaced by the username from the recipient address. $ and $ are Sendmail variables that hold the remote hostname and the remote user's address in a standard delivery. In this case, however, procmail is being used as local mailer, so there is no hostname and the $ is used to hold the detail value. (See Appendix C, "Sendmail Variables, Options, and Flags," for a full listing of Sendmail flags.)
- The flags for this mailer. The default is SPFhn. (See Appendix C, "Sendmail Variables, Options, and Flags," for a full listing of mailer flags.)

> **NOTE** With the local_procmail feature, procmail is being used as the local mailer. The command-flags arguments and the mailer flags affected are those set by LOCAL_MAILER_FLAGS and LOCAL_MAILER_ARGS, not set by PROC_MAILER_FLAGS and PROC_MAILER_ARGS, which are used by the MAILER (procmail) command—despite the fact that local_procmail uses the path from PROC_MAILER_PATH instead of the path from LOCAL_MAILER_PATH. Oh well, no one said it was easy to understand.

The linux.m4 OSTYPE type defines the directory for the smrsh program, the path for procmail, and a feature that uses procmail as the local mailer. Clearly, the OSTYPE type is a good place to look for filenames and mailer options. The name of settings in linux.m4 relate to the problem we saw when we tried to use the generic.cf file on our sample system; everything in the linux.m4 file is worth understanding because all of these settings affect the configuration of a Linux system.

The second m4 source file loaded by generic-linux.mc, as shown in Listing 5.1, is the generic.m4 file from the domain directory. It looks at that file in detail.

## The Generic DOMAIN File

The DOMAIN command is optional. It loads the m4 source file that you create to configure values specific to your domain or network. You don't have to create a DOMAIN source file, but it is highly recommended that you do if you have any domain-specific processing.

Host and username processing, domain name masquerading, mail relaying, and anti-spam features are the types of information normally found in a DOMAIN source file. Listing 5.3 shows the generic.m4 DOMAIN file used by the generic-linux.mc macro configuration file.

### Listing 5.3 The Configuration Commands in domain/generic.m4

```
[craig]$ tail -6 generic.m4
VERSIONID($id: generic.m4,v 8.15 1999/04/04 00:51:09 ca Exp '$)
define(CONFORWARD_PATH, '$forward.w+h$z$/forward.w+h$z$/)
forward.w$)\dn1
define(CONMAX_HEADERS_LENGTH, '32768')dn1
FEATURE(redirect)dn1
FEATURE(use_cw_file)dn1
EXPOSED_USER(root'))
```
