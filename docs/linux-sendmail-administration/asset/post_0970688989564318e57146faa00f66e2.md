Study the actual usage patterns of your system before you select a value, and then set the value at least 50 percent above the observed maximum value to allow for usage spikes.

confCONNECTION_RATE_THROTTLE is useful on the exact systems as confMAX_DAEMON_CHILDREN. In fact, the two parameters are often used together. confMAX_DAEMON_CHILDREN sets the absolute upper limit on the number of simultaneous-mail connections and confCONNECTION_RATE_THROTTLE sets the rate at which you will limit to that maximum. However, an attacker can easily overrun the connection rate you set in order to deny you mail access. However, setting the rate can protect the other services on your system so that you have an operational system to help you with the attack.

confMAX_MESSAGE_SIZE This parameter defines the maximum size of messages the mail server will accept. Any messages larger than this are rejected. By default, Sendmail accepts messages of any size. This command overrides default and sets the maximum message size to 2,000,000 bytes.

```
define('confMAX_MESSAGE_SIZE', '2000000');
```

Some DoS attacks are designed to overwhelm the file systems by writing enough large e-mail messages to completely fill the disk containing the spool directory. This parameter is intended to protect against these attacks, but it is largely ineffective because the attacker can send a large number of smaller messages for the same effect.

It is impossible to completely protect Sendmail from denial of service attacks. Limiting the amount of damage done by the attack is the real purpose of the parameters described above. Similarly, the techniques used to protect Sendmail from unauthorized access are really meant to protect the system as a whole.

# Securing Sendmail against Unauthorized Access

The most dangerous security exploits are those that use unauthorized access to grab root permission. Once an intruder has gained root access, nothing can be done to protect anything on the system, including Sendmail. The purpose of most Sendmail security is to make sure that Sendmail is not used as the means for an intruder to gain unauthorized access or root permission. To that end, the user IDs and files that Sendmail depends on be secured.

Sendmail uses three different user IDs depending on the action it is taking. The three user IDs are:

DefaultUser This is an option in the sendmail.cf file that identifies the user ID and group ID used to run mailers and other external commands. There are three possible default values for the DefaultUser option:

- If the user mailnull is defined in the /etc/passwd file, the user ID and group ID assigned to mailnull are used.
- If mailnull is not defined and the user daemon is defined in the /etc/passwd file, the user ID and group ID assigned to daemon are used.
- If neither mailnull nor daemon is defined in the /etc/passwd file, 1 is used as the user ID and 1 is used as the group ID.

The default value for the DefaultUser option can be overridden by defining a specific value in the m4 configuration file with the confDEF_USER_ID parameter. The m4 configuration file delivered with Red Hat 7 contains the following confDEF_USER_ID command:

```
define(`confDEF_USER_ID`, '8:12`)
```

This command sets the user ID to 8 and the username in /etc/passwd file delivered with the Red Hat 7 system. It is interesting to note that the Red Hat 7 /etc/passwd file also has an entry for the user mailnull and for the user daemon. daemon is no surprise because it is used by several different daemon processes. On the other hand, the surprise mailnull must have been specifically added to act as a default value for the DefaultUser option because it serves no other purpose. Given that, it is not clear why Red Hat also defined a value for the confDEF_USER_ID parameter. Here are the mailnull entries from Red Hat 7 /etc/passwd file and the /etc/shadow file:

```
[craig]$ grep mail /etc/passwd
mail:x:8:12:/var/spool/mail:
mailnull:x:47:47:/var/spool/mqueue:/dev/null
[root]# grep mail /etc/shadow
mail::11267:0:99999:::
mailnull::11267:0:99999:::
```

While Red Hat provides two /etc/passwd entries that are specifically defined to be used by the DefaultUser option, many Linux systems do not provide such entries. Both of the Red Hat entries show two of the characteristics you need to be aware if you add a mailnull account. mailnull cannot have an associated password and it cannot have a valid login shell. mailnull has /dev/null as the login shell defined in the /etc/passwd file. Additionally, the mailnull user does not have a valid password in either the /etc/passwd file or the /etc/shadow file. Therefore, the mailnull user meets the first two requirements. The third requirement for the mailnull user account is that it cannot own any files. These three requirements prevent the account from being exploited to gain unauthorized access.

# Securing Files and File Access

Using the correct user for Sendmail is only part of the story. Sendmail also needs to be careful about the files it reads and what is in them. Maintaining the following standards will help avoid problems:

- Files that the relay-domains file is writable, for example, if anyone on the system can grant relay permission to their favorite spammer. The recommended permission for files read by Sendmail is 644.
- Files read by Sendmail should not be in group- or world-writable directories. Again, anyone in a given group, or perhaps anyone on the system, can create a file Sendmail bad instructions. The recommended permissions for directories used by Sendmail is 755.
- Files read or written by Sendmail should not be symbolic links.

In some conditions—for reading a .forward file—Sendmail checks that these standards are being maintained. You can disable this file access by setting the DontBlameSendmail option using the DontBLAME_SENDMAIL parameter in the m4 configuration file. All of the DontBlameSendmail settings reduce security, so they are not covered here. For more information about this option, see Appendix C, "Sendmail Variables, Options, and Flags."

Sendmail takes special care with the .forward file because that can contain an e-mail address that forwards the file to a program using the l program, where program is the name of the program to be executed. The aliases database can also use this syntax.
