In Listing 11.2, the administrator of wen used grep to check that the sendmail.cf file is already configured to read the relay-domains into class R. If it wasn't, a configuration file using either the confFR_FILE option or the RELAY_DOMAIN_FILE macro, would be needed before the relay-domains would be effective. After configuring the relay-domains, the administrator passes Sendmail a SIGHUP signal to make sure it reads the new configuration. After the reload, wen relays mail for any system in the mammals domain, including ox.mammals.org, as the final test clearly shows.

In Listing 11.2, class R contains four values. The first two values illustrate that individual hosts can be granted relay privileges either by specifying the host's fully qualified name or by specifying the host IP address. Both the hostname ibis.foobirds.org and the host address 192.168.30.20 are granted relay access in Listing 11.2. The third value in the example is a domain name. It grants relaying to every host in the mammals.org domain. The last value in class R is a network address that grants relaying privileges to every host on the network 172.30.

The access database can also be used to relax relay restrictions for hosts, domains, and networks. The four items in the relay-domains file shown in Listing 11.2 could grant granted relay privileges with the following access database entries:

- ibis.foobirds.org RELAY
- 192.168.30.20 RELAY
- mammals.org RELAY
- 172.30 RELAY

Again, the systems granted access are identified by name or address. But this time the specific action to be is explicitly spelled out by the RELAY keyword. The other keywords and values that can be used in the action of access database entry mean that the database can be used for more than just enabling. As you will see later in this chapter, the access database is also a powerful anti-spam tool. It holds everything in one file—both the entries that enable relaying and the entries that block spam—I prefer to use the access database over the relay-domains file. I like to have controls in one place where they can be evaluated together as a whole. By nature, access controls are most effective if they are coordinated, and a single file makes coordination easier. (The details of the syntax and structure of the access database are covered in Chapter 6.)

The systems relaying through class R or the access database are identified as individual hosts, entities or entire networks. Generally, the hosts, domains, and networks identified in class R or the access database are remote hosts, domains, and networks. If you want to relay for the hosts in your domain, Sendmail provides a simpler way to handle your local domain.

The relay_entire_domain feature grants relaying to every host in the domains listed in class m. Because class m is used for more than just relaying, only local domains should be listed in this class. Adding the following command to the sample server configurations shown throughout would enable relaying for every host in the foobirds.org domain:

```
FEATURE(relay_entire_domain)
```

At first glance, the relay_local_from feature appears to do the same thing as the relay_entire_domain feature—they both relay mail from every host in the local domain. The difference is that they differ in ways. The relay_entire_domain feature checks the source of the mail connection against the values in class m to see if the connection is from a local host, relay_local_from relays mail that contains the local domain name in the Mail From: header. Because the Mail From: header can be written to anything the source system sends, relay_local_from is not as secure as relay_entire_domain.

The relay_based_on_mx feature is another feature that grants relating to a group of hosts. This feature will relay mail for any host where the local host is an MX server. This is a useful feature if the server that inbound mail for your clients is also the system that handles their outbound mail. The MX record that routes mail through the server to its clients can also be the signal to relay outbound mail from those clients. The weakness of this approach is that the Sendmail administrator cannot control all of the MX records in the same domain name. A remote site could relay mail through your server by simply adding an MX record to their domain. Despite this weakness, this feature is still an effective defense against spammers. Because they can hide the source of spam mail, spammers don't send mail that can be tracked back to their domain names, and thus they cannot write MX records for the domain names they use.

The last feature that relaxes restrictions is probably the most dangerous. Is the FEATURE ('promiscuous_relay') Current versions of Sendmail block by default. The promiscuous_relay feature returns to the past by telling Sendmail to relay all mail from any source. This feature is intended for those times when Sendmail cannot resolve domain names because of intermittent connectivity or a restrictive firewall. Otherwise I wouldn't use it.

## Chapter 11 Stopping Spam

The first step toward blocking spam is to remove the accept_unvable_domains from the configuration of your system. Course, this is just a first step that returns your system to a nominal level of spam control. This further that increase spam controls. One uses a DNS-based service to block spam sources, another uses a local database that you create, and still others use custom rewrite rules. The first is easy and convenient; the second gives you greater control; the third gives you complete control. Not Surprisingly, the more control complex the technique becomes.

## Using the Realtime Blackhole List

The simplest way to block spam is to let someone else do it. Sendmail allows you to use the Realtime Blackhole List (RBL) that comes from the Mail Abuse Prevention System (MAPS). The RBL is a DNS database that contains the IP addresses of spam sources. The sources can be the original source of the spam, or a mail server that permits spammers to relay mail.
