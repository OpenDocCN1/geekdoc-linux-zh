```
VIRTUSER_DOMAIN_FILE('/etc/mail/virtual-domains')
```

After adding the VIRTUSER_DOMAIN command to the macro configuration file, rerun m4 to build the new sendmail.cf file. Then add the virtual domains from Listing 6.9 to the new virtual-domains file, one domain per line, as shown below:

> TIP Both the VIRTUSER_DOMAIN and VIRTUSER_DOMAIN_FILE macros require changing and rebuilding the sample configuration. Because we already had the local-host-names file in our configuration, it would be easier to add the virtual domains to that file. It works just well because Sendmail checks both w and class (VirthHost) when processing virtual domains.

## Defining virtetable Delivery Addresses

The delivery address in all three sample entries in Listing 6.9 is a simple e-mail address. It doesn't have to be the input address or an error message that Sendmail returns to the sender. Listing 6.10 shows a larger virtetable with a variety of values in the delivery address field.

Listing 6.10 A Sample virtetable

```
sales@bridal-gowns.com  jill
info@patient-rights.org  sara@hawk.foobirds.org
@imaginary.com  david@lion.mammals
sales@outbusiness.com  error:user address is not valid
sales@webroke.com  error:5.1.5 Destination address invalid
@other.org  %1@local.org
+*@thatplace.com  %2@newplace.com
```

The first three entries have already been explained. Mail is accepted with a virtual domain address routed to a real e-mail address. The e-mail address in the second field must be a real address; it cannot be another virtual domain address. For example, the virtuosable entries would not work as you might think:

sales@bridal-gowns.com sales@imaginary.com
@imaginary.com david@lion.mammals.org

This cannot be used to forward mail addressed to sales@bridal-gowns.com to david@lion.mammals.com. Unlike aliases that can point to other aliases, virtual domains cannot point to other virtual domains.

The next two lines in Listing 6.10 illustrate the use of error messages. Mail addressed to sales@outofbusiness.com is not delivered. Instead, an error message “User address is not valid” is returned to the sender. Mail sent to sales@webroker.com returns the error message “Destination invalid” to the sender.

Error messages must start with the error code, which is the name of a special mail that is built into Sendmail. Separated by a colon from the error code is an error condition, specified either as a keyword or as a DSN code. The DSN code can be any valid code defined in RFC 1893. The error condition keyword must be a keyword recognized by the error mail. A list of valid error condition keywords is found in Chapter 8, “Understanding Rewrite Rules,” in the discussion of the error mail.

> TIP DSN codes are an Internet standard and are well defined in the RFC. The change to Sendmail and subject to change in future releases.

The two lines in Listing 6.10 provide examples of how values from the input address can be used in the outbound address. The @other.org entity provides the class example. The username part of the input address is passed in the % variable, so that % in the outbound address is replaced by the username from the input address. Using the virtuunable shown in Listing 6.10, mail addressed to pat@other.org would be delivered to pat@local.org and mail sent to doris@other.org would be forwarded to doris@local.org.

This is a powerful feature. Obviously, it can be used to ease the transition when you change domain names, but that is a rare occurrence. More importantly, this feature can be used when the products you sell are not clearly associated with your official domain name. Assume you have an online mall that sells party products. The real name of your domain is stuffycorporation.com, but you also own the domains funstuff.com and happythings.com. The following two lines in the virtuertable would route mail to the correct employee regardless of the domain to which it was addressed:

```
@funstuff.com               %1stuffycorporation.com
@happythings.com         %1stuffycorporation.com
```

The last line in Listing 6.10 shows that the +detail value in the +detail syntax can be passed to the outbound address as Mail sent to sales+info@thatplace.com would be delivered to info@newplace.com and mail sent to +detail sent to sales+orders@thatplace.com would be delivered orders@newplace.com. Notice that the use of +detail syntax must be indicated the first field of the virtuertable by placing +before in the virtual address domain. Use of e-mail addresses enough without using the +detail syntax. For this reason, the syntax is rarely used unless you have a program that automatically generates this syntax for the user. It is covered here the sake of completeness, but you will probably not use it in your configuration.

[root]# makedemap hash virertable <
[root]# sendmail -bv sales@bridal-gowns.com
sales@bridal-gowns.com... deliverable: mailer local, user jill

The virertable database is built with the makedmap command and then tested sendmail with the bv argument. The -bv argument causes the sendmail command to process the address on the command line as a delivery address. The test shows that sales-gown.com will be delivered via the local mailer to the user jill. This is just what we expected on the first line of the virterable.

In Listing 6.1 we examine the contents of the local-host-names file and the virtable source file shows that all of the virtual domains have been added to class. If the virtual domains are not added to class virtHost, the sendmail -bv produces the following result:

```
[root]# sendmail -bv sales@bridal-gowns.com
sales@bridal-gowns.com... deliverable: mailer smtp,
host bridal-gowns.com, user sales@bridal-gowns.com
```

This test shows Sendmail believes that sales@bridal-gowns.com is an external domain that can be reached through the smtp. If we define the virtual domain in the local-host-names file and forgot to provide the mapping in the virtable, either by not including it in the file or not running makedemap, sendmail -bv produces the following result:

```
[root]# sendmail -bv info@patient-rights.org
info@patient-rights.org... deliverable: mailer local, user info
```

Here the virtual domain is accepted, but the address is not mapped to the external host as we wished.

There are many reasons to use the virtertable, particularly if you run an ISP that provides service to a large number of customers or run an e-business site. It is easy to see why Red Hat includes this in their default Sendmail configuration. The last database included in the redhat.mc file, the mailtable, is more rarely used.

## The mailtable

The mailtable is rarely used. It maps domain names to the internal mailer that should handle mail bound for that domain. The reason that this database is rarely needed is that Sendmail usually routes to the correct mailer without any help from you.
