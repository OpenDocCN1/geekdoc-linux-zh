## Extended SMTP

SMTP was not designed to handle multiple data types; thus, it needed enhancements to handle MIME data. RFC 1869 ("SMTP Service Extensions") defines an extensible version of SMTP, by defining specific service extensions, and by specifying a technique that systems can use to negotiate SMTP extensions they support. RFC 1869 defines a new version of the SMTP EHLO command named EHLO.

A system that runs ESMTP sends EHLO in the greeting to start the session. If the receiving system does not run ESMTP, it rejects EHLO as an error. The sending system can initiate the session with the old EHLO command or terminate the session. If the receiving system runs ESMTP, it responds to the EHLO command by sending a listing of the extended SMTP features it supports. Each feature is identified by a standard keyword. Thus the sending system knows the capabilities of the receiving system and can use any of the features that the remote system advertises.

## Extended Service Keywords

Two of the advertised services are basic SMTP commands defined in RFC 821. HELP provides access to the online help system, EXPN displays the addresses in a mailing list. This system advertises these services in the keyword list because many sites do not implement these commands.

Some of the keywords in the list indicate service extensions that are defined in various RFCs.

- ENHANCEDSTATUSCODES This server uses the enhanced status codes with Delivery Status Notifications (DSNs). The enhanced status codes are defined in RFC 1893, "Enhanced Mail System Codes."

- 8BITMIME This keyword indicates that the server can accept eight-binary data, which means 8bit and binary data types can be sent to this system without any additional encoding. This extension is defined in RFC 1652 ("SMTP Service Extension for 8-bitMIME transport").

  - >>> Mail From:<craigani.foobirds.org> SIZE=73

In this example, the SIZE keyword tells the receiving system that the message carries 73 bytes.

- DSN This server can provide delivery status notification. For example, the remote user can receive a receipt notification when the message is read. This extension is defined in RFC 1891 ("SMTP Service Extension for Delivery Status Notifications").

- ETRN This server allows remote sites to retrieve messages from the server's queue that are bound for the remote site. ETRN is an updated version of the TURN command that fixes the security problems that existed in TURN. This extension is defined in RFC 1985 ("SMTP Service Extension for Remote Message Queueing Starting").

- AUTH DIGEST-MD5 The AUTH keyword advertises the type of authentication supported by this server. In this case, the server supports Message Digest 5 (MD5) for authentication. The AUTH extension is defined in RFC 2554 (“SMTP Service Extension for Authentication”).

There are also a few keywords in this list that are not standard services. VERB sets the remote mail server in verbose mode. ONEX limits the SMTP session to the transfer of a single message. XUSR is used when a user mail agent sends directly to a remote server instead of passing it through a mail transfer agent, as Sendmail. (I don't know of any user mail agents designed to work this.) VERB, ONEX, and XUSR are specific to Sendmail version 8; they are not defined in an RFC.

## Mailbox Protocols

SMTP moves between e-mails, and MIME allows that mail to contain anything the user wants to send. SMTP is the protocol implemented by Sendmail, but it is the only protocol used in delivering the mail to the end user. As we saw in Listing 1.3, Sendmail stores the mail it receives in a mailbox on the Linux server. Any user that can log to the server can read it there. Many users, however, cannot or don't want to read their mail on the server. Those users want to move the mail from the server mailbox to a mail reader on their desktop systems. There are two popular protocols designed to move mail from the mailbox server to the desktop-client: Post Office Protocol (POP), which is the traditional mailbox protocol, and Internet Message Access Protocol (IMAP), which has become more popular.

## Post Office Protocol

The Post Office Protocol is a simple request/response protocol. It is defined in RFC 1939 (“Post Office Protocol”). POP3 is the most common version.

### Table 1.3 POP3 Commands

| Command | Function |
| :--- | :--- |
| USER | The username required for the login. |
| PASS | The password required for the login. |
| STAT | Requests the number of unread messages. |
| RETR | Retrieves the message. |
| DELE | Deletes the message. |
| LAST | Requests the number of the last message accessed. |
| LIST [msg] | Requests the size of message or all messages. |
| RSET | Undeletes all messages and resets the message number to 1. |
| TOP n | Prints the headers and the first n lines of message. |
| NOOP | Does nothing except request an OK response. |
| APOP string | Identifies a mailbox and provides an MD5 string for authentication. |
| UIDL [msg] | Requests the unique ID for the specified message, or a listing of all messages. |
| QUIT | Ends the POP3 session. |
