
## On a BSD-Style System

Linux systems as Slackware use BSD-style boot procedures start Sendmail by executing the sendmail command directly from one of the main start-up files. The code that runs the Sendmail daemon in the Slackware Linux /etc/rc.d/rc start-up script is very straightforward, as shown in Linux 3.1.

### 3.1 Starting Sendmail from a Slackware Boot Script

```
# Start sendmail daemon:
if [ -x /usr/sbin/sendmail ]; then
  echo "Starting sendmail daemon"
  /usr/sbin/sendmail -bd -q 15m
fi
```

Listing 3.1 shows a kernel system ready to run Sendmail. The first line is a comment, as indicated by the fact that it starts with a pound sign (#). The next lines are if statement checks whether or not the sendmail command is available. If the command fails, a message is displayed on the console indicating that Sendmail is starting and then the sendmail command is run.

The code in 3.1 runs the sendmail command with the -bd and the -q options. In addition to listening for inbound mail, the Sendmail daemon periodically checks to see whether there is mail waiting to be delivered. It's possible that a Sendmail process that was started to send a message was not able to successfully deliver the mail. In that case, the process writes the message to the mail queue and counts on the daemon to deliver it at a later time. The -q option tells the Sendmail how often to check the undivered mail queue. In the Slackware example, the queue is processed every 15 minutes (-15m).

To prevent Slackware from starting Sendmail at boot time, comment the lines shown in Listing 3.1 out of the rc.script by placing a pound sign at the beginning of each line. To restore Sendmail to the boot process, remove the pound signs. These techniques are easy and work, but they are far from elegant.

Directly editing a start-up script is easy, but dangerous. Most system administrators worry that an editing error will have a major negative impact on the next boot. I have never had a major boot problem cause by an editing error, but I understand the fear. Distributions that use V-style start-up procedures alleviate this fear by making it unnecessary to directly edit the start-up file.

## On a System V-Style Linux System

Most distributions use a System V-style boot process that allows the system to be initialized in different ways depending on the runlevel. All of the service initialization scripts are located in a single directory, usually called /etc/rc.init.d on Linux systems that use this style of start-up. The initialization scripts are indirectly invoked by links contained in directories assigned to each runlevel. Caldera and Red Hat are good examples of System V-style systems.

> NOTE: A detailed description of the Linux boot process is beyond the scope of this book. To learn more about the boot process, runlevels, and start-up scripts, Linux Network Servers 24seven by Craig Hunt (Sytex, 1999).

The code that Caldera and Red Hat use to start the Sendmail daemon is found in /etc/rc.init.d/sendmail script. It is more complex than the code used by Slackware, because Red Hat and Caldera use script variables from an external file to set the command-line options. The file they read is /etc/sysconfig/sendmail, which normally contains these lines:

```
DAEMON=yes
QUEUE=1h
```

Changing the values in the /etc/sysconfig/sendmail file controls the daemon configuration. The QUEUE variable sets the value of the -q option. In this case, it is one hour (1h), which is a value that I like even over the 15 minutes used in Slackware configuration. Setting this too low. Processing the queue often can cause problems if the queue grows too large due to a delivery problem such as a network outage.

If the variable DAEMON is equal to "yes", the sendmail command is run with the -bd option. If you are configuring a mail client and do not want to run Sendmail as a daemon, you could edit the /etc/sysconfig/sendmail file to set DAEMON=no.

> TIP: While changing the DAEMON value is one way to do this, it is generally better idea to edit the sendmail script from the start-up as described below than is to edit the contents of a script.

With System V-style start-up, you don't have to directly edit start-up files. One of the advantages of the System V-style boot procedure is that many services have their start-up scripts and those scripts are indirectly invoked, which makes it possible to control whether or not a service is started at boot time by controlling whether or not the script is invoked. The sendmail script is invoked indirectly from the runlevel directories by the S80sendmail script (see Listing 3.2). An examination of that script shows that it is just a symbolic link to the real sendmail script.

### Listing 3.2 The Sendmail Link for Runlevel 3

```
[craig]$ cd /etc/rc/rc3.d
[craig]$ ls -l S80sendmail -> ../init/sendmail
lrwxrxr-x 1 root 18 Dec 26 1999 S80sendmail
```

To enable or disable the sendmail start-up script for a specific runlevel, simply add or remove the symbolic link in that level's directory. In itself this would be simple enough, Linux systems make it easier by providing tools to manage the runlevel directories.

### Enabling Sendmail with sysvinit

All the services that can be controlled by sysvinit are listed on the left. On the right are the runlevels 2, 3, 4, and 5. To disable a service for a specific runlevel, simply highlight the service in the list and click Remove. For example, remove sendmail from runlevel 5. To Add a runlevel, highlight sendmail in the list and click Add. You'll be asked to select the runlevel. The default is 3 for multiuser users. Select the runlevel and click Done. The next time the system reboots, Sendmail starts.

> TIP: Of course you don't want to reboot your system just to run the sendmail script. Use the Execute button to run the script immediately.

sysvinit has a couple of nice features. First, it comes bundled with different versions of Linux. It runs just as well on Caldera as it does on Red Hat, and it runs just as well under Red Hat 6 as it does under Red Hat 7. Second, a clone of sysvinit called nsys runs in text mode and doesn't require X Windows. In that case, you will want a tool like nsys.

### Enabling Sendmail with nsys

ntsys is even easier to use because it doesn't bother you with lots of questions about runlevels. It allows the current runlevel as a default unless it is run with the --level argument. nsys presents you with a list of services that can be automatically started at boot time. One of these is Sendmail. The start-up script for every item in the list that has an asterisk next to it will be run during the next boot. Use the arrow keys to scroll down to the sendmail entry in the list and use the space bar to deselect sendmail. When the settings are just what you want, tab over to the OK button and press Enter. That's all there is to it. Figure 3.2 shows the main nsys screen.
