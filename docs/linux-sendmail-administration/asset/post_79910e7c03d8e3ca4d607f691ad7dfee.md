
There are more databases available for Sendmail than you will ever use. A couple are of little or no value to Linux sites—the bitdomain database converts addresses for a network that works no Linux sites and the uucdomain database converts UUCP “bang” addresses, the old hostuser e-mail addresses, that almost no one uses. Other databases have overlapping functions that you might not need to use both of them at your site. The default delivered by the RPM contains fewer than half of the defines and features listed above, and that configuration probably has more database capabilities than you will really need. To help you evaluate databases you do need, we will examine all of them in detail.

## The Cr, Cw, and Ct Files

The first three databases we cover are not, in the strict sense of the word, databases. They are disk files used to load sendmail.cf classes. The “cr” and “cw” perform important roles in configuring Sendmail, but changes in the security atmosphere of the network mean that the “ct” file has no useful role.

The file that loads the ct variable is often called the “ct” file because the traditional name of this file was /etc/sendmail.ct. In Sendmail 8.11 the default name of this file is /etc/mail/trusted-users, but the function of the file remains the same. It is used to add usernames to the list of users that are trusted to send mail under another user's name. By default, ct contains the usernames daemon, root, and ucp.

You will never use the /etc/mail/trusted-users file, and there are some good reasons why you won't. First, it is a bad idea to let people send mail under other people's names. In general, if you don't want to expand the list of trusted users, if you decide absolutely must add usernames to the trusted user list, you won't add enough to justify putting them in a separate file. For example, you could add the username “mail” to the trusted user list. You could edit the macro configuration file to add the FEATURE(use_ct_file) command, rebuild the sendmail.cf file, and create a trusted-users file containing the single word mail. But why? You could easily edit the macro configuration file to add the define(`TRUSTED_USERS`, `mail`) command, rebuild the sendmail.cf file, and be done with it. It is not only this second approach slightly easier, but it is safer because there is fewer file created and thus fewer file where the permissions could be set.

> **WARNING** Despite this example, neither TRUSTED_USERS nor use_ct_file is recommended because you shouldn't add any users to the trusted user list. Trusting users is a bad idea in this age of spammers and security crackers.

Unlike the "ct" file, which is never used, the "cr" file is always used. The "cr" file is really named the relay-domains file. Sendmail always uses the data it finds in the relay-domains file. The purpose and structure of the file is the next topic.

## The relay-domains File

When mail arrives at a Sendmail server, it is either accepted, rejected, or relayed. If it is addressed to the server itself, then any name that the server accepts as its, the mail is accepted for local delivery, meaning that the mail is placed in the mailbox of a local user or routed as directed by one of the Email databases. If the mail is not addressed to the server itself, the mail is either rejected or relayed. Mail is relayed by re-sending it to the delivery address. Prior to Sendmail 8.9, all mail addressed to another host that was received by a Sendmail server was relayed. Now, no mail is relayed unless you tell Sendmail to relay it. This change was a headache for many system administrators who were using a Sendmail server for outbound mail for their PCs. But Spammers were exploiting the relaying feature of Sendmail to hide the true source of spam. Now all administrators must pay the price of spam, and that is the extra work necessary to create an explicit relay configuration.

One way to explicitly enable relay is to list the names of hosts allowed to relay mail in the /etc/mail/relay-domains file. Sendmail copies anything written in that file to the class R. Any host listed in class R is allowed to relay mail. Listing 6.2 shows the contents of a simple relay-domains file.

## 6.2 Using the relay-domains File

```
[root]# cat /etc/mail/relay-domains
is.foobirds.org
[root]# ps -ax | grep sendmail
542 ? S 0:00 sendmail: accepting connections
[root]# kill -HUP 542
[root]# sendmail -bt
ADDRESS TEST MODE (ruleset 3 NOT automatically invoked)
Enter <ruleset> <address>
>$R
is.foobirds.org
^D
```

A SIGHUP signal is passed to the Sendmail process to ensure that it reads the hostnames from relay-domains into class R. The test in Listing 6.2 shows that class R was successfully modified.

NOTE The hosts listed in relay-domains and in class R are the sources of relayed mail; they are not the destinations. Class w, covered in the next section, Class R contains source hostnames.

6.2 adds only one domain name to class R. It is possible to add a limited number of domains to class R from using the Sendmail configuration by using the RELAY_DOMAIN macro. For example, the following command placed inside the Sendmail configuration would have the same effect as the relay-domains file shown in Listing 6.2:

```
RELAY_DOMAIN`ibis.foobirds.org`
```

However, the relay-domains file is simpler than using the RELAY_DOMAIN macro. The RELAY_DOMAIN command requires modifying the Sendmail configuration and rerunning m4 to build the new sendmail.cf file. By default, Sendmail checks for a file named /etc/mail/relay-domains and adds the names it finds to class R. No modifications to the configuration are required. You would need to place a command in the macro configuration only if you wanted to change the default filename of the relay-domains file. There are two ways to do this:

There are three commands relating to setting relay values for class R, RELAY_DOMAIN, RELAY_DOMAIN_FILE, and confCR_FILE. But you do not need to use any of them. Just create a file named /etc/mail/relay-domains and put the names of the hosts for your server should relay in mail. That is all that Sendmail needs.

The “cr” file is a default feature of the Sendmail configuration. Nothing needs to be done to the Sendmail configuration to add it. On the other hand, the “cw” file, which is discussed next, must be specifically added to the configuration even though its role is as important as that of the “cr” file.

## The local-host-names File

In Chapter 5, both the generic Linux configuration and the Red Hat configuration contain the FEATURE(use_cw_file) command. That feature reads the /etc/mail/local-host-names file and adds the hostnames listed there to the hostnames defined in class w. Listing 5.4 in Chapter 5 shows that, by default, class w contains the special name localhost, 127.0.0.1, and the system's IP addresses, full domain names, and unqualified hostnames. Anything you put in local-host-names is added to these default values. The system checks w to decide or not it should accept inbound mail. The Sendmail server only accepts mail for local delivery that is addressed to the server. Yet many systems might use the Sendmail server as a mailbox to collect and hold their mail. If the mail that the server should collect and hold is literally to another system, the name of that system needs to be added to class w. The other system's hostname is treated by Sendmail as if it were an alias for names. Mail addressed to systems listed in class w is accepted as if it were to the server. An example will make this clear.

Assume that robin.foobirds.org is a PC that uses the wren.foobirds.org as a mailbox to collect and hold. An MX record is placed in the DNS server that directs robin's mail to wren. Listing 6.3 shows what happens when logon on bear.mammals.org sends mail to robin on logon on bear.mammals.
