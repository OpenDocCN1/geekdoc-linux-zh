# Using the smrsch Feature

The smrsch feature was introduced during the discussion of the Red Hat configuration in Chapter 5, "Understanding a Vendor's Configuration." smrsch is the Sendmail Restricted Shell. It replaces /bin/sh as the program used for the prog mail. The mail delivery agent used when Sendmail processes an address that uses the | program syntax. On Linux systems /bin/sh is the Bourne Again Shell (bash), which means that any command that can be processed by bash can be processed by the prog mail. is a flexible configuration but a potentially dangerous one. Anyone who can get a command to the prog mail has the same access to the system as a user logged on to a terminal. smrsch limits the flexibility and reduces the damage.

smrsch is a restricted shell. Some built commands—exec, exit, and echo—work, but most not. smrsch does not allow standard I/O redirection. Of special the special characters used by the shell—carriage return, newline, <, >, &, $, ( and are not allowed; only ll and && are accepted. Most importantly, only those commands that can be run by exec or those that you choose to make available to smrsch through a special execution directory are available to the user.

smrsch forwards only to programs in the /usr/adm/sm.bin directory. The Sendmail administrator creates the directory and populates it with the programs that are trusted to be accessible through the prog mail. smrsch strips the initial pathname of the program to which mail is being forwarded. Thus, if the user enters /usr/local/vacation as the program name, smrsch strips the program name down to vacation and looks for a file of that name in the /usr/adm/sm.bin directory.

/usr/adm/sm.bin is the default execution directory used by smrsch. Compile smrsch with either -PATH or -DCMDBIN to specify a different execution path.

# Sendmail Security Protocols

The first two sections of this chapter cover techniques for securing a Sendmail server. None of the things you do to make your server more secure can ensure the security of mail as it moves through the network. Mail can be corrupted or read at any point as it travels through the network. No one can have a reasonable expectation of privacy with e-mail. It is cleartext data moving through a shared network. Everyone knows their e-mail is an open communication shouted to the world.

Sometimes, however, you want to keep your mail private. This can be done using add-ons, such as Pretty Good Privacy (PGP) or Gnu Privacy Guard (GnuPG), to secure messages. These tools, however, are not integrated into Sendmail. Starting with Sendmail 8.11, some Internet security protocols have been added to Sendmail to authenticate and secure connections. Four basic protocols have been added to Sendmail to support secure mail messages:

- STARTTLS RFC 2487 ("SMTP Service Extension for Secure SMTP over TLS") defines the STARTTLS protocol that standardizes the transmission of encrypted e-mail. STARTTLS depends on transport layer security.

- TLS RFC 2246 ("The TLS Protocol Version 1.0") defines a protocol that provides encrypted communications between two applications, such as two message transfer (MTA) programs. TLS is based on Secure Sockets Layer (SSL). SSL is the security mechanism used for e-commerce on the Web. TLS and SSL have different differences, but the TLS RFC allows for compatibility with SSL. Sendmail takes advantage of this and uses SSL for its transport layer security.

- AUTH RFC 2554 ("SMTP Service Extension for Authentication") defines the AUTH protocol that is used to authenticate the end points in an e-mail exchange. AUTH depends on the Simple Authentication and Security Layer (SASL).

- SASL RFC 2222 ("Simple Authentication and Security Layer (SASL)") defines a generalized method for adding authentication to connection-oriented protocols, such as SMTP.

# Encryption and Cryptography

There are two basic types of cryptography: secret key, which is also called symmetric cryptography, and public key, which is sometimes called asymmetric cryptography. Symmetric cryptography is easy to understand. Operating systems using the same key and the algorithm to encrypt and decrypt data. The problem with symmetric cryptography is that a prior agreement must be reached among all participating systems about the key and the algorithm. The secret key in a secret system is far from being a secret because every system must have a copy of the key. The more systems the secret, the greater the possibility that the secret will be compromised.

Public key cryptography is a much more interesting system. There two keys—a public key that can be available to everyone and a private key that does not to be shared with anyone. When the public key is used to encrypt a message, the message can be decrypted with the private key. Anyone can encrypt a message bound for the target system using the public key, but only the target can decrypt and read the message using its private key. Equally, only messages encrypted with the private key can be decrypted with the public key. This elegant system is without complexity. Two things are required to make it work:

**Authentication** In a secret key cryptography system, the fact that a message is properly encrypted means it must have come from a trusted system that has the secret key. A public key system is different. Because the public key is available to everyone, a method for authenticating the source of an encrypted message is needed. Messages are authenticated by a digital signature. A digital signature is produced by running a cryptographic checksum using the content of the message as data for the checksum and the private key of the source of the message for the encryption.
