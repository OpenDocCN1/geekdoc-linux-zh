The access database can also be used to relax relay restrictions for hosts, domains, and networks. The four items in the relay-domains file shown in Listing 11.2 could grant granted relay privileges with the following access database entries:

+   ibis.fobirds.org RELAY
192.168.30.20 RELAY
mammals.org RELAY
172.30 RELAY

Again, the systems granted access are identified by name or address. But this time the specific action to be is explicitly spelled out by the RELAY keyword. The other keywords and values that can be used in the action of access database entry mean that the database can be used for more than just enabling. As you will see later in this chapter, the access database is also a powerful anti-spam tool. It holds everything in one file—both the entries that enable relaying and the entries that block spam—I prefer to use the access database over the relay-domains file. I like to have controls in one place where they can be evaluated together as a whole. By nature, access controls are most effective if they are coordinated, and a single file makes coordination easier. (The details of the syntax and structure of the access database are covered in Chapter 6.)

The systems relaying through class R or the access database are identified as individual hosts, entities or entire networks. Generally, the hosts, domains, and networks identified in class R or the access database are remote hosts, domains, and networks. If you want to relay for the hosts in your domain, Sendmail provides a simpler way to handle your local domain.

The relay_entire_domain feature grants relaying to every host in the domains listed in class m. Because class m is used for more than just relaying, only local domains should be listed in this class. Adding the following command to the sample server configurations shown throughout would enable relaying for every host in the foobirds.org domain:

```
FEATURE(relay_entire_domain)
```
