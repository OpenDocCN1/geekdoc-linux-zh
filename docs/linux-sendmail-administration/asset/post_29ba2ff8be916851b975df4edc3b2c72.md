We run two tests using Sendmail in -bt mode. In both cases we ask Sendmail to process the header/sender address, and give it the address to process through the local mailer. The first test uses the generic-linux.cf configuration, which does not use the always_add_domain feature. The address goes in craig and comes out craig. In the second test we use the redhat.cf configuration, which uses the always_add_domain feature. In fact, craig is converted to craig@wren.foobirds.org. The effect of always_add_domain is clearly shown.

This is a good feature to use. The address shown, even on local mail, is valid everywhere. This helps avoid confusion among your users, and confused users are something you want to avoid!

- access_db This feature tells the access database to decide what hosts, domains, and networks are acceptable sources of e-mail. An optional argument that defines the database type and path can be used with the access_db feature. The default database type is hash and the default path is /etc/mail/access. The access database is described in Chapter 6. Its use in fighting spam is covered in Chapter 11.

- blacklist_recipients This feature allows the access database to be used to block mail to specific recipients. Normally, the access database is used to control mail from undesirable sources. With this feature, the access database can also be used to control mail bound for certain destinations. The blacklist_recipients feature is covered in detail in Chapter 11.

- accept_unresolvable_domains This tells Sendmail to accept mail from a source if the domain name of the source cannot be resolved by DNS. By default, Sendmail takes the hostname in the MAIL: header and asks DNS to map that name back to an address before it accept incoming mail. This option overrides default behavior.

Allowing mail from unsolvable domains is a security problem, but this feature is necessary for systems that do not have full-time DNS service. Systems are laptops that be disconnected from the network or systems behind a firewall that are not given DNS access. The Red Hat configuration includes this feature because Red Hat must create a configuration with the widest range of systems. If you have full-time DNS service for your network—and you—should remove this feature from your configuration.

Following this match of FEATURE commands are two MAILER commands. The first is the MAILER(smtp) command that we have already described. The second is the MAILER(procmail) command. Looking at this, you might think it has some to do with the local_procmail parameter described earlier. It doesn't—local_procmail means that the mailer named procmail will use the procmail program will be added to your configuration. These two are unrelated. The mailer installed by MAILER(procmail) is used only if you configure entries in the mailertable to use it.

That's—a big configuration that includes important capabilities, such as smr, and not so important capabilities, like MAILER(procmail). As we are in Chapter 4, this configuration works fine and delivers mail for our Red Hat system. It is only a start. As the discussion of the accept_unresolvable_domains feature and the comments inside the redhat.mc file we make clear, we are expected to create our own configuration that suits ours. In the next section we do just that. Starting with the redhat.mc file, we create our own Red Hat configuration.
