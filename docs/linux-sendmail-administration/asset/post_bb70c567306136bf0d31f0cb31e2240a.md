
The first lines are the authorization identity and the authentication identity. They both have the same value—in this case craig. Sendmail expects these to be the same value. If they aren't, Sendmail will not relay mail for the client. (Of course, you can change this behavior by writing your rewrite rules; but the default configuration expects these values to match.) The third line is the secret used to encrypt the client's response to the server. The last line is the hostname of the client, which is the default realm value used by Sendmail.

# Sendmail Security Protocols

The preceding paragraph points out that the Sendmail server checks the values provided by the client to determine if it should relay the client's mail. The examples of relay configuration in Chapter 11 all relied on IP addresses or domain names. The mobility and dynamic address assignment in today's network means, however, that clients do not always have fixed addresses or names that can be resolved back to fixed addresses. The sole reason Sendmail has for authenticating clients with the AUTH extension is to decide or not the mail from that client should be relayed without regard to the domain name or address of the client.

# The Role of Authentication in Relaying

The server in Listing 12.6 offers the client only one type of authentication. If the client cannot perform DIGEST-MD5 authentication, the client can proceed to send the mail without initiating authentication. All servers accept unauthenticated mail—they might not relay it.

If the client is authenticated by a trusted authentication method, the client is allowed to relay mail. To change that behavior, you need to create your own rewrite rules. Custom rewrite rules can be defined in the Local_check_ruleset. TRUST_AUTH_MECH can list the trusted authentication methods. For example, to trust DIGEST-MD5, place the following in the m4 macro configuration:

```
TRUST_AUTH_MECH(`DIGEST-MD5`) )
```

Even a client authenticated by a trusted mechanism is not allowed to relay mail for everyone. To change that behavior, you need to create your own rewrite rules. Custom rewrite rules defined in the Local_check_ruleset or the Local_trust_auth ruleset are used to verify whether the client is authenticated and what authentication method was used to do the job. The Local_trust_auth ruleset is used to modify the fact that Sendmail sends the AUTH keyword on MAIL From: header only if the user identifies is the same as the user that was authenticated by challenge/response. Three variables contain information that can be used in these rulesets:

- **auth_type**: This variable contains the name of the authentication technique that was used to authenticate the client—for example, DIGEST-MD5.
- **auth_user**: This variable contains the name that was authenticated by the original challenge/response exchange of the client and the server.
- **auth_author**: This variable initially contains the value from the authorization identity. If a value is defined by the AUTH keyword on MAIL From: header, that becomes the value for auth_author variable.

# Chapter 12 Sendmail Security

The fact that authentication is used only for relaying reduces the overall security of AUTH protocol. Readers familiar with encryption may have hoped that AUTH was used to provide cryptographic authentication of content of e-mail messages. This is not the case. RFC 2554 states that the AUTH extension can be optionally used to negotiate security layer for subsequent interaction, meaning message encryption is not really used in this way.

# Transport Layer Security

AUTH extension uses a shared secret. The authentication data is encrypted and decrypted with the same key, making AUTH symmetric encryption system. TLS, on the other hand, is a public key encryption system. TLS is the protocol used to encrypt message transfers. Securing e-mail with SSL requires the same information that is used to secure Web communications. To find out more about using SSL for Linux server, see Apache Server Administration. SSL public key cryptography requires three things:

- **A certificate authority**: A trusted party called certificate authority (CA) is the server from which public keys are obtained. You cannot trust the system it claims to be. On the other hand, the CA is a well-known server. Some tools, such as the browser, come preconfigured to recognize any certificate authorities.
- **A certificate**: This is your public key. It is written in the form of X.509 certificate, which contains the identity of your system and dates that verify the key is currently valid. X.509 certificate is signed by a CA. Thus, when you send your certificate to a remote server, the server can decrypt your certificate using the well-known public key of your CA.
- **A private key**: This is the key you use to encrypt your communications, which are then decrypted by the public key. The private key has been encrypted by the public key. The private key must be kept secure, but it cannot be stored in encrypted format.

# Sendmail Security Protocols

These essential pieces of information must be identified to Sendmail in the configuration. The path to the directory where certificates are stored is defined by the confCACERT_PATH parameter, and the certificate for the CA is defined using the confCACERT parameter. Both can be used in the m4 configuration—for example:

```
define(`confCACERT_PATH`, `/etc/httpd/conf/ssl`)
define(`confCACERT`, `/etc/httpd/conf/ssl/crt`)
```

In this example, we use the same certificate directory that was set up for the Apache server on our system. This is, however, completely arbitrary. Certificates can be stored anywhere as long as the directory and the certificates in the directory can be written by root.

In addition to information about CA certificates, Sendmail needs to know the public and private keys it should use to identify and encrypt its own communication. Sendmail uses a different set of public and private keys to define whether it is acting as a server or a client. These values are defined by four m4 parameters:

- **confSERVER_CERT**: This parameter sets a value for the ServerCertFile option. ServerCertFile identifies the file that contains the X.509 certificate used when Sendmail acts as a server. In effect, this is the server's public key. For example:
- **confSERVER_KEY**: This parameter sets a value for the ServerKeyFile option. ServerKeyFile identifies the file that contains the private key used when Sendmail acts as a server. The confSERVER_KEY parameter could be defined as follows:

```
define(`confSERVER_KEY`, `/etc/httpd/conf/ssl/server.key`)
```
- **confCLIENT_CERT**: This parameter sets a value for the ClientCertFile option. ClientCertFile identifies the file that contains the X.509 certificate used when Sendmail acts as a client. In effect, this is the client's public key. The following example points to a certificate in the Apache SSL directory:

```
define(`confCLIENT_CERT`, `/etc/httpd/conf/ssl/client.crt`)
```
- **confCLIENT_KEY**: This parameter sets a value for the ClientKeyFile option. ClientKeyFile identifies the file that contains the private key used when Sendmail acts as a client. The following command tells Sendmail where the client's private key is stored:

```
define(`confCLIENT_KEY`, `/etc/httpd/conf/ssl/client.key`)
```
