
- A printer forwarding queue is required wherever it says “forward” in the above examples. The data is forwarded without filtering.
- Where it says “prefilter” or “filter”, a print queue is required to filter the data. If filtering takes place on the client, this filter queue is a “prefilter” for the “printer forwarding queue” of the print server. If filtering takes place on the print server, the filter queue is one of the regular queues configured on the print server, such as `lp`.

## Prerequisites

The printer must be supported by SuSE Linux, since the prefilter produces printer-specific data in the same manner as for a locally connected printer (normally via Ghostscript). See Section *Connecting Printers Locally* on page 194 for more information on this.

There must be a working TCP/IP connection to the network printer. The name service especially needs to be set up properly.

## Configuration

Use YaST2 to configure the required prefilter and forwarding queues and test all queues defined. The division into prefilter and forwarding queues is the classical configuration of printer spoolers that use lpd protocol (according to RFC 1179).

With print server units or network printers, this may not work (see Section *In Case of Problems* on the following page). The LPRng spooler allows for other methods of accessing network printers or print server units. These methods are already, in part, supported by lprsetup. See `lprsetup --help` and the man page for `lprfilter` (man `lprfilter`). Detailed information for the LPRng spooler is outlined in the *LPRng Howto* in file: `/usr/share/doc/packages/lprng/LPRng-HOWTO.html`. The lpd protocol is also described there. file: `/usr/share/doc/packages/lprng/LPRng-HOWTO.html#NETWORKPRINTER` file: `/usr/share/doc/packages/lprng/LPRng-HOWTO.html#NETWORKPRINTER`.

## In Case of Problems

### Check the configuration of the prefilter

Connect the printer directly to the first parallel port of the PC. Configure the printer as a local printer for testing purposes to eliminate any network problems that may exist. Proceed as described in Section *Connecting Printers Locally* on page 194. If the printer works locally, you now know the correct Ghostscript driver and other parameters for the configuration of the prefilters. Now, configure the printer in the network as described above with the correct settings.

### Verify remote lpd

As user root, request a status report for the queue on the remote host (provided that lpd is running and it can receive direct requests) with:

```sh
earth: ~ # echo -e "\004queue" | netcat -w 2 -p 722 host 515
```

This report may be very long. Lack of response from the lpd may be the result of some fundamental network problems. If you do get a response from the remote lpd, it should indicate why nothing can be printed from the queue on the remote host. Examples:

```
lpd: your host does not have line printer access
lpd: queue does not exist
printer: spooling disabled
printer: printing disabled
```

*Output 13: Error message from lpd*

If you receive this type of response from the lpd, the source of the problem is the remote lpd.

### Network printer or print server unit does not work reliably

Sometimes problems may occur with the printer spooler located on the print server unit or network printer, especially when several clients are sending print jobs to the printer server unit or network printer simultaneously. As the problem is the printer spooler in the printer server unit or in the network printer, the easiest solution is to connect the printer directly to a print server or filter the print data on the client.

## Custom-Generated Print Filters

### Preliminary Remarks

The main intention of this section is not to introduce an alternative to lpfilter, but instead to furnish some background on printing in Linux based on a simple example of a custom-designed print filter. The example outlined here has been kept as simple as possible to emphasize the most essential steps. For this reason, we have left error correction procedures out of the sample filter script below. The following is also based on the assumption that the printer is connected to the first parallel port (/dev/lp0). If the printer is connected to another port, use the other port device in place of /dev/lp0.

A print filter receives the data to print from the spooler over the standard input. The print filter’s task is to convert this data to the printer-specific format before relaying it to the standard output. The printer spooler ensures that everything that the print filter outputs over the standard output reaches the printer device /dev/lp0. The kernel, in turn, forwards everything that arrives at the printer device to the designated port (e. g., to the IO address 0x378). The hardware is responsible for making sure everything sent to the IO address (0x378, in this case) is relayed to the printer over the parallel connection cable. The printer then interprets this data stream and, finally, prints it according to the specifications.

The following commands are usually only executable as user root, since normal users cannot access the printer device directly unless root allows this with the `chmod a+w /dev/lp0` command. Commands are given as shown in the following:

```sh
earth:  # cat ascii-file > /dev/lp0
```

Here, replace ascii-file with the name of an existing ascii file.

### A Simple Example

The command `echo -n "\rHello\r" > /dev/lp0` skips the printer spooler and filters by addressing the printer device `/dev/lp0` itself. This command just sends the ASCII characters `\r`, `H`, `e`, `l`, `l`, `o`, `\r`, and `\f` straight to the printer. The characters `\r` and `\f` stand for carriage return and formfeed. If the printer can print ASCII characters directly, it will print the word Hello and eject the page.

```sh
earth:  # cat ascii-file > /dev/lp0
```

skips the printer spoolers and filters by addressing the printer device `/dev/lp0` itself. The ASCII characters from the ASCII text file are sent straight to the printer.

In Linux, only a linefeed ASCII sign separates two ASCII text lines. In DOS/Windows, two ASCII text lines are separated by a linefeed and a carriage return ASCII symbol.

If an ASCII text file is sent to the printer using the command shown above, the printout will typically appear as follows:

```
First line
             Second line
                         Third line
                                      ...
```

as the printer will only indent the lines without providing a carriage return, since a carriage return ASCII symbol was not sent. The printer can be reconfigured so that it provides a carriage return with each linefeed.

For printers that understand the printer language PCL3, a carriage return is triggered after each linefeed (if a linefeed ASCII sign is given) using the escape sequence `\033&k2G`.

The command `echo -en "\033&k2G" > /dev/lp0` sends the escape sequence to the printer. Then, the ASCII text file is printed with the correct line returns with `cat ascii-file > /dev/lp0`. Afterwards, you may need to enter `echo -en "\f" > /dev/lp0` to eject the last page from the printer.

Special characters, such as umlauts, will usually not be printed correctly, since such special characters are encoded differently in DOS/Windows than in Linux and the printer is usually preset for DOS/Windows.

The commands

```sh
earth:  # cp ascii-file ascii-file.ibmpc
earth:  # recode lat1..ibmpc ascii-file.ibmpc
```

copy the ASCII file to ascii-file.ibmpc before recoding it to DOS/Windows standards.

The command `cat ascii-file.ibmpc > /dev/lp0` should ensure that the line breaks as well as umlauts or tildes are printed correctly. As these characters are already encoded in ascii-file.ibmpc according to DOS/Windows standards, you no longer need any special escape sequences to set up the appropriate line break behavior for the printer.

Therefore, the commands

```sh
earth:  # cp ascii-file ascii-file.ibmpc
earth:  # recode lat1..ibmpc ascii-file.ibmpc
```
