

## 7.3 处理错误和处理命令行选项

我们的下一个客户端 `connect2` 在连接到 MySQL 服务器、断开连接并退出这一点上与 `connect1` 类似。然而，`connect2` 有两个重要区别：

- 它在发生错误时提供更多信息：如果出现问题，`connect1` 仅打印一条简短的消息，但由于 MySQL 客户端库包含返回错误具体原因信息的函数，我们可以更好地进行错误报告。
- 它允许用户将连接参数作为选项指定在命令行或选项文件中。

### 7.3.1 检查错误

让我们先讨论错误处理的话题。首先，我想强调，每当调用可能失败的 MySQL 函数时，检查错误非常重要。似乎许多编程书籍常说“错误检查留给读者作为练习”。我想这是因为检查错误——让我们面对现实——确实很乏味。尽管如此，MySQL 客户端程序测试错误条件并做出适当响应是必要的。客户端库中返回状态值的函数这样做是有原因的，如果你忽视它们，将承担风险。例如，如果函数返回指向数据结构的指针，或返回 NULL 表示错误，你最好检查返回值。如果函数返回的是指向有效数据结构的指针，而你在程序稍后尝试使用 NULL，这将导致奇怪的结果或使你的程序崩溃。

不检查返回值是不必要的编程困难原因，这种现象在 MySQL 邮件列表上经常发生。典型的问题是“为什么我的程序在发出这个语句时会崩溃？”或“为什么我的查询不返回任何内容？”在许多情况下，相关程序在发出语句前没有检查连接是否成功建立，或者在尝试获取结果前没有检查服务器是否成功执行了语句。

不要犯下假设每个客户端库调用都会成功的错误。如果你不检查返回值，最终你会试图追踪程序中发生的晦涩问题，或者你的程序用户会困惑于这些程序为何行为 erratic，或者两者兼有。

MySQL 客户端库中返回值的例程通常通过两种方式之一指示成功或失败，这取决于返回值是指针还是整数。指针值函数在成功时返回非 NULL 指针，在失败时返回 NULL。（在此上下文中，NULL 意味着“C NULL 指针”，而不是“MySQL NULL 列值”。）

在我们迄今为止使用的客户端库例程中，`mysql_init()` 和 `mysql_real_connect()` 都返回指向连接处理器的指针以指示成功，返回 NULL 以指示失败。

整数值函数通常返回 0 表示成功，非零表示失败。重要的是不要测试特定的非零值，例如 -1。没有保证客户端库函数在失败时返回任何特定值。偶尔，你可能会看到代码错误地测试 C API 函数 `mysql_XXX()` 的返回值，如下所示：

```c
if (mysql_XXX () == -1)     /* 此测试是不正确的 */
   fprintf (stderr, "something bad happened\n");
```

此测试可能有效，也可能无效。MySQL API 未指定任何非零错误返回值将是特定值，除了它（显然）不是零之外。你应该像这样编写测试：

```c
if (mysql_XXX () != 0)     /* 此测试是正确的 */
   fprintf (stderr, "something bad happened\n");
```

或者，像这样编写测试，它是等效的，并且编写起来稍微简单一些：

```c
if (mysql_XXX ())          /* 此测试是正确的 */
   fprintf (stderr, "something bad happened\n");
```

如果你查看 MySQL 本身的源代码，你会发现它通常使用第二种形式的测试。

并非每个 API 调用都返回值。我们使用的另一个客户端例程 `mysql_close()` 就是这样做的。（它怎么可能失败？即使失败了，又怎样？反正你已经完成了连接。）

当客户端库调用失败时，API 中有三个调用对于查明原因很有用：

- `mysql_error()` 返回包含错误消息的字符串。
- `mysql_errno()` 返回 MySQL 特定的数字错误代码。
- `mysql_sqlstate()` 返回 SQLSTATE 代码。SQLSTATE 值更具厂商中立性，因为它基于 ANSI SQL 和 ODBC 标准。

每个函数的参数都是指向连接处理器的指针。你应该在错误发生后立即调用它们。如果你发出另一个返回状态的 API 调用，你从 `mysql_error()`、`mysql_errno()` 或 `mysql_sqlstate()` 获得的任何错误信息将适用于后续的调用。

通常，程序用户发现错误消息比任何错误代码都更有启发性，所以如果你只报告一个值，我建议它是消息。本章中的示例报告所有三个值以求完整。然而，在每次可能发生错误的地方编写三个函数调用是一项繁重的工作。相反，让我们编写一个实用函数 `print_error()`，它打印我们提供的错误消息以及 MySQL 客户端库例程提供的错误值。换句话说，我们不会在每次发生错误测试时像这样写出 `mysql_errno()`、`mysql_error()` 和 `mysql_sqlstate()` 函数的调用：

```c
if (...some MySQL function fails...)
   {
      fprintf (stderr, "...some error message...:\nError %u (%s): %s\n",
         mysql_errno (conn), mysql_sqlstate (conn), mysql_error (conn));
   }
```

使用可以像这样调用的实用函数来报告错误更容易：

```c
if (...some MySQL function fails...)
{
   print_error(conn, "...some error message...");
}
```

**print_error()** 打印错误消息并调用 MySQL 错误函数。**print_error()** 调用比 `fprintf()` 调用更简单，因此更容易编写，并使程序更易读。此外，如果 **print_error()** 被编写为即使在 `conn` 为 `NULL` 时也能做合理的事情，我们就可以在诸如 `mysql_init()` 失败等情况下使用它。这样我们就不会混合错误报告调用——一些是 `fprintf()`，一些是 **print_error()**。

我能听到后排有人提出异议：“嗯，你并不真的需要在每次想报告错误时调用每个错误函数。你故意夸大以那种方式报告错误的乏味程度，只是为了让你的实用函数看起来更有用。而且你真的不会把那些错误打印代码写出来好几次；你会写一次，然后当你再次需要它时使用复制和粘贴。”这些是合理的异议，但我这样回应：

- 即使你使用复制和粘贴，使用较短的代码片段这样做也更容易。
- 如果报告错误很容易，你更有可能在应该检查它们时保持一致。
- 无论你是否倾向于每次报告错误时都调用所有错误函数，以冗长的方式写出所有错误报告代码会导致你在报告错误时走捷径并保持一致性的诱惑。将错误报告代码封装在易于调用的实用函数中可以减少这种诱惑并提高编码一致性。
- 如果你确实决定修改错误消息的格式，如果你只需要在一个地方而不是整个程序中做出更改，那将容易得多。或者，如果你决定将错误消息写入日志文件而不是（或除了）写入 `stderr`，如果只需要更改 **print_error()**，那就更容易。这种方法更不易出错，并且再次减少了做事一半并保持一致性的诱惑。
- 如果你在测试程序时使用调试器，在错误报告函数中设置断点是当程序检测到错误条件时让程序中断到调试器的便捷方式。

基于这些原因，本章其余部分需要检查 MySQL 相关错误的程序使用 **print_error()** 来报告问题。
