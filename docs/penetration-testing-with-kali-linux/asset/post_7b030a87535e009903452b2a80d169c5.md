# 17.1.3 Automated Enumeration

As learned in the previous section, Linux systems contain a wealth of information that can be used for further attacks. However, collecting this detailed information manually can be rather time-consuming. Fortunately, we can use various scripts to automate this process.

To get an initial baseline of the target system, we can use unix-privesc-check851 on UNIX derivatives such as Linux. This bash script is pre-installed on our local Kali machine at /usr/bin/unix-privesc-check, and it performs a number of checks to find any system misconfigurations that can be abused for local privilege escalation. We can review the tool's details by running the script without any arguments.

# 17.2.1 Inspecting User Trails

As penetration testers, we are often time-constrained during our engagements. For this reason, we should focus our efforts on low-hanging fruit.

One target is users' history files. These files often hold clear-text user activity that might include sensitive information such as passwords or authentication method.

On Linux, applications frequently store user-specific configuration files and subdirectories within a user's home directory. These files are often called dotfiles because they are prepended with a period. The prepended dot character instructs the system not to display these files when listing command.

One example is bashrc. The .bashrc script is executed when a new terminal is opened from an existing login session or when a new instance is started from an existing login session. From this script, additional environment variables can be specified automatically whenever a new user's shell is spawned.

Sometimes administrators store credentials inside environment variables as a way to interact with custom scripts that require authentication.

Reviewing our target Debian, we'll notice an unusual environment variable entry:

```
joe@debian-presc~$ env
XDG_SESSION_CLASS=user
TERM=xterm-256color
SCRIPT_CREDENTIALS=lab
USER=joe
LC_TERMINAL_VERSION=3.4.16
```

From the above list, the SCRIPT_CREDENTIALS variable holds value that resembles a password. When we are dealing with a particular variable, we need to inspect the .bashrc configuration file.

> Storing a clear-text password inside an environment variable is not considered a secure best practice. To safely authenticate with an interactive script, it's recommended to adopt public key authentication and protect private keys with passphrases.

```
@debian-privesc~$ cat .bashrc
# ~/.bashrc: executed by bash(1) for non-login shells.
# for /usr/share/doc/bash/examples/startup-files (in the package bash-doc)
# for examples

# If not running interactively, don't do anything
case $ - in
 i)
  *) return;
esac
```

```
# don't duplicate lines or lines starting with space in the history.
# See bash(1) for more options
export SCRIPT_CREDENTIALS="lab"
HISTCONTROL-ignoreboth
...
```
