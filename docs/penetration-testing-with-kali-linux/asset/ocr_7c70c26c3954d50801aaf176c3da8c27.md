# OffSec

This kind of attack has been documented since the late 1980s, the development of various mitigations like ASLR and Executable Space Protection,684 among others. Since exploit mitigations are not in scope for this Module, we assume our target has none enabled.

The general flow of a stack-based buffer overflow is fairly straightforward. The exploit will:

+   1. Create a large buffer to trigger the overflow.

+   2. Take control of EIP by overwriting a return address on the stack, packing the large buffer with an appropriate offset.

+   3. Include a chosen payload in the buffer preceded by an optional NOP685 sled.

+   4. Choose a correct return address instruction such as J ESP (or a different register) to redirect the execution flow to the payload.

As we fix the exploit, depending on the nature of the vulnerability, we might need to modify elements of the deployed buffer to suit our target such as file paths, IP addresses and ports, URLs, and more. If these modifications are offset, we must adjust the buffer length to ensure we overwrite the return address with the desired bytes.

While we could trust that the return address used in the exploit is correct, the more reliable alternative is to find the return address ourselves, especially if the one used is not part of the vulnerable application or its libraries. One of most reliable ways to do this is to clone the target locally in a virtual machine and use a debugger on the vulnerable software to obtain the memory address of the return address instruction.

We must also consider the payload contained in the original exploit code.

As mentioned in a previous Module, public exploits present an inherent danger because they often contain hex-encoded payloads that must be reverse-engineered to determine how they function. Because of this, we must review the payloads used in public exploits or better insert our own.

When we create a payload, we will include our own IP address and port numbers and may exclude bad characters, which we can determine independently or from the exploit comments.

Bad characters are ASCII or Unicode characters that break the application when included in the payload because they might be interpreted as control characters.686 For example, the null-byte "\x00" is often interpreted as a string terminator and, if inserted in the payload, could prematurely truncate the buffer.

While generating our own payload is advised whenever possible, there are exploits using custom payloads that are key to successfully compromising the vulnerable application. If this is the case, our only option is to reverse the payload to determine how it functions and if it is safe to execute. This is difficult and beyond the scope of this Module, so we will instead focus on shellcode.
