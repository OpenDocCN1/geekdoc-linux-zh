Listing 496 - Inspecting passwd's process credentials

Interestingly, passwd is running as the root user: this is needed for it to access and modify
/etc/shadow.

We can also inspect the real UID and effective UID assigned to the process by inspecting the
proc pseudo-filesystem, which allows us to interact with kernel information. Using the passwd
PID (1932) from the previous output, let's inspect the at /proc/1932/status, which
provides a summary of the process attributes:

```
joe-debian-privesc:-$ grep /proc/1932/status
Uid:     1000     0     0
```

Listing 497 - Inspecting passwd's process credentials

Filtering by the "Uid" keyword returns four parameters that correspond to the real, effective, saved
set, and filesystem UIDs. In this case, the Real UID value is 1000, which is expected as it belongs
to joe. However, the other three values, including the effective UID, the root's ID 0: consider why.

Under normal circumstances, all four values belong to the same user who launched the
Executable. For instance, the bash process for joe (PID 1131 in this case) has the\values:

```
joe-debian-privesc:-$ cat /proc/1131/status | grep Uid
Uid:     1000     1000     1000
```

Listing 498 - Inspecting passwd's process credentials

The passwd behaves differently because the binary program has a special named Set-
User-ID, or SUID in root. Let's inspect it.

```
joe-debian-privesc:-$ ls -al /usr/bin/passwd
64 -rwxr-xr-x 1 root root 6736 Jul 27 2018 /usr/bin/passwd
```

The SUID flag is depicted with the s flag in the output. This flag can be configured with the
chmod u+s command sets the effective UID of the running process to the executable
owner's ID - in this case root's.

Using this technique results in a legitimate and constrained privilege escalation because of
this (as we'll learn shortly), the SUID binary must be bug-free to avoid any misuse of the
application.
