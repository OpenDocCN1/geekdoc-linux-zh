# LDAP is not exclusive to AD. Other directory services use it well.

LDAP communication with AD is not always straight-forward, but we'll leverage Active Directory Services Interface (ADS)¹10¹⁸ (a set of interfaces built on COM¹10¹⁹) as an LDAP provider.
According to Microsoft's documentation.¹10²⁰ we need a simple LDAP ADSpath in order to communicate with the AD. The LDAP path prototype looks like this:

```
LDAP://[HostName[:PortNumber]][DistinguishedName]
```

We need three parameters for a full LDAP path: HostName, PortNumber, and a DistinguishedName. Let's take a moment to break this down.
Host is a computer name, IP address or domain name. In our case, we use the corp.com domain, so we could simply add that to our LDAP path and likely obtain information. That domain may have multiple DCs, so setting the domain name could potentially resolve the IP of any DC in the domain.

In fact, to make our enumeration as accurate as possible, we should look for the DC that holds the most updated information. This is known as the Primary Domain Controller (PDC)¹10²¹ There can be only one PDC in a domain. To find the PDC, we need to find the DC holding the PDCRoleowner. We'll eventually use PowerShell and .NET class to find this.
The PortNumber for the LDAP connection is optional as per Microsoft's documentation. In our case we will not add the port number since it will automatically choose the port based on which domain we are using or an SSL connection. However, it is worth noting that if we come across a domain in the future using non-default ports, we will need to manually add this to the script.
Lastly, a DistinguishedName is a part of the LDAP path. A DN is a name that uniquely identifies an object in AD, including the domain name. If we're not familiar with LDAP, this might be confusing so let's go into a bit more detail.
