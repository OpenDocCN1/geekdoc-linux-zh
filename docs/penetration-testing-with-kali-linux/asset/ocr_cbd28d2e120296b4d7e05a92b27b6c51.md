Penetration Testing with Kali Linux

We can serve TXT records from Dnsmasq. First, we'll kill our previous dnsmasq process with a Ctrl+C. Then we'll check the contents of dnsmasq_txt.conf and run dnsmasq again with this new configuration.

```
kali@felelineauthority:~$ dns_tunnelling cat dnsmasq_txt.conf
# Do not read /etc/resol.conf or /etc/hosts
no-resol
no-hosts

# Define the zone
auth-zone=feleline.corp
auth-server=feleline.corp
# TXT record
txt-record=www.feleline.corp,here's something useful!
txt-record=www.feleline.corp,here's something else less useful.
kali@felelineauthority:~$ dns_tunnelling sudo dnsmasq -C dnsmasq_txt.conf -d
dnsmasq: started, version 2.88 release 150
dnsmasq: compile options: ipv6 GNU-getobus no-Ubis i18N ID2 DHCP DHCPv6 no-
UA Tftp connect ipnetset captcha DNSSEC-loop identify dumpfile
dnsmasq: warning: no upstream servers configured
dnsmasq: cleared cache
```

> Listing 606 - The TXT configuration file starting dnsmasq with it.

The dnsmasq_txt.conf contains two lines starting with 'txt-record='. Each of these lines represents a TXT record that dnsmasq will serve. Each contains the domain the TXT record is for, then an attribute string⁹ separated by comma. From these two definitions, any TXT record requests for www.feleline.corp should return the strings 'here's something useful!' and 'here's something else less useful.'

Let's test this hypothesis. On PGDATABASE1, we'll make a request for TXT records for www.feleline.corp with nslookup by passing the -type argument.

```
database_adein@pgdatabase1::-$ nslookup -type=txt www.feleline.corp
Server: 192.168.50.64
Address: 192.168.50.64

Non-authoritative answer:
www.feleline.corp text = "here's something useful!"
www.feleline.corp text = "here's something else less useful."
```

Authoritative answers can be found from:

```
database_adein@pgdatabase1::-$
```

> Listing 607 - The TXT response from www.feleline.corp.

Success! We received the attribute strings that we wanted to get into an internal network using DNS records. If we wanted to infiltrate binary data, we could serve it as a series of Base64 or ASCII encoded TXT records, and convert that back into binary on the internal server.

⁹⁸ (IETF RFC, 2022), datatracker.org/doc/html/rfc1464
