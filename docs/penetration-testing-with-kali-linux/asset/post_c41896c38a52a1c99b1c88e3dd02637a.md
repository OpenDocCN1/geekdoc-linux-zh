### 21.3.2 Getting an Overview - Permissions and Logged on Users

Now that we have a clear list of computers, users, and groups in the domain, we will continue our enumeration and focus on the relationships between as many objects as possible. These relationships play a key role during an attack and our goal is to build a map to find potential attack vectors. For example when a user logs in to the domain, their credentials are cached in memory on the computer. If we are able to steal those credentials, we may be able to use them to authenticate as another user or even escalate our privileges.

However, during assessment we may not always want to escalate our privileges right away. Instead, it's important to establish a good foothold, and our goal at the very least should be to maintain our access. If we are able to compromise other users that have the same permissions as the user we access to, we will still have access to the domain via other users if for example the password is reset for our originally obtained account or the system administrators notice suspicious activity and disable the account.

When the time comes to escalate our privileges, we do not necessarily immediately escalate to Domain Admins because there may be other accounts that have more permissions than a regular domain user, such as local administrator privileges on specific servers. Service Accounts, which we will discuss later, are a good example. Organization's most sensitive and important data may be stored in locations that do not require domain privileges, such as a database or a file server. This means obtaining domain administrator privileges should not always the end goal to reach the "crown jewels". When an attacker or penetration tester improves through multiple higher-level accounts to reach a goal it is known as chained compromise. In order to find attack paths, we'll need to learn more about our initial user and see what we have access to the domain. We also need to find out where other users are logged in. Let's dig into that now.

PowerView's FindLocalAdminAccess command scans the network in an attempt to determine if our current user has administrative permissions on any computers in the domain. The command relies on the OpenServiceW function which will connect to the Service Control Manager (SCM) on target machines. The SCM essentially maintains a database of installed services and drivers on Windows computers. PowerView will attempt to open this database with the SC_MANAGER_ALL_ACCESS right, which requires administrative privileges, and if the connection is successful, PowerView will deem that our current user has administrative privileges on the target machine.

Let's run Find-LocalAdminAccess as. While the command supports such ComputerName and Credentials, we will run it without parameters in this case since we are interested in enumerating all computers and we already logged as. In other words, we are spraying the environment to find possible local administrative access on computers under the current user context. Depending on the size of the environment, it may take a few minutes for FindLocalAdminAccess to finish.

```
PS C:\Tools> Find-LocalAdminAccess
client74.corp.com
```

Listing 755 - Scanning to find local administrative privileges for that user

This reveals that stepanie has administrative privileges on CLIENT74. While it may be tempting to log in to CLIENT74 and check permissions right away, this is a good opportunity to zoom out and generalize.

Penetration testing can lead us in many directions and we should ideally follow up on the many different paths based on our interactions, we should stick to our schedule/plan most of the time to keep a disciplined approach.

Let's continue by trying to visualize how computers and users are connected. The first step in this process will be to obtain information as which user is logged in which computer.

Historically, the two most reliable Windows APIs that could (and still may) help us achieve these goals are NetWkUserEnum and NetSessionEnum. The former requires administrative privileges, while the latter does not. Windows has changes over the last couple of years, making the discovery of logged enumeration more difficult for us.

PowerView's Get-Session command uses the NetWkUserEnum and NetSessionEnum APIs under the hood. Let's try running it one of the machines in the domain and if we can find any logged users:

```
PS C:\Tools> Get-Session -ComputerName files08
```
