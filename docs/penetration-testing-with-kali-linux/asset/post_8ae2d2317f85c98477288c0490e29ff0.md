# 23.1.3 Pass the Hash

The Pass Hash (PtH) technique allows an attacker to authenticate to a remote system or service using a user's NTLM hash of the associated plaintext password. Note that this will not work for Kerberos authentication but for servers or services using NTLM authentication. This lateral movement sub-technique is also mapped in the MITRE Framework under the Use Alternate Authentication Material generic:

Many third-party tools and frameworks use PtH to authenticate and code execution, using *PsExec* from Metasploit,¹1143 *Passing-the-hash toolkit*¹1144 and *Impacket*¹1145 The mechanisms behind them are more or less the same as that attacker connects to the victim using the *Server Message Block (SMB)* protocol and performs authentication using the NTLM hash.¹1146

Most tools that are built to abuse PtH can be leveraged to start a Windows service (for example, cmd.exe or an instance of PowerShell) and communicate with it using *Named Pipes*¹1147 This is done using the Service Control Manager¹1148.API.

> We want to gain remote execution code to create a Windows service for any other use, such as accessing an SMB share.

Similar to PsExec, this technique requires an SMB connection through the firewall (commonly port 445) and the Windows File and Printer Sharing feature to be enabled. These requirements are common in international enterprise environments.

This lateral movement also requires the admin share called ADMIN to be available. In order to establish a connection to this, the attacker must present valid credentials with local administrative permissions. In other cases, this type of lateral movement typically requires administrative rights.

Note that PTH uses the NTLM hash legitimately. The vulnerability lies in the fact that we gained unauthorized access to the password hash of a local administrator.

To demonstrate this, we use wmiexec from the Impacket suite from our local Kali machine against going to invoke the command by passing the local administrator account on the hash we gathered in a previous Module and then defining the username with the target IP.

```
kali@kali:~ /usr/bin/impacket-wmiexec -hashes :2892D26CF84D7A0E2EB3B9F05C42E5
Administrator@192.168.50.73
Impacket v0.10.0 - Copyright 2022 SecureAuth Corporation
```

# 23.1.4 Overpass the Hash

With the overpass¹11⁵⁰ we can "over" abuse the NTLM user hash to gain a full Kerberos Granting Ticket (TGT). We then use the TGT to obtain a Ticket Granting Service (SGS).

To demonstrate this, let's assume we have compromised a workstation (or server) that jen has authenticated to. We'll also assume that the machine is now caching their credentials (and therefore, their NTLM hash). To simulate this cached credential, we will log in to the Windows machine as jen and run a process, which prompts authentication.

The simplest way to do this is to right-click the Notepad icon on the desktop then click "show options", yielding the options in Figure 285. (img/33d6ea891e7464f18ad64261ced4_786.png)

Figure 285: Enabling options

From here, we enter jen as the username with the associated password, which will launch Notepad in the context of that user. After authentication, jen's credentials will be cached on this machine. We can validate this with secrets::logonpasswords from mimikatz after spawning an Administrative shell. The command will dump the cached hashes.

```
mimikatz # privilege::debug
mimikatz # secrets::logonpasswords
```

```

_ kerberos - data copy @ 00001F3D5D366C8
_ des_cbc_md4 --> null
_ des_cbc_md4 OK
_ des_cbc_md4 OK
_ des_cbc_md4 OK
_ des_cbc_md4 OK
_ des_cbc_md4 OK
_ +Password replace @ 00001F3D5C6B68
```

This output shows jen's cached credentials under jen's session. It includes the NTLM hash, which we will leverage to overlap the hash. The essence of the overpass hash lateral movement technique is to turn the NTLM hash into a Kerberos ticket and avoid the use of NTLM authentication. A simple way to do this is with secrets:pth command from Mimikatz. The command requires a few arguments and creates a new PowerShell process in the context of jen. this new PowerShell prompt will allow us to obtain Kerberos tickets without performing NTLM authentication over the network, making this attack different than a traditional pass-the-hash. As the first argument, we specify /user/ /domain:, setting them to jen and corp.com respectively. We use the NTLM hash with /ntlm; finally, use /run: to specify the process to create (in this case, PowerShell).

```
mimikatz secrets:pth /user:jen /domain:corp.com/ntlm:369ef79d8372408bf6e936cc93075/run:powershell
user : jen
domain : corp.com
program : powershell
impers : no
NTLM :
| PID 87116
| TID 8348
| LSA Process is now R/W
| LUID 0 : 16534348 (00000000:08fc4b4c)
```

Listing 842 - Creating a process with users NTLM hash

At this point, we have a new PowerShell session that allows us to execute commands as jen. At this point, running the whoami command on the newly created session would show identity instead of jen. While this could be confusing, it is the intended behavior of the whoami utility which only checks the current process's token and it does not inspect any imported kerberos. Let's list the cached Kerberos tickets with klist

```
PS:\Windows\system32> klist
```
