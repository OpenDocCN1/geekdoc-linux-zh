# 8.4 Cross-Site Scripting

This Learning Unit covers the following Learning Objectives:

- Understand Cross-Site Scripting vulnerability types
- Exploit basic Cross-Site Scripting
- Perform Privilege Escalation via Cross-Site Scripting

One of the most important features of a well-defended web application is data sanitization, 358, a process in which user input is processed so that all dangerous characters or strings are removed or transformed. Unsanitized data allows an attacker to inject, and potentially execute, malicious code.

Cross-Site Scripting (XSS) 359 is a vulnerability that exploits a user's trust in a website by dynamically injecting content into the page rendered by the user's browser.

Once thought to be a relatively low-risk vulnerability, XSS today is both high-risk and prevalent, allowing attackers to inject client-side scripts, such as JavaScript, into web pages visited by other users.

# 8.4.1 Stored vs Reflected XSS Theory

XSS vulnerabilities can be grouped into two major classes: stored 360 and reflected 361

Stored XSS attacks, also known as Persistent XSS, occur when the exploit payload is stored in a database or otherwise cached by a server. The web application retrieves this payload and displays it to anyone who visits a vulnerable page. A Single XSS vulnerability can therefore attack all site users. Stored XSS vulnerabilities often exist in forum software, especially in comment sections, in product reviews, or wherever user content can be stored and reviewed later.

Reflected XSS attacks include the payload in a crafted request or link. The web application takes this value and places it in the page content. Reflected XSS only affects the person submitting the request or visiting the link. Reflected XSS vulnerabilities can occur in search fields and results, as well as wherever user input is included in error messages.

Either of these vulnerability variants can manifest as client- (browser) or server-side.

DOM-based XSS occurs when the browser parses the content; the key is that DOM-based 362 takes place solely within the Document Model (DOM) 363 While we won't cover too much detail for now, we know that DOM-based can be significant, with impacts session hijacking, forced redirection to malicious pages, or even trojanized web applications as user. No matter how the XSS payload is delivered, the injected scripts run under the context of the user visiting the affected page. This means the user's browser, not the web application, executes the XSS payload.

# 8.4.2 JavaScript Refresher

JavaScript is a high-level programming language that became one of the main components of modern web applications. All modern browsers include a JavaScript engine that runs JavaScript code from within the browser.

When a browser processes a server's HTTP response containing HTML, the browser creates a DOM tree and renders it. The DOM is composed of forms, inputs, images, etc. related to the page.

JavaScript's role is to access and modify the DOM, resulting in a more user experience. From an attacker's perspective, this also means that if we inject JavaScript code into the application, we can access and modify the DOM. With the DOM, we can redirect login forms, extract passwords, and steal cookies.

Like many other programming languages, JavaScript can combine a set of instructions into a function. 364
