## 3.4.7 Continuous Patching and Supply Chain Validation

Another defensive technique known as continuous automated patching is pulling the upstream source code and applying it to the lowest development environment. Next, the change is tested, and only moved to production if it is successful. We can leverage cloud provider infrastructure to easily spin up complete replicas of environments for testing these changes. Rather than continuously running a full test environment, we can create one with relative ease using our cloud provider, run the tests, then delete it. The primary risk of this approach is supply chain compromise.

Continuous supply chain validation occurs when people and systems validate that the software and hardware received from vendors is the expected material and that it't been tampered with, as well as ensuring output software and materials are verifiable by customers and partners. Continuous supply chain validation is difficult, and sometimes requires more than software checks, such as physical inspections of equipment ordered. On the software side of supply chain security, we can use deeper testing and inspection techniques to evaluate data more closely. We might opt to increase the security testing duration to attempt to detect sleeper malware in upstream sources. Sleeper malware is software that is inactive within a system or for a period of time, potentially weeks, before it starts action.

Utilizing a bill of materials (SBOM)⁸¹ as a way to track dependencies in the application build process greatly helps evaluate supply chain tampering. If we identify the software dependencies, create an SBOM with them, and package the container and SBOM together in a cryptographically-verifiable way, then we can verify the container's SBOM signature before loading it into production. This kind of process presents additional challenges for adversaries.

## 3.4.8 Encryption

Beyond tracking software, many organizations likely want to learn encryption. Encryption often protects us from any other type of control. While using encryption doesn't solve all problems, well-integrated encryption at multiple layers of controls creates a stronger security posture.

Keeping this in mind, there are some caveats when it comes to encryption. Encrypting all our data will be useful if we can't decrypt and restore it when required. We must also consider some types of data that we don't want to decrypt as the information is to be used only ephemerally. One example of ephemeral encryption is TLS,⁸² in which nobody the server and the client of that interaction can decrypt the information (not even the administrators), and the decryption keys only exist in memory for a brief time before discarded.

Decryption keys in such a scenario are never on disk and sent across the network. [Note: original text seems to say "Decryption keys in such a scenario are never on disk and sent across the network."] This type of privacy is commonly used when sending secrets or Personal Identifiable Information (PII) across the wire. Any required tracing and auditing data can be fetched from the applications after intercepted, the secrets and PII can be excluded, encrypted, or scrubbed. PII can include names, addresses, phone numbers, email addresses, SSNs, and other information that can be used to track down or spy on an individual person.

Along with ensuring we can encrypt data, we should ensure that only the minimum required persons or systems can decrypt data. We also want backups that are encrypted with different keys. In general, we don't want to re-use encryption keys for different users, as each key should only have one purpose. A file encryption key might encrypt millions of files, but that key should be used for that purpose, and not for example, signing to TLS.

Although encryption and backups are great practices, we also should implement protocols for routinely restoring from backups to that we know, and that the process works for every component. In some cases, we don't need to back up detailed log; however, most standards require auditing logs. Some specifications may require that systems are in place to query and delete specific history log records.

## 3.4 Logging and Chaos Testing

Being able to access granular data quickly is of great benefit to an organization. Well-engineered logging is one of the most important security aspects of application design. With consistent, easy to process, and sufficiently-detailed logging, an operations team can more quickly respond to problems, meaning incidents can be detected and resolved fast. With well-engineered security and application logging, it's also possible to access quickly.

The last control we'll explore is Chaos Testing.⁸³ Chaos testing is a type of BEC or disaster recovery (DR)⁸⁴ that is often handled via automation. For example, we might leverage a virtual machine that has administrative credentials in the production network to cause intentional dissions from within. Chaos engineering includes a variety of different approaches, as having red teams create chaos in the organization to test how well the organization is able to handle, scheduling programmed chaos having malicious platform API commands sent in. The goal is to test our controls during messy and unpredictable situations. If a system and organization can handle chaos with relative grace, then it is an indication that it will be robust and resilient to security threats.

## 3.5.1 Laws and Regulations

Much be written about cybersecurity laws and regulations, especially since countries and jurisdictions have all their own. Most of the items we'll discuss here are centered on the United States; however, some are applicable globally well. As a security professional, it is always important to understand exactly laws and regulations one may be subject to.

HIPAA The Health Insurance Portability and Accountability Act of 1996 (HIPAA)⁸ is a United States federal law regulating health care and the privacy of patient health information. Included in this law was a requirement to create a set of standards for protecting patient health information, known as Protected Health Information (PHI). The standards that regulate how PHI can be used and disclosed are established by the Privacy Rule⁶ This rule sets limits on how information can be shared without a patient's consent and grants patients a number of rights over their information, such as the right to obtain a copy.

Another rule known as the Security Rule⁷ outlines how electronic PHI (e-PHI) must be protected. It describes three classes of safeguards that must be in place:
- administrative (having a designated security officer, a security management process, periodic assessments, etc.)
- physical (facility access, device security)
- technical (access control, transmission security, audits, etc.)

These rules also include provisions for enforcement and penalties. Importantly, HIPAA also requires that covered entities (healthcare providers, health plans, business associates, etc.) provide notification⁸ that a breach occurs.

FERPA also grants parents and learners over the age of 18 a number of rights over their information. These rights include the right to inspect records, the right to request modification to inaccurate or misleading records, and more. Schools that fail to comply with these laws risk access to federal funding.
