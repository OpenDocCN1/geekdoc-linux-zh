## 16.2.3 Unquoted Service Paths

Another interesting attack vector that can lead to privilege escalation on Windows systems revolves around unquoted service paths. We can use this when we have permissions to a service directory or cannot replace subdirectories within them. As we learned in the previous sections, how service paths to an executable file will run when the service is started. If the path of this file contains one or more spaces and is not enclosed within quotes, it may be turned into an opportunity for privilege escalation. When a service is started and a process is created, the Windows CreateProcess function is used to specify the first parameter of the process, lpApplicationName is used to specify the filename, [Andrew Freeman](https://www.tenable.com/report-templates/unquoted-service-vulnerability), and the rest are arguments (Microsoft Documentation, 2022), not enclosed in quotation marks, it can be interpreted in various ways because it is unclear where the file name ends and arguments begin. To determine this, the function starts interpreting the path from left right until a space is reached. For every space in the file path, the function uses the preceding path as filename and the rest are arguments. Let's show this in an example with the unquoted binary path C:\Program Files\MyService\exe. When Windows starts, it will use the following order to start the executable file due to the spaces in the path:

```text
C:\Program.exe
C:\Program Files\My.exe
C:\Program Files\My Program.exe
C:\Program Files\MyService\exe
```

Listing 437 - Example of how Windows tries to interpret the service path to locate the executable file

To exploit this, we must create a malicious executable, place it in a directory that corresponds to one of the interpreted paths, and match it to the filename. Then, once the service starts, we get executed with the same privileges that the service starts with. Often this happens to be the LocalSystem account, which results in a successful privilege escalation. In the context of the example, we could name our executable Program.exe and place it in C:\My.exe or My.exe and place it in C:\Program Files\. However, the first two options would require admin permissions since standard users don't have the permissions to write to these directories by default. The third option is more likely as it is the software's main. If an administrative user or developer sets the permissions for this directory too, we can place our malicious binary there.

Now we have a basic understanding of this vulnerability, let's use it in an example. We connect to CLIENTWK220 as steve with RDP. We open PowerShell and enumerate running and stopped services.

```powershell
PS C:\Users\steve Get-CimInstance -ClassName win32_service | Select Name,State,PathName
```

Listing 438 - List of services with binary path

Listing 438 shows a stopped service named GammaService. The unquoted binary path contains multiple spaces and is potentially vulnerable to this attack.

A effective way to identify spaces in the paths using quotes is the WMI command-line (WMIC) utility. We can enter service to obtain service information and use get name and pathname as arguments to retrieve these specific properties. We'll pipe the output of this command to findstr /i for case-insensitive searching and /v to print lines that don't match. As argument for this command, we'll "C:\Windows" to show only spaces with a binary path outside of the Windows directory. We will pipe the output of this command to another findstr command, which uses "" as print matches without quotes. Let's consider this in cmd.exe instead of PowerShell to avoid escaping issues for the quote in the second findstr command. Alternatively, we use Select-String in PowerShell.

```powershell
C:\Users\steve> wmic service get name,pathname | findstr /i /v "C:\Windows\" | findstr /i /v ""
```
