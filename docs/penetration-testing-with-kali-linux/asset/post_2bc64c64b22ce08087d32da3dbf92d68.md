## 16.1.4 Goldmine PowerShell

In the previous section, we discussed how we can use sensitive information found in plain-text files to elevate our privileges. Over the last decade, IT security awareness for the average enterprise user has tremendously improved through training, IT policies and the prevalent threat of cyber attacks backed by media. Fortunately, this has led to less sensitive information being stored in nodes or text files.

Because of the growing threat of cyber attacks, more defensive measures were developed and implemented for clients and servers. One of these measures is to collect and record more data on systems using executed commands and operations, which allows the IT staff to review and respond accordingly to threats. One important source of this information is PowerShell, since it is a vital resource for attackers.

With default settings, Windows only logs a small amount of information on PowerShell usage, which is not sufficient for enterprise environments. Therefore, we'll find PowerShell logging mechanisms enabled on Windows clients and servers. Two important logging mechanisms for PowerShell are PowerShell Transcription⁷⁷ and Script Block Logging⁶⁸.

Transcription is often referred to as "over-the-shoulder-transcription", because, when enabled, the logged information is equal to what a person would obtain from over the shoulder of a user entering commands in PowerShell. The information is stored in transcript files, which are often saved in the home directories of users, a central directory for all systems of a machine, or a network share collecting the files from all configured commands.

Script Block Logging records commands and blocks of script code as events while executing. This results in a much broader logging of information because it records the full content of commands as they are executed. This means each event also contains the original representation of encoded code or commands.

Both mechanisms are quite powerful and have become increasingly common in enterprise environments. However, while they are great from the defensive perspective, they often contain valuable information for attackers.

In this example, we'll demonstrate how we can retrieve information recorded by PowerShell with the help of enabled logging mechanisms and the PowerShell history. We will again connect on port 4444 to bind the shell running as the user dave and launch PowerShell.

For the purpose of this demonstration, we'll assume the files containing sensitive information from the previous section do not exist.

Before we check if Script Block Logging in PowerShell is enabled, we should always check the PowerShell history of a user. We use the Get-History cmdlet to obtain a list of commands executed in the past.

```
PS C:\Users\dave> Get-History
Get-History
```
Listing 397 - Empty result from commands were issued so far.

The output indicates that no PowerShell history was issued. At this point, we can explore how PowerShell's history works. Most Administrators use the Clear-History cmdlet to clear the PowerShell history. But this cmdlet is only clearing PowerShell's own history, which can be retrieved with Get-History. Starting with PowerShell v5, v5.1, and v7, a module named PSReadline is included, which is used for line-editing and command functionality.

Interestingly, Clear-History does not clear the command history recorded by PSReadline. Therefore, we can check if the user is in our misunderstanding the Clear-History cmdlet clears all traces of commands.

To retrieve history from PSReadline, we can use Get-PSReadlineOption to obtain information from the PSReadline module. We put it in parentheses and use HistorySavePath prepended with a syntax that allows us to check one option from all options of the module.

```
PS C:\Users\dave> Get-PSReadlineOption.HistorySavePath
(Get-PSReadlineOption).HistorySavePath
:\Users\AppData\Roaming\Microsoft\PowerShell\PSReadline\ConsoleHost.txt
```

The output contains various highly interesting commands for us.

First, dave executed Register-SecretVault with the module SecretManagement.keeps, which implies that the user created a new password database for KeePass. In the next line, dave used Set-Secret to create a secret, or entry, in the password manager with the name Server02 Admin PW and password paperMonitor33#. As the name suggests, these are probably credentials for another system. However, we would attempt to leverage this password for any user, or login on CLIENTWK220 as it be reused by the user. We'll note the password for later and continue analyzing the history.

Next, the output shows that dave used Clear-History revealing that the history is cleared after executing the Cmdlet.

Finally, dave used Start-Transcript to start a PowerShell Transcription. This command creates the path where the transcript file is stored. Before we examine it, let's analyze the next line.

The user executed Enter-PSSession772 with the hostname of the local machine as argument -ComputerName and a PSredential773 object $cred containing the username and password for -Credential. The commands to create the PSredential object are not included in the history file and therefore we do not know which user and password were used for Enter-PSSession.

> PowerShell Remoting774 by default uses WinRM for Cmdlets as Enter-PSSession. Therefore, a user needs to be in the local group Management Users to be a valid user for these Cmdlets. However, WinRM,SSH775 can also be used for PowerShell remoting776.
