## 22.2.3 Kerberoasting

Let's recall the Kerberos protocol. When a user wants to access a resource hosted by the client, the client requests a service ticket generated by the domain controller. The service ticket is then decrypted and validated by the application server, since it is encrypted by the password hash of the SPN.

When requesting a service ticket from the domain controller, no checks are performed to confirm whether the user has permissions to access the service hosted by the SPN.

These checks are performed as a second step only when connecting to the service itself. This means if we know the SPN we want to target, we can request a service ticket for it from the domain controller.

The service ticket is encrypted using the SPN's password hash. If we are able to recover the ticket and decrypt it using brute force or guessing, we can use this information to crack the cleartext password of the account. This technique is known as Kerberoasting.[1112]

In this section, we will abuse a service ticket and attempt to crack the password of the service account. Let's begin by connecting to CLIENT75 via RDP as jeff with the password HenchmanPutridoBonBon.[11]

To perform Kerberoasting, we will use Rubeus. We specify the kerberos command to launch this attack technique. In addition, we'll provide hashes.kerberoast as an argument /outfile to store the resulting TGS-REP hash in. If we execute Rubeus as an authenticated domain user, the tool will identify all SPNs with a domain user.

This technique is immensely powerful if the domain contains high-privilege service accounts with weak passwords, which is not uncommon in many organizations. However, if the SPN runs in the context of a computer account, a managed service account,[1117] password will be randomly generated, complex, and 120 characters long, making cracking infeasible. The same is true for the krbtgt user account which acts as service account for the KDC. Therefore, our chance of performing a successful Kerberos attack against SPNs running under user accounts is much higher.

Let's assume we are performing an assessment and notice that we have GenericWrite on another AD account. As stated before, we could reset the user's password; this might raise suspicion. However, we could also set an SPN for the user,[1119] kerberos account, and crack the password hash in another targeted Kerberoasting. We'll note that in an assessment, we should delete the SPN once we have obtained the hash to avoid any potential vulnerabilities to the client's infrastructure.

## 22.2.4 Silver Tickets

In the previous section, we obtained and cracked a TGS-REP hash to retrieve the plaintext password of an SPN. Now we go one step further and forge our own service tickets.

Remember the inner workings of the Kerberos authentication, the application on the server executing in the context of the service account checks the users' passwords from the group memberships in the service ticket. However, the user and group memberships in the service ticket are not verified by the application in a majority of environments. In this case, the application blindly trusts the integrity of the service ticket since it is encrypted with a password hash that is, in theory, known only to the service account and the domain controller.
