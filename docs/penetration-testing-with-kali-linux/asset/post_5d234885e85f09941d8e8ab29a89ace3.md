## 13.2.3 Cracking Methodology

In the next sections we'll walk through the various phases of a real-world password-cracking session, beginning with an overview of a solid methodology.

We describe the process of cracking a hash with the following steps:

- 1. Extract hashes
- 2. Format hashes
- 3. Calculate the cracking time
- 4. Prepare wordlist
- 5. Attack the hash

The first step is to extract the hashes. In a penetration test we'll find hashes in various locations. For example, if we get access to a database system, we can dump the database table containing the hashed users.

The next step is to format the hashes into our tool's expected cracking format. To do this we'll need to know the hashing algorithm used to create the hash. We can identify the hash type with hash-identifier⁶³¹ or hash-hashid⁶³² which are installed on Kali. Depending on the hashing algorithm and the source of the hash, we may need to check if it is already in the correct format for our cracking tool. If not, we need to use helper tools to change the representation of the hash into the expected format of our cracking tool.

In the third step, we will determine the feasibility of the cracking attempt. As we discussed before, the cracking time consists of the keyspace divided by the hash rate. If the calculated cracking time exceeds our expected lifetime, we might reconsider this approach!

> ⁶³¹ (Kali Tools, 2022), https://www.kali.org/tools/hash-identifier/
⁶³² (Kali Tools, 2022), https://www.kali.org/tools/hashid/

More realistically, we should consider the duration of the penetration test considering that we are likely obliged to stop the session (along with other clean-activity) when the test is terminated. Instead of holding out for success in an overly-lofty prospective cracking session, we should consider alternative attack vectors or in a hardware upgrade or a cloud-based machine instance.

The fourth step consider wordlist preparation. In all cases we should mutate our wordlist and perform a rule-based attack, instead of a straight dictionary attack. In this step, we investigate potential password policies and research other passwords, including online leak sites. Without this, we may need to run multiple wordlists with (or without) pre-existing rules for a broad coverage of possible passwords.

After the preparation, we can start our tool and begin the cracking process. At this point, we must take special care in copying and pasting our hashes. An extra space or a newline could render our efforts useless. In addition, we should be sure of the hash type we are using. For example, hascat cannot automatically determine if bd02f47de7c6558fc4c3eb0db462 is MD2, MD4, or MD5. An incorrect choice will obviously waste time. We can avoid this situation by double-checking the results with other tools and adding additional research.

We'll follow this methodology in the upcoming demonstrations to reinforce the important aspects and details of the cracking process. The best way to improve our results in this often-length process is to operate with focus and structure.

## 13.2.4 Password Manager

Password managers create and store passwords for different services, protecting them with a master password. Users often copy and paste these passwords from the password manager or use an auto-fill function tied to a browser. Examples of popular password managers are 1Password⁵⁵³³ and KeePass⁵⁵³⁴ This type of software can assist users who are often forced to maintain, complex passwords, but it can also introduce risk into an organization.

In this section we'll demonstrate a very common penetration test scenario. Let's assume we have gained access to a client workstation running a password manager. In the following demonstration, we'll extract the password manager's database, transform the file into a format using Hashcat, and crack the database password.

Let's begin connecting to the SALESWK01 (192.168.50.203) over RDP. Assuming we've obtained credentials for the jason user (lab), we'll log in and after a successful connection, we'll gain access to the system desktop.

Once connected, we'll check which programs are installed on the system. There are many ways to search for installed programs, but since we have GUI access, we use the Apps & features function of Windows, which is the most straight-forward approach. We'll check the Windows icon, type "Apps", select Add or remove programs and scroll down to review all installed programs.

Our next step is to locate the database files for searching all .kdbx files on the system.

Lets use PowerShell with the Get-ChildItem cmdlet to find files in specified locations. We'll use -Path C to search the whole drive. We'll use **Include** to specify the file types we want to use **File** and **Recurse** arguments. Finally we'll use -Action SilentlyContinue to silence errors.

```powershell
PS C:\> Get-ChildItem -Path C -Include *.kdbx -Recurse -Action SilentlyContinue
```
