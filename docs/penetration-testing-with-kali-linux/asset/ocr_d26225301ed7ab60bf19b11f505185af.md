# 18.3.1 SSH Local Port Forwarding

Let's recall the first port forwarding from the Socat scenario. We set up Socat to listen on TCP port 2345 on the WAN interface of CONFLUENCE01. Packets received on that port were forwarded to TCP port 5432 on PGDATABASE01. We used this to connect to our Kali machine, through CONFLUENCE01, to the PostgreSQL service on PGDATABASE01. The crucial thing to notice in this case is that listening and forwarding were both from the same host (CONFLUENCE01).

SSH local port forwarding¹⁴ adds a small twist. With SSH local port forwarding, packets are not forwarded by the same host for listens. Instead, an SSH connection is made between two hosts (an SSH client and an SSH server), a listening port is opened by the SSH client, and all packets received on this port are tunneled through the SSH connection to the SSH server. The packets are then forwarded by the SSH server to the socket we specify.

This concept might seem a bit abstract at the moment. We can understand it better by getting experience setting up a local port forward.

Let's reconsider the previous scenario with a slight modification: Socat is no longer available on CONFLUENCE01. We still have the credentials we previously cracked from the Confluence database, and there is still no firewall preventing us from connecting to the ports we bind on CONFLUENCE01.

With the database_admin credentials, we will log in to PGDATABASE01 and find that it's attached to another subnet. We find a host with a Server Message Block (SMB) server open (on TCP port 445) in that subnet. We will be able to connect to that server and download what we find to our Kali machine.

In this type of scenario, we'll plan to create an SSH local port forward as part of our SSH connection from CONFLUENCE01 to PGDATABASE01. We will bind a listening port on the WAN interface of CONFLUENCE01. All packets sent to that port will be forwarded through the SSH tunnel. PGDATABASE01 will then forward these packets towards the SMB port on the new host we found.
