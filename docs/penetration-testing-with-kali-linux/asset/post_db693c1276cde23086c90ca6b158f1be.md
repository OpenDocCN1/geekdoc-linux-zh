## 8.4.3 Identifying XSS Vulnerabilities

We can find entry points for XSS by examining a web application and identifying input fields (such as search fields) that accept unsanitized input, which then displayed as output in subsequent pages.

Once we identify an entry point, we can input special characters and observe the output to determine if any of the special characters returned unfiltered.

The most common special characters used for this purpose include:

```
< > ' " { } ;
```

> Listing 120 - Special characters for HTML and JavaScript "<" and "\""

Let's describe the purpose of these special characters. HTML uses "<" and ">" to denote elements the various components that make up an HTML document. JavaScript uses "\"" and '\' in function declarations. Single ('') and double ("") quotes are used to denote strings, and semicolons (;) are used to mark the end of a statement.

If the application does not remove or encode these characters, it may be vulnerable to XSS because the app interprets the characters as code, which in turn, enables additional code.

366 (Wikipedia, 2022), https://en.wikipedia.org/wiki/HTML_element

While there are types of encoding, the most common we'll encounter in web applications are HTML encoding³⁶⁷ and URL encoding³⁶⁸ URL encoding, sometimes referred to as percent encoding, used to convert non-ASCII and reserved characters in URLs, such as converting a space to “%20”.

HTML encoding (or character references) is used to display characters with special meanings, like tag elements. For example, “&lt;” is the character reference for “<”. When encountering this type of encoding, the browser will not interpret the character as the start of an element, but will display the character as-is.

If we inject these special characters into the page, the browser will treat them as code elements. We can then begin to build code that will be executed in the browser's browser once it loads the maliciously-injected JavaScript.

We need to use different sets of characters, depending on where our input is included. For example, if our input is added between div tags, we need to include our script tags³⁶⁹ and need to inject “<” as part of the payload. If our input is added within an existing JavaScript tag, we may only need quotes and semicolons to add our own code.

## 8.4.4 Basic XSS

Let's demonstrate basic XSS with a simple attack against the OffSec WordPress instance. The WordPress installation is running a plugin named *Visitors* that is vulnerable to stored XSS.³⁷⁰ The plugin's main feature is to log the website's visitor data, including the IP, source, and User-Agent fields.

The source code for the plugin can be downloaded from its website.³⁷¹ If we inspect the **database.php** file, we can verify how the data is stored inside the WordPress database:

```php
function VST_save_record() {
    global $wpdb;
    $table_name = $wpdb->prefix . 'VST_registros';

    VST_create_table_records();

    return $wpdb->insert(
        $table_name,
        array(
            'patch' => $_SERVER['REQUEST_URI'],
            'datetime' => current_time('mysql'),
            'useragent' => $_SERVER['HTTP_USER_AGENT'],
            'ip' => $_SERVER['HTTP_X_FORWARDED_FOR']
        )
    );
}
```

### Listing 121 - Inspecting Visitor Creation

This PHP function is responsible for parsing various HTTP headers, including the User-Agent, which is saved in useragent record. Next, when a administrator loads the Visitor, the function will execute the following code from `start.php`:

```php
$count=count(VST_records($date_start, $date_finish));
foreach(VST_records($date_start, $date_finish) as $record) {
    echo '<tr class="active">
        <td scope="row">'.date($date_start,$format).'</td>
        <td scope="row">'.get_option("links",$record->path).'</td>
        <td scope="row"><a href="https://www.google.com/search?ip='.$record->ip.'">'.$record->ip.'</a></td>
        <td scope="row">'.$record->user-agent.'</td>
    </tr>';
}
```

From the above code, we'll notice that useragent record is retrieved from the database and inserted plainly without any of sanitization. As the User-Agent header is under control, we could craft XSS attack by inserting a script tag invoking the alert() method to generate a pop-up message. Given the immediate visual impact, this is very commonly used to verify that an application is vulnerable to XSS. Although we just performed white-box testing, we could have discovered the same vulnerability through black-box testing.
