C:\Users\student>nslookup -type txt info.megacorptwo.com 192.168.50.151

Listing 51 - Using nslookup to perform a more specific query

In this example, we are specifically querying the 192.168.50.151 DNS server for any TXT record related to the info.megacorptwo.com host.

The nslookup utility is as versatile as the Linux host and the queries can be further automated through PowerShell or Batch scripting.

## 6.3.2 TCP/UDP Port Scanning Theory

Port scanning is the process of inspecting what services are running on the target and what potential attack vectors may exist.

> Please note that port scanning is not representative of traditional user activity and could be considered illegal in some jurisdictions. Therefore, it should not be performed outside the labs without direct, written permission from the target network owner.

It is essential to understand the implications of port scanning, as well as the impact that specific port scans can have. Due to the amount of traffic scans can generate, with the intrusive nature, running port scans blindly have adverse effects on target systems or the client network as overloading servers and network links or triggering an IDS/IPS²¹ Running the wrong scan can result in downtime for the customer.

Using a proper scanning methodology can significantly improve our efficiency as penetration testers while also limiting the risks. Depending on the scope of the engagement, instead of running a full scan against the target network, we can start by only scanning ports 80 and 443. With a list of possible web servers, we can run a full scan against these servers in the background while performing other enumeration. Once the full scan is complete, we can further narrow our scans to probe for more information with each subsequent scan. Port scanning should be understood as a dynamic process that is unique to each engagement. The results of one scan can determine the type and scope of the next scan.

We'll begin our exploration of scanning with a simple TCP and UDP port scan using Netcat. It should be noted that Netcat is not a port scanner, but it can be used in a rudimentary way to showcase how a typical port scanner works.

Since Netcat is present on many systems, we can repurpose some of its functionality to mimic a basic port scan when we are in need of a fully-featured scanner. We will also explore better tools to detect port scanning in detail.

Let's start by covering TCP scanning techniques, focusing on UDP layer. The simplest port scanning technique, usually using CONNECT scanning, relies on the three-way TCP handshake²² This mechanism is designed so that two hosts attempting to communicate negotiate parameters of the network socket connection before transmitting any data.

In basic terms, a host sends a TCP SYN packet to a destination port. If the destination port is open, the server responds with a SYN-ACK packet and the client host sends an ACK packet to the handshake. If the handshake completes successfully, the port is considered open.

We can demonstrate this by running a TCP Netcat port scan on ports 3388-3390. We'll use the -W option to specify the connection timeout in seconds, as well as -z to specify zero-I/O mode, which is used for scanning and not data.

```
kali@kali:~$ nc -nvw 1 -z 192.168.0.152 3388-3390
(UNKNOWN) [192.168.0.152 3390 (?)]: Connection refused
(UNKNOWN) [192.168.0.152 3389 (ms-wbt-server)] open
(UNKNOWN) [192.168.0.152 3388 (?)]: Connection refused
sent 0, rcvd 0
```

Now that we have a good understanding of the TCP handshake and have examined how a TCP scan works, let's cover UDP scanning. Since UDP is stateless and does not involve a three-way handshake, the mechanism behind UDP port scanning is different from TCP.

Let's run a UDP Netcat scan against ports 120-123 on a different target. We will use the only nc option we have covered, which indicates a UDP scan.

```
kali@~$ nc -nu -z -w 1 192.168.50.149 120-123
(UNKNOWN) [192.168.50.149] 123 (ntp) open
```

Figure 32: Wireshark capture of a UDP Netcat scan

As shown in Figure 32, every UDP packet is sent to a specific port (packets 2, 3, 5, and 7). If the destination port is open, the packet will be processed by the application layer. The response received will depend on how the application is programmed to respond to packets. For example, the application sends no response. If the destination port is closed, the target should respond with an ICMP port unreachable (as shown in packets 5, 7, and 9), sent by the UDP/IP stack of the target machine. However, if the port is filtered by a firewall, in these cases the scanner will report the target port as as open because of the absence of the ICMP message.
