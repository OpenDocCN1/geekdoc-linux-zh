Most of the connections we make, suggesting that there's nothing there. In contrast, we'll notice PGDATBASE01 (172.16.50.215) actively refused the connection. We also find that there is a host on the subnet, which has TCP port 445 open: 172.16.50.217!

We want to enumerate the SMB service on this host. If we find anything, we want to download it to our Kali machine for inspection. There are at least two ways we could do this:

One way is to use whatever built-in tools we find on PGDATBASE01. However, if we find anything, we would have to download it to PGDATBASE01, then transfer it back to our Kali machine, CONFLUENCE01, then would create a tedious manual data transfer.

The alternative is to use SSH port forwarding. We could create an SSH connection to CONFLUENCE01 as part of that connection, we could create an SSH local port forward. This would listen on port 445 on the WAN interface of CONFLUENCE01, forwarding packets through the SSH tunnel of CONFLUENCE01 and directly to the SMB service we found.

In this scenario, there is no firewall preventing us from accessing ports that bind on the WAN interface of CONFLUENCE01. In later sections, we will put the firewall up, and use more advanced techniques to traverse this boundary. Now we should kill our existing connection to PGDATBASE01. We will set up a new connection with arguments to establish the SSH port forward.

> Listing 537 - Running the local port forward command.

As discussed, the rest of the SSH command is usual. A port forward can be set up OpenSSH's -L option, which takes two sockets (in format IPADDRESS:PORT separated with a colon as an argument (IPADDRESS:PORT:IPADDRESS:PORT)). The first socket is the listening socket that will be bound to the machine. The second socket is where we want to forward the packets to. In this case, we will use SSH to listen on all instances on port 445 on CONFLUENCE01 (0.0.0.0:4455), then forward all packets (through the SSH tunnel to PGDATABASE01) to port 445 on the newly-found host (172.16.50.217).

```
confluence01:/opt/atlassian/confluence/bin$ ssh -N -L 0.0.0.0:4455:172.16.50.217:445 database_admin@10.40.521
Could not create directory '/home/confluence/'. The authenticity of host '10.40.521' can't be established. ECDSA key fingerprint is SHA256:K9v2nXQjIYYYm/mVB0VkyKy7TeqIeyytlh. Are sure you want to continue connecting? (yes/no) yes
Failed to add the host to the list of known hosts (/home/confluence/known_hosts)._admin@10.40.521:password:
```

Once we've perceived, we receive no output. When running SSH with the -N flag, this is normal. The -N flag prevents SSH from executing any remote commands, meaning we will only receive output related to our port forward.

If the connection or the port forwarding fails for some reason, and the output we get from the SSH session isn't sufficient to troubleshoot it, we can pass the -v flag in ssh to receive debug output.

This reverse shell from CONFLUENCE01 is now occupied with an open SSH session, we need to connect to CONFLUENCE01. We can do this by listening on another port and modifying our CVE-2022-26134 payload to return a shell to that port.
