Listing 419 shows that the service is set to Auto, meaning it will start automatically after a reboot. In order to issue a reboot, we need to have the privilege SeShutdownPrivilege. We can use whoami /priv to get a list of all privileges.

```
PS C:\Users\d> whoami /priv
```

| Privilege Name | Description | State |
|----------------|-------------|-------|
| SeSecurityPrivilege | Manage auditing and security log | Disabled |
| SeShutdownPrivilege | Shut down the system | Disabled |
| SeChangeNotifyPrivilege | Bypass traverse crossing | Enabled |
| SeUndockPrivilege | Remove remote computer from docking window | Disabled |
| SeIncreaseWorkingSetPrivilege | Increase a process working set | Disabled |
| SeTimeZonePrivilege | Change the time zone | Disabled |

Listing 420 shows that our user has the privilege (among others) and therefore, we should be able to enable a system shutdown or reboot. The Disabled state only indicates if the privilege is currently enabled for the running process. In our case, that whoami has not requested and not currently using the SeShutdownPrivilege.

If the SeShutdownPrivilege privilege was not present, we would have to wait for the victim to manually start the service, which would be much less convenient.

We can issue a reboot with shutdown /r (reboot instead of shutdown) and /t 0 (in seconds).

> We always try to avoid avoiding reboots on production systems in a real penetration test. A reboot could lead to unforeseen problems and should only be issued in direct collaboration with the client's IT staff. If a system doesn't boot up after reboot, this could disrupt their day-to-day business and even cause long-term damage of the infrastructure. This is especially the case in a situation where there is no current backup available.

```
PS C:\Users\dave> shutdown /r /t 0
```
