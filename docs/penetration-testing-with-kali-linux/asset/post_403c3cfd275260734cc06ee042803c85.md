
# OffSec Penetration Testing with Kali Linux

execute (symbolized by x). Each file or directory has specific permissions for three categories of users: the owner, the owner group and others group.

Each permission (rwx) allows the designated collection of users to perform different actions depending on if the resource is a file or a directory.

For files, r allows reading the content, w allows changing its content and x allows the file to run. A read gives the right to consult the list of its contents (files and directories). Write allows creating or deleting files. Finally, execute access allows crossing the directory to its contents (the cd command, example). Being able to cross through a directory without being able to read gives the user permission to access known entries, but only by knowing their name.

Let's examine a simple combination of file permissions using a real-world example on our local Kali machine, since it's based on the Linux Debian distribution.

```
kal@kali:-$ ls -l /etc/shadow
-rw------- 1 root shadow 1751 May 09:31 /etc/shadow
```

Listing 456 - Inspecting file permissions and users ownership

For each user category, the three different permissions are displayed. The very first hyphen describes the file type. Since it's not strictly related to file permissions, we can safely ignore it.

The next three characters display the file owner (root) permissions, which are rw-, meaning the owner has read, but no privileges. The shadow group owner has only been given read access, as the write and execute flag are unset. Finally, the other group has not been granted any rights to this file.

We can now apply this introductory knowledge about Linux file permissions while performing privilege escalation in the next section.

## 17.1.2 Manual Enumeration

Manually enumerating Linux systems can be time-consuming. However, this approach allows for a more controlled outcome because it helps identify peculiar escalation methods that are often overlooked by automated tools.

Furthermore, automated enumeration cannot replace manual investigation because the customized settings of our target environments are likely to be exactly those that are misconfigured.

> Some of the commands in this Module may require minor modifications depending on the target operating system version. In addition, not all the commands presented in this section will be reproducible on the dedicated clients.

# OffSec

When gaining access to a target, the first things we should identify is the user context. We can use command to gather context information. We can do so connecting through SSH as the user to our Debian lab

```
joe@debian-privesc:~ $ id
uid=1000(joe) gid=1000(joe)
groups=1000(joe),24(cdrom),25(floppy),29(audio),30(dip),44(video),46(plugdev),109(netdev),112(bluetooth),116(padman),117(scanner)
```

List 457 - Getting information about the current user

The output reveals that we are operating as the user, who has a User Identifier (UID) and Group Identifier (GID) of 1000. The user joe is also part of other groups that are out of scope for this Module.

To enumerate all users, we can print the contents of the /etc/passwd file.

```
joe@debian-privesc:~ $ cat /etc/passwd
root:x:0:0:root:/root:/usr/sbin/nologin
daemon:x:1:1:daemon:/bin:/usr/sbin/nologin
bin:x:2:2:bin:/bin:/usr/sbin/nologin
sys:x:3:3:sys:/dev:/usr/sbin/nologin
...
www-data:x:33:33:www-data:/var/usr/sbin
dnmasq:x:106:65534:dnmasq://var/lib/misc:/usr/sbin/nologin
usbmux:x:107:46:usbmux:/var/lib/usbmux:/usr/sbin/nologin
rtkit:x:108:114:RealtimeKit:/proc:/usr/sbin/nologin
:x:109:65534:ssh:/run/sshd:/usr/sbin/nologin
Debian-gdm:x:117:124:Gnome Display Manager:/var/lib/gdm3:/bin/false
joe:x:1000:1000,,,/home/joe:/bin/bash
system-coredump:x:999:999:System Core Dump:/sbin/nologin
eve:x:1001:1001,,,/home:/bin/bash
```

List 458 - Getting information about the users

The password field lists user accounts, accounts used by various services on the target machine such as www-data and sshd. This indicates a web server and an SSH server are likely installed on the system.

We can now show in our current user's data:

- **Name:** "joe" - Indicates the username used for login.
- **Encrypted Password:** "x" - This field contains the hashed version of the user's password. In this case, value x means that the encrypted password hash is contained in the /etc/shadow file (more on that shadow).
- **UID:** "1000" - Aside from the root who has a UID of 0, Linux starts counting regular user IDs from 1000. This value is also called real ID.
- **GID:** "1000" - Represents the user's specific Group ID.

> 823 (Linux man-pages project, 2019), https://man7.org/linux/man-pages/man/1/id.1.html
>829 (Wikipedia, 2022), https://en.wikipedia.org/wiki/User_identifier

- **Comment:** "joe," - This field generally contains a description about the user, often repeating username information.
- **Home Folder:** "/home/joe" - Describes the user's home directory prompted upon login.
- **Login Shell:** "/bin/bash" - Indicates the default interactive shell, if one exists.

In addition to the joe user, we also notice another user eve, and we can infer this is a standard user since it has a configured home folder /home/eve. On the other hand, system services are configured with /usr/sbin/nologin home folder, where the nologin statement is used to block any remote or local login for service accounts.
