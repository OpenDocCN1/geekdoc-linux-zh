# 20.2.1 Staged vs Non-Staged Payloads

In this section, we'll explore the differences between staged and non-staged payloads. Let's assume we identified a buffer overflow vulnerability in a service. As we learned in Fixing Exploits, we need to be aware of the buffer size our shellcode will be stored in. If shellcode size of our exploit exceeds the buffer size, our exploit attempt will fail. In a situation like this, it's vital which payload we choose: staged or non-staged.

The difference between these payloads is subtle but important. A non-staged payload is sent in its entirety along with the exploit. This means the payload contains the full shellcode for a selected task. In general, "all-in-one" payloads are more stable. The downside is that the size of these payloads will be bigger than other types.

In contrast, a staged payload is usually sent in two parts. The first part contains a small payload that causes the victim machine to connect back to the attacker, transfer a larger secondary payload containing the rest of the shellcode, and then execute it.

There are several situations in which we would prefer to use a staged payload instead of non-staged. If there are space limitations in an exploit, a staged payload might be a better choice as it is typically smaller. In addition, we need to keep mind that antivirus software can detect shellcode in an exploit. By replacing the full code with a first stage, which loads the second and malicious payload of the shellcode, the remaining payload is retrieved and injected directly into the victim's memory. This may prevent detection and increase our chances of success.

Now that we have a basic understanding of these two types of payloads, let's get our hands dirty. For this, we'll use the same example payload as in the previous section and show payloads to get a list of all payloads that are compatible with the currently selected exploit module.
