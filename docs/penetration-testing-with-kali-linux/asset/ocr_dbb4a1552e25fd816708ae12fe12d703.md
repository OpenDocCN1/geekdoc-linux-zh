When the admin loads the Visitor's dashboard that contains the injected JavaScript, executes whatever we provided as a payload, it will alert pop-up or a more complex JavaScript function.

For instance, we could craft a JavaScript function that adds WordPress administrative account, so once the real administrator executes our injected code, the function will execute behind the scenes.

In order to succeed with our attack angle, we need to cover another web application class.

To develop this attack, we will build a similar scenario as depicted by Shift8.³376 First, we will create a JS function that fetches the WordPress admin nonce.³377 The nonce is a server-generated token that is included in each HTTP request to add randomness and prevent Cross-Site-Request-Forgery (CSRF)³378 attacks.

A CSRF attack occurs via social engineering in which the victim clicks on a malicious link that performs a configured action on behalf of the attacker.

The malicious link could be disguised by an apparently harmless-address, often lurking the victim to click on it.

```
<a href="http://fakecryptobank.com/send_btc?account=ATTACKER&amount=10000">check out these awesome cat memes!!</a>
```

In the example, the URL link is pointing to a Fake Bank website API, which performs a bitcoin token transfer to the attacker. If this link was embedded into the HTML code of an email, the user would only be able to see the link description, not the actual HTTP response it is pointing to. This attack would be successful if the user is already logged in with a valid session on the website.

In our case, by including and checking the pseudo-random nonce, WordPress prevents this of attack, since an attacker could not have prior knowledge of the token. However, as we'll explain, the nonce won't be an obstacle for the stored XSS vulnerability we discovered in the plugin.
