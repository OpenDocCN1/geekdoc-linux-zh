## 8.3.2 Inspecting HTTP Response Headers and Headers

We can also search server responses for additional information. There are two types of tools we can use to accomplish this. The first is a proxy, like Burp Suite, which intercepts requests between a client and a web server, and the other is the browser's Network tool.

We will explore both approaches in this Module, but let's begin by demonstrating the Network tool. You can learn from the Firefox Web Developer menu to review HTTP headers and responses. This tool shows network activity that occurs after it launches, so we must refresh the page to display traffic.

![](img/336d6ea891e7464f18ad64426619ced4_222_0.png)

Figure 106: Using the Tool to View Requests

We can click on a request to get more details about it. In this case, we want to inspect response headers. Response headers are a subset of HTTP headers that are sent in response to an HTTP request.

The Server header will often reveal the name of the web server software. In many configurations, it also reveals the version number.

HTTP headers are not always generated solely by the web server. For instance, web proxies actively insert the X-Forwarded-For header to signal the web server over the original client IP address.

## 8.3.3 Enumerating and Using APIs

In many cases, our penetration test is an internally-built web application that is shipped with a number of Application Programming Interfaces (API). These APIs are responsible for interacting with the back-end logic and providing a backbone of functions. A specific type of API named Representational State Transfer (REST) is used for a variety of purposes, including authentication. In a typical white-box scenario, we receive complete API documentation to help us map the attack surface. However, when performing a black-box test, we'll need to discover the target's APIs ourselves.

We can use Gobuster to brute the API endpoints. In this test, API gateway server is listening on port 5001 at 192.168.50.16, so we can attempt a directory brute attack. API paths are followed by a version number, resulting in a pattern such as:

```
/api_name/v1
```

The API name is often quite descriptive about what it uses to operate, followed directly by the version number. With this information, let's try forcing the API paths using a wordlist with Gobuster feature. We can call this feature by the -u option and providing a file with patterns. For our test, we'll create a sample file on our Kali system using the following:

```
{GOBUSTER}/v1
{GOBUSTER}/v2
```

In this example, we are using the "GOBUSTER" placeholder to match any word from our wordlist, which will be appended to the version. To keep our test simple, we'll try with only two versions. We are now ready to enumerate the API with gobuster using the following command:

```bash
kali@kali:~ gobuster dir -u http://192.168.50.16:5002 -w /usr/share/wordlists/dir/big.txt -p pattern
```
