The Listing above shows the hashing of the Keepass database stored in keeppass.hash. Before we can crack the hashing, we need to modify it.

In our case, the JIR script prefilled the filename Database to the hash. The script does this to act as the username for the target hash. This is helpful when cracking databases, since we want to output the corresponding username and not only the password. Since Keeps uses a master password without any kind of username, we need to remove the "Database" with a string text.

After removing the "Database", the hash is in the correct format for Hashcat:

```bash
kali@kali:~/downloads$ cat keeppass.hash
keeppass$2=60+0*d74ec2a9272e938717d2a7d4577ba3486d20dec73a9db1a7fbc7a068c9aec6bd04b0
bdf878988ddcd4a3d436e--
```

## 13.2.5 SSH Private Key Passphrase

In this section we will focus on cracking SSH private key passphrases.

Even though SSH private keys should be kept confidential, there are many scenarios in which these files could be compromised. For example, if we gain access to a web application via vulnerability Traversal, we could read files on the system. We could use this to retrieve a user's SSH private key. However, when we try to use it to connect to the system, we would be prompted for a passphrase. To gain access, we'll need to crack the passphrase.

Let's demonstrate this scenario and how to use the methodology we discussed to crack the passphrase of a private key. When we use a dictionary attack on the HTTP form, we gain access to a web-based file manager which (for demonstration) is located at http://192.168.50:2080 and log in with the username of user and a password of 12122.
