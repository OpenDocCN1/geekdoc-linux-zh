Writing an exploit from scratch can be difficult and time-consuming. But it can be equally difficult and time-consuming to find a public exploit that fits our exact needs during an engagement. Great compromise is to modify a public exploit to suit our specific needs.

Understanding each of these elements is very important. For example, if our target is running Windows Server 2022 and we attempt to run an exploit that was written and tested against Windows 2003 Server, never protection mechanisms such as Address Layout Randomization (ASLR)$679 will most likely result in an application crash. These kind of events could lock down that attacker vector for a period of time or even the production environment, both situations we should avoid.

Before running a penetration test, its scope should be defined upfront and the client should accept any potential downtime associated with attack vectors. Keeping in mind, as penetration testers we should always strive to minimize the impact of any exploit we plan to run.

To avoid potential downtime, instead of firing a mismatched exploit, we should always read the exploit code carefully, if it is modified, and test it against our sandbox target whenever possible.

> These target-specific variables explain why online resources like the Exploit Database$680$ host multiple exploits for the same vulnerability, each written for different operating system versions and architectures.

We may also benefit from porto an exploit to a different language in order to include additional pre-written libraries and extend the exploit functionality by importing it to an attack framework.
