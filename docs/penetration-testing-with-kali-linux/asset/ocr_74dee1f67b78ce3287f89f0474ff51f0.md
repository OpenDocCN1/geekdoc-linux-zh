Figure 31: Wireshark capture of the Netcat port

In this caption (Figure 31), netcat sent several TCP packets to ports 3390, 3389, and 3388 on packets 1, 3, and 7. Due to various factors, including timing issues, the packets may appear out of order in Wireshark. Here we observe that the server sends a SYN-ACK packet from port 3389 on packet 4, indicating that the port is open. The other ports did not reply with a similar SYN-ACK packet, and actively rejected the connection attempt by a RST-ACK packet. Finally, on packet 6, Netcat closed this connection by sending a FIN-ACK packet.

Now that we have a good understanding of the TCP handshake and have examined how a TCP scan works, let's cover UDP scanning. Since UDP is stateless and does not involve a three-way handshake, the mechanism behind UDP port scanning is different from TCP.

Let's run a UDP Netcat scan against ports 120-123 on a different target. We will use the only nc option we have covered, which indicates a UDP scan.

```
kali@~$ $ nc -nu -z -w 1 192.168.50.149 120-123
(UNKNOWN) [192.168.50.149] 123 (ntp) open
```

Figure 32: Wireshark capture of a UDP Netcat scan

As shown in Figure 32, every UDP packet is sent to a specific port (packets 2, 3, 5, and 7). If the destination port is open, the packet will be processed by the application layer. The response received will depend on how the application is programmed to respond to packets. For example, the application sends no response. If the destination port is closed, the target should respond with an ICMP port unreachable (as shown in packets 5, 7, and 9), sent by the UDP/IP stack of the target machine.

Most UDP scanners use the standard 'ICMP port unreachable' message to inform the status of a target port. However, if the port is filtered by a firewall, in these cases the scanner will report the target port as as open because of the absence of the ICMP message.
