VMware's unique virtual machine design makes it extremely powerful and probably unlike anything you've ever seen before, even if you've experimented with emulators and virtual machines in the past.

This chapter pops open the VMware hood and explains in detail what VMware can do and how it's done.

## Sharing the CPU

The most important thing to remember about VMware's virtual machine design is that your CPU's attention is split between your host OS (Linux) and whatever guest OS you run in VMware. That's because VMware looks just like a Linux application to the Linux task scheduler.

The VMware software layer and Linux's own multitasking kernel manage the CPU demand to ensure that neither side can completely deny the other of attention, although it is possible for heavy demand from either to greatly slow down your computer. Think of a flowing stream, with a new irrigation branch. As long as things remain under control and nobody gets too greedy, there's still plenty of water for everyone. Figure 2.1 is a diagram of the VMware virtual machine architecture.

VMware runs in two pieces: the virtual machine itself, in which your guest operating system and programs run, and a "traffic cop" VMware Virtual Platform software layer

that manages all the I/O between the guest OS, you, and your computer. This emulation layer is less demanding than it would be if VMware had to emulate its own CPU as well. VMware claims that in some circumstances the Virtual Platform layer consumes less than 5 percent of available CPU time; you might find it needs 20 percent or more. See Figure 2.2 for an example of typical CPU usage on a computer running Linux and a VMware guest session.

> VMware does not support multiprocessor access from within a virtual machine, but if your host machine has more than one CPU, you can lighten the load. VMware will run a second virtual machine on your second CPU, the third on a third CPU (if available), and so on. This makes it feasible to run more than one instance of VMware at once; otherwise, your system starts to get a bit crowded. Unfortunately, VMware does not provide a built-in tool to select which CPU will run each virtual machine.

Keep in mind that the features and quirks of the host CPU are replicated in the VMware guest virtual machine. For instance, computers using AMD K6-2 CPUs of 350MHz or more are susceptible to a crashing on startup in Windows 95, and the same patch that cures the problem on a standalone Windows PC is required in VMware.

By the same token, if you want your guest operating system to have access to the Streaming Single Instruction Multiple Data (SIMD) Extensions of the Intel Pentium III or the Enhanced 3DNow! capabilities of the AMD Athlon, then that needs to be the CPU in your computer. VMware can't make a four-cylinder engine look like a V8.

> The AMD K6-2/Windows 95 problem is described at http://www.amd.com/products/cpg/k623d/win95_update_k6.html.

## Creating an Isolated Environment

VMware takes great pains to build an ironclad, “I can’t believe it’s not a PC” virtual machine. Here’s the best news first: It is extremely unlikely that even the worst crash in a VMware virtual machine will damage or even inconvenience your host Linux OS.

Aside from their communication with the VMware Virtual Platform layer, VMware sessions do not have any special privileges or access to your computer’s files or memory space. You predefine a hard memory limit that VMware’s guest OS cannot exceed, and you similarly lay down the law as to which system devices and disk storage units VMware can touch. Everything else is off-limits; it’s completely invisible and inaccessible.

Although Linux can temporarily reclaim memory allocated to a VMware virtual machine through paging and swapping, the resulting performance hit is extremely unpleasant. It will behoove you to think of any memory given to a virtual machine as off-limits to Linux applications.

Because VMware can form a virtual network between the emulation and your host OS, it is possible for network trojans to spread between the two. You should treat the virtual machine as just as real a security risk as any other computer. Enforce whatever antivirus and network security policies you might have, and if you don’t have any, now is a good time to make some.
