By committing, you make the changes permanent. Discard loses the changes forever, leaving the disk image in the same state it was before you last launched VMware.

But by merely keeping the changes, you can mull over your choice until the next time you run VMware. At that point, you are asked again to commit or discard the changes. You're also presented with a new option: append new changes to the current redo log. This means that the virtual machine boots with the changes you made last session intact (in other words, as if you had committed to the changes) but leaves the redo log open, which still leaves you the option of undoing all the changes you made in both the current and the last session. Figure 2.6 shows VMware starting a new session with a "kept" redo log.

If you decide to append new changes to the existing redo log, all the changes you have made are part of the same log: You cannot selectively undo only the changes made in the current or previous session.

If you entirely forgot to make a decision about the changes, you can cancel the VMware load sequence so you can make up your mind about the redo log.

# What Hardware Can VMware Share?

The good news is that VMware and any supported guest operating systems work flawlessly with most of the hardware you're currently enjoying under Linux. The bad news is that VMware only works with hardware you're currently enjoying under Linux. The VMware Virtual Platform layer can only address hardware that can be configured and used in the Linux universe.

VMware Hardware Compatibility Rule #1: If the hardware doesn't work in Linux, it won't work in any VMware guest OS, even if that guest OS natively supports the hardware. Exception: Some dongles (which are useless under Linux) are properly recognized in VMware guest operating systems.
