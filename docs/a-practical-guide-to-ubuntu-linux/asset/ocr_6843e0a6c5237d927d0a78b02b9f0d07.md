# root-owned setuid programs are extremely dangerous

security Because root-owned setuid programs allow anyone who does not know the root password and cannot use sudo to gain root privileges, they are tempting targets for a malicious user. Also, programming errors that make normal programs crash become root exploits in setuid programs. A system should have as few of these programs as possible. You can disable setuid programs at the filesystem level by mounting a filesystem with the nosuid option (page 508). See page 454 for a command that lists all setuid files on the local system.

optional The following techniques for gaining root privileges depend on unlocking the root account (setting up a root password) command as explained on page 431.

+   * You can use a su (substitute user) command while you are logged in as yourself. When you provide then the root password, you will have root privileges. For more information refer to “su: Gives You Another User’s Privileges” on page 431.
* Once the system is up and running in multiuser mode (page 448), you can log in as root. When you supply the root password, you will be running with root privileges.

Some techniques limit how one can log in as root. For example, PAM (page 478) controls the who, when, and how of logging in. The /etc/security/access.conf file controls which terminals (tys) a user can log in as root. The /etc/security/access.conf file adds another dimension to login control (see the comments in the file for details).

# Do not allow root access over the Internet

security Prohibiting root users logging in over a network is the default policy of Ubuntu and implemented by the PAM security module. The /etc/security/access.conf file must contain the name of all users/workstations that you want to be able to log in as. Initially every line in access.conf is commented out.

You can, log in root over a network using ssh (page 663). As shipped Ubuntu, ssh does not follow the instructions in security or access.conf. In addition, /etc/ssh/sshd_config, Ubuntu sets PermitRootLogin to yes to permit root to log in using ssh (page 680).

# sudo: RUNNING A COMMAND WITH root PRIVILEGES

Classically a user gained root privileges by logging in as root or by giving an su (substitute user) command and providing the root password. When an ordinary user executed a privileged command in a graphical environment, the system would prompt for the root password. Most recently the use of sudo (www.sudo.ws) has taken over these classic techniques of gaining root privileges.
