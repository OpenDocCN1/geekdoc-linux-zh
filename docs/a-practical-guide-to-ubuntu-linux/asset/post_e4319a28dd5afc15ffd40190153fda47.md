Setauid files make sure no one except with root privileges can write to files containing programs that are owned by root and run in setuid mode (for example, password sudo). Make sure users do not transfer programs that run in setuid mode and are owned by root onto the system by mounting tapes or disks. These programs can be used to circumvent system security. One technique that prevents users from using setuid files is to use the -nosuid flag to mount, which you can set in the flags section the fstab file. The BIOS in many machines gives you some degree of protection from an unauthorized person who tries to modify the BIOS or reboot the system. # LOG FILES AND MAIL FOR root

Users frequently email root and postmaster to communicate with the system administrator. If you do not forward root's mail to yourself (/etc/aliases on page 722), remember to check root's mail periodically. You will not receive reminders mail that arrives for root when you use sudo to perform system administration tasks. However, you can use the command sudo -u root to look at root's mail.

Review the system log files for evidence of problems. Some important files are /var/log/messages, where the operating system and some applications record errors; /var/log/mail.err (or /var/log/exim4/mainlog if you are running exim4), which contains errors from the mail system; and /var/log/syslog, which contains messages from system, including messages from cron.

# MONITORING DISK USAGE

Sooner or later you will probably run out of disk space. Do not fill up a partition; Linux can write to files significantly faster if at least 5 to 30 percent of the space in a partition remains free. Using more than the maximum optimal disk space in a partition can degrade system performance.

As a filesystem becomes full, it can become fragmented. This is similar to the DOS concept of fragmentation but is not nearly as pronounced and typically rare on modern Linux filesystems; design Linux filesystems are resistant to fragmentation. If you keep filesystems from running near full capacity, you may never need to worry about fragmentation. If there is no space on a filesystem, you cannot write to it at all.

To check for filesystem fragmentation, unmount the filesystem and run fsck (page 512) (with the -f option on ext2 ext3, and ext4 filesystems). The output of fsck includes a percentage figure for the filesystem. You can defrag a filesystem by backing it up; using mkfs (page 458) to make a clean, empty image; and restoring the filesystem. Which utility do you use to perform the backup and restore—dump, tar, cpio, and a third-party backup program—is not important.

Linux provides several programs for report on is how much disk space on which filesystems. Refer to the du, quota, and df man pages and the -size option in the find utility man page. In addition to these utilities, you can use the disk quota (page 625) to manage disk space.

Four strategies to increase the amount of free space on a filesystem are to compress files, delete files, LVM-based filesystems, and condense directories. This section contains some ideas to maintain a filesystem so that it does not become overloaded.

Some files, such as log files and temporary files, inevitably grow over time. Core dump files, for example, take up substantial space and are rarely used. Also, users occasionally run programs that accidentally generate huge files. As the system administrator, you must review these files periodically so they do not get out of hand.

If a filesystem is running out of space quickly (that is, over a period of an hour rather than weeks or months), first figure out why it is running out of space. Use ps ef command to determine whether a user has a runaway process that is creating a huge file. When evaluating the output of ps, for a process that has consumed a large amount of CPU time. If such a process is running and creating a large file, the file will continue to grow as you free space. If you remove the file, the space it occupied will not be freed until the process terminates, so you need to kill the process. Try to contact the user running the process, and ask the user to kill it. If you cannot contact the user, use sudo to kill the process yourself. Refer to kill on page 455 for more information.

You can also truncate a large log file rather than removing it, although you can deal with this recurring situation using logrotate (discussed next). For example, if the /var/log/messages file has become very large because a system daemon is mis-configured, you can use /dev/null to truncate it:

```
$ sudo cp /dev/null /var/log/messages
```

or

```
$ sudo cat /dev/null > /var/log/messages
```

or, without spawning a new process,

```
$ sudo > /var/log/messages
```

If you remove /var/log/messages, you have to restart the syslogd daemon. If you do not restart syslogd, the space on the filesystem will not be released.

When no single process is consuming the disk space but capacity has been used up gradually, locate unused files and delete them. You can archive these files using cpio, dump, or tar before you delete them. You can safely remove most files core that have not been accessed for several days. The command line performs this without removing necessary files core (such as /dev/core):

```
$ sudo find -type f -name core xargs file | grep 'B core file' | sed 's/ELF.*//g' | xargs rm -f
```

The command lists all ordinary file named and sends its output to xargs, which runs on each of the files in the list. The file utility displays a string that includes B core file for files created as the result of a core dump. These files need to be removed. The grep command filters out file any lines that do not contain this string. Finally removes everything following the colon so that all that is left on the line is the pathname of the core file; xargs removes the file.

To free more disk space, look through the /tmp and /var/tmp directories for old temporary files and remove them. Keep track of disk usage in /var/mail, /var/spool, and /var/log.

# logrotate: MANAGES LOG FILES

Rather than truncating log files, you may want to keep these files for a while in case you need to refer to them. The logrotate utility manages log system (and other) files automatically by rotating (page 1170), compressing, mailing, and removing each file as you specify. The logrotate utility is controlled by the /etc/logrotate.conf file, which sets default values and can optionally specify files to be rotated. Typically logrotate.conf has an include statement that points to utility-specific files in /etc/logrotate.d/. Following is the default logrotate.conf:

```
$ cat /etc/logrotate.conf
# see "man logrotate" for details
# rotate log files weekly
# keep 4 weeks worth of backlogs
rotate 4
```
