
# There is a root account, but no root password

tip As installed, Ubuntu locks the root account by not providing a root password. This setup prevents anyone from logging into the root account (except when you run sudo [445]). There is, however, a root account (a user with the username root—look at the first line in /etc/passwd). This account/user owns files (give the command -l) and runs processes (give the command -ef and look at the left column of the output). The root account is critical to the functioning of an Ubuntu system.

The sudo enables you to run a command as though it had been run by a user logged in as root. This book uses the phrase "working with root privileges" to emphasize that, although you are not logged in root, when you use sudo you have the privileges of the root.

Ubuntu encourages the use of sudo. In fact, as shipped, Ubuntu locks the root account (there is no password) so you cannot use the classic techniques. Using sudo rather than the root account for system administration offers many advantages:

- When you run sudo, it requests your password—not the root password—so you have to remember only one password.
- The sudo utility logs all commands it executes. This can be useful for retracing your steps if you make a mistake and for system auditing.
- The sudo utility logs the username of a user who issues a sudo command. On systems with more than one administrator, this log tells you which users have issued sudo commands. Without sudo, you would not know which user issued a command while working with root privileges.
- The sudo allows implementation of a finer-grained security than the use of su and the root account. Using sudo, you can enable specific users to execute specific commands—something with the classic root account setup.
- Using sudo makes it harder for a malicious user to gain access to a system. When there is an unlocked root account, a malicious user knows the username of the account she wants to crack before she starts. When the root account is locked, the user has to determine the username and password to break into a system.

Some users question whether sudo is less secure than su. Both rely on passwords, they share the same strengths and weaknesses. However, if the password is compromised, the system is compromised. However, if the password of a user who allowed by sudo to do one task is the entire system may not be at risk. Thus, if used properly, the finer granularity of sudo's permissions structure can make it a more secure tool than su. Also, when sudo is used to invoke a single command, it is less likely that a user will be tempted to keep working with root privileges if the user opens a root shell with.

Using sudo may not always be the best, most secure way to set up a system. On a system used by a single user, there is not much difference between sudo and carefully using sudo and a root password.

## RUNNING COMMANDS WITH root PRIVILEGES

### Run graphical programs using gudo, sudo
gudo (kde-sudo of KDE) instead of sudo when you run a graphical program that requires root privileges (Try this with an argument). Although both run a program with root privileges, sudo uses your configuration files, whereas gudo uses root configuration files. Most of the time this difference is not important, sometimes it is critical. Some programs will not run when you call them with sudo. Using gudo can prevent incorrect permissions from being applied to files related to the X Window System in your home directory. In a few cases, misapplying these permissions can prevent you from logging back in. In addition, you can use gudo in a launcher (page 121) on the desktop or on a panel.

On a system with several users, and especially on a network of systems with central administration, sudo can be up to more secure than su. If you are a dyed-in-the-wall UNIX/Linux user who cannot get comfortable with sudo, it is easy enough to get the root account password and use sudo (page 431).

When you install Ubuntu, the first user you set up is included in the admin group. As installed, sudo is configured to allow members of the admin group to run with root privileges. Because there is no root password, initially only the first user to perform privileged administrative tasks from the command line is the first user to run using sudo. Graphical programs call other programs, such as gudo (the adjacent tip), which in turn call sudo authentication.

By default, sudo asks for your password (the root password) the first time you run it. At that time, sudo sets your timestamp. After you supply a password, sudo will not prompt you for again for 15 minutes, based on your timestamp.

In the following example, Sam tries to set the system clock while working as the user sam, a privileged user. The date utility displays an error message followed by the expanded version of the date Sam entered. When he uses sudo to run date the sudo prompts him for his password, and the command succeeds.

```
$ date 03111424
date: cannot set date: Operation not permitted
Thu Mar 11 14:24:00 PST 2010
```

```
$ sudo date 03111424
[sudo] password for sam:
Thu Mar 11 14:24:00 PST 2010
```

Next Sam uses sudo to unmount a filesystem. Because he gives this command within 15 minutes of the previous sudo command, he does not need to supply a password:

```
$ sudo umount /music
$
```

Now Sam uses the -l option to check which sudo will allow him to run. Because he was the first user registered on the system (and is therefore a member of the admin group), he is allowed to run any command as any user.

```
$ sudo -l
```
User may run the following commands on this host:
(ALL) ALL

### Spawning a root shell
When you have several commands you need to run with root privileges, it may be easier to spawn a root shell, give the commands without having to type sudo in front of each one, and exit from the shell. This technique defeats some of the safety safeguards built into sudo, so use it carefully and remember to return to a non-root shell as soon as possible. (See the caution on least privilege on page 420.) Use the sudo -i option to spawn a root shell:

```
$ pwd
/home/sam
$ sudo -i
# id
uid=0(root) gid=0(root) groups=(0)
# pwd
/root
# exit
$
```

In this example, sudo spawns a root shell, which displays a # prompt to remind you that you are running with root privileges. The id utility displays the identity of the user running shell. The exit command (you can also use CTRL-D) terminates the root shell, returning the user to his normal status and former prompt.

### sudo's environment
The pwd builtin in the preceding example shows one aspect of the modified environment created by the -i option (page 425). This option spawns a root login shell (a shell with the same environment as a user logging in as root would have) and executes root's startup files (page 293). Before issuing the sudo -i command, the command shows /home/sam as Sam's working directory; after the command, it shows /root, root's home directory, as the working directory. Use the -s option (page 426) to spawn a root without modifying the environment. When you call sudo without an option, it runs the command you specify in an unmodified environment. To demonstrate this feature, the following example shows sudo pwd without an option. The working directory of a command run does not change that.

```
$ pwd
/home/sam
$ sudo pwd
/home/sam
```

### Redirecting output
The following command fails, although the shell that sudo spawns executes is with root privileges, the nonprivileged shell that the user is running redirects the output.

```
$ sudo ls > /root/ls
bash: /root/ls: Permission denied
```

There are several ways around this problem. The easiest is to pass the whole line to a shell:

```
$ sudo bash -c 'ls > /root/ls'
```

The bash -c option spawns a shell that executes the string following the option and terminates. The sudo utility runs the spawned shell with root privileges. You can quote the string to prevent the unprivileged shell from interpreting special characters. (See the preceding section.) Another way to deal with the problem of redirecting output of command run is to use tee (page 254):

```
$ ls | sudo tee /root/ls
```

This writes the output of ls to the file but also displays it. If you do not want to display the output, have the nonprivileged redirect the output to /dev/null (page 489). The next example uses this technique to do away with screen output and uses the -a option to append to the file instead of overwriting:

```
$ ls | sudo tee -a /root/ls > /dev/null
```

## OPTIONS

You can use command-line options to control how sudo runs a command. The syntax of sudo command is sudo [options] [command] where options is one or more options and command is the command you want to execute. Without the -u option, sudo runs command with root privileges. Some of the more common options follow; see the sudo man page for a complete list.

- b (background) Runs command in the background.
- e (edit) With this option, command is a filename and not a command. This option causes sudo to edit the file named command with root privileges using the editor named by SUDO_EDITOR, VISUAL, or EDITOR environment variable. It uses the nano editor by default. Alternatively, use the sudoedit utility with any options.
- i (initial login environment) spawns the shell that is specified for root (or another user specified by -u) in /etc/passwd, running root's (or the other user's) startup files, with some exceptions (e.g., TERM is not set). Does not take a command.
- k (kill) Resets the timestamp (page 423) of the user running the command, which means the user must enter a password the next time he runs sudo.
- l (list defaults) Lists the parameters that you can set on a Defaults line (page 429) in the sudoers file. Does not take a command.
- L (list commands) Lists the users who is running sudo is allowed to run on the local system. Does not take a command.
