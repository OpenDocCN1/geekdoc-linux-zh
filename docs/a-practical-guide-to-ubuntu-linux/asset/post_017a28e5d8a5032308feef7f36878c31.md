
fqdn (fully qualified domain name) Performs DNS lookups on FQDNs (page 1149) in the sudoers file. When this flag is set, you can use FQDNs in the sudoers file, but doing so may negatively affect sudo's performance, especially if DNS is not working. If this flag is set, you must use the local host's DNS name, not an alias. If host returns a FQDN, you do not need to set this flag. The default is off.

insults Displays mild, hurtful insults when a user enters a wrong password. The default is also off. See passed_tries.

lecture=freq Controls when sudo displays a reminder message before the password prompt. Possible values of freq are never (default), once, and always. Specifying !lecture is same as specifying freq of never.

mail_always Sends to the mailto each time a user runs sudo. The default is off.

mail_badpass Sends to the mailto user when a user enters an incorrect password while running sudo. The default is off.

mail_no_host Sends to the mailto user when whose username is in the sudoers file who does not have permission to run commands on the local host runs sudo. The default is off.

mail_no_perms Sends to the mailto user when whose username is in the sudoers file who does not have permission to run the requested command runs sudo. The default is off.

mail_no_user Sends to the mailto user when whose username is not in the sudoers file runs sudo. The default is off.

mailsub=subj (mail subject) Changes the default email subject for warning and error messages from the default *** SECURITY information for %sh *** subj. The utility expands %sh within subj to the local system's hostname. Place subj between quotation marks if it contains special characters (page 160).

mailto=eadd Sudo warning and error messages to eadd (an email address); the default is root). Place eadd between quotation marks if it contains special characters.

passwd_tries=num Num the number of times the user can enter an incorrect password in response to the sudo password prompt before sudo quits. The default is 3. See also insults and lecture.

# Using the root password in place of your password

tip If you set up a root password (page 431), you can use graphical programs that require a password to recover the root password in place of the password of the user who is running the program by running rootpw. The programs will ask for your password, but will accept only the root password. Making this change causes an Ubuntu system to use the root password in a manner similar to the way other distributions use this password.

rootpw Causes sudo to accept only the root password in response to its prompt. Because sudo issues the same prompt whether it is asking for your password or the root password, turning this flag on may confuse users. **Do not turn on this flag if you have not unlocked the root account** (page 431), as you will not be able to use sudo. To fix this problem, bring the system up in recovery mode (page 245) and turn off (remove) this flag. The default is off, causing sudo to prompt for the password of the user running sudo. See the preceding tip.

shell_noargs Uses sudo, when called without any arguments, to spawn a root shell without changing the environment. The default is off. This option is the same as the sudo -s option.

timestamp_timeout=mins The mins is the number of minutes that the sudo timestamp (page 423) is valid. The default is 15; set mins to -1 to cause the timestamp to be valid forever.

tty_tickets Uses sudo to authenticate users on a per-tty basis, not a per-user basis.

umask=val Val the umask (page 459) that uses sudo to run the command that the user specifies. Set val to 0777 to preserve the user's umask value. The default is 0022.

# UNLOCKING THE ROOT ACCOUNT (ASSIGNING A PASSWORD TO ROOT)

Except for a few instances, there is no need to unlock the root account on an Ubuntu system; in fact, Ubuntu suggests that you do not so. The following command unlocks the root account by assigning a password to it:

```bash
$ sudo passwd root
Enter new UNIX password:
Retype new UNIX password:
password: password updated successfully
```

Relocking the root If you decide you want to lock the root account after unlocking it, give the command sudo passwd -l root. You can unlock it again with the preceding command.

# SU: GIVES ANOTHER USER’S PRIVILEGES

To use sudo to gain root privileges, you must unlock the root account (as discussed in the preceding section).

The su (substitute user) utility can spawn a shell or execute a program with the identity and privileges of a specified user. Follow su on the command line with the name of the user; if you are working with root privileges or if you know the user's password, you will then take the identity of that user. When you give a command without an argument, su defaults to spawning a shell with root privileges (you have to know the root password).

When you give a command to work as root, it spawns a new shell, which displays the # prompt. You can return to your normal status (and your former shell and prompt) by terminating this shell: Press CTRL-D or give an exit command. Giving an command by itself changes your user and group IDs but makes minimal changes to the environment. For example, PATH has the same value as it did before you gave the su command. When you give the command su -l or --login (in the hyphen), you get a root login shell: It is as you logged in as root. Not only do the shell's user and group IDs match of root, but the environment is identical to that of root. The login shell executes the appropriate startup files (page 293) before displaying a prompt.

The id utility displays the changes in your user and group IDs in the groups you are associated with:

```bash
$ id
uid=1002(sam) gid=1002(sam) groups=117(admin),1002(sam)
$ 
# id
uid=0(root) gid=0(root) groups=0(root)
```

You can use su with the -c option to run a command with root returning to the original shell when the command finishes executing. The following example shows that a user is not permitted to kill (page 455) a process. With the use of su -c and the root password, however, the user is permitted to kill the process. The quotation marks are necessary because su -c takes its command as a single argument.

```bash
$ kill -15 4982
-bash: kill: (4982): Operation not permitted
$ su -c "kill -15 4982"
```

# UPSTART EVENT-BASED DAEMON

The Upstart init daemon is event based and runs specified programs when the system changes. Instead of starting and stopping services only when the runlevel changes, Upstart can start and stop services when it learns from udev (page 502) a filesystem, printer, or other device has been added or removed from the system. Such a change is called an event. For example, Upstart can start and stop services when the system boots, when the system is shut down, or when a job changes.

Changing from Sysinit to Upstart involves many parts of the Linux system. To make the switch smooth and to introduce as few errors as possible, the Upstart team elected to make this transition over several releases.

Ubuntu has been moving away from the Sysinit setup and toward the cleaner, flexible Upstart setup. As more services are under control of Upstart, entries in the init directory (see the tip on page 440) will replace the contents of the /etc/init.d and /etc/rc. directories. Runlevels will no longer be a formal feature of Ubuntu, although they will be maintained for compatibility with third-party software. Upstart will also respond cron.

# SOFTWARE PACKAGE

The Upstart system is contained in one package, which is installed by default:

-   upstart—Provides the Upstart init daemon and initctl utility.

# DEFINITIONS

Events An event is a change in state that can be communicated to init. Almost any change in state—either internal or external to the system—the startup event can trigger an event. For example, the boot loader triggers the startup event (startup man page) and the tell command (page 444) triggers the runlevel event (page 444). Removing and installing a hotplug (page 502) or USB device (such as a printer) can trigger an event as well. You can also trigger an event manually by giving the initctl command (page 436). For more information refer to “Events” on page 437.

Jobs A job is a series of instructions that init reads. These instructions typically include a program (binary file or shell script) and the name of an event. The Upstart init daemon runs the program when it is triggered. You can run and stop a job manually by giving the initctl start and stop commands, respectively (page 436).
