The named.conf.default-zones file holds the following Zone clauses:

- (Name of the zone is a period.) The hint zone. Specifies when the server starts or does not know which server to query, it should look in the /etc/bind/db.root file to find the addresses of authoritative servers for the root domain.
- localhost—Sets up the normal server on the local system.
- 127.in.addr.arpa—Sets up IPv4 reverse name resolution.
- 0.in-addr.arpa—Specifies that the local server handle reverse lookup for IP addresses starting with 0, thereby preventing the local server from looking upstream for this information.
- 255.in.addr.arpa—Specifies that the local server handle reverse lookup for IP addresses starting with 255, preventing the local server from looking upstream for this information.

# named.conf.options: OPTIONS FILE

named.conf.options file, which named.conf incorporates with an include statement, holds mostly comments with the following uncommented statements:

```
directory "/var/cache/bind";
auth-nxdomain no; # conform to RFC1035
listen-v6 { any; };
```

The directory statement specifies that all relative pathnames in this file, named.conf, and all other files incorporated in named.conf are relative to. If you are running named in a chroot jail, this directory is located under /var/lib/named (page 847). The auth-nxdomain statement does not allow the server to answer authoratively on NXDOMAIN (nonexistent domain error; negative caching [page 1161]) answers. The listen-v6 { any; } enables the server to listen for IPv6 queries on any address. Change any to none to change the server not to listen for IPv6 queries.

# ZONE FILES

There are five zones in /etc/bind, each of which corresponds to one of the Zone zones. This section describes three of these zone files.

The hint zone file, db.root, is similar to the output of a dig @root-servers.net command, which does not change frequently (check the date on the last update near the beginning of the file). It specifies authoritative servers for the root domain. The DNS server initializes its cache from this file and can determine an authority for any domain from this information.

**db.local** The **db.local** file defines the localhost, the normal server on the local system. It starts with a `$TTL` directive and holds four resource records: SOA, NS, A, and AAAA. The `$TTL` directive in the following file specifies that the default time for the resource records in this file is 604,800 seconds (one week):

```
$ cat /etc/bind/db.local
; BIND data for local loopback interface
$TTL 604800 localhost.root.localhost. (
IN SOA : Serial
604800 : Refresh
86400 : Retry
241920 : Expire
604800 ) : Cache TTL
@ IN NS localhost.
IN A 127.0.1
IN AAAA ::1
```

As earlier, the @ stands for the origin (the name of the zone), which is localhost, as specified in named.conf. The last three lines are the NS resource record that specifies the nameserver for the zone as localhost, A resource record that specifies the IPv4 address of the host as 127.0.1, and the AAAA resource record that specifies the IPv6 address of the host as ::1.

The db.127. zone file provides information for the 127.in.addr.arpa reverse lookup zone. It follows the same pattern as the localhost zone, with one exception: Instead of the A resource record, this file has a PTR resource record that provides the name associates with the IP address. The PTR resource record specifies the name 1.0.0, which equates the system at address 1.0.0 in the zone (127.in-addr.arpa) with the name localhost, which has an address of 127.0.1.

```
$ cat /etc/bind/db.127
; BIND reverse data file for local loopback interface
TTL 604800 localhost.root.localhost. (
@ IN SOA : Serial
      604800 : Refresh
      86400 : Retry
      241920 : Expire
      604800 ) : Negative Cache TTL
```

The other zones perform similar functions as described on page 84. One named is started (page 834), you can use the tests described under “Troubleshooting” on page 849 to make sure the server is working.

# DNS GLUE RECORDS

It is common practice to put the nameserver for a zone inside the zone it serves. For example, you might put the nameserver for the zone starting at site1.example.com (Figure 24-3, page 825) in ns.site1.example.com. When a DNS cache tries to resolve www.site1.example.com, the authoritative server for example.com gives the NS record pointing to ns.site1.example.com. In an attempt to resolve ns.site1.example.com, the DNS cache again queries the authoritative server for example.com, which points to ns.site1.example.com. The simplest solution to this problem is to prevent any nameserver from residing inside the delegating zone.
