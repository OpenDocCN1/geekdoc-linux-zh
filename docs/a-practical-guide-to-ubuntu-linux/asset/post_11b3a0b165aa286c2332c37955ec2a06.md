# Security and the X -nolisten tcp option

In a production environment, if you need to place an X server and the clients on different systems, it is best to forward (tunnel) X over ssh. This setup provides a secure, encrypted connection. The method described in this section is useful on local, secure networks and for understanding how X works. See "Forwarding X11" on page 681 for information on setting up ssh to forwards X.

# The X -nolisten tcp Option

As Ubuntu is installed, the X server starts with the -nolisten tcp option, which protects the X server by preventing TCP connections to the X server. To connect to a remote X server, you must turn this option off the server. To turn it off, while working with root, create a file /etc/gdm/custom.conf with the following lines:

```
max@tty:~$ cat /etc/gdm/custom.conf
[security]
DisallowTCP=false
```

Reboot the system to restart the X server and gdm (gdm-binary) to effect this change. See library.gnome.org/admin/gdm/2.28/configuration.html#daemonconfig for more information.

# xhost GRANTS ACCESS TO A DISPLAY

As installed, xhost protects each user's X server. A user who wants to grant access to his X server needs to run xhost. Assume Max is logged in on the system and tiny wants to allow a user on dog to use his display (X server). Max runs this command:

```
max@tty:~$ xhost +dog
dog being added to access control list
access control enabled, only authorized clients can connect
INET:dog
```

Without any arguments, xhost describes its state. In the preceding example, INET indicates if Max wants to allow all systems to access his display, he can give the following command:

# $ xhost +

access control disabled, clients can connect from any host

If you frequently work with other users via a network, you might find convenient to add an xhost to your line .bash_profile (page 293)—but see the tip on the next page regarding security and granting access to your X display with xhost; if another system has access to your display, you may find your work frequently interrupted.

# Security and xhost

Giving a remote system access to your display using xhost means any user on the remote system can watch everything you type in a terminal window, including passwords. For this reason, software packages, such as the Tcl/Tk development system (www.tcl.tk), restrict their capabilities when xhost permits remote access to the server. If you are concerned about security or want to take full advantage of systems such as Tcl/Tk, you should use a safer means of granting remote access to your X session. See the xauth man page for information about a more secure replacement for xhost.

# THE DISPLAY VARIABLE

The most common method of identifying a display is to use the DISPLAY environment variable to hold the X server ID. This locally unique identification is automatically set up when the X server starts. The DISPLAY variable holds the screen number of a display:

```
$ echo $DISPLAY
local:0
```

The format of the complete (globally unique) ID string for a display is

[hostname]:display-number[.screen-number]

where hostname is the name of the system running the X server, display-number is the number of the logical (physical) display (0 unless multiple monitors or graphical terminals are attached to the system, or if you are running over ssh), and screennumber is the logical number of the (virtual) terminal (0 unless you are running multiple instances of X). When you are working with a single physical screen, you can shorten the identification string. For example, you can use tiny:0 or tiny:id to identify only the physical display on the system named tiny. When the server and the X clients are running on the same system, you can shorten this identification even further to :0.0. An ssh connection uses DISPLAY as localhost:10.0. You may have to use ssh -X to see this value. "X11 forwarding" on page 664 for information on setting up ssh so that it forwards X.

If DISPLAY is empty or not set, the screen you are working from is not running X. An application (the X client) uses the value of the DISPLAY variable to determine which display, keyboard, and mouse (collectively, the X server) to use. One way to run an application, such as gnome-calculator, on the local system but use the X display on a remote system is to change the value of the DISPLAY variable on the client system so it identifies the remote server.

```
$sam@~$ export DISPLAY=tiny:0.0
sam@~$ gnome-calculator &
```

The preceding example shows running gnome-calculator with the default X server running on the system named tiny. After setting the DISPLAY variable to the tiny server, all programs (clients) start using tiny as their server (i.e., output appears on tiny's display and input comes from tiny's keyboard and mouse). Try running xterm in place of gnome-calculator and see which keyboard accepts input. If this example generates an error, refer to the preceding sections, which explain how to set up the server to allow a remote system to connect to it.
