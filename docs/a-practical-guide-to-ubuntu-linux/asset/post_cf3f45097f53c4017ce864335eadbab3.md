SOA Start of Authority Designates the start of a zone. Each zone must have exactly one SOA record. An authoritative server maintains the SOA record for the zone it is authoritative for.
All files must have one SOA resource record, which must be the first resource in the file. The Name field holds the name of the domain at the start of the zone. The Data field holds the name of the host was created on, the email address of the person responsible for the zone, and the following information, which must be enclosed within parentheses if the record does not fit on one line. If this information is enclosed within parentheses (and it usually is), the opening parenthesis must appear on the first physical line of the SOA record:

- serial A in the range 1 to 2,147,483,647. A change in this number indicates the zone has changed. By convention, this field is set to the string yyyymmddann (year, month, day, change number). Along with the date, the final two digits—that is, the change-day—should be incremented each time you change the SOA record.

- refresh The elapsed time after the primary master server notifies slave (secondary) servers to refresh the record; and the time of updates between them.

- retry The time to wait after a refresh fails before trying to refresh again.

- expire The elapsed time after the zone is no longer authoritative and the root servers must be queried. The expire applies to slave servers only.

- minimum The negative caching (caching NXDOMAIN TTLs) TTL, which is the amount of time that a nonexistent domain error (NXDOMAIN) can be held in a slave server's cache. negative caching TTL is the same as a normal TTL except it applies to domains that do not exist rather than domains that do.

The TTL directive (page 839) defines the zone TTL (the maximum amount of time days in a slave server's cache). Jointly, the default zone TTL and the negative TTL encompasses all types of records the server can generate. If you will be adding domains or modifying existing domains frequently, the negative TTL to a low number. A short TTL increases traffic for DNS for clients requesting that do not exist, but allows domains to propagate quickly, albeit at the expense of increased traffic.

The two SOA resource records are equivalent (the parents in the first record are optional because the record fits on one physical line:

```
@ IN SOA ns.zach.net. sobel.com. ( 2010111247 8H 2W 1D )
@ IN SOA ns.zach.net. sobel.com. (
 : serial 2010111247
8H : refresh
2H : retry
4W : expire
1D : minimum
)
```

TXT Associates a character string with a domain. The Name field holds the domain name. data can contain up to 256 characters and must be enclosed within quotation marks. TXT records can contain any arbitrary text value. As general information, they can be used for things such as public key distribution. Following is a TXT resource record that specifies a company name:

```
zach.net IN TXT "Sobell Associates Inc."
```

# DNS QUERIES AND RESPONSES

Queries A DNS query has three parts:

1. Domain name, FQDN, or IP address for reverse name resolution
2. Type—Type of record requested (page 827)
3. Class—Always IN for Internet

Most DNS servers store in cache memory the query responses from other DNS servers. When a DNS server receives a query, it first tries to resolve the query from its cache. If attempt fails, the server may query other servers to get an answer. Because DNS uses cache, when you make a change to a DNS record, the change takes time—sometimes a matter of days—to propagate throughout the DNS hierarchy.

Responses A DNS message sent in response to a query can hold the following records:

- Header record—Information about this message
- Query record—Repeats the query
- Answer records—Resource records that answer the query
- Authority records—Resource records for servers that have authority for the answers
- Additional records—Additional resource records, such as NS records

The dig utility does not consult /etc/nswitch.conf (page 475) to determine which server to query. The following example uses dig to query a DNS server. The +all option causes dig to query for all records.

# Reverse Name Resolution

In addition to normal or forward name resolution, DNS provides reverse name resolution (also referred to as inverse mapping or reverse mapping) so you can look up domain names given an IP address. Because resource records in the forward DNS database are indexed hierarchically by domain name, DNS cannot perform efficient search by IP address on this domain.

DNS reverses name resolution by means of special domains named in-addr.arpa (IPv4) and ip6.int (IPv6). Resource records in these domains have fields that hold IP addresses; the records are indexed hierarchically by IP address. Data fields hold the FQDNs correspond to these IP addresses.

Reverse name resolution can verify that someone is who he is or at the domain he says he is. In general, it allows a server to retrieve and record the domain names of the clients it provides services to. For example, legitimate mail contains the domain of the sender and the IP address of the sending machine. A mail server can verify the stated domain of a sender by checking the domain associated with the IP address. Reverse name resolution can also be used by anonymous FTP servers to verify that a domain in an email address used as a password is legitimate.
