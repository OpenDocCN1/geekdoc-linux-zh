## When you encrypt your personal key

The private part of the key is kept in a file that only you can read. If a malicious user compromises your account, an account that can use sudo to gain root privileges, or the root account on the local system, then has access to your account on the remote system because she can read the part of your personal key.

Encrypting the private part of your personal key protects the key and, therefore, restricts access to the remote system should someone compromise your local account. However, if your personal key is encrypted, you must supply the passphrase you used to encrypt the key each time you use the key, negating the benefit of not having to type a password when logging in to the remote system. Also, most passphrases that you remember can be cracked quite quickly by a powerful computer.

A better idea is to store the private keys on a removable medium, such as a USB flash drive, and use ~/.ssh directory as the mount point for the filesystem stored on your drive. You may encrypt these keys with a passphrase in case you lose the flash drive.

```
The ssh-keygen utility generates two keys: a private key or identification in ~/.ssh/id_rsa and a public key in ~/.ssh/id_rsa.pub. No one except the owner should be able to write to either of these, and only the owner should be able to read from the private key file.
```

To enable you to log in to files and from another system without supplying a password, first create a ~/.ssh directory with permissions set to 700 on the server (remote system). Next copy ~/.ssh/id_rsa.pub from the client (local system) to a file named ~/.ssh/authorized_keys on the server (remote system). Set its permissions to 600 so that no one except the owner can read or write to this file. Now when you run ssh or scp to the server, you do not have to supply a password. To make the server even more secure, you can disable password authentication by setting PasswordAuthentication to no in /etc/ssh/sshd_config (remove the # from the beginning of the PasswordAuthentication line and change the yes to no; page 680).

## COMMAND-LINE OPTIONS

Command-line options override defaults in the configuration files. Following are descriptions of some of the more useful ssh options.

- -d (debug) Sets debug mode so that sshd sends messages to the system log and the server stays in the foreground (-D). You can specify this option a maximum of three times to increase the verbosity of the output. See also -e. (the ssh client uses -v for debugging; see page 672.)

- -e (error) Sends output to normal error, not to the system log. Use with -d.

- -f Files file as the default configuration file instead of /etc/ssh/sshd_config.

## SETTING UP AN OPENSSH SERVER (sshd)

- -t (test) Checks the configuration file syntax and the sanity of the key files.
- -D (noDetach) Keeps sshd in the foreground. Useful for debugging; implied by -d.

## /etc/ssh/sshd_config Configuration File

The /etc/ssh/sshd_config configuration file contains one-line declarations. Each of these declarations starts with a keyword that is not sensitive, followed by whitespace, followed by case-sensitive arguments. You must reload the sshd server before these changes take effect.

AllowUsers userlist
The userlist is a space-separated list of usernames which specifies users are allowed to log in using ssh. This list can contain * and ? wildcards. You can specify a user as user or user@host. If you use the second format, make sure you specify the host as returned by hostname. Without this declaration, any user who can locally log in using OpenSSH client.

ClientAliveCountMax n
The specifies the number of client-alive messages that can be sent without receiving a response before sshd disconnects from the client. See ClientAliveInterval. The default is 3.

ClientAliveInterval n
Sends a message through the encrypted channel after n seconds of receiving a message from the client. See ClientAliveCountMax. The default is 0, meaning that no messages are sent.

This declaration passes messages over the encrypted channel (application layer; page 380) and is not susceptible to IP spoofing (page 1154). It differs from TCP-KeepAlive, which uses the TCP keepalive option (transport layer; page 380) and is susceptible to IP spoofing.

Deny userlist
The userlist is a space-separated list of usernames specifies users who are not allowed to log in using ssh. This list can contain * and ? wildcards. You can specify a user as user or user@host. If you use the second format, make sure you specify the host as returned by hostname.

HostBasedAuthentication yes
Tries hosts and /etc/hosts.equiv authentication when set to yes. For a more secure system, set this declaration to no (default).

IgnoreHosts yes no
Ignores .hosts and .hosts files for authentication. Does not affect the use of /etc/hosts.equiv and /etc/ssh/shosts.equiv files for authentication. For a more secure system, set this declaration to no (default).

LoginGraceTime n
Waits n seconds for a user to log in on the server before disconnecting. There is no time limit. The default is 120 seconds.

LogLevel val Specifies how detailed the log messages are. Choose val from QUIET, FATAL, ERROR, INFO (default), and VERBOSE.

PasswordAuthentication
Permits a user to use a password for authentication. For a more secure system, set up automatic login (page 677) and set this declaration to no. The default is yes.

PermitEmptyPasswords
Permits a user to log in on an account that has an empty password. The default is no.

PermitRootLogin
Permits root to log in using an OpenSSH client. Given the number of brute-force attacks on a typically system connected to the Internet, it is important to set this declaration to no. (How you set this declaration is not an issue if the root account locked.) The default is yes.

Port num
Specifies that the ssh server listens on port num. It may improve security to change num to a nonstandard port. The default is 22.

StrictModes yes no
Checks modes and ownership of the user's home directory and files. Login fails for users other than one if the directories and/or files can be written by anyone other than the owner.

This declaration passes messages over the encrypted channel (application layer; page 380) and is not susceptible to IP spoofing (page 1154). It differs from TCP-KeepAlive, which uses the TCP keepalive option (transport layer; page 380) and is susceptible to IP spoofing.
