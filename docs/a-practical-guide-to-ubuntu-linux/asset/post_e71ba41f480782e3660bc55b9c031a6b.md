
# /etc/exports: HOLDS A LIST OF EXPORTED DIRECTORY HIERARCHIES

The /etc/exports file is the access control list for exported directory hierarchies that NFS clients mount; it is the only file you need to edit to set up an NFS server. The exports utility (page 791) reads this file when it updates the files in /var/lib/nfs (page 789), which the kernel uses to keep its mount table current. The exports file controls the following NFS characteristics:

- Which clients can access the server (see also "Security" on page 776)
- Which directory hierarchies are on the server each client can access
- How each client can access each directory hierarchy
- How client usernames are mapped to server usernames
- Various NFS parameters

Each line in the file has the following format:

```
export-pointclient1 (option-list) [client2(option-list) ... ]
```

where export-point is the absolute pathname of the root directory of the directory hierarchy that is exported. The client-names are the names or IP addresses of one or more clients, specified by SPACE, that are allowed to mount the export-point. The option-list, described in the next section, is a comma-separated list of options that applies to the preceding client; it must not contain any SPACE. There must be no SPACE between each client name and the parenthesis that starts the option-list.

You can use shares-admin (page 783) to make changes to exports or edit this file manually. The following exports files grant read and write access to /home, and jam and the system at 192.168.0.12 read and write access to /pl16:

```
$ cat /etc/exports
/home /grape(rw,no_subtree_check)
/pl16 192.168.0.12(rw,no_subtree_check) jam(rw,no_subtree_check)
```

The specified directories are on the local server. In this case, access is implicitly granted for the directory hierarchy exported at the directory. You can specify IP addresses or hostnames and you can specify more than one client system on a line. By default, directory hierarchies are exported in readonly mode. The current version of exports complains when you do not specify either subtree_check or no_subtree_check (page 78).

## GENERAL OPTIONS

The left column of this section lists default options, followed by nondefault options enclosed in parentheses. Refer to the exports man for more information.

auth_nlm (no_auth_nlm) causes the server to require authentication of lock requests (using the NLM [NFS Lock Manager] protocol). Use no_auth_nlm for clients when you find that only files that anyone can read can be locked.

## SETTING UP AN NFS SERVER 

**mountpoint=[path]** Allows a directory to be exported only if it has been mounted. This option prevents a mount point that does not have a directory hierarchy mounted on it being exported and prevents the underlying mount point from being exported. Also **mp**.

**nohide (hide)** When a server exports two directory hierarchies, one of which is mounted on the other, a client must have both directory hierarchies explicitly mounted to access both. When the second (child) directory hierarchy is not explicitly mounted, its mount point appears as an empty directory and the directory hierarchy is hidden. The **nohide** option causes the underlying second directory hierarchy to appear when it is not explicitly mounted, but this option does not work in all cases.

**ro (readonly)** Permits only read requests on an NFS hierarchy. **Use rw** to permit read and write requests.

**secure (insecure)** Requires NFS to originate on a *privileged port* (page 1160) as a program running without *root* privileges cannot mount a directory hierarchy. This option does not guarantee a secure connection.

**no_subtree_check (subtree_check)** Checks for valid files. As you have exported a directory hierarchy that has its root below the root of the filesystem that holds it (that is, an exported subdirectory of a filesystem). When the NFS server receives a request for a file in that hierarchy, it performs a subtree check to confirm the file is in the exported directory hierarchy.

Subtree checking can cause problems with files that are renamed while opened, and when *no_root_squash* is used, only a process running with *root* privileges can access. The **no_subtree_check** option disables subtree checking and can improve reliability in some cases.

For example, you may need to disable subtree checking for home directories. Home directories are frequently subtrees (of */home/), are written to often, and can have files within them frequently renamed. You would probably not need to disable subtree checking for directory hierarchies that contain files that are most read, such as */usr/.

Because the default has changed (it is now **no_subtree_check**), exports displays a warning when you do not specify either **subtree_check** or **no_subtree_check**.

**sync (async)** Specifies that the server should reply to requests only after disk changes made by the request are written. The **async** option specifies that the server does not have to wait for information to be written and can improve performance, at the cost of possible data corruption if the server crashes or the connection is interrupted.

**wdelay (write delay)** Causes the server to delay committing write requests when it anticipates that another, related request will follow, thereby improving performance by committing multiple write requests within a single operation. The **no_wdelay** option does not delay committing write requests and can improve performance when the server receives multiple, small, unrelated requests.

Use the anonym and anagid options to override these values. Maps requests from root on a remote system so they appear from the UID 65534, a nonprivileged user on the local system, or as specified by anon. The **no_root_squash** option turns off this mapping so that requests from root appear from root.

**all_squash** Does not change the mapping of users making requests to the NFS server. (all_squash) option maps all users—just root—to the anonymous account. Set the UID and GID of the anonymous account to un or gn, respectively. NFS uses these accounts when it does not recognize an incoming UID and GID and when it is instructed to do so.

## The System Keeps Mount Information

A server holds lists of directory hierarchies it can export. The list that you as system administrator works with is /etc/exports. The following discussion assumes that the local server, plum, is exporting these directory hierarchies:

```
$ cat /etc/exports
/home /grape(rw,no_subtree_check)
/pl16 192.168.0.12(rw,no_subtree_check) jam(rw,no_subtree_check)
```

As explained in more detail on page 791, exports displays the list of exported directory hierarchies:

```
$ exportfs
/home grape
/pl16 jam
192.168.0.12
```

The important files and pseudofs that NFS works with are described next.

/var/lib/nfs/stab (export table) On the server, lists the directory hierarchies that are exported (can be mounted, but are not necessarily mounted at the moment) and the options they are exported with:

```
$ cat /var/lib/nfs/stab
/home grape(rw,wdelay,hide,nocrossmnt,secure,root_squash,no_all_squash,no_subtree_check,secure_locks,acl,mapping=identity,anouid=65534,anongid=65534)
/pl16 jam(rw,wdelay,hide,nocrossmnt,secure,root_squash,no_all_squash,no_subtree_check,secure_locks,acl,mapping=identity,anouid=65534,anongid=65534)
/pl16 192.168.0.12(rw,wdelay,hide,nocrossmnt,secure,root_squash,no_all_squash,no_subtree_check,secure_locks,acl,mapping=identity,anouid=65534,anongid=65534)
```

The stab file is initialized from /etc/exports when the system is brought up, read by plum when a client mounts a directory hierarchy, and modified by exportfs (page 791) as the list of exported directory hierarchies changes.
