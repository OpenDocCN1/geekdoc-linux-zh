## ~/.ssh: USER FILES

OpenSSH creates the ~/.ssh directory and the known_hosts file therein automatically when a user connects to a remote system.

authorized_keys server Enables a user to log in or copy files to and from another without supplying a user login password (page 677). However, the user may need to supply a passphrase, depending on how the key was set up. No one except the owner should be able to write to this file.

config client User's OpenSSH configuration file (page 674). Entries however override entries in /etc/ssh/ssh_config.

environment server Contains assignment statements that define environment variables on server when a user logs in ssh.

id_dsa client User authentication DSA keys generated by ssh-keygen (page 677). Both files id_dsa.pub public file should be owned by the user in whose home directory they appear. id_dsa.pub public file should be readable by anyone but writable by its owner (644 permissions). The id_dsa private file should not be readable or writable by anyone except its owner (600 permissions).

id_rsa client User authentication RSA keys generated by ssh-keygen (page 677). Both files id_rsa.pub public file should be owned by the user in whose home directory they appear. The id_rsa.pub public file should be readable by anyone but writable by its owner (644 permissions). The id_rsa private file should not be readable or writable by anyone except its owner (600 permissions).

known_hosts client Contains public keys (default) of hosts the user has connected to. SSH automatically adds entries each time the user connects to a new server (page 668). # Running the ssh, scp, and sftp OpenSSH Clients

This section covers up and using the ssh, scp, and sftp clients.

## Prerequisites

The openssh-client package is installed by default. You do not need to install any packages to run an OpenSSH client. There is no init script for OpenSSH clients.

## JumpStart: Using ssh and scp to connect to an OpenSSH Server

The ssh and scp clients do not require setup beyond the requisite package, although you can create and edit files that facilitate their use. To run a shell on securely copy a file to a remote system, the following criteria must be met: The remote system must be running the OpenSSH daemon (sshd), you must have an account on the remote system, and the server must properly identify itself to the client.

The following example shows Zach ssh to log in on the remote host named plum giving an exit command to return to the shell on the local system:

```
$ zach@plum
zach@plum's password:
Linux 2.6.27-1-generic #1 SMP Sat Aug 23 23:20 UTC 2008 
Last login: Mon Jan 18 21:58:22 192.168.0.12
zach@plum: exit
Connection to plum closed.
```

scp can use user (zach@plum) from the command line if you want to log in as yourself and have the same username as others. The first time you connect to a remote OpenSSH server, ssh or scp asks you to confirm that you are connected to the right system. Refer to "First time authentication" on page 668. The following example uses scp to copy from the working directory to Zach's home directory on plum:

```
$ scp zach@plum
zach@plum's password:
100% 2KB/s 0:00
```

# CONFIGURING OPENSSH CLIENTS

This section describes how to set up OpenSSH on the client side.

## RECOMMENDED SETTINGS

The configuration files provided by Ubuntu meet most needs. One OpenSSH parameter you may want to change is ForwardX11, which is set to yes by default. To increase security, and in some cases usability, set ForwardX11 (page 675) to no. See page 681 for more information about X11 forwarding.

Two files list the hosts you have connected to: ~/.ssh/known_hosts (user) and /etc/ssh/known_hosts (global). No one except the owner should have access to either of these files. No one except the owner should be able to write to these files. When you connect to an OpenSSH server for the first time, the OpenSSH client prompts you to confirm that you are connected to the server and can help prevent man-in-the-middle attack (footnote 3 on page 114):

> The authenticity of 'plum (192.168.0.10)' can't be established.
RSA key fingerprint is 9d:1b:5b:97:5c:80:e9:4b:41:9a:bc7
Are you sure you want to continue connecting (yes/no)? yes
Warning: Permanently added 'plum,192.168.0.10 (RSA)' to the list of hosts.

Before you respond to the preceding query, make sure you are logging in on the correct system and not an imposter. If you are not sure, call someone you know in that system to verify that you are on the intended system. When you answer yes (you must spell it out), the client appends the server's public host key (the line in /etc/ssh/ssh_rsa_key.pub or /etc/ssh/ssh_dsa_key.pub) to the server's ~/.ssh/known_hosts file on the local system, creating the ~/.ssh directory if necessary. So that it can keep track of which known_hosts applies to which server, OpenSSH prepends the name of the server and the server's IP address to the line.

When subsequently use OpenSSH to connect to that server, the client verifies that it is connected to the correct server by comparing this to the one supplied by the server. You can display the local system's RSA key using ssh-keygen:

```
$ ssh-keygen -f /etc/ssh/ssh_rsa_key.pub
2048 9d:1b:5b:97:5c:80:e9:4b:41:9a:bc7 /etc/ssh/ssh_rsa_key.pub (RSA)
```

The known_hosts file uses one or two long lines to identify each host it keeps track of. Each line starts with the hostname and IP address of the line it corresponds to, followed by the type of encryption used and the server's public key

Because it hashes hostname and IP address separately, OpenSSH puts lines in known_hosts for each host.
