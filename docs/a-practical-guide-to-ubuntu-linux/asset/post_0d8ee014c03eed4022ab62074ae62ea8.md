Answer y to this prompt when you are restoring entire filesystems or files that have been accidentally removed. Doing so will restore the appropriate permissions to the files and directories being restored. A variety of device names can access the /dev/st0. Each name accesses a different device number that controls some aspect of how the tape drive is used. After you complete a dump using /dev/st0, the tape drive automatically rewinds the tape. Use the nonrewinding SCSI tape device (/dev/nst0) to keep the tape rewinding on completion. This feature allows you to back up multiple filesystems to the same volume.

Following is an example of backing up a system where the /home, /usr, and /var directories reside on different filesystems:

```
$ dump -ouf /dev/nst0 /home
$ dump -ouf /dev/nst0 /usr
$ dump -ouf /dev/st0 /var
```

The preceding example uses the nonrewinding device for the first two dumps. If you are using the rewinding device, the tape rewinds after each dump, and you are left with only the last dump on the tape.

You can use mt (magnetic tape), which is part of the cio package, to manipulate files on a multivariable dump tape. The following mt command positions the tape (fsf 2 instructs mt to skip past two files, leaving the tape at the start of the third file). The restore command restores the /var filesystem from the previous example:

```
$ mt -f /dev/st0 fsf 2
$ dump restore rf /dev/st0
```

It is a good practice to schedule certain tasks to run automatically. For example, you may want to remove old core files once a week, summarize accounting data daily, and rotate system log files monthly.

## cron AND anacron: SCHEDULE ROUTINE TASKS

The cron daemon executes scheduled commands periodically. This daemon can execute commands at specific times on systems that are always running. The anacron utility executes scheduled commands when it is called. It works well on laptops and other systems that are not all on the time. The anacron init script, calls anacron, will not run commands when a system is running on batteries (i.e., not on AC).

## CRONTAB FILES

The cron daemon reads it to execute from personal crontab files in /var/spool/cron/crontab. Users can use the crontab utility to set up personal cron files are kept in the /etc/cron directory and in the /etc/crontab file. The term crontab has three meanings: It refers to a file in a specific format [a crontab], and it is the name of a file [/etc/crontab].

By default, Ubuntu is set up with no restrictions on how can cron run commands in the format. See cron.allow and cron.deny on page 491 for ways of restricting this access.

System crontab files specify how often cron is to run a command. In a system crontab file, such as /etc/crontab, has the following format:

minute day-of-month month day-of-week user command

The first five fields indicate when cron will execute the command. The minute is the number of minutes after the start of the hour, the hour is the hour of the day based on a 24-hour clock, the day-of-month is a number from 1 to 31, and the day-of-week is a number from 0 to 7, and 7 indicating Sunday. An asterisk (*) stands for any value in a field. The user is the username or ID of the user who will run it. Following are some examples:

```
* 20 1 * * root /usr/local/bin/checkit
25 9 17 * * /usr/local/bin/monthly.check
40 23 * * 7 root /usr/local/bin/sunday.check
```

All three lines run their commands with root privileges. The first line runs check every day at 1:20 AM. The second line runs monthly.check at 9:25 AM on 17 of every month. The third line runs sunday.check at 11:40 PM. Give the command man 5 crontab to obtain more information on crontab files.

User crontab files A user crontab file is a system file that it does not include the user field because it always runs as the user who created it. Users can work with their own crontab files by using the command crontab followed by -l to list the file, -r to remove the file, -e to edit the file. This command uses the nano editor; if you prefer, export (page 992) and use the VISUAL or EDITOR environment variable to the text editor of your choice. See the crontab man for more information.

/etc/crontab Following is the /etc/crontab file. Comments begin with a hashmark (#). The file sets SHELL and PATH (page 319) environment variables.

```
$ /etc/crontab
# /etc/crontab: system-wide crontab
# Unlike any other crontab you don't have to run the 'crontab'
# command to install the new version when you edit this file
# and files in /etc/cron.d. These files also have username,
# that none of the other crontabs do.
SHELL=/bin/sh
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/bin
```

## Running jobs at the right time

As installed, if the /usr/bin/anacron file is present and executable, cron uses anacron to run daily, weekly, and monthly jobs as soon as possible. Refer to "run-parts" on page 607 and the section on /etc/anontab. An easy way to get cron to run these jobs as scheduled in /etc/crontab is to change permissions on the file so it is not executable:

```
$ sudo chmod 644 /usr/bin/anacron
```

If you need to reanchor, change its permissions by 755.

## RUN OCCASIONAL TASKS

Like cron, at runs a job sometime in the future. Unlike cron, at runs a job only once. For instance, you can schedule an at job that will reboot the system at 3:00 AM (when all users are probably logged off)

```
$ at 3am
warning: commands will be executed using /bin/sh
at> reboot
at> CONTROL-<EOT>
job 1 2010-02-01 03:00
```

It is also possible to run an at job within an at job. For instance, an at job might check for new patches every 18 days—something that would be more difficult with cron. See the at man page for more information.

By default, Ubuntu is set up with restrictions that prevent some system accounts from running at. See @allow and at.deny on page 491 for more information.
