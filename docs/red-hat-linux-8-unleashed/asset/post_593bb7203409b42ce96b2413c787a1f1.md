
# Configuring Display Graphics

When you add or change the graphics devices used in your system after the initial Red Hat Linux installation, you must configure those devices. Adding or changing the display for a Red Hat system can be as simple as swapping out the monitor or replacing a display adapter. For Intel-based PCs, this can mean switching from the use of the motherboard's built-in display adapter (if available)—by inserting a graphics card in the Accelerated Graphics Port (AGP) or Peripheral Component Interface (PCI) slot—or adding a second display adapter to support the use of multiple display monitors for X sessions.

Although a display monitor can be easily disconnected or reattached to a running Red Hat Linux system, insertion or removal of a graphics display adapter will require downtime—the bane of academic, enterprise, corporate, or small-business operations.

# Red Hat Linux and KVM

Keyboard, video, and mouse (KVM) hardware provides the capability to quickly switch display and control banks of individual computers using a single monitor, keyboard, and pointer. This provides efficient organization and use of computers in larger installations, allows a single operator to perform system administration tasks without physically moving to each computer.

Using KVM can bring other costs. Eliminating the need for some monitors reduces the amount of storage required for the system and the amount of energy used to run and cool the system.

Red Hat Linux administrators should be careful to research any hardware compatibility before implementing KVM. Many switches work regardless of the operating system and application used; however, take time to research what keyboard and pointer devices you'll need to use (such as whether I/O, PS/2, or USB devices may be required). Some KVM switches come with some of an embedded operating system (even Linux) that provides hardware emulation; these switches will have power requirements.

Other issues to include cable construction, compatibility, and distance limitations, hardware software switch configuration (such as providing push-button or key-combination switching), and scalability.

If you use X and want to control the graphical desktops of remote hosts on your network, use x2 and X2vnc clients. Although not included with Red Hat, you can find clients at http://ftp.digital.com/pub/Digital/SRC/x2x/ and http://www.hubbe.net/~hubbe/x2vnc.html.

Smaller Red-hat users can avoid the use of KVM switching hardware by leveraging graphical networking features of X11, multiple terminal sessions, and virtual desktops. Text-based virtual consoles can also be used on servers or workstations that do not use X11 to manage computers or to receive messages from various services (such as email or Web services or the kernel). See Chapter 5, "First Steps to Linux," to learn more using virtual consoles. If you are limited to a single remote session window, use the screen command, a text-based window manager that allows a single terminal session to manage several shells. For additional information on using virtual consoles, see http://www.tlp.org/HOWTO/Keyboard-and-Console-HOWTO.html.

# Configuring Display Graphics

The Red Hat desktop is provided by the X Window System, a client and server software package that is configured to use your computer's video card, monitor, keyboard and mouse. If you use Red Hat's graphical desktop and kudzu (discussed earlier in this chapter) and change your graphics card, monitor, keyboard, or mouse, you might be asked to remove existing hardware configuration and reconfigure the new equipment when you boot Red Hat.

The details about configuring XFree86 for Red Hat Linux are covered in Chapter 6, but the basic utilities you can use to configure a new XF86Config file are:

- xf86config—A text-based X configuration tool
- redhat-config-xfree86—Red Hat's graphical configuration tool
- XFree86—The XFree86 server, which can be used to generate XF86Config file by probing installed hardware

> NOTE
> Connecting using an external monitor with a notebook can be convenient, especially if the external monitor provides a larger desktop than the notebook's built-in display. However, configuring an external display for a notebook can sometimes be a problem when using X11. The notebook's graphics chipset must be supported by an XFree86 driver module, and the module must enable switching or concurrent use of an external monitor. Fortunately, many notebook chipset manufacturers provide support information for configuring external displays. For example, if your notebook has a Neomagic chipset, use the internDisp and externDisp options in the XF86Config to enable use of an external display. Keep in mind that although Red Hat, Inc. encourages and supports XFree86 development and X graphics support, it does. See Chapter 6 for more information about Red Hat Linux and X.

Fortunately, creating a XF86Config file (found in the directory /etc/X11) is easily accomplished when installing Red Hat Linux. If a new video card or monitor is put in use before installation, it will most likely work because XFree86 supports many families and types of graphics chipsets. Although newer graphics chipsets might cause some display compatibility problems, it is usually possible to configure a basic working display using existing software. The XFree86 Project, Inc. and contributing developers do a great job of providing software that works with nearly every product on the market.

> NOTE
> If your equipment is problematic, you can purchase a commercial alternative X11 display from a vendor, such as Xi-Graphics, at http://xig.com. You can also check out MetroX, which has touchscreen support, and specialized versions of X for embedded software development at http://www.metrolink.com/products/metrox/metrox.html.

# CHAPTER 4 Post-Installation Configuration

If you are experiencing X11 problems during installation, skip the configuration. Boot Red Hat Linux, and then look for a document under /usr/X11R6/lib/X11/ directory with information about your computer's graphics card. Various README files with specifics about a particular chipset are included with XFree86. # Configuring Sound Devices

Most workstation users want to have a configured sound card working with Red Hat Linux. Sound support is generally configured when Red Hat Linux first boots (or during the install process if the sound card is recognized). This section shows how to configure sound for Red Hat using the text-based sndconfig command, or the graphical redhat config.

If you cannot configure sound for your system using Red Hat's software, turn to the Advanced Linux Architecture (ALSA) at http://www.alsa-project.org. Download and install the ALSA driver, libraries, and utilities using RPM packages, or build ALSA from source. One way to do this is to first download the compressed archives:

- alsa-driver-0.9.rc5.tar.bz2
- alsa-lib-0.9.rc5.tar.bz2
- alsa-utils-0.9.rc5.tar.bz2

The archives have been decompressed:

- tar xjvf alsa*driver*
- tar xjvf alsa*lib*
- tar xjvf alsa*utils*

Next, navigate to the resulting ALSA driver directory, and then configure, build, and install the driver:

- cd alsa*driver*; ./configure; make; make install

Do the same for ALSA software libraries, and then build and install the ALSA utility software. You can then use the modprobe command to load supporting kernel modules:

- modprobe snd-via8xx
- modprobe snd-pcm-oss
- modprobe snd-mixer-oss
- modprobe snd-seq-oss

This will initialize your soundcard (which ALSA numbers 0). To sound you, you should then use ALSA's alsixer command to unmute your soundcard's channels and save the settings using the alsactl command:

- alsactl store 0

The state of your soundcard will be saved in the file /etc/sound.state. These settings, as channel volumes, can be retrieved later using the restore option instead of store.

> NOTE
> You'll find complete documentation about the Linux kernel's sound support in various text files under the /usr/src/linux-2.4/Documentation/sound directory if you install the source code to Linux.

Configuration problems can arise, especially if your soundcard's manufacturer won't release specifications to help open source developers create working drivers. If your sound card is not recognized, or is recognized but won't work, and using ALSA fails, you can turn to commercial drivers from 4Front Technologies. These relatively inexpensive drivers support more than 350 sound systems and are installed, configured, and controlled using shell scripts. Browse to http://www.opensound.com for more information.

# Using Loadable Kernel Modules to Start Sound Service

Although support for sound cards can be compiled directly in the Linux kernel, loadable kernel modules are most used to start sound service. These modules are enabled by entries in /etc/modules.conf—similar to this example, which enables a SoundBlaster-compatible chipset:

```
alias sound-slot-0 sb
options sound dmabuf=1
alias synth op13
options opl3 io=0x388
options sb io=0x220 irq=5 dma=0 mpu_io=0x530
```
