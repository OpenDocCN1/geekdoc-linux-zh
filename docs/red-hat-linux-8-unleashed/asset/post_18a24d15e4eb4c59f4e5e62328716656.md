smtp.lion.org  smtp.cheetah.org

**FIGURE 19.1** A simple example of how email is successfully processed and sent to its destination.

- 1. user1@lion.org composes and sends an email message to user2@cheetah.org.
- 2. The MTA at lion.org receives user1's email message and queues it for delivery behind any other messages that are also waiting to go out.
- 3. The MTA at lion.org contacts the MTA at cheetah.org on port 25. After cheetah acknowledges the connection, the MTA at lion.org sends the mail message. After cheetah.org accepts and acknowledges receipt of the message, the connection is closed.
- 4. The MTA at cheetah.org places the mail message into user2's incoming mailbox, user2 is notified that she has new mail the next time she goes on.

Of course, several things can go wrong during this process:
If user2 doesn't exist at cheetah.org? In this case, the MTA at cheetah.org will reject the email and notify the MTA at lion.org of the problem. The MTA at lion.org will then generate an email message and send it to user1@lion.org, informing her that no user2 exists at cheetah.org (or perhaps just silently discard the message and give the sender no indication of the problem, depending on how the server is configured).
What happens if cheetah.org doesn't respond to lion.org's connection attempts? (Perhaps the server is down for maintenance.) The MTA at lion.org notifies the server that the initial delivery attempt has failed. Further attempts will be made at intervals decided by server administrator until the deadline is reached, and the sender will be notified that the mail is undeliverable.

# The Mail Transport Agent

Different MTAs are available for Red Hat, and each has its own strengths and weaknesses. Some are extremely powerful, but very difficult to configure and somewhat slow; others are very fast and easy to configure, but do not contain any features. The following sections provide more details about some of the more common MTAs available for use with Red Hat Linux.

# Sendmail

The vast majority of email traffic on the Internet is handled by an MTA called Sendmail, the default MTA shipped with Red Hat Linux (and a number of UNIX distributions). Sendmail has the advantage of being installed and well-supported in your Red Hat Linux system. The commercial version (not included with Red Hat) sports a GUI configuration utility, as well.

Sendmail is one of the oldest and most powerful MTAs in existence, but it has a few disadvantages. One is that it is somewhat slow: in a high load environment, other MTAs, including Postfix and Qmail, can typically handle a much greater volume of messages per second. Sendmail is also notoriously convoluted; configuration files are extremely cryptic. (The best-selling book on Sendmail is more than 1,000 pages in length.)

Fortunately, the default configuration of Sendmail works fine for most basic installations, and only minor changes are needed to configure it for a basic server installation. However, because of the complexity of advanced Sendmail configuration, many administrators choose to replace it with one of the alternative MTAs. (You learn the basics of configuring and using Sendmail in “Basic Sendmail Configuration and Operation,” later in this chapter.)

# Postfix

Postfix (originally released in 1998 as IBM Secure Mailer) is a popular Sendmail alternative; it's fast, secure, and easy to administer. Postfix is a drop-in replacement for Sendmail, and migrating a Sendmail installation to Postfix is relatively simple. Postfix uses a Sendmail wrapper (that's an interface for making other programs that think it is Sendmail) so that MUAs can communicate with it just as if they were communicating with Sendmail.

Because of the drop-in nature of Postfix, it is easy to migrate an existing Sendmail installation to Postfix without breaking existing scripts.

For enhanced security, many Postfix processes use the chroot facility (which restricts access to only specific parts of the filesystem) for improved security, and there are no setuid components in Postfix. If you are starting from scratch, Postfix might be a better choice than Sendmail.

# Qmail

Qmail is a direct competitor to Postfix. Postfix is designed to be easier to use than Sendmail, as well as faster and more secure. However, Qmail isn't a drop-in replacement for Sendmail, so migrating an existing Sendmail installation to Gmail isn't quite simple as migrating from Sendmail to Postfix. Qmail is relatively easy to administer, and integrates with a number of software add-ons, including Web mail systems and POP3 servers. Qmail is not provided as part of the Red Hat distribution, but is available from http://www.qmail.org/.

# MDIR Versus Mailbox

Qmail also introduced maildir

The traditional mbox format keeps all mail assigned to a folder as a single file and maintains an index of individual emails. With maildir, each mail folder has three subfolders: cur, new, and temp. Each email is kept in a separate, unique file. If you are running a large number of people, you should select a filesystem that can efficiently handle a large number of small files.

Mbox offers one major disadvantage. While you are accessing the monolithic mbox file that contains all your mail, suppose some type of corruption occurs, either to the file itself or the index. Recovery from this problem can be difficult. This is especially troublesome if the file is accessed over a network;

The maildir format offers several advantages. Since each email is a separate file, corruption of one file does not affect the others. Furthermore, maildir is much faster for systems with many users, as it doesn't have to lock the entire mailbox to add a new message. Maildir is also easier to back up and restore, as you can simply copy the files.

The choice between mbox and maildir depends on your needs. If you have a small number of users and few emails, mbox might be sufficient. But if you have a large number of users and high volume of mail, maildir is the better choice.

The maildir format is also more flexible. You can have multiple subfolders within each mail folder, which is useful if you want to organize your mail by category. For example, you could have one folder for work, another for personal, and another for junk.

The maildir format is designed to be highly scalable, and is used by many large-scale mail systems. If you are setting up a large-scale mail server, maildir is likely the best choice for you. In summary, while mbox and maildir both have advantages, maildir is generally the modern and robust option for most users.

# The Mail Delivery Agent

SMTP was designed to deliver mail to systems that are always connected. To accommodate this, many systems also include a mail delivery agent, or MDA. The MDA transfers mail between systems but does not provide an interface to the user. Procmail or Spassassin are examples of MDAs; both provide filtering services to the MTA.

The MDA uses POP3 and IMAP protocols for this (see the Note for more information on these protocols). In a manner similar to a post office, POP3 and IMAP implement a “store and forward” process that alleviates the need to maintain a local mail server. For example, dial-up users connect to their ISP’s mail server to retrieve mail using "Fetchmail to Retrieve Mail," later in this chapter.

# The Mail User Agent

The mail user agent, or MUA, is another necessary part of the email system. The MUA is a client that uses the email engine to compose and provides the user interface. If the email application itself is not, most users are familiar with “email.” Some popular UNIX command-line MUAs are elm, pine, and matt. Red Hat also provides modern GUI MUAs: Mozilla Mail, Balsa, Evolution, Sylpeed, and Kmail. For comparison, common non-UNIX MUAs are Microsoft Outlook, Outlook Express, Eudora, and Netscape Messenger.

The Microsoft Windows and Macintosh MUAs often include some MTA functionality; UNIX does not for. For example, Microsoft Outlook can connect to your Internet provider’s mail server to send messages. On the other hand, UNIX MUAs generally rely on an external MTA. This might seem like a needlessly complicated way to do things, and it is for a single user connected to their IPS. For any other situation, it allows you much greater flexibility because you can use a great number of external programs to handle your email functions and customize the service.
