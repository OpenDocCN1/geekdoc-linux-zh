# Understanding the ext3 Filesystem Structure

Red Hat's rationale for choosing ext3 is compelling. Although it provides availability, data integrity, and speed similar to other filesystem choices, it has one unique advantage: It's an easy transition from ext2 to ext3, and the transition is forgiving of mistakes along the way. It is also potentially to recover a deleted file from an ext3 filesystem; it is not possible at all for the ReiserFS filesystem.

The ext3 filesystem can accommodate files as large as 2GB, directories as large as 2TB, and a maximum filename length of 255 characters. (With special kernel patches, this limit can be increased to 1024 if the standard length is insufficient for you.) The ext3 filesystem can allocate and use empty space in a very efficient manager.

The usage of space is so efficient that ext3 filesystems typically don't need de-fragmenting (rearranging the files to make them contiguous). The dynamic allocation of resources is also the source of one Achilles heel for the filesystem. When a file is deleted, it is erased and the data blocks associated with it are freed; they might very well be reallocated immediately, and the old data lost forever.

> A defragmentation program for the ext2 filesystem does exist, but it is infrequently used, isn't typically included with Linux distributions such as Red Linux, and isn't recommended for general use.

Every filesystem varies in structure, depending on its efficiency, security, and even proprietary designs to deliberately limit cross-compatibility. The ext3 filesystems were designed to follow UNIX design concepts, particularly "everything is a file."

For example, a directory in the ext3 filesystem is a simple file; that file contains the names of the files to be found in that directory, and the locations of those files. The list of names is linked so that space isn't wasted of varying filesystem lengths.

# Journaling Options in ext3

The ext3 filesystem has several options, depending on your needs, allow you to select how much information is journaled. According to Red Hat, the typical journal requires a second or to be read and recovered. The time needed to recover an improper shutdown of a journaled filesystem isn't dependent on the filesystem size, but the amount of data in the journal.
