Larger software projects might have a number of traditional targets in the makefile, such as the following:

- test—To run specific tests on the final software
- man—To process an include troff document
- clean—To delete any remaining object files
- archive—To clean up, archive, and compress the entire source tree
- bugreport—To collect and then mail a copy of error logs

Large applications require hundreds of source files. Compiling and linking applications can be a complex and error-prone task. The make utility helps you organize the process of building the executable from many source files.

### Using the autoconf utility

The make command is only one of several programming automation utilities included in Red Hat Linux. There are others, such as cmake (which causes parallel make), automake (which is a dependency-driven myfile generator), and one of the newer tools, autoconf, which builds shell scripts that can be used to configure.

Many software packages for Linux are distributed in source form. The idea is to increase portability and ease the task of the programmer who is faced with a project that is expected to run on many compatible, yet disparate, software platforms. To configure the source build and then install the new program, operator may use a command such as:

```bash
./configure; make install
```

The program uses a file named configure.in that contains a basic rules or set of macros. The configure.in file is created with the make command. Building a properly executing configure script also requires a template for the make, named Makefile.in. ### Managing Software Projects with RCS and CVS

Although RCS may be used to manage a software project, larger software projects require document management, source code controls, security, and revision tracking as the source code goes through a series of changes during development. RCS and CVS provide source code control utilities for this kind of software project management. You can find both of these utilities in RPM packages on your Linux CD-ROMs.

The RCS and CVS systems are used to track multiple versions of files, and they can be used to backtrack or branch off versions of documents inside the scope of a project. They can also be used to prevent or resolve conflicting entries changes made to source files by multiple developers.

Although RCS and CVS provide similar features, RCS uses a locking and unlocking scheme to control access to revisions; CVS, on the other hand, provide a merging approach to working on old, current, or new versions under a directory; CVS uses a number of administrative files.

RCS uses at least the following eight separate programs to track source code revisions:

- ci—Checks in revisions
- co—Checks out revisions
- ident—Starts the keyword utility for source files
- rcs—Changes file attributes
- resclean—Cleans up working files
- rsdiff—Starts the revision comparison utility
- rcmerge—Merges revisions
- rlog—Activates the logging and information utility

Source code control with CVS requires the use of at least the following command options on the cvs command line:

- checkout—Checks out revisions
- update—Updates your sources with changes made by other developers
- add—Adds new files in records
- import—Adds new sources to the repository
- remove—Eliminates files from the repository
- commit—Publishes changes to other developers

Some of these commands require you to use additional fields, such as the names of files. RCS and CVS can be used for more than software development projects. These tools can be used for document preparation and group editing of documents, and they can work with any text files. Both systems use registration and control files to accomplish revision management. Systems also offer the opportunity to revisit any step or branch in a revision history and to restore previous versions of a project. This mechanism is extremely important in cross-platform development and for software maintenance.

Tracking information is usually contained in separate control files; each document within a project might contain information that is automatically updated with each change to a project. A process called keyword substitution is used to perform these automatic updates. CVS and RCS use similar keywords, which are usually included inside C comment strings (/*) near the top of a document. The following are some of the available keywords:

- $Author$—The username of the person who performed the last check-in
- $Date$—The date and the time of the last check-in
- $Header$—The pathname of the document's RCS file, with the revision number, date and author, and state inserted
- $Ids$—Same as Header, but without a full name
- $Name$—A symbolic name (see the co man page)
- $Revision$—The assigned revision number (such as 1.1)
- $Source$—The RCS file's full name
- $State$—The state of the document, as Exp for experimental, Rel for released, or stable
