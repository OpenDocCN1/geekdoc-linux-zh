your table has 500,000 rows (or records) in it, all 500,000 rows are locked any time a row is accessed. Once again, in environments with a relatively small number of simultaneous users, this doesn't cause serious performance problems because most operations complete so quickly that the lock time is extremely short. However in environments where a lot of people are accessing the data simultaneously, MySQL's table-level locking can be a significant performance bottleneck.

PostgreSQL, on the other hand, locks data at the row level. In PostgreSQL, only the row that is currently being locked. The rest of the table can be accessed by other users. This row-level locking significantly reduces the performance impact of locking in environments that have a large number of simultaneous users. Therefore, as a general rule, PostgreSQL is better suited for high-load environments than MySQL.

> MySQL's data locking methods are discussed in more depth at http://www.mysql.com/doc/en/Internal_locking.html. Red Hat Linux includes MySQL version 3.23.52, but the newer version, 4.0 (in beta testing at the time of this writing), provides row-level locking.

You can find more information on PostgreSQL's locking at http://www.postgresql.org/docs/index.php?locking=tables.html.

# ACID Compliance in Transaction Processing to Protect Data Integrity

Another way MySQL and PostgreSQL differs is in the amount of protection they provide for keeping data from becoming corrupted. The acronym ACID is commonly used to describe aspects of data protection:

+   - Atomicity is a term that is derived from the word atom, which you might know, means "indivisible.\ In the database world, means that several database operations will be treated as an atomic unit, often called a transaction. In a transaction, either all the operations are carried out or none of them are carried out. In other words, if any operation in the atomic unit fails, the entire atomic unit is canceled.

If you have a power failure or server crash after an original record has been deleted, for example, but before the updated one has been added, you don't lose the record because atomic transactions ensure that the original record isn't deleted by the update portion of the atomic unit.

+   - Consistency ensures that no transaction can cause the database to be left in an inconsistent state. Inconsistent states can be caused by database client crashes, network failures, and similar situations.
