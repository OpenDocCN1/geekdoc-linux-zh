> One of the common errors among new database programmers is confusing logical AND and OR. For example, in everyday speech, you might say "Find me all records with genus Panthera and Acinonyx." At glance, you might think that if you fed this statement to the database SQL format, it would return the rows for the African lion and the cheetah. In fact, it would return no rows at all. This is because the database interprets the statement "Find all rows in which the animal belongs to the genus Panthera and the genus Acinonyx." It is, of course, impossible for an animal to belong to more than one genus, so this statement would never return any rows, no matter how many animals were stored in the table. The correct way to form this statement is with an OR statement instead of an AND statement.

## Speed

Until recently, the speed was quite simple: if the speed of performing queries was paramount to your application, you used MySQL. MySQL has a reputation for being extremely fast database. Until recently, PostgreSQL was quite slow by comparison.

Newer versions of PostgreSQL have improved in terms of speed (when it comes to disk access, sorting, and so on). In certain situations, such as periods of heavy simultaneous access, PostgreSQL can be significantly faster than MySQL, as you'll see in the next section. MySQL is still extremely fast when compared to many other databases.

## Data Locking

In order to prevent data corruption, a database needs to put a lock on data while it is being accessed. As long as the lock is on, no other process can access the data until the first process has released the lock. This means that any other processes trying to access the data have to wait until the current process completes. The next process in line locks the data until it is finished, and the remaining processes have to wait their turn, and so on.

Of course, operations on a database generally complete quickly, in environments with a small number of users simultaneously accessing the database, the locks are usually of such short duration that they don't cause any significant delays. However, in environments where a lot of people are accessing the database simultaneously, locking can begin to create performance problems as different people wait their turn to access the database.

MySQL uses a data-locking method that is fundamentally different from the data-locking method used by PostgreSQL.

Current versions of MySQL lock data at the table level, which can be considered a bottleneck for updates during periods of heavy access. This means that when someone writes a row of data in the table, the entire table is locked so that no else can enter data. If your table has 500,000 rows (or records) in it, all 500,000 rows are locked any time a row is accessed. Once again, in environments with a relatively small number of simultaneous users, this doesn't cause serious performance problems because most operations complete so quickly that the lock time is extremely short. However in environments where a lot of people are accessing the data simultaneously, MySQL's table-level locking can be a significant performance bottleneck.

PostgreSQL, on the other hand, locks data at the row level. In PostgreSQL, only the row that is currently being locked. The rest of the table can be accessed by other users. This row-level locking significantly reduces the performance impact of locking in environments that have a large number of simultaneous users. Therefore, as a general rule, PostgreSQL is better suited for high-load environments than MySQL.

> MySQL's data locking methods are discussed in more depth at http://www.mysql.com/doc/en/Internal_locking.html. Red Hat Linux includes MySQL version 3.23.52, but the newer version, 4.0 (in beta testing at the time of this writing), provides row-level locking.

You can find more information on PostgreSQL's locking at http://www.postgresql.org/docs/index.php?locking=tables.html.

## ACID Compliance in Transaction Processing to Protect Data Integrity

Another way MySQL and PostgreSQL differs is in the amount of protection they provide for keeping data from becoming corrupted. The acronym ACID is commonly used to describe aspects of data protection:

- Atomicity is a term that is derived from the word atom, which you might know, means "indivisible." In the database world, means that several database operations will be treated as an atomic unit, often called a transaction. In a transaction, either all the operations are carried out or none of them are carried out. In other words, if any operation in the atomic unit fails, the entire atomic unit is canceled.

If you have a power failure or server crash after an original record has been deleted, for example, but before the updated one has been added, you don't lose the record because atomic transactions ensure that the original record isn't deleted by the update portion of the atomic unit.

- Consistency ensures that no transaction can cause the database to be left in an inconsistent state. Inconsistent states can be caused by database client crashes, network failures, and similar situations. Consistency ensures that, in such a situation, any transaction or partially completed transaction would cause the database to be left in an inconsistent state is rolled back, or undone.
