
## Viewing Your System’s Filesystems

Your installation of Red Hat Linux has its own unique set of usable virtual filesystem modules. You can view the filesystems that your system can access right now (and verify your kernel's support for these filesystems) by using the following command:

```
# cat /proc/filesystems
```

Your output will vary, depending on your system’s hardware and kernel settings. The tested system we used for this chapter presented this output:

```
nodev rootfs
odev bdev
odev proc
odev sockfs
odev tmpfs
nodev shm
odev pipefs
  ext2
nodev ramfs
  iso9660
nodev devpts
  ext3
nodev devfs
nodev usbfs
  ReiserFS
  vfat
nodev nfs
nodev autofs
nodev binfmt_misc
```

The entries not preceded by nodev aren’t of interest to us because they don’t tell us any information about the filesystem. On this machine, the ext2, ext3, vfat, ReiserFS, and iso9660 filesystems are supported. Modules for other filesystems could be loaded if needed.

## Working with the ext3 Filesystem

Red Hat has invested in the development of the ext3 filesystem and provides support for the ext3 filesystem as the journaling filesystem for its distribution. Red Hat does not provide that level of support for other filesystems. Other distributions such as SuSE and Mandrake support the Reiser filesystem. (You learn about these in later sections of this chapter.)

The ext3 filesystem is an update to the ext2 filesystem, which has been one of the most popular Linux filesystems for some time. You can choose to use the ext3 filesystem during a fresh install or automatically convert an ext3 filesystem when you upgrade your present system to the current version of Red Hat Linux. All the ext2 tools provided by Red Hat have been upgraded to work with both ext2 and ext3. We mention the ext2 tools only because you see the ext3 filesystem mentioned frequently; ext3, as supplied with Red Hat Linux, is completely compatible with ext2.

## Understanding the ext3 Filesystem Structure

Red Hat's rationale for choosing ext3 is compelling. Although it provides availability, data integrity, and speed similar to other filesystem choices, it has one unique advantage: It's an easy transition from ext2 to ext3, and the transition is forgiving of mistakes along the way. It is also possible to recover a deleted file from an ext3 filesystem; it is not possible at all for the ReiserFS filesystem.

The ext3 filesystem can accommodate files as large as 2GB, directories as large as 2TB, and a maximum filename length of 255 characters. (With special kernel patches, this limit can be increased to 1024 if the standard length is insufficient for you.) The ext3 filesystem can allocate and use empty space in a very efficient manager. The usage of space is so efficient that ext3 filesystems typically don't need defragmenting (arranging the files to make them contiguous). Dynamic allocation of resources is also the source of Achilles heel for the filesystem. When a file is deleted, the data blocks associated with it are freed; they might not be reallocated immediately, or lost forever. A defragmentation program for the ext2 filesystem does exist, but is infrequently used, isn't typically included with Linux distributions, and isn't recommended for general use.

Every filesystem varies in structure, depending on its efficiency, security, and even proprietary design compatibility. The ext3 filesystems were designed to follow UNIX concepts, particularly "everything is a file." For example, a directory in the ext3 filesystem is a simple file; that file contains the names of the files to be found in that directory, and the locations of those files so that space isn't wasted.

## Journaling Options in ext3

The ext3 filesystem has several options, depending on your needs, allow you to select how much information is journaled. According to Red Hat, the journal requires a second read. The time needed to recover an improper shutdown of a journaled filesystem isn't dependent on the filesystem size, but the amount of data in the journal. The default setting provided by Red Hat is adequate for most needs. The optimal choice depends on many factors (computer usage, hardware used, and evaluation methods) that are beyond the scope of this chapter. You learn in this chapter what the choices are and how they differ, but whether a choice is right for you can only be determined on an individual basis.

Like journaling filesystems, the traditional filesystem check (fsck) is not necessary on ext3 filesystem. Although only annoying on a small drive on your machine, the seemingly endless hours that fsck would take to run on a terabyte of data is shared with the other filesystems.

When choosing journaling options, you can trade off data integrity (keeping your data current and valid) for data speed in your filesystem's operation; you can't have both because of the nature of the filesystem. To keep the state consistent, three modes available in ext3 are as follows:

- Writeback—allow data to stay in the filesystem, attaining the fastest speed. It doesn't schedule any data writes; it just allows the kernel to flush the buffer.
- Ordered—keeps the data consistent, but with some sacrifice in speed (the default mode for Red Hat).
- Journal—requires more disk space to journal data. You might see slower performance because data is written twice, but there are some speed benefits if you are doing synchronous data writes in database operations.

For most, the selection represents a good trade-off. Red Hat supports booting from an ext3 formatted root filesystem with the proper drivers loaded in the initrd image. The mode is selected by using the appropriate mount point in /etc/fstab.

## Verifying File Integrity in ext3 with the fsck Utility

The filesystem integrity is assured through the use of the fsck, or filesystem check, program—one of five commands in the library that are used to maintain and modify the ext3 filesystem.

When fsck is run, it performs a sequential analysis of the filesystem information available in the filesystem if it detects a directory that cannot be traced back to the root or a deleted file with a zero link count. It places these directories and files in the /lost+found directory that is created on each physical partition by the filesystem formatting process. Some blocks are reserved for this and other uses of the superuser. It is possible to reduce this allocation to free regular users by special arguments to the formatting program mk2fs.

## Other Filesystems Available to Red Hat Linux

To run the fsck command, use the name of the filesystem as the argument. If you want to fsck the filesystem at /dev/hdc, for example, do this:

```
# fsck /dev/hdc
```

The filesystem state is tracked in the design superblock. A special field in the superblock tells the kernel that, after the filesystem is mounted read/write, it is marked as not clean; when it is unmounted, it is marked as clean. If a filesystem is unmounted properly, it could contain corrupt data because all the file data might not have been written to it. (This is what the journaling filesystems such as ext3 strive to eliminate.) When the system is booted, this flag is checked and if it is not clean, the program fsck is run. (Actually, fsck is a wrapper program that provides the appropriate version of fsck: fsck.minix, fsck.ext2, fsck.ext3, fsck.reiserfs, fsck.msdos, fsck.vfat.) If the kernel detects an inconsistency in the superblock field, the filesystem is marked erroneous, and the filesystem check is forced even if other indicators suggest that fsck doesn't need to be run.

By default, the system will run fsck on a filesystem after a periodic number of reboots regardless of the status of the clean flag. This is triggered by a mount counter kept in the superblock or after a predetermined amount of time that has elapsed since the last reboot (information also kept in the superblock). These parameters can be adjusted by tune2fs command, and this command can also be used to modify how the kernel handles the erroneous flag and, interestingly, the number of blocks reserved for the superuser, also known as root. This latter option is useful on very large or very small disks to make more disk space available to the user.

# The Reiser Filesystem (ReiserFS)

The other popular journaling filesystem for Linux is the written-from-scratch Reiser Filesystem, ReiserFS. It is used primarily in SUSE and Mandrake distributions, which support booting from a ReiserFS root filesystem. ReiserFS offers many features to ext3, but there is no easy migration path from an already existing ext2 partition, as you learn to do in "Converting an existing ext2 filesystem to ext3," later in the past. ReiserFS didn't work well over NFS mounts, but recent versions of nfsd daemon fixed those problems. Red Hat offers ReiserFS, but doesn't support booting from it as root partition filesystem, nor does it officially offer the choice to format non-root partitions as ReiserFS during the installation process.
