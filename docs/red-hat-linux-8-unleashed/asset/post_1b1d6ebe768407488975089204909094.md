
The first line, of course, simply specifies the username that is used to log in to the email server, and the second line specifies the password for that user. Many security-conscious depts cringe at the thought of putting clear-text passwords in a configuration file. The only protection is to make certain that the file is readable only by the owner; that is, with file permissions of 600.

The third line tells Fetchmail that it should fetch all messages from the server, even if they have already been read.

The fourth line tells Fetchmail that it should delete the messages from the mail server after it has completed downloading them. This is the default, so we wouldn't have to specify this option. If you wanted to leave the messages on the server after downloading them, use the option no flush.

The configuration options you just inserted configured the entire .fetchmailrc file to look like this:

```
set daemon 600
set postmaster foobar ownset logfile ./fetchmail.log
```

```
poll mail.samenet.org
proto pop3
no dns
```

```
user foobar
pass secretword
fetchall
flush
```

What this file tells Fetchmail to do

- Check the POP3 server mail.samenet.org for new mail every 600 seconds
- Log in using the username foobar and the password secretword
- Download all messages off the server
- Delete the messages from the server after it has finished downloading them
- Send any mail it receives that cannot be delivered to a local user to the account foobar

As mentioned before, many more options can be included in the .fetchmailrc file than are listed here. However, these options will get you up and running with a basic configuration.

For additional flexibility, you can define multiple .fetchmailrc files in order to retrieve mail from different remote servers using the same Linux account. For example, you can define settings for your most used account and save them in the default .fetchmailrc file. Mail can be quickly retrieved like so:

$ $ fetchmail -a
1 message for bball at mail.myserver.com (1108 octets).
reading message 1 of 1 (1108 octets) . flushed

By using fetchmail's -f option, you can specify an alternative resource file and then easily retrieve mail from another server like this:

$ $ fetchmail -f .othermailrc
2 messages for bball at othermailer.org (5407 octets).
reading message 1 of 2 (3440 octets) ... flushed
reading message 2 of 2 (1967 octets) . flushed
You have new mail in /var/spool/mail/bball

By using the -d option, along with a time interval (in seconds), you can use Fetchmail in its daemon, or background mode. The command will launch as a background process and retrieve mail from a designated remote server at a specified interval. For more advanced options, see the Fetchmail page, which is very well-known and documents all options in detail.

> CAUTION
> Because .fetchmailrc file contains your mail server password, it should be readable only by you. This means that it is owned by you and should have permissions no greater than 600. Fetchmail will complain and refuse to start if the .fetchmailrc file has permissions greater than this.

# Choosing a Mail Delivery Agent (MDA)

Because of the modular nature of mail handling, it is possible to use multiple applications to process mail and accomplish more than simply deliver it. Getting mail from the storage area and displaying it to the user is the purpose of the mail delivery agent (MDA). MDA functionality can be found in some of the mail clients (MUAs), which can cause some confusion to those still unfamiliar with the concept of UNIX mail. As an example, the Procmail MDA provide filtering by rulesets; Kmail and Evolution, both MUAs, provide filtering, the MUAs pine, mutt, and baldo do not. Some MDAs perform sorting, and other MDAs are designed to eliminate unwanted emails, like spam and viruses.

You would choose an MDA based on what you want to do with your mail. We’ll look at five MDAs that offer functions you might find useful in your particular situation. If you have simple needs (just organizing mail by rules), one of the MUAs that offers filtering might be better for your needs. Red Hat provides the Evolution MUA as the default selection (and it contains some MDA functionality as previously noted), so try that and see if it meets your needs. If not, investigate one of the following MDAs provided by Red Hat.

Unless otherwise noted, all the MDA software is provided with the Red Hat discs. Chapter 8, details the actual installation of software.

# Procmail

As a tool for advanced users, the Procmail application acts as a filter for email as it is retrieved from a mailserver. It uses rulesets (known as recipes) as it reads each email message. No default configuration is provided; you must manually create a ~/.procmail file for each user, or each can create their own.

There is no systemwide default configuration file. The creation of a ~/.procmail file is not trivial and requires an understanding of regular expressions. Detailed instructions can be found in /usr/share/doc/procmail/README. What's done covered in this chapter is beyond the scope. Procmail provide filtering by rulesets; Kmail and Evolution, both MUAs, provide filtering, the MUAs pine, mutt, and baldo do not. Some MDAs perform sorting, and other MDAs are designed to eliminate unwanted emails, like spam and viruses.

# Spamassin

If you've used email for any length of time, you've likely been subjected to spam. Enabling Spamassassin is simple. You must first have installed and configured procmail. The README found in /usr/share/doc/spamassassin/README provides details on configuring procmail. It will tag probable spam with a unique header. One interesting use of Spamassassin is to use it to tag email received at special accounts. Red Hat provides a solution for this, but it is not provided with spam. It employs a combination of rulesets and blacklists. Red Hat provides a solution for the purpose of attracting spam.

# Squiremail

Perhaps you don't want to read your mail in a MUA. If you use your Web browser, it might make sense to read and send mail via a Web interface, like the one used by Gmail or Yahoo! Red Hat provides a solution for that purpose. Squiremail is written in PHP4 and uses IMAP and SMTP. It supports MIME attachments, as well as an address book and folders for segregating email.

You must configure your Web server with PHP4. Detailed instructions can be found in /usr/share/doc/squiremail/INSTALL. Once configured, point your Web browser to http://www.yourdomain.com/squiremail to read and send mail.

# Virus Scanners

Although the currently held belief that Linux is immune to email viruses targeted at Microsoft Outlook users, it certainly makes no sense for UNIX mail servers to permit infected email by sending through them. Red Hot does not provide a virus scanner, one of the more popular of such scanners is MailScanner, available from http://www.sng.ecs.soton.ac.uk/mailscanner/; a RPM package is available as well as the source code. It provides Sendmail and Exim (another MTA, not provided by Red Hot), but not Postfix or Qmail. Searching on the terms "virus" and "email" at Fresh.net will turn up a surprising list of GPL'd virus scanners that might serve your needs.

# Special Mail Delivery Agents

If you already use Hotmail or any other Web-based email account, the currently available MUAs will not be useful to you; formal POP3 access to a Hotmail account is not available free of charge. However, Microsoft Outlook Express can access Hotmail at no cost using a special protocol called HTTPMail. What that's done covered in RFC-2518 as "WebDAV extensions to HTTP/1.1."

Hotway is available from http://people.freetenet.de/courierave/ and implements this functionality, allowing you to use your favorite mail client to read mail from Hotmail.
