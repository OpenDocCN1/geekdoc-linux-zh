We've already discussed the contents of the config subdirectory, so let's examine the other directories found under /usr/src/linux-2.4. The most useful for us is the Documentation directory, and in its subdirectories, you will find all the documentation concerning every part of the kernel. The file0-INDEX (each subdirectory also contains a 0-INDEX file as well) contains a list of files in the main directory and a brief explanation of what they are. Many files are written solely for kernel programmers and writers, but a few are useful to the intermediate or advanced Linux user when attempting to learn about kernel and device drivers. Some of the most interesting and useful documents:

- devices.txt—List of possible Linux devices that are represented in the /dev/, giving major and minor numbers and a short description. If you have ever gotten an error message mentioning "char-major-xxx", this file is where that list is kept. Devices are mentioned in Chapter 10, "Managing Filesystems."

- ide.txt—If your system uses IDE hard drives, this file discusses how the kernel interacts with them and lists the various kernel command that can be used to solve IDE-related hardware problems, manually set data transfer modes, and otherwise manage your IDE drives. Most of this management is automatic, but if you want to understand how the kernel interacts with IDE devices, this file explains it.

- initrd.txt—Chapter 10 also discusses the initial ramdisk. This file provides much more in-depth knowledge of initial ramdisks, giving details on the loopback filesystem to create and mount and explaining how the kernel interacts with them.

- kernel-parameters.txt—In Chapter 7, "Managing Services", we touch briefly on kernel arguments, which are commands that can be passed to the kernel at boot to configure kernel or hardware settings. This file is a list of most those kernel arguments, but it doesn't appear too useful at first glance because it's a list. However, knowing that a parameter exists and might relate to what you're looking for can assist you in tracking down more information than you have to enter into an Internet search engine like http://www.google.com/linux.

- sysrq.txt—If you have ever wondered what key you keyboarded "SysRq" was used for, this file has the answer. Briefly, it's a key combination hardwired into the kernel that can help you recover from a system lock. Red Hat disables this by default for security reasons. You can re-enable it by entering the command # echo "1" > /proc/sys/kernel/sysrq and disable it by choosing a value of "0" instead of "1"

In the nearly 30 other directories found in Documentation, you'll find similar text files that deal with the kernel modules for CD-ROM drivers, filesystem drivers, gameport and joystick drivers, video drivers (not graphics card drivers—those belong to XFree86 and not to the kernel), network drivers, and all the other drivers and systems in the Linux operating system.

# The Linux Kernel

## Types of Kernels

In the early days of Linux, Linux kernels were a single block of code containing all the instructions for the processor, the motherboard, and the hardware. If you changed hardware, you were required to recompile the kernel to include what you needed and discard what you did. Including extra, unneeded code carried a penalty: The kernel became larger and occupied more memory. On older systems that had only 4MB of memory, wasting precious memory was unacceptable. Kernel compiling was something of “black art” as early Linux users attempted to write the most from their computers. These kernels compiled as a single block of code are called monolithic kernels.

As the kernel code grew larger and the number of devices that could be added to a computer increased, the requirement to recompile became onerous and a new method was developed that would solve the problem. The part of the kernel's source code that composed the device drivers could be optionally compiled as a module that could be loaded and unloaded. This approach to building the kernel is called modular. Now, all the code could be compiled at once, with most of the code into modules. The required modules would be loaded; the kernel could be kept small, and adding hardware was much simpler.

The typical Red Hat kernel has some drivers compiled as part of the kernel itself (in-line drivers) and others as modules. Only device drivers compiled in-line are available to the kernel during the boot process; modular drivers are only available after the system has booted.

> As a common example, drivers must be available to the kernel if you intend to boot from SCSI disks. If the kernel isn't compiled with those drivers in-line, the system won't boot because it won't be able to access the disks.

A way around this problem for modular kernels is to use the initial Ram disk (initrd) discussed later in the chapter. The initrd loads a small kernel and the appropriate device driver, which then can access the device to load the actual kernel you want to run.

Some code could be one or the other (for technical reasons unimportant to the average user), but code could be compiled either way. Depending on the application, some administrators prefer one way over the other, but with fast processors and abundant system memory, the performance differences are of little concern to all but the most ardent Linux hackers.

When compiling a kernel, the step in which you make the selection of modular or in-line is part of the make config step that we'll detail later in this chapter. Unless you have a specific reason to otherwise, we suggest that you select the module option given a choice. The process of managing modules is addressed in the next section because you'll be managing them more frequently than you will be compiling a kernel.
