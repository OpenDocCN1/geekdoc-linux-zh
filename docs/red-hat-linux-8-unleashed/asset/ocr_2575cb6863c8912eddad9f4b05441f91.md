# Debugging Tools

Debugging is both a science and an art. Sometimes, the simplest tool—the code listing—is the best debugging tool. At other times, however, you need to use other debugging tools. Three of these are splint, gprof, and gdb.

Using splint to Check for Source Code
splint command is similar to the traditional UNIX lint command; it examines source code for possible problems, and it also has many additional features. Even if your C code meets the standards for C and compiles cleanly, it might still contain errors. splint performs many different types of checks and can provide extensive error information. For example, this simple program might compile cleanly and even run:

```
$ gcc tux.c -o tux
$ ./tux
```

But the splint command might point out some problems with the source:

```
$ splint tux.c
splint 3.0.1.6 --- 27 May 2002
```

```
tux.c:(in function main)
tux.c:2:19: Return value (type int) ignored: putchar(t[++j]) ...
Result returned by function call is not used. If this is intended, can
result to (void) to eliminate message. (Use -retvalint to inhibit warning)
Finished checking --- 1 code warning
```

You can use the spl command's -strict option, like this, to get a more verbose report:

```
$ splint -strict tux.c
```

The GNU compiler also supports diagnostics through the use of extensive warnings (through the -Wall and -pedantic options: )

```
$ gcc -Wall tux.c
tux.c:1: warning: return type defaults to `int`
tux.c: In function `main`
tux.c:2: warning: implicit declaration of function `putchar`
```
