You can enable SSI with the XBitHack directive to be set to a value of on or off, and can be set in your configuration file or in .htaccess. If the XBitHack directive is on, it indicates that all files with the user execute bit set be parsed for SSI directives. This has two main advantages. One is that you don't need to rename a file, and change all links to it, simply because you want to add a little dynamic content to it. The other reason is more cosmetic: Users looking at your Web content can't tell by looking at the filename that you're generating a page dynamically, so your wizardry is just a tiny bit more impressive.

Another side effect of using XBitHack is that it enables you to control how clients cache your page. Pages containing SSI statements will not usually contain a Last-modified HTTP header. Therefore, they won't be cached by proxies or Web browsers. If you enable XBitHack, the group-execute bit for files will control whether a Last-modified header should be generated. It will be set to the same value as the last modified time of file. Be sure to use this only on files that are really supposed to be cached.

Another way to enable SSI is to indicate that files with a certain extension (typically .shtml) are be parsed by the server when they're served. This is accomplished with the following lines in your httpd.conf file:

```
# To use server-parsed HTML files
#
#AddType text/html .shtml
#AddHandler server-parsed .shtml
```

If you uncomment the AddType and AddHandler lines, you will tell the server to parse .shtml files for SSI directives.

In addition to these directives, the following directive must be specified for directories in which you want to permit SSI:

Options Includes
This can be set in the server configuration file or in an .htaccess file.

# Basic SSI Directives

SSI directives look rather like HTML comment tags. The syntax is as follows:

```
<--Element attribute=value attribute=value ... -->
```

The element can be one of several directives, including

+   - config
- echo
- exec
