# Startup Parameters

In many of the previous examples, we had to hard-wire something into the kernel module, such as the file name for /proc files or the major device number for the device so we can have ioctl() to it. This goes against the grain of the Unix, and Linux, philosophy which is to write flexible program, or a kernel module the user can customize.

The way to tell a program, or a kernel module, something it needs before it can start working is command line parameters. In the case of kernel modules, we don't get argc and argv—instead, we get something better. We can define global variables in the kernel module and insmod will fill them for.

In this kernel module, we define two of them: str1 and str2. All you need to do is compile the kernel module and then run insmod str1=xxx str2=yyy. When init_module is called, str1 will point to the string 'xxx' and str2 to the string 'yyy'.

In version 2.0 there is no type checking on arguments¹. If the first character of str1 or str2 is a digit the kernel will fill the variable with the value of the integer, rather than a pointer to the string. If a real situation you have to check for this.

On the other hand, in version 2.2 you use the macro MACRO_PARM to tell insmod that your parameters, its name and type. solves the type problem and allows kernel modules to begin with a digit, for example.

¹There can't be, since C the object file has only the location of global variables, not their type. That is why header files are necessary.

# System Calls

So far, the only thing we've done was to use well-defined mechanisms to register /proc files and device handlers. This is fine if you want to do something the kernel programmers thought'd want, such as write a device driver. But if you want to do something unusual, change the behavior of the system in some way, you're mostly on your own.

This is when kernel programming gets dangerous. While writing the example below, I killed the open system call. This meant I couldn't open any files, I couldn't run any programs, and I couldn't shut down the computer. I had to pull the power switch. Luckily, nothing died. To ensure you lose no files, please sync right before you do insmod and rmmod.

Forget /proc files, about device files. They're just details. The real process to kernel communication, the one used by processes, is system calls. When a process requests a service from the kernel (such as opening a file, forking to a new process, or requesting memory), this is the mechanism used. If you want to change the behaviour of the kernel in interesting ways, this is the place to do it. By the way, if you want to see which system calls a program uses, run strace <arguments>.

In general, a process is not supposed to access the kernel. It can't access kernel memory and it can't call kernel functions. The hardware of the CPU enforces this (that's reason why it's called 'protected mode'). System calls are an exception to this general rule. What happens is that the process fills the registers with the appropriate values and then calls a special instruction which jumps to a previously defined location in the kernel (of course, location is readable by user processes, it is not writable).

Under Intel CPUs, this is done by means of interrupt 0x80. The hardware knows that you jump to this location, you are no longer running in restricted user mode, but as the operating system kernel — and therefore you are allowed to do whatever you want.

The location in the kernel process is called system_call. The entry at that location checks the call number, which tells the kernel what service the process requested. Then, it looks at the table of system calls (sys_call_table) to see the address of it. Then it calls the function, and after returns, it does a few system checks and then return back to the process (or a different process, if the process ran out). If you want to read this code, it is the source file arch/<architecture>/kernel/entry.S, after the line ENTRY(system_call).

So, if we want to change a certain system call, what we need to do is write our function to implement it (usually by adding a bit of our own code and then calling the original function) and then change the pointer to sys_call_table to point to out function. Because we might be removed and we don't want to leave the system in unstable state, it is important for cleanup_module to restore the table to its original state.

The source code is an example of such a kernel module. We want to 'spy' on certain user, and to print a message when that user opens a file.
