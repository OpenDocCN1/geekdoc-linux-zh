
取决于内核版本的条件编译。实现此点的方法是使用 `LINUX_VERSION_CODE` 宏。在 a.b.c 版本的内核中，该宏的值为 $2^{16}a + 2^8b + c$。为了获取特定内核版本的值，我们可以使用 `KERNEL_VERSION` 宏。由于它在 2.0.35 中没有定义，如果有必要，我们自己定义它。

## 第 3 章

## /proc 文件系统

在 Linux 中，内核和内核模块有一种用于向进程发送信息的额外机制——`/proc` 文件系统。它最初的设计是为了方便地访问有关进程的信息（因此得名），现在它被内核中每一个有有趣报告内容的部分使用，例如 `/proc/modules`（包含模块列表）和 `/proc/meminfo`（包含内存使用统计）。

使用 `proc` 文件系统的方法与使用设备驱动程序的方法非常相似——你创建一个包含 `/proc` 文件所需所有信息的结构体，包括指向任何处理函数的指针（如果只有一个函数，则是当有人尝试读取 `/proc` 文件时调用的那个函数）。然后，`init_module` 注册该结构体，`cleanup_module` 注册它。

我们使用 `register_dynamic` 的原因是我们不想确定用于我们文件的索引节点（index-node），而是让内核来决定，以防止冲突。普通文件系统位于磁盘上，而不是仅仅在内存中（`/proc` 所在的位置），在这种情况下，索引节点是一个指向磁盘位置的指针，该文件的索引节点（inode for for）位于该磁盘位置。该节点包含有关文件的信息、文件权限，以及指向可以找到文件数据的磁盘位置或多个位置的指针。

由于在文件被打开或关闭时我们不会被调用，因此在该模块中我们没有地方放置 `MOD_INC_COUNT` 和 `MOD_DEC_COUNT`，而且如果文件被打开且模块被移除，就没有办法避免后果了。在下一章中，我们将看到一种更复杂但更灵活的处理 `/proc` 文件的方法，它将允许我们防止防止这个问题。

> 在 2.0 版本中，在 2.2 版本中，如果我们将节点设置为 0，就可以完成这一点。

## 第 4 章

## 使用 proc 进行输入

到为止，我们有两种从内核模块生成输出的方法：我们可以注册设备驱动程序并 mknod 设备文件，或者创建一个 `/proc` 文件。这允许内核模块告诉我们任何它想要。唯一的问题是我们没有方法反馈。我们向内核模块发送输入的第一种方法是通过写回 `/proc` 文件。

由于 proc 文件系统主要是为了允许内核报告其情况而编写的，`proc_dir_entry` 结构没有包含指向输入函数的指针，但它包含指向输出函数的指针。相反，为了写入 `/proc` 文件，我们需要使用标准的文件系统机制。

在 Linux 中，有一种标准的文件注册机制。由于每个文件系统都有处理文件和文件操作的函数，因此有一个存储所有函数指针的特殊结构 `inode_operations`，它包含一个指向 `file_operations` 的指针。在 `/proc` 中，每当我们注册一个新文件时，我们被允许指定使用哪个 `inode_operations` 来访问它。这就是我们使用的机制，一个 `inode_operations` 包含一个指向 `file_operations` 的指针，后者包含了我们的 `module_input` 和 `module_output` 函数。

¹ 这者之间的区别在于，文件操作处理文件本身，而节点操作处理引用文件的方式。
