## Chapter 3

## The /proc File System

In Linux there is an additional mechanism for the kernel and kernel modules to send information to processes — the /proc file system. Originally designed to allow easy access to information about processes (hence the name), it is now used by every bit of the kernel which has something interesting to report, such as /proc/modules which has the list of modules and /proc/meminfo which has memory usage statistics.

The method to use the proc file system is very similar to the one used with device drivers — you create a structure with all the information needed for the /proc file, including pointers to any handler functions (in case there is only one, the one called when somebody attempts to read from the /proc file). Then, init_module registers the structure with the cleanup_module registers it.

The reason we use register_dynamic is because we don't want to determine the index-node used for our file but allow the kernel to determine it to prevent clashes. Normal file systems are located on a disk, rather than just in memory (which is where /proc is), and in that case the index-node is a pointer to a disk location where the file's index-node (inode for for) is located. The node contains information about the file, the file's permissions, with a pointer to the disk location or locations where the file's data can be found.

Because we don't get called when the file is opened or closed, there's no where for us to put MOD_INC_COUNT and MOD_DEC_COUNT in this module, and if the file is opened and the module is removed, there's no way to avoid the consequences. In the next chapter we'll see a harder implement, but more flexible, way of dealing with /proc files which will allow us to protect against this problem as well.

## Chapter 4

## Using /proc For Input

So far we have two ways to generate output from kernel modules: we can register a device driver and mknod a device file, or we can create a /proc file. This allows the kernel module to tell us anything it likes. The only problem is that there is no way for us to talk back. The first way we'll send input to kernel modules will be by writing back to the /proc file.

Because the proc filesystem was written mainly to allow the kernel to report its situations, the proc_dir_entry struct doesn't include a pointer to an input function, which it includes a pointer to an output function. Instead, to write into a /proc file, we need to use the standard filesystem mechanism.

In Linux there is a standard mechanism for file registration. Since every file system has its own functions to handle file and file operations¹, there is a special structure to hold pointers to all functions, struct inode_operations, which includes a pointer to struct file_operations. In /proc, whenever we register a new file, we're allowed to specify which struct inode_operations will be used for access to it. This is the mechanism we use, a struct inode_operations which includes a pointer to struct file_operations which includes pointers to our module_input and module_output functions.

It's important to note that the standards of read and write are reversed in the kernel. Read functions are used for output, whereas write functions are used for input.

> ¹The difference between the two is that file operations deal with the file itself, and inode operations deal with ways of referencing the file, such as creating links to it.
