
# Advanced Bash–Scripting Guide

We will be using Bash, an acronym for "Bourne–Again Shell" and a pun on Stephen Bourne's classic Bourne Shell. Bash has become a de facto standard for shell scripting on all flavors of UNIX. Most of the principles dealt with in this book apply equally well to scripting with other shells, such as the Korn Shell, from which Bash derives some of its features, [2], and the C Shell and its variants. (Note that C Shell programming is not recommended due to certain inherent problems, as pointed out in a news group posting by Tom Christensen in October of 1993).

The following is a tutorial in shell scripting. It relies heavily on examples to illustrate the features of the shell. As far as possible, the example scripts have been tested, and some of them may actually be useful in real life. The reader should use the actual examples in the source archive (`chmod u+rx something-or-other.sh`, [3] give them execute permission), then run them to see what happens. Should the source archive not be available, then cut-and-paste from the HTML, pdf, or text rendered versions. Be aware that some of the scripts below introduce features before they are explained, and this may require the reader to temporarily skip ahead for enlightenment.

Unless otherwise noted, the author wrote the example scripts that follow.

In the simplest case, a script is nothing more than a list of system commands stored in a file. At the very least, this saves the effort of retyping that particular sequence of commands each time it is invoked.

Example 2–1. cleanup: A script to clean up the log files in /var/log

```bash
# cleanup
# Run as root, of course.

cd /var/log
cat /dev/null > messages
cat /dev/null > wtmp
echo "Logs cleaned up."
```

There is nothing unusual here, just a set of commands that could as easily be invoked by one from the command line in a console or an xterm. The advantages of placing the commands in a script beyond having to retype them time and again. The script can easily be modified, customized, or generalized for a particular application.

The *sha-bang* (#) at the head of a script tells your system this is a set of commands to be fed to the command interpreter. The # is actually a two-byte [magic number", a special marker that designates a file type, or in the case of an executable shell (see **man magic** for details on this fascinating topic). Immediately following the *sha-bang* is a path name. This is the path to the program that interprets the commands, whether it be a shell, a programming language, or a utility. This command interpreter executes the commands in the script, at the top (line 1 of the script), [5]

```bash
#!/bin/sh
#!//bin/bash
#!//usr/bin/perl
#!//usr/bin/tcl
#!//bin/sed -f
#!//usr/awk -f
```

Each of the script header lines calls a different command interpreter, or /bin/sh, the default (bash in a Linux system) or otherwise. [6] Using #!/bin/sh, the default Bourne Shell in most commercial variants of UNIX, the script portable to non-Linux machines, though you may have to sacrifice a few Bash-specific features (the script will conform to the POSIX [7] standard).

Note that the path given at "sha-bang" must be correct, otherwise an error message, usually "Command not found" will be the only result of running the script.

#! can be omitted if the script consists only of a generic system commands, using no internal directives. Example 2, above, requires the initial #!, the variable assignment line, line=50, uses a shell-specific construct. Note that #!/bin/sh invokes the default interpreter, which defaults to /bin/bash on a Linux machine.

# 2.1. Invoking the script

Having written the script, you can invoke it by sh scriptname, [18] or alternately bash scriptname. (Not recommended is using sh <scriptname, since this effectively disables reading from stdin within the script.) More convenient is to make the script itself directly executable with chmod.

Either:

```bash
chmod 555 scriptname (gives everyone read/execute permission) [9]

chmod +rx scriptname (gives everyone read/execute permission)

chmod u+ scriptname (gives only the owner read/execute permission)
```

or

Having made the script executable, you may now test it by ./scriptname. [10] If it begins with a "sha-bang" line, the script calls the correct command interpreter to run it.

As a final step, after testing and debugging, you would likely like to move it to /usr/local/bin (as root, of course), to make the script available to yourself and all other users as a system-wide executable. The script could then be invoked by simply typing scriptname [ENTER] from the command line.
