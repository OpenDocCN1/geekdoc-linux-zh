Summarizing the symptoms of a buggy script,

+   1. It bombs with an error message syntax error,
2. It runs, but does not work as expected (logic error)
3. It runs, works as expected, but has nasty side effects (logic bomb).

Tools for debugging non-working scripts include

+   1. echo at critical points in the script to trace the variables, and otherwise give a snapshot of what is going on.
2. using the tee filter to check processes or data flows at critical points.
3. setting option flags -n -v -x

```
sh -n scriptname for syntax errors without actually running the script. This is the equivalent of inserting set -n or set -o noexec into the script. Note that certain types of scripts can pass this check.

sh -v scriptname echoes each command before executing it. This is the equivalent of inserting set -v or set -o verbose in the script.
```

The -n and -v flags work together. set -nv scriptname gives a verbose syntax check.

```
sh -x scriptname echoes each result command, but in an abbreviated manner. This is the equivalent of inserting set -x or set -o xtrace in the script.
```

Inserting set -u or set -o nounset in the script runs, but gives an unbound variable error at attempt to use an undeclared variable.

+   4. Using an "assert" function to test a variable or condition at critical points in a script. (This is an idea borrowed from C.)

```
#!/bin/bash
assert.sh

asassert () {
  E_PARAM_ERROR=98
  +# exit from script with error message.
  E_ASSERT_FAILED=99
}

if [ -z "$2" ]; then
  return $E_PARAM_ERROR
  # No damage done.
nfi
```
