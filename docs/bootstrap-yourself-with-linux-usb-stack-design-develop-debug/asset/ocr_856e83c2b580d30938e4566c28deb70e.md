The variable setup_flag indicates whether the data structure object is a setup packet and can hold the following values: 0 (Setup data captured), - (Unable to capture the Setup Packet), and Z (invalid).

```
char setup_flag;
```

The data_flag variable indicates whether the data structure object holds data as part of the event information. It can hold the following values: 0 (data available), ≤ (IN Completion), ≥ (OUT Submit), L (Length is 0), and Z (invalid).

```
char data_flag;
```

The next member, numdesc, maps number_of_packets from the URB structure that indicates the number of isochronous packets.

```
int numdesc;
```

Because this is a debug mechanism for the USB transfers, a complete hook of data from the URB is not required. Therefore, the text version of the usmon maps part of the URB data. The following members capture/hold data based on the transfer type.

```
struct mon_iso_desc isodes[ISODESC_MAX];\unsigned char setup[SETUP_MAX];\unsigned char data[DATA_MAX];
```

From the preceding macros, you can understand that the data field contains only part of the data. The binary version of usmon provides complete information for the URB. However, this extra data is mostly class specific, and packet analyzers that are specific to those modules are more effective than usmon. For example, there are class-specific packet monitors for classes such as mass storage, name scsim. Having a brief overview of the data structure that handles usmon’s URB event, the subsequent section focuses on the sequence flow inside the usmon, how it hooks information, and how it shares hooked information with the user space.

# USB Monitors Internals

Like any other module, usmon extends the Linux kernel details to the user space through a file system. Because the usmon module is for debugging, it debugfs (instead of usbfs), a Virtual File System (VFS) added exclusively to assist export of debug data. You need to mount debugfs to view usmon files in the user space. /sys/kernel/debug is the usual location if you are using Ubuntu.
