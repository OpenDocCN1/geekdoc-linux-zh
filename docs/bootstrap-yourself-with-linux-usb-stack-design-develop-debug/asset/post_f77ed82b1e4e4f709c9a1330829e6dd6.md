In a normal synchronous transfer, the threads use normal read and write operations. These operations are blocking calls in which the function has to wait until the transfer is complete.

```c
status = read(sink_fd, buf, sizeof(buf));
status = write(source_fd, buf, len);
```

An asynchronous input/output (AIO) transfer is ideal for ISO transfers, enable you to submit one or more I/O requests in a system call without waiting for completion.

```c
io_prep_write(iocb, source_fd, buf, fill_in_buf(buf, iosize), 0);
io_set_callback(iocb, in_complete);
iocb->key = USB_DIR_IN;
```

```c
status = io_submit(ctx, 1, &iocb);
if (status < 0) {
    perror(__FUNCTION__);
    break;
}
aio_in_pending++;
```

## SUMMARY

Developing drivers for the Linux kernel is more challenging and time consuming than developing drivers for user mode. User drivers satisfy the needs of protocols as USB. On Linux, libraries as libusb provide a generic driver infrastructure for USB devices that eliminates the need to develop device drivers in the kernel mode. Many USB applications on Linux have adopted libusb as their driver to reduce the developmental effort. Gadget functional drivers as Media Transfer Protocol (MTP) also operate from user mode. The gadgetfs framework makes it easy to write applications and reduces developmental efforts.

For a developer, developing a system is simple, but debugging the same system to find the root cause of the problem requires extra ingenuity. This ingenuity can come from tools that can collect information on the system's state at the time of the problem. The complexity increases when the system to be debugged is part of a kernel subsystem. You can use many approaches to debug a kernel subsystem. Printing debug information in American Standard Code for Interchange (ASCII) text form is a common method developers use to debug modules in the kernel space. However, printing this information has limitations in terms of buffer size available. Also, sometimes an increase in information nullifies the problem.

So what does a protocol system such as universal serial bus (USB) need? In a protocol system, packet transfer detail is the key to debugging. Thus, details of USB transactions between a device and a host help isolate and fix the cause of a problem. Printing of so much information in ASCII text is not advisable from a practical standpoint. Moreover, it is difficult to print complete transaction information from low-level layers in any closed operating system.

Linux is an ideal platform for such debugging because it provides complete access to the entire protocol layer. To debug a USB system, Linux uses the traditional ASCII text printing method, which provides limited user-readable information on USB transactions and a software-based USB packet capture tool usbm that can hook up USB packet transfers and share them to the user through the Linux debug file system.

This chapter explores the tools available on Linux that assist in debugging a USB subsystem. Initially, you learn how to configure USB packet capture usbm on Linux, followed by a quick bootstrap session on the design of usbm and how to use it. This chapter also looks at how to use usbfs_snoop, a lighter tool available on Linux that can capture USB transactions occurring between the user space drivers and uscore module via the usbfs file system. Subsequently, you can see the kernel configuration option to configure verbose debug info of the Linux-USB subsystem.
