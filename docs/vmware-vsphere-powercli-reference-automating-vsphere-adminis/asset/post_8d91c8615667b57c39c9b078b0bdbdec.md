## Resanning for New Storage

Whatever the type of SCSI storage is used, a common task is to rescan the adapter when new storage has been provisioned. You do this either by hot-adding local disks or by providing a new logical unit (LUN) from Fibre Channel or iSCSI SAN. The ESXi host cannot see the newly available storage until a rescan task has been initiated by the adapter.

## CHAPTER 4 • AUTOMATING STORAGE

Prior to vSphere, rescanning was an onerous task in the vSphere Client. It involved navigating to the Configuration menu for the host and moving to the Storage Adapters section and clicking the Rescan task. For a cluster with many hosts, this could take a long time and was very tedious. In vSphere 4, VMware added a Rescan Storage item whenever you right-clicked a Cluster, Folder, or Datacenter, which is still present in the modern vSphere Web Client. Consequently, it becomes much easier to rescan storage for multiple hosts. This functionality is also available from the `Get-VMHost` PowerCLI cmdlet. For example, the code in Listing 4.6 rescans storage for clusters 01 and 02.

### LISTING 4.6 Resanning clusters for new storage

```powershell
Get-Cluster Cluster01, Cluster02 | Get-VMHost | Get-VMHost -RescanAllHBA
```

## Adding Datastores

Now that you have filled your servers with local disk drives, connected them to Fibre Channel or iSCSI SAN, or set up an NFS server, you need to create some datastores you can store your virtual machines on. To do this, use the `New-Datastore` PowerCLI cmdlet (the `New-Datastore` cmdlet can be used to create datastores for any of the supported storage types). The key to get it right with this cmdlet is to understand the types of path you must provide to `New-Datastore`. Paths provided by `Get-SCSILun` cmdlet can prove useful in helping you identify the correct path for each type.

## Local Storage

Let's look at creating a new datastore on local storage. By using the `Get-SCSILun` cmdlet, you can identify the LUN provided by the local SCSI controller. In the next example, we use the fact that we have a Dell ESXi host with a PERC 6/i integrated RAID controller to identify the LUN it provides:

```powershell
$LocalLun = Get-VMHost esxi05* | Get-SCSILun -LunType disk | Where {$_.Model -match "PERC 6/i"}
```

To create a datastore on a LUN, you need to provide what is known as the canonical name to the `New-Datastore` cmdlet. The `$LocalLun` variable includes the `CanonicalName` property, which you can retrieve. It will look something like this:

```powershell
$LocalLun.CanonicalName
aa.60022180a9de3f00114e4d006df11de
```

You can now create the datastore using the `New-Datastore` cmdlet (4.7).

### LISTING 4.7 Creating a datastore on local storage

```powershell
$LocalLun = Get-VMHost esxi05* | Get-SCSILun -LunType disk | Where { $_Model -match "PERC 6/i" }
New-Datastore -VMFS -VMHost esxi05* -Name LocalStorage -Path $LocalLun.CanonicalName
```

## NAME THAT LUN

The Network Address Authority (NAA) identifier seen is an industry standard method of generating a unique number to identify a LUN. This value remains the same when accessed by any ESXi host. In terms of the object returned by the `Get-SCSILun` cmdlet, it is referred to as the `CanonicalName` property—which was the more commonly used term when identifying LUNs in ESX 3.

## SAN Storage

For Fibre Channel or iSCSI storage, you can use the `Get-SCSILun` cmdlet to identify LUNs made available from a particular vendor. For instance, if you have storage from the vendor NetApp, the Vendor property is tagged as NetApp:

```powershell
$iSCILun = Get-VMHost esxi05* | Get-SCSILun -LunType disk | Where { $_Model -match "NetApp" }
```

With SAN-based datastores, you will likely be dealing with multiple datastores. Let's say you need to add 10 new iSCSI datastores; the naming convention for these is iSCSI_01, iSCSI_02, and so on.
