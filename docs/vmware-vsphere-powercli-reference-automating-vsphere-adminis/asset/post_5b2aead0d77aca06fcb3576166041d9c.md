# Interval Manipulation

As explained earlier in the "Understand Some Basic Concepts" section, there are four statistics intervals and one real-time interval, each with its own interval duration. However, the statistics intervals vCenter Server provides are not always the intervals you want to use in your reports.

There are several ways to produce reports with user-defined intervals. Listing 16.17 shows one of the methods. The script generates a report with the average CPU busy metric over a business day for all of the previous week's business days.

```powershell
$esxName = 'esxl.test.local'
$metric = 'cpu.usage.average'
```

```powershell
# Define the time frame
$todayMidnight = (Get-Date -Hour 0 -Minute 0 -Second 0)
$endOfWeek = $todayMidnight.DayOfWeek.value__+1
$Adds(-($todayMidnight.DayOfWeek))
$Start = $endOfWeek.AddDays(-7).AddSeconds(1)

$workingDays = 'Monday','Tuesday','Wednesday','Thursday','Friday'
# Use New-Object to create a DateTime Object from which we will

$businessStart = New-Object DateTime(1,1,1,9,0,0) # 09:00 AM

```

```powershell
# Group per hour
$codeBlock1 = {
$_.Timestamp.Day
}
```

```powershell
# Aggregate value for Business hours
$codeBlock2 = {
if($_.Instance -eq $null -and
$workingDays -contains $_.Timestamp.DayOfWeek -and
$_.Timestamp.TimeOfDay -gt $businessStart.TimeOfDay -and
$_.Timestamp.TimeOfDay -lt $businessEnd.TimeOfDay){
$true
}else{
$false
}
}
```

# Using Workflows

In PowerShell v3 the concept of workflows was introduced. One of the nice features that PowerShell offers is the concept of parallelism. In other words, you can run multiple instances of the same code. This allows you to split single-threaded jobs into many smaller jobs, each running against specific instance or entity.

In Listing 16.18, we retrieve the statistical data for two ESXi nodes. A retrieval task is started for each of the ESXi nodes.

# LISTING 16.18 Parallel Jobs

```powershell
workflow Get-StatData {
Param(
  [string]$vcenter,
  [string[]]$names,
  [string]$session
)
foreach -parallel($name in $names){
$stats = InlineScript{
Add-PSSin VMware
Connect-VIServer -Server $using:vcenter \
-Session $using:session | Out-Null
Get-Stat -Entity $using:name -Realtime \
-Stat cpu.usage.average -MaxSamples 5
}
}
$esxNames = 'esx1.local.test','esx2.local.test'
$data = Get-StatData -names $esxNames -vcenter 'vcenter' \
-session $global:DefaultVIServer.Session
$data | Group-Object -Property Entity
}
```

The code launches a Get-Stat cmdlet in a separate thread against each of the ESXi nodes. Data returns to the caller as one data collection, as demonstrated in our results.

| Count Name | Group |
| :--- | :--- |
| 15 esx2.local.test | {0.38, 0.71, 0.64, 0.37...} |
| 15 esx1.local.test | {1.39, 0.42, 0.36, 0.55...} |

This is, of course, a constructed and meaningless example, but besides retrieving the statistical data, you could also handle the data in each thread. You could do some calculations for each ESXi node; produce the report, and get all the results back in one block after the call to the workflow.

Parallelism with PowerShell workflows should be used with caution. Since you are running multiple threads, the resource consumption on the workstation where you run the script will also increase. Make sure there are sufficient resources available on the workstation.

# Improving Execution Time

As we've said many times before, with PowerShell there is always more than one way to do something. At times, you'll find that the path you chose was not the optimal path. When you are working with lots of statistical data, the execution time of your script can become a critical factor. The following list shows some ways to improve execution time.

- Limit the number of calls to the Get-Stat cmdlet.
- Combine entities.
- Combine metrics.
- Combine groups in one call to Group-Object.
- Use only metrics that are meaningful for your report.

# Offload Statistical Data

As you learned in the "Understand Some Basic Concepts" section, the data for vCenter is kept for one year by default. You can change the retention time to five years, that will increase the size of your vCenter Server database with a possible performance impact.

If you want to be a statistics report on older data, there is another solution. At regular points in time, collect the oldest statistical data you want to use later and store it in an external file. PowerShell provides the Export-Clixml cmdlet to store PowerShell objects in an external file. Later, you can use the Import-Clixml cmdlet to retrieve the objects and bring them back into your PowerShell session.

The script in Listing 16.19 shows some metrics to an external file.

## LISTING 16.19 Exporting statistical data

```powershell
$entityNames = 'esx1*esx2*'
$metrics = 'cpu.usage.average','mem.usage.average',
$disk.usage.average','net.usage.average'
$archiveLocation = 'C:\Archive'

# Time range - 12 months
$monthsBack = 12
$todayMidnight = (Get-Date -Hour 0 -Minute 0 -Second 0)
$xMonthsAgoMidnight = $todayMidnight.AddMonths(-monthsBack + 1)
$endOfMonth = $xMonthsAgoMidnight
```

```powershell
$AddDays = -($xMonthsAgoMidnight.Day)
$Start = $endOfMonth.AddMonths(-1).AddDays(1).AddSeconds(1)
$Finish = $endOfMonth
```

```powershell
# All entities
$entities = Get-VMHost -Name $entityNames
```

```powershell
$archiveFilename = 'Stat-' + $Start.ToString("MM_dd_yyyy") + '-' +
$Finish.ToString("MM_dd_yyyy") + '.xml'
```

```powershell
# Export statistics
Get-Stat -Entity $entities -Stat $metrics -Start $Start \
-Finish $Finish | Export-Clixml \
-Path ($archiveLocation + '\' + $archiveFilename)
```

The following script reads the archive file back into a PowerShell array. You can work with that imported array just as if you had created it with the Get-Stat cmdlet.

```powershell
$archiveFilename = 'C:\Archive\Stat-01_01_2015-31_01_2015.xml'
$stats = Import-Clixml -Path $archiveFilename
```

> **TIP** Make sure you use a filenames schema that clearly defines what kind of data is stored in each file. You could include the entity type, the start and finish dates, the metrics that were used, and similar information.
