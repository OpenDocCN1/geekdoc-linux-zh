process {
    $arrVMHostOfInterest = if ($PSBoundParameters.ContainsKey("VMHost")) {
        $VMHost
    } else {
        Get-VMHost
    }

    foreach ($host in $arrVMHostOfInterest) {
        $arrAdvSettings_theseHosts = Get-AdvancedSetting -Entity $host -Name $arrHardGuideSettingInfo.Name
        $arrAdvSettings_theseHosts | Foreach-Object {
            $thisSetting = $_
            $thisHardItem = $arrHardGuideSettingInfo | Where-Object ($_.Name -eq $thisSetting.Name)
            $isSuggestedValue = $thisSetting.Value -eq $thisHardItem.Value
            
            if ($Remediate) {
                if (-not $isSuggestedValue) {
                    if ($PsCmdlet.ShouldProcess($thisSetting.Entity, ("Set {0} from {1} to {2}" -f $thisSetting.Name, $thisSetting.Value, $thisHardItem.Value))) {
                        Set-AdvancedSetting -AdvancedSetting $thisSetting -Value $thisHardItem.Value -Confirm:$false |
                        Select-Object Entity, Name, Value
                    }
                }
            } else {
                ## else, report the current settings' values, and whether
                # match the values that the hardening guide suggests
                Select-Object -InputObject $_ -Entity, Name, Value,
                @{n="GuidelineId"; e={$thisHardItem.GuidelineId}},
                @{n="IsSuggestedValue"; e={$isSuggestedValue}}
            }
        }
    }
}

Now we made the function easily extensible, too. By using the variable `$arrHardGuideInfo`, an array of `Objects` in the begin block of the `Assert-HardeningGuideESAdvSetting` function, it is trivial to add more guidelines or advanced settings. For example, let's say that VMware has a new guideline recommending “Enable” advanced setting should be set to `True` on all hosts. You can just add another hash table with the pertinent setting name, ID, and value. The subsequent call in the function to the `New-Object` makes another new `Object` from the hash table. The script block will assess and remediate that new `Setting`.

One ESXI-related guideline is `ESXI.firewall-enabled`. The Hardening Guide suggests that you leverage the ESXI host to restrict access to services running on the host. While the PowerCLI remediation value in the Hardening Guide is `N/A`, that may be due to the semi-operational nature of this guideline. It is not a blanket, but depends on your particular environment and rules for your ESXI hosts. For example, if you use NFS 4.1 datastores, syslog, and NSF, you would have the `nfs4Client`, `NSX Distributed Router Service`, and `syslog VMHost` firewall exceptions enabled, allowing such traffic in and out of the ESXI host. So, when looking at enabled firewall exceptions on a VMHost, you need to consider what features you are using, which will dictate which exceptions you enable.
