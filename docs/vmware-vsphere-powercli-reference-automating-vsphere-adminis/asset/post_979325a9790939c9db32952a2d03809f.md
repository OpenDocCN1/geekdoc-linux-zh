
# Alarm Actions

Alarm actions are many and varied. Some are quite simple to work with, such as group, method, task, and SNMP actions. We'll provide an overview of those actions. Others, like script or email actions, are more flexible and complex. We will cover those in greater detail.

### Grouping Actions The API Reference indicates that you can have a single AlarmTriggeringAction without GroupAlarmAction. It is possible to define an alarm with a single action, but the problem comes when you try to edit the settings of that alarm from the vSphere Client; Edit Settings option is gray out. The vSphere Web Client has an even worse issue; an error will be generated when you try to edit the alarm. For that reason we advise you to specify your actions, even if it is only one action, under GroupAlarmAction where these issues do not occur.

> NOTE If you want to create an alarm without any actions, there is no need to specify either an AlarmTriggeringAction or a GroupAlarmAction.

### Method Action Method actions are only available for HostSystem and VirtualMachine objects. Using a method action, you can call any SDK method that is available on the HostSystem or VirtualMachine object that fired the alarm.

### Task Action Task actions are also only available for HostSystem and VirtualMachine objects. You can call any of the tasks that are available on the extensions over your vCenter Server.

### SNMP Action Simple Network Management Protocol (SNMP) actions are the simplest of all actions. They don't require any parameters. The SNMP trap will be sent to the SNMP communities you define in your vCenter Server.

# Script Actions

Script actions take one parameter—the command that you want vCenter Server to execute when an alarm is fired. There can be some issues related to how you achieve this, in particular with the security account used to execute the script and the privileges within vCenter Server are required. We prefer to take the following approach:

- The vCenter Server runs with a domain account. Consequently, the scripts execute through the Security Support Provider Interface (SSPI) and use single sign-on to connect to vCenter Server. Therefore you do not need to specify credentials.
- The domain account that the vCenter Server runs holds the required privileges within vCenter's permission model to execute whatever you want to accomplish in the script.

Unlike the code you'll see, the actual text for the Configuration field in the Actions section of the Edit Alert wizard is entered in one line, with no carriage or linefeeds. (We had to break the text into three lines; it's too long to fit the page.) For a 64-bit OS, like Windows 2012, it would look like Listing 17.2.

## 17.2 An example script

```
C:\Windows\System32\cmd.exe /powershell
-PSConsoleFile C:\Scripts\MyConsole.ps1 -noninteractive
-profile file C:\Scripts\Alarm-action-script.ps1
```

A common method for monitoring processes on Windows server is to use the Process Explorer from Microsoft's Sysinternals website at http://sysinternals.com. When you use Process Explorer on your vCenter Server, you can see how vCenter Server runs your alarm script. Process Explorer allows you to see the parameters that are used for each of the spawned processes. Open the properties of the cmd.exe and the powershell.exe processes. Process Explorer also allows you to verify when your alarm script is finished. Just check whether the cmd.exe and powershell.exe processes have disappeared below the vpxd.exe process.

In Listing 17.2, notice the use of the console file on the command line. With this file, you can define the snap-in(s) that need to be loaded into the PowerShell session that will run your script.

> A PowerShell console file is an XML-based file that contains details of PowerShell snap-ins and is saved with a *.pscl extension. PowerCLI clips with a console file, vim.pscl, in the installation directory. You can also create your own console file using the Export-Console cmdlet.

Script actions can take a bit of time to completely execute. This depends on the load of your vCenter Server but also on the number of snap-ins you are loading through the console file. Be patient when you want to check the results of your alarm script. On the command line, you can pass one or more of the predefined variables that vCenter Server provides. Again, you'll enter the information on one line with carriage returns or line breaks (Listing 17.3).

## 17.3 An example alarm script with predefined variables

```
C:\Windows\System32\cmd.exe /c powershell.exe
-ConsoleFile C:\Scripts\MyConsole.ps1 -noninteractive
-profile file C:\Scripts\Alarm-action-script.ps1 {targetName}
```

Note that these parameters are sensitive. That means, for example, you can't use `targetName`. Find the complete list of parameters in the vSphere 6.0 Documentation (http://docs.vmware.com). The script can access these parameters as regular PowerShell parameters. In other words, you can use the `$alarm` variable or define a `param` statement in your script. Before using your script in an alarm, it's a good idea to test it as an individual piece of code. That way, you can guarantee it is going successfully as part of the alarm and there will be no issues as the local security policy preventing its execution or problems with vCenter Server.

If you want to capture the execution of the alarm, the method is to pipe all output to the `Out-File` cmdlet. That way, all output from the script is captured in a file. An alarm script logs the parameters it receives to a file could look like this:

```
$OutFile = C:\alarm.log
$Args | Out-File $OutFile -Append
```

There is an alternative for accessing information about the alarm that triggered your script. vCenter Server spawns your alarm script with a number of environment variables that contain information about the alarm that triggered the script. You can find the complete list of these environment variables in the vSphere 6.0 Documentation (http://docs.vmware.com). A summary of these and typical values can be found in Table 17.6.

You can use these environment variables in script through the environment variable provider. A short example is shown in Listing 17.4.

## LISTING 17.4 Environment variable provider example

```powershell
$outFile = "C:\outfile.txt"
$report = @()
$report += ("Time:" + (Get-Date).ToShortTimeString())
$report += ("Alarm:" + $env:VMWARE_ALARM_NAME)
$report += ("On:" + $env:VMWARE_ALARM_TARGET_NAME)
$report += ("User:" + $env:VMWARE_ALARM_EVENT_USERNAME)
```

$report | Out-File -FilePath $outFile
```

This script will produce something like this:

```
Time: 3:21 AM
Alarm: Change custom field
On: PCI
User: TEST\administrator
```

If you are using PowerCLI cmdlets in your script, you will need to connect to a vCenter Server and have PowerCLI installed on that server. As we said earlier, these alarm scripts are spawned from the vCenter service; make sure that your script runs with a domain account that has the required privileges. That way, you can connect through SSPI and you don't have to provide credentials.

The environment variables that are available in the alarm script contain a number of ID values. For example, the VMware_ALARM_TARGET_ID variable (see Table 17.6). Unfortunately, this is not the kind of ID that can be used in a PowerCLI cmdlet Get-View. Consequently, it is much better to use the environment variables with a suffix. These contain the name of the vSphere entity that you can use to access (through the PowerCLI cmdlets) the vSphere object. The code in Listing 17.5 shows you how, for example, the VMware_ALARM_TARGET_NAME variable to retrieve the virtual machine and database.

## LISTING 17.5 Accessing vSphere objects in an action script

```powershell
$outFile = "C:\output.txt"
$report = @()
Connect-VIServer -Server vSphere
$vm = Get-VM -Name $env:VMWARE_ALARM_TARGET_NAME
$ds = Get-Datastore -VM $vm

$report = @(
$report += "Time:" + (Get-Date).ToShortTimeString())
$report += "Alarm:" + $env:VMWARE_ALARM_NAME)
$report += "On:" + $env:VMWARE_ALARM_TARGET_NAME)
$report += "User:" + $env:VMWARE_ALARM_EVENT_USERNAME)
$report += "DS:" + $ds.Name
)

$report | Out-File -FilePath $outFile
```
