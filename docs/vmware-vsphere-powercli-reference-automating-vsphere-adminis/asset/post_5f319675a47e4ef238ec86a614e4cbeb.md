
# ZIP Files

New VMware patches are distributed in ZIP format, which is supported by the PowerCLI Core cmdlet Install-VMHostPatch. There are a few different ways to make the patch file accessible to the ESXi host to be updated. If the patch needs to be deployed to more than one host, then it makes good sense to copy that patch to a shared datastore that is available to all the hosts requiring it. Listing 14.21 demonstrates how to copy a folder patches for vSphere 5.5 U2 to a shared datastore.

## 14.21 Copying a patch to a shared datastore

```
$Datastore = Get-Datastore "NFS10"
New-PSDrive -Location $Datastore -Name ds -PSProvider \
VimDatastore -Root "\"
New-Item -ItemType Directory 'ds:\Patches-from-esxi5.5-5.5_update02'
Copy-DatastoreItem 'C:\Scripts\update-from-esxi5.5-5.5_update021*' -Recurse \
Destination=$ds:\Patches-from-esxi5.5-5.5_update02
```

Now that the patch files are available to ESXi hosts via a shared datastore, you can run the commands in Listing 14.22 to install the patch. Note that Install-VMHostPatch requires the full path to the metadata.zip file in the folder containing the patches.

## 14.22 Installing a patch with Install-VMHostPatch

```
$Datastore = Get-Datastore "NFS10"
$FilePath = 'Patches/update-from-esxi5.5-5.5_update02/metadata.zip'
$DatStoreURL = $Datastore.ExtensionData.Info.Url -Replace 'ds://'
$FullPath = $FilePath
$VMHost = Get-VMHost vesxi10.sunnydale.local
$VMHost = Set-VMHost -State Maintenance -Confirm:$false
$VMHost = Install-VMHostPatch -HostPath $FullPath
$VMHost = Restart-VMHost -Confirm:$false
```

# VIB Files

Patches and plug-ins from VMware and other third-party vendors are distributed in VIB format. Typically, the documentation for installing VIB files by VMware or the third party will involve using the ESXi command-line tool esxcli. You can use the PowerCLI cmdlet Get-EsXcli to access the same functionality.

Again, the VIB file first be made accessible to each ESXi host that needs it via a shared datastore. Use the code in Listing 14.21 to then demonstrates how to use Get-EsXcli to install an example third-party Broadcom tg3 async driver from the VMware Download website, Listing 14.23 shows how it has been uploaded to a shared datastore.

**LISTING 14.23** Installing Broadcom driver with Get-EsXcli

```
$Datastore = Get-Datastore "NFS10"
$FilePath = 'Patches/Broadcom/async/net-tg3-3.133d.v55.1-10EM.550.0.0.119611.x86_64.vib'
$DataStoreURL = $Datastore.ExtensionData.Info.Url -Replace 'ds://'
$FullPath = $DatastoreURL + $FilePath
$VMHost = Get-VMHost sunnyydale.local
$VMHost | Set-VMHost -State Maintenance -Confirm:$false
$EsXcli = $VMHost | Get-EsXcli
$EsXcli.software.vib.update($null,$false,$false,$false,$false,$false,
	$true,$null,$null,$FullPath)
$VMHost | Restart-VMHost -Confirm:$false
```

## The Basics

To get started, let's begin with some basic concepts. Besides a brief introduction to the PowerCLI cmdlets which allow you to retrieve information, this section introduces some techniques for ordering and grouping the data presented through objects. The basic building block that you will use for creating reports are the numerous cmdlets. Get-VM usually returns one or more objects; each holds a number of properties that you can select for your report. Consider the next example:

```
Get-VM
```

| Name | PowerState | Num CPUs | MemoryGB |
| --- | --- | --- | --- |
| VM3 | PoweredOff | 1 | 2.000 |
| VM2 | PoweredOff | 1 | 2.000 |
| VM1 | PoweredOff | 1 | 4.000 |

The Get-VM cmdlet in this example returned three objects that each represent a virtual machine (VM). Remember that the PowerCLI cmdlets display only a limited set of the available properties. With the Get-Member cmdlet you can see all the properties on an object. For example:

```
Get-VM | Get-Member -MemberType Property | Select-Object --Property Name
```

Note that the last example only shows some of the available properties; there are many more. Once you have determined which properties you want to include in your report, start composing you with Select-Object line:

```
Get-VM | Select-Object -Property Name, PowerState, GuestId, VMHost | Format-Table -AutoSize
```

| Name | PowerState | GuestId | VMHost |
| --- | --- | --- | --- |
| VM3 | PoweredOff | windows_64Guest | es61.local.test |
| VM2 | PoweredOff | windows_64Guest | es61.local.test |
| VM1 | PoweredOff | windowsServer64Guest | es62.local.test |

In the example, you piped the result of the Select-Object cmdlet to the Format-Table cmdlet with the AutoSize switch. This makes the output more compact. Although you can create great reports with the available properties there are occasions when you want to display derived or more complex information in your report. That is where the calculated property is your friend. A calculated property is in fact a hash table with two elements: a name and an expression. In the expression element, you can provide value for the property that you define in the name element.

The VirtualMachine objects that by default returned by the Get-VM cmdlet include a property called ProvisionedSpaceGB, but since that property is defined as a decimal, it is displayed with a long series of values to the right of the decimal:

```
Get-VM | Select-Object -Property Name,PowerState,ProvisionedSpaceGB | Format-Table -AutoSize
```

| Name | PowerState | ProvisionedSpaceGB |
| --- | --- | --- |
| VM3 | PoweredOff | 34.14025686215609312057495172 |
| VM2 | PoweredOff | 34.14025686215609312057495172 |
| VM1 | PoweredOff | 44.14025686215609312057495172 |

In the next example, we used a .NET method from the System.Math class to round the decimal and display the data in a more user-friendly fashion.

```
Get-VM | Select-Object Name,PowerState,
@{N='ProvSpaceGB';E={[Math]::Round($_.ProvisionedSpaceGB,1)}}
| Format-Table -AutoSize
```

| Name | PowerState | ProvSpaceGB |
| --- | --- | --- |
| VM3 | PoweredOff | 34.1 |
| VM2 | PoweredOff | 34.1 |
| VM1 | PoweredOff | 44.1 |
