
# CHAPTER 7 • USING TEMPLATES AND CUSTOMIZATION SPECIFICATIONS

## Maintaining Templates

Templates are an incredibly powerful tool—one critical to the VM life cycle. It is, however, important to keep templates up to date. It's a level-of-effort deal; it's easier to maintain one template than it is to patch or update many VMs postdeployment. Some companies choose to update their templates quarterly and rely on their management tools to fill that gap. We find this foolish: regardless of how good an enterprise tool is, why cycles on a fresh guest deployment when it is easier to just maintain the source template? Whatever the decisions, just remember: PowerCLI is here to assist. With that in mind, there are a few common issues, but one universal pain point with templates.

No matter what you're doing, the first step is always to convert a template into a VM and the last is to convert back to a template. You might or not need to power on the VM in the middle of the process. You will find that you constantly account for the state of the VM during any update. To assist in this trivial task, you can use Wait-VMQuest function (see Listing 7.15).

## LISTING 7.15 The Wait-VMQuest function

```powershell
function Wait-VMQuest {
  [CmdletBinding(DefaultParameterSetName='VM')]
  [parameter(Position=0)
      ParameterSetName='VM'
  )
  [parameter(Position=0)
      ParameterSetName='Guest'
  )
  [ValidateSet("Startup","Shutdown")]
  [string]
  $Operation

  [parameter(Mandatory=$True)
      ValueFromPipeline=$True
      ParameterSetName='VM'
  )
  [VMware.VimAutomation.ViCore.Impl.Vl.Inventory.VirtualMachineImpl]
  $VMn

  [parameter(Mandatory=$True)
      ValueFromPipeline=$True
      ParameterSetName='Guest'
  )
  [VMware.VimAutomation.ViCore.Impl.V1.VM.Guest.VMGuestImpl]
  $Guest

}

Process {
  if ($PSCmdlet.ParameterSetName -eq 'Guest') {
    $VM = $VMGuest.VM
  }

  Switch ($Operation) {
    "Startup" {
      while ($vm.ExtensionData.Guest.ToolsRunningStatus -eq "guestNotRunning") {
        Start-Sleep -Seconds 1
        Write-Verbose "Waiting on VMware tools start for ${(vm.Name)"
        $vm.ExtensionData.UpdateViewData("Guest")
        # return a fresh VMOObject
        Write-Output (Get-VM $VM)
        break;
      }
    }
    "Shutdown" {
      # wait for the VM to be shut down
      while ($VM.ExtensionData.Runtime.PowerState -ne "poweredOff") {
        Start-Sleep -Seconds 1
        Write-Verbose "Waiting for ${(vm.Name) to power off"
      }
    }
  }
  $VM.ExtensionData.UpdateView("Runtime.PowerState")
  # return a fresh VMObject
  Write-Output (Get-VM $VM)
}
```

Wait-VMQuest simplifies the code required to update a template by pausing the pipeline while the target VM either shuts down or starts up. Take note of the way it streamlines the VM. Imagine having to put the pipeline into a loop every time a VM is power-cycled. Doing so would break the streaming nature of PowerShell. The Wait-VMQuest function enables the pipeline to stream while still waiting.

## WHAT'S WRONG WITH START-VM/STOP-VM?

> Create a new function? Why not just Start-VM or Stop-VM with -RunAsync and pipe that into Wait-Task?

Wait-VMGuest function was designed for situations where you need the VM to be all the way up and stood or the way down and powered off before you release the pipeline. While automating a situation like this, one of the authors started with Start-VM/Stop-VMGuest and was shocked to discover they only waited for the task to clear vCenter Server. PowerCLI provides the Wait-Cmdlet, but it only helps with starting a VM.

## Upgrading Hardware

Although this doesn't come very often, if a heavy investment was made previously and an organization has amassed a vast collection of templates in a previous version of vSphere, they might want to upgrade all templates to the latest hardware version to take advantage of new capabilities. Fortunately, this is one of those tasks that lends itself to automation. In Listing 7.16 we'll update the template to hardware version 11.

## LISTING 7.16 Update VM hardware version

```powershell
$VM = Get-Template "v7k8" | Set-Template -ToVM
$VM.ExtensionData.UpgradeVM("vmx-11")
Set-VM $VM -ToTemplate
```

As tasks, this is easy. Get the template object and convert it into a VM. Then, call the UpgradeVM method on the virtual machine to perform the upgrade. Finally, convert the VM back into a template. There is one problem, though: VMware requires that current version of VMware Tools be installed prior to upgrading a VM’s hardware version—which means forcing the upgrade (which is dangerous) or handling the tools upgrade as well (which is complicated). The script in Listing 7.17 forces the upgrade and upgrades the hardware version in one action.

## LISTING 7.17 Forcing a VM hardware upgrade

```powershell
$VM = Get-Template "vm01" | Set-Template -ToVM
$taskMoreRef = $VM.ExtensionData.UpgradeVM_Task("vmx-11")
$task = $taskMoreRef
while ($task.Info.State -eq 'running') {
    $task.UpdateView("Info.State")
    $Question = Get-VM $VM
    Answer-VM $Question -DefaultOption -Confirm:$false
}
Set-VM $VM -ToTemplate
```

There are scenarios where it makes sense to force an upgrade. For example, if the template didn’t have operating system or VMware Tools installed, there is no choice but to force the upgrade. Best practice is to always have VMware Tools installed, and a template will almost always have operating system. How does one safely automate an upgrade when operating system or VMware Tools are missing? Before we get into the actual code, let’s talk about what safe hardware upgrade entails. First, the template must be converted back into a VM to make it writable. Then, VMware Tools need to be upgraded. Once upgraded, the VM needs to be powered off. Then, the hardware version can be upgraded. For good measure, the template should be powered back on to see how it went.

Listing 7.18 breaks that process into code.

## LISTING 7.18 Safely upgrading the VM hardware

```powershell
# get our template, convert it to a VM, and power said on.
$VM = Get-Template 'vm01' | Set-Template -ToVM | Start-VM | Wait-VMGuest Startup
# kick off a tools update and wait for it to finish.
Update-Tools -VM $VM
Stop-VM $VM -Confirm:$false | Wait-VMGuest Shutdown Out-Null
# Perform the hardware upgrade
$vm.ExtensionData.UpgradeVM("vmx-11")
# Power on our VM
Start-VM -VM $VM
# Log in and make sure the upgrade went okay.
# Power our VM back down
$VM = Stop-VM $VM -Confirm:$false | Wait-VMGuest Shutdown
# Convert back to template
Set-VM $VM -ToTemplate -Confirm:$false
```

Very straightforward! Given enough templates to justify the investment, it is possible to fully automate the complete upgrade cycle. The Update-TemplateHardware function in Listing 7.19 does just that. This script handles the complete upgrade cycle and performs checks before making any modification to ensure it's only affecting templates that require an update.

## LISTING 7.19 Update-TemplateHardware

```powershell
function Update-TemplateHardware {
  [CmdletBinding()]
  param(
    [parameter(Mandatory=$True)
      ValueFromPipeline=$True
      HelpMessage='Template object to upgrade')
    VMware.ViAutomation.ViCore.Impl.V1.Inventory.TemplateImpl
    $Template

    [parameter()]
    [ValidatePattern("vmx-\dd")]
    [string]
    $Version="vmx-11"
  )

  Process {
    # Convert our template back to a VM, and PowerOn.
    $VM = Set-Template -Template $Template -ToVM

    #check VM Hardware version
    if ($VM.ExtensionData.Config.Version -ne $Version) {
      Write-Host "VM Hardware version out of date!" -ForegroundColor 'RED'
      $VM = Start-VM -VM $VM | Wait-VMGuest Startup
    }

    # Check VMware tools version if tools are out of date
    # upgrade them.
    if ($VM.ExtensionData.Guest.Status -ne "ToolsOk") {
      Write-Host "VMware tools are out of date!" -ForegroundColor 'RED'
      #Kick off a tools update
      Try {
        Update-Tools -VM $VM
      }
      Catch {
        Write-Warning $_.Exception.Message
        break;
      }
    }
  }
}
```
