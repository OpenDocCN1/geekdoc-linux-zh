## 如何使用Otto
以下是Otto的一个用例示例，展示了在AWS上部署Rails应用程序的开发和部署步骤。

1. **启动你的Rails项目**
   使用默认配置初始化一个新的Rails应用程序：
   ```
   $ rails new
   ```

2. **编译和配置**
   Otto的编译步骤会自动检测应用程序类型为Rails，然后准备Docker来管理你的应用程序生命周期。你可以通过编写Ottofile来定制Otto行为的几乎所有方面。
   ```
   $ otto compile
   ```

3. **本地开发**
   Otto构建并运行一个本地开发环境，这样你就可以轻松测试和修改你的应用程序：
   ```
   $ otto dev
   ```

4. **构建基础设施**
   Otto根据行业最佳实践创建一个基础基础设施：
   ```
   $ otto infra
   ```

5. **构建你的应用程序**
   Otto打包你的应用程序，并准备好将其部署到你的基础设施中：
   ```
   $ otto build
   ```

6. **部署**
   你的Rails应用程序被转换为运行中的基础设施——你的应用程序现在可供全世界访问：
   ```
   $ otto deploy
   ```

而且想法是你只需要定制上述的细微差异。你不需要重新编写公共部分。

第二件事是部署。早在多年前，在Vagrant 0.1或0.2的时候，我们就收到一个功能请求：“我能不能用vagrant up部署到生产环境？”多年来我们一直试图实现这一目标，最终我们发现Vagrantfile并不是描述如何将某物部署到生产环境的合适方式，因为一方面Vagrantfile描述了许多机器层面的事情，很难将其转换为像AWS这样的环境，另一方面它还描述了许多你在生产环境中不需要的开发相关配置。所以我们尝试了许多方法，但感觉最好的方案是重新创建一个全新的文件——你会有一个用于开发的Vagrantfile和用于生产的其他配置文件，但这感觉很奇怪。我们为解决这个问题所做的主要事情是提高了一层抽象。通过描述应用程序而不是机器，我认为我们拥有了能够同时处理开发和生产环境的正确配置。

第三件事是微服务。正如我所说，这目前还不是主流，但增长迅速。在一个Vagrantfile中描述所有依赖关系很难，而使用多虚拟机对微服务来说太重了。如果你有六个微服务，那你就要运行六个虚拟机，这会拖垮许多基础开发机——多虚拟机本来就不是为微服务设计的。

**很多人转向了Docker，对吧？**
是的，我们看到很多人试图使用Docker来开发微服务。Docker在打包微服务方面非常出色——将微服务封装在容器中是使其易于运行的好方法。从Vagrant的角度来看，我们发现使用Docker并没有真正解决所有问题。虽然打包问题解决了，但安装哪些服务以及如何配置它们的负担仍然落在最终的应用程序开发者身上。所以如果你在开发一个应用程序，你就必须知道所有的依赖关系——你仍然需要了解这些——但你还必须知道它们所有的依赖关系。我们在Otto中采取的方法是，你只需要告诉Otto你的直接依赖关系——Otto会找出你的传递依赖关系，然后由该依赖关系告诉Otto如何安装、运行和配置它。

**你认为学习曲线会怎样？**
我认为，从开发角度来看，对于Vagrant用户来说会非常熟悉。Otto本身不同，所以这需要一些习惯，但`otto dev`类似于`vagrant up`，`otto dev`类似于`vagrant ssh`。`otto dev destroy`类似于`vagrant destroy`；有很多相似之处。同时，从开发角度来看，Otto将会为你做很多事情，Vagrant开发者会非常喜欢。它自动找到一个不冲突的IP地址并给机器一个静态IP，所以你不再需要配置网络。有一个命令可以获取该地址——`otto dev address`——所以你不需要像使用Vagrant那样记住它。

部署方面对我们来说是新的，所以我们试图建立一个像Vagrant一样简单的工作流。不过，我认为，不幸的是，Otto的学习曲线将会很低。这种简单性的代价是Otto为你做了很多决定——我们完全预期这会让人们感到不舒服。但如果你觉得不舒服，并且这是一个合理的原因，那么我们希望听到你的声音，以便我们可以将这种知识编码到Otto中，让它做出让你感到舒适的选择，如果这是行业最好的选择的话。

# 评论

## 内核专栏

Jon Masters总结了Linux内核社区的最新动态，随着Linux 4.3的发布，4.4的开发工作正在进行

![](img/0fc17bd4c29dc437e3ac28a53f7559db_15_0.png)

**Jon Masters**
是一位Linux内核黑客，从事Linux工作已有19年，自13岁首次进入大学以来。Jon居住在马萨诸塞州剑桥市，为一家大型企业Linux供应商工作，在那里他正推动制定基于ARM的低功耗服务器标准。

Linus Torvalds宣布Linux内核4.3版本发布，并指出在开发周期的后期，修复工作似乎有点忙碌，但“实际查看数据显示，那只是我主观的感觉，可能是由于内核峰会和从韩国回家的旅行造成的”。最新内核包含几个令人兴奋的新功能——PIDs控制器的用户空间缺页中断（user space page faults）就是其中之一——同时也移除了久经考验的ext4文件系统（尽管读者不必为此担忧，稍后我们会解释）。

Linux 4.3中的PIDs控制器功能基于一个简单的想法：防止曾经在旧Unix系统上常见的“fork炸弹”攻击。在fork炸弹中，攻击者运行代码试图创建尽可能多的新进程，从而占用系统RAM和计算机资源。因此，Linux（和Unix）系统长期以来一直对允许的最大进程数（在内核中被称为任务）实施看似任意限制。事实上，在一台Fedora笔记本电脑上，**ulimit**命令显示作者的用户账户（默认情况下）被限制最多创建1,024个进程。但是，在用户级别设置限制是非常**粗糙**的。新的控制器组方法允许一组进程（例如作为容器一部分启动的进程）限制它们创建更多进程的能力。

Linux 4.3中对用户空间缺页中断的支持将为包括虚拟化在内的多个领域带来新的能力。虚拟机、chrun（在Linux上运行KVM时），利用现有的“宿主”内核提供所需的大部分支持驱动程序和基础设施，同时将运行的VM抽象为一个常规进程。该进程基于修改后的QEMU有一个用户空间组件，提供模拟提供给VM的硬件（和其他资源）的支持能力。现在，QEMU也可以代表虚拟机在实时迁移活动期间处理缺页中断，从而允许在迁移过程中以非常轻量级的方式跟踪运行中机器的内存修改，最终加快实时迁移速度并减少对VM的延迟影响。

随着Linux 4.3的发布，合并窗口（这段时间——通常持续略短于两周——允许对最终将成为Linux 4.4的版本进行破坏性更改）也开启了。此时，正在跟踪以便纳入4.4的一个更有趣的功能是**richacl**（也称为**native**，未映射到**POSIX**，NFSv4 **ACLs**在文件系统中），这对网络和 enterprise 用户尤其重要。我们将在下期的杂志中全面总结那些被纳入4.4的功能。与此同时，看到对超低成本CHIP“9美元计算机”（基于sunxi 32位ARM芯片）的支持可能赶上首批发货时间并进入4.4，这也是令人兴奋的。

最后这个月，让我们为Jaccon Bastiaansen留一点思考空间，他发布了一篇长消息，标题为“内核‘futex代码’中可能存在竞态条件”，描述了他在一台8核64位“实时”（因此引用了-rt58补丁集）x86系统上使用较旧的3.12/4.2-rt58内核的情况。他的配置利用了50个线程、自定义内存分配器以及初始消息中描述的各种其他复杂性。这个故事有趣的部分在于他（以及消息中暗示的一些同事）为了找出问题的根本原因所投入的程度。

Jaccon描述了Linux的“pthreads”（**POSIX线程**）代码是如何失效的，声称两个线程同时获取相同的futex（一种用于表示快速用户互斥锁的结构——因此称为“futex”——否则也称为锁）时出现了死锁条件。他最终发现，他的内核的编译版本（通过反汇编器运行后）显示内核在不安全且非原子的字节级访问中检查锁，而本应使用字（在Intel上意味着4字节）检查。这个问题在某些编译器版本上与他较旧的内核是可以复现的，但正如Thomas Gleixner指出的那样，它已在新内核中得到修复。这个线程的深度阅读价值很高：[https://lkml.org/lkml/2015/10/5/400](https://lkml.org/lkml/2015/10/5/400)。
