# Become a Kubernetes

Kubernetes (ku-be-ner) is the leading orchestration tool today, and it comes from Google. Google, the origin of Kubernetes, is an internal Google project that was used to run most of Google's applications including its search engine, Google Maps, and more. When Google declassified and published a paper about it in 2015, the master project revealed that Borg was the orchestration behind Kubernetes.

Borg is a system that manages clusters in Google's data centers and keeps Google's applications, both production and development despite hardware failure, resource exhaustion or other issues that might have otherwise caused an outage. By carefully monitoring the thousands of nodes that make up Borg and the containers running on them, starting or stopping containers as required in response to problems or fluctuations in load.

Kubernetes was born out of Google's GAFEE (Google's Infrastructure For Everyone), and was designed to be a friendlier version of Borg that could be useful outside Google. It was donated to the Linux Foundation in 2015 through the formation of Cloud Native Computing Foundation (CNCF).

Kubernetes provides a system to "declare" your container applications and services, and it makes sure your applications run according to those declarations. If applications require external resources such as storage or network, Kubernetes can provide them automatically. You can scale your applications up or down with a few commands, and scale the whole cluster with ease. Your Kubernetes ensures that you don't need to know where they run; Kubernetes provides naming services to applications so that they can connect to "endpoint" and be seamlessly connected across components.

The end result is a platform that can be used to run your applications, from a single cluster on an on-premise rack of servers to virtual machines in the cloud, using the same containers and configuration. Kubernetes is provider-agnostic: run it

Kubernetes is a powerful tool, and is nearly complex. Before we get into an overview, we need to introduce terms within Kubernetes. Container run-applications above are grouped into pods. A pod is a group of closely linked containers that are deployed on the same host and share resources. The containers in a pod can perform functions, such as an application and a logging container with specific services for the application.

Kubernetes components are the API Server, the Scheduler, Controller Manager and the configuration database etcd. The API Server is the heart of Kubernetes, and endpoint management controllers may be generated by sources including Kubernetes components, such as the scheduler, via command line or web-based interfaces. It validates requests and updates data in etcd.

The Scheduler decides which nodes pods will run on, taking into account constraints such as resource requirements, hardware or software constraints, workloads, and deadlines.

Each node communicates with the API server and containers—using Docker and Kube-Proxy, which handle proxying and load balancing within the cluster.

The etcd distributed database system gets its name from alert on Linux systems, which is used to store configuration information; the suffix ‘cd’ is used to denote data. The API server keeps all state in the cluster. The scheduler and controller manager can have only one instance. This means that Kubernetes can run Highly Available without single points of failure.

# Putting it all together

How do we use these components in practice? This follows an example of setting up WordPress using Kubernetes. If you wanted to do this alone, you would probably use a recipe called Helm. Helm is available for a number of common applications, but here we will look at the steps to get WordPress up and running.

The first task is to define MySQL: `kubectl create secret mysql --literal-password=` will talk to the API Server, which will validate the command. Our services are defined in YAML, and we need some persistent storage for MySQL.

apiVersion: v1
kind: PersistentVolumeClaim
name: mysql-claim
labels:
  app: wordpress
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    storage: 20Gi

The specification should be self-explanatory. The name and labels are used to refer to this storage from other parts of Kubernetes, which is why we define them.

Once we've defined the database, we define a MySQL instance, pointing to the predefined storage. That follows by defining the database itself; we get the name and label for each service.

Now we need another container to run WordPress.

kind: Deployment
name: wordpress
labels:
  app: wordpress
spec:
  type: Recreate

The strategy ‘Recreate’ means that if any of the code changes, the running instance will be deleted and recreated. Other options allow creating new instances in running while removing existing ones, which can be useful during deployment of an update. Finally, we create a service for WordPress itself, using PHP and Apache. Part of the YAML is:

kind: Service
name: wordpress
labels:
  app: wordpress
spec:
  ports:
    - port: 80
  selector:
    app: wordpress
  type: LoadBalancer

Note the last line, defining type as LoadBalancer. That instructs Kubernetes to make the service available outside of Kubernetes. Without it, the service line would be an internal ‘only’ service.

And that Kubernetes will use those YAML files, as a declaration of what is required, and will set up pods, connections and so on as required to get the cluster into the “desired” state.
