# TAMING THE CLOUD

Tiger Computing's Edmunds reveals how Kubernetes can be used to build a secure, resilient and scalable Linux infrastructure. When you want to use Linux to provide services to a business, those services will need to be secure, resilient and scalable. Nice words, but what do we mean by them? 'Secure' means that users can access the data they require, be read-only or access write at the same time, no data is exposed to any party that's not authorized to see. Designing in security from the start of a project is far easier than trying to retrofit it. 'Resilient' means your services tolerate failures within the infrastructure. A failure might be a server controller that can no longer access disks, rendering the data unreachable. The failure might be a network switch that no longer enables two or more systems to communicate. In this context, a 'single point of failure' or SPOF is a failure that adversely affects availability. A resilient infrastructure is one with no SPOFs. 'Scalable' describes the ability of systems to handle spikes of demand gracefully. It dictates how easily changes may be made. For example, adding a new user, increasing the storage capacity or moving an infrastructure from Amazon Web Services to Google Cloud – or moving it in. As your infrastructure expands beyond one server, there are lots of options for increasing the security, resilience and scalability. We look at how these problems have been solved traditionally, and what new technology is available that changes the face of big computing.

To understand what's possible today, it's helpful to look at how technology projects have been traditionally implemented. Days ago – more than 10 years ago – businesses would buy or learn to handle the cost of their applications. Even installing and maintaining them. Even simple applications, such as a website, have multiple components. In the case of WordPress, a MySQL database is needed with a web server, such as Apache, and with Apache handling PHP code. So, they'd build it up Apache, PHP and MySQL instead of WordPress and off it today. And by lately, that argued that there are still a large number of hurdles to configure. But it wasn't perfect, and many of the bigger problems were resilience and scalability. Lack of resilience meant that any issue on the server would result in a crash. A clear failure meant no website, but there was no room to go out scheduled maintenance without impacting and activating a recovery service would mean a few seconds outage for the website. The resilience problem was solved by building "high availability clusters". The principle was to have two servers running the cluster, so if that failed the website wouldn't result in being down. The service proved resilient even if the individual servers were not.
