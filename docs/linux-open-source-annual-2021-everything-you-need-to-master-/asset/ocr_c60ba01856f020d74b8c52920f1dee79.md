The Controller Manager monitors the state of the cluster, and will try to start or stop pods as needed, via the API Server, to bridge the cluster to the desired state. It also manages internal connections and security tokens.

Each node communicates with the API server and containers—using Docker and Kube-Proxy, which handle proxying and load balancing within the cluster.

The etcd distributed database system gets its name from alert on Linux systems, which is used to store configuration information; the suffix ‘cd’ is used to denote a daemon process. The goals of etcd are to store key-value data in a distributed, consistent, and highly tolerant way.

The API server keeps all state in etcd and runs many instances. The scheduler and controller manager can have only one active instance but uses a lease to determine running instance. This means that Kubernetes can run as Highly Available without single points of failure.

# Putting it all together

How do we use these components in practice? This follows an example of setting up a WordPress website using Kubernetes. If you wanted to do this alone, you would probably use a defined recipe called a helm chart. Helm is available for a number of common applications, but here we will look at the steps to get a WordPress site up and running on Kubernetes.

The first task is to define for MySQL: `kubectl create secret mysql-pass --literal-password= ` will talk to the API Server, which will validate the command and store the password in etcd. Our services are defined in YAML, and we need some persistent storage for the MySQL database.

apiVersion: v1

kind: PersistentVolumeClaim

name: mysql-pv-claim

labels:
  app: wordpress

spec:
  accessModes:
  - ReadWriteOnce

resources:
  storage: 20Gi

The specification should be self-explanatory. The name and labels are used to refer to this storage from other parts of Kubernetes, which is why we define them.

Once we've defined the database, we define a MySQL instance, pointing to the predefined storage. That follows by defining the database itself; we get the name and label for each service within Kubernetes.

Now we need another container to run WordPress.

kind: Deployment

name: wordpress
labels:
  app: wordpress
spec:
  type: Recreate
The strategy ‘Recreate’ means that if any of the code changes, the running instance will be deleted and recreated. Other options allow to creating new instances in running while removing existing ones, which can be useful during deployment of an update. Finally, we create a service for WordPress itself, using PHP and Apache. Part of the YAML is

name: wordpress
labels:
  app: wordpress
spec:
ports:
  - port: 80
selector:
  app: wordpress
tier:
type: LoadBalancer
Note the last line, defining type as LoadBalancer. That instructs Kubernetes to make the service outside of Kubernetes. Without it, the line would be an internal ‘only’ service.
