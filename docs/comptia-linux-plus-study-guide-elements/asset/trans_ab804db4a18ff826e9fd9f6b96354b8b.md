## 重新构建软件包

软件包系统的一个特点是，它允许您安装*二进制软件包*（有时也称为*预编译软件包*）或在您的系统上重新编译*源代码软件包*。前者通常更简单且耗时较少，但后者允许您自定义程序。这种自定义既包括对程序源代码的修改，也包括编译时的更改（例如在不寻常的架构上编译软件包）。复杂的 RPM 和 Debian 系统以及更简单的 tarball 都支持重新编译——事实上，源代码分发的主要方式通常是 tarball。

如果您发现某个软件包仅提供 tarball 形式而没有其他形式，您有两种基本选择：您可以按照 tarball 中的说明编译或安装软件，这将绕过您的 RPM 或 Debian 数据库（如果您的发行版使用它们）；或者，您可以从原始 tarball 创建 RPM 或 Debian 软件包，然后安装生成的二进制软件包。尽管会丢失软件包数据库信息的缺点，但如果您只想在一个系统上安装该软件包，前一种方法通常更简单。如果需要在一台或多台类似的系统上安装该软件包，后一种方法更优，但这需要更多的努力——您必须创建特殊文件以控制最终 RPM 或 Debian 软件包的创建，然后使用特殊命令创建该软件包。

![](img/a78bc63f22351f522ba5ec1fa0c060d2_336_0.png)

接下来的部分“编译源代码”涵盖了从源代码编译程序的基础知识。然而，从源代码 tarball 创建二进制 RPM 和 Debian 软件包超出了本书的范围。有关更多信息，请查阅*软件包系统*的文档。特别是，RPM HOWTO（http://tild.org/HOWTO/RPM-HOWTO/）包含有关 RPM 的此类信息。Eric Foster-Johnson 著的书*Red Hat RPM Guide*（Wiley，2003）对于需要深入了解 RPM 系统的人可能也有用。

源代码存在于 tarball 之外的格式中。如今，许多程序作者会花费时间创建*源代码 RPM*，这是旨在由 RPM 工具处理的源代码软件包。Debian 使用控制文件、补丁文件和原始源代码 tarball 作为源代码 RPM 的等价物。这些文件最常见于专门为基于 Debian 的系统服务的站点。将源代码 RPM 编译为任何特定计算机的二进制 RPM 都很简单；您只需使用 --rebuild 参数和源代码软件包名称调用*rpm*build 程序即可。（有时需要额外的参数，例如在另一个平台上进行交叉编译时）。这种重新编译通常只需几秒到几分钟，但对于慢速计算机上的大型软件包，可能需要*数小时*。结果是 /usr/src/redhat/RPMS/i386 目录或类似位置中的一个或多个二进制 RPM（*redhat* 在非 Red Hat 发行版中可能是其他名称，在 x86 平台之外或为 Pentium 或更新 CPU 优化的发行版中，i386 可能也是其他名称）。

无论您如何操作，与使用现成的二进制软件包相比，*从源代码重新编译程序*都有若干优缺点。主要优点之一是您可以控制各种编译选项，甚至可以*修改*源代码以修复 bug 或根据特定需求自定义程序。然而，与从 RPM 或 Debian 源代码软件包开始相比，从 tarball 开始进行此类修改要容易得多。另一个优点是您可以为不寻常的发行版编译程序。例如，您可能找不到针对 Alpha 或 PowerPC 架构的特定程序的软件包，但如果提供源代码软件包，您可以自行编译。同样，如果您自行编译软件包，则可以解决使用预构建二进制文件时可能遇到的一些库不兼容性问题，特别是当这些二进制文件是在您使用的发行版之外的其他发行版上创建时。

自行编译软件包的主要*缺点*是耗时。如果您需要安装额外的开发库、编译器或其他工具才能使软件包编译通过，这个问题会加剧。（许多程序编译时需要特定的实用工具，但运行时不需要。）有时源代码软件包需要特定版本的其他程序才能编译，但您可能拥有不兼容的版本，导致在您更改当前拥有的版本之前无法编译。新 Linux 用户由于对这些步骤不熟悉，也常在重新编译时遇到困难。

> Gentoo Linux 发行版旨在让用户相对轻松地重新编译整个发行版。不过，这个过程需要*数小时*（有时甚至超过一天）。

## 安装和移除软件包

Linux 中最常见的三种软件包格式是 RPM 软件包、Debian 软件包和 tarball。在这三者中，tarball 最原始，但也得到最广泛的支持。大多数发行版使用 RPM 或 Debian 软件包作为大多数已安装文件的基础。因此，对于大多数发行版，了解如何使用这两种格式中的一种以及 tarball 非常重要。从源代码编译有其自身的挑战。

## 处理 RPM 软件包

Linux 世界中流行的软件包管理器是 RPM。RPM 系统提供了前文“理解软件包概念”部分所述的所有基本工具，例如允许检查冲突和特定文件所有权的软件包数据库。

## RPM 发行版和约定

RPM 由 Red Hat 为其自有发行版开发，但后来被 Fedora、Mandriva、SUSE 和 Yellow Dog 等其他发行版采用。这些发行版在软件包管理之外的许多细节上有所不同。这一事实对软件包安装产生影响，因为为某个发行版准备的软件包可能在另一个发行版上安装顺利，也可能不会。

![](img/a78bc63f22351f522ba5ec1fa0c060d2_338_0.png)

> 注意 Red Hat 已分裂为两个发行版：Fedora 是家庭用户、学生和预算紧张的企业更青睐的免费下载版本。*Red Hat* 名称现专指该发行版的付费版本。

RPM 是一个跨平台工具。一些非 Linux 的 Unix 系统可以使用 RPM，尽管大多数系统并未将其作为主要的软件包分发系统。RPM 支持任何 CPU 架构，基于 RPM 的发行版适用于 x86、x86-64、IA-64、PowerPC 和其他 CPU。总体而言，源代码 RPM 可跨架构传输——您可以使用相同的源代码 RPM 为您喜欢的任何 CPU 构建软件包。一些程序实际上由架构无关的脚本组成，因此无需重新编译。还有一些文档和配置软件包适用于任何 CPU。RPM 软件包文件的命名约定如下：

`packagename-a.b.c-x.arch.rpm`

文件名每个组成部分都有特定含义：

- **packagename** 这是软件包的名称，例如 Samba 文件和打印服务器的 *samba*。
- **a.b.c** 这是软件包版本号，例如 3.2.4。版本号不必是三个由点分隔的数字，但这是最常见的形式。版本号由程序作者指定。
- **x** 版本号后面的数字是*构建号*（也称为*发布号*）。该数字代表软件包维护者而非程序作者所做的微小更改。这些更改可能包括启动脚本或配置文件的变更、文件位置的改变、添加的文档，或附加到原始程序以修复 bug 或使程序与目标 Linux 发行版更兼容的补丁。一些发行版维护者在构建号后添加字母代码，以将其软件包与其他人的软件包区分开来。请注意，这些数字在软件包维护者之间*不可*比较——George 的某个软件包的构建号 5 *并不*一定比 Susan 的同一软件包的构建号 4 更好。
- **arch** 在 .rpm 扩展名之前的最后一个组成部分是软件包架构的代码。i386 架构代码代表为 80386 及以后任何 x86 CPU 编译的文件。一些软件包包含针对 Pentium 及以上处理器（i586 或 i686）的优化，x86-64 软件包使用 x86_64 代码，其他 CPU 的二进制软件包使用其 CPU 的代码，
