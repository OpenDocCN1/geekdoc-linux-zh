Before you begin, you should familiarize yourself with the kernel upgrade process as much as possible. 2. How do you tell the difference between a production kernel and a development kernel?

Kernels that use an even minor number, such as 2.2.x, are production or stable kernels with the bugs removed. Those kernels numbered with an odd minor number, such as 2.3.x, are development kernels. Development kernels are for testing purposes and might contain lots of bugs. You can think of a development kernel as beta software.

3. What should you do to prepare yourself before you install a new kernel?

You will need to make sure that the required libraries and utilities installed on your system are updated to a certain minimum version number. If your system is not up-to-date with the needed libraries and utilities, the kernel will not install properly.

### Dealing with Program Crashes

It's not an everyday occurrence in Linux, but every now and then, a program crashes. You know the routine... everything is working fine, then all of a sudden, the program hoses and either locks up on you or disappears into thin air. When this happens, the system creates a core dump file that contains all kinds of information. As you can tell from the core dump in Figure 17.1, much of this information looks like gibberish. But, to the trained eye, it contains important debugging information.

**New Term** A core dump is a file that is written to your home directory whenever there is a failure (also known as a crash) somewhere in the system. A core dump contains the process information that is stored in memory at the time of the failure.

Looking at Figure 17.1, you'll notice that the core dump file can be quite large. In this example, the core dump file is 8,738 lines long (and almost 2MB in size). That's a lot of used space on your hard drive and a ton of reading material. If a core dump appears in your home directory, you can read the contents in the less pager. To do this from the command line, change to the directory in which the core dump file is stored and type less core.

One way to find the cause of a core dump is to use a debugging program such as gdb (as shown in Listing 17.1). ### Looking at System Log Files

Linux keeps track of all kinds of system information in log files. These files are stored in different places and are maintained by the syslogd daemon. The syslogd daemon is started when the system boots and knows what type of information to store based on the contents of the /etc/syslog.conf file (shown in Figure 17.2). After the syslogd daemon knows where it should log system information, it goes merrily about its business once a minute, collecting messages from everywhere and entering them in log files.

FIGURE 17.2
Type less /etc/syslog.conf and press Enter to see where system log files are stored.

![](img/782ecfdc0b083a767896cc983e10427f_275_0.png)

You can also look in the /var/log directory to find the logs maintained by the syslogd daemon. Here are a few of the system logs that you'll find:

- The /var/log/messages file is the main system log and contains the information gathered by the kernel when the system was last booted.
- The /var/log/wtmp file contains the login time and duration for each user.
- The /var/log/utmp file is where information about currently logged-in users is kept.
- The /var/log/lastlog file is where user login times are stored.

As you can see, with all these system log files and new information added every minute, log files can get out of hand quickly. To keep from being buried under the information overload, you'll need to monitor the status of system log files and periodically clean them out. Because the logs are a valuable source of information about your system, and some are used by commands that the system runs, you shouldn't just delete them.
