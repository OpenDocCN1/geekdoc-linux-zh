If your organization is geographically distributed, make sure that other offices help with testing. International participation is particularly valuable in multinational environments. If no one in the U.S. office speaks Japanese, for example, you had better get the Tokyo office to test anything that might affect Kanji support. A surprising number of system parameters vary with location. Does the U.S. office test changes to the printing infrastructure with A4 paper, or will the non-U.S. offices be in for a surprise?

# Compiling locally

In the old days of UNIX, when there were many different architectures, programs were generally distributed in the form of source archives, **tar.gz** files that you would uncompress and then compile. Once the program was built, you would install the software in a location as **/usr/local**. Today, the use of package management systems means fewer programs need to be installed this way. It also means administrators make fewer decisions since packages specify where their contents are installed.

Even with package management, some people still prefer to compile their own software.¹¹² Running your own build gives you more control over the software-compiled options. It also lets you more paranoid because you can inspect the source code you are compiling. Some people seem to think that once-over is important, unless you've got the time and skill to inspect every line of a 20,000-line software package, the added security value is minimal.

Since not piece of software in the world has been packaged for every distribution and UNIX flavor, it's likely that you will run at least a few programs you need to compile and install yourself, especially if your computers are not 32-bit Intel systems. What's more, if you are a development site, you will have to consider where to put your owns locally developed software.

Historically, the most common location for local software is **/usr/local**, and this convention is still widely followed today. The UNIX/Linux Filesystem Hierarchy Standard (FHS) specifies that **/usr/local** be present and empty after the initial OS, and many packages to install them there.

**/usr/local** is traditional, many sites find it to be an unmanageable dumping ground. The traditional way it was laid out (basically the same as **/usr**, with binaries in **/usr/local/bin**, man pages in **/usr/local/man**, and so) creates a rate of problems in some environments: it's hard to have multiple versions of the same software installed, the directories can be large, it's a pain to manage multiple architectures.
