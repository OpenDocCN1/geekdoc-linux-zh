
# NSD configuration example

There can be only one server statement. Zone states list zone-specific options, and key statements define cryptographic keys, which are required for communication between master and slave servers and for controlling n. Whitespace separates attributes from values. Values can be quoted, but they don't have to be.

Like BIND, nsd generalizes IP addresses, but in a slightly different manner than BIND's address map list construct. It is called an ip-spec and can:

- A plain IP address (IPv4 or IPv6)
- A subnet in CIDR notation, e.g., 1.2.3.0/24
- A subnet with an explicit mask, e.g., 1.2.3.4&255.255.255.0
- A range of IP addresses such as 1.2.3.4-1.2.3.235

Spaces are not allowed in any of these forms.

Another fundamental difference is the use of key values for authentication of zone transfers and notification messages. In BIND, a key is associated with an IP address, and to communication from that address is signed and validated with that key. In NSD, the key is finer grained, so nsd could have one key for notifications, a different key for sending a zone transfer, and a third key for receiving that transfer. Useful? Well...

The semantics of notify in NSD are analogous to BIND's notify explicit clause: only servers explicitly listed are notified. (By default, BIND notifies all name servers in the zone file for the domain in.)

The NSD documentation refers to master and slave servers, whereas the BIND documentation uses adjectives to refer to servers. These are basically the same thing. An “instance” of a name server is the master server or slave server for a specific zone.

nsd favors sensible default behavior for configurability. For example, DNSSEC is turned off by default for signed zones and for unsigned zones. By default, nsd listens on both IPv4 and IPv6 sockets. Logging is on or off rather than having the infinite shades and gradations of the BIND paradigm. nsd uses TSIG for communication among servers (zone transfers, notifications, etc.).

The file doc/NSD-FOR-BIND-USERS gives a quick description of the differences between BIND and NSD and includes a sample config file. The main page for the configuration file, nsd.conf, and the doc/README file also have examples, but sadly there is no consistency between them.

# Chapter 17 DNS: The Domain Name System

configured nsd to be the master server for the domain at atrust.com and a slave server for the domain admin.com.

```
server:
  username: nsd # User nsd should run after chroot
  database: /var/db/nsd/nsd.db # Precompiled database file
  logfile: /var/log/nsd.log # Log file, default is to stderr + syslog
  pidfile: /var/run/nsd.pid # nsd process id
  key:
    name: atrust.com # Key for atrust.com transfers
    algorithm: hmac-md5
    secret: "base64 secret goes here"
zone:
  name: atrust.com
  zonefile: /var/nsd/primary/atrust.com
  provide-xfr: 1.2.3.40 tsig.atrust.com # Address of atrust.com slave
  notify: 1.2.3.40 tsig.atrust.com # Key for notify or xfrs.
  provide-xfr: 1.2.3.40 tsig.atrust.com # Address of another slave
  notify: 1.2.30.40 tsig.atrust.com # Key for notify or xfrs.
key:
  name: admin.com # Key to get admin.com slave data
  algorithm: hmac-md5
  secret: "base64 secret goes here"
zone:
  name: admin.com # Zone we are a slave for
  zonefile: /var/nsd/secondary/admin.com.signed"
  allow-notify: 5.6.7.8 NUKES # Its master server
  request-xfr: 5.6.7.8 tsig.admin.com. # Key for xfrs
```

This **nsd.conf** file configures the server to be the master for atrust and to notify provide zones to two slaves, one at IP address 1.2.3.4 and the other at IP address 1.2.30.40. The server will use the TSIG key called tsig.atrust.com to authenticate both servers for transfers and notifications. (You should, and probably, use a separate key for each slave.)

This server is also a slave for the signed admin.com, whose master server is at IP address 5.6.7.8. We can receive notifications of zone changes with a key, but you must use the tsig key to receive zone transfers. Master zones provide-xfr clauses and slave zones have a request-xfr clause.

After you've installed **nsd** and set up your configuration file, use **nsd-check** to check the config file's syntax. Its error reports are a bit terse; for example, "error: syntax" and a line number. After fixing **nsd-check**, it runs again and repeat until nsd-check reports no errors.

# NSD key definitions

A **key** defines a named key to be used in access control operations. Each key has three attributes: name, algorithm, and a shared secret (password). Consider putting key definitions, or at least their secrets, into files that have restricted permissions. You can use the **include** statement to import **nsd.conf**—just put `include: filename` wherever you want the text inserted. Here is the syntax of the key statement:

- name: key
- algorithm: alg
- secret: password

There can be multiple key statements. The **name** field identifies the key and reflect the servers involved. The algorithm can be `hmac-md5`, `hmac-sha1`, or `hmac-sha256`. You can use the **ns-keygen** command to generate TSIG keys, even though it really designed for generating DNS public/private keys. Here's an example using hmac-sha1:

```
$ ndns-keygen -a hmac-sha1 example.com
```

This command produces a file called *example.com.key* that contains the TSIG key. Just cut and paste the secret part into your key specification. The `hmac-sha1` stands for the algorithm. `hmac-md5` is, and `hmac-sha256` is a placeholder for random key. If you have multiple keys, this helps you keep them straight.

# NSD global options

We divide NSD options into two groups: global options for the server, and zone-specific options that can be applied to any zones served by nsd. Server options generally have sensible defaults and require attention only if your directory structure is nonstandard or if you want to do something fancy. Below, we show default values in square brackets. As BIND options, we have added margin notes describing each group of options to make navigation easier.

The **include** directive can appear anywhere in the configuration file. The specified **filename** is read in the config file, and it contains the directives.

| | | |
|---|---|---|
| ip-address | ip addresses | [all IP addresses] |
| ip4-only | no | [no] |
| ip6-only | yes | [no] |
| port | portnum | [53] |

By default, NSD binds to port 53 on all network interfaces, both IPv4 and IPv6. If you list the addresses with an **ip-address** clause, **nsd bypass** the kernel's routing tables and ensures that a query to one IP address does not receive its answer from a different IP address; many resolvers require this. If your machine has only one interface, this option is not useful. The **ip4-only** and **ip6-only** options limit nsd to a particular protocol, and port sets the network port on which to listen for incoming queries.

You should not normally need any of these options, the defaults are fine.

- identity: string [hostname]
hide-version: yes | no [no]

This pair of options controls whether nsd tells the truth about its version and hostname when queried for the CHAOS class names id.server and version.server. As explained on page 58, we recommend not tampering with these values.

- logfile: filename [stderr and syslog]
verbosity: level [0]
debug-mode: yes | no [no]
statistics: #secs [0] # statistics

Logging is, by default, to standard error and to syslog (facility daemon), with the amount of logging determined by the verbosity option. The range of possible values is 0–5; higher numbers mean more data should be logged. The logfile parameter directs log messages to a file instead of sending them to syslog.

If you specify debug-mode, nsd does not fork extra copies of itself and stays to your terminal that you can see messages to standard error.

If you keep statistics, #secs to the number of seconds between dumps. Statistics are like other log messages, they go to the log file or to syslog if no log file has been specified. It is best to watch the output for a bit to make sure you have chosen a sensible interval and are not filling your disks with information.

- database: filename [/var/db/nsd/nsd.db]
diffile: filename [/var/db/nsd/xfrd.db]
xfrfile: filename [/var/db/nsd/xfrd.state]
pid-file: filename [Os-specific, usually /var/run/nsd.pid]
zondirect: directory [/etc]

Compiled zone files and zone transfer default logging to /var/db/nsd; it’s unlikely that you will need to change this. The PID file should show where operating system puts other PID files, usually in /var/run. By default, human-editable zone files go in /etc/nsd, which feels like a bad choice. Considering moving them /var, perhaps to /var/nsd/zones.
