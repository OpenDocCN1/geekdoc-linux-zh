
## 20.12 SENDMAIL PERFORMANCE

sendmail has several configuration options that improve performance. Although we have scattered them throughout the chapter, we expand on the most important ones in this section. These are options and features you should consider if you run a high-volume mail system (in either direction). Actually, if you really need to send 1,000,000 mail messages an hour and you aren't a spammer, your best bet might be to use the commercial side of sendmail, Sendmail, Inc.

## Delivery modes

sendmail has four basic delivery modes: background, interactive, queue, and defer. Each represents a tradeoff between latency and throughput. Background mode delivers the mail immediately but requires sendmail to fork a new process to do it. Interactive mode also delivers immediately, but delivery is by the same process and makes the remote side wait for the results. Queue mode queues mail for delivery by a queue runner at some later time. Defer mode is similar to queue mode, but it also defers all map, DNS, aliases, and forwarding-ups. Interactive mode is rarely used. Background mode favors lower latency, and defer or queuing favor higher throughput. The delivery mode is set with the option confDELIVERY_MODE and defaults to background.

## Queue groups and envelope splitting

Queue groups let you create multiple queues for outgoing mail and control the attributes of each queue group individually. Queue groups are used with an envelope-splitting feature that distributes an envelope with many recipients (such as a message sent to a mailing list) across multiple queue groups. Several configuration-parameters are used with queue groups. See the O'Reilly sendmail book or the cf/README file for examples and details.

## Queue runners

sendmail forks copies of itself to perform the actual transport of mail. You can control how many copies are running at any time and how many copies are attached to each queue group. By using this feature, you can balance the activities of sendmail and the operating system on your busy mail hubboxes.

Three sendmail options control the number of queue runner daemons processing each queue:

- MAX_DAEMON_CHILDREN option sets the total number of copies of the sendmail daemon that are allowed to run at any one time, including those running queues and those accepting incoming mail.
- MAX_QUEUE_CHILDREN option sets the maximum number of queue runners allowed at one time.

## Load average controls

sendmail has always been able to refuse connections or queue messages instead of delivering them when the system load average goes too high. Unfortunately, the load average has only a one-minute granularity, it's not very finely tuned for smoothing out the resources consumed by sendmail. The DELAY_LA priority you set a value of the load average at which sendmail would slow down; it will sleep for one second between SMTP commands for current connections and before accepting new connections. The default value is 0, which turns the mechanism off.

## Undeliverable messages in the queue

Undeliverable messages in the mail queue can kill performance on a busy mail server. sendmail has several features to help with the issue of undeliverable messages. The most effective is the FALLBACK_MX option, which handles a message offset to another machine if it cannot be delivered on the first attempt. Your primary machine cranks out the messages to good addresses and shunts the problem children to a secondary fallback machine. Another aid is the host directory of remote hosts across queue runs.

The FALLBACK_MX option is a performance win for a site with large mailing lists that invariably contain addresses that are temporarily or undesirable. To use it, you specify the host to handle the deferred mail. For example, it forwards messages that fail their first delivery attempt to backup for further processing. There can be multiple fallback machines if the designated hosts have multiple MX records in DNS.

The TO_CONNECT option sets a timeout on the initial attempt to connect and send a message. If it's short, more work is shunted to the fallback MTA. However, it does let the main server whip through the first pass for a large mailing list in record.

On the fallback machines, you can use the HOST_STATUS_DIRECTORY option to help with multiple failures. This option directs sendmail to maintain a status for each host to which mail is sent and to use that information to prioritize the hosts each time the queue is run. This status information effectively implements negative caching and allows information to be shared across queue runs. It's a performance win on servers that handle mailing lists with a lot of addresses, but it can be expensive in terms of I/O.

A third performance enhancement for busy machines involves setting a minimum queue age so that no message can be delivered on the first it stays in the queue. This technique is usually coupled with command-line flags that run the queue more often (e.g., -q5m), resulting in a more responsive system.

```
define(MINQUEUE_AGE, "2m")
```

## Kernel tuning

If you plan to use a UNIX or Linux box as a high-volume mail server, you should modify several of the kernel's networking configuration. Table 20.16 shows the parameters to change under Linux on a high-volume mail server along with suggested and default values. Similar parameters exist for UNIX with slightly different names.

Table 20.16 Kernel parameters to change on high-volume servers

| Variable (relative to /proc/sys) | Default | Suggested |
| :--- | :--- | :--- |
| net/ipv4/tcp_timeout | 180 | 30 |
| net/ipv4/keepalive_time | 7200 | 1800 |
| net/core/netdev_max_backlog | 300 | 1024 |
| fs/file_max | 4096 | 16384 |
| fs/inode_max | 16384 | 65536 |

These changes can be made permanent with the sysctl command or by putting the appropriate echo commands in a shell script that runs at boot time. For example, to change TCP's FIN timeout, you could use the following command:

```
linux$ sudo sh -c "echo 30 /proc/sys/net/ipv4/tcp_fin_timeout"
```

Solaris and HP-UX use the ndd command to tune network parameters. The HP-UX implementation is well documented, and ndd-h (help) gives a clear description of each variable, its range of values, and the default value. Solaris's ndd understands a question mark to mean you want documentation, but you must backslash it (ndd?) to protect it from the shell. Unfortunately, Solaris's ndd names the tunable variables instead of describing them.

For example, to change the FIN timeout value with ndd on HP-UX:

```
hp-ux$ sudo ndd -set tcp_fin_wait_2 30000
```

The time unit for ndd is milliseconds, thus 30000 instead of 30. In Solaris, the variable is called tcp_fin_wait_2_flush_interval, with no units in the man page—but Google! In fact, the units are milliseconds, with the default value 675,000. ndd is described in more detail in Chapter 14, TCP/IP Networking on page 498 for Solaris and page 504 for HP-UX.

AIX uses no command to tune network parameters. sudo no -L lists tunable variables with their min, max, and current values with all these values. If you want a to be permanent, use no with the -p flag—your changes will survive a reboot.

For example, to set the TCP FIN_WAIT parameter, use:

```
aix$ sudo no -p -o tcp_finwait=2
```

The units are half-seconds, so the value 60 achieves the 30 seconds recommended in the tuning table above.
