# Git

Git shtschick is that it has no central repository. Instead of checking out a particular version of a project's files, you simply copy the repository (including its entire history) and carry it with you like a hermit crab shell. Your commits to the repository are local operations, so they're fast and you don't have to worry about communicating with a central server.

Git uses an intelligent compression system to reduce the cost of storing the entire history, and in most cases this system is quite effective. In many cases, working requirements for storage space are even lower than with Subversion.

Git is great for developers because you can pile their code onto a laptop and work without being connected to a network while still making all of the benefits of version control. When the time comes to integrate multiple developers' work, their changes can be integrated from one copy of the repository to another in any fashion that suits the organization's workflow. It is always possible to unwind copies of a repository back to their common ancestor state, no matter how many changes and iterations have occurred after the split.

Git's promiscuous copying-branching strategy isn't relevant to the context of system administration, but its use of a local repository is a big leap forward for system administrators—or perhaps more accurately, is a big leap backward, in a good way. Early version control systems (e.g., RCS and CVS) used local repositories but were unable to handle collaboration, merging, and independent development. Now we've come full circle to a point where putting under control is a fast, simple, local operation. At the same time, all of Git's advanced collaboration features are available for use in situations that require them.

Before you start Git, set your name and email address:

```
$ git config --global user.name "John Q. Ulsah"
$ git config --global user.email "ulsah@book.admin.com"
```
