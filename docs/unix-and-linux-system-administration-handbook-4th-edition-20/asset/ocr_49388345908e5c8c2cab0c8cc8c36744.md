Let's dissect that record in a bit more detail:

+   - v=spf1 indicates the record conforms to version 1 of the SPF protocol, described in RFC4408, v=spf2.0 would indicate Microsoft's Sender ID system, described in RFC4408.
- The ip4 tags indicate the following data value is a normal IP network or host address. Multiple clauses can be included, as is done here.
- ?all indicate "done" to the checking function that interprets the record.

The complexity of the full SPF language is disheartening. Other tags are available to list hostname, MX records, PTR records, IPv6 addresses, and so. Some of these forms require a second DNS lookup, although they may add convenience or flexibility, they are less efficient than the ip4 tag. The examples at the end of RFC4408 are a good reference if you want to tag with your SPF records.

Here is another example, obtained with dig sendmail.com txt:

```
sendmail.com. IN TXT v=spf1 ip4.209.246.26.40 ip4.209.246.26.41 ip6.231.143.38 ip4.209.246.26.36 ip4.209.246.26.39 ip4.209.246.26.24 ip209.246.26.25 ip4209.246.26.10 ip4.209.246.26.53 ip4.72.32.154/227 ptr:constantcontact.com -all
```

This record completes server IP addresses rather than entire networks. The tail end of the IP address is a ptr: clause that permits constantcontact.com to send mail purporting to be from sendmail.com. This clause should only take effect if constantcontact.com has a matching PTR record, which isn't currently the case—as we are using, the PTR maps back to wellcontact.com, not constantcontact.com. Either email are not checking the PTR record or the SPF record has a small bug.

Surveys (dkim/survey) of 1,000 U.S. banks and Fortune 1000 companies showed that SPF was supported by more than 90% of sites, with the Sender ID format used by only 1%-2%. Some readers (e.g., Gmail) print a red warning banner across a message that failed an SPF check or be phishing.

sendmail, Postfix, and exist support SPF processing; Microsoft Exchange supports Sender ID. See page 768 for more SPF information.

# DKIM and ADSP records

DKIM stands for DomainKeys Identified and is a merge and enhancement of two systems: DomainKeys from Yahoo! and Identified Mail from Cisco. The receiver of the email can authenticate the sender (no forgeries) and guarantee the message's integrity (no meddling).

A lot of work has gone into the DKIM specifications so that edge cases like mailing lists and outsourced email work well. Another focus of the DKIM design is to make implementation easy; it requires no per-user or per-host
