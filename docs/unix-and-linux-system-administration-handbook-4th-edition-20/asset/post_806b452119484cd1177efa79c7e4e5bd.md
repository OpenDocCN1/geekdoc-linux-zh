
# Chapter 20 Electronic Mail

You can enable greeting pauses with this entry in the .mc file:
FEATURE(greet_pause, '700')

This line causes a 700 millisecond delay at the beginning of every new connection. You can set per-host or per-net delays with a GreetPause: prefix in the access database, but most sites use a blank value for this feature.

# Milter configuration in sendmail

Miltering in general is introduced on page 767; this section describes how to configure miltering in sendmail. The configuration directive INPUT_MAIL_FILTER and MAIL_FILTER controls the miltering action. A slew of options gives you fine control over exactly when in the SMTP conversation each filter is applied (MILTER_MACROS, _). For example, the line

```
INPUT_MAIL_FILTER('filename', '/etc/mail/var/run/filter.socket')
```

passes each incoming message through the /etc/mail/filter program through the socket specified in the second argument. Below is a more realistic example that uses milters to connect to SpamAssassin through a local domain socket and to check DKIM signatures with the dkim-filter program through a TCP socket at 8699.

```
dnl 1 Enable SpamAssassin
INPUT_MAIL_FILTER('spamassassin')
S:local=/var/run/spam-milter.sock, F=T;C=15m;S:4;R:4;E:10m;

dnl 2 Enable DomainKeys and DKIM
INPUT_MAIL_FILTER('dkim-filter', 'S=inet:8699@127.0.0.1, T=R:2m')
```

```
define(CONFTER_MACROS_CONNECT, 'j', [daemon_name])
def(CONFTER_MACROS_ENVFROM, 'i', [auth_type])
```

The last two statements set parameters to the milters when the session connection starts and after the MAIL command, respectively.

For information, check libmailer/README or the HTML documentation in the libmailer/docs directory of the sendmail distribution. The README file gives an overview and a sample example of a filter that logs messages to a file. The files in docs describe the library interface and how to use the virtual calls to build your own mail filtering programs. milter.org is a great reference.

# amavisid and sendmail connection

amavisid is an external, industrial strength virus and spam scanner introduced on page 769. This section illustrates how to use it with sendmail.

The easiest way to connect sendmail and amavisid is to use two servers: one that receives mail from the Internet and passes it to amavisid; the other runs in queue-only mode, receives scanned messages from amavisid, and transmits them on their way, for local delivery or to the Internet. amavisid sits in the middle, acting as a MAIL_HUB for incoming mail and a SMART_HOST for outgoing mail.

Unfortunately, this scheme scans messages off-line after sendmail has already accepted them for delivery. To use amavisid-in-line, see the file README.mil in the amavisid-new documentation.

The key configuration lines on the Internet-facing server—the ones that pass all mail to the amavisid process listening on port 10024—are

```
FEATURE(stickyhost)
define('MAIL_HUB', 'esmt=[127.0.0.1]')
define('SMART_HOST', 'esmt=[127.0.0.1]')
define(DELIVERY_MODE, 'q')
define(ESMTP_MAILER_ARGS, 'TCP #10024')
DAEMON_OPTIONS(Name=receivingMTA)
```

This last line makes debugging the configuration much easier because you can then tell which process (the receiving sendmail, or transmitting amavisid) is logging what messages.

After scanning, amavisid passes messages to the queuing-one sendmail listening on port 10025 (not port 25 as usual), and from there, queue runners either complete local delivery or ship the messages to the Internet.

On the transmitting server, setting

```
DAEMON_OPTIONS(Addr=127.0.0.1, Port=10025, Name=transmittingMTA)
```

sendmail to listen on port 10025 for messages returning from amavisid. It logs any info or error messages with the name transmittingMTA to distinguish it from the receivingMTA.

There are more settings you can tweak (for example, performance limits) to make sure the two instances of sendmail play well together. Some thought needs to go into deciding exactly what checks will, which process will do them, and in what order they will occur.

The file README_FILES/README.sendmail-dual in the amavisid-new distribution is a good reference.

# 20.11 SECURITY AND SENDMAIL

With the explosive growth of the Internet, programs such as sendmail accept arbitrary user-supplied input and deliver it to local users, files, or shells frequently provide an avenue of attack. sendmail, along with DNS and even IP, is flirting with authentication and encryption as a built-in solution to some of these fundamental security issues.

sendmail supports both SMTP authentication and encryption with TLS, Trans-port Layer Security (formerly known as SSL, the Secure Socket Layer). TLS brought with it six new configuration options for certificate files and key files. New actions for access database matches can require that authentication must have succeeded.

In this section, we discuss TLS and SASL (Simple Authentication and Security Layer). TLS is used for both authentication and encryption, while SASL is used only for authentication. sendmail supports both through external modules.

# Milter configuration in sendmail

Miltering in general is introduced on page 767; this section describes how to configure miltering in sendmail. The configuration directive INPUT_MAIL_FILTER and MAIL_FILTER controls the miltering action. A slew of options gives you fine control over exactly when in the SMTP conversation each filter is applied (MILTER_MACROS, _). For example, the line

```
INPUT_MAIL_FILTER('filename', '/etc/mail/var/run/filter.socket')
```

passes each incoming message through the /etc/mail/filter program through the socket specified in the second argument. Below is a more realistic example that uses milters to connect to SpamAssassin through a local domain socket and to check DKIM signatures with the dkim-filter program through a TCP socket at 8699.

```
dnl 1 Enable SpamAssassin
INPUT_MAIL_FILTER('spamassassin')
S:local=/var/run/spam-milter.sock, F=T;C=15m;S:4;R:4;E:10m;

dnl 2 Enable DomainKeys and DKIM
INPUT_MAIL_FILTER('dkim-filter', 'S=inet:8699@127.0.0.1, T=R:2m')
```

# amavisid and sendmail connection

amavisid is an external, industrial strength virus and spam scanner introduced on page 769. This section illustrates how to use it with sendmail.

The easiest way to connect sendmail and amavisid is to use two servers: one that receives mail from the Internet and passes it to amavisid; the other runs in queue-only mode, receives scanned messages from amavisid, and transmits them on their way, for local delivery or to the Internet. amavisid sits in the middle, acting as a MAIL_HUB for incoming mail and a SMART_HOST for outgoing mail.

# Security and sendmail

Unfortunately, this scheme scans messages off-line, after sendmail has already accepted them for delivery. To use amavisid-in-line, see the file README.mil in the amavisid-new documentation.

The key configuration lines on the Internet-facing server—the ones that pass all mail to the amavisid process listening on port 10024—are

```
FEATURE(stickyhost)
define('MAIL_HUB', 'esmt=[127.0.0.1]')
define('SMART_HOST', 'esmt=[127.0.0.1]')
define(DELIVERY_MODE, 'q')
define(ESMTP_MAILER_ARGS, 'TCP #10024')
DAEMON_OPTIONS(Name=receivingMTA)
```

This last line makes debugging the configuration much easier because you can then tell which process (the receiving sendmail, or transmitting amavisid) is logging what messages.

After scanning, amavisid passes messages to the queuing-one sendmail listening on port 10025 (not port 25 as usual), and from there, queue runners either complete local delivery or ship the messages to the Internet.
