## iptables firewall setup

Before you can use iptables as a firewall, you must enable IP forwarding and make sure that various iptables modules have been loaded into the kernel. For more information on enabling IP forwarding, see Tuning Linux kernel parameters on page 421 or Security-related kernel variables on page 492. Packages that install iptables generally include start scripts to achieve this enabling and loading.

A Linux firewall is usually implemented as a series of iptables commands in an rc startup script. Individual iptables commands usually take one of the following:

```
iptables -F chain-name
iptables -P chain-name target
iptables -A chain-name -i interface -j target
```

The first form (-F) flushes all prior rules from the chain. The second form (-P) sets a default policy (aka target) for the chain. We recommend that you use DROP for the default chain target. The third form (-A) appends the current specification to the chain. Unless you specify a table with the -t argument, your commands apply to chains in the filter table. The -i parameter applies the rule to the named interface, and -j identifies it. iptables accepts many other classes, of which are shown in Table 22.3.

## Command-line flags for iptables filters

| Clause | Meaning or possible values |
| :--- | :--- |
| -p proto | Matches by protocol: tcp, udp, or icmp |
| -s source-ip | Matches host or network source IP address (CIDR notation is OK) |
| -dest-ip | Matches host or network destination address |
| --sport port | Matches by source port (note the double dashes) |
| --dport port | Matches by destination port (note the double dashes) |
| --icmp-type type | Matches by ICMP type code (note the double dashes) |
| ! | Negates a clause |
| -t table | Specifies the table to which a command applies (default is) |

## A complete example

Below we break a complete example. We assume that the eth1 interface goes to the Internet and the eth0 interface goes to an internal network. The eth1 IP address is 128.138.101.4, the eth0 IP address is 10.1.1.1, and both interfaces have a mask of 255.255.255.0. We use stateless packet filtering to protect the web server with IP address 10.1.1.2, which is the standard method of protecting Internet servers. Later in the example, we show how to use stateful filtering to protect desktop users.

Our first set of rules initializes the filter table. First, all chains in the table are flushed, then the INPUT and FORWARD chains' default target is set to DROP. As with any other firewall, the most secure strategy is to drop any packets you have not explicitly allowed.

```
iptables -F
iptables -P INPUT DROP
iptables -P FORWARD DROP
```

Since rules are evaluated in order, we put our busiest rules at the front. The first rule allows all connections through the firewall that originates from the trusted net. The next three rules in the FORWARD chain allow connections through the firewall to network services on 10.1.1.2. We allow SSH (port 22), HTTP (port 80), and HTTPS (port 443) to out to our server.

```
iptables -A FORWARD -d eth0 -p ANY -j ACCEPT
iptables -A FORWARD -d 10.1.1.2 -p tcp --dport 22 -j ACCEPT
iptables -A FORWARD -d 10.1.1.2 -p tcp --dport 80 -j ACCEPT
iptables -A FORWARD -d 10.1.1.2 -p tcp --dport 443 -j ACCEPT
```

The only TCP traffic allowed to our firewall host (10.1.1.1) is SSH, which is useful for managing the firewall itself. The second rule allows loopback traffic, which stays local to the host. Administrators get nervous when they can't ping their default route, so the third rule allows ICMP ECHO_REQUEST from internal IP addresses.

```
iptables - INPUT -i eth0 -d 10.1.1.1 -p tcp --dport 22 -j ACCEPT
iptables - INPUT -i lo -d 127.0.0.1 -p ANY -j ACCEPT
iptables - INPUT -i eth0 -d 10.1.1.1 -p icmp --icmp-type 8 -j ACCEPT
```

For any host to work properly on the Internet, certain types of ICMP packets must be allowed through the firewall. These eight rules allow minimal set of ICMP packets to the firewall host, as well as the network behind it.

```
iptables - INPUT -p icmp --icmp-type 8 -j ACCEPT
iptables - INPUT -p icmp --icmp-type 3 -j ACCEPT
iptables - INPUT -p icmp --icmp-type 5 -j ACCEPT
iptables - INPUT -p icmp --icmp-type 6 -j ACCEPT
iptables - FORWARD -d 10.1.1.2 -p icmp --icmp-type 0 -j ACCEPT
iptables - FORWARD -d 10.1.1.2 -p icmp --icmp-type 3 -j ACCEPT
iptables - FORWARD -d 10.1.1.2 -p icmp --icmp-type 5 -j ACCEPT
iptables - FORWARD -d 10.1.1.2 -p icmp --icmp-type 8 -j ACCEPT
```

We add rules to the PREROUTING chain in the nat table. Although the nat table is not intended for packet filtering, PREROUTING is particularly useful for anti-spoofing. If we drop entries in the PREROUTING chain, they need not be present in the INPUT and FORWARD chains, since the PREROUTING chain is applied to all packets that enter the firewall. It's cleaner to put the entries in a single place rather than duplicate them. However, you must be careful that reordering the rules for performance doesn't modify functionality.

```
iptables -t nat -A PREROUTING -i eth1 -s 10.0.0.0/8 -j DROP
iptables -t nat -A PREROUTING -i eth1 -s 172.16.0.0/12 -j DROP
iptables -t nat -A PREROUTING -i eth1 -s 192.168.0.0/16 -j DROP
iptables -t nat -A PREROUTING -i eth1 -s 127.0.0.0/8 -j DROP
iptables -t nat -A PREROUTING -i eth1 -s 224.0.0.0/4 -j DROP
```

Finally, we end both INPUT and FORWARD chains with a rule that forbids packets not explicitly permitted. Although we already enforced this behavior with iptables -P commands, the LOG target tells us who is knocking on our door.

One of the most powerful features that Netfilter brings to Linux. Instead of allowing incoming services, a firewall for clients connecting to the Internet needs to allow incoming responses to the client's requests. The stateful FORWARD chain below allows all traffic to leave our network but only incoming traffic that initiated by our hosts.

```
iptables -A INPUT -i eth0 -j ACCEPT
iptables -A FORWARD -m state ESTABLISHED,RELATED -j ACCEPT
```

Certain kernel modules must be loaded to enable iptables to track complex sessions such as FTP. If these modules are not loaded, iptables simply disallows those connections. Although stateful packet filters can increase the security of your site, they also add to the complexity of the network. Be sure you use stateful functionality before implementing it in your firewall.

Perhaps the best way to debug your iptables rules is to use iptables -v. These options tell you how many times each rule in your chains has matched a packet. We often add temporary iptables rules with the LOG target when we want information about the packets that matched. You can also solve tricky problems by using a packet sniffer as tcpdump.

## 22.13 IPFilter for UNIX systems

Most UNIX vendors don't have their own firewall software. But it's easy enough to add IPFilter, an open source package developed by Darren Reed, supplies NAT and stateful firewall services for UNIX systems. Solaris includes it by default, and it's also available as an add-on for HP-UX, AIX, and many other systems, including Linux. You can use IPFilter as a loadable kernel module (which is recommended by the developers) or include it statically in the kernel.

IBM is an exception. AIX includes a separate packet-filtering suite in its IP Security implementation, although the suite does not stateful filtering. See the pages for filter to get started.

IPFilter is mature and feature-complete. The package has an active user community and a history of continuous development. It is capable of stateful tracking such as UDP and ICMP.

IPFilter reads rules from a configuration file (usually /etc/ipf.conf or /etc/ipf/ipf.conf) rather than making you run a series of commands as does iptables. An example of a simple rule that could appear in ipf.conf is

```
block in all
```

This rule blocks all inbound traffic (that is, network activity) on all network interfaces. Certainly secure, but not particularly useful!

## Table 22.4 Commonly used ipf conditions

| Condition | Meaning or possible values |
| :--- | :--- |
| on interface | Applies the rule to the specified interface |
| proto protocol | Selects packet according to protocol: tcp, udp, or icmp |
| source-ip | Filters by source: host, network, or any |
| dest-ip | Filters by destination: host, network, or any |
| port = port# | Filters by port name (/etc/services) or number |
| flags-spec | Filters by TCP header flags |
| icmp-type number | Filters by ICMP type and code |
| keep state | Retains details about the flow of a session; see comments |

a. You can use any comparison operator: =, <, <=, >=, etc.

IPFilter evaluates rules in the sequence in which they are presented in the configuration file. The last match is binding. For example, inbound packets traversing the following filter will always pass:

```
block in all
pass in all
```

The block rule matches all packets, but so does the pass rule, and pass is the last match. To force a matching rule to apply immediately and make IPFilter skip rules, use the quick keyword:

```
block in quick all
pass in all
```

An industrial-strength firewall typically contains many rules, so use of quick is important to maintain the performance of the firewall. Without it, every packet is evaluated against every rule, and this wastefulness is costly.
