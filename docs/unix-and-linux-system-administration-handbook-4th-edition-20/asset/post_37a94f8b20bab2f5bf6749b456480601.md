```
logfile /var/svc/log/network-ssh:default.log
restarter /var/svc/svc/starter:default
contract_id 65
dependency require_all/none svc/system/filesystem/local (online)
dependency optional_all/none svc/system/filesystem/autofs (online)
dependency require_all/none svc/network/loopback (online)
dependency require_all/none svc/network/physical (online)
dependency require_all/none svc/system/cryptos (online)
dependency require_all/none svc/network/utmp (online)
dependency require_all/none=/restart file:/localhost/etc/ssh/ssh_config (online)
```

This command line uses the full MRI, but there is only one instance of the service, svcs -1 ssh would. The state can assume the following values:

- + online - enabled and successfully started
- disabled - not enabled and not running
- degraded - enabled running with limitations
- legacy_run - running; using the few services that have not been converted to SMF and still use traditional init.d scripts
- uninitialized - starting and reading configuration
- maintenance - reporting an error requiring administrative attention has occurred
- offline - enabled off-line because the service is waiting on unsatisfied dependency or cannot start for some reason

In addition to the current service status, svcs -l lists the service's log location, dependencies, and other essentials.

Dependencies allow the specification of arbitrarily complex relationships among services. This facility essentially replaces the system of numbered startup scripts used by the traditional init system, a script prefixed with S20 runs before prefixed with S90.

In the example above, SSH requires local filesystems, network interfaces, cryptography services, utmp, and the existence of the ssh_config file. The system automounter is marked as an optional dependency; SSH will run if the automounter is intentionally off-line (as set by the administrator) or if it is on-line and running.

The svcadm command changes the status of a service. To disable the SSH service (don't try this remotely!), use

```
solaris$ svcadm disable ssh
```

This example uses the short MRI for SSH, since it's unambiguous. The disabling is a persistent change; use svcadm -t to disable SSH temporarily.

Under the hood, SMP configures services through XML files called manifests and profiles. A manifest describes the properties of a service, such as its dependencies and the instructions for starting and stopping it. Manifest files are stored in /var/svc/manifest directory. Each instance of a service has its own manifest.

# A brave world: booting with SMF

The exec_method lines in a manifest file usually point to scripts that start and stop services, like the scripts used in the init.d system. For instance, the startup process for the SSH daemon is defined in /var/svc/manifest/ssh.xml as

```xml
<exec_method
type='method'
name='start'
exec='/lib/svc/method/sshd start'
timeout_seconds='60'>
```

The /lib/svc/method/sshd script that is referred to as in starts starts the service. It looks suspiciously like a script that might have lived in /etc/rc.d—the more things change, the more they stay the same.

The service's profile file determines whether the instance is enabled or disabled. Profiles are kept in /var/svc/profile.

The persistent configuration for service is actually stored as a SQLite database in /etc/repository.db. Therefore, you shouldn't directly modify the contents of the XML files. Using inetadm you can manage the manifests and profiles with the svcfcg command. The daemon sees the pages for svcfcg, inetadm, and svc.config for more information.

One of the most touted features of SMF is the concept of "restarts", part of Solaris's much-hyped "predictive self-healing" technology. By contemplating the carefully defined dependency system, SMF can supposedly determine the reason that a service died and restart it if appropriate. The cause of a service failure might be a software bug, a hardware problem, or even administrator error. A designated SMF restart process, closely tied to the kernel, automatically performs the appropriate recovery actions.

# A brave new world: booting with SMF

The boot process on Solaris 10 or later system is very similar to traditional bootstrapping. SPARC booting is slightly different from booting on Intel systems, the general concept is that low-level firmware (PROM for SPARC, BIOS for Intel) reads in a boot config, which loads the OS kernel.

The kernel scans /etc/system for loadable modules, then spins up init, which immediately starts the svc.startd process. svc.startd is the master SMF starter and is responsible for starting services in dependency order, as defined in the SMF configuration repository.

Unfortunately, the run-level system and the init scripts from previous versions of Solaris are not completely dead. Some services—the ones that show as legacy-run in svcs -a output—still rely on scripts in the /etc/rc.d directories. The collision between SMF milestones and traditional run levels has left behind something of a pile of wreckage.

To avoid cutting your fingers on the sharp edges, keep in mind a few key points:

- Services in the legacy-run state were started from an rc script.
- Solaris defines eight run levels. See the main page for init for details.
- To change run levels, use init n, where n is the new run level. Do not try to use SMF to change milestones.

# REBOOTING AND SHUTTING

Traditional versions of shutdown were like a deconstructions. Modern systems have become much better. The shutdown command is the safest way.

- For example, a Linux shutdown command reminds us of scheduled maintenance and halts the system at 9:30 a.m. would look something like this:

```
$ sudo shutdown -h 09:30 "Going down for scheduled maintenance.
Expected downtime is 1 hour."
```

- It's also possible to specify a relative shutdown time. For example, the shutdown command shuts the system 15 minutes from when it is run:

```
$ sudo shutdown -h +15 "Going down for emergency disk repair."
```

# shutdown: the safest way

The shutdown command is the safest way to shut down. It is shutdown -h can also be used by itself. halt logs the shutdown, kills unnecessary processes, executes the sync system call (called by equivalent to the sync command), waits for filesystem writes to complete, and halts the kernel.

halt -n prevents the sync call. It's used by fsck after it repairs the root partition. fsck did not use -n, the kernel might overwrite fsck's repairs with old versions of the superblock that were cached in memory.

reboot is almost identical to halt, but it causes the machine to reboot instead of halting. reboot is called by shutdown -r.
