Here's how you print the files `foo.pdf` and `/tmp/testprint.ps` for your default printer under CUPS:

```bash
$ lpr foo.pdf /tmp/testprint.ps
```

The lpr transmits copies of the files to the CUPS server, which stores them in the print queue. CUPS processes each file in turn as the printer becomes available.

When printing, CUPS examines both the document and the printer's PostScript Description (PPD) to see what needs to be done to get the document to print properly. (As we discuss in more detail on page 102, PPD files are used for non-PostScript printers).

To prepare a job for printing on a specific printer, CUPS passes it through a series of filters. For example, one filter might reformat the job so that two reduced-size images print on each page (aka "2-printing"), and another might transform the job from PostScript to PCL. CUPS can also perform printer-specific processing such as printer initialization. Some filters perform rasterization, turning abstract instructions such as "draw a line across the page" to a bitmap image. Rasterizers are useful for printers that do not include their own rasterizers or do not speak the language in which a job was originally submitted.

The final stage of the print pipeline is a back that transmits the job from the host to the printer through an appropriate protocol such as Ethernet. The back end also sends status information in the other direction, back to the CUPS server. To see your available back ends, try the command

```bash
$ locate backup | grep -i cups
```

After transmitting the print job, the CUPS daemon returns to processing its queues and handling requests from clients, and the printer goes off to print the job it shipped.

For example, the lpq command requests job status information from the server and reformats it for display. Other CUPS clients ask the server to suspend, cancel, or reprioritize jobs. They can also move jobs from one queue to another.

Most changes require jobs to be identified by their job number, which you can get from lpq. For example, to remove a print job, just run `lprm job`.

`lpstat -t` summarizes the print server's overall status.

# Multiple printers and queues

The CUPS server maintains a separate queue for each printer. Command-line clients accept an option (typically -P printer or -p printer) to specify which queue you want to address. You can also set a default printer for yourself by setting the PRINTER environment variable

```bash
$ export PRINTER=printer_name
```

or by telling CUPS to use a particular default for your account.

```bash
$ loptions -printer_name
```

When run as root, loptions sets system-wide defaults in /etc/cups/loptions, but it's more typically used by individual, non-root users. loptions lets each user define personal printer instances and defaults, which it stores in ~/.loptions; `loptions -l` lists the current settings.

# Printer instances

If you have only one printer but want to use it in several ways—say, for both drafts and for final production work—CUPS lets you set up "printer instances" for these different uses.

For example, if you already have a printer named Phaser_6120/2up, the command `$ loptions -p Phaser_6120/2up -o number-up=2 -o job-sheets=standard` creates an instance named Phaser_6120/2up that performs 2-up printing and adds banner pages. Once the instance has been created, the command

```bash
$ lpr -t Phaser_6120/2up biglisting.ps
```

prints the PostScript file biglisting.ps as a 2-up job with a banner page.

# Network printing

From CUPS perspective, a network of machines isn't very different from an isolated machine. Every computer runs cupsd, and all the CUPS daemons talk to one another.

If you're working on the command line, you configure CUPS to print jobs from remote systems by editing the /etc/cups/cupsd.conf file (see Network print server setup on page 1039). By default, servers that are set up this way broadcast information every 30 seconds about the printers they serve. As a result, computers on the local network automatically learn about the printers that are available to them. You can effect the same configuration by clicking a check box in the CUPS GUI in your browser.

If someone has plugged in a new printer, if you've brought your laptop to work, or if you've just installed a new workstation, you can tell cupsd to look and see what's out there by clicking on the Find New Printers button in the Administration tab of the CUPS GUI.

Because broadcast packets do not connect subnets, it's a bit tricky to make printers available to multiple subnets. One solution is to designate a slave server on each subnet that polls the other subnets' servers for information and then relays that information to machines on the local subnet.

For example, suppose the print servers alice (192.168.1.5) and jj (192.168.2.14) live on different subnets and we want both of them to be accessible to users on a third subnet, 192.168.3.10. We designate a slave server (say, copeland, 192.168.3.10) and add these lines to its cupsd.conf:

```
BrowsePoll alice
BrowsePoll jj
BrowseRelay 127.0.0.1 192.168.2.355
```

The first two lines tell the slave's cupsd to poll the cupsds on alice and jj about the printers they serve. The third line tells copeland to relay the information it learns to its own subnet. Simple!
