## Naming conventions for devices

Naming conventions for devices are somewhat random. They are often holders from the ways they were done under UNIX on a DEC PDP-11, archaic as that may sound in this day and age.

For devices that have both block and character identities, the character device name is usually prefixed with the letter r for “raw” (e.g., /dev/da0 vs. /dev/rda0). An alternative convention is to store device files in a subdirectory that starts with t (e.g., /dev/dsk/dks0d3s vs. /dev/rdsk/dks0d3s). However, an r does not always imply a raw device file.

Serial devices are usually named tty by a sequence of letters that identify the port is attached to. TTYs are represented by more than one device file; the extras fully afford access to alternative control methods or locking protocols.

The names of tape devices often include not only a reference to the device itself but also an indication of whether the device rewinds after the tape device is closed. Each vendor has a different scheme.

The naming conventions for the files that represent hard disks and SSDs are rather complex on most systems. Disk device files on page 224 for details.

## Custom kernels versus loadable modules

When the system is installed, it comes with a generic kernel designed to run most applications on most hardware. The generic kernel includes many different device drivers and option packages. Some drivers may also be dynamically inserted into the running kernel. On Linux, the udev system can also manage device time changes, such as the insertion of a USB device.

There are various schools of thought on whether the production servers should have built-custom kernels. Although there is some potential for performance gains, especially in embedded systems without much memory, the manageable tradeoff for patching and system upgrades is a deal breaker. Unless there’s legitimate need to write every last ounce of performance out of the system, we recommend using the vendor’s stock kernel.

When it comes to kernel device support, the wise administrator is also the laiest. Use the dynamic module approach whenever possible. Avoid building a custom kernel unless it is strictly necessary. On Linux systems, most USB devices can be attached with no administrator intervention.

## 13.3 LINUX KERNEL CONFIGURATION

You can use any of four basic methods to configure a Linux kernel. Chances you'll have the opportunity to try all of them eventually. The methods are:

- Modifying tunable (dynamic) kernel configuration parameters
- Building a kernel from scratch (really, this means compiling it from the source code, possibly with modifications and additions)
- Loading new drivers and modules into an existing kernel on the fly
- Providing operational directives at boot time through the kernel loader, GRUB. See page 82 for more information.

These methods are each applicable in slightly different situations. Tuning parameters are the easiest and most common, building a kernel from source files is the hardest and least often required. Fortunately, all approaches become second nature with a little practice.

## Tuning Linux kernel parameters

Many modules and drivers in the kernel were designed with the knowledge that one size doesn't fit all. To ensure flexibility, special hooks allow parameters such as an internal table size or the kernel's behavior in particular circumstance to be adjusted by the system administrator. These hooks are accessible through an extensive kernel-to-user interface represented by files in the /proc filesystem (aka procfs). In some cases, a large-user-level application (especially an "infrastructure" application such as a database) may require a sysadmin to adjust kernel parameters to accommodate its needs.

You can view and set kernel options at run through special files in /proc/sys. These files mimic standard Linux files, but they are really back doors the kernel. If a file in /proc/sys contains a value to change, you can write to it. Unfortunately, not all files are writable (regardless of their apparent permissions). If you have the kernel tree installed, you may be able to read about some of the values and their meanings in the subdirectories Documentation/sysct.

For example, to change the maximum number of files the system can have open at, something like:

```
linux$ cat /proc/sys/fs/file-max
34916
linux$ sudo sh -c "echo 32768 > /proc/sys/fs/file-max"
```

Once you get to this unorthodox interface, you'll find it quite useful. A word of caution, however: changes are not remembered across reboots.

## Building a Linux kernel

Because Linux evolves rapidly, it is likely that you'll eventually be faced with the need to build a kernel. Kernel patches, device drivers, and new functionality arrive on the scene. This is really something of a mixed blessing. On one hand, it's convenient to always support the "latest and greatest," but on the other hand, it can become time consuming to keep up with the constant flow of new material.

It's likely you'll need to build a kernel on your if you're running a "stable" version. Originally, Linux adopted a versioning scheme in which the part of the version number indicated whether the kernel was stable (even numbers) or in development (odd numbers). For example, kernel version 2.6.6 would be a "stable" kernel, whereas 2.7.4 would be a "development" kernel. Today, this scheme isn't religiously followed, so you'd check the home page at kernel.org for the official word on this. The kernel.org site is also the best source for Linux source code if you're not relying on a particular distribution (or vendor) to provide you with a kernel.

## If it ain't broke, don't fix it

A good system administrator carefully weighs needs and risks when planning kernel upgrades and patches. Since, the new release may be the latest and greatest, but is it as stable as the current version? Could the upgrade or patch be delayed and installed with another group of patches at the end of the month? A good rule of thumb is to upgrade or apply patches only when the productivity gains you expect will exceed the effort and lost time required to perform the installation. If you're having trouble quantifying the specific gain, that's a good sign that the patch can wait for another day. (Of course, security-related patches should be installed promptly.)
