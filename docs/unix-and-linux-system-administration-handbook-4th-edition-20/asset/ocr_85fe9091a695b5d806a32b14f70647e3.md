For example, the default iptables table is named “filter”. Chains of rule in this table are used for packet-filtering network traffic. The filter table contains three default chains: FORWARD, INPUT, and OUTPUT. Each packet handled by the kernel is passed through exactly one of these chains.

Rules in the FORWARD chain are applied to all packets that arrive on one interface and need to be forwarded to another. Rules in the INPUT and OUTPUT chains are applied to traffic addressed to or originating from the local host, respectively. These three standard chains are usually all you need for firewalling between two network interfaces. If necessary, you can define a custom configuration to support more complex routing scenarios.

In addition to the filter table, iptables includes the “nat” and “mangle” tables. The nat table contains chains of rules that control Network Address Translation (Translation, here “nat” is the name of the iptables table and “NAT” is the name of the generic address translation scheme). The Private addresses and network address translation (NAT) on page 462 discusses NAT, and an example of the nat table is shown on page 493. In this section, we use the nat table PREROUTING chain for anti-spoofing packet filtering.

The mangle table can modify or alter the contents of network packets outside the context of NAT and packet filtering. While the mangle table is handy for special packet handling, as resetting IP time-to-live values, it is not typically used in most production environments. We discuss the filter and nat tables in this section, leaving the mangle to the adventurous.

# Rule targets

Each rule that makes a chain has a “target” that defines what to do with matching packets. When a packet matches a rule, its fate is in most cases sealed; no additional rules will be checked. Although many targets are defined internally by iptables, it is possible to specify another chain as a rule target.

The targets available rules in the filter table are ACCEPT, DROP, REJECT, LOG, MIRROR, QUEUE, REDIRECT, RETURN, and ULOG. When a rule in an ACCEPT, matching packets are allowed to proceed on their way. DROP and REJECT drop both packets; DROP is silent, and REJECT returns an ICMP error message. LOG gives a simple way to track packets as they match rules, and ULOG expands logging.

REDIRECT sends packets to a proxy instead of letting them go on their merry way. For example, you might use this to force all your site's web traffic through a web cache as Squid. RETURN terminates user-defined chains and is analogous to the return statement in a subroutine call. The MIRROR swaps the IP source and destination address before sending the packet. Finally, QUEUE handles packets to local user programs through a kernel module.
