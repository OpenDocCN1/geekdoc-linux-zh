
# Chapter 12 Software Installation and Management

Sadly, HP-UX does not have a convenient on-line software repository from which you can easily install patches. The closest to it is the HP-UX Software Assistant tool, which analyzes the system with reference to an HP-provided catalog of patches, downloads the appropriate patch bundles, and builds a software depot from which you can use swinstall to patch the system.

Let’s look at a few examples. To install security patch PHKL_ from an NFS-based software depot on the host hpux.booklab, we run the command

```
hpux-$ sudo swinstall -s hpux.booklab:/hpux/patches PHKL_40197
```

swinstall runs configuration scripts automatically during installation. If you need to reconfigure a package, use the swconfig command. swconfig config a software package for the local system (e.g., by making modifications to a file in /etc or changing the permissions in a directory). To reconfigure the sudo package, we run the following command:

```
hpux-$ sudo swconfig -x reconfigure=true sudo
```

To remove this package, we run swremove sudo. It verifies a package and performs an integrity check on its essential components. Use swverify to fix problems such as broken defaults files or missing directories.

swlist shows you the software installed or available in a depot. The interactive interface is generally handled for searching, but here’s a simple command that lists the Java-related packages on our example HP-UX system:

```
hpux-$ sudo swlist "Java"
# Initializing.
# Contacting target "hpux11"...
# Target: hpux11/
```

| Java15IDK | 1.5.01.100 | Java 1.5 JDK for HP-UX |
| Java15JDK,Jdk15 | 1.5.01.100 | Java 1.5 JDK |
| Java15JDK,Jre | 1.5.01.100 | Java 1.5 JRE |
| #JRE | 1.5.01.100 | Java 1.5 JRE for HP-UX |
| Java15Jre,Jre15 | 1.5.01.100 | Java 1.5 JRE |

Remote operation is a powerful feature of Software Distributor. The remote features allows sysadmins to push software to remote systems (optionally, on a pre-schedule). Most commands support remote operations, and some, such as swinstall, also support them in their GUIs. Remote operations are performed with remote procedure calls (RPC), and security is controlled with access control lists. See man 5 sd to configure remote operations.

# Software management in AIX

Most UNIX vendors have at least attempted to keep up with Linux in the software management space, IBM has opted for something of a Stone Age approach in AIX. The SMIT install_software fastpath is recommended in most cases; behind the curtains, it invokes the installapp command. The SMIT easy_install fastpath is another option that requires fewer keystrokes for install_software.

installapp processes on IBM-proprietary package called Backup File Format, or .bbf, as well as an older version of the RPM format used by many Linux systems. Unfortunately, installall is missing many features that skilled administrators have come to take for granted, such as package installation from a network depot and even effective package querying. We always use smit install_software or easy_install when we add packages to our AIX systems.

AIX lspp command lists the installed software packages, which IBM refers to as "filesets." lspp -L lists all software products on the system—you can also use the smit list_installed_sw fastpath to similar effect. Installed software has state and type codes that indicate the condition and origin of each package. The state can be one of applied, broken, committed, locked, obsolete, or inconsistent. The type is an installapp fileset, proper, component, feature, RPM, or fix.

# 12.9 REVISION CONTROL

Mistakes are a fact of life. Therefore, it's important to keep track of the changes you make so that if these changes cause problems, you can easily revert to a known-good configuration. In this section we discuss common ways of managing changes at the level of individual files. Choose the tools that match your needs and the complexity of your site.

# Backup file creation

This command probably looks familiar:

```
$ cp bigfile.conf bigfile.bak
```

It seems a bit bashful, as—surely, real system administrators do something more sophisticated?

In fact, there's much to be said in favor of this kind of impromptuu backup. Backup files are simple to create, easy to diff, and they create an audit trail, at least the extent that backup files can be ordered by modification time. and there's no possibility that someone will leave the backup system in an ambiguous state.

We suggest a couple of tweaks, however. It is best to create backup files by moving the original file to its new name with mv and copying it back to its original name. Use cp -p to preserve the file's attribute settings. This procedure preserves the original file's modification time and handles cases in which a process has an open reference to the original file.

Better yet, add a short scriptlet the one below to your ~/.bash_profile or ~/.profile. It defines a backup "command" (a bash function, really) that picks a backup filename and does the switcherooo for you.

```
function backup () {
newname=$1.$(date +%Y%m%d.%H%M.bak);
mv $1 $newname;
echo "Backed up $1 $newname";
cp -p $newname $1;
}
```

For example:

$ backup hello.py
Backed up hello.py.20091030.1612.bak.

The filename encodes the date and time at which the backup occurred, and the file's modification time records the time at which the contents were changed prior to your new (still-to-be-made) updates. Both pieces of information are potentially useful. This script encodes the time in such a way that an alpha sort of the filenames sorts the backup files correctly by date.

Systems that are regularly backed up to tape can still benefit from the use of manually created backups. Recovery from a backup file is faster and easier than recovery from a tape, and manual backups preserve an additional layer of history.

# Formal revision control systems

At the next level are formal revision control systems. At the next level of complexity, formal revision control systems address several problems. First, they provide history of modifications. Second, they extend the concept of versioning beyond individual files. Finally, they coordinate activities of editors.

The last few years have witnessed a boom in open source version control. Major contenders among the newer systems are Arch, Mercurial, and Bazaar. Git, originally developed by Lin Torvalds, has gained traction and is now widely used.

The most popular systems today are Subversion and Git. Either system works well for system administration, but Git has an edge in what it sets up for fast and simple.

# Subversion

In the Subversion model, a central server or directory acts as a project's authoritative repository. By default, the Subversion server is a module in the Apache server, which is convenient for software development but may not be so good for administrative uses. Furthermore, Subversion follows an alternative type of server in the form of a daemon svnserve. You can run svnserve from your home directory while experimenting with Subversion, but in production it should have its own account and be run from incd.

Setting up a repository is easy. For example, the following steps create a new Subversion repository called admin:

```
# cd /home/svn
# mkdir repositories
# cd repositories
# svnadmin create admin
# chmod 700 admin
```

If you peek inside the admin directory, you will find a well-organized repository structure, including a conf README file. The configuration file svnconf can be found in the conf subdirectory. This file tells the server daemon how to provide access to the new repository. Here's an example configuration appropriate for administrative uses:

```
[general]
anon-access = none
auth-access = write
password-db = passwd
realm = The Sysadmin Repository
```

Because one of Subversion's design goals was to facilitate collaboration among people at different sites, it has an access control method that is separate from that of the operating system. The file password (in the same directory) contains a list of users and their plaintext (!) The plaintext bit is not nice, but the saving grace is that the passwords are never transmitted over the network. They are also never typed from memory by users, so you may assign passwords that are long enough and random enough to be secure.

Several commercial version control systems are also available. You may already have access to one of them if you work in a development shop, and you might be tempted to use it. Tread carefully, though; our experience has been these commercial systems are usually overkill for sysadmin.

For other advantages of Git, see Scott Chacon's whygitbetterthanx.com site.
