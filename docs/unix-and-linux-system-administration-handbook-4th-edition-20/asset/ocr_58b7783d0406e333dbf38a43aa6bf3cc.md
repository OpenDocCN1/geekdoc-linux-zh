# Throttles, rates, and connection limits

After the no-such-login count reaches the limit set in the BAD_RCPT_THROTTLE option, sendmail sleeps for one second after each rejected RCPT command, spawning a spammer's address harvesting to a crawl. Set that threshold to 3, use

```
define(confBAD_RCPT_THROTTLE, `3`)
```

Setting the MAX_RCPITS_PER_MESSAGE option causes the sender to queue extra recipients for later. This is a cheap favor of greylisting for messages that have a suspiciously large number of recipients.

The ratecontrol and conncontrol features allow per-host or per-net limits on the rate at which incoming connections are accepted and the number of simultaneous connections. Both use the /etc/mail/access file to specify limits and the domains that they should obey, the first with tag ClientRate: in the key field and the second with tag ClientConn:. To enable controls, insert lines like these in .mc file:12

```
FEATURE(ratecontrol', 'nodelay', terminate)
FEATURE('conncontrol', 'nodelay', terminate)'
```

Then, add to /etc/mail/access the list of hosts or nets to be controlled and their restriction thresholds. For example, the lines

```
ClientRate:172.168.6.17 2
ClientRate:170.65.3.4 10
```

limit the hosts 192.168.6.17 and 170.65.3.4 to two new connections per minute, respectively, the lines

```
ClientConn:192.168.2.8 2
ClientConn:175.14.4.1 7
ClientConn: 10
```

set limits of two simultaneous connections for 192.168.2.8, for 175.14.4.1, and ten simultaneous connections for all hosts.

Another nifty feature is greet_pause. When a remote MTA connects to your sendmail server, the SMTP protocol mandates that it wait for your server's coming greeting before speaking. However, it's common for spam mailers to blunt an EHLO command immediately. This behavior is partially explained as poor implementation of the SMTP protocol in spam-sending tools, but may also be a feature that aims to save time on the spammer's buffer. Whatever the cause, this behavior is suspicious and is known as 'slamming'.

The greet_pause feature makes sendmail wait for a specified period of time at the beginning of the connection greeting its newfound friend. The remote MTA does not wait to be properly greeted and proceeds with an EHLO or HELLO command during the planned awkward moment, sendmail logs an error and refuses subsequent commands from the remote MTA.
