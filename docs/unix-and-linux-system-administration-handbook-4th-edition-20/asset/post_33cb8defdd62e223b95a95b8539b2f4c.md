## 17.2 How DNS WORKS

Each host that uses DNS is either a client of the system or simultaneously a client and a server. If you do not plan to run any DNS servers, it is not essential that you read the next few sentences. skip ahead to page 561 for details on configuring a machine to be a client of DNS.

## Resource records

Each site maintains one or more pieces of the distributed database that makes up the world-wide DNS system. Your piece of the database contains text files that contain records for each of your hosts; these are known as "resource records." Each record is a single line containing a name (usually a hostname), a record type, and some data values. The name field can be omitted if it is the same as that of the previous line.

For example, the lines

```
nubark      IN A      63.173.189.1
            MX     10 mailserver.atrust.com.
```

in the "forward" file (called atrust.com), and the line

```
1           IN PTR     nubark.atrust.com.
```

in the "reverse" file (called 63.173.189.rev) associate nubark.atrust.com with the IP address 63.173.189.1. The MX record reroutes email addressed to this machine to the host mailserver.atrust.com.

Resource records are the lingua franca of DNS and are independent of the configuration files that control the operation of any given DNS server implementation. They are also the pieces of data that flow around the DNS system and become cached at various locations.

## Delegation

All name servers resolve the identities of the root servers from a local config file or have them built into the code. The root servers know the name servers for net, edu, fi, de, and other top-level domains. Further down the chain, edu knows about colorado.edu, berkelely.edu, and so on. Each domain can delegate authority for its subdomains to other servers.

Let's inspect a real example. Suppose we want to look up the address for the machine vong.cs.berkeley.edu, from the machine lair.cs.colorado.edu. The host asks its local name server, ns.cs.colorado.edu, to figure out the answer. The following illustration (Exhibit A) shows the subsequent events.

![](img/579efec8c67772f31ecf34844bbb71a2_604_0.png)

The names on the arrows between servers show the order of events, and a letter indicates the type of transaction (query, referral, or answer). We assume that none of the required information was cached before query, except for the names and IP addresses of the servers of the root domain.

The local server doesn't know vangogh's address. In fact, it doesn't know anything about cs.berkeley.edu or vangogh.edu or even edu. It knows servers for the root domain, however, it queries a root server over vangogh.cs.berkeley.edu and receives a referral to the servers for edu.

The local name server is a recursive server. When an answer query consists of a referral to another server, the local server resubmits the query to the new server. It continues to follow referrals until it finds a server that has the data it's looking for.

In this case, the local name server sends its query to a server of the edu domain (asking, as always, about vangogh.cs.berkeley.edu) and gets back a referral to the servers for berkeley.edu. The local name server then repeats the query in the berkeley.edu domain. If the Berkeley server doesn't have the answer cached, it returns a referral to the servers for cs.berkeley.edu. The cs.berkeley.edu server is authoritative for the requested information, looks the answer up in its zone files, and returns vangogh's address.

When the dust settles, ns.cs.berkeley.edu has each cached data on the servers for edu, berkeley.edu, and cs.berkeley.edu.

You can view the query process in detail with dig and drill -T.

## Adding a new machine to DNS

If your network is set up to the Dynamic Host Configuration Protocol (DHCP) you may not need to perform any manual configuration for DNS. When a new computer is connected, the DHCP server informs it of the DNS servers it should use. Hostname-to-address mappings for the outside world were most likely set up when the DHCP server was configured. To identify which machine is the master server, you probably should not be messing with it, but you can use the **dig** (SOA domainname) to identify it. You can use **drill** if dig is not installed.

**Step 1**: Choose an unused hostname and IP address for the new machine in conjunction with local synams or your upstream ISP.

**Step 2**: Identify a similar machine on the same subnet. You’ll use that machine’s records as a master for the new ones. In this example, we use a machine called template.example.com on the subnet 208.77.188/24 as the master.

**Step 3**: Log in to the master server machine. If you don’t know which machine is the master server, you probably should not be messing with it.

**Step 4a**, for sites binding BIND servers:

- Find the master server configuration file, usually /etc/named.conf.
- Within the **options** statement in **named.conf**, find the **directory** line that tells you zone data files are kept at your site (see page 603). The zone files contain the actual host and IP address data.

- From the **zone** statements, the filenames for the forward zone file and reverse zone file appropriate for your new IP address (page 612). Verify from the **zone** statements that this server is fact the master server (type **master**, not **slave** or some value) for the Domain. If it’s not, you’re on the wrong server! The forward zone statement in **/etc/named.conf** should look something like this:

```
www IN A 192.168.0.1
    IN A 192.168.0.2
    IN A 192.168.0.3

# Delegation

All name servers resolve the identities of the root servers from a local config file or have them built into the code. The root servers know the name servers for net, edu, fi, de, and other top-level domains. Further down the chain, edu knows about colorado.edu, berkelely.edu, and so on. Each domain can delegate authority for its subdomains to other servers.

Let's inspect a real example. Suppose we want to look up the address for the machine vong.cs.berkeley.edu, from the machine lair.cs.colorado.edu. The host asks its local name server, ns.cs.colorado.edu, to figure out the answer. The following illustration (Exhibit A) shows the subsequent events.
