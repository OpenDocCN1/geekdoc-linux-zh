
## Access determination

When the ACL in the previous example is expanded to include entries for a specific user and group, setfac automatically supplies an appropriate mask:

```
$ ls -l /tmp/example
-rw-r-- 1 garth 0 Jun 14 15:57 /tmp/example
$ setfac -m user:trent:rwx,group:admin:rw /tmp/example
$ ls -l /tmp/example
-rw-r----+ 1 garth 0 Jun 14 15:57 /tmp/example
$ setfac --omit-header /tmp/example
```

As here, the Linux version of setfac generates a mask that allows all the permissions granted in the ACL to take effect. If you want to set the mask by hand, include it in the ACL list given to setfac or use the -n option to prevent setfac from regenerating it. (The Solaris setfac defaults to not recalculating the mask entry; use the -r flag to regenerate it.)

Note that after the setfac command, ls -l shows a + sign at the end of the file's mode to indicate that it now has a real ACL associated with it. The first ls -l shows no + because at that point the ACL is "minimal." and it is entirely described by the 9-bit mode and does not need to be stored separately.

If you use the chmod command to manipulate the permissions on an ACL-bearing file, be aware that your changes affect only the mask. To continue the previous example:

```
$ chmod 770 /tmp/example
$ ls -l /tmp/example
-rwxrwx----+ 1 garth staff 0 Jun 14 15:57 /tmp/example
$ setfac --omit-header /tmp/example
```

The ls output is misleading. Despite the apparently generous group permissions, no one actually has permission to execute the file by reason of group membership. To grant such permission, you must edit the ACL itself.

## Access determination

When a process attempts to access a file, its effective UID is compared to the UID that the file. If they are the same, access is determined by the ACL's user:: permissions. Otherwise, if a matching user-specific ACL entry exists, permissions are determined by that entry in combination with the ACL mask.

If no user-specific entry is available, the filesystem tries to locate a valid group-related entry that provides the requested access; these entries are processed in conjunction with the ACL mask. If no matching entry is found, the other:: entry prevails.

## ACL inheritance

In addition to the ACL entry types listed in Table 6.8, the ACLs for directories can include default entries that are propagated to the ACLs of newly created files and subdirectories created within them. Subdirectories receive both entries in the form of active ACL entries and in the form of the default entries. Therefore, the original default entries may eventually propagate through several layers of the directory hierarchy.

The connection between the parent and child ACLs does not continue once the default entries have been copied. If the parent's default entries change, the changes are not reflected in the ACLs of subdirectories.

## NFSv4 ACLs

In this section, we discuss the characteristics of NFSv4 ACLs and briefly review the Solaris syntax used to inspect them. AIX also supports NFSv4 ACLs, but it uses different commands (acget, aclpt, aclited, et al.) for this purpose. Rather than elaborating the details of any particular command set, we concentrate on the theory behind the system. Once, the system-specific commands are easy to pick up.

From a structural perspective, NFSv4 ACLs are similar to Windows ACLs. The main difference between them lies in the specification of the entity to which an access control entry refers.

In both systems, the ACL stores this as a string. For Windows ACLs, the string typically contains a Windows security identifier (SID), whereas for NFSv4, the string is typically of the form user:username or group:groupname. It can be one of the special tokens owner@, group@ or everyone. These entries are the most common because they correspond to the mode bits found every file.

Systems such as Samba share files between UNIX and Windows systems provide some way of mapping between Windows and NFSv4 principals.

The Windows and NFSv4 permission is more general than the traditional UNIX read-execute model. The main refinements are as follows:

- NFSv4 distinguishes permission to create files within a directory from permission to create subdirectories.
- NFSv4 has a separate "append" permission bit.
- NFSv4 has separate read and write permissions for data, file attributes, extended attributes, and ACLs.
- NFSv4 controls a user's ability to change the ownership of a file through the standard.

Table 6.9 shows the various permissions that can be assigned:

| Code | Verbose name | Permission |
| :--- | :--- | :--- |
| r | read_data | data (file) |
| w | write_data | data (file) |
| p | append_data | data (file) |
| R | read_xattr | extended attributes |
| W | write_xattr | extended attributes |
| D | delete | extended attributes |
| a | audit | extended attributes |
| A | alarm | extended attributes |
| d | delete child | access list |
| C | read_acl | access list |
| o | write_acl | access list |
| s | synchronize | ownership |

Some permissions have multiple names because they are represented by the traditional system. For example, x in the traditional system indicates execute.

An extended attribute is a named chunk of data that is stored along with file; most modern filesystems support such, although they are not widely used.
