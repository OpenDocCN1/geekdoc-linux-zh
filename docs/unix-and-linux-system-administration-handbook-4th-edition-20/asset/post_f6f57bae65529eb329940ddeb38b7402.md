The kernel allows a process to restrict its own use of physical memory by calling the setlimit call. This facility is also available in the C shell through the built-in limit command. For example, the command

% limit memoryuse 32m

causes all subsequent commands that the user runs to have their use of physical memory limited to 32Mib (Solaris uses memoriesize rather than memory). This feature is roughly equivalent to renice for memory-bound processes.

If a runaway process doesn't seem to be the source of poor performance, investigate other possible causes. The first is an overloaded network. Many programs are intimately bound by the network and it's hard to tell where system performance ends and network performance begins. See Chapter 21 for more information about the tools used to monitor networks.

Some network overloading problems are hard to diagnose because they come and go. For example, if every machine on the network runs a network-related program at a particular time each day, then there will be a brief but dramatic glitch. Every machine on the net will hang for five seconds, and then the problem will disappear as quickly as it came.

Server-related delays are another possible cause of performance issues. UNIX and Linux systems are constantly consulting remote servers for NFS, Kerberos, DNS, and any dozen other facilities. If a server is dead or some other problem makes the server expensive to communicate with, on a busy system, process may use the library every few seconds or so, you will likely perceive a difference in overall performance. Forward and reverse lookup problems are responsible for a surprising number of server issues.

# 30 Cooperating with Windows

Chances are high that your environment includes both Microsoft Windows and UNIX systems. If so, these operating systems can assist each other in many ways. Among other feats, Windows applications can run from a UNIX desktop or access a UNIX server's printers and files. UNIX applications can display their user interfaces on a Windows desktop.

Both platforms have their strengths, and they can be made to work together. Windows is a popular and featured desktop platform, capable of bridging the gap between the user and the network. UNIX, on the other hand, is a reliable and scalable infrastructure platform. So let's not fight, OK?

## 30.1 LOGGING TO A UNIX SYSTEM FROM WINDOWS

See page 926 for more information about SSH.

Users may often find themselves wanting to head for the snow-covered slopes of a good bash without abandoning the Windows box on their desk. The best remote access tool for UNIX and Linux systems is the secure shell protocol, SSH.

Several SSH client implementations are available for Windows. Our current favorite, the open source PuTTY, is simple and effective. It supports many of the features you have come to expect from a native terminal application such as xterm.

SSH also supports file transfer, and PuTTY includes two command-line clients for this purpose: psftp and pscp. Hard-core “never touch a command line” users might prefer the graphical WinSCP client from winscp.net.

Another good option is to install the more general UNIX-on-Windows Cygwin package and run its SSH utilities using ssh. There's more information about Cygwin starting on page 1140.

A nifty zero-footprint Java implementation of SSH called MindTerm is available from AppGate (appgate.com). It is free for personal use. It runs on any system that supports Java and can be configured in a variety of ways.

Of commercial SSH client implementations, our favorite is VanDyke Soft-SecureCRT, available for purchase from vandyke.com. SecureCRT supports all our favorite terminal features, and VanDyke offers excellent customer service and an open-minded attitude towards feature requests. Like PuTTY, SecureCRT features built-in SFTP file transfer.

An interesting feature of SSH is its ability to forward ports between client and server. For example, this feature allows you to set up a client local port that forwards connections to a different port on a machine that is reachable from the server. Although this feature opens a world of new possibilities, it is also dangerous and something you must be aware of granting SSH access to your server. Fortunately, the port-forwarding feature can be disabled on the server side to limit SSH to terminal access and file transfer.

## 30.2 ACCESSING REMOTE DESKOPS

Graphical desktops on UNIX are tied to the free X Window System, which is in no way related to Microsoft Windows. X is a client/server system. The X server is responsible for displaying data on the user’s screen and for acquiring input from the user’s mouse and keyboard. It communicates with client applications over the network. The server and clients need not be on the same machine.

A more detailed discussion of the X Windows architecture can be found in Chapter 25, *The X Window System*, which starts on page 1011.
