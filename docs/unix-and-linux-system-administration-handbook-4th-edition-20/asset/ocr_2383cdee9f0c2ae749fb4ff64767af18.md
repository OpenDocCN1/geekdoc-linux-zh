# PAM configuration

The general format is
[service] module-type-control-flag module-path [arguments]

Fields are separated by whitespace.

Linux systems don't use a service field, or more accurately, they put each service in its own configuration file and let the filename assume the role of the UNIX service parameter. The service can name an authentication context to which the configuration lines apply (e.g., login for vanilla logins) or can contain the keyword other to set system defaults.

Here's an illustrative snippet from a Solaris system; all module-path fields are relative to the /usr/lib/security directory.

```
login auth required pam_authok_get.so.1
login auth required pam_dhkeys.so.1
login auth required pam_unix_cred.so.1
login auth required pam_unix_auth.so.1
login auth required pam_dial_auth.so.1
```

The order in which modules appear in the PAM configuration file is important. For example, the module that prompts the user for a password must come before the module that checks for password validity. One module can pass its output to the next by setting environment variables or PAM variables.

The module-type parameter--auth, account, session, or pam--determines what the module is expected to do. auth modules identify the user and group memberships. Modules that do account chores enforce restrictions such as limiting the number of simultaneous users, or limiting the ports on which logins can occur. (For example, you would use an account-type module to restrict logins to the console.) session chores include tasks that are done before or after a user is granted access; for, mounting the user's home directory. Finally, password modules change a user's password or passphrase.

The control-flag specifies how the modules in the stack should produce an ultimate result for the stack. Table 22.1 on page 910 shows the common values.

If PAM could return a failure code as the first individual module in a stack failed, the control-flags system would be simpler. Unfortunately, the system is designed so that most modules have a chance to run regardless of their success or failure, and this fact causes some subtleties in the flow of control. (The intent is to prevent an attacker from learning which module in the PAM stack caused the failure.)
