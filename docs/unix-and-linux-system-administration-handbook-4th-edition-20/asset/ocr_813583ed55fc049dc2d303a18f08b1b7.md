This all works if subsets are defined on both boundaries. But how do you handle reverse mappings for a subnet such as 63.173.180/26, where last byte can be in any of four subsets: 0-63, 64-127, 128-191, or 192-255? An elephant hack defined in RFC2317 exploits CNAME resource records to accomplish this feat; see page 585.

The reverse mappings provided by PTR records are used by any program that authenticates inbound network traffic. For example, sshd may allow remote logging without a password if the machine of is listed, in a user's ~/.hosts file. When the destination host receives a request, it knows the source machine by IP address. It uses DNS to convert the IP address to a hostname, which is compared to the appropriate file. netstat, sendmail, tcpd, ssh, Windows, and ftppd do reverse mappings to get hostnames from IP addresses.

It's important that A records match their corresponding PTR records. Matched PTR records cause authentication failures that can slow your system to a crash. This problem is annoying in itself; it can also facilitate denial of service attacks against any application that requires the reverse mapping to match the A record.

# MX records

The mail system uses mail exchanger (MX) records to route mail more efficiently. An MX record preempts the destination specified by the sender of a message, in most cases directing the message to a hub at the recipient's site. This feature puts the flow of mail into a site under the control of local sysadmins instead of senders.

The format of an MX record is

```
name [ttl] [IN] MX preference host ...
```
