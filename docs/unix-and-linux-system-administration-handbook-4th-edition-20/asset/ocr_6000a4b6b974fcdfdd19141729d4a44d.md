# Restricting exports to privileged ports

NFS clients are free to use any TCP or UDP source port they like connect-
to an NFS server. However, some servers may insist that requests come from a
pileged port (a port numbered lower than 1024). This allows their behavior to
set as an option. In the world of PCs and desktop Linux boxes, the use of priv-
 ports ports little actual security.

Most NFS clients adopt the traditional (and still recommended) approach of-
failing to a privileged port to avert the potential for conflict. Under Linux,
can accept mounts from unprivileged ports with the insecure export option.

# 18.5 IDENTITY MAPPING FOR NFS VERSION 4

Unlike earlier versions of NFS, which identify users with raw UID and GID val-\uers, version 4 uses strings of the form user@nfs.domain and group@nfs.domain.
On both NFS servers and clients, an identity mapping daemon translates between
the string identifiers and the local UNIX and GID values. Mapped values are
to translate file attribute information, but they are not used for access-
trol, is handled separately.

All systems participating in an NFS4 network should have the same NFS do-\main. In most cases, it is reasonable to use your DNS name as the NFS domain.
 example, trast.com is a straightforward choice of NFS for the server
harp.atrust.com. Clients in subdomains (e.g., booklab.atrust.com) may or
not want to use the shorter site-wide name (e.g., trast.com) to facilitate NFS
communication.

Unfortunately for administrators, there is no standard implementation of NFSv4
UID mapping, so the details of administration differ slightly among systems. Ta-le 18.10 on the next page names the mapping daemon on each of our example
systems and note the location of its configuration file.
