Most X servers are configured to refuse remote connections by default, so you should be safe as long as you do not run the xhost (or its equivalent) to grant remote access

Unfortunately, granting remote access is exactly what you need to do when you seek to run programs on UNIX and their interfaces on Windows. So, how to run a remote application without granting remote access to the X server? The most common method is to use a feature of the SSH protocol that is specifically designed to support X11. This scheme creates a secure tunnel between clients running on the remote host and the local X server. Programs started on the remote host display automatically on the local machine, but through the magic of SSH, the X server perceives them as having originated locally.

Note that X forwarding only works if the X forwarding features have been enabled on both the SSH server and the SSH client. If you use PuTTY SSH client on Windows, simply activate the X11 forwarding feature in its setup. On the X server side (that is, the X11 client side; the UNIX machine), make sure that the /etc/ssh/sshd_config file contains the line

X11Forwarding yes

If you modify the SSH server configuration, make sure to restart the sshd process to activate the new configuration. The X11Forwarding option is enabled by default on most UNIX systems that use OpenSSH.

As our technical reviewer Dan Foster, forwarding X connections over SSH "can be excruciating slow, even over a LAN, and it is even worse if there is any network latency." VNC, discussed below, is an alternative.

Although Apple provides a free server for Mac OS, Microsoft unfortunately offers no corresponding feature. A free server for Windows is available from the Cygwin project (cywin.com), and it works well once you've configured it. The Xming server for Windows is an excellent alternative that's much easier to configure. Commercial servers for Windows would include Exceed and X-Win32. These offer much simpler configuration at a rather steep price.

# VNC: Virtual Network Computing

In the late 1990s, a few people at AT&T Labs in Cambridge, UK, developed a system for remote desktop access called VNC. Their idea was to marry the simplicity of a dumb terminal with the modern world of window systems. In contrast to X11, the VNC protocol does not deal with individual applications. Instead, it creates a virtual desktop (or provides remote access to an existing desktop) as a unit.

AT&T published the VNC software under a liberal license source. This openness allowed other folks to hop on the bandwagon and create additional server and viewer implementations, as well as protocol improvements that reduced the consumption of network bandwidth. Today, VNC viewers are available for most devices that provide some means for graphical display. VNC servers for UNIX, Linux, and now are widely available.

The UNIX VNC server implementation is essentially a graphics adapter emulator that plugs into the X.Org Windows server. Running a vncserver on UNIX creates a new virtual desktop in the self-contained world of the UNIX machine. You can use a VNC viewer to access that desktop remotely. We recommend taking advantage of the vncpassword command before starting the server for the first time to establish a connection password.

The VNC protocol is stateless and bitmap based. Therefore, viewers can freely connect and disconnect. Moreover, several viewers can access the same server at the same time. This last feature is especially useful for remote support and training setups. It also facilitates shared console access for system administration.

VNC servers in the Windows world do not normally create an extra desktop; they simply export the Standard Windows desktop as it is displayed on screen. The main application for this technology is remote support.

These days, the original authors of the VNC protocol are running their own project, RealVNC (realvnc.com). The UltraVNC project is concentrating on the Windows domain with a very fast and feature-rich Windows-based VNC server implementation, and TightVNC is working on improved compression ratios. These groups talk with each other, so features tend to cross-pollinate among the various implementations.

The VNC protocol has been designed with extensibility in mind. All combinations of viewers and servers can work together; they pick the best protocol variant that both sides understand. Implementation-specific features (such as file transfer) can only be accessed by a server and client running from the same.

# Windows RDP: Remote Desktop Protocol

Ever since Windows 2000 Server, every Windows box has the technical ability to provide graphical remote access to several users at the same time. The remote access component is called Remote Desktop, and it uses a protocol called the Remote Desktop Protocol (RDP) to communicate between client and server. RDP can map the server's printers and disks onto the client.

# Running Windows and Windows-like applications

## 30.3 RUNNING WINDOWS AND WINDOWS-LIKE APPLICATIONS

As discussed in Chapter 24, the free but proprietary VMware Server from vmware.com lets you run multiple operating systems on PC hardware. VMware emulate "guest machines" on top of a host operating system, which must be either Linux or Windows. Regardless of the OS, you can install Intel-compatible operating systems into one of VMware's virtual machines. From the guest machine's perspective, the operating system runs exactly if on dedicated hardware, and applications install normally. Other virtualization offerings such as KVM and VirtualBox also run Windows and should be candidates for running Windows applications.

To take advantage of RDP, you must enable it on the server (Windows) side and set up a client. In Windows 7, go to the System control panel, click Remote settings, and select an option.

A different approach is taken by the Wine system from winehq.org. Wine implements the Windows programming API in the UNIX environment, allowing you to run Windows applications directly on top of X. This free software translates native Windows API calls to their UNIX counterparts and can do so without any Microsoft code. Wine supports TCP/IP networking, serial devices, and sound output. It runs on Linux, BSD, Mac OS, and Solaris systems.

On the UNIX side, install the open source rdesk program (www.rdesktop.org) to display Windows desktops over your workstation. Clients exist for other operating systems, too, including mobile devices.

A large number of Windows applications run in Wine without problems, and others can be made to work with a few tricks; see the web site for details. Unfortunately, getting an application to run under Wine is not so simple. The talented folks codewavers.com have written a commercial installer system that can make some of the bulkier Apps work correctly.

If your tool of choice is supported by CodeWeavers, or even if it is not, give the application a try—you might be pleasantly surprised. If an application does work on its own and you find any prewritten hints, be prepared to spend some serious spare time whipping it into shape if you are determined to it on your own. If you have the budget, you can consider contracting CodeWeavers to help you.
