# 31.4 HARDWARE FLOW CONTROL

The CTS and RTS signals make sure that a device does not send faster than the receiver can process. For example, if a modem is in danger of running out of buffer space (perhaps because the connection to the remote site is slower than the serial link between the local machine and the modem), it can tell the computer to shut up until room becomes available in the buffer.

Flow control is essential for high-speed devices and is also very useful for serial printers. Systems that do not support hardware flow control (either because the serial ports do not understand it or because the serial leaves CTS and RTS disconnected), flow control can sometimes be simulated with software using the ASCII characters XON and XOFF. However, flow control can be explicitly supported by high-level software, and then it does not work well.

XON and XOFF are <Control-Q> and <Control-S>, respectively. This is a problem for emacs users because <Control-S> is the default binding for the emacs search. To fix the problem, bind the search command to another key or use start and stop to change the terminal driver's idea of XON and XOFF.

Most terminals ignore the CTS and RTS signals. By jumping pins 4 and 5 together at the terminal end of the cable, you can fool terminals that require a handshake before they communicate. When the terminal sends out a signal on pin 4 saying "I'm ready", it gets the same signal on pin 5 saying "Go ahead." You can also inject the DTR/DSR/DCD handshake like this.

With soft carrier, hardware flow control can be set through configuration files or with the stty command.

# 31.5 SERIAL DEVICE FILES

Serial ports are represented by device files in or under /dev. Even today, many computers have one or two serial ports built in, mainly as a communication mechanism of last resort. In the past, such ports were usually known by names such as /dev/ttyA and /dev/ttyB, but naming conventions have diverged over time, and those ports are now often named /dev/ttyS0 or /dev/tty1.
