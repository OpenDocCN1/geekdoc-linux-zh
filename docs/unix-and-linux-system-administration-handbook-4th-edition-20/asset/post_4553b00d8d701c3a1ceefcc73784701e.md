If a caching server dies, the network essentially stops working for all the users that were primary clients of their server. (And your phone starts ringing.) Start your caching name servers with a script that restarts them after a few seconds if they die. Here is an example of a nanny script from a machine that runs named for several TLDs:

```
#!/bin/sh
PATH=/usr/local/sbin:/usr/sbin:/sbin:$PATH
export PATH

trap "" 1
while ; do
  named -f /var/named/named.conf >> /var/log/named 2>&1
  /dev/null
  logger "named restart"
  sleep 15
done
exit
```

When named crashes, the script submits a syslog entry with the logger command, which waits 15 seconds (an arbitrary value) before restarting named. BIND ships with a nanny script in the contrib directory, although it's not as necessary as it once was.

On Solaris, you can let SMF do your nannying for you; see page 97.

# Hardware requirements

Name servers need to be well provisioned in three dimensions: CPU, memory, and network bandwidth. Of these, CPU is probably the least critical for now, but it will become more of an issue as DNSSEC is fully deployed and zone signing and signature validation are required. If possible, use dedicated machines for your busy name servers and separate authoritative servers from recursive ones.

Busy servers get thousands of queries per second and therefore need multiple network interfaces and high bandwidth connections. The traffic usually consists of trillions of small UDP packets.

Recursive servers need enough memory to cache all the answers users demand. The best way to determine if a name server has enough memory to run it for a while and wait the size of the name server process. It takes a week or two to grow on a stable state at which old cache records are expiring about the same rate that new ones are being inserted. Once stable, the system should not be swapping, and its paging rates should be reasonable.

If your name server runs on a dedicated machine, a good rule of thumb is for the machine to double the amount of memory consumed by the name server daemon after it has been running for a week. The top and vmstat commands show memory usage; see Analyzing memory usage page 1125 for more details.

Authoritative servers need enough memory to store all the data for which they are authoritative. Most sites can manage this, but for top-level domains and DNS hosting sites may need huge memory or special software that facilitates storing part of the data on.

You can control the amount of resources that a name server uses through configuration options. See the list of tuning options for BIND on page 608 and for dns on page 630.

# Summing up

DNS security is covered in a whole section of its own, starting on page 642. We won't duplicate this discussion here except to remind you that if you use a firewall, be sure that your DNS system does not emit queries to your firewall blocks the answers. Make sure that your DNS administrators have ongoing communication with your security and network administrators.

By default, DNS uses UDP with random unprivileged source ports (>1023) for queries; the answers are UDP packets addressed to those ports. DNSSEC and internationalized domain names, DNS responses may be larger than the path MTU and therefore fragmented. Ergo, your firewall should not block fragmented UDP packets. If a UDP query fails due to fragmentation, often it is issued as a TCP query, so your firewall should be kind to TCP DNS replies, too.

# 17.7 WHAT'S NEW IN DNS

One of the newest developments in the DNS world is the use of DNS records to authenticate and verify the integrity of email. This system, called DomainKeys Identified (DKIM), helps expose phishing (e.g., mail that appears to come from your bank and detects attackers who forge the address). In DKIM system, originating servers sign outbound messages with a cryptographic private key. The corresponding public key is published as a DNS TXT record. Email receivers can verify the integrity and origin of message by looking up the DKIM (public) key and checking against the message's signatures.

From DNS point of view, only the configuration files need change to support a new function. For example, DNSSEC could create a subdomain called _domainkey. Even better, a construct called DNS Signing Practice (ADSP) declaration allows a site to say whether it signs all or none of its outgoing email for each zone. Receiving sites can use this policy to decide how to treat unsigned messages and to be secure.

This mechanism for expressing policy is similar to Sender Policy Framework (SPF), which defines a way for organizations to publish the identities of valid mail servers in DNS so that spammers who try to forge the From address are rejected. Also on our “what’s new” list is the upcoming BIND 10, the next generation of software developed by Internet Systems Consortium, which has maintained BIND since version 4. BIND 10 will continue as an open source reference implementation of DNS, partially built by mostly domain registrars and will focus on improving modularity, customizability, integration, resilience, and run-time control.

BIND 9 and earlier versions stored the database in memory; BIND 10 will support multiple storage systems. Another planned feature is a user interface API so folks can build interfaces to populate zones and control the software. see isc.org/bind10 for details. Several of other “what's new” issues from previous editions are still in the proposed-standard-but-not-widely-adopted pile. Some examples are DNS-sec (security), IDN (internationalized domain names), and IPv6. These initiatives are progressing, but slowly.
