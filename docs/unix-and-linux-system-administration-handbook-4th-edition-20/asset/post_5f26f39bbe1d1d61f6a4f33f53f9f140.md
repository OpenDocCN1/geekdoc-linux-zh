
## NFS4 ACL viewing in Solaris

## ACL inheritance

Like POSIX ACLs, NFSv4 ACLs allow newly created objects to inherit access controls from their enclosing directory. However, the NFSv4 system is a bit more powerful and a lot more confusing. Here are the important points:

- * Any ACE can be flagged as inheritable. Inheritance for newly created subdirectories (dir_inherit or d) and newly created files (file_inherit or f) are flagged separately.

- * You can apply different access controls to files and directories by creating separate access controls on the parent directory and flagging them appropriately. You can also apply a single ACE to all new child entities (of whatever type) by turning on both the d and f flags.

- * From the perspective of access determination, access controls have the same effect on the parent (source) directory whether or not they are inheritable. If you want an entry to apply to children but not the parent directory itself, turn on the ACE's inherit_only (i) flag.

- * New subdirectories normally inherit copies of each ACE: one with the inheritance turned off, which applies to the subdirectory itself; and one with the inherit_only flag turned on, which sets up the subdirectory to propagate its inherited ACEs. You can suppress the creation of this ACE by turning on the no_propagate (n) flag on the parent directory's copy of the ACE. The result is that the ACE propagates only to immediate children of the original directory.

- * Don't confuse the propagation of access controls with true inheritance. Your setting an inheritance-related flag on an ACE simply means the ACE will be copied to new entries. It does not create any ongoing relationship between the parent and its children. If you later change the ACE on the parent directory, the children are not updated.

Table 6.10 NFSv4 ACE inheritance flags

| Code | Verbose name | Meaning |
| --- | --- | --- |
| f | file_inherit | Propagate this ACE to newly created files |
| d | dir_inherit | Propagate this ACE to newly created subdirectories |
| i | inherit_only | Propagate, but don't apply to the current directory |
| n | no_propagate | Propagate to new subdirectories, but not their children |

NFSv4 ACL viewing in Solaris

Solaris has integrated its ACL support into ls and chmod, which is a nice approach and a straightforward extension of the commands' usual functions.

## Chapter 6 The Filesystem

POSIX and NFSv4 ACLs are supported in this manner, although we show only NFSv4 examples. The specific flavor of ACLs that we see or depends on the underlying filesystem.

ls -v shows ACL information for filesystem objects. With -l, you must include the -d option if you want to see the ACL for a directory; otherwise ls -v shows the ACL of every child of the directory. Here's a simple (1):

```
solaris$ mkdir /var/tmp/example
solaris$ ls -dv /var/tmp/example
drwrt-x 2 garth Jan 21 07:19 /var/tmp/example
0owner:deny
1owner@list_directory/read_add_file/write_data/add_subdirectory/append_data/write_xattr/execute/write_attributes/write_acl
/write_owner:allow
2group@list_file/write_data/add_subdirectory/append_data:deny
3group@list_directory/read_data/execute:allow
4everyone@list_file/write_data/add_subdirectory/append_data/write_xattr/_attributes/acl/write_owner:deny
5everyone@list_directory/read_data/read_xattr/execute/read_attributes/_acl/synchronize:allow
```

This newly created directory seems to have a complex ACL, but in fact it's an ACL just the nine-bit mode shown on the first line of output translated into an ACL. It is not necessary for the filesystem to store an actual ACL because ACL and the mode are equivalent. (Such ACLs are termed "trivial") if the directory had an actual ACL, ls would show the bits + a on the end (i.e., drwxt-xr-x+) to indicate the presence of the ACL. (Wait, the text says "a-ACL", likely a typo for "an-ACL" or just "an ACL").

Each numbered clause represents one access entry. The format is:

```
index:entity:permissions:inheritance_flags:type
```

The index numbers are added by ls for clarity and are not part of the actual ACL. They can be used in later chmod to identify a specific ACE to be replaced or deleted.

The entity can be the keys owner@, group@, or everyone@, or a form such as user: username or group:groupname.

The type of an ACE is either allow or deny. Theoretically, alarm and audit are allowed as well, but ZFS does not implement these features.

Both the permissions and the inheritance_flags are slash-separated lists of options. Stringly, it is the inheritance_flags field (and one of the color delimiters) flags are all turned off, but it does not do with the permissions.

For added confusion, ls displays multiple names for the r (read data/list directory), w (write data add file), and p (append data/add subdirectory) permission bits, if they were separate permissions. In fact, they are file- and directory-specific interpretations of the same bits and will always be present or absent others.

## Interactions between ACLs and modes

These quirks, together with the entity field, make it tricky for scripts to parse ls -v output. If you need to process ACLs programmatically, look first for an existing library (such as the Solaris::ACL module from the Comprehensive Perl Archive Network (CPAN) that facilitates the process. As a last resort, you can use the output of ls -V (described next), this format is more amenable to parsing.

You can obtain a tabular display of ACL entries with ls -V. In this mode, permissions are represented by their one-letter codes as shown in Chapter 6.9 on. All possible bits are displayed for each access control entry; those that are turned off are represented by dashes (just as ls displays a traditional mode).

```
ls -dv /var/tmp/example
drwxr-xr-x 2 garth staff 21 Jan 07:19 /var/tmp/example
owner@--rwxp---A-W-Co----:deny
group@------w-p------allow
group@----------------------allow
everyone@--w-p---A-W-Co----:deny
everyone@--r-x---A-R-C-s-:allow
```

## Interactions between ACLs and modes

Several aspects of the translation of modes merit further discussion. First, note that the mode and ACL must remain consistent, or whenever you adjust one, the other updates to conform. ZFS does a good job of determining the appropriate ACL for a given mode, but its algorithm for generating and updating ACLs in response to mode changes is rudimentary. The results are functionally incorrect, but they are often verbose, unreadable, and unmaintainable. In particular, the system may generate multiple and seemingly inconsistent sets of entries for owner@, group@, and everyone@ that depend on evaluation order for their aggregate effect. As a general rule, never touch a file or directory's mode once you've applied an ACL. If worse comes to worst, remove the ACL with chmod A- and start over.

## Modifying NFSv4 ACLs in Solaris

Because ZFS enforces consistency between a file's mode and its ACL, all files have at least a trivial ACL (virtual or not). Ergo, ACL changes are always updated. You make ACL changes with chmod. The basic syntax is the same as:

```
chmod [-R] acl_operation file ...
```

Table 6.11 shows the various types of ACL operations understood by chmod. Unfortunately, there is no ACL analog of chmod's incremental, symbolic syntax for manipulating traditional modes. You cannot add or remove individual permissions from an ACE; you must replace the entire.

| Operation | Function |
| --- | --- |
| A-index- | Replaces the entire ACL with its trivial version from the mode |
| A-ace | Deletes a access control entry by position |
| Index=ace,[ace...] | Deletes a access control entry wherever it appears |
| A+ace | Adds one or more access control entries |
| Index+ace,[ace...] | Adds an access control entry to the top of the ACL |

```
solaris$ chmod A:user:Callow /var/tmp/example
```

gives the user ben to edit the ACL on the /var/tmp/example directory. Remember that access determination is an iterative process that works its down the ACL, so retains any rights he had under the previous version of the ACL. The new access control entry goes at the start of the ACL (at index 0), so the command

```
solaris$ chmod A0- /var/tmp/example
```

removes the ACE that was just added and reverts the ACL to its original state.
