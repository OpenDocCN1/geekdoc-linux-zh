During the development of the ADSP system, prior to RFC5617, a domain's ADSP TXT record was kept in a different subdomain (_domainkey.domain, with no_prefix) and had a slightly different syntax, O=- meant that the domain signed some of its email, and O== meant it signed all email.

# SSHFP resource records

SSH, the secure shell, allows secure logins over an insecure network. It uses two authentication schemes, for the host itself and for the user to log in. Unfortunately, users typically accept whatever key ssh presents to them without verifying it. DNS's SSHFP record lets ssh verify the host key automatically, ensuring that the user has reached the intended machine and not an impostor.

SSHFP records are specified in RFC4255 (2006).

# DNSSEC resource records

To keep packet sizes down, SSHFP records do not store a complete copy of a host's public keys. Instead, they store digests (i.e., cryptographic hashes) of those keys. Here is the syntax:

```
name [ttl] SSHFP algorithm# fingerprint_algorithm# fingerprint
```

The algorithm# identifies the public key cryptystem to generate the host's key. This algorithm is not actually used in the verification process; usually used by the remote host to be sure that both parties are talking about the same kind of key. RSA is algorithm 1 and DSA is algorithm 2.

The fingerprint is the hash to be matched, and the fingerprint_algorithm# tells how to process the public key presented by the remote host to produce a hash for comparison. Only one hashing algorithm (SHA-1) is defined, so the contents of this field are always 1.

Here's an example from RFC4255:

```
host.example. SSHFP 2 123456789abcdef6789123456789abcdef67890
```

SSH requires both RSA and DSS keys; they are usually stored in /etc/ssh with names like ssh_host_rsa_key and ssh_host_dsa_key.pub by the user's end, SSH accepts public keys in the .ssh/hosts file in the user's home directory.

You can grab the host keys from that directory to build your SSHFP resource records. Recent versions of ssh-keygen can generate the SSHFP DNS records with the -r and -g flags. There is also an sshfp daemon on Linux and available for UNIX (freesports.org/dns/sshfp) that converts the keys to fingerprints and produces the necessary DNS records.

You can ask OpenSSH to use SSHFP records by setting the VerifyKeyDNS option to yes. SSH supports authentication and verification methods, and since SSHFP records are not yet widely used, you shouldn't make them the only possible option. Try SSHFP first, and if that fails, back to prompting the user to confirm the key manually as was done before before SSHFP. See page 926 in Chapter 22, Security, for more information about configuring SSH.

Like SPF and DKIM records, the SSHFP system more or less assures that you are using DNSSEC and DNS records are trustworthy. That probably isn't true right now, but DNSSEC is gaining traction and will eventually see the light of day. See page 648 for your DNSSEC coverage.

# DNSSEC resource records

Six resource records are currently associated with DNSSEC. DSS, DLV, and DNSKEY are for storing various types of keys or fingerprints. RRRSIG contain the signatures of other records in the zone (record sets, really). Finally, NSEC and NSEC3 give DNS servers a way to prove nonexistent records, providing cryptographic security for negative answers to queries. These six records are different from most in that they are generated by software tools rather than being typed in hand.

DNSSEC is a big topic in its own right, so we discuss these records and their use in the DNSSEC section that begins on page 648.

# Glue records: links between zones

Each zone stands alone with its own set of data files, name servers, and clients. But zones need to be connected to form a parent hierarchy: booklab.atr.com is a part of at.com, and we need some kind of link.

Since DNS referrals occur only from the parent, the parent zone must know the subdomains. We need some kind of link between the parent and child of the zone. In DNS terms, the parent zone must know the IP addresses.

There are two ways the child can meet this requirement: by including the records directly, or by using stub zones.

With the first method, you simply include the NS records and the corresponding A records of name servers in the parent. For example, ns1.atr.com is a part of at.com, and we need some kind of link.

Since parent and child zones are run by different sites, updates can be a tedious manual task that requires coordination across administrative boundaries. A corollary is that in the real world, this type of configuration is out of date.

The scheme described is the standard way of connecting zones, but it requires the child to keep in touch with the parent and tell about any changes or additions.

The second way to maintain links is to use stub zones. A stub zone is essentially the same as a slave zone, but it includes only the NS records and the corresponding A records of name servers. Like a slave, a stub zone is automatically updated and eliminates the need for communication between the parent and child zones.

An important caveat is that stub zones must be configured identically on both the master and slave servers of the parent zone. It might be easiest to keep in touch manually with your parent domain and to verify its configuration a times a year (especially if it is local).

You can use the dig command to see of which your parent domain is currently advertising. First run

```
$ dig parent-domain
```

to determine the name servers for your parent domain. Pick one and then run

```
$ dig @name-server.parent-domain child-domain ns
```

to see your list of public name servers. One situation in which stub zones are very useful when your internal network uses RFC1918 private IP address space and you need to keep the RFC1918 delegations in sync.

# 17.9 The BIND software

BIND, the Berkeley Internet Name Domain system, is an open source package from ISC that implements the DNS protocol for Linux, UNIX, Mac OS, and Windows systems. There have been three main flavors of BIND: BIND 4, BIND 8, and BIND 9, with BIND 10 currently under development by ISC. We cover only BIND 9 in this book.
