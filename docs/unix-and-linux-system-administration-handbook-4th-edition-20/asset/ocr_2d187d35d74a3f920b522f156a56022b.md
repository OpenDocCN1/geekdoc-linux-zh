# Chapter 8 Storage

Since the LVM adds a layer of indirection between logical and physical blocks, it can freeze the logical state of a volume simply by making a copy of the mapping table. Therefore, logical volume managers often provide some kind of a "snapshot" feature. Writes to the volume are directed to new blocks, and the LVM keeps the old and new mapping tables. Of course, the LVM has to store both the original image and all modified blocks, so it can eventually run out of space if a snapshot is never deleted.

+   * A filesystem mediates between the raw bag of blocks presented by a partition, RAID array, logical volume or the standard filesystem faced by programs: paths such as /var/spool/mail, UNIX file types, UNIX permissions, etc. The filesystem determines where and how the contents of files are stored, how the namespace is represented and searched on disk, and how the system is made resistant to (or recoverable from) corruption.

Most space ends up as part of the filesystem, but swap space and database storage can potentially be more efficient without "help" from a filesystem. The kernel or device imposes its structure on the storage, rendering the filesystem unnecessary.

If it seems to you that this system has a few many components that implement one block storage device in terms of another, you are in good company. The trend over the last few years has been towards consolidating these components to increase efficiency and remove duplication. Logical volume managers did not originally function as RAID controllers, most have absorbed some RAID-like features (notably, striping and mirroring). Administrators are comfortable with logical volume management, partitions are disappearing, too.

On the cutting edge today are systems that combine a filesystem, RAID controller, and an LVM system all in one tightly integrated package. Sun's ZFS filesystem is the leading example, and the Btrfs development for Linux has similar design goals. We have more to say about ZFS on page 264.
