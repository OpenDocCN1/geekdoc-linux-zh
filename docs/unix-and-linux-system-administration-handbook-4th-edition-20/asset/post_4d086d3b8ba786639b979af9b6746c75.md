
# Chapter 21 Network Management and Debugging

You can use ping to check the status of individual hosts and to test segments of the network. Routing tables, physical networks, and gateways are all involved in processing a ping, so the network must be more or less working for ping to succeed. If ping doesn't work, you are pretty sure that no more sophisticated will work either.

However, this rule does not apply to networks that block ICMP requests with a firewall. Make sure that a firewall isn't interfering with your debugging before you conclude that the target host is ignoring ping. You might consider disabling a medlesome firewall for a short period of time to facilitate debugging.

If your network is in bad shape, chances are that DNS is not working. Simplify the situation by using numeric IP addresses when ping, and use ping -n option to prevent ping from attempting to reverse lookups on IP addresses—lookups also trigger DNS requests.

Be aware of the firewall issue if you're using ping to check your connectivity. Some well-known sites answer ping packets and others. We've found google.com to be a consistent responder.

Most versions of ping run in an infinite loop unless you supply a packet count argument. Under Solaris, ping -s provides the extended output that other versions use by default. Once you have filled of ping, type the interrupt character (usually <Control-C>) to get out.

Here's an example:

```
linux$ ping beast
PING (10.0.1.46): 56 bytes of data.
64 bytes from beast (10.0.1.46): icmp_seq=0 ttl=54 time=48.3ms
64 bytes from beast (10.0.1.46): icmp_seq=1 ttl=54 time=46.4ms
64 bytes from beast (10.0.1.46): icmp_seq=2 ttl=54 time=88.7ms
^\^
-- ping statistics *
3 packets transmitted, 3 received, 0% packet loss, time 2026ms
rtt/avg/max/dev = 46.490/61.202/88.731/19.481 ms
```

The output shows the host's IP address, the ICMP sequence number of each response packet, and the round trip travel time. The most obvious thing that the output above tells you that the server beast is alive and connected to the network.

The ICMP sequence number is a particularly valuable piece of information. Continuities in the sequence indicate dropped packets. They're normally accompanied by a message for each missing packet.

Despite the fact that IP does not guarantee the delivery of packets, a healthy network should drop very few of them. Lost-packet problems are important to be masked by higher-level protocols. The network may appear to function correctly, but it will be slower than it ought to be, not only ping: check to see if a host is alive because of the retransmitted packets also because of the protocol overhead needed to detect and manage them.

To track the cause of disappearing packets, first run traceroute (see the next section) to discover the route that packets are taking to the target. Then ping the intermediate gateways in sequence to discover which link is dropping packets. To pin down the problem, you need to send a fair number of packets. The fault generally lies on the link between the last gateway you can ping without loss of packets and the gateway beyond.

The round trip time reported by ping gives you insight into the overall performance of a path through a network. Moderate variations in round trip time not usually indicate problems. Packets may occasionally be delayed by tens or hundreds of milliseconds for no reason; that's just how IP works. You should expect to see a fairly consistent round trip time for the majority of packets, with occasional lapses. Many of today's routers implement rate-limited or lower-priority responses to ICMP packets, which means that a router may delay responding to your ping if it is dealing with a lot of traffic.

The ping program can send echo packets of any size, so by using a packet larger than the MTU of the network (1,500 bytes for Ethernet), you can force fragmentation. This practice helps you identify errors or low-level issues such as problems with a congested network or VPN.

On Linux systems, you specify the desired packet size in bytes with the -s flag.

```
$ ping -s 1500 cuinfo.edu
```

Under Solaris, HP-UX, and AIX, you simply add the desired packet size to the end of the ping command.

```
$ ping cuinfo.edu 1500
```

Note that even a simple command ping can have dramatic effects. In 1998, the so-called Ping of Death attack crashed large numbers of Unix and Windows systems. It was launched simply by transmission of an overly large packet. When the fragmented packet was reassembled, it filled the receiver's memory buffer and crashed the machine. The Ping of Death issue has since been fixed, but other caveats should be kept in mind regarding ping.

First, it is hard to distinguish the failure of a network from the failure of a server with only the ping command. In an environment where ping tests normally, a failed ping just tells you that something is wrong.

Second, a successful ping does not guarantee much about the target machine's state. Echo request packets are handled within the IP protocol stack and do not require a server to be running on the probed host. A response guarantees only that the machine is powered on and has not experienced a kernel panic. You'll need higher-level methods to verify the availability of individual services such as HTTP and DNS.

## 21.3 SMOKEPING: GATHERING STATISTICS OVER TIME

As mentioned earlier, even a healthy network occasionally drops a packet. On the other hand, networks should not drop packets regularly, even at a low rate, because the impact on users can be disproportionately severe. Because high-level protocols often function in the presence of packet loss, you might never notice dropped packets unless you're actively monitoring for them.

For this purpose, you may want to check SmokePing, an open source tool by Tobias Oetiker that tracks of network latencies. SmokePing sends ping packets to a target host at regular intervals. It shows the history of each monitor linked through a web front and can send alerts when goes amiss. You can get a copy from smoketier.com/smokeping.

Exhibit A a SmokePing graph. The vertical axis is the round trip of pings, and the horizontal axis is time (weeks). The black line from which the gray spikes up indicates the median round trip time; the spikes themselves are the transit times of individual packets. Since the gray in this graph appears only below the median line, the great majority of packets must be traveling at close to the median speed, with just a few being delayed. ## 21.4 TRACOUTE: TRACE IP PACKETS

traceroute, originally written by Van Jacobson, uncovers the sequence of gateways through which an IP packet travels to reach its destination. All modern operating systems come with some version of traceroute. The syntax is simply

```
traceroute hostname
```

There are a variety of options, most of which are not important in daily use. As usual, the hostname can be specified as either a DNS name or an IP address. The output is simply list of hosts, starting with the first gateway and ending at the destination. For example, a traceroute from our host to host nubark produces the following:

```
$ traceroute nubark
traceroute to nubark (172.16.8.254) 30 hops max, 38 byte packets
1 lab-gw (172.16.8.254) 0.840 ms 0.693 ms
2 dmz-gw (192.168.1.254) 4.642 ms 4.582 ms 4.674 ms
3 nubark (192.168.1.210) 7.999 ms 5.949 ms 5.908 ms
```

From this output we can tell that jaguar is three hops away from nubark, and we can see which gateways are involved in the connection. The round time for each gateway is also shown—three samples for each hop. A typical traceroute between Internet hosts often includes more than 15 hops, even if the two sites are just across town.

traceroute works by setting the time-to-live field (TTL, "hop count to live") of an outbound packet to an artificially low number. Packets arrive at a gateway, their TTL is decreased. When a gateway decreases the TTL to 0, it discard the packet and sends an ICMP "time exceeded" message back to the origin host.

The first traceroute packets have their TTL set to 1. The first gateway to see such a packet (lab-gw in this case) determines that the TTL has been exceeded and notifies of the dropped packet by sending back an ICMP message. The sender's IP address in the header of the packet identifies the gateway, and traceroute looks up this address in DNS to find the gateway's hostname.

To identify the second-hop gateway, traceroute sends out a round of packets with TTL fields set to 2. The first gateway routes the packets and decreases their TTL by 1. At the second gateway, the packets are dropped and ICMP error messages are generated as before. The TTL is equal to the number of hops to the destination host and the packets reach their destination successfully.
