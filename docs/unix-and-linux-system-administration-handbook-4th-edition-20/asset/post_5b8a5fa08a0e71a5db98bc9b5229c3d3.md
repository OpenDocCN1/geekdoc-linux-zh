
# Installing a printer driver from the command line

As you may have guessed already, some of these steps are hard to replicate without Windows, especially the setting printer defaults. But if you want to set up hundreds of printers on a Samba server, you may want to try to do it from the command line all the time. Command-line configuration works particularly well for PostScript printers because the Windows PostScript printer driver works correctly without default configuration information.

If you made a note of the files required by a particular driver, you can install the driver from the command line. First, copy the files required to the [print]$ share:

```
$ cd ~/mydriver
$ smclient -U printdam //samba-server/print$ -c "mput *"
```

Next, assign the driver to a particular printer. Let's assume you have a simple Post-Script printer with a custom PPD file:

```
$ rpclient -U printdam -c "\"
addriver\"Windows NT x86\"Our Custom PS:\nPSCRIPT.DLL:CUSTOM.PPD:PSSUI.DLL:PSCRIPT.HLP:NULL:NULL:PSCRIPT.NTF""\nsamba-server
```

The backslashes at the ends of lines allow the command to be split onto multiple lines for clarity; you can omit these and enter the command on one line if you prefer. The backslashes before double quotes distinguish the nested sets of quotes.

The long string in the example above contains the information listed in the property of the printer driver that is seen when the printer driver is being installed from Windows:

- Long printer name
- Driver filename
- Data filename
- Configuration filename
- Help filename
- Language monitor name (set this to NULL if you have none)
- Default data type (set this to NULL if there is none)
- Comma-separated list of additional files

To configure a printer to use one of the uploaded drivers,

```
$ rpclient -U printdam -c "\"Our Custom PS\"" samba-server
```

# 30.8 DEBUGGING SAMBA

Samba usually runs without requiring much attention. However, if you have a problem, you can consult two primary sources of debugging information: the log files for each client and the smbstatus command. Make sure you have appropriate log settings in your configuration file.

```
[global]
: %m causes a separate file to be written for each client.
log file = /var/log/samba.log.%m
max size = 1000
: How much info to log. You can also specify log levels for components
; of the system (here, 3 generally, level 10 for authentication).
log level = 3 auth:10
```

Higher log levels produce more information. Logging takes time, so don't ask for much detail unless you are debugging. Operation can be slowed considerably.

The following example shows the logs generated by an unsuccessful content followed by a successful one.

The smbdcontrol is handy for altering the debug level on a running Samba server without altering the smb.conf. For example,

```
$ sudo smbdcontrol debug "4 auth:10"
```

The example above set the global debug level to 4 and the debug level for authentication-related matters to 10. The smbd argument specifies that all smb daemons on the system will have their debug sets. To debug a specific established connection, you can use the smbstatus command to figure out which smb daemon handles the connection and passes its PID to smbd debug just one connection. At log levels over 100 you will start to see (encrypted) passwords in the logs.

smbstatus shows currently active connections and locked files. This information is especially useful when you are tracking down locking problems (e.g., "Which user has file xyz open read/write exclusive?"). The first section of output lists resources that a user has connected to. The last section lists any file locks.

# 30.9 ACTIVE DIRECTORY AUTHENTICATION

The Windows desktops on your network most likely use Microsoft's Active Directory system for authentication, directory services, and other network services. Active Directory (AD) collects users, groups, computers, and operating systems under a single umbrella, centralizing and simplifying system administration. It is also one of the primary reasons why Windows has gained a permanent foothold in many enterprises. UNIX has assembled some of the pieces of this puzzle, but none of the UNIX solutions are polished or as widely implemented as Active Directory.

# Getting ready for Active Directory integration

See page 908 for more information about PAM. Ever devised, the Samba project folks have made great strides toward providing Active Directory support for UNIX and Linux environments. With the help of Samba, Linux systems can join an Active Directory domain and allow access to the system by accounts defined in AD that have no entries in the /etc/passwd file. Linux UIDs are derived from their analogue Windows users, known as security identifiers or SIDs. By leveraging PAM, a home directory can automatically created for a user who does already have one. The integration system even the passwd command to change a user's AD password. All of this Windows integration magic is handled by a component of Samba called winbind.

Active Directory embeds and extends several standard protocols, notably LDAP and Kerberos. In an attempt to achieve IT management nirvana, Microsoft has unfortunately synchronized with the original protocols, creating a toxic web of proprietary RPC dependencies.

See page 739 for more information about the name switch.

To emulate that an Active Directory client, winbind hooks into PAM, SSS, and Kerberos. It connects authentication and system information requests to the appropriate Microsoft-specific formats. From the standpoint of UNIX, Active Directory is another source of LDAP directory information and Kerberos authentication data.

You must complete the following configuration chores before your Linux system enters Active Directory paradise:

- Install Samba with support for Active Directory and identity conversion.
- Configure the name service switch, nswitch.conf, to use winbind as a source of user, group, and password information.
- Configure PAM to authentication requests through winbind.
- Configure Active Directory as a Kerberos realm.

See Chapter 17 for more information about DNS.

Samba is included by default on most Linux distributions, but some distributions do not include the identity mapping services needed for a full AD client implementation. Those components can be fitted to set up correctly if you're compiling from source code, so we recommend installing binary packages if they're available for your distribution.
