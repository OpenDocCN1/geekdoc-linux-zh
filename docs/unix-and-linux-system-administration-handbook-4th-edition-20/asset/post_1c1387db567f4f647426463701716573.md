
# DNSSEC 651

Even DNS0-aware servers, the MTU over the path between two servers may be smaller than a big fat packet stuffed with keys. If the packet is too large, it should in theory be fragmented at the IP layer, but problems remain. Some implementations of TCP/IP fragment TCP packets not UDP packets. Some firewalls do not have saved state to properly reassemble UDP packets. And finally, firewalls drop UDP packets to port 53 that are larger than 512 bytes. Oops. When a UDP response is mutilated to or fails to get through, the client then switches to TCP, which causes performance problems of its own.

A few issues:

- RSA refuses to use the RSA algorithm, and RSA is currently the only algorithm that DNSSEC-aware names are required to implement. Russia has standardized on an algorithm called GOST, a symmetric cipher, which is similar in design to DES.
- China (among other countries) has its own root, .com, and net servers, fracturing the DNS naming tree. How will DNSSEC work with a fractured root?
- RFC5011, a proposed standard for automated updates of DNSSEC anchors, inflates the key overhead by adding keys to DNSKEY record sets. This extension would exacerbate the MTU problem mentioned above and seems to be a bad idea. There are also situations in which of the RFC5011 scheme would leave a site's keys in a revoked state even though cached data might require those keys for verification.
- Linux distributions ship with a list of keys to get you started. This seems like a bad idea since the keys will inevitably become out of date and wrong. Your DNS will slowly degrade unless you really know why. Key lists themselves are not necessarily a bad idea. For example, you can use lists from RIPE and IANA web sites to cross-check keys you obtain through DNS until the root and TLDs are signed.
- Maybe need a well-known hostname (analogous to www for web servers) that can sign their public keys while we wait for the top of the DNS tree to be signed—key.domain-name, or something like that.

Sysadmins need to start thinking about signing their domains and setting up a shiny new server or two. We recommend that you deploy DNSSEC at this point, but stage carefully on a test network before you plan to deploy it on production networks.

GOST is secure (as far as we know) and has a much shorter key length than other algorithms. It is a symmetric cipher and not a public key system, it can replace TSIG but cannot be used for DNS-SEC. Proposals to allow GOST are winding their way through the IETF standardization process.

DNSSEC deployment can be done in two independent steps:

- Sign your zones and serve signed data to DNSSEC-aware clients.
- Validate the answers to your users queries.

Check out UCLA's handy SecSpider tool at scspider.ucla.edu. It probes DNSSEC setup from several locations around the globe to verify that your keys are available and large packets containing them can reach locations. (It was in fact SecSpider that first discovered the MTU issue with DNSSEC.) SecSpider also identifies DNS misconfigurations, and it may help a grad student trying to gather enough data to write his thesis. You can also obtain copies of the public keys for other signed zones from the SecSpider web site (secspider.ucla.edu/trust-anchors.com).

The DNS-OARC (DNS Operations, Analysis, and Research Center) has implemented a reply-size test that you can query with **dig** to find out how large a UDP reply packet can transit between your server and your:

```
$ dig +short rs.dns-oarc.net txt
rst1014.rs.dns-oarc.net
rst1022.x1014.rs.dns-oarc.net
st1382.x1014.rs.dns-oarc.net
"63.83.113 DNS reply size limit is at least 1382 bytes"
"63.23.113 sent EDNS buffer size 4096"
```

This example tells you that DNS replies of size 1,382 can get through, but not much larger, even though you are advertising a buffer size of 4,096. In this case, the problem is likely that the firewall is not admitting UDP fragments.

Common sizes are 486, indicating a server that does not support EDNS0 and limits UDP packets to 512 bytes, and 4,023, which indicates that the 4,096-byte buffer size can be used. If you use the @server argument to **dig**, you will see the packet size limitations from the DNS-OARC machine to server. For more information, see dns-oarc.net/oarc/servicesylistizer.

If you are to implement DNSSEC and either SecSpider or DNS-OARC indicates a problem with packet sizes, it might be time to talk to your firewall folks and try to get things fixed before you deploy.

# DNSSEC policy

Before you begin deployment of DNSSEC, there are few policies and procedures that you should nail down or at least think about. For example:

- What size will you use? Longer keys are more secure, but they may make for larger packets.
- How often will you change keys in the absence of a security incident?
- How will you distribute your public keys? How will sites that need yours verify that they are authentic?

# DNSSEC resource records

We suggest that you keep a key log that records the date you generated each key, the hardware and operating system used, the version of the key generator, the algorithm used, the key length, and signature validity period. If a cryptographic algorithm is later compromised, you can check your log to see if you are vulnerable.

# DNSSEC resource records

DNSSEC uses resource record types that were referenced in the DNS database on page 590 but were not described in detail: DS, DNSV, DNSKEY, RRSIG, and NSEC. We describe them in general and outline the steps involved in signing a zone.

The DS (Designated Signature) record appears only in the parent zone and indicates whether a subsection is signed. It identifies the key used by child to sign its own resource set. The DS record includes a key identifier (five-digit number), a cryptographic algorithm, digest type, and digest of the public key allowed.

If your parent is not signed, you can establish a trust anchor by using a DNSV (domain validation) record with the same format. Here are examples of each:

```
example.com.
IN DS 682 5 12898DCF72AD0BCE597...
example.com.
IN DNSV 682 5 12898DCF72AD0BCE597...
```

The question of how to change existing keys in the parent and child zones has been a thorny one that seems cooperation and communication between parent and child. The creation of the DS record, the use of separate key-signing and zone-signing keys, and the use of multiple pairs have helped this problem.

Keys in DNSKEY resource record can be key-signing keys (KSKs) or zone-signing keys (ZKSs). A new flag, called SEP (secure point), distinguishes between them. Bit of the flags is set to 1 for KSKs and 0 for ZKSs. This convention marks flags of KSKs and ZKSs as decimal numbers 257 and 256, respectively. Multiple keys generated and signed so that a smooth transition from one key to the next is possible. The child may change its zone-signing keys without notifying the parent; it must only coordinate with the parent if it changes keys. As keys roll over, both the old key and the new key are valid for a certain interval. When cached values on the Internet have expired, the old key can be retired. In this section, base-64-encoded hashes and keys have been truncated to save space and illustrate the structure of the records.

An RRSIG record is the signature of a resource record set (that is, the set of all records of the same type and name within a zone). RRSIG records are generated by zone-signing software and added to the signed version of the zone file.

An RRSIG record contains a wealth of information:

- The type of record set being signed
- The signature algorithm used, encoded as a small integer
- The number of labels (dot-separated pieces) in the name field
- The TTL of the record set that was signed
- The time it expires (as yyyymddhhhhsss)
- The time the record was signed (also yyyymddhhhhsss)
- A key identifier (a 5-digit number)
- The signer's name (domain name)
- And finally, the digital signature itself (base-64 encoded)

Here's an example:

```
RRSIG NS 5 257600 200909182841 200908020128241 23301 example.com.
MMK76wa7VtbjjuGUQNuNVIEWHau4p...==
```

NSEC and NSEC records are produced as a zone. Rather than signing records, they certify the intervals between record sets and so allow for a signed answer of "no such domain" or "no such record set". For example, a server might respond to records named bark.trust.com with an NSEC record that certifies the nonexistence of any A records between bark.trust.com and borlia.trust.com.

Unfortunately, the inclusion of the endpoint names in NSEC records allows one to walk through the zone and obtain all of its valid names. NSEC3 fixes this feature by including hashes of the endpoint names rather than the endpoint names themselves, but it is more expensive to compute: more security, less performance. NSEC and NSEC3 are both in current use, and you can choose between when you generate your keys and sign zones.

Protecting against a zone walk is critically important for your site, recommend you use NSEC for now. Only recent versions of BIND (9.6 and later) and NSEC (3.1 and later) understand NSEC3 records.
