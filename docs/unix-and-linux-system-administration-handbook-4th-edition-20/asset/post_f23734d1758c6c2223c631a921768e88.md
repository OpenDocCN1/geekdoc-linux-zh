The Bacula director is the daemon that coordinates backup, restore, and verification operations. You can submit backup or restore jobs to the Bacula console. You can also ask the director daemon to query the Bacula storage daemon or the file daemons located on client computers.

You communicate with the director daemon through the Bacula console, which can run as a GNOME or MS Windows GUI or as a command-line tool. The console can run anywhere; it doesn't have to be located on the same computer as the director daemon.

A storage daemon is the Bacula component that reads and writes tapes or other backup media. This service must run on the machine that is connected to the tape or storage device used for backups, but it does not have to be installed on the same server as the director (although it can be).

A Bacula file daemon runs on each system that is to be backed up. File daemon implementations for each supported operating system send the appropriate data and attributes to the storage daemon as backup jobs are executed.

# Chapter 10 Backups

The final Bacula component is the catalog, the relational database in which Bacula stores information about every file and volume that is backed up. The catalog makes Bacula fast and efficient during a restore because the entire backup history is available-online; Bacula knows what storage volumes need to restore a particular file before it reads a single tape. Bacula currently supports three different databases: MySQL, PostgreSQL, and SQLite. The catalog database does not need to reside on the same server as the director.

An additional, optional component is the Bacula Rescue CD-ROM. This component is a separately downloadable package that creates individualized, bootable rescue CDs for Linux systems to use for “bare metal” recovery. The CDs contain a statically linked copy of the system's file daemon as well as customized scripts that configure information about the system's disks, kernel, and network interfaces. If a Linux system has a catastrophic failure, use its rescue CD to boot the fresh system, partition the disk, and connect to the Bacula director to perform a full system restore over the network.

# Setting up Bacula

Because of Bacula's complexity, advanced feature set, and modular design, there are many ways to use a site-wide backup scheme. In this section we walk through a basic Bacula configuration.

In general, six steps get Bacula up and running:

- Install a supported third-party database and the Bacula daemons.
- Configure the Bacula daemons.
- Install and configure the client file daemon.
- Start the Bacula daemons.
- Add media to media pools with the Bacula console.
- Perform a test backup and restore.

A minimal setup consists of a single backup server machine and one more clients. The clients run only a file daemon. The remaining four Bacula components (director daemon, storage daemon, catalog, and console) all run on the server. In larger environments it's advisable to distribute the server-side Bacula components among several machines, but the minimal setup works great for backing up to a few dozen systems.

# Installing the database and Bacula daemons

It's important to run the (major) version of Bacula on every system. In the past, some major releases have been incompatible with one another.

Before you install Bacula, you must first install the back-end database for your catalog. For sites backing up just a few systems, SQLite provides the easiest installation. If you are backing up more systems, it's advisable to use a more scalable database. Our experience with MySQL in this role has been positive, and we- assume MySQL in the following examples.

# Configuring Bacula daemons

Stability and reliability are a must when you are dealing with a backup platform, so once you have installed the database, we recommend that you download and install the latest stable source code from the Bacula web site. Step-by-step installation documentation is included with the source code in the docs directory. The documentation is also on-line at bacula.org, where it is available in both HTML and PDF format. Helpful tutorials and developer guides can also be found.

After unpacking the source code, run ./config--with-mysql followed by make to compile the binaries, and, finally, run make to complete the installation.

Once Bacula has been installed, the next step is to create the actual MySQL database and the data tables inside. Bacula includes three scripts that prepare MySQL to store the catalog. The grant_mysql_privileges script sets up the appropriate MySQL permissions for the Bacula daemon. The create_mysql_database script creates the Bacula database, and, finally, the make_mysql_tables script populates the database with the required tables. Analogous scripts are included for PostgreSQL and SQLite. Bacula prebuilt database creation scripts are included in the src/cats directory of the Bacula source distribution.

Bacula saves a table entry for every file backed up from every client, the database server should have plenty of memory and disk space. Database tables for a medium-sized network can easily grow to millions of entries. For MySQL, you should properly dedicate the resources in my-cnf. If you eventually find that your catalog has to become unmanageable, you can always set up a second instance of MySQL and use catalogs for different groups.

# Configuring Bacula daemons

After setting up the database, you must configure the other four Bacula components. By default, all configuration files are located in /etc/bacula. Bacula has a separate configuration file for each component. Table 10.3 lists the files and the machines on which configuration is needed.

| Component | File | Which machines |
|---|---|---|
| Director daemon | bacula-dir.conf | The server that runs director |
| Storage daemon | bacula-sd.conf | Every server with storage device |
| File daemon | bacula-fd.conf | Every client that is backed up |
| Management console | bconsole.conf | Every machine used as console |

It might seem silly that you have to configure each independently when you have a single server, but this modular design allows Bacula to scale incredibly well. Tape backup to off-site location? Install storage daemon on a server. Need to back up new clients? Install and configure the clients' file daemons. New backup administrator? Install the management console on his or her workstation.

The configuration files are human-readable text files. The sample configuration files included in the distribution are well documented and are a great starting point for a typical configuration.

Before we begin a more detailed discussion of our example set, first define some key Bacula terms:

- Jobs are the fundamental unit of Bacula activity. They come in two flavors: backup and restore. A job comprises a client, a fileset, storage pool, and a schedule.
- Pools are groups of physical media that store jobs. For example, you might use two pools, one for full backups and another for incrementals.
- Filesets are lists of systems and individual files. Files can be explicitly included or excluded from backup or restore.
- Messages are inter-daemon communiqués (log entries, really) regarding the status of daemons and jobs. Messages can also be sent by email and written to log files.

We do not cover all the possible configuration parameters in this chapter. Instead, we begin each section with a general overview and then point out some parameters that are either particularly useful or hard to grasp.

# Common configuration sections

The Bacula configuration files are composed of sections known generically as “resources.” Each resource is enclosed in curly braces. Some resources appear in multiple configuration files. Comments are introduced with a # sign in all Bacula configuration files.

All four files contain a Director resource:

```
# Sample Bacula director configuration file, /etc/bacula-dir.conf
```

```
Director {
  Name = bull-dir # a canonical name for our Bacula
  DIRPort = 9101
  Query File = "/etc/bacula/query.sql"
  Working Directory = "/var/Bacula/working"
  Pid Directory = "/var/run"
  Maximum Concurrent Jobs = 1
  Password = "zHpScUnHN9"
  Messages = Standard
}
```
