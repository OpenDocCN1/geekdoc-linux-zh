# UID (user ID number)

The UID identifies the user to the system. Login names are provided for the convenience of users, but software and the filesystem use UID internally. UIDs are usually unsigned 32-bit integers.

By definition, root has UID 0. Most systems also define pseudo-users such as bin and daemon to be the owners of commands or configuration files. It's customary to put fake logins at the beginning of the /etc/passwd file and give them low UIDs and a fake shell (e.g., /bin/fail) to prevent anyone from logging in as those users. We allow plenty of room for nonhuman users who might want to add in the future. (The desired range for new UIDs can be specified in the configuration files we use useradd.)

Another special UID is of the pseudo-user “nobody”; it is usually assigned a high value as -1 or -2, which unsigned UIDs in the UID field are the highest and next-possible UIDs. The “nobody” login is used when the root user on one machine tries to access files that are NFS-mounted from another machine that does not trust the first machine.

It's a good idea to have multiple accounts with UID 0. While it might seem convenient to have multiple root logins with different shells or passwords, setup just creates more potential security holes and gives you multiple logins to secure. If people need to alternate ways to log in as root, you are better off if they use a program as sudo.

Do not recycle UIDs, even when users leave your organization and delete their accounts. This precaution prevents confusion if files are restored from backups, where users may be identified by UID rather than login name.

UIDs should be kept unique across your entire organization. That is, a particular UID should refer to the same login name and the same person on every machine that person is authorized to use. Failure to maintain distinct UIDs in security problems with systems such as NFS and can also result in confusion when a user moves from one workgroup to another.
