
## Mail queues

sendmail uses two queues: /var/spool/mqueue when acting as an MTA on port 25, and /var/spool/clientmqueue when acting as an MSA on port 587. All messages make at least a brief stop in the queue before being sent on their way.

A queued message is saved in pieces in several different files. A filename has a two-letter prefix that identifies the queue, followed by a random ID built from sendmail's process ID. Table 20.7 shows the six possible pieces.

### Table 20.7 Prefixes for files in the mail queue

| Prefix | File contents |
| --- | --- |
| qf | The message header and content file |
| df | The body of the message |
| tf | A temporary version of the qf file is being updated |
| Tf | Signifies that 32 or more failed locking attempts have occurred |
| Qf | Signifies that the message bounced and could not be returned |
| xf | Temporary transcript file of errors from mailers |

Subdirectories qf, df, or xf exist in a queue directory, then those pieces of the message are put in the proper subdirectory. The qf file contains not only the header but also the envelope addresses, the date at which the message should be returned as undeliverable, the message's priority in the queue, and the reason the message is in the queue. Each line begins with a single-letter code that identifies the rest of the line.

Each message that is queued must have a qf and df file. All the other prefixes are used by sendmail during delivery. When a machine crashes and reboots, the startup sequence for sendmail should delete the tf, xf, and Tf files from each queue. The sysadmin responsible for mail should check occasionally for Qf files in local configuration that is causing the bounces. At one glance of the queue directories lets you spot problems before they become disasters.

The mail queue opens several opportunities for things to go wrong. For example, the filesystem can fill up (putting /var/spool/mqueue and /var/log on the same partition), the queue can become clogged, or orphaned mail messages can get stuck in the queue. sendmail has configuration options to help with performance on very busy machines; we have collected these in the performance section starting on page 802.

## 20.9 SENDMAIL CONFIGURATION

sendmail's actions are controlled by a single configuration file, typically called /etc/mail/sendmail.cf for a sendmail running as an MTA or /etc/mail/submit.cf.

- 1. sendmail can use multiple queues beneath mqueue to increase performance; see page 802.

### The sendmail configuration pieces

for a sendmail acting as an MSA. the flags with which sendmail is started determine which config file uses: -bm, -bs, and -bt use submit.cf if it exists, and all other modes use sendmail.cf. You can change these names with command-line flags or config options, but it is best not to.

The raw config file format was designed to easily parse by machines, not humans. The m4 source (.mc) file from which the cf file is generated is an improvement, but its tricky and rigid syntax isn't going to win any awards for friendliness, either. Fortunately, many of the paradigms you might have already been hammered out by others with similar needs and are supplied in the distribution by prepackaged features.

sendmail configuration involves several steps:

- Deciding the role of the machine you are configuring: client, server, Internet-facing mail receiver, etc.

- Choosing the features needed to implement that role and building an .mc file for the configuration

- Compiling the .mc file with m4 to produce a .cf config file

We cover the features commonly used for site-wide, Internet-facing servers and for little desktop clients. For more detailed coverage, we refer you to two pieces of documentation on the care and feeding of sendmail: The O'Reilly sendmail by Bryan Costales et al and the cf/README from the distribution.

### The m4 preprocessor

m4 originally intended as a front end for programming languages, lets users write more readable (or perhaps more cryptic) programs. m4 is powerful enough to use in many input transformation situations, and it works nicely for sendmail configuration files.

m4 macros have the form:

```
name(arg1, arg2, ..., argn)
```

There cannot be any space between the name and the opening parenthesis. Left and right single quotes designate strings as arguments. m4's quotes are weird, since the left and right quotes are different characters. Quotes nest, so that m4 has some built-in macros, and users can also define their own. Table 20.8 on the next page lists the most common built-in macros that are used in sendmail configuration.

### A configuration file built from a sample mlc

Before we dive into the details of the various macros, features, and options you might use in sendmail configuration, let's put the cart before the horse and a “no frills” configuration to illustrate the general process. Our example is for a leaf node, myhost.example.com; the master configuration file is called myhost.mlc. Here’s the complete mlc file:

```
divert(-1)
#### basic .mlc file for example
divert(0)
VERSIONID($id$)
OSTYPE(local)
MAILER(local)
MAILER(smtp)
```

Except for the diversions and commands, each line invokes a packaged macro. The first four lines are boilerplate; they insert comments in the compiled file to note the version of sendmail, the directory the configuration was built in. The OSTYPE macro includes the ..ostype/linux.m4. The MAILER lines allow for local delivery (to users with accounts myhost.example.com) and for delivery to Internet sites.

To build the real configuration file, just run the Build command you copied over to the new cf directory:

```
$Build myhost.cf
```

Finally, installing myhost.cf in the right spot—normally /etc/mail/sendmail.cf, but some vendors prefer hiding places. Favor vendor hiding places as /etc and /usr/lib.

At a larger size, you may want to create a separate m4 file for host site-wide defaults; put individual hosts can then include the contents of this file by using the DOMAIN macro. Not every host needs a separate config file, but each group of similar hosts (same architecture and same role: server, client, etc.) will probably need its own configuration. The order of the macros in the .mc file is not arbitrary. It should be

```
VERSIONID
OSTYPE
DOMAIN
FEATURE
local macro definitions
MAILER
```
