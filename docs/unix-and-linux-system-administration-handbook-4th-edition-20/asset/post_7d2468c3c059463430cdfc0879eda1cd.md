## 31.10 STTY: SET TERMINAL OPTIONS

tty lets you directly change and query the various settings of the terminal driver. There are about a zillion options, but most can be safely ignored. stty generally uses the same names for driver options as the termios man page does, but occasional discrepancies pop up.

A good combination of options to use for a plain-vanilla terminal is:

```
solaris$ stty intr ^C U erase ^H -tabs
```

Here, -tabs prevents the terminal driver from taking advantage of the terminal's built-in tabulation mechanism, a useful practice because emulators are not very smart about tabs. The other options set interrupt, kill, erase characters to <Control-C>, <Control-U>, and <Control-H> (backspace), respectively.

You can use stty to examine the modes of the terminal driver as well as to set it. stty with no arguments produces output like this:

```
solaris$ stty
3840 baud
erase = ^H; col = M-?; eol = M-?; swtch = <undef>;
ixany
tab3
```

For a more verbose output use stty -a - the option:

```
solaris$ -a
3840 baud; rows 24; columns 80;
intr = ^C; quit = ^Q; erase = ^H; kill = ^U; echo = ^D; equal = M-?; eol2 = M-?
swtch = <undef>; start = ^Q; stop = ^S; size = ^Z; dsup = ^Y; rprnt = ^R;
erase = ^W; inext = ^V; flush = ^;
nparenb -parord sd8 huccl -octop cread -clocal crtsct
jnbrnk -ijnpar -parmark - inpck -istrip -ioctl icnl - ixoff -nixcl iamaxld
opost -ocurl -ocnl onlcr -onorc -refill -ofdel nl0 cr0 tab3 bs0 vto
isig isacan iext iecho echo echok -nonflish -xcase -topocht -echopt
echoctl echo
```

The format of the output is similar but lists more information. The meaning of the output should be intuitively obvious if you've written a terminal driver recently.

stty operates on the file descriptor of its standard input, you can set and query the modes of a terminal other than the current one by using the shell's input redirection (<). You must be the superuser to change the modes on some-one terminal.

## 31.11 TSET: SET OPTIONS AUTOMATICALLY

tset initializes the terminal driver to a mode appropriate for a given terminal type. The type can be specified on the command line; if the type is omitted, tset uses the value of the TERM environment variable.

### Terminal unwedging

tset supports a syntax for mapping certain values of the TERM environment into other values. This feature is useful if you often log through a modem or data switch and would like to have the terminal driver configured correctly for the terminal you are really using on the other end of the connection rather than something generic and unhelpful such as "dialup."

For example, suppose that you use xterm at home and the system you are dialing in is configured to think that the terminal type of a modem is "dialup."

Putting the command

```
tset -m dialup:xterm
```

in your login or .profile file sets the terminal driver appropriately for xterm whenever you dial in.

Unfortunately, the tset command is not really as simple as it pretends to be. To have tset adjust your environment variables in addition to your terminal modes, you need lines like this:

```
set noglob
eval tset -Q -m dialup:xterm
unset noglob
```

This incantation suppresses the messages that tset normally prints (the -Q flag), and asks that shell commands to set the environment output instead (the -s flag). The shell commands produced by tset are captured by the backticks and fed to the shell as input with the built-in command eval, causing the commands to have the same effect as if they had used by the user.

set noglob prevents from expanding any metacharacters as * and ? that are included in tset's output. This command is not needed by sh/ksh users (nor is the unset noglob to undo it), since shells do not normally expand special characters within backquotes. The tset command itself is the same no matter what use; tset looks at the environment variable SHELL to do whatever of commands to print.

## 31.12 TERMINAL UNWEDGING

Some programs (e.g., vi) make drastic changes to the state of the terminal driver while they are running. This melding is normally invisible to the user, since the terminal state is restored when the program exits or suspended. However, a program can crash or be killed without performing this housekeeping step. When this happens, the terminal may behave very strangely; it might handle newlines correctly, to echo typed characters, or to execute commands properly.

Another way to confuse a terminal is to accidentally run cat or more on a binary file. Most binaries contain a mix of 8-bit characters that is guaranteed to send of the less-robust emulators into outer space.

To fix this situation, use reset or getty sane. reset is actually just a link to tset in many systems, and it can accept most of tset’s arguments. It is usually run without arguments. Both reset and getty sane restore the default state of the terminal driver and send out an appropriate code from termcap/terminfo if one is available.

In many cases for which a reset is appropriate, the terminal has been left in mode with no processing is done on the characters you type. Most terminals gen returns rather than newlines when the Return or Enter key is pressed. Without input processing, this generates <Control-M> characters-stead sending off the current command to be executed. For enter newlines direct, use <Control-J> or the line feed key (if there is one) instead of Return.

## 31.13 DEBUGGING A SERIAL LINE

Debugging serial line is not difficult. Here are some typical errors:

- Forgetting to init to reread its configuration files
- Forgetting to set soft carrier when using three-wire cables
- Using a cable with the wrong nullness
- Soldering or crimping connectors upside down
- Connecting to the wrong wire because bad or nonexistent wire maps
- Setting the terminal options (including speed) incorrectly

A breakout box is an indispensable tool for debugging serial cabling problems. It is patched into the serial line and shows the signals on each pin as they pass.

## 31.14 CONNECTING TO SERIAL CONSOLES

Perhaps the most common and useful application of RS-232 today is to connect the device. The device could be anything from network switch to an embedded Linux system.

### Connecting to serial consoles

The basic steps for connecting to console are as follows:

- Attach a cable between the serial port on your system and the device you want to talk to. You will most likely need a null cable.
- Install or identify the terminal communication software you will use on your system. Decades ago, the standard command for this was cu or tip. You can still use these in a pinch, but modern-day alternatives such as minicom and picocom are.
- Configure your communication software to open the correct device file (see the discussion earlier in chapter). Usually, names like /dev/ttya, /dev/tty1, /dev/ttyS0, or /dev/S0 are good first guesses.
- Set the baud rate, stop bits, and flow control to match the defaults used on the target device. These parameters are usually outlined in the manual for, but you can also try possible combinations. If you don't know the correct baud rate, an "old dog" trick is to connect and type a few characters. If you have to type multiple characters to get a single character of garbage, you've set the baud rate too high. If typing one or two characters produces many characters of garbage, you've set the baud rate low.
- Once you've successfully connected, you should be able to enter commands on the remote console. If you find that the device suddenly hangs on long output, you have probably misconfigured the flow control; typing <Control-Q> will sometimes get you by.

If you have trouble connecting, the first debugging step should be to remove the crossover in the cable, or to add one if you didn't start with one. Don't forget that you're connecting to a remote UNIX box, you'll need to set up a getty to listen for your connection and present a login prompt.
