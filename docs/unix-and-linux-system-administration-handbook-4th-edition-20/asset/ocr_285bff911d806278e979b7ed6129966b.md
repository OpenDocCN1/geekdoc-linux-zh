# Property inheritance

Many properties are naturally inherited by child filesystems. For example, if we wanted to mount the root of the demo pool in /opt/demo instead of /demo, we could simply set the mountpoint parameter:

```
solaris$ zfs set mountpoint=/opt/demo demo
solaris$ zfs list -d
NAME USED AVA REFER MOUNTPOINT
demo 1.00G 48G 21K /opt/demo
demo/new_fs /19K 1024M 19K /opt/demo/new_fs
solaris$ ls /opt/demo
new_fs
```

Setting the mountpoint parameter automatically remounts the filesystems, and the mount point change child filesystems in a predictable and straightforward-way. The usual rules regarding filesystem activity still apply, however; see page 143.

Use zfs get to see the effective value of a particular property; zfs get dumps them all. The SOURCE column tells you why each property has its particular value: local means the property was explicitly, and a dash means the property is read-only. If the property value is inherited from an ancestor filesys-tem, SOURCE shows the details of that inheritance as:

```
solaris$ zfs get all demo/new_fs
solaris$ zfs get all demo
NAME PROPERTY VALUE SOURCE
demo/new_fs type filesystem
demo/new_fs creation Wed Mar 17 17:50 2010
demo/new_fs available 1024M
demo/new_fs referenced 19K
demo/new_fs compressratio 1.0x
demo/new_fs mounted yes
demo/new_fs quota 1G local
demo/new_fs reservation 1G local
demo/new_fs mountpoint /opt/demo/new_fs inherited from demo
<many more, about 40 in all>
```

Vigilant readers notice that the available and referenced properties look suspiciously similar to the AVAIL and REFER columns shown by zfs list. In fact, zfs list is just a different way of displaying filesystem properties. If we included the full output of our zfs get command above, there would have a used prop-erty in there, too. You can specify the properties you want zfs list to show with the -o option.
