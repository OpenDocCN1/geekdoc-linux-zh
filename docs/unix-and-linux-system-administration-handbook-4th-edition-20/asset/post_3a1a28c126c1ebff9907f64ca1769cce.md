
# Solaris basic network configuration

mode("default"). Run svcadm to switch the configuration. For example, the following example shows the system being taken from NWAM to traditional mode.

```bash
solaris$ svcs svc:network/physical
STATE STIME FMRI
disabled Mar_31 svc/network/physical:default
online Mar_31 svc/network/physical:nnam
solaris$ sudo svcadm disable svc/network/physical
solaris$ sudo svcadm enable svc/network/physical
```

Solaris configures the IP address of each network interface through a file called /etc/hostname.interface, where each is the usual name of the interface or an IP address. The value in a hostname.interface file is used as the address parameter to ifconfig, so it's safe to use an address, even though configuration implies that a hostname is expected.

Any special ifconfig options can be put in the hostname.interface file on the same line as the hostname or IP address; is is all one ifconfig command line. The startup script tries to discover the IP addresses of all interfaces without responding hostname files by DHCP.

As shipped, the Solaris startup file relies on using the ifconfig options netmask + and broadcast +. The means to look in etc/netmasks for the netmask value and to figure out the broadcast address value from it. The /etc/netmasks lists network numbers and their corresponding netmask values. Any network that is subnetted differently from its inherent class (A, B, or C) must be represented in the file. Here is an example of a netmasks:

```
# CS Department network masks database
# Network netmask
#
=======
128.138.0.0 255.255.255.192 # default for dept.
#
128.138.192.64 255.255.255.192 # drag
128.138.192.192 255.255.255.192 # csops
128.138.193.0 255.255.255.224 # bcrg
128.138.193.32 255.255.255.224 # database
128.138.198.0 255.255.255.0 # slip
```

The first line sets a default of /26 for the class B address 128.138.0.0, which is then overridden with specific masks that vary from the default. All networks are listed, even though many use the default value and could in fact be left out. On the systems from which this example is taken, the netmasks file is centrally maintained and distributed to all hosts. No single host has interfaces on all these networks.

Solaris network interfaces must be scoped with ifconfig plumb to make them accessible. You might have to run this command by hand when performing manual configuration.

# Chapter 14 TCP/IP Networking

In older versions of Solaris, the network startup scripts were files in /etc/init.d (chiefly rootusr, ininitit, sysid.net, and inetsvc). Solaris 10 radically restructured the way that startup files and system services are managed. The scripts have been refactored and now use in /lib/svc/method. See page 97 for an overview of Solaris's Service Management.

If /etc/defaultrouter exists, it is assumed to contain the identity (which can again be a hostname or a numeric address) of the default gateway, and no further routing configuration is performed. As usual, a numeric address is preferable; using a name requires an /etc/hosts entry or a DNS server on the local network.

Solaris used to run routed (which is called routed) whenever no default gateway was specified, but in Solaris 10 and later you may enable routed explicitly with svcadm enable routing/route. Use the svcmd route to determine the service's current state.

Beware: routed will go into server (talkative) mode automatically if the machine has more than one network interface or the file /etc/gateways exists. This is generally not what you want. You can prevent routed from squawking by turning on the "quiet mode" flag:

```bash
solaris# svconfig -s routing/route:default setprop routing/quiet_mode = true
```

# Solaris configuration examples

Here are some examples of the commands needed to bring a Solaris interface and add a route to a default gateway:

```bash
solaris$ sudo ifconfig e1000g0
solaris$ sudo ifconfig e1000g0 192.108.21.48 mask 255.255.255.0 up
solaris$ sudo route add 192.108.21.254
```

The following examples show how to see the status of network interfaces and routing tables. Commands prefaced with sudo must be run as root. The final example shows a feature of the Solaris route command that is not present on our other architectures: the get argument shows the next hop to a particular destination. We have taken liberties to make them fit on the page:

```bash
solaris$ ifconfig -a
io0:flags=UP,LOOPBACK,RUNNING,MULTICAST,IPv4,VIRTUAL>
mtu 832 index 1 127.0.0.1 mask ff000000
e1000g0:flags=1000843-UP,BROADCAST,RUNNING,MULTICAST,IPv4> mtu 1500
index 2 inet 192.108.21.48 mask fxffffff broadcast 192.108.21.255
```

```bash
solaris$ ifconfig e1000g0
e1000g0:flags=1000843-UP,BROADCAST,RUNNING,MULTICAST,IPv4> mtu 1500
index 2 inet 192.108.21.48 mask fxffffff broadcast 192.108.21.255
ether 0:14:4f:e6:1c
```

Notice that when run as root, ifconfig shows the hardware address, but when run as a user, it does not.

# Solaris DHCP configuration

```bash
solaris$ netstat -nr
Routing Table: IPv4
Destination Gateway Flags Ref Use Interface
default 192.108.21.254 UG 1 9959
192.108.21.0 192.108.21.48 U 1 4985 e1000g0
127.0.0.1 127.0.0.1 UH 1 107 lo
```

```bash
solaris$ sudo route get google.com
route to: gw-in-f100.google.com
destination: default
mask: default
gateway: 192.108.21.254
interface: e1000g0
flags: <U,GATEWAY,DONE,STATIC>
recpipe sendpipe sthresh rtt,ms rttvar,ms hopcount mtu expire
0 0 0 0 0 1500 0
```

Solaris' ndd command reconfigures the TCP/IP stack on a running system. Perhaps "reconfigure" is too strong a word; each module exposes parameters that can be examined and in some cases adjusted. The basic syntax is

+   ndd [-set] device ? | variable

If you give the argument ? (which must be protected from the shell as \?), ndd returns a list of variables understood by the driver for the specified device. If you supply the name of a variable, ndd returns the value of that variable. If you use the -set flag and a value, the specified variable is set to the value you specify.

Unfortunately, the ndd man page does not tell you the possible names of devices, and it does not tell you that you must be run ndd on some devices (ip and hme, for example) and not on others (tcp and udp). Table 14.10 slips you a quick cheat sheet.

Table 14.10 Devices you can probe with Solaris's ndd command

| Device | Description | Variable names |
| :--- | :--- | :--- |
| /dev/tcp | TCP protocol variables | tcp_* |
| /dev/udp | UDP protocol variables | udp_* |
| /dev/ip | IP protocol variables | ip_* and ip6_* |
| /dev/icmp | ICMP protocol variables | icmp_* |
| /dev/rawip | Identical to /dev/icmp | icmp_* |
| /dev/arp | ARP protocol variables | arp_* |

Interface-specific variable names in the /dev/ip category control IP forwarding on specific network interfaces. For example, e1000g0:ip_forwarding controls IP forwarding on /dev/e1000g0, too.
