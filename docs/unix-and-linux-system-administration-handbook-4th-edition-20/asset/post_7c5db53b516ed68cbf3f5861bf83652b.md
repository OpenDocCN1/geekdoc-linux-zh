Second, HUP signals are sometimes generated by the terminal driver in an attempt to "clean up" (i.e., kill) the processes attached to a particular terminal. This behavior is largely a holdover from the days of wired terminals and modem connections, hence the name "hangup".

Shells in the C shell family (tcsh et al.) usually make background processes immune to HUP signals so that they can continue to run after the user logs out. Users of Bourne-ish shells (ksh, bash, etc.) can emulate this behavior with the nohup command.

- * QUIT is similar to TERM, except that it defaults to producing a core dump if not. A few programs cannibalize this signal and interpret it to mean something else.

The signals USR1 and USR2 have no set meaning. They're available for programs to use in whatever they'd like. For example, the Apache web server interprets the USR1 signal as a request to gracefully restart.

## 5.4 KILL: SEND SIGNALS

As its name implies, the kill command is most used to terminate a process. kill can send any signal, but by default it sends a TERM. kill can be used by normal users on their own processes or by root on any process. The syntax is

```
kill [-signal] pid
```

where signal is the number or symbolic name of the signal to be sent (as shown in Table 5.1) and pid is the process identification number of the target process.

A kill without a signal does not guarantee that the process will die, but the TERM signal can be caught, blocked, or ignored. The command

```
kill -9 pid
```

"guarantees" that the process will die because signal 9, kill cannot be. Use kill -9 only if a polite request fails. We put quotes around "guarantees" processes can occasionally become so when KILL does not affect them (usually because of some degenerate I/O var lock waiting for a disk that has stopped spinning). Rebooting is usually the only way to get rid of these processes.

The command performs wildly different functions on UNIX and Linux. Under Linux, kill kills processes by name. For example, the following kills all apache server processes:

```bash
ubuntu$ killall httpd
```

The standard UNIX kill command that ships with Solaris, HP-UX, and AIX takes no arguments and simply kills all the current user's processes. Running it as root kills init and shuts down the machine. Oops.

The pgrep and pkill commands for Solaris, HP-UX, and Linux (but AIX) search for processes by name (or other attributes, such as EUID) and display or signal, respectively. For example, the following command sends a TERM signal to all processes as the user ben:


## 5.5 PROCESS STATES

A process is not automatically eligible to receive CPU time just because it exists. You need to be aware of the four execution states listed in Table 5.2.

### Table 5.2 Process states

| State | Meaning |
| --- | --- |
| Runnable | The process can be executed. |
| Sleeping | The process is waiting for some resource. |
| Zombie | The process is trying to die. |
| Stopped | The process is suspended (not allowed to execute). |

A runnable process is ready to execute whenever CPU time is available. It has acquired all the resources it needs and is waiting for CPU time to process its data. As the process makes a call that cannot be immediately completed (such as a request to read a file), the kernel puts it to sleep.

Sleeping processes are waiting for a specific event to occur. Interactive shells and system daemons spend most of their time sleeping, waiting for terminal input or network connections. Since a sleeping process is effectively blocked until its request has been satisfied, it will get no CPU time unless it receives a signal or response to one of its I/O requests.

Some operations process enter an uninterruptible state. This state is usually transient and not observed in ps output (indicated by a D in the STAT column; see Table 5.4 on page 132). However, a few situations can cause it to persist. The most common involves server problems on a filesystem mounted with the "hard" option. Since processes in the uninterruptible sleep state cannot be roused to service a signal, they cannot be killed. To get rid of them, you must fix the underlying process or reboot.

Zombies are processes that have finished execution but have not yet had their status collected. If you see zombies around, check their PPIDs with ps to find out where they are.

Stopped processes are administratively forbidden to run. Processes are stopped on receipt of STOP signal and are restarted with CONT. Being stopped is similar to sleeping, but there's no way for a process to get out of the stopped state than having some other process wake it up.

## NICE AND RENICE: SCHEDULING PRIORITY

The "niceness" of a process is a numeric hint to the kernel about its priority in relation to other processes contending for the CPU. The strange name is derived from the fact that it determines how nice you are. A high value means a low priority for your process; a negative value means high priority: you are not very nice.

The range of allowable niceness varies among systems. The most common range is -20 to +19. Some systems use a range beginning at 0 (typically 0 to 39). The ranges used on example systems are shown in Table 5.3.

Despite their numeric differences, all systems handle nice values in the same way. Unless the user takes special action, a newly created process inherits the nice value of its parent. The owner of the process can increase its nice value but cannot lower it, returning the process to the default. This restriction prevents processes with low priority from bearing high-priority children. The superuser may set nice values arbitrarily.

It's rare to have to set these days. In the 1970s and 80s, performance was significantly affected by which process was on the CPU. Today, with more CPU power, the scheduler does a good job of servicing all processes. The addition of scheduling classes gives developers additional control when response is essential. I/O performance has not kept up with increasingly fast CPUs, and most nice-nice processes can still monopolize the kernel's management of its memory or I/O: disproportionate share of these resources.

A process nice value can be set at the time of creation with the nice command and adjusted with the renice command. nice takes a command line as an argument, and renice takes a PID or (sometimes) a username. Examples:

```bash
$ nice -5 task      // Lowers priority (nice) by 5
$ sudo renice -5 pid // Sets nice value to -5
$ sudo renice 5 user // Sets nice value of user to 5
```

Unfortunately, there is little agreement among systems about how the desired priorities should be specified; in fact, even nice and renice from the same system usually don't agree. Some commands want a nice value increment, others want an absolute nice value preceded by a dash. Others want a flag (-n), and some just a value. To complicate things, a version of nice is built into the C shell and some other shells (but not bash). If you don't type the full path to nice, you'll get the shell's version rather than the operating system's. This duplication can be confusing because shell-nice and command-nice use different syntax: the shell wants its priority increment expressed as +incr or -incr, but the stand-alone command wants a flag followed by the priority increment.

Table 5.3 summarizes all these variations. A prio is an absolute value, while an incr is relative to the niceness of the shell from which nice or renice is run. When an incr or a prio is called for, you can use a double dash to enter negative values (e.g., --10). Only the shell nice understands plus signs (in fact, it requires them); leave them out in all other circumstances.

### Table 5.3 How to express processes versions of niceness and renice

| System | Range | bash nice | csh nice | renice |
| --- | --- | --- | --- | --- |
| Linux | -20 to 19 | -incr or -incr | +incr or -incr | prio |
| Solaris | 0 to 39 | -incr or incr | +incr or -incr | incr or -n incr |
| HP-UX | 0 to 39 | -prio or -prio | +incr or -incr | -prio |
| AIX | -20 to 19 | -incr or - incr | +incr or -incr | -n incr |

* a. Uses absolute priority, adds 20 to the value you specify.

The most commonly niced in the modern world is ntpd, the clock synchronization daemon. Since once is critical to its mission, it usually runs at a nice value about 12 below the default (that is, at a higher priority than normal).

If a problem drives the system's load average to 65, you may need to use nice to start a high-priority process before you can run commands to investigate the problem. Otherwise, you may have difficulty running even simple commands.

## 5.7 PS: MONITOR PROCESSES

ps is the system administrator's main tool for monitoring processes. While versions of ps differ in their arguments and display, they deliver essentially the same information. Part of the enormous variation among versions of ps can be traced back to differences in the development history of UNIX. ps is also a command that vendors need to customize for other reasons. It is closely tied to the kernel's handling of processes, so it reflects all of a vendor's underlying kernel changes.

ps can show the PID, UID, priority, and control terminal of processes. It also gives information about how much memory a process is using, how much CPU time it has consumed, and its current status (running, stopped, sleeping, zombies). zombies show up in a ps listing as <exiting> or <defunct>.
