# 4.4 PSEUDO-USERS OTHER THAN ROOT

Root is the only user that has special status in the eyes of the kernel, but
several other pseudo-users are defined by the system. You can identify these sham
accounts by their UIDs, usually less than 100. Most often, UIDs under 10 are
system accounts, and UIDs between 10 and 100 are pseudo-users associated with
species of software.

It’s customary to replace the encrypted password field of these users in
/etc/shadow with a star so that their accounts cannot be logged in. Set their
shells to /bin/fail or /bin/nologin as, to protect against remote login exploits that use password alternatives such as SSH keys.

Files and processes that are part of the operating system that may not be
wowned by root are sometimes given to the users bin or daemon. The theory was
that this convention would avoid the security hazards associated with ownership by ship. It is not a very compelling argument, however, and current systems often just use the root account for this purpose.

On some systems, the user owns a number of special files such as the kernel’s
memory image in /dev. Programs access these files, but those that do run
setuid to sys rather than root if this ownership is in use. On some systems,
group called kmem or sys is used instead of a user account.

See 697 for more information about the nobody account.

The Network File System (NFS) uses the nobody account to represent root on
other systems. For remote roots to be stripped of their powers, the remote
UID 0 has to be mapped to something other than the local UID 0. In NFv4, it can
apply remote users with no local account as well.

Since the nobody account is supposed to represent a generic and relatively powerful-user, it shouldn’t own any files. If nobody owns files, remote roots will be able to take control of them. Nobody shouldn’t own now files!

A UID of -1 or -2 is traditional for nobody. The Linux kernel defaults to
UID 65,534, the 16-bit twos-complement version of -2. But really, the number is
Arbitrary: Root has 99, which makes more sense than 65,534 now that we have
32-bit UIDs. Solaris uses 60,001, which doesn’t, but at least it is easy to remember
t the 16-bit twos-complement version of -2, truncated—not rounded—one
significant digit, plus one.

The only snag with nobody’s UID is that exportfs does not seem to pay
tention to the passwd file. You must explicitly tell it with the anonuid option to
 a different UID for nobody.
