The /etc/initab files tell what to do at each run level. Its format varies from system to system, but the basic idea is that initab defines commands that are to be run (kept running) when the system enters each level.

As the machine boots, init ratches its way up from run level 0 to the default run level, which is also set in /etc/initab. To accomplish the transition between each pair of adjacent run levels, init runs the actions spelled out for that transition in /etc/initab. The same progression is made in reverse order when the machine is shut down.

The telinit command changes init's run level is the system. For example, telinit 3 goes to run level 3. telinit's most useful argument is -q, which causes init to reread the /etc/initab file. Unfortunately, the semantics of the initab file are freely crude, and they do not mesh with the way that services are actually started and stopped on UNIX systems. To manage the facilities of the initab file into something bit usable, init implements another layer of abstraction. This layer usually takes the form of a “change run levels” command that in turn executes scripts from a run-level-dependent directory to bring the system to its new state.

This second layer is well developed in AIX. Indeed, AIX systems rely heavily on the initab file itself to manage services. AIX's startup scripts are also different from those of other systems. These days, most Linux distributions boot to level 5 by default, which may be appropriate for systems that need to run a window server. The default run level 5 is easy to change. In the following discussion, we mostly ignore the initab file and the glue that attaches init to the execution of startup scripts. Just keep in mind that when we say init runs such-a script, the connection may not be so direct.

# Overview of startup scripts

The master copies of the startup scripts live in the /etc/init.d directory. Each script is responsible for one daemon or one particular aspect of the system. The scripts understand start and stop to mean that the service should be initialized or halted, which is typically the same as restart. As a system administrator, you can manually start and stop individual services by running their associated init.d scripts. For example, here’s a simple startup script that can start, stop, or restart sshd:

```bash
#!/bin/sh
test -f /usr/sbin/sshd || exit 0
case "$1" in
  start)
    echo -n "Starting sshd: sshd"
    /usr/sbin/sshd
    echo ""
    ;;
  stop)
    echo -n "Stopping sshd: sshd"
    kill /var/run/sshd.pid
    echo ""
    ;;
  restart)
    echo -n "Stopping sshd: sshd"
    kill /var/run/sshd.pid
    echo ""
    echo -n "Starting sshd: sshd"
    /usr/sbin/sshd
    echo ""
    ;;
  *)
    echo "Usage: /etc/init.d/sshd start|stop|restart"
    exit 1
    ;;
esac
```

Although the scripts in /etc/init.d can start and stop individual services, the master script needs additional information about which scripts (and with what arguments) to enter any given level. Instead of looking directly at init.d directory when it takes the system to a new level, the master script looks at level.d directories (e.g., rc0.d, rc1.d, ...). The level.d directories contain symbolic links which point back to the scripts in init.d directory. The names of the links start with S or K and the sequence number controls the order of services. When init transitions from a lower run level to a higher one, it runs all the scripts starting with S in ascending numerical order with the argument. When init transitions from a higher run level to a lower one, it runs all the scripts starting with K (for "kill") in descending numerical order with the argument. This scheme gives administrators fine-grained control of the order in which services are started. For example, it doesn’t make sense to start sshd before the network interfaces are up. Although the network and sshd are both configured to start at run level 3 in Red Hat, the network script is sequence number 10 and the sshd script has sequence number 5, so network is certain to run first. To tell the system when to start a daemon, you must place symbolic links into the appropriate directory. For example, to start cups (the printing daemon) at run level 2 and to stop nicely before shutting down, the following pair of links would suffice:

```
# In -s /etc/init.d/cups /etc/rc2.d/S80
# In -s /etc/init.d/cups /etc/rc0.d/K80
```

The first line tells the system to run the /etc/init.d/cups startup script as one of the last things to do when entering level 2 and to run it with the start argument. The second line tells the system to run /etc/init.d/cups relatively soon when shutting down the system and to run it with the stop argument. Some systems treat shutdown and reboot differently, so we should probably put a symbolic link in the /etc/rc6.d directory as well to make sure the daemon shuts properly when the system is rebooted.

# Red Hat startup scripts

Startup scripts are one of the areas in which Linux distributions are most distinguished from each other. Red Hat uses a primary init-script-based approach, with a few twists just to make life difficult for everyone.

At each run level, init invokes /etc/rc.d/rc with the new run level as an argument. /etc/rc.d/rc usually runs in 'normal' mode, in which it runs scripts, but it can also run in 'confirmation' mode, where it prompts you for confirmation before running each individual startup script.

Startup scripts store lock files in the /var/lock/subsys directory. The presence of a lock file with the same name as a startup script indicates that service should already be running. Startup scripts create lock files when you give a start command and remove them when performing a stop.

Red Hat has a chconfig command to help you manage services. This adds or removes startup scripts from the system, manages the run levels at which they operate, and lists the run levels for which a script is configured. See the man page for usage information for this simple and handy tool.

Red Hat also has an /etc/rc.d/rc.local (not directory) that runs at boot. The last run script as part of the startup process and is a good place to add specific tweaks and post-boot tasks.

Once you see the “Welcome to Red Hat Enterprise Linux” message during the boot process, you can press the 'i' key to enter confirmation mode. # SUSE startup scripts

SUSE's startup system resembles that of Red Hat, at least in terms of its general organization. However, SUSE's scripts are well organized, robust, and well documented.

As in Red Hat, init invokes /etc/init.d/rc at each run level and provides the new run level as an argument. Package-specific scripts live in the /etc/init.d directory, and their configuration files live in /etc/sysconfig. An excellent introduction to the SUSE startup process can be found in /etc/init.d/README.

Both SUSE and Red Hat concentrate their boot configuration files in /etc/sysconfig, the specific files within this directory are quite different. For one SUSE's files are generally well commented. You invoke options by setting shell environment variables, and these variables are then referenced by the scripts within /etc/init.d. Some subsystems require more configuration than others, and those that need multiple files have private subdirectories, such as the sysconfig/network directory.
