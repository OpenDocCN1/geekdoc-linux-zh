## LDAP querying

To administer LDAP, you need to be able to see and manipulate the contents of
the database. the phpLDAPAdmin tool mentioned earlier is one of the nicer free
tools for this purpose because it gives you an intuitive point-and-click interface.
phpLDAPAdmin isn't an option, ldapsearch (distributed with both OpenLDAP
and 389 Directory Server) is an analogous command-line tool that produces-
out in LDAP format. ldapsearch is especially useful for writing scripts and for
debugging environments in Active Directory is acting as the LDAP server.

The following example query uses ldapsearch to look up information
for every user cn starts with "ned". In this case, there's only one result.
The meanings of the various flags are discussed below.

```
ldapsearch -h atlantic.com -p 389
x -xD "cn=tren,cn=users,dc=boulder,dc=atrust,dc=com" -W
-b "CN=users,DC=boulder,DC=atrust,DC=com" "cn=ned*"
```

## LDAP and security

lastLoginTimestamp: 12908695248943974

ldapsearch -h and -p flags specify the host and port of the LDAP server you want to query, respectively.

You usually need to authenticate yourself to the LDAP server. In this case, the -x flag requests simple authentication (as opposed to SASL). The -D flag identifies the distinguished name of a user account that has the privileges needed to execute the query, and the -W flag allows ldapsearch prompt you for the password.

The -b flag tells ldapsearch where in the LDAP hierarchy to search. The parameter is known as the baseDN; by default, ldapsearch returns all entries below the baseDN; you can change this behavior with the -s flag.

The last argument is "filter," which is a description of what you're searching. It doesn't require an option flag. This filter, cn=ned*, returns all LDAP entries that have a common name that starts with “ned”. The filter is quoted to protect the search from shell globbing.

If you want to extract all entries below a given baseDN, just use objectClass=* as the search filter—or leave the filter out, since that is the default.

Any arguments that follow the filter select specific attributes to return. For example, if you added givenName to the command line, ldapsearch will return only those attributes of matching entries.

## LDAP and security

Traditionally, LDAP was used more in the manner of a phone directory than anything else, and it was usually acceptable. As a result, the “standard” LDAP implementation grants unencrypted access through TCP port 389. However we strongly advise against the use of unencrypted LDAP for the transmission of authentication information, even if passwords are individually hashed or encrypted.

As an alternative, LDAP-over-SSL (known as LDAPS, usually running on TCP port 686) is available in most situations (including the Microsoft world) on both the client and server. This access method is preferred because it protects the information contained in both the query and the response. Use LDAP when possible.

A system as complex as LDAP inevitably has the potential to be misconfigured in a way that weakens security. Of course it is likely to contain some old-fashioned security holes, too. Caveat administrator.

## 19.4 NIS: THE NETWORK INFORMATION SERVICE

NIS, released by Sun in the 1980s, was the first "prime time" administrative data-base. It was originally called the Sun Yellow Pages, but eventually had to be renamed for legal reasons. NIS commands still begin with the letters yp, so it's hard to forget the original name. NIS was widely adopted among UNIX vendors and is supported by every Linux distribution.

These days, NIS is an old grey mare. NIS should not be used for new deployments. We say this primarily because of the inevitable need to integrate with Windows systems, but also because of NIS's various security shortcomings.

## The NIS model

The unit of NIS is the record, not the file. A record corresponds to a line in a flat file. The master server maintains the copies of the maps. When you modify a file on the master, the Makefile in the NIS directory ensures that all maps are rebuilt. The makedbm command generates the maps from flat files. On HP-UX systems, a command called ypmake is used instead of make.

## Understanding NIS works

The ypsfr command copies maps from the master server to the slave servers. ypsfr is a pull command; it must be run on each slave to ensure they have the most recent maps. Slaves usually execute it every so often; you use cron to control how often.

ypush is a "push" command that's used on the master server. It actually does not transfer any data but rather instructs each slave to execute a ypsfr.

The special map called ypsvers does not correspond to any flat file. This map contains a list of all the servers of the domain. It is automatically constructed when domain is set up.

After initialization, the only active components of the NIS system are the ypserv and ybind daemon. ypserv runs only on servers (both master and save); it accepts queries from clients and answers them by looking up information in the hashed map files.

ybind runs on every machine in the NIS domain, including servers. The C library contacts the local ybind daemon when it needs to answer an administrative query (provided that /etc/nswitch.conf says to do so). ybind locates a ypserv in the appropriate domain and returns its identity to the C library, which contacts the server directly.
