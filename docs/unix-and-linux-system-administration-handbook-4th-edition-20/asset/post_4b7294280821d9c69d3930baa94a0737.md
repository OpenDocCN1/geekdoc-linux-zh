# Pipes and redirection

Every process has at least three communication channels available to it: "standard input" (STDIN), "standard output" (STDOUT), and "standard error" (STDERR). The kernel sets up channels on the process's behalf, the process itself doesn't necessarily know where they lead. They might connect to a terminal window, a file, a network connection, or a channel belonging to another process, to a few possibilities.

The shell interprets the symbols < , and >> as instructions to reroute a command's input or output to a file. A < symbol connects the command's STDIN to the contents of an existing file. The > and >> symbols redirect STDOUT; replaces the file's existing contents, and >> appends to them. For example, the command

```
$ echo "This is a test message." > /tmp/mymessage
```

stores a line in the file /tmp/mymessage, creating the file if necessary. The command below emails the contents of that file to user johndoe.

```
$ mail -s "Mail test" johndoe < /tmp/mymessage
```

To redirect both STDOUT and STDERR to the same place, use the && symbol. To redirect STDERR only, only 2.

The find command illustrates how you might want to handle STDOUT and STDERR separately because it tends to produce output on both channels, especially when running as an unprivileged user. For example, a command as

```
$ find / -name core
```

usually results in so many "permission denied" error messages that get lost in the clutter. To discard all the error messages, you can use

```
$ find / -name core 2 /dev/null
```

In this version, only real matches (where the user has read permission on the parent directory) come to the terminal window. To save the list of matching paths to a file,

```
$ find / -name core > /tmp/corefiles 2> /dev/null
```

This command sends matching paths to /tmp/corefiles, discards errors, and sends nothing to the terminal window.

To connect the STDOUT of one command to the STDIN of another, use the | symbol, commonly known as a pipe. Some examples:

```
$ ps -ef | grep httpd
$ cut -d: -f7 < /etc/passwd | sort -u
```

The first example runs ps to generate a list of processes and pipes it through the grep command to select lines that contain the word httpd. The output of grep is not redirected, the matching lines come to the terminal window.

The cut command in the second example picks the path to each user's shell from /etc/passwd. The list of shells is then sent through sort -u to produce a sorted list of unique values.

To execute a second command only if its precursor completes successfully, you can separate the commands with &&. For example,

```
$ lpr /tmp/t2 && rm /tmp/t2
```

removes /tmp/t2 only if it is successfully queued for printing. Here, the success of the lpr command is defined as an exit code of zero, the use of a symbol that suggests "logical AND" for this purpose may be confusing if you're used to short-circuit evaluation in other programming languages. Don't think about it much; just accept it as a shell idiom.

Conversely, the || executes the following command only if the preceding command fails (produces a nonzero exit status)

In a script, you can use a backslash to break a command into multiple lines, help distinguishing the error-handling code from the rest of the command pipeline:

```
$ cp --preserve --recursive /etc/* /sparse/backup \
$ echo "Did NOT make backup"
```

For the converse effect—multiple commands combined into one line—you use a semicolon as a statement separator.

# Variables and quoting

Variable names are unmarked in assignments but prefixed with a dollar sign when their values are referenced. For example:

```
$ etcdir='/etc'
$ echo $etcdir
/etc
```

# Common filter commands

Do not put spaces around the = symbol or the shell will mistake your variable name for a command name.

When referencing a variable, you can surround it with curly braces to clarify to the parser and to human readers that the variable name stops and other text begins; for example, $(etdir) instead of $etdir The braces are not normally required, but they can be useful when you want to expand variables inside double-quoted strings. Often, you'll want the contents of a variable to be followed by literal letters or punctuation. For example,

```
$ echo "Saved$8th version of mdadm.conf"
Saved 8th version of mdadm.conf.
```

There's no standard convention for the naming of shell variables, but all-caps names typically suggest environment variables or variables read from global configuration files. More often than not, local variables are read as lowercase with components separated by underscores. Variable names are case sensitive.

Environment variables are automatically imported into $bash's variable namespace, which you can set and read with the standard syntax. export varname to promote a shell variable to an environment variable. Commands for environment variables that you set at login time should be included in ~/.profile or ~/.bash_profile file. Other environment variables, such as PWD for the current working directory, are maintained automatically by the shell.

The shell treats strings enclosed in single and double quotes similarly, except double-quoted strings are subject to globbing (the expansion of filename-metacters such as * and ?) and variable expansion. For example:

```
$ mylang="Pennsylvania Dutch"
$ echo "I speak ${mylang}"
i speak Pennsylvania Dutch.
$ echo 'I speak ${mylang}'
I speak $(mylang).
```

Back quotes, also known as back-ticks, are treated similarly to double quotes, but they have the additional effect of executing the contents of the string as a command and replacing the string with the command's output. For example,

```
$ echo "There are wc -l /etc/passwd lines in the passwd file."
There are 28 lines in the passwd file.
```

sort: sort lines
sort sorts its input lines. Simple, right? Well, maybe not—there are a few subtleties regarding the exact parts of each line that are sorted (the "keys") and the collation order to be imposed. Table 2.1 shows a few of the more common options, but check the man page for others.

# Table 2.1 sort options

| Opt | Meaning |
|------|
| -b | Ignore leading whitespace |
| -f | Case insensitive sorting |
| -k | Specify the columns that form the sort key |
| -n | Compare fields as integer numbers |
| -r | Reverse sort order |
| -t | Set field separator (the default is whitespace) |
| -u | Output unique records only |

The commands below illustrate the difference between numeric and dictionary sorting, which is the default. Both commands use the -t: and -k3,3 options to sort the /etc/group file by its third colon-separated field, the group ID. The first sorts numerically and the second alphabetically.

```
$ sort -t: -k3,3 -n /etc/group
root:x:0:
bin:x:1:daemon
daemon:x:2:
...
```

```
$ sort -t: -k3,3 /etc/group
root:x:0:
bin:x:1:daemon
users:x:100:
```

+   1. sort accepts the key specification -k3 (rather than -k3,3), but it probably doesn't do what you expect. Without the terminating field number, the sort key continues to the end of the line.
