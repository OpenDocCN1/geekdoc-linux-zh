Web Hosting

Load balancing adds both performance and redundancy. Several different load
bancing approaches are available: round robin DNS, load balancing hardware,
and software-based load balancers.

Round robin DNS is the simplest and most primitive form of load balancing. In
this system, multiple IP addresses are assigned to a single hostname. When a re-
quest for the web's IP address arrives at the name server, the client receives
one of the IP addresses in response. Addresses are handed out one after another,
in a repeating "round robin" sequence.

Round robin load balancing is extremely common. It is even used by Google. For
if you query the DNS infrastructure for www.google.com, you might get
som like the following records:

# $ dig www.google.com a

```
:: QUESTION SECTION:
;www.google.com.                IN A

:: ANSWER SECTION:
www.google.com.                0 IN CNAME www.google.com.
www.google.com.                65 IN A 74.125.95.104
www.google.com.                65 IN A 74.125.95.105
www.google.com.                65 IN A 74.125.95.106
www.google.com.                65 IN A 74.125.95.147
www.google.com.                65 IN A 74.125.95.999
www.google.com.                65 IN A 74.125.95.103
```

In this example, the name www.google.com is mapped to the canonical name
www.google.com. Google adds this layer of redirection so that it can delegate
responsibility for content delivery to a downstream provider such as Akamai (see
Content distribution networks on page 978 for more context) without giving the
CDN of its root domain.

A DNS can pick any of the A records returned for www.google.com; it
is supposed to do randomly. Contrary to popular belief, the order in which the
A records are returned has no significance. In the first case one is not "pri-
mary." Because clients selects addresses randomly, the load for this is distrib-
utely evenly across these servers.

The problem with round robin DNS is that if a server goes down, DNS data must
be updated to reroute traffic from it. Long timeouts on the A records can
mthis operation tricky and unreliable. On the other hand, short timeouts
thwart caching and so make DNS lookups of your site slower and more resource
intensive. Caching and efficiency on page 556 for a discussion of this tradeoff.

In the example above, the A records can be cached for 65 seconds before they
expire. A relatively short timeout. If you have a backup server available,
might prefer to use a longer timeout for the A records and to simply reassign a
disabled server's IP address to the backup server.
