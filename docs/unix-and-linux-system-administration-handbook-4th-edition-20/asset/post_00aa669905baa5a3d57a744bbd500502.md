## 4 Access Control and Root Powers

Access control is an area of active research, and it has long been one of the major challenges of operating system design. Generically speaking, operating systems define accounts for individual users, and they offer those users a smorgabord of possible operations: editing text files, logging into remote computers, setting the system's hostname, installing new software, and so on. The access control is running a single black box that contains potential actions (user/operation pairs) and issues rulings as to whether each action is permissible.

In the case of UNIX and Linux, there isn't really a single black box that implements access control. In fact, it's more like a warehouse full of black boxes—and the warehouse is running out of storage space. In this chapter, we go back to the dawn of UNIX to understand how the access control situation got to be the way it is. We then look at modern UNIX and Linux access control systems in theory and in practice, review some tools that help make the administration of access control (and especially, the management of the all-powerful root account) relatively painless.

Chapter 22, *Security*, describes how to avoid unwanted and embarrassing user access by others. Chapter 32, *Management, Policy, and Politics* covers the relevant political and administrative aspects.

## 4.1 TRADITIONAL UNIX ACCESS CONTROL

Even in earliest and simplest versions of UNIX, there was never a single-point access control system. There were, however, some general rules that shaped the system's design:

- * Objects (e.g., files and processes) have owners. Owners have broad (but not necessarily unrestricted) control over their objects.
- You own new objects that you create.
- The special user account called "root" can act as the owner of any object.
- Only root can perform certain sensitive administrative operations.

There's no single "black box" of access control because the code that makes access control decisions is scattered about the system. For example, certain system calls (e.g., setimeofday) are restricted to root; the system implementation checks the identity of the current user and rejects the operation if the user is not root. Other system calls (e.g., kill) implement different calculations that involve both ownership and matching provisions for root. The filesystem implements its own access control system, one that is more sophisticated than found anywhere in the kernel. The only systems use the concept of UNIX groups for access control, for example.

Complicating the picture is that the kernel and the filesystem are intertwined. For example, you control and communicate with most devices through files that represent them in /dev. Since these device files are filesystem objects, they are subject to filesystem access control semantics.

### Filesystem access control

In the traditional model, every file has both an owner and a group, sometimes referred to as the "group owner". The owner can set the permissions of the file. In particular, you can set them restrictively that no one can access it.¹. We talk more about file permissions in Chapter 6, The Filesystem (see page 152).

Although the owner of a file is always a single person, many people can be owners of the file, as long as they are all part of a system group. Groups are traditionally defined in the /etc/group file, but these days group information is more commonly stored on an NIS or LDAP server over the network; see Chapter 19, Sharing System Files, for details.

The owner of a file gets to specify what the group owners do with it. This scheme allows files to be shared among members of the same project. For example, we use a UNIX group to control access to the source files for the admin web site.

The ownership of a file can be determined with ls -l filename.

### The root account

For example:

```bash
ls -l /home/garth/todo
rw-r------ 1 garth staff 1258 Jun 4 18:15 /home/garth/todo
```
This file is owned by the user garth and the group staff. The letters and dashes in
the first column symbolize the permissions on the file; see page 154 for details
how to read this information.

Both the kernel and the filesystem track owners and groups as numbers rather than names. In the most basic case, user identification (UIDs for short) are mapped to usernames in the /etc/passwd file, and group identification numbers (GIDs) are mapped to groups in /etc/group. The text names that correspond to UIDs and GIDs are defined only for the convenience of the system's human users. When commands as ls want to display ownership information in a human-readable format, they must look up each name in the appropriate file or database.

### Process ownership

The owner of a process can send the process signals (see page 124) and can also reduce (degrade) the process's scheduling priority. Processes actually have multiplicities associated with them: a real, effective, and saved UID; a real, saved GID; and under Linux, a "filesystem UID" that is used only to determine access permissions. Broadly, the real numbers are used for accounting and the effective numbers are for the determination of access permissions. The real and effective numbers are normally the same.

Saved UIDs have no direct effect. They allow programs to park an inactive ID for later, utilizing the parsimonious use of enhanced privileges. The filesystem UID is generally explained as an implementation of NFS and is usually the same as the effective UID.

### The root account

The root account is UNIX's omnipotent administrative user. It's also known as the superuser account, although the actual user is "root".

The defining characteristic of the root account is its UID of 0. Nothing prevents you changing the username on it or from creating additional accounts UIDs are 0; however, these are bad ideas. Such changes have tendency to create inadvertent breaches of system security. They also create confusion other people have to deal with the strange way you configured your system.

Traditional UNIX allows the superuser (that is, any process whose effective UID is 0) to perform any valid operation on any file or process.²

2. "Valid" is the order used here. Certain operations (such as executing a file on which the execute permission bit is not set) are forbidden even to the superuser.

Examples of restricted operations are:

- Changing the root directory of a process with chroot
- Creating device files
- Setting the system clock
- Raising resource limits and process priorities
- Setting the system's hostname
- Configuring network interfaces
- Opening privileged ports (those numbered below 1,024)
- Shutting down the system

An example of superuser powers is the ability of a process owned by root to change its UID and GID. The login program and its window system equivalents are a case in point; the process prompts you for your password when you log in to the system initially runs. If the password is legitimate, the login program changes its UID and GID to your UID and GID and starts up under your user environment. Once a root process has changed its ownership to a normal process, it cannot recover its privileged status.

### Setuid and setgid execution

Traditional UNIX access control is complemented by an identity substitution system that is implemented by the kernel and the filesystem in collaboration. The system is described in more detail on page 153; the short version is that it allows specially prepared executable files to run with elevated permissions, usually of root. This mechanism lets developers and administrators set structured ways for unprivileged users to perform privileged operations.

When the kernel runs an executable file that has "setuid" or "setgid" permissions set, it changes the effective UID or GID of the resulting process to the UID or GID of the file containing the program rather than the UID or GID of the file that ran the command. The user's privileges are promoted for the execution of that command only.

For example, users must able to change their passwords. But since passwords are stored in the protected /etc/shadow file, users need a set password to mediate their access. The password command checks to see who's running and customizes its behavior accordingly: users can only change their own passwords, but root can change any password. (This, incidentally, is yet another example of UNIX's ad hoc access control—the rules are written into the code of the password command.)
