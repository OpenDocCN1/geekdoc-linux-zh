## Template Tree 2: cfengine helper

Template Tree 2 was created at the Swiss Federal Institute of Technology (ETH) by Tobias Oetiker. It is a component-based system driven by a two-level approach to defining a site’s configuration and can reduce complexity by dealing with the relocated root directories of diskless machines.

On the lower level, the system consists of a number of "feature packs." A feature pack is a collection of files accompanied by a META file that describes how these files must be installed on the target system. A feature can be anything from network configuration to the latest version of OpenSSH. Features expose configurable parameters that can be set in the configuration file.

The upper level of configuration is a master site file in which you pull the features together and associate them to machines or groups of machines. At this level, you must specify values for the unbound configuration parameters exposed by each feature. For example, one of the parameters for a mail server feature might be the name of the main domain.

Template Tree 2 combines the information from the master configuration file and the individual features META files to generate cfengine configuration file for the whole site. While each feature must contain documentation about its purpose and usage, Template Tree 2 can also generate documentation.

## DMTF/CIM: the Common Information Model

The Distributed Management Task Force (DMTF), a coalition of "more than 3,000 active participants," has been working since 1992 to develop its Common Information Model (CIM) in an attempt to create standards for an object-oriented, cross-platform management system.

In DMTF’s own words, CIM is "management schema...provided to establish a common conceptual framework at the level of a fundamental topology with respect to classification and association, and with respect to the basic set of classes intended to establish a common framework for a description of the managed environment." Whatever.

All major vendors from Microsoft to Sun are members of the DMTF. Unfortunately, the standards they have demonstrated an an impressive mastery of the arts of obfuscation and buzzword husbandry. The companies involved seem eager to demonstrate their willingness to standardize whatever matters. The standards around XML and object orientation. However, we have yet to see sensible product built on top of them.

If there is any upside to this quasire, it is that the DMTF efforts at least require vendors to provide programmatically accessible configuration interfaces to the systems based on an open standard. For UNIX and Linux environments this is nothing new, but the DMTF is not a UNIX creature. It includes Cisco, Microsoft, Symantec, and many other companies with little history of providing sensible ways of scripting their systems. Giving these products a configuration API is a good thing, even if the implementations are still lacking.

## 12.12 Sharing software OVER NFS

Where should extra software be installed: on individual clients or on a central server from which it can be shared over NFS? The standard answer is "the clients," but the NFS makes updates quicker (it is faster and more reliable to update ten servers over 1,000 clients) and save disk space on clients (not that this matters in the world of 1TB disks).

The question really boils down to manageability versus reliability. Network file-based access is centralized and easier to manage from day to day, and it makes fixes and new packages instantaneously on all clients. However, running over the network may be a bit slower than accessing a local disk. In addition, the network server adds dependencies on the network and the file server, not only because it adds potential points of failure but also because it requires clients and servers agree on things like the shared libraries that will be available and the version of those libraries will be installed. The bottom line is that NFS software libraries are an advanced administrative technique and should only be attempted in environments that allow for a high degree of central coordination.

In general, networks of heterogeneous systems derive the most benefit from shared software repositories. If your site is standardized on one operating system and that operating system provides reasonable package management facilities, you're likely to be better off sticking with the native system.

## Package namespaces

Traditional UNIX sprays the contents of new packages across multiple directories. Libraries to /usr/lib, binaries to /usr/bin, documentation to /usr/share/docs, and so on. Linux inherits more or less the same system, although Filesystem Hierarchy Standard makes the locations more predictable. (See pathname/fhs for more information about the FHS.)

The advantage of this convention is that files show up in well-known places. As your PATH environment variable points to /usr/bin and the other standard binary directories, for example, newly installed programs will be readily available.

The downsides are that the origins of files must be explicitly tracked (by means of package management systems) and that the scattered files are difficult to share over a network. Fortunately, sysadmins are willing to put in some extra work to have a reasonable way out of this dilemma: package namespaces.

![](img/579efec8c67772f31ecf34844bbb71a2_459_0.png)

The gist of the scheme is to install every package into its own separate root directory. For example, you might install /tools/graphics/gimp, with the binary located at /tools/graphics/gimp/bin/gimp. You can then recreate an aggregate directory for your collection of tools by placing symbolic links into a directory such as /tools/bin:

```
/tools/bin/gimp -> /tools/graphics/gimp/bin/gimp
```

Users can add /tools/bin to their PATH to be assured of picking up all the tools.

There are various options for structuring the tools directory. A hierarchical approach, /tools/graphics, /tools/editors, facilitates browsing and speeds performance. You may want to include the software version, hardware architecture, operating system, or responsible person's initials in your naming conventions to allow the same collection of tools to be served to many types of clients. For example, Solaris users might include /tools/sun4/bin in their PATHs, and Ubuntu users /tools/ubuntu/bin.

When you install a new version of a major tool, it's a good idea to keep older versions around indefinitely, particularly when users may have significant time and effort invested in projects that they use. Ideally new versions of tools would be compatible with old data files and software, but in practice, disasters are common. It's fine to require users to go through some configuration to access an older version of a package; it's not fine to just break their existing work and make them deal with the consequences.

## Dependency management

Some packages depend on libraries or on other software packages. When you install software locally through a package-management system, you get lots of help with resolving these issues. However, when you build your site-wide network repository, you must address these issues explicitly.

If you manage libraries in the same you you manage applications, you can pool your tools to use libraries from the shared /tools directory. This means because dependent applications are linked against specific versions of the library, the setup remains stable even when new versions of the library are released. The downside is that this type of setup can be complicated to maintain over time.

Resist the temptation to link against a global /tools/lib directory that contains generically named links to common libraries. If you change the libraries, you may run into unexpected and difficult-to-diagnose problems. Shared library systems are designed to address some of the potential headbutts but it makes sense to play it safe in a complicated setup.
