## 9.3 CRONTAB MANAGEMENT

crontab filename installs as your crontab, replacing previous version. cron -e checks out a copy of your crontab, invokes your editor on it (as specified by the EDITOR variable), and then resubmits it to the crontab directory. crontab -l lists the contents of your crontab to standard output, crontab -r removes it, leaving you with no crontab file at.

Root can use a username to edit or view other users' crontabs. For example, crontab -r jsmith erases the crontab belonging to the user jsmith, cron -e edits it. Linux allows both a username and a filename argument with the same command, so crontab must be prefixed with -u to disambuate (e.g., crontab -u jsmith crontab.new).

Without command-line arguments, most versions of crontab will try to read from standard input. If you enter this by accident, doing so will try to exit with <Control-D>; instead. Linux requires you to supply a dash as the filename argument if you want cron to pay attention to its standard input. Smart.

If neither the allow nor the deny file exists, systems default (apparently at random, there is no dominant convention) to allowing all users to submit crontabs or limiting cron access to root. ## 9.4 LINUX AND WIXIE-CRON EXTENSIONS

The version of **cron** included on Linux distributions (including our examples) is usually the one known as ISC **cron** or "Wixie-cron", named after its author, Paul Wixie.

A primary difference is that Wixie-cron also looks for crontabs in /etc/cron.d, which provides another way for software packages to install jobs without editing of a crontab file. These files have a slightly different format because the *username* field comes before the command. In general, /etc/cron.weekly are run once a day, and you can put files in these directories by hand, whereas /etc/cron.d is provided as a depot into which software packages can install any crontab entries they might need.

## 9.5 COMMON USES FOR CRON

A number of standard tasks are especially suited for invocation by cron, and these usually make up the bulk of the material in root's crontab. In this section we look at a few common chores and crontab lines used to implement them.

Systems often come with crontab entries installed. If you want to deactivate the standard entries, comment them out by inserting a pound sign at the beginning of each file. Don't delete them; you might want to refer to them.

In addition to /etc/cron.d mechanism, Linux distributions also reinstall crontab entries that run the scripts in a set of well-known directories, providing another way for software packages to install jobs without editing of a crontab file. For example, scripts in /etc/cron.weekly are run once a day, and you can put files in these directories by hand.

Time ranges in Wixie-cron crontabs can include a step value. For example, the series 0,3,6,9,12,15,18 can be written more concisely as 0-18/3. You can also use three-letter mnemonics for the names of months and days.

You can specify environment variables and their values in a cron file. See the cron(5) man page for more details.

Vixie-cron logs its activities through syslog using the facility "cron", with most messages submitted at level "info". Default syslog configurations generally send cron log data to its file.

For reasons that are unclear, cron has been renamed cron on Red Hat. But it is still the same Wixie-cron we know and love.

# Simple reminders
