Nevertheless, it has some obvious shortcomings:

- From a security perspective, the root account represents a potential single failure. If it's compromised, the integrity of the whole system is violated. There is no limit to the damage an attacker can inflict.

- The only way to subdivide the special privileges of the root account is by writing suited programs. Unfortunately, as the Internet's steady stream of security updates demonstrates, it's difficult to write truly secure software. Besides, you shouldn't write custom software to express something as "I'd like these three people to be able to perform backups on the file server."

- The security model isn't strong enough for use on a network. No computer connected to an unprivileged user who has physical access can be trusted to accurately represent the ownerships of the processes it's running. Who's to say that someone hasn't reformatted the disk and installed their hacked copy of Windows or Linux, with UIDs of their choosing?

- Many high-security environments enforce conventions that simply can't be implemented with traditional UNIX security. For example, United States standards require computer systems to forbid privileged users (e.g., those with Top secret clearance) from repubishing high-security documents at a lower security level. Traditional UNIX security depends on the good will and skill of individual users in this regard.

- Because many access-control-related rules are embedded in the code of commands and daemons, you cannot redefine the system's behavior without modifying the source code and recompiling. But that's not practical in the real world.

- There is minimal support for auditing. You can easily see which groups a user belongs to, but you can't necessarily determine what those group memberships permit a user to.

Because of these shortcomings, UNIX and Linux systems have undergone a variety of interventions over the years to enhance various aspects of the access control system and to help make UNIX systems more acceptable to sites with high security requirements. Some of the adjustments, such as PAM (see page 109), now have nearly universal support. Others are relatively idiosyncratic. The following sections outline the most common extensions.

# Role-based access control

Role-based access control, sometimes known as RBAC, is a theoretical model formalized in 1992 by David Ferraiolo and Rick Kuhn. The basic idea is to add a layer of indirection to access control calculations. Instances of permissions assigned directly to users, they are assigned to intermediate constructs known as "roles," and roles in turn are assigned to users. When an access control decision, the access control library enumerates the roles of the current user and checks if any of those roles have the appropriate permissions.

You might detect some similarity between roles and UNIX groups, in fact there is debate about whether these constructs are fully distinguishable. In practice, roles are more useful than groups because the systems that implement them allow them to be used outside the context of the filesystem. Roles also have a hierarchical relationship to one another, a fact that greatly simplifies administration. For example, you might define a "senior administrator" that has all the permissions of an "administrator" plus the additional permissions X, Y, and Z.

The RBAC model makes it practical to manage large collections of permissions. Most of the effort goes into defining the role hierarchy, that is a one time project. Day-to-day administration of users is simple. Similarly, systems that support RBAC normally take advantage of it to split the permissions of the root account into many different fragments that can be separately assigned.

Many authorizations have a specific read or write granularity, There are 158 of them defined in the auth_attr file. The Solaris commands to manipulate roles using roleadd, rolemod, and roledel.

Since 99 of OpenSolaris in May 2008, Solaris's RBAC system has been robust enough to allow the system to operate without a root account.

HP-UX also uses authorizations to define fine-grained privileges, which assigned to roles associated with individual users and groups. The authorizations have names hpux.process.kill, hpux.admin.network.config, and hpux.device.instance. There are 137 authorizations defined in the file /etc/rbac/auth. You manage roles using the roleadm, authadm, and more.

In AIX, roles have names like DomainAdmin, BackupRestore, AccountAdmin, SysConfig, and Policy. Authorizations are at a similar granularity to those in Solaris or HP-UX. Some examples of authorization names are aix.device, aix.proc, aix.fs.manage, and aix.system.config. Roles are tied to the AIX system SMIT. mkrole, chrole, rmrole, rolelist, and swrole.

# SELinux: security-enhanced Linux

SELinux is an NSA project that has been freely available since 2000. It has been integrated into the 2.6 series of the kernel and is available on most distributions. Some distributions ship with it (often in a somewhat dysfunctional state).

The primary focus of SELinux is to enable "mandatory access control," aka MAC, an access control system in which all permissions are assigned by administrators. Under MAC, users cannot delegate their access or access control parameters on the objects they own.^3

SELinux can also be used to implement a form of role-based access control, although this was not a primary objective of the system.

# POSIX capabilities (Linux)

Linux systems—even those that do not make use of SELinux extensions—are theoretically capable of subdividing the privileges of the root account according to the POSIX standard for "capabilities." Capability specifications can also be set to executable programs. The programs then acquire the specified capabilities when they are executed. It's essentially a lower-risk form of setuid. # PAM: Plugg Authentication Modules

PAM is an authentication technology rather than an access control technology. That is, rather than answering the question "Does user X have permission to perform operation?", it helps answer the precursor question "How do I know this is real user X?" PAM is an important component of the access control chain in systems. In the past, user passwords were checked against the /etc/shadow file (or network equivalent) at login time so an appropriate UID could be set for the shell or window system. Programs run by the user had to track the UID on faith. In the modern world of networks, cryptography, and biometric identification devices, a more flexible and open system is required. Here, PAM.
