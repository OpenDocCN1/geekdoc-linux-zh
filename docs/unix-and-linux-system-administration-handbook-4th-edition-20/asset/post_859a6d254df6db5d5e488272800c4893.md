If you use FTP, a reasonable approach is to allow FTP to the outside world only from a single, isolated host. Modern security-conscious sites use a two-stage filtering scheme. In this scheme, one filter is a gateway to the Internet, and a second filter lies between the gateway and the rest of the local network. The idea is to terminate all inbound connections on systems that lie between these two filters. If these systems are administratively separate from the rest of the network, they can provide a variety of services to the Internet with reduced risk. The partially secured network is usually called the “demilitarized zone” or DMZ.

The most secure way is to use a packet filter with a configuration that allows no inbound connections. You can then liberalize the filter bit by bit as you discover useful things that don't work and, hopefully, your Internet-accessible services onto systems in the DMZ.

## Stateful inspection firewalls

The theory behind stateful inspection firewalls is that if you could listen and understand all the conversations (in all the languages) that were taking place in a crowded airport, you could make sure that someone wasn't planning to bomb a plane later that day. Stateful inspection firewalls are designed to inspect the traffic that flows through them and compare the current network activity to what “should” be.

For example, if the packets exchanged in an FTP command sequence mean a port used later for a data connection, the firewall should expect a connection to occur only on that port. Attempts from the remote site to connect to other ports are presumably bogus and should be dropped.

So what are vendors really selling when they claim to provide stateful inspection? Their products either monitor a very limited number of connections or protocols or search for a particular set of “bad” situations. Not that there is anything wrong with that; clearly, some benefit is derived from any technology that can detect traffic anomalies. In this particular case, it’s important to remember that the claims are mostly marketing hype.

## Firewalls: how safe are they?

A firewall should not be your primary (or only!) means of defense against intruders. It's only one component of what should be carefully considered, multilayer security strategy. The use of firewalls often confers a false sense of security. If a firewall lures you into relaxing other safeguards, it will have a negative effect on the security of your site.

Every host within your organization should be individually patched, hardened, and regularly monitored with one or more tools such as Bro, Snort, Nmap, Mapmap, and OSSEC. Likewise, your entire community needs to be educated about basic security hygiene. Otherwise, you are simply building a structure that has a hard crunchy outside and a soft chewy center.

Ideally, local users should be able to connect to any Internet service they want, but machines on the Internet should only be able to connect to a limited set of local services hosted within your DMZ. For example, you may want to use SFTP access to a local archive server and allow SMTP connections to a server that receives incoming.

To maximize the value of your Internet connection, we recommend that you minimize connectivity and accessibility when deciding how to set up your network. At the end of the day, it is the system administrator's vigilance that makes a network secure, not a fancy piece of firewall hardware.

## Rules, chains, and tables

Version 2.4 of the Linux kernel introduced an all-new packet-handling engine, called Netfilter, along with a command-line tool, iptables, to manage it.

iptables applies ordered “chains” of rules to network packets. Sets of chains make up “tables” and are used for handling specific kinds of traffic.

For example, the default iptables table is named “filter”. Chains of rule in this table are used for packet-filtering network traffic. The filter table contains three default chains: FORWARD, INPUT, and OUTPUT. Each packet handled by the kernel is passed through exactly one of these chains.

Rules in the FORWARD chain are applied to all packets that arrive on one interface and need to be forwarded to another. Rules in the INPUT and OUTPUT chains are applied to traffic addressed to or originating from the local host, respectively. These three standard chains are usually all you need for firewalling between two network interfaces. If necessary, you can define a custom configuration to support more complex routing scenarios.

In addition to the filter table, iptables includes the “nat” and “mangle” tables. The nat table contains chains of rules that control Network Address Translation (Translation, here “nat” is the name of the iptables table and “NAT” is the name of the generic address translation scheme). The Private addresses and network address translation (NAT) on page 462 discusses NAT, and an example of the nat table is shown on page 493. In this section, we use the nat table PREROUTING chain for anti-spoofing packet filtering.

The mangle table can modify or alter the contents of network packets outside the context of NAT and packet filtering. While the mangle table is handy for special packet handling, as resetting time-to-live values, it is not typically used in most production environments. We discuss the filter and nat tables in this section, leaving the mangle to the adventurous.

## Rule targets

Each rule that makes a chain has a “target” that defines what to do with matching packets. When a packet matches a rule, its fate is in most cases sealed; no additional rules will be checked. Although many targets are defined internally by iptables, it is possible to specify another chain as a rule target.

The targets available rules in the filter table are ACCEPT, DROP, REJECT, LOG, MIRROR, QUEUE, REDIRECT, RETURN, and ULOG. When a rule in an ACCEPT, matching packets are allowed to proceed on their way. DROP and REJECT drop both packets; DROP is silent, and REJECT returns an ICMP error message. LOG gives a simple way to track packets as they match rules, and ULOG expands logging. REDIRECT sends packets to a proxy instead of letting them go on their merry way. For example, you might use this to force all your site's web traffic through a web cache as Squid. RETURN terminates user-defined chains and is analogous to the return statement in a subroutine call. MIRROR swaps the IP source and destination address before sending the packet. Finally, QUEUE handles packets to local user programs through a kernel module.
