# Subversion

Several commercial version control systems are also available. You may already have access to one of them if you work in a development shop, and you might be tempted to use it for administrative data. Tread carefully, though; our experience has been that these commercial systems are usually overkill for sysadmin.

The most popular systems today are Subversion and Git. Either system works well for system administration, but Git has an edge in what it sets up new repositories for fast and simple operation. For other advantages of Git, see Scott Chacon's whygitisbetterthanx.com web site.

# Subversion

In the Subversion model, a central server or directory acts as a project's authoritative repository. By default, the Subversion server is a module in the Apache server, which is convenient for distributed software development but may not be so good for administrative uses. Furthermore, Subversion follows an alternative type of server in the form of a daemon svnverse. You can run svnverse from your home directory while experimenting with Subversion, but in production it should have its own user account and be run from incd.

Setting up a repository is easy. For example, the following steps create a new Subversion repository called admin:

```
# cd /home/svn
# mkdir repositories
# cd repositories
# svnadmin create admin
# chmod 700 admin
```

If you peek inside the admin directory, you will find a well-organized repository structure, including a conf README file. The configuration file svnverse.conf can be found in the conf subdirectory. This file tells the server daemon how to provide access to the new repository. Here's an example configuration appropriate for administrative uses:

```
[general]
anon-access = none
auth-access = write
password-db = passwd
realm = The Sysadmin Repository
```

Because one of Subversion's design goals was to facilitate collaboration among people at different sites, it has an access control method that is separate from that of the operating system. The file password (in the same directory) contains a list of users and their plaintext (!) The plaintext bit is not nice, but the saving grace is that the passwords are never transmitted over the network. They are also never typed from memory by users, so you may assign passwords that are long enough and random enough to be secure.
