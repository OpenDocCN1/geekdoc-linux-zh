
## Chapter 17 DNS: The Domain Name System

Sample BIND logging configuration

The following snippet from `named.conf` for a busy name server illustrates a comprehensive logging regime:

```bind
logging {
    channel default_log { # Default channel, to a file
        file "log/named.log" versions 3 size 10m;
        print-time yes;
        print-category yes;
        print-severity yes;
        severity info;
    };
    channel xfer-log { # Zone transfers channel, to a file
        file "log/xfer.log" versions 3 size 10m;
        print-category yes;
        print-severity yes;
        print-time yes;
        severity info;
    };
    channel dnnssec { # DNSSEC channel, to a file
        file "log/dnnssec.log" versions 3 size 1m;
        severity debug 1;
        print-severity yes;
        print-time yes;
    };
    category default { default_log };
    category dnnssec { dnnssec-log };
    category xfer-in { xfer-log };
    category xfer-out { xfer-log };
    category notify { xfer-log };
};
```

### Debug levels in BIND

named debug levels are indicated by integers from 0 to 100. The higher number, the more verbose the output. Level 0 turns debugging off. Levels 1 and 2 are fine for debugging your configuration and database. Levels beyond 4 are appropriate for the maintainers of the code.

You invoke debugging on the named command line with the -d flag. For example:

```bash
$ sudo -d2
```

would start named at debug level 2. By default, debugging information is written to the file named.run in the current working directory where named is started. The named.run flies very fast, so do not go out for a beer while debugging or you will have bigger problems when you return.

You can turn on debugging while named is running with `rndc trace`, which increments the debug level by 1, or `rndc trace level`, which sets the debug level to the specified value. `rndc notrace` turns debugging off completely. You can also enable debugging by defining a logging channel that includes a severity specification

```bind
severity debug 3;
```

which sends all debugging messages up to level 3 to that particular channel. Other lines in the channel definition specify the destination of those debugging messages. The higher the severity level, the more information is logged.

Watching the logs or the debugging output illustrates how DNS is misconfigured in the real world. That pesky dot at the end of names (or the lack thereof) accounts for an alarming amount of DNS traffic. The dot is at the end of each fully qualified domain name.

## Logging in NSD/Unbound

Logging in NSD and Unbound is simple in comparison to BIND. According to NSD's doc/README, "DNS doesn't do any logging." What really means is that NSD does not do any DNS traffic logging or monitoring; however, it does log important events to syslog.

By default, logs go to standard error and to syslog with facility daemon. However, if the logfile attribute of the server statement in either unbound.conf or nsd.conf is set, then logging goes to the specified file.

The amount of data logged (aside from errors, which are always included) is controlled by a verbosity level you set in the config files. In the case of unbound, you can also set the verbosity level as a command-line option.

### Sample BIND logging configuration

- **Many timeouts resolving xxx: disabling EDNS.** This message can result from a broken firewall not admitting UDP packets over 512 bytes or not admitting fragments. It can also indicate problems at the firewall. Verify that the problem is not your firewall and consider redirecting these messages to the null channel.
- **Unexpected RCODE (SERVFAIL) resolving xxx.** This can result from an attack or, more likely, a sign of something repeatedly querying a zone.
- **Bad referral.** This message indicates miscommunication among zone's name servers.
- **Not authoritative.** For slave server is unable to get authoritative data for a zone. It's pointing to the wrong master, or perhaps the master had trouble loading the zone in question.
- **Rejected zone.** `named` rejected a zone file because it contained errors.
- **No NS records.** A zone file did not include NS records after SOA record. It could be that they don't start with tab or other whitespace. In the latter case, the records are not attached to the zone of SOA record and are therefore misinterpreted.
- **No default TTL set.** The preferred way to set the default TTL for records is with $TTL directive at the top of the zone file. This error message indicates that $TTL is missing; required in BIND 9.
- **No root server.** Your server is having trouble finding the root servers. Check your hints file and the server's Internet connectivity.
- **Address in use.** The port on which `named` wants to run is already used by another process, probably another copy of `named`. If you don't see `named` around, it might have crashed and left a `rndc` socket open that you have to track down and remove. A good way to fix the problem is to stop the `named` process with `rndc` and then restart:

```bash
$ sudo rndc stop
$ sudo /usr/sbin/named
```
- **updating zone: update** A dynamic update was attempted but refused, most likely because of allow-update in `named.conf` for this zone. This is a common error message and often caused by misconfigured boxes.

## Name server control programs

All of three name servers come with a control program: nsd controls nsd, rndc controls named, and unbound-control controls unbound. nsd works on the local machine only, but rndc and unbound-control can work across the Internet.

### Using BIND's rndc

Table 17.16 shows the options accepted by rndc (Note: Table content not provided). Typing rndc with no arguments gives a list of available commands and a short description of what they do. Earlier instances of rndc used signals as nsd does, but with over 25 commands, BIND folks ran long ago. Commands put them in whatever directory is specified as named's home in named.conf.

rndc reload makes named read its configuration file and reload zone files. The reload command is handy when one zone has changed and you don't want to reload all the zones, especially on a busy server. You can also specify a class and view to reload only the selected zone of the zone's data.

Note that rndc reload is not sufficient to add a completely new zone; that requires named to read both the named.conf and the new zone file. For new zones, use rndc reconfig, which reloads the config file and any new zones without disturbing existing zones.

rndc freeze stops dynamic updates and reconciles the journal of dynamic updates to the data files. After freezing the zone, you can edit the zone data by hand. As long as the zone is frozen, dynamic updates are refused. Once you've finished editing, use rndc thaw zone to start accepting dynamic updates.
