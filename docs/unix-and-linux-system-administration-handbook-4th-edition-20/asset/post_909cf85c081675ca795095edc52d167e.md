
# Chapter 11 Syslog and Log Files

```
# syslog.conf file for nonmaster machines
```

```
# Emergencies: tell everyone who is logged on
  *emerg.user.node *
```

```
# Forward important messages to the central logger
  *warning;lpr,local1.none @netloghost
  daemon,auth.info @netloghost
```

```
# Send some local stuff to the central logger too
  local2.info;local7.debug @netloghost
```

```
# Keep printer errors local
  lpr.debug /var/log/lpd-errors
```

```
# sudo logs to local2 - keep a copy here too
  local2.info /var/log/sudo.log
```

```
# Keep kernel messages local
  kern.info /var/log/kern.log
```

This configuration does not keep log information locally. It's worth mentioning that if loghost is down or unreachable, log messages will be retrieved. You may want to keep duplicates of important messages to guard against this possibility.

At a site with software installed, logs of messages can be logged inappropriately to facility, level emerg. In this example, user/emerg has been specifically excluded by the user.node clause in the first noncomment line.

The second and third lines forward all important messages to the central logging host; messages from the printing system and the campus-wide card access system (local1) are explicitly excluded. The fourth line forwards a subset of local logging to loghost as well. The three entries keep local copies of printer errors, sudo messages, and kernel messages.

# Central logging host

This example is for the central, secure logging host for a moderate-sized network of 7,000 hosts.

```
# syslog.conf file for master logging
```

```
# Emergencies to the console and log file, with timing marks
  *emerg /dev/console
  *err,kern.mark.debug:auth.notice /dev/console
  *err,kern.mark.debug:user.node /var/log/console
  auth notice /var/log/console
```

```
# Send non-emergency messages to the usual log files
  *err.user.node:kern.debug /var/log/messages
  daemon,auth.notice:mail.crit /var/log/messages
  lpr.debug /var/log/lpd-errors
  mail.debug /var/log/mail
```

# Alternatives to syslog

# Local authorization messages, e.g., sudo
local2.debug /var/log/sudo.log
local2.alert /var/log/sudo.log
auth.info /var/log/auth.log

# Other local stuff
local0.info /var/log/messages
local4.notice /var/log/daemon.log
local6.debug /var/log/tcp.log

# Local messages (the default if no facility is specified)
user.info /var/log/user.log

Messages arriving from local programs and on the network are written to log files. In some cases, the output from each facility is put into its own file. The central logging host generates the timestamp for each message as it writes it out. If you have machines in several time zones or your system clocks are not synchronized, the timestamps are somewhat misleading.

# Syslog debugging

The logger command is useful for submitting log entries from scripts. You can also use it to test changes in syslog's configuration file. For example, if you added the line

```
local5.warning /tmp/messages.log
```

and to verify that it is working, run

```bash
logger -p local5.warning "test message"
```

A line containing "test message" should be written to /tmp/messages.log. If this doesn't happen, perhaps you forgot to create the file, give the appropriate permissions, or've used spaces instead of tabs?

# Alternatives to syslog

Although syslog has long been the reigning logging system for UNIX and Linux, several alternatives have been developed in an attempt to address some of syslog's shortcomings. One of these, syslog-ng (next generation), is now used by SUSE systems by default. From a configuration standpoint it is quite different from the standard syslog, and we do not describe it in detail. If you would like to try it on a non-SUSE system, syslog-ng adds additional configuration facilities, filtering based on message content, and better support for messages forwarded over the network.

SDSC syslog (from the San Diego Supercomputing Center) is also known as high-performance syslog. It provides a forensically sound auditing system by implementing the specifications of RFC3195 (Reliable Delivery for syslog). It was designed with high-traffic sites in mind and contains a number of performance optimizations. You can download the source from SourceForge: sourceforge.net/projects/sdsyslog

Syslog-ng, another powerful next-generation alternative, is the default with several Linux distributions, including Fedora. Syslog-ng is multithreaded and aims for high reliability and robust security. It supports TCP (as opposed to UDP, original syslog) and can use SSL, which may be required at some sites for regulatory reasons. Syslog-ng can even log to databases. Learn more at syslog.com.

# Linux kernel and boot-time logging

![](img/579efec8c67772f31ecf3484bbb71a2_400.png)

The kernel and system startup scripts present some special challenges in the domain of logging. In the case of the kernel, the problem is to create a permanent record of the boot process and the operation of the kernel without building dependencies on any particular filesystem organization. In the case of the startup scripts, the challenge is to capture a coherent narrative of the startup procedure without dumping any of the system daemon to a startup log file, interfering with any program's logging, or clogging up the startup scripts with double entries or redirection.

Kernel logging is dealt with by having the kernel store its entries in an internal buffer of limited size. The buffer is large enough to accommodate messages about all the kernel's boot-time activities. When the system has come all the way up, a user process accesses the kernel's log buffer and makes a final disposition of its contents. The dmesg command is the best way to view the kernel buffer; the output even contains messages that were generated before starting.

The kernel's ongoing logging is handled by a daemon called klogd. The functions of klogd are a superset of dmesg; in addition to dumping the kernel log, it passes generated entries along to a file or to syslog. In normal operation, klogd runs in this latter mode. Syslog processes the messages according to the instructions for the “kern” facility. They are typically sent to /var/log/messages or /var/log/syslog.

Our example distributions' startup scripts do not use the dmesg -c flag when they make their initial dump of log messages, so the kernel's message buffer is not reset. When klogd starts up, it finds the same set of messages seen by dmesg in the buffer and submits them to syslog. For this reason, some entries appear in both the dmesg and boot.msg file and in the system's primary syslog file.

# AIX logging and error handling

Another issue in kernel logging is the appropriate management of the system console. As the system is booting, it's important for all the output to come to the console. However, once the system is up and running, console messages may be more an annoyance than a help, particularly if the console is used for logins.

Both **dmesg** and **klog** let you set the kernel's console logging with a command-line flag. For example:

```bash
sudo dmesg -n 2
```

Level 7 is the most verbose and includes debugging information. Level 1 includes only panic messages (the lower-numbered levels are the most severe). All kernel messages continue to go to the console (as syslog) regardless of whether they are forwarded.

The kernel provides some control files underneath the **/proc/sys** directory to allow floods of repeated messages to be choked off. See the section **Tuning kernel parameters** starting on page 421 for more information about the general mechanism through which kernel parameters are set. The specific control files are **/proc/sys/kernel/printk_ratelimit**, which specifies the minimum number of seconds that must elapse between kernel messages once the choke has been activated (default 5), and **/proc/sys/kernel/printk_ratelimit_burst**, which specifies how many messages to let through before activating the choke (default 10). These parameters are advisory, so do not absolutely guarantee that a heavy flow of messages will be stashed. They also apply only to messages created in the kernel by the `printk()` function.

Logging for the startup scripts is unfortunately not well managed as kernel logging. Red Hat Enterprise Linux uses an **initlog** command to capture the output of startup commands and shut off to syslog. Unfortunately, **initlog** must be mentioned explicitly whenever a command is run, so the information comes at the cost of some complexity. Events make their way to **/var/log/boot.log**.
