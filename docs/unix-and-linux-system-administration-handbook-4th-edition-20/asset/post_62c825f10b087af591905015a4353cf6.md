
# Table 6.5 Examples of chmod mnemonic syntax

| Spec | Meaning |
|---|---|
| u+w | Adds write permission for the owner of the file |
| ug=rw,o= | Gives r/w permission to owner and group, and read permission to others |
| a-x | Removes permission for all categories (owner/group/other) |
| ug=rx,o= | Makes setuid/setgid and r/x permission to owner and group only |
| g=u | Makes the group permissions to be the same as the owner permissions |

With the -R option, chmod recursively updates the file permissions within a directory. This feat is trickier than it looks because the enclosed files and directories may not share the same attributes; for example, some might be executable files while others are text files. Mnemonic syntax is particularly useful with -R because it preserves bits that you don't set explicitly. For example,

```bash
$ chmod -R g+w mydir
```

adds group write permission to mydir and all its contents without messing up the execute bits of directories and programs.

If you want to adjust execute bits, be wary of chmod -R. It's hard to find that the execute bit has a different interpretation on a directory than it does on a flat file. Therefore, chmod -R a-x probably won't do what you intend.

# chown and chgrp: change ownership and group

The chown changes a file ownership, and the chgrp command changes its group ownership. The syntax of chown and chgrp mirrors that of chmod, except the first argument is the new owner or group, respectively.

To change a file's group, you must either be the owner of the file and belong to the group you're changing to or be the superuser. The rules for changing ownership are more complex and vary among systems. Most systems define some of process-specific capability that fine-tunes the behavior of chown.

Like chmod, chown and chgrp offer the recursive -R flag to change the settings of a directory and all the files underneath it. For example, the sequence

```bash
$ chown -R matt /matt/restore
$ chgrp -R staff /matt/restore
```

could be used to reset the owner and group of files restored from a backup for the user matt. If you're setting up a user's home directory, don't try to chown files with a command such as

```bash
$ sudo chmod -R matt ~matt/
```

since the pattern will match ~matt/ and will therefore end changing the ownership of the parent directory and probably the home directories of other users.

# Chapter 6 The Filesystem

chown can change both the owner and group of a file at once with the syntax
`chown user:group file ...`

For example,

```bash
$ sudo chown -R matt:staff /matt/restore
```

Linux and Solaris take this syntax to its logical end and let you omit either user or group, making the chgrp command superfluous. If you include the colon as no group, chown uses the user's default group.

# umask: assign default permissions

You can use the built-in shell command umask to influence the default permissions given to the files you create. Every process has its own umask attribute; the shell's built-in umask command sets the shell's own umask, which is inherited by commands that you run.

The umask is specified as a three-digit octal value that represents the permissions to take away. When a file is created, its permissions are set to whatever the creating program requests whatever the umask forbids. Thus, the individual digits of the umask allow the permissions shown in Table 6.6.

Table 6.6 Permission encoding for umask
| Octal | Binary | Perms | Octal | Binary | Perms |
|---|---|---|---|---|---|
| 0 | 000 | rwx | 4 | 100 | --wx |
| 1 | 001 | rw-- | 5 | 101 | -w- |
| 2 | 010 | r-x | 6 | 110 | --x |
| 3 | 011 | r-- | 7 | 111 | --- |

For example, umask 027 allows permissions for the owner who forbids write permission to the group and allows no permissions for anyone else. The default umask value is often 022, which denies write permission to the group and world but read permission.

See Chapter 7 for more information about startup files.

You cannot force users to have a particular umask value because they can always reset it to whatever they want. However, you can put a suitable default in the profile file that gives you yours.

# Table 6.7 Ext2 and ext3 bonus flags

| Flag | Meaning |
|---|---|
| A | Never update access time (st_atime; for performance) |
| a | Allow writing in append mode (only root can set) |
| D | Force directory updates to be written synchronously |
| d | No backup--dump this file |
| i | Make file immutable and undeletable (only root can set) |
| j | Keep a journal for data changes as well as metadata |
| S | Force changes to be written synchronously (no buffering) |

With the possible exception of the "no backup", it's clear that any of these features offer much day-to-day value. The immutable and append-only flags were largely conceived as ways to make the system more resistant to tampering by hackers or hostile code. Unfortunately, they can confuse software and not protect against hackers who don't know enough to use chatter -ia. Real-world experience has shown that these flags are often used by hackers against them.

The S and D options for synchronous writes also merit a special caution. Since they force all filesystem pages associated with a file or directory to be written immediately on changes, they might seem to offer additional protection against data loss in the event of a crash. However, the order of operations for synchronous updates is unusual and has been known to confuse fsck; recovery of a damaged filesystem might therefore be made more difficult than a more simple method.

# 6.6 ACCESS CONTROL LISTS

The traditional UNIX permission system is powerful enough to accommodate most needs. Virtually all non-UNIX operating systems use access control lists, ACLs. Each file or directory can have an associated ACL that lists the rules to be applied. Each of the rules within an ACL is called an access control entry, or ACE.
