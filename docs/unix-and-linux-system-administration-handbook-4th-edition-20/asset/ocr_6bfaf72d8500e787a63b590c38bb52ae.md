In the typical scenario, the display manager prompts for a username and password. The user's password is then authenticated according to the PAM configuration specified in **/etc/pam.xdm** (or **gdm/kdm** if you are using the GNOME or KDE display managers). The login screen can also offer several alternative desktop top environments, excluding the important failsafe option discussed below.

The display manager's final duty is to execute the **Xsession** script, which sets up the user's desktop environment. The **Xsession** script, also often found in **/etc/X11/xsession,gdm.x**, is a system-wide startup script. It sets application defaults, installs standard key bindings, and config language settings. The **Xsession** script then executes the user's own startup script, usually **/.xsession**, to start up the window manager, task bar, helper agents, and possibly other programs. GNOME and KDE also have their own startup scripts that configure the user's desktop with GNOME and KDE's configuration tools; this scheme is less error-prone than users' editing of their own startup scripts.

When the execution of **~/.xsession** completes, the user is logged out and the display manager goes back to prompting for a username and password. Therefore, **~/.xsession** must start all programs in the background (by appending & to the end of each command) except for the last one, which is normally the window manager. (If all commands in- are in the background, the script terminates right away and the user is logged out immediately after logging in.) With the window manager as the final, foreground process, the user is logged out only after the window manager exits.

The failsafe login option allows users log in to fix their broken startup scripts. This option can be uniquely selected from the display manager's login screen. It opens only a terminal window; once the window closes, the system logs the user out. Every system allows the failsafe login option; it helps users fix their own errors rather than having to page you in the middle of the night.

Expecting to leave a process in the foreground is the most common startup problem, but it is the only possibility. If the case of problems is not obvious, you may refer to the **~/.xsession-errors** file, which contains the output of the commands run from **~/.xsession**. In a pinch, move the **~/.xsession** script aside and make sure you can log in with it out. Then restore it or one or two lines at a time until you find the offending line.
