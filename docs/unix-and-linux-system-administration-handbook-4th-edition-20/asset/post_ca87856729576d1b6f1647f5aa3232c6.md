# One filesystem per user

Since filesystems consume no space and take time to create, the optimal number of them is closer to "a lot" than "a few". If you keep home directories on a ZFS storage pool, it's recommended that you make each home directory a filesystem. There are several reasons for this convention.

- * If you need to set disk quotas, home directories are a natural granularity to which to do. You can set quotas on all individual's filesystems and on the filesystem that contains all users.
- Snapshots are per filesystem. If each user's home directory is a separate filesystem, the user can access old snapshots through ~/.zfs. This is a huge saver for administrators because it means that users can service most of their own file restores.
- ZFS lets you delegate permission to perform various operations such as taking snapshots and rolling back the filesystem to an earlier state. If you wish, you can gain control over these operations for their home directories. We do not describe the details of ZFS permission management in this book; see the ZFS Administration Guide.

# Snapshots and clones

ZFS is organized around the principle of copy-on-write. Instead of overwriting disk blocks in place, ZFS allocates new blocks and updates pointers. This approach makes ZFS resistant to corruption because operations never end half-completed in the event of a power failure or crash. Either the root block is updated or not; the filesystem is consistent either way (though a few changes may be "undone")

Just as a volume manager, ZFS brings copy-on-write to the user level by allowing to create instantaneous snapshots. However, there's an important difference: ZFS snapshots are implemented perfilesystem rather than volume, they have arbitrary granularity. Solaris uses this feature to get effect in the Time Slider widget for GNOME desktop Machine, the Time Slider is a combination of scheduled tasks that create and manage snapshots at regular intervals and a UI that makes it easy for you to reach older versions of your files.

On the command line, you create snapshots with zfs snapshot. For example, the following command sequence illustrates creation of a snapshot, use the snapshot through the filesystem's .zfs/snapshot directory, and reversion of the filesystem to its previous state.

```
solaris touch /opt/demo/new_fs/now_you_see_me
solaris $ /opt/demo/new_fs
now_you_see_me
solaris zfs snapshot demo/new_fs@snapshot1
solaris $ rm /opt/demo/new_fs/now_you_see_me
solaris $ /opt/demo/new_fs
solaris $ /opt/demo/new_fs/.zfs/snapshot/snapshot1
now_you_see_me
solaris zfs rollback demo/new_fs@snapshot1
solaris $ /opt/demo/new_fs
now_you_see_me
```

You assign a name to each snapshot at the time it create. The completed specifier for a snapshot is usually written in the form filesystem@snapshot.

Use zfs snapshot -r to create snapshots recursively. The effect is the same as creating zfs snapshot on each contained individually: each receives its own snapshot. All the snapshots have the same name, but they're logically distinct.

ZFS snapshots are read-only, and although they can bear properties, they are not true files. However, you can instantiate a snapshot as a full-fledged, writable filesystem by "cloning" it.

```
solaris zfs clone demo/new_fs@snapshot1 demo/subclone
solaris $ /opt/demo/subclone
now_you_see_me
solaris touch /opt/demo/subclone/and_me_too
solaris $ /opt/demo/subclone
and_me_too now_you_see_me
```

The snapshot that is basis of the clone remains undisturbed and read-only. However, the new filesystem (demo/subclone in this example) retains a link to both the snapshot and the filesystem on which it's based, and neither of those entities can be deleted as the clone exists.

Cloning isn't a common operation, but it's the only way to create a branch in a filesystem's evolution. The zfs rollback operation demonstrated above can revert a filesystem to its most recent snapshot, so to use it you must permanently delete (zfs destroy) any snapshots since the snapshot that is your reversion target. Cloning lets you go back in time without losing access to recent changes.

# Raw volumes

You create areas and raw storage areas with **zfs create**, just as you create filesystems. The `-V` size argument makes **zfs** treat the new object as a raw volume instead of a filesystem. The *size* can use any common unit, for example, **128m**.

Since the volume does not contain a filesystem, it is not mounted; it shows up in the `/dev/zvol/` and `/dev/zvol` directories and can be referenced as if it were a hard disk or partition. ZFS mirrors the hierarchical structure of the storage pool in these directories, **sudo zfs create -V 128m demo/swap** creates a 128MB swap volume located at `/dev/zvol/dsk/demo/swap`.

You can create snapshots of raw volumes just as you can with filesystems, but because there's no filesystem hierarchy in it to put a .zfs/snapshot directory, the snapshots show up in the same directory as their source volumes. Clones work too, just as you'd expect.

By default, raw volumes receive a space reservation equal to their specified size. You're free to reduce the reservation or away with it entirely, but note that you can write to the volume return an "out of space" error. Clients of raw volumes may not be designed to deal with such an error.

# Filesystem sharing filesystem through NFS, CIFS, and iSCSI

For example, suppose that you've discovered a security breach that occurred some within the last week. For safety, you might want to revert a filesystem to its state of a week ago to be sure it contains no hacker-installed back doors. At the same time you don't want to lose recent work or the data for forensic analysis. The solution is to clone the week-ago snapshot to a new filesystem, **zfs rename** the old filesystem, and then **zfs rename** the clone in place of the original filesystem.

For good measure, you should also **zfs promote** the clone; this operation reverts the relationship between the clone and the filesystem of. After promotion, the main-line filesystem has access to all the old filesystem's snapshots, and the old, moved-aside filesystem becomes the "cloned" branch.

Just as ZFS redefines many aspects of traditional filesystem management, it changes the way that filesystems are shared over a network. In particular, you can set the **sharefs** and **sharesmb** property of a filesystem to **on** to make it available through NFS or Solaris's built-in ZFS server. See Chapter 18, *The Network File System*, for more information about NFS, and *Sharing files with Samba and CIFS* on page 320.

By default, all the share* properties are inheritable. If you share /home for NFS, for example, you automatically share the individual directories beneath it, even if they are defined as file systems. Of course, you can override this behavior by setting an explicit sharefs=no value on each.

ZFS uses the NFS4 standard for access control lists. Nuances of that standard are discussed in more detail in Chapter 6, The Filesystem, and on page 166 The summary is that ZFS provides excellent ACL support for both Windows and NFS clients.

# Storage pool management

Now we've peeked at some of the features that ZFS offers at the filesystem and block-level unit, let's take a longer swim in ZFS's storage pools.

Up to this point we've used a pool "demo" that we created from a single disk on page 266. Here is it in the output of zfs pool:

```
solaris$ zpool list
NAME SIZE AVAIL CAP HEALTH ALTROOP
demo 496G 240K 496G 0% ONLINE ALTROOP
rpool 748G 23.78G 724G 3% ONLINE
```

The named rpool contains the bootable filesystem. Bootable pools are currently restricted in several ways: they can only contain a single virtual device, and that device must be either a mirror array or a single disk drive; it cannot be a RAID array. If it is a disk, it cannot have a GPT partition table.

zpool status adds detail about the virtual devices that make up a storage pool and reports their current status.

```
solaris$ zpool status demo
pool: demo
state: ONLINE
scrub: none requested
config:
NAME STATE READ WRITE CKSUM
demo ONLINE 0 0 0
c8d1 ONLINE 0 0 0
```
