### Identity mapping in version 4

As discussed in Chapter 7, UNIX operating systems identifies users through a collection of UIDs and GIDs in the passwd file or administrative database. NFS version 4, on the other hand, returns users and groups as string identifiers of the form user@nfs-domain and group@nfs-domain. Both NFS clients and servers run an identity mapping daemon that maps UNIX identities to strings.

When a version 4 client performs an operation that returns identities, such as a file list with -l (the underlying operation is a stat call), the server's identity mapping daemon uses its local passwd file to convert the UID and GID then reverses the process, converting ben@attrust.com to local UID and GID values, which may or not be the same as the server. If the string value does not match any local identity, the nobody user account is used.

At this point, the remote call (stat) has completed and returned UID and GID values to its caller (the ls command). But since ls was called with the -l option, it needs to display text names instead of numbers. So, ls in turn translates the IDs back to textual names using the getuid and getgid library routines. These routines once again consult the passwd file or its network database equivalent. What a long, strange trip it's.

Confusingly, the identity mapping is only when retrieving and setting file attributes, typically ownership. Identity mapping plays no role in authentication or access control, all of which is handled in the traditional way by RPC. Ergo, passwd files are still essential for users of AUTH_SYS “security,”

An unfortunate side effect of this identity and authentication ambiguity arises on systems that do not have synchronized passwd files. The identity mapper may do a better job of mapping the underlying NFS protocol, causing the apparent file permissions to conflict with the permissions of the NFS server may actually enforce. Consider, for example, the following commands on an NFS4 client:

```bash
[ben@fs-client]$ id ben
uid=1000(ben) gid=1000(ben) groups=1000(ben)
```

```bash
[john@fs-client]$ id john
uid=1010(john) gid=1010(john) groups=1010(john)
```

```bash
[john@fs-client]$ ls -ld root
drwx-xr-x 2 john 4096 May 27 16:42 ben
```

```bash
[ben@fs-client]$ touch ben/file
[ben@fs-client]$ ls -l ben/file
-rw-rw-r-- 1 john nfsnobody 0 May 27 17:08 ben/file
```

First, ben is shown to have UID 1000 and to have UID 1010. An NFSexported directory called ben appears to have permissions 755 and is owned by john. However, ben is able to create a file in the directory even though the -l output indicates that he lacks permission.

On the server, john has UID 1000. Since john has UID 1010 on the client, the identity mapper performs UID conversion as described above, with the result that “john” appears to be the owner of the directory. However, the identity mapping daemon plays no role in access control. For the file operation, ben’s UID of 1000 is sent to the server, where it is interpreted as john’s.

Unfortunately for administrators, identity mapping daemons are not standardized across systems, so their configuration processes may be different. The specifics of each our examples are covered starting page 709.

### Root access and the nobody account

Although users should generally have identical privileges wherever they go, it is traditional to prevent root from rampant on NFS-mounted filesystems. By default, the NFS server intercepts requests on behalf of UID 0 and changes them to look as if they came from some other user. This modification is called “squashing root”. The root account is not entirely shut out, but it is limited to the abilities of a normal user.

### Disk quotas

Disk quotas are a mechanism to prevent any single user or group from filling up the disk. Quotas allow administrators to limit the amount of space (blocks) or the number of files (inodes) a user or group can consume. Quotas are typically implemented at the filesystem level.

- Soft limit: A limit that a user can exceed for a limited period of time.
- Hard limit: The absolute limit that a user cannot exceed.

### Grace period

The grace period is the time during which a user can exceed the soft limit before it is treated as the hard limit. Once the grace period expires, the user must delete files to get below the soft limit.

### Server-side caching

In NFS 4, the server can handle some of the caching operations previously handled by the client. This reduces the number of requests over the network and can improve performance. Server-side caching is particularly effective for files that are frequently accessed.

### Server-side NFS

NFS 4 introduces several features to improve performance and security, such as delegation. Delegation allows the client to cache file attributes and data locally, reducing the need to communicate with the server.

- Read delegation: The client is allowed to read the file without checking.
- Write delegation: The client is allowed to write to the file, flushing changes to the server only when necessary.
