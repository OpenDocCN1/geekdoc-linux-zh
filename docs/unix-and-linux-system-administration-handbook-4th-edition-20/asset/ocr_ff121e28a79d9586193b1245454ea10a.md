Access to NFS systems is granted by a file /etc/exports that enumerates the hostnames (or IP addresses) of systems that have access to the server's shared filesystems. Unfortunately, this too is a weak form of security because the server trusts the clients to tell it who they are. It's easy to make clients lie about their identities and IP addresses, so this mechanism cannot be fully trusted. Nevertheless, you should export only to clients that you trust, and always check that you have not accidentally exported systems to the whole world.

See page 932 for more information about firewalls. NFS 4 uses only TCP as a transport protocol and typically communicates over port 2049. Since V4 does not rely on any other ports, opening access through a firewall is as simple as opening port 2049. With all list configurations, be sure to specify source and destination addresses in addition to the port. If your site does not need to provide NFS services to the Internet, block access through the firewall or use a local packet filter.

File service over wide area with NFSv2 and V3 is not recommended because of the long history of bugs in the RPC protocols and the lack of strong security mechanisms. Administrators of NFS version 3 servers should block access to TCP and UDP ports 2049 and also the portmap port, 111.

# Identity mapping in version 4

As discussed in Chapter 7, UNIX operating systems identifies users through a collection of UIDs and GIDs in the passwd file or administrative database. NFS version 4, on the other hand, returns users and groups as string identifiers of the form user@nfs-domain and group@nfs-domain. Both NFS clients and servers run an identity mapping daemon that maps UNIX identities to strings.

When a version 4 client performs an operation that returns identities, such as a file list with -l (the underlying operation is a stat call), the server's identity mapping daemon uses its local passwd file to convert the UID and GID then reverses the process, converting ben@attrust.com to local UID and GID values, which may or not be the same as the server. If the string value does not match any local identity, the nobody user account is used.

At this point, the remote call (stat) has completed and returned UID and GID values to its caller (the ls command). But since ls was called with the -l option, it needs to display text names instead of numbers. So, ls in turn translates the IDs back to textual names using the getuid and getgid library routines. These routines once again consult the passwd file or its network database equivalent. What a long, strange trip it's.

Confusingly, the identity mapping is only when retrieving and setting file attributes, typically ownership.
