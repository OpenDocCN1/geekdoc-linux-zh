```
ubuntu$ seterial -g /dev/ttyS0

```

To set the parameters, you specify the device file and a series of parameters and values. For example, the command

```
ubuntu sudo seterial /dev/tty1 port 0x2f8 irq 3
```

sets the I/O port address and IRQ for ttyS1. It's important to keep in mind that this command does not change the hardware configuration in any way; it simply informs the Linux serial driver of the configuration. To change the actual settings of the hardware, consult your system's BIOS.

seterial changes only the current configuration, and the settings do not persist across reboots. Unfortunately, there isn't a standard way to make the changes; each of our example distributions does it differently.

- The /etc/init.d/seterial script on Ubuntu systems is used for serial initialization. It reads parameters from each port from /var/lib/seterial/autoserial.conf.

- SUSE's /etc/init.d/seterial handles serial port initialization. Unfortunately, this script has no configuration file; you must edit it directly to reflect the commands you want to run. Bad SUSE! The script uses its little metalanguage to construct the seterial command lines, but fortunately there are plenty of commented-out example lines to choose from.

- Red Hat's /etc/rc.d/rcysinit script checks for the existence of /etc/rc.serial and executes it at startup time if it exists. No example file is provided, so you must create the file if you want to make use of this feature. Just list the seterial commands you want to run, one per line. For completeness, it's probably a good idea to make the file executable and to put #/bin/sh on the first line; however, touches d'élégance not strictly required.

### 31.7 Pseudo-terminals

Hardwired CRT terminals may be nothing more than museum fodder these days, but their spirit lives on the form of pseudo-terminals. These pairs of device files emulate a terminal interface on behalf of such virtual consoles, virtual terminals (e.g., xterm), and network login services telnet and ssh.

Here's how Each of the paired device files accesses the same device driver inside the kernel. A process that would normally interact with a physical terminal, such as a shell, uses the slave device in a physical device such as /dev/ttyS0. A host process /dev/ptyp1 opens the master device—in example, the pseudo-terminal device driver shuttles keystrokes and text between the two devices, hiding the fact that no physical terminal exists.

Although pseudo-terminals don't need a baud rate or flow control strategy, most of the other attributes and settings covered in this chapter apply to them.

### The login process

The expect scripting language uses a pseudo-terminal to control a process (such as ftp or parted) that expects to interact with a human user. It is quite useful for automating certain types of sysadmin tasks.

### 31.8 CONFIGURATION OF TERMINALS

Cheap computers have replaced ASCII terminals. However, even the “terminal” windows on a graphical display (such as xterm) use the same drivers and configuration files as real terminals, so system administrators still benefit by understanding how archaic technology works.

Terminal configuration involves two tasks: making sure a process is attached to a terminal to accept logins, and making sure that information about the terminal is available once a user has logged in. Before we dive into the details of these tasks, let's look at the entire login process.

### The login process

The login process involves several programs, the most important of which is the init daemon. One of init's jobs is to spawn a process, generally called a getty (but not on Solaris, which calls it a tmon), on each terminal port that is turned on in /etc/tty or /etc/init file. The getty gets the port's initial characteristics (such as speed and parity) and prints a login prompt.

The actual name of the getty varies among Linux distributions, and some distributions include multiple implementations. Red Hat and SUSE use a simplified version called mingety to handle logins on virtual consoles. To manage terminals and dial-in modem, they provide Doert's getty implementation. Ubuntu uses a single getty by Wietse Venema et al.; this version called getty has largely been superseded by getty. Finally, HylaFAX (hylafax.org), a popular open source fax server, has its own version of getty faxget.

To distinguish this plenitude of getys, think of them in order of complexity: getty is the simplest and serves as a placeholder for a getty. It only handles logins on Linux virtual consoles. getty is a bit more well-rounded and handles serial ports and modems. getty is the current king of the day. It handles incoming fax as well and does proper locking and coordination so the same modem can be used as a dial-in and a dial-out line.

The sequence of events in a complete login is as follows:

- getty prints a login prompt (along with the contents of the /etc/issue file on Linux systems).
- A user enters a login name with getty's prompt.
- getty runs the login program with the specified name as an argument.
- login requests a password and validates the account against /etc/shadow or an administrative database system as NIS or LDAP.

- login prints the message of the day from /etc/motd and runs a shell.
- The shell executes the appropriate file.
- The shell prints a prompt and waits for input.
- When the user logs out, control returns to init, which wakes up and spawns a getty on the terminal port.

Files in /etc control the characteristics associated with each terminal. These include the presence of a login prompt, the baud rate, and the type of terminal that is assumed to be connected to the port. ### The /etc/ttype file

On many systems, terminal type information is kept in a file called /etc/ttype. The format of an entry in ttype is

```ttype device
```

where device is the short name of the device representing the port and the names in the termcap and terminfo database. When you log in, the TERM environment variable is set to the value of this field.

### The /etc/gettyab file

The gettyab file associates symbolic names such as std.9600 with port configurations that include parameters such as speed, parity, and login prompt. Here is a sample:

```
# The default entry, used to set defaults for other entries, and in cases
# where getty is called with no specific name.
default:line=\r\nlogin:sp=#9600
# Fixed-speed entries
std.9600-baud:sp=#9600
std.38400-baud:sp=#38400
```

The format is the same as that of printcap or termcap. The lines with names separated by a vertical bar (|) list the names by which each configuration is known. The other fields in an entry set are the options to be used with the serial port.

### The /etc/gettydefs file

Like gettydefs, getty defines port configurations used by getty. A given system will usually have one or the other, never both. The gettydefs file looks like this:

```
console# B9600 HUPCL B9600 SANE IXANY:login=#console
19200 B1900 HUPCL B19200 SANE IXANY:login=#9600
9600 HUPCL B9600 SANE IXANY:login=#4800
4800 B4800 HUPCL B4800 SANE IXANY:login=#2400
2400 B2400 HUPCL B2400 SANE IXANY:login=#1200
1200 B1200 HUPCL B1200 SANE IXANY:login=#300
300 B300 HUPCL B300 SANE IXANY TAB3:login=#9600
```

The format of an entry

```
label# initflags #finalflags #prompt #next
```

getty tries to match its second argument with a label entry. If called without a second argument, the first entry in the file is used. The initflags field lists ictal(2) flags that should be set on a port until login is used. The finalflags field sets flags that should be used thereafter.

There must be an entry that sets the speed of the connection in both initflags and the finalflags. The flags that are available vary by system; check the gettydefs or metodydefs page for authoritative information.

The prompt field defines the login prompt, which may include tabs and newlines in backslash notation. The next field gives the label of an initab entry that should be substituted for the current one if break is received.
