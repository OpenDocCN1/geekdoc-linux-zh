A ZFS “pool” is analogous to a “volume group” in other systems. Each pool is composed of “virtual devices,” which can be raw storage devices (disks, partitions, mirror groups, or RAID arrays). ZFS is similar in spirit to RAID 5 it uses one or more parity devices to provide redundancy for the array. However, ZFS calls the scheme RAID-Z and uses variable-sized stripes to eliminate the RAID 5 hole. All writes to the storage pool are striped across the pool’s virtual devices, so a pool that contains only individual devices is effectively an implementation of RAID 0, although the devices in this configuration are not required to be of the same size.

Unfortunately, the current ZFS RAID is a bit brittle you cannot add new devices to an array nor you permanently remove a device. In most RAID implementations, devices must be the same size; you can force ZFS to accept mixed sizes, but the size of the smallest dictates the overall size of the array. To use disks of different sizes efficiently in combination with ZFS, you must partition the disks ahead of time and define the leftover regions as separate devices.

Although you can turn over unpartitioned disks to ZFS's care, ZFS secretly writes a GPT-style partition table onto them and allocates all of each disk's space to its first partition. Most configuration and management of ZFS is done through two commands: **zpool** and **zfs**. We use zpool to build and manage pools and the entities created from pools, chiefly filesystems and raw volumes used as swap space and database storage.

# Storage: Example: Solaris disk addition

The first step is to link the disk and add it to a new storage pool:

```
solaris$ zpool create demo db1
```

Before we descend into the details of ZFS, let's start with a high-level example. Suppose you've added a new disk to your Solaris system and the disk has shown up as /dev/cdb1. The format command shows you a menu of the system's disks from which you can spot the disk. Step two is... ZFS labels the disk, creates the pool "demo", creates a filesystem inside that pool, and mounts that filesystem as /demo. The filesystem will be mounted automatically when the system boots.

```
solaris$ ls -a /demo
```

It would be even more impressive if we could simply add our new disk to the existing pool of the root, which is called "rpool" by default. The command would be sudo zpool add rpool db1. Unfortunately the root pool can only contain a single virtual device. Other pools can be extended in this manner, however.

# Filesystems and properties

It's for ZFS to automatically create a filesystem on a new storage pool because by default ZFS filesystems consume no particular amount of space. All filesystems live in a pool can draw from the pool's available space. Unlike traditional filesystems, which are independent of one another, ZFS filesystems are hierarchical and interact with their parent and child filesystems in various ways. You create new filesystems with zfs create.

```
solaris$ sudo zfs create demo/new_fs
solaris$ zfs list -r demo
NAME        USED AVAIL REFER MOUNTPOINT
demo        100K  488G  21K   /demo
demo/new_fs  19K   488G  19K   /demo/new_fs
```

The -r to zfs makes it recursive through child filesystems. Most other zfs subcommands understand -r, too. Very helpful, ZFS automounts the new filesystem as soon as we create it. To simulate traditional filesystems of fixed size, you can adjust the filesystem's properties to add a "reservation" (an amount of space reserved in the storage pool for the filesystem) and use a quota. This adjustment is one of the keys to ZFS management, and it's something of a paradigm shift for administrators who are used to other systems. Here, we set both values to 1GB:

```
solaris$ sudo zfs set reservation=1g demo/new_fs
solaris$ zfs set quota=1g demo/new_fs
solaris$ zfs list -r demo
NAME        USED AVAIL REFER MOUNTPOINT
demo        1.00G  487G  21K   /demo
demo/new_fs  19K   1024M  19K   /demo/new_fs
```

The new quota is reflected in the AVAIL column for /demo/new_fs. Similarly, the reservation shows up immediately in the USED column for demo. That's because the reservations of /demo's descendants are included in its size tally.

Both property changes are purely bookkeeping entries. The only change to the actual storage pool is the update of a block or to record the new settings. No process goes to format the 1GB of space reserved for /demo/new_fs. Most ZFS operations, the creating of new storage pools and filesystems, are lightweight. Using this hierarchical system of space management, you can easily group several filesystems to guarantee that collective size will not exceed a threshold; you do not need to specify limits on individual filesystems.

You must set the quota and reservation properties to properly emulate a fixed-size filesystem. The reservation alone simply ensures that the filesystem has enough room available to grow at least to that the quota limits the filesystem.

# Property inheritance

Many properties are naturally inherited by child filesystems. For example, if we wanted to mount the root of the demo pool in /opt/demo instead of /demo, we could simply set the mountpoint parameter:

```
solaris$ zfs set mountpoint=/opt/demo demo
solaris$ zfs list -d
NAME        USED AVAIL REFER MOUNTPOINT
demo        1.00G  487G  21K /opt/demo
demo/new_fs  19K   1024M  19K /opt/demo/new_fs
solaris$ ls /opt/demo
new_fs
```

Use zfs get to see the effective value of a particular property; zfs get dumps all. The SOURCE column tells you why each property has its particular value: local means the property was explicitly, and a dash means the property is read-only. If the property value is inherited from an ancestor filesystem, SOURCE shows the details of that inheritance as:

```
solaris$ zfs get all demo/new_fs
solaris$ zfs get all demo
NAME PROPERTY VALUE SOURCE
demo/new_fs type filesystem
demo/new_fs creation Wed Mar 17 17:50 2010
demo/new_fs available 1024M
demo/new_fs referenced 19K
demo/new_fs compressratio 1.0x
demo/new_fs mounted yes
demo/new_fs quota 1G local
demo/new_fs reservation 1G local
demo/new_fs mountpoint /opt/demo/new_fs inherited from demo
<many more, about 40 in all>
```
