
# Chapter 17 DNS: The Domain Name System

Configuring a slave server for a zone

The zone statement for a slave is similar to that of a master:

```
zone "domain_name" {
  type slave;
  file "path";
  masters { ip_addr [port ip_port] [key name]; ... }; [no default];
  allow-query { address_match_list };
}
```

Slave servers normally maintain a complete copy of their zone's database. The file statement specifies a local file in which the replicated data can be stored. Each time the server fetches a new copy of the zone, it saves the data in this file. If the server crashes and reboots, the file can then be reloaded from the local disk without being transferred across the network.

You shouldn't edit this cache file, since it's maintained by named. However, it can be interesting to look at it if you suspect you have an error in the master server's data file. The slave's disk file shows how named has interpreted the original zone data—relative names and origin directives all have been expanded. If you see a name in the data file that looks like one of these

```
128.134.243.151.cs.colorado.edu.
anchor.cs.colorado.edu.
```

you can be pretty sure that you forgot a trailing dot somewhere.

The masters lists the IP addresses of one or more machines from which the zone database can be obtained. It can also contain the name of a masters list defined with a previous masters statement.

We have said that only one machine can be the master for a zone, so why is it possible to list more than one address? Reasons, the first master might have more than one network interface and therefore more than one IP address. It's possible for one interface to become unreachable (because of network or routing problems) while others are still accessible. Therefore, it's a good practice to list all of the master's servers topologically distinct addresses.

Second, named really doesn't care where the zone comes from. It can pull the database just easily as a slave server as from the master. You could use this feature to allow a well-connected slave server as a sort of backup master, since the IP addresses are tried in order until a working server is found. In theory, you can also set up a hierarchy of servers, with one master serving several second-level servers, which in turn serve several third-level servers.

Setting the root server hints

Another form of zone statement points named toward a file from which it can preload its cache with the names and addresses of the root servers.

```
zone ". {
  type hint;
  file "path";
};
```

The "hints" are a set of DNS records that list servers for the root domain. They're needed to generate a recursive, caching instance of named a place to start searching for information about other sites' domains. Without them, named would leave you about the domains and their subdomains.

When named starts, it reloads the hints from one of the root servers. You'll be fine as long as your hints file contains at least one value, reachable root server. As a fallback, the root server hints are also compiled into named.

The hints file is often called root.cache. It contains the response you would get if you queried any root server for the name server records in the root domain. In fact, you can generate this file by running dig. For example:

```
$ dig @root-servers.net ns > root.cache
```

Mind the if.root-server is not responding, you can run the query without specifying a particular server:

```
$ dig ns > root.cache
```

The output will be similar; however, you will be obtaining the list of root servers from the cache of a local name server, not from an authoritative source. That should be just fine—even if you have not rebooted or restarted your name server for a year or two, it has been refreshing its root server records periodically as their TTLs expire.

Setting up a forwarding zone

A zone of type forward overrides named's default query path (ask the root first, then referrals as described on page 606) for a particular domain:

```
zone "domain_name" {
  type forward;
  forward only | first;
  forwarders { ip_addr, ip_addr, ... };
};
```

You might use a forward zone if your organization had a strategic relationship with some other group or company and you wanted to funnel traffic directly to that company's name servers, bypassing the standard query path.

# The controls statement for rndc

The controls statement limits the interaction between the running named process and rndc, the program a sysadmin can use to signal and control it. rndc can start and stop named, dump its state, put it in debug mode, etc. rndc is a network program, and with improper configuration it might let anyone on the Internet mess with your name server. The syntax is

```
controls {
  inet_addr port ip-port allow { address_match_list } keys { key_list };
}
```

The port that rndc uses to talk to named defaults to 953 if it is not specified with the port clause.

Allowing your name server to be controlled remotely is both handy and dangerous. Strong authentication through a key entry in the allow clause is required; keys in the address match list are ignored and must be explicitly stated in the keys clause of the controls statement.

You can use the rndc-command to generate an authentication key for you between rndc and named. There are essentially two ways to set this up: you can use the same file for both rndc and named, or you can include the key in named.conf. The latter is more complicated, but necessary when rndc is used from localhost. When controls statement is present, you can use the 127.0.0.1 address for the allow list. This precaution may seem draconian, but it's necessary if rndc is used from the outside.

Here is an example of the lines you need to add to named.conf:

```
controls {
  inet_addr 127.0.0.1 port 953 allow { 127.0.0.1; } keys { rndc-key; };
}
```

The key "rndc-key" is generated using the command:

```
$ rndc-control generate rndc-key
```

The output will show the key, which should then be placed in the rnd.conf and named.conf files.
