# Local domain sockets

Sockets are connections between processes that allow processes to communicate hygienically. UNIX defines several kinds of sockets, most of which involve the use of a network. Local domain sockets are accessible only from the local host and are referred to as a filesystem object rather than a network port. They are sometimes known as “UNIX domain sockets.”

Unlike files visible to other processes as directory entries, they cannot be read from or written to processes not involved in the kernel. Syslog and the X Window System are examples of standard facilities that use local domain sockets.

Local domain sockets are created with the socket system call and removed with the rm command or the unlink system call once they have no more users.

# Named pipes

Like local domain sockets, named pipes allow communication between two processes running on the same host. They're also known as “FIFO files” (FIFO is short for the phrase “first in, first out”). You can create named pipes with mkknod and remove them with rm.

As with local domain sockets, real-world instances of named pipes are far and between. They rarely require administrative intervention.⁵

Named pipes and local domain sockets serve similar purposes, and the fact that both exist is essentially a historical artifact. Neither of them would exist if UNIX and Linux were designed today; network sockets would stand in for.

# Symbolic links

A symbolic or “soft” link points to a file name. When the kernel comes upon a symbolic link in the course of looking up a pathname, it redirects its attention to the pathname stored as the contents of the link. The difference between hard links and symbolic links is that a hard link is a direct reference, whereas a symbolic link is a reference by name. Symbolic links are distinct from the files they point to.

You create symbolic links with ln -s and remove them with rm. Since symbolic links can contain arbitrary paths, they can refer to other filesystems or nonexistent files. Multiple symbolic links can also form a loop.

A symbolic link can contain either an absolute or a relative path. For example $ sudo ln -s archived/secure/var/log/secure links /var/log/secure to /var/log/archived/secure with a relative path. It creates the symbolic link /var/log/secure with a target of “archived/secure”, as demonstrated by this output from ls:

```
$ -ls /var/log/secure
lrwxrwxrwx 1 root root 18 2019-07-05 12:54 /var/log/secure -> archived/secure
```

The entire /var/log directory could be moved elsewhere without causing the symbolic link to start working (not moving this directory is advisable).

It is a common mistake to think that the first argument to ln -s is interpreted relative to your current working directory. However, it is not resolved as a filename by; it's simply a literal string that becomes the target of the symbolic link.

# 6.5 File Attributes

Under the UNIX and Linux filesystem model, every file has a set of nine permission bits that control who can read, write, and execute the contents of the file. With three other bits that affect the operation of executable programs, these bits constitute the file “mode”.

The twelve mode bits are set together with four bits of file-type information. The four file-type bits are set when the file is first created and cannot be changed, but the file’s owner and the supervisor can modify the mode bits with the chmod (change mode) command. Use ls -l (or ls -ld for a directory) to inspect the values of these bits. An example is given on page 154.

# The permission bits

Nine permission bits determine what operations may be performed on a file and by whom. Traditional UNIX does not allow permissions to be per-user-(although all systems support access control lists of one sort or another; page 159). Instead, three sets of permissions define access for the owner of the file, the group owners of the file, and everyone else (in that order). Each has three bits: a read bit, a write bit, and an execute bit (also in order).

It’s convenient to discuss permissions in octal (base 8) numbers because each digit of an octal number represents three bits and each group of permission bits consists of three bits. The topmost three bits (with access values of 400, 200, and 100) control access for the owner. The second (40, 20, and 1) control access for every-one (“the world”). The last three (4, 2, and 1). In each triplet, the high bit is the read bit, the middle is the write bit, and the low bit is the execute bit.

# The setuid and sidgid bits

Each user fits into only one of the three permission sets. The permissions used are those that are most specific. For example, the owner of a file has access determined by the owner permission bits and never the group permission bits. It is possible for the "other" and "group" categories to have more access than the owner, although this configuration would be highly unusual.

On a regular file, the read bit allows the file to be opened and read. The write bit allows the contents of the file to be modified or truncated; however, the ability to delete or rename (delete and recreate!) the file is controlled by the permissions on its parent directory because that is where the name-to-dataspace map is stored.

The execute bit allows the file to be executed. Two types of executable files exist: binaries, which the CPU runs directly, and scripts, which must be interpreted by a shell or some other program. By convention, scripts begin with a line similar to

```
#!usr/bin/perl
```

that specifies an appropriate interpreter. Nonbinary executable files that do not specify an interpreter are assumed to be bash or sh scripts.

For a directory, the execute bit (often called the "search" or "scan" bit in this context) allows the directory to be entered or passed through while a pathname is evaluated, but not to have its contents listed. The combination of read and execute bits allows the contents of the directory to be listed. The combination of write and execute bits allows files to be created, deleted, and renamed within the directory.

A variety of extensions such as access control lists (see page 159), SELinux (page 923), and "bonus" permission bits defined by individual filesystems (see 158) complicate or override the traditional nine-bit permission model. If you're having trouble explaining the system's observed behavior, check to see which one of these factors might be interfering.

# The setuid and sidgid bits

The bits with octal 4000 and 2000 are the setuid and sidgid bits. When set on executable files, these bits allow programs to access files and processes that would otherwise be off-limits to the user they run. The setuid/sidgid mechanism for executables is described on page 105.

When on a directory, the setgid bit causes newly created files within the directory to take the ownership of the directory rather than the default group of the user who created the file. This connection makes it easier to share a directory among several users, as long as they belong to a common group. The interpretation of the setgid bit is unrelated to its meaning when set on an executable, but no ambiguity can exist as to what is meaning appropriate.
