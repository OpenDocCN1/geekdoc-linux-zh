# The root account

For example:

```
ls -l /home/garth/todo
rw-r------ 1 garth staff 1258 Jun 4 18:15 /home/garth/todo
This file is owned by the user garth and the group staff. The letters and dashes in
the first column symbolize the permissions on the file; see page 154 for details
how to read this information.
```

Both the kernel and the filesystem track owners and groups as numbers
an than names. In the most basic case, user identification (UIDs for
short) are mapped to usernames in the /etc/passwd file, and group identification
numbers (GIDs) are mapped to groups in /etc/group. The text names that
correspond to UIDs and GIDs are defined only for the convenience of the system's
human users. When commands as ls want to display ownership information
in a human-readable format, they must look up each name in the appropriate file
or database.

# Process ownership

The owner of a process can send the process signals (see page 124) and can also
reduce (degrade) the process's scheduling priority. Processes actually multi-
ities associated with them: a real, effective, and saved UID; a real, eff-
saved GID; and under Linux, a "filesystem UID" that is used only to
determ access permissions. Broadly, the real numbers are used
for accounting and the effective numbers are for the determination of access
permissions. The real and effective numbers are normally the same.

Saved UIDs have no direct effect. They allow programs to park an inactive ID for
later, utilizing the parsimonious use of enhanced privileges. The filesystem
UID is generally explained as an implementation of NFS and is usually the
same as the effective UID.

# The root account

The root account is UNIX's omnipotent administrative user. It's also known as the
superuser account, although the actual user is "root".

The defining characteristic of the root account is its UID of 0. Nothing prevents
you changing the username on it or from creating additional ac-
counts UIDs are 0; however, these are bad ideas. Such changes have
tendency to create inadvertent breaches of system security. They also create-
usion other people have to deal with the strange way you configured
your system.

Traditional UNIX allows the superuser (that is, any process whose effective UID
is 0) to perform any valid operation on any file or process.²

+   2. "Valid" is the order used here. Certain operations (such as executing a file on which the execute
permission bit is not set) are forbidden even to the superuser.
