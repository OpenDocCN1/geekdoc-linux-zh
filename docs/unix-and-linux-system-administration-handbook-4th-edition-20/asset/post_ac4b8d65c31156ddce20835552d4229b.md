# OSSEC: host-based intrusion detection

Do you lie awake at night wondering the security of your systems has been breached? Do you have a disgruntled coworker installing malicious programs on your systems? If you answered to either of these questions, you may want to consider installing a host-based intrusion detection system (HIDS) such as OSSEC.

OSSEC is free and available as source code under the GNU General Public License. Commercial support is available from Third Brigade (recently acquired by Trend Micro). OSSEC is available for Linux, Solaris, HP-UX, AIX, and Windows. It provides the following services:

- Rootkit detection
- Filesystem integrity checks
- Log file analysis
- Time-based alerting
- Active responses

OSSEC runs on the systems of interest and monitors their activity. It can send alerts or take action according to a set of rules you configure. For example, OSSEC can monitor systems for the addition of unauthorized files and send email notifications like this one:

> Subject: OSSEC Notification - courtesy - Alert level 7
Date: Fri, Jan 15 2010 14:53:04-0700
From: OSSEC HIDS <ossecm@atrust.com>
To: <courtesy-admin@atrust.com>

OSSEC HIDS Notification.
2010 Jan 15 14:52:52

Received From: courtesy->syscheck
Rule: 554 fired (level 7) -> "File added to the system."
Portion of the log(s):

New file
'/courtesy/http/barkingseal.com/html/wp-content/2010/01/hbird.jpg'
added to the file system.

--END OF NOTIFICATION

In this way, OSSEC acts as your 24 eyes and ears on the system. We recommend running OSSEC on every production, in combination with a change management policy (discussed in Chapter 32, Management, Policy, and Politics, on page 1211).

# OSSEC basic concepts

OSSEC has two primary components: the manager (server) and the agents (clients). You need one manager on your network, and you should install that one component first. The manager stores the file-integrity-checking databases, logs, events, rules, decoders, may configuration options, and auditing entries for the entire network. A manager can connect to any OSSEC agent, regardless of its operating system. The manager can also monitor devices that do not have a dedicated OSSEC agent.

Agents run on the systems you want to monitor and report back to the manager. By design, they have a small footprint and operate with minimal set of privileges. The agent's configuration is obtained from the manager. Communication between the server and the agent is encrypted and authenticated. You need to create an authentication key for each agent on the manager.

OSSEC classifies alerts by severity at levels 0 to 15; 15 is the highest severity.

# OSSEC installation

OSSEC is not yet part of the major UNIX and Linux distributions, as a fetch package. Therefore, you will need to download the source code package with a web browser or a tool such as wget and then build the following:

```
$ wget http://ossec.net/files/ossec-hids-latest.tar.gz
$ tar -xvf ossec-hids-latest.tar.gz
$ cd ossec-hids-
$ sudo ./install.sh
```

The install script asks what language you prefer (use "en" for English), and then what type of installation you want to perform: server, agent, or local. If you are only installing OSSEC on a single, personally managed system, you may want to choose local. Otherwise, first do the server install on the system you want to be on that and all other systems you want to monitor. The install script asks some additional questions, such as to which email address alerts should be sent and which monitoring modules should be enabled.

# OSSEC configuration

Once the installation has finished, start OSSEC with
server$ sudo /var/ossec/bin/ossec-control start

Next, register each agent with the manager. On the server, run
server$ sudo /var/ossec/bin/manage_agents

You'll see a menu that looks something like this:

* * OSSEC HIDS v2.3 Agent manager.
* The following options are available:

(A)dd an agent (A).
(E)xtract key for an agent (E).
(L)ist already added agents (L).
(R)remove an agent (R).
(Q)uit.
Choose your: A,E,L,R or Q:

Select option A to add an agent, then type the name and IP address of the agent. Next, select option E to extract the agent's key. Here's what that looks like

Available agents:
ID: 001, Name: linuxclient1, IP: 192.168.74.33
Provide the ID of the agent to extract the key (or '\^q' to quit): 001
agent key for '001' is:
MDAYGlxbpnV4Y2xpZW50MSAsXOtuMTU0Yj4cJMgZjk4YMyYzZlkMkg5MWJMT

Finally, log in to the system and run manager_agents there:
agent$ sudo /var/ossec/bin/manage_agents

On the client, you will see the menu has somewhat different options.

* * OSSEC HIDS v2.3 Agent manager.
* The following options are available:

(I)mport key from the server (I).
(Q)uit.
Choose your action: I or Q:

Select option I and then cut and paste the key you extracted. After you added an agent, you must restart the OSSEC server.

Once OSSEC is installed and running, you'll want to tweak it so that gives you enough information, but not too much. The majority of the configuration is stored on the server in the /ossec/etc/ossec.conf This XML-style file is well commented and fairly intuitive, it contains dozens of options.

A common item you may want to configure is the list of files to ignore when doing file integrity checking. For example, if you have a custom application that writes its log file to /var/log/customapp.log, you can add the following line to the <syscheck> section of the file:

```
<syscheck>
<ignore>/var/log/customapp.log</ignore>
</syscheck>
```

After you've made this change and restarted the OSSEC server, OSSEC will stop alerting you every time the log changes. The new OSSEC configuration options are documented at ossec.net/manual/configuration.

It takes time and effort to get your HIDS system running. After a few weeks, you've filtered out the noise and the system will start to provide valuable information about changing conditions in your environment.

## 22.9 MANDATORY ACCESS CONTROL (MAC)

Mandatory Access Control is an alternative to the traditional UNIX access control system that controls all permissions in the hands of a security administrator. In contrast to the standard model (described in Chapter 4, Access Control and Root Powers, and to some extent in Chapter 6, The Filesystem), MAC does not allow users to modify permissions, even on their own objects.

MAC security policies control access according to the perceived sensitivity of the resource being controlled. Users are assigned a security classification to a structured hierarchy. Users can read and write items at a higher classification level or cannot access items at a higher classification. For example, a user with "secret" can access and write "secret" objects but cannot read objects that are classified as "top secret."

Needless to say, kernel modifications are necessary to implement MAC on UNIX and Linux. Our example UNIX systems (Solaris, HP-UX, and AIX) are all available in MAC-enabled versions at additional cost. These versions are called Solaris Trusted Extensions (formerly Trusted Solaris), HP-UX Security Containment, and Trusted AIX, respectively.

Unless you're handling sensitive data for a government entity, it is unlikely that you will ever need or encounter these security-enhanced editions.
