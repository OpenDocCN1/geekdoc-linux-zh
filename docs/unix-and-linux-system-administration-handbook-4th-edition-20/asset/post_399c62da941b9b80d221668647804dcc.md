## 2 FILESYSTEM MOUNTING UNMOUNTING

The filesystem is composed of smaller chunks—each consisting of one directory and its subdirectories and files. It's normally apparent from context what type of "filesystem" is being discussed, but for clarity in the following discussion, we use the term "file tree" to refer to the overall layout and reserve the word "filesystem" for the chunks attached to the tree.

Most filesystems are disk partitions or disk-based volumes, as we mentioned earlier, they can be anything that obeys the proper API: network file servers, kernel components, memory-based disk emulators, etc. Linux and Solaris even have a "loopback" filesystem that lets you mount individual files as if they were distinct devices. It's great for developing filesystems without having to worry about partitioning your disks.

In most situations, filesystems are attached to the tree with the mount command. mount maps a directory within the file tree, the mount point, to the newly attached filesystem. The previous contents of the mount point become inaccessible as long as another filesystem is mounted. Mount points are usually empty directories, however.

For example,

```
$ sudo mount /dev/sda4 /users
```

installs the filesystem stored on the disk partition by /dev/sda4 under the path /users. Then you could use /users to see your contents.

A list of filesystems that are customarily on a particular system is kept in the /etc/fstab, /etc/vfstab (Solaris), or /etc/filesystems (AIX) file.

You detach filesystems with the unmount command. unmount complains if you try to unmount a filesystem that is in use; the filesystem to be detached must not have open files or processes whose current directories are located there, and if the filesystem is currently executing executable programs, they cannot be running.

Linux has a "lazy" unmount option (unmount -l) that removes a filesystem from the hierarchy but does not truly unmount it until all file references have been closed. It is debatable whether this is a useful option. To begin, with no guarantee that existing references will ever close on their own. In addition, the "semi-unmounted" state can prevent inconsistent filesystem semantics to the processes that are using; they can read and write through existing files but cannot open new files or perform other filesystem operations.

unmount -f force-uns a busy filesystem and is supported on all our examples. However, it's almost always a bad idea to use it on Non-MFS nodes, and it may not work on certain types of filesystems (e.g. those that keep journals, as ext3 or ext4).

Instead of reaching for unmount -f when a filesystem you're trying to unmount turns to be busy, run the fuser command to find which process holds references to that filesystem. fuser -c finds the PID of every process using a file or directory on that filesystem, plus a series of letter codes that show the nature of the activity: For example,

```
$ fuser -c /usr
/usr: 157 315 474 509 844 996 902 358 484
```

The exact letter code varies from system to system. Table 6.1 summarizes the meanings of the codes, but the details are usually unimportant; the PIDs that you want.

### Table 6.1 Activity codes shown by fuser -c

| Codes | Meaning |
| :--- | :--- |
| f,o | The process has a file open for reading or writing. |
| c | The process's current directory is on the filesystem. |
| e,t | The process is currently executing a file. |
| r | The process's root directory (set with chroot) is on the filesystem. |
| m,s | The process has mapped a file or shared library. |

To investigate offending processes, just run ps with the list of PIDs returned by fuser. For example,

```
$ ps -fp "157 315 474 509 844 996 902 358 484"
UID PPID C TTY TIME CMD
root 509 0 Oct 14 0:00 /usr/bin
root 157 1 Jun 27 0:00 /usr/sbin
root 315 1 Jun 27 0:00 /usr/lib
```

Here, the quotation marks force the shell to pass the list of PIDs to ps as a single argument. On Linux systems, you can avoid the PIDs through ps by running fuser with the -v flag. This option produces a more readable display that includes the command name.

```
$ fuser -cv /usr
USER PID ACCESS COMMAND
root 444 .. atd
root 499 .. sshd
root 520 .. lpd
```

The letter codes in ACCESS column are the same used in fuser's verbose output. A more elaborate alternative to fuser is lsof. lsof is more complex and sophisticated program than fuser, and it is available from people.freebsd.org and works on all systems. Under Linux, scripts in search of specific information about processes can read the files in /proc directory.

## 6.3 THE ORGANIZATION OF THE FILE TREE

Filesystems in the UNIX family have never been well organized. Incompatible naming conventions are used simultaneously, and different types of files are scattered randomly around the namespace. In many cases, files are divided by function and not by how likely they are to change, making difficult to upgrade the operating system. The /etc directory, for example, contains some files that are never customized and some that are entirely local. How you know which files to preserve during the upgrade? Well, you have to know...

Despite incremental improvements over the years (such as the designation of /var as a place to store system-specific data), UNIX and Linux systems are still pretty much a disorganized mess. Nevertheless, there's a correct place for everything. Most software can be installed with little reconfiguration if system is set up in a standard way. If you try to improve upon the default structure, you are also asking for trouble.

See Chapter 13 for more information about configuring the kernel.

The root filesystem includes the root directory and a minimal set of files and subdirectories. The file that contains the OS kernel usually lives somewhere within the root filesystem, but in Solaris, it is not even a single file so a set of components.

Also part of the root filesystem are /etc for system and configuration files, /sbin and /bin for important utilities, and sometimes /tmp for temporary files. /dev is a real directory that's included in the root filesystem, but some or all of it may be overlaid with other filesystems if your system has virtualized device support. (See page 419 for more information about this topic.)

Some systems kept shared library files and a few other things such as the C preprocessor in the /lib directory. Others have moved these into /usr/lib, sometimes as a symbolic link.

See page 231 for reasons why partitioning might be desirable and some rules of thumb to guide it.

The directories /usr and /var are also of great importance. /usr is where most standard programs are kept, along with other stuff such as on-line manuals and most libraries. It is not strictly necessary that /usr be a separate filesystem, but for convenience in administration it is often. Both /usr and /var must be available to the system to come up all the way to multiuser.

/var stores directories, files, accounting information, and other items that grow rapidly and vary on each host. Since /var contains log files, which are apt to grow in times of trouble, it's a good idea to put /var on its own filesystem if that is practical.

Home directories of users are often kept on a separate filesystem, usually one that's mounted in the root directory. Dedicated filesystems can also be used to store bulky items such as source code libraries and databases.

### Table 6.2 Important directories

| Directory | Description |
| :--- | :--- |
| / | the root of the entire file tree |
| /etc | system and configuration files |
| /sbin, /bin | essential system binaries and utilities |
| /tmp | temporary files |
| /dev | device files |
| /usr | standard programs, manuals, and libraries |
| /var | variable data (logs, accounting) |
| /home | user directories |
| /proc | process information (virtual filesystem) |
| /lib | shared libraries |
