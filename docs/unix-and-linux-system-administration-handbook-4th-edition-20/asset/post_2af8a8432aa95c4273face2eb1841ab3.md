```bash
$ svn checkout --username tobi //server.trust.com/admin checkout
```

Authentication realm: `<svn://server.trust.com:3690>` The Sysadmin Repository Password for 'tobi': `<password>`

When you enter the password for the first time, Subversion squirrels away a directory that it creates in your home. To add or move files within your local copy of the project, use the **svn** command:

```bash
$ cd checkout
$ vi foo.c
$ svn add foo.c
```

Once you are done, commit your changes to the repository:

```bash
$ svn commit -m "Initial checkin; added foo.c"
```

It is not necessary to list the files you want to commit, although you can do if you wish; **svn** will figure it out on its own. If you omit the **-m** option, **svn** starts an editor for you so that you can edit the commit message.

To get the latest updates from the repository, run **svn update** in the project. Subversion performs a merge operation on any files that have been modified in both your local copy of the project and the master repository. Files with unresolved conflicts are marked as "conflicted," and Subversion does not allow you to check them in until you have fixed the problems and told Subversion that the conflicts have been resolved:

```bash
$ svn resolved foo.c
```

If you want to know who has changed which lines in a file, you can ask **svn blame** to dish out the blame:

```bash
$ svn blame bar.c
```

This command prints an annotated version of the file that shows when and by whom each line was last modified. (Those of a more forgiving or optimistic nature can use the synonym **svn praise**.) It's also easy to get diffs relative to a particular date or version. For example, if you want to know what has changed in foo.c since July 4, 2010, the following command will tell you:

```bash
$ svn diff -r "2010-07-04" foo.c
```

You can download the latest version of Subversion from tigris.org. The standard documentation is the book Version Control with Subversion, published by O'Reilly. The full text is available online at svnbook.red-bean.com.

# Git

The catch with Git is that it has no central repository. Instead of checking out a particular version of a project's files, you simply copy the repository (including its entire history) and carry it with you like a hermit crab shell. Your commits to the repository are local operations, so they're fast and you don't have to worry about communicating with a central server.

Git uses an intelligent compression system to reduce the cost of storing the entire history, and in most cases this system is quite effective. In many cases, working requirements for storage space are even lower than with Subversion.

Git is great for developers because you can pile their code onto a laptop and work without being connected to a network while still making all of the benefits of version control. When the time comes to integrate multiple developers' work, their changes can be integrated from one copy of the repository to another in any fashion that suits the organization's workflow. It is always possible to unwind copies of a repository back to their common ancestor state, no matter how many changes and iterations have occurred after the split.

Git's promiscuous copying-branching strategy isn't relevant to the context of system administration, but its use of a local repository is a big leap forward for system administrators—or perhaps more accurately, is a big leap backward, in a good way. Early version control systems (e.g., RCS and CVS) used local repositories but were unable to handle collaboration, merging, and independent development. Now we've come full circle to a point where putting under control is a fast, simple, local operation. At the same time, all of Git's advanced collaboration features are available for use in situations that require them.

Before you start Git, set your name and email address:

```bash
$ git config --global user.name "John Q. Ulsah"
$ git config --global user.email "ulsah@book.admin.com"
```

To garden-variety changes to configuration files, you'll generally want to use in-situ repositories that are never duplicated and therefore never need to be reconciled or integrated. This convention makes the Git wrangling pretty simple, but

since commits will be done as root, it's important to make sure that all commit messages are clear. To avoid confusion, we use git status.

To avoid these blocks, run git status and assess the situation manually. For example, suppose we edited /etc/mdadm.conf as in the previous example and also installed a new system daemon, daemon. Git status may show the following:

```bash
$ git status
# On branch master
# Changed but not updated:
# (use "git add <file>") to update what will be committed
# modified: mdadm/mdadm.conf
# modified: mtab
# modified: password
# Untracked files:
# (use "git add <file>") to include in what will be committed
# daemon/
# no changes added to commit (use "git add" and/or "git commit -a")
```

The daemon.conf is not listed by name because Git does not yet see the directory it contains. We can see that both mtab and password have changes. The mtab changes are spurious, but the password changes might or not be. Perhaps the install script for daemon created a system account for it, or perhaps someone else edited the password and forgot to commit their changes to the repository.

To resolve the question, you can run git diff password to see the actual changes in the password file. Let's assume that in this case the password changes are unrelated to our recent activities. Therefore, we'll probably want to check in these changes separately:

```bash
$ git commit password -m "Checking in existing password changes"
Created 6f7853c: Checking in existing password changes
1 files changed, 1 insertion(s), 0 deletions(-)
```

We can make Git ignore the mtab file, now and forever; however, though two steps are required. We'll "delete" mtab from the current repository image:

```bash
$ git rm --cached mtab
rm 'mtab'
```

The --cached option prevents Git from actually deleting the mtab file, so don't leave it out! In essence, we're stuffing a virtual deletion operation into Git's staging area. Git will behave as if we had deleted the file with rm.

The second step to eradicating mtab from Git's universe is to add it to Git's list of files to ignore in the future. That is by creating or editing a .gitignore file.
