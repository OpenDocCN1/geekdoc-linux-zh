The username option specifies the unprivileged user as whom unbound should run once it has completed its startup housekeeping. You will have to jump through some hoops to make sure that everything unbound is available from the jail directory, but recent versions of the code make this pretty easy.

The code is smart about mapping global paths in the chrooted world. Most paths can be specified as absolute global paths, as paths within the jail directory, or as paths to the working directory. unbound performs the appropriate mapping when necessary.

A couple of points about running unbound in jail: Running the config file of course prepares the chroot, so the config file specified on unbound's command should be a global path. The PID file, the unbound-control key files, and the syslog can all remain outside the jail directory because they are opened before unbound performs its chroot.

unbound reads /dev/random before chroot, but it's still a good idea to make /dev/random available after the chroot; unbound may need to return to it to obtain more data. If unbound cannot reach /dev/random, it uses a default source of randomness and logs a warning message.

Under Linux, you can make /dev/random available in the jail with the following invocation (which assumes that var/unbound is your jail directory):

```
linux$ sudo mount --bind -n /dev/random /var/unbound/dev/random
```

unbound has several options that control the interfaces which it listens for queries and the port numbers used for receiving and sending queries. The defaults are for most sites and are not vulnerable to Kaminsky-type cache poisoning attacks. However, the interface and outgoing-port-avoid options should be configured explicitly.

The interface option specifies the interfaces which listens for queries. It needs to be set explicitly as the default is localhost—if every machine runs unbound, but not so fine if you run one server per subnet or site. Add an interface statement for each interface on which clients might try to submit queries.

You should also configure outgoing-port-avoid to exclude any ports that are blocked by your firewall and all ports used by another program. unbound excludes ports below 1,024 and IANA-assigned ports.

These options all deal with DNSSEC deployment; they allow you to trust anchors by listing the files they live in or by tuning the resource record directly into the option's value. There can be at most one DLV anchor.

Setting module-config: validator iterator turns on DNSSEC validation and must be accompanied by trust anchors, either explicitly configured or via DL. See DNSSEC on page 648 for more info.

Signatures

val-*:<various> [signature options, defaults are ok]

The val-* series of options deal with the validation process for signatures of zones. They involve various parameters (such as maximum permissible clock skew) that can affect validation. The default values are fine unless you are debugging your DNSSEC deployment. Setting val-log-level to 1 logs failures, which is also helpful for debugging.

Tuning

unbound supports several performance-tuning options. An important one is num-threads, which should be set to the number of cores available on the server (i.e., the number of cores per processor times the number of processes).

The tuning defaults are for most sites, so rather than list them all here, we refer you to the man page for unbound.conf and the how-tos at unbound. Toward end of the page is a helpful example that tunes performance on a small-memory machine.

Private addresses
private-address: ip-address-or-subnet [none]
private-domain: domain-name [none]

The private-address statement blocks the listed IP addresses from being returned in query results. It's normally in conjunction with RFC1918 private IP addresses (see page 462) to keep shameful addresses from escaping to the Internet. This behavior is generally what you want for external sites, but if you are actually using RFC1918 addresses, you probably don't want to blacklisting your own internal addresses. The private-domain statement resolves this conflict by allowing the specified domain and all its subdomains to contain private addresses.

The next set of configuration options pertains to the forwarder, which controls communication between unbound and another server. There are a few options:

- control-enable: yes | no [no]
- control-interface: ip-address [localhost]
- control-port: number [53]
- control-key: filename [none]
- control-cert: filename [none]

The forward-zone option allows you to use a forwarder. If you specify the name as . (a single period), all queries are forwarded. See page 569 for general information about forwarders and why you might want to use them. Forwarding occurs only if unbound cannot answer a query from its cache. To implement this, set the control-enable to yes, and the control-interface to the network. This depends on your software.

If you have the notify option turned off, you can force BIND slaves to update themselves by running rndc reload on each. This command makes the slave check with the master, see that the data has changed, and request a zone transfer. The corresponding NSD command is nsdc reload.

# 17.12 UPDATING ZONE FILES

To change a domain's data (e.g., to add or delete host), you update the zone files on the master server. You must also increment the serial number in the SOA record. Finally, you must get your name server software to pick up and distribute your changes. This final step varies depending on your software:

- BIND: Run rndc reload to signal named to pick up the changes. You can also kill and restart named, but if your server is authoritative for your zone and recursive for your users, this operation discards cached data from other domains.
- NSD: Run ndsc rebuild, followed by nsdc reload. nsd does no caching, so it is not affected by being restarted.

Updated zone data is propagated to servers of BIND masters right away because the notify option is by default. In NSD, you must configure the notify ACL to get this (desired) effect. If notifications are not turned on, your servers will not pick up the changes until refresh seconds, and in the zone's SOA record (typically an hour later).

Don't forget to modify both the forward and reverse zones when you change a hostname or IP address. Forgetting the reverse files leaves sneaky errors: some commands work and some won't.
