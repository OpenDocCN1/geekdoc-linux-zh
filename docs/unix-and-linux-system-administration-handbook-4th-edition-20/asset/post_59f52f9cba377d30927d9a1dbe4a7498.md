
# Chapter 11 Syslog and Log Files

AIX-specific diagnostics and on a custom-configured syslog for centralized application logs.

**errdemon** starts at system boot in /etc/rc.bootc and reads error events from the special file /dev/error. Both the kernel and some AIX user applications errors to this file according to predefined templates in /dev/adm/ras/errmplt. **errdemon** compares new entries to the templates and writes the output in a binary format to the file /var/adm/ras/errlog. AIX loves binary formats!

**errlog** is a circular file, so it overwrites the first event with the most recent when the file reaches its maximum size, 1MB by default. **errdemon** also buffers events that haven't been written to the log. The settings can be viewed or adjusted by running /usr/lib/errdemon directly. See the man page for invocation details.

Because errpt is not a text file, use another proprietary tool called **errpt** to read its contents. Without any arguments, *errpt* prints a list of all events in the log in a short form. Add the -a argument for detailed output. A sample entry from our AIX systems looks like this:

```
aix errpt -a
```

Although errdemon is a useful source of log data on a stand-alone AIX system, you can interfere with a more broadly defined enterprise logging strategy. You may have to do some scripting to capture errdemon in syslog format or to forward them for central archiving. IBM's extensive on-line documentation also shows how to send error reports to syslog through the Object Data Manager.

You may need to delete entries from the error logs, and IBM provides the errclear command for this purpose. errclear deletes messages older than the number of days specified as an argument. For example, errclear 7 deletes error messages older than one week.

Run errclear 0 to clear all error messages or errclear -j identifier 0 to clear a specific message.

# Syslog configuration under AIX

By default, AIX's syslog.conf file consists of a long list of commands and no configuration data. It's up to the system administrator to configure syslog with settings on other systems.

Always the renegade, AIX provides a native log rotation facility within syslog. Logs can be rotated at regular intervals or rotated when they reach a size. They can be optionally compressed and archived to a new location. Although we appreciate the convenience of these features, they cannot manage files outside syslog's control, as logs that are generated by non-syslog-aware applications. To implement comprehensive log management, you will probably need a combination of the native syslog rotation features and one of the tools covered later in this chapter.

To replicate a Linux-style syslog configuration, append the following lines to /etc/syslog.conf and run refresh -s syslog. Don't forget to use tabs in places of spaces to create each file in device.

```
mail.debug      /var/log/mail
user.debug      /var/log/user
kern.debug      /var/log/kern
syslog.debug    /var/log/messages
daemon.debug    /var/log/daemon
auth.debug      /var/log/secure
local2.debug   /var/log/sudo
```

You may specify log rotation in syslog.conf by appending the term rotate to the end of a configuration file. Logs can be rotated when they reach a file size or after a given time increment. If you set both size and time constraints, syslog rotates the file as soon as either criterion is met. Furthermore, files can be compressed or archived to a new location. Table 11.6 summarizes these options.

## **Table 11.6** log rotation options in syslog.conf

| Option | Meaning |
| --- | --- |
| rotate size N[km]ᵃ | Indicates that the specified file should be rotated Rotates when the file reaches the specified sizeᵇ |
| files time N[hdwmy]ᶜ | Keeps the number of versions in rotation Rotates after the specified time interval has elapsed |
| compress archive location | Compresses the rotated file with **compress** Moves the rotated file to location |

ᵃ. k = kilobytes, m = megabytes\ᵇ. There must be no space between N and the unit. For example, 3m is correct, but 3 m is not.
ᶜ. h = hours, d = days, w = weeks, m = months, y = years

For example, here are **syslog.conf** configuration lines from the previous example that have been expanded to include rotation options:

- # Rotate at 500MB, keep 4 files
  mail.debug /var/log/mail rotate size 500m files 4
- # Rotate after 1 week, keep 10 files, compress the file
  user.debug /var/log/user rotate files 10 time 1w compress
- # Rotate after 100KB or 2 months, whichever occurs first, keeping 4 files
  kern.debug /var/log/kern rotate size 100k 4 files 2m
- # Keep 1 week of weekly logs, compress the file, move the file to /logs
  syslog.debug /var/log/messages rotate files 52 time 1w compress archive

# 11.4 LOGROTATEATE: MANAGE LOG FILES

Erik Trojan's excellent logrotate utility implements a variety of log management policies and is standard on all example Linux distributions. It also runs on Solaris, HP-UX, and AIX, which you have to install. We prefer logrotate to the inferior **logadm** package that comes with Solaris.

A **logrotate** configuration file consists of a series of specifications for groups of log files to be managed. Options that appear outside the context of a log specification (such as *errors*, *rotate*, and *weekly* in the following example) apply to all following specifications. They can be overridden within the file and also be specified later in the file to modify the defaults.
Here's a somewhat contrived example that handles several different log files:

- # Global options
  errors errors@book.admin.com
  rotate 5
  weekly

# logrotate: manage log files

```
# Logfile rotation definitions and options
/var/log/messages {
    postrotate
    /bin/kill -HUP `/var/run/syslogd.pid`
    endscript
}
/var/log/samba/*.log {
    notifempty
    copydruncate
    sharedscripts
    postrotate
    /bin/kill -HUP `/var/lock/samba*.pid`
    endscript
}
```

This configuration rotates /var/log/messages every week. It keeps free versions of the file and notifies syslog each time the file is reset. Samba log files (of there may be several) are also rotated weekly, but instead of being moved and restarted, they are copied and truncated. The Samba daemons are sent HUP only after log files have been rotated.

Table 11.7 lists the most useful logrotate.conf options.

| Option | Meaning |
| --- | --- |
| compress | Compresses all nonresident versions of the log file |
| daily, weekly, monthly | Rotates log files on the specified schedule |
| delaycompress | Compresses all versions but current and next-most-recent |
| endscript | Marks the end of a prerorate or postrotate script |
| errors emailaddr | Errors notification to the specified emailaddr |
| missing | Doesn't comply if the log file does not exist |
| notifempty | Does not rotate the log file if it is empty |
| olddir | Specifies that older versions of the log file are placed in dir |
| postrotate | Introduces a script to run after the log has been rotated |
| prerorate | Introduces a script to run before any changes are made |
| rotate n | Includes n versions of the log rotation schedule |
| sharedscripts | Runs scripts only once for the entire log group |
| size | Rotates if log size > size (e.g., 100K, 4M) |
