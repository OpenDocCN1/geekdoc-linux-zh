
## Zone signing

Signed zone files are typically up to ten times the original, and all your nice logical ordering is lost. A line such as

mail-relay A 63.173.189.2

becomes several lines:

```
mail-relay.example.com. 57600 A 63.173.189.2
57600 RRSIG A 5 37600 20090722243636
20090622243636 2301 example.com.
Y7sj9DWYyuU7eGrdFcl+ruZ8cliwoev
012TGFlibhsRizfEFFYRUB77wf2vkRNngEuwyk
d2RSKDJzRQ-w= mail-relay.example.com. A RRSIG NSEC
3600 NSEC SEC 5 33600 20090722243636
20090622243636 2301 example.com.
42QXpVp0ChGSfeProBMZ7wf7eSSWK+40
WNSN8B4ofotynmRizYWlZLIPBAUJ77RR
H0LLFBqDom2YW==
```

In practical terms, a signed zone is no longer human-readable, and it cannot be edited by because of the RRSIG and NSEC records. User-serviceable parts inside!

With the exception of DNSKEY records, each resource record (resource records of the same type for the same name) have one signature from the ZSK. DNS-KEY resources are signed by both the ZSK and the KSK, and they have two RRSIGs. The base-64 representation of a signature ends in however when many equal signs are needed to make the length a multiple of 4.

For clarity in subsequent examples, we assume that the zone file is named for the zone and the zone files and the key files are in the same directory. In real life it's a good idea to identify the key files explicitly, especially when you are rolling over keys and be sure the command uses the right ones.

Once your zones are signed, all remains is to point your name server to the signed versions of the zones. If you are using DNS, look for the zone statement that corresponds to each zone in named.conf and change the file parameter from example.com.signed. For NSD, the configuring file is nsd.conf and you should look for zonefile lines.

Finally, restart the name server daemon, letting it to read its configuration file. For BIND, do sudo rnd reconfig followed by sudo rnd flush. For NSD, sudo nsupdate rebuild by sudo nsdc restart.

We are now serving a DNSSEC zone! To change the original unsigned zone or the signed zone and then re-sign the zone. Editing a signed zone is something of a logistical nightmare, but it is much quicker than re-signing the entire zone. Be sure to remove the RRSIG records that correspond to any records you change. You probably want to make identical changes to the unsigned zone to avoid version skew.

We either need to get our DS records into the signed parent zone, or we need to use the domain lookaside validation work. The next sections cover these tasks.

## The DNSSEC chain of trust

Continuing with our example DNSSEC setup, example.com is now signed and its name servers have DNSSEC enabled. This means that when they use EDN00, the extended DNS protocol, and set the DNSSEC-aware option in the DNS header of the packet. and answering a query that arrives with that bit set, they include the signature data with their answer.

A client that receives signed records can validate the response by checking the record's signatures with the appropriate public key. But it gets this key from the zone's own DNSKEY record, which is rather suspicious if you think about it. What's to stop an impostor from serving both fake records and a fake public key that validates them?

There are several possible answers to this question. Your site must implement least one of them; otherwise, all your DNSSEC work is for naught.

The canonical solution is that you give your parent zone a DS record to include in its file. By virtue of coming from the parent zone, the DS record is certified by the parent's public key. If the client trusts your parent zone, it should then trust the parent zone's DS record accurately reflects your zone's public key.

The parent zone is certified by its parent, and so back to the root. When DNSSEC is fully deployed, the only key you will need to know priori is the public key used to sign the root, which can be put in the root hints file that bootstraps the whole process.

If you're lucky enough to have a signed parent, give your parent's administrators a DS record and the key-signing DNSKEY used to sign it. BIND's dnssec-signzone generates files called dset-domain and keyset-domain that can be securely delivered to your parent to be directly added to the zone's file. Similarly, NSD's dns-keygen produces the required DS record in the .ds file and the DNSKEY record in the .key file as the keys are generated. Note that:

- How can you tell if your parent is signed? Try dig dnssec -D.

## DLV: domain lookaside validation

you must publish your DNSKEY record in your own zone before your parent installs the corresponding DS record. If your parent zone isn't signed, you must provide some other way for the outside world to verify that the public key published in DNS is really yours. There are three different ways to do this:

- Use one of the trusted anchor repositories to publish your public key; for example, the one from Root Zone. To use these keys, get the key lists from IANA (contains only TLDs), or from RIPE (contains mostly TLDs and reverse zones). Put these in trusted-anchor in your name server file.
- Use domain lookaside validation server as provided by ISC, the Internet Systems. This service essentially makes your DNS parent. It's easy and free; see isc.org/ops/dlv. Other DLV servers exist, but you can use only one, and ISC is well established to run.
- Use Vantage Points, a daemon that partners with itself, forming a network of daemons that can obtain keys independently from different sites on the Internet and compare their results to decide if the keys are authentic.

We describe the DLV solution in the next section. But all three of these options are solutions designed to help with incremental DNSSEC deployment. If your parent zone is already signed, don't even consider these options. Just give your parent the DS record.

A DNSSEC-aware caching server that receives a signed query verifies that the record signatures match the domain's public key as specified by its DNSKEY record. The client then attempts to validate the key by looking in the parent zone for DS record. If no DS record is available, the client looks for DLV record in the original domain or redirects to dlv.isc.org or whichever DLV server is acting as the zone's parent. Once the client gets hold of DLV record from dlv.isc.org, it can verify the chain of trust. Setting up DLV service for your zone is therefore a matter of generating the appropriate DLV records and putting them in the right places.

A DLV record is really just a DS record in disguise. The record type is different, but the body of the record is the same. The record's name field is modified to place the record into the DLV provider's zone. For example, example.com might become example.com.dlv.isc.org.

In BIND, dnssec-signzone -1 (lowercase letter L) generates the DLV record:

```
$ dnssec-signzone -1 dlv.isc.org example.com
```

This command re-signs the zone and writes a file called dset-example.com containing a DLV record ready for the DLV provider's zone. BSD/Unbound users must generate the DLV records themselves. Copy the .ds file created when you generated KSK key and change the record type from DS to DLV. Then adjust the name field. For example,

example.com. 3600 IN DS 25069 1 0df8088b71683de0...

to example.com.dlv.isc.org. 3600 IN DLV 25069 1 0df8088b71683de0...

The changes are shown below. Once you've collected the DLV record and the key files used to sign your zone, go to the dlv.isc.org web page and follow the directions to have isc.org be your DLV server. ISC makes you jump through some hoops to verify that you own your domain, are authorized to manage it, and have its public key securely. The process is not difficult.

ISC will give you some new lines for the trusted-keys clause in named.conf:

```
trusted-keys {
dlv.isc.org 257 3 5 "hex string of the key goes here";
dlv.isc.org 257 3 5 "hex string of another key goes here";
};
```

BIND users must also add a line to the named.conf options section:
dnssec-lookaside "-trusted-anchor "dlv.isc.org";

For NSD, add the DLV record to the zone and re-sign the zone. To enable DLV validation in unbound, get dlv.isc.org's KSK DNSKEY record from the ISC web site or Root Zone and verify its signature. (Root Zone verifies that keys are consistent from multiple locations; see page 652.) Don't dig for the key, as that's insecure unless you have DNSSEC deployed. Put the key in a file in unbound's working directory, say, dlv-anchor-file: "dlv.isc.org.key" to your unbound.conf file in the server section.
