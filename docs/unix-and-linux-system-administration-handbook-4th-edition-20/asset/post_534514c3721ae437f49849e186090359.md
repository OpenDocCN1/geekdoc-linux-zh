### The RFCs

The RFCs that define the DNS system are available from rfc-editor.org. We used to list a page or some of the most important DNS-related RFCs, and there are now many (more than 100, with another 50 Internet drafts) that are better off searching rfc-editor.org to access the entire archive. Refer to the **doc/rfc** and **doc/draft** directories of the current BIND distribution to see the whole fleet.

The original, definitive standards for DNS, vintage 1987, are:

- RFC1034 – Domain Names: Concepts and Facilities
- RFC1035 – Domain Names: Implementation and Specification

## 18 The Network System

The Network File System, commonly known as NFS, allows users to share files over a network. It was introduced by Sun Microsystems in 1984. The Network File System is an open standard, and many vendors have implemented versions of it.

### 18.1 INTRODUCTION TO NETWORK FILE SERVICES

Network filesystems should provide users with a seamless experience. Accessing a file over the network should be no different from accessing a file on a local filesystem. Unfortunately, wide area networks have high latencies, which causes operations behave erratically, and low bandwidth, which results in slow performance for larger files. Most file service protocols, including NFS, incorporate techniques to minimize performance problems on both local and wide area networks.

### 18.2 Issues of state

One of the design decisions made when designing a network filesystem is determining what part of the system will track the files each client has open, information referred to as “state.” A server that does not record the status of files is said to be stateless; one that is state. Both approaches have been used over the years, and both have benefits and drawbacks.

Stateful servers keep track of all open files. This mode of operation introduces many layers of complexity (more than you might expect) and makes recovery in the event of a crash far more difficult. When the server returns from a hiatus, a negotiation between the client and server must reconcile the last known state. Statelessness allows clients to maintain more control over files and facilitates the management of files are opened in read/write mode.

On a stateless server, each request is independent of the requests that preceded it. If either the server or the client crashes, nothing is lost in the process. Under this design, it is painless for servers to crash or reboot, since no context is maintained. However, it's impossible for the server to know which clients have opened files for write, so the server cannot manage concurrency.

### 18.3 Performance concerns

Network filesystems should provide users with a seamless experience. Accessing a file over the network should be no different from accessing a file on a local filesystem. Unfortunately, wide area networks have high latencies, which causes operations behave erratically, and low bandwidth, which results in slow performance for larger files. Most file service protocols, including NFS, incorporate techniques to minimize performance problems on both local and wide area networks.

Most protocols try to minimize the number of network requests. For example, read-ahead caching reads portions of a file into a local memory buffer to avoid delay when a new section of the file is read. A little extra network bandwidth is consumed in an effort to avoid a full round trip with the server. Similarly, some systems cache writes in memory and remember their updates in batches, reducing the delay incurred when communicating write operations to the server. These types of batch operations are generically referred to as request coalescing.
