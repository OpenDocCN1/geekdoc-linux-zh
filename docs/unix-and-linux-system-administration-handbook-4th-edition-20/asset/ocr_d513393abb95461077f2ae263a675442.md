To track the cause of disappearing packets, first run traceroute (see the next section) to discover the route that packets are taking to the target. Then ping the intermediate gateways in sequence to discover which link is dropping packets. To pin down the problem, you need to send a fair number of packets. The fault generally lies on the link between the last gateway you can ping without loss of packets and the gateway beyond.

The round trip time reported by ping gives you insight into the overall performance of a path through a network. Moderate variations in round trip time not usually indicate problems. Packets may occasionally be delayed by tens or hundreds of milliseconds for no reason; that's just how IP works. You should expect to see a fairly consistent round trip time for the majority of packets, with occasional lapses. Many of today's routers implement rate-limited or lower-priority responses to ICMP packets, which means that a router may delay responding to your ping if it is dealing with a lot of traffic.

The ping program can send echo packets of any size, so by using a packet larger than the MTU of the network (1,500 bytes for Ethernet), you can force fragmentation. This practice helps you identify errors or low-level issues such as problems with a congested network or VPN.

On Linux systems, you specify the desired packet size in bytes with the -s flag.

```
$ ping -s 1500 cuinfo.edu
```

Under Solaris, HP-UX, and AIX, you simply add the desired packet size to the end of the ping command.

```
$ ping cuinfo.edu 1500
```

Note that even a simple command ping can have dramatic effects. In 1998, the so-called Ping of Death attack crashed large numbers of Unix and Windows systems. It was launched simply by transmission of an overly large packet. When the fragmented packet was reassembled, it filled the receiver's memory buffer and crashed the machine. The Ping of Death issue has since been fixed, but other caveats should be kept in mind regarding ping.

First, it is hard to distinguish the failure of a network from the failure of a server with only the ping command. In an environment where ping tests normally, a failed ping just tells you that something is wrong.

Second, a successful ping does not guarantee much about the target machine's state. Echo request packets are handled within the IP protocol stack and do not require a server to be running on the probed host. A response guarantees only that the machine is powered on and has not experienced a kernel panic. You'll need higher-level methods to verify the availability of individual services such as HTTP and DNS.
