
## Chapter 20 Electronic Mail

### virtuertable feature
The virtualtable feature supports domain aliasing for incoming mail. This feature allows multiple virtual domains to be hosted on one machine and is used frequently at web hosting sites. The key field of the table contains either an email address (user@host.domain) or a domain specification (@domain). The value is a local or external email address. If the key is a domain, the value can either pass the user field along the variable %1 or route the mail to a different user. Here are some examples:

```
@registered.com %1@atrust.com
unix@book.admin.com sa-book-authors@atrust.com
linux@book.admin.com sa-book-authors@atrust.com
webmaster@example.com billy.y@zakowski@colorado.edu
info@testdomain.net username@hotmail.com
```

All the hosts on the left side of the data mappings must be listed in the cw file, /etc/mail/local-host-names, or included in the VIRTUS_DOMAIN list. If they are not, sendmail will not accept the mail locally and will try to find the destination host on the Internet. But DNS MX records will point mail back to this server and you will get a "local configuration error" message in the resulting bounce message. Unfortunately, sendmail cannot tell that the error for this instance should really be "virtuertable key not in cw file."

### ldap_routing feature
LDAP, the Lightweight Directory Access Protocol, can be a source of data for aliases or mail routing information as well as general tabular data as described. The cf/README file has a long section on LDAP with lots of examples.

To use LDAP in this, you must have built sendmail to include LDAP support. In your .mail file, add
```
define(CONF_DEFAULT_SPEC, '-h server -b searchbase')
FEATURE('ldap_routing')
LDAPROUTE_DOMAIN(my_domain)
```

Those lines tell sendmail that you want to use an LDAP database to route incoming mail addressed to the specified domain. The LDAP_DEFAULT_SPEC option identifies the LDAP server and the basename for searches. LDAP uses port 389 unless you specify a different port by adding -p ldap_port to the define.
sendmail uses one of two tags in the LDAP database:

- * mailLocalAddress for the addressee on incoming mail
- * mailRoutingAddress for the destination to which email should be sent

sendmail also supports the tag mailHost, which if present routes mail to the MX-designated mail handler for the specified host. The recipient address remains the value of the mailRoutingAddress tag.

### MAIL_HUB and SMART_HOST macros 787

LDAP database entries support a wild card entry, @domain, which reroutes addressed to anyone at the specified domain (as was done in the virtuertable).

By default, mail addressed to user@host1.mydomain would first trigger a lookup on user@host1.mydomain. If that failed, sendmail would try @host1.mydomain but not @mydomain. Including the line
```
LDAPROUTE_EQUIVALENT('host1.mydomain')
```
would also try user@mydomain and @mydomain. This feature enables a single database to route mail to a complex site. You can also take the entries for LDAPROUTE_EQUIVALENT from a file, which makes the feature quite useful. The syntax for that form is
```
LDAPROUTE_EQUIVALENT_FILE(filename)
```
Additional arguments to the ldap_routing feature let you specify more details about the LDAP schema and control the handling of addresses that have a part. As always, see cf/README file for details.

### masquerading features
An email address is usually made up of a username, a host, and a domain, but many sites do not want the names of their hosts exposed on the Internet. MASQUADE_AS lets you specify a single identity for other machines to hide. All mail appear to emanate from the designated machine or domain. This is fine for regular users, but for debugging purposes, users as root should be excluded from the masquerade. For example, would stamp as coming from user@atrust.com unless it was sent by root of the mail system; in these cases, the mail would carry the name of the originating host. MASQUADE_AS is just the tip of masquerading that extends through many variations. The masquerade_envelope features (in combination with MASQUADE_AS) hide just the local info. See cf/README for details.

### MAIL_HUB and SMART_HOST macros
Masquerading makes all appear to come from a single host or domain by rewriting the headers and, optionally, the envelope. Most sites will want all mail to actually come from (or go to) a single machine so they can control the flow of viruses and spam. You can achieve this with a combination of MX records in the DNS, the MAIL_HUB macro for incoming mail, and SMART_HOST macro for outgoing mail.
![](img/579ec8c67772f31ecf484bbb71a2_835_0.png)

See page 583 for more information about DNS MX records. For example, in the architectural diagram on page 754, MX records would direct incoming email from the Internet to the MTA in the demilitarized zone. After verification that the received email was free of viruses and spam and directed to valid local users, the mail could be relayed with the following definition:
```
define(`MAIL_HUB`, 'smtp:routingMTA.mydomain')
```
Likewise, clients would relay their mail to the SMART_HOST designated in the nullclient feature in their configuration. The SMART_HOST could then filter for viruses and spam so that your site does not pollute the Internet. The syntax of SMART_HOST parallels MAIL_HUB, and the default delivery agent is again relay. For example:
```
define(`SMART_HOST`, 'smtp:outgoingMTA.mydomain')
```
You can use the same machine as the server for both incoming and outgoing mail. Both the SMART_HOST and the MAIL_HUB must allow relaying from the clients inside your domain and the MTA in the DMZ.

### Client configuration
If you follow the paradigms illustrated in the mail system design (page 753), most of your machines will be configured as clients who just submit mail generated by users and do not receive mail at all. One of sendmail's FEATURES, nullclient, is just right for this situation. It creates a config file that follows all mail to a central hub by SMTP. The entire config file, after the VERSIONID and OSTYPE lines, would be simply own```
FEATURE('config')
FEATURE('mailserver')
EXPOSED_USER('root')
```
where mailserver is the name of your central hub. The config tells sendmail not to do DNS lookups or rewrite addresses with fully qualified domain names. All of that work will be done by the mailserver. This feature is similar to SMART_HOST and assumes the client is MASQUADE_AS. The EXPOSED_USER clause exempts root from the masquerading and so facilitates debugging. The mailserver machine must allow relaying from its clients. Permission is granted in the access_db, described on page 785. The client must have an associated MX record that points to mailserver and must also be included in the mailserver's cw file (usually /etc/mail/host-names). These settings allow the mailserver to accept mail for the client.

sendmail should run as an MSA (without the -bd flag) if the user on the client machine can be taught to use port 587 for submitting mail. If not, run sendmail in daemon mode (-bd) but set the DAEMON_OPTIONS configuration to listen for connections only on the loopback interface.

### Spam-related features in sendmail
SUSE provides a sample .mc file for a null client in /etc/mail/linux.nullclient.mc. Fill in the name of your mail server, build the sendmail.cf file, and you're done.

### Configuration options
You set config options with m4's define command. A complete list of options that are accessible as m4 variables (along with their default values) is given in the cf/README file. The defaults are OK for a typical set that is not too paranoid about security and not too concerned with performance. The defaults try to protect you from spam by turning off relaying, by requiring addresses to be fully qualified, and requiring sending domains to resolve to an IP address. If your mail machine is very busy and services a lot of mailing lists, you may need to tweak some of the performance values.

Table 20.11 on the next page lists options you might need to adjust (about 10% of over 175 configuration options). Their default values are shown in parentheses. To space the names without their conf prefix; for example, the FALLBACK_MX option is really named confFALLBACK_MX. We divided the table into subsections that identify the issue of the variable addresses: resource management, performance, security and spam abatement, and miscellaneous options. Some options fit in more than one category, but we listed them only.
