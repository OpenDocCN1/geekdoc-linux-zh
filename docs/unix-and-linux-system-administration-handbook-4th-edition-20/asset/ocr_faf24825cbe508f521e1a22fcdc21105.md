# Access determination

When the ACL in the previous example is expanded to include entries for a specific user and group, setfac automatically supplies an appropriate mask:

```
$ ls -l /tmp/example
-rw-r-- 1 garth 0 Jun 14 15:57 /tmp/example
$ setfac -m user:trent:rwx,group:admin:rw /tmp/example
$ ls -l /tmp/example
-rw-r----+ 1 garth 0 Jun 14 15:57 /tmp/example
$ setfac --omit-header /tmp/example
```

As here, the Linux version of setfac generates a mask that allows all the permissions granted in the ACL to take effect. If you want to set the mask by hand, include it in the ACL list given to setfac or use the -n option to prevent setfac from regenerating it. (The Solaris setfac defaults to not recalculating the mask entry; use the -r flag to regenerate it.)

Note that after the setfac command, ls -l shows a + sign at the end of the file's mode to indicate that it now has a real ACL associated with it. The first ls -l shows no + because at that point the ACL is "minimal." and it is entirely described by the 9-bit mode and does not need to be stored separately.

If you use the chmod command to manipulate the permissions on an ACL-bearing file, be aware that your changes affect only the mask. To continue the previous example:

```
$ chmod 770 /tmp/example
$ ls -l /tmp/example
-rwxrwx----+ 1 garth staff 0 Jun 14 15:57 /tmp/example
$ setfac --omit-header /tmp/example
```

The ls output is misleading. Despite the apparently generous group permissions, no one actually has permission to execute the file by reason of group membership. To grant such permission, you must edit the ACL itself.
