
# Chapter 17 DNS: The Domain Name System

## SPF records

SPF records are specified in RFCs 4406 and 4408 (2006).

SPF (Sender Policy Framework) records are an direct to identify email messages with forged Headers, which are often spam or phishing. If the site receiving a message detects that the headers are forged, it can drop the mail, filter it, or tag it before delivering it to the recipient. This functionality was first implemented with TXT records, but we now have a dedicated SPF record type that uses the same syntax as the TXT version. Sites can have SPF records, TXT records in SPF format, or, neither.

Unfortunately, there are two competing ways of using SPF records: Microsoft's Sender ID and the rest of the world's. The IETF's working groups could not reach consensus on the best option, so both approaches were experimental RFCs. The main difference is whether the tests are done on the envelope's address or the header's address.

Both the SPF and Sender identifications have a serious flaw: email that is forwarded fails the SPF check because the receiver checks the sender's SPF record with the forwarder's IP address. Therefore, sites need to be careful with the disposition of mail that fails the SPF check.

Here, we describe a subset of the syntax and semantics of the RFC4408 version of SPF records. The complete specification is infinitely flexible, with macros, redirects, and such yielding a dozen ways to achieve a given policy. We concentrate on an efficient subset of that.

An SPF record lists the IP addresses of servers that originate the sender's legitimate email. For example, `dig gmail.com spf` returns the following record:

```
gmail.com             300 IN SPF = "vspf=spf.google.com"
```

This SPF record redirects clients to the _spf subdomain at google.com. A followup query, `dig spf.google.com spf`,

```
_spf.google.com      300 IN SPF = "v=spf ip4:216.239.32.0/17 ip4:64.233.160.0/19
ip4:66.249.80.0/20 ip4:72.14.192.0/18 ip4:209.85.128.0/17 ip4:66.102.0.0/20
ip4:74.125.0.0/16 ip4:64.18.0.0/20 ip4:207.127.144.0/27 "all"
```

Rather than listing specific hosts, this SPF record enumerates the IP networks of Google's mail servers. This is all one long SPF record, but we have inserted line breaks to make it fit the page.

Quoted strings are limited to 255 bytes, so if you need more than 255 characters for your entry, you must use quoted strings. Multiple strings are concatenated with no extra space. Try to keep the total length below about 450 bytes, so that query responses can still fit in a single 512-byte UDP packet. SPF records are insensitive.

- 15. This is a little white; Google and many other sites implement their SPF records with TXT records because the SPF record type is new and only currently supported by popular name software. But by looking to the future, we have taken editorial license and shown SPF records instead of TXT records. The digs were also for TXT records, not SPFs.

## DKIM and ADSP records

Let's dissect that record in a bit more detail:

- v=spf1 indicates the record conforms to version 1 of the SPF protocol, described in RFC4408, v=spf2.0 would indicate Microsoft's Sender ID system, described in RFC4408.
- The ip4 tags indicate the following data value is a normal IP network or host address. Multiple clauses can be included, as is done here.
- ?all indicate "done" to the checking function that interprets the record.

The complexity of the full SPF language is disheartening. Other tags are available to list hostname, MX records, PTR records, IPv6 addresses, and so. Some of these forms require a second DNS lookup, although they may add convenience or flexibility, they are less efficient than the ip4 tag. The examples at the end of RFC4408 are a good reference if you want to tag with your SPF records. Here is another example, obtained with dig sendmail.com txt:

```
sendmail.com. IN TXT v=spf1 ip4:209.246.26.40 ip4:209.246.26.41 ip4:231.143.38 ip4:209.246.26.39 ip4:209.246.26.24 ip4:209.246.26.25 ip4:209.246.26.10 ip4:209.246.26.53 ip4:72.32.154/27 ptr:constant.com "all"
```

This record completes server addresses rather than entire networks. The tail end of the IP address is a clause that permits constant.com to send mail purporting to be from constant.com. This clause should only take effect if matching PTR record—as we are using, the PTR maps back to constant.com. Either email are not checking the PTR record or has a small bug. Surveys showed that SPF was supported by more than 90% of sites, with some readers (e.g., Gmail) print a red banner across a message that failed SPF check. sendmail, Postfix, and Microsoft Exchange supports Sender ID. See page 768 for more SPF information.

DKIM stands for DomainKeys Identified Mail and is an enhancement of two systems: DomainKeys from Yahoo! The receiver of the email can authenticate the sender (no forgeries) and guarantee the message's integrity (no meddling). A lot of work has gone into the DKIM specifications so that edge cases like mailing lists and outsourced work well. Another focus of DKIM design is to make implementation easy; it requires no per-user or per-host changes. Here, we cover only the DNS aspects of DKIM. The implications are described in Chapter 20, Electronic Mail, starting on page 845.

DKIM resource records have not yet been standardized as a DNS record type; TXT records in a special format are used instead. They use a DNS name formed from a "selector" concatenated with _domainkey. The record's data is the site's public key. Multiple selectors may exist so that keys can be easily rolled and revoked. A site using DKIM computes a signature over selected header fields and the body of the message with its DKIM private key. It puts the signature into the outbound message in the form of a header field DKIM-Signature. The corresponding public key is available through the sending site DNS zone as a TXT record associated with the name _domainkey. The receiving site does a DNS lookup for this key and uses it to validate the message signature. Successful verification authenticates the message as coming from the purported domain and verifies that the message has not been modified.

Here is an example of DKIM-Signature line from a signed message:

```
DKIM-Signature: v=1;rsa=sha256;c=relaxed/relaxed;d=gmail.com;s=gamma;h=domainkey.mime-version:reported-to:date:message-id:subject:from:content-type;bh=24HFUvt1OA4jRXnBm46JzUpSbkO4dz2pp4ls;b=UtYWupx/UpdiQ7sd1n0H5zfDIkJR7/Ge+HywBxM0ClshlwhRhyRHy1ea3S0EnMXEJEY13Jyj3VNEMGAOAOSQlQIMdIdSlPj7avxptY0VFLgYGM9ID4uwB0la7ZjuUJHmsEA/Ek48rvj10ZYG+ARDdpbx6/56fSfVt+a+A=
```

The tags in the signature are explained in Table 17.7.

| Table 17.7 Tags in the DKIM-signature header | Tag | Example value | What it is |
|---|---|---|
| v | 1 | Version number; must be 1 |
| a | rsa-sha256 | Encryption algorithm: rsa-sha1 or rsa-sha256 |
| c | relaxed/relaxed | Canonicalization algorithm: simple or relaxed |
| d | gmail.com | Domain of the sender |
| s | gamma | Selector or key |
| h | domain... | Header fields to include in the header signature |
| bh | 24HFUvt1... | Cryptographic hash of the body of the message |
| b | UtYWupx... | Cryptographic signature of the whole message |

a. The algorithm specifies how the header and body are merged before encryption.

The selector tag, s=gamma, tells us the name of the public key, and d= gives the parent domain. To get our hands on the public key, we dig for the TXT record for the pseudo-host gamma_domainkey.gmail.com.

RFC5627 defines a TXT record you can stash in a special subdomain to express your overall policy with signing messages. This record was recently standardized (2009) and is called ADSP (Author Domain Signing Policy) text record. The subdomain is `_adsp._domainkey.domain`.

Inside the TXT record, include a `dkim=` clause to declare your site's signing policy. The possible values are

- all, for domains that sign all outgoing messages
- unknown, for domains that sign some all email messages
- discardable, for domains that sign all email and recommend directs discard messages whose signature cannot be verified
