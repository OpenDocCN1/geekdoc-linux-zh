useradd on AIX does not provide a -D option to show the default values for users. It puts new users in a single group and does not create their home directories unless invoked with the -m flag (in which it copies in a .profile file from the /etc/security directory).

## useradd example

To create a new "hilbert" using the system defaults on a Linux system, you could

```bash
$ useradd hilbert
```

This command would create the entry in /etc/passwd:

```
hilbert:x:1005:20::/home/hilbert:/bin/sh own```

useradd disables the account by putting an x in the password field. You must assign a real password to make the account usable.

A more realistic example is shown below. We specify that hilbert's primary group should be "faculty" and that he should also be added to the "famous" group. We override the default home directory location and shell, and ask useradd to create the home directory if it does not already exist

```bash
$ useradd -d "David Hilbert" -d /home/math/hilbert -g faculty -G famous -m -s /bin/tcsh hilbert
```

This command creates the following passwd entry:

```
hilbert:x:1005:30:David Hilbert:/home/math/hilbert:/bin/tcsh
```

The assigned UID is one higher than the highest UID on the system, and the corresponding shadow entry

```
hilbert!:14322:0:99999:7:0::
```

The password placeholder character(s) in the passwd and shadow file vary depending on the operating system. useradd also adds hilbert to the appropriate groups in /etc/group, creates the directory /home/math/hilbert, and populates it from the /etc/skel directory.

## 7.6 ADDING USERS IN BULK WITH NEWUSERS (LINUX)

Linux's newusers creates multiple accounts at one time from the contents of a text file. It is pretty gimpy, but it can be handy when you need to add a lot of users at once, such as when creating class-specific accounts. newusers expects an input file of lines just like the /etc/passwd file, except the password field contains the initial password in clear text. Oops... better protect that file.

newusers honors the password age parameters set in the /etc/login.defs file, but it does not copy in the default startup files as useradd. The only startup file it provides is xauth.

At a university, what's really needed is a batch script that can use a list of students from enrollment or registration data to generate the input for newusers, with usernames formed according to local rules and guaranteed to be locally unique, with strings randomly generated, and UIDs and GIDs increasing for each user. You're probably better off writing your own wrapper for useradd in Perl or Python to get newusers to do what you need.

## 7.7 REMOVING USERS

When a user leaves your organization, user's login account and files should be removed from the system. This procedure involves the removal of all references to the login name that you added or by your useradd program. If you remove a user by hand, you may want to use the following checklist:

- Remove the user from any local databases or phone lists.
- Remove the user from the aliases file or add a forwarding address.
- Remove the user's crontab file and any pending at jobs or print jobs.
- Kill any of the user's processes that are still running.
- Remove the user from the passwd, shadow, group, and gshadow files.
- Remove the user's home directory.
- Remove the user's mail spool.
- Clean up entries on shared calendars, room reservation systems, etc.
- Delete or transfer ownership of any mailing lists run by the deleted user.

Before you remove someone's home directory, be sure to relocate any files that are needed by other users. You usually can't be sure those files might be, so it's always a good idea to make an extra backup of the user's home directory and mail before deleting them.

Once you have removed a user, you may want to verify that the user's old UID no longer exists on the system. To find the paths of orphaned files, you can use the command with the -nouser argument. Because find has a way of "escaping onto network servers if you're not careful, it's usually best to check filesystems individually with xdev.

```bash
$ sudo filesystem -xdev -nouser
```

Killing the deleted user's running processes can be tricky in a distributed environment. Shared calendars and room reservation systems may have ongoing items scheduled by the now-defunct user that is suddenly orphaned and need to be cleaned up. There are probably several places in your environment where the user needs to be removed—make your own list, perhaps in the form of a cleanup script.

## 7.8 DISABLING LOGINS

Unfortunately, modifying a user' password simply makes logins fail. It does not notify the user of the account suspension or explain why the account no longer works. An alternative way to disable logins is to replace the user's shell with a program that prints an explanatory message and supplies instructions for rectifying the situation. The program then exits, terminating the login session.

This approach has both advantages and disadvantages. Any forms of access that check the password do not pay attention to the shell will not be disabled. To facilitate the "disabled shell" trick, many daemons provide nonlogin access to the system (e.g., ftppd) to check if a user's login is listed in /etc/shells and deny access if it is not. This is the behavior you want. Unfortunately, it's not universal, so you may have to do some fairly comprehensive testing if you decide to use shell modification as for disabling accounts.

Another issue is that your carefully written explanation of the suspended account might never be seen if the user tries to log in through a window system or through a terminal emulator that does not leave output after a logout.
