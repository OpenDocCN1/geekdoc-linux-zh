## NSD zone-specific configuration options

Unlike global zones, zone-specific options do generally require some configuration, especially the access control lists.

```
name: zonename
zonefile: filename
```

A zone is defined by a zone name and a file of resource records.

```
notify: ip-address (key-name) | NOKEY | BLOCKED²
provide-xfr: ip-spec (key-name) | NOKEY | BLOCKED²
```

The master server for a zone notifies its slaves of updates to the zone. Then, when requested by the slaves, it initiates zone transfers to the modified data. Therefore, a zone for which this server is the master must have the notify and provide-xfr access lists specified. The values of these options will normally be the same. Notification messages are signed with the listed key-name unless you specify the notify option.

Keep in mind that unlike named, nsd does not automatically notify the slave servers of a zone; you must list them in the notify and provide-xfr clauses. There may be multiple instances of these statements.

```
allow-notify: ip-spec (key-name) | NOKEY | BLOCKED²
request-xfr: [ AXFR | UDP ] | ip-address (key-name) | NOKEY)²
```

A slave server for a zone must explicitly allow the master to send notification messages. Any messages received from servers that are not in the allow-notify list (or that are BLOCKED) are ignored.

The request-xfr clause allows the slave server a zone transfer from the master server at the listed ip-address using the specified key-name. If you include the AXFR argument, only AXFR transfers (transfers is, of the entire zone, opposed to incremental updates) will be requested. The UDP argument specifies the request for a zone transfer be sent with UDP transport rather than the default TCP. It's best to just use TCP.

² The parentheses are here to show grouping; do not include them in an actual value.

Source address outgoing-interface: ip-spec

This list controls the IP address used by a slave server to request a zone transfer or by master to send notifications. The addresses must match; that is, the access control clause in the master's zone configuration must use the same address as the corresponding clause in the slave's zone configuration.

## Running nsd

Once you have configured nsd, run the nsd-checkconf program to be sure there are no syntax errors in your nsd.conf file. Then put your files in the right directory (the one specified in nsd.conf) and use nsd, the NSD control script, to compile them into database files. Finally start the server with nsd.

```
$ nsd rebuild
$ nsd start
```

Test the name server with dig drill, and if you're happy with the results, add nsd start to your operating system startup sequence and nsd stop to its shutdown sequence. You can also set up a crontab to run nsd patch once a day to update the zone files from the database files.

## Installing and Configuring Unbound

Unbound is a recursive, caching, validating DNS name server from the folks (NLNet Labs) that produce NSD. It was originally developed for UNIX and Linux, but it's now available for Windows, too.

To install, create a new user "unbound", log in as this user, and download the distribution from unbound.net. Unbound requires libevent and OpenSSL libraries and can use the libwevent libraries (monkey.org~/provos/libwevent) if they are available. Like NSD, Unbound initially runs as root, but then falls back to running under its dedicated account.

To build:

```
$ /configure
$ make
$ sudo make install
```

Unbound also comes with an extensive test suite that you can run with make test. The distribution installs the following binaries:

- unbound - the recursive name server
- unbound-checkconf - syntax checker of the unbound.conf file
- unbound-control, unbound-control-setup - secure remote control
- unbound-host - simple query tool

## Locations

directory: directory [/usr/local/etc/unbound]
pidfile: filename [/usr/local/etc/unbound.pid]
root-hosts: filename [none]

The directory option sets the server's working directory. unbound defaults to a directory under /usr/local/etc, but many sets prefer /var. The location of the PID defaults to unbound's working directory, but it also works in more traditional places such as /var/run.

Root hosts are built into code, so the hosts file is not required. However, you can provide one if you like the addresses in the code may eventually become out of date. Use dig @a.root-servers.net for a fresh copy.

## Logging

use-syslog: yes | no [yes]
logfile: filename [none]
log-time-ascii: yes | no [no]
verbosity: level [1]

Logging information can go either to syslog or to a file. Choose between them with the use-syslog and logfile options. If you want normal time (seconds since 1/1970) in log messages, use the log-time-ascii option. The verbosity determines the amount of logging: see page673 for details.

## Statistics

statistics-interval: seconds [0, i.e., disabled]
statistics-cumulative: yes | no [no]
extended-statistics: yes | no [no]

Statistics are turned off by default they slow down the name server. If you turn them by setting the statistics-interval to a nonzero number of seconds, statistics will be written to the log file (or syslog) at the specified interval. By default, the statistics counters are reset to 0 each time they are written; use the statistics-cumulative option to make them accumulate over time.

Setting extended-statistics to yes generates more data that you can dump using unbound-control.

## Query access

access-control: network allow [allow only localhost]

The access-control option is the key to configuring unbound to a recursive name server for your own users and for the rest of the world. Use multiple access-control lines to allow multiple networks. The access parameter can take four values:

- - blocks queries from the specified network or host
- refuse – blocks queries and sends a REFUSED message back
- allow – answers queries from clients requesting recursion
- allow-snoop – answers queries from recursive and iterative clients
