## Analyzing disk I/O

As in UNIX output, the number of processes that are immediately runnable and that are blocked on I/O are shown under the procs heading. Page statistics are condensed into two columns, si and so, which represent pages swapped in and out, respectively.

Any apparent inconsistencies among the memory-related columns are for the most part. Some columns count pages and others count kilobytes. All values are rounded averages. Furthermore, some are averages of scalar quantities and others are different averages.

Use the si and so fields to evaluate the system's paging behavior. A page-in (si) does not necessarily represent a page being recovered from the swap area. It could be executable code paged from a filesystem or a copy-on-write page duplicated, both of which are normal occurrences that do not necessarily indicate a shortage of memory. On the other hand, page-outs (so) always represent data written to disk after being evicted by the kernel.

If your system has a constant stream of page-outs, it's likely that you would benefit from more memory. But if paging happens occasionally and does not produce annoying hiccups or user complaints, you can ignore it. If your system falls in the middle, further analysis should depend on whether you are trying to optimize for interactive performance (e.g., a workstation) or to configure a machine with many simultaneous users (e.g., a compute server).

On a traditional disk, you can find that every 100 page-outs cause about one second of latency. If 150 page-outs must occur every second, you will wait for about1.5 seconds. A rule of thumb used by researchers perceives the system to be "slow" when response times are longer than ten seconds.

You can monitor disk performance with iostat. Like vmstat, specify an interval and a repeat count, and its first line of output is a summary since boot. Like vmstat, it also tells you how the CPU's time is being spent. Here is an example from Solaris: Columns are divided into topics (in this case: tty, swap, nfs, and cpu), with the data for each topic presented beneath it. iostat output tends to be somewhat different on every system. The tty topic presents data concerning terminals and pseudo-terminals. This information is basically uninteresting, although it might be useful for characterizing the throughput of the modem. The in and out columns give the average total number of input and output by all terminals. Each disk has columns kps, tps, and serv, indicating kilobytes transferred per second, transfers per second, and average "service times" (seek times, essentially in milliseconds). One transfer request can include several sectors, so you can readily read the actual throughput in KiB/s. Transfers, on the other hand, are nebulously defined. The ratio between kps and tps tells you whether there are a few large transfers or lots of small ones. Large transfers are more efficient.

The cost of seeking is the most important factor affecting disk performance. To a first approximation, the rotational speed of the disk and the speed of the bus to which the disk is connected have relatively little impact. Modern disks can transfer hundreds of megabytes of data per second if they are read from contiguous sectors, but they can only perform about 100 to 300 seeks per second. If you easily realize less than 5% of the disk's drive throughput, seeks are more expensive when the heads travel a long distance. If you have a disk with several filesystem partitions and files are read from each partition in a random order, the heads must travel back and forth to switch between partitions. On the other hand, files within a partition are relatively local to one another. When partitioning a new disk, consider the performance implications and put files that are accessed together in the same filesystem.

## sar: collect and report statistics over time

It's especially important to split the paging (swap) area among several disks if possible, since paging can slow down the entire system. Many systems have both dedicated swap partitions and swap files on a formatted filesystem.

Some systems also let you set up multiple "memory-based filesystems," which are essentially the same thing as RAM disk. A special driver poses as a disk which actually stores data in high-speed memory. Many sites use a RAM disk for their /tmp filesystem or for other uses such as web server logs or emails. Using a RAM disk reduces the memory available for general use, but it makes the reading and writing of temporary files blindingly fast. It's generally a good deal.

The ls command, which lists files, and the f which shows the processes that are using a filesystem, can be helpful for isolating disk I/O performance issues. These commands show interactions between processes and filesystems some of which may be unintended. For example, if an application is writing its log to the same device used for database logs, a bottleneck may occur.

## iostat: analyze subsystem performance

Modern storage systems can involve network or SAN-attached devices, RAID arrays, and other layers of abstraction. Consider the iostat tool for measuring and optimizing these complex systems. iostat is available under the GPL and runs on all of our example systems (not to mention Windows).

iostat measures I/O on single systems and on clusters. It is well documented and yields accurate and reproducible performance measurements.
