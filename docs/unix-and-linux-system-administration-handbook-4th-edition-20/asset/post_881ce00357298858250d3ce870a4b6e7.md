
# 21.13 NetFlow: CONNECTION-ORIENTED MONITORING

SNMP is widely known for its ability to report the amount of network traffic flowing through an interface. But if you want to know more about the exact type of traffic and its destinations, SNMP is not much help. In a UNIX box you could run a script to unearth some additional details, but this option isn't available on a dedicated router.

In response, router vendors have come up with their own solutions to this problem. The most popular of these solutions is Cisco's NetFlow protocol.

NetFlow tracks every connection with seven keys: source and destination IP address, source and destination port number, protocol (TCP, UDP, etc.), type of service (ToS), and logical interface. This metadata, combined with additional information such as the number of packets and bytes involved, can be sent to any collector.

The predominant NetFlow protocol versions are v5 and v7, which are usually lumped together because they're the same except that v7 adds an additional field (source router). v7 is used on Cisco Catalyst switches. Version 9 is gaining popularity. This template-based approach makes it very flexible.

You can have your NetFlow send a running account of its metadata to a suitable receiver such as Cisco's cflow. On a busy network link, this configuration generates a huge amount of data, so you may need to provide substantial disk space and look into analysis tools that are up to the task.

For the latter, one possibility is Dave Plonka's FlowScan package. It has not been updated in time, but it still works well. You can find it at net.doit.wis.edu/~plonka/FlowScan.

# Monitoring NetFlow data with ndump and Nfsen

Another pair of useful tools for collecting and analyzing NetFlow data are Peter Haag's ndump (ndump.sourceforge.net) and Nfsen (nfsen.sourceforge.net). The collector (ncapd) stores NetFlow data on disk for later processing by ndump.

ncapd and ndump handle NetFlow protocol versions v5/7 and v9. For IPv6 support, you'll have to use v9; versions 5 and 7 do not support it.

ndump works like a tcpdump (see page 875). It has a similar filter syntax that has been adapted for NetFlow data. Flexible output formats allow you to customize the display of records. Built-in summaries show you the top N talkers on your network and other useful information.

Since the NetFlow data is stored on disk, you can analyze it with different filters. Another nice feature is nfdump's ability to match incoming and outgoing flows into a single bidirectional flow. NfSen is a web front end for NetFlow that sits on top of nfdump and combines graphing capabilities with all the features of nfdump. It displays three different categories: flows, packets, and bytes. NfSen does more than create static graphs—lets you navigate through the individual flows. You can also see peaks in the graphs, and drill down to the individual flows, and apply arbitrary nfdump filters to refine the display. The combination of GUI with the underlying power of nfdump lets you save your filter and display settings to create a profile so that you can easily return to a specific type of analysis in the future. For example, profiles that monitor traffic for your DMZ, web reader, or client's network also make NfSen a valuable tool for security incident response teams because they make it easy to track specific types of incidents or network traffic. # Setting up NetFlow on a Cisco router

To started with NetFlow, you must first configure your network device to send NetFlow data to nfcapd. This section outlines the configuration of NetFlow on a Cisco router.

Export of NetFlow data is enabled per interface:

```
ios interface fastethernet 0/0
ios ip route-cache flow
```

To tell the router where to send the NetFlow data, enter the following command:

```
ios ip flow-export nfcapd-hostname listen-port
```

The options below break up long-lived flows into 5-minute segments. You can choose any segment length between 1 and 60 minutes, but it should be equal to less than nfdump file rotation period, which is 5 minutes by default.

```
ios ip flow-export version 5
ios ip flow-cache timeout active 5
```

On the Catalyst 6500/7600, you must enable NDE (NetFlow Data Export) in addition to normal NetFlow export.

# Recommended reading

Here's how:

```
ios# mls flow ip interface-full
ios# mls flow ip ipv6 interface-full
ios# mls nde sender version 5
```

On a busy router, consider aggressively timing out small flows:

```
ios# mls aging fast time 4 threshold 2
ios# mls aging normal 32
ios mls aging long 900
```

You still need the traditional NetFlow configuration, using ip flow ingress or ip route-cache flow on every interface, so that you see "software switched" flows such as those that go to the router itself.

For NetFlow v9, the configuration may be even longer. Depending on your IOS version, you can also define your own template. With the introduction of Flexible NetFlow (FNF), the NetFlow environment has become even more complex.
