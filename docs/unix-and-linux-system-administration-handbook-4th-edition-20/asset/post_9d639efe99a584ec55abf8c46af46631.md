## Screen sections

A Screen section ties a device (video card) to a monitor at a specific color depth and set of display resolutions. Here's an example that uses the video card and monitor specified above.

```xconfig
Section "Screen"
Identifier "Screen0"
Device "Videocard0"
Monitor "ViewSonic"
DefaultDepth 24
Subsection "Display"
Depth 8
Modes "640x400"
EndSection
Subsection "Display"
Depth 16
Modes "640x400" "640x480" "800x600" "1024x768"
EndSection
Subsection "Display"
Depth 24
Modes "1280x1024" "1024x768" "800x600" "640x400" "640x480"
EndSection
```

As you might expect, the screen is named with an Identifier, and the identifiers for the previously defined video device and monitor are mentioned. This is the first section we have introduced with subsections. One subsection is defined for each color depth, with the default being specified by the DefaultDepth field.

A given instance of the X server can run at only one color depth. At startup, the server determines what resolutions are supported for that device. The possible resolutions generally depend on the video card. Special keyboard combinations for X on page 1026 describes how to cycle through the resolutions that are defined here.

Any modern video card should be able to drive your monitor at its full resolution in 24-bit or 32-bit color. If you want to run old programs that require a server in 8-bit color, run a second X server on a virtual console. The -depth 8 flag on the X command line to override the DefaultDepth option.

## InputDevice sections

An InputDevice section describes a source of input events such as a keyboard or mouse. Each device gets its own InputDevice section, and with other sections, each is named with an Identifier field. If you are sharing a single configuration file among machines with different hardware, you can define all the input devices; only those referenced in the ServerLayout section are used. Here is a typical-keyboard definition:

| Section | Identifier |
| --- | --- |
| InputDevice | "Generic Keyboard" |
| Driver | "Keyboard" |
| Option | "AutoRepeat" "500 30" |
| Option | "KkbModel" "pc104" |
| Option | "XkbLayout" "us" |

You can select the options in the keyboard definition to express your particular religion's stance on the proper position of Control and Caps Lock keys, among other things. In this example, the AutoRepeat option specifies how long a key needs to held down before it repeats.

The mouse is configured in a separate InputDevice section:

| Section | Identifier |
| --- | --- |
| InputDevice | "Generic Mouse" |
| Driver | "mouse" |
| Option | "CorePoint" |
| Option | "Device" "/dev/input/mice" |
| Option | "Protocol" "IMPS/2" |
| Option | "EmulateButtons" "off" |
| Option | "ZAxisMapping" "4 5" |

The CorePoint option designates this mouse as the system's primary device. The device file associated with the mouse is specified as an Option; Table 25.2 lists the device multiplexer files for examples.

### Table 25.2 Common device files

| OS | Device file |
| --- | --- |
| Linux | /dev/input/mice |
| Solaris | /dev/mouse |
| HP-UX | /dev/mousemux
| AIX | |

The communication protocol depends on the particular brand of mouse, its features, and its interface. You can set it to auto to make the server try to figure out the protocol. If your mouse wheel doesn't work, try setting the protocol to IMPS/2. If you have more than a few buttons, try using Explorer/2. Some users report success with theing protocol. The EmulateButtons option lets a two-button mouse emulate a three-button mouse by defining a click on both buttons.

## ServerLayout sections

The ServerLayout is the top-level node of the configuration. Each hardware configuration on the server will have its own instance of ServerLayout section. The layout used by a particular X server is usually specified on the server's command line. This section ties together all the other sections to represent a display. It associates a set of screens with the layout. If multiple monitors are attached to separate video cards, each screen is specified along with orientation directions to indicate how they are properly arranged. In this example, screen one is on the left and screen is on the right. Here is an example of a complete ServerLayout section:

| Section "ServerLayout" |
| --- | --- |
| Identifier | "Simple Layout" |
| Screen | "Screen 1" LeftOf "Screen 2" |
| Screen | "Screen 2" RightOf "Screen 1" |
| InputDevice | "Generic Mouse" "CorePointer" |
| InputDevice | "Generic Keyboard" "CoreKeyboard" |
| Option | "BlankTime" "10" # Blank the screen in 10 minutes
| Option | "StandbyTime" "20" # Turn off in 60 minutes (DPMS)
| Option | "SuspendTime" "60" # Full hibernation in 60 minutes (DPMS)
| Option | "OffTime" "120" # Turn off DPMS monitor in 2 hours |
| EndSection |

Some video cards can display monitors once. In this case, only a single Screen is specified in the ServerLayout section. The following list is the list of input devices to associate with the layout. The CorePointer and CoreKeyboard options are passed to the InputDevice section to identify that the devices are active for configuration. These options can also be set directly in the corresponding InputDevice sections, but it's cleaner to set them in the ServerLayout.

The last few lines configure several layout-specific options. In this example, these all relate to DPMS, which is the interface that tells Energy Star-compliant monitors when to power down. The monitors must also have their DPMS options enabled in the corresponding Monitor sections.

- Not all options are supported by Xorg.
- Recall that screens identify a monitor/video combination at a particular color depth.

## xrandr: not your father's X server configurator

The X Resize and Rotate Extension (RandR) lets clients dynamically change the size, orientation, and reflection of their X server screens. xrandr is the command-line interface to this extension.

Of course, we would all love to spend a few days tediously crafting each line of the xorg.conf file to support brand-new SUPERATOR 3000 system with your deluxe displays. But in many cases, you can have xrandr do the configuration for you and be time to grab a few beers. With no arguments, xrandr shows the available displays and their possible resolutions.

$ xrandr

```
VGA-0 connected 1024x768+0+0 (normal left inverted x a...) 0mm x0mm
1024x768 61.0 60.0 59.9 59.9
800x600 60.3 61.0 59.9 56.2 59.8
640x480 59.9 61.0 59.4 59.5
DVI-0 connected 1024x768+0+0 (normal left inverted x a...) 0mm x0mm
1024x768 61.0 60.0 59.9
```

You can specify the resolution to use for each display with the display's placement relative to other displays. For example:

```
$ xrandr --output VGA-0 --mode 800x600 --right-of DVI-0
```

The --output argument sets all monitors. The --output and --mode arguments set the VGA display to a resolution of 800x600, and the --right-of argument specifies that the VGA display is physically located to the right of the D display (The latter option is needed to properly implement desktop continuity.) xrandr --help to see the available options.

If you want xrandr to run automatically when you start the X server, you can do it in your ~/.xprofile file, which is executed at server startup.

## Kernel mode setting

To make the system's presentation more seamless and flicker free, responsibility for setting the initial mode of the graphics display is now being pushed into the Linux kernel through the "kernel mode setting" (KMS) module. You enable or disable KMS through settings in the video driver configuration files in /etc/modprobe.d. For example, if you have an ATI Radeon card, you can turn off KMS by adding the following line to /etc/modprobe.d/radeon.conf:

```
options modeset=0
```
