APT originated in the world of Debian and dpkg, but it has been extended to pass RPMs, and versions that work with all of our example distributions are available. We like APT and consider it a solid choice if you want to set up your automated package distribution network. See the section: The Advanced Package Tool on page 387 for more information. ## Package repositories

Linux distributors maintain software repositories that work hand-in-hand with their chosen package management systems. The default configuration for the package management system usually points to one or more well-known or FTP servers that are under the distributor’s control.

However, it’s not obvious what such repositories contain. Should they include only the sets of packages released as base, major releases? Formal releases plus current security updates? Up-to-date versions of all packages that exist in the formal releases? Use third-party software not officially supported by the distributor? Source code? Binaries for multiple architectures? When you run apt-upgrade, yum upgrade, and zypper dup to bring the system up to date, what exactly should that mean?

## Chapter 12 Software Installation and Management

In general, package management systems must answer all these questions and make it easy for sites to select the cross-sections they want to include in their software “world.” The following concepts help structure this process.

- A “release” is a self-consistent snapshot of the package universe. Before the Internet era, OS releases were more or less immutable and were associated with one specific point in time; security patches were made available separately. These days, a release is a nebulous concept. Some releases evolve over time as packages are updated. Some, as Red Hat Enterprise Linux, are designed to evolve slowly; by default, only security updates are incorporated. Other releases, as beta versions, change frequently and dramatically. But in all cases, the release is the baseline, the target, the “thing I want to update my system to look like”.

- A “component” is a subset of the software within a release. Distributions partition differently, but one distinction is between core software blessed by the distributor and extra software made available by the broader community. Another distinction’s common in the Linux world is the one between the free, open source portions of a release and the parts that are tainted by some kind of restrictive licensing agreement.

Of particular note from an administrative standpoint are minimally active components that include security fixes. Some releases allow you to combine a security component with an immutable baseline to create a relatively stable version of the distribution, even though the mainline may evolve much faster.

- An “architecture” represents a specific class of hardware. The expectation is that machines within an architecture class will be similar enough that they can all run the same binaries. Architectures are instances of releases, for example, “Ubuntu Karmic Koola for x86_64.” Since components are subdivisions of releases, there’s a corresponding architecture-specific instance for each of them.

- Individual packages are the elements that make up components, and therefore, indirectly, releases. Packages are usually architecture specific and are versioned independently of the main release and other packages. The correspondence between packages and releases is implicit in the way the network repository is set.

The existence of components that aren't maintained by the distributor (e.g., Ubuntu’s “universe” and “multiverse”) raises the question of how these components relate to the core OS release. Can they really be a “component” of the specific release, or are they some other kind of animal entirely? From a package management perspective, the answer is clear: extras are a true component. They are associated with a specific release, and they evolve in tandem with it.

## RHN: the Red Hat Network

With Red Hat having gracefully departed from the consumer Linux business, the Red Hat Network has become the system management platform for Red Hat Enterprise Linux. You purchase the right to access the Red Hat Network by subscribing. You can use the Red Hat Network as a glorified web portal and mailing list. At its simplest, the Red Hat Network is not much different from the patch notification mailing lists that have been run by UNIX vendors for years. But more features are available if you're willing to pay for them. Current pricing and features, see rhn.redhat.com.

The Red Hat Network provides a web-based interface for downloading new packages as well as a command-line alternative. Starting with Red Hat Enterprise 5, the CLI tool is yum; before it was the dependency-inducing tool. yum lets you download and install new packages without human intervention. Once you register, your machines get all the patches and bug fixes they need without you ever to intervene.

The downside of automatic registration is that Red Hat decides what updates you run. You might consider how much you really trust Red Hat (and the software maintainers whose products they package) not to screw up. Some of the choices Red Hat has made when it comes to which compiler to ship, some folks might remain skeptical.

A reasonable compromise might be to sign up one machine in your organization for automatic updates. You can take snapshots from that at periodic intervals to test as candidates for internal releases.

## APT: the Advanced Package Tool

APT is one of the most mature package management systems. It's possible to upgrade an entire system using software with the apt-get command or even (with the Red Hat Network) to have your boxes continuously keep up to date without human intervention.

The first rule of using apt-get on Ubuntu systems (and all management of Debian packages) is to ignore the existence of dselect. It's not a bad idea, but the user interface is poor and can be intimidating to the novice user. Some documentation will try to steer you towards dselect, stay strong and stick with APT.

If you are using apt-get to manage a Ubuntu installation from a mirror, the easiest way to see the available packages is to visit the master list at packages.ubuntu.com. The web site includes a search interface. If you set up your apt-get server (see page 390), you will know what packages you have made available and you can list them in whatever way you want.
