# 18.6 NFSSTAT: DUMP NFS STATISTICS

nfsstat displays various statistics maintained by the NFS system. nfsstat -s shows server-side statistics, and nfsstat -c shows information for client-side operations. By default, nfsstat shows statistics for all protocol versions. For example:

$ nfsstat -c

| Client rpc |
| calls | callbacks | retrans | badx | timeout | wait | newcred | timers |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 64235 | 195 | 0 | 3 | 1592 | 0 | 0 | 886 |
Client nfs |
| calls | callbacks | nclget | nclsleep |
| --- | --- | --- | --- |
| 62613 | 3 | 62643 | 0 |
| null | getattr | setattr | readlink | root | read |
| --- | --- | --- | --- | --- | --- |
| 0% | 34% | 0% | 21% | 30% | | 2% |
| write | wrcache | create | remove | rename | link | symlink |
| --- | --- | --- | --- | --- | --- | --- |
| 0% | | | 0% | | 0% | | |
| mkdir | readdir | rmdir | fsstat |
| --- | --- | --- | --- |
| 0% | 6% | 0% | |

This example is from a relatively healthy NFS client. If more than 3% of RPC calls time out, it is likely that there is a problem with your NFS server or network. You can easily discover the cause by checking the badxid field. If badxid is near 0 with timeouts over 3%, packets to and from the server are getting lost on the network. You may be able to solve this by lowering the rsize and wsi mount parameters (and read block sizes).

If badxid is nearly as high as timeout, the server is responding, but too slowly. Either replace the server or increase the timeout parameter.

Running nfsstat and netstat occasionally and becoming familiar with their output will help you discover NFS problems before your users do.
