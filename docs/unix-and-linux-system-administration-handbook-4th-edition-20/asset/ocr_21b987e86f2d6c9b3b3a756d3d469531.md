CIDR simplifies routing information and imposes hierarchy on the routing process. Although CIDR was only intended as an interim solution along the road to IPv6, it proved to be sufficiently powerful to handle the Internet's problems for the better part of a decade.

For example, suppose that a site has been given a block of class C addresses numbered 192.144.0.0 through 192.144.7.0 (in CIDR notation, 192.144.0.0/21). Internally, the site could use them

+   - 1 network of length /21 with 2,046 hosts, netmask 255.255.258.0
- 8 networks of length /24 with 254 hosts, netmask 255.255.255.0
- 16 networks of length /25 with 126 hosts, netmask 255.255.255.128
- 32 networks of length /26 with 62 hosts, netmask 255.255.255.192

and so on. From the perspective of the Internet, it is not necessary to have 32, 16 or 8 routing tables for these addresses. They all refer to the same organization, and all the packets go to the same ISP. A single routing entry for 192.144.0.0/21 suffices. CIDR makes it easy to allocate portions of class A and B addresses and increases the number of available manifolds.

Inside your network, you can mix and match regions of different subnet lengths as long as the pieces fit together without overlaps. This is called variable subnetting. For example, for an ISP with the 192.144.0.0/21 allocation could define /30 networks for point-to-point customers, or /24s for large customers, and /27s for smaller folks.

All the hosts on a network must be configured with the same netmask. You can't tell one host that it is a /24 and another host on the same network that it is a /25.

# Address allocation

Only networks are formally assigned; sites must define their own host numbers to form complete IP addresses. You can subdivide the address space to subnets in whatever manner you like.

Administively, ICANN (the Internet Corporation for Assigned Names and Numbers) has delegated blocks of addresses to 5 regional Internet registries, and these regional authorities are responsible for doling out blocks to ISPs within their regions (see Table 14.4 on the next page). These ISPs in turn divide up their blocks and hand out pieces to individual clients. Only large ISPs should have to deal directly with one of the ICANN-sponsored address registries.

The delegation from ICANN to regional registries and to national or regional ISPs has allowed for further aggregation in the backbone routing tables. ISP customers who have been allocated address space within the ISP's block do not need individual routing entries on the backbone. A single entry for the aggregated block that points to the ISP suffices.
