# 9 Periodic Processes

Scripting and automation are the keys to consistency and reliability. For example, an adduser program can add new users faster than you can, with a smaller chance of making mistakes. Almost any task can be encoded in a Perl or Python script.

It's often useful to have a script or command executed without any human intervention. For example, you might want to have a script verify (say, every half-hour) that your network routers and switches are working correctly, and have the script send you when problems are discovered.¹

## 9.1 CRON: SCHEDULE COMMANDS

The cron daemon is the standard tool for running commands on a predetermined schedule. It starts when the system boots and runs as long as the system is up.

cron reads configuration files that contain lists of command lines and the times at which they are to be invoked. The command lines are executed by sh, so almost anything you can do by hand from the shell can also be done with cron²

# Chapter 9 Periodic Processes

A cron configuration file is called a "crontab", short for "cron table." Crontabs individual users are stored under /var/spool/cron. There is (at most) one crontab file per user: for root, for jsmith, and so on. Cron files are named with the login names of the users to whom they belong, cron uses to figure out UID to use when running the commands contained in each file. The cron command transfers crontab files to and from this directory.

Although the exact implementations vary, all versions of cron try to minimize the time spent repairing configuration files and making calculations. The cron command helps maintain cron's efficiency by notifying cron when the crontabs change. Ergo, you shouldn't edit crontab files directly, this may result in cron not notifying your changes. If you get into a situation where cron doesn't seem to acknowledge a modified crontab, a HUP signal will force it to reload on systems.

See Chapter 11 for more information about syslog.

cron normally does itself, but most systems keep a log file (usually /var/cron/log or /var/admin/cron/log) that lists the commands that were executed and the times at they ran. See Table 9.2 on page 287 for logging details.

On some systems, creating the log file enables logging, removing the log file turns logging off. On other systems, the log is turned on or off in a configuration file. Yet another variation is for cron to use syslog. The log file grows quickly and is rarely used; leave logging turned off unless you're debugging a specific problem or have auditing requirements.

## 9.2 THE FORMAT OF CRONTAB FILES

All crontab files on a system share a similar format. Comments are introduced with a pound sign (#) in the first column of a line. Each noncomment line contains six fields and represents one command:

```
minute hour dom month weekday
```

The first five tell cron when to run the command. They are separated by whitespace, but within the command field, whitespace is passed along to the shell. The fields in the time specification are interpreted as shown in Table 9.1.

## Table 9.1 Crontab time specifications

| Field | Description | Range |
| --- | --- | --- |
| minute | Minute of the hour | 0 to 59 |
| hour | Hour of the day | 0 to 23 |
| dom | Day of the month | 1 to 31 |
| month | Month of the year | 1 to 12 |
| weekday | Day of the week | 0 to 6 (0 = Sunday) |

# The format of crontab files

Each of the time-related fields may contain

- A star, which matches everything
- A single integer, which matches exactly
- Two integers separated by a dash, matching a range of values
- A range followed by a slash and a step value, e.g., 10-14/2 (Linux only)
- A comma-separated list of integers or ranges, matching any value

For example, the time specification

```
45 10 * * 1-5
```

"10:45 a.m., Monday through Friday." Hint: never put a star in the first field unless you want the command to run every minute.

There is a potential ambiguity to watch out for with the weekday and dom fields. Every day is a day of the week and a day of the month. If both weekday and dom are specified, a day need satisfy only one of the two conditions to be selected. For example,

```
0,30 * 13 * 5
```

"half-hour on Friday, and every half-hour on the 13th of the month," not every half-hour on Friday the 13th."

The command is the sh command line to be executed. It can be any valid command should not be quoted. The command is considered to continue to the end of the line and may contain blanks or tabs.

Although sh is involved in executing the command, the shell does not act as a login shell and does not read the contents of ~/profile or ~/.bash_profile. As a result, the command's environment variables may be set up something differently from what you expect. If a command seeks to work when executed from the shell fails when introduced into a crontab file, the environment is the likely culprit. If need, you can wrap your command into a script that sets up the appropriate environment variables.

Percent signs (%) indicate newlines within the command field. Only the text up to the first percent is included in the actual command. The remaining lines are given to the command as standard input.

Here are some examples of legal crontab commands:

```
echo The time now 'date > /dev/console
mail -s Reminder@email % Don't forget to write your chapters.
cd /etc; /bin/mail -s "Password file" evi < password
```

And below are some additional examples of complete crontab entries:

```
30 2 * * 1 (cd /home/joe/project; make)
```
