# Chapter 20 Electronic Mail

See page 583 for more information about DNS MX records.

For example, in the architectural diagram on page 754, MX records would direct incoming email from the Internet to the MTA in the demilitarized zone. After verification that the received email was free of viruses and spam was directed to valid local users, the mail could be replayed, with the following definition, to the internal routing MTA for:

```
define(`MAIL_HUB`, 'smtp:routingMTA.mydomain')
```

Likewise, client users would relay their mail to the SMART_HOST designated in the nullclient feature in their configuration. The SMART_HOST could then filter for viruses and spam so that your site did not pollute the Internet.

The syntax of SMART_HOST parallels of MAIL_HUB, and the default delivery agent is again relay. For example:

```
define(`SMART_HOST`, 'smtp:outgoingMTA.mydomain')
```

You can use the same machine as the server for both incoming and outgoing mail. Both the SMART_HOST and the MAIL_HUB must allow relaying, from the clients inside your domain and the MTA in the DMZ.

# Client configuration

If you site the paradigms illustrated in the mail system design section (page 753), most of your machines will be configured as clients who just submit mail generated by users and do not receive mail at all. One of sendmail's FEATURES, nullclient, is just right for this situation. It creates a config file that follows all mail to a central hub by SMTP. The entire config file, after the VERSIONID and OSTYPE lines, would be simply

```
FEATURE('nocanify')
FEATURE('mailserver')
EXPOSED_USER('root')
```

where mailserver is the name of your central hub. The nocanify sendmail not to DNS lookups or rewrite addresses with fully qualified domain names. All of that work will be done by the mailserver. This feature is similar to SMART_HOST and assumes the client is MASQUERADE_AS assembler. The EXPOSED_USER clause exempts root from the masquerading and so facilitates debugging.

The mailserver machine must allow relaying from its clients. Permission is granted in the access_db, described on page 785. The client must have an associated MX record that points to mailserver and must also be included in the mailserver's cw file (usually /etc/mail/host-names). These settings allow the mailserver to accept mail for the client.

sendmail should run as an MSA (without the -bd flag) if the user on the client machine can be taught to use port 587 for submitting mail. If not, run sendmail in daemon mode (-bd) but set the DAEMON_OPTIONS configuration to listen for connections only on the loopback interface.
