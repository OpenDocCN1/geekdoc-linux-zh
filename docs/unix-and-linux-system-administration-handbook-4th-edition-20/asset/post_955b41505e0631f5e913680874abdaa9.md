## Sharing System Files

## The point of LDAP

Until you've had some experience with it, LDAP can be a slippery point to grab hold of. LDAP by itself doesn't solve any specific administrative problem. There's no "primary task" that LDAP is tailor-made to handle, and since diverge widely in their reasons for deploying LDAP servers. So we move to the specifics of installing and configuring OpenLDAP, it's probably worth reviewing reasons why you might want to investigate LDAP for your site.

Here are the big ones:

- LDAP can act as a central repository for information about your users, including everything from your phone numbers and addresses to their login names and passwords.
- In a similar vein, you can use LDAP to distribute configuration information for ancillary applications. Most systems—sendmail, Exim, and Postfix—can draw a large part of their routing information from LDAP, and this is in fact one of LDAP's most popular applications. Tools varied as the Apache web server and the autofs automounter can be configured to pay attention to LDAP, too. It's likely that LDAP will become more and more common over time.
- LDAP makes it easy for applications (even written by other teams and other departments) to authenticate users without having to worry about the exact details of account management.
- Changes to LDAP data take effect immediately and are instantly visible to all hosts and client applications.
- It's easy to access LDAP data through command-line tools such as ldsearch. In addition, LDAP is well supported by common scripting languages such as Perl and Python (through the use of libraries). Ergo, LDAP is a terrific way to distribute configuration information for locally written scripts and administrative utilities.
- Well-backed tools are available for managing LDAP, examples being phpldap (phpldap.sourceforge.org) and Directory Administrator (dirad.open-it.org). These tools are so easy to use that you can just rip the box open and start without reading the manual.
- LDAP is well supported as a public directory service. Most major email clients support the use of LDAP to access user directories. Simple LDAP searches are also supported by many web browsers using the use of an LDAP URL type.
- Microsoft's Active Directory architecture is based on LDAP, and the current release of Windows Server includes extensions (originally called "Services for UNIX,") then "Windows Security and Directory Services for UNIX; and now "Windows Server 2008 UNIX Interoperability Components" that facilitate the mapping of UNIX users and groups. See Chapter 30, Operating with Windows, for more information about integrating your UNIX systems with Active Directory-based LDAP.

## OpenLDAP: the traditional open source LDAP server

OpenLDAP is an extension of work originally done at the University of Michigan; it continues as an open source project. It is shipped with many Linux distributions, though it is not necessarily included in the default installation. You'll need to download and install the software to run on Solaris, HP-UX, or AIX. The documentation is perhaps described as "brisk."

In the OpenLDAP distribution, slapd is the standard LDAP server daemon. In an environment with multiple OpenLDAP servers, slurpd runs on the master server and handles replication by pushing changes to slave servers. A selection of command-line tools enable the querying and modification of LDAP data.

Setup is straightforward. First, create an /etc/openldap/slapd.conf file by copying the sample installed with the OpenLDAP server.

These are the lines you need to pay attention to:

```
database bdb
suffix dc=mydomain, dc=com
rootdn cn=admin, dc=mydomain, dc=com
rootpw [crypt]{ab/ngaxhB/YWI
directory /var/lib/ldap
```

The database format for Berkeley DB, which is fine for data that will live within the OpenLDAP system. You can use a variety of other back ends, including ad hoc methods such as scripts that create the data on the fly.

suffix is your "LDAP baseline." It's the root of your portion of the LDAP namespace, similar in concept to your DNS name. In fact, this example illustrates the use of a DNS name as an LDAP baseline, which is a common practice.

rootdn is your administrator's name, and rootpw is the administrator's UNIX-format) password. Note that the domain components leading up to the administrator's name must also be specified. You can either copy or pass the password from /etc/shadow (if you don't use MD5 passwords) or generate it with a simple Perl one-liner

```
perl -e "print crypt('password','salt")",
```

where the desired password and salt is an arbitrary two-character string. Given the presence of this password, make sure that the permissions on your slap.conf file are 600 and that the file is owned by root.

Edit /etc/openldap.conf to set the default server and basename for LDAP client requests. It's pretty straightforward—just the argument of the host entry to your server and set the base to the same value as in slapd.conf. (Make sure both lines are uncommented.)

At this point, you should be able to start up by running it with no arguments.

## 389 Directory Server: alternative open source LDAP server

Like OpenLDAP, the 389 Directory Server (port389.org) is an extension of the work done at the University of Michigan. However, it spent some years in the commercial world before returning as an open source project.

There are many reasons to consider the 389 Directory Server as an alternative to OpenLDAP, but its superior documentation is one clear advantage. The 389 Directory Server comes with several professional-grade administration and use guides, including detailed installation and deployment instructions.

A few key features of the 389 Directory Server are:

- Multimaster replication for fault tolerance and high write performance
- Active Directory user and group synchronization

## LDAP instead of /etc/passwd and /etc/group

- A graphical console for all facets of user, group, and server management
- On-line, zero downtime, LDAP-based update of schema, configuration, and in-tree Access Control Information (ACIs)

As of this writing, the 389 Directory Server appears to have a more active-development community than OpenLDAP. We generally recommend it over OpenLDAP for new installations.

From an administrative standpoint, the structure and operation of the two open source servers are strikingly similar. This fact is perhaps not too surprising since both packages were built on the same original code base.

## LDAP instead of /etc/passwd and /etc/group

Client-side LDAP support is relatively easy to add. Some systems include the necessary nss_ldap package by default.

Client-side LDAP defaults for nss_ldap are set in /etc/ldap.conf, which shares its format with /etc/openldap.conf (described on page 732) but includes additional options to the name service and PAM contexts. You must also edit the /etc/nsswitch.conf on each client to add LDAP as a source for each type of data you want to LDAPify. The switch changes the C library for requests to the libnss library, which uses the /etc/ldap.conf information to figure out how to perform the LDAP queries. See Prioritizing sources of administrative information on page 739 for details.

RFC2307 defines the standard mapping from traditional UNIX data sets, such as the password and group files, for sysadmins using LDAP in a UNIX environment, it's a useful reference document at least in theory. In practice, the specifications are a lot easier for computers to read than for humans; you're better off at examples.

Pad Software offers a free set of Perl scripts that migrate flat files or NIS maps to LDAP. It's available from padl.com/OSS/MigrationTools.html, and the scripts are straightforward to run. They can be used as filters to generate LDIF, or they can be run against a live server to upload the data directly. For example, the migrate_group script converts this line from /etc/group

```
cssstaff:x:2033:matthew,trent
```

to the following LDIF:

```
dn: cn=staff,ou=Group,dc=classname,dc=com
cn: staff
objectClass: posixGroup
objectClass: top
```
