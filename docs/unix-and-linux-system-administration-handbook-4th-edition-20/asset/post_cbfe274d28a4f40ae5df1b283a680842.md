On Linux systems, the chage program controls password aging. Using change, administrators can enforce minimum and maximum times between password changes, password expiration dates, the number of days to warn users before their expire, the number of days of inactivity that are permissible before accounts are automatically locked, and more. The following command sets the number of days between password changes to 2, the maximum number to 90, the expiration date to July 31, 2010, and warns the user for 14 days that the expiration date is approaching:

![](img/579efec8c67772f31ecf34844bbb71a2_955_0.png)

```
$ sudo chage -m 2 -M 90 -E 2010-07-31 -W 14 ben
```

For more information about user account settings, Chapter 7.

Other systems implement password aging differently, usually with less granularity. Under Solaris, you set password aging preferences in /etc/default/password. Password aging on HP-UX systems is controlled through the smc console, and AIX it is configured in the file /etc/security/user.

# Group logins and shared logins

Any login that is used by more than one person is bad news. Group logins (e.g., "guest" or "demo") are sure terrain for hackers to homeless and are prohibited in many contexts by federal regulations as HIPAA. Don't allow them at your site. However, technical controls cannot prevent users from sharing passwords, so is the best enforcement tactic.

# User shells

In theory, you can set the shell for a user account to be just about any program, including a custom script. In practice, the use of shells other than standards as bash and tsch is a dangerous practice, and the risk is even greater for passwordless logins that have a script as their. If you feel tempted to create such a login, you might consider a passphrase-less SSH key pair instead.

# Rootly entries

The only distinguishing feature of the root login is its UID of zero. Since there can be more than one entry in the /etc/passwd file that uses this UID, there can be more than one way to log in root.

A common way for a hacker to install a back door after having obtained a root shell is to edit root logins into /etc/passwd. Programs as who and we refer to the name stored in utmp rather than the UID that owns the login shell, so they cannot expose hackers that appear to be innocent users but really logged in UID 0.

Don't allow root to log in remotely, even through the standard root account. Under OpenSSH, you can set the PermitRootLogin configuration option to No in /etc/ssh/sshd_config file to enforce this restriction.

On Solaris, you can use CONSOLE=/dev/console in /etc/default/login to prohibit root logins from locations beside the console.

## 22.5 PAM: COOKING SPRAY OR AUTHENTICATION WONDER?

PAM stands for “pluggable authentication modules.” The PAM system relieves programmers of the chore of implementing authentication systems and gives admins flexible, modular control over the system's authentication methods. Both the concept and the term come from Sun Systems (now part of Oracle) and from a 1996 paper by Samar and Lai of SunSoft.

In the distant past, commands like login included hardwired authentication code that prompted the user for a, tested the password against the encrypted version from /etc/shadow (/etc/passwd at that time), and, rendered a digest as whether the two passwords matched. Other commands (e.g., passwd) demanded similar code. It was impossible to change authentication methods without source code, and administrators had little or no control over details such as whether the system should accept “password” as a valid password. PAM changed all of that.

PAM puts its system routines into a shared library that login and other programs can call. By separating authentication functions into a discrete subsystem, PAM makes it easy to integrate new advances in authentication and encryption into the computing environment. For instance, multi-factor authentication can be supported without changes to the source code of login and passwd.

For the sysadmin, setting the right level of security for authentication has become a simple configuration task. Programmers win; they no longer have to write tedious authentication code, and more importantly, their authentication systems are implemented correctly on the first try. PAM can authenticate all activities: user logins, other forms of system access, use of protected websites—the configuration of applications.

# System support for PAM

All of our example systems support PAM. Configuration information goes in the /etc/pam.d directory (Linux) or in the /etc/pam.conf file (Solaris, HP-UX, and AIX). The formats of the configuration files are basically the same, but UNIX systems put everything in one file and the Linux systems have a file for each service or command that uses PAM.

PAM support is nearly universal at this point, if you're using other variants of UNIX and want to check whether your system uses PAM, you can run ldd /bin/login to see if binary links to PAM's shared library, libpam.

# PAM configuration

The control-flag system determines how the modules interact. The general format is:
[service] [control-flag] [module-path] [arguments]

The control-flags are:
- **required**: If the module fails, the stack eventually fails. If it succeeds, the stack continues.
- **sufficient**: If the module succeeds, the stack succeeds immediately. If it fails, the stack continues.
- **requisite**: If the module fails, the stack fails immediately. If it succeeds, the stack continues.
- **optional**: If the module fails, the stack only fails if no other sufficient module has succeeded.
- **include**: Includes another PAM configuration file.

The order of modules in the file is critical. For example, a `required` module should come before a `sufficient` module to ensure the check is performed.

# Table 22.1 PAM control flags

| Flag | Stop on failure? | Stop on success? | Comments |
| :--- | :--- | :--- | :--- |
| binding | No | Yes | Like sufficient, but can't fail the stack |
| include | | No | Includes another config at this point |
| optional | No | No | Significant only if this is the lone module |
| required | No | No | Failure eventually causes the stack to fail |
| requisite | Yes | No | Like required, but fails the stack immediately |
| sufficient | No | Yes | The name is kind of lie; see comments |

The interaction between these different control-flags can be complex, but for most cases, following the standard rules will suffice. Linux uses a slightly different set of these flags in terms of how it handles passwords, but the logic remains the same. If you're going to modify your systems' security settings, make sure that you understand the system thoroughly and that you double-check the particulars.

For example, here is a snippet of a typical PAM configuration:

```
# login service

login auth requisite pam_authtok_get.so.1
login auth required pam_dhkeys.so.1
login auth required pam_unix_cred.so.1
login auth required pam_unix_auth.so.1
login auth required pam_dial_auth.so.1
```
