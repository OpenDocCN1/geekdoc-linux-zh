# Naming conventions for devices

Naming conventions for devices are somewhat random. They are often holders from the ways they were done under UNIX on a DEC PDP-11, archaic as that may sound in this day and age.

For devices that have both block and character identities, the character device name is usually prefixed with the letter r for “raw” (e.g., /dev/da0 vs. /dev/rda0). An alternative convention is to store device files in a subdirectory that starts with t (e.g., /dev/dsk/dks0d3s vs. /dev/rdsk/dks0d3s). However, an r does not always imply a raw device file.

Serial devices are usually named tty by a sequence of letters that identify the port is attached to. TTYs are represented by more than one device file; the extras fully afford access to alternative control methods or locking protocols.

The names of tape devices often include not only a reference to the device itself but also an indication of whether the device rewinds after the tape device is closed. Each vendor has a different scheme.

The naming conventions for the files that represent hard disks and SSDs are rather complex on most systems. Disk device files on page 224 for details.

# Custom kernels versus loadable modules

When the system is installed, it comes with a generic kernel designed to run most applications on most hardware. The generic kernel includes many different device drivers and option packages. Some drivers may also be dynamically inserted into the running kernel. On Linux, the udev system can also manage device time changes, such as the insertion of a USB device.

There are various schools of thought on whether the production servers should have built-custom kernels. Although there is some potential for performance gains, especially in embedded systems without much memory, the manageable tradeoff for patching and system upgrades is a deal breaker. Unless there’s legitimate need to write every last ounce of performance out of the system, we recommend using the vendor’s stock kernel.
