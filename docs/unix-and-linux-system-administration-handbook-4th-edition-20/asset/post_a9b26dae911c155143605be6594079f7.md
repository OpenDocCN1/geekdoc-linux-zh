
## Chapter 22 Security

Software packages on the Internet are distributed with a PGP signature file that purports to guarantee the origin and purity of the software. However, it is difficult for people who are not die-hard PGP users to validate these signatures—not because the process is complicated, but because true security can only come from having a personal library of public keys from whose identities you have directly verified. Downloading a single public key with a signature file and software distribution is approximately same as downloading the distribution.

Some clients, such as Mozilla Thunderbird, have add-ons that provide a simple GUI for encrypted incoming and outgoing messages. Enigmail, the solution for Thunderbird, can even search on-line public key databases if for your recipient isn't already in your key ring. See enigmail.moz.dev for details.

## SSH: the secure shell

The SSH system, written by Tatu Yönen, is a secure replacement for login, rcp, and telnet. It uses cryptographic authentication to confirm a user's identity and encrypts all communications between the two hosts. The protocol used by SSH is designed to withstand a wide variety of potential attacks. The protocol is documented by RFCs 4250 through 4256 and is now a proposed IETF standard.

SSH has morphed from a freely distributed open source project (SSH1) to be a slightly different (and more secure) protocol, SSH2. Fortunately, the open source community has responded by releasing the excellent OpenSSH package (maintained by FreeBSD), which now implements protocols.

The main components of SSH are a server daemon, sshd, and a few user-level commands, notably ssh for remote logins and sftp/scp for copying files. Other components are an ssh-keygen command that generates public keys and a couple of utilities that help secure X Windows.

sshd can authenticate user logins in different ways. It is up to the administrator to decide which of these methods are acceptable:

- Method A: If the name of the remote host from which the user is logging is listed in ~/.hosts, ~/shosts, /etc/hosts.equiv or /etc/hosts, then ssh logs in the user automatically without a password check. This scheme mirrors that of the old login daemon and in our opinion is never acceptable for normal use.

- Method B: As a refinement of method A, sshd can also use public key cryptography to verify the identity of the remote host. For that to happen, the remote host's public key (generated at install time) must be listed in the local host's /etc/ssh/known_hosts file or the user's ~/.ssh/known_hosts file.

If the remote host can prove that it knows the corresponding private key (normally stored in /etc/ssh_host_key, a world-unreadable file), then sshd logs in the user without asking for a password.

Method B is more restrictive than method A, but we think it is still not enough enough. If the security of the originating host is compromised, the local site will be compromised as well.

- Method C: sshd can use public key cryptography to establish the user's identity. At login time, the user must have access to a copy of his or her private key file and must supply a password to decrypt it. The key can also be created without a password, which is a reasonable option for automating logins from remote systems.

This method is the most secure, but it's annoying to set up. It also means that users cannot log in when traveling unless they bring a copy of their private key file (perhaps on a USB key, hopefully encrypted).

If you decide to use key pairs, make extensive use of /ssh -y during the troubleshooting process.

- Method D: Finally, sshd can allow the user to enter his or her normal login password. This makes ssh behave much like telnet, except that the password and session are both encrypted. The main drawbacks of this method are that system login passwords can be weak if you have not beef your security, and ready-made tools (such as the John Ripper) have been designed to break them. However, this method is probably the best choice for normal use.

Authentication policy is set in /etc/ssh_config. This file gets filled with configuration stuff for you as of the installation process, you can safely ignore most of it. The options relevant to authentication are shown in Table 22.2.

## Table 22.2 Authentication-related options in /etc/ssh_config

| Option | Meth | Dfl | Meaning when turned |
| --- | --- | --- | --- |
| RhostsAuthentication | A | No | Obys ~hosts, /etc/ssh.equiv, etc. |
| RhostsRSAAuthentication | B | Yes | Allows ~hosts by key, but requires host key |
| IgnoreHosts | A | No | Ignores the ~/hosts and hosts.equivᵇ |

a. The authentication methods to which this variable is relevant
b. But continues to honor ~/hosts and hosts.equiv
c. Defaults to the value of IgnoreHosts

Our suggested configuration, which allows methods C and D but not methods A or or B, is as follows:

```
RhostsAuthentication no
RhostsRSAAuthentication no
RSAAuthentication yes
PasswordAuthentication yes
```

It is never wise to allow root to log in via sudo. Superuser access should be achieved through the use of sudo. To encourage this behavior, you use the option

```
PermitRootLogin no
```

The first time you connect to a new system through SSH, you are prompted to accept the server's public key (which is usually generated as part of the server's installation of OpenSSH, or soon thereafter). A truly paranoid user might manually verify it, but most of us blindly accept the key, which is then stored in the ~/.ssh/known_hosts file for future use. SSH won't mention the server's key unless it changes. Users' rubber-tapping the keys of systems leaves you vulnerable to a man-in-the-middle attack if the host key was actually being presented by an attacker's system.

A DNS record known as SSHFP has been developed to address this vulnerability. The premise is the server's key is stored as a DNS record. When a client connects to an unknown system, SSH looks up the SSHFP record to verify the server's key rather than asking the user to verify it.

The sshfp utility, available from xelerance/software/sshfp, generates SSHFP DNS resource records either by scanning a remote server or by parsing previously accepted key from the known_hosts file. (Of course, either choice assumes the source of the key is known to be correct). Usage is simple: use the -s flag to generate a key from a network scan, or use -k to change the known_hosts file (the default). For example, the following command generates a BIND-compatible SSHFP record for solaris.booklab.astrust.com.

```
solaris$ sshfp solaris.booklab.astrust.com
solaris.booklab.astrust.com IN SSHFP 1 1 94a2678ee713a3f6a78110fad9bd
saris.booklab.astrust.com IN SSHFP 2 1 7cf7d202e3d2f93a47125bcde0a6...
```

Add these records to the domain zone file (be careful of the names and the ORIGN), reload the domain, and use dig to verify the key:

```
solaris$ dig solaris.booklab.astrust.com IN SSHFP | grep SSHFP
;>>> 9.5.1-P2 << solaris.booklab.astrust.com IN SSHFP
solaris.booklab.astrust.com IN SSHFP 1 1 94a2678ee713a3f6a78110fad9bd
saris.booklab.astrust.com IN SSHFP 2 1 7cf7d202e3d2f93a47125bcde0a6
```

ssh does not consult SSHFP records by default. Add the VerifyHostDNS option to /etc/ssh_config to enable this. With most SSH client options, you can -o "VerifyHostDNS yes" on the command line when first accessing a new system.

SSH has a couple of ancillary functions that are useful for system administrators. One of these is the ability to tunnel TCP connections through an encrypted channel, thereby allowing connectivity to insecure or firewalled servers. This functionality is ubiquitous among SSH clients and is simple to configure. Exhibit A shows a typical use of SSH tunnel and should help clarify how it works.

## Exhibit A An SSH tunnel for RDP

![](img/579ec8c67772f31ecf3484bbb71a2_977_0.png)

In this scenario, a remote user wants to establish an RDP (remote desktop) connection to a Windows system on the enterprise network. Access to that host or to port 3389 is blocked by the firewall, but since the user has SSH access, he can route his connection through the SSH server.

To set this up, the user logs in to the remote SSH server with ssh. On the command line, he specifies an arbitrary (but specific; in this case, 9989) local port that ssh should forward through the secure tunnel to the remote Windows machine's port 3389.(For the standard OpenSSH implementation, the option to request this behavior is -Llocalport:remote.)

To access the Windows machine's desktop, the user then opens the remote desktop client (here, rdesktop) and enters localhost:9989 as the address of the server to connect to. The local ssh receives the connection on port 9989 and tunnels the traffic over the existing connection to the remote ssh. In turn, sshd forwards the connection to the Windows host.

Of course, tunnels such as these can be intentional or unintentional back doors as well. System administrators should use tunnels with caution and should also watch for unauthorized misuse of this facility by users.
