Although the elif form is used, a case selection is often a better choice for clarity. Its syntax is shown below in a sample routine that centralizes logging for a script. Of particular note are the closing parenthesis after each condition and the two semicolons that follow the statement block to be executed when the condition is met. The case statement ends with esac.

The log level is set in the global variable LOG_LEVEL. The choices are, from most to least, Error, Warning, Info, and Debug

```bash
function logMsg {
  message_level=$1
  message_itself=$2

  if [ $message_level -le $LOG_LEVEL ]; then
    case $message_level in
      0) message_level_text="Error" ;
      1) message_level_text="Warning" ;
      2) message_level_text="Info" ;
      3) message_level_text="Debug" ;
      *) message_level_text="Other"
    esac
    echo "$message_level: $message_itself"
  fi
}
```

This routine illustrates the common "log level" paradigm used by many administrative applications. The code of the script generates messages at many different levels of detail, but only the ones that pass a globally set, $LOG_LEVEL, are actually logged or acted upon. To clarify the importance of each message, the message text is preceded by a label that denotes its associated log.

# Loops

bash for... construct makes it easy to take some action for a group of values or files, especially when combined with filename globbing (the expansion of pattern-matching characters such as * and to form filenames or lists of filenames). The .sh pattern in the for loop returns a list of matching filenames in the current directory. The for statement iterates through that list, assigning each filename in the variable to $file.

```bash
#!/bin/bash
suffix=BACKUP-$(date +%Y%m%d-%H%M)
for script in *.sh; do
  newname=$script.$suffix
  echo "Copying script to $newname..."
  cp $script $newname
done
```

The output looks like:

```
$ sh rhel.sh.BACKUP-20091210-1708...
Copying rhel.sh to sles.sh.BACKUP-20091210-1708...
```

The filename expansion is not magic in this context; it works exactly as it does on the shell and the line is then processed by the interpreter in its expanded form. You could just as well have entered the filenames statically, as in the line

```bash
for script in rhel.sh sles.sh; do
```

- More accurately, the filename expansion is just a little bit magic that it does maintain a notion of the atomicity of each filename. Filenames that contain spaces will go through the for loop in a single pass.

In fact, any whitespace-separated list of things, including the contents of a variable, as a target of for...in.

bash also has the more familiar loop for traditional programming languages in which you specify starting, increment, and termination clauses. For example:

```bash
for (( i=0; i < $CPU_COUNT ; i++ )); do
  CPU_LIST=$CPU_LIST $i
done
```

The next example illustrates bash's while loop, which is useful for processing command-line arguments and running the lines of a file.

```bash
#!/bin/bash
exec 0<$1
counter=1
while read line; do
  echo "$counter: $line"
  $((counter++))
done
```

Here's what the output looks like:

- ubuntu$ sh example /etc/passwd
1: root:x:0:Superuser/root:/bin/bash
2: bin:x:1:1:bin:/bin/bash
3: daemon:x:2:2:Daemon:/bin/bash

This script has a couple of interesting features. The exec statement redefines the script's standard input to whatever file is named by the first command-line argument. The file must exist or the script generates an error.

The read statement within the while clause is in a shell built-in, but it acts as an external command. You can put external commands in a while clause as well; in that form, the while loop terminates when the external command returns a nonzero exit status.

The $((counter++)) expression is an odd duck, The ((...)) notation forces numeric evaluation. It also makes optional of $ to variable names. The ++ is the familiar increment operator from C and other languages. It returns the value of the variable to which it is attached, but has the side effect of incrementating variable's value as well.

The $((...)) shenanigans work in the context of double quotes, so the body of the loop could be collapsed down to one line.

- Depending on the invocation, exec can also have the more familiar meaning "stop this script and transfer control to another script or expression." It yet another shell oddity that both functions are accessed through the same statement.
