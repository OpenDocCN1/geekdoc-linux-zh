# Chapter 22 Security

Buffer overflows are a subcategory of a larger class of software bugs known input validation vulnerabilities. Nearly all programs accept some type of input from users (e.g., command-line arguments or HTML forms). If the code processes data without rigorously checking it for appropriate format and content, bad things can happen. Consider the simple example:

```
#!/usr/bin/perl
# Example input validation error

open(HTMLFILE, "var/www/html/\$ARGV[0]") or die "trying\n";
while(<HTMLFILE>) { print ; }
close HTMLFILE;
```

The intent of this code is to print the contents of HTML file at /var/www/html, which is the default document root for the Apache server over Red Hats. The code accepts a filename from the user and includes it as part of the argument to open. If a malicious user entered, ../../../etc/passwd would be echoed, the contents of /etc/passwd would be echoed

What can you do as an administrator to prevent this type of attack? Very little, at least a bug has been identified and addressed in a patch. Keeping up with patches and security bulletins is an important part of most administrators' jobs. Most Linux distributions include automated patching utilities, such as yum on Red Hat and apt-get on Ubuntu. OpenSolaris has also (and failsafe) updates implemented through pkg image-update. Take advantage of these utilities to keep your site safe from software vulnerabilities.

# Configuration errors

Many pieces of software can be configured securely or not-so-securely. Unfortunately, not-secure is often the default. Hackers frequently gain access by exploiting software features that could be considered helpful and convenient in less treacherous circumstances: accounts without passwords, disks shared with the world, and unprotected databases, to name a few.

A typical example of a host configuration vulnerability is the standard practice of allowing Linux systems to boot without requiring a boot loader. GRUB can be configured at install to require a password, but administrators almost always decline the option. This omission leaves the system open to physical attack. However, it's also a perfect example of the need for security against usability. Requiring a password means that if the system was unintentionally rebooted (e.g., after a power outage), an administrator would need to be physically present to get the machine running again.

One of the most important steps in securing a system is simply making sure that you haven't put out a welcome mat for hackers.
