# Serial Devices and Terminals

```
ubuntu$ seterial -g /dev/ttyS0
/dev/ttyS0, UART: 16550A, Port: 0x3f8, IRQ: 4
```

To set the parameters, you specify the device file and a series of parameters and values. For example, the command

```
ubuntu sudo seterial /dev/tty1 port 0x2f8 irq 3
```

sets the I/O port address and IRQ for ttyS1. It's important to keep in mind that this command does not change the hardware configuration in any way; it simply informs the Linux serial driver of the configuration. To change the actual settings of the hardware, consult your system's BIOS.

seterial changes only the current configuration, and the settings do not persist across reboots. Unfortunately, there isn't a standard way to make the changes; each of our example distributions does it differently.

+   The /etc/init.d/seterial script on Ubuntu systems is used for serial initialization. It reads parameters from each port from /var/lib/seterial/autoserial.conf.

+   SUSE's /etc/init.d/seterial handles serial port initialization. Unfortunately, this script has no configuration file; you must edit it directly to reflect the commands you want to run. Bad SUSE! The script uses its little metalanguage to construct the seterial command lines, but fortunately there are plenty of commented-out example lines to choose from.

+   Red Hat's /etc/rc.d/rcysinit script checks for the existence of /etc/rc.serial and executes it at startup time if it exists. No example file is provided, so you must create the file if you want to make use of this feature. Just list the seterial commands you want to run, one per line. For completeness, it's probably a good idea to make the file executable and to put #/bin/sh on the first line; however, touches d'élégance not strictly required.

# 31.7 Pseudo-terminals

Hardwired CRT terminals may be nothing more than museum fodder these days, but their spirit lives on the form of pseudo-terminals. These pairs of device files emulate a terminal interface on behalf of such virtual consoles, virtual terminals (e.g., xterm), and network login services telnet and ssh.

Here's how Each of the paired device files accesses the same device driver inside the kernel. A process that would normally interact with a physical terminal, such as a shell, uses the slave device in a physical device such as /dev/ttyS0. A host process /dev/ptyp1 opens the master device—in example, the pseudo-terminal device driver shuttles keystrokes and text between the two devices, hiding the fact that no physical terminal exists.

Although pseudo-terminals don't need a baud rate or flow control strategy, most of the other attributes and settings covered in this chapter apply to them.
