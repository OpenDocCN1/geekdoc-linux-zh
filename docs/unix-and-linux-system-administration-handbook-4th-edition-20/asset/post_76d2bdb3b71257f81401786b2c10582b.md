## A records

A (address) records are the heart of the DNS database. They provide the mapping from hostnames to IP addresses that were formally specified in the /etc/hosts file. A host usually has one A record for each of its network interfaces. The format is

```
hostname [ttl] [IN] A ipaddr
```

For example:

```
ns1 IN A 63.173.189.1
```

In this example, the name field is not-deterministic, so the name server adds the default domain to form the fully qualified name "ns1.atrust.com." The record associates that name with the IP address 63.173.189.1.

## PTR records

PTR (pointer) records map from IP addresses to hostnames. As described on page 566, reverse mapping records live under the in-addr.arpa domain and are named with the bytes of the IP address in reverse order. For example, the zone for 189 subnet in this example is 189.173.63-in-addr.arpa.

The general format of a PTR record

```
addr [ttl] [IN] PTR hostname
```

For example, the PTR record in the 189.173.63-in-addr.arpa zone that corresponds to ns1's A record above is

```
1 PTR ns1.atrust.com.
```

The name 1 does not end in a dot and therefore is relative. But relative to what? Not atrust.com—for this sample to be accurate, the default zone has to be "189.173.63-in-addr.arpa."

## MX records

You can set the zone by putting the PTR records for each subnet in their own file. The default domain associated with the file is set in the name configuration file. Another way to reverse mappings is to include records such as

- 1.189 IN PTR ns1.atrust.com.

with a default domain of 173.63.in-addr.arpa. Some sites put all reverse records in the same file and use ORIGIN directives (see page 596) to specify the subnet. Note that the hostname ns1.atrust.com ends with a dot to prevent the default domain, 173.63-in-addr.arpa, from being appended to it.

This all works if subsets are defined on both boundaries. But how do you handle reverse mappings for a subnet such as 63.173.180/26, where last byte can be in any of four subsets: 0-63, 64-127, 128-191, or 192-255? An elephant hack defined in RFC2317 exploits CNAME resource records to accomplish this feat; see page 585.

The reverse mappings provided by PTR records are used by any program that authenticates inbound network traffic. For example, sshd may allow remote logging without a password if the machine of is listed, in a user's ~/.hosts file. When the destination host receives a request, it knows the source machine by IP address. It uses DNS to convert the IP address to a hostname, which is compared to the appropriate file. netstat, sendmail, tcpd, ssh, Windows, and ftppd do reverse mappings to get hostnames from IP addresses.

It's important that A records match their corresponding PTR records. Matched PTR records cause authentication failures that can slow your system to a crash. This problem is annoying in itself; it can also facilitate denial of service attacks against any application that requires the reverse mapping to match the A record.

The mail system uses mail exchanger (MX) records to route mail more efficiently. An MX record preempts the destination specified by the sender of a message, in most cases directing the message to a hub at the recipient's site. This feature puts the flow of mail into the control of local sysadmins instead of senders. The format of an MX record is

```
name [ttl] [IN] MX preference host
```

The records below route mail to user@somehost.atrust.com to the mailserver.atrust.com if it is up and accepting email. If mailserver is not available, mail goes to mail-relay.atrust.com. If neither machine named in the MX records is accepting mail, the fallback behavior is to deliver the mail as originally.

Hosts with low preference values are tried first: 0 is the most desirable, and 10 is as bad as it gets (It might seem that this configuration is not robust both servers are in fact on different networks and are not co-located.)

```
somehost      IN MX 10 mailserver.atrust.com.
               IN MX 20 mail-relay.atrust.com.
```

But shouldn't, for security reasons. MX records are useful in many situations:

- When you have a central mail hub for incoming mail
- When you want to filter spam or viruses before delivering it
- When the destination host isnt directly reachable from the Internet
- When the local sysadmin knows where mail should be sent better than correspondents do (i.e., always)

Every host that the outside world would know should have MX records. Other entities in DNS need them, for example, hosts that can never receive email (e.g., network printers) should have MX records. The domain itself should have an MX record that points to a mail hub so that mail to user@domain work as expected (But not that configuration requires unique across all machines.)

Wild MX records are also sometimes seen in the DNS database:

```
* IN MX 10 mailserver.atrust.com.
```

At first glance, this record seems like it would save typing and add a default MX record for all hosts. But wildcard records don't work quite well as you might expect. They match anything in the name field of a resource record that is not already listed as an explicit name in another resource record. Thus, you cannot use a star to set a default value for all hosts. By perverse, you can use it to set a default value for names that. This setup causes lots of mail to be sent to your host only to be rejected the hostname matching the star really not belong to your domain. Ergo, avoid wildcard MX records.

## CNAME records

CNAME records are specified in RFC1035 (1987). CNAME records assign additional names to a host. These nicknames are commonly used either to associate a function with a host or shorten a long hostname. The real name is sometimes called the canonical name (hence, "CNAME"). Some examples:

```
ftp IN CNAME anchor
kb IN CNAME kibblesbit
```

The format of a CNAME record is

```
nickname [ttl] [IN] CNAME hostname
```

When DNS software encounters a CNAME record, it stops its query for the name and queries for the real name. If a host has a CNAME record, other records (A, MX, etc.) for that host must refer to the real name.

CNAME can nest eight deep. That is, a CNAME record can point to another CNAME, and that CNAME point to a third CNAME, and so on, up to seven times; the eighth target must be the real hostname. If you use CNAMEs, the PTR record should point to the real name, not a nickname.

You can avoid CNAMEs altogether by publishing A records for both a host's real name and nicknames. This configuration makes lookups slightly faster because the extra layer of indirection is not needed.

See page 460 for more information about CIDR.

## CNAME hack

CNAMEs are also used to torture the existing semantics of DNS into supporting reverse zones for networks that are not necessarily on a byte boundary. Before subnet assignments were commonplace, subnet assignments within the same organization, and the reverse delegations were easy to manage. For example, if the class B 128.138 was subnetted into a set of class-C networks, each subnet would make a tidy package for the in-addr.arpa domain. The reverse zone for the 243 subnet would be 243.128.138.in-addr.arpa.

But what if the 243 subnet is divided into four, say pieces network? If all four pieces are assigned to the same organization, there is actually no problem. The four subnets share a single file that contains all of their PTR records. However, if the 243 subnet is assigned to an ISP that wants to delegate each /26 network to a different customer, a complicated solution is necessary. The ISP must either maintain the reverse records of each client, or it must find a way to take the third octet of the IP address (243 in this case) and divide it into four different pieces that can be delegated independently.
