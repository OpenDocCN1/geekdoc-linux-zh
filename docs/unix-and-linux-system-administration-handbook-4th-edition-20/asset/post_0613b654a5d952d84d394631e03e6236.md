```
ubuntu$ sudo debconf-get-selections --installer > preseed.cfg
```

Make the config file available on the net and then pass it to the kernel installation with the following kernel argument:
preseed/url=http://host/path/to/preseed

The syntax of the preseed file, usually called preseed.cfg, is simple and reminiscent of Red Hat's ks.cfg. The sample below has been shortened for simplicity.

+   -d debian-installer/locale string en_US
-d console-setup/ask_detect boolean false
-d console-setup/layoutconfigure string
-d netcfg/choose_interface select auto
-d netcfg/get_hostname string unassigned-hostname
-d netcfg/get_domain string unassigned-domain
-d netcfg/wireless_webp string

+   -d partman-auto/disk string /dev/sda
-d partman-auto/method string lvm
-d partman-auto/choose_recipe select atomic
...

+   -d password/user-filename string Duffy Duck
-d password/username string dduck
d$1$/mk9$G$/it6N.x6670.951VSM/
-d user-setup/enter-home boolean false
tasksel/first/multiselect ubuntu-desktop
d-d grub-installer/only_debian boolean true
d-d grub-installer/with_other_os boolean true
d-d finish-install/reboot_in_progress note
xserver-org xserver-org/autodetect_monitor boolean true

Several options in this list display simple dialogs that would normally require user interaction. For example, the ask_detect disables keymap selection. Similarly, the wireless_webp fetches a question about WEP keys.

This configuration identifies a network interface that's connected to a network (choose_interface select auto) and obtains network information through DHCP. The system hostname and domain values are presumed to be provided by DHCP and are not overridden.

The partman* are evidence that the partman-auto package is used for disk partitioning. You must specify a disk to install unless the system has only one. In this case, /dev/sda is used.

Several partitioning "recipes" are provided:

+   - atomic puts all system's files in one partition.
- home creates a separate partition for /home.
- multi creates separate partitions for /home, /usr, /var, and /tmp.

You can create users through the password series of directives. As with Kickstart configuration, we strongly recommend providing MD5 hashed password values. Preseed files are often stored on HTTP servers and apt to be discovered by curious users. (Of course, an MD5 password is still subject to brute force attack.)

The task selection (tasksel) option chooses the type of Ubuntu system to install. Available values include standard, ubuntu-desktop, dns-server, lamp-server, kubuntu-desktop, edubuntu-desktop, and xubuntu-desktop.

The sample preset file shown above comes from the Ubuntu documentation at help.ubuntu.com. The guide contains full documentation for the syntax and usage of the preseed file.

The Kickstart functionality in Ubuntu's installer is missing a number of important features that are supported by Red Hat's Anaconda, such as LVM and fiery configuration. We recommend sticking with the Debian installer unless you have a good reason to choose Kickstart.

# 12.2 Installing Solaris

Like most hardware vendors, Sun ships new servers with Solaris preinstalled. Administrators need only answer a few quick questions and reboot the server before the operating system is ready for localization. We appreciated this preinstallation feature over the years because the Solaris installer was abysmal. The OpenSolar has seen the light, and the new installer (originally code "Caiman") is the bees' knees.

The Solaris media is now a live CD that provides a "try before you buy" experience, similar to Ubuntu. The installation process is extremely straightforward and asks only a few questions before installing to the local drive.

In the Linux world, Solaris administrators need to implement deployments over the network. Solaris systems running Intel processors can use PXE servers for network boot assistance, like their Linux-weielding siblings. Systems with SPARC processors use the OpenBoot PROM, aka OBP. The OBP is usually accessed with the STOP+A key on Sun keyboards. Identities and tests hardware, detects error conditions, and hands over the boot process to a more sophisticated boot loader, like the BIOS on Intel systems. Ubuntu has more features than most PC BIOSes, however, including built-in support for booting over a network.

# Network installations with JumpStart

The network boot feature obtains an IP address through DHCP or RARP, then downloads a kernel via TFTP. When booted for automated installation, the kernel connects to an HTTP server or mounts an NFS share to download an appropriate system image and start the installation.

Solaris offers two automatic network installation methods:

+   * JumpStart, the traditional installer service developed by Sun
* Automated Installer, a replacement service developed by OpenSolaris

JumpStart is a veteran installation tool that first appeared in Solaris 2.6 and can be used in all releases through Solaris 10. Like most automatic installation methods, JumpStart uses predefined answers file and rule-based client to select installation choices automatically.

The biggest drawback to JumpStart is its poor scalability. Each client must be manually added to the install server by MAC address. Configuration files specify installation types, configuration values, and other parameters on a per-client basis. This gives the administrator power and flexibility, but it becomes cumbersome when you have hundreds or thousands of systems.

The Automated Installer (sometimes referred to as AI) is the new kid on the block. Its primary development goals were improved scalability and reduced configuration. It has its roots in JumpStart but distances itself part through the use of new terminology. At the time of this writing, AI remains a work in progress, but it's more or less ready for production use. Notably, AI is limited to recent releases of OpenSolaris and currently does not work at all with traditional Solaris.

# Network installations with JumpStart

JumpStart's original purpose was to allow Solaris to be installed over a network, but it does have facilities for automatic installation as well. The Sun realized that more granular control was needed over the automated installations, so they added the advanced features now dubbed JumpStart. Automated network installation involves several components:

+   * An install server that hosts the media.
* A boot server that helps clients and points them toward the install servers.
* A series of files that identify clients, answer questions, and select packages.
* An NFS or HTTP server that shares configuration information.

Server-side components can all be located on the same machine. The servers are release-independent. For example, a SPARC-based Solaris 10 can offer installation services for x86.

Since boot parameters can be included in DHCP responses, you can use a DHCP server as an alternative to JumpStart. DHCP is probably the better option for clients on different subnet from the install server. We discuss the subsequent case here; refer to docs.sun.com/doc/817-5504 for more details.

Setting up an install server is straightforward. The setup tools are on the Solaris media. Insert the Solaris medium into the drive on the install server and run commands as the following to configure a simple install server:

```
solaris$ sudo mkdir -p /jumpstart/s10sparc
solaris$ cd /cdrom0/cdrom0/Solaris_10/Tools
solaris$ sudo ./setup_install_server /jumpstart/s10sparc
```

Here, we transfer the SPARC installation files to the /jumpstart/s10sparc directory on the install server. The setup_install_server script copies the files and adds the appropriate hooks for network-based installations. If only CD media are available, use the add_install_server command to replicate the contents of multiple CDs to the server.

Several files configure the automated tasks:

+* Rules file identifies clients and assigns installation profiles.
* Individual profile files specify partition layout, packages to install, and other system details.
* Sysidcfg files provide preconfigured answers to installation questions.
* Optionally, scripts can run before and after the installation process.

The first step in creating a JumpStart configuration is to create a directory for all the various configuration files:

```
solaris$ sudo mkdir -m 755 /jumpstart/config
```

This directory must be shared through NFS or HTTP so that clients can access it. For example, to share by NFS, add the line

```
share -F NFS /jumpstart
```

to /etc/dfs/fstab and run shareall to initiate NFS service.
