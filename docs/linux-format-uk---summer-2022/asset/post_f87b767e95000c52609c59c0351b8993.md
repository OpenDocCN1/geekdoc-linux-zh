### Focus on classes
Now that we can control the individual blocks, it would be nice to create a block at a time, as a single object. So we want to have separate objects for a block at a time to represent a block. In this example, a tetromino is actually a collection of four blocks. But it seems to be more efficient to have blocks as one object and then we don’t have to think about the different types of blocks. That is the object we’ll focus on.

The class below has a constructor, `__init__` method which takes colour and a list of blocks that make up the Tetromino. Each block has x, y position (the block is a square with side=1). Each block stores its own x and y.

```python
class Piece:
  def __init__(self, color, blocks):
    self.blocks = []
    for b in blocks:
      x, y = b
      self.blocks.append([x, y, color])
```

- Some other methods that the Piece object can have: move, rotate, check collisions

A move method allows the Piece to be moved in 2-D. A rotate method allows the Piece to be rotated around a point. Collisions are checked by looking at the current block and checking if it will collide with the wall or the ground.

In the constructor (the special method, `__init__`), a colour, a list of four blocks that make up the object are taken. In the constructor, we set self.color to color and self.blocks to the list of four x/y values.

As you can see, we can use a class to create a single piece of data, and then use that to make multiple pieces. That gives a more modular and readable structure to the code.

To get a game computer up and running we’re making modifications to this Linux kernel that has suffered from all the bugs that we’ve ever dreamed up. The only way to get it working properly is through the magic of a **kernel module**. A kernel module is a piece of code you can load onto the system. It gets compiled as a small object file that you then load onto the running system. It’s like a puzzle piece that slots into your running kernel.

So what makes a game computer great? For me it’s how responsive it feels. There’s two main ways you can tweak a kernel to get it working the way you want: changing the scheduler, or changing the timing.

The first is the **scheduler**, which manages how the processor hands out CPU cycles. The default Linux scheduler isn’t bad, but for a game we want it to know which processes are important and which can wait. The second is the **timing**, which controls how the system keeps time.

Every branch, main, paragraph that’s been built with us on the **control** is a **kernel module**. This is a self-contained piece of code. If you look at our GitHub repo, you’ll see it all. There are six main components that make up the game:

- The piece
- The board
- The AI
- The user interface
- The game loop
- The input

Each of these is a separate kernel module. They work together to make the game. They are also all **re-entrant**, meaning they can be loaded and unloaded at any time. This is important for development because you can test each piece individually. For example, you can test the AI against the user, or you can test the board without the AI.

```bash
sudo modprobe -r kernel_module
sudo modprobe kernel_module
```
