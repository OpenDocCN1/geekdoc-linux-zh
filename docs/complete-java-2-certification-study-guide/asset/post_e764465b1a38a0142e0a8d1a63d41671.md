
# Chapter 8 · The java.lang and java.util Packages

Apparently, the TreeMap class is a good substitute for the original HashMap class. You will see how easy it is to replace one collection implementation with another. Because all references to the hash map are of type Map (the interface) rather than type HashMap (the class), only one line of code needs to be modified: the line in which the hash map is constructed. That line originally was

Map map = new HashMap();

All that is required is to call default constructor:

Map map = new TreeMap();

Many data-processing methods pass references to map back and forth among themselves. In fact, the only major change that needs to be made is to dispense with the sort() method and the call to it. This modification is not relevant to the main point of this example which is how easy it is to replace one collection type with another. However, it is instructive to see how the modification is accomplished. The final code looks like this:

```java
private String getNext(int nShoppers) {
    Map<String, String> map = new TreeMap();
    for (int i = 0; i < nShoppers; i++) {
        map.put(getNext(), getNextEmail());
    }
    String[] keys = new String[nShoppers];
    Iterator<String> iter = map.keySet().iterator();
    int i = 0;
    while (iter.hasNext()) {
        keys[i++] = (String)iter.next();
    }
    return keys;
}
```

Here the Iterator on line 13 returns the elements of the map. Because the map is an instance of TreeMap, the keys are guaranteed to be sorted. This example shows the importance of referencing collections with the interface rather than class type.

# Generic Collections

If you have spent much time with Java's collection classes, you know that putting an object into a collection is lot easier than getting it out. This is because when you store an object you take advantage of conversion, but when you retrieve it are obliged to cast. For example:

```java
Vector myVec;
myVec = new Vector();
myVec.add(new Dragon());
// ... and later
Dragon otherDragon = (Dragon)myVec.get(0);
```

Java 1.5 lets you avoid the cast in many situations. Generic collections (or just generics) are collections whose members are of a single type that is known to the compiler.

NOTE: The 5.0 framework is backward compatible with Java 1.4, which means you don't need to rewrite all your code to use generics. Also, new code you write in 5.0 doesn't have to use generics, though it is always a good idea.

Generics provide two substantial benefits:

- Objects retrieved from generic collections need never cast.
- The compiler ensures that objects of the wrong type are not stored in generics.

The first benefit is convenience because casting is a nuisance. The second benefit eliminates bugs before they happen because the wrong object can never be stored in the wrong collection. To create a generic Vector that contains only dragons, you would use the following syntax:

```java
Vector<Dragon> myVec;
myVec = new Vector<Dragon>();
```

The identifier between angle brackets may be the name of any class or interface. The declaration on line 1 says that myVec is not merely a Vector but a Vector of dragons. You can think of the <Dragon> notation as part of the type, which is Vector but not Vector<Dragon>. Note that this appears on line 2, the Vector is constructed. If angle-bracket notation is used in a variable's declaration (as line 1), that variable should be used to reference an object without angle bracket (as line 2). If you don't follow this rule, you'll get a compiler warning (but your code will still compile).

The Vector of dragons constructed in lines 1 and 2 may contain only objects compatible with the Dragon class. The most common way to add to a Vector is to call the add() method. The compiler insists that the arguments of all add() calls made on myVec must be type Dragon or subclasses of Dragon. Assuming that class WaterDragon extends Dragon, the following code compiles:

```java
Vector<Dragon> myVec;
myVec = new Vector<Dragon>();
Dragon dragon = new Dragon();
myVec.add(dragon);
WaterDragon mango = new WaterDragon();
myVec.add(mango);
```

However, the following code does not compile:

```java
Vector<Dragon> myVec;
myVec = new Vector<Dragon>();
String s = "fireproof";
myVec.add(s);
```

Line 4 generates a compiler error.

When you retrieve a member of a generic vector, you may assign the retrieved value to a variable of the vector's type without casting. The following code is legal:

```java
Vector<Dragon> myVec;
myVec = new Vector<Dragon>();
Dragon dragon = new Dragon();
myVec.add(dragon);
Dragon d = myVec.get(0);
```

The compiler thinks that myVec contains dragons, line 5 the cast that would otherwise be required is omitted.

Iterators may be generic. To declare a generic Iterator, use the same angle-bracket notation that you use to declare a generic vector:

```java
Iterator<Dragon> iter;
```

When you call a generic Iterator's next() method, the returned value may be assigned without casting to a variable of the Iterator's type. For example:

```java
public void allDragonSeekasure(Vector<Dragon> vec) {
    Iterator<Dragon> iter = vec.iterator();
    while (iter.hasNext()) {
        Dragon d = iter.next();
        d.seekTreasure();
    }
}
```

Notice the absence of casting on line 4. This code can be simplified to:

```java
public void allDragonSeekasure(Vector<Dragon> vec) {
    Iterator<Dragon> iter = vec.iterator();
    while (iter.hasNext())
        iter.next().seekTreasure();
}
```

To appreciate the benefits of generic vectors and Iterators, compare the version above to the code that would be required without generics:

```java
public void allDragonSeekasure(Vector vec) {
    Iterator iter = vec.iterator();
    while (iter.hasNext())
        ((Dragon)iter.next()).seekTreasure();
}
```
