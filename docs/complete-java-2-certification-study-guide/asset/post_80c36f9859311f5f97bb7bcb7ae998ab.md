# Benefits of Object-Oriented Implementation

As a Java programmer and developer, you should have an understanding of the benefits of object-oriented design. These benefits accrue from two particular features of the OO. The first of these, and perhaps the most important, is the notion of encapsulation; the second and perhaps better known is the extensibility provided by inheritance.

## Encapsulation

Encapsulation is really just a fancy name for the aggregation of data and behavior. Consider the primitive types of any programming language you have ever used. You do not know how data items are stored and, for the most part, you do not care. What matters are the operations that you can perform on this data and the boundary conditions which you can expect those operations to work. These primitive types are in fact reference types, albeit not user-defined.

Your first goal in defining a good class should be to clearly the data members that describe instances of that class, keeping in mind that this should be done only with variables of private accessibility. Next, consider how to represent the behavior associated with these data.

# Objects Objects and Classes

Sometimes, perhaps as a consequence of the way you have stored the state in a class, boundary conditions must be applied to its methods. A boundary condition is a limit on the range of arguments for which a method can operate properly. For example, a square-root function cannot operate on a negative number unless imaginary numbers are included in its range; an odd operation cannot operate if both of its arguments are more than half the maximum value for the operation's return type.

When you encounter a boundary condition that results from your choice of storage format, you must make a choice. If you consider the boundary conditions reasonable, then you should do two things. First, detect the boundary condition. Next, test the boundary conditions at the entry to the method, and if the boundary condition exceeds, a runtime exception of some kind. Alternatively, you might decide that the boundary condition is not acceptable, in which case you should redesign the storage used in the class.

Now, consider this: if you allowed access to any of the variables to represent the object state, redefining the way the object's state is stored would immediately cause any other code that uses these variables to have to be rewritten. However, by using only member variables, you have insisted that all interaction with this object is made through methods and no direct variable access—so you have eliminated this problem. In consequence, you are able to redesign your internal storage freely and provided the signatures of all the methods remain the same, no other code needs to change.

# Re-use

How tight encapsulation can make code more reliable and robust. Now we will consider the most significant advantage of object-oriented programming: code re-use.

Writing good, encapsulated classes usually requires more work in the initial stages than would be required to produce the same functionality with a traditional programming approach. However, you will never find that using rigorous OO techniques will actually reduce the time required to produce finished code. This is the case for two reasons. First, the robust classes you produce require less time to integrate into the final program and less time to fix bugs. Second, with careful design, you can re-use classes in some circumstances that are different from the original intent of them.
