> Boxing also occurs when a method's return type is a wrapper. You do not need to explicitly construct a wrapped object. For example, you can now get away with the following:


The Java 5.0 compiler also allows you to unbox a wrapped value. Unboxing is the automatic extraction of a wrapped value. Unboxing happens when a wrapper object appears as a boolean or numerical operation, as shown in the example below:

- 1. Integer wi = 234;
2. int times9 = wi * 9;

Line 1 boxes to construct a wrapper object. Line 2 multiplies the wrapper by a (primitive) int. Prior to 5.0, it would not have compiled, so the 5.0 compiler edits that extracts (unboxes) the primitive value wrapped in wi and multiplies by 9. We can now rewrite the area() method as follows:

```
Double area(double radius) {
  return Math.PI * radius * radius;
}
```

This version of the method shows the power and convenience of boxing and unboxing. However, you should be aware that the boxing and unboxing syntaxes are just abbreviations. They do not eliminate the creation of wrapper objects or the extraction of wrapped values; they just hide these operations from the untrained eye. Consider the following code:

```
Double rad=0;
for (rad<=1; rad+=1.0e-9)
System.out.println(rad);
```

This code calls area() one billion times. The loop's increment step constructs (via the boxing mechanism) one billion wrapper objects, which later are garbage collected; it also extracts one billion wrapped values (via the unboxing mechanism). The radius() method unboxes and boxes once during each of its billion calls. The innocent-looking method has phenomenally more overhead than equivalent code that uses primitive primitives, but the overhead is visible only to people who understand the underlying mechanisms.

# The Collections Framework

Many programs need to keep track of groups of related data items. The most basic mechanism for doing this is the array. Although they are useful for many purposes, arrays have some limitations. For example, they provide only a very simple mechanism for storing and accessing data. Moreover, their capacity must be known at construction time because there is no way to make an array bigger or smaller. Java's collections classes and interfaces support much more general-purpose management.

![](img/09f8389b7ae2705d1ab14be2d5e857e3_302_0.png)

Collections are a mechanism for manipulating object references. Although arrays are capable of storing primitives or references, collections are not. If you need to take advantage of collection functionality to manipulate primitives, you will have to wrap the primitives in the wrapper presented earlier in this chapter.

Java's Collections API is often referred to as a framework, which consists of several interfaces and classes that implement these. The central interfaces are:

- java.util.Collection
- java.util.List (which extends Collection)
- java.util.Set (which also extends Collection)
- java.util.Map (which does not extend Collection)

There is more to than just interfaces and classes. The framework also defines semantics. In technical speech, "semantics" means "meaning." When people argue about the precise definition of a word, we say they are "quibbling about semantics."

For example, the Set interface has a method called addAll(). If you look up that method in the API page the return type is boolean and the argument sequence is a single Set. That's not semantics, it's just syntax: it tells you that addAll() in any implementing class takes a Set and returns a boolean; but it doesn't tell you what the method does. To learn what each method does, you must read the API's explanatory comment: "Adds all of the elements in the specified collection to this set if they're not already present." It's the class that defines the semantics, by explaining what it means to call it. All classes that implement the method will describe what action the method is called. Now you know the semantics of "semantics."

Since semantics of all the implementing classes are well defined (and easily found in the API pages), if you think you might want to use a collection in a particular situation, your decision process is straightforward. First figure out which interface (List, Set, or Map) is appropriate.
