covariant return types. A covariant return type of an overriding method is a subclass of the return type of the superclass version. Here's an example:

```
class Superclass {
  Number getValue() {
    return new Long(33);
  }
}
```

```
class TheSubclass extends Superclass {
  Float getValue() {
    return new Float(1.23f);
  }
}
```

The superclass version returns a Number. The subclass version returns a Float, which extends Number. This would be illegal without covariant return types.
The accessibility of an overriding method must not be less than the method it overrides, simply because it is to be the replacement method in conditions like those of the rectangular example. So, imagine that the setState() method of DisplayedRectangle was inaccessible from the main() method of the Testclass. The calls to recs[1].setSize() and recs[2].setSize() would be illegal, but the compiler would be unable to determine that it knows only that the elements of the array are Rectangle objects. The extends keyword literally requires that the subclass be an extension of the parent class: if methods could be removed from the class or less accessible, the subclass would not be a simple extension but potentially be a reduction. Under those conditions, the idea of treating DisplayedRectangle objects as being Rectangle objects when method arguments or elements of a collection would be severely failed.

A similar logic gives rise to the final rule relating checked exceptions. Checked exceptions are handled in the source you write. With accessibility, it must be possible for the compiler to make correct use of a variable of the parent class if that variable really refers to an object of a derived class. For checked exceptions, this means that an overriding method must not be able to throw exceptions that would not be thrown by the original method.
