The .ser suffix is conventional for files containing serialized objects. To read the stored object back into a program, you can do the following:

```
StringBuffer readStringBuffer()
    throws IOException, ClassNotFoundException {
    FileInputStream fis = new FileInputStream(\'sbuf.ser');
    ObjectInputStream ois = new ObjectInputStream(fis);
    StringBuffer sb = (StringBuffer)ois.readObject();
    ois.close();
    fis.close();
    return sb;
}
```

Notice that the value returned by readObject() is of type Object, so it must be cast. The read object is identical to the one that was written out in the previous code example.
The ObjectOutputStream has a writeUTF() method, as well as writeByte(), writeShort(), and all other write-primitive methods that appear in data output streams. The InputInputStream has corresponding read methods. If you want to create a file that contains serialized primitives as well as serialized objects, you can do it with a single output stream.

When you use object streams, it's important to know what information gets serialized and what does not. It is only an object's data that is serialized, not its class definition. Moreover, not all data is serialized. Static fields are not, because it would be inappropriate to change a static variable, which is shared by all instances of a class, just because one instance of the class was deserialized. To deserialize to convert a serialized representation into a replica of the original object.) (Transient fields are also not serialized. Serialization provides a level of security in situations where you are concerned that sensitive values are exposed. By declaring a variable to transient, you tell the JVM not to serialize it.

You might expect that private data would not be serialized, but in fact object streams have no access to methods. All non-static non-transient fields are written to output streams, regardless of whether they are public, private, or protected.
When an object is serialized, it will probably be deserialized by a different JVM. Any JVM that tries to deserialize an object must have access to that object's class. In other words, if the class is not already loaded, its class file must appear in the JVM's classpath. If this is not the case, readObject() will throw an exception.

When an object output stream serializes an object that contains references to other objects, every referenced object is serialized along with the original object. For example, consider a VectorBytes:

```
Vector<Byte> vec = new Vector<Byte>();
vec.add(new Byte(11));
vec.add(new Byte(22));
vec.add(new Byte(33));
```
