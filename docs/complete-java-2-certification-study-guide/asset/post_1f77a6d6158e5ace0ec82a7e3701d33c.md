
# Anonymous Class Declarations

As you have already seen, the structure of the code that declares and constructs an anonymous inner class is

```
new Xxx() { /* class body. */ };
```

where Xxx is a class or interface name. It is important to grasp that this code of this form is an *expression* that returns a value to an object. It is incomplete by itself but can be used wherever you can use object reference. For example, you might assign the reference to the constructed object into a variable, like this:

```
Xxxx anXxxx = new Xxx() { /* class body. */ };
```

Notice that you must be sure to make a complete statement, including the closing semicolon. Alternatively, you might use the reference to the constructed object as an argument to a method. In the case, the overall appearance is

```
someMethod(new Xxx() { /* class body. */ });
```

# Passing Arguments into the Construction of an Anonymous Inner Class

If the anonymous inner class extends another class, and parent class has constructors that take arguments, you can arrange for any of these constructors to be invoked by specifying the argument list to the construction of the anonymous inner class. An example follows:

```
// Assume this code appears in some method
Button b = new Button("Anonymous Button") {
    // behavior for the button
};
do things with the button b...
```

In this situation, the compiler will build a constructor for your anonymous inner class that effectively invokes the superclass constructor with the argument list provided, something like this:

```
// This is not the code you wrote! This exemplifies what the
 compiler creates internally when you're asked to compile something like the previous example
class AnonymousSubclass extends Button {
    public AnonymousSubclass(String s) {
    }
}
```

This isn't the actual code—but it conveys the general idea.

# Initializing an Anonymous Inner Class

Sometimes you will want to perform some kind of initialization when an inner class is constructed. In normal classes, you would create a constructor. In anonymous inner class, you cannot do this but you can use the initializer feature that was added to the language at JDK 1. If you provide an unnamed block in class scope, then it will be invoked as part of the construction process, like:

```java
public MyClass {
  // initializer
  System.out.println("Creating an instance");
}
```

This is true of any class, but the technique is particularly useful with inner classes, where it is the only tool you have that provides some control over construction.

# A Complex Example of Anonymous Inner Classes

Now lets look at a complete example following the pattern of the earlier example. This example uses two inner classes, one nested inside the other; an initializer; and a constructor that takes an argument:

```java
import java.awt.*;
import java.awt.event.*;

class X extends Frame {
    private int count;

    public static void main(String[] args[]) {
        X x = new X();
        x.pack();
        x.setVisible(true);
        final l = new Label("Count = " + count);
        add(l, BorderLayout.SOUTH);
        add(new ActionListener() {
            public void actionPerformed(ActionEvent ev) {
                count++;
                l.setText("Count = " + count);
            }
        }, BorderLayout.NORTH);
        add(new MouseAdapter() {
            public void mousePressed(MouseEvent ev) {
                // ...
            }
        });
    }
}
```

Lines 19–29 form the initializer and use a listener on Button; as we said earlier, we can arbitrarily nest these. Notice how label variable declared at line 14 is final; this allows it to be accessed from the inner classes.

# Contracts and Naming Conventions

In programming, as in life, a contract is an agreement about behavior; each party agrees to act in predictable ways and gains the right to expect predictable behavior from the other party. More precisely, a contract is an agreement that prescribes the behavior of some of class methods. Java's two most common contracts are the equals contract and the hash code. They describe the expected behavior of any equals() or hashCode() method. If a class's equals() and hashCode() honors the contract, the many useful classes can take advantage of which is described in Chapter 8, "The java.lang and java.util Packages."

The equals contract is described in detail on the API page for java.Object, which has several parts, of which important are:

- Any object should be equal to itself.
- If x equals y, then y equals x.
- If x equals y and y equals z, then x equals z.

The version of equals() inherited from Object uses the == operator to test for equality. If you override this behavior, the compiler will have no way to know whether your new version honors the contract. Your choices are to make sure it does or to forgo the benefits of, example, the Collections framework. If you violate the contract and use collections anyway, the resulting bugs could be very difficult to track down (This is useful information: if you have an elusive bug related to storing your class in a collection, check your equals() and hashCode() methods to make sure they obey their contracts).

The hash code specifies behavior of the hashCode() method. A hash code is an int that represents the uniqueness of an object; it is used by classes that need an efficient way to determine whether two objects contain different values. The contract is specified on the API page for java.lang.Object, in the hashCode() method description. It requires that if two objects are equal according to their equals() methods, then they must have hash codes. Note that the converse is not part of the contract; it is okay for unequal objects to have the same hash code.

Consider a class Point3D, representing a point in three-dimensional space. A reasonable implementation would do:

```java
public class Point3D {
    private int x, y, z;

    public boolean equals(Object ob) {
        Point3D that = (Point3D) ob;
        return this.x == that.x &&
               this.y == that.y &&
               this.z == that.z;
    }

    public int hashCode() {
        return x + y + z;
    }
}
```

Two instances of this class are equal if their x, y, and z values match. Clearly the hash code is honored. Note that it is possible for unequal instances to have equal hash codes. For example, one instance might have values (100, 200, 300) while another has values (600, 1, -1). This is acceptable. However, be aware that collection classes may slow down when dealing with unequal objects with equal hash codes.

A hash code algorithm would strike a reasonable balance between detecting uniqueness and running efficiently. You can avoid slow collisions by writing hashCode() methods that are scrupulous about uniqueness, but it does no good to speed up collection efficiency if your scrupulous hashCode() methods are inefficient. For example, you might wonder if the following alternative hashCode() version for Point3D:

```java
public int hashCode() {
    return (int)(Math.pow(2, x) +
                 Math.pow(3, y) +
                 Math.pow(5, z));
}
```

This version is unlikely to return equal codes for unequal objects, so collections containing Point3D instances will be efficient, but those three power operations will make the hashCode() method run too slowly.
