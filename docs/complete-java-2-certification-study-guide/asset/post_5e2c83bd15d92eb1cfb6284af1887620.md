# Arithmetic Error Conditions

> If you want to control the formatting of the converted result, you should use the facilities in the java.text package.

Now that you understand arithmetic operators and concatenation of text using the + operator, you realize that some arithmetic does not work as intended—it could result in an error of some kind. The next section discusses what happens under such error conditions.

We expect arithmetic to produce “sensible” results that reflect the mathematical meaning of the expression being evaluated. Because the computation is performed on a machine with specific limits on its ability to represent numbers, calculations can sometimes result in errors. You saw, in the section on the multiplication and division operators, that overflow and underflow occur if the operands are too large or too small. In exceptional conditions, the following rules apply:

- Integer division by zero, including modulo (%) operation, results in ArithmeticException.
- No other arithmetic causes any exception. Instead, the operation proceeds to a result, though might be mathematically incorrect.
- Floating-point calculations represent out-of-range values using IEEE 754 infinity, and Not a Number (NaN). Named constants representing these are declared in both the Float and Double classes.
- Integer calculations, other than division by zero, that cause overflow simply leave the final bit pattern in the result. This bit pattern is derived from the operation and number representation and may even be of the wrong sign. Because the operations and number representations do not depend upon platform, neither the result values.

These rules describe the effect of error conditions, but some additional significance is associated with NaN values. NaN values are used to indicate that a calculation has no result in ordinary arithmetic, such as calculations involving infinity or the square root of a negative number. Some floating-point calculations can return NaN. This occurs, for a result of calculating the square root of a negative number. NaN values are defined in java.lang package and are considered non-ordinal. This means that any value of x, including NaN itself, all the following comparisons return false:

```
x < Float.NaN
x <= Float.NaN
x == Float.NaN
x > Float.NaN
x >= Float.NaN
```

In fact, the test x != Float.NaN returns true, as you might deduce from the fact that x == Float.NaN gives false. The most appropriate way to test for NaN result from a calculation is to use the Float.isNaN(float) or Double.isNaN(double) static method provided in the java.lang package.

# Arithmetic Promotion of Operands

Arithmetic promotion of operands takes place before any binary operator is applied so that all numeric operands are at least int. This promotion has an important consequence for the unsigned right-shift operator applied to values narrower than int. The diagram in Figure 2.2 shows the process by which a byte is shifted. The first byte is promoted to int, treating the byte as a signed quantity. Next, the shift occurs, and 0 bits are propagated into the top bits of the result—but these bytes of the original byte. When the result is cast down to a byte, the higher-order bits of that byte appear to have been created by a signed shift, rather than an unsigned one. This is why you should not use the logical right-shift operator with operands smaller than int: it is unlikely to produce the result you expected.

# The Comparison Operators

Comparison operators <, <=, >, and != return a boolean result; the relation as written is either true or it is false. In addition, the instanceof determines whether or not a given object is an instance of a particular class. These operators are commonly used to form conditions, as in if() statements or in loop control. There are three types of comparison:

- Ordinal comparisons test the relative value of numeric operands.
- Object-type comparisons determine whether the runtime type of an object is of a particular type or a subclass of that particular type.
- *Equality comparisons* test whether values are the same and may be applied to values of non-numeric types.

# The Ordinal Comparisons Operators: <, <=, >, and >=

The ordinal comparison operators are:

- Less than: <
- Less than or equal to: <=
- Greater than: >
- Greater than or equal to: >=

These are applicable to all numeric types and to char and produce a boolean result. So, for example, given the following declarations the following tests all return:

```
p < q
f < q
f <= c
c > q
c >= q
```

That arithmetic promotions are applied when these operators are used. This is entirely according to the normal rules discussed in Chapter 4. For example, although it would be an error to assign the float value 9.0F to the char c, it is perfectly acceptable to compare the two. To achieve the result, Java promotes the smaller type to the larger type; hence the char value 'A' (represented by the Unicode value 65) is promoted to a float 65.0. The comparison is then performed on the float values.

Although the ordinal comparisons operate satisfactorily on dissimilar numeric types, including char, they are not applicable to any non-numeric types. They cannot take boolean or any class-type operands.

# The instanceof Operator

The instanceof operator tests the class of an object at runtime. The left argument can be any object expression, usually a variable or array element, whereas the right operand must be a class, interface, or array type. You cannot use a lang.Class reference or a String representing the name of the class as the right operand. A compiler error occurs if the left operand cannot be cast to the right operand.

Casting is discussed in Chapter 4.

This code fragment shows an example of how instanceof may be used. Assume that class hierarchy exists with Person as a base class and Parent as a subclass:

```java
public class Classroom {
  private Hashtable inTheRoom = new Hashtable();
  public void enterRoom(Person p) {
    inTheRoom.put(p.getName(), p);
  }
  public Person getParent(String name) {
    Object p = inTheRoom.get(name);
    if (p instanceof Parent) {
      return (Parent)p;
    } else {
      return null;
    }
  }
}
```
