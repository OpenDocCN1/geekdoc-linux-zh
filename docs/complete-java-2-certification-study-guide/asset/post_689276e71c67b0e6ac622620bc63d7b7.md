
# Lists

Lists are the most straightforward of Java's collections. A List keeps its elements in the order which they were added. Each element of a List has an index, starting from 0. So you can think of a List as something like an array that grows as needed (and can't contain primitives).

The java.util.List contains a few methods in addition to those inherited from the java.util.Collection interface. These include

```java
void add(int index, Object x) // Inserts at index. The index of each subsequent element is increased by one, so indices remain
```

```java
Object get(int index) // Returns the element at index.
```

```java
int indexOf(Object x) // Returns the index of the first occurrence of x, or -1 if the List does not contain x
```

```java
Object remove(int index) // Removes the element at index. The index of each subsequent element is reduced by one, so indices remain```

The most common class that implements List is Vector, which provides a straightforward implementation of the interface. The methods of Vector are synchronized so that multiple threads accessing a single instance don't have to worry about corrupting the vector's contents. The following code shows the wrapped elements 101 through 110 in a Vector and uses an Iterator to retrieve and print them:

```java
1. for (int i=101; i<=110; i++)
2. vec.add(i);
3.
4. Iterator iter = vec.iterator();
5. while (iter.hasNext())
6. System.out.println(iter.next());
```

Line 2 looks like an int to the Vector, which stores primitives; they store only object references. List takes advantage of boxing the int to the corresponding Integer. The code is equivalent to

```java
vec.add(new Integer(i));
```

In addition to Vector, three other classes in java.util.List exist. These are Stack, ArrayList, and LinkedList. The first two are simple. Stack extends Vector, adding push(Object), pop(), and peek(Object) methods to support classic stack behavior. ArrayList is nearly identical to Vector, but its methods are not synchronized.

LinkedList is an implementation that is used to support the operations of classic linked list and double-ended queue data structures. In addition to the methods of the List interface, LinkedList has methods addFirst(), getLast(), getFirst(), getLast(), removeFirst(), and removeLast(). These let you append, retrieve, and remove at either end of the List.

# Sets

You've seen that Lists are based on an ordering of their members. Sets have no concept of order. A Set is just a collection of references to objects.

Sets may not contain duplicate elements. If you try to add an element to a Set that already contains it the add() call will return false and the Set will not be changed. A true return might be expected. Sets use the equals() method, not the == operator, to check for duplicates of elements. You might be surprised by the following code:

```java
1. void addTwice(Set set) {
2.   set.clear();
3.   Point p1 = new Point(10, 20);
4.   Point p2 = new Point(10, 20);
5.   set.add(p1);
6.   set.add(p2);
7.   System.out.println(set.size());
8. }
```

The Point class in java.awt package is a simple class that contains x and y values. The class's equals() method returns true if the two points have identical x and y values. The Point instances created in lines 2 and 3 are distinct but equal. Sets use equals() to check for membership duplication, line 6 will not affect the Set, and line 7 will print out 1, not 2.

The java.util.Set interface extends java.util.Collection but does not add any methods. The most commonly used implementations are java.util.HashSet and java.util.TreeSet. Their names are, unfortunately, they refer to the underlying hash tables and red-black trees and aren't very descriptive of their purpose. It is important to understand the difference between the two, and that you need to understand what it means to iterate over a Set. When you use a List, the Iterator returns elements in their order of appearance. A List has an inherent sense of order, and it would make sense to present the elements in any order. But a Set has no order, so how should we return an Iterator? We can imagine three possibilities:

- 1. An Iterator could present elements in the order in which they were added.
- 2. An Iterator could present elements in an unpredictable order.
- 3. An Iterator could present elements in some sort of order.

Option 1 is not useful, since Lists already present elements in the order in which they were added. Option 2 is implemented by the HashSet class, and option 3 is implemented by the TreeSet class. When you iterate over a Set, you can't predict the order in which elements will be presented. The API for the HashSet class explains that no matter how many elements a Set contains, its basic operations (that is, add(), remove(), and contains()) always execute in constant time. When you iterate over a TreeSet, elements will always be presented in sorted order (whatever that means!). You might expect that there is a performance cost paid for maintaining order. In fact, as you can see in the TreeSet API, the amount of time required to perform an operation on a TreeSet is proportional to the logarithm of the number of elements in the set. Don't worry if you've forgotten your school math; you don't need to remember what a logarithm is. All you have to know is that as a TreeSet's population grows, the time to perform basic operations increases, but not drastically.

The TreeSet class implements java.util.SortedSet, which extends java.util.Set. The SortedSet interface provides several useful methods that support dealing with sorted data. These include:

- **Object first()** Returns this set's first element.
- **Object last()** Returns this set's last element.
- **SortedSet headSet(Object to)** Returns a sorted set containing this set's elements through the specified element.
- **SortedSet tailSet(Object from)** Returns a sorted set containing this set's elements from the specified element through the end.
- **SortedSet subSet(Object from, Object to)** Returns a sorted set containing this set's elements from to to.

So do you choose which set to use? If you care about iteration order, use a TreeSet and pay the time penalty. If iteration order doesn't matter, use the higher-performance HashSet.

But what does iteration order mean? If a Set contains only instances of Integer or String, you would have elements presented in numerical or alphabetical order, and that is what would happen. There is nothing magic about this. Sets rely on all their elements implementing the java.lang.Comparable interface, which defines a single method:

```java
public int compareTo(Object x)
```

The method returns a positive number if the current object is "greater than" x, by whatever definition of "greater than" the class itself uses. The method returns a negative number if the current object is "less than" x, and 0 if the current object is "equal to" x. When you add an object to a TreeSet, the TreeSet maintains order by calling compareTo() on its elements and on the object added. There's something going on there. Did you spot? TreeSet implements Collection, and Collection's add() method has an argument of type Object. But the internals of TreeSet require a Comparable, not an Object. This requirement isn't enforced by the compiler. You just have to know that you can store only Comparables, and if you forget, you'll get into trouble at runtime. You're fine as long as your TreeSet contains only one element. When you try to add a second element, the TreeSet needs to determine how the element compares to the first. The second element is cast to Comparable, and if the case is illegal, a ClassCastException is thrown. That makes you uneasy about using TreeSets; don't worry. The problem can be completely eliminated by using generics which are discussed a little later in this chapter.

Many of the Java classes can reasonably be thought of as having an inherent order. These all implement Comparable. So, for example, if you want to store some strings or wrappers in a TreeSet, you don't need to worry about getting that ClassCastException at runtime.

The following method generates random numbers, wraps them, and stores them in a TreeSet. The TreeSet's contents are printed out in their natural order:

```java
1. static void sortRandoms(int nRandoms)
2. {
3.    TreeSet set = new TreeSet();
4.    for (int i = 0; i<nRandoms; i++)
5.        set.add(Math.random());
6.
7.    Iterator iter = set.iterator();
8.    while (iter.hasNext())
9.        System.out.println(iter.next());
10. }
```

Once again, we have used boxing as a convenience for avoiding typing. Line 5 is equivalent to `set.add(new Double(Math.random()));`.

Here is a sample of output from the method:

```
0.09753898485505195
0.14214429064845446
0.2406814471249824
0.374633033848745
0.4430642976965066
```
