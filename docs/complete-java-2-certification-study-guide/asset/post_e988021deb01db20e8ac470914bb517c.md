
# Common-Sense GUI Design

You could spend years mastering the principles of modern GUI design. You probably don't want to make that kind of commitment, though, and the exam expects you only to show good common sense. You can't get into much trouble if you remember the goal of a GUI is to make life easier for your users. With that in mind, I will review three principles that are easy to understand and implement: standardization, resizing, and disabling the impossible.

The first principle is standardization. Look at several programs that you use frequently: a web browser or a mail reader, for example. What features do they have in common? Do they share these features with many other less-used programs?

It's difficult to find a successful program that *doesn't* have most of the following:

- A menu bar at the bottom of the main frame
- A File menu at the far-end of the menu bar
- One or more toolbars below the menu bar
- A work area below the toolbar(s)
- A status bar at the bottom of the main frame

Standardized features are good because they put expected functionality in places. People who apply your application for the first time can extend their learning how to use the unique parts of creates. If I try to use your program to create a new file of whatever your program creates, and don't find a New... menu item at the top of a File menu at the left of a menu bar at the top of a main frame, then I have to spend figuring out where you put the file-creation functionality. Every time my comfortable habit of looking in the File menu fails, I would prefer to spend my time using your program to get useful work.

This does not mean that you should implement all standard features whenever you create a GUI. Rather, if your GUI provides standard functions, then the controls for those features should appear in standard places. For-example, every GUI needs a way to quit, and the Exit menu item goes at the bottom of the File menu. But you need to provide a menu bar to hold the File menu, which holds the Exit menu item. But not every GUI needs a status bar. You need to provide one only if your program generates helpful status information. Similarly, if your GUI supports standard functionality, then functionality should be controlled in a standard way.

The second principle concerns resizing. What you saw in Chapter 12, "Layout Managers," is that Java provides sophisticated layout managers to ensure appropriate resizing of components. If components are too large, screen space is wasted. If components are too small, they are difficult to use.

But what makes a component too large or small? Generally the best size for a component is its preferred size. Often components that aren't their preferred size look this especially some of text components, whose preferred height is determined by the font and preferred width is determined by the label. Consider the dialog created by the following code:

```
JDialog dialog = new JDialog();
Container cont = dialog.getContentPane();
cont.setLayout(new GridLayout(1, 2));
cont.add(new JLabel("Name:"));
cont.add(new JTextField(10));
```

The dialog is shown in Figure 14.1.
If you look closely at the text field, you'll see that it isn't as wide as it could be. There's a small area of wasted space between the label and the text field. The wasted space grows if the dialog becomes wider, as in Figure 14.2.

Figure 14.2 shows the downside of using a Grid layout manager for this dialog. When a user resizes the dialog, their intention is to get more space for typing in a name. They don't need a wider label, but that's exactly what they get, thanks to the Grid layout manager's blind fairly policy of sharing all new pixels among all child components.
It's even worse when the dialog becomes taller as well as wider. Look at Figure 14.3.

In addition to the width problem, this dialog now has a height problem. The text field has become taller, but the font hasn't grown. The text looks lost in the middle of all that background.
As a general principle, it isn't enough to think about the size of a component at the moment it is displayed. You need to consider the consequences of resizing. In our example, a more sophisticated layout scheme is used for:

```
JDialog dialog = new JDialog();
Container cont = dialog.getContentPane();
cont.setLayout(new GridBagLayout());
GridBagConstraints gbc = new GridBagConstraints();
gbc.gridx = 0;
gbc.gridy = 0;
gbc.gridwidth = 1;
gbc.gridheight = 1;
gbc.weightx = 0;
cont.add(new JLabel("*"));
```
Now even in its initial appearance the label's width is appropriate, as seen in Figure 14.4. When the dialog resizes, the components stay the right, as seen in Figure 14.5.

# Common-Sense GUI Design

Our last principle of GUI design can be called "disabling the impossible." A GUI should make it impossible for a user to configure a request that the GUI cannot fulfill. As a simple example, think about typing a credit card number into a web page. What would you type the first digits? A space? A hyphen? The next digits? Have you guessed wrong and had to wait for an error message page that tells you without entering the required format? Then you have to remember what you typed into the original page, which is now gone forever. It would be better if the error message page told you how it was wrong. It would be better if the original form made it impossible to type a bad format, either by accepting all formats, or by prompting you as in Figure 14.6.

In the figure, it's obvious that digits are separated by hyphens, and it's equally obvious that the user shouldn't type any hyphens—because they're already there. The ultimate in user-friendliness would be if the field accepted only digits as input.

Another example, consider a form for ordering ice cream. Suppose the ice cream stands only chocolate, vanilla, and strawberry. Figure 14.7 would be the wrong way to prompt for input.

What happens if the user uses an unavailable flavor or misspells an available flavor, in the figure? This kind of GUI usually flashes a dialog box that says something irritating like, "Flavor unavailable, please try again." This is a waste of the user's time. The GUI should make it impossible to specify an unavailable flavor or miss an available one. Since the program already has access to the list of available flavors, it should present users with all legal options and allow them to choose from those options. This can be done with a combo box or group of radio buttons as shown in Figure 14.8.

Now there's no possibility of misspelling, because the GUI doesn't require typing. There's no possibility of requesting a flavor that isn't sold at this virtual ice cream stand, because only the available flavors are displayed. Users have no way to request a service that the GUI doesn't provide.

Most error dialogs in GUIs complain about invalid input. When your GUI code includes an error dialog, ask yourself whose fault the error is. It might really be your fault, for creating the conditions for the user to make an invalid request.

There is much more that could be said about creating great GUIs, but our purpose isn't to make you the world's greatest user interface designer. We're just here to get you a good grade on your exam, and you'll be fine if you keep in mind the principles of standardization, resizing, and disabling the impossible.

# Using the jar Tool

A jar file is a Java archive file. Its format is compatible with zip files and tar files. The jar command resides in the Java/bin directory. You invoke it by typing a command line, for example:

```
jar -cvf sources.jar *.java
```

-cvf is a cluster of options. The c is the most important option; that starts a new jar file to be created. jar can create, extract, list the contents of, or update an archive file. To specify which operation is performed, the first argument (after the hyphen) must be c, x, t, or u. Think of these as primary options. The remaining options are secondary; they tell how to do its job.

Table 14.1 shows some of jar's secondary options.

The v option means that jar prints detailed information about every file it adds to or extracts from the archive. The -o option, is used only when creating or updating, overrides jar's compression algorithm, which is compatible with zip algorithm and produces nearly the same degree of compression. The -m option, also only used when creating or updating, tells jar not to create a manifest inside the archive. A manifest is a file that provides information about the jar's contents; by default jar creates one for you. The -f and -m options each require that you specify a filename in the command line. The -f specifies the name of the file to be created, extracted, listed, or updated. The -m option is used when you use your own manifest file, which you do when you want to make an executable archive.
