# Blocking

Many methods that perform input or output have to wait for some occurrence in the outside world before they can proceed; this behavior is known as *blocking*. A good example is from a socket:

+   1. try {
2. Socket sock = new Socket("magnesium", 5505);
3. InputStream istr = sock.getInputStream();
4. int b = istr.read();
5. }
6. catch (IOException e) {
7. // Handle the exception
8. }

It looks like line 4 reads a byte from an input stream that is connected to port 5505 on a machine called magnesium. Actually, line 4 *tries* to read a byte. If a byte is available (that is, magnesium has previously written a byte), then line 4 can return immediately and execution can continue. If magnesium has not yet written anything, the `read()` call has to wait. If magnesium is busy doing other things and takes an hour to get around to writing a byte, then the `read()` call has to wait for half an hour.

Clearly, it would be a serious problem if the thread executing the read() call on line 4 remained in the Running state for the entire hour. Nothing else could get done. In general, if a method needs to wait an indeterminate amount of time until some I/O occurrence takes place, then a thread executing that method should graciously step out of the Running state. All Java I/O behave this way. A thread that has graciously stepped out in this fashion is said to be *blocked*. Figure 7.4 shows the transitions of the Blocked state.
