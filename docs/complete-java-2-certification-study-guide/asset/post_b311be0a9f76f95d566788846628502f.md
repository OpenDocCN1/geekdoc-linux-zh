# Encodings

The preceding discussion has avoided a crucial point. Consider a reader who reads from a file and returns strings of Unicode. How does the reader know how to translate an 8-bit character from the disk into a 16-bit character inside the JVM? Similarly, how does a file writer know how to translate a 16-bit Unicode character into an 8-bit byte?

The whole idea of readers and writers is that they connect the world inside the JVM, where characters are strictly 16-bit Unicode, to the external world, where text is historically presented as ordered sequences of bytes. Bytes represent different characters on where they appear in the world. Only 256 combinations are available in a byte; in different languages and cultures map these combinations to different characters, and thus to different Unicode values. Readers and writers are sensitive to these linguistic and cultural differences.

An encoding is a mapping between 8-bit characters and Unicode. Figure 9.5 shows a few of the encodings that have been established by the Unicode Consortium. The figure is not drawn to scale. Note that some encodings are small (Greek requires only 144 Unicode), whereas others are huge (more than 50,000 values for Chinese, Japanese, and Korean characters; in the 8-bit world, such a character is represented by a sequence of multiple bytes.

Modern operating systems know what part of the world they are operating in—they are given this information when they are installed. The machine's locale is accessible to the JVM. By default, the encoding used by a reader or writer is the one appropriate to the machine's locale. However, readers and writers have forms of constructors that allow you to specify any desired locale. (You specify a locale by providing a string that identifies it.)

When the data written by a writer is to be read within the same locale, you don't need con encoding to use; the default encoding will be appropriate. On the other hand, it may be that the data will cross a locale boundary. The writer might be connected to a socket, which communicates with a machine in a different locale. Or perhaps the writer is writing to a file of a floppy disk that will be carried across a boundary. In such cases, the people involved must agree on encoding; the common practice is to use the U.S. ASCII encoding. For programmers in the United States, this is conveniently the default. Others must specify this encoding when constructing readers and writers. The strings that denote encoding names are determined by standards committees, so they are not especially obvious or informative. For example, the U.S. ASCII encoding is not USASCII as you might expect, but rather ISO-8859-1.

# Object Streams and Serialization

As you have seen, input and output streams allow you to read and write primitives and strings, rather than individual bytes. Object streams go one step beyond data streams by allowing to read and write entire objects.

The process of writing an object is called serialization. To serialize an object, first create in instance of io.ObjectOutputStream. This class, like DataOutputStream, expects to be chained onto a lower-byte-oriented stream such as a file output or a socket's output stream. The method uses an object stream to store a string buffer in a file named suffer.

```
void writeStringBuffer(StringBuffer writeMe)
  throws IOException {
    FileOutputStream fos = new FileOutputStream("buf.ser");
    ObjectOutputStream oos = new ObjectOutputStream(fos);
    oos.writeObject(writeMe);
    oos.close();
    fos.close();
}
```

The .ser suffix is conventional for files containing serialized objects. To read the stored object back into a program, you can do the following:

```
StringBuffer readStringBuffer()
    throws IOException, ClassNotFoundException {
    FileInputStream fis = new FileInputStream("buf.ser");
    ObjectInputStream ois = new ObjectInputStream(fis);
    StringBuffer sb = (StringBuffer)ois.readObject();
    ois.close();
    fis.close();
    return sb;
}
```

Notice that the value returned by readObject() is of type Object, so it must be cast. The read object is identical to the one that was written out in the previous code example.
The ObjectOutputStream has a writeUTF() method, as well as writeByte(), writeShort(), and all other write-primitive methods that appear in data output streams. The InputInputStream has corresponding read methods. If you want to create a file that contains serialized primitives as well as serialized objects, you can do it with a single output stream.
