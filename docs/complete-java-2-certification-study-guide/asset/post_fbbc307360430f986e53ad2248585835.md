There are two phrases that are commonly used when describing a class in plain English: “is a” and “has a.” As a working simplification, they are used to describe the superclass and member variables, respectively. For example, consider this description:
“A home is a house that has a family and a pet.”
This description would give the outline of a Java class in this form:

```java
1. public class Home extends House {
2.     Family inhabitants;
3.     Pet getPet;
4. }
```

Notice the direct correspondence between the “is a” clause and the extends clause. In this example, a direct correspondence also exists between the items listed after “has a” and the variables. Such a correspondence is representative of simple examples and in a test situation; however, you should be aware that in real examples, there are other ways to provide a class with attributes. The most important of these alternatives is the approach taken by JavaBeans, which is to supply accessor and mutator methods that operate on data members.

## Methods, Overloading and Overriding

As you construct classes and add methods to them, in some circumstances you will want to re-use the same name for a method. You can do so two ways with Java. Using the same method with different arguments and perhaps a different return type is known as overloading. A method can be re-used anywhere, as long as certain conditions are:

- In an unrelated class, no special conditions apply, and the two methods are not considered related in any way.
- In the class that defines the original method, or a subclass of that class, the method name can be re-used if the argument list differs in terms of the type of at least one argument. this is overloading. It is important to realize that a difference in return type or list of thrown exceptions is insufficient to constitute an overload and is illegal.
- In a strict subclass of a class that defines the original method, the method name can be re-used with identical argument types and order with identical return type. this is overriding. In this case, additional restrictions apply to the accessibility of, and exceptions that may be thrown.

## Coupling and Cohesion

After object-oriented programming has been practiced for a while, the research community coined the terms “coupling” and “cohesion” to describe two related qualities of object-oriented programs. The Programmer’s Exam requires you to be familiar with these concepts.

*Coupling* is an object's reliance on the internals of another entity's implementation. When an object A is tightly coupled to object B, a programmer who wants to use or modify A is required to have inappropriately extensive expertise in how to use B.

The best insurance against coupling classes is good encapsulation. However, Java's access model makes it possible to create coupling between two instances of the same class, even if that class is well encapsulated. Recall from Chapter 3, “Modifiers,” that an object's private data and methods may be accessed by any instance of that class. If an instance accesses another's private data or methods, the result is tight coupling.

*Cohesion* is the degree to which a class or method resists being broken down into smaller pieces. Cohesion is desirable and easy to recognize in its absence.

Consider a *Telescope* class with methods that aim and focus a telescope and other methods that process the image captures. If you were modeling the Hubble, your class would have a lot of methods of each type. If you looked at the class’s source, you would probably find that the finding and programming methods each call each other, but they wouldn’t call the image-processing methods or access the image-processing data. The converse would also be: the image-processing code wouldn’t have much contact with the aiming/focusing code.

A class like *Telescope* can be split into distinct elements that probably model not one but two (or more!) real-world objects. Such a class would be divided into its constituents.

Methods as classes can have or lack cohesion. A low-cohesion method can often be spotted by the presence of “and” in its name. For example, if you’re reading the source code for a Java-based-guitar-playing robot, you might come across a method `tuneStringAndPlayMinorScale()`. Obviously this method performs two different tasks; the only reason they are together is playing a scale on a string is often done right after tuning that string. But often isn't *always*. If you separate the code into `tuneString()` and `playMinorScale()`, then people have the option of playing a different scale, or not playing a scale at all, they tune the string.
