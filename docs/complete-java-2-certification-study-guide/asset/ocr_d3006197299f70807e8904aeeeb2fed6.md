Notice that the original method() in BaseClass is declared as throwing an IOException or any object that is a subclass of IOException. This declaration allows it, and any overiding method defined in a subclass, to throw an exception. Overriding methods may, however, throw any checked exceptions that are not subclasses of IOException.

Given these rules, will line 21 in IllegalOne be correct, because method() is declared exactly the same way as the one that it overrides. Similarly, line 18 in IllegalThree is correct, because both IOException and MalformedURLException are subclasses of IOException—so this adheres to the rule that may be thrown that is not a subclass of the exceptions already declared. Line 12 in IllegalTwo is correct, because it throws Exception and therefore cannot throw any checked exceptions that are not subclasses of IOException.

The methods at lines 23 and 29 are not permissible, because both of them checked exceptions that are not subclasses of IOException. In IllegalOne, IllegalAccessException is a subclass of Exception. In IllegalTwo, Exception is a superclass of IOException. Both IllegalAccessException and Exception are checked exceptions, so that the methods attempt to throw them as illegal overriding methods of method() in BaseClass.

The point of this rule relates to the use of base class variables as references to objects of subclass. Chapter 4, "Converting and Casting", explains that you can declare a variable of a class X and then refer to object of class X or any subclass of X.

Imagine that in the examples just described, you declared a variable myBaseObject class BaseClass; you can use it to refer to any of the classes IllegalOne, IllegalTwo, and IllegalThree. You cannot use it to refer to objects of class IllegalOne or IllegalTwo, because those objects cannot be created in the first place: the compiler checks how you call myBaseObject.method(). Those checks ensure that for each call, either you have enclosed the call in a try block and providing a matching catch block or you have declared that the method itself might throw an IOException. Now suppose that at runtime, the variable myBaseObject referred to an object of class IllegalOne. Under these conditions, the compiler would still believe that the only exceptions that must be dealt with are class IOException, it believes that myBaseObject refers to an object of class BaseClass. The compiler would therefore not insist that you provide a try/catch catch that catches that IllegalAccessException, nor that you declare the calling method as that exception. If thus the class IllegalOne were permitted, overriding methods would be able to bypass the enforced checks for checked exceptions.
