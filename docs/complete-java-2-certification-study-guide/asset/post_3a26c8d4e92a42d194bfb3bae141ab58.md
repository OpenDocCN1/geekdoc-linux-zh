
To summarize, you can use two approaches to specify which run() method will be executed by a thread:

- Subclass Thread. Define your run() in the subclass.
- Write a class that implements Runnable. Define your run() method in that class. Pass an instance of that class to the Thread constructor.

## When Execution Ends

When the run() method returns, the thread has finished its task and is considered dead. There is no way out of this state. Once a thread is dead, it cannot be started; if you want the thread's task to be performed, you must construct and start a new thread. The dead thread continues to exist; it is an object like any other object, and you can access its data and call its methods. You can't make it again. In other words,

- You can't restart a thread by calling start() or run() methods.
- You can call other methods (besides start() and run()) of a dead thread.

The Thread includes a method called stop(), which forcibly terminates a thread, putting it into the dead state. This method is deprecated since JDK 1.2, however, it is generally poor design to terminate heavily operation, involving significant kernel resources or deadlock if you kill a thread that is in a critical section of code. ## Thread States

When you call start() on a thread, the thread does not run immediately. It enters a "ready-to-run" state and stays until the scheduler moves it to the "running" state. The run() method is called. In the course of executing run(), the thread may temporarily give up the CPU and enter some other state for a while. It is important to be aware of the possible states that a thread might be in and of the triggers that cause the thread's state to change.

The thread states are as follows:

**Running** A thread gets all the of the JVM's processor, which executes the thread's run() method.

**Various non-running states** The basic non-running states are Suspended, Sleeping, and Blocked.

There are some non-running states that relate to monitors, which are explained later in this chapter.

## Thread Priorities

Every thread has a *priority*, which is an integer from 1 to 10; threads with higher priority should get preference over threads with lower priority. The scheduler considers the priority when it decides which thread should execute. The scheduler chooses the highest-priority waiting thread. If more than one thread is waiting, the scheduler chooses one of them. There is no guarantee that the thread chosen will be the one that runs longest.

The default priority is 5, but all newly created threads have their priority set to that of the creating thread. By using `thread.setPriority()`, you can set the new priority. The `getPriority()` method returns the current priority of the thread. The following code example avoids hard-coding the value 10, and instead uses `MAX_PRIORITY`. The Thread class defines `MIN_PRIORITY` (which is 1) and `NORM_PRIORITY` (which is 5).

1. int oldPriority = thread.getPriority();
2. int newPriority = Math.min(oldPriority, MAX_PRIORITY);
3. thread.setPriority(newPriority);

The specifics of how thread priorities affect scheduling are platform dependent. The Java specification states that threads must have priorities, but it does not dictate precisely what the scheduler should do about them. This vagueness is a problem: algorithms that rely on manipulating thread priorities might not run consistently on all platforms.

## Daemon Threads

Some threads are daemon threads (Pronounced like "demon", the name comes from the folklore of the early days of Unix). Daemon threads are infrastructure threads, created automatically by the JVM. The garbage collector is a daemon thread, and so is the GUI event-processing thread.

When an application begins, there is only one non-daemon thread, the main thread, which runs `main()` method. Any threads created by daemon threads are initially daemon threads. Threads created by non-daemon threads are initially non-daemon threads. Before a thread begins execution, you can change its daemon status by calling `setDaemon()`. The JVM runs until the only live threads are daemons. In other words, the JVM considers its work to be done when the only remaining threads are its own infrastructure threads.

## Controlling Threads

Thread control is the art of moving threads from state to state. You control threads by triggering state transitions. This section examines the various pathways out of the Running state. These pathways are

- Yielding
- Suspending and then resuming
- Sleeping and then waking up
- Blocking and then continuing
- Waiting and then being notified

The first four of these pathways are presented below. The fifth concerns monitors, and is discussed in the major section "Monitors, Waiting, and Notifying."

## Yielding

A thread can offer out to the virtual CPU by yielding. A call to the yield() method causes the currently executing thread to move to the Ready state if the scheduler is willing to run any other thread in place of the yielding thread. The Yield state is shown in Figure 7.2.

A thread that has yielded goes into the Ready state. There are two possible scenarios. If any other threads are in the Ready state, then the thread that just yielded might have to wait a before it gets to execute again. However, if no other threads are waiting, then the thread that yielded will get to continue executing immediately. Note that most schedulers do not stop the thread from running in favor of a thread of lower priority.

The yield() method is a static method of the Thread class. It always causes the currently executing thread to yield.

## Controlling Threads

Yielding allows a time-consuming thread to permit other threads to execute. For example, consider an applet that computes $300 \times 300$ pixel image using a ray-tracing algorithm. The applet might have a Compute button and an Interrupt button. The action event handler for the Compute button would create and start a separate thread, which would call traceRays().
A first cut at this method look like this:

1. private void traceRays() {
2. for (int j = 0; j < 300; j++) {
3. for (int i = 0; i < 300; i++) {
4. computeOnePixel(i, j);
5. }
6. }
7. }

There are 90,000 pixel values to compute. If it takes 0.1 second to compute the color of one pixel, then it will take two and a half hours to compute the complete image.
Suppose after half hour the user looks at the partial image and realizes that something is wrong (perhaps the viewport or zoom point is incorrect). The user will click the Interrupt button, because there is no sense in continuing the useless image. Unfortunately, the thread that handles GUI input might not get a chance to execute unless the thread that is traceRays() gives up the CPU. Thus the Interrupt button will not have any effect for another two hours.

If priorities are implemented meaningfully in the scheduler, then lowering the priority of the ray-tracing thread will have the desired effect, ensuring that the GUI will run when it has something to do. However, this mechanism is not reliable between platforms (although it is a good course of action anyway, because it will do no harm). The reliable approach is to have the ray-tracing thread periodically yield. If no input is pending when the yield is executed, then the ray-tracing thread will not be moved off the CPU. If, on the other hand, there is input to be processed, the input-listening thread will have a chance to execute like this:
rayTraceThread.setPriority(Thread.NORM_PRIORITY-1);

The traceRays() method listed earlier can yield each pixel value is computed, after the revised version looks like this:

1. private void traceRays() {
2. for (int j = 0; j < 300; j++) {
3. for (int i = 0; i < 300; i++) {
4. computeOnePixel(i, j);
5. Thread.yield();
6. }
7. }
