# Protected Access in Depth

In this exercise you will look at how protected data can be accessed from a subclass that belongs to a different package. Because access is enforced at compile time, you will not be writing code that is intended to be executed. Rather, you will write several simple classes and see which ones compile.

Begin creating a public superclass Bird, in a package called birdpack. This superclass should have a single data member: a protected int nFeathers. Then create four subclasses of Bird, all of which reside in a package called duckpack. Thus you will have subclasses whose package is different from their super’ package; this is exactly the situation for which protected access is designed.

The first subclass, called Duck1, should have a method that constructs a new instance of the nFeathers variable of the current instance of Duck. Before compiling Duck1.java, ask yourself if the code should compile.

The second subclass, called Duck2, should have a method that constructs a new instance of Duck2 and accesses the nFeathers variable of the new instance. Before compiling Duck2.java, ask yourself if the code should compile.

The third subclass, called Duck3, should have a method that constructs a new instance of Bird (the super) and accesses the nFeathers variable of the Bird1 instance. Before compiling Duck3.java, ask yourself if the code should compile.

The fourth and last subclass, called Swan, should have a method that constructs a new instance of Duck and accesses the nFeathers variable of that instance. Before compiling Swan.java, ask yourself if the code should compile.

Sample solutions appear on your CD-ROM in the directory solutions\Chapter_03.

A note on compilation: When a source file contains a package declaration, it is generally more convenient to compile with the -d option. Doing so will ensure creation of an appropriate directory hierarchy, with class files installed correctly. Thus, for example, the easiest way to compile Bird.java is with the following command line:

```
javac -d Bird.java
```

# Subclasses and Method Privacy

Java specifies that methods may not be overridden to be more private. For example, most applets provide an init() method, which overrides the do-nothing version inherited from the java.applet.Appletsuperclass. The inherited version is declared public, so declaring the subclass version to be protected, or default would result in a compiler error. The error message says, "Methods can’t be overridden to be more private."
