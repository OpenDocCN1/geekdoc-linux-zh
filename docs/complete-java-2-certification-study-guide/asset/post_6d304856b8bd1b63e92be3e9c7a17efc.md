## The GridBag Layout Manager

The GridBag layout manager is the most powerful layout manager. It can perform the work of the Flow, Grid, and Border layout managers if appropriately programmed and is capable of much more, often without the need for nesting multiple panels as so often required with the other layout managers.

The GridBag manager divides its container into an array of cells, but (unlike the cells of a Grid layout manager) different cell rows can have different heights, and different columns can have different widths. A component can occupy part or all of a region that is based on either a single cell or a rectangle made up of multiple cells. A GridBag layout manager requires a lot of information to know where to put a component. A helper class GridBagConstraints is used to hold the layout position. When you add a component, use the add(Component, Object) version of the add() method, passing an instance of GridBagConstraints as the Object parameter.

## Designing a Layout with GridBag

Although the GridBag layout manager is powerful, it is sometimes hard to use. This perception seems mostly from two things. First, the supplied documentation, although precise and complete from a technical point of view, does not describe more than the API. An explanation of the principles of operation is noticeably missing. Second, some aspects of the control of the GridBag layout manager are confusing. Specifically, you will notice that the row and column sizing controls are typically mixed with the individual component controls. To use the GridBag layout easily and confidently, you need to first understand the principles that drive it and then worry about the API that you must use.

# Chapter 12 · Layout Managers

Three levels of control are applied to a GridBag layout to make up the final layout in the container. The sizes of the various rows and columns, along with the way they stretch the container is resized, must be considered. Also, the cell (or cells) that provides the target space for each component is determined. The final control determines how each component is stretched to fit, or if it isn't, how the component is positioned within the target space.

The API governing each of these aspects is built into a single mechanism based around the GridBagConstraints class. This class can be confusing, so we will discuss each of the principles of control separately as much as possible. As we do so, we will describe the API controls this behavior. Finally, we will look at the interactions between these controls and generalizations that will be useful to you when designing layouts and answering examination questions.

## Controlling the Rows and Columns

The row and column behavior of a GridBag layout has three aspects. The first is the number of rows and columns present. Typically, this total is determined by the number of rows and columns you add components to. So, for example, if you place components at coordinates 0, 1, 2, and 3, you will find at least four columns.

There is another way to specify the number of rows. The GridBag manager has variables called columnWidths and rowHeights. If you use these arrays, the layout will contain at least four rows.

The second aspect is the default size of a row or column. The default height of a row is normally the height of the tallest component in the row. Similarly, the default width of a column is the width of the widest component.

The final aspect of rows and columns is the stretchiness that occurs when the container is resized. It is governed by properly called weight.
