# Answers to Review Questions

+   1. A Runnable interface defines a run() method with void return type and no parameters. The method in the problem has a String parameter, so the compiler will complain that Greebo does not define run() from interface Runnable. B is wrong, because you can definitely pass a parameter to a thread's constructor; the parameter becomes the thread's target. C, D and E are nonsense.

+   2. There is no way to predict thread priority manipulation will affect the specific performance of individual threads. Priority manipulation only affects overall statistical behavior.

+   3. The yield(int) method is static and always causes the current thread to yield. In this case, ironically, the first thread will yield.

+   4. The first thread will sleep for 100 milliseconds (more or less, the resolution of the JVM being used). The thread will enter the Ready state; it will not actually run until the scheduler permits it to run.

+   5. When you call notify() on a monitor, you have no control over which waiting thread gets notified.

+   6. A call to xxx() occurs before the thread is registered with the thread scheduler, so the object executes the method in the main thread.

+   7. A monitor is an instance of any class that has synchronized code.

+   8. The suspend() and resume() methods were deprecated in the Java 2 release. They still appear on the API page for Thread but should not be used.

+   9. Threads inherit their priority from their parent thread. A is incorrect, although the default priority for a thread is 5, it may be changed by the parent thread. C is incorrect because Java does not make promises about priority at runtime. Finally, D is incorrect because thread priorities range from 1 to 10.

+   10. The thread that calls wait() enters the monitor's pool of waiting threads. Option A is incorrect because wait() and notify() must be called within synchronized code. B is incorrect because notify() can arbitrarily select a thread from the pool of waiting threads. Option D is incorrect because the thread that calls wait() is the thread that gives up the lock.

+   11. You can synchronize a block by protecting the block with synchronized code. You can declare a static method to be synchronized; since there is no object, the thread that executes the method will synchronize on a lock belonging to the class. You can synchronize a block inside a static method as you would a block within a non-static method; again, synchronization will occur on a lock belonging to the class.

+   12. A, B, C, D All four situations are legal. Java has no restrictions regarding which methods may call which threads, with respect to synchronization.

+   13. An object has only one lock, which controls access to all synchronized code.
