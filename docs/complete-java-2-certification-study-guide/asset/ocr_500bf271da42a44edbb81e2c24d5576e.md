The Mailbox class is now safe from its clients, but the clients still have problems. A message-producing client should call sendMessage() only when the request flag is false; a message-consuming client should call retrieveMessage() only when the request flag is true. In the Consumer class of the previous section, the synchronized main loop checks the request flag every 50 milliseconds. (Presumably a message-producing thread would do something similar. Now the request flag is private, you must find another way).
It is possible to come up with any clear level for your clients to poll the mailbox, while the whole approach is backward. The mailbox becomes available or unavailable based on changes of its state The mailbox should be in charge of the progress of the clients. Java's wait() and notify() methods provide the necessary controls, and as you will see in the next section.

# wait() and notify()

The wait() and notify() methods provide a way to pause a thread when it becomes unavailable and allow it to be awakened by another thread when appropriate.
The threads themselves never have to check the state of the shared object.
An object that controls the clients in this thread in a manner known as a monitor. In strict Java terminology, a monitor is any object that has some synchronized code. Any such object has the infrastructure needed to allow it to block and revive threads. To be really useful, monitors make use of wait() and notify() methods. The Mailbox is already a monitor; it just is not quite useful.
