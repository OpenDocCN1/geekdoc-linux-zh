> In object-oriented windowing systems, including Java, the term hierarchy is ambiguous. When discussing classes, hierarchy refers to the structure of inheritance from superclass to subclass. When discussing GUIs, hierarchy can refer to the structure of GUI components, such as applets, frames, panels, buttons, and so on.

The GUI in Figure 12.1 is a moderate-size frame for specifying a color. You can see at a glance that the panel contains labels, scroll bars, text fields, and buttons. You have probably guessed that the frame also contains panels, even though they cannot be seen. In fact, the frame contains five panels, not counting the frame's content pane. Each of the six (the five panels, plus the content pane) has its own layout manager. There are four instances of Grid layout managers, one Flow layout manager, and one Border layout manager.

Figure 12.2 schematically shows the frame's containment hierarchy. A Java programmer must master the art of transforming a produced GUI into a workable and efficient containment hierarchy. This skill comes with experience, when the fundamentals are understood. The Developer's Certification Exam does not require you to develop any complicated containments, but does require you to understand the fundamentals.

# Layout Manager Theory

As you can see from the listing, no code specifies exactly where the labels, scroll bars, text fields, buttons, or panels go or what size they should be. Instead, the content pane of the JFrame, as well as the various JPanels uses its default layout manager or is specifically assigned a non-default layout manager.

After each container is constructed and possibly assigned a new layout manager, the container is populated with the components it is to contain. For example, the lower JPanel constructed in line 24, is populated with JButtons in lines 25, 26, and 27 (using its default layout manager). Finally, the newly-populated panel is added to the container that is to hold it (line 28).

Each panel in the sample code is built in four steps:

1. Construct the panel.
2. Give the panel a layout manager.
3. Populate the panel.
4. Add the panel to its own container.

When a container is constructed (step 1), it is a default layout manager. For panels, the default is a Flow layout manager, and step 2 can be skipped if this is the desired manager. In step 3, populating the panel involves constructing components and adding them to the panel; if any of these components is itself a panel, steps 1–4 must be executed recursively.

There is a version of the JPanel constructor whose single argument is a layout manager, which of course is assigned to the panel. So lines 15 and 16 above be abbreviated as

```java
JPanel level1 = new JPanel(new GridLayout(3, 1, 0, 10));
```

A container delegates to its layout manager the job of determining where components will be and (optionally) how they will be resized. If the container is subsequently resized, the layout manager lays out the container's components (probably with different results, because it has a different area to work with). This "conference" between the container and the layout manager is the work of this section.

# Component Size and Position

Components know where they are and how big they are. That is to say, the java.awt.Component class, is a superclass of all AWT and Swing components, has instance variables x, width, and height. The x and y variables specify the position of the upper-left corner of the container, and width and height are in pixels. Figure 12.3 illustrates the x, y, width and height of a component inside a frame. It seems reasonable that the following code, which calls setLayout(), would create two buttons:

```java
import java.awt.*;
import javax.swing.*;

public class Disa extends JFrame {
  public static void main(String[] args) {
    JFrame frame = new JFrame();
    JPanel panel = new JPanel();
    for (int i=0; i<2; i++) {
      JButton btn = new JButton("We're enormous!");
      btn.setSize(300, 300);
      panel.add(btn);
    }
    frame.getContentPane().add(panel);
    frame.setSize(450, 70);
    frame.setVisible(true);
  }
}
```

It seems that line 10 would force the buttons to be 300 pixels wide by 300 pixels. In fact, the buttons are just the size they would be if line 10 were omitted or commented out. Line 10 has no effect after it executes, the button is added to a panel (line 11). Eventually (after a complicated sequence of events), the panel calls on its layout manager to enforce its layout policy on the button. The layout manager decides where and how big the button should be; in this case, the layout manager wants the button to be large enough to accommodate its label. When this size has been calculated, the layout manager calls setBounds() on the button, clobbering the work you did in line 10.

In general, it is futile to call set() on a component, because layout managers always get the last word; that is, their call to setBounds happens after yours. There are ways to defeat this functionality, but they tend to be complicated, difficult to maintain, and not in the spirit of Java. Java's GUI system wants you to let the layout managers do the work. In order to build a sophisticated GUI, you have to be familiar with the layout policies of the available layout managers. These policies are covered in the next several sections.
