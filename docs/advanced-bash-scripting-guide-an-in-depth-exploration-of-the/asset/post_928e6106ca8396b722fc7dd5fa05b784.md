## Appendix E. Exit Codes With Special Meanings

Table E-1. Reserved Exit Codes

| Exit Code Number | Meaning | Comments |
| --- | --- | --- |
| 1 | Catchall for general errors | let var1 = 1/0 | Miscellaneous errors, such as "divide by zero" and other impermissible operations |
| 2 | Misuse of shell builtins (according to Bash documentation) | empty_function() [] | Missing keyword or command, or permission problem (and return error code on a failed binary file comparison). |
| 126 | Command invoked cannot execute | /dev/null | Permission problem or command is not executable |
| 127 | "command not found" | illegal_command | Possible problem or command is not $PATH or a type |
| 128 | Invalid argument to exit | exit 3.14159 | exit takes only integer args in the range 0-255 (see first footnote) |
| 128+n | Fatal error signal "n" | kill -9 $PID of script | $? returns 137 (128 + 9) |
| 130 | Script terminated by Control-C | Ctrl-C | Control-C is fatal error signal 2, (130 = +2, see above) |
| 255* | Exit status out of range | exit - | exit takes only integer args in the range 0-255 |

According to the table above, exit codes 1-2, 126-128 and 255 [144] have special meanings, and avoiding a script with exit 127 would certainly cause confusion during troubleshooting (is error code a "command not found" or a user-defined one?). However, many scripts use exit 1 as a general bailout-upon. Exit code 1 signifies many possible errors, it is not particularly useful in debugging.

There has been an attempt to systematize exit statuses (using /usr/include/sysext.h), but this is intended for C and C++ programmers scripting user-defined exit codes for the range 64-113 (in addition to 0, for success) conform with the C/C++ standard. This would allow 50 valid codes, and make troubleshooting scripts straightforward. [145] All user-defined exit codes in the accompanying examples do not conform to this standard, except where overriding circumstances arise, as in Example 9-2.

Issuing $? from the command-line after a script exits gives consistent results with the table above only from the Bash or sh prompt. Running the C-shell or tsh may give different values in some cases.

## Appendix F A Detailed Introduction to I/O and I/O Redirection

written by Stéphane Chazelas and redirected by the document author.

A command expects the first three file descriptors to be available. The first, fd 0 (standard input, stdin), is for reading. The other two (fd 1, stdout and fd 2, stderr) are for writing.

There is a stdin, stdout, and a stderr associated with each command. ls 2>&1 temporarily connecting the stderr of the ls to the same "resource" as the shell's stdout.

By convention, a command reads its input from fd 0 (stdin), prints normal output to fd 1 (stdout), and output error to fd 2 (stderr). If any of these three are not open, you may encounter problems:

```bash
bash cat /etc/passwd >-
cat: standard output: Bad file descriptor
```

For example, when xterm runs, it initializes itself. Before running the user's shell, xterm opens the terminal device (/dev/pts/0 or something similar) three times.

At this point, Bash inherits these three descriptors, and each command (child process) by Bash inherits in them, unless you redirect the command. Redirection means assigning one of the descriptors to another (or a file, or anything permissible). File descriptors may be reassigned locally for a command, a group, a subprocess, a while or if or for loop...), for the remainder of the shell (using exec).

ls > /dev/null means ls with its fd 1 connected to /dev/null

```bash
bash lsof -n -p $$-0,1,2
COMMAND PID USER FD TYPE DEVICE SIZE NAME
bash 3630 Ou CHR 136,1 3 /dev/pts/1
bash 3630 1u CHR 136,1 3 /dev/pts/1
bash 3630 2w CHR 1,3 120 /dev/null
```

```bash
bash exec 2> /dev/null
bash lsof -a -p $$-0,1,2 | cat
COMMAND PID USER FD TYPE DEVICE SIZE NAME
lsof 3701 Ou CHR 136,1 3 /dev/pts/1
lsof 3701 1w FIFO 7118 pipe
lsof 3701 29 CHR 136,1 3 /dev/pts/1
```
