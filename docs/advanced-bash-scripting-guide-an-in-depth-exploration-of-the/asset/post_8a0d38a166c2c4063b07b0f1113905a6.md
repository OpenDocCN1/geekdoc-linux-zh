# Closing File Descriptors

```
n<&-
Close input file descriptor n.
0<-, <-
Close stdin.
n>&-
Close output file descriptor n.
1>&, >-
Close stdout.
```

Child processes inherit file descriptors. This is why pipes works. To prevent an fd from being inherited, close it.

# 20.1. Using exec

An exec <filename> redirects stdin to a file. From that point on, all stdin comes from that file, rather than its normal source (usually keyboard input). This provides a method of reading a file line by line and possibly parsing each line of input using sed and/or awk.

Example 20-1. Redirecting stdin using exec

```bash
#!/bin/bash
# Redirecting stdin using 'exec'

exec 6<0               # Link file descriptor #6 with stdin.
                                 # Saves stdin.
exec < data-file        # stdin replaced by file "data-file"

read a1                 # Reads first line of file "data-file".
read a2                 # Reads second line of file "data-file".

echo
echo "Following lines read from file,"
echo "----------------------"
echo $a1
echo $a2

echo; echo;

exec 0<&6 6<-\
# Now restore stdin from #6, where it had been saved,
# and close fd #6 (6<-) to free it for other processes to use.
#
<66 6<-\                 # also works.

echo -n "Enter data "
read b1 # Now "read" functions as expected, reading from normal stdin.
echo "Input read from stdin."
echo "----------------------"
echo $b1

echo 0
```

Similarly, an exec <filename> command redirects stdout to a designated file. This sends all command that normally goes to stdout to that file.

exec N > filename affects the script or current shell. Redirection in PID of the script from that point on has changed. However... N > filename affects only the newly-forked process, the entire shell. Thank you, Ahmed, for pointing this out.

Example 20-2. Redirecting stdout using exec

```bash
#!/bin/bash
# redirect-stdout.

LOGFILE=logfile.txt
exec 6>&1
# Link file descriptor #6 with stdout
# Saves stdout.
exec > $LOGFILE
# stdout replaced with file "logfile.txt"

# All output from commands in this block sent to file $LOGFILE.
echo -n "Log: "
date
echo "--------------------------------"
echo "Output of ls -al command"
ls -al
echo
echo "Output of df command"
df

exec 1>&6 6<& # Restore stdout and close file descriptor #6.
echo "stdout now to default="
ls -al
exit 0
```

# 20.2 Redirecting Code Blocks

Blocks of code, such as while, until, and for loops, if/then test blocks can also incorporate redirection of stdin. Even a function may use this form of redirection (see Example 24-11). The < operator at the end of the code block accomplishes this.

Example 20-5. Redirected while loop

```bash
#!/bin/bash
# redir2.sh

if [ -z "$1" ]
then
    Filename=names.data      # Default, if no filename specified.
else
    Filename=$1
fi
# Filename=${1:-names.data}
# can replace the above test (parameter substitution).

count=0
echo

while read -r line <"$Filename"
do
    echo "$line"
    ((count++))
done
echo "$count names read"
``` 

# Note that in some older shell scripting languages,
# the redirected loop would run as a subshell.
# Therefore, $count would return 0, the initialized value outside the loop.
# Bash and ksh avoid starting a subshell "whenever possible",
# so that this script, for example, runs correctly.
# (Thanks to Heiner Steiner for pointing this out.)

# However.
# Bash "can" sometimes starts a subshell in a PIPED "while-read" loop,
# as distinct from a REDRECTED "while" loop.

```bash
abc-hi
echo -e "1\n2\n3" | while read r
do abc="$1"
echo $abc
done
echo $abc
```

# 20-4. Avoiding subshell

```bash
#!/bin/bash
# avoid-subshell.sh
# Suggested by Matthew Walker.

Lines=0
echo

exec 3<> myfile.txt
while read -r line <&3
do
    echo "$line"
    ((Lines++))
done
# No subshell, problem.
exec 3>&-

echo "Number of lines read = $Lines"
