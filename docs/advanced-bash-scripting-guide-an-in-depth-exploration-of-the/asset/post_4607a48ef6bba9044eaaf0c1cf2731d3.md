# Chapter 1. Shell Programming!

> No programming language is perfect. There is not even a single best language; there are only languages well suited or poorly suited for particular purposes.

> --Herbert Mayer

A working knowledge of shell scripting is essential to anyone wishing to become reasonably proficient in system administration, even if they do not anticipate ever having to write a script. Consider that as a Linux machine boots up, it executes the scripts in /etc/rc.d to restore the system configuration and set up services. A detailed understanding of these startup scripts is important for analyzing the behavior of a system, and possibly modifying it.

The craft of scripting is not hard to master, since scripts can be built in bite-sized sections and there is only a fairly set of shell-specific operators and options [1] to learn. The syntax is simple -- similar to that of invoking and chaining together utilities at the command line, and there are only few "rules" governing them. Most short scripts work the first time, and debugging the longer ones is straightforward.

In the early days of personal computing, the BASIC language enabled anyone reasonably proficient to write programs on any generation of microcomputers. Decades later, the Bash scripting language enables anyone with a rudimentary knowledge of Linux or UNIX to do the same on modern machines.

We now have miniaturized single-board computers with amazing capabilities, such as the Raspberry Pi. Bash scripting provides a way to explore the capabilities of fascinating devices.

A shell script is a quick-and-dirty method of prototyping a complex application. Even a limited subset of the functionality to work in script is often a useful first stage in project development. In this way, the structure of the application can be tested and tinkered with, and the major pitfalls fall before proceeding to the final coding in C, C++, Perl, or Python.

Shell scripting brings back the classic UNIX philosophy of breaking complex problems into simpler tasks, of chaining together components and utilities. Many consider this a better, or at most aesthetically pleasing approach to problem solving using one of the new generation of high-powered all-in-one languages, such as Perl, which attempt to be all things to all people, but at the cost of forcing you to alter your thinking processes to fit the tool.

According to Herbert Mayer, "a useful language needs arrays, pointers, and a generic mechanism for building data structures." By these criteria, shell scripting falls somewhat short of being "useful." Or perhaps not . . .

When not to use shell scripts

# Advanced Bash-Scripting Guide

- Resource-intensive tasks, especially where speed is a factor (sorting, hashing, recursion [2] ...)
- Procedures involving heavy-duty math operations, especially floating point arithmetic, arbitrary precision calculations, and complex numbers (use C++ or FORTRAN instead)
- Cross-platform portability required (use C or Java instead)
- Complex applications, where structured programming is a necessity (type-checking of variables, function prototypes, etc.)
- Mission-critical applications upon which you are beating the fire of the company
- Situations where security is important, where you need to guarantee the integrity of your system and protect against intrusion, cracking, and vandalism
- Project consists of with interlocking dependencies
- Extensive file operations required (Bash is limited to serial file access, and that only in a particularly clumsy and inefficient line-by-line fashion)
- Need native support for multi-dimensional arrays
- Need data structures, such as linked lists or trees
- Need to generate / manipulate graphics or GUIs
- Need direct access to hardware or external peripherals
- Need port or socket I/O
- Need to use libraries or interface with legacy code
- Proprietary, closed-source applications (Shell scripts put the source code right in the open for all the world to see.)

If any of the above applies, consider a more powerful scripting language -- Perl, Tcl, Python, Ruby -- or possibly a compiled language as C, C++, or Java. Even then, prototyping the application as a shell script might still be a useful development step.

We will using Bash, an acronym [3] for 'Bourne-Again shell' and a pun on Stephen Bourne's classic Bourne shell. Bash becomes a de facto standard for scripting on most flavors of Unix. The principles this book covers apply well to scripting with other shells, like the Korn Shell, which Bash derives of its features, [4] and the C Shell and its variants. (Note that C Shell programming is not recommended due to certain inherent problems, as pointed out in an October, 1993 Upset post by Tom Christensen.)

What follows is a tutorial on shell scripting. It relies heavily on examples to illustrate various features of the shell. The shell examples work -- they have been tested, insofar and some of them are even in real life.
