Untyped variables are both a blessing and a curse. They permit more flexibility in scripting and make it easier to grind out lines of code (if you have enough rope to hang yourself!). However, likewise subtle errors creep in and encourage sloppy programming habits.

To the lighten of keeping track of variable types in a script, Bash *does* permit declaring variables.

## 4.4. Special Variable Types

- Local variables: Variables visible only within a code block or function (see also local variables in functions)
- Environmental variables: Variables that affect the behavior of the shell and user interface

> In a more general context, each process has an "environment", that is, a group of variables that the process may reference. In this sense, the shell behaves like any other process.

Every time a shell starts, it creates shell variables that correspond to its own environmental variables. Updating or adding new environmental variables causes the shell to update its environment, and all the shell *child processes* (the commands it executes) inherit this environment.

The space allocated to the environment is limited. Creating too many environmental variables or ones that use excessive space may cause problems.

```bash
bash$ eval "seq 10000 | sed -e 's/./export var=ZZZZZZZZZZZZZZZZ/'"
bash$ du
bash$: /usr/bin/du: Argument list too long
```

Note: this "error" has been fixed, as of kernel version 2.6.23.

If a script sets environmental variables, they need to be "exported," that is, reported to the *environment* location to the script. This is the function of the *export* command.

> A script can export variables only to child processes, that is, only to commands or processes which particular script initiates. A script invoked from the command-line *cannot* export variables back to the command-line environment. Child processes cannot export variables back to the parent processes that spawned them.

**Definition:** *A child process is a subprocess launched by another process, its Positional parameters*

Arguments to the script from the command line [26]: $0, $1, $2, $3…

$0 is the name of the script itself, $1 is the first argument, $2 the second, $3 the third, and so forth. [27] After $9, the variables must be enclosed in brackets, for example, ${10},${11},${12}.

The special variables *$ and @$ denote *all* the positional parameters.

**Bracket notation** for positional parameters leads to a fairly simple way of referencing the last argument passed to a script on the command-line. This also requires indirect referencing.

```bash
args=$# # Number of args passed.
lastarg=${args} # an "indirect reference" to $args

Or: lastarg=${!!} # (Thanks, Chris Monson.)
```

Some scripts can perform different operations, depending on name they are invoked for. For this work, the script needs to check $0, the name it invoked by. [28] There must also exist symbolic links to alter all the names of the script. See Example 16-2.

> If a script expects a command-line parameter but is invoked without one, this may cause a null variable assignment, an undesirable result. To prevent this is to append an extra character to both sides of the assignment statement using the expected positional parameter.

```bash
variable_=$1  # Rather than variable=$1
# This will not prevent an error, even if positional parameter is absent.
critical_argument0=$variable_

# The extra character can be stripped off later, like so.
variable=$($variable_)
# Side effects only if $variable_ begins with an underscore_
# This uses one of the parameter substitution techniques discussed later.
# (Leaving out the replacement pattern results in a deletion)

# A more straightforward way of dealing with this is
# simply test whether expected positional parameters have been passed
if -z $1
then
    exit $E_MISSING_POS_PARAM
fi

# However, as Fabian Kreutz points out,
# the above method may have unexpected side-effects.
# A better method is parameter substitution:
# ${1:-DefaultVal}
# See the "Parameter Substitution" section
# in the "Variables Revisited" chapter.
```

The shift command reassign the positional parameters, in effect shifting them to the left.

$1 <--- $2, $2 <--- $3, $3 <--- $4, etc.

The old $1 disappears, but $0 (the script name) does not change. If you use a large number of positional parameters to a script, shift lets you access those past 10, although bracket] notation also permits this.

## Example 4-7. Using shift

```bash
#!/bin/bash
# shift.sh: Using 'shift' to step through all the parameters.

# Name this script something like shft.sh,
# and invoke it with some parameters.
# For example:
  sh shft.sh a bc def 83 baroor

until [ -z "$1" ] # Until all parameters used
do
  echo -n "$1"
  shift
done

echo      # Extra linefeed.

# But, what happens to the "used-up" parameters?
echo "$
# Nothing echoes!
# When $2 shifts into $1 (and there is no $3 to shift into $2)
# then $2 remains empty.
# So, it is not a parameter *copy*, but a *move*.

exit
```

# See also the echo-params.sh script for a "shiftless"
# alternative method of stepping through the positional parameters.

The shift command can take a numerical parameter indicating how many positions to shift.

```bash
#!/bin/bash

# n=3; shift $n
# Has the same effect.
```
