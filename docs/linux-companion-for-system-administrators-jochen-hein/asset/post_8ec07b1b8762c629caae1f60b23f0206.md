## 2.5.6 /var/log - all kinds of log files

Even without programs such as syslog, a UNIX system always writes a series of log files. These are used for system monitoring and error detection. Examples of such files are last for the date of the last user login and wtmp for the times of all login and logout processes.

Log files created by root processes can be directly stored in this directory. If log files are generated by systems such as news and UUOCP which run under their own IDs, a separate directory should be created for each ID, which is writable for each ID.

## 2.5.7 /var/mail - mailboxes of the UNIX users

The /var/mail directory contains the mail of the users in UNIX format (mbox). This directory has been shifted from /var/spool/mail to improve cross-functionality with other systems.

## 2.5.8 /var/opt - variable data for programs /opt

This directory is used to store variable data of the packages installed under /opt. As under /opt, a separate subdirectory should be created for each package.

## 2.5.9 /var/run - PID files of processes

Here, the PID (process id) files for daemons are stored, so that the process number of a background process can be easily identified. These files should be called program.pid and should contain the process number in clear text. This facilitates sending a signal to a background process, for example, the syslog daemon (see also Listing 2.2).

```
(Linux):# kill -HUP cat /var/run/syslog.pid
```

This directory should also be employed for UNIX domain sockets that are used for communication between programs. Since daemons are started under different user IDs (the news daemons, for example, run under the user name news) this directory must be writable for all users. For reasons of security, however, the t bit should be set as with the tmp directory. Thus, users can only delete a file that they own. An alternative could be for appropriate subdirectories to be created, which would then be writable for the corresponding user or for a special program.

## /var/spool - directories for waiting queues

The /var/spool directory is used for temporary storage of uucp jobs, printer outputs, or others that the system must carry out at a later time. Often, the data is automatically deleted after the task has been executed. The precise structure of this directory is determined by the system administrator, on the basis of the available hardware and software environment. Table 2.9 shows an overview of subdirectories which might exist in /var/spool.

## Variable status information - /var/state

This directory contains variable information about the status of individual applications. Users should never modify one of these files.

In old versions of the FHS, there used to be the directory /var/lib, which was replaced with /var/state. Data stored here are persistent and preserved even after a reboot of the system. Examples are the database of the package management of a distribution or the locate database. No log files or spool data should be stored here.

For individual packages, separate directories should be created. The FHS provides several examples which are of particular interest for distributors and system integrators.

## 2.5.12 /var/tmp - temporary files

The /var/tmp directory is a directory for temporary files. It is used to keep the root partition, which also contains the /tmp directory, as small as possible. Here too, is up to the system administrator to decide how long the data is kept in /var/tmp. However, the data should be kept for at least as long as the data in the /tmp directory.

## 2.5.13 /var/yp - Network Information Service (NIS)

The Network Information Service (NIS) was formerly known as Yellow Pages (YP). With this service, files such as passwd or group can be centrally maintained on a NIS server; all clients receive this data via the network. The /var/yp directory is used to store the corresponding data. More details on the configuration of the Network Information Service are given in Chapter 22.

NIS should not be confused with the extended version NIS+. NIS+ uses /var/nis as its directory.

## 2.6 The further development of the FHS

In today's forum, the file system hierarchy standard is generally recognized among LINUX users as a sensible and reasonable agreement. Nevertheless, there are all (and will probably continue to be) significant differences between the individual distributions.

Whenever these differences (may) lead to problems, there will be a discussion in the corresponding mailing list. At present, there is a discussion about the integration of (commercial) packages into the standard, and the use of the file hierarchy standard for the *BSD systems as well.

Although different opinions are put forward on many issues, which occasionally causes lively discussions, the mailing list is very productive. Because of the extensive discussion going on, traffic is very high when compared to other mailing lists, with regard to both the number and the extent of the messages.

## 2.7 LINUX Standard Base

In the last few years almost all distributions respected the FHS and that helped LINUX to gain respect in the corporate world. In any case people recognized that only a small part of the requirements for users, developers and independent software vendors (ISVs) have been documented so far. To get a stable and useful platform for ISVs, much more needs to be defined. The Linux Standard Base is a group of LINUX developers, distributors and software vendors who tries to fill that need.

Some problems they try to address (for more information see their Web Site at www.linuxbase.org):

- * Which libraries (in which version) are available? What functions are defined?
- * Which commands can be used in portable scripts?
- * Which users are created on the system? How are users created for applications that need them?
- * Which fonts are installed and how can they be used?

Besides the standard itself the group implements a test suite to check the implementation on a given system. The test suite for the FHS is already available, some parts from the POSIX test suite will be used and some parts need to be created from scratch. Up to now, a lot of questions have been unanswered, and many new documents need to be written, so the participation of experienced LINUX users and software vendors will be of value.

See http://www.linuxbase.org for more details.

## 3.1 The Basic Input/Output System (BIOS)

## System start-up

When a computer starts up, it is as though something happens happens. process is commonly known as ‘bootstrapping.’ The image this conjures up is someone pulling himself up by his own bootstraps. But there are logical explanations which show that each step of the process assumes specific outcomes from the previous steps, so that there is always a solid base for the next step. The start-up of a LINUX PC has the following phases:

- Execution of the Power On Self Test (POST) of the Basic Input/Output System (BIOS); this is often stored in ROM or flash EPROM.
- Execution of a boot loader from a floppy disk, hard disk, or CD-ROM drive.
- Start of the kernel by means of the boot loader.
- Processing of the individual configuration via `init`.

In the following sections I present the initialization of PC hardware. Other systems have very similar functions, but may do things in a different order or use other commands.
