## 3.3 Starting the kernel

After one of the boot loaders has loaded the kernel image, for example \mlinuz, from the active partition into RAM, the kernel must first be decompressed, since version 0.99pl12, all kernels are created in a compressed form. The additional load of the CPU does not count because that time is ‘twiddling its thumbs,’ waiting for data to arrive from the disk I/O ‘bottleneck.’ The net loading time of compressed data is even lower. If, in contrast, the CPU represent the bottleneck, using uncompressed data would be more advantageous; however, this is not to be expected in the near future. Another advantage of compression is the saving of disk space, but in this case this is not important.

The use of compressed kernels has become necessary, because in an uncompressed form they became bigger than 704 Kbytes (640 Kbytes of ‘conventional DOS memory’ plus 64 Kbytes of unused data area of the graphic boards under DOS), and the processor at that point is still in real mode, in which only memory addresses below 1 Mbyte are available. Obviously this is only a restriction on Intel hardware.

The introduction of compressed kernels has only obfuscated the real problem. because of the large number of drivers that can be linked into the kernel, one again reaches the limits of the real mode, which requires the kernel to be loaded initially into the memory below 1 Mbyte. Sooner or later, the boot loader will run in protected mode, so the size of the kernel will only be limited by the real amount of RAM.

# 64 SYSTEM START-UP

Viewed under the aspect of configuration possibilities, two stages can be identified during start-up, after having selected the operating system:

- determination and checking of the hardware configuration,
- processing of the configuration files and automatic starting of programs.

During the first stage (see arch/i386/boot/setup.S) parts of the hardware configuration are detected even before unpacking the kernel. The corresponding BIOS variables (for diskette and hard disk parameters plus the connected graphics card) are read and stored in a safe place in main memory. Further hardware tests are carried out after switching into 32-bit mode; more about this later (for the exact sequence cf.: ./linux/init/main.c). First, however internal functions and tables of the system are initialized:

- the table for memory management,
- the assignment of error interrupts and IRQs, and
- the process table.

Subsequently, the scheduler is started and the screen is initialized; from now on messages are not only displayed on screen, but are also managed by means of syslogd and may be stored in a file. More about the use of syslog can be found in Section 4.7. These messages can later be replayed by means of dmesg program.

At this point, with the initialization of the corresponding device drivers, the previously mentioned second phase of the hardware tests begins. The hardware is checked by means of various tests (auto-probing or auto-detect). By looking at the screen messages, you can trace which devices have been found. If in this phase no message is displayed or there is an error message (for example, different I/O ports or interrupts) for a controller card, you will not be able to access this device later.³

Now, the processor is switched from privileged (or kernel) mode into privileged(or user) mode; from now on, the first UNIX process runs with process number 0). This process is in principle the same as all other UNIX processes, but it runs only if no other process is active. Process 0 is the idle process, which in case of non-use of the processor 100% of the system resources.

Process 1 is started from process 0 by means of the system call fork(). This process in turn initiates the further initialization of the system. Here, the hardware is initialized, the root partition is mounted, and the init program is executed. In UNIX, init is often called the parent of all processes, for whichUX is not entirely correct; here, by right, would be the idle process with the number 0. One further process is started which takes care of regular updates of the internal information about the file system on the hard disk the behaviour of this process can be influenced by means of the bdflush program.

According to the file system hierarchy standard (FHS version 2.0), the init process should be located in /sbin/init. The actual search order established in linux/unix/main.c is, however, /etc/init, /bin(), and /sbin/init. If init is not found, an attempt is made to start /etc/rc or /bin/sh to allow the repair of a 'disordered' system. With current kernel versions it is possible to use the command line parameter INIT=/bin/sh to start a shell instead of init.

To conclude the initialization, the kernel reports its version number and creation date. First, one of the three init processes normally used under LINUX is started. This connects the system start-up from the point of view of the kernel. However, the system can still not be used at this point because no login can take place and no background processes (daemons) have been started.

Now the kernel may start more processes or 'kernel threads' to carry housekeeping, such as flushing dirty buffers to disk, or memory management.

## 3.3.1 Kernel parameters

Many initializations (for example I/O addresses for expansion boards) of the kernel can be influenced by means of command line parameters. These parameters are passed to the kernel by the boot loader.

debug

Sets console_loglevel to 10, activating 'verbose' console messages.

mem=size

Sets the size of the physical memory. This may be necessary when the RAM size cannot be determined automatically, for example in computers with more than 64 Mbytes of RAM.

no387

The above maths coprocessor is not used.

no-hlt

Prevents use or execution of the HLT instruction of more recent Intel (-compatible) processors when the system is idle. When this instruction is used, the CPU is less heated and laptops consume significantly less power, but some machines may hang.

reserve=port1,num1,[portn,numn]

Excludes I/O ports and zones from auto-probing. This is needed, for example, when auto-probing leads to 'hanging' of the system. port1 represents the first address, num1 indicates the number of addresses to be excluded from port1 onward. You may repeat portn, numn until you have all parts excluded that you wanted to exclude.

root=device

Changes the device used as root file system. This overwrites the specifications stored in the kernel image. device is either a device name such as /dev/hda3 or a hexadecimal device number.

ro or rw

The root partition is mounted into the directory tree read-only or/write.
