## 16.12 Overview of active computers in the network.

Often the rwho daemon is not started as the regular exchange of logged-in users and the workload cause a fairly high network load. This is often the case where diskless computers are employed. After each rwho broadcast, the rwh programs are loaded via the network into the main memory of all workstations, and then the appropriate entries are made in the files, again via the network, so a high data volume rwho is produced in a relatively short time.

As an alternative to rwho, Sun developed the programs rusers and rstat. These deams communicate with the corresponding servers (ruserd and rstatd) which were implemented by RPC. Under LINUX, the programs are actually called rpc.userd and rpc.rstat. Here network load only comes into being if a user is actually interested in the data.

For reasons of data protection or security, there is often a need to prevent access to login and working times of the users. In these cases, the finger rwho will not be started.

## 16.4 The secure shell ssh

Many protocols used in connection with TCP/IP were initially designed with a view to functionality and performance. Aspects of safety against failures and redundancy also played a role, but the importance of data protection was still marginal. Today this subject is much more important than it used to be.

In many programs, passwords are transmitted in clear text. Examples for this telnet and ftp. When a connection is established in a local network, you can use a packet sniffer like tcpdump to protocol the entire session including the login. Remedy can be brought by methods such as one-way passwords (as S/Key), but the whole connection is still transmitted in clear text, including further passwords.

The r programs, for example login and rsh, can be configured by means of the files /etc/hosts.equiv (system-wide) or ~.hosts in such a way that no password is required. This method of authentication is, however, not particularly safe and can, for example, be hoodwinked by IP or DNS sniffing. Here login programs have the option -x for encryption of the session by DES.

This can be replaced by the ssh package which contains (nearly) all r programs in a more secure version. This begins with the programs ssh and rsh and login and ends with a more agreeable version of rcp, scp. These programs are set up on your network, you can quietly delete the (unsafe) r programs from your system without noticing any change.

The s programs are based on a series of key methods. Each computer has a host key which exists in one and private variation. Computers can authenticate each other by encrypting a challenge with the public key of the other computer and sending it to that computer. Only this computer can decrypt and answer the challenge and send it back (encrypted).

Furthermore, a session key is generated for the encryption of each session. This key is not stored on the hard disk, but only in RAM. For security reasons, this key is periodically discarded and generated fresh.

Besides the host-based authentication, users can define their own confidential relationships that allow logging without password. However, we will install and configure the programs. We will first consider a series of computers under unique administration. Formerly, the file /etc/hosts.equiv was used in a computer pool, so users could switch between different computers by login.

As already known from many other programs, the ssh package is compiled with ./configure and make and installed with install (in /usr/local); this can be changed by means of the option -prefix in configure. This automatically creates a host key (by means of ssh-keygen). If you install the programs on a shared disk (/usr/local is shared via NFS, you must manually create a pair of keys for each computer.

The host keys are stored in the /etc directory, the file ssh_host_key containing the private key and the file ssh_host_key.pub the public key. The configuration files are for /etc/ssh_config for the client programs and /etc/ssh_config for the server.

For reciprocal authentication, each host must know the public keys of all other computers, together with its own private key. These are stored in the file /etc/ssh_known_hosts. Since the keys are very long and cryptic, they are usually not entered manually, but generated by means of the program ssh-known-hosts. This program can ask all computers in the domain for their public keys and store them. This requires the sshd process to be already running on all computers.

The sshd process should be started at system start-up, for example the rc.local, because the generation of the keys may well take several seconds, which can be inconvenient if the process is started by the inetd server. In the last step, the computers that are to allowed direct access must be entered in the file /etc/hosts.equiv. This file functions exactly like the file /etc/hosts.equiv, except that the identity of the alien computer is ensured by cryptographic methods. The file /etc/hosts.equiv is used even if no hosts.equiv exists.

Each user can additionally create the file ~/.hosts, which will then be used for authentication. Here too the file ~/.hosts is used as a fallback if the server is configured to do so in the file ssh-config. However, in my opinion, the more specific hosts files are more suitable, as the services are not (inadvertently) released if they have not (yet) been switched off.

As with the r tools, the system-wide /etc/hosts.equiv does not allow a login as root. If you want this to be possible, the entry PermitRootLogin in the file /etc/ssh_config must have the value yes.
