Several development tools are needed to compile the kernel. First, you need the GNU C compiler GCC together with its binutils; others, the assembler gas and the linker gld. Generating the kernel's boot sector requires the 16-bit assembler as86. The compilation process is controlled by means of the make program, which is discussed in more detail in Chapter 11. Dependencies are generated by means of a simple C Program which fulfils this task faster than the corresponding function of the C compiler. Compilation of the NCR SCSI driver also requires perl.

## 4.1.2 Compiling the kernel

After compilation

You should reboot with the newly created floppy disk and, after a successful install, execute the make command to install the new kernel. If the LILO boot loader is installed on your system, this command is equivalent to the command make zlilo. If, however, you use a different boot loader, such as loadlin, you can create a script /sbin/installkernel which will automatically execute all operations needed for the installation of the new kernel. I have created an alias that executes all the commands at once, which stops when an error occur (Listing 4.2).

(Linux):/usr/src/linux# make btdisk

(Linux):/usr/src/linux# make modules_install

## 4.1.3 Updating the kernel

A kernel update can be carried out in two ways. You can install a completely new kernel, or the changes in the source code can be transferred to the kernel sources by means of the patch program (see also Chapter 10).

### Complete installation of the kernel

Installing a new kernel is quite easy. First, the old kernel sources should be saved, so that the old kernel can be used again in case an error occurs. If you have enough hard disk space, it is sufficient to rename the complete path. Otherwise, it would be sensible to execute make clean and then store the kernel in a (compressed) archive (for example, by using tar). Subsequently, the new kernel sources can be unpacked and the already known process of kernel configuration and compilation can be run. Many system-related programs depend on the fact that at least the make step is performed. The necessary commands are shown in Listing 4.3.

```
(Linux):/usr/src/linux# make clean
(Linux):/usr/src/linux# cd .
(Linux):/usr/src/linux# mv linux linux.old
(Linux):/usr/src/linux# tar xvzf /tmp/linux-1.2.2.tar.gz
(Linux):/usr/src/linux# cd linux
(Linux):/usr/src/linux# make config
```
Listing 4.3 Complete kernel update.

### Patching the kernel

The second method of updating the kernel is known as patching the kernel. Since the source code of two kernel versions is often nearly the same, much less data has to be transferred for an update. A patch only contains the changes from one version to the next. Thus, if you want to use a kernel that is several versions more recent, it is even easier to obtain the new sources than to execute all patches in the correct order.

If these aspects are taken into consideration, updating the kernel is quite simple. As an example, we show the update from kernel version 1.2.1 to version 1.2.2. The advantage of patching is that you find all changes to the source text in a relatively well-structured way. If you have some programming experience, you should definitely have a good look at the patches before you install them. The zmore program used in the present example is not contained in the widely used Slackware distribution; you will have to use zless instead. The necessary commands are listed in Listing 4.4.

```
(Linux):/usr/src/linux# zmore /tmp/patch-1.2.2.gz
(Linux):/usr/src/linux# zcat /tmp/patch-1.2.2.gz|patch -p1
(Linux):/usr/src/linux# make oldconfig
```
## 4.4 Kernel update with patch.

After a patch, you should look for failed modifications. This can be done by the find program (see also Chapter 10) to search for the corresponding backup files. Depending on the patch version, these files are named *.rej or #*. Failed modifications are a bad sign; depending on your experience, you should either install a completely new kernel or perform the modifications manually using an editor. This kind of problem tends to occur if you have modified the kernel yourself or installed patches.

Backup copies are also created for files that have been successfully modified. Depending on the patch version, these files are named *.orig or ~ and can be deleted later. Further information on the patch program can be found in Chapter 10.

### Reconfiguring the kernel

It is error-prone and cumbersome to go through the kernel configuration time you install a new kernel or a patch. It is far more convenient to get only the new questions answered.

If you have patched your kernel start with oldconfig. This command reads your old .config file and stops at every new question. That way a reconfigurations takes only a few seconds instead of minutes.

If you installed completely new sources you may copy the file .config from your old kernel tree. Be aware that oldconfig may fail. In that case you can issue the make mrproper to start a fresh configuration.

## 4.2 Configuring the hardware

Many drivers use auto-probing to find and initialize the hardware by searching various I/O addresses (ports), interrupts or DMA channels for typical signatures. This can crash your computer, but it may also happen that installed devices are not found. In such cases you can change the list of addresses or interrupts to be checked in the kernel, or you can set the corresponding parameters by means of kernel command lines. This presumes however, that you use an appropriate boot loader (see also Chapter 3). The syntax of the kernel command line option depends on the individual driver, therefore you will find its documentation in the corresponding HowTo or README files.

Often, multi-serial cards are not correctly recognized. The corresponding parameters (I/O address and IRQ) can be set with setserial. In the widely used Slack distribution, examples can be found in the file /etc/rc.d/rc.serial.

Some drivers, for example CD-ROM drivers, support the configuration of the behaviour of the devices via the ioctl function. Here, for example, automatic ejection of the media when unmounting a CD-ROM file system can be switched on or off. An example that can be employed directly is the cject package. Parameters for a QIC-2 compatible tape drive can be set by means of the setqic2 program if you have not programmed directly into the kernel.

## 4.3 Kernel modules

One of the criticisms of LINUX is use a monolithic kernel instead of today’s ‘modern’ kernel. This criticism is, however, only partially justified. Interested readers should refer to a discussion between Linus Torvalds and Andrew S. Tannbaum, author of Minix and operating system specialist, on the advantages and disadvantages of the new development of LINUX. You will find the discussion that took place in the comp.os.minix newsgroup in the file linux_is_obsolete in the doc directory of the Linux ftp server.

A micro kernel (such as, for example, Mach) is a minimal kernel that contains only the most important functions (such as memory and process management or hardware drivers). File systems, personalities (such as a BSD or UNIX interface), or other functions are loaded later and implemented in the user space, that is, by means of normal programs. This allows greater flexibility, but at the expense of a higher cost and less speed. Since LINUX was originally developed on relatively slow (by today’s standards) 386 PCs, Linus had to make do without ‘modern’ concepts as a micro kernel.

During the course of time, however, several disadvantages of the original concept came to light. The kernel must be almost completely recompiled to accommodate a new driver. During the development of a driver, the kernel must be rebooted after each change, which entails a restart of the whole computer. Thus, the development of drivers takes more time, and the user loses out on the flexibility of other systems.

These problems led to the development of the concept of kernel modules. Here, drivers or other functions are added to or removed from the kernel (by means of the programs insmod and rmmod, respectively) at kernel runtime.
