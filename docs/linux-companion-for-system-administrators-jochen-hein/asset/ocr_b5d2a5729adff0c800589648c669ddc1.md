It is possible to obtain permissions via an additional group. Thus, for example, the devices for floppy disks (/dev/fd*) can be associated to a group, floppy, which is also given write permission for these devices. Subsequently, one can make the required users additional members of this group. If you use PAM there is a module that adds groups based on the configuration file /etc/security/group.conf to the current set of groups when running on the console. This is not bullet-proof but helps a lot.

In UNIX systems, the t bit for programs causes the program not to be reloaded from the file system when real memory runs, but from the swap space. Under LINUX this is not implemented, but with today's hard disks, this will not give a noticeable increase in speed.

As opposed to binary programs, shell scripts must be both executable and readable, for their execution they must be read and interpreted by the shell. For scripts, the setuid and setgid bits are ignored by the kernel for security reasons (with some trickery concerning PATH and IFS it would be easy to execute arbitrary programs by the setuid user). Thus, you may either write a small C wrapper or implement the script using methods of Perl which internally provides the setuid mechanism and performs many security checks.

Programs started with setuid or setgid should, if possible, not be readable for users, in order to make life more difficult for intruders. For example, strings could be used to find out which files are read and written, or the program could be disassembled¹. Making programs unusable is considered security-by-obscurity that generally does not work. On the other hand, why would an attacker get more information than necessary? Think of it as an additional safeguard.
