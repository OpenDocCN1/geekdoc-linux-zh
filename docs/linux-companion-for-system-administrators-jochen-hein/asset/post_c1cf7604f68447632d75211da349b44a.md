Some clients always send the password to the server in upper case. Under UNIX, upper and lower case spelling in passwords is significant. samba converts the password into lower case and attempts the login. If the password contains one or more upper case letters, the attempt fails. In the file samba.conf, you can enter password level = N in the [global] section to specify that all combinations with N upper case letters in the password are to be tried. For values of N, this can, however, take large amounts of CPU time.

In addition, samba can be used as a print server for SMB networks. For this, you must include the section [printers] in the file samba.conf. You need not define each individual printer; samba exports all printers and aliases from the /etc/printcap file. In the example of Listing 19.13, guests are not allowed to print, and the printers are not displayed in the browse list.

You, however, also define private printers for individual users. An example of this can be found in the samba sources.

If you use Windows for Workgroups, you should ensure that login the 'store password' box is not activated. Otherwise, anybody having access to your PC can login on the server under your name without a password. I consider this 'comfort function' a security problem, but it is often difficult to enforce the acquisition of products that allow a single login on the network.

```
[printers]
comment = all printers defined in /etc/printcap
path = /var/spool/samba
browseable = no
printable = yes
```

# Configuration and operation of a name server

The Domain Name Service (DNS) is defined in [rfc1034], [rfc1035], and [rfc1183]. It is used to manage an up-to-date and flexible database of the entire Internet, which has the purpose of converting computer names into IP addresses and vice versa. In the early stages of the Internet, this task was fulfilled by the file HOSTS.TXT, which was centrally maintained and then copied by the administrators to their local computers.

Such a method, however, is only practicable in relatively small networks, so a new service, the DNS, was developed. Today, the client side of this service is an integrated part of all TCP/IP implementations; today's Internet could not even be thought of without DNS. Local networks from a certain size onward also benefit from the use of a name server, even if they are not connected to the Internet. The administrative effort created by many (different) hosts files and problems arising from inconsistent entries can be prevented.

Detailed information on configuration and operation of a name server can be found in the sources of BIND (Berkeley Internet Name Domain). The official source of supply is given at the end of this chapter. Additional tips and tricks together with hints on frequently committed errors can be found in [rfc1536] and [rfc1912]. The program that manages the database and answers the requests of the clients is called named. On the client side, use is made of the Resolver library, which communicates with the name server.

# 20.1 The concept of Domain Name Service

The administration of names in the Internet is structured as a hierarchy. At the very top, we find the root name servers. These computers are primarily responsible for the resolution of names, and they keep the register that specifies which other name servers are responsible (or constitute the authority) for individual zones. In other words, these zones are delegated.

A domain as we know it the host name is not in all cases identical with a DNS zone. An example for different zones is shown in Figure 20.1.

![](img/ad3b0471a5d608a011338d028bec5422_497_0.png)

**Figure 20.1** Examples of DNS zones.

The top zone, which is not considered any further at this point, is .org. Here, the zones tuttifruti.example.org, veggies.example.org, and xpilot.org are delegated to other name servers. In our sample domain, the purchasing department runs its own name server. Therefore, the subdomain purchase.example.org is not part of the zone example.org. This zone is marked in Figure 20.1 by the dotted line.

Technically, a zone is determined by an NS data record in the superior name server. A zone can be identical with the domain, but further name servers which in turn manage separate zones may be defined as being responsible for subdomains. This separation originates from organizational factors, such as different responsibilities for network administration or geographical separation of individual departments or branches.

Users generally use computer names, and no IP addresses, because well-chosen names are easier to remember. Therefore, a failure of the name server is

# 20.2 Migrating from BIND4 to BIND8

If you have already running BIND as a name server, you may still be running version 4 of BIND. Since there have been many updates, bug fixes and security fixes, it might be a good idea to switch to BIND8. It is not much work, and if you have any problems it is easy to revert to the old version.

The only thing that has really changed is the syntax and the name of the primary configuration file. It was formerly named.boot and is now called named.conf. You'll find that the script named-bootconf in the BIND distribution will create a reasonable configuration for BIND8 from your existing BIND4 configuration.

```
(Linux):# named-bootconf < named.boot > named.conf
```
