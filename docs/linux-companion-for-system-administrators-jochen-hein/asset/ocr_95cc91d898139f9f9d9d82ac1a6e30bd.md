# SYSTEM LOGS 125

The output files must exist at the start of the syslog daemon. If a file has not been created, the daemon displays an error message. The corresponding file can then be created by means of the command touch file name. One reason for this is security. Only the system administrator can decide on the correct permissions of logfiles.

After a modification of the configuration file /etc/syslog.conf, the daemon must be reinitialized. This can be done by sending the HUP signal to the running syslog, for example using the command

```
kill -HUP /var/run/syslog.pid
```

If you want to know whether the required message is correctly protocled, you can verify this by means of the command

```
logger -porigen.importance "text"
```

However, this also allows messages to be generated and the size of the log files to be significantly increased, especially if the attacker sends two different messages repeatedly.

Protocol files have the annoying property that they continue to grow and never ever disk space. Therefore, log files should be emptied at regular intervals. To prevent older messages from being deleted immediately, it is a good idea to send the logs to the system administrator via mail or to create a backup copy. In part (for the news system or in UUCP), this is already done by scripts which belong to the system. For the other log files, you can use your own script or resort to the prune package

In a multi-user system it is necessary and sensible that not all users can read all log files. Thus, for example, log error messages in which user names or passwords might appear read only for the system administrator. During creation of a protocol file with touch, the permissions are set according to the specified umask. These might be incorrect permissions; therefore log files should not only be deleted and newly created with touch. It is much better to reset the files by means of output redirection, for example with the command echo -n > Logfile.

The Red Hat contains the logrotate program, which can be used to shorten log files on a regular basis. Before and after shortening, commands can be executed, for example a restart of the syslog daemon. In addition, the file permissions can be specified and version management can be set up. In this way, you always have an up-to-date log file plus one or more versions of which will be deleted.
