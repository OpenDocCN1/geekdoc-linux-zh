- Under X, there are two alternatives for how windows are focused on, that, become the current window. fwm normally uses 'focus follows mouse'; alternatively, the keyword ClickToFocus can transfer the focus via clicking in the window. Active windows are automatically brought to the foreground after the number of milliseconds specified by AutoRaise has.

- fwm can manage virtual desktops. The size is specified by the entry DesktopSize. You can toggle the various desktops by means of the keyboard (Alt-arrow key) or the mouse. The window pointer may be moved to the screen border. After the lapse of time specified after EdgeResistance, the screen is scrolled by EdgeScroll. The second parameter after Edge-Resistance specifies how one has to wait when a window is moved as well.

- Some settings can be made for reasons of compatibility with mwm (Motif Window Manager).

Positioning of the windows can be influenced via different settings.

- Interactive positioning of the windows is the default.

- RandomPlacement stands for arbitrary positions.

- SmartPlacement tries to find a free area on the screen. If this fails, interactive or random placement is used.

- StubbornPlacement prevents covering up of iconized programs.

- The Menus which appear on the background (the root window) can also be arbitrarily modified.

- Together with fwm a series of modules is installed which are also configured in the .fwmrc. A more detailed presentation of some of the modules follows in the next section.

- Many functions of fwm can also be triggered by function keys. This can be useful for transferring the focus, for example by using (Alt-Tab).

After changing the configuration, fwm must be restarted. For many other window managers this would require termination of the session, but fwm can simply be restarted by means of a menu option.

## 6.4.2 The fwwm modules

Many functions required by some users need large amounts of memory which can be saved without causing problems for other users. fwwm supports this via the use of modules that carry out special functions.

- GoodStuff
This module generates an icon bar which allows frequently used programs to be started with a click of the mouse. This bar can be easily configured for each user and can be positioned anywhere on the screen. To make the bar appear, fwwm must be started together with this module.

- FwmAudio
This module allows you to associate sounds to specific window actions, for example every time the close button is selected, you hear the sound of a breaking glass pane (provided a sound driver pulse hardware exists and is activated).

- FwmBack
Allows you to associate each desktop to a separate screen background and display it when desktops are changed. Any available program can be used for this purpose, for example xv, xsetroot, xpmroot, hearth, and so on.

- FwmBanner
Shows the fwwm logo in the middle of the screen for five seconds. Can also be called from the command line.

- FwmIconBox
Manages a box containing the icons of the started programs.

- FwmPager
Allows to switch between the virtual desktops by means of a simple click in an overview window. This window can also be integrated into the icon bar of GoodStuff.

- FwmSave
Allows the layouts (sizes and positions) of the active applications to be stored in the file ~/.new.xinitrc. Obviously, this file must then be used by ~/.session or ~/.xinitrc.

- FwmWinList
Displays a list of open windows. A window can be activated by clicking on the corresponding entry in this list.

## 6.4.3 Other window managers

If you use Motif, you will find that it includes mwm. This is a window manager that harmonizes with other Motif applications and is described by the style guide. This window manager is seldom used, since current commercial systems are usually equipped with CDE.

The lestif project contains a free implementation of mwm which is based on fwwm. This has kept its capability of handling virtual desktops, but the syntax of the configuration file was made compatible with the original. Both programs read the file ~/.mwmrc.

CDE and KDE also include their own window managers. CDE uses dtwm, which is based on mwm, whereas the KDE project uses kwm.

Further window managers worth looking are AfterStep, which emulates the look and feel of the OpenStep system (for a complete implementation http://www.gnustep.org), and Enlightenment, which is particularly eccentric in its graphics. Whichever window manager you choose, you will certainly be able to find one under LINUX that meets your requirements.

## 6.5 General X11 command line options

Many X11 application programs, including all programs developed by the X tool kit (libXt), 'inherit' some command line options. Even if, according to its man page, an application program is unable to specify size and position of a window at the call, for example, this is nevertheless possible because the passed options are first evaluated and also understood by the X tool kit. The following points briefly present some of these generally applicable command line options. All options are described in the man page for X(1).

- Screen
With -display, host name and screen number of the server are specified; for example, 'display' corresponds to dorin:0.0. More details on the use of X in the network can be found in Section 6.6.

- Size and position of windows
The option -geometry is used to specify the initial size and position of a window. A valid 'Geometry' could be, for example, -81x24+0+0, which would open a window of 81 chars by 24 lines in the upper left corner of the screen. The xwininfo program displays this (and further) information.

It is, however, not sensible that any user can access any server - unfortunately, this is still the standard with many commercial X servers or terminals. On the one hand, screen output and keyboard input can be monitored; on the other hand, keyboard input can even be foisted on clients. This can become a real security problem, because as a user, one is not always aware of such proceedings.

## 6.6.1 Allowing computer access with xhost

To maintain flexibility despite the security concerns, sophisticated security mechanisms are needed. Up to release 4 (X11R4) access control was only possible via the computer name. With more recent releases, you should use xauth procedure presented in the next section. By default, access from other machines is not allowed; entering the command xhost + allows access from arbitrary. Some X terminals use this setting, which leaves the door open. If you come across this setting, you should immediately remove it. It may be easier to forget about these things, but it ruins the security of the whole system. The command xhost prevents general access. Usually, you will authorize access only for a specific computer with the command xhost hostname. As already mentioned above, this procedure is not particularly secure. Every user with an account on the corresponding computer can gain access to this server. Therefore, another authorization procedure was implemented with X11R5. Management of access rights is carried out by means of the xauth program. During the start of the X server (or the login with xdm), a random cookie is generated and stored in the file ~/.xauthority. Each client knowing this cookie is authorized to access the server. Thus, if you transfer the magic cookie to another computer, it can be monitored with a packet sniffer and used for breaking in. The magic cookie is newly generated by xdm with each login, so an old access authorization cannot be used for second time.

## 6.6.2 Allowing user-specific access with xauth

With this method, you can reduce the lapse of time during which you are vulnerable, but the procedure is still far from secure. If you have the same home directory on the corresponding computers (via example NFS), client and server have direct access to the key. If the client runs on a computer which has no access to the key, then the key must be transferred. Listing 6.3 shows an example for the application of xauth. If you work with different computers, you can define appropriate aliases. Please note that magic cookies should not appear in the command line for xauth. Otherwise, the key can be read, for example, from the process list.

```
(Linux):~$ xauth list
hostname/unix:0 WITH-MAGIC-COOKIE-1 66e15be3b6c1b12e0df5
(Linux):~$ xauth extract - rsh dorin xauth merge -
(Linux):~$ rsh dorin xterm -display 'hostname' -f':0'
```
