## Performance measurements with spray

The spray program can be used to determine the possible throughput over the network with relatively simple means. On one computer, the sprayd daemon must be started. Subsequently, you can use spray to test the connection with this computer. The packets are transmitted by means of the UDP protocol.

If you know the values for an empty and normally loaded network, you may be able to get an idea of the state of the network. Bear in mind with this program, you can hammer other users in their work, because the network is fully loaded. At the end, the spray program displays a statistical overview of sent and received packets. By means of the options -cs and -l, the number and size of the packets can be made. Additional options are explained in the man page.

Listing 24.6 shows a sample output of spray. The program was only run for a short time to avoid disturbing other users in the network. Note that with many of the programs presented here, you can actually increase the network load substantially, worsening the situation.

```
(Linux:> spray pea
sending 1162 packets of length 86 to pea...
in 2.36 seconds elapsed time,
0 packets (0.00%) dropped.
Sent: 491 packets/sec, 42.3 KBytes/sec
Recvd: 523 packets/sec, 45.0 KBytes/sec
```
Listing 24.6 The spray program.

spray uses UDP as a protocol. This does not ensure reliable transmission of the packets, and the measurement depends on the speed difference of the two computers. Therefore, the TCP-based tcpspray is better suited to make meaningful assertions about network performance.

## Performance measurements with tcpspray

As an alternative to spray, you can also use tcpspray. Here, TCP is used for data transmission instead of UDP. Again, all caveats mentioned above apply. As a 532 NETWORK ADMINISTRATION counterpart, tcpspray uses the internal discard service of the inetd on the computer specified as the parameter. Alternatively, you can also use the echo port if you specify the option -e.

## 24.2.3 Testing of TCP services

For testing a TCP service, you can use the telnet program. To do this, you must establish a connection directly to the required port, after which you can test the service directly. We suggest that you begin by trying telnet localhost smtp. If you know how this protocol works (this is defined in [rfc0821]) you can now test this service manually.

It is often possible to start a new version of a daemon under a different port and check it there before replacing the old version. If a system is already utilized by users, care should be taken that such changes are kept as far as possible to them.

Listing 24.7 shows an example of a simple test of a POP3 server. POP3 servers are used to give users access to their mailboxes from remote machines (people are now migrating to IMAP (Internet Message Access Protocol), but for the purpose of this example we stick to POP3). Please note that the password is transferred transparently (security-aware tunnel POP3 over an ssh connection). Sometimes you see messages that are incorrectly interpreted by ssh or indicate an error that is not correctly displayed by the client. And if all fails, you may work through the description of the protocol in the corresponding RFC.


## 24.2.4 Fault detection in RPC services

When you are using RPC services, additional errors can occur besides the problems already mentioned above. First of all, you should check whether the port mapper is running. Subsequently, you can use `rpcinfo -p hostname` to find out which services are registered with the port mapper. As a last step, you can test the individual daemons by means of `rpcinfo -u hostname` service.

## 24.2.5 Network File System

The Network File System is based on RPCs, so that you should first check the items mentioned above in connection with RPC services. You can use the `showmount` program to determine which volumes are exported by the computer in question. You can also find out which client has mounted directories.
If you have problems with data throughput via NFS, you can try increasing the buffer sizes for write and read access to 4 and 8 Kbytes, respectively. This should usually result in a significant improvement in reading and writing speed.

## 24.3 IP network management

In many companies, the IP network is managed with the aid of SNMP (Simple Network Management Protocol [rfc1157]). Each device managed with SNMP (including workstations, routers, switches, printers, and many others) organizes its information in the Management Information Base (MIB). The MIB is defined in the Internet Standards [rfc1441|rfc1450]. Beside (static) information on the device (for example, person responsible), dynamic data are also managed. Access to the information in MIB is managed via the Community. The default Community is public and allows read access. Modification of the data should be permitted to another Community. Furthermore, it may be sensible to limit access to the MIB to the IP address of the management station.

Individual devices can register with the network console by means of SNMP trap and trigger different actions. A great disadvantage in heterogeneous networks is, however, that only IP devices are included. Other protocols cannot be handled, so you might need an additional tool for this purpose.

## LINUX as an SNMP client

One available package for LINUX is the snmp package of Carnegie Mellon University (CMU). This can be used to call upon various items of information on a LINUX computer. This information extends from data connection of the computer to CPU load or occupation of hard disks.

## LINUX for network management

At the Technical University of Braunschweig, the tkined package was developed for network management with SNMP. This program package was written in Tcl/Tk (with extensions for network access); the source code can be found on the ftp server of the TU Braunschweig.

With this program, you can generate a map of your network. Based on this map, you can carry out various management tasks and create statistics (also as graphics). This tool is an inexpensive alternative to commercial packages available, for example, IBM, Sun, or HP.

Figure 24.1 shows the representation of a simple map. The centre is constituted by a switch which connects the different network segments with each other. Here, these segments are represented as icons, which can be expanded if required; then, access is possible to all devices of that segment. Here, each segment is associated a statistical representation of the network load.
