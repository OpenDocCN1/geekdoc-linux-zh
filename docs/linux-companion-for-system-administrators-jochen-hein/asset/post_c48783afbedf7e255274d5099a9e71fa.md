## 17.2.1 Problems with the use of NFS

NFS is implemented on the basis of RPCs. Usually, a stateless protocol (UDP) is used. This means that the server has no history for the current requests and that, therefore, caching functions can only be realized to a very limited extent. The advantage of NFS is that the client can be sure that the data is stored on the server disk after the corresponding call is terminated.

Sharing files is only possible in a reasonable way if the user names and the corresponding user IDs on the participating computers match. When you activate NFS for the first time, you will notice that users sometimes have different UIDs on different computers or that one UID belongs to several servers. Before you employ NFS, you should clean up the password files (and assign the files to the correct users).

First, you should create a list of the files that are owned by a user, for example using `find -uid userID`. Then you adapt the password file and convey these files to the new ID using `chown`. Manual synchronization of the password files is laborious and error-prone. You should therefore think about using NIS (see Chapter 21). The use of the augd program which adjusts the user IDs at runtime on the basis of the names may only be seen as an emergency solution.

During data exchange via NFS, the internal clocks of the participating computers should be synchronized to prevent problems. When files are created, they receive a time stamp by the server. When the same files are read (maybe afterwards) this time stamp is interpreted on the basis of the local time of the client. If the times differ, programs such as make get confused.

Apart from these problems, it is also less confusing for the user if the internal clocks do not differ. Since PC clocks in particular are inaccurate, you must take special measures. Relative divergences can be corrected locally by means of the adjtime program. To synchronize the clocks in the network, you can employ various methods, all of which have their raison:

- You can request the time from the NIST Network Time Service via the Internet (for example, from http://www.time.nist.gov). The service responds in several formats, including the DAYTIME, TIME, and NTP protocols.

- If a time server exists in the network, you can fetch the time from there by means of program ntp. Some RFCs (for example [rfc1305] and [rfc1769]) describe appropriate protocols for time synchronization.

- You can use the programs netdate or rdate to obtain the time from one or all computers in the network.

In the management of data and program files, NFS is almost completely transparent to the user. The situation is different for device files and normed pipes. Here, communication with the kernel or an application program on the other side of the pipe is to be established. Neither can be realized via the NFS if different operating systems are involved.

You should make sure that the NFS server is connected to the same subnet and network segment. Otherwise, the router may be (overstrained through the high network load, and bridges cannot separate loads between individual segments. In the long run, neither is good for the safe operation of the network and thus for user satisfaction.

Currently the SMB protocol is further developed to become the Common Internet File System (CIFS). Beside Microsoft, the Samba team is also participating in this development, which is intended to provide better performance and better semantics than NFS.

## 17.3 automounter

In a local network in which many directories are mounted back and forth between different computers via NFS, it is often not sensible to do this directly at the start-up of the computer. On the one hand, each mounted volume occupies one of 32 superblocks in the LINUX kernel; on the other hand, the corresponding server must be available for the mounting process. If the NFS server can no longer be reached during active operation, then, depending on the type of data used, operational restrictions must be expected. Furthermore, the fstab files continue to grow and, in case of a change, must be adapted on all computers.

These problems were the background for the development of the automounter. Here, the corresponding directories are only mounted into the directory tree when they are actually needed. If the data is not used for a certain period of time, the volume is unmounted. The automounter is flexible enough to ensure that, in the event of failure of a server, another computer can take its place.

Because of the flexible (and somewhat more complex) syntax, one configuration file can be used for all computers in the local network. This significantly reduces management effort, in particular if this file is distributed by means of NIS (see Chapter 21).

### 17.3.1 Internals of the automounter

In the local network, each exported volume receives a unique name. Under this name, all computers in the local network can address this volume. This makes it possible to have the same home directory on all computers. Frequently, the mail directories are mounted in the same way.

However, depending on the computer architecture or the operating system used, the automounter can mount different volumes that fulfilment the same purpose (for example the TeX path for different architectures).

Besides this, local devices such as a CD-ROM drive or diskette drives can be mounted as well. This allows you to do without the usermount program.

### 17.3.2 Conditions for using the automounter

The automounter is implemented internally as a server. Therefore, as with NFS server or client, the RPC port mapper and the other daemons are required. In addition, amd must obviously be started. The configuration of the automounter is carried out in two steps. First, the list of maps to be managed is stored in the map file `/etc/auto.master` (Listing 17.4). The format of this file is documented in the man page for `auto.master`. Each individual map is located in a separate file.

## 17.3.3 The LINUX autofofs

Kernel version 2.1 and later versions include the autofofs file system. This is an alternative to the BSD automounter (amd) and is intended to take its place in the foreseeable future. In addition to autofofs in the kernel, you will need the appropriate utilities. A source is given in the info box at the end of the chapter.
