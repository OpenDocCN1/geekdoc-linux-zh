## 4.6.3 Printing on other network printers

In many networks, not all printers can be accessed via TCP/IP; often they can only be accessed via the NetWare protocol or the protocol of the Windows network. Since LINUX can be integrated into both networks, it is possible to use these printers as well.

If the IPX system is installed and configured (see Section 20.1), it is possible to print to NetWare printers by means of the command `nprint`. If you include a `nprint` call in an input filter of the `lpr` system, you can use a LINUX computer as a gateway between the different systems.

Printers on a Windows network can be accessed by means of `smbclient`. This program is part of the `samba` package; more information on this package can be found in Section 20.2.

## 4.7 System logs

Every UNIX system keeps a series of log files for the purpose of system behaviour monitoring and error detection. A generally accessible interface by means of which programs can write log files is the `syslogd`. This daemon is configured by entries in the file `/etc/syslog.conf`. Depending on their origin or importance, it allows messages to be displayed or redirected into different files. In networked environments it is possible to have the log files kept by a special computer, known as the log host.

Depending on their importance and origin, the log entries can be treated in different ways. Table 4.6 describes the different origins (or facilities).

| Origin | Description |
| --- | --- |
| auth | Security/authorization messages |
| authpriv | Private security/authorization messages |
| cron | Messages from cron and at |
| daemon | Other system daemons |
| kern | Output of the kernel |
| lpr | Logs of the lpr system |
| mail | Messages of the mail system (sendmailetc.) |
| mark | Inclusion of marks in the log files |
| news | Output of the news system |
| syslog | Messages of the syslog daemons |
| user | General messages (default) |
| uucp | Logs of the UUCP system |
| local0-7 | Origins for local use |

**Table 4.6** Origins of syslog messages.

For each of these origins, the message can have a different importance. Table 4.7 contains various settings ordered by decreasing importance.

| Importance | Description |
| --- | --- |
| emerg | An emergency is signalled |
| alert | ‘Yellow alert, active shields!' |
| crit | A critical situation has occurred |
| err | An error situation has been recognized |
| warning | A warning |
| notice | A notice |
| info | Informative message |
| debug | Output for detection |

**Table 4.7** Importance of syslog messages.

Listing 4.29 shows an explanatory example of a syslog daemon configuration. It should be noted that message origin and destination must be separated by tabs. Also, many syslog implementations do not allow spaces before or after the destination.

| Facility.Level | Destination |
| --- | --- |
| kern.* | /var/log/kernel |
| kern.emerg | * /var/log/errorlog |
| *.err | * /dev/console |
| *.emerg | /var/log/debug |
| *.debug | root,jochen |
| *.crit | * /alogost |

Listing 4.29 Excerpt from the /etc/syslog.conf.

All messages generated by the UNIX kernel (kern.*) are written into the file /var/log/kernel. The slash (/) as first character tells the syslog daemon that this destination is a file or a device. Kernel messages that signal an emergency are sent to all users (*) currently logged in. All messages of systems that are of importance err or higher are recorded in the file /var/log/errorlog. Messages that signal an emergency are in addition prototyped to the console.

If you want to prevent more messages from being included in a protocol, you can specify the importance with an equals sign (=). Thus, all messages concerning error detection (and no others) are recorded in the file /var/log/debug. The last two lines demonstrate the notification of users root and jochen in the case of critical messages, together with the transmission of these messages to another computer (loghost) for prototyped.

If you want to store messages on a log host, you start the syslog process with the command option -r. Otherwise, no messages are accepted from remote computers to prevent users filling the hard disk by means of the logger program. Other useful options are -l followed by a list of computers whose names should not be stored and -s by a list of domain names which should also appear in the log.

On a private system it can be sensible to display all messages on an unused virtual console, for example /dev/tty12. Then, with the touch of a key, the log entries can be viewed and the necessary measures can be taken. The appropriate entry in the file /etc/syslog.conf is shown in Listing 4.30. Please note that not all UNIX systems support this kind of entry.

```
* /dev/tty12
```

Listing 4.30 All messages are directed to /dev/tty12.

## SYSTEM LOGS

The log rotate can work with arbitrary files, old logs can be deleted or compressed, an arbitrary count of old versions can be kept, and you can execute any command you wish before or after the rotating of the logs. Logs can be rotated daily, weekly, or monthly, or depending on the size of the log file. logrotate is not integrated in syslog, but apart from that almost everything you can wish for is implemented.

logrotate's option create creates an empty file with the corresponding owner, group, and permissions. Listing 4.31 is an example of a simple configuration. More information is available in the main page logrotate(8).

```
# Log file get rotated weekly
weekly
# keep four versions
rotate 4
# please send error message to 'root'
errors root
# create new log files as default
create
# More configuration in that directory.
include /etc/logrotate.d
```

**Listing 4.31** A simple configuration for logrotate.

The configuration in listing logrotate.conf is for all files that logrotate rotates. You can override the configuration for each file as needed. The directory /etc/logrotate.d is a storage pool for other packages that logrotate configures. That each package that writes log files can easily drop in a configuration file for logrotate. Examples for such packages include UUCP, apache, or samba.
