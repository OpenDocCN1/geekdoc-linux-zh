In a bigger network, the maintenance of a large number of hosts files is very labour-intensive and easily leads to inconsistencies because on different computers you will often find divergent and incomplete name tables. The correspondence between names and addresses should be unique so that on each computer the same hosts can be addressed under the same names. Here, centralized administration is needed to ensure this consistency.

The unique nature of host names can be ensured by means of the Domain Name Service (DNS) for which a name server is set up. All data is centrally maintained on this computer and distributed via the network on demand.

Another alternative is the use of the Network Information Service (NIS) (see Chapter 21). The use of NIS, however, only makes sense in UNIX networks since Windows clients usually cannot handle NIS, whereas they can start NIS requests and use the answers.

## 15.2 Domain Name Service

Setting up a name server is sensible for a variety of reasons. The administrative effort of synchronizing the name tables in a bigger network can be reduced, in particular when Windows and other clients are used which do not allow central administration of hosts files. For dial-up connections it may be sensible to use a cache server. This avoids repeated requests to external name servers. More information on the DNS can be found in [rfc1033], [rfc1034], and [rfc1035].

A name server is responsible (authoritative) for a determined zone. Requests that the name server cannot answer are forwarded to the next higher server, which in turn may also forward the request. Since the superior server does not have all the data of the subordinate servers, it can also forward the request downward to the appropriate server. When you are connected to the Internet, it is therefore important to announce the existence of your own name server, for example to your local NIC. When you apply for your own domain, this is done either by the provider or the responsible Network Information Centre.

To ensure fail-safe operation, there should be at least two name servers for each zone, one primary server and at least one secondary (backup) server.

primary server maintains databases which store information on computers and their addresses. The backup server copies this data at regular intervals and can thus take over the function of the name server in case of failure. For this purpose, the secondary server stores the data in a file which is used as a basis for answering the DNS requests.

In many cases, your ISP will operate the name server for you or at least provide a secondary server. Often or two customers of an ISP mutually operate a secondary server.

Please ensure the presence of a DNS backup server in your network. If this service breaks down, it looks to many users like a total breakdown of the network – the DNS is a central service in TCP/IP network. For this reason, the protocol requires secondary servers that fetch their data automatically from the primary server. With respect to the clients, you simply enter several name servers into their configurations.

## 15.3 Using a name server with LINUX

This section deals with the use of an already existing name server as a client. The configuration of a name server is extensively described in Chapter 20, where you will find additional hints for its operation.

With the GNU libc (also known as libc-6), linkage to a name server is configured in the file /etc/nswitch.conf. This file has the same format as under Solaris; an example can be found in Listing 15.2.

The name nswitch stands for ‘Name Service Switch’ and is used not only for configuration of the DNS client, but for many other configurations. If application programs only use the libc functions gethostname() and gethostbyname() for reading the hosts file, the call of remote services is completely transparent for programmers and users. More information on this subject can be found in the Info documentation on GNU libc version 2.0 or higher.

passwd      files nisplus nis
shadow      files nisplus nis
group       files nisplus nis

In the next step, the name server to be used in the file /etc/resol.conf (Listing 15.3). The name of the file is derived from the resolver library (libresolv) which is responsible for name resolution. On some UNIX systems (as under older LIN systems) this library is an integrated part of libc, whereas on other systems and now with the GNU libc version 2, the resolver library must be explicitly linked with the option -lresol.

Up to three **nameserver** entries are allowed in the file /etc/resol.conf. The servers are addressed in the specified order, so the local (or most reliable) server should occupy the first position.

```
nameserver 192.168.3.150
domain store.tittfrutti.example.org
search store.tittfrutti.example.org tittfrutti.example.org
# sortlist sort-list
# options option-list
```

If no name server is registered in resolv.conf, your own computer is used as a name server. However, the IP address should be specified instead of the host name to prevent recursion (name server or NIS requests) or deadlocks. If the top-level domain (for example .uk, .edu or .com) were also part of the search list, a further request is added to the above-mentioned requests which would, for example, for the computer somehost.somewhere.org org.uk. This kind of domain name is no longer assigned, and neither are two-letter subdomain names.

The search list (keyword search) specifies how to construct an existing computer name out of an incompletely specified name. By default, the only domain name is appended rather than all parts of the domain separated by dots, as in older versions. An incongruent entry in the search list can lead to a number of unwanted DNS requests to alien computers, which is not well received. The following example is intended to clarify the process.

In the sample file /etc/resolv.conf (Listing 15.3), the search list is entered as store.tittfrutti.example.org. Now, a user tries to establish a connection with the computer name into an IP address (with a aid of name server, the file /host.conf), a search is made for the computer name itself. If it is not found in the name server, the string store.tittfrutti.example.org is appended with a dot (.) to the computer name, and the next entry of the search list is asked again. If this request is unsuccessful (tittfrutti.example.org in the above example) is tried.

For individual processes, you can overwrite the configuration of search and option with the environment variables LOCALDOMAIN or RES_OPTIONS. More detailed information on the keywords sortlist and option can be found in the man page for resolver (5).

## 15.4 Testing a name server

Several programs are available to test the connection to a name server or its configuration. Some of the widely used tools are presented in the following sections.
