Each name in the PTR record is terminated with a dot to prevent BIND binding from the domain IN-ADDR.ARPA. ## 20.7.8 Mail Exchange (MX)

If a computer cannot be reached at the moment of sending mail (or the computer is not connected to the Internet, but via UUCP), another available computer can be entered for receiving the mail. If the original computer becomes reachable again, the mail is forwarded. Lower preference values correspond to 'costs'.

This function is often employed to enable only one or two computers in the network to accept mail. This concentrates configuration efforts and availability problems to a few computers only. You should check with the administrator of the computer before you have an MX record point to another computer. Otherwise, this computer will be bombarded with unexpected mail which may get lost.

Most mail servers are configured to accept only local mail and relay mail only to from local users. This is considered good practice, it stops members from abusing the system. However, you cannot simply use that machine as your MX, because relaxing is denied, and mail will be bounced back to the sender.

```
name                (ttl) addr-class preference exchange
pea.example.org.      MX 0
```
**Listing 20.12** Mail Exchange.

## 20.7.9 Text (TXT)

For each computer, arbitrary text can be stored as additional information. Apart from the fact that this text must be enclosed in double quotes (""), no further restrictions apply.

| name | {ttl} | addr-class | TXT | string |
|---|---|---|---|

| pea.example.org. | IN | TXT | "A text" |

**Listing 20.13** Text.

## 20.7.10 Responsible Person (RP)

Besides the person responsible for the name server, a contact person for this computer can be stored for each entry. Here again, the '@' character (@) in the mail address is replaced with a dot. If, however, you manage your computer with the aid of SNMP (Simple Network Management Protocol), you should enter this information into the Management Base (MIB).

| owner | {ttl} | addr-class | RP domain-name |
|---|---|---|---|
| jochen.example.org. | IN | RP | |
| sysadmins.example.org. | IN | TXT | "Tel:..."

**Listing 20.14** Responsible Person.

## 20.7.8 The file named.local

The file named.local (see Listing 20.15) which is located in /var/named directory contains the data pertaining to your own computer and consists of only a few entries which are important if users also want to use the entry in their hosts files.

```
@ SOA example.org. hostmaster.example.org. (19860201 3600 300 3600 14400)
IN NS example.org.
0 IN PTR loopback
0 IN PTR localhost
```
**Listing 20.15** The file named.local.

## 20.9 The file named.rev

The file named.rev stores the names belonging to given IP addresses. This makes it relatively quick and easy to find a corresponding name for an IP address; this function is also reverse lookup. The file is stored in Master format. Some people generate both from an external database by means of perl or awk script. In any case you may want to use a program like nslookup that checks your zones in detail.

```
@ SOA example.org. hostmaster.example.org. (198602501 10800 3600 3600 86400)
IN NS example.org.
0 IN PTR example.org.
IN PTR A example.org.255.255.255.0
151.31 IN PTR corn.example.org.
155.31 IN PTR pea.example.org.
```
**Listing 20.16** The file named.rev.

Please note that you must terminate each host name with a dot. Otherwise, the domain in-addr.arpa would be appended. Also, you should ensure consistency between the files named.data and named.rev.

## 20.10 Secondary name servers

For reasons of safety against failures, at least two name servers should be operated in each zone. In the event of the failure of one computer, the second name server can answer all requests. To keep the data consistent at any time, only one (authorized) master server must exist per zone. Besides this, one or more secondary servers may be configured. a secondary server fetches its data from the primary server. If this is not available, the data stored in backup copies (.bak) is used. If the life of the data has expired, an attempt is made to fetch this data afresh from a primary server. Listing 20.17 shows an example of the file /etc/named.conf for a secondary server.

```
zone "example.org" {
  type slave;
  masters { 192.168.3.150 };
  file "named.bak"
}
zone "192.in-addr.arpa" {
  type slave;
  masters { 192.168.3.150 };
  file "named.rev.bak"
}
```
**Listing 20.17** The file /etc/named.conf for a secondary server.

On the basis of the serial numbers registered in the SOA records, a secondary name server can determine whether it has the current data of a zone. If not, a new transfer is triggered. If you specify a smaller serial number in the primary data, the secondary name server will react with an appropriate message. You should therefore keep an eye on the system log entries of all name servers to exclude this kind of error. Otherwise, secondary servers are completely maintenance-free.

## 20.11 Slave name servers

A slave server does not manage zone-related data, but only a cache, and forwards requests that cannot be answered on the basis of the cache contents to specific name servers (forwarders). This allows this computer to build up a good cache from which all users can benefit.

In principle, every name server can be configured for use of forward. This is sensible if, for example, the name server is not directly connected to the Internet. If the router or firewall is entered as a forwarder, this can forward the requests. A further advantage is the formation of a large cache so fewer requests need to be answered by other name servers.

Forwarders ask the registered servers in addition to the known root name servers. In a slave server, only the forwarders are asked. If these cannot supply an answer, the host name cannot be resolved. Since these computers may need to procure data themselves, you should enter the addresses several times in the file /etc/named.conf. An example is shown in Listing 20.18.

```
# config file for forwarding only name server {
    directory "/etc/named";
    forward only;
    forwarders {
        194.45.71.65;
        192.168.3.150;
        194.45.71.65;
    }
};
zone "." {
    type hint;
    file "named.root";
};
```
**Listing 20.18** The file /etc/named.conf for a slave server.

In the first place, you should enter the fastest (and most stable) name server. Since it is possible (and even probable) that this computer must initially procure the data itself, you should place the entry for this computer once or twice between the other forwarders.
