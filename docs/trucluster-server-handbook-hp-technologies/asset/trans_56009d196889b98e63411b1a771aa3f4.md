

如果某个文件系统在集群范围内挂载，且为该文件系统提供服务的成员发生故障，只要集群中还有另一个成员具有通往包含该文件系统的设备的活动路径，那么CFS就会自动将服务器功能重新定位到该成员。此规则有两个例外：

- 文件系统以分区文件系统方式挂载（即 `mount -o server_only`）。参见第13.4节。
- 文件系统是NFS文件系统。

如果集群成员正作为NFS挂载文件系统的CFS服务器（即该集群成员是NFS客户端）并且该成员发生故障，则该NFS挂载的文件系统会在整个集群范围内被卸载。

为防止成员故障时丢失NFS挂载的文件系统，可以为您希望重新挂载的NFS文件系统配置automount或AutoFS（autofs）。

有关automount的更多信息，请参阅automount(8)参考页、《Tru64 UNIX 5.1A版网络管理：服务指南》或《Tru64 UNIX 5.1版或5.0A版网络管理指南》。

有关autofs的更多信息，请参阅autofs(8)、autofs mount(8)和sys_attrs_autofs(5)参考页，以及《Tru64 UNIX 5.1A版网络管理：服务指南》或《Tru64 UNIX 5.1版网络管理指南》。V5.0A不支持AutoFS。另请参见第20.4节。

## 13.4 文件系统分区

在TruCluster Server产品的第一个版本（V5.0A¹）中，当您在集群中的任何成员上发出mount命令时，所有成员都会自动在同一挂载点访问该文件系统。虽然这通常被认为是一件好事，但可能有些原因会使您不希望集群中的每个成员都能访问某个文件系统。例如，您可能有一个应用程序，由于应用程序本身未内置同步机制，只能同时在其中一个成员上运行。如果该应用程序位于所有成员都能访问的文件系统上，那么该应用程序有可能被同时在多个成员上启动。

虽然您可以设置一个集群应用程序可用性（CAA）应用程序资源，以在集群中自动启动/停止/重定位应用程序，但除非设置应用程序的权限（这实际上可能会带来其他问题），否则无法阻止某人启动该应用程序。有关CAA的信息，请参见第23章和第24章。

### 13.4.1 挂载分区文件系统

仅在一个成员上挂载文件系统非常简单。您只需在mount(8)命令中添加“-o server_only”选项即可。例如，我们集群中的/kits挂载点当前是在集群范围内挂载的。我们可以通过对集群中的每个成员发出df(1)或mount命令来验证这一点。

```
[sheridan]
# df /kits
Filesystem     512-blocks     Used Available Capacity Mounted on
extra#kits    13054928   4875562   8082544    38%    /kits
```

```
[molari]
# df /kits
Filesystem     512-blocks     Used Available Capacity Mounted on
extra#kits    13054928   4875562   8082544    38%    /kits
```

那么让我们卸载该文件系统，并使用“-o server_only”选项重新挂载它。请注意，我们只需在一个成员上发出umount(8)命令即可在集群范围内卸载该文件系统。

```
[sheridan]
# umount /kits
```

```
[sheridan]
# mount -o server_only extra#kits /kits
```

如果我们现在在每个成员上重新发出df命令，应该会看到/kits仅挂载在sheridan上。让我们检查一下：

```
[sheridan]
# df /kits
Filesystem     512-blocks     Used Available Capacity Mounted on
extra#kits    13054928   4875562   8082544    38%    /kits
```

```
[sheridan]
# rsh molari-ics0 df /kits
/kits: Permission denied
```

在最后一个示例中，我们决定使用rsh(1)访问另一个集群成员，这样就不需要登录了。我们只是偷懒……实际上是高效。让我们更进一步，看看当我们尝试在每个成员上操作/kits目录时会发生什么。
