get <code>PID</code> from <code>smbstatus</code>. Then use <code>c</code> to continue and try to cause the core dump using the client. The debugger should catch the fault and tell you where it occurred.

Sometimes it is necessary to build Samba binary files that have debugging symbols so as to make it possible to capture enough information from a crashed operation to permit the Samba Team to fix the problem.

Compile with <code>-g</code> to ensure you have symbols in place. Add the following line to the <code>smb.conf</code> file global section:

```
panic action = "/bin/sleep 90000"
```

to catch any panics. If <code>smbd</code> seems to be frozen, look for any sleep processes. If it is not, and appears to be spinning, find the <code>PID</code> of the spinning process and type:

```
root# gdb /usr/local/samba/sbin/smbd
```

then “attach ‘<code>pid</code>’” (of the spinning process), then type “<code>bt</code>” to get a backtrace to see where the <code>smbd</code> is in the call path.
