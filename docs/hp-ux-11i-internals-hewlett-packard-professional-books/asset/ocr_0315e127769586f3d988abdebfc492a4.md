Now it’s finally time to build the new image map! The compiler magic type tells us what type of mapping (\texttt{DEMAND\_MAGIC}, \texttt{EXEC\_MAGIC}, \texttt{SHMEM\_MAGIC}, \texttt{SHARE\_MAGIC}) to use as we locate the regions in quadrants. First, the null dereference and text regions are configured and mapped (if we are doing an \texttt{exec} self, then these regions will have been retained). Private regions for data (initialized, BSS, and heap) and user stack are added next. Additional regions are added as required for shared memory objects and memory-mapped files (both private and shared varieties).

The transformation is now complete, and we return from the \texttt{exec()} call wearing our new image and ready to run its code. Before we examine the final call in a process’s life cycle, \texttt{exit()}, let’s take a closer look at the way shared memory objects are mapped into the system’s virtual space and attached to a process’s logical view.

# Shared Memory Objects Revisited

When a program filename is passed to \texttt{exec()}, it must find the file (also called the front store) and open it. If the file is already open, there will be an existing \texttt{vnode} for the file in the kernel memory. If not, a new \texttt{vnode}, pseudo \texttt{vas}, a single \textit{region}, and a \textit{region} are created, as illustrated in Figure 9-7. In most cases, a \texttt{vas} structure is pointed to by a \textit{proc} structure (\texttt{p\_vas}), but in the case of an executable or memory-mapped file, it is a \textit{vnode} (\texttt{v\_vas}) that references it. In turn, the \textit{vas} (\texttt{va\_fp}) points back to the \textit{vnode} for which it was created.
