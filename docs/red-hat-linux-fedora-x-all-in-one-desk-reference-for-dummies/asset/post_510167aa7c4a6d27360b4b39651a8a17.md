
# Protecting Files and Directories 543

To set a new umask, type umask followed by the numerical value of the mask. Here is how you go about it:

- 1. Figure out permission settings you want for new files.

For example, if you want new files that can be read and written only by the owner and by nobody else, the permission setting looks like this:

```
rw-------
```

- 2. Convert the permissions into a numerical value by using the conversion method that assigns 4 to the first field, 2 to the second, and to the third.

Thus, for files that are readable and writable only by their owner, the permission setting is 600.

- 3. Subtract the desired permission setting from 666 to get the value of the mask.

For a permission setting of 600, the mask becomes 666 - 600 = 066.

- 4. Use the umask command to set the file-mask:

```
umask 066
```

A default umask of 022 is good for system security because it translates to files that have read and write permission for the owner and permissions for everyone else. The bottom line is that you don't want a default umask that results in files that are writable by the whole wide world.

## Checking for set user ID permission

Another permission setting can be a security hazard. This permission setting, called the user ID (or setuid for short), applies to executable files. When the setuid bit is enabled, the file executes under the user ID of its owner. In other words, an executable program is run by root if setuid is set, no matter who executes it. This means that the program can do a lot more (for example, read all files, create new files, and delete files) than what a normal user program can do. Another risk is that if a setuid program has some security hole, crackers can do a lot more damage through such programs than other vulnerabilities.

You can find setuid programs with a simple find command:

```
find / -type f -perm +4000 -print
```

## Using exec-shield

Buffer overflow is (if you'll pardon the expression) the root cause of many Linux security holes. When buffer overflow occurs, a cracker can overwrite data-areas of memory with instructions designed to execute nasty commands. But what if the kernel refuses to execute instructions from any data area? Poof! — no buffer overflows! That's exactly what the latest kernel does: It protects against the common buffer overflow of vulnerabilities by making parts of a program's memory (including the stack where temporary variables are stored) not executable. This feature of the Linux kernel is called exec-shield.

The best part about exec-shield is that you don't have to fix the applications that have the buffer-overflow problem. All you have to do is turn on the feature. To make the process even easier, Fedora Core enables exec-shield by default.

## Using SELinux 545

Some programs may have trouble working correctly when exec-shield is enabled. If you have to turn off exec-shield, log in as root and type the following command from a terminal window:

```
echo 0 > /proc/sys/kernel/exec-shield
```

That command sets the exec-shield kernel option to 0. The exec-shield option can take one of three values — 0, 1, and 2. Think of these values as three different levels of security. Table 2-2 summarizes the meaning of the three values of exec-shield. Fedora Core sets exec-shield to 1 by default.

| This Value of exec-shield | Has This Meaning |
| :--- | :--- |
| 0 | exec-shield is always disabled. |
| 1 | exec-shield is enabled for programs compiled with the newest version of gcc compiler. |
| 2 | exec-shield is always enabled. |

## Using SElinux

Fedora Core comes with Security Enhanced Linux (SELinux), which provides mandatory access control with a much finer-grained control than just user and group ownership of files and processes. The access control is determined by the SELlinux policy that specifies the access permissions for everything — files, devices, programs, and users — in the system. Fedora Core comes with a default security policy that works out of the box. If you install Fedora with SELinux (by typing sellinux at the boot: prompt), you don't have to do anything and users or processes can access various system resources, such as files and devices.

For the fine-grained access control, SELinux requires a security context — think of it as the security attributes of the file or directory. Adding contexts to the files is referred to as labeling the filesystem. The filesystem is already labeled when you install Fedora Core and enable SELinux. However, if you need to re-label a filesystem, you can do so with the setfiles or fixfiles command.

## 546 Using SELinux

You can easily check the context of a file, a user, or a process. For the details of /etc/passwd including its context, type ls -Z /etc/passwd. Here is a typical output:

The user you want to know the context of the file is in the first column, the context is in the second, and the type is in the third.

| USER | CONTEXT | TYPE |
| :--- | :--- | :--- |
| root | system_u:object_r:passwd_t:s0 | passwd_t |

The s in the owner's permission setting (r-s) tells you that the setuid permission is set. To know the context of a user, type id -Z. To see the context of a process, type ps -Z.

Adding contexts to the files is referred to as labeling the filesystem. The filesystem is already labeled when you install Fedora Core and enable SELinux. However, if you need to re-label a filesystem, you can do so with the setfiles or fixfiles command.
