
## Understanding Domain Name System (DNS)

BIND includes three major components:

- The named daemon — the name server — that responds to queries host names and IP addresses
- A resolver library that applications can use to resolve host names into IP addresses (and vice versa)
- Command-line DNS utility programs (DNS clients), such as dig (Domain Internet Groper) and host that users can use to query DNS

I describe these components of BIND in the next few sections. In later, explain how to configure the resolver and the name server.

## named — the BIND name server

The named daemon is the name server that responds to queries about host names and IP addresses. Based on the configuration files and the local DNS database, named either provides answers to queries or asks other servers to cache their responses. The named server also performs a function referred to as zone transfer, which involves copying data among the name servers in a domain.

The name server operates in one of three modes:

- Primary or Master: In this case, the name server keeps the master copy of the domain's data on disk. One primary server is for each domain or subdomain.
- Secondary or Slave: A secondary name server copies its domain's data from the primary server using a zone transfer operation. You can have one or more secondary name servers for a domain.
- Caching: A caching name server loads the addresses of a few authority for the root domain, and gets all domain data by caching to queries it has resolved by contacting other name servers. Primary and secondary servers also cache responses.

A name server can be authoritative or not, depending on what information it's providing. As the term implies, the response from an authoritative name server is supposed to be accurate. The primary and secondary name servers are authoritative for their own domains, but they are not authoritative for responses provided from cached information.

Caching name servers are never authoritative because all their responses come from cached information.

## Resolver library

Finding an IP address for a host name is referred to resolving the host name. Network-aware applications, such as a Web browser or an FTP client, use a resolver library to perform the conversion from the name to an IP address. Depending on the settings in the /etc/hosts.conf file, the resolver library consults the /etc/hosts file or makes a DNS query to resolve a host name to its IP address. The resolver library queries the name servers listed in the /etc/resolv.conf file.

You don't have to know much about the resolver unless you are writing network-aware applications. To run Internet services properly, all you have to know how to configure the resolver. In this chapter, I show you how to configure the other aspects of DNS.

## DNS utility programs

You can use the DNS utility programs — dig and host — to try out DNS from the shell prompt interactively. These utility programs are DNS clients. You can use them to query the DNS database and debug any name server you set up on your system. By default, these programs query the name server listed in your system's /etc/resolv.conf file.

You can dig, the Domain Internet Groper, to look up IP addresses for a domain name or vice versa. For example, to look up the IP address of ftp.redhat.com,

```
dig ftp.redhat.com
```

dig prints the results of the DNS query in great detail. Look in the part of the output labeled ANSWER SECTION: for the result. For example, here's what section looks like for this sample query:

```
:: ANSWER SECTION:
ftp.redhat.com.      300      A       209.132.176.30
ftp.redhat.com.      300      A       66.187.224.51
```

This output means that name ftp.redhat.com refers to both IP addresses — 209.132.176.30 and 66.187.224.51.

Reverse lookups (finding host names for IP addresses) are also easy with dig. For example, to find the host name corresponding to the IP address 209.132.176.30, type the following:

```
dig -x 209.132.176.30
```

Again, the answer appears in the ANSWER SECTION of the output, which, for this, looks like this:

```
:: ANSWER SECTION: 30.132.209.in-addr.arpa. 600 IN PTR ftp.redhot.com.
```

In this case, the host name corresponding to the IP address 209.132.176.30 happens to be ftp.redhot.com.

You can also query DNS using the host program. The host program outputs in a compact format. For example, here's a typical use of host to look up an IP address for a host name:

```
host www.google.com
```

This command generates the following one-liner:

```
www.google.com has address 142.250.190.46
```

By default, host prints the IP address and any MX record (these records list the names for the host). For a reverse lookup, use the -t ptr option, along with the IP address as an argument, like this:

```
host -t ptr 142.250.190.46
```

Here's output from host:

```
46.190.250.142.in-addr.arpa pointer google.com.
```

In this case, host prints the PTR record (from the DNS database) that shows the host name corresponding to the IP address. You can also try other types of records, such as CNAME (for canonical name), as follows:

```
host -t cname www.example.com
```

The response from host says www.example.com is an alias for example.com. This output indicates that the canonical name (or alias) for www.example.com is example.com.

## Configuring DNS

You configure DNS by using number of configuration files. The exact set of files depends on whether you're running a name server and, if so, the type of name server — caching or primary. Some configuration files are needed whether you run a name server or not.

## Configuring the resolver

You don't need a name server running your system to use the DNS clients (dig and host). You can use them to query your domain's name server. Typically, your ISP provides you with this information. You have to list the IP addresses of these name servers in the /etc/resolv.conf file — the resolver reads this file to determine how to resolve host names. The format of this file is:

```
domain domain.com
search domain.com
nameserver A.B.C
nameserver X.Y.Z
```

where A.B.C and X.Y.Z are the IP addresses (dot-separated numeric addresses, such as 192.168.0.1) of the primary and secondary name servers your ISP provides. The domain line lists the local domain name. The search line specifies the domains on which a host is searched (usually, you put your own domain in the search line). The domain listed on the search line is appended to any host name before the resolver tries to resolve it. For example, if you look for host, the resolver first tries host.domain.com; if that fails, the search line applies to any name you access. For example, if you're trying www.redhat.com, the resolver first tries www.redhat.com.domain.com and then www.redhat.com.

Another important configuration file is /etc/hosts.conf — this file tells the resolver what to do when attempting to resolve a host name. A typical /etc/hosts file contains the following line:

```
order hosts.bind
```

This command tells the resolver to consult the /etc/hosts file first, and if it fails, to query the name server listed in the /etc/resolv.conf file. The /etc/hosts file lists any host names and their IP addresses. Here's a typical line from the /etc/hosts file:

```
127.0.0.1  localhost localhost.local
```

This line says that the IP address 127.0.0.1 is assigned to the host names localhost, localhost.local, and localhost.

In the latest version of the Linux kernel that uses GNU C Library version 2 (glibc 2 or later), the name service (NSS) file, /etc/nsswitch.conf controls how services such as the resolver library, NIS, and local files such as /etc/hosts and /etc/shadow interact. For example, the hosts entry in the /etc/nsswitch.conf file specifies that the resolver library first tries the /etc/hosts file, then NIS, and finally DNS:

- hosts files nisswitch dns

To find more about the /etc/nsswitch.conf file and what it does, type info libc Name Switch in a terminal window.

## Configuring a caching name server

A simple, useful name server that finds answers to hostname queries using other name servers and remembers the answer (by saving it in a cache) the next time you use it. This caching name server can shorten the time it takes to access hosts you have accessed recently; the answer is always in the cache.

When you install the DNS Name Server package group during Fedora Core installation, the configuration files for a caching name server are also installed. This means you can start running the caching name server without much work on your part. This section describes the configuration files and what you have to do to start the name server.

## /etc/named.conf file

The first configuration file you need is /etc/named.conf. The named server reads this configuration file when it starts. You already have this file if you installed the DNS Name Server during Fedora Core installation. Here's what the default /etc/named.conf contains:

```
// generated by named-bootconf.pl
options {
    directory "var/named";
    /*
     * If there is a firewall between you and nameservers
     * talk to, you might need to uncomment the query-source
    */
}
```
