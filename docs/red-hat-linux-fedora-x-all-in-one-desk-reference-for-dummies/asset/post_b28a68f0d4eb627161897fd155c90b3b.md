## 538 Securing Passwords

Another advantage of MD5 over old-style password encryption is that the older passwords were limited to a maximum of eight characters; new passwords (encrypted with MD5) can be much longer. Longer passwords are harder to guess, even if the /etc/shadow file falls into the wrong hands.

You can tell that MD5 encryption is in effect for the /etc/shadow file. The encrypted passwords are longer and they all sport the $1 prefix, in the second field of the following sample entry:

```
root:$AAANi/ynEShYbUp9qc8foibD5O:1107:0:9999:-1:134540356
```

An in-program module called a pluggable authentication module (PAM) performs the actual MDS encryption. Fedora Core PAMs provide a flexible method for authenticating users. By setting the PAMs configuration files, you can change your authentication method on the file, without having to modify vital programs (such as login and passwd) that verify a user's identity.

Fedora Core uses PAM capabilities extensively. The PAMs reside in many different modules (about that moreover); their configuration files are in the /etc/pam.d directory of your system. You can check the contents of this directory by typing the following command:

```
/etc/pam.d
```

Each configuration file in this directory specifies how users are authenticated for a specific utility. For example, you find a file for login, passwd, and so. Here is what I see when I type cat /etc/pam.d/passwd file on my system:

```
#PAM-1.0
auth required pam_stack.so service=system-auth
account required pam_stack.so service=system-auth
password required pam_stack.so service=system-auth
```

These lines indicate that authentication, account management, and password checking are all done by using the pam_module (/lib/security/pam_stack.so) with the argument service=system-auth. Essentially, the pam_module refers to another configuration file in the /etc/ directory. In this case, the configuration file is /etc/pam.d/system-auth file on my Fedora PC:

```
#PAM-1.0
# This file is auto-generated.
# User changes will be destroyed the next auth config is run.
auth required /lib/security/$ISA/pam_env.so
```

```
auth sufficient /lib/security/$ISA/pam_unix.so wellknown nullock
auth required /lib/security/$ISA/pam_deny.so
account required /lib/security/$ISA/pam_unix.so
password required /lib/security/$ISA/pam_cracklib.so retry=3 type=
password sufficient /lib/security/$ISA/pam_unix.so nullock authtok md5
password required /lib/security/$ISA/pam_deny.so
session required /lib/security/$ISA/pam_limits.so
session required /lib/security/$ISA/pam_unix.so
```

Here's a brief explanation of some of these lines in the configuration file:

- The first auth line loads the PAM module /lib/security/pam_env.so. This module can set or unset environment variables (the ISA in /lib/security/$ISA/pam_env.so refers to an environment variable's typically not defined, so the effective pathname for the PAM module is /lib/security/pam_env.so).
- The auth line specifies an authentication module that checks the user's identity using the PAM module /lib/security/pam_unix.so with the argument wellknown nullock. The options in the argument string have the following:
    - wellknown: Returns the value whether the module is used to set new credentials or authenticate an existing username.
    - nullock: Allows a blank password.
- The third auth line in the /etc/pam.d/system-auth file denies access to the system if the pam_unix.so module's authentication is unsuccessful.
- The account line in the /etc/pam.d/system-auth file checks to make that the user's account has not expired, the user is allowed to log in at any time of day, and so.
- The next two password lines in the /etc/pam.d/system-auth file specify how passwords are set:
    - the first password line uses the /lib/security/pam_cracklib.so module to crack the new password (that's what the cracklib in the module's name indicates).
    - The retry=3 part indicates that the user can try to enter a new password three times at most. The second password line indicates that the MD5 encryption is used to store the password in the /etc/shadow file.

## Protecting Files and Directories

One important aspect of securing the host is to protect system files and the directories that contain these files. You can protect the files through the ownership and the permission settings that control who can read, write, or execute the file.

The default Fedora Core security is controlled through the following settings for each file or directory:

- User ownership
- Group ownership
- Read, write, execute permissions for owner
- Read, write, execute permissions for group
- Read, write, execute permissions for others (everyone else)

## Viewing ownership and permissions

You can see these settings for a file when you look at the detailed list with ls -l command. For example, type the following command to see the detailed listing of /etc/passwd:

```
ls -l /etc/passwd
```

The resulting listing looks like this:

```
-rw-r--r--  1 root root  00 Aug 24 10:56 /etc/passwd
```

## Protecting Files and Directories

The first set of characters describes the permissions for user, group, and others. The third and fourth fields show the user and group that own the file. In this case, both user and group names are the same: root.

## Changing ownership

You can set the user and group ownership with the chown command. For example, if the file /etc/passwd is owned by the user root and the group disk, then type the following command as root to set this ownership:

```
chown root /etc/passwd
```

To change the group ownership alone, use chgrp command. For example, here's how you can change the group ownership of a file to accounting:

```
chgrp accounting /etc/passwd
```

## Changing permissions

Use the chmod command to set the permission settings. To use chmod effectively, you have to specify the permission to concatenate letters from each of the following tables, in the order shown (Who/Action/Permission) in Table 2-1:

| Table 2-1 | Action | Permission |
| :--- | :--- | :--- |
| u user | + | r read |
| g group | - | w write |
| others | = | x execute |
| a all | s | set user ID |

You can read and access all files in a directory, chmod a+rw *. On the other hand, to permit everyone to execute a specific file, type chmod +x filename.

Another way to specify a permission setting is to use a three-digit sequence of numbers. In a detailed listing, the read, write, execute permission settings for the user, group, and others appear as the sequence:

```
rwx rwx rwx
```

## 542 Protecting Files and Directories

With dashes in place of letters for disallowed operations, think rwxrwxrwx as three occurrences of the string rwx. Assign the values r=4, w=2, and x=1. To get the value of the sequence rwx, simply add the values of r, w, and x. Thus rwx = 7. Using this formula, you can assign a three-digit value to any permission setting. For example, if you can read and write the file but everyone else can only read the file, the permission is rw-r---- (that is how it appears in the listing), and the value is 644. Thus, if you want all files in a directory to be readable by everyone but writable only by you, use the following command:

```
chmod 644 *
```

## Setting default permission

What permission does a file get when you (or a program) create a new file? The answer is in what is known as the user file-creation mask that you can see and set using the umask command.

**Type umask**, and it prints out a number showing the current file-creation mask. The default setting is for the root user and other normal users. The root user mask is set to 022, whereas the mask for normal users is 002. To see the effect of this file-creation mask and to interpret the meaning of the mask, follow these steps:

1. Log in as root and type the following command:

```
touch junkfile
```

This command creates a file named `junkfile` with nothing in it.

2. Type -l to see the file's permissions.

You see a line similar to the following:

```
-rw-r--r--  1 root root  00 Aug 24 10:56 junkfile
```

Interpret the numerical value of the setting by converting each three-letter permission in the first field (excluding the very first) into a number from 0 to 7. For each letter the second letter is 4, and the third is 1. For example, rw- translates to 4+2+0 (because the third letter is missing) or 6. Similarly, r-- is 4+0+0=4. The permission string `-rw-r--r--` becomes 644.

3. Subtract the numerical setting from 666 and what you get is the umask setting.

In this case, 666-644 results in an umask of 022.

Thus an umask of 022 results in a default permission setting of 666-022=644. When you rewrite 644 in terms of a permission string, it becomes `rw-r--r--`.
