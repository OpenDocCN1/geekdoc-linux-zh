
## 5.9 信号、终止与等待

下面是之前 `waitpid` 示例中的 `wait_and_display` 和 `display_status` 函数，已改写为适用于 `waitid` 的版本：

```c
static bool wait_and_display(void)
{
    siginfo_t info;

    ec_negl( waitid(P_ALL, 0, &info, WEXITED) )
        display_status(&info);
        return true;

EC_CLEANUP_BGN
    return false;
EC_CLEANUP_END
}

void display_status(siginfo_t *infop)
{
    printf("Process %ld terminated:\n", (long)infop->si_pid);
    printf("\ttcode = %s\n",
           get_macrostr("sigchld-code", infop->si_code, NULL));
    if (infop->si_code == CLD_EXITED)
        printf("\ttext value = %d\n", infop->si_status);
    else
        printf("\tsignal = %s\n",
               get_macrostr("signal", infop->si_status, NULL));
}
```

输出结果：

```text
Process 9580 terminated:
	tcode = CLD_EXITED
	exit value = 123
Process 9581 terminated:
	tcode = CLD_DUMPED
	signal = SIGGPPE
Process 9582 terminated:
	tcode = CLD_KILLED
	signal = SIGHUP
```

使用 `waitid` 时，可以通过类似以下的算法避免意外获取到错误子进程的报告：

1. 执行带有 `P_ALL` 和 `WNOWAIT` 选项的 `waitid`。
2. 如果返回的进程 ID 不是程序这部分关心的，则返回步骤 1。
3. 如果该进程 ID 是被关心的，则为该进程 ID 重新执行 `waitid` 而不带 `WNOWAIT` 选项（或者直接调用 `waitpid`），以清除其状态，使其不再处于可等待状态。
4. 如果还有任何其他未被等待的子进程需要等待，则返回步骤 1。

使用 `waitid` 的唯一问题是，在 SUS1 之前的系统上不可用，截至本文写作时，这些系统包括 Linux、FreeBSD 和 Darwin。因此，必须使用之前在 `waitpid` 讨论中描述的更繁琐的方法。

`wait`、`waitpid` 和 `waitid` 的行为还受到父进程对 `SIGCHLD` 信号处理方式的进一步影响，详见下一节。

关于信号的大多数细节都在第 9 章中，但在这里讨论 `SIGCHLD` 是合理的。第 1.1.3 节中关于信号的快速入门介绍应该足以理解本节的内容；如果不够，可以跳至阅读完第 9 章后再看本节。

如上一节所述，父进程可以使用其中一个 `wait` 变体函数来获取状态发生变化的子进程（终止、停止或继续）的状态。如果一个子进程从未被等待过，它将保持可等待状态（即僵尸进程），直到父进程终止。

我之前没有提到，但状态发生变化的子进程通常会向其父进程发送一个 `SIGCHLD` 信号。除非父进程做了其他安排，否则该信号的默认操作是被忽略，这就是为什么在之前的例子中处理它并不重要。

父进程可以捕获该信号，以便在子进程状态变化时得到通知。不幸的是，父进程无法获知*哪个*子进程导致了该信号。 [12] 如果它使用其中一个 `wait` 变体函数来获取进程 ID，那么如上一节所述，存在获取错误进程状态的危险，因为在信号发送和调用 `wait` 变体函数之间，其他某些进程可能已经改变了状态。安全的做法是使用 `waitid`（如上一节所述）或者使用 `waitpid` 逐个检查所有可能的子进程。

> 12. 除非使用了实时信号扩展的高级特性，但该扩展并非普遍可用。

与其等待，父进程可以通过调用带有 `SA_NOCLDWAIT` 标志的 `sigaction` 来阻止未被等待的子进程变成僵尸进程（变成*可等待状态*）。这样子进程终止时其状态将被直接丢弃，父进程因此无法获取该状态（并且推定也不关心）。如果父进程仍然执行 `wait` 或 `waitpid`，无论其参数如何（甚至包括 `WNOHANG`），它将阻塞直到*所有*子进程终止，然后返回 -1，并将 errno 设置为 `ECHILD`。如果父进程捕获 `SIGCHLD` 信号，它仍可能得到通知。

如果父进程*显式*地设置忽略 `SIGCHLD` 信号（例如，调用 `sigaction` 并设置操作为 `SIG_IGN`），而不是接受默认操作，这与使用 `SA_NOCLDWAIT` 标志的效果相同 [X/Open]。但鉴于并非所有系统都支持此行为，同时设置 `SA_NOCLDWAIT` 标志是个好主意，因为它被更广泛地支持。

### 5.10 实现 Shell（版本 3）

使用第 5.8 节中 `waitpid` 版本的 `display_status` 函数，我们可以改进第 5.6 节中的 `execute2`：

```c
static void execute3(int argc, char *argv[])
{
	pid_t pid;
	int status;

	switch (pid = fork()) {
	case -1: /* parent (error) */
		EC_FAIL
	case 0: /* child */
		execvp(argv[0], argv);
		EC_FAIL
	default: /* parent */
		ec_neg1( waitpid(pid, &status, 0) )
		display_status(pid, status);
	}
	return;

	EC_CLEANUP_BGN
	EC_FLUSH("execute3*")
	if (pid == 0)
		_exit(EXIT_FAILURE);
	EC_CLEANUP_END
}
```

### 5.11 获取用户和组 ID

有一系列系统调用用于获取真实和有效的用户及组 ID（这些概念在第 1.1.5 节中有解释）：

```c
getuid—获取真实用户 ID

#include <unistd.h>
uid_t getuid(void);
/* 返回用户 ID（无错误返回） */
```

```c
geteuid—获取有效用户 ID

#include <unistd.h>
uid_t geteuid(void);
/* 返回用户 ID（无错误返回） */
```

```c
getgid—获取真实组 ID

#include <unistd.h>
gid_t getgid(void);
/* 返回组 ID（无错误返回） */
```

```c
getegid—获取有效组 ID

#include <unistd.h>
gid_t getegid(void);
/* 返回组 ID（无错误返回） */
```

用户或组 ID 只是一个数字。如果你想要名称，你必须调用 `getpwuid` 或 `getgrgid`，这些在第 3.5.2 节中已有描述。下面是一个显示真实和有效用户及组 ID 的示例程序：

```c
int main(void)
{
	uid_t uid;
	gid_t gid;
	struct passwd *pwd;
	struct group *grp;

	uid = getuid();
	if ( (pwd = getpwuid(uid)) != NULL )
		printf("Real user = %ld (%s)\n", (long)uid, pwd->pw_name);

	uid = geteuid();
	if ( (pwd = getpwuid(uid)) != NULL )
		printf("Effective user = %ld (%s)\n", (long)uid, pwd->pw_name);

	gid = getgid();
	if ( (grp = getgrgid(gid)) != NULL )
		printf("Real group = %ld (%s)\n", (long)gid, grp->gr_name);

	gid = getegid();
	if ( (grp = getgrgid(gid)) != NULL )
		printf("Effective group = %ld (%s)\n", (long)gid, grp->gr_name);

	exit(EXIT_SUCCESS);

CLEANUP_BEG
	exit(EXIT_FAILURE);
CLEANUP_END
}
```

为了使输出更有意思，我更改了程序文件（`uidgrp`）的用户和组所有者，然后为用户和组设置了 set-ID-on-execution 位：


### 5.12 设置用户和组 ID

关于真实和有效用户及组 ID 如何改变的规则很复杂，并且取决于进程是否以超级用户身份运行。在解释这些规则之前，我需要指出，除了其当前的真实和有效用户及组 ID 外，内核还为每个进程保留了一条记录，记载了上一次 *exec* 设置的*原始*有效用户和组 ID。这些被称为*保存的 set-user-ID* 和*保存的 set-group-ID*。

下面是设置用户 ID 的规则；组 ID 的规则类似：

1. 除了通过 *exec*（它可以更改保存的 ID）之外，普通（非超级用户）进程永远不能显式更改真实用户 ID 或保存的 ID。
2. 普通进程可以将有效 ID 更改为真实 ID 或保存的 ID。
3. 超级用户进程可以将真实和有效用户 ID 更改为任何用户 ID 值。
4. 当超级用户进程更改真实用户 ID 时，保存的 ID 也会更改为该值。

超级用户的规则并不太有趣——为所欲为。普通用户的两条规则本质上意味着：如果 *exec* 导致真实和有效用户 ID（或组 ID）不同，进程可以在它们之间来回切换。

这是一个来回切换有用的场景：想象一个名为 *putfile* 的工具，它在网络上的计算机之间传输文件。该工具需要访问一个仅管理用户（称之为 *pfadm*）可以访问的日志文件。程序文件的所有者是 *pfadm*，并设置了 set-user-ID 位。它开始运行时可以访问日志文件，因为其有效用户 ID 是 *pfadm*。然后，为了写入真实用户的文件，它将有效用户 ID 设置为真实用户 ID，以便真实用户的权限控制访问。完成写入后，它再次将有效用户 ID 设置回 *pfadm* 以再次访问日志文件。（如果原始的*有效*用户 ID 没有被保存，它就无法回去。）请注意，虽然对于该工具而言 *pfadm* 看起来很特殊，但对于内核来说，它只是一个普通用户——不是超级用户。

现在是这些调用本身。对于普通用户进程，唯一有用的就是 *seteuid* 和 *setegid*。
