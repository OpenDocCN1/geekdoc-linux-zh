```
ec_rv( pthread_mutex_lock(&uenv_mtx) )
while ( event_head == NULL )
ec_rv( pthread_cond_wait( uenv_cond_event, &uenv_mtx) )
e = event_head;
event_head = event_head->ue_next;
ec_rv( pthread_mutex_unlock (&uenv_mtx) )
return e;
EC_CLEANUP_BGN
(void)pthread_mutex_unlock (&uenv_mtx);
return NULL;
EC_CLEANUP_END
}
```

When the predicate is true (event present on queue), it removes the event from the queue and returns a pointer to it. It’s the responsibility of the caller to free the memory with a call to `uenv_free`, as I mentioned earlier.

Except for some additional bookkeeping details and the rest of the registration functions, that’s the whole system. It solves the blocking problem!

Because it’s so reliant on threads, this approach is only as good as the underlying thread implementation. Threads have to be fast, lightweight, and plentiful, and they have to follow the POSIX standard rigorously. Otherwise, there will be too much overhead, valuable system resources will be consumed, and there will be too many subtle bugs in the application that, because of all the multithreading, will be very hard to find.

If you’re interested, try to rewrite the `uenv` package using processes instead of threads. You’ll find it difficult to write and extremely difficult to make efficient. But the effort should help you appreciate why threads are so important.
