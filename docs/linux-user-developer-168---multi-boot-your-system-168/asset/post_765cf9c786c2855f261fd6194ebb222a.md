
let's do something more interesting: let's find out how many binaries in the `/usr/bin` directory have the NX bit cleared. Thanks to the `execkstack` utility and its `-q` flag, you can query an ELF binary for the presence of the NX bit.

```bash
$ find /usr/bin -exec execkstack -q {} ";" 2>/dev/null | egrep --color=auto 'X'
X /usr/bin/grub-mklayout
X /usr/bin/grub-mkrelpath
X /usr/bin/grub-mkimage
...
```

## ASLR and PIE

Address Space Layout Randomization (ASLR) is a protection mechanism introduced in Linux and other operating systems that randomises the process memory space so that it is extremely difficult to find the address of functions or gadgets that an attacker could use in order to exploit a binary. Shared libraries are compiled with the `-fPIE` flag, allowing them to make use of the ASLR protection automatically. However, binary `.text` segments are not compiled with this protection unless they are built as Position Independent Executable (PIE). Grab your favourite text editor once again and write this code down:

```c
#include <stdio.h>
void *getEIP () {
	return __builtin_return_address(0)-0x5;
}
int main(int argc, char** argv){
	printf("EIP located at: %p\n",getEIP());
	return 0;
}
```

Compile the code and then start to execute it a minimum of ten times (or more). You will get the same exact memory address for EIP each time.

```bash
$ gcc -m32 aslr.c -o aslr
$ ./aslr
EIP located at: 0x80483f8
$ ./aslr
EIP located at: 0x80483f8
```

Now, let's give it another try but this time setting the PIE protection on the `.text` segment.

```bash
$ gcc -m32 -fPIE -pie aslr.c -o aslr
$ ./aslr
EIP located at: 0xff770d5c
$ ./aslr
EIP located at: 0xff77635c
```

Of course, if you do this with an ELF64 binary, the entropy will be greater and therefore the ASLR will become more reliable. There are plenty of papers exposing a way to bypass ASLR on 32 bit architectures using brute-force.

## Stack Canaries

One well-known method to inject alien code into an executable is by means of corrupting its stack. Open your favourite ASCII editor and write this code down:

```c
#include <stdio.h>
#include <string.h>
void vuln(char *);
int main (int argc, char **argv){
	printf("Arg is: %s\n", *(argv+1));
	vuln(*(argv+1));
}

void vuln(char *arg){
	char buffer[10];
	strcpy(buffer, arg);
}
```

This is a classic buffer-overflow vulnerable code. Compile it the usual way and run it passing as many bytes as you need until you overflow the buffer:

```bash
$ gcc -m32 vuln.c -o vuln
$ ./vuln AAAAAAAAAAAAAAAAAAAAAAA
Arg is: AAAAAAAAAAAAAAAA
Segmentation fault
```

Now, execute it inside a `gdb` session until you get the `0x41414141` value for the EIP register. To achieve this, just increase the total number of "As" passed to the vulnerable program at each execution until you reach the desired value:

```bash
$ gdb ./vuln
(gdb) r AAAAAAAAAAAAAAAAAAAAAAA
Program received signal SIGSEGV, Segmentation fault.
0x41414141 in ?? ()
```

It is obvious that you can control the return address by corrupting the stack. If you want to overwrite the EIP register with, say, `0x54544432`, you can do it easily by altering the last 4 bytes passed as an argument like this:

```bash
(gdb) r "$(perl -e 'print "\x41" x 20 . "\x32\x44\x54\x54"')"
Program received signal SIGSEGV, Segmentation fault.
0x54544432 in ?? ()
```

The stack has been corrupted, that is undeniable. Now, compile the previous code with the stack guard protector to detect the corruption. The GNU C compiler offers this feature:

```bash
$ gcc -m32 -fstack-protector-all vuln.c -o vuln
```

### Compile new software

- Protections and performance

Some of these protections can affect the program's throughput. For example, `relro`/`full relro` means that the loader will resolve every library function's binary function to load immediately. To do this, some loading is performed before the binary is responsive. Take this into account and always run performance tests.

Try to overflow the buffer now as you did before:

```bash
$ ./vuln `perl -e 'print "A"x18'`

terminated
```

### Full RELRO

Whenever running a new binary that makes use of shared libraries, the addresses of these libraries are resolved at execution time when a first call is made to any one of these libraries; this is called Lazy Binding. Because some addresses have to be figured out later on in the life of a binary loaded in memory, some ELF segments must be writable. This can lead to a well-known attack that overwrites the Global Offset Table (GOT) so that instead of making a call to, say, `printf`, once the attacker has been able to overwrite the address for `printf`, the program will end up calling some malicious injected code.

```c
#include <stdio.h>
int main(int argc, char **argv){
    printf("Hello there!\n");
    return 0;
}
```

Save it and compile it this way:

```bash
$ gcc -m32 -no-builtin-printf relro.c -o relro
```

Disassemble the binary by running the `objdump` utility:

```bash
$ objdump -d relro > relro.S
```

Open the resulting disassembled file and look for the main function. Instead of calling `printf`'s address directly, there is a call to a symbol named `printf@plt`:

```asm
00048348 <main>:
...
80483f5: e8 06 ff ff ff    call  8048306 <printf@plt>
80483fa: 68 00 00 00 00    mov $0x0, %eax
```

Go to that offset, i.e. `0048300`. You can clearly see that there is a jump into the GOT. The push `$0x0` is going to set the actual address for `printf` in the first GOT entry available for shared symbols, i.e. `GOT[3]`:

![](img/628186dda7facdc011bf39c938de3975_33_0.png)

```asm
00048300 <printf@plt>:
8048300: ff 25 98 94 04 08  jmp    *0x0894998
8048306: 68 00 00 00 00    push $0x0
804830b: e9 e0 ff ff ff    jmp    80482f0 <.init+0x34>
```

Run the executable inside a `gdb` session to analyze the GOT. Because the `_got.plt` table is a section inside this ELF binary, you can ask `gdb` for its exact address:

```bash
$ gdb ./relro
(gdb) info sections _got.plt
0x089495c >0x0894964  0x0000068 _got.plt
ALLOC LOAD DATA HAS CONTENTS
```

Set a breakpoint right after the call to the `printf@plt` function and run the program:

```bash
(gdb) b *0x00483fa
Breakpoint 1 at 0x00483fa
(gdb) r
Hello there!
Breakpoint 1, 0x00483fa in main ()
```

Let's find out where the `printf` function is located:

```bash
(gdb) p system
$3 = <text variable, no debug info> 0x7f7e82c80
```

So `GOT[3]` must have the address `0x7f7e82c80`, which is the address for `printf`. To make sure this is so, dump the first 4 bytes for the `_got.plt` table:

```bash
(gdb) x/4w 0x089495c
0x089495c <_GLOBAL_OFFSET_TABLE_>   0x0894958
0x7fff0598      0x7fff3598
```

Because this is a writable address in the ELF binary, you can put whatever address you want in `GOT[3]`. You can find out which address equals to `GOT[3]` by doing pointer arithmetic:

```bash
(gdb) x/4w 0x089495c+12
0x0894968 <printf@plt>          0x7f7e82c80
```

So `GOT[3]` is located at `0x0894968`! Let's toy with the GOT, your goal will be to execute the system function instead of the "Hello world!" message. To do this, first find out where the address of `system` is:

```bash
(gdb) p system
$8 = <text variable, no debug info> 0x7f74c90
```

Set a breakpoint before calling the `printf@plt` symbol:

```bash
(gdb) b *0x00483f5
Breakpoint 2 at 0x00483f5
```

Run the program from the beginning until it breaks at 0x80483f5. Then, overwrite the GOT entry at offset address 0x804968 (correcting OCR typo 0x8049698) with the address for the system function:

```bash
(gdb) set *0x804968 = system
(gdb) x/wx 0x804968
0x804968 <printf@plt+...>    0x7f74c90
```

Continue the execution using the “c” command in gdb:

```bash
(gdb) c
Continuing.
sh: Hello: command not found
```

You have successfully overwritten the address in the GOT entry for the function printf with system. But because system expects the command to execute from the stack, and the stack has the string “Hello world!\n”, system tries to execute “Hello” and fails! Anyway, you have altered the GOT table. To prevent this, use Full RELRO:

```bash
$ gcc -m32 -fno-builtin-printf -Wl,-z,relro,-z,now relro.c -o relro
```

Now that all the symbols are resolved before returning control to the executable program by the linker, there is no need to have writable sections loaded in memory. To check this, use the readelf command like this:

```bash
$ readelf -S ./relro | grep "got.plt"
```

## Auditing for unhardened binaries

On modern GNU/Linux distros, most binaries are pre-compiled with these protections enabled. To check, you can use either the readelf tool or the checksec script.

```bash
$ wget http://www.trapkit.de/tools/checksec.sh
```

Using checksec, let’s test the previous code protections after compiling it using Full RELRO:

```bash
$ ./checksec.sh -file relro
Full RELRO    No canary found    NX enabled
No PIE
```

Checksec is reporting to you that this binary has been hardened with Full RELRO and the NX bit. And yet, its .text segment is not protected by ASLR and it has no stack corruption protection.

```bash
$ gcc -m32 -fstack-protector-all -fPIE -pie -fno-builtin-printf -Wl,-z,relro,-z,now relro.c -o relro
$ ./checksec.sh -file relro
Full RELRO    Canary found    NX enabled
PIE enabled
```

Checksec also allows you to check every process that is running on your system and obtain its protections by using the --proc-all flag. To get a list of binaries that may be vulnerable to stack corruption or GOT overwriting, you can run the following:

```bash
# ./checksec.sh --proc-all | egrep 'No RELRO|No canary'
init          1 No RELRO    No canary found    NX enabled No PIE
rpc.statd 2426 No RELRO No canary found NX enabled No PIE
rpc.idmapd 2440 No RELRO No canary found NX enabled No PIE
...
```

However, it’s important to note that if you compile legacy code in a newer GNU/Linux distro, chances are that it will be built without protections.

> Checksec allows you to check every process that is running on your system and obtain its protections

```bash
$ wget http://disbaux.es/wp-content/uploads/2012/10/xmgr-4.1.2.tar.bz2
```

Decompress the file and start the building process as usual:

```bash
$ tar xvjf xmgr-4.1.2.tar.bz2
$ cd xmgr-4.1.2/
$ ./configure && make
```

Use the checksec script to make sure the only enabled protection is NX:

```bash
$ checksec.sh -file src/xmgr
No RELRO    No canary found    NX enabled    No PIE
```

Harden it by altering its Makefile so that it has the proper flags set. Modern GNU/Linux distros include an environment variable that turns on these flags automatically. Edit the xmgr-4.1.2/Make.conf and set these flags to the CFLAGS0 variable:

```makefile
CFLAGS0 = -fstack-protector-all -fPIE -pie -Wl,-z,relro,-z,now
```

Add the -fPIC flag to the cephos library too:

```makefile
# vi cephos/Makefile
...
CFLAGS= $(CFLAGS0) -fPIC -I$TOP -I.
```

Now recompile the binary and check its protections again:

```bash
$ make clean
$ make
$ checksec.sh -file src/xmgr
Full RELRO    Canary found    NX enabled    PIE enabled.
```
