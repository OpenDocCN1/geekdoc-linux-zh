## 4.7.1. Generating Keys

The dnskeygen program is used to generate keys.
A secure zone must contain one or more zone keys. The zone keys will sign all records in the zone, as well as the zone keys must have the same name as the zone, a name type ZONE, and be used for authentication. It is recommended that zone keys use a cryptographic algorithm designed as "mandatory to implement" by the IETF; currently these are RSA1 (which is not supported in BIND 9.2) and DSA.

The following command will generate a 768 bit DSA key for the child.example zone:

```
dnsseckey -a DSA -b 768 -n ZONE.example.
```

Two output files will be produced: Rchild.example,+00312345.key and Rchild.example,+00312345.private (where 12345 is an example of a key tag). The key file names the key name (child.example.), algorithm (3 is DSA, 1 is RSA, etc.), and the key tag (12345 in this case). The private key (in the .private file) is used to generate signatures, and the public key (in the .key file) is used for signature verification.

To generate another key with the same properties (but with a different tag), repeat the command.

The public keys should be inserted into the zone file with INCLUDE statements, including the .key files.

## 4.7.2. Creating a Keyset

The dnsmakekeysyset program is used to create a keyset from one or more keys.

Once the keys have been generated, a keyset must be built for transmission to the administrator of the parent zone, so that the parent zone can sign the keys with its own zone key and correctly indicate the security status of this zone. Building a keyset, the list of keys to be included and the TTL of the set must be specified, and the desired signature validity period of the parent's signature may also be specified.

The list of keys to be inserted into the key set may also included non-zone keys present at the top of the zone. dnssec-makekeyset may also be used at other names in the zone.

The following command generates a key set containing the above key and another key similarly, generated with a TTL of 3600 and a signature validity period of 10 days starting from now.
dnssec-makekeyset -t 3600 -e +864000 Kchild.example.+003+12345 Kchild.example.+003+23456

One output file is produced: keyset-child.example.. This file should be transmitted to the parent to be signed. It includes the keys, as well as signatures over the key set generated by the zone keys themselves, which are used to prove ownership of the private keys and ensure the desired validity period.

## 4.7.3. Signing the Child's Keyset

The dnssec-signkey program is used to sign one child's keyset.
If the child.example has any delegations which are secure, for example, grand.child.example, the child administrator should receive keyset files for each secure subzone. These keys must be signed by this zone keys.

The following command signs the child's keyset with the zone keys:
dnssec-signkey keyset-grand.child.example. Kchild.example.+003+12345 Kchild.example.+003+23456

One output file is produced: signedkey-grand.child.example.. This file should be both transmitted back to the child and retained. It includes all keys (the child's keys) from the keyset file and signatures generated by this zone keys.

## 4.7.4. Signing the Zone

The dnssec-signzone program is used to sign a zone.
Any signedkey files corresponding to secure subzones will be present, as well as a signedfile for this zone generated by the parent (if there is one). The zone signer will generate NXT and SIG records for the zone, as well incorporate the zone key signature from the parent and indicate the security status at all delegation points.

The following command signs the zone, assuming it is in a file called zone.child.example. By default, all zone keys which have an available private key are used to generate signatures.

```
dnssec-signzone -o child.example zone.child.example
```

One output file is produced: `zone.child.example.signed`. This file should be referenced by `named.conf` as the input file for the zone.

## 4.7.5. Configuring Servers

Unlike BIND 8, data is not verified on load in BIND 9, so zone keys for authoritative zones do not need to be specified in the configuration file.

The public key for any security root must be present in the configuration file's `trusted-keys` statement, as described later in this document.

## 4.8. IPv6 Support in BIND 9

BIND 9 fully supports all defined forms of IPv6 name to address and address to name lookups. It will also use IPv6 addresses to make queries on IPv6 capable system.

For forward lookups, BIND 9 supports both A and AAAA records. The use of AAAA records is deprecated, but is still useful for hosts to have both AAAA and A6 records to maintain backward compatibility with implementations where stub resolvers support only AAAA lookups, because following A6 chains is harder than doing AAAA lookups.

For IPv6 reverse lookups, BIND 9 supports the new "bitstring" format used in the `ipv6.arpa` domain, as well as the older, "nibble" format used in the `ipv6` domain. BIND 9 includes a lightweight resolver which new applications may choose to avoid the complexities of A6 chain following bitstring labels, see Chapter 5.

For an overview of format and structure of IPv6 addresses, see Section 3.

## 4.8.1. Address Lookups Using AAAA Records

The AAAA record is parallel to the IPv4 record. It specifies the entire address in a single record.

```
$ORIGIN example.com.
host AAAA fffe:8050:201:80::
```
While their use are deprecated, they are useful to support older IPv6 applications. They should not be added where they are not necessary.

## 4.8.2. Address Lookups Using A6 Records

The A6 record is more flexible than the AAAA record, and is therefore complicated. The A6 record can be used to form a chain of A6 records, specifying part of the IPv6 address. It can also be used to specify the entire record as well. For example, this record supplies the same data as the AAAA record in the previous example:

```
$ORIGIN example.com.
host A6 0:3fe:8050:201:860::1
```

## 4.8.2.1. A6 Chains

A6 records are designed to allow network numbering. This works when an A6 record only specifies the part of the address owner controls. For example, a host may be named "company." has two ISPs which provide IPv6 address space. These two ISPs fully specify the IPv6 prefix.

In the company's address space:

```
$ORIGIN example.com.
IN A6 64 0:0:0:0:42::1.example1.net.
host A6 64 0:0:0:0:42::1.example2.net.
```

ISP1 will:

```
$ORIGIN example1.net.
company A6 0:3fe:8050:201:860::
```

ISP2 will:

```
$ORIGIN example2.net.
company A6 0 1234:5678:90ab:ffff::
```

When host.example.com is looked up, the resolver (in the resolver daemon or caching server) will find two A6 records, and will use the name to find the remainder of the data.

## 4.8.2.2. A6 Records for DNS Servers

When an A6 record specifies the address of a name server, it should use the full address rather than specifying a partial address. For example:

```
$ORIGIN example.com.
IN NS ns0
@ 14400 IN NS ns1 14400
```

| ns0 14400 IN A6 0 3fffe:8050:201:860:42::1 |
| ns1 14400 IN A 192.168.42.1 |

It is recommended that IPv4-in-6 mapped addresses not be used. If a host has an IPv4 address, use an A record, not an A6, with :ffff:192.168.42.1 as the address.

## 4.8.3. Address to Name Lookups Nibble Format

While the use of nibble format to look up names is deprecated, it is supported for backwards compatibility with existing IPv6 applications.

When looking up in nibble format, the address components are simply reversed, just as in IPv4, and ip6.int. is appended to the reverse name. For example, the following would provide reverse name lookup for a host with :3fffe:8050:201:860:42::1.

```
$ORIGIN 0.6.8.1.1.0.2.0.5.0.8.e.f.3.ip6.int.
1.0.0.0.0.0.0.0.2.4.0.0 14400 IN PTR host.example.com.
```

## 4.8.4. Address to Name Lookups Using Bitstring Format

Bitstring labels can start and end on any bit boundary, rather than on a multiple of 4 bits in the nibble format. They also use ipv6.arpa rather than ip6.int.

To replicate the previous example using bitstrings:

```
$ORIGIN \[x3fffe805020021860/64].ip6.arpa.
\[x004200000000001/64] 14400 IN PTR host.example.com.
```

## 4.8.5. Using DNS for Delegation of IPv6 Reverse Addresses

In IPv6, the same host may have many addresses from many network providers. Since the trailing portion of the address usually remains constant, DNAME can reduce the number of zone files used for reverse mapping that needs to be maintained.

For example, consider a host with two providers (example.net and example2.net) and therefore two IPv6 addresses. Since the host chooses its own 64 bit host address portion, the provider address is the only part that changes.
