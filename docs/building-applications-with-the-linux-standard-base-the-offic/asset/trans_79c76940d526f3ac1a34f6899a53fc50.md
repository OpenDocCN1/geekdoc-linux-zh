

Apache 的一个版本具有一个已知版本的 **libexpat** 可以供其使用，而不是依赖于在其执行所在的系统上已安装该库。依赖系统上非 LSB 共享库的某些预期行为是危险的，因为该库的接口没有保证是一致且稳定的。为了确保与 Apache 一起打包的三个共享库不会干扰系统上安装的库，它们被安装在与 Apache 应用程序相同的整体目录结构中。

appbat 中的一些应用程序静态链接了一些非 LSB 库，以满足 LSB 的要求。例如，XPaint 应用程序利用了 **libpng**、**libjpeg** 和 **libtiff** 库中的接口。应用程序电池（Application Battery）选择静态链接这些库，而不是构建和打包这些库的共享版本以随 XPaint 一起分发。为了避免依赖于构建 XPaint 时所在系统上安装的静态库的版本，appbat 创建了一组从每个库的已知版本构建的静态库。这组库被称为 LSB 库电池，即 libbat。在 libbat 构建完成后，这些静态库被打包到一个 RPM 软件包中，该软件包安装在 LSB 开发环境之上。静态库被放置在 LSB 子库所在的同一目录中。将它们放置在那里确保了 appbat 应用程序在查找系统上是否安装了共享版本或静态版本之前，会优先与这些库的静态版本进行链接。

### 14.3.2 编码问题的解决

使用 LSB 开发环境构建应用程序有助于在编译时识别任何合规性问题。这对于应用程序电池中的许多应用程序都是成立的，并导致需要解决源代码中的问题。有些更改相当简单，例如需要使用标准参数类型而不是 LSB 未定义的类型。在另一种情况下，应用程序使用的接口未被 LSB 覆盖，但可以用 LSB 中的类似函数替换。很少情况下，应用程序使用的接口在 LSB 中没有等效函数。对于这种情况，解决方案可能包括将该功能合并到应用程序源代码中，禁用使用该接口的应用程序部分，或者重写应用程序以不同方式处理这些情况。应用程序电池中的几个示例展示了这些编码问题及其克服方法。

Samba 应用程序在上游源代码中存在一些较小的问题，导致其无法使用 LSB 开发环境进行构建。其中一个问题比较简单，即变量被声明为 `uint` 类型。`uint` 类型通常定义在大多数 Linux 发行版的头文件中，但它不是 LSB 定义的标准类型。大多数程序员使用 `uint` 作为 `unsigned short` 的简写。解决此问题的方法是向 Samba 的 configure 脚本添加功能，以检测开发环境中是否存在 `uint` 类型。在执行非 LSB 构建时，`uint` 会在常规系统头文件中找到，Samba 源代码中不会看到任何更改。当同一个 configure 脚本在 LSB 开发环境中运行时，它确定 `uint` 未定义，因此会在包含在所有 Samba 源代码中的 `config.h` 文件中添加 `#define uint unsigned short`。使用非 LSB 类型定义的问题也可以通过将所有该类型的实例替换为 LSB 中的类型之一来解决。

`rsync` 的情况比 Samba 稍微复杂一些。`rsync` 应用程序使用 `getpass()` 函数调用来提示并读取运行命令的用户输入的密码。不幸的是，`getpass()` 接口未被 LSB 定义，也没有方便的等效物。针对这种情况，在 `rsync` 源代码中添加了一个名为 `getpassword()` 的函数。`getpassword()` 的算法取自 `glibc` 文档，并稍作修改以满足 `rsync` 的需求。接下来，源代码中调用 `getpass()` 的地方被改为调用 `getpassword()`。之后，`rsync` 能够避免使用非 LSB 接口，但仍能取得预期的结果。

`rsync` 以及某些其他应用程序遇到的另一个问题涉及某些变量在代码迁移到 64 位 Linux 发行版时未得到正确处理。在许多地方，这些应用程序声明了变量来保存指针、内存地址偏移量或其他在 32 位和 64 位操作系统上大小不同的项。用于保存指针值的变量被定义为 `int` 类型，因为在 32 位系统上，整数的大小与指针的大小相同，均为 32 位。然而，这种巧合在 64 位系统上并不成立，因为在 64 位系统上，整数的大小和指针的大小不同。解决此问题的方法是将这些变量类型的定义从 *int* 更改为 *size_t*。*size_t* 变量的实际长度取决于*系统是 32 位还是* 64 位。以这种方式更改代码使 *rsync* 能够在两种不同环境之间拥有通用代码，并正确处理不同大小的指针。

Celestia 应用程序遇到了一个特定于某个处理器架构的问题。作为*为符合 LSB 要求构建 Celestia*的一部分，它被配置为使用 GL 进行图形操作，而不是使用像 Gnome 和 KDE 提供的那些非 LSB 库。在运行 GL 模式的 Celestia 启动代码的早期阶段，程序解析命令行以获取任何提供的参数。它循环调用 *getopt()* 函数来获取参数，只要 *getopt()* 的返回值大于负一。不幸的是，用于保存返回值的参数被定义为 *char*，而 *getopt()* 函数实际上返回的是 *int*。在 LSB 支持的大多数架构上，使用错误的变量类型不会造成问题，因为 *char* 类型默认是有符号的。然而，在 PowerPC 架构上，*char* 类型是无符号的。这意味着 *getopt()* 的返回值永远不会小于负一，因此程序会永远循环尝试读取命令行参数。为解决应用程序电池中的此问题，Celestia 的源代码被打补丁将参数类型更改为 *int*，从而使程序得以继续执行。

另一个需要更改应用程序的领域涉及一些非常陈旧的上游源代码。XPaint 应用程序可以读取和写入多种不同格式的图像文件，其中之一是 JPEG。应用程序通过使用 *libjpeg* 共享库中的函数调用来实现此功能。如前所述，任何非 LSB 共享库必须随应用程序提供，或者应用程序必须静态链接该库。应用程序电池通过静态链接 LSB 库电池（libbat）中提供的 *libjpeg* 实现了后一种选择。事实证明，*libjpeg* 的上游源代码相当陈旧，因此它用于确定其运行硬件类型的 configure 脚本不知道一些较新的硬件架构，如 PPC64 和 x86_64。*libjpeg* 库像许多其他尝试进行自动配置的应用程序一样，使用名为 *config.guess* 的脚本来确定构建系统的处理器架构。用于绕过此限制的方法是将 **libjpeg** 源代码中存在的 `config.guess` 版本替换为较新的版本。此更新是通过补丁完成的。打补丁后，**libjpeg** 的 configure 脚本正确工作，并允许 XPaint 在所有七个 LSB 处理器架构上成功构建。

前几段给出了构建 LSB 兼容应用程序时必须克服的一些编码问题的具体示例。一些问题无论使用哪种处理器都是相同的，而其他问题则仅在部分架构上显现。每个应用程序必须单独检查以了解存在哪些困难，但上述示例应该有助于克服遇到的任何问题。

### 14.3.3 禁用非 LSB 功能

在解决了应用程序中的任何编码问题（如前一节所述）之后，仍有一些问题需要克服。有时，即使最终选择将函数的静态版本链接到应用程序，也可能因各种原因无法正常工作。应用程序可能使用无法因其软件许可证而静态链接到应用程序的共享库。在其他情况下，构建应用程序所需的某些函数的静态版本可能困难甚至不可能。对于这些情况，剩下的唯一选项是禁用使用该共享库的应用程序部分，或者决定该应用程序不适合满足 LSB 书面规范。LSB 应用程序电池遇到了几种这样的情况，不得不禁用所涉应用程序的非关键功能。这是理解 LSB 应用程序电池中的应用程序不能被视为生产就绪的重要原因之一。一些示例说明了这对某些应用程序的影响，有助于解释问题以及解决方案。

Apache Web 服务器使用数据库来管理用户认证。由于 Apache 被设计为在许多不同的操作系统上运行，它有一个 configure 脚本，可以确定要使用的最佳可用数据库引擎。它可以使用几个版本的 Berkeley DB（**libdb**）、GNU DB（**libgdbm**）或几种其他选择。这种灵活性非常有价值，但它给以 LSB 兼容方式构建 Apache 带来了问题。LSB
