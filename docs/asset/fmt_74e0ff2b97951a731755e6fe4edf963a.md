
通过互惠，`GPL` 创建了一个同样根据 `GPL` 许可的软件公地。任何人都可以根据 `GPL` 条款对这些软件进行组合和修改，因此许可证不会将人归类为贡献者或其他任何身份。`GPL` 将所有被许可者称为“你”。再次，如果软件是血液，`GPL` 许可的软件将都是同一种血型。

`GPL` 许可软件可以在所有使用 `GPL` 许可证的项目中重用。不需要单独的贡献者协议。然而，某些开源许可证更直接地处理贡献者的特殊特征。例如，`MPL` 区分了“初始开发者授予”（`MPL` 第 2.1 节）和“贡献者授予”（`MPL` 第 2.2 节）。许可证的这两个节几乎完全相同，区别在于初始开发者贡献“原始代码”，而贡献者贡献“修改”。`MPL` 的第 3.1 节使许可证对贡献者具有互惠性。

在随后的案例中，由初始开发者编写并因此反映该公司利益的 `MPL` 对贡献者设定了更严苛的条件。例如，后者必须接受了有关知识产权事项的义务，而这些义务并不一定适用于初始开发者（`MPL` 第 3.4 节）。`MPL` 还允许初始开发者——而非贡献者——在受保护代码的部分指定替代许可证。（`MPL` 第 13 节和附件 A。）

`CPL` 比 `MPL` 更平衡。启动软件开发过程的人或公司仅仅是“初始贡献者”，其他人都是“后续贡献者”。许可延伸到接收者，接收者被定义为“根据本协议接收程序的任何人，包括所有贡献者”（`CPL` 第 1 节）。在 `CPL` 下，贡献者仅是指分发程序的人。（`CPL` 第 1 节。）

如果一个项目在 `CPL` 下分发其软件，它可以接受根据 `CPL` 许可的贡献。不需要单独的贡献者协议。

`OSL`/`AFL` 许可证将 `GPL` 的方法应用于贡献者——在许可者或被许可者的类型之间没有做出区分，也不需要单独的贡献者协议。许可者是原始作品的所有者，被许可者是“你”。如果软件是血液， `AFL` 下的贡献者将是万血型供者，而 `OSL` 许可的软件（由于其互惠条款）将都是同一种血型。

# 集体作品的许可证兼容性

我最后解释了开源原则 #5，该原则规定被许可者可以自由结合开源和其他软件。

在当前语境下，“结合”（combine）一词意味着“汇聚或连接”。这是软件世界中的常见活动。当我们向硬盘中加载各种软件时会这样做，这些软件可能来自不同的供应商；企业所有者经常将用于收集和存储财务数据的会计实务软件，与年底用于根据财务数据计算政府应缴税款的税务软件包结合在一起。办公效率套件可能包含用于文字处理、电子表格和电子邮箱的独立程序。这些软件包之间实际上可以相互通信，因此数据只需输入一次。

开源软件的分发者通常将单独开发的贡献汇集到他们的分发盘中，以方便客户使用。这些贡献最初由其作者设计，用于与聚合中的其他程序进行交互，且原始作者或下游聚合者可能已经对它们进行了兼容性测试。或者，它们之所以兼容，仅仅是因为这些贡献的设计就是为了满足行业标准。

计算机硬件和软件供应商通常构建交钥匙系统，将操作系统、驱动程序、数据库、服务器软件、实用、应用程序和其他“胶水”结合起来，创建全面的客户解决方案。在著作权法下，此类组合属于集体作品。

集体作品中的某些贡献是开源的而某些是专有的这并不重要。任何开源许可证都禁止被许可者在集体作品中使用开源会计软件包与专有税务软件包结合，或将 `GPL` 许可的操作系统与 `Apache` 许可的服务器以及 `MPL` 许可的浏览器结合。用户可以根据技术标准自由选择开源软件，而对软件的用途（或用途的组合）不受限制。

集体作品的贡献始终保留其原始著作权（`17 U.S.C. § 103(b)`）。如果它们是开源的，那么集体作品的贡献可以在其原始许可证的条款下被移除并重用在其他集体作品中，即使没有作者的许可也可以。

另一方面，作为一个整体的集体作品也是一个原始作品，受其自身著作权及其许可证的约束。这里有一个软件领域之外的简单例子：你可以复制中国诗集中的每首公有领域诗歌，但未经作者许可，你不能复制整本诗集。

软件也是如此。虽然你可能移除并重用集体作品中的开源贡献，但在未经作者许可的情况下，你不能复制集体作品本身。例如，你可以从 Red Hat 或 SuSE 分发盘中移除并重新发行 Linux，但你不能复制并分发这些拷贝的分发盘——除非像这些开源分发者一样，分发盘的许可证允许你这样做。

没有任何开源许可证会阻止人们创建非开源的软件集体作品。

# 派生作品的许可证兼容性

如果开源许可社区中有一个引起困惑和焦虑的问题，那就是：当从多个贡献创建派生作品时，开源许可证之间是如何相互作用的？

例如，一个 `GPL` 许可的贡献可以用于 `Apache` 许可的派生作品。或者一个 `OSL` 许可的贡献可以用于 `GPL` 许可的派生作品？生成的派生作品适用什么许可证？该贡献在符合贡献和派生作品条款的情况下可以被接受吗？

我在上一节中讨论了将贡献纳入集体作品的简单问题；这在开源许可证下由于开源原则 #5 是总是允许的。我将如何判断某物实际上是派生作品的复杂问题留到第 12 章。对于目前而言，我要求的只是开源作品在创建派生作品时是否兼容，无论技术术语如何定义。

## 开源许可

### 互惠许可下贡献的许可兼容性

理解在根据互惠许可（reciprocal licenses）对贡献进行再许可时会发生什么是非常简单的。除非该贡献和衍生作品都根据相同的互惠许可进行许可，否则你无法将其用于衍生作品。这就是互惠制的核心原则，如下表所示：

| | `GPL` | `MPL` | `CPL` | `OSL` |
|---|---|---|---|---|
| **衍生作品** | | | | |
| **贡献** | **GPL** | 是 | 否 | 否 |
| `MPL` | 否 | 是 | 否 | 否 |
| `CPL` | 否 | 否 | 是 | 否 |
| `OSL` | 否 | 否 | 否 | 是 |

这表明，一旦你开始在 `GPL`、`MPL`、`CPL` 或 `OSL` 下进行贡献，该许可即是唯一可用于后续衍生作品的许可。然而在实际上，开源许可中的互惠条款比这要微妙得多。

某些许可（如 `MPL` 和 `CPL`）通过定义一个迭代过程使分析复杂化，在该过程中，贡献成为一个随时间增长的软件包的一部分。这些贡献并不一定是单独许可的，你必须仔细分析许可，以确定是否可以在除 `MPL` 或 `CPL` 许可条款之外，将这些软件包的贡献在其他单独开发的衍生作品中重用。

## 选择开源许可

例如，`MPL` 期望贡献（修改内容或文件）受 `MPL` 条款的约束。（`MPL` 第 3.1 节）。但 `MPL` 允许贡献作为“较大作品”（Larger Work）的一部分被重用。（`MPL` 第 2.2[a] 节）。“较大作品”一词的定义让人联想到集体作品。（`MPL` 第 1.7 节）。我将其理解为受 `MPL` 许可的贡献可以用于不同许可的作品，但不能用于衍生作品，这似乎与上面的图表保持一致。

`MPL` 许可提供了另一种解决许可不兼容问题的潜在途径方法，它允许被许可者根据其选择的 `MPL` 或初始开发者（Initial Developer）指定的替代许可来分发衍生作品。自由软件基金会（`fs.org`）的网站建议，如果替代许可是 `GPL`，那么程序的一部分就具有兼容的许可。但请注意，这种选择仅适用于初始开发者，而且之所以适用是因为替代许可是 `GPL` 而非 `MPL`。根据自由软件基金会的说法，`MPL` 本身与 `GPL` 不兼容。

`OSL` 简要阐述了互惠性：

[许可者授予你向公众分发原始作品和衍生作品副本的许可，前提是你分发的原始作品或衍生作品副本根据开放软件许可（Open Software License）授权。（`OSL` 第 1[c] 节）。]

没有例外。无论贡献的许可如何，衍生作品只能根据 `OSL` 进行分发。当然，贡献的许可必须授权该行为：

许可者保证，在获得这些版权和专利权贡献者许可的情况下，贡献已根据本许可的条款被再许可。（（`OSL` 第 7 节。）

在 `CPL` 下，贡献不包括“根据其自己的许可协议与程序一同分发的软件独立模块”。（`CPL` 第 1 节。）

“贡献”意味着：…… (b) 对于每个随后的贡献者：i) 对程序的更改，以及 ii) 对程序的添加。（（`CPL` 第 1 节。）

因此，在 `CPL` 下，衍生作品的创建不是通过接受一个独立的贡献并以某种方式将其与另一个作品结合，而是通过对该作品进行更改或添加。此外，`CPL` 要求贡献者必须是其自身贡献的作者和分发者，这意味着 `CPL` 完全不允许经过再许可的贡献。

`GPL` 许可在这一方面被广泛认为限制性最大，这是因为以下条款的相互作用：

- 你必须确保你分发或发布的任何全部或部分包含或源自程序或其任何部分的作品，都必须根据本许可的条款，向所有第三方免费作为整体进行许可。（`GPL` 第 2[b] 节。）
- 你不能对接收者行使本文中授予的权利施加任何进一步的限制。（`GPL` 第 6 节。）

在 `GPL` 下提交的贡献的衍生作品必须根据 `GPL` 分发，你不能添加任何进一步的限制。一旦 `GPL` 下的贡献启动了所有权链，`GPL` 就是唯一可用于后续衍生作品的许可。

### 学术许可下贡献的许可兼容性

`GPL` 说你不能添加任何进一步的限制，这意味着什么？

`BSD` 和 `MIT` 许可被认为不包含任何可能干扰衍生作品任何其他许可的条件。根据自由软件基金会的说法，这些许可可以用于向受 `GPL` 许可的衍生作品提供贡献，我没有发现过任何许可下的任何开源项目曾拒绝接受 `BSD` 和 `MIT` 许可的贡献来创建衍生作品。此类软件可用于任何目的。

自由软件基金会声称，`Apache` 许可可能因为其关于商标的规定而与 `GPL` 不兼容。（但根据商标法基本规则的商标排除是否是导致与 `GPL` 不兼容的额外限制？）大多数贡献者将 `Apache` 许可用于 `Apache` 软件，而不用于其他地方。遗憾的是，由于 `GPL` 作者对额外限制的抵抗，导致 `Apache` 软件无法用于 `GPL` 许可的衍生作品。

对于学术自由许可（`AFL`），答案并不简单。正如我在第 9 章中描述的，`AFL` 包含了若干项与其他许可不同、甚至相冲突的条款和条件。`AFL` 允许根据任何许可授权衍生作品，但这是否意味着 `AFL` 许可的贡献实际上可以不与其他许可冲突地使用？

`AFL` 中超出 `GPL` 的条款包括：专利授予的范围、归属权要求、预防保证、关于管辖权、审地、适用法律和律师费的规定，以及可能最具争议的 `AFL` 第 10 节中的专利终止条款。

考虑最初根据 `AFL` 许可的贡献对下游许可者和再许可者的影响。这种保护使原始许可者 A 免受其许可者的专利侵权诉讼的侵害。假设 As 的贡献被另一作者 D 用于创建衍生作品。显然 D 是 A 的许可者，D 在不终止许可的情况下不能对 A 发起专利侵权诉讼。这在 `AFL` 第 10 节下是明确的。

但 `AFL` 是可以再许可的，那么当衍生作品根据一种未提供专利辩护通知的另一种许可分发给下游消费者 X 时，会发生什么？其他许可可能是 `GPL`、书中描述的其他开源许可之一，或者是私有许可。`AFL` 对此类下游再许可没有任何限制，As 的贡献实际上被许可给了 X。

X 可以在不冒险终止对 D 许可的情况下对 A 的作者提起专利侵权诉讼吗？X 有什么办法知道 As 许可的条款？`AFL` 第 10 节是否通过再许可延伸，保护 A 的作者免受像 X 这样的下游许可者的专利侵权诉讼？类似的问题也可以针对 As 许可中可能令人不安的条款提出，例如 `AFL` 的律师费条款或专利范围

我很难相信法院会强制要求任何开源贡献的下游被许可者受限于其既未被知情也未对其产生显性影响的许可任何条款和条件。这无疑是合同法的一项基本原则，在互联网上免费提供的大型开源软件背景下，这也是一个公平的结果。因此，如果一个 `AFL` 许可的组件作为衍生作品的一部分被 D 分许可，那么链条末端的客户 X 无法受到 `AFL` 的约束，而只能受到其接受的与 D 的许可的约束。

这种情况对 A 来说并不公平。请记住，A 本本可以在禁止分许可的许可证下发布其软件或贡献来避免这种结果。相反，A 意图在一个对衍生作品完全宽容的许可证下贡献软件。A 的软件可以被用于专有的衍生作品中。除非 A 在软件许可证中明确要求，否则许可条款不会通过分许可进行传递，而 `AFL` 并没有此类规定。

因此，我不清楚像 `AFL` 这样的学术许可证如何能与任何其他开源许可证不兼容。`AFL` 没有对该软件的被许可者施加任何条件，而被许可者被允许根据任何许可证对贡献做出决定。

当然，这些关于公平的说明以及要求被许可者知晓其受何约束条件的规定，仅适用于合同法，而不适用于著作权法下的纯粹许可（bare license）。我不知道法院将如何判定此类纯粹许可的分许可问题。

`MPL` 许可证通过要求特定的“贡献者授权”（Contributor Grant）来处理衍生作品的许可兼容性问题。只要贡献者根据该贡献者授权的条款提交其修改（Modification），`MPL` 就不关心其他许可证。确保贡献者所提供的任何内容都可以被贡献者许可，是贡献者的责任。（`MPL` 第 2.2 节。）

> 可许可的（Licenseable）意味着有权在最大范围内，无论是在初始授予时还是随后获得的，授予此处转让的任何和所有权利。（`MPL` 第 1.8.1 节。）

`CPL` 仅允许由贡献者原创的贡献。不接受分许可的贡献。（`CPL` 第 1 节。）

`OSL` 未明确禁止施加“进一步限制”，也没有单独处理贡献者。但它确实包含以下关于来源的保证，该保证具有承诺所有合并到衍生作品中的贡献之许可兼容性的效果：

许可者保证原始作品的著作权以及许可者在此处授予的专利权归许可者所有，或在这些著作权和专利权贡献者的许可下，根据本许可证的条款分许可给您。（（`OSL`/`AFL` 第 7 节。）

许可者承诺其拥有许可（即许可证）在 `OSL` 下在原始作品中分发这些贡献。`OSL` 通过让衍生作品的创作者承担一项义务——即确保其所接受的任何贡献都已获得授权，可以包含在受 `OSL` 许可的衍生作品中——从来处理了许可不兼容性问题。

## 重新许可 (Relicensing)

对于我们中的一些来说，在不同的衍生作品下组合软件是一个令人沮丧的问题。许可不兼容阻止了软件的自由使用和组合。随着开源许可证的激增，问题正变得越来越糟，越来越好。

但版权法和合同法是明确的：开源分发者除非获得许可，否则不能简单地对他人的版权保护软件进行重新许可。

一种方法是说服贡献者在不同的许可证下提供他们的作品。这对于贡献者较少、容易就许可策略达成共识的小型项目来说可能是可能的。要在大型项目中说服每个人重新考虑他们的许可是非常困难的。

他们是否由于其接收贡献时所使用的许可证，而被阻止对衍生作品进行重新许可，以替换他们不再想要的许可证转而使用不同的许可证？项目是否可以通过重新许可来使其作品与其他贡献者许可证保持兼容？

这有一个法律答案，也有一个政治答案，而且对于这个特定问题，政治答案要意义得多。开源必须是一个协作过程。任何在事实上做出的许可许可变更都可能导致社区的分裂。项目可能会失去一些关键贡献者。客户将面临来自不同开发者小组的分歧开发策略，每个小组都在竞争关注和支持。整个项目可能会死亡。

对于那些无法通过共识重新许可以适应衍生作品贡献的软件项目来说，困难的选择之一是避免创建衍生作品。这本质上是自由软件基金为了在不兼容其兼容许可证的情况下使用 `Apache` 所建议的：

我们敦促你不要为你编写的软件使用 `Apache` 许可证。然而，没有理由避免运行根据此类许可证发布的程序，例如 `Apache` (`http://www.apache.org/`)。

通过仅仅聚合来自不同来源的软件并将其视为黑盒，在技术上可以避免（尽管有时很笨拙）创建衍生作品。人们可以从软件中获益，而实际上无法对其进行内部修改和改进。

这与专有软件产品发生的情况并不相似。最终，通过足够的创造力和发明精神，可以绕过几乎所有知识产权的许可限制。

## 共享、、最终以及其他许可模型

### 开源的替代方案

许可软件的方式有很多。没有哪一种方式在法律上具有特权。合同法允许双方根据人们可以想象的几乎任何条款和条件对软件进行许可。版权法和专利法起到了最后保障的作用，防止任何人在未经许可许可的情况下复制、修改、分发、使用或出售受保护的软件——除此之外，许可的条款和条件则由各方自行决定。

开源软件分发是一个年轻但趋于成熟的商业模式。极其成功的软件已经开发出来并在全球范围内可用，通常是免费。尽管取得了这些成功，许多公司仍然拒绝在开源上“走到底”，担心免费提供软件会违背其营利动机。

在另一个极端，当然存在完全的专有软件，这些软件无法被复制、修改或分发。源代码不可用，禁止反向工程，且没有任何版权权利被让出。（但请记住，你安装自己拥有的软件副本以及制作备份副本不需要单独的许可；请参见 `17 U.S.C. 117`。） 显而易见，这种模型在市场上仍然非常成功。专有软件无疑将继续繁荣。

在完全专有和完全开源模型之间，还有其他软件分发的替代方案。本章描述了其中一些向开源致敬但并未完全走到底的变体。这些许可可以可以说，部分是专有的，部分是开源的。
