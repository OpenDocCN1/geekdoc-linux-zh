## 磁盘空间

随着磁盘空间的使用，我们必须计划增加空间（或缩小某些文件），并可能将其迁移到分级存储管理或 `HSM` 系统中。几乎每个系统管理员最终都会编写一个脚本来检查文件系统，并在任何接近容量时发出警告。以下是此类脚本的一个示例。

```bash
#!/bin/bash
## SLEW: 空间早期警告
# 由 James T. Dennis 编写
# Starshine Technical.
```

应用运行迟缓也可能是由于可用内存不足——或者磁盘驱动器上运行着一个繁忙的文件系统（可能正被其他应用程序使用）。也可能是系统的显卡速度较慢。对于 `X WINDOW` 应用程序，显卡可能比主机的处理器和内存更重要。网页渲染速度慢通常被错误地归咎于下载速度慢。

## 解决方案

容量问题有三个通用的解决方案：优化性能、增加资源和降低利用率。

解决 `DNS` 查找缓慢的一种解决方案是在本地局域网网段或本地主机上提供缓存 `DNS` 服务器。权衡是这会增加 `DNS` 服务器上内存、`CPU` 和磁盘空间的利用率。另一个解决方案可能是重新配置 `Web` 服务器，使其在处理日志文件时不对每个客户端进行反向查询。另一种解决方案是升级网络。最佳解决方案取决于本地情况以及对计算环境其他部分的可能影响。

## 性能优化

通常，性能问题并不是由硬件引起的。有时应用程序是在“更努力地工作”而不是“更聪明地工作”。例如，`Web` 服务器可能会为生成每个网页都产生一个 `Perl` 副本。许多网站以付出巨大的 `CPU` 和内存代价让其文档树保持“动态”。这些网站中的一些可以通过每天生成一次或两次静态页面（通过 `cron` 任务）来提供相同的信息，而不是为每次访问都动态地重建每个页面。另一种方法是为 `Apache` `Web` 服务器使用 `mod_perl` 模块。它会加载一次 `Perl` 解释器并在内部处理脚本。索引、哈希和缓存也可以用于减少许多进程的 `CPU` 开销。

业务系统和 `IT` 实践的优化可以极大提高系统的效率和容量。例如，某些网站使用中央数据库来分发员工电话列表。有些网站可能通过其内网 `Web` 为该数据库提供一个 `CGI`/`Web` 前端。在大多数情况下，用户最近没有更改过数据，因此提供这些信息的最有效方法是定期从数据库中生成静态页面。

在我们基于 `Web`/`CGI` 的示例中，可能会有一个链接允许任何用户强制对数据库进行检查。因此，如果从静态页面中接收到意外的答案（这可能是一前的版本），用户可以查询实时数据库。请求将由静态页面处理，只有特殊情况才会影响服务器的负载。此外，静态生成的页面可以在整个组织中缓存，而复制“实时”数据库要复杂得多，并且在 `CPU` 周期和（更重要的是）管理开销方面的成本高得多。

静态页面会被索引（例如使用 `glimpseindex`）并在网上搜索（例如使用 `GlimpseHTTP`）。然而，也可以通过简单的 `Web` 浏览和书签访问它们。生成同一信息的多个版本——按部门划分的层级结构和按姓首字母划分的页面组——也是一种元素。

通常情况下，在合理的目录层次结构中拥有许多小的 `HTML` 文件，比拥有几个私有格式的文件（如 `PDF`）具有更大的网站容量和易用性。

`Web` 服务器通过记录完全限定域名而非 `IP` 地址，涉及反向 `DNS` 查询，这会消耗更多带宽和 `CPU` 时间。如果 `Web` 服务器还在执行身份查询——即请求执行特定查询的远程系统的“用户身份”（通常是登录名）——情况会更加恶剧（此处原文 `indent` 应为 `identify`）。禁用这些功能（以及 `Cookie`）是产生显著性能益处的简单步骤。这并不是说网站管理员永远应该启用这些服务器日志功能。要考虑这些额外数据的成本和价值。也可以让一个单独的日志在非高峰时段执行反向查询。

在大多数情况下，“许多更小的”会比少数较大的、更昂贵的系统或外围设备有效。例如，较小的 `SCSI` 磁盘驱动器（更多磁柱）将明智地优于一个大型驱动器，因为每个驱动器可以并行处理请求并向 `CPU` 异步提供结果。一个磁盘驱动器将（内部）一次处理一个请求。
