
客户端发送循环中有四个步骤：使用 `fgets` 从标准输入读取一行，使用 `sendto` 将行发送到服务器，使用 `recvfrom` 读取服务器的回显，并使用 `fputs` 将回显的行打印到标准输出。

我们的客户端没有请求内核为其套接字分配一个临时端口。对于 TCP 客户端，我们说 `connect` 是发生这一过程的地方。对于 UDP 客户端，当进程第一次调用 `sendto` 时，如果套接字尚未绑定本地端口，内核将选择一个临时端口。与 TCP 一样，客户端可以显式调用 `bind`，但很少有这样做。注意 `recvfrom` 的第五和第六个参数指定为空指针。这告诉内核我们不关心是谁发送了回复。存在一种风险，即无论是哪个进程，都可能收到回复。由于同一个指针 `pcliaddr` 被作为目标地址传递给 `sendto`，这就是数据报回显给发送该数据报的客户端的方式。正如 `recvfrom` 所示，`recvfrom` 填充了客户端的 IP 地址和端口号。

## 8.7 丢失的数据报

UDP 客户端是不可靠的。如果数据报在到达服务器之前丢失，例如被路由器丢弃，客户端将在 `recvfrom` 处阻塞。

## 8.8 验证客户端的响应

无论数据报从哪个接口到达，其目标都是宿主机的任何一个 IP 地址，参见 TCPv2 第 217–219 页。RFC 1122 [Braden 1989] 将此称为“弱端点系统模型”。如果一个系统实现了 RFC 所说的“强端点系统模型”，那么它只有在数据报到达其所指向的接口时才会接收该数据报。

`recvfrom` 返回的 IP 地址，即 UDP 数据报的源 IP 地址，并不是我们发送时的那个 IP 地址。当服务器发送回复时，目标地址是 172.24.37.78。freebsd 内核中的路由函数选择 172.24.37.94 作为输出接口。由于服务器的套接字没有 IP 地址，内核会为 IP 数据报选择源地址。然后需要通过在 freebsd 上运行 `netstat` 来验证该地址是否为输出接口的主 IP 地址，参见 TCPv2 第 232–233 页。此外，由于它是接口的主 IP 地址，如果我们将数据报发送到接口的非主 IP 地址，即任意地址，这将导致我们在图 8.9 中的测试失败。

一种解决方案是客户端根据 `recvfrom` 返回的 IP 地址，通过在 DNS 查询服务器名称来验证响应方的域名，而不是其 IP 地址。另一种解决方案是 UDP 服务器为主机上配置的每一个 IP 地址创建一个套接字，将该 IP 地址绑定到该套接字上，在所有这些套接字中进行选择，等待其中任何一个变为可读，然后从该套接字向客户端请求的 IP 地址进行回复，否则数据报将无法投递到客户端请求的目标地址，这保证了回复的源地址与回复的目标地址相同。我们将在第 22.6 节中展示一个示例。

在多网卡的 Solaris 系统上，服务器回复的源 IP 地址是客户端请求的目标 IP 地址。本节描述的场景适用于 Berkeley 派的实现，这类实现根据输出接口来选择源 IP 地址。

## 8.9 服务器未运行
