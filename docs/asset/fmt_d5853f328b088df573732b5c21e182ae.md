4. 执行多次系统日志切换，以恢复每个新成员的状态使其为 `INVALID`（无效）或 `STALE`（过旧），可以通过 `V$LOGFILE` 查看。

与控制文件相比，重做日志的多路复用会有更多的维护和性能开销。具体来说，如果你将重做日志文件所需的磁盘空间增加了一倍，由于额外的写入将产生更多的 I/O 操作。然而，为了防止因重做日志文件丢失导致数据库崩溃并可能丢失数据，这个代价是非常微小的。

# 数据库自动启动

当 Unix 或 Linux 服务器关闭（计划内或其他原因）时，运行在其上的任何数据库也会被关闭。一旦服务器重启，所有数据库默认都将处于关闭状态。如果数据库需要重启，这可能会产生问题。除非有 DBA 提供 7x24 小时的待命以应对问题，否则解决方案是让数据库在机器启动时自动重启。

## Unix 和 Linux 上的 Oracle DBA

Unix 和 Linux 服务器在关闭或启动时会经历一组预定义的阶段。每个运行级别（run level）都可能有一组与之相关的进程列表。DBA 可以包含脚本，用于在特定的运行级别启动或关闭一个或多个数据库和监听器。这允许数据库在执行关闭时自动关闭，并允许数据库在服务器重启后重新启动。在服务器崩溃的情况下，Oracle 实例恢复将自动解决大多数问题。

决定数据库是否自动重启的控制文件是 `/etc/oratab`（Linux 或 HP-UX）或 `/var/opt/oracle/oratab`（Sun Solaris）。图 9.2 显示了 oratab 文件的副本。

![](img/69e00a365a25f8ffa32835d529d74f90_261_0.png)

图 9.2
`/etc/oratab` 文件。

每行的最后字符（`Y` 或 `N`）表示重启时是否将重启数据库。如你所示，只有 `rh1p1` 和 `rh1dev1` 会自动重启。

Oracle 提供了两个脚本来自动启动和关闭 `/etc/oratab` 中指定的数据库。这些脚本是：

```bash
$ORACLE_HOME/bin/dbshutdown
```

以及

```bash
$ORACLE_HOME/bin/dbstart
```

请与你的 SA（系统管理员）协作实现这些脚本，因为它们需要 root 权限。可能存在特定平台的问题，因此你应该咨询《安装和配置指南》。但是，以下步骤提供了在 Sun Solaris 上实现自动启动和关闭过程的一种方法：

1. （以 Oracle 身份）编辑 `$ORACLE_HOME/bin/dbshutdown` 为 `SHUTDOWN IMMEDIATE`。
2. （以 root 身份）创建文件：`etc/init.d/dbshutdown`。
```csh
#!/bin/csh

su oracle -c "/u01/app/oracle/product/8.1.6/bin/lsnrctl stop"

su oracle -c "/u01/app/oracle/product/8.1.6/bin/dbshut"
```
3. 为 `dbshut` 分配权限 755。
```bash
$ chmod 755 dbshut
```
4. （或）为 `/etc/rc0.d/K0dbshut` 创建指向 `/etc/init.d/dbshut` 的软链接。
```bash
$ ln -s /etc/init.d/dbshut /etc/rc0.d/K0dbshut
```
此链接将强制 `dbshut` 停止监听器。Oracle db 将关闭正在运行的数据库。

5. （或）创建文件：`etc/init.d/dbstart`。
```csh
#!/bin/csh

su oracle -c "/u01/app/oracle/product/8.1.6/bin/dbstart"

su oracle -c "/u01/app/oracle/product/8.1.6/bin/lsnrctl stop"
```
6. 为 `dbstart` 分配权限 755。
7. （或）为 `/etc/rc0.d/K0dbshut` 创建指向 `/etc/init.d/dbstart` 的软链接。

# 离线备份与 ARCHIVELOG 模式

在 `NOARCHIVELOG` 模式下的数据库只能通过完全的冷（离线）备份进行备份和恢复。如果任何数据文件或在线重做日志文件丢失或损坏导致数据库需要恢复，则必须恢复数据库中的每一个文件。

唯一不需要完全恢复的文件是控制文件。如果你只丢失了一个控制文件，且仍然拥有有效的副本，则不需要恢复整个数据库。恢复控制文件的内容将在本章稍后部分介绍。

在示例中，你在周日关闭了数据库，并对所有控制文件、重做文件和数据库文件进行了冷备份。周一你重启数据库，业务正常运行，直到周三 `/u07` 故障。你知道 `/u07` 包含你的 `customers_01.db` 文件，但你必须从周日的备份中恢复整个数据库。这意味着你丢失了直到周日晚上所有的事务。

这是一次严重的数据丢失，但这是 `NOARCHIVELOG` 模式下恢复数据库的代价。你只能恢复到上一次备份的时间。

执行恢复操作在概念上非常简单：删除损坏数据库的所有控制文件、在线重做日志文件和数据文件。从同一个备份中恢复所有控制文件、在线重做日志文件和数据文件到完全相同的位置。每个文件必须来自同一次备份，并且必须位于相同的位置。如果任何文件在备份期间缺失或未被“关闭”，数据库将无法正常启动。如果文件已到位，只需启动 `SQLPlus`，进行内部连接并启动数据库。你将获得一个与冷备份关闭前完全一模一样的数据库。

# ARCHIVELOG 模式下的冷备份

`ARCHIVELOG` 模式下数据库的冷备份遵循相同的规则——但在恢复上有更大的灵活性。具体来说，你不需要恢复整个数据库。只需恢复那些损坏或丢失的文件。Oracle 会识别出从备份恢复的文件具有较早的时间戳，并应用归档重做日志将这些文件更新。

要开始冷备份，请正常关闭数据库。接下来，将所有数据文件和控制文件复制到备份位置。所有文件复制完成后，即可重启数据库。

不要复制 `ARCHIVELOG` 模式下数据库的在线日志文件。你需要保留故障时刻的在线重做日志，因为它们可能包含需要重新应用于数据库的事务。这是 `ARCHIVELOG` 模式数据库冷备份与 `NOARCHIVELOG` 模式冷备份的主要区别。下表总结了备份内容。

## 备份内容对比

| 备份模式 | 控制文件 | 数据文件 | 重做日志文件 |
|---|---|---|---|
| NOARCHIVELOG 模式 | 是 | 是 | 是 |
| ARCHIVELOG 模式 | 是 | 是 | 否 |

备份和恢复重做日志通常是一个困惑点，即使对于经验丰富的 DBA 也是如此。事实上，我甚至见过 Oracle 文档在这一问题上存在冲突的信息。原因在于人们认为 `NOARCHIVELOG` 模式和 `ARCHIVELOG` 模式数据库的冷备份是相同的。实际上，对每种类型数据库的要求是不同的。

关于冷备份，请考虑以下三点确定性：

- 数据库在备份前必须关闭
- 数据库在备份期间不可用
- 它是 `NOARCHIVELOG` 模式数据库的唯一选择

冷备份易于理解、实施和恢复。如果使用得当，它们可以提供到备份时间点的完全恢复。然而，因为它们需要时间，而且 `NOARCHIVELOG` 模式不支持时间点恢复，许多站点选择改用热备份。

# 热备份与恢复

热备份（又称在线备份）是在数据库运行期间拍摄的数据文件副本。只有处于 `ARCHIVELOG` 模式的数据库才有资格进行热备份。此外，备份并不是一次性对整个数据库进行操作系统级的拷贝。每个表空间被放入“热备份模式”，这会冻结数据文件头以使 SCN 不增加。然后，将表空间中的每个数据文件复制到数据库目标位置。一旦这些文件成功复制，表空间将退出备份模式并解除文件头的冻结。随后，备份过程将进行到下一个表空间并执行相同的操作。一旦所有文件都复制完成，热备份即完成。结果是每个表空间及其相应数据文件的副本，其中每组数据文件的时间戳略有不同。

信不信由你，这种方法是备份 Oracle 数据库最灵活的方法。与其备份整个数据库（使用冷备份），这些热备份在表空间级别节省了时间。如果磁盘故障导致你丢失了挂载点，只需从热备份中恢复那些丢失的文件即可。在恢复期间，Oracle 会注意到这些文件的时间戳比存储控制文件中指定的时间戳要早。Oracle 将进入恢复模式，并提示你提供恢复文件时间戳之后的所有归档日志文件。Oracle 将“重放”归档日志文件中的事务，将所有重做日志文件带到当前 SCN。随后，Oracle 将正常打开数据库供业务。

## 恢复原理

从概念上，这就是 Oracle 使用归档日志文件恢复到当前时间点的方法。所需的是归档日志文件、当前的控制文件（用于查看恢复到什么程度）以及数据文件的有效副本。恢复的数据文件可以来自冷备份、一系列热备份，或者两者的混合。Oracle 关乎的是文件是正常关闭的还是处于备份模式。然而，Oracle 确实要求连续的归档日志文件链。如果你在归档日志文件中遇到间隙，恢复将在该点停止。

热备份仅适用于表空间的一部分数据文件。控制文件和重做日志本身并不属于热备份。相反，它们被用于通过提供指导（通过控制文件）和最新事务（通过重做日志）来实现恢复。热备份和恢复方法论在很大程度上基于这样一个假设：至少有一个控制文件和一个每个重做日志的成员在初始故障中存活。如果你丢失了任何控制文件或日志文件，你必须在尝试恢复数据文件之前先恢复它们。故障的规模会增加恢复的复杂性和时间。

# 将数据库设置为 ARCHIVELOG 模式

数据库默认处于 `NOARCHIVELOG` 模式。在构建数据库、创建应用表空间并加载初始数据后，你应该将数据库置于 `ARCHIVELOG` 模式。

第一步是识别归档日志文件生成的位置。该位置通常称为归档目的地或 `ORACLE_ARCHIVE_DEST`。默认位置是 `$ORACLE_HOME/admin/$SID/arch`。这可能不是最佳位置，特别是当它没有被定期备份或空间不足时。在选择归档日志文件的位置时，考虑两个因素：

- 任何归档日志文件的丢失将限制恢复到该点。
- 如果归档目的地满（没有剩余磁盘空间）或由于任何原因无法写入，DML 活动将挂起。此外，新用户可能无法登录数据库。

通常，你的归档目的地需要一个为 Oracle 专门保留的大文件系统。最好有一个 cron 任务来自动压缩或 gzip 这些文件。一旦这些文件位于磁盘上，请确保将这些文件复制到磁带或可写光盘，或者通过 FTP 传输到另一台机器。如果由于某种原因丢失了文件，你需要对数据库进行新的备份并以此作为基准，因为在该丢失文件日期之后的归档日志文件是没用的。

确保归档日志文件的目的地可用。例如，如果文件系统满了导致 Oracle 无法向该位置写入归档日志，数据库在执行任何 DML 活动时将挂起。正常查询可以进行，但不允许进行 DML，因为 Oracle 无法对其进行归档。诊断此类问题也将非常困难，因为错误对用户是不可见的，只会出现在告警日志中。请记住归档目的地文件压缩或复制的速度。曾经我启动过一次大数据加载，归档日志文件极快地写入归档目的地。虽然我们正在写入磁盘，但光驱无法跟上文件从磁盘移动到 CD 的速度。我们几乎挂起了数据库。

将数据库设置为 `ARCHIVELOG` 模式，请执行以下操作：

1. 编辑 `initSID.ora` 文件以包含以下值：
```text
log_archive_start = true
log_archive_dest = "/u01/oracle/admin/rhidev1/arch"
log_archive_format = arch_rhidev1_%s.arc
```
这些参数允许 `ARCH` 进程自动运行，定义归档目的地为 `$ORACLE_BASE/admin/rhidev1/arch`，并定义每个导出文件的命名格式。

2. 以 mount 模式启动数据库。
```sql
SQL> startup mount
ORACLE instance started.
```

3. 将数据库设置为 `ARCHIVELOG` 模式。
```sql
SQL> alter database archivelog;
Database altered.
```

4. 验证数据库状态。
```sql
SQL> archive log list
Database log mode Archive Mode
Automatic archival Enabled
Archive destination /u01/oracle/admin/rhidev1/arch
Oldest log sequence archive 37
Next log sequence to archive 39
Current log sequence 39
```

5. 打开数据库以进行正常使用。
```sql
SQL> alter database open;
Database altered.
```

强制切换日志并验证日志是否已在正确位置创建。

```sql
SQL> alter system switch logfile;
System altered.
```

```bash
SQL > ls /u01/app/oracle/admin/rh1dev1/arch
arch_rh1dev1_39.arc
```

日志文件的格式为 `arch_rh1dev1_thread_#.arc`。`thread#` 应用于存在多个实例的并行服务器安装。Sequence 标识归档日志文件。例如，此文件的值为 39；下一个日志将是 40。

以上涵盖了将数据库设置为 `ARCHIVELOG` 模式的基础知识。其他需要考虑的参数是如果你是否想将归档日志写入到多个目的地。其原理是，如果一个位置无法写入，归档日志也将写入备份位置。顺序参数为 `LOG_ARCHIVE_DEST[1...5]`。此外，你可以通过 `LOG_ARCHIVE_DEST` 指定多五个位置，但你可以指定每个位置是可选的还是强制的。如果你有一个高可用性系统并且有充足的空间，这些参数将很有用，但大多数数据库不需要这种程度的保护。

关于归档日志的最后一点：它们可以在数据库运行期间进行更改。例如，如果数据库空间满了，而你有另一个可以存储它们的文件系统，那么这是一个非常有价值的选项。请确保不要在写入多个位置时丢失任何日志文件。语法如下：

```sql
SQL> alter system archive log to '/ubap/rh1dev1/'
```

# 将数据库置于热备份模式

热备份（在线备份）要求数据库处于 `ARCHIVELOG` 模式。接下来，每个表空间被置于热备份模式，这实际上冻结了文件头使其无法更改。该表空间对应的文件被复制到备份位置。一旦进程完成，表空间将退出热备份模式。

当表空间处于热备份期间，可以发生与该表空间相关的正常数据库活动，但会产生更多的重做日志。更改将在块级别而非行级别进行记录。因此，重做活动会增加。这将影响性能，这就是为什么热备份应该在数据库最空的时候进行。

此外，并没有要求备份每个表空间，也不要求顺序备份每个表空间。然而，如果你可以将每个表空间放入每晚备份中，请这样做。此外，顺序备份每个表空间比一次性将所有表置于热备份模式要快。记住，与 `NOARCHIVELOG` 模式下的冷备份不同，你不需要具有匹配时间戳的数据文件。此过程会恢复每个数据文件的有效备份副本（带有不同的时间戳），并让恢复过程通过应用归档日志将数据文件更新至最新。

在热备份模式下备份表空间需要以下步骤。

1. 通过将表空间置于热备份模式来冻结数据文件。
```sql
SQL> alter tablespace users begin backup;
Tablespace altered.
```
记住，此时允许对 `USERS` 表空间中的对象进行正常访问，但代价是重做活动增加。

2. 接下来，使用任何操作系统命令将 `USERS` 表空间的数据文件复制到你的备份位置。这可以是磁盘、磁带或光盘介质。
```bash
SQL> cp /u04/oradata/rhdev1/users01.dbf /ubap/rhdev1/backups/
```

3. 将表空间退出热备份模式。
```sql
SQL> alter tablespace users end backup;
Tablespace altered.
```

4. 将控制文件备份为 trace。
```sql
SQL> alter database backup controlfile to trace;
Database altered.
```

5. 将控制文件备份为二进制副本。
```sql
SQL> alter database backup controlfile to '/ubap/rhdev1/control.2014';
Database altered.
```

6. 刷新在线日志以确保更改已归档。
```sql
SQL> alter system archive log current;
```
