
也就是说，目标和前置条件是立即展开的，而构建目标的配方始终是延迟展开的。这一通用规则适用于显式规则、模式规则、后缀规则、静态模式规则和简单的的前置条件定义。

在上一节中，我们了解到 GNU `make` 分两个不同的阶段：读取阶段和目标更新阶段（见见第 16 页第 3.7 节 [make 如何读取 Makefile](How Make Reads a Makefile)）。GNU `make` 还有能够为 Makefile 中定义的全部或部分目标启用前置条件（仅限前置条件）的二次展开。为了发生这种二次展开，在第一个前置条件列表使用此功能之前，必须定义特殊目标 `.SECONDEXPANSION`。

如果定义了特殊目标，那么在上述两个阶段中，在读取阶段的末尾，目标之后定义的所有目标的前置条件都会被第二次展开。在大多数情况下，这种二次展开将没有任何影响，因为所有变量和函数引用在 Makefile 的初始解析期间已经展开了。为了利用解析器的二次展开阶段，请对目标中的变量或函数引用进行转义。在这种情况下，第一次展开仅仅取消引用的转义但不展开它，展开留给二次展开阶段。例如，考虑这个 Makefile：

```
.SECONDEXPANSION:

ONEVAR = onefile

TWOVAR = twofold

myfile: $(ONEVAR) $$(TWOVAR)
```

在第一次展开阶段后，`myfile` 目标的前置条件列表将是 `onefile` 和 `$(TWOVAR)`；第一个（取消转义的）引用未被展开，展开留给二次展开阶段。

相应地。在第三种情况下，它们的值分别是 `foo.1`、`foo.1 bar.1`、`foo.2 bar.2` 以及 `foo.1 bar.1 foo.2 bar.2 foo.1 foo.1 bar.1`。

`makefile` 顺序中二次扩展的规则如下，例外是带有 recipe 的规则总是会被求值。

变量 `$$` 和 `$$` 是不可用的，会扩展为空字符串。

静态模式规则二次扩展的规则与上述的显式规则相同，但有一个例外：对于静态模式规则，`$$` 被设置为模式主干（pattern stem）。与显式规则一样，`$$` 不可用且会扩展为空字符串。

当 `make` 搜索隐式规则时，它会替换主干，然后对每个匹配目标的规则执行二次扩展。自动变量的值获取方式与静态模式规则相同。例如：

```

当对目标 `foo` 尝试隐式规则时，`$$<` 扩展为 `bar`，`$$` 扩展为 `bar boo`，`$$` 也扩展为 `bar boo`，而 `$$` 扩展为 `f`。

规则出现在 `makefile` 中，说明了何时以及如何重新制作某些文件，这些文件被称为规则的目标（targets）（通常每个只有一个）。它列出了作为目标依赖（prerequisites）的其他文件，以及用于或更新目标的 recipe。

## 4.3.2 使用通配符的陷阱

现在有一个使用通配符展开的示例，它的效果并不符合你的预期。假设你想表示可执行文件 `'foo'` 是由目录中的所有文件生成的，你是这样写的：

```
objects = *.o
```

```
foo := $(objects)

cc - foo $(CFLAGS) $(objects)
```

`objects` 的值为实际字符串 `'*.o'`。通配符展开发生在 `'foo'` 的规则中，因此创建 `'*.o'` 变成了 `'foo'` 的前提条件，并在必要时重新编译。

但如果你删除了所有的 `*.o` 文件呢？当通配符没有匹配到任何文件时，它将保持原样，那么 `'foo'` 将依赖于一个命名异常的文件 `'*.o'`。没有这样的文件链接到它；`make` 会给你一个错误，说它无法确定如何制作 `'*.o'`。这并不是你想要的！

实际上，通过通配符展开可以获得所需的结果，但你需要更高级的技术，包括通配符函数和字符串替换。这些将在后续节中进行描述。

微软操作系统（MS-DOS 和 MS-Windows）使用反斜线分隔路径名中的目录，如下：

```
c:\foo\bar\.baz
```

这等同于 Unix 风格的 `'c:/foo/bar/baz.c'`（`'c:'` 部分是所谓的驱动器号）。当 `make` 在这些系统上运行时，它支持路径中的反斜线以及 Unix 风格的斜杠。然而，这种支持并不包括通配符展开，除非反斜线是引号字符。因此，在这些情况下你必须使用 Unix 风格的斜杠。

## 4.3.3 wildcard 函数

通配符展开在规则中自动发生。但通配符展开不会在变量赋值时或函数参数内部发生。如果你想在这些地方使用通配符展开，需要使用 `wildcard` 函数，如下：

```

```

这个在 Makefile 中任何地方使用的字符串将被替换为由空格分隔的列表，这些是匹配其中一个文件名模式的存在文件的名称。如果没有现有文件匹配模式，则该模式将从 `wildcard` 函数的输出中省略。注意，这与规则中未匹配的通配符的行为不同，在规则中，它们被原样使用，而不是被忽略（参见第 4.3.2 节 [通配符陷阱]，第 24 页）。

例如，

被解释为像写成这样一样：

`foo.o : src/foo.c`

## 4.4.5 目录搜索与隐式规则

在 `VPATH` 中或通过路径指定的目录搜索也会在考虑隐式规则时发生（参见第 10 节 [使用隐式规则]，第 111 页）。

## 4.4.6 链接库的目录搜索

目录搜索以一种特殊的方式出现在与链接器使用的库上。当你使用类似于 `-lname` 格式的依赖项时，这种特殊功能就会发挥作用（你可以察觉到发生了奇怪的事情，因为依赖项不是文件名，而且库的文件名看起来像 `libname.a`，而不是 `-lname`）。

当依赖项名称为 `-lname` 时，`make` 会特殊处理它：搜索文件 `.libname.so`，如果未找到，则在当前目录搜索 `.libname.a`，在匹配 `vpath` 搜索路径和 `VPATH` 搜索路径指定的目录中搜索，然后在 `/lib`、`/usr/lib` 和 `prefix/lib`（通常为 `/usr/local/lib`，除非是 MS-DOS/Windows 版本）。

例如，如果系统中存在 `/usr/lib/curses.a` 库（且没有 `/usr/lib/curses.so`），

```
foo.o : -lcurses

cc $\$ -o $$
```

当 `foo` 老于 `foo.c` 或 `/usr/lib/curses.a` 时，将会执行命令 `cc foo.c /usr/lib/curses.a -o foo`。

虽然搜索 `libname.so` 和 `libname.a` 有一组默认的文件集，但可以通过 `LIBPATTERNS` 变量进行自定义。该变量值中的每个单词都是模式字符串。当看到依赖项 `-name` 时，`make` 将将列表中每个模式中的 `%` 替换为 `name`，并使用每个库文件名执行上述目录搜索。

`LIBPATTERNS` 的默认值为 `lib%.so lib*.a`，它提供了描述的默认行为。

你可以通过将此变量设置为空值来完全关闭链接库扩展。

## 4.5 伪目标 (Phone Targets)

伪目标并不是真正的文件名；它只是一个在对做出显式请求时执行的配方名称。使用伪目标有两个原因：避免与同名文件冲突，以及提高性能。

如果你写了一个不会创建该目标的目标，那么每当目标需要重新制作时，配方都会被执行。这里有一个例子：

```
clean

rm *.o temp
```

由于 `rm` 命令不会创建一个名为 `clean` 的文件，可能永远不会存在该文件。因此，每当你执行 `make clean` 时，`rm` 命令都会执行。

如果有人在该目录中创建了一个名为 `clean` 的文件，伪目标将失效。因为它没有依赖项，文件 `clean` 将不可避免地被认为是最新的，其配方将不会执行。为了避免这种情况，你可以使用特殊的 `.PHONY` 显式声明目标为伪目标（参见第 4.8 节 [特殊内置目标名称]，第 32 页），如下：

```
.PHONY : clean
```

一旦完成此操作，无论是否存在名为 `clean` 的文件，`make clean` 都会运行配方。由于 `make` 知道伪目标不是可以从其他文件中删除的实际文件，它会跳过对伪目标的隐式搜索（参见第 10 节 [隐式规则]，第 111 页）。这就是为什么如果你不担心实际执行，声明伪目标有利于性能。

因此，你首先写下声明 `clean` 是伪目标的行，然后写规则：

```
.PHONY : clean

rm *.o temp
```

伪目标的用处的另一个例子是结合递归调用 `make`（更多信息请参见第 5.7 节 [make 的递归使用]，第 50 页）。在这种情况下，Makefile 通常包含一个列出要构建的多个子目录的变量。处理此问题的方法是用一个规则配方对子目录进行 shell 循环，如下：

SUBDIRS = foo baz

.PHONY : subDIRS

subdirs: $(SUBDIRS)

	for dir in $(SUBDIRS); do \
		$(MAKE) -C $$dir; \
	done
```
