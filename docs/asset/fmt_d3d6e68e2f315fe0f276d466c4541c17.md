
（我们使用了非常特定的 `ps` 参数来向我们显示与此讨论相关的信息。）在输出中，我们在同一个窗口中运行了客户端和服务器（`pts/6`，代表伪终端编号 6）。`PID` 和 `PPID` 列显示了父子关系。我们可以看出第一行 `tcpserv01` 是父进程，第二行 `tcpserv01` 是子进程，因此子进程的 `PPID` 是父进程的 `PID`。此外，父进程的 `PPID` 是 shell（`bash`）。

我们这三个网络进程的 `STAT` 列均为 `S`，意味着进程正在睡眠（等待某些内容）。当进程处于睡眠状态时，`WCHAN` 列指定了等待条件。当进程在 `accept()` 或 `connect()` 中阻塞时，Linux 打印 `wait_for_connect`；当进程在套接字输入输出上阻塞时，打印 `tcp_data_wait`；当进程在终端 I/O 上阻塞时，打印 `read_chan`。我们这三个网络进程的 `WCHAN` 值都是合理的。

## 5.7 正常终止

此时，连接已经建立，我们在客户端输入的任何内容都会被回显。

```
linux %tcpcli0 127.0.0.1             我们稍早展示过这一行
hello, world                               我们现在输入这个
hello,world                                 并且该行被回显
good bye
good bye
^D                               Control-D 是我们的终端 EOF 字符
```

我们输入了两行内容，每行都会被回显，然后我们输入终端的 EOF 字符（Control-D），这终止了客户端。如果我们立即执行 `netstat`，将会得到：

```
linux %netstat -a | grep 9877             *:*
tcp             0 **:9877                    LISTEN
tcp             0 localhost:42758      localhost:9877      TIME_WAIT
```

连接的客户端侧（本地端口为 `42758`）导致了 `TIME_WAIT` 状态（第 2.7 节），而监听的服务器仍在等待另一个连接。（这次我们将 `netstat` 的输出通过管道传给 `grep`，只打印带有我们服务器已知端口的行。这样做去除了标题。）

我们可以在客户端和服务器的正常终止中遵循以下步骤：

1. 当我们输入 EOF 字符时，`fgets()` 返回一个空指针，函数 `str_cli()`（图 5.5）返回。
2. 当 `str_cli()` 返回到客户端 `main()` 函数（图 5.4）时，后者通过退出终止。
3. 进程终止的一部分是关闭所有打开的描述符，客户端套接字由内核关闭。这会向服务器发送一个 `FIN`，服务器用一个 `ACK` 响应。这是 TCP 连接终止序列的第一半。此时，服务器套接字处于 `CLOSE_WAIT` 状态，客户端处于 `FIN_WAIT_2` 状态（图 2.4 和 2.5）。
4. 当服务器接收 `FIN` 时，服务器侧阻塞在 `readline()` 调用中（图 5.3），`readline()` 返回 0。`str_echo()` 函数返回到服务器子进程的 `main()`。
5. 服务器子进程通过调用 `exit()` 终止（图 5.2）。
6. 服务器子进程中所有打开的描述符都被关闭了。子进程对已连接套接字的关闭导致 TCP 连接终止的两个片段发生：从服务器到客户端的 `FIN` 以及从客户端的 `ACK`（图 2.5）。此时，连接完全终止。客户端套接字进入 `TIME_WAIT` 状态。
7. 最后，当服务器子进程终止时，`SIGCHLD` 信号被发送给父进程。这在示例中发生了，但我们没有在代码中捕获该信号，信号的默认动作是忽略。因此，子进程进入僵尸状态。我们可以通过 `ps` 命令验证这一点。

```
linux % ps -t pts/6 -o pid,ppid,tty,stat,args,wchan
PID PPID TT STAT WCHAN
22038 22036 pts/6 S      read_chan
17870 22036 pts/6 S      ./tcpserv01 wait_for_connect
19315 17870 pts/6 Z      [tcpserv01 <defu do_exit
```

子进程的 `STAT` 现在是 `Z`（代表 zombie 僵尸）。

我们需要清理我们的僵尸进程，这需要处理 Unix 信号。在下一节中，我们将提供信号处理的概述。

## 5.8 POSIX 信号处理

信号是向进程发出的某个事件已发生的通知。信号有时被称为软件中断。信号通常是异步发生的。这意味着进程事先并不知道信号具体会在何时发生。

信号可以通过以下方式发送：

- 从一个进程发送到另一个进程（或发送给自己）
- 从内核发送到一个进程

我们在上一节末尾描述的 `SIGCHLD` 信号是每当进程终止时，内核发送给该进程的父进程的信号。

每个信号都有一个处理方式（disposition），也称为与信号相关的动作。我们通过调用 `sigaction()` 函数（稍后描述）来设置信号的处理方式，对于处理方式有三种选择：

1. 我们可以提供一个函数，每当特定信号发生时就会被调用。该函数被称为信号处理程序，这种动作被称为捕获（catching）。信号 `SIGKILL` 和 `SIGSTOP` 无法被捕获。我们的函数接收一个整数参数，该参数是信号号，且函数没有返回值。因此，其函数原型为

```
void handler (int);
```

对于大多数信号，调用 `sigaction()` 并指定信号发生时调用的函数就是捕获信号的全部。稍后我们将看到信号 `SIGIO`、`SIGPOLL` 和 `SIGURG` 在某些情况下需要额外的动作。

2. 我们可以通过将处理方式设置为 `SIG_IGN` 来忽略信号。信号 `SIGKILL` 和 `SIGSTOP` 无法被忽略。

3. 我们通过将处理方式设置为 `SIG_DFL` 来设置信号的默认处理。默认是在接收信号时终止进程，某些信号的默认处理是忽略：`SIGCHLD` 和 `SIGURG`（带外数据，第 24 节）是我们在文中会遇到的两个。

### `signal()` 函数

POSIX 设置信号处理方式的方法是调用 `sigaction()` 函数。然而，这很复杂，因为函数的参数是一个我们必须分配并填充的结构。设置信号处理方式的一种方法是调用 `signal()` 函数。第一个参数是信号名称，第二个参数是 `SIG_IGN` 或 `SIG_DFL` 常量之一。`signal()` 是一个在调用时提供不同信号语义的历史函数。解决方案是定义我们自己的名为 `signal()` 的函数，以提供 POSIX 语义。这提供了一个符合 POSIX 语义的简单接口。我们将它与 `err_XXX()` 函数和包装函数一起放入库中，供我们在文中构建任何程序时使用。该函数见图 5.6（包装函数未在此显示，因为无论调用我们的函数还是供应商提供的 `signal()` 函数，它们都是相同的）。

`lib/sig.c`

```c
# 1 "unp.h"
2 Sigfunc *
3 signal (int signo, Sigfunc *func)
4 {
5     struct sigaction act, oact;
6     act.sa_handler = func;
7     sigemptyset(&act.sa_mask);
8     act.sa_flags = 0;
9     if (signo == SIGALRM) {
11    #ifdef SA_INTERRUPT
12    act.sa_flags |= SA_INTERRUPT; /* SunOS 4.x */
13    #endif
14  } else
15    #ifdef SA_RESTART
16    act.sa_flags |= SA_RESTART; /* SVR4, 4.4BSD */
17    #endif
18  }
19  if (sigaction(signo, &act, &oact) < 0)
20    return (SIG_ERR);
21  return (oact.sa_handler);
22 }
```

### 使用 typedef 简化函数原型

2-3 `signal()` 的正常函数原型由于嵌套括号的层级而变得复杂。

```c
void (*signal (int signo, void (*func) (int)) (int);
```

为了简化这一点，我们在 `unp.h` 头文件中定义 `Sigfunc` 类型为

```c
typedef void Sigfunc(int);
```
