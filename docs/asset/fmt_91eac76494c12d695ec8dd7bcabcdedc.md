
虽然这看起来是显而易见的的，但我们的 `grep` 搜索一直都在使用正则表达式，尽管它们是极其简单的正则。正则表达式 `bzip` 意味着只有当文件中的行至少包含四个字符，并且在行的某处按顺序找到 b、z、i、p 这几个字符且中间没有其他字符时，才会发生匹配。字符串 `bzip` 中的字符都是字面量，即它们本身就代表其自身。

除了字面量外，正则表达式还可能包含用于指定更复杂匹配的元字符。正则表达式元字符包含以下内容：

^ $. [ { } - ? * + ( ) |

所有其他字符都被视为字面量，尽管反斜线字符在某些情况下用于创建转义序列，并允许元字符被转义从而被视为字面量，而不是被解释为元字符。

正如我们看到的，许多正则表达式元字符也是在执行扩展时对 shell 有意义的字符。当我们通过命令行传递包含元字符的正则表达式时，将其封装在引号内以防止 shell 尝试对其进行扩展。

### 通用字符

我们将看到的第一个元字符是点（`.`）字符，它用于匹配任何字符。如果我们将其包含在正则表达式中，它将匹配该字符位置上的任何字符。这是一个例子：

```
me@linux~}$ grep -h '.zip' dirlist.txt
zip2
bzip2
bzip2recover
gzip
gzip
funzip
gpg-zip
prezip
prezip
prezip-bin
unzip
unipsfx
```

我们在文件中搜索匹配正则表达式 `.zip` 的任意行。注意发现没有找到 `zip` 程序。这是因为在我们的正则表达式中包含元字符使得所需的匹配长度增加到四个字符，而 `zip` 名字只包含三个字符，因此它不匹配。此外，如果我们的列表中的任何文件具有扩展名 `.zip`，它们也会被匹配，因为文件扩展名中的点字符也会被“任意字符”匹配。

### 锚点

脱符号（`^`）和美元符号（`$`）在正则表达式中被视为锚点。这意味着只有当正则表达式出现在行首（`^`）或行尾（`$`）时，匹配才会发生。

```
[me@linuxbox ~]$ grep -h '^zip' dirlist*.txt
zip
zipcloak
zipgrep
zipinfo
zipnote
zipsplit
[me@linuxbox ~]$ grep -h '$zip$' dirlist*.txt
pzip
gzip
funzip
GPG-zip
preunzip
prezip
unzip
zip
[me@linuxbox ~]$ grep -h '^zip$' dirlist*.txt
zip
```

在这里，我们在文件列表中搜索位于行开头、行尾以及既在行开头又在行尾（即在行中独占一行）的字符串 `zip`。注意，正则表达式 `^$`（中间没有任何内容的开头和结尾）将匹配空行。

### 填字游戏助手

即使我们对正则表达式的知识有限，我们也可以做一些实用的事情。我的妻子喜欢填字游戏，她有时会就某个特定问题寻求我的帮助。比如“一个五个字母的单词，第三个是 j，最后一个是 r，意思是……？”这类问题可以让我思考。你不知道你的 Linux 系统包含一个字典吗？它是。看一眼 `/usr/share/dict/words`。我们可以使用 `grep` 来寻找符合标准的单词。

```
[me@linuxbox ~]$ grep '..j.r' /usr/share/dict/words
```

### 括号表达式与字符类

除了字面量外，正则表达式还可能包含用于指定更复杂匹配的元字符。正则表达式元字符包含以下内容：

^ $. [ { } - ? * + ( ) |

所有其他字符都被视为字面量，尽管反斜线字符在某些情况下用于创建转义序列，并允许元字符被转义从而被视为字面量，而不是被解释为元字符。

### 否定

脱符号（`^`）和美元符号（`$`）在正则表达式中被视为锚点。这意味着只有当正则表达式出现在行首（`^`）或行尾（`$`）时，匹配才会发生。

```
[me@linuxbox ~]$ grep -h '[^bg]' dirlist*.txt
bzip2
gzip
GPG-zip
prezip
prezip
prezip-bin
unzip
unipsfx
```

该字符不能是集合的成员。

### 传统字符范围

如果我们想构造一个找到每个大写字母文件的正则表达式，我们可以这样做：

```
[me@linuxbox ~]$ grep -h '[A-Z]' dirlist.txt
```

### POSIX 字符类

传统的字符范围是处理快速指定字符集问题的一种于理解且有效的方法。遗憾的是，它们并不总是有效。虽然我们到为止在使用 `grep` 时没有遇到任何问题，但在使用其他程序时可能会遇到问题。

（取决于 Linux 发行版的不同，我们将得到不同的文件列表，甚至可能为空列表。本示例来自 Ubuntu。）此命令产生了一个仅包含以大写字母开头的文件列表，但使用以下命令，我们得到了完全不同的结果（仅显示了结果的部分列表）：

```bash
me@linux~$ ls /usr/sbin/[A-Z]*
/usr/sbin/biosdecode
/usr/sbin/chat
/usr/sbin/chpasswd
/usr/sbin/chpasswd
/usr/sbin/chroot
/usr/sbin/cleanup-info
/usr/sbin/complain
/usr/sbin/console-kit-daemon
```

为什么会这样？这是一个长故事，但简单来说是：

当 Unix 最初开发时，它只认识 ASCII 字符，这一特性反映了事实。在 ASCII 中，前 32 个字符（0–31）是控制代码，如制表符、退格符和回车。接下来的 32 个（32–63）包含打印字符，包括标点符号和数字 0–9。接下来的 32 个（64–95）包含大写字母和更多的标点符号。最后的 31 个（96–127）包含小写字母和更多的标点符号。基于这种排列，使用 ASCII 的系统使用的*排序规则（collation）*如下：

```
ABCDEFGHIABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmmnopqrstuvwxyz
```

这与正确的字典顺序不同，字典顺序如下：

```
aABBcCcdeEeFfGhHIiJkLlMmNOoPpQqRrSsTtUvVwXyZz
```

Unicode 的流行扩展到了美国之外；人们对支持美国英语中未发现的字符的需求日益增长。ASCII 表被扩展为使用完整的 8 位，添加了字符 128–255，这容纳了许多语言。为了支持这一点，POSIX 标准引入了一个名为*区域设置（locale）*的概念，可以通过调整该设置来选择特定区域所需的字符集。我们可以使用以下命令查看系统的语言设置：

```bash
me@linux~$ echo $LANG
en_US.UTF-8
```

有了此设置，符合 POSIX 标准的应用程序将使用字典排序顺序而非 ASCII 顺序。这解释了之前命令的行为。在字典顺序中解释的字符范围 [`A-Z`] 包含了除小写 a 以外的所有字母；这里是我们的结果。

为了部分解决这个问题，POSIX 标准包含许多字符类，这些类提供了有用的字符范围，如表 19-2 所示。

## 表 19-2：POSIX 字符类

| 字符类 | 说明 |
| --- | --- |
| `[:alnum:]]` | 字母数字字符。在 ASCII 中，等于：[`A-Za-z0-9`] |
| `[:word:]]` | 与 `[:alnum:]` 相同，增加了下划线 (`_`) 字符。 |
| `[:alpha:]]` | 字母。在 ASCII 中，等于：[`A-Za-z`] |
| `[:blank:]]` | 包含空格和制表符。 |
| `[:ctrl:]]` | ASCII 控制代码。包括 ASCII 字符 0 到 31 以及 127。 |
| `[:digit:]]` | 数字 0 到 9。 |
| `[:graph:]]` | 可见字符。在 ASCII 中，它包括字符 33 到 126。 |
| `[:lower:]]` | 小写字母。 |
| `[:punct:]]` | 标点符号。在 ASCII 中，等于：[!"#$%&'()*+,-./:;<=>@[\\]^_\`\|~] |
| `[:print:]]` | 可打印字符。`[:graph:]` 中的所有字符加上空格字符。 |
| `[:space:]]` | 空白字符，包括空格、回车、换行、垂直制表符和分页符。在 ASCII 中，等于：[` \t\n\f`] |
| `[:upper:]]` | 大写字母。 |
| `[:xdigit:]]` | 用于表示十六进制数字的字符。在 ASCII 中，等于：[`0-9A-Fa-f`] |

即使有了字符类，仍然没有方便的方法来表示部分范围，例如 [`A-M`]。

使用字符类，我们可以重复列出目录并看到改进后的结果。

```bash
[me@linuxbox ~]$$ ls /usr/sbin/[[:upper:]]*
/usr/sbin/NetworkManagerDispatcher
/usr/sbin/NetworkManager
```
