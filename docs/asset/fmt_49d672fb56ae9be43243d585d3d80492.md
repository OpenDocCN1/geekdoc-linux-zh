
由于我们在一个相当底层的系统软件中发现了一个问题和潜在解决方案，与作者合作解决该问题是一个好主意。我们至少必须提交一个错误报告，以便作者知道问题的存在。提交我们用于发现问题的测试将有助于他重现问题，并希望修复它。在这种情况下，我们将向 Red Hat 的 bug (`zilla.redhat.com`) 跟踪系统添加一个错误报告。（大多数发行版都有类似的跟踪系统。）我们的错误报告描述了我们遇到的问题以及我们发现的可能解决方案。

到达 bugzilla 时，我们首先搜索 `prelink` 的错误报告，查看是否其他人报告过此问题。在没有发现的情况下，我们查看列表 12.22 中的错误报告并等待作者或维护者的响应并修复 bug。

### 列表 12.22

```
From Bugzilla Helper:
User-Agent: Mozilla/5.0 (X11; Linux i686; en-US; rv:1.6) Gecko/20040510

Description of problem:

在快速模式下运行时，prelink 不缓存某些二进制文件无法预链接这一事实。结果是，即使在快速模式下运行，它也会重新扫描这些文件。这导致磁盘剧烈工作并显著减慢整个系统。

有三种可执行文件在快速模式下重试：

- 1) 静态二进制文件
- 2) Shell 脚本
- 3) 依赖于不可链接二进制文件的文件。（例如 OpenGL）

对于 1 & 2，如果 prelink 缓存这些可执行文件无法预链接的这一事实，并在快速模式下检查它们的 ctime & mtime，如果它已经知道它们无法预链接，则甚至不尝试读取它们，那将很好。

对于 3，如果 prelink 能记录导致 prelink 失败的库（以 OpenGL 情况为例），并记录下来，那将很好。
```

## 12.9. 测试解决方案

由于我们没有在 `prelink` 代码中解决问题，而是报告了一个 bug，因此我们无法立即将修复后的 `prelink` 时间与我们的原始基准进行对比。然而，如果作者或维护者能够实施建议的更改，或者找到更好的优化方法，我们就可以可以在更新版本发布时检查其性能。

## 12.10. 章节总结

在本章中，我们从一个运行异常的系统开始，使用性能工具确定了哪一个子系统被过度使用（`vmstat` 显示了磁盘子系统），以及哪个组件导致了问题（`prelink`）。然后，我们调查了 `prelink` 应用，通过 `strace` 确定它为什么会使用如此多的 I/O。我们在 `prelink` 的缓存模式下发现，它本应该大幅减少磁盘 I/O。我们调查了缓存模式的性能，发现它消除磁盘 I/O 的效果并没有想象中那么大，因为它试图预链接那些无法被预链接的文件。随后，我们模拟了一个避免尝试预链接无法预链接文件的缓存，并验证了它显著减少了快速模式下 `prelink` 的磁盘 I/O 量和运行时间。最后，我们向 `prelink` 的作者提交了错误报告，希望作者能意识到问题并将其修复。本章是 Linux 性能猎寻的最后一章。

在下一章（也是最后一章），我们将观察 Linux 性能和性能工具的更高层次。我们将回顾本书涵盖的文档方法论和工具，并查看 Linux 性能工具某些亟待改进的领域。

# 第13章 性能工具：下一步是什么？

本章包含了对当前 Linux 性能工具现状的思考、哪些仍然需要改进，以及为什么 Linux 目前是进行性能调查的绝佳平台。

读完本章后，你应该能够：

- 理解 Linux 性能工具箱中的缺陷，并理解一些理想的解决方案
- 理解 Linux 作为性能调查平台的优势

## 13.1. Linux 工具的现状

本书将介绍当前的 Linux 性能工具、如何单独使用它们，以及如何结合使用它们来解决性能问题。与 Linux 的各个方面一样，这些性能工具也在不断演进，因此在调查问题时，查看性能工具的 `man` 页（手动帮助页）或文档以确定其用法是否发生变化总是一个好主意。性能工具的基本功能很少改变，但通常会添加新特性，因此查看特定工具的最新发布说明和文档是有帮助的。

## 13.2. Linux 还需要哪些工具？

在我们遍历 Linux 工具时，我们发现整体性能调查功能存在一些缺陷。这些缺陷是内核局限性的结果，而另一些则仅仅是因为没有人编写工具来解决这些问题。然而，填补这些缺陷将使得追踪和修复 Linux 问题变得容易得多。

### 13.2.1. 缺陷 1：性能统计数据是分散的

一个显而易见的缺陷是 Linux 没有工具能为特定进程提供相关的性能统计数据。在原始 UNIX 中，`ps` 是为了填补这个缺陷，而在 Linux 上，它相当良好，但没有涵盖其他商业实现所提供的所有统计数据。某些统计数据对于追踪性能问题无价的——例如，`inblk`（入 I/O 块）和 `outbl`（出 I/O 块）指示了磁盘 I/O 的使用量；`vcsw`（自愿上下文切换）和 `incsww`（非自愿上下文切换）通常显示应用程序正在使用的网络 I/O 量。

### 13.2.2. 缺陷 2：缺乏可靠的调用树

下一个问题是 Linux 缺乏一种为进程提供完整调用树的工具。虽然像 `perf` 和 `system` 等工具提供了一些信息，但它们通常难以使用，或者无法提供执行流的全景。

### 13.2.3. 缺陷 3：I/O 归因

最后一个缺陷是缺乏一种能将 I/O 操作准确归属于特定进程或线程的工具。这使得识别 I/O 相关瓶颈的根源变得困难。

## 13.3. Linux 性能调优

尽管存在上述缺陷，Linux 仍然是优化性能的理想场所。它是为开发者编写的，因此它对性能调查人员非常友好。Linux 有几个使其变得伟大的特性：

### 13.3.1. 可用的源码

首先，开发者可以访问整个系统的大部分（如果不是全部）源代码。在追踪似乎出现在你代码之外的问题时，这是无价的。在没有源码的商业 UNIX 或其他操作系统上，你可能需要等待供应商调查问题，而且你无法保证他们会修复。然而，在 Linux 上，你可以自己调查问题并弄明为什么会发生性能问题。如果问题在你的代码之外，你可以修复它并提交补丁，或者直接运行修复后的版本。通过阅读 Linux 代码的源码，如果你意识到问题出在你的代码中，你就可以修复它。无论何种情况，你都可以立即修复，而不会受限于等待他人的。

### 13.3.2. 轻松接触开发者

Linux 的第二个优势是相对容易找到并联系特定应用程序或库的开发者。与大多数专有操作系统相比（在后者很难确定哪位工程师负责某段特定代码），Linux 开放得多。通常，特定软件的开发者的姓名或联系信息随软件包一起提供。接触开发者允许你询问关于特定代码的行为、运行缓慢的代码意图是什么，以及执行给定的优化是否安全。开发者们通常非常乐意为此提供帮助。

## 13.4 章节总结

在本章中，我们研究了 Linux 性能工具集存在不足的几个领域，并提出了一些理想的解决方案。我们还讨论了为什么 Linux 是进行性能调查和优化的良好平台。

改进 Linux 性能取决于你，这位读者。Linux 性能和 Linux 性能工具的改进机会随处不在。如果你发现了一个困扰你的性能问题，请修复它，或者将其报告给开发者并与他们合作修复。无论哪种方式，都不会再受到该问题的影响，整个 Linux 社区都从中受益。
