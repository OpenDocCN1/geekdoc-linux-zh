
然而，如果 Unix 在许多方面优于其他系统，那么它仅仅证明了“差”比“正确”或“错误”的东西有更好的生存机会。因为 Unix 和 Linux 已经展现了在新技术不断使现有技术过时的世界中持续存在的非凡能力。

计算机世界存在一种学派，认为所有合理的设计应该具有四个特征：简单性、正确性、一致性和完整性。设计应该是简单的，在所有可观察的方面都是正确的（无 bug），在整个过程中保持一致，并在方面上是完整的，即它们必须涵盖人们可以预期的所有情况。

# 7.10 分层思考

Unix 成功的原因之一是它在许多方面一直被认为比其他系统差。它适用于任何严肃的工作，因为这类任务通常留给工业级操作系统。Unix 通常占据硬件配置的较低层次——它缺乏大型主机的蛮力，但对于平凡的工作已经足够了。由于微计算机通常用于不重要的任务，对于科学界来说，在微计算机上投入大量资金是不现实的。当工作站出现时，这种趋势被进一步放大。只需迁移现有系统的成本就变得更低。

今天，要找到比 Linux 上提供的免费软件更好的商业版本并不困难。大多数免费软件缺乏良好商业软件包的功能和润色。然而，免费应用程序的增长轻易超过了商业软件包。今天，一些供应商和行业联盟正在努力让 Linux 。通过这样做，他们希望它能失去“差一点更好”的特性并最终被认真对待。这可能是一个致命的错误。如果 Linux 变成一个在所有方面都真正更好的东西，那么它面临着灭绝的风险。在变得更完善的过程中，它需要牺牲简单性来追求完整性。一旦这种情况发生，可能会出现一种比目前的 Linux 系统更能体现 Unix 原则的新操作系统。

为了她的图片文件。没多久，她意识到自己可以在目录中创建目录，这样她就可以将画作组织在嵌套五层深处的整洁电子文件夹中了。

她学会了层次化思考。

这是一个简单的想法，但像 Unix 中的许多事物一样，它具有深远的意义。虽然在今天很多人看来，文件系统应该分层布局是理所当然的，但过去并非如此。早期的操作系统通常将系统相关文件放在一个目录中，并将用户文件放在目录树的同一水平。在那时，人们还看不到层次化思维的好处。

大多数现代操作系统都对文件和目录进行层次化组织，Unix 与其它系统的细微区别在于，引用深度嵌套在多级目录中的文件时的语法。Unix 方便地使用“=”字符来分隔文件路径的各个部分。因此：

```
/usr/a/users/garcanz/.profile
```

表示文件“profile”位于目录“garcanz”之中。“garcanz”目录位于“users”目录之中，以此此类推，直到目录“/”，它就是“根root”目录。Unix 文件系统的层次结构本质上是一棵倒立的树，根目录位于分支（目录）和叶子节点（文件）之上。

Unix 也对其他组件进行层次化组织。例如，Unix 中的任务（被称为进程）占据树形结构。进程号 1 的 `init` 进程是树的根。所有其他进程（包括用户会话）都是 `init` 或其子进程的后代。进程通过创建自己的副本并将其标记为子进程的父进程来产生子进程。就像现实生活中一样，子进程继承父进程的属性。

X Windows 系统用户界面库是层次化方法的另一个例子。它使用一个资源管理器，允许其他用户界面对象（如按钮和菜单）层次化地从其他用户界面对象继承属性。这一强大的想法让用户自定义应用程序多个组件中的字体、颜色和其他属性成为可能。

微软也对文件和文件夹进行层次化组织。然而，用户必须始终意识到物理驱动器或分区（例如 `C` 盘）。相反，Unix 的根目录代表了树的顶端，包含了系统上的所有目录，而不是为每个物理驱动器设置单独目录。Unix 用户不需要担心系统上（通常复杂的）物理驱动器和分区布局。在 Unix 下，一切都是一棵大树。

除了 Unix 内部的实际用途外，层次化思考还有一个哲学原因。没有人能否认，自然界大部分也是层次化有序的。用一句老话来说，从小橡果长出的高大橡树会产生它自己的橡果。那些橡果将长出更多的橡树。这种循环自远古以来一直在重复。同样，在人性中，父母生育孩子，孩子随后成长为森林中的树木。由于 Unix 的层次化组织镜像了自然，这可能是它是一个良好方法的好信号。

在本章中，我们探索了 Unix 哲学的 10 个次要原则。并不要求整个 Unix 或 Linux 社区的所有成员都同意这里讨论的所有内容。这并不重要。Unix 社区像自由世界的其他部分一样，允许很大程度的个人表达和偶尔的分歧。

这些思想中的一些也可以在其他操作系统找到。Unix 是这些原则的源头还是接收者尚不清楚。尽管如此，许多 Unix 用户和程序员无论有意还是无意都在遵循这些原则。Linux 社区也是如此。

# 让 Unix 做好一件事

我们目前为止涵盖的大部分都是抽象的。虽然我们已经看到 Unix 哲学每一条原则背后都有实际原因，但你们中的某些人可能仍然认为它们在现实世界中不起作用。“小即是美”固然，但大任务呢？真的可能从一组小程序构建出一个完整的应用程序吗？没有 GUI 的程序能发挥有用作用吗？这些都是合理的问题。你将在本章中找到它们的答案以及更多。

我们将查看 MH，这是一种由兰德公司（RAND Corporation）开发的邮件处理应用程序。它由一系列程序组成，这些程序结合在一起赋予了用户处理电子邮件巨大能力。作为一个复杂的应用程序，它表明不仅可以从较小的组件构建大型应用程序，而且这种设计实际上是更好的。

如果一个程序是有价值的，它就会从一个平台迁移到另一个平台。MH 就是如此。原始想法保持不变，但多年来的新版本增强了原始功能。在今天的 Linux 发行版中，New MH (`NMH`) 已在很大程度上取代了 MH。`NMH` 整合了 MH 的所有主要功能，最重要的是——遵循了 MH 的原始哲学。为了讨论起，我们将涵盖 MH 背后的思想，并承认这些思想非常适用于 `NMH`。

在 Web 邮件出现之前，有两个程序——`/bin/mail` 和 Berkeley Mail——多年来一直专门用于在 Unix 下处理电子邮件。尽管 Berkeley Mail 被频繁使用，但这两个程序在 Unix 哲学方面都是糟糕的范例。它们都使用 CUI（命令行界面），作为过滤的能力有限，而且在 Berkeley Mail 的情况下，几乎不能被认为是小程序。它们都没有专注于“做好一件事”，而是选择在单个用户界面中整合一系列邮件相关功能。

MH 提供了等同于 `/bin/mail` 和 Berkeley Mail 的功能。它是小程序的集合，每个程序执行一个其他程序无法提供的功能。以下是命令的部分列表：

MH 使用文件夹集合来组织用户的邮件。它将邮件存储为单独的文件。收件箱（inbox）有一个特殊用途：系统邮箱的内容首先通过 `inc` 命令放入收件箱。一旦邮件移动到收件箱，就可以由命令进行选择和操作。

正如你从列表中看到的，MH 提供了你对综合电子邮件应用程序预期的所有功能。`scan` 命令显示当前文件夹中范围内消息的发送者、日期和主题行。`show`、`next` 和 `prev` 命令显示所选消息的内容、当前文件夹中的下一条消息或上一条消息。`comp` 和 `repl` 允许你创建新的邮件消息或回复现有的消息。

MH 与其他邮件程序的主要区别在于，你可以从 shell 提示符级别调用任何邮件处理函数。这赋予了 MH 巨大的灵活性。每个函数都是独立的命令，你可以像调用 Unix 下任何其他命令一样调用这些函数。

命令可以在 shell 脚本中使用过滤器。例如，`scan` 的输出可以“管道”到 Unix `grep` 搜索命令，以快速定位特定发送者的邮件。如果文件夹包含大量消息，导致 `scan` 的输出刷出了屏幕，可以将输出管道到 Unix 的 `more` 命令，允许用户一次查看一个列表。如果用户想查看最后五条消息，`scan|tail-5` 就能解决问题。
