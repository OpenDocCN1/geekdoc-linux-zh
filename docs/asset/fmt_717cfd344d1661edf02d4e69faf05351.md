
专利的集体方法也有助于鼓励开源和专有软件开发。这就是为什么公司在反垄断法的限制内，要开发受专利限制的行业标准。开放标准对于开源成功的重要作用是本书下一章也是最后一章的主题。

## SCO 对阵开源

任何读过之前关于诉讼地位（standing）章节的人都会很快发现“SCO vs. 开源”这一标题的不协调。SCO 是 The SCO Group, Inc. 的缩写，一家德特拉华州公司。开源是一种软件开发、业务和许可模式。开源不具备作为诉讼中被告的诉讼地位。无论是 SCO 还是任何其他原告，都不就任何值得诉讼的诉由起诉一个整个运动——特别是一个深根于知识产权和合同法的运动。

在写此文时，SCO 集团是几起一起针对某些软件公司（包括 IBM、Novell 和 Red Hat）的诉讼的当事人，涉及其旗舰开源产品 Linux 的知识产权。

最初，SCO 的起诉状指控它已向 IBM 许可了某些专有软件，而 IBM 随后不当地贡献了开源 Linux。原始诉讼以传统的违约条款为框架，是一场关于 IBM 和 SCO 之间协议的争议，该协议据要求 IBM 维护其许可软件的商业秘密。IBM 否认了所有指控，并反诉 SCO，指控其违约和专利侵权。SCO 随后扩大了起诉状，包含了对 Linux 所获许可的 GPL 的指控。

然后 Red Hat 起诉 SCO，指控其存在不正商业行为等商业转折。最后，SCO 和 Novell 就 SCO 的前身继承人从 Novell 处购买 UNIX 权利的原始合同条款产生了争议。

当你读到这本书时，SCO 诉讼可能已经得到解决，在这种情况下，请使用以下观点来评估我的预见性：SCO 案件是一场法律混乱，是公司花费数百万美元律师费来捍卫其知识产权和合同权利，并对巨额赔偿索赔进行辩论的不机会。它们并不直接影响开源。

## 开源许可

以及全球数以千计的程序员，我们并不归 SCO 所有。SCO 也无法拥有 Linux 中体现的未专利构想。根据我对操作系统历史和演进（包括 UNIX 和 Linux）的了解，对我来说，Linux 的大部分部分是 SCO 软件或其衍生作品是不可想象的。大多数 Linux 专家都向我保证，当这场诉讼结束时，法院将判定 SCO 对 Linux 的知识产权几乎没有或完全没有所有。

SCO 的诉讼揭示了一些有趣的开源现象。SCO 分发了 Linux 开源软件，即使在 SCO 对 IBM 发起首次诉讼后，被许可者仍可以通过 SCO 的网站根据 GPL 获得 Linux。我没有听说过任何重要的案例——而 Linux 软件恰恰是如此——即在商业上非常成熟的被许可者被允许放弃其对争议软件的自身的许可。

SCO 公开挑战 GPL 宪性的论点特别引人入胜（参阅 2003 年 12 月 4 日由 SCO 总裁兼首席执行官 Dar McBride 写的公开信）。如果美国法院允许一家公司对其自身的许可协议提出宪性挑战，那将是真正令人兴奋的新闻。

但假设法院最终从整个开源现象中抽身，并在具有诉讼地位的当事人提出的合法诉讼背景下询问：“这种构建开源软件公共领域的许可方案是否符合宪法？是否应该允许许可方以这种方式颠倒著作权，将软件许可以以以贡献的互惠义务为条件？”

完全没有法律依据认为这种方案是违反宪法的。许可方可以对其知识产权随心所欲，并为其使用设定条件，这是一个基本的法律原则。

公众对 SCO 案件的关注证明了我在本章中暗示的观点。关于开源软件的诉讼将是罕见的；如果经常发生，公众现在对 SCO 那些歇斯底里的诉讼主张早已厌了。SCO 诉讼的独特性以及其数十亿美元的损害赔偿请求，使其脱颖而出。

针对 Linux 的 SCO 诉讼也标志着开源运动的成熟，它终于成为了一个足够大的现象，以至于其软件成为了大型诉讼的对象。简单来说，开源软件现在已经到足以被起诉。开源软件特别是 Linux 的流行和成功不可避免地引发了诉讼，因为涉及到重要且巨大的经济利益。

SCO 诉讼是一个异常现象。这是一场大型诉讼，但大多数专业律师认为这是特定公司之间的一个小问题。它最终将得到解决——Linux 和开源将继续演进。这也会过去的。

许多开源倡导者私下渴望出现测试案例，以便法院能够清晰地阐述开源许可法律。到目前为止，此类案例很少。开源双方主要争论的是违约、商标侵权、偶尔的专利侵权，以及是否创建了衍生作品。大多数争论都是通过非正式方式解决的，大多数文明化国家的几乎所有商业纠纷都是如此。如果开源许可方和被许可者可以通过开源慷慨的精神解决分歧，他们为什么要互相起诉呢？

很难想象会有开源许可方和被许可者就自由软件问题进行诉讼的重要案例。

只要开源项目作为知识产权的负责任的护护人，仔细跟踪他们接收的软件和他们创建的软件，那么被许可者就可以依靠开源规则下该软件的持续可用性。只要被许可者遵守他们接受的软件的许可条件，就没有理由担心它会通过诉讼被夺走。

# 开源标准

## 定义开源标准

我参加的第一场关于开源的演讲实际上本应该是关于开源标准的。一个来自一些主要软件公司的代表小组正试图为观众定义开源标准。他们无法对一个定义达成共识，并且不断将开源标准与开源混为一谈。

那时我已经开始与开源倡议（Open Source Initiative）合作，并且对开源的定义感到自得自足。我们有一份已发布的《开源定义》可以依靠（参见第 1 章）。我理解开源与软件自由之间的关系。但我完全不知道小组成员所说的“开源标准”到底是什么意思。它与软件自由有关吗？

那时我相信，即使这个小组没有向世界解释这一点，至少全球范围内受推崇的标准必须找到了一种让这些标准在全球范围内被“自由实现”的方法。事实证明，我们都早了几年。直到 2002 年，世界维网联盟（W3C）才发布了一份真正与开源兼容的开源标准有效定义。我将在本章的后半部分全文重印该定义。

标准由行业协会开发，在反垄断法的指导下制定，通过合作发布关于产品应如何相互操作的规范。共同的设计或实现对于防止产品无法相互工作而碎片化开发通常至关重要。每家参与公司都应使其产品满足约定的规范——并鼓励每公司寻找自己的方法来改进规范，并将自己的产品与竞争对手的产品区分开来。正如惠尔罗惠的 Scott Peterson 曾向我描述的那样：“公司在标准上运行，在实现在竞争。”

我们离开行业标准就无法生存。标准允许一个制造商的电话在其他制造商的通信设备上工作。所有浏览器（理论上）如果符合行业标准，就可以相同地显示网页。来自不同软件供应商的电子邮件系统可以交换邮件。没有标准，这真的将是一座巴别塔。

## 开源规范

假设有人写了一本书教你如何计算所得税，这是对你必须执行的年度流程的规范。你在当地图书馆读了这本书。你在计算机软件中实现了该规范，创建了你自己的受版权保护的作品。你没有在软件中复制这本书，可能在少数几个地方写了类似“从你的年度总收入中减去扣除额”之的话，并将其翻译成软件中的代码。你是否构成了著作权侵权？

口语中，我们经常说“你复制了规范”。但这与我在第 2 章解释的“复制”定义几乎没有关系。我们想要表达的是：“你阅读并理解了规范关于税收规则和程序的说明，然后从零开始，基于你学到的知识编写了你的软件。”如果你复制了任何东西，那也是书籍的基础思想——我已经描述过的“不可复制的主体”。

换句话说，你在实现标准时进行的复制并不一定是著作权侵权。你并没有通过直接复制规范来获取规范作者受版权保护的知识产权。

当然，规范本身（即标准组织出版的书）是有版权保护的。该规范符合美国著作权法对“原创作品”和“复制”的定义（第 101 节）。没有版权所有者的许可，不能复制规范。（`17 U.S.C. § 106`）。

仅仅因为它描述了开源标准并不意味着你可以复制或分发该规范。你必须单独查看规范许可以确定是否可以这样做。（在某些管辖区，对于纳入法律并执行的规范，这不再适用。）禁止人们在不向许可方支付许可的情况下阅读规范，或以任何方式限制其所含信息使用的规范许可，都不是开源规范许可。它与开源原则 #1 不兼容。此类标准不是开源标准。

## 开源许可

描述开放标准的发布规范（类似于开源软件）并不需要以零价格分发。（参见开源原则第 2 条。）标准组织可以且确实销售其规范的副本。由于大多数标准组织的目标是实现其规范的实施最大化，因此它们通常不会对其文档收取过高费用——或者根本不收费。

某些标准组织通过出售规范副本来收回成本，当成本合理时，大多数人愿意为官方打印版付费。无论开放标准规范的定价如何，也无论单份规范的价格是多少，任何数量的人都可以阅读和复制它。同样，任何数量的人都可以编写该规范的软件，而无需向该规范的版权所有者支付任何额外费用。

## 通过版权限制强制标准

某些标准会成为每个人必须遵守的法律。例如，在美国，有统一的代码来规范建筑、电气和水暖工程行业。承包商不得建造违反这些标准的设施。

许多州和地方法律强制执行行业标准，但并未指明具体的标准内容；它们通过引用由标准组织发布的某些规范将标准纳入其中。这些标准具有法律效力，必须遵守。美国法院直到最近才处理了标准组织是否可以就公众复制法律强制执行的行业标准的权利收取费用的问题。在某些司法管辖区，不再允许收取复制法律的版税。

一些公司和其他非政府组织也希望控制行业标准。由于行业标准没有被立法机构作为法律采用，它们不能像建筑、电气和水暖规范那样被强制执行。标准知识产权的私有所有者可以通过合同法以及版权、专利和商标法的应用，通过对标准规范许可权的控制，私下强制执行其标准。

如下所述，版权、专利和商标许可与开源及开放标准是兼容的。

## 测试集的许可：Open Group 许可

Open Group 是一个标准组织，主要负责促进与 UNIX 相关的标准等内容。它还拥有在全球范围内注册的 UNIX 认证标志，并管理一个认证其他公司 UNIX 实现的计划。符合 Open Group 规范的 UNIX 版本可以携带 UNIX 认证标志。

认证需要测试。根据大多数国家的商标法，认证机构必须确保其认证标志仅用于经过测试并批准的产品。否则，认证标志可能会丢失。认证机构（例如 The Open Group）负责验证认证货的质量。

Open Group 通过发布的测试套件（用于测试 UNIX 版本的程序）来实现这一点。如果测试套件在待认证的 UNIX 实现上成功运行，则该 UNIX 版本即获得认证。

Open Group Test Suite License 适用于测试套件本身，即软件包（Package）（请访问 `www.opensource.org` 获取此许可副本。）该软件包是开源的。该许可并不要求针对该软件包进行测试的 UNIX 实现本身必须是开源。

Open Group Test Suite License 试图充分控制测试软件中受版权保护的元素，以保护 Open Group 的认证标志。许可的前言称为“艺术性控制”，但此许可实际上具有更具实际意义的目标。Open Group 主要关注测试对于确保合规性的重要性：

由于这些是衡量合规性的基准标准，我们认为测试工具的完整性非常重要。为了保留此测试包现有合规模式的完整性，并允许该包修改后版本的接收者运行原始测试模式，本许可要求保留原始测试模式。（Open Group Test License Preamble。）

本许可符合开源原则。许可者可以复制、修改和分发软件包的副本。这些是重要条件：

- 你必须复制此软件包标准版本（Standard Version）中的所有原始版权声明和相关的免责声明。（Open Group Test Suite License 第 1 节。）

- 你必须在每个更改的文件中插入醒目通知，说明你如何以及何时更改了该文件。（Open Group Test Suite License 第 3 节。）

- 你必须重命名任何非标准的可执行文件和测试用例，并提供独立的说明页，清晰记录其与标准版本的差异。（Open Group Test Suite License 第 3 节。）

- 当你分发你的版本时，必须将你的修改与其相应的标准版本可执行文件和测试用例一起提供。（Open Group Test Suite License 第 4 节。）

通过对其测试软件包使用这种开源许可，Open Group 能够控制其自身认证标志的标准，同时赋予所有人创建软件包衍生作品的软件自由。这些衍生作品并不要求符合标准，但如果它们不符合，就不能被称为“标准版本”。

> *标准版本*（Standard Version）指未被修改的、或根据版权所有者的意愿进行修改的软件包。（Open Group Test Suite License Definitions。）

只有成功通过标准版本测试的 UNIX 实现才能被 Open Group 认证并得称为 UNIX。

## 震慑分支：Sun 的 SISL

Sun Microsystems 希望有一种更稳健的方法来防止标准被分叉。*分叉*（Forking）是开源社区使用的一个术语，用于描述协作项目分裂为两个或多个不合作的独立项目的情况。结果是一个机会或一个问题，这部分取决于你从哪个项目分叉出来，部分取决于分支项目软件在市场上的最终成功。允许行业标准测试套件产生衍生作品的风险之一是竞争对手偏离标准。Open Group 通过要求对此更改进行通知和记录避免了这个问题，并禁止将衍生作品称为“标准版本”。但这仅部分有效。公司可以偏离标准或添加新需求，而无需将这些贡献回给开放标准。

开源许可无法禁止分叉。（参见开源原则第 3 条，该原则规定了创建衍生作品的自由）。但许可可以对此类衍生作品设定条件，包括互惠性条件。

Sun 行业标准源码许可（ISSL）在很大程度上借鉴了 MPL，其重点是文件而非更广泛的衍生作品概念。（ISSL 的全文可以在 `www.opensource.org` 获取。）你会认出 MPL 的大部分结构，但它在互惠性条件上增加了这一有趣的补充。

你创建的修改必须符合在你发布贡献者版本前 120 天内生效的标准机构所规定的所有要求。如果修改不符合此类要求，你同意发布：

- (i) 导致你的修改实现的任何协议偏差以及修改的参考实现，或

- (ii) 以源代码形式发布你的修改，并根据相同的条款向所有第三方提供任何偏差和参考实现或修改

在首次向客户交付修改版本后的三十（30）天内，以免特许费的基础上授予此项许可。（SISSL 第 3.1 节。）

与开源许可证中所有的互惠条款一样，SISL 要求被许可者提供的权利不超过许可方所给予的权利。它允许对标准进行分叉，但任何破坏与标准兼容性的修改都将以互惠的方式供所有人采纳。它还对衍生作品的创建施加了时间限制，允许标准组织——在本例中为 Sun 公司——有机会重新创建被尝试分叉的版本。

Sun 对其版本的 Open Office 软件的文件格式和编程接口规范使用 SISSL 许可证，对 Open Office 软件本身使用 GPL 许可证。

## 开放标准中的专利

当有人拥有实现开放标准规范所需的专利时，会发生什么？你可能记得，专利所有者无论你是如何学会制造该技术的，都可以阻止你制造、使用或出售其专利发明，即使该发明是你随后自己发明的。

如果有人拥有实施某项开放标准所需的专利权利，你将需要获得专利所有者的许可才能在你自己的软件中使用该标准。你在软件中实施该标准的自由受专利所有者许可条款的限制。

标准组织意识到了这一点。这就是为什么他们近年来专注于设计与开源兼容的专利政策。开放标准的关键在于一种专利政策，这种政策鼓励标准在各种软件中（包括开源软件）被广泛采纳。

实施行业标准的专利声明可能会突然出现。关于这种情况的故事通常是关于一个古怪的科学家，他在自家车库里工作时，秘密发明了并可能试图推迟一项对贵贵技术重要的专利的发布。在标准颁布后，标准组织或任何其他人都无法防止专利局颁布此类“突袭性专利”。

但相比之下，许多更及时、更重要的专利是由参与标准组织的同一公司所拥有的。毕竟，比那些在该特定行业领域拥有专门知识的公司，还有谁更有可能在特定行业技术上申请专利呢！这些公司拥有人才和资源来创建围绕标准领域的大量专利。

标准组织需要方法保护其成员免受其他私有专利的影响。最新的技术是开发一致的专利政策，以限制成员执行私有专利的选项，这是解决行业标准专利问题的重要解决方案之一。W3C 的专利政策是开放标准这一新领域的者；W3C 专利许可在本章的最后一节中描述。

## 合理且无视

大多数标准组织要求其成员同意根据“合理且非歧视的条款”对其实施标准所需的所需的任何专利权利进行许可。以下是思科（Cisco）向一个标准组织互联网工程任务组（IETF）提供的典型许可授予：

Cisco 拥有一个与 `draft-ietf-mobileip-nat-traversal-06.txt` 主题相关的专利申请，“使用 UDP 隧道进行移动 IP NAT/APT 穿越”。如果 IETF 采纳与此主题相关的标准，且任何已发布的 Cisco 专利的任何权利对于实施该标准是必要的，任何一方都能够从 Cisco 获得许可，在合理、非歧视且互惠的条款下使用任何此类专利，以实施并完全符合该标准。（来自 `www.ietf.org`。）

此信中的词汇是合理且非歧视的。你在全球大多数面向标准组织的专利授予中都能看到这些词。这只是一个例子；Cisco 和 IETF 并不独特。我重复这封信并不是在针对他们。

“合理”一词无法精确定义。它始终取决于特定案件的事实。例如，汽车或房屋没有所谓的合理价格，对于什么构成合理的保修条款没有共识，也许对于某些公司来说，根本没有合理的方法接受互惠条款。对于居住在非洲或欧洲的开源程序员，诉讼的合理管辖权和审判地是什么？

“非歧视”一词也模棱两义。它是否意味着富人和穷人不会受到歧视？（除了接近零的价格外，很难设定任何不会歧视至少一部分穷人的价格。）还是说，这种不予歧视的承诺仅延伸到法律已经禁止的歧视形式，如年龄、种族和性别？正如某些对 GPL 和其他互惠开源许可证所抱怨的那样，所有的互惠条款难道不是对那些不想或无法接受互惠义务的人具有歧视性吗？

在实践中，“合理且非歧视”的承诺仅仅意味着每个人为相同的专利许可权利支付相同的价格，并遵守相同的条款和条件——即使这些条款是苛刻且与自由软件不兼容的。这不是开源，就像说微软 Windows 是开源的因为每个人都支付相同的价格并同意相同的最终用户许可协议一样。正如我在书中所提到的，魔鬼隐藏在必须同意的详细许可条款和条件中。

Cisco 信中的另一个模棱两义的短语是“具有互惠性”。标准实施者或用户所预期的互惠许可范围在 Cisco 揭示准确许可条款之前是未知的。在这种情况下，互惠是良性的吗？

当一家公司对其专利发出关于合理且非歧视许可的模糊承诺时，开放许可方很难获得慰藉。我们需要确保专利许可实际上与开源兼容。
