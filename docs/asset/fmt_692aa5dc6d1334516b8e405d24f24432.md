
到目前为止讨论的是 UNIX 网络相关问题的不同方面。本章涵盖了足够的内容，让读者了解 UNIX 网络配置和运行的复杂性。在本节中，你将看到一套可以对 UNIX 网络进行故障排除的工具集；这些工具适用于网络安装后的早期安装和配置阶段以及网络成熟阶段。

正如你的经验将证实的那样，将网络运行维持在合理的性能、可靠性和可用性水平上，可能是维护计算环境最具挑战性的方面之一。网络问题是足够多样化的，以至于网络管理员别无选择；一套全面的故障排除工具集需要根据对通信协议和应用协议行为的最细微细节的熟悉，进行持续的教育，并随着技术的变化不断更新技能。需要注意的是，网络故障排除需要持续的教育；知识和技能的结合应该应用于一种方法论，旨在高效地识别和解决网络中检测到的问题。

## 故障排除方法论

总的来说，故障排除通过三个阶段的活动：

- 1. 信息收集 - 2. 制定并执行针对特定问题的故障排除计划
- 3. 记录问题

网络故障排除中信息收集效率主要取决于维护一份最新的网络文档。文档是网络管理员最讨厌的部分，只有在需要时才会被重视。将文档记录过程视为主动故障排除中的一项战略计划。无论这项工作在你看来多么枯燥，永远不要在它的质量或准确性上妥协。适当的文档应包含以下项目：

- 连接到网络的所有设备清单（服务器、工作站、路由器等）。
- 网络的物理布局，包括布线细节和显示每个设备精确位置的平面图。
- 网络的逻辑布局，包括分配的 IP 地址、网络 ID 和相关的掩码。
- 服务器、路由器和其他网络连接设备（例如网络打印机）的配置细节。
- 每个使用其资源的服务器和用户组的用途。还包括该服务器可能对其他服务器的依赖关系。
- 网络更改的历史。诸如网络分段、地址更改、基础更改以及服务器的添加和删除都是该文档涵盖的内容示例。记录更改的理由可以为网络性能故障排除提供有价值的见解。
- 网络遇到的问题历史，以及帮助修复这些问题的相关修复和补丁。半以上的问题具有重复性。记录它们及其解决方案可以提供经过证明，在未来类似的情况下可以使用。

手头拥有这些细节可以大大减少通过猜测或手动工作查明它们所需的时间。文档应被视为网络故障排除中的一种主动练习。

养成及时完成此工作的习惯，在完整信息可以减少维修所需的时间和精力的情况下，可以迅速证明其价值。

与文档同样重要的方面是用户报告的错误消息和投诉。每当报告错误时，请用户通过重复错误发生时的每一个按键操作来重现它。如果成功重现了错误，请虔诚地记录导致错误产生的一切——包括错误消息本身。

## 制定故障排除计划

根据你收集的信息，你应该能够为网络故障排除制定一个有效的计划。该计划应该基于对观察结果和收集信息的详尽理解和分析。一个有效的计划应该包含这些步骤，这些步骤执行后有助于缩小问题的范围（例如：是特定用户的问题、特定组的问题还是整个网络范围的问题？）。广泛的测试练习有助于实现这一目标。

计划的另一个步骤应该考虑自上一次网络服务运行良好以来发生了什么变化。如果你想要良好的文档，这个问题就不应该被怀疑。用户工作站、路由器或任何其他网络服务配置中细微且未被察觉的变化，正是更改发生之前不存在的异常背后。

你的计划应该识别出执行这些任务所需的工具和访问权限，以及它们执行的顺序描述。

## 识别并解决问题

目标是通过在多个用户工作以及可能的多个网络段的情况下尝试重现问题来识别问题。这项练习有助于你快速确定问题是影响了所有用户、一组用户还是仅一个用户。故障排除练习下一阶段所需的工具和方法论将通过你在此阶段的发现得到显著改进。

影响一个用户的问题可能是由于用户的操作不当，或者是他/她的工作站上的配置（或错误配置）。一致地，使用适当的故障排除工具，你的努力应该集中在用户工作站层面。这并不意味着工作站是寻找 bug 的唯一地方。bug 可能是由于网络的变化影响了该特定用户（例如在另一个工作站或设备上重复该用户的 IP 地址，这是一个常见问题）。

影响一组用户的问题需要检查这些用户聚集在一起的因素。例如，你可能会发现只有网络特定分段的用户受到影响。在这种情况下，你缩小对该特定分段的搜索。如果识别出的组成员属于不同的分段，那么可能意味着他们在逻辑上聚集在一起以使用某个公共网络资源。下一步是找到他们独享的服务，并弄清楚如何解决问题以允许该服务运行。

使用适当的故障排除工具（下节将讨论），你应该能够进一步缩小连接过程中受影响的层。这有助于将注意力集中在该层以及可能对网络产生不利影响的相关配置上。

作为故障排除练习，你应该跟踪你所做的观察。在这样做的同时，永远不要忽略看似微不足道的事。凭借对 TCP/IP 的深入理解，网络故障排除主要基于敏锐的观察和对性质的说明。

记录问题 一个成功的故障排除练习总是更新文档，对遇到问题的完整描述以及解决方案的详尽描述。这样做有两个重要原因：

1. 你跟踪了更改和问题，在出现类似情况时提供指导，
2. 无论对解决方案测试有多彻底，某些情况下解决方案会导致未来问题的根源。

## ping: 测试可达性

每当遇到可达性问题时，`ping` 通常是用户脑中想到的第一个诊断命令。对于确定故障是由于配置、路由还是物理故障引起的，而不是通信过程中上层应用层的故障，`ping` 特别有帮助。

在最简单的形式中，`ping` 以主机作为参数（当然，该名称可以使用 `/hosts` 文件或 DNS 服务器进行解析）。以下是一个使用 `ping` 进行成功测试的示例：

```
# ping cello

cello alive
```

`ping` 采用 ICMP 协议来建立与目标主机的可达性。当调用 `ping` 时，它向命令行指定的主机发送一个 ICMP ECHO REQUEST（请求）消息。作为响应，`ping` 发送一个 ICMP ECHO RESPONSE（响应）消息。如果在超时时间内未收到响应，`ping` 将判定该主机不可达；并在用户屏幕上显示熟悉的“host unreachable”（主机不可达）消息。

“host unreachable”消息可能是由于主机故障引起的。目标主机可能已关机，或其通信栈可能无法响应用户请求。通过尝试 `ping` 与指定主机处于同一网段的其他主机，可以确定目标主机在该故障中的责任责任。 `ping` `ping` 成功返回，则可以结论目标服务器是故障的根源。因此，你可能需要花时间尝试修复其目标服务器的问题。否则，问题可以归因于本地配置错误、物理故障或路由问题。

> **使用 ping 时**，`ping` 是一个功能性命令，能够发送特定大小和特定间隔的多个 ICMP ECHO REQUEST 数据包。根据互联网标准，`ping` 预计处理的最大数据包大小为 64 字节。你之所以可能想让 `ping` 发送大尺寸数据包，是为了测试路径对大数据包的分段/重组/重新排序的能力。然而，发现某些 `ping` 的实现允许使用大于 64 字节的数据包（例如 Windows 9 中的 `ping` 实现）。强烈建议你避免指定此类大数据包大小的诱惑。据报道，`ping` 可能会因为针对大尺寸 ICMP ECHO REQUEST 包的攻击导致从大型机到任何规模的计算机崩溃。
请参阅你系统上实现的 `ping` 的确切语法。

## 验证本地配置

可以使用熟悉的 `ifconfig` 命令验证主机的 IP 地址。通过 `ifconfig`，网络管理员可以检查主机的 IP 地址、子网掩码和广播地址，以及网络接口的状态。你也可以使用 `ifconfig` 检查接口是否被标记为 UP（开启）或 DOWN（关闭），这分别意味着接口正常运行或未运行。

以下是使用 `ifconfig` 的示例：

```
# ifconfig el30

el30: flags=23<UP,BROADCAST,NOILERS>

inet 150.1.0.1 netmask fffff00 broadcast 150.1.255.255
```

根据此，el130 接口配置 IP 地址为 150.1.0.1，子网掩码为 fff00（等同于点进制表示法的 255.255.0.0），广播地址为 150.1.255.255。注意接口被标记为 UP，表示它正在运行。标记为 DOWN 的接口意味着主机本身存在硬件问题或连接到网络的物理接线问题。

如果 `ifconfig` 验证参数正确，但主机仍然无法访问网络上的其他主机，那么你可能需要考虑 IP 地址冲突或通往目标主机路径上的路由问题。

## arp: 谁是我的双胞胎

`arp` 命令在检测大多数重复 IP 地址问题时特别有用。IP 地址冲突会导致已建立的连接间歇性缓慢、超时并中断。所有共享该 IP 地址的工作站和网络都不可避免地遭受性能下降，甚至完全掉线。

正如所解释，每当用户尝试与网络上的另一个主机建立会话时，他通常会指定该主机的名称。应用程序接管并将解析为 IP 地址。随后，ARP 协议将 IP 地址解析为物理地址，通常称为 MAC 地址（即介质访问控制）。ARP 通过发送 ARP Request 来查找目标的 MAC 身份，目标主机接收 ARP 请求包并对其进行处理。一旦某个具有匹配 IP 地址的主机，它*应该*返回一个包含其 MAC 地址的 ARP Response 响应包。一旦获得 MAC 地址，原始主机将使用发现的地址与目标主机进行数据交换。为了节省 ARP 过程消耗的带宽，每个主机都会缓存网络中的 ARP 响应。

使用 `arp -a` 命令，你可以看到所示的 ARP 缓存表：

```
# arp -a

cello (150.1.0.10) at 0:0:32:1:ad permanent

jade (100.0.0.2) at 0:0:c0:15:ad:18

oboe (150.1.2.1) at 0:0:8c:12:4:ab
```

注意每个条目都包含主机的地址以及与该接口对应的 MAC（即物理）地址。例如，cello 的 IP 地址是 150.1.0.10，MAC 地址是 0:0:32:1:ad。

上述内容不应让你认为 ARP 与三个主机进行了通信。事实上，ARP 响应的是工作站未通信的主机。这些条目的默认超时时间为四分钟。如果需要，你可以更改默认值。

如果两个工作站被错误配置共享同一个 IP 地址会发生什么？正如想象的，它们都会尝试响应 ARP 请求——这会引发问题。在两个响应中，只有先到达的一个会被处理并用于数据交换。因此，如果 MAC 地址对应于“冒充”主机，原始工作站将无法告知服务器，因为帧携带了错误的地址。

当怀疑网络存在 IP 地址冲突时，询问用户有关该服务或他尝试访问的问题。重复地址可能是用户工作站的，或者是主机被复制了，并。

## 关于 arp 的更多信息

`arp -a` 命令的输出有时包含状态限定符类型。以下是三种类型：temporary（临时的）、permanent（永久的）和 incomplete（未）：

```
# arp -a

tenor (100.0.0.3) at 0:0:03:32:1:1ad permanent

jade (100.0.0.2) at 0:0:0c:15:ad:18 permanent

cello (198.53.237.2) at 0:0:c8:12:4:ab

absent (184.34.32.23) at (incomplete)
```

如果没有状态限定符（例如 cello 的情况），默认是 temporary。临时 ARP 条目通过 ARP 请求/响应交换动态添加到主机的缓存中。这些条目通常在持续四分钟后被删除。

标记为 permanent 的条目（如限定符所示）是静态性质的条目；它会保留在 ARP 表中，直到由系统管理员（或）使用 `arp -d` 命令删除。通常，永久条目是手动添加并持久于用户

通信。这种措施的优点是节省带宽，否则这些带宽会在 ARP 请求/响应交换中浪费。在 ARP 缓存中添加永久条目需要使用以下形式的 arp 命令：

```
# arp -s hostname MACaddress
```

例如，通过输入以下命令将主机 jade 的 IP 地址到 MAC 的映射永久地添加到用户的 ARP 缓存中：

```
# arp -s jade 00:0:c0:15:ad:18
```

标记为 `pub` 的条目使该主机有权代表此条目中的工作站地址进行响应。示例列表包含一个针对 tenor 的永久条目。这意味着当查询 tenor 的 IP 地址时，该主机有权代表 saturn 响应 ARP 请求。当查询主机属于两个由路由器桥接的不同网络段时，且这些路由器被配置为抑制广播，通常会采用这种方法。在这种情况下，你可以在每个网段指定一个主节点作为 ARP 服务器，强制响应未连接到同一网段的主机的 ARP 请求。为了便于管理，可以强制 arp 循环读取文件的内容，你可以在文件中维护所有已发布的条目。文件的通用格式如下：

```
hostname MACaddress pub
```

确保 `/etc/hosts` 文件中存在与 hostname 匹配的条目。

要使用包含所有所需 ARP 映射的文件内容强制 arp 更新 ARP 缓存，请使用 -f 输入命令：

```
# arp -f filename
```

因此，在排查重复 IP 地址时，你应该检查用于更新 ARP 服务器缓存的 ARP 文件。它们可能是产生重复的源头，或者由于文件中过时的数据导致了错误的响应。

## traceroute

在某些情况下，无法访问的问题主要归因于路由配置问题。让排查路由问题变得更加困难的是源主机和目标主机之间中间路由器的数量。为了帮助你处理涉及大量路由器的情况，UNIX 配备了一个易用且强大的 `traceroute` 命令。

使用 `traceroute`，你可以追踪数据包从网络中一个主机到另一个主机的路径。该命令为数据包所经过的每个路由器显示一行。这些行包含了被追踪的路由器的 IP 地址、跳数（即主机与所描述的路由器之间的中间路由器数量）以及以毫秒为单位的往返时间。`traceroute` 支持的最大跳数为 30。

要追踪一个主机或任何其他网络设备，只需输入：

```
# traceroute hostname
```

在下面的示例中，`traceroute` 被用于追踪到主机的路由：

```
traceroute rome

traceroute rome (148.53.27.11), 30 hops, 40 byte packets

1 198.237.53.1 (198.237.53.1) 5 ms 5 ms 4 ms

2 198.235.54.2 (198.235.54.2) 6 ms 6 ms 4 ms

3 143.22.45.9 (142.22.45.9) 11 ms 8 ms 7 ms

4 168.91.1.158 (169.48.1.158) 28 ms 24 ms
```

根据这个示例，获取主机 rome 的数据包来自使用 `traceroute` 的工作站，按顺序经过了四个路由器。

结合图 20.34 可以了解 `traceroute` 的原理。在本章开头，已经解释了数据包在网络上停留多久是由 IP 头部包含的生存时间（TTL）字段的内容决定的。数据包经过的每个路由器都会递减 TTL 字段。一旦 TTL 减到零，数据包就会检测到它的第一个路由器并丢弃。`traceroute` 利用了这种机制。它按顺序发送最多 30 个 UDP 包，其中第一个包的 TTL 设置为 1。每个后续包的 TTL 均相对于上一个包增加 1。在实践中，这意味着第一个包在到达第一个路由器或其目标主机（即图中的 rome）时 TTL 就会归零。第二个 UDP `traceroute` 包通过路由器 R1 仅到达了 R2 的门槛（此时其 TTL 设置为 2）。每当路由器丢弃一个数据包时，它（根据设计）向源主机返回一个 ICMP 超时消息（ICMP Timeout Message）。

### 图 20.34.

```
traceroute flow of events.
```

这一系列事件一直持续到到达目标主机。为了从目标主机获取响应，`traceroute` 将 UDP 包的目标端口设置为 33344 - 这是一个预留的无效数字。无效的端口号强制接收主机忽略该包并返回 ICMP 端口不可达（ICMP Unreachable Port，而非时间超时）。在收到此最后消息后，`traceroute` 停止发送诊断 UDP 包。

这是一个说明了当 `traceroute` 无法到达目标主机时会发生什么的示例：

```
# traceroute rome

traceroute rome (148.53.27.11), 30 hops, 40 byte packets

1 198.237.53.1 (198.237.53.1) 5 ms 5 ms 4 ms

2 198.235.54.2 (198.235.54.2) 6 ms 6 ms 4 ms

3 * *

4 * *

29 * *

30 *
```
