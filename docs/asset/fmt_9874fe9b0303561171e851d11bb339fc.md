
有三个工具用于准备 `.config` 文件：`make config`（一个命令行工具）；`make nconfig`（提供基于文本的菜单、单选列表和对话框）以及 `make xconfig`（一个基于 Windows 的配置工具）。根据作者的经验，`make config` 的更新速度比图形化工具更好，这在稳定版内核上可能并不完美。然而，`make config` 缺乏返回之前所选选项的功能，因此如果需要更改则需要再次运行 `make config`。如果存在现有 `.config` 文件，则默认值来自那里。

此外，`make oldconfig` 与 `make config` 类似，区别在于它只对新的配置选项提问，并将所有其他选项设置为上一次配置内核时的 `.config` 值。如果使用 `make oldconfig` 配置新内核版本，且需要之前选择的选项，请务必将之前的 `.config` 文件移动到新目录。

具有编译 Linux 内核经验的系统管理员可能倾向于直接编辑 `.config`。如果内核需要编译自 `.config` 文件最初生成以来添加的配置选项，这种方法可能不起作用。还要注意，仅在 `.config` 中注释掉某些行可能无法达到预期结果。如果不确定，无论使用哪种工具生成 `.config` 文件，请务必使用配置工具将其与之前的 `.config` 文件进行比较，并理解所有差异。在少数情况下，可能需要参考源码，但文档通常足够了。如果之前的 `.config` 文件可用，请仔细查看新文件。这些选项应该是合理的。如果不符合，请查阅文档。

请注意，一旦编译了 `proc` 文件系统，许多内核特性可以在不重新编译的情况下重新配置。如上所述，Linux 使用位于 `/proc` 的伪文件系统提供了像处理 ASCII 文件一样查看和更改运行中内核参数的手段。

## 模块

确定内核是否需要某些特性是一项简单的任务。然而，Linux 提供了两种不同的包含方法。特性可以静态编译到内核中，也可以作为可加载模块。

静态编译内核的优势是简单和执行快速。编译可加载模块的优势是基础内核保持较小，在不需要模块时使用更少的内存。当然，当加载模块时，使用的内存比静态内核多，而且加载会产生微小的执行延迟。

在决定静态编译还是作为可加载模块编译之前，要问的两个问题是：有多少系统需要它？它们需要的频率如何？前者问题比后者更重要。少数系统频繁使用的功能应编译为可加载模块。

例如，某人可能对没有网络接口的打印机有业务需求。这需要一个打印主机进行打印。为该机器编译非标准内核会使支持和升级变得异常困难。因此，最好将打印支持编译为所有机器的模块，尽管很少有人。

## 编译内核

一旦准备好 `.config` 文件，就可以编译内核了。请遵循内核源码随附的 `README` 文件中的说明。这些说明随内核一同演进，因此不宜重复它们。

注意依赖关系，因为新内核通常需要一个或多个更新后的包，例如 `binutils` 或 `net-tools`。内核源码中 `Documentation` 目录下的 `Changes` 应该提供完整的列表。

# 安装内核

聘用内核开发人员的组织可能会让他们负责编译将用于生产环境的内核。这种做法是不明智的。开发者通常不具备完成此任务所需的极端谨慎心态。系统管理员应该负责编译内核，并在遇到文档中未解释的技术困难时，向公司内部的内核开发人员提问。

# 安装内核

当然，在向生产机器上安装新编译的内核之前，需要进行一些质量保证工作，甚至在安装到数千台或上万台机器上之前也是如此。文档中出现的内核安装说明适用于在单台或几台机器上安装内核。对于测试新内核来说，这可能足够了。

每当安装新内核时，都应该注意一些注意事项。在添加任何新内核之后重启机器之前，运行 `/sbin/ldinitconfig` 至关重要。此外，确保 `/etc/ldinitconfig.conf` 指向的 `System.map` 文件与内核版本匹配也同样重要。如果 `/boot` 中存在多个版本的内核，则那里也应该存在相应的 `System.map` 文件（具有不同的名称），并且 `/etc/ldinitconfig.conf` 反映了这种对应关系。

然而，由于内核无论如何都应该为了批量安装而打包，因此从一开始就这样做是有益的。这种方法的优点是能够同时测试软件包及其内容（即内核）。在有缺陷的包中部署一个完美的内核可能与部署一个有缺陷的内核一样灾难。

一旦打包了新内核，安装就变成了安装包的问题。这应该先在测试机器上进行。当测试机器一切正常后，应在阶段环境中安装新内核包。最后，当在阶段环境中验证了正确的功能后，即可将新内核部署到生产环境。我们在第 15 章“自动化安装与升级”中提供了如何部署新软件的建议。

# 11 脚本编写

永远不要让一个人去做脚本的工作。

LINUX 最强大的优势之一是其易于进行配置或修改。操作系统的两个特性使得这一切成为——几乎所有的配置和系统数据文件都使用纯 ASCII 文字，许多系统初始化代码以可执行 shell 脚本的形式存在。Shell 脚本以文件形式存储为人类可读的指令，由 LINUX 系统上提供的许多命令解释器之一执行。

本章描述了 LINUX 系统本身使用的许多解释型语言，以及用于构建系统管理工具的语言。文中提供了各种脚本语言的示例。这并不意味着特定任务必须用特定语言编写脚本，而是为了展示有多种选择。当然，某些语言比其他语言更适合特定任务，但几乎任何脚本语言都可以使用。最佳选择往往取决于系统管理员的技能，也取决于任务的性质。

¹. 命令解释器是程序，它们通过在执行时解释一系列命令来实现一种编程语言。这与编译器形成对比，后者会将整个程序翻译成机器指令，以供以后执行。

## Shell

Shell 是命令解释器，主要旨在供用户和系统管理员交互式使用。基础 shell 提供了一小组内置命令，这些命令在 shell 内部实现。Shell 使用的其他命令实际上是存储在 `/bin` 和 `/usr/bin` 目录或其他 `$PATH` 中的程序。

大多数系统上都存在 `bash`、`ash` 和 `tsh` shell。系统上可能还安装了其他 shell，如 `ksh` 或 `zsh`。Linux 系统的默认 shell 是 `dash`。

Shell 可以交互式使用，也可以执行称为脚本的存储的程序。Shell 脚本可以使用任何文本编辑器（如 `vi` 或 `emacs`）编写。Shell 编程环境真正的威力不在于任何单一工具的能力（事实上，大多数都非常简单），而在于将简单命令组合成强大结构的能力。命令可以使用管道和 I/O 重定向进行组合。例如，要找到用户 `root` 的进程，可以输入以下内容：

```bash
ps aux | awk '$1 == "root" { print }'
```

管道运算符（由 `|` 字符表示）将 `ps` 命令的输出重定向到 `awk` 命令的输入。现在，为了按内存大小查看 `root` 的进程，我们在管道中添加了 `sort`：

```bash
ps aux | awk '$1 == "root" { print }' | sort +3n
```

当然，我们漏掉了前几个进程，因为它们滚过了终端窗口顶部。我们在管道末尾添加了 `more` 命令，以便一次显示屏幕：

```bash
ps aux | awk '$1 == "root" { print }' | sort +3n | more
```

通过这种方式，可以从 LINUX 提供的简单实用工具创建非常强大的表达式。

## 通用实用工具

Shell 脚本中始终可以使用许多 UNIX 实用工具。`expr` 命令用于简单的数学运算和模式匹配。`test` 命令用于条件评估；它可以用于确定有关文件的信息并比较字符串或数字。流编辑器 `sed` 用于以自动方式编辑流。`grep` 工具打印匹配模式的行。`awk` 编程语言用于基础数据处理，例如求加输入字段或从表格数据行中提取字段。`sort` 实用工具可对数据行进行排序。通常，shell 会调用几十种其他实用工具来完成大部分工作。
