
### 数据结构

`gmk_floc` 此结构表示文件名/位置对。它在定义项目时被提供，因此 GNU make 在需要时可以告知定义发生的位置。

### 注册函数

目前 Makefile 只有一种方式可以调用加载对象提供的操作：通过 *make* 调用接口。加载对象可以注册一个或多个函数，然后像调用任何其他函数一样，在 Makefile 内部调用这些函数。

使用 `gmk_add_function` 创建一个新的 *make* 函数。其参数如下：

- `name`: 函数名。这是 Makefile 调用该函数时应使用的名称。该名称的长度必须在 1 到 255 个字符之间，且只能包含字母、数字、点（`.`）、连字符（`-`）和下划线（`_`）。它不能以点开头。
- `func_ptr`: 指向函数的指针，*make* 在在 Makefile 中展开函数时将调用该函数。此函数必须由加载对象定义。
- `min_args`: 函数调用时的最少参数数量。它必须在 0 到 255 之间。如果调用函数时参数太少，GNU make 将检查此项并在调用 `func_ptr` 之前失败。
- `max_args`: 函数调用时的最大参数数量。它必须在 0 到 255 之间。如果调用函数时参数过多，GNU make 将检查此项并在调用 `func_ptr` 之前失败。如果值大于 0，则它必须大于或等于 `min_args`。
- `flags`: 指定该函数如何运行的标志；所需的标志应进行位或运算。如果给了 `GMK_FUNC_NOEXPAND` 标志，则参数将不会展开；否则它们将被展开。

### 注册函数接口

向 *make* 注册的函数必须匹配 `gmk_floc_ptr` 类型。它将带有三个参数调用：`name`（函数名）、`argc`（函数的参数数量）和 `argv`（指向函数的指针的数组）。最后一个指针是 `argv[argc]`，它将为 `null`。

函数的返回值是函数展开的结果。如果函数展开为空，则返回值可能为 `null`。否则，它必须指向一个使用 `gmk_alloc` 创建的字符串的指针。一旦函数返回，make 将拥有该字符串并在适当时释放它；加载对象无法访问该字符串。

### GNU makeset

GNU make 输出了一些供加载对象使用的功能。通常，这些功能将在设置函数和/或通过 `gmk_add_function` 注册的函数内部运行，以获取或修改 make 数据。

- `gmk_expand`: 此函数接收一个字符串并将其展开。
- `gmk_eval`: 此函数将字符串作为 Makefile 语法进行评估。

### 内存管理

某些系统允许不同的内存方案。因此，你不应该直接传递你分配的内存，也不应该尝试释放由 make 返回的内存。相反，请使用 `gmk_alloc` 和 `gmk_free`。

- `gmk_alloc`: 返回指向新分配内存的指针。此函数始终返回有效指针；如果没有可用内存，make 将会失败。
- `gmk_free`: 释放 make 返回给你的缓冲区。一旦函数返回，字符串将不再有效。

## 12.2.4 示例加载对象

假设我们想编写一个新的 GNU make 函数，它可以创建一个临时文件并返回其名称。我们希望该函数接受一个前缀作为参数。首先我们将函数写在文件 `mk_temp.c` 中：

```c
#include <stdlib.h>
#include <stdlib.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <gnumake.h>
```

```c
int plugin_is_GPL_compatible;
```

```c
char *gen_tmpfile(const char *nm, int argc, char **argv)
{
    int fd;
    /* 计算文件名的大小并为其分配空间。 */
    int len = strlen(argv[0]) + 6 + 1;
    char *buf = gmk_alloc(len);
    strcpy(buf, argv[0]);
    strcat(buf, "XXXXX");
    fd = mktemp(buf);
    if (fd >= 0) {
        /* 不要泄漏文件描述符。 */
        close(fd);
        return buf;
    }
    /* 失败。 */
    fprintf(stderr, "mktemp(%s) failed: %s\n", buf, strerror(errno));
    gmk_free(buf);
    return NULL;
}
int mk_temp_gmk_setup() {
    /* 以 make 名称 "mk-temp" 注册该函数。 */
    gmk_add_function("mk-temp", gen_tmpfile, 1, 1, 1);
    return 1;
}
```

接下来，我们将编写一个 Makefile，可以构建此共享对象、加载它并使用它：

```make
$ make
cc -shared -fPIC -o mk_temp.so mk_temp.c
Temporary filename: tmpfile.A7JEwd
```

# GNU make 的 13 特性

以下是 GNU make 特性的总结，用于与其他版本的 make 进行比较并向其致敬。我们将 4.2 BSD 系统中的 make 特性作为基准。如果你担心编写可移植的 Makefile，则不应使用这里列出的 make 特性，具体请参见第 14 章 [缺失]，第 147 页。

许多特性来自 System V 版本的 make。

- *VPATH* 变量及其选择。参见第 4.4 节 [在目录中搜索前置文件]，第 25 页。该功能在 System V 中存在，但未文档说明。它在 4.3 BSD make 中有记录（该版本限制了 System V 的 VPATH 功能）。
- *包含的 makefiles。参见第 3.3 节 [包含其他 Makefile]，第 13 页。允许通过单个指令包含多个文件是 GNU 的扩展。

- *自动变量 `$` 被设置为存档引用中的成员名称。参见第 10.5.3 节 [自动变量]，第 120 页。
- *自动变量 `$=`、`$$` 和 `$?` 具有相应的形式，如 `$(@)` 和 `()`。我们将这种 `$` 引入作为一个显而易见的扩展。参见第 10.5.3 节 [自动变量]，第 120 页。

- *接受并忽略命令行选项 `-b` 和 `-m`。在 System V 中，这些选项实际上是有作用。

- *GNU make 支持后缀 `.a`，这是因为第 10.4 节 [隐式规则链]，第 117 页中特性链的通用规则允许使用一个在存档中安装成员的模式规则（参见第 11.2 节 [更新存档]，第 129 页）即可。
- *在打印配方（recipes）时，保留了行和反斜杠/换行的布局，因此它们显示的方式与在 make 中一致，除了去除了开头的空白外。

## 14 不兼容性与缺失功能

各种系统中的 make 程序支持一些 GNU make 中未实现的功能。规定 make 的 POSIX.2 标准（IEEE Standard 1003.2-1992）并不要求这些中的任何功能。

- 形式为 `file((entry)) ` 的目标表示归档文件 `file` 的一个成员。该成员的选择不是通过名称，而是通过它是定义了链接器符号 `entry` 的对象文件。

此功能没有被引入 GNU make，是因为在 make 中引入归档文件符号表内部格式的知识会导致非模块化。请参见第 11.2.1 节 [更新存档目录]，第 130 页。

- 以字符 `*` 结尾的后缀（在后缀规则中）在 System make 中具有特殊含义；它们指的是如果不带 `*` 则会获取的文件对应的 SCCS 版本。例如，后缀 `.c*` 将根据 SCCS 文件覆盖范围生成 `n.o` 文件，这需要一整套这样的规则。请参见第 10.7 节 [旧式后缀规则]，第 125 页。

在 GNU make 中，这些情况通过两种从 SCCS 提取的模式结合规则链的通用功能来处理。请参见第 10.4 节 [隐式规则链]，第 117 页。

- 在 System V 和 4.3 BSD make 中，通过 PATH 搜索找到的文件（参见第 4.4 节 [在目录查找先决条件]）的名字在 make 配方内部会被更改。我们认为使用自动变量要清晰得多，从而使这一功能变得过时。
- 在某些 Unix make 中，我们认为这种用法是错误的。make 的先决条件属性是有良好定义的（对于 GNU make 是如此），而这样做简单来说不符合该模型。
- GNU make 不包含任何用于编译或预处理 EFL 程序的内置规则。如果我们听闻有人在使用 EFL，我们将乐意添加它们。
- 在 SVR4 make 中，可以指定没有名称的后缀规则，如果它有一个隐式配方（参见第 5.9 节 [空配方]，第 57 页）。例如：

```
.c.a:
```
这将覆盖内置的 'c.a' 后缀规则。

我们认为对于没有配方的规则，始终简单地添加到目标的先决条件列表中会更清晰。上面的示例可以轻松重写以便 GNU make 中获得所需的行为：

```
.c:a: ;
```
- 某些版本的 make 在调用 shell 时带有 '-e' 标志，除 '-k' 之外（参见第 9.6 节 [测试程序的编译]，第 104 页）。'-e' 标志告诉 shell 在其运行的任何程序返回非零状态时立即退出。我们认为编写配方的每一行都使其保持独立且不需要这种特殊处理要清晰得多。

## 15 Makefile 惯例

本章描述了为 GNU 程序编写 Makefile 的惯例。Automotake 将帮助你编写遵循这些惯例的 Makefile。关于可移植 Makefile 的更多信息，请参考 POSIX 和 Autoconf 中的“可移植 Make”章节。

### 15.1 通 通惯例

每个 Makefile 都应该包含此行：

```
SHELL = /bin/sh
```
以避免在 SHELL 变量可能从环境中继承的系统中出现问题（GNU make 没有这个问题）。不同的 make 程序具有不兼容的后缀列表和隐式规则，有时会引起混乱或行为异常。在 Makefile 中仅使用你需要的后缀显式设置后缀是一个好主意，如下：

```
.SUFFIXES =
SUFFIXES := .c .o
```
第一行清除后缀列表，第二行引入了在该 Makefile 中可能受隐式规则影响的所有后缀。不要假设 `.` 在命令执行的路径中。当需要在 make 过程中运行你包包的程序时，确保如果该程序是 Makefile 的一部分，则使用 `./`；如果该文件是源代码中不可更改的部分，则使用 `$(srcdir)/`。如果没有其中之一，将使用当前搜索路径。`./`（构建目录）和 `$(srcdir)/`（源代码目录）之间的区别是重要的，因为用户可以使用 'configure' 的 '--srcdir' 选项在单独目录中构建。形式如下的规则：

```
foo.1 foo.man
sed -f foo.man > foo.1
```
当构建目录不是源代码目录，且 foo.man 和 'descript' 在源代码目录时，该规则将失败。当使用 GNU make 时，在存在单个依赖的情况下，依赖 'PATH' 寻找源文件将可行（因为 make 自动的 '$' 只在隐式规则中使用）。像下面的 Makefile

```makefile
foo.0 : bar.c
$(CC) -I$(srcdir) $(CFLAGS) -c bar.c -o foo.o
```
应该写成

```makefile
foo.0 : bar.c
$(CC) -I$(srcdir) $(CFLAGS) -c $< -o $$
```
以便让 'PATH' 正确工作。当目标有多个依赖项时，使用显式的 '$(srcdir)' 是让工作最简单的方法。例如，上面的目标 'foo.1' 写为：

```
foo.1 : foo.man
sed -f $(srcdir)/foo.man > $$
```
GNU 发通常包含一些不是源码的文件——例如，Info 文件以及来自 Autoconf、Bison 或 Flex 的输出。由于这些文件通常出现在发行版中，它们应该始终出现在源代码目录，而不是构建目录。因此，Makefile 规则应该始终出现在源代码目录，而不是构建目录。在某些 make 中，我们认为这种配方使用变量是更清晰的。

在编写 Makefile 的配方时，Makefile 规则应该始终出现在源代码目录，而不是构建目录。

## 15.4 DESTDIR: 对安装的支持

DESTDIR 是一个加在每个安装目标文件之前的变量，如下：

```
$(INSTALL_PROGRAM) foo $(DESTDIR)$(bindir)/foo
$(INSTALL_DATA) libfoo.a $(DESTDIR)$(libdir)/libfoo.a.
```

DESTDIR 变量由用户在 make 命令行上以绝对文件名的形式指定。例如：

```
make DESTDIR=/tmp/stage install
```
