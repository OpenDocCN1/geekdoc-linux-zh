
“现在等一下，”你可能会这样想。我们是在说 Unix 包含了只检查文件是否存在的程序吗？简而言之，是的的。标准的 Unix 发行版带有数百个微型命令和程序，它们本身的作用非常其微。有些程序，例如 `test` 命令，执行着诸如确定文件可读性等等操作的平庸功能。如果这听起来并不那么重要，请记住 `test` 命令是 Unix 中使用最频繁的命令之一。

小型程序本身做不了什么。它们通常只执行一两个功能，外无他物。然而，将它们结合起来，你就开始体验到真正的力量。这种财富大于部分之和。大型、复杂的任务可以轻而易举地处理。你只需在命令行中输入它们，就可以编写新的应用程序。

## 软件工程变得简单

人们经常说，Unix 为程序员提供了世界上最丰富的环境。其中一个原因是，在其他操作系统上难以完成甚至无法完成的任务，在 Unix 下相对容易实现。难道是小型程序让这些任务变得简单了吗？确是如此。

### 2.2.1 小型程序易于理解

小型程序的“专精细业”方法将冗余减少到最低，转而专注于很好地执行一个功能。它们只包含少数算法，其中大多数算法与所涉及的工作直接相关。

- 某些 Unix/Linux shell（命令解释器），例如 `bash`，已经将 `test` 命令成为 shell 本的一部分，消除了调用新进程来运行命令的需求，从而减少了开销。缺点是，如果你不断向 shell 本身添加命令，最终 shell 将会增长到某种程度，由于 Unix/Linux 创建进程的方式，执行非 shell 命令的代价将变得高昂。或许依靠这样一个事实更好：频繁使用的命令通常已经驻留在内核的缓冲区缓存中，因此不需要从磁盘获取它们（这在时间成本上是极其昂贵的）。

另一方面，大型程序倾向于复杂化，并为理解制造了障碍。程序变得越大，它就离它的作者越远。代码行的巨大数量令人目不应接。例如，程序员可能会忘记程序的子程序位于哪些文件中，或者在引用变量和记住它们的用法时遇到困难。调试代码将变成一场噩梦。

某些程序无论大小如何都可能难以理解，这仅仅是因为它们所执行的功能性质本质上是模糊的。然而，这种程序很少。即使是具有中等经验的程序员也能轻松理解大多数小型程序。这是小型程序相对于其大型对应物的一个明显优势。

在此时，你可能会好奇小型程序在何时会变成大型程序。答案是，这取决于情况。在一个环境中的大型程序在另一个环境中可能被认为是平均水平。对于一个程序来说是面条代码，对下一个程序来说可能是家常便。以下是一些迹象，表明你的软件可能偏离了 Unix 方法：

- 传递给函数的参数数量超过了屏幕行宽。
- 子程序的长度超过了屏幕长度或标准 8x11 英寸纸的长度。请注意，大型工作站显示器上较小的字体和高大的窗口允许你舒适地稍微突破限制。只要不要做得过头就好。
- 如果不阅读代码中的注释，你就无法记住一个子程序是做什么。
- 你发现一个文件已经变得太臃肿，无法定义程序的全局变量。
- 你仍在开发该程序，但你不记得什么条件导致了特定的错误信息。
- 你发现自己不得不将源代码打印在纸上以帮助你更好地组织它。

这些警告信号可能会让某些程序员感到不悦，特别是那些“大即是好”阵营的人。他们说，并不是每个程序都能做小。这个世界是一个很美的地方，那里有一些非常大的问题，我们正试图用一些非常大的计算机来解决。这些问题要求我们编写一些非常大的程序。

这是一个非常大的误解。

存在一种软件工程师，他们为编写自己除了自己之外无人能理解的大型程序而感到自豪。他认为这种工作是“职业安全保障”。你可能会说，比他的自尊更大的东西就是最后一个应用程序了。这样的软件工程师在传统的软件工程环境中太常见了。

这种获得职业安全保障的方法的问题在于，他们所工作的公司不可避免地意识到这些工程师最终会离开，留下公司独自收拾烂子。明明的公司会采取措施防止这种情况。他们雇佣那些理解什么是易于维护软件的人。

软件设计者再不能说“天佑下一个人吧”了。优秀的设计师必须努力让他们的软件易于维护。他们保持代码彻底的——但不要太彻底。他们保持子程序短小。他们将代码精简到绝对必要的程度。这通常会导致易于维护的小型程序。

### 2.2.2 小型程序易于维护

由于小型程序通常易于理解，它们很可能易于维护，因为理解程序是维护它的第一步。毫无疑问你以前听过这些，但许多程序员忽略了维护这个主题。他们认为，如果他们花时间写了一个程序，那么别人也会同样愿意花时间在之后维护它。

大多数软件工程师并不满足于维护他人的程序为生。他们相信——也许是正确的——真正的钱是靠写新程序赚的，而不是修复错误。遗憾的是，用户并不这样看。他们期望软件在第一次运行时就能工作。如果没有，他们会对程序员非常生气。不能维护软件的公司无法生存。

由于维护软件不是光鲜的工作，程序员寻找方法让任务变得简单或完全避免。如果他们运气好，可能可以将维护工作交给初级人员。但通常不是这样

### 2.2.3 小型程序消耗更少的系统资源

由于小型程序通常易于理解，它也很可能易于维护，因为理解程序是维护它的第一步。软件责任通常落在原始作者身上，他必须尽力让任务变得更容易被接受。小型程序很好地满足了需求。因为它们的可执行映像占据内存很少，操作系统发现更容易为它们分配空间。这大大减少了交换和分页的需求，通常会导致显著的性能提升。Unix 世界的一个流行术语是“轻量级”（即小型程序通常被认为是轻量级的）。

大型程序带有巨大的二进制映像，加载时向操作系统付出沉重代价。分页和交换经常发生，导致性能下降。操作系统设计师意识到大型程序的资源需求，试图通过构建动态加载和共享运行时库等增强来解决这个问题。这些是症状，而不是问题。

我在职业早期遇到的一位计算机硬件工程师开道：“程序员总是想要更多的内存！我们停止你抱怨的方法就是给你另一块内存板。”他部分正确。给程序员更多内存，程序运行得会更快，编写时间会更短，大大提高了生产力。

思考一下这种“更多内存”疗法。我的硬件工程师不恰切地根据他领域内程序员编写大型复杂程序的倾向得出了结论。这并不意外。如果我们使用 Unix 并拥抱其小型程序哲学，对更多内存的需求就不会那么明显了。笑话会变成：“程序员总是想要更多的 MIPS！”（`MIPS` 代表每秒百万条指令，一种流行但未必准确的 CPU 性能衡量标准）。

## 2.2 让软件工程变得简单

显而易见，如果 CPU 能力不足，那么每个程序必须在内存中停留更长时间，才能让下一个小程序加载并执行其任务。

使用小程序的系统也能从额外的内存中受益。更大的内存允许更多的小程序在内核缓冲区缓存中停留更久，从而减少对二级存储的依赖。较小的程序也更容易在缓冲区缓存中进行布局。正如我们后面将看到的，同时运行的小程序越多，系统的整体性能就越高。这构成了 Unix 哲学中一个核心原则的 basis，我们稍后将会讨论这一原则。

### 2.2.4 小程序可以轻松与其他工具结合

任何编写过大型复杂程序的人都知道这一点。单体程序（Monolithic programs）是一个自成自足的世界。在试图在一个程序中提供任何人可能需要的每一个功能时，它们构建了阻碍其与其他应用程序交互的屏障。

那么一个提供许多到其他数据格式转换的大型应用呢？它难道不比一个只允许一种数据格式的小程序更有价值吗？从上看，这听起来是一个合理的假设。只要需要的格式恰好是应用程序已经支持的格式，你就能相处愉快。但当应用程序必须与一种它未配备的数据格式接口时，会发生什么？

软件开发者通常在一种错误的观念下编写大型程序，认为他们已经处理了所有突发情况（即他们的程序可以与今天存在的任何数据格式交互）。这可能会成为一个问题。虽然开发者可以处理今天的数据格式，但他们并不知道可能会出现什么新格式会使他们的应用程序过时。大型复杂程序的编写者在一种自大的假设下运作，认为未来不仅是可预测的，而且与今天不会有太大区别。

另一方面，小程序的作者们含不蓄蓄地避免了预言未来。他们对明天唯一的假设就是它将与今天不同。新的接口在出现。数据格式在演变。交互风格在公众喜爱中兴起又落。新硬件让旧算法过时。变化是不可避免的。

总之，编写小型程序而不是大型程序具有独特的优势。它们的简单性使得它们更容易编写、理解和维护。此外，人类和机器都发现它们更具适应性。最重要的是，你将使程序能够处理那些在你编写它们时完全无法预测到的情况。

展望未来。它比你想象中更快到来。

## 2.3 观察 bug（虫）

让我们花点时间谈谈 bug——不是软件 bug，而是另一种虫。

一种奇特的飞行昆虫栖息在维多利亚湖周围，那是尼罗河的源头。已探险家雅克·库斯特（Jacques Cousteau）拍摄的壮丽视频显示，这种被称为湖蝇（lake fly）的昆虫聚集在湖中，在湖面上和附近的丛林中形成如雾般的聚集。它们的大小和外观与蚊相似，有时会在湖面上形成密集的云，人们很容易将其误认为是水龙卷或小龙卷风。

大量的鸟类经常俯冲进“虫龙卷”，尽享大自然的馈赠，在一次空袭中消耗数百万昆虫。尽管如此遭了掠食性的冲击，仍有数百万昆虫生存下来，它们阴影般的群体几乎没有减少的迹象。

当库斯特仔细观察这种异常昆虫的生命周期时，他发现成虫寿命异常短——大约 6 到 12 小时。即使它们没有成为我们羽毛朋友的食物，它们的成虫生存也不过阳光下短暂的闪动。
