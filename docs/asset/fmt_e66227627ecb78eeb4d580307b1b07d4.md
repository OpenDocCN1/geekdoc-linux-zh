    unsigned long pfn,
    struct zone *zone, unsigned int order,
    int migratype, fpi_t fpi_flags)
{

    unsigned long buddy_pfn;
    unsigned long combined_pfn;

    VM_BUG_ON_PAGE(pfn & ((1 << order) - 1), page);
    VM_BUG_ON_PAGE(bad_range(zone, page), page);

    }

列表 2-80: mm/page_alloc.c: `free_one_page()` 顶层逻辑

代码执行以下步骤：

1. 初始设置和健全检查。
2. 合并循环 - 这是实现伙伴分配器合并的代码部分，即检查页面伙伴是否空闲，以便合并为 `order + 1` 级的页面并循环尝试合并该块。循环迭代到但不包含最大允许阶 `MAX_ORDER - 1`，因为每次迭代可能导致合并为 `order + 1` 级的页面。
3. 将页面添加到空闲列表 - 最后，逻辑将页面添加到适当的空闲列表中。

注意，代码通过 `struct page_control` 引用了压缩，但这超出了本章的范围，更多信息请参阅关于压缩和迁移的章节。

在释放页面后（在本书范围内），唯一的复杂性在于是将页面添加到空闲列表的头部还是尾部。如果设置了 `FPI_TO_TAIL`，则覆盖算法，通过 `is_shuffle_order()` 开始判断是否应该洗牌（这仅适用于 order-0 页面且仅在设置了 `CONFIG_SHUFFLE_PAGE_ALLOCATOR` 时，这是为直接映射缓存设计的）。该主题超出本书范围。因此，调用 `shuffle_pick_tail()` 来随机选择是否将页面放在空闲列表的尾部。

# 虚拟内存

可以认为，硬件提供的最重要的内存功能是能够对地址进行完全抽象的能力。这构成了现代内存管理的基础，因为它允许每个运行进程的地址空间相互分离，并允许内核决定内存范围的权限以及如何处理非法访问。在本章中，我们将探讨内核是如何初始化和管理虚拟内存的。

在过去，硬件并没有对软件访问机器上所有可用物理内存施加限制。这在许多方面都存在问题：

- **稳定性** - 程序可以访问任何内存，无论该内存属于谁——是它自己的、另一个程序的、还是系统的。这意味着，导致访问非预期内存的编程错误可能会导致无法察觉的内存损坏；运气好的话会导致系统挂起，而运气不好的则会导致数据丢失。
- **复杂性** - 加载程序变得异常复杂。操作系统必须确保将程序加载到内存中的某个位置，使其不仅不会与其他程序重叠，也不会与这些程序被设置为使用的内存重叠。
- **安全性** - 每个进程的权限与其他任何进程相同，并且可以随意访问无论敏感程度如何的数据，这意味着实际上程序之间完全没有安全性可言。
- **连续性** - 连续内存块是指跨越地址范围且没有间隙的内存。如果你直接暴露物理内存，那么连续内存块就会变成一个问题；你无法控制物理内存布局，因此碎片始终存在，且内存无法移动，因为任何引用它的程序都持有指向内存中*实际*位置的指针，一旦尝试移动它，该指针就会失效。一个合理的程序会被要求分配连续内存，结果就是由于碎片导致的内存耗尽变得极可能发生。
- **容量** - 当直接暴露物理内存时，你只能访问系统可用的物理内存。这似乎是一个无关紧要的问题，但在没有分页等机制的情况下，内存耗尽将成为一种致命故障。

在计算机发展历史上，人们尝试过多种解决这些问题的方法，但硬件开发者最终达成共识的方法是虚拟内存。

这个概念非常简单。与其直接暴露内存，不如使用*虚拟地址*，这种地址可以以页为粒度和对齐方式任意地映射到物理地址。一旦实现了这一点，你就可以让每个进程都认为自己拥有所有可用内存，从而一次性消除了上述所有问题。

> **注意**：我在这里区分了“程序”和“进程”，因为在没有虚拟内存的情况下，虚拟内存的概念确实需要将“特权”内核代码与“非特权”用户空间分离开来，因为将虚拟内存映射到物理内存意味着对*所有内存*的访问，而只有内核被允许这样做。

最终，对虚拟内存的支持来自于硬件，硬件提供了更改虚拟映射的能力，并确定当前执行的代码是否具有特权（从而决定映射是否可以更改）。

利用这一功能，内核可以切换用户空间进程的虚拟映射，每个进程都有自己独立的虚拟*地址空间*。内核提供了系统，以页为粒度将内存分配到它们的地址空间中，从而完全抽象了获取内存的过程。从内核的角度来看，这是一个两步过程：分配物理内存，将其映射到进程中。

当用户空间进程访问未映射的内存或无权访问的内存，或者尝试在虚拟内存范围内执行未允许的操作（例如，在只读映射中写入或在标记为不可执行的内存中执行代码）时，CPU 会产生页异常，这是内核可以捕获并响应的硬件异常。

当访问不应访问的任意内存时，内核会以应用程序程序员熟悉的方式触发段错误。然而，页异常也可以用于实现有用的功能（列表并不完整）：

- **按需分页** - 我们之前提到，从内核的角度来看，用户内存分配是一个两步过程：物理分配和虚拟映射。然而，内核也可以选择“懒惰”，将其转变为一个零步操作——只需更新内部数据结构。这样做允许将实际的分配和映射推迟到访问内存时（此时触发页异常）。这是一个强大的概念，我们将在第 4 章进程管理和第 6 章页异常中再次遇到。
- **写时复制** - Unix 操作系统的一个重要功能是进程分叉。这是进程创建自己的一个精确副本，并作为新的子进程独立执行。虚拟内存为此提供了一种非常高效的方法：复制虚拟内存映射（但不复制物理内存），将其标记为只读和“写时复制”。正如名称所示，这指示内核仅在内存被写入时才复制底层物理内存。通过将映射标记为只读，我们可以利用产生的页异常仅复制被写入的页面。
- **NUMA 平衡** - 在 NUMA 系统中，核心访问某些“非本地”内存（即物理上靠近它的内存）可能需要更长时间。目前无法确定哪个核心最终会访问特定的内存页，因此为了确保内存分配得到高效分布，用户态可以定期取消映射，允许“故障时迁移”语义——即如果访问内存的核心不是其本地，则进行迁移并重新映射。

由于虚拟内存所依赖的硬件机制不可避免地特定于架构，为了简洁起见，我在直接与硬件接口的内核代码部分选择了关注 x86-64（正如我在书中所做的那样）。

## 3.1 页表

在上一章关于虚拟内存的章节中，我们提到内存必须划分为页。为了避免在映射表上浪费大量内存，我们使用分级页表。在 x86-64 中，这通常被实现为多级结构。

页表层次结构始于一个进程始终可访问的全局表，称为页全局目录。PGD 提供下一层页表的物理地址，下一层再提供下一层页表的物理地址，依此类推，直到最终提供映射数据的物理地址。

我们如何将虚拟地址映射到页表项中？我们将地址视为进入每个页表以及最终进入页面本身的一系列索引。

为了清晰起见，让我们检查具体的示例。我们在这里考虑 x86-64 的页表语义，但其他架构的原理是相同的。假设页面大小为 4 KiB，每项 8 字节，我们设置的最小映射单位为每次 512 页（即 2 MiB 地址空间）。

由于 2¹² = 4096 = 4 KiB，我们需要 12 位作为虚拟地址指向的页偏移，每个页表级需要 9 位。现代 x86-64 硬件可以支持高达 57 位的物理内存。由于虚拟访问物理上不存在的内存是没有意义的，这意味着虚拟内存地址的低 57 位是有效的，因此我们最多需要五级页表来映射虚拟内存。

> 在 x86-64 中，虚拟地址必须是规范形式，这意味着所有高位必须等于最高允许的位。例如，如果位-56 为 0，那么第 57 到 63 位也必须为 0。如果它是 1，它们也必须是 1。

（四级），其他架构或配置可能提供显著支持。内核通过定义五级页表层级并巧妙地使用宏忽略不存在的层级（将其折叠到上一级）来处理此。
