
在我们看来，这是系统管理员的“首要指令”。从首要指令推导出的最显而易见的隐性需求是“不要弄坏系统”。或者从另一个角度来看，是“保持系统运行”。当然，这两个陈述的含义并不相同。

Linux 和 UNIX 系统停机最常见的原因是操作员或管理员的错误。我们都听过某位不幸的系统管理员，在错误的目录下输入了 `rm -fr`。当以 `root` 身份登录时，其实要“弄坏”一个 Linux 系统，并不需要像这（误删命令）那样具有戏剧性或显而易见的动作。

系统管理员经常需要安装或升级新的系统软件（新内核、安全补丁等）。理想情况下，你希望在阶段环境中发布这些重大升级中的每一个，然后将其“滚动推广”到生产环境。然而，时间限制经常不允许一次性完成所有工作，而预算限制限制了阶段环境复制生产环境的能力。

此外，预计系统管理员在面对各种灾难时能够维护系统资源——从数据丢失、意外删除和损坏，到整个系统的毁坏或被盗。因此，恢复计划是另一组从我们的第一个隐性需求推导出的需求。

当我们审视“可用性”一词，并将系统资源的概念扩展到包含 `CPU` 周期、网络带宽和磁盘空间时，我们发现管理用户可能会将各种容量规划的失败视为灾难。因此，性能监控和容量规划也是隐性的。

- 维护系统可用性。
- 设计、实施和测试恢复计划。
- 监控并调优系统性能。
- 规划必要的容量。
- 提供逻辑网络结构。
- 监控并维护系统的安全性和完整性。

这些需求在第一部分的其他章节中会有详细解释。

## 促进升级、扩展和新安装

仅仅维护现有系统通常应该少于系统管理员工作的一半——或者说少于一半系统管理员的工作。随着组织的变化，其系统和网络也会随之变化。整个商业软件行业致力于说服用户更换其系统（通过升级以及新购买）。这在网络和系统变化的其他原因之外。

1991 年，Web 还是一个新奇事物——一些物理学家使用的工具和协议，用于通过易于遵循的交叉引用共享技术文档。现在，LINUX 系统管理员经常被要求做出决策和建议。LINUX 拥有 UNIX 传奇般的力量和灵活性，体现了计算的“工具箱”方法。它提供了一组“机制”，可以从这些机制中构建特定站点的解决方案，使组织免受软件供应商构想的策略的影响。这种灵活性力量对 LINUX 系统管理员来说既是祝福也是诅咒。

LINUX 和 UNIX 比其他操作系统限制少。因为它们不设定策略，我们必须选择符合我们要求的工具和方法。为了做到这一点，我们必须理解自己的需求并了解自己的选择。

这就是本书其余部分的内容。正如第 1 章“首要指令”所述，这本书的主题之一是“通常还有其他选择”。

## 进一步学习

需求分析这个主题值得写一本书，例如 `Donald C. Gause` 和 `Gerald M. Weinberg` 编写的《探索需求：设计之前的质量》（`Exploring Requirements: Quality Before Design`）。尽管它是为软件开发者编写的，但它是该主题的极佳资源。

学习需求分析可能会深远影响你的个人生活以及职业。学习区分需求和偏好，识别任何问题或过程中的参与方，定义约束条件，设定优先级，并通过推迟对任何提议解决方案的承诺直到……从而使自己能够“跳出思维框”。

如第 15 章“自动安装与升级”中所述，`Red Hat` 发行版支持 `KickStart` 功能（概念上类似于 `Sun` 的 `JumpStart`），它允许系统管理员编写脚本来自动完成安装过程，包括驱动器分区、文件系统创建 (`mkfs`)、软件包选择、安装和配置。这可以用于为新系统创建一个“无人干预”的软磁盘。第 15 章“自动安装与升级”中也讨论了其他形式的自动安装。

对于许多系统而言，自动安装过程可能比传统的“备份/恢复”方案提供更有效的恢复。在典型的工作站上，分配给“易耗”文件（那些包含在操作系统和应用程序安装 `CD` 中的文件、缓存等）的空间远大于系统数据本身。知晓此，系统管理员可以专注于保护数据。实现这一目标有多种方法。

除了维护救援盘外，在每个系统驱动器上额外创建一个额外的小型分区，用于存放内核和全套修复工具以及配置快照是明智之举——`100MB` 的空间完全足够了。这样，如果根分区变得不可用，可能会启动到这个救援分区并修复或替换根分区。当然，在某些磁盘故障和/或损坏的情况下，这种方法无法恢复，因此救援磁盘可能仍然有用。

有一种巧妙的方法可以设置一个系统，使其能够从根文件系统某些类别的损坏中自动恢复。设置生产根分区和“救援根”，并在它们之间复制所有基础文件。在救援根上，放置一份生产根 `/etc` 文件的额外副本（或许放在一个 `.tar` 文件中）。

然后，修改救援根上的 `/etc/rc.d/.*` 文件，以对生产根执行 `fsck` —— 并带有错误处理程序和超时设置，以便在必要时跳过文件系统检查；使用异常脚本（`except script`）是实现此目标的好方法。如果 `fsck` 失败，你可以编写脚本执行 `mkfs.ext2` 生产根并进行恢复——复制并提取生产环境 `.etc.tar.gz` 文件，以覆盖两个系统之间存在差异的文件。结果是，“救援根”可以自动恢复生产模式下使用的文件系统。

### 该技巧的后续部分

分区表与引导加载程序代码

`/sbin/lilo -R root=/dev/sda3`

此命令将为下一次重启设置默认命令行，而不会影响后续的重启或默认设置。因此，如果系统正常关闭，它将从生产文件系统启动。如果通过其他方式重置，它将默认进入“自动救援”模式。

在 Linux 下，要确保从损坏的分区表和系统主引导记录 (`MBR`) 的损坏中恢复很容易。`MBR` 是任何 `PC` 硬盘上第一个磁道第一个磁头的第一个扇区。它由两部分组成：一些引导加载代码和分区表。

引导加载代码由系统上的任何操作系统提供。大多数 Linux 使用安装在主硬盘 `MBR` 上的 `LILO`（Linux 加载）。另一些则使用 `GRUB`（GNU GRand Unified Bootloader）。在其他情况下，人们可以在 `MBR` 上使用 `System Commander` 或 `Windows NT` 或 `OS/2 Boot Manager`，并在逻辑引导记录（或根文件系统的超级块——或者任何 Linux 文件系统，无论如何）中运行 `LILO`。

在许多常见情况下，引导加载代码可能会被替换或损坏，而不会影响分区表，尽管它们共享同一个扇区。大多数启动扇病毒和许多操作系统的安装软件会将 `MBR` 中的引导代码替换为它们自己的版本——通常将现有的引导加载器移动到零道上的另一个“未使用”扇区上。

因此，当引导加载代码被覆盖时，通常有恢复它的需求。简单的方法是直接运行 `/sbin/lilo`。这将在（默认情况下）读取 `/etc/lilo.conf` 文件并根据其中的指定构建新的引导记录。它会将现有的分区表附加到引导加载器，并合并 `LILO` 映射文件的 `BIOS` 磁盘地址。这些映射使 `LILO` 引导加载器能够找到内核、启动消息和其他文件，而无需“感知”存储这些文件的文件系统。

因此，在引导加载代码被（例如）`Windows NT` 的最新重新安装替换后，只需运行不带参数的 `/sbin/lilo` 即可（假设存在正确的 `/etc/lilo.conf` 文件）。

人们可以采取防御性措施，例如在每次关机时重新运行 `lilo`。然而，在以下系统简单为无法启动的罕见情况下，这样做可能风险更大：

3. 商业引导加载程序和分区表，它们对于启动多个版本的 `MS-DOS` 和/或其他操作系统特别有用——这些系统通常无法共存。
4. 注意 `LILO`（引导加载程序包）与 `/sbin/lilo`（生成引导块的命令）之间的区别。更多细节请参见第 9 章“启动与关机”。

内核、分区表或启动消息文件已更改。在任何情况下，没有比维护一个经过良好测试的救援软盘和近期备份更有效的防御措施了。

如所述，`lilo` 不会修改或恢复分区表。这可以通过 `fdisk` 手动完成。然而，有一种简单的方法可以实现该自动化。使用 `dd` 命令对 `MBR` 进行快照（即使仅是最后的 66 字节——这包含四个每个 16 字节的分区表条目及其签名 `0x5AA`）。以下是将整个 `MBR` 保存到根目录的示例：

```
dd if=/dev/hda of=/root/mbr.bin count=1
```

注意我们使用的是设备名称代表整个磁盘，而不是 `/dev/hda1`，后者仅指向第一个分区。对于 `SCSI` 磁盘，我们将使用 `/dev/sda` 作为输入文件 (`if`)。`Gnu dd` 默认块大小 (`bs`) 为 512 字节，尽管我们也可以通过该参数进行谨慎操作。

要将此 `MBR` 还原系统，只需反转 `dd` 命令的 `if` 和参数：

```
dd if=/root/mbr.bin of=/dev/hda count=1 bs=512
```

并运行 `lilo`，内核映射可能发生了变化。

当然，我们也可以使用不同的参数通过 `dd` 保存分区表：

```
dd if=/dev/hda of=/root/ptable.bin count=66 bs=1 skip=446
```

我们将其恢复：

```
dd if=/root/ptable.bin of=/dev/hda count=66 bs=1
```

在这些情况下，我们不需要运行 `/sbin/lilo`，因为我们没有触及 `MBR` 前 446 字节的引导加载器。
