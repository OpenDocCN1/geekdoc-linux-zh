
这里的点是，用户不仅限于原始程序员在 `MH` 中内置的功能范围。人们只需要将 `MH` 命令与其他 `Unix` 命令结合，就可以创建新的、实用的功能。这不需要新的编程。用户可以根据意愿组合命令。如果所需的功能不存在，就可以创建。

只需花费极少努力就能立即完成。通过这种简单而强大的架构，许多功能可以在用户的命令行上根据需要临时开发。

人们有时会对 `MH` 提出一个有效的问题：你如何记住哪些命令是可用的？例如，熟悉 Berkeley Mail（伯克利邮件）命令的人知道可以通过输入“?”来获取可用命令列表。`MH` 在这方面非常出色。由于它没有使用鼠标用户界面（`MUI`），你可以随时参考在线的 `Unix` 手册页（manual pages）。这些手册页比 Mail 提供的短命令列表详尽得多。因此，`MH` 的操作文档更为详备，因为每个单独的命令通常有一整页（甚至更多！）的文档。

那么那些偏好使用 `MUI` 的用户呢？`MH` 提供了 `msh` 命令，供那些喜欢被提示下一步操作操作的用户使用。显然，如果用户不选择，他们并不被局限于 `msh`。他们可以自由编写自己的用户界面，将其作为 `MH` 命令集之上的层来运行。例如，`xmh` 是一个 `MH` 的用户界面，它在 Windows 系统下作为客户端运行。`xmh` 应用程序中的按钮和菜单项只需根据需要调用底层的 `MH` 命令。然而，`xmh` 用户界面为用户提供了一个无缝界面。它看起来就像是一个直接执行邮件处理功能的应用程序编写的。

`MH` 为我们提供了一个在 `Unix` 下构建复杂应用的绝佳示例。图 8.1 展示了更通用的情况。

小程序层（Small Programs Layer）由一组 `Unix` 命令或 shell 脚本组成，每个执行应用程序的一个功能。当需要新功能时，创建其他小程序来提供所需的功能是非常容易的。另一方面，如果想要功能有限的应用，则无需任何操作。应用程序层（Application Layer）只需停止调用那些必要的程序即可。

应用程序层决定对用户至重要的功能。功能本身由小程序层执行。它

封装了业务规则并为应用程序提供了边界。应用程序层主要作为小程序层和用户界面层之间的纽梁。通过在单一环境中统一小程序层的元素，它有助于建立小程序之间的关系，并提供将它们结合在一起的框架。换句话说，它是集成层。

用户界面层（User Interface Layer）是用户在调用应用程序时在屏幕上看到的部分。它是高度可塑的，因为根据所需的展示效果可以有多种用户界面样式。`Unix` 环境中最常见的三种用户界面样式是：命令行驱动的用户界面，参数从命令行传递给命令；滚动菜单类型，一种 `CUI`（字符用户界面），通过与用户的一系列交互式对话收集参数；以及 `GUI`（图形用户界面），通常在具有图形能力的 PC 上找到，如 X Windows 系统下的界面。

构建良好的应用程序层允许用户从多种用户界面样式中进行选择，这意味着用户界面层永远不应该是“硬编码”的。用户应该自由选择适合特定情况的界面。因此，用户可以利用 `GUI` 提供的强大功能进行偶尔使用，但在性能重要时，仍然选择使用滚动菜单界面。`MH` 及其伴侣 `xmh` 提供出了一个结合了这种灵活性的应用示例。

在上一章中，我们看到整体往往大于部分之和。这对于 `Unix` 哲学本身也同样如此：它的每一条准则几乎都没有独立立足的力量。除非你有操作数据的工具，否则将数据存储在扁平文件中意义不大。如果没有 shell 脚本和 `C` 语言来实现，可移植性优于效率的目标似乎就无从谈起。如果一组小程序不能作为过滤器（filters）使用，那么编写它们就意义不大。

`Unix` 哲学就像游乐场里的一个巨型水滑梯。你不能在玩到途中决定想跳过几个弯道——你只会满身青紫地摔在地上。正如许多人通过教训发现的那样，如果你碎片化地使用 `Unix` 哲学，它是不起作用的。

## 8.1 Unix 哲学：整体整体

然而，当 `Unix` 哲学的准则结合在一起时，它们展现出更广泛、更强大的维度。它们相互运作并相互加强。对任何单一准则的批评都可以得到另一个准则的回应。“团结者胜，分者必亡”的古谚在这里是不为真理。

让我们再次回顾 `Unix` 哲学。这次，我们将关注准则之间的关系，目标是揭示通过共同使用它们所产生的协同效应。

小程序具有明确的优势。它们更容易理解，因为人们处理小东西比处理大东西要容易。更容易理解也意味着它们更容易维护。因此，最终它们更具成本效益。它们使用的系统资源也更少。这意味着它们能够被快速加载、运行和释放，从而产生更高的效率，而这种属性是为了获得更大的可移植性而必须牺牲的。最后，小程序与其他工具结合。它们本身的作用很小。在与其他小程序的协作下，它们让程序员——重要的是用户——能够快速创建新的应用程序。

小程序应该保持专注（即它们应该只做好一件事）。解决一个问题比在大型程序中解决一系列问题更重要。通过将大型复杂的问题拆分为更小的问题，就可以逐个攻克。做好一件事的程序可以更容易地在其他应用程序中重用。它们的能力被定义得很清楚，不会被可能模糊功能定义的无用“垃圾代码”（cruft）所干扰。

做好一件事的小程序避免了变成巨大的单体。这些单体通常包含“面条代码”，难以与其他应用程序连接。小程序承认了这样一个明天：今天的功能看起来可能不完整，或者甚至是过时。单体程序涵盖了所有已知情况，而小程序则坦然承认软件是进化的。软件永远不会完成，只有发布。

由于世界软件处于不断演化的状态，每个人都在学习曲线上。没有人能绝对地预测软件世界明天将走向何方。能做的最好就是基于未来会变化的假设，构建满足今天需求的软件。因此，与其花费几周或几个月编写设计规范，不如开发者应该记录他们计划采取的方向的概述，然后着手去做。

早期构建原型是一个重要的步骤。它帮助设计者尽早将应用程序交付他人，以便让第三系统的开发尽早开始，而不是推迟。

他人为你所的工作。脚本可以帮助这些工作对世界产生的影响产生积效应，同时让你能够投入更少的精力完成更多的工作。

如果你有一系列小程序可以操作，构建脚本就会变得简单得多。然而，如果这些程序需要用户直接输入信息，那么它们就大派用处。因此，请避免字符用户界面（`CUI`）。相反，将所有程序都视为过滤器。程序不创建数据，它们只修改数据。这让你的程序易于在任何地方使用。

协同。这一切关乎协同效应。

就这些吗？嗯，是的。大多数 `Unix` 和 `Linux` 程序本身并不值一谈。你总能在 `Unix` 系统上找到比它们更好的文字处理程序、更酷炫的电子邮件程序，或者更精美的目录文件夹视图。（不过，某些 `Linux GUI` 应用程序其本身也相当令人印象深刻。）然而，如果你尝试对文本进行一些单体文字处理器并非设计用来执行的操作，你会发现 `Unix` 是非常强大且胜任的。

其他操作系统的支持者声称，特定的操作系统在某些方面比 `Unix` 做得更好。这在某些情况下可能是事实。即便如此，`Unix`（以及随着其日益成熟的 `Linux`）可能也能在编写新应用程序所需时间的一部分内提供 90% 的解决方案。此外，`Unix` 几乎在所有情况下都能提供这 90% 的解决方案，即使在那些看似无法实现的情况下。

但等一下。我们在这里进展太快了。如果你想学习 `Unix` 哲学与其他操作系统哲学相比的优劣，是时候进入下一章了。

如果你曾尝试根据动态变化的业务规则修改数千份文档中的文本字符串，那么你就理解了文字处理器的一个局限性。那需要一个非常好的过滤器程序。另一方面，如果你正尝试创建一个文档的版本，那么文字处理器就是一个极佳的工具。

## Unix 与其他操作系统的哲学

在此时，简要讨论一下 `Unix` 之外的几个其他操作系统的哲学是合适的。我们不会深入探讨这一领域，因为我们并不打算写一篇关于操作系统哲学哲学的比较性论文。但对软件世界中其他几种“宗教”进行简短探究应该能带来启发，仅仅是为了阐明为什么 `Unix` 的方法与其他软件设计方法相比是如此激进的背离。

在本章中，我们将观察三个历史操作系统的设计哲学。它们在各自的领域都取得了成功。它们都培养了一批忠诚的追随者。它们都与 `Unix` 和 `Linux` 具有某些共同点，并且都带有某些使其与众不同的特征，有时是以令人惊叹的方式。

由于多种原因（其中最重要的是硬件能力有限），这些操作系统是为特定的硬件平台编写的。用户需要充分的理由才值得花费几千美元购买这些灵活性不大的系统。你不会在折扣零售店和跳蚤市场上找到成千上万的可用应用程序。个人电脑并不便宜，也不常见。很少有人有旧电脑在地下室的一堆未使用的家庭用品上落灰。

更新、更快的硬件最终到来了，导致这些操作系统被废弃。由于缺乏 `Unix` 的移植性，当硬件设计师生产出具有不断增加的存储、专用外围和先进图形能力的机器时，它们就无法跟上。这里唯一的例外是微软的磁盘操作系统（`MS-DOS`）。它被移植到日益强大的机器上，但它们本质上都是采用相同的架构。在较后版本的 Windows 中，微软已几乎完全消除了 `MS-DOS`，转而采用 Windows API 和 `GUI`。

尽管这里讨论的操作系统本身已在很大程度上淡出了历史舞台，但它们的设计哲学仍然以某种形式存在。例如，虽然雅达利家用电脑（Atari Home Computer）的生产早已停止，但其操作系统中的人机工程概念在当今最热门的游戏机仍在继续实施和完善。
