# Java

原则：可移植、扁平、重用、树形、并行、分级

核心概念：选择可移植性优于效率。

太阳微系统公司（Sun Microsystems）的 Java 编程语言本身就是一个现象。作为曾经被 C 语言占据的“主流可移植语言”王座的继承者，它已牢确立了自己作为新应用开发事实标准语言。它并不完美，也有自己的怪癖。然而，它正被日益进步的大众迅速采纳。

太阳的宣传口号“一次编写，随运行”听起来充分体现了可移植性的价值。虽然 Java 比 C 更具可移植性，但它的效率仅为后者的 95% 左右。考虑到 Java 可移植性的上述优势，很难理解为什么有人会担心那 5% 的效率损失。

尽管如此，旧习性难改。对于那些坚持要榨干硬件每一分性能的纯主义者来说，C 仍然是首选语言，对于许多 Linux 开发者（尤其是从事 Linux 内核开发的开发者）也是如此。这没关系。相比之下，只有少数人实际上从事内核工作。到目前，最大的开发者群体是那些在 Linux 和 Windows 平台上编写应用程序的人。Java 完美契合这一需求。

在推广 Java 作为开放标准方面，太阳公司在专有控制和开源灵活性之间寻求到了平衡，做得相当不错。许多开发者对太阳保留对 Java 命运控制权的动机表示怀疑，并更倾向于让 Java 的演进由一个公开的开放标准机构来管理。但我们将这些问题留给营销人员和战略家，转而关注该语言的技术和哲学方面。

代码重用在 Java 程序员中非常流行，这很大程度上归功于其面向对象的体系。通过分级继承机制，大多数 Java 类都利用了继承链中由他人编写的代码。新类通常是现有类的扩展。尽管太阳公司进行了营销，但这种易于重用的特性让 Java 获得了快速且广泛的接受。

Java 通过其属性文件机制遵循了 Unix 哲学中“使用扁平文件”的原则。虽然在某些应用环境中，Java 配置信息存储在二进制文件中，但 Java 属性文件表面上是人类可读的。系统上的文本搜索引擎也可以对它们进行索引，使开发者能够轻松在瞬间定位环境中的任何属性。

Java 不仅仅是对并行操作口头支敬。它的类包含了一组用于创建和操作线程的对象。因此，今天许多 Java 应用都是多线程的。这并不总是是好事，因为一些开发者发现了许多滥用这种机制的方法。但总的来说，它很好地服务了 Java 社区。

另一个正确的方向是太阳的 Javadoc。该工具从源代码的注释中生成 HTML 格式的 API 文档。由于输出是 HTML，大多数 Javadoc 文档通过网络浏览器查看，而不是打印文档本身。我们在这里节省了数公顷的森林。

考虑到 Java 所做的一切，还有什么是它做错的吗？虽然 C 语言中令人讨厌的 `#include` 指令导致了变量之间无尽的命名冲突，但 Java 找到通过其类路径（`classpath`）机制重新发明这种噩梦的方法。一次又一次，我们看到程序员在类路径问题上的挣扎，就像 C 程序员在 `#include` 指令上的问题一样。也许有一天会有人发明解决这个问题的方案。在此，我们只能忍受它。

最后，关于谁控制 Java 的问题会反复浮现出来。许多硬核 Linux 开发者避开 Java，因为它并不像他们认为的开源应有的那样开源。这种想法可能过于局限。太阳微系统公司在 Java 方面扮演着某种仁慈独裁者的角色。它向任何想要的人提供源码。它响应建议和批评。它只是想保留某种程度的控制权，以确保它们不会被另一个实体污染或侵占。

另一个实体是微软。太阳正在与微软进行一场生死攸关的象棋博弈，努力从这个软件巨头手中夺回开发环境的控制权。与此同时，微软通过引入 `.NET` 试图动摇 Java。Java 能生存下来吗？这取决于 Java。

所有的需求都需要预先提出，因为有人要为这些需求编写测试。

问题在于，随着需求的不断变化，后期没有足够的时间来修改这些测试。更好的做法是先花时间构建一个不带测试的原型，将其交给用户，然后再编写测试。这样，你编写的测试更少，并且能花更多时间去贴合客户真正的需求。然后，为了提高应用程序的整体质量，你只编写那些投入产出率最高的测试。这与使用代码性能分析器来确定程序在何处耗费时间，然后投入 10% 的精力来获得 90% 的改进并无异。

尽管存在这些差异，但我怀疑 Unix 社区和 XP 社区的关系非常融洽。他们有着许多共同的目标，方法也相当相似。XP 和 Unix 就像英国和美国。他们有共同的根源，说着同一种语言。但英国人稍微更正式一点，而美国人在方法上则更带有一种“牛仔”气息（随性、野）。

## 重构 (Refactoring)

- 准则：`SMALL`, `THING`, `PROTO`, `FILTER`, `90cent`
- 核心概念：简化，再简化。

如今重构的思想是将程序员、黑客和其他捣索者们喜欢做的事情形式化：通过调整某些东西来使其变得更好。他们主要的倡导者可能是《重构：改进现有代码的设计》一书的作者马丁·福勒（Martin Fowler）。所有重构工作背后的基本思想是：可以在不改变软件外部行为的情况下，改进其内部结构。

重构的一个酷点在于，它能帮助你意识到接口的重要性，这可能比你过去理解的要重要得多。当你讨论一个由大量小型且协作良好的工具构成的系统时，这一点至关重要。除非在它们之间定义稳固的接口，否则你最终只会得到堆没有任何逻辑可言的杂物。换句话说，你得到的是一团乱麻。

开发者和其他哲学家正在撰写大量关于设计模式以及今天软件重构中使用的其他技术的著作。遗憾的是，人们终于开始描写那些在程序员脑海中运行了多年的过程了。这种分析只能让我们更好地理解我们所的工作，并向改进我们所的工作迈进。

重构的一个公理是，它应该以小规模、增式的更改进行，而不是大规模的重写。在这里，Unix 哲学家和重构者有着共同点。Unix 开发者一直采用小规模、增量、迭代的开发风格。然而，就像 XP 方法论与 Unix 哲学之间的区别一样，Unix 方法与重构者有共同基础，但在至少一点上不同，即愿意“丢弃东西”。重构者很少提倡对任何东西进行完全重写。Unix 开发者经常构建第一系统，将其丢弃，然后构建第二系统，并且非常清楚这是通往第三系统（即正确的系统）最快捷的路径。因此，Unix 开发者在这方面更大胆一些。有时一个系统太糟糕，通往软件乌托邦最快的方法就是走另一条路。

在重构中做出的许多决策都是为了帮助软件符合特定的设计模式，或者在情况不符合任何已知模式时发明一种新模式。所有的设计模式无论多么雄辩，都仅仅是原始设计模式的超集；也就是说，每个程序都是一个过滤器。这类似于古老的时代，一切都是 0 和 1。最复杂的数值或逻辑系统也总可以归简化为一系列二进制表示。

在重构中，当人们寻求合适的设计模式作为架构的模型时，最好记住：只有当你能以单输入单输出过滤器的形式表达它时，你可能才完全理解了一个程序的逻辑过程。当你达到那种理解水平时，你就可以进行重构了。

## Apache Jakarta 项目 (The Apache Jakarta Project)

- 准则：`SMALL`, `THING`, `PROTO`, `REUSE`, `sum`
- 核心概念：开源协作利用许多人的工作，产生巨大的收益。

当观察 Apache 项目的协作水平、对标准的忠实执行、诚实的技术互动以及产出持续的高质量时，可以得出一个结论：开源开发是有效的。

从项目的治理方式、软件编写方式以及用户的热烈接受程度来看，Jakarta 显然已经立了一个标杆，让所有专有软件开发者都警觉起来。

是什么让这个项目如此成功？并不是单一的因素。是所有部分的总和使其成为一个强大、凝聚的开发组织。但如果必须选出一个比任何其他因素更有影响的因素，那就是“社区比软件更重要”这一观点。换句话说，许多智者的民主式协作优于为单一（通常运营良好的）实体工作的开发者等级制度。

Jakarta 软件任何人想要的人都可以免费获取。由于该软件公认的高质量，大型公司一直在使用它来运行关键业务功能。此的副作用是，顾问和开发者涌现出来，提供定制化服务以使软件适应特定行业。这说明了一个重要的原则：免费软件仍然可以从中获利。

我们看到计算行业经历了几次大范围的机遇浪。首先是硬件浪，大量资金投入了硬件。第二波浪是软件浪，让 IBM、Novell 和微软等公司脱颖而出。下一波浪是服务浪，每个人都可以随时获取任何内容。注意，当 PC 的商品化导致硬件利润消失时，第一波浪潮结束了。同样，免费软件让从软件赚钱变得几乎不可能。盈利能力现在位于光谱的末端。
