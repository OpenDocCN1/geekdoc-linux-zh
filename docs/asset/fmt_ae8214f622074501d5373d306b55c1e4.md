
这两种技术对于手动操作或手动运行的脚本都是足够的。后者仅复制分区表的形式更适用于定时任务——每天获取分区表快照，并与原始备份对比，如果有差异则发送警报。我们还可以测试 MBR 的完整性——尽管应该注意，`sbin/lilo` 需要在它创建的引导代码中包含某些时间戳。这样，任何运行 `lilo` 的操作都会导致 MBR 的 LILO 部分发生变化，即使相关文件没有任何变化。

当从灾难性故障恢复系统时，可以跳过 `fdisk` 执行，直接使用 `dd` 将新的分区表置到位。虽然在理论上这应该对具有相同几何结构的磁盘进行，但在大多数现代磁盘（SCSI 和 IDE）上都是有效的。事实上，现代磁盘的内部几何结构对主机系统来说越来越没有意义，因为位记录被用于实现每轨道不同数量的扇区、自动翻译、线性块寻址以及其他使得传统的“柱面、头部、扇区”模型过时的抽象。无论在任何情况下，对于大小相似的硬盘，`dd` 命令可以自动化准备分区表的过程，并可以使用如下类似的命令：

```
for i in hda3 hda4; do mkefs -c q /dev/$i; done
```

用于在选定的分区上创建新的文件系统。在这个示例中，我们假设 `/dev/hda2` 可能是一个交换分区，并显示一个可能用于 `/usr` 和 `/var` 的列表。

有一个工具可能帮助到那些在分区表损坏之前没有预见并对其进行备份的人。Gordon Chaffee 编写了一个小工具来创建分区表。可以在此处找到：

```
http://bmrc.berkeley.edu/people/chaffee/fat32.html
```

## 文件系统

文件系统应该是健壮的，以避免用户和系统管理员删除和覆盖所需文件的问题。大多数当前的文件系统缺乏某些功能，尽管有几种类型的文件系统能够提供这些功能。

每当文件写入磁盘时，不应将文件的旧版本标记为删除。相反，应该将其标记为只读并从普通视图中隐藏。可以使用如 `ls -a` 的命令查看这些副本以及其他隐藏文件。

此时，一种预计提供此类功能的文件系统名为 `ext3`，正在为 Linux 开发。版本号为 2.4 及以上的 Linux 内核预计将包含 `ext3`。

此类文件系统的替代方案是快照文件系统。定期对文件系统进行快照（例如每小时或每天）；这些快照包含了快照时刻 `inode` 的只读副本。一个示例实现是 Network Appliance 的文件系统。

Linux 目前没有快照文件系统，但系统管理员可以在用户空间实现一种粗略的近似方案。这样做是将整个文件系统或目录结构复制到另一个文件系统上。

## 快照分区

磁带驱动通常很慢，在许多地方，其成本使其在内部网络中是合理的。白天需要需要的恢复通常本身就是一项任务，并且可能消耗一些网络带宽。更糟糕的是，需要某个文件树的用户通常没有足够的权限来访问给定磁带上的所有其他文件。因此，通常需要系统管理员从磁带服务器并在多用户主机上恢复文件。

大多数数据丢失是由用户或系统管理员的意外删除造成的。通常，这种丢失会在几分钟内被察觉。如果有一个只有一天以前的文件副本，并且可以通过简单的 `mount` 和 `cp` 命令序列轻松检索，那么恢复将节省一些时间并真正给用户留下深刻印象。这可以通过每晚 `cron` 任务来实现：挂载伪快照文件，运行 `rsync` 脚本将伪快照与配置文件系统同步，然后卸载。

请注意，这与使用 `md` 驱动命令或硬件 RAID 控制器进行 RAID 镜像完全不同。那些是解决不同问题的解决方案。如果有人不小心删除了 RAID 文件系统上的文件，在进行任何恢复工作之前，它几乎肯定会从磁盘上移除。RAID 旨在防止硬件故障——硬盘的丢失、某个磁头的崩溃或（在某些配置下）甚至是磁盘控制器的丢失。

我们的伪快照模型依赖于事实：意外删除在一天结束前被检测——在用户按下回车键后的几分钟内。然而，可以在不同的间隔处维护多个快照。

当然，可以在生产文件系统和快照文件系统上 RAID 镜像、条带和冗余，并结合此类脚本应用于任何配置。

这种技巧的变体是使用“空”分区和/或未在其创建文件系统的整个硬盘。你可以将这些作为 `tar` 或 `cpio` 命令的目标。由于 `ext2` 文件系统对任何单个文件的最大大小有 2GB 的限制，因此使用“原始”磁盘分区进行类的“快照”存档是非常方便的。

将快照导出到高级用户工作站的一个优势是，它使系统管理员能够直接访问以恢复文件。人们可以在 `/etc/fstab` 文件中将这些快照文件系统标记为用户可挂载（详情见 `man 8` 和 `fstab 5`）。这允许用户在没有系统管理员干预的情况下恢复自己的文件，且不会带来安全和访问问题（假设是目录树的递归而不是使用 `tar` 或 `cpio` 分区）。

对完整目录树拍摄快照的一种方法是使用 GNU `cp` 命令的 `-a`（归）选项。这等同于其他选项的组合，可以递归目录结构并保留所有权和权限。通常还可以包含 `-x` 选项以防止目录递归跨越文件系统边界（进入其他挂载的文件系统）。因此，为了在辅助驱动器上对根、/usr、home 目录树制作快照，我们可能会使用如下脚本：

```
mount /dev/sdbl /mnt/tmp &&
cd /mnt/tmp &&
cp -ax /usr /home 
mount /mnt/tmp
```

在这个示例中，我们使用条件执行来确保如果 `mount` 或 `cd` 失败，则不执行 `cp` 命令。

请注意，这些风险必须从其对业务的影响的角度进行评估，而不仅仅是它们对计算机系统的影响。

这里我们列出了系统管理员面临的一些常见风险。大多数系统管理员都会要求一个计划来应对所有这些风险，但某些人会发现，为某些类型的灾难做好准备的必要性与其成本并不相符。

最需要恢复的常见灾难是删除或覆盖了所需的文件。在理想的世界里，这永远不会成为一个问题，因为所有文件系统都支持日志记录（journaling），而且用户能够自己从这些错误中恢复。好消息是，Linux 的日志文件系统正在取得进展。在此，系统管理员必须准备好为删除了文件的用户恢复文件。在大型组织中，系统管理员部门可以为每次恢复向用户所在部门收费。这鼓励用户要谨慎对待，并且只请求真正需要的文件，这对整个组织而言是一种节约举措。

与用户误删几乎一样常见的是管理员的误删。虽然系统管理员通常比普通用户谨慎得多，但他们使用的命令本质上更危险。因此，当系统管理员出错时，其错误规模通常比任何用户可能造成的都要大。同样，更好的文件系统将对此有所帮助，但不一定能达到解决用户面临的那种单文件删除问题的程度。

系统管理员应该养成使用双安符（`&&`）而不是分号（`;`）执行严格命令的习惯。这确保了例如，如果 `cd` 失败，接下来的 `rm` 将不会在错误的目录下执行。正如我们在第 11 章“脚本”中讨论的，脚本是减少拼写错误导致灾难概率的更好方法。

此外，系统管理员应该始终使用绝对路径。某些命令在文件系统的不同位置可能有不同的意图，调用错误的命令可能会导致严重后果。使用绝对路径可以防止特洛马程序的攻击。

为了减少管理员错误的概率，在对生产系统进行任何类型的更改时，制定一个测试、部署和回归的计划是非常重要的。你应该让其他人检查该计划，然后遵循该计划。

## 硬件故障

硬件故障是另一个常见的危机原因。防止硬件故障的最佳防御是冗余系统和手头备件，以及一套熟练的更换故障硬件程序。当硬盘故障时，该程序有时会很复杂，并且应该有良好的文档记录。

## 公用事业中断

在世界的某个地方，电力和电信等公用事业并非完全可靠。在某些地方，可靠性比其他地方差。但必须始终考虑公用事业中断对业务可能的影响，以及在准备和响应方面可以采取什么措施。

停电通常会导致 Linux 系统非正常关机。至少在服务器的情况下，许多组织将有足够的 UPS（不间断电源）容量来执行正常关机。许多组织拥有自己的发电机作为应急电源，并配电池处理转换。这种应急电源并非没有成本，因此要确定哪些系统对业务运行至关重要，并确保它们有持续电源。

许多数据中心拥有独立的电源（来自不同的公用事业变电站），机柜带有来自每个电源的电源插。一个运行左侧，另一个运行右侧。具有冗余电源的系统（如路由器和主要服务器）插在每个电源上。通常，两个电源源中至少有一个由发电机和电池备份，因为公用事业中断往往会影响多个变电站。

外部数据通信的中断不如失去电力那样具有灾难性，但它可能会导致某些业务停运并损害其他业务的运行。如果失去电信的成本对业务来说是值得付出的，就需要冗余。你可以从建筑内不同的分界点处订购线路，沿着不同的线沟通到电信中心局。所有这些费用都需要钱，并且从根本上是一项业务决策。系统管理员的角色是帮助记录风险、选项及其成本，以便管理层做出明智的决定。
