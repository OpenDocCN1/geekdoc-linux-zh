
```，以确保函数 `foo()` 在汇编中会被调用 `bar`。

注意，来自 `binutils` 软件包的 `objcopy` 工具应该允许你将 `a.out` 对象转换为 `ELF` 对象，在某些情况下也可能反之亦然。更通用地说，它将执行许多文件格式转换。

### 5.1.3. 直接 Linux 系统调用

通常你会听人说 C 库 `libc` 是唯一途径，而系统调用是不调用的。这在某种程度上是正确的。通常情况下，你必须知道 `libc` 并不安全，在大多数情况下它只进行检查，然后调用内核并设置 `errno`。你可以在程序中这样做（如果需要的话），你的程序将减小几十倍，这也会提高性能，仅仅是因为你没有使用共享库（静态二进制执行文件更快）。或者，在汇编编程中不使用 lib 更多是一个出于情趣或考量的个人偏好/信仰问题，而非实际性问题。请记住，Linux 的目标是符合 POSIX 标准，lib 也是。这意味着任何 lib “系统调用”的语法与真实内核系统调用的语法完全匹配（反之亦然）。此外，GNU `glibc` 随着版本的更新变得越来越慢，消耗也越来越多；因此，使用直接系统调用的情况变得非常普遍。但抛弃 lib 的主要缺点在于你可能需要自己实现几个 `libc` 函数（而不仅仅是系统调用封装器，如 `printf()` 等），你准备好了，不是吗？

以下是直接系统调用的优缺点总结。

**优点：**

- 尽可能的体积；压榨出系统的最后一个字节
- 尽可能快的速度；从你喜爱的基准测试中运行出循环
- 完全控制：你可以根据特定的语言或内存需求或任何需求来调整你的程序/库
- 不受 lib 编写技巧的污染
- 不受 C 调用约定的污染（如果你正在开发自己的语言或环境）
- 静态二进制执行文件使你独立于 lib 的升级或崩溃，独立于指向解释器的悬空 `!` 路径（且速度更快）
- 仅仅是为了好玩（你不觉得写汇编程序很有趣吗？）

**缺点：**

- 如果你电脑上的任何其他程序都使用了该 lib，那么重复代码实际上会浪费内存，而不是节省内存。
- 在许多静态二进制文件中冗余实现的服务是内存浪费。但你可以将你的 lib 替代品变为共享库。
- 通过某种字节码、字码或结构解释器来节省空间，比用写来写一切要好得多（解释器本身可以是 C 也可以是汇编）。保持库精小的最佳方法不是拥有多个二进制文件，而是让一个解释器进程处理带有 `#` 前缀的文件。这就是 OCaml 在代码模式下（与原生代码相反）使用时的工作方式，并且与使用 lib 兼容。这也是 Christian 使用 Perl Powers 实现 unix 工具的方法。最后，最后一种让事物保持精小的方法，它不依赖于硬编码路径的外部文件（无论是库还是解释器），就是只保留一个二进制文件，通过指向同一二进制文件的命名良好的硬链接或软链接将以最优空间提供你所需的一切，且没有子程序或未二进制文件的冗余；它将根据 `argv[]` 分发其特定行为；如果未使用可识别的名称调用，它必须默认设为 `a`，并且可能还可以作为解释器使用！
- 你无法从 Linux 系统调用中从 lib 提供的许多功能获益：即手册页第 3 节中描述的功能，如 `malloc`、线程、密码、高级网络管理等。
- 因此，你可能需要实现 lib 的大部分部分，从 `printf()` 到 `malloc()` 再到 `getbyname`。有了冗余的编辑，这有时会非常无聊。有些人已经实现了 lib 的“轻量级”替代品——去看看它们吧！

### 6.2.1. 程序布局

程序可以分为若干部分：`.text` 用于代码（只读），`.data` 用于数据（读写），`.bss` 用于未初始化数据，以及一些用户定义的部分，但实际上只有少数其他部分。现在我们将展示你的第一个程序。代码如下：

section .data

msg      db          "Hello, world!",0xa
