
一家石油公司使用一个系统在墨西哥湾进行地震勘探以寻找石油沉积。他们每天获得数 GB 的数据，这需要在系统集群上使用九十多块大硬盘。所有数据必须随时可用。出于安全考虑，没有地质学家可以持有访问所有数据的密钥，担心该个人会带着价值数十亿美元的关于下一次钻井位置的知识跑掉。

一家电信公司每天在数据库中存储超过 1000 万条记录，他们设计了一个新系统，允许他们每天插入超过 1 亿条记录。处理每秒超过 1000 次数据库插入已经足够困难了。现在他们必须处理高峰期每秒多达 5000 次的插入。

电力公用公司有一个系统，是美国最大的州之一的电网的中央控制器。停电将导致数百万人没有电，直到系统修复。

## 3.2 第三条原则：尽早构建原型

Unix 的开发者们显然不知道 Unix 之后会发生什么。MS-DOS、OpenVMS 以及每种操作系统的开发者们也是如此。每一个新的操作系统——Linux 也不例外——都会让设计者进入未知水域。他们唯一的希望就是不断收集进展，然后根据情况进行纠正。

例如，肯·汤普森（Ken Thompson）在编写第一个 Unix 内核时，意识到可移植性的重要性了吗？显然没有，因为他用汇编语言编写了早期内核。后来他们用一种高级语言重写了它们，这改变了他最初的方向。里奇（Ritchie）是否预料到 C 将成为一种被数百万程序员既喜爱又讨厌的通用编程语言？几乎没有。他的经典著作*C 语言程序设计*（The C Programming Language）的重版对语言规范进行了修改，这证明了他第一次并没有做对。

所以，我们大多数人仍然在学习。即使我们自大到认为知道一切，也会有人改变我们的需求。我们该如何构建软件呢？下一条原则掌握着关键。

当我们说“尽早”时，我们的意思就是越快越好。要快。花一点点时间规划应用程序，然后着手去做。写代码时要得好像你的命取决于它一样。趁热打铁。你连一纳钟的时间都没有浪费！

这个想法与许多人认为的“正统工程方法论”背道而驰。大多数人被告诉，在开始编码阶段之前，应该完全设计好一个应用程序。“你必须编写功能规格书，”他们说，“进行定期评审以确保你处于正轨上。编写一份设计说明书来澄清你对细节的想法。在启动编译器之前，90% 的设计应该完成。”

这些指南在原则上听起来很好，但它们没有对原型给予足够的重视。正是在构建原型的过程中，想法才第一次以视觉化、现实化的方式测试其价值。在此之前，你拥有的仅仅是关于某哪里出了问题的想法集合。在那个阶段，概念几乎没有被理解，而且每个人不太可能以相同的方式感知它。在项目进行之前，我们需要达成感知上的共识。原型通过提供目标的具体表述来走向共识。

### 3.2.1 原型制作是一个学习过程

越早开始，你离发布的产品就越近。原型向你展示什么是有效的，最重要的是，什么是无效的。你需要对你所选路径的肯定或否定。及早发现一个错误的假设并仅遭受一次微小的挫折，远比在开发会议上花费几个月时间，却不知道一个“致命缺陷”（Mother of All Flaws）正要在截止前三周伏击你要好得多。

### 3.2.2 早期原型制作可以降低风险

假设你有一些具体的东西可以指着说：“它看起来会是这样。”如果你能把它展示给信任的用户并获取他们的反应，你可能会发现你的设计是准确的。通常情况下，你的原型会满是百漏洞。不过没关系。你获得了宝贵的设计信息。听一小群批评者的意见，比听着数百万用户尖叫着召回你的产品要好。

对于每一个正确的设计，都有成百个错误的设计。通过及早剔除几个坏方案，你开始了一个淘汰法的过程，这个过程不可避免地带你更接近高质量的完成品。你发现了无法计算的算法、总是对不上拍的时机，以及无法交互的用户界面。这些试验有助于筛选掉谷壳，为你留下坚实的谷物。

大多数人同意原型制作有许多优点。教授传统软件工程方法论的学者也承认它的价值。然而，原型制作是一种手段，而不是目的本身。所有原型制作的目标应该是构建我们所谓的“第三系统”（The Third System）。不过，在我们讨论第三系统之前，我们需要先谈谈它之前的两个系统。

## 3.3 人类的三个系统

人类只有构建三个系统的能力。无论他如何如何努力，无论挣扎了多少小时、几个月或几年，他最终都会意识到自己无法构建更多。他根本无法构建第四个系统。认为其他是自欺欺人。

为什么只有三个？这是一个棘手的问题。人们可以从科学、哲学和宗教观点出发对几种理论进行推测。

## 3.4 人类的第一个系统

每种理论都能为这种现象的原因提供一个合理的解释。但最简单的解释是，人像他自己一样，经历着阶段：青少年、成熟期和老年。

在青少年阶段，人类充满活力。随着进入成熟期，他的影响力随之增长。当他进入老年时，他的潜力就会消退。这对所有系统都是如此。

### 3.4.1 人类背水一战构建原型

通常，开发者面临着满足截止日的压力。这点燃了他体内的创造力火花。最终，当他花费数小时在脑海中反复思考这个想法时，火花变成了一小火焰。

### 3.4.2 他没有时间做对

如果他有时间做对，他就不会面临任何截止日压力了。所以他必须即兴发挥。但由于典型的即兴发挥往往是妥协，批评者们会反对他。“他不能这样混过去！”他们坚持道，“他不知道自己在做什么。”他的回应是？”是的，这很丑，但它管用！”

### 3.4.3 人类独自构建第一个系统，或者最多和一小小组一起

这部分是因为主流中的许多人对他所做的事情并不太理解。他们没有从自己的视角看到他所看到的，所以他们不知道他为什么兴奋。因此，他们得出结论：他的工作很有趣，但还还不足以让他们参与。

许多人之所以在第一个系统的第二个原因更具务实：构建第一个系统涉及巨大的风险。没有人知道第一个系统是否会具有开发第二个系统的特征。失败的概率总是超过 80%。在行业术语中，与一个失败的第一个系统相关联可能是“职业受限的”（career limiting）。

### 3.4.4 第一个系统是一个“精悍、冷酷的计算机器”

它以最小的成本实现了性能。它的开发者在大多数领域都不得不采取权宜之计的方法，迫使他们“硬编码”大量的应用代码，用功能和灵活性换取简单和快速。完善的功能被留到了下一个版本。任何与系统目标不正交的内容都被排除在外。软件完成了任务——仅此而已了。

当人们将第一个系统与他们熟悉的更成熟的系统比较时，通常会对它的性能感到惊叹。他们纳闷为什么自己的系统无法与这个磁盘块上的“新秀”竞争。他们感叹这个小之卒在流行的基准测试中表现优于他们喜爱的系统。这看起来不公平，事实也如此。将第一个系统与处于第 n 次发布版本的系统进行比较，无异于苹果比橘子。设计者心中有不同的目标。

第一个系统的设计者高度专注于试图解决眼下的问题，让某些事情运转起来，让任何事情运转起来。随后的设计师通常花费大量时间尝试添加新功能，以满足感知的市场目标。当这些功能被整体考虑时，它们往往会对性能产生负面影响。

## 3.4 人类的第一个系统

一种相关的风险是，不了解情况的经理可能会将“第一个系统”宣布为某个产品，并过早地将其交给营销部门。这通常导致销售人员过度炒作一个尚未准备就绪的系统，而这种做法是有迹可循的。系统频繁崩溃，往往发生在最尴尬的时刻。用户对该系统产生了强烈的偏见，因为他们认为它的质量很低。最终，系统的销量会受到影响。

当一小群构建“第一个系统”时，他们充满了极大的动力。进展非常迅速。一种协同效应渗透了团队，产生了一个强大、凝聚力强的整体，他们拥有共同的愿景，并强烈渴望实现该系统。他们理解目标，并狂热地为实现目标而努力。与这样一个小组工作既让人心潮兴奋又让人精疲力竭，更不用说如果成功成功回报将是丰厚的。

有一点是肯定的：第一个系统几乎不是由大群体构建的。一旦团队规模大到成员之间无法进行日常互动，生产力就会下降。性格发生冲突。人们怀着隐藏的意图。随着人们开始追求私利，一个个小割据地之然而生。这些发生稀释了目标，使其变得难以实现。

### 3.4.5 第一个系统展示了一个点燃他人想象力的概念

是的，后来的系统确实可以做得更多，但新功能是有代价的。

第一个系统导致人们陷入各种“如果……会怎样？”的狂野幻想中。它激发了人们对更多的渴求：更多的功能、更多能力、更多一切。人们会说诸如“想一下这些可能性”以及“想象一下我们在 Gamma BioTech 用这个能做些什么！”

以下列表列出了一些创新正点燃人们想象力的概念领域和技术，这些领域催生了许多第一个系统：

- 人工智能
- 技术
- 数字成像
- 数字音乐
- 电子货币系统和无现金社会
- 基因工程与克隆
- 互联网和万维网
- 交互式电视
- 火星着陆
- 微型机器
- 纳米技术
- 质量（六西格玛管理、全面质量管理等）
- 虚拟现实
- 无线技术

点燃他人想象力的概念成为第二个系统紧随第一个系统之后的主要原因。如果第一个系统没有任何进展，每个人都会认为它已经满足了一个人的需求，而且（哈欠！）自己有更好的事情要做。许多第一个系统在婴儿时期就夭折了，因为它未能激励观察者用它创造出伟大神奇的事。

一个新第一个系统的流行互联网仓库是 SourceForge (`http://www.sourceforge.net`)。当人们对某个新概念或技术感到兴奋时，那里展示的一些软件会引发大量活动。但遗憾的是，那里贡献的并非所有内容都符合成功第一个系统的标准。其中一些内容根本无法激励任何。。因此，SourceForge 已经变成某种第一个系统的“坟墓”。
