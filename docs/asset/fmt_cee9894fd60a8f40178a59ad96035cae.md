
从救援磁盘启动，然后使用它来挂载并修复选作根设备的分区的 `/etc/fstab` 文件，或者 `/dev` 目录及其节点。大多数 Linux 发行版 `/dev` 目录下的 `MAKDEV` 脚本可以创建所需的节点。`mknod` 命令可以选择性地执行这些操作。

注意，新版本的 Linux 内核支持通过分发器（称为 `ptm`，它使用 `/dev/pts` 文件系统）动态管理 tty 节点。用户空间支持由 `glibc 2.0` 及更高版本提供。链接到旧库的二进制文件在没有可用状态时可能会失败，且如果 pty 系统出现问题（例如内核编译时未开启 UNIX8 支持），新的二进制文件可能会失败。

## 屏幕闪烁且未出现登录提示

如果你配置的工作站使用 `xdm` 或 GNOME 程序在 X WINDOW 中提供图形化登录界面，且系统反复尝试启动 X 但在能够显示任何内容之前崩溃，请检查鼠标。

首先，确保鼠标已插好。然后以单用户模式手动调起系统，并检查 `/dev` 目录下是否存在相应的设备节点。然后尝试运行 `gdm` 命令以确保系统能够“看到”鼠标——或者手动重启以查看错误。检查 X WINDOW 依赖的配置文件（`/etc/X86config` 和 `/etc/x11/X86config` 最常见），以确定它正在寻找的鼠标是否是你找到的那个。

X WINDOW 系统正确启动的另一个常见问题是确保它正确访问了字体目录，或者其服务器正在运行且可访问。

如果以上都没问题，那么你的 `xdm` 配置有问题。

如果你在启动后立即反复遇到此问题，很可能是 `/etc/ld.so.cache` 损坏了，你需要运行 `ldconfig` 命令通过读取 `/etc/ld.so.conf` 中的库路径来重新构建它。库路径也可以通过环境变量 `LD_LIBRARY_PATH` 进行控制。

否则，你可能耗尽了所有内存（物理和虚拟内存）或所有进程表（启动新任务需要这些）。找到一种方法从运行的任务中杀死某些进程以恢复资源，然后考虑如何防止再次发生。如果是失控进程，请找到它的创建者并修正程序。

在最坏的情况下，你可能需要按照“丢失根密码”章节中描述的方法执行在没有访问权限的情况下关闭系统的程序。

可以使用额外的交换文件以及分区，因此可以为系统添加交换空间。

## 程序“转储核心储”（SIG 11）

当程序报告响应 `SIG 11` 导致“转储核心储”（dumped core）时，意味着该程序尝试执行一条指向未分配给它的内存区域的指令。

这通常是编程错误的结果。通常这是由尝试解引用（使用）未初始化的指针，或者由于指针算术错误引起的。（指针是引用内存地址的变量。）

然而，当你在广泛使用且经过良好测试的程序上对已知数据集执行常用操作时遇到这些错误，通常指示着硬件故障。

例如，如果尝试使用当前版本的 `gcc` 重新编译 LINUX 内核失败，并收到类似“内部编译器错误”（internal compiler error）的消息且引用了 `SIG 11`，这可能是由内存不可靠引起的。

不幸的是，检测 RAM 芯片的间歇性故障非常困难。系统非常复杂，简单的顺序“写入、读取、验证”内存测试可能无法触发真实的硬件问题。编译内核，以及压缩、解压缩和归档/解档大型数据集，会以简单软件不会采用的方式访问内存。

关于此主题的更多信息，请访问“SIG 11 页面”：`http://www.bitwise.nl/sig11`

如果在一个系统上失败而在另一个系统上正常，请尝试在其他系统运行，这很可能是硬件问题。

如果是硬件问题，要修复此问题，请尝试在受影响的系统中安装新的或不同的内存。如果看起来源于软件漏洞，请让程序员修复它们（或向软件维护者报告）。（尝试使用 `Electric Fence` 链接程序并运行它。`Electric Fence` 是标准内存分配函数的边界检查版本。）

## root 的 SPATH “损坏”

把这称为“紧急情况”可能看起来很愚蠢，但某些人对于如何修复它完全不知所措。他们应该知道，你可以通过向程序提供完整的文件规范来启动任何程序——并且 `/bin/bin` 会使其恢复正常。此外，一条命令行：

```bash
export PATH=/bin:/usr/sbin:/usr/bin
```

应该足够让系统恢复运行（针对单次会话）。很自然地，需要编辑 `/etc/profile` 和/或 `/etc/csh.csh` 文件。这些是大多数常用 Shell 用于配置初始 `PATH` 设置的文件。通常，即使在缺少这些文件的情况下，`PATH` 设置也是合理的。`init` 程序中编译了默认值，它是所有 UNIX 进程的祖先。

## 附录 紧急情况

创建一个 `/bin` 目录并从那里创建硬链接或符号链接到 root 应该使用的每个文件是可能的也是明智的。这样，root 的 `PATH` 可以仅包含该目录而不其他内容。

虽然这看起来可能是一个愚蠢的练习，但它有助于防止操作员不必要的 root 身份运行程序，甚至可能防止木马程序（某些旧案例中，攻击可以在 `bin` 目录之一添加新文件，而他们无法覆盖该目录下的任何文件）。

## 最大打开文件数

内核有一个内置限制（在正常使用下很少达到），限制同时可以打开的文件数量。遇到此限制可能会导致文件打开失败，即使没有其他用户在竞争该文件。

将新值 `echo` 写入 `/proc/sys/kernel/file-max` 和 `/proc/sys/kernel/inode-max`

例如：

```
inode-max = 32768
file-max = 5120
```

```
NR_TASKS = 1024 (linux/tasks.h)
MAX_TASKS_PER_USER = 128 (linux/tasks.h)
```

同时确保 `/dev` 设备下存在 256 个 pty 节点：许多发行版仅创建 64 个（使用 `/dev/MAKDEV` 脚本）。

与最大任务数（系统范围）和每个用户最大任务数相关的设置可以在内核源码的编译时进行修改。在 `/usr/src/linux/include/linux/tasks.h` 查看这些设置。

## 文件系统问题

本节详细说明了文件系统可能提出的各种困难。

## “无法找到交换空间签名”错误

使用 `fdisk` 双重检查分区表中的条目的的分区类型。在确认分区设置正确后，使用 `mkswap` 命令。

在尝试与其他操作系统共享交换空间时，可能会导致此错误。请参阅 `LINUX+FreeBSD HOWTO` 获取正确的交换共享示例。

## 文件系统空间不足

如果用户耗尽了文件系统的可用空间，你会发现由于 UNIX 系统的预留空间功能，root 有一点“喘息空间”。

可以使用 `tune2fs` 命令设置允许使用此预留空间的用户 ID 和组 ID。

显而易见的答案是删除一些文件。另一个是将一些文件移动（迁移）到另一个卷（留下一个符号链接）。使用 `gzip` 或另一个压缩工具压缩某些文件也是另一个选择。

如果 root（以 root 权限运行的进程）溢出磁盘卷，磁盘的预留空间将被填充。因此，root 邮件应始终发送到非特权账户，并应仔细维护日志轮转。

为了主动防止文件系统达到容量，请安装某些监控系统，如 `SLEW`（可以在第 4 章“容量规划”中找到）。

## 文件系统 inode 耗尽

即使剩余大量磁盘空间，也可能耗尽 inode。这发生在创建许多小文件时。每个文件都需要一个 inode。
