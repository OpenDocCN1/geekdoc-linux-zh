在没有远见规划的情况下解决问题是痛苦的。你会浪费时间，并不断感到于问题原因反复从指间溜走。通过遵循正确的程序，你可以将一次沮丧的性能查找转化为一个有趣的侦探故事。每一条信息都让你更接近真魁祸首。人并不总是值得信赖，证据将是你唯一的朋友。当你调查问题时，它会经历不同常的转折，你在查找初期发现的信息可能就是你最终解决问题的关键。最棒的部分是，当你最终抓住“坏人”并解决问题时，你会感到一种肾上腺素飙升的快感和成就感。

如果你从未调查过性能问题，起步可能会无所适从。通过遵循一些显而易见和不易的技巧，你可以节省时间。本章的目标是为你提供帮助查找性能问题的系列技巧和指南。这些都是从浪费时间换来的深刻教训。这些技巧将帮助你快速解决性能问题。

阅读本章后，你应该：

- 避免重复他人的工作
- 避免重复自己的工作
- 避免因收集信息产生误导
- 创建一份关于你调查的有用参考文档

尽管没有任何性能调查是完美的（你几乎总是说“如果我早点想到就好了”），但这些技巧可以帮你避免性能调查中的常见错误。

## 1.1 通用技巧

### 1.1.1. 详尽记录（保存一切）

在调查性能问题时，你可能做的最重要的事情就是记录你看到的一切。一组组织良好的笔记允许你比较配置如何影响性能。虽然可以重新测试，但测试配置通常是非常耗时的。

- 记录硬件/软件——这涉及记录硬件（内存大小、CPU 类型、网络、磁盘）以及软件环境（操作系统和版本）。这些信息早期看起来可能无关，但在追踪问题时，你可能会更改配置。保存 `cat /proc/pci`、`dmesg` 和 `uname -a` 的输出。
- 保存并组织性能结果——这允许你在运行很久之后回顾结果。保持笔记有序并避免重复更为高效。
- 记录命令——当你运行性能工具时，你经常会创建测量你感兴趣区域的复杂命令。如果你想重新运行测试，或在不同的应用程序上运行，重现这些命令可能会非常麻烦且难以完成。最好记录下使用的具体内容。这样你可以在未来的测试中重现准确的命令行，回顾过去的结果时也能看到具体测量了什么。Linux 命令 `script`（在第 8 章“实用工具：性能工具助手”中详细描述）或从终端“剪切和粘贴”都是实现此操作的好方法。

## 1.2. 性能调查概述

本节概述了在开始性能调查时需要的一系列基本步骤。由于最终目标是修复问题，最好的主意是在接触性能工具之前先对问题进行研究。遵循特定的方案是解决问题且不浪费宝贵时间的有效方法。

### 1.2.1. 确定指标、基准和目标

性能调查的第一步是确定当前的性能，并弄清楚需要改进多少。如果你的系统性能低于预期，你可能会认为值得花时间进行调查。如果系统性能接近其峰值，那么可能就不需要调查了。确定性能值允许你设定合理的性能预期，并为你提供一个性能目标，以便你知道何时停止优化。你总是可以对系统进行微调，但如果没有性能目标，你可能会浪费大量时间去挤榨那额外的百分之几性能，尽管你可能并不需要它。

#### 1.2.1.1 建立指标

为了确定你已完成，你必须为系统性能创建一个或使用一个已建立的指标。例如，如果你正在优化 Web 服务器，你会选择“每秒处理的 Web 请求数”。如果你没有一个衡量性能的目标，在调优系统时，几乎无法判断你是否取得了任何进展。

#### 1.2.1.2 建立基准

在你确定正在衡量特定系统或应用程序的性能后，确定当前的性能水平至关重要。在任何调优或优化之前运行应用程序并记录其性能；这被称为基准值，它是调查的起点。

#### 1.2.1.3 建立目标

在为性能选择指标和基准后，选择一个目标也是至关重要的。这个目标将引导你走向性能搜索的终点。你可以无限地微调系统，并且总是可以通过投入更多精力让它变得好一点。如果你选定了目标，就会知道何时结束。选择一个合理的目标，以下是起点：

- **通过相似配置查找结果**——这是一种理想情况。如果你能找到性能更好的相似系统，不仅可以为你的系统选择目标，还可以通过比较配置差异来辅助工作。将另一个系统作为参考在调查问题时非常有用。
- **查找行业基准结果**——许多网站都比较各个系统的基准测试。某些基准只能通过努力实现。然而，许多基准系统都有特定的配置结果，这些配置可以帮助你调优系统。
- **使用不同的操作系统或应用程序**——这可能是在你的系统上运行不同的应用程序。例如，如果你有两个 Web 服务器，其中一个运行较慢，尝试运行另一个看看性能是否更好。如果系统在任何一种情况下性能更好，你就知道原始配置有改进空间。

## 1.3. 章节总结

性能调查应该是一个令人满意且兴奋的过程。如果你有一个良好的方法来研究和分析，性能调查将多次得到回报。首先，确定其他人员是否存在类似的问题；如果是，尝试他们的解决方案。为你的调查创建一个合理的指标和目标；指标让你知道何时完成。自动化性能测试。确保保存测试结果并记录任何与问题相关的信息。最后，定期查看记录以发现可能遗漏的信息。如果你遵循这些指南，你将有一个清晰的目标和清晰的调查程序。

本章为性能调查提供了背景，后续章节涵盖了 Linux 性能工具。学习如何使用这些工具、它们可以提供什么类型的信息，以及如何结合使用它们查找特定系统上的性能问题。

本章概述了系统性能工具。这些工具是跟踪性能问题的第一道防线。它们可以向你展示系统的整体性能以及哪些区域出现了异常。本章讨论了这些工具可以测量的统计数据以及如何使用单个工具收集这些数据。阅读本章后，你应该：

## 2.1 CPU 性能统计

每个系统性能工具都提供了提取统计数据的不同方法。尽管没有工具显示所有统计数据，但某些工具会显示相同的统计数据。与其每个工具都多次描述统计数据的含义，我们在工具显示之前只进行一次审查。

### 2.1.1. 运行队列统计

在 Linux 中，进程可以是就绪的（runnable）或阻塞等待事件完成的。阻塞进程可能在等待 I/O 设备的数据或系统调的结果。如果一个进程是就绪的，意味着它正在与其他就绪进程竞争 CPU。就绪进程并不一定正在使用 CPU，但当 Linux 调度器决定运行哪个进程时，它会从就绪进程列表中选择。当这些进程处于就绪但等待使用处理器时，它们形成了一个所谓的运行队列（run queue）。队列越长，等待的进程就越多。

性能工具通常显示就绪进程的数量和等待 I/O 的阻塞进程的数量。另一个常见的系统统计数据是平均负载（load average）。系统的负载是就绪和阻塞进程的总数。例如，如果有两个进程正在运行，三个可运行，那么系统的负载就是五。平均负载是给定时间内的负载量。通常，平均负载包括 1 分钟、5 分钟和 15 分钟。这允许你看到负载随时间的变化。

### 2.1.2. 上下文切换
