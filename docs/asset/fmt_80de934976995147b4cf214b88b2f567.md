
汤普森与托瓦尔兹之间的相似之处非常奇，至少是如此。有人可能会认为汤普森编写 `Space Travel` 程序仅仅是为了好玩。而托瓦尔兹对 `Minix`（另一种类 Unix 操作系统）的痴迷让他觉得让一个流行的 Unix 命令解释器 `bash` 运行在他的“玩具”操作系统上非常有意思。再次，起初出于“好玩”的，最终改变了软件行业的根本方面。

Linux 起初并不是一个可移植的操作系统。托瓦尔兹并没有打算将它移植到 Intel `386` 架构之外。在某种意义上，他处于背水一战的地地，因为他拥有的计算机硬件非常少。他充分利用了现有资源，最初并没有打算进一步。然而，他发现设计原则和可靠的开发模型最终引导他为了纯粹而让 Linux 变得更有移植性。其他人接过了这一点，并指向了任何其他架构。

当托瓦尔兹的 Linux 出现时，借用他人编写的软件的想法已经相当普遍。事实上，理查德·斯塔曼（Richard M. Stallman）在他具有里程碑意义的 GNU 公共许可证（`GPL`）中将其正式化。`GPL` 是一项适用于软件的法律协议，它几乎可以保证任何想要源代码的人都能免费获取。托瓦尔兹最终为 Linux 采用了 `GPL` 方案，这样做使得任何人都由于由于托瓦尔兹是免费赠送 Linux，其他人免费贡献自己的软件到 Linux 开发工作中也是顺理成章的。

从早期开始，Linux 已经表现出它确实是一个类 Unix 操作系统。它的开发者全心全意接受 Unix 哲学的宗旨，然后从头开始编写一个新的操作系统。问题在于，Linux 世界中几乎不再有东西是从头开始写的。几乎所有内容都是构建在他人编写的代码和概念之上的。

## I.4 Unix 哲学的核心要义

Unix 哲学的原则是具有欺骗性的简单事实上它们如此简单，以至于人们倾向于认为它们并不重要。这正是欺骗之处。它们的简单性掩盖了这些想法在执行时极其有效。

以下列表将让你了解什么是 Unix 哲学原则。书的其余部分将帮助你为什么它们很重要。

- 小即美。小物品相比其大型对应品具有巨大的优势。其中包括以独特且有用的方式与其他物品结合，这些方式是原始设计者无法预到的。
- 让每个程序只做好一件。通过专注于单一任务，程序可以消除许多导致过度复杂和缺乏灵活性的额外代码。
- 尽早构建原型。大多数人都会同意原型是任何项目的宝贵元素。但在其他方法中，原型只是设计阶段的一部分，而在 Unix 中，它是生成有效的设计工具。
- 可移植性优于效率。当 Unix 作为第一个具有重要意义的可移植操作系统取得突破时，这是一个大新闻。今天，可移植性被认为是现代软件设计中必须的，这是一个被广泛接受的原则示例。
- 将数据存储在平文件中。可移植性和效率之间的选择涉及到可移植代码的价值。可移植的数据与可移植代码同样重要，甚至更为重要。可移植性是公式中经常被忽视的部分。
- 利用软件杠杆的优势。许多程序员对可复用代码模块的重要性只有肤浅的理解。代码复用有助于利用软件杠杆，这是一个 Unix 开发者在相对短时间内创建许多应用的强大概念。
- 使用 Shell 脚本增加杠杆和移植性。Shell 脚本是增强软件杠杆和可移植性的双刃剑。只要可能，编写脚本而不是完整的 C 程序是更好的选择。
- 避免捕获式用户界面。某些命令具有 Unix 开发者称为“捕获式”的用户界面。这些界面防止用户在命令运行时运行其他命令，实际上使用户在命令持续期间被系统俘获。在图形用户界面世界中，这种界面被称为“模态”。

## 1.4 简述 Unix 哲学

前面的列表包含了关于 Unix 开发者应该是信教徒主义的准则。你会在其他关于 Unix 的书中发现类似的列表，因为这些要点被每个人认为是 Unix 的基础性概念。如果你采纳了这些观点，你将被视为一个“Unix 专家”。

以下列出了 10 个次要准则，这些思想本应该是 Unix 世界信仰体系的一部分。并不是所有参与 Unix 的人对这些都深信不疑，而且其中某些也并非 Unix 的典型特征。尽管如此，它们似乎是 Unix 文化的一部分（由于包含，也包括 Linux 文化）。

- 允许用户定制环境。Unix 用户喜欢控制自己环境的能力——控制一切。许多 Unix 应用程序都坚决不对交互样式做出决策，而是将选择留给用户。这里的思想是实现执行某事的机制，而不是如何执行某事的策略。让用户发现他们通往计算彼岸的道路。
- 使操作系统内核保持短小和轻量化。尽管对新功能的追求永无止，但 Unix 开发者倾向于保持操作系统最核心部分的精简。他们并不总是能成功，但这是他们的目标。
- 使用小写字母并保持简洁。在 Unix 环境中使用小写字母是一项传统，在之所以做的原因消失很久后这种传统依然持续了很久。现在的许多 Unix 用户根据自己的意愿使用小写命令和晦涩的名字，因为他们不再被迫这样做了。
- 节省树木。Unix 用户通常对软件包列表嗤以鼻。将所有文本保留在网上并使用强大的工具对其进行处理有充分的理由。
- 沉默是金。在产生详细错误信息方面，Unix 命令是臭名昭著的“沉默”。尽管更有经验的 Unix 用户认为这是一个理想的特质，但许多其他操作系统会持不同意见。
- 并行思考。大多数任务都可以被拆分为一系列更小的子任务。这些子任务随后可以并行运行，从而在与一个大型任务相同的时间内完成更多工作。在今天，围绕对称多处理器 `SMP` 设计的活动非常多。考虑到“教条主义”、“准则”和“信仰体系”等词汇，人们可能会想，Unix 哲学在描述技术现象之外，是否还描述了一种文化现象，即计算机行业迈向并行化趋势的一个例子。
- 7. 部分之和大于整体。这一准则源于这样一个想法：由一组较小的程序构建的大应用程序比单个大程序更灵活，因此更有用。两种解决方案可能具有相同的功能能力，但“小程序集合”的方法是两者中更具前瞻性的。
- 8. 寻找 90% 的解决方案。做任何事情的 100% 都是困难的。做 90% 要高效得多且成本效益更高。Unix 开发者经常寻找满足 90% 目标用户的群解决方案，让剩下的 10% 自求是。
- 9. 差比全强。拥护者认为，“最小公约数”系统是最有可能生存的系统。廉价但有效的东西比高质且昂贵的东西更容易泛化。PC 兼容世界从 Unix 世界借用了这一想法并正在付诸实践。这里的关键词是“包含性”。如果某个东西足够易于获取而可以包含几乎所有人，它就比表现出“排他性”的东西要好。
- 10. 分层思考。Unix 用户和开发者倾向于按层级组织事物。例如，在首次应用于文件系统的树形结构架构中，Unix 的目录结构。Unix 已将分层思考扩展到其他领域，例如网络服务命名、窗口管理和面向对象的开发。

## 2.1 准则一：小即美

如果你要写一个程序，从小开始并保持其小。当你编写一个简单的过滤器、图形包或庞大的数据库时，努力将其减小到可能的软件片段。抵制将其变成单体结构的诱惑。

传统的程序员往往怀着编写宏大程序的秘密欲望。当他们启动一个项目时，似乎想花费几周、几个月甚至几年时间用一个程序解决所有问题。

这仍然给我们留下了一个问题：有效的源文件和目标文件名是从哪里而来的？答案很简单：来自其他小型程序。这些程序承担着获取文件名、检查文件是否存在以及判断文件是否包含大于零字节的数据的功能。
