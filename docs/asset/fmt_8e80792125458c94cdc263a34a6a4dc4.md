取决于你运行的 GDB 版本，此输出可能会略有不同。此时，程序已加载，但尚未运行。调试器正在等待你的命令。要运行你的程序，只需输入 `run`。此命令不会返回，因为程序正在无限循环中运行。要停止程序，按下 `control-c`。屏幕会显示如下内容：

```
Starting program: /home/johnnyb/maximum

Program received SIGINT, Interrupt.

start_loop () at maximum.s:34

mov data_items(%edi,4), %eax

(gdb)
```

这告诉你程序被 SIGINT 信号（来自你的控制-c）中断，并且当时处于标记为 `start_loop` 的区域，并在停止时执行到第 34 行。它给了你即将执行的代码。

取决于你按下控制-c 的准确时间，它可能停止在与示例不同的行或不同的指令上。

寻找程序中 bug 的最佳方法之一是跟踪程序的流，查看它在哪里发生了错误的跳转。要跟踪此程序的流：

```
(gdb) step

35 cmpl %ebx, %eax

(gdb) step

36 jle start_loop

(gdb) step

32 cmpl $0, %eax

(gdb) step

33 je loop_exit

34 mov data_items(%edi,4), %eax

(gdb) step

35 cmpl %ebx, %eax

(gdb) step

36 jle start_loop
```

你可以看出，它在循环。通常情况下这是好的，因为我们希望它循环。然而，问题在于它从不停止。因此，为了找出问题，让我们查看退出循环的地方：

```
cmpl $0, %eax

je loop_exit
```

基本上，它在检查 `eax` 是否为零。如果是，它应该退出循环。这里有几点需要检查。首先，你可能完全漏掉了这一行。其次，你应该确保 `loop_exit` 确实在循环之外。如果我们把标签放在错误的位置，就会发生奇怪的事情。然而，再次，这些潜在问题都不是罪魁祸首。

所以，下一步可能是 `%eax` 的值不对。在 GDB 中检查寄存器内容有两种方法。第一种是命令 `寄存`。它会以十六进制显示所有寄存器的内容。然而，我们现在只关心 `%eax`。只想显示 `%eax`，可以使用 `print/$eax` 以十六进制打印，或者使用 `print/d $eax` 以十进制打印。

```
(gdb) print/d $eax

$1 = 3

(gdb)
```

这意味着你第一次查询的结果是 3。你进行的每次查询都会分配一个带有美元符号的前缀数字。现在，如果你回看代码，你会发现 3 是搜索列表中的第一个数字。如果你再单步几次，你会发现每次迭代中 `%eax` 的值都是 3。这并不是应该发生的情况。`eax` 每次迭代应该是列表中的下一个值。
