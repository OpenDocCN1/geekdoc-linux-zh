一个 folio（页对单元）可能处于这种状态，等待异步 I/O 操作可能持续很长时间，这就是为什么实现 `folio_unlock_mmmap_for_io` 机制的方法存在缺陷——该机制在等待此操作完成时会释放高度竞争的 `mm_struct->mmmap_lock`。

这同时也意味着等待锁的行为比典型的互斥锁要复杂得多——例如，通过 `folio_lock()` 获取锁，意味着该线程在释放锁之前应该等待任何 I/O 完成。

这同样意味着开始异步 I/O 以读取数据的代码会隐式地等待 I/O，例如，在执行同步预读（*synchronous reahead*，后见第 ?? 节）触发缺页中断时会调用 `folio_lock_drop_mmap()`，该函数会锁定 folio（如果缺页状态允许），从而隐式地等待 I/O 完成。

这进一步解释了为什么某些内核代码在接入锁之前会倾向于使用乐观的 `folio_trylock()`，因为这意味着完全没有等待 I/O。正如列表 9-137 所示，每个 `folio_trylock()` 都会首先尝试这样做。我们在列表 9-138 中检查 `folio_trylock()`。

```c
/**
 * folio_trylock() - 尝试锁定 folio。
 * @folio: 尝试锁定的 folio。
 *
 * 有时等待 folio 被解锁是不理想的（例如
 * 当锁的获取顺序错误时，或者通过批量 folio
 * 进展比按顺序处理它们更重要时）。通常情况下
 * 调用 `folio_lock()` 是正确的函数。
 *
 * Context (上下文): 任何上下文。
 * Return (返回值): 锁是否成功获取。

static inline folio_trylock(struct folio *folio)
{
    return likely(!!test_and_set_bit_lock(PG_locked, folio_flags(folio, 0)));
```

由于 folio 锁意味着线程可以睡眠并等待 I/O，因此我们实现了一种信号机制，以指示致命信号可以中断此过程（默认情况下是不可中断的），该功能通过 `folio_lock_killable()` 实现，我们在列表 9-139 中检查了它。

```c
/**
 * folio_lock_killable() - 锁定此 folio，可被致命信号中断。
 * @folio: 要锁定的 folio。
 *
 * 尝试锁定 folio，类似于 `folio_lock()`，不同之处在于
 * 等待锁的睡眠可以被致命信号中断。
 *
 * Context: 可能会睡眠；参见 `folio_lock()`。
 * Return: 如果获取锁则返回 0；如果收到致命信号则返回 -EINTR。
 */
static inline folio_lock_killable(struct folio *folio)
{
    might_sleep();
    if (!folio->trylock(folio))
        return _folio_lock_killable(folio);
    return 0;
}
```
