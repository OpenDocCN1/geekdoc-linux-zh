
本章中描述的每种许可都向被许可者提供源代码。你可能记得第一章提到源代码是实现目的的手段；它本身并不是目的。（开源原则 #1.）真正的目标是软件自由，这体现在为了任何目的使用的权利、在不支付版税的情况下复制的权利以及自由创建和分发派生作品的权利。（开源原则 #1、2 和 #3.）

本章描述的所有许可存在的问题在于，它们未能充分促进软件自由。它们的条款比典型的专有软件许可要合理得多，但它们所许可的软件并非真正的自由。

这并不意味着你不应该接受这些许可下的软件。其中一些是很好的许可，只是还没有到开源的程度。

### 共享源代码 (Shared Source)

为了响应客户访问源代码的需求，微软创建了其共享源代码许可计划。该计划允许微软客户阅读和检查公司的源代码。

微软共享源代码许可对于全球最大的专有软件供应商来说是一个巨大的飞跃，这家公司传统上出于竞争考虑对其源代码保持保密。终于，微软的客户可以检查该公司的部分源代码并从中学习。当然，从开源许可的角度来看，共享源代码的概念是一个弱势的替代方案，远没有达到提供软件自由的程度。

微软共享源代码许可具有有限的用途：

- 你可以根据本许可的限制，将本软件用于任何非商业目的。（微软共享源代码 CLI、C# 和 JSCRIPT 许可.）

该许可中对“非商业目的”的限制本身就使其与开源原则 #1 不兼容。但该许可更进一步，使其也与开源原则 #2 和 #3 不兼容。开源软件必须供任何人用于任何目的、创建派生作品以及销售软件。而微软的软件并不可用：

- 你不能以任何形式出于商业目的使用或分发本软件或任何派生作品。商业目的的示例包括运行业务、许可、租赁或出售本软件，或为了供商业产品使用而分发本软件。（微软共享源代码 CLI、C# 和 JSCRIPT 许可.）

从更根本的来说，当你看到微软的源代码时，该许可规定了你可以做的事以及你禁止做的事：

- 你可以使用你在访问软件后记住的任何无形形式的信息。然而，这一权利并没有授予你对你可能使用此类信息所创建的任何微软版权或专利的许可。（微软共享源代码 CLI、C# 和 JSCRIPT 许可.）

一个非常有趣的问题是：一个拥有过目记忆的工程师是否可以在不侵犯微软版权的情况下，根据其记住的无形信息重新创建微软软件。但对于大多数工程师来说，这并不是法律上有趣的问题。相反，该许可的效果是，工程师/被许可者可以使用微软源代码中的某些信息来完成他们在版权或专利保护下无法获得的实际性工作。源代码可以帮助被许可者为微软产品设计接口，并创建读取和写入微软数据格式的程序。它可以用于验证微软产品的安全性或可靠性。对于微软的一些客户来说，这种出于有限目的的源代码可用性已经满足了他们的需求；他们并不真正需要开源许可所提供的软件自由。

所以，如果你仅仅使用你记住的无形信息，并且你基于这些无形信息开发软件，你是被允许的。然而，微软的源代码不能用于编写侵犯微软版权或专利的软件。

如果你是一个打算编写可能与微软版权或专利产生竞争的软件开发人员，那么查看微软的源代码具有巨大的风险。根据美国的版权法，如果微软证明你的软件与他们的软件之间存在“实质性相似”，你可能就是侵权者。你可能需要证明你看到并读过代码，但在编写软件时仅依赖于无形信息。

这是一个困难的举证责任。我不确定经验丰富的程序员如何在那条微妙的界线上行走。也许最好的方法仅仅是根本不要看微软的源代码。至少，如果你正在指导与竞争微软共享软件的产品相关的公司项目，请建立一道坚固的墙，将查看微软源代码的人与那些可能（即使是无意）创建派生作品的程序员隔离开。

这种风险并非共享源代码软件所有。员工可能会受到他们在之前的雇主工作期间看到或编写的专有源代码的污染。即使开源软件也包含可能污染程序员记忆的无形信息。

解决方案显然不是完全避免源代码，而在你公司内部，创建专有软件的人周围建立起坚固的墙。确保那些工程师不会无意中创建他们读过的任何源代码的派生作品，因为你必须遵守那些许可的条件和限制。

对于那些创建开源软件的人，不要创建微软共享源代码软件的派生作品。微软共享源代码许可与开源许可不同——它没有给你软件自由。

## 开源许可

这类许可通常倾向于大公司而非贡献者。虽然此类许可并不总是像微软共享源代码许可那样禁止商业用途，但公共源码许可通常要求在使用商业用途时支付特权费。

这种形式的许可被称为公共源码（public source），表示源代码已发布，但该软件并非在开源许可下分发。

公共源码许可有很多种类，取决于所分发软件的特征以及许可者的商业模式。例如，Ping Identity 公司（见 www.pingid.com）根据以下条款分发其部分软件：

- a. 无需为无限的个人使用或非商业分发（如需文所述术语定义）支付特权费；
- b. 对于个人使用和非商业分发以外的其他用途，只要被许可软件运行在少于100个处理器上（如如下文所述术语定义），无需支付特权费；以及
- c. 对于100个或更多处理器上的个人使用和非商业分发以外的用途，须支付一次性预付特权费。在额外处理器上运行软件的许可受限于从 http://www.pingidentity.com 获取的特权费及支付条款，并自从许可方获得额外许可之日起生效。在额外处理器上运行软件的特权费应在首次使用这些处理器之前支付给许可方。（SourceID 公共源码许可第1节。）

与未对“商业分发”术语进行定义的 CPL 许可不同，SourceID 公共源码许可精确定义了其术语：

在本许可中，“个人使用”一语是指个人仅为了其个人、私人且非商业目的对软件的功能性使用。个人以其公司、企业或组织（商业或非商业）官员、员工、成员、独立承包商或代理人的身份使用软件，均不被视为个人使用。（SourceID 公共许可许可第3节。）

在本许可中，“非商业分发”一语是指将软件分发给任何第三方，且与此类分发有关未支付任何费用，无论是直接支付（包括但不限于支付软件副本的费用）还是间接支付（包括但不限于支付与软件相关的服务费用，或支付包含“免费”软件副本的商品或服务的费用）（SourceID 公共许可许可第3节。）

根据开源原则第1条，开源许可中不允许此类用户之间存在区别。也不得存在此类要求开源软件计算处理器或类似软件使用指标的条件。像这样的公共源码许可并不保证软件自由——它们不是开源的。

## 双重许可与多重许可

版权所有者可以对其作品进行任何次数的许可。专有软件的分发者在向受青客户提供折扣、向大公司发行无限副本的通用许可，以及对商店出售的副本应用缩壳许可（shrink-wrap licenses）时这样做。

第7章描述的 MPL 提供了双重许可的一个示例。在 MPL 下，初始开发者可以将部分涵盖代码（Covered Code）指定为“多重许可”（Multiple-Licensed）。这允许任何被许可者选择在 MPL 或“附件A”中指定的第二种许可下接受这些部分。在使用该选项时，初始开发者通常选择 GPL。

现在，比这种双重和多重许可更复杂的示例已广泛应用于重要软件。开源软件的所有者可以同时在非开源许可下对相同软件进行许可。对于不愿接受现有开源许可中某些条件、并愿意支付额外许可费以免除这些条件的被许可者来说，这特别具有吸引力。

此类最初许可的软件是开源的。它可以在开源许可下获得。但它也可以通过其他许可获得。

考虑 MySQL 数据库，它在 GPL 和一个单独的商业许可下分发。MySQL 软件通常集成在更大的软件包中。取决于对 GPL 的解释，此类较大的软件包可能受到 GPL 互惠条件的限制。对于某些希望保持其衍生作品为专有的 MySQL 潜在客户来说，这是不可接受的。

MySQL 的分发者也是该软件版权的所有者。因此，它可以根据意愿同时以许多不同的许可对 MySQL 进行许可。除了 GPL 外，MySQL 还提供了不带互惠义务的商业许可——需要付费。

MySQL 首席执行官 Märten Mickos 这样描述其公司的双重许可商业模式：

- 我们的付费客户获得了他们付钱买到的：一个具有商业支持的产品，具有供应商提供的某种保证，且没有任何典型的开源要求（链接软件必须开源为……通过双重许可法律在建立长期业务的同时，兼顾了开源/自由软件社区的需求。见 www.mysql.com。

Mickos 解释了这种双重许可交易的对等性。他指出，他们的商业客户从开源客户中受益，因为开源软件本质上更可靠、更有效。（他称之为“严苛的战斗测试”）。同时，他们的开源客户也从商业客户中受益，因为 MySQL 公司“负担得起快速开发和改进产品的费用”。

该模型的一个问题是，第三方对 MySQL GPL 版本的贡献必须根据 GPL 进行许可。（见 GPL 第2[b] 节。）版权所有者可以将其对 MySQL 的贡献在商业许可下进行双重许可，但 GPL 中没有任何条款规定要求他们必须这样做。MySQL 可以通过要求贡献者将其版权转让给公司，或通过在许可下明确接受贡献（该许可允许 MySQL 按其意愿使用贡献）来尝试避免此问题。

此类双重许可替代方案可能用于避免互惠义务。开源许可中的其他条件对潜在的被许可者来说可能是不可接受的（例如，公司反对专利终止条款；MPL 第8.2 节、CPL 第7 节、OSL/ASL 第10 节）。某些公司寻求更详细的保修或赔偿形式，这些通常在开源许可下是提供的。包含特殊豁免或额外利益的许可有时可以通过协商。

任何面临不可接受源码许可的潜在被许可者都应联系许可方获取其他可行的许可方案。任何开源软件的被许可者都应考虑将双重许可作为吸引新客户的一种。

## 最终源码与计划许可

在业务中，时机就是一切。领先几个月开发和商业化产品可能意味着商业成功与失败的区别。对于某些商业被许可者来说，获取源码而非最终获取，可能使得支付这些许可费用是合理的。

这种现实鼓励公司创建许可策略，以从那些愿意支付额外费用以获得更多开发时间的客户那里产生收入。

Ghostscript 的分发者 Artif Software 使用计划许可模式。最初，Ghostscript 新版本并非完全开源，但在随后它们将根据 GPL 变为开源。

## 11 • 共享源码、最终开源或其他许可模型

Artifex Software 的某些客户通过尽早获得 Ghostscript 的新版本来寻求营销优势。

Ghostscript 新版本最初根据 Aladdin 免费公共许可（Aladdin Free Public License）发行。它们同时也根据 Artifex Software 的商业许可发行。

尽管名称具有误导性，但 Aladdin 免费公共许可并非开源许可。它禁止对 Ghostscript 或包含 Ghostscript 的产品进行商业分发。对 Ghostscript 进行商业分发需要 Artifex 商业许可——这需要支付版税。

Ghostscript 的作者、这种通过支付商业优势来换取许可的计划模式的首位实践者 Peter Deutsch 是这样描述 Aladdin 免费许可的：

> 本许可并非开源许可：在其他方面，它对程序的分发施加了限制，特别包括对程序进行销售。虽然 Aladdin Enterprises 尊重并支持开源定义的哲学，并认同 GNU 项目让许可软件以源代码和目标代码的形式自由重新分发的愿望，但我们认为，开源许可不公平地阻止了有用软件开发者获得与其相应的回报，而其他人却从他们的工作中获得经济利益。本许可试图确保那些根据开源和自由软件哲学接收、重新分发和贡献许可程序的人有权这样做，同时保留程序开发者的权利，让那些使用程序来增强商业产品价值的人为这种特权付费。（Aladdin 免费公共许可。）

Aladdin 免费公共许可对分发施加了某些特定限制。在其他方面，如果发生了任何支付行为，它就禁止对 Ghostscript 软件进行商业分发。该许可（第 2 节）描述了一些不允许的分发类型：

- 当直接为程序副本付费时。
- 当进行间接付费时，例如为与程序相关的服务付费。
- 当为包含“免费”程序副本的产品或服务付费时。

在许多其他方面，Aladdin 免费公共许可读起来像 GPL。像 GPL 一样，它允许对源代码进行检查，并创建和分发衍生作品。它甚至包含一项互惠条件：

> 你必须使作品作为一个整体获得许可，并且不根据本许可的条款向所有第三方收取费用。（Aladdin 免费公共许可第 2 节 [c][iv]）。

Ghostscript 的商业分发商 Artifex Software 同时根据商业许可对程序的新版本进行许可。这些许可允许客户将最新版本的 Ghostscript 嵌入到他们的打印机中。它们还允许商业许可者以他们喜欢的任何方式使用源代码，并且不对衍生作品施加互惠义务。

在 Ghostscript 的版本通过 Aladdin 免费公共许可及其商业许可发布约一年后，Artifex Software 会在 GPL 下重新发布该版本，此时该软件才真正变为了开源软件。

Artifex 客户购买商业许可的动力是显而易见的。他们可以使用带有所有最新功能的软件版本。他们可以签订合同获得 Artifex Software 工程师的支持，以帮助他们创建自己的产品和衍生作品。他们可以购买保修。

这些额外的时间和增值服务使得许可作为一种开源业务模式取得了了成功。但这种软件最初并不是开源的，其许可者仅承诺它最终将是开源。

## 结合许可模型

没有任何规定规定许可者必须以开源许可发布其所有软件。即使是对开源友好的公司也可能决定其某些软件应该保持专有。

一个很好的例子是 Jabber, Inc.，它创建并分发即时消息软件。Jabber 有客户端和服务器版本。Jabber 软件的客户端版本是开源的，而服务器版本则不是。

用户桌面上的 Jabber 得益于开源软件的易于获取，这些软件可以从 www.jabber.org 网站免费下载。同时，公司可以在 www.jabber.com 提供的 Jabber 商业服务器软件之上构建根据其需求定制的即时消息应用。这种将相关软件分为 .org 和 .com 分发商的便利划分凸显了开源软件与专有软件之间的区别，但也证明了这两个世界实际上可以相互支持和鼓励。

正如软件分发者可能选择单独许可软件的不同组件一样，他们也可以只在商业许可下发布其开源产品的高级版本。Red Hat 就是这样销售其针对 Linux 优化的集合作品 Red Hat Applications 的。（参见 www.redhat.com。）这些产品由一系列付费提供的 Red Hat 服务支持。

开源许可是一种成功的模型，但它不是一种宗教。替代方案是可能的，而且某些替代方案对开源并非完全不利。许可创意允许贡献者和分发者在赚钱的同时，仍然鼓励、创建和共享开源软件。

## 12 开源诉讼

### 拥有诉讼理由（Owning a Cause of Action）

开源软件诉讼的前景令我们所有人都感到不安。开源软件无法在一个诉讼频繁的环境中繁荣，在这种环境中，每个人都会对感知到的有关开源许可的不公正行为提起诉讼。

事实上，在实践中，关于开源的诉讼非常少。毕竟，一个允许任何人复制、修改和分发其软件的许可者，为什么要对做了这些事情的人抱怨呢？而一个接收了本质上拥有无限权利软件的被许可者，为什么要向许可者要求更多呢？当软件本质上是免费的（即零价格），且软件自由由许可保证时，谁会费力起诉任何人呢？

但诉讼可能会发生，对于任何涉及开源软件的人来说，理解风险至关重要。

风险很低。如果你遵守所获取的开源软件的许可条款，你可能不会受到扰。而且你对开源软件所承担的任何诉讼风险与专有软件基本上是相同的。如果你在一个诉讼频繁的社会中，你需要为诉讼做好准备。

诉讼理由简单是指可以进行法律行动的事。在开源背景下，案件可能产生于知识产权问题，例如版权或专利的所有权，许可和合同条款的解释或可执行性，以及一方或另一方认为不公平的商业行为。诉讼理由被认为属于可以在法院维护该权利的方。

当被许可者根据开源许可接受，或其获得了软件知识产权的非独占权利时，包括制作副本、创建和分发衍生作品以及执行制造、使用和销售包含此类产品的许可的权利。你会记得，许可者对每个被许可者就软件的可用性和质量做了承诺。被许可者可能会起诉以执行这些承诺，即使这意味着要起诉最初给予权利的许可者，或起诉不当干扰这些权利履行的第三方。因此，被许可者可能拥有一个或多个诉讼理由并成为诉讼原告。

许可者根据包含被许可者必须遵守的条款的开源许可发布软件。许可者可以在法院起诉其被许可者，以执行许可条款或终止许可。因此，许可者可能拥有一个或多个诉讼理由并成为诉讼原告。

第三方可能在未经其授权的情况下，拥有体现在开源软件中的版权或专利。他或她可能会提起诉讼，要求移除软件中的侵权知识产权。那么，第三方也可能拥有一个或多个诉讼理由，并成为诉讼的原告。

最后，开源软件还涉及社会利益。政府可能会颁布软件出口法、强制执行安全标准并执行反垄断规则。破产法可能会干扰知识产权的所有权。这些利益可能会在法庭上执行，有时由政府直接执行。政府或政府机构可能拥有一个或多个诉讼理由，并成为诉讼的原告。

当然，拥有诉讼理由并不意味着你一定会在法庭上胜诉。你拥有的仅仅是启动司法程序的权利，而法官或法官根据法官决定原告还是被告胜诉。

## 损害赔金 (Damages)

我们之所以担心诉讼，主要原因是失败的后果。另一个大原因是诉讼本身的成本。对于大公司之间的重大战斗，在美国，每月超过 300,000 美元的律师费已是常态。不过，先不考虑律师费，输掉诉讼的潜在后果是什么？

计算软件纠纷中因诉讼理由产生的损害赔金是复杂的。软件的价值是多少？它是购买软件的价格的函数，还是从软件中获得的利益的函数？损害赔金是取决于损失的内容（如业务机会或销售额）的函数吗？如果损害是由软件的某而非整个软件包造成的，损害赔金是否应该按比例计算？

目前没有默认的损害赔金计算规则，尽管某些许可证模糊地涉及了这个问题（例如，MPL 第 8.3 节；OSL/AFL 第 11 节）。对于版权或专利，并没有标准的许可费费率可以据此计算损害赔金。

损害赔金的前景可能会鼓励客户提起诉讼，但除非有合理的可能获得足够的损害赔金以支付其自身的律师费和成本，否则他们可能不会这样做。
