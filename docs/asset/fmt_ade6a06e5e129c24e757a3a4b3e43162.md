## 3.5.3.3 配置 IPv6tables

`iptables` 用于在 Linux 内核中设置、维护和检查 IPv6 数据包过滤规则表。可能会定义多个不同的表。每个表包含数量的内置链，并可能包含用户定义的链。每个链是规则列表，可以匹配一组数据包。每条规则规定了对匹配的数据包执行什么操作。它可以是一个“目标”（`target`），可以跳转到同一张表中用户定义的链。

如果系统中启用了 IPv6，则应该配置 `iptables`。

注意：此部分泛泛假设从空的 `iptables` 防火墙规则开始（通过使用 `iptables -F` 清空规则建立）。修复步骤仅影响运行中的系统，您还需要配置您的默认防火墙以便在启动时生效。直接通过远程连接对运行系统进行配置通常会导致被排除在系统之外。建议设置一个良好的防火墙配置在启动时运行，并在脚本中配置整个防火墙结构，然后在启动前运行并测试。

以下脚本将实现本节的防火墙规则，并从任何地方开放 `22` (`ssh`) 端口：

```bash
#!/bin/bash

# 清空 ip6tables
ip6tables -F

# 确保默认拒绝防火墙策略
ip6tables -P INPUT DROP
ip6tables -P OUTPUT DROP
ip6tables -P FORWARD DROP

# 确保环回流量已配置
ip6tables -A INPUT -i lo -j ACCEPT
ip6tables -A OUTPUT -o lo -j ACCEPT
ip6tables -A INPUT -s ::1 -j DROP

# 确保出站和已建立的连接已配置
ip6tables -A OUTPUT -p tcp -m state --state NEW, ESTABLISHED -j ACCEPT
ip6tables -A OUTPUT -p udp -m state --state NEW, ESTABLISHED -j ACCEPT
ip6tables -A OUTPUT -p icmp -m state --state NEW, ESTABLISHED -j ACCEPT
ip6tables -A INPUT -p tcp -m state --state ESTABLISHED -j ACCEPT
ip6tables -A INPUT -p udp -m state --state ESTABLISHED -j ACCEPT
ip6tables -A INPUT -p icmp -m state --state ESTABLISHED -j ACCEPT

# 开放入站 ssh (tcp 端口 22) 连接
ip6tables -A INPUT -p tcp --dport 22 -m state --state NEW -j ACCEPT
```

## 4 日志与审计

本节内容描述了如何使用大多数发行版中包含的工具来配置日志记录、日志监控和审计。

建议使用 `syslog` 进行日志记录（配合 `logwatch` 提供摘要），并使用 `auditd` 进行审计（配合 `ausearch` 提供摘要），以自动监控日志中的检测入侵尝试和其他可疑的系统行为。

除了本节步骤创建的本地日志文件外，还建议站点通过加密连接将系统日志的副本收集到安全的、集式的日志服务器上。集中式日志不仅有助于关联可能同时在多个系统上发生的事件，而且在系统被攻破后（攻击者可能修改了受影响系统上的本地日志文件），此时拥有的系统日志信息的第二份副本可能是至关重要的。如果部署了日志关联系统，请配置其处理本节中描述的日志。

由于通常需要关联来自许多不同系统的日志信息（特别是在安全事件发生后），建议连接到本地网络的系统和设备之间同步时间。

定期对本节中描述的所有日志进行监控并进行关联以确定趋势是非常关重要的。一个日志中看似无害的条目，与另一个日志中的条目相比时可能具有重大意义。

关于日志文件权限的说明：日志文件的权限并没有真正的“一刀切”解决方案。许多站点利用组权限，使得处于定义安全组（例如 `wheel`）中的管理员无需将特权提升到 `root` 即可读取日志文件。此外，如果使用了第三方日志聚合工具，它可能需要组权限来读取日志文件，这比将其设置为 `setuid` 为 `root` 更为优。因此，对于日志文件权限有两个修复和审计步骤。一个适用于未实现安全组方法（即仅允许 `root` 读取日志文件）的系统（`root:root 600`）。另一个适用于已具备此类设置并被指派为 `root:securegrp 640` 的站点，其中 `securegrp` 是定义的安全组（在某些情况下为 `wheel`）。

# 4.1 配置系统账户统计 (auditd)

Linux 审计系统基于一组规则运行，收集特定类型的系统活动，以便于事件调查、检测未经授权的数据访问或修改。默认情况下，事件将记录到 `/var/log/audit/audit.log`，这可以在 `/etc/audit/auditd.conf` 中进行配置。

可以指定以下类型的审计规则：

- 控制规则：审计系统的配置。

- 文件系统规则：允许对特定文件或目录的访问进行审计。也称为文件监视（`file watches`）。

- 系统调用规则：允许记录任何指定程序执行的系统调用。

可以设置审计规则：

- 在命令行上使用 `auditctl` 工具设置。这些规则在重启后不会持续。

- 在 `/etc/audit/audit.rules` 中设置。这些规则在生效之前必须经过合并和加载。

注意：

- 对于具有 `arch` 规则参数的 64 位系统，您需要两条规则：一条用于 64 位系统，另一条用于 32 位系统。而对于 32 位系统，只需要一条规则。

- 如果审计系统被配置为锁定（`-e 2`），则需要重启系统以加载更改。

- 规则中的键名（`Key`）是可选的，将不会用于合规性审计。强烈建议使用键名，因为它有助于组织和搜索，例如修复步骤将提供键名。

- 最佳实践是将规则以数字前缀的文件存储在 `/etc/audit/rules.d/` 中。规则必须以 `.rules` 后缀结尾。使用 `augenrules` 根据字母（词法）排序顺序将所有规则合并到 `/etc/audit/audit.rules`。所有基准建议都遵循此修复最佳实践，具体使用以 50 为前缀（如果所有规则集都使用之前的命名约定的话）。

- 您的系统可能经过自定义以更改了默认的 `UID_MIN`。所有示例输出均使用 `1000`，但该值不会用于合规性审计。要确认您系统的 `UID_MIN`，请运行以下命令：`awk '/\s*UID_MIN/{print $2}' /etc/login.defs`

# 规范化

审计系统会对某些条目进行规范化，因此在查看示例输出时请记住：

- 对于未设置登录 UID 的，值 `-1` / `unset` / `4294967295` 是等价的，并被规范化为 `-1`。

- 当比较字段类型且比较的双方都是合的字段类型时（例如 `suid!=uid`），审计系统可能会进行规范化，使输出变为 `uid!=euid`。

- 规则的某些部分可能会重新排列，而其他部分则取决于之前的语法。例如，以下两个语句是：

```
-a always,exit -F arch=b64 -S execve uid!=euid F aud!=-1 -F key=user_emulation
```

以及

```
-a always,exit -F arch=b64 -C uid!=uid -F aud!=unset -S execve -k user_emulation
```

# 容量规划

本节中的建议实现的审计策略不仅会产生大量的日志数据，还可能对系统性能产生负面影响。容量规划非常重要，以免对生产环境产生不利影响。

- 磁盘空间。如果捕获了大量数据，确保日志发送到远程日志服务器，否则磁盘将满。

- 磁盘 I/O。测试日志生成的速率。

- CPU 开销。系统规则可能会产生可观的开销。
