
就绪进程流队列的格式取决于短期调度规划的实现方式。该阶段可以基于先进先出（`FIFO`）原则组织，设置优先级，采用轮转法，或者采用无序方式（称为就绪列表）。

下面我们探讨的所有规划策略和算法均属于短期规划。

## 规划策略 - 抢占式与不可抢占式多任务

在考虑基本的规划策略之前，让我们列举一下将控制权从一个线程转移到另一个线程的几种情况：
- 当进程流进入等待状态后（例如，在输入/输出或连接期间）
- 进程流完成之后
- 显式转移（线程本身暂时将处理器交给其他线程，直到其忙碌）
- 中断（例如，定时器中断可以中断运行时间超过允许的进程流）

上述最后一个选项与其他选项不同之处在于，进程流无法控制何时到达控制转移的时间点，这是操作系统调度器的职责。根据这种控制传输变体，存在两种主要的进程流规划策略——抢占式多任务处理和不可抢占式多任务处理。在抢占式多任务处理中，逻辑进程流可以被暂时中断，而无需其将控制权转移给其他进程流。中断进程流并将控制权转移到另一个进程流的操作通常是在系统中断处理程序中完成的。这一策略在所有现代操作系统中均有实现。

在不可抢占式多任务处理中，进程流可以无限期执行，且不能被操作系统中断。对于不可抢占式多任务处理，上述最后一种控制传输方式并未实现，进程流自身必须将控制权交给操作系统以便传输给其他线程，或者至少进入等待状态。如果一个线程忘记或未能这样做，例如陷入无限循环，其他线程将无法继续工作。`Novell NetWare`中曾实现过这种策略。

显然，在一般情况下实现不可抢占式多任务处理会使系统变得极不稳定（任何用户编写的错误应用程序都可能导致整个系统“挂起”）。实践表明，在包含用户应用程序的系统中无法实现不可抢占式多任务处理。然而，这种策略可用于所有应用程序均在内核模式下运行且实际上是系统驱动程序的系统中。开发此类应用程序需要程序员具备极高的技能，且对应用程序可靠性的要求可与对操作系统本身的要求相媲美。得益于实现简单且没有操作系统对进程流的外部中断，调度器可以在有限范围的任务中提高系统生产力（例如，在`NetWare`操作系统中，它是将系统用作文件服务器）。

## 规划算法

调度算法允许短期调度器从就绪线程中选择下一个要执行的线程。可以说，规划算法实现了规划策略。

根据算法实现的规划策略，它们分为抢占式（位移）和不可抢占式（非位移）。抢占式算法在进程流执行期间中断它们，而非抢占式算法则不中断。一些算法仅适用于其中一种策略，而另一些算法可能同时具有抢占式和非抢占式的实现。

### FIFO 规划

考虑最简单的（“朴素”）不可抢占式算法，在该算法中，进程流按照其在系统中出现的顺序执行，并在进入等待、显式传输或完成之前执行完毕。已完成进程流的队列根据先进先出（`FIFO`）原则组织，因此该算法被称为`FIFO`算法。一旦系统中创建了一个新进程流，其控制单元就会被添加到队列尾部。当处理器释放时，它会分配给队列头部的进程流。

该算法有许多缺点：
- 根据定义，它是不可抢占式的
- 其平均响应时间可能相当长（例如，如果第一个获取处理器的进程流具有较长的`CPU`使用时间间隔，其他进程流即使自身仅使用短时间间隔也需等待）
- 它容易受到护航效应（`convoy effect`）的影响

护航效应可以通过这种情况来解释。假设系统中有一个单独的线程（称之为 `$T_{CPU}$`），受处理器能力限制，以及许多 `$T_{io}$` 线程，受`I/O`能力限制。迟早，`$T_{CPU}$` 线程将变得可用于处理器，并以很长的`CPU`使用间隔执行指令。在此期间，其他 `$T_{io}$` 进程流将完成`I/O`操作，排队已完成的线程并在其中等待，而`I/O`设备则处于空闲状态。当 `$T_{CPU}$` 最终阻塞并转移控制权时，所有 `$T_{io}$` 进程流会快速执行其时间片内的指令，然后转向`I/O`。之后，`$T_{CPU}$` 将再次长时间占用处理器，如此循环往复。

### 循环规划

最容易理解且最公平的算法是*循环规划*（`round-robin scheduling`，轮转调度）算法。在中世纪，“`round-robin`”一词出现在请愿书中，签名呈圆形排列，以至于无法知道谁第一个签名（这个名称表明对于这种算法，所有进程流都是平等的）。

分配给每个进程流的时间段，允许该进程流在此期间运行，称为*时间片*（`time slice`，或时间量子）。当线程在时间片耗尽后仍在运行时，它会被中断，处理器切换到执行另一个线程的指令。如果线程在时间片耗尽前阻塞或完成执行，处理器也会传递给另一个线程。整个系统的时间片长度是相同的。

这种算法相当容易实现。为此，就绪线程的轮转顺序应为一个循环列表。当一个进程流的时间量子耗尽时，它被移动到列表末尾，在那里提供新的进程流。检查时间量子是否耗尽的操作是在来自系统定时器的中断处理程序中执行的。

影响该算法运行的唯一特征就是时间量子的长度。这里必须牢记在切换上下文所花费的时间与响应大量同时交互查询之间保持平衡。

将时间片设置得过长会导致大量的上下文切换，相当大比例的`CPU`时间并非用于有用工作，而是消耗在这些切换上。另一方面，过长的时间片虽然节省了`CPU`时间，但也降低了交互查询的响应时间，因为如果十名用户同时按键，就绪列表中将有十个线程，导致最后一个线程需要等待十个长时间片的时间。在时间片长度无限大的情况下，循环调度退化为`FIFO`算法（所有线程都有时间在时间片耗尽前阻塞或结束）。在实践中，建议将时间片长度设置为 10 - 100 毫秒。

请注意，传统的循环调度可能会向受处理器能力限制的进程流“倾斜”。此类线程倾向于完全利用其时间片，而受`I/O`限制的线程往往在时间片耗尽前就传递控制权，结果导致它们获得的处理时间较少。为了解决这个问题，可以增加时间片的长度（考虑到前述问题），或者引入一个附加的已完成`I/O`进程流队列，该队列优先于已完成队列。

### 优先级规划

循环轮转调度假设所有进程流同等重要。否则，应使用优先级规划。基本思想很简单：每个线程都被赋予一个优先级，而来自就绪线程队列中具有最高优先级的进程流将被执行。优先级可以是静态的，也可以是动态的。

实现优先级规划算法的方法之一是多重队列（多级队列）。在这种情况下，多个队列组织具有不同优先级的进程流组（每组中的进程流通常具有不同的用途）。

选择要执行线程的决策如下做出：
- 如果最高优先级队列包含进程流，它们应使用更简单的调度算法（如循环调度），而不考虑其他队列中的进程流
- 如果该队列中没有线程，较低优先级的线程将移动到该队列

不同的调度算法可以应用于不同的队列，并且可以为每个队列分配一定数量的`CPU`时间。共享优先级是一项困难的任务，如果无法解决这些问题，可能会导致低优先级进程的流等待很长时间。例如，1973 年，麻省理工学院的一台机器停机，原因是一个低优先级进程——它于 1967 年排队等待执行，但此后一直无法运行。这种情况被称为*饥饿*。

解决饥饿问题有多种方法。例如，调度程序可以逐渐降低其所执行流（`stream/thread`，此处指进程上下文）的优先级（此过程称为老化），当该优先级低于下一个优先级流时，将上下文切换到该流。相反，你也有可以逐渐增加等待在用户终端（`UT`）中流优先级的做法。

### 基于性能特征的规划

优先级调度算法的一个重要类别是那些基于对其后续执行特征的知识或评估来做出执行流选择决策的算法。

首先，需要注意的是，在“*最短完成时间优先*”算法（`Shortest Time to Completion First, STCF`）中，当每个流关联一个预计的`CPU`使用时长区间时，系统会选择那个具有最短该区间的流来执行。结果是，占用`CPU`时间较短的流在调度中占据优势，并能更快地离开系统。

`STCF`算法在平均响应时间指标上是理论最优的，也就是说，可以证明对于选定的流组，应用此算法时的平均响应时间将比任何其他算法都小。不幸的是，在短期规划中无法实现它，因为其实现需要对预期特征的预测。在长期规划中，它经常被使用（在这种情况下，操作员在设置任务时必须指示预期的完成时间，系统在做出选择时会考虑这一点）。此外，请注意，此类算法的最优性与其对较长`CPU`使用区间流的“不公平性”是不可分割的。

对于短期调度，可以根据对下一个处理器使用区间长度的估计来实现对该算法的近似，该估计会考虑同一流之前的区间。你可以使用递归公式来计算此估计值：

```
t_{n+1} = a * t_n + (1 - a) * T_n,    0 <= a <= 1,    t_0 = T_0
```

- `t_{n+1}` - 区间长度的估计值；
- `t_n` 是前一个区间长度的估计值；
- `T_n` 是前一个区间的真实长度。

最常用的值是 `a = 0.5`，在这种情况下，只需计算前一个估计值和实际区间值之间的平均值即可。

**最短剩余完成时间优先，`SRTCF`。**

它与 `STCF` 的区别在于，当一个新的线程进入就绪线程队列时，如果下一个 `CPU` 使用时限短于当前线程完成前剩余的时间，则当前线程会被中断，新线程取而代之。

### 多级反馈队列

*多突发带反馈*算法（多级反馈队列）是调度算法（通过配置，它可以退化为其他任何算法），但其中一种变体被广泛用于实现中。在组织数据结构方面，此算法与传统的多级队列算法相似：存在几个具有不同优先级的就绪线程队列，低优先级队列中的线程仅在所有上级队列为空时运行。
