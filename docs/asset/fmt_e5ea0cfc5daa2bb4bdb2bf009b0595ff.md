
一个从子目录 `RCS` 生成对应文件 `x` 的规则。由于目标是 `%`，只要前提文件存在，该规则适用于任何。双冒号使规则终止，这意味着其前提可以是中间文件（参见第 123 页节 10.5.5 [匹配任意规则]）。

此模式有两个目标：

- `tab.c`: `%`
- `bison $<`

这告诉配方 `bison -d x.y` 会生成 `x.c` 和 `x.h`。文件 `foo` 依赖于 `parse.tab.o` 和 `scan.o`，而 `scan.o` 依赖于文件 `tab.h`；当 `parse.y` 改变时，配方 `bison -d parse.y` 只执行一次且 `parse.tab.o` 满足要求（假设 `parse.tab.o` 将从 `tab.c` 和 `scan.o` 重新编译，当 `foo` 从它们链接时）。

## 10.5.4 模式如何匹配

目标模式由前缀和后缀之间的 % 组成，前缀或后缀或两者都可以为空。只有当文件以前缀开头并以后缀结尾且不重叠时，该模式才匹配文件名。前缀和后缀之间的文本被称为主干（stem）。因此，当模式 %. 匹配文件名'test.o'时，主干是'test'。模式规则的前提通过用主干替换字符 '%' 转换为实际文件名。因此，如果示例中的一个前提被写为 %.c，它将展开为'test.c'。

当模式不包含斜杠时（它通常不包含），在文件名与目标前缀和后缀比较之前，文件名中的目录名会被移除。在文件名与目标模式进行比较后，目录名连同斜杠会被添加到从模式规则的前提模式和文件名生成的前提文件名中。目录仅在使用时被忽略，例如 e%c 匹配文件名'src/cat'，以'src/a'为主干。当前提被转换为文件名时，主干中的目录会被添加到前面，而主干的其他部分将替换为 '%'。模式为'src/*c'的主干'src/a'会生成文件名'src/car'。

只有当存在匹配文件名的目标模式，且该规则中的所有前提要么存在要么可以被构建时，模式规则才能用于构建文件。你编写的规则优先于被构建的规则。但请注意，一个前提已经存在的规则，其优先级高于一个必须通过链式隐式规则构建的前提规则（此处原文漏单词，推断为 rules）。

可能有多个规则符合这些标准。在这种情况下，make 将选择主干最短的规则（即匹配最具体的模式）。如果多个模式规则具有最短的主干，make 将选择在 Makefile 中找到的。

这种算法使得更具体的规则优于更通用的；对于：

```
%.c

$(CC) -c $(CFLAGS) $(CPPFLAGS) -o $$
```

```
%.o : %.f

$(COMPILE.F) $(OUTPUT_OPTION) $$
```

```
lib/%o:lib/%c

$(CC) -fPIC $(CFLAGS) $(CPPFLAGS) -o $$
```
给定规则，如果'bar.c' 和'bar.f' 都存在，make 将选择第一个规则并将'bar.c' 编译为'bar.o'。在'bar.c' 不存在的相同情况下，make 将选择第二个规则并将'bar.f' 编译为'bar.o'。

如果要构建'lib/bar.o'且'lib/bar.c' 和'lib/bar.f' 都存在，则选择第三条规则，因为该规则的主干（'bar'）比第一个规则的主干（'lib/bar'）短。如果'lib/bar.c' 不存在，则第三条规则不适用，将使用第二条规则，即使其主干更长。

## 10.5.5 通配匹配模式规则

当模式规则的目标为 % 时，它可以匹配任何文件名。我们称这些规则为任意匹配规则。它们非常有用，但 make 可能会花费大量时间来

思考一下它们，因为它必须为列出的作为目标或前提的每个文件名考虑每一个规则。

假设 Makefile 中提到了 'foo.c'。对于这个目标，make 必须考虑通过链接对象文件 'foo.c.o' 来生成它，或者通过 'foo.c.c' 一步完成 C 编译-链接来生成，或者通过 'foo.c.p' 进行 Pascal 编译-链接来生成，以及许多其他可能性。

我们知道，如果没有 'foo.c'，这些可能性是荒谬的——因为它是一个源文件而不是可执行文件。如果 make 真的考虑了这些可能性，它最终会拒绝它们，因为像 'foo.c.o' 和 'foo.c.p' 这样的文件并不存在。这些可能性非常多，如果 make 必须考虑它们，运行速度将会非常缓慢。

为了提高速度，我们对 make 匹配规则的方式加上了限制。可以应用两种不同的限制，每当你定义一个匹配规则时，都必须为该规则选择其中一种。

其中一种选择是通过定义双冒号（`::`）将匹配规则标记为**终端规则**（terminal）。当一个规则是终端规则时，除非其前提已经存在，否则它就不会生效。仅用隐式规则标记的前提是不够的。换句话说，终端规则下方不允许进一步的链式调用。

例如，从 RCS 和 SCCS 提取源码的内置规则就是终端规则；结果是，如果文件 'foo.c' 不，make 将不会尝试将其作为从 'foo.c' 或 'RCS/SCCS/foo.c.v' 生成的中间文件。RCS 和 SCCS 文件通常是最终源文件，不应从任何其他文件中删除；然而，make 可以通过不寻找重新生成它们的方法来节省时间。

如果你不将匹配规则标记为终端规则，那么它就是**非终端规则**（non-terminal）。非终端匹配规则不能应用于指示特定数据类型的文件名。如果某些不匹配的隐式规则的目标是该文件名，则该文件名就指示了特定类型的数据。

例如，文件名 'foo.c' 匹配规则 `%.c : %.y`（运行 yacc 的规则）。无论该规则实际上是否适用（只有在存在 'foo.y' 时才会适用），其目标匹配的这一事实都是为了防止对 'foo.c' 考虑任何非终端匹配规则。因此，make 甚至不会考虑从 'foo.c.o'、'foo.c.c'、'foo.c.p' 等生成可执行文件 'foo.c'。

这种限制的动机是：非终端匹配规则用于生成包含特定类型数据的文件（如可执行文件），而带有已识别后缀的文件名指示了其他类型的数据（如 C 源文件）。

提供的特殊内置虚拟模式仅用于识别不被考虑的文件名。这些虚拟规则没有前提也没有配方（recipes），在所有其他用途中都会被忽略。例如，内置隐式规则

```
%.p :
```

的存在是为了确保如 'foo.p' 的 Pascal 源文件匹配一个特定的目标，从而避免在 'foo.p.o' 或 'foo.c.p' 上浪费时间。

像 `%.p` 这样的虚拟模式规则是为每个列为可在后缀规则使用的有效后缀制作的（参见第 10.7 节 [旧式后缀规则]，第 125 页）。

## 10.5.6 取消隐式规则

你可以通过定义一个具有相同目标和前提但配方不同的新模式规则，来覆盖内置隐式规则（或你自定义规则）。当新规则被定义时，内置规则将被替换。新规则在隐式规则序列中的位置取决于你编写该规则的位置。

你可以通过定义一个具有相同目标和前提但没有配方的模式规则来取消内置隐式规则。例如，以下规则将取消运行汇编器的规则：

```
%.o: %s
```

## 10.6 定义最后的备选默认规则

你可以通过编写一个没有前提的终端匹配模式规则（参见第 10.5.5 节 [匹配任意规则]，第 123 页）来定义一个最后的备选隐式规则（last-resort implicit）。这与任何模式规则都一样；它唯一特殊之处在于它将匹配任何目标。此类规则的配方将用于所有没有自己的配方且没有其他隐式规则适的目标和前提。

例如，在测试一个文件时，你可能不需要源文件包含真实数据，只需要它们存在即可。你可以这样做：

```
$$:
```

你也可以定义一个配方，用于那些没有任何规则（甚至是那些没有指定配方的规则）的目标。你通过为目标 `.DEFAULT` 编写规则来实现这一点。规则的配方将用于所有未在任何隐式规则中出现过目标、且没有隐式规则适的前提。自然地，除非你写了一个，否则没有 `.DEFAULT`。

如果你对 `.DEFAULT` 使用了没有前提配方：

```
.DEFAULT:
```

存储为 `.DEFAULT` 的配方将被清空。然后 make 的表现就像你从未定义过 `.DEFAULT` 一样。

如果你不希望目标从匹配任意模式规则或 `.DEFAULT` 获取配方，你也不希望该目标有任何配方，你可以给它一个空配方（参见第 5.9 节 [定义空配方]，第 57 页）。

你可以使用最后的备选规则来覆盖另一个包含的部分。参见第 3.6 节 [覆盖另一个 Makefile 部分]，第 15 页。

## 10.7 旧式后缀规则

后缀规则是定义隐式规则的旧方法。模式规则更通用、更清晰。它们分为两种：双后缀和单后缀。双后缀由一对后缀定义：目标后缀和源后缀。单后缀由单个后缀定义。

已知后缀简单来说特殊目标 `.SUFFIXES` 的前提名称。你可以通过为 `.SUFFIXES` 编写一个添加更多前提的规则来添加自己的后缀，例如：

```
.SUFFIXES: .hack .win
```

这将 `.hack` 和 `.win` 添加到后缀列表的末尾。

如果你想消除默认已知后缀而不是仅仅添加它们，请为 `.SUFFIXES` 编写一个没有前提的规则。特殊例外，这将消除了 `.SUFFIXES` 的所有现有前提。你可以编写另一个规则来添加你需要的后缀。例如：

```
.SUFFIXES: # 删除默认后缀

SUFFIXES: .c .h # 定义我们的后缀列表
```
