# 第 7 章 开发健壮的程序

本章涉及开发健壮的程序。健壮的程序能够优雅地处理错误情况。它们无论用户做什么都不会崩溃。构建健壮的程序是编程实践至关重要的。编写健壮的程序需要纪律——它通常意味着考虑可能发生的每个问题，并为你的程序制定行动计划。

## 时间花在哪里了？

程序员计划得很糟糕。在几乎每个编程项目中，程序员花费的时间比预估出的两倍甚至八倍。这有很多原因，包括：

- 程序员并不总是为每天的非编码活动安排时间。
- 程序员经常低估反馈时间（往返修改请求的时间）。
- 程序员并不总是理解他们所产出的完整范围。
- 程序员经常低估使程序健壮所需的时间。
- 最后一项是我们在这里感兴趣的。开发健壮的程序比猜测需要更多精力。

## 开发健壮程序的建议

### 用户测试

测试是程序员做的最基本的事情之一。如果你没有测试过某个东西，就应该假设它无法工作。然而，测试不仅仅是确保你的程序可以工作，还要确保你的程序不会崩溃。例如，如果我有一个程序只应该处理正数，你需要测试如果用户输入负数会发生什么。或者字母。或者数字零。你必须测试如果他们在数字前面或后面加上空格，以及其他小

各种可能性。你需要确保以符合用户逻辑的方式处理用户数据，并以符合你程序其他部分逻辑的方式传递这些数据。当你的程序发现不符合逻辑的输入时，它需要执行适当的操作。根据程序的不同，这可能包括终止程序、提示用户重新输入值、通知中央错误日志、回滚操作，或者忽略它并继续。

你不仅应该测试你的程序，还需要让其他人也进行测试。你应该邀请其他程序员和程序的用户来帮助你测试程序。如果某个问题对你的用户来说是个问题，即使对你来说没问题，也需要修复它。如果用户不知道如何正确使用你的程序，这应该被视为一个需要修复的 bug。

你会发现，用户在你的程序中发现的 bug 比你发现的要多得多。原因是用户并不知道计算机期望什么。你知道计算机期望什么类型的数据，因此更有可能输入符合计算机逻辑的数据。用户输入的是符合他们逻辑的数据。允许非程序员为了测试目的使用你的程序，通常能给你提供关于程序真实健壮程度的更准确的结果。

### 数据测试

在设计程序时，你的每个函数都需要非常明确地定义它将接受或不接受的数据类型和范围。然后你需要测试这些函数，以确保它们在处理适当数据时能够按照规范执行。最重要的是测试边界情况（corner cases）或边缘情况（edge cases）。边界情况是最可能引起问题或产生意外之外行为的输入。

在测试数值数据时，有几个是你总是需要测试的边界情况：

- 数字 0
- 数字 1
- 期望范围内的数字
- 期望范围外的数字
- 期望范围内的第一个数字
- 期望范围内的最后一个数字
- 范围以下的第一个数字
- 期望范围以上的第一个数字

例如，如果我有一个程序应该接受 5 到 200 之间的值，我至少应该测试 0, 1, 4, 5, 153, 200, 201 和 255（153 和 255 分别是在范围内和外随机选择的）。你拥有的任何数据列表也是如此。你需要测试程序在处理包含 0 个、1 个项目、大量项目等的列表时行为是否符合预期。此外，你还应该测试任何转折点。例如，如果你有不同的代码来处理 30 岁以下和以上的人，那么你至少需要测试 29、30 和 31 岁的人。

会有一些内部函数，是你假设它们获取了良好的数据，因为你在在此之前已经检查了错误。然而，在开发过程中，你通常仍然需要检查错误，因为其他代码可能存在错误。为了在开发期间验证数据的一致性和有效性，大多数语言都提供了一种方便检查数据正确性假设的机制。在该语言中，有一个 `assert` 宏。你只需要在代码中放入 `assert(a > b);`，如果条件不成立并运行到该处，它就会报错。此外，由于在代码稳定后进行此类检查是浪费时间，`assert` 宏允许你在编译时关闭 `assert`。这可以确保你的函数接收到良好的数据，而不会在发布给公众的代码中引起不必要的幻灯片效果。

### 模块测试

你不仅应该测试整个程序，还需要测试程序的每一个部分。在开发程序时，你应该通过提供你创建的数据来测试单个函数，以确保它们做出恰当的响应。

为了有效地做到这一点，你必须开发专门用于调用其他函数进行测试的函数。这些被称为驱动程序（drivers，不要与硬件驱动程序混淆）。它们只是加载你的函数，为其提供数据并检查结果。当你正在处理未完成的程序部分时，这特别有用。由于你无法将所有部分一起测试，你可以创建一个驱动程序来逐个测试每个函数。

此外，你正在测试的代码可能会调用尚未开发的函数。为了解决这个问题，你可以写一个称为“存根”（stub）的小函数，它只需返回该函数继续执行所需的值即可。例如，在一个一个电子商务应用程序中，我有一个名为 `is_ready_to_checkout` 的函数。在我实际编写该函数之前，我只是在每次调用时都将其设置为 `true`，这样依赖于 `is_ready_to_checkout` 的函数就可以在该函数尚未完全实现的情况下继续运行。
