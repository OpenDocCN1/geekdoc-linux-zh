
# 第 13 章

## 13.1
由于命令行参数个数无效导致的启动错误将使用 `syslog` 进行记录。

## 13.2
`echo`、`discard` 和 `charger` 服务器的 TCP 版本在被 `inetd` fork 之后，都将作为子进程运行，因为这三个进程会一直运行到客户端终止连接为止。另外两个 TCP 服务器 `time` 和 `daytime` 不需要需 fork，因为它们的服务实现非常简单（获取当前时间和格式化，写入它，然后关闭连接），这两个服务器直接由 `inetd` 处理。所有五个 UDP 服务器都是直接在不进行 fork 的情况下被处理的，因为每个服务器在响应触发服务的客户端数据报时，最多只生成一个数据报。因此，这些服务器也是直接由 `inetd` 处理的。

## 13.3
这是一个著名的拒绝服务攻击（`(CERT 1996a)`）。来自端口 7 的第一个数据报会导致 `charger` 服务器向端口 7 发回一个数据报。该数据报被回显（`echo`）并向 `charger` 服务器发送了另一个数据报。这个循环会持续下去。一种在 FreeBSD 中实现的解决方案是：如果传入数据报的源地址属于任何内部服务器，则拒绝向任何一个内部服务器发送数据报。另一种解决方案是禁用这些内部服务，可以通过每个主机上的 `inetd` 或者该机构连接到 Internet 的路由器来实现。

## 13.4
客户端的 IP 地址和端口是从 `accept` 填充的套接字地址结构获取的。

`inetd` 不对 UDP 套接字执行此操作是因为读取数据报的 `recvfrom` 是由执行的实际服务器完成的，而不是由 `inetd` 本身完成。

`inetd` 可以指定 `MSG_PEEK`（第 14.7 节）读取数据报，仅为了获取客户端的 IP 地址和端口，同时将数据报留在原处供实际服务器读取。

# 第 14 章

### 14.1
如果没有设置处理函数（`handler`），则第一次调用 `signal` 设置为 `SIG_DFL` 的返回，以及调用 `signal` 重置处理函数的调用，将只是将其重置为默认值。

### 14.3
这里仅仅是 `for` 循环：

```c
for ( ; ; ) {
  if ( n = Recv(sockfd, recvline, MAXLINE, MSG_PEEK) == 0)
    break;       /* server closed connection */
  Ioctl(sockfd, FIONREAD, &npend);
  printf("%d bytes from PEEK, %d bytes pending\n", n, npend);
  n = Read(sockfd, recvline, MAXLINE);
  recvline[n] = 0;      /* null terminate */
  Fputs(recvline, stdout);
}
```

### 14.4
数据仍然会被输出，因为从主函数的末尾退出等于从该函数返回，而主函数是由 C 启动程序如下调用的：

```c
exit(main(argc, argv));
```

因此，`exit` 被调用，标准 I/O 清理程序也被调用。

# 第 15 章

### 15.1
`unlink` 从文件系统中删除路径，当客户端稍后调用 `connect` 时，连接将失败。服务器的监听套接字不受影响，但在 `unlink` 之后没有客户端能够连接。

### 15.2
即使路径存在，客户端也无法连接到服务器，因为要使 `connect` 成功，Unix 域套接字必须处于打开状态并绑定到该路径（第 15.4 节）。

### 15.3
当服务器通过调用 `sock_ntop` 打印客户端的协议地址时，输出是 `"datagram"`（无路径），因为没有路径绑定到套接字的默认值。

一种解决方案是在 `udp_client` 和 `udp_connect` 中专门检查是否为 Unix 域套接字，并将临时路径绑定到套接字。这把协议逻辑放在了它所属的库函数中，而不是我们的应用程序中。

### 15.4
尽管我们强制服务器对 26 字节的回复进行 1 字节写入，但在客户端中加入 `sleep` 保证了在调用 `read` 之前接收了所有 26 个段，导致 `read` 返回整个回复。这仅仅是为了（再次）确认 TCP 是一个流，没有固有的记录标记。

若要使用 Unix 域协议，请使用两个命令行参数 `/local`（或 `unix`）和 `/tmp/datetime`（或你任想要使用的任何临时路径）启动客户端和服务器。一切都没有变化：客户端每次运行时，每次都会返回 26 字节。

由于服务器对每次 `send` 都使用 `MSG_ERROR` 标志，每个字节被视为一个逻辑记录，`read` 每次被调用都会返回 1 字节。这里发生的情况（Berkeley 派生的实现默认使用 `MSG_ERROR` 标志）是未文档的，且不应在生产环境中使用。从实现的角度来看，输出到内存缓冲区（`mbuf`）的 `MSG_ERROR` 标志由内核从发送套接字保留到接收套接字的缓冲区。当调用 `read` 时，`MSG_ERROR` 标志仍然附加在上面，因此通用 `read`（支持 `MSG_ERROR` 标志）返回 1 字节。这对于 TCP 是不可行的，因为 TCP 永远不会查看 `mbuf` 头部，即使它查看，也没有办法将此标志传递给接收端 TCP。（感谢 Matt Thomas 指出这一“特性”。）
