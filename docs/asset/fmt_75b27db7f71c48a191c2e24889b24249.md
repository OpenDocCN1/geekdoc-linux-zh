
你应该建立一个用于恢复备份的文件系统——在大多数情况下，保留数据库是明智的，以防备份损坏或制作不当。此文件系统应该与 db 文件系统具有相同的特性。

一个用于向磁盘转储和加载的区域（在备份到磁带之前），并与所有区域分开，提供了最大的灵活性。理想情况下，该区域在加载过程中使用处于空闲状态的磁盘。

在之前映像（Before Image）之前，IO 本质上是顺序的。磁盘执行顺序操作的速度比随机操作快 10 到 20 倍。如果你混合了这些类型，就会获得随机访问的性能。如果对 IO 操作的总需求大于磁盘所能提供的，就会出现磁盘队列和性能下降。这种现象首次出现的地方是日志检查点（log checkpoints），此时所有用户都会冻结，因为需要对你拥有工作组许可的数据进行内存拷贝（如果你没有使用企业许可的异步页写入器的话）。专门分配一个磁盘给 `.bi` 文件，可以使其避免受到其他 IO 活动的影响，并以全速度运行。这对于工作组许可尤为重要，而且当在你开始压榨机器性能时，对于企业许可来说同样重要。

为 `.ai` 文件专门分配一个磁盘的原因与上述相同，并且还有一个额外的原因——之后映像（after-imaging）提供了前滚恢复（roll forward recovery）。如果 `.ai` 文件位于你尝试恢复时发生损坏的介质上，你就会陷入进退两难境地。如果可能，你应该为之后映像留出一块磁盘。如果无法做到，你对严重的硬件故障和管理错误（如不小心重新格式化磁盘）的保护将非常有限。你应该使用之后映像——它通过通往未来某个时间点的路径，保护你免受极可能的用户错误（如删除所有客户）的影响。但除非它是一个独立的磁盘，否则你无法获得该功能的全部收益。

镜像（Mirroring）`.bi` 和 `.ai` 文件是一个好主意——你不希望因为任何原因丢失其中任何一个。镜像不是任何者的替代品。`.bi` 文件对于成功的崩溃恢复至关重要。镜像会忠实地重人为错误，例如之前提到的“删除所有客户”场景，或者像在错误的目录下执行 `rm *` 这种简单的操作。只有之后映像可以从这些失误中救你。镜像提高了可用性——但它不能保护你免受所有影响。

划分（Striping）`.bi` 和 `.ai` 文件没有用——它破坏了 IO 模式的顺序性，并限制了这些文件的潜在吞吐量。当然，RAID 5 完全不适用于这些文件。

内存受限严重或查询索引不良的系统可能会对 `-T` 会话启动参数定义的文件区域产生高 IO 速率。这是一个 Progress 为各种用途创建临时文件的文件系统。这些文件通常是未链接的，因此是不可见的，但可以使用 `-t`（小写）参数使其可见。在 `-T` 区域找到的主要文件类型有：

- - Srta<pid>: 排序文件——客户端查询解析和 r-code 缓冲
- Lbia<pid>: 本地映像（Local Before Image）——子事务和变量回滚节点
- DBIa<pid>: 临时缓冲区溢出

如果你无法使用内存来减少这种 IO（`-mmax` 和 `-Bt` 参数是相关参数），那么确保 `-T` 区域具有良好的 IO 吞吐量是非常重要的——例如在划分且镜像的磁盘组上。

## 创建新数据库

虽然有很多设置数据库的方法，但我们将专注于性能最好的方法。Progress 提供了两种使用数据库的方法——单卷（single-volume）和多卷（multivolume）。在大规模环境中，多卷是绝对必要的，但它为所有用户提供了许多优势。

## 多卷

Progress 提供两种不同类型的数据库布局。单卷数据库最容易创建，但最大大小为 2GB字节（`seek()` 系统调用的限制）。在多卷数据库中，数据区（data extents）仍有 2GB 的限制，但可以将它们组合以获得更大的存储容量。从 Progress 9 版本开始，所有数据库都将是多卷的。这结合潜在的性能增强，使得多卷成为推荐选择。

Progress 数据库分为四类文件——之前映像区（before-image extents）、之后映像区（after-image extents）、数据区（data extents）和 DB 文件。之前映像使 Progress 具有备份事务的能力。之前映像文件通过扩展名 `.b1`、`.b2`，或者单卷数据库的简写 `.b1` 来识别。之后映像区以 `.a1`、`.a2` 等结尾，以及前滚恢复文件。数据区既包含数据也包含指向数据的索引。这些文件中的每一个都在一个结构文件（structure file）中描述，然后在集合中组合在一起形成数据库。结构文件以 `.st` 结尾，用于创建其二进制等效文件 `.db`——一旦创建创建，就不需要 `.st` 文件，并且可以使用 `prostruct` 工具重新创建——然而，为了文档记录的需要，仍保留它。

创建新数据库的步骤在 Progress 文档中有明确定义，但这里提供一个简单的示例。首先，你需要创建一个包含所有区列表的 `.st` 文件。区由其类型（之前映像、之后映像、数据）、是否是固定的或可变的，以及以 1k 块为单位（或你创建的数据库的任何块大小——1k 是默认值）来定义。只能有一个可变之前映像和一个可变数据区。让我们保持示例简单，定义一个包含之前映像和数据的一个固定区和一个可变区的结构文件。强烈建议使用之后映像区，因为它们提供了从上次备份点到此后任何时间点恢复数据库的能力。为了简单起见，本示例中未包含它们。这样的结构将命名为 `mydata.st`，并如下所示：

```
B /mnt/bi/myData.b1 f 10000
B /mnt/bi/myData.b2
D /mnt/db/myData.d1 f 500
D /mnt/db/myData.d2
```

注意，第一列表示区类型，B 表示固定。第二列是路径，第三列是类型，第四列是大小。要创建数据库，使用以下命令：

```
prostruct mydata.st
```

现在数据库可以以单用户模式访问了。为了允许一个用户进入数据库，有必要启动多用户代理（broker）。只需使用 `proserve` 命令启动该代理。在没有任何其他选项的情况下，该代理允许本地系统 10 个用户。要允许更多用户，使用 `-n` 选项。对于网络访问，使用 `-H -N -S`。这些选项以及许多性能参数在这里讨论，在《Progress 系统管理参考手册》中也有。

## 设置缓冲区池

在大多数 Progress 安装中，内存消耗最大 `-B` 缓冲区池。这是一个用于缓存磁盘块以提高性能的共享内存区域。不要按用户调优！要根据子系统处理 IO 的能力进行调优。基本上，你正试图将物理 IO 降低到磁盘利用率在 25% 到 50% 之间、没有队列且响应时间小于 20ms 的水平。如果你的磁盘平均访问时间为 10ms，那么它们每秒可以执行 100 次 IO 操作，并且可以在不阻塞的情况下维持 25 到 50 次 IO 操作。

诚然，用户数量可能与数据库访问请求有关。但它们与缺失率之间的关系是非线性的。它的曲线类似于：

> R = L / sqrt(c * B )

其中：

R = 物理 IO 操作

L = 逻辑池大小

B = 缓冲区池大小

C = 某个常数（可能接近 1.5）

因此，这里没有所谓的“每用户 X 内存”的规则可以让你遵循。不过，为了得到一个大致范围，每个用户 2-4MB 是一个很好的猜测。一旦你有了一些数据，就可以更准确地调整该值，以更好地满足目标 IO。图 8.7 提供了一个示例。
