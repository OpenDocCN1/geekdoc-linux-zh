
## 文件系统检查

当指定备用超级块时，`e2fs`程序将确保在文件系统完成后适当更新主超级块。确切的块号取决于文件系统中使用的块大小。如果你之前如前所述识别了文件系统，则需要使用`-B`选项指定更大的块大小。例如：

```
fsck -B 4096 -v /dev/hda3
```

这些数字随系统而变化，请记住，理想情况下是在格式化硬盘时运行`dump2fs`程序，并将打印结果贴在系统机箱内部。这里是`dump2fs`输出的列表：

| :--- | :--- |
| 文件系统状态 | not clean (未清理) |
| 错误行为 | Continue (继续) |
| 文件系统 OS 类型 | Linux |
| inode 数量 | 3112960 |
| 块数量 | 6225187 |
| 留块数量 | 311259 |
| 空闲块 | 465897 |
| 空闲 inode | 2891098 |
| 第一个块 | 1 |
| 块大小 | 1024 |
| 分段大小 | 1024 |
| 每组块数 | 8192 |
| 每组段数 | 8192 |
| 每组 inode 数 | 4096 |
| 每组 inode 块 | 512 |

当你看到正确的`-b`参数是`8193`，且`-B`块大小是默认的`1024`时。

使用`fsck`遇到的另一个可能问题是硬盘上存在物理错误。在这种情况下，使用`-c`选项运行`fsck`。例如：

```
fsck -c /dev/hda2
```

`fsck`遇到的另一种可能性是`fsck`发现了一个格式错误的超级块，因此它宣布问题并终止。使用`-b`选项运行程序，提供有效备份超级块的块号。例如：

```
fsck -b 8193 -v /dev/hda3
```

## MBR 修复

即使根文件系统正常工作，如果缺少共享库，系统仍然可能挂起。在这种情况下，MBR损坏了，需要修复。为了修复这个问题，你可以通过救援磁盘修复，或者使用`ln`命令。最简单的方法是挂载磁盘，例如：

```
mount /dev/initrd
```

通常情况下，LILO在挂载磁盘后运行。在这种情况下，MBR损坏了，需要修复。这种方法是删除旧的链接并安装新的链接，无需重新磁盘。最简单的方法是挂载救援磁盘，例如：

```
mount /dev/hda3
```

```
mkknod /dev/initrd b 1 250
```

有关创建设备块的更多信息，请参阅第3章“Shell和命令”，或参考`mkknod`的帮助页。

## 执行文件系统一致性检查

通过两种方式之一到达此处：如果你能够启动旧内核，然后运行`fsck`失败，并提示你手动运行`fsck`。如果你是从救援磁盘启动的，它会将一个小型根文件系统加载到一个或多个RAM磁盘中。你无法启动硬盘的事实表明MBR存在问题，但MBR修复可以推后，改为在修复MBR之前，先确保根文件系统是有效的。无论你是如何到达此处的，下一步都是手动运行`fsck`程序，但随后你很快会发现`fsck`有许多形式：`debugfs`、`dosfs`、`dumpe2fs`、`efsck`、`fsck.ext2`和`fsck.minix`。`mkfs`也是如此；它的形式有`mk2efs`、`mkfs.ext2`、`mkfs.minix`和`mkfs.msdos`。这些`fsck`多重形式的原因是，Unix类操作系统在历史上只有一个文件管理器前端和后端，而Linux具有一个前端和多个后端管理器。`fsck`和`mkfs`程序是各种文件系统类型的后兼容前端，默认为`ext2`文件系统类型。

```
fsck /dev/hda2
```

或者

```
efsck /dev/hda2
```

在此时，`fsck`程序可能会发现任何数量的问题，包括：

- 缺失或重复的数据块、inode和目录
- 格式错误的超级块（superblock）或块组描述符
- 硬盘上的物理错误
