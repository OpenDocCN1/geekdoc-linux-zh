
## 9.6 从磁盘读取 Folios

数据实际上从磁盘读取到页缓存的两个原理——预读（readahead），我们在第 9.7 节中探讨它，以及从磁盘读取单个 folio（可能是通过批处理操作）。我们在本节中探讨后者。

有许多调用者需要我们从磁盘读取单个 folio。我们已经在第 9.5 节中检查了实现此点的两种核心方法，解释了内核通常如何访问页缓存 folio。

通过 `read()` 系统调用读取 folios 时，我们通过 `filemap_get_pages()` 批量读取 folio，如列表 9-44 和第 9.5.2 节所示。同样，`filemap_fault()` 要求我们在必要时从磁盘读取，如第 9.4 节和列表 9-35 所示。

此外，还有许多文件系统、驱动程序和其他系统的 folio 访问最终会调用 `do_read_cache_folio()`（见图-9-9 和列表 9-53），在必要时从磁盘读取。无论操作源自哪里，folio 最终通过 `filemap_read_folio()` 从磁盘读取，我们在列表 9-56 中检查了它。

### 列表 9-56: mm/filemap.c: filemap_read_folio()

```c
static int filemap_read_folio(struct file *file, filler_t filler,
                              struct folio *folio)
{
    int error;

    /*
     * 之前的 I/O 错误可能是由于临时故障导致的，
     * 例如，多路径错误。如果 read_folio
     * 失败，则会设置 PG_error。
     */
    folio_clear_folio(folio);

    /* 开始实际读取。读取将解锁页面。 */
    error = filler(file, folio);
    if (error)
        return error;

    error = folio_wait_locked(folio);
    if (error)
        return error;

    if (page_uptodate(folio))
        return 0;

    if (file)
        shrink_readhead_aio(file);

    return -EIO;
}
```

我们需要传入此函数的 folio 已经是锁定状态，准备好写入。此函数本质上是 `filler` 的封装，`filler` 的类型执行实际读取，如列表 9-57 所示。

### 列表 9-57: include/linux/page.h: filler_t


如果 filler 返回错误，我们直接将其返回给调用者。否则，我们等待锁释放，此时 folio 应该已经被读取并更新。如果是这样，我们返回零表示没有错误。

### 列表 9-58: mm/filemap.c: page_endio()

```c
/*
 * 在完成页的 I/O 后，调用此例程更新页
 * 标志
 */
void page_endio(struct page *page, bool is_write, int err)
{
    if (!is_write) {
        if (!err) {
            SetPageUptodate(page);
        } else {
            ClearPageUptodate(page);
            SetPageError(page);
        }
        unlock_page(page);
    } else {
        if (err) {
            struct address_space *mapping;

            SetPageError(page);

            mapping = page_mapping(page);
            if (mapping)
                mapping_set_error(mapping, err);
        }
        end_page_writeback(page);
    }
}
```

这分为两个部分——读和写。在两种情况下，如果出现错误，我们设置 `PG_error` folio 标志，写入时我们通过 `mapping_set_error()` 在相关的 `struct address_space` 映射对象中设置错误。

对于回写，调用 `end_page_writeback()`，它会调用 `folio_end_writeback()`，该函数封装了 `_folio_end_writeback()`，我们将在回写章节的列表 9-72 中探讨它。

此处相关的是读取情况——我们使用生成的 folio 标记辅助函数来设置/清除 folio 标记，在没有发生错误时设置 `PG_uptodate`，如果发生错误则清除它（并设置 `PG_error`）。在这两种情况下，我们都通过 `unlock_page()` 解锁 folio，它封装了 `folio_unlock()`。关于 folio 锁的更多细节请参见第 9.11 节。

## 9.7 预读 (Readahead)

预读（Readahead）是指在读取或文件支持的页异常之外将需求之外的页面读取到页缓存中的过程。这样做是基于：用户可能想要访问顺序数据，因此在请求之前数据的同时提前读取这些数据会更高效。

预读机制允许交错读取：当发生主页异常（major fault）时，为 folio 标记 `PG_readahead` 标记（即异常需要阻塞调用进程直到可以从磁盘读回数据）；当该 folio 在次页异常（minor fault，即 folio 存在于页缓存中但尚未映射到进程）中读取时，会再次触发预读。

第一种预读被称为“同步”预读，后者是异步预读。当我们顺序读取数据时，每当在次页异常中遇到 `PG_readahead`，我们就会开始下一批预读，并为后续的 folio 标记 `PG_readahead` 以再次触发预读。

这允许连续的后台异步读操作发生，意味着对于顺序访问，我们可以轻松地从根本上避免主页异常的发生，或者至少显著减少它们。

默认情况下，预读的最大页数由块设备对象（BDI）决定，由 `struct backing_dev_info->ra_pages` 指定。

此参数可以通过块设备文件（例如 `/dev/sda`）上的 `ioctl()` 使用 `BLKRAGET` 命令（并使用 `BLKRAGET` 命令检索）更改为 `bdi_alloc()` 中的 `VM_READAHEAD_PAGES`。

此预读值也可以在 sysfs 目录 `/sys/devices/virtual/bdi/maj:min/read_ahead_kb`（其中 `maj` 和 `min` 分别为主、次设备号）中设置，或者更方便地通过 `/sys/block/sda/bdi/read_ahead_kb`（例如 `/dev/sda`）设置。该值以 KB 为单位。

你也可以使用 `blockdev --getra /dev/sda` 使用 blockdev CLI 获取以逻辑扇区（硬编码 512 字节单位）表示的预读。

例如 `/dev/sda1`，使用 `blockdev --setra 512 /dev/sda1` 将预读设置为例如 512 扇区（256 KiB）。

预读行为可以由用户调节，用户可以使用 `madvise()` 或 `posix_fadvise()` 来提示文件将按顺序访问（分别通过 `MADV_SEQUENTIAL` 或 `POSIX_FADV_SEQUENTIAL`），或者将按随机访问，因此不应发生预读（分别通过 `MADV_RANDOM` 或 `POSIX_FADV_RANDOM`）。

因此这允许在文件支持的内存映射在 `struct vm_area_struct (VMA)` 级别（使用 VMA 标记）或 `struct file` 级别（使用文件标记）修改三种不同的预读“模式”，如表 9-1 所示。

### 表 9-1：预读模式

| 模式 | madvise() | 标记 | posix_fadvise() | 标记 | VMA 标记 | 文件模式 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 随机访问 | `MADV_RANDOM` | | `POSIX_FADV_RANDOM` | | `VM_RAND_READ` | `FMODE_RANDOM` |
| 正常 | `MADV_NORMAL` | | `POSIX_FADV_NORMAL` | | | |
| 顺序 | `MADV_SEQUENTIAL` | | `POSIX_FADV_SEQUENTIAL` | | `VM_SEQ_READ` | `FMODE_SEQUENTIAL` |

预读是由虚拟 `read()` 或页异常机制触发的，这些第 9.5 节中的 `filemap_get_pages()`（见列表 9-44 和第 9.5.2 节）或第 9.4 节中的 `filemap_fault()`（见列表 9-35），或者通过自定义文件系统代码或内核机制触发。

预读有两种：

- **同步预读**：发生主页异常时执行，即 folio 不存在于页缓存中。此时，我们应该获取 folio 并从那时开始启动预读。我们读取某些 folio 并建立一个“同步尾部”——除了立即读取的 folio 之外，我们将在用户访问其中一个同步预读 folio 时读取它们。我们为该 folio 标记 `PG_readahead` 标记，异步预读据此判断何时执行此任务。我们在第 9.7.1 节探讨同步预读。

- **异步预读**：发生次页异常时执行，即 folio 存在于页缓存中但尚未映射到进程。此时，我们应该获取 folio 并从那时开始启动预读。我们读取某些 folio 并建立一个“同步尾部”——除了立即读取的 folio 之外，我们将在用户访问其中一个同步预读 folio 时读取它们。我们为该 folio 标记 `PG_readahead` 标记，异步预读据此判断何时执行此任务。我们在第 9.7.2 节探讨异步预读。

```c
/**
 * struct file_ra_state - 跟踪文件的重读状态。
 * @start: 最近一次重读的开始位置。
 * @size: 最近一次重读中读取的页数。
 * @async_size: 立即不需要且因此“提前”读取的页数。
 *              当这些页中的第一个被访问时，开始下一次
 *              重读。

 */

    unsigned int size;
    unsigned int async_size;
    unsigned int ra_pages;
    unsigned int mmap_miss;
```
