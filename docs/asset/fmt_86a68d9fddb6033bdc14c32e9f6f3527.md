
| 2 | INT | 中断 | 在用户按下 INTR 键（由 `stty` 命令定义）后发送；通常是 Ctrl-C；有时是 BREAK。 |

| 3 | QUIT | | 在用户按下 QUIT 键后发送（由 `stty` 命令定义；没有默认值）。 |

| 9 | KILL | 杀死 | 仅由 `kill` 命令发送；它强制立即终止进程且无法被忽略或捕获。 |

| 10 | BUS | 总线错误 | 通常由编程错误引起，总线错误只能由硬件故障引起。 |

| 11 | SEGV | 段错误 | 由程序引用无效的内存地址引起；只能由二进制文件引起。 |

| 13 | PIPE | 管道 | 当没有可用进程读取管道时向管道写入数据引起；通常作为错误出现。 |

| 15 | TERM | 终止 | 由 `kill` 命令或系统函数引起。该信号是按次序终止的温和请求；进程可以忽略该信号。 |

如果你省略了 `signal`，则默认发送 `TERM` 信号（除非指定了 `-1` 选项，在这种情况下将不发送任何信号）。

对于 `job`，请指定一个或多个作业或进程标识符。作业引用可以指向以下任何项：

- 本章前面“引用作业编号：fg 和 bg”中介绍的任何 `%` 运算符。
- 进程 ID (PID) 数字。

`%` 运算符和进程 ID 可以在命令行上使用——例如，`kill %2 1660 543 33%`。

`job` 没有默认值。你必须指定至少一个接收信号的作业或进程。

你可以使用命令 `kill -1` 列出有效的符号信号名称。在使用新版本不熟悉的 csh 版本时，始终使用 `kill -1` 命令来识别精确的信号。

另见 `bg`、`fg`、`wait` 和 `jobs` 命令更多有关使用 C shell 进行作业控制的信息。

## 使用 shell 的哈希表

shell 哈希表通过识别命令可能所在的目录来执行搜索。哈希表根据你的 `path` C 变量指定的目录创建。

对于搜索路径或哈希表中的每个目录，shell 都会调用 `exec` 系统函数来搜索要执行的命令。如果失败，搜索将继续在其他可能的位置。然而，`exec` 系统函数涉及大量的操作系统开销；其使用取决于系统加载负载会降低系统性能。因此，shell 哈希表的有效性是一个值得关注的问题。Bash 提供了三个命令来使用哈希表：`hashstat`、`rehash` 和 `unhash`。

### 确定哈希表的有效性：hashstat

你可以使用 `hashstat` 命令来确定 shell 哈希表机制的有效性。例如，

```
$ hashstat
```

`hashstat` 打印的统计信息指示定位命令平均所需的尝试次数，从而决定了每个发出的命令所执行的 `exec` 调用次数。理想情况下，每个命令都应该通过一次查找找到。如果命中率低，则对于每个执行的命令都会发生大量的目录搜索（`exec` 触发）。你需要重新排列搜索路径中的目录，并在可能的情况下，从路径中删除不包含你常用命令的目录。换句话说，哈希表性能低下是由结构不合理的路径或路径变量引起的。你频繁使用的命令应该位于路径中第一个命名的目录，后续目录的引用应该越少越少。如果你在路径中列出了不包含任何常用命令的目录，shell 将浪费时间在这些目录中搜索你需要的命令。

### 重建哈希表：rehash

你可以使用 `rehash` 命令来重建 shell 的哈希表。哈希表通过减少需要搜索以定位特定命令的目录集，来加速命令执行。例如，

```
rehash
```

当你更改 `path` 变量的值时，哈希表会自动更新，但当你更改可执行文件的名称或移出搜索路径中的目录时，无法进行自动更新。系统管理员对包含系统命令的目录所做的更改也不会被察觉。在这种情况下，使用 `rehash` 使哈希表与真实情况同步。

每当尝试执行搜索路径中存在的命令却返回“未找到”（not found）消息时，你需要执行 `rehash` 命令。

### 禁用哈希表的使用：unhash

你可以使用 `unhash` 命令停止 shell 使用哈希表来加速命令的目录搜索。shell 将继续按照通常的方式使用 `path` 变量搜索目录，但效率会降低。使用 `rehash` 命令恢复对哈希表的使用。例如，

```
unhash
```

当你正在开发一个新的 shell 时；当你重构 `path` 变量列出的目录内容时；或者当你的路径中有 NFS 挂载且 NFS 服务器离线时，你可能想要使用 `unhash` 命令。

## 管理资源限制：limit 和 unlimited

UNIX 对任何用户可以投入的资源数量实施了若干限制。对于每种类型的资源，都有系统定义的最大值。系统管理员可以使用 `limit` 命令增加或减少限制的大小，或者使用 `limit` 将限制恢复到正常值。普通用户也使用 `limit` 和 `unlimited` 命令，但仅用于限制资源使用——而不是增加它。

你可以通过 `limit` 和 `unlimited` 命令控制的特定资源类型下所示。

除非你是管理员，否则更改资源限制仅影响当前进程。它不会影响你同时作为后台作业运行的任何命令，也不会影响任何其他用户。

管理资源限制并不是你不常做的事情。管理好参与确定决定的程序员和系统管理员至关重要。你应该意识到存在的限制以及它们的值，因为资源限制可能会导致命令由于虚假或误导性的原因而执行失败。例如，其中一个资源限制对磁盘文件的大小设置了上限。如果一个命令执行以写入一个大于文件大小限制的文件，该命令可能会失败并报告空间不足。这可能会导致你要求系统管理员给你磁盘空间。然而，获得更多的磁盘空间并不能解决问题，因为文件大小限制不会在空间可用时允许你的命令使用该空间。正确的解决方法是要求系统管理员更改系统内置的文件大小限制，或者停止写入此类大文件。

### 显示或设置最大资源限制：limit

你可以使用 `limit` 命令来显示或更改适用于当前 shell 调用以及你从该 shell 启动的所有命令和作业的最大系统限制。例如，

```
limit [ resource { maximum ] ]
```

UNIX 提供了一个 `limit` 命令，你可以用它来更改使用任何命令可以写入的最大文件大小。`limit` 内置 shell 命令也可用于相同目的，还可以更改多个限制。

如果你不提供任何参数，`limit` 命令将列出当前生效的所有可设置限制。

对于 `resource`，请指定表 12.16 显示的选项之一。（注意：你可以指定的资源类型取决于你所使用的 `csh` 和 UNIX 的特定实现。）

### 表 12.16. 资源选项。

| 选项 | 说明 |

| --- | --- |

| coresumsize | 可以写入的转储文件（coredump）的最大 own。系统可以减少该限制或将其增加到系统定义的限制。 |

| cputime | 任何进程可以运行的 CPU 秒数上限。超过此限制的进程将被终止。 |

| datasize | 分配给程序数据和栈区域的最大内存量。系统为程序可以使用的内存定义了一个上限。你可以减少该限制，或者如果你之前减少了它，可以将其增加回系统定义值。 |

| filesize | 文件可以包含的最大字节数。尝试创建新文件或追加一个超过此大小的文件会导致操作系统向程序发送内存耗尽信号。 |

| stacksize | 系统应允许程序栈区域的最大内存量。系统定义了任何程序可以增长的最大尺寸。你可以减少该限制，或者如果你之前减少了它，可以将其增加回系统定义值。 |

如果你指定了 `resource` 但省略了 `maximum`，`limit` 命令将显示指定资源的当前限制值。对于 `cputime` 为秒，对于任何其他资源为千字节（例如 `limit 32` 将最大文件大小设置为 32KB 或 32768 字节）。你可以在数字后附加 `m` 以指定兆字节而不是千字节：`datasize 2m` 将最大数据区域设置为 2097152 字节（2048KB）。

### 取消之前的 limit 命令：unlimit

你可以使用 `unlimit` 来消除之前的限制产生的影响。例如，

```
unlimit [ resource ]
```

由于 `limit` 命令只能用于进一步限制系统限制（超级用户外），`unlimit` 命令将指定的限制（或所有限制）恢复为系统定义的上限。

参见“显示或设置最大资源限制：limit”关于 `resource` 允许值的描述。

## 总结

与 Bourne shell 相比，C shell 提供了键盘环境和 shell 编程环境的扩展。除了文件名通配符、命令历史、历史替换和作业控制外，C shell 还提供了数组变量、算术表达式、方便的 `if` 语句以及 `while` 和 `foreach` 的简化形式（去掉了 Bourne shell 中无用的 `do`）。

C shell 的大部分功能也由 Korn shell 支持，且形式与 Bourne shell 的语法和用法更为一致。由于其对键盘用户和 shell 编写者的扩展，C shell 值得你研究；你可能会发现你喜欢它。

本章提供了 C shell 语法和特性的快速概述。然而，你可以在你特定版本的 UNIX 的参考手册中找到更详细的阐述；你应该查阅这些手册以获取运行的最后细节。C shell 源自 BSD，从未像 System V 的 UNIX 家族那样经历过相同程度的标准化。

## 哪种 Shell 最适合你？Shell 比较

作者：John Valley 和 Sean Drew

大多数现代 UNIX 版本都提供三种标准配置：Bourne shell 和/或 POSIX shell、C shell 以及 Korn shell。然而，还有许多其他可用的 Shell，包括但不限于：Z shell、TC shell、RC shell 和 Bourne Again。选择一个合适的 Shell 是一项重要的决定，因为你将花费大量精力和精力学习一种 Shell，而在实际使用它上花费的时间更多。本章旨在通过引起你对每个 Shell 特性的关注，来帮助你选择 Shell。

当然，没有哪种 Shell 是适用于所有用途的。如果你有 Shell 可供选择，你需要学习如何为特定任务选择合适的 Shell。

Shell 主要有三个用途：

1. 作为操作系统的键盘接口
2. 作为编写个人使用脚本的载体
3. 作为为他人开发新命令的编程语言

这三个方面中的每一个都对你以及你选择的 Shell 提出了要求。此外，每个 Shell 对这三个用途提供的支持程度也不同。本章描述了某些常用 Shell 在你通过 Shell 执行的三类任务方面的优缺点。

### 交互式用法

在选择用于交互的 Shell 时，需要记住的第一点是，你的决定只影响你个人。这这给了你极大的自由：你可以选择任何 Shell，而无需考虑别人的需求和意愿。只有你自己的需求和偏好才是。

影响你选择交互式 Shell 的主要因素如下：

- **以往经验。** 在选择 Shell 时，以往经验既可能是加分项也可能是减分项。例如，在使用 Bourne shell 变体（如 Korn shell）时，熟悉 Bourne shell 是一个优势；但在使用 C shell 或其变体时，这又成了一个劣势。不要依赖经验来探索陌生 Shell 的用处。Shell 基本上有两种主要的风格：Bourne 和 Z。Bourne 家族的主要成员有 Bourne、Bourne、POSIX、Korn 和 Z。C 家族的主要成员有 C 和 TC。像 C 和 Bourne 这样的 Shell 内置了不同程度的 C 语法支持。
- **Bourne。** 生活中一个令人遗憾的事实是，工具越强大、灵活性越高，学习如何使用它就越发困难。多功能的 VCR 随着便利功能的激增，每种功能都有其独特的无声见证。UNIX Shell 也是如此：从 Bourne shell 到 C shell，再到 Korn shell 以及其他 Shell，复杂度不断递增，每个 Shell 都在前一个 Shell的基础上增加了功能和快捷键。成为这些功能精手的代价是花费额外的时间进行学习。你必须判断自己是否真的会足够使用那些额外功能以至于值得投入时间。请记住，所有 Shell 都非常相似，且在最基础的水平上很容易学习。Bourne 家族拥有的编程语言比 C shell 丰富得多（尽管过时）。虽然 C shell 的编程接口更容易学习，但对于掌握最简单脚本的任务来说，它可能是很大的阻碍。
- **命令编辑。** 所有的 Shell 都提供了重新显示和重用以前命令的功能，Bourne shell 是一个显著的例外。你通过命令编辑节省的额外时间很大程度上取决于你使用 Shell 的频率。几代 UNIX 用户在 C shell 和 Korn shell 发明之前就已经生活和工作，这证明 Bourne shell 是完全可用的，只是缺乏经验丰富的用户使用的某种形式的命令重用便利性。
- **通配符和快捷键。** 再次，这种为你提供快速处理常见事务方式的 Shell 将增强你的个人生产力（以及一般的心理平静）。如果你一天中要输入 UNIX 命令，通配符、命令别名和自动补全可以节省大量时间。
- **可移植性。** 如果你每天都坐在同一个终端，使用相同的 UNIX 软件和应用程序完成所有工作，并且极少需要选择你系统可用的最佳工具。如果你需要在运行不同版本 UNIX 的许多不同的计算机之间进行工作（正如系统和网络管理员经常必须的那样），你可能需要建立一套工具集（Shell、编辑器等），这些工具在你使用的大多数或所有系统上都是可用的。不要忘记，如果一个强大的 Shell 不可用，那么精通它对你来说无济于事。对于 UNIX 专业人士来说，了解一种在所有 UNIX 系统上都支持的 Shell 比任何其他考虑都更重要。

### Bourne Shell

我将 Bourne 评为学习的最佳选择，因为它最简单。Bourne shell 是所有 Shell 中最老的，而且随处可用。如果你对 Bourne shell 进行了一些交互式增强，结果就是 POSIX（可移植操作系统接口）shell。POSIX shell 在提供的交互功能方面与 Korn shell 非常相似，在大多数情况下甚至到按键都是如此。Korn shell 没有标准化，因此不同厂商的版本之间存在令人恼的差异；POSIX shell 试图提高通用可用 Shell 的标杆。

目前的 POSIX shell 基于 IEEE Bourne Shell 和工具规范的 POSIX 2（IEEE 工作组 103.2）。POSIX shell 是 Bourne shell 的超集。

我将 POSIX 的学习评为 2，因为它比 Bourne shell 拥有更多的交互功能，但少于 Bourne Again 或 Z shell。POSIX shell 在命令编辑领域评为 1，提供了 vi 和 emacs 命令支持。POSIX shell 支持的命令行编辑功能集没有 TC、Bour Again 那么丰富，但对于大多数任务已经足够。

POSIX shell 提供了许多快捷键，如别名、cd 路径搜索、文件名补全和作业控制。快捷键评分为 2，是因为 POSIX shell 比 Bourne shell 多，但比 TC、Bour Again 和 Z shell 少。POSIX shell 在移植性方面获得高分，因为它应该在大多数常见的 UNIX 版本上都可用。

Bourne shell 由你的 UNIX 厂商提供，尽管它正在被 POSIX shell 取代。例如，在 HP-UX 10.X 系统上，Bourne shell 现在位于 `/usr/old/bin`，而 POSIX shell 现在位于传统的 `/usr/bin`。

POSIX shell 在体验类别中被评为 2 分，如果你熟悉 POSIX shell 并且对它的功能集满意，那么就没有太大的动力去切换到其他 shell。Bourne Again 和 Z 提供了更多功能，并支持大多数 POSIX 特性；如果默认可用性不是问题，且你不需要额外的功能，那么切换将是一项相当轻松的任务。

POSIX shell 应该由你的 UNIX 供应商作为默认 shell 的一部分提供。

### C Shell (C Shell)

C shell 在学习性上评分为 2 分，这仅仅是基于可学习材料的总量。在功能的数量和复杂性方面，C shell 处于 shell 谱的低端。不要误会——C shell 使用起来可能很棘手，而且它的某些功能文档记录非常糟糕。要熟练并精通 C shell 需要时间、练习以及某种程度的创造性实验。仅从功能角度与 Bourne shell 相比，C shell 并不更复杂，只是有所不同。

C shell 在命令编辑方面的评分只能算是勉强及格，因为它并没有真正的命令编辑功能。C shell 的历史替换机制有些复杂，有时可以学会变得易用，但它比完全没有好得多。仅仅拥有命令和历史替换机制就是对 Bourne shell 的改进。与 Korn、Bourne Again、TC 或 Z shell 简单易用（如果你熟悉 vi）的命令编辑相比，C shell 是一个很差的。
