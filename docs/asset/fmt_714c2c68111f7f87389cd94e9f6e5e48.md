
# nis+, NIS+, nis — 网络信息命名服务的新版本（New Version of the Network Information Name Service）

## 描述

NIS+ 是网络信息命名服务的新版本。该版本与版本 2（在早期版本中称为 NIS 或 YP）有几个显著不同之处。增强的具体领域包括扩展到更大网络的能力、安全性以及服务的管理。

NIS+ 的手册页分为三个基本类别。第 1 手册页描述了经常从 shell 脚本或直接从命令行执行的用户命令。第 1M 手册页描述了网络管理员用于管理服务本身的命令。第 3N 手册页描述了 NIS+ 编程 API。

所有使用 NIS 版本 2 的命令和函数都带有 yp 前 yp，例如 `ypmatch(1)`、`ypcat(1)`、`yp_match(3N)` 和 `yp_first(3N)`。使用新软件 NIS+ 的命令和函数带有字母 nis 前缀，例如 `nismatch(1)`、`nischown(1)`、`nis_list(3N)` 和 `nis_add_entry(3N)`。请参阅第 893 页的“命令列表”以获取 NIS+ 命令的完整列表。

本手册页介绍了 NIS+ 术语。它还描述了 NIS+ 命名空间、身份验证策略和授权策略。

## NIS+ 命名空间

NIS+ 的命名模型基于树形结构。树中的每个节点对应于一个 NIS+ 对象。NIS+ 有六种对象：

- 目录 `Directory`
- 表 `Table`
- 组 `Group`
- 链接 `Link`
- 条目 `Entry`
- 私有 `Private`

### NIS+ 目录对象

每个 NIS+ 命名空间至少包含一个 NIS+ 目录对象。NIS+ 目录类似于 UNIX 文件系统，包含其他 NIS+ 对象，包括 NIS+ 目录。构成 NIS 命名空间根的 NIS+ 目录称为根目录。NIS+ 有两个特殊的目录：

- `org_dir` 包含所有系统级管理表，如 `passwd`、`hosts` 和 `mail_aliases`
- `groups_dir` 持有用于访问控制的 NIS+ 组对象。

`org_dir`、`groups_dir` 及其父目录的集合称为 NIS+ 域（domain）。你可以将 NIS+ 目录排列成树形结构，以便 NIS+ 命名空间匹配组织或管理层级。

### NIS+ 表对象

NIS+ 目录中的 NIS+ 表（而非文件）存储某些特定类型的实际信息。例如，`hosts` 表存储了域内主机 IP 地址的信息。NIS+ 表是多列的，你可以通过任何可搜索列对表进行搜索。每个表对象定义了表的模式（schema）。NIS+ 表由 NIS+ 条目对象组成。对于 NIS+ 表中的每个条目，都有一个符合 NIS+ 表对象所定义模式的 NIS+ 条目对象。

### NIS+ 组对象

NIS+ 对象用于组粒度的访问控制。包含在域的 `groups_dir` 目录中的 NIS+ 对象包含特定 NIS+ 组内所有 NIS+ 主体（principals）的列表。NIS+ 主体是发出 NIS 请求的用户或机器。

### NIS+ 链接对象

NIS+ 链接对象类似于 UNIX 符号文件系统链接。它们通常用于 NIS 命名空间的快捷方式。

有关 NIS+ 对象的更多信息，请参阅 `nis_objects(3N)`。

### NIS+ 名称

NIS+ 服务定义了两种形式的名称。

- 简单名称（Simple names）识别 NIS 命名空间内的 NIS+ 对象
- 索引名称（Indexed names）识别 NIS+ 表内的 NIS+ 条目

此外，NIS+ 表内的条目以 entry 类型 NIS 对象的格式返回给调用者。NIS+ 对象以 entry 类型 NIS 对象的格式实现。

## 语法

以下名称代表了定义合法的 NIS+ 名称集的上下文无关文法（context-free grammar）。该文法中的终结符是点（`.`）、左括号（`[`）、右括号（`]`）、逗号（`,`）、等号（`=`）和空格。竖线（`|`）字符用于分隔备选产生式。将此语法读为“此产生式或该产生式”。

```
name ::= simple-name indexed-name
simple-name ::= string.string.simple-name
indexed-name ::= search-criterion, simple-name
search-criterion ::= [attribute-list]
attribute-list ::= attribute | attribute, attribute-list
attribute ::= string
string ::= string
```

出现在字符串中的终结符用双引号（`"`）括起来。可以通过对引号本身进行引用（`""`）来引用 `"` 字符。

## 名称扩展

NIS 服务仅接受完全限定名称。然而，由于此类名称可能非常冗长，第 1 节中的 NIS+ 组合使用一组扩展规则，尝试对部分限定名称进行限定。这种扩展实际上是由 NIS+ 函数 `nis_getnames(N)` 完成的，它通过默认的 NIS+ 目录搜索路径或 `NIS_PATH` 环境变量生成名称列表。默认 NIS+ 目录搜索路径包含其路径中的所有名称。`nis_getnames()` 由函数 `nis_lookup(N)` 和 `nis_list(N)` 调用。

`NIS_PATH` 环境变量包含有序名称列表。名称之间用冒号（`:`）分隔。如果列表中的任何名称包含逗号，则应按照“语法”节中的描述对冒号进行引用。当列表耗尽时，解析函数返回错误 `NIS_NOTFOUND`。此错误可能会掩盖名称存在但其服务器无法访问的事实。如果提供列表或查找接口的名称是完全限定的，则忽略 `EXPAND_NAME` 标志。在 `NIS_PATH` 环境变量的名称列表中，美元符号（`$`）被特殊处理。简单名称中的 `$` 具有该字符会被替换为默认目录（参见 `nis_local_directory(N)`）。在此列表中使用 `$` 作为名称，会导致该名称被替换为默认目录和全局根之间包含至少两个标签的目录列表。

以下是此扩展的示例。假设默认目录为 `some.long.domain.name`，且 `NIS_PATH` 变量设置为 `fred.bar.:org_dir.:$$`，路径最初被拆分为以下列表：

- 1 `fred.bar.`
- 2 `org_dir.$`
- 3 `$`

第二个部分中的美元符号被替换为默认目录。第三部分的美元符号被替换为默认目录和全局根之间包含至少两个标签的目录名称。有效路径值变为：

- 1 `fred.bar.`
- 2 `org_dir.some.long.domain.name.`
- 3 `some.long.domain.name.`
- 4 `bld.domain.name.`
- 5 `dc.domain.name.`

这些简单名称中的每一个都被附加到传递给 `nis_lookup(N)` 或 `nis_list(N)` 接口的部分限定名称。依次尝试每个，直到返回 `NIS_SUCCESS` 或列表耗尽。
如果未设置 `NIS_PATH` 变量，则使用该路径。
可以从用户程序调用库函数 `nis_getnames(N)` 来生成将尝试的名称列表。带有 `-s` 选项的 `nisdefaults(1)` 也可以显示完全扩展后的路径。

## 拼接路径

通常，特定类型信息的所有条目都存储在表本身。然而，有时希望表指向可能存储条目的其他表。例如，你可能希望在主机表中存储其所属域的所有 IP 地址，并希望能够在不显显式指定域名名的情况下解析某些其他域中的主机。NIS+ 提供了一种机制，通过 NIS+ 拼接路径将不同的相关表连接起来。通过拼接路径，你可以从层次结构结构中创建一种类似于扁平的命名空间。你还可以创建一个没有条目的表，仅将主机或任何其他表指向其父域。请注意，在这样的设置下，你将管理表的行政负担转移到了父域。
拼接路径会减慢响应时间，因为需要搜索更多的表和服务器。如果表路径中的某个目录服务器出现故障，也会降低表的可用性。

NIS+ 拼接路径也被称为表路径（table path）。该路径在创建表时通过 `nistblad(1)` 设置。你可以指定多个要拼接的表，并按顺序搜索这些表。请注意，NIS+ 客户端库默认不会遵循在特定特定表中设置的拼接路径。更多细节请参见 `nis_list(N)`。

## 命名空间

NIS+ 服务定义了两个额外的不相交命名空间供自身使用。这些命名空间是：

- NIS+ 主体命名空间。
- NIS+ 组命名空间。

与组和主体命名空间关联名称在语法上与简单名称相同。然而，它们代表的信息无法通过直接将这些名称提交给 NIS+ 接口来。相反，定义了特殊接口将这些名称映射为 NIS+ 名称，以便对其进行解析。

### 主体名称

NIS+ 主体名称用于唯一标识发起 NIS+ 请求的用户和机器。这些名称具有以下格式：
`principal_domain`

此处，`domain` 是可以找到主体的完全限定名称。更多信息请参见第 89 页的“目录与域”。

用户程序可以使用带有 `-p` 选项的 `nisdefaults(1)` 来返回此信息。

从 UID 到 NIS+ 名称的映射通过以下方式完成。NIS+ 主体名称通过 `nisadd(1)` 管理。表包含 `cname`、`auth_type`、`public_data` 和 `private_data`。

NIS+ 服务使用数据加密标准（DES）将与安全 RPC 请求相关的名称映射为 NIS+ 主体名称。使用安全 RPC 的请求包含请求头中的客户端名称。此名称名称具有以下格式：
`unix.UID@domain`

服务通过以下格式构造查询，其中域是提取的，而不是使用默认域。

`[auth_type=DES, auth_name=netname],cred_org_dir.domain`

此查询用于在创建创建的域中将此名称映射为 NIS+ 主体名称。映射 UID 和名称的机制确保 NIS+ 服务只有一个主体名称。该主体名称用于下文所述的授权基础。NIS+ 命名空间中的所有对象和 NIS+ 表中的所有条目必须指定所有者。此所有字段始终包含 NIS+ 主体名称。

## DES

NIS+ 服务使用数据加密标准（DES）将与安全 RPC 请求相关的名称映射为 NIS+ 主体名称。使用安全 RPC 的请求包含请求头中的客户端名称。此名称具有以下格式：
`unix.UID@domain`

服务通过以下格式构造查询，其中域是提取的，而不是使用默认域。

`[auth_type=DES, auth_name=netname],cred_org_dir.domain`

此查询用于在创建创建的域中将此名称映射为 NIS+ 主体名称。映射 UID 和名称的机制确保 NIS+ 服务只有一个主体名称。该主体名称用于下文所述的授权基础。NIS+ 命名空间中的所有对象和 NIS+ 表中的所有条目必须指定所有者。此所有字段始终包含 NIS+ 主体名称。

## DHnnnn-m

映射扩展 Diffie-Hellman 密钥的名称和 NIS+ 主体名称，例如 `DH640-0`、`DH1024-0`。更多信息请参见 `nisauthconf(1)`。

NIS+ 客户端库函数 `nis_local_principal` 使用 `cred_org_dir` 表将身份、进程映射为 NIS+ 主体名称。用户程序可以使用带有 `-p` 选项的 `nisdefaults(1)` 程序返回此信息。

从 UID 到 NIS+ 主体名称的映射通过以下方式完成。

`[auth_type=LOCAL, auth_name=uid],cred_org_dir.defaultdomain`

此查询返回机器默认域中与 UID 相关的 NIS+ 主体名称。

### 组名称

与 NIS+ 主体名称一样，NIS+ 组名称采用以下格式

`group_name.domain`

NIS+ 命名空间中的所有对象和 NIS+ 表中的所有条目都可以指定组所有者。此组所有者字段在填充时始终包含完全限定的 NIS+ 组名称。

## NIS+ 安全

NIS+ 定义了一个安全模型来控制对服务管理的信息的访问。该服务定义了选择性授予单个客户端或客户端组的访问权限。主体名称和组名定义了可能被授予或拒绝访问 NIS+ 信息的客户端和客户端组。这些主体和组按照定义与 NIS+ 领域关联。

安全模型还使用了主体类 `nobody` 的概念，它包含了所有客户端，无论它们是否已对服务进行了验证。该类包含任何已验证的客户端。

## 目录与领域

NIS+ 命名空间内的某些目录被称为 NIS+ 领域。领域是指包含 `groups_dir` 和 `org_dir` 子目录的那些 NIS+ 目录。此外，子目录 `org_dir` 应该包含名为 `cred` 的表。NIS+ 组名和 NIS+ 主体名称始终在第一个标签之后包含 NIS+ 领域名。

## 认证

NIS+ 名称服务使用 Secure RPC 来确保 NIS+ 服务的完整性。Secure RPC 要求服务的用户及其机器必须拥有与其关联的 Secure RPC 密钥对。该密钥最初通过 `addscred(1M)` 或 `nisclient(1M)` 命令生成，并通过 `chkey(1)` 或 `nispasswd(1)` 命令进行修改。

Secure RPC 的使用使得网络上不可信机器或用户无法获取的私有信息可以存储在名称服务中。

除了 Secure RPC 密钥外，用户还需要其 UID 映射到 NIS+ 主体名称的映射。该映射由系统管理员使用 `nisclient(1M)` 或 `nisaddcred(1M)` 命令创建。

在多个 NIS+ 领域中使用机器的用户必须确保他们在这些领域中的每一个都有本地凭据。该凭据应使用用户在其“主”领域中的 NIS+ 主体名称进行创建。对于 NIS+ 和 Secure RPC 而言，主领域定义为用户 Secure RPC 密钥对所在的领域。

尽管扩展 Diffie-Hellman 密钥使用了 Secure RPC 的替代方案，但管理仍通过相同的命令完成。参见 `nisauthconf(1M)`。

## 授权

NIS+ 服务定义了四种可以授予或拒绝服务客户端的访问权限。这些权限是：

- 读取 `Read`
- 修改 `Modify`
- 创建 `Create`
- 销毁 `Destroy`

这些访问权限在创建时在对象结构中指定，之后可以使用 `nismod(1)` 命令进行修改。通常情况下，授予对象的权限仅适用于该对象。然而，出于授权目的，授予读取目录对象和表对象的客户端的权限，将授予访问父对象所“包含”的所有对象的客户端。这种包含概念是抽象的。对象内部实际上并不包含其他对象。请注意，组对象在其定义中包含了主体列表。

访问权限的解释如下：

- **read 读取**：授予对对象的访问权限。对于目录和表对象，拥有父对象的读取权限意味着对目录的所有直接子对象或表内的条目的访问权限。
- **modify 修改**：授予对现有对象的修改访问权限。修改不需要读取权限。但在许多应用程序中，用户在修改对象之前需要读取它。如果未授予读取权限，此类操作将失败。
- **create 创建**：授予客户端在之前不存在的地方创建新对象的权限。`create` 仅用于目录和表对象。拥有表的创建权限允许客户端向表中添加额外条目。拥有目录的创建权限允许客户端向 NIS+ 目录添加新对象。
- **destroy 销毁**：授予客户端销毁或移除现有对象或条目的权限。当客户端尝试通过移除某个条目或对象时，服务首先检查包含该对象的表或目录是否授予了客户端访问。如果是，则继续操作；如果包含对象未授予此权限，则将检查对象本身是否授予了客户端此权限。如果对象授予了权限，则继续操作；否则，请求被拒绝。

这些权限中的每一个都可以授予四个不同类别之一：

- **owner 所有者**：授予对象所有者权限。所有者是所有者字段标识的 NIS+ 主体。可以通过 `nisowner(1)` 命令更改所有者。注意，如果所有者没有该对象的修改权限，除非他拥有父对象的修改权限，否则他无法更改对象的任何访问权限。
- **group 组**：授予对象的组所有者。这授予了任何被识别为与对象关联组成员的主体。组所有者可以通过 `nischgrp(1)` 命令更改。对象所有者不必是组的成员。
- **world 世界**：授予世界上每个人权限。这授予了所有客户端。
- **nobody 无身份**：授予 nobody 权限。这授予了任何未经过验证的客户端。
