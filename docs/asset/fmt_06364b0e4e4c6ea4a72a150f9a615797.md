
当你最终到达这里时，你的问题可能已经解决，但你将获得大量的特征信息。在组组中搜索类似问题。邮件给开发者看看他们是如何解决的。尝试解决方案并观察系统是否发生了变化。

## 9.10. 章节总结

本文提供了一种结合使用 Linux 工具追踪不同类型问题的方法。虽然无法捕捉可能出现的问题类型，但这种方法可以帮助你发现一些常见问题。此外，如果你面临的问题未被涵盖，你收集的数据仍然有用。

接下来的章节将展示如何使用该方法发现性能问题。

- 使用本章作为追踪 CPU 相关问题的模板。

## 10.1. 密集型应用程序

在本章中，我们调查了一个密集型应用程序。优化密集型应用程序是非常重要的，因为它是最常见的问题之一。它通常是经过调优应用程序的最后边界。当磁盘和网络瓶颈被消除后，应用程序就会变得密集。此外，购买更快的磁盘或更多内存通常比升级 CPU 更容易，因此如果一个进程是密集型的，追踪并修复 CPU 性能问题是一项重要的技能，而不是直接买新系统。

## 10.2. 识别问题

性能猎寻的第一步是识别要调查的问题。在本例中，我选择调查在使用 `GIMP`（一个开源图像处理程序）时出现的一个性能问题。`GIMP` 可以切割和处理图像的各个方面，但它还有一套强大的过滤器可以各种方式扭曲和改变图像。这些过滤器根据复杂的算法改变图像。通常，这些过滤器完成需要很长时间，并且非常消耗 CPU。其中一个过滤器是 Van Gogh (`LIC`)，它接收输入图像并对其修改，使其看起来像梵高风格的绘画。这个过滤器完成所需的时间特别长。完成时间取决于图像的大小、机器 CPU 的速度以及传递给过滤器的参数值。

## 10.3. 寻找基准/设定目标

任何性能调优的第一步都是确定问题的当前状态。以 `GIMP` 过滤器为例，我们需要弄清楚运行特定图像需要多少时间。这就是我们的基准时间。一旦有了这个基准，我们就可以尝试进行优化并看看它是否能缩短执行时间。有时，测量某个操作耗时是比较困难的。这不像使用秒表那么简单，因为在我们的进程 CPU 密集型任务运行时，操作系统正在调度其他任务。除了 CPU 密集型任务外还有其他任务在运行，挂钟时间（wall-clock time）可能会大于进程实际使用的 CPU 时间。在这种情况下，我们很幸运；通过在过滤器运行时查看 `top` 命令，我们可以看到 `lic` 进程占用了大部分 CPU 使用率，如列表 10.1 所示。

### Listing 10.1.

```
[ezolt@localhost ktracer]$ top
```

```
top - 08:24:48 up 7 days, 9:08, 6 users, load average: 1.04, 0.64, 0.76

PID USER PR NI VIRT RES SHR S %CPU %MEM TIME+
32744 ezolt 25 0 53696 45m 11m R 89.6 14.6 01:16 lic
2067 root 15 0 06952 21m 17m S 6.0 6.8 01:56:22 X
32738 ezolt 15 0 35292 27m 14m S 2.3 8.7 00:05:08
gimp
```

从这里，我们可以推断出 `GIMP` 实际上启动了一个单独进程来运行过滤器。当过滤器运行时，我们可以使用 `ps` 来跟踪进程使用了多少 CPU 时间以及它何时完成。当我们通过 `top` 获取了过滤器的 PID 后，可以参考列表 10.2 并让 `ps` 定期观察过滤器正在使用多少 CPU 时间。

### Listing 10.2.

```
while true; do sleep 1; ps 32744; done

PID TTY STAT TIME COMMAND
32744 pts/0 R 2:46
/usr/local/lib/gimp/2.0/plugin-ins/lic -gimp 8 6 -run 0
```

### Note

如果你需要为一个应用计时但手头秒表，可以使用 `time` 和 `cat` 作为简单的秒表。只需在想要开始时输入 `time cat`，并在完成后按 `<Ctrl-D>` 即可。`time` 会显示已经过了多少时间。

在参考图像（一张从 `gimp` 抓取的图片）上运行 `lic` 并使用 `ps` 方法仅为过滤器计时时，我们可以从列表 10.2 看到开箱即运行需要 2 分钟 46 秒，因此我们可以知道过滤器开箱即运行所需的时间，并将其用于性能调优。为性能调查设定一个合理的目标并不总是容易的。一个合理的目标值可能取决于几个因素，例如对……已进行的调优量等。

## 10.4. 为性能调优配置应用程序

我们调查的下一步是通过带符号（symbols）的方式重新编译应用程序，为性能调优做好准备。符号允许性能工具（如 `oprofile`）调查哪些函数和源代码行导致了所花费的 CPU 时间。

对于 `GIMP`，我们从其网站下载 `GIMP` tar 包，然后对其进行重新编译。在 `GIMP` 和许多开源软件的情况下，重新编译的第一步是运行 `configure` 命令，它生成用于构建的 `makefile`。`configure` 命令会将任何 `CFLAGS` 环境变量传递给 `makefile`。在这种情况下，由于我们希望构建带符号的 `GIMP`，我们在 `makefile` 中将 `CFLAGS` 变量设置为 `-g`。此命令在列表 10.3 所示。

### Listing 10.3.

```
[root@localhost gimp-2.0] env CFLAGS=-g ./configure
```

然后我们运行 `make install` 安装带符号的 `GIMP` 版本，当我们运行这个版本时，性能工具将告诉我们时间花费在哪里。

## 10.5. 安装和配置性能工具

如果尚未安装性能工具，下一步就是安装它们。虽然这看起来可能是一件易事，但通常涉及到从发行版包中从头编译工具。在这种情况下，我们将使用 Fedora Core 2 模块，因为 Fedora Core 包含了对称多处理（SMP）内核，我们需要跟踪哪些库函数被调用以及调用的频率。

## 10.6. 运行应用程序和性能工具

接下来我们运行应用程序并使用性能工具进行测量。因为 `lic` 过滤器直接由 `GIMP` 调用，我们必须使用工具来捕获正在运行的进程。在 `profile` 的情况下，我们可以启动 `profile`，运行过滤器，然后在过滤器完成后停止 `profile`。`lic` 在运行时占了 90% 的 CPU，系统范围收集将与 `lic` 相关。当 `lic` 开始时，我们在另一个窗口启动 `profile`；当 `lic` 完成时，我们停止。`profile` 的启动和停止在列表 10.4 所示。

### Listing 10.4.

```
[root@localhost ezolt]# profile --start
[root@localhost ezolt]# profile --dump
[root@localhost ezolt]# profile --stop
```

`ltrace` 必须以不同的方式运行。过滤器启动后，`ltrace` 可以附加到运行进程上。与将 `ltrace` 附加到进程导致进程爬行不同，它可以准确地增加每个库调用所需的时间；然而，它提供了关于调用次数的信息。列表 10.5 显示了来自 `ltrace` 的列表。
