
| `/usr/reports` -rw=bass:soprano | 此条目授予来自 `bass` 和 `soprano` 的用户对 `/usr/reports` 目录的读写权限。注意，只要指定了主机，权限仅适用于它们。来自其他主机的用户被授予只读权限。在上面的示例中，除了 `bass` 和 `soprano` 之外的所有主机对 `/usr/reports` 目录具有只读访问权限。 |

| `ro` | 指定对导出目录的只读权限。用户尝试向目录写入将导致“Permission denied”（拒绝访问）或“Read-only filesystem”（只读文件系统）等错误消息。 |

| `access=hostname[:hostname]...` | 指定允许挂载导出目录的主机。如果影响导出目录的条目未包含此选项，则网络上所有可以挂载该目录的主机（即目录最终被导出到每个主机）。 |

| `root=hostname[:hostname]...` | 授予来自指定 `hostname` 的 `root` 用户 `root` 访问权限。即：如果没有指定 `hostname`，则拒绝（默认）来自所有主机的 `root` 用户的 `root` 权限。 |

# 启动和停止 NFS 服务

一旦完成文件系统自动共享和挂载的所有必要步骤，你就可以在服务器和客户端主机上启动 NFS 运行。虽然启动 NFS 服务所需的守护进程对于所有 UNIX 变体都是相同的，但启动过程本身可能有所不同。

## 在 SVR4 上启动和停止 NFS（不包括 Solaris 2.x）

使用命令行手动启动 NFS，请使用以下命令：

```
sh /etc/init.d/nfs start
```

此命令启动同一组 NFS 守护进程，无论该命令是在客户端还是服务器上调用的。根据供应商的不同，脚本会启动 4 到 8 个不同的 `nfs` 和 `bind` 守护进程。启动这些守护进程的多个实例可以提高 NFS 服务的整体性能。

`/etc/init.d/nfs` 脚本还会启动包括 `lockd`、`statd` 和 `mount` 在内的所有守护进程。所有 NFS 守护进程都会在服务器和客户端上被调用，UNIX 允许同时担任服务器和客户端角色。当系统在网络中作为客户端时，它本身也可以是某些（机器）的客户端。

如果 `/etc/init.d/nfs` 脚本在你的系统上运行失败，可能是因为系统不在级别 3。要检查系统状态，请输入以下 "`who -r`" 命令：

```
# who -r
run-level 3 Nov 12 10:40 3 0 S
```

如果系统尚未达到级别 3，输入以下 `init` 命令将系统提升到级别 3：

```
# init 3
```

要在启动时将系统提升到级别 3，你必须确保 `/etc/inittab` 文件包含以下 `initdefault` 条目：

```
is:3:initdefault:
```

在检查 `/etc/inittab` 文件时，你可能会发现以下目：

```
is:2:initdefault:
```

在这种情况下，请使用你偏好的编辑器将 `initdefault` 条目中的 `2` 替换为 `3`。这保证了系统在启动时运行在级别 3。这是在客户端和服务器上启动 NFS 服务的必要条件。

> 注意：如前所述，SVR4 允许对 `/etc/dfs/fstab` 中指定的目录进行自动共享（启动时导出）。同样，SVR4 允许根据 `/etc/vfstab` 文件中的条目对远程文件资源进行自动挂载。通过 `vfstab` 文件，系统管理员可以指定 NFS 服务器的名称、挂载目录以及影响远程资源挂载方式的一些选项。请咨询 `man` 页以获取有关要包含条目的内容和语法的详细信息。

## 在 Solaris 2.x 上启动 NFS

Solaris 2.x 依赖两个不同的脚本分别用于 NFS 服务器和客户端。启动 NFS 服务器（与导出、挂载和响应 NFS 服务请求相关的守护进程）的脚本是 `/etc/init.d/nfs.server`。

启动客户端守护进程（如 `biod`、`lockd` 和 `statd`）的脚本是 `/etc/init.d/nfs.client`。

在 Solaris 2.x 上将脚本拆分为两个可以优化资源利用率，因为只需要启动需要的组件（即服务器/和/客户端服务）。

除了将脚本拆分为两个（一个用于服务器，一个用于客户端）之外，在启动时调用 NFS 的配置和机制仍与 SVR4 下提供的描述几乎完全相同。

## 在 Linux 上启动 NFS

与 Solaris 2.x 类似，Linux 也依赖两个不同的脚本来启动 NFS 服务器和客户端组件。启动服务器的脚本是 `/etc/rc.d/init.d/nfs`，而启动客户端守护进程的脚本是 `/etc/rc.d/init.d/nfsd`。这两个脚本都非常易读易理解。

Linux 还允许在启动时自动挂载 NFS 资源。为了实现这一点，系统管理员应该编辑 `/etc/fstab` 配置文件。该类似于 SVR4 的 `/etc/vfstab` 文件，但条目内容不同。共享由每个远程资源的一个条目组成，提供 NFS 服务器的名称、该服务器导出的文件系统以及影响资源挂载方式的选项（包括挂载点）。要准确描述此内容，请参考你系统上的 `man` 页。

## 手动卸载文件系统

可选地，你可以手动中断部分服务，以便进行故障排除或在主机上重新配置 NFS。

要在客户端上选择性地卸载文件系统，你只需输入以下 `umount` 命令：

```
# umount mountpoint
```

其中 `mountpoint` 是 NFS 文件系统挂载的目录名称。因此，要卸载例如服务器 `tenor` 的 `/bfs` 目录到客户端 `jade` 的 `/rfs` 目录（见图 20.30），

```
# umount /rfs
```

要卸载所有文件系统，你可以多次执行 `umount` 完成任务，或者简单地使用 `umountall` 命令。

```
# umountall
```

然而，请小心使用 `umountall`，因为它会卸载所有文件系统。

# DNS数据库和启动文件

配置服务器涉及创建许多数据库和启动文件。从后文可以看出，文件的数量取决于组织的规模、其互联网结构以及受委托管理的主机数量。在接下来的讨论中，将介绍四种不同的文件类型。根据名称服务器的类型（主、、从或缓存），你最终可能会配置不同类型文件的组合。你也可能会配置多个相同类型的文件。

以下是每个 DNS 数据库和启动文件对应的通用名称和基本定义（深入细节将在后文中介绍）：

| `named.hosts` | 此文件定义了名称服务器具有权威性的域名，主要包含主机到 IP 地址的映射。记住，权威服务器是产生与该权威性域相关数据的服务器。换句话说，就是域名创建和更新的地方，数据从这里传播到网络或互联网上的服务器。 |

| `named.rev` | 此文件定义了名称服务器具有权威性的反向域名（reverse-in-addr domain）。它还包含 IP 地址到主机的映射记录。 |

| `named.local` | 此文件内容极少。它包含的信息足以将 `127.0.0.1` 回环地址解析为 `localhost`。 |

| `named.ca` | 此文件包含互联网根域名服务器的名称和地址。使用此文件中维护的信息，名称服务器将能够在本章早些解释的那样联系根服务器进行名称查询。 |

| `named.boot` | `named`（DNS 守护进程）在启动时查找的第一文件。使用它来确定数据库文件及其在文件系统中的位置，以及远程主机。 |

你不必固限于这些文件名。如后文所示，通过合理利用 `named.boot` 文件，你可以为它们命名对你更有意义的名称，并让 `named`（DNS 守护进程）能够识别。

域名数据以资源记录（RRs）的形式在这些文件中维护。为了让 DNS 完美运行，资源记录必须遵循 RFC 1033 定义的结构。在接下来的几个小节中，将展示一组资源记录。我们将关注建立最小名称服务（仅用于主机和 IP 地址的双向映射目的）立即所需的记录。

# DNS 资源记录 (RR)

RFC 1033 定义了多种资源记录（RR）类型。每种类型负责处理全局数据库的一个方面。例如，`A` 类型记录用于维护主机到 IP 地址的关联，而 `NS`（名称服务器）记录则用于维护域名到名称服务器的关联。

以下仅为实现上一节所述目标而所需的资源记录描述。对更多信息感兴趣的读者请参考所注的 RFC。

任何 RR 的通用语法如下：

```
[name] [ttl] class type data
```

其中，

- `name`: 是该资源记录描述的资源对象的名称。`name` 可以具体到主机名，也可以通用到域名名称。如果留空……
- `ttl`: 是生存时间值，单位为秒。为了获得更好的性能，DNS 通常会缓存它从名称服务器接收到的信息。`ttl` 定义了该条目被信任并保留在缓存中的持续时间。如果没有使用，则应用 SOA 记录中指定的默认值。
- `Class`: 定义 DNS 记录的类别。DNS 识别几类 RR，其中 `IN`（即 Internet）是与本文讨论相关的唯一类别。其他类别包括 `HS`（即服务器）和 `CH`（Chaos 信息）。
- `Type`: 定义 RR 记录的类型。最常用的类型记录是 `SOA`、`A`、`MX` 和 `PTR`。例如，A RR 记录包含主机到 IP 地址的映射并属于 `named.hosts` 文件，而 `PTR` 记录恰恰相反（即它将地址映射到相应的主机），属于 `named.rev` 文件。关于记录类型的更多将在将在后介绍。
- `Data`: 与 `name` 字段指定对象相关的实际数据。内容的性质各异。

内容的性质各异，仅需要实现上一节所述的资源记录。对更多信息感兴趣的读者请参考所注的 RFC。

```
[hostname] [ttl] IN A address
```

其中，

`hostname` 是受影响主机的名称。主机名可以相对于当前域名指定，也可以使用完全限定域名（即相对于根域名）。例如，host `cell` 可以直接输入为 `cell`（即 `cello`），在这种情况下该名称被认为是相对于当前域；或者可以输入 `cello.harmonics.com.`，在这种情况下该名称是完全限定的。完全限定域名末尾的点具有意义，且必须包含。

`ttl` 是生存时间（time-to-live）。这通常留空，意味着使用 SOA 记录中定义的默认值。

`IN` 定义类，几乎总是 Internet（互联网）类。

`A` 定义记录类型（地址记录）。

`address` 是对应于 `hostname` 的 IP 地址。

例如，以下是针对 `jade.harmonics.com.` 的 A 记录：

```
jade.harmonics.com.  IN  A  100.0.0.2
```

主机名是完全限定域名 (FQDN)。由于这个原因，它必须以点 `.` 结尾。或者，也可以写成：

```
jade  IN  A  100.0.0.2
```

由于 `jade` 属于 `harmonics.com.`，DNS 没有足够的智能通过将域名附加到 `jade` 来限定该名称（使其变为 `jade.harmonics.com..`）。关于点（dot）规则的更多细节将在后面提供。

## 名称服务器 (NS) 资源记录

名称服务器资源是使 DNS 分级结构紧密结合的胶水。NS 记录定义了服务器对哪个区域或子域具有权威性。使用指向子域的名称服务器特别有用。

如图 20.33 所示，对 `.com` 域具有权威性的服务器必须包含一条 NS 记录，用于标识对 `harmonics.com` 域具有权威性的服务器（即 `jade.harmonics.com`）。

# 图 20.33.

对 `.com` 域具有权威性的服务器必须包含一条 NS 记录，用于标识对 `harmonics.com` 域具有权威性的服务器 (`jade.harmonics.com`)。

NS 记录的语法遵循以下格式：

```
[domain] [ttl] IN NS server
```

其中

`domain` 是该服务器作为权威名称服务器的域名。

`Ttl` 生存时间。如果留空，则应用 SOA 记录中指定的默认值。

`IN` 再次，类为 IN (Internet)。

`NS` 标识 RR 记录类型为 NS（即指向名称服务器的指针）。

`server` 为 `domain` 中指定的域名提供权威名称服务的主机名称。

应用到 `harmonics.com.` 的情况，com 域服务器应该在它的 `named.hosts` 文件中包含以下 NS 记录：

```
harmonics.com. IN NS jade.harmonics.com.
```

此 NS 记录也必须包含 `jade.harmonics.com.` 的 `named.hosts` 文件中。当查询 com 服务器关于 `cello.harmonics.com` 的 IP 地址时，它会检查其数据库以确定 `jade.harmonics.com` 是应该重定向查询的服务器。在这里，com 服务器向发布查询的客户端返回 `jade` 的 IP 地址，而不是它的名称。这意味着仅包含一条描述对给定域名具有权威性的 NS 记录是不够的。NS 记录应该始终与描述域名服务器地址的 A 记录结合使用。所涉及的 com 服务器必须包含以下两个记录，以便将对 `harmonics.com.` 域的查询重定向到 `jade`：

```
harmonics.com. IN NS jade.harmonics.com.
jade IN A 100.0.0.2
```

## 别名 (CNAME) 记录

CNAME 记录定义了一个指向主机官方名称的别名。它通常属于 `named.hosts` 文件。以下是 CNAME 记录的语法：

```
aliasname [ttl] IN CNAME [host]
```

其中

- `aliasname` 定义了托管在 `host` 中的[别名]。
- `ttl` 定义了生存时间。如果留空，则应用 SOA 记录中的默认值。
- `IN` 是 IN 类。
- `CNAME` 标识记录为 CNAME 类型。
- `host` 是主机的官方名称。

以下是 CNAME 记录的示例：

```
fake.harmonics.com. IN CNAME cello.harmonics.com.
```

如果客户端对主机 `fake` 发起查询，名称服务器在搜索查询信息期间，会使用上述 CNAME 记录将 `fake` 替换为 `cello`。

当需要更改主机名时，CNAME 记录特别有用。在这种情况下，你所做的是更改官方名称，并将旧名称保留为新官方名称的别名。允许一段宽限期，直到用户习惯新名称并且受更改影响的应用已重新配置。

## 指针 (PTR) 记录

PTR 用于将 IP 地址映射到名称。为了将 IP 地址反向解析为主机，互联网在其 DNS 中使用了 `in-addr.arpa` 顶级域名。在此之下，创建一个子网，每个子网在自己的名称后都有一个域名。例如，网络 `198.53.237.0` 拥有 `237.53.198.in-addr.arpa` 用于反向查找（请参考本章节前面的“服务名称”部分以理解反向名称转换）。通常，当像 harmonics（虚构的名称）这样的组织委托其 `harmonics.com` 域的权威性时，NIC 会委托属于该组织网络 ID 对应的反向域的权威性。在 Harmonics 中，反向域名是 `100.in-addr.arpa`。

PTR 记录维护在 `named.rev` 文件中，用于反向映射 IP 地址到主机。以下是 PTR 记录的语法：

```
name [ttl] IN PTR host
```

其中

`name` 指定主机的反向域名。主机的反向域名具有以下格式：

```
reverse_IP_address.in-addr.arpa
```

由于 `cello` 的 IP 地址是 `198.53.237.2`，它的 `reverse_IP_address` 变为 `237.53.198.in-addr.arpa`。

- `[ttl]` 指定生存时间。如果留空，假设使用 SOA 记录中指定的默认值。
- `IN` 类。
- `PTR` 标识记录为 PTR。
- 指向 `host`，将其 IP 地址解析为名称的 PTR 记录应如下：

```
237.53.198.in-addr.arpa IN PTR cello
```

## 邮件交换器 (MX) 记录
