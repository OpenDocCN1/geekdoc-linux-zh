## 软件工程

软件工程的定义与背景。

[R.L.G.]

软件系统的制造过程。软件系统由可执行的计算机代码以及制造、使用和维持这些代码所需的支持文档组成。例如，字处理系统由可执行程序（字处理器）、用户手册以及生成可执行程序和手册所需的文档（如需求和设计）组成。参见 `软件`。

随着更大、更复杂且关乎生命安全的软件系统的普及，软件工程变得越来越重要。计算机硬件成本的快速下降意味着典型系统中的软件成本通常高于其运行的硬件。大型软件系统可能是有史以来构建的最复杂事物。这对软件工程过程提出了巨大要求，该过程必须是严格和受控的。

为了应对这一挑战，软件工程师采用了其他工程领域的许多技术，同时也开发了新技术。例如，分治法是一种处理复杂问题的知名技术，在软件工程中也有许多应用方式。例如，软件工程过程本身通常被划分为阶段。这些阶段的定义、顺序以及阶段之间的相互作用指定了软件生命周期模型。最著名的生命周期模型是瀑布模型，包括需求定义阶段、设计阶段、编码阶段、测试阶段和维护阶段。每个阶段的输出作为下一个阶段的输入。参见 `系统工程`。

需求阶段的目的是定义系统应做什么以及它必须运行的约束条件。这些信息记录在需求文档中。典型的需求文档可能包括产品概述；产品开发、运行和维护环境的规范；系统的高级概念模型；用户接口的规范；功能需求规范；非功能需求规范；与开发系统外部接口接口的规范；错误处理方式的规范；以及系统可能的变更和增强列表。每个需求通常编号以便引用，并且必须是可测试的。

在设计阶段，制定系统如何实现需求的计划。该计划使用设计方法和符号表示。已经开发了许多软件设计方法和符号。每种方法都关注系统的某些方面，忽略或最小化其他方面。这类似于使用建筑图纸、管道图、电气接线图等来查看建筑物。

软件生命周期的编码阶段涉及开发实现设计的代码。该代码使用称为编程语言的正式语言编写。编程语言随着时间从计算机直接可解释的一串零和一，经过符号机器代码、汇编语言，最终演变为对人类更具可读性的高级语言。参见 `编程语言`。

如今的大多数编码都是用其中一种高级语言完成的。当代码用高级语言编写时，它由编译器翻译成汇编代码，最终变成机器代码。许多高级语言已经开发出来，它们可以归类为函数式语言、声明式语言和命令式语言。

遵循模块化原则，大型系统中的代码被分隔成模块，并分配给各个程序员。程序员通常使用文本编辑器编写代码。有时使用了解给定编程语言并能提供编程模板和检查代码语法错误的语法指导编辑器。程序员可能会使用各种调试工具，包括帮助查找代码错误的调试器、显示模块中哪些部分花费最多时间执行的分析器，以及使代码运行更快的优化器。

测试是检查软件产品以发现错误的过程。这不仅适用于代码，还适用于所有生命周期产品以及支持软件的文档，例如用户手册。

软件测试过程通常分为阶段。第一阶段是对单个程序员开发的软件进行单元测试。第二阶段是集成测试，其中单元组合在一起并作为一组进行测试。系统测试是在整个系统上进行的，通常根据系统需求开发测试用例。软件的验收测试由其预期用户执行。

测试的基本单位是测试用例。测试用例由测试用例类型（测试用例应测试的系统方面）；测试条件（测试的输入值）；以及测试中要使用的系统环境状态；以及给定输入和环境因素下系统的预期行为组成。

当软件被修改以修复 bug 或添加增强功能时，往往会引入严重错误。为了确保这种情况不会发生，每次更改后必须运行所有测试用例。重新运行测试用例以确保未引入错误的过程称为回归测试。参见 `软件测试与检查`。

走查和检查用于改进软件开发过程的质量。因此，由该过程创建的软件产品的质量得到提高。质量系统是技术集合，其应用结果是开发过程质量的持续改进。质量系统的元素包括评审、检查和过程审计。

大型软件系统不是静态的；相反，它们在开发期间和部署后都会经常变化。维护是软件生命周期中部署后的阶段。维护阶段的成本可能超过其他所有阶段的总和，因此是软件组织的主要关注点。例如，Y2K 问题就是一个维护问题。

维护由三项活动组成：适应、纠正和增强。增强是为系统添加新功能的过程。这通常根据系统用户的请求进行。此活动需要自身完整的生命周期。也就是说，增强需要需求、设计、实现和测试。研究表明，大约一半的维护工作花在增强上。

适应性维护是改变系统以适应新运行环境的过程，例如将系统从 Windows 操作系统移动到 Linux 操作系统。据发现，适应性维护约占维护总工作量的四分之一。纠正性维护是在发布后修复系统中错误的过程。纠正性维护占维护工作量的约 20%。

由于软件系统随时间频繁变化，软件配置管理是一项重要活动。这包括跟踪生命周期对象的版本、控制它们的变更以及监控它们之间的关系。配置管理活动包括版本控制（涉及跟踪生命周期对象的版本）、变更控制（处理系统变更请求的有序过程）和构建控制（跟踪哪些工作产品版本共同构成给定版本的软件产品）。

### 软件测试与检查

检测软件故障的程序。当软件未能按预期方式运行时，即发生软件故障。软件故障是由软件程序中的一个或多个部分不正确引起的。这些不正确的部分中的每一个都称为软件故障（fault）。故障可能简单得只是一个错误的值，也可能与程序中的某个决策有关。故障产生的原因有很多，包括对需求的误解、忽略特殊情况、使用了错误的变量、对算法的误解，甚至包括打字错误。如果软件发生故障可能导致严重后果，则称该软件为安全关键软件。飞机、医疗、核电站和交通领域的许多应用都涉及此类软件。

软件测试是执行软件以检测故障的过程。软件检查是一种通过分析源代码来检测故障的人工过程。这两种程序通常使用许多相同的技术。也可以使用其他技术来最小化软件中发生故障的可能性。这些技术包括使用形式化规格说明、正确性的形式化证明以及模型检查。然而，即使使用了这些技术，使用测试用例执行软件以检测潜在故障仍然至关重要。

软件测试包括选择测试用例、确定软件的正确输出、使用每个测试用例执行软件，以及将实际输出与预期输出进行比较。更多的测试通常更好，但需要耗费时间和努力。必须权衡额外测试的价值与额外努力成本以及软件交付延迟之间的关系。另一个需要考虑的因素是软件发生故障的潜在成本。安全关键软件通常比其他任何软件都经过更彻底的测试。

潜在测试用例的数量非常庞大。例如，对于一个简单的将两个整数相乘的程序，如果该整数在内部表示为32位数字（这是内部表示的常见大小），那么每个数字都有 $2^{32}$ 种可能的值。因此，可能的输入组合总数为 $2^{64}$，这超过了 $10^{19}$。如果一个测试用例可以在每微秒（$10^{-6}$ 秒）内运行一次，那么尝试所有可能的测试用例将花费数万年。尝试所有可能的测试用例称为穷举测试，由于任务规模巨大，这通常不是一种合理的方法。

软件测试的一种方法是找到测试用例，使得程序中的所有语句都被执行。更广泛的测试选择标准是“每个分支覆盖”。这意味着测试每个决策产生的每个分支。而不仅仅要求整个决策为真或假，“多重条件覆盖”标准还要求覆盖决策中每个简单比较的真值组合。另一种方法称为数据流覆盖。覆盖的基础是变量被赋值的语句（定义点）和使用该值的语句之间的执行路径。这些路径必须不包含目标变量的其他定义。参见 `数据流系统`。

功能测试将软件的实际行为与预期行为进行比较。预期行为通常在规格说明中描述。更复杂的功能测试用例选择涉及分析任务中固有的条件。

另一种测试选择方法侧重于子域之间的边界。这种方法认识到许多故障与边界条件有关。选择测试用例以检查边界是否正确。会选择位于边界上的测试用例以及刚偏离边界的测试用例。参见 `软件`；`软件工程`。[D.A.G.]

## 土壤

细碎的、源自岩石的物质，含有有机质混合物，能够支持植被生长。土壤是独立的自然体，每个土壤都具有独特的形态，这是由气候、动植物、母岩材料、地貌、地下水和年龄的特定组合形成的。土壤支持植物，占据地球表面的大部分区域，并具有形状、面积、广度、宽度和深度。此处使用的“土壤”一词的含义与工程师使用的术语不同，后者指未固结的岩石材料。参见 `土壤学`。
