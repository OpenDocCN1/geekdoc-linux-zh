
- `AppImage` 采用的是直接下载并运行单个文件的方法。这很简单，但并非对所有新用户都容易。首先，在你运行应用程序之前，需要设置下载的 `AppImage` 文件为可执行文件。此外，没有内置的机制来更新你的 `AppImages`。该项目提供了一个外部工具来实现这一点，但你也需要自己下载并配置该工具。

尽管如此多关于优缺点的讨论，你可以同时在你的机器上使用上述格式中的任意一个（或全部）。

## 拆解 Flatpak

像大多数开源项目一样，`Flatpak` 站在巨人的肩膀上来实现其目标。`Flatpak` 背后的两项关键技术是 `ostree` 和 `bwrap`（原文拼写为 `bubblwrapar`，根据上下文和技术背景，此处应指 `bwrap` 或 `bubblewrap` 的沙箱机制，但原文如此，此处保留 `bubblwrapar` 的音译或直译以保持忠实，实际上 `bubblwrap` 可能是 `bubblewrap` 的笔误，下文将按 `bubblewrap/bwrap` 的技术含义进行理解翻译，但为了严谨，若原文确为 `bubblwrapar`，则翻译为 `bubblwrapar`。鉴于这是技术文档，`bubblewrap` 是 Linux 下真实的沙箱工具，故此处推测 `bubblwrapar` 为 `bubblewrap` 的误写，翻译时修正为 `bubblewrap` 更符合技术准确性，但若需严格字面翻译则保留。考虑到“高级文档工程师”的身份，我将采用技术正确的 `bubblewrap`，并在必要时注明。*修正策略：根据上下文“Linux kernel's user namespaces feature”，这明确指向 `bwrap` (bubblewrap)。原文 `bubblwrapar` 显然是 typo。我将翻译为 `bubblewrap`。*)

安装 `Flatpak` 时，你安装的包含该应用程序的 `ostree`“捆绑包”。该项目网站将其描述为类似于“用于操作系统二进制的 git”。除了其他好处外，这种方法提供原子更新，这是一种花哨的说法，意思是只更新需要更新的内容。它还提供了回滚机制。

假设你有一个包含文件 1 和文件 2 的程序。更新提供了文件 2 的新版本，实际上指定为文件 3。该程序使用文件 1 和文件 3 运行得非常好，直到你想要回滚一个版本。但你不需要进行完整的卸载/重装操作。你只需要更改应用程序，使其使用文件 2 而不是较新的文件 3（如果以后想要“向前滚动”，文件 3 仍然存在）。

另一个辅助技术是 `bubblewrap`（原文误写为 `bubblwrapar`），它是一个软件层，反过来利用 Linux 内核的用户命名空间特性。它允许非 root 用户账户在容器中充当 root 账户，包括 `Flatpak` 沙箱。当你运行一个 `Flatpak` 应用程序时，它会启动一个由 `Flatpak` 应用程序和供沙箱使用的一组精选系统资源组成的子系统。GitHub 上的 `Flatpak` wiki（[https://github.com/flatpak/flatpak/wiki/Sandbox](https://github.com/flatpak/flatpak/wiki/Sandbox)）有一页详细描述了沙箱的内容，但一些关键属性是：

- 应用程序的 `runtime(s)` 被挂载到沙箱内的 `/usr` 中（其结构在右侧的框中作了更详细的说明）。
- 应用程序本身被挂载在 `/app` 中。
- 来自主机 `/etc` 目录的配置被挂载到沙箱的 `/usr/etc`。
- 只有沙箱内的进程可以从沙箱中看到，例如 `/proc` 目录。
- 如图标、字体等资源通过“绑定挂载”（bind-mounts）可用，即将文件系统中的一个文件/目录（沙箱外）挂载到文件系统中的另一个位置（沙箱内）。
- 总体而言，沙箱只能访问其运行所需的资源，并且只有最低限度的权限。

现在，如果你还没有被搞糊涂，我们要再增加一层复杂性。因为虽然大多数软件在 Linux 系统上安装需要 root 权限，但普通用户可以安装 `Flatpaks`。在下一节中，我们将研究这种“用户安装”与更传统的“系统安装”之间的区别。

## 系统安装与用户安装

经验丰富的 Linux 用户习惯于在安装软件时提供 root 密码。该软件最终会位于你的 `HOME` 目录之外的目录中，例如 `/usr/bin`、`/opt` 或甚至 `/usr/local`。但正如我们在优点列表中提到的，`Flatpak` 支持为特定用户而非整个系统安装程序的能力。这是可行的，因为普通用户有权访问运行程序所需的资源。

## FLATPAK 结构剖析

安装 `Flatpak` 会为程序及其运行时创建文件结构，以及一些元数据。这个基本结构由位于 `$HOME`/`local/share/flatpak` 或 `/var/lib/flatpak` 中的四个顶级目录组成，具体取决于它是系统安装还是用户安装。

第一个是 `repo`，它包含有关已安装应用程序、远程源和其他元数据的信息。`app` 目录是应用程序本身所在的位置。每个程序都有一个以其三部分标识符命名的子目录（例如，`org.gnome.GEdit`）。还有进一步保留给架构（例如 `x86_64`）、版本号和其相关校验和的子目录。

运行时以相同的方式管理，但在 `runtime` 目录中单独保存。这是因为它们可以在多个应用程序之间共享。最后一个目录是 `exports`，包含与 `Flatpak` 程序相关但位于沙箱外部的项。这些包括应用程序图标和 `desktop` 文件（将出现在你的桌面应用程序菜单中）以及系统引用，例如与窗口系统的连接。`exports` 目录包含指向 `Flatpak` 内部事物的链接，是主机系统和 `Flatpak` 沙箱之间受控制的接触点之一。

## FOSS

用户创建的沙盒也会获得这种相同的访问权限。

当你运行接下来会看到的任何安装命令时，系统会提示你输入密码。这是因为 `Flatpak` 默认会执行系统级安装。这意味着该程序将对所有用户可用，并且其文件将存储在 `/var/lib/flatpak` 目录中。

或者，如果你在命令中使用 `--user` 标志——它只会为你自己的账户安装（此时你不需要输入密码）。在这种情况下，文件将位于 $HOME/.local/share/flatpak。如果你没有系统管理员账户，这将非常有用。

或者，如果你想尝试位于系统其他地方的某个程序的尖端版本，也会用到这种方法。

之所以能进行用户级安装，是因为沙盒的构建方式。你可以这样理解：作为用户，你拥有运行应用程序的能力。该应用程序通过你的用户账户拥有在屏幕上创建窗口、向磁盘写入文件以及访问网络连接的权利。当你以用户身份安装 `Flatpak` 时，来自宿主系统的任何资源都受限于你使用“常规”程序所能访问的范围。
