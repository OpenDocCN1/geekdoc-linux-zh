
这两个文件的权限令我们感兴趣。`/bin`中的`passwd`文件在权限字段中有一个`s`。现在让我们理解为什么。

`/etc`目录中的`passwd`文件不允许用户直接写入。然而，同一个文件可以由调用`/bin`目录的可执行文件的修改。

## 在 Unix 中操作

`passwd`可执行文件设置了所谓的`su-id`位，以便任何调用它的用户都能获得`auth`的组ID并成为`/etc/passwd`的临时所有者。注意，如果没有发生这种情况，用户将无法向`/etc/passwd`文件写入修改或删除他的密码。因此，当你执行`/bin/passwd`文件时，我们的组ID将与“auth”相同，从而我们可以访问`/etc/passwd`文件。

当我们停止执行`passwd`命令返回Shell时，我们的id将恢复到初始值，就像什么都没有发生过一样。这种机制是万无一失的。使用这种`su-id`（替换用户ID）位，Unix为重要的系统文件提供了保护。

对于普通用户，`su-id`位可以用于类似的目的。假设有一个受高度保护的数据库文件只向“组”和“其他”提供读取权限，这样用户就不被允许直接写入文件。但在调用可执行文件时，可能会授予相同的权限以确保数据安全地写入数据库。要创建这样的设置，设置可执行文件的`suid`位：

```
$ chmod u+s data-entry
ls -l data-entry
-rwsrx-x 1 user group 14 Apr 05 
```

现在调用此可执行文件的用户将自动获得user-id并被允许写入“data-entry”文件。

## 受限制的 Shell "rsh"：监禁

标准Shell允许用户在系统中移动、执行许多命令、更改环境变量等。然而，出于某些原因，这些权限不应该授予用户，Unix提供了另一种被称为受限制的Shell。这是一种关禁，如你所见。

`rsh`是一个像`sh`一样的可执行程序，存在于`/bin`目录，它授予用户最少的权限。这种Shell被某些操作限制：

- 1. 用户被限制在自己的`HOME`目录。他不能切换到系统中的其他目录。
- 2. 用户不能更改`PATH`变量，只有系统管理员设置的路径是可用的。例如，如果他的`PATH`设置为`/bin`，他无法执行位于`/usr/bin`或`/etc`的命令。
- 3. 用户无法使用`>`或`>>`操作符创建新文件或附加现有文件。

受限制Shell用于防止新手或业余用户对系统目录造成损坏或意外删除。通常，`rsh`授予那些有有限权限的用户。

## 在 Unix 中操作

让我们自己尝试使用受限制Shell，但作为临时。毕竟，熟练的Unix专业人士不会被这种敌对环境限制。调用受限制shell，只需输入：

```
$ rsh
```

现在受限制Shell已安装到你现有的Shell上。`ps`命令将证实这一点。

```
$ ps

721 tty 0:00 rsh
723 tty 0:00 ps
$
```

```
$ cd /etc

```

这非常难以忍受。我们知道如何杀死在终端上运行的进程。我们通过`ps`命令知道了`rsh`的`PID`。所以，让我们打破枷锁吧。

记住，要杀死像Shell这样的进程，必须向它发送终止信号9。因此我们得出，`rsh`并不是完全安全的。任何熟练的Unix用户都可以突破受限制Shell并再次获得主Shell，只要主Shell在后台存在。

强制对任何用户施加受限制Shell的最佳方法之一是将其添加到`/etc/passwd`文件。该文件的最后一个字段指定了每个用户登录时的Shell。如果没有指定Shell，默认是`/bin/sh`。如果该值被超级用户更改为`/bin/rsh`（记住只有超级用户可以直接写入“passwd”文件），那么`rsh`将成为该用户的主要Shell。

```
# cat /etc/passwd | grep 'b77'
b77:*:224:50::/data/bb7:/bin/rsh
#
```

现在当"b77"登录时，他将获得受限制Shell作为他的主要shell。

## 文件系统与设备管理

从安装系统到日常例行备份任务，所有操作系统都需要与磁盘和磁带等各种介质交互。Unix对大量介质有惊人的理解，其中一些在今天已经过时了。

Unix对媒体和设备的理解来自于“dev”目录中的特殊文件。对于所有设备来说，这就是智慧的源泉。因此，“/dev”目录是Unix通往外部世界的一扇“窗户”。

## 使用 Unix 操作

通常，`/dev/`目录包含数百个文件，允许Unix能够理解各种外部设备，如磁盘、软磁盘、磁带、终端、打印机、鼠标等。对于每个设备，都有许多类和类型。而对于每种类型，都有唯一的文件。这就是Unix设备管理的全局图景：关键在于依赖文件。在这些海量文件中，即使是某一个丢失或意外损坏，也可能导致混乱。

获取Unix设备管理清晰视图的最佳方法之一是将其视为一个设备驱动程序数据库，这些驱动程序的名称毫无意义，且极其晦涩。我们将一个一个地处理它们，从磁盘开始，即Unix系统所处的介质。

在深入学习之前，先了解一点理论，这有助于理清基础知识。

### 磁盘块与 Inode

为了优化存储和跟踪效率，文件以512字节扇区的倍数存储在磁盘上。这些扇区被称为逻辑块或简单称为块（`blocks`）。通常，Unix系统使用两个512字节的扇区形成一个1024字节的逻辑块。

当你复制、创建或修改文件时，Unix会处理将文件内容保存到磁盘的事务。Unix会确保预留足够的块来存放文件。现在，由于每个文件的最小分配空间为一个块，即使是一个微不足道的5字节文件也会占用磁盘上的一个完整块。因此，可用磁盘空间减少了1024字节！同样，一个大小为1025字节的文件将占用两个完整的磁盘块。更糟糕的是，目录即使是空的，也会占用一个完整的磁盘空间！

这一切似乎看起来像是一个设计糟糕的悲剧。但Unix在块分配空间方面有自己的理由。请记住，Unix必须将每个文件名转换为磁盘上数据的实际物理位置。而磁盘上数据的物理位置是基于磁盘上文件系统的块号。

当用户删除现有文件时，块会被提供给新文件或需要扩展的现有文件。删除文件会导致块孤立在分配块的区域内。因此，当创建新文件时，分配给它的块可能会分散在磁盘的大部分。这样的文件被称为碎片文件。这就是`Inode`的用用场。

### Inode、Inode 表与超级块

除了磁盘块外，文件系统还包含一个磁盘上所有文件名的列表，并与每个名称关联的磁盘块指针匹配。每个名称和关联块都存储在`inode`（或索引节点）中。我们在第一章关于文件系统的初步讨论中已经提到过`inode`。一个`inode`存储了与每个文件关联的数据块块列表，以及其他相关详细信息，如文件权限、所有者、访问时间等。这个`inode`是一个数字，对每个文件都是唯一的，并存储在包含该文件的目录中。现在，这些碎片似乎正在逐渐就位。

## 使用 Unix 操作

文件系统能够容纳的文件数量不仅取决于可用磁盘块的数量，还取决于可用`inode`的数量。我们知道，当创建一个新文件时，Unix会从一个名为“`inode`表”（`inode table`）的结构中为其分配一个空闲`inode`。每个文件系统中可以分配的`inode`数量是有限的，因此如果你在磁盘上有许多占用极小物理磁盘空间的小文件，请记住它们消耗了一个珍贵的空闲`inode`。可能会出现这样一个阶段：尽管有磁盘空间，但没有可分配的空闲`inode`了。因此，平衡`inode`数量与平均文件大小以优化磁盘空间利用率，始终是一个好主意。
