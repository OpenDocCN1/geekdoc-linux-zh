
- Postgres 中的每个用户都分配有一个用户名和（可选的）密码。默认情况下，用户对其未创建的数据库没有写权限。
- 用户可以分配到组，并可以根据组权限限制访问。

# 用户身份验证

认证是后端服务器和主进程（`postmaster`）确保请求访问的用户确实是其声称的身份的过程。然而，验证用户的实际身份是通过多种方式完成的：

- 从用户外壳（shell）：

从用户外壳启动的后端服务器会在执行 `setuid` 到 `postgres` 用户-id 之前记录用户的（有效）用户-id。

- 从网络：

Postgres 系统被构建为分布式的，可以访问主进程的 TCP 端口。`PGDATA` 目录下的 `pg_hba.conf` 文件根据连接的主机及其连接的数据库来配置使用何种认证系统。请参见 `pg_hba.conf(5)` 获取可用认证系统的描述。当然，在 UNIX 中基于主机的认证并非无一失，入侵者可能伪装成来源。这些安全问题超出了 Postgres 的范围。

# 基于主机的访问控制

基于主机的访问控制是 PostgreSQL 对允许访问数据库的客户端的基本控制，以及它们如何验证身份。每个数据库在其 `PGDATA` 目录中都包含一个名为 `pg_hba.conf` 的文件，该文件控制谁可以连接。每个访问数据库的客户端都受 `pg_hba.conf` 中某一个条目的覆盖。否则，来自该客户端的所有尝试连接将以身份验证失败的消息被拒绝。`pg_hba.conf` 的通用格式是一个记录文件，每行一条，由多个由空格或制表符分隔的字段组成。空行和以井字符（`#`）开头的行会被忽略。可以使用 UNIX 域套接字或 Internet 域套接字（即 TCP/IP）建立连接。使用 UNIX 域套接字的连接使用以下格式的记录控制：

```
local database authentication method
```

其中

- `database` 指定该记录适用的数据库。
- `all` 指定适用于所有数据库。
- `authentication method` 指定用户在连接到该数据库时必须使用的方法。接下将描述不同的方法。

使用 Internet 域套接字的连接使用以下格式的记录控制：

```
host database TCP/IP address TCP/IP mask authentication method
```

`TCP/IP address` 与指定的 TCP/IP 掩码以及连接客户端的地址进行逻辑与（AND）运算。如果得到的两个值相等，则对该连接使用该记录。如果一个连接匹配了多个记录，则使用文件中最早的那个。TCP/IP 地址和 TCP/IP 掩码都以点分十进制表示法指定。如果连接未匹配到任何记录，则应用拒绝认证方法（见下文）。

# 认证方法

对于 UNIX 和 TCP/IP 域套接字均支持以下认证方法：

- `trust`

无条件允许连接。

- `reject`

无条件拒绝连接。

- `crypt`

要求用户提供密码。该密码使用 `crypt(3)` 加密发送，并与 `pg_shadow` 表中有的密码进行比较。如果密码匹配，则允许连接。

- `password`

要求用户提供密码。该密码明文发送，并与 `pg_shadow` 表中有的密码进行比较。如果密码匹配，则允许连接。在 `password` 关键字之后可以指定一个可选的密码文件，它用于匹配提供的密码而非 `pg_shadow` 表。请参见 `pg_passwd`。

仅对 TCP/IP 域套接字支持以下认证方法：

- `krb4`

使用 Kerberos V4 验证用户。

- `krb5`

使用 Kerberos V5 验证用户。

- `ident`

使用客户端上的 ident 服务器验证用户（RFC 1413）。在 `ident` 关键字之后可以指定一个可选的映射名称，允许 ident 用户名映射到 Postgres 用户名。映射存储在 `$PGDATA/pg_ident.conf` 文件中。

以下是一些示例：

```
# 信任通过 Unix 域套接字的任何连接。
local       trust
# 信任通过 TCP/IP 来自此机器的任何连接。
host        all             127.0.0.1       255.255.255.255      trust
# 我们不喜欢这台机器。
all all 192.168.0.10 255.255.255.0 reject
# 这台机器无法加密，因此要求文密码。
host all 192.168.0.3 255.255.255.0 password
# 这组机器的其他机器应该提供加密密码。
host all 192.168.0.0 255.255.255.0 crypt
```

`grolist`

属于该组的 `pg_user` ID 列表。这是一个 `int4` 类型

## 访问控制

Postgres 提供了相应的机制，允许用户限制其向其他用户的数据访问。

## 数据库超级用户

数据库超级用户（即设置了 `pg_user.usesuper` 为真的用户）会静默跳过后续描述的所有访问控制，但有两个例外：如果用户没有设置 `pg_user.usecatdup`，则不允许手动更新系统目录表；且永远不允许破坏系统目录表（或修改其模式）。

## 访问权限

使用访问权限来限制对类的读取、写入和规则设置的操作已包含在 `grant/revoke(l)` 命令中。

## 类删除和模式修改

破坏或修改现有类结构的命令（如 `alter`、`drop table` 和 `drop index`）仅对类的所有者生效。如前所述，这些操作绝不允许在系统目录表上执行。

## 函数与规则

函数和规则允许用户将代码插入到后端服务器，其他用户可能会在不知情的情况下执行这些代码。因此，这两种机制都允许用户在几乎不受惩罚的情况下对他人实施“特洛伊木攻击”。唯一的真正保护是对谁可以定义函数（例如向带有 SQL 字段的关系表写入数据）和规则进行严格控制。建议对 `pg_class`、`pg_user` 和 `pg_group` 设置审计日志和告警。

## 函数

除 SQL 以外的任何语言编写的函数都会以 `postgres` 用户的权限在后端服务器过程中运行（后端服务器运行时，其真实和有效用户 ID 均设置为 `postgres`）。用户可能会从信任函数内部更改服务器的内部数据结构。因此，在许多其他因素中，此类函数可以绕过任何系统访问控制。这是用户定义 C 函数的固有问题。

## 规则

与 SQL 函数一样，规则始终以调用后端服务器的用户身份和权限运行。

# 注意事项

Postgres 目前没有显式支持内部加密数据的计划（尽管没有什么阻止用户在用户定义函数内部对数据进行加密）。由于需要完全重写前端/后端协议，目前也没有显式支持加密网络连接的计划。用户名、组名以及相关的系统标识符（例如，假设 `pg_user.usersysid` 的内容在整个数据库中是唯一的）。如果不是，则可能会出现不可预测的结果。

## 安全 TCP/IP 连接

你可以使用 `ssh` 来加密客户端与 Postgres 服务器之间的网络连接。如果操作得当，这应该带来一个足够安全的网络连接。`ssh` 文档提供了启动所需的大部分信息。请参考 http://www.heimhardt.de/htdocs/ssh.html 以获取更深入见解。

## 通过 ssh 运行安全隧道

只需两个步骤即可完成逐步说明：

- 建立一个到后端机器的隧道，如下：

```
ssh -L 3333:wit.mcs.anl.gov:5432 postgres@wit.mcs.anl.gov
```

`-L` 参数中的第一个数字 `3333` 是你隧道末端的端口号。第二个数字 `5432` 是隧道的远程端——即你的后端正在使用的端口号。数字之间的名称或地址属于服务器机器，`ssh` 的最后一个参数（也包含可选的用户名）也是如此。如果不提供用户名，`ssh` 将尝试使用你当前登录的客户端机器名称作为用户名。你可以使用服务器机器接受的任何用户名，而不一定与 `postgres` 相关。

- 现在你已经有一个正在运行的 `ssh` 会话，可以根据你在上一步指定的端口号连接到本地的 `postgres` 客户端。如果是 `psql`，你需要另一个 shell，因为你在第 1 步中 shell 会话现在被 `ssh` 占用了。

```
psql -h localhost -p 3333 -d mpw
```

注意，你必须指定 `-h` 参数以使客户端使用 TCP 套接字而不是 UNIX 套接字。如果你选择 5432 作为隧道末端，可以省略端口参数。

## 添加和删除用户

`createuser` 命令允许特定用户访问 Postgres。`destroyuser` 移除用户并防止他们访问 Postgres。这些命令仅在 Postgres 方面影响用户；它们不会影响用户在底层操作系统方面的其他权限或状态。

```bash
bash# su - postgres
bash$ man createuser
bash$ createuser
```
