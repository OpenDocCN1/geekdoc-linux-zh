
`make` 程序接收 `makefile`（通常命名为 `Makefile`）作为输入，它描述了组成完成程序的组件之间的关系和依赖关系。

`makefile` 的开头定义了变量，这些变量会在 `makefile` 的后续部分被替换。例如，我们看到了以下行：

```
CC=gcc
```

这定义编译器为 `gcc`。在 `makefile` 中，我们看到了一处用法。

```
diction: diction.sentence.misc.o getopto.getopt1.o
$(CC) -o $@ $(LIBS) diction.sentence.misc.o \
getopto.getopt1.o $(LIBS)
```

这里执行了替换，`$(cc)` 的值在运行时被替换为 `gcc`。`makefile` 的大部分由行组成，它们定义了一个目标，在本例中是可执行文件 `diction` 以及它所依赖的文件。其余行描述了这些组件。

从其组件创建目标所需的命令。在这个示例中，我们看到可执行文件 `diction`（产物之一）依赖于 `diction.o`、`sentence.o`、`misc.o`、`getopt.o` 和 `getopt1.o` 的存在。稍后，在 `Makefile` 中，我们看到了这些目标的定义。

```
diction.o:         diction.c config getopt.h misc.o sentence.h
getopt.o:           getopt.c config getopt_int.h
getopt1.o:          getopt1.c config getopt.h getopt_int.h
misc.o:             misc.c config misc.h
sentence.o:        sentence.c config misc.h sentence.h
style.o:            style.c config getopt.h misc.h sentence.h
```

然而，我们没有看到为它们指定任何命令。这是通过文件中前面的一个通用目标处理的，该目标描述了将 `.c` 文件编译为 `.o` 文件的用到的命令：

```
.c.o:
	$(CC) -c $(CFLAGS) $(CFLAGS) $<
```

这看起来非常复杂。为什么不直接列出编译部分的所有步骤并完事了呢？答案很快就会明朗。在此期间，让我们运行 `make` 并构建我们的程序。

```
[@linuxbox diction-1.11]$ make
```

`make` 程序将运行，使用 `Makefile` 的内容来指导其操作。它将产生大量信息。

在完成后，我们将看到所有目标现在都出现在我们的目录中。

```
[@linuxbox diction-1.11]$ ls
```

| config.guess | de.po | en | install-sh | sentence.c |
| :--- | :--- | :--- | :--- | :--- |
| config.h | diction | en_GB | Makefile | sentence.h |
| config.in | diction.1 | en_GB | Makefile.in | sentence.o |
| config.log | dictionary.1 | en_GB | misc.c | style |
| config.status | dictionarygetoptc | misc.h | style.1 | |
| config.sub | diction | getopt1.o | misc.o | style.1.in |

| configure.in | diction.spec | getopt_int.h | nl | style.o |
| COPYING | diction.spec | | test | |
| de | diction.text | getopt.o | nl.po | |
| de.mo | diction.text | INSTALL | README | |

在这些文件中，我们看到了 `diction` 和 `style`，这些都是我们正打算构建的程序。恭喜！我们刚刚从源代码编译了我们的第一个程序！

但出于好奇，让我们再次运行一次 `make`。

```
[@linuxbox diction-1.11]$ make
make: Nothing to be done 'all'.
```

它输出了这条奇怪的消息。发生了什么？为什么它没有再次构建程序呢？啊，这就是 `make` 的魔法。`make` 并不是简单地重新构建一切，而是只构建需要的内容。由于所有目标都存在，`make` 认为无事可做。我们可以通过删除其中一个目标并再次运行 `make` 来观察它做了什么，以此演示这一点。让我们去掉其中一个中间目标：

```
[me@linuxbox diction-1.11]$ make getopt.o
[me@linuxbox diction-1.11]$ make
```

我们看到 `make` 重新构建并重新链接了 `diction` 和 `style` 程序，因为它们依赖于缺失的模块。这种行为还指出了 `make` 的另一个重要特性：它保持目标更新。`make` 确保目标比它们的依赖项新。这完全合理，因为程序员经常会更新部分源代码，并使用 `make` 构建完成产品的新版本。它确保根据更新后的代码确定哪些内容需要构建。如果我们使用 `touch` 程序“更新”其中一个源代码文件，就可以看到这一点：

```
[me@linuxbox diction-1.11]$ ls -l diction getopt.c
-rw-xr--x 1 me 37164 2025-03-05 06:14 diction
-rw-r--r-- 1 me 33125 2007-03-30 17:45 getopt.c
[me@linuxbox diction-1.11]$ touch diction -l getopt.c
-rw-xr--x 1 me 37164 2025-03-05 06:14 diction
-rw-r--r-- 1 me 33125 2025-03-05 06:23 getopt.c
[me@linuxbox diction-1.11]$ make
```

在 `make` 运行后，我们看到它已恢复目标使其比依赖项更新。

```
[@linuxbox diction-1.11]$ ls -l diction.c
-rw-xr--x 1 me 37164 2009-03-05 06:24 diction
-rw-r--r-- 1 me 33125 2009-03-05 06:23 gotten.c
```

`make` 智能构建仅需要的内容的能力对程序员来说是一个巨大的优势。虽然在我们的小项目中节省时间的优势可能并不明显，但它是意义巨大的。Linux 内核（一个持续更新的程序）……

## 可执行权限

我们接下来要做的事情是让我们的脚本具有可执行权限。这可以使用 `chmod` 轻松完成。

```bash
@me@linuxbox ~$ ls -l hello_world
-rw-r--r-- 1 me 63 2025-03-07 10:10 hello_world
@me@linuxbox ~$ chmod 755 hello_world
@me@linuxbox ~$ ls -l hello_world
-rwxr-xr-x 1 me 63 2025-03-07 10:10 hello_world
```

脚本有两种常用的权限设置：`755` 适用于所有人执行的脚本，`700` 适用于仅所有者可以执行的脚本。注意，脚本必须可读才能执行。

## 脚本文件位置

有了权限，我们就可以执行脚本了。

```bash
@me@linuxbox ~$ ./hello_world
Hello World!
```

为了让脚本运行，我们必须在脚本前加上显式路径。如果不这样做，我们会得到：

```bash
@me@linuxbox ~$ hello_world
bash: hello_world: command not found
```

这是为什么呢？我们的脚本和其他程序有什么区别吗？事实证明，并没有区别。问题在于我们脚本的位置。在第 11 章中，我们讨论了 `PATH` 环境变量及其对系统搜索可执行程序的影响。回顾一下，当系统每次需要查找可执行程序时，如果没有指定显式路径，它会搜索一个目录列表。这就是为什么当我们在命令行输入 `ls` 时，系统知道去执行 `/bin/ls`。`/bin` 目录是系统自动搜索的目录之一。目录列表存储在环境变量 `PATH` 中。`PATH` 变量包含一个用冒号分隔的搜索目录列表。我们可以查看 `PATH` 的内容。

```bash
@me@linuxbox ~$ echo $PATH
/home/me:/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games
```

在这里我们看到了自己的列表。如果我们的脚本位于列表中的任何目录下，我们的问题就解决了。注意列表中的第一个目录 `/home/me/bin`。大多数 Linux 发行版都将 `PATH` 变量配置为包含用户主目录下的 `bin` 目录，允许用户执行自己的程序。如果我们创建 `bin` 目录并将脚本放在其中，它应该就能像其他程序一样工作。

```bash
@me@linuxbox ~$ mkdir bin
@me@linuxbox ~$ mv hello_world bin
@me@linuxbox ~$ hello_world

Hello World!
```

事实确实如此。

如果 `PATH` 变量不包含该目录，我们可以通过在 `.bashrc` 文件中包含此行来轻松添加。

```bash
export PATH=$bin:$PATH
```

此更改后，它将在新的终端会话中生效。要将更改应用于当前终端会话，我们必须让 shell 重新读取 `.bashrc` 文件。这可以通过“源”`source` 它来实现。

```bash
me@linuxbox ~$ . .bashrc
```

点 `.` 是 `source` 命令的同义词，这是一个 shell 内置命令，用于读取指定的 shell 命令文件并将其视为来自键盘的输入。

### 注意

Ubuntu（以及大多数其他基于 Debian 的发行版）在执行用户的 `.bashrc` 文件时，如果 `~/bin` 目录存在，会自动将其添加到 `PATH` 变量中。因此，在 Ubuntu 系统上，如果我们创建 `~/bin` 目录并注销重新登录，一切都能工作。

## 脚本的好位置

`~/bin` 目录是存放个人用途脚本的好地方。如果我们编写一个系统上所有用户都可以使用的脚本，传统位置是 `/usr/local/bin`。供系统管理员使用的脚本通常位于 `/usr/local/bin`。在大多数情况下，本地提供的软件（无论是脚本还是编译程序）都应该放在 `/usr/local` 层次结构中，而不是 `/bin` 或 `/usr/bin`。这些目录由 Linux 文件系统层次结构标准规定仅包含由 Linux 发行版提供和维护的文件。

## 更多格式技巧

严肃写作的核心目标之一是易于维护，也就是说作者或其他人可以方便地修改脚本以适应变化的需求。让脚本易于阅读和理解是促进易于维护的方法之一。

### 长选项名称

我们学习过的许多命令都同时具有短选项和长选项名称。例如，`ls` 命令有许多可以用短形式或长形式表示的选项。例如，以下：

```bash
[me@linuxbox ~]$ ls -ad
```

等同于：

```bash
[me@linuxbox ~]$ ls --all --directory
```

为了减少输入量，在命令行输入选项时优选短选项，但在编写脚本时，长选项可以提供更好的可读性。

### 缩进与续行

在使用长命令时，可以通过将命令跨多行来增强可读性。在第 17 章中，我们查看了一个特别长的命令示例。

```bash
[me@linuxbox ~]$ find playground \ -type f -not -perm 0600 -exec chmod 0600 '{}' ';' \ -o \ -type d -not -perm 0700 -exec chmod 0700 '{}' ';' \
```

显然，这初看之下有点难懂。在脚本中，如果这样写，这个命令可能会更容易理解：

```bash
[me@linuxbox ~]$ find playground \ -type f -not -perm 0600 -exec chmod 0600 '{}' ';' \ -o \ -type d -not -perm 0700 -exec chmod 0700 '{}' ';' \
```

### 为脚本配置 vim

`vim` 编辑器有许多配置设置。一些常用选项可以方便脚本编写。以下开启语法高亮：

```vim
syntax on
```

开启此设置后，元素将以不同的颜色显示。注意，为了让此功能工作，你必须有一个指示文件是 shebang。以下开启搜索高亮：

```vim
hlsearch
```

假设我们搜索该词，每个实例都会被高亮。以下设置 `tab` 占据的列数：

```vim
tabstop=4
```

默认是八。将其设置为 4 可以长行更容易适应屏幕。以下开启“自动缩进”功能：

```vim
autoindent
```

这会导致 vi 按照刚刚输入行的量进行缩进。这些更改可以通过在 `~/.vimrc` 文件中添加这些命令永久永久。

## 总结

在脚本的第一章中，我们学习了如何编写脚本并使其轻松执行。我们还看到了如何使用各种格式技巧来提高脚本的可读性（从而提高维护性）。在未来的章节中，易于维护将再次出现并作为良好写作的核心原则。

## 开始项目

![project](img/58edd539af3a70704734ced1ac0c271_351_0.png)

从本章开始，我们将构建一个程序。这个项目的目的是观察如何使用各种 shell 特性创建程序，特别是良好的程序。我们编写的程序是一个报告生成器。它将展示有关系统的各种统计数据并以 HTML 格式生成报告，以便我们使用 Firefox 或 Chrome 等浏览器查看。

程序通常分阶段构建，每个阶段添加功能和能力。我们程序的第一个阶段将产生一个不包含系统信息的最小 HTML 文档。这将在以后。

### 第一阶段：最小文档

我们需要知道的第一件事是良好的 HTML 文档的格式。它如下：

```html
<html>
<head>
  <title>Page Title</title>
</head>
<body>
  Page body.
</body>
</html>
```

我们程序的第一个阶段将能够将这个 HTML 文件输出到标准输出。

我们可以很容易地编写程序来实现这一点。让我们启动文本编辑器并创建一个名为 `~/bin/sys_info_page` 的新文件。

```
me@linuxbox:~$ vi ~/bin/sys_info_page
```

### 输入以下程序：

```bash
#!/bin/bash

## 输出系统信息页的程序

echo "<html>"
echo "<head>"
echo "<title>Page Title</title>"
echo "</head>"
echo "<body>"
echo "  Page body."
echo "</body>"
echo "</html>"
```

我们这个问题的第一次尝试包含 shebang、一个注释（这总是个好主意）以及一系列用于每行输出的 `echo` 命令。在保存文件后，我们将赋予它可执行权限并尝试运行它。

```bash
me@linuxbox:~$ chmod 755 ~/bin/sys_info_page
me@linuxbox:~$ firefox sys_info_page.html
```

当程序运行时，我们应该会在屏幕上看到 HTML 文档的文本，因为 `echo` 命令将其输出发送到标准输出。我们将再次运行程序，并将程序的输出重定向到文件 `sys_info_page.html`，这样我们可以用浏览器查看结果：

```bash
me@linuxbox:~$ sys_info_page > sys_info_page.html
me@linuxbox:~$ firefox sys_info_page.html
```

到目前为止一切良好。

编写时，始终追求简单和清晰是一个好主意。当程序易于阅读和理解时，维护会变得更容易，更不用它通过减少打字量让程序更容易编写了。我们当前版本的程序运行良好，但它可以更简单。我们实际上可以将所有的 `echo` 命令合并为一个，这无疑将向程序输出中添加更多行变得更容易。所以，让我们将程序更改为：

```bash
#!/bin/bash

## 输出系统信息页的程序

echo "<html>
<head>
<title>Page Title</title>
</head>
<body>
  Page body.
</body>
</html>"
```

带引号的字符串可以包含换行符，因此包含多行文本。shell 将继续读取文本，直到遇到闭合引号。在命令行上也是这样工作的。

```bash
me@linuxbox -]$ echo "<html>
> <head>
> </head>
> <title>Page Title</title>
> <body>
> Page body.
> </body>
> </html>
```

领先字符是包含在 `PS2` shell 变量中的 shell 提示符。每当我们向 shell 输入多行语句时，它就会出现。这个功能现在看起来有点模糊，但稍后当我们涵盖多行编程语句时，事实证明它是非常方便。

### 第二阶段：添加少量数据

现在我们的程序可以生成一个最小的文档了，让我们在报告中放入一些数据。为了做到，我们将我们将以下更改：
