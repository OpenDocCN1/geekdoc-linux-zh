
```c
#include <stdio.h>
#include <sys/types.h>
#include <unistd.h>

int main ()
{
    pid_t child_pid;

    printf("the main program process ID is %d\n", (int) getpid());

    child_pid = fork();
    if (child_pid != 0) {
        printf("this is the parent process, with id %d\n", (int) getpid());
        printf("the child's process ID is %d\n", (int) child_pid);
    }
    else
        printf("this is the child process, with id %d\n", (int) getpid());

    return 0;
}
```

## 3.3 信号

当进程接收到信号时，它可能会执行几种操作之一，取决于信号的*处理方式*（disposition）。对于每个信号，都有一个*默认处理方式*，它决定了当程序可能没有指定其他行为时，进程会发生什么。对于大多数类型，进程可以指定其他行为——要么忽略该信号，要么调用*信号处理*（signal-handler）函数来响应信号。如果使用了信号处理函数，当前正在执行的进程会被暂停，执行信号处理函数，当处理函数返回后，进程恢复执行。

Linux 系统处理信号以响应特定条件。例如，`SIGBUS`（总线错误）、`SIGSEGV`（段错误）和 `SIGFPE`（浮点异常）可能会发送给尝试执行非法操作的进程。这些信号的默认处理方式是终止进程并产生核心转储文件（core file）。

进程也可以向另一个进程发送信号。该机制的一个常见用途是通过发送 `SIGTERM` 或 `SIGKILL` 信号来结束另一个进程。另一个常见用途是向运行中的程序发送命令。“用户定义”信号是为此目的预留的：`SIGUSR1` 和 `SIGUSR2`。`SIGHUP` 信号有时也用于此目的，例如唤醒空闲进程或导致进程重新读取其配置文件。

`sigaction` 函数可用于设置信号处理方式。第一个参数是信号值。接下来两个参数是 *sigaction* 结构体；其中第一个包含该信号号所需的处理方式，而第二个接收之前的处理方式。第一个或第二个 sigaction 结构体中最重要的字段是 `sa_handler`。它可以取以下值之一：

- `SIG_DFL`，指定信号的默认方式。
- `SIG_IGN`，指定应该忽略该信号。
- 指向信号处理函数的指针。该函数应该接收一个参数（即信号值），并返回空值（void）。

由于信号是异步的，当信号发送时以及在信号处理函数执行期间，主程序可能处于一种非常脆弱的状态。因此，你应该避免在信号处理函数中执行任何 I/O 操作或调用大多数库函数。

信号处理函数应该只执行响应信号所所需的最少工作，然后返回主程序（或终止程序）。在大多数情况下，这仅仅是记录信号发生的实。主程序定期检查信号是否发生，并做出相应的反应。

信号处理函数可能会被另一个信号的传递中断。虽然这听起来可能罕见，但如果真的发生了，诊断和调试该问题将非常困难。（这是一个竞态条件的示例，请参见第 4 章“线程”，第 4.4 节“同步与临界区”）。因此，你应该非常小心程序在信号处理函数中所执行的操作。

`SIGTERM` 信号请求终止；进程可以通过屏蔽或忽略信号来忽略该请求。`SIGKILL` 则总是立即杀死进程，因为进程可能无法屏蔽或忽略 `SIGKILL`。

例如，列表 3.5 中的此程序骨架使用信号处理函数来计算程序接收 `SIGUSR1` 的次数，这是预留给应用程序信号之一。

### 列表 3.5 signal1.c 使用信号处理函数

```c
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <sys/types.h>
#include <unistd.h>

sig_atomic_t sigusr1_count = 0;

void handler (int signal_number)
{
    ++sigusr1_count;
}

int main ()
{
    struct sigaction sa;
    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = &handler;
    sigaction(SIGUSR1, &sa, NULL);

    /* 在这里执行一些耗时的工作。 */

    printf("SIGUSR1 was raised %d times\n", sigusr1_count);
    return 0;
}
```

### 3.4 进程终止

通常，进程通过两种方式之一终止：要么执行中的程序调用 `exit` 函数，要么程序的主函数返回。每个进程都有一个退出码：进程返回给其父进程的数字。退出码是传递给 `exit` 函数的参数，或者是从 `main` 返回的值。

进程可能会由于响应信号而异常终止。例如，之前提到的 `SIGBUS`、`SIGSEGV` 和 `SIGFPE` 信号会导致进程终止。其他信号被用于显式地终止进程。当用户尝试通过在终端输入 Ctrl+C 来结束进程时，会向该进程发送 `SIGINT` 信号。`kill` 命令会发送 `SIGTERM` 信号。这些信号的默认处理方式是终止进程并产生核心转储文件。

最简单的函数是 `wait`。它阻塞调用进程，直到其中一个子进程退出（或发生错误）。它通过一个整数指针返回状态码，你可以从中提取关于进程如何退出的信息。例如，`WEXITSTATUS` 宏提取子进程的退出码。

#### 3.4.1 等待进程终止

如果你输入运行了列表 3.4 中的 `fork` 和 `exec` 示例，你可能注意到 `ls` 的输出通常出现在主程序已经完成之后。那是子进程，ls 在其中运行，它独立于父进程进行调度。因为 Linux 是多任务操作系统，两个进程看起来同时执行，你无法预测哪个会在父进程之前或之后运行。

在某些情况下，父进程希望等待一个或多个进程完成。这些函数允许你等待进程完成，并使父进程检索有关其终止的信息。`wait` 族有四个不同的系统调用；你可以选择获取关于退出进程的多或少信息，你也可以选择是否关心哪个进程终止。

#### 3.4.2 wait 系统调用

在大多数 shell 中，可以使用特殊变量 `$` 来获取最近执行的程序的退出码。这里有一个示例，其中 `ls` 被调用了两次，并在每次调用后显示其退出码。在第一情况下，ls 正确执行并返回零。在第二情况下，ls 遇到了一个错误（因为指定的文件名不存在），因此返回非零码。

```bash
% ls /
bin dev etc home mnt opt proc sbin tmp var
% echo $
% ls bogusfile
ls: bogusfile: No file or directory
% echo?
1
```

你可以使用 `WIFEXITED` 宏根据子进程的退出状态判断进程是正常退出（通过 `exit` 函数或从 `main` 函数返回）还是由于未处理的信号而死亡。在后的情况下，使用 `WTERMSIG` 宏从其退出状态中提取导致死亡的信号编号。

以下是 `fork` 和 `exec` 示例中的 `main` 函数。这次，父进程调用 `wait` 直到执行 `ls` 命令的子进程完成。

```c
int main() {
    int child_status;

    /* 传递给 "ls" 命令的参数列表。 */
    char *arg_list[] = {
        "ls",
        argv[0], /* 程序的名称。 */
        "-l",
        "/",
        NULL /* 参数列表必须以 NULL 结尾。 */
    };

    /* 产生一个运行 "ls" 命令的子进程。忽略返回的子进程 ID。 */
    spawn("ls", arg_list);

    /* 等待子进程完成。 */
    wait(&child_status);
    if (WIFEXITED(child_status)) {
        printf("子进程正常退出, %d\n", WEXITSTATUS(child_status));
    } else {
        printf("子进程异常退出\n");
    }

    return 0;
}
```

Linux 中还提供了类似的系统调用，它们更灵活，并能提供更多关于退出子进程的信息。`waitpid` 函数可以用于等待特定的子进程，而不是任何子进程。`wait3` 返回关于退出子进程的 CPU 使用统计信息，而 `wait4` 允许你指定关于等待哪些进程的额外选项。

#### 3.4.3 僵尸进程

如果子进程在父进程调用 `wait` 函数时终止，子进程将会消失，其终止状态将通过 `wait` 调用传递给父进程。但当子进程终止而父进程没有调用 `wait` 时会发生什么？它会消失吗？因为关于它的终止的信息——例如是否正常退出以及如果是，退出状态是什么——将会丢失。相反，当子进程终止时，它会变成一个僵尸进程。

僵尸进程已经终止但尚未被清理的进程。清理其僵尸子进程是父进程的责任。`wait` 函数也会执行此，因此在等待子进程之前没有没有跟踪它是否仍在执行。例如，假设一个程序 `fork` 了一个子进程，执行了一些其他计算，然后调用 `wait`。如果子进程在此时尚未终止，父进程将在 `wait` 处阻塞，直到子进程完成。如果子进程在父进程调用 `wait` 之前完成，子进程就会变成僵尸。当父进程调用 `wait` 时，子进程的状态被提取，子进程被删除，`wait` 立即返回。

如果父进程不清理它的子进程会发生什么？它们将作为僵尸进程留在系统中。列表 3.6 中的程序 `fork` 了一个子进程，该子进程立即终止并睡眠一分钟，而没有清理该子进程。

#### Listing 3.6 zombie.c 制造僵尸进程

```c
#include <stdlib.h>
#include <sys/types.h>
#include <unistd.h>

int main ()
{
    pid_t child_pid;

    /* 创建子进程。 */
    child_pid = fork ()
    if (child_pid > 0) {
        /* 这是父进程。睡眠一分钟。 */
        sleep (60);
    }
    else {
        /* 这是子进程。立即退出。 */
        exit (0);
    }
    return 0;
}
```

尝试编译此文件生成一个名为 `make-zombie` 的可执行文件。运行它，并在它仍在运行时，在另一个窗口中通过以下命令列出系统上的进程：

```bash
% ps -e -o pid,ppid,stat,cmd
```

这列出了进程 ID、父进程 ID、进程状态和进程命令行。观察到，除了 `make-zombie` 进程外，还列出了另一个 `make-zombie` 进程。它是子进程；注意它的父 ID 是 `main-zombie` 进程的进程 ID。子进程被标记为 `<defunct>`，其状态码为 `Z`，代表 zombie。

当父进程退出且没有调用 `wait` 时，`main-zombie` 进程结束会发生什么？僵尸进程会留在系统中吗？没有——尝试再次运行 `ps`，注意 `make-zombie` 进程已经消失了。当一个进程退出时，它的子进程会被特殊进程 `init` 程序继承，该程序始终以进程 ID 1 运行（它是 Linux 启动时启动的进程）。`init` 进程会自动清理它继承的僵尸进程。

#### 3.4.4 异步清理子进程

如果你使用子进程执行另一个程序，在父进程中立即调用 `wait` 是可以的，它将阻塞直到子进程完成。通常，你希望父进程继续运行，因为一个或多个子进程正在异步执行。你如何确保清理了已完成的子进程，以免留下消耗系统资源的僵尸进程呢？

一种方法是让父进程定期调用 `wait3` 或 `wait4` 来清理僵尸子进程。为此目的调用效果并不好，因为如果没有子进程终止，调用将阻塞直到有一个终止为止。更优雅的解决方案是使用信号。当子进程终止时，Linux 向父进程发送 `SIGCHLD` 信号。该信号默认处理是什么都不做，但你可以提供一个信号处理程序来清理子进程。这样，父进程可以继续工作并在子进程终止时收到通知。

#### Listing 3.7 sigchld.c 通过处理 CHLD 清理子进程
