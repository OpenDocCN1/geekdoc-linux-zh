
有些组织拥有足够的系统管理员来形成一个松散的分级结构，底部是系统操作员，上方是初级系统管理员和高级管理员，由一名“经理”或“总监”负责。较大的组织层级更加严密。

在其他情况下，系统操作员在大型机和微型机（如 `UNIX` 集群）上工作，网络经理和网络主管负责 `NetWare` LAN 和服务器，系统管理员负责 `UNIX` 和 `Linux` 主机。在其他情况下，这些标题之间没有区别。

关于这些职位名称，似乎没有广泛遵守的相同标准。然而，区分组织中不同的角色是有用的——即使同一个人兼任了许多或所有这些角色。因此，我们做出了如下规定：

系统管理员负责这些程序的构思和实施。他解释政策，建议并实施计划，并研究新技术——通常包括对工具和应用程序进行实操测试和评估。优秀的系统管理员会记录环境。该角色的典型职责包括：

- 执行风险评估
- 准备恢复计划
- 实施备份和测试程序
- 监控并调整性能
- 为系统容量的必要增加制定计划
- 创建脚本以缩短或自动化某些操作；委托并监管其他操作
- 选择监控软件和设备
- 审查并建议系统安全策略和程序
- 选择、安装和配置安全工具
- 协助操作员和帮助台员工处理特殊需求
- 安装和配置新的软件和硬件
- 升级现有软件（或为重大升级准备过渡计划）
- 建议服务器配置

我们使用“网络管理员”这一称号来指那些负责网络基础设施的人，包括路由器、交换机、集线器和布线。系统管理员是网络管理员的客户。

理论上，政策由管理层下发由行政人员执行。经理或总监获得（或协商）一组指令/目标，并将其转化为需求或政策。理想情况下，经理还充当调解员，为他们的 `IT` 部门提供工作所需的资源——并作为与其他经理的联络，处理跨部门问题。

通常，系统管理员与其经理必须协商一份服务水平协议（`SLA`）或规范。这可能是非正式的，也可能是季度/年度目标的形式。一份经过合理同意的服务规范对系统管理员和管理层都有很大好处，因为它有助于系统管理员在冲突的解决方案中确定优先级，并为新的、意外的目标提供合理无模糊的参考。

`IT` 部门的性质可能使其成为其他部门的替罪羊。经常，部门经理会参与“领土争夺”和“推卸责任”。随之而来的辩论和谈判总是不必要的——职责的分配确实在组织之间存在差异，并随着时间而变化。

优秀的经理会在处理这些问题的同时，让系统管理员专注于更技术和更具体的问题。优秀的系统管理员会理解这些问题，并在建议和规划中考虑到它们。

正如我们在第 2 章所示，识别参与方、他们的优先级以及整个过程中的权限链是需求分析过程的重要部分。这对于 `IT` 部门每个人的工作都至关重要。不那么明显的是完成这些任务所投入的工作。

## “供应商”文档

任何操作系统或软件包的主要信息来源始终应该是其自身的文档，无论是打印版还是电子版。它包括帮助页面（传统上在 `UNIX` 中通过 `man` 命令提供，并由 `texinfo` 程序补充）、帮助屏幕、菜单和其他程序内部功能。

由于 `Linux` 不是单一“供应商”的产品，我们发现不同 `GNU`、`Linux` 和开源软件包的文档来自不同的来源并具有多种格式。

`Linux` 文档的开发过程与 `Linux` 本身相同，并以相同的方式发布……大量的 `FAQ` 以及一系列指南（全书）。

这些是 `Linux` 文档的“供应商”来源。`Linux` 初学者的起点是《Linux 安装与入门》。从那里开始，用户可能会学习《Linux 用户指南》，而有志的系统管理员无疑会查阅《Linux 网络管理员指南》和《Linux 系统管理员指南》。

除了这些来源外，大多数 `Linux` 发行版都自带自己的文档。这些可能是打印的（`Red Hat`），有些以电子形式包含（`Debian`），有些可能以两种形式包含（`S.U.S.E.`）。

在所有情况下，请参考你的文档的文档。某些软件包会随着升级和移植而变化。地图并非地形。如果我们的程序与你处的 `man` 或 `texinfo` 页面不一致，很可能是程序行为与文档一致的。最终，程序本身才是“地形”。

关于 `LINUX` 的绝大多数信息可以在网上找到。`LINUX` 是通过互联网进行协作构建的，其文档也遵循同样的模式。

归根结底，`LINUX` 是 `Unix` 的一种实现。因此，大多数关于 `UNIX` 的书籍对 `LINUX` 的适用性不亚于其他版本的 `UNIX`。许多专门为 `LINUX` 编写的文档可以适用于任何其他 `UNIX`——尤其是几乎所有在 `LINUX` 下运行的程序都可以移植到大多数其他 `UNIX` 平台。这就是为什么其他平台上的许多 `UNIX` 专业人士通常会订阅《Linux Journal》，并在工作中参考 `LINUX` 文档项目的 `HOWTO` 指南。

我们只推荐两本值得关注的系统管理书籍：

- Eileen Frisch 编写的《Essential System Administration, 2nd Edition》（第2版）
- Evi Nemeth 等人编写的《Unix System Administration Handbook, 2nd Edition》

`USENET` `comp.unix.admin` 新闻组中最经常被问的问题（`FAQs`）之一是：“我是一个新系统管理员：我应该读哪些书？”答案总是包含这几本书（并希望能包含《Linux System Administration》）。

单个章节中涵盖的许多主题都是整本书的主题。例如，邮件处理和域名命名服务是需要专门书籍的特殊课题。其他特定需求则需要更专业的书籍。出于如此，大多数章节都包含了详尽的建议阅读列表。

`Linux` 系统管理到处都是 `URL`。`LINUX` 是互联网的产物，几乎关于它的所有信息都可以通过万维网获取。然而，网络是巨大的。有了谷歌、`Yahoo!` 和 `Alta Vista` 等搜索引擎，可能很难找到你想要的内容。此外，网络在不断变化。人们改变爱好和/或更换 `ISP`，`ISP` 会倒闭，因此今天某个主题的最佳 `URL` 可能是明天的“404错误”。

# 2 需求分析

对错误的问题采取优雅的方法会产生错误的解决方案。向系统管理员提出要求的用户和经理往往会提出错误的问题，因为他们缺乏“跳树木看森林”的视角。当系统管理员忙于解决表面问题和对浅层症状做出反应时，很容易忽视优先级和目标。因此，系统管理员有责任对业务有深入的理解，以辨别那些排队等待的投诉背后的真实问题。

需求分析是将预期结果转换为规范的过程。管理层制定政策，系统管理员将政策转化为程序和计划（针对操作人员）并提出建议（针对管理层）。系统管理员的投入对于为管理层提供制定政策正确信息是至关重要的。

需求分析的关键在于真正理解我们的经理和用户预期的结果（即使他们自己并不清楚这一点），并管理这些预期或满足这些需求。这样做可以避免许多问题。

归根结底，任何工作或项目都关乎一群人的需求。确定需要满足的人群是弄清楚需要做什么的第一步。然后我们就可以询问他们真正想要什么。例如，用户经常想要新电脑，抱怨他们的电脑太慢了。
