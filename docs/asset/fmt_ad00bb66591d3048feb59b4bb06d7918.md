
```
@me@linux~$ array-2 /usr/bin
/usr/bin
```

`command`。这允许将循环的整个输出管道到 `sort` 命令中。这是必要的，因为数组元素的展开并不是经过排序的。

**第 29–40 行：** 这两个循环与文件循环相似，不同之处它们使用了 `"${array[@]}"` 展开，它展开为数组索引列表，而不是数组元素列表。

## 进程替换 (Process Substitution)

虽然它们看起来相似且都可以用于合并流以进行重定向，但组命令（group commands）和子壳（subshells）之间存在重要区别。组命令在当前 shell 中执行其所有命令，而子壳（顾名思）在当前 shell 的子进程中执行其命令。这意味着环境被复制并传递给子壳的新实例。当子壳退出时，环境的副本就会丢失；在大多数情况下，对子壳环境的任何更改（包括变量赋值）也会丢失。除非脚本需要子壳，否则组命令优于子壳。组命令执行速度更快，且所需的内存更少。

我们在第 28 章中看到过子壳环境问题的示例，当时我们发现管道中的 `read` 命令的作用方式不像我们直觉预期的那样样。回顾一下，如果我们构建如下管道：

```
echo "foo" | read
echo $REPLY
```

`REPLY` 变量的内容是空的，因为 `read` 命令是在子壳中执行的，其 `REPLY` 副本在子壳终止时会被销。

由于管道中的命令始终在子壳中执行，任何分配变量的命令都会遇到此问题。幸运的是，shell 提供了一种名为*进程替换*（process substitution）的特殊展开形式，可以用来解决这个问题。

进程替换有两种表示方式。

对于产生标准输出的进程，它如下所示：

- `(列表)`

对于取标准输入的进程，它如下所示：

- `(列表)`

其中 *list* 是命令列表。

为了解决 `read` 的问题，我们可以这样使用进程替换：

```
read <<(echo "foo")
echo $REPLY
```

进程替换允许我们认为子壳的输出视为用于重定向目的的普通文件。事实上，由于它是展开的形式之一，我们可以检查它的真实值。

```
$me@linuxbox ~$ echo <<(echo "foo")
n/dev/fd/63
```

通过使用 `echo` 查看展开的结果，我们看到子壳的输出是由一个名为 `/dev/fd/63` 的文件提供的。

进程替换经常与包含 `read` 的循环一起使用。这是一个通过子壳处理目录列表内容的 `read` 循环示例：

```bash
#!/bin/bash
while read sub demo of process substitution attr links group size date filename; do cat << EOF
Filename: $filename
Size: $size
Owner: $owner
Group: $group
Modified: $date time
Links: $links
Attributes: $attr
EOF
done <<(ls -l | tail -n +2)
```

循环为目录列表的每一行执行一次。列表本身在脚本的最后一行生成。这一行将进程替换的输出重定向到循环的标准输入。`tail` 命令包含在进程替换管道中，以消除列表中不需要的第一行。

执行该执行时，它产生的输出如下：

```
$me@linuxbox ~ pro-sub head -n 20
Filename: addresses.ldif
Size: 14540
Owner: me
Group: me
Modified: 2009-04-02 11:12
Links: 1
Attributes: -rw-r--

Filename: bin
Size: 4096
Owner: me
Group: me
Modified: 2009-07-10 07:31
Links: 2
Attributes: drwxr-xr-x
Filename: bookmarks.html
Size: 394213
Owner: me
Group: me
```

## 陷阱 (Traps)

在第 10 章中，我们看到了程序如何响应信号。我们也可以将这种功能添加到脚本中。到目前为止编写的脚本不需要这种功能（因为它们的执行时间很短且没有创建临时文件），更大更复杂的脚本可能会从信号处理程序中受益。

在设计大型复杂的脚本时，重要的是考虑用户在脚本运行时注销或关闭电脑会发生什么。当此类事件发生时，信号将发送给所有受影响的进程。例如，我们写了一个在执行期间创建临时文件的脚本。良好的设计是在当脚本完成工作时让其删除该文件。bash 提供了一种用于此目的的机制，称为 `trap`。陷阱通过内置命令 `trap` 实现。`trap` 使用以下语法：

```
trap argument [signal...]
```

其中 `argument` 是一个被读取并视为命令的字符串，`signal` 是触发该命令执行的信号指定。这是一个简单的示例：

```bash
#!/bin/bash

# trap-demo: simple signal handling

trap 'echo I am ignoring you."' SIGINT SIGTERM

for i in {1..5}; do
	echo 'Iteration $i of 5'
	sleep 5
done
```

该脚本定义了一个陷阱，每接收到 SIGINT 或 SIGTERM 信号都会执行 `echo` 命令。当用户在脚本执行期间按下 CTRL-C 时，结果如下：

```
$me@linuxbox]$ trap-demo
Iteration 1 of 5
Iteration 2 of 5
^CI am ignoring you.
Iteration 3 of 5
^CI am ignoring you.
Iteration 4 of 5
Iteration 5 of 5
```

可以看到，每次用户尝试中断程序时，构造一个有用的命令字符串都很麻烦，因此通常的做法是指定 shell 函数作为命令。在这个示例中，为每个处理的信号指定了单独 shell 函数：

```bash
#!/bin/bash

# trap-demo2: simple signal demo

exit_on_signal_SIGINT() {
  echo "Script interrupted." 2>&1
  exit 0
}

exit_on_signal_SIGTERM() {
  echo "Script terminated." 2>&1
  exit 0
}

trap exit_on_signal_SIGINT SIGINT
trap exit_on_signal_SIGTERM SIGTERM
for i in {1..5}; do
  echo "Iteration $i of 5"
  sleep 5
```

此脚本具有两个 `trap` 命令，每个信号一个。每个 `trap` 都指定了一个接收到特定信号时执行的 shell 函数。信号处理函数包含了 `exit` 命令。如果没有 `exit`，脚本将在完成函数后继续。

当用户在执行此脚本期间按下 CTRL-C 时，结果如下：

```
$me@linux~]$ trap-demo2
Iteration 1 of 5
Iteration 2 of 5
^Cscript interrupted.
```

## 临时文件 (TEMPORARY FILES)

脚本中包含处理程序的原因之一是移除脚本执行期间可能创建的用于中间结果的临时文件。命名临时文件有一定的门道。传统上，类 Unix 系统上的程序在 `/tmp` 目录中创建临时文件，这是一个为此文件设计的共享目录。然而，由于该目录是共享的，这引发了某些安全问题，特别是对于具有超级权限的程序。除了为所有用户设置正确权限这一显而易见的步骤外，给临时文件起不可预测的名字很重要。这避免了被称为 temp攻击的利用。创建不可预测但仍具描述名称的一种方法是：

```
tempfile=/tmp/$(basename $).$RANDOM
```

这将由程序名、进程 ID (PID) 和随机整数组成的文件名。但注意，`$RANDOM` 变量返回的值范围为 1–32767，在计算机术中并不大，因此单个变量实例不足以克服坚定的攻击者。

更好的方法是使用 `mktemp` 程序（不要与 chmod 标准函数混淆）来命名和创建临时文件。`mktemp` 程序接受一个参数用于构建文件名。模板应该包含一系列 X 字符，这些字符会被相应数量的随机字母和数字替换。X 字符序列越长，随机字符序列就越长。这是一个示例：

```
tempfile=$(mktemp /tmp/foobar.$$XXXXXXXXXX)
```

这创建了一个临时文件并将其名称赋值给变量 `tempfile`。模板中的 X 字符被随机字母和数字替换，因此最终文件名（在本示例中还包含了用于获取 PID 的特殊参数 `$$` 的展开值）可能如下：

```
/tmp/foobar.6593.00ZuvM654
```
