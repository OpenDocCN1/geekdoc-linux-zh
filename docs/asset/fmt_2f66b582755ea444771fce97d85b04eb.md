### 验证与授权

许多人混淆了验证（authentication）和授权（authorization），有些人甚至认为它们是同义词，但其实不然。为了理解两者的区别，请考虑以下示例。当你想要访问一个国家时，你需要什么？护照和签证。护照是向外国证明你身份的文件。它告诉对方你确实是你所声称的那个人。所以，当你出示护照时，你是在向外国官员验证自己的身份。接下来，你必须证明你被允许（即被授权）进入该外国。这就是签证文件。

现在，用计算机术语来说，`验证`通常涉及提交用户名和密码。用户名和密码成功提交并被接受，表明你就是你所声称的那个人。换句话说，你已经`验证`了自己。

你试图访问的某个给定资源可能除了验证之外还需要授权。例如，如果你在凌晨4点访问计算机，由于系统管理员决定你在那个时间没有被授权访问，计算机可能会拒绝让你进入。同样，你可能被授权从办公室访问受限网站，但不能从家访问，因为公司政策规定网络管理员必须在场地内进行所有受限访问。

#### 了解验证是如何工作的

基本HTTP验证其实相当简单。使用挑战 - 响应机制来验证用户。步骤如图7-1所示并在下面讨论：

1. 当Web浏览器请求由HTTP验证方案保护的URL时，验证开始。这在图中显示为(1)。
2. Web服务器随后返回一个401状态头部，以及一个`WWW-Authenticate`响应头部，这意味着访问该URL需要验证。头部包含正在使用的验证方案（目前仅支持基本HTTP验证）和`realm`名称。这在图中是(2)。

3. 此时，会出现一个Web浏览器对话框，要求用户输入用户名和密码。这在图中是(3)。
4. 用户输入所需用户名和密码并点击确定。然后，浏览器将用户名和密码与之前的URL请求一起发送到服务器。服务器检查用户名和密码是否有效。这在图中是(4)。

> **注意**
>
> 当密码从客户端系统（运行Web浏览器的托管主机）发送时，它既不是以明文发送，也不是加密的。相反，它经过`uuencode`编码并通过Internet传输。这对于这种验证方法来说是不利的，因为任何拥有网络流量嗅探硬件和软件的人都有可能检索到携带`uuencoded`密码的IP数据包。由于`uuencode`是一种广泛使用的数据编码方案，解码器`uudecode`也广泛可用，因此实际上任何人都可以解码`uuencoded`密码并可能滥用它。确实，数据包嗅探器必须能够找到正确的数据包才能进行解码，但技术上是可能的。这就是为什么你绝对不应该将基本HTTP验证用于任何关键应用程序的原因。例如，不要使用此方案来保护你国家的秘密。但是，如果你已经允许`Telnet`或`ftp`访问你的系统，那么你已经在这些服务中使用了与基本HTTP验证非常相似的验证方法。如果你信任你的服务器连接到Internet，并且允许任何人尝试`Telnet`进入，那么你也没有理由不信任这种方法。

5. 如果用户名和密码有效（即真实），服务器返回请求的页面。这在图中是(5a)。如果用户名和密码无效，服务器以401状态响应，并将相同的`WWW-Authenticate`响应头部发送到浏览器。这在图中是(5b)。
6. 在浏览器会话期间对同一服务器的每个后续请求中，浏览器都会发送用户名和密码对，这样服务器就不必为落入网站同一区域下的调用生成401状态头部。例如，如果URL`/apache.nitcc.com/protected/`需要基本HTTP验证，那么对`http://apache.nitcc.com/protected/a=page.html`和`http://apache.nitcc.com/protected/b=page`的后续调用也需要用户名和密码。这就是为什么浏览器在服务器发出另一个验证挑战（即401状态头部和`WWW-Authenticate`响应头部）之前发送这两个信息的原因。这比为每个请求生成挑战并让用户重复输入用户名和密码要快且更实用。

## 通过mod_auth模块对用户进行身份验证

`mod_auth`模块是Apache的默认身份验证模块。该模块允许你验证存储在文本文件中的用户凭据。通常，系统会使用包含用户名和加密密码的文本文件。你还可以使用文本文件创建用户组，这些用户组可用于创建授权规则（将在本章稍后讨论）。建议对少量用户采用基于`mod_auth`的身份验证。通常，当文本文件中的用户名达到数千个时，查找性能就会大幅下降。因此，如果你拥有非常大的用户群，则不建议使用此模块。但是，该模块非常适合大约几百名用户的情况。

你可以使用`/usr/local/apache/bin/httpd -l`来验证此模块是否已编译到你的Apache二进制文件中。如果没有，则需要在`configure`脚本中使用`--enable-module=auth`选项，并重新编译和重新安装你的Apache发行版。

### 理解mod_auth指令

`mod_auth`模块提供了Apache指令`AuthUserFile`、`AuthGroupFile`和`AuthzAuthoritative`。让我们看看这些指令以及使用该模块的一些示例。

#### AuthUserFile指令

此指令设置用于基本HTTP身份验证的用户名和密码所在的文本文件的名称。此指令要求你提供要使用的文件的完全限定路径。

- **语法：** `AuthUserFile filename`
- **上下文：** `Directory`, 每目录访问控制文件(`.htaccess`)
- **覆盖：** `AuthConfig`

例如，以下指令将`/www/mobidac/secrets/.htpasswd`设置为用户名和密码文件：

```apache
AuthUserFile /www/mobidac/secrets/.htpasswd
```

用户名和密码文件通常使用名为`htpasswd`的工具创建，该工具作为支持程序包含在标准Apache发行版中。此文件的格式非常简单。每行包含一个用户名和一个加密密码。密码使用标准`crypt()`函数进行加密。

> **注意**
>
> 重要的是，`AuthUserFile`指定的文件必须位于Web站点的文档树之外。如果将其放在Web可访问的目录内，可能会允许某人下载该文件。

#### AuthGroupFile指令

此指令指定用于基本HTTP身份验证的用户组列表的文本文件。文件名是组文件的绝对路径。你可以使用任何文本编辑器创建此文件。

- **语法：** `AuthGroupFile filename`
- **上下文：** `Directory`, 每目录访问控制文件(`.htaccess`)
- **覆盖：** `AuthConfig`

此文件的格式为：

```text
groupname: username username username [...]
```

例如：

```text
startrek: kirk spock picard data
```

这将创建一个名为`startrek`的组，其中包含四个用户：`kirk`、`spock`、`picard`和`data`。上一节中的注意图标也适用于此指令。

#### AuthAuthoritative指令

如果你对同一目录使用多个身份验证方案，可以将此指令设置为`off`，这样当用户名/密码对在第一方案中失败时，它会传递到下一个（较低）级别。

- **语法：** `AuthAuthoritative On | Off`
- **默认值：** `AuthAuthoritative On`
- **上下文：** `Directory`, 每目录访问控制文件(`.htaccess`)
- **覆盖：** `AuthConfig`

例如，如果你使用`mod_auth_mysql`（将在本章稍后讨论）和标准`mod_auth`模块来提供身份验证服务，并且其中一个模块的用户名/密码对失败，则在可能的情况下，下一个模块将用于验证用户。当用户名/密码对在所有模块中均失败时，服务器会重新发出401状态标头并发送`WWW-Authenticate`响应标头以进行重新身份验证。然而，如果某个模块成功验证了用户名/密码对，较低级别的模块将不会收到该用户名/密码对。

建议保持默认值不变，因为你不应设计一种逐级下传的身份验证方案，即用户可能在一个模块中失败但在另一个模块中通过。

### 在你的Web站点中创建仅限成员的区域

通过使用`mod_auth`指令，你可以在你的Web站点上创建仅限成员的区域，该区域需要基于用户名/密码的身份验证。例如，假设你想创建一个名为`http://your_server_name/memberonly`的仅限成员的区域。以下是操作方法。

1. 确定你想要限制访问的物理目录。大多数人使用`DocumentRoot`指定目录内的一个目录，但你可以使用任何目录，只要Apache用户（由`User`指令设置）被允许读取目录的内容即可。这里，假设你的`DocumentRoot`设置为`/www/mysite/htdocs`，并且你想要限制访问名为`/www/mysite/htdocs/memberonly`的目录。
2. 修改`httpd.conf`文件以创建一个名为`/memberonly/`的新别名，如下所示：

   ```apache
   Alias /memberonly/ "/www/mysite/htdocs/memberonly/"
   ```

3. 接下来，将以下指令添加到`httpd.conf`文件中，以将`/memberonly/`设置为需要用户身份验证的限制区域。

   ```apache
   <Location /memberonly/>
       AuthName "Member-Only Access"
       AuthType Basic
       AuthUserFile /www/secrets/.members
       require valid-user
   </Location>
   ```

   这里，`AuthName`指令只是创建一个标签，该标签由Web浏览器显示给用户。该标签应该是某种有意义的东西，以便用户知道正在请求什么。请务必使用如上所示的双引号。`AuthType`始终设置为`Basic`，因为HTTP默认仅支持`Basic`身份验证。`AuthUserFile`指向一个名为`.members`的密码文件。`Require`指令声明只有有效用户才被允许访问。
4. 现在，使用`htpasswd`工具创建密码文件。假设你已将Apache安装在`/usr/local/apache`，`htpasswd`命令应仅在第一次运行时按如下方式执行：

   ```bash
   /usr/local/apache/bin/htpasswd -c path_to_password_file
   username
   ```

   `-c`选项仅用于创建文件，并且应仅使用一次。例如，要为上述`/memberonly/`配置创建第一个名为`mrbert`的用户，请运行：

   ```bash
   /usr/local/apache/bin/htpasswd -c /www/secrets/.members mrbert
   ```

5. 为确保用户已创建在密码文件中，请使用文本编辑器查看其内容。此外，请确保只有Apache用户（使用`User`指令设置）可以访问此文件。例如，如果你以`httpd`用户身份运行Apache，你可以运行`chown httpd:httpd /www/secrets/.members && chmod 750 /www/secrets/.members`命令，以确保只有`httpd`用户（和组）可以读取此文件。
6. 使用`/usr/local/apache/bin/apachectl restart`命令重启Apache服务器。
7. 现在，使用`http://your_server_name/memberonly/`访问仅限成员的区域；你应该会被要求输入用户名和密码。你应该在显示的对话框中看到`AuthName`的值（“`Member-Only Access`”）。
8. 输入无效的用户名和密码，你应该看到拒绝消息。
9. 最后，再次尝试访问该站点，然后输入由`htpasswd`工具创建的有效用户名和密码。你应该能够访问受限区域。

> **注意**：如果你使用默认的通用日志格式来记录访问，你可以在日志文件中看到已登录的用户名。

#### 使用`.htaccess`文件创建仅限成员的区域

对于诸如互联网服务提供商(ISP)和在同一Web服务器上运行虚拟Web站点的许多部门的大型公司之类的组织，在`httpd.conf`中添加仅限成员的配置（在上一节中已讨论）可能不是一个可管理的解决方案，因为你必须根据各种用户（在ISP设置中）请求此类变更的速度来添加或移除配置。然而，通过使用基于`.htaccess`的身份验证，你可以允许用户或部门创建任意多的仅限成员区域，而无需你的参与——这对于忙碌的系统管理员来说是一种福音。

要对仅限成员的身份验证使用基于`.htaccess`的身份验证，请遵循以下步骤。

1. 在你的`httpd.conf`文件中添加以下指令：

   ```apache
   ```
