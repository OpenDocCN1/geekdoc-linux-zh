
加载器（loader）是一个双刃剑，因为这些代码是未压缩的。然而，通常可以删除大部分代码，这应该是移除代码的地方之一。

## initrd

Linux 内核用于创建小型镜像最有用的特性是 `initrd` 文件系统。最初的设计目的是为了简化 Linux 的安装过程，`initrd` 文件系统允许通过加载内核的同一个存储介质加载一个小型文件系统。最好的是，文件系统以压缩格式存储，内核在运行时将其解压到内存磁盘（RAM disk）。这有助于标准发行版的安装过程，消除了从几十种不同的驱动程序中选择的需求。在 `initrd` 文件系统出现之前，除非驱动程序被编译进内核，否则没有办法启动 Linux。这对于使用 SCSI 控制器的 PC 尤其为困难。与 IDE 不同，每个 SCSI 控制器都有自己的驱动程序。有了 `initrd`，一个压缩的文件系统——包含必要的驱动程序和一个启动脚本——与内核一起从启动介质加载。内核解压这个文件系统并执行 `/init` 文件。一旦脚本退出，`initrd` 文件系统通常会被卸载，内存会被释放，启动过程继续到真正的 `init`。然而，对于嵌入式设备，没有理由退出 `initrd` 文件系统。你的嵌入式应用程序所需的所有软件位于 `initrd` 文件系统中，只要 `/init` 可执行文件运行，内核过程就不会发生。这种技术提供了若干优点。

这些是优点：

- 如果你能让加载器加载内核，你也可以让它加载 `initrd` 文件系统。它们并排存储在加载器读取的介质。
- 与内核不同，`initrd` 像是压缩的。这大幅减少了存储在启动介质上所需的空间。
- 它实际上是一个内存磁盘，因此任何运行时配置更改都不会在重启后保留。

这些是缺点：

- `initrd` 文件系统的配置更改也不会在重启后保留。这意味着任何日志数据或配置信息必须单独存储。你无法通过向 `/etc/passwd` 添加新行来添加用户；`/etc/passwd` 在下次重启期间将会丢失。

# 第2章 极简 Linux

## Shell

从命令行的角度来看

你可能会奇怪，世界上为什么需要一个 shell。如果你想为你的任何应用程序编写脚本，shell 就变得重要了。例如，在第7章的《嵌入式 Linux Workshop》中，大多数基于 Web 的管理软件实际上是用 shell 脚本编写的。

结论是：如果你的应用程序很复杂，它可能有多个可执行文件；你总是希望以同一种方式编写它们的脚本，而 shell 是实现这一点的完美方法。额外的优势是，你用 shell 脚本构建的每个“可执行文件”可能只需要几百字节，但即使是动态的 C 程序也会需要几千字节。

## C 库

嵌入式 Linux 应用程序最大的软件组件之一是动态库。除非你静态链接可执行文件，否则你至少需要 `glibc` 库。你可能还需要其他库。

`glibc` 库包含了标准 UNIX 函数所需的代码，例如 `open()`、`close()`、`read()`、`printf()` 等。在编写时，`glibc` 库经过了剥符号处理（stripped），其大小略大于 1MB。对于嵌入式应用程序来说这太大了，特别是库中有很多代码是没必要的。

目前有两种减少所需库大小的方法。最明显的方法是直接使用另一个库。编写时，有几个替代 `glibc` 的竞争者：`dietlibc`、`Newlib` 和 `uClibc`。另一种缩小库大小的技术是从移除式式应用程序使用的函数。这可以实现，因为所有所需的可执行文件在设备构建时都是已知的。扫描每个可执行文件并编译出一个使用函数列表。在扫描所有可执行文件后，任何不在使用函数列表中的剩余函数可以使用 `objdump` 命令删除。Marcus Brinkmann 为 Debian 启动软盘编写了一个名为 `mklibs.sh` 的脚本来完成此工作。Lineo 有一个类似的 Perl 编写的工具 `lpo`，作为 Lineo SDK 的一部分提供。

## 工具

如果你像我建议的那样使用 shell 编写脚本，那么你必须拥有几个 shell 工具，如 `grep`、`awk` 和 `expr`，以便你能够编写有效的脚本。

这些工具的一个很好的资源是 `BusyBox`。`BusyBox` 最初为 Debian 安装磁盘编写，它在一个小型可执行文件中包含了你需要的许多工具。该二进制文件与它可以运行的每个程序都建立了符号链接，因此你使用 `BusyBox` 时不需要对脚本进行任何奇怪的操作。例如，如果你运行 `grep`，文件系统会查看 `grep` 的目录条目，发现它是 `BusyBox` 的符号链接。

### C 编译器

如果不使用 `-O`，编译器会将被声明为 `register` 的变量分配到寄存器中。

生成的编译代码比使用 `-O` 的 GNU C 编译器（`GCC`）生成的代码稍微差一点。

使用 `-O` 时，编译器会尝试减小代码体积和执行时间。

当你指定 `-O` 时，编译器会在所有机器上开启 `-fthread-jumps` 和 `-fdeeperpop`。在具有延迟槽位（delay slots）的机器上，编译器会开启 `-delayed-branch`；在支持不使用帧指针即可进行调试的机器上，则会开启 `-fomit-frame-pointer`。在某些机器上，编译器还会开启其他标志。

- `-O2`

进一步优化。GNU C 编译器执行了几乎所有支持的、不涉及空间/速度权衡的优化。当你指定 `-O2` 时，编译器不会进行循环展开（loop unrolling）或函数内联（function inlining）。与 `-O` 相比，此选项增加了编译时间并提升了生成代码的性能（循环展开和函数内联除外）。它还会在所有机器上开启 `-fforce-mem` 选项，并在不影响调试的机器上消除帧指针。

- `-O3`

进一步优化。`-O3` 在开启 `-O2` 指定的所有优化的基础上，还会开启内联函数（inline-functions）选项。

- `-Os`

针对大小进行优化。`-Os` 开启了通常不会增加代码体积的 `-O2` 优化。大多数情况下，`-Os` 是嵌入式应用的最佳选择。

遗憾的是，这意味着你必须自己编译大部分二进制文件。你还需要修改 `configure` 脚本或其生成的 `Makefile`。如果应用程序编写者能将为 `configure` 添加一个 `--compile-small` 选项作为标准做法，将非常有帮助。

### 无优化对比 `-O3` 或 `-Os`

`Proc2()` 是 `dhtstone` 基准测试中重要的函数之一（参见列表 2.1 至 2.4）。它被一个内部循环调用，其本身包含一个可以运行多次的循环。即使你没有汇编语言背景，也可以了解不同优化级别下，该循环产生的 i386 汇编代码指令的复杂度，从而看到 C 编译器如何减少达到相同结果所需的指令数量。

### 列表 2.1 C 代码

```c
int IntGlob;
char Char1Glob;

void Proc2(int *IntPar10){
    int IntLoc;
    int EnumLoc;

    IntLoc = *IntPar10 + 10;
    for (;;) {
        if (Char1Glob == 'A') {
            --IntLoc;
            *IntPar10 = IntLoc - IntGlob;
            EnumLoc = 1;
        }
        if (EnumLoc == 1) break;
    }
}
```
