
这里最大的问题是速度。现在，如果只进行了几次分配，那么速度将不是大问题。但请想想如果你进行了一千次分配会发生什么。在第 1000 次分配时，你必须搜索 999 个内存区域才能发现你需要请求更多内存。如你看到的，这变得非常慢。此外，请记住 Linux 可以将内存页留在磁盘上而不是内存中。因此，由于你必须遍历程序的每一部分内存，这意味着 Linux 必须将当前在磁盘上的每部分内存加载进来以检查它是否可用。你可以看到这有多慢。

```
cmpl %edx, %ecx

```

如果请求的大小小于或等于当前区域的大小，我们就可以使用这个块。当前区域比请求的尺寸大关系，因为额外的空间将不会被使用。所以，让我们跳转到 `allocate_here` 看看发生了什么：

```
movl $UNAVAILABLE, HDR_AVAIL_OFFSET(%eax)
addl $HEADER_SIZE, %eax
movl %ebp, %esp
popl %ebp
ret
```

它将内存标记为不可用。然后它将指针 `%eax` 移动过头部，并将其作为函数的返回值。请记住，使用此函数的人甚至不需要知道我们的内存头部记录。他们只需要指向可用内存的指针。

好了，假设区域不够大。那该怎么办呢？那么，我们将到达标记为 `next_location` 的代码。每当我们发现当前内存区域无法分配内存时，就会使用这段代码。它做的仅仅是将 `%eax` 推进到下一个可能的内存区域，并回到循环开始。请记住 `%edx` 持有当前内存区域的大小，而 `HEADER_SIZE` 是内存区域头部大小的符号。所以这段代码将我们移动到下一个内存区域：

```
addl $HEADER_SIZE, %eax
addl %edx, %eax
jmp alloc_loop_begin
```

然后函数运行另一个循环。

每当你有一个循环时，你必须确保它总是结束的。最好的方法是检查所有可能性，并确保所有这些最终都会导致循环结束。在我们的情况下，有以下几种可能性：

- 我们将到达堆的末尾
- 我们将找到一个可用且足够大的内存区域
- 我们将前往下一个位置

前两项是会导致循环结束的条件。第三项会让循环继续。然而，即使我们找到了一个空闲区域，最终也会到达堆的末尾，因为它的尺寸有限的。因此，我们知道无论哪种条件成立，循环最终都将遇到终止条件。

### deallocate 函数

`deallocate` 函数比 `allocate` 函数要简单得多。这是因为它不需要进行任何搜索。它只需要将当前内存区域标记为 `AVAILABLE`，`allocate` 在下次被调用时就会找到它。所以我们有：

```
movl ST_MEMORY_SEG(%esp), %eax
subl $HEADER_SIZE, %eax
movl $AVAILABLE, HDR_AVAIL_OFFSET(%eax)
ret
```

在这个函数中，我们不需要保存 `%ebp` 或 `%esp`，因为我们没有改变它们，也不需要在最后恢复它们。我们所做的只是从栈中读取内存区域的地址，回退到头部开头，并将区域标记为可用。此函数没有返回值，所以我们不在乎在 `%eax` 中留下了什么。
