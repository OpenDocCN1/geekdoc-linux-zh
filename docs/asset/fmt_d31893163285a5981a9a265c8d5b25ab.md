
经常将 `Make` 用于构建可执行文件以外的其他用途。它是一个通用的项目管理工具。例如，我目前在使用 `makefile`，这样当我想预览这本书时，不需要删除大量文件然后运行 `LaTeX`、`MakeIndex`。考虑以下 `makefile`：

```
foo: foo.c
	gcc foo.c -o foo
```

```
clean:
	rm *.o
	rm foo
```

`clean` 目标没有依赖项，因此只有在命令行中特别指定时才会构建。

所有的对象文件以及可执行文件 `foo` 都将被删除，因此其目的是强制重新构建项目。为了方便起见，程序员通常会在 `Makefile` 中包含一个 `clean` 目标。

从更广泛的意义上说，`Make` 通常用作复杂命令的简单接口。用于此目的的目标实际上并不描述构建过程，而是当请求该目标时执行的一系列命令。但如果这样一个“伪目标”与当前目录下的某个文件同名呢？例如，如果有一个名为 `clean` 的文件，`Make` 将检测到该文件存在，并决定不构建该目标。

`Make` 提供了一个特殊的伪目标 `.PHONY` 用于此目的。`.PHONY` 像其他目标一样接受依赖列表，但没有构建规则。`.PHONY` 的依赖项被标记为伪目标，无论是否存在同名文件，在被请求时始终会被构建。以下是之前的 `makefile`，重写为使用 `.PHONY` 目标后的。

```
foo: foo.c
gcc foo.c -o foo
```

```
clean:
rm *.o
rm foo
```

## 错误处理

在发生错误时，`Make` 会立即停止并打印错误信息。`Make` 通过执行的规则的返回码来检测错误：返回码零表示成功，任何其他值均表示错误。大多数 `UNIX` 命令都遵循这一约定。如果 `Makefile` 本身存在语法错误，`Make` 将对此报错并退出。

# LINUX 开发工具

## 使用库

库提供了一种将代码封装成可重用二进制模块的方法。`Linux` 软件可以使用两种库：静态库和共享库。静态库仅仅是对象文件的集合，它们被归档到一个带有符号表的文件中。静态库的文件扩展名为 `.a`，它们可以像普通对象文件一样链接到程序中。共享库与静态库类似，区别在于它永久地存在独立的文件中，永远不会直接链接到应用程序中。共享库由操作系统的动态链接器在运行时进行链接。

### 静态库

静态库的创建和使用非常简单。一旦你创建了想要封装为库的对象文件，使用实用工具将它们合并：

```
$ ar .a file1.o file2.o file3.o
```

`ar` 是一个简单的归档工具。`r` 选项指定了一种操作模式：它告诉 `ar` 将文件添加到归档中，替换任何同名的现有文件。`c` 选项指定如果归档不存在则应创建它。最后，`s` 告知 `ar` 这是一个对象文件的归档，即静态库，并且应该添加符号表。可选情况下，你可以省略 `s` 标志并使用 `ranlib` 实用来添加符号表；生成的文件是等效的。

要使用静态库，只需像传递普通对象文件一样将其传递给 `gcc`。`gcc` 会将 `.a` 文件扩展识别为对象文件的归档。

### 共享库

共享库的管理比静态库稍微复杂一些，但它们通常值得付出额外努力。共享库并不存储在使用它们的可执行文件内部；它们是独立的文件，在运行时被链接到可执行文件中。在许多情况下，可以在不重新编译依赖它们的程序的情况下更新共享库。操作系统可以实现一个共享库加载到内存中一次，供多个应用程序使用。

## 第2 章

共享库遵循非常特定的命名方案，旨在将不兼容的版本隔离开。每个共享库应该赋予一个唯一的基名称，或 `soname`，格式为 `libFooBar.so.n`，其中 `n` 是主版本号。每当破坏向兼容性时，主版本号就应该增加。要版本号和修订号表示不应影响兼容性的微改被添加到基名称的末尾，因此最终名称看起来像 `libFooBar.so.2.1.3`。

`ldconfig` 实用工具对可能存在的各种版本的库进行规范检查。它在特定的目录集中搜索库，这些目录通常在 `/etc/ld.so` 或环境变量 `LD_LIBRARY_PATH` 中指定。它找到的每个符合 `libSomething.so.m.r` 格式命名的库都会为 `libSomething.so.m` 创建一个符号链接。如果两个库具有相同的基名称，`ldconfig` 会创建一个指向后续版本的符号链接。应用程序引用这些符号链接而不是库的全名。如果安装了库的新版本，`ldconfig` 会更新符号链接，所有使用该库的应用程序将自动引用新版本。

### 创建共享库

共享库的创建非常简单。首先，使用 `-fPIC` 标志将你的源码编译为对象文件。这会导致 `gcc` 输出位置无关代码，这种代码对动态链接器更加友好。然后使用 `-shared` 标志链接 `gcc`。你还需要告知链接器你想要使用的 `soname`。要查看如何操作，请看以下示例：

```
$ gcc -fPIC foo bar.c
$ gcc -shared -Wl,soname,libFooBar.so.1 foo.o bar.o -o \
    libFooBar.so.1.1.1
$ su
Password:
# install -m 0755 libFooBar.so.1.1.1 /usr/lib
# ldconfig
# ln -s /usr/lib/libFooBar.so.1 /usr/lib/libFooBar
# exit
```

第一条命令产生对象文件 `foo.o` 和 `bar.o`，第二条创建共享库。注意使用 `-W1` 标志来发送选项。

### 使用共享库

`dlopen()` 是使用共享库的另一种方法。该接口允许你手动打开并访问对象文件。例如，假设 `libfoo.so` 是一个包含函数的共享对象文件。以下示例将打开文件并调用该函数：

```
#include <dlfcn.h>
/* dlfcn.h 提供了 dlopen() 接口 */

int main()
{
    void *handle;
    void (*bar)(void);

    /* 打开库并保存句柄 */
    handle = dlopen("libfoo.so", RTLD_NOW);
    if (handle == NULL) {
        /* dlerror() 返回错误信息 */
        printf("dlopen failed: %s\n",dlerror());
        return 1;
    }

    /* 尝试找到 bar() 的地址 */
    bar = dlsym(handle,"bar");
    if (bar == NULL) {
        printf("dlsym failed: %s\n",dlerror());
        return 1;
    }

    /* 很好，我们找到了 bar()，所以调用它 */
    bar();

    /* 关闭 libfoo.so */
    dlclose(handle);
    return 0;
}
```

`dlopen` 中的 `RTLD_NOW` 标志表示 `dlopen` 应该立即尝试共享库依赖的所有符号。另一个选项是 `RTLD_LAZY`，它指示链接器在遇到符号时进行解析。

有时动态加载的库需要访问父应用程序中的符号。为了允许这些符号被解析，编译应用程序时使用 `--dynamic` 和 `--export-dynamic` 选项。正确的语法是 `-w,--export-dynamic.`。`--export-dynamic` 允许共享库中未解析的符号与父应用程序中的符号匹配，而 `--export-dynamic` 选项指示链接器生成适用于此目的的额外符号信息。

## Linux 链接特性

`Linux` 链接器 `GNU ld` 是一个复杂但奇特的工具。虽然对 `ld` 的完整讨论远超出本书的范围，但这些提示可能会让你的生活变得轻松。

`ld` 以及 `gcc` 对命令行中指定库和目标文件的顺序非常敏感。如果 `libfoo.so` 依赖于 `libbar.so`，你必须先指定 `libfoo.so`。原因在于 `ld` 仅将未解析的符号视为链接项进行跟踪。如果 `libfoo.so` 和 `libbar.so` 相互依赖，则必须对其中一个库指定两次，例如 `-lfoo -lbar -lfoo`。这与 `Visual C++` 链接器的行为不同，并且在从 `Windows` 移植游戏时会导致很多头疼的问题。如果链接器找不到某个符号，而你又确定已经给它提供了正确的库，请双倍检查它们在命令行中的指定顺序。

`Linux` 运行时链接器在处理 `setuid root` 可执行文件时不会遵循 `LD_LIBRARY_PATH` 环境变量。这有点让人困扰，但对于安全至关重要。

名称冲突非常烦人，因为它们可能极其难以追踪。`-warn-common` 标志会在对象文件之间合并符号时打印警告。

最后，请记住 `Linux` 发行版不认为 `/usr/local/lib` 是库目录，因此放置在该处的任何库都将无法访问。你可以通过编辑 `/etc/ld.so.conf` 来修复此。在编辑库路径列表后，记得运行 `ldconfig` 程序。

## 调试 Linux 应用

`Linux` 的编程环境提供了交互式调试的支持。`gcc` 编译器可以生成调试符号信息，并且有多个调试器可用。

### 为调试编译

为了让调试器以人类有用的方式分析可执行文件的行为，它需要确定程序变量和函数入口点的精确位置。这需要编译器的帮助；应用程序必须专门为调试进行编译，否则符号调试器将毫无用处。要编译具有必要的调试支持的程序，请使用 `-ggdb` 标志：

```
$ gcc -ggdb foo.c -o foo
```

在调试时禁用优化是一个好主意，即不要使用 `-O3` 选项。虽然 `gcc` 和 `gdb` 允许你调试优化过的可执行文件，但结果可能会有点意外。

尽管程序员有时会使用 `-fomit-frame-pointer` 编译器选项以提高性能，但该选项在大多数情况下与调试是不兼容的。为调试编译可执行文件会增加其体积并极可能降低其性能；用于公开发的可执行文件不应为调试进行编译。

### gdb

`GNU` 调试器被称为 `gdb` 是 `Linux` 的主要调试器。它允许你单步执行程序、在程序运行时检查变量，并分析核心文件。`gdb` 是极其强大的工具，但它的界面可能会让初学者不知所措。

`gdb` 是一个基于文本的交互式调试器。一旦程序加载到调试器中，`gdb` 会接受命令来引导程序的运行。输入 `help` 可查看类型索引。

### 一个简单的示例

以下程序应该打印从 0 到 9 的数字。然而，它有一个 `bug`。在 `for` 循环后面多了一个分号，导致 `printf` 语句与循环分开了。

```c
#include <stdio.h>

int main() {

    int i;
    for (i = 0; i < 10; i++) {
        printf("Counter is now %i\n",i);
    }
}
```

首先，编译程序并测试：

```
$ gcc -ggdb buggy.c -o buggy
$ ./buggy
Counter is now 10
```

要将程序加载到 `gdb`，请在命令行中传递程序的名称：

```
$ gdb buggy
GNU gdb 4.18
Copyright 1998 Free Software Foundation, Inc.
license notice removed
```

设置断点然后启动程序：

```gdb
(gdb) b main
Breakpoint 1 at 0x80483d6: file buggy.c, line 6.
(gdb) r
Starting program: /home/overcode/book/test/buggy
```

```gdb
Breakpoint 1, main () at buggy.c:6
6     for (i = 0; i < 10; i++);
```

`b` 命令设置断点。`r` 启动程序。使用 `n` 单步执行：

```gdb
(gdb) n
7     printf("Counter is now %i
```

查看源码：

```gdb
(gdb) list
3     int main()
4     {
5         int i;
6         for (i = 0; i < 10; i++);
7             printf("Counter is now %i\n");
8         return 0;
9     }
```

### 访问数据

`gdb` 可以返回当前作用范围内任何变量的值。它还可以在程序运行时修改变量。查看变量请使用 `p` 命令。`p foo` 将返回 `foo` 的当前值。还有一个 `printf` 命令，其行为类似于 `C` 语言中的同名函数。修改变量使用 `set varname=value` 命令。

程序员经常需要跟踪在程序运行过程中变化的变量。通过 `gdb`，你可以定义一个每次程序挂起时显示的变量列表。`display` 命令将变量添加到列表中，`undisplay` 命令将其移除。
