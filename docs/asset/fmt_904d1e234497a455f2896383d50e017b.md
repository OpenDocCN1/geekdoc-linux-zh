
我们的脚本现在不再使用 `echo`，而是使用 `cat` 和“在此文档”。字符串 `EOF`（意为文件结束，即 end-of-file，一种惯例）被选择为标记，并标志着嵌入文本的结束。注意，该行末尾不能有空格。

那么，使用“在此文档”的优势是什么？它大部分与 `echo` 相同，区别在于默认情况下，“在此文档”内部的单引号和双引号对 shell 来说失去了意义。这是一个命令行示例：

```
me@linux ~$ foo="some text"

me@linux ~$ cat << _EOF_

$foo

"foo"

'$foo'

\foo

_EOF_

some text

"some text"

'some text'

$foo
```

如我们所见，shell 不忽略引号。它将其视为普通字符。这允许我们能够在“在此文档”中自由地嵌入引号。这对我们的报告程序可能非常有用。

“在此文档”可以配合任何接受标准输入的命令。在示例中，我们使用“在此文档”向 `ftp` 程序传递一系列命令，以从远程 FTP 服务器检索文件：

```bash
#!/bin/bash
## 通过 FTP 获取文件的脚本

FTP_SERVER=ftp.nl.debian.org
FTP_PATH=/debian/dists/lenny/main/installer-i386/current/images/cdrom
REMOTE_FILE=debian-cd_info.tar.gz

ftp -n << EOF
$FTP_SERVER
user anonymous me@linuxbox
cd $FTP_PATH
hash
get $REMOTE_FILE
bye
EOF

ls -l $REMOTE_FILE
```

如果我们将重定向运算符从 `<<` 改为 `<<-`，shell 将忽略“在此文档”开头的制表符字符。这允许“在此文档”进行缩进，从而提高可读性：

```bash
#!/bin/bash
## 通过 FTP 获取文件的脚本

FTP_SERVER=ftp.nl.debian.org
FTP_PATH=/debian/dists/lenny/main/installer-i386/current/images/cdrom
REMOTE_FILE=debian-cd_info.tar.gz

ftp -n <<- EOF
	$FTP_SERVER
	user anonymous me@linuxbox
	cd $FTP_PATH
	hash
	get $REMOTE_FILE
	bye
EOF

ls -l $REMOTE_FILE
```

## 自顶向下设计

随着程序变得越来越大和复杂，设计、编码和维护它们变得越来越困难。与任何大型项目一样，将大型复杂的任务分解为一系列简单的小任务通常是一个好主意。

想象我们正在尝试描述一个常见的过程——去市场——细化这些步骤，直到去市场的整个过程被完全定义。这种识别顶层步骤并开发这些步骤的更详细视图的过程被称为自顶向下设计。这种技术允许我们将大型复杂的任务分解为许多简单任务。自顶向下设计是一种设计程序的常用方法，特别适用于简单编程。在本章中，我们将使用自顶向下设计进一步开发我们的报告脚本。

## Shell 函数

我们的脚本目前执行以下步骤生成 HTML 文档：

1. 打开页面
2. 打开页头
3. 设置标题
4. 打开正文
5. 打开正文
6. 输出标题
7. 输出时间
8. 关闭正文
9. 关闭页面
10. 关闭页头
11. 关闭标题
12. 主程序开始
13. 调用 shell 函数
14. 最后的 `echo` 命令

我们将为脚本添加基本的函数定义：

```bash
#!/bin/bash
# 输出系统信息页的程序

TITLE="System Information Report For $HOSTNAME"
CURRENT_TIME=$(date +"%x %Z")
TIME_STAMP="Generated $CURRENT_TIME, by $USER"

report_uptime() {
    return
}

report_disk_space() {
    return
}

report_home_space() {
    return
}

cat << _EOF_
<HTML>
<HEAD>
<TITLE>$TITLE</TITLE>
</HEAD>
<body>
<p>$TIME_STAMP</p>
${report_uptime}
${report_disk_space}
${report_home_space}
</body>
</HTML>
_EOF_
```

当 shell 读取脚本时，它会跳过第 1 到 11 行，因为这些行由注释和函数定义组成。执行从第 12 行开始，即 `echo` 命令。第 13 行调用 shell 函数，shell 会像执行任何其他命令一样执行该函数。程序控制移动到第 6 行并执行第二个命令。接下来执行第 7 行。它的 `return` 命令终止函数并将控制返回到函数后的行（第 14 行），然后执行最后的 `echo` 命令。

## 局部变量

在我们目前为止编写的脚本中，所有的变量（包括常量）都是全局变量。全局变量在整个程序运行期间都存在。这对于很多事情没有问题，但有时会使 shell 函数的使用变得复杂。在 shell 函数内部，通常希望使用局部变量（local variables）。局部变量仅在定义它的 shell 函数内部可访问，一旦该 shell 函数终止，它们就会消失。

使用局部变量允许程序员使用可能在脚本全局范围或其他 shell 函数中已经存在的变量名，而无需担心潜在的命名冲突。

下面是一个示例脚本，演示了如何定义和使用局部变量：

```bash
#!/bin/bash
## local-vars: 演示局部变量的脚本

foo=0      # 全局变量 foo

funct_1 () {
    local foo      # 变量 foo 对 funct_1 局部
    foo=1
    echo "funct_1: foo = $foo"
}

funct_2 () {
    local foo      # 变量 foo 对 funct_2 局部
    foo=2
    echo "funct_2: foo = $foo"
}

echo "global: foo = $foo"
funct_1
echo "global: foo = $foo"
funct_2
echo "global: foo = $foo"
```

我们可以看到，局部变量是通过在变量名前面加上 `local` 单词定义的。这创建了一个对于定义它的 shell 函数局部的变量。一旦脚本退出该 shell 函数，该变量就不再存在了。当我们运行此脚本时，看到了如下结果：

```
[me@linux~$] local-vars

global: foo = 0

funct_1: foo = 1

global: foo = 0

funct_2: foo = 2

global: foo = 0
```

我们看到，在两个 shell 函数内部对局部变量 `foo` 赋值对函数外部的 `foo` 的值没有影响。

这一特性允许编写 shell 函数时使它们之间以及与它们所处的脚本之间保持独立性，这非常有价值，因为有助于防止程序的某部分与另一部分产生干扰。它还允许编写 shell 函数时具有可移植性。也就是说，根据需要可以在不同脚本之间进行剪切粘贴。

## 保持脚本运行

在开发程序时，保持程序处于可运行状态是有用的。通过这样做并频繁测试，我们可以在开发过程的早期检测到错误。这将使调试问题变得更容易。例如，如果我们运行程序、进行微小的更改、再次运行程序并发现问题，那么最近的更改很可能是程序的根源。通过添加称为存根（stubs）的空函数，我们可以在早期验证程序的逻辑流。在构建存根时，最好的做法是包含一些能向程序员提供反馈的内容，显示逻辑流正在执行。如果我们现在查看脚本的输出，会发现在时间戳之后的输出中有一些空行，但我们无法确定原因。

me@linuxbox ~$ sys_info_page

<TITLE>System Information Report For twin2</TITLE>

</HEAD>

<BODY>

<h1>System Information Report For linuxbox</h1>

<P>Generated 03/19/2012 04:02:10 PM EDT, by me</P>
