
要通过 Web 浏览器访问该脚本，我请求以下 URL：

`http://wormhole.nitec.com/~kabir/test.pl`

CGI 脚本只有在通过 `suEXEC` 执行的所有安全检查后才会执行。`suEXEC` 还会在其日志文件中记录脚本请求。我的请求的日志条目如下：

`[2000-12-01 16:09:22] aid: (kabir/kabir) gid: (kabir/kabir) cmd: test.pl`

如果您真的想知道脚本是否在用户的 UID 下运行，请在 `foreach` 循环中插入一个 `sleep` 命令（如 `sleep(10);`）。这将减慢执行速度，并允许您在 Web 服务器控制台上运行 `top` 或 `ps` 等命令，以找出运行 `test.pl` 的进程的 UID。您也可以使用 `chown` 命令更改脚本的所有权。尝试通过 Web 浏览器访问该脚本，并查看 `suEXEC` 记录的错误消息。例如，当我按如下方式更改 `~kabir/public_html` 目录中 `test.pl` 脚本的所有权时，

`chown root test.pl`

我遇到了一个服务器错误，日志文件显示如下行：

```
[2000-12-01 16:00:22]  uid/gid (500/500) mismatch with
directory (500/500) or program (0/500)
```

这里，该程序由UID 0拥有，而组仍然是kabir (500)，因此`suEXEC`拒绝运行它，这意味着`suEXEC`正在执行其应有的功能。

为了确保`suEXEC`将在其他目录中运行`test.pl`程序，我在`~kabir/public_html`中创建了一个`cgi-bin`目录，并将`test.cgi`放在该目录中。确定新目录和文件的用户和组所有权均设置为用户ID `kabir`和组ID `kabir`后，我使用以下命令访问了该脚本：

`http://wormhole.host.com/~kabir/cgi-bin/test.pl`

如果您有虚拟主机，并希望使用`suEXEC`运行CGI程序和/或SSI命令，则必须在`<VirtualHost>`标记内使用`User`和`Group`指令。将这些指令设置为Apache服务器当前运行时所用的用户和组ID之外的其他ID。如果为`<VirtualHost>`容器仅指定了其中一个指令，或两者均未指定，则将假定为服务器用户ID或组ID。

出于安全和效率的原因，所有`suEXEC`请求必须保持在虚拟主机请求的顶级文档根目录或用户ID请求的一个顶级个人文档根目录内。例如，如果您配置了四个虚拟主机，则需要将所有虚拟主机文档根目录构建在一个主Apache文档层次结构下，以便为虚拟主机利用`suEXEC`。

## CGIWrap

`CGIWrap`类似于`suEXEC`程序，因为它允许用户使用CGI应用程序，而不会危及Web服务器的安全。CGI程序以文件所有者的权限运行。此外，`CGIWrap`会对CGI应用程序执行多项安全检查，如果任何检查失败，则不会执行。

`CGIWrap`由Nathan Neulinger编写。`CGIWrap`的最新版本可从主要FTP站点`ftp://ftp.cc.umn.edu/pub/cgi/cgiwrap/`获取。`CGIWrap`通过HTML文档中的URL使用。在分发版中，`CGIWrap`被配置为运行位于`~/public_html/cgi-bin/`目录中的用户脚本。

`CGIWrap`作为`gzip`压缩的`tar`文件分发。您可以使用`gzip`解压缩，并使用`tar`实用程序提取。

运行`Configure`脚本，它将提示您回答许多问题。这些问题大多不言自明。另请注意，此包装程序中有一项功能与`suEXEC`不同。它允许您创建`allow`和`deny`文件，可用于限制对CGI应用程序的访问。这两个文件具有相同的格式，如下所示：

- 用户ID

- 用户名@子网1/掩码1, 子网2/掩码2 ...

您可以拥有单个用户名（非数字UID）或`user ID@subnet/mask`行，其中可以定义一个或多个`subnet/mask`对。例如，如果在`allow`文件中找到以下行（您指定文件名），

```
Myuser@1.2.3.4/255.255.255.255
```

用户`kabir`的CGI应用程序允许由属于206.171.50.0网络（网络掩码255.255.255.0）的主机运行。

运行`Configure`脚本后，您必须运行`make`实用程序以创建`CGIWrap`可执行文件。

要使用包装器应用程序，请将`CGIWrap`可执行文件复制到用户的`cgi-bin`目录中。请注意，此目录必须与您在配置过程中指定的目录匹配。最简单的方法是为CGI应用程序目录保留`~username/public_html/cgi-bin`类型的目录结构。

复制`CGIWrap`可执行文件后，请按如下方式更改所有权和权限位：

```
chown root CGIWrap
chmod 4755 CGIWrap
```

在`cgi-bin`目录中创建三个名为`nph-cgiwrap`、`nph-cgiwrapd`和`cgiwrapd`的硬链接或符号链接，链接到`CGIWrap`，如下所示：

```
ln [-s] CGIWrap cgiwrapd
ln [-s] CGIWrap nph-cgiwrap
ln [-s] CGIWrap nph-cgiwrapd
```

在我的Apache服务器上，我仅将`cgi`扩展名指定为CGI应用程序；因此，我将`CGIWrap`可执行文件重命名为`cgiwrap.cgi`以使其工作。如果您有类似的限制，可以尝试此方法或改为创建链接。

现在，按如下方式执行CGI应用程序：

```
http://yourdomain.com/cgi-bin/cgiwrap/username/scriptname
```

例如，要访问`wormhole.nitec.com`站点上用户`kabir`的CGI应用程序`test.cgi`，我必须使用以下内容：

```
http://wormhole.nitec.com/cgi-bin/cgiwrap/kabir/test.cgi
```

如果您想查看CGI的调试输出，请指定`cgiwrapd`而不是`CGIWrap`，如以下URL所示：

```
http://www.yourdomain.com/cgi-bin/cgiwrapd/username/scriptname
```

如果脚本是`nph`风格的脚本，则必须使用以下URL运行它：

```
http://www.yourdomain.com/cgi-bin/nph-cgiwrap/username/scriptname
```

## 降低服务器端包含风险

如果您使用SSI命令（如`exec`）运行外部应用程序，则安全风险与CGI应用程序几乎相同。但是，您可以使用`Options`指令在Apache中轻松禁用此`exec`命令，如下所示：

```
<Directory />
Options Includes=NOEXEC
</Directory>
```

这将在您的整个Web空间中禁用`exec`和`includes` SSI命令；但是，您可以通过定义范围更窄的目录容器，在必要时启用这些命令。以下是一个示例：

```
<Directory />
Options Includes=NOEXEC
</Directory>

<Directory "/ssi">
Options +Includes
</Directory>
```

此配置段在除`/ssi`目录以外的所有位置禁用`exec`命令。

## 使用SSL进行安全交易

Web上的电子商务正以惊人的速度蓬勃发展。许多公司维护电子商务网站以在互联网上开展业务。电子商务网站的一个先决条件是具备安全交易能力，这由安全套接字层（SSL）提供。目前Apache有多种第三方SSL软件可供选择。表12-5将帮助您选择适合您需求的软件。

### 表12-5 Apache的SSL解决方案

| 软件 | 分发方式 | 评论 |
| :--- | :--- | :--- |
| Apache-SSL | 免费 | 不推荐，因为它不是最简洁的解决方案。Apache-SSL基本上是一组Apache补丁，文档不太完善。 |
| mod_ssl | 免费 | 一个简洁的解决方案。虽然部分基于Apache-SSL，但它更简洁且文档更完善。作者推荐。 |
| Red Hat Secure Server | 商业 | 最便宜的商业解决方案。基于`mod_ssl`模块。 |
| Raven SSL模块 | 商业 | 价格适中的解决方案。 |
| Stronghold Web Server | 商业 | 作者最喜欢的用于严肃电子商务网站的SSL解决方案。它是最昂贵的商业选项。 |

`mod_ssl`模块不仅比Apache-SSL方法更简洁，而且是免费的。虽然它部分基于Apache-SSL，但它是Ralf S. Engelschall编写的另一个文档完善的模块。如果您使用的是最新版本的Apache，我建议使用它。
