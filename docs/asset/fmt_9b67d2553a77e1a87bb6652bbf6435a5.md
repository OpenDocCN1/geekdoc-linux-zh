
```bash
% gcc -fPIC test1.c
```

`-fPIC`选项告诉编译器你将把`test.o`作为共享对象的一部分使用。

#### 位置无关代码 (Position-Independent Code)

`PIC`代表位置无关代码。共享库中的函数在不同的程序可能被加载到不同的地址，因此共享对象中的代码不能依赖于它加载时的地址（或位置）。这种考虑对你（程序员）没有影响，除非你忘记在编译将用于共享库的代码时使用`-fPIC`标志。

### 2.3 编写与使用库

然后，你将对象文件合并成共享库，如下所示：

```
% gcc -shared -fPIC -o libtest.so test1.o test2.o
```

`-shared`选项告诉链接器生成共享库而不是普通的可执行文件。共享库使用`.so`扩展名，代表共享对象（shared object）。与静态库一样，它的名称始终以`lib`结尾，以指示该文件是一个库。

与共享库链接非常简单。例如，如果`libtest.so`存在于当前目录或系统的标准库搜索目录之一，下行命令将与其链接：

```
% gcc -o app app.o -L. -ltest
```

假设`libtest.a`和`libtest.so`都是可用的。那么链接器会选择其中一个库而不是另一个。链接器会首先搜索由`-L`选项指定的每个目录，然后是标准目录。当链接器找到一个包含`libtest.a`或`libtest.so`的目录时，链接器就会停止搜索该目录。如果目录中只存在这两个变体之一，链接器将选择该变体。否则，除非你显式指示，否则链接器将选择共享库。你可以使用`-static`选项来要求使用静态存档。例如，即使共享库可用，下行命令也会使用`libtest.a`：

```
% gcc -static -o app.o -L. -ltest
```

`ld`命令显示链接到可执行文件中的共享库。这些库在运行可执行文件时必须是用的。请注意，`ld`还需要一个名为`ld-linux.so`的额外库，它是GNU/Linux动态链接机制的一部分。

#### 使用 LD_LIBRARY_PATH

当你的程序与共享库链接时，链接器不会将共享库的完整路径放入生成的可执行文件中。相反，它只放置了共享库的名称。当程序实际运行时，系统会搜索并加载该共享库。系统默认只搜索`/lib`和`/usr/lib`。如果链接到你程序中的共享库安装在这些目录之外，系统将无法找到它，并拒绝运行该程序。

解决此问题的一种方法是在链接程序时使用`-Wl,-rpath`选项。假设你使用它：

```
% gcc -o app.o -L. -ltest -Wl,-rpath,/usr/local/lib
```

那么当运行`app`时，系统将在`/usr/local/lib`中搜索任何所需的共享库。

解决此问题的另一种方法是在运行程序时设置`LD_LIBRARY_PATH`环境变量。像`PATH`环境变量一样，`LD_LIBRARY_PATH`是由冒号分隔的目录列表。例如，如果`LD_LIBRARY_PATH`为`/usr/local/lib:/opt/lib`，则会搜索标准的`/lib`和`/usr/lib`目录。你还需要注意，如果你设置了`LD_LIBRARY_PATH`，链接器在搜索用于构建可执行文件的`-l`选项所指定的目录外，还会搜索所给出的目录。

#### 2.3.3 标准库

如果你在链接程序时没有指定任何库，它几乎肯定使用了共享库。这是因为`GCC`会自动为你链接标准C库`libc`。标准C数学函数没有包含在`libc`中；相反，它们在一个单独的库`libm`中，你需要显式指定它。例如，要编译并链接一个使用`sin`和`cos`等三角函数的程序`compute.c`，你必须调用：

```
% gcc -o compute compute.c -lm
```

如果你编写了一个C++程序并使用`c++`或`g++`命令进行链接，也将自动获得标准C++库`libstdc++`。

#### 2.3.4 库依赖

一个库会依赖于另一个库。例如，许多GNU/Linux系统包含了`libtiff`，这是一个包含读取和写入TIFF格式图像文件函数的库。该库反过来使用了`libjpeg`（JPEG图像例程）和`libz`（压缩例程）。

列表2.9显示了一个使用`libtiff`打开TIFF图像文件的极小程序。

#### 列表 2.9 (tiffest.c) 使用 libtiff

```c
#include <stdio.h>
#include <tiff.h>

int main (int argc, char** argv)
{
    TIFF* tiff;
    tiff = TIFFOpen (argv[1], "r");
    TIFFClose (tiff);
    return 0;
}
```

你可能会在某些在线文档中看到引用`LD_RUN_PATH`。不要相信你读到的；这个变量在GNU/Linux下实际上没有任何任何作用。

### 2.3 编写与库

将此源文件保存为`tifftest.c`。要编译它并与`libtiff`链接：

```
% gcc -o tifftest tifftest.c -ltiff
```

默认情况下，这会选取位于`/usr/lib/libtiff.so`的`libtiff`共享库版本。由于`libtiff`使用了`libjpeg`和`libz`，这两个的共享库版本也被引入了（共享库可以指向依赖它们的其他共享版本）。要验证这一点，请使用`ldd`命令：

```

libc.so.6 => /usr/lib/libc.so.6 (0x40000000)
libjpeg.so.62 => /usr/lib/libjpeg.so.62 (0x40000000)
libz.so.1 => /usr/lib/libz.so.1 (0x00000000)
ld-linux.so.2 => /lib/ld-linux.so.2 (0x00000000)
```

`ld`命令显示链接到可执行文件中的共享库。这些库在运行可执行文件时必须是可用的。注意`ld`还需要一个名为`ld-linux.so`的额外库，它是GNU/Linux动态链接机制的一部分。

#### 2.3.6 动态加载与卸载

有时你可能在运行时加载某些代码，而不显式链接这些代码。例如，考虑一个支持“插件”模块的应用程序，如Web浏览器。浏览器允许第三方开发者创建插件提供额外功能。第三方开发者创建共享库并放置在已知位置。浏览器随后会自动加载这些库中的代码。

这种功能在Linux下通过使用`dlopen`函数实现。你可以通过调用`dlopen`来打开名为`liblibest.so`的共享库：

```
dlopen ('liblibest.so', RTLD_LAZY);
```

### 2.3 编写与使用库

（第二个参数也可以是一个标志，指示如何绑定共享库中的符号。如果你需要更多信息，可以查阅`dlopen`的在线页面，但`RTLD_LAZY`通常是你需要的设置。）要使用动态加载函数，请包含`<dlfcn.h>`头文件并使用`-dl`选项链接以引入`libdl`库。

该函数的返回值是一个`void *`，用作共享库的句柄。你可以将此值传递给`dlsym`函数，以获取命名为`my_function`的函数地址。例如，`libtest.so`定义了一个函数，你可以这样调用它：

```c
void* handle = dlopen("libtest.so", RTLD_LAZY);
void (*test()) = dlsym(handle, "my_function");
test();
dlclose(handle);
```

`dlopen`系统也可以用于获取共享库中静态变量的指针。

`dlopen`和`dlsym`在执行失败时都会返回`NULL`。在这种情况下，你可以调用`dlerror`（不带参数）来获取描述问题的可读错误消息。

`dlclose`会卸载共享库。从技术上讲，`dlopen`只有在库尚未加载时才会加载它。如果库已经加载，`dlopen`仅仅会增加库的引用计数。同样，`dlclose`会减少引用计数，并仅在引用计数达到零时才卸载库。

如果你在用C++编写共享库中的代码，你可能希望使用`extern "C"`链接规范符来声明你计划访问的函数和变量。例如，如果C++函数`my_function`在一个共享库中，而你想通过`dlsym`访问它，你应该这样声明它：

```cpp
extern "C" void foo();
```

这可以防止C++编译器对函数`foo`进行符号修饰（mangling），修饰会将函数名变为一个不同的、看起来奇怪的名字，该名字编码了关于函数的额外信息。C编译器不会进行符号修饰；它将使用你提供给函数或变量的任何名称。
