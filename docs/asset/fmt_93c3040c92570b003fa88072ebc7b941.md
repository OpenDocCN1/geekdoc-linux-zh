## 电子邮件 (E-Mail)

电子邮件是互联网上使用最广泛的应用程序。它被认为是一种异步通信系统，在邮件消息发送后，它会一直留存在接收者的计算机上，直到接收者登录并检索消息。本节重点关注电子邮件的许多方面，包括邮件消息的结构、随邮件发送二进制数据（如图形文件）、电子邮件地址、消息如何在互联网上传输以及常用的终端用户邮件程序。

## 邮件消息的组件

邮件消息由两部分组成：消息头部（header）和消息正文（body）。头部包含如谁发送了消息以及何时发送等信息。正文包含实际的消息文本。有些人会在消息结束处添加一个可选的第三部分，称为“签名（signature）”。这些邮件部分的每个将在后面的章节中详细描述。

### 消息头部

消息头部在顶部包含几行，格式为“关键词”：值对。对于使用 `mail` 或 `mailx` 程序发送给同一本地 UNIX 主机用户的消息，其结构非常简单。例如：

```
From smithj Thu Apr 24 00:42 EDT 1997
To: jonest
Subject: Code Review Meeting
Status: R
```

（正文：请计划参加明天上午 10:00 的代码审查会议。）

然而，最终通过互联网传输的邮件头部消息要复杂得多。例如：

```

Flags: 000000000000

happy.phones.com (8.6.5/QC-BSD-2.1) via SMTP;

Cc: james@foobar.com

```

消息头部是由被称为“邮件代理（MUA）”和“邮件传输代理（MTA）”的程序自动构建的。事实上，头部中某些项目（如抄抄和回执通知）的存在取决于邮件本身的复杂性，这些电子邮件的组件将在稍后的章节中讨论。某些头部需要一些解释。这是第一行：

```
From nihil@eniac.seas.void Thu Apr 24 08:15:01 1997
```

这一行是由本地系统上的 MTA (`sendmail`) 添加的。它被用作快速摘要，注明谁发送了消息以及时间。当许多系统将用户的所有消息存储在单个文件中时，这种摘要也用于区分一条消息的结束和下一条的开始。对于大多数程序来说，这意味着如果你尝试将其放在其之前，它就不会错误地指示新消息的开始。

```
Flags: 000000000015
```

`Flags` 字段是 Berkeley mail 特有的，也由本地程序添加。

日期：1997年4月24日，星期四 11:14:44 EST

这是我们生成的日期。EST 是东部标准时间。

```
In-Reply-To: <CMM.342342.rdipippold@happy.phones.com>
from "Ron Pippold" at Apr 24, 97 1:00 am
```

此消息是对 Ron Pippold 发送的上述 ID 消息的回复。

```
X-Mailer: ELM [version 2.3 PL11-void1.13]
```

发送者使用 ELM 邮件系统发送了此邮件。这些信息在调试时也很有用。

```
Mime-Version: 1.0
Content-Type: text/plain; charset=US-ASCII
Content-Transfer-Encoding: 7bit
```

本章讨论了 MIME 格式。简而言之，这表示消息仅包含 7 位文本。

```
Content-Length: 10234
```

消息正文（此处未显示）的长度为 10,234 个字符。

还有其他一些头部项可能偶尔对你有用：

```
Bcc: recipient
```

Bcc 是密密抄。这类似于 Cc 头，不同之处在于，To 和 Cc 头中列出的收件者不知道该消息已通过特定的 Bcc 头发送给他们。使用此项可以发送消息的副本，而不让其他人知道你正在发送它。

```
Encrypted: software keyhelp
```

这表示消息正文已用加密软件加密，keyhelp 选项有助于选择解码所需的密钥。注意，头部本身不能加密，因为它们包含了关键的路由信息。

头部中使用的日期格式如下：

```
Thu, 24 Apr 97 11:44 -0500
```

星期（Thu）是可选的。时间以当地时间的 24 小时制（00--23:59）给出。最后一个字段是几种格式之一的时区。

| UT 或 GMT | 通用标准时间/格林尼治标准时间 |

| :--- | :--- |

| EST 或 EDT | 东部时区 |

| CST 或 CDT | 中部时区 |

| MST 或 MDT | 山地时区 |

# PST 或 PDT 太平洋时区

- -HHMM 比 UT 早 HH 小时 MM 分钟

- +HHMM 比 UT 晚 HH 小时 MM 分钟

RFC 822 文档记录了互联网文本消息的标准格式，其中包含了关于头部格式的信息。

> 注意：在本章中，将多次引用 RFC。RFC 代表“请求意见”（Request Comments），是研究和开发社区用于记录构成互联网基础的标准手段。例如，RFC 821 文档了用于发送邮件的 SMTP 协议。

## 消息正文

消息正文通过一个空行与消息头部分开。消息正文包含消息的实际文本。在这里，你可以自由地向收件者输入任何内容。不过，有几个建议的指南需要遵循。

许多系统只能处理最多 65 个字符的行。保持每行的字符数少于该数量通常是一个好主意。此外，尝试混合使用大写和小字母。如果你全部使用大写字母，看起来就像你在大大叫！此外，消息正文有时包含一种被称为表情符号的特殊字符序列，例如 :)。如果你侧着看这个表情符号，它看起来像一个笑脸。

> 注意：在与其他交流时，我们的肢体语言、面部表情和语气为我们的意图被理解提供了框架。这在电子邮件中是不可能的，因此使用了称为表情符号的特殊字符来点饰简短的情绪描述。以下是你可能会看到的某些表情符号列表及其通常含义：
> - -:-) 幽默、笑、友好
> - :( 悲伤、愤怒、不悦
> - :-O 惊讶
> - -:$ 言出必行（把你的钱付诸行动）
> - -:- 带着微笑所说
> - :-T 绷着脸
> - :-| 无表情
> - -(:-D 嘴很大（或笑得开心）

不过度使用这些符号被认为是一种良好的做法。

## 签名

某些电子邮件以可选的签名结尾。签名是关于发送消息者身份的简短描述，例如全名、电话和传真号码，以及电子邮件地址。有些签名还用 ASCII 字符绘制的图片来装饰这些信息。将签名限制在五行或以内被认为是良好的做法。大多数现代邮件程序都可以配置为自动将签名附加到消息末尾。

## 发送二进制数据

在互联网上传输电子邮件的协议（SMTP）仅允许传输 ASCII 文本字符。因此，不支持直接传输音频或视频文件等二进制文件。发送二进制数据的优方法是使用支持多用途互联网邮件扩展（MIME）的邮件程序。这将在后面的章节中讨论。在 MIME 出现之前，一种规避此限制的技术是在使用如 elm 或 quail 等邮件程序发送之前，先将每条数据编码为 ASCII 文本。在 UNIX 系统上，使用 `uencode` 程序将二进制文件转换为 ASCII。例如，可以使用以下命令向远程用户发送文件：

```
uencode picture.tif picture.tif | mailx -s "image file" gcobb@net.com
```

域名。域名的每个部分都用点隔开。例如，注意以下 Internet 地址：

`ccarter@minn.com`

域名的最右侧部分 `.com` 表示这是一个商业站点。以下列表显示了美国最流行的域名：

| com | 商业 |

|---|---|

在美国境外，站点可以注册为其他国家代码，例如代表英国的 "ca" "uk" 等。此外，也可以使用两个字母的 ISO 国家代码。例如，代表加拿大的 "ca"。

在顶级域名（edu、org 等）的左侧可以出现任意数量的逻辑子域名。这些子域名用于更详细地指定收件人所在的主机名称。根据 Internet 惯例，`Carter@Minn.com`、`cARTER@Minn.com` 和 `carter@Minn.COM` 是等价。为了保持一致性，大多数现代邮件软件会忽略域名中用户名部分的大小写。然而，这不是强制要求。因此，保留用户名的大小写被认为是一种良好的做法，以防在使用旧邮件软件的收件者系统中出现问题。

一种旧的地址方案被称为 UUOCP bang-path 地址（bang 是计算机术语，指感叹号）。尽管如此，你可能看不到这种格式的地址，在这里提到它是出于历史原因。在这种方案中，你希望你发送的邮件通过特定的路径。例如，注意以下用户 katherine 的地址：

```
comp01!comp02!comp03!katherine
```

这表示邮件将通过命名为 `comp01`、`comp02` 和 `comp03` 的系统。一旦消息送达 `comp03`，它将被投递给 `katherine`。

## 邮件如何在 Internet 上路由

在将 `username@domain` 格式的 Internet 地址用于传输之前，必须将其转换为 IP 地址。IP 地址由四个用点隔开的数字组成，用于唯一标识 Internet 上的主机。例如，“128.254.17.7” 就是一个 IP 地址的示例。将 Internet 地址转换为 IP 的过程由 Internet 上称为域名服务器的系统完成。

当通过 Internet 发送消息时，它是数据包的形式的形式，每个数据包包含消息的一部分。每个数据包还包含目的 IP 地址。数据包使用 IP 协议在 Internet 上传输。Internet 上称为路由器的专用网络系统会检查每个数据包中的 IP 地址，并将其路由到适当的主机。会考虑各种备份上的网络流量等许多因素，以确定最佳路径。事实上，来自同一封邮件的数据包可能会采取不同的路由。所有数据包在接收主机上使用 TCP 协议按正确顺序重新组合。

## 向其他网络发送邮件

除了通过 Internet 发送电子邮件之外，还可以将邮件发送到其他网络，例如在线服务。

一个巨大的优势是连通性。只要邮件服务增加一台计算机（称为网关），可以从其系统传输到 Internet 并反之亦然，用户就可以与该服务上的任何人或 Internet 上的任何人交换邮件。那里有很多人。许多新服务现在都提供某种网关。即使是对于掌握这些可能性方面有些落后的 Prodigy，现在也有了一个。

Genic 不需要安装一个特殊的网关来分别与 Prodigy、CompuServe、SprintMail 和 BubbleNet 通信，它只需要为 Internet 建立并维护一个单一的网关即可，所有流量都通过该网关流动。考虑到大多数在线服务实施此类升级的速度，要求单一网关是一件好事。

所以，现在任何人都可以向任何地方发送电子邮件了！嗯，并不完全是。

### 地址问题

事实证明，Internet 的服务保留了它们的账户名和邮件邮箱。CompuServe 的账户地址就像明信片一样过时，但由于公司的投资，它不会改变。你可以直接使用 Internet 风格的地址向 CompuServe 账户发送邮件。CompuServe ID 看起来如下所示：

`112233,44`

在 Internet 地址中，逗号分隔列表成员，因此你可以在 Compuverse 地址中使用逗号。有一种解决办法（使用点代替逗号），但你必须预先知道这一点。尝试向系统发送邮件的人必须处理这些特殊之处。因此有了这一节，它详细介绍了主要网络之间需要进行的转换。

再次，电子邮件地址看起来如下所示：

```
user@machine.site.domain
```

任何指向邮件网关的地址都会是此主题的某种变体（大小）。

### X-400 地址

Internet 使用正式称为 RFC-822 的地址方案。许多从事电子邮件的大型商业服务使用称为 X.400 网关的设备与 Internet 通信。这些地址看起来如下：

```
/A=value/B=value/C=value
```

这种风格在 Internet 上是可以使用的，因为 RFC-822 允许使用斜杠和等号。事实上，存在相反的问题：RFC-822 允许在地址中使用许多字符，这些字符会导致 X.400 网关陷入混乱，包括 @ 符号。由于它出现在所有 Internet 风格的邮件地址中，这是一个显而的问题。

每当 Internet 地址包含特殊字符时，你需要使用以下转换表：

| Internet | 转换 |

|---|---|

| @ | a |

| % | p |

| ! | q |

| - | u |

| " | l |

| ) | r |

| * | s |

关于 Internet 邮件（Internet Mail）的站点：

来自 Internet（From）：使用以下地址格式：

```
userid@delphi.com
```

示例：`jjones@delphi.com`

发往 Internet（To）：不需要任何特殊操作；直接使用标准的 Internet 格式即可：

```
userid@domain
```

示例：`bsmith@wubba.edu`。

FidoNet FidoNet 是一个大型国际 BBS——可以说是是 BBS 爱好者的 Internet。它虽然不像 Internet 那么快，但通常非常便宜，而且你所在的地区通常有一个 FidoNet BBS。

由于它是通过线路运行的，BBS 运营商会对任何传输的邮件收取长途费用，因此请不要向 FidoNet 站点发送大容量消息。许多站点甚至会将你的消息截断为 8,000 或 16,000 字节，这样你的大部分消息就能通过。

来自 Internet（From）：首先，你需要知道收件者所在的 BBS 的网络地址。它的格式类似于 Z/N/P。然后将邮件发送到以下地址：

```
userid@pP.FF.nN.ZZ.fidonet.org
```

如果 BBS 网络包含一个 P 组件，请从地址中删除 pP 部分。对于 userid，请将任何非字母数字的字符（如空格）替换为点（.）。

示例：`Jim_Jones@p4.f3.n2.z1.fidonet.org`
