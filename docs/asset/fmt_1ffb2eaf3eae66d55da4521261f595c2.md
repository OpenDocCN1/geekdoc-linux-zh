
线程可能尝试通过对互斥锁调用 `pthread_mutex_lock` 来尝试锁定它。如果互斥锁处于未锁定的状态，它将变为锁定状态且函数立即返回。如果互斥锁已被另一个线程锁定，`pthread_mutex_lock` 将阻塞执行，并直到另一个线程解锁该互斥锁后才会返回。同时可以有多个线程阻塞在一个锁定的互斥锁上。当互斥锁被解除阻塞时，阻塞的线程中只有一个（不可预测地选择）会被解除阻塞并允许锁定互斥锁；其他线程保持阻塞状态。

调用 `pthread_mutex_unlock` 会解锁互斥锁。此函数应该始终从锁定互斥锁的同一个线程中调用。

列表 4.11 显示任务队列示例的另一个版本。现在队列由互斥锁保护。在访问队列之前，线程首先锁定互斥锁。只有当检查队列和移除任务的整个序列完成后，才会解锁互斥锁。这防止了之前描述的竞态条件。

列表 4.11 (`job-queue2.c`) 任务队列线程函数，受互斥锁保护

```
#include <stdlib.h>
#include <pthread.h>

struct job {
  /* 链表的链接字段。 */
  struct job* next;

  /* 其他需要执行的工作字段... */
};

/* 待处理任务的链表。 */
struct job* job_queue;

/* 保护 job_queue 的互斥锁。 */
pthread_mutex_t job_queue_mutex = PTHREAD_MUTEX_INITIALIZER;
```

### 4.4 同步与临界区

```
/* 处理队列中的任务直到队列为空。 */
void* thread_function(void* arg) {
  while (1) {
    struct job* next_job;

    /* 锁定任务队列上的互斥锁。 */
    pthread_mutex_lock(&job_queue_mutex);
    /* 现在可以安全检查队列是否为空。 */
    if (job_queue == NULL) {
      next_job = NULL;
    } else {
      /* 获取下一个可用的任务。 */
      next_job = job_queue;
      /* 从列表中移除此任务。 */
      job_queue = job_queue->next;
    }
    /* 解锁任务队列上的互斥锁，因为我们现在已经处理完该队列了。 */
    pthread_mutex_unlock(&job_queue_mutex);

    /* 队列是否为空？如果是，则结束线程。 */
    if (next_job == NULL)
      break;

    /* 执行工作。 */
    process_job(next_job);
    /* 清理。 */
  }
  return NULL;
}
```

所有对 `job_queue`（共享数据指针）的访问都发生在调用 `pthread_mutex_lock` 和调用 `pthread_mutex_unlock` 之间。存储在 `ext_job` 中的任务对象在这一区域之外的访问仅是在它从队列中移除之后，因此对其他线程是不可见的。

请注意，如果队列为空（即 `job_queue` 为 `null`），我们不会立即跳出循环，因为这会导致互斥锁永久锁定，并防止任何其他线程再次访问任务队列。相反，我们通过将 `next_job` 设置为 `null` 来记住这一点，并且在解锁互斥锁后才跳出循环。

使用互斥锁锁定 `job_queue` 并不是自动的；这需要你自己在访问该变量之前添加互斥锁的锁定代码，并在之后解锁它。例如，向任务队列添加任务可能看起来如下：

```
{
  pthread_mutex_lock(&job_queue_mutex);
  new_job->next = job_queue;
  job_queue = new_job;
  pthread_mutex_unlock(&job_queue_mutex);
}
```

#### 4.4.3 互斥锁死锁

互斥锁提供了一种允许一个线程阻塞另一个线程执行的机制。这引发了一类新错误的可能性，称为死锁。当一个或多个线程正在等待某些永远不会发生的事情时，就会发生死锁。

当同一个线程尝试连续锁定同一个互斥锁时，可能会发生简单类型的死锁。这种情况下的行为取决于使用的是哪种互斥锁。存在三种互斥锁：

- 锁定快速互斥锁（默认类型）会导致死锁发生。尝试锁定互斥锁会阻塞，直到互斥锁被解锁。但由于锁定互斥锁的线程阻塞在同一个互斥锁上，该锁永远无法被释放。

- 锁定递归互斥锁（`recursive mutex`）不会导致死锁。递归互斥锁允许同一个线程安全地锁定多次。互斥锁会记录持有锁的线程调用了多少次 `pthread_mutex_lock`；该线程在释放锁之前必须进行相同次数的 `pthread_mutex_unlock`。

- 锁定错误检查互斥锁（`error-checking mutex`）不会导致死锁，但如果线程尝试锁定它已经持有的互斥锁，它将返回错误。

当两个或多个线程等待对方释放锁时，也会发生死锁。例如，如果线程 A 锁了互斥锁 1 然后尝试锁互斥锁 2，而线程 B 锁了互斥锁 2 然后尝试锁互斥锁 1，两者都无法继续。这是一个经典的死锁场景。为了避免这种情况，必须始终以相同的顺序获取多个互斥锁。

#### 4.4.4 非阻塞互斥锁测试

有时，测试互斥锁是否被锁定而不实际阻塞它是很有用的。例如，线程可能需要锁定互斥锁，但如果互斥锁已被锁定，则执行其他工作。由于 `pthread_mutex_lock` 会阻塞直到互斥锁解锁，因此需要另一个函数。

GNU/Linux 为此提供了 `pthread_mutex_trylock`。如果你对未锁定的互斥锁调用 `trylock`，将像调用 `pthread_mutex_lock` 一样锁定互斥锁，且 `trylock` 将返回零。然而，如果互斥锁已被另一个线程锁定，`trylock` 不会阻塞。它会立即返回错误代码 `BUSY`。其他线程的锁不受影响。你可以再次尝试锁定。

#### 4.4.5 用于线程的信号量

在前面的示例中，多个线程从队列中处理任务，主函数处理下一个任务直到没有任务为止并退出线程。如果所有任务都预先入队或者新任务入队的速度快线程处理的速度，这种方案是有效的。然而，如果线程运行得太快，队列为空，线程将退出。如果之后入队了新任务，可能没有剩余线程来处理它们。我们可能需要的机制是在队列为空时阻塞线程，直到有可用任务

信号量提供了一种方便的方法。信号量是一种用于同步多个线程的计数器。通过互斥锁，GNU/Linux 保证检查或修改信号量的值可以安全进行，不会产生竞态条件。

每个信号量有一个计数器，是非负整数。信号量支持两个基本操作：

- 等待操作（`wait`）将信号量的值减1。如果值已经为零，该操作将阻塞直到信号量的值变为正数（由于其他线程的操作）。当信号量的值变为正数时，它被减1且等待操作返回。

- 发布操作（`post`）将信号量的值加1。如果信号量之前为零且有线程阻塞在该信号量的等待操作上，其中一个线程将被解除阻塞，其等待操作将完成（这将使信号量的值回到零）。

## 第 4 章：线程

注意，GNU/Linux 提供了两种略有不同的信号量实现。我们在这里描述的是 POSIX 标准信号量实现。在线程之间通信时，请使用这些信号量。另一种用于进程间通信的实现详见第 5.2 节“进程信号量”。如果你使用信号量，请包含 `<semaphore.h>`。

信号量由 `sem_t` 变量表示。在使用它之前，你必须使用 `sem_init` 函数对其进行初始化，传递指向 `sem_t` 变量的指针。第二个参数应该是 0，第三个参数是信号量的初始值。如果你不再需要某个信号量，最好用 `sem_destroy` 将其销毁。

要等待信号量，使用 `sem_wait`。要向信号量发送信号，使用 `sem_post`。还提供了一种非阻塞等待 `sem_trywait`。这与 `pthread_mutex_trylock` 类似——如果因为信号量的值为0 而导致阻塞，该函数将立即返回错误 `EAGAIN`，而不是发生阻塞。

GNU/Linux 还提供了一个获取信号量取值的函数 `sem_getvalue`，它将值放入其参数指向的 `int` 变量中。你不应该使用从此函数获取的信号量值来做出等待或发送信号的决策，因为这可能导致竞态条件。另一个线程可能会在调用 `sem_getvalue` 和调用另一个信号量函数之间更改信号量的值。请使用原子性的发送（`post`）和等待实例。

回到我们的任务示例，我们可以使用信号量来统计队列中等待的任务数量。`enqueue_job` 函数使用信号量控制队列。

列表 4.12 (`job-queue.c`) 信号量控制的任务队列

```c
#include <stdlib.h>
#include <pthread.h>
#include <semaphore.h>

struct job {
    /* 链表使用的 next 字段。 */
    struct job* next;

    /* 其他描述待执行任务的字段... */
};

/* 待处理任务的链表。 */
struct job* job_queue;

/* 保护 job_queue 的互斥锁。 */
pthread_mutex_t job_queue_mutex = PTHREAD_MUTEX_INITIALIZER;

/* 统计队列中任务数量的信号量。 */
sem_t job_queue_count;

/* 对任务队列进行一次初始化。 */
void initialize_job_queue () {
    /* 队列初始为空。 */
    job_queue = NULL;
    /* 初始化统计队列中任务的信号量。其
       初始值应为 0。 */
    sem_init(&job_queue_count, 0, 0);
}

/* 处理队列中的任务直到队列为空。 */
void* thread_function(void* arg) {
    while (1) {
        struct job* next_job;

        /* 等待信号量。如果它的值为正数，
           表示队列不空，则计数减 1。
           如果队列为空，则阻塞直到有新任务入队。 */
        sem_wait(&job_queue_count);

        /* 锁定任务队列互斥锁。 */
        pthread_mutex_lock(&job_queue_mutex);
        /* 因为有信号量，我们知道队列不空。获取
           下一个任务。 */
        next_job = job_queue;
        /* 从列表中移除该任务。 */
        job_queue = job_queue->next;
        /* 解锁任务队列互斥锁，因为我们暂时完成了
           对队列的操作。 */
        pthread_mutex_unlock(&job_queue_mutex);

        /* 执行工作。 */
        process_job(next_job);
        /* 清理。 */
        free(next_job);
    }
    return NULL;
}

/* 将新任务添加到任务队列的前端。 */
void enqueue_job (job-specific data) {
    struct job* next_job;

    /* 分配一个新任务。 */
    next_job = (struct job*) malloc(sizeof(job));
    /* 在这里设置任务的其他字段... */

    /* 在访问队列之前锁定任务队列互斥锁。 */
    pthread_mutex_lock(&job_queue_mutex);
    /* 将新任务放在队列头部。 */
    next_job->next = job_queue;
    job_queue = next_job;
    /* 向信号量发送信号，表示另一个任务可用。如果
       线程正在阻塞并等待信号量，则其中一个
       将被唤醒以处理该任务。 */
    sem_post(&job_queue_count);
    /* 解锁互斥锁。 */
    pthread_mutex_unlock(&job_queue_mutex);
}
```

### 4.4 同步与临界区

#### 4.4.6 条件变量

我们已经展示了如何使用互斥锁保护变量免受两个线程的同时访问，以及如何使用信号量来实现共享计数器。条件变量是 GNU/Linux 提供的一种线程同步设备；通过它，你可以实现更复杂的线程执行条件。

假设你编写了一个无限循环的线程函数，在每次循环中执行某些工作。然而，线程循环需要由一个标志来控制，只有当标志被设置时循环才运行；当标志未设置时，循环暂停。列表 4.13 显示了你如何通过循环自旋来实现这一点。在循环的每次迭代中，线程函数都会检查标志是否被设置。由于多个线程会访问该标志，因此需要通过互斥锁来保护。这种实现是正确的，但效率低下。当标志未设置时，线程函数会花费大量的 CPU 资源来反复锁定和解锁互斥锁。你真正想要的是让线程在标志未设置时进入睡眠。

列表 4.13 (`spin-condvar.c`) 简单的条件变量实现

```c
#include <pthread.h>

int thread_flag;
pthread_mutex_t thread_flag_mutex;

void initialize_flag() {
    pthread_mutex_init(&thread_flag_mutex, NULL);
    thread_flag = 0;
}

/* 当标志设置时，在循环中调用 do_work。 */
void* thread_function(void* arg) {
    while (1) {
        int flag_is_set;

        /* 使用互斥锁保护标志。 */
        pthread_mutex_lock(&thread_flag_mutex);
        flag_is_set = thread_flag;
        pthread_mutex_unlock(&thread_flag_mutex);

        if (flag_is_set) {
            do_work();
            /* 否则什么都不做，再次循环。 */
        }
    }
    return NULL;
}

/* 将线程标志设置为 FLAG_VALUE。 */
void set_thread_flag(int flag_value) {
    /* 使用互斥锁保护标志。 */
    pthread_mutex_lock(&thread_flag_mutex);
    thread_flag = flag_value;
    pthread_mutex_unlock(&thread_flag_mutex);
}
```

条件变量允许你实现线程执行的条件，反之，也是线程阻塞的条件。只要可能更改条件状态的线程都正确使用条件变量，Linux 就能保证当条件变化时，阻塞在该条件的线程会被唤醒。

与信号量一样，线程可以等待条件变量。如果线程 A 等待条件变量，它会被阻塞，直到另一个线程 B 信号条件变量。与信号量不同，条件变量没有计数器或内存；线程 A 必须在 B 发送信号之前等待条件变量。如果 B 在 A 等待之前发送了信号，信号就会丢失。

为了解决这个问题，我们需要一个锁将标志和条件变量一起固定下来。GNU/Linux 正好提供了这种机制。每个条件变量必须与互斥锁配合使用，以防止这种竞态条件。使用这种方案，线程函数遵循以下步骤：

- 线程函数中的循环锁定互斥锁并读取标志值。

- 如果标志已设置，则解锁互斥锁并执行工作函数。

- 如果标志未设置，则原子地解锁互斥锁并等待条件变量。

这里的关键特征在于第 3 步，GNU/Linux 允许你原子地解锁互斥锁并等待条件变量，而没有其他线程干预的可能性。这消除了在线程函数测试标志值和等待条件变量之间，另一个线程更改标志值并发送条件变量信号的可能性。

## 4.4 同步与临界区 89

条件变量由 `pthread_cond_t` 实例表示。请记住，每个条件变量必须配对一个互斥锁（`mutex`）。以下是操作条件变量的函数：

- `pthread_cond_init` 初始化条件变量。第一个参数是指向 `pthread_cond_t` 实例的指针。第二个参数是指向条件变量属性对象的指针，在 GNU/Linux 下会被忽略。

互斥锁必须单独初始化，如第 4.4.2 节“互斥锁”所示：

- `pthread_cond_signal` 向条件变量发送信号。一个阻塞在条件变量上的线程将被解除阻塞。如果没有其他线程阻塞在条件变量上，则该信号被忽略。参数是指向 `pthread_cond_t` 实例的指针。

类似的调用 `pthread_cond_broadcast` 会唤醒所有阻塞在条件变量上的线程，而不仅仅是一个。

- `pthread_cond_wait` 阻塞调用者，直到条件变量接收到信号。参数是指向 `pthread_cond_t` 实例的指针。第二个参数是指向 `pthread_mutex_t` 实例的指针。

当调用 `pthread_cond_wait` 时，调用线程必须已经锁定了该互斥锁。该函数会原子地释放互斥锁并阻塞在条件变量上。当条件变量被信号且调用线程解除阻塞时，`pthread_cond_wait` 会自动重新获取互斥锁。

每当你的程序执行可能改变你用条件变量所保护的条件含义的操作时，都应该执行以下步骤。在我们的示例中，条件是线程标志（`thread flag`）的状态，因此每当标志发生变化时，必须采取这些步骤：

1. 锁定与条件变量关联的互斥锁。

2. 执行可能改变条件含义的操作（在我们的示例中，设置标志）。

3. 根据所需的行为对条件变量发送信号或广播。

4. 解锁与条件变量关联的互斥锁。
