
- **Account expired**—An administrator can set an expiration time for a specific user account. If that user tries to log in after that time has passed, the user gets a message that the account has expired and cannot be used to log in.

During a successful authentication, pam_windbind acquires a ticket granting ticket (TGT) from the Kerberos server of Active Directory and stores it in the user’s credential cache. It also renews the TGT in the background without requiring any user interaction.

SUSE Linux Enterprise Desktop 10 supports local home directories for AD users. If configured through YaST, as described in “Configure a Linux Client for Active Directory,” user homes are created at the first login of a Windows (AD) user to the Linux client.

These home directories look and feel entirely the same as standard Linux user home directories and work independently of the AD domain controller.

Using a local user home, it is possible to access a user’s data on this local machine, even when the AD server is disconnected, provided the Linux client has been configured to perform offline authentication.

**Offline Service and Policy Support** Users in a corporate environment must have the ability to become roaming users, so they can, for example, switch networks or even work disconnected for some time.

To enable users to log in to a disconnected machine, extensive caching was integrated into the windbind daemon. The windbind daemon enforces password policies even in the offline state. It tracks the number of failed login attempts and reacts according to the policies configured in Active Directory.

Offline support is disabled by default and must be explicitly enabled in the YaST Domain Membership module.

As in Windows, when the domain controller has become unavailable, the user can still access network resources (other than the AD server itself) with valid Kerberos tickets that have been acquired before losing the connection.

Password changes cannot be processed unless the domain controller is online. While disconnected from the AD server, a user cannot access any data stored on this server.

When a workstation has become disconnected from the network entirely and attaches to the corporate network again later, SUSE Linux Enterprise Desktop 10 acquires a new Kerberos ticket as soon as the user has locked and unlocked the desktop.

## Configure a Linux Client for Active Directory

Before your client can join an AD domain, you must make some adjustments to your network setup to ensure a flawless interaction of client and server. These adjustments affect:

- DNS
- NTP
- DHCP
- Firewall
- AD Account

![](img/9129877170834ca9d5fdac5319bf5f12_492_0.png)

**DNS** Configure your client machine to use a DNS server that can forward DNS requests to the AD DNS server. Alternatively, configure your machine to use the AD DNS server as the name service data source.

**NTP** To succeed with Kerberos authentication, the client must have set its time accurately. It is highly encouraged to use a central NTP time server for this purpose (this can also be the NTP server running on your Active Directory domain controller).

If the clockskew between your Linux host and the domain controller exceeds a certain limit, Kerberos authentication fails and the client is logged in only using the weaker NTLM (NT LAN Manager) authentication.

**DHCP** If your client uses dynamic network configuration with DHCP, configure DHCP to provide the same IP and hostname to the client. If possible, use static IP addresses to be on the safe side.

**Firewall** To browse your network neighborhood, either disable the firewall entirely or mark the interface used for browsing as part of the internal zone.

To change the firewall settings on your client, do the following:

1. Log in as root and start the YaST Firewall module.
2. Select Interfaces.
3. Select *your network interface* from the list of interfaces; then select Change.
4. Select Internal Zone and apply the settings by selecting OK.
5. Complete the firewall settings by selecting Next; then select Accept.

To disable the firewall, set Service Start to **Manually**. Exit the Firewall module by selecting Next; then select Accept.

**AD Account** You cannot log in to an AD domain unless the AD administrator has provided you with a valid user account for this domain. Use the AD username and password to log in to the AD domain from your Linux client.

Join an existing AD domain during installation or by later activating SMB user authentication with YaST in the installed system.

![](img/9129877170834ca9d5fdac5319bf5f12_493_0.png)

Currently only a domain administrator account, such as Administrator, can join SUSE Linux Enterprise Desktop 10 into Active Directory.

To join an AD domain in a running system, do the following:

1. Log in as root and start **YaST**.
2. Select Network Services > Windows Domain Membership.

A Windows Domain Membership dialog appears, as shown in Figure 13-8.

If you enter the short name of your domain (also known as the pre-Windows 2000 domain name), YaST must rely on NetBIOS name resolution instead of DNS to find the correct domain controller.

## Log In to an AD Domain

If your machine has been configured to authenticate against Active Directory and you have a valid Windows user identity, you can log in to your machine using the AD credentials.

Login is supported for both desktop environments (GNOME and KDE), the console, SSH, and any other PAM-aware application.

![](img/9129877170834ca9d5fdac5319bf5f12_495_1.png)

SUSE Linux Enterprise supports offline authentication, allowing you to remain logged in to your client machine even if the client machine is disconnected from the network.

### GDM and KDM

To authenticate a GNOME or KDE client machine against an AD server, do the following:

1. Select the *domain*.
2. Enter your Windows *username*.
3. Enter your Windows *password*.

SUSE Linux Enterprise Desktop 10 can be configured to create a user home directory on the local machine on first login of each AD authenticated user.

This allows users to access their Active Directory files and structure while utilizing the features of SUSE Linux Enterprise Desktop 10.

### Console Login

In addition to logging in to the Active Directory client machine using a graphical front end, you can also log in using the text-based console login. You can even log in remotely using SSH.

To log in to Active Directory using SLED 10, from a console, enter *DOMAIN\\user* at the login prompt and provide the appropriate *password*.

To remotely log in to your AD client machine using SSH, do the following:

1. At the login prompt, enter

`ssh DOMAIN\\user@host_name`

The domain and login delimiter “\\” is escaped with another \\ sign.
2. Enter the appropriate *password*.

### Change Passwords

SUSE Linux Enterprise Desktop 10 has the ability to help a user choose a suitable new password that meets the corporate security policy. The underlying PAM module retrieves the current password policy settings from the domain controller.

It informs about the specific password quality requirements a user account typically has by means of a message at login time. Like the Windows counterpart, SUSE Linux Enterprise Desktop 10 presents a message describing the following:

- Password history settings
- Minimum password length requirements
- Minimum password age
- Password complexity

The password change process cannot succeed unless all requirements have been successfully satisfied. Feedback about the password status is given both through the display managers and the console.

GDM and KDM provide feedback about password expiration and prompt for new passwords in an interactive mode. To change passwords in the display managers, just provide the password information when prompted to do so.

To change your Windows password, you can use the standard Linux utility, passwd, instead of having to manipulate this data on the server. To change your Windows password, proceed as follows:

1. Log in at the console.
2. Enter passwd.
3. Enter your *current password* when prompted to do so.
4. Enter the *new password*.
