# The Author Lied—It Didn't Work!

The kernel didn't fly, did you? Or it froze all the way and nothing worked, right? First and foremost, panic! This kind of problem happens to everyone, even the pros. After all, they're more likely to untested software. So don't worry—the situation is definitely repairable.

First, notice that a new entry was added to the boot loader configuration file (/boot/grub/menu.lst for GRUB legacy systems or /boot/grub/grub2.cfg or /boot/grub.cfg for GRUB 2 systems) and any existing entry was removed. This allows you to safely fall back to the old kernel that you know and boot into it. Reboot, and at the GRUB menu, select the name of the previous kernel that was known to work. This action should bring you back to a known system state.

Now go back to the kernel configuration and verify that all the options you selected work for your system. For example, did you accidentally enable support for the Sun UFS file system of Linux's ext4 file system? Did you set any options that depended on other being set? Remember view the informative Help screen for each kernel option in the configuration interface, making sure that you understand what each option does and what you need to do to make it work.

When you're sure your settings are right, step through the compilation process and restart. Creating an appropriate RAM file image (initramfs file) is also important (see mkinitramfs).

If you are running GRUB legacy, you simply need to edit the /boot/grub/menu.lst file, create an appropriate entry for your new kernel, and reboot and try again.
Don't worry—each time you compile a kernel, you'll get better at it. When do do make a mistake, it'll be easier to go back, find it, and fix it.
